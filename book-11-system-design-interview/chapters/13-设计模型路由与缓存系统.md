# 第十三章：设计模型路由与缓存系统：在质量、延迟与成本之间做出可解释的选择

一个模型网关表面上只是接收请求、选择模型、转发结果；当流量、模型和数据规模增长以后，它实际上承担了三个不同的职责：把一个业务任务翻译成可执行的模型契约，把请求分配给合适的计算资源，以及在结果仍然有效时避免重复计算。

这三个职责不能被一个“便宜模型优先”规则代替。合同助手中的普通术语解释可以交给小模型，但同一用户要求比较两份长合同、引用当前版本条款并调用审批工具时，模型选择、上下文版本和工具权限都已经改变。若把上一次回答直接复用，答案可能在字面上很流畅，却引用了已经撤销的条款；若把所有请求都送到最大模型，正确率可能上升，单位任务成本和排队延迟却会让产品无法交付。

本章以“砚桥合同助手”为贯穿案例。它服务多个企业租户，能够回答制度问题、比较合同、生成修改建议，并在获得授权后创建审批任务。系统同时接入小型本地模型、中型推理模型和大型高可靠模型；部分请求还需要 embedding、检索、工具和长上下文服务。我们会从请求契约开始，逐步构造路由器和缓存层，再处理版本、权限、热点、故障与审计。

本章讨论的是系统设计方法，不把任何一个模型品牌的宣传参数当成普遍事实。模型支持的上下文长度、工具格式、价格和服务稳定性都属于随版本变化的目录数据，必须由实际供应商文档、模型卡、基准测试和本地实测共同确认。

## 13.0 先明确问题：路由和缓存优化的是什么

### 13.0.1 从一次请求看出三种成本

对使用者来说，一次请求只有“发出问题”和“得到答案”两个动作。对平台来说，它至少包含：

1. 请求排队、鉴权和预处理的时间。
2. 模型读取输入并生成输出的计算。
3. 检索、重排序、工具调用、审核和重试产生的附加计算。
4. 结果持久化、计量、日志和缓存写入。

因此，“模型单价低”不等于“任务便宜”。一个便宜模型若经常需要重试或被更强模型接管，完整任务的成本可能高于一次成功完成的中型模型调用。类似地，命中缓存可以节约模型 token，却可能因为权限校验、缓存查询和失效同步而增加固定延迟。

### 13.0.2 三个必须分开的目标

砚桥首先把优化目标拆成三类：

- **质量目标**：回答是否解决任务、事实是否有证据、引用是否支持主张、工具动作是否正确。
- **服务目标**：首 token 延迟（TTFT）、每输出 token 延迟（TPOT）、端到端 p95/p99、可用性和流式稳定性。
- **经济目标**：每次请求成本、每个成功任务成本、GPU 利用率、缓存节省量和人工复核成本。

这三类目标之间通常存在张力。例如，扩大候选上下文可能提高召回，却增加 prefill 时间；把 temperature 设为零有助于精确缓存，但不保证事实正确；把低风险请求路由到小模型能够降低成本，但小模型在长文档或工具参数生成上的失败率可能更高。

平台的首要产物不是一个分数，而是一组可追溯的请求记录：当一次回答质量下降时，工程师能够知道它使用了哪个模型版本、哪个路由规则、哪些缓存、哪一版检索索引，以及最终有没有发生真实副作用。

### 13.0.3 运行目标应写成约束和代价

设请求为 (q)，路由候选为 (r)，它可能代表某个模型、模型加参数配置，或一条包含回退的执行路径。可以用下面的教学模型表达选择目标：

~~~math
J(r \mid q)
=
C(r \mid q)
+ \lambda_L L(r \mid q)
+ \lambda_R R(r \mid q)
+ \lambda_E E(r \mid q)
~~~

其中，(C) 是估计的完整任务成本，(L) 是延迟代价，(R) 是风险或不确定性代价，(E) 是资源消耗或碳排等额外代价，(lambda) 是业务权重。这个式子只是把取舍显式化；不同量纲不能直接相加，工程实现需要先归一化或把硬约束单独表达。

更稳妥的形式是：

~~~math
\begin{aligned}
\min_r\quad & J(r \mid q) \\
\text{s.t.}\quad
& \Pr(\text{task success} \mid q,r) \geq Q_{\min} \\
& \mathrm{p95Latency}(q,r) \leq L_{\max} \\
& r \text{ satisfies permission, modality, context and tool constraints}
\end{aligned}
~~~

这里的 (Pr(	ext{task success})) 不是模型卡上的综合评分，而是针对任务定义、数据切片和验收标准测得的成功率。若没有可靠的质量标签，就只能把这个量称为估计值，并在报告中列出不确定性。

### 13.0.4 小白需要先记住的一条边界

路由器回答的是“这次任务应该由谁完成”，缓存回答的是“这次计算结果能不能安全地复用”。前者主要是选择问题，后者主要是身份、版本和有效期问题。两者都可以降低成本，却不能凭空提高事实正确性。

因此，以下说法都不够严谨：

- “命中缓存，所以答案一定正确。”缓存只说明找到了旧结果，不能说明旧结果仍适用于当前任务。
- “最大模型一定最好。”它可能更强，但也可能更慢、更贵，或不具备当前所需的工具协议。
- “语义相似就可以复用。”相似问题可能因用户权限、时间、币种、合同版本或动作意图不同而必须重新计算。
- “路由失败就自动切换。”自动切换可能重复执行工具，也可能把不应跨供应商的数据送到另一个处理域。

## 13.1 请求契约：路由器先理解任务，再看模型

### 13.1.1 不要用一串 prompt 作为系统接口

如果路由器只接收最终 prompt，它很难区分以下情况：

- 用户是在询问公开定义，还是在处理一份受限合同。
- 请求需要只读回答，还是会创建审批任务。
- 输入是短文本，还是包含表格、扫描 PDF 和音频转写。
- 用户希望快速草稿，还是要求可审计、带条款引用的正式输出。
- 业务允许跨区域处理，还是数据必须留在指定地域。

这些属性不能依靠模型“猜出来”。调用方应提交结构化请求契约，同时保留原始内容供后续模型使用。一个简化的契约如下：

~~~json
{
  "request_id": "req-20260811-0192",
  "tenant_id": "tenant-a",
  "task": {
    "type": "contract_compare",
    "quality_target": "cited_review",
    "deadline_ms": 3500,
    "requires_tools": false
  },
  "input": {
    "modalities": ["text", "pdf"],
    "input_tokens": 18400,
    "output_tokens_max": 1600,
    "language": "zh-CN",
    "data_class": "confidential"
  },
  "policy": {
    "allowed_regions": ["cn-east"],
    "target_revision": "contract-policy-v12",
    "citation_required": true
  }
}
~~~

这份契约不是让用户填写所有字段。网关可以从身份、文件解析结果和产品配置中补齐字段，但补齐过程必须可追踪。尤其不能让用户输入的 `quality_target` 直接覆盖租户策略，也不能让 prompt 中的一句话把 `requires_tools` 改成 `false`。

### 13.1.2 特征提取和策略字段要分开

路由所需的特征可以分为四组：

| 组别 | 典型字段 | 来源 | 是否可由用户直接改变 |
| --- | --- | --- | --- |
| 任务特征 | 任务类型、输出格式、是否需要引用 | 产品调用方、解析器 | 部分可以 |
| 工作量特征 | 输入 token、文件页数、输出上限、工具步数 | 网关和编排器 | 间接可以 |
| 风险特征 | 数据分类、动作可逆性、租户地域 | 身份与策略服务 | 不应由 prompt 改写 |
| 服务特征 | 当前队列、模型健康度、配额、价格 | 控制平面和运行时 | 由平台维护 |

“语言是中文”可以影响模型选择，但不应自动推导出“可以处理敏感数据”；“要求 JSON”可以影响协议兼容性，但不代表模型一定会输出合法 JSON。派生特征必须记录其计算来源和版本，便于复盘路由错误。

### 13.1.3 难度不是一个神秘的模型分数

平台常想用一个 `difficulty=0.83` 字段决定路由。这个分数只有在定义清楚时才有意义。它可以来自输入长度、逻辑连接词、表格数量、任务类型、历史失败率或一个专门的难度分类器，但它不是“问题有多难”的客观真理。

砚桥把难度拆成可解释信号：

- 事实检索：是否需要跨多个文档和版本合并证据。
- 推理深度：是否要求比较、计算、约束满足或反事实分析。
- 输出协议：自由文本、严格 JSON、代码、工具参数或引用结构。
- 感知负荷：扫描 PDF、表格、图像和音频是否需要多模态处理。
- 风险等级：答案错误的后果是否会影响钱、权限、法律义务或外部沟通。

这样做的好处是，模型路由失败时可以知道是“长上下文预算不足”，还是“工具协议不兼容”，而不是只看到一个无法解释的黑盒分数。

### 13.1.4 预算必须在路由前计算

输入 token 数、最大输出 token 数、工具调用预留和系统上下文共同决定最小上下文容量。一个保守的预算可以写成：

~~~math
B_{\mathrm{required}}
=
B_{\mathrm{system}}
+B_{\mathrm{history}}
+B_{\mathrm{retrieval}}
+B_{\mathrm{input}}
+B_{\mathrm{tool}}
+B_{\mathrm{output\_reserve}}
+B_{\mathrm{safety\_reserve}}
~~~

如果候选模型的可用上下文为 (B_{mathrm{model}})，至少要满足：

~~~math
B_{\mathrm{required}} \leq B_{\mathrm{model}}
~~~

“模型宣传支持一百万 token”并不自动说明当前供应商 API、工具模式、KV 缓存实现或输出预算都能在一百万上稳定工作。路由器应使用当前 endpoint 的实际限制，并把截断、摘要或拒绝作为明确事件记录下来。

### 13.1.5 请求身份与缓存身份不是一回事

请求 ID 用来追踪一次调用，不能直接当缓存键。两个不同请求可能具有相同的可复用计算，也可能有相同文本却不能共享结果。缓存键需要表达影响结果的输入、策略和版本；请求 ID 只需要唯一。

## 13.2 模型目录与候选集：先排除不可能，再比较代价

### 13.2.1 目录记录的是可验证能力

模型目录（Model Catalog）是控制平面的事实来源。每个模型版本至少需要记录：

~~~json
{
  "model_id": "medium-2026-07-18",
  "provider": "internal",
  "revision": "sha256:...",
  "modalities": ["text", "pdf_text"],
  "context_tokens": 131072,
  "max_output_tokens": 8192,
  "supports_tools": true,
  "tool_protocol": "responses-v3",
  "supports_json_schema": true,
  "regions": ["cn-east"],
  "data_retention": "zero-day",
  "price": {
    "input_per_million": 1.2,
    "output_per_million": 4.8
  },
  "quality_profiles": {
    "contract_compare.zh": 0.70,
    "tool_argument.exact": 0.96
  }
}
~~~

`context_tokens` 是接口或运行时容量；`quality_profiles` 是在指定任务集上的测量结果。二者都需要标明来源和时间。价格字段也不应只保留一个数字，因为批处理、缓存命中、输入输出 token、区域和供应商计费规则可能不同。

### 13.2.2 硬约束和软偏好

候选筛选先处理硬约束：

1. 能否处理输入模态。
2. 上下文和输出预算是否足够。
3. 是否支持所需工具协议、结构化输出和流式接口。
4. 是否允许处理当前数据分类和地域。
5. 版本是否处于可用状态，当前配额和健康度是否允许接收请求。

完成硬筛选后，再比较质量、延迟、成本和能耗等软指标。把“质量偏好”放在硬筛选之前，常常会出现一个分数很高但根本无法执行工具调用的模型被选中的情况。

### 13.2.3 能力声明不是能力证明

目录中的 `supports_tools=true` 只表示协议层可以发送工具定义；它不等于模型能稳定生成正确参数，更不等于工具服务会授权该动作。平台应至少保存三种证据：

- 供应商或内部实现的接口文档，说明协议和限制。
- 离线测试集上的格式、参数和任务成功率。
- 线上小流量的错误率、回退率和副作用记录。

同理，`supports_long_context=true` 不等于模型能在长文档中找到位于中间的证据。长上下文能力应通过检索、跨段合并和引用支持等任务切片测量，而不是只记录最大输入长度。

### 13.2.4 目录版本和路由版本同时冻结

一次路由决策至少关联两个版本：模型及其配置版本，以及路由规则/策略版本。如果只记录模型名，事后无法知道当时选择它的阈值、候选排序和价格快照。建议把决策记录成不可变事件：

~~~json
{
  "request_id": "req-20260811-0192",
  "router_revision": "router-v27",
  "catalog_revision": "catalog-2026-08-11-03",
  "candidate_models": ["medium-2026-07-18", "large-2026-07-02"],
  "rejected": {
    "small-2026-07-30": ["tool_protocol", "quality_target"]
  },
  "selected": "medium-2026-07-18",
  "reason_codes": ["meets_contract", "lowest_estimated_unit_success_cost"]
}
~~~

### 13.2.5 供应商路由还要考虑数据边界

把请求发给外部供应商可能带来数据驻留、保留期、训练使用、跨境传输和子处理者等问题。路由器不负责替代法务判断，但必须把已批准的策略变成机器可执行约束。对机密合同，若目录没有可信的 zero-retention 证据或地域配置，就应排除该候选，而不是在日志里提醒一句“请注意隐私”。

## 13.3 规则路由：最容易上线，也最容易积累例外

### 13.3.1 规则的价值在可解释

第一版路由通常从规则开始：

~~~text
if requires_tools and not model.supports_tools:
    reject_candidate("tool_protocol")
elif input_tokens > model.context_tokens:
    reject_candidate("context_capacity")
elif data_class == "confidential" and not model.zero_retention:
    reject_candidate("data_policy")
else:
    score(model)
~~~

这种规则的优点是上线快、审计清楚、故障时可以人工推演。缺点是例外会不断增加：某个租户需要更短延迟，某个语言切片在小模型上效果不好，某种 JSON 任务必须使用特定模板。若所有例外都堆在一份 if-else 中，路由行为会变成没人敢改的隐性协议。

### 13.3.2 将规则写成数据和决策原因

规则可以配置化，但配置化不意味着失去约束。每条规则应有唯一 ID、适用范围、优先级、生效时间、负责人、证据链接和回滚版本。决策输出同时保留命中的规则和落选原因。

~~~json
{
  "rule_id": "contract-cited-v4",
  "when": {
    "task_type": "contract_compare",
    "citation_required": true
  },
  "constraints": {
    "min_quality_profile": 0.70,
    "max_p95_ms": 3500
  },
  "action": "prefer_medium_then_large",
  "effective_from": "2026-08-01T00:00:00Z",
  "evidence": "eval-run-2026-07-29"
}
~~~

### 13.3.3 规则冲突需要确定性语义

如果租户策略要求“只使用本地模型”，产品策略要求“优先最快”，两条规则不能靠配置文件的排列顺序碰运气。可以把约束分层：数据与安全约束优先于产品偏好，产品偏好优先于成本优化；每层内部使用显式优先级。冲突无法解决时，系统应返回可解释的不可执行原因，而不是静默选择一个模型。

### 13.3.4 规则不是永远正确

规则写下的是当时的假设。模型更新、用户任务变化和价格变化都可能使假设失效。每条重要规则都要有离线回放结果和线上指标，关注：

- 规则命中率是否突然变化。
- 被排除的候选是否实际上更成功。
- 规则导致的回退、超时和误拒是否集中在某个切片。
- 规则节约的 token 成本是否被重试和人工复核抵消。

规则如果没有观测，就只是把不可解释的模型选择换成不可解释的配置选择。

## 13.4 难度路由与级联：让更贵的计算承担它擅长的工作

### 13.4.1 难度路由的基本想法

难度路由（difficulty-aware routing）不要求每个请求一开始就使用最强模型。平台先用便宜的分类器、规则或小模型估计任务属于哪个难度区间，再把请求送往满足约束的候选集合。简单任务使用轻量模型，困难任务直接使用强模型，边界任务则保留升级机会。

这个想法的关键不是“用小模型赌一把”，而是提前定义什么叫成功，以及失败以后是否还能以合理代价补救。对合同助手来说，简单任务可能是从给定条款中抽取到期日；困难任务可能是比较两个版本、处理交叉引用并生成带证据的修改建议。二者都叫“合同问题”，但所需能力完全不同。

### 13.4.2 级联和回退的区别

级联（cascade）通常表示先调用便宜模型，再依据结果或风险信号决定是否调用更贵模型。回退（fallback）通常表示当前执行路径因为超时、容量不足、协议错误或服务故障而改用另一个候选。二者都可能导致多次模型调用，但触发原因不同：

- 级联是质量和成本策略的一部分，即使第一个模型正常也可能升级。
- 回退是可用性和执行恢复的一部分，常在当前候选不能继续时发生。
- 级联要比较“是否值得继续投入”，回退要保证“不会重复副作用或违反数据策略”。

如果把两者混在一个 `retry_model()` 函数里，系统很容易在模型已经成功发起工具调用后再次执行同一个动作。

### 13.4.3 只读任务适合先试，副作用任务通常不适合

对于纯文本草稿、候选摘要和搜索结果重排，第一次调用的失败通常可通过重新生成或升级模型修复。对于退款、发信、删除和审批提交，模型输出只是动作意图，真正的副作用应由服务端授权和幂等执行器控制。此时不能因为“模型置信度低”就把同一工具调用再发给更强模型。

更安全的流程是：

1. 让模型生成结构化动作意图，但不直接执行。
2. 服务端校验租户、主体、资源、金额、权限和幂等键。
3. 若动作需要人工确认，暂停在待确认状态。
4. 只有授权执行器提交外部动作，并记录外部系统返回的唯一 ID。
5. 后续模型只负责解释已发生的状态，不重新猜测是否执行成功。

### 13.4.4 用可观测的质量信号触发升级

路由器可以使用以下信号触发升级：

- 输出不符合 JSON Schema 或引用结构不完整。
- 引用支持率低于任务要求。
- 检索证据之间存在冲突，且模型没有显式说明。
- 工具参数校验失败，但请求仍然可能可修复。
- 独立验证器发现算术、单位或字段一致性错误。
- 模型输出过早结束，未覆盖契约要求的字段。
- 采样一致性低，多个候选答案对关键事实结论不一致。

“模型自己的 confidence 字段”可以作为信号，但不能作为唯一证据。模型有时会对错误答案给出很高的自信语气；独立的规则、检索证据和任务验证器往往更有价值。

### 13.4.5 级联成本必须按完整任务计算

设第一阶段模型成本为 (c_1)，升级模型成本为 (c_2)，升级概率为 (p_u)，验证和路由固定成本为 (c_v)，则一个简化的期望成本是：

~~~math
\mathbb{E}[C_{\mathrm{cascade}}]
=
c_v+c_1+p_u c_2
~~~

若升级模型需要重新读取全部上下文，这个式子还应包含重复输入 token；若可以复用 prefix 或中间表示，则 (c_2) 的实际值会下降。更重要的是要按成功任务计算：

~~~math
C_{\mathrm{success}}
=
\frac{C_{\mathrm{all\ attempts}}+C_{\mathrm{review}}}
{N_{\mathrm{successful\ tasks}}}
~~~

第一阶段价格低但成功率差时，分母会减少，单位成功任务成本反而上升。报告中要说明“请求成本”和“成功任务成本”不是同一个指标。

### 13.4.6 一个小型决策器

下面的代码只演示决策关系，不代表生产级模型质量估计。它明确区分硬约束、质量预测和单位成功成本，避免把一个综合分数悄悄当成所有目标：

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Candidate:
    name: str
    supports_tools: bool
    max_context: int
    expected_quality: float
    request_cost: float
    success_probability: float


def choose(candidates, *, input_tokens, needs_tools, quality_floor):
    feasible = [
        c for c in candidates
        if c.max_context >= input_tokens
        and (not needs_tools or c.supports_tools)
        and c.expected_quality >= quality_floor
        and c.success_probability > 0
    ]
    if not feasible:
        raise RuntimeError("no candidate satisfies the request contract")
    return min(feasible, key=lambda c: c.request_cost / c.success_probability)


models = [
    Candidate("small", False, 32_000, 0.61, 0.18, 0.55),
    Candidate("medium", True, 128_000, 0.74, 0.55, 0.70),
    Candidate("large", True, 256_000, 0.86, 1.40, 0.86),
]
selected = choose(
    models,
    input_tokens=18_000,
    needs_tools=True,
    quality_floor=0.70,
)
print(selected.name)
print(round(selected.request_cost / selected.success_probability, 3))
~~~

这里的 `success_probability` 必须来自与当前任务相同的评估切片，不能拿通用 benchmark 的分数直接替代。若成本和概率都带有估计误差，可以为候选保留置信区间，并在高风险任务上增加人工复核，而不是假装排序结果精确到小数点后三位。

### 13.4.7 学习型路由：有了数据以后再使用

当平台积累了请求特征、模型选择、结果质量和成本数据，可以训练路由器预测不同候选在某类任务上的表现。RouteLLM 研究了利用偏好数据学习模型路由的方向；RouterBench 则强调用跨模型、跨任务的路由数据比较成本与质量。它们是研究和评估方法的参考，不是一个拿来即用的生产路由器。

学习型路由有三个常见陷阱：

1. **选择偏差**：历史上没被送给小模型的请求，没有小模型的真实标签；直接比较历史平均值会把路由策略当成模型能力。
2. **反馈延迟**：回答质量可能在用户后续操作、人工复核或业务结果出现后才知道。
3. **策略自我强化**：路由器偏爱某模型后，训练数据越来越多来自该模型，其他候选的估计越来越不可靠。

可行的做法包括保留随机探索流量、对关键切片做离线回放、记录候选反事实评估、按时间滚动验证，并给高风险任务设置明确的人工和规则约束。探索流量也必须遵守数据地域和工具副作用限制，不能为了收集标签而随机放行真实写操作。

### 13.4.8 研究结果和生产保证要分开

FrugalGPT 说明了通过级联、路由和提示优化组合模型以降低成本的研究思路；RouteLLM 说明偏好数据可以用于模型路由；RouterBench 提供了评估路由策略时需要考虑的质量、成本和任务覆盖视角。这些论文证明的是方法在其数据和实验设定下的结果，不证明砚桥在当前中文合同、当前模型版本和当前价格上也会得到相同收益。生产决策仍应引用自己的离线集、线上 shadow 流量和成功任务成本。

## 13.5 质量回退：模型换了，任务不能悄悄变形

### 13.5.1 回退前先判断失败类型

不同失败需要不同处理：

| 失败类型 | 例子 | 是否适合换模型重试 |
| --- | --- | --- |
| 瞬时基础设施失败 | 连接重置、实例不可用 | 可以，需有限重试 |
| 容量或排队超时 | 队列超过 deadline | 可以，选择有容量的候选 |
| 协议失败 | JSON 不合法、工具 schema 不匹配 | 可以，需修正协议或换兼容模型 |
| 输入不可执行 | 上下文超过所有候选容量 | 不能盲重试，应压缩或返回明确错误 |
| 证据不足 | 检索没有支持主张的材料 | 换模型未必有用，应改检索或拒答 |
| 权限拒绝 | 当前主体不能执行动作 | 不能通过换模型绕过 |
| 外部动作结果未知 | 请求超时但供应商可能已受理 | 先查询幂等状态，不能直接重发 |

把所有异常都归为 `MODEL_ERROR` 会使回退策略不安全。故障分类应保留在状态机里，且由服务端根据错误类型决定是否允许再次执行。

### 13.5.2 质量回退不等于换个名字再生成

如果中型模型没有找到合同中的关键条款，直接把同一个 prompt 发给大型模型只能增加计算；更好的升级可能包括重新检索、扩大证据窗口、改变输出 schema、要求逐条引用或调用专门的解析器。路由对象应该允许改变执行计划：

~~~text
原计划：retrieve(top_k=5) -> medium -> citation_check
升级计划：retrieve(top_k=12, hybrid=true)
       -> rerank(contract_clause_model)
       -> large -> citation_check -> human_review_if_conflict
~~~

这说明“模型路由”常常是“执行路径路由”。模型只是路径中的一个组件。

### 13.5.3 单位成功成本的完整示例

假设一周内有 1,000 个合同比较任务：中型模型直接成功 760 个，失败后由大型模型补救 180 个，剩余 60 个进入人工复核。中型模型调用成本为 0.40 元，大型模型调用成本为 1.50 元，人工复核平均 4 元。若 180 个补救任务都重新调用大型模型，则：

~~~math
C_{\mathrm{all}}
=
1000\times0.40
+180\times1.50
+60\times4
=1780\text{ 元}
~~~

成功完成任务数若按“模型或人工最终解决”计算为 940，则：

~~~math
C_{\mathrm{success}}
=\frac{1780}{940}
\approx1.894\text{ 元/成功任务}
~~~

如果报告只写“平均模型调用成本 0.40 元”，就掩盖了升级和人工带来的真实支出。若 60 个复核任务并非都成功，分母还要进一步按业务验收结果修正。

### 13.5.4 回退预算和循环上限

每个请求应带有剩余预算：最大总墙钟时间、最大模型调用次数、最大输出 token、最大工具步数和最大金额风险。预算不是为了让系统拒绝正常请求，而是让异常路径有终点。

~~~math
N_{\mathrm{attempts}}
\leq N_{\max}
\qquad
T_{\mathrm{elapsed}}
\leq T_{\mathrm{deadline}}
\qquad
\sum_i C_i \leq C_{\mathrm{budget}}
~~~

这些约束最好由编排器和服务端执行，而不是只写在 prompt 中。模型可以被要求“不要重复”，但无法替代可靠的计数器、超时和幂等存储。

## 13.6 Response Cache：复用完整回答，但必须证明它仍适用

### 13.6.1 什么是 Response Cache

Response Cache 保存某个完整请求的已生成结果，包括文本、结构化字段、引用、工具状态摘要和必要的元数据。下一次请求如果在语义、权限、版本和有效期上都满足复用条件，系统可以直接返回结果，跳过部分或全部模型计算。

它最适合：

- 稳定的公开 FAQ 和产品说明。
- 相同数据版本上的重复摘要或抽取。
- 允许短时间陈旧的低风险只读查询。
- 经过授权、键空间隔离的租户内部重复任务。

它不适合直接复用：

- 随时间、用户状态或库存变化的事实。
- 包含个人化权限的数据。
- 生成外部副作用的动作结果。
- 依赖随机性、当前会话或未记录环境的回答。

### 13.6.2 精确缓存键

精确缓存要求规范化后的请求在影响结果的字段上完全相同。一个概念键可以写成：

~~~math
K_{\mathrm{exact}}
=
H(
\mathrm{tenant\_scope}
\Vert \mathrm{principal\_scope}
\Vert \mathrm{task\_contract}
\Vert \mathrm{model\_revision}
\Vert \mathrm{prompt\_revision}
\Vert \mathrm{input\_digest}
\Vert \mathrm{retrieval\_revision}
\Vert \mathrm{policy\_revision}
\Vert \mathrm{generation\_params}
)
~~~

其中 (H) 是密码学哈希，(Vert) 表示按规定编码后拼接。不能直接把 JSON 字符串原样哈希，因为字段顺序、空白、浮点表示和默认值可能造成无意义的键差异；应先使用稳定的 canonical encoding。

需要特别谨慎的是 `principal_scope`。若回答包含用户可见的权限范围，租户 ID 可能还不够，角色、部门、资源 ACL 和数据脱敏策略也可能影响结果。宁可命中率低，也不能为了提高命中率把不同权限主体放进同一共享键空间。

### 13.6.3 新鲜度不是一个统一 TTL

TTL（time to live）只是一个时间上限，不是内容一定正确的证明。公告、汇率、库存、合同条款和公开教程的变化速度不同；应按照数据源的新鲜度要求设置 TTL，或由版本变更主动失效。

缓存有效性的教学表达是：

~~~math
\mathrm{Valid}(e,q,t)
=
\mathrm{KeyMatch}(e,q)
\land \mathrm{PolicyMatch}(e,q)
\land \mathrm{VersionMatch}(e,q)
\land \mathrm{Fresh}(e,t)
\land \mathrm{IntegrityOK}(e)
~~~

`KeyMatch` 表示键和请求契约一致，`PolicyMatch` 表示当前权限与策略没有变化，`VersionMatch` 表示引用的数据、提示和模型版本符合要求，`Fresh` 表示仍在允许的有效期内，`IntegrityOK` 表示缓存条目未损坏或被篡改。生产代码不应把这个布尔表达式简化成 `now < expires_at`。

### 13.6.4 共享缓存和私有缓存

响应缓存至少分为三种范围：

- **公共范围**：不含租户和个人数据，适合公开 FAQ；必须防止内部提示和调试字段泄露。
- **租户范围**：同一租户共享，但仍要检查角色和资源权限；适合企业制度的公开部分。
- **主体范围**：只对同一用户或同一授权主体复用；命中率较低，但隔离更强。

缓存条目中不要保存不必要的原始 prompt、敏感文档和工具凭证。返回给用户的结果与内部调试元数据应分开存储，日志也不应因为“这是缓存”而绕过脱敏。

### 13.6.5 语义缓存：相似不代表等价

语义缓存先对新问题和历史问题计算 embedding，再寻找相似条目。它可以提高同义问题的命中率，例如“报销单多久审核”和“费用审批一般需要多长时间”。但向量相似只表示语义邻近，不证明：

- 两个用户拥有相同权限。
- 问题依赖相同的时间和数据版本。
- 业务主体、地区、金额和单位相同。
- 回答可以承担相同的风险。

因此，语义缓存需要一个二次条件：相似检索只是候选生成，仍要做任务类型、租户范围、数据版本、时间条件和答案适用范围检查。高风险任务可以完全禁用语义复用；中风险任务可以要求重新验证引用；低风险公开 FAQ 才适合较宽松的阈值。

### 13.6.6 相似度阈值需要用任务数据校准

设新请求向量为 (x)，缓存条目向量为 (y)，余弦相似度为：

~~~math
\mathrm{cos}(x,y)
=
\frac{x\cdot y}{\lVert x\rVert_2\lVert y\rVert_2}
~~~

阈值 0.90 没有普遍含义。不同 embedding 模型、语言、文本长度和领域会改变相似度分布。平台应在标注过“可复用/不可复用”的配对集上测量 precision、recall 和风险切片，并把“错误命中”作为比“少命中”更高的代价处理。

可以把语义缓存的期望收益写成教学模型：

~~~math
\mathbb{E}[V]
=
p_{\mathrm{hit}}\left(
c_{\mathrm{recompute}}
-c_{\mathrm{lookup}}
-c_{\mathrm{validation}}
\right)
-p_{\mathrm{wrong\_reuse}}c_{\mathrm{harm}}
~~~

当错误复用的后果 (c_{\mathrm{harm}}) 很高时，即使命中率很高也可能不值得启用。对于合同审查，错误复用可能让用户错过新版本义务；这类场景应优先使用版本精确匹配和重新验证。

### 13.6.7 缓存结果要有生成证据

一个可审计的响应缓存条目应至少记录：

~~~json
{
  "cache_key": "sha256:...",
  "created_at": "2026-08-11T08:10:00Z",
  "expires_at": "2026-08-11T09:10:00Z",
  "tenant_scope": "tenant-a",
  "principal_scope": "role:contract-reader",
  "model_revision": "medium-2026-07-18",
  "prompt_revision": "contract-answer-v9",
  "retrieval_revision": "index-contract-441",
  "policy_revision": "contract-policy-v12",
  "evidence_refs": ["doc-88#clause-4", "doc-91#clause-2"],
  "response_digest": "sha256:...",
  "side_effect": "none"
}
~~~

证据引用允许后续审计回答来自哪里；版本字段允许数据变化时主动失效；`side_effect=none` 不是装饰，它告诉读取方这个条目只代表解释性结果，不能被当成“工具已执行”的证明。

### 13.6.8 HTTP 语义能提供什么，不能提供什么

RFC 9111 定义了 HTTP 缓存的缓存控制、验证和新鲜度语义，RFC 5861 描述了 `stale-while-revalidate` 与 `stale-if-error` 等控制扩展。它们适合帮助设计公开只读资源的 HTTP 层缓存，但不会自动解决 LLM 响应中的租户权限、提示版本、检索证据和副作用问题。


## 13.7 Prefix Cache 与 KV Cache：复用计算状态，不等于复用回答

### 13.7.1 从模型计算看 prefix

自回归 Transformer 在处理输入 token 时，会为每一层注意力保存 key 和 value。生成下一个 token 时，历史 token 的 key/value 可以重复使用，而不必从头计算整个前缀。对大量请求共享的系统提示、工具定义、格式说明和长文档前缀，系统还可以把这部分中间状态保存在 GPU 或 CPU 的缓存中。

这类缓存保存的是模型计算状态，不是最终回答。它通常只影响 prefill 计算和首 token 延迟，不能直接让模型跳过后续 decode，也不能跨不兼容模型版本复用。

小白可以把它理解为：Response Cache 保存“做完题的答案”，Prefix/KV Cache 保存“已经读过的一段题目所形成的草稿状态”。草稿状态只适用于完全相同且仍然兼容的前缀；题目后半段、采样参数和输出仍要重新处理。

### 13.7.2 KV Cache 的容量账本

对一个常见的多层注意力模型，若每层有 \(n_{kv}\) 组 key/value、每个 head 的维度为 \(d\)、缓存长度为 \(S\)，数据类型每个元素占 \(b\) 字节，单个序列的 KV 字节数可近似写为：

~~~math
M_{\mathrm{KV}}
\approx
2\times L\times S\times n_{kv}\times d\times b
~~~

其中 \(L\) 是层数，前面的 2 分别对应 K 和 V。若使用 GQA 或 MQA，\(n_{kv}\) 小于 query head 数，KV 占用会下降；若使用更低精度，\(b\) 会下降，但量化和反量化的实现细节会影响实际收益。

例如，假设 \(L=32\)、\(n_{kv}=8\)、\(d=128\)、\(S=16{,}384\)，KV 使用 BF16，每个元素 2 字节，则：

~~~math
M_{\mathrm{KV}}
\approx
2\times32\times16{,}384\times8\times128\times2
=2{,}147{,}483{,}648\text{ bytes}
\approx2\text{ GiB}
~~~

这只是一个序列的理论量，实际还要加上页表、对齐、批处理、临时张量和碎片。它说明为什么长上下文和并发数会共同挤压显存：缓存容量约与 \(S\times N\) 成正比，其中 \(N\) 是同时保留的序列数。

### 13.7.3 Prefix Cache 的命中条件

一个 prefix block 能否复用，至少要检查：

- token 序列完全相同，而不是字面字符串看起来相似。
- tokenizer、特殊 token、模板和 chat 格式版本一致。
- 模型权重、LoRA/adapter 和量化配置一致。
- attention、位置编码和缓存实现的兼容条件一致。
- 租户、系统策略和工具定义没有把不同权限主体混在一起。
- 缓存状态没有过期、损坏或被驱逐。

动态字段应放在共享前缀之后。例如，把当前用户姓名、账户余额和权限列表拼进一段所有租户共享的系统 prompt，会让共享 prefix cache 既难命中，又可能造成隔离风险。稳定模板、稳定工具 schema 和公开规则可以共享；主体相关内容应进入私有后缀或使用更细的缓存范围。

### 13.7.4 分块和局部命中

实践中的 prefix cache 通常按固定 token block 管理。请求前缀越长，共享块越多，节约的 prefill 计算越大；但 block 太小会增加元数据和查找开销，block 太大又会降低不同请求之间的共享机会。

设每个 block 含 \(B\) 个 token，共享前缀长度为 \(S_p\)，则可复用块数近似为：

~~~math
N_{\mathrm{reuse}}
=
\left\lfloor\frac{S_p}{B}\right\rfloor
~~~

若最后一个不完整 block 不能复用，则余下 token 仍需计算。vLLM 的 Automatic Prefix Caching 文档展示了这类运行时能力；SGLang 的 HiCache 文档则讨论了更大层级的缓存组织。它们是特定引擎的实现资料，不能直接推导出所有模型和硬件上的速度提升。

### 13.7.5 Prefix 缓存与位置编码边界

位置编码、RoPE 缩放、NoPE 或其他长上下文机制会改变 token 在模型中的表示方式。即使两个服务都声称支持相同上下文长度，只要位置配置、缩放因子或模板不同，缓存状态就可能不可复用。缓存键必须包含影响位置计算的配置摘要，而不是只包含 model_name。

这也是为什么“模型换了一个别名但权重相同”不能自动视为兼容。服务端编译图、量化方案、adapter、tokenizer 和运行时 kernel 都可能改变状态的解释方式。

### 13.7.6 Prefix Cache 的收益如何测

至少分别测量：

- prefix hit rate：请求中有多少前缀块成功复用。
- reused token ratio：总输入 token 中有多少来自复用块。
- TTFT 改善：命中与未命中在同一负载切片的差值。
- decode 影响：KV 占用是否导致并发下降或驱逐增加。
- 共享边界：不同租户、角色和策略是否出现越界命中。

只有 hit rate 没有意义。若命中率很高但缓存占满显存，导致长请求排队，端到端 p99 可能反而变差。指标必须按请求长度、batch 大小、租户和模型版本分层。

## 13.8 Embedding Cache 与 Retrieval Cache：缓存检索链路中的中间结果

### 13.8.1 Embedding Cache 缓存什么

Embedding Cache 保存文本、图像或查询经过 embedding 模型得到的向量。对于重复文档、重复问题和稳定的 chunk，它可以减少 embedding 计算。一个安全的 embedding 键至少包括：

~~~math
K_{\mathrm{embed}}
=
H(\mathrm{normalized\_content}
\Vert \mathrm{modality}
\Vert \mathrm{embedding\_model\_revision}
\Vert \mathrm{preprocess\_revision})
~~~

如果文本清洗、分词、截断或图像缩放发生变化，旧向量不能因为原始文件名相同就继续使用。向量本身也可能属于敏感数据：它可能泄露文档存在性、语义特征或被用来推断原始内容，因此要按数据分类施加访问控制和删除策略。

### 13.8.2 文档向量和查询向量的生命周期不同

文档 embedding 通常可以在索引构建时批量计算并长期保存；查询 embedding 更短命，可能只在一次请求或一个会话中使用。两者的缓存容量、TTL 和隐私策略不应完全相同。

文档更新时，不能只更新数据库中的一行文本而保留旧向量。可采用不可变文档版本和新索引 revision：新版本完成解析、embedding 和索引构建后，再切换可见指针。这样读路径始终看到一组相互一致的文本、向量和元数据。

### 13.8.3 Retrieval Cache 不能绕过权限

Retrieval Cache 保存“某个查询在某个索引和过滤条件下返回了哪些候选”。它的键必须包含：

- query 的规范化表示和 query rewrite 版本。
- embedding/reranker 版本。
- 索引 revision、租户和 ACL 过滤摘要。
- 时间窗口、地域、语言和其他过滤条件。
- top-k、阈值和排序配置。

最危险的错误是先查共享检索缓存，再在结果返回后做权限过滤。这样可能从缓存命中数量、候选 ID 或排序差异中泄露另一个租户的数据。正确顺序是把权限范围纳入查询身份，或者在一个可信的数据层内先完成权限过滤再缓存结果。

### 13.8.4 召回缓存和证据缓存要区分

候选文档 ID 列表与最终发送给模型的证据片段不是同一对象。前者可以在重新检查权限和版本后重新取正文；后者可能包含已经过时或脱敏策略不同的文本。

砚桥因此把两者分开：

- **召回缓存**：保存候选 ID、分数、索引版本和过滤条件。
- **证据缓存**：保存用于生成的片段、位置、哈希和脱敏版本，TTL 更短，范围更窄。

如果文档被撤销，所有引用该文档版本的证据缓存都必须失效；仅删除召回缓存是不够的。

### 13.8.5 查询改写使缓存键成为协议的一部分

同一个用户问题可能先经过语言识别、历史补全、拼写修正、HyDE 或多查询扩展。若只对原始文本做缓存键，改写器版本变化后可能错误复用旧召回结果。键应包含改写后的规范查询和改写器 revision，或者明确规定缓存只覆盖改写前的阶段。

这类中间缓存的价值在于缩短重复查询链路，但每增加一个缓存层，就增加一个版本和失效来源。设计时应画出从原始 artifact 到最终回答的依赖图，而不是逐个组件计算命中率后相加。

## 13.9 会话状态、工具结果和 Response Cache 的边界

### 13.9.1 会话不是一条不断增长的 prompt

聊天历史包含用户消息、模型消息、工具调用、工具结果、人工修改和系统事件。把这些内容简单拼接成字符串，会使路由器和缓存器无法知道哪些部分仍然有效。

砚桥把会话建模为带版本的事件流：

~~~text
conversation
  -> branch
      -> message
      -> model_response
      -> tool_intent
      -> authorization
      -> tool_result
      -> user_edit
~~~

每个事件有唯一 ID、父事件、产生时间、来源版本和可见范围。上下文构建器根据当前分支选择事件，而不是盲目读取“最后 N 条消息”。用户编辑或撤销某个文件后，依赖该文件的摘要、检索结果和回答也应有可查询的依赖关系。

### 13.9.2 摘要缓存可能传播错误

长会话需要摘要以控制上下文长度。摘要可以缓存，但必须带有输入事件范围、摘要模型 revision、语言、策略和生成时间。若原始事件被删除或权限改变，摘要不能继续作为完整事实使用。

摘要不是原始记录的等价替身。它可能丢失否定词、条件、例外和说话者。高风险任务应在摘要之外重新取关键原文，并让回答引用原始事件或文档，而不是只引用摘要。

### 13.9.3 工具结果缓存要看状态变化和副作用

只读、可版本化的工具结果适合缓存，例如“某个文档版本的章节列表”。实时库存、账户余额、权限状态和审批状态通常需要短 TTL、版本校验或强制查询。

写工具的结果不能被当作普通 Response Cache。至少要区分：

- intent_created：模型提出了动作意图。
- authorization_granted：服务端授权了意图。
- execution_started：外部执行器已提交。
- execution_succeeded：外部系统确认成功。
- execution_unknown：网络失败，状态需要查询。

只有最后的业务事实在外部系统提供稳定版本或幂等查询时，才可能被短暂缓存。execution_unknown 必须进入状态查询路径，不能用“没有看到成功响应”推断失败。

### 13.9.4 幂等键和缓存键不能混用

幂等键回答“同一个业务动作是否已经提交过”，缓存键回答“一个可复用的计算结果是否适用”。两者都使用哈希并不意味着可以共用：

- 幂等记录需要长期保存提交状态和外部 ID。
- 响应缓存需要依据版本和权限失效。
- 同一个用户问题可能有多个合法响应，但同一个退款动作必须只提交一次。

混用会导致缓存淘汰后重复写操作，或为了保存幂等状态而让敏感响应长期驻留。

## 13.10 版本、失效、撤销和删除：缓存最难的不是读，而是忘掉

### 13.10.1 失效来源要显式建模

缓存条目通常依赖多个对象：模型、prompt、策略、文档、索引、工具 schema、用户权限和时间。任一依赖变化，都可能使条目失效。可以为每条条目保存 dependency set，也可以使用分层 revision：

~~~text
tenant-policy-v12
  -> corpus-revision-441
      -> index-revision-441
          -> retrieval-entry
              -> response-entry
~~~

新版本发布时切换读指针，旧版本可以在保留期后删除。对需要立即撤销的内容，不能只等待 TTL；应维护撤销表或版本黑名单，在读取时拒绝旧条目，并异步清理物理副本。

### 13.10.2 软失效和硬删除

- **软失效**：标记条目不可用于新请求，但仍保留一段时间用于审计或回放。
- **硬删除**：从可访问存储、复制副本、磁盘缓存和备份生命周期中移除。

软失效适合快速切换版本，硬删除适合用户撤回、合规删除和凭证泄露后的清理。二者的完成含义不同，审计事件必须写清是“停止服务”还是“所有副本已清理”。

### 13.10.3 权限撤销比 TTL 更紧急

用户被移出合同项目后，旧回答可能仍然包含合同内容。若系统只依赖一天的 TTL，撤销后的窗口可能不可接受。权限变化事件应触发相关主体或资源范围的失效；读路径也要再次校验当前 ACL，不能把缓存命中当作授权证明。

### 13.10.4 删除的证据链

删除请求需要追踪：

1. 原始文档和解析产物。
2. 文档 embedding、索引条目和检索缓存。
3. 响应缓存、会话摘要和评估样本副本。
4. 日志、备份、异步队列和跨区域副本。

数据库中删除一行不代表模型已经“忘记”内容，也不代表所有缓存都立即消失。书稿应明确删除传播的目标、完成时间、无法立即删除的备份保留周期和访问限制。

### 13.10.5 加密擦除的适用边界

对高敏感缓存，可以使用每租户或每数据域的加密密钥；撤销密钥能够使密文不可读，减少大规模物理清理压力。但这不是删除的万能替代：密钥备份、明文日志、embedding、派生摘要和下游导出仍需单独处理。加密擦除能证明什么，取决于密钥管理和副本控制的实际设计。

## 13.11 容量、热点与成本：缓存会改变流量形状

### 13.11.1 命中率的基本账

设总请求数为 \(N\)，命中数为 \(N_h\)，则：

~~~math
H=\frac{N_h}{N}
~~~

若命中请求平均成本为 \(C_h\)，未命中请求平均成本为 \(C_m\)，缓存查询、校验和写入的平均固定成本为 \(C_c\)，则平均请求成本近似为：

~~~math
\bar C
=
H(C_h+C_c)+(1-H)(C_m+C_c)
~~~

实际还要纳入缓存内存、网络、失效同步、误命中损失和维护成本。一个只报告 \(H=80\%\) 的仪表盘无法告诉我们：命中的是低成本 FAQ，还是最昂贵的长上下文请求；也无法告诉我们是否有错误复用。

### 13.11.2 容量估算

若平均条目大小为 \(S_e\) 字节，保留条目数为 \(N_e\)，复制因子为 \(r\)，元数据和碎片开销比例为 \(\alpha\)，则存储需求可粗略估计为：

~~~math
M_{\mathrm{cache}}
\approx
N_e\times S_e\times r\times(1+\alpha)
~~~

若写入速率为 \(\lambda\)、平均保留时间为 \(T\)，在稳态且没有大量重复覆盖时：

~~~math
N_e\approx\lambda T
~~~

这是教学估算。真实系统还需考虑 Zipf 热点、条目大小长尾、压缩率、驱逐策略、热备和故障期间的积压。

### 13.11.3 热点和缓存击穿

一份热门制度或一个公共 prompt 可能被大量请求同时读取。缓存命中虽然省模型计算，却可能让单个键成为存储服务热点。过期瞬间，大量请求同时回源，会形成 cache stampede。

常见缓解方法包括：

- single-flight：同一键只允许一个请求回源，其余请求等待结果。
- 提前刷新：在 TTL 到期前由后台刷新热门条目。
- 抖动 TTL：避免同一批条目同时过期。
- stale-if-error：只对允许陈旧的低风险内容在上游失败时短暂返回旧值。
- 热点分片和本地只读副本：减少单节点压力。

这些机制必须受风险策略约束。一个“旧合同条款”不能因为是热点就被无限延长。

### 13.11.4 LRU 不是通用答案

LRU 适合一定程度上利用近期性，但长文档、大小差异和热点扫描会使它表现不佳。缓存设计还应比较 LFU、带成本/大小权重的驱逐、分层缓存和按租户配额的策略。若大租户可以填满整个共享缓存，小租户的 p99 和命中率都会受影响，容量策略应包含租户公平性。

### 13.11.5 读放大、写放大和一致性代价

一个响应可能依赖检索结果、多个证据片段和策略 revision。为此设置依赖反向索引会增加写入和失效开销；跨区域复制会增加网络成本；每次命中前做 ACL 校验会增加读取延迟。这些成本不能被“模型调用省下的钱”完全忽略。

平台要按层计量：

~~~text
请求数
  -> 缓存查询数/命中数/误命中数
  -> embedding 查询
  -> retrieval 查询
  -> rerank 查询
  -> model 调用
  -> tool 调用
~~~

这样才能知道缓存到底减少了哪一段工作，是否只是把成本移动到了另一个组件。

## 13.12 故障降级、灰度与可观测性

### 13.12.1 控制平面和数据平面

模型目录、路由规则、价格配置、缓存版本和策略属于控制平面；请求执行、缓存读取、模型生成和工具调用属于数据平面。控制平面发布失败时，数据平面应继续使用最后一个已验证配置；数据平面局部故障时，控制平面仍应能冻结危险路由和撤销缓存版本。

关键配置不应每次请求都依赖一个不可用的远端控制服务。可在本地保留签名、带版本的只读快照，并记录快照年龄；超过允许年龄后，普通只读请求可以有限降级，高风险写动作则应暂停。

### 13.12.2 缓存服务失败时的策略

缓存读失败不等于模型失败。对低风险公开内容，可以绕过缓存回源；对机密内容，应保留权限和版本检查，不要为了可用性直接返回旧条目。缓存写失败通常不应影响已经成功的用户响应，但要产生指标和告警，防止容量问题悄悄积累。

缓存数据损坏或完整性校验失败时，应删除或隔离该条目并重新计算；不能“先返回看看”。高风险结果应在回源后重新验证证据和策略。

### 13.12.3 模型服务失败时的策略

候选回退要满足：

- 数据处理地域和保留策略仍然兼容。
- 上下文、工具和输出协议仍然兼容。
- 剩余 deadline 足够完成回退。
- 没有重复执行未确认的外部副作用。
- 回退结果明确标注模型和 quality profile，供用户和审计使用。

当所有候选都不可用时，系统应返回具体可行动的错误或受限草稿，例如只展示已经核验的缓存资料，并说明实时回答暂不可用。不能把“降级”写成静默降低质量后仍声称任务已经完成。

### 13.12.4 灰度路由

新路由规则或新模型先进入 shadow 或小比例灰度。shadow 请求可以计算新路径的输出和成本，但必须注意：

- 不要重复执行工具和写操作。
- 敏感输入必须遵守同一数据域和保留策略。
- 比较时要固定请求切片、上下文版本和超时预算。
- 新旧路径的差异要由任务级指标解释，而不是只比较字符串相似度。

灰度期间至少看成功率、引用支持、协议错误、回退率、p95/p99、单位成功成本、缓存误命中和租户切片差异。发现问题时回滚的是路由 revision 或目录指针，而不是手工修改几个运行实例。

### 13.12.5 观测字段和追踪关系

每次请求应能关联一条 trace，包含：

~~~json
{
  "trace_id": "trace-...",
  "request_id": "req-...",
  "tenant_id": "tenant-a",
  "router_revision": "router-v27",
  "model_revision": "medium-2026-07-18",
  "route_reason": ["quality_floor", "lowest_unit_success_cost"],
  "cache": {
    "response": "miss",
    "prefix": "partial_hit",
    "embedding": "hit",
    "retrieval": "miss"
  },
  "tokens": {
    "input": 18400,
    "cached_input": 12200,
    "output": 734
  },
  "latency_ms": {
    "queue": 43,
    "prefill": 712,
    "decode": 1080,
    "total": 2035
  },
  "side_effect": "none"
}
~~~

OpenTelemetry 可以作为跨服务 trace、metric 和 log 关联的工程规范入口，但具体语义约定和敏感字段治理仍由平台自己定义。追踪系统本身也可能包含合同文本和工具参数，必须做字段级脱敏、访问控制和保留期限管理。

## 13.13 贯穿案例：一次错误缓存如何扩大成合同事故

### 13.13.1 事故发生

砚桥把“合同到期日”问答设置为语义缓存，以提高客服响应速度。缓存键只包含规范化问题文本和租户 ID，没有包含用户角色、合同资源 ID、合同版本和策略 revision。某用户先询问“供应商甲合同什么时候到期”，系统用旧索引检索到合同 A 并生成答案；另一名项目成员随后询问同样的问题，语义缓存直接返回了上一条答案。

事故中同时存在三个缺陷：

1. 问题文本没有显式绑定资源，答案中的主体来自隐含上下文。
2. 缓存读路径没有再次检查当前用户对合同 A 的访问权限。
3. 合同 A 更新后只重建了索引，没有向响应缓存传播新 revision。

模型本身可能完全按照缓存内容生成了流畅回答；错误发生在身份、数据版本和缓存语义的系统设计上。

### 13.13.2 影响分析

复盘不能只统计“错误回答 1 次”。应回答：

- 哪些租户和主体访问过受影响键。
- 返回的是过期事实、越权事实，还是两者都有。
- 是否有用户根据答案创建了审批或发送了外部邮件。
- 旧条目是否还存在于本地、共享、备份和日志副本。
- 哪个版本的路由、索引和策略允许它命中。

可以把严重度加权的失败率写成：

~~~math
F_{\mathrm{weighted}}
=
\frac{\sum_{i=1}^{N} w_i\,\mathbf{1}(\mathrm{failure}_i)}
{\sum_{i=1}^{N} w_i}
~~~

\(w_i\) 是按越权、过期和外部影响设定的权重。它适合排序和复盘，不应冒充真实损失概率。若存在一例严重越权，平均质量分很高也不能掩盖问题。

### 13.13.3 修复路径

修复先止血，再恢复能力：

1. 关闭合同类语义 Response Cache，保留精确键但要求资源和版本匹配。
2. 将受影响文档、索引和所有派生响应标记为撤销，查询当前 ACL 和访问日志。
3. 修正缓存键和条目 schema，强制加入主体范围、资源范围、索引 revision 和策略 revision。
4. 对缓存命中路径增加证据存在性、版本和权限校验。
5. 用历史请求和专门的跨租户样本做回放，确认不会复现越权。
6. 以 shadow 流量比较命中与回源结果，检查过期率、引用支持和成本。

修复完成的标准不是“缓存命中率恢复”，而是权限撤销、文档更新和索引切换都能在承诺时间内阻止旧答案被新请求使用。

### 13.13.4 一个最小审计示例

下面的教学程序模拟三个模型候选和一个旧缓存条目。它展示为什么要先检查硬约束和版本，再按单位成功成本选择模型。数值是合成数据，不代表任何供应商的实测：

~~~python
from dataclasses import dataclass


@dataclass(frozen=True)
class Model:
    name: str
    context: int
    tools: bool
    quality: float
    cost: float
    success: float


def cache_is_valid(entry, *, target_revision, now):
    return (
        entry["target_revision"] == target_revision
        and now < entry["expires_at"]
        and entry["side_effect"] == "none"
    )


def select(models, *, input_tokens, needs_tools, quality_floor):
    candidates = [
        model for model in models
        if model.context >= input_tokens
        and (not needs_tools or model.tools)
        and model.quality >= quality_floor
        and model.success > 0
    ]
    return min(candidates, key=lambda m: m.cost / m.success)


models = [
    Model("small", 8_000, False, 0.62, 0.20, 0.55),
    Model("medium", 32_000, True, 0.74, 0.55, 0.70),
    Model("large", 128_000, True, 0.88, 1.40, 0.86),
]
entry = {
    "target_revision": "policy-v11",
    "expires_at": 100,
    "side_effect": "none",
}
valid = cache_is_valid(entry, target_revision="policy-v12", now=50)
selected = select(
    models,
    input_tokens=6_000,
    needs_tools=True,
    quality_floor=0.70,
)
print(f"cache_valid={valid}")
print(f"selected_model={selected.name}")
print(f"cost_per_success={selected.cost / selected.success:.3f}")
~~~

程序输出：

~~~text
cache_valid=False
selected_model=medium
cost_per_success=0.786
~~~

small 的上下文容量虽然足够，但不支持工具且质量低于下限；缓存条目属于旧的 policy-v11，所以不能命中；medium 满足硬约束且单位成功成本低于 large。如果请求实际不需要工具，候选集合和选择结果会改变，这正是结构化请求契约比单一 prompt 更重要的原因。

## 13.14 资料的可信度与适用边界

本章资料按证据类型使用：

- **原始论文**：FrugalGPT（[arXiv:2305.05176](https://arxiv.org/abs/2305.05176)）、RouteLLM（[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)）、RouterBench（[arXiv:2403.12031](https://arxiv.org/abs/2403.12031)）用于理解路由、级联和比较方法。论文中的数据、模型版本和成本不能直接当作砚桥的线上保证。
- **推理引擎文档**：[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html) 与 [SGLang HiCache](https://docs.sglang.io/docs/advanced_features/hicache_best_practices) 用于说明 prefix/KV 状态缓存的实现视角。它们描述的是特定引擎和配置，收益需要本地压测。
- **协议与工程规范**：[RFC 9111](https://www.rfc-editor.org/rfc/rfc9111) 和 [RFC 5861](https://www.rfc-editor.org/rfc/rfc5861) 用于 HTTP 缓存新鲜度和陈旧响应语义；[OpenTelemetry documentation](https://opentelemetry.io/docs/) 用于跨服务观测的概念入口。
- **缓存系统资料**：[Memcached](https://memcached.org/about/) 和 [CacheLib](https://cachelib.org/) 用于理解通用缓存的内存、驱逐和分层设计。它们不是 LLM 权限和版本失效方案。
- **推理系统论文**：DistServe（[arXiv:2401.09670](https://arxiv.org/abs/2401.09670)）用于理解 prefill/decode 解耦；Speculative Decoding（[arXiv:2211.17192](https://arxiv.org/abs/2211.17192)）用于说明减少解码延迟的另一类机制。二者与 Response Cache 的复用对象不同。

资料使用时要区分：论文是特定实验设定下的研究证据，官方文档是实现或协议说明，benchmark 是任务集上的比较工具，教学公式是帮助建立账本的近似，合成案例是用来练习推理链条的材料。任何一项都不能替代对当前模型、数据和业务的实测。

## 13.15 章末练习：把选择写成可以被审计的系统

1. 为一个需要读取租户制度、生成带引用回答但不产生写操作的请求定义完整契约。列出至少三项硬约束和三项软偏好，并说明每项字段的来源。
2. 设计一个精确 Response Cache 键，分别解释租户、主体、文档版本、模型版本和策略版本缺失时会发生什么。
3. 给出一个语义缓存误命中的例子，说明为什么 embedding 相似度不足以证明答案等价，以及你会增加哪些二次校验。
4. 比较“先用小模型、失败后升级”和“直接用中模型”的单位成功任务成本。请把重试、人工复核和失败分母写进计算。
5. 画出一次文档删除从原始文件、embedding、索引、检索缓存、响应缓存到日志和备份的传播链，标明软失效和硬删除分别何时完成。
6. 为一个会创建审批任务的 Agent 设计故障状态。特别说明外部请求超时后为什么不能简单换模型重试，以及如何用幂等键和状态查询恢复。

真正成熟的路由与缓存系统，不是让每个请求都更快或每个 token 都更便宜，而是让系统在任务、权限、版本和证据都清楚时放心复用，在不确定时知道为什么重新计算，并且能够用一条完整记录解释每一次选择。
