# 第十四章：从开放问题到可运行方案：大模型系统设计的推理方法

系统设计不是把若干基础设施名词排列在一张图上。真正的设计工作，是在目标不完整、资源有限、模型行为有不确定性的情况下，定义一个可以被实现、测量、回滚和追责的服务。

“设计一个 ChatGPT”“设计一个 RAG”“设计一个推理平台”都不是单一组件题。它们要求你把一个自然语言目标翻译成服务契约：谁可以调用，输入和输出是什么，系统在多长时间内响应，什么叫任务成功，哪些失败可以恢复，哪些动作不能自动重试，以及如何证明新版本没有破坏旧能力。

本章以“远岑企业助手”作为共同背景。远岑为多个企业租户提供制度问答、合同检索、语音接待和审批协作。它接入模型服务、检索服务、工具服务和人工复核。每个案例都会回到同一条主线：先定义边界，再计算工作量，接着组织状态和证据，最后用指标、故障演练和成本账本验证设计。

本章中的架构、数字和代码示例是教学模型。论文、规范和工程文档用于说明方法与机制；只有在目标数据、模型版本和线上负载上完成的测量，才能成为远岑自己的工程结论。

## 14.0 先理解系统设计题：它其实是在考建模

### 14.0.1 从模糊愿望到服务契约

产品常用这样的语言提出需求：

> 用户上传一份合同，系统快速回答问题，并在必要时创建审批任务。

这句话有用，但还不足以指导实现。设计者需要继续问：

- “快速”是首 token 在 500 ms 内，还是完整答案在 5 s 内？
- 回答需要引用合同原文吗？引用到段落、页码还是条款？
- 合同是否包含多个版本，用户能访问哪些版本？
- 创建审批任务是建议，还是已经发生的外部动作？
- 系统允许哪些模型和区域处理机密内容？
- 用户断线后，任务是否继续？计费和重复提交如何处理？

把自然语言目标写成契约，系统才有边界。一个简化的在线请求契约可以是：

~~~json
{
  "task_type": "contract_question",
  "tenant_scope": "tenant-a",
  "principal_scope": "role:contract-reader",
  "input_revision": "contract-a-v12",
  "quality_target": "cited_answer",
  "deadline_ms": 3500,
  "requires_tools": false,
  "allowed_regions": ["cn-east"],
  "output_schema": "answer-with-evidence-v4"
}
~~~

契约中的字段要有来源。租户和主体来自身份系统，文档版本来自对象服务，工具权限来自策略服务，deadline 来自产品 SLA；不能让 prompt 中的一句话直接改变这些字段。

### 14.0.2 五个问题贯穿所有案例

读任何系统设计题时，都可以按五个问题组织思考：

1. **任务是什么**：系统要完成的是回答、检索、生成、预测，还是外部动作？
2. **边界在哪里**：哪些能力在系统内，哪些由上游或下游负责？
3. **状态是什么**：一次请求、会话、文档版本、模型部署和外部动作处于哪些状态？
4. **证据是什么**：怎样证明结果正确、权限有效、版本新鲜、动作确实发生？
5. **失败怎么办**：故障、超时、冲突、未知状态和数据删除如何恢复？

这五个问题比固定的“先说需求、再画架构、最后讲扩展”更重要。后者是表达顺序，前者是设计内容。

### 14.0.3 质量、延迟和成本必须同时量化

设一次任务是否成功的指示变量为 \(S_i\)，任务成本为 \(C_i\)，端到端延迟为 \(T_i\)。在一批 \(N>0\) 个任务上，任务成功率是：

~~~math
Q=\frac{1}{N}\sum_{i=1}^{N}S_i
~~~

同样在 \(N>0\) 时，平均请求成本是：

~~~math
\bar C=\frac{1}{N}\sum_{i=1}^{N}C_i
~~~

但平台更关心每个成功任务的成本：

~~~math
C_{\mathrm{success}}
=
\frac{\sum_{i=1}^{N}C_i}
{\sum_{i=1}^{N}S_i}
~~~

若某次调用包含模型、embedding、reranker、审核、工具和人工复核，\(C_i\) 应包含这些调用，而不是只写模型 API 价格。上式还要求 \(\sum_{i=1}^{N}S_i>0\)；若这一分母为零，单位成功成本应报告为“没有成功任务”，不能写成零。若没有采集到任何任务，即 \(N=0\)，成功率、平均请求成本和单位成功成本都应报告为“无样本”，不能用零代替。

对延迟则至少区分：

~~~math
T_{\mathrm{e2e}}
=
T_{\mathrm{queue}}
+T_{\mathrm{preprocess}}
+T_{\mathrm{retrieve}}
+T_{\mathrm{prefill}}
+T_{\mathrm{decode}}
+T_{\mathrm{postprocess}}
+T_{\mathrm{network}}
~~~

首 token 延迟（TTFT）通常止于第一个可展示 token，完整响应时间还要包含后续 decode 和后处理。一个系统可能 TTFT 很好，却因为每 token 生成慢而有糟糕的完整响应 p95。

### 14.0.4 架构图要表达责任，不只是连接

高层图可以这样画：

~~~text
客户端
  -> 接入与身份
  -> 请求契约与策略
  -> 编排器
      -> 检索
      -> 模型推理
      -> 工具执行
      -> 审核
  -> 响应协议
  -> 事件、指标、评估和审计

离线控制链：
数据/文档 -> 解析与索引 -> 评估集 -> 模型/策略版本 -> 灰度与回滚
~~~

每条箭头都应回答“谁负责什么”。例如，模型负责提出工具意图，授权服务负责判断权限，执行器负责提交动作；把三者画成一个“Agent 模块”会隐藏最重要的安全边界。

### 14.0.5 小白视角和专家视角如何衔接

小白先把请求想成一条流水线：请求进来，经过检查、计算和存储，最后返回结果。专家进一步问每一段的输入输出、资源约束、状态转移和可观测证据。

例如，“加入缓存”对小白意味着更快；专家会继续问：缓存的对象是什么，键包含哪些版本，读前是否校验权限，命中后是否仍要校验证据，失效通知丢失怎么办，缓存占满显存会不会让 p99 变差。两种视角不是两套答案，而是从直觉逐步走向可验证实现。

## 14.1 第一层建模：需求、约束与不可变事实

### 14.1.1 功能需求不等于系统目标

“支持文档上传”只是功能。真正的目标可能是“管理员发布后的制度在十分钟内可查询，且回答引用正确版本”。“支持流式输出”只是接口能力，真正的目标可能是“首个可理解片段在 800 ms 内到达，断线后不会重复计费”。

把功能写成可验收主张：

| 功能 | 可验收主张 | 主要证据 |
| --- | --- | --- |
| 多轮问答 | 在目标任务集上完成率达到约定值 | 任务评估与人工抽检 |
| 文档更新 | 新版本在承诺时间内成为可见版本 | 发布事件和索引 revision |
| 工具调用 | 未授权动作不产生外部副作用 | 授权日志和工具模拟器 |
| 流式输出 | TTFT 和断线恢复符合协议 | trace、事件序号和客户端回放 |
| 多租户 | 主体只能获得授权范围内的内容 | ACL 交叉测试和访问审计 |

数值需要根据产品和风险设定。若尚未测量，可以先写成待估计的目标，但不要把“支持”直接当作“已经达到”。

### 14.1.2 非功能约束也要有对象

延迟、可用性、成本和隐私不是漂浮在架构图旁边的形容词。它们应绑定对象：

- 是哪个接口的 p95，输入长度和输出长度如何分层？
- 是单租户可用性，还是整个服务的可用性？
- 成本是每请求、每成功任务，还是每月固定成本？
- 数据删除要求覆盖在线副本，还是还包括备份保留周期？
- 安全要求是防越权读取，还是防所有不当内容？

约束对象不清楚，后续优化很容易出现“指标变好了，但业务没有变好”的假象。

### 14.1.3 识别不可变事实和可变推断

系统设计里有些字段应该由权威系统给出：用户身份、租户归属、订单状态、文档版本、工具执行 ID。另一些字段是模型或分类器的推断：任务难度、答案置信度、是否需要升级。

把推断写回权威字段是常见事故来源。例如模型回答“审批已经提交”，不等于审批服务返回了提交 ID；模型判断“用户可以看这份文档”，不等于授权服务给出了允许结果。架构应让不可变事实拥有清晰的权威来源，让推断带有不确定性和证据引用。

### 14.1.4 先写状态机，再写组件

对会产生外部动作的任务，先写状态比先选消息队列更重要。一个审批请求可以经历：

~~~text
received
  -> validated
  -> planned
  -> awaiting_confirmation
  -> authorized
  -> submitted
  -> confirmed
  -> failed / unknown / cancelled
~~~

状态转移应由事件驱动，并满足不变量：未授权不能提交；未确认的外部结果不能被标记为失败；取消不能抹掉已经提交的外部 ID。存储、队列和 worker 都是实现这些不变量的手段。

## 14.2 通用容量模型：先算工作量，再谈组件

### 14.2.1 QPS 只是入口

假设峰值请求率为 \(\lambda_q\)，每个请求平均触发 \(a\) 次模型调用、\(r\) 次检索、\(e\) 次 embedding、\(t\) 次工具调用，内部工作量分别是：

~~~math
\lambda_{\mathrm{model}}=a\lambda_q
\qquad
\lambda_{\mathrm{retrieval}}=r\lambda_q
\qquad
\lambda_{\mathrm{embed}}=e\lambda_q
\qquad
\lambda_{\mathrm{tool}}=t\lambda_q
~~~

级联、重试和并行分支会让 \(a,r,e,t\) 大于 1。若只用外部 QPS 估算 GPU 和存储，会低估内部压力。

输入输出 token 也要独立计量。令平均输入 token 为 \(I\)，平均输出 token 为 \(O\)，则模型 token 工作量近似为：

~~~math
W_{\mathrm{token}}
=
\lambda_{\mathrm{model}}(I+O)
~~~

但 prefill 和 decode 的资源特性不同，最好分别记录 \(\lambda_{\mathrm{model}}I\) 与 \(\lambda_{\mathrm{model}}O\)。

### 14.2.2 Little 定律的直觉

在稳定系统中，平均在途请求数 \(L\)、吞吐率 \(\lambda\) 和平均停留时间 \(W\) 近似满足：

~~~math
L=\lambda W
~~~

如果每秒进入 20 个请求，端到端平均耗时 5 秒，则平均有约 100 个请求在途。这些请求占用连接、上下文、KV Cache、队列槽位和数据库状态。减少延迟不仅改善体验，也会降低并发状态占用。

Little 定律描述平均关系，不会告诉你 p99，也不保证突发流量下系统稳定。容量设计还要用长尾分布、峰值窗口和故障场景验证。

### 14.2.3 KV Cache 的显存预算

对 \(L\) 层、每层 \(n_{kv}\) 个 K/V 头、每头维度 \(d\)、序列长度 \(S\)、每元素 \(b\) 字节的模型，单序列 KV Cache 近似为：

~~~math
M_{\mathrm{KV}}
\approx
2L S n_{kv} d b
~~~

并发 \(N\) 个序列时：

~~~math
M_{\mathrm{total}}
\approx
N M_{\mathrm{KV}}
+M_{\mathrm{weights}}
+M_{\mathrm{workspace}}
+M_{\mathrm{overhead}}
~~~

其中 \(M_{\mathrm{overhead}}\) 包含页表、分配碎片、通信缓冲区和 runtime 元数据。这个账本适合容量初估，不应替代目标硬件上的压测。PagedAttention 通过更灵活的 KV block 管理减少碎片，是否改善某个负载的吞吐仍取决于请求长度和调度策略。

### 14.2.4 不要把模型卡参数当作 SLA

参数量、最大上下文、理论吞吐和 benchmark 分数是目录信息，不是线上 SLA。线上 SLA 还受 tokenizer、模板、并发、batch、网络、审核、检索和输出长度影响。可靠的设计会同时记录：

- 模型版本和推理 runtime。
- 输入长度、输出长度和工具步数。
- 目标并发和负载分布。
- TTFT、TPOT、完整响应 p95/p99。
- 任务质量、失败类别和回退率。
- 单位成功任务成本。

## 14.3 在线请求链路：每个阶段都要能解释

### 14.3.1 接入和身份

网关验证认证凭证、租户、主体、配额、请求大小和协议版本。身份信息进入后续上下文和缓存范围，但不应原样拼进 prompt。网关还应生成 trace ID 和幂等键候选，防止客户端重试造成重复业务请求。

### 14.3.2 预处理和请求分类

预处理计算 token 数、模态、文件版本、语言、任务类型、是否需要检索和工具。分类结果可以作为路由信号，但不能覆盖安全策略和权限事实。

一个结构化 RequestProfile 可能是：

~~~json
{
  "task_type": "policy_question",
  "input_tokens": 8200,
  "modalities": ["text"],
  "data_class": "internal",
  "needs_retrieval": true,
  "needs_tools": false,
  "deadline_ms": 2500,
  "citation_required": true
}
~~~

### 14.3.3 上下文构建不是字符串拼接

上下文构建器把会话事件、检索证据、系统策略和用户输入组织成模型可读的输入。它至少要回答四件事：

1. 哪些内容属于当前任务，而不是旧分支或被撤回的消息？
2. 哪些内容可以作为事实参考，哪些内容只是来自不可信来源的文本？
3. 每一块内容的版本、权限和来源是什么？
4. 在上下文预算不足时，先压缩什么，必须保留什么？

可以把上下文视为带来源的集合，而不是纯字符串：

~~~math
X
=
X_{\mathrm{policy}}
\cup
X_{\mathrm{conversation}}
\cup
X_{\mathrm{retrieval}}
\cup
X_{\mathrm{tool}}
\cup
X_{\mathrm{user}}
~~~

每个元素还应有 source、revision、visibility 和 trust metadata。模型看到一段检索文档，不代表这段文档获得了改变系统策略的权限；模型看到工具返回“已成功”，也不代表执行器的状态已经确认。

上下文预算可以写成：

~~~math
B_{\mathrm{needed}}
=
B_{\mathrm{policy}}
+B_{\mathrm{history}}
+B_{\mathrm{evidence}}
+B_{\mathrm{tool}}
+B_{\mathrm{input}}
+B_{\mathrm{output\ reserve}}
~~~

当 \(B_{\mathrm{needed}}\) 超出候选模型容量时，系统应采用有顺序的处理：删除重复证据、压缩低价值历史、缩小检索候选、改用异步长任务，最后才是明确拒绝。静默截断可能删掉否定条件、适用范围和安全限制，造成比返回错误更难发现的问题。

### 14.3.4 权限要在数据路径上生效

远岑的企业知识库有文档权限、字段权限和版本权限。权限判断不能只在页面显示时做一次，因为模型输入、检索缓存、摘要、日志和工具都可能成为数据泄露路径。

一个稳妥的检索顺序是：

~~~text
身份认证
  -> 获取当前授权范围
  -> 带 ACL 过滤检索候选
  -> 读取正文并再次校验版本
  -> 只把授权证据放入上下文
  -> 生成并审查回答
~~~

如果先在共享索引中取出所有候选，再在生成后遮盖答案，私有文档可能已经进入模型、缓存或日志。遮盖输出不能撤销已经发生的数据暴露。

权限结果也要有版本和有效时间。用户被移出项目后，旧的 response cache、retrieval cache 和会话摘要应被撤销；读路径还要检查当前授权，不能把缓存命中当成授权凭证。

### 14.3.5 编排器要管理可恢复状态

编排器协调模型、检索、审核和工具，但不应把整个任务藏在一个不可观测的函数里。建议为每个阶段记录事件：

~~~json
{
  "task_id": "task-204",
  "state": "retrieval_completed",
  "attempt": 1,
  "input_revision": "contract-a-v12",
  "evidence_refs": ["doc-88#clause-4"],
  "next_action": "generate_answer",
  "deadline_remaining_ms": 1810
}
~~~

每个阶段都要有超时、重试和取消语义。只读模型调用可以在瞬时网络错误后有限重试；工具写操作必须使用幂等键和状态查询；未知状态不能直接当作失败。

重试次数、调用放大和成功任务成本之间的关系可以近似表示为：

~~~math
A_{\mathrm{internal}}
=
1
+E[N_{\mathrm{retry}}]
+E[N_{\mathrm{cascade}}]
+E[N_{\mathrm{parallel}}]
~~~

其中 \(A_{\mathrm{internal}}\) 是每个外部请求平均产生的内部工作量倍数。它不能用固定常数代替，必须按任务类型和失败切片观测。

### 14.3.6 流式接口是一种有序事件协议

流式输出不只是把文本分成很多小片段发送。客户端需要知道每个事件的序号、类型、所属响应、是否可重放、是否最终完成以及是否发生错误。

一个简化事件序列是：

~~~text
response.started
  -> response.metadata
  -> response.output.delta(seq=1)
  -> response.output.delta(seq=2)
  -> response.citation.added
  -> response.completed
~~~

事件应带有单调递增序号和响应版本。客户端断线后，可以从最后确认的序号恢复；服务端若无法保证重放，就必须返回明确的不可恢复错误，而不是让客户端猜测缺失片段。

取消也要分层：取消模型生成、停止向客户端发送、取消尚未开始的工具任务，和撤销已经提交的外部动作不是一回事。对于已经提交的动作，客户端的取消请求不能假装动作从未发生。

### 14.3.7 观测应支持从结果回到原因

仅记录总耗时和 HTTP 状态码不够。一次 RAG 回答变差时，平台需要沿 trace 回看：

- 使用了哪一版请求分类和模型路由？
- 检索命中还是回源？使用了哪一版索引？
- 证据是否通过 ACL 和新鲜度检查？
- 模型输入和输出 token 是多少？
- 是否因为超时切换模型？
- 引用验证、输出审核和人工复核发生了什么？
- 最终任务是否成功，还是只是返回了文本？

指标、日志和 trace 需要关联同一个 request_id/task_id。OpenTelemetry 提供跨服务观测的通用概念，但合同正文、音频和工具参数属于敏感字段，必须有脱敏、访问控制和保留策略。

### 14.3.8 在线链路和离线控制链必须闭合

在线系统产生请求、响应、错误、用户反馈和工具结果；离线系统利用这些数据构造评估集、更新路由策略、重建索引、校准审核器和生成回归报告。两条链之间通过版本和血缘连接：

~~~text
线上请求
  -> 脱敏样本
  -> 标注/评估集版本
  -> 模型或策略实验
  -> 灰度配置
  -> 新线上 trace
~~~

不能把线上日志未经筛选地直接用于训练或评估。需要先处理权限、个人信息、数据代表性、标签质量和污染风险。离线指标改善后，也要在 shadow 或小流量中检查任务成功、成本和副作用。

## 14.4 案例一：设计 ChatGPT 类服务

### 14.4.1 服务边界

远岑聊天服务支持文本对话、文件问答、可选工具调用和流式响应。它不直接把任意数据库连接暴露给模型，也不把“模型生成了动作 JSON”视为动作已经执行。企业制度问答和审批协作是两个不同任务类型，前者通常只读，后者会产生外部状态变化。

服务契约包含：

- 创建会话、发送消息、生成响应、取消响应和列举历史。
- 每个响应都有唯一 response_id、父消息和模型版本。
- 结果可以是文本、引用、结构化动作意图或明确错误。
- 工具动作需要服务端授权，必要时等待用户确认。
- 计费依据实际消耗和重试/回退规则记录。
- 删除请求要能追踪消息、文件、索引和派生缓存。

### 14.4.2 数据模型：消息、响应和分支

聊天记录不应只有一个不断追加的文本字段。一个实用的数据模型可以拆为：

~~~text
Conversation
  - tenant_id
  - owner_id
  - current_branch_id
  - retention_policy

Message
  - message_id
  - conversation_id
  - branch_id
  - role
  - content_artifact_id
  - parent_id
  - created_at
  - visibility

Response
  - response_id
  - assistant_message_id
  - model_revision
  - router_revision
  - input_snapshot
  - status
  - usage
  - evidence_refs

ToolExecution
  - execution_id
  - response_id
  - idempotency_key
  - authorization_revision
  - external_status
~~~

消息内容和大型文件可以存为不可变 artifact，数据库保存摘要、哈希和引用。这样用户编辑一条消息时，可以创建新分支，不覆盖原始回答和评估证据。

### 14.4.3 请求状态和不变量

一次回答可以经历：

~~~text
accepted
  -> context_building
  -> awaiting_model
  -> streaming
  -> validating
  -> completed
  -> cancelled / failed / unknown
~~~

如果模型流式输出已经开始，客户端取消只能停止后续发送，不代表已经产生的 token 可以从计量系统中删除。若工具提交超时，响应状态应变为 unknown，直到根据幂等键查询外部服务。

重要不变量包括：

- assistant message 只能关联一个不可变 response 结果。
- 已完成响应不能被新的模型重试静默覆盖。
- 工具执行 ID 和外部系统 ID 关系可追溯。
- 删除消息后，派生摘要和缓存不能继续对新请求可见。
- 只有授权主体可以读取对应会话和 artifact。

### 14.4.4 上下文选择与记忆污染

最简单的上下文策略是保留最近消息，但它会在长会话中丢失早期约束，也会把用户曾经说过的猜测当成永久事实。远岑采用分层上下文：

1. 当前用户消息和系统策略。
2. 当前分支中与任务直接相关的最近消息。
3. 经过版本和权限校验的长期摘要。
4. 对当前问题重新检索的证据。
5. 工具返回的结构化状态。
6. 输出格式和引用要求。

摘要只是压缩后的推断，不能替代权威状态。比如用户说“我已经获得财务审批”，这个陈述可以进入会话，但真正的审批状态必须来自审批系统。

### 14.4.5 流式输出和断线恢复

SSE 适合服务器向客户端单向推送文本增量，WebSocket 适合需要双向事件的打断、实时音频和交互控制。无论选择哪种传输方式，应用层都要设计事件协议。

每个 delta 事件包含 response_id、seq、内容片段和产生阶段。服务端保存短期事件日志，客户端携带 last_seq 重连。重连时：

- 若事件仍在保留窗口，服务端从下一个序号重放。
- 若事件已被淘汰，服务端返回当前响应状态和完整结果摘要。
- 若响应仍在生成，客户端可以重新订阅。
- 若发生未知工具状态，客户端看到的是查询中的状态，而不是一条猜测性的“失败”。

流式审核可以对增量做状态累积，而不是只检查每个片段。敏感信息可能跨多个片段才形成完整模式；外部动作意图也可能在前后文合并后才清晰。

### 14.4.6 重复提交、计费和取消

客户端因网络超时重发消息很常见。网关应接收客户端幂等键，并将同一个会话、消息内容摘要、用户主体和幂等键绑定。重复请求返回已有 response_id，不能再次扣费或再次提交工具。

计费需要记录：

~~~math
C_{\mathrm{request}}
=
C_{\mathrm{input\ tokens}}
+C_{\mathrm{output\ tokens}}
+C_{\mathrm{retrieval}}
+C_{\mathrm{tool}}
+C_{\mathrm{review}}
~~~

取消发生在不同阶段，成本和语义不同。排队前取消可以释放槽位；prefill 过程中取消可能已经消耗 GPU；生成中取消要记录已生成 token；工具提交后取消不能撤回外部事实。

### 14.4.7 安全和数据治理

输入侧检查文件类型、大小、恶意内容、权限和提示操控；上下文构建器隔离不可信文档内容；工具执行器做服务端授权；输出侧检查隐私、未支持承诺和不应展示的内部字段。

日志要使用最小必要原则。完整 prompt、合同和音频不应默认进入所有 trace。可以保存哈希、artifact 引用、风险标签和截断后的调试片段；需要复核原文时再由授权人员按审计流程读取。

删除不是只删除会话表。还要处理摘要、检索缓存、响应缓存、评估样本、导出文件、异步队列和备份保留周期。

### 14.4.8 质量评估

聊天服务至少评估四层：

- 协议：事件序号、重连、取消和错误结构是否正确。
- 任务：是否真正解决用户问题，是否完成工具动作。
- 事实：引用是否存在、版本是否正确、主张是否得到支持。
- 体验：TTFT、完整延迟、追问率、重试率和用户反馈。

点赞率可以作为产品信号，但不能代替高风险任务的人工审计；模型输出更长也不能直接视为更有帮助。

### 14.4.9 故障复盘：把“回答错了”拆开

假设制度问答满意度下降。排查顺序应是：

1. 请求分类是否把制度问题路由到了不适合引用的模型？
2. 文档索引是否切换到了不完整版本？
3. 权限过滤是否使关键证据被排除？
4. 上下文构建是否截断了例外条款？
5. Response Cache 是否复用了旧策略结果？
6. 模型是否生成了没有证据支持的主张？
7. 引用验证或输出审核是否漏掉了问题？

这种归因比重新调 prompt 更有效，因为它区分了检索、版本、路由、生成和验证各自的责任。

## 14.5 案例二：设计大模型推理平台

### 14.5.1 推理平台的真正产物

推理平台不是“把模型放进 GPU 后提供一个 HTTP 接口”。它要把请求转换成可调度的 token 工作，并在不同模型、长度、优先级和租户之间提供可预测服务。

远岑的平台同时服务三类请求：

- 短文本分类，要求高吞吐。
- 交互式对话，要求低 TTFT 和稳定流式输出。
- 长文档分析，输入大、prefill 重，允许异步或较长等待。

如果三类请求共用一个无限队列，长文档会阻塞短请求；如果只追求 GPU 利用率，batch 等待可能破坏交互 SLA。因此平台的核心不是某个单独优化，而是把工作量、调度目标和失败边界显式化。

### 14.5.2 模型目录和部署单元

Model Registry 保存模型 artifact、权重摘要、tokenizer、模板、上下文限制、工具协议、量化配置和评估结果。部署单元则记录：

~~~json
{
  "model_revision": "medium-2026-07-18",
  "runtime_revision": "engine-v9",
  "tokenizer_revision": "tok-v4",
  "parallelism": {
    "tensor": 2,
    "pipeline": 1
  },
  "quantization": "bf16",
  "max_context": 131072,
  "max_batch_tokens": 32768,
  "regions": ["cn-east"],
  "quality_profile": "contract.zh.v12"
}
~~~

模型名称不足以确定行为。权重、模板、tokenizer、runtime、adapter、量化和并行配置共同决定一个可执行部署版本。请求路由和缓存都应绑定这个完整 revision。

部署流程先验证 artifact 完整性、显存需求、启动健康、协议兼容和小型回归集，再接入灰度流量。模型加载成功只说明进程能启动，不说明长上下文、结构化输出和流式取消都正确。

### 14.5.3 Prefill 和 decode 是两种工作

Prefill 读取输入上下文并建立 KV Cache，计算量随输入 token 增长；decode 每次生成少量新 token，却需要反复读取模型权重和历史 KV。两阶段对 batch、显存和延迟的敏感点不同。

交互式服务关注：

- TTFT：用户多久看到第一段结果。
- TPOT：后续 token 之间的间隔。
- 完整响应时间：生成结束和后处理完成的时间。

长输入会压高 prefill；长输出会拉长 decode；二者混在一个平均延迟里，调度器无法知道该优化哪一段。

### 14.5.4 连续 batching 和公平调度

静态 batching 要等一批请求都到齐，且通常要等最长请求结束；连续 batching 在请求完成、暂停或被取消时动态补入新请求。它能提高 GPU 的利用率，但必须配合 token 预算和公平策略。

可用的调度输入包括：

- 请求已等待时间和剩余 deadline。
- 输入 token 与预估输出 token。
- 租户优先级和配额。
- 当前 KV Cache 使用量。
- 请求是否处于 prefill、decode 或流式暂停。
- 是否有更高风险的外部动作等待执行。

一个简单的 token 工作量账本是：

~~~math
W_{\mathrm{step}}
=
\sum_{j\in\mathrm{batch}}
\left(
I_j^{\mathrm{new}}+O_j^{\mathrm{decode}}
\right)
~~~

其中 \(I_j^{\mathrm{new}}\) 是本 step 新做的 prefill token，\(O_j^{\mathrm{decode}}\) 是本 step 需要生成的 token 数。运行时还要受到显存可用量和 max batched tokens 的双重限制。

公平性不能只看平均吞吐。可以按租户统计等待时间、服务份额、deadline 违约率和被驱逐次数。一个大租户把 GPU 填满后，小租户即使平均利用率很好，也可能得到糟糕的 p99。

### 14.5.5 KV Cache、prefix cache 和会话亲和

KV Cache 绑定正在运行的序列；prefix cache 可以复用稳定前缀；会话亲和则是把同一会话尽量路由到保留其状态的 worker。三者不能混为一谈：

- KV Cache 的生命周期通常随请求或会话分支。
- prefix cache 的命中依赖 token 前缀和模型运行时兼容。
- 会话亲和是调度策略，可能在 worker 故障后失效。

系统要决定状态放在 GPU、CPU、远端内存还是重新计算。远端状态减少本地显存压力，但会增加网络延迟和一致性复杂度。对于短请求，重新计算可能比搬运状态更便宜；对于长稳定前缀，迁移或分层缓存才可能值得。

### 14.5.6 批处理和延迟的取舍

设请求等待窗口为 \(w\)，batch 带来的计算效率收益为 \(G(w)\)，排队延迟代价为 \(L(w)\)，可以把调度目标写成：

~~~math
J(w)
=
-C_{\mathrm{throughput}}G(w)
+\lambda_L L(w)
+\lambda_S \mathrm{SLA\_violations}(w)
~~~

\(G(w)\) 和 \(L(w)\) 必须通过目标硬件、请求长度和并发负载测量。没有一个对所有场景都正确的 batching window。交互式短回答可能使用很短窗口；离线批任务可以等待更久。

### 14.5.7 阶段解耦和路由

当 prefill 和 decode 的资源冲突严重时，可以把两阶段部署到不同资源池，或使用专门的调度策略。DistServe 研究了 prefill-decode 解耦的系统视角；它帮助理解为什么一个统一 worker 可能在长输入和长输出混合时出现干扰。

但阶段解耦会引入 KV 状态传输、路由、故障恢复和容量配比问题。若 prefill 池很快、decode 池不足，整体响应仍会被 decode 卡住；若状态传输耗时很大，解耦收益也可能消失。设计时要按 TTFT、TPOT 和完整任务延迟分别压测，而不是只看 GPU 利用率。

### 14.5.8 量化与投机解码的验证边界

量化减少权重或 KV 的存储和带宽，但可能改变算术、长上下文、代码和工具参数质量。发布前应对目标任务集做逐切片回归，至少包含：

- 数值和结构化输出。
- 长上下文引用。
- 中文和多语言。
- 工具参数与拒绝边界。
- 低并发和高并发延迟。

投机解码使用 draft model 提议 token，再由 target model 验证。它在接受长度足够时可以减少 decode 步骤，但收益受 draft 与 target 的相似性、batch、序列长度和实现开销影响。它不等于模型质量提升，也不替代 Response Cache 或 prefix cache。

### 14.5.9 过载、限流和降级

过载时不能让所有请求一起排队到超时。平台应根据任务和风险进行分层：

- 拒绝超过上下文或输出预算的请求。
- 限制低优先级长任务的并发。
- 对只读任务使用已有证据的受限回答。
- 把可异步的长文档分析转为任务队列。
- 保护高优先级租户的 token 和 GPU 配额。
- 对写工具保留授权和状态查询能力，不因过载重复提交。

降级后的结果必须标注能力边界。例如“实时索引暂不可用，只返回已核验的缓存版本”比静默给出旧答案更诚实。

### 14.5.10 观测和故障定位

推理平台需要把请求级和 worker 级指标连接起来：

- 请求：queue time、TTFT、TPOT、完整时间、输入/输出 token、回退、取消。
- batch：batch size、batched tokens、等待窗口、padding 或空槽比例。
- KV：使用量、命中率、驱逐、碎片和 OOM。
- worker：GPU 利用率、显存、通信、模型加载和健康状态。
- 质量：任务成功、结构化解析、引用支持、用户反馈。
- 成本：GPU 秒、模型调用、缓存节省和失败重试。

当 p99 上升时，先确定是排队、prefill、decode、KV 驱逐、网络还是后处理；“GPU 利用率 90%”本身不能说明瓶颈在哪里。

## 14.6 案例三：设计 RAG 系统

### 14.6.1 RAG 的产物是证据链

RAG 系统不只是向量数据库加一个生成模型。它的核心产物是：

~~~text
原始文档 artifact
  -> 解析版本
  -> chunk 和位置
  -> embedding/倒排索引版本
  -> 权限过滤后的候选
  -> 重排和证据选择
  -> claim 与引用
  -> 可审计回答
~~~

回答质量受到链路中最弱环节影响。模型很强但解析丢了表格，最终答案仍然可能错误；检索召回很高但没有权限过滤，系统可能泄露数据；引用链接存在但不支持回答主张，用户会得到虚假的可追溯感。

### 14.6.2 文档生命周期和版本切换

远岑把上传文件视为不可变 artifact。解析器产生结构化文本、页面/区域坐标、表格和元数据；每次修订产生新 revision。索引构建完成后，知识库通过一个可见指针切换到新版本：

~~~text
uploaded
  -> validated
  -> parsed
  -> chunked
  -> embedded
  -> indexed
  -> evaluated
  -> visible
  -> superseded / revoked
~~~

在新 revision 还未完成评估和权限校验之前，旧版本继续服务。切换要是原子的，避免文本来自新版本、向量来自旧版本的混合状态。

### 14.6.3 解析、chunk 和位置证据

固定字符长度切分实现简单，却可能把标题和定义分开，把表格行拆散，把代码块从上下文中截断。结构化切分应保留：

- 文档、章节、页码和段落 ID。
- 表格的行列关系和单位。
- 图片、图注和 OCR 区域。
- 代码语言、文件路径和行号。
- 标题层级和前后文关系。

chunk 不是越大越好。可以保留 parent section 作为展示和引用单位，再用较小 child chunk 做召回。这样模型获得足够上下文，用户也能定位原文。

### 14.6.4 混合检索和重排

向量检索适合语义相近的问题，BM25 等倒排方法适合精确术语、编号、产品名和错误码。两路候选可以用 Reciprocal Rank Fusion（RRF）组合：

~~~math
\mathrm{RRF}(d)
=
\sum_{m\in\mathrm{retrievers}}
\frac{1}{k+\mathrm{rank}_m(d)}
~~~

\(d\) 是候选文档，\(k\) 是平滑常数，rank 是该候选在某一路的名次。RRF 是排序组合方法，不保证最终事实正确；需要在目标任务集上测 Recall@k、MRR/NDCG、延迟和成本。

权限过滤可以理解为条件召回：

~~~math
P(\mathrm{evidence\ retrieved}\mid q)
=
P(\mathrm{retrieved}\mid q,\mathrm{authorized})
P(\mathrm{authorized}\mid q)
~~~

如果先检索再过滤，第二项不等于过滤后候选真正可见；工程上应使 ACL 成为检索条件或在可信数据层完成过滤。

重排模型可以使用 query、候选正文、标题和元数据重新判断相关性。强重排会增加延迟，且可能偏好较长或语气更明确的片段。评估时要观察“重排后是否找到了支持主张的证据”，不能只看向量相似度。

### 14.6.5 上下文选择和引用支持

把所有 top-k 片段塞进 prompt 会增加噪声。证据选择器应根据任务预算、来源可信度、版本、权限、互相冲突和主张覆盖来选择片段。

设回答包含主张集合 \(C\)，证据集合为 \(E\)，可以定义教学性的引用支持率：

~~~math
\mathrm{SupportRate}
=
\frac{\sum_{c\in C}w_c\mathbf{1}(\exists e\in E:\mathrm{supports}(e,c))}
{\sum_{c\in C}w_c}
~~~

\(w_c\) 可以让关键主张权重大于背景描述。supports 需要由人工、规则或经过校准的评估器判断，不能只用文本相似度代替。一个回答有十个引用但关键结论没有被支持，支持率仍然很低。

### 14.6.6 冲突、缺证和拒答

企业文档常有新旧制度冲突。系统应把冲突作为结果的一部分：列出版本、指出差异、依据当前可见 revision 选择，或将问题交给人工。不能让模型通过语气自信地抹平冲突。

没有证据时，正确行为可能是：

- 明确说当前资料不足。
- 请求用户指定文档或版本。
- 返回已确认的部分，并标出未确认部分。
- 对高风险动作停止执行并转人工。

“回答不知道”不是模型质量失败，而是在证据不足时守住事实边界。它是否合适，要结合任务风险和用户目标评估。

### 14.6.7 RAG 安全

检索内容是数据，不自动获得系统指令权限。文档可能包含恶意文本、伪造政策或诱导模型调用工具的内容。上下文构建器应标记来源和信任等级，工具授权仍由服务端独立完成。

检索缓存、embedding 和日志都要纳入删除和权限传播。文档撤销后，不仅新检索不能返回它，引用它生成的旧回答也不能继续对新用户可见，除非审计保留规则明确允许且访问受控。

### 14.6.8 RAG 的评估矩阵

一个完整评估至少分开：

- 解析：页码、表格、区域和文本恢复率。
- 检索：Recall@k、MRR/NDCG、权限后召回。
- 证据：claim support、引用正确性、版本新鲜度。
- 生成：answer correctness、完整性、拒答适当性。
- 系统：延迟、成本、索引更新时延、错误率。
- 安全：越权召回、间接指令、隐私泄露和误拒。

端到端分数不能替代分层诊断。若答案错了，先知道是没有召回、召回了错误版本、证据未覆盖，还是模型把证据解释错，修复才有方向。

## 14.7 案例四：设计实时语音助手

### 14.7.1 语音系统首先是时间系统

文本请求通常按“请求—响应”理解；语音助手同时处理采集时钟、网络时钟、识别时钟、模型生成时钟和播放时钟。用户可能还没有说完，ASR 已经给出 partial transcript；TTS 已经开始播放时，用户又开始说话。系统必须处理这些事件的先后关系，而不是把音频当成一条更长的文本。

远岑语音接待助手的目标是回答常见业务问题、查询订单并在必要时创建工单。它保留原始音频的策略与文本会话不同，工具动作也必须遵守同样的授权和幂等边界。

### 14.7.2 音频帧、VAD 和端点检测

客户端把音频切成固定时长的 frame 发送。网关为每个会话维护序号、时间戳和丢包统计。VAD 判断某段音频是否包含语音，端点检测进一步判断一轮话语何时结束。

VAD 太敏感会把背景噪音当成语音，导致错误唤醒；太保守会截掉开头或增加等待。端点太早会在用户停顿时抢答，端点太晚会让首响变慢。参数不能只在安静录音上调，应按设备、方言、噪声和网络条件切片评估。

### 14.7.3 partial 和 final transcript 的不同责任

partial transcript 适合提前做意图预判、检索预热和 UI 展示，但它会被后续音频修正；final transcript 才适合写入正式会话、触发高风险工具和计费。

一个安全状态流可以是：

~~~text
audio_received
  -> speech_started
  -> partial_transcript
  -> final_transcript
  -> intent_confirmed
  -> model_response
  -> tts_started
  -> playback_interrupted / completed
~~~

如果系统在 partial 阶段提前调用了修改工具，最终识别结果改变时就可能造成错误副作用。因此预判只允许做无副作用准备，例如预取公开 FAQ；真正工具调用必须等待稳定文本和服务端授权。

### 14.7.4 端到端延迟账本

语音体验通常关心从用户停顿到听到第一个可理解音频片段的时间：

~~~math
T_{\mathrm{first\ audio}}
=
T_{\mathrm{endpoint}}
+T_{\mathrm{asr\ final}}
+T_{\mathrm{intent}}
+T_{\mathrm{llm\ first\ token}}
+T_{\mathrm{tts\ first\ chunk}}
+T_{\mathrm{network}}
~~~

缩短其中一段可能把压力转移到另一段。比如提前使用 partial transcript 能降低 endpoint 等待，却可能增加错误意图和取消次数。语音系统要同时报告首响、打断反应时间、完整回答时间和用户重复率。

### 14.7.5 Barge-in：用户说话时系统必须让路

当用户在 TTS 播放过程中开始说话，系统需要：

1. 客户端降低或停止本地播放。
2. 服务端标记当前播放分支被打断。
3. 停止 TTS 生产和未发送音频。
4. 取消可取消的模型生成。
5. 保存已经播放到用户的文本范围。
6. 用新一轮 final transcript 构造上下文。
7. 对已经发生的工具动作查询状态，不重复提交。

“停止播放”不等于“撤销模型生成”，更不等于“撤销外部动作”。每一层都要有独立的取消语义。

### 14.7.6 流式 ASR、LLM 和 TTS 的背压

如果 ASR 产生 partial 的速度快于对话管理器处理速度，需要背压或合并中间结果；如果 LLM 生成文本快于 TTS 合成，文本缓冲会增长；如果 TTS 快于网络和播放，客户端队列会积压。

可以监控队列长度和各阶段速率：

~~~math
Q_{t+\Delta t}
=
Q_t
+\left(\lambda_{\mathrm{in}}-\mu_{\mathrm{out}}\right)\Delta t
~~~

当输入速率 \(\lambda_{\mathrm{in}}\) 长时间超过处理速率 \(\mu_{\mathrm{out}}\)，系统必须合并、降采样、暂停上游或拒绝新任务。无限队列只会把延迟推迟到用户无法接受的位置。

### 14.7.7 弱网、重连和隐私

音频链路要处理丢包、乱序、重连和设备切换。会话事件带序号，重连后可以从确认位置恢复；音频帧是否可重放要看隐私和存储策略。

录音保存便于质检，但会扩大敏感数据范围。系统可以按租户策略选择不落原音频、只保存短期加密片段、保存转写和特征摘要，或由经过授权的人工复核读取。删除请求要覆盖音频、转写、TTS 结果和评估副本。

### 14.7.8 语音评估

语音助手不能只看 ASR WER。至少分开：

- ASR：WER/CER、专有名词和数字识别。
- 交互：端点错误、首响、打断成功率、重复询问率。
- 任务：订单查询和工单创建是否正确。
- TTS：首块延迟、播放连续性、自然度和可懂度。
- 安全：录音隐私、工具越权和不当承诺。
- 用户：完成率、转人工率和满意度。

WER 下降不一定带来任务成功率上升；一个数字识别错误可能远比一个语气词错误严重。指标应按业务影响加权。

## 14.8 案例五：设计评估平台

### 14.8.1 评估平台的对象是主张

“新模型更好”不是一个足够精确的主张。应具体写成：

- 在中文合同问答切片上，引用支持率提高。
- 在相同工具权限和输入预算下，任务成功率不下降。
- 在相同质量下，单位成功任务成本降低。
- 新版本没有增加跨租户召回和高严重度工具失败。
- TTFT p95 保持在交互目标内。

每个主张需要数据集版本、对照系统、指标、切片、运行环境和允许的不确定性。评估平台的第一张表不是组件表，而是 claim/evidence 表。

### 14.8.2 评估任务和 artifact

一个可复现评估任务要冻结：

~~~json
{
  "evaluation_id": "eval-2026-08-11-17",
  "dataset_revision": "contract-set-v8",
  "model_revision": "medium-2026-07-18",
  "router_revision": "router-v27",
  "prompt_revision": "answer-v9",
  "retrieval_revision": "index-441",
  "decode": {
    "temperature": 0.0,
    "max_output_tokens": 1200
  },
  "scorer_revision": "citation-rubric-v3"
}
~~~

输出 artifact 包括原始响应、事件 trace、引用、工具意图、评估器结果、人工改判和成本。只保存最终总分，无法解释某个样本为什么改变，也无法重跑裁判。

### 14.8.3 数据切片决定结论范围

总体平均值可能掩盖长上下文、少数语言、复杂表格、高风险工具和特定租户的退化。评估集至少按任务类型、输入长度、语言、数据分类、工具需求、风险级别和来源版本切片。

设切片 \(g\) 中有 \(n_g>0\) 个样本，成功指标为 \(S_i\)，则：

~~~math
Q_g
=
\frac{1}{n_g}\sum_{i\in g}S_i
~~~

如果切片没有样本，即 \(n_g=0\)，应报告“该切片无样本”，不能把它记为 \(Q_g=0\) 或 \(Q_g=1\)。不同切片的样本量和不确定性不同。小切片出现一次失败，不能直接推断总体失败率；但若切片属于高严重度工具动作，也不能因为样本少就忽略。报告要同时写点估计、分母、置信区间或人工复核范围。

### 14.8.4 自动指标、裁判和人工评审

有标准答案的分类、抽取和代码测试可以使用确定性指标；开放生成要拆成事实正确、任务完成、引用支持、风格和安全等维度。LLM judge 能提高覆盖率，但它会受到位置、长度、措辞和模型家族偏差影响。

人工校准集合用于回答：裁判的判定与人工是否一致，错误集中在哪些类别，换一个模型或语言后是否仍然成立。可以报告一致率，但不能把一致率等同于真值；冲突样本应保留原始评语并进入 rubric 修订。

配对比较比孤立打分更适合比较两个系统。对每个同一输入 \(i\)，记录质量差异 \(D_i=Y_{i,B}-Y_{i,A}\)。在存在 \(n>0\) 个有效配对时，平均差异为：

~~~math
\bar D
=
\frac{1}{n}\sum_{i=1}^{n}D_i
~~~

如果没有有效配对，即 \(n=0\)，应报告“无有效配对”，不能把平均差异写成零。配对设计能消除一部分样本难度差异，但不消除数据污染、裁判偏差和切片选择偏差。

### 14.8.5 回归与发布判断

评估报告应区分“整体提升”和“不可接受退化”。例如新版本在普通问答上提高 3%，但在工具参数精确性上下降 1%；如果工具动作风险更高，整体平均分不能替代分层判断。

发布前可写成约束：

~~~math
Q_{\mathrm{core,new}}\geq Q_{\mathrm{core,base}}-\delta_q
~~~

~~~math
F_{\mathrm{high\ risk,new}}\leq F_{\mathrm{high\ risk,max}}
~~~

~~~math
T_{\mathrm{p95,new}}\leq T_{\mathrm{p95,max}}
~~~

~~~math
C_{\mathrm{success,new}}\leq C_{\mathrm{success,max}}
~~~

这些是发布条件，不是一个神秘总开关。若质量、安全、延迟和成本相互冲突，应说明哪个风险被保守处理、需要什么额外证据，以及是否只灰度到低风险范围。

### 14.8.6 评估平台本身也会出错

评估器可能读取错字段、引用旧答案、把缓存命中和模型生成混在一起，或因为超时样本没有进入分母而高估成功率。平台要对评估任务做自测试：

- 已知输入和预期输出的指标单元测试。
- 评估器版本和数据血缘检查。
- 故意注入空结果、超时和重复样本。
- 人工抽样比对原始响应与报告。
- 检查失败样本是否进入正确分母。
- 对裁判模型做位置、长度和模型身份对照。

评估系统不是事实源本身；它需要像生产系统一样被观测和审计。

## 14.9 五个案例之间的共同结构

### 14.9.1 ChatGPT 是会话状态问题

聊天服务的难点在于消息、分支、上下文、流式事件、取消和用户可见状态。模型只是其中一个计算阶段。若没有不可变消息、事件序号和恢复语义，模型再强也无法修复重复提交和断线丢失。

### 14.9.2 推理平台是资源调度问题

推理平台的难点在于 token 工作量、prefill/decode、KV 显存、批处理、公平性和尾延迟。它要把模型能力转化为稳定吞吐，不能只展示一个 GPU 利用率。

### 14.9.3 RAG 是证据和版本问题

RAG 的难点在于文档 artifact、解析、权限、索引、证据选择和引用。生成模型不是检索事实的替代品，引用也不是事实支持的自动证明。

### 14.9.4 语音助手是多时钟状态问题

语音助手要在 partial/final、播放、打断、取消和弱网事件之间保持一致。它不能把“音频转成文本”当作全部设计。

### 14.9.5 评估平台是证据生产问题

评估平台要把主张、数据、运行、指标、人工判断和成本连起来。一个漂亮的 dashboard 如果无法回到原始样本，就不能支撑重要发布决策。

## 14.10 设计复盘：一个完整故障案例

### 14.10.1 事故背景

远岑发布了新的合同问答路由：短问题优先使用小模型，长问题升级到中型模型；同时为重复问题启用租户级 Response Cache。发布后一小时，客服发现部分用户得到旧合同的到期日，另一些用户的回答延迟显著上升。

### 14.10.2 事件链

1. 合同 A 发布 v12，索引 revision 更新。
2. Response Cache 的键只含问题文本和租户 ID，没有合同 revision 和主体范围。
3. 路由器把带隐含合同上下文的短问题送给小模型。
4. 小模型生成了没有引用的答案，质量检查触发升级。
5. 升级路径重新检索，但缓存层仍返回旧证据。
6. 文档更新事件没有传播到响应缓存。
7. 热门旧键集中过期，回源请求同时进入中型模型，p99 上升。
8. 一名用户根据旧到期日创建了错误的审批草稿。

这不是一个单点“模型答错”事故，而是路由、缓存版本、质量回退、失效传播和容量保护共同失败。

### 14.10.3 影响范围和修复

先冻结合同类语义复用和自动审批提交，保留只读回源与人工确认。然后查询受影响缓存键的读日志、租户和主体范围，撤销旧证据和派生摘要，核对是否发生外部写动作。

修复包括：

- 缓存键加入合同资源、文档 revision、索引 revision、主体范围和策略 revision。
- 小模型路由只用于已验证的低难度任务；没有引用能力的候选不能满足 cited_answer 契约。
- 质量回退重新构建证据链，而不是把同一旧上下文发给更强模型。
- 版本更新事件写入失效队列，读路径仍做当前 ACL 和 revision 校验。
- 热点键采用 single-flight 和抖动 TTL，限制回源并发。
- 自动审批改为意图—授权—确认—提交—查询状态的状态机。
- 为短问题、长问题、缓存命中、回退和工具风险分别建立回归集。

### 14.10.4 复盘指标

设 500 个受影响请求中，旧版本命中 40 个，其中 8 个主体无权读取对应合同，2 个请求产生了错误审批草稿。应分别报告：

~~~math
\mathrm{stale\ rate}
=
\frac{40}{500}
=0.08
~~~

~~~math
\mathrm{cross\ scope\ rate}
=
\frac{8}{500}
=0.016
~~~

~~~math
\mathrm{side\ effect\ rate}
=
\frac{2}{500}
=0.004
~~~

这些比例描述观测样本，不等于全量真实风险概率。由于越权和外部副作用严重度不同，复盘还要列出每个事件的主体、资源、版本、实际影响和补救状态，不能只给一个平均数字。

### 14.10.5 从事故中提炼设计原则

事故之后，系统设计原则变得具体：

- 模型选择必须服从任务契约，不是只看价格。
- 缓存键必须表达权限、版本和数据依赖。
- 质量回退需要重新验证证据，不是盲目换模型。
- 工具写操作必须与回答缓存分离。
- 失效、删除和撤销要有在线读路径和异步清理两层。
- 容量指标要覆盖回源风暴和回退放大。
- 重要主张要能回到原始请求、证据和版本。

## 14.11 研究资料与证据边界

本章使用不同类型的资料，不能把它们当成同一种证据：

- [Attention Is All You Need](https://arxiv.org/abs/1706.03762) 解释 Transformer 注意力架构；它不是线上推理吞吐保证。
- [FlashAttention](https://arxiv.org/abs/2205.14135)、[FlashAttention-2](https://arxiv.org/abs/2307.08691) 解释 attention 计算和内存访问优化；实际收益依赖硬件、长度和实现。
- [vLLM/PagedAttention](https://arxiv.org/abs/2309.06180) 用于理解 KV Cache 管理；引擎文档和本地压测才决定具体配置。
- [DistServe](https://arxiv.org/abs/2401.09670) 讨论 prefill/decode 解耦的系统权衡；不保证每类流量都适合解耦。
- [RAG survey](https://arxiv.org/abs/2312.10997)、[DPR](https://arxiv.org/abs/2004.04906) 和 [BEIR](https://arxiv.org/abs/2104.08663) 说明检索增强和 benchmark 的研究视角；目标企业的权限、文档格式和新鲜度需要单独评估。
- [OpenTelemetry](https://opentelemetry.io/docs/)、[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455) 和 [WHATWG Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html) 提供观测和通信协议入口；业务事件、敏感数据治理和恢复语义仍由系统定义。
- [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) 与 [OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/) 提供风险治理和威胁组织语言；它们不是某个业务的完整权限策略。

论文是特定实验的研究证据，规范是协议语义，工程文档是实现说明，benchmark 是任务集比较，教学公式是容量或成本近似，远岑案例是合成练习。写设计结论时，要说明自己依据的是哪一层证据。

## 14.12 章末练习：把设计讲成可以运行的系统

1. 为企业合同问答写一份请求契约，列出身份、文档版本、权限、质量、延迟、输出 schema 和失败语义。
2. 计算一个峰值请求率为 40 QPS、平均每请求触发 1.3 次模型调用的服务的内部模型调用率，并说明重试和升级如何改变结果。
3. 设计一个有 3 个状态的工具执行状态机，解释外部超时后为什么进入 unknown，以及如何用幂等键查询恢复。
4. 为 RAG 画出文档从上传到可见版本的生命周期，标明解析失败、权限变更和删除事件的处理位置。
5. 比较“提高 top-k”和“增加 reranker”对召回、延迟、成本和证据支持的影响，写出需要测量的切片。
6. 为实时语音助手定义 partial transcript、final transcript、播放中断和取消事件，说明哪些事件可重放。
7. 设计一个评估 claim/evidence 表，至少包含数据版本、模型版本、路由版本、原始响应、评分器版本和人工复核。
8. 复盘本章的合同缓存事故：如果只能先修复一个问题，你会选择权限校验、版本失效、模型路由还是容量保护？说明风险排序依据。
9. 将一个你熟悉的系统设计题改写为“服务契约—状态机—证据—故障—指标”的五段式设计，并指出哪些结论仍需实测。

系统设计能力最终体现在：面对一个没有标准答案的问题，能够把假设说清，把边界画清，把成本和风险算清，把失败状态写清，并用可复现的证据说明为什么这个方案值得上线。
