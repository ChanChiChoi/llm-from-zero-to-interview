# 第三章：设计训练平台：从数据版本到可发布模型

训练平台不是一个把 python train.py 放到 GPU 上运行的页面。训练脚本只解决一次运行如何完成；训练平台要解决的是一组长期问题：谁提交了什么任务，任务使用哪一版数据和代码，为什么获得这些 GPU，运行中发生了什么，失败后能否从正确状态恢复，产出的模型是否经过评估，最后又是谁批准它进入线上。

大模型训练把这些问题放大了。一个小规模 LoRA 任务可能几分钟完成，一个继续预训练任务可能消耗数百张 GPU 数天或数周；数据、代码、镜像、tokenizer、并行策略和随机状态任何一个没有记录，结果就可能无法复现。节点、网络、存储或进程任何一个故障，都可能让训练停下来；如果 checkpoint 不完整，重新开始的成本可能非常高。

本章以“山海训练平台”为贯穿案例。山海平台服务多个研究团队，第一版有 512 张 GPU，支持继续预训练、SFT、LoRA、DPO 和离线评估。用户提交一个训练任务后，平台要把数据、代码、模型、资源、日志、checkpoint、评估和模型注册串成一条有血缘的链路。预训练、微调和实验任务会在相同系统里共享底层能力，但它们的调度、容错和质量标准不同。

## 3.0 训练平台的对象不是作业，而是可追溯的训练事件

一次训练的结果可以写成一个函数：

~~~math
\theta_{\mathrm{out}}
=
F(
\theta_{\mathrm{init}},
D_{\mathrm{version}},
C_{\mathrm{code}},
H_{\mathrm{hyperparam}},
E_{\mathrm{environment}},
S_{\mathrm{seed}},
P_{\mathrm{parallel}}
)
~~~

其中：

- θ_init 是初始模型或 checkpoint。
- D_version 是冻结的数据版本和处理清单。
- C_code 是代码仓库和 commit。
- H_hyperparam 是训练配置。
- E_environment 是镜像、驱动、框架和硬件环境。
- S_seed 是随机种子和数据顺序状态。
- P_parallel 是并行和切分策略。

如果这些输入只存在于用户的 notebook、shell 历史或口头约定里，平台就无法回答“这个模型到底怎么来的”。训练平台的元数据系统要把 F 的主要输入和输出显式保存下来。

### 给初学者：训练平台像一座有仓库和维修记录的工厂

数据是原材料，代码和配置是生产工艺，GPU 是机器，训练作业是生产批次，checkpoint 是中间产品，评估报告是质检单，模型注册表是成品仓库。

只把成品权重放进仓库而没有原材料批次、工艺版本和质检单，下一次出现问题时就无法追溯。机器中途断电时，如果没有可靠的中间产品，也只能从头生产。

### 给专家：区分计算正确性、恢复正确性和证据正确性

训练任务有三种不同的正确性：

- 计算正确性：梯度、参数更新和 loss 按预期执行。
- 恢复正确性：从 checkpoint 继续运行时，训练状态、数据位置和优化器状态没有被悄悄改变。
- 证据正确性：模型产物、指标和数据血缘真实对应这次运行，而不是被错误的日志、缓存或版本记录拼接出来。

一个任务可能计算正确但恢复错误；也可能训练成功但实验记录错误。平台必须分别观测和验证这三层。

## 3.1 先定义平台范围和生命周期

山海平台第一版支持四类任务：

| 任务 | 主要目标 | 资源特征 | 成功标准 |
| --- | --- | --- | --- |
| 继续预训练 | 用领域文本继续训练基座模型 | 多机多卡、运行时间长 | loss、泛化和数据合规 |
| SFT | 用指令示例训练对话行为 | 中等 GPU、数据质量重要 | 指令遵循、安全和领域质量 |
| LoRA | 低成本适配特定任务 | 少量 GPU、启动快 | 任务指标和适配器可复用 |
| 离线评估 | 比较模型和数据版本 | 可抢占、读多写少 | 评估报告和可追溯输入 |

DPO、偏好优化和后续 RL pipeline 可以复用数据注册、任务编排、资源调度、日志、评估和模型注册，但它们的奖励、偏好数据和安全审计需要额外模块。

### 3.1.1 平台边界

本章设计从用户提交训练意图开始，到模型通过评估进入 Model Registry 为止。集群底层的电力、物理机采购和云厂商结算作为外部依赖；具体训练算法在训练容器内执行，平台负责提供可复现和可观测的运行环境。

这个边界避免两个极端：

- 只讲训练脚本，忽略调度、权限和恢复。
- 把所有数据仓库、集群管理、模型部署和业务产品都塞进一章，最后没有一个边界讲透。

### 3.1.2 任务成功不是进程退出码

训练进程 exit code=0 只表示进程正常结束。平台还要检查：

- 是否处理了预期 token 数。
- 是否读取了正确的数据版本。
- loss 和梯度是否出现 NaN。
- checkpoint 是否完整且可恢复。
- 评估是否使用了独立数据。
- 模型产物是否与 manifest 一致。
- 是否满足安全和许可要求。

因此任务状态应分为计算状态和发布状态。一个训练作业可以 succeeded，但模型仍然 blocked，直到评估或审批完成。

## 3.2 训练任务的状态机

训练平台首先要把任务生命周期显式化：

~~~text
draft
  -> submitted
  -> validated
  -> queued
  -> allocated
  -> launching
  -> running
  -> checkpointing
  -> evaluating
  -> registered
  -> published

任何阶段都可能进入:
  failed
  canceled
  preempted
  blocked
~~~

状态转换需要有原因和操作者。比如：

- queued -> allocated：调度器分配了满足约束的资源。
- running -> checkpointing：训练主动保存或被抢占。
- running -> failed：出现无法恢复的代码、数据或硬件错误。
- running -> preempted：资源被高优先级任务回收。
- evaluating -> blocked：模型不满足安全或质量要求。
- registered -> published：经过审批和部署系统接受。

状态存储应采用条件更新，避免多个控制器同时把任务写成不同终态：

~~~math
transition\_allowed
\iff
state_{\mathrm{stored}}
=
state_{\mathrm{expected}}
~~~

每次状态变更记录 event_id、时间、控制器版本、原因和相关 artifact。这样恢复控制器可以从事件和当前状态判断下一步，而不是重复执行所有动作。

## 3.3 数据集：把原材料变成不可含糊的版本

大模型训练平台中，数据往往比页面和调度器更决定最终质量。数据服务要保证“同一个数据版本”能够被重新取回、重新处理和重新审计。

### 3.3.1 数据集注册

Dataset Service 至少记录：

- dataset_id 和版本号。
- 原始来源和采集时间。
- 数据格式和 schema。
- 文件清单、大小和内容哈希。
- 许可、用途和地域限制。
- 清洗、过滤和去重配置。
- tokenizer 和 special token 配置。
- train、validation、test 划分。
- PII、恶意内容和版权扫描结果。
- 创建者、审批者和变更记录。

数据集名称不够。一个不断追加文件的目录不应该被训练任务直接引用；任务应引用不可变版本或带明确快照的 manifest。

### 3.3.2 数据处理 DAG

数据处理可以表示为：

~~~text
raw source
  -> format normalize
  -> language and quality filter
  -> PII and policy scan
  -> deduplicate
  -> document segmentation
  -> tokenizer
  -> sequence packing
  -> train/valid/test split
  -> immutable manifest
~~~

每一步输出新的 artifact，并记录输入版本、处理代码、参数、镜像和输出哈希。失败时可以重跑某个节点，而不是重新处理全部原始数据。

### 3.3.3 去重与污染

去重不仅为了省存储，也影响评估可信度。训练集和验证集的重复内容会让 validation loss 看起来更好；预训练数据与下游 benchmark 的近重复会造成污染。

平台可以保存 exact hash、近重复指纹和数据来源标签。去重规则改变时，要生成新的数据版本，而不是覆盖旧结果。

### 3.3.4 Tokenizer 是数据依赖

tokenized 数据不能脱离 tokenizer 讨论。以下变化都可能让旧的 tokenized 文件不可直接复用：

- tokenizer vocab 变化。
- merge 规则变化。
- special token ID 变化。
- chat template 变化。
- 文本规范化变化。

数据 manifest 应保存 tokenizer 的名称、版本、文件哈希和 special token 配置。训练任务启动前，launcher 校验 tokenized 数据与模型配置是否一致。

### 3.3.5 Packing 和数据顺序

把多个短样本 packing 到固定长度序列可以提高计算利用率，但要处理样本边界、attention mask、loss mask 和跨样本泄漏。packing 策略变化会改变有效训练数据和 loss 统计，因此必须进入数据版本或训练 manifest。

数据顺序也影响恢复。若每次重启都从不同随机位置读取，模型可以继续训练，但严格复现实验会变得困难。平台至少要记录 epoch、global step、data shard、sample cursor 和 shuffle seed。

### 3.3.6 删除、撤回和数据血缘

如果一条数据后来被要求删除，平台要知道它进入了哪些 tokenized 文件、哪些 checkpoint、哪些评估样本和哪些派生模型。数据血缘不能只存在数据仓库，需要能从模型版本反查数据版本，也能从数据项正向追踪受影响的模型。

删除和 unlearning 是不同问题。删除原始数据可以阻止未来训练继续使用；已经进入模型权重的信息是否真正消失，需要额外评估和处理，不能由数据删除状态推断。

## 3.4 任务 manifest：把一次运行固定下来

训练任务提交后，平台要生成一个不可变或可签名的 manifest。它是调度、启动、恢复和审计的共同依据。

### 3.4.1 Manifest 的组成

~~~yaml
task_id: train-2026-0811-0042
project_id: dialogue-team
code:
  repository: internal/train-stack
  commit: abc123
image:
  reference: registry/train@sha256:...
model:
  init_checkpoint: models/base-v7
data:
  dataset_version: corpus-v12
  tokenizer_version: tok-v5
training:
  objective: sft
  global_batch_size: 1024
  max_steps: 20000
  seed: 17
resources:
  gpu_type: selected-by-scheduler
  gpu_count: 32
  topology: same-rack-preferred
distributed:
  strategy: fsdp
checkpoint:
  every_steps: 500
evaluation:
  suites: [instruction, safety, domain]
~~~

这里的 YAML 是概念示例。实际系统应把秘密写成 secret 引用，把可变标签解析成不可变 digest，把默认值展开成最终值，并保存平台控制器版本。

### 3.4.2 代码、镜像和依赖

只保存 git branch 不够，因为 branch 会移动。训练任务要保存 commit、子模块、未提交差异、依赖锁文件和容器镜像 digest。

如果允许用户在容器启动时在线 pip install，环境会随时间变化，也可能引入供应链风险。生产训练尽量使用经过扫描和签名的镜像；研究探索可以允许临时镜像，但必须标记为不可复现或低信任。

### 3.4.3 Secrets 不能进入 manifest 正文

数据源凭证、对象存储 token、实验平台密钥和模型下载凭证应通过 Secret Manager 注入。manifest 只保存 secret_id、用途、租户和版本。

日志要防止把环境变量和命令行完整打印出来。一个训练容器有权限读取数据，不代表它有权限读取所有项目的 secret。

### 3.4.4 可重放与不可变

重新提交任务时，可以使用原 manifest 作为输入，生成一个新的 task_id。新任务可以改变资源数量或只改变调度位置，但不能悄悄改变数据、代码和模型版本。

如果用户想改变超参，应该生成新的 manifest，并在 metadata 中记录 parent_task_id 和 diff。这样实验比较可以知道哪些变量真正改变了。

## 3.5 资源调度：GPU 数量只是约束的一部分

训练调度的对象不是“申请 32 张任意 GPU”，而是一个带拓扑、网络、存储和时间约束的资源请求。

### 3.5.1 资源需求

任务资源描述可以包含：

- GPU 型号、显存和数量。
- CPU、内存和本地 NVMe。
- 共享文件系统或对象存储。
- 节点数量和每节点 GPU 数。
- 高速互联要求。
- 可接受的故障域。
- 是否允许抢占。
- 最早开始时间和最长等待时间。
- 租户、项目和优先级。

FSDP、tensor parallel 或 pipeline parallel 可能要求特定的 GPU 分组和通信域。资源调度器如果只按 GPU 总数匹配，会把无法高效通信的节点拼在一起。

### 3.5.2 多队列

山海平台可以设置：

| 队列 | 适合任务 | 调度策略 |
| --- | --- | --- |
| fast-experiment | 少量 step 的实验 | 低等待、限制最大 GPU |
| finetune | SFT、LoRA、DPO | 常规公平队列 |
| large-train | 继续预训练 | 资源预留、连续运行 |
| evaluation | 模型评估 | 可抢占、发布前优先 |
| recovery | 失败任务恢复 | 继承原任务优先级 |
| emergency | 高优先级修复 | 需审批和审计 |

队列数量不是越多越好。每增加一类队列，就增加资源碎片和公平性规则。关键是把交互实验的等待目标与大训练的连续资源目标分开。

### 3.5.3 GPU 小时和队列

任务的资源成本近似为：

~~~math
GPUH
=
G\times T_{\mathrm{run}}
+
G\times T_{\mathrm{retry}}
+
G\times T_{\mathrm{preempt\_waste}}
~~~

G 是实际占用 GPU 数，T_run 是有效训练时长。失败重试和被抢占但未保存的运行时间都应计入成本。

队列等待时间可以写为：

~~~math
T_{\mathrm{wait}}
=
T_{\mathrm{resource\_wait}}
+
T_{\mathrm{image\_pull}}
+
T_{\mathrm{data\_stage}}
+
T_{\mathrm{launch}}
~~~

如果任务一直排队，不应通过盲目增加优先级解决，而要检查 GPU 碎片、队列配额、拓扑约束和任务请求是否过大。

### 3.5.4 公平与利用率

公平调度和 GPU 利用率会冲突。让大任务优先凑齐资源可以提高通信效率，却可能让小团队长时间没有资源；过度切碎集群可以降低等待，却让大任务无法启动。

平台可以使用配额、借用额度、老化优先级、资源预留和抢占组合解决。规则必须可解释：用户知道为什么排队，管理员知道哪个团队消耗了多少资源。

### 3.5.5 抢占的前提

抢占只有在任务可恢复、检查点可靠、状态传播正确时才有价值。若一个任务每小时保存一次，刚启动就被抢占，可能浪费大量 GPU；若保存过于频繁，又会降低训练吞吐和占满存储。

抢占策略要考虑保存时间和恢复时间。一个保存 checkpoint 需要十分钟的任务，不应在只剩五分钟运行窗口时被启动。

## 3.6 分布式训练：数据并行不是唯一答案

训练平台不需要重写每种分布式框架，但必须理解不同并行策略的资源和故障含义。

### 3.6.1 数据并行

数据并行让每个 rank 持有模型副本，处理不同数据，反向后通过 all-reduce 同步梯度。它实现简单，但每张 GPU 都要保存完整模型、梯度和 optimizer state。

同步数据并行的一个训练 step 通常包含：

~~~text
load batch
  -> forward
  -> backward
  -> gradient synchronization
  -> optimizer step
~~~

当通信时间接近计算时间时，增加 GPU 不一定提高吞吐。

### 3.6.2 FSDP、ZeRO 与状态切分

FSDP 或 ZeRO 类方法把参数、梯度和 optimizer state 在 rank 之间分片，降低单卡显存压力。它们在通信、参数 all-gather、梯度 reduce-scatter 和 checkpoint 组织上有额外复杂度。

一个理想化的 Adam 混合精度训练内存账本可以写成：

~~~math
M_{\mathrm{replica}}
\approx
M_{\mathrm{bf16\_weights}}
+
M_{\mathrm{fp32\_master}}
+
M_{\mathrm{gradients}}
+
M_{\mathrm{adam\_moments}}
+
M_{\mathrm{activations}}
+
M_{\mathrm{runtime}}
~~~

FP32 master 和两个 Adam moment 会让训练状态远大于推理权重。具体字节数随实现、精度、激活重计算和优化器变化，因此只能作为量级模型。

状态分片后，单卡内存近似降低，但通信和参数重建成本上升。平台需要把 parallel_strategy、shard layout 和 checkpoint format 一起记录。

### 3.6.3 Tensor parallel

Tensor parallel 把单层矩阵或 attention 计算切到多个 GPU，需要频繁的高速通信。它对节点拓扑和互联带宽敏感，适合模型单卡放不下或希望在层内扩展的场景。

### 3.6.4 Pipeline parallel

Pipeline parallel 把不同层放到不同设备，微批次依次通过。它可以容纳更深的模型，但会产生 pipeline bubble，调度和故障恢复更复杂。

### 3.6.5 Sequence 或 context parallel

长序列训练可以进一步切分序列维度，降低激活和注意力压力，但需要额外通信和 mask 处理。是否采用取决于序列长度、模型结构和网络。

### 3.6.6 混合并行

大模型训练通常组合数据、张量和流水线并行。可以把总 GPU 数表示为：

~~~math
G_{\mathrm{total}}
=
D_{\mathrm{data}}
\times
T_{\mathrm{tensor}}
\times
P_{\mathrm{pipeline}}
~~~

这里的关系是理想化的资源分解；实际还可能有 sequence/context parallel、expert parallel 和冗余副本。平台不应只保存 total GPU count，而要保存各维度和拓扑。

### 3.6.7 论文事实和平台结论

Megatron-LM、ZeRO 和 PyTorch FSDP 资料分别讨论模型并行、状态分片和分布式训练机制。它们的论文或文档不能直接推出山海平台的吞吐、稳定性或最佳配置。

平台自己的结论必须来自与模型、序列长度、batch、网络、硬件和 checkpoint 方式匹配的基准。资料说明“可以如何做”，项目基准说明“在这里做得怎样”。

## 3.7 通信、拓扑和训练步时间

GPU 利用率不是训练效率的充分指标。训练速度由计算、输入、通信和同步共同决定。

### 3.7.1 训练步时间

可以用简化模型表示：

~~~math
T_{\mathrm{step}}
\approx
\max(
T_{\mathrm{compute}},
T_{\mathrm{input}},
T_{\mathrm{communication}}
)
+
T_{\mathrm{serialization}}
~~~

如果通信和计算能够重叠，取最大值只是近似；如果不能重叠，时间可能更接近几项相加。平台要通过 profiler 和通信指标判断，而不是凭 GPU utilization 猜测。

### 3.7.2 有效吞吐

以 token 为单位的有效吞吐可以写为：

~~~math
R_{\mathrm{token}}
=
\frac{
N_{\mathrm{global\_batch}}
\times
N_{\mathrm{tokens/sample}}
}{
T_{\mathrm{step}}
}
~~~

global batch 要说明是每个 rank 的 batch、全局 batch 还是累积后的有效 batch。梯度累积会改变优化器更新频率，因此配置中要分别记录 micro batch、gradient accumulation 和 global batch。

### 3.7.3 MFU 和利用率边界

Model FLOPs Utilization 可以粗略写成：

~~~math
MFU
=
\frac{
F_{\mathrm{achieved}}
}{
F_{\mathrm{peak}}
}
~~~

它需要明确 FLOPs 估算方法、模型结构、硬件峰值和是否包含通信。GPU 利用率高可能只是等待内存或通信，MFU 高也不代表 loss 或数据质量正确。性能指标必须和训练质量一起看。

### 3.7.4 NCCL 和网络故障

分布式任务可能出现：

- rank 不一致。
- master 地址或端口错误。
- NCCL 初始化失败。
- 某个 rank OOM，其他 rank 等待。
- 网络丢包或带宽下降。
- GPU 拓扑与预期不符。
- 进程组进入 collective hang。

平台 launcher 要把 world_size、rank、节点清单、网络接口和通信配置写入日志。训练监控要能显示哪个 rank 首先报错，而不是只看到主任务最终 timeout。

### 3.7.5 拓扑感知调度

如果 tensor parallel 要求高速互联，scheduler 应优先选择同一节点或同一高速互联域；如果只是数据并行，跨节点代价可能不同。任务 manifest 要声明 topology constraint，调度器返回实际分配拓扑，训练报告中记录通信基准。

## 3.8 训练启动：把分布式复杂性收进 launcher

用户不应该手工填写每个 rank，但平台不能隐藏所有分布式事实。

### 3.8.1 Launcher 输入

Launcher 读取：

- 任务 manifest。
- 分配的节点和 GPU。
- 分布式策略。
- 数据和 checkpoint 挂载。
- 网络和通信配置。
- secrets 引用。
- 日志和监控 endpoint。
- 取消和 checkpoint 信号。

它生成每个节点的环境变量和启动命令，并把展开后的 launch manifest 保存下来。

### 3.8.2 进程组初始化

典型初始化需要 world_size、rank、local_rank、master_addr 和 master_port。launcher 必须处理：

- 节点启动顺序变化。
- 某节点镜像拉取失败。
- 端口冲突。
- rank 进程提前退出。
- 主节点故障。
- 任务取消时的进程清理。

不能只在启动脚本里写一个固定 IP。集群调度每次可能分配不同节点，恢复任务也可能使用不同的 rank 映射。

### 3.8.3 训练容器和挂载

训练容器需要访问模型、数据、checkpoint 和日志，但这些路径的读写权限不同：

- 原始数据通常只读。
- 临时缓存可写但可删除。
- checkpoint 目录由训练任务写入。
- 模型注册产物需要经过提交和校验。
- 日志 endpoint 不能让任务任意覆盖其他任务。

运行时要限制网络访问、GPU 可见性和 secret 范围。用户代码具有很高权限，不能把所有内部服务直接暴露给容器。

## 3.9 Checkpoint：训练平台的生命线

Checkpoint 设计是训练平台最需要深入展开的部分，因为它同时影响训练速度、存储、恢复、抢占和审计。

### 3.9.1 两种产物不能混淆

模型权重适合推理或初始化另一个任务；训练 checkpoint 还需要优化器和运行状态。

完整恢复状态可能包括：

- 模型参数。
- 混合精度 master weights。
- 梯度或梯度缩放器。
- optimizer state。
- scheduler state。
- global step 和 epoch。
- 数据 shard 和 sample cursor。
- 随机数状态。
- 并行切分信息。
- 代码和配置版本。

只保存权重时，用户可以从相同模型开始新的训练，但不能宣称“严格断点续训”。

### 3.9.2 Checkpoint 一致性

多机训练保存 checkpoint 时，所有 rank 必须对保存时刻有一致认识。一个 rank 已经写完而另一个 rank 仍在更新，如果直接发布目录，恢复可能读取混合状态。

可以使用：

1. 生成 checkpoint_id 和目标临时目录。
2. 各 rank 写自己的 shard 和 checksum。
3. barrier 或协调器确认所有 shard 完成。
4. 写全局 manifest。
5. 原子提交一个 COMMITTED 标记。
6. 注册服务只读取已提交版本。

恢复时先检查 manifest、所有 shard、checksum、模型配置和并行布局，再让训练进程加载。

### 3.9.3 分片和格式

全量 checkpoint 可能无法由单个进程汇总，也不应要求一个中心节点承受全部写带宽。分片 checkpoint 让每个 rank 写自己的状态，恢复时按当前拓扑重新映射。

旧拓扑和新拓扑可能不同。若 checkpoint 的 shard layout 与新的 world size 绑定，恢复器需要支持 reshard；否则只能用相同的并行规模恢复。这个限制要写进模型产物元数据。

### 3.9.4 保存频率

保存频率的取舍可以用期望损失表示：

~~~math
C_{\mathrm{checkpoint}}
=
C_{\mathrm{write}}
+
C_{\mathrm{storage}}
+
C_{\mathrm{recovery\_loss}}
~~~

保存间隔越短，写入和存储成本越高，但故障时丢失的有效训练时间更少。若任务平均每六小时发生一次故障，checkpoint 间隔为一小时，故障前平均可能丢失约半小时有效计算；这是粗略期望，实际还受故障分布和保存耗时影响。

### 3.9.5 原子提交和校验

训练进程不应直接把最终目录作为可见路径。正确流程通常是临时目录、分片写入、校验、全局 manifest、原子 rename 或 commit marker。

对象存储可能提供最终一致或分段上传语义，平台要验证“目录存在”是否真的等于所有对象可读。恢复任务在加载前应检查文件大小、checksum、版本和可读性。

### 3.9.6 清理策略

checkpoint 清理不能只按文件修改时间：

- 保留最近 K 个恢复点。
- 保留指标最好的 K 个。
- 保留发布前的里程碑。
- 保留合规要求的版本。
- 临时 checkpoint 在任务终态后按策略过期。
- 失败任务的损坏或未提交目录可安全清理。

清理动作本身要有审计记录，不能让用户以为某个模型可恢复但平台已经删除了唯一 checkpoint。

## 3.10 从故障中恢复：先分类，再决定重试

训练失败不是一个状态。错误分类决定是否重试、从哪里恢复以及谁承担成本。

### 3.10.1 可重试的基础设施故障

例如节点重启、可恢复的网络抖动、临时对象存储错误和可替换 GPU 故障。平台可以重新调度，读取最近 COMMITTED checkpoint，并记录恢复损失。

### 3.10.2 不应盲目重试的错误

代码异常、shape mismatch、配置错误、数据 schema 错误、tokenizer 不匹配和确定性 OOM 通常重试不会解决。平台应停止任务，生成诊断建议，并保留现场。

### 3.10.3 训练不稳定

loss NaN、gradient explosion、eval 突然退化、吞吐异常下降都可能不是硬件故障。平台应在检测到异常时保存最后状态和少量诊断快照，再暂停或终止，而不是继续消耗 GPU。

### 3.10.4 恢复正确性

恢复不仅是从 checkpoint 读回权重。要比较：

- global step 是否正确。
- optimizer 和 scheduler 状态是否正确。
- random state 是否恢复。
- data cursor 是否跳过或重复样本。
- world size 和 shard layout 是否兼容。
- learning rate 曲线是否连续。
- 评估指标是否可解释地接续。

严格复现需要更强的确定性；工程恢复有时允许数据顺序略有变化，但报告中要明确区别“精确恢复”和“近似续训”。

### 3.10.5 弹性训练

PyTorch Elastic 等机制允许 worker 数量变化或在故障后重新启动，但弹性改变了数据并行和优化轨迹。平台需要记录每次 membership change、world size、rank 映射和重新分片。

弹性训练适合追求资源利用和可恢复性，不应在没有评估的情况下宣称与固定 world size 完全等价。

## 3.11 实验追踪和血缘

实验追踪的价值不是画漂亮的 loss 曲线，而是把“结果”连接回“条件”。

### 3.11.1 最小实验记录

每个 run 至少记录：

- task_id 和 parent_task_id。
- manifest digest。
- 数据集及其处理 DAG。
- 代码 commit 和镜像 digest。
- 初始模型和 tokenizer。
- 超参、随机种子和并行策略。
- 设备、节点和 world size。
- step、epoch、token 数和时间。
- loss、学习率、梯度范数和吞吐。
- checkpoint 和评估结果。
- 终态、失败原因和资源成本。

### 3.11.2 指标不能只存最终值

loss 曲线、学习率曲线、吞吐、GPU 利用率和通信时间需要按 step 或时间记录。只保存最终 loss 会隐藏训练中途 NaN、数据加载停顿和恢复后的行为变化。

高频指标可以聚合或采样，但要保存聚合规则和原始 artifact 的引用。评估报告要指向具体的 checkpoint，而不是只写“best model”。

### 3.11.3 实验比较

比较两个任务时，平台需要生成差异：

~~~math
\Delta
=
Diff(
code,
data,
model,
hyperparam,
environment,
parallel,
evaluation
)
~~~

如果只改变 learning rate，其他变量应显示为 equal；如果数据版本也变了，模型效果差异不能简单归因于 learning rate。

### 3.11.4 实验系统与训练系统的边界

MLflow 等实验追踪工具可以记录参数、指标和产物，但训练平台还需要租户权限、资源成本、任务状态、恢复事件和数据血缘。实验追踪工具可以是一个组件，不能替代整个训练控制面。

## 3.12 训练过程监控：从 loss 到系统健康

训练平台需要同时观察算法指标和基础设施指标。

### 3.12.1 Loss 和梯度

要监控：

- training loss。
- validation loss。
- learning rate。
- gradient norm。
- overflow 或 loss scale。
- 参数更新幅度。
- NaN/Inf 计数。

loss 不下降可能是数据、学习率、模型、标签或代码问题；loss 下降很快也可能是数据泄漏或训练集重复。平台需要把 loss 与数据版本和评估一起解释。

### 3.12.2 吞吐和 MFU

训练吞吐可用 tokens/s、samples/s 和 steps/s 表示。MFU 用于估算模型计算占硬件峰值的比例，但必须固定计算口径。

如果吞吐下降，排查顺序可以包括：

- 数据读取是否变慢。
- checkpoint 是否占用过长时间。
- rank 是否不均衡。
- all-reduce 是否变慢。
- 某个 GPU 是否降频或出现错误。
- 节点拓扑是否改变。
- 日志或监控是否造成阻塞。

### 3.12.3 告警等级

小型实验的单次失败可以进入通知；大任务的 checkpoint 连续失败、loss NaN、多个 rank hang、存储容量不足和 GPU ECC 错误应高优先级告警。

告警要关联 task_id、run_id、rank、节点、最近 checkpoint 和 manifest digest。只有一条“训练失败”日志无法支持恢复。

## 3.13 评估和 Model Registry：训练结束后的发布条件

训练任务完成只是计算阶段结束，不是模型可以上线。

### 3.13.1 评估分层

不同任务需要不同评估：

- 继续预训练：validation loss、领域能力、污染检查。
- SFT：指令遵循、事实性、拒答质量和领域任务。
- LoRA：目标任务指标、基座能力保持和适配器兼容性。
- DPO：偏好质量、安全、长度偏差和分布外行为。
- 代码模型：编译、测试和安全扫描。
- 多语言模型：各语言切片和退化情况。

评估集、判定器和报告版本也要进入血缘。模型通过一个 benchmark 不代表满足所有部署任务。

### 3.13.2 训练中和训练后评估

训练中评估用于监控趋势、早停和发现崩溃；训练后评估用于发布决策。二者不应使用同一批数据而不标记，否则早停和最终报告会互相污染。

评估任务应该引用 checkpoint_id、模型版本、数据集版本、代码版本和评估器版本。报告中明确哪些是训练中观察、哪些是独立 holdout。

### 3.13.3 Model Registry

注册模型时保存：

- model_id 和 immutable version。
- 来源 task_id。
- 基座模型和适配器关系。
- 权重或分片位置。
- tokenizer 和 chat template。
- 数据和代码血缘。
- 评估报告。
- 安全和许可报告。
- 推理要求。
- 审批、状态和所有者。

注册并不等于发布。模型可以处于 candidate、approved、staged、published、deprecated 或 blocked 状态。推理平台只加载符合策略的版本。

### 3.13.4 适配器和合并权重

LoRA 等适配器可能独立发布，也可能与基座合并。平台要记录适配器所依赖的 base model version、target modules、rank、alpha、tokenizer 和合并方式。

同一个适配器不能默认兼容所有同名基座模型。注册服务应在发布前验证权重结构、配置和推理模板。

## 3.14 多租户、安全和合规

训练平台运行用户代码、读取敏感数据并产生核心模型资产，安全边界比普通 Web 服务更复杂。

### 3.14.1 权限模型

权限至少覆盖：

- 项目和团队。
- 数据集读取和导出。
- 训练任务查看和取消。
- GPU 配额和优先级。
- checkpoint 读取和删除。
- 模型注册和发布。
- 评估报告和安全报告。
- secret 使用。

用户可以查看自己的任务，不一定可以查看其他租户的日志和配置。平台管理员的紧急访问也应有临时授权和审计。

### 3.14.2 容器和代码隔离

训练代码可能执行任意 Python、编译自定义算子或访问网络。平台要控制：

- 容器镜像来源和签名。
- GPU、CPU、内存和文件系统权限。
- 原始数据是否只读。
- 外网访问和内网服务访问。
- secret 注入范围。
- 临时目录和进程权限。
- 训练完成后容器清理。

不能因为用户是内部员工，就把所有集群凭证和其他项目的存储挂载进去。

### 3.14.3 模型和数据出口

模型权重、数据快照和日志都可能有外部导出风险。下载、复制和跨区域传输应有权限、审批、审计和水印或签名策略。

### 3.14.4 供应链

代码 commit、容器镜像、Python 依赖、预训练权重和 tokenizer 都可能成为供应链入口。平台应保存 digest、扫描报告和来源。研究试验允许更灵活，发布候选则需要更严格的 artifact 约束。

### 3.14.5 合规删除

删除数据后，平台要根据血缘确定哪些 tokenized artifact、评估数据、checkpoint 和模型受到影响。保留合规所需审计记录与删除用户内容不是矛盾，但要区分内容与证明事件。

## 3.15 成本：训练一次与浪费一次的区别

训练成本不仅是 GPU 运行时长，还包括失败、空闲、通信、存储和人工。

### 3.15.1 资源账本

任务成本可以近似为：

~~~math
C_{\mathrm{job}}
=
G\times T_{\mathrm{active}}\times P_{\mathrm{GPU}}
+
C_{\mathrm{storage}}
+
C_{\mathrm{network}}
+
C_{\mathrm{checkpoint}}
+
C_{\mathrm{failure}}
~~~

G 是 GPU 数，T_active 是有效运行时长，P_GPU 是单位 GPU 时间成本。C_failure 包括失败重试、被抢占丢失的计算和人工排障成本。

### 3.15.2 Smoke test 的价值

大规模训练前先跑少量数据、少量 step 和小资源配置，可以发现：

- shape mismatch。
- tokenizer 不兼容。
- loss mask 错误。
- checkpoint 无法写入。
- NCCL 初始化失败。
- 显存超限。
- 评估脚本无法读取输出。

Smoke test 的成本很小，却能避免把明显错误扩大到数百张 GPU。

### 3.15.3 早停和预算

训练任务可以设置最大 GPU 小时、最大 step、验证集无提升的 patience 和异常 loss 阈值。自动早停要保留原因和最后 checkpoint，不能只杀进程。

超参搜索还要把搜索空间、并发数量和单任务预算一起控制，避免几十个低质量配置把大集群占满。

### 3.15.4 Checkpoint 存储成本

保存 optimizer state 的完整 checkpoint 可能远大于推理权重。平台可对恢复点、发布权重、评估快照和归档版本采用不同存储策略，但不能在用户需要恢复时已经删除所有训练状态。

## 3.16 完整案例：山海平台提交一个 SFT 任务

现在把上述组件串成一次真实运行。

### 3.16.1 用户请求

对话团队提交一个 SFT 任务：

- 基座模型 base-v7。
- 数据集 dialogue-sft-v12。
- tokenizer tok-v5。
- 32 张 GPU。
- FSDP。
- 20,000 steps。
- 每 500 steps 保存 checkpoint。
- 每 2,000 steps 运行指令遵循和安全评估。
- 完成后注册 candidate 模型，不自动发布。

### 3.16.2 校验阶段

平台检查：

1. 用户是否属于 dialogue-team。
2. 是否有 dialogue-sft-v12 的读取权限。
3. base-v7 与 tok-v5 是否兼容。
4. 镜像 digest 是否存在并通过扫描。
5. 32 张 GPU 是否在预算内。
6. 训练配置与模型结构是否匹配。
7. 评估集是否独立于训练数据。
8. checkpoint 目标存储是否有空间。
9. 是否包含未授权 secret。

校验通过后生成 immutable manifest，任务进入 queued。

### 3.16.3 调度阶段

scheduler 发现一个节点组拥有 32 张满足显存和网络要求的 GPU。它记录：

- 节点列表。
- 每节点 GPU 分配。
- topology。
- driver、CUDA 和 NCCL 版本。
- 资源队列和优先级。
- 预计开始时间。

如果只能找到两组 16 GPU 但网络拓扑不满足 FSDP 目标，调度器不能只因为总数够就启动；它可以等待、选择另一策略或提示用户调整资源约束。

### 3.16.4 Smoke test

launcher 先用 2 个节点、少量 step 启动 smoke test：

- 读取少量数据。
- 初始化进程组。
- 跑 forward/backward。
- 写一个临时 checkpoint。
- 启动一次小评估。
- 验证监控和日志。

smoke test 成功后，平台才允许 full run。失败时保留 stdout、rank 错误、manifest 和临时 artifact，任务标记为 validation_failed，而不是无限重试。

### 3.16.5 训练阶段

full run 开始后：

- 每 step 上报 loss、学习率、梯度范数和 token 数。
- 每隔一段时间上报 throughput、MFU、GPU、显存和通信时间。
- 每 500 steps 写 sharded checkpoint。
- 每 2,000 steps 触发评估任务。
- 评估结果回写到 run metadata。
- scheduler 观察资源和抢占事件。

如果 loss 出现 NaN，监控发出高优先级告警，训练器保存诊断状态并停止；它不会继续跑到 20,000 steps 再报告失败。

### 3.16.6 节点故障

第 8,300 step 时一个节点重启。协调器发现 worker 数不完整，停止其他 rank，任务进入 recovery。它找到最近已经 COMMITTED 的 8,000 step checkpoint，检查所有 shard 和 checksum，重新调度 32 张 GPU，重新生成 rank 映射并启动恢复。

恢复报告记录：

- 故障节点。
- 丢失的 300 steps。
- 恢复 checkpoint。
- 新的 world size 和 topology。
- 是否恢复 random state。
- 是否重复或跳过数据。
- 恢复后的 loss 和学习率曲线。

这比一句“任务自动重试成功”更有价值，因为它告诉用户恢复是否严格以及成本是多少。

### 3.16.7 注册阶段

训练完成后，平台生成 candidate artifact：

- 去掉 optimizer state 的推理权重。
- 保留训练 checkpoint。
- 绑定 tokenizer 和 chat template。
- 绑定数据、代码、镜像和配置版本。
- 生成 instruction、safety 和 domain 评估报告。
- 记录资源成本和恢复事件。

如果安全评估未通过，模型进入 blocked，不进入线上推理。即使 loss 很好，也不能绕过这个状态。

## 3.17 训练平台的关键取舍

### 3.17.1 固定资源还是弹性资源

固定 world size 更容易复现，弹性资源可以提高利用率和故障恢复能力。弹性会改变数据并行、batch 和优化轨迹，需要在实验报告中标记 membership change。

### 3.17.2 全量 checkpoint 还是轻量 checkpoint

全量 checkpoint 恢复能力强，但写入慢、存储大；只保存权重便宜，但不能严格续训。可以按恢复点、评估点和发布点采用不同级别，但要让用户知道每种 artifact 能做什么。

### 3.17.3 中央数据预处理还是任务内处理

中央预处理便于复用和审计，任务内处理更灵活。对于大规模共享数据，建议把昂贵且稳定的处理做成版本化 artifact；研究试验可允许任务内变换，但把代码和输出纳入 manifest。

### 3.17.4 抢占还是专用集群

抢占提高资源利用率，专用资源减少等待和恢复复杂度。训练平台可以把实验任务放在可抢占池，把长时间大训练放在预留池，再用配额控制成本。

### 3.17.5 自动评估还是人工评估

自动评估速度快、可重复；人工能发现开放式质量和安全边界。发布模型通常需要两者，且人工样本要有来源和标注协议。

## 3.18 把训练系统讲成因果链

一个好设计能够说明每个组件为什么存在：

> 因为模型效果依赖具体数据和 tokenizer，所以任务引用不可变 dataset manifest；因为训练时间长且 GPU 昂贵，所以 scheduler 需要队列、拓扑、配额和抢占规则；因为故障会发生，所以 checkpoint 不只是权重，还要包含 optimizer、随机状态、数据位置和分片布局，并以原子提交发布；因为多个任务共享集群，所以容器、数据、secret、日志和模型权重必须隔离；因为训练完成不等于可上线，所以独立评估和 Model Registry 负责把 candidate 与 published 分开；因为结果必须可解释，所以代码、镜像、配置、数据、硬件、事件和成本要通过 manifest 与 metadata 连接起来。
这条因果链比“我们使用 Kubernetes、FSDP 和 MLflow”更接近系统设计。工具只是实现选择，契约和失败边界才是平台的骨架。

### 初学者的阅读顺序

先问五个问题：

1. 训练任务拿什么数据。
2. 任务拿多少机器以及为什么。
3. 训练中断后从哪里恢复。
4. 如何知道这次训练真的完成且没有异常。
5. 产出的模型如何被评估、注册和使用。

### 专家的阅读顺序

再追问：

- manifest 是否真正不可变，还是只保存了一个会移动的标签？
- 数据 cursor 和随机状态是否被 checkpoint 覆盖？
- world size 改变后，optimizer 和 shard 是否还能正确恢复？
- checkpoint 的 COMMITTED 语义能否跨对象存储一致读取？
- all-reduce、数据加载、checkpoint 和日志是否在关键路径上互相阻塞？
- 资源配额和抢占会不会造成系统性不公平？
- 训练数据删除如何追踪到 tokenized artifact 和模型？
- 评估和注册是否独立于训练作业自报的指标？

## 3.19 复盘练习

### 练习一：数据版本漂移

一个训练任务引用了 dataset-latest，任务运行两天后数据目录新增了文件。设计如何保证这次训练仍然可复现，并说明已经运行的任务是否应该看到新文件。

### 练习二：OOM 与恢复

一个 70B SFT 任务在第 200 step OOM。请区分确定性 OOM、临时碎片和 batch 波动三种情况，设计诊断信息、自动建议和是否允许重试。

### 练习三：Checkpoint 一致性

32 个 rank 中有 31 个 shard 写成功，最后一个 rank 进程崩溃。设计 checkpoint 状态、清理和恢复逻辑，说明为什么不能直接把目录标为 latest。

### 练习四：拓扑约束

任务需要 16 张 GPU 的高速互联，但集群只有两组各 8 张空闲 GPU。比较等待、改变并行策略、抢占低优先级任务三种方案，并说明成本和复现影响。

### 练习五：弹性恢复

任务从 64 GPU 运行到 20,000 step 后，故障恢复时只能获得 48 GPU。设计重新分片、global batch、学习率、数据 cursor 和实验记录，说明哪些指标不能和固定 64 GPU 运行直接比较。

### 练习六：模型注册

一个模型 validation loss 很好，但安全评估失败，且训练数据中发现后来撤回的隐私样本。设计 Model Registry 状态、阻断发布、数据血缘查询和后续处理，不要把模型权重直接覆盖掉。

## 3.21 本章小结

训练平台的对象不是一条训练命令，而是一条从数据版本、代码和环境，到资源分配、分布式启动、训练状态、checkpoint、评估和模型注册的可追溯链路。

数据必须有不可变版本、tokenizer 绑定、处理血缘和权限；任务必须有可重放 manifest；调度器必须同时理解 GPU 数量、显存、网络拓扑、队列、公平性和抢占；分布式训练要区分数据、状态、张量和流水线并行，并用真实基准解释通信开销；checkpoint 要保存足够的优化器、随机、数据和分片状态，并通过原子提交保证一致性；恢复必须区分基础设施故障、代码错误、数据错误和训练不稳定；实验系统要把指标连接回代码、数据、模型和环境；评估通过后，模型才进入 Registry，再由推理平台发布。

一个成熟平台的价值，不是让每个任务都永远成功，而是让失败有分类、恢复有证据、资源有账本、数据可追溯、模型可审计。后续章节会把推理平台的在线资源问题单独展开。
