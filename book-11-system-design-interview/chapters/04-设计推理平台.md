# 第四章：设计推理平台：从一次请求到可观测的 token 生产系统

训练平台把数据、代码和 GPU 变成模型；推理平台把模型变成可以被真实用户依赖的服务。两者都运行在 GPU 上，却面对完全不同的约束。训练可以把一个 step 做得很慢，只要总训练时间可接受；在线推理则要在请求到达时立即决定是否接收、排队、合批、迁移或拒绝。训练关注参数是否收敛，推理还要同时关注首 token 延迟、每 token 延迟、流式连接、显存状态、租户隔离、单位成功任务成本和故障恢复。

因此，推理平台不是“加载权重并暴露一个 HTTP 接口”。它是一套把模型版本、请求工作量、GPU 资源、缓存状态和服务承诺连接起来的运行系统。本章沿着“澜沧推理平台”展开。澜沧服务企业聊天、检索增强生成、Agent、embedding 和 reranker，模型来自第 3 章训练平台的 Model Registry。我们先从一个请求到底消耗什么资源讲起，再逐步进入调度、KV Cache、推理引擎、并行、量化、缓存、扩缩容和故障处理。

## 4.0 先建立正确的直觉：平台交付的是服务能力

### 给初学者：模型像发动机，推理平台像交通系统

把模型权重想成发动机，只能说明它具备产生输出的能力。真正的交通系统还要安排车辆从哪里出发、走哪条路、遇到拥堵如何等待、乘客中途取消时如何处理，以及一辆车发生故障后如何把乘客送到目的地。

推理平台中的请求就是乘客，GPU 是道路和车辆，显存是有限的停车空间，KV Cache 是一段行程已经产生但仍要继续使用的路线状态。一个请求的输入越长，启动阶段需要处理的工作越多；输出越长，逐 token 生成阶段占用资源的时间越长。平台如果只按“请求数”排队，就像只按车辆数量判断道路拥堵，却不看每辆车的长度和行驶距离。

### 给专家：拆开五个容易混淆的对象

设计时至少要把以下五件事分开：

1. 模型能力：权重、tokenizer、chat template、上下文上限和安全行为。
2. 计算工作量：输入 token 的 prefill 工作、输出 token 的 decode 工作，以及重试和工具调用放大。
3. 运行状态：请求的 token 位置、KV Cache、采样状态、流式连接和取消状态。
4. 资源容量：GPU 计算、显存、互联带宽、CPU、网络和权重存储。
5. 服务承诺：TTFT、TPOT、P99、成功率、质量、安全和成本。

一个模型卡上的 context length 不是可用容量，一个 GPU 的理论 FLOPS 不是在线吞吐，一个请求完成也不是一次业务任务成功。平台设计的第一步，是让这五种对象在数据模型和指标中分别出现。

### 本章的贯穿问题

澜沧平台收到一个来自 RAG 的请求：输入 12,000 token，预计输出 800 token，租户要求首 token 小于 1.5 秒，流式传输，不能与其他租户共享敏感前缀。平台需要依次回答：

- 这个模型版本和 tokenizer 是否允许该请求？
- 当前实例还有多少可分配的 KV Cache？
- 应该进入短请求队列、长上下文队列，还是异步队列？
- prefill 和 decode 是否与别的请求混合执行？
- 如果客户端断开，已经生成的 token 如何计费，状态如何释放？
- 如果实例 OOM 或模型质量回归，路由如何切回旧版本？
- 这次请求消耗了多少 GPU 时间，又是否完成了上层任务？

这些问题相互影响，不能分别写成几个孤立的 API。

## 4.1 先定义边界和服务契约

### 4.1.1 平台服务什么

澜沧第一版提供四类能力：

| 能力 | 输入 | 输出 | 主要资源特征 |
| --- | --- | --- | --- |
| 文本生成 | token 序列、采样参数、工具协议 | token 流或完整文本 | prefill、decode、KV Cache |
| Embedding | 文本或多模态片段 | 向量 | 计算密集，通常没有长生命周期 KV |
| Reranker | 查询与候选文档 | 相关性分数 | batch 友好，延迟敏感 |
| 多模态生成 | 文本、图像或音频输入 | token、图像或音频 | 编码器、跨模态缓存、显存波动 |

模型注册、权重发布、评估和来源血缘属于平台边界；模型训练算法属于训练平台；会话、权限业务规则、RAG 召回和 Agent 编排属于上层应用。边界不是为了少做工作，而是为了让每个组件对状态负责。推理平台不应擅自解释业务权限，应用也不应直接改写推理引擎的 KV 状态。

### 4.1.2 请求契约要比模型接口稳定

应用调用推理平台时，契约至少要定义：

- model_id 和可选的 model_version。
- messages 或已经分词的输入，但两者不能同时以含糊方式出现。
- max_output_tokens、temperature、top_p、stop 条件和随机种子。
- 是否流式返回。
- 优先级、租户、trace_id 和 idempotency_key。
- 工具 schema、响应格式和安全策略引用。
- 超时、取消和客户端重连语义。

平台返回的元数据也要稳定：

- request_id、model_version、tokenizer_version。
- accepted_at、prefill_started_at、first_token_at、completed_at。
- input_tokens、output_tokens、cached_tokens。
- finish_reason 和错误分类。
- 是否发生降级、重试、量化路由或投机解码。
- 成本估算和质量审计引用。

这样，应用可以围绕服务契约开发，而不必知道底层是 vLLM、TensorRT-LLM、SGLang 还是内部引擎。底层引擎可以替换，语义不能悄悄改变。

### 4.1.3 同步、流式和异步是三种不同产品

短文本分类可以使用同步请求；聊天和代码生成常使用流式请求；长文档总结、批量 embedding 和离线评估可以使用异步任务。三者不只是把 HTTP 响应格式换一下：

- 同步请求需要在一个连接生命周期内完成。
- 流式请求需要处理事件序号、背压、断连、取消和部分输出。
- 异步任务需要持久化状态、轮询或回调、重试和结果保留。

如果把三者都塞进一个“generate”接口，用户会在超时、重连和计费时遇到无法解释的行为。第 2 章已经讨论聊天产品的响应状态，这一章关注平台如何把这些状态落实到 GPU 调度和引擎执行。

## 4.2 非功能目标：延迟、吞吐、质量和成本必须同时记录

### 4.2.1 延迟不是一个数字

一次生成请求至少有以下时间：

~~~math
T_{\mathrm{e2e}}
=
T_{\mathrm{admission}}
+
T_{\mathrm{queue}}
+
T_{\mathrm{prefill}}
+
T_{\mathrm{decode}}
+
T_{\mathrm{network}}
+
T_{\mathrm{postprocess}}
~~~

其中：

- T_admission 是鉴权、限流、参数校验和资源检查。
- T_queue 是在路由器和推理引擎中等待的时间。
- T_prefill 是处理输入并建立初始 KV Cache 的时间。
- T_decode 是生成输出 token 的总时间。
- T_network 是 token 流经过服务端和网络的时间。
- T_postprocess 是结构化解析、审核和落库时间。

用户首先感知的是 TTFT：

~~~math
T_{\mathrm{TTFT}}
=
T_{\mathrm{admission}}
+
T_{\mathrm{queue}}
+
T_{\mathrm{prefill}}
+
T_{\mathrm{first\_flush}}
~~~

对已经开始输出的请求，还要观察 TPOT。若请求至少生成一个输出 token，且输出 token 数是 $N_{\mathrm{out}}>0$：

~~~math
T_{\mathrm{TPOT}}
\approx
\frac{T_{\mathrm{decode}}}{N_{\mathrm{out}}}
~~~

没有生成 token 的请求没有可解释的 TPOT，应单独统计为拒绝、取消、超时或首 token 前失败。平均值只能说明整体趋势。长请求可能把 P50 拉得很好看，却让短请求 P99 失控；所以平台要按请求长度、租户、模型版本和队列分别切片。

### 4.2.2 吞吐也要注明口径

常见的吞吐有三种：

- request throughput：每秒完成多少请求。
- input token throughput：每秒处理多少输入 token。
- output token throughput：每秒生成多少输出 token。

对 decoder-only 模型，输入 token 和输出 token 的计算路径不同。一个系统可能提高 input token throughput，却让输出 token 的 TPOT 变差；也可能提高 output token throughput，却因排队增加而降低用户体验。报告吞吐时必须给出 batch、输入长度、输出长度、并发、精度和引擎版本。

### 4.2.3 质量和成本不能放到系统之外

推理平台不负责定义所有业务质量，但要把模型版本和线上反馈关联起来。至少记录：

- 任务成功率，而不仅是 HTTP 200。
- 引用支持率、结构化输出合法率或工具调用完成率。
- 安全策略触发率和误拒率。
- 单位成功任务成本，而不仅是单位 token 价格。
- 降级、重试、缓存命中对上述指标的影响。

如果量化模型使 token 成本下降 40%，却让代码修复成功率下降 15%，单看 GPU 账单会得到错误结论。

## 4.3 工作量模型：从 QPS 走到 token 和阶段

### 4.3.1 外部请求不等于内部调用

设第 i 类业务的外部请求速率为 lambda_req,i，每个外部请求平均触发 a_i 次模型调用，每次调用平均输入 L_in,i、输出 L_out,i 个 token，则输入和输出工作量分别为：

~~~math
\Lambda_{\mathrm{in}}
=
\sum_i
\lambda_{\mathrm{req},i}
a_i
L_{\mathrm{in},i}
~~~

~~~math
\Lambda_{\mathrm{out}}
=
\sum_i
\lambda_{\mathrm{req},i}
a_i
L_{\mathrm{out},i}
~~~

如果只把 QPS 相加，就会漏掉 Agent 的多步调用和 RAG 的上下文扩展。总 token 数可以粗略写成：

~~~math
\Lambda_{\mathrm{all}}
=
\Lambda_{\mathrm{in}}
+
\Lambda_{\mathrm{out}}
~~~

但这不是一个足以直接换算 GPU 数的数字，因为输入主要进入 prefill，输出主要进入 decode，二者的计算强度和显存占用不同。

### 4.3.2 澜沧的容量例子

假设峰值业务如下：

| 业务 | 外部 QPS | 调用放大 a | 平均输入 | 平均输出 |
| --- | ---: | ---: | ---: | ---: |
| Chat | 1000 | 1 | 1000 | 500 |
| RAG | 300 | 1 | 4000 | 800 |
| Agent | 100 | 5 | 2000 | 300 |

三类业务的 token 速率为：

~~~math
\Lambda_{\mathrm{Chat}}
=
1000
\times
1
\times
(1000+500)
=
1{,}500{,}000
~~~

~~~math
\Lambda_{\mathrm{RAG}}
=
300
\times
1
\times
(4000+800)
=
1{,}440{,}000
~~~

~~~math
\Lambda_{\mathrm{Agent}}
=
100
\times
5
\times
(2000+300)
=
1{,}150{,}000
~~~

所以总量约为 4.09M token/s。这里的 4.09M 是工作量账本，不是容量承诺。RAG 贡献了 1.2M input token/s 和 0.24M output token/s，Chat 贡献了 1.0M input token/s 和 0.5M output token/s，Agent 贡献了 1.0M input token/s 和 0.15M output token/s。平台需要用代表性长度和并发基准测出每种 GPU 在这三种负载下的有效容量，再决定实例数。

### 4.3.3 峰值、平均值和突发要分开

如果平均 QPS 是 400，五分钟峰值是 1000，按平均值部署会在峰值到来时让队列快速积压。可用容量应包含安全余量：

~~~math
C_{\mathrm{usable}}
=
C_{\mathrm{benchmark}}
\times
(1-r_{\mathrm{headroom}})
\times
(1-r_{\mathrm{failure}})
~~~

其中 C_benchmark 是固定模型、精度、输入输出长度和并发下的实测容量；r_headroom 是留给突发、批处理波动和系统开销的余量；r_failure 是考虑节点故障或维护后的可用性折减。它们不是理论常数，应从历史流量和故障演练中估计。

### 4.3.4 Little 定律解释为什么队列会突然变长

对稳定系统，Little 定律给出：

~~~math
N_{\mathrm{inflight}}
=
\lambda_{\mathrm{req}}
\times
W_{\mathrm{e2e}}
~~~

当到达速率接近系统服务能力时，W_e2e 会受到排队影响而快速增长，inflight 数量和 KV Cache 占用也随之增长，最终形成“队列增加 -> KV 紧张 -> batch 变小 -> 处理更慢 -> 队列继续增加”的反馈。推理平台的过载保护必须在显存耗尽之前发生，不能等 GPU OOM 后再处理。

## 4.4 资源账本：权重、KV、激活和运行时状态

### 4.4.1 GPU 显存不是只放权重

一张 GPU 的显存可以近似拆成：

~~~math
M_{\mathrm{GPU}}
=
M_{\mathrm{weights}}
+
M_{\mathrm{KV}}
+
M_{\mathrm{activations}}
+
M_{\mathrm{workspace}}
+
M_{\mathrm{runtime}}
+
M_{\mathrm{reserve}}
~~~

推理时没有训练 optimizer state，但仍然需要：

- 模型权重和量化元数据。
- 当前 prefill 的激活和中间 buffer。
- 所有活跃序列的 KV Cache。
- attention、通信和矩阵乘法 kernel 的 workspace。
- CUDA graph、allocator 和引擎运行时的额外空间。
- 留给波动、碎片和异常路径的 reserve。

把剩余显存全部分配给 KV Cache 会让短时峰值直接触发 OOM。平台应把 reserve 作为显式配置，并在启动时用真实引擎测量，而不是只用权重文件大小估算。

### 4.4.2 权重估算只能提供下界

若模型有 P 个参数，每个参数平均占 b_weight 字节，则：

~~~math
M_{\mathrm{weights}}
\approx
P
\times
b_{\mathrm{weight}}
+
M_{\mathrm{scales}}
+
M_{\mathrm{metadata}}
~~~

例如 BF16 的权重通常约为每参数 2 字节，INT4 的权重约为每参数 0.5 字节，但实际还要加 scale、zero point、分组元数据和 kernel 对齐开销。INT4 不能简单地把 BF16 权重显存除以 4 后当作整个实例的显存需求。

### 4.4.3 给初学者：为什么输入不生成也会占显存

模型读完一个 prompt 后，会把每层 attention 所需的 key 和 value 保存下来。后续生成下一个 token 时，可以直接复用它们，不必重新计算整个 prompt。这些保存下来的中间状态就是 KV Cache。

所以“输入只有 10,000 token，输出还没开始”也可能消耗大量显存。对一个拥有很多层和 KV head 的模型，单个 token 要在每层保存 K 和 V；并发请求的所有 token 叠加起来，才是 KV Cache 的总量。

## 4.5 推理平台架构：控制平面和数据平面各自负责什么

### 4.5.1 控制平面

控制平面处理变化慢、需要持久化和审计的对象：

- Model Registry 和版本元数据。
- Deployment、实例规格、区域和副本数。
- canary、灰度比例和回滚记录。
- GPU 资源声明、节点标签和拓扑信息。
- 租户配额、模型权限和成本规则。
- 评估报告、质量回归和发布条件。
- 引擎配置、量化产物和校验哈希。

控制平面故障时，已有数据平面实例不一定要立刻停止服务。实例可以使用最近一次有效配置继续运行一小段时间，再进入保护状态；这比把配置中心短暂不可用扩大成全平台不可用更稳妥。

### 4.5.2 数据平面

数据平面处理每个请求的快路径：

~~~text
client
  -> API gateway
  -> authentication and quota
  -> model router
  -> admission controller
  -> request queue
  -> scheduler
  -> prefill and decode engine
  -> stream or final response
  -> usage and quality events
~~~

数据平面需要低延迟，但不应把所有元数据都同步写入数据库。请求的关键事件可以先写入本地或消息队列，再异步汇总；不过计费、取消和最终状态要有明确的可靠性边界，不能以“异步”掩盖丢失。

### 4.5.3 组件之间的契约

| 组件 | 输入 | 输出 | 不能替它承担的责任 |
| --- | --- | --- | --- |
| Gateway | 请求、凭证、协议 | 已鉴权请求 | 不决定模型质量 |
| Router | 模型要求、租户、负载 | 部署和实例选择 | 不分配 GPU 内存 |
| Admission | token 估算、KV 预算、队列 | 接受、延后或拒绝 | 不执行模型 |
| Scheduler | 可运行请求和资源 | 本轮 batch | 不修改模型版本 |
| Engine | batch、KV block、采样参数 | token 和状态事件 | 不解释业务权限 |
| Usage recorder | 事件和 token 计数 | 用量、成本、审计 | 不决定是否继续生成 |

这种拆分使故障定位具有方向：如果 Router 选择了不存在的版本，属于控制或路由问题；如果 Engine 返回错误 token，属于执行问题；如果 token 数正确但账单丢失，属于用量记录问题。

## 4.6 模型注册、格式转换和发布条件

### 4.6.1 Registry 记录的是可运行模型，而非一个权重文件

一个可部署版本至少要绑定：

- model_id、model_version 和内容 digest。
- 架构、参数规模、层数、hidden size、attention head 和 KV head。
- tokenizer 文件、special token 和 chat template。
- 权重分片、精度、量化方法和校准数据摘要。
- 最大上下文、最大输出和支持的采样能力。
- 推理引擎版本、CUDA/driver 兼容范围和推荐 GPU。
- LoRA 或 adapter 的基座版本。
- 离线质量、安全、结构化输出和压力测试报告。
- 训练任务、数据版本和许可证血缘。
- 发布者、审核记录、回滚版本和变更说明。

同一个权重配上不同 chat template，可能把 system、user、assistant 的边界改变；同一个模型配上不同 tokenizer，也会改变 token 数、上下文预算和成本。它们必须成为同一个可审计版本的组成部分。

### 4.6.2 训练 checkpoint 和推理 artifact 不能混淆

训练 checkpoint 可能包含 optimizer state、随机状态、数据 cursor 和分布式分片；在线推理 artifact 需要面向执行优化。转换过程通常包括：

1. 读取并校验训练 checkpoint。
2. 合并或重新分片参数。
3. 删除推理不需要的训练状态。
4. 转换 dtype 或量化格式。
5. 编译或选择 attention、GEMM 和通信 kernel。
6. 生成 tokenizer、template 和引擎配置。
7. 用 hash 绑定全部文件。
8. 用代表性输入做数值和行为校验。

如果只校验权重文件可读取，无法发现 tokenizer 不匹配、量化 scale 丢失或 chat template 改变。

### 4.6.3 发布过程要能解释每一次变化

澜沧把发布过程建模为：

~~~text
registered
  -> converted
  -> offline-evaluated
  -> canary-deployed
  -> traffic-expanded
  -> serving
  -> retired
~~~

其中任意阶段都要保存原因、操作者、配置 digest 和指标快照。canary 不仅观察 HTTP 错误率，还要观察 TTFT、TPOT、结构化输出合法率、安全触发率、任务成功率、成本和显存水位。

自动回滚的触发条件应区分硬故障和质量回归：

- 硬故障：启动失败、持续 OOM、错误率异常、流式协议损坏。
- 性能回归：P99 TTFT、TPOT 或队列等待超过目标。
- 质量回归：特定任务集、工具调用或安全集显著变差。
- 成本回归：单位成功任务成本超过预算。
- 数据与权限问题：版本血缘、租户边界或日志策略不完整。

模型回滚不只是把权重换回去，还要同时恢复 tokenizer、template、引擎参数、量化版本和路由规则。

## 4.7 请求生命周期：从 admission 到释放状态

### 4.7.1 请求状态

一个生成请求可以有以下状态：

~~~text
received
  -> validated
  -> admitted
  -> queued
  -> prefill
  -> decoding
  -> streaming
  -> completed

任何运行状态都可能进入:
  canceled
  timed_out
  rejected
  failed
  preempted
~~~

状态转换应记录时间和原因。例如，queued 到 prefill 表示调度器已经为请求分配了本轮 token 预算；decoding 到 canceled 表示收到取消并释放了剩余 KV block；prefill 到 rejected 表示资源检查在真正执行前发现预算不足。

### 4.7.2 Admission 要做三件事

第一，估算工作量。输入 token 可以由 tokenizer 精确计算，输出 token 只能用 max_output_tokens、历史分布或租户配额估算。第二，检查资源。请求不能只看当前空闲 GPU，还要估计它将占用的 KV block 和最长可能生命周期。第三，选择保护动作：

- 立即执行。
- 进入合适的队列。
- 降低最大输出或切换模型。
- 转为异步。
- 在明确的错误码下拒绝。

“接收请求”不等于“保证一定能生成完整输出”。契约要告诉调用方哪些是硬约束，哪些是预算不足时可能变化的软约束。

### 4.7.3 取消、重试和幂等

客户端断开时，平台要区分：

- 网络连接断开但服务仍继续生成。
- 用户明确取消，服务应停止生成。
- 上层任务重试，同一 request_id 是否复用原结果。
- 引擎已经生成一部分 token，计费和结果如何处理。

推理执行通常难以提供跨引擎的 exactly-once 语义。更现实的做法是给请求分配 idempotency_key，持久化最终结果和用量事件，并约定重试可能复用已完成结果；流式中断后是否能从序号继续，要由协议和引擎共同支持，不能把一次新的生成冒充为原流的无缝续接。

## 4.8 Prefill 和 decode：两个阶段、两种瓶颈

### 4.8.1 Prefill 处理输入

Prefill 一次处理整个 prompt，建立初始 KV Cache。它通常有更大的矩阵乘法和 attention 工作量，适合较大的 batch，但长 prompt 会占用大量计算和显存带宽。

对长度 n 的序列，标准 self-attention 的全量计算在理论上具有与 n 的平方相关的项：

~~~math
\mathrm{Cost}_{\mathrm{prefill}}
\sim
O(n^2 d)
~~~

其中 d 是 head 或 hidden 维度的相关量级。FlashAttention 通过 tile、片上内存和 IO-aware 计算减少中间矩阵读写，它保持 attention 结果精确，并不等于把所有长上下文计算变成线性复杂度。具体收益仍取决于 GPU、kernel、batch 和序列长度。

### 4.8.2 Decode 逐 token 读取历史状态

Decode 每轮通常为每个活跃序列生成一个或少量 token，并读取历史 KV Cache。单个序列的输出是自回归的，不能把任意未来 token 直接并行生成。因此 decode 经常受到显存带宽、KV 读取、batch 形状和同步开销影响。

一个简化的输出时间模型是：

~~~math
T_{\mathrm{decode}}
\approx
N_{\mathrm{out}}
\times
\left(
T_{\mathrm{kernel}}
+
T_{\mathrm{KV\_read}}
+
T_{\mathrm{sync}}
\right)
~~~

这解释了为什么“输入变短”不一定改善长回答的 TPOT，也解释了为什么增加并发有时提高总吞吐，却让单请求 TPOT 变慢。

### 4.8.3 共享 GPU 时的干扰

如果 prefill 长请求和 decode 短请求在同一轮中争夺 GPU，长 prefill 可能占住计算资源，使正在输出的请求出现 token 间隔抖动；如果优先保证 decode，又可能使长上下文请求的 TTFT 变差。平台应分别记录：

- prefill queue time 和 prefill service time。
- decode queue time 和每轮 decode time。
- prefill tokens/s 和 output tokens/s。
- prefill 对 decode 的干扰。
- 不同长度分桶的 P50/P95/P99。

这是调度问题，不是单纯更换 GPU 型号就能解决的问题。

## 4.9 Batching 和调度：从整批等待到迭代级调度

### 4.9.1 静态 batching 的问题

传统静态 batching 等一批请求到齐后一起开始，一批中最长的请求决定结束时间。若四个请求输出长度分别是 20、40、200、800，短请求完成后仍可能保留填充位置，GPU 利用率和响应时间都会受影响。

大模型生成每一轮都产生新 token，因此更适合在迭代边界重新决定 batch。Orca 论文把这种迭代级调度与选择性 batching 作为生成模型服务的重要设计，论文中的结果属于其模型、硬件和实现条件，不能直接当作所有引擎的吞吐承诺。

### 4.9.2 Continuous batching 的真实含义

Continuous batching 不是“把所有请求混在一起”。它意味着：

1. 每个 decode iteration 都可以加入已经完成 prefill 的新请求。
2. 完成、取消或达到 stop 条件的请求可以退出。
3. 调度器根据 token 预算、KV 预算和优先级选择本轮工作。
4. prefill 可以与 decode 混合，也可以分离或分阶段执行。

一个概念化调度循环如下：

~~~python
while service_is_running:
    finished = engine.collect_finished()
    release_kv_blocks(finished)

    candidates = admission_queue.ready_requests()
    running = engine.running_sequences()

    batch = scheduler.select(
        running=running,
        candidates=candidates,
        max_num_seqs=limits.max_num_seqs,
        max_prefill_tokens=limits.max_prefill_tokens,
        max_decode_tokens=limits.max_decode_tokens,
        kv_budget=kv_allocator.available_tokens(),
    )

    engine.step(batch)
    emit_stream_events(batch)
~~~

这段代码没有规定具体引擎 API，它要表达的是一个不变量：调度器每轮都必须让“可运行请求、token 预算、KV 预算和取消状态”保持一致。若只更新 batch 而忘记释放已经完成的 KV block，最终仍会表现为显存泄漏。

### 4.9.3 Chunked prefill

长 prompt 可以被拆成多个 chunk，在多个 iteration 中逐步处理。这样能避免一次长 prefill 把 decode 请求长时间阻塞，但会增加调度状态和中间同步。chunk size 太大，短请求仍被拖慢；太小，kernel 效率和调度开销下降。

chunked prefill 适合在以下条件下启用：

- 长短请求混合明显。
- TTFT 和 TPOT 都有严格要求。
- 引擎能够安全保存 prefill 中间状态。
- 调度器能对每个 chunk 计算 KV 和计算预算。

它不是对所有负载都更快。离线批处理通常更喜欢大 chunk，交互式服务通常更看重尾延迟。

### 4.9.4 Token-based batching

请求数不是公平的容量单位。调度器应同时约束：

~~~math
\sum_{r \in B}
L_{\mathrm{prefill},r}
\leq
K_{\mathrm{prefill}}
~~~

~~~math
\sum_{r \in B}
L_{\mathrm{decode},r}
\leq
K_{\mathrm{decode}}
~~~

~~~math
\sum_{r \in B}
B_{\mathrm{KV},r}
\leq
B_{\mathrm{KV,max}}
~~~

B 是本轮 batch，K_prefill、K_decode 和 B_KV,max 是根据引擎实测得到的预算。max_num_seqs 仍然有用，因为 kernel 和调度器需要限制序列数量，但它不能替代 token 和 KV 约束。

### 4.9.5 公平性和优先级

如果系统只追求吞吐，大请求可能占满每轮预算，交互式短请求一直排队；如果系统只追求低延迟，batch 过小，GPU 成本会迅速上升。澜沧使用分层策略：

- 高优先级交互请求限制最大等待时间。
- 长上下文请求进入独立预算池。
- 离线任务使用可抢占资源。
- 同一租户受并发和 token 配额约束。
- 优先级提升有额度上限和审计记录。
- 超过预测可接受等待时间的请求转异步或返回明确错误。

调度规则要能从 trace 解释“为什么这个请求在这里等待”，否则用户会把容量问题误认为随机故障。

## 4.10 KV Cache：推理平台的状态资源

### 4.10.1 KV Cache 的基本估算

设模型有 L 层、n_kv 个 key/value head、每个 head 维度为 d_head，每个元素占 s bytes，活跃序列总缓存 token 数为 B_tokens。忽略对齐和量化细节时：

~~~math
M_{\mathrm{KV}}
\approx
2
\times
L
\times
n_{\mathrm{kv}}
\times
d_{\mathrm{head}}
\times
s
\times
B_{\mathrm{tokens}}
~~~

前面的 2 表示 K 和 V。MHA 为每个 query head 保留对应的 K/V；GQA 让一组 query head 共享 K/V；MQA 则让更多 query head 共享一组 K/V。于是 MHA 中 n_kv 等于 query head 数，GQA 中 n_kv 小于 query head 数，MQA 中 n_kv 可以接近 1。因此，同样的模型层数和上下文长度下，GQA/MQA 会显著改变 KV Cache 容量，但不会自动消除所有 decode 计算。

单请求的缓存 token 数近似是：

~~~math
B_{\mathrm{tokens,request}}
=
L_{\mathrm{input}}
+
L_{\mathrm{generated}}
+
L_{\mathrm{reserved}}
~~~

L_reserved 代表引擎为了 block 对齐、候选 token 或特殊执行路径预留的空间。用输入长度代替总长度会低估长回答的显存。

### 4.10.2 可用 token 容量

把模型权重和运行时空间扣除后，可用于 KV 的显存为：

~~~math
M_{\mathrm{KV,budget}}
=
M_{\mathrm{GPU}}
-
M_{\mathrm{weights}}
-
M_{\mathrm{workspace}}
-
M_{\mathrm{runtime}}
-
M_{\mathrm{reserve}}
~~~

于是理想 token 容量为：

~~~math
B_{\mathrm{tokens,max}}
\approx
\left\lfloor
\frac{M_{\mathrm{KV,budget}}}
{2 L n_{\mathrm{kv}} d_{\mathrm{head}} s}
\right\rfloor
~~~

实际系统还要扣除 block 对齐、跨卡通信、CUDA graph、adapter 和多模态编码器的开销。这个公式的价值是帮助我们发现容量瓶颈，不是替代启动时的真实 profile。

### 4.10.3 PagedAttention 解决什么

传统实现可能为每个序列预留较大的连续 KV 区域，而生成长度、完成时间和 batch 组成都是动态的，容易出现内部碎片和预留浪费。PagedAttention 借鉴虚拟内存的分页思想，把逻辑连续的序列映射到若干物理 KV block。vLLM 论文报告，这种管理能减少 KV 浪费并支持更灵活的共享；论文中的吞吐对比受其测试环境约束。

理解 PagedAttention 时要区分三层：

- 算法层：attention 读取逻辑序列对应的 block。
- 内存层：block allocator 管理物理显存。
- 调度层：scheduler 根据可用 block 决定接收多少序列。

只有第一层存在，不代表后两层自动正确。block 泄漏、跨租户共享和回收竞态仍然是平台问题。

### 4.10.4 Prefix Cache 的收益和边界

若多个请求具有完全相同的前缀，可以复用前缀对应的 KV，减少重复 prefill。输入 token 节省量可以估算为：

~~~math
L_{\mathrm{saved}}
=
\sum_{r}
L_{\mathrm{prefix\_hit},r}
~~~

但前缀缓存的 key 必须绑定：

- 模型权重 digest。
- tokenizer 和 chat template 版本。
- 前缀 token 序列或其可信 hash。
- adapter、量化和相关引擎配置。
- 租户、数据域和权限边界。
- 影响 hidden state 的运行参数。

temperature 通常不改变已经计算好的前缀 hidden state，但会影响后续采样；工程上仍应把“可以安全复用的计算前缀”和“请求完整参数”分成两个层次记录，避免把可复用状态误认为可复用结果。

跨租户共享敏感前缀是严重的数据泄漏风险。即使 token 序列相同，也不代表两个租户有权观察缓存命中、缓存大小或响应时间差异。

### 4.10.5 KV Cache 的驱逐与迁移

当显存紧张时，平台可以：

- 驱逐已完成请求的 block。
- 释放长时间空闲会话的状态。
- 将部分 prefix cache 下沉到 CPU 或 SSD。
- 取消低优先级、尚未开始执行的请求。
- 把新请求路由到有容量的实例。
- 在支持的引擎中迁移或重建状态。

KV 迁移不是免费操作。网络传输、序列化、重建和版本兼容都可能比重新 prefill 更慢。是否迁移应比较：

~~~math
T_{\mathrm{migrate}}
+
T_{\mathrm{restore}}
<
T_{\mathrm{recompute}}
~~~

只有左侧确实更小，且中间状态可以在目标实例安全恢复，迁移才有价值。

## 4.11 推理并行和拓扑：GPU 数量不是唯一变量

### 4.11.1 Tensor parallel

Tensor parallel 把一个层的矩阵或 attention 计算切到多张 GPU，需要在层间或层内进行 collective communication。它可以让单卡放不下的模型运行，但每个 token 都可能触发跨 GPU 通信，因此对 NVLink、PCIe、跨节点网络和 batch 形状很敏感。

推理部署时要记录：

- tensor parallel size。
- 每个 rank 的权重分片。
- collective 类型和通信量。
- GPU 到 GPU 的拓扑。
- 单节点内和跨节点的延迟。
- 发生 rank 故障时能否整体重启。

把模型从 4 卡扩到 8 卡不一定让单请求延迟减半；通信比例可能上升，反而让 TPOT 变差。

### 4.11.2 Pipeline parallel

Pipeline parallel 把不同层放在不同 GPU。它可以降低单卡权重和中间状态压力，但推理时会产生 pipeline bubble。对低并发交互请求，流水线填充和排空成本尤其明显；对足够大的批量，bubble 可以被更多 micro-batch 摊薄。

Pipeline parallel 更适合明确的高吞吐负载，不应因为“显存不够”就直接启用而忽略首 token 延迟。

### 4.11.3 Expert parallel

MoE 模型的总参数量可能很大，但每个 token 只激活部分 expert。expert parallel 将不同 expert 放在不同 GPU 或节点，router 需要把 token 分发到对应设备，再把结果聚合。负载不均和跨节点通信会让“active parameters 较少”不等于“推理一定便宜”。

调度器要观察每个 expert 的 token 数、容量上限、丢弃或重路由情况，以及通信占比。只看平均 GPU 利用率会掩盖某个 expert 已经成为热点。

### 4.11.4 副本和并行的组合

副本扩展增加独立服务实例，主要缓解请求并发；tensor 或 pipeline parallel 增大单个实例的模型容量。一个简单的放置模型是：

~~~math
G_{\mathrm{total}}
=
R_{\mathrm{replica}}
\times
G_{\mathrm{parallel\_group}}
~~~

增加副本可能增加权重显存，但降低请求互相干扰；增大 parallel group 可能减少副本数量，却提高通信和故障域。部署选择要以目标负载的 profile 为依据，而不是追求某个固定并行策略。

### 4.11.5 Prefill/decode 解耦

DistServe 研究指出，prefill 和 decode 的资源目标不同：前者影响 TTFT，后者影响 TPOT；把两者放在同一批处理路径中会产生干扰。将两个阶段放到不同 GPU 池，可以分别配置并行度和容量。

Mooncake 进一步以 KV Cache 为中心讨论解耦架构，把 GPU、CPU、DRAM 和 SSD 的缓存资源纳入调度，并讨论在过载下基于预测的早期拒绝。两篇论文都提供了有价值的系统设计方向，但其收益取决于网络、缓存传输、工作负载和实现。生产系统引入解耦前要先测量 KV 传输成本和故障恢复，而不能只复制论文架构图。

## 4.12 量化：减少显存不是免费午餐

### 4.12.1 权重量化和运行时量化

量化把高精度数值映射到较低比特表示。常见选择包括 FP16、BF16、FP8、INT8 和 INT4。要区分：

- weight-only quantization：主要压缩权重，激活仍使用较高精度。
- weight-activation quantization：同时压缩权重和激活，需要更严格的校准。
- runtime quantization：执行时动态处理部分张量。
- pre-quantized artifact：发布前已经生成量化权重和元数据。

量化格式、分组大小、scale 的粒度以及 GPU kernel 是否支持，会共同决定真实性能。一个文件名里写着 INT4，不足以说明运行时真的以四位完成全部矩阵乘法。

### 4.12.2 质量评估要按任务切片

量化回归经常不是均匀发生的。至少分别评估：

- 普通对话和长文本。
- 数学、代码和结构化输出。
- 多语言和罕见 token。
- 工具调用和函数参数。
- 安全拒答、越权尝试和敏感内容。
- 长上下文的中间位置检索。

同一个平均分可能掩盖一个高价值任务集显著下降。质量差异可以用配对请求比较：

~~~math
\Delta_j
=
q_{\mathrm{quantized},j}
-
q_{\mathrm{baseline},j}
~~~

对同一组输入使用相同的采样和评估规则，观察 Delta 的分布，而不是只比较两个独立平均数。

### 4.12.3 量化发布的边界

量化适合低风险、成本敏感或吞吐优先的请求；高价值代码、复杂工具调用和安全关键场景可能仍使用高精度版本。路由依据应该写入请求 trace，用户和运维人员需要知道一次响应使用了哪种精度。

vLLM 官方文档维护多种量化后端和支持矩阵，但文档中的支持不等于某个模型在你的 GPU、序列长度和质量目标下已经达到可用状态。NVIDIA TensorRT-LLM 的官方文档也展示了针对 NVIDIA 平台的优化组件；同样要以本地 profile 和回归集决定最终配置。

## 4.13 投机解码与多 token 预测：减少大模型串行步数

### 4.13.1 投机解码的直觉

标准自回归生成每次由大模型生成一个 token。投机解码让一个更小、更快的 draft model 先提出多个候选，再由 target model 批量验证。接受的 token 可以一次提交多个，从而减少大模型逐步运行的次数。

论文方法的核心要求是验证和采样规则能够保持目标模型的分布，早期论文报告在其 T5 实验中获得加速且输出分布保持一致。工程实现还要考虑 draft model 质量、候选长度、验证 kernel、KV 状态和采样参数。

### 4.13.2 Acceptance length 决定收益

设每轮 draft 提出 k 个 token，平均接受长度为 a，target 验证一次的成本为 C_target，draft 和额外管理成本为 C_draft，则一个粗略的每 token 成本模型是：

~~~math
C_{\mathrm{token}}
\approx
\frac{C_{\mathrm{target}}+C_{\mathrm{draft}}+C_{\mathrm{verify}}}
{\max(1,a)}
~~~

a 越大，潜在收益越高；但 draft model 越弱，a 可能接近 1，额外工作反而让系统变慢。不同任务的 acceptance length 不同，代码、中文、工具 JSON 和随机采样不能共用一个固定结论。

### 4.13.3 投机解码的失败边界

以下条件会减少或消除收益：

- draft 和 target 的 tokenizer 或词表不兼容。
- target 频繁拒绝候选。
- 输出很短，启动成本占主导。
- batch 很大，target 已经接近饱和。
- 需要严格的结构化输出，而 draft 经常破坏前缀。
- 目标 GPU 缺少高效的验证 kernel。
- draft model 的额外显存挤压了 KV Cache。

因此平台要记录 draft model、候选长度、acceptance length、target calls、output tokens 和最终 TPOT。不能只记录“启用了 speculative decoding”。

### 4.13.4 多 token 预测和引擎能力

某些模型训练了额外预测头，或使用树状候选验证来一次处理多个未来 token。这类方法与传统 draft model 不是同一实现。平台 Registry 要记录模型是否支持、训练目标、推理引擎版本、候选树配置和回退路径；当 acceptance 下降时，可以自动回到普通 decode。

## 4.14 路由：模型、版本、实例和负载要一起选择

### 4.14.1 路由键

Router 至少综合：

- 请求声明的模型或能力。
- 租户权限和成本预算。
- 输入长度、最大输出和多模态类型。
- 质量、延迟和安全要求。
- 模型版本和灰度比例。
- 实例队列、KV 可用量和 GPU 健康。
- 区域、数据驻留和网络距离。
- 是否允许量化、缓存、投机或降级。

“round-robin”只适合极其同质的实例。一个有 10,000 token KV 状态的实例与一个空闲实例，不应被视为同样健康。

### 4.14.2 长短请求隔离

长度分桶能减少 head-of-line blocking，但会产生资源碎片。澜沧可以设置：

| 队列 | 典型输入 | 目标 | 允许动作 |
| --- | ---: | --- | --- |
| interactive-short | 小于 2K | 低 TTFT 和低尾延迟 | 小 batch、短等待 |
| interactive-long | 2K 到 32K | 稳定 TTFT 和 KV 控制 | chunked prefill |
| agent-step | 中等输入、短输出 | 快速返回工具参数 | 优先 decode |
| offline | 任意 | 高吞吐、低单请求优先级 | 可抢占、较大 batch |

分界线应来自实际分布，而不是随意选择 2K 或 32K。队列要有借用规则，否则低峰期会出现一边排队、一边空闲的资源浪费。

### 4.14.3 模型路由和质量反馈闭环

如果小模型路由后的任务成功率下降，Router 不能只看成本。可以给每条路由记录：

~~~math
U_{\mathrm{route}}
=
w_q Q
-
w_l L
-
w_c C
-
w_r R
~~~

其中 Q 是质量或任务成功率，L 是延迟，C 是成本，R 是风险或错误率，权重由业务目标决定。这个公式不是让 Router 实时计算一个神秘总分，而是提醒设计者：路由决策必须有可观测的目标和反事实比较。

## 4.15 流式输出：token 生成之后还有协议问题

### 4.15.1 流式事件

一次流式响应建议包含：

~~~text
response.started
response.metadata
response.output.delta
response.output.delta
response.tool_call.delta
response.output.completed
response.completed
~~~

每个事件携带 response_id、sequence、timestamp、model_version 和 usage 增量或最终 usage。客户端断线后，平台至少能根据 sequence 判断已经发送到哪里；是否支持续传则需要持久化事件或重新生成协议。

### 4.15.2 背压和 flush

GPU 生成速度可能高于客户端读取速度。若平台无限制地把 token 放进进程内存，慢客户端会把资源从 GPU 扩散到网关、消息队列和应用服务器。需要设置：

- 每连接发送 buffer 上限。
- flush 批量和最大等待时间。
- 慢客户端超时。
- 取消信号传播时间。
- 中间代理的空闲超时和心跳。
- 部分输出审核策略。

flush 太频繁会增加网络和系统调用；flush 太慢会让用户感到模型“卡住”。应按 TTFT、token 间隔和连接稳定性共同调参。

### 4.15.3 输出审核和高风险响应

对普通闲聊，可以逐块发送；对高风险文本、工具调用和外部动作，先生成后审核更安全，但会增加 TTFT 和显存占用。平台可以提供不同的 streaming policy：

- raw：低风险实验，直接发送。
- buffered：积累若干 token 后审核再发送。
- reviewed：完整生成和审核后一次返回。
- structured：等待 JSON 或工具参数闭合后再发送。

这不是简单的“开关”，而是延迟、风险和用户体验的取舍。

## 4.16 自动扩缩容：扩的是可用 token 容量

### 4.16.1 指标选择

CPU 利用率通常不能代表生成服务是否拥塞。扩缩容控制器应观察：

- 每个队列的排队时间和长度。
- prefill 和 decode token throughput。
- 活跃序列和 KV block 使用率。
- TTFT、TPOT、P95/P99。
- GPU 计算、显存、带宽和通信。
- pending deployment 数和权重加载进度。
- 取消、超时、OOM 和错误率。
- 质量回归与降级比例。

控制器应使用平滑窗口、冷却时间和最小副本，避免流量抖动导致频繁启动和销毁。

### 4.16.2 目标副本数的近似

若当前每个副本的有效输出 token 容量为 C_out，目标输出速率为 Lambda_out，目标利用率为 u，故障余量为 h，则：

~~~math
R_{\mathrm{target}}
=
\left\lceil
\frac{\Lambda_{\mathrm{out}}}
{C_{\mathrm{out}} \times u \times (1-h)}
\right\rceil
~~~

这只是 decode 侧近似。若 prefill 已经饱和，应该用 input token 容量计算另一侧副本数；若两者瓶颈不同，可能需要不同的 prefill 和 decode 池。

### 4.16.3 冷启动

大模型冷启动包括：

1. 拉取或挂载权重。
2. 校验分片和 digest。
3. 加载到 GPU。
4. 初始化 tokenizer、engine 和 CUDA graph。
5. 分配 KV block。
6. 执行 warmup。
7. 加入健康实例池。

因此“扩容命令已发出”不等于“容量已经增加”。Kubernetes Device Plugins 负责把 GPU 等设备资源暴露给调度系统，Horizontal Pod Autoscaler 负责依据指标调整工作负载副本；二者都不理解模型权重加载时间、KV Cache 和 TTFT，推理平台需要在上层补充这些指标。

### 4.16.4 缩容

缩容要先停止接收新请求，再等待或迁移已有请求。对于长输出，等待可能很久；对于可取消的离线任务，可以提前保存结果和用量。强行杀掉实例会引发重复请求、流式中断和 token 计费争议。

缩容策略应该记录“draining_started”“active_requests”“remaining_kv_tokens”和“terminated_reason”，让一次正常维护不会被误报成模型故障。

## 4.17 缓存：节省计算，也引入一致性和权限问题

### 4.17.1 Response Cache

只有在输入、模型版本、采样参数、租户权限和外部数据新鲜度都兼容时，完整回答缓存才可复用。对随机生成模型，temperature、seed、工具状态和时间上下文都会影响结果。适合 response cache 的通常是：

- 固定 FAQ。
- 确定性分类。
- 有明确版本的模板化摘要。
- 权限边界清晰的公开内容。

缓存 key 可以抽象为：

~~~math
K_{\mathrm{response}}
=
H(
\mathrm{tenant},
\mathrm{model\_digest},
\mathrm{tokenizer\_digest},
\mathrm{input},
\mathrm{sampling},
\mathrm{tools},
\mathrm{policy\_version},
\mathrm{data\_snapshot}
)
~~~

少一个字段都可能返回过期、错误或越权结果。

### 4.17.2 Embedding Cache

Embedding cache 比完整回答更容易复用，但文本规范化、embedding 模型版本、语言和权限仍应进入 key。文档发生更新时，旧向量应该按数据快照失效，而不是让索引和回答引用不同版本。

### 4.17.3 Prefix Cache 和 Response Cache 的区别

Prefix Cache 复用中间计算状态，通常仍要运行后续 decode；Response Cache 直接复用最终输出。前者减少 prefill，后者减少整个推理，但后者更容易受到权限、随机性和新鲜度影响。把两者都称作“缓存命中”会让成本分析失真，指标中要分别记录。

## 4.18 观测、质量和成本：用一次 trace 串起因果链

### 4.18.1 一条请求 trace 记录什么

trace_id 下至少要能找到：

- gateway 接收时间和认证结果。
- 路由的模型、版本、区域和实例。
- 队列进入和离开时间。
- prefill 开始、结束和输入 token 数。
- decode iteration 数、输出 token 数和 TPOT。
- KV block 分配、命中和释放。
- prefix/response cache 命中。
- 量化、投机解码和降级信息。
- 流式事件、取消和网络断开。
- 引擎、GPU、节点和 rank。
- 质量反馈、任务结果和用量账单。

这不是要求把完整 prompt 永久写入日志。敏感内容应脱敏、哈希、采样或在受控存储中保存；trace 仍要能通过 request_id 和 artifact digest 关联行为。

### 4.18.2 延迟告警和资源告警要分开

TTFT 变差可能来自排队、prefill、网络或网关；GPU 利用率高不一定是坏事，KV block 使用率高也可能只是稳定高吞吐。告警要带原因维度：

- queue_p99_high。
- prefill_tokens_per_second_low。
- decode_tpot_high。
- kv_free_blocks_low。
- gpu_memory_fragmentation_high。
- stream_disconnect_rate_high。
- model_quality_regression。
- billing_event_lag。

只有“推理服务异常”这个总告警，不能帮助工程师选择修复方向。

### 4.18.3 单位成功任务成本

设一段时间内 GPU、存储、网络和重试成本之和为 C_total，完成的业务成功任务数为 N_success，则：

~~~math
C_{\mathrm{success}}
=
\frac{
C_{\mathrm{GPU}}
+
C_{\mathrm{storage}}
+
C_{\mathrm{network}}
+
C_{\mathrm{retry}}
+
C_{\mathrm{idle}}
}{
N_{\mathrm{success}}
}
~~~

只有在评估窗口内存在至少一个成功业务任务时，这个式子才有定义；当 $N_{\mathrm{success}}=0$ 时，应记录为“没有成功证据”，而不是用 1 代替分母。还要明确重试成本是否已经包含在 $C_{\mathrm{retry}}$ 中，以及 GPU、存储和网络成本的统计窗口。如果只按 output token 计费，会把长 prompt、缓存命中和失败重试隐藏掉；如果只按 GPU 小时计成本，又无法比较不同模型路由的业务价值。平台可以同时展示 token 成本和成功任务成本，但不能把两者混为一谈。

## 4.19 高可用和故障恢复：先保住状态语义，再谈重试

### 4.19.1 常见故障

| 故障 | 直接表现 | 首要动作 |
| --- | --- | --- |
| GPU OOM | 新请求失败或进程退出 | 停止接收、保存事件、摘除实例 |
| 节点故障 | 所有 rank 失联 | 切换副本，重建运行状态 |
| 权重存储不可用 | 新实例无法启动 | 保留健康副本，暂停扩容 |
| KV allocator 泄漏 | 可用 block 持续下降 | 采样 block 生命周期并排空实例 |
| 引擎 hang | 队列和 token 进度停滞 | watchdog、隔离、重启 |
| 版本质量回归 | 任务成功率下降 | 停止流量扩大，按版本回滚 |
| 网关断连 | 流式中断 | 传播取消或按协议恢复 |
| 审核服务超时 | 高风险响应无法完成 | 使用明确的保守策略或异步 |

### 4.19.2 健康检查不能只返回 HTTP 200

实例健康至少分三层：

- liveness：进程是否还活着。
- readiness：能否接受新请求，模型和 KV allocator 是否准备好。
- serving health：在代表性输入下，prefill、decode、流式和取消是否正常。

一个进程可以 liveness 正常，却因 GPU kernel hang 无法推进 token；一个实例可以 readiness 暂时为 false，却仍在优雅完成已有流。控制器需要理解这些状态，不能用一次 HTTP 200 覆盖所有情况。

### 4.19.3 重试边界

可以自动重试的通常是尚未开始执行、且请求幂等的路由和资源错误。已经生成部分 token 的请求重试会带来：

- 重复计算。
- 输出不同。
- 工具调用重复。
- 计费重复或丢失。
- 客户端看到两个不同的流。

对带外部副作用的 Agent 工具调用，推理平台不能替应用保证幂等。平台只提供 request_id、token 使用量和执行事件，应用要为转账、发邮件或写数据库设计自己的幂等键和补偿。

### 4.19.4 排空和优雅升级

升级实例时：

1. 停止从 Router 接收新请求。
2. 保留已有流并设置最长排空时间。
3. 观察活跃序列、KV token 和 stream 状态。
4. 超过时间的请求按协议取消或迁移。
5. 写入最终用量和原因。
6. 验证新实例 readiness 和 serving health。
7. 再扩大流量。

如果引擎不支持 KV 迁移，迁移意味着重新 prefill，用户可能看到更高 TTFT；这个代价应在升级策略中显式记录。

## 4.20 多租户、安全和数据边界

### 4.20.1 租户隔离

租户边界覆盖：

- 模型访问权限。
- 队列和 token 配额。
- KV、prefix 和 response cache。
- prompt、输出和 trace。
- 成本和账单。
- adapter、工具 schema 和区域。
- 管理员操作和审计。

共享 GPU 不等于共享数据状态。共享只应发生在明确证明不会泄漏的计算 kernel 和公共模型权重层面。

### 4.20.2 缓存侧信道

即使缓存没有直接返回另一个租户的文本，命中率、响应时间、显存变化和错误信息也可能泄漏某个前缀是否存在。高敏感租户可以：

- 禁用跨请求 prefix reuse。
- 使用租户独立 cache namespace。
- 限制命中信息暴露。
- 对缓存统计做聚合和采样。
- 让缓存失效与权限版本绑定。

### 4.20.3 日志和输入输出数据

推理日志可能包含源码、个人信息、内部文档和秘密。平台要定义：

- 哪些字段默认不记录。
- 哪些字段只保存哈希或长度。
- 采样和脱敏规则。
- 加密和访问审批。
- 保留期限和删除流程。
- 调试临时日志的自动过期。

“为了排查问题把 prompt 全量打印”通常会把一次服务故障变成数据泄漏事故。

### 4.20.4 容器、模型和供应链

推理容器需要最小权限，模型 artifact 要有 digest 和来源验证，量化文件和引擎插件也要进入供应链扫描。只验证基础镜像而不验证自定义 CUDA extension、tokenizer 或 adapter，供应链链路仍然不完整。

## 4.21 完整案例：澜沧平台发布一个长上下文模型

### 4.21.1 需求

澜沧要上线 model-v7：

- BF16 基座模型，支持 32K context。
- Chat 业务峰值 800 QPS，平均输入 1200、输出 400 token。
- RAG 业务峰值 180 QPS，平均输入 9000、输出 700 token。
- Agent 业务峰值 60 QPS，每个任务平均 4 次调用。
- 目标 TTFT P95 小于 1.8 秒，TPOT P95 小于 80 ms。
- 高敏感企业租户不允许跨租户 prefix cache。
- 允许低风险请求路由到经过评估的 INT8 版本。

### 4.21.2 先算工作量

Agent 每次调用平均输入 1800、输出 250 token。因此：

~~~math
\Lambda_{\mathrm{in}}
=
800\times1200
+
180\times9000
+
60\times4\times1800
=
3{,}012{,}000\ \mathrm{input\ tokens/s}
~~~

~~~math
\Lambda_{\mathrm{out}}
=
800\times400
+
180\times700
+
60\times4\times250
=
506{,}000\ \mathrm{output\ tokens/s}
~~~

这说明系统不是简单的“3.518M token/s”问题。RAG 主要压 prefill，Chat 和 Agent 的输出比例更高，Agent 还会产生更多路由和连接事件。

### 4.21.3 选择实例和队列

平台先用真实模型做三组基准：

- 2K input / 256 output，交互短请求。
- 9K input / 512 output，RAG 长请求。
- 1K input / 1K output，长回答。

每组记录不同并发和 batch token 限制下的 TTFT、TPOT、KV 水位和 GPU 功耗。基准结果显示，单一队列在 RAG 峰值时会让 Chat P95 TTFT 翻倍，因此部署两类池：

- short-pool：高优先级、较小 batch 等待、较多副本。
- long-pool：chunked prefill、较大 KV 预算、严格输入上限。

Agent-step 先复用 short-pool，但为工具参数输出设置较高的 decode 优先级。离线评估不占用这两个池的保留容量。

### 4.21.4 发布 INT8 路由

INT8 版本在普通对话和分类上接近 BF16，但代码和工具参数集出现回归。Router 只把低风险分类、FAQ 和简单摘要送到 INT8；代码、工具调用、长上下文和高敏感租户继续使用 BF16。每个请求的 trace 记录 precision、quantization_config_digest 和 route_reason，质量平台按任务切片比较。

### 4.21.5 压测中发现的问题

压测时总 GPU 利用率只有 62%，但 Chat TTFT P99 已经超过 3 秒。进一步拆解发现：

- RAG prefill chunk 太大，长请求阻塞 decode。
- short-pool 和 long-pool 共享一个节点级 GPU 资源池。
- prefix cache 对公共 system prompt 命中率不错，但高敏感租户被错误纳入同一 cache namespace。
- GPU 仍有计算空闲，却没有足够连续的 KV block。

修复动作不是简单加 GPU：

1. 缩短 long-pool 的 prefill chunk。
2. 为 short-pool 保留 KV block 和拓扑稳定的 GPU。
3. 按租户重建 prefix cache namespace。
4. 监控 free_blocks、fragmentation 和 queue_p99。
5. 对超出预测等待时间的 RAG 请求转异步。

### 4.21.6 一次节点故障

一个 long-pool 节点在 600 个活跃序列时失联。平台执行：

1. Router 摘除节点，停止新请求。
2. 写入受影响 request_id、已发送 sequence 和 usage snapshot。
3. 已完成的请求不重试。
4. 尚未开始 decode 的请求重新排队。
5. 已发送部分流的请求返回可识别的中断原因。
6. 对允许重试且无外部副作用的请求使用同一 idempotency_key。
7. 新实例通过 serving health 后逐步接收流量。

平台没有声称“所有流都无缝迁移”，因为当前引擎没有跨节点 KV 迁移能力。它选择了诚实的中断语义和可审计的重试边界，避免把重复输出当成连续输出。

## 4.22 设计取舍：没有单一最优配置

### 4.22.1 更大的 batch 还是更低的尾延迟

大 batch 通常提高吞吐，但增加等待和资源竞争。在线交互系统优先保护 TTFT 和 TPOT；离线任务优先提高 token throughput。可行的策略是为不同业务设置不同队列和预算，而不是在一个全局参数上寻找妥协。

### 4.22.2 共享实例还是专用实例

共享实例提高平均利用率，却增加租户干扰、缓存边界和故障影响面。专用实例更易于保证 SLA 和数据域，但可能在低峰期浪费 GPU。决策应同时比较：

~~~math
C_{\mathrm{shared}}
=
C_{\mathrm{GPU}}
+
C_{\mathrm{interference}}
+
C_{\mathrm{isolation}}
~~~

~~~math
C_{\mathrm{dedicated}}
=
C_{\mathrm{GPU}}
+
C_{\mathrm{idle}}
+
C_{\mathrm{operations}}
~~~

这里的成本既可以是金钱，也可以是延迟、风险和运营复杂度。

### 4.22.3 Prefix Cache 还是重新计算

Prefix Cache 节省 prefill，但占用显存或外部缓存，并带来失效和权限复杂度。对公共且稳定的 system prompt，它通常有价值；对变化快、权限敏感或命中低的前缀，重新计算可能更简单。用命中率和实际节省的 prefill 时间评估，而不是只看缓存条目数量。

### 4.22.4 量化还是更多 GPU

量化减少权重和部分计算成本，但可能降低质量或引入 kernel 限制；更多 GPU 保持高精度，却增加空闲和通信成本。最终指标应是“质量约束下的成功任务成本”和“质量约束下的尾延迟”，而不是单独的显存数字。

### 4.22.5 Prefill/decode 解耦还是共享池

解耦可以减少阶段干扰，代价是 KV 传输、额外网络、资源碎片和更复杂的故障恢复。流量稳定、TTFT 和 TPOT 都严格时更值得考虑；流量小、模型小、运维能力有限时，共享池可能更可靠。

## 4.23 复盘练习：用数字和状态解释系统行为

### 练习一：token 工作量

一个 RAG 服务 200 QPS，平均输入 6000 token、输出 600 token；每次请求有 20% 概率重试一次。计算期望 input/output token 速率，并说明重试是如何进入容量和成本账本的。

### 练习二：KV 容量

某模型有 48 层、8 个 KV head、head dimension 为 128，KV 使用 BF16。单卡除权重和运行时后有 20 GiB 可用于 KV。估算单 token 的 KV 字节数和理想缓存 token 数，再列出 block 对齐、reserve 和多模态 encoder 会造成的偏差。

### 练习三：长短请求干扰

短请求输入 500、输出 100；长请求输入 16,000、输出 500。设计两个队列的 token budget、最大等待时间和借用规则，说明为什么总 GPU 利用率上升不代表短请求 P99 一定改善。

### 练习四：量化回归

INT4 版本单位 token 成本下降 45%，但代码任务成功率从 0.74 降到 0.68，普通 FAQ 成功率不变。设计路由和评估方案，计算代码任务是否值得使用 INT4 需要哪些业务数据。

### 练习五：流式取消

客户端在收到第 120 个 token 后断开，服务端已经生成到第 150 个 token。设计事件、计费、KV 释放和重试语义，说明为什么不能简单把新请求的前 150 个 token 拼到旧流上。

### 练习六：阶段解耦

prefill 池的 TTFT 达标但 decode 池 TPOT 超标，或反过来。分别列出扩容、调度、KV 传输和路由动作，并说明哪些动作会改变成本和故障域。

## 4.25 本章小结

设计推理平台时，最先要问的不是“使用哪一个引擎”，而是一次请求包含多少输入和输出工作、它处于 prefill 还是 decode、需要保持多久的 KV 状态，以及服务要对用户承诺什么样的延迟、质量和成本。

工作量模型把外部 QPS 展开为 input token、output token 和 Agent 调用放大；资源账本把权重、KV、workspace、运行时和 reserve 分开；调度器再用 token budget、KV budget、优先级和队列把请求组成每轮 batch。PagedAttention、prefix cache、continuous batching、量化、投机解码和 prefill/decode 解耦，都是对某个瓶颈的优化，不是可以无条件叠加的魔法。

一个可运营的平台还要把模型版本、tokenizer、template、量化产物、引擎配置和路由策略一起发布；把流式取消、重试、缓存命中、KV 释放、质量反馈和成本事件记录在同一条 trace 上；在 GPU OOM、节点故障、模型回归和过载时给出可解释的状态。最终，推理平台的成熟度不在于它能否让某个 benchmark 跑出漂亮数字，而在于面对不同长度、不同租户、不同风险和不同故障时，仍能把一次请求的资源、结果和代价说清楚。
