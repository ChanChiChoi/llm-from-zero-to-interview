# 第九章：设计视频生成服务：把时空模型变成可治理的异步资产系统

视频生成服务与聊天、检索和实时语音系统的时间尺度不同。一次聊天请求通常在几秒内返回，实时语音要尽快开始播放；视频生成却可能需要数十秒、数分钟甚至更久，还要消耗大量 GPU、写入大对象、经过内容审核和转码。

用户提交的也不只是文字。一个任务可能包含文本提示、首帧图片、参考人物、动作控制、已有视频、蒙版、音频和镜头参数。模型输出也不只是一个字符串，而是一组有版本、有权限、有审核状态和有生命周期的媒体 artifact。

可以把生产视频生成系统看成：

~~~text
任务请求
  -> 身份、配额、输入安全和授权
  -> 参数规范化与模型路由
  -> 可取消的异步队列
  -> GPU worker 生成时空 latent
  -> 解码、转码、缩略图和水印
  -> 输出安全与来源声明
  -> 对象存储、CDN、通知和删除
~~~

本章用营销团队的“镜河”视频平台贯穿说明。镜河帮助团队根据产品说明和获授权的产品图生成 4 到 10 秒演示短片。它可以生成草稿、比较候选和重新生成，但不能把未经授权的人脸变成广告、把一段输入视频的版权自动转给平台，也不能因为模型输出了一个视频就跳过审核和来源记录。

真正需要设计的问题是：

- 为什么视频任务不能按普通同步 API 处理？
- 画面分辨率、帧数、采样步数和模型大小怎样放大 GPU 成本？
- 任务在排队、生成、后处理和审核之间怎样恢复、取消和计费？
- 用户取消时，GPU 已经消耗的成本和正在写入的文件怎么处理？
- 输出视频的内容安全、人脸授权、版权和来源声明怎样进入系统状态？
- 进度百分比和预计等待时间怎样既有用又不制造虚假承诺？
- 质量评估如何同时覆盖提示遵循、时序一致性、物体身份和安全漏检？
- 删除一个视频时，原始参考图、latent、预览、CDN 缓存和审计记录怎样一起失效？

## 9.0 先理解视频生成：比图片多了一条时间轴

### 9.0.1 给初学者：视频不是很多张独立图片

如果逐帧独立生成图片，每一帧可能都有漂亮的画面，但人物、物体、光照和背景会跳动。视频生成需要让相邻帧保持合理的运动和身份关系。

因此，视频任务至少有三种质量：

1. 单帧质量：某一帧是否清晰、构图是否合理。
2. 时间一致性：人物、物体、纹理和镜头运动是否连续。
3. 语义遵循：是否按照提示、参考图和控制条件生成。

一段视频整体看起来漂亮，不代表它正确执行了提示；一段语义符合的视频，也可能出现手指、文字或物体在帧间变形。系统必须分别记录这些质量维度。

### 9.0.2 给专家：时空计算量

设视频有 F 帧，每帧宽度 W、高度 H，视觉 patch 或 latent 的空间步长近似为 P，则未考虑时间压缩时，时空 token 数可以粗略写为：

~~~math
N_{\mathrm{spatiotemporal}}
\approx
F
\cdot
\left\lceil \frac{W}{P} \right\rceil
\cdot
\left\lceil \frac{H}{P} \right\rceil
~~~

真实模型通常会在时间和空间上做 latent 压缩、patch 合并、窗口注意力或分层生成，因此这个式子不是某个模型的实际 token 计算。它只说明：时长、分辨率和帧率不是三个无关参数，它们会共同增加显存、计算、解码和存储压力。

### 9.0.3 生成模型路线的边界

DDPM 等扩散模型工作建立了逐步去噪生成的基本框架。Video Diffusion Models 把扩散过程扩展到视频数据，研究时间维度和视频生成。Make-A-Video、Imagen Video、Stable Video Diffusion 等工作探索文本到视频、图像到视频、级联分辨率和视频预训练等路径。

DiT 研究把扩散模型的去噪骨干表示为 Transformer，这对理解模型规模、token 数和计算路径有帮助。AnimateDiff 等工作探索在图像生成模型上加入运动建模的路线；VideoCrafter 等工作则体现了开源视频生成系统的工程与模型组合。

这些论文支持模型结构和受控实验的理解，不直接给出镜河的 GPU 秒、内容通过率、稳定性或商业授权结论。产品系统仍需用自己的分辨率、时长、语言、参考图和安全样本测量。

## 9.1 定义范围和任务契约

### 9.1.1 镜河第一版

镜河第一版支持：

- 文本到短视频。
- 一张已授权产品图到短动态视频。
- 固定的 4、6、8 秒时长。
- 少量宽高比和输出分辨率。
- 生成草稿、取消、重新生成和比较候选。
- 输入与输出安全审核。
- 可见水印和来源元数据。
- 团队配额、项目归属和结果删除。

第一版不支持长视频连续叙事、任意真人身份转换、自动广告投放、未经验证的版权素材混合、音视频精确对口型和实时生成。先把短任务的资产、审核、队列和成本做清楚，比开放所有参数更容易建立可追责边界。

### 9.1.2 请求契约

一个视频任务至少包括：

- tenant_id、project_id、requester_id。
- prompt 和语言。
- reference_asset_ids。
- mask、控制条件或运动指引。
- model_profile。
- duration、fps、width、height 和 aspect_ratio。
- seed_policy。
- safety_policy。
- output_format。
- retention_policy。
- idempotency_key。
- trace_id 和客户端版本。

这些字段不能只存在于模型 prompt。任务服务要把它们规范化并保存版本，这样计费、重试、审核和复现才有共同依据。

### 9.1.3 结果契约

成功结果不只是一个下载地址，还要包含：

- asset_id 和 task_id。
- output_version。
- 文件格式、大小、时长、帧率和分辨率。
- model_version、seed 和生成参数。
- input_asset_refs。
- 输入与输出审核状态。
- 水印或 provenance 状态。
- 过期时间和下载权限。
- 缩略图和预览版本。
- 质量警告和人工复核结果。

如果结果审核尚未完成，接口应返回 reviewing，而不是把临时文件当成可公开资产。

## 9.2 资产、任务和版本

### 9.2.1 任务和资产分开

一个任务可能生成多个候选，用户可能从候选中收藏一个，也可能在同一参数上重新生成。任务记录计算过程，资产记录可被用户查看、下载、编辑和删除的媒体对象。

任务对象包含：

- task_id、状态和队列信息。
- 规范化输入和配置快照。
- 当前 worker、尝试次数和成本。
- 进度事件和错误。
- 审核与计费状态。

资产对象包含：

- asset_id、来源 task_id 和版本。
- 视频文件、缩略图和编码版本。
- 所有权、项目和可见范围。
- 内容标签、来源声明和水印。
- 过期、删除和下载记录。

混淆两者会导致“任务失败但临时视频可下载”“用户删除资产但任务重试又生成同一内容”等问题。

### 9.2.2 不可变输入和派生 artifact

镜河为每次任务保存：

~~~text
prompt_snapshot
reference_asset_snapshot
normalized_config
  -> latent_or_checkpoint_reference
  -> raw_video
  -> decoded_preview
  -> transcoded_asset
  -> safety_report
  -> provenance_manifest
  -> thumbnail_and_storyboard
~~~

每个对象关联上游 digest、处理代码、模型版本、时间和权限。大体积中间 latent 默认不长期保留，但如果需要复现或争议调查，必须有明确的保留等级和加密策略。

### 9.2.3 复现与随机性

视频生成通常包含随机采样。seed 可以帮助复现同一配置下的近似结果，但不能保证不同硬件、CUDA、算子、模型权重和采样实现得到字节级相同的视频。

因此复现记录至少包括：

- seed。
- 模型权重 digest。
- VAE、文本编码器和控制模块版本。
- 采样器和步数。
- 运行时、GPU 类型和精度。
- 输入文件 digest。
- 后处理和编码器版本。

“同一个 seed”没有这些上下文时，不能被写成完全可复现的承诺。

### 9.2.4 处理状态

视频任务可以有：

~~~text
created
  -> input_reviewing
  -> queued
  -> preparing
  -> running
  -> post_processing
  -> output_reviewing
  -> succeeded
~~~

任意阶段也可能进入 failed、cancel_requested、cancelled、expired 或 blocked。输入审核未通过直接进入 rejected，不应该进入 GPU 队列。

状态转移要记录前序版本、操作者和原因。用户重复点击、客户端重试和 worker 重启都不能让状态回退或重复扣费。

## 9.3 输入接入与授权

### 9.3.1 Prompt 规范化

Prompt Processor 可以做语言检测、模板展开、敏感词分类、长度限制和参数校验，但不能悄悄改变用户的核心意图而不留记录。

如果系统为用户补充镜头、风格和负面提示，应保存：

- 原始 prompt。
- 规范化 prompt。
- 生成的模板字段。
- 使用的策略和版本。
- 用户是否允许自动改写。

输出审核和事故调查需要知道模型实际看到的文本，而不是只看用户最初输入。

### 9.3.2 参考图和输入视频

参考素材要经过：

- 文件类型与解码检查。
- 恶意文件和资源消耗检查。
- 内容安全分类。
- 人脸与敏感对象检测。
- 版权或授权声明收集。
- 租户和项目权限校验。
- digest 和来源保存。

用户拥有上传权限，不自动意味着平台可以把素材公开、训练、用于广告或生成真实人物变体。授权范围要映射到具体任务和输出用途。

### 9.3.3 输入水位

如果参考图正在扫描、上传未完成或授权状态未知，任务不得直接进入生成队列。任务应等待输入 ready 或进入 blocked，并向用户说明缺少什么。

### 9.3.4 输入外发

外部模型服务可能位于不同区域或不同供应商。任务路由要考虑数据区域、租户合同、版权和隐私。敏感参考图不能因为“模型效果更好”就无记录地发往任意外部端点。

## 9.4 GPU 计算账本

### 9.4.1 生成工作量

视频生成的工作量可以用教学近似表示为：

~~~math
W_{\mathrm{gen}}
\propto
F
\cdot
R_{\mathrm{spatial}}
\cdot
S_{\mathrm{denoise}}
\cdot
C_{\mathrm{model}}
~~~

F 是帧数，R_spatial 表示空间 token 或 latent 数量，S_denoise 是采样步数，C_model 表示每一步的模型计算量。实际计算还受 batch、时间窗口、注意力优化、条件数量、精度和硬件影响。

时长和帧率共同决定 F：

~~~math
F
=
\mathrm{duration\_seconds}
\cdot
\mathrm{fps}
~~~

例如把 8 秒、24 fps 的视频改成 12 秒、30 fps，帧数从 192 增加到 360，变化并非“只多 50% 时长”，而是还提高了帧率带来的时空负担。

### 9.4.2 显存不是只由模型参数决定

视频 worker 的显存账本可能包含：

- 模型权重。
- 文本编码器和条件编码器。
- latent 和中间激活。
- 注意力工作区。
- VAE 解码缓冲。
- batch 中的多个样本。
- 视频帧和后处理缓存。

长视频通常需要时间切片、空间切片、分段生成或分阶段解码。把模型权重能放进 GPU，不能推出任意分辨率和时长都能运行。

### 9.4.3 精度和质量

FP16、BF16、量化和不同 attention 实现可以降低显存或提高吞吐，但可能影响细节、稳定性和极端输入。视频平台要以输出质量、时序一致性和安全漏检共同做回归，不能只比较 GPU 利用率。

## 9.5 模型路由与生成策略

### 9.5.1 规格 profile

不要让用户直接操纵所有底层参数。平台可以提供有限的 model profile：

| Profile | 目标 | 典型限制 |
| --- | --- | --- |
| draft | 快速预览 | 低分辨率、短时长 |
| standard | 默认质量 | 固定时长和常用比例 |
| quality | 更高细节 | 更高 GPU 成本和等待 |
| image_motion | 产品图动态化 | 需要参考图和运动限制 |
| enterprise_batch | 批量生产 | 固定模板、配额和回调 |

每个 profile 固定模型、采样器、允许分辨率、时长范围和成本系数，避免客户端构造无法调度的组合。

### 9.5.2 级联生成

可以先低清草稿，再对用户选中的候选做高分辨率生成。低清草稿的价值是尽早淘汰错误构图和不合适的运动，减少昂贵任务。

但低清预览和高清结果不一定完全一致。用户界面要说明预览只是候选信号，不能把预览审核状态直接沿用到高清输出。

### 9.5.3 多候选和 seed

一次生成多个候选可以提高选中概率，却按候选数量近似放大 GPU 成本。平台可以让用户选择候选数，并在额度和预算上预先估算。

同一 seed 可以用于复现或对照，不同 seed 用于探索。用户切换 prompt、参考图、分辨率或模型后，应创建新任务版本。

### 9.5.4 控制条件

首帧、姿态、深度、边缘、蒙版和运动轨迹都可能影响生成。控制越多，模型路由、显存、失败模式和评估越复杂。输入契约要记录控制条件的来源和权重，输出质量评估要检查是否遵守控制而非只看文本相关性。

## 9.6 队列、优先级与公平调度

### 9.6.1 为什么单队列不够

长任务和短任务混在一个 FIFO 队列中，会让短预览被长高质量任务阻塞；所有用户共享一个队列，又可能被批量客户占满。

镜河可以按以下维度分组：

- 免费、个人付费和企业 SLA。
- draft、standard 和 quality。
- 文生视频和图生视频。
- 交互预览和离线批处理。
- 普通任务和人工复核任务。

### 9.6.2 优先级不是无限插队

优先级可以由用户等级、任务年龄、截止时间、历史消费和资源规格共同决定。老化机制让等待时间较长的低优先级任务逐渐获得服务机会；每个租户还应有并发和预算上限。

如果企业客户永远插队，免费用户可能永久饥饿；如果完全 FIFO，高价 SLA 又无法兑现。公平是策略约束，不是调度器自动获得的性质。

### 9.6.3 预计等待时间

设队列中在先任务的预计 GPU 时间为 g_i，可用等价 worker 数为 M，当前任务的优先级和队列规则决定可见集合 Q，则粗略等待时间为：

~~~math
\widehat{T}_{\mathrm{wait}}
\approx
\frac{\sum_{i \in Q} g_i}{M}
+
T_{\mathrm{dispatch}}
~~~

这是教学估算。worker 冷启动、模型切换、失败重试、抢占和资源碎片都会让实际值偏离。界面应显示估计区间或阶段，而不是承诺精确到秒的完成时间。

### 9.6.4 规格分桶

把相近模型、分辨率、时长和控制条件的任务分在一起，可以提高 warm cache 和批处理机会；代价是任务可能等待更久。调度器要把模型加载成本也作为工作量，而不是只看单个任务的采样时间。

## 9.7 GPU 调度与 Worker 生命周期

### 9.7.1 资源匹配

GPU Scheduler 需要知道：

- GPU 显存和计算能力。
- 模型权重已加载在哪些节点。
- 任务所需 profile 和精度。
- 单卡、跨卡或分片需求。
- 节点健康、温度和错误。
- 租户和队列配额。
- 预计执行时间和取消策略。

Kubernetes 的 GPU 调度文档可以说明设备资源如何暴露给工作负载，但它不会替视频平台决定任务公平性、模型 warm pool 或输出审核。

### 9.7.2 Warm pool 与冷启动

热门模型可以保留 warm pool，减少加载权重和初始化 VAE 的等待；冷门模型按需加载，节省显存。模型数量增多时，warm pool 可能造成显存碎片和低利用率。

系统应按近期请求、SLA 和加载成本调整池大小。warm pool 变化本身要观测，因为冷启动会直接进入用户首阶段等待。

### 9.7.3 Worker 心跳和租约

任务被分配给 worker 后，要有租约、心跳和 attempt_id。worker 崩溃时，调度器回收任务，但不能盲目从头重跑写入或计费。任务状态应先判断：

- 是否产生了可复用中间结果。
- 是否上传了临时视频。
- 是否已经扣除额度。
- 是否需要检查 GPU 和对象存储残留。

### 9.7.4 批处理

相同 profile 的任务可以 batch，提高 GPU 吞吐；但 batch 会增加等待，且不同输入时长、控制条件和显存需求可能无法合并。调度器要有最大等待窗口，超过窗口即使 batch 不满也开始执行。

### 9.7.5 抢占与暂停

扩散生成并非天然支持任意位置暂停。若要抢占，系统需要保存足够的随机状态、latent 和模型阶段，存储与恢复成本可能高于继续运行。

第一版可以只在任务阶段边界取消，不做任意中间抢占；高优先级任务通过保留专用资源和队列配额实现，而不是把所有低优先级任务强制打断。

## 9.8 Worker 执行与进度

### 9.8.1 执行阶段

一个 worker 可以报告：

1. loading_model。
2. preparing_condition。
3. denoising。
4. decoding。
5. encoding。
6. uploading。
7. waiting_output_review。

这些阶段对应不同的资源和失败原因，用户看到的状态比一个模糊 processing 更有解释力。

### 9.8.2 采样进度

如果采样有 S 步，当前完成 s 步，可以给出一个局部进度近似：

~~~math
p_{\mathrm{sample}}
=
\frac{s}{S}
~~~

但总任务进度不能直接等于 p_sample，因为模型加载、VAE 解码、转码、上传和审核也耗时。可以用阶段权重：

~~~math
p_{\mathrm{total}}
=
\sum_{k=1}^{K}
w_k p_k,
\qquad
\sum_{k=1}^{K} w_k = 1
~~~

w_k 来自历史实测，不是物理定律。模型切换和队列等待的估算误差应显示为不确定性。

### 9.8.3 取消语义

任务处于 queued 时取消最简单；running 时需要向 worker 发送 cancel_requested。worker 在安全检查点停止，释放 GPU 并清理临时文件。已经消耗的 GPU 时间是否退还，要由计费策略和失败原因决定。

如果客户端断开，不能自动把任务当成取消。用户可能只是切换页面，任务是否继续由产品策略和显式取消决定。

### 9.8.4 输出原子发布

生成结果先写临时对象，完成编码、校验、审核和元数据写入后，再把 asset 状态切换为 visible。这样用户不会下载到未上传完、未审核或缺少来源信息的视频。

## 9.9 后处理、编码与媒体资产

### 9.9.1 为什么模型输出还不是产品视频

模型可能输出 latent、帧序列或临时编码。产品还需要：

- 统一视频容器和 codec。
- 生成多码率播放版本。
- 抽取封面和 storyboard。
- 检查帧率、时长、黑帧和损坏。
- 加入可见水印或来源标记。
- 写入 metadata 和 provenance。
- 上传对象存储并刷新 CDN。

后处理也会消耗 CPU、GPU、磁盘和网络，不能把所有成本归到生成 worker。

### 9.9.2 编码和质量

重新编码可能改变清晰度、颜色和音频。系统应保存编码器版本、参数和输出 digest。视频可以通过文件完整性校验、解码试播、帧数和时长检查发现损坏。

### 9.9.3 预览和完整版

预览可以使用低码率和短片段，完整版按权限和下载策略提供。预览与完整版要有 asset_version 关系，不能让 CDN 缓存把旧预览当作新结果。

### 9.9.4 临时文件清理

worker 本地的 latent、帧缓存、失败输出和日志可能包含敏感输入。任务结束、取消或失败后要按保留策略清理，磁盘满也应触发告警和回收，而不是让新任务随机失败。

## 9.10 内容安全、身份和版权

### 9.10.1 输入和输出都审查

输入 prompt、参考图、参考视频、蒙版和控制条件都可能包含风险。输出视频还可能出现输入没有明确要求的裸露、暴力、真实人物变体或错误标识，因此必须进行输出审核。

输出审核可以组合：

- 抽帧图像分类。
- 视频时序分类。
- 音频和字幕检测。
- OCR 与文字识别。
- 人脸、人物和敏感对象检测。
- prompt、输入资产和输出的策略关联。

抽帧不是完整视频审核。抽样间隔过大可能漏掉短暂出现的危险帧；时序模型和高风险片段抽取需要按任务风险分层。

### 9.10.2 真实人物和肖像

涉及真实人物的参考图，要确认使用授权和用途。名人、普通用户和未成年人需要不同策略。身份检测是风险信号，不是法律授权证明。

对于高风险身份变换或冒充，系统可以拒绝、要求证明、限制传播或转人工。不能用“用户上传了照片”推断其拥有发布和变造该人物的权利。

### 9.10.3 C2PA 与来源声明

C2PA 规范提供内容来源和编辑历史的结构化声明方式。它可以帮助记录素材来源、生成软件和编辑操作，但它不是内容真实、版权拥有或模型输出安全的证明。

镜河可以在输出中附加签名的 provenance manifest，记录输入资产、模型服务和后处理。签名被删除或链路中断时，系统应显示来源不可验证，而不是把视频标成真实。

### 9.10.4 水印的边界

可见水印可以提醒用户内容是生成或预览，隐式水印或签名可以支持检测和来源追踪；二者都不能替代访问控制、审核、版权授权和用户举报。压缩、裁剪、转码可能影响水印检测，必须测量鲁棒性和误报。

### 9.10.5 违规结果的处理

违规输出应隔离而不是进入用户公开资产列表。系统保留必要的安全事件和最小证据以供审计，同时按照隐私和保留策略处理原始素材。输出审核失败不能自动重试同一风险输入，除非策略改变并有明确理由。

## 9.11 存储、CDN 和删除

### 9.11.1 对象分层

可以把对象分为：

- 用户输入。
- 原始生成结果。
- 审核前临时对象。
- 审核后可见资产。
- 缩略图和 storyboard。
- 多码率播放版本。
- provenance manifest。
- 审计和计费记录。

每一层有不同的权限、生命周期和删除条件。

### 9.11.2 存储估算

设统计窗口内每天新增的成功资产数为 N，平均每个视频对象的大小为 B_asset，保留天数为 D，预览、编码版本和备份放大因子为 k：

~~~math
S_{\mathrm{video}}
\approx
N \cdot B_{\mathrm{asset}} \cdot D \cdot k
~~~

如果每天 20 万个视频、每个视频对象平均 20 MB、保留 7 天、k 取 1.8，则：

~~~math
200000
\cdot
20\ \mathrm{MB}
\cdot
7
\cdot
1.8
\approx
50.4\ \mathrm{TB}
~~~

这是教学估算，未包含输入参考图和日志。它说明结果生命周期和冷热存储必须与生成能力一起设计。

### 9.11.3 CDN 缓存权限

下载 URL 应短时有效并绑定 asset_id、版本和用户范围。删除资产时要撤销下载令牌、使 CDN 缓存失效，并检查分享链接和回调是否仍能访问。

### 9.11.4 删除传播

删除一个资产可能需要失效：

- 可见视频和多码率版本。
- 封面、缩略图和 storyboard。
- CDN 缓存。
- 参考图和输入视频的任务引用。
- 生成参数和 prompt 中的个人信息。
- provenance 关联。
- 用户可见的历史和搜索索引。

安全审计和计费记录可能需要按合规要求保留，但应尽量减少可识别的媒体原文。

## 9.12 用户体验：等待也是产品的一部分

### 9.12.1 状态与阶段

界面可以显示队列、准备、生成、后处理、审核和完成，但不要把采样步数伪装成精确的全局百分比。用户更需要知道：

- 任务是否已被接收。
- 是否正在排队。
- 是否已经占用 GPU。
- 是否需要人工审核。
- 是否可以取消。
- 预计还要等多久。
- 失败后能否重试以及是否收费。

### 9.12.2 ETA 的不确定性

ETA 受队列、模型 warmup、任务规格和失败重试影响。可以显示区间和更新时间，例如“预计 1 到 3 分钟，最近一次更新 10 秒前”，并在估算失效时诚实调整。

### 9.12.3 取消与收费提示

用户取消 queued 任务通常可以退还额度；running 任务已经消耗 GPU，可能只能部分退还。规则必须在提交前展示，避免用户以为取消就完全没有成本。

### 9.12.4 反馈和重生成

重生成可以复用输入快照，但要明确它是新任务、新成本和新资产。用户反馈要区分：

- 提示没有遵循。
- 画面质量低。
- 运动不自然。
- 人物或产品不一致。
- 内容不安全。
- 生成等待过长。
- 来源或版权问题。

这些反馈会导向不同修复，不应只汇总成一个喜欢/不喜欢分数。

## 9.13 评估：质量、安全和成本一起看

### 9.13.1 任务质量

视频生成质量可以按：

- prompt adherence：是否满足文本要求。
- image/condition adherence：是否保持参考图或控制条件。
- temporal consistency：跨帧身份、纹理和背景是否稳定。
- motion quality：运动是否自然。
- visual quality：清晰度、构图和伪影。
- composition：主体、镜头和布局是否合理。

一个视频可能单帧很漂亮，但时间一致性差；也可能运动稳定但没有遵循 prompt。指标需要分开。

### 9.13.2 自动指标的限制

像素、特征和视频分布距离可以用于相对比较，但会受到参考视频、数据分布、分辨率和实现影响。用户评分和人工抽检能发现时序闪烁、文字变形和内容不符合业务的情况，但也有主观偏差和成本。

更可靠的评估组合是：

- 固定回归集。
- 结构化断言，例如时长、帧率和对象存在。
- 抽帧与时序一致性分析。
- 人工 pairwise 或 rubric 评分。
- 安全红队和举报复盘。
- 单位成功资产成本。

### 9.13.3 失败率分解

任务成功可以用条件概率链近似分解为：

~~~math
P(S)
\approx
P(\mathrm{input\ valid})
\cdot
P(\mathrm{scheduled}\mid\mathrm{input\ valid})
\cdot
P(\mathrm{generated}\mid\mathrm{scheduled})
\cdot
P(\mathrm{postprocessed}\mid\mathrm{generated})
\cdot
P(\mathrm{safe\ and\ deliverable}\mid\mathrm{postprocessed})
~~~

这里不是假设各事件相互独立，而是沿任务生命周期拆解条件成功率。每个条件概率都要说明分母和样本范围；例如输入审核拒绝的任务不会进入 scheduled，不能把它们混入 GPU 运行失败率。若某一阶段没有可评估样本，应报告未定义而不是记成 0。这个分解能把“成功率低”拆成输入失败、GPU 资源不足、模型崩溃、编码失败或审核拒绝。审核拒绝不是基础设施失败，也不应通过无限重试掩盖。

### 9.13.4 安全指标

安全评估至少包括：

- 输入拒绝率。
- 输出违规漏检率和误报率。
- 真实人物风险拦截。
- 未授权参考素材命中。
- 水印和 provenance 生成率。
- 删除后的可访问残留。
- 举报处理时延。
- 人工复核一致性。

## 9.14 高可用与故障恢复

### 9.14.1 队列积压

队列积压时可以：

- 限制低优先级新任务。
- 提供更低规格草稿。
- 扩容 warm pool。
- 估算并更新 ETA。
- 保留企业 SLA 资源。
- 让用户选择异步通知而非长轮询。

不应通过无限提高并发把 GPU、对象存储和审核服务一起压垮。

### 9.14.2 Worker 崩溃

worker 心跳超时后，任务进入 retryable_failed 或 recovery_pending。调度器先清理租约和临时对象，再根据 attempt_id 判断是否能够重跑。若模型已经上传了部分结果，资产层必须保持不可见，避免半成品被当成成功。

### 9.14.3 审核服务故障

输出审核不可用时，结果可以进入 pending_review，不能直接公开。低风险内部草稿是否允许用户本人预览，要有单独策略和审计。

### 9.14.4 元数据写入失败

视频上传成功但 task 状态写入失败时，不能重复生成。后台可以通过对象 digest、task_id 和上传 manifest 对账，补写元数据；无法确认归属的孤儿对象进入隔离回收队列。

### 9.14.5 模型版本回滚

回滚模型需要同时考虑队列中待执行任务和已经生成的资产。新旧 worker 不能对同一任务使用不兼容的参数；任务记录的 model_profile 和权重 digest 决定恢复路径。

## 9.15 计费、配额与预算

### 9.15.1 工作量计费

可以建立一个教学化工作量：

~~~math
U_{\mathrm{job}}
=
a \cdot F
\cdot R_{\mathrm{spatial}}
\cdot S_{\mathrm{denoise}}
\cdot q_{\mathrm{model}}
+
b \cdot T_{\mathrm{post}}
+
c \cdot S_{\mathrm{storage}}
~~~

a、b、c 是根据 GPU、后处理和存储成本校准的系数，q_model 表示模型 profile 的相对成本。它不是精确账单公式，但能让用户理解时长、分辨率、采样步数和质量 profile 为什么影响额度。

### 9.15.2 额度冻结

任务创建时可以冻结预计额度，任务失败、审核拒绝、取消和成功分别按策略结算。冻结与实际计费必须可审计，避免客户端重复提交造成双重扣费。

### 9.15.3 异常成本告警

如果某租户连续提交超长、高分辨率、多候选任务，系统应触发预算和风控，而不是等月底才发现 GPU 成本异常。额度控制和内容安全是两条不同的策略，不能用一种替代另一种。

## 9.16 完整案例：产品演示短片

### 9.16.1 用户请求

营销团队上传一张已授权的产品图并提交：

> 生成一个 6 秒、16:9 的产品演示短片。产品从桌面缓慢旋转，背景保持简洁，不要出现人物和额外文字。

任务服务保存原始 prompt、参考图 digest、项目授权和标准 profile。系统把“不要出现人物和额外文字”变成输出审核和质量检查条件，而不是只交给模型理解。

### 9.16.2 输入检查和排队

参考图扫描通过，项目成员关系有效。路由器选择 image_motion profile，估算帧数、分辨率、采样步数和预计额度。任务进入企业预览队列，等待 warm worker。

用户看到：

~~~text
已接收 -> 输入已审核 -> 等待 GPU -> 生成中 -> 输出检查 -> 可预览
~~~

取消在等待 GPU 时不产生生成 GPU 成本；如果进入 denoising 后取消，系统记录已经消耗的 GPU 时间并按规则结算。

### 9.16.3 生成和后处理

worker 加载模型和产品图条件，生成 raw_video。阶段进度记录采样步数和 worker attempt_id。编码器生成播放版本、封面和低清预览；质量检查验证时长、分辨率、帧数和黑帧。

输出审核抽取关键帧并分析整段运动，发现某一帧出现了额外文字。资产进入 needs_review，不能直接发送到广告素材库。团队可以选择重新生成、修改 prompt 或由人工复核。

### 9.16.4 来源和交付

审核通过后，系统写入 provenance manifest，标记输入产品图、模型 profile、生成时间和后处理版本；视频加入可见生成标识和项目权限。用户可以下载、收藏或创建新任务，不同版本拥有独立 asset_id。

### 9.16.5 删除

项目结束后，管理员删除素材。系统失效视频、封面、CDN URL、任务引用和搜索索引；审计记录保留最小化的 task_id、操作者和时间。若参考图授权到期，相关输出也进入待复核或不可见状态。

## 9.17 三个故障复盘

### 9.17.1 把 GPU 可用当成任务可运行

调度器看到 GPU 有空闲显存，就把高分辨率长视频放上去；运行中激活和 VAE 解码超出显存，worker 崩溃，队列不断重试。

根因是只按模型权重估算资源，没有把帧数、分辨率、条件和中间激活纳入 profile。修复方式是按规格做显存基准、限制参数组合、预留安全余量，并把失败重试设置为有限且可解释。

### 9.17.2 进度百分比停在 99%

采样已经结束，但转码、上传和审核没有纳入进度模型，用户看到 99% 长时间不动。

修复方式是把任务拆成阶段，记录每阶段历史耗时，给出区间 ETA，并明确“生成完成，正在检查与上传”。进度显示是状态可视化，不应伪造单一精确百分比。

### 9.17.3 输入通过但输出违规

参考图和 prompt 都通过审核，模型在中间帧生成了不允许的真实人物变体，系统只检查首帧，最终把视频发布。

修复方式是抽取全时序关键帧，按风险提高采样密度，结合视频级分类和人脸策略；输出未审核完成前保持不可见。输入安全和输出安全是不同阶段，不能互相替代。

## 9.18 发布和变更

### 9.18.1 分阶段发布

镜河可以按以下顺序扩大能力：

1. 只支持固定 profile 和内部测试素材。
2. 生成低清草稿，人工检查时序和安全。
3. 开放少量租户的标准短视频。
4. 加入高清、图生视频和多候选。
5. 接入企业审批、来源声明和批量任务。
6. 根据回归集、成本和举报结果扩大范围。

### 9.18.2 变更版本

以下变化都要进入任务配置和回滚记录：

- 模型权重和文本编码器。
- VAE、采样器和步数。
- 分辨率、帧率和时长 profile。
- prompt 规范化和安全规则。
- 抽帧、时序审核和水印策略。
- 编码器、CDN 和存储生命周期。
- 计费系数和队列优先级。

只回滚模型而不回滚输出审核器，可能让同一输入在不同时间得到无法比较的安全结论。

### 9.18.3 生产观测

按模型、profile、分辨率、租户、输入类型和审核状态分桶观察成功率、GPU 秒、时延、重生成率和举报。新版本先 shadow 或小流量运行，确认没有出现输出质量、安全和成本的组合回归。

## 9.20 读者练习：从长耗时任务推回系统边界

### 练习一：取消和计费

一个任务已经运行 45 秒，用户点击取消。worker 停止前又上传了一个临时视频。请设计状态、额度和临时对象的处理。

任务应进入 cancel_requested，确认 worker 停止后进入 cancelled；临时视频保持不可见并按生命周期清理；额度按已消耗 GPU 时间和产品规则结算，不能把“取消成功”直接等同于“零成本”。

### 练习二：两个版本的模型

同一个 task 在新模型发布前排队，发布后开始执行。如何避免任务无记录地使用新模型？

创建任务时保存 model_profile、模型权重 digest、采样器和安全策略版本。调度器根据快照选择兼容 worker；如果策略要求只使用当前版本，就暂停并重新确认，而不是静默切换。

### 练习三：时序安全

一个输出视频抽取首帧通过安全审核，但中间某一秒出现了不允许内容。如何改进审核和评估？

按风险动态增加抽帧密度，结合视频级分类和时序窗口；对人脸、裸露和文字等短暂事件采用更细粒度扫描；输出在所有必要检查完成前保持不可见，并把漏检加入回归集。

### 练习四：质量与成本

质量 profile 的 GPU 成本是草稿的四倍，但用户最终选择率只提高 5%。如何判断是否保留？

比较单位成功资产成本、用户选择率、等待时间、重生成率和质量分桶，而不是只看单任务成本。也可以用草稿预览筛选后再对少数候选使用高质量 profile，验证级联策略的整体收益。

## 9.21 结语：把视频生成当成资产系统

视频生成的技术难点来自时空计算，产品难点来自长等待和质量不确定，平台难点来自 GPU、对象存储、审核、版权和来源治理。把它当成一次模型调用，会遗漏最昂贵、最危险和最难恢复的部分。

可承担业务责任的视频平台至少应做到：

- 任务、资产、输入和派生结果有独立对象、版本和血缘。
- 时长、帧率、分辨率、采样步数和模型 profile 进入 GPU 与成本账本。
- 队列有优先级、老化、公平和租户配额，避免资源被单一用户占满。
- worker 有租约、心跳、取消、重试和临时对象清理。
- 生成、转码、上传、审核和来源声明完成后，资产才对用户可见。
- 输入和输出都做内容、身份、版权和安全检查。
- C2PA、水印和 provenance 支持来源说明，但不代替授权和审核。
- 进度和 ETA 表达不确定性，用户能知道排队、生成、审核和失败原因。
- 评估同时观察提示遵循、时序一致性、安全漏检、成本和单位成功资产。
- 删除、回滚和模型变更能够沿数据血缘传播。

当视频生成从“GPU 上跑完一个模型”变成“可追踪、可审核、可取消、可交付的资产生命周期”，长耗时和高成本才有机会被包装成真正可运营的产品。
