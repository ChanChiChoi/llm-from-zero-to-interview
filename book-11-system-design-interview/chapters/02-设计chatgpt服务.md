# 第二章：设计 ChatGPT 服务：从一条消息到可恢复的响应

ChatGPT 类服务表面上是一个聊天页面，底层却是一条持续运行的交互系统。用户发送一句话之后，系统要确认身份，恢复会话状态，决定哪些历史仍然有用，检查输入风险，选择模型，安排 GPU 推理，增量传输输出，处理断线和取消，保存最终结果，并把这次交互变成可以评估和改进的证据。

如果只画出“客户端 -> 后端 -> 模型 API”，真正困难的部分都没有被回答。一个完整的设计必须说明：同一条消息为什么可能有多个回答分支；客户端断线后怎样避免重复生成或重复扣费；用户点击停止时工具调用是否已经产生副作用；模型版本变化后旧会话如何复现；流式输出已经发出一半时安全策略如何生效；以及服务返回成功但用户任务失败时，系统如何知道自己做错了。

本章以一个面向个人和企业用户的文本聊天服务“白鹭”为贯穿案例。第一版只做多轮文本对话、流式生成、历史管理、重新生成、反馈和基础安全；联网搜索、文件问答、语音和工具调用会在架构上留下接口，但不假设它们已经实现。这样既能讲清 ChatGPT 服务自身的核心问题，也能看出以后扩展 Agent 或多模态能力时会增加什么代价。

## 2.0 先区分三种 ChatGPT 类产品

“设计 ChatGPT 服务”不是一个唯一问题。产品形态不同，责任边界也不同。

### 2.0.1 面向个人用户的聊天产品

个人产品关注多轮体验、首 token 延迟、会话历史、重新生成、内容安全、滥用防护和单位请求成本。用户可能同时打开多个设备，可能删除会话，也可能要求导出数据。服务要处理大量短请求和少量超长对话的混合流量。

### 2.0.2 面向开发者的模型 API

API 产品更强调 API key、租户隔离、计费、配额、幂等、版本兼容、错误码和 SLA。调用方可能使用自己的重试逻辑，因此服务端必须清楚说明流式事件、超时和部分响应的语义。一个人类聊天界面可以把失败显示为“请重试”，开发者 API 则需要让程序知道是否可以安全重试。

### 2.0.3 企业内部助手

企业产品需要额外处理数据驻留、组织权限、审计、管理员策略、知识库和合同约束。会话内容可能属于公司，而不是单个员工；员工离职、部门变更和文档删除会影响已有记忆和缓存。

本章先设计共同的在线核心，再在相关位置说明这三种形态的不同。不要把个人产品的“方便记住用户偏好”直接复制给企业产品，也不要把开发者 API 的错误语义简化成页面上的一句提示。

## 2.1 先写服务契约，而不是先画页面

白鹭第一版的服务契约如下：

| 项目 | 第一版约束 |
| --- | --- |
| 用户 | 已认证的个人用户或企业租户成员 |
| 核心动作 | 创建会话、发送消息、流式接收、停止、重新生成、删除、反馈 |
| 输出 | 文本增量、完成状态、用量和响应标识 |
| 会话 | 支持多轮消息和回答分支 |
| 模型 | 至少一个主模型和一个降级模型 |
| 数据 | 对话可查询、可删除、可导出；日志分层保存 |
| 安全 | 输入、上下文、输出和滥用行为都有控制 |
| 版本 | 模型、prompt、策略和 tokenizer 可追踪 |
| 不做的事 | 第一版不让模型直接执行不可逆业务动作 |

这个契约不是产品说明书的全部，而是系统设计的边界。它提前回答了几个容易被遗漏的问题：

- “重新生成”会不会覆盖原答案？
- “删除会话”是否包括缓存、日志和异步样本？
- 流式输出已经发送的部分，最终失败时如何标记？
- 用户停止生成后，已消耗的 token 如何记账？
- 同一个会话是否允许多个设备并发写入？
- 企业管理员能否读取成员会话，还是只有用户本人可见？

### 给初学者：聊天服务像一个有收据的对话柜台

可以把聊天服务想成一个柜台。用户交来一张问题单，柜台先确认是谁、这张单属于哪个会话，然后给问题单编号。专家开始回答时，柜台把回答一小段一小段递给用户；回答结束时，柜台再盖上“完成”或“失败”的章。

如果用户中途离开，柜台要知道这张单是否应该停止。如果用户再次提交同一张单，柜台不能无缘无故产生两份收费结果。每个步骤都有编号和状态，系统才不会把“已经递出的半句话”与“完整保存的答案”混为一谈。

### 给专家：把响应视为有状态的业务对象

响应不是一个字符串，而是一个有生命周期的对象。它至少经历 created、queued、generating、completed、failed 或 canceled 等状态。消息正文、增量事件、计费记录、审核结果和模型元数据应通过 response_id 关联，而不是由客户端自行拼接后再猜测最终状态。

状态对象还要包含版本和因果关系：它由哪个 user message 产生，继承哪一条 conversation branch，使用哪个模型和 prompt，是否触发了重试，以及最后一次有效事件的序号是多少。

## 2.2 用户看到的体验其实是协议

聊天产品的用户体验由几个可感知阶段组成：

1. 点击发送后，请求是否立即被接受。
2. 多久看到第一个可读字符。
3. 后续文本是否稳定到达。
4. 停止按钮是否真的停止。
5. 刷新或断线后，内容是否重复或丢失。
6. 最终答案是否能在历史中找到。
7. 失败时，用户是否知道哪些内容已经完成。

这几个阶段对应不同的系统指标和协议状态。TTFT 只描述首 token，不描述请求是否被接受；流式吞吐只描述生成速度，不描述网络缓冲；完整响应时间也不能说明答案已经持久化。

白鹭可以把一次响应的用户可见状态设计成：

~~~text
accepted
  -> waiting
  -> streaming
  -> completed
       \-> saved
  -> canceled
  -> failed
~~~

saved 不是 completed 的同义词。模型已经完成生成，但数据库写入失败时，用户可能看到了答案，却在刷新后找不到它。系统应决定这是“响应完成但保存失败”，还是把保存视为完成契约的一部分。

### 2.2.1 指标的分解

响应时间可以近似写成：

~~~math
T_{\mathrm{response}}
=
T_{\mathrm{admission}}
+
T_{\mathrm{queue}}
+
T_{\mathrm{context}}
+
T_{\mathrm{prefill}}
+
T_{\mathrm{first\_decode}}
+
T_{\mathrm{remaining\_decode}}
+
T_{\mathrm{persist}}
~~~

其中：

- T_admission 是鉴权、配额、输入校验和安全预检查。
- T_queue 是编排器和模型调度器的等待时间。
- T_context 是读取和裁剪历史的时间。
- T_prefill 是模型处理输入上下文的时间。
- T_first_decode 是生成第一个 token 的时间。
- T_remaining_decode 是剩余输出的解码时间。
- T_persist 是保存消息、用量和状态的时间。

TTFT 通常止于 first_decode，而用户刷新后能否看到答案还取决于 T_persist。将这两个时间混成一个“接口耗时”，会让故障定位变得困难。

### 2.2.2 质量也属于产品协议

一个回答可以在技术上 completed，但在业务上不成功。白鹭可以将成功拆为：

- 生成成功：模型按协议返回了文本。
- 交互成功：用户看到了完整且顺序正确的文本。
- 保存成功：会话历史可以恢复。
- 任务成功：回答满足用户要求。
- 安全成功：没有违反策略或泄露不应展示的信息。

产品指标应分别记录这些状态。否则模型只要吐出任意文本，系统就会把任务计为成功。

## 2.3 会话、消息和响应：为什么不能只存一张消息表

一个成熟的聊天服务至少要区分用户、会话、消息、响应、分支和反馈。

### 2.3.1 User 与 Tenant

个人产品中的 user_id 可以是主要隔离键；企业产品还需要 tenant_id、组织角色和数据区域。所有读取和写入都应该从服务端身份上下文得到这些字段，不能接受模型或客户端传来的任意 tenant_id。

用户资料和会话内容也不一定拥有相同的可见性。计费管理员可能能看用量，不能看正文；安全审计人员可能在受控流程下查看高风险样本；普通成员只能看到自己的会话。

### 2.3.2 Conversation

Conversation 描述一段对话的容器，包含：

- conversation_id。
- owner 或访问控制信息。
- 标题和创建、更新时间。
- 当前活动分支。
- 默认模型和场景配置。
- 会话状态，例如 active、archived、deleted。
- 摘要版本和长期记忆引用。
- 数据保留和删除状态。

标题可以由用户设置，也可以由小模型生成。自动标题应被视为派生数据，不能因为标题生成失败而阻塞主回答。

### 2.3.3 User Message

一条用户消息应包含：

- message_id。
- conversation_id。
- parent_node_id。
- role。
- content 或内容引用。
- 客户端幂等键。
- 创建时间。
- 输入安全状态。
- token 计数和 tokenizer 版本。

parent_node_id 很重要。用户对同一个问题点击重新生成时，新的响应应挂在同一条 user message 上；用户从某个历史回答继续提问时，新消息则挂在该回答节点上。

### 2.3.4 Response 与候选答案

一次响应至少包含：

- response_id。
- message_id。
- model_version。
- prompt_version。
- decoding 参数。
- 状态和 finish_reason。
- 输入、输出和缓存 token。
- TTFT、TPOT、总耗时。
- 安全审核结果。
- trace_id。
- 最终正文或正文存储引用。

重新生成时，不要覆盖原有 assistant message。保留多个候选答案能让用户切换，也能保留真实的偏好信号。覆盖旧答案会破坏审计和评估，并让“用户为什么点踩”失去上下文。

### 2.3.5 用树而不是线性列表表达分支

一个会话可以表示为：

~~~text
user_1
  ├─ response_1a
  └─ response_1b
        |
      user_2
        |
      response_2a
~~~

当前界面可以只展示 active branch，但存储层应保留其他候选。分支结构带来额外问题：

- 删除一条分支是否删除其后代？
- 摘要是针对整棵树，还是针对当前分支？
- 重新生成的候选是否参与长期记忆？
- 用户从旧分支继续时，模型看到的是哪条路径？
- 反馈绑定到 response 还是绑定到 conversation？

把这些语义写清楚，比单纯选择关系型数据库还是文档数据库更重要。

### 2.3.6 状态转移和不变量

响应状态可以设计为：

~~~text
created -> queued -> generating -> completed
                         |          |
                         v          v
                      canceled    persist_failed
                         |
                         v
                      refunded_or_billed
~~~

实际项目中的状态名称可以不同，但应满足几个不变量：

1. completed、canceled 和 failed 互斥。
2. 一个 response_id 只能有一个最终状态。
3. 增量事件序号不能回退。
4. 已经确认执行的计费不能因为客户端重连而重复。
5. response 终态后不能再写入新的正文增量。
6. 删除请求不能让客户端继续读取已撤销的会话。

## 2.4 API 设计：把自然语言请求变成可重放命令

API 设计需要同时照顾浏览器、移动端、SDK 和内部服务。重点不是列出很多 URL，而是明确幂等、版本、错误和流式语义。

### 2.4.1 创建会话

示意接口：

~~~text
POST /v1/conversations
Idempotency-Key: client-generated-key
~~~

请求可以包含标题、场景和默认模型。响应返回 conversation_id、权限摘要和当前配置版本。

创建会话通常可以幂等。如果客户端因网络超时再次提交同一 Idempotency-Key，服务端应返回第一次创建的 conversation_id，而不是产生两个空会话。

### 2.4.2 创建响应

示意接口：

~~~text
POST /v1/conversations/{conversation_id}/responses
Idempotency-Key: client-message-key
Accept: text/event-stream
~~~

请求结构可以包含：

~~~json
{
  "input": [
    {
      "role": "user",
      "content": "请解释这个概念"
    }
  ],
  "stream": true,
  "model": "auto",
  "max_output_tokens": 1200,
  "client_message_id": "msg-client-123"
}
~~~

这里的字段是教学设计，不是某个厂商 API 的承诺。服务端应根据账户、模型能力和安全策略重新校验 model、max_output_tokens 以及输入大小，不能原样信任客户端。

### 2.4.3 停止与取消

示意接口：

~~~text
POST /v1/responses/{response_id}/cancel
~~~

取消请求有三个可能结果：

- canceled：推理和流式传输都已停止。
- cancel_pending：系统已收到请求，但底层 GPU 仍在安全停止。
- too_late：副作用或最终写入已经发生，无法撤回。

对纯文本生成，too_late 通常只意味着无法节省剩余计算；对未来的工具调用，too_late 可能意味着需要人工补偿。因此取消 API 不能只返回 HTTP 200。

### 2.4.4 反馈和删除

反馈接口应绑定 response_id，而不是只绑定 conversation_id。删除接口要返回异步删除任务或明确的删除完成状态，因为正文、缓存、异步事件和备份不一定在同一瞬间删除。

导出接口同样需要定义数据范围：是否包含失败响应、被删除分支、反馈、用量和安全记录。数据访问权限不能由前端决定。

### 2.4.5 错误分类

错误至少分为：

| 类型 | 例子 | 客户端动作 |
| --- | --- | --- |
| 输入错误 | token 超限、格式错误 | 修改请求后重试 |
| 鉴权错误 | key 过期、无权限 | 更新凭证或停止 |
| 配额错误 | 余额、并发或频率超限 | 等待、升级或减少请求 |
| 暂时故障 | 模型池、网络或依赖超时 | 仅在幂等时重试 |
| 安全拒绝 | 请求或输出触发策略 | 不自动重试同一输入 |
| 终止状态 | canceled、length、content_filter | 展示部分结果和原因 |
| 持久化故障 | 生成成功但保存失败 | 允许受控恢复或重新保存 |

错误码应该让 SDK 能做正确动作。把所有失败都返回“请重试”，会让客户端在安全拒绝和服务过载时不断制造新负载。

## 2.5 请求生命周期：每一步都要有责任人

下面沿着用户发送一条消息的过程走一遍。这个过程把 API、会话、推理和数据闭环串起来。

### 2.5.1 接入和认证

网关验证 access token 或 API key，解析用户、租户、套餐、区域和权限。它还校验 Content-Length、输入结构、最大消息大小和流式协议。

网关生成 request_id、response_id 和 trace_id。request_id 代表一次入口请求，response_id 代表一个可计费的响应对象，trace_id 贯穿内部服务。三者不应混为一个字段。

### 2.5.2 幂等与会话并发

服务端根据 conversation_id 和 client_message_id 判断消息是否已经创建。若客户端因网络超时再次提交同一个幂等键，返回原 response_id 和当前状态。

同一个会话可以由多个设备并发写入。简单策略是使用版本号或 optimistic concurrency control：

~~~math
write\_allowed
\iff
version_{\mathrm{client}}
=
version_{\mathrm{server}}
~~~

版本不一致时，服务端返回冲突，让客户端重新读取会话，而不是静默覆盖另一台设备刚写入的消息。

### 2.5.3 输入安全和配额

在进入模型前，系统检查滥用风险、敏感输入、频率和 token 预算。输入审核可以产生风险标签，不一定立即拒绝；不同风险等级决定是否允许普通模型、是否需要更强模型、是否禁止流式或要求人工处理。

配额应同时考虑请求数、输入 token、输出 token、并发连接数和每日预算。只按请求数限流会让一个超长请求绕过真实资源限制。

### 2.5.4 读取和裁剪上下文

会话服务读取当前分支、最近消息、摘要和必要的记忆。Context Manager 计算 token 长度，并在预算不足时按优先级裁剪。

裁剪顺序不能只按时间。系统 prompt、当前用户问题和安全策略通常不能被随意删除；旧闲聊可以摘要或丢弃；带有明确来源的业务事实可以保留引用；过期或权限变化的记忆应先失效。

### 2.5.5 路由和模型准备

Model Router 根据用户套餐、任务类型、输入长度、延迟预算、质量要求、成本、模型健康和灰度配置选择模型。路由决策要写入 response 元数据，否则之后无法解释为什么同一个问题走了不同模型。

如果模型实例尚未 warm，系统要在准入阶段决定是等待加载、路由到其他副本，还是返回异步受理。把模型加载时间藏在普通请求的超时里，会造成严重尾延迟。

### 2.5.6 推理与事件

推理服务接收结构化 prompt，进入 prefill 和 decode。每个增量事件包含 response_id、序号、增量内容或控制状态。编排器不应根据“收到空字符串”猜测完成，必须使用明确的终止事件。

如果模型产生 finish_reason=length，服务端要告诉客户端回答被最大输出截断；如果是 safety 或 content_filter，则应区分安全策略终止和普通长度终止。

### 2.5.7 持久化和返回

事件可以先流给客户端，再异步保存；也可以在完成后同步保存再发送最终完成事件。两者的体验和一致性不同。

白鹭第一版可以采用：

1. user message 在接受请求时同步写入。
2. response 元数据立即创建。
3. 增量 token 通过流式通道发送，不逐 token 写主数据库。
4. 完成、取消或失败时保存最终正文、用量和状态。
5. 详细 trace 和反馈事件异步写入。

这样避免每个 token 都产生数据库写放大，同时保证用户消息不会因模型失败而丢失。

## 2.6 上下文管理：不是把历史全部复制给模型

对话上下文是 ChatGPT 服务区别于一次性生成 API 的核心。上下文管理同时影响质量、延迟、显存、成本和隐私。

### 2.6.1 上下文预算公式

设模型上下文窗口为 W，系统需要预留输出和安全余量，则可用输入预算近似为：

~~~math
B_{\mathrm{input}}
=
W
-
B_{\mathrm{output}}
-
B_{\mathrm{system}}
-
B_{\mathrm{tool}}
-
B_{\mathrm{margin}}
~~~

实际输入由多部分组成：

~~~math
B_{\mathrm{input}}
=
B_{\mathrm{current}}
+
B_{\mathrm{recent}}
+
B_{\mathrm{summary}}
+
B_{\mathrm{memory}}
+
B_{\mathrm{evidence}}
~~~

每个 B 都是 token 数，而不是字符数。不同 tokenizer、语言和代码内容的字符/token 比例不同，不能用固定字符截断代替实际计数。

### 2.6.2 三种历史策略

最简单的 recent window 只保留最近 N 轮。优点是便宜、可解释，缺点是会丢失早期约束。

摘要策略把早期历史压缩成状态摘要。摘要降低 token 成本，但可能丢失否定条件、时间范围和未解决事项；摘要本身也需要版本、来源和质量评估。

检索式记忆把历史消息切成可搜索单元，按当前问题召回。它能找回较早信息，但会引入召回错误、隐私范围和记忆污染。长期记忆不应自动等同于事实，用户应能查看、修改和删除。

生产系统通常混合使用三者：

- 保留少量最近原文，维护对话语气和当前指代。
- 用结构化摘要表示长期任务状态。
- 只在需要时检索历史记忆。
- 将高风险事实绑定到原始消息或外部来源。

### 2.6.3 摘要的输入和输出契约

摘要器不应只输出一段自由文本。更可控的摘要可以包含：

~~~json
{
  "goal": "用户正在准备季度预算说明",
  "facts": [
    "预算周期是 2026 年第二季度",
    "用户不希望修改原始数据"
  ],
  "decisions": [
    "先完成结构，再补充数字"
  ],
  "open_questions": [
    "是否需要加入部门对比"
  ],
  "source_message_ids": ["m-17", "m-21"],
  "summary_version": "sum-v4"
}
~~~

结构化字段让系统能检查来源、更新和删除，也减少摘要器把推测写成事实的机会。摘要仍然可能错，因此不能在高风险任务中把它当作唯一证据。

### 2.6.4 记忆的生命周期

一条长期记忆至少有：

- 创建来源和时间。
- 用户是否授权保存。
- 适用范围和租户。
- 置信或确认状态。
- 过期时间。
- 原始消息引用。
- 删除和更正记录。

用户说“我不喝咖啡”与系统从多次对话推测“用户喜欢某种饮料”不是同一种记忆。前者可能是明确偏好，后者是推测；系统不应以相同的权限和保留时间处理。

### 2.6.5 上下文污染

上下文污染不只来自攻击，也可能来自正常历史：

- 用户在旧消息中写了已经作废的要求。
- 模型前一轮犯错，下一轮把错误当作事实。
- 摘要把一个假设压缩成结论。
- 多设备同时编辑导致消息顺序混乱。
- 删除后的记忆仍命中缓存。
- 外部文档被拼成看似系统指令的文本。

Context Manager 应给不同内容加来源和信任标签，并在 prompt 结构上区分系统规则、用户内容、历史内容和外部数据。标签不是安全边界，但能帮助模型和后处理理解上下文来源。

## 2.7 Streaming：把一次响应拆成可恢复的事件序列

流式输出的关键不是“把字符串切小块”，而是定义事件顺序、重连、结束、错误和取消语义。

### 2.7.1 SSE 的适用边界

Server-Sent Events 使用 HTTP 长连接和 text/event-stream，适合服务端向客户端单向推送文本事件。WHATWG 规范定义了事件流格式和重连相关机制，客户端可以根据事件 ID 请求从某个位置继续。

SSE 对普通文本聊天很合适，因为主要方向是服务端发送 token；它的限制是交互语义以服务端推送为主，客户端到服务端的控制仍通常通过普通 HTTP 请求完成。

### 2.7.2 WebSocket 的适用边界

WebSocket 提供持久的双向通信，适合语音、实时协作、客户端频繁发送控制事件或多个方向的状态同步。RFC 6455 定义了 WebSocket 协议，但协议层并没有替你定义 token 序号、模型状态、计费和安全策略，这些仍要由应用层设计。

不要因为 WebSocket 更“实时”就默认它更适合文本聊天。连接管理、代理兼容、水平扩展和状态路由都可能更复杂。

### 2.7.3 事件模型

白鹭可以定义如下事件：

~~~text
event: response.created
data: {"response_id":"r-1","sequence":0}

event: response.output_text.delta
data: {"response_id":"r-1","sequence":1,"delta":"你好"}

event: response.output_text.delta
data: {"response_id":"r-1","sequence":2,"delta":"，"}

event: response.completed
data: {"response_id":"r-1","sequence":3,"usage":{"input_tokens":80,"output_tokens":24}}
~~~

这里的事件名称是本书的设计例子。每个事件至少要有 response_id 和单调递增 sequence。客户端可以丢弃重复 sequence，拒绝倒退事件，并在完成事件之后停止接收正文。

### 2.7.4 心跳和代理缓冲

长连接可能经过负载均衡器、反向代理和移动网络。若长时间没有可见 token，代理可能误判连接空闲。服务端可以发送心跳或注释事件，但心跳不应被客户端当作正文。

某些代理会缓冲小片段，导致服务端已经生成 token，客户端却迟迟看不到。部署时要验证代理的 buffering、flush、超时和最大连接时间，而不是只在本机 curl 测试。

### 2.7.5 顺序和持久化

token 增量的传输顺序不能被多线程异步发送打乱。推理服务、编排器和网关之间应有明确的序号归属。

持久化不必逐 token 写，但必须在最终状态中保存完整正文或可恢复的片段。若流中途断开，服务端应记录已生成 token 数和终止原因，用户刷新时可以看到“部分回答已保存”还是“本次回答未完成”。

## 2.8 取消、重连和重复请求

流式系统最容易出问题的地方，是用户操作和网络状态都可能变化。

### 2.8.1 用户点击停止

停止动作可能发生在四个阶段：

1. 请求还在网关排队。
2. 上下文正在读取。
3. 模型已经开始 decode。
4. 模型已完成但最终保存尚未结束。

每个阶段的取消成本不同。编排器应把 cancel_requested 写入 response 状态，并向下游传播 deadline 或取消信号。推理引擎若只能在下一个调度轮次停止，服务端也要及时停止向客户端发送。

### 2.8.2 断线不等于取消

浏览器断线可能只是网络切换，用户仍希望恢复；也可能是用户关闭页面，不再需要计算。默认把断线视为取消会损害移动端体验；默认继续生成又会浪费资源。

可选策略：

- 短暂保留任务，允许客户端通过 response_id 重连。
- 超过 grace period 后自动取消。
- 对付费或长任务提供显式后台继续选项。
- 对高成本请求按用户套餐设置保留时间。

### 2.8.3 重连与 Last-Event-ID

如果客户端保存了最后收到的 sequence，重连时可以携带 last_event_id 或自定义 cursor。服务端从事件日志或 response 缓冲中补发缺失事件。

这要求服务端暂存增量事件一段时间。若只保留最终全文而没有序列化增量，就不能精确恢复中间事件；可以退化为发送当前完整文本快照，但客户端必须知道这是 snapshot，而不是新的增量。

### 2.8.4 重复提交和重复计费

客户端发送消息后超时，无法知道服务端是否已经接受。它再次发送时，服务端必须用 client_message_id 或 Idempotency-Key 去重。

计费记录应绑定 response_id 和一次最终用量结算。重连可以重复读取事件，不能重复创建计费。若一次响应因服务端故障产生了两个实际推理任务，需要通过父请求和幂等记录决定如何计费与补偿。

### 2.8.5 重新生成与取消的竞态

用户可能先点击重新生成，随后又点击停止。系统需要给每个 response 独立状态，不能用 conversation 的一个布尔值表示“正在生成”。

安全的状态更新可以采用条件写入：

~~~math
update\_response
\text{ only if }
state\in\{created,queued,generating\}
~~~

已经 completed 的旧响应不能被新的取消请求改写；新生成的 response 也不能复用旧 response 的序号。

## 2.9 模型路由和推理服务

ChatGPT 服务通常不会永远只有一个模型。路由系统把产品策略翻译成资源选择。

### 2.9.1 路由输入

路由器可以观察：

- 用户套餐和租户策略。
- 任务分类，例如闲聊、写作、代码、总结。
- 输入 token 长度和预计输出长度。
- 是否需要结构化输出或多语言。
- 延迟和成本预算。
- 模型当前健康、队列长度和区域。
- 灰度实验分组。
- 安全策略和数据驻留要求。

路由器不应依赖模型自己说“我是复杂问题”。任务分类可以使用规则、小模型或产品入口，但最终决策要可记录。

### 2.9.2 路由目标

一个简化的路由目标可以写为：

~~~math
m^\*
=
\arg\max_{m\in\mathcal{M}}
\left[
Q(m,x)
-
\alpha C(m,x)
-
\beta T(m,x)
-
\gamma R(m,x)
\right]
~~~

Q 是任务质量效用，C 是成本，T 是延迟，R 是风险。α、β、γ 由业务决定。这个公式表达取舍，不要求系统每次都精确估计所有项。

模型选择还要考虑容量。如果一个模型质量最高但队列已经很长，等待它可能降低任务成功率；路由到满足质量底线的健康模型，可能使整体体验更好。

### 2.9.3 Inference Service 的内部阶段

推理服务可以分为：

1. 请求准入和 token 计数。
2. 排队和优先级调度。
3. prefill。
4. decode。
5. 流式事件封装。
6. 停止条件和取消处理。
7. usage 统计。
8. 实例健康与资源回收。

长短请求混部会带来队列和 KV Cache 冲突。可以按输入长度、优先级、是否流式和预计输出长度建立队列，也可以使用连续批处理动态加入和退出。

### 2.9.4 模型版本和会话一致性

模型升级后，同一个会话继续聊天可能出现风格、事实和工具协议变化。产品可以选择：

- 新请求默认使用最新模型。
- 允许用户固定会话模型。
- 对高价值会话保存完整 model_version 和 prompt_version。
- 重大升级时自动生成新会话或提示用户。
- 旧模型只保留有限时间用于回放和重试。

没有版本记录，用户说“昨天它还记得，今天怎么变了”时，工程团队只能猜。

### 2.9.5 Prefix cache 与上下文复用

很多请求共享相同的 system prompt、工具描述或会话前缀。Prefix cache 可以减少重复 prefill，但缓存键必须绑定模型、tokenizer、prompt 版本、权限范围和实际前缀内容。

会话分支中的共享前缀可以复用；用户私有历史不能跨用户复用。缓存命中不应绕过最新安全策略或会话删除。

## 2.10 安全：输入、上下文、输出和滥用是四个问题

聊天安全不是一个“审核模型”就能解决的问题。四类风险的信任边界不同。

### 2.10.1 输入风险

输入可能包含危险请求、个人信息、攻击载荷、垃圾内容或试图绕过系统规则的提示。输入审核可以把请求分成低风险、中风险、高风险和不确定，但分类结果只是策略输入。

输入审核失败或不可用时，系统要按风险选择：普通低风险可以延迟处理；高风险请求应保守拒绝；不能为了保持可用性而默认放行。

### 2.10.2 上下文和提示注入

历史消息、用户上传的文本和未来的检索结果都可能包含“请忽略之前规则”之类的内容。模型能看懂这些文字，不代表它们获得了系统级权限。

上下文组装时应区分：

- 系统策略。
- 开发者或产品指令。
- 用户内容。
- 历史模型输出。
- 外部不可信内容。

外部内容应带来源标签，并限制其能影响的动作。对于第一版纯文本白鹭，最简单的边界是：模型只生成文本，不执行外部工具。未来增加工具时，必须把模型候选调用送到独立授权器。

### 2.10.3 输出风险

输出审核既要检查有害内容，也要检查隐私、事实和高风险建议。对流式响应来说，审核有两个时点：

- 增量审核：尽早发现明显风险，但上下文不完整，容易误判。
- 完整审核：上下文完整，判断更好，但风险文本可能已展示。

风险越高，越应增加缓冲或限制流式展示。医疗、金融、法律、未成年人和企业机密等场景不能直接照搬普通闲聊策略。

### 2.10.4 PII 和数据泄露

PII 检测可以识别身份证号、电话、邮箱、地址等模式，但规则和模型都可能漏报或误报。日志、反馈、训练候选和客服排障工具应采用不同的脱敏策略。

输出中的个人信息不一定都是违规的。用户要求查看自己的手机号，与系统把另一个人的手机号拼进回答，风险不同。安全策略要结合身份、数据来源和任务，而不是看到任何数字就全部替换。

### 2.10.5 滥用防护

滥用包括批量爬取、账号共享、自动化攻击、资源消耗、提示注入探测和高风险内容反复尝试。防护信号可以包括频率、token 量、失败比例、相似请求、账号关系和 IP/设备行为。

风控不应只依赖单一黑名单。误伤正常用户会造成体验和合规问题，封禁理由也应可审计。对企业租户可以提供管理员可见的配额和风险事件，但不要把所有员工的正文默认暴露给管理员。

### 2.10.6 安全资料的边界

OWASP 的 LLM 应用风险资料可以帮助建立威胁词汇和检查面，但它不是某个产品已经安全的证明。安全策略仍需要在自己的模型、用户、数据、工具和损失模型上验证。

## 2.11 数据存储和删除

聊天系统保存的并不只有一张 messages 表。不同对象需要不同存储和生命周期。

### 2.11.1 事务数据

用户、租户、会话、消息元数据、响应状态、反馈和用量适合放在有事务语义的数据库中。核心访问模式包括：

- 查询用户可见的会话列表。
- 按 conversation_id 分页读取当前分支。
- 按 response_id 查询状态和用量。
- 条件更新响应状态。
- 记录幂等键和最终结果。

正文可以存储在数据库或对象存储，元数据保存内容哈希、长度、版本和访问控制。

### 2.11.2 缓存

缓存可以保存会话摘要、最近消息、模型前缀和短期流事件，但必须有过期、失效和权限语义。缓存命中不能绕过会话删除和策略更新。

一个安全缓存键可以抽象为：

~~~math
K
=
hash(
tenant\_id,
user\_scope,
conversation\_branch,
model\_version,
prompt\_version,
policy\_version,
input\_hash
)
~~~

缓存键越具体，命中率可能越低；越宽松，数据串租户和旧答案风险越高。应以安全语义为先，再通过分层缓存优化命中率。

### 2.11.3 日志和 trace

在线指标可以只保存 token 数、耗时、错误类别和版本；排障需要的正文应单独存储、脱敏和授权。高风险样本需要严格审计。

日志还应记录删除状态。一个会话被用户删除后，异步事件可能仍在队列中，评估样本可能已复制到离线存储，备份可能暂未过期。删除任务要有数据血缘清单和完成证明。

### 2.11.4 软删除和硬删除

软删除方便恢复和审计，但会让用户以为数据已消失而实际仍被内部读取。硬删除更符合数据最小化，但需要处理备份、索引和灾备。

产品应该明确承诺的是“用户界面不可见”“在线服务不再使用”还是“所有副本在某期限内删除”。不同承诺对应不同实现和成本，不能用一个 deleted=true 覆盖所有语义。

### 2.11.5 数据不直接进入训练

生产日志可能包含隐私、错误、攻击载荷、版权内容和模型输出。进入训练或评估池前至少需要：

1. 访问授权和用途确认。
2. 脱敏和实体替换。
3. 去重和污染检查。
4. 有害内容处理。
5. 质量筛选和人工抽样。
6. 训练集、评估集和反馈集隔离。
7. 删除请求的传播机制。

用户点赞只是一种反馈信号，不是自动训练许可。

## 2.12 反馈与评估：从聊天记录到可解释证据

上线后的改进依赖真实交互，但真实交互不是天然干净的标注集。

### 2.12.1 反馈信号的含义不唯一

- 点赞可能表示内容有用，也可能只是格式满意。
- 点踩可能来自事实错误、风格不合、延迟过高或用户目标改变。
- 重新生成表示第一版没有满足用户，但不一定说明第二版更好。
- 继续追问可能表示用户感兴趣，也可能表示答案没有回答问题。
- 复制可能表示答案有用，也可能只是复制后去修改。

因此反馈事件应关联 response、任务类型、延迟、模型版本和后续行为，不能把一个按钮直接当作训练标签。

### 2.12.2 一条反馈样本的结构

可以保存：

~~~json
{
  "response_id": "r-42",
  "feedback": "down",
  "reason": "not_answered",
  "user_text": "我需要的是具体步骤",
  "model_version": "model-v8",
  "prompt_version": "prompt-v3",
  "input_tokens": 312,
  "output_tokens": 488,
  "redaction_status": "reviewed",
  "label_status": "pending"
}
~~~

这里的 reason 由用户选择或后续标注得到，不能让模型自动生成并当作真值。人工复核可以把“没有回答”“事实错误”“不安全”“太长”等类别进一步拆分。

### 2.12.3 离线评估集

白鹭的离线评估集至少包括：

- 普通对话和多轮指代。
- 长历史和摘要边界。
- 不可回答问题。
- 语言切换和代码混合。
- 安全边界和提示注入。
- PII 和删除请求。
- 断线、取消和重试的协议测试。
- 不同模型版本的回归样本。

评估既要看文本质量，也要看协议：事件是否有序、取消是否生效、状态是否终态唯一、重连是否重复扣费。

### 2.12.4 任务成功率

对开放聊天，任务成功需要人工或 judge 结合上下文判断；对结构化任务，可以用程序判定器。一个简单的单位成功任务成本是：

~~~math
C_{\mathrm{task}}
=
\frac{
C_{\mathrm{inference}}
+
C_{\mathrm{storage}}
+
C_{\mathrm{safety}}
+
C_{\mathrm{review}}
}{
N_{\mathrm{successful\ tasks}}
}
~~~

当模型路由、小模型重试和人工接管改变时，这个指标比单独的每 token 价格更能反映真实经济性。

## 2.13 监控：把“回答不好”变成可定位问题

聊天系统的监控不能只看 HTTP 200。

### 2.13.1 入口和协议指标

包括：

- 请求率、并发连接数和租户分布。
- 输入校验失败率。
- 幂等命中率。
- 接受、排队、流式、完成、取消和失败数量。
- SSE/WebSocket 连接时长。
- 重连成功率和重复事件率。
- 客户端断开率。

如果 completed 数量下降但 HTTP 错误没有上升，可能是流式连接或持久化问题；如果 response.created 正常但 first_token 下降，可能是模型队列问题。

### 2.13.2 模型指标

包括：

- TTFT、TPOT、端到端时间。
- 输入、输出和缓存 token。
- 模型队列长度和年龄。
- prefill、decode 时间。
- KV Cache 占用。
- GPU 利用率、显存和实例健康。
- finish_reason 分布。
- 各模型版本的错误和质量。

TPOT 可以定义为生成阶段每个输出 token 的平均时间，但要说明是否排除首 token、是否包含网络发送，以及如何处理短输出。

### 2.13.3 质量和安全指标

质量指标包括任务成功率、反馈率、重新生成率、人工抽检、事实错误、上下文引用错误和多轮跟随。

安全指标包括输入违规率、输出违规率、拒答率、过度拒答、PII 命中、滥用事件和高风险请求的人工升级率。安全指标必须按任务和风险等级切片，否则低风险闲聊的大量样本会掩盖少量高风险事故。

### 2.13.4 成本指标

成本监控按模型、租户、功能、地区和任务类型聚合：

~~~math
C_{\mathrm{day}}
=
C_{\mathrm{GPU}}
+
C_{\mathrm{storage}}
+
C_{\mathrm{network}}
+
C_{\mathrm{moderation}}
+
C_{\mathrm{observability}}
~~~

模型路由和重试会改变 GPU 成本；日志保留和流式连接会改变存储与网络成本。成本告警应结合任务成功率，不能仅因 GPU 利用率升高就判断异常。

### 2.13.5 追踪字段和隐私

trace 可以包含 auth、conversation.load、context.build、safety.input、model.route、inference.prefill、inference.decode、safety.output 和 persist 等 span。内容正文不应默认放进所有 trace 属性。

用 model_version、prompt_version、policy_version、conversation_branch 和 cache_hit 作为结构化字段，可以解释行为；原始正文通过受控引用访问。

## 2.14 高可用和降级

ChatGPT 服务的高可用不仅是模型多副本，还包括状态、连接、数据和策略的可用。

### 2.14.1 模型池故障

如果主模型池故障，路由器可以：

- 切换到同能力的副本。
- 切换到小模型，但记录质量和降级状态。
- 对长上下文或高成本请求排队。
- 对低优先级批任务暂停。
- 对安全敏感请求保守失败。

降级模型不能假装成主模型返回。响应元数据应记录 fallback_reason，用户界面也可以在需要时说明答案来自降级路径。

### 2.14.2 会话数据库变慢

如果会话读取变慢，不能简单把空历史交给模型，因为模型可能误以为这是新会话。可以：

- 短暂从带版本的缓存读取。
- 返回“正在恢复会话”的明确错误。
- 对无历史的新会话继续服务。
- 限制新请求而不是让所有请求无限等待。

### 2.14.3 安全服务不可用

输入审核不可用时，高风险请求应停止或进入备用审核；低风险请求可以使用保守规则或延迟。输出审核不可用时，是否允许流式展示取决于风险等级。

安全服务故障不能通过“默认通过”解决。安全和体验的降级路径必须在发布前演练。

### 2.14.4 流式网关故障

如果模型已经生成但网关断开，response 状态仍应由服务端保存。客户端重连可以通过 response_id 查询最终状态或补发事件。

如果网关重试导致新的模型请求，幂等键必须阻止重复生成。否则一次网络故障会变成两次 GPU 消耗和两个不同答案。

### 2.14.5 过载保护

过载时要同时保护 GPU、数据库和连接池：

1. 按 token 和并发限流。
2. 限制最大输入和输出。
3. 长请求单独排队。
4. 低优先级用户进入较低优先级队列。
5. 暂停非必要标题、摘要和日志加工。
6. 对已经超出 deadline 的请求快速失败。
7. 控制客户端重试。

队列中的请求有年龄。一个已经等待十秒、只剩一秒 deadline 的请求，不应继续占用资源完成一个必然超时的全流程。

## 2.15 容量估算：从 DAU 到模型池

下面使用一个教学规模，不把结果当成部署结论：

- DAU 为 1,000,000。
- 每个用户每天 10 次响应请求。
- 每日入口请求为 10,000,000。
- 平均入口 QPS 为 115.7。
- 峰值系数为 10，入口峰值约 1,157 QPS。
- 每次请求平均输入 1,000 token，输出 500 token。
- 平均每个请求触发 1.2 次生成模型调用。

平均入口 QPS：

~~~math
Q_{\mathrm{avg}}
=
\frac{1000000\times10}{24\times3600}
\approx115.7
~~~

峰值入口 QPS：

~~~math
Q_{\mathrm{peak}}
=
10\times115.7
\approx1157
~~~

模型调用峰值：

~~~math
Q_{\mathrm{model}}
=
1157\times1.2
\approx1388.4
~~~

粗略 token 吞吐：

~~~math
R_{\mathrm{token}}
=
1388.4\times(1000+500)
\approx2.08\times10^6\ \mathrm{token/s}
~~~

这个数字只说明规模。真正的资源规划还需要：

- 峰值持续时间和输入输出分布。
- 小模型与大模型的流量比例。
- prefix cache 命中率。
- 重试和取消比例。
- 每个模型在真实 batch 下的 prefill/decode 基准。
- 长上下文请求的并发上限。
- 故障时保留多少容量。

### 2.15.1 并发连接

若平均响应停留时间为 4 秒：

~~~math
L_{\mathrm{model}}
=
Q_{\mathrm{model}}\times4
\approx5554
~~~

这表示模型层平均有约 5,554 个在途调用。它不等于 5,554 个同时生成的请求，部分可能在队列中；但它说明连接、状态、KV Cache 和取消处理都不能按几百个请求设计。

### 2.15.2 存储量

假设每个请求的消息、元数据和审核结果平均占 10KB，未计算副本：

~~~math
S_{\mathrm{day}}
=
10000000\times10\ \mathrm{KB}
\approx100\ \mathrm{GB/day}
~~~

如果保存完整 trace、增量事件、反馈和多副本，实际存储会更大。冷热分层和采样不是事后优化，而是从容量假设开始就应该存在的设计。

### 2.15.3 GPU 不能由 token/s 直接除出

每个模型要分别测量：

- 给定输入长度下的 prefill token/s。
- 给定 batch 和输出长度下的 decode token/s。
- TTFT 和 P95/P99。
- KV Cache 峰值。
- 模型加载和故障恢复时间。
- 长短请求混部时的尾延迟。

如果大模型承担 30% 流量、小模型承担 70% 流量，必须按模型池分别计算，而不是用一个平均 token/s 掩盖差异。容量还要加故障余量和扩容时间。

## 2.16 成本和计费：用户体验背后的账本

聊天产品的成本不只来自模型 token。它还包括审核、存储、网络、流式连接、日志、评估和客服。

### 2.16.1 请求成本

一个响应的粗略成本为：

~~~math
C_{\mathrm{response}}
=
C_{\mathrm{input\ tokens}}
+
C_{\mathrm{output\ tokens}}
+
C_{\mathrm{cache\ miss}}
+
C_{\mathrm{safety}}
+
C_{\mathrm{storage}}
+
C_{\mathrm{network}}
~~~

如果部署自有 GPU，模型成本可以按 GPU 秒、模型池占用和能耗分摊；如果调用外部 API，则按输入、输出、缓存和失败调用结算。两种模式都要记录内部 token 和 response_id。

### 2.16.2 取消如何计费

用户停止生成后，已经计算的输出 token 不能消失。计费策略可以是：

- 按实际产生的 input/output token 计费。
- 对用户取消的部分只收已产生用量。
- 对服务端错误进行补偿。
- 对客户端重复重连不重复计费。

关键是让 usage、状态和计费记录一致。不能因为客户端没有收到最后一个 usage 事件，就让用户或系统无法对账。

### 2.16.3 免费和付费用户的优先级

优先级可以影响排队、模型选择、最大长度和并发，但不能让低优先级用户绕过安全策略。优先级队列也要防止付费租户占满所有 GPU，导致系统完全没有故障缓冲。

### 2.16.4 成本优化的验证

每项优化都要同时看：

- TTFT 和尾延迟。
- 任务成功率。
- 重新生成率。
- 安全和拒答。
- 每成功任务成本。
- 对不同租户的公平性。

单纯提高 GPU 利用率可能增加用户等待；单纯降低模型价格可能增加重试和人工处理。

## 2.17 版本、灰度和回滚

聊天产品会频繁变化。模型权重只是版本的一部分。

### 2.17.1 需要一起版本化的对象

一次可复现的响应至少需要：

- 模型权重和 tokenizer。
- chat template。
- system prompt。
- 安全策略和审核模型。
- 上下文裁剪策略。
- 路由配置。
- 解码参数。
- 会话和记忆版本。
- 客户端协议版本。

只写 model_name 不足以解释结果。

### 2.17.2 灰度顺序

可以先在离线评估集比较，再做 shadow 或小流量灰度。灰度期间按用户或租户稳定分桶，避免同一个会话在不同版本之间来回跳。

主要观察：

- 质量和任务成功率。
- TTFT、P95/P99 和流式断连。
- 安全违规和过度拒答。
- 每成功任务成本。
- 数据库、缓存和 GPU 资源。
- 反馈和重新生成行为。

### 2.17.3 回滚不只回模型

如果新模型导致问题，回滚模型但保留新 prompt，问题可能仍在；如果只回滚 prompt，缓存中的新答案仍可能继续返回。回滚单元应包含模型、prompt、策略、路由和缓存失效。

已生成的错误回答不会因为回滚自动消失。系统需要标记受影响版本，重新评估相关样本，并在必要时通知用户。

## 2.18 完整案例：白鹭企业版的一次真实请求

假设白鹭企业版新增“根据内部对话历史帮助员工起草项目周报”，但第一版仍不允许自动发布周报。

用户请求：

> 根据这个会话里的项目进展，写一版本周周报，保留未解决问题，不要编造数字。

### 2.18.1 系统如何处理

1. 网关验证员工身份和租户。
2. 会话服务只读取该员工有权限访问的会话分支。
3. Context Manager 统计历史 token，保留最近讨论和已确认摘要。
4. 摘要器把事实、决定和未解决问题分开。
5. 模型路由到写作模型，但配置为不能调用工具。
6. 输入策略检查会话中是否包含其他员工的敏感信息。
7. 模型生成周报草稿，要求每个数字能够回指原始消息。
8. 输出策略检查是否出现没有来源的具体数字和不应展示的字段。
9. 响应流式返回，完成后保存草稿和来源 message_id。
10. 用户可以点赞、修改或重新生成，但系统不自动发布。

### 2.18.2 一个失败如何被解释

如果周报遗漏了早期承诺，可能有几种原因：

- 历史读取遗漏了分支。
- 摘要没有保留未解决事项。
- token budget 把关键消息裁掉。
- 模型没有遵守“不编造数字”。
- 输出校验没有发现无来源数字。

因为系统保存了 message_id、summary_version、token budget、model_version 和输出检查结果，团队可以沿链路定位，而不是笼统地说“模型能力不够”。

### 2.18.3 用户重新生成

重新生成会创建 response_2，仍然挂在同一 user message 下。response_1 保留其正文、模型版本和反馈；如果用户选择 response_2 继续写，后续 user message 的 parent_node_id 指向 response_2。

这种设计让产品拥有真正的分支，也让评估系统知道同一个输入下不同生成之间的偏好，而不是把历史覆盖成最后一份文本。

## 2.19 常见故障演练

### 2.19.1 网关在生成中断开

模型服务仍在生成，网关连接断开。编排器收到连接关闭事件，进入 grace period；如果客户端在短时间内重连，则从最后 sequence 补发；如果超过时间，发送 cancel，保存已生成片段和 canceled 状态。

如果网关盲目重试创建响应，就会产生两个 response_id。幂等键和原始 client_message_id 应阻止这种情况。

### 2.19.2 新模型上线后答案变长

输入输出 token 增长，TTFT 变化不大，但总延迟、成本和存储上升。只看用户点赞可能误判为质量提升。应比较输出长度、任务成功率、重新生成率和每成功任务成本，并检查 max_output_tokens 和 stop 条件是否变化。

### 2.19.3 安全审核服务超时

低风险闲聊可以使用保守规则并稍后补审；高风险请求不能直接放行；正在流式的中风险响应可以暂停发送，等待完整审核。所有选择都应记录策略版本和降级原因。

### 2.19.4 会话删除后仍命中摘要缓存

删除接口已经从主数据库删除，但 Context Manager 仍从缓存读取旧摘要。修复需要让删除事件传播到会话缓存、prefix cache、异步评估样本和搜索索引，并记录删除完成状态。只删数据库一行不等于系统忘记了会话。

## 2.20 取舍：产品承诺决定技术选择

### 2.20.1 低延迟还是更长上下文

保留更多历史可能减少用户重复解释，但会增加 prefill、KV Cache 和成本。可以提供“精简上下文”和“完整上下文”模式，也可以在历史很长时明确展示摘要而不是假装模型记住了一切。

### 2.20.2 及时流式还是先审核

普通闲聊适合流式，风险更高的内容适合缓冲后审核。不要用一个全局配置覆盖所有任务。

### 2.20.3 覆盖答案还是保留分支

覆盖更简单，存储少，但破坏审计和偏好数据；保留分支更完整，却需要树结构、界面选择和摘要策略。只要产品支持重新生成，保留分支通常更诚实。

### 2.20.4 同步保存还是异步保存

同步保存提高刷新后的确定性，但会增加尾延迟；异步保存降低主链路压力，但需要处理生成成功、保存失败和用户断线之间的差异。第一版可以同步写消息元数据、异步写详细正文和 trace，但必须向用户明确最终保存状态。

### 2.20.5 一个模型还是模型分层

单模型便于运维和评估；多模型可以优化质量、成本和延迟，但增加路由、版本、灰度和回归复杂度。模型分层只有在任务差异和资源成本足够明显时才值得。

## 2.21 复盘练习

### 练习一：流式断线

客户端收到 sequence=18 后断网，服务端在 sequence=19 到 24 之间完成生成。设计重连请求、事件保留、重复事件处理和最终状态查询。说明如果事件日志已经过期，如何退化为完整文本快照。

### 练习二：多设备并发

用户在手机和浏览器同时向同一会话发送消息。设计版本号、分支、排序和冲突提示，说明如何避免一个设备覆盖另一个设备的消息。

### 练习三：长对话摘要

总上下文窗口为 32K，要求预留 4K 输出、2K 系统规则和 1K 安全余量。当前历史、摘要和用户问题合计超过预算。请用公式说明裁剪顺序，并列出摘要错误的三种检测方式。

### 练习四：取消与计费

用户在生成 300 个 token 后点击停止，但服务端又生成了 40 个 token 才停止。设计 usage、状态、退款和客户端显示，避免重复计费或错误显示为完整成功。

### 练习五：模型升级

新模型让事实性提升，但输出长度增加 40%，P95 总耗时增加 25%。请设计灰度指标和回滚条件，不要只用点赞率做结论。

### 练习六：企业删除

员工删除会话后，系统仍有热缓存、摘要、异步日志、备份和评估样本。设计删除事件和可验证的完成状态，区分“用户不可见”和“所有副本已删除”。

2. OpenAI API Reference，Streaming。该官方入口用于核对产品 API 的流式主题，但本次自动化请求返回 403，因此本章不把页面中无法独立核验的字段写成确定事实。链接：[https://platform.openai.com/docs/api-reference/streaming](https://platform.openai.com/docs/api-reference/streaming)。
3. WHATWG，Server-sent events。规范定义事件流的媒体类型、事件字段和重连相关行为，是 SSE 协议事实的主要来源。链接：[https://html.spec.whatwg.org/multipage/server-sent-events.html](https://html.spec.whatwg.org/multipage/server-sent-events.html)。
4. IETF RFC 6455，The WebSocket Protocol。RFC 定义 WebSocket 协议本身；token 事件、状态、计费和安全仍属于应用层设计。链接：[https://www.rfc-editor.org/rfc/rfc6455](https://www.rfc-editor.org/rfc/rfc6455)。
5. OWASP，Top 10 for Large Language Model Applications。该资料提供 LLM 应用常见风险和安全词汇，不能替代针对具体模型、数据和工具的安全评估。链接：[https://owasp.org/www-project-top-10-for-large-language-model-applications/](https://owasp.org/www-project-top-10-for-large-language-model-applications/)。
6. OpenTelemetry，Observability primer。上一章已说明 traces、metrics、logs 的来源；本章将其扩展到 response、sequence、token 和版本字段。链接：[https://opentelemetry.io/docs/concepts/observability-primer/](https://opentelemetry.io/docs/concepts/observability-primer/)。
7. NIST，Artificial Intelligence Risk Management Framework。上一章已说明 Govern、Map、Measure、Manage 的治理边界；本章将其落到聊天数据、模型版本和安全事件。链接：[https://www.nist.gov/itl/ai-risk-management-framework](https://www.nist.gov/itl/ai-risk-management-framework)。

资料使用时要区分：

- 协议规范说明通信语义，不说明你的推理服务吞吐。
- 官方示例说明一种实现，不等于所有 SDK 的兼容保证。
- 风险清单帮助建立 threat model，不等于上线安全证明。
- 本章容量数字和状态机是教学设计，必须用实际流量、模型和合规要求校准。

## 2.23 本章小结

ChatGPT 服务不是一个把文本转发给模型的接口，而是一条有状态、可流式、可取消、可重连、可计费、可审计的交互系统。

会话层要用消息、响应和分支表达真实历史；API 层要定义幂等、错误和终态；上下文层要在 token 预算内组织最近消息、摘要和记忆；模型层要处理路由、版本、队列、prefill、decode、KV Cache 和长短请求隔离；流式层要定义事件序号、心跳、重连和取消；数据层要处理缓存、删除、导出和训练授权；安全层要覆盖输入、上下文、输出、PII 和滥用；评估和观测层要把协议成功、任务成功、质量、安全和成本分别记录。

真正成熟的设计，不是让模型永远回答，而是让用户知道响应处于什么状态，让系统知道每个 token 属于哪一次响应，让重试不会制造重复动作，让删除能传播到派生数据，让模型升级可以回放和回滚。后续章节会把其中的训练、推理、RAG、Agent 和评估子系统分别展开。
