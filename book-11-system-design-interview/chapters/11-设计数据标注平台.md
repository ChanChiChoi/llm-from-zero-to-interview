# 第十一章：设计数据标注平台：把原始样本变成可审计训练资产

数据标注平台不是一个让人打开网页、选择标签、点击提交的表单系统。对于大模型，标注对象可能是一段多轮对话、两个候选回答、一条带引用的 RAG 轨迹、一次工具调用，或者一段同时包含文字、图片和音频的交互。标注结果也不只是一个类别，它可能影响 SFT、偏好优化、安全策略、评估结论和后续数据采样。

因此，平台真正生产的是一种数据资产：它有来源、有用途、有标注规范、有质量证据、有版本、有权限边界，能够在模型出现问题时被追溯，也能够在数据被删除或修订时沿着血缘传播。

本章贯穿衡川客服助手的数据工作台。衡川的线上系统会产生脱敏后的客服对话、检索片段、工具轨迹和用户反馈。数据团队要从中构造三类数据：

- 用于监督微调的高质量问答和工具调用轨迹。
- 用于偏好优化的候选回答比较。
- 用于安全与回归评估的风险样本、证据和期望行为。

一次看似简单的样本，可能经历下面的路径：

~~~text
线上事件
  -> 受控采样与数据最小化
  -> 原始 artifact 固化
  -> 去重、脱敏、格式检查和风险分层
  -> 按标签 schema 生成标注任务
  -> 人工独立判断、模型辅助或专家复核
  -> 一致性检查、抽检和仲裁
  -> 不可变数据集版本与 manifest
  -> 训练、评估或安全系统消费
  -> 新模型失败回流，形成下一版本
~~~

如果只保存最后一个标签，平台就丢失了大部分可解释性。本章要解决的，是怎样让这条路径可靠、可扩展、可保护，也让初学者能理解每个对象为什么存在，让专家能判断每个统计量和工程保证的边界。

## 11.0 先理解：标注到底在改变什么

### 11.0.1 给初学者：标注不是把“正确答案”抄进表格

对于一张猫的图片，标注员可以标出类别；对于客服助手，一条输入可能没有唯一正确的自然语言回答。标注员真正要做的，往往是把一个复杂判断拆成几个可观察的部分：

1. 用户想完成的目标是什么？
2. 回答中的哪些事实可以被给定证据支持？
3. 这个回答有没有遗漏使用户无法行动的条件？
4. 模型是否做了未经授权的承诺或工具操作？
5. 两个候选回答哪个更符合这些约束？

如果把这些问题压缩成“好/不好”，标注员会用自己的偏好填补空白。不同人会偏好不同长度、语气和拒答方式，训练数据中就会出现无法解释的噪声。

所以标注平台的第一项工作不是分发任务，而是定义要观察的事实和判断规则。

### 11.0.2 给专家：标签是测量，也是干预

标注数据一方面测量模型输出，另一方面会被用于改变模型行为。标签定义错误时，平台不仅会产生错误报告，还可能把错误偏好写回训练集。

可以把一个标注流程表示为：

~~~math
\mathrm{Label}
=
g(\mathrm{Artifact},\ \mathrm{Guideline},\ \mathrm{Annotator},\ \mathrm{Context})
+\eta
~~~

其中 Artifact 是被标注对象，Guideline 是规范版本，Annotator 是标注员及其能力条件，Context 是向标注员展示的上下文，\eta 表示误解、疲劳、主观分歧和界面误导造成的误差。

当结果进入训练时，标签还会影响模型：

~~~math
\mathrm{ModelBehavior}_{t+1}
=
F(\mathrm{ModelBehavior}_{t},\ \mathrm{Dataset}_{t},\ \mathrm{TrainingConfig})
~~~

这不是说可以从一个标签精确预测模型行为，而是说明“标注质量”是系统输入的一部分。标注规范、展示顺序、模型预标注和样本采样都可能改变下一代模型。

### 11.0.3 三种数据产品

衡川先区分三个数据产品，而不是把所有样本放进一张总表。

监督数据要求回答本身满足任务契约，例如字段完整、事实有依据、工具参数合法。它适合训练模型模仿一种目标行为。

偏好数据要求候选之间有可解释的比较关系。它不一定能给出一个绝对正确答案，但要说明为什么 A 比 B 更合适，或者为什么两者都不可接受。

评估与安全数据要求样本和标签尽量独立于被测版本，并保留风险、证据和覆盖信息。它们不能因为方便训练而被模型团队反复看到。

同一条线上事件可以衍生出多个版本，但每个版本必须声明用途。用于训练的数据不能自动成为无偏的测试数据。

## 11.1 明确标注任务的边界

### 11.1.1 标注对象的五种形态

大模型平台通常至少处理五种对象：

- 单个样本：分类、摘要、问答和实体标记。
- 一段会话：多轮上下文、遗忘、意图转移和任务完成。
- 一组候选：pairwise 或 listwise 偏好比较。
- 一条轨迹：检索、工具调用、观察、重试和最终结果。
- 多模态 artifact：图片区域、视频片段、音频转写和跨模态引用。

对象不同，界面、schema、质量控制和导出格式都不同。一个 pairwise 任务如果被错误建模成“给单个回答打分”，会丢失相对比较信息；一个工具轨迹如果只保存最终文字，会丢失副作用和权限证据。

### 11.1.2 任务用途决定标签语义

同一句模型输出，用于不同用途时标签含义可能不同。

用于 SFT 时，标注员通常要改写或确认一个可以让模型学习的目标回答。

用于偏好优化时，标注员比较多个回答，关注的是相对质量、约束和原因。

用于安全评估时，标注员要判断风险类别、严重度、应有响应和是否触发工具保护。

用于数据筛选时，标注员可能只判断样本是否值得进入候选池。

平台在项目层保存 purpose，并阻止同一套标签被无声明地导出到其他用途。

### 11.1.3 范围声明

衡川第一版数据工作台支持：

- 中文和英文文本、多轮客服会话。
- 两个或三个候选回答的偏好比较。
- RAG 回答的断言、引用和证据支持标注。
- 工具调用轨迹的参数、权限和结果状态标注。
- 个人信息、密钥和高风险操作的安全标签。
- 训练和评估数据的不可变版本导出。

第一版暂不支持任意医学诊断、开放互联网爬取、未经授权的人脸身份标注和自动执行真实退款。范围限制不是功能缺失，而是把权限、专家能力和责任边界放在可运营的范围内。

### 11.1.4 数据产品契约

每个项目在创建时要声明：

- 目标用途和下游消费者。
- 输入字段、输出字段和 schema 版本。
- 允许展示给标注员的上下文。
- 标签类型、未知值和拒绝标注条件。
- 重复标注比例、金标比例和仲裁规则。
- 质量统计、最小样本量和抽检策略。
- 数据敏感等级、标注员资格和保存期限。
- 导出格式、训练或评估的版本要求。

没有契约的项目会在中途不断改变目标，最后得到一批数量不少但无法解释的数据。

## 11.2 数据接入：先管理来源，再管理标签

### 11.2.1 原始来源

衡川的候选数据来自：

- 用户同意范围内的线上会话抽样。
- 评估平台中的失败样本。
- 安全团队设计的风险样例。
- 经过授权的内部制度文档。
- 模型生成的候选回答与工具轨迹。
- 专家编写的边界案例。

每种来源的偏差不同。线上抽样更贴近真实流量，但包含隐私和分布偏差；专家样例质量高，但可能过于规整；模型生成候选覆盖广，却可能重复模型已有错误。

来源字段不能只写一个 team name。至少要记录采样时间、采样策略、原始系统版本、授权范围和是否经过人工挑选。

### 11.2.2 原始 artifact 与工作副本

原始 artifact 是接入时固化的内容摘要、媒体文件、会话事件或工具轨迹。它应该被写入受控存储，采用不可变 revision。

工作副本是经过脱敏、裁剪、格式化和分段后的内容。标注员通常只看工作副本，训练或评估导出也使用明确版本的工作副本。

二者不能混为一谈：

~~~math
\mathrm{WorkingCopy}
=
\mathrm{Transform}(
\mathrm{RawArtifact},\ \mathrm{RedactionPolicy},\ \mathrm{SamplingPolicy})
~~~

若脱敏规则修订，生成新的工作副本 revision；不能覆盖原始内容，也不能让旧标注悄悄指向新文本。

### 11.2.3 接入校验

接入阶段至少做：

1. schema 解析和字段类型检查。
2. 内容摘要和重复检测。
3. 编码、语言和模态识别。
4. PII、密钥、内部链接和恶意附件扫描。
5. 文件大小、时长和分辨率限制。
6. 租户授权、保留期限和来源审计。
7. 样本完整性与会话顺序检查。

校验失败的样本进入隔离区，并带有可解释原因。不能把所有失败样本直接丢弃，否则会把“难解析”误认为“没有问题”。

### 11.2.4 去重不只是字符串比较

完全相同的文本可以用内容哈希去重；改写、复制粘贴和同一会话的相邻事件还需要近似去重。可组合：

- 规范化后的字符串哈希。
- n-gram 重合。
- embedding 近邻。
- 会话 ID、时间窗口和业务事件键。

去重过强会丢掉真实重复发生的事件，去重过弱会让一个模板样本在训练集里获得过高权重。平台保存去重规则和被合并样本的关系，允许重新计算。

### 11.2.5 数据文档

数据集应像软件包一样有说明文档。Datasheets for Datasets 提倡记录数据集的动机、组成、收集过程、处理、用途和限制；Data Statements for NLP 则强调语言数据的来源、人口与语言属性、注释和使用边界。它们不是衡川的具体标注规范，但为数据说明提供了可复用的检查维度。

衡川的数据说明至少回答：

- 为什么收集这些样本？
- 谁产生了样本，哪些人群被代表或缺失？
- 样本的时间和业务分布是什么？
- 哪些字段被脱敏或改写？
- 标签由谁、按什么规范产生？
- 哪些用途允许，哪些用途不允许？
- 已知的偏差、污染和覆盖盲区是什么？

资料入口见 [Datasheets for Datasets](https://arxiv.org/abs/1803.09010) 和 [Data Statements for NLP](https://aclanthology.org/Q18-1041/)。

## 11.3 标签 schema：把模糊判断变成可执行对象

### 11.3.1 标签的基本类型

常见标签类型包括：

- 单选：一个主意图或一个风险等级。
- 多选：多个风险类别同时存在。
- 序数：从 1 到 5 的质量等级。
- 连续值：概率、强度或时间估计。
- 排序：多个候选的相对优先级。
- Span 或区域：文本片段、图片框、视频时间段。
- 结构化对象：工具参数、证据链和纠错后的完整回答。
- 分布标签：多个标注员对同一答案的偏好比例。

类型决定聚合方式。把“风险等级 1、2、3”当成普通类别，和把它当成有序值，统计含义不同；把两个可接受答案强行选成一个，也会丢失不确定性。

### 11.3.2 未知、无法判断和不适用

高质量 schema 必须允许：

- unknown：信息不足，无法判断。
- not_applicable：该字段不适用于此样本。
- abstain：标注员因权限、专业能力或安全原因不应继续判断。
- ambiguous：存在多个合理解释，需要仲裁。

把这些情况都记成负例，会把数据系统性推向错误方向。例如没有订单号时，正确标签可能是“需要核验”，不是“退款失败”；没有音频清晰度时，正确标签可能是“不适用”，不是“识别错误”。

### 11.3.3 多维 rubric

衡川的客服回答可以使用以下 rubric：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 事实支持 | 有关键错误或编造 | 部分正确但缺条件 | 关键断言均有证据 |
| 任务完成 | 没有回应目标 | 回应了一部分 | 可直接推动下一步 |
| 指令遵循 | 违反关键约束 | 有格式或范围问题 | 满足全部约束 |
| 风险处理 | 产生严重风险 | 需要人工修正 | 无可见严重风险 |
| 表达质量 | 造成误解 | 基本可读 | 清楚、适度、可核验 |

分数的文字定义比数字本身更重要。若 1 分的边界不清，统计小数点后三位也没有意义。

### 11.3.4 证据字段

事实性任务不应只记录“正确/错误”，还要记录：

- 关键断言。
- 支持断言的证据 ID。
- 证据有效日期。
- 未被支持的文字。
- 需要补充的条件。

证据字段提高了复核成本，但它让错误可以被解释，也能用于后续自动质检和回归测试。

### 11.3.5 偏好标签不是绝对真值

DPO 和 RLHF 类流程使用偏好数据把多个候选的相对关系提供给训练过程。[Direct Preference Optimization](https://arxiv.org/abs/2305.18290) 给出了一种直接利用偏好数据优化策略的目标，[InstructGPT](https://arxiv.org/abs/2203.02155) 工作展示了人工示范、排序和强化学习组成的训练流程。它们说明偏好数据是重要训练信号，但不意味着任何一组人工偏好都能代表普遍价值。

偏好 schema 至少包括：

~~~json
{
  "task_type": "pairwise_preference",
  "prompt": "用户想查询退款条件",
  "context_ids": ["policy-2026-08-01#refund"],
  "candidates": [
    {"id": "a", "text": "可以，已经为你完成退款。"},
    {"id": "b", "text": "我先核验订单状态和退款期限，再判断是否符合退款条件。"}
  ],
  "label": {
    "preferred": "b",
    "reason_tags": ["avoids_unsupported_commitment", "asks_required_verification"],
    "confidence": 2
  }
}
~~~

如果两个回答都存在严重问题，应允许 both_bad；如果差异不可分辨，应允许 tie。强行选择 A 或 B 会制造虚假的训练信号。

### 11.3.6 schema 的不变量

系统在提交时校验不变量，例如：

- preferred 必须引用候选 ID。
- 标记事实支持时必须至少有一个 evidence_id。
- 标记 high_risk 时必须填写 risk_type。
- 选择 unknown 时不能要求填写不存在的证据。
- 评分字段必须在项目版本声明的范围内。

不变量应该在前端、API 和导出器中保持一致。只在界面上禁用按钮，不能防止直接调用 API 写入非法标签。

## 11.4 标注规范：把判断过程写完整

### 11.4.1 一份规范的结构

规范文档至少包含：

1. 任务目的和下游用途。
2. 输入字段与可见上下文。
3. 标签定义和互斥关系。
4. 正例、反例和边界案例。
5. 不确定、拒绝和升级处理。
6. 多维评分的等级锚点。
7. 冲突解决优先级。
8. 提交前自检清单。
9. 版本变更记录和生效时间。

标注员不是靠阅读一段长说明就能保持一致。规范要把抽象原则落到样例和决策顺序上。

### 11.4.2 先判断事实，再判断风格

客服回答可能既正确又不够简洁，也可能很简洁但事实错误。衡川规定先判断：

1. 用户目标和事实条件。
2. 关键事实是否被证据支持。
3. 是否遵守权限与安全要求。
4. 是否完成任务。
5. 最后评价表达和风格。

这样可以减少“写得很像客服”掩盖事实错误，也避免因为语气不喜欢就否定正确答案。

### 11.4.3 冲突优先级

当帮助性与安全性冲突时，不能让标注员自行猜。规范明确：

- 防止严重未授权副作用优先于立即满足请求。
- 事实准确优先于语言流畅。
- 证据不足时，承认不确定优先于编造完整答案。
- 指令格式不能覆盖更高层的隐私和权限约束。

这些是项目规则，不是所有业务的普遍伦理结论。变更时需要版本化并重新校准金标。

### 11.4.4 标注员培训

培训集不应该只展示容易样本。它至少包括：

- 明确正例。
- 明确反例。
- 两个标签都看似合理的边界例。
- 规范最近改动的样本。
- 真实线上故障的脱敏版本。

培训结果与项目权限绑定。新标注员可以先处理低风险任务，完成校准后再进入复杂或敏感队列。

## 11.5 任务分发：让正确的人在正确的时间处理正确的样本

### 11.5.1 分发的六个目标

任务调度同时追求：

- 吞吐：按业务时限完成项目。
- 质量：难样本交给合适的能力层级。
- 独立性：重复标注尽量避免同一人的相关偏差。
- 公平：不让某个租户或标注员长期占满队列。
- 隐私：敏感数据只分配给有授权的人。
- 成本：把专家时间用在真正需要专家的样本上。

只做平均分发会把简单样本和高风险样本混在一起，也会让敏感权限失控。

### 11.5.2 任务状态与租约

任务状态可以设计为：

~~~text
CREATED -> READY -> LEASED -> IN_PROGRESS -> SUBMITTED
                                  |             |
                                  |             +-> QC_PENDING -> ACCEPTED
                                  |             +-> REWORK -> READY
                                  |             +-> ARBITRATION
                                  |
                                  +-> EXPIRED -> READY
                                  +-> CANCELLED
~~~

LEASED 状态带有过期时间和版本号。标注员领取任务后断网，租约过期，任务可以重新分配；旧客户端恢复提交时，服务端用版本号拒绝覆盖新一轮结果。

### 11.5.3 领取和提交的幂等

领取接口用项目、标注员、任务批次和请求幂等键防止重复领取；提交接口使用 task revision 和 client submission ID，避免重复点击创建两条有效标注。

标注内容允许保存草稿，但只有一次明确提交事件进入质量流程。草稿和最终标注分开存储，否则自动保存会被误认为正式标签。

### 11.5.4 技能和权限路由

标注员画像可以包含：

- 可处理的语言和模态。
- 通过的领域培训。
- 当前项目权限。
- 历史质量区间和争议类型。
- 每日负载与可用时间。

路由先做硬过滤，再做排序：

~~~math
\mathrm{Eligible}(a,s)
=
\mathbf{1}[
\mathrm{Permission}(a,s)
\land
\mathrm{Skill}(a,s)
\land
\mathrm{Capacity}(a)
]
~~~

只有 Eligible 为 1 的标注员才能接触样本 s。之后可以按风险、等待时间、质量和负载排序，但不能用一个综合分数绕过权限过滤。

### 11.5.5 等待和公平

如果任务到达率为 \lambda，平均在系统时间（包括等待和处理）为 W，系统中任务数为 L，Little 定律给出稳态近似：

~~~math
L\approx\lambda W
~~~

它帮助估算系统中的任务积压，但只有在到达率、在系统时间和系统处于相对稳定状态时才适用。高峰期、任务会被丢弃或频繁返工时，不能用它直接承诺完成时间；若只想估算等待队列，还要明确使用的是队列长度和等待时间，而不是把两者与 L、W 混用。

为了避免低优先级任务永久等待，可以让等待时间逐渐增加排序权重：

~~~math
\mathrm{Priority}
=
\mathrm{BasePriority}
+\alpha\cdot\mathrm{WaitMinutes}
-\beta\cdot\mathrm{CurrentLoad}
~~~

\alpha 和 \beta 是调度策略参数。敏感级别、截止时间和租户配额仍应作为硬约束或独立维度保存。

### 11.5.6 重复标注分配

需要计算一致性的样本应分给相互独立的标注员。平台避免把同一会话的近邻样本连续分给同一人，也不提前暴露其他人的选择。

重复次数按风险和不确定性调整：

- 低风险、规则明确的样本可以一次标注加低比例抽检。
- 普通偏好样本常用两人独立判断。
- 高风险、低一致性或专家任务需要更多判断和仲裁。

重复标注是获取证据的成本，不是越多越好。若规则本身不清，多复制几次只会复制分歧。

## 11.6 标注界面：展示什么会改变标签

### 11.6.1 上下文最小化

界面要让标注员看到做出判断所需的上下文，同时隐藏不必要的身份信息、版本噪声和其他人的标签。展示更多内容不一定更好：过长的历史会增加认知负担，未授权的内部字段会扩大隐私风险。

平台为每种项目定义 Context View：

- 可见消息范围。
- 可见检索证据。
- 可见工具结果和权限状态。
- 是否显示时间与文档版本。
- 是否允许复制、下载或外链访问。

这些配置也要版本化。改变可见上下文，可能改变标注分布。

### 11.6.2 模型建议与锚定偏差

模型预标注可以提高速度，却可能让人顺着模型选择。尤其当模型建议先出现在界面中央，标注员会把它当作默认答案。

对高风险或研究用途项目，平台可采用：

1. 标注员先独立完成初判。
2. 提交初判后才展示模型建议。
3. 若修改标签，要求说明修改原因。
4. 对模型建议与人工初判冲突的样本加大抽检。

如果业务只追求快速筛选，可以选择先显示建议，但报告必须承认标签受模型辅助影响，不能把它当作独立人工 gold。

### 11.6.3 草稿、自动保存和并发

长对话和多模态任务需要自动保存草稿。保存接口使用客户端序号和服务端 revision：

~~~math
\mathrm{AcceptWrite}
=
\mathbf{1}[
\mathrm{clientRevision}
=
\mathrm{serverRevision}
]
~~~

版本不匹配时，服务端返回冲突，客户端重新加载并让用户选择合并。静默覆盖会丢失标注员的判断，也破坏审计。

### 11.6.4 证据和理由

理由字段不应只是“看起来更好”。对事实任务，要求选择断言、引用证据或标记缺失条件；对偏好任务，要求选择主要差异标签；对安全任务，要求填写风险类型和期望响应。

理由本身也可能包含 PII 或敏感内容，需要经过同样的存储、权限和删除策略。

## 11.7 质量控制：一致性不是唯一答案

### 11.7.1 金标样本

金标样本由经过授权的专家根据当前规范确认，并混入普通任务。金标用于发现规范理解错误和注意力问题，不直接代表所有样本的真实分布。

金标设计要注意：

- 不让固定格式或答案长度暴露金标。
- 覆盖边界、未知和安全样本。
- 定期重新审查。
- 记录金标规范版本。
- 标注员失败时进入培训或复核，而不是立刻把一个样本当成绝对真理。

### 11.7.2 重叠标注和分歧

同一样本由多名标注员独立处理，可以估计分歧。分歧至少有三种来源：

- 样本信息不足。
- 规范存在歧义。
- 标注员没有遵循规范或缺少领域能力。

平台保存每一票原始判断，不只保存最终仲裁结果。原始分布有时比单一标签更适合偏好训练和研究。

### 11.7.3 一致性统计

对两个分类标注员，可使用 Cohen's kappa：

~~~math
\kappa
=
\frac{p_o-p_e}{1-p_e}
~~~

p_o 是观察到的一致率，p_e 是按两位标注员边际分布计算的偶然一致率，且只有在 p_e<1 且存在有效重叠样本时该表达式才有定义。kappa 受类别不平衡、标签稀疏和样本分布影响，不能单独解释质量。

对多个标注员，可以用 Fleiss 类统计；对排序任务可以观察 Kendall tau 或 pairwise agreement；对主观评分还应报告均值、分布和评审员间的方差。

一个项目的 kappa 低，可能意味着样本太难或规范太模糊，而不是简单意味着“标注员不合格”。因此报告同时列出每类样本数量、混淆矩阵、分歧样本和仲裁原因。

scikit-learn 提供了 Cohen kappa 的实现文档，可作为统计接口入口，但库函数不会替平台决定抽样单位、标签语义和业务阈值，见 [cohen_kappa_score](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html)。

### 11.7.4 仲裁流程

仲裁员看到规范、样本和各方理由，但不应看到谁先标了什么，除非任务需要调查过程。仲裁结果包括：

- 采用某个标签。
- 允许多个标签。
- 标记 unknown 或 ambiguous。
- 修改规范并让一批历史样本重审。
- 样本不进入当前数据产品。

仲裁不是把所有分歧强行压平。若两个回答确实难以区分，保留 tie 比伪造偏好更诚实。

### 11.7.5 质量分数的边界

平台可以将多个信号组合为一个内部排序分数：

~~~math
\mathrm{QualityIndex}
=
w_g G
+w_o O
+w_a A
-w_r R
~~~

其中 G 是金标表现，O 是重叠标注一致性，A 是抽检通过率，R 是返工或严重错误率。这个分数适合安排培训、任务路由和抽检，不应直接作为对个人的惩罚或作为标签真值。

### 11.7.6 质量与真值的区别

多人一致可能是因为他们共同误解了规范；专家意见也可能过时；高 kappa 可能只是所有人都选择了占比最大的类别。质量控制要结合规范审查、外部证据、下游模型表现和线上错误，而不是把一致率当成真值证明。

## 11.8 模型辅助和主动学习

### 11.8.1 预标注的四种用途

模型可以参与：

- 预填标签，减少重复输入。
- 生成候选理由或摘要。
- 发现格式、证据和安全异常。
- 选择更值得人工处理的样本。

四种用途的风险不同。预填标签影响人工判断，自动质检影响样本去留，主动学习影响数据分布，自动生成理由还可能把模型幻觉写进训练资产。

### 11.8.2 不确定性和分歧

对样本 s，可以用模型预测熵、不同比较模型的分歧、历史错误率和业务风险构造采样优先级：

~~~math
\mathrm{SelectionScore}(s)
=
\alpha U(s)
+\beta D(s)
+\gamma R(s)
+\delta N(s)
~~~

U 是预测不确定性，D 是模型或版本分歧，R 是风险，N 是新颖性。主动学习的目标不是把所有高分样本丢掉，而是让有限人工预算覆盖不确定、重要和分布盲区。

主动学习文献将样本选择视为减少标注成本、提高模型信息增益的问题。其方法可以启发平台设计，但真实项目需要重新验证选择策略是否让数据分布发生偏斜。资料见 [Active Learning Literature Survey](https://burrsettles.com/pub/settles.activelearning.pdf)。

### 11.8.3 人机协作的安全等级

可以把自动化分为四个等级：

1. 建议：模型只展示候选，人类完整判断。
2. 预填：模型填写字段，人类必须逐项确认。
3. 筛选：模型把明显样本分层，人类处理关键和不确定样本。
4. 自动通过：只允许在规则明确、风险低、持续抽检的范围内使用。

高风险工具操作、隐私泄露、医疗法律结论和评估 gold 不应因为模型置信度高就自动通过。

### 11.8.4 预标注接受率不是模型准确率

如果标注员经常接受模型建议，可能说明建议有用，也可能说明界面存在锚定偏差。平台区分：

- 人工初判与模型建议的一致率。
- 人工最终标签与模型建议的一致率。
- 模型建议被修改的比例。
- 修改后的标签是否更接近专家仲裁。

只有在独立 gold 或专家标签上验证，才能讨论模型预标注质量。

### 11.8.5 自动质检的失败模式

模型质检可能：

- 把正确但少见的答案当成异常。
- 被标注员理由中的幻觉说服。
- 对敏感内容过度拦截。
- 只检查文本，不检查工具副作用。
- 在不同语言或群体上性能不均衡。

自动质检结果进入风险排序和人工复核队列，除非项目已经证明其精确率足以承担自动决策，并且持续有随机抽检。

## 11.9 版本、血缘与可复现

### 11.9.1 一条数据的血缘

一条训练样本的来源可能是：

~~~text
线上会话 event-81
  -> 采样策略 sample-2026w32
  -> 脱敏策略 redact-v5
  -> 工作副本 artifact-9a
  -> 标注规范 support-v6
  -> 标注 annotation-22
  -> 仲裁 record-7
  -> 质检策略 qc-v3
  -> 数据集 support-sft-v4
  -> 训练任务 train-104
~~~

每条边都要有 producer、时间、版本和状态。只保存最终 JSONL 文件，无法解释它为什么进入数据集。

### 11.9.2 W3C PROV 的启发

W3C PROV 用 Entity、Activity、Agent 描述数据实体、处理活动和执行者之间的关系。标注平台不必机械复制规范，但可以采用同样的思路：

- Entity：原始会话、工作副本、标注、规范、数据集。
- Activity：采样、脱敏、标注、质检、仲裁、导出。
- Agent：用户、标注员、模型服务、规则服务、项目组。

这样一条数据的“谁在什么时候用什么规则做了什么”可以被查询。入口见 [W3C PROV Overview](https://www.w3.org/TR/prov-overview/)。

### 11.9.3 不可变版本

发布后的数据集、规范和质检策略不可原地修改。纠错流程是：

1. 标记旧样本或旧标签存在问题。
2. 创建新规范或修订版本。
3. 重新生成受影响的标注任务。
4. 生成新数据集 revision。
5. 让下游训练或评估明确选择新版本。

旧版本保留到其保留期限结束，除非法律、隐私或删除请求要求更早清理。版本不可变不等于永远保存，删除策略优先于复现便利。

### 11.9.4 Manifest

一个可消费的数据集 manifest 至少包含：

~~~json
{
  "dataset_id": "support-preference-v4",
  "revision": "sha256:6d...",
  "purpose": "preference_training",
  "source_entities": ["artifact-batch-2026w32"],
  "sample_count": 48000,
  "schema_revision": "pairwise-v3",
  "guideline_revision": "support-guideline-v6",
  "quality_policy_revision": "qc-v4",
  "redaction_revision": "redact-v5",
  "filters": ["dedup-v2", "remove-unknown-v1"],
  "label_distribution": {
    "A": 0.46,
    "B": 0.41,
    "tie": 0.09,
    "both_bad": 0.04
  },
  "created_by": "data-platform"
}
~~~

manifest 不是装饰信息。训练平台用它恢复数据输入，评估平台用它解释模型版本，审计系统用它确认授权和处理步骤。

### 11.9.5 标签修订和下游影响

一个仲裁员修正标签后，平台需要知道哪些数据集、训练任务、评估套件和报告引用了旧标签。可以把影响分析写成图搜索：

~~~math
\mathrm{Affected}(e)
=
\{v\mid e\leadsto v\}
~~~

其中 e 是被修订的实体，v 是沿血缘可达的派生对象。这个集合不等于“所有对象都必须删除或重跑”，它只是提供影响候选；项目负责人仍要根据用途和风险决定重跑范围。

## 11.10 隐私、安全和数据删除

### 11.10.1 最小化原则

标注员只需要知道完成任务所需的字段。偏好比较通常不需要用户姓名、订单号或地理位置；安全审核可能需要保留攻击上下文，但也不需要完整账户身份。

展示层、日志层、对象存储和导出层分别做字段控制。把原始对象权限收紧，却在前端日志里打印完整内容，仍然等于泄露。

### 11.10.2 脱敏的效果与损失

脱敏可能把“张三在上海的订单”变成“用户在某地的订单”，这降低隐私风险，却可能影响地理规则和指代理解。平台记录：

- 使用的识别器和规则版本。
- 被替换的字段类型。
- 置信度和误报处理。
- 哪些任务允许看受控原文。
- 脱敏是否改变了标签语义。

Microsoft Presidio 可以作为 PII 识别和匿名化的工程参考，但工具识别结果不是法律意义上的绝对无 PII 保证，见 [Presidio](https://microsoft.github.io/presidio/)。

### 11.10.3 权限模型

权限至少覆盖：

- 项目与租户。
- 数据敏感等级。
- 原始内容与脱敏副本。
- 文本、图片、音频和视频等模态。
- 标注、质检、仲裁和导出动作。
- 训练数据与评估数据的用途。

采用最小权限时，worker、标注员、专家、项目负责人和数据导出服务具有不同权限。只读访问也应有审计，因为读取敏感内容本身可能是受控行为。

### 11.10.4 删除请求

删除一个用户或租户相关样本时，不能只删除 Sample 表的一行。需要沿血缘检查：

~~~text
原始对象
  -> 脱敏副本
  -> 标注与理由
  -> 质检与仲裁附件
  -> 数据集分片与缓存
  -> 训练导出和评估样本
  -> 搜索索引、报表和备份
~~~

有些已发布模型无法逐条删除其训练影响，这需要在产品和合规层提前定义保留政策、训练数据排除机制和后续模型处理方案。平台至少要能定位受影响的模型和数据集，而不是声称一个数据库删除就完成了全部删除。

### 11.10.5 评估完整性和隐私的冲突

为了复现一个敏感错误，工程师可能希望保留完整原文；为了保护用户，又必须最小化内容。折中方案可以是受控专家访问、可逆映射隔离、字段级权限、短期保留和脱敏版本复现。这个决策应记录在项目数据说明里。

NIST Privacy Framework 为识别、治理、控制、沟通和保护隐私风险提供框架语言，入口见 [NIST Privacy Framework](https://www.nist.gov/privacy-framework)。它不替项目给出保存天数或具体脱敏规则，平台仍需结合业务和法律要求制定策略。

## 11.11 多模态与高风险任务

### 11.11.1 多轮对话

多轮对话标注不能只显示最后一轮。界面要区分：

- 系统和开发者约束。
- 用户消息。
- 检索证据。
- 工具返回。
- 模型中间思路或不可展示的内部字段。

标注员判断的是公开行为和任务结果，不应被要求查看或保存不必要的隐藏推理内容。

### 11.11.2 视觉和音频

视觉标注需要记录区域坐标、图像 revision、缩放方式和遮挡情况；音频标注需要记录时间段、转写版本、噪声和说话人边界。坐标或时间轴的单位一旦不一致，数据看似完整却无法训练。

多模态样本的质量检查包括：

- 附件是否与样本 ID 绑定。
- 预览是否经过同样的脱敏。
- OCR 文本是否标明来源。
- 音频时间戳是否落在文件范围内。
- 图片区域标注是否使用原始分辨率坐标。

### 11.11.3 工具调用轨迹

工具任务要把模型文字、工具选择、参数、权限判断、工具结果和环境最终状态分开标注。最终回答正确但工具调用越权，应是严重失败；工具调用正确但外部系统超时，应区分模型错误与环境错误。

### 11.11.4 安全和高影响场景

高风险项目要声明：

- 风险类别和严重度。
- 标注员专业资格。
- 是否允许标注员看到完整敏感上下文。
- 何时必须升级专家。
- 哪些标签可进入训练，哪些只进入评估。
- 如何处理标注员的心理安全和内容暴露。

安全数据不能因为数量少就降低质量要求。少量高严重度样本可能比大量普通样本更影响发布决策。

## 11.12 架构：让数据流、状态和证据分离

### 11.12.1 服务边界

衡川数据工作台可以拆成：

~~~text
项目与规范 API
        |
        v
数据接入服务 -> 原始对象存储 -> 脱敏与预处理队列
        |                         |
        v                         v
数据集注册表               工作副本与样本索引
        |                         |
        +-------------> 任务编排器
                              |
                +-------------+-------------+
                |                           |
                v                           v
          标注员任务队列                专家/仲裁队列
                |                           |
                +-------------+-------------+
                              v
                       标注与事件存储
                              |
                +-------------+-------------+
                |                           |
                v                           v
          质量评估器                    模型辅助服务
                |                           |
                +-------------+-------------+
                              v
                    版本、血缘与 manifest
                              |
                 训练平台 / 评估平台 / 安全系统
~~~

项目服务不直接修改标注结果；任务服务不决定标签真值；模型辅助服务不直接把建议写成最终标签；导出服务只消费通过策略的不可变版本。边界清楚，系统才容易审计。

### 11.12.2 存储分工

关系数据库保存项目、任务状态、权限、revision、标注索引和事件元数据；对象存储保存原始文本、媒体、附件、理由和导出文件；搜索和分析库保存可检索字段与聚合指标。

数据库不应承载所有视频和长对话，也不应让分析库成为原始敏感内容的无边界副本。每个对象通过内容摘要、权限引用和保留策略关联。

### 11.12.3 事件记录

关键状态变化写入事件：

~~~json
{
  "event_id": "evt-annotation-2001",
  "type": "annotation_submitted",
  "project_revision": "project-support-v6",
  "task_id": "task-00421",
  "sample_revision": "sample-9a",
  "actor_type": "human_annotator",
  "actor_ref": "ann-hash-17",
  "occurred_at": "2026-08-11T11:42:00Z",
  "payload_ref": "object://controlled/annotation/2001"
}
~~~

事件保存动作和引用，不一定把完整敏感内容塞进消息队列。删除策略要同时处理事件、派生索引和备份。

### 11.12.4 资源 API

创建项目：

~~~http
POST /annotation-projects
Content-Type: application/json

{
  "name": "support-preference-2026-08",
  "purpose": "preference_training",
  "schema_revision": "pairwise-v3",
  "guideline_revision": "support-guideline-v6",
  "quality_policy_revision": "qc-v4",
  "sensitivity": "internal"
}
~~~

提交标注：

~~~http
POST /annotation-tasks/task-00421/submissions
Content-Type: application/json
Idempotency-Key: submit-task-00421-client-9

{
  "task_revision": 12,
  "label": {
    "preferred": "b",
    "reason_tags": ["evidence_supported"]
  },
  "unknown_fields": [],
  "guideline_revision": "support-guideline-v6"
}
~~~

API 必须检查任务租约、schema revision、标注员权限和提交幂等键。返回值包含 accepted、rework 或 conflict，不把所有异常都返回成一个通用错误。

## 11.13 容量和成本

### 11.13.1 一个教学规模

假设衡川每天采样 80,000 条线上事件，其中 25% 通过初步筛选进入标注候选；每条候选平均需要两次人工判断，10% 的样本进入专家仲裁。每日人工任务量为：

~~~math
N_{\mathrm{label}}
=
80000\cdot0.25\cdot2
=
40000
~~~

专家任务量约为：

~~~math
N_{\mathrm{expert}}
=
80000\cdot0.25\cdot0.10
=
2000
~~~

若普通标注平均 2.5 分钟，专家仲裁平均 6 分钟，则总人工分钟约为：

~~~math
T_{\mathrm{minutes}}
=
40000\cdot2.5
+2000\cdot6
=
112000
~~~

这相当于约 1,867 个小时。若没有足够标注员，队列会增长；若把所有样本都交给专家，成本会快速失控。

### 11.13.2 吞吐和并发

若一个标注员每天有效工作 6 小时，平均每条任务需要 2.5 分钟，单人理论吞吐为：

~~~math
N_{\mathrm{per\ annotator}}
=
\frac{6\cdot60}{2.5}
=
144
~~~

实际要乘以培训、休息、页面等待、返工和仲裁的有效系数 \rho。若 \rho=0.75，则约为 108 条。这个数字是容量估算，不是对标注员的绩效承诺。

### 11.13.3 成本分解

数据项目总成本可以拆为：

~~~math
C_{\mathrm{total}}
=
C_{\mathrm{annotator}}
+C_{\mathrm{expert}}
+C_{\mathrm{model\ assist}}
+C_{\mathrm{storage}}
+C_{\mathrm{quality}}
+C_{\mathrm{privacy}}
~~~

更有意义的指标是单位有效样本成本：

~~~math
C_{\mathrm{accepted}}
=
\frac{C_{\mathrm{total}}}
{N_{\mathrm{accepted\ samples}}}
~~~

当 N_accepted_samples=0 时，单位有效样本成本没有定义，应报告“无有效产出”以及总成本、候选数、拒绝数和返工数，而不是用 1 替代分母。如果模型预标注使人工速度提升，但错误标签和返工增加，单位有效样本成本可能反而上升。因此模型辅助要和通过质量、返工率、仲裁率一起评估。

### 11.13.4 存储估算

若每日 20,000 条工作副本平均 8 KB、每条保留 3 个标注事件平均 3 KB、元数据和审计平均 2 KB，则每天热数据约为：

~~~math
S_{\mathrm{day}}
=
20000\cdot(8+3+2)\mathrm{KB}
=
260000\mathrm{KB}
\approx
254\mathrm{MB}
~~~

媒体、备份、派生索引和长期版本会显著放大这个数字。估算时不要只看标签 JSON。

## 11.14 运营指标：数量不等于数据价值

### 11.14.1 进度和服务指标

平台观察：

- 就绪任务、租约中任务和积压时间。
- 提交成功、冲突、过期和返工数量。
- 普通标注与专家队列的 P50、P95 等待时间。
- 每个租户和项目的吞吐、SLA 和取消率。

### 11.14.2 质量指标

平台观察：

- 金标表现和校准变化。
- 重叠标注一致性及其置信区间。
- 各标签分布和 unknown 比例。
- 返工、仲裁和严重错误率。
- 模型建议接受与修改比例。
- 不同语言、领域和风险切片的质量差异。

### 11.14.3 产出指标

平台观察：

- 通过质检的数据量。
- 单位有效样本成本。
- 训练数据覆盖的新错误类型。
- 评估集覆盖与回归修复率。
- 新数据进入训练后目标指标的变化。

最后一项需要谨慎做因果归因。模型变好可能同时来自架构、训练超参数、检索、提示词和数据。标注平台可以提供数据版本和对照，但不能仅凭相关性宣称某批标签造成了全部提升。

### 11.14.4 质量收益和数据级联

Data Cascades in High-Stakes AI 研究了数据问题如何沿系统传播，提醒团队不要只盯着模型和算法。标注规范模糊、样本覆盖偏斜、反馈闭环缺失都可能形成级联影响。资料入口为 [Data Cascades](https://arxiv.org/abs/2207.04391)。

衡川把一条线上失败修复为一条训练样本，并不意味着问题已经解决。还要看：

- 失败类型是否在数据中获得足够覆盖。
- 训练后是否在独立评估集上改善。
- 是否引入过度拒答、啰嗦或新的安全退化。
- 线上分布是否真的包含该失败。

## 11.15 完整案例：从一次错误退款承诺到新数据集

### 11.15.1 发现问题

客服记录发现，模型在用户尚未提供订单信息时回答“已经为你完成退款”。事件包含用户请求、检索片段、模型输出、工具轨迹和最终账户状态。

数据团队先把它定义为一个高风险工具样本，而不是普通客服问答。样本的目标是判断：

1. 模型是否识别了需要核验订单。
2. 回答是否作出未经事实支持的承诺。
3. 是否调用了正确的只读查询工具。
4. 在查询结果未知时是否暂停或转人工。

### 11.15.2 处理链

~~~text
事件冻结 revision e-81
  -> 移除姓名、电话、订单号
  -> 保留工具类型、状态码和时间顺序
  -> 两名安全标注员独立判断
  -> 一个标注员标记严重违规，另一个标记信息不足
  -> 专家查看脱敏证据并确认严重违规
  -> 修订“未经核验承诺”规范
  -> 将相似历史样本加入安全回归集
  -> 生成训练候选，但不自动进入训练
~~~

专家仲裁同时发现第二位标注员的问题不是粗心，而是界面没有展示工具状态。平台修订 Context View 后重新标注同一批样本。

### 11.15.3 为什么要保留不同意见

如果系统只保存最终“严重违规”，团队会知道标签，却不知道规范或界面哪里导致分歧。保留两票、理由和仲裁过程后，数据团队可以区分：

- 标注员没有理解规则。
- 样本真的缺少信息。
- 展示上下文不完整。
- 模型输出本身有多个合理解释。

这些区别决定修复是培训、改界面、补数据还是改模型。

### 11.15.4 数据集决策

该样本可以派生出三份资产：

- 安全评估样本：保留原始风险标签、严重度和期望行为。
- SFT 候选：包含一个先核验、再回答的示范，但需要专家复核。
- 偏好样本：比较未经核验的承诺和谨慎回答，明确主要差异是证据和权限，而不是长度。

三份资产引用同一个脱敏 artifact，但有不同 purpose、schema 和质量策略。导出时不能把评估样本自动混进训练集。

## 11.16 故障复盘：标注平台怎样把问题放大

### 11.16.1 模型预标注污染人工判断

一个偏好项目先展示模型建议，标注员接受率达到 93%，项目负责人认为模型预标注极其准确。后来专家盲审发现，标注员只是跟随建议，模型在“长但不准确”的回答上有系统偏好。

修复包括先收集人工初判、随机隐藏建议、对冲突样本做专家复核和按领域报告接受率。93% 的接受率不能再被写成模型标签准确率。

### 11.16.2 规范更新却原地覆盖

客服制度变化后，项目负责人直接修改 guideline 文件，继续让旧任务提交。旧任务按旧规则完成，新任务按新规则完成，最终数据集混有两种标签语义。

修复是规范不可变、任务绑定 guideline revision、版本不匹配时阻止提交或进入迁移流程。历史标签是否重审由影响分析决定。

### 11.16.3 只看一致率造成错误自信

一个风险项目中 98% 的样本都被标成“安全”，一致率很高。抽查后发现，标注员把未展示的工具副作用当成不存在。

问题不是标注员之间不一致，而是共同缺少上下文。平台必须把上下文版本、样本覆盖、金标设计和专家审查纳入质量证据。

### 11.16.4 删除只删了工作表

租户要求删除一批用户样本，工程师删除了 Sample 行，却忘了对象存储、搜索索引、导出数据集和报表缓存。数据已经不在主表里，仍可能从其他副本被读取。

修复是以 artifact ID 追踪派生对象，删除任务逐层确认状态，报告中保留最小化的删除审计记录，不保留被删除的原始内容。

### 11.16.5 训练数据和测试数据交叉污染

一批高质量偏好样本先被用于训练，又被加入公开回归集。模型在回归集上分数很高，团队误以为泛化能力提高。

平台在数据集 manifest 中声明 purpose 和 lineage，训练数据、开发数据、评估数据默认互斥，若确需复用必须显式记录并在报告中标记证据限制。

## 11.17 版本化架构与删除验证

### 11.17.1 导出前的策略检查

导出服务在生成 manifest 前检查：

- 所有样本是否通过质量策略。
- 是否有未处理的 unknown 或仲裁任务。
- 所有对象是否通过授权和保留期限检查。
- schema、规范、脱敏和质检版本是否固定。
- 是否与评估集或禁止复用的数据集冲突。
- 是否记录 owner、purpose 和下游目的地。

检查失败时，导出任务返回具体原因和受影响样本，不生成一个看似成功但内容不完整的数据集。

### 11.17.2 删除任务状态

删除流程也有状态机：

~~~text
REQUESTED -> LOCATED -> MARKED -> PURGED
                          |
                          +-> WAITING_FOR_BACKUP
                          +-> FAILED_RETRYABLE
                          +-> FAILED_REVIEW
~~~

LOCATED 阶段列出原始对象、工作副本、标注、派生数据集、索引和缓存；MARKED 阶段阻止新导出；PURGED 阶段只确认内容已按策略删除。删除审计记录只保留请求、时间、范围和结果，不重新存储原文。

### 11.17.3 恢复和灾备

备份可能包含已删除对象。系统要定义备份保留、到期清理和恢复时的删除重放策略。若一次灾备恢复重新带回已删除对象，恢复流程必须再次执行删除清单，而不是把备份当成绕过策略的后门。

## 11.18 一个最小的质量产出审计

下面的纯 Python 示例计算两组标注的一致率、通过质量后的有效样本数和单位有效样本成本。数据是教学合成数据，不代表任何真实标注员结论。

~~~python
from collections import Counter


rows = [
    {"sample": "s1", "a": "safe", "b": "safe", "accepted": True},
    {"sample": "s2", "a": "unsafe", "b": "unsafe", "accepted": True},
    {"sample": "s3", "a": "safe", "b": "unsafe", "accepted": False},
    {"sample": "s4", "a": "unknown", "b": "unknown", "accepted": False},
    {"sample": "s5", "a": "safe", "b": "safe", "accepted": True},
]


agreement = (
    sum(row["a"] == row["b"] for row in rows) / len(rows)
    if rows
    else None
)
accepted = sum(row["accepted"] for row in rows)
label_distribution = Counter(row["a"] for row in rows)
total_cost = 18.0
cost_per_accepted = total_cost / accepted if accepted else None


print(
    f"agreement={agreement:.3f}"
    if agreement is not None
    else "agreement=undefined"
)
print(f"accepted_samples={accepted}")
print(
    f"cost_per_accepted={cost_per_accepted:.2f}"
    if cost_per_accepted is not None
    else "cost_per_accepted=undefined"
)
print(f"labels={dict(sorted(label_distribution.items()))}")
~~~

预期输出：

~~~text
agreement=0.800
accepted_samples=3
cost_per_accepted=6.00
labels={'safe': 3, 'unknown': 1, 'unsafe': 1}
~~~

这里的 agreement 只是原始一致率，没有扣除偶然一致，也没有判断哪一个标签是真值；accepted_samples 也只是项目质量策略的结果。示例的作用是展示为什么平台要同时保存分歧、有效产出和成本，而不是把所有提交都算作有效数据。

## 11.19 资料等级与证据边界

本章的资料按用途区分：

- 数据说明论文：Datasheets for Datasets、Data Statements for NLP，用于设计数据文档和限制说明。
- 数据系统研究：Data Cascades，用于理解数据问题如何沿高风险系统传播。
- 对齐论文：InstructGPT、DPO，用于解释示范数据、偏好数据和训练目标的关系。
- 过程标准：W3C PROV，用于组织实体、活动、执行者和血缘关系。
- 治理框架：NIST Privacy Framework，用于隐私风险的管理语言，不直接给出项目阈值。
- 工程工具文档：[scikit-learn kappa](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html)、[Presidio](https://microsoft.github.io/presidio/) 和 [DVC](https://dvc.org/doc)，用于实现统计、识别和版本工作流，不证明标签一定正确。
- 主动学习综述：用于理解样本选择策略，不保证某个不确定性公式在衡川上最优。

论文中的实验结果不能直接变成平台 SLA；库和工具文档不能替代数据设计；本章中的衡川样本、数字、公式和代码输出都是教学示例。真实项目必须用自己的语言、领域、风险、标注员和下游模型做校准。

## 11.20 章节回顾与实践

一个成熟的数据标注平台要能回答四个问题：

1. 这条样本从哪里来，为什么进入这个项目？
2. 标注员依据哪一版规范、看到了哪些上下文？
3. 这个标签经过了哪些独立判断、质检和仲裁？
4. 它最终进入了哪些数据集、训练任务或评估流程，删除或修订时怎样找到它们？

读者可以继续练习：

- 为一个多轮客服偏好任务设计 schema，明确 tie、both_bad 和 unknown 的区别。
- 设计模型预标注先展示和后展示两种界面，并说明如何测量锚定偏差。
- 给出一个二人分类项目的一致性报告，说明为什么不能只写 kappa。
- 设计一个规范修订对旧任务、旧标签和已导出数据集的影响分析。
- 为一条包含姓名、订单号和工具轨迹的样本设计展示、日志、导出和删除策略。
- 估算每日 50,000 条候选、两次独立标注和 8% 专家仲裁所需的人员、队列和成本。

数据标注平台的核心不是让人点得更快，而是稳定生产可训练、可评估、可追溯、可删除、可解释的数据资产。数量、速度和漂亮的报表都只是手段；当标签语义、来源和质量证据能够被重新检查时，数据才真正进入工程系统。
