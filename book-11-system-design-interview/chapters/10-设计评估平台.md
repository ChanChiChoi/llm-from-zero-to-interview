# 第十章：设计评估平台：把模型质量变成可追溯的证据

模型评估不是在表格里填几个分数，也不是让一个更大的模型读完回答后给出“4.5 分”。它是一套测量系统：先说明要证明什么，再固定被测对象、数据、执行条件和评估规则，最后把结果连同不确定性、成本、失败样例和适用边界交给发布与改进流程。

这件事之所以容易被低估，是因为模型输出看起来像自然语言，而自然语言不像分类标签那样可以直接比较。一个回答可能没有使用参考答案中的任何词，却准确地解决了问题；另一个回答可能写得流畅、术语很多，却在关键事实处编造。评估平台要做的不是消灭这种复杂性，而是把复杂性拆成可以观察、复现和追问的证据。

本章贯穿一个具体场景。衡川是一家企业客服公司的内部助手，帮助客服查找制度、总结工单、调用退款和工单工具。团队准备把线上使用的 support-v11 换成 support-v12。v12 在公开问答集上分数更高，平均响应更快，但一轮小规模灰度中出现了两类问题：它在少数退款场景中过度自信地给出未经授权的承诺；它在检索结果冲突时引用了旧版本制度。团队需要的不是一个“总分”，而是一套能回答以下问题的系统：

- 这次被测的到底是模型权重，还是权重加提示词、检索索引和工具策略的组合？
- v12 的提升来自哪些能力切片，哪些能力发生了退化？
- 离线样本上的提升是否超过了抽样误差和运行随机性？
- 自动评估器是否真的能识别事实错误和不当工具调用？
- 哪些失败样例足以阻止高风险流量扩大，哪些问题可以在低风险灰度中观察？
- 评估所消耗的 GPU、裁判模型和人工时间，换来了多少可靠的业务证据？

## 10.0 先把“评估”说清楚

### 10.0.1 给初学者：评估不是问模型“好不好”

“好不好”不是一个可以直接测量的属性。我们必须先把它改写成可观察的主张。

例如，不要写“v12 更聪明”，而要写成：

1. 在冻结的客服制度测试集上，v12 对可核验事实的支持率不低于 v11。
2. 在退款工具任务中，v12 的正确工具选择率提高，同时未授权副作用率不增加。
3. 在相同解码配置下，v12 的 P95 首 token 延迟不超过 v11 的 1.2 倍。
4. 在高风险安全样例中，v12 的严重失败数不超过预先约定的范围。

每个主张都有对象、数据、指标、对照和条件。没有这些部分，数字就没有明确含义。

评估平台可以抽象成一条证据链：

~~~text
质量主张
  -> 被测对象清单
  -> 数据集版本与样本切片
  -> 固定运行配置
  -> 原始输出与执行轨迹
  -> 自动、人工或执行型评估器
  -> 分数、置信区间与失败样例
  -> 版本比较和发布决策
  -> 线上反馈回流
~~~

链条中任意一环没有版本或没有记录，之后都可能无法解释结果。

### 10.0.2 给专家：测量对象、构念与证据

评估通常要区分三个概念。

第一是测量对象（measurement object）。它是一次真正执行的目标，例如某个模型 checkpoint 加上 tokenizer、system prompt、RAG 索引、工具 schema 和运行时版本。

第二是构念（construct）。它是想了解的抽象能力，例如事实性、指令遵循、拒答合理性、工具安全或长上下文检索。构念不能直接观测，只能通过任务和指标近似。

第三是证据（evidence）。它包括样本级输出、检索轨迹、工具参数、执行日志、人工标签、聚合统计和线上行为。

公开 benchmark 通常只提供构念的一部分证据。HELM 将语言模型评估放在多场景、多指标的框架中，强调准确性之外还要观察效率、偏差、毒性和其他维度；它证明的是一套评估方法如何组织，而不是某个模型在所有业务上的最终结论。论文和框架入口见 [HELM](https://crfm.stanford.edu/helm/latest/) 与 [Holistic Evaluation of Language Models](https://arxiv.org/abs/2211.09110)。

从构念到指标的映射可以写成：

~~~math
\mathrm{ObservedScore}
=
f(\mathrm{Task},\ \mathrm{Dataset},\ \mathrm{Evaluator},\ \mathrm{Runtime})
+ \varepsilon
~~~

其中 f 是具体评估流程，\varepsilon 表示抽样、随机生成、标签噪声和测量误差。这个式子不是要拟合一个真实函数，而是提醒我们：分数不只由模型权重决定。

### 10.0.3 三个容易混淆的结论

“测试集分数上升”不等于“所有用户都更满意”。它只说明在给定测试流程下，某个观察量上升。

“人工评审一致”不等于“答案事实正确”。评审员可能共同接受了错误的参考答案，或者 rubric 没有要求核查证据。

“安全样例全部通过”也不等于“系统没有风险”。测试集只能覆盖已经被设计出来的攻击和误用方式，不能证明未观测区域不存在问题。

成熟报告必须把“观察到什么”和“能推断到哪里”分开写。

## 10.1 先确定被测对象

### 10.1.1 模型权重不是完整产品

衡川的线上助手并不是一份 safetensors 文件。一次请求经过的路径可能是：

~~~text
请求
  -> 系统提示词与会话拼接
  -> 查询改写
  -> 权限过滤后的检索
  -> 模型生成工具调用或自然语言
  -> 工具执行
  -> 结果回填
  -> 安全过滤与格式化
~~~

只替换模型权重，其他环节不变，测量的是“权重替换的影响”；替换权重和索引，测量的则是一个组合变更。如果报告把后者写成“模型能力提升”，就把因果归因说过头了。

因此平台使用 EvaluationTarget 表示被测目标：

~~~math
\mathrm{Target}
=
(\mathrm{Weights},\ \mathrm{Tokenizer},\ \mathrm{Prompt},
\mathrm{Retrieval},\ \mathrm{Tools},\ \mathrm{Policy},\ \mathrm{Runtime})
~~~

有些字段可以为空。例如纯语言模型评估没有 Retrieval 和 Tools；但空值也要明确记录，而不能因为“没有使用”就不写。

### 10.1.2 目标清单

一个目标清单至少包含以下信息：

~~~json
{
  "target_id": "support-v12-release-candidate",
  "weights": {
    "model_id": "support",
    "revision": "sha256:9f...",
    "adapter": "sha256:2a..."
  },
  "tokenizer_revision": "sha256:7d...",
  "prompt_revision": "prompt-support-2026-08-04",
  "retrieval": {
    "index_revision": "policy-index-2026-08-01",
    "reranker_revision": "reranker-3"
  },
  "tools": {
    "schema_revision": "tools-v6",
    "policy_revision": "tool-policy-v4"
  },
  "runtime": {
    "engine": "inference-runtime-2.8.1",
    "quantization": "bf16",
    "region": "cn-east"
  }
}
~~~

清单中的 revision 应该指向不可变内容，或至少指向可验证的内容摘要。latest 之类的浮动标签适合部署发现，不适合历史评估。

### 10.1.3 组合变更和因果归因

假设一次实验同时改变了模型和 prompt，结果从 0.72 变成 0.77。平台只能观察到组合差异：

~~~math
\Delta_{\mathrm{observed}}
=
S(M_2,P_2)-S(M_1,P_1)
~~~

它不能仅凭这一次运行推出：

~~~math
\Delta_{\mathrm{model}}
=
S(M_2,P_1)-S(M_1,P_1)
~~~

后一个量需要额外的交叉实验，至少比较 (M1, P1)、(M2, P1)、(M1, P2) 和 (M2, P2)，或者在变更足够小且有其他证据时谨慎归因。

这个区别对生产排障很重要。v12 如果同时换了 reranker 和权重，RAG 事实性变好，不能直接把功劳记在权重上；如果安全失败增加，也不能只回滚模型而不检查策略版本。

### 10.1.4 可复现不等于完全确定

大模型输出可能受温度、top-p、随机种子、批处理顺序、硬件内核、服务负载和外部工具状态影响。即使记录了 seed，也不一定跨硬件得到 bitwise 相同的结果。

平台应该把复现分为三个层级：

- 配置可复现：能重新找到相同的模型、数据、提示词和解码参数。
- 统计可复现：重复运行后，主要指标落在相近区间。
- 位级可复现：输出字节完全相同，只适用于严格受控的部分流程。

生产评估通常追求前两层。报告应写清采用哪一层，而不是笼统写“结果可复现”。

## 10.2 数据集是测量仪器

### 10.2.1 数据集决定问题长什么样

评估数据不是被动的“题库”，而是测量仪器。它决定模型面对的输入分布、错误类型和被赋予的权重。

衡川的客服评估集不能只包含干净、完整、语气礼貌的标准问题。真实工单还包括：

- 用户只写半句话或错别字。
- 同一会话中引用了几个月前的上下文。
- 制度文档在不同日期有不同版本。
- 用户要求模型执行退款，但权限和金额条件不满足。
- 参考答案存在多个可接受表述。
- 输入里包含恶意指令或不应暴露的个人信息。

如果数据集没有这些切片，平台测到的只是“模型处理规范样例的能力”。

### 10.2.2 数据集的最小元数据

每个数据集版本至少需要记录：

- dataset_id 和不可变 dataset_revision。
- 样本 schema 与字段含义。
- 任务类型和目标构念。
- 来源、授权和敏感等级。
- 去重、脱敏、过滤和采样步骤。
- 训练集、开发集、公开测试集、隐藏测试集的关系。
- 标签版本、参考答案版本和评估规范版本。
- 样本切片字段及其生成规则。
- owner、创建时间和变更记录。

数据版本只保存一个文件名是不够的。相同文件名被重新上传、标签被静默修正、过滤脚本升级，都可能改变分数。

### 10.2.3 分层采样与总分

假设评估集分成 H 个切片，第 h 个切片包含 N_h 条样本，切片平均分为 \bar{s}_h，总体目标分布中该切片的权重为 w_h。加权总分为：

~~~math
\hat{S}
=
\sum_{h=1}^{H} w_h \bar{s}_h,
\qquad
\sum_{h=1}^{H}w_h=1
~~~

只有 N_h>0 的切片才有定义上的 \bar{s}_h；没有可评估样本的切片应报告未定义，不能先填 0 再参与加权。如果直接把所有样本混在一起，样本数量最多的切片会自动获得最大权重。那可能与真实业务流量完全不同。例如普通咨询占 95%，退款和隐私请求占 5%，若安全风险只在后者发生，平均分会掩盖严重问题。

w_h 不能为了让报告好看而事后调整。它应该来自业务流量、风险政策或明确的研究目标，并在运行前冻结。

### 10.2.4 参考答案不是唯一真理

开放问答常常有多个正确答案。平台可以把参考物从单一字符串扩展为：

- 事实断言集合。
- 必须出现或必须避免的条件。
- 可接受的答案范围。
- 证据来源和有效日期。
- 格式 schema。
- 安全和权限约束。

例如退款政策题的参考物可以要求回答包含退款期限和适用条件，但不允许模型在没有订单核验时承诺已退款。这样评估的是业务约束，而不是与一段标准文字的表面相似度。

### 10.2.5 数据污染与过拟合

公开 benchmark 被反复用于提示词调优后，分数可能反映记忆、格式适配或题目泄露，而不完全反映泛化能力。污染检测可以通过训练语料近似检索、n-gram 重合、语义相似度、发布时间和数据来源审计来发现风险，但任何一种方法都不能证明“绝对没有污染”。

平台至少应同时保留：

- 公开套件分数。
- 未公开或新采样回归集分数。
- 线上脱敏样本分数。
- 被怀疑污染的样本比例。

报告中可以把数据污染标记为证据限制，而不是把可疑样本悄悄删除后继续宣传总分。

### 10.2.6 隐藏数据的用途和代价

隐藏测试集的目的是减少直接针对标签调优，而不是制造神秘分数。它需要：

- 访问控制和读取审计。
- worker 只能获得完成任务所需的字段。
- 报告展示脱敏样例和聚合结果。
- 定期轮换已被大量使用的样例。
- 记录哪些评估运行读取过它。

隐藏集越重要，维护成本越高。若标签本身错误，团队会很难发现；因此仍然需要专家抽检、版本修订和公开的评估说明。

## 10.3 从样本到任务：固定执行协议

### 10.3.1 样本契约

每条样本不只包含输入和答案，还要有评估上下文：

~~~json
{
  "sample_id": "refund-00421",
  "slice": ["refund", "high-risk", "multi-turn"],
  "conversation": [
    {"role": "user", "content": "这个订单能不能退款？"}
  ],
  "retrieval_snapshot": "policy-index-2026-08-01",
  "allowed_tools": ["lookup_order", "create_refund"],
  "reference": {
    "claims": ["需要先核验订单状态和退款期限"],
    "evidence_ids": ["policy-2026-07-12#refund-window"]
  },
  "privacy_class": "internal"
}
~~~

allowed_tools 和 retrieval_snapshot 是样本的一部分。若每次运行都从“当前线上索引”读取，历史结果会随索引更新而变化。

### 10.3.2 运行协议

执行器在每条样本上至少记录：

- 目标清单和数据集 revision。
- system、developer、user 消息的模板 revision。
- 解码参数和随机种子。
- 检索候选、排序分数和最终注入上下文。
- 工具调用名称、参数、返回值摘要和副作用状态。
- 首 token 延迟、总延迟、输入输出 token 数。
- 原始输出、解析后输出和错误分类。
- 重试次数、缓存命中和取消原因。

对敏感数据，原始内容放在受控对象存储，分析库保存 URI、摘要和权限引用；不能因为“评估内部使用”就把所有对话复制到任意日志系统。

### 10.3.3 状态机

一个 run 可以分成多个 shard，每个 shard 再分成样本任务。样本状态至少包含：

~~~text
PENDING -> CLAIMED -> RUNNING -> SUCCEEDED
                    |          |
                    |          +-> EVALUATED
                    |
                    +-> RETRYABLE_ERROR -> CLAIMED
                    +-> TERMINAL_ERROR
                    +-> CANCELLED
~~~

模型调用成功但评估器失败时，不能把样本标成“整体成功”。应分别保存 generation_status 和 evaluation_status。否则报告中的缺失分数会被误当成零分或被无声忽略。

### 10.3.4 幂等、重试和未知结果

网络超时不等于模型没有生成。请求在服务端可能已经完成，客户端只是没有收到响应。此时自动重试可能导致重复计费或重复工具副作用。

对于纯生成样本，可以用 (run_id, sample_id, target_revision, evaluator_revision) 作为结果幂等键；对于带工具的样本，还要把工具调用幂等键传给副作用服务。无法确认结果时，状态应是 UNKNOWN，等待查询、人工处理或明确的补偿，而不是假装失败后再执行一次。

这条原则同时适用于评估平台自己的写入：对象存储已经成功、数据库回执丢失时，重试写入应该检查内容摘要，而不是盲目创建第二份结果。

## 10.4 评估器的分层设计

### 10.4.1 为什么不能只有一个总评估器

不同问题需要不同证据。格式是否为合法 JSON 可以由解析器确定；代码是否通过测试需要执行；回答是否符合品牌风格可能需要人工或裁判模型；工具是否越权则要结合权限策略和调用轨迹。

平台把评估器分成四层：

1. 确定性评估器：精确匹配、schema、正则、规则和数值检查。
2. 执行型评估器：代码测试、SQL 查询、工具模拟器、浏览器任务或环境状态检查。
3. 模型辅助评估器：LLM 裁判、语义相似度、分类器和事实核验模型。
4. 人工评估器：专家判断、偏好比较、仲裁和风险确认。

下层评估器便宜、稳定，适合大规模运行；上层评估器能处理开放问题，但更昂贵、更需要校准。它们应该并存，不能用一个“万能裁判”吞掉所有差异。

### 10.4.2 统一输出格式

评估器的输出应包含结果、证据和不确定性：

~~~json
{
  "evaluator_id": "refund-policy-check",
  "evaluator_revision": "2026-08-05",
  "status": "scored",
  "score": 0.0,
  "label": "unsupported_commitment",
  "confidence": 0.91,
  "evidence": [
    {"type": "claim", "text": "已为你完成退款", "supported": false},
    {"type": "policy", "id": "policy-2026-07-12#refund-window"}
  ],
  "failure_tags": ["missing_order_verification", "high-risk"]
}
~~~

confidence 是评估器对自身判断的置信表达，不是模型回答正确的概率。两者不能混用。status=unknown 也应该是一等结果，表示评估器没有足够证据作出判断。

### 10.4.3 精确匹配与结构化输出

选择题、数学最终值、分类标签、JSON schema、工具名和参数类型适合确定性检查。对数值题需要定义容差、单位、舍入规则和异常值处理。例如 0.3 与 30% 可能等价，0.03 却不等价；把这些规则隐含在代码里会让结果难以解释。

结构化检查可以先解析，再按字段比较：

~~~math
\mathrm{SchemaPass}
=
\mathbf{1}[
\mathrm{Parse}(y)\ \mathrm{exists}
\land
\mathrm{Validate}(\mathrm{Parse}(y),\sigma)=\mathrm{true}
]
~~~

这里 y 是模型原始输出，\sigma 是 schema。通过 schema 不说明业务内容正确，它只说明输出满足形式契约。

### 10.4.4 文本指标的正确位置

BLEU、ROUGE、METEOR、BERTScore 等指标可以用于翻译、摘要或复述的辅助比较，但词面重合不是事实正确性的充分条件。一个模型复制参考答案中的句子，仍可能在条件、时间或数字上犯错。

文本指标更适合作为：

- 发现明显退化的低成本信号。
- 对同类数据做相对趋势比较。
- 帮助聚类和抽样人工复核。

不应把单一文本相似度直接当成开放对话的发布依据。

### 10.4.5 代码与程序执行

代码生成需要执行测试，而不是只比较文本。执行器要把模型代码放进隔离环境，限制 CPU、内存、时长、网络和文件系统，并记录测试版本。

执行通过率也有边界。测试覆盖不到的分支仍可能错误；测试本身可能过弱；模型可能生成硬编码答案。因此平台保存测试用例版本、覆盖率摘要、超时和异常，而不是只存一个 pass=true。

### 10.4.6 RAG 评估

RAG 必须把“有没有找到证据”和“有没有正确使用证据”分开。

若相关文档集合为 R，检索前 k 个结果为 L_k，则：

~~~math
\mathrm{Recall@k}
=
\frac{|R\cap L_k|}{|R|}
~~~

它回答“相关文档是否被找回来”，不回答生成答案是否忠实。若某条 query 没有可评估的相关文档集合，即 |R|=0，Recall@k 对该 query 未定义，应将无答案或无标注证据样本单独报告，而不是记成 0 或 1。生成侧还需要检查：

- 回答中的每个关键断言是否能在证据中找到支持。
- 引用是否指向真正支持该断言的片段。
- 多版本文档冲突时是否使用了有效日期。
- 证据不足时是否承认不确定。

可以定义断言支持率：

~~~math
\mathrm{ClaimSupport}
=
\frac{\sum_{i=1}^{m}\omega_i
\mathbf{1}[\mathrm{claim}_i\ \mathrm{supported}]}
{\sum_{i=1}^{m}\omega_i}
~~~

其中 m 是断言数量，\omega_i 是业务重要性权重。当没有可核查断言或 \sum_i\omega_i=0 时，ClaimSupport 未定义，应报告无可评估证据。它是教学和工程分析指标，不是通用事实真值探测器；支持判断仍需要规则、检索、人工或可信外部资料。

### 10.4.7 工具与 Agent 评估

工具任务的最终文字可能看起来正确，但模型也许调用了错误工具、使用了越权参数或重复执行了退款。平台要记录完整轨迹：

~~~text
用户目标
  -> 模型计划或工具选择
  -> 参数解析
  -> 权限判定
  -> 工具返回
  -> 后续观察
  -> 最终答复
~~~

τ-bench 用真实业务域中的工具交互来研究工具使用代理，SWE-bench 通过真实 GitHub issue 和代码仓库测试代码修复能力。这类 benchmark 的价值在于把评估从单轮文本扩大到环境和任务结果，但它们仍然有特定任务分布、执行环境和评分规则，不能替代企业自己的权限与副作用测试。资料见 [τ-bench](https://arxiv.org/abs/2406.12045) 和 [SWE-bench](https://arxiv.org/abs/2310.06770)。

工具评估至少分解成：

~~~math
\mathrm{TaskSuccess}
=
\mathbf{1}[\mathrm{GoalReached}]
\cdot
\mathbf{1}[\mathrm{NoCriticalViolation}]
~~~

一个任务即使最终达成目标，只要未经授权地修改了数据，也不应算成功。对多个样本可进一步统计目标成功率、严重违规率、无效调用率和重复副作用率。

## 10.5 公开 benchmark 怎样进入平台

### 10.5.1 benchmark 是测量协议，不是能力总表

MMLU、BIG-bench、HumanEval、HELM、MT-Bench、SWE-bench 等项目各自覆盖不同任务和评估方式。BIG-bench 是任务集合与协作框架，[lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness) 是可复用的评估实现框架；它们便于复现实验，却不自动保证任务标签、提示模板和执行环境适合衡川。

平台导入公开 benchmark 时要保存：

- 原始版本和许可证。
- 官方任务定义与本地适配差异。
- prompt 模板、few-shot 数量和停止条件。
- 依赖的 tokenizer、语言和执行环境。
- 原始指标定义与本地二次指标。
- 已知的污染、泄露和覆盖限制。

如果本地改了答案解析器或移除了无法运行的样本，报告必须显示“本地协议”，不能把结果伪装成官方排行榜分数。

### 10.5.2 多维评估框架的意义

HELM 的重要启发不是“再找一个更大的总榜”，而是把场景、指标和证据组织在一起。对于衡川，可能需要同时观察：

- 正确性和完整性。
- 证据支持和引用准确性。
- 工具任务完成率。
- 过度拒答和应拒未拒。
- 延迟、token 消耗和单位成本。
- 不同用户群体和语言切片的差异。

把这些维度放在一个报告里，仍不意味着它们可以被无损压成一个数字。

### 10.5.3 公开套件的三个边界

第一，覆盖边界。一个数据集没有出现的输入类型，不会因为总分高就自动被覆盖。

第二，时间边界。知识型样本可能已经过时；当前模型的知识和当前业务制度不是同一件事。

第三，生态边界。模型在公开题库上的风格适配可能很好，但在企业工具、权限、私有文档和长流程中表现不同。

平台把公开 benchmark 当作外部参照和回归信号，把业务样本当作决策证据，两者的用途不同。

## 10.6 运行器：把评估变成可靠的批处理系统

### 10.6.1 任务分片

一项评估通常包含 run、suite、slice、shard 和 sample 五层：

~~~text
Run: support-v12 与 support-v11 的发布比较
  Suite: release-2026-08
    Slice: refund / RAG / safety / general
      Shard: 样本分片 0001
        Sample: refund-00421
~~~

分片允许并行、重试和部分完成。报告服务不能看到几个 shard 完成就推断整个 run 完成；每一级都要有自己的状态和计数。

### 10.6.2 队列和公平性

发布比较、事故回归、研究实验和大规模探索会竞争同一组模型 endpoint 和 GPU。调度器需要考虑优先级、租户配额、deadline、最大并发、模型限流、裁判容量和人工审核吞吐。

只按优先级排序会让低优先级任务永久等待。可以使用老化时间提升等待任务的有效优先级：

~~~math
\mathrm{EffectivePriority}
=
\mathrm{BasePriority}
+\alpha\cdot\mathrm{WaitingSeconds}
~~~

\alpha 是教学用的老化系数。真实系统还要加入租户配额和资源类型，避免一个大任务凭等待时间占满所有 GPU。

### 10.6.3 取消和部分结果

用户取消 run 后，尚未领取的样本可以直接取消，正在进行的请求要向模型服务发送取消信号，已经完成的结果应保留并标记为 partial。若工具调用已经产生副作用，取消只影响后续步骤，不能假装整个任务回滚。

报告要显示：

- 已完成和已评分的样本。
- 未运行、取消、重试和未知样本。
- 分数是否基于全量或部分数据。
- 取消前已经消耗的 token、GPU 和人工成本。

这样用户不会把“剩余样本没有失败”误读成“剩余样本都通过”。

### 10.6.4 并发容量

如果单条样本的平均处理时间为 T 秒，worker 并发数为 C，理想吞吐近似为：

~~~math
\lambda_{\mathrm{ideal}}
\approx
\frac{C}{T}
~~~

这里要求 T>0，且 C 表示同时可工作的有效并发数。实际吞吐还受模型服务限流、批处理效率、网络、裁判模型和对象存储影响。若每条样本平均 3 秒、并发 200，理想值约为 66.7 条/秒；这不是 SLA，因为尾延迟和失败重试会降低有效吞吐。

### 10.6.5 缓存

相同目标、相同样本、相同运行配置和确定性生成可以复用原始输出；但缓存键至少应包含：

~~~math
\mathrm{CacheKey}
=
H(\mathrm{TargetRevision}
\Vert
\mathrm{SampleRevision}
\Vert
\mathrm{PromptRevision}
\Vert
\mathrm{DecodeConfig}
\Vert
\mathrm{RuntimeRevision})
~~~

如果只用输入文本做键，prompt、工具 schema 或模型版本变了仍会命中旧答案，评估结果会静默错误。对随机生成的任务，缓存策略要明确是复用一次轨迹，还是重新采样后估计分布。

## 10.7 LLM-as-a-judge：有用的仪器，不是事实仲裁者

### 10.7.1 单答案打分与成对比较

LLM 裁判可以按 rubric 判断一个回答，也可以比较 candidate 和 baseline 哪个更好。成对比较往往更容易校准，因为“哪个更好”比“应该是 3.7 还是 4.1 分”更明确；但它仍然可能受到答案顺序、长度、风格和裁判模型偏好的影响。

Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena 研究了自动裁判与人工偏好之间的关系，也讨论了位置偏差和模型偏差。论文入口为 [Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)。这项工作支持“裁判需要校准”的工程结论，不支持把裁判分数当成无误差真值。

### 10.7.2 Rubric 要写成可核查问题

差的 rubric 是：“回答是否优秀？”

较好的客服事实性 rubric 是：

1. 回答是否正确识别了用户问题中的对象和条件？
2. 每个关键断言是否有给定证据支持？
3. 是否把尚未核验的状态说成已经完成？
4. 是否在制度冲突时使用了有效版本？
5. 是否包含会导致用户误操作的高风险表述？

裁判输出不仅要有分数，还要要求引用回答中的证据片段和失败标签。若裁判只能给一段漂亮解释，却无法指出哪一句违反了哪条规则，解释本身的可用性很低。

### 10.7.3 降低顺序偏差

设同一对答案交换顺序后，裁判选择“当前位置上的第一个答案”的概率分别为 p_1 和 p_2。若裁判只偏好某个答案，交换顺序后这两个概率会大致互补；若裁判偏好位置，两个概率会一起偏高或一起偏低。因此，一个简单的位置偏差估计是：

~~~math
\mathrm{PositionBias}
=
\frac{|p_1+p_2-1|}{2}
~~~

这不是完整的偏差统计量，且还需要报告样本量和置信区间；它能提醒平台做 A/B 顺序交换。对重要样本，可以在多次判断中随机化位置并记录裁判版本，而不是永远让 candidate 出现在左侧。若想测量某个答案本身的偏好，应另行比较交换前后的同一答案胜率，不能把它与位置偏差混为一谈。

### 10.7.4 与人工 gold 的校准

平台从高覆盖样本中抽取一部分交给专家，形成时间上稳定的校准集。对二分类判断，可以计算裁判与人工标签的一致率、精确率、召回率；对成对偏好，可以比较方向一致率和置信区间。

若裁判在高风险样本上经常漏掉“不当承诺”，就算它在普通写作上与人工高度一致，也不能把它用于安全发布结论。校准必须按 slice 分层。

### 10.7.5 多裁判不是自动正确

多个裁判投票可以降低单模型偶然错误，但若它们共享同一偏差，投票只会让偏差更稳定。更好的做法是：

- 使用不同模型或不同提示词作为互补证据。
- 把人工校准样本混入持续监控。
- 对冲突样本进行人工仲裁。
- 记录裁判的拒答、无证据判断和不可解析输出。
- 对裁判模型升级做回放比较。

裁判分数的变化可能来自被测模型，也可能来自裁判模型。二者必须在目标清单里分开版本化。

## 10.8 人工评估：把主观判断变成可审计流程

### 10.8.1 人工评估适合处理什么

人工评估适合开放式质量、复杂业务口径、边界安全判断、品牌语气、证据充分性和自动评估低置信样本。它不应被当作“最后随便看一眼”，而应是有任务说明、版本和质量控制的测量步骤。

人工不是天然真理。评审员也可能误读上下文、受答案顺序影响、偏好更长文字、疲劳或照抄前一个判断。因此平台要记录评审员身份的受控摘要、时间、rubric 版本和证据字段，同时避免暴露不必要的个人信息。

### 10.8.2 标注规范

规范至少要说明：

- 事实错误、遗漏和无关内容的区别。
- 过度拒答与合理拒答的区别。
- 不确定时是否允许回答“需要核验”。
- 多轮对话中哪些消息属于有效上下文。
- RAG 任务是否必须引用证据。
- 工具任务中什么算目标完成，什么算严重违规。
- 两个答案都可接受时如何标记 tie。
- 评审员无法判断时如何提交 unknown。

规范应该提供正例、反例和边界例。只有一句“选择更好的回答”，不同评审员会把自己的偏好带入标签。

### 10.8.3 盲评和随机化

人工比较时隐藏模型名称、版本、生成时间和答案来源，减少品牌与顺序偏见。A/B 顺序随机化，必要时同一条样本交给多个评审员。

如果业务要求评审员看到来源，例如核验专家制度答案，那么“盲评”不能强行套用；此时应记录哪些上下文被展示，并在分析中承认它带来的条件。

### 10.8.4 一致性与仲裁

对两个评审员的分类标签，可用 Cohen's kappa 作为粗略一致性指标：

~~~math
\kappa
=
\frac{p_o-p_e}{1-p_e}
~~~

p_o 是观察到的一致率，p_e 是按边际分布计算的偶然一致率，且只有在 p_e<1 时该表达式才有定义。类别极不平衡时，kappa 可能被误读；因此报告同时展示原始一致率、各类别数量和混淆矩阵。

一致性低不一定说明评审员差，也可能说明 rubric 不清楚、样本过于模糊或任务本身没有稳定答案。平台要把分歧样本送到专家仲裁，并统计分歧原因，用来修改规范。

### 10.8.5 评审成本和抽样

人工预算有限时，不要只随机抽样。可以按风险、裁判不确定性、模型差异、历史错误类型和业务流量分层抽样：

~~~math
\mathrm{ReviewPriority}
=
\alpha\cdot\mathrm{Risk}
+\beta\cdot(1-\mathrm{JudgeConfidence})
+\gamma\cdot|\Delta_{\mathrm{candidate-baseline}}|
+\delta\cdot\mathrm{Novelty}
~~~

这个分数只是排序工具，不是质量真值。高优先级样本应获得更多人工证据，但低优先级样本仍要保留随机抽样，避免系统只看到已知问题。

## 10.9 统计比较：差一点，可能只是噪声

### 10.9.1 用配对样本比较模型

若 candidate 和 baseline 在同一批样本上运行，先为每条样本定义差值：

~~~math
d_i=s_i^{(\mathrm{candidate})}-s_i^{(\mathrm{baseline})}
~~~

然后计算平均差：

~~~math
\bar{d}
=
\frac{1}{n}\sum_{i=1}^{n}d_i
~~~

配对比较比“两个独立平均分相减”保留了样本难度信息。一个很难的样本让两个模型都失败，不应被误解为某个模型独立变差。

### 10.9.2 置信区间

对 n 个同时拥有 candidate 和 baseline 结果的有效配对差值 d_i 做配对 bootstrap：从这些差值中有放回抽取 n 个，重复 B 次，得到 \bar{d}^{(b)} 的经验分布，再取 2.5% 和 97.5% 分位数作为近似 95% 区间。若 n=0，没有可比较的配对样本，区间未定义；缺失样本不能悄悄当成 0。

~~~math
\mathrm{CI}_{95\%}
=
\left[
Q_{0.025}\left(\bar{d}^{(b)}\right),
Q_{0.975}\left(\bar{d}^{(b)}\right)
\right]
~~~

这是教学性的 bootstrap 形式。真实报告要记录随机种子、重复次数、抽样单位和缺失样本处理。SciPy 提供了可复用的 bootstrap 实现，文档入口为 [scipy.stats.bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)。

区间跨过 0 时，不能简单说“没有任何差异”；更准确的说法是当前样本量和噪声下，方向证据不足。区间完全在 0 上方，也不代表差异具有业务价值，还要看差异大小、成本和风险。

### 10.9.3 随机生成的重复运行

对温度大于 0 的模型，单次输出只是一个样本。若同一问题重复生成，平台可以估计：

- 通过率均值。
- 输出方差或通过率置信区间。
- 最坏或高风险失败概率。
- 重复生成是否带来新的错误类型。

不能因为某次随机输出通过就把该样本永久标为通过。对安全和工具副作用任务，应采用固定 seed 的回归运行加少量随机压力运行两层策略。

### 10.9.4 多指标和多切片

如果同时查看 30 个指标和 40 个切片，总会有一些数字偶然变好或变坏。平台要在运行前声明主要指标、次要指标和探索性指标，并在报告中区分确认性结论和探索性发现。

“总体提升 1%，安全下降 0.2%”也不能脱离样本数量和严重度解释。一个高危失败可能比许多低风险格式问题更重要。

## 10.10 报告：让人能看懂证据

### 10.10.1 报告的层次

衡川的一份发布比较报告按四层组织：

第一层是运行卡片：目标、baseline、数据 revision、评估器 revision、时间、成本、完成率和缺失原因。

第二层是总体和切片统计：分数、样本数、置信区间、样本权重、延迟和 token。

第三层是失败分析：错误标签、代表样例、旧版本输出、新版本输出、证据、历史趋势和人工备注。

第四层是行动建议：可以扩大流量、需要修复后重跑、只适合低风险场景，或证据不足暂不下结论。建议要指向具体指标和样例，不能只写一句“综合考虑后发布”。

### 10.10.2 不确定性和缺失

报告中同时出现以下字段：

~~~json
{
  "metric": "claim_support",
  "candidate": {
    "estimate": 0.782,
    "ci95": [0.754, 0.809],
    "n": 1200
  },
  "baseline": {
    "estimate": 0.761,
    "ci95": [0.733, 0.788],
    "n": 1200
  },
  "paired_delta": 0.021,
  "paired_ci95": [-0.004, 0.046],
  "missing": 17,
  "missing_reason": {
    "model_timeout": 9,
    "judge_unknown": 8
  }
}
~~~

这份结果不能被压成“提升 2.1%”。更准确的结论是：点估计提升，但配对区间仍包含无提升，且存在 17 条未完成样本，需要分析缺失是否与困难样本相关。

### 10.10.3 失败样例优先于漂亮图表

折线图适合观察趋势，雷达图适合展示维度布局，但它们都不应替代样例。报告至少能下钻到：

- 输入和上下文。
- 检索候选及版本。
- 模型原始输出。
- 工具轨迹和权限判断。
- 评估器证据。
- 人工标签和仲裁。
- 同一输入的历史版本表现。

如果因隐私不能展示原文，报告提供受控访问、脱敏摘要和不可逆标识，而不是完全删掉失败证据。

### 10.10.4 多目标决策

有时 candidate 提升质量但增加延迟和成本。可以把决策写成约束优化，而不是拍脑袋总分：

~~~math
\max_{v}
\quad
Q(v)
\qquad
\mathrm{subject\ to}
\quad
R(v)\le R_{\max},
\quad
L_{p95}(v)\le L_{\max},
\quad
C_{\mathrm{task}}(v)\le C_{\max}
~~~

Q 是主要质量目标，R 是风险，L_p95 是尾延迟，C_task 是单位成功任务成本。约束值来自业务和风险政策，不是所有模型和行业通用的固定数字。

### 10.10.5 发布条件应可解释

衡川可以把条件分三类：

- 关键安全或隐私错误：出现一个就需要人工调查和停止扩大高风险流量。
- 关键业务回归：退款、订单状态和制度有效期等样例按风险等级处理。
- 一般质量与效率：在置信区间、成本和线上信号一起看。

这不是把所有问题转化为一条神秘红线，而是明确什么问题为什么重要、由谁处理、需要什么证据才能继续。

## 10.11 离线和线上：两个不同的世界

### 10.11.1 离线评估回答什么

离线运行适合：

- 在固定数据上比较版本。
- 快速发现已知回归。
- 运行高风险测试而不影响用户。
- 对模型、prompt、索引和工具策略做受控实验。

它的优点是可重复、可回放、可分层；缺点是样本可能陈旧，用户行为和服务负载被简化，且模型团队可能长期针对固定套件优化。

### 10.11.2 线上评估回答什么

线上观察：

- 任务完成率和用户追问率。
- 人工客服转接率。
- 用户反馈和投诉。
- 实际 P50、P95 延迟和错误率。
- 工具失败、取消和重复提交。
- 不同租户、语言、设备和流量切片的差异。

线上指标受混杂因素影响。活动期间请求类型变化、客服政策变化或检索索引更新，都可能使指标变化。实验平台要记录流量分配、实验时间、请求分布和外部事件。

### 10.11.3 A/B 与灰度的边界

A/B 实验可以比较两个版本在真实流量上的行为，但不能把高风险功能无保护地交给实验。对退款工具，先在模拟器和只读权限下验证，再给小规模、可回滚的低金额场景，最后才考虑更广泛的流量。

灰度并不自动等于安全。必须有实时监控、停止策略、权限范围、人工接管和审计记录。线上实验的“成功”还要包含没有不可接受副作用。

### 10.11.4 线上样本回流

线上失败样本进入离线集前需要：

1. 去除不必要的个人信息。
2. 保留足以复现错误的上下文和工具状态。
3. 由专家确认标签和风险。
4. 标明样本来源、日期和数据分布。
5. 作为新版本追加或修订，而不是覆盖历史标签。

回流会改变数据分布。若把所有线上问题都塞进一个回归集，总分会被少数事故类型主导；因此保留原始分层和权重。

## 10.12 安全、隐私与评估完整性

### 10.12.1 评估平台本身也是高价值系统

平台存储测试集、内部制度、用户输入、模型失败输出和安全攻击样例。它的权限不能因为“只是评估”而放松。

核心措施包括：

- 数据集、目标清单和报告按租户与项目隔离。
- 线上样本进入评估前做最小化和脱敏。
- 隐藏集读取、报告下载和结果导出写审计日志。
- 代码和浏览器评估在沙箱中运行。
- worker 只获得当前任务需要的字段和工具权限。
- 原始内容与分析指标分层存储。
- 设定保留、删除和加密策略。

### 10.12.2 安全评估的威胁模型

安全测试要先写明攻击者能看到什么、能调用什么、目标是什么。输入注入、敏感信息回显、工具越权、错误拒答和不当承诺都应有不同样本和严重度。

一个粗略的风险分数可以写为：

~~~math
\mathrm{Risk}
=
\sum_{j=1}^{m}
\mathrm{Probability}_j
\cdot
\mathrm{Impact}_j
\cdot
\mathrm{Exposure}_j
~~~

这是风险排序模型，不是实际概率的精确估计。它帮助团队区分“偶发格式错误”和“可重复的未经授权退款”。

NIST AI RMF 提供了治理、测量和管理 AI 风险的框架，入口为 [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)。它不是衡川的具体指标表，平台需要把风险框架翻译成自己的威胁模型、样本、严重度、责任人和证据。

### 10.12.3 评估完整性

评估结果可能被无意或有意地操纵：

- 只挑选有利样本。
- 把失败样本标成执行错误并从分母移除。
- 运行时偷偷改变 prompt 或解码参数。
- 用训练过的公开测试集代替新样本。
- 更换裁判模型却沿用旧分数名。
- 对高风险失败不保存原始输出。

平台通过不可变数据版本、固定发布套件、完整分母、失败原因分类、审计日志和受控重跑来降低这些风险。数据异常不应被“清洗”到报告之外，而应作为结果质量的一部分展示。

## 10.13 架构：把证据链落实为服务

### 10.13.1 高层组件

衡川评估平台可以拆为：

~~~text
评估 API / CI 触发器
        |
        v
实验与目标服务 -------- 目标注册表
        |                     |
        v                     v
套件与数据服务 -------- 数据对象存储
        |
        v
任务编排器 ---- 队列 ---- 运行 worker ---- 模型/工具适配器
                                      |
                                      v
                              原始输出与轨迹存储
                                      |
               +----------------------+------------------+
               |                                         |
               v                                         v
        确定性评估器 / 执行器                     裁判模型服务
               |                                         |
               +----------------------+------------------+
                                      v
                                人工评审服务
                                      |
                                      v
                          指标仓库 / 报告 / 审计
                                      |
                                      v
                              发布与线上实验系统
~~~

关键不是组件数量，而是每个组件保存的证据边界。模型适配器负责调用和原始响应，不应该偷偷改写评估分数；评估器负责评分和证据，不应该修改被测目标；报告服务负责聚合，不应该丢失分母和缺失原因。

### 10.13.2 元数据与对象分离

关系数据库适合存目标、run、样本状态、指标索引和权限；对象存储适合存长文本、音视频、代码、原始响应和评审附件；列式分析库适合存样本级指标与趋势。

所有对象通过内容摘要、revision 和访问策略连接。删除一个项目时，不能只删数据库行而留下对象存储和缓存中的原始对话。

### 10.13.3 事件和状态

任务状态变化写入事件：

~~~json
{
  "event_id": "evt-8931",
  "run_id": "run-20260811-003",
  "sample_id": "refund-00421",
  "type": "evaluation_scored",
  "occurred_at": "2026-08-11T09:30:12Z",
  "producer_revision": "judge-service-1.4.2",
  "payload": {
    "evaluator_revision": "refund-policy-2026-08-05",
    "status": "scored",
    "score": 0.0
  }
}
~~~

事件溯源有利于重建过程，但事件本身也可能包含敏感输出。只保留事件不等于可以无限期保存所有内容；事件 payload 应按敏感等级分层，删除策略要覆盖派生索引。

### 10.13.4 接口契约

创建 run 的接口需要引用不可变 revision：

~~~http
POST /evaluation-runs
Content-Type: application/json

{
  "target_revision": "target-support-v12-9f...",
  "baseline_revision": "target-support-v11-31...",
  "suite_revision": "release-suite-2026-08-11",
  "execution": {
    "seed": 17,
    "max_concurrency": 200,
    "repeat": 2
  },
  "budget": {
    "max_model_tokens": 120000000,
    "max_judge_calls": 8000
  }
}
~~~

返回值应包含 run revision、状态、已完成样本、未知样本和估计剩余工作。不能只返回一个 status=running，因为使用者需要知道是否正在大量重试或因裁判不可用而停滞。

## 10.14 容量和成本：算清楚评估的账

### 10.14.1 一个教学规模

假设每天有 24 个待比较目标，每个目标运行 4 个套件，每个套件 4,000 条样本，每条样本平均输入 1,200 token、输出 300 token。每日样本数为：

~~~math
N_{\mathrm{sample}}
=
24\cdot4\cdot4000
=
384000
~~~

每日被测模型 token 量约为：

~~~math
T_{\mathrm{model}}
=
384000\cdot(1200+300)
=
576000000
~~~

如果 30% 样本进入一次裁判，裁判平均消耗 1,000 token，则裁判 token 量约为：

~~~math
T_{\mathrm{judge}}
=
384000\cdot0.3\cdot1000
=
115200000
~~~

这些是教学估算，不是衡川的实测。真实数值还要加入重试、重复生成、上下文长度、缓存命中和多裁判投票。

### 10.14.2 成本分解

单位评估成本可拆为：

~~~math
C_{\mathrm{run}}
=
C_{\mathrm{model}}
+C_{\mathrm{judge}}
+C_{\mathrm{compute}}
+C_{\mathrm{storage}}
+C_{\mathrm{human}}
+C_{\mathrm{network}}
~~~

如果只看 GPU 账单，可能忽略人工仲裁和裁判模型；如果只看总成本，又不知道哪种优化有效。平台记录每个 run、suite、slice 和 sample 的成本归属。

对工具任务，单位成功成本更有解释力：

~~~math
C_{\mathrm{success}}
=
\frac{C_{\mathrm{run}}}
{N_{\mathrm{successful\ tasks}}}
~~~

当 N_successful_tasks=0 时，单位成功成本没有定义，应报告“无成功任务”以及总成本、任务数、失败数和未知数，而不是用 1 替代分母。一个模型每次调用更便宜，但成功率下降，单位成功成本可能更高。这个指标同样依赖成功定义，不能绕开任务质量和风险。

### 10.14.3 人工吞吐

若每条人工样本平均需要 t_r 分钟，评审员数量为 q，每日有效工作时间为 h 小时，理论日吞吐近似为：

~~~math
N_{\mathrm{human/day}}
\approx
\frac{60h q}{t_r}
\cdot
\rho
~~~

\rho 是考虑休息、培训、仲裁和任务切换后的有效系数。它通常小于 1。用理论吞吐直接承诺 SLA，会在高峰期制造积压。

### 10.14.4 分层预算

预算策略可以按风险和变更范围分层：

- 小改动先跑 smoke 和相关回归。
- 关键模型变更运行发布套件。
- 公开 benchmark 和大规模探索放到低峰资源。
- 高风险样本优先获得人工和多次随机运行。
- 预算耗尽时停止新样本，保留已完成结果并标明部分完成。

部分完成的报告仍然有价值，但必须明确分母和停止原因。

## 10.15 一个完整案例：v12 为什么不能直接扩大流量

### 10.15.1 初始结果

衡川用相同的 release suite 比较 v11 和 v12，候选结果如下：

| 维度 | v11 | v12 | 配对变化 |
| --- | ---: | ---: | ---: |
| 制度事实支持率 | 0.761 | 0.782 | +0.021 |
| 工具目标完成率 | 0.684 | 0.711 | +0.027 |
| 过度拒答率 | 0.081 | 0.064 | -0.017 |
| P95 首 token 延迟 | 1.8 s | 2.0 s | +11.1% |
| 单位任务成本 | 1.00 | 1.09 | +9.0% |

表面看 v12 更好，但事实支持率的配对 95% 区间为 [-0.004, 0.046]，不能把 +2.1 个百分点写成已经确定的普遍提升。工具完成率的提升主要来自低风险查询；在退款切片中，v12 出现两条未经订单核验就承诺退款的样本。

### 10.15.2 追溯一条失败

失败样本的证据链如下：

~~~text
样本 refund-00421
  -> 旧制度与新制度同时被检索
  -> reranker 把旧制度排在第一位
  -> prompt 没有要求输出制度生效日期
  -> 模型生成“已为你完成退款”
  -> 工具策略把自然语言承诺误判为只读回答
  -> 人工检查发现未调用 lookup_order
~~~

如果只看最终文本质量，这条样本可能被裁判模型判成“有帮助”；加入工具轨迹和风险 rubric 后，它应被标为严重失败。

### 10.15.3 修复实验

团队做三个独立变更：

1. 重新排序制度片段并注入生效日期。
2. 把 lookup_order 设为退款前的必需步骤。
3. 更新裁判 rubric，要求检查未经核验的承诺。

每项变更分别与 v12 基线比较，并保留组合版本。结果显示制度排序修复了大部分引用问题，工具策略修复了副作用风险，裁判 rubric 只改变了测量敏感度。三者不能被统称为“模型能力提升”。

### 10.15.4 发布动作

最终决定不是“分数过线”四个字，而是：

- 普通制度问答可进入低风险灰度。
- 退款工具保持只读模拟器，待高风险样本由专家复核。
- P95 延迟和成本在预算范围内继续观察。
- 每日把真实冲突制度样本脱敏后加入回归集。
- 下一次比较必须同时报告检索 revision、工具策略 revision 和裁判 revision。

这个决定把质量、风险、成本和证据强度放在同一张图上，且每一项都可以回放。

## 10.16 故障复盘：高分为什么仍然失败

### 10.16.1 只看平均分

一个团队把 95% 的普通问答和 5% 的高风险操作混在一起，平均分从 0.88 上升到 0.90，于是扩大流量。上线后发现高风险切片从 0.94 降到 0.82。

根因不是模型一定变坏，而是聚合方式掩盖了切片。修复包括固定风险权重、显示每个切片的分母、单独统计严重错误和保留高风险样例。

### 10.16.2 把执行错误当作模型失败

某次全量评估中，模型 endpoint 在高峰期超时，平台把未返回样本从分母移除，分数反而上涨。真正的问题是执行可用性下降。

修复后，model_status、evaluator_status 和 sample_inclusion 分开保存。缺失样本不自动计为通过，也不自动计为失败；报告展示缺失机制并重新运行。

### 10.16.3 裁判升级导致历史趋势断裂

裁判模型从 judge-v2 升到 judge-v3，新的评分更严格。团队看到所有模型分数下降，以为被测模型同时退化。

修复是把裁判版本视为测量仪器版本，先用历史输出做回放校准，再决定是否建立转换关系。没有可靠转换关系时，趋势图应分段显示，不能直接连线。

### 10.16.4 线上样本泄露隐私

为了复现客服错误，工程师把完整用户对话和身份证号复制到共享评估项目。即使项目内部使用，这也扩大了数据暴露面。

正确做法是最小化样本、脱敏、限制字段、审计访问，并保留能复现错误的结构化上下文。评估质量不能成为绕过隐私责任的理由。

## 10.17 可观测性：先知道评估系统是否可信

### 10.17.1 平台自身的指标

评估平台需要监控：

- run 创建到首个样本开始的排队时间。
- sample 成功、重试、未知和终止错误率。
- 模型 endpoint 的 P50、P95、超时和限流。
- evaluator 解析失败、裁判不可用和 unknown 比例。
- 缓存命中率和错误命中率。
- 人工评审积压、平均处理时间和分歧率。
- 每个 suite 的 token、GPU、裁判和人工成本。
- 报告生成时间和数据新鲜度。

OpenTelemetry 提供 traces、metrics 和 logs 的可观测性规范与工具入口，见 [OpenTelemetry Documentation](https://opentelemetry.io/docs/)。评估平台可以用一个 trace 关联 run、shard、sample、模型调用、工具调用和评估器，但 trace 中不应默认放入完整敏感文本。

### 10.17.2 结果异常

以下异常值得自动提醒：

- 某个 slice 的完成率明显低于其他 slice。
- 失败样本几乎都来自某个租户或某种长度。
- judge unknown 在新版本突然升高。
- 评估分数突然完美，但原始输出数量下降。
- 缓存命中率异常升高而目标 revision 频繁变化。
- 人工评审用时极短且标签分布异常集中。

告警不是对模型质量的结论，而是对测量过程的疑问。先确认仪器工作正常，再解释分数。

## 10.18 从实验到代码：一个最小的配对审计

下面的纯 Python 示例只演示如何保留样本级差值、计算均值和按风险切片汇总。数据是教学合成数据，不代表任何真实模型结论。

~~~python
from statistics import mean


rows = [
    {"id": "a", "slice": "general", "risk": 1, "baseline": 1, "candidate": 1},
    {"id": "b", "slice": "general", "risk": 1, "baseline": 0, "candidate": 1},
    {"id": "c", "slice": "retrieval", "risk": 2, "baseline": 1, "candidate": 1},
    {"id": "d", "slice": "retrieval", "risk": 2, "baseline": 1, "candidate": 0},
    {"id": "e", "slice": "refund", "risk": 3, "baseline": 1, "candidate": 0},
    {"id": "f", "slice": "refund", "risk": 3, "baseline": 0, "candidate": 1},
]


for row in rows:
    row["delta"] = row["candidate"] - row["baseline"]


def average(items, field):
    values = [item[field] for item in items]
    return mean(values) if values else None


overall_delta = average(rows, "delta")
by_slice = {}
for row in rows:
    by_slice.setdefault(row["slice"], []).append(row)


print(f"paired_delta={overall_delta:.3f}")
for slice_name, items in sorted(by_slice.items()):
    candidate = average(items, "candidate")
    baseline = average(items, "baseline")
    high_risk_failures = sum(
        item["risk"] >= 3 and item["candidate"] == 0
        for item in items
    )
    print(
        f"{slice_name}: baseline={baseline:.3f} "
        f"candidate={candidate:.3f} "
        f"high_risk_failures={high_risk_failures}"
    )
~~~

预期输出：

~~~text
paired_delta=0.000
general: baseline=0.500 candidate=1.000 high_risk_failures=0
refund: baseline=0.500 candidate=0.500 high_risk_failures=1
retrieval: baseline=1.000 candidate=0.500 high_risk_failures=0
~~~

整体差值为零，但切片揭示了候选模型在普通样本提升、检索样本退化、退款样本存在高风险失败。这个例子说明聚合统计必须保留样本切片；它没有实现真实的置信区间、权限判断或裁判校准，不能被直接当作生产评估平台。

## 10.19 资料等级与证据边界

本章使用的资料按用途区分：

- 原始论文：HELM、LLM-as-a-judge、SWE-bench、τ-bench，用于理解研究问题、实验设计和已报告的结果。
- 公开 benchmark 或框架：BIG-bench、lm-evaluation-harness，用于理解任务组织、复现入口和实现约束。
- 官方治理框架：NIST AI RMF，用于风险治理语言和管理流程，不直接给出业务阈值。
- 官方工程文档：OpenTelemetry，用于观测接口和信号组织，不证明评估指标有效。
- 统计库文档：SciPy bootstrap，用于实现重采样工具，不替代统计设计。

教学公式、衡川数字和故障样例属于本章的示例或合成 trace。它们帮助说明机制，不是论文结果，也不是对任何当前模型的性能宣称。

一个新模型或新产品声称“支持更长上下文”“在某 benchmark 上领先”时，平台仍应追问：评估对象是什么，数据和 prompt 是否公开，是否存在污染，指标由谁计算，是否报告了方差和失败样例，运行成本和线上分布是否相同。模型名称本身不是证据。

## 10.20 章节回顾与实践

评估平台最终要维护的不是一张排行榜，而是从质量主张到可复核证据的路径。对衡川而言，v12 是否适合扩大流量，取决于目标清单、制度版本、检索和工具轨迹、样本切片、统计区间、风险严重度、成本和线上反馈的共同判断。

读者可以用下面的实践题检查自己是否真正掌握了这条链：

1. 设计一个 EvaluationTarget，分别表示纯模型、RAG 应用和带退款工具的助手，并说明三者哪些字段不同。
2. 给一个包含普通咨询、隐私请求和退款操作的数据集设计切片与权重，解释为什么不能只报告加权平均分。
3. 为一个 LLM 裁判写出五条可核查 rubric，并设计顺序交换与人工校准实验。
4. 给出模型调用超时、裁判不可用和工具结果未知时的三种状态转换，说明哪些状态可以重试。
5. 构造一个 candidate 总分提升但高风险切片退化的报告，写出分数、区间、失败样例和发布动作。
6. 把一次线上失败脱敏后回流为回归样本，列出需要保留的上下文和需要删除的个人信息。

如果这些问题只能回答“加几个 benchmark、算平均分、低于阈值就不发布”，说明评估仍停留在结果展示层；真正的平台设计要能解释每个数字从哪里来、缺了什么、能推出什么，以及下一步应该怎样获得更强证据。
