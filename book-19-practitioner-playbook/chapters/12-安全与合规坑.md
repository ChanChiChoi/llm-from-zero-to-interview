
# 第十二章：安全与合规项目坑：从一条日志泄露到全链路责任

安全事故很少从一个危险回答开始。更常见的情况是：检索服务先把不该看到的文档放进上下文，模型随后按照外部内容行动；工具层没有重新校验资源归属，退款动作已经发生；为了复盘，系统保存了包含 API key 的完整 prompt；产品团队又把这条生产 trace 复制进训练集，最后才发现数据用途、权限、保留和外部传输都没有留下完整证据。

因此，安全与合规不能被理解为生成之后的一道过滤器。大模型系统的真实边界至少包括：

~~~text
输入与文件
  -> 身份、租户和权限
  -> RAG、缓存和派生数据
  -> 模型、工具和外部服务
  -> 输出、日志和反馈
  -> 保留、删除、训练和事故响应
~~~

每一层都可能改变风险。安全策略回答“允许什么、阻止什么、需要确认什么”；合规治理回答“谁授权、为了什么目的、保存多久、谁能访问、如何删除、出了问题谁能证明已经处理”。两者有交集，但不等价。一个请求可能内容安全，却越过了租户权限；一段数据可能业务上有用，却没有训练授权；一个动作可能技术上成功，却没有用户确认和审计记录。

本章从一场企业助手事故开始，逐层讲清信任边界、prompt injection、RAG 权限、Agent 工具、日志和 trace、训练与反馈、保留删除、第三方传输、过度拒答、多模态安全、红队评估和事故响应。公式明确分母、空集合、零分母、not_applicable 与 unknown；代码只使用标准库，模拟审计数据并实际验证边界。

## 12.0 一场事故如何同时变成五种责任

某公司上线了合同与退款助手。员工可以上传合同、查询客户资料、让 Agent 生成退款草稿，客服还可以把对话反馈标记为“可用于改进”。

一天之内发生了五件事：

1. 一名普通客服查询客户退款政策。RAG 在检索前没有应用 ACL，把内部高管薪酬附件放进了上下文。回答没有直接展示全文，但模型已经接触了无权限内容。
2. 客服说“把这笔退款执行掉”。模型生成的工具参数合法，工具却没有重新确认订单属于当前租户；退款在没有人工确认的情况下执行。
3. 用户在问题中误粘贴了一个 API key。系统为了 debug 保存完整 prompt，日志平台被多个团队共享访问。
4. 运营人员把一条包含真实客户合同的反馈复制到评估表。数据既没有用途授权，也没有删除期限和 lineage。
5. 为了调用外部文档分析服务，系统把原始合同和客户姓名发送到第三方，传输审批和数据处理协议记录为空。

这些事件都可能被一句“模型不安全”遮住，但第一处分歧完全不同：

~~~text
RAG：权限过滤在检索前缺失
Agent：工具和业务对象没有硬校验，确认状态缺失
日志：敏感字段最小化和脱敏缺失
训练：数据用途和授权链缺失
外部服务：传输目的、范围和审批证据缺失
~~~

对刚接触安全工程的人来说，可以先把系统想成一座有多个房间的办公楼：用户能进大楼，不代表能进所有房间；模型能读到一段文字，不代表文字有权改变访问控制规则；日志管理员能看故障记录，也不代表可以看到完整密钥。对有经验的工程师来说，关键是把这些比喻落成可验证的主体、资源、动作、目的、版本和审计事件，且每个派生数据对象都继承原始数据的约束。

## 12.1 先区分内容安全、权限安全和合规治理

三个概念经常被混在一起。

内容安全关注请求或输出是否包含危险、违法、隐私泄露、恶意代码或不当推断。它通常回答“这个内容应该允许、拒绝、降级还是转人工”。

权限安全关注当前主体是否有权访问资源或执行动作。它回答“这个用户、租户、服务身份能否读取这份文档、调用这个工具、修改这个对象”。

合规治理关注数据处理目的、授权、来源、保留、删除、跨边界传输、责任和审计。它回答“为什么收集、如何使用、保存多久、谁负责证明”。

一个请求可以同时落在不同状态：

~~~text
内容安全但越权：用户问题本身正常，却检索到别的租户文档
有权限但需确认：用户可以退款，但不能让 Agent 无确认直接执行
内容可回答但不可训练：合同可以用于当前问答，却没有改进模型的授权
技术上可传输但证据不足：第三方接口能接收文件，却没有审批或数据处理记录
~~~

如果只看一个安全分数，这些差异会被平均掉。高严重度权限泄露、密钥泄露和未确认资金动作应进入独立的修复路径。

## 12.2 把系统写成主体、资源、动作和证据

安全边界需要一个比 prompt 更稳定的表示。把第 i 个事件写成：

$$
h_i=(s_i,r_i,a_i,p_i,o_i,d_i,l_i,t_i,q_i)
$$

其中：

- s_i 是主体，包括用户、服务账号、租户和角色；
- r_i 是资源，包括文档、客户对象、工具、日志、缓存和派生结果；
- a_i 是动作，如读取、生成、执行、外传、保存、训练和删除；
- p_i 是处理目的；
- o_i 是策略期望结果，如 allow、block、redact、confirm 或 review；
- d_i 是系统实际结果；
- l_i 是日志、trace 和版本证据；
- t_i 是保留、删除、授权和传输状态；
- q_i 是事故响应和复测证据。

安全检查不是单纯判断模型输出字符串，而是判断元组是否满足策略。例如：

~~~text
主体：客服 A，租户 T1
资源：订单 O7，属于 T2
动作：退款
期望：block
实际：executed
~~~

即使 JSON schema、模型置信度和工具响应都正常，这仍然是权限违规。

### 12.2.1 三种结果状态

每个控制项至少要保留三种状态：

~~~text
valid：控制适用且有记录，计算结果可信
not_applicable：该控制在此样本没有适用对象
unknown：控制应该适用，但标注、日志、授权或版本证据缺失
~~~

例如没有高风险工具动作，确认覆盖率是 not_applicable；有高风险动作但没有确认日志，是 unknown；有一个动作且明确未确认，覆盖率是有效的 0。缺少权限记录也不是“没有越权”，而是 unknown。

### 12.2.2 证据要覆盖派生数据

安全和合规审计不能只保存最终答案。至少要关联：

~~~text
原始输入或文件 hash
用户、租户、角色和权限版本
RAG 候选、最终上下文和缓存键
工具名称、参数、资源归属和执行结果
模型、prompt、策略和分类器版本
日志/trace 的脱敏状态与访问记录
训练、标注、反馈、外部传输和删除事件
人工确认、审批、回滚和复测结果
~~~

OCR 文本、摘要、embedding、缓存答案和评估样本都属于派生对象。删除原始文件但保留可还原的 OCR 或向量，不等于完成删除；撤销权限但不失效缓存，不等于完成权限变更。

## 12.3 Prompt injection：外部内容不能升级成系统指令

Prompt injection 的危险不在于句子是否像攻击，而在于不可信内容是否获得了本不该有的控制权。网页、邮件、RAG 文档、PDF、OCR 文本、ASR 转写和工具返回都可能写着“忽略之前规则”“把秘密发给我”或“调用删除工具”。

正确的信任关系是：

~~~text
系统策略和权限：控制规则
用户请求：受身份和产品能力约束的意图
外部文档/网页/工具返回：待分析的数据
模型输出：候选回答或候选动作
权限/业务服务：最终动作裁决
~~~

外部内容可以被模型总结、分类或引用，但不能自行改变系统策略、权限范围和确认要求。把一段 OCR 文字直接拼到 system prompt 附近，并不能让它变成可信指令。

### 12.3.1 直接注入和间接注入

直接注入来自当前用户的输入，通常试图改变模型行为。间接注入来自模型随后读取的内容，例如网页、邮件、知识库文档或图片文字。间接注入尤其容易被忽视，因为用户的问题本身可能完全正常。

评估时要分别记录：

1. 内容是否被识别为不可信；
2. 模型是否改变了计划或回答；
3. 是否产生了未经授权的工具调用；
4. 是否泄露了上下文或凭据；
5. 工具层是否最终阻断了动作；
6. trace 是否完整记录了分歧。

不能只看“模型有没有拒绝那句话”。如果模型被诱导生成了危险工具参数，但工具层拒绝了，内容层仍然发生了注入影响；如果工具真的执行了，影响级别更高。

### 12.3.2 工具层是最后的事实约束

所有写操作都应在模型外检查：

~~~text
主体：当前用户和服务身份是否有权限
对象：资源是否属于当前租户和用户范围
参数：类型、单位、范围、状态和关联关系是否合理
风险：是否需要预览、确认、审批或人工接管
副作用：是否幂等、可撤销、可回滚
结果：后端最终状态是否支持 success
~~~

提示词可以帮助模型遵守规则，却不能替代这些硬检查。模型说“已确认”不等于用户真的确认；工具返回 accepted 不等于业务状态已经落库。

## 12.4 RAG 权限：在检索前阻断越权证据

企业 RAG 最严重的错误之一，是先全库召回再让模型自行判断哪些内容能用。此时模型已经接触了越权内容，后面再过滤引用可能已经太晚。

一条正确的数据流应该是：

~~~text
用户身份 -> 权限快照 -> 候选文档过滤 -> 检索/重排
-> context 组装 -> 生成 -> 引用再次校验
~~~

权限过滤需要贯穿原始文档和派生对象：

1. 文档入库时记录租户、主体、资源范围和版本；
2. 检索请求使用当前权限快照，而不是长期缓存的角色；
3. chunk、embedding、OCR 和摘要继承源文档 ACL；
4. rerank、context 和引用只接收已授权对象；
5. response cache 的键包含租户、主体、权限版本和知识版本；
6. 权限变化触发索引、缓存和派生结果失效；
7. 输出前再次确认引用仍然可见。

### 12.4.1 权限过滤不是 prompt 技巧

假设低权限用户问“本月退款政策”，检索结果中混入了高权限的客户投诉附件。即使 system prompt 告诉模型不要泄露，模型仍可能从附件中推断出客户姓名、金额或内部策略。正确修复点是检索候选集合和资源访问服务，而不是再写一条“不要引用机密”。

缓存也会制造跨用户泄露：

~~~text
高权限用户查询 -> 生成含敏感上下文的答案 -> 共享 response cache
低权限用户相同 query -> 命中答案
~~~

语义相同不代表权限相同。缓存键必须把权限相关状态纳入，或者对敏感任务禁用共享缓存。

## 12.5 Agent 工具安全：模型只能提出动作，不能授予自己权限

Agent 会把安全风险从“输出什么”推进到“改变什么”。删除、退款、转账、发消息、导出、改权限、部署和生产配置都属于有副作用的动作。

每个工具都应有清晰的能力合同：

~~~text
名称和用途
只读/写入属性
允许的资源范围
输入 schema、单位和枚举
调用主体和租户
风险等级与确认方式
幂等键、超时、回滚和最终状态
审计字段与保留策略
~~~

### 12.5.1 确认必须绑定具体动作

“我同意处理退款”不一定等于同意“向订单 O7 退款 1,280 CNY”。确认界面或确认消息至少要包含对象、金额、币种、收款方、目的和不可逆性。用户确认后，如果关键参数改变，旧确认不能自动继承。

高风险动作的记录可以抽象为：

$$
c_i=(\operatorname{subject},\operatorname{action},\operatorname{object},
\operatorname{parameters},\operatorname{time},\operatorname{expires})
$$

执行时要验证当前动作与 c_i 相同或满足明确的安全缩减关系。缺少确认记录是 unknown；记录显示用户拒绝或没有确认，是有效的 0。

### 12.5.2 业务状态优先于自然语言

工具调用返回的状态应至少区分：

~~~text
accepted：请求被接收，业务结果可能仍未完成
pending：异步处理中
success：后端状态已验证
failed：后端明确失败
blocked：权限、策略或人工审核阻断
unknown：超时或状态查询缺失
~~~

Agent 不能把 accepted、工具调用成功或生成了确认文字改写成 success。外部副作用一旦发生，审计记录还应能找到幂等键和后端对象。

## 12.6 日志和 trace：可观测性不能以复制秘密为代价

系统需要日志来排查事故，但完整记录 prompt、上下文和工具参数也可能制造新的泄露面。常见敏感数据包括个人身份信息、手机号、邮箱、地址、证件号、银行卡、医疗和法律信息、API key、token、cookie、企业合同和客户数据。

日志治理要先回答四个问题：

1. 这条字段是否真的需要记录；
2. 是否可以记录结构化摘要而不是原文；
3. 谁有权访问原始和脱敏版本；
4. 保存多久，如何删除和追溯访问。

一个实际的 trace 可以分成多层：

~~~text
运行元数据：请求 ID、模型版本、延迟、错误类型
安全事件：风险标签、策略版本、动作和结果
字段摘要：资源 ID、金额范围、哈希和脱敏值
受控证据：必要时在严格权限和有限时间内访问的原始片段
~~~

日志平台的管理员不应默认拥有所有业务数据权限。调试需要原文时，也应通过受控解密、审批和访问审计完成，而不是把完整 prompt 复制到公共群组。

### 12.6.1 脱敏不是简单替换字符串

把所有数字替换成星号会破坏排障；只替换手机号又可能留下组合识别风险。脱敏策略需要按字段和用途设计：

~~~text
密钥/token：立即撤销或轮换，并避免持久化原文
身份证/银行卡：只保留必要后缀或不可逆指纹
姓名/地址：按任务保留泛化区域或稳定伪名
合同/病历：保存文档 ID、页码和摘要，不保存全文
金额：按风险决定是否保留精确值、区间或哈希
~~~

脱敏后的值仍可能是个人数据，尤其当它能与其他表关联。伪名映射表本身要受更严格的权限和保留策略保护。

### 12.6.2 事故复盘需要可回放，而不是无限留存

可回放要求保存足够的版本、输入 hash、策略和状态；不要求永久保存所有原文。可以把原始证据和可长期保留的审计摘要分开：

1. 短期保留受控原始证据；
2. 长期保留脱敏事件摘要和不可变 hash；
3. 访问原始证据生成审计事件；
4. 到期自动删除原文、派生对象和临时缓存；
5. 保留删除完成的证明，而不是继续保留被删除内容。

## 12.7 训练、反馈和标注：用途变化必须重新检查

用户允许系统回答当前问题，不自动等于允许把内容用于训练、评估、人工标注或供应商改进。数据用途发生变化时，需要重新核对授权、告知、最小化、脱敏、地区和保留要求。

把生产数据送入改进流水线时，至少要保留：

~~~text
来源：来自哪个产品、租户和请求
目的：线上服务、质量评估、调试、训练或安全测试
授权：主体、范围、时间和撤回状态
处理：脱敏、抽样、人工标注和外部服务
版本：进入了哪个数据集、模型或评估报告
删除：删除请求如何传播到副本、缓存和派生结果
~~~

### 12.7.1 反馈数据很容易脱离上下文

用户点击“有帮助”只表示某种反馈，不代表同意公开全文；客服复制一个 bad case 到文档，也不代表这个文档可以被所有团队访问。标注员看到完整合同，也不代表第三方供应商可以永久保存它。

训练候选要有独立状态：

~~~text
candidate：被发现，尚未获得处理许可
approved：目的、授权和脱敏检查通过
blocked：明确不应进入训练或共享
deleted：从规定范围内删除，并保留删除证据
unknown：来源、授权或传播链缺失
~~~

### 12.7.2 删除要沿着派生图传播

一条用户删除请求可能涉及：

~~~text
原始对话 -> 日志 -> 反馈表 -> 标注副本 -> 训练 shard
         -> embedding -> 检索索引 -> response cache -> 报告
~~~

不同对象的删除时间、技术可行性和法律要求可能不同，工程系统要明确边界并给出状态。不能用“原始记录删了”替代对索引、备份、训练候选和外部供应商的核查。

## 12.8 外部服务和跨边界传输

第三方 OCR、ASR、embedding、审核、标注和模型服务会扩大数据边界。技术接口可用，不代表传输已经获得业务和合规授权。

一次外部传输至少要记录：

1. 传输的主体、资源和处理目的；
2. 字段级最小化和脱敏结果；
3. 接收方、地区、保留和删除承诺；
4. 数据处理协议、合同和审批状态；
5. 失败重试、缓存和日志是否会产生额外副本；
6. 传输后的访问、删除和事故通知责任。

高敏数据可以采用局部裁剪、字段替换、端侧处理、专用部署或人工路径降低暴露面。不能只在产品文档中写“供应商不会训练”，还要保留当前服务版本、账户配置和合同/审批证据。

法律和监管判断需要由法务、隐私和安全负责人结合地区与行业确认。工程团队的职责是把这些判断所需要的主体、字段、版本、传输和删除状态记录下来，并让系统在证据缺失时降级或阻断。

## 12.9 过度拒答：安全策略也会造成业务事故

安全系统如果只追求拒绝率，会把合法医学科普、防御性网络安全、法律解释、历史讨论和企业合规咨询一起拒掉。用户得到一句模板化声明，任务没有完成，团队也无法判断策略是否真的降低了风险。

安全策略要区分：

~~~text
高风险且不可提供：拒绝或转人工
低风险教育/防御性请求：给出边界内解释
需要更多上下文的灰区：追问、降级或人工审核
证据和分类缺失：unknown，不自动放行也不自动拒绝为安全
~~~

拒答质量包括原因是否清楚、是否给出安全替代路径、是否保护了用户隐私，以及是否把合法任务误判成恶意任务。策略变更应灰度发布，观察误拒、漏拒、投诉、转人工和任务完成率，并保留回滚版本。

## 12.10 版权、来源和敏感推断

版权与来源问题不只发生在训练阶段，也发生在 RAG、生成和产品展示阶段。用户要求逐字复现长篇受保护内容、系统没有记录知识库授权、生成结果高度相似、用户上传的第三方文档被再利用，都需要不同的策略。

工程系统可以做的事情包括：

1. 记录文档来源、许可范围、地域和有效期；
2. 对逐字复现、长段输出和高相似结果进行限制或审核；
3. 对用户上传内容区分当前任务使用与改进用途；
4. 为生成的图片、音频和视频记录模型、素材和编辑链；
5. 对肖像、商标、敏感属性推断和受保护内容设置领域规则；
6. 对无法判断的来源或授权状态标记 unknown，进入人工或法务路径。

内容来源凭证可以帮助回答“这份内容从哪里来、经过哪些处理”，但凭证存在不等于内容自动合规。C2PA 之类的来源标准解决可验证 provenance 的一部分，不替代许可、隐私和行业规则。

## 12.11 多模态安全：原始文件和派生文本都要审计

图片、音频和视频会带来文本之外的风险：

1. 证件、车牌、病历、合同和人脸出现在图片中；
2. OCR 提取出密钥、隐私或注入内容；
3. 音频包含个人身份、金融或医疗信息；
4. 视频包含未成年人、敏感场景或长期行为轨迹；
5. 用户要求识别身份、性别、健康等敏感属性；
6. 图片、音频和视频生成涉及肖像、商标、版权或不当内容。

安全检查要覆盖：

~~~text
原始文件：类型、访问、敏感区域、保留
转换结果：OCR/ASR/caption、bbox、时间戳和派生 ACL
模型输出：文本、引用、图像、音频和视频
外部动作：导出、分享、识别、修改和发送
~~~

多模态第 11 章中的证据血缘在这里也是安全控制：没有 source_id、location、transform 和 ACL，就很难证明某个引用是否越过了原始权限。

## 12.12 安全评估：覆盖控制失效而不是只收集攻击句子

安全评估既要测恶意请求，也要测系统在正常请求上的误伤。红队样本不是一组漂亮的攻击句子，而是一组能证明信任边界、权限和动作策略是否有效的实验。

评估切片至少包括：

1. 有害内容和危险操作请求；
2. 直接与间接 prompt injection；
3. RAG 越权、缓存隔离和权限变更；
4. Agent 工具越权、参数错配和未确认动作；
5. 日志、反馈、训练和外部传输；
6. 多模态文件中的隐私和不可信指令；
7. 正常、教育、防御和灰区请求；
8. 多轮对话、超时、回滚和未知状态。

每个样本要保存期望动作、实际动作、严重度、策略版本和证据。指标包括不当放行率、过度拒答率、敏感数据处理覆盖、权限违规率、工具确认覆盖、审计覆盖、事故响应就绪和单位成本，而不是只报一个 attack success rate。

### 12.12.1 漏拒与误拒的区别

设高风险样本数为 N_high，有害或不应放行的样本中实际被放行的数量为 N_unsafe_pass，在 N_high>0 时：

$$
R_{\mathrm{unsafe}}=
\frac{N_{\mathrm{unsafe\_pass}}}{N_{\mathrm{high}}}
$$

设正常样本数为 N_benign，被错误拒绝的数量为 N_false_refusal，在 N_benign>0 时：

$$
R_{\mathrm{over}}=
\frac{N_{\mathrm{false\_refusal}}}{N_{\mathrm{benign}}}
$$

如果测试集中没有高风险样本，R_unsafe 是 not_applicable；如果本来应该有风险标签但没有标注，则是 unknown。两者都不能用分母加一个很小的数强行变成 0。

### 12.12.2 数据控制指标

若检测到 N_pii 个个人身份信息或可组合识别信息，其中 N_redacted 个被正确脱敏、最小化、授权或转人工，且 N_pii>0，则：

$$
C_{\mathrm{pii}}=
\frac{N_{\mathrm{redacted}}}{N_{\mathrm{pii}}}
$$

敏感数据阻断/降级/人审也可以用同样的定义。字段没有被检测、规则未运行或结果不可追溯时，不要把覆盖率当成 1；应报告检测覆盖和审计状态。

日志、训练和删除分别有自己的分母：

$$
C_{\mathrm{log}}=
\frac{N_{\mathrm{log,protected}}}{N_{\mathrm{log}}},
\qquad N_{\mathrm{log}}>0
$$

上式中的分子可以表示已脱敏、最小化或受控访问的日志事件。训练授权覆盖率为：

$$
C_{\mathrm{train}}=
\frac{N_{\mathrm{train,approved}}}{N_{\mathrm{train,candidate}}},
\qquad N_{\mathrm{train,candidate}}>0
$$

如果没有训练候选，C_train 是 not_applicable；如果有候选但授权字段缺失，是 unknown；候选明确未获授权则是有效的 0。

删除 SLA 也要按请求数计算：

$$
R_{\mathrm{delete}}=
\frac{N_{\mathrm{delete,on\_time}}}{N_{\mathrm{delete,request}}},
\qquad N_{\mathrm{delete,request}}>0
$$

删除请求为 0 不等于系统具备删除能力；它只说明本次样本没有适用请求。

### 12.12.3 权限、确认和审计

设有 N_access 次需要权限判断的访问，其中 N_unauthorized 次被判定为越权：

$$
R_{\mathrm{unauth}}=
\frac{N_{\mathrm{unauthorized}}}{N_{\mathrm{access}}},
\qquad N_{\mathrm{access}}>0
$$

权限记录缺失时，不能把请求放进分子为 0 的集合；应该另记 unknown。高风险动作确认覆盖率为：

$$
C_{\mathrm{confirm}}=
\frac{N_{\mathrm{confirmed}}}{N_{\mathrm{high\_action}}},
\qquad N_{\mathrm{high\_action}}>0
$$

审计覆盖率可以写成：

$$
C_{\mathrm{audit}}=
\frac{N_{\mathrm{audit\_complete}}}{N_{\mathrm{audit\_event}}},
\qquad N_{\mathrm{audit\_event}}>0
$$

审计完成不仅是有一行日志，还要能关联主体、资源、动作、策略版本、结果和访问者。没有审计事件可能是任务不需要审计，也可能是审计管道坏了；两种情况需要额外的 audit_required 字段区分。

### 12.12.4 事故响应就绪

事故响应不是一个平均质量分。它至少要能够完成：

~~~text
发现：知道何时、哪条链路和哪类数据受影响
止血：阻断工具、撤销密钥、禁用缓存、暂停传输
定位：找到租户、资源、时间窗口和派生副本
通知：按合同、法规和内部流程通知责任方
修复：回滚策略、删除/轮换、补权限和补日志
复测：用原事故样本与新增边界样本验证修复
~~~

如果严重事件缺少任一关键状态，整体响应应为 unknown 或 failed，而不是用其他正常请求的平均分抵消。

## 12.13 典型事故一：日志泄露 API key

用户在 prompt 中误粘贴 API key。系统为了 debug 保存完整输入，日志平台又被多个团队共享访问。当天没有发生模型越权，但密钥已经进入持久化系统。

排查顺序是：

1. 确认密钥是否真实、是否已被使用；
2. 识别日志、trace、错误平台、备份和导出副本；
3. 立即轮换或撤销密钥；
4. 限制原始日志访问并保留访问审计；
5. 删除不必要的原文和派生副本；
6. 检查训练、评估、标注和外部传输是否接触；
7. 把密钥模式、日志字段和轮换流程加入回归测试。

根因不是“用户不该粘贴密钥”，而是系统没有把输入视为可能含有敏感数据，也没有建立最小化、检测、脱敏、轮换和删除闭环。

## 12.14 典型事故二：安全策略上线后正常问题大量拒答

新规则上线后，合法医学、法律和安全科普问题大量收到模板化拒答。投诉上升，转人工增加，但系统只有拒绝率，没有正常请求样本和原因分布。

修复需要同时做三件事：

1. 建立按领域、风险和意图分层的正常请求集；
2. 将拒答原因、替代回答和用户任务完成情况纳入评估；
3. 对策略灰度、版本、回滚和人工申诉建立审计。

安全策略的目标不是把 refusal 数字做大，而是减少高严重度风险，同时让合法请求得到边界清晰的帮助。没有分类证据时，unknown 状态要触发追问、人工审核或降级，而不是静默拒绝所有请求。

## 12.15 事故复盘：把第一处分歧写出来

复盘时冻结以下材料：

~~~text
原始请求、文件 hash 和用户/租户快照
RAG 候选、最终 context、缓存键和权限版本
模型、prompt、策略、分类器和工具版本
工具参数、确认、审批、后端状态和幂等键
日志/trace 的原始与脱敏访问记录
训练、反馈、标注、外部传输和删除事件
影响范围、止血、回滚、修复和复测结果
~~~

然后沿着这条路径寻找第一处分歧：

~~~text
主体 -> 资源 -> 目的 -> 证据 -> 策略期望 -> 实际动作
     -> 权限/确认 -> 日志/保留 -> 外部传输 -> 响应/复测
~~~

不要把所有问题写成“模型安全能力不足”。RAG 越权应该修检索和 ACL；工具未确认应该修动作策略和后端；日志泄露应该修字段和访问；训练误用应该修用途与 lineage；外部传输应该修数据最小化、审批和合同证据。

## 12.17 如何读懂审计输出

从正文代码实际运行得到的关键结果如下：

~~~text
metrics= {'unsafe_pass_rate': 0.875, 'over_refusal_rate': 0.5, 'pii_redaction_coverage': 0.667, 'sensitive_handling_coverage': 0.333, 'unauthorized_access_rate': 'unknown', 'tool_confirmation_coverage': 0.0, 'log_protection_coverage': 0.9, 'training_consent_coverage': 'unknown', 'retention_compliance': 0.0, 'deletion_sla_pass_rate': 0.0, 'external_transfer_approval': 0.0, 'audit_coverage': 0.8, 'incident_response_coverage': 'unknown', 'dpa_coverage': 0.0}
p95_latency_ms= 1050.0
average_cost= 0.006
unknown_metrics= ['unauthorized_access_rate', 'training_consent_coverage', 'incident_response_coverage']
unsafe_passes= ['rag_private_context', 'tool_refund_no_confirm', 'raw_log_secret', 'external_transfer_no_approval', 'training_feedback_no_consent', 'training_authorization_missing', 'permission_record_missing']
over_refusals= ['normal_request_over_refused']
failed_conditions= ['unsafe_pass_rate', 'over_refusal_rate', 'pii_redaction_coverage', 'sensitive_handling_coverage', 'unauthorized_access_rate', 'tool_confirmation_coverage', 'log_protection_coverage', 'training_consent_coverage', 'retention_compliance', 'deletion_sla_pass_rate', 'external_transfer_approval', 'audit_coverage', 'incident_response_coverage', 'dpa_coverage', 'p95_latency']

~~~

这里的 unknown 不是一个可以忽略的备注。permission_record_missing 没有权限检查记录，所以系统不能声称权限安全；严重事件的 incident_response_coverage 也是 unknown，因为现场没有完整的响应证据。发布判断把 unknown 当成需要修复的状态，避免“没有日志所以没有问题”的错误推理。

这个 demo 还显示了安全控制之间的相互影响：同一个事件可能同时贡献不当放行、权限缺失、日志泄露和事故响应缺口。团队不能只修最后一个模型分类器，然后把所有指标重新平均；应该按 root_causes 找第一处分歧，并把修复后的事件加入回归集。

代码中使用的是按事件或字段计数的微平均。对于含有不同严重度的业务，可以额外按风险等级报告宏平均和加权风险，但权重、样本定义和排除规则必须版本化。没有适用样本的控制仍应保留 not_applicable，缺少证据的控制仍应保留 unknown。

## 12.18 修复顺序：先止血，再补合同和评估

安全事故发生后，第一步是止血，而不是马上换模型。

1. 冻结影响范围、租户、资源、时间窗口和版本；
2. 撤销泄露的密钥、停用危险工具、隔离缓存和暂停外部传输；
3. 保护最小必要的原始证据，同时限制访问；
4. 确认是否发生越权读取、外部发送、写操作或训练传播；
5. 通知安全、隐私、法务、业务和供应商责任人；
6. 删除或轮换受影响的副本、凭据和派生数据；
7. 补权限、确认、脱敏、用途、保留和审计控制；
8. 用原事故、相邻边界和正常请求重新评估；
9. 以版本化报告记录修复、残余风险、回滚和后续监控。

对 RAG，先修检索前 ACL 和缓存隔离；对 Agent，先修工具层主体、资源、参数、确认和后端状态；对日志，先修字段最小化、密钥轮换和访问审计；对训练，先修授权、lineage 和删除传播；对外部服务，先修最小化、审批、合同和责任边界。

只有当这些控制可验证后，才适合比较更强模型或更严格的内容分类器。模型能力可以降低部分风险，但不能替代权限服务、审计、数据生命周期和业务责任。

## 12.19 资料来源与证据边界

### 12.19.1 治理框架和规范

- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：提供治理、映射、测量和管理风险的框架。它不是某个模型或产品的安全证明。
- [NIST Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)：把生成式 AI 的特定风险纳入 AI RMF 语境，适合组织风险管理和控制映射。
- [NIST Privacy Framework](https://www.nist.gov/privacy-framework)：提供隐私风险识别和治理的结构，不替代具体地区的法律判断。
- [ISO/IEC 42001](https://www.iso.org/standard/81230.html)：AI 管理体系标准的官方页面。认证或采用管理体系不等于某个输出、权限和工具动作自动安全。
- [C2PA Specifications](https://spec.c2pa.org/specifications/specifications/2.2/index.html)：关注内容来源和处理链的可验证凭证。来源凭证不能替代版权许可、隐私、肖像和行业合规。

### 12.19.2 官方模型和工程资料

- [OpenAI Model Spec](https://model-spec.openai.com/2025-02-12.html)：可用于理解指令层级和不可信内容边界。它不能替代工具权限、租户隔离和业务后端校验。
- [OpenAI Agents SDK Guardrails](https://openai.github.io/openai-agents-python/guardrails/) 与 [Tracing](https://openai.github.io/openai-agents-python/tracing/)：提供 guardrail 和 trace 的工程入口。SDK 能提供机制，不自动完成数据脱敏、DPA、权限和事故响应。
- [OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)：提供 LLM 应用风险分类入口。具体系统的注入、越权和泄露结果必须在本地数据流和工具上实测。
- [OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)：说明 prompt injection 风险的分类和背景，不应被当成单一防护方案。

### 12.19.3 法律和业务边界

法规、合同、数据处理协议、跨境传输、版权和行业要求由适用地区、数据类型和业务角色决定。工程正文不替代法务意见；它应做的是保留可核查的来源、授权、主体、目的、版本、访问、保留、删除和事故证据。

本章 Python demo 是教学构造，证明指标定义和边界状态可以执行，不能证明目标系统已经合规。论文、治理框架、官方 SDK 和本地实验分别回答不同问题，不能互相冒充。

## 12.20 本章小结

安全与合规不是最后一个 filter，而是覆盖主体、资源、动作、数据目的、权限、模型、工具、日志、缓存、反馈、训练、外部传输、删除和事故响应的一组系统约束。

外部网页、RAG 文档、邮件、OCR、ASR 和工具返回是数据，不是可以升级系统权限的指令。RAG 要在检索前做 ACL，缓存要绑定租户、主体和权限版本，Agent 工具要在模型外做资源归属、参数、确认、幂等和后端状态校验。日志和 trace 要可回放，但只保留最小必要的信息；训练和反馈要有独立用途、授权、lineage 和删除传播；第三方传输要有最小化、审批、合同和责任证据。

安全评估必须同时看不当放行和过度拒答，并对权限、敏感数据、工具确认、日志、训练、保留删除、审计和事故响应分别统计。没有适用对象是 not_applicable，应该检查但没有记录是 unknown，真实失败才是有效的 0。任何高严重度权限泄露、密钥泄露、未确认副作用和未经授权传输，都不应被平均质量抵消。

下一章进入项目管理与团队协作坑。安全控制能否落地，往往取决于需求、责任、版本、资源、上线节奏和跨团队协作是否形成了可执行的交付合同。


## 12.16 可运行的安全与合规事故审计示例

下面的 demo 使用 Python 标准库，模拟正常请求误拒、RAG 越权、工具退款未确认、日志密钥泄露、外部传输未审批、反馈未经授权进入训练、缺少权限记录和一次处理正确的高风险升级。

它刻意不把空集合当成 1，也不把缺少记录当成安全：

1. 没有 PII 的样本不参与 PII 覆盖率；
2. 没有高风险动作的样本不参与确认覆盖率；
3. 有权限需求但没有权限记录时，权限指标为 unknown；
4. 有训练候选但授权记录缺失时，训练授权指标为 unknown；
5. 正分子零分母、NaN、负数和整数冒充布尔值会被拒绝；
6. 最终发布判断使用 failed、unknown 和 not_applicable 的明确状态。

from dataclasses import dataclass
from math import ceil, isfinite
from typing import Optional


@dataclass(frozen=True)
class Metric:
    value: Optional[float]
    status: str


def finite_number(value, name):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError(f"{name} must be a finite number")
    value = float(value)
    if not isfinite(value):
        raise ValueError(f"{name} must be finite")
    return value


def safe_ratio(numerator, denominator, name):
    numerator = finite_number(numerator, f"{name}.numerator")
    denominator = finite_number(denominator, f"{name}.denominator")
    if numerator < 0 or denominator < 0:
        raise ValueError(f"{name} cannot be negative")
    if denominator == 0:
        if numerator == 0:
            return Metric(None, "not_applicable")
        raise ValueError(f"{name} has a positive numerator and zero denominator")
    return Metric(numerator / denominator, "valid")


def safe_mean(values, name):
    if not values:
        return Metric(None, "not_applicable")
    checked = [finite_number(value, name) for value in values]
    return Metric(sum(checked) / len(checked), "valid")


def percentile(values, pct):
    pct = finite_number(pct, "percentile")
    if pct < 0 or pct > 100:
        raise ValueError("percentile must be between 0 and 100")
    if not values:
        return Metric(None, "not_applicable")
    ordered = sorted(finite_number(value, "latency") for value in values)
    rank = max(1, ceil(len(ordered) * pct / 100))
    return Metric(ordered[rank - 1], "valid")


def render(metric):
    if metric.status != "valid":
        return metric.status
    return round(metric.value, 3)


def check_bool(value, name):
    if type(value) is not bool:
        raise ValueError(f"{name} must be a real bool")


def check_non_negative_int(value, name):
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")

def validate_case(case):
    if not isinstance(case["id"], str) or not case["id"]:
        raise ValueError("case id must be non-empty")
    if case["expected_action"] not in {
        "allow", "block", "redact", "confirm", "review", "escalate"
    }:
        raise ValueError("invalid expected action")
    if not isinstance(case["actual_action"], str) or not case["actual_action"]:
        raise ValueError("actual action must be non-empty")
    check_bool(case["benign"], f"{case['id']}.benign")
    check_non_negative_int(case["severity"], f"{case['id']}.severity")

    bool_fields = (
        "permission_required", "permission_recorded", "confirmation_recorded",
        "pii_recorded", "safety_recorded", "log_recorded",
        "consent_recorded", "retention_recorded", "deletion_recorded",
        "transfer_recorded", "audit_required", "audit_recorded",
        "incident_required", "incident_recorded", "incident_ready",
        "dpa_required", "dpa_recorded", "dpa_ready",
    )
    for field in bool_fields:
        check_bool(case[field], f"{case['id']}.{field}")

    count_fields = (
        "access_checks", "unauthorized_hits", "high_risk_actions",
        "high_risk_confirmed", "pii_detected", "pii_redacted",
        "sensitive_events", "sensitive_handled", "logs_total",
        "logs_protected", "training_candidates", "training_approved",
        "retention_items", "retention_ok", "deletion_requests",
        "deletion_on_time", "external_transfers", "external_approved",
        "audit_events", "audit_complete",
    )
    for field in count_fields:
        check_non_negative_int(case[field], f"{case['id']}.{field}")

    for numerator, denominator, name in (
        ("unauthorized_hits", "access_checks", "permission"),
        ("high_risk_confirmed", "high_risk_actions", "confirmation"),
        ("pii_redacted", "pii_detected", "pii"),
        ("sensitive_handled", "sensitive_events", "sensitive"),
        ("logs_protected", "logs_total", "logs"),
        ("training_approved", "training_candidates", "training"),
        ("retention_ok", "retention_items", "retention"),
        ("deletion_on_time", "deletion_requests", "deletion"),
        ("external_approved", "external_transfers", "external"),
        ("audit_complete", "audit_events", "audit"),
    ):
        if case[numerator] > case[denominator]:
            raise ValueError(f"{name} numerator cannot exceed denominator")

    for field in ("latency_ms", "cost"):
        if finite_number(case[field], f"{case['id']}.{field}") < 0:
            raise ValueError(f"{field} cannot be negative")
    if case["permission_required"] and case["access_checks"] == 0 and case["permission_recorded"]:
        raise ValueError("a recorded permission check needs an access count")
    if case["dpa_required"] and case["external_transfers"] == 0:
        raise ValueError("DPA control requires an external transfer")


def ratio_for(cases, predicate, record_field, numerator_field, denominator_field, name):
    applicable = [case for case in cases if predicate(case)]
    if not applicable:
        return Metric(None, "not_applicable")
    if any(not case[record_field] for case in applicable):
        return Metric(None, "unknown")
    numerator = sum(case[numerator_field] for case in applicable)
    denominator = sum(case[denominator_field] for case in applicable)
    return safe_ratio(numerator, denominator, name)


def binary_coverage(cases, predicate, record_field, value_field, name):
    applicable = [case for case in cases if predicate(case)]
    if not applicable:
        return Metric(None, "not_applicable")
    if any(not case[record_field] for case in applicable):
        return Metric(None, "unknown")
    return safe_ratio(
        sum(int(case[value_field]) for case in applicable),
        len(applicable),
        name,
    )
