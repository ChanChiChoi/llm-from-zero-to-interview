# 第十四章：让失败留下证据：实验复盘、事故报告与系统学习

## 14.1 同一个团队连续相信了三个错误结论

一个团队把内部知识助手交给了两组工程师。第一组负责训练和评估，第二组负责线上检索与服务。项目初期进展顺利：公开评估集上的答案正确率上升，演示中的引用看起来完整，接口也能在测试环境中稳定返回。

几周后，三个结论先后被证明不可靠。

第一个结论是“新模型的能力提升了”。模型在内部 benchmark 上提高了 12 个百分点，但训练数据中混入了 benchmark 的原题和近似题。换成没有参与训练的私有 holdout 后，提升几乎消失；在真实用户的多轮、长上下文和格式约束任务上，部分能力反而下降。

第二个结论是“新索引已经发布成功”。文档索引 v47 构建完成，离线检索指标比 v46 好看，团队开始灰度。线上却有一段时间持续引用旧版制度。原因不是向量没有更新，而是 reranker 缓存的 key 没有包含文档版本；新索引已经存在，服务仍然从旧缓存读取排序结果。

第三个结论是“Agent 只是在查询订单”。用户说“帮我看一下这个订单并处理异常”，模型把“处理”解释成修改状态，调用了写工具。工具 schema 没有清楚区分查询和更新，写操作也没有二次确认。测试订单被改变后，团队才发现工具选择准确率的报告从未统计过高风险误调用。

三个事故表面不同：一个是数据污染，一个是缓存和版本，一个是 Agent 行为边界。它们共享同一个组织问题：实验报告只保存了好看的总分，发布报告只写了“已完成”，事故记录只写了直接触发点，行动项没有验证证据。团队记住了“这次出了问题”，却没有让系统获得下一次排查所需的记忆。

实验复盘和事故报告的价值，正是在这里体现出来。它们不是失败之后补写的作文，而是把一次判断变成可复查证据，把一次事故变成系统改动，再用回归和监控确认改动确实生效。

## 14.2 实验、复盘和事故报告分别解决什么问题

实验是主动改变系统并观察结果。复盘是对实验、发布或运行结果进行结构化解释。事故报告是对已经造成影响的异常进行事实还原、止损记录和防复发设计。三者相互连接，但不能互相替代。

一个实验即使没有上线，也需要复盘，因为失败结果可能说明假设错误、评估集不合适、变量没有隔离，或者系统已经触碰资源边界。一个线上事故即使很快回滚，也需要报告，因为快速恢复并不能说明发现及时、影响可知或根因已经消失。

可以把它们放在一条证据链上：

~~~text
任务问题
   |
实验假设
   |
受控变更
   |
评估与观察
   |
决定：继续、灰度、放弃或回退
   |
线上运行
   |
异常与影响
   |
止损和恢复
   |
复盘、行动项、回归和监控
~~~

链条中任何一段缺失，后面的结论都会变弱。没有任务问题，实验可能只是追逐分数；没有 baseline，提升没有参照；没有线上观察，离线结果无法代表真实分布；没有行动项和回归，复盘只能解释过去，不能改变未来。

刚接触工程项目的人容易把复盘理解成“把发生过的事情按时间写一遍”。真正有用的复盘还要回答三个更难的问题：

1. 当时哪些事实是已知的，哪些只是推测。
2. 哪个环节第一次偏离了任务合同。
3. 什么具体改变会让下一次事故更难发生、更早被发现或更快恢复。

## 14.3 一份实验报告要保存一条可复现路径

实验报告不是结果截图。它应该让另一个工程师在合理成本内重建实验条件，或者明确指出哪些条件已经无法重建。

一份完整报告至少要有以下内容：

| 部分 | 需要记录的内容 | 缺失后的问题 |
| --- | --- | --- |
| 任务 | 用户、场景、成功行为和失败边界 | 不知道在优化什么 |
| 假设 | 改什么、为什么改、预测什么 | 只能事后解释 |
| baseline | 模型、数据、Prompt、检索和系统组合 | 无法判断增量 |
| 变更 | 文件、配置、代码和服务的具体差异 | 无法归因 |
| 数据 | 训练、评估、文档、抽样和标注版本 | 结果无法复现 |
| 运行 | 解码、资源、超时、重试和随机性 | 结果不稳定 |
| 指标 | 主指标、护栏、分桶和定义域 | 总分掩盖副作用 |
| 失败 | bad case、错误类型和影响 | 不知道哪里坏 |
| 决定 | 继续、灰度、回退或停止的原因 | 报告无法指导行动 |
| 后续 | 负责人、证据、时间和验证结果 | 改进无法关闭 |

例如，“换了 Prompt，引用更准了”几乎不能复查。下面的记录更接近工程证据：

> 任务是企业制度问答，baseline 为线上 Prompt v12、索引 v46、reranker r8，评估集为 rag_eval_2026_05 的 300 条固定样本。假设是：把回答结构改为先给结论、再给引用，并在无证据时拒答，可以提高引用支持率，同时不让复杂制度问题的完整性下降超过 2 个百分点。候选为 Prompt v13，模型、索引和检索结果保持不变。候选的引用支持率从 84.5% 变为 90.2%，平均输出 token 下降 18%，但复杂制度问题完整性下降 3.4%，简单问题 P95 变为 4.8 秒。决定是先在内部用户中灰度，复杂制度问题单独建模板，不把整体结果作为全量发布依据。

这个记录不仅保存了结果，还保存了限制条件。它允许别人质疑“为什么提升不能归因于 Prompt”，也允许团队在下一次回归时确认哪些变化是预期的，哪些是新问题。

### 14.3.1 报告中的事实、解释和决定要分开

一份报告常同时包含三种句子：

- 事实：“候选版本在 300 条样本上得到 79.1% 的答案正确率。”
- 解释：“复杂制度问题下降，可能与上下文裁剪有关。”
- 决定：“暂不全量发布，先增加长文档分桶和上下文保留实验。”

三者不能混在一起。事实应该能指向原始数据；解释应标注证据强度和替代解释；决定应说明使用了哪些硬约束和取舍。把解释写成事实，会让后续排查从一个未经验证的假设开始。

### 14.3.2 失败实验也要有结论

失败实验至少可以产生四类知识：

1. 某个改动没有带来预期收益；
2. 某个收益只存在于特定分桶；
3. 某个方案触碰了成本、延迟或安全边界；
4. 某个评估方法无法区分真正能力和数据记忆。

“效果没提升，所以实验没价值”是错误的。只要实验边界清楚，失败结果就能减少下一轮搜索空间。真正浪费的是失败之后没有留下条件，导致团队几周后重复尝试同样的方案。

## 14.4 假设必须可被反驳

“新模型会更强”“加数据会变好”“Prompt 会更稳”都不是可执行假设，因为它们没有说明场景、改动、测量和失败条件。

一个可反驳的假设应当包含四部分：

1. 当前观察：系统在哪类任务上失败；
2. 可能原因：哪一环节最值得怀疑；
3. 具体改变：只改变或明确组合哪些变量；
4. 可观察预测：哪些指标会如何变化，什么结果会否定假设。

例如：

> 当前制度类问题的主要失败来自召回不足。如果把同一 embedding 和索引下的候选数量从 20 增加到 80，并使用固定 reranker，那么制度类问题的 Recall@10 至少提高 8 个百分点，上下文 token 增长不超过 40%，P95 总延迟不超过 5 秒。若召回提高但答案支持率不提高，说明主要瓶颈可能在 context construction 或生成，而不是召回。

这个假设有明确的反例。即使结果是“召回提高、答案没提高”，团队也学到了瓶颈位置发生了转移。

### 14.4.1 一个假设只能承担一个主要因果问题

如果同时更换模型、数据、Prompt、embedding、reranker 和调度策略，实验可能有效，却无法回答哪个变化产生了结果。组合实验可以作为最后的系统验证，但它不应该代替组件级实验。

更稳妥的顺序是：

1. 固定模型、数据、Prompt 和索引，只比较检索参数；
2. 固定候选证据，只比较上下文组织；
3. 固定输入和 Prompt，只比较模型；
4. 固定所有生成条件，只比较安全策略；
5. 最后运行组合版本，观察交互副作用。

“单变量”不是要求每次只改一个字符，而是要求因果范围被清楚命名。如果一次实验确实包含多个变化，应诚实地把它写成“组合方案实验”，而不是把全部收益归给其中一个组件。

### 14.4.2 假设的反例应进入报告

实验报告中应保留：

- 支持假设的样本；
- 反驳假设的样本；
- 结果不确定的样本；
- 输入或标签有争议的样本；
- 评估方法可能失效的样本。

如果只保存“成功案例”，报告就会变成宣传材料。反例能帮助团队区分“方法本身无效”和“方法只适合某些任务”。

## 14.5 baseline 和数据契约决定比较是否可信

baseline 是完整运行组合，不是一个模型名字。至少要包含：

- 模型或 API 路由；
- tokenizer 和模板；
- 训练或评估数据版本；
- Prompt；
- 检索、重排和过滤；
- 解码参数；
- 工具和安全策略；
- 运行资源和超时；
- 评估脚本和人工判定指南。

如果候选版本使用了更新的文档、更多重试或更长输出预算，报告必须说明。否则，分数变化可能来自输入和资源条件，而不是模型能力。

### 14.5.1 数据契约要写清样本单位

评估结果的分母应明确是：

- 请求；
- 对话；
- 任务；
- 工具动作；
- 文档；
- claim；
- token；
- 用户或租户。

一个用户任务可能包含多次模型调用。按调用统计成功率会夸大局部正确，按任务统计才反映工作流完成。一个回答有多个引用时，引用支持率的样本单位可能是 claim，而不是整条回答。

数据契约还要说明：

- 空输入如何表示；
- 缺失标签如何表示；
- 争议标签如何处理；
- 重复样本是否保留；
- 训练和评估是否可能重叠；
- 时间切分是否遵循生产顺序；
- 权限和隐私字段是否需要脱敏。

### 14.5.2 评估集污染不是只有完全重复

污染可能包括：

- exact duplicate；
- 轻微改写；
- 同一事实的模板化变体；
- 训练数据中的答案片段；
- 评估题的解析过程或提示模板；
- benchmark 的公开讨论和人工答案。

因此，报告要区分“未发现完全重复”和“已经证明没有信息泄露”。后者需要更强的近重复、来源和时间证据。私有 holdout、时间后移数据和真实业务样本通常比一个公开总分更能检验泛化。

## 14.6 指标报告必须包含分桶、不确定性和护栏

平均值是一个摘要，不是完整证据。

设非空评估集为 S，样本 i 的成功标记为 yi，比例为：

$$
R =
\frac{\sum_{i\in S} y_i}{|S|}
$$

当 |S| 大于 0 时，R 等于 0 是有效结果；当 |S| 等于 0 时，R 不适用。若 yi 缺失，不能直接把缺失样本从分母删除并声称它代表原总体，应同时报告有效样本量和缺失状态。

候选与 baseline 的绝对变化为：

$$
\Delta R = R_c - R_b
$$

只有 Rb 大于 0 时，才可以报告相对变化：

$$
\Delta_{\mathrm{rel}} =
\frac{R_c-R_b}{R_b}
$$

成对样本的变化为：

$$
\Delta_{\mathrm{paired}} =
\frac{1}{n}
\sum_{i=1}^{n}
\left(y_i^{(c)}-y_i^{(b)}\right)
$$

其中 n 大于 0，两个版本必须处理同一个样本。成对变化仍然不能替代成本、延迟和安全指标。

### 14.6.1 微平均、宏平均和业务加权

若第 k 个分桶的成功数为 ck，样本数为 nk，微平均是：

$$
R_{\mathrm{micro}} =
\frac{\sum_k c_k}{\sum_k n_k}
$$

要求总样本数大于 0。宏平均是：

$$
R_{\mathrm{macro}} =
\frac{1}{K}
\sum_{k=1}^{K}
\frac{c_k}{n_k}
$$

要求每个被纳入的分桶都满足 nk 大于 0；空分桶应标记为 not_applicable，不能被当作 0 参加平均。

若业务权重为 wk 且 wk 大于等于 0，则加权成功率为：

$$
R_w =
\frac{\sum_k w_k R_k}{\sum_k w_k}
$$

要求总权重大于 0，权重含义和版本必须被记录。权重不是为了调出好看的总分，而是为了表达任务价值或真实流量分布。

### 14.6.2 变化区间和样本量

一个 1 个百分点的变化，在 50 条样本上和在 50 万条样本上含义不同。报告至少应保留样本量、成功数、分桶数量和判定方式。对于抽样评估，可以使用 bootstrap 或其他不确定性方法，但要说明抽样单位。

如果样本来自同一对话或同一用户，直接把每条消息当作独立样本会低估相关性。Agent 任务中的多个动作也不能被当成多个独立成功任务。统计单位必须与业务决策单位一致。

### 14.6.3 护栏指标是不可替代的证据

质量提升如果伴随以下变化，就不能被简单称为成功：

- P95 延迟超过任务合同；
- 输出 token 大幅增加；
- 单成功任务成本超过预算；
- 过度拒答或安全漏拒上升；
- 引用支持率下降；
- 高风险工具误调用增加；
- trace 缺失导致无法复现。

护栏不是为了阻止优化，而是为了防止团队用一个容易刷高的指标掩盖其他层面的退化。

## 14.7 Bad case 要从样本变成错误系统

一个 bad case 只有在经过分类、归因、修复和回归之后，才成为工程资产。

最小记录可以包括：

| 字段 | 含义 |
| --- | --- |
| case_id | 可稳定引用的样本编号 |
| input | 用户输入和必要上下文 |
| expected | 期望行为及来源 |
| actual | 实际输出或动作 |
| versions | 模型、Prompt、检索、工具、策略和运行版本 |
| error_type | 错误分类 |
| first_divergence | 第一次偏离契约的阶段 |
| severity | 影响等级 |
| fix | 临时止损和长期修复 |
| regression | 是否进入回归集 |
| owner | 负责推动关闭的人 |

错误分类要能连接到修复动作。

RAG 常见分类：

1. 文档不存在；
2. 解析破坏标题、表格或页码；
3. chunk 跨越证据边界；
4. 召回没有找到支持片段；
5. reranker 把关键片段排到后面；
6. context 构造丢失或截断证据；
7. 模型忽略或误读证据；
8. 引用不支持 claim；
9. 版本或时效判断错误；
10. 权限过滤错误；
11. 资料不足时没有正确拒答。

Agent 常见分类：

1. 任务理解错误；
2. 计划不可执行；
3. 工具选择错误；
4. 参数构造错误；
5. 工具返回结果没有被使用；
6. 中间状态丢失；
7. 重试和循环没有停止；
8. 权限或确认边界失败；
9. 外部状态未知却宣称完成；
10. 最终叙述与实际动作不一致。

### 14.7.1 先找第一处分歧

连续系统可以表示为：

$$
x_0
\rightarrow x_1
\rightarrow x_2
\rightarrow \cdots
\rightarrow x_m
$$

其中每个状态都对应一个可检查的合同。第一处分歧定义为最小的 j，使得 xj 不满足该阶段契约。它不一定等于最终用户看到的错误位置。

例如，模型回答引用错误，可能在检索阶段就没有召回当前文档；如果在检索结果中已经存在正确证据，问题才可能在上下文拼接或生成阶段。先定位第一处分歧，可以减少无效地反复修改 Prompt。

第一处分歧不是完整根因。旧索引可能是文档发布流程缺少失效通知造成的，缓存权限问题可能是版本设计缺陷造成的。复盘需要同时记录局部失败和上游系统原因。

### 14.7.2 反例回归集的组成

回归集应保留：

- 原事故请求；
- 最接近事故但应正确处理的样本；
- 资料缺失和版本冲突；
- 权限相邻但不应访问；
- 长上下文和多轮状态；
- 工具超时、重复、未知和部分成功；
- 输出格式边界；
- 真实高峰的输入输出长度；
- 过去被修复但可能重新出现的错误。

只加原始样本会导致针对性修复；加入邻近反例，才能检验修复是否扩大了拒答、改变了正常任务或损害了其他分桶。

## 14.8 证据链要保留来源和可信度

事故和实验结论的可信度取决于证据，而不是报告写得多长。

可以把证据分成几层：

1. 原始请求、原始响应、工具返回和系统事件；
2. 请求 trace、日志、配置和版本记录；
3. 可重复运行得到的评估结果；
4. 人工复核和标注指南；
5. 参与者回忆和事后解释；
6. 未经验证的推测。

层级越靠前，通常越接近当时事实，但也可能受到采样、脱敏、日志缺失和时钟不同步影响。高质量报告会写清楚证据缺口，而不是把所有内容伪装成同样确定。

### 14.8.1 保留原始数据，同时限制敏感扩散

复盘需要足够证据，但事故数据可能包含个人信息、客户内容、密钥、内部文档和工具参数。应当：

- 只保存排查所需字段；
- 对展示版本脱敏；
- 原始证据设置访问权限；
- 记录脱敏规则和版本；
- 不把敏感样本直接复制到公共群聊；
- 保留事件 ID，使报告能回到受控原始记录；
- 明确保留和删除期限。

“为了复盘把所有日志都拷出来”可能制造新的安全事故。证据完整性和数据最小化要同时考虑。

### 14.8.2 时间戳和时钟不是小问题

事故时间线经常同时使用网关、应用、模型服务、数据库和客户端时间。若时钟不同步，事件顺序可能被误排。报告应记录：

- 时间来源；
- 时区；
- 精度；
- 是否经过网关或客户端转换；
- 相同事件的关联 ID。

如果时间顺序仍不能确定，应写成时间范围或 unknown，而不是凭感觉补出精确分钟。

## 14.9 事故报告首先要量化影响

“用户反馈变差”不是影响范围。事故报告至少需要估算：

- 起止时间；
- 请求和任务数量；
- 受影响用户、租户和业务线；
- 质量、延迟、成本和错误率的变化；
- 错误回答或错误动作数量；
- 是否涉及敏感数据；
- 是否需要重新处理；
- 是否有外部传播；
- 影响估算的未知部分。

如果日志缺失，不能因为没有查到泄露就写“没有泄露”。应该写“受影响范围暂时 unknown，正在通过访问记录和下游审计补证据”。

### 14.9.1 事故报告和实验报告的不同重点

实验报告回答“主动改变什么，观察到什么”；事故报告回答“异常发生了什么，影响如何被控制”。

实验报告重点是：

- hypothesis；
- baseline；
- controlled change；
- 结果、分桶和不确定性；
- decision。

事故报告重点是：

- impact；
- timeline；
- detection；
- mitigation；
- direct cause；
- systemic cause；
- recovery；
- prevention。

两者都需要版本和证据，但不能用实验报告的总分替代事故影响，也不能把事故回滚结果当成修复完成。

## 14.10 时间线要写事实和决策

事故时间线既要记录系统事件，也要记录人做出的决定：

~~~text
10:02 索引 v47 开始向 10% 流量灰度。
10:16 引用支持率下降，但监控只显示整体答案正确率，未触发告警。
10:23 租户 A 反馈看到旧制度。
10:30 值班工程师按租户和文档版本分桶，确认问题集中在 A、B。
10:38 暂停灰度并切回索引 v46。
10:45 新请求的旧引用比例下降，服务恢复。
11:20 发现 reranker cache key 没有包含 document_version。
14:00 修复 cache key，增加版本回归和过期引用告警。
16:00 低风险流量验证完成。
~~~

不要在第一版时间线中直接写“某人错误地改了配置”。先记录变更、指标、反馈和决策。事实足够后，再讨论为什么系统允许那项变更直接影响生产。

### 14.10.1 发现、止损和恢复时间

设事故开始时间为 tstart，系统检测时间为 tdetect，完成止损时间为 tmitigate，恢复时间为 trecover，则：

$$
T_{\mathrm{detect}} =
t_{\mathrm{detect}}-t_{\mathrm{start}}
$$

$$
T_{\mathrm{mitigate}} =
t_{\mathrm{mitigate}}-t_{\mathrm{start}}
$$

$$
T_{\mathrm{recover}} =
t_{\mathrm{recover}}-t_{\mathrm{start}}
$$

这些时间需要明确事件定义。发现时间可以是监控首次超过阈值，也可以是值班人员确认异常；两者不能混写。事故没有发生时，这些指标是 not_applicable；事故发生但时间字段缺失时，是 unknown。

更短的恢复时间不一定代表事故更轻。报告仍需保留影响量、数据范围和恢复后验证。

## 14.11 根因分析不能停在直接触发点

“Prompt 改错了”“缓存没清”“模型答错了”通常是直接原因。它们还没有解释系统为什么允许错误进入生产、为什么没有更早发现、为什么恢复需要这么久。

可以使用五个为什么：

~~~text
为什么格式解析失败？
因为 Prompt 改动破坏了 JSON 输出结构。

为什么一次 Prompt 改动就能破坏结构？
因为发布前只验证了一个正常样例。

为什么没有自动验证？
因为 Prompt 被当作文案，没有纳入代码和回归流程。

为什么 Prompt 没被当作生产逻辑？
因为配置没有版本、review 和请求 trace。

为什么这些能力不存在？
因为项目合同和发布流程没有把可复现性列为交付要求。
~~~

最后的行动项应落在系统上：

- Prompt 版本化；
- 核心格式回归；
- 请求 trace 记录 Prompt hash；
- 灰度和回滚；
- 输出解析失败告警。

### 14.11.1 直接原因、促成条件和系统根因

可以把根因拆成三层：

| 层次 | 例子 | 对应动作 |
| --- | --- | --- |
| 直接原因 | cache key 缺少文档版本 | 修复代码或配置 |
| 促成条件 | 没有过期引用监控 | 增加诊断和告警 |
| 系统根因 | 发布合同没有版本和恢复要求 | 修改流程、责任和验证 |

只修直接原因可能让当前样本恢复，但不一定降低同类事故概率。只写系统根因又可能让行动项太泛。三层都要有对应负责人和验证方式。

### 14.11.2 鱼骨图和故障树的价值

复杂事故往往由多个条件共同造成。可以按以下类别展开：

- 数据：来源、授权、解析、去重、版本；
- 模型：能力、模板、解码、对齐；
- 检索：召回、重排、缓存、权限；
- 工具：schema、参数、幂等、外部状态；
- 系统：调度、容量、超时、依赖；
- 评估：样本、污染、judge、分桶；
- 组织：责任、变更、告警、恢复。

故障树不是为了把责任分散，而是为了避免把多因素事故压缩成一个人的最后动作。最终报告仍然需要指出哪些条件是必要的、哪些只是放大器、哪些证据还没有获得。

## 14.12 止损、修复和预防是三个时间尺度

事故处理中要分开三个动作。

### 14.12.1 止损：先让影响停止扩大

例如 RAG 越权事故：

- 暂停受影响租户；
- 关闭可能返回敏感文档的检索路径；
- 回滚权限过滤和缓存组合；
- 清理可能污染的响应缓存；
- 转人工或只展示可核验证据；
- 保存事件和访问记录。

止损不要求根因已经完全解释，但必须记录它牺牲了什么功能、影响何时被控制。

### 14.12.2 修复：解决已知技术缺陷

修复可能包括：

- 检索前 ACL 过滤；
- cache key 加入权限和文档版本；
- 工具写操作增加后端状态校验；
- Prompt 和输出 schema 回滚；
- scheduler 增加长短请求隔离；
- 清理污染数据并重建索引。

修复后要用原事故样本、邻近反例和集成测试验证，而不是只确认代码提交成功。

### 14.12.3 预防：改变系统条件

预防措施应该改变未来的概率或影响：

- 将事故样本加入回归；
- 增加分桶指标和告警；
- 发布记录强制包含版本组合；
- 高风险工具必须确认和审计；
- 旧版本保留并演练回切；
- 事故行动项有关闭证据；
- 定期检查数据和评估污染。

只做止损会复发，只做修复会在相邻路径上重演，只写预防而不修当前缺陷会让影响继续存在。

## 14.13 行动项必须可以关闭

“加强 review”“提高意识”“持续关注”不是可验收行动项，因为它们没有明确的动作和完成证据。

一个可关闭的行动项至少包括：

- 具体动作；
- 负责人；
- 截止时间；
- 优先级；
- 验收标准；
- 证据位置；
- 是否需要回归和观察窗口。

例如：

> 将生产 Prompt 迁移到版本化配置，生成 prompt_version，并让 100% 的生成请求 trace 记录该字段。负责人为应用服务负责人，截止日期为 2026-06-05。验收证据是连续 24 小时的 trace 抽样和缺失率报告。

另一个例子：

> 新增 200 条 JSON 格式回归样本，覆盖缺字段、嵌套结构、中文标点和工具异常返回；当核心格式合法率低于 99% 时，发布流程停止扩大流量。验收证据是评估集版本、CI 运行记录和一次故意失败的发布演练。

行动项关闭不是负责人说“做完了”，而是证据显示系统行为已经改变。

### 14.13.1 关闭条件和观察窗口

有些修复需要运行一段时间才能判断有效。例如，过期引用率、P99 延迟和真实用户投诉不是一次测试就能证明。关闭条件应写明：

- 最小样本量；
- 观察时长；
- 需要覆盖的用户或任务分桶；
- 允许的异常范围；
- 是否要比较 baseline；
- 失败时重新打开的条件。

如果只在修复后的第一条请求上看到成功，不能关闭一个线上事故行动项。

## 14.14 复盘会议要保护事实，也要保留责任

无责备文化的含义是：不要用事后信息把一个合理决策者变成替罪羊；它不等于没有责任、没有决定或没有改进。

一次有效的复盘会议可以按以下顺序进行：

1. 先确认任务合同和影响定义；
2. 读取事实证据和时间线；
3. 标注哪些结论是已知、未知或推测；
4. 找到第一处分歧；
5. 区分直接原因、促成条件和系统根因；
6. 确认止损和恢复是否完成；
7. 形成有负责人和验收标准的行动项；
8. 约定回归和观察窗口；
9. 将结果同步给受影响的团队和用户支持人员。

会议中不应从“谁改的”开始，也不应把所有问题归因于模型能力。与此同时，负责人和决定必须被记录：谁执行了变更、谁批准了放量、谁负责回滚、谁推动行动项关闭。事实责任和人格指责是两件不同的事。

## 14.15 三类事故的完整复盘

### 14.15.1 评估集污染：分数上涨但泛化没有提高

现象是新 SFT 模型在公开 benchmark 上提升 12 个百分点，真实任务没有改善。第一轮排查不能只看模型输出，而要检查：

- 训练数据和评估数据的 exact duplicate；
- 近重复和模板变体；
- 数据来源和时间；
- 评估题是否被开发过程反复查看；
- 私有 holdout 的结果；
- 真实用户任务的分桶结果。

如果提升集中在训练中出现过的题型，而私有 holdout、长上下文和多轮任务没有提升，结论应改成“对已见分布的表现提高”，而不是“通用能力提高”。

修复应包括：

- 训练和评估数据做 exact 与 near dedup；
- 建立来源和时间 lineage；
- 使用不参与开发的私有 holdout；
- 把真实任务、格式和安全边界加入评估；
- 报告污染证据等级和未确认范围；
- 将污染检查加入数据发布流程。

这个事故的行动项不应只是“换一个 benchmark”。如果数据 lineage、时间切分和污染检查仍然缺失，换题目只会把同一个问题推迟。

### 14.15.2 P99 推理抖动：平均吞吐掩盖尾延迟

现象是平均 tokens/s 正常，用户却频繁遇到流式卡顿。排查要按请求级时间线分解：

1. 按输入和输出 token 长度分桶；
2. 比较 TTFT、TPOT、队列时间和总延迟；
3. 查看长 prompt 是否阻塞短请求；
4. 检查 prefill 和 decode 是否争抢 token budget；
5. 检查 KV Cache 使用率和分配失败；
6. 对照客户端、网络和 GPU worker 时间戳；
7. 用真实混合分布重放，而不是只压短请求。

如果 P50 稳定而 P99 在高峰期恶化，平均吞吐不是反证。修复可以包括 chunked prefill、长短请求隔离、token budget、容量扩展和排队策略。回归需要验证短请求体验没有被长请求拖慢，同时检查总吞吐和成本变化。

事故报告应写出真实影响：多少请求超过 P95，哪些租户受到影响，用户可见的卡顿发生在首 token 还是 token 间隔，而不是只写“性能波动”。

### 14.15.3 Agent 工具误调用：合法参数不等于合法动作

一个用户查询订单状态，Agent 却调用了更新工具。排查证据可能显示：

- 用户输入含有“处理异常”的模糊词；
- query_order 和 update_order 的描述边界不清；
- 模型生成的 JSON 结构合法；
- 权限 token 有效；
- 工具层没有动作风险分级；
- 写操作没有确认；
- 评估只统计工具选择准确率，没有统计高风险误调用。

这里“JSON 合法”和“权限通过”都不能证明动作合法。系统需要把任务意图、工具权限、业务状态和用户确认分开检查。

修复应包括：

- 拆分只读与写入工具；
- 工具 schema 说明动作和副作用；
- 写操作先 dry-run，再明确确认；
- 后端校验业务状态和幂等键；
- 评估误调用、越权、重复提交和未知状态；
- 保存完整 trace 和审计记录。

如果工具已经改变了外部状态，恢复还要考虑撤销或人工补偿，而不是只把模型路由切回旧版本。

## 14.16 用状态和公式表达复盘质量

复盘指标的难点不在公式本身，而在于不能把缺失证据伪装成失败或通过。

设复盘记录集合为 P。对字段 j，如果记录存在且可验证，记为 eij=1；如果明确不适用，记为 not_applicable；如果理论上需要但缺失，记为 unknown。

### 14.16.1 比例和状态

对于非空且字段适用的集合 S：

$$
R =
\frac{\sum_{i\in S} y_i}{|S|}
$$

S 为空时，R 为 not_applicable。若 S 非空但所有 yi 都为 0，R 是有效的 0；若关键 y 缺失，状态为 unknown。

假设覆盖率、证据完整率、回归验证率都可以用这个形式表达，但它们的分母必须是各自适用的记录集合，不能把没有发生事故的实验强行放进事故时间线分母。

### 14.16.2 复盘字段覆盖

如果每条记录都要求 K 个字段，N 大于 0 且 K 大于 0，则：

$$
E =
\frac{1}{NK}
\sum_{i=1}^{N}\sum_{j=1}^{K} e_{ij}
$$

这个值只表示记录完整度。它不表示根因正确，也不表示行动项有效。一个内容完整但根因错误的报告，E 可能很高，系统风险却没有下降。

### 14.16.3 事故时间和变更失败率

检测、止损和恢复时间分别为：

$$
T_{\mathrm{detect}} =
t_{\mathrm{detect}}-t_{\mathrm{start}},
\quad
T_{\mathrm{mitigate}} =
t_{\mathrm{mitigate}}-t_{\mathrm{start}},
\quad
T_{\mathrm{recover}} =
t_{\mathrm{recover}}-t_{\mathrm{start}}
$$

变更失败率为：

$$
R_{\mathrm{change\_failure}} =
\frac{N_{\mathrm{failed\_change}}}
{N_{\mathrm{change}}}
$$

要求变更样本数大于 0。没有发布或变更的项目，这个指标不适用；有变更但失败字段缺失，指标未知。不能给分母加一个小常数来制造一个看似稳定的百分比。

### 14.16.4 证据状态的传播

一个复盘的整体状态可以按硬失败、未知和不适用传播：

- 任意硬性安全或恢复指标失败，整体为 failed；
- 没有硬失败但关键证据未知，整体为 unknown；
- 所有指标都不适用，整体为 not_applicable；
- 其余才可以说当前记录达到定义上的 passed。

这不是某个组织必须采用的唯一规则，而是一种防止“缺证据被当通过”的保守语义。硬风险不能被平均分数抵消，未知也不能被默认为安全。

## 14.17 一个可运行的复盘审计示例

下面的程序把实验和事故复盘记录放在同一张表里。它不模拟公司的事故平台，而是展示如何严格处理：

- 空集合；
- 缺失字段；
- 有效的失败 0；
- 非法布尔值；
- NaN；
- 没有发布时的 not_applicable；
- 有发布但失败字段缺失时的 unknown；
- P95 延迟和变更失败率的上限；
- 第一处分歧与后续行动的关系。

~~~python
from dataclasses import dataclass
from math import isfinite
from typing import Iterable, Optional


@dataclass(frozen=True)
class Metric:
    value: Optional[float]
    status: str
    reason: str = ""


STATUSES = {"passed", "failed", "unknown", "not_applicable"}


def make_metric(
    value: Optional[float],
    status: str,
    reason: str = "",
) -> Metric:
    if status not in STATUSES:
        raise ValueError(f"invalid status: {status}")
    if value is not None:
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            raise TypeError("metric value must be numeric or None")
        if not isfinite(float(value)):
            raise ValueError("metric value must be finite")
        value = float(value)
    return Metric(value, status, reason)


def bool_rate(
    records: list[dict],
    field: str,
    threshold: float,
) -> Metric:
    if not records:
        return make_metric(None, "not_applicable", "no records")
    if isinstance(threshold, bool) or not isinstance(threshold, (int, float)):
        raise TypeError("threshold must be numeric")
    values = []
    for record in records:
        if field not in record:
            return make_metric(None, "unknown", f"missing {field}")
        value = record[field]
        if type(value) is not bool:
            raise TypeError(f"{field} must be a real bool")
        values.append(value)
    observed = sum(values) / len(values)
    status = "passed" if observed >= threshold else "failed"
    return make_metric(observed, status, f"{sum(values)}/{len(values)}")


def quantile(
    values: list[float],
    probability: float,
) -> Metric:
    if not values:
        return make_metric(None, "not_applicable", "no values")
    if isinstance(probability, bool) or not isinstance(
        probability, (int, float)
    ):
        raise TypeError("probability must be numeric")
    if not isfinite(float(probability)) or not 0 <= probability <= 1:
        raise ValueError("probability must be in [0, 1]")
    checked = []
    for value in values:
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            raise TypeError("quantile values must be numeric")
        if not isfinite(float(value)) or value < 0:
            raise ValueError("quantile values must be finite and non-negative")
        checked.append(float(value))
    ordered = sorted(checked)
    if len(ordered) == 1:
        return make_metric(ordered[0], "passed", "one value")
    position = (len(ordered) - 1) * float(probability)
    lower = int(position)
    upper = min(lower + 1, len(ordered) - 1)
    fraction = position - lower
    value = ordered[lower] + fraction * (
        ordered[upper] - ordered[lower]
    )
    return make_metric(value, "passed", f"{len(ordered)} values")


def upper_limit(
    values: list[float],
    limit: float,
    label: str,
) -> Metric:
    if not values:
        return make_metric(None, "not_applicable", f"no {label}")
    if isinstance(limit, bool) or not isinstance(limit, (int, float)):
        raise TypeError("limit must be numeric")
    if not isfinite(float(limit)) or limit < 0:
        raise ValueError("limit must be finite and non-negative")
    observed = quantile(values, 0.95)
    if observed.value is None:
        return observed
    status = "passed" if observed.value <= float(limit) else "failed"
    return make_metric(observed.value, status, f"P95 {label} <= {limit}")


def failure_rate(
    records: list[dict],
    field: str,
    threshold: float,
) -> Metric:
    if not records:
        return make_metric(None, "not_applicable", "no change records")
    if isinstance(threshold, bool) or not isinstance(threshold, (int, float)):
        raise TypeError("threshold must be numeric")
    values = []
    for record in records:
        if field not in record:
            return make_metric(None, "unknown", f"missing {field}")
        value = record[field]
        if type(value) is not bool:
            raise TypeError(f"{field} must be a real bool")
        values.append(value)
    observed = sum(values) / len(values)
    status = "passed" if observed <= float(threshold) else "failed"
    return make_metric(observed, status, f"{sum(values)}/{len(values)} failed")


def mean_failed_recovery(records: list[dict]) -> Metric:
    failures = []
    for record in records:
        if "failed_change" not in record:
            return make_metric(None, "unknown", "missing failed_change")
        if type(record["failed_change"]) is not bool:
            raise TypeError("failed_change must be a real bool")
        if record["failed_change"]:
            if "recover_min" not in record:
                return make_metric(None, "unknown", "missing recover_min")
            value = record["recover_min"]
            if isinstance(value, bool) or not isinstance(value, (int, float)):
                raise TypeError("recover_min must be numeric")
            if not isfinite(float(value)) or value < 0:
                raise ValueError("recover_min must be finite")
            failures.append(float(value))
    if not records:
        return make_metric(None, "not_applicable", "no changes")
    if not failures:
        return make_metric(None, "not_applicable", "no failed changes")
    return make_metric(
        sum(failures) / len(failures),
        "passed",
        f"{len(failures)} failed changes",
    )


def overall_decision(metrics: Iterable[Metric]) -> str:
    metrics = list(metrics)
    if not metrics:
        return "not_applicable"
    if any(item.status == "failed" for item in metrics):
        return "repair_required"
    if any(item.status == "unknown" for item in metrics):
        return "evidence_incomplete"
    if all(item.status == "not_applicable" for item in metrics):
        return "not_applicable"
    return "reviewed_for_next_change"
~~~

示例中，not_applicable 只表示当前没有适用对象：没有发布，就没有变更失败率；没有失败变更，就没有失败变更平均恢复时间。项目有发布但某条失败记录缺少 recover_min 时，应该返回 unknown，而不是跳过该条记录。

False 是有效事实：有复盘、有发布、有回归记录，但字段明确为 False，覆盖率可以是 0，并且在阈值判断中失败。字段缺失、字段类型错误和 NaN 则属于数据质量问题，不能静默转成 False。

程序还把检测和恢复上限作为独立指标。即使所有文档字段都填写完整，恢复时间超出任务约束，整体仍然需要修复。反过来，复盘字段覆盖率很高也不能证明根因正确；代码只负责让语义可检查，工程团队仍然需要阅读样本和证据。

在这组构造数据中，假设、baseline、版本 trace、证据和时间线覆盖率都是 0.8，但分桶分析只有 0.6，预防措施只有 0.6，行动项关闭率和回归验证率都只有 0.4。部署记录的检测时间 P95 为 42.00 分钟，恢复时间 P95 为 885.15 分钟，变更失败率为 0.600，均超过示例上限；失败变更的平均恢复时间为 473.0 分钟，只说明已经发生的失败记录有一个可计算的平均值，并不能抵消恢复 P95 的失败。因此整体决定是 repair_required。第一处分歧分别落在假设、baseline 和时间线，说明不同事故需要从不同证据入口开始排查。

### 14.18.4 公式和程序的边界

这里的公式用于解释分母、状态、时间和覆盖率。不同组织可以选择不同的分位数、阈值和事故等级，只要定义、版本和适用范围清楚。

## 14.19 把一次失败变成下一次排查的起点

回到开头的三个事故，真正的修复不是各自写一份总结，而是把它们变成共同的工程能力。

评估集污染事故让团队建立数据来源、时间切分、近重复检测和私有 holdout；之后每次报告都能说明分数代表什么分布。

RAG 旧引用事故让团队把文档版本加入索引、缓存和请求 trace；之后发布索引时，构建成功只是一个阶段，版本一致性和过期引用回归也必须被验证。

Agent 误调用事故让团队区分合法格式、有效权限、业务允许和用户确认；之后工具评估不再只报选择准确率，还要观察副作用、未知外部状态和恢复路径。

一份成熟的实验报告让团队知道“为什么相信这个结果”；一份成熟的事故报告让团队知道“为什么当时会出错”；一份成熟的行动项记录让团队知道“系统具体改变了什么”；一份成熟的回归集和监控让团队知道“改变是否持续”。

失败不会自动产生经验。只有当事实被保存、假设被检验、影响被量化、根因被分层、行动项被验收、回归被运行，失败才会从一次损失变成组织能力。
