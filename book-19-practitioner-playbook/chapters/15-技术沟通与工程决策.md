# 第十五章：技术沟通与工程决策：把复杂系统讲清楚

## 15.1 一次发布为什么会在沟通中失败

一个企业助手准备上线新版本。算法报告写着“答案正确率提升 6 个百分点”，产品文档写着“支持复杂制度咨询”，服务文档写着“接口延迟满足要求”，安全评审写着“未发现高风险问题”。

这些句子分别看都像好消息，放在一起却没有形成可执行的结论。

产品负责人理解为：复杂制度咨询已经可以自动完成。算法工程师实际测量的是 500 条离线样本上的答案标签；服务团队测量的是短输入、低并发请求的平均延迟；安全团队只检查了拒绝样本，没有验证普通请求的误拒和检索缓存隔离。上线之后，长问题变慢，复杂政策引用不完整，普通员工在权限相邻的文档上得到错误提示，客服也不知道该把什么请求转给人工。

事故的触发点可能是模型、检索或配置，但项目在更早的地方已经失去共同语义：每个团队都说了一个局部正确的句子，却没有共同的主体、任务、分母、证据和失败边界。

技术沟通不是把术语翻译成更简单的词，而是让不同角色对同一个系统状态形成相同的可验证理解。工程师需要能够说明：

- 要解决的具体任务是什么；
- 当前结论由哪些证据支持；
- 哪些结论只在特定分桶成立；
- 方案带来了什么收益和代价；
- 哪些未知不能被忽略；
- 如果上线后出现偏差，谁负责决定、如何止损和怎样恢复。

真正成熟的表达会减少歧义，缩短决策时间，并让错误更早暴露。它不是个人修辞，而是系统可靠性的一部分。

## 15.2 技术沟通是一种接口设计

跨团队沟通和服务接口有相似之处。接口需要定义输入、输出、状态、错误和版本；技术沟通也需要定义事实来源、结论范围、未知状态和下一步行动。

一份有效的技术说明至少包含五层：

1. 结论：现在建议做什么。
2. 任务：这个结论服务于哪个用户和工作流。
3. 证据：哪些数据、日志、评估或实验支持它。
4. 边界：结论在哪些条件下不成立。
5. 行动：谁在什么时候完成什么可验证的改变。

如果只给结论，听者会用自己的经验填充背景；如果只给细节，听者可能找不到决定；如果不写边界，一个小范围结果很容易被传播成普遍承诺。

### 15.2.1 根据受众改变顺序，不改变事实

同一个系统，面向不同角色时，信息顺序可以不同：

| 受众 | 首先关心 | 需要看到 |
| --- | --- | --- |
| 产品 | 用户任务和业务影响 | 成功行为、失败边界、反馈 |
| 算法 | 误差和能力瓶颈 | 数据、分桶、bad case、实验 |
| 服务 | 延迟、容量和恢复 | trace、资源、依赖、回滚 |
| 安全 | 权限和副作用 | 数据流、工具动作、审计 |
| 业务 | 可用范围和风险 | 能做什么、不能做什么、人工兜底 |
| 值班人员 | 当前状态和动作 | 影响、止损、恢复、联系人 |

改变顺序不是迎合受众，也不是对不同团队讲不同事实。所有角色都应该能够回到同一份版本化证据，只是从自己最关心的入口理解。

### 15.2.2 先给行动，再给背景

线上事故中，值班人员需要先知道当前是否暂停放量、是否回滚、哪些用户受影响；设计评审中，决策者需要先知道推荐方案和未解决风险；实验复盘中，研究者需要先知道假设是否得到支持。

因此可以采用两层结构：

- 第一层：一句结论、状态、影响和下一步；
- 第二层：证据、方法、替代解释和详细记录。

这不是把细节隐藏起来。相反，它让需要深挖的人能快速进入原始证据，也让需要行动的人不必从几十页日志中猜决定。

## 15.3 用一页任务简报建立共同对象

复杂项目开始时，最容易缺失的是一个所有人都能引用的任务简报。它不应该是宣传文案，而是任务合同的压缩版本。

一页简报至少包括：

| 部分 | 具体问题 |
| --- | --- |
| 用户 | 谁发起请求，具有什么权限 |
| 工作流 | 请求发生在什么业务步骤 |
| 成功行为 | 用户完成了什么才算成功 |
| 失败行为 | 无证据、无权限或外部失败时怎样表现 |
| 主指标 | 最重要的结果和分母 |
| 护栏 | 质量、延迟、成本、安全限制 |
| 范围 | 当前版本包含和不包含什么 |
| 证据 | 评估集、baseline、线上样本和资料来源 |
| 负责人 | 谁执行、谁决定、谁需要被同步 |
| 恢复 | 如何暂停、回滚、降级和转人工 |

例如：

> 本版本服务已经登录的普通员工，只回答当前生效且用户有权限访问的制度问题。主指标是一次可采用率，评估单位为完整用户任务；护栏包括引用支持率不低于 90%、P95 总延迟不超过 5 秒、权限文档进入上下文的比例为 0、单成功任务成本不超过预算。资料缺失、版本冲突或权限不足时必须明确说明无法确认，不自动猜测。灰度先覆盖内部用户，旧模型、Prompt、索引和策略组合保留为可切回版本。

这段文字比“支持复杂制度咨询”长，却更接近可执行合同。它告诉产品如何定义功能，告诉算法如何构造评估，告诉服务如何做监控，也告诉安全和客服什么情况不能被当成普通回答失败。

### 15.3.1 任务简报中的动词要能验收

“提升”“优化”“增强”“支持”“保障”都需要继续追问对应行为：

- 提升什么指标；
- 优化哪个阶段；
- 增强哪个分桶；
- 支持哪些输入和输出；
- 保障哪种风险不发生。

把抽象动词改成可验收动作：

- “支持多轮”变成“在连续三轮中保留用户、文档版本和待确认字段”；
- “提升引用”变成“每个关键 claim 至少有一个当前版本的支持片段”；
- “保障安全”变成“检索前按主体权限过滤，写工具在后端校验并记录确认”；
- “降低成本”变成“单成功任务成本下降，同时任务成功率和 P95 不超过边界”。

## 15.4 事实、结论和未知要分层

技术文档中经常把观察直接写成原因，把原因直接写成决定。例如：

> 新 Prompt 导致延迟上升，所以应该回滚。

这句话可能有三个问题：延迟是否真的上升，是否与 Prompt 改动时间一致，是否还有 top-k、流量或服务配置变化。更稳妥的写法是分层：

- 事实：Prompt v13 在 10:20 发布，P95 从 4.1 秒升到 6.2 秒；
- 关联：延迟上升主要出现在长 context 请求，和输出 token 增长同时发生；
- 假设：Prompt v13 可能增加了输出长度，但 top-k v8 也在同一时段变更；
- 决定：先暂停 Prompt 和 top-k 的共同灰度，分别回退并重放同一请求；
- 未知：目前还不能把延迟变化全部归因于 Prompt。

### 15.4.1 结论要带证据等级

可以把结论分成：

1. 已直接观察：有原始 trace、日志或重复实验；
2. 高度支持：多个独立证据一致，但仍有替代解释；
3. 工作假设：适合指导下一步排查，尚未证实；
4. 未知：关键记录缺失或证据冲突；
5. 不适用：当前任务没有该组件或事件。

这些状态不是修辞。把未知写成“没有问题”，会让后续决策建立在虚假确定性上；把不适用写成“缺失”，会产生不必要的修复；把工作假设写成根因，会让行动项指向错误位置。

### 15.4.2 用证据表代替口头争论

一个简单的证据表可以是：

| 主张 | 证据 | 反例或替代解释 | 当前状态 | 下一步 |
| --- | --- | --- | --- | --- |
| 召回不足导致答案错 | 正确文档不在候选集 | 查询改写也可能丢实体 | 高度支持 | 比较 hybrid retrieval |
| Prompt 使输出变长 | Prompt 变更后输出 token 上升 | top-k 同时变化 | 工作假设 | 拆分回放 |
| 权限过滤正确 | 过滤日志显示通过 | 缓存 key 未含权限版本 | 未知 | 做跨租户回归 |
| 工具未产生副作用 | 工具返回成功 | 外部状态尚未回读 | 未知 | 查询后端状态 |

证据表让讨论从“我觉得”转向“哪个主张还缺什么证据”。它也能直接变成实验计划和事故行动项。

## 15.5 讲清 baseline 和指标，避免把数字变成口号

一个结果只有放在对照和定义中才有意义。

介绍 baseline 时，要说明：

- 原系统是什么；
- 原系统在哪些场景有效；
- 原系统在哪里失败；
- 失败是否由数据、模型、检索或系统造成；
- 候选版本保持了哪些条件不变。

介绍指标时，要说明：

- 样本单位；
- 分母；
- 标签来源；
- 评估集版本；
- 分桶；
- 是否有人工复核；
- 成本、延迟和安全护栏；
- 统计不确定性和未知记录。

“准确率提高 10%”至少有四种不同含义：

1. 从 60% 到 70% 的绝对提高 10 个百分点；
2. 相对提高 10%，例如从 60% 到 66%；
3. 只有某一分桶提高；
4. judge 分数提高，但用户任务没有提高。

必须把用词和计算方式写清楚。设 baseline 成功率为 Rb，候选为 Rc，则绝对变化为：

$$
\Delta R = R_c-R_b
$$

当 Rb 大于 0 时，相对变化为：

$$
\Delta_{\mathrm{rel}} =
\frac{R_c-R_b}{R_b}
$$

评估集为空时，比例不适用；baseline 成功率为 0 时，相对变化没有定义。工程说明中应同时写成功数、样本数和状态。

### 15.5.1 分桶结果要先说最重要的差异

不要把十几个指标平铺给读者。先指出最影响决定的差异：

> 候选版本总体正确率从 78% 到 84%，但提升主要来自短事实问题；高频简单问题 P95 增加 1.6 秒，复杂制度问题的引用支持率下降 4 个百分点。因此，这不是全量发布的证据，只支持在低延迟分桶中继续灰度。

这样的表达不是隐藏总分，而是把总分放回业务判断中。

### 15.5.2 解释一个坏数字比展示一个好数字更有价值

如果某个指标下降，应说明：

- 下降是否在预期范围；
- 是否换来了更重要的改善；
- 哪些用户会受到影响；
- 是否有补救和恢复路径；
- 这个取舍是否被任务合同允许。

“安全拒绝率上升”可能是风险控制变好，也可能是正常请求被误拒。必须同时看漏拒、误拒、任务完成和用户反馈。

## 15.6 不要用术语堆叠代替架构说明

复杂系统的沟通不是把所有组件名称说一遍。听者真正需要知道的是：请求如何流动，每个阶段解决什么问题，哪里可能失败，怎样观测和恢复。

以企业 RAG 为例，可以按请求路径讲：

~~~text
用户身份和任务
    |
问题解析与查询改写
    |
权限前置过滤
    |
dense / sparse / hybrid retrieval
    |
reranker
    |
版本和时效检查
    |
context construction
    |
模型生成
    |
claim 与 citation 校验
    |
回答、拒答或人工转交
~~~

每一层至少说明四件事：

1. 输入是什么；
2. 输出是什么；
3. 主要错误是什么；
4. 通过什么指标或 trace 观察。

例如，reranker 不应只描述成“提升精度的模块”。更清楚的说法是：它接受召回候选和用户查询，输出排序后的证据列表；主要错误是把旧版本或相似但不支持结论的片段排在前面；观察指标包括 MRR、context precision、版本冲突率和阶段延迟。

### 15.6.1 用一条请求讲清系统

系统设计文档可以挑一条真实请求，逐步展示：

- 用户身份和权限；
- 原始问题；
- 查询改写；
- 候选文档及分数；
- 过滤掉的文档及原因；
- 最终 context；
- 模型输出；
- claim 与引用；
- 记录的版本；
- 用户反馈或后续动作。

这条请求比一张只有方框和箭头的架构图更能暴露协议缺口。它会逼迫团队回答“权限在哪里检查”“版本在哪里记录”“没有证据时怎样返回”“工具状态如何回读”。

## 15.7 解释 Debug 过程要按证据顺序展开

别人问“你是怎么排查的”时，最有用的不是列出所有尝试，而是说明为什么按这个顺序排查。

一个通用的排查顺序是：

1. 确认现象和影响范围；
2. 验证是否可复现；
3. 固定输入和版本；
4. 与稳定 baseline 比较；
5. 沿链路寻找第一处分歧；
6. 检查替代解释；
7. 做最小修复；
8. 用原样本和邻近反例验证；
9. 观察线上是否再次出现。

### 15.7.1 训练问题

loss spike 出现后，先检查：

- 异常 batch；
- label mask；
- 有效 token 数；
- NaN 和 Inf；
- gradient norm；
- 学习率和 warmup；
- AMP overflow；
- rank 间状态；
- checkpoint 和 optimizer state。

如果直接先调学习率，可能把数据或 mask 问题掩盖掉。沟通时应说明每一步排除了什么可能性，以及哪条证据让判断发生了变化。

### 15.7.2 RAG 问题

RAG 答错时，按以下顺序检查：

1. 正确文档是否存在；
2. 文档解析和版本是否正确；
3. 权限过滤是否在召回前生效；
4. 正确证据是否进入候选集；
5. reranker 是否把它排到可用位置；
6. context 是否被截断或污染；
7. 模型是否忽略证据；
8. citation 是否真的支持 claim；
9. 资料不足时是否应当拒答。

如果正确文档没有进入候选集，修改生成 Prompt 通常不是第一修复点。若证据已经在 context 中，才有必要研究模型阅读和引用行为。

### 15.7.3 推理问题

用户反馈卡顿时，不能只报平均 tokens/s。应拆分：

- queue time；
- TTFT；
- prefill；
- TPOT；
- decode；
- tool 或检索等待；
- transport；
- P95 和 P99；
- 输入输出长度；
- KV Cache 使用和分配。

如果 P50 稳定而 P99 在高峰期恶化，应把请求按长度和租户分桶，检查长 prompt 是否阻塞短请求，再观察调度和资源分配。这样沟通的是排查路径，而不是一个“性能优化”的空结论。

### 15.7.4 Agent 问题

Agent 工具失败时，需要区分：

- 任务理解；
- 计划可执行性；
- 工具选择；
- 参数合法性；
- 权限和确认；
- 工具返回状态；
- 中间状态更新；
- 最终叙述是否与外部状态一致。

合法 JSON 只证明格式合法，权限 token 有效只证明身份或授权字段通过。它们都不等于业务动作被允许，更不等于动作已经成功。

### 15.7.5 Debug 的最小证据包

一次可复查的排查，至少需要一份最小证据包。它不要求把所有日志都搬进报告，而要求保存足够还原第一处分歧的对象：

1. 脱敏后的原始输入；
2. 期望行为和判断来源；
3. 实际输出、工具动作或系统状态；
4. baseline 和候选版本；
5. 模型、Prompt、索引、工具、安全策略和运行配置；
6. 请求 trace、阶段时间和错误码；
7. 第一处分歧及其证据；
8. 已排除的替代解释；
9. 临时止损和恢复动作；
10. 进入回归集的样本编号。

例如，一个引用错误的 RAG 请求不应只保存最终回答。还要保留用户权限、文档候选、排序结果、最终 context、文档生效时间和 citation claim。这样才能区分“正确文档没有召回”“正确文档被过滤”“正确文档没有进入 context”和“模型没有遵循 context”。

一个 Agent 工具误调用也不应只保存模型生成的 JSON。还要保存用户确认状态、工具注册表版本、后端权限判定、请求前后的外部状态和幂等键。若外部状态没有回读，报告必须把动作结果标为 unknown，而不是从工具返回格式推断成功。

一个推理长尾问题则需要输入输出 token、排队时间、prefill、decode、KV Cache 状态、取消和重试记录。只保存平均吞吐，无法证明短请求是否被长请求阻塞。

最小证据包的价值在于把排查从“讲一个故事”变成“复查一条链”。它也保护团队免于过度收集敏感数据：只保存定位问题所需的字段，并让原始证据回到受控存储。

### 15.7.6 把排查过程写成可复用路径

排查记录不应只是按时间排列的尝试，还应说明每一步改变了什么判断：

~~~text
观察：普通制度问题引用旧版本
假设 A：检索没有召回新版本
检查：候选列表包含新版本，否定 A
假设 B：缓存返回旧排序结果
检查：cache key 没有 document_version，支持 B
最小修复：加入版本字段并清理相关缓存
回归：旧版、新版、版本冲突和无权限样本
线上观察：旧引用率和 P95 在灰度窗口内恢复
~~~

这种记录能让后来的人知道为什么没有继续修改 Prompt，也能让新的相似事故快速复用排查路径。好的工程沟通会保存被否定的假设，因为它们同样能减少未来的搜索空间。

## 15.8 讲取舍时同时给收益、代价和选择理由

技术决策不是列出“方案 A、B、C”就结束。读者需要知道为什么选择某个方案，以及被放弃的代价。

一个完整取舍至少写四项：

1. 目标收益；
2. 直接代价；
3. 被放弃的替代方案；
4. 验证取舍是否可接受的指标。

例如：

> 更强 reranker 可以提高复杂问题的 context precision，但增加检索阶段延迟和 GPU 成本。全量启用的方案被放弃，因为简单高频问题的 P95 已接近上限。最终按问题类型路由：简单问题使用轻量检索，跨文档或高风险问题启用 reranker。通过引用支持率、P95、单任务成本和转人工率验证取舍。

常见取舍包括：

| 取舍 | 收益 | 代价 | 需要观察 |
| --- | --- | --- | --- |
| 更大模型 | 复杂推理可能更强 | 延迟、成本、资源 | 分桶质量、P95、成本 |
| 更大 top-k | 证据召回可能提高 | 噪声、上下文和延迟 | Recall、precision、P95 |
| 更长上下文 | 可能保留更多证据 | KV Cache、注意力稀释 | 证据支持、显存、长尾 |
| 更严格拒答 | 可能降低漏拒 | 误拒和任务损失 | 漏拒、误拒、完成率 |
| 更多自动工具 | 人工操作减少 | 副作用和恢复复杂 | 确认、幂等、误调用 |
| 更激进量化 | 资源成本降低 | 格式和长尾质量风险 | 分桶回归、吞吐、错误率 |

如果没有代价，通常说明方案还没有被认真分析，或者代价尚未被观测。

## 15.9 用决策记录替代口头记忆

技术决策记录不是会议纪要。它应该保存一个决定的背景、选项、证据、取舍和重新打开条件。

推荐结构：

~~~text
标题：按任务类型启用 reranker
状态：accepted
背景：复杂制度问题引用支持率低，简单问题 P95 已接近 5 秒
候选方案：
  A. 全量 reranker
  B. 所有请求继续轻量检索
  C. 按问题类型路由
决定：C
理由：在复杂问题上改善证据排序，同时控制高频简单请求的延迟和成本
证据：eval_v18 分桶结果、线上 P95、成本压测
未解决：复杂问题分类器存在误分
监控：citation support、P95、reranker 调用率、转人工
回滚：关闭路由并回到轻量检索
重开条件：复杂问题误分超过 8%，或引用支持率在灰度中下降
负责人：服务负责人和检索负责人
~~~

好的决策记录能让新成员知道为什么系统不是“最强方案”，也能让未来团队在条件变化后重新评估，而不是重复争论过去已经解决的问题。

### 15.9.1 记录被拒绝的方案

被拒绝的方案同样有价值。记录“为什么不全量启用更强模型”“为什么不让 Agent 自动写入”“为什么不把所有文档塞进 context”，可以防止团队在换一批人后再次从同一个误区开始。

被拒绝不是永久否定。只要写明条件，例如成本下降、数据质量改善、出现新的回滚能力或风险边界变化，未来就能有依据地重新打开。

## 15.10 事故沟通要短、准、可行动

事故发生时，第一条通知的目标不是解释全部根因，而是让相关人知道影响和动作。

一条合格的初始更新包括：

- 当前状态；
- 影响范围；
- 已采取的止损；
- 是否暂停放量或回滚；
- 下一次更新时间；
- 事件负责人；
- 仍然未知的部分。

示例：

> 状态：正在处理。09:42 至 10:08，租户 A、B 的制度问答出现旧版本引用，影响范围仍在核对。已暂停索引 v47 灰度并切回 v46，新的请求旧引用比例正在下降。当前未确认是否存在敏感文档泄露，安全团队正在核查访问记录。下一次更新在 15 分钟后，由服务负责人统一发布。

这条消息没有过早宣布根因，也没有把未知写成没有风险，但它足够支持业务和客服采取动作。

### 15.10.1 进度更新和结案报告不同

进度更新追求及时，允许保留未知；结案报告追求完整，必须补充影响、根因、证据和行动项。不要在事故最初为了看起来确定而编造完整解释，也不要在恢复后只发一句“已修复”。

结案报告至少要说明：

- 影响起止时间；
- 受影响请求和用户；
- 检测和止损时间；
- 直接原因和系统原因；
- 为什么原有检查没有发现；
- 修复是否经过回归和灰度；
- 仍然存在的未知；
- 行动项和验收证据。

### 15.10.2 事故消息的状态转换

事故沟通可以按状态转换组织，而不是每次重新写一段散文：

| 状态 | 必须说明 | 不应过早声称 |
| --- | --- | --- |
| suspected | 观察、时间、当前影响和负责人 | 已确认根因 |
| contained | 止损动作、剩余影响和用户兜底 | 已完全修复 |
| recovering | 回滚或修复进度、验证样本和下一更新时间 | 没有遗留风险 |
| recovered | 服务状态、指标恢复和观察窗口 | 根因已彻底消失 |
| closed | 影响、根因、行动项和回归证据 | 所有未来风险为零 |

例如，在 suspected 状态下可以说“旧版本引用比例上升，正在验证缓存和索引”，不能说“索引发布失败”；在 recovered 状态下可以说“新请求指标恢复，进入两小时观察”，不能说“问题不会再出现”。

状态词必须和监控证据绑定。否则，消息从 suspected 直接跳到 closed，只是把未知从正文中删除，并没有减少风险。

### 15.10.3 不同受众共享同一事件 ID

产品、客服、安全和工程团队可能需要不同粒度的内容，但都应引用同一事件 ID、时间窗口和版本组合。这样：

- 客服可以知道哪些用户需要重新处理；
- 产品可以知道功能是否暂时关闭；
- 安全可以追查访问和传输；
- 工程可以回到 trace 和配置；
- 管理者可以看到影响和恢复进度。

如果每个团队各写一份相互独立的事故描述，稍微不同的时间和影响数字就会造成第二轮协调事故。统一事件 ID 不要求所有人看到同样的敏感细节，而是要求不同视图能回到同一事实来源。

## 15.11 处理跨团队分歧：先对齐对象，再讨论方案

很多争论不是技术意见不同，而是团队在讨论不同对象：

- 产品说“用户觉得不好用”，算法说“benchmark 更高”；
- 安全说“应该拒绝”，业务说“正常请求被挡住”；
- 服务说“平均吞吐够了”，产品说“用户一直卡”；
- 数据团队说“样本很多”，评估团队说“关键长尾没有覆盖”。

解决分歧的第一步不是投票，而是把讨论对象写成共同指标和任务单位。

可以按以下顺序推进：

1. 复述双方的主张；
2. 写出各自主张使用的样本和分母；
3. 区分硬约束和软性取舍；
4. 找到最小共同实验；
5. 指定决定人和截止时间；
6. 保存不同意见和未解决风险。

例如，若安全误拒和业务任务损失冲突，可以分桶测量：

- 高风险请求的漏拒率；
- 普通请求的误拒率；
- 任务完成率；
- 人工升级率；
- 用户可接受度；
- 策略版本和样本来源。

争论会从“安全太严格”变成“哪类请求的误拒超过了任务合同，怎样在不提高漏拒的情况下降低它”。

## 15.12 成本、延迟和安全要用同一张决策表

一个只展示质量的报告，会把系统推向不可持续；一个只展示成本的报告，会掩盖任务失败；一个只展示安全拒绝率的报告，会掩盖正常用户损失。

对候选版本，可以建立：

| 维度 | baseline | 候选 | 变化 | 边界 | 状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| 一次可采用率 | 0.78 | 0.84 | +0.06 | 不低于 0.80 | passed |
| 引用支持率 | 0.91 | 0.88 | -0.03 | 不低于 0.90 | failed |
| P95 延迟 | 4.1s | 6.2s | +2.1s | 不高于 5s | failed |
| 单成功任务成本 | 0.11 | 0.14 | +0.03 | 不高于 0.13 | failed |
| 权限泄露率 | 0 | unknown | unknown | 必须为 0 | unknown |
| 普通请求误拒率 | 0.04 | 0.11 | +0.07 | 按任务合同 | failed |

这张表不需要把所有维度压缩成一个总分。硬性安全和权限问题应先单独处理；在硬性风险可接受后，再比较质量、成本和延迟的软性取舍。

## 15.13 文档要让别人能够接手

高质量技术沟通的终点不是“作者讲得很好”，而是别人能继续做决定和排查。

一份可接手的文档应提供：

- 术语和对象定义；
- 任务合同；
- 版本和依赖；
- baseline；
- 指标及分母；
- 典型输入输出；
- bad case 和错误分类；
- 监控和告警；
- 发布、回滚和降级；
- 未解决风险；
- 联系人和责任；
- 决策历史。

文档还应该有更新时间、适用版本和失效条件。一个没有版本的架构图会在系统变化后继续误导新成员；一个没有样本来源的指标会在评估集变化后继续制造虚假趋势。

### 15.13.1 让代码和文档互相校验

如果文档说接口会返回 unknown，而代码只返回 True 或 False，说明协议已经不一致。可以用以下方式减少漂移：

- 从 schema 生成示例；
- 将指标定义和测试放在同一仓库；
- 用回归样本检查文档中的关键行为；
- 在发布清单中记录文档版本；
- 变更接口时同时更新 runbook；
- 用真实 trace 抽样检查文档字段是否存在。

沟通质量最终要落到系统状态，而不是停留在文字层。

### 15.13.2 交接不是把链接发出去

一个项目交接至少需要一次可验证的接手过程。接手人应当能够：

1. 找到任务合同和当前范围；
2. 用已记录的 baseline 重现一个结果；
3. 从请求 trace 找到模型、Prompt 和索引版本；
4. 运行核心回归集；
5. 解释关键监控和告警；
6. 在低风险环境执行一次回滚或降级；
7. 找到未解决风险和责任人；
8. 知道事故发生时的第一条沟通路径。

如果接手人只能听作者口头讲解，说明知识还没有进入系统。交接演练中暴露出的缺字段、失效链接和不能运行的命令，应当进入项目行动项，而不是被当成接手人的个人问题。

文档也会失效。模型、Prompt、索引、工具和策略变更后，原来的流程图和指标定义可能不再准确。因此可以给关键文档增加：

- 适用版本；
- 最后验证时间；
- 失效条件；
- 负责人；
- 复核周期；
- 对应回归或演练记录。

文档维护不是写作任务的附属工作，而是让团队在人员变化和事故压力下仍能保持共同状态的工程能力。

## 15.14 公式：把表达质量拆成可检查的维度

本节公式不是招聘评分标准，也不是用一个数字替代人的判断。它们用来检查一份技术说明是否遗漏关键维度。

### 15.14.1 主张覆盖率

设说明中的主张集合为 C。对每个主张 c，若它有可定位证据、适用边界和下一步动作，分别记为 e(c)、b(c)、a(c)，取值为 0 或 1。若 |C| 大于 0，则：

$$
Q_{\mathrm{claim}} =
\frac{1}{3|C|}
\sum_{c\in C}
\left(e(c)+b(c)+a(c)\right)
$$

C 为空时，该指标不适用。主张存在但没有证据时，得分为有效 0，不应被当作未知；若证据字段缺失且无法判断，整体状态应为 unknown。

### 15.14.2 取舍深度

设取舍集合为 T。对每个 t，收益、代价、替代方案和验证方式分别是 u(t)、v(t)、a(t)、w(t)，则：

$$
Q_{\mathrm{tradeoff}} =
\frac{1}{4|T|}
\sum_{t\in T}
\left(u(t)+v(t)+a(t)+w(t)\right)
$$

T 为空时不适用。只说“用了更强模型”没有成本、延迟和替代方案，不能算完整取舍。

### 15.14.3 决策记录完整度

设一条决策记录需要 K 个字段，N 条记录中的字段存在且可验证记为 eij，则 N 大于 0 且 K 大于 0 时：

$$
Q_{\mathrm{decision}} =
\frac{1}{NK}
\sum_{i=1}^{N}
\sum_{j=1}^{K}
e_{ij}
$$

该指标只测记录完整度，不测决定是否正确。错误决定也可能被写得很完整，因此必须配合结果、回归和线上观察。

### 15.14.4 事件沟通时效

设事件开始、首次通知、止损和恢复时间分别为 tstart、tnotice、tmitigate、trecover：

$$
T_{\mathrm{notice}} =
t_{\mathrm{notice}}-t_{\mathrm{start}}
$$

$$
T_{\mathrm{mitigate}} =
t_{\mathrm{mitigate}}-t_{\mathrm{start}},
\qquad
T_{\mathrm{recover}} =
t_{\mathrm{recover}}-t_{\mathrm{start}}
$$

没有事故时，这些指标不适用；事故发生但通知时间缺失时，通知时效 unknown。时效不能代替通知内容的正确性，快速发布错误信息可能扩大影响。

### 15.14.5 状态传播

对一组指标，若任一硬性安全或恢复指标 failed，则整体为 failed；否则若关键指标 unknown，则整体为 unknown；如果所有指标 not_applicable，则整体为 not_applicable；其余才为 passed。

这套传播规则防止缺失证据被当作通过，也防止用平均分抵消硬性风险。不同团队可以调整阈值，但不能省略状态语义。

## 15.15 一个可运行的技术沟通审计示例

下面的程序检查四份工程简报，分别模拟稳定的 RAG 发布说明、性能事故说明、安全事故说明和一个范围过大的技术提案。它不评价文风，而检查：

- 主张是否有证据、边界和动作；
- 取舍是否同时说明收益、代价、替代方案和验证；
- 关键字段是否缺失；
- 事故通知是否及时；
- 成本、延迟和安全状态是否被隐藏；
- 空集合、缺失字段、有效 0、非法布尔值和 NaN 是否被正确区分。

~~~python
from dataclasses import dataclass
from math import isfinite
from typing import Iterable, Optional


@dataclass(frozen=True)
class Metric:
    value: Optional[float]
    status: str
    reason: str = ""


STATUSES = {"passed", "failed", "unknown", "not_applicable"}


def make_metric(
    value: Optional[float],
    status: str,
    reason: str = "",
) -> Metric:
    if status not in STATUSES:
        raise ValueError(f"invalid status: {status}")
    if value is not None:
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            raise TypeError("metric value must be numeric or None")
        if not isfinite(float(value)):
            raise ValueError("metric value must be finite")
        value = float(value)
    return Metric(value, status, reason)


def bool_rate(
    records: list[dict],
    field: str,
    threshold: float,
) -> Metric:
    if not records:
        return make_metric(None, "not_applicable", "no records")
    values = []
    for record in records:
        if field not in record:
            return make_metric(None, "unknown", f"missing {field}")
        value = record[field]
        if type(value) is not bool:
            raise TypeError(f"{field} must be a real bool")
        values.append(value)
    observed = sum(values) / len(values)
    status = "passed" if observed >= threshold else "failed"
    return make_metric(observed, status, f"{sum(values)}/{len(values)}")


def claim_coverage(claims: list[dict]) -> Metric:
    if not claims:
        return make_metric(None, "not_applicable", "no claims")
    required = ["evidence", "boundary", "action"]
    scores = []
    for claim in claims:
        for field in required:
            if field not in claim:
                return make_metric(None, "unknown", f"missing claim {field}")
            if type(claim[field]) is not bool:
                raise TypeError(f"claim {field} must be a real bool")
        scores.append(sum(claim[field] for field in required) / len(required))
    observed = sum(scores) / len(scores)
    status = "passed" if observed >= 0.8 else "failed"
    return make_metric(observed, status, f"{len(claims)} claims")


def tradeoff_depth(items: list[dict]) -> Metric:
    if not items:
        return make_metric(None, "not_applicable", "no trade-offs")
    required = ["benefit", "cost", "alternative", "validation"]
    scores = []
    for item in items:
        for field in required:
            if field not in item:
                return make_metric(None, "unknown", f"missing trade-off {field}")
            if type(item[field]) is not bool:
                raise TypeError(f"trade-off {field} must be a real bool")
        scores.append(sum(item[field] for field in required) / len(required))
    observed = sum(scores) / len(scores)
    status = "passed" if observed >= 0.75 else "failed"
    return make_metric(observed, status, f"{len(items)} trade-offs")


def upper_limit(
    records: list[dict],
    field: str,
    limit: float,
) -> Metric:
    if not records:
        return make_metric(None, "not_applicable", "no incident records")
    values = []
    for record in records:
        if field not in record:
            return make_metric(None, "unknown", f"missing {field}")
        value = record[field]
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            raise TypeError(f"{field} must be numeric")
        if not isfinite(float(value)) or value < 0:
            raise ValueError(f"{field} must be finite and non-negative")
        values.append(float(value))
    observed = max(values)
    status = "passed" if observed <= limit else "failed"
    return make_metric(observed, status, f"{field} <= {limit}")


def overall_decision(metrics: Iterable[Metric]) -> str:
    metrics = list(metrics)
    if not metrics:
        return "not_applicable"
    if any(item.status == "failed" for item in metrics):
        return "repair_required"
    if any(item.status == "unknown" for item in metrics):
        return "evidence_incomplete"
    if all(item.status == "not_applicable" for item in metrics):
        return "not_applicable"
    return "ready_for_review"


BRIEFS = [
    {
        "id": "rag_release_note",
        "objective": True,
        "baseline": True,
        "metrics": True,
        "constraints": True,
        "evidence": True,
        "uncertainty": True,
        "decision": True,
        "risks": True,
        "rollback": True,
        "owner": True,
~~~

## 15.17 从“会说”到“能让系统前进”

技术沟通的最终衡量标准不是语言漂亮，而是团队是否因此做出了更准确、更可恢复的决定。

一份好的任务简报会让产品知道功能边界，让算法知道评估分母，让服务知道监控和回滚，让安全知道数据和动作边界。

一份好的实验报告会让团队知道为什么相信一个结果，也知道结果在哪些分桶不成立。

一份好的设计决策记录会保存被放弃的方案、代价和重新打开条件，避免每次人员变化都从头争论。

一份好的事故更新会让受影响的人及时采取动作，同时诚实保留未知；一份好的结案报告会把根因、行动项和回归证据连接起来。

当沟通具备目标、证据、边界、取舍和行动时，复杂系统就不再依赖某个熟悉它的人的口头记忆。工程知识能够被审查、接手、复现和修正，这才是资深工程能力真正留下的东西。
