# 第五章：分布式训练事故的状态与证据

分布式训练把一个训练过程拆到多个 rank、节点和并行维度上。它能够提供显存、吞吐和模型规模，却也把一个局部问题变成全局故障：某个 rank 数据读取慢，所有 rank 都在 collective 等待；某个 shard 没保存，整个 checkpoint 不能恢复；某个节点的环境变量不同，训练可能只在多机时出现异常；按样本数分片看起来均匀，按 token 数却严重倾斜。

分布式事故的排查对象不是“多卡是否能跑”，而是每个 rank 是否在同一个状态协议上推进。每个 step 的输入、phase、collective 顺序、数据量、耗时、loss、版本和保存状态都要能对齐。只有这样，卡死、吞吐下降、loss skew、显存反常和恢复失败才有可能被分成不同问题，而不是统称为“分布式不稳定”。

本章使用一个四 rank 的 toy 训练事件贯穿讨论：rank 2 落后，rank 1 少了一次 collective，rank 3 分到更多 token 并成为 straggler，同时 checkpoint 缺 shard、resume 后学习率跳变、pipeline micro-batch 过少。示例不启动真实多进程，而是展示真实系统应该记录什么、怎样定义未知状态和怎样避免零分母伪装。

## 5.1 分布式训练首先是状态一致性问题

第 `r` 个 rank 在第 `t` 个 step 的局部状态可以抽象为：

```math

u_{r,t}=(s_{r,t},p_{r,t},b_{r,t},n_{r,t},T^{step}_{r,t},T^{data}_{r,t},T^{comm}_{r,t},q_{r,t},v_r)
```

其中：

- `s` 是 step 或 global step；
- `p` 是当前 phase，例如 dataloader、forward、backward、collective、optimizer；
- `b` 是 batch 或 shard 标识；
- `n` 是本 rank 处理的 token 数；
- `T` 是阶段耗时；
- `q` 是已经调用或即将调用的 collective 序列；
- `v_r` 是该 rank 的代码、容器、驱动、CUDA、NCCL、模型和数据版本。

如果只记录 rank 0 的 step 和 loss，无法知道其他 rank 是已经到达同一步、停在 dataloader、停在 backward、还是等待 collective。分布式日志必须保留 rank 维度，并允许从同一个 step 关联所有 rank 的局部事件。

分布式系统的“正常”也不是每个 rank 的 loss 必须完全相等。不同数据 shard 的 loss 可以不同；真正需要满足的是关键同步阶段的协议一致、数据和状态符合计划、差异在可解释范围内。把所有局部差异都当成故障，会误报；把所有差异都平均掉，会漏报。

## 5.2 先画出一次 step 的阶段图

一个典型数据并行 step 可以表示为：

```text
rank r:
  data loader
    -> batch validation
    -> forward
    -> loss / backward
    -> gradient synchronization
    -> optimizer step
    -> logging / checkpoint coordination
```

模型并行、流水线并行、FSDP 和 ZeRO 会在其中插入 all-gather、reduce-scatter、send/recv、参数重建和 shard 保存，但它们仍然需要一个可比的阶段序列。

发生卡死时，第一步不是调整网络参数，而是确定每个 rank 最后完成的 phase：

- 如果某个 rank 停在 data loader，先看文件系统、worker、数据 shard 和空 batch；
- 如果所有 rank 都在同一个 collective 前后，检查通信、拓扑和 collective 参数；
- 如果只有一个 rank 进入 collective，检查条件分支、异常处理和 batch 数量；
- 如果某个 rank 先抛异常，其他 rank 等待是结果，不是根因；
- 如果卡死只出现在保存或评估阶段，检查全局同步和 rank 0 特殊路径。

把 phase 写入日志比一句“程序卡住了”更有价值，因为它能把调查范围从整个集群缩小到一个状态转换。

## 5.3 Rank 对齐与 collective 顺序

若第 `t` 个观察点所有 rank 的 step 相同，step 对齐可以写成：

```math

A_{step}(t)=\mathbf{1}[\max_r s_{r,t}=\min_r s_{r,t}]
```

这个指标只有在每个预期 rank 都有记录时才有定义。缺失 rank 不是“它和其他 rank 一样”，而是 `unknown` 或直接异常。

Collective 序列也需要一致。设参考序列为 `q*`，每个 rank 实际序列为 `q_r`：

```math

C_{coll}(t)=\mathbf{1}[q_r=q^*\text{ 对所有预期 rank 成立}]
```

生产实现还需要比较 collective 的类型、顺序、张量形状、dtype 和参与 rank 集合。一个 rank 因条件分支跳过 `all_reduce`，其他 rank 继续等待，最终表现为 NCCL timeout；timeout 是表面症状，collective 协议不一致才是更接近根因的描述。

常见来源包括：

1. 只在 rank 0 执行的分支没有配套同步。
2. 某 rank 得到空 batch 后提前 `continue`。
3. 异常处理只在本地捕获，其他 rank 不知道它已经退出当前 phase。
4. eval、save 或日志路径在不同 rank 执行了不同的 collective。
5. pipeline stage 或 tensor parallel group 的成员配置不一致。
6. 恢复后 world size、rank mapping 或 shard 组改变。

## 5.4 Rank 卡死的调查路径

一次 rank 卡死应先建立时间线：最后一个正常 step、每个 rank 最后一个 phase、最后一次完成的 collective、最近的数据读取和最近一次保存。然后再查看 NCCL、驱动、网络和存储日志。

建议记录的最小事件：

```text
rank=2 step=122 phase=dataloader batch=shard_2_122 start=...
rank=0 step=122 phase=all_reduce_grad start=...
rank=1 step=122 phase=all_reduce_grad start=...
rank=3 step=122 phase=all_reduce_grad done=...
```

这几行已经能说明：rank 2 尚未进入同一个阶段，rank 0 和 rank 1 正在等待，rank 3 可能已经完成或正在等待其他参与者。没有 phase 和 rank 的日志，只能看到全局没有新输出。

小 world size、单机多卡和单卡回放是有用的缩小实验，但它们分别排除了不同因素：

- 单卡可以排除通信和 rank 协议，但保留数据、模型和数值问题；
- 单机多卡可以观察本机互联和 collective，但不能覆盖跨节点网络；
- 小 world size 可以降低同步复杂度，却可能改变 bucket、负载和拓扑；
- 多机回放才真正验证跨节点通信和环境一致性。

实验结果要记录“哪些因素被排除”，不能把单卡正常写成“系统没有问题”。

## 5.5 Token shard 不均比样本数不均更重要

对大语言模型，样本长度差异很大。每个 rank 样本数相同，并不意味着计算量、激活量和通信时长相同。若每个 rank 的 token 数为 `n_r`，且所有 rank 都有正 token 记录，token 不均衡比率为：

```math

I_{token}=\frac{\max_r n_r}{\min_r n_r}
```

如果某个 rank 的 token 数为 0，比例没有正常定义，应单独标记空 shard 或数据切分错误。不能把分母换成一个固定正数后继续宣称负载均衡。

还要同时观察：

- 平均和最大序列长度；
- 每个 rank 的来源、语言和任务分布；
- 有效 label token，而不仅是 input token；
- data loader 时间和存储路径；
- padding 比例和动态 batch 行为。

按样本数均衡适合长度相近的数据；对长短差异大的语言数据，更合理的策略可能是按 token、长度桶或估算计算量分配。按 token 均衡也不代表统计分布完全一致，仍需检查语言、领域和质量切片。

## 5.6 Straggler：最慢 rank 决定整体速度

同步训练的 step 完成时间通常受最慢 rank 影响。设各 rank step 时间为 `T_r`，中位数为 `median(T)`，当中位数大于 0 时，可以定义：

```math

R_{straggle}=\frac{\max_r T_r}{median_r(T_r)}
```

如果没有 rank 记录或中位数为 0，指标未定义。straggler 比率高时，应继续拆解 `T_data`、计算时间和 `T_comm`，因为“慢”可能来自完全不同的层。

常见 straggler 来源：

- 一个 rank 分到了更长的序列；
- 共享存储在某个节点抖动；
- dataloader worker 死锁或 CPU 不足；
- GPU 时钟、温度、显存或硬件状态异常；
- 网络拓扑、RDMA 或网卡选择不一致；
- all-gather 或 reduce-scatter 被最慢链路拖住。

只看平均 step time 会掩盖 straggler。应保留按 rank 的 P50/P95、最长 step、阶段耗时和对应 batch。

## 5.7 计算、数据和通信的关键路径

若某个 step 的阶段完全串行，总时间可以近似写成：

```math

T_{step}=T_{data}+T_{compute}+T_{comm}+T_{other}
```

现实中计算和通信可能 overlap，因此这些项不能盲目相加。trace 应记录阶段开始和结束时间，并用关键路径而不是简单总和解释吞吐。

当 `T_step>0` 时，rank `r` 的通信占比为：

```math

R_{comm,r}=\frac{T_{comm,r}}{T_{step,r}}
```

若 `T_step=0`，比例未定义；如果计时缺失，也应标记 `unknown`。通信占比高不一定意味着 NCCL 有问题，可能是 batch 太小、gradient bucket 不合适、计算通信没有重叠、跨节点拓扑不佳或 pipeline stage 切分不均。

对比单机多卡和多机多卡时，要固定模型、batch、序列长度、通信组和数据加载条件。多机吞吐下降才说明跨节点路径可能是瓶颈；单机也下降则应先查 batch、bucket、显存或计算配置。

## 5.8 数据、通信和环境三类证据要分开

分布式事故常被笼统归为“网络问题”，但至少要区分：

| 证据类别 | 典型观察 | 下一步 |
| --- | --- | --- |
| 数据/负载 | token 不均、某 rank data time 高、空 shard | 检查 sampler、长度桶和存储 |
| 通信/拓扑 | comm time 高、collective timeout、带宽/重传异常 | 检查 NCCL、网卡、RDMA 和拓扑 |
| 环境/硬件 | 只有某节点异常、版本或驱动不同、GPU 降频 | 对齐镜像并检查节点健康 |

启动前环境 manifest 应至少包含 CUDA、driver、PyTorch、NCCL、Python 包、容器镜像、环境变量、挂载路径和 GPU 型号。版本不一致并不一定立刻报错，可能只在某种 collective、dtype 或 checkpoint 路径下表现出来。

NCCL debug 日志和通信 benchmark 能提供证据，但它们是诊断工具，不是修复。把所有环境变量调成“更激进”并不能证明拓扑或网络正确；任何配置改变都要有固定 workload 对照。

## 5.9 Checkpoint：保存 shard 不等于保存训练状态

分布式 checkpoint 需要保存模型参数、优化器状态和运行位置的分片。设预期 shard 集合为 `S_expected`，实际保存集合为 `S_saved`，且 `|S_expected|>0`，覆盖率为：

```math

C_{ckpt}=\frac{|S_{saved}\cap S_{expected}|}{|S_{expected}|}
```

只有 shard 文件齐全还不够，还要检查每个 shard 的 hash、metadata、optimizer、scheduler、scaler、global step、数据位置和版本。只保存 rank 0 权重可能得到一个可以推理的文件，却不是一个可恢复的训练状态。

保存过程中某个 rank 失败，其他 rank 可能已经写入部分文件。恢复程序不能因为目录存在就认为 checkpoint 完整；应使用 manifest、完成标记和原子提交，区分“正在写入”“写入失败”和“完整可恢复”。

定期 restore test 是必要的。至少用小规模作业验证：保存前后模型输出、optimizer state、scheduler step、scaler、随机状态和数据 sampler 是否达到预期。没有恢复演练的 checkpoint 只能称为“已写入文件”，不能称为“已验证恢复”。

## 5.10 Resume 连续性和 world size 变化

恢复训练时，应该比较加载状态和预期状态：

```math

D_{resume}=|s_{loaded}-s_{expected}|+\lambda|\eta_{loaded}-\eta_{expected}|
```

其中 `lambda` 只是把 step 和学习率差异映射到同一审计分数的教学权重；更重要的是分别记录两个差异。若 global step、consumed tokens 或实际学习率的定义不一致，`D_resume` 不能被解释为连续性证明。

world size 变化会影响数据分片、global batch、optimizer 状态布局和通信组。某些框架支持重分片，某些 checkpoint 只适合原 world size。恢复前要明确：

- 是否允许改变 world size；
- optimizer state 是否能重新分片；
- sampler 和 consumed tokens 如何迁移；
- pipeline、tensor、data parallel group 如何重建；
- 旧 rank 的 shard 如何映射到新 rank。

加载成功只能说明文件和代码走通，不能说明训练曲线、数据顺序和优化状态连续。

## 5.11 FSDP/ZeRO 显存反常

FSDP 和 ZeRO 的目标是减少每个设备保存的参数、梯度或 optimizer state，但显存峰值还受到 all-gather、参数重建、activation、通信 buffer、offload、checkpoint state dict 和临时张量影响。

看到“开了 sharding 反而更占显存”时，先拆峰值发生在哪个 phase：

1. forward 参数 all-gather；
2. activation 和 activation checkpointing；
3. backward reduce-scatter；
4. optimizer step；
5. full state dict 保存；
6. offload 和 CPU/GPU 传输缓冲。

比较方案时要固定 batch、序列长度、precision、activation checkpointing 和保存方式。DDP、ZeRO stage、FSDP 不同配置的显存数字不能直接横比。一个方案平均显存较低，但保存 full state dict 时峰值爆掉，仍然不满足运行约束。

## 5.12 Pipeline bubble：切分之后还要看空转

流水线并行把模型分成 `P` 个 stage，用 `M` 个 micro-batch 填充和排空流水线。一个理想化的 bubble 比例近似为：

```math

B_{pipe}\approx\frac{P-1}{M+P-1}
```

要求 `P>=1`、`M>=1`。当 micro-batch 很少时，stage 会在流水线填充和排空期间空转；stage 计算量不均时，慢 stage 还会进一步降低有效吞吐。

优化不能只增加 micro-batch。还要考虑梯度累积、显存、通信、激活保存、调度策略和 stage 层数。一个 stage 的计算时间明显高于其他 stage 时，增加 `M` 可能只让所有 stage 等待慢 stage。

## 5.13 日志和监控要能够回答事故问题

每个 rank、step 和 checkpoint 需要关联以下数据：

```text
run_id / job_id / node_id / rank
code / image / CUDA / driver / NCCL versions
world_size / parallel groups / seed
step / global_step / phase / batch_id
sample_count / token_count / effective_label_tokens
loss / rank_loss / lr / grad_norm / overflow
data_time / compute_time / communication_time / step_time
collective name / sequence / shape / dtype
checkpoint id / shard / write status / restore status
```

监控数据也需要保留敏感信息边界。batch ID 和内容 hash 通常比完整训练文本更适合进入一般日志；原始数据应在受控存储中按权限查看。日志缺失、rank 缺失或计时为零要被标记为 `unknown`，不能自动填充为正常。

## 5.14 分布式事故的逐级复现

分布式故障应逐级增加复杂度：

1. 固定 batch 的单卡前向、反向和 optimizer step。
2. 单机多卡，验证本机 collective 和数据 shard。
3. 小 world size 多机，验证跨节点通信和环境。
4. 目标 world size，验证真实 bucket、拓扑和 checkpoint。
5. 目标流量、保存频率和恢复流程。

每一级都要报告 loss、tokens/s、step time、memory、comm ratio、数据顺序和失败状态。如果问题只在多机出现，优先排除数据和单卡数值问题后再查网络、环境和通信组；如果问题在单卡已存在，扩大 world size 只会增加排查噪声。

## 5.15 分布式事故指标的定义域

### 5.15.1 Step 对齐

在所有预期 rank 都有 step 记录时：

```math

A_{step}=\mathbf{1}[\max_r s_r=\min_r s_r]
```

缺少 rank 记录应为 `unknown`，而不是把现有 rank 的最小最大值当成全局结论。

### 5.15.2 Token 不均衡

当所有 rank token 数都大于 0 时：

```math

I_{token}=\max_r n_r/\min_r n_r
```

存在零 token shard 时，先处理空 shard，不生成正常比例。

### 5.15.3 Straggler

当 rank step time 的中位数大于 0 时：

```math

R_{straggle}=\max_r T_r/median_r(T_r)
```

缺失或零计时不能作为良好性能的证据。

### 5.15.4 Checkpoint 覆盖

```math

C_{ckpt}=|S_{saved}\cap S_{expected}|/|S_{expected}|
```

`S_expected` 为空时不适用；预期集合非空但实际 shard 缺失时，覆盖率为真实比例并附带缺失列表。

### 5.15.5 通信占比

```math

R_{comm,r}=T_{comm,r}/T_{step,r}
```

每个 rank 都必须有正的 step time。并行 overlap 时，比例是观测指标，不一定等于关键路径上的纯通信占比。

这些指标不应被强行乘成一个总分。分布式事故通常需要同时知道“是否协议一致”“是否负载均衡”“是否能恢复”，不同失败项的动作不同。

## 5.16 一个可运行的分布式事故审计示例

下面的示例不启动真实进程，只使用标准库和四条 rank 日志。它展示如何在缺失、零值和版本状态异常时返回明确结果，而不是用 `max(1, ...)` 把数据问题隐藏掉。

```python
from dataclasses import dataclass
from math import isfinite
from statistics import median
from typing import Dict, List, Optional, Tuple


def strict_int(value: object) -> bool:
    return type(value) is int


def require_non_negative_int(name: str, value: object) -> None:
    if not strict_int(value) or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")


def require_positive_finite(name: str, value: object) -> None:
    if type(value) not in (int, float) or not isfinite(float(value)):
        raise ValueError(f"{name} must be finite")
    if float(value) <= 0:
        raise ValueError(f"{name} must be positive")


def safe_ratio(numerator: int, denominator: int) -> Optional[float]:
    require_non_negative_int("numerator", numerator)
    require_non_negative_int("denominator", denominator)
    if numerator > denominator:
        raise ValueError("numerator cannot exceed denominator")
    if denominator == 0:
        return None
    return round(numerator / denominator, 3)


@dataclass(frozen=True)
class RankStep:
    rank: int
    step: int
    phase: str
    tokens: int
    step_ms: float
    data_ms: float
    comm_ms: float
    collectives: Tuple[str, ...]
    loss: float


def validate_rank(row: RankStep) -> None:
    require_non_negative_int("rank", row.rank)
    require_non_negative_int("step", row.step)
    require_non_negative_int("tokens", row.tokens)
    if not row.phase.strip():
        raise ValueError("phase must not be empty")
    for name, value in (
        ("step_ms", row.step_ms),
        ("data_ms", row.data_ms),
        ("comm_ms", row.comm_ms),
        ("loss", row.loss),
    ):
        if type(value) not in (int, float) or not isfinite(float(value)):
            raise ValueError(f"{name} must be finite")
        if float(value) < 0:
            raise ValueError(f"{name} must be non-negative")
    if row.step_ms <= 0:
        raise ValueError("step_ms must be positive")
    if not row.collectives or any(not item.strip() for item in row.collectives):
        raise ValueError("collectives must contain non-empty names")


def checkpoint_audit(expected: List[int], saved: List[int]) -> Dict[str, object]:
    if not expected:
        return {"state": "not_applicable", "coverage": None, "missing": []}
    if len(expected) != len(set(expected)) or len(saved) != len(set(saved)):
        raise ValueError("checkpoint shard ids must be unique")
    expected_set = set(expected)
    saved_set = set(saved)
    coverage = len(expected_set & saved_set) / len(expected_set)
    return {
        "state": "complete" if coverage == 1.0 else "incomplete",
        "coverage": round(coverage, 3),
        "missing": sorted(expected_set - saved_set),
    }


def resume_audit(
    expected_step: int,
    loaded_step: int,
    expected_lr: float,
    loaded_lr: float,
) -> Dict[str, object]:
    require_non_negative_int("expected_step", expected_step)
    require_non_negative_int("loaded_step", loaded_step)
    require_positive_finite("expected_lr", expected_lr)
    require_positive_finite("loaded_lr", loaded_lr)
    return {
        "step_delta": loaded_step - expected_step,
        "lr_delta": round(loaded_lr - expected_lr, 6),
        "continuous": loaded_step == expected_step and abs(loaded_lr - expected_lr) <= 1e-8,
    }


def pipeline_audit(stages: int, micro_batches: int, stage_ms: List[float]) -> Dict[str, object]:
    require_non_negative_int("stages", stages)
    require_non_negative_int("micro_batches", micro_batches)
    if stages == 0 or micro_batches == 0:
        return {"state": "unknown", "bubble": None, "slow_stage": None}
    if len(stage_ms) != stages:
        raise ValueError("stage_ms length must equal stages")
    for value in stage_ms:
        require_positive_finite("stage_ms", value)
    bubble = (stages - 1) / (micro_batches + stages - 1)
    slow_stage = max(range(stages), key=lambda index: stage_ms[index])
    return {
        "state": "observed",
        "bubble": round(bubble, 3),
        "slow_stage": slow_stage,
    }


def audit(
    rows: List[RankStep],
    expected_collectives: Tuple[str, ...],
    expected_shards: List[int],
    saved_shards: List[int],
) -> Dict[str, object]:
    if not rows:
        return {"state": "unknown", "reason": "no_rank_logs"}
    if not expected_collectives:
        raise ValueError("expected_collectives must not be empty")
    for row in rows:
        validate_rank(row)
    ranks = [row.rank for row in rows]
    if len(ranks) != len(set(ranks)):
        raise ValueError("rank ids must be unique")

    steps = {row.rank: row.step for row in rows}
    step_alignment = len(set(steps.values())) == 1
    mismatches = {}
    for row in rows:
        missing = [item for item in expected_collectives if item not in row.collectives]
        extra = [item for item in row.collectives if item not in expected_collectives]
        if missing or extra:
            mismatches[row.rank] = {"missing": missing, "extra": extra}

    tokens = [row.tokens for row in rows]
    if min(tokens) == 0:
        token_imbalance = None
        token_state = "unknown"
    else:
        token_imbalance = round(max(tokens) / min(tokens), 3)
        token_state = "observed"

    step_times = [row.step_ms for row in rows]
    typical = median(step_times)
    if typical <= 0:
        straggle_ratio = None
        stragglers = []
    else:
        straggle_ratio = round(max(step_times) / typical, 3)
        stragglers = [row.rank for row in rows if row.step_ms > 1.5 * typical]

    comm_ratios = {
        row.rank: round(row.comm_ms / row.step_ms, 3) for row in rows
    }
    checkpoint = checkpoint_audit(expected_shards, saved_shards)
    checks = {
        "step_alignment": step_alignment,
        "collective_sequence": not mismatches,
        "token_balance": token_state == "observed" and token_imbalance <= 2.0,
        "straggler": not stragglers,
        "communication": max(comm_ratios.values()) <= 0.35,
        "checkpoint": checkpoint["state"] in {"complete", "not_applicable"},
    }
    missing_evidence = []
    if token_state == "unknown":
        missing_evidence.append("zero_token_rank")
    if checkpoint["state"] == "not_applicable":
        missing_evidence.append("no_checkpoint_plan")
    state = "failed" if not all(checks.values()) else "observed_stable"
    if state == "observed_stable" and missing_evidence:
        state = "unknown"
    return {
        "state": state,
        "steps": steps,
        "step_alignment": step_alignment,
        "collective_mismatch": mismatches,
        "token_imbalance": token_imbalance,
        "straggle_ratio": straggle_ratio,
        "stragglers": stragglers,
        "communication_ratios": comm_ratios,
        "checkpoint": checkpoint,
        "checks": checks,
        "missing_evidence": missing_evidence,
    }


rows = [
```

## 5.17 从事故到恢复

分布式事故处理应分为止损、定位、修复和恢复验证：

1. 暂停扩大训练或停止可能覆盖证据的重试。
2. 保存每个 rank 的最后 phase、step、batch、collective 和环境版本。
3. 标记受影响 checkpoint，不把部分 shard 当作可恢复版本。
4. 在单卡、单机多卡、小 world size 和多机环境中逐级复现。
5. 修复数据切分、collective 顺序、环境、网络、checkpoint 或并行配置。
6. 用固定 workload 比较 step time、token balance、通信占比和 loss。
7. 运行 save/restore 和 world size 迁移测试。
8. 在真实拓扑和目标保存频率下观察一个完整窗口。

回滚到旧 checkpoint 只能限制损失，不能证明当前代码、环境和数据切分已经正确。恢复验证必须回答“是否从正确 step、正确 shard、正确 optimizer/scheduler 状态和正确数据位置继续”。

## 5.18 常见但危险的处理方式

### 只看 rank 0

rank 0 正常不代表所有 rank 已到达同一 phase。事故记录必须有 rank 维度。

### 看到 timeout 就调长 timeout

延长 timeout 可能让故障更晚暴露，却没有修复 collective 不一致、数据卡住或网络退化。先找最后 phase 和最后一次一致的 collective。

### 只按样本数均衡

长序列任务中样本数均匀可能对应 token 数四倍差异。按 token、长度桶和实际 data time 检查负载。

### 看到 FSDP/ZeRO 就默认省显存

all-gather、activation、full state dict 和 offload buffer 都可能造成峰值。必须按 phase 和保存路径 profile。

### checkpoint 目录存在就继续训练

目录存在不等于 shard 完整、manifest 完整、optimizer 和 scheduler 已保存。恢复前必须做覆盖和连续性检查。

### 把单机结果推广到多机

单机不能覆盖跨节点网络、RDMA、网卡选择和容器环境差异。规模扩展必须逐级验证。

## 5.19 资料与证据边界

本章参考以下公开资料：

- PyTorch DistributedDataParallel、FSDP 和 Distributed Checkpoint 文档用于说明 rank、shard、状态和恢复接口的公开边界；具体训练循环仍需检查自定义逻辑。
- NVIDIA NCCL 文档和环境变量说明用于通信、拓扑和诊断背景；NCCL 日志不能单独证明根因是网络。
- DeepSpeed ZeRO 论文和文档用于参数、梯度与 optimizer state 分片的机制背景；显存和吞吐需要在目标硬件上实测。
- GPipe、Megatron-LM 和流水线并行资料用于说明 micro-batch、stage balance 和 bubble 的关系；理想公式不包含所有通信、调度和负载不均。
- OpenTelemetry 和 SRE 监控资料用于 trace、阶段耗时和事件关联的通用方法；分布式训练还需要记录 rank、collective、shard 和数据状态。

官方文档支持公开 API、配置和协议说明，不支持把某个环境的吞吐、带宽或 checkpoint 行为写成普遍结论。任何性能数字都必须绑定 GPU、节点、拓扑、batch、序列长度、precision、world size 和软件版本。

## 5.20 本章小结

分布式训练事故的关键不是“卡多所以复杂”，而是多个 rank 必须在同一个状态协议上推进。先对齐 step、phase 和 collective，再检查 token 负载、关键路径和 straggler；先验证 checkpoint shard 和训练状态，再讨论恢复；先做单卡、单机多卡、小 world size 反事实，再扩大到真实多机环境。

当日志能够回答每个 rank 在哪里、拿到了什么数据、调用了什么 collective、花了多少时间、保存了哪些 shard、恢复了哪个 step，分布式训练就不再是只能靠经验猜测的黑箱。卡死、慢、显存反常和 resume 异常可以分别定位，也可以通过固定回归和恢复演练转化为可持续的工程能力。
