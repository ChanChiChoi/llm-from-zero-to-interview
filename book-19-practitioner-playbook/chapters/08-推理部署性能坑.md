# 第八章：推理部署性能坑：平均吞吐变高，用户却更卡

推理部署是大模型从实验室进入生产环境后的第二次考试。离线评估只能说明模型在给定输入上回答得怎样，不能说明服务是否能在高并发、长上下文、网络抖动、客户端取消和依赖变慢时稳定工作。

这里的**推理服务**是模型收到输入后逐步生成输出、并由服务端交付给调用者的整条路径。用户先等待首 token 延迟（time to first token，TTFT），再等待后续 token 持续流出；后续 token 平均间隔常用每输出 token 时间（time per output token，TPOT）表示。服务端通常把输入上下文一次或分块送入预填充（prefill）阶段，再逐步进入解码（decode）阶段。键值缓存（key-value cache，KV Cache）保存注意力计算中可复用的 K/V（键/值）状态，避免每一步都从头重算历史 token。模型输入上下文也常叫 prompt，通常由系统指令、对话历史、检索内容、工具说明和本轮用户输入组成。检索增强生成（retrieval-augmented generation，RAG）先从外部资料中检索相关内容，再把选出的证据放入 prompt。

推理性能不是一个数字。平均每秒输出 token 数变高，可能只是系统在每轮把更多 token 放进批次；如果新来的短请求因此排在长请求后面，用户反而会觉得系统变慢。P50、P95、P99 分别表示中位数、第 95 和第 99 百分位。本章从一次“吞吐提升但投诉增加”的事故开始，逐层解释 TTFT、TPOT、端到端延迟、尾延迟、prefill/decode、KV Cache、分页管理、批处理调度、量化、prompt 成本、流式传输、缓存、限流、容量规划和质量回归，并明确空样本、单 token 输出、取消请求、零分母和未知状态的语义。

## 8.0 先看一场吞吐上升的事故

下面是一场为讲解而构造的事故，不是生产测量记录。某团队把推理服务的批处理（batch）调度参数改大，GPU（图形处理器）利用率从 45% 上升到 75%，集群平均输出吞吐从每秒 24 token 上升到每秒 32 token。监控首页显示绿色，发布负责人认为优化成功。

几个小时后，客服收到“输入后很久没有反应”和“回答一顿一顿”的投诉。进一步拆分请求发现：短问题的首 token 等待时间明显增加，长上下文请求占满了 KV Cache，P99 端到端延迟超过用户可接受范围；缓存命中率几乎没有改善，prompt 比旧版本膨胀，代码和 JSON（JavaScript Object Notation，一种结构化文本格式）输出质量也发生回归。

先跟一条短问答的时间线。为便于手算，这里把请求发出和到达服务入口视为同一时刻，暂不计入站网络。请求在 `t=0 ms` 到达；调度器让它等到 `t=180 ms` 才能运行；模板和 tokenizer（分词器）在 `40 ms` 内准备好输入；prefill 再用 `160 ms` 处理上下文并产出首 token 所需的 logits；服务端用 `40 ms` 完成首 token 选择、组装并写出首个流式块，因此服务端写出时间是 `180+40+160+40=420 ms`。假设网络再用 `70 ms` 把块送到客户端，客户端用 `40 ms` 渲染，用户在 `530 ms` 看到内容；按本章客户端接收边界，TTFT 是 `420+70=490 ms`，渲染延迟另计。

把 batch 参数调大后，更多 token 可以共用 GPU 的一次调度，集群总输出从每秒 24 token 增至每秒 32 token；但这条短请求的调度等待若从 `180 ms` 增至 `430 ms`，它的 TTFT 就从 `490 ms` 变成 `740 ms`，客户端渲染时间不变时，用户看到内容也会晚 `250 ms`。这个小例子展示了因果链：调度改变了请求等待时间，因此总体吞吐上升并不保证单个用户更早看到回答。餐厅比喻中，“排队”对应服务队列，“首道菜上桌”对应首 token，“后续上菜间隔”对应生成间隔，“整桌完成”对应请求完成；真实推理还会把多条请求放进同一设备批次，token 之间有自回归依赖，所以比喻不能用来推导 GPU 性能。

本章反复使用的事故链是：

```text
请求到达 -> 网关/鉴权 -> tokenizer 与 prompt 组装 -> 排队
        -> prefill -> 首个 token -> decode 循环 -> 流式发送
        -> 客户端接收/渲染 -> 完成、取消、计费和质量记录
```

如果只在 GPU 进程里记录一个“平均生成速度”，就无法判断用户到底卡在了哪一段。RAG 链路先检索文档，再把选出的内容放进模型输入；检索、重排和组装 prompt 的耗时发生在模型预填充之前。

## 8.1 性能目标先写成用户和系统的共同约束

在调 batch、换量化或更换推理引擎之前，先写清楚服务要保护的对象。聊天问答、代码补全、批量摘要和 Agent 工具调用的性能目标不同。

聊天问答通常更在意 TTFT 和流式间隔；代码补全可能更在意短请求的 P95（第 95 百分位）；批量摘要可以接受更高 TTFT，但希望单位成本和总吞吐稳定；Agent（由模型按步骤调用工具、并根据工具结果继续处理的应用）还要把工具调用、重试和外部依赖算进完整任务延迟。

这几种任务不该只用同一个 token 吞吐目标衡量。JITServe 的 NSDI 2026 论文把服务目标区分为流式交互的逐 token 延迟、工具触发等任务的完整响应截止时间（deadline），以及包含多次依赖调用的复合请求；它以满足请求目标的有效服务产能（service goodput）作为系统目标。这个分类有助于选对测量单位；论文报告的性能数字只适用于其工作负载、硬件和基线，不能当作通用承诺。[JITServe, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/zhang-wei)

SLO（service-level objective，服务等级目标）是针对一个明确请求或任务单位设定的性能目标；它必须说明测量边界和分母，不能只写成“系统延迟要低”。一个可执行的性能合同至少包含：

```text
请求单位：单轮请求、完整会话，还是一次完整任务
输入分布：input token 的 P50、P95、最大值和长上下文占比
输出分布：实际生成 token、取消、截断和空输出比例
用户目标：TTFT、TPOT、端到端延迟和可接受尾部
系统目标：吞吐、GPU/CPU（图形处理器/中央处理器）利用率、KV Cache、错误率和单位成本
质量目标：格式、代码、引用、安全和工具协议不能退化到什么程度
降级策略：超长输入、依赖故障、队列拥塞和容量不足时如何处理
```

没有输入输出分布的“单卡 QPS”很容易误导。相同 QPS 下，输入从 500 token 变成 5,000 token，prefill、KV Cache 和成本都可能发生数量级变化；相同输入下，输出从 80 token 变成 800 token，decode 时间和活跃状态也会改变。

### 8.1.1 三种吞吐不要混在一起

至少要区分三种产能。QPS（queries/requests per second，每秒请求数）数的是请求到达或处理频率；它没有记录每条请求包含多少输入和输出 token，因此不能单独表示模型工作量。

1. **prefill 吞吐**：单位时间处理的输入 token，影响新请求的首 token；
2. **decode 吞吐**：单位时间生成的输出 token，影响持续流式速度；
3. **任务吞吐**：单位时间完成的有效任务，必须扣除失败、取消、重试和人工接管。

GPU 报告的 token 数可能是算子处理量，网关报告的 token 数可能是已经发送的 token，产品报告的任务数则可能只计算用户采纳的结果。三者都可以叫吞吐，但不能直接比较。

### 8.1.2 质量是性能合同的一部分

量化、截断、缓存、降级模型和更激进的采样都可能改变质量。若性能优化导致 JSON 解析失败、代码测试失败、RAG 引用不支持或安全边界漂移，重试和人工介入会反过来增加总成本。

因此性能压测需要带着一小组质量回归集运行：短问答、长上下文、代码/结构化输出、工具调用、拒答边界和真实业务样本。性能结果不能脱离质量结果独立宣布。

## 8.2 先把请求记录成可以回放的 trace

一次请求如果只能在日志里看到 `latency=3.2s`，它几乎不能用于排障。至少要把请求拆成阶段，并保留每阶段的开始、结束、状态和版本。trace（追踪记录）可把请求跨越的组件串起来；span（阶段记录）保存某个组件的开始和结束。分布式时间戳应来自可比较的时钟；跨主机没有时钟同步时，优先使用各组件内部的持续时间，不能直接相减不一致的墙钟时间。

可以把第 `i` 个请求记录成下面的 trace。`a_i` 是客户端发出时间；`n_i` 是请求到达服务入口的网络时间；`q_i` 是排队时间；`z_i` 是分词、模板和 prompt 组装时间；`p_i` 是 prefill 到首 token 所需 logits 产出的时间；`f_i` 从这一步之后开始，包含首 token 选择、首块发送与传输，直到首个流式块抵达所选客户端观测端；`d_i` 保存首块之后可观测的输出间隔。若这些阶段并行或重叠，应保存各自起止时间并按 span 归因，不能把重叠时长重复相加。

```math
r_i=(a_i,n_i,q_i,z_i,p_i,f_i,d_i,u_i,k_i,e_i,v_i)
```

其中 `u_i` 记录输入、计划/实际输出和业务切片；`k_i` 记录 KV Cache、前缀缓存（prefix cache）和 batch 状态；`e_i` 记录错误、取消、超时和依赖状态；`v_i` 记录模型、模板、引擎、精度和部署版本。某项字段无法采集时要保留 `unknown`；该请求在指标定义域之外时才记 `not_applicable`。这两种状态不能在聚合时都当作零。

### 8.2.1 请求级字段不能被平均掉

排障必须保留以下字段的原始值或可重建摘要：

```text
request_id、假名化 tenant/user 范围标识、arrival、queue_start、prefill_start、first_token
input_tokens、max_output_tokens、emitted_tokens、cancel_reason、finish_reason
model_id、checkpoint、tokenizer、chat_template、precision、engine_version
batch_id、running_batch_size、prefill_budget、decode_budget、priority
kv_requested、kv_allocated、kv_evicted、prefix_hit_tokens、cache_key_version
gateway_send、client_receive、client_render、upstream/tool spans
quality_status、parse_error、safety_status、cost、retry_count
```

trace 用来关联同一请求的阶段，不需要保存原始用户身份或完整 prompt；租户/用户字段应使用受控的假名化标识，并遵循服务的数据保留策略。

用户取消尤其重要。取消不是普通成功请求的尾部样本，也不一定是模型质量问题；但如果取消集中发生在首 token 之前，它就是用户感知延迟的证据。完成、取消、超时、服务错误和质量失败应保持不同状态。

### 8.2.2 阶段边界必须互相对齐

如果 worker 认为 `first_token=1200ms`，网关认为 `first_chunk=1600ms`，客户端认为 `first_render=2400ms`，三个数字都可能正确，因为它们测量的边界不同。监控命名应明确：

```text
model_first_token：模型生成第一个 token
server_first_chunk：服务端准备发送的第一个 chunk
client_first_byte：客户端收到首字节
client_first_render：界面真正显示内容
```

只有边界一致的指标才能做版本对比。否则团队可能误以为模型变慢，实际是代理缓冲或前端渲染变慢。

## 8.3 TTFT、TPOT 和端到端延迟的定义域

### 8.3.1 TTFT 不是模型 forward 的别名

先固定 TTFT 的起点和终点。本章默认的用户侧 TTFT 从客户端发送请求开始，到客户端收到第一个流式输出块结束。若把入站网络、请求排队、输入准备、prefill 和首块传输按不重叠时间记录，可分解为：

```math
\mathrm{TTFT}^{client}_i=n_i+q_i+z_i+p_i+f_i
```

这里的 `n_i` 是客户端发出到服务入口的入站网络时间；`f_i` 从 prefill 产出首 token 所需 logits 后开始，包含首 token 选择、服务端发送和到所选客户端观测点的传输。若只测服务端生成首 token，得到的是另一条边界；若要解释“界面何时显示”，还应继续记录客户端渲染。公式假设各阶段非负、边界不重叠；若分布式 span 发生重叠，应按起止时间计算关键路径，不能直接相加。

指标名称本身不能保证测量边界一致。以 vLLM v0.33.0 的 `vllm bench serve` 为例，客户端 TTFT 是请求发出到收到首个流式输出；服务端 `server_queue_time` 只计调度等待，`server_ttft` 从调度到首 token 生成。文档给出的近似关系还包含前端和网络开销，且开启逐请求指标会增加服务端 CPU 成本，因此这类运行适合诊断，不宜直接当作无观测开销的压测结果。[vLLM v0.33.0 指标定义](https://docs.vllm.ai/en/v0.33.0/benchmarking/cli/)；[vLLM v0.33.0 生产指标](https://docs.vllm.ai/en/v0.33.0/usage/metrics/)

TTFT 高的原因可能在排队、tokenizer、RAG 前置链路、prefill、路由、prefix cache 失效、网关发送或客户端首字节，而不只是模型算力。

### 8.3.2 TPOT 对单 token 输出没有定义

如果请求输出 `O_i` 个 token，并且第一个 token 已计入 TTFT，且可以观测到逐 token 时间戳，后续 token 之间的间隔为 `d_{i,j}`，则当 `O_i>1` 时：

```math
\mathrm{TPOT}_i=\frac{\sum_{j=2}^{O_i}d_{i,j}}{O_i-1}
```

本章按相邻输出 token 的实际间隔先计算每条请求的 TPOT，再对请求级结果报告分布或汇总值。流式块间延迟（inter-token latency，ITL）通常按相邻输出块之间的间隔统计；标准逐 token 输出时它和 TPOT 接近，但投机解码（speculative decoding）或一次发送多个 token 时二者的样本单位不同。指标端点也会改变结果：本章把输出间隔与最后 token 后的完成收尾时间分开；vLLM v0.33.0 的 benchmark 将逐请求 TPOT 按 `(E2E-TTFT)/(output_tokens-1)` 计算。因此，只有当两边 E2E 截止事件和 token/chunk 对应关系一致时，结果才可直接比较；否则要回到输出事件时间戳核对，不能只看字段名。[vLLM v0.33.0 延迟指标说明](https://docs.vllm.ai/en/v0.33.0/benchmarking/cli/)

当 `O_i=1` 时没有后续 token 间隔，按本章口径 TPOT 是 `not_applicable`；当 `O_i=0` 时没有首 token，TPOT 也是 `not_applicable`，而 TTFT 记 `not_observed`。若日志缺失导致无法判断实际输出数或首块时间，则应记 `unknown`。不能用人为的非零分母把这些不同状态改成一个数字。

### 8.3.3 端到端延迟包含结束路径

当首 token、后续输出间隔和完成事件都在同一客户端边界被观察到时：

```math
T_i^{e2e}=\mathrm{TTFT}^{client}_i+\sum_{j=2}^{O_i}d_{i,j}+c_i
```

其中 `c_i` 包括最后一个输出块后的收尾、客户端完成事件和该业务定义内的必要后处理。若任务还要等工具或重试，任务级端到端时间要继续覆盖这些依赖；请求级模型延迟不能冒充完整 Agent 任务延迟。若请求在完成前取消，保留“从发送到取消”的生命周期时间，但不能把它伪装成成功完成请求的端到端延迟。

### 8.3.4 分位数要求非空样本

对非空延迟集合 `X=(x_1,...,x_n)`，P50 是中位数，P95/P99 分别是 95/99 百分位；分位数实现还必须明确排序和插值规则。例如采用线性插值时，令比例 `p` 取 0 到 1 之间的值，先算 `h=(n-1)p`，再在相邻顺序统计量之间插值。`n=0` 时这些分位数都是 `not_applicable`；不同实现对小样本 P99 的结果可能不同，报告应保存实现版本、样本量和请求筛选口径。

尾延迟不能用平均值替代。平均值可能被大量短请求拉低，而少量长请求正是用户投诉、超时和资源耗尽的来源。

## 8.4 prefill 和 decode 是两种不同的瓶颈

### 8.4.1 Prefill 决定新请求何时开始说话

prefill 一次处理整个输入上下文，通常更偏计算密集。输入 token 越多，需要建立的注意力状态越多；RAG chunk、工具 schema（参数字段、类型和约束的结构说明）、多轮历史和长文档都会影响它。

prefill 变慢的证据可能包括：

```text
input token P95 上升
tokenizer 或 prompt assembly CPU 占用上升
queue 正常但 TTFT 和 prefill time 同时上升
prefix cache 命中下降
长 prompt 在 GPU 上占用一个调度轮次过久
RAG/rerank/tool 前置 span 先于模型出现长尾
```

如果 GPU 利用率不高但 TTFT 变高，优先检查排队、CPU、路由和上游链路；如果 prefill tokens/s 下降且输入长度稳定，再看 kernel、精度、显存带宽和设备状态。

### 8.4.2 Decode 决定持续输出速度

decode 每轮通常只为每个活跃序列生成一个或少量 token，受到权重读取、KV Cache 读取、batch 形状和调度开销影响。decode 变慢时，首 token 可能正常，但后续 token 间隔变大或抖动。

应该同时记录：

```text
GPU decode step time、每轮活跃序列数、每轮生成 token 数
KV block 读取/抢占、显存带宽、量化 kernel、speculative 接受率
服务端生成时间、网关发送时间、客户端接收时间
```

如果 worker 的 decode step 很快而客户端间隔很长，问题在 streaming、网络或渲染；如果两者都慢，才进入模型和调度层。

### 8.4.3 混合调度的核心是资源时间分配

过度优先 prefill，新请求 TTFT 可能降低，但已有流式请求会出现 token 间隔尖峰；过度优先 decode，已有请求顺畅，但新请求可能长时间排队。分块预填充（chunked prefill）、每轮 token 预算、长短请求分队列和优先级都在解决这个时间分配问题。

具体策略会随引擎和版本而变。以 vLLM v0.33.0 的 V1 文档为例，支持时默认启用 chunked prefill，并先调度待解码请求，再用剩余 `max_num_batched_tokens` 预算处理 prefill；文档称较小预算通常改善 ITL，较大预算可改善 TTFT，在特定小模型/大 GPU 配置下也可能提升吞吐。这说明预算是在不同请求之间分配设备时间的旋钮，不是可跨模型照抄的默认值。[vLLM v0.33.0 chunked prefill 调优说明](https://docs.vllm.ai/en/v0.33.0/configuration/optimization/)

调度器不应只看请求数量。一个 8,000 token 的长请求和八个 100 token 的短请求都是“一个请求”，但它们对 prefill、KV 和队列的影响完全不同。按 token 和预计生命周期管理资源，通常比按 request count 更接近真实容量。

如果 trace 显示 prefill 和 decode 长期争用同一批设备，还可以评估把两阶段放进独立资源池（Prefill/Decode disaggregation）。这样能分别配置两类容量，但必须把 prefill 生成的 KV 状态传输、跨池网络与协调开销、两侧负载比例和故障路径一起算进端到端时间；流量比例变化时，一侧排队而另一侧闲置也会抵消收益。DistServe 论文展示了这种设计在其工作负载和 SLO 下的收益，不是所有服务都能获得同样结果。本章只把它作为定位到阶段争用后的进阶候选；机制与实施取舍见[第六册第五章《推理引擎》](../../book-06-llm-deployment/chapters/05-推理引擎.md)、[第六册第十二章《成本优化》](../../book-06-llm-deployment/chapters/12-成本优化.md)和[第二十四册第四十二章《P/D 分离的优缺点、适用场景和反模式》](../../book-24-llm-inference-engine/chapters/42-pd分离的优缺点适用场景和反模式.md)。

## 8.5 KV Cache：容量、碎片和共享要一起看

模型权重通常在启动时固定占用显存，KV Cache 则随着活跃请求的上下文和输出增长。高并发服务中，KV Cache 常常比权重更早达到容量上限。

### 8.5.1 基本显存估算

对 `L` 层、每层 `H_kv` 个 K/V 头、每头维度 `D_h`、每个元素占 `b` 字节的模型，第 `i` 个活跃请求当前保留 `A_i` 个 token 的注意力状态时，未计入实现额外开销的 KV 字节数近似为：

```math
M_{KV}=2L H_{kv}D_h b\sum_i A_i
```

前面的 `2` 对应 Key 和 Value。分组查询注意力（grouped-query attention，GQA）和多查询注意力（multi-query attention，MQA）通过减少 KV 头数 `H_kv` 降低每 token 的 KV 状态，但不会消除层数、头维度 `D_h`、上下文长度和活跃并发的影响。

这个公式是容量估算，不是实际显存读数。实际系统还需要考虑 block 元数据、对齐、临时 workspace、prefix 共享、碎片、抢占、量化格式和框架保留空间。

### 8.5.2 block 分配会引入内部碎片

如果系统按 `B` token 一个 block（块）分配，第 `i` 个请求的已分配 token 数可能是：

```math
\tilde A_i=B\left\lceil\frac{A_i}{B}\right\rceil
```

当请求集合非空且总分配 token 数大于零时，内部碎片比例可以写成：

```math
R_{frag}=1-\frac{\sum_i A_i}{\sum_i\tilde A_i}
```

block 太大，短请求浪费更多；block 太小，管理元数据和调度开销可能增加。分页管理的价值在于让 KV Cache 能按块增长、回收和共享，而不是保证任何负载下都不会显存不足（out of memory，OOM）。PagedAttention 论文把动态 KV 分配映射到类似分页的块管理，并在其论文模型、硬件、请求分布和基线下报告吞吐提升；论文机制解释内存管理为何能影响 batch 容量，不能直接推出今天某个引擎的加速倍数。[PagedAttention 原论文](https://arxiv.org/html/2309.06180v1)

### 8.5.3 共享 prefix 既节省显存，也增加正确性约束

多个请求拥有相同的 system prompt 或工具说明时，前缀缓存（prefix cache）可以复用已计算的 KV 块，跳过共享前缀的重复 prefill。共享的前提是 token 序列、模型版本、精度、位置语义、权限上下文和失效策略都一致；它只减少可复用部分的输入计算，不会缩短生成新 token 的 decode 时间。[vLLM v0.33.0 prefix caching 说明](https://docs.vllm.ai/en/v0.33.0/features/automatic_prefix_caching/)

以下内容不能随意放进可共享前缀：

```text
用户身份、租户权限和敏感文档
随时间变化的政策、价格和库存
请求级随机数、工具状态和外部 observation
包含用户输入的可变历史
```

缓存命中率高但答案错用了其他用户权限，是比缓存不生效更严重的事故。KV 节省必须和权限、版本、失效和错误复用率一起审计。

在共享进程的多租户服务里，还要考虑前缀缓存造成的时序侧信道：调用者可能从 TTFT 差异推测某个前缀是否已缓存。vLLM v0.33.0 提供可选 `cache_salt`，把盐值混入首块哈希，让只有带相同盐值的请求共享前缀块；它缓解的是这类缓存复用风险，不构成租户隔离。安全分组越细，跨组可复用的缓存越少。认证和租户边界仍应由可信网关或独立部署控制，盐值也应由服务端按信任组生成，不能直接信任调用者任意传入的值。[vLLM v0.33.0 prefix cache 设计](https://docs.vllm.ai/en/v0.33.0/design/prefix_caching/)；[vLLM v0.33.0 多租户安全说明](https://docs.vllm.ai/en/v0.33.0/usage/security/)

## 8.6 batching 和调度：吞吐不是免费的

连续批处理（continuous batching，也叫 in-flight batching）可以让新请求在已有请求生成期间加入运行批次，减少设备空闲。但它也会让不同长度、不同优先级和不同阶段的请求共享资源。

### 8.6.1 变大 batch 的三个副作用

第一，短请求可能被长请求占住 KV block 和调度轮次；第二，prefill 大块工作可能阻塞 decode；第三，设备吞吐增加的同时，排队和尾延迟可能上升。

一个常见的错误实验是固定 prompt、固定输出、固定并发做 benchmark，然后把结果推广到真实流量。真实流量至少有长短混合、取消、重试、不同业务优先级和外部依赖波动。压测必须保留这些结构。

### 8.6.2 token budget 比 request count 更有解释力

调度器可以在每轮限制 prefill token budget 和 decode token budget，让长请求不能无限占用设备。预算过小会增加调度开销，预算过大则会造成其他请求等待。需要通过不同长度分桶观察 TTFT、TPOT 和 P99，而不是只看一条总吞吐曲线。

### 8.6.3 公平性和优先级必须可观测

核心业务可能需要更低的 TTFT，批处理任务可以延后；但优先级不能变成不可解释的饥饿。记录每个请求的优先级、排队时长、被跳过次数和实际服务时间，才能发现低优先级请求是否长期没有机会。

长短请求隔离通常增加一些资源碎片，却能保护短请求的尾延迟。是否值得隔离，应由任务价值、SLO 和容量成本决定，而不是由 GPU 利用率单独决定。

## 8.7 量化优化的是资源，不自动优化体验

量化减少权重或激活的存储占用，可能降低显存和带宽压力；实际速度是否提升取决于 GPU kernel（设备上执行的计算程序）、硬件、反量化开销、batch 形状和内存访问。INT4（4 位整数表示）能加载并不等于它在业务上更好。

### 8.7.1 量化质量要按行为切片

至少要比较：

```text
通用问答、数学、代码和长上下文
JSON/schema、函数调用和工具参数
中文/多语言、RAG 引用和拒答边界
输出长度、重试率、解析失败和人工接管
```

校准数据覆盖不到真实业务时，平均 benchmark（基准测试）可能没有明显退化，但关键格式或长上下文已经变差。量化后的质量回归要与 FP16（16 位浮点）/BF16（brain floating-point 16）对照基线（baseline）使用相同 prompt、解码和硬件条件。

### 8.7.2 量化的真实收益要按有效任务计算

如果量化把单请求成本降低 30%，却让 JSON 解析失败、重试和人工审核增加，那么单位成功任务成本可能上升。性能报告应同时给出：

```text
每请求成本、每成功任务成本、每秒有效任务数
TTFT/TPOT/P95/P99、显存和 OOM
质量回归、解析失败、重试、取消和人工接管
```

只有在这些指标的组合下，才能判断量化是否值得保留。

## 8.8 Prompt、RAG 和工具说明会改变推理成本

长 prompt 不只增加输入 token 价格，还会增加 prefill 时间、KV Cache 需求和上下文干扰。系统 prompt、RAG chunk、工具 schema、多轮历史和用户文件常常在产品迭代中悄悄增长。

### 8.8.1 输入 token 的增长需要基线

设新版本和基线版本的输入 token 总数分别为 `I_new` 与 `I_base`，且 `I_base>0`，prompt 漂移比为：

```math
\gamma_{prompt}=\frac{I_{new}}{I_{base}}
```

如果基线样本没有输入 token 记录，漂移是 `unknown`；不能用零或任意常数修补。报告还应按 system、history、retrieved、tool schema 和 user content 拆分增长来源。

### 8.8.2 RAG 的上下文预算要看有效信息

把更多 chunk 放进上下文，可能提高证据召回，却同时增加 prefill 和噪声。应记录每个请求的候选文档数、最终注入 token、有效证据 token、重复 token 和引用支持结果。只看上下文长度不能说明检索质量，只看检索命中也不能说明回答会利用证据。

### 8.8.3 工具 schema 不是免费的静态文本

把几十个工具的完整 schema 每轮注入，会让输入变长、prefill 变慢，也会增加模型选择错误。按任务路由工具、压缩描述、稳定共享前缀，并在 schema 版本变更时使缓存失效，通常比无限提高 `max_context` 更有效。

## 8.9 Streaming 的瓶颈可能在模型之外

流式生成的用户体验由至少三段时间组成：模型生成、服务端发送、客户端接收和渲染。任何一段缓冲都可能让用户看不到已经生成的 token。服务器推送事件（Server-Sent Events，SSE）和 WebSocket 是两类流式传输方式；代理缓冲、压缩和背压（backpressure，即下游暂时接收不了时向上游传递的流量约束）都可能改变块抵达客户端的时间。

### 8.9.1 三端打点才能定位

建议为同一个 chunk 记录：

```text
worker_generate_at
server_enqueue_at
gateway_write_at
client_receive_at
client_render_at
```

如果 `worker_generate_at` 很早，`client_receive_at` 很晚，检查网关、代理、SSE/WebSocket、压缩和 backpressure；如果收到很快但显示很晚，检查前端批量渲染和 markdown 解析；如果 worker 本身间隔很大，才回到 decode 和调度。

### 8.9.2 错误、取消和结束事件也属于协议

客户端断开后，服务端应尽快取消生成并释放 KV；超时和依赖失败需要明确结束原因；重试请求要有 request id 或幂等关联，避免一次用户动作产生多条计费和外部副作用。只实现“正常 token 流”而没有错误/取消事件，会让监控和资源回收都不可靠。

## 8.10 缓存的收益和正确性必须同时计算

推理系统可能使用前缀缓存（prefix cache）、prompt cache、response cache（回答缓存）、向量嵌入（embedding）缓存、检索 cache 和工具结果 cache。不同供应商对 prompt cache 的含义和计费口径可能不同；比较时要查具体接口定义。缓存命中不是收益的同义词。

当可被这类缓存策略复用的输入 token 数 `I>0` 时，可复用输入 token 命中率为：

```math
R_{hit}=\frac{H}{I}
```

其中 `H` 是这些可复用输入 token 中实际命中的 token 数。若没有符合缓存策略的输入，命中率为 `not_applicable`；若命中字段缺失，状态为 `unknown`。还要计算节省的 prefill 时间、占用的内存和错误复用率。

缓存 key 至少要考虑：

```text
模型/模板/精度版本
system prompt 和工具 schema 版本
租户、用户和权限上下文
文档版本、生效时间和地域
随机性、外部状态和失效时间
```

response cache 可能复用过期政策，RAG cache 可能跨权限泄露，tool result cache 可能复用已经变化的库存。缓存设计要有失效和审计，而不是只在仪表盘上展示 hit rate。

## 8.11 限流、取消和降级是容量系统的一部分

没有限流时，少量长请求、无限重试或上游故障就能占满队列和 KV Cache。限流不是简单拒绝请求，而是按资源和价值控制系统在峰值下的行为。

可以按以下维度限制：

```text
请求数、输入 token、预计输出 token、活跃序列数
KV Cache token/block、租户配额、业务优先级
单用户重试次数、长上下文比例和工具调用次数
```

取消处理同样重要。客户端已经离开页面时，继续生成会浪费显存和成本；但取消信号如果没有传到 worker，监控看到的“请求数下降”不代表资源已经释放。应记录取消传播时间和 KV 回收时间。

降级策略可以包括小模型、较短上下文、异步队列、只返回检索结果、关闭非核心工具或转人工。降级必须标记在结果中，并进入质量、成本和用户行为统计；不能把降级成功伪装成主模型成功。

## 8.12 容量规划要使用分布而不是平均值

容量规划至少需要输入：

```text
峰值和突发 QPS、输入/输出 token 分布、并发和取消分布
TTFT/TPOT/P95/P99 目标、模型精度和引擎版本
KV Cache 可用预算、长上下文比例、prefix 命中率
依赖服务耗时、限流/降级比例、故障切换和冗余容量
```

一个粗略流程是：先从真实流量得到输入、输出和并发分布；再对真实混合负载做压测；然后用 KV 和尾延迟反推每实例可承载的活跃 token；最后加入故障冗余和突发余量。

平均 QPS 只能给出产能大致方向，不能证明 P99 可控。长请求和短请求的混合比例、prefix cache 命中、取消和重试都会改变有效容量。

### 8.12.1 计算容量和显存容量要分开

某实例可能还有计算空闲，却因为 KV block 不足无法接受新请求；也可能显存足够，但 tokenizer、网络或 CPU 调度成为瓶颈。容量报告要分别给出：

```text
计算利用率、prefill/decode 产能
KV token/block 容量和分配失败
队列长度、排队时间和尾延迟
CPU tokenizer、网关、网络和外部依赖
```

“再加一张 GPU”只对真正的设备瓶颈有效。若路由不均、队列锁、缓存失效或上游 RAG 才是根因，扩容不会消除问题。

## 8.13 监控看板要能回答“用户为什么等”

建议把看板分为四层。

请求体验层：TTFT、TPOT、端到端延迟、P50/P95/P99、首 token 前取消率、流式间隔。

调度和资源层：QPS、活跃序列、队列时间、batch size、prefill/decode token budget、GPU/CPU 利用率、显存、KV block、OOM 和抢占。

若采用 prefill/decode 分池，还要分别记录两侧队列和利用率、KV 状态传输的字节数/耗时/失败，以及跨池请求的端到端延迟；单看任一池的 tokens/s 无法说明整条服务路径是否改善。

链路层：tokenizer、RAG、rerank、工具、网关写入、客户端接收、错误和依赖超时。

价值和质量层：成功任务成本、重试、解析失败、代码测试、引用支持、安全、人工接管和用户采纳。

每一个指标都要能按模型版本、引擎、精度、业务线、输入长度、输出长度、租户和时间窗口切分。总平均掩盖问题时，切片才是定位入口。

## 8.14 性能压测要像真实流量，而不是算子展示

压测前先固定版本和环境：模型权重、tokenizer、chat template、引擎、精度、硬件、驱动、batch 参数、cache 状态和网络路径。然后构造接近生产的请求分布。

压测至少覆盖：

```text
短/中/长输入和短/中/长输出
冷 cache、热 cache、部分命中和失效
低/中/峰值并发、突发流量和长短混合
若采用 prefill/decode 分池，覆盖两阶段负载比例变化及 KV 传输拥塞/失败
正常完成、客户端取消、超时、重试和依赖故障
不同优先级、限流、降级和实例故障切换
量化版本与 baseline 的质量和协议回归
```

每组压测都记录稳定时间、预热方式、样本量、分位数算法、异常请求处理和结果版本。单次短时间 benchmark 可能只测到热 cache 和稳定 GPU，不代表长时间运行的碎片、泄漏、排队和漂移。

## 8.15 典型修复顺序：先保护用户，再追求极限吞吐

推理性能事故修复可以按因果顺序推进。

第一步，保留现场并降低影响：限制超长请求、暂停扩大流量、保护核心业务、设置清晰超时和降级。

第二步，按请求 trace 拆分 queue、tokenizer、prefill、decode、streaming 和外部依赖，确认第一处异常，而不是只看最后的总延迟。

第三步，检查输入和输出分布是否漂移，尤其是 RAG chunk、工具 schema、多轮历史和 max output 是否变长。

第四步，核对 KV Cache：活跃 token、block 分配、碎片、prefix 共享、取消回收和实例路由。

第五步，针对调度做小范围对照：batch、token budget、chunked prefill、长短队列和优先级，每次只改变主要因素。

第六步，重新跑质量回归，确认量化、截断、缓存和降级没有损伤格式、代码、引用、安全和工具协议。

第七步，在真实混合流量上灰度，比较用户级 TTFT/P99、任务完成、成本和取消，而不只看 GPU 利用率。

## 8.16 关键公式与边界语义

### 8.16.1 输出吞吐

若测量窗口长度 `T_wall>0`，且窗口内实际发出 `O_total` 个输出 token（包括后来未通过质量校验的输出），则：

```math
S_{out}=\frac{O_{total}}{T_{wall}}
```

`O_total` 是该窗口实际发出的输出 token 数，`S_out` 的单位是 token/s。没有有效时间窗口时吞吐为 `not_applicable`；token 计数缺失时为 `unknown`。`S_out` 只代表产能，不代表任务成功或用户体验。

### 8.16.2 KV 压力

若当前估计的 KV 占用为 `M_KV`，可用于 KV 的显存预算 `B_KV>0`，则：

```math
\rho_{KV}=\frac{M_{KV}}{B_{KV}}
```

当预算缺失或为零时，压力没有定义；当实际分配还要加上碎片和临时空间时，公式值只能作为下界。真正的分配失败、抢占和 OOM 事件应单独计数。

### 8.16.3 任务完成成本

设第 `i` 个尝试任务的总成本为 `c_i`，成功交付的任务索引集合为 `S`。请求成本可以按请求平均，但生产更关心单位成功任务成本：

```math
C_{success}=\frac{\sum_i c_i}{\lvert S\rvert},\qquad \lvert S\rvert>0
```

没有成功任务时，单位成功成本没有定义，不能为了让图表有数值而写成零。成本还应包括重试、工具、RAG、人工审核和失败补偿。

### 8.16.4 性能和质量的联合判断

可以把一次发布判断写成多个独立条件的记录：

```text
ttft_status、tpot_status、tail_latency_status
kv_status、cache_status、prompt_cost_status
quality_status、safety_status、rollback_status
```

这些状态的来源不同，不能随意相乘成一个“综合通过率”。如果某项没有样本或没有测量，应标记 `not_applicable` 或 `unknown`，而不是用零分假装完成了测试。

## 8.17 用一份手算账本解释吞吐与等待的分歧

下面所有请求、时间、成本点和质量结果都是构造的教学输入，不代表生产测量。候选发布同时扩大了 batch 调度参数并更新了系统 prompt；五条请求代表相同的用户任务，但输入 token 长度发生变化，所以这不是能单独证明调度参数因果作用的受控实验。客户端到服务入口的入站时间在本例中设为 0；首块路径 `f` 从 prefill 产出首 token 所需 logits 计到客户端收到首块，包含 token 选择、首块发送和传输；所有时间单位都是毫秒。

### 8.17.1 先沿五条请求走完时间线

对每条请求，依次记录排队 `q`、输入准备 `z`、prefill `p`、首块路径 `f`。这些阶段各做什么已经在 8.2 说明；这里逐项相加，是为了看出候选配置把时间花在哪一步。

| 请求 | q | z | p | f | O（输出 token） | 首块后的间隔 `d` | 收尾 c | TTFT | 完整请求端到端 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: | ---: | ---: |
| FAQ | 80 | 20 | 50 | 50 | 3 | 90, 110 | 50 | 200 | 450 |
| 短咨询 | 170 | 20 | 100 | 60 | 4 | 120, 130, 150 | 50 | 350 | 800 |
| 摘要 | 350 | 30 | 180 | 40 | 3 | 200, 220 | 60 | 600 | 1,080 |
| 代码 JSON | 500 | 50 | 350 | 150 | 5 | 180, 190, 200, 210 | 70 | 1,050 | 1,900 |
| 长上下文 RAG | 500 | 50 | 800 | 150 | 5 | 200, 210, 220, 230 | 130 | 1,500 | 2,490 |

先看 FAQ。请求先排队 80 ms，再用 20 ms 准备输入、50 ms 做 prefill，最后经过 50 ms 才让首块抵达客户端，所以 `TTFT=80+20+50+50=200 ms`。模型一共输出 3 个 token，首 token 已包含在 TTFT 中；后面两个 token 间隔是 90 ms 和 110 ms，因此 `TPOT=(90+110)/(3-1)=100 ms/token`。最后再加 50 ms 收尾，完整请求时间是 `200+90+110+50=450 ms`。

短咨询的首 token 时间是 `170+20+100+60=350 ms`；3 个后续间隔共 `400 ms`，除以 3 个间隔得到 `133.3 ms/token`；加上 50 ms 收尾，端到端时间为 `350+400+50=800 ms`。摘要请求同理：`TTFT=350+30+180+40=600 ms`，`TPOT=(200+220)/2=210 ms/token`，端到端时间为 `600+420+60=1,080 ms`。

代码 JSON 请求的排队、输入准备、prefill 和首块路径合计 `500+50+350+150=1,050 ms`；4 个后续间隔合计 780 ms，所以 `TPOT=780/4=195 ms/token`，完整请求为 `1,050+780+70=1,900 ms`。这条输出未通过 JSON 结构解析。它仍然产生了 token，所以会增加输出吞吐；但它没有交付一个有效任务结果。

长上下文 RAG 请求的 `TTFT=500+50+800+150=1,500 ms`。4 个后续间隔合计 860 ms，故 `TPOT=860/4=215 ms/token`；再加 130 ms 收尾，端到端为 `1,500+860+130=2,490 ms`。表中队列和 prefill 都很长，它们是下一步应沿 trace 核对的两个阶段；单凭这张表还不能断言哪项调度参数造成了变化。

### 8.17.2 对齐 baseline，再算 P95

下表是同五类用户请求在 baseline 配置下的请求级结果；比较时假设输出 token 数和完成条件相同。百分位只对五条已收到首块并完成的请求计算；另外发生的首 token 前取消不混进这个样本，需另行报告。

| 请求 | baseline TTFT | 候选 TTFT | baseline TPOT | 候选 TPOT | baseline 端到端 | 候选端到端 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| FAQ | 180 | 200 | 90 | 100 | 380 | 450 |
| 短咨询 | 240 | 350 | 100 | 133.3 | 580 | 800 |
| 摘要 | 400 | 600 | 140 | 210 | 730 | 1,080 |
| 代码 JSON | 700 | 1,050 | 150 | 195 | 1,400 | 1,900 |
| 长上下文 RAG | 900 | 1,500 | 180 | 215 | 1,740 | 2,490 |

本例采用 8.3.4 的线性插值规则。五个数从小到大排列后，`P95` 的位置为 `h=(5-1)×0.95=3.8`，也就是第 4 个数到第 5 个数之间走 0.8 的距离。baseline 的 TTFT 顺序值是 `180, 240, 400, 700, 900`，因此 `P95=700+0.8×(900-700)=860 ms`；候选值是 `200, 350, 600, 1,050, 1,500`，所以 `P95=1,050+0.8×(1,500-1,050)=1,410 ms`。

按同一方法，baseline/候选 TPOT P95 分别是 `150+0.8×(180-150)=174 ms/token` 和 `210+0.8×(215-210)=214 ms/token`。端到端 P95 分别是 `1,400+0.8×(1,740-1,400)=1,672 ms` 和 `1,900+0.8×(2,490-1,900)=2,372 ms`。这五条构造样本显示三项尾部延迟都变长；样本太小，只用于演示复算，不能估计生产总体的 P95。

另一个独立的 10 秒测量窗口里，baseline 实际输出 240 token，候选配置输出 320 token：

```math
S_{base}=\frac{240\ \mathrm{token}}{10\ \mathrm{s}}=24\ \mathrm{token/s},\qquad
S_{candidate}=\frac{320\ \mathrm{token}}{10\ \mathrm{s}}=32\ \mathrm{token/s}
```

输出吞吐提升 `(32-24)/24=33.3%`。这个分子数的是窗口内实际发出的 token，包括上面未通过 JSON 解析的那条响应；P95 的分母却是完成的五条请求。两个指标回答不同问题，因此吞吐上升可以和用户等待变长同时发生。

### 8.17.3 回到账本检查 prompt、缓存和 KV

五条请求的输入 token 数在 baseline 下分别是 `620, 390, 760, 1,250, 3,200`，合计 `6,220`；候选配置下分别是 `600, 420, 900, 1,800, 5,600`，合计 `9,320`。假设本小例里这些输入都属于可缓存候选，则 prompt 漂移比为 `9,320/6,220≈1.498`，即输入总量约为 baseline 的 1.50 倍。记录中只有 FAQ 命中 500 个前缀 token，所以缓存命中比例是 `500/9,320≈5.4%`。输入变长本身就是延迟对照中的混杂因素；要单独估计调度参数的影响，还需对同一 prompt、同一输出条件分别重放两个调度配置。缓存比例说明本样本里可复用量有限，并不说明所有服务都应达到某个固定比例。

再单独构造一个 KV 容量快照：五条活跃序列当前分别占用 `603, 424, 903, 1,805, 5,605` 个 token，合计 `9,340`。假设模型有 32 层、每层 8 个 KV 头、头维度 128、每个 Key/Value 元素占 2 字节，且暂不考虑共享前缀、元数据和临时工作区。先算每个 token 的 KV 字节数：

```math
2\times32\times8\times128\times2=131,072\ \mathrm{bytes}=128\ \mathrm{KiB/token}
```

于是未计额外开销的 KV 估算为 `9,340×128=1,195,520 KiB=1,167.5 MiB≈1.140 GiB`。若每个 block 容纳 128 个 token，五条序列分别向上取整为 `640, 512, 1,024, 1,920, 5,632` 个已分配 token，合计 `9,728`；内部空位是 `9,728-9,340=388` 个 token，碎片比例为 `388/9,728≈4.0%`。按同一假设，块分配后的容量约为 `9,728×128 KiB=1.1875 GiB`。这只是简化账本；真实 KV 预算还要按模型结构、并发时刻、共享块、量化和框架开销复核。

任务成本也要把失败算进去。假设 baseline 五个任务总共消耗 10 个构造成本点，五个都成功，则单位成功任务成本 `10/5=2` 点；候选任务总成本 15 点，其中代码 JSON 失败，只有 4 个任务成功，所以 `15/4=3.75` 点。失败请求已经消耗的推理和重试资源留在分子，不能因为没成功就从成本账本里消失。这里的“成本点”只是示例单位，不是货币报价。

### 8.17.4 单独保留取消和质量状态

另有一条请求在首个输出块前取消：它的生命周期记录为“发送后 1,300 ms 收到取消”，但 TTFT 是 `not_observed`，完整请求端到端延迟不适用。若只统计成功完成的请求，必须把首 token 前取消数和取消耗时一起列出，避免 P95 悄悄变成“留下来的请求”的分位数。候选样本的五条完整请求中有一条 JSON 解析失败；`1/5` 是这份合成样本的观察比例，不能据此推断线上失败率。

这份账本不提供通用发布门槛，也不自动输出“通过/拒绝”。实际团队应在压测前按任务价值确定 TTFT、TPOT、完整任务时间、质量和成本目标，再对齐模型、精度、流量、缓存和测量端点。当前示例给出的排查顺序是：先复核长请求排队和 prefill，再查 prompt 增长和前缀复用，随后确认格式失败是否来自模板、模型或精度变化；扩大流量之前，还要用足够样本和同条件质量回归复核。每一步都要留下支持或推翻假设的 trace，不能把候选解释写成根因。

## 8.18 资料来源与证据边界

### 8.18.1 论文和算法资料

- [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/html/2309.06180v1) 解释动态 KV Cache 的碎片、重复分配和分页管理，并在论文实验条件下报告 vLLM 相对当时基线的吞吐改进。论文结果不能直接推出当前硬件、模型和业务流量的加速比例。
- [JITServe, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/zhang-wei) 区分流式逐 token 延迟、完整响应 deadline 和多调用复合任务的服务目标，并将 service goodput 用作系统目标。论文数字绑定作者评测的模型、GPU、工作负载和基线。
- [DistServe v3](https://arxiv.org/abs/2401.09670v3) 研究将 prefill 与 decode 放到不同资源池、分别配置两阶段资源并传递生成状态的 serving 设计。其 goodput/SLO 结果只适用于论文列出的模型、请求分布、硬件和比较基线；本章只借它说明分池是有额外传输与容量匹配成本的架构候选。
- continuous batching、chunked prefill、speculative decoding 和量化 kernel 的效果依赖请求分布、硬件、实现和质量目标。论文或仓库中的 benchmark 是实验结果，不是生产 SLO。

### 8.18.2 官方文档

- OpenAI 的 [Latency Optimization](https://platform.openai.com/docs/guides/latency-optimization) 和 [Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching) 适合了解请求延迟拆分、输入输出 token、缓存组织和 API 观测字段。供应商接口和计费规则会随版本变化，不能把文档中的示例数字当作本地服务容量。
- Hugging Face [Text Generation Inference Streaming](https://huggingface.co/docs/text-generation-inference/en/conceptual/streaming) 说明 streaming 接口层的行为。它不能证明网关、代理、网络和客户端已经实现端到端低延迟。
- NVIDIA [TensorRT-LLM 文档](https://nvidia.github.io/TensorRT-LLM/) 可作为特定硬件和引擎的配置、benchmark 与调度参考。其结果必须绑定 GPU、CUDA、驱动、引擎版本和输入分布。
- 本章涉及 vLLM 指标、batch 调度、前缀缓存和多租户缓存风险时固定参考 [vLLM v0.33.0 benchmark 指标](https://docs.vllm.ai/en/v0.33.0/benchmarking/cli/)、[生产监控指标](https://docs.vllm.ai/en/v0.33.0/usage/metrics/)、[chunked prefill 调优](https://docs.vllm.ai/en/v0.33.0/configuration/optimization/)、[prefix caching](https://docs.vllm.ai/en/v0.33.0/design/prefix_caching/) 和[安全说明](https://docs.vllm.ai/en/v0.33.0/usage/security/)。这些页面描述该 release 的公开行为，不保证其他版本或其他引擎相同。

官方资料适合确认 API、实现和配置，不替代目标集群的压测、故障演练和质量回归。

### 8.18.3 本章示例的状态

8.0 和 8.17 的时间、吞吐、KV、缓存、成本与质量数字都是构造的教学输入，用来演示请求级归因和公式代入；本章没有提供真实硬件 benchmark 或本地运行结果。真实结论需要保存压测脚本、硬件和软件版本、输入输出分布、cache 状态、并发模型、异常请求处理、质量结果和原始 trace。

当宣传材料只给出“吞吐提升多少”，而没有延迟分位数、请求长度、并发、模型精度和基线时，最多只能把它当成待验证线索，不能直接写进容量规划或产品承诺。

## 8.19 事故复盘应回答的六个问题

一次推理性能事故复盘不应只写“GPU 不够”。至少要回答：

1. 用户在什么时间、什么业务、什么请求长度下开始变慢？
2. 第一处异常出现在队列、tokenizer、prefill、decode、网络还是外部依赖？
3. 输入、输出、batch、KV、cache 或路由的哪个分布发生了变化？
4. 性能变化是否伴随格式、代码、引用、安全或工具质量回归？
5. 为什么现有监控、容量余量、取消回收和降级没有提前保护用户？
6. 修复后用什么混合流量、版本对照和质量样本证明问题真正消失？

如果回答不了这些问题，扩容或换引擎只能暂时降低症状，不能说明根因。

## 8.20 本章小结

推理部署优化的目标不是让某个吞吐数字最大，而是在真实请求分布下同时保护首 token、持续流式、尾延迟、显存、成本、稳定性和质量。

TTFT 要拆出排队、tokenizer、prefill 和发送路径；TPOT 只对存在后续 token 的请求定义；端到端延迟要包含结束路径；P95/P99 要保留非空样本和实现细节。prefill 和 decode 的资源特征不同，batch 越大不一定越好；KV Cache 要同时看容量、block 碎片、共享、取消回收和分配失败；分页管理能改善内存利用，但不会消除所有容量问题。

量化、prompt 压缩、缓存、限流和降级都必须与格式、代码、RAG、工具、安全和任务成功一起评估。流式输出要在 worker、网关和客户端三端打点；容量规划要使用输入输出分布和混合流量；压测要包含取消、重试、长短请求、cache 冷热、依赖故障和故障切换。

下一章进入 RAG 落地。推理服务解决的是“系统能否稳定地把模型运行起来”，RAG 还要继续回答“送进模型的证据是否正确、及时、可追溯并且符合权限”。
