# 第八章：推理部署性能坑：平均吞吐变高，用户却更卡

推理部署是大模型从实验室进入生产环境后的第二次考试。离线评估只能说明模型在给定输入上回答得怎样，不能说明服务是否能在高并发、长上下文、网络抖动、客户端取消和依赖变慢时稳定工作。

推理性能也不是一个数字。用户先等待首个 token，再等待后续 token 持续流出；系统同时要管理队列、prefill、decode、KV Cache、网关、网络、缓存和外部工具。平均 tokens/s 变高，可能只是系统把更多请求塞进了 batch；如果短请求因此排在长请求后面，用户反而会觉得系统变慢。

本章从一次“吞吐提升但投诉增加”的事故开始，逐层解释 TTFT、TPOT、端到端延迟、尾延迟、prefill/decode、KV Cache、分页管理、batch 调度、量化、prompt 成本、流式传输、缓存、限流、容量规划和质量回归。正文把每个指标放回请求生命周期中解释，并明确空请求、单 token 输出、取消请求、零分母和未知状态的语义。

## 8.0 先看一场吞吐上升的事故

某团队把推理服务的调度参数改大，GPU 利用率从 45% 上升到 75%，集群平均输出吞吐从每秒 24 token 上升到每秒 32 token。监控首页显示绿色，发布负责人认为优化成功。

几个小时后，客服收到“输入后很久没有反应”和“回答一顿一顿”的投诉。进一步拆分请求发现：短问题的首 token 等待时间明显增加，长上下文请求占满了 KV Cache，P99 端到端延迟超过用户可接受范围；缓存命中率几乎没有改善，prompt 比旧版本膨胀，代码 JSON 质量也发生回归。

这场事故不是 GPU 变慢，而是系统优化了一个脱离用户体验的指标。批处理把更多 token 放进了设备，却改变了队列顺序和资源竞争；吞吐数字变好，服务目标却变差。

对初学者来说，可以把一次推理请求想成餐厅订单：先排队，再准备食材，再开始出第一道菜，之后每道菜逐步上桌。第一道菜多久上桌对应 TTFT，后续上菜间隔对应 TPOT，整桌完成对应端到端延迟。对专家来说，这是一条包含调度、计算、显存、网络和外部依赖的关键路径；任何一段的尾部放大，都可能通过队列传导到所有请求。

本章反复使用的事故链是：

```text
请求到达 -> 网关/鉴权 -> tokenizer 与 prompt 组装 -> 排队
        -> prefill -> 首个 token -> decode 循环 -> 流式发送
        -> 客户端接收/渲染 -> 完成、取消、计费和质量记录
```

如果只在 GPU 进程里记录一个“平均生成速度”，就无法判断用户到底卡在了哪一段。

## 8.1 性能目标先写成用户和系统的共同约束

在调 batch、换量化或更换推理引擎之前，先写清楚服务要保护的对象。聊天问答、代码补全、批量摘要和 Agent 工具调用的性能目标不同。

聊天问答通常更在意 TTFT 和流式间隔；代码补全可能更在意短请求的 P95；批量摘要可以接受更高 TTFT，但希望单位成本和总吞吐稳定；Agent 任务还要把工具调用、重试和外部依赖算进完整任务延迟。

一个可执行的性能合同至少包含：

```text
请求单位：单轮请求、完整会话，还是一次完整任务
输入分布：input token 的 P50、P95、最大值和长上下文占比
输出分布：实际生成 token、取消、截断和空输出比例
用户目标：TTFT、TPOT、端到端延迟和可接受尾部
系统目标：吞吐、GPU/CPU 利用、KV Cache、错误率和单位成本
质量目标：格式、代码、引用、安全和工具协议不能退化到什么程度
降级策略：超长输入、依赖故障、队列拥塞和容量不足时如何处理
```

没有输入输出分布的“单卡 QPS”很容易误导。相同 QPS 下，输入从 500 token 变成 5,000 token，prefill、KV Cache 和成本都可能发生数量级变化；相同输入下，输出从 80 token 变成 800 token，decode 时间和活跃状态也会改变。

### 8.1.1 三种吞吐不要混在一起

至少要区分三种产能：

1. **prefill 吞吐**：单位时间处理的输入 token，影响新请求的首 token；
2. **decode 吞吐**：单位时间生成的输出 token，影响持续流式速度；
3. **任务吞吐**：单位时间完成的有效任务，必须扣除失败、取消、重试和人工接管。

GPU 报告的 token 数可能是算子处理量，网关报告的 token 数可能是已经发送的 token，产品报告的任务数则可能只计算用户采纳的结果。三者都可以叫吞吐，但不能直接比较。

### 8.1.2 质量是性能合同的一部分

量化、截断、缓存、降级模型和更激进的采样都可能改变质量。若性能优化导致 JSON 解析失败、代码测试失败、RAG 引用不支持或安全边界漂移，重试和人工介入会反过来增加总成本。

因此性能压测需要带着一小组质量回归集运行：短问答、长上下文、代码/结构化输出、工具调用、拒答边界和真实业务样本。性能结果不能脱离质量结果独立宣布。

## 8.2 先把请求记录成可以回放的 trace

一次请求如果只能在日志里看到 `latency=3.2s`，它几乎不能用于排障。至少要把请求拆成阶段，并保留每阶段的开始、结束、状态和版本。

可以把第 `i` 个请求记录成：

$$
r_i=(a_i,q_i,z_i,p_i,f_i,d_i,u_i,k_i,e_i,v_i)
$$

其中：

- `a_i` 是到达时间；
- `q_i` 是排队等待；
- `z_i` 是 tokenizer、模板渲染和 prompt 组装；
- `p_i` 是 prefill；
- `f_i` 是首个 chunk 的发送开销；
- `d_i=(d_{i,2},...,d_{i,O_i})` 是后续输出 token 的间隔序列；
- `u_i` 是输入、计划输出、实际输出和业务切片；
- `k_i` 是 KV Cache、prefix cache 和 batch 状态；
- `e_i` 是错误、取消、超时和依赖状态；
- `v_i` 是模型、模板、引擎、精度和部署版本。

### 8.2.1 请求级字段不能被平均掉

排障必须保留以下字段的原始值或可重建摘要：

```text
request_id、user/tenant、arrival、queue_start、prefill_start、first_token
input_tokens、max_output_tokens、emitted_tokens、cancel_reason、finish_reason
model_id、checkpoint、tokenizer、chat_template、precision、engine_version
batch_id、running_batch_size、prefill_budget、decode_budget、priority
kv_requested、kv_allocated、kv_evicted、prefix_hit_tokens、cache_key_version
gateway_send、client_receive、client_render、upstream/tool spans
quality_status、parse_error、safety_status、cost、retry_count
```

用户取消尤其重要。取消不是普通成功请求的尾部样本，也不一定是模型质量问题；但如果取消集中发生在首 token 之前，它就是用户感知延迟的证据。完成、取消、超时、服务错误和质量失败应保持不同状态。

### 8.2.2 阶段边界必须互相对齐

如果 worker 认为 `first_token=1200ms`，网关认为 `first_chunk=1600ms`，客户端认为 `first_render=2400ms`，三个数字都可能正确，因为它们测量的边界不同。监控命名应明确：

```text
model_first_token：模型生成第一个 token
server_first_chunk：服务端准备发送的第一个 chunk
client_first_byte：客户端收到首字节
client_first_render：界面真正显示内容
```

只有边界一致的指标才能做版本对比。否则团队可能误以为模型变慢，实际是代理缓冲或前端渲染变慢。

## 8.3 TTFT、TPOT 和端到端延迟的定义域

### 8.3.1 TTFT 不是模型 forward 的别名

当请求确实产生了首个 token 时，TTFT 可以写成：

$$
\mathrm{TTFT}_i=q_i+z_i+p_i+f_i
$$

这个公式的前提是各阶段时间非负且边界不重叠。若请求在首 token 前取消或失败，TTFT 不是 `0`；应该记录为 `not_observed` 或 `unknown`，并另行统计“首 token 前取消率”。

TTFT 高的原因可能在排队、tokenizer、RAG 前置链路、prefill、路由、prefix cache 失效、网关发送或客户端首字节，而不只是模型算力。

### 8.3.2 TPOT 对单 token 输出没有定义

如果请求输出 `O_i` 个 token，并且第一个 token 已计入 TTFT，后续 token 间隔为 `d_{i,j}`，则当 `O_i>1` 时：

$$
\mathrm{TPOT}_i=\frac{\sum_{j=2}^{O_i}d_{i,j}}{O_i-1}
$$

当 `O_i=1` 时没有后续间隔，TPOT 是 `not_applicable`；当 `O_i=0` 或首 token 未观察到时，TPOT 是 `unknown` 或 `not_observed`。不能用人为的非零分母把这些不同状态改成一个数字。

### 8.3.3 端到端延迟包含结束路径

当首 token 和后续间隔都被观察到时：

$$
T_i^{e2e}=\mathrm{TTFT}_i+\sum_{j=2}^{O_i}d_{i,j}+r_i
$$

其中 `r_i` 包括 postprocess、最后一个 chunk、计费、日志、网络收尾和客户端结束事件。若请求在完成前取消，应该保留“从到达到取消”的生命周期时间，但不能把它伪装成完整请求的端到端延迟。

### 8.3.4 分位数要求非空样本

对非空延迟集合 `X=(x_1,...,x_n)`，分位数实现必须明确排序和插值规则。例如采用线性插值时，先令 `h=(n-1)p`，再在相邻顺序统计量之间插值。`n=0` 时 P50、P95 和 P99 都是 `not_applicable`；不同实现对小样本 P99 的结果可能不同，报告应保存实现版本和样本量。

尾延迟不能用平均值替代。平均值可能被大量短请求拉低，而少量长请求正是用户投诉、超时和资源耗尽的来源。

## 8.4 prefill 和 decode 是两种不同的瓶颈

### 8.4.1 Prefill 决定新请求何时开始说话

prefill 一次处理整个输入上下文，通常更偏计算密集。输入 token 越多，需要建立的注意力状态越多；RAG chunk、工具 schema、多轮历史和长文档都会影响它。

prefill 变慢的证据可能包括：

```text
input token P95 上升
tokenizer 或 prompt assembly CPU 占用上升
queue 正常但 TTFT 和 prefill time 同时上升
prefix cache 命中下降
长 prompt 在 GPU 上占用一个调度轮次过久
RAG/rerank/tool 前置 span 先于模型出现长尾
```

如果 GPU 利用率不高但 TTFT 变高，优先检查排队、CPU、路由和上游链路；如果 prefill tokens/s 下降且输入长度稳定，再看 kernel、精度、显存带宽和设备状态。

### 8.4.2 Decode 决定持续输出速度

decode 每轮通常只为每个活跃序列生成一个或少量 token，受到权重读取、KV Cache 读取、batch 形状和调度开销影响。decode 变慢时，首 token 可能正常，但后续 token 间隔变大或抖动。

应该同时记录：

```text
GPU decode step time、每轮活跃序列数、每轮生成 token 数
KV block 读取/抢占、显存带宽、量化 kernel、speculative 接受率
服务端生成时间、网关发送时间、客户端接收时间
```

如果 worker 的 decode step 很快而客户端间隔很长，问题在 streaming、网络或渲染；如果两者都慢，才进入模型和调度层。

### 8.4.3 混合调度的核心是资源时间分配

过度优先 prefill，新请求 TTFT 可能降低，但已有流式请求会出现 token 间隔尖峰；过度优先 decode，已有请求顺畅，但新请求可能长时间排队。chunked prefill、token budget、长短请求分队列和优先级都在解决这个时间分配问题。

调度器不应只看请求数量。一个 8,000 token 的长请求和八个 100 token 的短请求都是“一个请求”，但它们对 prefill、KV 和队列的影响完全不同。按 token 和预计生命周期管理资源，通常比按 request count 更接近真实容量。

## 8.5 KV Cache：容量、碎片和共享要一起看

模型权重通常在启动时固定占用显存，KV Cache 则随着活跃请求的上下文和输出增长。高并发服务中，KV Cache 常常比权重更早达到容量上限。

### 8.5.1 基本显存估算

对 `L` 层、每层 `H_kv` 个 K/V 头、每头维度 `D_h`、每个元素占 `b` 字节的模型，第 `i` 个活跃请求占用 `A_i` 个 token 时，未计入实现额外开销的 KV 字节数近似为：

$$
M_{KV}=2L H_{kv}D_h b\sum_i A_i
$$

前面的 `2` 对应 Key 和 Value。GQA/MQA 通过减少 `H_kv` 降低每 token 的 KV 状态，但不会消除层数、head dimension、上下文长度和活跃并发的影响。

这个公式是容量估算，不是实际显存读数。实际系统还需要考虑 block 元数据、对齐、临时 workspace、prefix 共享、碎片、抢占、量化格式和框架保留空间。

### 8.5.2 block 分配会引入内部碎片

如果系统按 `B` token 一个 block 分配，第 `i` 个请求的已分配 token 数可能是：

$$
\tilde A_i=B\left\lceil\frac{A_i}{B}\right\rceil
$$

当请求集合非空且 `sum_i tilde A_i>0` 时，内部碎片比例可以写成：

$$
R_{frag}=1-\frac{\sum_i A_i}{\sum_i\tilde A_i}
$$

block 太大，短请求浪费更多；block 太小，管理元数据和调度开销可能增加。分页管理的价值在于让 KV Cache 能按块增长、回收和共享，而不是保证任何负载下都没有 OOM。

PagedAttention 论文把 KV Cache 的动态分配和碎片问题类比为分页内存，并在论文设定下报告了显著吞吐收益。这个结果不能直接迁移成“换成某个引擎就一定快多少”，因为模型、硬件、batch、序列长度和基线都会改变结果。

### 8.5.3 共享 prefix 既节省显存，也增加正确性约束

多个请求拥有相同的 system prompt 或工具说明时，可以共享前缀状态。共享的前提是 token 序列、模型版本、精度、位置语义、权限上下文和失效策略都一致。

以下内容不能随意放进可共享前缀：

```text
用户身份、租户权限和敏感文档
随时间变化的政策、价格和库存
请求级随机数、工具状态和外部 observation
包含用户输入的可变历史
```

缓存命中率高但答案错用了其他用户权限，是比缓存不生效更严重的事故。KV 节省必须和权限、版本、失效和错误复用率一起审计。

## 8.6 batching 和调度：吞吐不是免费的

连续 batching 或 in-flight batching 可以让新请求在已有请求生成期间加入运行批次，减少设备空闲。但它也会让不同长度、不同优先级和不同阶段的请求共享资源。

### 8.6.1 变大 batch 的三个副作用

第一，短请求可能被长请求占住 KV block 和调度轮次；第二，prefill 大块工作可能阻塞 decode；第三，设备吞吐增加的同时，排队和尾延迟可能上升。

一个常见的错误实验是固定 prompt、固定输出、固定并发做 benchmark，然后把结果推广到真实流量。真实流量至少有长短混合、取消、重试、不同业务优先级和外部依赖波动。压测必须保留这些结构。

### 8.6.2 token budget 比 request count 更有解释力

调度器可以在每轮限制 prefill token budget 和 decode token budget，让长请求不能无限占用设备。预算过小会增加调度开销，预算过大则会造成其他请求等待。需要通过不同长度分桶观察 TTFT、TPOT 和 P99，而不是只看一条总吞吐曲线。

### 8.6.3 公平性和优先级必须可观测

核心业务可能需要更低的 TTFT，批处理任务可以延后；但优先级不能变成不可解释的饥饿。记录每个请求的优先级、排队时长、被跳过次数和实际服务时间，才能发现低优先级请求是否长期没有机会。

长短请求隔离通常增加一些资源碎片，却能保护短请求的尾延迟。是否值得隔离，应由任务价值、SLO 和容量成本决定，而不是由 GPU 利用率单独决定。

## 8.7 量化优化的是资源，不自动优化体验

量化减少权重或激活的存储占用，可能降低显存和带宽压力；实际速度是否提升取决于 kernel、硬件、反量化开销、batch 形状和内存访问。INT4 能加载并不等于 INT4 在业务上更好。

### 8.7.1 量化质量要按行为切片

至少要比较：

```text
通用问答、数学、代码和长上下文
JSON/schema、函数调用和工具参数
中文/多语言、RAG 引用和拒答边界
输出长度、重试率、解析失败和人工接管
```

校准数据覆盖不到真实业务时，平均 benchmark 可能没有明显退化，但关键格式或长上下文已经变差。量化后的质量回归要与 FP16/BF16 baseline 使用相同 prompt、解码和硬件条件。

### 8.7.2 量化的真实收益要按有效任务计算

如果量化把单请求成本降低 30%，却让 JSON 解析失败、重试和人工审核增加，那么单位成功任务成本可能上升。性能报告应同时给出：

```text
每请求成本、每成功任务成本、每秒有效任务数
TTFT/TPOT/P95/P99、显存和 OOM
质量回归、解析失败、重试、取消和人工接管
```

只有在这些指标的组合下，才能判断量化是否值得保留。

## 8.8 Prompt、RAG 和工具说明会改变推理成本

长 prompt 不只增加输入 token 价格，还会增加 prefill 时间、KV Cache 需求和上下文干扰。系统 prompt、RAG chunk、工具 schema、多轮历史和用户文件常常在产品迭代中悄悄增长。

### 8.8.1 输入 token 的增长需要基线

设新版本和基线版本的输入 token 总数分别为 `I_new` 与 `I_base`，且 `I_base>0`，prompt 漂移比为：

$$
\gamma_{prompt}=\frac{I_{new}}{I_{base}}
$$

如果基线样本没有输入 token 记录，漂移是 `unknown`；不能用零或任意常数修补。报告还应按 system、history、retrieved、tool schema 和 user content 拆分增长来源。

### 8.8.2 RAG 的上下文预算要看有效信息

把更多 chunk 放进上下文，可能提高证据召回，却同时增加 prefill 和噪声。应记录每个请求的候选文档数、最终注入 token、有效证据 token、重复 token 和引用支持结果。只看上下文长度不能说明检索质量，只看检索命中也不能说明回答会利用证据。

### 8.8.3 工具 schema 不是免费的静态文本

把几十个工具的完整 schema 每轮注入，会让输入变长、prefill 变慢，也会增加模型选择错误。按任务路由工具、压缩描述、稳定共享前缀，并在 schema 版本变更时使缓存失效，通常比无限提高 `max_context` 更有效。

## 8.9 Streaming 的瓶颈可能在模型之外

流式生成的用户体验由至少三段时间组成：模型生成、服务端发送、客户端接收和渲染。任何一段缓冲都可能让用户看不到已经生成的 token。

### 8.9.1 三端打点才能定位

建议为同一个 chunk 记录：

```text
worker_generate_at
server_enqueue_at
gateway_write_at
client_receive_at
client_render_at
```

如果 `worker_generate_at` 很早，`client_receive_at` 很晚，检查网关、代理、SSE/WebSocket、压缩和 backpressure；如果收到很快但显示很晚，检查前端批量渲染和 markdown 解析；如果 worker 本身间隔很大，才回到 decode 和调度。

### 8.9.2 错误、取消和结束事件也属于协议

客户端断开后，服务端应尽快取消生成并释放 KV；超时和依赖失败需要明确结束原因；重试请求要有 request id 或幂等关联，避免一次用户动作产生多条计费和外部副作用。只实现“正常 token 流”而没有错误/取消事件，会让监控和资源回收都不可靠。

## 8.10 缓存的收益和正确性必须同时计算

推理系统可能使用 prefix cache、prompt cache、response cache、embedding cache、检索 cache 和工具结果 cache。缓存命中不是收益的同义词。

当输入 token 总数 `I>0` 时，可复用输入 token 命中率为：

$$
R_{hit}=\frac{H}{I}
$$

其中 `H` 是命中的 token 数。若没有可缓存输入，命中率为 `not_applicable`；若命中字段缺失，状态为 `unknown`。还要计算节省的 prefill 时间、占用的内存和错误复用率。

缓存 key 至少要考虑：

```text
模型/模板/精度版本
system prompt 和工具 schema 版本
租户、用户和权限上下文
文档版本、生效时间和地域
随机性、外部状态和失效时间
```

response cache 可能复用过期政策，RAG cache 可能跨权限泄露，tool result cache 可能复用已经变化的库存。缓存设计要有失效和审计，而不是只在仪表盘上展示 hit rate。

## 8.11 限流、取消和降级是容量系统的一部分

没有限流时，少量长请求、无限重试或上游故障就能占满队列和 KV Cache。限流不是简单拒绝请求，而是按资源和价值控制系统在峰值下的行为。

可以按以下维度限制：

```text
请求数、输入 token、预计输出 token、活跃序列数
KV Cache token/block、租户配额、业务优先级
单用户重试次数、长上下文比例和工具调用次数
```

取消处理同样重要。客户端已经离开页面时，继续生成会浪费显存和成本；但取消信号如果没有传到 worker，监控看到的“请求数下降”不代表资源已经释放。应记录取消传播时间和 KV 回收时间。

降级策略可以包括小模型、较短上下文、异步队列、只返回检索结果、关闭非核心工具或转人工。降级必须标记在结果中，并进入质量、成本和用户行为统计；不能把降级成功伪装成主模型成功。

## 8.12 容量规划要使用分布而不是平均值

容量规划至少需要输入：

```text
峰值和突发 QPS、输入/输出 token 分布、并发和取消分布
TTFT/TPOT/P95/P99 目标、模型精度和引擎版本
KV Cache 可用预算、长上下文比例、prefix 命中率
依赖服务耗时、限流/降级比例、故障切换和冗余容量
```

一个粗略流程是：先从真实流量得到输入、输出和并发分布；再对真实混合负载做压测；然后用 KV 和尾延迟反推每实例可承载的活跃 token；最后加入故障冗余和突发余量。

平均 QPS 只能给出产能大致方向，不能证明 P99 可控。长请求和短请求的混合比例、prefix cache 命中、取消和重试都会改变有效容量。

### 8.12.1 计算容量和显存容量要分开

某实例可能还有计算空闲，却因为 KV block 不足无法接受新请求；也可能显存足够，但 tokenizer、网络或 CPU 调度成为瓶颈。容量报告要分别给出：

```text
计算利用率、prefill/decode 产能
KV token/block 容量和分配失败
队列长度、排队时间和尾延迟
CPU tokenizer、网关、网络和外部依赖
```

“再加一张 GPU”只对真正的设备瓶颈有效。若路由不均、队列锁、缓存失效或上游 RAG 才是根因，扩容不会消除问题。

## 8.13 监控看板要能回答“用户为什么等”

建议把看板分为四层。

请求体验层：TTFT、TPOT、端到端延迟、P50/P95/P99、首 token 前取消率、流式间隔。

调度和资源层：QPS、活跃序列、队列时间、batch size、prefill/decode token budget、GPU/CPU 利用率、显存、KV block、OOM 和抢占。

链路层：tokenizer、RAG、rerank、工具、网关写入、客户端接收、错误和依赖超时。

价值和质量层：成功任务成本、重试、解析失败、代码测试、引用支持、安全、人工接管和用户采纳。

每一个指标都要能按模型版本、引擎、精度、业务线、输入长度、输出长度、租户和时间窗口切分。总平均掩盖问题时，切片才是定位入口。

## 8.14 性能压测要像真实流量，而不是算子展示

压测前先固定版本和环境：模型权重、tokenizer、chat template、引擎、精度、硬件、驱动、batch 参数、cache 状态和网络路径。然后构造接近生产的请求分布。

压测至少覆盖：

```text
短/中/长输入和短/中/长输出
冷 cache、热 cache、部分命中和失效
低/中/峰值并发、突发流量和长短混合
正常完成、客户端取消、超时、重试和依赖故障
不同优先级、限流、降级和实例故障切换
量化版本与 baseline 的质量和协议回归
```

每组压测都记录稳定时间、预热方式、样本量、分位数算法、异常请求处理和结果版本。单次短时间 benchmark 可能只测到热 cache 和稳定 GPU，不代表长时间运行的碎片、泄漏、排队和漂移。

## 8.15 典型修复顺序：先保护用户，再追求极限吞吐

推理性能事故修复可以按因果顺序推进。

第一步，保留现场并降低影响：限制超长请求、暂停扩大流量、保护核心业务、设置清晰超时和降级。

第二步，按请求 trace 拆分 queue、tokenizer、prefill、decode、streaming 和外部依赖，确认第一处异常，而不是只看最后的总延迟。

第三步，检查输入和输出分布是否漂移，尤其是 RAG chunk、工具 schema、多轮历史和 max output 是否变长。

第四步，核对 KV Cache：活跃 token、block 分配、碎片、prefix 共享、取消回收和实例路由。

第五步，针对调度做小范围对照：batch、token budget、chunked prefill、长短队列和优先级，每次只改变主要因素。

第六步，重新跑质量回归，确认量化、截断、缓存和降级没有损伤格式、代码、引用、安全和工具协议。

第七步，在真实混合流量上灰度，比较用户级 TTFT/P99、任务完成、成本和取消，而不只看 GPU 利用率。

## 8.16 关键公式与边界语义

### 8.16.1 输出吞吐

若在墙钟区间 `T_wall>0` 内实际发送了 `O_total` 个输出 token，则：

$$
S_{out}=\frac{O_{total}}{T_{wall}}
$$

如果没有有效时间窗口，吞吐是 `not_applicable`；如果 token 计数缺失，状态是 `unknown`。`S_out` 只代表产能，不代表任务成功或用户体验。

### 8.16.2 KV 压力

若可用于 KV 的显存预算 `B_KV>0`，则：

$$
\rho_{KV}=\frac{M_{KV}}{B_{KV}}
$$

当预算缺失或为零时，压力没有定义；当实际分配还要加上碎片和临时空间时，公式值只能作为下界。真正的分配失败、抢占和 OOM 事件应单独计数。

### 8.16.3 任务完成成本

请求成本可以按请求平均，但生产更关心成功任务集合 `S`：

$$
C_{success}=\frac{\sum_i c_i}{\lvert S\rvert},\qquad \lvert S\rvert>0
$$

没有成功任务时，单位成功成本没有定义，不能为了让图表有数值而写成零。成本还应包括重试、工具、RAG、人工审核和失败补偿。

### 8.16.4 性能和质量的联合判断

可以把一次发布判断写成多个独立条件的记录：

```text
ttft_status、tpot_status、tail_latency_status
kv_status、cache_status、prompt_cost_status
quality_status、safety_status、rollback_status
```

这些状态的来源不同，不能随意相乘成一个“综合通过率”。如果某项没有样本或没有测量，应标记 `not_applicable` 或 `unknown`，而不是用零分假装完成了测试。

### 8.17.1 统计工具和请求契约

```python
from dataclasses import dataclass
from math import ceil, isfinite
from typing import Iterable, Optional


@dataclass(frozen=True)
class Metric:
    value: Optional[float]
    status: str
    reason: str = ""


def finite_number(value, name):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError(f"{name} must be a finite number")
    value = float(value)
    if not isfinite(value):
        raise ValueError(f"{name} must be finite")
    return value


def nonnegative_int(value, name):
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")
    return value


def safe_mean(values: Iterable[float], *, empty_status="not_applicable"):
    values = list(values)
    if not values:
        return Metric(None, empty_status, "empty sample set")
    checked = [finite_number(value, "mean.value") for value in values]
    return Metric(sum(checked) / len(checked), "valid")


def safe_ratio(numerator, denominator, *, name="ratio", empty_status="not_applicable"):
    numerator = finite_number(numerator, f"{name}.numerator")
    denominator = finite_number(denominator, f"{name}.denominator")
    if numerator < 0 or denominator < 0:
        raise ValueError(f"{name} cannot be negative")
    if denominator == 0:
        if numerator == 0:
            return Metric(None, empty_status, f"{name} has no denominator")
        raise ValueError(f"{name} has positive numerator and zero denominator")
    return Metric(numerator / denominator, "valid")


def percentile(values, percentage):
    values = [finite_number(value, "percentile.value") for value in values]
    percentage = finite_number(percentage, "percentile.percentage")
    if not values:
        return Metric(None, "not_applicable", "empty sample set")
    if not 0 <= percentage <= 100:
        raise ValueError("percentage must be between 0 and 100")
    ordered = sorted(values)
    position = (len(ordered) - 1) * percentage / 100
    lower = int(position)
    upper = min(lower + 1, len(ordered) - 1)
    fraction = position - lower
    value = ordered[lower] + (ordered[upper] - ordered[lower]) * fraction
    return Metric(value, "valid")


def validate_request(request):
    for key in ("arrival_ms", "input_tokens", "baseline_input_tokens", "emitted_tokens",
                "queue_ms", "tokenize_ms", "prefill_ms", "first_chunk_ms",
                "postprocess_ms", "kv_active_tokens"):
        nonnegative_int(request[key], key)
    for key in ("cancelled", "kv_alloc_failed", "quality_ok"):
        if type(request[key]) is not bool:
            raise ValueError(f"{key} must be a real bool")
    if request["emitted_tokens"] == 0:
        if request["first_chunk_ms"] != 0 or request["decode_ms"]:
            raise ValueError("zero emitted tokens cannot have token timing")
    elif len(request["decode_ms"]) != request["emitted_tokens"] - 1:
        raise ValueError("decode timing must contain one interval per token after the first")
    for value in request["decode_ms"]:
        nonnegative_int(value, "decode_ms.value")
```

### 8.17.2 计算请求级指标

```python
def request_metrics(request):
    if request["emitted_tokens"] == 0:
        return {
            **request,
            "ttft": Metric(None, "not_observed", "no first token"),
            "tpot": Metric(None, "not_applicable", "no output interval"),
            "e2e": Metric(None, "unknown", "request did not produce output"),
        }
    ttft = request["queue_ms"] + request["tokenize_ms"]
    ttft += request["prefill_ms"] + request["first_chunk_ms"]
    tpot = safe_mean(request["decode_ms"], empty_status="not_applicable")
    e2e = ttft + sum(request["decode_ms"]) + request["postprocess_ms"]
    return {**request, "ttft": Metric(ttft, "valid"),
            "tpot": tpot, "e2e": Metric(e2e, "valid")}


reports = [request_metrics(request) for request in requests]
ttft_values = [r["ttft"].value for r in reports if r["ttft"].status == "valid"]
tpot_values = [r["tpot"].value for r in reports if r["tpot"].status == "valid"]
e2e_values = [r["e2e"].value for r in reports if r["e2e"].status == "valid"]
queue_values = [r["queue_ms"] for r in reports]

ttft_p95 = percentile(ttft_values, 95)
tpot_p95 = percentile(tpot_values, 95)
e2e_p99 = percentile(e2e_values, 99)
queue_p95 = percentile(queue_values, 95)
```

`tpot_values` 不包含单 token 或没有后续间隔的请求；这不是丢掉失败，而是保持指标定义域。单独报告 `not_applicable` 的数量，才能知道某个 TPOT 结果到底覆盖了多少请求。

### 8.17.3 计算 KV、缓存、吞吐和质量

```python
layers = 32
kv_heads = 8
head_dim = 128
bytes_per_value = 2
kv_block_tokens = 128
kv_budget_gib = 2.35

requested_kv_tokens = sum(r["kv_active_tokens"] for r in reports)
allocated_kv_tokens = sum(
    ceil(r["kv_active_tokens"] / kv_block_tokens) * kv_block_tokens
    for r in reports
)
kv_bytes = 2 * layers * requested_kv_tokens * kv_heads * head_dim * bytes_per_value
kv_peak_gib = kv_bytes / (1024 ** 3)
kv_pressure = safe_ratio(kv_peak_gib, kv_budget_gib, name="kv_pressure")
fragmentation = safe_ratio(
    allocated_kv_tokens - requested_kv_tokens,
    allocated_kv_tokens,
    name="kv_fragmentation",
)

input_tokens = sum(r["input_tokens"] for r in reports)
baseline_input_tokens = sum(r["baseline_input_tokens"] for r in reports)
emitted_tokens = sum(r["emitted_tokens"] for r in reports)
cache_hits = sum(r["cache_hit_tokens"] for r in reports)
cache_hit_rate = safe_ratio(cache_hits, input_tokens, name="cache_hit_rate")
prompt_cost_ratio = safe_ratio(
    input_tokens, baseline_input_tokens, name="prompt_cost_ratio"
)
bad_flags = [
    r["cancelled"] or r["kv_alloc_failed"] or not r["quality_ok"]
    for r in reports
]
bad_request_rate = safe_ratio(sum(bad_flags), len(reports), name="bad_request_rate")
quality_regressions = [r["id"] for r in reports if not r["quality_ok"]]
kv_failures = [r["id"] for r in reports if r["kv_alloc_failed"]]

start_ms = min(r["arrival_ms"] for r in reports)
end_ms = max(r["arrival_ms"] + r["e2e"].value for r in reports
             if r["e2e"].status == "valid")
wall_seconds = (end_ms - start_ms) / 1000
throughput = safe_ratio(emitted_tokens, wall_seconds, name="output_throughput")
```

这里的 `kv_pressure` 是用估算显存除以预算，`kv_failures` 则是直接观察到的分配失败。两者都要报告：估算低于预算不代表没有碎片、临时 workspace 或路由竞争，分配失败也可能来自估算遗漏。

### 8.17.4 用条件列表记录发布判断

```python
if queue_p95.status != "valid" or queue_p95.value > SLO["queue_p95_ms"]:
    failed_conditions.append("queue_wait")
if kv_pressure.status != "valid" or kv_pressure.value > SLO["kv_pressure"] or kv_failures:
    failed_conditions.append("kv_capacity")
if cache_hit_rate.status != "valid" or cache_hit_rate.value < SLO["cache_hit_rate"]:
    failed_conditions.append("cache_effectiveness")
if prompt_cost_ratio.status != "valid" or prompt_cost_ratio.value > SLO["prompt_cost_ratio"]:
    failed_conditions.append("prompt_cost_drift")
if bad_request_rate.status != "valid" or bad_request_rate.value > SLO["bad_request_rate"]:
    failed_conditions.append("errors_or_quality")

release_decision = "continue_investigation" if failed_conditions else "expand_evidence"
```

这些阈值是教学构造，不是通用服务标准。真实 SLO 要根据任务价值、用户等待容忍度、模型质量、流量结构和成本校准。代码使用 `status` 保护未定义值：没有样本时不会把 `None` 和数字直接比较，也不会把未测量当成通过。

### 8.18.1 论文和算法资料

- [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180) 解释动态 KV Cache 的碎片、重复分配和分页管理，并在论文实验条件下报告 vLLM 相对当时基线的吞吐改进。论文结果不能直接推出当前硬件、模型和业务流量的加速比例。
- vLLM 的 [Paged Attention 文档](https://docs.vllm.ai/en/latest/design/paged_attention.html) 和 [prefix caching 文档](https://docs.vllm.ai/en/latest/design/prefix_caching.html) 适合确认具体实现的概念和版本边界。文档页面标明版本状态，部署时仍需锁定 commit 或 release 并做本地压测。
- continuous batching、chunked prefill、speculative decoding 和量化 kernel 的效果依赖请求分布、硬件、实现和质量目标。论文或仓库中的 benchmark 是实验结果，不是生产 SLO。

### 8.18.2 官方文档

- OpenAI 的 [Latency Optimization](https://platform.openai.com/docs/guides/latency-optimization) 和 [Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching) 适合了解请求延迟拆分、输入输出 token、缓存组织和 API 观测字段。供应商接口和计费规则会随版本变化，不能把文档中的示例数字当作本地服务容量。

- NVIDIA [TensorRT-LLM 文档](https://nvidia.github.io/TensorRT-LLM/) 可作为特定硬件和引擎的配置、benchmark 与调度参考。其结果必须绑定 GPU、CUDA、驱动、引擎版本和输入分布。

官方资料适合确认 API、实现和配置，不替代目标集群的压测、故障演练和质量回归。

### 8.18.3 本地实测

本章的 Python demo 是教学构造，用来演示请求级归因和定义域，不代表任何真实硬件的 benchmark。真实结论需要保存压测脚本、硬件和软件版本、输入输出分布、cache 状态、并发模型、异常请求处理、质量结果和原始 trace。

当宣传材料只给出“吞吐提升多少”，而没有延迟分位数、请求长度、并发、模型精度和基线时，最多只能把它当成待验证线索，不能直接写进容量规划或产品承诺。

## 8.19 事故复盘应回答的六个问题

一次推理性能事故复盘不应只写“GPU 不够”。至少要回答：

1. 用户在什么时间、什么业务、什么请求长度下开始变慢？
2. 第一处异常出现在队列、tokenizer、prefill、decode、网络还是外部依赖？
3. 输入、输出、batch、KV、cache 或路由的哪个分布发生了变化？
4. 性能变化是否伴随格式、代码、引用、安全或工具质量回归？
5. 为什么现有监控、容量余量、取消回收和降级没有提前保护用户？
6. 修复后用什么混合流量、版本对照和质量样本证明问题真正消失？

如果回答不了这些问题，扩容或换引擎只能暂时降低症状，不能说明根因。

## 8.20 本章小结

推理部署优化的目标不是让某个吞吐数字最大，而是在真实请求分布下同时保护首 token、持续流式、尾延迟、显存、成本、稳定性和质量。

TTFT 要拆出排队、tokenizer、prefill 和发送路径；TPOT 只对存在后续 token 的请求定义；端到端延迟要包含结束路径；P95/P99 要保留非空样本和实现细节。prefill 和 decode 的资源特征不同，batch 越大不一定越好；KV Cache 要同时看容量、block 碎片、共享、取消回收和分配失败；分页管理能改善内存利用，但不会消除所有容量问题。

量化、prompt 压缩、缓存、限流和降级都必须与格式、代码、RAG、工具、安全和任务成功一起评估。流式输出要在 worker、网关和客户端三端打点；容量规划要使用输入输出分布和混合流量；压测要包含取消、重试、长短请求、cache 冷热、依赖故障和故障切换。

下一章进入 RAG 落地。推理服务解决的是“系统能否稳定地把模型运行起来”，RAG 还要继续回答“送进模型的证据是否正确、及时、可追溯并且符合权限”。
