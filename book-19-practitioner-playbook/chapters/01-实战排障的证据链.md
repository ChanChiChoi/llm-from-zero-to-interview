# 第一章：实战排障的证据链

大模型系统的故障很少表现为一个函数明显写错。用户只看到回答变差、请求变慢或任务没有完成，后台却可能同时发生了模型升级、索引切换、流量变化、权限策略更新和下游超时。直接换模型或重写提示词，也许能暂时改变结果，却不一定能解释发生了什么。

实战排障要把模糊的异常逐步变成可核对的判断：什么任务没有达标，影响了哪些请求，变化从何时开始，哪条证据支持哪种解释，修复后怎样确认问题消失且没有引入新的副作用。本章以一套企业采购制度助手为例建立通用方法，再说明怎样把它带到训练、评估、推理服务、检索增强生成（Retrieval-Augmented Generation，RAG）、能够选择工具并依据执行回执继续工作的 Agent，以及多模态系统。各领域的深入机制分别见第 2—12 章。

## 1.1 现象、故障和根因是三件事

“模型回答变差”是现象，不是故障原因。“检索召回错了”比现象更具体，却仍没有说明为什么召回错。文档解析、版本字段、权限过滤、索引延迟和重排都可能造成相似的最终输出。

- **现象**是用户或监控直接观察到的表现，例如引用缺失、P99（第 99 百分位）延迟上升或 loss 出现 NaN。
- **故障**是系统没有满足一项已定义的任务或服务要求。例如采购问答在有权限且存在有效制度时仍引用失效版本。
- **触发变化**是让问题出现的事件，例如索引快照切换、数据批次上线、依赖升级或流量变化。
- **放大条件**会扩大影响或延缓恢复，例如没有回滚快照、重试重复提交副作用，或 trace 中没有保存版本字段。
- **根因解释**必须说明证据如何从触发变化走到用户可见故障，并能通过受控回放或其他反事实检查得到支持。

发现某次改动后指标恢复，还不能单独证明因果关系。若同一时间更换了模型、数据和评分器，团队仍不知道哪一项起了作用。排障记录首先要把“观察到什么”和“我认为为什么”分开。

## 1.2 先写任务契约，才知道什么算失败

用户说“答案不对”时，可能指事实错误、引用过期、表达太长、无权访问或系统没有说明下一步。不同任务的成功条件不同，所以先把系统承诺写成可检查的任务契约。

采购制度问答可以约定：输入是问题、用户身份、租户和知识库快照；答案要给出结论和可访问的当前制度依据；无证据或版本不明时应说明无法确认；系统不得泄露无权查看的材料，也不得替用户执行付款或合同变更。由此，引用是否指向有效版本是硬条件，而“创建付款”不属于这项只读任务。

记录任务状态时，至少区分以下情形：

| 状态 | 含义 | 排障时的处理 |
| --- | --- | --- |
| 成功 | 适用的必要条件均有证据支持 | 检查是否只在某个切片或版本上成功 |
| 失败 | 已观测到违反任务契约的结果 | 保留输入、实际结果和失败条件 |
| 未知 | 契约要求检查，但记录或状态不足以判断 | 补证据；不能当作成功或失败填入普通分母 |
| 不适用 | 当前任务不包含该条件 | 明确记为不适用，不把它伪装成满分 |

“调用成功”“HTTP 返回 200”“用户任务完成”是不同对象。工具返回成功但写错了订单，仍然是任务失败；没有权限日志则是未知，不代表没有越权。

## 1.3 先划出影响范围

总平均会掩盖局部故障。总体成功率只下降一点，仍可能意味着高风险任务或某个租户全部失败。最初应把故障按能改变判断的维度切开：

| 维度 | 要确认的内容 | 可用证据 |
| --- | --- | --- |
| 时间 | 最后成功和首次失败分别何时出现？ | 请求记录、发布、配置和数据切换时间 |
| 任务 | 哪类任务失败，哪些仍正常？ | 任务类型、验收结果、状态码和用户反馈 |
| 频率 | 偶发、集中爆发还是持续发生？ | 请求级事件、按时间分桶的序列和历史基线 |
| 用户与权限 | 哪些租户、角色或地区受到影响？ | 经过授权的身份切片和权限版本 |
| 输入 | 长度、语言、文件格式或业务类别是否相关？ | 脱敏后的输入元数据和分桶 |
| 版本 | 模型、提示、检索、工具、策略各是什么版本？ | trace（一次请求跨组件的链路记录）、发布清单（release manifest）和数据快照 |
| 后果 | 体验下降、人工返工、数据暴露还是外部副作用？ | 业务记录、安全事件和人工复核 |

样本数要和任务定义绑定。日志没有记录到受影响请求时，不能把影响数填成零；也可能是观测链路漏了数据。若严重程度、业务损失或受影响人数还没有可靠定义，就先分别呈现可核实的数量和未知项，不用一组未经校准的权重压成“影响分”。

## 1.4 时间线先限制猜测空间

以下是采购制度助手的教学时间线，日期和时刻是构造案例，不代表真实生产事件：

| 时间 | 观察或动作 | 证据状态 |
| --- | --- | --- |
| 09:00 | 检索服务发布新版本，仍读取旧索引 | 发布记录可核对 |
| 09:12 | 切换到新索引快照，版本过滤规则同步变更 | 变更记录可核对；影响尚未确认 |
| 09:18 | 第一条“引用已失效制度”的反馈出现 | 反馈样本待复核 |
| 09:35 | 同类反馈增加，值班人员暂停扩大灰度 | 工单和灰度状态可核对 |
| 09:50 | 回放 trace，发现部分旧文档缺少生效日期字段 | 输入与索引记录可核对 |
| 10:10 | 对缺失或已失效日期采取拒绝入选的规则 | 修复部署记录可核对 |
| 10:40 | 固定回归集通过，先恢复小流量观察 | 只支持固定样本结论 |

“09:12 切换索引”是已记录的事实；“索引切换导致过期引用”仍是假设。若开始时间不清楚，先找最后一条成功记录和第一条失败记录，再按时间窗口比较版本、输入和路由。把每个时间点的来源写清，比事后依靠记忆补齐更可靠。

Google SRE 的监控材料区分外部可见行为和系统内部信号，并把它们用于不同的监控问题；迁移到大模型服务时，用户任务结果和内部 trace 需要同时观察，但两类指标不能相互替代。[Google SRE：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)

## 1.5 把猜测写成能被证据推翻的假设

“可能是数据、模型、prompt、部署”列出了名词，却没有告诉团队下一步检查什么。一个可用的假设至少要说清：如果它为真，应该看到什么；如果证据相反，接下来排除哪条分支。

对过期制度引用，可以这样展开：

```text
最终答案引用过期
├── 文档与索引：当前文档缺失、旧版本混入、索引快照不完整
├── 权限与过滤：用户权限错误、版本字段缺失时默认放行
├── 上下文与生成：有效片段已进入上下文，但答案没有采用它
├── 引用校验：只检查链接可打开，没有检查版本和 claim 支持
└── 任务定义：用户问题超出知识范围，系统却没有拒答
```

每个叶子都要配一项观测。例如，“旧版本进入候选”要看检索原始 top-k 和版本字段，不能只读最终答案；“模型忽略了证据”要确认支持片段确实进入上下文；“缓存返回旧答案”要比较带与不带索引版本的缓存键。这样的假设树把下一步检查连到可能的结果，也避免团队一开始就换模型。

## 1.6 证据要贴近请求，也要标明边界

不同材料能回答的问题不同。原始请求和工具回执有助于还原单次事件；trace 连接服务中的多个步骤；聚合指标发现分布变化；论文、产品文档和模型卡帮助解释机制或公开接口，但不能证明目标部署在当前配置下正常。

排查时可按这条顺序收集材料：

1. 经过允许的原始输入、预期结果和用户任务。
2. 预处理后的文本、图像、音频或结构化字段。
3. 模型、提示、检索器、索引、工具和策略版本。
4. 请求级候选文档、工具参数、外部回执和状态迁移。
5. 按任务、用户、输入和版本切片的聚合指标。
6. 人工复核、用户反馈和业务后果。
7. 用于解释机制的论文、官方文档或框架材料。

抽象资料能说明“某种机制可能怎样工作”，不能替代目标系统的失败 trace。反过来，单条 trace 可以说明这次请求发生了什么，却不足以证明整个模型家族或所有流量都如此。

## 1.7 让每次检查区分假设

实验不是把所有日志丢进脚本，而是改变或对照某个条件来区分解释。开始前记录问题、假设、要观察的信号和判断规则：

| 问题 | 可检验假设 | 检查或对照 | 支持假设的观察 |
| --- | --- | --- | --- |
| 旧制度为什么进入候选？ | 新索引把缺失生效日期的分块当作有效 | 固定问题，比较旧/新索引和旧/新过滤规则 | 过期分块只在新索引配旧规则时进入候选 |
| 答案为什么仍引用旧版本？ | 引用校验只验证链接可访问 | 对每个 claim 检查引用版本和生效日期 | 链接打开，但所引版本早于当前生效版本 |
| 是不是模型升级造成？ | 模型版本变化导致生成偏移 | 固定提示、检索结果和解码设置，只换模型 | 同一上下文下仅候选模型出现该偏差 |

优先做成本低、一次能区分多条分支的检查。例如查看原始候选文档、版本字段和过滤结果，通常比立即重新训练模型更能缩小范围。实验无法区分两个假设时，要记录“仍未知”，而不是挑一个更顺眼的解释。

## 1.8 最小复现要保留故障机制

最小复现不是把输入删到最短，而是在不改变故障机制的情况下去掉无关条件。通常先选一条有明确失败判定的请求，保存原始输入和版本，再固定模型、提示、索引、权限、工具和依赖；随后关闭与问题无关的并发、重试或缓存，逐步恢复真实流量条件。

同一输入重复回放 10 次，其中 8 次出现相同失败，只能说明该固定条件下观察到 8/10 次复现。它不能说明生产发生率是 80%，也不能解释未复现的 2 次是否受随机采样、动态数据或外部服务影响。复现记录要写分母、输入版本、环境和失败判定；任一条件变了，就不是同一个复现实验。

复制生产合同、令牌或完整用户 trace 到个人环境，可能把排障变成新的安全事件。复现时应最小化并脱敏输入；确需原文时，通过受控存储、授权访问和访问审计完成。

## 1.9 Baseline 与反事实说明“变化带来了什么”

Baseline 是固定条件下的参照，不是为了证明新方案一定赢。反事实则问：如果没有这项变化，结果会怎样？要回答它，尽量固定任务样本、提示、工具返回、权限和评估规则，只改变正在调查的版本或控制。

采购制度案例可以对照旧索引与新索引，也可以在同一新索引上只切换版本过滤规则。若同时更换模型、提示、分块和评分器，即使答案恢复，也不能判断是哪一项变化造成的。质量、延迟、成本和安全结果也应各自保留，不能用一个加权总分让某个维度替其他维度抵消。

只在任务集合、样本筛选、失败判定和配置足够一致时才比较差值。样本分布不相同、分母变化或评估器升级时，报告应标明不可直接横比，并把变化拆成新的基线或配对实验。

## 1.10 Trace 要连接系统决定与外部结果

对一次请求，工程师需要知道：系统收到什么、按什么身份和版本运行、检索或模型作出了什么决定、工具实际执行到哪一步、最后用户看到什么结果。Trace 应围绕这条因果链建模，而不是只存最终答案。

```mermaid
flowchart LR
    A["任务与身份"] --> B["输入和版本"]
    B --> C["检索与模型决定"]
    C --> D["工具或服务执行"]
    D --> E["外部状态与用户结果"]
    E --> F["回归和修复验证"]
```

采购制度问答可记录 request/task ID、租户和角色的受控标识、模型与提示版本、索引快照、策略版本、候选文档及版本、答案主张与引用的对应关系、工具状态、终态、分阶段延迟和成本。没有调查需要时，不要把完整问题、制度正文或工具参数复制进普通日志。各阶段要记录起止时间和依赖关系：串行耗时可以相加，并行链路应看关键路径，不能把重叠的等待重复计入总延迟。

OpenTelemetry 当前的 GenAI 语义约定把指令、输入、输出和工具调用内容列为可能敏感的遥测数据，建议默认不采集完整内容，只有明确启用并选定采集范围后再记录；具体 SDK 是否遵循以及配置如何生效仍需核对。语义约定本身不会替应用完成脱敏、权限、保留和删除。[OpenTelemetry GenAI spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)。OpenAI 的 Agent 工作流评估指南说明，一条 trace 可以记录一次运行中的模型调用、工具调用、安全护栏（guardrail）和控制权移交（handoff）；它建议先用 trace 排查工作流，再在成功标准明确后转向固定数据集和重复评估。这是供应商产品指南，不是通用评估方法的独立验证。[OpenAI：Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)

## 1.11 贯穿案例：新索引让旧制度重新进入答案

下面的时间、样本数和回放结果均为教学构造。采购人员发现制度助手的回答仍然流畅，引用也能打开，但其中几条付款规则已过期。团队先暂停扩大灰度，并从用户反馈中挑出 20 个能够确认当前有效制度的固定问题。

### 固定条件

回放时使用相同的问题、模型版本、提示、用户权限、top-k（检索候选数量）、重排配置和引用判定。对比只改变索引快照和版本过滤规则。每个样本都保留候选文档 ID、版本、生效日期、过滤结果和最终引用。

### 观察候选，而不是只读答案

在新索引中，当前制度存在，但部分旧文档分块缺少生效日期。旧过滤规则把空字段当成“无需限制”，因此旧版本进入候选；引用检查只确认链接能打开，没有检查制度是否仍有效。模型看到旧内容后照常生成，表面上像模型知识错误，实际分歧发生在检索过滤和引用校验。

### 对照回放

| 固定条件 | 当前版本引用 | 过期版本引用 | 结论 |
| --- | ---: | ---: | --- |
| 旧索引 + 旧过滤规则 | 20/20 | 0/20 | 固定样本基线 |
| 新索引 + 旧过滤规则 | 14/20 | 6/20 | 过期分块通过了过滤 |
| 新索引 + 严格版本过滤 | 20/20 | 0/20 | 这组固定样本支持过滤缺陷假设 |

这些比例只描述这 20 个教学样本，不是线上错误率。如果一条候选文档缺少版本信息，严格过滤后应进入“无法确认”并停止给出确定结论；不能因为这类样本没有产生过期引用，就把它算作成功。

### 从止损走到恢复

止损时先暂停高风险建议，隔离缺少版本字段的分块，并保留可回滚索引快照。根治时让生效版本成为索引必需字段，缺失时隔离而不是放行；引用校验同时检查链接、版本和 claim 支持关系。回归集覆盖当前版本、旧版本、缺字段、无权限和无支持证据等边界。

若修复后这 20 条固定样本都引用当前制度，另有 4 条边界样本按预期拒答或转人工，这说明修复通过了这些检查；仍不能证明整个知识库无遗漏，也不能替代线上分桶、监控和后续抽查。结果报告应保留样本范围、配置、每类状态和剩余未知。

## 1.12 同一排查方法怎样转到其他领域

跨领域时，保留前面的证据方法，换掉要观察的系统状态。下表只给首要入口；专题机制由对应章节承担。

| 领域 | 先固定什么证据 | 常见误判 | 深入入口 |
| --- | --- | --- | --- |
| 训练稳定性 | 第一次异常 step、原始 batch、参与损失的标签 token 数、梯度、优化器/调度器状态、精度、异常 rank 和 checkpoint（训练检查点） | 看到 loss spike 就直接降学习率 | [第 4 章：训练稳定性](04-训练不稳定排查宝典.md) |
| 分布式训练 | 各 rank（并行进程编号）的 step、数据 token 数、集体通信（collective）顺序、通信时间和恢复状态 | 只看 rank 0 日志 | [第 5 章：分布式训练](05-分布式训练事故宝典.md) |
| 监督微调（supervised fine-tuning，SFT）与对齐 | 训练样本和监督掩码（mask）、偏好对、奖励、版本差异及能力回归切片 | 把奖励分数上升当作用户目标达成 | [第 6 章：SFT 与对齐](06-sft与对齐训练坑.md) |
| 评估 | 数据快照、样本 ID 与过滤原因、评分规则/评估器版本、模型/提示/评测执行环境（harness）版本和分母 | 忽略污染、样本筛选或评分器变化，把分数跳升直接当作能力提升 | [第 7 章：评估指标](07-评估指标陷阱.md) |
| 推理服务 | 请求关键路径、队列、输入/输出长度、输入处理（prefill）、逐 token 生成（decode）、下游等待和长尾 | 用平均延迟或单请求 benchmark 代表用户等待 | [第 8 章：推理部署性能](08-推理部署性能坑.md) |
| RAG | 原始文档、版本与访问控制列表（ACL）、候选、重排、上下文和答案主张/引用关系 | 只读最终答案来判断召回 | [第 9 章：RAG](09-rag落地坑.md) |
| Agent | 计划、授权决定、发送回执、外部状态、幂等键和最终任务验收 | 超时就认为动作失败并盲目重试 | [第 10 章：Agent](10-agent落地坑.md) |
| 多模态 | 原始媒体、转换/裁剪、时间戳或坐标、结构化字段和证据回链 | 把输入未解析误认为模型推理失败 | [第 11 章：多模态](11-多模态项目坑.md) |
| 安全治理 | 主体、资源、动作、授权、数据用途、审计记录和外部传输 | 没有安全日志就当作没有安全事件 | [第 12 章：安全与合规](12-安全与合规坑.md) |

遇到 Agent 工具发送后超时，关键状态是“外部副作用可能已经发生，但本地回执未知”。先按幂等键或外部请求 ID 查询状态，再决定是否重试或转交人工；不要把未知状态改写为失败。Agent 执行的完整权限和恢复机制见第 10、12 章。

## 1.13 把应急、修复和防复发分开

事故处理中常见的混乱，是把“暂时安全了”误报成“根因已修”。三种动作的目标不同：

| 动作 | 目标 | 例子 | 尚不能证明什么 |
| --- | --- | --- | --- |
| 止损 | 限制当前影响 | 暂停高风险建议、切回已知索引、降低灰度 | 根因已解决 |
| 根治 | 移除已验证的故障机制 | 修复缺失版本字段的默认处理 | 任何相似问题永不发生 |
| 防复发 | 让问题更容易被发现或阻止 | 加入边界回归、缺字段告警和回滚演练 | 当前所有数据均正确 |

回滚不是万能修复：切回旧索引可能丢掉新制度，回滚模型也不能撤销已执行的付款或消息。应急记录要说明受影响对象、已发生的外部动作、当前状态和恢复条件。复杂的事件指挥和正式事故报告留到[第 14 章：实验复盘与事故报告](14-实验复盘与事故报告.md)。

## 1.14 回归要重现真实失败

只运行一条正常样本，无法说明刚修复的故障已经覆盖。回归至少要包含：

- 原始失败样本，确认已知问题不再出现；
- 相邻正常样本，确认修复没有过度收缩能力；
- 边界样本，例如缺少版本、权限服务超时、长输入和外部状态未知；
- 反例样本，例如旧制度、无支持证据、重复提交或未授权资源；
- 任务级验收，确认局部引用或工具指标改善后，最终用户任务也正确。

每条结果要绑定代码、模型、数据、索引、策略和评估器版本。Agent 还要断言模拟环境中的外部状态；服务性能要按代表性并发和输入分布测试；多模态应保留原始媒体与预处理产物的关联。样本为空或缺少判定规则时，评估没有结果，不是“全部通过”。

Google SRE 的事故材料把事件的影响、采取的动作、原因和后续措施作为复盘的重要内容；正式报告还要服务于系统改进，而不是只证明某位工程师执行过检查。[Google SRE：Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)。本书第 14 章进一步处理怎样形成完整、可关闭的实验和事故记录。

## 1.15 留下一份能继续工作的排查记录

排障记录无需堆满仪表盘截图，但要让下一位工程师能从现场继续：

```text
任务契约：系统原本承诺什么
事件范围：影响时间、任务、用户/权限和可核实后果
时间线：事实、来源和处置动作
固定条件：输入、版本、配置和运行环境
假设与证据：每条假设支持、反证或未知的依据
第一处分歧：链路中最早偏离预期的位置
止损与修复：已限制的影响、实际变更和回滚条件
验证结果：原始失败、相邻正常、边界和任务级样本
剩余未知：还不能回答什么，为什么
下一步：负责人、截止时间和完成证明
```

“加强监控”不是可验收动作。写成“trace 保存索引快照和文档生效版本，缺失时隔离候选，并在固定回归集覆盖缺字段样本”后，团队才知道完成条件是什么。第 14 章讲报告与行动项，第 15 章讲怎样把证据和工程取舍表达给不同角色。

## 1.16 几种常见捷径为什么会误导

- **只换模型：** 若错误上下文、权限或服务超时仍在，新模型可能只是把错误说得更流畅。
- **只看平均数或最后输出：** 它们掩盖租户、任务和长尾差异，也看不见最终答案之前的候选与状态迁移。
- **把没有日志当作没有问题：** 缺少观测只能记为未知；还要补齐观测，才能评估风险。
- **一次改多个变量：** 结果恢复后仍无法识别真正起效的条件，无法判断能否推广到下一批流量。
- **把回滚或清单当成根因分析：** 回滚只能止损；勾选“看过 trace”也不能代替说明它支持或否定了哪条假设。

排障清单只有在对应某条假设、并保留实际观察时才有用。若它只记录“已检查”，就还不是证据。

## 1.17 资料与证据边界

本章借用可靠性工程和公开工具文档中的方法时，保留它们各自的适用范围：

- [Google SRE：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)、[Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)、[Managing Incidents](https://sre.google/sre-book/managing-incidents/) 和 [Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)支持监控、排障、事件管理和复盘的工程方法；这些材料不是大模型任务质量或权限安全的专门评测标准。
- [OpenAI Production best practices](https://developers.openai.com/api/docs/guides/production-best-practices)、[Agent tracing](https://developers.openai.com/api/docs/guides/agents-api/tracing) 和 [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)描述供应商公开的 API 与工作流入口。文档会随平台更新；接口能力不证明目标系统配置正确，也不替代业务验收。
- [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)提供遥测字段与 span 的约定参考。语义约定和 SDK 的版本、支持程度可能变化；采集内容仍需按应用的敏感数据、访问权限和保留政策核对。
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)是自愿采用的风险管理框架，不是法律意见或产品合规认证。NIST 页面截至 2026-11-16 标注 AI RMF 1.0 正在修订，未来使用时应重新核验状态。

模型分数、最大上下文、吞吐、成本和“更可靠”等结论，都应绑定模型、提示、数据、硬件、权限、harness、评测方法和时间。发布材料或官方说明能支持它们实际披露的范围，不能代替目标环境的回放和验证。各领域后续更新见本书对应章节。

## 1.18 本章小结

实战排障不是凭经验猜一个答案，而是让经验帮助团队更快地产生可验证证据。先写清任务契约和影响范围，再用时间线和可证伪假设缩小问题；固定输入、版本和环境，通过最小复现、baseline 和反事实对照隔离变量；修复后覆盖原始失败、邻近正常和关键边界，并把剩余未知交接清楚。

训练 loss、RAG 引用、Serving 延迟、Agent 工具状态和多模态输入属于不同领域，却都可以追问同一条链：输入是什么，系统在什么身份和版本下作了什么决定，中间状态发生了什么，外部结果是否满足任务契约。后面的领域章节会分别讲清这些链路的技术细节。
