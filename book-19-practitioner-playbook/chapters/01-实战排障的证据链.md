# 第一章：实战排障的证据链

大模型系统的故障很少以“某个函数明显写错了”的形式出现。更常见的情况是，用户只看到一句回答变差、一次请求变慢、一个任务没有完成，后台却同时存在数据版本、模型版本、检索结果、工具状态、权限策略和流量变化。工程师如果直接换模型、加数据或修改提示词，往往只是改变了现象，没有找到原因。

真正的实战能力，是把模糊的异常转换成可以验证的命题：什么现象发生了，影响了哪些任务，何时开始，在哪些条件下可以复现，哪一条证据支持或否定哪一个假设，修复之后怎样证明没有引入新的问题。这个过程既需要对模型、训练和推理有足够理解，也需要像可靠性工程一样尊重时间线、版本、范围、回滚和责任边界。

本章用一个企业知识助手作为贯穿案例。系统为采购人员回答制度和合同问题，回答需要引用当前生效的文档；在低风险场景下可以生成工单草稿，但不直接执行付款或合同变更。后文还会把同一套方法迁移到训练、评估、推理、RAG、Agent 和多模态系统。读者不需要先记住一长串清单，只需要跟着故障从现象走到证据、从证据走到修复，再观察哪些步骤可以沉淀成自动化。

## 1.1 先区分现象、故障和根因

“模型回答差”是现象，不是根因。“RAG 召回错了”通常也还不是根因，因为召回错可能由文档解析、版本过滤、权限策略、查询改写、索引延迟或重排器共同造成。排障的第一步，是把几个经常混用的词拆开。

**现象**是用户或监控直接观察到的表现，例如回答缺少引用、P99 延迟升高、训练 loss 变成非有限值。现象可以被记录，但通常不能直接指导修复。

**故障**是系统没有满足某项已定义的服务或任务要求。例如合同问答在有权限且存在支持文档时没有返回可访问引用，或者 Agent 在外部系统状态未知时重复提交了同一张工单。故障必须绑定适用条件，否则“没有引用”在创作任务中可能不是问题，在制度问答中却是关键问题。

**触发因素**是让系统进入异常状态的变化，例如索引切换、依赖升级、流量突增或新数据批次上线。触发因素未必是最深层原因。

**放大因素**是让小问题扩散或变得更难恢复的条件，例如没有超时、没有回滚快照、缓存没有带权限版本、日志被采样掉，或者错误重试把下游服务压垮。

**根因**是修复后能够解释现象、并且在反事实实验中得到支持的机制。只有“我们改了某处后指标恢复”还不够；如果同时改了五个变量，就很难证明到底是哪一项修复有效。

可以把一次事件写成：

```math

\mathcal{I}=(o, f, g, t, v, e, h, a)

```

其中 `o` 是观察到的现象，`f` 是受影响的任务集合，`g` 是适用条件，`t` 是时间线，`v` 是涉及的版本，`e` 是证据集合，`h` 是假设集合，`a` 是已经采取的动作。一个完整的排障记录不能只有 `o` 和 `a`，否则团队只知道“发生了什么”和“改了什么”，不知道为什么这样改，也无法判断下一次是否会复发。

以“制度问答引用不可信”为例，至少要继续追问：

1. 是所有问题都没有引用，还是只有涉及新版制度的问题没有引用？
2. 是模型没有引用，还是检索结果本身就没有当前文档？
3. 用户是否有权访问被引用的文档？
4. 问题在索引版本切换前是否已经存在？
5. 没有引用时系统是否仍然给出了确定性结论？
6. 影响的是回答正确性、用户信任，还是已经造成业务决策错误？

问题被这样拆开以后，“换一个更强模型”只是众多待验证假设中的一个，不再是默认答案。

## 1.2 从任务契约开始确定故障边界

没有任务契约，就没有稳定的“成功”定义。一个用户说“答案不对”，可能是在抱怨事实错误、引用位置不便、表达太长、权限被拒，或者产品没有告诉他下一步该做什么。工程师必须先知道这项任务本来承诺了什么。

合同与采购助手的只读问答任务可以写成如下契约：

```text
输入：用户问题、租户、用户身份和当前知识库快照
前置条件：问题属于制度或合同知识范围，用户身份可解析
必要证据：有权限、当前生效、能够支持结论的文档片段
输出：事实、证据位置、不确定项和下一步建议
禁止行为：编造没有证据的条款，不泄露无权限文档，不执行外部副作用
成功条件：事实正确、引用可访问、版本有效、状态可解释
未知条件：权限服务超时、索引版本不明、引用检查未完成
```

同一个系统的工单草稿任务契约则不同：允许输出结构化字段，要求字段能够回链到输入或证据；“创建草稿”可以由系统完成，但“提交付款”属于另一个高风险任务，需要人工确认和幂等保护。把多个任务混成一个成功率，会掩盖真正的失败。

任务成功可以抽象为一组适用条件的合取：

```math

S(q)=\prod_{j\in J_q} I_j(q)

```

`J_q` 是问题 `q` 的适用验收条件集合，`I_j(q)` 取 0 或 1。例如只读制度问答可能包含“事实正确”“引用可访问”“版本有效”；不涉及外部动作时，“动作提交成功”不属于 `J_q`，应记录为 `not_applicable`，不能人为加上一个满分项。若某个必要条件没有任何观测，`S(q)` 不是 0 或 1，而是 `unknown`，因为系统还没有足够证据判断它。

这一区分会直接影响排障方向：事实正确但引用检查没有执行，不应马上把模型判为失败；事实正确、引用存在但指向过期版本，则是版本治理问题；引用存在且权限正确、用户仍不满意，则需要继续看任务定义和交互设计。

## 1.3 记录影响范围，而不是只记录一个总平均

故障的边界往往比故障的平均值更有信息。一个模型总体准确率下降 1 个百分点，可能意味着所有用户轻微变差，也可能意味着一个关键租户的高风险任务全部失败。这两种情况的处理优先级完全不同。

最开始至少要记录以下维度：

| 维度 | 需要回答的问题 | 典型证据 |
| --- | --- | --- |
| 时间 | 何时开始，是否与发布或数据切换重合 | release、索引、配置和流量时间线 |
| 任务 | 哪些任务失败，哪些任务仍正常 | 任务类型、状态和验收结果 |
| 用户 | 哪些租户、角色或地区受影响 | 租户、权限和地域切片 |
| 输入 | 哪种长度、语言、文件格式或领域更容易失败 | 输入元数据和样本分桶 |
| 版本 | 模型、提示、检索、工具和策略分别是什么版本 | trace 和 release manifest |
| 频率 | 偶发、集中爆发还是持续发生 | 请求级事件与时间序列 |
| 后果 | 是体验下降、人工返工、数据泄露还是外部副作用 | 业务记录和安全事件 |

一个简单的影响量可以表示为：

```math

I_{\mathrm{impact}}=N_{\mathrm{affected}}\cdot w_{\mathrm{task}}\cdot w_{\mathrm{risk}}

```

`N_affected` 是在同一观察窗口内、满足同一任务定义的受影响任务数；`w_task` 和 `w_risk` 必须事先定义且为非负数。这个量不是法律意义上的损失估算，也不能替代业务负责人判断，它只是帮助团队把“很多用户觉得不好”转成可比较的排查对象。

没有合法的受影响任务计数时，不应把 `N_affected` 写成 0。可能是没有任务，也可能是日志没有记录。前者可以是 `not_applicable`，后者只能是 `unknown`。系统没有观测能力时，低数字并不代表低风险。

## 1.4 用时间线限制猜测空间

时间线是排障中最便宜、却经常被忽略的证据。它能把“可能是模型变差”改写成“索引切换后 17 分钟内，带有旧版本文档的问题开始失败”。后者已经给出了可操作的实验方向。

一条有用的时间线至少包括：

```text
09:00  发布检索服务 v2.4，仍使用旧索引快照
09:12  切换到新索引，文档版本过滤策略更新
09:18  第一条“新采购制度”负反馈出现
09:35  受影响租户比例超过历史基线
09:42  暂停扩大灰度，保留旧索引快照
09:50  回放同一问题，发现 top-k 中出现已失效制度
10:10  修复版本过滤并重建受影响分区
10:40  固定回归集通过，恢复小流量观察
```

时间线中要把事实和推测分开。`09:12 切换索引` 是事实；“索引切换导致故障”在回放和反事实实验完成前仍是待验证假设。记录者可以在每个时间点标注证据来源，例如发布系统、监控、用户反馈、trace 或人工复核，避免事后用记忆填补空白。

如果开始时间不清楚，先寻找最早失败样本和最后成功样本。二分时间窗口通常比阅读所有日志更快；如果失败与某个发布、数据快照或配置变更稳定重合，优先构造旧版本和新版本的固定输入对照。

## 1.5 建立假设树，而不是列一堆可能性

“可能是数据、可能是模型、可能是 prompt、可能是部署”看似全面，实际上没有告诉团队下一步做什么。好的假设树需要把每个假设连接到可观测证据和反事实实验。

以 RAG 回答缺少当前制度引用为例，可以先分成四层：

```text
答案不可信
├── 证据层
│   ├── 当前文档没有进入候选
│   ├── 候选被权限或版本过滤掉
│   └── 引用 ID 与文本片段错配
├── 生成层
│   ├── 证据存在但模型没有使用
│   ├── 输出格式丢失引用字段
│   └── 无证据时仍生成确定结论
├── 任务层
│   ├── 用户问题超出知识库范围
│   └── 评价标准要求了系统没有承诺的能力
└── 运行层
    ├── 索引或权限服务超时
    ├── 缓存命中了旧结果
    └── 版本清单缺失，无法复现
```

每个叶子节点都要有一个“如果它为真，我应该看到什么”的陈述。例如“当前文档没有进入候选”意味着原始检索结果中没有对应文档，而不是只看最终回答；“模型没有使用证据”意味着支持片段已进入上下文，但答案 claim 无法从片段推出；“缓存命中旧结果”意味着相同问题在缓存失效或绑定索引版本后表现不同。

假设可以按信息增益排序。一个低成本、能够一次排除多条分支的检查，通常比立即训练模型更有价值。读取原始 top-k 和版本元数据，可能同时验证解析、索引、过滤和缓存四个假设；单独换模型通常只改变生成层，无法解释证据为什么不存在。

## 1.6 证据有层级，也有适用范围

不同证据的可靠性和解释范围不同。用户说“最近经常错”是重要线索，但不能替代请求级样本；平均延迟图能发现回归，却不能单独解释某次卡顿；模型卡能说明公开能力和限制，不能证明目标系统在当前配置下通过。

可以按从具体到抽象的顺序收集证据：

1. 原始输入和用户期望结果。
2. 预处理后的文本、图像、音频或结构化字段。
3. 模型、提示、检索、工具和策略的版本。
4. 请求级 trace、候选文档、工具参数和返回状态。
5. 聚合指标、切片指标和历史基线。
6. 用户反馈、人工复核和业务后果。
7. 论文、官方文档或模型卡提供的通用背景。

越靠近具体请求的证据，越能回答“这一次发生了什么”；越抽象的资料，越适合说明机制和可能性。不能用一篇论文中的平均结果，替代一次目标系统的失败 trace；也不能因为官方文档声称某个接口支持结构化输出，就推断自己的调用一定满足业务 schema。

为了度量排查是否停留在猜测阶段，可以定义证据覆盖分数：

```math

E_j=\sum_{k\in K}w_k I_{jk}

```

`K` 是当前问题需要的证据类别，`I_{jk}` 表示第 `j` 个问题是否已经获得第 `k` 类证据，取 0 或 1；`w_k` 是非负权重。若 `K` 为空，`E_j` 没有定义；若权重总和为 0，不能把分数默认为满分。实际使用时还应记录“缺了哪一类证据”，因为两个同样的 `0.6` 可能分别代表缺输入样本或缺线上 trace，修复动作不同。

## 1.7 先验证边界，再选择工具和实验

排障不等于把所有日志、所有模型和所有数据一次性放到一个脚本里。实验的目标是区分假设，工具的目标是提供证据。每做一个实验，都应该写下四项内容：

```text
问题：当前要解释的现象是什么？
假设：如果 H 为真，哪个可观测量会改变？
实验：只改变哪个变量，使用什么固定输入和环境？
判定：什么结果支持 H，什么结果否定 H，什么结果仍然未知？
```

例如要验证“新版索引的版本过滤导致召回错误”：

- 固定 100 条带有已知支持文档和生效日期的问题；
- 使用旧索引、新索引和关闭版本过滤的三个条件；
- 分别记录候选文档 ID、版本、权限和最终引用；
- 如果只有新索引且开启版本过滤时失败，假设得到支持；
- 如果三个条件都失败，应回到解析、标注或任务定义，而不是继续修改过滤器。

这个实验比“换 embedding 再跑一遍”更有信息量，因为它直接隔离了索引快照和过滤策略。

## 1.8 最小复现：把系统压缩到仍然失败

最小复现不是把输入改得越小越好，而是在不改变故障机制的前提下去掉无关复杂度。一个可用的压缩顺序是：

1. 从完整事件中选择一条有明确失败结果的样本。
2. 保存原始输入，不只保存清洗后的文本。
3. 固定模型、提示、索引、工具、策略和依赖版本。
4. 关闭与问题无关的并发、重试、缓存或外部动作。
5. 删除不影响失败的字段、历史消息和候选文档。
6. 在旧版本、新版本和基线之间回放同一输入。
7. 逐步恢复真实流量条件，确认哪一个变量重新触发故障。

对于随机生成模型，“一次失败”不能证明问题稳定。可以把复现率写成：

```math

R_{\mathrm{repro}}=
\begin{cases}
N_{\mathrm{same\ failure}}/N_{\mathrm{attempts}},&N_{\mathrm{attempts}}>0\\
\text{undefined},&N_{\mathrm{attempts}}=0
\end{cases}
```

分子和分母必须使用同一输入、同一版本和同一失败判定。若输入、版本或判定标准发生变化，得到的不是复现率，而是混合实验结果。低复现率也不能自动说明问题不存在，可能是竞争条件、流量相关状态、外部服务或未记录的随机种子造成的。

最小复现还要保护数据和权限。复制生产合同到个人环境、把用户凭据放进调试脚本或把完整 trace 发到公共渠道，可能让排障本身变成新的安全事故。生产样本应脱敏、最小化，并保留能够影响失败机制的字段。

## 1.9 Baseline 和反事实比直觉更有说服力

Baseline 不是为了证明新方案一定赢，而是回答“复杂方案带来的增益是否超过复杂度”。对一个 RAG 或 Agent 系统，baseline 可以逐级增加：

```text
规则或关键词检索
  -> BM25 或其他稀疏检索
  -> embedding 检索
  -> 混合检索
  -> 加重排
  -> 加引用校验和拒答
  -> 加工具、状态和人工确认
```

每增加一层，都应在同一评估集、同一权限条件和同一资源预算下比较质量、延迟、成本和风险。否则“加了 reranker 后效果变好”可能只是因为同时更换了文档切分或扩大了上下文。

反事实实验关注的是“如果没有这个变化，结果会怎样”。例如一个新模型发布后线上质量下降，可以把固定请求同时送入旧模型和新模型，并固定 prompt、检索结果、工具返回和解码参数。若两者都失败，模型可能不是根因；若只有新模型失败，再继续看模型输入格式和版本配置。

对比结果最好保留绝对值和差值：

```math

\Delta M=M_{\mathrm{candidate}}-M_{\mathrm{baseline}}
```

如果任务样本、分母或切片不一致，`\Delta M` 没有可比意义。质量提升也要与延迟、成本和风险一起报告；一个答案准确率只提高一点、却把单位有效任务成本提高数倍的方案，可能不适合当前业务。

## 1.10 从请求链路读取证据

一个完整的请求 trace 应让工程师回答五个问题：系统收到了什么，决定做什么，实际调用了什么，得到了什么，最后为什么返回这个状态。

对于合同问答，建议至少记录以下结构化字段：

```text
request_id
task_id
tenant_id_hash
actor_role
model_version
prompt_version
retriever_version
index_snapshot
policy_version
input_hash
candidate_document_ids
candidate_versions
filtered_document_ids
claim_ids
tool_events
final_status
latency_breakdown
cost_breakdown
```

日志中不应默认保存完整敏感正文。可以使用内容哈希、短期受控引用、脱敏字段和受权限保护的原文存储。最小化记录并不意味着丢掉调试能力，而是把“谁能在什么情况下查看原文”设计成明确的审计流程。

延迟排查必须拆分阶段。总延迟可以写成：

```math

T_{\mathrm{total}}=T_{\mathrm{queue}}+T_{\mathrm{prefill}}+T_{\mathrm{decode}}+T_{\mathrm{retrieval}}+T_{\mathrm{tool}}+T_{\mathrm{postprocess}}
```

这个分解只在各项时间边界不重叠时成立；如果检索与模型调用并行，就不能简单相加，需要记录关键路径。平均值、P50、P95 和 P99 也不能互换。没有完成请求的延迟记录时，分位数是 `unknown`，不是 0 毫秒。

质量 trace 也要区分“模型输出了引用字段”和“引用实际支持 claim”。前者是协议检查，后者是证据检查；把字段存在率当成引用准确率，会让系统在最需要可信度的场景产生虚假通过。

## 1.11 贯穿案例：一次 RAG 引用事故

### 1.11.1 用户看到的现象

采购团队反馈：合同助手最近经常引用已经失效的付款制度。回答措辞流畅，引用链接也能打开，但法务人员发现引用的版本早于当前生效版本。监控中的总体任务成功率只下降了几个百分点，平均延迟没有变化，因此最初没有触发系统级告警。

这条反馈至少包含三个不同问题：答案事实是否错误，引用是否指向有效证据，系统是否把旧制度用于建议动作。不能把它们合并为一个“RAG 质量下降”。

### 1.11.2 先固定样本和版本

工程师从反馈中抽取 20 个问题，保存用户角色、问题文本、期望制度版本、原始文档 ID 和最终回答。回放时固定：

- 同一个模型版本和提示版本；
- 同一个索引快照；
- 同一个权限身份；
- 同一个检索 top-k 和重排配置；
- 同一个引用校验逻辑。

这样可以先回答“线上结果是否可以离线重现”。如果离线回放与线上不一致，优先检查版本清单、缓存、流量路由和动态数据，而不是先调模型。

### 1.11.3 读取候选文档而不是只读答案

回放 trace 后发现，当前制度文档确实存在于新索引，但 top-k 中同时出现了旧版本和新版本。一个版本过滤字段在索引切换后没有被写入部分分块；过滤器把缺失字段当成“没有限制”，旧文档因此进入候选。模型看到旧文档后选择了内容更完整的片段，生成层没有能力判断版本元数据缺失。

这个根因链条是：

```text
索引切换
  -> 部分分块缺少生效时间
  -> 过滤器对缺失字段采用宽松默认值
  -> 旧版本进入候选
  -> 模型使用旧版本完整段落
  -> 引用校验只检查链接可访问，不检查有效版本
  -> 用户得到看似有据、实际过期的答案
```

其中模型生成只是最后一环。即使换成更强的模型，如果输入上下文仍混有旧版本且没有明确版本约束，也不能保证正确。

### 1.11.4 修复要分为止损和根治

短期止损可以暂停相关自动建议，保留只读检索；对版本字段缺失的文档不再进入高风险任务上下文；将受影响索引切回已知完整的快照；在用户界面明确展示“版本无法确认”。这些动作减少继续扩大的影响，但不等于根因已经修好。

长期修复包括：

1. 把文档版本和生效时间设为分块写入的必需字段。
2. 对缺失元数据的记录采取阻断或隔离，而不是宽松放行。
3. 在候选、生成和引用三个阶段都检查有效版本。
4. 将索引快照绑定到 release manifest 和 trace。
5. 增加旧版本、新版本、版本缺失和跨段引用的回归样本。
6. 监控“引用链接可访问但版本无效”的独立指标。

### 1.11.5 用反事实证明修复有效

固定 20 个失败问题后，构造四个条件：旧索引加旧过滤器、新索引加旧过滤器、新索引加严格过滤器、新索引加严格过滤器并开启引用有效性检查。只有第四个条件恢复，才说明完整修复覆盖了候选和引用两处约束；如果第三个条件已经恢复，引用检查可能只是额外保护；如果四个条件都失败，应回到文档解析或问题标注。

这个案例说明一个重要原则：先读证据流，再读生成文本。RAG 失败的第一分歧点经常发生在文档治理、权限、版本和检索，而不是模型输出的最后几行。

## 1.12 训练异常：从 loss 曲线回到第一个坏 batch

训练问题也适用同样的证据链。看到 loss 突然升高时，不能仅凭曲线判断学习率或模型结构。应先找到第一次异常出现的 step，并保存该 step 的 batch、有效 token 数、loss mask、梯度范数、学习率、混合精度状态、rank 和 checkpoint 信息。

设第 `t` 步的有效监督 token 数为 `n_t`，被 mask 的 token 不应进入损失平均。一个常见的 token 平均损失是：

```math

L_t=\frac{\sum_{i=1}^{n_t}m_{t,i}\ell_{t,i}}{\sum_{i=1}^{n_t}m_{t,i}}
```

其中 `m_{t,i}` 为 0 或 1。如果分母为 0，损失没有定义，不能用一个人为的小数把它伪装成正常 batch。此时应该记录 `empty_supervision`，检查数据、角色 mask 和 batch 过滤逻辑。

一个由 loss spike 到根因的排查顺序可以是：

1. **batch 内容**：是否出现极长样本、非法 token、空标签、异常数值或损坏图像。
2. **mask 和标签**：是否把 padding、用户问题或错误角色计入监督。
3. **优化状态**：学习率、梯度范数、optimizer state 和 scheduler 是否在该 step 发生变化。
4. **数值状态**：是否出现 Inf/NaN，AMP scaler 是否连续回退，某个算子是否溢出。
5. **分布式状态**：是否只有一个 rank 先异常，collective 是否阻塞或参数不同步。
6. **恢复状态**：从最近 checkpoint 重启后，异常是否在同一数据位置再次出现。

若固定坏 batch 单独前向就出现非有限损失，问题更接近数据或 mask；若单独前向正常、只有大 batch 或混合精度下异常，才应进一步研究数值范围、通信和优化器状态。把所有变量一起改成小学习率、关闭 AMP、换数据和减少 batch，虽然可能让训练恢复，却无法说明根因。

## 1.13 评估异常：分数跳升也可能是事故

评估分数大幅上升通常令人高兴，但工程师应先问它是否可信。常见原因包括测试集被训练数据污染、评估模板改变、参考答案泄露、评分器版本更新、样本过滤条件变化或 harness 使用了额外工具。

评估记录至少要绑定：数据快照、样本数量、切片定义、提示模板、模型版本、解码参数、工具权限、评分器版本和失败样例。两个分数只有在这些条件足够一致时才适合直接比较。

若某个指标在 `N` 条合格样本上统计，通过数量为 `K`，且 `N>0`，则：

```math

M=K/N
```

如果样本筛选过程没有留下 `N`，分数就缺少分母证据；如果 `N=0`，不是 0 分，而是没有评估结果。若评估器只给出分数、不提供逐样本判定和版本信息，团队应该把结论标为 `unknown`，而不是用更多小数位制造精确感。

评估分数跳升的最小检查包括：

- 用旧评估器重新运行新模型；
- 用新评估器重新运行旧模型；
- 比较样本 ID 集合和过滤原因；
- 搜索训练数据与评估问题的 exact/near duplicate；
- 抽取分数变化最大的样本进行人工复核；
- 在一个从未参与开发的私有 holdout 上重复比较。

只有当多个独立证据方向一致时，才能把分数跳升解释成能力提升。

## 1.14 Serving 性能异常：先看关键路径和长尾

“接口变慢”同样是一个需要拆解的现象。请求可能慢在排队、prefill、decode、检索、工具、网络或序列化；平均值正常时，P99 仍可能因为少量长上下文、GPU 争用或下游重试而恶化。

对于一个交互式生成请求，若各阶段串行，总延迟可以表示为：

```math

T=T_q+T_p+T_d+T_r+T_t+T_o
```

`T_q` 是排队时间，`T_p` 是输入处理时间，`T_d` 是生成时间，`T_r` 是检索时间，`T_t` 是工具等待时间，`T_o` 是后处理时间。若其中两项并行，实际总延迟取关键路径而非简单求和，因此 trace 必须带开始和结束时间。

排查顺序通常是：

1. 先看 P50、P95、P99 和请求量是否同时变化。
2. 按输入 token、输出 token、任务类型和租户切片。
3. 看排队、prefill、decode、KV cache 命中和下游等待的分解。
4. 对照 batch、并发、GPU 利用率、显存和通信指标。
5. 检查是否有重试、工具循环、缓存失效或索引服务退化。
6. 用固定短请求和固定长请求分别回放，确定问题是否与序列长度相关。

如果只有长输入 P99 变差，不应简单把所有请求降级到更小模型；可能需要上下文压缩、检索去重、KV cache 策略或容量配置调整。如果只有高并发时变差，要看队列和批处理，而不是用单请求 benchmark 证明服务没有问题。

## 1.15 Agent 异常：外部状态未知时不要盲目重试

Agent 故障的危险在于它不只是生成错误文本，还可能产生真实副作用。调用工单、付款、库存或账户系统时，网络超时并不等于动作没有发生。若系统没有收到响应就再次提交，可能形成重复工单或重复扣款。

一次工具调用至少应经历：

```text
planned -> authorized -> sent -> acknowledged
                         ├-> rejected
                         ├-> failed_before_commit
                         └-> unknown_after_send
```

`unknown_after_send` 表示请求已经可能到达外部系统，但本地没有足够证据判断最终状态。此时下一步应使用幂等键查询外部状态，或交给人工确认；不能直接把它改写成 `failed` 后重试写操作。

工具执行记录应包含动作参数摘要、授权策略版本、幂等键、发送时间、外部请求 ID、响应状态和查询结果。重试只对确认没有副作用、或外部系统明确支持幂等的操作开放。高风险动作还需要在发送前后重新检查身份、金额、目标对象和当前业务状态。

Agent 任务的成功率也必须绑定适用任务集合：

```math

R_{\mathrm{task}}=
\begin{cases}
N_{\mathrm{correct\ terminal\ tasks}}/N_{\mathrm{eligible\ tasks}},&N_{\mathrm{eligible\ tasks}}>0\\
\text{undefined},&N_{\mathrm{eligible\ tasks}}=0
\end{cases}
```

“模型调用成功”“工具返回 200”和“用户任务完成”是三个不同指标。工具返回 200 但填写字段错误，仍然是任务失败；外部状态未知时不能把结果放入成功或失败的普通分母，应该单独统计未知状态并修复状态查询能力。

## 1.16 多模态异常：先确认输入是否可处理

图像、音频、视频和文档的错误经常被误判为模型能力问题。低分辨率、旋转、反光、遮挡、噪声、采样率不匹配、扫描版 PDF、复杂表格布局和视频抽帧不足，都可能让模型接收到与人类看到的内容不同的信息。

多模态排障需要保存输入质量和预处理结果：

- 图像的分辨率、方向、色彩和裁剪区域；
- OCR 的文本、版面框和字段置信度；
- 音频的采样率、声道、时长、静音和噪声比例；
- 视频的帧率、抽帧策略、时间窗口和音频轨道；
- 文档的页数、解析器版本、表格结构和缺失页。

如果输入质量不满足任务条件，系统应该请求重新上传、补充信息或转人工，而不是生成一个看似完整的答案。对于医疗、财务和身份材料，输入不足与模型判断错误的风险不同，日志和用户提示也应区分。

多模态质量指标必须按任务定义。例如 OCR 字符错误率在参考文本长度为 0 时没有定义；如果没有参考文本，不能把“没有错误”当成 1。图像生成的用户采纳率、图像问答的事实支持率和视频的时序一致性也不应被压成一个无解释的总分。

## 1.17 把修复分成止损、根治和防复发

事故处理常见的混乱，是把临时止损和永久修复混为一谈。止损的目标是降低当前影响，根治的目标是消除触发机制，防复发的目标是让下一次更快发现或更难发生。

| 类型 | 目标 | 例子 | 不能证明什么 |
| --- | --- | --- | --- |
| 止损 | 立刻限制影响 | 暂停高风险动作、切回旧索引、降低灰度 | 根因已经解决 |
| 根治 | 修复触发机制 | 补齐版本字段、修正 mask、修复状态查询 | 永远不会复发 |
| 防复发 | 增加检测和回归 | 固定失败样本、补监控、演练回滚 | 当前版本一定正确 |

回滚也不是万能动作。回滚模型可能恢复质量，却无法撤销已经发生的外部动作；切回旧索引可能恢复引用，却可能丢失新文档；关闭 Agent 工具可以止损，却会改变用户任务完成路径。因此回滚记录要说明范围、数据状态、外部副作用和恢复条件。

如果需要按优先级排序，可以定义一个教学性的排查优先级：

```math

P_j=\frac{S_j\cdot F_j\cdot U_j}{C_j}
```

要求严重度 `S_j`、发生频率 `F_j`、影响范围 `U_j` 为非负数，修复成本 `C_j>0`。各量必须在同一项目内采用稳定尺度；如果成本未知，优先级是 `unknown`，不能把未知成本当成 0 以制造无穷大。低频但不可逆的安全事件也不应仅靠这个排序决定处理顺序，组织的安全和合规政策可以直接提高其优先级。

## 1.18 让回归测试复现真实失败

把事故修好后只运行一条“正常样例”，几乎不能证明系统恢复。回归集应同时包含：

1. 原始失败样本，保证已知故障不再出现。
2. 相邻正常样本，防止修复过度收缩能力。
3. 边界样本，例如空输入、长输入、权限缺失、版本缺失和超时。
4. 反例样本，例如旧版本制度、无支持证据、重复工具提交。
5. 任务级样本，确认局部指标改善确实转化为最终任务完成。

测试结果要绑定代码、数据、模型、索引、策略和评估器版本。对于 Agent，还要记录外部系统的模拟状态和副作用断言；对于 Serving，要在目标并发和输入长度分布下测试长尾；对于多模态，要保留预处理和原始输入的关联。

回归通过率只有在测试集合非空且每条测试有明确判定时才有意义：

```math

R_{\mathrm{reg}}=
\begin{cases}
N_{\mathrm{passed}}/N_{\mathrm{tests}},&N_{\mathrm{tests}}>0\\
\text{undefined},&N_{\mathrm{tests}}=0
\end{cases}
```

没有测试不代表全部通过。测试不适用于某个任务时，应在测试计划中明确标记 `not_applicable`，而不是从分母中悄悄删除造成选择偏差。

## 1.19 复盘不是总结，而是可执行的工程资产

复盘报告的价值不在于把事故叙述得完整，而在于让下一位工程师可以更快识别同类故障。报告至少应有：

```text
事件摘要：一句话说明故障和影响
任务契约：本来承诺了什么
影响范围：时间、租户、任务、数据和业务后果
时间线：事实、证据来源和处理动作
第一处分歧：哪一步最早偏离预期
根因：触发因素、放大因素和证据
止损：立即限制了什么影响
修复：代码、数据、配置和流程变化
验证：回归、反事实、灰度和监控结果
剩余未知：还没有证据回答什么
后续动作：负责人、截止时间和完成证明
```

“第一处分歧”比“最后看到的错误输出”更重要。若检索候选在第一步已经错误，后面的模型编造和引用错误是放大表现；如果工具状态在发送后变成未知，后面的重复提交是恢复逻辑问题。责任归因应围绕系统和流程，不把一次复杂故障简化成某个人“粗心”。

复盘动作必须可以验证。例如“加强监控”不是完成条件；更具体的动作是“在 trace 中记录索引快照和文档生效时间，并为版本缺失增加独立告警，回归集覆盖四种版本边界”。只有这样，复盘才会从文字变成系统能力。

## 1.20 一个可运行的事故审计示例

下面的示例使用 Python 标准库，模拟四条事故记录。它不替代真实监控平台，也不把教学阈值当成通用标准；示例的重点是三件事：非法计数必须被拒绝，零分母必须保留为未定义，缺少证据不能被误判为已经解决。

```python
from dataclasses import dataclass
from math import isfinite
from typing import Dict, List, Optional, Tuple


def is_strict_int(value: object) -> bool:
    return type(value) is int


def require_non_negative_int(name: str, value: object) -> None:
    if not is_strict_int(value) or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")


def require_finite_non_negative(name: str, value: object) -> None:
    if type(value) not in (int, float) or not isfinite(float(value)):
        raise ValueError(f"{name} must be finite")
    if float(value) < 0:
        raise ValueError(f"{name} must be non-negative")


def safe_rate(numerator: int, denominator: int) -> Optional[float]:
    require_non_negative_int("numerator", numerator)
    require_non_negative_int("denominator", denominator)
    if numerator > denominator:
        raise ValueError("numerator cannot exceed denominator")
    if denominator == 0:
        return None
    return round(numerator / denominator, 3)


@dataclass(frozen=True)
class Incident:
    incident_id: str
    module: str
    affected_tasks: int
    severity: int
    frequency: float
    evidence: Dict[str, bool]
    reproducible: bool
    root_cause_found: bool
    rollback_ready: bool
    postmortem_fields: int
    fix_cost_days: float


EVIDENCE_WEIGHTS = {
    "input": 0.15,
    "version": 0.15,
    "logs": 0.15,
    "trace": 0.20,
    "baseline": 0.15,
    "regression": 0.20,
}


def validate(item: Incident) -> None:
    if not item.incident_id.strip():
        raise ValueError("incident_id must not be empty")
    if not item.module.strip():
        raise ValueError("module must not be empty")
    require_non_negative_int("affected_tasks", item.affected_tasks)
    require_non_negative_int("severity", item.severity)
    if item.severity > 5:
        raise ValueError("severity must be between 0 and 5")
    require_finite_non_negative("frequency", item.frequency)
    if item.frequency > 1:
        raise ValueError("frequency must be at most 1")
    require_non_negative_int("postmortem_fields", item.postmortem_fields)
    require_finite_non_negative("fix_cost_days", item.fix_cost_days)
    if item.fix_cost_days <= 0:
        raise ValueError("fix_cost_days must be positive")
    for name in ("reproducible", "root_cause_found", "rollback_ready"):
        if type(getattr(item, name)) is not bool:
            raise ValueError(f"{name} must be bool")
    if set(item.evidence) != set(EVIDENCE_WEIGHTS):
        raise ValueError("evidence keys do not match the schema")
    if any(type(value) is not bool for value in item.evidence.values()):
        raise ValueError("evidence values must be bool")

    validate(item)
    return round(
        sum(weight for key, weight in EVIDENCE_WEIGHTS.items() if item.evidence[key]),
        3,
    )


def priority(item: Incident) -> float:
    validate(item)
    impact = item.severity * (1.0 + item.frequency) * (1.0 + item.affected_tasks / 1000.0)
    return round(impact / item.fix_cost_days, 3)

    if missing:

    return "resolved_for_review", []
```

## 1.21 常见但危险的捷径

### 直接换模型

换模型有时是合理的止损措施，但它不能解释数据、权限、格式、检索或服务问题。若问题来自错误的上下文，换模型可能只让错误回答更流畅。

### 只看平均值

平均准确率和平均延迟都可能掩盖关键切片。至少要按任务类型、风险等级、输入长度、租户、版本和失败状态观察分布。

### 只看最后输出

最后输出是链路末端的症状。没有候选文档、工具响应、状态事件和版本信息，无法判断生成错误还是上游输入错误。

### 把缺少日志当成没有问题

没有 trace 只能说明观测缺失。任何“未记录的故障率”都应该是 `unknown`，不能为了绘制图表而填成 0。

### 同时改很多变量

同时换模型、换数据、换提示和换评估器，短期可能看到分数恢复，长期却无法知道哪一项有效，也不能把结果迁移到下一次故障。

### 把回滚当成修复

回滚能限制影响，但旧版本可能仍包含同一缺陷，且不能撤销已发生的外部动作。回滚之后仍要完成根因分析和回归。

### 把清单当成证据

勾选“已检查日志”不等于日志回答了当前假设。每一项证据都应写出观察结果、版本范围和对假设的支持或否定。

### 用更复杂的系统掩盖基本问题

加 Agent、重排、长上下文和更大的模型都可能增加变量。首先保证输入、输出、权限、版本和任务契约正确，再逐层增加复杂度。

## 1.22 资料与证据边界

本章的工程方法参考以下资料，但不同资料解决的问题不同，不能把它们的建议直接当成目标系统的实测结论：

- Google SRE 的 Monitoring、Incident Response 和 Postmortem Culture 章节用于说明可观测指标、事件响应、时间线和无责复盘的基本思路；其中的服务可靠性方法迁移到大模型任务时，还必须补充任务质量、证据、权限和业务副作用。
- OpenAI Production Best Practices 用于说明生产环境中的错误处理、重试、延迟、成本和版本实践；具体 API 字段、价格和模型行为必须以目标版本的官方文档为准。
- OpenAI Evals 和 graders 文档用于说明固定样本、评分器、回归和失败样例的组织方式；评估框架本身不能证明任何应用已经达到业务目标。
- OpenAI Agents tracing 资料用于说明请求、工具调用和运行轨迹的可观测边界；公开 SDK 的 trace 接口不能被解释为模型内部思维过程的完整记录。
- OpenTelemetry 文档用于说明 trace、span、属性和上下文传播等通用可观测性概念；它不自动解决敏感数据脱敏、采样策略或业务事件建模。
- NIST AI Risk Management Framework 用于说明风险识别、度量、治理和持续监控的框架；它不是具体司法辖区的法律意见。
- PyTorch 的 autograd anomaly detection、AMP、DistributedDataParallel 和 checkpoint 文档用于训练故障的机制背景；一个框架接口的存在不等于目标训练作业已经正确使用它。

论文、官方文档、框架建议、供应商产品页和目标系统实测应分开记录。特别是模型的基准分数、最大上下文、吞吐、价格和“更可靠”等宣传性陈述，都必须绑定版本、硬件、提示、工具、评估集和时间。无法由一手资料确认的内部结构或训练配方，应写成公开信息支持的假设，而不是事实。

## 1.23 本章小结

实战排障不是凭经验猜答案，而是把经验变成更快、更安全的证据生产过程。先写清任务契约和影响范围，再沿时间线建立假设；先保存原始输入、版本和 trace，再做最小复现和 baseline；先用反事实实验区分变量，再决定止损、根治和防复发动作；修复之后用失败样本、边界样本和任务级指标回归，最后把剩余未知和后续责任写进复盘。

训练 loss、RAG 引用、Serving 延迟、Agent 工具状态和多模态输入看起来属于不同领域，但它们共享同一条因果链：上游输入是什么，系统依据什么做决定，中间状态发生了什么，最终结果是否满足任务契约。掌握这条链，才能在新模型、新框架和新产品形态出现时继续排障，而不是只会复述某个模型或工具的名字。
