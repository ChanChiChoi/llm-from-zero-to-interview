# 第四章：训练不稳定的定位与恢复

训练不稳定是大模型工程中最昂贵的故障之一。一个小实验中的 loss spike 可能只浪费几分钟，但大规模训练中的异常 batch、非有限梯度、错误的 scheduler 状态或损坏 checkpoint，可能浪费数百张 GPU 数小时，并让团队在几天后才发现模型已经偏离了预期。

训练事故难排查，是因为它通常不是一个单点错误。数据长度分布、label mask、学习率、梯度累积、混合精度、optimizer state、分布式 rank 和 checkpoint 恢复可能同时影响同一条 loss 曲线。看到 NaN 后直接降低学习率，可能暂时让曲线恢复，却没有解释第一个非有限值是怎样产生的；看到 loss 不下降后直接换模型，也可能掩盖 labels 全部被忽略的 collator 错误。

本章把训练过程视为一个可记录的状态机。每个 step 都应该能回答：使用了哪个 batch、真实学习率是多少、有效监督 token 有多少、梯度是否有限、是否发生 overflow、各 rank 是否一致、checkpoint 和恢复状态是什么。排障从第一次异常开始，而不是从日志最后一行开始；修复分为止损、根因修复、恢复验证和防复发回归。

## 4.1 训练运行是一条状态时间线

一个训练 step 不只是一个 loss 数字。可以把第 `t` 步的运行状态写成：

```math

u_t=(L_t,\eta_t,g_t,n_t,o_t,\rho_t,b_t,c_t,r_t)
```

其中：

- `L_t` 是训练损失；
- `eta_t` 是实际生效的学习率；
- `g_t` 是梯度范数；
- `n_t` 是有效 label token 数；
- `o_t` 是 AMP overflow 或 scaler 异常状态；
- `rho_t` 是各 rank 的 loss 集合；
- `b_t` 是 batch 标识和样本摘要；
- `c_t` 是 checkpoint、global step 和 optimizer/scheduler 状态；
- `r_t` 是该 step 的运行版本和资源上下文。

如果只记录 `L_t`，后面几乎所有根因都只能靠猜。一个完整的 step 记录至少要关联数据版本、tokenizer、collator、模型、优化器、scheduler、precision、world size、rank、随机状态和 checkpoint manifest。

训练稳定性不是要求所有数值永远单调下降。loss 可以有正常波动，梯度也会随 batch 难度变化。需要定义的是“什么变化属于预期范围，什么变化需要保存证据并暂停扩大训练”。这个范围必须与任务、模型规模、batch、精度和训练阶段绑定，不能把一个小模型的阈值直接复制给另一套系统。

## 4.2 先找到第一次异常 step

后续的 NaN、Inf、梯度爆炸和 loss 全部失真，往往只是第一次异常的传播结果。排障的第一个问题不是“现在为什么是 NaN”，而是“哪一个 step 第一次偏离了已知正常状态”。

建议在每个 step 或固定间隔记录：

```text
step / global_step
batch_id 和样本 ID 摘要
loss 和有效 label token 数
learning rate 与 scheduler step
gradient norm、parameter norm
AMP scaler 和 overflow
各 rank loss、batch shard 和通信状态
数据、模型、collator、optimizer 版本
最近 checkpoint 和随机状态
```

如果日志采样过稀，第一次异常可能落在两个采样点之间。应在发现异常后提高该时间窗口的日志粒度，或用保存的 batch ID 回放相邻 step。没有 batch ID 的 loss spike 只能说明曲线异常，不能直接开始数据调查。

## 4.3 Loss spike：区分单个 batch 和系统性发散

Loss spike 是损失在短时间内突然高于近期水平。它可能由一个极端 batch 引起，也可能是学习率、精度或状态变化让之后的所有 batch 都变差。

先把现象分成三类：

1. **单点 spike 后恢复**：优先看该 batch 的长度、来源、标签、mask 和异常 token。
2. **spike 后持续上升**：检查学习率、梯度、AMP、optimizer state 和参数是否已经被破坏。
3. **周期性 spike**：检查数据分片、scheduler、梯度累积边界、评估/保存切换和分布式同步。

可以用近期窗口的中位数和离差构造教学性的 spike 分数。设窗口中位数为 `m_t`，窗口的中位绝对偏差为 `d_t`，且 `d_t>0`：

```math

S_t=\frac{L_t-m_t}{d_t}
```

如果窗口为空或 `d_t=0`，这个分数没有定义，应改用绝对阈值、相邻 step 对照或保留“没有足够基线”的状态。不能把一个固定的小数放到分母里掩盖窗口没有波动的事实。

看到 spike 后，先保存对应 batch，再做三组对照：

- 正常 batch 在相同模型状态下前向和反向；
- 异常 batch 在相同模型状态下单独运行；
- 异常 batch 替换为裁剪长度或过滤后的版本。

如果只有异常 batch 触发 spike，根因更接近数据、mask 或长度；如果所有 batch 都在同一步开始变差，根因更接近学习率、精度、optimizer 或分布式状态。

## 4.4 Loss 不下降：先验证训练链路真的在更新

loss 不下降不一定代表模型学不会。常见的链路错误包括：

- 所有 labels 都是 `-100`；
- optimizer 没有拿到可训练参数；
- 梯度没有反传或被过早清零；
- 学习率实际为 0 或 scheduler 已经走到错误位置；
- 数据和 labels 错位；
- 模型处于错误的训练/评估状态；
- 记录的是旧的 loss 或未完成 optimizer step 的 loss。

最小 sanity check 是在几十条固定样本上尝试 overfit。若模型、collator、optimizer 和 loss 链路正确，小数据通常应能显著降低训练误差；如果连一个极小集合都无法拟合，优先检查参数更新、labels、mask 和数据格式，而不是先增加模型容量。

参数是否更新可以用两次状态的差异验证。对参数向量 `theta`，若在有效 optimizer step 后：

```math

\Delta\theta=\|\theta_{t+1}-\theta_t\|_2
```

在学习率非零、存在有效 labels 且梯度应当非零的条件下，持续 `Delta theta=0` 是异常信号。被冻结参数、梯度累积尚未达到更新边界和梯度裁剪为零是不同原因，日志需要记录更新阶段。

## 4.5 NaN/Inf：追溯第一个非有限值

NaN 和 Inf 不是一个可直接修复的根因类别。它们可能来自输入、前向算子、loss 归一化、反向梯度、optimizer state、混合精度或 checkpoint。

排查要按数值传播顺序进行：

1. 输入张量、labels、mask 和长度是否有限、合法。
2. 前向输出和 logits 是否先出现非有限值。
3. loss 分子和有效 token 分母是否有效。
4. 反向后梯度是否先出现非有限值。
5. optimizer step 后参数或 optimizer state 是否变坏。
6. AMP scaler、通信归约或 checkpoint 恢复是否改变了状态。

如果单独前向一个 batch 就有 NaN，优先查数据、mask、除零、log 和 attention mask；如果前向正常、反向异常，查梯度范围和算子；如果 optimizer step 后才异常，查学习率、精度和 optimizer state。

非有限率在 `T>0` 个已记录 step 上可以写成：

```math

R_{\mathrm{nf}}=\frac{N_{\mathrm{nonfinite}}}{T}
```

若 `T=0`，不是稳定率 0，而是没有观测。只要出现第一个必要状态的非有限值，就应保存该 step 及其上下文；后续全部 NaN 不能替代第一处证据。

## 4.6 梯度范数、裁剪和损失归一化

梯度爆炸通常表现为 gradient norm 突然变大，随后 loss spike、overflow 或 NaN。它可能由学习率过高、极端长样本、错误 mask、异常初始化、LoRA 配置或梯度累积错误引起。

全局梯度范数可以写成：

```math

g_t=\sqrt{\sum_{\ell=1}^{K}\|\nabla_{\theta_\ell}L_t\|_2^2}
```

梯度 clipping 能把更新限制在一定范围内，但它不是数据和目标错误的修复。若每个 step 都触发大幅裁剪，说明真实梯度分布已经超出预期，应该检查 loss 归一化、有效 token 数、学习率和 batch，而不是只把 clipping 阈值继续调大。

梯度累积还会引入两个常见错误：一是每个 micro-batch 与完整 global batch 的 loss 归一化不一致，二是达不到累积步数时仍错误地执行 optimizer step。记录每个 micro-batch 的有效 token 数，并明确 loss 是按样本、token 还是 global batch 归一化。

## 4.7 有效 label token 是稳定性指标

SFT 和语言建模的 loss 不是对所有 padding 位置求平均。设 batch 中 labels 为 `y_{j,s}`，忽略值为 `-100`，有效监督 token 数为：

```math

n_t=\sum_{j=1}^{B}\sum_{s=1}^{S}\mathbf{1}[y_{j,s}\ne -100]
```

如果 `n_t=0`，平均损失没有定义；如果 `n_t` 突然比历史水平小很多，常见原因包括：

- assistant-only mask 把所有目标都排除了；
- 截断切掉了答案；
- 空答案或只有控制 token 的样本进入 batch；
- padding、角色或多模态 labels 错位；
- 数据过滤后 batch 仍保留空记录。

有效 token 数还影响不同长度 batch 的 loss 可比性。只比较 batch 平均 loss 而不记录 `n_t`，可能把“监督 token 变少”误认为模型变容易或变稳定。

建议对有效 token 数设置数据级和 step 级检查：空分母直接隔离；低于历史分位数的 batch 保存样本；长短样本混合时分别报告按 token 和按样本的统计。

## 4.8 Learning rate、warmup 和 scheduler 状态

学习率是训练稳定性的核心变量，但配置文件中的目标值不等于每一步真实生效值。梯度累积、warmup、cosine scheduler、resume、跳过 batch 和分布式 global step 都可能改变实际曲线。

训练日志应同时记录 `lr`、scheduler step 和 global step。恢复训练时，把实际学习率与根据同一 scheduler 和 global step 计算出的预期值比较：

```math

D_{\eta,t}=|\eta_t-\hat{\eta}_t|
```

其中 `hat_eta_t` 是在版本、warmup 和 global step 都明确时的预期值。如果 scheduler 配置或总步数未知，`D_eta` 没有可靠定义，应该补齐 manifest。

常见事故包括：

1. resume 后 global step 从 0 重新开始，学习率重新 warmup。
2. optimizer state 恢复了，但 scheduler state 没恢复。
3. 改变 global batch 后仍使用原来的学习率和 warmup 步数。
4. 梯度累积步数变更导致实际更新频率改变。
5. 只保存了配置中的学习率，没有保存每一步实际值。

降学习率可以作为止损实验，但必须在固定数据和其他变量下验证。若学习率恢复后连续、异常 batch 单独正常、只有原训练设置发散，才可以把结论写成学习率或数值范围问题。

## 4.9 混合精度和 overflow

fp16、bf16 和 fp32 的动态范围、舍入和算子实现不同。混合精度能降低显存和提高吞吐，也会让某些前向、反向和 optimizer 状态更容易出现数值问题。

需要观察：

- scaler 的变化和 overflow 次数；
- unscale、gradient clipping 和 optimizer step 的顺序；
- 哪些算子被强制使用更高精度；
- fp16、bf16 和 fp32 的最小复现差异；
- overflow 是否集中在某类长度、数据或 rank。

如果 fp32 稳定、fp16 不稳定，不代表模型或数据一定错误，而是说明数值范围或实现路径需要调整。bf16 在许多硬件上动态范围更宽，但也不保证所有算子、硬件和框架组合都稳定。

overflow rate 在 `T>0` 个 step 上为：

```math

R_{\mathrm{overflow}}=\frac{N_{\mathrm{overflow}}}{T}
```

`R_overflow` 为 0 也不证明没有数值风险，因为未记录的 scaler 或非有限参数仍可能遗漏；`T=0` 则是 `unknown`。

## 4.10 异常 batch：把数据和训练日志连起来

没有 batch ID 的 loss 曲线很难排查。每个 batch 至少需要关联样本 ID 摘要、来源桶、序列长度、有效 label token 数、媒体是否存在、过滤规则版本和数据分片。

异常 batch 的常见特征包括：

- 极长序列或异常长短混合；
- 空答案、全 mask 或角色错位；
- 乱码、非法 token、特殊 token 密集；
- 低质量来源或高风险代码；
- 重复模板集中出现；
- 图像、音频或标注缺失；
- 只在某个 rank 的 shard 出现。

排查时要保存原始记录和处理后 batch。只保存 token ID，无法回答文本来源和过滤规则；只保存原始文本，无法回答 collator 最终产生了哪些 labels。数据、tokenizer 和训练版本必须能共同回放。

## 4.11 Train/Eval 背离：先拆评估链路

train loss 下降而 eval loss 上升，可能是过拟合，也可能是训练和评估格式、mask、数据分布或评分器不一致。常见误判是看到 eval 变差就立刻加数据或换正则化。

先比较：

1. train 和 eval 是否使用同一 tokenizer、template 和 label policy。
2. 两边的有效 token 分母是否可比。
3. 数据来源、语言、领域、长度和合成比例是否不同。
4. eval 是否有污染、过滤或参考答案变化。
5. 生成样例是否支持 loss 曲线的结论。
6. 指标是否按任务切片而不是只看总平均。

训练集重复过多会让 train loss 很低；合成数据比例过高会让同分布 eval 看起来很好，真实用户输入却变差；评估模板多一个 EOS 或少一个 role token，也可能制造损失差异。只有先排除评估链路问题，才有必要讨论过拟合和泛化。

## 4.12 Checkpoint 恢复是状态恢复，不是加载权重

一个可继续训练的 checkpoint 至少包含：

```text
model parameters
optimizer state
scheduler state
global step / consumed tokens
gradient scaler state
random states
dataloader position or replay manifest
model/tokenizer/collator versions
distributed shard metadata
```

只保存模型权重后继续训练，可能得到一个能推理的模型，却不是原训练过程的连续恢复。optimizer 动量丢失、scheduler 重新 warmup、随机状态变化和数据位置跳跃都会让 loss 曲线改变。

恢复测试应使用一个小任务：运行若干 step，保存 checkpoint；从 checkpoint 恢复，继续运行相同数量的 step；比较参数、optimizer、scheduler、随机状态和数据顺序。完全位级一致在某些非确定性硬件上不一定可行，但应事先定义允许差异和需要保持的行为指标。

恢复后第一步异常时，优先检查：

1. global step 和 consumed tokens；
2. 真实 learning rate；
3. optimizer 和 scaler；
4. dataloader 是否跳过或重复样本；
5. 模型和 adapter 是否加载完整；
6. world size、shard 和 rank mapping 是否变化。

## 4.13 分布式训练：不要只看 rank 0

分布式训练会把单卡问题放大，也会引入 rank 间不一致。每个 rank 应至少记录 loss、batch shard、有效 token 数、梯度或归约后的状态、通信错误和硬件事件。

如果第 `t` 步各 rank loss 为 `L_{t,r}`，rank skew 可以写成：

```math

D_{\mathrm{rank},t}=\max_r L_{t,r}-\min_r L_{t,r}
```

只有当所有 rank 都有有限且同口径的 loss 时，`D_rank` 才有定义。某个 rank loss 缺失或非有限时，应标记为 `unknown` 或直接进入异常处理，而不是用剩余 rank 计算出一个看似正常的差异。

常见原因包括：

- 数据 shard 长度、过滤和随机种子不一致；
- 某个 rank 得到异常长样本或空 batch；
- all-reduce 前后梯度或 loss 归一化不一致；
- FSDP/ZeRO shard、保存和恢复元数据不完整；
- 单节点硬件、通信或显存错误；
- 某个 rank 的异常数据先触发 overflow，其他 rank 随后被同步影响。

单卡复现和缩小 world size 是重要反事实实验，但单卡正常不能证明分布式正确，只能说明某些通信和 shard 条件可能参与了故障。

## 4.14 训练监控应该能支持回放

监控不是只画 loss 曲线。为了回放一次故障，系统需要把指标、事件和版本关联起来：

| 类别 | 指标或事件 | 作用 |
| --- | --- | --- |
| 数值 | loss、grad norm、param norm、非有限值 | 定位数值传播 |
| 优化 | learning rate、warmup、scheduler step | 检查更新状态 |
| 监督 | 有效 label token、mask 比例、长度 | 检查目标边界 |
| 精度 | scaler、overflow、算子精度 | 检查低精度风险 |
| 数据 | batch ID、来源、长度、版本 | 回放异常样本 |
| 分布式 | rank loss、shard、通信状态 | 定位 rank 差异 |
| 恢复 | checkpoint、global step、随机状态 | 验证连续性 |
| 资源 | GPU memory、吞吐、数据加载时间 | 区分系统瓶颈 |

指标采样和存储也需要版本化。若训练异常发生在采样间隔之间，团队应能在指定窗口临时提高粒度，不能因为成本控制而永久丢失 batch 级证据。

## 4.15 最小复现和修复顺序

训练不稳定时，建议按以下顺序压缩环境：

1. 固定代码、配置、数据和 tokenizer 版本。
2. 取第一次异常前后的 batch 和 checkpoint。
3. 单卡、少量 step、关闭外部副作用地回放。
4. 先使用相同 precision，再以 fp32/bf16 做对照。
5. 固定 batch，分别改变数据、mask、learning rate 和长度。
6. 恢复原始并发、world size、checkpoint 和 dataloader。
7. 每一步记录哪个假设被支持或排除。

修复顺序通常是：先隔离异常数据和停止继续扩大损失，再恢复到已知正常 checkpoint；然后修正明确的 mask、scheduler、precision 或状态问题；最后在小规模和目标规模上分别验证。不要在一个尚未知道根因的大训练任务上连续试十个配置，因为每次试验都会改变证据。

## 4.16 训练稳定性指标

### 4.16.1 非有限率

在 `T>0` 个已记录 step 中：

```math

R_{\mathrm{nf}}=N_{\mathrm{nonfinite}}/T
```

`T=0` 时结果未定义。`R_nf=0` 也只说明记录到的 loss/grad 没有非有限值，不能证明未记录的参数、optimizer state 和通信张量正常。

### 4.16.2 有效监督覆盖

对样本或 batch，若有效 label token 数为 `n_t`，历史目标范围和分母必须按相同粒度统计。`n_t=0` 直接是无监督样本，不能参与普通平均 loss。

### 4.16.3 学习率连续性

```math

D_{\eta,t}=|\eta_t-\hat{\eta}_t|
```

只有 scheduler 版本、global step、总步数和 warmup 定义完整时，`hat_eta_t` 才是可计算的。

### 4.16.4 Rank 差异

```math

D_{\mathrm{rank},t}=\max_r L_{t,r}-\min_r L_{t,r}
```

rank loss 缺失或非有限时保持 `unknown`，不要用 0 填补。

### 4.16.5 训练状态判断

综合状态不应把所有指标简单相乘。一个实用的状态顺序是：

```text
failed：必要指标明确违反约束，或已出现不可接受异常
unknown：缺少判断必要的 batch、版本、rank 或恢复证据
observed_stable：当前观测满足约束，但仍需持续监控
```

`observed_stable` 不是永久保证，也不等于模型已经达到业务目标。训练稳定只说明数值和状态链路在当前观察范围内没有发现明确异常。

## 4.17 一个可运行的训练稳定性审计示例

下面的示例用标准库处理 toy step 日志，定位第一次异常、区分 spike/NaN/overflow/label token/LR/rank 问题，并验证空日志、非有限输入、非法计数和布尔字段边界。

```python
import math
from dataclasses import dataclass
from statistics import median
from typing import List, Optional, Tuple


def strict_int(value: object) -> bool:
    return type(value) is int


def require_non_negative_int(name: str, value: object) -> None:
    if not strict_int(value) or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")


def require_finite_non_negative(name: str, value: object) -> None:
    if type(value) not in (int, float) or not math.isfinite(float(value)):
        raise ValueError(f"{name} must be finite")
    if float(value) < 0:
        raise ValueError(f"{name} must be non-negative")


def safe_ratio(numerator: int, denominator: int) -> Optional[float]:
    require_non_negative_int("numerator", numerator)
    require_non_negative_int("denominator", denominator)
    if numerator > denominator:
        raise ValueError("numerator cannot exceed denominator")
    if denominator == 0:
        return None
    return round(numerator / denominator, 3)


@dataclass(frozen=True)
class StepLog:
    step: int
    loss: float
    lr: float
    expected_lr: float
    grad_norm: float
    label_tokens: int
    overflow: bool
    rank_losses: Tuple[float, ...]
    batch_id: str
    resumed: bool


def validate(row: StepLog) -> None:
    require_non_negative_int("step", row.step)
    require_non_negative_int("label_tokens", row.label_tokens)
    if not row.batch_id.strip():
        raise ValueError("batch_id must not be empty")
    if type(row.overflow) is not bool or type(row.resumed) is not bool:
        raise ValueError("overflow and resumed must be bool")
    for name, value in (
        ("loss", row.loss),
        ("lr", row.lr),
        ("expected_lr", row.expected_lr),
        ("grad_norm", row.grad_norm),
    ):
        if type(value) not in (int, float):
            raise ValueError(f"{name} must be numeric")
    if not row.rank_losses:
        raise ValueError("rank_losses must not be empty")
    if any(type(value) not in (int, float) for value in row.rank_losses):
        raise ValueError("rank losses must be numeric")


def finite_values(values: Tuple[float, ...]) -> List[float]:
    return [float(value) for value in values if math.isfinite(float(value))]


def inspect(logs: List[StepLog], label_token_floor: int = 128):
    require_non_negative_int("label_token_floor", label_token_floor)
    if not logs:
        return {"state": "unknown", "reason": "no_step_logs", "first_bad_step": None}
    for row in logs:
        validate(row)
    steps = [row.step for row in logs]
    if len(steps) != len(set(steps)):
        raise ValueError("step values must be unique")

    spike_steps: List[int] = []
    nonfinite_steps: List[int] = []
    grad_steps: List[int] = []
    overflow_steps: List[int] = []
    label_steps: List[int] = []
    lr_steps: List[int] = []
    rank_steps: List[int] = []
    reasons = {}
    finite_losses: List[float] = []
    for index, row in enumerate(logs):
        current: List[str] = []
        loss_finite = math.isfinite(float(row.loss))
        grad_finite = math.isfinite(float(row.grad_norm))
        if not loss_finite or not grad_finite:
            nonfinite_steps.append(row.step)
            current.append("non_finite_loss_or_grad")
        else:
            finite_losses.append(float(row.loss))
            window = [
                float(previous.loss)
                for previous in logs[max(0, index - 3) : index]
                if math.isfinite(float(previous.loss))
            ]
            if window:
                baseline = median(window)
                if float(row.loss) > baseline + 1.0:
                    spike_steps.append(row.step)
                    current.append("loss_spike")
        if grad_finite and float(row.grad_norm) > 5.0:
            grad_steps.append(row.step)
            current.append("gradient_norm_high")
        if row.overflow:
            overflow_steps.append(row.step)
            current.append("amp_overflow")
        if row.label_tokens < label_token_floor:
            label_steps.append(row.step)
            current.append("too_few_label_tokens")
        if math.isfinite(float(row.lr)) and math.isfinite(float(row.expected_lr)):
            if abs(float(row.lr) - float(row.expected_lr)) > 0.00001:
                lr_steps.append(row.step)
                current.append("lr_discontinuity")
        else:
            nonfinite_steps.append(row.step)
            current.append("non_finite_learning_rate")
        ranks = finite_values(row.rank_losses)
        if len(ranks) == len(row.rank_losses) and max(ranks) - min(ranks) > 1.0:
            rank_steps.append(row.step)
            current.append("rank_loss_skew")
        if current:
            reasons[row.step] = current

    bad_steps = sorted(
        set(
            spike_steps
            + nonfinite_steps
            + grad_steps
            + overflow_steps
            + label_steps
            + lr_steps
            + rank_steps
        )
    )
    state = "observed_stable" if not bad_steps else "failed"
    return {
        "state": state,
        "first_bad_step": bad_steps[0] if bad_steps else None,
        "spike_steps": spike_steps,
        "nonfinite_steps": sorted(set(nonfinite_steps)),
        "gradient_steps": grad_steps,
        "overflow_steps": overflow_steps,
        "label_steps": label_steps,
        "lr_steps": lr_steps,
        "rank_steps": rank_steps,
        "reasons": reasons,
        "summary": {
            "spike_rate": safe_ratio(len(spike_steps), len(logs)),
            "nonfinite_rate": safe_ratio(len(set(nonfinite_steps)), len(logs)),
            "overflow_rate": safe_ratio(len(overflow_steps), len(logs)),
            "min_label_tokens": min(row.label_tokens for row in logs),
            "max_finite_grad_norm": (
                max(
                    float(row.grad_norm)
                    for row in logs
                    if math.isfinite(float(row.grad_norm))
                )
                if any(math.isfinite(float(row.grad_norm)) for row in logs)
                else None
            ),
        },
    }


logs = [
    StepLog(100, 1.82, 0.000080, 0.000080, 1.2, 4096, False, (1.81, 1.82, 1.80, 1.83), "clean_100", False),
    StepLog(101, 1.80, 0.000081, 0.000081, 1.1, 4096, False, (1.80, 1.79, 1.81, 1.80), "clean_101", False),
    StepLog(102, 1.79, 0.000082, 0.000082, 1.3, 4096, False, (1.78, 1.79, 1.80, 1.79), "clean_102", False),
    StepLog(103, 4.95, 0.000083, 0.000083, 12.5, 4096, True, (4.80, 4.95, 5.10, 8.20), "long_seq_bad", False),
    StepLog(104, float("nan"), 0.000084, 0.000084, float("inf"), 12, True, (float("nan"), 4.90, 5.20, 5.00), "mask_empty", False),
    StepLog(200, 2.80, 0.000250, 0.000085, 5.6, 4096, False, (2.70, 2.82, 2.79, 2.86), "resume_first", True),
]

report = inspect(logs)
print("state=", report["state"])
print("first_bad_step=", report["first_bad_step"])
print("reasons=", report["reasons"])
print("summary=", report["summary"])
assert report["state"] == "failed"
assert report["first_bad_step"] == 103
assert report["summary"]["min_label_tokens"] == 12
assert 200 in report["lr_steps"]
assert safe_ratio(0, 0) is None

assert inspect([])["state"] == "unknown"

bad_bool = StepLog(1, 1.0, 0.1, 0.1, 1.0, True, False, (1.0,), "bad_bool", False)
try:
    validate(bad_bool)
except ValueError as exc:
    assert "label_tokens" in str(exc)
else:
    raise AssertionError("bool must not masquerade as label token count")

bad_step = StepLog(1, float("nan"), 0.1, 0.1, 1.0, 10, False, (1.0,), "bad_nan", False)
validate(bad_step)
report_nan = inspect([bad_step])
assert report_nan["state"] == "failed"
assert report_nan["first_bad_step"] == 1

try:
    safe_ratio(1, 0)
except ValueError:
    pass
else:
    raise AssertionError("positive numerator with zero denominator is invalid")
```

示例中的 step 103 是第一处分歧：loss、梯度、overflow 和 rank skew 同时异常；step 104 的 NaN 和极少 label token 是后续证据；step 200 的学习率跳变属于恢复状态问题。`inspect([])` 返回 `unknown`，因为没有任何 step 证据；它不把空日志当成稳定训练。

## 4.18 从事故到恢复验证

训练恢复要分阶段进行：

1. 保存异常 step 前后的日志、batch、checkpoint 和环境版本。
2. 暂停扩大训练或标记受影响 checkpoint，防止污染后续实验。
3. 在单卡、固定 batch 和短窗口中复现第一次异常。
4. 对数据、mask、学习率、precision、optimizer 和分布式分别做反事实实验。
5. 选择已知正常 checkpoint 或重新生成干净状态。
6. 进行 checkpoint save/resume 连续性测试。
7. 在小规模训练和目标规模训练上分别回归。
8. 观察恢复后的 loss、有效 token、lr、overflow、rank 和资源指标。

“训练跑起来了”不是恢复验证。至少要确认新的运行没有复现原始失败样本，恢复后的 scheduler 和 optimizer 状态连续，数据版本没有混入被隔离记录，评估集和模型输出没有出现新的回归。

## 4.19 常见但危险的处理方式

### 一上来调小学习率

学习率可能确实过高，但如果真正原因是空 labels、异常 batch 或 checkpoint 恢复跳变，调小学习率只是掩盖问题。应先保存第一处分歧证据，再把学习率作为一个隔离变量实验。

### 发现 NaN 后直接重启

重启可能让曲线短暂恢复，却丢失第一次非有限值的 batch 和状态。正确做法是保留原运行、记录重启原因，并明确新运行是否从干净 checkpoint 开始。

### 只看 rank 0

rank 0 的平均 loss 可能掩盖某个 rank 的异常长样本、overflow 或通信问题。分布式日志至少要能定位到 rank、shard 和 batch。

### 只看总 loss

没有有效 label token、不同 padding 比例或不同数据切片时，总 loss 不可直接比较。应同时看有效 token、长度、来源和 mask。

### 同时改变多个变量

换数据、换精度、换 batch、调学习率和换模型一起做，无法知道哪个动作有效，也无法把结论迁移到下一次事故。

### 把梯度裁剪当作根因修复

裁剪可以限制一次危险更新，但持续触发说明训练配置或数据分布超出预期。应记录裁剪前后的梯度范数和触发比例。

## 4.20 资料与证据边界

本章的训练稳定性方法参考以下资料：

- PyTorch autograd anomaly detection 用于定位反向传播中的异常数值；它增加开销，不能替代生产级指标和输入检查。
- PyTorch AMP、GradScaler 和 gradient clipping 文档用于说明混合精度、unscale 和梯度裁剪的公开接口；实际稳定性仍取决于模型、硬件、算子和配置。
- PyTorch DistributedDataParallel、FSDP 和 Distributed Checkpoint 资料用于说明分布式参数、状态和 checkpoint 的公开边界；加载成功不等于恢复连续性。
- Hugging Face Transformers Trainer 和相关训练恢复文档用于说明 optimizer、scheduler、global step 和数据加载状态的常见保存方式；框架版本和自定义训练循环可能改变行为。
- 梯度爆炸、混合精度和优化器的论文用于解释一般机制；论文实验不能直接给出目标模型的学习率、梯度阈值或 batch 结论。

官方文档能支持接口和公开行为，不能证明某个训练作业的日志、labels、rank 状态或 checkpoint 完整。训练事故结论必须绑定代码、数据、硬件、precision、world size、版本和实测回放。

## 4.21 本章小结

训练不稳定排查的核心是把一条损失曲线还原成一条有上下文的状态时间线。先找到第一次异常 step，保存它的 batch、labels、有效 token、学习率、梯度、overflow、rank 和 checkpoint；再用单变量反事实实验区分数据、mask、优化、精度、恢复和分布式原因；修复后进行 save/resume、最小训练和目标规模回归。

NaN 不是根因，loss spike 也不是根因，低 loss 更不是成功证明。只有当训练状态可观测、异常样本可回放、恢复状态可验证、指标分母清楚且失败能够进入回归集时，训练过程才从一次昂贵的长跑变成可诊断、可恢复的工程系统。
