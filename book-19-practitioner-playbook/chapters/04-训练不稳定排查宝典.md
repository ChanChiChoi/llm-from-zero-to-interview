# 第四章：训练不稳定的定位与恢复

训练不稳定是大模型工程中最昂贵的故障之一。一个小实验中的 loss spike 可能只浪费几分钟，但大规模训练中的异常 batch、非有限梯度、错误的 scheduler 状态或损坏 checkpoint，可能浪费数百张 GPU 数小时，并让团队在几天后才发现模型已经偏离了预期。

训练事故难排查，是因为它通常不是一个单点错误。数据长度分布、label mask、学习率、梯度累积、混合精度、optimizer state、分布式 rank 和 checkpoint 恢复可能同时影响同一条 loss 曲线。看到 NaN 后直接降低学习率，可能暂时让曲线恢复，却没有解释第一个非有限值是怎样产生的；看到 loss 不下降后直接换模型，也可能掩盖 labels 全部被忽略的 collator 错误。

本章把训练过程视为一个可记录的状态机。每个 step 都应该能回答：使用了哪个 batch、真实学习率是多少、有效监督 token 有多少、梯度是否有限、是否发生 overflow、各 rank 是否一致、checkpoint 和恢复状态是什么。排障从第一次异常开始，而不是从日志最后一行开始；修复分为止损、根因修复、恢复验证和防复发回归。

## 4.1 训练运行是一条状态时间线

一个训练 step 不只是一个 loss 数字。可以把第 `t` 步的运行状态写成：

```math

u_t=(L_t,\eta_t,g_t,n_t,o_t,\rho_t,b_t,c_t,r_t)
```

其中：

- `L_t` 是训练损失；
- `eta_t` 是实际生效的学习率；
- `g_t` 是梯度范数；
- `n_t` 是经过任务目标对齐、causal shift 和 loss mask 后实际参与损失的目标位置数；
- `o_t` 是 AMP overflow 或 scaler 异常状态；
- `rho_t` 是各 rank 的 loss 集合；
- `b_t` 是 batch 标识和样本摘要；
- `c_t` 是 checkpoint、global step 和 optimizer/scheduler 状态；
- `r_t` 是该 step 的运行版本和资源上下文。

如果只记录 `L_t`，后面几乎所有根因都只能靠猜。一个完整的 step 记录至少要关联数据版本、tokenizer、collator、模型、优化器、scheduler、precision、world size、rank、随机状态和 checkpoint manifest。

训练稳定性不是要求所有数值永远单调下降。loss 可以有正常波动，梯度也会随 batch 难度变化。需要定义的是“什么变化属于预期范围，什么变化需要保存证据并暂停扩大训练”。这个范围必须与任务、模型规模、batch、精度和训练阶段绑定，不能把一个小模型的阈值直接复制给另一套系统。

## 4.2 先找到第一次异常 step

后续的 NaN、Inf、梯度爆炸和 loss 全部失真，往往只是第一次异常的传播结果。排障的第一个问题不是“现在为什么是 NaN”，而是“哪一个 step 第一次偏离了已知正常状态”。

建议在每个 step 或固定间隔记录：

```text
step / global_step
batch_id 和样本 ID 摘要
loss、损失目标定义、有效目标位置数与实际归一化分母
learning rate 与 scheduler step
gradient norm、parameter norm
AMP scaler 和 overflow
各 rank 的 loss numerator、denominator、有效目标数、batch shard 和通信状态
数据、模型、collator、optimizer 版本
最近 checkpoint 和随机状态
```

如果日志采样过稀，第一次异常可能落在两个采样点之间。应在发现异常后提高该时间窗口的日志粒度，或用保存的 batch ID 回放相邻 step。没有 batch ID 的 loss spike 只能说明曲线异常，不能直接开始数据调查。

## 4.3 Loss spike：区分单个 batch 和系统性发散

Loss spike 是损失在短时间内突然高于近期水平。它可能由一个极端 batch 引起，也可能是学习率、精度或状态变化让之后的所有 batch 都变差。

先把现象分成三类：

1. **单点 spike 后恢复**：优先看该 batch 的长度、来源、标签、mask 和异常 token。
2. **spike 后持续上升**：检查学习率、梯度、AMP、optimizer state 和参数是否已经被破坏。
3. **周期性 spike**：检查数据分片、scheduler、梯度累积边界、评估/保存切换和分布式同步。

Spike 是现象，不是根因。关于 Adam 更新不稳定的研究分析和观测到的规模差异，只能说明某些优化器状态与训练条件值得检查；另一项研究把 loss spike 和自适应预条件器下的曲率联系起来，也只在作者规定的理论设定和实验配方内成立。它们支持把 optimizer state、梯度方向和学习率纳入假设集，不能让我们仅凭曲线就把事故归因于 Adam 或照搬论文超参。[Molybog 等](https://arxiv.org/html/2304.09871)、[Bai 等](https://arxiv.org/html/2506.04805v2)

可以用近期窗口的中位数和离差构造教学性的 spike 分数。设窗口中位数为 `m_t`，窗口的中位绝对偏差为 `d_t`，且 `d_t>0`：

```math

S_t=\frac{L_t-m_t}{d_t}
```

如果窗口为空或 `d_t=0`，这个分数没有定义，应改用绝对阈值、相邻 step 对照或保留“没有足够基线”的状态。不能把一个固定的小数放到分母里掩盖窗口没有波动的事实。

看到 spike 后，先保存对应 batch，再做三组对照：

- 正常 batch 在相同模型状态下前向和反向；
- 异常 batch 在相同模型状态下单独运行；
- 异常 batch 替换为裁剪长度或过滤后的版本。

如果只有异常 batch 触发 spike，根因更接近数据、mask 或长度；如果所有 batch 都在同一步开始变差，根因更接近学习率、精度、optimizer 或分布式状态。

## 4.4 Loss 不下降：先验证训练链路真的在更新

loss 不下降不一定代表模型学不会。常见的链路错误包括：

- 所有 labels 都是 `-100`；
- optimizer 没有拿到可训练参数；
- 梯度没有反传或被过早清零；
- 学习率实际为 0 或 scheduler 已经走到错误位置；
- 数据和 labels 错位；
- 模型处于错误的训练/评估状态；
- 记录的是旧的 loss 或未完成 optimizer step 的 loss。

最小 sanity check 是在几十条固定样本上尝试 overfit。若模型、collator、optimizer 和 loss 链路正确，小数据通常应能显著降低训练误差；如果连一个极小集合都无法拟合，优先检查参数更新、labels、mask 和数据格式，而不是先增加模型容量。

参数是否更新可以用两次状态的差异验证。对参数向量 `theta`，若在有效 optimizer step 后：

```math

\Delta\theta=\|\theta_{t+1}-\theta_t\|_2
```

在学习率非零、存在有效 labels 且梯度应当非零的条件下，持续 `Delta theta=0` 是异常信号。被冻结参数、梯度累积尚未达到更新边界和梯度裁剪为零是不同原因，日志需要记录更新阶段。

## 4.5 NaN/Inf：追溯第一个非有限值

NaN 和 Inf 不是一个可直接修复的根因类别。它们可能来自输入、前向算子、loss 归一化、反向梯度、optimizer state、混合精度或 checkpoint。

排查要按数值传播顺序进行：

1. 输入张量、labels、mask 和长度是否有限、合法。
2. 前向输出和 logits 是否先出现非有限值。
3. loss 分子和有效 token 分母是否有效。
4. 反向后梯度是否先出现非有限值。
5. optimizer step 后参数或 optimizer state 是否变坏。
6. AMP scaler、通信归约或 checkpoint 恢复是否改变了状态。

如果单独前向一个 batch 就有 NaN，优先查数据、mask、除零、log 和 attention mask；如果前向正常、反向异常，查梯度范围和算子；如果 optimizer step 后才异常，查学习率、精度和 optimizer state。

调试时可以启用 PyTorch anomaly detection，让 backward 异常关联到创建相应节点的 forward traceback；`check_nan=True` 会在 backward 产生 NaN 时抛错。它会显著增加开销，也不是一遍扫描所有 forward 张量的 finite check，仍要在关键边界显式检查输入、logits、loss、梯度和 optimizer state。[PyTorch autograd anomaly detection（2.15）](https://docs.pytorch.org/docs/2.15/autograd.html#anomaly-detection)

非有限率在 `T>0` 个已记录 step 上可以写成：

```math

R_{\mathrm{nf}}=\frac{N_{\mathrm{nonfinite}}}{T}
```

若 `T=0`，不是稳定率 0，而是没有观测。只要出现第一个必要状态的非有限值，就应保存该 step 及其上下文；后续全部 NaN 不能替代第一处证据。

## 4.6 梯度范数、裁剪和损失归一化

梯度爆炸通常表现为 gradient norm 突然变大，随后 loss spike、overflow 或 NaN。它可能由学习率过高、极端长样本、错误 mask、异常初始化、LoRA 配置或梯度累积错误引起。

全局梯度范数可以写成：

```math

g_t=\sqrt{\sum_{\ell=1}^{K}\|\nabla_{\theta_\ell}L_t\|_2^2}
```

梯度 clipping 能把更新限制在一定范围内，但它不是数据和目标错误的修复。若每个 step 都触发大幅裁剪，说明真实梯度分布已经超出预期，应该检查 loss 归一化、有效 token 数、学习率和 batch，而不是只把 clipping 阈值继续调大。

梯度累积还会引入两个常见错误：一是每个 micro-batch 与完整 global batch 的 loss 归一化不一致，二是达不到累积步数时仍错误地执行 optimizer step。记录每个 micro-batch 的有效 token 数，并明确 loss 是按样本、token 还是 global batch 归一化。

使用 FP16 `GradScaler` 时，先累积完整 effective batch，再对对应 optimizer 调用一次 `unscale_`，之后测量或裁剪未缩放的梯度；PyTorch 的 `clip_grad_norm_` 返回裁剪前的总范数，`error_if_nonfinite=True` 可在该总范数非有限时中止。[AMP 裁剪示例](https://docs.pytorch.org/docs/2.15/notes/amp_examples.html)、[`clip_grad_norm_` API](https://docs.pytorch.org/docs/2.15/generated/torch.nn.utils.clip_grad_norm_.html)。总范数检查能及时阻止坏更新，但不告诉你是哪一个张量最先异常。

## 4.7 有效 label token 是稳定性指标

SFT 和语言建模的损失只会计算训练目标实际选中的位置。原始 `labels != -100` 数量只是一个预检查值：模型可能在 forward 内部做 causal shift，loss 函数还可能应用额外的忽略规则或权重。令 `T_loss` 表示完成目标模型要求的对齐/shift 和 loss mask 后，真正送入损失计算的目标位置集合；则：

```math

n_t=|T_{\mathrm{loss}}|
```

还要记录该 loss 实际使用的归一化分母 `d_t`。按 token 求均值时通常 `d_t=n_t`；按样本先求均值、带权目标或自定义目标时，分母可能不同。比较训练 step、数据切片或 rank 前，必须让损失定义、reduction 和分母口径一致。

看一个六 token 的 toy 序列。若模型收到六个 token，并在 forward 内部用位置 `s` 的 logits 预测位置 `s+1`，原始 labels 中六个位置都非忽略值，原始计数是 6；但第 0 个 label 没有前一位置的 logits 与之对齐，实际可被预测的目标位置只有 1—5，所以 `n_t=5`。若 assistant-only 目标在对齐后只保留答案和 EOS 两个位置，`n_t=2`。已经由数据管线预先移位的实现要按它的实际对齐重新数，不能让模型再 shift 一次。

当 `n_t=0` 时，token-mean loss 没有定义，应该隔离该 batch 并保留原始 labels、shift 后目标和 mask；当 `n_t>0` 但明显偏离同一数据/任务的历史分布时，先检查 assistant-only mask、截断、空答案、padding/角色边界和媒体对齐。有效目标减少会改变 batch loss 的样本权重；仅凭平均 loss 变小，不能说模型学得更稳定。

## 4.8 Learning rate、warmup 和 scheduler 状态

学习率是训练稳定性的核心变量，但配置文件中的目标值不等于每一步真实生效值。梯度累积、warmup、cosine scheduler、resume、跳过 batch 和分布式 global step 都可能改变实际曲线。

训练日志应同时记录 `lr`、scheduler step 和 global step。恢复训练时，把实际学习率与根据同一 scheduler 和 global step 计算出的预期值比较：

```math

D_{\eta,t}=|\eta_t-\hat{\eta}_t|
```

其中 `hat_eta_t` 是在版本、warmup 和 global step 都明确时的预期值。如果 scheduler 配置或总步数未知，`D_eta` 没有可靠定义，应该补齐 manifest。

常见事故包括：

1. resume 后 global step 从 0 重新开始，学习率重新 warmup。
2. optimizer state 恢复了，但 scheduler state 没恢复。
3. 改变 global batch 后仍使用原来的学习率和 warmup 步数。
4. 梯度累积步数变更导致实际更新频率改变。
5. 只保存了配置中的学习率，没有保存每一步实际值。

降学习率可以作为止损实验，但必须在固定数据和其他变量下验证。若学习率恢复后连续、异常 batch 单独正常、只有原训练设置发散，才可以把结论写成学习率或数值范围问题。

## 4.9 混合精度和 overflow

fp16、bf16 和 fp32 的动态范围、舍入和算子实现不同。混合精度能降低显存和提高吞吐，也会让某些前向、反向和 optimizer 状态更容易出现数值问题。

需要观察：

- scaler 的变化和 overflow 次数；
- unscale、gradient clipping 和 optimizer step 的顺序；
- 哪些算子被强制使用更高精度；
- fp16、bf16 和 fp32 的最小复现差异；
- overflow 是否集中在某类长度、数据或 rank。

如果 fp32 稳定、fp16 不稳定，不代表模型或数据一定错误，而是说明数值范围或实现路径需要调整。bf16 在许多硬件上动态范围更宽，但也不保证所有算子、硬件和框架组合都稳定。GradScaler 检测到梯度 Inf/NaN 时可以跳过该次 optimizer 更新并调整 scale；因此一次 overflow 是要记录的训练事件，不自动等于权重已损坏。要把 scaler 变化、被跳过的更新数和 scheduler 实际 step 对齐，检查问题是否持续或超过该运行预先声明的容忍策略。[PyTorch AMP 示例（2.15）](https://docs.pytorch.org/docs/2.15/notes/amp_examples.html)

还有一种需要谨慎处理的迟发假设：一篇 2026 年预印本报告，在其刻意采用较高学习率并长时间过训练的 28M—1.4B 参数实验中，输出 logits 均值增长会放大 BF16 与 FP32 输出头计算之间的误差，进而伴随较晚出现的 loss spike。若异常只在长时间稳定后出现，且 logits 尺度持续漂移，可把同一 hidden states 的 BF16/FP32 logits RMS 误差和 softmax KL 作为研究性探针；它计算成本较高，论文对自然大模型训练的迁移尚未确定，不能据此推断一般生产 spike 来自输出头量化。[Chen 等（2026）](https://arxiv.org/abs/2610.38277)

overflow rate 在 `T>0` 个 step 上为：

```math

R_{\mathrm{overflow}}=\frac{N_{\mathrm{overflow}}}{T}
```

`R_overflow` 为 0 也不证明没有数值风险，因为未记录的 scaler 或非有限参数仍可能遗漏；`T=0` 则是 `unknown`。

## 4.10 异常 batch：把数据和训练日志连起来

没有 batch ID 的 loss 曲线很难排查。每个 batch 至少需要关联样本 ID 摘要、来源桶、序列长度、有效 label token 数、媒体是否存在、过滤规则版本和数据分片。

异常 batch 的常见特征包括：

- 极长序列或异常长短混合；
- 空答案、全 mask 或角色错位；
- 乱码、非法 token、特殊 token 密集；
- 低质量来源或高风险代码；
- 重复模板集中出现；
- 图像、音频或标注缺失；
- 只在某个 rank 的 shard 出现。

排查时要保存原始记录和处理后 batch。只保存 token ID，无法回答文本来源和过滤规则；只保存原始文本，无法回答 collator 最终产生了哪些 labels。数据、tokenizer 和训练版本必须能共同回放。

## 4.11 Train/Eval 背离：先拆评估链路

train loss 下降而 eval loss 上升，可能是过拟合，也可能是训练和评估格式、mask、数据分布或评分器不一致。常见误判是看到 eval 变差就立刻加数据或换正则化。

先比较：

1. train 和 eval 是否使用同一 tokenizer、template 和 label policy。
2. 两边是否采用相同的目标定义、causal shift、mask、loss reduction 和归一化分母；并分别报告原始非忽略 label 数、shift 后有效目标数和实际 loss denominator。
3. 数据来源、语言、领域、长度和合成比例是否不同。
4. eval 是否有污染、过滤或参考答案变化。
5. 生成样例是否支持 loss 曲线的结论。
6. 指标是否按任务切片而不是只看总平均。

训练集重复过多会让 train loss 很低；合成数据比例过高会让同分布 eval 看起来很好，真实用户输入却变差；评估模板多一个 EOS 或少一个 role token，也可能制造损失差异。token-mean 汇总应对各 batch 的 loss numerator 和有效目标数求总和后相除；不能直接平均目标数量不同的 batch mean。按样本平均的任务则按其样本分母汇总。只有先排除评估链路问题，才有必要讨论过拟合和泛化。

## 4.12 Checkpoint 恢复是状态恢复，不是加载权重

一个可继续训练的 checkpoint 至少包含：

```text
model parameters
optimizer state
scheduler state
global step / consumed tokens
gradient scaler state
random states
dataloader position or replay manifest
model/tokenizer/collator versions
distributed shard metadata
```

只保存模型权重后继续训练，可能得到一个能推理的模型，却不是原训练过程的连续恢复。optimizer 动量丢失、scheduler 重新 warmup、随机状态变化和数据位置跳跃都会让 loss 曲线改变。

恢复测试应使用一个小任务：运行若干 step，保存 checkpoint；从 checkpoint 恢复，继续运行相同数量的 step；比较参数、optimizer、scheduler、随机状态和数据顺序。完全位级一致在某些非确定性硬件上不一定可行，但应事先定义允许差异和需要保持的行为指标。以 Hugging Face `Trainer` 为例，当前公开文档说明 resume 会恢复 optimizer、scheduler 和 RNG；缺少 optimizer/scheduler state 的 `save_only_model` checkpoint 不能按原状态继续训练。`ignore_data_skip=False` 会跳过已经看过的数据以继续原数据进度，设为 `True` 则从数据开头开始、速度较快但结果不同；这属于该 Trainer 的公开行为，不能替自定义 sampler、worker 随机状态或流式数据源证明精确恢复。[Trainer resume 文档](https://huggingface.co/docs/transformers/main_classes/trainer#resuming-training)、[Trainer checkpoint 教程](https://huggingface.co/docs/transformers/trainer_recipes#resume-training)。

PyTorch Distributed Checkpoint 可以在支持的状态表示和并行方案内按加载拓扑重新分片，但文档没有承诺 checkpoint state_dict 跨 PyTorch 版本向后兼容。能加载或改变 world size，只证明对应 API 的状态映射成功；不证明优化轨迹、样本顺序和数值结果与原运行等价。[Distributed Checkpoint（2.15）](https://docs.pytorch.org/docs/2.15/distributed.checkpoint.html)

恢复后第一步异常时，优先检查：

1. global step 和 consumed tokens；
2. 真实 learning rate；
3. optimizer 和 scaler；
4. dataloader 是否跳过或重复样本；
5. 模型和 adapter 是否加载完整；
6. world size、shard 和 rank mapping 是否变化。

## 4.13 分布式训练：不要只看 rank 0

分布式训练会把单卡问题放大，也会引入 rank 间不一致。每个 rank 应至少记录 loss、batch shard、有效 token 数、梯度或归约后的状态、通信错误和硬件事件。

如果第 `t` 步各 rank loss 为 `L_{t,r}`，rank skew 可以写成：

```math

D_{\mathrm{rank},t}=\max_r L_{t,r}-\min_r L_{t,r}
```

`L_{t,r}` 必须是同一目标和 reduction 下的本地平均 loss；同时记录每个 rank 的 loss numerator、实际 denominator 和有效目标数 `n_{t,r}`。某个 rank 的 loss 或 denominator 缺失、非有限或为零时，rank mean 的差异记为 `unknown`，不能拿剩余 rank 拼出一个看似正常的范围。`D_rank` 是观测量；是否触发告警要依据任务和运行预先声明的策略，而非共用一个固定阈值。

rank loss 数值还会影响全局平均的解释。假设 rank 0 的 loss sum 为 3、有效目标数为 2；rank 1 的 loss sum 为 6、有效目标数为 6。两边的 token-mean loss 分别是 1.5 和 1.0，rank mean 的简单平均是 1.25；全局 token mean 应为 `(3+6)/(2+6)=1.125`。因此，跨 rank 合并 token-mean loss 时要累加 numerator 和有效目标数，不能不加权地平均各 rank 的 mean。DDP 默认 reducer 对各 rank 梯度做平均；设参与同步的 rank 数为 `W`，在无自定义通信 hook、框架额外缩放等条件下，若目标是全局 token mean，可让每个 rank 对本地 loss sum 使用 `W/Σ_r n_{t,r}` 缩放，再由 DDP 求平均。[DDP 设计说明（2.15）](https://docs.pytorch.org/docs/2.15/notes/ddp.html)。按样本或加权目标计算时，应使用其真实 denominator 推导对应缩放。

常见原因包括：

- 数据 shard 长度、过滤和随机种子不一致；
- 某个 rank 得到异常长样本或空 batch；
- all-reduce 前后梯度或 loss 归一化不一致；
- FSDP/ZeRO shard、保存和恢复元数据不完整；
- 单节点硬件、通信或显存错误；
- 某个 rank 的异常数据先触发 overflow，其他 rank 随后被同步影响。

单卡复现和缩小 world size 是重要反事实实验，但单卡正常不能证明分布式正确，只能说明某些通信和 shard 条件可能参与了故障。

## 4.14 训练监控应该能支持回放

监控不是只画 loss 曲线。为了回放一次故障，系统需要把指标、事件和版本关联起来：

| 类别 | 指标或事件 | 作用 |
| --- | --- | --- |
| 数值 | loss、grad norm、param norm、非有限值 | 定位数值传播；同时保存 loss contract、numerator 和 denominator |
| 优化 | learning rate、warmup、scheduler step | 检查更新状态 |
| 监督 | 原始非忽略 labels、shift 后有效目标数、实际 loss denominator、mask 比例、长度 | 检查目标边界和平均口径 |
| 精度 | scaler、overflow、算子精度 | 检查低精度风险 |
| 数据 | batch ID、来源、长度、版本 | 回放异常样本 |
| 分布式 | 各 rank loss numerator / denominator / 有效目标数、shard、通信状态 | 计算可比较的 rank mean 和全局加权 loss |
| 恢复 | checkpoint、global step、随机状态 | 验证连续性 |
| 资源 | GPU memory、吞吐、数据加载时间 | 区分系统瓶颈 |

指标采样和存储也需要版本化。若训练异常发生在采样间隔之间，团队应能在指定窗口临时提高粒度，不能因为成本控制而永久丢失 batch 级证据。

## 4.15 最小复现和修复顺序

训练不稳定时，建议按以下顺序压缩环境：

1. 固定代码、配置、数据和 tokenizer 版本。
2. 取第一次异常前后的 batch 和 checkpoint。
3. 单卡、少量 step、关闭外部副作用地回放。
4. 先使用相同 precision，再以 fp32/bf16 做对照。
5. 固定 batch，分别改变数据、mask、learning rate 和长度。
6. 恢复原始并发、world size、checkpoint 和 dataloader。
7. 每一步记录哪个假设被支持或排除。

修复顺序通常是：先隔离异常数据和停止继续扩大损失，再恢复到已知正常 checkpoint；然后修正明确的 mask、scheduler、precision 或状态问题；最后在小规模和目标规模上分别验证。不要在一个尚未知道根因的大训练任务上连续试十个配置，因为每次试验都会改变证据。

## 4.16 训练稳定性指标

### 4.16.1 非有限率

在 `T>0` 个已记录 step 中：

```math

R_{\mathrm{nf}}=N_{\mathrm{nonfinite}}/T
```

`T=0` 时结果未定义。`R_nf=0` 也只说明记录到的 loss/grad 没有非有限值，不能证明未记录的参数、optimizer state 和通信张量正常。

### 4.16.2 有效监督覆盖

对样本或 batch，`n_t` 按 4.7 定义为 shift 和 loss mask 后实际参与目标损失的位置数；另记 `d_t` 为该损失真实使用的归一化分母。原始 `labels != -100` 计数可保留作格式诊断，但不能冒充 `n_t`。当训练目标是 token mean 时两者常相等；其他 reduction 需按实现记录 `d_t`。历史分位数、step 间变化和 rank 间比较只能在同一 loss contract 下解释。`n_t=0` 表示没有有效监督目标；如果某个 batch 有样本但空目标，不能把其 loss 当作普通均值并入汇总。

### 4.16.3 学习率连续性

```math

D_{\eta,t}=|\eta_t-\hat{\eta}_t|
```

只有 scheduler 版本、global step、总步数和 warmup 定义完整时，`hat_eta_t` 才是可计算的。

### 4.16.4 Rank 差异

```math

D_{\mathrm{rank},t}=\max_r L_{t,r}-\min_r L_{t,r}
```

只有目标、reduction 和实际分母口径相同时才比较 rank loss mean；同时报告各 rank 的 numerator、denominator 和有效目标数。任一 rank 缺失、非有限或分母为零时保持 `unknown`，不要用 0 填补。rank spread 是诊断量，策略阈值需要绑定当前任务、数据和训练配置。

### 4.16.5 训练状态判断

综合状态不应把所有指标简单相乘，也不能在没有运行策略时自行发明通用合格阈值。一个实用的状态顺序是：

```text
failed：出现非有限 loss/梯度、零有效目标等硬失败，或违反本次运行明确配置的策略
unknown：缺少判断必要的 batch、loss denominator、rank、版本或恢复证据
observed_stable：本次观察未触发硬失败或已声明策略，但仍需持续监控
```

loss 偏离、梯度范数、rank 差异和 overflow 应先按原始测量值与发生率报告；当团队为具体模型、数据、precision 和训练阶段声明阈值后，才据此判断是否违反策略。单次 AMP overflow 也可能被 scaler 用跳过更新的方式处理，其是否超出可接受范围由运行策略和实际更新状态决定。`observed_stable` 不是永久保证，也不等于模型已经达到业务目标，只说明当前观察范围内没有发现明确异常。

## 4.17 一个训练稳定性审计示例

审计器先保留测量值，再把它们与本次运行显式声明的策略比较。硬失败、策略违规、观察事件和无法判断的项目分开保存；例如，没有配置梯度范数上限时，程序仍报告梯度范数，却不替作者认定它“过高”。下面的标准库示例以已记录的 loss numerator、denominator、rank 统计和 shift 后目标数为输入，不试图从原始 labels 猜训练框架内部的 loss 口径。

```python
import math
from dataclasses import dataclass
from statistics import median
from typing import Dict, List, Optional, Tuple


def is_number(value: object) -> bool:
    return type(value) in (int, float)


def require_non_negative_int(name: str, value: object) -> None:
    if type(value) is not int or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")


@dataclass(frozen=True)
class StepLog:
    step: int
    loss: float
    loss_numerator: float
    loss_denominator: float
    loss_contract: str
    lr: float
    expected_lr: Optional[float]
    grad_norm: float
    raw_non_ignored_labels: int
    effective_targets: int
    overflow: bool
    world_size: int
    rank_loss_numerators: Tuple[float, ...]
    rank_loss_denominators: Tuple[float, ...]
    rank_effective_targets: Tuple[int, ...]
    batch_id: str
    resumed: bool


@dataclass(frozen=True)
class DiagnosticPolicy:
    loss_delta: Optional[float] = None
    max_grad_norm: Optional[float] = None
    min_effective_targets: Optional[int] = None
    lr_tolerance: Optional[float] = None
    max_rank_mean_range: Optional[float] = None
    baseline_window: int = 3


def validate(row: StepLog) -> None:
    require_non_negative_int("step", row.step)
    require_non_negative_int("raw_non_ignored_labels", row.raw_non_ignored_labels)
    require_non_negative_int("effective_targets", row.effective_targets)
    if type(row.world_size) is not int or row.world_size < 1:
        raise ValueError("world_size must be a positive integer")
    if not row.batch_id.strip() or not row.loss_contract.strip():
        raise ValueError("batch_id and loss_contract must not be empty")
    if type(row.overflow) is not bool or type(row.resumed) is not bool:
        raise ValueError("overflow and resumed must be bool")
    values = (row.loss, row.loss_numerator, row.loss_denominator, row.lr, row.grad_norm)
    if any(not is_number(value) for value in values):
        raise ValueError("loss, numerator, denominator, lr, and grad_norm must be numeric")
    if row.expected_lr is not None and not is_number(row.expected_lr):
        raise ValueError("expected_lr must be numeric or None")
    lengths = (
        len(row.rank_loss_numerators),
        len(row.rank_loss_denominators),
        len(row.rank_effective_targets),
    )
    if any(length not in (0, row.world_size) for length in lengths):
        raise ValueError("rank fields must be absent or cover every rank")
    if len(set(lengths)) != 1:
        raise ValueError("rank numerator, denominator, and target counts must align")
    if any(not is_number(value) for value in row.rank_loss_numerators):
        raise ValueError("rank loss numerators must be numeric")
    if any(not is_number(value) for value in row.rank_loss_denominators):
        raise ValueError("rank loss denominators must be numeric")
    for count in row.rank_effective_targets:
        require_non_negative_int("rank_effective_targets", count)


def validate_policy(policy: DiagnosticPolicy) -> None:
    require_non_negative_int("baseline_window", policy.baseline_window)
    if policy.baseline_window == 0:
        raise ValueError("baseline_window must be positive")
    for name, value in (
        ("loss_delta", policy.loss_delta),
        ("max_grad_norm", policy.max_grad_norm),
        ("lr_tolerance", policy.lr_tolerance),
        ("max_rank_mean_range", policy.max_rank_mean_range),
    ):
        if value is not None and (
            not is_number(value) or not math.isfinite(float(value)) or value < 0
        ):
            raise ValueError(f"{name} must be finite and non-negative or None")
    if policy.min_effective_targets is not None:
        require_non_negative_int("min_effective_targets", policy.min_effective_targets)


def inspect(logs: List[StepLog], policy: DiagnosticPolicy) -> Dict[str, object]:
    validate_policy(policy)
    if not logs:
        return {"state": "unknown", "reason": "no_step_logs", "first_event_step": None}
    for row in logs:
        validate(row)
    steps = [row.step for row in logs]
    if steps != sorted(set(steps)):
        raise ValueError("step values must be unique and ordered")

    observations: Dict[int, List[str]] = {}
    hard_failures: Dict[int, List[str]] = {}
    policy_violations: Dict[int, List[str]] = {}
    unknown: Dict[int, List[str]] = {}
    measured: Dict[int, Dict[str, object]] = {}

    def add(target: Dict[int, List[str]], step: int, reason: str) -> None:
        target.setdefault(step, []).append(reason)

    for index, row in enumerate(logs):
        metrics: Dict[str, object] = {
            "loss_delta": None,
            "lr_abs_deviation": None,
            "rank_mean_range": None,
            "loss_numerator": float(row.loss_numerator),
            "loss_denominator": float(row.loss_denominator),
            "effective_targets": row.effective_targets,
            "grad_norm": float(row.grad_norm),
        }
        if not math.isfinite(float(row.loss)):
            add(hard_failures, row.step, "non_finite_loss")
        if not math.isfinite(float(row.loss_numerator)):
            add(hard_failures, row.step, "non_finite_loss_numerator")
        if not math.isfinite(float(row.grad_norm)):
            add(hard_failures, row.step, "non_finite_grad_norm")
        if not math.isfinite(float(row.lr)):
            add(hard_failures, row.step, "non_finite_lr")
        if not math.isfinite(float(row.loss_denominator)) or row.loss_denominator <= 0:
            add(hard_failures, row.step, "invalid_loss_denominator")
        if row.effective_targets == 0:
            add(hard_failures, row.step, "zero_effective_targets")
        if row.overflow:
            add(observations, row.step, "amp_overflow_event")

        if (
            policy.min_effective_targets is not None
            and row.effective_targets < policy.min_effective_targets
        ):
            add(policy_violations, row.step, "below_run_minimum_effective_targets")
        if math.isfinite(float(row.grad_norm)) and policy.max_grad_norm is not None:
            if row.grad_norm > policy.max_grad_norm:
                add(policy_violations, row.step, "exceeds_run_grad_norm_policy")

        if row.expected_lr is None:
            add(unknown, row.step, "expected_lr_missing")
        elif not math.isfinite(float(row.expected_lr)):
            add(hard_failures, row.step, "non_finite_expected_lr")
        elif math.isfinite(float(row.lr)):
            deviation = abs(float(row.lr) - float(row.expected_lr))
            metrics["lr_abs_deviation"] = deviation
            if policy.lr_tolerance is not None and deviation > policy.lr_tolerance:
                add(policy_violations, row.step, "exceeds_run_lr_tolerance")
                if row.resumed:
                    add(observations, row.step, "lr_mismatch_after_resume")

        if math.isfinite(float(row.loss)):
            previous = [
                float(item.loss)
                for item in logs[max(0, index - policy.baseline_window):index]
                if item.loss_contract == row.loss_contract
                and math.isfinite(float(item.loss))
            ]
            if previous:
                delta = float(row.loss) - median(previous)
                metrics["loss_delta"] = delta
                if delta > 0:
                    add(observations, row.step, "loss_above_recent_median")
                if policy.loss_delta is not None and delta > policy.loss_delta:
                    add(policy_violations, row.step, "exceeds_run_loss_delta_policy")
        if index and row.loss_contract != logs[index - 1].loss_contract:
            add(unknown, row.step, "loss_contract_changed")

        if row.world_size > 1:
            rank_data_present = all((
                len(row.rank_loss_numerators) == row.world_size,
                len(row.rank_loss_denominators) == row.world_size,
                len(row.rank_effective_targets) == row.world_size,
            ))
            if not rank_data_present:
                add(unknown, row.step, "rank_loss_data_missing")
            elif any(
                not math.isfinite(float(numerator))
                or not math.isfinite(float(denominator))
                or denominator <= 0
                for numerator, denominator in zip(
                    row.rank_loss_numerators, row.rank_loss_denominators
                )
            ):
                add(unknown, row.step, "rank_mean_not_computable")
            else:
                means = [
                    float(numerator) / float(denominator)
                    for numerator, denominator in zip(
                        row.rank_loss_numerators, row.rank_loss_denominators
                    )
                ]
                rank_range = max(means) - min(means)
                metrics["rank_mean_range"] = rank_range
                metrics["rank_means"] = tuple(means)
                metrics["rank_denominators"] = row.rank_loss_denominators
                metrics["rank_effective_targets"] = row.rank_effective_targets
                if (
                    policy.max_rank_mean_range is not None
                    and rank_range > policy.max_rank_mean_range
                ):
                    add(policy_violations, row.step, "exceeds_run_rank_mean_policy")

        measured[row.step] = metrics

    hard_steps = sorted(hard_failures)
    policy_steps = sorted(policy_violations)
    unknown_steps = sorted(unknown)
    event_steps = sorted(set(observations) | set(hard_steps) | set(policy_steps) | set(unknown_steps))
    if hard_steps or policy_steps:
        state = "failed"
    elif unknown_steps:
        state = "unknown"
    else:
        state = "observed_stable"
    overflow_steps = [row.step for row in logs if row.overflow]
    return {
        "state": state,
        "first_event_step": event_steps[0] if event_steps else None,
        "first_hard_failure_step": hard_steps[0] if hard_steps else None,
        "observations": observations,
        "hard_failures": hard_failures,
        "policy_violations": policy_violations,
        "unknown": unknown,
        "measured": measured,
        "overflow_rate": round(len(overflow_steps) / len(logs), 3),
    }


def rank_payload(means: Tuple[float, ...], counts: Tuple[int, ...]):
    numerators = tuple(mean * count for mean, count in zip(means, counts))
    denominators = tuple(float(count) for count in counts)
    return numerators, denominators, counts


policy = DiagnosticPolicy(
    loss_delta=1.0,
    max_grad_norm=5.0,
    lr_tolerance=0.00001,

print("first_event_step=", report["first_event_step"])
print("first_hard_failure_step=", report["first_hard_failure_step"])
print("policy_violations=", report["policy_violations"])
print("step_103_measurements=", report["measured"][103])
print("overflow_rate=", report["overflow_rate"])
```

这组构造日志中，step 103 的 loss 相对近期中位数升高约 3.96、梯度范数为 12.5、rank mean range 为 3.4，因此违反了代码里显式传入的 toy 策略；它也是第一条事件。step 104 的实际有效目标数和 loss denominator 都为 0，并出现非有限 loss/梯度，构成硬失败。step 200 的真实学习率与预期相差 `0.000165`，结合 `resumed=True` 定位到恢复后的连续性检查。没有传入相应策略时，loss 差、梯度范数、学习率差和 rank range 仍会保留为测量值，但不会被代码自动判成通用失败阈值。

## 4.18 从事故到恢复验证

训练恢复要分阶段进行：

1. 保存异常 step 前后的日志、batch、checkpoint 和环境版本。
2. 暂停扩大训练或标记受影响 checkpoint，防止污染后续实验。
3. 在单卡、固定 batch 和短窗口中复现第一次异常。
4. 对数据、mask、学习率、precision、optimizer 和分布式分别做反事实实验。
5. 选择已知正常 checkpoint 或重新生成干净状态。
6. 进行 checkpoint save/resume 连续性测试。
7. 在小规模训练和目标规模训练上分别回归。
8. 观察恢复后的 loss、有效 token、lr、overflow、rank 和资源指标。

“训练跑起来了”不是恢复验证。至少要确认新的运行没有复现原始失败样本，恢复后的 scheduler 和 optimizer 状态连续，数据版本没有混入被隔离记录，评估集和模型输出没有出现新的回归。

## 4.19 常见但危险的处理方式

### 一上来调小学习率

学习率可能确实过高，但如果真正原因是空 labels、异常 batch 或 checkpoint 恢复跳变，调小学习率只是掩盖问题。应先保存第一处分歧证据，再把学习率作为一个隔离变量实验。

### 发现 NaN 后直接重启

重启可能让曲线短暂恢复，却丢失第一次非有限值的 batch 和状态。正确做法是保留原运行、记录重启原因，并明确新运行是否从干净 checkpoint 开始。

### 只看 rank 0

rank 0 的平均 loss 可能掩盖某个 rank 的异常长样本、overflow 或通信问题。分布式日志至少要能定位到 rank、shard 和 batch。

### 只看总 loss

没有有效 label token、不同 padding 比例或不同数据切片时，总 loss 不可直接比较。应同时看有效 token、长度、来源和 mask。

### 同时改变多个变量

换数据、换精度、换 batch、调学习率和换模型一起做，无法知道哪个动作有效，也无法把结论迁移到下一次事故。

### 把梯度裁剪当作根因修复

裁剪可以限制一次危险更新，但持续触发说明训练配置或数据分布超出预期。应记录裁剪前后的梯度范数和触发比例。

## 4.20 资料与证据边界

本章的训练稳定性方法参考以下资料：

- [PyTorch autograd anomaly detection（2.15）](https://docs.pytorch.org/docs/2.15/autograd.html#anomaly-detection)说明 backward 错误的 forward traceback 和 NaN 检查行为；它增加开销，也不能替代逐边界的输入与状态检查。
- [PyTorch AMP 示例（2.15）](https://docs.pytorch.org/docs/2.15/notes/amp_examples.html)和 [`clip_grad_norm_` API（2.15）](https://docs.pytorch.org/docs/2.15/generated/torch.nn.utils.clip_grad_norm_.html)说明 unscale、梯度累积、overflow 跳步和梯度范数裁剪的公开接口；具体稳定性仍取决于模型、硬件、算子和配置。
- [PyTorch DDP 设计说明（2.15）](https://docs.pytorch.org/docs/2.15/notes/ddp.html)、[Distributed Checkpoint（2.15）](https://docs.pytorch.org/docs/2.15/distributed.checkpoint.html)与 [FSDP（2.15）](https://docs.pytorch.org/docs/2.15/fsdp.html)说明公开的梯度归约、分片和恢复边界；加载成功不等于恢复后的样本顺序和优化轨迹连续。
- [Transformers Trainer resume 文档](https://huggingface.co/docs/transformers/main_classes/trainer#resuming-training)和[恢复训练教程](https://huggingface.co/docs/transformers/trainer_recipes#resume-training)说明当前公开 API 的 optimizer、scheduler、RNG 和 data skip 行为；它们不保证自定义 dataloader、worker 随机状态和外部数据游标自动恢复。
- [Molybog 等](https://arxiv.org/html/2304.09871)、[Bai 等](https://arxiv.org/html/2506.04805v2)和[Chen 等（2026）](https://arxiv.org/abs/2610.38277)分别研究特定训练设置中的 Adam 不稳定、预条件器曲率与迟发有限精度 spike。论文结论和训练配置不直接给出目标模型的学习率、梯度阈值或 batch 处方。

官方文档能支持接口和公开行为，不能证明某个训练作业的日志、labels、rank 状态或 checkpoint 完整。训练事故结论必须绑定代码、数据、硬件、precision、world size、版本和实测回放。

## 4.21 本章小结

训练不稳定排查的核心是把一条损失曲线还原成一条有上下文的状态时间线。先找到第一次异常 step，保存它的 batch、labels、有效 token、学习率、梯度、overflow、rank 和 checkpoint；再用单变量反事实实验区分数据、mask、优化、精度、恢复和分布式原因；修复后进行 save/resume、最小训练和目标规模回归。

NaN 不是根因，loss spike 也不是根因，低 loss 更不是成功证明。只有当训练状态可观测、异常样本可回放、恢复状态可验证、指标分母清楚且失败能够进入回归集时，训练过程才从一次昂贵的长跑变成可诊断、可恢复的工程系统。
