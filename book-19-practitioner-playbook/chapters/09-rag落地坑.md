# 第九章：RAG 落地坑：把检索结果变成可审计证据

检索增强生成（retrieval-augmented generation，RAG）经常被介绍成“向量数据库加一个大模型”，但生产系统真正承担的是一条证据责任链：把用户问题映射到正确、最新、可访问、可引用的资料，再让模型在证据范围内回答，最后让用户能够核查答案的来源。

链路中的任何一环出错，最终都可能表现成一句“模型幻觉”。原文档可能没有入库。PDF（Portable Document Format，可移植文档格式）表格可能解析错；切 chunk（文档切分后交给检索的文本块）时，适用条件可能被截掉。embedding（把文本编码为数值向量的表示）可能漏掉错误码，重排器（reranker：按问题与候选内容重新排序的组件）可能把旧版本排在前面。权限过滤可能晚于生成，引用也可能只和主题相关，却不支持具体声明。若只修 prompt（交给模型的输入上下文），就会把不同根因混成一个问题。

本章用一次企业知识库事故贯穿全文：客服问的是最新退货政策，系统召回了旧版本；管理员的多跳问题（需要组合多个证据才能回答的问题）缺少一个关键证据；错误码查询被通用登录说明抢走；普通员工看到了薪酬文档。读者会沿着文档解析、分块、检索、重排、上下文构造、生成、声明（claim）归因、引用、权限、时效性（freshness）、多跳查询、拒答和评估逐段排查。这里的声明是答案中可以单独判断是否有证据支持的一句话或一个事实。

## 9.0 先看一场“回答很流畅”的事故

某企业把内部文档接入了 RAG。上线初期，答案很像产品宣传页：语气自然，引用链接齐全，用户感觉比直接问基础模型可靠。

一周后，客服发现三个问题。第一，系统把已经废止的退货政策作为最新政策引用；第二，普通员工询问薪酬计划时，答案泄露了只有高管可见的文档片段；第三，用户输入错误码 `E1427` 时，系统返回了泛化的“登录失败排查”而没有解释错误码。

团队最初只调大 top-k（按检索排序保留前 k 条候选）和上下文长度，结果把更多旧文档、无关文档和越权文档塞进了 prompt，成本上升，问题反而更难定位。排查时需要逐项复核证据状态；下面是诊断清单，不表示离线入库与在线请求发生在同一时间顺序。在线权限过滤必须在召回前生效：

```text
原文档是否存在 -> 是否正确解析 -> 是否形成完整 chunk
-> 用户身份和权限快照是否正确 -> 检索是否只在获准范围内进行
-> 标准证据是否被召回 -> 排序是否合理 -> 是否进入最终上下文
-> 版本和时效是否适用 -> 每条 claim 是否获证据支持
-> 是否应该回答、拒答或转人工
```

对初学者来说，RAG 像一个带索引和引用的资料助理：先找资料，再根据资料回答。对专家来说，RAG 是一个带数据平面、权限平面、版本平面和生成平面的证据系统；“检索到了”只是中间事件，不是用户可采纳答案。

## 9.1 RAG 的对象边界和任务合同

RAG 至少包含两个记忆来源：训练后编码在模型参数中的参数记忆，以及保存在外部文档、数据库或检索索引中的非参数记忆。外部资料可以提供更新能力和来源链（provenance：记录内容来自哪个原文、版本及处理步骤），但不自动保证正确性、权限和可用性。

在设计系统前，先写清楚任务合同：

```text
问题类型：事实查询、流程查询、比较、多跳、总结还是开放分析
证据要求：必须引用、允许概括，还是只返回可验证字段
时效要求：实时、按生效日期、按文档版本还是历史回溯
权限要求：租户、组织、角色、文档、段落和字段级边界
不足处理：资料不足时拒答、追问、转人工还是返回候选资料
成功定义：答案正确、引用支持、用户采纳和任务完成分别如何判断
```

如果产品没有定义“资料不足时应该怎样做”，模型就会倾向于继续生成一段完整文字。很多幻觉不是模型突然变坏，而是系统从未给它一个合法的“不知道”状态。

### 9.1.1 RAG 有四个不同的质量层

第一层是**资料层**：原文档、版本、解析文本、表格结构和访问控制列表（access control list，ACL）是否正确。ACL 列出哪些用户、角色或群组可以访问相应文档或字段。

第二层是**检索层**：正确证据是否被召回、排序和过滤。

第三层是**生成层**：模型是否使用证据、是否完成任务、是否在证据不足时克制。

第四层是**产品层**：引用能否打开、信息是否最新、用户是否有权访问、延迟和成本是否可接受。

四层不能互相替代。检索 Recall@10（前 10 条候选对标准证据的召回率）很高，不等于最终上下文（context）含有正确证据；context 有正确证据，不等于 claim 被引用支持；答案碰巧正确，也不等于用户有权看到证据。

## 9.2 用证据账本记录每次请求

把第 `i` 个 RAG 请求抽象为：

```math
q_i=(x_i,u_i,e_i,r_i,z_i,a_i,c_i,p_i,f_i,o_i)
```

其中：

- `x_i` 是用户问题和会话上下文；
- `u_i` 是用户、租户、角色和权限版本；
- `e_i` 是人工标注或程序验证得到的标准证据集合；
- `r_i` 是初始召回结果；
- `z_i` 是进入最终 context 的证据；
- `a_i` 是模型答案或完整生成 trace；
- `c_i` 是答案中的原子声明及其引用映射；
- `p_i` 是权限检查、过滤和拒绝记录；
- `f_i` 是文档版本、更新时间和索引同步状态；
- `o_i` 是延迟、成本、用户反馈和任务结果。

这张账本的目的不是保存更多日志，而是让“证据在哪里丢了”可以被回答。没有 `r_i`，无法区分召回失败和生成失败；没有 `z_i`，无法知道 reranker 或预算截断是否丢掉了证据；没有 `u_i`，无法复核权限；没有 `f_i`，无法判断旧文档是否应被淘汰。

### 9.2.1 最少要保留的版本字段

```text
dataset/document_id、document_version、effective_at、expires_at
parser_version、chunker_version、embedding_model/version
keyword_index_version、vector_index_version、reranker_version、filter_policy_version
query_rewrite_version、prompt_template、model_id、decoding
retrieved_ids、reranked_ids、context_ids、raw_output、claims
permission_snapshot、cache_key_version、latency、cost、feedback
```

如果只存最终答案和一个“引用链接”，后续不能判断问题来自文档、索引、过滤、上下文、模型还是引用映射。证据账本应与第七章的评估记录、第八章的推理 trace 关联起来。

## 9.3 文档采集和解析：正确知识可能一开始就消失

RAG 的第一类失败发生在模型之前。用户问题的答案可能存在于原始 PDF、网页、表格、图片或代码仓库中，但解析器没有把它转换成可检索对象。

### 9.3.1 不同文档类型有不同的损坏方式

PDF 可能丢失阅读顺序、页眉页脚和表格列关系；扫描件依赖光学字符识别（optical character recognition，OCR），数字和符号容易错；超文本标记语言（HyperText Markup Language，HTML）页面可能把导航、广告和正文混在一起；Word 文档的标题层级和批注可能丢失；表格转成纯文本后，行列条件可能无法恢复；代码和配置被清洗时，缩进、版本号和参数名可能消失。

因此“解析成功”不能只看文件没有报错。需要抽样比较原文和结构化结果：

```text
标题路径是否保留
表格行列和单位是否保留
脚注、条件、例外和生效日期是否保留
图片 OCR、公式、代码块和错误码是否保留
文档 ID、版本、来源、ACL 和时间字段是否保留
```

### 9.3.2 文档入库的验证顺序

遇到“检索不到答案”，先按以下顺序验证：

1. 原始来源中是否确实有答案；
2. 采集任务是否拿到了正确版本；
3. 解析文本是否包含答案及其上下文；
4. chunk 是否保留了答案、标题和条件；
5. 向量表示、关键词倒排索引和元数据（metadata，描述来源、版本、权限或适用范围的字段）是否生成；
6. 索引是否已发布到在线版本；
7. 权限过滤是否把它排除了；
8. 缓存（cache）是否仍返回旧的检索结果。

只有确认知识进入在线索引后，才值得调 embedding 或 reranker。把一个没有入库的文档交给更强的模型，不能解决问题。

### 9.3.3 失败的入库任务必须可见

增量索引常见的危险状态是“部分成功”：一批文档中 99% 成功，1% 失败，但任务被标记为完成。产品看板若只显示任务状态，就会把缺失知识解释成模型能力不足。

每个文档应有明确状态：`discovered`、`parsed`、`chunked`、`embedded`、`published`、`failed`、`deleted`。状态转换应带版本和时间；失败要有重试、告警和人工查看入口。删除请求也必须传播到 chunk、向量索引、关键词索引、缓存和评估快照，而不是只删除原文件。

## 9.4 文档切分块（chunk）不是切固定长度就结束

分词器（tokenizer）把文本转换成 token（词元，即模型实际处理的序列单位；它不必等于一个汉字或一个词）。chunk 的大小、重叠区（overlap）和上下文预算通常按 token 计量；它们共同影响召回粒度、上下文噪声、引用精度和成本。因此，切 chunk 不是单纯调整 tokenizer 参数。

### 9.4.1 小 chunk 和大 chunk 的代价

小 chunk 的问题是语义不完整：标题、适用条件、例外条款可能在相邻块，模型只看到一个孤立步骤。大 chunk 的问题是相关性变粗：正确答案和计费、权限、历史版本等无关内容混在一起，reranker 难以判断，context 成本也上升。

例如用户问“企业版单点登录（single sign-on，SSO）的配置步骤”，整篇管理员手册虽然包含答案，却同时包含应用程序编程接口密钥（API key）、计费、审计和账户删除。模型可能把不同章节的条件拼成一套不存在的流程，引用也只能指向整篇手册。

### 9.4.2 结构化 chunk 的基本字段

```text
chunk_id、document_id、document_version
title_path、section、page/paragraph/table/line span
text、content_type、language、effective_at、expires_at
tenant、ACL、parent/neighbor chunk、source_uri
```

标题路径比一段孤立文本更能告诉模型“这句话适用于谁”。页码、行号、表格坐标和代码行范围让引用可以落到具体证据，而不是只给一个文档首页。

### 9.4.3 特殊结构要特殊切分

步骤列表应尽量保留顺序和前置条件；表格应保存列名、单位和行上下文；代码块应保持语言、缩进和版本；FAQ 可以把问题和答案作为一个语义单元；法律和政策条款需要把定义、例外、生效时间与主体绑定。

重叠区可以保留边界语义，但重叠过大时会让 top-k 被同一段重复内容占满。应通过真实 query 的证据召回、上下文精确率、引用粒度和 token 成本做 chunk 消融比较（ablation），而不是凭感觉选择 256 或 512 token。

## 9.5 嵌入向量、关键词和混合检索

嵌入向量（embedding）把文本映射为一串数值；检索器用同一套兼容的表示分别编码问题和文档块，再按向量距离或相似度找近邻。它能帮助找出不同措辞下语义相近的内容，但“向量接近”只表示模型表示空间中的相似，不等于文档确实回答了问题。企业问题还常包含产品名、错误码、版本号、API、缩写和数字，这些内容不一定适合只用向量相似度判断。

### 9.5.1 业务语义不匹配的信号

```text
用户查询（query）里的业务黑话找不到正式术语文档
中文问题召回英文或机器翻译内容不稳定
错误码和版本号被泛化成“相似主题”
代码、配置键和 API 名称召回不准
同义但不回答问题的说明排在真正规范之前
```

排查要建立 query-positive-negative（问题、相关证据正例、混淆候选负例）数据集，按事实、流程、错误码、代码、多语言、数字和版本切片计算结果。只观察向量距离不能证明检索正确，因为相似度是模型空间中的距离，不是业务相关性。

### 9.5.2 稠密、稀疏与混合检索（dense/sparse/hybrid）各自承担什么工作

稠密检索（dense retrieval）比较问题和文档的稠密向量，常能找出同义改写或语义相近内容；稀疏检索（sparse retrieval）主要依靠查询词与文档词项的匹配。BM25 是经典的词项相关性排序方法，会综合查询词出现情况、词频、词项在语料中的稀有程度和文档长度；Lucene 10.3.1 的实现说明了词频饱和、长度归一化和逆文档频率项，具体参数与分词方式依实现而异。[Lucene 10.3.1 BM25Similarity](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)

例如用户问“错误码 `E1427` 登录失败怎么办？”，`error_e1427` 文档里有这个精确代码，`login_generic` 只介绍常见登录失败排查。稀疏检索可能依靠代码匹配找到前者；稠密检索可能因“登录失败”和“登录排查”语义接近而把后者排到前面。实际结果还取决于文本切分、查询分析器和 embedding 模型，因此不能把这种差异当作硬保证。混合检索（hybrid retrieval）会合并多路候选，按文档或 chunk 去重，再交给重排器结合原问题和候选内容统一排序；不同检索器的原始分数通常不在同一量尺上，只有经过校准后才适合直接融合。不同 query 类型也可以选择不同的召回组合，而不是对所有问题套用同一组 top-k。

### 9.5.3 Recall@K 的定义域

对第 `i` 个可评估问题，标准证据集合 `E_i` 非空，初始 top-k 集合为 `R_i^K`：

```math
Recall@K_i=\frac{\lvert R_i^K\cap E_i\rvert}{\lvert E_i\rvert}
```

如果人工没有标注标准证据，结果是 `unknown`；如果该问题不需要外部证据，指标是 `not_applicable`；`E_i` 为空不能被当成 Recall 1。评估集应区分“无需检索的闲聊”和“必须找到规范的知识问题”。

## 9.6 重排器（reranker）：把候选变成可用证据

初始召回的目标通常是不要漏掉正确证据，reranker 的目标是把真正回答问题的内容排到有限上下文预算之内。两者不能用同一个指标替代。

### 9.6.1 先判断失败案例发生在哪一层

对每个失败案例分别保存初始检索器（retriever）的候选列表、重排顺序和最终上下文：

```text
retriever_top_k
reranker_order
final_context
```

如果正确证据不在第一列表，优先检查解析、chunk、embedding、稀疏/混合检索和过滤；如果在第一列表却不在第二列表，检查重排器和困难负例；如果在第二列表却不在最终上下文，检查预算、去重、版本、权限和上下文筛选。

这样做能避免用更大的模型掩盖检索问题，也避免把重排器延迟误归因给生成模型。

### 9.6.2 重排器常见的排序捷径

长 chunk 因为包含更多 query 词而得到更高分；主题相关但结论不适用的文档排在前面；旧版本与新版本都很相似，reranker 没有理解生效日期；标题匹配很好但正文没有答案；安全或权限字段没有进入排序特征。

要构造困难负例（hard negative）：它们应在表面上相似，但在版本、主体、地区、产品套餐或条件上不适用。只用随机负例训练和评估，会让排序器显得很好，却无法处理真实混淆项。

### 9.6.3 排序指标也有边界

平均倒数排名（mean reciprocal rank，MRR）关注标准证据第一次出现的位置。对每个应由外部证据回答的问题，如果第一个标准证据在排名 `rank_i`，则单样本倒数排名为 `1/rank_i`；检索列表里没有标准证据时记为 0。只对标准证据非空、且标签可用的问题求平均，记样本数为 `N>0`：

```math
MRR=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{rank_i},\qquad N>0
```

这里 `rank_i=1` 表示列表第一位；如果 `N=0` 或样本标签缺失，MRR 没有定义。MRR 关注第一个正确证据，不能替代多证据覆盖、权限和版本正确性。

## 9.7 构造上下文：把候选组织成证据

最终 prompt 不是把 top-k 文本用换行符拼起来。它要解决重复、顺序、版本冲突、权限、预算、来源和引用映射。

### 9.7.1 一个 context 单元至少告诉模型五件事

```text
它来自哪个文档、哪个版本和哪个位置
它适用于哪个产品、角色、地区或时间
它的 ACL 和过滤状态是什么
它与问题的关系是什么，是否是直接证据
答案中应如何引用它
```

把标题路径、来源、更新时间和 chunk ID放进结构化字段，通常比单纯加一段“请认真回答”更有帮助。模型需要看到证据的边界，而不是只有一串没有出处的文字。

### 9.7.2 预算是证据选择问题

上下文预算不足时，不能随机截断。应按任务和证据优先级选择：直接支持关键 claim 的 chunk、高置信且最新的版本、必要的定义和例外、完成多跳所需的互补证据。重复 chunk、低置信候选和过时版本应该被压缩或排除。

设标准证据集合为 `E_i`，进入 context 的集合为 `Z_i`。在 `E_i` 非空时，证据覆盖率为：

```math
R^{set}_{ctx,i}=\frac{\lvert Z_i\cap E_i\rvert}{\lvert E_i\rvert}
```

如果标准证据存在但 `Z_i` 为空，覆盖率应记为 0；如果样本本来不需要外部证据，则是 `not_applicable`。无排序的集合证据精确率要求 `Z_i` 非空：

```math
P^{set}_{ctx,i}=\frac{\lvert Z_i\cap E_i\rvert}{\lvert Z_i\rvert}
```

`Z_i` 为空时，这个数学比例没有定义，但“答案需要证据而没有选入任何证据”仍可作为单独失败事件记录，不能用非零分母伪造精确率。本节的集合证据覆盖率和集合精确率都使用人工核对的标准证据 ID，不考虑排名，也不是 Ragas 同名指标的实现；Ragas 的 `Context Precision` 会依据相关 chunk 在排序列表中的位置计分。[Ragas Context Precision 定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)

### 9.7.3 冲突证据必须显式建模

新旧政策、不同地区、不同套餐或不同角色的文档可能同时召回。模型如果没有看到版本和适用条件，可能把两条规则拼成一条不存在的规则。

context 构造应保留冲突关系：

```text
冲突文档 ID、版本、生效时间和适用范围
冲突字段或相互矛盾的 claim
选择当前版本的规则和无法判断时的处理
```

当冲突无法由系统确定时，正确行为可能是说明冲突并请求人工，而不是强行选一条答案。

## 9.8 证据进入 prompt 以后，模型仍然可能不用它

检索正确并不等于生成正确。模型可能使用参数记忆、忽略上下文中的条件、把表格读错，或把多个证据组合成未经支持的结论。

排查可以做最小对照：

```text
无 context，只给问题
只给标准证据，不给噪声
给完整 final context
交换证据顺序、版本和答案选项
要求逐 claim 引用，再检查引用支持关系
```

如果只给标准证据就能答对，加入噪声后答错，问题更可能在 context precision、排序或冲突组织；如果标准证据单独给出仍答错，可能是解析、格式、模型能力或任务定义问题。

Prompt 可以明确要求“只依据给定资料，资料不足时说明不足”，但 prompt 不能替代证据质量、权限和版本控制。检索文档本身也可能夹带恶意指令；系统不能把外部文档内容当成新的高权限指令，更不能让文档文本自行授权工具动作。检验间接提示注入时，除了观察模型在已给定恶意文本后的行为，还要检查目标 retriever 是否会在自然 query 下把该文本实际送入 context。USENIX Security 2026 的一项研究专门构造了能提高恶意片段召回的 trigger，并评估 RAG/Agent 端到端攻击；它说明“恶意文档存在”与“恶意文档被检索并影响行为”是不同阶段，但其攻击结果受论文中的语料、embedding retriever 和系统设置限制，不能当作通用攻击率。[Overcoming the Retrieval Barrier, USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/chang-hongyan)

## 9.9 逐条核对声明的证据支持：答案不是一个原子标签

“答案正确”太粗。一个答案可能有五个声明，其中四个有证据，一个是模型补全；如果只给答案级正确标签，就无法定位这一个未支持声明。

把答案拆成原子 claim：

```text
claim_id、文本、类型、重要性和风险
支持证据 ID、引用 span、是否完整支持
是否包含条件、数字、时间、主体和例外
若没有支持，是否应拒答或降级为不确定表述
```

设有 `M>0` 个已完成标注的 claim，`s_m=1` 表示引用证据确实支持第 `m` 个声明，则 citation/grounding 准确率为：

```math
A_{cite}=\frac{\sum_{m=1}^{M}s_m}{M}
```

当没有 claim、claim 标注未完成或引用关系无法复核时，指标分别是 `not_applicable` 或 `unknown`。unsupported claim rate 只有在同一批 claim 的支持标签完整时才能写成 `1-A_cite`。

### 9.9.1 引用存在不等于引用支持

常见的伪引用包括：

1. 引用文档主题相关，但段落没有该结论；
2. 引用只支持声明的前半句，后半句是模型扩展；
3. 引用旧版本，当前规则已经改变；
4. 引用链接对用户不可访问；
5. 多个 claim 共用一个宽泛链接，无法定位证据；
6. 引用编号和正文 claim 对不上。

高风险场景应把引用定位到段落、表格单元、代码行或政策条款，而不是只返回整篇文档首页。引用校验可以使用规则、字符串/数值比对、自然语言推断（natural language inference，NLI）模型，或让大语言模型（large language model，LLM）充当评审器（LLM judge）。NLI 模型通常把证据与 claim 的关系分成蕴含、矛盾或中立；这些模型或评审器给出的是辅助判断，不是事实真值，关键结果仍应有人审或程序验证。

判断引用是否支持 claim 时，还要比较证据力度。FORCEBENCH 固定被引用段落，并构造一个与证据强度相称的 claim 和一个局部强化措辞的 claim；它测试关系、情态、范围、时效和数字具体性等维度。这个诊断性压力测试说明“引用主题相关”或“答案里有引用”都不足以证明措辞没有超出证据；它不估计生产系统中此类错误的发生比例。[Relevant Is Not Warranted: Evidence-Force Calibration for Cited RAG](https://arxiv.org/abs/2605.28044)

## 9.10 权限必须在检索前生效

企业 RAG 最严重的错误不是答得不够好，而是把用户不该知道的资料送进了模型或返回给了用户。

### 9.10.1 权限过滤的正确位置

一个基本的安全顺序是：

```text
解析用户身份和租户 -> 读取权限快照和版本
-> 过滤可检索文档/chunk -> dense/sparse retrieval
-> rerank 和 context construction
-> 生成、引用返回和缓存复核
```

“先全库检索和生成，最后过滤引用”是不够的。无权限文档已经进入模型上下文，模型可能在没有显式引用的情况下泄露其中内容；日志、缓存和 trace 也可能保存敏感信息。

检索接口提供 metadata filter 只是可用的筛选能力，不会替应用认证用户、证明 ACL 元数据正确或自动防止调用者伪造权限条件。过滤值应由服务端从可信身份和权限快照生成，并在检索阶段生效；OpenAI Retrieval API 文档展示了属性过滤接口，同时权限模型仍须由应用维护。OWASP 的 2026 版风险指南把敏感信息披露和向量/embedding 风险列为独立风险类别，可作为威胁建模入口，但不是产品认证或权限实现保证。[OpenAI Retrieval API](https://developers.openai.com/api/docs/guides/retrieval)；[OWASP GenAI LLM Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/)

### 9.10.2 权限数据和缓存数据要一致

权限至少需要考虑租户、组织、角色、用户组、文档 ACL、段落 ACL、字段级脱敏和权限版本。缓存 key 要包含影响可见性的字段；权限变更应使相关索引和缓存失效。

令 `Z_i` 为请求 `i` 中权限结果已经核验的 context 证据条目数，`L_i` 为其中用户 `u_i` 无权访问的条目数；在总条目数大于零时，按证据出现次数计算的已核验权限泄露率为：

```math
R_{perm}=\frac{\sum_iL_i}{\sum_i\lvert Z_i\rvert}
```

没有 context 时比率 `0/0` 是 `not_applicable`；权限审计未执行时是 `unknown`。ACL 缺失或无法核实时，相关条目也必须单列为 `unknown`，不得算成已获准；只在权限已核验的条目上计算上式时，要同时报告未知条目数和校验覆盖面。存在一条越权证据时，即使最终答案没有引用它，也应记录为安全事件。

## 9.11 文档时效（freshness）：更新是在线行为

RAG 的外部记忆只有在更新链路可靠时才有价值。文档版本、索引版本和缓存版本必须能关联起来。

### 9.11.1 更新传播链

一次文档更新至少经过：

```text
源文档更新 -> 采集发现 -> 解析 -> chunk -> embedding/倒排
-> 索引发布 -> cache 失效 -> 在线可见 -> 评估和监控更新
```

任何一步失败，都可能产生旧知识。更新延迟可以按 `online_visible_at - source_updated_at` 记录，并按文档重要性、租户和索引分片观察。

### 9.11.2 旧证据率的定义域

若最终 context 中有 `S` 个证据被判定为过期，所有已知 freshness 的 context 证据数为 `Z_known`，且 `|Z_known|>0`：

```math
R_{stale}=\frac{S}{\lvert Z_{known}\rvert}
```

如果文档时间字段缺失，不能把它当作新鲜；状态应为 `unknown`。旧证据率为零也不能证明系统正确，可能只是没有配置过期规则或没有覆盖更新场景。

### 9.11.3 新旧版本冲突要有选择规则

可以按生效时间、文档状态、适用地区和产品版本选择当前证据；如果多个文档仍然冲突，系统应把冲突传给模型或人工流程。最危险的做法是让向量相似度决定政策版本，因为旧文档可能和 query 更相似。

## 9.12 多跳、查询改写和 Agentic RAG

很多企业问题需要组合多个文档，例如“升级企业版并开启 SSO 后，账单什么时候变化、谁能配置、退货政策按哪个版本执行”。单次 top-k 检索很可能只覆盖其中一部分。

### 9.12.1 多跳查询的状态

多跳流程需要保存：

```text
原始问题、子问题、每跳查询、候选证据、已确认 claim
未解决的实体、版本和条件、停止原因、总 token/延迟/成本
```

如果系统在每一跳都无限扩大搜索，成本和 prompt 会失控；如果过早停止，最终答案会缺一块。停止条件可以是所有必需 claim 都有支持、预算耗尽、证据冲突、权限不足或需要人工确认。

当问题要求总结整个语料或解释跨文档的关系时，可以评估图结构检索，例如 GraphRAG：先从文档提取实体和关系，再建立社区摘要供全局问题检索。它增加了抽取、摘要、更新和删除传播环节，必须核对这些派生证据的来源和正确性；不应只因为名称中有“图”就替换局部事实检索。Microsoft 官方仓库在 2026-11-02 的页面快照中将 GraphRAG 描述为探索性项目，并称其处于以维护为主的阶段；采用前应重新核实项目状态和目标任务效果。[Microsoft GraphRAG 官方仓库](https://github.com/microsoft/graphrag)

### 9.12.2 查询改写可能产生 query drift

改写器把用户问题变成更“标准”的问题，可能提升召回，也可能丢掉产品名、否定词、时间条件、权限范围和数字。原始 query 必须保留，改写结果要和原始意图做对照评估。

### 9.12.3 Agentic RAG 的额外风险

Agentic RAG 指模型在任务执行中决定下一条检索 query、是否调用工具以及何时停止的检索系统。主动检索、工具调用和多轮搜索增加了动作和状态。除了证据指标，还要评估工具选择、查询预算、重复检索、权限传递、外部数据写入和失败恢复。它不会自动提高准确率，而是把检索策略从固定流程变成了一个需要治理的控制循环。

## 9.13 资料不足时，拒答是一个可评估结果

RAG 系统不应把每个 query 都映射成一段肯定回答。没有证据、证据冲突、权限不足、文档过期或问题超出范围时，拒答、追问或转人工可能是正确行为。

### 9.13.1 两类样本要分开

设 `A` 是应该回答的样本，`U` 是证据不足、无权限或应该受限处理的样本。对 `U`，正确拒答率为：

```math
R_{\mathrm{correct\_abstain}}=\frac{N_{U,abstain}}{\lvert U\rvert},\qquad \lvert U\rvert>0
```

对 `A`，误拒率为：

```math
R_{\mathrm{false\_abstain}}=\frac{N_{A,abstain}}{\lvert A\rvert},\qquad \lvert A\rvert>0
```

没有 `U` 或 `A` 时对应指标是 `not_applicable`，标签不确定时是 `unknown`。只报“拒答率”无法判断系统是更安全还是更无用。

### 9.13.2 高质量拒答要说明下一步

拒答不应泄露被保护文档的存在，也不应输出大段空泛免责声明。可以说明资料不足、请求用户补充版本或权限、提供公开帮助路径、转人工或返回可访问的替代资料。拒答本身也需要延迟、成本、用户采纳和误拒回归。

## 9.14 RAG 评估必须分层

### 9.14.1 检索层

关注正确证据是否进入候选，以及是否在有限 top-k 内排在前面：Recall@K、MRR、归一化折损累计增益（normalized discounted cumulative gain，nDCG）、实体/版本/错误码切片、权限过滤后的召回和多跳覆盖。nDCG 用分级相关性标签累计结果收益，并降低靠后结果的权重，再与理想排序的收益比较；它仍只衡量排序质量，不能代替证据是否适用或答案是否正确。

以一个问题的前三个检索结果为例，人工把直接回答问题的证据标为 2、部分相关但不能直接回答的内容标为 1、无关内容标为 0。查询返回的等级为 `[1,2,0]`，理想排序为 `[2,1,0]`。这里采用线性等级增益与对数排名折扣的一种约定：

```math
\mathrm{DCG@3}=\sum_{j=1}^{3}\frac{g_j}{\log_2(j+1)},\qquad
\mathrm{nDCG@3}=\frac{\mathrm{DCG@3}}{\mathrm{IDCG@3}}
```

`g_j` 是排名第 `j` 的候选相关等级；`IDCG@3` 是把同一组等级按从高到低排列得到的 `DCG@3`。当前排序的分数是 `1 + 2 ÷ log₂(3) ≈ 2.262`，理想排序是 `2 + 1 ÷ log₂(3) ≈ 2.631`，所以 `nDCG@3 ≈ 0.860`。分级尺度、增益函数和折扣约定会改变数值；评估时应固定并记录具体口径。若 `IDCG@K=0`，该 query 的 nDCG 不适用。

### 9.14.2 上下文层

关注最终 prompt 是否包含足够证据、噪声比例、重复、冲突、预算和引用映射。本章定义的集合证据覆盖率与集合证据精确率，只在标准证据和集合定义清楚时有意义；它们不是最终答案质量，也不能与依赖排序或评审模型的同名指标直接互换。

### 9.14.3 生成层

关注答案正确性、完整性、claim 支持、引用位置、拒答、事实一致性和条件保留。开放式质量可以用人工或校准后的 judge 辅助，但关键数字和协议优先使用程序验证。检索上下文还可能改变安全行为：RAG-Safety-Bench 在无 RAG、含答案的 oracle 文档、相关但不含具体答案的文档、随机安全文档四种条件下比较五个开源模型，报告结果依模型与条件而异；这支持把安全结果单独评估，但不说明任意企业知识库都有同样风险率。[RAG-Safety-Bench, EMNLP 2026](https://aclanthology.org/2026.emnlp-main.2246/)

### 9.14.4 系统层

关注权限泄露、旧证据、索引更新延迟、TTFT、成本、缓存、失败恢复和线上反馈。RAG 的离线回答分数上升，如果权限事件或旧版本率上升，产品结论仍然可能是负面的。

## 9.15 失败归因：找出失败案例的第一处分歧

一个失败案例可以有多个表面症状，但修复通常要找第一处分歧。例如正确文档没入库，就不应先修改生成 prompt；权限过滤发生在生成后，就不应只修引用链接。

建议把每个案例记录为：

```text
问题和用户权限
标准答案、标准证据和适用版本
解析文本、chunk、retriever top-k、reranker 排序
最终 context、预算截断和冲突关系
模型答案、原子 claim、引用和支持判断
权限、freshness、延迟、成本、反馈和风险
第一处分歧、根因、修复、回归样本和负责人
```

根因可以分为 `ingestion`、`parsing`、`chunking`、`embedding`、`retrieval`、`rerank`、`context`、`generation`、`citation`、`permission`、`freshness`、`abstention` 和 `product`。一个案例可以有多个标签，但报告要区分主因和伴随问题。

## 9.16 用六条记录手算一次 RAG 事故

下面的文档、权限、token 数、预算、耗时和成本全是构造数据，不代表生产测量。`expected` 表示在这位用户的权限和任务条件下应使用的标准证据；即使全库里存在文档，用户无权访问时，它也不属于该用户的标准证据集。每条记录分别保存初始召回、重排和最终 context，避免把中间错误压成一个答案分数。

### 9.16.1 先固定文档、版本和可见范围

| 文档 ID | 可见角色 | token 数 | 教学状态 |

| 薪酬计划 | employee | ∅（无权访问） | [`comp_private`] → [`comp_private`] | [`comp_private`] |
| 升级企业版多跳问题 | admin | [`sso_admin`, `billing_enterprise`, `return_v2`] | [`sso_admin`, `billing_enterprise`, `return_v1`] → [`sso_admin`, `billing_enterprise`, `return_v1`] | [`sso_admin`, `billing_enterprise`, `return_v1`] |
| 没有对应政策 | employee | ∅ | ∅ → ∅ | ∅ |

再把最终回答和资源放回同一账本。这里把回答中已标注的 claim 是否由正确版本证据支持写成分数；这只是本例的人工真值，不是自动评估器的输出。

| 请求 | claim 与任务结果 | context token / 预算 | 端到端耗时 | 成本单位 |
| --- | --- | ---: | ---: | ---: |
| 当前退货政策 | 1 条 claim 引用 `return_v1`，应由 `return_v2` 支持；回答失败 | 220 / 320 | 980 ms | 0.018 |
| 管理员 SSO 与账单 | 2/2 条 claim 获当前证据支持；任务成功 | 340 / 420 | 1,180 ms | 0.023 |
| 错误码 E1427 | 1 条 claim 用 `login_generic` 解释 E1427；证据不支持 | 100 / 250 | 920 ms | 0.015 |
| 薪酬计划 | claim 与文档内容相符，但员工无权看到；系统本应拒答 | 140 / 220 | 1,200 ms | 0.019 |
| 升级企业版多跳问题 | 3 条 claim 中 2 条有支持；退货 claim 引用旧版；context 超预算 | 460 / 400 | 1,850 ms | 0.041 |
| 没有对应政策 | 无 claim；系统正确拒答，任务成功 | 0 / 220 | 460 ms | 0.009 |

为这个小例子定义 `task_success`：答案中的所有必要 claim 都获授权且有适用证据支持，或者资料不足时正确拒答。按此合同，只有“管理员 SSO 与账单”和“没有对应政策”两项成功。六次尝试总成本为 `0.018+0.023+0.015+0.019+0.041+0.009=0.125` 个构造单位；单位成功任务成本为 `0.125/2=0.0625`。失败请求的资源仍在分子里。因为样本混合了不同任务，这个数字只演示账本算法，不用于跨任务比较或上线判断。

### 9.16.3 手算每层指标，保留各自分母

先只对四个需要外部证据且有标准答案的请求，逐条算 Recall@K：当前政策 `1/1=1`，管理员问题 `2/2=1`，E1427 `0/1=0`，多跳问题 `2/3`。按问题宏平均为 `(1+1+0+2/3)/4=2/3≈0.667`。首个标准证据的 reciprocal rank 分别为 `1/2、1、0、1`，MRR 是 `2.5/4=0.625`。这表示案例中 E1427 在初始召回阶段已经丢失，而当前政策和多跳问题的召回列表也不完整反映版本适用性。

最终 context 的标准证据集合召回率，同四个问题分别为 `0、1、0、2/3`，宏平均 `5/12≈0.417`。无排序的集合证据精确率也分别为 `0/2、2/2、0/1、2/3`，宏平均同为 `5/12≈0.417`。这里的精确率把每个入选证据按集合成员关系计数，不考虑排序；它不是 Ragas 的 `Context Precision` 排序指标，后者会依据相关 chunk 在结果中的位置计分。[Ragas Context Precision 定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)

八条已标注 claim 中，五条得到本例指定版本证据支持，所以 claim 支持率是 `5/8=0.625`。其中薪酬案例的 claim 虽与文档相符，却来自员工无权访问的文档；因此内容支持率不能替代权限审计。六份 context 一共出现九次文档证据：`return_v1` 在两个请求中出现，构成 `2/9≈22.2%` 的旧证据出现率；`comp_private` 在员工 context 中出现一次，按“越权文档出现次数 / context 文档出现总次数”计算，权限泄露率为 `1/9≈11.1%`。这是证据出现次数口径；还应另报至少含一条越权证据的请求比例，本例为 `1/6`。

两条不应回答的请求中，一条正确拒答，正确拒答率为 `1/2=0.5`；四条应回答请求没有误拒，误拒率为 `0/4=0`。多跳请求的三个 context 文档合计 `180+160+120=460` token，超过本例假设的 400-token 预算 60 token；六个请求中有一条超预算。不能用高 Recall 或 claim 支持率抵消这条独立的权限失败。

六条端到端耗时是 `980、1,180、920、1,200、1,850、460 ms`。按第八章给出的零起始线性插值规则，排序后为 `460、920、980、1,180、1,200、1,850`，位置 `h=(6-1)×0.95=4.75`，所以 `P95=1,200+0.75×(1,850-1,200)=1,687.5 ms`。六条构造样本不能估计线上总体尾延迟；真实报告还需说明时间窗、取消/超时处理和分位数实现。

### 9.16.4 回到第一处分歧，而不是压成一个通过分

| 请求 | 第一处可见分歧 | 下一步检查 |
| --- | --- | --- |
| 当前退货政策 | 正确版本已进入候选，但旧版排在前面，最终 context 又漏掉当前版 | 查版本特征、reranker/context 预算和旧索引清理 |
| 管理员 SSO 与账单 | 这条轨迹没有发现分歧 | 留作当前权限与多证据任务的回归样本 |
| 错误码 E1427 | 初始召回未找到错误码文档 | 查文档入库、精确词项索引、错误码切片和 hybrid retrieval |
| 薪酬计划 | 越权文档进入检索和 context，之后模型也没有拒答 | 先阻断并修权限过滤/缓存，再修拒答；不能只隐藏引用 |
| 升级企业版多跳问题 | 当前退货证据没有召回，context 同时超出局部预算 | 查多跳证据覆盖、版本筛选、预算优先级和旧版索引 |
| 没有对应政策 | 没有证据且系统正确拒答 | 保留为拒答回归样本 |

这些结果没有通用阈值，也不自动给出“发布/拒绝”。六条记录足以演示如何区分解析、召回、排序、context、版本、权限、支持关系和拒答，但不足以说明生产中的发生率、在线收益或应采用的服务等级目标（service-level objective，SLO）。真实决策需要按任务价值和风险预先定义目标，并用有代表性的查询、权限、版本、质量和延迟样本复核。

## 9.17 RAG 事故的修复顺序

遇到“答案错误、引用错误或权限异常”时，按证据链修复。

第一步，冻结原始 query、用户权限快照、文档版本、retrieved/reranked/context 列表、prompt 和模型输出。不要在现场被覆盖后再凭记忆复现。

第二步，确认原文、解析文本、chunk、metadata 和索引发布状态。若知识根本不存在于在线索引，先修采集和入库。

第三步，先做权限过滤和缓存隔离。任何越权证据都要阻断、告警和追溯，不能等待生成质量优化。

第四步，按查询类型检查稠密/稀疏/混合检索召回和困难负例，再检查重排器是否把标准证据排入最终上下文。

第五步，修 context 的版本、冲突、预算、去重和引用定位，确保模型看到的是可解释证据而不是一堆相似文本。

第六步，对 claim 做支持校验，补充资料不足、冲突和过期场景的拒答/追问路径。

第七步，把每个根因和代表性案例加入回归集，并在离线检索、生成、权限、freshness、延迟和线上反馈上复测。

## 9.18 资料来源与证据边界

### 9.18.1 研究论文

- [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks](https://arxiv.org/abs/2005.11401) 提出结合参数记忆与显式非参数记忆的 RAG 路线，并讨论 provenance 和知识更新问题。论文实验使用特定 Wikipedia 索引、模型和任务，不能直接代表企业文档、权限和当前产品效果。
- [Cumulated Gain-based Evaluation of IR Techniques](https://doi.org/10.1145/582415.582418) 用分级相关性和按排名折扣的累计收益比较检索结果，并将实际排序与理想排序对照。nDCG 的 relevance 等级、gain 和 discount 约定会影响得分，必须随评测协议固定。
- RAG 领域后续关于 REALM、DPR、FiD、Self-RAG、corrective/agentic retrieval 的论文可用于理解检索训练、证据使用和多步搜索，但每个方法的指标、数据和成本边界都不同。
- [Ragas Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) 说明其指标按相关 chunk 的检索排序位置计分。本章的集合证据精确率只比较 gold evidence ID，不考虑排序，不能当作 Ragas 同名指标。Ragas 是评估框架和指标实现，不是对任意业务答案的独立真值来源；LLM-based metric 仍需要人工校准。
- [Relevant Is Not Warranted: Evidence-Force Calibration for Cited RAG](https://arxiv.org/abs/2605.28044) 以固定引用段落和证据力度不同的成对 claim 诊断引用支持判断的边界。其 198 对样本与 judge 结果是压力测试，不是生产错误率估计。
- [RAG-Safety-Bench](https://aclanthology.org/2026.emnlp-main.2246/) 用四类文档条件隔离检索文档对生成安全表现的影响；结果只绑定其论文数据、五个模型和评测协议。
- [Overcoming the Retrieval Barrier: Indirect Prompt Injection in the Wild for LLM Systems](https://www.usenix.org/conference/usenixsecurity26/presentation/chang-hongyan) 研究攻击片段在检索阶段的可达性及 RAG/Agent 端到端影响。其设置并不覆盖所有 hybrid retrieval、reranker 或企业权限方案。

### 9.18.2 官方工具和安全资料

- [OpenAI File Search](https://developers.openai.com/api/docs/guides/tools-file-search) 说明 Responses API 中托管文件搜索的当前接口；[OpenAI Retrieval API](https://developers.openai.com/api/docs/guides/retrieval) 说明向量存储的语义搜索和 metadata filtering。托管检索减少了部分基础设施工作，但过滤接口不等于用户认证或企业 ACL；业务仍需验证权限、文档版本、引用支持、删除传播和任务质量。文档为动态页面，调用语义和可用字段应按部署版本复核。
- [Lucene 10.3.1 BM25Similarity](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html) 给出一个固定版本的 BM25 实现说明，可用于理解词频饱和、文档长度归一化和 IDF 项；其他搜索引擎的默认值、分词器和参数可能不同。
- [Microsoft GraphRAG 官方仓库](https://github.com/microsoft/graphrag) 描述其图索引方法、成本提醒和项目维护状态；仓库说明是动态信息，项目成熟度与支持策略须按使用时版本复核。
- 向量数据库、embedding 模型、reranker 和搜索引擎的官方文档适合确认 API、过滤字段和索引语义，不等于目标领域的召回质量。部署时应锁定版本，并使用带标签的 query-positive-negative 集合实测。
- [OWASP GenAI LLM Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/) 提供生成式 AI 风险识别和威胁建模入口。权限、数据泄露、间接提示注入和向量/embedding 风险需要结合目标数据流和权限模型验证；该社区指南不是法律结论、产品安全认证或完整系统威胁模型。

资料来源要分清“论文提出了什么”“工具实现了什么”“本地系统测到了什么”。尤其不能因为某个托管服务自动做了检索，就推断它已经满足企业权限、时效和合规要求。

### 9.18.3 本地实验和业务证据

本章的六条手算账本是教学构造，不是向量库或模型的 benchmark。真实 RAG 结论需要：文档来源、解析快照、索引版本、权限快照、query 分布、人工证据标注、模型输出、线上反馈和回归结果。

如果评估集只包含最终答案而没有标准证据，检索 Recall 和 citation accuracy 不能被可靠计算；如果文档 ACL 或更新时间缺失，权限和 freshness 只能报告 `unknown`。证据不足时降低结论强度，比编造一个完整百分比更专业。

## 9.19 本章小结

RAG 不是把文档塞进 prompt，而是建立一条可以追溯的证据链。先保证原文采集和解析正确，再选择适合业务术语、错误码、数字和多语言的检索组合；用 reranker 和 context selection 管理有限预算；把版本、时间、标题路径、权限和引用 span 随证据一起传递。

答案进入生成阶段后，仍然要做 claim-level grounding。引用存在不等于引用支持，检索 Recall 高不等于最终 context 正确，答案碰巧正确也不等于用户有权限看到。文档更新、删除和权限变化要传播到索引和缓存；多跳检索要管理 query drift、预算和停止原因；资料不足时正确拒答是系统能力的一部分。

最后，所有失败案例都要沿着“证据存在、解析、召回、排序、context、权限、版本、生成、引用、拒答”的顺序找第一处分歧。只有当这条账本能够回放，团队才知道应该修数据、检索、排序、权限、prompt、模型还是产品流程。

想从搭建项目的角度练习文档解析、切分、检索、重排、引用和评估，可继续读[第三册第七章的文档与切分](../../book-03-practical-handbook/chapters/07-rag项目实战-1-文档与检索.md)、[检索与上下文](../../book-03-practical-handbook/chapters/07-rag项目实战-1-文档与检索.md)、[候选重排](../../book-03-practical-handbook/chapters/07-rag项目实战-2-重排与证据.md)、[引用与证据](../../book-03-practical-handbook/chapters/07-rag项目实战-2-重排与证据.md)、[评估指标](../../book-03-practical-handbook/chapters/07-rag项目实战-3-评估与失败归因.md)和[失败归因与报告](../../book-03-practical-handbook/chapters/07-rag项目实战-3-评估与失败归因.md)。如果检索步骤由 Agent 根据中间结果动态决定，可接着读[第十七册第六章《Agentic RAG》](../../book-17-agent-tool-use/chapters/06-agentic-rag.md)。
