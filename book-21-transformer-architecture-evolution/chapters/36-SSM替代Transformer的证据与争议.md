# 第三十六章：SSM 会不会替代 Transformer：证据、争议与面试回答

## 36.1 这是一个开放问题，不是二选一

“SSM 会不会替代 Transformer”常被当作观点题，但严谨回答必须先限定：替代的是哪一层、哪种 workload、哪种模型规模、哪种服务目标，还是整个通用 LLM 生态。更现实的可能性包括：SSM 在流式长序列中占优势；Transformer 保留 global reader；二者组成 hybrid；不同请求由路由器选择不同 backbone。

## 36.2 先定义证据层级

可以把结论按证据分层：

1. **数学证据**：递归/卷积的复杂度、状态大小、稳定性推导。
2. **kernel 证据**：在明确 GPU、dtype、batch、长度和 baseline 下的 profile。
3. **模型证据**：同参数/训练 token/数据下的任务结果。
4. **系统证据**：真实请求的 TTFT、TPOT、p99、显存、恢复和单位成功成本。
5. **产品证据**：上线后的可用性、故障、生态、迭代和维护成本。

低层证据不能自动推出高层结论。数学线性不等于 GPU 快，单个 benchmark 不等于通用能力，产品页面的“long context”也不等于精确检索。

## 36.3 公平比较的实验矩阵

比较 SSM 和 Transformer 至少要固定：

~~~text
参数量 / 训练 token / 数据 mixture / tokenizer / context
学习率和 batch / 后训练 / 量化 / GPU / kernel / prompt
~~~

任务至少分为局部预测、长距复制、多证据合并、冲突消解、ICL、工具调用、流式分类和长输出 decode。系统指标和质量指标分开报告，避免用质量小幅下降换来的吞吐提升被无条件接受。

## 36.4 关键任务：精确证据与状态记忆

对于一个需要从长文档中恢复罕见数字的任务，建立如下 probe：在位置 p 写入数字，加入不同长度干扰，末尾询问数字；再加入第二个相似实体和冲突版本。记录：

~~~math
R(p,L)=\Pr[\text{answer exact}\mid\text{position }p,\text{length }L]
~~~

绘制位置/长度曲线，比单一平均 accuracy 更能说明状态压缩和位置路径的差异。对 SSM，还应测 state reset、chunk continuation 和跨请求隔离。

## 36.5 长流任务中的优势条件

SSM 更可能受益于：输入持续到达、需要在线状态、局部性/趋势明显、输出与输入交替、上下文极长、随机原文引用较少、设备带宽紧张。日志流分类、音频、传感器和某些基因组任务是自然候选。

但优势仍取决于 kernel 和数据。若每步 state update 很小、权重读取主导、batch 不足或设备没有 fused scan，理论线性可能无法转成端到端低延迟。

## 36.6 Transformer 保留优势的条件

Transformer 更适合需要任意内容寻址、few-shot 示例重排、长文档引用、工具 observation 比较、跨模态 token 对齐和成熟 serving 生态的任务。GQA、FlashAttention、PagedAttention、prefix cache 和 KV 量化已经缓解部分推理瓶颈。

这不意味着 Transformer 永远更好；如果上下文非常长、KV 成本压倒质量收益，hybrid 或 state path 可能更合理。

## 36.7 Hybrid 的评价方式

不能把 hybrid 只写成“兼顾两者优点”。要问：哪些层/头/位置走哪条路径；global 入口如何选择；显式 KV 和递归 state 的内存是多少；训练时如何平衡；serving 如何 snapshot/rollback；失败时回退到哪条路径。

可以把请求分成 fast-state 和 evidence-global 两类，由任务分类器或不确定性门控选择。路由器本身也会增加延迟和错误，必须把误路由成本计入。

## 36.8 一个架构决策表

| 约束 | SSM/State 路径 | Transformer/Global 路径 |
|---|---|---|
| 历史状态 | 固定/压缩 | 显式 K/V 或稀疏 cache |
| 任意引用 | 需检索/补偿 | 更自然 |
| 长流内存 | 有利 | 随长度增长 |
| 训练 kernel | scan/结构化 | GEMM/attention 生态成熟 |
| 服务状态 | 需 snapshot/迁移 | paged/cache 管理成熟 |
| 开放权重与工具 | 视模型 | 丰富 |

表格只建立假设，不替代实验。

## 36.9 常见新闻式结论为什么不可靠

“线性复杂度击败二次复杂度”“百万上下文无需 cache”“没有 attention 也能无限记忆”都把局部事实扩大成了全局结论。正确表达必须加入条件：在哪个模型、长度、任务、硬件和实现中，哪个指标改善；是否有质量代价；是否有独立复现。

对闭源模型、未公开架构或产品宣传语，最多作为 release radar 观察项，不能补写不存在的层数、状态维度或训练配方。

## 36.10 面试标准回答

可以这样回答：

> SSM 不一定整体替代 Transformer。它把历史压缩为递归状态，在长流、固定状态和部分硬件场景有明显潜力；Transformer 的显式 attention 在内容寻址、ICL、任意引用和成熟生态上仍有优势。更可能的演进是按 workload 使用 SSM、attention、retrieval 和 memory 的混合架构。判断方案时我会固定训练预算和硬件，分别测精确检索、多证据推理、流式状态、TTFT/TPOT、p99、显存、恢复和单位成功成本。

这段回答的价值在于承认优势和边界，并给出验证方法，而不是选择一个绝对立场。

## 36.11 机制与边界：研究议题

值得继续研究的问题包括：有限 state 如何保留可查询记忆；选择性更新能否有可解释/可验证验收条件；hybrid global layer 的最小数量；state 与外部 retrieval 的接口；跨 chunk/设备的可逆或近似恢复；大规模训练中的 scan kernel；以及多模态和 Agent workload 中不同路径的分工。

评价新模型时，可以把它看作一组假设：它假设历史查询具有某种结构、硬件适合某种更新、训练数据能教会选择性、服务状态可以可靠管理。每个假设都应有实验。

## 36.12 练习起点与资料范围

练习：选一个长文档问答、一个日志流检测和一个实时语音任务，分别设计 dense、SSM、hybrid 的 baseline；为每个 baseline 写质量验收条件、系统指标、失败回退和证据级别。

SSM 代表论文包括 S4（https://arxiv.org/abs/2111.00396）、Mamba（https://arxiv.org/abs/2312.00752）和 Mamba-2/SSD（https://arxiv.org/abs/2405.21060）；Transformer 基线见 https://arxiv.org/abs/1706.03762。论文、模型卡和产品资料的结论应分层使用。

## 36.13 比较中的混淆变量

SSM 与 Transformer 的比较经常混入模型规模、训练 token、数据质量、tokenizer、实现成熟度和解码预算。一个更快的 SSM 可能只是使用了更小模型，一个更强的 Transformer 可能只是训练更多数据。

实验报告应把模型、数据、训练、kernel、硬件和任务条件分栏，使用 ablation 或 matched compute 解释差异。没有 matched condition 的排名只能作为产品观察。

## 36.14 争议如何转成可验证问题

“SSM 是否能做精确检索”可以转成远距离数字、实体冲突和引用位置任务；“线性复杂度是否更快”可以转成不同长度和 batch 的端到端压测；“是否能长期记忆”可以转成 state reset、恢复和租户隔离测试。

把口号改成测试，才能让架构讨论从新闻和立场回到证据。

## 36.15 用 Pareto 前沿而不是单一排名做选择

架构比较通常同时追求质量、延迟、显存、吞吐和开发成本，这些目标很少由同一个方案同时最优。对方案 i，可以记录：

~~~math
q_i=\text{任务质量},\quad
\ell_i=\text{p99 延迟},\quad
m_i=\text{峰值显存},\quad
c_i=\text{单位成功成本}
~~~

若方案 A 在所有指标上都不差于方案 B，且至少一项更好，则 A 支配 B；其余方案构成 Pareto 前沿。这个概念比“谁的平均分最高”更接近生产选择，因为一个略弱但显著省显存的模型，可能在给定 SLO 下才是可行解。

需要特别小心质量指标的可比性。SSM 若使用固定状态，可能减少长上下文的内存，却把一部分成本转移到外部检索、重试或引用校验。于是更合理的单位指标不是单次生成成本，而是：

~~~math
C_{\mathrm{success}}
=\frac{C_{\mathrm{inference}}+C_{\mathrm{retrieval}}
 +C_{\mathrm{retry}}+C_{\mathrm{verification}}}
{\Pr(\text{task success})}
~~~

只有把这些补偿成本算进去，才知道“更便宜的 backbone”是否真的更便宜。

## 36.16 混合架构的接口比模块名称更重要

当系统把 SSM、attention、retrieval 和外部 memory 组合起来，真正困难的是信息在模块之间如何流动。一个可操作的接口至少要说明：

1. state 的 shape、dtype、版本和生命周期；
2. global attention 读到的是原始 token、摘要 token 还是检索候选；
3. 路由器依据任务类型、置信度还是预算做决定；
4. 失败时能否回到原始证据，而不是只重复压缩状态；
5. snapshot、rollback 和 batch reorder 如何跨模块保持一致。

例如，SSM 路径可以负责扫描整段日志，检索器在异常分数升高时返回原始事件，少量 attention 层再完成证据对齐。这种设计不是“每种架构各取一点”的口号，而是明确了压缩状态和精确证据的职责边界。若没有回读路径，系统在第一次压缩错误后就没有恢复机会。

## 36.17 把开放争议写成面试中的实验方案

面试官若问“你认为 Mamba 会不会替代 Transformer”，高质量回答不应停留在态度。可以按以下顺序展开：先给出 workload 假设，再给 matched baseline，接着列出质量和系统验收条件，最后说明失败回退。

例如长文档问答要测 exact recall、引用支持率和冲突版本；流式日志要测 state reset、跨 chunk 延续和每条事件成本；实时语音要测首包延迟、持续状态漂移和中断恢复。每个任务都要有 Transformer、SSM 和 hybrid 三个版本，并固定 tokenizer、训练 token、量化、GPU 和解码预算。

这样的回答体现的是研究判断力：架构不是先验信仰，而是一组关于信息访问模式和硬件执行方式的假设。证据不足时，明确说“公开资料支持到这里，剩余部分需要实验”，比猜测某个闭源模型内部结构更可靠。

## 36.18 把争议改写成可复现实验

“谁会替代谁”不是单一问题。可以拆成：固定质量下谁更省算力，固定算力下谁更强，长流下谁的状态成本更低，精确引用下谁的失败率更低，迁移到现有 runtime 谁的工程成本更低。每个问题都有不同的 baseline 和 workload。

实验要控制混淆变量：参数量、训练 token、数据质量、上下文训练、tokenizer、位置处理、kernel、硬件、batch 和 stopping rule。至少报告平均质量、困难样本曲线、精确检索、状态字节、吞吐、p99、恢复和 fallback，而不是只截取一个榜单数字。

## 36.19 用证据等级回答开放问题

面试或研究讨论中，可以把结论分为已证明、公开实验支持、合理推断和未知。已证明可以是复杂度或代数关系；公开实验支持是某论文在某模型和任务上的结果；合理推断来自结构和资源分析；未知包括闭源模型内部路由、未披露训练配方和跨硬件泛化。

这样的回答比“SSM 更快/Transformer 更强”更可靠，也能说明下一步实验。开放问题不需要假装已有结论，重要的是给出能区分假设的控制变量和失败判据。

## 36.20 最小报告模板

一份可比较的架构报告至少要列出：模型/代码 revision、参数和训练 token、上下文 curriculum、tokenizer、硬件、kernel、batch、解码、任务切片、state/cache、质量、吞吐、p99、单位成功成本和 fallback。缺失字段要写成未知，不能用论文标题或模型品牌推断。

报告还要把“架构改变带来的收益”和“工程回退带来的收益”分开。例如 hybrid 通过 RAG 提升引用正确率时，提升属于完整系统，不能写成 SSM backbone 单独学会了精确检索；如果 dense baseline 使用了不同的 harness，比较也不成立。

## 36.21 用 Pareto 前沿替代路线站队

架构选择通常同时追求质量、长程精确度、状态字节、TTFT、TPOT、p99、恢复时间和单位成功成本。一个方案不可能在所有维度都最优，因此应先把不满足 hard gate 的方案排除，再在剩余方案中找 Pareto 前沿。

例如，SSM 可能拥有更低的 state bytes，却在精确引用上需要 retrieval 和 verification；Transformer 可能拥有更高的 KV 成本，却能直接读取原文并使用成熟 serving。若把 retrieval、重试和人工审核成本漏掉，SSM 的单次推理便会被错误地当成完整任务成本。比较时要把 backbone、harness 和业务动作放在同一账本里。

## 36.22 从平均分转向任务切片

“SSM 更高效”或“SSM 可以替代 Transformer”都不是最小可验证命题。至少要把任务分成局部预测、连续状态跟踪、远距精确复制、多证据合并、工具历史引用和长流恢复，再分别记录质量、状态大小、训练吞吐、decode 吞吐、p99、失败率和单位成功成本。

如果 SSM 在趋势预测上更好、在精确引用上更差，结论不是“SSM 失败”，而是它的状态表示不适合该访问模式；如果 hybrid 通过少量 attention 和 retrieval 恢复了引用能力，则要把额外模块、索引和回读成本计入比较。任务切片把“架构优劣”改写成“给定访问原语的系统选择”。

## 36.23 worked example：同一日志的三种结论

构造一份包含 50,000 个事件的日志：前段定义错误码，中段有多次修复，末尾要求返回最终版本和三个证据位置。对纯 SSM、纯 attention 和 SSM+retrieval 做相同输入和输出预算的对照。

纯 SSM 可能以很小的固定状态完成“是否出现过错误”的统计，却在返回精确版本时丢失来源；纯 attention 能保留任意位置的候选，但 KV 和长 prefill 成本更高；混合方案可以让 SSM 扫描全量日志，retrieval 回读相关事件，再由 attention 做冲突消解。报告必须说明每个答案用了哪条路径，并记录回读、重试和验证时间。

## 36.24 替代证据的比较条件

对每个“替代”结论建立 `claim -> protocol -> measurement -> uncertainty -> scope` 记录。论文的渐近复杂度支持理论命题，模型卡支持公开结构或接口，独立实验支持特定任务结果；它们不能互相替代。闭源模型没有披露的训练配方、内部 kernel 或全面 benchmark，只能写成公开资料支持范围内的推断。

最终比较应保留 baseline、硬件、长度分布、训练 token、dtype、kernel、batch、工具和 verifier 版本。没有这些条件，“线性复杂度”只能作为机制直觉，不能直接写成生产吞吐承诺。

## 36.25 一个有统计意义的比较，而不是一次压测

如果只跑一次长序列 benchmark，任何一个偶然的 batch 形状、kernel warmup 或随机种子都可能改变结论。质量比较应使用成对样本：同一问题、同一证据、同一输出预算分别交给 Transformer、SSM 和 hybrid，记录每条样本是否成功、引用是否支持、是否触发回退。

设第 `i` 条样本上 SSM 与 baseline 的成功指示分别为 `s_i` 和 `t_i`，可以先看配对差：

```math
d_i=s_i-t_i,\qquad
\bar d=\frac{1}{n}\sum_{i=1}^{n}d_i.
```

`\bar d` 只描述样本平均差异，还要报告 bootstrap 置信区间或按任务桶分层的区间。若总体差异接近零，但长流桶为正、精确引用桶为负，汇总平均数反而会掩盖架构的适用边界。

系统指标也要成对采集。对每个请求记录 `TTFT`、`TPOT`、p99、峰值 state/KV、fallback 触发、检索时间、重试和最终成功。不能把 SSM 的纯 backbone 时间与 Transformer 的完整 retrieval harness 比较，也不能只把 fallback 请求排除后报告“主路径吞吐”。

## 36.26 从硬性条件到 Pareto 选择

架构决策通常有一些不能妥协的条件，例如高风险引用任务要求引用支持率不低于 0.98，交互式服务要求 p99 不超过 2 秒，训练平台要求恢复成功率不低于 0.999。先过滤掉不满足硬性条件的方案，再在剩余方案上比较质量、成本和迁移难度。

可以定义一个仅用于排序的软分数：

```math
S_i=w_qQ_i-w_lL_i-w_mM_i-w_cC_i-w_rR_i,
```

其中 `Q` 是质量，`L` 是延迟，`M` 是内存，`C` 是单位成功成本，`R` 是迁移/维护风险。这个分数不能替代硬性条件，也不能把安全漏放、租户隔离失败或数据丢失用平均性能抵消。权重必须来自业务约束，并在报告中公开。

## 36.27 一份可复现报告需要哪些附件

为了让其他人能够复查结论，报告至少应保存：模型和代码 revision、tokenizer、训练 token、上下文长度分布、数据切分、随机种子、dtype、kernel、GPU 拓扑、batch 组成、解码参数、retrieval/verifier 版本、失败样例和原始 trace。对于 state 模型，还要保存 reset、snapshot、chunk 和跨设备迁移策略；对于 Transformer，还要保存 KV 精度、分页大小、prefix cache 命中和抢占策略。

结果表应区分三种数字：论文或官方资料直接披露的数字、当前实验测得的数字、基于资源模型的估计。估计值可以用于容量规划，但不能冒充实测吞吐；实测值也只能代表指定硬件和 workload。资料边界写清楚，反而能让结论在换模型版本后继续使用。

## 36.28 小结

SSM 是否替代 Transformer 没有脱离条件的答案。真正可迁移的判断框架是：先看未来查询需要什么历史信息，再看状态/attention 如何提供这条路径，最后用成对样本、分层统计、硬验收条件和完整资源账本验证。未来更可能是架构组合和按 workload 路由，而不是单一路线宣告终结；任何“替代”结论都必须绑定模型、数据、硬件、harness 和回退条件。
