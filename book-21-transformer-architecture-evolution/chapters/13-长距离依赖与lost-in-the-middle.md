# 第十三章：长距离依赖与 Lost in the Middle

## 13.1 “能放进去”为什么不等于“能用起来”

长上下文最容易制造一个错觉：只要接口允许输入一百万个 token，模型就拥有一百万 token 的等价阅读能力。实际上，至少有四个不同的问题经常被混在一起：输入能否被 tokenizer 和 runtime 接受；模型是否在这样的长度上训练过；模型能否定位某一段证据；模型能否把多处证据组合成正确结论。

例如，在一份很长的合同中，第一段写着“付款周期为 30 天”，中间章节写着“对于海外订单，付款周期改为 60 天”，最后又有一条补充协议。模型可能能复述合同主题，却在回答“海外订单的付款周期是多少”时引用了第一条。问题不是上下文窗口不够，而是相关证据的定位、冲突消解和条件化推理没有同时通过。

因此，长上下文能力不能只用最大长度描述。更完整的能力向量是：

```text
可接收长度 -> 位置稳定性 -> 精确检索 -> 多证据组合 -> 抗干扰 -> 成本可接受
```

## 13.2 直觉：把上下文想成一张很长的桌子

把 attention 想成一个人在一张很长的桌子上找资料。桌子变长后，理论上资料仍在桌面上，但人要面对三个困难：

1. 资料之间的距离变大，翻阅和比较更费力。
2. 大量无关纸张会把重要句子淹没。
3. 如果两个位置写着互相冲突的答案，还要判断哪条规则优先。

模型的注意力权重可以帮助它“看向”某些 token，但权重高不必然意味着模型正确使用了该 token。它可能找到关键词，却没有把限定条件带到最终输出；也可能在答案中提到正确段落，但计算时仍依赖了错误的旧事实。

## 13.3 从一次注意力到跨段推理

在第 `l` 层，位置 `t` 对历史位置 `j` 的注意力权重可写成：

```math
a_{tj}^{(l)}=\operatorname{softmax}_j\left(\frac{q_t^{(l)}(k_j^{(l)})^\top}{\sqrt{d_h}}+b_{tj}^{(l)}\right)
```

其中 `b` 可能包含因果 mask、相对位置偏置或局部窗口限制。这个公式只说明“当前位置可以给历史位置分配权重”。真正的答案还要经过 value 聚合、残差连接、后续层变换和输出头：

```math
h_t^{(l+1)}=h_t^{(l)}+\sum_{j\le t}a_{tj}^{(l)}v_j^{(l)}
```

如果关键证据在第 `j` 个位置，模型要完成的不是一次检索，而是一个链条：识别证据类型，绑定它对应的实体和条件，把多个证据放进同一个中间表示，再让后续层使用这个表示。长距离任务难点往往出现在链条后半段，而不是简单的“attention 有没有扫到”。

## 13.4 Lost in the Middle 是什么

“Lost in the Middle”描述了一类稳定的实验现象：当相关信息被放在长上下文的开头、中间和结尾，并要求模型回答时，开头和结尾的信息通常更容易被利用，中间位置的信息利用率可能下降。这个现象不是所有模型、所有任务和所有 prompt 都相同，也不等价于模型完全看不到中间 token；它是一种位置敏感性风险。

可以用位置归一化坐标表示证据位置：

```math
r=\frac{p}{L-1},\qquad r\in[0,1]
```

对每个 `r` 测量准确率 `A(r)`，就能得到位置曲线，而不是只报告一个平均分。若 `A(0.5)` 显著低于 `A(0)` 和 `A(1)`，说明系统存在中间位置风险。还应改变干扰长度、证据数量、问题类型和证据是否冲突，因为单一 passkey 测试无法代表文档推理。

## 13.5 一个可复现的最小实验

下面的代码不调用模型，只构造一个位置敏感的 toy 检索器。它的意义是帮助读者理解实验设计：把同一条证据移动到不同位置，其他内容保持不变。

```python
from dataclasses import dataclass


@dataclass
class Probe:
    length: int
    evidence_at: int
    noise: int

    def score(self) -> float:
        # 教学化位置曲线：中间位置惩罚，不代表任何真实模型。
        r = self.evidence_at / max(self.length - 1, 1)
        middle_penalty = 0.35 * (1.0 - abs(2.0 * r - 1.0))
        noise_penalty = min(self.noise / self.length, 0.25)
        return max(0.0, 1.0 - middle_penalty - noise_penalty)


for position in (0, 250, 500, 750, 999):
    probe = Probe(length=1000, evidence_at=position, noise=900)
    print(position, round(probe.score(), 3))
```

真实评测需要让模型输出结构化答案，然后用 exact match、数字一致性、引用位置准确率和多证据组合准确率判分。不要把模型自己的“我找到了第几段”当作检索真值；应根据原文标注支持证据。

## 13.6 精确检索、证据合并和长程推理要分开测

至少可以建立四个任务层级：

1. **单点检索**：文档中只有一处答案，测试数字、实体名和短字符串复制。
2. **条件检索**：答案由实体、时间或权限条件限定，测试模型是否带上限定词。
3. **多点合并**：答案需要从两处或更多位置拼接，测试跨段信息流。
4. **冲突消解**：旧版本和新版本同时出现，测试时间、来源优先级和否定规则。

可以把任务成功定义为：

```math
S=\mathbb{1}[\text{answer correct}]\cdot
\mathbb{1}[\text{all required evidence used}]\cdot
\mathbb{1}[\text{format valid}]
```

在工程中还要报告单位成功成本：

```math
C_{\mathrm{success}}=\frac{C_{\mathrm{input}}+C_{\mathrm{output}}+C_{\mathrm{retrieval}}}{\max(\Pr(S=1),\epsilon)}
```

一个堆满无关文档的 1M prompt，即使偶尔回答正确，也可能不如先检索 20K token 的 RAG 管线。

## 13.7 工程上如何降低中间信息损失

第一种方法是先做外部检索，把候选证据放进较短上下文。检索器负责召回，模型负责重排和推理，两者要分别评估。第二种方法是对长文档做结构化分块，把章节名、实体、时间和来源作为显式字段。第三种方法是把关键事实在问题附近以“证据表”重新组织，但必须防止摘要阶段已经丢失原始条件。第四种方法是多次查询同一问题，改变证据顺序，再用 verifier 合并结果。

重排不是免费的。它会增加预处理延迟、索引维护和召回错误；把证据移到开头也可能让 prompt 变长。实际系统应在固定质量门槛下比较端到端成本、首 token 延迟和 p99，而不是只追求一次评测最高分。

## 13.8 与 RAG、长上下文和滑窗注意力的边界

长上下文提供的是“可以把更多内容放进一次前向计算”，RAG 提供的是“先从更大的外部集合中筛出候选”，滑窗注意力提供的是“限制每个位置直接看的范围”。三者可以组合，也不能互相替代。

滑窗降低计算和显存，但远处信息要经过多层传播或全局 token 才能到达；RAG 能减少干扰，但检索错了就没有后续补救；全量 attention 允许任意跳转，却不保证模型会正确使用每个证据。选择哪条路线，取决于文档是否稳定、证据是否稀疏、是否需要原文引用以及服务成本。

## 13.9 机制与边界：为什么平均 loss 可能掩盖问题

语言模型训练目标通常是 token-level cross entropy：

```math
\mathcal{L}=-\frac{1}{T}\sum_{t=1}^{T}\log P_\theta(x_t\mid x_{<t})
```

它对所有 token 近似平均加权。一个长文档中，绝大多数 token 是普通叙述，少量关键数字只占很小比例；模型即使牺牲这些数字，平均 loss 也可能变化不大。因此长上下文评估要增加稀有实体、数字、跨段组合和反事实任务，并报告按长度、位置和干扰强度分桶的结果。

还要区分模型层面的位置能力和 serving 层的输入处理。截断、错误 tokenizer、文档排序、模板中的 system message、prefix cache 复用和中间重试都可能制造类似 lost-in-the-middle 的表象。排查时先保存最终发送给模型的 token 序列，再核对 position id、attention mask 和检索结果，最后才讨论架构本身。

## 13.10 面试追问、误区与练习

**问：模型支持 1M context，能否说明它能可靠读取任意 1M 文档？**

标准回答：不能。要分别验证接口上限、训练长度、位置外推、单点检索、多证据组合、冲突消解和单位成功成本。最大上下文是容量声明，不是有效能力证明。

**问：为什么把证据放在开头或结尾有时更有效？**

标准回答：长序列中的位置表示、注意力分布、训练数据布局和输出位置共同影响信息利用；中间证据可能受到干扰和表示压缩。它是经验风险，不应当被写成所有模型固定的定律。

常见误区包括把 attention 权重解释成因果证据、只测 passkey、只看平均准确率、把长上下文和 RAG 当作同一个技术，以及把模型生成的引用当作真实检索轨迹。

练习：构造一份包含版本冲突、时间条件和三处证据的 32K 文档，分别测原始顺序、证据重排、外部检索和摘要后的回答，记录位置曲线、引用准确率、TTFT 和单位成功成本。

## 13.11 资料范围与继续实验

本章关于 Transformer 的注意力公式来自 Vaswani 等人的 *Attention Is All You Need*（https://arxiv.org/abs/1706.03762）；关于长上下文位置敏感性，参见 Liu 等人的 *Lost in the Middle*（https://arxiv.org/abs/2307.03172）。具体模型的上下文上限、训练长度和长上下文成绩必须绑定模型版本、评测集、prompt、推理参数和日期，不能由论文现象外推到所有模型。

## 13.12 从 benchmark 曲线到任务能力

长上下文评测至少要区分四种能力：把目标信息放进输入、在任意位置找到它、把多个证据合并、根据证据完成推理。一个 needle 任务可能只测第二项；多文档冲突任务才会测第三项；需要引用和计算的任务才开始接近第四项。把四者都叫“长上下文能力”，会让模型发布报告看起来比实际更强。

可以把一次任务成功拆成几个门：

```math
P_{\mathrm{task}}
=P_{\mathrm{fit}}P_{\mathrm{retrieve}}P_{\mathrm{ground}}
 P_{\mathrm{reason}}P_{\mathrm{format}}
```

这里分别表示输入被正确编码、目标被找到、证据被正确绑定、推理结论正确以及输出协议正确。它们不是统计上严格独立的概率，但这个分解有助于定位失败。例如目标 token 的 attention 很高却引用错文档，问题发生在 evidence grounding，而不是检索；最终答案正确但漏掉必填字段，问题发生在 format gate。

评测集应随机化证据位置、文档长度、干扰主题、同名实体、版本冲突和答案形式。还要加入“目标不存在”的负例，检查模型是否会因为看到了相似词就强行作答。报告应给出随输入长度和证据位置变化的曲线，而不是只给一个平均分。

## 13.13 Context surgery：改变输入形状而不是盲目加窗口

当模型在中间证据上失败时，第一反应不应是继续增加 context length。可以做 context surgery：把检索结果按来源分组，给每组加标题和文档 ID；将问题相关的原子证据放在结构化字段中；对长工具结果做分页和摘要；对冲突版本显式标记时间和 revision；必要时让模型先输出证据表，再生成结论。

一个研究问答流程可以是：先用低成本检索拿到候选片段，再让模型为每个片段生成 claim/evidence 对，最后只把经过引用检查的证据交给推理阶段。这样做牺牲了一点预处理延迟，却减少了无关文本、来源混淆和中间位置竞争。

如果使用摘要，摘要必须保留来源、时间、数字、限定条件和未解决问题。摘要越短不代表信息密度越高；把“可能导致”压成“导致”，会让后续推理获得一个错误的确定事实。生产系统应保存原文 artifact 和摘要之间的引用映射，允许在发现冲突时回读原文。

## 13.14 长上下文能力与架构/Serving 的耦合

输入长度增加会同时影响位置编码、attention mask、KV cache、prefill 调度和尾延迟。即使模型在离线长文档上能回答，线上也可能因为 prefill 队列、显存 admission 或 prefix cache 失效而不可用。一个完整的验收条件要把质量和服务条件绑定：

```math
G_{\mathrm{long}}
=G_{\mathrm{quality}}G_{\mathrm{position}}G_{\mathrm{cache}}
 G_{\mathrm{latency}}G_{\mathrm{cost}}
```

例如同一模型在 128K 输入上 retrieval 通过，但 p99 超过产品 deadline，不能称为“支持 128K 生产任务”；另一模型 p99 合格，却在中间证据上系统性失败，也不能只因为接口接受请求就宣称有效长上下文。长上下文应当是能力、协议和资源的联合声明。

本文引用的 Lost in the Middle 研究、RULER 等长上下文评测和具体模型的 context claim 只能支持相应公开实验条件。不同 tokenizer、模板、位置缩放、硬件和 runtime 会改变结果，不能把一个模型的曲线复制给另一个模型。

## 13.15 证据图：从“找到段落”到“证明关系”

长上下文任务经常在“检索成功”之后才真正开始。假设一份事故报告中有三类证据：发布记录说明某个配置在 4 月 17 日上线，监控记录说明错误率在 4 月 18 日上升，回滚记录说明回滚后错误率下降。模型如果只找到了三段文字，却没有把它们绑定到同一个服务、同一个版本和正确的时间顺序，仍然不能回答“哪一个变更最可能导致事故”。

可以把证据组织成一个有类型的图。节点表示文档片段、实体、版本、时间和主张，边表示 `describes`、`belongs_to`、`before`、`supports` 或 `contradicts`。一次回答不再只是生成字符串，而是先得到候选图 `G_c`，再检查它是否覆盖问题要求的关系。

```math
G_c = (V_c, E_c)
S_ground = |E_c intersect E_star| / max(|E_star|, 1)
```

其中 `E_star` 是标注的必要关系集合。这个分数不是通用真理，但能区分“引用了正确段落”和“把正确段落连成了正确关系”。对于前面的事故例子，至少要检查：发布记录与错误率记录的服务名一致，版本时间满足 `t_release < t_incident`，回滚记录确实对应同一个变更，并且没有一条更新的反证。

小白可以把它理解成做案情时间线：找到三张纸不等于证明三张纸说的是同一件事。专家则要进一步区分实体消歧、时间排序、因果强度和证据缺失。文档中出现“之后发生”只能支持时间相关性，不能自动证明因果；如果没有对照实验或回滚证据，回答应写成“与该变更一致”或“目前材料不足以确认”。

因此，长上下文评估应至少报告四个门：候选片段召回、实体绑定、关系覆盖和结论校验。一个模型可以在第一门得分很高，却在后三门失败。把这四个分数拆开，才能知道应该改检索、提示结构、模型训练，还是答案验证器。

## 13.16 失败回放：定位是输入、位置还是推理错误

线上发现长文档回答错误时，不能只保存最终 prompt 和最终答案。应保留一条可以重放的 artifact 链：原始文档 manifest、tokenizer revision、最终 token ids、模板、截断结果、position ids、attention mask、模型 revision、采样参数、检索/重排结果、输出引用和验证器判定。缺少其中任何一项，都可能让一次事故在离线环境里“自己消失”。

一个实用的回放顺序是先固定随机性并运行短上下文对照，再改变证据位置，最后改变输入长度。如果短上下文和长上下文都失败，优先查事实、模板或任务定义；如果只有中间位置失败，做位置旋转实验；如果 token ids 已经少了关键文档，问题属于输入管道；如果模型引用正确片段但结论错，才进入关系推理和验证器排查。

```math
E_replay = E_token + E_position + E_mask + E_retrieve + E_ground + E_reason
```

这里的加法是诊断账本，不表示这些误差严格可加。它要求每次回放都记录“第一个发生变化的层”。例如，把文档顺序换回原始顺序后答案恢复，说明模型可能依赖顺序捷径；把 `position_ids` 修正后恢复，说明不是长程语义能力；替换验证器后仍然错误，则不能把问题归咎于格式检查。

还要保存负例：目标证据不存在、证据互相冲突、只有过期版本存在、引用段落被截断。模型在这些样本上的拒答或不确定性同样是能力的一部分。一个只在有答案的样本上得分很高的系统，可能只是擅长从相似文本中拼出一个看似确定的答案。

## 13.17 小结

长距离能力不是一个二元开关，而是一组从“看见”到“正确使用”的验收条件。工程上，位置探针、精确检索、多证据组合、冲突消解和成本评估应当分开记录。只有这些验收条件一起通过，长上下文才真正改变系统设计。
