# 第 56 章 Gemini、Claude、GPT-4V：多模态、长上下文与系统能力

## 56.1 为什么闭源模型要用“系统证据”阅读

Gemini、Claude 和 GPT-4V 代表的不是单一公开 checkpoint，而是由模型、接口、产品策略、安全层、工具和服务基础设施组成的系统。外部读者通常无法看到完整的层数、参数量、训练数据、位置实现和推理 kernel。

因此研究这些模型时，必须把证据分级。论文或技术报告可以支持公开的模型目标和实验；官方文档可以支持接口、模态和上下文声明；产品页面可以支持发布方对能力的描述；第三方测试只能支持特定版本和特定 harness 下的观察，不能自动还原内部架构。

## 56.2 多模态系统的三种形态

一个多模态系统可能使用：

1. 编码器加语言模型：视觉或音频 encoder 输出表示，再由语言模型理解。
2. 统一 token backbone：不同模态被映射到共同序列或共享表示空间。
3. 多模型系统：专门模型负责感知、语言、工具和安全，由路由器组合。

可以用抽象形式表示：

~~~math
z_m=E_m(x_m),\qquad
h=P_m(z_m),\qquad
y=\mathrm{LM}(x_{\mathrm{text}},h)
~~~

E_m 是模态 encoder，P_m 是 projector 或对齐模块。这个公式不是对某个闭源模型的内部实现断言，只是阅读多模态系统的共同接口。

## 56.3 Gemini 的公开信息应该怎样理解

Gemini 系列公开资料强调多模态能力、长上下文和统一模型方向。阅读时可以讨论输入模态、上下文接口、工具和 benchmark，但不能仅凭产品表现推断其每层 attention、视觉 token 化或训练数据细节。

一个“支持图像、音频、视频和文本”的接口声明，至少涉及 processor、模态编码、时间/空间位置、token budget、跨模态 attention 和服务限制。真正的有效能力还要看高分辨率、长视频、时间定位、图中文字、跨模态冲突和延迟。

## 56.4 Claude 的长上下文与安全系统

Claude 的公开产品资料常把长上下文、对话、代码和安全作为重要能力。长上下文声明仍然需要拆成四个问题：接口是否接受、模型是否训练、任务能否检索、成本是否可接受。

安全也不是一个单独的拒答模型。系统可能包含训练后的行为、分类器、策略、工具权限、内容过滤和人工流程。公开资料没有说明的部分，不能用社区猜测补齐。

评估 Claude 类产品时，应固定 API 版本、模型 id、system prompt、输出预算、工具开关和区域。不同版本的上下文、延迟和行为可能变化。

## 56.5 GPT-4V 类系统的感知边界

视觉语言模型的输入可以是图像、文本或两者组合。用户容易把“能看图”误解为“具有像素级、几何级和时间级的可靠感知”。实际任务要区分：

- 物体和场景识别。
- OCR 和小字号文本。
- 空间关系和坐标。
- 图表数值和趋势。
- 多图比较。
- 视频时序和动作。
- 安全敏感细节。

模型可能在主题描述上表现很好，却在一处数字、否定词或空间方向上失败。产品设计要为高风险任务保留 OCR、检测器、规则或人工复核路径。

## 56.6 长上下文的资源模型

如果多模态 token 总数为：

~~~math
T=T_{\mathrm{text}}+T_{\mathrm{image}}+T_{\mathrm{audio}}+T_{\mathrm{video}}
~~~

全局 attention 的交互规模大致随 T 的平方增长。即使使用稀疏或高效 kernel，编码、投影、内存和网络传输仍然存在：

~~~math
C_{\mathrm{total}}
=C_{\mathrm{encode}}+C_{\mathrm{project}}
+C_{\mathrm{attention}}+C_{\mathrm{decode}}
+C_{\mathrm{io}}
~~~

因此接口上的 token window 不是单一的质量或成本指标。视频帧采样、图像分辨率、音频窗口和文本长度要共同纳入预算。

## 56.7 多模态位置与因果性

图像有二维空间位置，音频和视频有时间位置，文本有序列位置。把这些模态混合后，系统必须回答：空间位置如何保留，时间戳如何对齐，文本生成能否看到未来帧，跨模态 cache 如何续接。

一个因果测试是改变未来视频帧，检查当前时间点的 logits 是否变化。如果变化，可能存在未来泄漏或接口把全视频作为已知输入；如果不变化，也要确认模型是否在当前任务中真正使用了前序观测。

跨模态位置错误常常不导致 API 报错，却会导致“能回答主题但引用错位置”。这类错误需要通过时间戳、坐标和 provenance 测试发现。

## 56.8 工具和系统能力

闭源模型的产品能力常常包含 browsing、code execution、文件处理、函数调用或 workspace。要把模型推理和系统行动分开：

~~~text
model proposes
  -> tool policy checks
  -> executor runs
  -> result is returned
  -> model interprets
  -> verifier decides completion
~~~

模型答对一个计算题可能来自内部推理，也可能来自工具；模型引用一个网页可能来自检索系统。评测需要记录工具轨迹和证据来源，否则无法比较“模型本身能力”和“系统增强能力”。

## 56.9 公开 benchmark 的阅读方法

benchmark 分数受题目、提示、工具、上下文、解码和版本影响。比较闭源模型时至少记录：

~~~text
provider
model_id
api_date
system_prompt
tool_mode
temperature
max_output_tokens
input_modalities
grader_version
~~~

对于多模态任务，还要记录分辨率、压缩、帧数、采样间隔、OCR 前处理和图像顺序。否则一次分数无法复现，也无法判断差异来自模型还是输入处理。

## 56.10 能力、系统和供应商声明的分层

可以将结论分为三层：

第一层是直接事实，例如官方接口列出的输入类型、模型 id 或最大请求长度。第二层是受控观察，例如固定 harness 下的准确率、引用支持率、p95。第三层是推断，例如猜测内部使用某种 encoder、MoE 或位置机制。

技术分析应明确区分“官方文档说明”“在该版本实验中观察到”和“公开资料无法确认”这三种证据层级，不能把第三层写成第一层。

## 56.11 一个多模态评测骨架

下面的代码表示评测记录应保存输入和系统元数据：

~~~python
def record_case(model_id, image, prompt, result, meta):
    return {
        "model_id": model_id,
        "image_sha256": meta["image_sha256"],
        "prompt": prompt,
        "result": result,
        "resolution": meta["resolution"],
        "tool_trace": meta.get("tool_trace", []),
        "evidence": meta.get("evidence", []),
        "latency_ms": meta["latency_ms"],
    }
~~~

真实实验还应保护用户数据、记录 API 版本和保存原始输入的授权状态。对长视频或敏感图像，不能为了复现而无限期保存原始媒体。

## 56.12 安全与隐私边界

图像、音频和文件可能包含个人信息、凭证、屏幕内容或内部文档。多模态系统的安全风险包括模型误识别、提示注入、跨模态注入、工具越权、数据留存和引用泄漏。

产品验收条件应包括输入扫描、权限隔离、工具 allowlist、输出审计、数据保留策略和高风险人工复核。安全测试要覆盖图像中的恶意文字、PDF 隐藏指令、音频中的口令和跨模态冲突。

## 56.13 常见误区

第一，把闭源产品名当成内部架构名。第二，把上下文窗口当成有效长程理解。第三，把多模态输入支持当成所有细节任务可靠。第四，把产品工具结果当成模型原生能力。第五，只记录最终答案，不记录 API 版本、输入处理和工具轨迹。第六，把第三方逆向猜测写成官方事实。

## 56.14 闭源模型的能力评估要绑定 harness

闭源模型的结果很容易被 system prompt、工具、重试、隐藏上下文、输出预算和 grader 改变。评估记录至少要保存模型 id、revision 或日期、API 参数、system policy、媒体预处理、工具开关、采样参数和失败重试规则。

同一个任务可以拆成裸模型、模型加检索、模型加工具和完整产品四种 harness。这样才能知道能力来自模型本身、外部证据还是执行器。对外只给出“产品能完成”而不说明 harness，无法支持架构推断。

## 56.15 多模态有效能力的分层

多模态输入的有效能力可以按四层验收：接口接受、模态解析、跨模态对齐和任务决策。图像上传成功只证明第一层；识别物体不代表能读小字；读出文字不代表能把文字与问题中的空间关系对齐；对齐成功也不代表最终结论正确。

对视频还要加入时间位置、帧采样、长视频中间证据和未来帧反事实。对音频要区分转写、说话人、时间段和语义推理。指标应按字段和时间/空间范围记录，不要只用一条自然语言答案评估。

## 56.16 长上下文的系统成本

长上下文请求的成本由 token 数、媒体编码、KV/state、网络、输出和安全扫描共同决定。即使模型能接收长输入，p99、配额、限流和租户公平性也可能不允许所有请求使用最大窗口。

容量规划要把输入长度和输出长度分布分开，记录 TTFT、TPOT、峰值显存、媒体缓存和失败率。长上下文产品的关键问题不是“上限是多少”，而是“在目标任务和成本验收条件下，多少上下文真正有用”。

## 56.17 闭源系统比较要坚持证据分层

对于 Gemini、Claude、GPT-4V 等闭源系统，公开发布页、技术报告、system card、模型卡和 API 文档可以支持不同层级的结论。模型支持图像输入是接口事实；在某 benchmark 上得分是条件实验事实；“内部使用了某种 encoder 或 planner”若未披露则不能写成确定结构。

## 56.18 系统能力来自模型和 harness

多模态、工具、长上下文和 Agent 成绩往往依赖 processor、prompt、检索、代码执行、并行工具、重试、评估器和权限。公平比较必须固定或公开 harness；否则比较的是“供应商系统”而不是裸模型，二者都可以有价值，但结论不能混用。

## 56.19 能力声明要带边界条件

报告一个系统能力时，至少注明媒体类型/分辨率、上下文长度、工具权限、版本、采样、时间、语言、评估集和成功定义。尤其是“支持长上下文”“能做电脑操作”“具备推理能力”等宽泛表述，应进一步拆成检索、证据合并、动作成功、恢复和安全验收条件。

## 56.20 资料范围与系统判断

Gemini、Claude 和 GPT-4V 的公开论文、模型卡、产品文档和 API 文档可支持不同层次的结论。对于闭源模型，合理的知识目标不是猜出隐藏的层表，而是建立证据分级、可复现实验和系统边界。

多模态和长上下文让模型从“文字预测器”变成复杂服务系统。比较它们时，应同时看感知保真、位置/时间对齐、工具闭环、隐私安全、版本稳定性和端到端成本。

## 56.21 面试问题与练习

**问：如何判断一个闭源模型的长上下文是否真实有效？**

固定版本和 harness，改变长度、证据位置、干扰和任务类型，测 evidence recall、引用支持、跨段推理、p95 和成本；不能只接受窗口数字或单个 needle 结果。

**问：多模态模型看错图上的数字时，应该先换更大模型吗？**

先定位是分辨率、OCR、token 压缩、位置、提示、模型能力还是工具链问题；高风险数字任务可以接入专用 OCR、结构化解析和验证器。

**练习：**设计一个对 Gemini、Claude 或 GPT-4V 类 API 的可复现实验记录 schema，并区分官方事实、实验观察和内部架构推断。

资料入口：

- Gemini technical report: https://arxiv.org/abs/2312.11805
- GPT-4V system card: https://cdn.openai.com/papers/GPTV_System_Card.pdf
- Anthropic model overview: https://docs.anthropic.com/en/docs/about-claude/models/overview
- Gemini API models: https://ai.google.dev/gemini-api/docs/models

## 56.22 多模态证据矩阵

多模态系统的评测要把“能接收媒体”拆成感知、对齐、推理、工具和安全五层。对图像测 OCR、坐标和遮挡；对视频测时间位置、事件顺序和长视频中间证据；对音频测 WER、说话人、时间戳和语义。每层都保存输入媒体版本、processor、分辨率/采样率、模型 revision 和失败类型。

## 56.23 闭源模型的可复现记录

闭源模型比较不能还原未公开的层表，但可以建立完整的行为实验记录：模型 ID 和日期、API 参数、system/developer prompt、媒体 processor、分辨率/采样率、工具列表、权限、重试、输出 token、停止原因、原始媒体 hash 和评估脚本。缺少这些字段，下一次版本升级后很难解释成绩变化。

评测应把感知、对齐、推理、工具和安全分开。图像数字错误先检查分辨率和 OCR；视频中间事件失败要检查帧采样和时间位置；音频对话要看 WER、首包、打断和安全；工具任务要验证参数和副作用。官方 benchmark 只能作为入口，不能替代自己的 workload 回放。

## 56.24 多模态比较的最小实验矩阵

比较闭源多模态系统时，可以把同一任务做成四个版本：裸图文输入、图像加 OCR、图像加结构化工具、完整产品 harness。再改变图像分辨率、视频帧率、证据位置、语言和输出预算。若只有完整 harness 成功，结论应写成“系统完成了任务”；若裸模型也成功，才有理由讨论模型本身的感知或推理能力。

每个版本都记录 media hash、processor、模型 ID/日期、工具权限、重试、输入输出 token、错误类型和人工复核。一个模型在图表数字上错，而 OCR 工具正确，责任可能在跨模态绑定；一个模型在裸图上正确、在产品里错误，优先查预处理和上下文组装，不要立即归因于模型退化。

## 56.25 公开声明的证据边界

“支持图像输入”是接口事实，“在某评测上得分更高”是绑定条件的实验事实，“内部使用某种视觉编码器或规划器”只有在官方资料明确披露时才是结构事实。产品页面、system card、技术报告和第三方逆向分析的证据等级不同，正文应保留来源类型、版本和日期。

对于长上下文、电脑操作和工具调用，至少把接口接收、证据定位、任务完成、恢复和安全副作用分别验收。最大窗口或演示视频不能代替这些验收条件，也不能支持跨版本的永久结论。

## 56.26 用 harness 做一次因果归因

当一个多模态产品答对了图表问题，答案可能来自视觉编码器、OCR、检索、代码执行、隐藏的系统提示或重试。要判断哪一层产生了贡献，可以把同一批样本拆成逐步增加能力的 harness：

| Harness | 输入与能力 | 能回答的问题 |
| --- | --- | --- |
| H0 | 裸图像/文本模型 | 模型自身是否能感知和推理 |
| H1 | H0 + 固定 OCR 结果 | 错误是否来自小字识别 |
| H2 | H1 + 结构化解析或计算工具 | 数值计算和表格解析是否是瓶颈 |
| H3 | 完整产品流程、检索、重试和策略层 | 端到端系统是否完成任务 |

若 H0 失败而 H1 成功，优先查分辨率、视觉 token 压缩和 OCR；若 H1 已经正确、H2 才成功，瓶颈可能在计算或结构化绑定；若 H2 正确但 H3 失败，要查上下文组装、工具权限、重试和安全策略。只有在固定其余条件后比较 H0 与 H1，才能把差异归因于感知模块，而不是把整个产品成绩倒推成“模型内部能力”。

这个设计也适用于视频和音频：视频可以逐步加入帧采样、时间索引和动作检测；音频可以逐步加入转写、说话人分离和时间戳。每一步都保存原始媒体 hash、processor 版本和输出证据，才能解释版本升级后的回归。

## 56.27 多模态 token 预算是系统资源模型

公开接口通常把文本、图像、音频和视频都称作“输入”，但不同媒体经过 processor 后占用的计算和上下文预算并不相同。可以用一个不依赖具体厂商的抽象表示：

~~~math
T_{\mathrm{total}}
=T_{\mathrm{text}}
 +\sum_{m\in\{\mathrm{image,audio,video}\}}r_m(\mathrm{media}_m,\mathrm{processor}),
~~~

其中 `r_m` 是由分辨率、采样率、帧数、压缩、patch 或 codec 规则共同决定的映射，不能把它擅自等同为固定的“每张图多少 token”。若视频帧数翻倍，可能同时增加视觉编码、跨模态 attention、网络传输和后续 KV；如果 processor 先下采样，token 数可能不变，却损失时间或空间细节。

容量规划应把输入预算拆成四个验收条件：媒体能否被接受、关键细节是否保留、跨模态证据能否对齐、请求的 TTFT/p99 是否仍可接受。一个系统能接收更大图片，不意味着图中文字、坐标和时间事件的有效召回同步提高。高分辨率和长视频应按任务价值做自适应采样，并在采样结果中保留来源和时间范围。

## 56.28 版本漂移会改变“模型能力”的含义

闭源 API 的模型 ID、别名、默认 system prompt、processor、安全策略和工具执行器都可能变化。一次评测记录如果只保存模型名称和最终答案，下一次失败时无法知道是模型更新、输入预处理改变、工具返回不同，还是 grader 改了。

可以为每个结论建立一个证据卡：

~~~text
claim: 在固定图像分辨率下，表格数字任务达到某个成功率
model_id: exact id, not display name
revision_or_date: provider revision or test date
processor: resize, crop, frame/audio sampling
harness: H0/H1/H2/H3 and tool permissions
metric: exact value, coordinate accuracy, citation support, p95
source: official report, API doc, controlled observation, inference
status: verified / conditional / unknown
~~~

`verified` 只表示字段有直接资料或可复现实验；`conditional` 表示结论只在给定 harness、日期和数据集成立；`unknown` 不是失败，而是拒绝用猜测填空。对于内部 encoder、MoE、位置机制和训练数据，没有公开证据时，系统能力可以继续测，架构断言必须留白。

| 路径 | 数值精确率 | 证据支持率 | p95 | 失败归因 |
| --- | ---: | ---: | ---: | --- |
| H0 裸模型 | 0.72 | 0.61 | 1.1 s | 小字、坐标绑定 |
| H1 加 OCR | 0.86 | 0.83 | 1.4 s | 趋势解释、表头关联 |
| H2 加结构化计算 | 0.94 | 0.91 | 1.8 s | 工具参数和拒答 |
| H3 完整系统 | 0.93 | 0.89 | 2.6 s | 安全策略、重试、限流 |

如果只看 H3，可以说“系统完成率为 0.93”，但不能说“模型视觉能力为 0.93”。H0 到 H1 的提升说明 OCR 或输入处理贡献很大；H2 的提升说明数值推理不是单纯视觉识别；H3 的轻微下降可能来自安全门或工具失败。真实报告还要按字体大小、图表类型、语言、压缩质量和遮挡程度分桶，否则平均值仍会遮住高风险子集。

## 56.30 高风险场景必须把模型和执行器分开验收

多模态系统常被用于票据、合同、医学影像、屏幕操作和语音指令。这些场景的错误不只是“回答错”，还可能造成隐私泄露、错误付款、越权操作或不当诊断。模型输出应经过结构化 schema、来源核对、权限检查和必要的人工确认；图像中的文字、PDF 隐藏内容和音频口令都应被视为可能携带不可信指令的输入。

工具执行器不能因为模型给出了高置信度参数就直接执行。一个安全的事务边界是：模型提出动作，策略层验证资源和权限，执行器以最小权限运行，返回结构化结果，验证器检查副作用，最后才提交状态。评测中同时报告任务成功率、工具参数错误率、越权阻断率、误阻断率、隐私泄露率和恢复时间，才足以支持上线判断。

## 56.31 小结

闭源多模态系统的可靠分析不在于猜内部层表，而在于绑定版本、processor、harness、媒体预处理、工具、评测和安全边界。接口支持、局部实验和内部架构推断属于不同证据等级，长上下文和多模态能力都要以有效任务指标和成本验收。
