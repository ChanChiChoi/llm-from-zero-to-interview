# 第七十九章 Mistral Small 4：混合推理与 EAGLE/NVFP4 部署

Mistral Small 4 是一个适合练习“从公开材料还原模型结构、又不把推断说成事实”的案例。发布方称它把 Instruct、Reasoning（此前称 Magistral）和 Devstral 路线整合进一个模型；同一发布还提供请求级 reasoning effort 设置，并链接 EAGLE 草稿头和 NVFP4 量化检查点。它们分别涉及能力描述、请求配置、模型权重、辅助草稿权重和服务实现，不能因为出现在同一发布页就当成一项机制。

本章先读公开配置，理解 Mistral4 文本主干的 MLA 与稀疏 MoE，再估算每 token 的缓存状态；随后跟踪 EAGLE 怎样提出候选并让目标模型验证，最后解释 NVFP4 制品能支持哪些资源判断。讨论固定到 Mistral 模型卡与配置的指定 revision、Transformers 引入 Mistral4 的实现，以及对应方法论文和格式文档。公开配置和发布材料不等于完整训练配方，也不等于任意推理后端的实现承诺。

## 79.1 一份模型发布包含模型、请求配置与推理制品

发布页常把模型能力、服务参数和部署选项放在相邻位置。读架构时先把这些对象分开：模型结构回答权重中的层如何组织；检查点标识一份具体权重制品；请求设置影响一次生成的行为；EAGLE 草稿头是辅助提出候选的另一份权重；NVFP4 检查点改变权重的数值表示；推理后端负责把它们组合成实际计算。相邻出现只说明发布方把它们与同一模型关联，不能证明所有制品已互相兼容。

### 79.1.1 Instruct、Reasoning 与 Devstral 是发布方的能力合并主张

Mistral 的[发布文章](https://mistral.ai/news/mistral-small-4/)把 Small 4 描述为结合 Instruct、Magistral Reasoning 与 Devstral coding 能力的开放模型。模型卡也介绍它面向指令、推理和代码任务，并支持文本与图像输入。可以据此说发布方希望一个模型覆盖这些使用方向；公开资料没有完整披露训练数据、各阶段配方、专家是否按任务专门化，以及每种能力怎样对应到内部网络。

因此，“统一”不是“三个模型被简单拼接”，也不是“运行时会根据任务切换三套权重”的证据。要回答内部如何学到这些能力，需要模型结构、训练报告或可复核的消融；单凭发布文案不能还原这些过程。

### 79.1.2 `reasoning_effort` 改变请求行为，不代表另一套权重

模型资料公开了 `reasoning_effort` 的 `none` 和 `high` 值。它们是调用同一模型时可选的请求设置，发布方将其用于控制是否采用较深的推理行为。这个字段本身没有说明内部增加了哪条计算路径、改变了哪些专家路由，也不能证明输出 token 数或质量会按固定比例变化。

应把“参数可设置”和“参数具体触发的内部机制已公开”分开。若要判断某个任务是否值得使用 `high`，要对同一模型版本和任务集测答案质量、输出长度与延迟；模式名不是质量保证，也不是跨供应商可比的刻度。Mistral 的[模型文档](https://docs.mistral.ai/models/mistral-small-4)支持公开能力与参数层面的描述，不支持从参数名推断未披露的计算图。

### 79.1.3 模型结构、检查点、解码方法和服务层属于不同对象

| 对象 | 本章中的例子 | 它能说明什么 |
| --- | --- | --- |
| 模型与结构 | 文本主干配置、MLA、MoE | 层、投影和路由等公开结构字段 |
| 检查点 | 未量化基础检查点、NVFP4 变体 | 某个版本的参数值及数值表示 |
| 请求配置 | `reasoning_effort=none/high` | 一次调用可选的行为设置 |
| 辅助草稿制品 | Small 4 EAGLE head | 与目标模型关联的候选生成权重 |
| 解码算法 | speculative decoding / EAGLE | 草稿与目标模型如何生成、验证和校正 |
| serving runtime | vLLM、SGLang 或其他指定版本 | 制品在具体软件、硬件和负载下如何执行 |

例如，EAGLE 的接受校正可以保证采样结果服从“当前 verifier 所定义的目标分布”；如果 verifier 使用量化权重，这个分布就是量化模型的分布。它不能额外保证量化模型与原始高精度模型行为相同。runtime 是否接受某个草稿头、能否与某种精度格式联合运行，也必须看对应版本的实现和制品说明。

## 79.2 固定配置显示 Mistral4 文本主干与多模态封装

截至本章核对的公开配置 revision，外层模型类型是 `mistral3`，架构字段是 `Mistral3ForConditionalGeneration`，其中的 `text_config.model_type` 为 `mistral4`。这表示配置将条件生成封装和文本主干分层描述；模型卡另行声明可接收文本、图像并生成文本。类名和配置字段不足以推出图像编码器的全部细节或产品能力的实现路径。

后续维度与缓存估算取自[固定配置 revision](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603/blob/7ecb947/config.json)，缓存写入路径取自[Transformers 引入 Mistral4 时的固定实现](https://github.com/huggingface/transformers/blob/3b50327/src/transformers/models/mistral4/modeling_mistral4.py)。它们说明这些来源中的配置和实现，不代表其他后端一定采用相同张量布局。

### 79.2.1 顶层 Mistral3 条件生成封装内部使用 Mistral4 文本配置

不要只看模型外部名称或一个 `model_type` 字段。配置树的顶层描述条件生成模型，文本配置再描述其解码器。外层配置决定制品怎样组织输入模态和生成任务；文本配置包含解码层数、注意力和专家参数等架构信息。

模型卡确认输入可含图像、输出为文本，但这不等于公开了完整视觉编码器结构、图像切块方式或图文 token 的展开策略。本章只使用配置中可直接核验的文本主干字段，不从条件生成类名猜出隐藏模块。

### 79.2.2 36 层 MLA 用低秩 latent 缓存和分离的 RoPE key

固定文本配置列出 36 层、32 个 query heads、32 个 key/value heads；注意力字段包括 `q_lora_rank=1024`、`kv_lora_rank=256`、`qk_nope_head_dim=64`、`qk_rope_head_dim=64` 和 `v_head_dim=128`。其中 `q_lora_rank` 描述 query 投影的低秩路径，`kv_lora_rank` 描述压缩的 key/value latent 宽度；两个 key 维度分别对应不做 RoPE 的部分与带 RoPE 的位置部分。

MLA 的省缓存思路不是把每个 head 展开的 K、V 都原样留在历史中。实现先保留压缩的 KV latent，并单独保留位置编码所需的 RoPE key；计算当前注意力时，再由 latent 投影出各 head 所需的 key/value 表示。该 Transformers 版本的 `Mistral4Attention` 在扩展成逐头 K/V 之前缓存 `k_pass` 与 `k_rot`，因此可按每层每 token 的 $256+64=320$ 个数值估算其缓存形状。其他后端可能融合投影、改变布局或使用不同精度，不能默认都存成相同张量。

### 79.2.3 四路 routed top-k 与 shared expert 不能混为一个数字

配置中的 `n_routed_experts=128` 表示有 128 个路由专家；`num_experts_per_tok=4` 表示每个 token 选择其中四个；`n_shared_experts=1` 则把共享专家单独列出。路由专家由门控网络按 token 选择，共享专家不参与这 128 路中的 top-k 竞争。指定 Transformers 实现先汇集被选中的路由专家输出，再加上共享专家输出。

可把该层关系概括为：

```math
y_t = \sum_{i \in \mathrm{Top4}(x_t)} g_{t,i} E_i(x_t) + E_{\mathrm{shared}}(x_t)
```

其中 $x_t$ 是第 $t$ 个 token 的层输入，$E_i$ 是第 $i$ 个路由专家，$g_{t,i}$ 是门控权重，$E_{\mathrm{shared}}$ 是共享分支。这个式子概括路由与共享输出关系，不给出路由容量、溢出策略或通信调度的完整细节。

因此，模型卡的“128 experts、4 active”与配置中的共享专家字段应分别阅读。不能仅凭“4 active”断言总的活跃 MLP 参数精确等于四个专家，也不能把共享专家遗漏后又把公开的 6B、6.5B 或 8B 说成已完全对账。

### 79.2.4 公布的 256K 上下文不由位置配置字段单独决定

Mistral [模型卡](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603)和[产品页](https://docs.mistral.ai/models/mistral-small-4)公开标称 256K 上下文；所检查配置的 `max_position_embeddings` 为 1,048,576，并含位置扩展字段。这个配置值说明指定配置怎样声明位置范围，不单独证明模型经过 1M 长度的质量验证、产品端接受 1M 输入，或每种推理后端都能运行该窗口。

有效上下文还取决于训练与评测、位置外推、输入模态展开、服务合同和资源预算。报告模型窗口应引用公开支持和实际验证口径，而不能只摘出一个更大的配置字段。

## 79.3 参数、KV 状态和模型窗口需要分开估算

总参数、每 token 计算量、KV cache 和可用上下文不是同一个“模型大小”。MoE 每个 token 只走部分路由专家，可能降低每 token 的矩阵乘量，但权重制品仍包含大量未被该 token 选择的专家。MLA 改变历史状态的表示方式；上下文窗口描述模型或服务能接收多长的序列。这几个账本需要分别计算。

### 79.3.1 6B、6.5B 与包含嵌入/输出的 8B 有不同公开口径

Mistral [发布文章](https://mistral.ai/news/mistral-small-4/)写“6B active”，并另称“including embeddings and output layers”为 8B；[模型卡](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603)与[官方模型页](https://docs.mistral.ai/models/mistral-small-4)写约 6.5B activated/token。它们都同时公开约 119B total parameters。可见材料没有提供足够细的逐层参数表来把这些激活参数口径精确换算成同一个数字。

应保留来源各自的说法，不能自行挑一个数字消去差异。总参数主要关联完整权重规模、分片与存储；激活参数近似描述每个 token 实际参与计算的参数量。两者都不能单独给出整机显存或端到端时延：还要考虑 KV 状态、专家通信、批量和临时工作区。

### 79.3.2 压缩 KV cache 的指定实现每层每 token 存 320 个 BF16 数值

按上一节缓存形状，若 36 层都缓存每 token 256 个 KV latent 数值和 64 个位置 key，每 token 的缓存元素账本为：

```math
N_{\mathrm{cache/token}} = 36(256+64)=11{,}520 \text{ values}
```

若缓存值按 BF16 计算，每个值占 2 bytes：

```math
B_{\mathrm{cache/token}} = 36(256+64)\times 2 = 23{,}040 \text{ bytes}=22.5 \text{ KiB}
```

这里的 320 是每层元素数，11,520 是 36 层合计元素数。对照配置中 32 个 KV heads、key 每头 $64+64=128$ 维、value 每头 128 维的显式 K/V 账本，每层每 token 会保存：

```math
N_{\mathrm{explicit/token/layer}}=32(128+128)=8{,}192 \text{ values}
```

元素数之比为 $8{,}192/320=25.6$。它只说明这些配置维度及该 Transformers 缓存路径下的存储元素差异，不是跨实现的显存或速度倍率。

### 79.3.3 256K 单序列只计上述 cache 已约为 5.625 GiB

以模型卡标称窗口 $256\text{K}=262{,}144$ token 估算，并假设每个 token 都按上述 BF16 缓存：

```math
22.5 \text{ KiB/token}\times 262{,}144 \text{ tokens}=5.625 \text{ GiB}
```

这是单序列、单份历史 KV 状态的静态估算。它没有计入权重、图像输入可能带来的 token 数、分配器对齐、并发序列、路由缓冲区、draft 状态、临时激活和 runtime workspace，所以不是整机显存最低值，更不是硬件部署承诺。

MoE 主要改变每 token 经过哪些 FFN 参数；MLA 主要改变注意力历史如何存储。即使 active parameters 较少，长上下文状态仍会占用显著显存；即使 KV 状态更紧凑，也不代表 119B 全部权重能放入一张卡。

## 79.4 reasoning_effort 是请求级控制面，效果要按工作负载评估

公开的 `none` 与 `high` 是同一模型的两种请求设置。它们适合当成评测变量，不能直接当作两套架构或确定的计算预算。对请求端可观察差异作测量，和推断模型内部如何实现这种差异，是两种不同工作。

### 79.4.1 `none` 与 `high` 是同一模型公开的两个模式值

资料将 `none` 用于不启用较深推理的请求，将 `high` 用于需要较深推理的请求。它是一种调用时控制入口；在不知道服务端具体实现时，不应进一步推断它一定改变模型参数、切换专家集合、调用额外模型或设置固定 token 预算。

### 79.4.2 测试时计算的具体内部机制仍属未披露范围

模型发布材料把 reasoning effort 与可调节的推理深度或测试时计算联系起来，但没有完整说明该字段在模型内部对应什么执行步骤、使用何种停止准则、是否改变专家路由，以及如何影响隐藏状态。外部可见的回答长度或质量差异不能独立证明某一种内部机制。缺少实现或技术报告时，应把结论限制在公开接口语义和实际可测行为。

### 79.4.3 固定任务后同时测答案质量与生成成本

比较两种模式时固定模型 revision、提示词、任务集、工具与环境、采样设置、最大输出预算和硬件。按任务选择正确率、代码测试通过率或结构化输出校验等质量指标；同时记录输出长度、首 token 延迟（TTFT）、每输出 token 延迟（TPOT）、端到端时延及 p95。对有重试或人工复核的流程，还要报告单位成功成本。

若 `high` 提高了任务成功率但也增加生成时长，是否值得采用取决于成功价值与服务约束。只在简单任务上比较平均 token 数，不能推断它对复杂代码或长链路任务的总体收益。这里给出的是评测设计，不是 Mistral Small 4 的实测结果。

## 79.5 EAGLE 把特征级草稿与目标模型验证接成一轮

普通自回归解码每生成一个 token，都要等待目标模型给出下一个 token 分布。推测解码让较轻的草稿机制先提出候选，再由目标模型并行检查；若候选与目标分布相符，就一次接受多个 token，若不符则在分歧处校正。它节省的是串行等待，代价是额外草稿计算与目标验证计算。

原始 EAGLE 将草稿放在目标模型的中间特征层，而不只是训练一个独立小语言模型。它预测中间特征，再借目标模型的归一化与语言模型头得到候选 token。机制来自[EAGLE 原论文](https://proceedings.mlr.press/v235/li24bt.html)及[论文全文](https://arxiv.org/html/2401.15077)；[NVIDIA 的推测解码讲解](https://developer.nvidia.com/blog/an-introduction-to-speculative-decoding-for-reducing-latency-in-ai-inference/)也展示 proposer、verifier 与拒绝校正的整体流程。这些资料解释方法，不证明 Mistral 制品采用哪一代或达到何种性能。

### 79.5.1 草稿只提出候选，输出权仍由目标模型掌握

设目标模型在已接受前缀 $s$ 后的下一个 token 分布为 $p(\cdot\mid s)$，草稿机制提出的分布为 $q(\cdot\mid s)$。草稿可以提议 token 或形成候选树，但不单独决定最终输出。目标模型会在候选对应的上下文上计算分布，再由验证与校正规则决定哪些 token 成为已确认的生成前缀。

这不同于“让小模型接管后续生成”。按正确算法验证和拒绝时，草稿质量影响接受率和额外计算，而不会把最终输出权从目标模型转交出去。

### 79.5.2 原始 EAGLE 在第二顶部特征上自回归并输入前移 token

普通 token 草稿直接预测下一个离散 token；原始 EAGLE 则预测目标模型靠近输出端的隐藏特征。论文使用第二顶部层的特征作为草稿目标，并复用目标模型的语言模型头把预测特征映射为 token 概率。这样草稿沿着目标模型学到的特征空间前进，而不是只从 token ID 重新学习全部输出结构。

特征预测有一个困难：目标模型的下一位置特征依赖下一 token，而生成时这个 token 尚未知。EAGLE 使用前移一个时间步的 token 作为条件输入；草稿生成候选 token 后，再将它作为下一步预测的离散条件。草稿仍是近似的，候选随后须由目标模型检查。

EAGLE-3 后来改变了特征使用与训练方式。Mistral 制品页面只标为 EAGLE，未标出代际，因此不能把原始论文的具体结构冒充为该制品的已确认实现。

### 79.5.3 Tree Attention 让目标模型一次读取候选树的条件分布

连续草稿在某一步分歧后，其后续候选都属于不同上下文。EAGLE 可把共享前缀和分支候选组织成树，再由目标模型在一个批量前向中计算多个节点的条件分布。树状验证的掩码必须让每个节点只看到根前缀和自己分支上的祖先；兄弟分支不能互相读取，后代也不能影响祖先。否则所得就不是各候选路径需要的自回归条件分布。

树深、宽度和节点排列会改变目标侧计算量；候选更多不必然意味着有效接受更多。论文机制说明候选路径可以并行计算，不表示任意标准 causal attention 调用都能自动实现同样结果。

### 79.5.4 接受概率和残差分布解释为何拒绝后仍保持目标分布

设 $p(x)$ 与 $q(x)$ 是同一已接受前缀、同一词表和同一采样规则下，目标模型与草稿对候选 $x$ 的概率。草稿候选按以下概率接受：

```math
a(x)=\min\left(1,\frac{p(x)}{q(x)}\right)
```

如果候选被拒绝，就从目标分布减去草稿已经覆盖的概率质量，再归一化抽样：

```math
r(x)=\frac{\max(p(x)-q(x),0)}{\sum_z \max(p(z)-q(z),0)}
```

被接受的候选质量为 $q(x)a(x)=\min(p(x),q(x))$。草稿概率超过目标概率的部分会被拒绝；拒绝事件按 $r$ 重新分配到目标仍有剩余概率质量的 token。因此正确实现下，接受分支与修正分支合起来恢复目标分布 $p$。这只保证相对于当前 verifier 的分布，不保证量化目标与原始高精度目标行为相同。

用两个 token 做教学演算：目标分布为 $p=(0.6,0.4)$，草稿分布为 $q=(0.75,0.25)$。提议 A 时接受率为 $0.6/0.75=0.8$，A 的接受质量为 $0.75\times0.8=0.6$；拒绝质量为 $0.15$，由残差分布全部给 B。提议 B 时接受率为 $1$，接受质量为 $0.25$。最终 A 的概率是 $0.6$，B 的概率是 $0.15+0.25=0.4$，仍为目标分布。该例只演示校正关系，不是 Mistral 的接受率。

序列草稿按每个已接受前缀依次验证；第一个拒绝发生后，依赖错误前缀的后续候选都要丢弃。树式算法还要使用与候选树构造匹配的分支概率和校正规则，不能把链式公式机械套在任意剪枝树上。

### 79.5.5 接受的前缀被提交，拒绝分支及其缓存被丢弃

可把一轮候选树想成尚未确认的多个续写草案。目标验证后，最长被接受前缀才能并入正式上下文；若所有候选都接受，算法还可按其规则从目标分布取得额外 token。拒绝处的替代 token 进入上下文，但它之后建立在错误分支上的候选全部作废。

推理后端必须让 KV 状态与决定同步：保留已接受前缀对应的状态，撤销或忽略拒绝分支及其后续位置，再以替代 token 继续。缓存采用何种页、索引或回滚方式由后端决定，不是 EAGLE 概念固定规定的布局。状态提交错误会让后续生成基于未被 verifier 确认的内容。

### 79.5.6 加速取决于接受长度和整轮计算，而非草稿 token 数

若一轮目标验证平均确认 $a$ 个草稿 token，并按算法再生成一个目标 token，每轮前进的 token 数可近似为 $a+1$。但每轮时间还包括草稿头计算、候选树构建和目标验证。一次验证多个节点虽可并行，仍要占用算力、显存带宽和调度资源。

比较 EAGLE 与普通解码时，应固定硬件、模型精度、上下文长度、batch 和输出任务，测端到端延迟、TPOT、吞吐、接受长度及额外显存。低接受率、昂贵树验证或高并发调度都可能抵消草稿收益。其他模型上的论文加速数字不能直接当成 Small 4 结果。

## 79.6 Mistral EAGLE artifact 的名称不足以确认代际和配对能力

Mistral 基础模型卡链接了一个名为 Mistral Small 4 EAGLE 的仓库。所检查的模型卡与指定 revision 能确认它是与 Small 4 关联的草稿制品；名称和链接没有给出足以复现训练、树设置及所有后端适配的说明。制品存在不等于每种 target checkpoint、精度和 runtime 的组合都受支持。

### 79.6.1 官方链接指向一个附属于 Mistral Small 4 的草稿制品

[基础模型卡](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603)链接至[Mistral Small 4 EAGLE 仓库固定 revision](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603-eagle/tree/9a8ea22)。该仓库是辅助草稿权重，不是与目标模型等价的独立聊天模型。记录时应分别保留目标模型 ID、target revision、draft revision 和运行时支持情况。

### 79.6.2 model card 未标注 EAGLE 代际或 Small 4 专属性能表

所检查的 Mistral EAGLE 模型卡没有明确写出它属于 EAGLE-1、EAGLE-2 还是 EAGLE-3，也没有给出在固定模型、硬件与 serving 设置下的 Small 4 接受长度或性能表。原始 EAGLE 与[EAGLE-3 论文](https://arxiv.org/abs/2503.01840)可以说明方法版本的差别，却不能替 Mistral 制品补出未公开的代际标签。

部署或复现时，应从制品配置、runtime 文档和实验记录确认层映射、树结构、词表、目标权重版本及精度。确认不到的字段应列为待核，而不是从论文默认值或仓库名猜出来。

### 79.6.3 head 与目标权重或 NVFP4 checkpoint 的适配必须单独核验

目标权重或结构变化后，草稿分布 $q$ 与验证分布 $p$ 的差距可能变大，表现为接受长度下降。即使草稿仍能被目标 verifier 正确校正，这也只保证结果相对于该 verifier 分布，而不保证与选定的高精度 target 相同。

截至所检查的模型卡与固定 EAGLE revision，公开材料没有明确确认该 head 与 NVFP4 checkpoint 的组合结果或兼容矩阵。实际组合前应确认后端支持、结构/词表匹配、模型载入和拒绝分支状态，再测目标任务质量、接受长度及端到端性能。不能将 EAGLE 与 NVFP4 两项单独介绍相乘，推算联合收益。

## 79.7 NVFP4 把低位 payload 与尺度层级一起存储

四位表示只说明每个量化值的 payload 位数。浮点数还需要尺度信息恢复数值范围；完整检查点也可能保留部分高精度张量，采用打包与对齐布局，并附带配置等文件。模型压缩、权重搬运、矩阵计算和实际 GPU 占用不是同一个数字。

### 79.7.1 E2M1 的 4-bit 编码依赖 E4M3 block scale 与 FP32 tensor scale

[NVIDIA Transformer Engine 2.19 文档](https://docs.nvidia.com/deeplearning/transformer-engine-releases/release-2.19/features/low_precision_training/nvfp4/nvfp4.html)将通用 NVFP4 表示描述为 E2M1 的 4-bit payload，并以两层尺度恢复动态范围：每 16 个数值共享一个 E4M3 block scale，整个 tensor 另有 FP32 global scale。E2M1 本身可表示的范围有限，局部尺度把一组数值映射到合适范围，全局尺度再调整该 tensor 的整体范围。概念上可理解为“量化值 × block scale × tensor scale”，但实际编码与权重 layout 还由量化 recipe 决定。

NVIDIA 的资料也讨论面向权重的二维 scale 方案。不能把通用一维分组方式直接当成每个模型 checkpoint 的完整配方；数值格式定义和具体模型逐层量化策略是两层信息。

### 79.7.2 Mistral 卡公开 checkpoint 来源但没有完整逐层量化清单

[Mistral NVFP4 模型卡固定 revision](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603-NVFP4/tree/084d625)将制品描述为使用 `llm-compressor` 创建的 post-training quantized 变体，并提及 vLLM、Red Hat 与 NVIDIA 相关支持。这支持制品来源与量化路线的概述。

所检查的模型卡和文件说明没有提供完整的逐层量化/排除表、校准样本、精确 scale layout、各张量 dtype 与高精度保留策略，以及覆盖任务切片的独立质量对照。因此，不把一般 NVFP4 文档的每项 recipe 细节宣称为该 Mistral 检查点的已核事实。

### 79.7.3 4-bit payload 下界不等于 NVFP4 artifact 或 GPU 占用

若作极简假设：1190 亿参数全部只保留 4-bit payload，且不算 scale 或文件开销，下界为：

```math
119\times10^9 \text{ parameters}\times \frac{4\text{ bits}}{8\text{ bits/byte}}=59.5\times10^9 \text{ bytes}
```

即约 59.5 GB（十进制）或 55.4 GiB。若相同数量的参数用 BF16、仅计原始数值，则为 238 GB（十进制）。两者都是按参数总数与位宽做的理论算术，未说明模型卡实际装载方式，也未计 scales、未量化张量、对齐与打包、代码和 runtime 缓冲区。

实际服务显存还要加上并发序列的 KV 状态、draft 相关状态、路由工作区、临时激活及后端开销。Hub 仓库体积、检查点文件大小和 GPU 运行占用分别是不同口径；不能将一个数字替代另外两个。

### 79.7.4 低精度能否变快取决于硬件、kernel 与工作负载

低位权重可能降低权重搬运量，也可能利用特定硬件上的低精度矩阵乘内核。但如果目标 GPU 不支持对应路径、后端需要转换或回退、kernel 未覆盖该张量形状，或者负载主要受其他部分限制，文件更小不必然让 token/s 提高。prefill、decode、batch 与上下文长度也可能处在不同瓶颈区间。

判断 NVFP4 是否适用于某任务，应在固定后端与硬件上分别检查模型质量、峰值显存和实际延迟/吞吐。代码、数学、图像、长上下文等切片可能对量化误差敏感程度不同；模型卡未给出的数据不能由通用格式说明补成实测结论。

## 79.8 部署评估须将模式、draft、量化和服务条件分开

公平对照先建立目标模型基线，再一次加入一个已确认受支持的变量。每条结果至少绑定 target 与 draft revision、精度格式、模式、runtime/backend 版本、硬件、并行方案、上下文、batch、采样参数和任务集。这样才能判断变化来自请求配置、草稿验证、量化还是服务条件。

### 79.8.1 先建立目标 checkpoint 基线，再加入已受支持的单项制品

先测基础 target checkpoint 的 `none` 和 `high` 模式；在有明确后端支持时，再单独加入 NVFP4 checkpoint 或 EAGLE head。只有 artifact 文档和 runtime 明确支持相应组合时，才把 EAGLE+NVFP4 作为实验臂。若兼容性未知，就将它记为待验证配置，不能把尝试性加载称为正式支持。

每轮保存模型与制品 revision、服务端版本、GPU、并行切分、采样配置和输入负载。只写“用了 Small 4”不足以复现，也无法解释软件或硬件变化带来的差别。

### 79.8.2 质量门同时测任务结果和推测校正行为

应用任务指标按场景选择，例如问答正确率、代码测试通过率、视觉文档抽取或长上下文证据检索；还需检查输出格式和失败类型。EAGLE 实验另记录 draft acceptance、平均接受长度、验证工作量、拒绝后采样和状态回滚。NVFP4 则与选定高精度 target 对照任务质量。

这两类判断不能混为一项：speculative sampling 的校正正确性针对它使用的 verifier 分布；量化质量比较量化 verifier 与高精度参考模型。前者通过不代表后者没有精度损失。

### 79.8.3 速度与资源报告要区分 prefill、decode 和并发区间

至少分别报告 TTFT、TPOT、端到端延迟、p50/p95、吞吐、有效输出 token 数和峰值显存，并给出上下文与并发条件。prefill 的大矩阵计算、逐 token decode 的 KV 读取、EAGLE 草稿与验证、NVFP4 权重搬运和低精度 kernel 可能影响不同阶段。用单一 tok/s 概括所有负载会隐藏机制差异。

测试时还应包括失败与回退成本：draft 接受率低时草稿计算仍会发生；量化路径回退到其他 dtype 时，小文件也可能没有预期吞吐。报告观察值和机制推断时应分别标明，不把性能解释写成测量结果。

### 79.8.4 官方 40% latency 与 3 倍吞吐是独立设置下的模型比较

Mistral [发布文章](https://mistral.ai/news/mistral-small-4/)称，Small 4 相对 Small 3 在 latency-optimized 设置下端到端时间降低 40%，在 throughput-optimized 设置下请求吞吐达到 3 倍。这是发布方报告的两个不同优化设置下的模型级比较；发布说明没有把数字拆解成 EAGLE、NVFP4、MLA 或 reasoning effort 各自的贡献。

阅读时保留比较对象、优化目标和发布方来源。没有相同模型、硬件、后端、精度、负载与测量协议下的消融，不能把 headline 数字改写为某个组件的加速比，也不能把延迟降低和吞吐提升合并成普遍保证。
