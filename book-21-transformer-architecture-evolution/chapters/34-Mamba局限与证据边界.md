# 第三十四章：Mamba 的局限：精确检索、ICL、规模验证与生态

## 34.1 先把“局限”说具体

说 Mamba 有局限，不是说它不能处理长序列，也不是说 Transformer 一定更强。要问的是：在哪些能力上，固定或压缩状态可能比显式 token 历史更脆弱；哪些结果来自模型结构，哪些来自训练数据、规模、实现和评测方法。

至少要分开四类主张：长序列内存成本；局部/连续信号建模；内容条件的精确检索；通用语言、ICL 和多证据推理。Mamba 在第一、二类可能很有吸引力，在第三、四类必须用专项实验而不是口号判断。

## 34.2 精确检索的状态瓶颈

显式 attention 保存历史 K/V，当前 query 可以直接对每个历史位置打分。Mamba 把历史压成 state：

~~~math
s_t=F(s_{t-1},x_t)
~~~

若两个历史序列得到相似 state：

~~~math
F(x_{1:t})\approx F(x'_{1:t})
~~~

之后的 query 很难恢复二者差异。选择性更新可以提高关键 token 的写入概率，但不能让有限 state 同时保存所有任意细节。

高价值测试包括随机位置数字、多个相似实体、顺序交换、版本冲突、长距离复制和引用证据。分类或摘要分数高，不能证明精确 recall 没有问题。

## 34.3 ICL 的条件化难点

ICL 要求模型从上下文示例中识别任务规则、标签空间、输入分布和输出格式。attention 可以在预测每个 token 时重新读取示例；递归 state 则需要把这些规则压缩到状态中，并在后续 token 维持。

few-shot 示例越多、任务规则越复杂，状态容量和选择性门控要求越高。某个 Mamba 变体在短 few-shot 上表现不错，不代表它能处理长、多任务、示例冲突或工具返回结果。

## 34.4 规模与训练配方的证据边界

比较 Mamba 与 Transformer 时，必须控制参数量、训练 token、数据质量、上下文长度、tokenizer、学习率、batch、后训练和评估。小规模实验的优势可能在大规模变成劣势，反之亦然。

一个实验结论应至少标注：

~~~text
模型规模 / 训练 token / 数据域 / 序列长度 / kernel / hardware
~~~

如果论文只报告若干 benchmark，不能把结果外推到所有语言、Agent、RAG 或多模态任务。公开模型的性能数字也要绑定 revision 和推理设置。

## 34.5 为什么语言是难题

语言包含离散符号、变量绑定、精确复制、层次结构和长距离条件。连续信号的平滑性可以被状态滤波器利用，语言中的一个 token 可能突然改变解释，例如否定、作用域、版本号或函数变量。

Mamba 的输入依赖参数能让 state 对 token 选择性响应，这是针对语言难点的重要改进；但门控仍受到 state 维度、更新频率和训练任务的限制。它需要在内容识别、写入、遗忘和读取之间分配有限预算。

## 34.6 与外部检索的组合

在需要原文细节的任务中，可以把 Mamba 用作高效序列编码器，再用外部检索保存可寻址事实。流程可能是：

~~~text
长流/文档 -> Mamba 状态扫描 -> 候选片段或索引 -> global reader/LLM -> 答案
~~~

这不是承认 Mamba 无用，而是让状态路径负责压缩和召回线索，让显式检索负责证据保真。系统代价是索引、召回、排序和跨模块一致性。

## 34.7 Hybrid 是一种能力补偿

混合架构可让多数层使用 Mamba/SSM，少数层使用 global attention；也可以在文档边界、问题 token 或工具返回时打开显式路径。设 global 层比例为 r：

~~~math
C_{\mathrm{hybrid}}\approx (1-r)C_{\mathrm{state}}+rC_{\mathrm{global}}
~~~

但质量不随 r 线性变化。少量 global 层如果位置和任务选择正确，可能承担大量证据传递；如果放置不当，增加计算却没有改善关键任务。

## 34.8 Serving 生态的现实成本

Transformer 拥有成熟的 tokenizer、checkpoint、量化、speculative decoding、prefix cache、paged KV 和多模态 connector。Mamba 需要维护 state cache、scan kernel、不同 batch 的 state layout、snapshot/restore 和与已有 API 的适配。

如果模型质量接近，生态差异本身可能决定上线选择。若 Mamba 能显著降低长流单位成本，则迁移值得；若 workload 主要是短 prompt 和复杂工具调用，成熟 Transformer 的风险可能更低。

## 34.9 一个证据矩阵

| 主张 | 最小证据 | 不能单独证明 |
|---|---|---|
| state 随长度固定 | 内存 profile | 精确长程理解 |
| 线性序列计算 | FLOPs/kernel 分析 | GPU 一定更快 |
| 选择性记忆 | store/reset probe | 所有 ICL |
| 长流稳定 | 长序列 loss/恢复 | 任意文档引用 |
| 规模竞争力 | 同预算模型比较 | 生产 SLO |

用矩阵记录结论，可以避免把一个实验的结果扩展成整个架构的宣传语。

## 34.10 失败模式和排查

若长流分类正常、精确复制失败，先查 state 压缩和 gate；若短序列就失败，查 tokenizer、block、初始化和训练；若训练很好、流式推理失败，查 scan/递归一致性和状态 reset；若质量好、速度差，查 kernel fallback、batch 和权重带宽。

评测中还要加入多租户 state 隔离、请求取消、preemption、跨设备迁移和模型版本校验。架构限制和系统 bug 的表现可能相似。

## 34.11 机制与边界：证据级别

论文报告是直接证据，模型卡提供版本和任务边界，独立复现实验提供外部验证，产品页面和社区传言只能作为观察线索。对于闭源模型或未公开 Mamba 变体，不要根据名称猜测 state dimension、层 schedule 或 selective 公式。

理论复杂度是结构证据，kernel profile 是实现证据，真实 workload 是产品证据。三者缺一不可。尤其不要把某个版本在某个硬件上的 throughput 变成架构普遍定律。

## 34.12 面试追问、误区与练习

**问：Mamba 的主要局限是什么？**

标准回答：历史被压缩到递归 state，精确任意 token 检索和复杂 ICL 可能更难；输入依赖 scan 需要专门 kernel；训练/推理生态、状态恢复和多模态工具链仍需建设。是否构成问题取决于 workload。

**问：如何公平比较 Mamba 与 Transformer？**

标准回答：固定数据、训练 token、参数/active FLOPs、tokenizer、上下文、后训练、硬件和服务设置，分开测局部、远距、精确引用、ICL、吞吐、显存、p99、恢复和单位成功成本。

常见误区包括把“线性”当“全方位更强”、只看长序列 loss、用一个 benchmark 代表 ICL，以及把待核验的内部结构写成事实。

练习：为一个 1M 日志系统建立 dense/Mamba/hybrid 三套证据矩阵，列出每条主张需要的实验和上线条件。

## 34.13 证明“能替代”需要什么证据

要声称 Mamba 或其他 SSM 替代 Transformer，至少需要同数据、同训练 token、相近参数和相同评估 harness 的对照。任务要包含局部语言、长程复制、多实体冲突、代码、流式和精确引用。

同时报告训练吞吐、推理吞吐、峰值显存、state size、p99 和失败类型。只在一个分类 benchmark 上更好，不能支持通用替代。

## 34.14 失效时的混合回退

对需要随机访问的请求，可以让 SSM 负责长流扫描，再用 retrieval 或少量 full attention 回读候选证据。回退策略应有明确触发信号，例如 state 置信度低、证据字段缺失或 verifier 不通过。

这类组合通常比“所有任务都换成 SSM”更容易落地，但会增加路由、来源和 cache 管理复杂度。

## 34.15 从“局限”到可测的失败类型

Mamba 的局限不能只写成一个抽象的“不能记忆”。至少应区分四种失败：事实完全忘记、事实仍有影响但无法精确解码、多个实体发生状态碰撞、以及模型其实找到了事实但输出格式错误。它们对应不同的修复路径：扩大或改变 state、加入 selective update、引入 global/retrieval，或修正后处理和训练数据。

长程测试可以把目标 token 放在不同位置，加入相同格式的干扰数字和冲突版本，报告位置曲线：

~~~math
R(p,L,m)=\Pr(\text{exact answer}\mid p,L,m)
~~~

其中 p 是证据位置，L 是总长度，m 是相似实体数量。单一平均分无法告诉我们失败来自长度、位置还是实体碰撞。

## 34.16 公开证据、结构推断和未知部分

阅读模型资料时，结论可以分三层。论文或官方技术报告明确写出的结构属于公开事实；根据输入输出、资源曲线和开源代码做出的解释属于有条件推断；没有资料支持的内部层数、路由规则、state 维度和训练配方属于未知。三层不能在正文中混成同一种语气。

这条纪律对闭源 frontier 模型尤其重要。一个产品支持长上下文、流式输出或“thinking”，并不能据此推出它一定使用 SSM、NoPE、某种 MoE 路由或特定位置编码。面试中明确证据边界，往往比给出看似精确但无法验证的内部结构更专业。

## 34.17 迁移成本是架构选择的一部分

如果现有系统已经围绕 Transformer 建立 tokenizer、KV cache、量化、推测解码和多模态 connector，换成 Mamba 的成本不只是重新训练权重，还包括 serving state、监控指标、故障恢复、评估集和开发者工具。只有在目标 workload 的质量和单位成本收益足够大时，迁移才值得。

可以把迁移决策写成总成本：

~~~math
C_{\mathrm{migration}}
=C_{\mathrm{retrain}}+C_{\mathrm{serving}}
+C_{\mathrm{eval}}+C_{\mathrm{risk}}-C_{\mathrm{saved}}
~~~

其中风险成本包括不可解释回归、生态缺口和故障恢复难度。这个表达提醒读者，架构创新不是只比较一次 benchmark。

## 34.18 证明“可替代”需要完整证据链

声称 SSM 可以替代 Transformer，至少要回答四个问题：在相同数据和训练预算下是否达到质量；在目标长度和任务上是否保留精确检索；在目标硬件和 batch 下是否有端到端收益；在现有 tokenizer、工具、量化和 serving 生态中是否可维护。只满足其中一个，不能推出全面替代。

实验应把架构、训练配方、参数规模、上下文 curriculum、kernel、硬件和评估 harness 记录下来。闭源模型只披露能力时，应把内部架构和训练机制列为未知；开源模型也要绑定代码 revision，因为实现细节可能决定 scan 是否真的高效。

## 34.19 Hybrid 是可验证的回退设计

混合模型可以让 SSM 处理流式和局部模式，让少量 attention 或 RAG 处理精确证据。关键不是层比例，而是接口：global path 何时触发，证据如何回传，state 如何与 KV 对齐，fallback 如何收费和回滚。

一种安全策略是先用 state 路径生成候选，再在证据缺失、候选分歧或高风险任务上调用显式检索/attention。评测要报告触发率、额外延迟、质量提升、显存变化和错误类型，避免把所有请求都默认送入昂贵路径。

## 34.20 失败预算与混合实验

当 SSM 在精确检索任务上失败时，不应立刻把全部流量切回 attention。先区分错误是否集中在长距离、实体数量、冲突版本、状态 reset 或输出格式，再为每类错误设置预算。例如高风险引用任务可以要求 `exact_recall=1`，普通流式摘要则允许一定的压缩损失。

一个 matched experiment 至少包含 dense baseline、SSM、SSM+retrieval 和 hybrid 四条路径，固定训练 token、参数预算、tokenizer、解码和硬件。除任务质量外，还记录 state bytes、prefill/decode、p99、恢复时间、外部检索成本和 fallback 触发率。只有这样，才知道 SSM 的节省是否被回读与验证成本抵消。

## 34.21 把能力边界写成可证伪假设

“Mamba 不擅长精确检索”仍然太宽泛。可以把它拆成可证伪的假设：在固定状态维度和训练预算下，随着实体数量增加，远距数字 exact recall 会下降；加入输入依赖 gate 后，带控制标记的 reset 任务会改善；加入 retrieval 后，引用支持率会改善但延迟和成本会上升。

每个假设都要有 matched baseline、困难样本和失败判据。若实验没有出现下降，不能继续重复口号；若下降只发生在某一 tokenizer 或实现版本，也不能推广到所有 SSM。报告中把公开论文支持、自己实测和结构推断分列，才能避免把讨论写成新闻观点。

## 34.22 选择性状态的失败归因

当 Mamba 类模型在长任务上失败时，先区分四种情况：状态没有写入关键信息，状态写入但在后续衰减，状态保留了主题却丢了精确字段，或者模型已经保留信息但输出/工具协议错误。可以通过遮挡关键 token、增加 state 维度、改变 chunk 长度、强制回读和比较 full/chunk/step 输出来区分。

只看 perplexity 不能完成归因。数字复制、实体消歧、否定条件、版本冲突和引用位置应成为独立 probe；这些 probe 对状态选择性和压缩误差更敏感。

## 34.23 worked example：看似线性，任务却变贵

假设一个固定 state 模型把长日志处理成本降到近似线性，但它在精确引用任务上的成功率从 `0.92` 降到 `0.78`。如果每次失败都触发 retrieval 和 verifier，单次成功成本可写成：

```math
C_{\mathrm{success}}
=\frac{C_{\mathrm{state}}+C_{\mathrm{retrieval}}
 +C_{\mathrm{verify}}+C_{\mathrm{retry}}}
 {p_{\mathrm{success}}}.
```

即使主模型成本下降，回读和重试也可能使单位成功成本上升。正确结论应绑定任务类型：摘要可能受益，审计和代码证据任务可能需要 hybrid 或 attention fallback。

## 34.24 证据边界和复现要求

SSM 的论文、模型卡和工程 benchmark 各自回答不同问题。论文可以证明某种结构或复杂度，模型卡可以说明公开配置，benchmark 可以显示一个条件下的结果；没有公开资料支持的内部训练细节不能由名称或结果倒推。

复现实验至少固定长度、数据、训练预算、dtype、kernel、batch、state reset、chunk、工具和 verifier。报告平均值之外的中位数、p95、失败类型、恢复时间和外部补偿成本，才能避免把一次成功样例写成普遍能力。

## 34.25 一个状态碰撞的教学实验

“状态有限，所以会丢信息”是机制直觉，但还不够成为实验结论。可以用一个极小的递归编码器展示碰撞如何产生：令状态只有两个计数槽位，输入 token 按类别累加并取模；当序列变长时，不同历史会得到同一个 state。真实 Mamba 的 state 更新不是这个玩具函数，但这个例子能让读者看到压缩与可逆性的关系。

```python
def encode(sequence, width=2, modulus=5):
    state = [0] * width
    for token in sequence:
        for i, value in enumerate(token):
            state[i] = (state[i] + value) % modulus
    return tuple(state)


histories = [
    [(1, 0), (0, 1)],
    [(0, 1), (1, 0)],
    [(2, 0), (4, 1)],
]

for history in histories:
    print(history, encode(history))
```

前两条历史在这个编码器中可能产生相同 state，说明后续 reader 若只看到 state，就无法恢复顺序；第三条历史还可能在取模后与其他历史相撞。真实模型可以通过更高维 state、输入依赖的门控、非线性和训练目标降低碰撞概率，但只要表示不是可逆地保存全部历史，任意精确查询就需要额外假设或外部回读。

因此，实验报告不应只说“SSM 有固定 memory”。应该报告 state 的字节数、任务需要的可区分实体数、训练长度、精确字段长度和碰撞/漏召回曲线。状态越小不一定越好，关键是它是否覆盖目标 workload 的信息访问模式。

## 34.26 从 state 维度到任务容量

设每个请求的递归状态有 `d_s` 个元素，每个元素占 `b` 字节，层数为 `L`，并发为 `B`，则一个粗略的 state 预算为：

```math
M_{mathrm{state}}
\approx B L d_s b.
```

这比随 token 长度增长的普通 KV cache 更容易预测，但它没有告诉我们 state 能表达多少种可查询事实。若任务需要同时区分 `K` 个实体、每个实体有 `V` 种版本，理论上至少需要处理 `K V` 类组合；实际神经表示还要为噪声、顺序、关系和输出解码留出裕量。不能把 `d_s` 个浮点数直接等同于 `d_s` 个可靠记忆槽位。

可以把精确任务的有效容量写成条件化函数：

```math
\mathrm{Cap}_{\mathrm{exact}}
=g(d_s,L,T_{mathrm{train}},K,V,\mathrm{noise},\mathrm{reader}).
```

函数 `g` 没有通用闭式解，必须用 probe 测量。一个实用做法是逐步增加实体数量、版本数量和干扰长度，寻找 exact recall 下降到门限的区域；再比较扩大 state、加入 global layer 和使用 retrieval 的收益。这样才能知道瓶颈是容量、选择性、训练长度还是 reader。

## 34.27 失败归因的最小实验矩阵

同一个最终错误可能来自四个不同位置。可以固定模型和输入，做下面的最小对照：

| 对照 | 改变的变量 | 主要判断 |
| --- | --- | --- |
| mask 关键 token | 删除或替换证据 | 是否真的写入 state |
| 只改 chunk 边界 | 内容不变，重新分块 | scan 的边界一致性 |
| state snapshot/restore | 中途保存并恢复 | 状态序列化和设备迁移 |
| 强制 global/retrieval | 允许回读原文 | 压缩错误还是输出错误 |

若删除关键 token 后答案完全不变，说明模型可能依赖先验或存在数据泄漏；若只改变 chunk 边界就下降，优先查实现的递归一致性；若回读原文后恢复，则主要问题是压缩/召回；若已经找到证据却引用错，修复点在 reader、模板或 verifier。

## 34.28 证据等级和未知部分

Mamba 论文（https://arxiv.org/abs/2312.00752）明确讨论了选择性 SSM、语言任务和硬件感知算法；Mamba-2/SSD（https://arxiv.org/abs/2405.21060）提供了状态空间模型与注意力形式之间的统一视角；S4（https://arxiv.org/abs/2111.00396）可用于理解前置状态空间路线。这些资料支持相应论文模型和实验条件，不自动覆盖后来所有变体。

公开模型卡可以支持参数、上下文、权重和接口等披露；独立 profile 可以支持某个硬件上的吞吐；结构推断只能说明一个可能机制。没有公开证据的 state dimension、层调度、内部路由和训练配方必须保留为未知。把未知写成精确数字，会让读者无法区分论文事实和猜测。

## 34.29 小结与资料边界

Mamba 的局限不是一句“不能检索”可以概括的，而是状态压缩、内容选择、任务容量、规模证据和系统生态之间的边界。用碰撞 probe、位置/长度曲线、state 恢复和 global 回退把边界变成可测失败类型，才有资格讨论某个 workload 是否适合 Mamba；不能把一个模型或一个 benchmark 的结果写成所有 SSM 的普遍定律。
