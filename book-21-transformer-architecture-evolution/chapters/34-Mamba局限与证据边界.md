# 第三十四章：Mamba 的局限：精确检索、ICL、规模验证与生态

前两章已经解释了 Mamba 怎样用输入依赖的状态更新处理序列，以及这种扫描实现为什么可能降低某些长序列计算和内存开销。本章接着问另一个问题：当读者需要从已经读过的内容中找回一条指定事实，或依据上下文示例判断当前任务时，Mamba 的递归状态路径会带来什么影响？回答必须落到具体任务和实验条件，不能把架构简化成“能记忆”或“不能记忆”。

这里的“局限”主要指历史信息怎样被保留、寻址和读出。本文把精确关联检索、不同类型的上下文学习（ICL）、规模比较和版本差异分开讨论。ICL 的基础定义和示例作用见[第十二章](12-in-context-learning与显式token检索能力.md)，长上下文中的证据位置效应见[第十三章](13-长距离依赖与lost-in-the-middle.md)；Mamba-2/SSD 的机制由[第三十五章](35-Mamba-2与State-Space-Duality.md)展开，跨架构替代判断留给[第三十六章](36-SSM替代Transformer的证据与争议.md)。服务引擎和部署测量则分别由第六册与第二十四册主讲。

## 34.1 局限要落在具体信息访问任务

读者可以先对照两种读取路径。因果注意力为历史位置保留 key 和 value；生成到新位置时，当前 query 可以与这些历史 key 逐一计算相关性，再读取对应 value。Mamba 则在每个 token 到来时更新递归状态，并由输入依赖的参数控制哪些信息写入、保留或读出。它能选择性处理内容，但不会像显式 key-value 缓存那样，为每个历史 token 保留一条可由任意后续 query 直接寻址的记录。[Mamba 原论文](https://arxiv.org/abs/2312.00752v2)用 selective-copying 等合成任务说明输入依赖选择的作用；[《Dive into Deep Learning》的 Mamba 讲解](https://d2l.smola.org/chapter_recurrent-modern/mamba.html)也通过状态写入与读出解释这种机制。两者都不能据此证明模型可以精确重读任意历史内容。

状态路径不是简单的“把每个 token 丢掉”。训练后的递归状态可以保留对目标任务有用的统计、模式或事实，也能通过非线性和门控形成复杂表示。关键差别在于：随着序列增长，历史经过有限维状态反复变换；后续查询只能从当前状态及其读出路径中取信息。若任务要求区分很多内容相近的历史，并在很晚之后精确返回某个字段，模型就必须把相关差异保存在状态里，而且保留到查询到来时仍能正确解码。

理论分析可以说明这条路径在某些形式化任务中受到什么限制，但结论依赖所研究的状态模型类别、状态规模、精度和任务定义。[Jelassi 等人的复制研究](https://proceedings.mlr.press/v235/jelassi24a.html)分析了固定大小潜在状态的广义状态空间模型，并比较复制与上下文检索任务；它提醒读者，固定状态的表达能力与实际训练能否学出有用表示是两个问题。这个结果不能不加条件地改写成“Mamba 对任何精确检索必然失败”。反过来，某个模型在摘要或分类上表现良好，也不足以说明它能按 query 精确找回任意原文。

因此，讨论“局限”时先说清读者要模型访问什么信息：

- **保留主题或趋势**：输出只需概括一段内容，允许压缩掉局部细节。
- **按 key 返回 value**：输入给出若干关联事实，之后要求精确返回其中一项。
- **复制原文或字段**：必须保留具体 token、数字、标识符或版本字符串。
- **从示例归纳规则**：需要判断示例背后的函数、映射或序列生成规律。
- **组合多处证据**：答案依赖多个位置间的关系，而非从单点取回一项。

这些任务对状态保留和读取的要求不同。以下各节因此分别看检索、ICL 和规模证据，而不以单一 benchmark 为整个架构定性。

## 34.2 多条目精确检索如何暴露状态路径边界

设想一段变更日志记录多个服务版本、参数和值，最后的问题要求返回“服务甲在版本乙使用的超时值”。答案可能只出现过一次，也可能与其他服务共享相似字段；版本记录还可能前后冲突。读者能看到，模型需要完成的不是一般摘要，而是保存记录间的关联，识别 query 指向哪一项，再精确输出对应字段。若把正确答案改成近义表达或概括，虽然语义相近，仍不能算精确召回成功。

评测应逐步改变信息访问难度，避免只用一个平均分掩盖具体失败位置：

| 测试变化 | 主要检查什么 | 结果不能单独说明什么 |
| --- | --- | --- |
| 只有一条事实，逐步增加它与 query 的距离 | 单条长距离信息是否仍可读出 | 不能说明模型能处理多条事实或冲突实体 |
| 增加 key-value 条目和相似干扰项 | 状态是否能保留多条关联并区分 key | 不能把失败直接归因于状态维数 |
| 将目标事实分散到不同位置，或集中放在局部 | 结果是否依赖局部模式和证据密度 | 不能外推到任意自然文档分布 |
| 改变事实与 query 的先后顺序 | 相关性线索何时可用，以及顺序是否影响结果 | 不能据此判断所有训练顺序或提示格式 |
| 加入显式目标标记或改写 query 格式 | 相关性提示能否帮助模型选择内容 | 不能证明内部失败只有一种原因 |

[You 等人在受控 MQAR 实验中的研究](https://aclanthology.org/2025.findings-acl.629/)展示了这种分层的必要性：在其合成模板和模型设置里，单条局部 key-value 检索可以扩展到 60K 上下文；多条分散或局部密集条目的检索更容易下降，实验还观察到位置与 n-gram 模式捷径。这里的 60K 是特定训练数据、分词器、模板和模型设置下的结果，不表示一般 Mamba 模型都能在 60K 自然文本中可靠引用信息。

另一项针对 query-first Phonebook 任务的[2026 年预印本](https://arxiv.org/abs/2610.19709)报告，在所测 NVIDIA-Mamba 和 Codestral-Mamba 输入中，为目标条目增加局部相关性标记会提高检索准确率；门控干预也会明显改变结果。作者据此提出，部分失败可能与相关性信号何时形成、何时进入选择门有关，而不只是状态总容量。这是受控任务中的证据和解释，不是对所有 Mamba 变体的因果定论。它至少说明：即使事实都在输入里，query 的位置、目标线索和模型读入事实时可见的信息，也可能影响后续读出。

当答案错误时，仅看最终输出无法知道哪一步出错。关键信息可能没有被有效写入，key 与 value 的绑定可能混淆，后续状态更新可能削弱了相关差异，也可能是模型保留了内容但生成时输出了错误格式。因而，精确检索实验应同时记录目标位置、条目数量、干扰密度、query 顺序和提示格式；若要判断机制，再用相应干预区分这些可能路径。不能从一次错误直接跳到“有限状态容量就是唯一原因”。

## 34.3 ICL 是若干任务的集合

ICL 通常指模型不在当前任务中更新参数，而是把提示中的示例和说明作为当前上下文的一部分，据此完成后续预测。这个定义描述模型使用上下文的方式，不代表所有 ICL 任务都要求同一种能力。少量输入输出示例可能要求模型拟合一个函数；一段符号序列可能要求预测隐藏的 Markov 转移规律；另一种任务则只是根据示例格式输出答案。按 key-value 复制和从多处证据推导答案，也常被放在 ICL 研究中，但它们更直接测量关联召回和信息访问。

不同研究的结论并不冲突，只要先对齐任务：

| 任务切片 | 研究结果 | 适用边界 |
| --- | --- | --- |
| 函数近似与部分 NLP ICL | [Grazzi 等人](https://proceedings.mlr.press/v256/grazzi24a.html)报告其 Mamba 与 Transformer 在所测任务上的表现接近 | 仅覆盖论文中的模型、任务和提示设置 |
| 回归、稀疏 parity、决策树与关联召回 | [Park 等人的预印本](https://arxiv.org/abs/2402.04248)报告标准回归 ICL 中两类模型可比；Mamba 在其 sparse parity 任务上成功，而在 decision tree 和 vector-valued MQAR 等任务上失败 | 模型从特定任务分布采样示例并训练；不能等同于任意预训练模型的普遍上下文能力 |
| 随机 Markov 链的下一符号预测 | [Bondaschi 等人的 ICLR 2026 论文](https://proceedings.iclr.cc/paper_files/paper/2026/hash/8fef8a350b54e18758ea546bc984ba28-Abstract-Conference.html)分析了单层 Mamba 学习 Bayes/minimax 最优 Laplacian smoothing estimator 的条件 | 这是特定随机序列预测任务的理论和实验，不是任意事实检索或长文档推理 |
| 知识相关的上下文任务 | [Wang 等人的 2026 年研究](https://aclanthology.org/2026.findings-acl.39/)结合行为评估与干预，指出相似输出表现可能由不同内部路径实现 | 机制结论绑定论文所测模型与任务；行为正确率本身不揭示唯一内部解释 |

这组结果支持一个更精确的说法：Mamba 能在若干上下文规则学习和序列预测任务中展现 ICL，但它在多条目关联召回或其他任务上的表现可能不同。任务分布、示例数量、输入输出编码、上下文长度和训练过程都会改变测量结果。尤其要区分“在任务分布上训练模型学会从示例归纳规则”和“预训练模型在自然提示下自发利用示例”；两者不是同一实验主张。

行为结果和内部机制也应分开写。模型答对，说明它在该协议下产生了正确输出；这不自动证明它通过 attention、递归状态或某一种可解释电路完成了检索。若研究问题是内部路径，就需要对输入、状态或组件做干预并报告任务范围；若问题只是用户能否完成任务，则应使用与工作负载相符的行为指标。不能用一组内部机制分析代替真实任务评估，也不能仅凭总分断言某种机制。

## 34.4 规模与版本比较能确认哪些结果

比较规模较大的语言模型时，参数量相近只是起点。训练数据、token 数、上下文长度训练、tokenizer、后训练、提示格式和实现都会影响读者看到的差异。尤其应把纯 SSM 与 hybrid 分开：混合模型的结果同时包含 SSM 和显式 attention 等路径，不能把它记为纯 Mamba 的能力。

[Waleffe 等人的约 8B 模型研究](https://arxiv.org/abs/2406.07887)比较了 Mamba、Mamba-2、Mamba-2-Hybrid 与 Transformer，并考察 1.1T 和 3.5T token 等训练预算。论文的 3.5T 对照包含 Mamba-2 和 Transformer，而不是纯 Mamba。作者报告纯 SSM 在若干常见 zero-shot 任务上可以匹配或超过 Transformer；在该研究的 5-shot MMLU、Phonebook copying/lookup 和部分长上下文推理评测上则有差距。结果还受 continued pretraining、提示格式和 LongBench 任务组织影响。因此，这项工作能说明在特定预算、模型和评测协议下哪些任务出现差异，不能支持一个脱离版本与任务的“纯 SSM 普遍更强/更弱”结论。

后续版本也要单独对待。[Mamba-3 的 ICLR 2026 论文](https://proceedings.iclr.cc/paper_files/paper/2026/hash/8abd2043b71a074278d5f687947bff9c-Abstract-Conference.html)报告新递归、复值状态和 MIMO 设计在作者测试中改善 retrieval、state tracking 和下游结果；作者团队的[研究说明](https://pli.princeton.edu/blog/2026/mamba-3-improved-sequence-modeling-using-state-space-principles)同时指出，在其 retrieval 比较中纯 Transformer 仍然领先，且 NIAH、半结构化任务与更真实的检索对设计变化反应不同。这些结果说明版本和任务定义会改变观察，不能把 Mamba-3 的进步当成此前 Mamba/Mamba-2 结果的反证，也不能把单项改进外推为所有任务已经解决。

读论文或复查 benchmark 时，应至少固定并记录：

- **模型与结构**：精确模型版本、参数规模、纯 SSM 或 hybrid、checkpoint/revision。
- **训练条件**：数据来源、训练 token、上下文长度与 curriculum、后训练阶段。
- **任务协议**：样本构造、提示与输出格式、检索目标、示例分布和评分规则。
- **实现与测量**：分词器、精度、硬件、kernel、batch、运行时间及吞吐口径。

只要这些条件中有多项不同，结果差异就不能简单归因于“规模”或“架构”。论文结果是对应实验的证据，不是本地复现；若某项信息未公开，应保留为未知，而不是从产品行为或模型名称反推。

## 34.5 用匹配证据评估目标 workload 与生态

要判断某个 Mamba checkpoint 是否适合目标任务，先把“能力”改写成可检验的问题。例如，系统需要从长记录里返回某个字段，就用精确匹配评估，并按距离、实体数量、干扰密度、冲突记录和 query 顺序分桶；系统需要从示例学习规则，就明确规则族和示例分布，再用未见过的输入测试是否学到映射。摘要质量、zero-shot 分类或单一 needle-in-a-haystack 成功，都不能代替这些具体读者任务。

接着固定对照条件：比较模型使用相同的数据、训练预算或公开可比的 checkpoint，明确纯 SSM 与 hybrid；统一 tokenizer、提示、解码与评分协议。报告分桶结果和主要错误类型，而不只给总体平均分。若结论涉及实际部署，再在目标硬件和软件栈上测量端到端质量、吞吐、显存、延迟及回退代价；理论复杂度或单个 scan kernel 的速度不能单独说明用户工作负载是否受益。

生态也应作为具体迁移条件核查，而不是抽象地给某架构贴“成熟”或“落后”标签。检查目标 checkpoint 是否可获取和维护，推理实现是否支持该版本所需的 scan 与状态管理，量化、并行、多设备恢复、监控和现有工具接口是否满足当前系统要求。具体部署设计和引擎细节属于第六册与第二十四册；本章只要求把这些条件作为选型证据记录下来。

因此，Mamba 的局限不是一个脱离任务的“记忆容量”标签。状态路径、query 与相关性信号的关系、ICL 任务类型、训练预算、模型版本和实际实现共同决定测得的能力。读者应先说明目标 workload，再选择能区分失败来源的测试，最后把结论限制在对应模型与协议范围内。是否值得用 SSM 替代 Transformer，需要进一步对齐质量、成本和适用任务，由第三十六章综合讨论。
