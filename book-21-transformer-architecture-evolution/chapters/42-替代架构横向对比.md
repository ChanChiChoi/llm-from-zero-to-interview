# 第四十二章：替代架构横向对比：复杂度、表达力、硬件和生态

## 42.1 横向表不是结论

线性 attention、SSM、Mamba、RWKV、RetNet、Hyena、局部/稀疏 attention 都被称为 Transformer 替代或补充路线。横向表可以帮助定位差异，但不能替代各自章节的数学和实验。任何排序都必须绑定任务、规模、硬件和实现。

本章提供一个决策框架：先区分历史表示和查询方式，再比较训练/推理路径、状态成本、精确证据能力和生态。

## 42.2 主要路线的结构摘要

| 路线 | 历史表示 | 训练路径 | 推理状态 | 内容寻址 |
|---|---|---|---|---|
| Full Attention | 每 token K/V | dense parallel | KV 随长度增长 | 强 |
| Linear Attention | feature 聚合 state | scan/核化 | 固定 state | 受核/状态限制 |
| SSM/Mamba | 递归 state | scan/卷积 | 固定 state | selective 时增强 |
| RWKV | 衰减 KV 统计 | parallel/scan | 固定 state | 统计式 |
| RetNet | 多尺度 retention state | parallel/chunk | 固定 state | 衰减聚合 |
| Hyena | 长隐式卷积 + gate | convolution/FFT | overlap/state | 受滤波器/gate |
| Sparse Attention | 局部/全局/随机边 | sparse blocks | 窗口/部分 KV | pattern 约束 |
| Hybrid | 多种路径 | 路径组合 | 多类 cache | 取决于 global path |

表中“固定 state”只描述随长度不增长，不描述状态容量和可恢复细节。

## 42.3 复杂度的正确读法

对长度 T，理论序列项可以写为：

~~~math
C_{\mathrm{attention}}\sim O(T^2d),\quad
C_{\mathrm{state}}\sim O(Tsd),\quad
C_{\mathrm{conv}}\sim O(T\log T)
~~~

其中 s 是 state/feature 维度，实际还要加入层数、head、projection、kernel 和通信。若 s 很大或更新不规则，state 路径未必更快；若 T 很短，dense attention 的成熟 kernel 可能更优。

## 42.4 表达力的关键问题

不要问“哪个表达力最大”而不说明任务。至少问：

1. 当前 query 能否直接访问任意历史 token。
2. 历史压缩是否可区分相似实体。
3. 后来的条件能否重新解释早期证据。
4. 是否存在全局路径和多证据合并。
5. 长度增加时信息是否按预期衰减。

Full attention 在第一项最自然；state/conv 路线需要用训练和结构补偿；sparse 路线需要保证图可达；hybrid 可以把高价值精确访问保留在少量路径。

## 42.5 硬件和 serving 的比较

| 维度 | Dense attention | State/conv | Sparse/hybrid |
|---|---|---|---|
| GPU 大矩阵 | 强 | 可能偏小 | 依 pattern |
| decode 历史读取 | 随 KV 增长 | 固定/较小 | 窗口或部分 |
| kernel 成熟度 | 高 | 版本相关 | pattern 相关 |
| 内存管理 | paged/prefix KV | state snapshot | 多类 cache |
| batch 动态性 | scheduler 生态成熟 | state owner | 路由复杂 |
| 恢复协议 | KV/position | state/position | 多状态 |

选择架构时，服务工程师应参与模型设计评审，而不是等模型训练完成后才问 cache 如何管理。

## 42.6 一个多目标评分器

~~~python
def architecture_gate(quality, evidence, p99, memory,
                       quality_min, evidence_min,
                       p99_max, memory_max):
    checks = {
        "quality": quality >= quality_min,
        "evidence": evidence >= evidence_min,
        "p99": p99 <= p99_max,
        "memory": memory <= memory_max,
    }
    return checks, all(checks.values())


for name, values in {
    "dense": (0.94, 0.96, 110, 10.0),
    "state": (0.91, 0.89, 70, 4.0),
    "hybrid": (0.93, 0.95, 90, 6.0),
}.items():
    print(name, architecture_gate(*values, 0.92, 0.93, 100, 8.0))
~~~

这个评分器故意设置 evidence 独立验收条件：state 路径更快省内存，但若业务要求精确证据，它不能因为速度好就通过。

## 42.7 训练配方和生态成本

架构比较必须计入重新训练、数据、checkpoint 转换、量化、推理引擎、监控、模型更新和人才成本。一个理论上更优的路线，如果没有 tokenizer、训练稳定性或多模态接口，落地周期可能长于业务窗口。

相反，若已有大量长流数据、专用 kernel 和强状态 serving，state 架构的生态成本会下降。生态是可累积资产，不是固定属性。

## 42.8 任务到架构的初始映射

| 任务 | 初始候选 | 必测风险 |
|---|---|---|
| 长文档精确问答 | attention + retrieval/hybrid | 中间证据、冲突版本 |
| 实时音频/传感器 | SSM/conv/hybrid | chunk 恢复、漂移 |
| 日志流分类 | SSM/retention | 异常数字、状态泄露 |
| 长代码补全 | attention/hybrid | 变量绑定、跨文件引用 |
| 边缘低内存 | state/window/GQA | 设备 kernel、功耗 |
| 大 batch prefill | dense/flash/sparse | kernel 与 padding |

这只是实验起点，不能替代业务数据。

## 42.9 统一评测协议

一套可复用协议应包含：

1. 局部 next-token。
2. passkey/数字复制。
3. 多实体条件绑定。
4. 多证据合并。
5. 冲突版本选择。
6. 长流状态 continuation。
7. batch reorder/preemption/resume。
8. TTFT、TPOT、p99、峰值显存和单位成功成本。

所有模型使用同 tokenizer 约束不一定公平，因为原生 tokenizer 可能不同；要记录这一点。若模型接口不同，统一 wrapper 不能掩盖 protocol/模板差异。

## 42.10 常见失败模式

包括把所有线性路线当同一类、把固定 state 当同一容量、忽略 global path、只比较短 benchmark、只比较理论 FLOPs、没有 profile kernel、没有测试 state/kv 隔离，以及把产品宣传语当架构证据。

审计时应为每个结论标注来源：论文、模型卡、源码、独立实验、工程经验或待核验观察。缺少来源的内部结构不能写成事实。

## 42.11 机制与边界：Pareto 前沿而不是总榜

架构选择是多目标 Pareto 问题。可以把质量、证据 recall、延迟、内存、成本、生态和风险作为维度；没有一个方案支配所有点。不同 workload 会选择不同 Pareto 点。

研究报告最好给出曲线：质量—active compute、evidence recall—state size、p99—batch、吞吐—长度、恢复时间—snapshot size。曲线比“我们的模型更高效”更能支持决策。

## 42.12 面试追问、误区与练习

**问：你会如何判断一种新架构是否值得关注？**

标准回答：先确认公开结构和证据等级，再看它改变了哪一层信息流；在同预算/硬件下测局部、精确检索、长程组合、训练/推理 kernel、显存、p99、恢复和单位成功成本；最后判断它是替代、补充还是特定 workload 路径。

**问：为什么未来可能是 hybrid？**

标准回答：局部/状态路径擅长低成本扫描，attention/retrieval 擅长精确内容寻址，MoE 扩展容量；把职责分开可以改善 Pareto，但增加多状态和调度复杂度。

常见误区包括给架构贴绝对标签、只看模型名字、把结构宣传当结果，以及把横向表当独立章节的替代。

练习：选一个新模型或论文，按本章表格填写信息流、状态、复杂度、kernel、证据、风险和最小复现实验，写出一页技术判断。

## 42.13 统一比较表的最小字段

对 attention、linear attention、SSM、RWKV、RetNet、Hyena 和卷积路线，至少记录：

~~~text
history access
state size
training parallelism
decode update
exact retrieval
kernel maturity
long-context quality
fallback path
~~~

这张表不提供排名，却能防止把“固定状态”“线性计算”和“低延迟”当作同一个性质。

## 42.14 选择路线的场景化结论

精确引用和多证据审计偏向显式 attention 或 retrieval；长流、连续信号和低内存 decode 可优先考虑 state/conv；混合模型在两类任务之间折中，但增加 schedule、cache 和路由复杂度。

最终选择应由工作负载 trace 驱动：真实长度分布、并发、失败成本、硬件和维护团队能力都属于架构输入。

## 42.15 统一实验的三层 baseline

第一层是算法 baseline：相同 hidden 和 token 的 dense attention、linear/state 和卷积。第二层是实现 baseline：相同硬件、batch、dtype 和 kernel。第三层是任务 baseline：相同 prompt、证据、输出预算和 verifier。

只有三层都固定，才能回答“算法是否更好”。否则一个路线可能因为实现优化领先，另一个路线因为评估任务不适合而落后。

## 42.16 复杂度之外的维护成本

替代架构还会影响 checkpoint 转换、量化、监控、调度、故障恢复和人才成本。生产选型应将新 kernel、调试工具、模型升级和回退路径作为长期成本，而不是只算一次推理 FLOPs。

## 42.17 用同一任务观察信息碰撞

横向对比最容易犯的错误，是给每种架构填一行复杂度，然后直接下结论。更有区分度的实验是让不同历史只相差一个关键事实，再在末尾要求模型做选择。例如先写入两个实体和两个版本，加入长度相同的干扰，再改变问题指向的实体。

设历史编码为 S=f(H)，两个历史 H1 和 H2 只在目标字段上不同。如果 f(H1) 与 f(H2) 在读取器看来不可区分，就出现状态碰撞。实验要报告实体数量、证据距离、位置、状态 bytes 和错误类型；不能只报告“长上下文准确率”。

## 42.18 速度收益的组成

替代架构的端到端收益可以拆成：

~~~math
\Delta T
=\Delta T_{\mathrm{algorithm}}
+\Delta T_{\mathrm{kernel}}
+\Delta T_{\mathrm{memory}}
+\Delta T_{\mathrm{scheduler}}
+\Delta T_{\mathrm{fallback}}
~~~

算法层的线性计算只是第一项。若 scan kernel 没有融合、状态更新受带宽限制、batch 被 padding 破坏，或服务中频繁回退到 attention，最终收益可能消失。压测应该给出各项时间，而不是只给总吞吐。

## 42.19 选型结论的证据等级

架构比较可以分成研究结论、实现结论和产品结论。论文表明某种机制在给定任务上有效，不能自动证明开源实现已经稳定；单机 kernel 的 profile 也不能证明多租户服务满足 p99。每次写出“更适合”时，都要附带 workload、硬件、版本和指标范围。

这种证据分级对新模型尤其重要。公开模型卡没有披露的内部结构只能作为未知或条件推断，不能根据模型名称、上下文上限或产品宣传反推具体 backbone。

## 42.20 用失败类型而不是榜单决定架构

对比替代架构时，先列目标失败：长流状态漂移、精确证据丢失、短上下文质量下降、kernel fallback、显存不足、恢复不一致或协议不兼容。不同架构的优势可能对应不同失败类型，不能用一个总分掩盖。

可以建立一个矩阵：行是任务和失败，列是 full attention、sparse attention、SSM、convolution、hybrid 和 retrieval-augmented path；每个格子填质量、资源、成熟度和回退方式。再在目标硬件上做 controlled benchmark，记录平均和尾部指标。

## 42.21 迁移的真实门槛

替换 attention 往往会影响位置编码、KV/state、量化、训练 checkpoint、推理 runtime、prefix cache、speculative decoding 和多模态接口。一个新模块在 toy model 上成功，不代表能直接替换生产模型的一层；转换后的权重和训练/推理路径都要有 golden test。

若新架构不能处理某类工具调用、结构化输出或长上下文恢复，应明确标记 unsupported，并保留 dense fallback。架构选择不是一次论文结论，而是生命周期管理：训练、部署、观察、灰度和回滚都属于成本。

## 42.22 一个端到端选型例子

假设目标是给代码仓库做长时间审计。请求包含长日志、跨文件引用和少量精确版本号，产品要求引用支持率不低于阈值、TTFT p99 不超过 deadline、取消后状态必须释放。此时不能只问 SSM 的理论复杂度，而要比较 dense attention、窗口 attention、SSM+retrieval 和 hybrid 四条路径。

先用同一 tokenizer 和任务集测局部语法、远距复制、跨文件引用、冲突版本和工具 JSON；再在目标 GPU 上测 prefill/decode、KV/state bytes、p99、迁移和 fallback。若 SSM 在日志扫描上省内存，但引用任务需要频繁回读，回读成本应加到 `C_success`；若窗口 attention 省显存，却让证据不可达，应把质量 gate 设为硬失败。

最终结果不是一个总分，而是一张带 hard gate 的 Pareto 表。它应保留 baseline、失败类型、证据级别和回滚方式。只有在目标 workload 上满足质量、SLO、状态和维护验收条件，才有理由把某个替代架构纳入生产。

## 42.23 替代架构的比较条件

可参考 Transformer（https://arxiv.org/abs/1706.03762）、Mamba（https://arxiv.org/abs/2312.00752）、RetNet（https://arxiv.org/abs/2307.08621）、Hyena（https://arxiv.org/abs/2302.10866）和 Longformer（https://arxiv.org/abs/2004.05150）。具体数值必须绑定版本和硬件。

替代架构比较的核心不是背一张排行榜，而是回答三件事：历史如何表示，未来如何查询，系统如何把这种信息流可靠地跑起来。这样才能从论文观点走到工程选择。

## 42.24 先规定比较单位

“哪个架构更快”必须先规定比较单位。可以按每个训练 token、每个生成 token、每个请求、每个成功任务或每个 GPU 秒比较；不同单位会给出不同排序。一个 SSM 可能每 token 成本低，但需要外部 retrieval 才能保证引用；一个 dense 模型可能 token 成本高，却因为缓存命中和成熟 runtime 在请求层更稳定。

建议同时报告：

```text
quality per task / latency per request
tokens or state bytes / GPU-second
successful-task cost / fallback rate
recovery time / maintenance surface
```

把这些量混成单一加权分数时，要明确权重和 hard gate。安全、权限、数据丢失和协议错误不能用平均吞吐抵消。

## 42.25 架构替代的四种层级

替代可以发生在算子、block、模型主干或完整服务系统四个层级。FlashAttention 主要替代 dense attention 的 IO 实现，SSM/conv 可能替代某些 block，hybrid model 替代主干的信息流，RAG/路由则可能替代一部分模型上下文职责。不同层级的证据不能互相代替。

如果一个新 kernel 保持 token-level 输出等价，就可以先做 runtime 替换；如果新 block 改变状态和训练目标，需要重新训练与评估；如果完整服务增加了 retrieval、工具和 fallback，比较对象已经从模型变成系统。正文必须把边界写清楚，否则读者会把局部实验误读成全栈结论。

## 42.26 反事实矩阵和停止条件

架构迁移前至少保留 dense baseline、只换 kernel 的版本、候选架构和候选加 fallback 四条路径。每条路径用相同 tokenizer、数据切片、长度、解码协议和质量验收条件；再做短/长输入、局部/远距、开放/结构化、普通/高风险任务的矩阵。

停止条件应提前写出：关键质量低于阈值、p99 超预算、恢复不一致、fallback 超比例、工具协议错误或迁移维护成本超出预期就停止扩大实验。这样能防止团队因为已经投入大量时间而继续支持一个并不适合的架构。

## 42.27 “替代”结论的资料边界

论文适合支持机制和特定实验，代码/引擎资料适合支持实现接口，目标硬件压测适合支持性能，生产回放适合支持任务成本与可靠性。模型卡或产品页没有披露的内部结构只能作为未知；社区 benchmark 没有 harness、预算和版本也不能直接横比。

最终报告应给出条件句：在某个任务、长度、硬件、runtime 和质量验收条件下，候选路径形成了哪部分优势；哪些能力仍依赖 dense/RAG/工具；失败时如何回退。能做到这一点，比宣称某条路线“取代了 Transformer”更接近真实技术判断。
