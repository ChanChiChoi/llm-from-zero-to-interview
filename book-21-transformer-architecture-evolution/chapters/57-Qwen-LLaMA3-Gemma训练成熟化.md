# 第 57 章 Qwen、LLaMA 3 与 Gemma：开源训练工程的成熟化

## 57.1 开源模型竞争从结构转向全流程

早期比较开源模型时，人们常问它用了哪一种 attention、多少参数和多大上下文。随着基础模块趋同，真正拉开差距的部分越来越多地出现在数据、训练规模、tokenizer、后训练、评测、许可证和部署工具。

Qwen、LLaMA 3 和 Gemma 可以作为观察开源训练工程成熟化的三个锚点。它们不是同一个系列，也不代表所有开源模型，但都提醒我们：一个可用模型是训练配方、数据治理、模型卡、指令模板和生态的联合产物。

## 57.2 模型配置的共同骨架

许多现代开源 decoder-only 模型可以用以下抽象描述：

~~~math
h^{(l+1)}
=h^{(l)}
+\mathrm{FFN}\left(
\mathrm{Norm}\left(
h^{(l)}+\mathrm{Attention}(\mathrm{Norm}(h^{(l)}))
\right)\right)
~~~

差异主要来自 hidden size、层数、head 数、KV head 数、RoPE、FFN 门控、词表、上下文训练、MoE、数据和后训练。单个 block 看起来相似，不代表模型能力或运行成本相同。

## 57.3 Qwen 路线的可观察主题

Qwen 系列的公开资料通常强调多语言、代码、数学、工具调用、不同参数规模和逐步扩展的生态。阅读这类系列时，可以从三个方向理解：

第一，模型覆盖多个尺寸，使用户能在质量、显存和延迟之间选择。第二，数据和后训练覆盖更广的任务，模型不只面向英文聊天。第三，工具、函数调用和多模态接口把模型放入实际工作流。

这些是公开模型卡和技术报告支持的产品/训练方向，不意味着每个版本都使用相同架构。具体的 attention、专家、位置和上下文实现必须逐版本核对。

## 57.4 LLaMA 3 对训练数据规模的强调

LLaMA 3 的公开资料把更大规模、更高质量的数据和 tokenizer 作为重要组成。它说明开源基线的升级不一定来自全新网络模块：数据去重、质量筛选、代码和多语言比例、训练稳定性、上下文和指令数据都能显著影响结果。

一个模型的训练 token 数还要结合 tokenizer 解释。相同原始文本，词表不同会产生不同 token 数；直接用 token 数做横向结论，可能把 tokenizer 压缩率误认为训练数据量。

## 57.5 Gemma 的小模型和开放生态

Gemma 系列提供了面向较小规模部署和研究复用的开放权重路线。小模型的价值不只是成本低，还包括端侧部署、私有化、快速迭代、领域微调和作为大模型的 draft model。

但小模型选择不能只看参数。应同时看：

~~~text
quality per token
quality per watt
quality per dollar
memory footprint
fine-tuning stability
license and distribution
~~~

在一个低风险摘要场景中，小模型可能胜任；在复杂代码修改和多步工具任务中，额外失败率可能让总成本反而上升。

## 57.6 tokenizer 是跨语言和代码能力的基础设施

对文本 x，tokenizer 输出长度记为 T(x)。不同 tokenizer 的 T(x) 会改变：

~~~math
C_{\mathrm{prefill}}\propto T(x)^2,\qquad
M_{\mathrm{KV}}\propto T(x)
~~~

中文、数字、代码、表格和混合文本的分词效率差异，会直接影响上下文容量、推理成本和训练有效 token。新增 special token 还会影响 embedding、模板、损失和服务协议。

评测多语言和代码模型时，应报告原始字符数、token 数、tokenizer 版本和输出长度，而不是只报告字符串长度。

## 57.7 数据成熟化的四个环节

第一是来源治理：记录来源、许可、时间和领域。第二是质量筛选：去除乱码、低信息、重复和恶意内容。第三是配比控制：避免高频网页淹没代码、数学或低资源语言。第四是泄漏与污染检测：保证评测结论没有被训练集记忆虚高。

数据版本可以表示为：

~~~math
D_v=\mathrm{Build}(S,\mathrm{filters}_v,\mathrm{mix}_v,\mathrm{tokenizer}_v)
~~~

任何过滤规则、采样配比或 tokenizer 改变，都应产生新的数据版本。否则训练回归无法定位原因。

## 57.8 后训练和聊天模板

现代开源模型的 chat checkpoint 通常依赖特定角色模板、特殊 token、system/user/assistant 顺序和停止条件。使用错误模板可能出现：

- 输出把角色标记当普通文本。
- 模型不停止或重复生成。
- 工具调用 JSON 结构错误。
- 训练时学到的 system 约束失效。
- 评测结果被模板差异污染。

因此模型卡中 chat template、generation prompt、EOS 和 tool schema 是与权重同等重要的接口。

## 57.9 代码和数学能力的训练闭环

代码和数学不能只靠更多普通网页数据。高质量代码数据需要许可、构建、测试、依赖和语言版本；数学数据需要题目、答案、推导和难度检查。后训练还可能使用执行器、单元测试或可验证奖励。

对一个代码样本，质量标签可以包括：

~~~text
syntax_valid
tests_passed
dependency_reproducible
license_checked
solution_explanation
~~~

如果只把代码字符串放进训练集，模型可能学习风格却不会真正执行；如果只训练最终答案，模型可能缺少中间约束。

## 57.10 多尺寸系列的路由价值

同一系列提供多个尺寸时，产品可以按任务和预算路由。设任务 i 由模型 j 处理，效用为 Q_ij，成本为 C_j，风险为 R_ij：

~~~math
j^\star=\arg\max_j
\left(Q_{ij}-\lambda C_j-\mu R_{ij}\right)
~~~

路由不应只按 prompt 长度。复杂度、语言、代码、工具副作用和历史失败率也可能是信号。路由错误要有 fallback，例如小模型无法通过 schema 或测试时升级到更强模型。

## 57.11 最小的模型审计记录

~~~python
def model_record(name, revision, tokenizer, metrics, license_text):
    return {
        "name": name,
        "revision": revision,
        "tokenizer": tokenizer,
        "metrics": metrics,
        "license_excerpt": license_text[:160],
        "has_context_test": "context_recall" in metrics,
        "has_cost_test": "p95_ms" in metrics,
    }
~~~

这个记录结构提醒我们不要只保存 benchmark 分数。正式系统还应保存来源 URL、下载校验、量化版本、硬件和 prompt harness。

## 57.12 如何公平比较三个开源系列

先固定任务集合和数据版本，再固定 tokenizer 处理方式、模板、解码、最大输出和硬件。能力分桶包括普通知识、代码、数学、多语言、工具、长上下文和安全；系统分桶包括权重加载、吞吐、TTFT、TPOT、p99、显存和量化回归。

对于不同尺寸，画质量—成本曲线，而不是只选单一冠军。对于不同版本，按发布日期和 revision 记录，避免把一个系列的新模型和另一个系列的旧模型比较后作出架构结论。

## 57.13 常见误区

第一，把“开源”当作所有训练资料开放。第二，用参数量替代数据和训练配方。第三，忽略 tokenizer 造成的 token 成本差异。第四，使用错误 chat template 后责怪模型。第五，把一个版本的模型卡事实扩展到整个系列。第六，比较分数时没有固定量化、工具和解码。

## 57.14 开源模型的成熟度如何衡量

一个开源模型的成熟度可以分成四层：权重可加载，训练/推理配置可复现，任务和安全评估可审计，生产生态可维护。开放权重只覆盖第一层的一部分；tokenizer、模板、量化、许可证、模型卡、数据声明和版本管理决定后面几层。

评估开源基线时，除了质量，还要记录加载失败、模板错误、量化退化、工具 schema、上下文恢复、社区 issue 和发布频率。可复现性本身是工程能力，不是附属文档。

## 57.15 数据、后训练和模型结构的交互

当多个模型都使用相似的 RMSNorm、RoPE、SwiGLU 和 GQA 时，性能差异更可能来自数据和后训练。数据 mixture 决定模型接触哪些能力，SFT 决定格式，偏好优化决定交互风格，工具和评测决定产品行为。结构比较不能脱离这些变量。

一个控制实验应固定 tokenizer、模型规模和训练 token，只替换一个因素；若只能比较不同公司发布的完整模型，结论应限制为系统表现差异，而不是模块因果。

## 57.16 小模型不是大模型的简单缩小版

小模型可能有不同的最优数据配比、上下文、量化和后训练策略。它们适合端侧、draft、批量低风险任务和领域微调，但在复杂工具链或多步推理中，失败和重试成本可能抵消单次推理节省。

选择小模型时应计算：

~~~math
C_{\mathrm{effective}}
=C_{\mathrm{inference}}
+C_{\mathrm{retry}}
+C_{\mathrm{human\ review}}
~~~

质量/美元、质量/瓦特和单位成功成本比单纯参数量更能指导部署。

## 57.17 训练成熟化是系统工程

Qwen、Llama 3、Gemma 等路线的进步不能只归因于一个 attention 改动。数据过滤和去重、语言/代码/数学配比、长上下文 mid-training、tokenizer、训练稳定性、SFT、偏好优化、蒸馏和评测一起决定结果。

阅读技术报告时，把改动按数据、架构、优化、后训练、评估和部署分类，记录每类是否有 ablation。没有消融时，只能说发布路线中同时出现了这些因素，不能把增益精确归因给其中一个。

## 57.18 长上下文与短任务保护

扩大 context 需要位置方案、长样本、训练 batch、通信、checkpoint 和 serving 共同配合。长样本比例上升可能损害短代码、格式和指令任务；成熟 recipe 应用固定短任务回归集监测这种回退。

## 57.19 训练报告的可复现清单

至少记录模型 revision、tokenizer、数据版本和去重规则、训练 token、长度分布、学习率/优化器、精度、并行策略、后训练数据、评测 harness 和污染检查。对闭源模型，未知字段要保持未知，不用模型品牌补全缺失事实。

## 57.20 资料范围与训练判断

Qwen、LLaMA 3 和 Gemma 的官方模型卡、技术报告和权重仓库可以支持具体版本的配置与能力声明；社区复现和第三方 benchmark 只能支持对应 harness 下的观察。

这三类模型最值得学习的知识不是某个排名，而是开源训练工程如何成熟：数据有版本，tokenizer 有成本，模板是协议，后训练决定行为，权重许可影响部署，评测必须和系统条件绑定。

## 57.21 面试问题与练习

**问：为什么同样参数量的开源模型差异很大？**

数据质量和配比、tokenizer、训练 token、架构细节、后训练、评测污染和推理设置都可能不同，参数量只是一个维度。

**问：小模型适合什么场景？**

低延迟、端侧、私有化、批量处理、draft model 和结构简单的任务；复杂推理、工具链和高风险任务要用失败率和单位成功成本验证。

**练习：**为 Qwen、LLaMA 3 和 Gemma 设计同一套模型卡审计表，至少包含配置、数据、模板、许可证、能力和服务成本。

资料入口：

- Qwen: https://qwenlm.github.io/
- Llama 3: https://arxiv.org/abs/2407.21783
- Gemma: https://arxiv.org/abs/2403.08295

## 57.22 训练成熟度的审计例子

两个开源模型都宣称支持长上下文和工具调用时，不能只比较 benchmark。先核对数据/代码/权重 revision、tokenizer/template、长样本训练、后训练数据、许可证、量化和 runtime；再用同一套短任务、长文档、工具 JSON、拒答、成本和 p99 测试。若某字段只有模型卡声明，就标成声明；若有论文消融，才可讨论因果证据。

长上下文训练还要观察短任务保护、loss 曲线、packing、checkpoint 恢复和服务 KV。一个模型能在离线长文档上得分，不代表混合长度线上仍满足尾延迟和单位成功成本。

## 57.23 训练成熟度不是发布数量

可以把开源模型成熟度拆成五个可检查的面：配置和权重可复现，数据和 tokenizer 有版本，长上下文/代码/多语言有专门训练证据，后训练协议稳定，runtime、许可证和评估脚本可用。模型卡只写“支持工具”而没有 schema、示例和错误处理，不足以证明工具链成熟。

对 Qwen、LLaMA 3、Gemma 或其他系列，使用同一模型审计表做短任务、长文档、代码、工具 JSON、拒答和成本测试。要记录模型声明、论文消融、权重实测和未知项四种证据。这样比较的是训练工程和生态完整度，而不是把参数量或排行榜当成成熟度代理。

## 57.24 模型卡之外的训练证据

训练成熟度不能由模型发布数量或排行榜位置直接推出。最小证据链应包含配置和 tokenizer、训练 token 与长度分布、数据清洗/去重口径、后训练目标、评测 harness、许可证和 runtime 兼容性。若只公开权重而没有这些字段，读者最多能确认“权重可加载”，不能确认训练 recipe 可复现。

对闭源或资料不完整的系列，要把结论拆成三类：官方明确披露的事实、在固定接口上观察到的行为、根据行业惯例做出的推断。第三类不能写成内部结构事实。尤其是“某系列一定使用了某优化器”“某模型一定通过某数据配方训练”这类说法，如果没有技术报告或代码，应该保留为未知。

## 57.25 一个可手算的开源模型比较

假设模型 A 和 B 都有约 7B 参数。A 使用 2T token，B 使用 1T token；A 的 tokenizer 对目标代码平均每行产生 1.4 倍 token，B 产生 1.8 倍 token。不能只比较原始 token 数，还要估算目标语料被模型实际看到的有效序列长度、重复率和领域覆盖。若代码任务占比很低，A 的总 token 优势也不一定转化为代码能力。

比较时固定相同 prompt、输出预算和 serving 配置，记录短任务、代码、数学、长上下文、工具 JSON、拒答、TTFT、TPOT、峰值显存和单位成功成本。若 A 在代码上领先但多语言和安全切片下降，应写成 workload trade-off，而不是“训练更成熟所以全面更强”。

## 57.26 训练成熟度的决策验收条件

可以把开源模型的选型验收条件写成：

```math
G_{\mathrm{release}}
=G_{\mathrm{artifact}}
 G_{\mathrm{tokenizer}}
 G_{\mathrm{eval}}
 G_{\mathrm{runtime}}
 G_{\mathrm{license}}.
```

权重能加载但 tokenizer 或 chat template 不匹配，不能通过协议门；benchmark 通过但量化后工具参数错误，不能通过 runtime 门；质量合格但许可证不允许目标业务，不能通过发布门。这组条件把“模型能力”和“可用产品 artifact”分开，也避免把系列名当成部署保证。

## 57.27 从模型卡到可加载 artifact 的契约

一个开源模型真正交付给下游的不是一组权重文件，而是一组必须相互匹配的 artifact：权重、配置、tokenizer、special token、chat template、generation config、量化说明、许可证和评测脚本。任意一项不匹配，都可能让“模型能力”在部署时变成协议错误。

例如，tokenizer 的 `eos` 与 generation config 不一致，模型可能永不停止；chat template 少了 generation prompt，模型可能把用户问题当成普通续写；权重已经量化但 runtime 仍按 FP16 shape 加载，可能在启动时失败或偷偷反量化。一个可执行的发布准入条件可以形式化为：

~~~math
G_{\mathrm{artifact}}
=G_{\mathrm{weights}}
 G_{\mathrm{config}}
 G_{\mathrm{tokenizer}}
 G_{\mathrm{template}}
 G_{\mathrm{runtime}}
 G_{\mathrm{license}}.
~~~

这里的乘法表示硬性条件：只要有一项为零，artifact 就不能进入目标环境。把这些字段和下载 hash、revision、dtype、量化方式一起存入 manifest，才能在半年后复现同一个模型，而不是依赖一个会漂移的系列名称。

## 57.28 tokenizer 差异如何改变“训练规模”的解释

设同一份原始代码文档有 `C` 个字符，模型 A 和 B 的 tokenizer 平均每个 token 覆盖的字符数分别为 `r_A` 和 `r_B`，那么近似 token 数为：

~~~math
T_A\approx\frac{C}{r_A},
\qquad
T_B\approx\frac{C}{r_B}.
~~~

如果 A 对中文注释和常见代码片段压缩得更好，它在同样上下文窗口里能容纳更多原始内容；如果 B 对稀有符号切得更碎，训练 token 数看起来可能更多，但每个样本的有效字符和计算成本不同。prefill 的 attention 交互、KV cache 和训练步数都受 `T` 影响，因此“训练了 2T token”必须附带 tokenizer、语言/代码配比和去重口径。

实际比较可以固定一组跨语言、代码、数学和表格样本，记录字符数、字节数、token 数、token/字符比、截断率和每 token 延迟。这样能区分“模型见过更多信息”与“tokenizer 产生了更多碎片”。对多语言模型，按语言切片比平均压缩率更有用，因为低资源语言可能正是整体平均值掩盖的瓶颈。

## 57.29 训练、模板和工具协议的回归顺序

当一个系列更新权重或 chat template 时，回归不能只跑通用问答。更稳妥的顺序是先测协议，再测能力：

1. tokenizer 编解码、special token 和停止 token 是否与 manifest 一致；
2. 单轮、多轮、system message 和空内容的模板是否可逆；
3. JSON/schema、并行工具、错误返回和工具取消是否保持协议兼容；
4. 短指令、代码、数学、长上下文、拒答和多语言任务是否回归；
5. 量化、批处理、KV cache、snapshot/restore 和 p99 是否通过。

工具调用尤其要把“文本看起来像 JSON”和“解析器接受并执行”分开。结构化通过率可以写为：

~~~math
A_{\mathrm{protocol}}
=\frac{N_{\mathrm{parse\_and\_policy\_pass}}}{N_{\mathrm{tool\_cases}}}.
~~~

只报告模型生成的 JSON 字符串合法率，会漏掉字段类型、权限、幂等性和副作用校验。开源生态成熟的标志之一，就是这些协议回归可以由下游独立执行，而不是只能观看发布演示。

## 57.30 开源模型比较的统计不确定性

当两个模型的分数差异很小，结论还要考虑样本量、随机种子、解码和评测 judge 的误差。对一个二元通过率 `p`，粗略标准误差为：

~~~math
\mathrm{SE}(p)\approx\sqrt{\frac{p(1-p)}{n}}.
~~~

小型高难 benchmark 上，几个样本的变化就可能超过报告的平均差异；开放式评测还会增加 judge 方差和提示敏感性。正式比较应固定模型 revision、模板、温度、最大输出、工具、硬件和重试，再报告样本数、置信区间或至少给出多次运行范围。

若 A 在通用知识上高 1 分、在代码和工具上低 5 分，不能用一个平均分宣布 A 全面领先。应把差异绑定到 workload，并记录失败类型：截断、格式、事实、工具参数、超时、拒答还是安全阻断。这样选择结果才对迁移和上线有用。

## 57.31 “开放”有多个层次

权重可下载、代码可运行、训练数据可追溯、许可证允许商用和评测可复现是不同命题。一个模型可能开放权重但不公开数据；可能公开代码但许可证限制用途；可能能本地生成，却缺少官方 tokenizer/template 或稳定 runtime。把这些层次混为一个“开源”标签，会误导工程决策。

可以用四层描述开放程度：artifact 可访问、训练/推理可复现、来源和限制可审计、生态可维护。每一层都要标证据来源和未知项。对于 Qwen、LLaMA 3、Gemma 或未来新系列，具体结论绑定版本和许可证，不从系列名推导整个家族的开放边界。

## 57.32 小结

Qwen、LLaMA 3 和 Gemma 的可迁移知识不是排名，而是训练成熟化的方法：数据和 tokenizer 有版本，长上下文需要专门训练，后训练改变协议与行为，许可证和 runtime 决定部署边界。模型比较必须固定条件并保留未知事实。
