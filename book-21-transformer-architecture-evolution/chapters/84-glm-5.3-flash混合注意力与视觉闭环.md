# GLM-5.3-Flash：混合注意力、mHC 与视觉闭环

> 本章核验日期：2026-09-15。候选发现来自 [Artificial Analysis](https://artificialanalysis.ai/models/glm-5-3-flash) 与 [DataCurve DeepSWE](https://deepswe.datacurve.ai/)；模型规格优先来自 [Z.ai 官方文档](https://docs.z.ai/guides/vlm/glm-5.3-flash)、[Z.ai 官方博客](https://z.ai/blog/glm-5.3-flash) 和固定 revision 的 [Hugging Face 模型卡](https://huggingface.co/zai-org/GLM-5.3-Flash/tree/eb9eb208eb0d988989d07a6a12d0fdeb5f52574a)。榜单数字是配置级结果，官方 benchmark 和 serving speedup 是发布方自报；它们都不是本项目独立复现。

## 84.1 先看一个“会做但做不对”的 coding Agent

设想你让 Agent 根据几张截图重建一个前端页面。它生成了颜色、按钮和布局，代码也通过了语法检查，但最后交付时出现三个问题：

1. 下拉框能看见，却点不开；
2. 长标题在窄屏溢出，截图没有覆盖这个状态；
3. 页面加载慢时，模型没有等待真实反馈，而是凭“代码已经写完”宣布完成。

这说明“代码生成”与“产品完成”之间还有一段闭环：生成代码、启动环境、观察渲染、执行交互、检查结果、修改代码、再次验证。GLM-5.3-Flash 的官方定位把视觉能力直接放进 coding loop，并把混合注意力、稀疏 MoE、mHC 和专门 serving 组合起来，试图同时解决两个问题：

- 长上下文 Agent 需要保留大量历史，但每一层都做全量 attention 太贵；
- 视觉任务的最终正确性不只在文本或代码 token 中，还在渲染结果和交互反馈里。

本章先讲这两个问题，再拆解模型结构和系统账本。

## 84.3 规模表：total、active、层数和专家各自回答不同问题

官方文档与固定 `config.json` 给出：

| 维度 | 公开字段 | 它回答什么 | 它不回答什么 |
|---|---|---|---|
| 总参数 | 320B total | 权重容量、专家分片和存储压力 | 一次 token 的 FLOPs、显存峰值 |
| 激活参数 | 18B activated | 发布方的每 token 主要计算口径 | 18B dense 的延迟、吞吐、全部通信 |
| 主干深度 | 45 层 | 计算图深度和 pipeline 切分线索 | 每层真实 kernel 时间 |
| MLP 排布 | 前 3 层 dense，后续 sparse | 早期层先使用 dense MLP，后续层启用 MoE | 完整 capacity factor、丢 token 规则 |
| MoE | 288 routed experts，top-8，1 shared expert | token 到专家的稀疏计算路径 | 跨卡 all-to-all、负载倾斜和训练 loss |
| 上下文 | 1,048,576 positions | 接口/配置支持百万上下文 | 百万 token 的召回率、p99 延迟和并发 |

这张表是面试中非常重要的“口径防混淆”工具。`18B active` 不是把所有实际成本都压缩成 18B；至少还要加入 attention、router、shared expert、dispatch/combine、padding、cache、workspace 和输出头。

## 84.4 混合注意力：便宜地记住，再精确地找回

### 84.4.1 全量 attention 的矛盾

标准 causal attention 在位置 `t` 访问此前的 `0...t-1` 个 key/value。它的优势是历史 token 没有先被压缩，早期变量名、数字或工具回执仍有机会被精确匹配；代价是长上下文 prefill 的 query-key 组合和 decode 阶段的 KV 读取越来越重。

如果把所有历史压成固定 state，推理可以更便宜，但状态容量有限：两个语义不同的 token 可能争夺同一组方向，后来的写入还可能覆盖早期信息。Flash 的公开架构摘要采用混合思路：大多数层用线性 attention 的递归状态，少数层用稀疏 attention 借助 indexer 恢复远程显式检索。

```text
token stream
   ├─ 34 linear_attention layers ──> recurrent state / short-conv state
   └─ 11 sparse-attention layers ──> indexer -> top candidates -> explicit attention
```

配置里的 34/11 来自 45 层 `layer_types`；`deepseek_sparse_attention` 是公开配置的 layer type 名称，不应在没有完整源码/报告时擅自补写所有内部细节。

### 84.4.2 线性 attention 的直觉

对一个 head，先用抽象状态 `S_t` 汇总历史，再用 query 读取：

```math
S_t=\lambda_tS_{t-1}+\eta_tk_tv_t^{\top},
\qquad y_t=S_t^{\top}q_t.
```

其中：

- `S_t` 是固定形状的递归状态，不随历史 token 数量线性增长；
- `\lambda_t` 表示旧状态的保留/衰减；
- `\eta_t` 表示当前关联写入强度；
- `k_t` 和 `v_t` 提供当前 token 的关联和值；
- `q_t` 从状态读取与当前 query 相关的信息。

这是教学抽象，不是声称 Flash 的生产 kernel 只有这一行更新。固定配置另外给出 linear attention 的 64 heads、head dim 128 和 short-convolution kernel size 4；真实状态还涉及门控、归一化、位置处理、融合和 batch layout。

### 84.4.3 稀疏 attention 先问“看哪里”

稀疏路径的第一步不是直接对全部 token 做精确 attention，而是让轻量 indexer 为历史候选打分。官方博客的关键新名词是 **IndexPool**：4 个 indexer key vectors 经过 weighted pooling 压成 1 个，减少长上下文 indexer 自身的 latency 和 memory。

固定配置中的相关字段是：

```text
index_n_heads=32
index_head_dim=128
index_topk=2048
index_kpool=4
index_kpool_compress=true
index_kpool_always_select_tail=true
index_share_for_mtp_iteration=true
```

用 `k_{b,h,j}` 表示一个局部单元中第 `j` 个 indexer key，可以把池化理解为：

```math
\bar{k}_{b,h}=\sum_{j=1}^{4}\alpha_{b,h,j}k_{b,h,j},
\qquad \alpha_{b,h,j}\ge0,\quad\sum_j\alpha_{b,h,j}=1.
```

这个式子只说明加权池化的语义，不假定具体权重生成函数。query 与 `\bar{k}` 产生候选分数后，系统还要执行因果 mask、top-k、gather、显式 attention、分页和 cache 管理。

因此不能把 `index_topk=2048` 直接说成“模型最终只看 2048 个 token”。当前公开配置字段没有单独给出所有 batch、MTP、tail 保留和 kernel 实现下的最终可见 token 语义；这一项要以完整源码和 tracing 为准。

### 84.4.4 为什么混合不是简单平均

混合架构的价值不在于把两条分支的输出做一次平均，而在于按访问模式分配预算：

| 历史访问需求 | 更合适的路径 | 付出的成本 |
|---|---|---|
| 连续、局部、可由状态概括的模式 | linear attention | state update、短卷积、状态读写 |
| 远程、稀疏、需要精确 token 的模式 | sparse attention | indexer、排序/gather、显式 KV、通信 |
| 当前 query 的长期任务状态 | 两者配合 | 状态一致性、位置、MTP 与 cache manifest |

如果 indexer 选错，稀疏层的精确 attention 也无法看到被漏掉的 token；如果线性 state 更新不稳定，后面的 query 没有可靠的压缩历史可读。因此评测不能只测 kernel FLOPs，还要测 needle/long-context recall、工具回执恢复和 end-to-end Agent 成功率。

## 84.5 稀疏 MoE：少算不等于没有系统成本

设 `x` 是 token 表示，router 生成 288 个分数，选择 top-8 routed experts，并与 shared expert 合成：

```math
p=\operatorname{router}(x),\quad I=\operatorname{TopK}(p,8),\quad
y=E_{shared}(x)+\sum_{i\in I}\tilde p_iE_i(x).
```

这个教学式隐藏了实际系统最容易出问题的部分：

1. token 如何按 expert 分桶；
2. 热门 expert 是否超过 capacity；
3. 跨卡 dispatch/combine 的 all-to-all 如何与 attention overlap；
4. 输出如何恢复到原 token 顺序；
5. router、shared expert 和量化如何保持数值稳定。

面试回答应将“模型容量”与“每 token 计算”分开，再把通信和内存带宽补回来。只说 `320B` 会忽略稀疏激活；只说 `18B` 又会忽略权重、专家分片、通信和 cache。

## 84.6 mHC：把 residual 流的稳定性纳入架构

### 84.6.1 普通 residual 的放大风险

标准残差连接：

```math
x_{l+1}=x_l+F_l(x_l).
```

如果把 residual stream 加宽为多个流，并允许层间矩阵混合，表达力会提高，但多次矩阵连乘可能让某些流被不断放大、另一些流逐渐消失。mHC（Manifold-Constrained Hyper-Connections）把关键的流混合映射约束到双随机矩阵集合：

```math
\mathcal{B}_n=\{M\in\mathbb R^{n\times n}:M\mathbf 1=\mathbf1,\;
\mathbf1^{\top}M=\mathbf1^{\top},\;M\ge0\}.
```

行和为 1 表示每个输出流接收的混合总量受控，列和为 1 表示每个输入流分配出去的总量受控，非负性避免正负权重抵消后失去流量解释。

这不是范数恒等式，也不是“开启 mHC 就不会梯度爆炸”。非线性主分支、写回矩阵、归一化、量化误差、优化器和硬件数值仍会影响训练。

### 84.6.2 Flash 中能确认的字段

固定配置给出 `mhc=true`、`hc_mult=4`、`hc_sinkhorn_iters=20`。因此可以说公开 artifact 启用了 mHC 相关配置，并使用了 4 倍 residual 宽度/多流相关的配置口径与 20 次 Sinkhorn 迭代字段。不能仅靠这些字段推导每层所有 `A/B/C` 参数、融合 kernel、通信拓扑或训练消融结论。

Sinkhorn 的教学过程是：

```text
M^(0) = exp(raw_scores)
M^(t) = column_normalize(row_normalize(M^(t-1)))
```

它在有限步数后趋近双随机集合；数值精度、logit 范围和矩阵大小会影响误差。mHC 与 IndexPool 的对象不同：前者调 residual flow，后者调长上下文 indexer 的 key representation。

## 84.7 原生视觉：把“完成”定义成可观察的 artifact

### 84.7.1 Visual coding loop

GLM-5.3-Flash 的官方文档把它定位为首个原生多模态 GLM-5 系列模型，输入包括 video/image/text/file，输出为 text。关键不是“它可以看图”，而是视觉信息进入后续 coding/action decision：

```text
参考截图/视频/文件
       ↓
规划并生成代码或工具动作
       ↓
运行应用 / 渲染 / 游戏测试 / Blender / Office 操作
       ↓
观察 UI、画面、交互反馈和交付文件
       ↓
发现差异，修改，再运行
```

官方博客进一步把 visual coding 描述为 self-visual judgment 与 test-time improvement，并提到用 environment feedback 和 agent-based verification 检查真实用户流程。这里的“self-judgment”是模型/系统能力主张，不是一个已经公开完整定义的单一 loss。

### 84.7.2 四层验证门禁

一个视觉 Agent 的完成门禁最好分四层：

| 层次 | 例子 | 不能由什么替代 |
|---|---|---|
| 代码语义 | 编译、类型、单元测试 | 一张漂亮截图 |
| 交互行为 | 点击、输入、状态转移、异常恢复 | 模型说“已完成” |
| 视觉质量 | 溢出、遮挡、裁剪、对齐、风格 | 代码静态检查 |
| artifact 交付 | 文件可重开、来源、权限、版本、复现 | 单次 demo 成功 |

例如 PPTX 可以打开但文字溢出；网页可以渲染但按钮失效；游戏可以启动但没有胜负循环。模型应该决定何时观察和下一步动作，但终端、浏览器、文件系统、网络和审批权限都由宿主执行器负责。

## 84.8 EPD Serving：Encode、Prefill、Decode 三段式

### 84.8.1 为什么多模态需要 EPD

单纯的 PD disaggregation 只拆 prefill 和 decode。图像、视频和文件请求在 prefill 前还要完成视觉 encode；如果 encode 长时间占用同一 worker pool，短文本请求的 TTFT 会被拖长。EPD 的抽象是：

```text
Encode pool  --visual representation-->  Prefill pool
Prefill pool --KV/state metadata------->  Decode pool
Decode pool  --streaming text/tool----->  client
```

三个 pool 可以独立扩缩容、按阶段调度和设置不同硬件/并行策略，但跨池数据转移要求明确：request/session ID、模型 revision、tokenizer/template、位置偏移、cache dtype、取消、超时、重算、版本兼容和租户隔离。

### 84.8.2 Flash 的公开 serving 线索

Z.ai 公开提到在 SGLang 上构建 dedicated engine，并结合：

- `ReplaySSM`；
- Linear Attention 与 LM head 的 intra-node tensor parallelism；
- W8A8；
- INT8/FP8/BF16 hybrid cache quantization；
- Layer Split；
- EPD worker pools。

这些是工程组件/策略，不能写成“任意版本 SGLang 默认已支持全部特性”。官方还称在相同硬件上相对初始 baseline 取得约 3× end-to-end serving improvement；这必须标注为 Z.ai 特定硬件与配置的自报数字。

## 84.9 Cache、状态和带宽账本

### 84.9.1 不要给混合模型套一个统一 KV 公式

普通显式 attention 的 KV cache 教学估算是：

```math
\mathrm{KVBytes}=2_{K,V}\times L\times T\times H_{KV}\times d_{head}
\times b_{elem}.
```

但 Flash 的 34 个 linear attention 层不等价于 34 份随 `T` 增长的普通 KV；它们有递归 state、短卷积 state 和实现 metadata。11 个 sparse attention 层有显式 KV，同时 indexer 还需要候选 key、score、top-k index 和 gather buffer。mHC residual、视觉 encode 中间结果、MoE dispatch 和 EPD transfer 也会占用内存或带宽。

因此应使用多账本：

| 账本 | 至少记录 |
|---|---|
| 权重 | 320B total、18B active、288/8/1 expert、dtype、分片 |
| 递归状态 | 34 linear layers 的 state、short conv、batch/session layout |
| 显式 cache | 11 sparse layers 的 KV、indexer key/score/top-k/gather |
| 深度残差 | `hc_mult=4` 的 widened residual、量化/通信/重算 |
| dispatch | token-expert assignment、capacity、all-to-all、combine buffer |
| 多模态/EPD | visual representation、prefill metadata、跨池传输与失败重算 |

### 84.9.2 3.01× 和 4.44×应如何回答

官方页面把 Flash 与 GLM-5.3 比较时称 attention computation 约减少 3.01×、KV cache 约减少 4.44×；博客用约 3.0×/4.4×的四舍五入表达。面试回答应加三句限定：

1. 这是发布方的比较口径，不是本项目实测；
2. 计算和 cache 是两个不同指标，不能由其中一个推导另一个；
3. 端到端收益还取决于 indexer、MoE dispatch、state read/write、batch、量化、硬件和 EPD transfer。

### 84.9.3 SGLang 的双状态池：KV token 不是全部历史状态

如果你只给一个长上下文请求记录 `kv_tokens=500000`，仍然不知道它能否被调度。原因是 Flash 的 serving 路径同时存在两种生命周期不同的状态：

| 状态池 | 服务对象 | 调度问题 |
|---|---|---|
| paged KV pool | 显式 attention 层的 K/V block | block 分配、prefix 命中、eviction、dtype 和页表 |
| KDA state pool | KDA/线性路径的递归 state | session 绑定、state 读写、batch 合并、恢复与并发上限 |

SGLang 的 GLM-5.3-Flash recipe 明确提醒，KDA state pool 可能比 paged KV pool 更早限制并发。一个请求即使还有 KV block，也可能因为没有可用的 KDA state slot 而排队。因此生产 manifest 至少要保存：

```text
model_revision
attention_backend
kv_dtype
kv_page_table
kda_state_handle
kda_state_length
mtp_position
session_id
```

故障恢复时也不能只恢复 `past_length`。如果 paged KV 已恢复但 KDA state 丢失，继续生成可能表面上 token 数连续，实际上线性路径看到的历史已经断裂。反过来，只恢复递归 state 而缺少稀疏层的 KV/indexer metadata，也无法保证远程精确检索一致。

### 84.9.4 MTP 是 workload 策略，不是无条件的模型属性

SGLang 页面给低延迟路线使用 MTP `5/1/6`，而高吞吐路线可以关闭 speculative decoding。这里至少有三个可分开的概念：

1. checkpoint 或模型配置是否提供 MTP 相关层/接口；
2. runtime 是否实现 draft/verify、回滚和接受 token 的调度；
3. 当前 workload 是否值得为 speculative 路径支付额外显存、验证和调度成本。

因此面试中不能只回答“Flash 支持 MTP”。更完整的回答是：SGLang recipe 提供了特定 MTP serving 路径；低延迟与高吞吐的配置可能选择不同开关；最终接受率、失败重算、batch 形状和工具调用边界要在固定 revision、硬件和 harness 下实测。Transformers 的 GLM5-Next 接入文档当前明确不包含 MTP layer，这也说明基础模型接入和 serving 层 speculative 支持不能混写。

### 84.9.5 KV dtype 与 DSA backend 是一个配对契约

不同硬件路线不是简单地把 `kv_dtype` 从 BF16 改成 FP8。SGLang recipe 给出的默认组合是：Blackwell 使用 FP8 KV + TRT-LLM DSA，H100/H200 使用 BF16 KV + TileLang DSA；FP8 KV + TileLang DSA 被标为无效组合。

这背后的工程原因可以用一个抽象 pipeline 表示：

```text
KV write/quantize -> page layout -> DSA index/score -> gather/dequantize -> attention
```

KV 的量化格式、scale 布局、页内排列、DSA kernel 读取方式和反量化精度必须共同约定。单独替换其中一个 backend，可能出现初始化拒绝、非法 kernel 组合或更隐蔽的数值/召回下降。部署 checklist 应把下面几项绑定验收：

- GPU family 与 compute capability；
- KV dtype、scale dtype 和 page/block size；
- DSA backend 与编译/运行时版本；
- long-context evidence recall 和工具回执恢复；
- TTFT、TPOT、显存占用、p95/p99 与失败重试。

页面报告 GB300 上 FP8 路线相对 BF16 路线的 throughput 和 KV capacity 差异，但这是发布方 recipe 结果，不足以推导任意 GPU 上的收益。

### 84.9.6 EPD/PD 的“有入口”不等于“已通过生产门禁”

视频请求还多一个 encode 阶段。SGLang 页面给出视频默认 2 FPS、约 240K visual tokens 的上限语境，并报告 4x GB300 encoder disaggregation 可以降低最大 decode gap。这个结论要建立在 encode pool、prefill pool 和 decode pool 的队列/传输确实被分开测量的前提下。

同时，页面对 PD disaggregation 标注得很谨慎：当前只有 dummy weights 的机械验证，没有 load/accuracy 验证；普通 speculative decoding 尚不支持，不同 TP 的数值正确性也未完成验证。应把部署状态写成多级 gate：

```text
recipe command exists
    -> dummy-weight process wiring
    -> full-weight load
    -> numerical correctness
    -> multimodal/PD/EPD recovery
    -> target hardware profile
    -> tool/verifier and production SLO
```

任何一个箭头没有证据，都不能把上一级的存在升级为下一级的通过。尤其不能把“4x encoder disaggregation 的发布方 decode-gap 数字”写成本地服务的 p99 改善。

### 84.9.7 FlashX、vLLM 与模型身份的边界

Z.ai 文档列出的 `GLM-5.3-FlashX` 是关联服务入口，约 200 tokens/s；它不在本轮两个排行榜的新候选中。FlashX 的 endpoint 速度、套餐配额和 Flash 的模型卡字段应放在服务 manifest，而不是模型 inventory 的新行。

vLLM recipe 的 v0.29.0+、native FP8/MTP 和 hybrid KDA+sparse MLA 是部署实现证据；Transformers GLM5-Next 不含 MTP layer 是基础接入证据；模型卡/config 才是 320B/18B、45 层、34/11 layer types 等模型 artifact 证据。三个层次的结论不能互相反推：

```text
model artifact/config
    != Transformers feature surface
    != vLLM/SGLang serving recipe
    != target hardware production acceptance
```

### 84.9.8 upstream 源码里的三类历史状态

2026-09-22 的 upstream 源码补证把前面的“双状态池”再细分了一层。SGLang `v0.5.20` 的 `glm5_next.py` 已是固定 stable source entry；SGLang `main` 继续增加 projection fusion、KDA prefill metadata、mHC boundary fusion 和硬件量化路径。它们证明实现入口和代码演进，不证明本机已经加载 Flash 权重。

vLLM `main` 的 `vllm/models/glm5next/` 则把几个容易混淆的对象写得更具体：

1. `Glm5NextIndexerCache` 以 `index_kpool` 为 `tokens_per_state`，按 pool 粒度寻址 indexer metadata，并要求 block size 与 `index_kpool * 32` 对齐；这是压缩 indexer 的 cache layout，不是普通 KV token 数。
2. `Glm5NextTailCache` 单独保留尚未填满 pool 的 raw BF16 K 和 gate score。prefill、decode/spec-decode 和 PD connector 都要能够推进或传递这个 tail；如果只恢复已经完成的 pool，会在边界处丢掉未压缩历史。
3. `Glm5NextLinearAttention` 使用独立的 KDA/Mamba/GDN state shape 和 dtype 接口，conv state 还要为 `num_spec` 留出 speculative 更新空间；它不能和显式 sparse KV 共用一个“长度 + page table”字段。
4. MTP runtime 通过显式 layer/weight mapping、slot-based top-k compact 和后续迭代的 sparse index top-k 复用减少重复工作；vocab-parallel local argmax 也不必每个 draft step all-gather 全词表。

这给 serving manifest 一个更严格的最低字段集合：`model_revision`、stable/main/recipe provenance、explicit KV page table、indexer pool、tail buffer、KDA conv/recurrent state、MTP draft position/top-k mapping、dtype/backend 和 connector version。公开 vLLM `v0.29.0` tag 的 tree 中没有 `vllm/models/glm5next/` 专属路径，所以 recipe 的 `v0.29.0+` 不能写成 stable tag 已包含上述实现。源码检查、CI 测试或 recipe 命令仍要经过 full-weight load、state recovery、数值正确性、目标硬件 profile 和 tool/verifier gate 才能升级为生产结论。

### 84.9.9 vLLM v0.30.0：stable 文件实现与 fixed-main 差异

vLLM `v0.30.0` 于 2026-09-22 发布，tag commit 为 `ced6857afa0ea7b2e3f0846a62e1394e90f15607`。GLM5Next tree SHA 为 `118165530271cb3aa749d77bf927499957db2bd4`；本节将其逐文件对照固定 main commit `81d7293c2167e39f3ffddc9a82d633f94e8a1eaa`，不以 mutable main 代替版本基线。

| 能力/文件 | v0.30.0 stable | 固定 main 对照 | 可得结论 |
|---|---|---|---|
| Indexer/tail cache | `nvidia/attention.py` 中含 `Glm5NextIndexerCache` 与 `Glm5NextTailCache` | 对应 `common/attention.py` 也含这两类 cache | stable 已有 pool 粒度的压缩 indexer metadata 与未完成 pool 的 raw BF16 K/gate-score tail；不是只有目录空壳。 |
| KDA state | `nvidia/kda.py` | `common/kda.py` 同 Git blob | 文件完全相同；独立 recurrent/conv state 与 speculative conv 宽度逻辑可归于 v0.30.0。 |
| MTP | `nvidia/mtp.py` | `common/mtp.py` | diff 仅 fused norm 的 import 路径；layer/weight mapping、top-k buffer compaction 主体相同。 |
| attention/indexer | stable 调用通用 `SparseAttnIndexerKpool`，workspace 使用 `max_model_len` | main 改为 GLM5Next 自有 sparse-indexer wrapper，workspace 长度按 pool 数折算；RoPE scaling 映射也调整 | 文件 blob 不同；cache 抽象存在于两版，但不能把 main 的 indexer 和 RoPE 细节倒灌到 stable。 |
| KPool tail kernel | stable seed kernel 依据 dense layout 计算地址 | main 增加 `TAIL_BLOCK_ELEMS`/`KPOOL_HEAD`，按 cache stride 寻址并校验 shape/stride | 是 cache layout 的具体风险点；需要目标 cache 的数值/边界测试，不能仅凭源码差异断言 stable 有 bug。 |
| 权重加载 | stable `model.py` | main 增加 gate/up projection packed mapping，并兼容 Quark `.weight_scale` | main 的两项量化加载增量尚不在 v0.30.0 stable source。 |

路径也从 stable 的 `nvidia/`、`amd/` backend 目录，演进为 main 的 `common/` 核心加 backend-specific sparse-indexer 文件。可见稳定版确实包含 cache/KDA/MTP/multimodal 实现，但不是固定 main 的逐字拷贝。

这仍只是 source-level evidence。它不代表 PyPI wheel 已安装、完整权重已加载、cache stride/layout 数值正确、目标 GPU/ROCm 路径通过，或 PD/EPD recovery、MTP acceptance、工具/verifier 与生产 SLO 验收。应把 `release source -> wheel/runtime -> full weights -> target hardware/numerics -> serving recovery/SLO` 作为互不替代的门禁。

## 84.10 Thinking、工具流和结构化输出

Flash 的官方 API 文档是模型能力进入 Agent harness 的接口边界：

- `thinking.type` 只支持 `enabled`，thinking 不能通过旧的 `disabled` 方式关闭；
- `reasoning_effort` 支持 `low/high/max`，默认 `max`；
- 流式响应可分别携带 `reasoning_content`、`content` 和 `tool_calls`；
- `tool_stream=true` 时要按 tool-call index 累积函数名和参数片段；
- interleaved thinking 允许在工具结果之间继续 reasoning；多轮 preserved thinking 要按原序、完整、未修改地回传 reasoning content；
- JSON mode 的公开形式是 `response_format={"type":"json_object"}`，仍需本地 parse 和 schema validate。

工具调用应拆成四个事件：

```text
model proposes tool call
        -> host validates schema/policy
        -> executor runs with permission/timeout
        -> host returns tool result
        -> model reasons over result
```

“模型产生了 tool call”不是“工具已经成功执行”；“模型输出 reasoning”也不是访问文件、网络或终端的权限。`clear_thinking` 的默认值和作用还受 Coding Plan/标准 API endpoint 影响，接入时应锁定 endpoint、SDK 版本和错误回归。

## 84.11 零依赖教学 demo

下面的例子模拟 IndexPool、稀疏 block 选择、递归状态、mHC 的 Sinkhorn 投影、cache ledger 和 EPD/视觉验证。它使用玩具尺寸，目的是把机制讲清，而不是伪装成可以加载 320B 模型的实现。

```python
import math


def dot(left, right):
    if len(left) != len(right) or not left:
        raise ValueError("vectors must have the same non-zero length")
    return sum(a * b for a, b in zip(left, right))


def index_pool(keys, group_size=4):
    if group_size <= 0 or not keys:
        raise ValueError("invalid key groups")
    if any(not row or len(row) != len(keys[0]) for row in keys):
        raise ValueError("key rows must have the same non-zero width")
    pooled = []
    groups = []
    for start in range(0, len(keys), group_size):
        group = keys[start:start + group_size]
        weights = [float(i + 1) for i in range(len(group))]
        total = sum(weights)
        pooled.append([
            sum(weight * row[col] for weight, row in zip(weights, group)) / total
            for col in range(len(group[0]))
        ])
        groups.append((start, start + len(group)))
    return pooled, groups


def sparse_visible(query, keys, block_size=4, index_topk=2):
    if not query or index_topk <= 0:
        raise ValueError("query and index_topk must be valid")
    if not keys or len(query) != len(keys[0]):
        raise ValueError("query width must match keys")
    pooled, groups = index_pool(keys, group_size=block_size)
    candidates = []
    for block_id, (start, end) in enumerate(groups):
        # Only complete blocks strictly before the current position are visible.
        if end <= len(keys) - 1:
            candidates.append((dot(query, pooled[block_id]), block_id, start, end))
    if not candidates:
        return [], []
    candidates.sort(reverse=True)
    selected = candidates[:index_topk]
    tokens = [token for _, _, start, end in selected for token in range(start, end)]
    ranked = [(block_id, round(score, 3))
              for score, block_id, _, _ in selected]
    return tokens, ranked


def linear_state(values, decay=0.8):
    if not values or not 0.0 < decay <= 1.0:
        raise ValueError("values and decay must be valid")
    if not values[0]:
        raise ValueError("state width must be non-zero")
    state = [0.0 for _ in values[0]]
    for value in values:
        if len(value) != len(state):
            raise ValueError("state width changed")
        state = [decay * old + new for old, new in zip(state, value)]
    return [round(item, 3) for item in state]


def sinkhorn(raw, steps=20):
    if not raw or any(len(row) != len(raw) for row in raw) or steps <= 0:
        raise ValueError("raw must be a non-empty square matrix")
    matrix = [[math.exp(value) for value in row] for row in raw]
    for _ in range(steps):
        for row_id, row in enumerate(matrix):
            total = sum(row)
            matrix[row_id] = [item / total for item in row]
        for col_id in range(len(matrix)):
            total = sum(matrix[row_id][col_id] for row_id in range(len(matrix)))
            for row_id in range(len(matrix)):
                matrix[row_id][col_id] /= total
    return matrix


def cache_ledger(sequence_length):
    if not isinstance(sequence_length, int) or sequence_length <= 0:
        raise ValueError("sequence length must be positive")
    # Toy values: deliberately not the production GLM-5.3-Flash configuration.
    explicit_layers = 2
    linear_layers = 4
    kv_heads = 2
    head_dim = 8
    bf16_bytes = 2
    explicit_kv = (2 * explicit_layers * sequence_length * kv_heads
                   * head_dim * bf16_bytes)
    recurrent_state = linear_layers * kv_heads * head_dim * head_dim * bf16_bytes
    return {"explicit_kv_bytes": explicit_kv,
            "linear_state_bytes": recurrent_state}


def epd_plan():
    return [("encode", "visual input -> representation"),
            ("prefill", "text + representation -> KV/state metadata"),
            ("decode", "metadata -> streamed text/tool events")]


def visual_verification_loop():
    errors = [3, 2, 1, 0]
    for before, after in zip(errors, errors[1:]):
        if after > before:
            raise AssertionError("visual diff became worse")
    return errors[-1]


keys = [[1.0, 0.0], [0.9, 0.1], [0.0, 1.0], [0.1, 0.9],
        [0.8, 0.2], [0.2, 0.8]]
visible, ranked_blocks = sparse_visible([0.95, 0.05], keys)
state = linear_state(keys)
projected = sinkhorn([[1.4, 0.2], [0.1, 1.3]])
assert all(abs(sum(row) - 1.0) < 1e-3 for row in projected)
assert all(abs(sum(projected[row][col] for row in range(2)) - 1.0) < 1e-3
           for col in range(2))
assert visible and ranked_blocks
assert visual_verification_loop() == 0
print("visible_tokens:", visible)
print("ranked_blocks:", ranked_blocks)
print("linear_state:", state)
print("cache_ledger:", cache_ledger(16))
print("epd_stages:", [stage for stage, _ in epd_plan()])
print("visual_diff_after_refinement:", visual_verification_loop())
```

运行时应看到：

- IndexPool 将每 4 个 key 压成一个候选，并返回排序靠前的完整 block；
- `linear_state` 是固定宽度的教学 state，而不是按 token 保存的完整 KV；
- Sinkhorn 投影后的行和、列和都接近 1；
- `cache_ledger` 把显式 KV 与线性 state 分开；
- EPD 有 encode、prefill、decode 三个阶段；
- 视觉差异只有在每轮没有恶化且最终为 0 时才通过。

代码中的 2 个显式层、4 个线性层、2 个 KV heads 和 8 维 head 只是为了让读者能在本地运行；它不代表 Flash 的 34/11 层、64/32 heads 或真实 bytes/token。

## 84.12 对比其他长上下文路线

| 路线 | 历史表示 | 远程精确检索 | 主要系统风险 |
|---|---|---|---|
| 普通 full attention | 每 token 显式 K/V | 强 | prefill、decode KV 读取和长上下文成本 |
| 纯 linear/state | 固定递归 state | 弱或依赖额外机制 | 覆盖、遗忘、state 更新和状态 batching |
| GLM-5.3-Flash | 多数 linear state + 少数 sparse/indexer | 有，受 top-k/indexer 影响 | 两类 cache、indexer、MoE、EPD 和 kernel 融合 |
| Qwen3.8 Flash-Next | GDN + QSA micro-block | 有，先压 block 再稀疏 attention | block/tail budget、QSA 两阶段训练、host-memory table |
| DeepSeek V4.1-Flash | CED + CSA2/HSI 等另一条路线 | 有，采用不同压缩/索引设计 | CED prefill/decode、重算 cache、FP4 KV、部署复杂度 |

比较时必须保持“模型、层布局、cache dtype、context、batch、backend、硬件、effort、工具和 verifier”一致。不能因为多个项目都写了 sparse、linear 或 indexer，就把它们视为同一实现。

## 84.13 面试追问

### 问题 1：为什么 GLM-5.3-Flash 不把所有层都换成线性注意力？

线性 state 便宜地汇总历史，但固定容量可能损失逐 token 精确检索。少数 sparse attention 层通过 indexer 恢复远程候选，给早期接口、数字和工具回执一条显式检索路径。代价是 indexer、显式 KV、排序/gather 和系统复杂度。

### 问题 2：IndexPool 和 KV cache 压缩有何不同？

IndexPool 压缩的是稀疏路径 indexer 用来筛选历史的 key representation；KV cache 压缩针对主 attention 在后续计算中使用的 key/value 历史。前者减少候选打分的开销，不等于已经压缩或删除最终 attention 的全部 KV。

### 问题 3：为什么 320B total 和 18B active 不能直接变成容量规划？

320B 决定权重存储、专家分片和加载压力，18B 只是每 token 主要激活计算口径。容量规划还要加 attention/state/KV、router、shared expert、dispatch/combine、量化 workspace、batch padding、EPD 传输和并发 headroom。

### 问题 4：mHC 的双随机矩阵保证了什么？

它约束 residual stream 混合的行和、列和与非负性，提供流量守恒和深度传播的稳定性倾向；它不保证所有激活范数不变，不替代归一化、优化器、数值稳定和训练监控。

### 问题 5：视觉 self-verification 是否等于模型可以自己证明正确？

不等于。它表示模型能把观察、渲染和交互反馈纳入后续决策的公开工作流；可靠性仍需 compiler/test/行为 trace/视觉 diff/artifact validator 多层门禁，且宿主负责权限、沙箱、超时和回滚。

### 问题 6：EPD 的新增成本是什么？

Encode、prefill、decode 分池后需要传递 representation/KV/state metadata，处理取消、失败重算、版本兼容、网络带宽、租户隔离和 trace correlation。短请求、低视觉比例或传输慢的 workload 可能不值得分离。

### 问题 7：DataCurve 的 Pass@1 如何公平使用？

把它称为 `max + mini-swe-agent` 在固定任务集和 verifier 下的配置级 Agent 结果，保留 284/448、成本和 steps；要比较模型，固定相同 harness、工具、超时、重试、环境、模型 revision 和预算，不能与 AA Intelligence Index 拼接。

## 84.15 本章证据边界与来源

### 可以直接说

- GLM-5.3-Flash 的公开文档/模型卡给出 320B total、18B activated、45 层、34 linear/11 sparse layer types、288 routed experts、top-8、1 shared、1M context、原生视觉配置和 mHC/IndexPool 字段。
- Z.ai 官方资料公开描述 hybrid linear+sparse attention、IndexPool、30T multimodal corpus、visual self-judgment/test-time improvement、SGLang、ReplaySSM、混合 cache quantization、Layer Split 和 EPD。
- Artificial Analysis 和 DataCurve 的数字是带 effort/provider/harness/任务/verifier 条件的配置级结果。

### 不能直接说

- 不能把 GLM-5.3 主模型沿用 GLM-5.2 的描述套给 Flash；Flash 模型卡称其 newly trained base。
- 不能把 `index_topk=2048` 直接写成最终可见 token 数，也不能把 `index_kpool=4` 写成完整生产池化公式。
- 不能把 18B active 当成 18B dense 的显存/延迟；不能把 3× serving 或 3.01×/4.44×写成普遍保证。
- 不能由 `mhc=true` 推导每层完整 hyper-connection、训练稳定性定理或 zero-overhead kernel。
- 不能把视觉 self-judgment 当作独立完备 verifier；工具权限和 artifact 正确性由宿主与验证器负责。

完整快照哈希、官方链接和待核验项见 [`glm-5.3-flash-source-notes.md`](../../research/model-update-2026-09/glm-5.3-flash-source-notes.md)。相关基础章节包括：第 10 章的 O(n²) attention 瓶颈、第 11 章的 KV cache、第 21/22 章的 MoE、第 43/47 章的混合架构、第 69/71 章的 cache/state、第 78 章的 mHC，以及第二十四册的 EPD/serving engine。
