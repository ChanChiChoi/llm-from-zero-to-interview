# 第 45 章 Retrieval-Augmented Architecture：把外部检索变成架构组件

检索增强生成（retrieval-augmented generation，RAG）给模型增加了一条读取外部语料的路径。用户的问题先触发检索，系统挑出相关材料，再把这些材料送到生成器。理解这类架构，关键不在于“接了一个向量库”，而在于外部证据经过哪些组件、以什么形式进入生成过程，以及每一步可能丢失什么。

## 45.1 参数记忆、请求上下文与外部语料处在不同位置

先区分三种信息来源：

| 信息来源 | 存放位置 | 生成时如何被使用 | 变化方式 |
| --- | --- | --- | --- |
| 参数知识 | 模型参数中 | 模型根据训练形成的表示生成 | 单条知识不能像文档一样直接定位和替换；通常需要模型更新，或用其他信息源补充 |
| 请求上下文 | 当前请求输入中 | 作为本轮可见的 token 参与计算 | 可随请求替换，不天然跨请求保存 |
| 外部语料 | 模型以外的文档集合或索引 | 检索器按问题选出材料，再交给生成器 | 语料和索引可以独立维护；是否反映新版本取决于维护流程 |

RAG 将外部语料与生成模型组合起来。Lewis 等人的原始 RAG 工作把预训练生成模型与外部 Wikipedia 索引结合，让模型在回答时访问检索出的段落；作者把这种组合描述为参数记忆与非参数记忆的结合。[原始论文](https://arxiv.org/abs/2005.11401)提供了这一设计的具体形式。

用一份会更新的设备维修手册作例子：模型参数可能没有某型号的内部手册；当前请求也未附上整本手册。系统可以把手册放入外部语料，用户提问时只取出相关段落。这个办法不会自动让答案变新：新版本只有在语料和检索索引都得到更新后，才可能进入生成上下文；即使段落已经进入上下文，模型仍可能误读或忽略它。

因此，检索增加的是一条取证路径，不是正确性证明。它让系统有机会把来源明确的材料送入模型，但无法仅凭“检索成功”保证材料足够、回答正确或引用成立。

## 45.2 一次检索增强回答怎样流过系统

RAG 通常包含一条离线语料路径和一条在线请求路径。离线阶段把来源文档整理成可查找的单元，并建立索引；在线阶段根据用户问题找到候选证据，把选中的材料与问题一起交给生成器。这个全局路径可概括为“建库—检索—组装证据—生成”，各系统会在具体组件上有所不同。

马里兰大学 Fall 2026 的 [RAG 课程讲义](https://www.cs.umd.edu/class/fall2026/cmsc389A/RAG-Agentic.html)把索引构建与请求时检索分开讲；Lewis 等人的原始 RAG 也以 Wikipedia 向量索引、检索器和生成器展示了这条路径。[原始论文](https://arxiv.org/abs/2005.11401)

继续看维修手册的例子。用户问“型号 R 的 E17 报警表示什么？”请求到来后，系统沿下表把问题转成回答：

| 阶段 | 主要工作 | 交给下一阶段的内容 |
| --- | --- | --- |
| 建立语料索引 | 解析手册，把内容整理为可查片段，并保留标题、页码或版本等来源信息 | 可检索的片段及其来源标识 |
| 检索候选 | 根据问题在索引中寻找可能相关的片段 | 若干候选证据 |
| 选择并组装 | 按相关性筛选、排序或压缩候选，再与用户问题组成模型输入 | 实际进入生成器上下文的证据和来源信息 |
| 生成回答 | 让模型基于问题和所给证据组织回答；系统可要求输出引用 | 回答，以及可选的来源引用 |

这张表也揭示了职责边界：索引提供可搜索的材料，检索器负责找候选，组装阶段决定模型实际能看到什么，生成器负责把问题与给定证据转换成回答。某个系统可以使用关键词检索、向量检索或多路组合；RAG 并不要求特定数据库，也不要求每个阶段都由一个独立模型实现。

如果候选里有正确的 E17 条目，但组装时只留下了相似型号的片段，生成器看到的上下文就已经错了；如果正确片段完整进入上下文，模型仍可能把型号或版本混淆。因而，描述 RAG 架构时必须追踪“实际送入生成器的证据”，不能只看检索器返回过哪些文档。

## 45.3 检索结果在提示边界接入生成器

一种常见的应用层结构保留现成的生成模型，不改模型参数；每次请求时，系统取出少量材料，与用户问题共同组成提示。此时检索器和语料位于模型调用之外，生成器把传入的材料当作当前上下文处理。

这个设计的优点是证据来源可以由外部系统维护，换语料或检索策略不必然要求重新训练生成模型。但模型能利用的外部信息受最终组装结果限制：没有进入上下文的文档不会因为索引中存在就被模型读到，进入上下文的文档也不会强制模型遵循。ALCE 的研究专门检查长答案中的事实和引用质量，说明“提供了段落”和“回答中的主张得到段落支持”是不同问题。[ALCE 论文](https://arxiv.org/abs/2305.14627)指出，检索增强语言模型并不因此自动给出忠实引用。

在维修手册例子中，系统可能把 E17 对应段落及手册版本号放入提示。回答若引用了旧版手册，问题可能出在召回或组装；若模型读到了正确版本却回答成相反含义，问题则落在生成或证据使用上。只检查最终文字，不足以区分这两类失败。

## 45.4 检索也可纳入模型训练与层内信息流

“检索增强”并不只指外部程序把几段文字拼进提示。研究架构还可以把检索文档作为生成过程中的潜变量、训练目标的一部分，或模型层内的额外信息流：

| 接入方式 | 检索材料怎样影响生成 | 代表性设计 |
| --- | --- | --- |
| 潜在文档建模 | 生成过程对候选文档分别计算，再按检索分布汇总输出概率 | Lewis 等人的 RAG-Sequence 与 RAG-Token |
| 检索增强预训练 | 预训练目标也训练检索器选择有用文档，生成模型在训练和推理阶段读取检索内容 | REALM |
| 解码器层内读取 | 先按输入块检索邻居，再通过交叉注意力把邻居表示送入自回归模型 | RETRO |

在 Lewis 等人提出的两种形式中，RAG-Sequence 对一段完整输出使用同一检索文档；RAG-Token 则允许不同输出 token 依赖不同文档。文档在模型里的作用因此不只是固定提示文本，而是参与其概率建模。[论文的模型定义](https://arxiv.org/abs/2005.11401)说明了这两种文档边缘化方式。

REALM 将学习检索器纳入预训练，并在微调和推理阶段使用检索；其知识增强编码器把输入和检索文档共同送入 Transformer。[REALM 论文](https://arxiv.org/abs/2002.08909)展示的是训练与检索协同设计，而不只是部署时增加一次搜索。

RETRO 则按序列块检索相邻文本，并通过 chunked cross-attention 把检索编码送入自回归 Transformer。[RETRO 论文](https://arxiv.org/abs/2112.04426)可用于观察检索如何进入解码器内部的信息流。这里的例子展示不同的结构位置和训练耦合；各论文的结果都只支持各自的模型、语料和评测条件，不能推出某一种接入方式普遍更好。

## 45.5 固定检索与按需检索改变控制位置

在固定流程中，系统在生成开始前取回一组材料，然后把它们交给模型。这样，检索是否发生主要由外部流程决定。另一种路线让模型判断当前回答是否需要外部资料，并在检索后评估候选材料及生成内容。

Self-RAG 是后一种设计的例子：模型可生成特殊的 retrieval/reflection tokens，表达是否要检索，并检查检索段落的相关性以及回答是否受段落支持。[Self-RAG 论文](https://arxiv.org/abs/2310.11511)描述了对应的训练和推理机制。它说明检索控制可以被纳入模型行为，但这需要特定训练与解码设计；普通生成模型不会因为接入检索器就自动学会何时查询或如何审查证据。

这种模型内的按需检索也要与 Agent 搜索区分。Self-RAG 研究模型围绕生成片段触发检索和反思；Agent 搜索则可能由控制器规划多步动作、调用外部工具并根据观察继续搜索。后者涉及工具协议与闭环运行，留给[第四十九章](49-Agentic-Model-Architecture.md)讨论。

## 45.6 错误会沿证据路径传递

同一条错误回答可能由不同阶段造成。沿着证据路径检查，才能知道该修复语料、检索策略、上下文组装，还是生成器：

| 发生位置 | 典型断点 | 读者应追问什么 |
| --- | --- | --- |
| 语料和索引 | 所需事实未收录，或新版本尚未进入索引 | 来源是否包含答案？索引对应哪个版本？ |
| 检索候选 | 有关段落未被找出，或相似但不适用的段落排在前面 | 支持答案的证据是否进入候选？候选是否匹配对象和条件？ |
| 证据组装 | 正确段落被截断、去重或排序时丢失，来源信息未保留 | 模型最终收到的文本是否含有完整证据和出处？ |
| 生成与引用 | 模型忽略证据、混合冲突材料，或引用不能支持该句的来源 | 该主张能否从实际上下文中的来源推出？引用是否覆盖主张？ |

RAG 不会自动同步资料，也不会自动裁决冲突版本。检索到相关段落，更不表示最终答案与其一致；Self-RAG 的论文也将“获得相关段落”与“生成内容受到段落支持”作为不同判断。[ALCE](https://arxiv.org/abs/2305.14627)对引用支持的分析同样表明，引用格式正确和引用在语义上支持主张不是一回事。

## 45.7 评估要分开检查检索覆盖、生成忠实度和回答质量

只用最终答案的准确率评估整个系统，会把不同组件压成一个结果。更有解释力的做法，是分别检查检索到的上下文是否相关、回答是否忠于这些上下文、回答是否回应问题，以及声明和引用之间是否有支持关系。

ARES 将 context relevance、answer faithfulness 和 answer relevance 分开评估；它使用轻量语言模型判断，并以一小部分人工标注配合 prediction-powered inference 减少估计误差。[ARES 论文](https://aclanthology.org/2024.naacl-long.20/)报告了其特定任务和校准条件下的评估结果。ALCE 则把流畅度、答案正确性和引用质量分开，并使用 citation recall 与 citation precision 检查声明和所引段落的支持关系。[ALCE 论文](https://arxiv.org/abs/2305.14627)中的指标不等于适用于所有领域的真值判定器。

还可以在同一组问题上比较三种证据条件：不提供外部段落、提供人工确认的 gold evidence、提供系统实际检索并组装的上下文。如果 gold evidence 条件下答案明显改善，而真实检索条件没有改善，检索或上下文构造可能是瓶颈；如果 gold evidence 也无法帮助模型，问题可能在模型使用证据、任务表达或评估设计。这种对照用于定位故障，不单独证明某种架构的普遍因果优势；ALCE 论文也报告了 gold-passage 条件与真实检索条件的对照。

自动评审结果仍应抽样人工复核，并在目标语料和任务上检查标签可靠性。ARES 的人工校准设计可以减少自动判断偏差，但它不免除对目标任务、数据分布和判断标准的核验。

## 45.8 按信息来源与任务控制方式划清架构边界

长上下文与 RAG 的差别首先在于证据进入请求的方式：前者把较大范围的材料直接放入当前上下文，后者从外部语料挑选片段后再送给模型。前者让模型直接面对较完整材料，后者增加了检索与筛选步骤。两者都可能漏掉或误用证据，结果取决于任务、材料组织、模型和评测方式；[第十三章](13-长距离依赖与lost-in-the-middle.md)进一步讨论长上下文中的位置和精确检索问题。

RAG 的外部文档检索也不等同于长期记忆。维修手册作为共享资料库，不必因为某个用户提问就变成该用户的跨会话记忆；若系统要保存用户偏好、历史事件并在后续更新或删除，就进入[第四十六章](46-Memory-Augmented-Transformer.md)的记忆读写问题。

如果模型只需在一次请求中从固定语料取证，检索增强路径可能已经足够；如果它要决定何时继续查找、调用网页或数据库工具、根据返回结果规划下一步，就进入[第四十九章](49-Agentic-Model-Architecture.md)的 Agent 搜索和执行路径。架构选择应由证据位置、更新方式和控制需求决定，而不是把长上下文、RAG、记忆和 Agent 搜索排成脱离任务的优劣榜。

RAG 的核心架构变化，是让外部语料可以通过检索进入生成过程。判断它是否真正发挥作用，需要同时看证据从哪里来、如何进入模型、模型怎样使用它，以及回答是否被来源支持。
