# 第十六章：Decoder-only 为什么成为通用 LLM 主流

## 16.1 先把架构、目标和任务拆开

解释 decoder-only 为何成为通用 LLM 的主流时，容易把三个问题合在一起：模型内部怎样传递信息、训练时优化什么目标、用户怎样把任务交给模型。先拆开它们，才能看清这种架构的优势到底来自哪里。

| 设计层次 | 要问的问题 | 例子 |
| --- | --- | --- |
| 架构 | 每个位置能读取哪些位置？输入和输出之间经过哪些模块？ | 双向 encoder、因果 decoder、encoder-decoder cross-attention |
| 预训练目标 | 哪些 token 是预测目标？模型要从什么上下文恢复它们？ | masked language modeling、next-token prediction、span denoising |
| 任务格式 | 任务输入和期望输出怎样表示？ | 分类标签、输入到输出的翻译、指令后续写 |

这些层次之间有关联，却不互相定义。Decoder-only 常与因果语言模型搭配，但同一类主干也能使用 prefix LM：提示前缀内部可以互相读取，生成目标仍按因果顺序读取前文。Encoder-decoder 常用于去噪或条件生成，也能训练语言建模目标。T5 的架构实验就分别比较了模型结构和去噪、语言建模目标；UL2 也明确将架构类型和预训练目标作为可组合的设计选择。[T5 论文](https://arxiv.org/abs/1910.10683)、[UL2 论文](https://arxiv.org/abs/2205.05131)

本章说的 decoder-only，是指主要文本主干由一串因果自注意力 block 组成，没有再分出一套双向 encoder 和连接两者的 cross-attention。模型仍需要 tokenizer、输入处理和输出投影；“only”描述的是主干的信息流，不是整个系统只含一种组件。因果 mask 的精确定义见[第八章](08-causal-mask-prefix-lm-bidirectional-attention与注意力模式.md)。

## 16.2 用同一个任务比较三类信息流

假设任务是把“我明天到”翻译成英文。三类架构都能用于这个任务，差别在源句如何进入网络，以及目标词如何访问源句。

| 架构 | 输入如何传播 | 输出如何产生 | 对这个任务的含义 |
| --- | --- | --- | --- |
| Encoder-only | 输入 token 通常彼此双向可见，形成上下文化表示 | 常见做法是在表示上接分类或抽取头；开放式序列生成通常需要额外生成机制或适配 | 适合形成输入表示，但不是最直接的标准生成路径 |
| Encoder-decoder | Encoder 双向读取源句；Decoder 的每一步通过 cross-attention 读取源句表示 | Decoder 按因果顺序逐 token 生成译文 | 输入和输出边界明确，适合直接表达源文本到目标文本的转换 |
| Decoder-only | 把任务指令、源句和答案前缀接成一条序列；目标位置只能读取此前 token | 在前缀末尾继续预测目标 token | 同一主干处理条件和续写，输入、输出使用同一种序列接口 |

原始 Transformer 采用 encoder-decoder 结构，最初验证任务是机器翻译；这说明 Transformer 本身并不等同于 decoder-only。[Attention Is All You Need](https://arxiv.org/abs/1706.03762) 在 decoder-only 方案里，模型没有单独的“源句编码阶段”，但源句仍会通过前缀中的 token 影响后续输出。它用较少的结构约定换来更统一的输入路径；这描述的是结构取舍，不等于证明它的计算或质量在所有任务上更好。

## 16.3 Next-token prediction 如何承载多种文本任务

可以把一个翻译样本表示为：

> 任务：翻译成英文。源句：我明天到。译文：I will arrive tomorrow.

训练时，完整样本序列已经可见；模型在每个受监督位置读取此前 token，预测训练文本中紧随其后的真实 token。这些位置的预测可以并行计算。监督信号可以从原有文本序列直接构造，因此不必为每一种文本任务都重新设计一种网络输出头。具体训练配方可能预测序列中的全部 token，也可能只对目标片段计算损失或改变不同位置的权重；不能仅凭“decoder-only”推断每个位置都以相同方式参与训练。

推理时，系统给模型任务说明和输入内容，再从目标开始的位置生成后续 token。同一种形式可承载不同任务：

| 任务 | 提供给模型的前缀 | 模型续写 | 仍需处理的任务差异 |
| --- | --- | --- | --- |
| 摘要 | 摘要指令和源文 | 一段摘要 | 长输入的证据覆盖与摘要质量 |
| 问答 | 问题、可选上下文和答案标记 | 答案文本 | 正确性、引用和拒答条件 |
| 分类 | 输入文本和允许的标签说明 | 标签 token，或对候选标签打分 | 标签格式、类别先验和决策阈值 |
| 代码续写 | 已有代码前缀 | 后续代码 token | 语法、执行结果和安全边界 |

因此，“统一成续写”统一的是模型接口和预测形式，不是各任务的目标、评估标准或可靠性要求。比如模型能够生成一个类别名称，不会自动使它成为成本最低或最准确的分类器；工具调用也可以序列化成文本，但外部执行器仍要检查参数和权限。

## 16.4 统一接口如何支持通用生成

当任务以开放式文本生成为主时，decoder-only 的数据路径和使用方式自然衔接：训练样本是一串 token，模型学习根据前文继续预测；使用时，指令、示例、已有对话和可选材料也作为前缀，模型继续生成回答。改变任务时，常能沿用主干并调整输入格式、数据和微调目标，而不是为每项任务都换一套网络结构。

GPT-3 论文提供了这种使用方式的代表性实例：研究者训练了 1750 亿参数的自回归语言模型，再把任务描述和少量示例放入文本上下文，在不做梯度更新的条件下测试翻译、问答、填空等任务。论文也列出模型表现较弱的任务和网络语料带来的方法学问题，所以它证明的是特定大模型在特定评测中的 few-shot 能力，不是“只要 next-token 训练就会可靠解决任意任务”。[Language Models are Few-Shot Learners](https://arxiv.org/abs/2005.14165)

这类结果与通用生成模型的使用接口相合：一个模型可以接收文本上下文，再给出文本续写。规模化训练、数据、计算和后续微调共同参与了这种能力的形成；公开结果没有把这些因素与架构本身完全分离。把 decoder-only 的主流地位只归因于“结构简单”，或只归因于“因果目标更强”，都超出了现有比较能单独证明的范围。GPT 的发展、scaling 结果与 ICL 证据见[第五十一章](51-GPT-decoder-only-scaling-ICL.md)；本章不展开 ICL 的内部机制和证据使用问题，详见[第十二章](12-in-context-learning与显式token检索能力.md)。

从结构上可以提出一个较窄的解释：decoder-only 让输入 token 和输出 token 共用同一条因果主干，任务格式也统一成前缀与续写。这降低了通用生成场景中需要管理的模型接口种类。把这种结构便利视为行业采用的一项可能原因是合理的综合判断，但它不是由单个对照实验隔离出来的因果结论；任务需求、训练配方、软硬件条件和模型生态也会影响选择。

## 16.5 为什么“主流”不等于“处处最优”

架构比较必须先说明比较对象和训练条件。不同结构需要的参数量、目标 token、训练计算、后训练和输入输出长度可能不同；只比较模型名称或参数量，不能说明谁在相同资源下更合适。

T5 的研究在其 text-to-text 任务和实验配方中发现，encoder-decoder 配合去噪目标在所测任务上表现最好。作者还指出，比较 encoder-decoder 与 decoder-only 时，参数量和计算量不能同时用简单的层数对齐；其结果因此既说明 encoder-decoder 的有效性，也说明结构比较取决于对齐方式。[T5 论文的架构实验](https://arxiv.org/abs/1910.10683)

Wang 等人的大规模比较把架构、预训练目标和提示式多任务微调分开考察：他们的纯无监督 zero-shot 结果中，causal decoder-only 配 autoregressive objective 最强；加入多任务微调后，带非因果输入可见性的模型配 masked-language-modeling 目标在该实验中表现最好。变化说明后训练配方会改变架构排序，并不推出某一种非因果架构在所有场景占优。[论文摘要与实验范围](https://arxiv.org/abs/2204.05832)

2025 年一项预印本把 encoder-decoder RedLLM 和 decoder-only DecLLM 从约 1.5 亿到 80 亿参数进行比较：作者报告 DecLLM 在其预训练的 compute-optimal 前沿上较强，而 RedLLM 经指令微调后能在部分下游指标上达到可比或更好表现，并在该团队报告的设置中具有推理效率优势。数据、模型设计、评测和规模范围都属于这项研究的具体条件，不应外推为普遍性能结论。[Encoder-Decoder or Decoder-Only?](https://arxiv.org/abs/2510.26622)

这些结果支持更有限也更可靠的判断：

- **Encoder-only** 直接产生上下文表示，常适合分类、检索和逐 token 标注等任务；若目标是开放式长文本生成，还需要补上相应的生成接口。
- **Encoder-decoder** 把输入表示和目标生成分开，输入可以双向编码、目标可以逐 token 生成；当源输入和目标输出有清楚边界时，这种结构很自然。
- **Decoder-only** 把条件与续写放入同一序列主干，适合需要一个模型覆盖多种开放式生成任务的场景；这并不意味着它在表示抽取、固定格式转换或长输入短输出任务中总有最低成本。

具体模型的推理缓存、长输入延迟和 serving 成本由模型细节与系统实现共同决定，本章不从架构名称直接推断；相关边界见[第十一章](11-kv-cache长上下文推理和显存增长问题.md)和[第十五章](15-Transformer流式在线与低延迟局限.md)。

## 16.6 用信息流和证据判断架构选择

回答“为什么 decoder-only 成为通用 LLM 主流”时，可以把理由说成一条有边界的链：很多通用助手任务需要开放式生成；decoder-only 把指令、上下文和目标放进同一 token 序列；next-token 训练和生成时的续写接口直接相连；大规模模型展示了用同一接口处理多类任务的可行性。架构便利、训练规模、数据和生态共同构成解释，现有研究不足以把主流地位还原成单一技术原因。

遇到一个新模型或新任务时，可按以下顺序分析：先画出输入和输出分别经过哪些模块，再标出 token 之间的可见范围；然后确认训练目标及实际参与损失的位置；最后对齐数据、参数、训练计算、微调方式、任务指标和推理条件。这样就不会把“常见”“能做”或“某次实验得分高”误说成“架构普遍最优”。

本章建立的是 decoder-only 作为通用生成主干的设计理由和比较边界。下一章转向现代 GPT、LLaMA 与 Mistral 风格 block 的具体结构和配置取舍，见[第十七章](17-LLaMA-GPT-Mistral架构对比.md)。
