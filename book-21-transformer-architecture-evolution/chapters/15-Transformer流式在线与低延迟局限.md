# 第十五章：Transformer 在流式、在线与低延迟场景的局限

## 15.1 先分清流式输入、流式输出和在线服务

“流式”常被用来描述三件不同的事：输入分段到达、模型逐步发出输出，以及服务持续接收和调度请求。它们会同时出现，但对应的限制并不相同。

| 场景 | 持续到达的对象 | 模型或系统要解决的问题 |
| --- | --- | --- |
| 流式输出 | 新生成的 token | 后一个 token 依赖前面已经生成的 token；用户能逐步看到结果，但不能把同一条自回归输出一次并行算完 |
| 流式输入 | 新输入片段 | 模型要决定何时开始输出、每段能看见哪些上下文，以及怎样保留跨段信息 |
| 在线服务 | 新请求、取消和状态变化 | runtime 要在请求之间分配计算和缓存，并在并发下控制等待时间 |

因此，Transformer 并非不能流式输出：自回归解码本来就是逐步产生 token。真正的限制是首个 token 要等已有输入完成必要计算，后续 token 又受前一步结果约束。若输入本身持续到达，还要额外解决“是否继续等更多输入”和“如何处理过去片段”的问题。

原始 Transformer 的 decoder 每一步都使用先前生成的符号；它的 encoder 则对已给定的输入序列做双向 self-attention。[《Attention Is All You Need》第 3 节](https://papers.neurips.cc/paper/7181-attention-is-all-you-need.pdf)定义了这种自回归 decoder。同步语音翻译研究进一步说明，能够处理部分输入、能够持续处理很长的输入流、以及能够在实际计算时间内输出，是彼此相关但不同的要求；其 augmented-memory encoder 和 wait-k 策略是针对特定任务的一种设计，不是所有 Transformer 的默认能力。[Ma 等，2020](https://arxiv.org/abs/2011.00033)

## 15.2 一条请求里，用户分别在等什么

一次常见的 decoder-only 请求可以沿时间线读：请求到达后，服务可能先排队并完成分词；prefill 处理已经提供的输入并构造后续解码所需的状态；模型据此采样第一个输出 token；之后 decode 反复生成并返回后续 token，直至结束。流式接口可以提前发送输出，但不会消除这些阶段。

| 指标 | 观察的等待 | 读数时要确认什么 |
| --- | --- | --- |
| TTFT（首 token 时间） | 请求发出到收到第一个输出 token | 起点是否包括排队、分词和网络；输入长度及缓存命中情况是什么 |
| TPOT（每输出 token 时间） | 首 token 之后，生成剩余 token 的平均间隔 | 输出 token 数、起止 token 和平均方法如何定义 |
| ITL（token 间隔） | 相邻输出 token 之间的间隔，可观察分布和尾部 | 是逐间隔统计，还是先对每个请求求平均；工具口径是否相同 |
| 端到端延迟 | 请求发出到完整响应结束 | 是否包括客户端、网络、工具调用和后处理 |

所以，“响应时间”一个平均数很难指出问题发生在输入处理、逐 token 解码、排队还是网络。TTFT 和 TPOT 常用于分别观察 prefill 与 decode，但真实计时边界由具体客户端和 benchmark 决定；不同工具对首个空响应、最后一个 token 和间隔分母可能采用不同规则。[NVIDIA 的推理 benchmark 指标说明](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)和 [Chip Huyen《AI Engineering》第 9 章摘要](https://github.com/chiphuyen/aie-book/blob/main/chapter-summaries.md)都把首 token 与后续 token 延迟分开讨论；比较数字前仍须核对实际计时协议。

## 15.3 自回归让单条输出必须逐步前进

模型生成第一个 token 时，依据的是已提供的输入；要生成第二个 token，模型还必须接收第一个 token 的结果。此依赖会继续传到后面。因此，Transformer 能在训练和 prefill 时并行处理一批已知位置，不代表它能并行确定同一条未知输出中的所有未来 token。

KV Cache 改变了重复工作的范围。prefill 为已有上下文建立各层的 key/value；后续 decode 可以复用它们，无须每生成一个 token 就重新计算整段历史的 K/V。但在保留全上下文的 attention 中，新位置仍需读取可见的历史 K/V；随着会话增长，缓存占用随保留的 token 和层数增加，每步 attention 接触的历史也更长。具体字节数和实际延迟还受注意力头配置、精度、缓存实现、batch 和硬件影响。[第十一章](11-kv-cache长上下文推理和显存增长问题.md)专门推导 KV 容量与读取成本，本章只保留它对逐步生成的含义。

这就是低延迟场景的一项结构性代价：无论 GPU 多快，普通自回归路径都要等前一步 token 确定后才能继续；即便状态缓存避免了重复计算，保留和读取长历史仍然有成本。实际每 token 时间不由某个单一复杂度式子决定，不能仅凭“长上下文”或“显存带宽”推断所有模型和负载的瓶颈。

## 15.4 输入持续到达时，模型需要明确的读取策略

双向 encoder 在给定输入上可以让每个位置读取其他位置。若语音或文本还没有结束，后续片段可能改变前面片段的解释；直接把当前前缀当成完整输入，未必等价于等整段到齐后再编码。系统通常要在几种做法中作选择：多等一些输入再输出、按段限制可见上下文、保留可复用的记忆，或在新输入到来后重新计算部分表示。每种选择改变的都是延迟、可用历史和任务质量之间的关系。

因果 decoder 的输入可以按片段追加，并在实现支持时复用已有 KV；但位置编号、mask、片段边界和状态更新必须与整段序列的约定一致。若需要将输入和输出交替推进，还要定义何时读下一段、何时写输出。同步翻译中的 wait-k 就是一个例子：先读取一定量的源内容，再开始交替读取和生成。因为翻译可能需要后续语境来处理语序，这个等待策略会影响质量和响应时间；该论文同时讨论算法延迟与实际计算延迟，提醒读者不能把“可以提前输出”直接当成“计算足够快”。[Ma 等，2020](https://arxiv.org/abs/2011.00033)

连续输入还会带来状态长度问题。保留全部历史，能让 attention 继续访问更早位置，却使 KV 状态增长；限制窗口或把过去压缩到记忆状态，可以控制保留量，却改变模型能精确访问哪些旧信息。[第十一章](11-kv-cache长上下文推理和显存增长问题.md)讨论缓存增长，[第十九章](19-Sliding-Window与稀疏注意力.md)讨论窗口注意力，[第二十四章](24-Linear-Attention基本思想与核技巧.md)讨论线性 attention 的状态表示；这里的重点是：流式处理必须说明历史如何进入下一步，而不能只说“每次送一个 chunk”。

## 15.5 调度能缓解延迟，不能取消模型的逐 token 依赖

在线服务同时处理许多请求。一条长 prompt 正在做 prefill 时，另一条请求可能已经进入 decode；二者共用计算设备时，调度方式会影响已有请求的 token 间隔。这个等待来自服务如何安排工作，并不等同于模型必须逐 token 生成的依赖。

系统研究展示了两类相关办法。Orca 把调度推进到模型迭代粒度，使新请求和正在生成的请求可以在后续迭代中重新组合；Sarathi-Serve 将长 prefill 切成小块，再与 decode 工作安排到一起，以缓和 prompt 计算造成的生成停顿。[Orca，OSDI 2022](https://www.usenix.org/system/files/osdi22-yu.pdf)；[Sarathi-Serve，2024](https://arxiv.org/abs/2403.02310)。这些是 runtime 层的缓解方式：它们能拆分 prompt 工作，却不改变普通逐步解码对前一 token 的条件依赖，也不自动消除不断增长的上下文状态。

具体取舍依赖 runtime 版本、硬件、请求长度和负载。例如，vLLM v0.25.1 的 V1 文档说明，chunked prefill 可把较长输入拆分后与 decode 请求同批处理，并通过 token budget 调节 TTFT、ITL 和吞吐之间的关系；这些参数说明只适用于该版本，不能当作所有引擎和负载的普遍结论。[vLLM 官方文档](https://docs.vllm.ai/en/v0.25.1/configuration/optimization/)。完整的批处理、调度和压测方法属于[第六册第二章](../../book-06-llm-deployment/chapters/02-推理基础.md)、[第五章](../../book-06-llm-deployment/chapters/05-推理引擎.md)和[第六章](../../book-06-llm-deployment/chapters/06-批处理与调度.md)；本章只借这个例子区分模型结构限制与服务调度限制。

## 15.6 选择架构时，先问历史要怎样保留

全上下文 Transformer 把各位置的 K/V 保存在显式状态里，后续 token 可以按内容访问保留的历史；代价是状态随序列增长。递归状态模型逐步更新有限状态，把过去压缩在这个状态中；固定模型配置下，单个序列的状态大小可以不随历史长度继续增长，但模型不再持有每个旧 token 的独立表示。两种设计回答的是不同的信息访问问题。

Mamba 论文展示了递归状态空间模型如何用输入相关的选择机制控制信息写入，并用硬件感知的并行 scan 实现序列计算。论文中的效率结果来自作者报告的指定模型、实现和硬件设置；它说明递归状态可通过适配硬件的方式计算，不足以证明任何 SSM 在任何服务中都更快。[Gu 与 Dao，Mamba，2023](https://arxiv.org/abs/2312.00752)。关于 SSM 的状态更新、Mamba 结构和 attention 混合路线，分别见[第二十九章](29-SSM数学直觉.md)、[第三十二章](32-Mamba与Selective-Scan.md)和[第四十三章](43-Attention与SSM混合架构.md)；架构横向取舍见[第四十二章](42-替代架构横向对比.md)。

遇到低延迟需求时，可以先定位约束属于哪一类：输入必须等齐、每个输出 token 受前一步约束、长历史需要保留，还是请求在 runtime 中排队。再问任务是否需要精确回看旧 token，能否接受窗口或压缩状态，以及目标硬件和请求负载下测到的 TTFT、TPOT/ITL 与质量如何。这样得到的是有条件的架构判断，而不是“Transformer 不能在线”或“线性复杂度必然更快”这样的绝对结论。
