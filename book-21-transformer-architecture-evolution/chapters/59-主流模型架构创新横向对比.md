# 第 59 章 主流模型创新点横向对比：从模块清单到资源账本

## 59.1 为什么横向比较很容易失真

模型发布材料常用不同口径描述参数量、上下文、训练 token、速度和 benchmark。一个模型报告 total parameters，另一个报告 active parameters；一个测裸模型，另一个测 chat 模型；一个启用工具，另一个关闭工具。把这些数字排成一张表，可能看起来整齐，却没有比较意义。

横向比较应该先建立共同坐标：模型结构、历史状态、训练数据、后训练、推理执行和任务结果。每个模型都要回答同样的问题，而不是只摘录它最有利的指标。

## 59.2 六个比较维度

第一是 attention 路径：MHA、MQA、GQA、MLA、local、global 或递归。第二是 FFN 和容量：dense、MoE、专家数、top-k 和 active 参数。第三是位置和上下文：RoPE、relative bias、插值、训练长度和有效 recall。第四是训练：数据、token、scaling、SFT、偏好和 reasoning RL。第五是推理：KV、latent/state、量化、speculative 和 kernel。第六是系统：工具、多模态、检索、安全、API 和 SLO。

## 59.3 统一的参数与计算账本

对 dense 模型，权重和每 token 的计算都主要受总参数影响；对 MoE，必须同时记录 total 和 active：

~~~math
N_{\mathrm{total}},\qquad
N_{\mathrm{active}},\qquad
C_{\mathrm{token}},\qquad
M_{\mathrm{weight}}
~~~

对 attention，还要记录：

~~~math
M_{\mathrm{KV}}
\approx 2BLTH_{\mathrm{kv}}d_hb
~~~

对 latent 或递归路径，还要记录 state/latent size、更新 kernel、恢复成本和精确检索能力。只有资源账本和质量账本同时存在，比较才不会停在宣传词。

## 59.4 典型模型路线的定位

GPT 系列的核心是 decoder-only scaling 和 ICL；Chinchilla 纠正参数与数据配比；LLaMA 把现代开源 decoder 配方标准化；Mistral 通过 GQA、滑窗和小模型效率优化推理；Mixtral 将开源稀疏 MoE 推到实用层面；Gemini、Claude、GPT-4V 代表多模态、长上下文和系统能力的产品化；Qwen、LLaMA 3、Gemma 体现数据和生态成熟；DeepSeek 将 MLA、MoE、MTP 与 reasoning RL 组合起来。

这些是研究和产品路线的概括，不是互斥分类。一个后续模型可能同时继承多个方向，且闭源模型的内部细节未必公开。

## 59.5 用能力—成本矩阵比较

可以把任务分为局部语言、长程检索、代码执行、数学推理、工具调用、多模态理解和流式处理。对每个模型记录质量 Q、成本 C、延迟 L、内存 M 和风险 R：

~~~math
\mathbf{v}_{m,t}
=\left(Q_{m,t},C_{m,t},L_{m,t},M_{m,t},R_{m,t}\right)
~~~

最终选择不是寻找一个所有维度都最大的模型，而是根据任务权重求解：

~~~math
m^\star=\arg\max_m
\sum_t w_t Q_{m,t}
-\lambda C_m-\mu L_m-\nu R_m
~~~

权重应由实际产品和风险定义，不能由 benchmark 排名代替。

## 59.6 比较实验的控制变量

至少固定：

~~~text
model revision
tokenizer
prompt and template
input length
output budget
decoding parameters
tool and retrieval status
hardware
runtime
quantization
grader
~~~

长上下文任务还要固定证据位置、干扰、文档版本和引用格式；推理任务要固定是否允许多次采样、工具和 verifier；多模态任务要固定分辨率、帧数和预处理。

## 59.7 一个横向评测记录器

~~~python
def comparison_row(model, task, result):
    return {
        "model": model["id"],
        "revision": model["revision"],
        "task": task["name"],
        "quality": result["quality"],
        "evidence_recall": result.get("evidence_recall"),
        "tokens_in": result["tokens_in"],
        "tokens_out": result["tokens_out"],
        "ttft_ms": result["ttft_ms"],
        "tpot_ms": result["tpot_ms"],
        "peak_memory_mb": result["peak_memory_mb"],
        "tool_calls": result.get("tool_calls", 0),
    }
~~~

把原始记录保存下来，再生成汇总表。不要手工抄 benchmark 数字，因为版本更新、模板和测量环境很容易造成错配。

## 59.8 结构比较和结果比较要分开

结构比较回答“模型怎么做”，结果比较回答“在特定任务和成本下表现如何”。结构相似不代表结果相同，结果相近也不代表资源路径相同。

例如两个模型都报告 1M context，一个可能使用显式 attention，另一个可能使用混合路径或 retrieval；一个在单 needle 上成功，另一个在多证据冲突上更强。只有将结构证据和受控实验并列，才能解释结果。

## 59.9 消融比排名更有信息

对某模型做模块消融：

~~~text
full model
  -> remove GQA or MLA
  -> remove local window
  -> dense FFN instead of MoE
  -> remove MTP
  -> reduce long-context training
  -> disable tool or verifier
~~~

每个消融都要测质量、成本和失败类型。若一个模块只提高普通 benchmark，却损害精确引用，是否保留取决于产品任务。

## 59.10 证据等级和不确定性

比较表可以增加证据等级：

| 等级 | 证据 | 可以支持的结论 |
| --- | --- | --- |
| A | 原始论文、官方技术报告、代码 | 公开结构和实验方法 |
| B | 官方模型卡、API、产品文档 | 接口和发布方声明 |
| C | 可复现第三方测试 | 特定版本与 harness 的观察 |
| D | 社区逆向、传闻、营销转述 | 只能作为待核验线索 |

如果某个模型是闭源的，结构列应填“公开未说明”，而不是根据输出猜测层表。横向表中明确缺失证据，反而比填入假精确值更专业。

## 59.11 版本和时间轴

前沿模型变化很快。比较记录要绑定日期、模型 id、API 版本和权重 revision。产品页面的“当前模型”可能在服务端更新，第三方结果如果没有时间戳就难以复现。

时间轴适合讲演进，不适合替代当前评估。历史模型的创新仍然有教育价值，但不能用旧 benchmark 推断今天的产品能力。

## 59.12 常见错误

只看总参数；把 active 和 total 混在一起；把上下文上限当有效能力；把 benchmark 分数跨 harness 直接排序；把闭源推测写成结构事实；忽略工具、检索和后训练；没有测 p95 和单位成功成本；把时间线摘要当成机制解释。

## 59.13 把比较表变成可复现的实验记录

横向表格中的每个数字都要有来源、版本、条件和采集时间。benchmark 分数绑定 prompt、shot、解码、工具、grader 和数据版本；吞吐绑定硬件、batch、长度、dtype、runtime 和并发；上下文声明绑定有效任务而非只绑定 API 上限。

推荐为每条结果保存 raw output、错误分类、引用证据、trace 和环境 manifest。只有表格没有原始证据，后续无法判断回归来自模型、评测器还是运行时。

## 59.14 结构创新与系统创新的区分

结构创新改变前向信息流或参数/状态表示，例如 GQA、MLA、MoE、SSM、NoPE 和混合 attention；系统创新改变 kernel、cache、调度、量化或工具编排。两者可能共同出现在一个发布中，但解决的问题不同。

判断一个新名词属于哪一层，可以看它是否进入训练计算图、是否改变 state shape、是否需要新权重、是否只在 runtime 生效。系统优化同样重要，但不能用 serving speedup 推断模型具有新的推理能力。

## 59.15 用 Pareto 前沿观察模型差异

模型比较通常没有全局赢家。对任务 t 和模型 m，记录质量、成本、延迟、内存和风险向量；删除被另一模型全面支配的点，剩余点构成 Pareto 前沿。不同产品的权重不同，前沿上的多个模型都可能合理。

面试回答应解释为什么某模型适合某 workload，而不是只报排名。还要说明未公开结构的未知项和需要补做的实验，避免把发布新闻改写成架构定律。

## 59.16 从发布数字到可迁移结论

横向比较的最终产物不应是一张静态排行榜，而应是一组带条件的判断：在某种长度和并发下，某种 cache 或 state 让单位成本下降；在某种证据任务下，某种 global 或 retrieval 路径让引用更可靠；在某种硬件上，某种 kernel 让 p99 改善。换硬件、版本或 harness 后，结论需要重新验证。

这也是阅读新模型发布的正确姿势。模型名是入口，公开结构和评测是证据，资源账本和失败回放才是能迁移到下一个模型的知识。

## 59.17 读新模型发布的最小证据链

一条可靠的比较结论至少要有四个环节：一手资料说明模型或接口是什么，结构/训练资料说明机制，独立或自建评测说明任务行为，profile 和成本记录说明系统代价。缺少其中一环，就要把结论限定在剩余证据范围内。

例如“更长上下文”需要上下文声明、训练或技术报告、位置/证据任务和长请求成本；“更高效 MoE”需要专家配置、active 口径、通信 profile 和质量验收条件。只抄产品页面的一句描述，不能形成完整架构判断。

## 59.18 迁移到下一代模型的比较方法

当模型版本升级时，保留一组固定的任务和系统基线，增加新模型而不是覆盖旧结果。记录同一 prompt、同一 tokenizer 或明确说明 tokenizer 差异，固定输出预算、工具、检索和 grader。这样可以判断收益来自模型、harness 还是评测条件。

回归集还要包括失败任务、长上下文中间位置、结构化输出、引用、工具副作用和恢复。前沿模型的平均分提高，不代表生产中所有高价值路径都改善。

## 59.19 用比较矩阵避免新闻摘要

横向比较至少分为六层：attention/KV、FFN/MoE、位置和长上下文、预训练数据与长度、后训练/reasoning、runtime/协议。每一格记录公开事实、证据来源、可复现实验、资源影响和未知字段。

例如“上下文更长”要继续问：训练长度是多少，评测是否测中间证据，位置方案是什么，KV 如何增长，p99 是否可接受，工具和多模态输入是否也支持。只有回答这些问题，模型发布才转化为架构知识。

## 59.20 比较结果要绑定 workload

模型 A 在短聊天领先，模型 B 在代码修复和长文档引用领先，不能用一个平均分决定选择。建立 workload matrix：短/长 prompt、短/长 output、文本/媒体、direct/reasoning/tool、低/高风险，并报告质量、成本、延迟、容量和安全。

## 59.21 生命周期判断

有些架构创新最终会成为 runtime 优化，有些会成为少数任务的专用路径，有些会被更强模型和更长上下文吸收。判断一项创新时，既要说明它解决的旧约束，也要说明约束消失后的生态位变化。

## 59.22 资料范围与比较条件

原始论文、技术报告、模型卡、API 文档和可复现实验各自承担不同证据角色。横向比较不追求把所有模型压成一个排名，而是建立清楚的资源、能力和证据账本。

真正有用的结论通常是条件句：在固定模型版本、任务、输入长度和硬件下，某种路径降低了某类成本，同时在哪些高价值任务上产生了什么影响。

## 59.23 面试问题与练习

**问：如何比较一个 dense 70B 和一个 MoE 400B 模型？**

同时报告 total/active 参数、训练 token、权重和 KV 内存、每 token 计算、通信、吞吐、质量、p95 和单位成功成本，不能只比较 70B 与 400B。

**问：为什么模型排行榜不等于选型答案？**

排行榜通常固定任务有限，可能没有工具、长上下文、成本、延迟、安全和版本治理；实际选型要按自己的任务和 SLO 复测。

**练习：**建立一个七任务横向评测矩阵，对每个模型填写结构证据等级、质量、显存、延迟和失败类型。

资料入口：

- GPT-3: https://arxiv.org/abs/2005.14165
- LLaMA: https://arxiv.org/abs/2302.13971
- Mistral: https://arxiv.org/abs/2310.06825
- Mixtral: https://arxiv.org/abs/2401.04088
- DeepSeek-V2: https://arxiv.org/abs/2405.04434

## 59.24 横向比较的证据卡

对每个模型建立同样格式的 evidence card：公开结构、训练事实、上下文声明、tokenizer/template、推理协议、硬件/价格、评测条件、未知字段和复测结果。来源按论文、官方模型卡、产品文档、代码/权重和自测分层，不能把产品宣传语与可复现实验混在一列。

然后把模型放入自己的 workload：短问答、代码、长文档、多模态、工具、拒答和高风险任务。每项不仅记录平均质量，还记录困难样本、引用支持、结构化通过率、TTFT/TPOT、p99、显存、fallback、迁移和回滚。横向比较最终服务于选择，而不是制造一个脱离条件的总排名。

## 59.25 一个有数字的 Pareto 比较

假设模型 A 的任务质量为 82、p99 为 1.2 秒、单位成功成本为 1.0；模型 B 的质量为 84、p99 为 2.4 秒、单位成功成本为 1.8；模型 C 的质量为 80、p99 为 0.6 秒、单位成功成本为 0.55。若业务要求质量至少 81 且 p99 不超过 2 秒，A 可能是最稳妥选择，B 被延迟验收条件排除，C 被质量验收条件排除。若业务是离线批处理，B 可能重新进入候选。

这个例子说明“新架构更强”没有脱离 workload 的意义。比较矩阵应保存原始向量和硬性条件，再计算 Pareto 前沿；不要先把质量、延迟和成本压成一个未经解释的总分。对安全和权限违规，还应使用硬失败而不是负权重稀释。

## 59.26 从模块名到因果结论

当一次模型发布同时改变 MLA、MoE、数据、MTP 和后训练时，发布前后差异只能支持整套系统的行为差异。要讨论某个模块的因果作用，至少需要 matched ablation：固定数据、训练 token、硬件和评测，只替换一个主要因素；对 serving 模块则还要固定模型质量和请求分布。

如果没有公开消融，正文可以写“该版本在公开条件下报告了更低成本/更高质量”，不能写成“提升完全来自某模块”。这条边界对阅读新模型尤其重要，因为架构名往往比实验条件更容易传播。

## 59.27 把 evidence card 变成可执行的比较矩阵

一张模型对比表只有在字段定义相同、来源可追溯、未知项不被填成猜测时才有用。每个模型可以先建立一张 evidence card，再把它展开成任务矩阵：

~~~text
identity: model id, revision, release date
architecture: dense/MoE, attention path, position, state/cache
training: disclosed data, tokens, objective, post-training
interface: context claim, modalities, tools, schema constraints
runtime: dtype, quantization, hardware, batch, scheduler
workload: task, input/output length, tool policy, retry policy
result: quality, evidence support, TTFT/TPOT, p99, memory, cost
unknowns: fields not publicly disclosed
source_level: paper / model card / API doc / code / controlled test
~~~

其中 `unknowns` 是正式字段，不是备注。一个闭源模型没有公开层数，就保留 unknown；一个开源模型虽然有配置文件，也不能因此推断所有训练细节。任务结果另存为原始样本、失败类型和评测脚本，汇总表只作为视图。这样做能避免“发布页的一句宣传语”与“同一 harness 下的实验观测”混在同一列。

## 59.28 MoE 的 total/active 参数必须接上通信账本

比较 dense 和 MoE 时，只写 `70B` 对 `400B` 没有意义。对 MoE，`N_total` 影响权重存储和专家加载，`N_active` 更接近每 token 的矩阵计算，而 router、容量因子和 expert parallel 又会带来通信和 padding。一个简化的每 token 账本是：

~~~math
C_{\mathrm{token}}
\approx C_{\mathrm{dense}}(N_{\mathrm{active}})
 +C_{\mathrm{router}}+C_{\mathrm{all\text{-}to\text{-}all}
 +C_{\mathrm{padding}}.
~~~

如果 batch 中 token 分布不均，热门 expert 会先达到 capacity，溢出的 token 被丢弃、回退或 padding；此时平均 active 参数仍然好看，但有效吞吐和质量下降。横向报告应同时记录 expert load 的均值、最大值和 p99、overflow rate、all-to-all bytes、权重显存、冷 expert 加载和失败时的 fallback。对于同一模型，短 prompt、长 prompt、高并发和跨节点部署可能得到完全不同的 Pareto 位置。

## 59.29 Pareto 前沿不能替代硬性条件

质量、成本、延迟和风险通常互相冲突。设模型 `a` 在所有指标上不差于模型 `b`，且至少一项严格更好，则可以说 `a` 支配 `b`；不被任何模型支配的点构成 Pareto 前沿。但真实系统还有硬约束：越权、结构化输出非法或引用缺失不能被低成本“抵消”。

可以先筛选验收条件，再计算软目标：

~~~math
\mathcal{M}_{\mathrm{valid}}
=\{m\mid Q_m\ge q_0,\ L_m\le l_0,
R_m\le r_0,\ S_m=1\},
~~~

再在 `M_valid` 中比较单位成功成本和吞吐。若业务要求质量至少 0.90、p99 不超过 2 秒、结构化通过率为 1，那么一个质量 0.95 但 p99 为 4 秒的模型不能靠加权平均偷偷入选。对于风险项尤其要使用硬失败验收条件，避免“平均分很好但关键样本越权”的错误选型。

## 59.30 多模块发布只能支持系统级因果结论

新模型往往同时修改 attention、MoE 路由、训练数据、上下文长度、MTP、后训练和推理 kernel。发布前后性能提升只能直接支持“这套系统在该评测条件下更好”，不能支持“提升完全来自 MLA”或“速度提升完全来自 MoE”。后一个判断需要 matched ablation：固定数据、token、训练步数、硬件、评测和 serving workload，只替换一个主要因素。

当官方没有公开消融时，比较记录应明确写出因果等级：

| 结论 | 证据最低要求 |
| --- | --- |
| 接口或配置事实 | 官方文档、配置或代码 |
| 该版本在某任务上更好 | 固定条件的复现实验或可信报告 |
| 某模块导致提升 | matched ablation 或足够强的替代解释排除 |
| 内部未公开实现 | 官方明确披露，否则只能标 unknown |

这条规则看似保守，却能防止把模型名字、社区逆向和营销叙述当成架构知识。它也能指导面试回答：先说公开事实，再说条件观察，最后说明不能从现有证据推出什么。

## 59.31 比较结果要能指导迁移和回滚

真正的模型选型不是写完排名表就结束，还要回答迁移成本：tokenizer 和 chat template 是否兼容，工具 schema 是否变化，长上下文位置语义是否一致，KV/state 是否能复用，量化和 kernel 是否支持，失败时能否回退到旧模型。一个质量略高但迁移要重写全部协议的模型，可能不如质量相近且可平滑灰度的模型。

因此 release record 还应保存 shadow traffic、分桶质量、结构化错误、引用支持、TTFT/TPOT、p99、GPU 小时、缓存命中、fallback rate、回滚时间和事故样本。灰度期间同时运行旧模型和候选模型，比较同一 request 的差异；候选模型出现安全或协议硬失败时立即回退，而不是等待平均分在周报中体现。

## 59.32 小结

横向比较模型时，最有用的结果不是一个脱离条件的排名，而是一张绑定版本、任务、资源、协议和证据等级的账本。架构创新可能成为通用能力、专用路径或 runtime 优化，选型要看自己的 SLO、失败类型和迁移成本。
