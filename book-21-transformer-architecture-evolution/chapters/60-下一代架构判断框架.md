# 第 60 章 从时间线看下一代架构：如何判断新模型到底新在哪里

## 60.1 遇到新模型先不要背缩写

前沿模型发布时常伴随新名称：新的 attention、位置机制、专家路由、缓存、推理模式或 agent 能力。最容易犯的错误是把缩写当知识点，把产品页面的一句话扩展成完整算法。

更可靠的做法是先问：它解决了哪一个瓶颈，改变了哪条信息流，带来了什么新的资源成本，有什么公开证据，在哪些任务上验证过。只有这五个问题回答清楚，名字才有学习价值。

## 60.2 第一步：确定问题边界

一个新设计可能主要解决：

1. 训练 FLOPs 或训练稳定性。
2. prefill 的二次 attention。
3. decode 的 KV cache 和带宽。
4. 长上下文位置外推。
5. 总参数容量与 active 计算。
6. 流式状态和低延迟。
7. 多模态 token 预算。
8. reasoning 的 test-time compute。
9. 工具、记忆和长期任务。

如果一个技术声称同时解决所有问题，反而需要更谨慎地查证。模块往往在一个目标上有收益，在另一个目标上引入代价。

## 60.3 第二步：画信息流图

至少画出 token 从输入到输出的路径：

~~~text
input
  -> tokenizer or modality encoder
  -> local / global / recurrent / latent representation
  -> attention or router
  -> FFN or experts
  -> cache or state update
  -> logits / tool action / verifier
~~~

对每个箭头标注：是否可并行、是否保存历史、是否有压缩、是否跨设备通信、是否可回滚。信息流图比“这是新 attention”更能解释系统行为。

## 60.4 第三步：建立资源账本

分别计算权重、激活、历史状态、通信、临时 buffer 和工具成本：

~~~math
C_{\mathrm{system}}
=C_{\mathrm{weight}}
+C_{\mathrm{activation}}
+C_{\mathrm{history}}
+C_{\mathrm{communication}}
+C_{\mathrm{runtime}}
~~~

~~~math
M_{\mathrm{system}}
=M_{\mathrm{weight}}
+M_{\mathrm{KV/state}}
+M_{\mathrm{workspace}}
+M_{\mathrm{metadata}}
~~~

理论复杂度只描述一部分。真正上线还要测 GPU 利用率、memory traffic、kernel launch、通信等待、排队和 p99。

## 60.5 第四步：分清训练收益和推理收益

有些方法主要优化训练，如并行化、辅助预测目标和数据配比；有些方法主要优化推理，如 KV 压缩、speculative decoding 和量化；有些方法同时影响两端，如 MoE 和混合状态架构。

训练收益不能直接等同于线上收益。一个新的训练目标可能让 loss 降低，却增加模型输出长度；一个 cache 压缩机制可能节省显存，却增加投影计算和精确引用错误。

评估表应分别列：

~~~text
training_loss
training_tokens_per_second
training_memory
prefill_tokens_per_second
decode_tokens_per_second
ttft
tpot
peak_memory
task_success
~~~

## 60.6 第五步：识别信息瓶颈

任何把历史压缩成 latent、summary 或 state 的方法，都要问它删除了什么。不同任务对信息的要求不同：

| 任务 | 更关心的保真信息 |
| --- | --- |
| 主题摘要 | 主要事件和主题 |
| 精确问答 | 数字、实体、限定词 |
| 代码修改 | 标识符、依赖、版本、上下文 |
| 审计 | 来源、时间、冲突、否定 |
| 流式分类 | 局部模式和累计状态 |
| 工具调用 | 参数、权限、顺序、结果 |

平均 loss 或 embedding 相似度不能覆盖所有高价值字段。新架构必须用任务分桶评估信息损失。

## 60.7 第六步：检查动态路由的系统代价

动态 gate、专家、全局路径和工具选择都可能让每个 token 走不同路径。理论上平均计算下降，但 batch 内分歧可能增加 padding、分支、通信和调度。

设第 t 个 token 的路径成本为 c_t，平均成本为：

~~~math
\bar c=\frac{1}{T}\sum_{t=1}^{T}c_t
~~~

服务体验还受尾部影响：

~~~math
\mathrm{p99}(C)\neq \bar c
~~~

少数触发全局路径的请求可能显著提高 p99。压测必须记录路径比例、每路径 token 数、kernel 时间和 batch 分裂。

## 60.8 第七步：验证训练—推理一致性

递归 state、位置扩展、MTP 和 speculative 都有训练与推理契约。检查：

1. 训练的 chunk 边界和线上 continuation 是否一致。
2. 训练的 position id 和 cache offset 是否一致。
3. rejected draft 是否回滚所有临时 state。
4. padding 是否更新了不该更新的 state。
5. batch 重排后 request owner 是否保持。
6. 模板、special token 和停止条件是否一致。

可以用 prefix continuation 对照：

~~~python
def compare_continuation(model, prefix, suffix):
    full = model(prefix + suffix)
    state = model.prefill(prefix)
    continued = model.decode_from_state(state, suffix)
    return full.logits, continued.logits
~~~

两条路径应在允许的数值误差内一致。否则先排查 runtime contract，而不是把所有差异归因于模型能力。

## 60.9 第八步：核对证据等级

对每个新术语建立证据卡：

~~~text
name
full_name_if_official
source_url
source_type
model_revision
public_formula
public_architecture
observed_behavior
unknown_details
confidence
~~~

source_type 可分原始论文、官方技术报告、模型卡、官方 API、第三方复现和社区推测。若 full_name、层表或 kernel 没有公开，就明确写未知，不要用相近概念补齐。

## 60.10 第九步：设计最小有区分度的实验

一个好实验不是尽可能复杂，而是能区分不同假设。比如判断一个模型是否真的使用长历史，可把证据放在首、中、尾，加入相似干扰和冲突版本；判断 cache 压缩是否损失细节，可专测数字、代码变量和引用；判断路由是否节省计算，可对比“计算后乘 gate”和“真正跳过 kernel”。

实验结果应保存：

~~~text
model revision
input construction
gold evidence
output
failure category
quality metric
latency metric
memory metric
tool or cache trace
~~~

## 60.11 第十步：用单位成功成本收束

最终架构选择要把质量和资源放到同一个指标上。可以定义：

~~~math
C_{\mathrm{unit\_success}}
=\frac{C_{\mathrm{compute}}
+C_{\mathrm{memory}}
+C_{\mathrm{tool}}
+C_{\mathrm{human\_review}}}
{\Pr(\mathrm{task\ success})}
~~~

对于高风险任务，还要加入失败损失：

~~~math
C_{\mathrm{risk\ adjusted}}
=\frac{C_{\mathrm{run}}+\lambda C_{\mathrm{failure}}}
{\Pr(\mathrm{accepted\ task})}
~~~

这解释了为什么一个更快但容易错过关键证据的模型，不一定更便宜；一个需要更多思考 token 但成功率高的模型，也可能在复杂任务上更划算。

## 60.12 “新架构”常见的五种包装

第一，把成熟模块重新命名。第二，把服务优化写成模型结构创新。第三，只报告 total parameters，不报告 active 和通信。第四，只展示最大 context，不报告有效检索和成本。第五，把模型、工具、检索和安全层的综合能力全部归功于 backbone。

识别包装不等于否定创新。它的意义是让读者知道哪些结论有证据，哪些需要自己复现。

## 60.13 一个架构决策表

| 问题 | 需要的证据 | 不能直接推断的内容 |
| --- | --- | --- |
| 是否降低 KV | cache bytes、decode 带宽、p99 | 质量一定不损失 |
| 是否支持长上下文 | 位置曲线、长训、检索任务 | 接口上限等于有效窗口 |
| 是否降低计算 | kernel 和端到端吞吐 | Big-O 等于 GPU 速度 |
| 是否增加容量 | active、total、专家负载 | 总参数等于每 token 成本 |
| 是否提升推理 | verifier、长度、成功率 | 思考越长越好 |
| 是否更安全 | 红队、权限、工具审计 | 模型拒答等于系统安全 |

## 60.14 对未来的谨慎判断

从公开技术路线看，下一代系统很可能继续组合多种机制：dense 或 MoE 的容量、MLA 或其他 cache 压缩、local/global/recursive 信息流、长上下文位置处理、retrieval、工具和 reasoning post-training。纯替代仍会出现，但能否成为主流取决于数据、kernel、通信、任务质量和供应链。

更重要的趋势是边界逐渐融合：模型架构影响 serving，serving 约束反过来影响训练；后训练改变输出长度，输出长度改变成本；工具和 verifier 改变任务定义，任务定义又改变模型选择。

## 60.15 一张新模型证据卡应该写什么

面对新模型，可以建立六栏证据卡：解决的问题，改变的信息流，新增资源成本，公开资料，已完成实验，未知和风险。每一栏都要绑定版本；模型名称或产品 slogan 不能代替证据。

例如，“支持超长上下文”要进一步记录 API 上限、训练长度、证据位置曲线、引用支持、TTFT、p99、KV/state bytes 和回退路径；“支持 reasoning”要记录思考预算、verifier、工具、输出长度和成功成本。

## 60.16 技术生命周期与架构判断

一个技术可能处于 emerging、生态扩张、接口标准化、被模型能力吸收或逐渐过渡几个阶段。MCP、skill、memory、tool calling、agent runtime 和外部 retrieval 的边界会随模型上下文、记忆和工具可靠性变化。

因此判断新技术时，除了问“现在是否流行”，还要问它解决的约束是否仍然存在。如果约束被模型或产品内置能力吸收，技术可能从核心架构降为实现细节；如果协议、权限和审计稳定下来，它可能上升为基础设施标准。

## 60.17 面试中的可迁移回答

一个稳健的回答顺序是：先说旧瓶颈，再说新机制，接着给出质量和资源 trade-off，最后说明公开证据和验证计划。例如面对新的 attention 变体，可以从历史访问、KV/state、精确引用、kernel、回滚和单位成本展开；面对新 agent 能力，可以从模型、工具、状态、权限、trace 和评估展开。

这样的回答既能让初学者理解技术为什么出现，也能让专家看到你没有把宣传语、内部猜测和实验证据混为一谈。

## 60.18 一份可执行的架构审计表

面对新模型或新模块，可以按以下顺序记录：问题定义、核心机制、计算复杂度、状态/cache、训练数据与目标、目标硬件、协议能力、评测任务、失败模式、回退路径、生命周期和证据来源。每一项都写“已知/推断/未知”，避免在资料缺口处补充想象。

## 60.19 从 claim 到实验

若 claim 是“长上下文更好”，就设计位置随机化、冲突证据、负例和引用测试；若 claim 是“推理更省”，就固定成功率比较 reasoning token、工具时间和单位成功成本；若 claim 是“架构更高效”，就测目标硬件上的 prefill/decode、p99、显存和 fallback。实验必须能区分候选解释。

## 60.20 面试中的成熟回答

回答下一代架构问题时，先说旧瓶颈，再说新机制改变哪条信息/计算路径，然后给出能力收益、资源代价和证据边界，最后说明什么 workload 下采用、什么条件下回退。不要只报模型名、参数量或榜单分数。

## 60.21 资料范围与判断条件

判断新架构不能依赖新闻摘要或模型名称。应先确定问题，再画信息流、算资源账本、找信息瓶颈、验证训练—推理一致性、分级证据并用端到端实验收束。

真正成熟的架构分析，允许结论保持条件化：某机制在某版本、某任务、某硬件和某 harness 下改善了某个指标，同时在另一个高价值任务上引入了什么代价。

## 60.22 面试问题与练习

**问：遇到一个声称支持百万上下文的新模型，第一步查什么？**

先查模型版本和官方上下文声明，再设计不同长度、证据位置、干扰和多证据任务，测有效 recall、引用、成本和 p99；不要只检查接口是否接受请求。

**问：如何判断一个新模块是模型创新还是 serving 优化？**

看它是否改变训练计算图、参数/状态表示和前向信息流；如果只改变 kernel、内存分配或调度，它可能是系统优化，但仍然有重要工程价值。

**练习：**选一个近期模型术语，制作证据卡并完成一页评估计划，明确已知、未知、实验变量和上线条件。

资料入口：

- Transformer: https://arxiv.org/abs/1706.03762
- FlashAttention-2: https://arxiv.org/abs/2307.08691
- Mamba: https://arxiv.org/abs/2312.00752
- DeepSeek-V2: https://arxiv.org/abs/2405.04434
- DeepSeek-R1: https://arxiv.org/abs/2501.12948

## 60.23 从新名词到研究计划

面对一个新模块，先写旧问题：是 KV 太大、prefill 太慢、长流状态不稳、精确检索失败、通信太贵，还是工具闭环不可靠。然后写机制改变了哪条信息路径和哪份资源账本，再列出能证伪它的任务、baseline、控制变量和失败判据。

一张合格的研究计划至少包括：假设、证据等级、模型/代码 revision、训练与推理预算、匹配的硬件、任务切片、质量指标、系统指标、安全门、回退路径和停止条件。若公开资料不能支持内部结构，就把它写成未知并设计行为实验，而不是用模型名称补全架构。

最终结论可以是“暂不采用”。如果新方法只在单一 benchmark 上领先，却在引用、协议、恢复或迁移成本上失败，保留它作为观察项比强行写成主干更诚实。架构判断的专业性，体现在知道何时下结论以及何时明确未知。

## 60.24 架构判断的阶段性结论

判断下一代架构的稳定方法是：先定义旧瓶颈，再画信息流和资源账本，区分模型创新与 serving 优化，设计能证伪的 matched experiment，并保留证据边界。成熟结论始终带着版本、任务、硬件和 harness 条件，而不是从新名词直接推导能力。

## 60.25 架构 claim 的最小证据卡

遇到一个新名词时，先把 claim 拆成五行：它改变了哪条信息路径、保存什么状态、减少哪种资源、增加哪种失败、在哪个任务被观察到。每行绑定来源、版本、实验条件和未知项。这样可以避免把“模型支持某接口”“论文提出某机制”和“线上因此更快”写成一个未经验证的句子。

## 60.26 从 toy 到 production 的升级阶梯

研究验证可以从 toy recurrence、固定 mask 或小模型开始，用于检查公式、信息路径和反事实；随后进入 matched model benchmark，检查质量和训练/推理一致性；最后才进入目标 GPU、变长 batch、cache、工具、权限、灰度和故障演练。每一级都需要自己的停止条件。

toy 结果不能直接证明生产收益，但它可以快速否定错误假设。生产压测也不能替代机制理解，因为它只能告诉你“这组配置下发生了什么”。两者结合，才能区分结构缺陷、实现缺陷和 workload 不匹配。

## 60.27 何时保留未知而不是补全故事

闭源模型、未公开权重或产品新版本往往只披露接口和少数性能数字。此时可以写已观察的字段、输入输出行为和发布条件；对内部层表、训练配方、kernel、数据和 reward 只能写未知或待核验。未知不是章节的空白，而是证据边界的一部分。

一个成熟的架构判断可以得出三种结论：采用、在受限 workload 试用、暂不采用。第三种结论同样有价值，尤其当质量/恢复/治理未通过验收时，避免把新名词变成无条件推荐。
