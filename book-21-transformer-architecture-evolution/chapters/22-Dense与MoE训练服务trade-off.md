# 第 22 章 Dense 与 MoE：训练、服务和成本的完整取舍

## 22.1 Dense 与 MoE 的资源账本分别回答什么

看到一个 MoE 模型的参数数字时，先问它统计的是哪种资源。Dense FFN 对每个 token 使用同一条参数路径；MoE 只让 token 经过所选 expert 的 FFN，但整层仍拥有全部 routed experts。于是，总参数、每 token 激活参数、当前设备持有的权重，以及完整训练或服务的实际耗时，回答的是不同问题。

| 口径 | 可以回答 | 单独不能推出 |
| --- | --- | --- |
| 总参数 | 模型包含多少可训练权重；权重文件和完整模型状态的大致规模 | 每个 token 的计算量、单卡显存或生成速度 |
| 每 token 激活参数 | 某种配置下一个 token 经过的主要参数路径规模 | 完整 FLOPs、kernel 利用率、跨卡传输量或端到端延迟 |
| 权重驻留 | 某个时刻哪些权重放在某类设备的高速内存中 | 模型全体权重是否已经从系统中消失；分片、缓存和 offload 会改变位置而不改变总参数 |
| 实测训练/服务时间 | 指定版本、硬件、精度、负载和软件下完成任务的时间 | 其他拓扑、batch、质量目标或服务栈下会有同样结果 |

因此，“MoE 只激活少量参数”可以解释它为何有机会以较少 expert 矩阵计算容纳更大的参数容量，却不是“它只需要少量权重内存”或“它一定更快”的同义句。权重精度、expert 是否分片或复制、KV cache、通信和执行负载都会改变真实资源需求。总参数与 active 参数的计算口径见[第五册第四章](../../book-05-llm-training/chapters/04-模型架构与初始化.md)，MoE 的 token 路由定义见[第二十一章](21-MoE路线Switch-GShard-Mixtral-DeepSeek.md)。

## 22.2 训练：稀疏计算必须放回每次更新

MoE 层的 expert 矩阵乘只处理被路由到该 expert 的 token；但训练时间不是把总参数简单乘以一个 active 比例就能得到。router 与数据重排本身需要工作；capacity padding 会让一部分计算落在空槽上，token dropping 则会改变哪些输入得到 expert 计算；expert 接收量不均会让部分设备等待最忙的 expert。实现方式和 batch 形状还会影响矩阵计算是否能充分利用 GPU。

稀疏前向也没有删除模型中未被当前 token 选中的参数。分布式训练可以把参数和优化器状态分片到多卡，但系统仍要表示整套专家权重、更新状态并保存可恢复的 checkpoint。单个 step 里未被选中的 expert 可能没有来自该批 token 的梯度，这不等于它的模型状态无需占据容量。

两个研究案例显示，系统实现会改变稀疏计算的实际账本。MegaBlocks 把动态 expert 计算改写为 block-sparse 操作；作者在 8 张 A100、64 个 top-1 expert 的中小型语言模型实验中，报告了相同验证损失下相对 dense Megatron-LM 的端到端训练速度结果。这个结果支持“特定稀疏计算实现可以在特定训练设定里胜过 dense baseline”，不能外推为任意大模型都更快。[MegaBlocks §6.1](https://arxiv.org/html/2211.15841)

DeepSeek-V3 报告给出另一种账本：671B 总参数、每 token 激活 37B，并报告官方预训练、上下文扩展和后训练合计使用 2.788M H800 GPU 小时。作者同时说明这笔总成本不包括更早的架构、算法或数据研究与消融；该训练结合了模型设计、FP8、分布式框架和硬件优化，也没有提供一个同质量、同数据、同硬件的 dense 对照。因此，这组数字说明完整系统共设计可以实现高效训练，不能单独证明 MoE 相比 Dense 的普遍成本优势。[DeepSeek-V3 Technical Report](https://arxiv.org/html/2412.19437v2)

## 22.3 训练通信：拓扑与重叠改变暴露等待

MoE expert 放在哪些设备上，会影响路由 token 走高速本地互联还是跨节点网络。第五册第七章已经说明 expert parallel 的 all-to-all 怎样分发和返回 token；这里关注它对训练比较的影响：通信总量、通信在关键路径上暴露多久，以及能否与其他计算重叠，是三个不同量。

如果 expert 都能放在本地高速互联域，通信等待可能较容易控制；若 expert parallel 跨节点，链路带宽、路由偏斜和同步等待就会直接影响 step time。增加并行设备可以分摊每卡的 expert 状态，也可能扩大通信域。重叠可以把一部分传输藏在独立计算之后，却不会让传过网络的数据字节自动消失；它还依赖可并行的工作、buffer 和 schedule。

Megatron-Core 的技术报告用 DeepSeek-V3 的 EP64/H100 训练配置举例：优化 dispatcher 后，作者仍报告 expert 通信暴露约占迭代时间的 30%—40%；再使用跨 micro-batch 的 forward/backward 通信重叠和梯度拆分后，该设置中报告的暴露比例降至 5% 以下。这是实现和设备条件固定的系统测量，描述的是通信等待暴露在迭代关键路径中的比例，不是通信字节减少比例，也不是任意 MoE 集群都能得到的端到端加速率。[Megatron-Core Technical Report §§4.2.2–4.2.3](https://arxiv.org/html/2603.07685v2)

比较训练路线时，不能只看 active 参数或总 FLOPs。至少要确认比较的是同一个目标质量、同一训练数据和 token 数、相近精度、明确的集群拓扑，以及同一计时范围；还要知道结果是否包含 checkpoint、评估、失败重跑和系统初始化。某项优化可能先减轻通信等待，随后暴露小矩阵效率或显存压力，因而系统方案必须作为整体解释。

## 22.4 服务：prefill 和 decode 暴露不同瓶颈

Prefill 一次处理 prompt 中的一批 token；decode 则按自回归依赖逐步生成 token。两阶段产生的 expert batch 不同：大量输入 token 可能让同一 expert 在一个批次中处理多行，而逐步 decode 中每条序列每步只新增少量 token。并发请求会改变总批量，但也会改变每步访问哪些专家、延迟和显存占用，所以训练时的 batch 结果不能直接预测线上服务表现。

若所有 expert 都常驻 GPU，MoE 仍要为完整权重集合安排设备内存，虽然单个 token 只使用其中一部分；若部分 expert 放在 CPU 或其他存储层，驻留量可能下降，但权重搬运会进入执行路径。DuoServe 的单 GPU offload 研究分别处理 prefill 的多 token expert batch 与 decode 的逐步专家访问，说明同一种缓存/预取策略可能同时遇到 prefill 峰值显存和 decode 传输尾延迟问题。它的实验范围是论文所测的模型、A5000 和服务负载，不能直接代表多机常驻推理。[DuoServe-MoE §§V–VI](https://arxiv.org/html/2509.07379v2)

即使权重都已驻留，路由和设备映射仍会影响 decode。METRO 研究在其 Qwen3、DeepSeek-V3、vLLM 8×A100 实机及 8—16×B200 模拟实验中发现，memory-bound decode 下按 GPU 平衡 token 数不一定能平衡被激活的 expert 权重；减少每卡需要访问的 expert 副本数，在该研究设定里改善了延迟和吞吐。这个结论提醒我们负载指标必须对应当前瓶颈，不能从训练侧的 token 均衡目标直接推出服务侧最优路由。[METRO §§III、VI](https://arxiv.org/html/2512.09277v1)

KV cache 另由 attention 的层数、KV heads、表示方式、缓存精度和序列长度决定。MoE FFN 稀疏不会自动缩小 KV；DeepSeek-V3 同时使用 MLA 与 MoE 时，MLA 和 expert 路由改变的是不同账本。[KV Cache](11-kv-cache长上下文推理和显存增长问题.md) 与 [Dense/MoE 结构分工](21-MoE路线Switch-GShard-Mixtral-DeepSeek.md)分别讨论这些机制。

## 22.5 对比结果要先对齐问题和分母

Dense 与 MoE 的比较至少有两种不同问题：在同一训练预算下，哪种模型达到更好的质量；以及达到同一质量目标时，哪种模型消耗更少的时间和资源。服务又增加一类问题：在任务质量相当时，哪种部署能在目标延迟和并发条件下处理更多有效请求。三类问题使用的分母和结果不能混成一个“效率”数字。

| 比较问题 | 关键共同条件 | 主要结果 |
| --- | --- | --- |
| 固定训练预算比质量 | 数据分布、训练 token、总训练时间或 GPU 小时、精度、模型版本、评估集 | 质量和损失差异，以及产生差异所用的训练资源 |
| 固定质量目标比训练成本 | 相同或明确对齐的目标质量、数据与评估口径、硬件与计时范围 | 达到目标所需的有效训练时长、设备资源和内存 |
| 固定服务目标比部署效率 | checkpoint、量化、runtime、设备互联、输入/输出长度、并发、请求质量要求和延迟 SLO | 可用吞吐、延迟分布、内存需求及对应部署资源 |

报告数字要按它自己的控制条件解释。MegaBlocks 的同验证损失结果来自中小型模型和 A100 实验；DeepSeek-V3 的训练 GPU 小时是作者报告的完整模型训练账目，但没有与 dense baseline 做 matched comparison；METRO 的 serving 结果回答特定 MoE 路由与 expert 副本映射问题。把这些数字并排相除，无法隔离模型结构、训练 recipe、kernel、硬件或 workload 的作用。

如果论文只报告 active 参数相近，仍需看总权重、训练时间、质量与路由实现；如果报告每秒 token，还要看它统计的是 prefill、decode 还是二者合计，输入输出长度和延迟目标是什么。一个有效比较不一定需要在所有维度都相同，但凡条件不同，就要把差异写进结论并降低归因范围。

## 22.6 选 Dense 还是 MoE 取决于当前约束

Dense 的固定路径使参数驻留、batch 组织和通信布局较直接。若目标模型能够在现有设备上高效运行、请求批量不大或低延迟比额外容量更重要，Dense 可能更合适；但它并不自动解决权重带宽、KV cache、长上下文或并发问题。

MoE 的吸引力在于条件容量：当更多专家确实能提高目标任务质量，而每 token 的计算预算有限时，稀疏路径提供了一种扩展空间。要兑现这一点，训练和服务系统还需能容纳全体专家权重，并让路由、expert batch、通信与目标 SLO 协调工作。容量增长如果没有质量收益，或通信和权重驻留压过计算节省，就可能不划算。

所以选择不是“Dense 便宜”或“MoE 高效”二选一。先明确正在比较训练质量、训练时长、设备容量还是服务时延；再用与目标任务、数据、硬件和并发相符的证据判断。只有这个具体问题得到回答，active 参数、GPU 小时和每秒 token 才有可解释的含义。
