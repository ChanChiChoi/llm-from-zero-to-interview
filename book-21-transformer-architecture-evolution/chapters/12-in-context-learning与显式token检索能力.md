# 第十二章：In-Context Learning 与显式 token 检索能力

## 12.1 从一个临时映射理解 ICL

给模型下面的输入：

```text
任务：照示例续写对应代号。

dax → vep
zim → nor
dax →
```

若模型输出 `vep`，它需要把当前的 `dax` 和前文的对应关系联系起来。这个映射可以只在当前输入里给出；模型进行这次预测时不必更新参数。

In-Context Learning（ICL，上下文学习）指模型在固定参数下，根据 prompt 中的任务说明、示例或证据形成当前输出。它的条件分布可以写成：

```math
P_\theta(y\mid x,\mathcal{C})
```

公式中的 $x,\mathcal{C},\theta$ 依次表示当前输入、按顺序排列的上下文和固定模型参数；本次推理不更新参数。Brown 等人用 GPT-3 展示了不做梯度更新、只通过文本给出任务和示例的 zero-shot、one-shot 与 few-shot 评测；结果因任务而异，也没有识别模型内部究竟怎样完成适配。[论文](https://arxiv.org/abs/2005.14165)

这里的“新映射”是给读者看的教学设定。称一个任务为 few-shot，并不自动证明它在预训练数据中从未出现过；大规模训练语料和 benchmark 的重叠通常难以彻底排除。[Stanford CS224U 讲义](https://web.stanford.edu/class/cs224u/slides/cs224u-incontextlearning-2023-handout.pdf)也提醒，严格定义中的“训练时未见过”往往无法由使用者验证。

## 12.2 上下文条件化与参数更新

Zero-shot、one-shot 和 few-shot 的区别，是任务输入中是否给出示例以及示例数量；fine-tuning 则改变模型参数。二者的计算对象不同：

| 用法 | 当前任务信息放在哪里 | 本次处理后留下什么 |
| --- | --- | --- |
| Zero/one/few-shot ICL | 指令和可选示例组成的上下文 | 参数不因这次推理更新；上下文随请求提供 |
| Fine-tuning | 训练样本与损失函数 | 经过优化的参数写入新的 checkpoint |

ICL 省去这次任务的反向传播和参数更新，但输入示例会占用上下文 token，并增加本次计算与延迟；Stanford CME295 2025 秋季课程也把这些成本列为 ICL 的取舍。[课程讲义](https://cme295.stanford.edu/slides/fall25-cme295-lecture3.pdf) 它不是“没有代价的微调”，也不能保证模型学会任意复杂的新技能。Zero-shot 也不代表没有任务信息：自然语言指令、输出格式和约束仍可写在 prompt 中。

## 12.3 示例不只提供正确标签

Few-shot 示例可能同时传递输入的样子、候选标签、字段格式以及输入和输出之间的映射。Min 等人在多个分类和多选任务及所测模型设置中发现，随机替换示例标签后，表现有时只小幅下降；他们指出，输入文本分布、标签空间和序列格式也能解释部分结果。[论文](https://arxiv.org/abs/2202.12837)

这项结果不能读成“标签不重要”。它限定于论文所测任务和提示；如果任务要求模型使用上下文才知道的任意映射，例如 `dax → vep`，映射本身就是答案所需的信息。更稳妥的判断是：示例包含多种信号，不同任务对这些信号的依赖不同。检验某个模型是否利用了映射，可以保持其他内容不变，只替换该映射，再观察对应输出是否随之改变；这个行为结果说明本次回答依赖了输入变化，但不能单独确定内部机制。

## 12.4 Prompt 设计、ICL 与 RAG

Prompt engineering 是组织指令、示例、输入和输出约束的实践；ICL 描述固定参数模型如何在这段上下文条件下作答。好的输入格式可以让示例关系更容易辨认，但格式本身不保证预测正确。

RAG（检索增强生成）还包含上下文之外的检索步骤：系统从语料库或索引中选出候选文档，再将文档交给生成模型。经典 RAG 论文把参数化生成器与外部非参数化文档索引、检索器组合起来；不同产品可能采用不同训练和运行架构。[Lewis 等人的论文](https://arxiv.org/abs/2005.11401)

因此，检索器是否找对文档，与生成模型是否读对、绑定并使用文档证据，是两个需要分别检查的问题。RAG 可以把检索结果放入模型的输入上下文，但 RAG 系统本身不等于 ICL；前者涵盖外部数据检索和系统连接，后者关注模型对当前上下文的条件化行为。

## 12.5 从可见 token 到可用信息

在标准 full-attention 层中，只要因果或稀疏 mask 允许，当前位置就能根据 query 与历史 key 的相似度，对可见 value 做加权汇总。单个 attention head 可简写为：

```math
a_{qj}=\frac{\exp(q^\top k_j/\sqrt{d_h})}{\sum_{r\in\mathcal{V}_q}\exp(q^\top k_r/\sqrt{d_h})},\qquad
z_q=\sum_{j\in\mathcal{V}_q}a_{qj}v_j
```

公式中的 $q,k_j,v_j,\mathcal{V}_q$ 分别表示当前 query、各上下文位置的 key/value，以及该 query 按 mask 可见的位置集合； $d_h$ 是该 head 中 query/key 的维度； $(a_{qj},z_q)$ 依次表示各可见位置的归一化权重和对应的加权 value 输出。式中省略了位置机制加入分数的项。这个计算给出了上下文信息进入当前位置的一条路径；它不保证模型会选中正确证据，也不保证后续层会正确保留实体、条件和证据之间的关系。attention 权重或一张注意力图不能单独证明模型正确使用了某个 token，也不能自动视为忠实的输出解释。Jain 与 Wallace 在所测 NLP 任务中发现，不同 attention 分布可能对应相同预测；Wiegreffe 与 Pinter 则指出，对 attention 是否构成解释的判断取决于解释定义和评估方法。这些研究不能概括所有 Transformer 机制，但支持对单独的 attention 图保持谨慎。[Attention Is All You Need](https://arxiv.org/abs/1706.03762)、[Jain 与 Wallace（NAACL 2019）](https://aclanthology.org/N19-1357/)、[Wiegreffe 与 Pinter（EMNLP-IJCNLP 2019）](https://aclanthology.org/D19-1002/)

本章把“显式 token 检索能力”作为一个操作性说法：相关信息已经出现在输入中时，模型能否定位它，并在回答中正确使用其内容及限定条件。它指上下文内部的信息读取，不是外部向量数据库的检索。可以用受控反事实检查这一行为：固定模板、查询和其他示例，只改变目标映射或证据；再检查输出是否随证据正确变化。通过一个合成查找题，只能说明模型在该任务条件下成功，不能推出任意长文档推理都可靠。

## 12.6 ICL 的几种解释及其证据范围

ICL 仍没有一个已被证实适用于所有模型和任务的单一机制。几类研究提供了不同的解释角度：

| 解释视角 | 能说明什么 | 证据范围 |
| --- | --- | --- |
| Induction head（归纳头） | 若前文出现 `[A][B]`，后文再次出现 `A` 时，某些电路会把 `B` 作为后续预测线索 | Olsson 等人在两层 attention-only 模型中分析了这种 pattern-copying 电路；他们对大型模型中它能否解释大部分 ICL 明确称为初步、间接证据支持的假说。[研究文章](https://transformer-circuits.pub/2022/in-context-learning-and-induction-heads/index.html) |
| 潜在任务推断 | 示例可能共同提示一个模型从上下文中推断的规则或概念 | Xie 等人的理论结果基于 HMM 混合等受控假设，并用合成数据展示现象；它不是自然语料大模型内部过程的通用证明。[论文](https://arxiv.org/abs/2111.02080) |
| 算法模拟或隐式优化 | 前向计算可能形成临时预测器，行为上接近某种学习算法 | Akyürek 等人在受控线性回归任务中构造并训练 Transformer，使其预测接近梯度下降、ridge 或最小二乘解。[ICLR 2023 论文](https://arxiv.org/abs/2211.15661) Shen 等人在预训练模型和所测任务中发现，ICL 与梯度下降的顺序敏感性及输出变化并不一致；二者是否等价仍是开放问题。[ICML 2024 论文](https://proceedings.mlr.press/v235/shen24d.html) |

这些解释可以帮助形成假说，但不能把“ICL 就是 induction head”或“ICL 就是梯度下降”当成已经确立的结论。区分行为描述与机制证据，才能避免把一个小模型或合成回归任务的结果扩大到所有预训练语言模型。

## 12.7 示例顺序与长上下文位置

即使示例内容相同，排列顺序改变也可能改变模型输出。Lu 等人在其 few-shot 任务中发现，示例排列的表现差异可能很大，而且一个模型上表现好的排列不一定适用于另一个模型或任务。[论文](https://aclanthology.org/2022.acl-long.556/) 因此，比较 prompt 时应把顺序当作一个实验变量；不能仅凭单次成功就断言“最新示例总是最重要”或“把最相关示例放到最后总会更好”。

上下文长度带来另一类位置问题。Lost in the Middle 在其多文档问答与键值检索实验中报告，所测模型对开头、中间和末尾证据的利用可能不同；这说明可见性和有效使用不是一回事，但不是所有任务、模型和版本都会出现相同的位置曲线。[研究范围与边界见第十三章](13-长距离依赖与lost-in-the-middle.md)。

## 12.8 把上下文检索作为架构评测任务

读者比较 Transformer 与状态型或混合序列架构时，可以用复制、变量绑定和依据示例完成映射等任务，检查它们如何利用输入中的历史信息。标准 full attention 在允许的位置间建立直接的 query-key 路径；递归或状态空间路线则通过状态更新传递历史。两种信息路径各有成本和表达条件，结构本身不等于实测能力。

比较时固定任务、输入和输出格式、示例内容与顺序、上下文长度和评测协议；模型规模、训练数据与计算预算尽量对齐，无法对齐时明确报告差异。把短程复制、长上下文证据利用与多证据推理分开报告。ICL 是有用的一类 workload，不是单独决定架构优劣的总分。归纳偏置与状态记忆见[第十四章](14-Transformer归纳偏置与状态记忆.md)，替代架构的跨路线比较见[第四十二章](42-替代架构横向对比.md)。

## 12.9 小结

ICL 是固定参数模型利用当前 prompt 作答的行为。上下文示例可以同时提供任务格式、输入分布、候选标签和输入输出关系；attention 为读取可见 token 提供信息路径，但不能保证证据被正确使用。归纳头、潜在任务推断和算法模拟都解释了部分现象，证据范围各不相同。示例顺序与证据位置需要按任务测量；RAG 的外部检索和模型内部使用上下文也应分别判断。
