# 第 50 章 未来大模型架构会如何演进：从单一网络到可组合系统

## 50.1 “下一代架构”到底在回答什么问题

当人们说 Transformer 会不会被替代时，往往把三个不同问题混在一起。第一个问题是训练时能否高效并行；第二个问题是推理时能否低成本保存和访问历史；第三个问题是系统能否在工具、记忆、多模态和安全约束下完成长期任务。

Attention、SSM、卷积、MoE、latent cache 和 retrieval 分别解决这些问题的不同部分。一个模块在理论复杂度上更优，不等于它在 GPU、数据、任务质量和服务尾延迟上更优。因此未来架构判断需要从“单个 block 的宣传”升级为“完整信息流和资源闭环”。

## 50.2 用信息流而不是模型名字比较

对一个序列模型，先问历史信息经过什么路径到达当前输出。可以用三类路径描述：

1. 显式路径：当前 query 直接访问历史 token 的表示。
2. 压缩路径：历史先被映射为 latent、摘要或固定 state。
3. 外部路径：模型通过 retrieval 或工具重新获取原始信息。

设三条路径输出分别为 y_e、y_c 和 y_r，一个混合输出可以写成：

~~~math
y_t=\alpha_t y_t^{\mathrm{explicit}}
 +\beta_t y_t^{\mathrm{compressed}}
 +\gamma_t y_t^{\mathrm{retrieved}},
\qquad
\alpha_t+\beta_t+\gamma_t=1
~~~

这只是抽象框架。真正重要的是每条路径何时可用、是否能保留来源、成本如何变化，以及失败后是否有 fallback。

## 50.3 Attention 为什么仍然有生命力

标准 attention 的独特能力是 query-time 的任意对齐。当前 token 可以根据任务临时决定读取哪一段历史，而不必在历史到来时提前知道未来问题。这种能力对代码变量追踪、跨段引用、冲突事实和工具参数尤其重要。

它的代价也很清楚：prefill 中存在大规模 token 交互，decode 中需要保存历史 K/V，长序列会增加带宽和调度压力。FlashAttention 主要减少中间矩阵的读写，PagedAttention 改善 KV 内存管理，GQA/MLA 压缩 cache，它们都说明标准 attention 可以通过系统和表示改造继续延伸。

## 50.4 SSM、线性 attention 和递归状态的机会

SSM 和线性 attention 将历史变成可递归更新的状态，理想情况下把序列处理从二次访问降为线性更新。它们适合局部连续、流式输入、长日志扫描和固定状态预测。

抽象状态更新为：

~~~math
s_t=F(s_{t-1},x_t),\qquad y_t=G(s_t,x_t)
~~~

其关键代价是状态是有损瓶颈。未来 query 不能一定恢复所有历史 token；如果需要精确引用，就必须保留额外的显式或外部路径。真正有潜力的方向不是笼统地说“SSM 替代 attention”，而是让不同层、不同 token 或不同请求采用不同信息通路。

## 50.5 混合架构的三种组织方式

第一种是按层混合。多数层使用 local、SSM 或线性路径，少数层保留 global attention。它容易解释和部署，但 global 层仍可能成为长上下文瓶颈。

第二种是按 token 或 query 动态路由。普通 token 使用便宜路径，难例或证据 token 触发显式 attention。它能节省平均成本，却可能造成动态分支、batch 分裂和 p99 抖动。

第三种是按任务路由。流式分类、摘要、精确代码修改和审计任务使用不同的模型或路径。这种做法系统收益更明确，但需要任务分类、能力边界和回退策略。

路由可以写成：

~~~math
p_t=\mathrm{Router}(h_t,\mathrm{task},\mathrm{budget}),
\qquad
y_t=f_{p_t}(h_t)
~~~

路由错误会把任务送进不适合的记忆路径，所以路由评估不能只看平均吞吐。

## 50.6 MoE 解决的是容量与激活计算的分离

稀疏 MoE 让每个 token 只激活少数专家，从而增加总参数容量而不让每个 token 都执行全部 FFN。设有 E 个专家，每个 token 选择 k 个：

~~~math
y_t=\sum_{e\in\mathcal{T}(x_t)}g_{t,e}f_e(x_t),
\qquad |\mathcal{T}(x_t)|=k\ll E
~~~

MoE 的瓶颈从矩阵乘扩展到路由、容量因子、token dispatch、跨卡 all-to-all、负载均衡和专家热点。它不等于“免费增加参数”，也不等于每个任务都会得到更强能力。

未来架构可能把 MoE 用在 FFN、记忆模块、工具策略或多模态专家上，但路由稳定性和通信成本会决定它的实际收益。

## 50.7 长上下文的四个层次

第一层是接口长度，表示 runtime 接受多少 token。第二层是位置机制，表示模型能否编码较远位置。第三层是有效检索，表示能否找到指定证据。第四层是长程推理和成本，表示能否整合多证据并满足服务 SLO。

长度支持不能用一个数字概括。可以定义有效能力曲线：

~~~math
Q(L,p,d)=
\mathrm{TaskSuccess}(L,\mathrm{position}=p,\mathrm{distractor}=d)
~~~

对不同 L、证据位置 p 和干扰强度 d 测量，才能知道模型的有效窗口。未来的位置研究会更多和数据配比、检索路径、cache 压缩、上下文并行以及任务路由一起设计。

## 50.8 外部记忆和 retrieval 不会被纯架构消灭

即使模型上下文变得很长，外部知识仍有三个理由存在：知识需要更新，原文需要可追溯，存储和访问成本不应全部由模型上下文承担。

检索系统可把原始文档保存在外部，把候选片段和来源送入模型。一个混合目标可以写成：

~~~math
\hat y=\mathrm{LM}\bigl(x,\mathrm{Retrieve}(x,\mathcal{D})\bigr)
~~~

其中 D 是外部数据。检索错误、时间过期、权限泄漏和引用错位仍然需要独立治理。长上下文和 retrieval 是互补关系，而非简单替代。

## 50.9 多模态会推动模块化而不是完全统一

文本、图像、音频和视频的冗余结构不同。统一 token 序列有利于跨模态组合，但会导致 token 预算和位置处理复杂；模态专用 encoder 或卷积/SSM 能够先消化局部冗余，再把关键表示交给共享语言 backbone。

对于视频问答，系统可能同时需要空间 patch、时间状态、关键帧 retrieval 和文本 global attention。未来架构的评价单位会从“参数量和单模态 benchmark”转向模态 token 预算、时间定位、来源回放和端到端延迟。

## 50.10 训练方法也是架构的一部分

同一个 block 在不同数据、长度和后训练 recipe 下可能表现完全不同。长上下文没有长样本训练，MoE 没有均衡路由和通信优化，reasoning 模型没有可验证奖励，多模态模型没有跨模态对齐，结构优势都不能落地。

因此架构实验至少控制：

| 维度 | 需要固定或报告的因素 |
| --- | --- |
| 模型 | 参数量、层数、hidden size、激活参数 |
| 数据 | token 数、质量、语言/模态配比、重复率 |
| 训练 | optimizer、学习率、上下文长度、batch、seed |
| 后训练 | SFT、偏好优化、RL、工具/环境数据 |
| 推理 | dtype、kernel、batch、cache、采样参数 |
| 评估 | 长度、位置、干扰、任务成功、成本 |

没有这些控制，架构之间的胜负很可能只是训练预算或系统实现差异。

## 50.11 如何建立未来架构的判断框架

可以用五个问题审查任何新路线。

第一，它替代了 attention 的哪一部分：二次计算、KV 存储、任意检索，还是只是某个 kernel。第二，它把信息保存在哪里：完整 token、latent、递归 state、外部数据库，还是多条路径。第三，它在训练和推理上是否使用同一信息流。第四，硬件是否有成熟 kernel 和通信方案。第五，质量下降是否集中在某些高价值任务。

一个粗略的综合分数可以写成：

~~~math
S_{\mathrm{arch}}
=w_qQ-w_cC-w_mM-w_lL-w_rR
~~~

其中 Q 是质量，C 是计算，M 是内存，L 是延迟，R 是风险。权重取决于场景；实时语音和离线训练不会使用同一个权重。

## 50.12 最小比较实验

可以用一个教学任务比较显式 attention、递归 state 和 retrieval：

~~~python
def evaluate(path, examples):
    rows = []
    for item in examples:
        answer, trace = path(item)
        rows.append({
            "correct": answer == item["gold"],
            "evidence": item["evidence"] in trace.get("evidence", []),
            "latency_ms": trace["latency_ms"],
            "memory_bytes": trace["memory_bytes"],
        })
    return rows
~~~

样本应包括局部复制、远距离数字、多个冲突版本、长日志分类和需要引用来源的问答。只测平均语言模型 loss，会漏掉压缩路径在精确证据上的损失。

## 50.13 未来更可能是可组合架构

从工程约束看，未来的主流系统更可能由多条路径组成：attention 提供精确动态对齐，SSM/线性路径处理连续长流，MoE 提供容量分配，MLA 或 latent cache 降低状态，retrieval 保留外部事实，工具和 verifier 处理环境交互。

这不是说所有模型都会采用相同组合。真正的竞争点会从“谁发明一个完全不同的 block”扩展到：谁能在相同质量验收条件下，把训练、kernel、通信、状态生命周期和产品工作流一起做好。

## 50.14 用约束判断下一代架构

面对一个新模块，先问它解决的是哪一种瓶颈：训练 FLOPs、decode 带宽、KV/cache、长程寻址、模态 token、工具闭环、数据效率还是安全验证。再问它把成本移到了哪里：更多状态、更复杂 kernel、更多通信、更多训练数据、更多评估或更难的回滚。

可以用一个约束表：

| 约束 | 需要测的量 | 典型补偿 |
| --- | --- | --- |
| 长上下文 | recall、引用、KV、p99 | RAG、压缩、hybrid |
| decode 成本 | TPOT、带宽、acceptance | GQA、speculative、state |
| 训练成本 | tokens、MFU、通信 | MoE、kernel、数据配比 |
| Agent 可靠性 | 成功、恢复、副作用 | verifier、sandbox、checkpoint |
| 多模态输入 | token budget、对齐、质量 | encoder、codec、fusion |

## 50.15 架构热点的生命周期

新技术可能处于 emerging、生态捕获、标准化、被模型能力吸收或过渡形态。MCP、skill、agent runtime 等外部层会随着模型记忆、上下文和工具调用能力提升而变薄；某种 attention 变体也可能被 serving kernel 吸收为实现细节。

书稿不应只记录“最近流行什么”，还要解释约束是否仍存在、该层是否会保留、迁移成本如何、失败时怎样回退。面试回答的价值在于能判断技术生命周期，而不是背发布日期。

## 50.16 从论文到产品的验证验收条件

架构论文要经过 reference 数学、任务质量、目标硬件、变长 serving、协议兼容、灰度和回滚七道门。每道门都需要明确成功定义和失败判据；如果只完成离线分数，结论应限制为离线研究结果。

## 50.17 资料范围与演进判断

Transformer、Longformer、FlashAttention、Mamba、Mamba-2、Switch Transformer、Mixtral、RETRO 和 DeepSeek-V2 等公开工作分别提供了不同路径的原始证据。模型宣传中的“新架构”如果没有结构图、技术报告或代码，只能作为待核验信号。

判断下一代架构时，不要问“某个模块是否替代了 Transformer”，而要问“哪类信息以什么成本到达当前决策，失败时能否回到更可靠的路径”。这个问题能跨越模型名称和发布周期。

## 50.18 面试问题与练习

**问：未来架构会是纯 SSM 还是纯 attention？**

更稳妥的回答是：取决于任务和系统目标。attention 擅长任意动态检索，SSM/线性路径擅长流式和固定状态；混合、检索和任务路由可能比单一替代更现实，最终要由受控消融和端到端指标决定。

**问：为什么理论复杂度下降后服务不一定更快？**

因为实际性能还受 kernel、memory traffic、通信、动态分支、batch 形状、调度和数据搬运影响；应测真实吞吐、p99、峰值显存和任务成功成本。

**练习：**为一个长代码审计任务设计三条路径：局部/递归、显式全局和外部检索；说明何时切换，以及每条路径失败后的 fallback。

资料入口：

- Transformer: https://arxiv.org/abs/1706.03762
- Switch Transformer: https://arxiv.org/abs/2101.03961
- Mamba: https://arxiv.org/abs/2312.00752
- Mamba-2: https://arxiv.org/abs/2405.21060
- RETRO: https://arxiv.org/abs/2112.04426
- DeepSeek-V2: https://arxiv.org/abs/2405.04434

## 50.19 用 release radar 追踪架构生命周期

面对一个新模型或新模块，可以先把它放进五阶段生命周期：刚出现的研究假设、开始抢占生态位、接口趋于标准化、被更强模型或产品能力吸收、以及只保留在少数场景的过渡技术。这个分类不是给技术贴永久标签，而是提醒读者：资料强度、投入方式和写作深度应随生命周期变化。

每次雷达记录至少包含旧约束、核心机制、公开证据、未知字段、受益 workload、反模式、运行成本、迁移成本和回退。新模型发布的 benchmark 只负责提出问题，不能直接证明架构因果；闭源模型没有披露的层表、训练配方和内部路由继续保持未知。

一个成熟的研究结论应能回答：如果上下文变长、工具变多、内置 memory 变强或 serving kernel 改善，这项技术的生态位会保留、下沉还是消失。这样写架构演进，读者学到的是判断方法，而不是一张会过时的热点清单。

## 50.20 一个长代码审计任务的架构选择

假设任务是审计一个持续增长的代码仓库：输入包含提交、构建日志、测试结果和安全策略，问题要求指出一条回归的引入提交、相关测试和相互矛盾的证据。这个任务同时有三种访问模式：扫描全部日志需要长流状态；回读原始 diff 需要精确寻址；最终答案还要把多个证据合并并给出引用。

可以先设计三条候选路径：

| 路径 | 负责的工作 | 主要风险 |
| --- | --- | --- |
| 全 attention | 直接保留并比较上下文 | 长 prefill、KV 和尾延迟 |
| state/SSM 扫描 + retrieval | 用 state 发现异常，再回读原文 | 状态压缩造成漏召回，索引有维护成本 |
| hybrid | 局部/递归路径扫描，少量 global path 对齐证据 | 路由和 state/KV 生命周期复杂 |

三条路径的输出格式、证据标识和 verifier 必须相同，否则比较的不是架构，而是 harness。质量验收条件至少包括回归提交识别率、证据召回率、引用支持率和冲突处理；系统验收条件包括输入吞吐、p99、峰值状态/缓存、取消恢复和单位成功成本。

设请求被路由到 state 路径的比例为 `1-r`，global 路径的比例为 `r`，路由错误率为 `e`，则一种教学估计是：

```math
C_{mathrm{request}}
\approx (1-r)C_s+rC_g+C_{mathrm{retrieval}}+eC_{mathrm{recovery}}.
```

这个式子不是精确计费公式，却指出一个常被遗漏的事实：把大部分 token 放到便宜路径上，并不会自动让系统便宜；误路由、证据回读、重试和验证都要付费。当任务风险较高时，应把 `C_{mathrm{recovery}}` 按失败后的人审或业务损失计入，而不是只看 GPU 时间。

## 50.21 最小的 matched experiment

架构演进的实验最好分成三层。第一层是算子或 kernel 层：固定输入输出，测实际显存读写、算力利用率和变长 batch。第二层是模型层：固定 tokenizer、训练 token、参数或 active FLOPs、上下文 curriculum 和后训练，测局部预测、精确复制、长程引用、工具 observation 和多模态任务。第三层是系统层：用相同 router、cache、verifier、流量和故障注入，测 p50/p99、并发、恢复和成本。

一个只有“长度—吞吐”两列的结果表是不够的。至少应记录：

```text
model_revision, code_revision, tokenizer, dtype, batch_shape
context_distribution, task_slice, quality, evidence_support
prefill, decode, state_or_kv_bytes, p99, fallback_rate
cost_per_success, recovery_time, rollback_result
```

如果新架构使用了更强的检索或更高的 reasoning budget，要把这些变化单独列为系统变量。否则“架构提升”可能只是外部工具或测试时计算带来的提升。

## 50.22 约束的传递：省掉的成本去了哪里

任何架构优化都在资源账本中移动成本。把全 attention 换成局部 attention，可能减少 pair 数，却需要跨窗口摘要或 global token；把 KV cache 压缩成 latent state，可能减少显存，却要求解码器从 latent 中恢复足够的信息；使用 MoE 减少每 token 激活计算，却会引入路由不均衡和 all-to-all 通信；使用多模态统一 token，可能减少接口数量，却增加序列预算和模态对齐风险。

可以用一个简化的总账本表达：

```math
C_{mathrm{total}}
=C_{mathrm{compute}}+C_{mathrm{memory}}+C_{mathrm{communication}}
 +C_{mathrm{data}}+C_{mathrm{verification}}+C_{mathrm{migration}}.
```

论文通常重点报告前两三项，产品还要承担数据构造、评测、监控、回滚和开发者迁移。工程师若只引用 FLOPs 下降，容易漏掉真正限制上线的通信、验证和维护成本。

## 50.23 新模型发布时如何写出可靠架构结论

面对一个只公布“更长上下文、更快推理或更强 Agent”的模型，先分三栏记录：官方明确披露的接口和评测；可由论文、代码或模型卡支持的结构；没有公开证据的内部猜测。产品页面可以支持“支持某输入长度”这一接口事实，但不能单独支持“具备通用百万 token 推理”或“采用某种未披露位置编码”。

还要绑定版本和条件：模型 revision、服务端 tokenizer、chat template、工具开关、解码参数、reasoning budget、是否使用检索、评测样本和成本。不同厂商的“thinking”“long context”“agent”字段不能因为名字相似就当作同一协议。

这套写法并不削弱前沿信息的价值，反而保留了未来可更新的接口。若后续技术报告披露了层结构或独立复现出现不同结果，只需更新证据栏，不必把整章建立在未经证实的内部细节上。

## 50.24 小结

下一代架构的判断不能靠发布日期或新名词完成。先找旧瓶颈，再把机制写成信息流、资源账本和失败路径，最后用 matched experiment 验证质量、SLO、成本和回退。一个架构只有在目标 workload、硬件、协议和维护约束下形成可复现优势，才值得写成工程结论；否则它仍然是有价值但条件有限的研究假设。
