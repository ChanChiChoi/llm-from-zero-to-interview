# 第 23 章 小模型、边缘模型与高效 Transformer 改造

## 23.1 为什么“更小”是独立的工程问题

把大模型缩小，不是简单地把层数和 hidden size 同时乘一个比例。小模型要在更少的参数、显存、带宽和功耗下完成目标任务，还要面对端侧 CPU/GPU/NPU 的算子支持、启动时间、网络断开、数据隐私和升级成本。

云端大模型通常可以用更多显存和并行卡解决问题；边缘设备则可能只有几 GB 内存、有限的内存带宽和不稳定的加速器支持。一个在服务器上更快的结构，换到手机、车载设备或本地工作站上，可能因为 kernel 不支持、访存不规则或频繁搬运而变慢。

因此高效 Transformer 的目标不是“所有指标都最小”，而是在给定设备和任务下寻找可用的 Pareto 点：质量不能低于门槛，延迟、内存、功耗和包体要在预算内。

## 23.2 小模型能力从哪里来

模型质量可以来自参数容量、训练数据、训练 token、架构归纳偏置和后训练。小模型在参数容量上处于劣势，通常需要用其他因素补偿：

1. 更高质量、更聚焦的数据；
2. 强模型蒸馏出的软目标或轨迹；
3. 针对任务的 tokenizer 和数据配比；
4. 更适合硬件的 attention、FFN 和位置机制；
5. 量化、剪枝和低秩适配后的联合训练；
6. 任务路由，让小模型只承担它擅长的请求。

“小模型接近大模型”通常是条件结论。它可能只在某个领域、语言、上下文长度、提示模板或工具闭环上成立。评估时要明确任务分布，不能把一个窄任务的蒸馏结果写成通用智能等价。

## 23.3 参数、显存和带宽的基本账本

若模型有 `N` 个参数，每个参数使用 `b_w` 字节，权重存储的下界约为：

~~~math
M_{\mathrm{weight}}\approx N b_w.
~~~

例如 1B 参数使用 FP16/BF16，权重下界约为 2 GB；使用 4-bit 权重，理想下界约为 0.5 GB。真实文件还包含 scale、zero point、alignment、embedding、临时 buffer、KV cache 和 runtime 开销，因此不能把理想数字当作安装后内存。

在线生成还要保存 KV cache。对普通 attention，一个粗略公式是：

~~~math
M_{\mathrm{KV}}
\approx 2 B L T H_{\mathrm{kv}}d_h b_{\mathrm{kv}}.
~~~

边缘设备常常不是算力先耗尽，而是内存带宽先成为瓶颈。每个 token 都要读取权重和 KV；当矩阵规模较小、batch 为 1 时，理论 FLOPs 不能预测真实延迟。应同时测权重读取、KV 读取、算子融合和 CPU/GPU/NPU 之间的数据搬运。

## 23.4 量化：先改变数值格式，再谈速度

量化把高精度权重或激活映射到较少 bit。对一个标量块，可以用简单的线性量化表示：

~~~math
q=\mathrm{clip}\left(\mathrm{round}\frac{x-z}{s},q_{\min},q_{\max}\right),
\qquad
\hat x=sq+z.
~~~

其中 `s` 是 scale，`z` 是 zero point。量化的误差取决于分组方式、异常值、权重分布、激活分布和硬件 kernel。4-bit 不等于所有层都以 4-bit 计算，也不等于显存一定按四分之一下降。

Weight-only quantization 主要压缩权重，生成时仍可能以更高精度做激活和累加；activation-aware 方法会根据输入分布处理异常通道；KV cache quantization 则改变历史状态的存储和读取精度。它们要分别评估，不能把“模型量化”作为一个单一开关。

小模型部署中，量化收益必须用端到端延迟验证。若设备没有对应 INT4 kernel，runtime 可能先反量化到 FP16 再计算，结果是包体变小但速度不快；如果量化 kernel 访存受限，理论带宽收益也可能被解码、调度和数据转换抵消。

## 23.5 结构改造一：减少 KV 压力

标准 MHA 为每个 attention head 保存独立 K/V。MQA 让多个 query head 共享 K/V，GQA 则把 query head 分成若干组共享 K/V。若 query head 数为 `H_q`，KV head 数为 `H_kv`，则 KV 表示的比例近似为：

~~~math
\rho_{\mathrm{KV}}=\frac{H_{\mathrm{kv}}}{H_q}.
~~~

当 `H_kv` 变小，KV cache 和读取压力通常下降，但 K/V 的共享也会限制表示自由度，质量和长上下文行为需要评估。对于端侧 batch=1 的生成，降低 KV 读写常常比减少理论 FLOPs 更有感知价值。

这类改造要同时修改 checkpoint shape、权重转换、attention kernel、KV layout 和 cache 复用。不能只在 config 中把 `num_key_value_heads` 改小，然后期待旧权重自动正确工作。

## 23.6 结构改造二：减少长序列交互

滑动窗口、块稀疏、局部 attention 和分层 token 汇聚都试图减少 `T^2` 交互。标准全 attention 的 score 单元数量约为：

~~~math
C_{\mathrm{full}}\propto T^2.
~~~

如果每个 token 只看宽度为 `w` 的局部窗口，教学式连接数约为：

~~~math
C_{\mathrm{local}}\propto Tw.
~~~

但少算连接也意味着远程信息要经过更长路径，或必须依赖 global token、检索、摘要、递归状态或跨层跳连。长上下文的质量损失不是“复杂度公式里的小数项”，而可能表现为中间证据丢失、版本冲突无法消解和引用不完整。

因此，边缘长文本系统经常采用混合方案：大部分层使用局部 attention，少数层保留全局 attention；先用检索缩短候选上下文，再让小模型处理；或把历史压成结构化状态并保留原文回查路径。

## 23.7 结构改造三：缩小 FFN 与门控开销

FFN 的中间维度常常是 Transformer 参数和计算的大头。SwiGLU 等 gated MLP 增加了投影支路，带来表达收益的同时也增加矩阵乘和内存读写。端侧模型可以通过减少 `d_ff`、使用更窄的 gated FFN、低秩分解或在部分层使用轻量 FFN 来控制成本。

一个线性层 `d_in -> d_out` 的权重参数量是：

~~~math
N_{\mathrm{linear}}=d_{\mathrm{in}}d_{\mathrm{out}}.
~~~

如果把矩阵近似成低秩乘积 `AB`，其中 rank 为 `r`，参数量变成：

~~~math
N_{\mathrm{low\ rank}}=r(d_{\mathrm{in}}+d_{\mathrm{out}}).
~~~

当 `r` 足够小才有压缩；但低秩限制可能损害需要丰富通道交互的任务。剪枝或低秩改造之后，要检查层间 residual scale、激活范围和量化误差，不能只看参数计数。

## 23.8 结构改造四：token 和序列预算

多模态和长文输入中，token 数本身可能比模型层数更快成为瓶颈。图像 patch、视频帧、音频窗口和文档 OCR 都会贡献 token。端侧系统可以使用分辨率自适应、帧采样、token pooling、重要 token 保留和 query-driven 编码，减少送入语言主干的 token。

但 token 压缩是信息瓶颈，不是无损优化。小字号数字、表格关系、时间顺序和空间坐标可能在 pooling 中丢失。压缩模块要有保真评估：OCR 字段准确率、grounding 坐标、视频时间定位、引用支持率和拒答质量都要单独记录。

## 23.9 蒸馏：小模型学的不只是答案

知识蒸馏可以让 student 模型学习 teacher 的软分布、隐藏表示、注意力模式、拒答边界或完整推理轨迹。最基本的 logits 蒸馏可以写成：

~~~math
\mathcal{L}_{\mathrm{KD}}
=T^2\,\mathrm{KL}
\left(
\mathrm{softmax}(z_s/T)
\middle\|
\mathrm{softmax}(z_t/T)
\right),
~~~

其中 `T` 是温度，`z_s` 和 `z_t` 分别是 student 和 teacher logits。温度提高后，低概率类别之间的相对关系更明显，student 可以学习 teacher 对相似候选的偏好。

蒸馏数据还可能包含 teacher 的错误、偏见、过度自信和不安全行为。对数学和代码任务，应该让外部 verifier 或执行器检查结果；对安全任务，要保留边界样本和正常允许样本，避免 student 只学会过度拒答。

## 23.10 从大模型到端侧模型的路线选择

常见路线并非互斥：

| 路线 | 主要缩减对象 | 主要风险 | 适合先验证什么 |
| --- | --- | --- | --- |
| 量化 | 数值 bit 和权重带宽 | 精度、kernel 不匹配 | 端到端延迟与质量 |
| 蒸馏 | 参数容量和行为函数 | teacher 错误、能力遗失 | 任务切片和长尾 |
| 剪枝 | 层、通道或连接 | 不规则稀疏不加速 | 硬件 kernel 是否支持 |
| GQA/MQA | KV head 和 cache | 表示自由度下降 | 长上下文 decode |
| 局部 attention | 远程连接数量 | 证据不可达 | 位置和多跳任务 |
| token 压缩 | 输入序列长度 | 细节和定位丢失 | 模态字段保真 |
| 路由/级联 | 每个请求使用的模型 | 路由误判和协议复杂 | 任务分类准确率 |

工程上常先做量化和缓存，再考虑结构改造；但如果目标硬件不支持对应 kernel，顺序应反过来，先验证算子和内存带宽。

## 23.11 一个边缘预算的 worked example

假设端侧设备可给模型使用 4 GiB 内存，其中 0.5 GiB 留给 runtime、输入缓冲和系统余量。一个 1.3B 模型使用理想 4-bit 权重，权重下界约为：

~~~math
M_{\mathrm{weight}}\approx1.3\times10^9\times0.5
\ \mathrm{byte}\approx0.65\ \mathrm{GB}.
~~~

真实量化权重加 scale、alignment 和 embedding 后可能更大。若 KV cache、workspace 和线程栈共占 1.2 GiB，理论上仍有空间；但如果上下文从 4K 增长到 32K，KV 项大约按 8 倍增长，系统可能突然从可运行变成频繁驱逐或 OOM。

这说明端侧配置不能只发布“模型大小”。至少要给出：模型权重格式、最大上下文、KV dtype、并发数、缓存策略、峰值内存、首 token 延迟、持续生成速度和热稳态结果。

## 23.12 评估要覆盖设备和任务，而不是只测 perplexity

小模型评估至少分成四层。

第一层是数值正确性：量化前后 logits、困惑度和短文本生成差异。第二层是任务质量：代码、数学、多语言、领域问答、结构化输出和安全。第三层是系统指标：冷启动、TTFT、TPOT、吞吐、峰值内存、功耗和温度。第四层是长期行为：连续对话、缓存增长、后台切换、网络断开、升级回滚和低电量策略。

一个端侧准入条件可以形式化为：

~~~math
G_{\mathrm{edge}}
=G_{\mathrm{quality}}
\land G_{\mathrm{memory}}
\land G_{\mathrm{latency}}
\land G_{\mathrm{power}}
\land G_{\mathrm{protocol}}.
~~~

评测应保留 baseline、优化版本和回退版本；如果量化只在短问答上通过，却让长代码或工具参数错误率上升，不能用平均分掩盖回归。

## 23.13 常见失败模式

### 只缩参数，不改数据

小模型容量更小，若仍使用大模型的宽泛数据配比，可能把有限参数浪费在低价值分布上。要按目标任务做数据质量和 mixture 设计。

### 只看文件大小

权重文件小不代表 runtime 内存小。KV、workspace、解码缓存和系统共享内存都可能超过权重。

### 只看理论稀疏度

硬件不支持不规则稀疏时，稀疏矩阵可能比 dense kernel 更慢。必须实测 kernel 和端到端延迟。

### 量化后没有重新校准

激活异常值、特殊 token、长上下文和工具 JSON 可能比普通文本更容易暴露量化误差。校准集应覆盖目标分布。

### 蒸馏只保留最终答案

student 可能学到表面模板，却没有学到拒答边界、证据引用和错误恢复。任务需要什么监督，就蒸馏什么行为。

### 忽略升级和回退

端侧模型要绑定 tokenizer、量化格式、算子版本和 schema。升级失败时必须能回到旧模型，不能让半加载权重或旧 KV 被新 runtime 使用。

## 23.14 一个保守的工程流程

第一步冻结原始模型、tokenizer、评测集和设备；第二步建立权重、KV、workspace 和功耗基线；第三步只做一个改动，例如 8-bit/4-bit 量化；第四步按任务切片检查质量；第五步测冷启动、TTFT、TPOT、峰值内存和热稳态；第六步再叠加 GQA、蒸馏或局部 attention；最后为每个改动保留可回退 artifact。

如果多个优化一起上线，出了问题很难判断是数值误差、结构表达能力、token 压缩还是 runtime kernel。端侧系统更需要小步实验，因为设备差异和版本差异会放大不可控因素。

## 23.15 面试回答：如何把一个 LLM 部署到边缘设备

先确认设备、内存、功耗、延迟、离线要求、上下文和任务分布。然后建立 FP16 baseline，按收益/风险顺序评估量化、KV 优化、蒸馏、结构压缩、token 预算和模型路由。

回答不能只说“用 INT4”。还要说明量化格式和 kernel 是否匹配，KV cache 如何预算，长上下文如何处理，质量如何按任务切片，功耗如何在热稳态测量，以及失败时如何回退。最后用一个带验收条件的 Pareto 表决定是否上线。

## 23.16 资料范围与端侧预算

高效模型与端侧路线可参考 DistilBERT（https://arxiv.org/abs/1910.01108）、GQA（https://arxiv.org/abs/2305.13245）、LLM.int8()（https://arxiv.org/abs/2208.07339）、GPTQ（https://arxiv.org/abs/2210.17323）、SmoothQuant（https://arxiv.org/abs/2211.10438）和 AWQ（https://arxiv.org/abs/2306.00978）。这些论文支持相应方法在公开实验条件下的结论，不代表任意设备、模型和任务都会获得同样收益。具体端侧部署还要以目标 NPU/GPU 的算子文档、runtime 版本和实测为准。

## 23.17 端侧优化的组合顺序

端侧优化最好按可回退的阶梯推进：先建立 FP16 或 BF16 baseline，再验证 8-bit/4-bit 权重，随后检查 KV dtype 和上下文预算，最后才叠加蒸馏、结构稀疏、局部 attention 或 token 压缩。每一步都要保留质量、峰值内存、首 token、持续生成速度、功耗和热稳态。

如果量化后质量下降，先按任务切片定位是数字、代码、工具 JSON、长上下文还是安全边界退化；如果内存达标但速度不变，优先查 kernel、带宽和线程调度；如果平均速度很好但长尾很差，查上下文增长、后台抢占和热降频。文件大小变小只是 artifact 指标，不是端侧成功。

## 23.18 端侧回退的第二个约束

生产设备必须绑定 tokenizer、量化格式、算子/runtime 版本、模型 manifest 和回退 artifact。升级时先在影子流量比较任务质量和资源，再逐步切换；新模型加载失败或质量未通过硬性检查时，应能回退到旧版本并清理不兼容的 KV/state。

论文可以支持某种量化、蒸馏或注意力改造在公开硬件上的结果，但不能替代目标 NPU/GPU 的实测。端侧方案最终要回答的是：在指定任务、设备、温度和功耗预算下，单位成功成本是否改善，且失败时能否安全回退。

## 23.19 端侧预算的第二个例子：质量下降会被重试放大

假设一个端侧模型单次推理成本为 `c=1`，一次任务成功率为 `p=0.82`；云端模型单次成本为 `c=4`，成功率为 `p=0.95`。如果失败需要重试，忽略重试上限时，单位成功任务成本的期望近似为：

~~~math
E[C_{\mathrm{success}}]\approx\frac{c}{p}.
~~~

端侧约为 `1/0.82=1.22`，云端约为 `4/0.95=4.21`，端侧仍有成本优势。但如果端侧失败会触发人工复核或工具回滚，额外代价 `c_f` 不能忽略：

~~~math
E[C_{\mathrm{success}}]
\approx\frac{c+(1-p)c_f}{p}.
~~~

当 `c_f` 很高时，便宜的小模型可能反而更贵。这个例子不用于证明某个规模永远更好，而是说明端侧选型要把任务失败、升级路由、人工确认和隐私收益放进同一个账本。低风险摘要可以接受较低 `p`；付款、删除、代码发布等任务应把成功率和安全验收条件设成硬约束。

## 23.20 蒸馏、量化和结构改造必须联合验证

小模型通常同时使用蒸馏、量化、剪枝、低秩适配或 attention 改造。若一次性全部改变，最终质量差异无法归因。一个最小消融矩阵可以以大模型教师和未压缩学生为基线：

| 方案 | 蒸馏 | 量化 | 结构改造 | 需要回答的问题 |
| --- | --- | --- | --- | --- |
| S0 | 否 | 否 | 否 | 学生基线能力和成本 |
| S1 | 是 | 否 | 否 | 软目标/轨迹带来多少收益 |
| S2 | 否 | 是 | 否 | 纯数值压缩造成多少退化 |
| S3 | 是 | 是 | 否 | 蒸馏是否抵消量化损失 |
| S4 | 是 | 是 | 是 | 完整端侧方案是否值得维护 |

每一行都要测短任务、长上下文、代码、结构化输出、拒答和设备端 p99。蒸馏可能提高平均准确率，却让学生更像教师的格式偏好；量化可能只伤害异常值密集的层；结构改造可能改善 KV，却损害远程证据。没有消融就不能把完整方案的收益归到某一项技术。

## 23.21 硬件感知的 benchmark 要测内存层次

端侧延迟不能只由 FLOPs 估算。一个粗略的 roofline 视角是：

~~~math
T\gtrsim\max\left(
\frac{F}{P_{\mathrm{peak}}},
\frac{B_{\mathrm{memory}}}{BW_{\mathrm{memory}}},
\frac{B_{\mathrm{transfer}}}{BW_{\mathrm{interconnect}}}
\right),
~~~

其中 `F` 是计算量，`B_memory` 是权重和 cache 的内存流量，`B_transfer` 是 CPU/GPU/NPU 之间的数据搬运。小 batch decode 常常更接近 memory-bound；模型首次加载、KV layout 转换和 tokenizer 又可能成为另一个瓶颈。理论上减少 FLOPs 的改造，如果引入不规则 gather 或频繁搬运，实际 p99 可能变差。

测试应报告冷启动、热启动、单请求、多请求、不同 prompt/output 长度、线程数、温度和功耗。除平均 latency 外，还要保存 p50/p95/p99、峰值 RSS、加速器内存、功耗、温度降频和后台线程。设备型号、驱动、runtime、kernel 版本也属于实验条件，不能只写“手机端更快”。

## 23.22 端侧能力的回退路线

边缘部署不是把一个固定模型推到所有设备。更可靠的系统会根据设备内存、温度、上下文长度、任务风险和网络状态选择路径：本地小模型、量化模型、云端强模型、检索/工具补偿或人工确认。路由器输出的不只是模型 ID，还应包括原因、版本、预算和回退状态。

当本地模型的结构化输出不合法、置信度低、引用缺失或安全分类不通过时，系统可以升级请求；升级前要决定是否把原始数据发送到云端，并向用户施加隐私和权限限制。对不能离端的数据，回退只能走本地规则、专用小模型或拒答，而不是默认上传。

路由质量要同时测升级率、回退延迟、隐私阻断率、任务成功率和错误恢复。一个小模型如果多数高价值请求都升级，节省的 GPU 成本可能不如预期；但如果它稳定处理大量低风险任务，端云混合仍可能有很高的总体收益。

## 23.23 小结

小模型和边缘模型的关键不是把大模型按比例缩小，而是在质量、显存、带宽、延迟、功耗、隐私和回退之间重新设计整条链路。量化、蒸馏、GQA、局部 attention、token 压缩和路由各自解决不同瓶颈；只有在目标设备和真实任务上通过联合验收条件，才算完成一次高效 Transformer 改造。
