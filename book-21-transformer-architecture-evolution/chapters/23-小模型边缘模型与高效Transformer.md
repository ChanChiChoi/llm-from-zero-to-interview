# 第 23 章 小模型、边缘模型与高效 Transformer 改造

## 23.1 小模型、边缘模型与高效分别回答什么问题

“小模型”说的是参数规模；“边缘模型”说的是模型运行的位置和设备约束；“高效”则必须说明在什么任务质量下节省了哪种资源。三者有关联，却不能互相代替。参数少的模型不一定能在目标任务上通过质量门槛；在服务器上吞吐高的模型不一定适合手机；本地运行提供离线和数据留在设备上的可能，也不自动代表速度快或耗能少。

评估端侧方案时，先把“模型大小”拆成几本账。权重文件大小描述磁盘或下载占用；运行时内存还包括常驻权重、KV cache、激活值、临时 workspace 和运行库；延迟和能耗则取决于实际工作负载、内存带宽与设备执行路径。每个指标只回答其中一类问题。

| 观察口径 | 能说明什么 | 单独不能说明什么 |
| --- | --- | --- |
| 参数量或模型文件字节数 | 权重规模和分发体积 | 峰值运行内存、任务质量或设备速度 |
| 峰值运行内存 | 指定输入和运行过程中的资源占用 | 其他上下文、并发或 runtime 下的占用 |
| Prefill 延迟与逐 token 解码速度 | 输入处理和自回归生成各自的时间表现 | 未测负载下的端到端交互体验 |
| 任务成功率与质量 | 模型是否能完成目标任务 | 资源成本或失败后的人工/工具代价 |
| 能耗与热稳态 | 指定设备和负载下的电量、温度表现 | 不同芯片、后台负载和机身散热下的表现 |

例如，把权重从 8 bit 改为 4 bit，通常会缩小权重表示，但运行内存还含其他状态；如果目标设备没有适合的低比特算子，转换与调度成本也可能抵消部分收益。反过来，某种结构可能增加运算次数，却因为减少了权重搬运而在特定设备上更合适。接下来的比较都要回到“目标任务、目标设备和目标指标”这三个条件。

## 23.2 小模型如何利用有限参数预算

小模型不是把大模型的层数、宽度和中间维度按同一比例缩小。给定相近的参数预算，层数、每层宽度、FFN 维度、嵌入表示和权重共享方式，都会改变模型表达能力和执行时需要做的工作。数据质量、领域配比和后训练又会改变模型把这些参数用在什么能力上。因此，单看参数量无法解释两个小模型为何在同一任务上差异很大。

MobileLLM 在亚十亿参数设置中组合了深而窄的结构、嵌入共享、Grouped-Query Attention（GQA）与相邻 block 权重共享，并分别比较了若干 125M、350M 模型的任务表现。论文还在 iPhone 13、ExecuTorch 和 Metal Performance Shaders 的固定设置下测量 125M 模型。它说明小参数预算下的结构选择值得单独研究，但不能证明深而窄的模型在所有规模、任务或手机上都更好。[MobileLLM（ICML 2024）](https://proceedings.mlr.press/v235/liu24ce.html)

OpenELM 展示了另一种参数分配：不是让每一层采用同一宽度，而是按层调整 attention heads 和 FFN 维度；论文同时提供公开训练框架，并报告 Apple Silicon 上的 MLX 测量。由于训练数据、配置和实现会共同影响结果，OpenELM 的具体基准不能单独隔离 layer-wise scaling 的普遍收益。[OpenELM 技术报告](https://arxiv.org/html/2404.14619v2)

小模型能力也可能来自数据和训练过程的选择。SmolLM2 报告记录了预训练数据评估、分阶段混合及按能力短板调整数据比例；这些实验说明数据配方是结果的一部分，却不是某一种数据混合可以普遍提升任意小模型的证据。该模型的大规模训练结果也不等于端侧设备上的运行结果。[SmolLM2 技术报告](https://arxiv.org/abs/2502.02737v1)

蒸馏、量化和结构改造同样不能混为一类。蒸馏改变学生模型学习的目标或样本，不自动减少学生的推理成本；量化改变权重或激活的数值表示；缩小层宽、改变 attention 或共享参数则改变模型结构。蒸馏训练流程可回到第五册相关章节；量化与模型压缩的部署实践见[第六册第七章](../../book-06-llm-deployment/chapters/07-量化与模型压缩.md)。

## 23.3 改造选项分别改变哪些计算、状态或信息路径

设计高效模型时，先判断主要压力来自权重、KV 状态、attention 交互、FFN 计算、输入长度，还是目标芯片不支持的执行路径。不同改动针对的账本不同，风险也不同。

| 改动 | 主要改变 | 仍需检查的代价或边界 | 详细机制 |
| --- | --- | --- | --- |
| 缩窄层、调整深度或共享权重 | 唯一参数量、矩阵形状和权重读取次数 | 共享权重可能增加重复计算；更深路径可能增加串行延迟 | [第 5 章](05-ffn-swiglu-gated-mlp与moe-ffn.md)、[第 23 章 23.2](#232-小模型如何利用有限参数预算) |
| 减少 KV heads（MQA/GQA） | 每层 KV 状态规模和 decode 时读取的 KV 数据 | 变化的是 KV 路径，不会自动缩小 FFN 权重或所有内存 | [第 4 章](04-mha-mqa-gqa-mla的演进与trade-off.md)、[第 11 章](11-kv-cache长上下文推理和显存增长问题.md) |
| 局部/稀疏 attention 或线性 attention | token 间直接交互数量，或历史表示的状态形式 | 远程信息路径、状态容量和实际 kernel 效率会随方法改变 | [第 19 章](19-Sliding-Window与稀疏注意力.md)、[第 24 章](24-Linear-Attention基本思想与核技巧.md) |
| MoE 路由 | 每个 token 计算的 FFN 专家子集 | 全部专家权重、路由、驻留与通信仍需安排 | [第 21 章](21-MoE路线Switch-GShard-Mixtral-DeepSeek.md)、[第 22 章](22-Dense与MoE训练服务trade-off.md) |
| 量化、剪枝或低秩变换 | 数值精度、非零权重或矩阵表示 | 精度损失、稀疏/低秩算子支持和转换开销 | [第六册第七章](../../book-06-llm-deployment/chapters/07-量化与模型压缩.md) |
| 减少输入 token 或 patch | 序列长度及其后续计算、状态占用 | 被压缩的数字、空间关系、时间顺序或证据细节可能无法恢复 | 多模态输入与编码由[第十五册](../../book-15-multimodal-generative-models/目录.md)主讲 |

表中的每一种改动都可能只是移走瓶颈。例如，少存 KV 不代表权重读取也变少；减少 attention 连接不代表端到端生成更快；MoE 减少单 token 的专家矩阵计算，也不代表完整模型状态消失。若目标设备的主要耗时在另一条路径上，这项改动就未必带来可见收益。

## 23.4 目标设备的内存层次和执行栈决定收益

端侧设备有不同的存储层级：片上高速存储容量有限，主存容量更大但访问较慢，闪存容量更大而读取延迟又不同。模型在这些层级之间如何放置权重、激活和状态，会影响启动、每 token 读取和峰值内存。实际推理栈还要能把模型结构映射到相应算子和 kernel；服务器上的配置不能直接代表手机 CPU、GPU 或 NPU 上的表现。

MobileLLM 的 block-sharing 方案展示了一个具体取舍：相邻层重复使用同一组权重，可以减少不同权重的存储和搬运，却仍要执行重复的 block。作者在 iPhone 13、iOS 17.2.1、ExecuTorch/MPS 上测量固定的 125M FP16 模型，并与权重不共享的更深模型作比较。这个 profile 支持的是该模型和软件路径下的测量结果，不是权重共享对所有端侧模型都“几乎免费”的保证。[MobileLLM §3.6](https://proceedings.mlr.press/v235/liu24ce.html)

Gemma 3n 的公开技术文档说明了另外两种分层设计：Per-Layer Embeddings（PLE）可以缓存到闪存，并在执行各层时加入；MatFormer 则在较大的模型中嵌套较小子模型，运行时可选择一部分参数。它们展示了模型结构怎样配合不同存储与计算预算，但具体内存收益需要按该模型、运行方式和设备解释。[Gemma 3n 技术文档](https://gemma.ai/models/gemma-3n/)

MobileMoE 的 2026 年预印本报告了在 Galaxy S25 和 iPhone 16 Pro 上运行小规模 MoE 的测试。作者为 MoE 前馈层实现了专用执行算子，并将量化训练、模型结构和手机端软件栈一起评估。这个案例的意义在于：稀疏结构并不会自动变成端侧速度，算子实现和芯片路径也是结果的一部分。它仍是特定模型、设备、backend 与负载下的作者报告，不能据此推出任意手机上的 MoE 优势。[MobileMoE arXiv v1](https://arxiv.org/html/2605.27358v1)

## 23.5 用与任务和设备相匹配的证据比较改造

一个改造主张可能在回答三个不同问题：架构消融是否改善了同一训练/任务条件下的模型质量；量化或压缩后任务质量损失多少；在目标设备和执行栈上，满足质量要求的模型占用多少内存、需要多少时间和能量。论文只回答其中一个问题时，不能把它扩展成“这个模型适合端侧”或“这个结构普遍更快”。

比较模型能力时，要说明测试任务、提示与样本范围；比较结构贡献时，需检查训练数据、模型大小和训练过程是否足以支持归因；比较设备效率时，还要锁定芯片、系统版本、runtime/kernel、权重格式、输入/输出长度和并发。Prefill 与逐 token decode 应分开看；模型文件字节数、峰值运行内存和任务完成成本也不能互相代替。能耗与热稳态若会影响目标场景，就需要报告对应设备和持续负载条件。

ACL 2025 的一项小模型研究收集了 68 个公开模型，并同时检查十类任务和两块真实边缘开发板上的 prefill/decode 与内存表现。它提供了一种把能力和设备成本并排观察的评测组织方式；研究模型样本止于 2024 年的 Llama 3.2，设备也只有两块开发板，因此适合作为评估维度参考，不是当前小模型排名或跨设备定律。[Demystifying Small Language Models for Edge Deployment](https://aclanthology.org/2025.acl-long.718.pdf)

因此，可靠的效率结论都应落到一个具体组合：什么模型版本、完成什么任务、达到什么质量、运行在哪种设备与软件栈、测了哪些资源指标。结构、训练数据、量化、kernel 或负载改变后，原有结论需要重新限定。小模型设计的目标不是找到一个脱离条件的赢家，而是找到满足特定设备和任务预算的结构与实现。
