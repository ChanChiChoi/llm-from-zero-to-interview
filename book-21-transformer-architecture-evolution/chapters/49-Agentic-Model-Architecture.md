# 第 49 章 Agentic Model Architecture：模型能力与执行闭环

“模型会调用工具”和“系统能完成任务”是两个不同的判断。语言模型可以输出一个工具请求，但实际动作要由宿主识别并交给环境执行；环境返回的结果再进入下一轮模型输入，系统才形成可继续或停止的闭环。这个闭环不要求改变 Transformer block，却会改变模型周围的信息路径、状态和控制权。

本章从架构角度追踪三件事：工具使用行为在哪里形成、模型动作如何跨过宿主进入外部环境、Agent 的评测结果究竟属于哪一部分。规划、记忆、RAG、安全策略、工具协议和 Runtime 都有专册主讲；这里将它们放在闭环图景中定位，不重复操作细节。

## 49.1 语言模型、单次工具调用与 Agent 系统

普通生成调用接收上下文并返回文本。模型也可以按训练或提示要求输出结构化工具请求，但这一步仍只是提出动作；只有宿主把请求解释为调用、实际执行并取得环境结果，才发生外部状态变化。Agent 系统再把观察送入下一次模型调用，让系统根据新状态选择继续行动还是结束。

| 交互形态 | 模型提供什么 | 后续是否依赖环境反馈 |
| --- | --- | --- |
| 单次生成 | 直接回答 | 通常不依赖 |
| 单次工具调用 | 一个待执行的动作请求 | 宿主执行后返回一次结果 |
| Agent 闭环 | 当前状态下的下一步请求或最终答复 | 多轮根据观察更新状态与动作 |

因此，单次 function call 的格式能力本身不能说明系统拥有任务规划、恢复或长程执行能力。反过来，某个 Agent 系统也不一定采用专门的神经网络层；它可以把通用模型放进一个有状态的控制循环。**Agent 架构**在本章指模型与宿主、工具和环境之间的这套组合关系，细致的循环模式见[第十七册](../../book-17-agent-tool-use/目录.md)。

## 49.2 工具使用能力可以放在不同架构层

工具使用可以通过提示、模型训练和外部检索等不同路径进入系统。它们分别改变当前上下文、模型参数和测试时可用资料，不是彼此排斥的三种产品形态。

| 路线 | 能力主要放在哪里 | 代表工作与支持范围 |
| --- | --- | --- |
| 提示中交错动作与观察 | 当前上下文和控制流程 | [ReAct](https://arxiv.org/abs/2210.03629) 用少样本轨迹引导模型在语言思考、动作与环境观察之间交替；论文展示的是指定提示和任务上的方法，不是新增 Transformer 模块 |
| 训练模型何时、怎样调用 API | 模型参数与训练数据 | [Toolformer](https://papers.neurips.cc/paper_files/paper/2023/hash/d842425e4bf79ba039352da0f658a906-Abstract-Conference.html) 用自监督候选调用筛选与微调，让模型学习选择 API、生成参数并将返回结果用于后续预测；证据绑定论文的工具与任务 |
| 训练模型并检索当前 API 文档 | 模型参数与外部检索上下文 | [Gorilla](https://arxiv.org/abs/2305.15334) 将 API 调用微调与文档检索结合，测试检索到的 API 信息怎样影响调用；[ToolLLM](https://proceedings.iclr.cc/paper_files/paper/2024/file/28e50ee5b72e90b50e7196fde8ea260e-Abstract-Conference.html) 也把工具数据、ToolLLaMA、API retriever 和 ToolEval 放入同一研究框架 |

这些路线说明，工具能力既可能部分学进权重，也可能由示例提示或当下检索的文档补足。它们不能互相代替：训练数据让模型熟悉调用模式，不会自动知道后来变更的 API；检索提供新文档，不保证模型正确选择和填写参数；提示能调整决策过程，也不能代替宿主执行。上述论文证明的是具体设计可行及其限定实验结果，不构成通用 Agent 能力排名。

## 49.3 模型提出的动作如何经过宿主进入环境

一次工具交互至少包含四个不同角色：模型根据上下文提出动作，宿主把输出解析成请求并决定是否执行，工具或环境产生实际结果，宿主再将结果作为观察交回模型。查询数据库、操作桌面或修改代码时，真实世界的状态由外部系统改变；模型生成“已完成”几个字并不会使操作发生。

| 阶段 | 负责方 | 本阶段产生的事实 |
| --- | --- | --- |
| 决策 | 模型 | 想调用哪个工具、提供什么参数，或直接答复 |
| 接收与控制 | 宿主/Agent runtime | 请求是否可解析、是否通过策略以及是否已提交执行 |
| 动作与返回 | 工具/环境 | 实际副作用、返回值、错误或环境状态 |
| 再决策 | 模型与宿主 | 新观察进入上下文；继续行动、修正计划或结束 |

此处要区分“模型打算做什么”“宿主实际发出了什么”“外部环境发生了什么”。若工具超时，实际状态还可能未知；文字解释不能替代外部回执或独立验证。结构化 schema、授权、重试、事务、trace、checkpoint 和恢复由[第二十册](../../book-20-agent-harness-runtime/目录.md)深入讲解；Function Calling、MCP、A2A 等接口协议见[第二十二册](../../book-22-tool-protocol-ecosystem/目录.md)。

## 49.4 当前上下文、外部检索、持久记忆与验证

闭环中的不同信息来源不能都叫“记忆”。当前任务上下文用于传递正在处理的目标、观察和动作历史；外部检索从知识库或文档中找本轮可用的证据；持久记忆保存跨片段或跨任务可能复用的状态；验证器则检查生成答案、动作结果或任务产物是否满足标准。

| 信息路径 | 主要回答的问题 | 本书对应的深入入口 |
| --- | --- | --- |
| 当前上下文/轨迹 | 这项任务到哪一步、刚收到什么结果？ | 第二十册的上下文和 trace 章节 |
| 外部检索 | 哪些外部资料与当前问题相关？ | [第 45 章](45-Retrieval-Augmented-Architecture.md) |
| 持久记忆 | 哪些过去的信息要保存、更新或再次读取？ | [第 46 章](46-Memory-Augmented-Transformer.md) |
| 验证器 | 结果是否符合任务定义、外部规则或可执行检查？ | 第十七册的 Agent 评估与第二十册的 Evaluation Harness |

检索结果可以提供证据，却不能保证模型按证据作答；写入记忆的旧状态也可能过期；一个 verifier 若只检查代理指标，仍可能误判真实目标。架构上应当指出每条信息由谁产生、以何种形式进入下一轮，以及由谁检查。记忆与检索的具体机制、更新策略和评测继续由对应章节承担。

## 49.5 Agent 评测成绩属于完整交互配置

Agent benchmark 测量的不是一个孤立的模型输出。模型面对什么任务、能调用哪些工具、环境从什么状态开始、是否有领域规则、如何把执行结果判为成功、以及调用预算是多少，都会限定成绩的含义。

| 基准 | 交互边界 | 它帮助审视什么 |
| --- | --- | --- |
| [AgentBench](https://openreview.net/pdf?id=zAdUB0aCTQ) | 数据库、网页、操作系统、游戏等多类环境 | 不同环境下的行动和决策表现不能缩成一个内部模块结论 |
| [OSWorld](https://proceedings.neurips.cc/paper_files/paper/2024/hash/5d413e48f84dc61244b6be550f1cd8f5-Abstract-Datasets_and_Benchmarks_Track.html) | 多操作系统中的真实桌面应用、初始状态和执行型评估脚本 | 电脑操作结果包含视觉定位、界面知识、模型和执行栈共同影响 |
| [τ-bench](https://arxiv.org/abs/2406.12045) | 模拟用户、多轮交流、领域 API 与策略规则；以结束时数据库状态对照标注目标状态 | 任务成功还取决于能否跟进用户请求并遵守规则；pass^k 描述多次运行一致性，与单次成功率不同 |

这些基准处理的任务和环境不同，其分数不能直接拼成 Agent 架构排名。若要把差异归因到模型本身，需要尽可能固定控制流程、工具、环境、verifier 与预算；若模型和运行配置同时改变，结果支持的是整套配置在该条件下的表现。这个归因边界来自基准实际包含的组件，也解释了为什么 Agent benchmark 的成绩不能证明系统内部采用了某种未公开的 planner、记忆结构或专用 Transformer block。

## 49.6 根据环境变化决定控制权如何分配

当步骤固定、环境变化少、成功条件可以提前写清时，确定性工作流能直接表达执行顺序；当下一步取决于工具结果、未知状态或新证据时，让模型根据观察挑选下一动作可以提供额外适应能力。这个选择关系到控制权由程序还是模型持有，而不是给同一任务贴上“有 Agent”或“无 Agent”的标签。

把控制权交给模型也会增加决策轮次、运行时间和需要处理的分支。是否值得采用闭环，要看环境是否会改变、反馈是否能改变下一步、动作结果是否可以验证，以及额外调用是否带来足够的任务价值。复杂任务如何规划、拆分和评估可转读[第十七册](../../book-17-agent-tool-use/目录.md)；如何让动作在具体代码环境安全运行和恢复转读[第二十册](../../book-20-agent-harness-runtime/目录.md)。

由 ReAct 的提示型交互、Toolformer/Gorilla 的工具使用训练和多种交互 benchmark 可以得到一个有限结论：Agent 系统可以在不改变基础 Transformer block 的情况下扩展模型可用的信息和动作路径，但外部控制环、工具和环境决定了模型输出如何影响真实状态。专门训练模型和专用多模态动作结构仍可进入系统；分析某个 Agent 时，应逐层找公开证据，而不要从最终行为推断未披露的内部实现。
