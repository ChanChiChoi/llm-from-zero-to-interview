# 第 49 章 Agentic Model Architecture：模型、工具、记忆、检索和执行器

## 49.1 Agent 为什么不是“多写几轮 prompt”

一个普通聊天请求可以近似成一次函数：输入上下文，模型生成输出。Agentic 系统则要在不确定环境中反复观察、判断、行动，再根据行动结果决定下一步。它面对的不是一个静态的答案题，而是一个带状态、工具和副作用的控制问题。

例如，用户说“查一下本周的错误率，找到回归提交，修复测试并给出 patch”。系统需要读取监控、查询代码、定位版本、运行测试、修改文件，并在失败时改变计划。任何一步的外部结果都可能和模型预期不同。只增加上下文长度，并不能自动获得这种闭环能力。

因此，Agentic Model Architecture 不是某一种固定的 Transformer block，而是模型、环境接口、记忆、检索、执行器和验证器共同组成的架构。模型负责提出候选决策，运行时负责把候选决策变成受控动作，环境返回观察，验证器判断动作是否真的生效。

## 49.2 从生成模型到闭环控制器

把第 t 步的系统状态记为 s_t，观察记为 o_t，动作记为 a_t。最小闭环可以写成：

~~~math
o_t\sim\mathcal{O}(s_t),\qquad
a_t\sim\pi_\theta(a\mid h_t),\qquad
s_{t+1}=\mathcal{T}(s_t,a_t)
~~~

这里 h_t 是模型看到的工作上下文，通常由历史观察、已批准动作、工具结果和任务约束组成；πθ 是模型诱导的策略；T 是环境转移。模型并不直接拥有环境真相，它只能通过观察和工具接口间接获得信息。

如果每一步都有成本 c_t，还可以把目标写成：

~~~math
J(\pi)=\mathbb{E}\left[
\sum_{t=1}^{H} r(s_t,a_t)
-\lambda_c c_t
-\lambda_r \mathrm{Risk}(a_t)
+\lambda_v \mathrm{Verify}(a_t)
\right]
~~~

这说明 Agent 优化的不是“回复越长越好”。一次危险但看似合理的写操作，可能比多一次只读检查更贵；一个没有验证的成功文本，也不等于任务完成。

## 49.3 六个需要明确分工的部件

一个可审计的 Agent 系统通常至少有六个部件。

第一是模型。它负责理解目标、生成计划、选择工具、解释观察和提出下一步动作。模型输出是候选决策，不应直接等价于已经执行的事实。

第二是工具与环境。工具提供搜索、数据库、浏览器、编译器、代码仓库或业务 API。每个工具都应声明参数 schema、权限、超时、幂等性和副作用。

第三是执行器。执行器解析结构化动作，做参数校验、权限检查、超时控制、重试和回滚。它是模型和外界之间的安全边界。

第四是记忆。短期记忆保存当前轨迹，长期记忆保存可复用的事实、经验或用户偏好。记忆写入不能因为模型说了一句话就自动发生，必须有来源、时间和可信度。

第五是检索。检索把大规模外部知识压缩成当前步骤可用的候选证据。它负责找什么，不负责替模型证明结论；最终回答仍需要检查证据支持关系。

第六是验证器。验证器可以是单元测试、类型检查、数据库约束、规则引擎、独立模型或人工审批。它把“动作看起来合理”转换成“动作达到可观测的验收条件”。

这六个部件的边界越模糊，系统越难排错。把工具结果直接拼进 prompt，或者把模型输出直接写入长期记忆，都会让错误在状态链路中扩散。

## 49.4 计划、动作与观察的协议

一个简单的 Agent 轨迹可以表示为：

~~~text
goal
  -> plan
  -> action(tool, arguments)
  -> observation(result, metadata)
  -> verification
  -> next action or final answer
~~~

实际协议还应区分计划文本和执行事件。计划是模型的意图，执行事件是运行时已经发出的动作，工具回执是外部系统的事实。三者都保留，才能在事故中回答“模型想做什么”“系统实际做了什么”“外部系统返回了什么”。

结构化动作可以有如下教学形式：

~~~json
{
  "tool": "run_tests",
  "arguments": {"suite": "unit", "timeout_s": 120},
  "reason": "验证改动没有破坏已有行为"
}
~~~

reason 可以帮助调试，但不应成为授权依据。真正的授权应来自工具注册表、用户权限、风险策略和审批状态。一个模型写出“这是安全的”，不能代替权限检查。

## 49.5 工具选择是一个受约束的决策问题

假设有工具集合 A，工具 a 的收益估计为 U(a)，调用成本为 C(a)，风险为 R(a)。一种简化的选择目标是：

~~~math
a^\star=\arg\max_{a\in\mathcal{A}_{\mathrm{allowed}}}
\left[U(a)-\lambda C(a)-\mu R(a)\right]
~~~

A_allowed 不是所有已注册工具，而是经过身份、资源范围、参数和审批筛选后的集合。高风险工具的可用性应由策略层决定，而不是让模型在自然语言中自己判断。

工具描述也会影响模型行为。过长或互相重叠的 schema 会增加选择错误；缺少错误示例会让模型把权限拒绝、空结果和服务故障混为一谈。工具设计应尽量让成功条件和失败类型可机器识别。

## 49.6 记忆不是聊天记录的同义词

短期轨迹记录“本次任务发生了什么”，长期记忆记录“未来可能复用什么”。如果把所有轨迹都永久塞回 prompt，成本会随任务长度增长；如果把所有内容都摘要，精确参数、时间和否定条件可能丢失。

一个记忆条目至少需要：

~~~text
content
source
created_at
valid_from
valid_to
confidence
scope
provenance
~~~

记忆写入可以先经过候选生成，再经过去重、冲突检测和来源校验。对于用户偏好这类可变事实，必须支持覆盖和失效；对于代码、配置和权限事实，优先回到权威源查询，不要把旧摘要当作真相。

可以把记忆价值近似写成：

~~~math
V_{\mathrm{memory}}
=\frac{\Delta Q_{\mathrm{future}}}
{C_{\mathrm{storage}}+C_{\mathrm{retrieval}}+C_{\mathrm{staleness}}}
~~~

一个记忆即使很容易检索，如果过期后造成错误决策，净价值仍然可能是负的。

## 49.7 检索、计划和验证的边界

检索负责缩小信息范围，计划负责安排动作顺序，验证负责判断结果是否成立。三者不能相互替代。

只做检索的系统可能找到正确文档，却不知道要先读取配置还是先运行测试。只做计划的系统可能生成漂亮的步骤，却没有拿到真实环境信息。只做生成后自检的系统可能重复模型自己的偏见，不能替代独立执行结果。

在代码任务中，最有价值的验证往往是编译、单元测试、静态检查和 diff 审查；在数据库任务中，可能是事务状态、行数变化和约束检查；在知识问答中，可能是来源覆盖、时间有效性和冲突证据。验证器应和任务目标绑定。

## 49.8 长任务中的上下文折叠

长任务不能无限保留原始轨迹。折叠时应把上下文分成四类：

1. 未完成的目标和硬约束。
2. 已确认的事实与来源。
3. 已执行的动作、结果和失败原因。
4. 待处理的假设、风险和下一步候选。

摘要不应把“计划调用工具”改写成“工具已经调用”，也不应把“测试失败”压成“代码有问题”。状态转换必须基于事件，而不是基于语言风格。

一个折叠函数可以表示为：

~~~math
h_{t+1}=F_{\mathrm{fold}}
(h_t,e_t;\,K_{\mathrm{must\_keep}},K_{\mathrm{drop}})
~~~

其中 e_t 是新事件，K_must_keep 包括任务约束、错误、证据和未提交副作用。折叠质量要用恢复任务测试：恢复后的 Agent 能否复述当前状态，能否继续正确动作，能否避免重复已经提交的操作。

## 49.9 工具副作用与事务语义

读操作、可重试写操作和不可逆操作不能用同一套重试策略。工具注册时应明确：

| 类型 | 例子 | 主要控制 |
| --- | --- | --- |
| 只读 | 搜索、查询、读取文件 | 权限、超时、结果大小 |
| 幂等写 | 更新同一个配置版本 | 幂等键、版本检查 |
| 非幂等写 | 创建订单、发送消息 | 审批、去重、人工确认 |
| 不可逆写 | 删除、发布、转账 | 强确认、最小权限、回滚或人工验收条件 |

执行器应为高风险动作生成 intent_id，并在重试时复用它。若工具端支持幂等键，服务器应按键去重；若不支持，运行时不能假设网络超时意味着动作没有发生。

## 49.10 最小可运行的受控 Agent

下面的教学代码把模型决策替换成固定策略，重点展示执行器如何限制工具和验证结果：

~~~python
from dataclasses import dataclass


@dataclass
class Event:
    kind: str
    payload: dict


def run_agent(goal, tools):
    events = [Event("goal", {"text": goal})]
    action = {"tool": "read_file", "arguments": {"path": "README.md"}}

    if action["tool"] not in tools:
        raise PermissionError("tool is not registered")
    result = tools[action["tool"]](**action["arguments"])
    events.append(Event("tool_result", {"tool": action["tool"], "result": result}))

    verified = result is not None
    events.append(Event("verification", {"passed": verified}))
    return events
~~~

真实系统还要加 schema 校验、路径沙箱、超时、审计、结果截断、租户隔离和失败恢复。这个例子最重要的地方是：工具调用和验证是显式事件，而不是藏在模型生成文本里。

## 49.11 如何评估 Agent，而不是只评估最终答案

Agent 评估至少要分四层。

第一层是任务结果：最终目标是否完成，产物是否正确。第二层是轨迹质量：是否调用了必要工具，是否出现无效循环，是否遵守权限。第三层是恢复能力：工具失败、超时、空结果和部分成功后能否继续。第四层是成本与风险：调用次数、token、延迟、人工介入率、副作用和越权尝试。

一个简单的任务成功率不能掩盖高风险错误。可以定义：

~~~math
S_{\mathrm{agent}}
=\mathbf{1}[\mathrm{goal\_passed}]
\cdot\mathbf{1}[\mathrm{policy\_passed}]
\cdot\mathbf{1}[\mathrm{side\_effect\_verified}]
~~~

对于不可逆操作，任何一个检查失败都应使任务进入人工复核，而不是通过平均分抵消。

## 49.12 常见失败模式

第一，模型把工具调用写成自然语言，执行器无法准确区分参数和意图。第二，重试没有幂等键，造成重复写入。第三，工具错误被摘要器改写成成功。第四，长期记忆保存了未经验证的模型猜测。第五，规划循环没有预算，Agent 在同一错误上反复调用。第六，完成请求后的临时状态没有清理，造成跨请求污染。第七，最终回答没有引用执行证据，把计划当成事实。

这些问题不靠换一个更大的模型就会消失。它们属于协议、状态机、权限和验证层的设计缺陷。

## 49.13 Agentic model 与普通生成模型的边界

Agentic model architecture 不应被理解为模型多了一个“Agent 层”就自动会完成任务。真正的闭环包括状态、环境观察、工具动作、权限、验证、恢复和终止；其中一部分可能在模型参数中，一部分必然属于外部 runtime。

一个动作循环至少要区分 proposal、policy check、execution、observation、verification 和 commit。模型负责提出候选和更新计划，runtime 负责事实状态、工具执行和副作用；把这两者混成一段文本，会让系统无法审计和恢复。

## 49.14 计划、记忆和工具的架构取舍

长计划可以减少重新规划，但容易过时；逐步规划适应环境，却增加模型调用。摘要记忆节省上下文，但可能丢失约束；结构化 checkpoint 更可恢复，却需要版本和迁移。工具越多，能力越广，路由、schema、权限和提示注入面也越大。

因此不能只比较“能不能调用工具”，要比较任务成功、无效调用、恢复、单位成功成本、p99、越权和人工接管。对代码 Agent，要把 workspace revision、测试 artifact 和 patch 提交边界纳入模型协议；对研究 Agent，要把来源、引用和不确定性纳入结果契约。

## 49.15 Agentic 架构的证据等级

闭源模型发布的“可执行电脑任务”“长周期工作”通常只证明公开 harness 条件下的系统能力，不足以证明模型内部有某种专用 planner、memory 或 world model。公开技术报告写出的架构和训练阶段可以作为事实；从行为反推内部模块，只能写成假设。

## 49.16 资料范围与架构判断

ReAct 论文展示了推理与行动交替的基本范式，Toolformer 讨论了模型学习调用工具，Reflexion 讨论了利用反馈形成语言化反思，MemGPT 讨论了分层记忆管理。它们提供的是研究范式，不是一个可直接部署的安全框架。

Agentic Model Architecture 的核心是把模型决策嵌入一个可观测、可约束、可恢复的闭环。模型越强，候选动作的范围越大，越需要清晰的工具协议、权限边界、记忆来源和独立验证。

## 49.17 面试问题与练习

**问：Agent 和普通 RAG 链有什么本质区别？**

普通 RAG 通常是固定的检索—生成流程；Agent 可以根据观察选择下一步工具、修改计划并处理环境反馈，但这也引入了循环、权限、副作用和状态一致性问题。

**问：为什么不能让模型直接执行工具？**

因为模型输出是概率生成结果，可能存在参数错误、越权、重复执行和对网络超时的误判。执行器需要做 schema、权限、幂等、超时、审计和验证。

**练习：**设计一个代码修复 Agent 的事件表，至少包含目标、读取、修改、测试、失败、重试、提交和回滚事件；为每种写操作标注是否幂等。

## 49.18 Agentic loop 的状态边界

Agent 架构的最小闭环可以写成：观察环境、更新任务状态、选择动作、执行工具、验证结果，再决定继续、回退或结束。每次循环都可能修改外部世界，因此模型的 hidden、workspace、工具结果和已提交副作用必须分开记录。

一个可靠的 trace 至少保存 goal、observation ids、plan revision、tool schema、参数校验、权限判定、执行结果、verifier、重试原因和最终状态。模型重试同一个工具调用时，要区分“上一次没有执行”“执行超时但状态未知”和“已经成功但响应丢失”；只有幂等且可查询的工具才适合自动重试。

Agent 的成功率还不能脱离成本和风险。一次任务成功但执行了三次不必要的写操作，或者花费过多 token 才得到答案，不应与一次干净成功等价。评估至少分解 task success、tool correctness、side-effect safety、recovery success、latency 和 cost per successful task。

## 49.19 小结

Agentic Model Architecture 不是给模型加一个“Agent 层”就完成了，而是把规划、工具、记忆、workspace、权限、验证和恢复组织成可观察的闭环。判断一条路线时，既要看模型能提出什么动作，也要看 harness 如何限制、执行和证明这些动作。
