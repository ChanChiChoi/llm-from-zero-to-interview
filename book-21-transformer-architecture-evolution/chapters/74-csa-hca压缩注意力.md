# 第 74 章 CSA/HCA：长历史压缩注意力的两个问题

## 74.1 为什么要压缩历史访问

在百万 token 场景中，完整历史既昂贵又包含大量冗余。CSA/HCA 这类缩写可以作为压缩 attention 路线的入口：历史可能被压缩成较少的表示、较少的访问块，或由不同路径分别处理局部和全局信息。

这里必须先处理证据边界。若公开资料没有给出缩写全称、层表和公式，不能随意扩展成一个统一算法。可以确定的是它们涉及“如何在长历史中减少存储或访问”，具体实现要回到官方技术报告、模型卡和代码。

## 74.2 两类压缩问题

第一类是表示压缩：把历史 `H` 映射为低维或少量 latent：

```math
Z=C(H),\qquad y=\mathrm{Attention}(q,Z)
```

第二类是访问压缩：历史仍可能存在，但 query 只读取局部窗口、摘要块或稀疏候选。前者可能造成表示瓶颈，后者可能漏掉正确位置。

压缩比可以写为：

```math
\rho=\frac{|Z|}{|H|}
```

`\rho` 小不代表任务成功率一定高。重要的是压缩后保留了哪些可验证信息，以及访问策略是否能找到它。

## 74.3 一个四段文档例子

四段文档中，第一段是背景，第二段是旧版本实验，第三段是新版本结果，第四段是例外条件。问题要求指出新版本是否真正改善，并引用冲突证据。

如果压缩器把四段合成主题摘要，模型可能知道“新版本更好”，却丢掉旧版本和例外条件；如果访问器只取第三段，又无法发现冲突。更稳妥的 hybrid 做法是保留每段来源、摘要和候选高价值句，最终让 verifier 检查引用支持。

## 74.4 信息压缩的目标函数

可以把压缩看成在存储成本和任务损失之间优化：

```math
\min_C\;L_{\mathrm{task}}(C(H))+\lambda L_{\mathrm{memory}}(C(H))
```

`L_task` 不应只用语言模型 loss，还应包括 evidence recall、citation support、数字准确、冲突识别和代码测试。否则压缩器可能保留主题流畅度，却牺牲审计所需的细节。

## 74.5 局部、全局和压缩路径

局部路径适合短距离语法，压缩路径适合重复背景，全局路径适合跨段证据。一个长上下文层可以先从压缩表示获得候选，再用显式 KV 或原文读取高价值片段。

路径预算也要动态。低风险摘要可以接受更高压缩比；精确引用、代码 patch 和安全审计应提高保真或直接走显式路径。压缩不是所有请求都使用同一个 ratio。

## 74.6 评估设计

比较 full KV、只局部、只压缩和 hybrid。测试主题摘要、精确数字、版本比较、冲突判断、长文档引用和工具参数。记录 compression ratio、evidence recall、citation support、answer accuracy、TTFT、TPOT、state GiB、p99 和单位成功成本。

把证据放在开头、中间和结尾，并增加相似干扰。只测平均分会掩盖“压缩在中间位置失败”的问题。

## 74.7 压缩误差与引用忠实度

压缩评估不能只看 embedding MSE 或 perplexity。对每个 atomic claim 保存 gold source、压缩摘要、模型引用和 verifier 结果。数字、表格、版本号和否定词要单独抽样，因为它们对小误差很敏感。

如果主题答案正确但引用不支持，说明压缩保留了语义而丢掉了可追溯性；如果召回下降但引用支持率不变，说明系统可能只保留了少数可靠证据。两个结果对应不同修复路径。

## 74.8 serving 的状态和版本

压缩表示要保存 compressor revision、模型 revision、dtype、scale、position、来源范围和 checksum。prefix cache、snapshot、preemption 和 speculative 都要区分临时压缩状态与已提交状态。

压缩 kernel 可能引入额外 prefill 延迟；访问稀疏块可能导致不规则内存访问；当高压缩 ratio 失败时，fallback 到 RAG 或显式原文路径要可观测。

## 74.9 常见失败

把缩写扩展成没有依据的具体算法；只报告压缩比；把摘要当证据；冲突事实被平均；重要 token 被稀释；global path 预算不足；压缩 cache 跨版本复用；kernel 反而更慢；没有高风险 fallback。

## 74.10 面试回答与练习

回答“如何评价长历史压缩 attention”时，应区分表示压缩和访问压缩，说明二者的误差来源；用精确数字、冲突、引用和位置分桶评估质量，同时测压缩比、显存、延迟、并发和单位成功成本。对于 CSA/HCA 的具体含义，先核对官方资料，不根据缩写猜实现。

练习一：设计四段文档压缩实验，给出 gold evidence 和引用支持指标。

练习二：解释为什么 embedding MSE 低不能证明 citation support 高。

练习三：为高风险审计任务设计压缩失败后的路由。

### 74.10.1 表示压缩和访问压缩

长历史优化有两种不同动作。表示压缩把多个 token 变成更小的向量、摘要或 state；访问压缩保留部分表示，但限制 query 能访问哪些位置。前者主要引入信息损失，后者主要引入可见性损失，CSA/HCA 这类缩写必须先确认属于哪一类或如何组合。

可以把最终输出误差粗略分解为：

```math
E_{\mathrm{total}}
\approx E_{\mathrm{repr}}+E_{\mathrm{access}}
 +E_{\mathrm{protocol}}+E_{\mathrm{runtime}}
```

这不是严格定理，而是工程诊断框架。引用错误可能来自压缩、窗口、模板或 cache 错位，不能只看 embedding 误差。

### 74.10.2 worked example：审计文档压缩

四份政策文档中，定义在第一份、例外条件在第二份、当前版本日期在第三份、权限限制在第四份。压缩器若只保留每份文档的主题摘要，模型可能得到一个听起来正确的总览，却丢掉例外和权限。测试要要求输出四条证据、版本和“不适用条件”，并比较原始、压缩和 RAG 路径的 citation support。

### 74.10.3 压缩后的安全路由

普通总结可以接受有损压缩；支付、法律、医疗和发布审计不能默认接受。若压缩后 evidence recall 或关键字段 recall 低于门槛，应回退原文检索、保留显式 global path 或转人工。回退原因要写入 trace，不能让用户误以为系统检查了全部原文。

### 74.10.4 评测不要只看平均相似度

压缩评测至少包含 reconstruction/embedding 指标、关键实体、数字、时间、版本、冲突、引用和拒答。一个压缩结果和原文的平均相似度很高，仍可能删除一个改变结论的“仅在……情况下”短语。高风险任务应按关键字段和原子主张做验收条件。

## 74.11 CSA/HCA 名称的核验方法

缩写可能指模型中的正式模块，也可能是社区对压缩或稀疏路线的简称。核验时先查官方技术报告、模型卡、代码和配置字段，确认全称、输入输出、压缩位置、是否保留原文和是否有专用 kernel。

如果没有一手资料，只能把它作为“压缩 attention 观察项”讨论通用问题。不要根据字母猜出一个完整的数学实现，也不要把别的论文中的 CSA/HCA 公式移植成某个模型的事实。

## 74.12 端到端压缩实验

压缩实验应有四个 baseline：原始 full KV、固定窗口、表示压缩和 hybrid 回读。每个 baseline 使用同一 prompt、同一 token budget 和同一文档版本，比较：

~~~text
compression ratio
evidence recall
citation support
exact numeric accuracy
conflict resolution
TTFT
TPOT
peak memory
p99
~~~

压缩收益只有在质量检查通过后才有意义。若高风险任务不通过，应自动回退原文路径，而不是用普通摘要样本的平均分掩盖。

## 74.13 压缩和外部检索的组合

压缩器可以先把长历史变成候选摘要，再由 retrieval 按来源、时间和权限回读原文。这样压缩负责降低初筛成本，retrieval 负责恢复细节；二者之间必须传递来源范围和查询条件。

如果摘要没有 provenance，retrieval 只能按语义相似度猜位置，可能返回同名实体或旧版本。高风险系统应保存原子主张、来源文档、段落范围和版本校验。

## 74.14 高风险压缩的验收条件

普通摘要可以接受语义近似，高风险审计需要字段级保真。可以为数字、版本、否定、权限、时间和来源建立 mandatory fields；只要其中一个字段在压缩后无法回读，就不能把任务标记为已审计。

~~~math
G_{\mathrm{compression}}
=\prod_{j\in\mathrm{critical\ fields}}
\mathbf{1}[\mathrm{recall}_j\ge \tau_j]
~~~

乘积形式表示任一关键字段失败都会阻断高风险路径。普通任务可以使用加权平均，但不能把普通任务验收条件套到支付、法律或发布审批。

## 74.15 压缩方法的版本和回归

压缩器的参数、训练数据、量化 scale、kernel 和来源索引都要版本化。升级压缩器时，重新跑固定的长文档、冲突、数字和引用集，并比较原始路径和压缩路径的差异。

若压缩比提高但 p99 下降，可能是稀疏读取不连续；若质量不变但内存没有下降，可能是临时 buffer 或 metadata 占主导。回归报告必须同时给出质量、内存和端到端延迟。

## 74.16 CSA/HCA 的共同问题是证据预算

无论采用何种压缩注意力，系统都在有限的 state、latent 或摘要预算中选择保留信息。主题摘要需要低维趋势，审计、代码和表格则需要高精度字段；同一压缩比例不能覆盖所有任务。

可以按任务给预算分配：

~~~math
B_{\mathrm{total}}
=B_{\mathrm{summary}}+B_{\mathrm{exact}}
+B_{\mathrm{recent}}+B_{\mathrm{global}}
~~~

最近窗口、全局摘要和关键字段的预算应由 query 需要决定，而不是平均分配。保留少量显式证据通常比盲目把所有 latent 维度加大更有效。

## 74.17 压缩注意力的回读协议

压缩器输出候选时，应同时返回来源文档、位置范围、revision、压缩版本和置信度。后续 query 若需要精确字段，读取器必须能够沿来源回到原始 token 或结构化记录。

回读不是可选的 UI 功能，而是纠正压缩错误的路径。没有回读，压缩器一次丢失否定词或版本条件，生成器就无法恢复。

## 74.18 长上下文压缩的部署验证

对不同压缩比例、量化精度和层 schedule，分别测 memory、projection、p99、exact recall、citation support、snapshot restore 和 rollback。长请求还要覆盖中间位置、冲突版本、删除和权限撤销。

如果压缩比增加但任务成功成本上升，可能是重试、回读或 verifier 变多；如果质量稳定但显存没有下降，可能是临时 buffer、索引和 metadata 主导。只有端到端账本通过，压缩才有部署价值。

## 74.19 从压缩机制走向上线条件

压缩 attention 的价值是用可接受的信息损失换取长历史的资源下降；真正的验收条件是“关键证据是否仍然找得到、引用是否仍然成立、成本是否满足 SLO”。因此发布前至少要做四组对照：不压缩的显式 attention、只压缩不回读、压缩后按 query 回读、压缩失败时显式 fallback。

评估不应只看语言模型 loss。对数字、否定、版本、时间、权限、代码标识符和跨段引用建立字段级 exact recall；对整条回答记录 citation support、unsupported claim rate、回读次数、重试次数、TTFT/TPOT、显存和单位成功成本。若压缩率很高但回读和 verifier 让 p99 翻倍，系统可能不适合普通在线请求，却仍适合离线摘要；结论应随 workload 分开。

上线条件还要验证 snapshot/restore、cache version、租户隔离、删除和权限撤销。CSA/HCA 的公开全称和细节若未完整披露，应保留为模型特定观察项；本节的字段保真、回读和成本验收条件是适用于所有压缩历史方案的通用工程要求。

## 74.20 压缩率不是唯一优化目标

设原始历史占用 M_raw，压缩后的表示和索引占用 M_comp，则压缩率可以写成：

~~~math
\rho=\frac{M_{\mathrm{comp}}}{M_{\mathrm{raw}}}.
~~~

但生产收益还取决于压缩、读取、回读和重试：

~~~math
C_{\mathrm{task}}
=C_{\mathrm{compress}}
+C_{\mathrm{read}}
+C_{\mathrm{verify}}
+C_{\mathrm{retry}}
+C_{\mathrm{fallback}}.
~~~

如果压缩率降低了 10 倍，却让 verifier 和原文回读增加 20 倍，单位成功任务成本反而会上升。压缩系统的优化目标应是满足质量和安全验收条件后的总成本，而不是最小 rho。

## 74.21 重要字段的保真约束

普通摘要允许同义改写，高风险文档不允许把关键字段平均化。可以把字段集合分成：

~~~text
numeric: numbers, units, thresholds
temporal: dates, version, effective time
logical: negation, exception, condition
access: tenant, role, permission
provenance: source, span, revision
~~~

每一类都应有单独 recall。一个摘要整体相似度很高，但删掉“仅在工作日生效”这个例外，业务结论就可能反转。压缩评测要以原子主张和字段为单位，而不是只用 embedding cosine 或 perplexity。

## 74.22 压缩器和读取器的协同

压缩器决定保留什么，读取器决定查询什么。若压缩器不知道未来 query，可能保留了主题却丢失低频字段；若读取器只能在 latent 上做相似度，不能沿 provenance 回到原文，压缩错误无法纠正。

更稳健的接口应返回候选和证据范围：

~~~text
latent block
source document
source span
revision
confidence
compression revision
~~~

读取器先用 latent 做候选筛选，再对高价值候选做显式回读。这样压缩负责降低初筛成本，原文负责最终证据；代价是 metadata、索引和回读延迟。

## 74.23 位置分布和压缩误差

长上下文压缩经常在开头和结尾表现较好，中间位置更容易失败。原因可能是训练数据位置偏置、摘要层顺序、window 边界或全局预算，而不一定是压缩维度不够。

把证据分别放在 1%、25%、50%、75% 和 99% 位置，比较：

~~~text
compression ratio
evidence recall
exact field recall
citation support
fallback rate
~~~

如果只增加 latent 维度而中间位置仍失败，应查位置训练和访问路径；如果中间位置在显式回读后恢复，说明压缩可以负责候选但不能负责最终证据。

## 74.24 冲突事实的压缩实验

构造四份文档：旧定义、当前定义、例外条件和权限限制。问题要求输出最终结论、适用范围、版本日期和四条引用。比较 full context、summary latent、compressed attention 和 compressed-plus-readback。

这个实验能区分四种失败：

1. 摘要丢失旧版本，无法判断变化。
2. 压缩丢失例外，结论过度泛化。
3. 读取器找到当前版本但漏掉权限。
4. 引用指向主题相关文档，却不支持具体 claim。

每种失败都要有独立指标和修复路径。

## 74.25 CSA/HCA 的证据边界

CSA/HCA 可能是特定模型中的正式模块名，也可能在不同资料中指代不同压缩/稀疏路径。阅读时先核对全称、输入输出、压缩位置、是否保存原文、是否有独立 kernel 和如何与 KV/state 交互。

如果公开资料只支持“模型使用压缩注意力降低长历史成本”，正文可以讲压缩的通用机制、评测和工程边界；不能根据缩写字母推导完整公式，也不能把另一篇论文的 CSA/HCA 实现移植成该模型事实。

## 74.26 压缩和权限撤销

缓存中可能保存撤销前的文档内容。用户权限变化后，不能只删除外部索引而继续使用 latent。需要让 provenance 与权限检查参与读取：

~~~math
\mathrm{readable}(z)
=\mathbf{1}[
\mathrm{tenant\_ok}
\land\mathrm{revision\_ok}
\land\mathrm{permission\_ok}
].
~~~

任一条件不满足，就触发失效、重压缩、原文重检索或拒答。压缩表示没有权限信息时，读取器不能假设它仍然可用。

## 74.27 压缩的线上发布

压缩器升级应经历：

1. 离线固定集对比。
2. shadow 生成，不影响用户动作。
3. 低风险请求灰度。
4. 高风险任务只读或人工复核。
5. 逐步扩大流量并保留旧路径。

发布记录包括 compressor revision、模型 revision、量化设置、压缩比、fallback、引用支持、p99 和用户任务成功率。若压缩率改善但危险漏报或 unsupported claim 增加，应立即回滚。

## 74.28 压缩 attention 的三个问题

第一是压缩什么：token、head、局部块还是历史表示；第二是怎样恢复查询需要的信息；第三是压缩后是否仍支持精确位置、工具格式和审计引用。CSA/HCA 等名称描述的是一类压缩思路，具体实现的压缩粒度和更新顺序必须以技术报告或模型卡为准。

## 74.29 压缩比例和质量曲线

实验可以改变压缩率 `r`，绘制质量、TTFT、TPOT、峰值显存和 p99 曲线。理想的压缩点不是 `r` 最大，而是位于质量和资源的 Pareto 前沿。对长文问答，另报证据位置和引用完整性；对代码和 JSON，另报语法/工具协议通过率。

## 74.30 压缩 state 的更新与回滚

压缩表示在 speculative、chunked prefill、preemption 和 cache migration 中都必须遵守同一个提交边界。候选 token 只能写临时 compressed state，target 接受后才提交；拒绝时恢复旧 state。若压缩更新不可逆，必须使用写时复制、日志或可重算窗口保证回滚。

## 74.31 从公开结构到工程决策

公开资料可以支持压缩目标、部分结构和公开评测，但不能用一个压缩比推断所有 workload 的收益。部署决策还要验证 kernel、量化、并行布局、版本兼容和安全删除，最终以真实服务曲线而不是架构名称决定。

## 74.32 小结

CSA/HCA 所代表的压缩注意力问题，最终不是“能把多少 token 变小”，而是“有限表示能否保留任务真正需要的字段，并在必要时回读原文”。表示压缩、访问压缩、位置、权限、版本和 serving 事务要一起评估。对于具体缩写和未公开内部结构，证据边界本身就是正文的一部分。
