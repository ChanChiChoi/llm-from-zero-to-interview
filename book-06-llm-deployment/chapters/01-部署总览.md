# 第 1 章 部署总览：从模型 artifact 到可运营服务

训练结束时得到的是 checkpoint，用户需要的却是一个能够接收请求、遵守协议、在预算内返回结果、持续接受监控并且可以回滚的服务。把 checkpoint 加载进显卡并调用 generate，只证明模型在某个开发环境中能执行一次推理，不能证明它适合真实流量。

部署工程把模型能力放进一个具体的 workload：输入有多长，输出有多长，流量什么时候到达，是否需要流式输出，能否排队，能否重试，是否允许调用工具，失败时怎样降级。模型精度、推理引擎、KV Cache、批处理、GPU 拓扑、API、鉴权、日志、质量、安全和成本，最终都要在这组约束下作出取舍。

初学者可以把服务想成一条生产线：请求进入网关，经过排队和调度，模型完成 prefill 和 decode，结果经过协议与安全检查后返回。工程人员还要追问每个环节的资源消耗和失败责任：首 token 慢是排队还是 prefill，后续 token 慢是显存带宽还是调度，质量退化是量化还是 chat template，超时是模型慢还是工具没有返回。

## 1.0 部署决策从 workload 开始

部署不应该从“团队熟悉哪个框架”开始，而应该先描述服务将承受的工作负载。至少要固定以下变量：

| 变量 | 需要回答的问题 |
| --- | --- |
| 输入长度 | 平均值、P95、最大值，是否包含检索文档或图片 token |
| 输出长度 | 平均值、P95、最大值，是否流式返回 |
| 到达率 | 平均和峰值请求数，是否有明显突发 |
| 并发 | 同时处于排队、prefill、decode 和工具等待的请求数 |
| 交互目标 | TTFT、TPOT、完整响应和超时预算 |
| 质量 | 事实、代码、结构化输出、引用和拒答要求 |
| 工具 | 是否调用数据库、浏览器、代码沙箱或企业 API |
| 故障策略 | 是否允许排队、降级、重试、异步完成和回滚 |
| 成本 | GPU、CPU、存储、网络、教师/工具调用和人工复核成本 |

可以将一类请求表示为 workload 向量：

~~~math
W=(\lambda,T_{\mathrm{in}},T_{\mathrm{out}},
B_{\mathrm{active}},S_{\mathrm{TTFT}},S_{\mathrm{E2E}},Q)
~~~

lambda 是请求到达率，T_in 和 T_out 是输入与输出 token 数，B_active 是同时活跃的请求数，S_TTFT 和 S_E2E 是首 token 与完整响应的目标，Q 表示质量、安全和协议要求。这个向量不是部署配置，而是选择配置的输入。

不同 workload class 不应被混在一个平均数里。普通短问答主要受 decode 和并发影响；长 RAG 主要受 prefill、上下文占用和 TTFT 影响；代码生成受输出长度、停止条件和工具执行影响；Agent 任务还会产生多轮工具等待和外部副作用；多模态请求需要把视觉、音频或视频 token 的编码时间放进前处理。

没有输入/输出长度、峰值到达率和质量目标时，回答“需要几张 GPU”没有可验证的含义。参数量只能给出权重存储的一个起点，不能代替真实 workload 压测。

## 1.1 为什么 checkpoint 不是服务

一个 checkpoint 至少要和以下 artifact 一起交付：

| artifact | 作用 | 不一致时的表现 |
| --- | --- | --- |
| 权重和配置 | 定义模型结构、层数、词表和精度 | 无法加载或输出异常 |
| tokenizer | 把文本映射为 token id | 长度、字符和特殊 token 行为改变 |
| chat template | 组织 system/user/assistant/tool 消息 | 模型把角色或工具结果理解错 |
| generation config | temperature、top-p、stop 和长度 | 输出分布与评估不一致 |
| 精度/量化配置 | 定义计算和存储格式 | 质量、显存和 kernel 不匹配 |
| 引擎适配层 | 将模型结构映射到 runtime | 某些算子或 cache layout 不兼容 |
| 安全与协议配置 | 定义输入、输出和权限边界 | 可能出现越权或数据泄露 |
| 评估与回归集合 | 比较版本行为 | 性能提升但质量退化无法发现 |

一个完整的部署链路可以表示为：

~~~text
checkpoint and config
  -> weight conversion and precision selection
  -> tokenizer and chat-template alignment
  -> inference engine loading
  -> batching, scheduling and KV state allocation
  -> API, authentication and request policy
  -> metrics, logs, traces and quality evaluation
  -> canary traffic and rollback
  -> continuous capacity, quality and security operations
~~~

每一个箭头都是接口，而不是一句流程口号。权重转换可能改变参数名和 tied embedding；chat template 可能改变 assistant mask 和 tool call；引擎可能要求特定 attention、quantization 或 cache layout；网关可能截断输入或重写超时；日志系统可能把敏感 prompt 持久化。

因此，模型版本最好不是一个短字符串，而是一个可追溯元组：

~~~math
R_{\mathrm{model}}=
(r_{\mathrm{weights}},r_{\mathrm{tokenizer}},r_{\mathrm{template}},
r_{\mathrm{engine}},r_{\mathrm{precision}},r_{\mathrm{policy}})
~~~

每个 revision 都应能指向真实 artifact。只有权重 revision 变化而其他字段不变，和 chat template 变化造成的回归，应该在报告中被区分。

## 1.2 离线推理和在线服务

离线推理与在线服务都使用模型 forward，但目标函数不同：

| 类型 | 典型任务 | 首要指标 |
| --- | --- | --- |
| 离线推理 | 批量评测、数据合成、离线标注、文档处理 | 总 tokens/s、总成本、完成时间 |
| 在线服务 | 聊天、代码助手、企业问答、实时 Agent | TTFT、TPOT、P95/P99、错误和超时 |
| 异步任务 | 长文档分析、批量报告、复杂 Agent | 排队可见性、完成时间、重试和幂等 |

离线批处理通常可以等待更多请求组成大 batch，接受更高单请求延迟，重点是 GPU 利用率和单位 token 成本。在线服务必须及时开始输出，不能为了提高总体吞吐而无限等待 batch；它还要处理突发、取消、断开连接和长尾请求。

异步任务处在两者之间。用户可以接受等待，但系统要返回任务 id、进度和最终 artifact，支持重试和幂等。把长 Agent 任务伪装成普通同步 HTTP 请求，往往会导致连接占用、超时重试和重复副作用。

请求吞吐和 token 吞吐也不是一回事：

~~~math
\mathrm{QPS}=\frac{N_{\mathrm{req}}}{T_{\mathrm{wall}}}
~~~

~~~math
\mathrm{TPS}_{\mathrm{out}}
=\frac{N_{\mathrm{out,total}}}{T_{\mathrm{wall}}}
~~~

QPS 表示每秒完成多少请求，输出 TPS 表示每秒生成多少 output token。两个系统可能有相同的 QPS，却因为输出长度不同而消耗完全不同的 GPU 时间。长上下文服务还应单独记录输入 token/s 或 prefill token/s，否则 output TPS 会掩盖输入处理瓶颈。

## 1.3 一次请求经历了什么

把在线请求拆成生命周期，很多“模型很慢”的判断就会变成可定位的问题：

~~~text
admit -> authenticate -> queue
      -> tokenize and validate
      -> prefill prompt and allocate KV state
      -> decode one token at a time
      -> stream, stop or call tool
      -> finalize, audit and release state
~~~

### 1.3.1 TTFT

TTFT（Time To First Token）是从请求进入服务到用户收到第一个输出 token 的时间。它通常包含排队、输入 tokenization、prefill、首 token decode 和网络发送：

~~~math
T_{\mathrm{TTFT}}
=T_{\mathrm{admit}}+T_{\mathrm{queue}}+T_{\mathrm{tokenize}}
+T_{\mathrm{prefill}}+T_{\mathrm{first}}+T_{\mathrm{network,first}}
~~~

在某些系统中，tokenization 和 admission 很小，可以合并到固定开销；在长 RAG 或多模态请求中，输入预处理可能不再小。TTFT 高可能是 prefill 慢，也可能只是请求在队列里等待。只有拆开 trace，才能决定是优化模型、调度还是网关。

### 1.3.2 TPOT

TPOT（Time Per Output Token）描述已经开始流式输出后，后续 token 的平均生成间隔。若第一个 token 已计入 TTFT，输出 token 数为 N_out，decode 总时间为 T_decode，则可用：

~~~math
T_{\mathrm{TPOT}}
=\frac{T_{\mathrm{decode}}}{\max(N_{\mathrm{out}}-1,1)}
~~~

TPOT 受 decode 阶段的 memory bandwidth、KV Cache 读取、batch 形状、GPU kernel、通信和调度影响。平均 TPOT 不能说明每个 token 都一样快；长输出中途的 batch 加入、抢占、工具等待和 cache eviction 可能造成局部抖动。

### 1.3.3 完整延迟与尾延迟

完整响应延迟还包括剩余 decode、网络和可能的工具往返：

~~~math
T_{\mathrm{E2E}}
=T_{\mathrm{TTFT}}+T_{\mathrm{decode,rest}}
+T_{\mathrm{network,rest}}+T_{\mathrm{tool}}
~~~

平均值容易被少量快请求拉低，P95/P99 才能告诉我们最慢的一部分用户经历了什么。生产监控应保存请求级 trace，并按输入长度、输出长度、模型 revision、路由副本、是否命中 prefix cache 和是否调用工具分桶。

流式服务还应明确“首 token 已生成”和“首 token 已到达客户端”的差别。服务器内部 decode 很快，但代理缓冲、网络拥塞或错误的 SSE flush 策略，仍然会让用户感觉 TTFT 很高。

## 1.4 延迟与吞吐的资源画像

Transformer 推理大致分为 prefill 和 decode：

| 阶段 | 主要输入 | 资源特征 | 常见瓶颈 |
| --- | --- | --- | --- |
| prefill | 一次处理整段输入 | 大矩阵计算、并行度高 | 算力、输入长度、attention |
| decode | 每次生成一个新 token | 反复读取权重和 KV 状态 | 显存带宽、KV、batch 调度 |

prefill 主要决定长 prompt 的 TTFT；decode 决定流式输出速度。增加 batch 可能提高 decode 的 GPU 利用率，也可能让短请求等待长请求；chunked prefill 试图在输入计算和已有 decode 请求之间做更细的调度。

Little 定律可以帮助建立一个粗略直觉。在稳定、守恒的队列中，平均并发数 L、到达率 lambda 和平均系统时间 W 近似满足：

~~~math
L=\lambda W
~~~

这个关系不告诉我们模型内部如何调度，也不能替代尾延迟约束，但它说明提高并发往往会提高排队和资源占用。如果服务的平均响应时间变长，即使到达率不变，活跃请求和 KV Cache 压力也会增加。

对于输出吞吐为 S_replica 的单副本，若平均输出到达率为 lambda T_out，理论副本下界可以写成：

~~~math
R_{\mathrm{throughput}}
=\left\lceil
\frac{\lambda T_{\mathrm{out}}}{S_{\mathrm{replica}}}
\right\rceil
~~~

这只是输出 token 的理想下界，没有计入输入 prefill、排队、峰值、故障和质量回归。实际容量要使用同一 workload 下的实测 S_replica，并为尾延迟和故障留余量。

## 1.5 容量规划：从 SLO 倒推副本

假设短问答流量平均为每秒 20 个请求，平均输入 600 token、平均输出 120 token，单副本在同样长度分布下实测输出吞吐为 2,400 token/s。只用平均输出吞吐估算：

~~~math
R_{\mathrm{throughput}}
=\left\lceil
\frac{20\times120}{2400}
\right\rceil=1
~~~

一个副本在纸面上足够，但这不是上线容量。若峰值是平均流量的 2.5 倍，希望单副本在 P95 负载下只使用 70% 的实测能力，并额外保留一个故障冗余副本：

~~~math
R_{\mathrm{safe}}
=\left\lceil
\frac{\lambda_{\mathrm{peak}}T_{\mathrm{out}}}
{0.7S_{\mathrm{replica}}}
\right\rceil+R_{\mathrm{reserve}}
~~~

代入 lambda_peak=50、T_out=120、S_replica=2400、R_reserve=1：

~~~math
R_{\mathrm{safe}}
=\left\lceil\frac{50\times120}{0.7\times2400}\right\rceil+1
=5
~~~

这个结果仍然依赖实测。长 RAG 请求会消耗更多 prefill 和 KV；工具 Agent 会让请求在模型之外等待；请求长度分布变化会让一个“平均 2,400 token/s”失去代表性。容量测试应使用短问答、长上下文、长输出、代码和工具调用等 workload class，而不是只用一个平均 prompt。

容量规划还要回答故障时发生什么。若一个副本停止接收新请求，已有请求是完成、取消还是迁移；重试会不会重复工具动作；路由器是否知道副本正在 drain；KV state 是否能够迁移。N+1 只是副本数概念，不能自动解决有状态 decode 和外部副作用。

## 1.6 单机部署与分布式部署

### 1.6.1 单机部署

如果权重、运行时工作区和预留 KV Cache 能放进一台机器的 GPU，单机部署通常是最容易调试的起点。它的通信路径短、故障面少，适合小模型、低并发、离线任务和早期验证。

单机并不等于没有容量问题。权重占满显存后，KV Cache、CUDA workspace、通信缓冲和临时 tensor 仍然需要空间；一个能启动的配置可能在第二个长请求到来时 OOM。单机服务也需要超时、限流、健康状态和回滚，只是拓扑更简单。

### 1.6.2 Tensor Parallel

Tensor Parallel（TP）把一个层内的矩阵或 attention head 切到多个 GPU，需要在层间或层内通信。它主要解决单卡放不下模型或单卡算力不足的问题，但性能取决于 GPU 互联和切分方式。NVLink、PCIe 和跨机器网络的通信代价不能用同一个数字估算。

### 1.6.3 Pipeline Parallel

Pipeline Parallel（PP）把不同层放到不同 GPU。它可以容纳更大的层堆叠，但需要处理 stage 间传输、微批调度和流水线气泡。对单条低延迟请求，PP 的额外 stage 往返可能很明显；对合适的批量 workload，它可能更有价值。

### 1.6.4 Replica 与 Expert Parallel

Data Parallel 在推理服务中通常表现为多个完整模型 replica，由路由器分摊请求，用容量和可用性换取显存。它不会让单个 replica 变小，但可以降低单副本排队。

MoE 的 Expert Parallel 把 experts 分散到不同 GPU，需要 token routing 和跨卡通信。总参数很多并不意味着每个 token 都激活全部参数，但路由偏斜、通信和 expert load balance 仍会决定真实吞吐。

| 方式 | 主要解决 | 主要代价 |
| --- | --- | --- |
| TP | 单层规模和单卡显存 | 频繁通信、拓扑依赖 |
| PP | 层数和总模型规模 | stage 延迟、流水线气泡 |
| Replica | 并发、容量和可用性 | 权重副本成本 |
| Expert Parallel | MoE expert 容量 | routing、通信和负载偏斜 |

工程选择要先看模型放置、请求形状和 GPU 拓扑，再决定并行方式。不能把训练时的并行配置原封不动地当成推理服务配置。

## 1.7 推理引擎：相似目标，不同生命周期

推理引擎通常负责权重加载、模型执行、KV Cache、batching、调度、解码、多 GPU 和高性能 kernel。它不是简单封装 model.generate，而是决定请求如何共享计算和显存。

| 引擎/生态 | 常见优势 | 选型时需要核对 |
| --- | --- | --- |
| vLLM | 开源 serving、PagedAttention、continuous batching、prefix caching 等能力 | 模型架构、硬件后端、版本和实际 workload |
| SGLang | 结构化程序/Agent 场景、prefix/radix 类缓存和 serving 优化 | API、模型支持、缓存语义和部署版本 |
| TensorRT-LLM | NVIDIA 硬件上的编译和 kernel 优化 | TensorRT/CUDA 版本、构建流程和算子覆盖 |
| llama.cpp | CPU、消费级 GPU 和本地量化部署 | 模型格式、量化 kernel 和并发目标 |
| TGI | Hugging Face 生态中的服务工具和历史生产能力 | 当前官方文档已标注 maintenance mode，新项目需重新评估 |

这些不是永久不变的排名。vLLM 当前文档列出了 continuous batching、chunked prefill、prefix caching 和多种后端能力；SGLang、TensorRT-LLM 和 llama.cpp 的适用场景也会随版本变化。真正的选择要基于模型支持、硬件、协议、观测、升级能力和压测结果。

Hugging Face 当前 TGI 文档明确写出其进入 maintenance mode，并建议后续下游采用 vLLM、SGLang 或其他本地引擎。已有 TGI 服务不必因为文档状态变化立即停机，但新项目不能把 TGI 当成没有生命周期差异的默认选项；应记录维护状态、迁移成本和替代 runtime 的回归结果。

PagedAttention 解决的是 KV Cache 的块式管理和碎片问题，不等于所有 KV 显存都减少；GQA/MQA 通过降低 KV head 数减少每 token 的 KV 字节；prefix caching 只有在前缀真实复用且版本/权限边界一致时才会带来收益。把这些优化名词混成同一个“缓存加速”会掩盖它们解决的问题不同。

## 1.8 Tokenizer、chat template 与模型协议

部署时 tokenizer 必须与训练和评估使用的版本、词表、special token 约定相匹配。Chat model 还需要正确的 chat template，把 system、user、assistant、tool 和多轮消息组织成模型训练时见过的序列。

协议问题经常不会报错，却会表现为模型能力异常：

1. tokenizer 版本改变，输入长度和边界 token 改变；
2. special token id 不一致，EOS 或 PAD 的含义改变；
3. chat template 遗漏 generation prompt，模型不知道该轮轮到谁回答；
4. assistant/tool 边界错误，模型把工具结果当成用户指令；
5. tool calling schema 和执行器 schema 不一致；
6. stop sequence、max new tokens 和截断顺序不同。

可以把输入协议的兼容性记录成诊断向量：

~~~math
d_{\mathrm{protocol}}
=(d_{\mathrm{vocab}},d_{\mathrm{special}},
d_{\mathrm{template}},d_{\mathrm{tool}},d_{\mathrm{stop}})
~~~

这些量不必被压成一个总分。只要 template 或 tool schema 不兼容，性能压测再好也不能解释为同一模型的线上表现。回归集应包含多轮对话、空 system、工具调用、工具拒绝、长上下文和 Unicode 边界。

模型 revision 的最小记录应包括 weights、tokenizer、template、generation config、precision、engine 和 policy。只在日志中写一个 model_name，无法在模型输出回归时确定是权重变了还是输入协议变了。

## 1.9 KV Cache 与显存预算

自回归 decode 会反复使用历史 token 的 key/value。KV Cache 避免每次生成新 token 时重新计算全部历史，但它把序列状态留在显存中，活跃请求越多、上下文越长，占用越大。

若第 i 个请求当前保留 T_i 个 token，使用 L 层、H_kv 个 KV heads、head dimension 为 D_h、每个数值 b 字节，则粗略 KV Cache 大小为：

~~~math
M_{\mathrm{KV}}
\approx
2L H_{\mathrm{kv}}D_h b
\sum_{i=1}^{B}T_i
~~~

2 表示 K 和 V，B 是活跃请求数。这个公式没有计入 block metadata、padding、对齐、临时 workspace、复制和通信缓冲；如果采用平均 token 数 T_avg，也可以近似成 2 L B T_avg H_kv D_h b。

GQA 和 MQA 通过减少 H_kv 降低每 token 的 KV 字节，但不等于减少权重或所有 activation。PagedAttention 类方法把 KV 分成可管理的块，主要改善分配和碎片；如果 block size、请求长度和回收策略不合适，仍可能因为内部碎片或峰值并发而 OOM。

整机显存预算还包括：

~~~math
M_{\mathrm{total}}
=M_{\mathrm{weights}}+M_{\mathrm{KV}}+M_{\mathrm{workspace}}
+M_{\mathrm{activation}}+M_{\mathrm{communication}}+M_{\mathrm{reserve}}
~~~

M_reserve 不能被忽略。没有预留空间的服务可能在平均请求下正常，在长 prompt、并发突发或 kernel 临时分配时崩溃。部署压测要记录 OOM 发生在加载、prefill、decode、batch 扩大还是 cache 回收阶段。

## 1.10 生产请求路径

一个线上 LLM 服务通常由多个职责不同的组件组成：

~~~text
client
  -> API gateway: auth, quota, request size, timeout
  -> router: model, replica and tenant selection
  -> admission and queue: backpressure and cancellation
  -> inference worker: tokenize, prefill, decode, stream
  -> tool or retrieval service: optional external actions
  -> policy and response layer: schema, safety and redaction
  -> metrics, trace and audit storage
~~~

网关负责身份、限额、输入大小、超时和请求 id；路由器根据模型 revision、租户、负载和能力选择副本；队列控制突发并提供 backpressure；worker 负责推理；响应层负责协议、脱敏和审计。一个组件可以承担多个职责，但边界要能在故障时被观察。

取消请求是生产服务的关键语义。用户断开连接后，系统是否停止 decode、释放 KV、取消工具调用和记录原因；如果只取消网络发送而继续生成，GPU 仍在消耗，长请求还可能挤压新请求。

重试也不能默认安全。模型生成可以重试，但工具写入、数据库提交和外部消息发送可能已经产生副作用。请求应携带幂等键，工具动作应有明确的提交状态，路由层不能用普通 HTTP 重试把一次写操作执行两次。

## 1.11 监控：性能指标和能力指标要分开

基础设施监控回答“服务是否健康”，能力评估回答“模型是否完成了正确任务”。两类信号都需要，但不能互相替代。

| 维度 | 例子 |
| --- | --- |
| 性能 | TTFT、TPOT、E2E、P95/P99、队列时间 |
| 吞吐 | QPS、输入 token/s、输出 token/s、batch 利用率 |
| 资源 | GPU 利用率、显存、KV blocks、CPU、网络 |
| 稳定性 | 错误率、超时率、取消率、重试率、OOM |
| 协议 | JSON/schema 失败、tool 参数错误、stop 异常 |
| 质量 | exact match、引用支持、代码测试、人工抽样 |
| 安全 | 越权、敏感信息、prompt/tool injection、审计缺失 |
| 成本 | GPU 时间、每请求 token、每成功任务成本 |

GPU utilization 很高不等于服务好。GPU 可能在处理无效重试、过长回答或低质量 batch；GPU 利用率低也可能是请求到达率低而不是 runtime 有问题。指标必须和请求 trace、质量样本和成本关联。

每次模型、模板、精度、引擎、调度或安全策略变化，都应保存对应 revision。线上出现质量下降时，按 revision 对比短问答、长上下文、代码、工具和拒答边界，而不是只看总平均分。

## 1.12 质量、安全与发布判断

换成量化版本、启用 speculative decoding 或修改 chat template 时，性能可能上升，但不能只比较 tokens/s。固定 replay 集至少覆盖：

1. 普通问答和多轮对话；
2. 长上下文引用与中部证据；
3. 数字、数学和代码；
4. JSON、函数调用和工具参数；
5. 拒答、隐私和越权边界；
6. 多模态或特殊 token 协议（如果服务支持）。

对每个请求同时保存 model revision、tokenizer revision、template revision、精度、解码参数、服务拓扑和工具版本，才能解释回归。性能与质量最好用同一 workload 重新测量；量化后的 token 速度提升若伴随代码测试或引用支持下降，不能把它称为单纯优化。

安全检查应覆盖输入、输出、工具和租户边界。Prompt injection 可能出现在用户输入、检索文档、网页和工具返回中；tool injection 可能让模型把数据字段误当作动作指令。模型服务本身可以做内容和 schema 检查，但最终权限仍要由执行器和网关决定。

发布判断可以保留为一个证据向量：

~~~math
d_{\mathrm{release}}
=(d_{\mathrm{fit}},d_{\mathrm{latency}},d_{\mathrm{capacity}},
d_{\mathrm{quality}},d_{\mathrm{safety}},d_{\mathrm{rollback}})
~~~

每个分量都应指向具体测量和回退动作。安全、协议和回滚证据缺失时，性能数据不能替代它们；发布并不是把多个数字相加，而是检查目标是否都被满足。

## 1.13 灰度、回滚与版本生命周期

模型上线不是一次性事件，而是从小流量开始观察的过程。常见灰度方式包括按比例、用户组、业务场景、地域或租户分流。灰度期间必须同时记录新旧版本的请求形状，因为如果新版本收到的是更短、更容易的请求，平均指标会产生假象。

回滚需要提前定义：

1. 哪些指标触发停止扩大流量；
2. 新请求切回旧版本还是等待当前请求；
3. 正在执行的工具动作如何处理；
4. KV state、队列和缓存是否可继续使用；
5. 质量回归样本如何保留；
6. 回滚后怎样确认旧版本恢复。

滚动升级时，旧版本不能过早删除。至少要等正在生成的请求完成或被安全取消，确认缓存和日志版本可区分，再释放资源。对有状态 Agent，模型回滚还要考虑 workspace、工具协议和记忆格式是否兼容。

## 1.14 一个最小部署指标 demo

下面的 0 依赖 demo 用四个 toy 请求模拟在线 trace，计算 TTFT、TPOT、P95 latency、QPS、输出 token/s 和 KV Cache 显存。它只用于说明指标的计算口径，不代表任何真实 GPU benchmark。

~~~python
import math


requests = [
    {
        "id": "chat_short",
        "arrival_s": 0.00,
        "queue_s": 0.04,
        "prefill_s": 0.20,
        "first_emit_s": 0.01,
        "decode_step_s": 0.018,
        "input_tokens": 800,
        "output_tokens": 80,
    },
    {
        "id": "faq",
        "arrival_s": 0.10,
        "queue_s": 0.01,
        "prefill_s": 0.05,
        "first_emit_s": 0.01,
        "decode_step_s": 0.012,
        "input_tokens": 120,
        "output_tokens": 40,
    },
    {
        "id": "long_rag",
        "arrival_s": 0.20,
        "queue_s": 0.08,
        "prefill_s": 0.35,
        "first_emit_s": 0.02,
        "decode_step_s": 0.020,
        "input_tokens": 2200,
        "output_tokens": 120,
    },
    {
        "id": "tool_call",
        "arrival_s": 0.35,
        "queue_s": 0.03,
        "prefill_s": 0.10,
        "first_emit_s": 0.02,
        "decode_step_s": 0.016,
        "input_tokens": 500,
        "output_tokens": 25,
    },
]

for request in requests:
    request["ttft_s"] = (
        request["queue_s"]
        + request["prefill_s"]
        + request["first_emit_s"]
    )
    request["decode_s"] = max(request["output_tokens"] - 1, 0) * request["decode_step_s"]
    request["latency_s"] = request["ttft_s"] + request["decode_s"]
    request["tpot_s"] = request["decode_s"] / max(request["output_tokens"] - 1, 1)


def percentile(values, q):
    ordered = sorted(values)
    rank = max(1, math.ceil(q / 100 * len(ordered)))
    return ordered[rank - 1]


wall_s = (
    max(request["arrival_s"] + request["latency_s"] for request in requests)
    - min(request["arrival_s"] for request in requests)
)
latencies = [request["latency_s"] for request in requests]
ttfts = [request["ttft_s"] for request in requests]
tpots = [request["tpot_s"] for request in requests]
total_output_tokens = sum(request["output_tokens"] for request in requests)
metrics = {
    "qps": round(len(requests) / wall_s, 2),
    "tokens_per_s": round(total_output_tokens / wall_s, 2),
    "avg_ttft_ms": round(sum(ttfts) / len(ttfts) * 1000, 1),
    "p95_latency_ms": round(percentile(latencies, 95) * 1000, 1),
    "p95_tpot_ms": round(percentile(tpots, 95) * 1000, 1),
}

layers = 32
active_tokens = sum(
    request["input_tokens"] + request["output_tokens"]
    for request in requests
)
kv_heads = 8
head_dim = 128
bytes_per_value = 2
kv_cache_mib = (
    2 * layers * active_tokens * kv_heads * head_dim * bytes_per_value / 1024**2
)

diagnostics = {
    "p95_latency_under_3s": metrics["p95_latency_ms"] <= 3000,
    "avg_ttft_under_300ms": metrics["avg_ttft_ms"] <= 300,
    "p95_tpot_under_25ms": metrics["p95_tpot_ms"] <= 25,
    "kv_cache_under_1gib": kv_cache_mib <= 1024,
}

print(f"request_count={len(requests)}")
print(f"wall_s={wall_s:.2f}")
print(f"metrics={metrics}")
print(f"longest_request={max(requests, key=lambda item: item['latency_s'])['id']}")
print(f"active_tokens={active_tokens}")
print(f"kv_cache_mib={kv_cache_mib:.2f}")
print(f"diagnostics={diagnostics}")
print(f"all_observed_conditions={all(diagnostics.values())}")
~~~

这个 demo 的关键输出应接近：

~~~text
request_count=4
wall_s=3.03
metrics={'qps': 1.32, 'tokens_per_s': 87.46, 'avg_ttft_ms': 230.0, 'p95_latency_ms': 2830.0, 'p95_tpot_ms': 20.0}
longest_request=long_rag
active_tokens=3885
kv_cache_mib=485.62
diagnostics={'p95_latency_under_3s': True, 'avg_ttft_under_300ms': True, 'p95_tpot_under_25ms': True, 'kv_cache_under_1gib': True}
all_observed_conditions=True
~~~

这个 demo 想说明：部署分析不能只看“模型能生成”，而要把请求 trace 拆成 queue、prefill、decode、输出长度和 KV Cache 占用。long_rag 是最长请求，说明长上下文和长输出会明显拉高尾延迟。示例中的 percentile 是教学实现，生产监控应明确采用 nearest-rank、线性插值还是观测系统自己的 histogram 语义。

## 1.15 从模型指标到服务 SLO

模型 benchmark 的准确率和服务 SLO 不是同一个层级。一个量化模型可能在离线 MMLU 或代码集上保持分数，却在真实长上下文、工具 schema 或拒答边界上退化；一个服务可以拥有很好的平均 TTFT，却在高峰期 P99 超时。

部署评估应把离线质量、在线性能和安全结果放在同一份 revision 记录里：

~~~math
E_{\mathrm{service}}
=(E_{\mathrm{quality}},E_{\mathrm{latency}},
E_{\mathrm{capacity}},E_{\mathrm{safety}},E_{\mathrm{cost}})
~~~

这仍然是一个证据向量，不是把不同单位的数字强行相加。质量项可以包含任务正确率、引用支持率、代码测试通过率和 schema 合法率；性能项包含 TTFT、TPOT 和 P99；安全项包含越权、敏感信息和审计缺失；成本项则按请求和成功任务统计。

压测必须和质量回放配对。只用随机短 prompt 压出的 tokens/s，不能代表长 RAG 或 Agent；只用固定 benchmark 测质量，又不能告诉我们排队和超时。请求 trace 中应记录输入/输出长度、是否命中 prefix cache、batch size、队列等待、GPU 拓扑、精度和引擎 revision。

## 1.16 常见部署误区

### 1.16.1 能运行 generate 就算部署

不对。它只证明单次执行路径成立。生产还需要并发、超时、取消、资源上限、鉴权、监控、质量回放、安全策略和回滚。

### 1.16.2 吞吐越高越好

不一定。增加 batch 可能提升 output tokens/s，却让短请求排队更久；为了追求吞吐而超过 KV 预算，可能导致 OOM 和尾延迟恶化。吞吐必须和 TTFT、P99、错误率和单位成功成本一起看。

### 1.16.3 量化只改变显存

不对。量化可能改变 logits、长上下文行为、数学和代码能力、工具参数格式以及 kernel 的实际性能。量化版本必须在代表性质量集和同一 workload 下比较。

### 1.16.4 只看平均 latency

平均值无法描述突发、长输入、长输出和工具等待。至少要看 P95/P99、超时率、队列时间和按 workload class 的分布。

### 1.16.5 上线后就完成了部署

上线只是新的观测阶段。模型、引擎、GPU 驱动、chat template、数据、工具和流量都会变化，服务需要持续回归、灰度、容量重估和安全审计。

## 1.17 面试中如何讲一个部署方案

回答“如何把一个大模型部署成线上服务”时，可以沿着以下因果顺序展开，而不是直接罗列引擎名称：

1. 先明确 workload：输入/输出长度、峰值 QPS、并发、流式要求、TTFT/TPOT/P99 和成本；
2. 再确认 artifact：权重、tokenizer、chat template、generation config、精度和模型协议；
3. 根据单卡显存、KV 预算和 GPU 拓扑选择单机、TP、PP 或多副本；
4. 根据模型结构、硬件、协议和维护周期选择 vLLM、SGLang、TensorRT-LLM、llama.cpp 或其他 runtime；
5. 配置 batching、队列、KV Cache、超时、取消、限流和 backpressure；
6. 接入鉴权、租户隔离、日志、trace、质量回放、安全过滤和成本统计；
7. 用代表性 workload 做压测，用独立质量和安全集合做回归；
8. 通过灰度观察新旧版本差异，准备 drain、回滚、缓存处理和工具幂等策略。

好的回答应解释取舍：短问答和长 RAG 的容量模型不同，TPOT 和 TTFT 的瓶颈不同，PagedAttention 和 GQA 解决的问题不同，量化带来的收益必须和质量代价比较，TGI 的当前维护状态会影响新项目选择。部署不是“会启动一个服务”，而是能把模型能力转成可观测、可回退、可运营的系统。

## 1.18 资料与进一步阅读

以下资料分别用于核对引擎能力、内存管理、协议和服务生命周期。官方文档说明当前接口和维护状态，论文说明方法来源；它们都不能替代当前硬件和 workload 的压测。

1. [vLLM Documentation](https://docs.vllm.ai/en/stable/)：核对 vLLM 的 serving、continuous batching、prefix caching、量化和硬件后端；当前 latest developer preview 与 stable 文档需要区分。
2. [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180)：PagedAttention 的原始论文，说明 KV Cache 虚拟分页和 serving 吞吐问题。
3. [TensorRT-LLM Documentation](https://nvidia.github.io/TensorRT-LLM/)：核对 NVIDIA 生态中的构建、kernel、量化、并行和 runtime 约束。
4. [SGLang Documentation](https://docs.sglang.ai/)：核对结构化生成、prefix/radix 类缓存、Agent/程序化调用和 serving 配置。
5. [Text Generation Inference Documentation](https://huggingface.co/docs/text-generation-inference/index)：核对 TGI 的历史功能和当前维护说明；当前文档明确标注 maintenance mode，新项目应评估迁移方向。
6. [Hugging Face Transformers Chat Templates](https://huggingface.co/docs/transformers/main/en/chat_templating)：核对消息序列、generation prompt、工具和 special token 的输入协议。

读者应把“框架当前支持什么”“论文证明了什么”“当前集群实测什么”分开记录。一个官方页面列出某个优化，不代表所有模型、GPU 和 batch 都能获得同样收益；一个 benchmark 提升，也不代表线上协议、安全和回滚已经解决。

## 1.19 小结

部署的对象不是孤立 checkpoint，而是带 tokenizer、template、精度、引擎、策略和评估证据的一组模型 artifact。部署的目标也不是单一的 tokens/s，而是在 workload、SLO、质量、安全和成本约束下，让请求稳定完成。

从 checkpoint 到服务，需要理解 prefill/decode、TTFT/TPOT、P95/P99、吞吐、队列、KV Cache、显存、并行、协议、鉴权、限流、监控、灰度和回滚。只有把这些因素放在同一条请求生命周期中，才能解释为什么一个模型“能跑”却还不能上线。
