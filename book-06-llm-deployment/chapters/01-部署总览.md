# 第 1 章 部署总览：从模型 artifact 到可运营服务

训练结束时得到的是 checkpoint，用户需要的却是一个能够接收请求、遵守协议、在预算内返回结果、持续接受监控并且可以回滚的服务。把 checkpoint 加载进显卡并调用 generate，只证明模型在某个开发环境中能执行一次推理，不能证明它适合真实流量。

部署工程把模型能力放进一个具体的 workload：输入有多长，输出有多长，流量什么时候到达，是否需要流式输出，能否排队，能否重试，是否允许调用工具，失败时怎样降级。模型精度、推理引擎、KV Cache、批处理、GPU 拓扑、API、鉴权、日志、质量、安全和成本，最终都要在这组约束下作出取舍。

初学者可以把服务想成一条生产线：请求进入网关，经过排队和调度，模型完成 prefill 和 decode，结果经过协议与安全检查后返回。工程人员还要追问每个环节的资源消耗和失败责任：首 token 慢是排队还是 prefill，后续 token 慢是显存带宽还是调度，质量退化是量化还是 chat template，超时是模型慢还是工具没有返回。

## 1.0 部署决策从 workload 开始

部署不应该从“团队熟悉哪个框架”开始，而应该先描述服务将承受的工作负载。至少要固定以下变量：

| 变量 | 需要回答的问题 |
| --- | --- |
| 输入长度 | 平均值、P95、最大值，是否包含检索文档或图片 token |
| 输出长度 | 平均值、P95、最大值，是否流式返回 |
| 到达率 | 平均和峰值请求数，是否有明显突发 |
| 并发 | 同时处于排队、prefill、decode 和工具等待的请求数 |
| 交互目标 | TTFT、TPOT、完整响应和超时预算 |
| 质量 | 事实、代码、结构化输出、引用和拒答要求 |
| 工具 | 是否调用数据库、浏览器、代码沙箱或企业 API |
| 故障策略 | 是否允许排队、降级、重试、异步完成和回滚 |
| 成本 | GPU、CPU、存储、网络、教师/工具调用和人工复核成本 |

可以将一类请求表示为 workload 向量：

~~~math
W=(\lambda,T_{\mathrm{in}},T_{\mathrm{out}},
B_{\mathrm{active}},S_{\mathrm{TTFT}},S_{\mathrm{E2E}},Q)
~~~

lambda 是请求到达率，T_in 和 T_out 是输入与输出 token 数，B_active 是同时活跃的请求数，S_TTFT 和 S_E2E 是首 token 与完整响应的目标，Q 表示质量、安全和协议要求。这个向量不是部署配置，而是选择配置的输入。

本章先建立决策地图：第 [2 章](02-推理基础.md)展开计算路径、时间戳和 roofline；第 [3 章](03-kv-cache与内存管理.md)、[5 章](05-推理引擎.md)、[6 章](06-批处理与调度.md)分别深入 KV 状态、运行时选型和调度；[第 8 章](08-并行推理与多gpu服务.md)讲多 GPU 拓扑，[第 11 章](11-监控评估与安全.md)讲观测与发布，[第 14 章](14-部署方案推导与故障复盘.md)把这些决策放进完整案例。本章只在需要做总览决策时解释机制，具体实现以这些章节为主讲位置。

不同 workload class 不应被混在一个平均数里。普通短问答主要受 decode 和并发影响；长 RAG 主要受 prefill、上下文占用和 TTFT 影响；代码生成受输出长度、停止条件和工具执行影响；Agent 任务还会产生多轮工具等待和外部副作用；多模态请求需要把视觉、音频或视频 token 的编码时间放进前处理。

没有输入/输出长度、峰值到达率和质量目标时，回答“需要几张 GPU”没有可验证的含义。参数量只能给出权重存储的一个起点，不能代替真实 workload 压测。

## 1.1 为什么 checkpoint 不是服务

一个 checkpoint 至少要和以下 artifact 一起交付：

| artifact | 作用 | 不一致时的表现 |
| --- | --- | --- |
| 权重和配置 | 定义模型结构、层数、词表和精度 | 无法加载或输出异常 |
| tokenizer | 把文本映射为 token id | 长度、字符和特殊 token 行为改变 |
| chat template | 组织 system/user/assistant/tool 消息 | 模型把角色或工具结果理解错 |
| generation config | temperature、top-p、stop 和长度 | 输出分布与评估不一致 |
| 精度/量化配置 | 定义计算和存储格式 | 质量、显存和 kernel 不匹配 |
| 引擎适配层 | 将模型结构映射到 runtime | 某些算子或 cache layout 不兼容 |
| 安全与协议配置 | 定义输入、输出和权限边界 | 可能出现越权或数据泄露 |
| 评估与回归集合 | 比较版本行为 | 性能提升但质量退化无法发现 |

一个完整的部署链路可以表示为：

~~~text
checkpoint and config
  -> weight conversion and precision selection
  -> tokenizer and chat-template alignment
  -> inference engine loading
  -> batching, scheduling and KV state allocation
  -> API, authentication and request policy
  -> metrics, logs, traces and quality evaluation
  -> canary traffic and rollback
  -> continuous capacity, quality and security operations
~~~

每一个箭头都是接口，而不是一句流程口号。权重转换可能改变参数名和 tied embedding；chat template 可能改变 assistant mask 和 tool call；引擎可能要求特定 attention、quantization 或 cache layout；网关可能截断输入或重写超时；日志系统可能把敏感 prompt 持久化。

因此，模型版本最好不是一个短字符串，而是一个可追溯元组：

~~~math
R_{\mathrm{model}}=
(r_{\mathrm{weights}},r_{\mathrm{tokenizer}},r_{\mathrm{template}},
r_{\mathrm{engine}},r_{\mathrm{precision}},r_{\mathrm{policy}})
~~~

每个 revision 都应能指向真实 artifact。只有权重 revision 变化而其他字段不变，和 chat template 变化造成的回归，应该在报告中被区分。

## 1.2 离线推理和在线服务

离线推理与在线服务都使用模型 forward，但目标函数不同：

| 类型 | 典型任务 | 首要指标 |
| --- | --- | --- |
| 离线推理 | 批量评测、数据合成、离线标注、文档处理 | 总 tokens/s、总成本、完成时间 |
| 在线服务 | 聊天、代码助手、企业问答、实时 Agent | TTFT、TPOT、P95/P99、错误和超时 |
| 异步任务 | 长文档分析、批量报告、复杂 Agent | 排队可见性、完成时间、重试和幂等 |

离线批处理通常可以等待更多请求组成大 batch，接受更高单请求延迟，重点是 GPU 利用率和单位 token 成本。在线服务必须及时开始输出，不能为了提高总体吞吐而无限等待 batch；它还要处理突发、取消、断开连接和长尾请求。

异步任务处在两者之间。用户可以接受等待，但系统要返回任务 id、进度和最终 artifact，支持重试和幂等。把长 Agent 任务伪装成普通同步 HTTP 请求，往往会导致连接占用、超时重试和重复副作用。

请求吞吐和 token 吞吐也不是一回事：

~~~math
\mathrm{QPS}=\frac{N_{\mathrm{req}}}{T_{\mathrm{wall}}}
~~~

~~~math
\mathrm{TPS}_{\mathrm{out}}
=\frac{N_{\mathrm{out,total}}}{T_{\mathrm{wall}}}
~~~

QPS 表示每秒完成多少请求，输出 TPS 表示每秒生成多少 output token。两个系统可能有相同的 QPS，却因为输出长度不同而消耗完全不同的 GPU 时间。长上下文服务还应单独记录输入 token/s 或 prefill token/s，否则 output TPS 会掩盖输入处理瓶颈。

以上两个比率都要求 `T_{wall}>0`；如果观测窗口没有完成请求，应报告吞吐未定义，而不是报告为零。

## 1.3 一次请求经历了什么

把在线请求拆成生命周期，很多“模型很慢”的判断就会变成可定位的问题：

~~~text
admit -> authenticate -> queue
      -> tokenize and validate
      -> prefill prompt and allocate KV state
      -> decode one token at a time
      -> stream, stop or call tool
      -> finalize, audit and release state
~~~

### 1.3.1 TTFT

TTFT（Time To First Token）是从请求进入服务到用户收到第一个输出 token 的时间。它通常包含排队、输入 tokenization、prefill、首 token decode 和网络发送：

~~~math
T_{\mathrm{TTFT}}
=T_{\mathrm{admit}}+T_{\mathrm{queue}}+T_{\mathrm{tokenize}}
+T_{\mathrm{prefill}}+T_{\mathrm{first}}+T_{\mathrm{network,first}}
~~~

在某些系统中，tokenization 和 admission 很小，可以合并到固定开销；在长 RAG 或多模态请求中，输入预处理可能不再小。TTFT 高可能是 prefill 慢，也可能只是请求在队列里等待。只有拆开 trace，才能决定是优化模型、调度还是网关。

### 1.3.2 TPOT

TPOT（Time Per Output Token）描述已经开始流式输出后，后续 token 的平均生成间隔。若第一个 token 已计入 TTFT，输出 token 数为 N_out，decode 总时间为 T_decode，则可用：

~~~math
T_{\mathrm{TPOT}}
=\frac{T_{\mathrm{decode}}}{N_{\mathrm{out}}-1},
\qquad N_{\mathrm{out}}>1
~~~

只有至少生成两个 output token 时，才存在一个后续 token 间隔；零 token 或只有一个 token 的请求应将 TPOT 标为 `not_applicable`，不能用 `max` 把不存在的间隔伪装成一个数。TPOT 受 decode 阶段的 memory bandwidth、KV Cache 读取、batch 形状、GPU kernel、通信和调度影响。平均 TPOT 不能说明每个 token 都一样快；长输出中途的 batch 加入、抢占、工具等待和 cache eviction 可能造成局部抖动。

TPOT 是**每请求一个平均值**，而 ITL（Inter-token Latency）是流中相邻输出事件之间的间隔分布，两者不能把名字当作同一个统计量。假设一次请求共生成 5 个 token，客户端收到 3 个事件，每个事件分别带 2、2、1 个 token，事件间隔都是 30 ms。ITL 样本是 `[30, 30] ms`；如果首 token 已计入 TTFT，request-level TPOT 则把首 token 后到结束的 60 ms 除以 4 个 token 间隔，得到 15 ms。使用 speculative decoding 或服务端合并 SSE chunk 时，一个事件也可能携带多个 token，差异会更明显。vLLM 当前指标文档分别记录事件级 ITL 和请求级 TPOT，并指出两者的样本数与聚合权重不同；SGLang 的 serving benchmark 也同时输出两种指标。[vLLM 指标定义](https://docs.vllm.ai/en/latest/design/metrics/)、[SGLang 压测代码与指标文档](https://github.com/sgl-project/sglang/blob/main/docs/docs/developer_guide/bench_serving.mdx)。

平均值还可能掩盖一次很长的停顿。若 21-token 请求的 20 个间隔中，19 个为 20 ms、一个为 500 ms，平均 request-level TPOT 仍是 44 ms，但用户实际会遇到一次 500 ms 空档；这时应同时看逐请求最大间隔，或在一个事件对应一个 token 时查看 ITL/TBT 尾部。反过来，ITL/TBT 也不能脱离客户端信息消费速度直接定义“坏体验”。一项 2025 年更新的研究用用户处理输出的速度构造 token-level deadline，并提出 smooth goodput；它是在 A100、vLLM 0.6.3、两种开源模型和 ShareGPT/LooGLE workload 上评估的研究指标，不是所有服务的通用标准。[SLO 与 smooth-goodput 研究 v2](https://arxiv.org/abs/2410.14257)。

零 token 或单 token 请求在数学上没有后续 token 间隔，正文和 toy demo 将 TPOT 记为 `not_applicable`。运行时监控字段可能采用不同编码：vLLM 当前文档说明其 Prometheus request-level TPOT 对不超过一个输出 token 的请求记为 0，而 `vllm bench serve` 的 TPOT 汇总会排除这些请求；SGLang benchmark 也把单 token response 的 TPOT 设为 0。因此比较 dashboard 与 benchmark 前，要检查零值是“真实的 0 ms”还是“无间隔样本”的占位；最好另报 eligible request 数，避免把极短/失败响应当成极快 TPOT。[vLLM 指标聚合边界](https://docs.vllm.ai/en/latest/design/metrics/)、[SGLang benchmark 的 TPOT 约定](https://github.com/sgl-project/sglang/blob/main/docs/docs/developer_guide/bench_serving.mdx)。

### 1.3.3 完整延迟与尾延迟

完整响应延迟还包括剩余 decode、网络和可能的工具往返：

~~~math
T_{\mathrm{E2E}}
=T_{\mathrm{TTFT}}+T_{\mathrm{decode,rest}}
+T_{\mathrm{network,rest}}+T_{\mathrm{tool}}
~~~

平均值容易被少量快请求拉低，P95/P99 才能告诉我们最慢的一部分用户经历了什么。生产监控应保存请求级 trace，并按输入长度、输出长度、模型 revision、路由副本、是否命中 prefix cache 和是否调用工具分桶。

流式服务还应明确“首 token 已生成”和“首 token 已到达客户端”的差别。服务器内部 decode 很快，但代理缓冲、网络拥塞或错误的 SSE flush 策略，仍然会让用户感觉 TTFT 很高。

## 1.4 延迟与吞吐的资源画像

Transformer 推理大致分为 prefill 和 decode：

| 阶段 | 主要输入 | 资源特征 | 常见瓶颈 |
| --- | --- | --- | --- |
| prefill | 一次处理整段输入 | 大矩阵计算、并行度高 | 算力、输入长度、attention |
| decode | 每次生成一个新 token | 反复读取权重和 KV 状态 | 显存带宽、KV、batch 调度 |

prefill 主要决定长 prompt 的 TTFT；decode 决定流式输出速度。增加 batch 可能提高 decode 的 GPU 利用率，也可能让短请求等待长请求；chunked prefill 试图在输入计算和已有 decode 请求之间做更细的调度。

定位时要把“用户看到的慢”拆成同一条 trace 上的阶段：queue time 增长而 prefill time 稳定，先查到达突发、准入和排队；prompt token 数与 prefill time 一起增长，优先检查输入长度、前缀复用和 prefill 资源；decode time、ITL/TPOT 与 KV 使用或抢占同时恶化，再检查活跃 batch、KV 带宽/容量和调度。单看 GPU 利用率不能区分这些路径。vLLM 的公开指标把 queue、prefill、decode、请求长度、KV block 使用、等待请求和抢占分别暴露出来，可作为一种可观察性实例；具体名称和语义要按部署版本核对。[vLLM Production Metrics](https://docs.vllm.ai/en/latest/usage/metrics/)。

Little 定律可以帮助建立一个粗略直觉。在稳定、守恒的队列中，平均并发数 L、到达率 lambda 和平均系统时间 W 近似满足：

~~~math
L=\lambda W
~~~

这个关系不告诉我们模型内部如何调度，也不能替代尾延迟约束，但它说明提高并发往往会提高排队和资源占用。如果服务的平均响应时间变长，即使到达率不变，活跃请求和 KV Cache 压力也会增加。

对于输出吞吐为 S_replica 的单副本，若平均输出到达率为 lambda T_out，理论副本下界可以写成：

~~~math
R_{\mathrm{throughput}}
=\left\lceil
\frac{\lambda T_{\mathrm{out}}}{S_{\mathrm{replica}}}
\right\rceil
~~~

这个式子要求 `\lambda\geq0`、`T_{out}\geq0`、`S_{replica}>0`，且各量使用同一时间单位和同一 workload 分布。这只是输出 token 的理想下界，没有计入输入 prefill、排队、峰值、故障和质量回归。实际容量要使用同一 workload 下的实测 S_replica，并为尾延迟和故障留余量。

`S_replica` 必须表示**满足指定延迟目标时的可持续输出吞吐**，不能取一次压测里最大的 tokens/s，也不能直接用 GPU 峰值。部署负载同时包含输入和输出，可先分别记输入需求 `D_in=λE[T_in]`、输出需求 `D_out=λE[T_out]`。只有当 `S_in`、`S_out` 是在明确、可分离的阶段配置下测得时，才可用 `max(D_in/S_in, D_out/S_out)` 作初始下界；普通共置服务里的 prefill 和 decode 会竞争 GPU、KV 和 batch 预算，两个单阶段峰值不能直接拼成真实容量。最终应在目标长度分布和到达过程下测出满足 SLO 的最大负载。

容量目标也不应只写成 token/s。给定一次测量窗口 T，若每个请求预先定义了 TTFT、request-level TPOT、E2E 等门槛，请求成功且满足所有门槛才计为 good request；超时、错误和取消应记为未达标，并另报错误/取消率。最简单的请求级 SLO goodput 是：

~~~math
G_{\mathrm{req}}
=\frac{\#\{r:\ r\text{ 成功且满足所有请求级 SLO}\}}{T}
~~~

SLO attainment 则是 good request 数除以测量窗口内全部发送请求数；它回答“有多少比例的用户达标”，goodput 回答“每秒有多少请求达标”。

例如两种配置都处理 100 个请求、测量 10 秒：A 产生 6,000 output token/s，但只有 60 个请求满足延迟目标，goodput 为 6 req/s；B 产生 5,000 output token/s，却有 90 个请求达标，goodput 为 9 req/s。若目标是交互体验，B 的可用容量更高。这里的数字是说明统计口径的教学例子。当前 SGLang `bench_serving` 已提供可配置 TTFT、TPOT、E2E 门槛的 request-goodput 和 SLO-attainment 统计，且失败请求计为未达标；若服务 SLO 定义为 fleet-level P95/P99，还需按分布单独检查分位数，不能用上式替代。arXiv v2 的指标研究指出，硬阈值 goodput 可能诱导调度器放弃难以达标的请求，并提出 smooth-goodput，因此 goodput 也要和完成率、取消率一起读。[SGLang goodput 定义](https://github.com/sgl-project/sglang/blob/main/docs/docs/developer_guide/bench_serving.mdx)、[SLO 与 smooth-goodput 研究 v2](https://arxiv.org/abs/2410.14257)。

## 1.5 容量规划：从 SLO 倒推副本

假设短问答流量平均为每秒 20 个请求，平均输入 600 token、平均输出 120 token，单副本在同样长度分布下实测输出吞吐为 2,400 token/s。只用平均输出吞吐估算：

~~~math
R_{\mathrm{throughput}}
=\left\lceil
\frac{20\times120}{2400}
\right\rceil=1
~~~

一个副本在纸面上足够，但这不是上线容量。假设峰值是平均流量的 2.5 倍，目标请求率不超过单副本在 SLO 条件下实测能力的 70%，并额外保留一个故障冗余副本：

~~~math
R_{\mathrm{safe}}
=\left\lceil
\frac{\lambda_{\mathrm{peak}}T_{\mathrm{out}}}
{0.7S_{\mathrm{replica}}}
\right\rceil+R_{\mathrm{reserve}}
~~~

代入 lambda_peak=50、T_out=120、S_replica=2400、R_reserve=1：

~~~math
R_{\mathrm{safe}}
=\left\lceil\frac{50\times120}{0.7\times2400}\right\rceil+1
=5
~~~

这个结果仍然依赖实测。长 RAG 请求会消耗更多 prefill 和 KV；工具 Agent 会让请求在模型之外等待；请求长度分布变化会让一个“平均 2,400 token/s”失去代表性。容量测试应使用短问答、长上下文、长输出、代码和工具调用等 workload class，而不是只用一个平均 prompt。

这里的 `0.7` 是示例安全余量，不是业界固定常数；应从目标集群的负载曲线、突发强度和允许的 SLO 违约率中确定。压测还要固定负载如何产生：固定到达率测试模拟外部流量持续进入，固定并发测试限制同时未完成的请求数，系统变慢时两种模式会产生不同的后续负载。SGLang 当前 benchmark 文档把 `--request-rate` 定义为按泊松过程发请求、把 `--max-concurrency` 定义为在途请求上限；真实容量测试应记录请求率/并发、输入输出长度分布、warm-up、测量窗口、流式模式、失败/超时处理和 SLO 判定。只给一个峰值 tokens/s 无法复现容量结论。[SGLang benchmark 配置与口径](https://github.com/sgl-project/sglang/blob/main/docs/docs/developer_guide/bench_serving.mdx)。

容量规划还要回答故障时发生什么。若一个副本停止接收新请求，已有请求是完成、取消还是迁移；重试会不会重复工具动作；路由器是否知道副本正在 drain；KV state 是否能够迁移。N+1 只是副本数概念，不能自动解决有状态 decode 和外部副作用。

## 1.6 单机部署与分布式部署

### 1.6.1 单机部署

如果权重、运行时工作区和预留 KV Cache 能放进一台机器的 GPU，单机部署通常是最容易调试的起点。它的通信路径短、故障面少，适合小模型、低并发、离线任务和早期验证。

单机并不等于没有容量问题。权重占满显存后，KV Cache、CUDA workspace、通信缓冲和临时 tensor 仍然需要空间；一个能启动的配置可能在第二个长请求到来时 OOM。单机服务也需要超时、限流、健康状态和回滚，只是拓扑更简单。

### 1.6.2 Tensor Parallel

Tensor Parallel（TP）把一个层内的矩阵或 attention head 切到多个 GPU，需要在层间或层内通信。它主要解决单卡放不下模型或单卡算力不足的问题，但性能取决于 GPU 互联和切分方式。NVLink、PCIe 和跨机器网络的通信代价不能用同一个数字估算。

### 1.6.3 Pipeline Parallel

Pipeline Parallel（PP）把不同层放到不同 GPU。它可以容纳更大的层堆叠，但需要处理 stage 间传输、微批调度和流水线气泡。对单条低延迟请求，PP 的额外 stage 往返可能很明显；对合适的批量 workload，它可能更有价值。

### 1.6.4 Replica 与 Expert Parallel

Data Parallel 在推理服务中通常表现为多个完整模型 replica，由路由器分摊请求，用容量和可用性换取显存。它不会让单个 replica 变小，但可以降低单副本排队。

MoE 的 Expert Parallel 把 experts 分散到不同 GPU，需要 token routing 和跨卡通信。总参数很多并不意味着每个 token 都激活全部参数，但路由偏斜、通信和 expert load balance 仍会决定真实吞吐。

| 方式 | 主要解决 | 主要代价 |
| --- | --- | --- |
| TP | 单层规模和单卡显存 | 频繁通信、拓扑依赖 |
| PP | 层数和总模型规模 | stage 延迟、流水线气泡 |
| Replica | 并发、容量和可用性 | 权重副本成本 |
| Expert Parallel | MoE expert 容量 | routing、通信和负载偏斜 |
| Prefill / Decode 分离 | 缓解两个阶段相互干扰，分别配置资源 | KV 传输、两类 worker 的容量匹配与运维 |

Prefill / Decode 分离是服务架构，不是 TP、PP 的替代项。DistServe 指出，共置阶段会让长 prefill 延迟 decode、也会让 decode 反过来占用 prefill 资源；它把 context 与 generation 放在不同 GPU 实例，独立调并行度，并把 prefill 生成的 KV Cache 传给 decode 实例。代价是要为状态传输、网络拓扑和两类 worker 分别规划容量；收益取决于请求形状和 TTFT/TPOT 目标。论文报告的最高 7.4× request rate / 12.6× tighter SLO 绑定作者测试的模型、应用、硬件和目标，不能迁移成一般部署倍率。[DistServe 论文](https://arxiv.org/abs/2401.09670)。当前 TensorRT-LLM 文档也提供 disaggregated serving 路径，并描述 KV 经 RDMA/NVLink 传输及其配置边界；这是该 runtime 的公开能力说明，不代表其他框架具备相同接口或限制。[TensorRT-LLM disaggregated serving](https://nvidia.github.io/TensorRT-LLM/features/disagg-serving.html)。

可以按瓶颈建立初筛顺序：模型或单层放不进一张卡时，再比较 TP/PP/EP 的切分和通信；模型能放入单副本、但并发排队过高时，先评估增加 Replica；长 prefill 明显拖慢活跃 decode 时，先测 chunked prefill，再评估独立 P/D 池；跨副本的 prefix 命中率很高时，要把缓存局部性和路由策略一起测。这个顺序只用于选实验方向，最终配置仍要在同一 workload 和 SLO 下比较。

## 1.7 推理引擎：相似目标，不同生命周期

推理引擎通常负责权重加载、模型执行、KV Cache、batching、调度、解码、多 GPU 和高性能 kernel。它不是简单封装 model.generate，而是决定请求如何共享计算和显存。

| 引擎/生态 | 常见优势 | 选型时需要核对 |
| --- | --- | --- |
| vLLM | 开源 serving、PagedAttention、continuous batching、prefix caching 等能力 | 模型架构、硬件后端、版本和实际 workload |
| SGLang | 结构化程序/Agent 场景、prefix/radix 类缓存和 serving 优化 | API、模型支持、缓存语义和部署版本 |
| TensorRT-LLM | NVIDIA 硬件上的编译和 kernel 优化 | TensorRT/CUDA 版本、构建流程和算子覆盖 |
| llama.cpp | CPU、消费级 GPU 和本地量化部署 | 模型格式、量化 kernel 和并发目标 |
| TGI | Hugging Face 生态中的服务工具和历史生产能力 | 官方文档自 2025-12-11 起标注 maintenance mode；新项目需重新评估 |

这些不是永久不变的排名。vLLM 当前文档列出了 continuous batching、chunked prefill、prefix caching 和多种后端能力；SGLang、TensorRT-LLM 和 llama.cpp 的适用场景也会随版本变化。真正的选择要基于模型支持、硬件、协议、观测、升级能力和压测结果。

Hugging Face [TGI 官方文档](https://huggingface.co/docs/text-generation-inference/main/en/index)明确写出其进入 maintenance mode，并建议后续下游采用 vLLM、SGLang 或其他本地引擎。这个状态说明维护投入和新能力路线已经变化，不等于已有服务必须立即停机；已有部署应评估漏洞修复、依赖更新、硬件支持与迁移回归，新项目则应把维护状态纳入选型记录。

几个代表性方案说明了“优化”具体在改哪一层：

| 研究/机制 | 解决的具体问题 | 主要限制或代价 |
| --- | --- | --- |
| Orca 的 iteration-level scheduling | 静态请求级 batch 需要等长请求结束；按一次模型迭代重新调度，让已完成请求退出、新请求进入 | 需要引擎和调度器在每轮生成间协作；论文对 FasterTransformer 的 GPT-3 结果绑定其模型和硬件配置 |
| PagedAttention / vLLM | 变长请求的 KV 预留和释放造成碎片；用块管理提升 KV 容量利用与请求并发 | 不减少 attention 必须读取的 KV 内容，也不自动保证更低 TTFT/TPOT；要一起看 batching 和工作负载 |
| Sarathi-Serve 的 chunked prefill | 长 prefill 插入活跃 decode batch 时造成生成停顿；切分 prefill 后与 decode 迭代混排 | chunk 大小影响 TTFT 与 ITL/TPOT；论文增益取决于模型、GPU、长度分布和调度配置 |
| DistServe 的 P/D disaggregation | 共置 prefill/decode 相互干扰，且两阶段只能共享一套并行配置；拆为不同实例分别扩缩 | 要传输 KV 并维护两种 worker 池；收益依赖网络、流量形状和资源利用 |

这些方案分别作用于请求调度、内存分配、阶段混排和服务拓扑，不能互相替代。Orca 的实验、Sarathi-Serve 的 serving capacity 结果都只能作为对应论文配置下的证据；代码和文档列出某个能力，也不等于目标模型及硬件已达 SLO。[Orca / OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/yu)、[Sarathi-Serve / OSDI 2024](https://arxiv.org/abs/2403.02310)。

PagedAttention 解决的是 KV Cache 的块式管理和碎片问题，不等于所有 KV 显存都减少；GQA/MQA 通过降低 KV head 数减少每 token 的 KV 字节；prefix caching 只有在前缀真实复用且版本/权限边界一致时才会带来收益。vLLM 当前的缓存实现把前缀 block、父 block hash、LoRA/多模态标识和可选 `cache_salt` 纳入 cache identity；按 salt 隔离可限制不同信任组之间复用。多租户服务仍须由身份与策略层决定 salt 的来源，不能让用户任意选择 salt 来替代授权，也不能把命中率当作权限正确性的证据。[vLLM prefix cache 设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)。把这些优化名词混成同一个“缓存加速”会掩盖它们解决的问题不同。

## 1.8 Tokenizer、chat template 与模型协议

部署时 tokenizer 必须与训练和评估使用的版本、词表、special token 约定相匹配。Chat model 还需要正确的 chat template，把 system、user、assistant、tool 和多轮消息组织成模型训练时见过的序列。

协议问题经常不会报错，却会表现为模型能力异常：

1. tokenizer 版本改变，输入长度和边界 token 改变；
2. special token id 不一致，EOS 或 PAD 的含义改变；
3. chat template 遗漏 generation prompt，模型不知道该轮轮到谁回答；
4. assistant/tool 边界错误，模型把工具结果当成用户指令；
5. tool calling schema 和执行器 schema 不一致；
6. stop sequence、max new tokens 和截断顺序不同。

可以把输入协议的兼容性记录成诊断向量：

~~~math
d_{\mathrm{protocol}}
=(d_{\mathrm{vocab}},d_{\mathrm{special}},
d_{\mathrm{template}},d_{\mathrm{tool}},d_{\mathrm{stop}})
~~~

这些量不必被压成一个总分。只要 template 或 tool schema 不兼容，性能压测再好也不能解释为同一模型的线上表现。回归集应包含多轮对话、空 system、工具调用、工具拒绝、长上下文和 Unicode 边界。

模型 revision 的最小记录应包括 weights、tokenizer、template、generation config、precision、engine 和 policy。只在日志中写一个 model_name，无法在模型输出回归时确定是权重变了还是输入协议变了。

## 1.9 KV Cache 与显存预算

自回归 decode 会反复使用历史 token 的 key/value。KV Cache 避免每次生成新 token 时重新计算全部历史，但它把序列状态留在显存中，活跃请求越多、上下文越长，占用越大。

若第 i 个请求当前保留 T_i 个 token，使用 L 层、H_kv 个 KV heads、head dimension 为 D_h、每个数值 b 字节，则粗略 KV Cache 大小为：

~~~math
M_{\mathrm{KV}}
\approx
2L H_{\mathrm{kv}}D_h b
\sum_{i=1}^{B}T_i
~~~

2 表示 K 和 V，B 是活跃请求数。这个公式没有计入 block metadata、padding、对齐、临时 workspace、复制和通信缓冲；如果采用平均 token 数 T_avg，也可以近似成 2 L B T_avg H_kv D_h b。

GQA 和 MQA 通过减少 H_kv 降低每 token 的 KV 字节，但不等于减少权重或所有 activation。PagedAttention 类方法把 KV 分成可管理的块，主要改善分配和碎片；如果 block size、请求长度和回收策略不合适，仍可能因为内部碎片或峰值并发而 OOM。

上式估算的是一个完整模型副本在某一时刻所有活跃序列的逻辑 KV 字节，不是所有 GPU 上平均分摊后的显存。TP rank 通常只保存切分后的 KV heads，PP rank 只保存本地层的 KV；具体每卡字节数还受 head/layer 切分、复制、cache block 对齐、并行策略和运行时工作区影响。做容量账本时先明确“整副本”还是“每 rank”，再按真实 cache layout 计算，不能把全模型总量简单除以 GPU 数。

整机显存预算还包括：

~~~math
M_{\mathrm{total}}
=M_{\mathrm{weights}}+M_{\mathrm{KV}}+M_{\mathrm{workspace}}
+M_{\mathrm{activation}}+M_{\mathrm{communication}}+M_{\mathrm{reserve}}
~~~

M_reserve 不能被忽略。没有预留空间的服务可能在平均请求下正常，在长 prompt、并发突发或 kernel 临时分配时崩溃。部署压测要记录 OOM 发生在加载、prefill、decode、batch 扩大还是 cache 回收阶段。

## 1.10 生产请求路径

一个线上 LLM 服务通常由多个职责不同的组件组成：

~~~text
client
  -> API gateway: auth, quota, request size, timeout
  -> router: model, replica and tenant selection
  -> admission and queue: backpressure and cancellation
  -> inference worker: tokenize, prefill, decode, stream
  -> tool or retrieval service: optional external actions
  -> policy and response layer: schema, safety and redaction
  -> metrics, trace and audit storage
~~~

网关负责身份、限额、输入大小、超时和请求 id；路由器根据模型 revision、租户、负载和能力选择副本；队列控制突发并提供 backpressure；worker 负责推理；响应层负责协议、脱敏和审计。一个组件可以承担多个职责，但边界要能在故障时被观察。

取消请求是生产服务的关键语义。用户断开连接后，系统是否停止 decode、释放 KV、取消工具调用和记录原因；如果只取消网络发送而继续生成，GPU 仍在消耗，长请求还可能挤压新请求。

重试也不能默认安全。模型生成可以重试，但工具写入、数据库提交和外部消息发送可能已经产生副作用。请求应携带幂等键，工具动作应有明确的提交状态，路由层不能用普通 HTTP 重试把一次写操作执行两次。

## 1.11 监控：性能指标和能力指标要分开

基础设施监控回答“服务是否健康”，能力评估回答“模型是否完成了正确任务”。两类信号都需要，但不能互相替代。

| 维度 | 例子 |
| --- | --- |
| 性能 | TTFT、TPOT、E2E、P95/P99、队列时间 |
| 吞吐 | QPS、输入 token/s、输出 token/s、batch 利用率 |
| 资源 | GPU 利用率、显存、KV blocks、CPU、网络 |
| 稳定性 | 错误率、超时率、取消率、重试率、OOM |
| 协议 | JSON/schema 失败、tool 参数错误、stop 异常 |
| 质量 | exact match、引用支持、代码测试、人工抽样 |
| 安全 | 越权、敏感信息、prompt/tool injection、审计缺失 |
| 成本 | GPU 时间、每请求 token、每成功任务成本 |

GPU utilization 很高不等于服务好。GPU 可能在处理无效重试、过长回答或低质量 batch；GPU 利用率低也可能是请求到达率低而不是 runtime 有问题。指标必须和请求 trace、质量样本和成本关联。

一个实用的诊断顺序是先看哪段时间变长，再找同一请求上的相关状态，而不是看到一个指标就直接归因：

| 观察到的变化 | 先对照的信号 | 可优先排查的路径 |
| --- | --- | --- |
| TTFT 上升 | queue、prompt token、tokenize、prefill、prefix-cache 命中 | 到达突发/准入、路由、长输入、前缀复用失效、prefill 算力 |
| TPOT 或 ITL 上升 | decode time、batch、KV 使用/抢占、stream flush | KV 带宽或容量、长 prefill 干扰、调度、网络/代理缓冲 |
| tokens/s 上升但 goodput 下降 | SLO 达标请求数、超时、取消、质量回归 | 过载、尾延迟变差、失败请求被吞吐计数掩盖 |
| OOM 或等待队列变长 | KV block 使用、最大上下文、活跃序列、workspace | 准入预算、长请求并发、碎片、瞬时 workspace 峰值 |

分位数的采集口径也会改变判断。Prometheus histogram 可以在实例间先合并 bucket 再估算分位数；不要把各副本预先算好的 P95 做算术平均，OpenMetrics 规范明确指出预计算 quantile 不可聚合。[OpenMetrics quantile 说明](https://prometheus.io/docs/specs/om/open_metrics_spec/)。bucket 必须覆盖目标 SLO 附近的范围：vLLM 当前文档举例指出默认最小 request-phase bucket 为 0.3 秒，测量 300 ms 以下目标时可自定义桶；每个 bucket 又会乘上标签组合增加时序数量，所以要在分辨率和监控成本之间选取少量有用边界。[vLLM histogram 配置](https://docs.vllm.ai/en/latest/usage/metrics/)。

每次模型、模板、精度、引擎、调度或安全策略变化，都应保存对应 revision。线上出现质量下降时，按 revision 对比短问答、长上下文、代码、工具和拒答边界，而不是只看总平均分。

## 1.12 质量、安全与发布判断

换成量化版本、启用 speculative decoding 或修改 chat template 时，性能可能上升，但不能只比较 tokens/s。固定 replay 集至少覆盖：

1. 普通问答和多轮对话；
2. 长上下文引用与中部证据；
3. 数字、数学和代码；
4. JSON、函数调用和工具参数；
5. 拒答、隐私和越权边界；
6. 多模态或特殊 token 协议（如果服务支持）。

对每个请求同时保存 model revision、tokenizer revision、template revision、精度、解码参数、服务拓扑和工具版本，才能解释回归。性能与质量最好用同一 workload 重新测量；量化后的 token 速度提升若伴随代码测试或引用支持下降，不能把它称为单纯优化。

安全检查应覆盖输入、输出、工具和租户边界。Prompt injection 可能出现在用户输入、检索文档、网页和工具返回中；tool injection 可能让模型把数据字段误当作动作指令。模型服务本身可以做内容和 schema 检查，但最终权限仍要由执行器和网关决定。

发布判断可以保留为一个证据向量：

~~~math
d_{\mathrm{release}}
=(d_{\mathrm{fit}},d_{\mathrm{latency}},d_{\mathrm{capacity}},
d_{\mathrm{quality}},d_{\mathrm{safety}},d_{\mathrm{rollback}})
~~~

每个分量都应指向具体测量和回退动作。安全、协议和回滚证据缺失时，性能数据不能替代它们；发布并不是把多个数字相加，而是检查目标是否都被满足。

## 1.13 灰度、回滚与版本生命周期

模型上线不是一次性事件，而是从小流量开始观察的过程。常见灰度方式包括按比例、用户组、业务场景、地域或租户分流。灰度期间必须同时记录新旧版本的请求形状，因为如果新版本收到的是更短、更容易的请求，平均指标会产生假象。

回滚需要提前定义：

1. 哪些指标触发停止扩大流量；
2. 新请求切回旧版本还是等待当前请求；
3. 正在执行的工具动作如何处理；
4. KV state、队列和缓存是否可继续使用；
5. 质量回归样本如何保留；
6. 回滚后怎样确认旧版本恢复。

滚动升级时，旧版本不能过早删除。至少要等正在生成的请求完成或被安全取消，确认缓存和日志版本可区分，再释放资源。对有状态 Agent，模型回滚还要考虑 workspace、工具协议和记忆格式是否兼容。

## 1.14 一个最小部署指标 demo

下面的 0 依赖 demo 用四个 toy 请求模拟模型服务端的成功请求 trace，计算 TTFT、request-level TPOT、P95 完成延迟、有限请求 cohort 的完成速率和输出 token 速率，以及活跃请求重叠时的 KV Cache 长度包络。它不包含客户端网络、RAG/工具执行、失败请求或真实 GPU 调度，因此 cohort 速率不是稳态容量或服务 QPS，也不是 GPU benchmark。

~~~python
from copy import deepcopy
import math


class TraceContractError(ValueError):
    """A serving trace cannot support the requested metric."""


def finite_nonnegative(value, name):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise TraceContractError(f"{name} must be a finite non-negative number")
    value = float(value)
    if not math.isfinite(value) or value < 0:
        raise TraceContractError(f"{name} must be a finite non-negative number")
    return value


def nonnegative_int(value, name):
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise TraceContractError(f"{name} must be a non-negative integer")
    return value


def required(record, name):
    if name not in record:
        raise TraceContractError(f"trace is missing {name}")
    return record[name]


def validate_request(request):
    if not isinstance(request, dict):
        raise TraceContractError("trace must be a mapping")
    request_id = required(request, "id")
    if not isinstance(request_id, str) or not request_id.strip():
        raise TraceContractError("id must be non-empty text")
    for name in ("arrival_s", "queue_s", "prefill_s", "first_emit_s", "decode_step_s"):
        finite_nonnegative(required(request, name), name)
    input_tokens = nonnegative_int(required(request, "input_tokens"), "input_tokens")
    output_tokens = nonnegative_int(required(request, "output_tokens"), "output_tokens")
    if output_tokens == 0:
        raise TraceContractError("this successful-generation demo requires at least one output token")
    return input_tokens, output_tokens


def percentile_nearest_rank(values, q):
    if not values:
        raise TraceContractError("percentile needs at least one observation")
    q = finite_nonnegative(q, "percentile q")
    if not 0 < q <= 100:
        raise TraceContractError("percentile q must be in (0, 100]")
    ordered = sorted(finite_nonnegative(value, "percentile observation") for value in values)
    rank = math.ceil(q / 100 * len(ordered))
    return ordered[rank - 1]


def derive_trace(request):
    input_tokens, output_tokens = validate_request(request)
    trace = dict(request)
    trace["ttft_s"] = trace["queue_s"] + trace["prefill_s"] + trace["first_emit_s"]
    trace["decode_s"] = (output_tokens - 1) * trace["decode_step_s"]
    trace["latency_s"] = trace["ttft_s"] + trace["decode_s"]
    trace["tpot_s"] = (
        trace["decode_s"] / (output_tokens - 1)
        if output_tokens > 1
        else None
    )
    trace["engine_start_s"] = trace["arrival_s"] + trace["queue_s"]
    trace["engine_finish_s"] = trace["arrival_s"] + trace["latency_s"]
    trace["observed_token_envelope"] = input_tokens + output_tokens
    return trace


def summarize(requests, layers, kv_heads, head_dim, bytes_per_value):
    if not isinstance(requests, list) or not requests:
        raise TraceContractError("requests must be a non-empty list")
    for name, value in (("layers", layers), ("kv_heads", kv_heads), ("head_dim", head_dim), ("bytes_per_value", bytes_per_value)):
        if isinstance(value, bool) or not isinstance(value, int) or value <= 0:
            raise TraceContractError(f"{name} must be a positive integer")

    traces = [derive_trace(request) for request in requests]
    ids = [trace["id"] for trace in traces]
    if len(ids) != len(set(ids)):
        raise TraceContractError("trace ids must be unique")

    start_s = min(trace["arrival_s"] for trace in traces)
    end_s = max(trace["arrival_s"] + trace["latency_s"] for trace in traces)
    wall_s = end_s - start_s
    if wall_s <= 0:
        raise TraceContractError("observation window must have positive duration")

    latencies = [trace["latency_s"] for trace in traces]
    ttfts = [trace["ttft_s"] for trace in traces]
    tpot_values = [trace["tpot_s"] for trace in traces if trace["tpot_s"] is not None]
    total_output_tokens = sum(trace["output_tokens"] for trace in traces)
    metrics = {
        "cohort_requests_per_s": round(len(traces) / wall_s, 2),
        "cohort_output_tokens_per_s": round(total_output_tokens / wall_s, 2),
        "avg_ttft_ms": round(sum(ttfts) / len(ttfts) * 1000, 1),
        "p95_latency_ms": round(percentile_nearest_rank(latencies, 95) * 1000, 1),
        "p95_tpot_ms": (
            round(percentile_nearest_rank(tpot_values, 95) * 1000, 1)
            if tpot_values
            else None
        ),
    }
    events = []
    for trace in traces:
        if trace["engine_finish_s"] <= trace["engine_start_s"]:
            raise TraceContractError("a successful request must spend positive time in the engine")
        tokens = trace["observed_token_envelope"]
        # End events sort before start events at the same timestamp.
        events.append((trace["engine_finish_s"], 0, trace["id"], tokens))
        events.append((trace["engine_start_s"], 1, trace["id"], tokens))

    live_requests = {}
    live_tokens = 0
    peak_live_tokens = 0
    peak_live_request_ids = []
    for _, is_start, request_id, token_envelope in sorted(events):
        if is_start:
            live_requests[request_id] = token_envelope
            live_tokens += token_envelope
        else:
            live_tokens -= live_requests.pop(request_id)
        if live_tokens > peak_live_tokens:
            peak_live_tokens = live_tokens
            peak_live_request_ids = sorted(live_requests)

    kv_cache_upper_bound_mib = (
        2 * layers * peak_live_tokens * kv_heads * head_dim * bytes_per_value / 1024**2
    )
    diagnostics = {
        "p95_latency_under_3s": metrics["p95_latency_ms"] <= 3000,
        "avg_ttft_under_300ms": metrics["avg_ttft_ms"] <= 300,
        "p95_tpot_observed": metrics["p95_tpot_ms"] is not None,
        "p95_tpot_under_25ms": metrics["p95_tpot_ms"] is not None and metrics["p95_tpot_ms"] <= 25,
        "peak_kv_envelope_under_1gib": kv_cache_upper_bound_mib <= 1024,
    }
    return {
        "traces": traces,
        "cohort_window_s": wall_s,
        "metrics": metrics,
        "peak_live_tokens": peak_live_tokens,
        "peak_live_request_ids": peak_live_request_ids,
        "kv_cache_upper_bound_mib": kv_cache_upper_bound_mib,
        "diagnostics": diagnostics,
    }
~~~

## 1.15 从模型指标到服务 SLO

模型 benchmark 的准确率和服务 SLO 不是同一个层级。一个量化模型可能在离线 MMLU 或代码集上保持分数，却在真实长上下文、工具 schema 或拒答边界上退化；一个服务可以拥有很好的平均 TTFT，却在高峰期 P99 超时。

部署评估应把离线质量、在线性能和安全结果放在同一份 revision 记录里：

~~~math
E_{\mathrm{service}}
=(E_{\mathrm{quality}},E_{\mathrm{latency}},
E_{\mathrm{capacity}},E_{\mathrm{safety}},E_{\mathrm{cost}})
~~~

这仍然是一个证据向量，不是把不同单位的数字强行相加。质量项可以包含任务正确率、引用支持率、代码测试通过率和 schema 合法率；性能项包含 TTFT、TPOT 和 P99；安全项包含越权、敏感信息和审计缺失；成本项则按请求和成功任务统计。

压测必须和质量回放配对。只用随机短 prompt 压出的 tokens/s，不能代表长 RAG 或 Agent；只用固定 benchmark 测质量，又不能告诉我们排队和超时。请求 trace 中应记录输入/输出长度、是否命中 prefix cache、batch size、队列等待、GPU 拓扑、精度和引擎 revision。

## 1.16 常见部署误区

### 1.16.1 能运行 generate 就算部署

不对。它只证明单次执行路径成立。生产还需要并发、超时、取消、资源上限、鉴权、监控、质量回放、安全策略和回滚。

### 1.16.2 吞吐越高越好

不一定。增加 batch 可能提升 output tokens/s，却让短请求排队更久；为了追求吞吐而超过 KV 预算，可能导致 OOM 和尾延迟恶化。吞吐必须和 TTFT、P99、错误率和单位成功成本一起看。

### 1.16.3 量化只改变显存

不对。量化可能改变 logits、长上下文行为、数学和代码能力、工具参数格式以及 kernel 的实际性能。量化版本必须在代表性质量集和同一 workload 下比较。

### 1.16.4 只看平均 latency

平均值无法描述突发、长输入、长输出和工具等待。至少要看 P95/P99、超时率、队列时间和按 workload class 的分布。

### 1.16.5 上线后就完成了部署

上线只是新的观测阶段。模型、引擎、GPU 驱动、chat template、数据、工具和流量都会变化，服务需要持续回归、灰度、容量重估和安全审计。

## 1.17 一个企业 RAG 服务的部署推导

把前面的概念放在一起，考虑一个企业知识库问答服务：工作日平均每秒 12 个请求，峰值每秒 30 个请求；输入包含检索片段，平均 1,800 token，P95 为 5,000 token；输出平均 220 token，P95 为 500 token；用户希望首 token P95 不超过 1.5 秒，完整响应 P95 不超过 8 秒。服务只允许读取企业文档，不能替用户执行写操作，回答必须带可定位引用。

第一步是把请求形状写成 workload class，而不是只保留一个平均值。至少要区分普通短问题、长上下文问题和检索为空的问题，并记录各类请求的比例。若只用 1,800 输入 token 和 220 输出 token 压测，长上下文请求造成的 prefill、KV Cache 和尾延迟会被平均数掩盖；若只测 5,000 token 的请求，又可能为了极端情况浪费大量常态容量。

第二步是固定可部署 artifact。权重、tokenizer、chat template、generation config、量化方式、引擎版本、检索器版本、引用格式和安全策略组成一个可追溯 revision。这里尤其要固定引用协议：模型必须从检索结果中的 document_id 和 span 生成引用，响应层检查引用是否真的存在，不能只检查回答中出现了一个看起来像 URL 的字符串。模板或检索字段发生变化时，应生成新的 revision，而不是继续复用旧的质量基线。

第三步是先做显存和延迟的可行性实验。假设某个 7B 模型的 BF16 权重、运行时 workspace 和预留空间在单卡上可以容纳，但在目标并发下 5,000 token 请求会让 KV Cache 超过安全余量，那么“单卡能加载”并不等于“单卡能服务”。可以先限制单请求最大上下文、对检索片段做预算分配，再分别测 prefill 和 decode；如果长请求的 TTFT 仍然超标，才考虑更强 GPU、TP、chunked prefill 或长短请求分池，而不是盲目提高 batch。

第四步是用峰值 workload 倒推副本数。假设在相同长度分布和质量配置下，一副本实测可在目标 SLO 内持续处理 4,000 output token/s。按平均输出长度估计，峰值时的期望输出需求为 `30×220=6,600 token/s`；它只代表期望负载，不代表尾部容量。若只按这个平均值、把目标利用率限制为 70%，并为故障保留一个副本，则粗略容量为：

~~~math
R=\left\lceil\frac{6600}{0.7\times4000}\right\rceil+1=4.
~~~

如果把每个请求都设成输出 P95 `500`，就得到 `30×500=15,000 token/s`，并在“副本能力仍为 4,000”的额外假设下算出 `ceil(15,000/(0.7×4,000))+1=7`。这个构造是“所有请求同时落在长输出压力场景”的压力包络，不是 P95 流量估计：单请求 P95 不代表所有请求都处于 P95，也没有给出输入/输出长度相关性；而副本处理全长输出混合分布时的可持续吞吐也未必仍是 4,000。要得到可用副本数，应从真实请求 trace 重放联合长度、到达时间和工具等待，并在目标 SLO 下逐级提高请求率。若长请求和短请求共享队列导致短请求 P99 失控，可以按 workload class 分池，或者使用有上限的 chunked prefill；不能用全局平均 tokens/s 证明服务满足 SLO。

第五步是确定权限和失败语义。检索器可以读取经过租户过滤的文档，模型只能看到当前租户允许的片段；应用层的缓存 identity 要绑定租户、文档版本和策略 revision，避免把一个租户的前缀复用给另一个租户。以 vLLM 为例，运行时提供 `cache_salt` 并把它纳入首个 KV block 的 hash；服务端可由租户与策略版本生成受控 salt，让同一信任组复用、不同组隔离。切换 salt 只改变可复用的 key，不等于从显存或备份中物理删除旧 cache；删除与保留仍须单独定义。[vLLM prefix cache isolation](https://docs.vllm.ai/en/latest/design/prefix_caching/)。引用检查失败时，响应应进入重试、澄清或人工复核路径，而不是把未经支持的回答当成成功。检索超时、模型超时、引用不完整和权限拒绝要使用不同错误码，便于重试策略和运营统计区分。

第六步是设计发布和回退。新量化版本先接收离线 replay，再接收少量影子流量，比较输入长度相同的请求在 TTFT、P99、引用支持率、拒答边界和单位成功成本上的差异。灰度期间若发现速度提高但引用支持率下降，应保留新版本产生的完整 artifact 和 trace，停止扩大流量并切回旧 revision。旧版本不能立即删除，因为正在生成的请求、prefix cache 和排查所需的日志仍可能依赖它；回退完成后还要验证旧版本的权限、引用和延迟指标恢复。

这个例子说明，部署方案不是引擎名称的排列，而是由 workload、artifact、资源、协议、权限、质量和生命周期共同推导出来的。短问答与长 RAG 的容量模型不同，TTFT 与 TPOT 的瓶颈不同，PagedAttention 与 GQA 解决的问题不同；一个优化只有在目标 workload、质量集和安全边界上都被重新测量，才可以称为服务改进。

8. [Sarathi-Serve](https://arxiv.org/abs/2403.02310)：阅读 chunked prefill、stall-free scheduling 和不同长度 workload 下的吞吐/延迟权衡。
9. [DistServe](https://arxiv.org/abs/2401.09670)：阅读 P/D 分离、KV 传输、资源分配和作者评测；论文倍率不迁移到不同集群。
10. [A Survey of LLM Inference Systems](https://arxiv.org/abs/2506.21901)：用作请求处理、batching、调度、KV 内存、量化、单副本/多副本/分离式服务的分类地图；它是综述入口，不替代原论文和固定版本实现核对。
11. [Revisiting Service Level Objectives and System Level Metrics in Large Language Model Serving](https://arxiv.org/abs/2410.14257)：阅读 v2 中请求级 SLO、goodput 与 smooth-goodput 的指标争议；实验绑定 vLLM 0.6.3、A100、Llama-3.1-8B/Qwen2.5-14B 和 ShareGPT/LooGLE。
12. [SGLang Bench Serving Guide](https://github.com/sgl-project/sglang/blob/main/docs/docs/developer_guide/bench_serving.mdx)：核对 request-rate、最大并发、流式模式、TTFT、ITL、TPOT、goodput 和压测输出字段；`main` 为动态文档，应留存实际部署版本。
13. [TensorRT-LLM Disaggregated Serving](https://nvidia.github.io/TensorRT-LLM/features/disagg-serving.html)：核对该 runtime 当前的 context/generation worker、KV transfer、通信 backend 和限制；动态文档不代表目标硬件实测。

读者应把“框架当前支持什么”“论文证明了什么”“当前集群实测什么”分开记录。一个官方页面列出某个优化，不代表所有模型、GPU 和 batch 都能获得同样收益；一个 benchmark 提升，也不代表线上协议、安全和回滚已经解决。

## 1.19 小结

部署的对象不是孤立 checkpoint，而是带 tokenizer、template、精度、引擎、策略和评估证据的一组模型 artifact。部署的目标也不是单一的 tokens/s，而是在 workload、SLO、质量、安全和成本约束下，让请求稳定完成。

从 checkpoint 到服务，需要理解 prefill/decode、TTFT/TPOT、P95/P99、吞吐、队列、KV Cache、显存、并行、协议、鉴权、限流、监控、灰度和回滚。只有把这些因素放在同一条请求生命周期中，才能解释为什么一个模型“能跑”却还不能上线。
