# 第 1 章 部署总览：从模型 artifact（部署工件）到可运营服务

训练得到的 checkpoint（训练检查点）只是一次模型执行的起点。要让用户稳定使用它，还要确定请求是什么样、允许消耗多少资源、模型和 tokenizer（分词器）如何配套、谁负责排队与调用工具、如何判断答案可用，以及出现回归时怎样暂停和回滚。部署工程解决的是这些接口和约束如何组成一项可运营服务。

本章回答一个问题：面对“部署一个大模型”的模糊要求，怎样把它改写成可测量的服务契约，并找到需要逐项验证的工程决定。它建立后续章节共用的问题地图，不代替推理指标、KV Cache（键/值缓存）、引擎、调度、量化和生产运维的完整讲解。读完后，读者应能列出交付物和 workload（工作负载），区分请求路径中的职责，估算不同请求类的输入/输出压力，并知道每个决定要到哪里计算、验证和复盘。

## 1.0 从模型工件到服务契约

### 把交付物和请求合同写清楚

一个只有权重的 checkpoint 也许能被引擎载入 GPU（图形处理器）并返回文本，但“载入成功”只证明一条执行路径走通。如果 tokenizer 的词表或版本不同，输入映射出来的 token（模型处理的离散词元）就可能改变；如果 chat template（对话模板）没有按预期组织 system、user、assistant 和 tool 消息，模型可能误解当前角色或工具结果；如果量化配置和目标计算内核（kernel）不匹配，模型即使能运行，也未必满足质量或延迟目标。一次 API（应用程序接口）返回成功，只能说明这次调用在某个接口上结束，不能证明服务行为正确。

因此，交付对象应当是一组互相匹配、可回溯的 artifact（部署工件）和验收证据，而不是一个可以被覆盖的模型名称：

| 交付对象 | 部署时要确认的事情 |
| --- | --- |
| 权重与模型配置 | 模型结构、权重 revision（版本标识）、词表和特殊 token 是否对应 |
| Tokenizer 与 chat template | 消息角色、生成前缀、工具往返和停止语义是否匹配 |
| 精度与量化 artifact | 权重或 KV 状态的实际格式、缩放因子（scale）、内存布局（layout）和校准版本是什么 |
| 推理 runtime 与硬件 | 引擎 revision、设备、kernel/backend 与并行拓扑是什么 |
| 服务策略 | 最大输入/输出、采样设置、超时、取消、限流和工具权限是什么 |
| 验收证据 | 哪组质量回放、服务压测、安全门槛和回滚记录对应这个版本 |

这些字段共同界定一次服务结果。换了权重但保留模板，与只换 chat template 并不是同一种版本变化；如果日志只有 `model_name`，发生质量回归时就很难确认输入协议、量化、引擎还是安全策略改变了行为。模型 artifact 和协议兼容性在[第五章](05-推理引擎.md)展开，发布和回滚证据在[第十一章](11-监控评估与安全.md)及[第十三章](13-生产系统设计.md)主讲。

服务方案也不能从“团队熟悉哪个框架”开始。首先要描述每一类请求的长度分布、到达时间、并发、流式要求、工具调用比例、质量与安全条件、超时和失败规则，以及 GPU、检索、工具和人工复核预算。只知道参数量或平均 QPS（Queries Per Second，每秒请求数），不能推导显存、尾延迟或可接受容量。

可把一类请求记为：

~~~math
W_c=(\lambda_c,E[T_{\mathrm{in},c}],E[T_{\mathrm{out},c}],
T_{\mathrm{in},c}^{95},T_{\mathrm{out},c}^{95},S_c,Q_c,F_c)
~~~

这里 `c` 表示请求类，`\lambda_c` 是该类每秒到达的请求数，`E[T]` 是平均输入或输出 token 数，95 上标表示相应的第 95 百分位数，`S_c` 是延迟或完成目标，`Q_c` 是任务质量和安全要求，`F_c` 是失败、重试、取消或异步完成规则。SLO（Service Level Objective，服务等级目标）应明确请求在哪些条件下才算达标。这个向量是服务需求，不是测量结果，也不是 runtime 参数。

分请求类的价值在于保存业务差异，而不是增加记账字段。短问答通常要求尽快开始输出；长 RAG（Retrieval-Augmented Generation，检索增强生成）请求需要处理较多输入并维持更大的 KV（key/value，键/值）状态；Agent（智能体）还可能在两次模型调用之间等待外部工具。它们的输入/输出比例、活动时间和失败方式不同，应在容量测试中分别出现。若把长文档请求、短对话和工具等待压成单一平均值，调度方案可能只适合最常见的请求，却让少数长请求耗尽显存或让交互式请求排队。

请求长度还要记录分布和关联关系。P95 输入长度与 P95 输出长度通常并不代表同一条请求，不能未经验证就把两个边缘分位数拼成一个“P95 请求”；峰值请求率也未必与最长输入同时出现。建模时先保留真实 trace（请求轨迹）中的联合形状，再用代表性样本做压力测试。请求时间戳、吞吐定义和长度影响在[第二章](02-推理基础.md)展开，队列与准入策略在[第六章](06-批处理与调度.md)主讲。

### 沿请求路径拆分资源与责任

线上服务可以看成一条带状态的请求路径。请求进入系统后先经过身份和预算检查，再被路由到一个副本或排队；服务端解析消息并处理输入，推理引擎完成 prefill（对输入序列的预填充计算）与 decode（逐 token 生成），结果可能在流式返回过程中调用检索或工具，最后经过响应校验并写入必要的运行记录：

~~~text
client
  -> API ingress: identity, quota, request contract
  -> router and admission: choose model/replica, apply backpressure
  -> prompt processing: tokenize, validate, assemble context
  -> inference runtime: prefill, decode, manage request state
  -> optional retrieval or tool execution
  -> response policy: validate, redact, stream or finalize
  -> trace, metrics, audit and versioned feedback
~~~

图中的 client 是客户端，API ingress 是身份与配额检查所在的接入层，router 负责选择模型或副本，admission 决定是否准入，backpressure（反压）则限制下游过载继续传回上游。图中的 prompt processing 表示把消息、检索上下文和约束组织成模型输入；response policy 表示发送前按业务规则检查响应。这些是逻辑职责，实际产品可以由网关、编排器、推理引擎或应用进程共同实现。

服务的具体组件可以合并，但工程评审仍要回答每个状态由谁持有、每个副作用由谁授权。谁判断租户身份和配额？谁决定新请求能否入队？用户断开连接时谁取消生成、回收 KV，并通知外部工具？工具超时后谁判断能否安全重试？谁校验结构化输出和工具参数 schema（结构定义），谁写入审计事件？如果这些责任没有明确边界，API 返回成功可能掩盖未经授权的检索、未清理的活动状态、被代理缓冲的流式响应或重复执行的工具动作。

不同交互方式的资源与状态生命周期也不同：

| 服务形态 | 用户看到的交互 | 需要单独设计的语义 |
| --- | --- | --- |
| 离线批处理 | 提交一组工作，等待批量完成 | 总完成时间、失败分片、重试和结果归档 |
| 在线流式 | 请求后逐步收到结果 | 首 token、后续输出间隔、取消和连接背压 |
| 异步任务 | 收到 task id，稍后取回结果 | 幂等、持久状态、进度、超时和重复副作用 |

这三类服务可以共用模型，但不能默认共用超时、队列和重试策略。离线任务通常容忍排队；流式交互希望尽快看到输出；异步 Agent 可能在网络断开后仍需保存工具执行状态。重试一次只读模型生成，和重试一次退款或写数据库记录，也不是同一种操作。RAG/Agent 的状态机、工具权限与审计见[第九章](09-rag与agent部署.md)，网关、异步状态和组件可靠性在[第十三章](13-生产系统设计.md)完整讲解。

衡量请求需求时，还要把输入和输出分别记账。QPS 只说明每秒有多少个请求，不说明每个请求要处理多少 token。对于请求类 `c`，输入需求与输出需求可以分别估为：

~~~math
D_{\mathrm{in}}=\sum_c \lambda_c E[T_{\mathrm{in},c}],
\qquad
D_{\mathrm{out}}=\sum_c \lambda_c E[T_{\mathrm{out},c}]
~~~

`D_in` 和 `D_out` 分别表示平均每秒输入与输出 token 数。输入处理与后续生成常有不同的计算和显存特征，因此把两者分开能指出下一步应该测什么。它们仍不是 GPU 容量结论：还需要真实长度与到达分布、目标 SLO、引擎/硬件实测、cache 命中以及故障余量。不能把输入 tokens/s 直接换算成输出 tokens/s，也不能把某次压测的 token/s 当作生产副本数。

### 一个合成 workload 的手算

假设服务每秒收到 10 个短问答和 2 个长 RAG 请求。短问答平均输入 500 token、输出 100 token；长 RAG 平均输入 6,000 token、输出 300 token。以下数值是为演示账本而构造的假设，不是线上测量或 benchmark：

| 请求类 | 请求率 | 平均输入 | 平均输出 | 输入需求 | 输出需求 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短问答 | 10 req/s | 500 token | 100 token | 5,000 token/s | 1,000 token/s |
| 长 RAG | 2 req/s | 6,000 token | 300 token | 12,000 token/s | 600 token/s |
| 合计 | 12 req/s | — | — | 17,000 token/s | 1,600 token/s |

输入需求按各类请求的到达率乘平均长度后相加：

~~~math
D_{\mathrm{in}}=10\times500+2\times6000
=5000+12000=17000\;\mathrm{token/s}
~~~

输出需求同理：

~~~math
D_{\mathrm{out}}=10\times100+2\times300
=1000+600=1600\;\mathrm{token/s}
~~~

长 RAG 占请求数的比例为 `2/12≈16.7%`，占输入 token 需求的比例为 `12,000/17,000≈70.6%`，但只占输出 token 需求的 `600/1,600=37.5%`。因此一个不分请求类的总 QPS 会隐藏输入压力的来源：长请求可能需要优先检查 prefill 时间和活动 KV；短问答的响应体验则可能更受排队和 decode 节奏影响。这个解释描述的是应检查的路径，不是所有长 RAG 服务都必然由同一资源瓶颈主导。

这组均值仍不足以选择 GPU 数。容量还受请求长度分布、到达突发、并发、取消率和延迟门槛影响；即便输入和输出需求相同，两种引擎、量化和调度方案也可能给出不同结果。下一步应按请求类测 TTFT（Time To First Token，首 token 延迟）、TPOT（Time Per Output Token，首 token 之后的平均每输出 token 时间）、队列时间和资源状态，再用目标硬件上的数据测满足 SLO 的容量。各指标的计时边界与 trace 诊断在[第二章](02-推理基础.md)，KV 账本在[第三章](03-kv-cache与内存管理.md)，端到端容量方案在[第十三章](13-生产系统设计.md)。

### 从候选架构走到验收

满足 workload 不是一个框架开关。部署评审至少要拆开三个问题：选什么执行软件、请求何时进入计算、计算和状态怎样分布到设备上。三者相互影响，但各自解决不同约束：

| 决策问题 | 典型方向 | 选型前要固定的条件 | 主讲位置 |
| --- | --- | --- | --- |
| 目标模型和协议由什么推理运行时（runtime）承载？ | Transformers、vLLM、SGLang、TensorRT-LLM、llama.cpp 等 | 模型结构、API/工具协议、硬件、维护与 workload | [第五章](05-推理引擎.md) |
| 请求怎样排队、组合和分配预算？ | 批处理（batching）、连续批处理（continuous batching）、token 预算、优先级、Prefill/Decode 分离 | 到达过程、长度、取消、延迟目标和 KV 预算 | [第六章](06-批处理与调度.md) |
| 计算和状态怎样跨设备组织？ | 单机、张量并行（TP）、流水线并行（PP）、专家并行（EP）、多副本 | 权重/KV 容量、通信拓扑、状态迁移与故障目标 | [第八章](08-并行推理与多gpu服务.md) |
| 如何减少存储或计算成本？ | 权重量化、KV 低精度、校准、蒸馏 | 量化对象、质量回放、目标 kernel 与容量基线 | [第七章](07-量化与模型压缩.md)及[第十五至十七章](15-fp4-mxfp4-nvfp4.md) |

例如，TP（tensor parallel，张量并行）把同一层的矩阵或注意力计算切分到多个设备；PP（pipeline parallel，流水线并行）把不同层放到不同设备；EP（expert parallel，专家并行）把混合专家（Mixture-of-Experts，MoE）模型的专家分布到多个设备。多副本则复制完整执行组以增加服务总容量；prefill/decode 分离为两类阶段分别配置执行 worker，并需要传递生成状态。它们可以组合，却会带来不同的通信、状态所有权、容量匹配和运维代价。PagedAttention（分页式 KV 管理方法）管理 KV block，不替代调度策略；一个量化格式能加载，也不证明目标 kernel 已启用或质量已达标。各方案的机制、比较与实验方法在主讲章节展开。代码或动态文档列出某个功能，只能证明指定版本公开了该入口，不能替代目标模型、硬件和 workload 下的测量。

部署验收也不是一个 tokens/s 数字或一次成功调用。质量、运行状态和资源效率是不同的门槛；任一关键门槛不满足，都需要调整配置、收窄适用流量或停止发布：

| 门槛 | 要回答的问题 | 细读入口 |
| --- | --- | --- |
| 协议和 artifact | 输入、模板、停止、工具 schema 和版本是否兼容？ | [第五章](05-推理引擎.md)、[第九章](09-rag与agent部署.md) |
| 延迟与容量 | 代表性请求在尾部和峰值流量下是否达到目标？ | [第二章](02-推理基础.md)、[第六章](06-批处理与调度.md)、[第十三章](13-生产系统设计.md) |
| 状态与故障 | 活跃 cache、取消、超时、重试和迁移是否正确？ | [第三章](03-kv-cache与内存管理.md)、[第八章](08-并行推理与多gpu服务.md)、[第十三章](13-生产系统设计.md) |
| 任务质量与安全 | 回答、引用、结构化输出、拒答和权限是否通过独立检查？ | [第九章](09-rag与agent部署.md)、[第十一章](11-监控评估与安全.md) |
| 运营与成本 | 能否观测、灰度、暂停、回滚，并按成功任务计算代价？ | [第十一章](11-监控评估与安全.md)、[第十二章](12-成本优化.md)、[第十三章](13-生产系统设计.md) |

性能改善若伴随回答质量、权限或失败恢复回退，就不能只用吞吐宣布优化成功。更换权重、引擎、模板、精度、工具或调度时，应沿真实请求链重新检查被影响的证据，并保留旧 revision 和回退条件。监控、质量、安全和发布判断在[第十一章](11-监控评估与安全.md)，成本优化在[第十二章](12-成本优化.md)，从需求推导生产架构在[第十三章](13-生产系统设计.md)。

本册的阅读路线也按这套判断顺序安排：第 1—4 章定义请求、推理、状态与生成控制；第 5—8 章比较 runtime、调度、压缩和多设备组织；第 9—10 章接入 RAG/Agent 与多模态请求；第 11—12 章建立运营和成本闭环；第 13—14 章综合设计和复盘。第 15—17 章分别深入特定低精度部署对象，第 18 章用托管模型 API 说明接口能力、状态与计费也要按版本核对。

本册不替代邻册的完整主线：第五册讲训练 artifact 如何产生，第七册讲评估方法与证据，第十五册讲多模态模型机制，第十七、二十、二十二册讲 Agent 方法、构建和安全，第二十三册讲 AI Infra 平台与集群资源，第二十四册讲推理 runtime 的源码和实现。需要跨过这些边界时，本册保留可到达的入口，把部署层的问题继续往下交接。

要开始一个实际项目，可以按“workload 契约 → 请求 trace → 状态/显存账本 → runtime/调度/拓扑 → 质量和安全回放 → 成本与发布门槛”的顺序形成方案。每一步都写明输入是什么、输出证据是什么、哪个前置假设尚未验证。这样架构评审中的“用哪个引擎”“需要几张卡”就会变成可以压测、比较和回滚的具体问题，而不是脱离请求形状的经验猜测。

## 小结

部署的对象是一组相互匹配、可追溯的模型 artifact、服务策略和验收证据。首先按请求类记录长度、到达、质量、权限和失败规则；随后沿请求路径划分状态与资源责任，再分别衡量输入、输出、延迟、容量和成本。只有把这些约束放在同一条请求生命周期里，才能判断 runtime、调度、并行和量化方案是否适合目标服务。

本章的手算只估计合成 workload 的平均输入/输出需求，没有承诺延迟或 GPU 数。后续章节会补充测量定义、状态公式和目标环境下的验证方法，并把局部优化放回生产系统和故障案例中检查。

## 资料与延伸阅读

本章由相邻章节承担机制细节，以下资料用于建立推理服务问题的原始入口。论文实验和动态官方文档代表不同证据类型，不能相互替代；具体版本与硬件表现应在对应主题章节核对。

1. [PagedAttention: Efficient Memory Management for Large Language Model Serving](https://arxiv.org/abs/2309.06180)：理解分页式 KV 状态管理的研究动机。
2. [DistServe: Disaggregating Prefill and Decoding for Goodput-optimized LLM Serving](https://arxiv.org/abs/2401.09670)：理解拆分 prefill/decode 资源池的系统设计问题；论文收益只适用于其测量设置。
3. [vLLM Documentation](https://docs.vllm.ai/en/stable/) 与 [SGLang Documentation](https://docs.sglang.io/)：查看项目公开的 serving 入口；动态文档不等于目标版本或硬件上的性能证据。
4. [Google SRE: Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)：理解如何把服务目标和可测量信号联系起来；目标值应由具体业务确定。
