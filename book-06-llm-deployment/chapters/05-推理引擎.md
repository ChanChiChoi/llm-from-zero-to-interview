# 第五章 推理引擎：把模型前向变成可运营的执行系统

在 Python 里调用一次 model.generate，能够验证模型、tokenizer 和权重基本可以工作；它还不能说明服务能否在真实流量下稳定运行。生产推理需要同时处理请求到达、变长输入、prefill/decode 调度、KV Cache 分配、流式发送、取消、量化 kernel、多 GPU 通信、协议兼容、监控和版本回滚。

推理引擎就是承载这些执行职责的 runtime。它位于模型权重和 API 平台之间：向上接收 token、generation config、工具或结构化输出约束，向下调用 GPU/CPU/NPU kernel、管理 cache 和执行调度。一个引擎可能提供 HTTP server，也可能只提供 Python/C++ runtime；有 HTTP 接口不等于已经具备鉴权、租户隔离、灰度、计费和安全治理。

初学者可以把引擎想成一条更聪明的生产线：它把许多不同长度的请求排队，尽量让 GPU 每一轮都有合适的工作，把每个请求的历史状态放进可回收的内存池，再把 token 按协议流式返回。专家则要问：这个引擎支持目标模型的 attention/state layout 吗，量化路径是否真的走了目标 kernel，dynamic batching 的等待会怎样影响 P99，structured output 是否和工具事件兼容，升级后 tokenizer、cache 和 stop 语义是否保持一致。

本章不把某个版本的 CLI 参数或 benchmark 数字当成永久结论。正文比较各类引擎的设计侧重点，给出可复现的选型方法；第 2-4 章解释的 prefill、KV Cache 和 decoding，是理解本章的前置知识，第 6 章会深入批处理和调度，第 13 章会把引擎放进完整生产系统。

## 5.1 引擎、模型和平台分别负责什么

### 5.1.1 模型 artifact 不等于 runtime

一个可部署模型至少包含权重、结构配置、tokenizer、chat template、generation config、量化信息和可能的 adapter。推理引擎负责把这些 artifact 转成可执行计算图和运行时状态，但不一定拥有它们的全部来源信息。

可以把一次引擎调用抽象为：

~~~math
y_i=E(m,x_i,c_i,s_i,p_i),
~~~

其中 E 是推理引擎，m 是模型 artifact，x_i 是第 i 个请求的 token 序列，c_i 是 cache 和上下文状态，s_i 是采样/停止/结构化输出配置，p_i 是并行、精度、租户和资源策略，y_i 是最终输出事件和 token。引擎不仅返回文本，还应能产生 token、finish reason、usage、错误和时间戳等事件。

### 5.1.2 引擎与推理平台的边界

引擎通常负责：

| 职责 | 引擎需要回答的问题 |
| --- | --- |
| 模型加载 | 权重、dtype、量化和自定义算子如何装载 |
| 执行图 | prefill/decode 使用什么 kernel 和计算路径 |
| 调度 | 哪些请求进入本轮，如何平衡 TTFT 和吞吐 |
| cache | KV/latent/state 怎样分配、增长、共享和释放 |
| 解码 | sampling、beam、grammar、stop 和 speculative 如何执行 |
| 并行 | tensor/pipeline/expert 等切分怎样通信 |
| 输出 | token、流式事件、usage 和错误怎样产生 |
| 基础指标 | queue、prefill、decode、cache 和 kernel 的时间如何记录 |

推理平台还需要：

1. API Gateway、鉴权和租户配额。
2. 限流、backpressure、优先级和多模型路由。
3. 灰度、回滚、版本和 artifact 注册。
4. 质量回放、安全策略、审计和敏感数据处理。
5. 成本分摊、告警、容量规划和故障演练。

引擎可以暴露 OpenAI-compatible API，但这个兼容通常只描述请求/响应字段；它不自动保证 tool event、reasoning channel、错误码、取消和结构化输出语义完全一致。客户端应对实际事件流做契约测试。

## 5.2 为什么朴素 generate 不够

最简单的路径是：

~~~python
outputs = model.generate(**inputs)
~~~

这条路径适合教学、单样本 sanity check 和离线实验，但它通常没有为真实服务解决以下问题：

1. 请求长度不同，如何组成高效 batch。
2. 一个请求结束时，如何把空出来的 decode 槽位给新请求。
3. KV Cache 如何按真实 token 数增长而不是按最大长度静态预留。
4. 客户端断开后，如何取消计算并释放状态。
5. 同时有长 prefill 和短 decode 时，如何控制队列和尾延迟。
6. 量化模型是否使用硬件匹配的 kernel，而不是回退到慢路径。
7. 多 GPU 上权重、cache、激活和通信如何分配。
8. 如何暴露 TTFT、TPOT、P95/P99、cache 水位和错误原因。

Transformers 本身可以提供 cache、batch 和生成策略的组件，这和“直接使用一次 generate”是两个层次。问题不在于某个库好不好，而在于一个研究调用路径没有自动变成多租户、高并发、可取消和可观测的服务 runtime。

## 5.3 一个引擎的请求生命周期

引擎内部可以用下面的状态图建立共同语言：

~~~text
received
  -> validate and tokenize
  -> waiting
  -> prefill
  -> decoding
  -> stream / tool event
  -> completed, cancelled, timeout, or error
  -> release cache and record metrics
~~~

每次状态转换都应该绑定 request id 和 trace span。尤其要区分：

1. waiting：请求尚未消耗 GPU，但可能已经占用连接和队列空间。
2. prefill：输入 token 进入模型，通常需要申请并写入大量状态。
3. decoding：每轮生成一个或多个 token，读取历史 cache。
4. tool wait：模型暂时不占用 decode kernel，但任务没有完成。
5. cancelled：客户端已不再需要结果，计算和 cache 应尽快停止。

如果引擎只返回最终字符串，平台很难知道慢在排队、模型、网络还是工具；如果只记录 GPU kernel，也无法解释用户看到的 TTFT。引擎与平台需要约定事件和时间戳，而不是各自猜测。

## 5.4 选择引擎前先定义 workload

没有 workload，比较“哪个引擎最快”没有稳定含义。至少固定：

| 变量 | 需要记录 |
| --- | --- |
| 输入 | 平均/P95/P99 token 数，是否 RAG、工具或多模态 |
| 输出 | 平均/P95/P99 token 数，是否流式，stop 分布 |
| 流量 | 平均和峰值到达率，突发形状，持续时间 |
| 并发 | active request、decode request、tool wait 数 |
| SLO | TTFT、TPOT/ITL、E2E、P95/P99、错误率 |
| 质量 | 任务成功、引用、代码测试、schema、拒答和安全 |
| 硬件 | GPU 型号、显存、互联、驱动、CPU 和网络 |
| 协议 | chat template、tool schema、事件格式、取消语义 |
| 运营 | 灰度、回滚、日志、成本、团队维护能力 |

短聊天、长 RAG、代码生成、离线合成和 Agent 的最佳引擎配置可能不同。短聊天更敏感于队列和 TTFT，长 RAG 更敏感于 prefill、prefix cache 和 cache bytes，离线合成更在意总 token 吞吐，Agent 则需要事件、工具和取消语义稳定。

把 workload 写成请求类别后，先算它给系统带来的工作量，而不要先给某个引擎贴“快”的标签。假设一分钟有 1,000 个请求：700 个短聊天请求各含 256 个输入 token、生成 80 个 token；300 个 RAG 请求各含 4,000 个输入 token、生成 400 个 token。短请求输入量是 $700\times256=179,200$ token，RAG 输入量是 $300\times4,000=1,200,000$ token，因此合计 $1,379,200/60\approx22,987$ 输入 token/s。输出量为 $700\times80+300\times400=176,000$ token/min，即约 $2,933$ 输出 token/s；请求到达率为 $1,000/60\approx16.7$ request/s。

总平均值会掩盖两类请求的不同压力：平均每请求只有约 1,379 个输入 token，但 30% 的请求是 4,000-token 长输入，所以 P95 会落在长请求类别。若业务分别要求短聊 TTFT P95 不超过 500 ms、RAG TTFT P95 不超过 2 s，单独报全体平均 TTFT 无法判断任一类别是否达标。以上是明确假设的容量输入，不是压测结果，也不能直接换算成 GPU 数；还需要目标模型在目标硬件上的 prefill/decode 速率、KV 字节数、队列变化和可用性余量。这样拆分后，5.14 的压测矩阵才有可复现的输入，5.16 的候选筛选也有明确的服务门槛。

## 5.5 Transformers：参考实现和轻量服务入口

Hugging Face Transformers 的优势是模型生态广、加载和调试简单、生成 API 统一，适合：

1. 新模型接入时验证 tokenizer、template 和 logits。
2. 训练后 checkpoint 的 sanity check。
3. 小规模离线生成和评估。
4. 研究 sampling、beam、logits processor 和自定义模型。
5. 为其他引擎提供 reference output。

要区分库 API、轻量服务入口和专用 serving runtime。单次 `model.generate()` 仍是很好的 reference path，但调用方要自己组织 batch、取消、并发和请求观测。Transformers v5.22.1 官方指南把 `transformers serve` 定位为本地/自托管的轻量 server，适用于评估、实验和中等负载，列出 continuous batching，并建议大规模生产使用 vLLM 或 SGLang 作为后端；这份指南没有把 `serve` 称为 experimental。[Transformers v5.22.1 Serving 指南](https://huggingface.co/docs/transformers/v5.22.1/serve-cli/serving) 因而，低运维入口可以成为一个真实候选，但它的官方适用范围仍不是容量承诺，是否合适要看目标模型、请求分布和平台层所需能力。

Reference path 的价值是建立可复查的行为基线，而不是要求所有 runtime 在任何采样条件下逐 token 相同。固定模型权重、tokenizer、模板和 greedy 参数时，可检查输入 token、assistant 起点、stop、finish reason、schema 与工具事件；使用随机采样或不同 kernel 后，个别 token 可能受随机数流和浮点舍入影响，应比较分布、任务结果和协议不变量。举一个合成回放集：70 条确定性文本样本中 68 条通过 token/finish-reason 契约，20 条 schema 样本中 19 条通过，10 条工具样本中 8 条产生正确工具事件，合计 $68+19+8=95$ 条通过。若本项目的示例门槛设为至少 98/100，这个候选仍不能替代 reference；差异必须继续定位到模板、stop、parser 或模型执行路径。这里的 95/100 是教学假设，不是 Transformers 的实测准确率。

正确的使用方式是把它作为协议和质量基线：同一输入、同一模板、同一 generation config 在 reference engine 和目标 engine 上回放，比较 token ids、finish reason、工具事件和任务结果。不要只比较最终字符串，因为 whitespace、流式事件或隐藏 reasoning 字段的变化可能被最终拼接掩盖。一个公平的回放 manifest 还要锁定模型 revision、依赖、dtype、chat template、stop 列表和确定性设置；若这些变量不同，输出差异就不能直接归因给引擎。Reference 本身也需校验：它定义的是当前被接受的行为合同，不是“质量一定正确”的证明。

回放结果应按失败位置归类，而不是只给一个总通过率。比如文本样本失败可能是特殊 token 或停止条件不一致，schema 样本失败可能是语法约束没有生效，工具样本则可能是解析器漏掉调用事件；这几类差异需要的修复人和回归集都不同。把失败请求保存成最小 fixture，记录 reference 与 candidate 的输入 token、首个分歧位置、终止原因和事件序列，后续换版本时就能重放同一条证据。若通过率按请求统计，还要说明各类样本的数量与权重；均匀混合的小测试集不是生产流量分布，也不自动给出真实任务成功率。

确定性与随机性也要分开验收。greedy、相同 token 序列和相同结束条件下，逐 token 对齐适合发现模板、cache position 或算子路径问题；sampling 则需固定 seed 和随机数调用路径才可能逐 token 复现，即使 seed 相同，不同 batch 排列也可能改变随机数消耗顺序。对随机生成，更稳妥的回放合同是检查格式、finish reason、工具合法性、任务评分分布和拒答边界，并重复多轮报告波动范围。若把不确定的采样差异直接判成引擎错误，可能误拒兼容实现；若把系统性协议偏差都称作随机噪声，也会放过真实故障。

`transformers serve` 是否足够，还要看项目由谁承担外围职责。轻量自托管入口降低了启动和调试成本，但鉴权、租户隔离、限流、审计、健康探针、重试策略和告警仍属于部署边界；这些能力可以由网关或平台提供，不能仅凭 server 能接收 HTTP 请求就默认具备。评估时先确认目标模型和接口路径是否在所用版本的文档范围内，再用目标并发、取消、长输入和错误恢复做小规模回放。若负载稳定且中等、团队希望简化本地实验，它可以成为合格候选；若目标是高并发、多租户或严格服务等级，则应把平台缺口和专用 runtime 的适配成本一起比较。

## 5.6 vLLM：通用 serving 的高效默认候选

### 5.6.1 设计侧重点

vLLM 的公开设计以高并发 LLM serving、分页式 KV Cache、continuous batching、prefix caching、流式 API 和多硬件/量化支持为重点。PagedAttention 让逻辑序列可以使用不连续的物理 block，continuous batching 让不同生命周期的请求在迭代粒度重新组合。

这些机制解决的是服务系统的资源问题：

1. 变长请求不需要按统一最大长度占满连续空间。
2. 完成请求的 cache block 可以回收给新请求。
3. 多请求 decode 可以共享一次批次计算。
4. 相同前缀在满足 key 和权限条件时可以复用。
5. API server 和 runtime 可以分离演进。

在 vLLM v0.32.0 的 V1 架构中，可以把一条请求链拆成 API server、engine core 和 GPU worker：前端处理 HTTP、tokenizer/多模态输入并回传流式结果；engine core 持有 scheduler 与 KV cache manager；worker 执行模型前向。这个边界说明“服务接口、调度和 GPU 计算”是不同进程职责，也决定了 benchmark 不能只量 kernel。该版本 scheduler 在 step 级统一安排 prompt 与 output token 的计算进度，长 prefill 可以按 token budget 切块并与已有 decode 请求共同进入执行循环；它没有先清空一整批 prefill、再整批 decode 的固定相位边界。具体进程和调度实现随 release 变化，应对照固定版本的 [V1 架构文档](https://docs.vllm.ai/en/v0.32.0/design/arch_overview/)、[scheduler API/source reference](https://docs.vllm.ai/en/v0.32.0/api/vllm/v1/core/sched/scheduler/)和[chunked-prefill 调优说明](https://docs.vllm.ai/en/v0.32.0/configuration/optimization/)。

这里的 token budget 是调度器本轮可安排的 token 计算上限，不是“最大并发请求数”，也不是每个请求都能用到的固定配额。设一轮上限为 12 个 token 位置，当前有 3 个 decode 请求各需推进 1 个 token，则先占 3 个位置；还剩 9 个位置。若一个等待请求有 20 个尚未计算的 prompt token，且当前允许 chunked prefill，调度器可以把这 9 个位置分给它，本轮总计安排 $3+9=12$ 个 token 计算。下一轮这个 prompt 还剩 11 个 token，再与当时仍活跃的请求竞争预算。这个小账本只演示 token 预算的分配关系；具体 batch shape、kernel padding、优先级和抢占还取决于配置与版本，12 也不是建议的生产参数。第六章再推导预算、队列和阶段调度的完整取舍。

PagedAttention 处理的是与这条调度链不同但互相影响的资源问题：序列长度不断变化，KV cache 若按最大上下文连续预留会留下大量空洞；按固定 token block 分配后，逻辑序列通过 block table 找到物理 KV，结束的请求可释放 block，公共前缀也可在满足 key、模型版本和隔离条件时共享。调度器因此能在 KV 空间和本轮计算预算两个约束下决定谁进入执行。分块并不消除内存成本：block 尾部仍可能有内部空闲，活跃 KV、prefix residency、模型权重和 workspace 依旧竞争显存。第 3 章已经讲清 block 和工作集的容量推导，本节把它当作选型时需要一起验收的状态契约。

因此，判断 vLLM 的“支持”要从名词落到执行路径。一个模型能被加载，不保证其 attention、MoE/MLA、量化、LoRA、multimodal encoder 和 speculative draft 都走预期 kernel；某条路径能运行，也不代表没有 fallback 或质量回归。选型前可把模型 artifact、revision、GPU、dtype、parallel config、cache 形式和请求协议写成一行配置坐标，再对照固定 release 的 model support、quantization 和 feature 文档。服务实际跑的 kernel、最大 batch token、KV block 水位、抢占与每类请求延迟，要从目标环境观测，不能用“vLLM 支持该模型”这句话补全。

多进程架构也影响容量估算。API server 做 tokenization、多模态加载和 SSE 回传，engine core 排队并管理 cache，GPU worker 加载权重并执行 forward；如果 tokenizer 或图像解码阻塞 CPU，单看 GPU 利用率可能把瓶颈误判为 scheduler。data parallel 还会增加 engine core 与路由协调进程，CPU、共享内存、文件描述符和网络连接都可能先于 GPU 成为限制。生产压测应至少保留客户端 TTFT 与 server-side queue/prefill/decode/cache 指标，按同一请求 ID 对齐，而不是只报告某个 worker 的 tokens/s。

V1 也提醒我们，工程演进常来自旧结构的边界：V0 中 scheduler、cache、worker 和 API 能力逐步累积，功能组合增加维护复杂度；V1 对这些核心边界统一重构。阅读版本说明时要问“本版本的 scheduler 能否混排 prefill/decode、cache manager 是否支持该状态、功能是否仍在支持矩阵”，不能只凭 `vLLM` 这个名字假设新旧语义相同。

### 5.6.2 适合什么场景

vLLM 常作为通用开源模型 API 的起点，尤其适合：

1. 多租户文本生成和聊天服务。
2. 需要较快接入多种开源模型的团队。
3. 在线与离线共用 serving runtime 的场景。
4. 需要 OpenAI-compatible API、流式输出和基础 metrics 的项目。

这不是对所有模型的承诺。自定义 attention、混合 state、特殊量化、非标准 tool event 和最新模型功能，必须核对具体版本的支持矩阵；接口启动成功也不等于目标 kernel、cache layout 和协议语义正确。

### 5.6.3 需要重点测什么

使用 vLLM 之前，至少做：

1. reference engine 与 vLLM 的 token、template、stop 和工具事件回放。
2. 按输入/输出长度测 TTFT、TPOT、P95/P99 和 cache 水位。
3. 比较 eager、CUDA graph、量化、prefix cache 和并行配置的实际路径。
4. 观察长请求、取消、抢占、OOM 和高峰 backpressure。
5. 在目标 GPU 和实际 workload 上测 tokens/s，而不是引用通用宣传数字。

测试结果还要按请求类别分层。若短聊天每秒到达 20 个请求，而长 RAG 在突发时一次到达 40 个，分别跑“恒定并发 8”可能既漏掉队列峰值，也看不见长 prefill 对短请求 decode 的干扰。可以把到达 trace 与输出长度固定，再比较默认预算与较小预算：较小预算可能更常让出计算位置给 decode、降低某些请求的 ITL，却让长 prompt 分更多轮完成并抬高 TTFT；哪侧更重要由 SLO 决定。该方向性不能代替压测结果，且 scheduler 参数的作用依 vLLM release、模型和输入形状而变。

当 vLLM 作为候选而非最终结论时，验收表至少分三栏：语义是否正确（token、stop、tool/schema、取消与错误）；资源是否可控（KV 峰值、preemption、OOM、CPU/显存水位）；目标类别是否满足 SLO（TTFT、TPOT/ITL、E2E 和 goodput）。若某一栏失败，先定位协议、kernel fallback、调度预算或容量限制，再决定换配置、换 backend 还是换引擎。这样能把“适合通用 serving 的起点”理解为一个便于验证的候选，而不是对所有模型和硬件的默认胜出。

调度旋钮要根据哪项 SLO 紧张来判断。假设业务把短聊天的 P95 TTFT 上限定为 800 ms、TPOT 上限定为 50 ms；同一 workload trace 下，配置 A 测得 P95 TTFT 620 ms、TPOT 42 ms，配置 B 因更积极地切小 prefill chunk，测得 TTFT 910 ms、TPOT 35 ms。A 两项都过门槛，B 的逐 token 间隔更短却因首 token 超限而不合格。数值是决策演示假设，不是 vLLM 性能结论；它说明不能把“更小的 token budget”或“更高的吞吐”直接写成优化方向。真实比较还要把长 RAG 的 TTFT 与短请求的 TPOT 分开看，并检查改动是否只是把等待从一类请求转移到另一类。

另一个常见误判是把 GPU 忙碌程度当成容量答案。若 KV block 已接近上限，scheduler 可能减少可进入本轮的请求、触发抢占或等待释放，即使本轮 token budget 尚有余量；反过来，cache 空间足够但长 prefill 占满计算预算，也会让 decode 请求等待。压测报告应在同一时间轴对齐 queue、active sequence、KV block 水位、抢占和每类请求延迟，区分“算力不够”“状态空间不够”和“请求未被公平调度”。本节只用这些信号做 runtime 验收，第六章再系统推导队列、预算、公平性和抢占策略。

版本升级也应被视作新的候选配置，而不是沿用旧表格中的结论。模型 revision、tokenizer、CUDA/driver、dtype、并行度或 cache 形式任一改变，都可能让原先通过的组合走到不同 kernel 或状态路径。回归时优先重放受影响的协议和 workload 切片，再确认原有容量与 SLO 结论是否仍成立；不能因服务仍能启动，就把前一版的吞吐、质量和内存证据自动搬到新版本。

## 5.7 SGLang：把结构化 LLM 程序作为执行对象

SGLang 不只把请求看成一段 prompt，也强调结构化生成程序、分支、并行采样、工具和 Agent 流程。它把 Python 前端和 serving runtime 放在同一套程序模型中：前端描述多个 generation call、并行分支和控制流，runtime 再负责调度和状态复用。原论文提出 RadixAttention 管理共享 KV 前缀，并用压缩有限状态机加速受约束解码；因此它解决的是“多次调用之间如何复用和执行程序”，不只是“单次 HTTP 请求如何 batching”。[SGLang 原论文](https://arxiv.org/abs/2312.07104)

本章把机制与实验范围固定到原论文 v2；论文报告的最高 6.4× throughput 属于作者测过的模型、任务和系统对照，不是当前 SGLang release 与其他引擎的通用倍率。[SGLang 原论文 v2](https://arxiv.org/abs/2312.07104v2)

### 5.7.1 它解决的不同问题

普通 server 主要优化“许多独立请求如何排队”；结构化 LLM 程序还需要处理“一个任务内部的多个生成节点如何复用上下文并组织依赖”：

~~~text
program
  -> shared system prefix
  -> branch A / branch B
  -> parallel samples
  -> verifier or tool
  -> merge result
~~~

如果每个分支都把公共前缀重新 prefill，计算和 cache 都会浪费；如果 runtime 能识别程序结构并复用公共状态，复杂任务可能获得更好的执行效率。代价是执行模型、缓存 key、分支生命周期和错误传播都更复杂。

Radix cache 可以理解为按 token 前缀压缩路径的树。新请求先沿树找到最长已计算前缀，命中部分的 KV 状态可以复用，只有未命中的后缀继续 prefill；分支在公共节点处分开时，cache 结构能表达共享前缀和不同后缀。它的收益主要随重复前缀比例、命中长度、缓存驻留时间和分支形状变化：如果请求前缀几乎都唯一，树结构带来的复用很少；如果 cache eviction、会话隔离或 key 设计不正确，复用还会引入显存压力和隐私风险。当前文档已分别列出 session-aware Radix Cache 与 eviction policy，具体语义应按版本核验。[SGLang Radix Cache 会话文档](https://docs.sglang.io/docs/advanced_features/session_radix_cache)；[Eviction policy 文档](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy)

本章于 2026-11-02 查阅的官方 current 文档列出 session-aware Radix Cache 与 eviction policy；它们是动态文档，部署时要按目标 release 复核。用一个合成分支任务看复用量：三个候选都以相同的 800-token system/task 前缀开始，各自再接 200 个不同的证据 token。若每个分支独立执行，要处理 $3\times(800+200)=3,000$ 个输入 token；若前缀已命中并且其 KV 仍驻留，只需一次计算公共的 800 token，再计算三段各 200 token，总计 $800+3\times200=1,400$ 个，少计算 1,600 个输入 token，按输入 token 计约减少 $1,600/3,000\approx53.3\%$。这是前缀 token 工作量，不是 wall-clock 加速比例：attention 的计算量并非只随 token 数线性变化，分支调度、KV 读取、模型并行和其他请求也会改变时间。

这个例子还依赖 exact prefix。模板空格、工具状态、模型 revision、tokenizer 或前置消息顺序不同，都可能让 token 序列在共享位置之前分叉；共享到 800 token 后，后缀不同的 KV 不能彼此当作相同状态。首次请求通常还要付出 cache 建立和保留成本；若缓存因容量压力被淘汰，后续分支会重新 prefill。应在目标 trace 里记录可复用前缀长度、命中率、命中 token 数、cache 驻留时间和 eviction，并与端到端 goodput 一起看。命中率高但请求等待缓存、跨租户错误共享或保留了大量低频状态，仍可能让整体服务变差。

“session-aware”也有明确边界：SGLang 当前文档要求应用在同一会话的请求中传递相同 `session_id`，它只登记可复用 KV 的会话引用，不会替应用保存或拼接对话历史；每次请求仍需带上本轮所需上下文。会话引用只是 eviction 偏好，空间不足时仍可回收被引用的 KV；会话结束时应用还应调用关闭接口移除引用。因而，session ID 不是授权凭据、对话存储或硬性 cache pin，不能替代应用层的租户隔离和会话生命周期管理。

原论文在其指定模型、硬件、任务和 baseline 上报告最高 6.4× throughput；这个数字用于证明多调用/共享前缀 workload 值得优化，不是与 vLLM 论文或今天的 SGLang/vLLM release 的通用横向排名。生产选型需要先测 prefix hit rate、实际复用 token、eviction、cache memory 和端到端 goodput，再判断程序 runtime 是否带来净收益。

### 5.7.2 适合什么场景

SGLang 倾向适合：

1. 结构化生成和 grammar 约束。
2. 多轮 Agent、工具和程序化 prompt。
3. 并行采样、rerank 和 verifier 流程。
4. 需要把共享前缀和程序节点放进同一执行图的服务。

如果只是单模型、短问答和简单文本 API，SGLang 的程序抽象未必带来足够收益。应比较开发复杂度、协议可观测性和目标 workload，而不是把“支持 Agent”当成质量保证。

对 Agent 负载，比较时要把一次端到端 job 还原成生成节点和非模型等待：例如一次任务先并行生成 3 个候选，再调用 verifier，最后根据结果进行一次汇总。SGLang 的程序前端能显式表达并行分支和依赖，但 verifier 的质量、工具权限、重试幂等与外部等待仍由应用负责；runtime 的快慢也只能覆盖它负责的模型步骤。压测应固定候选数、每轮 prompt 与输出长度、工具响应分布和完成标准，记录每个 generation call 的 queue、prefill、decode、cache hit 与 end-to-end 成功率。否则某引擎减少一次模型调用或把工具失败当作完成，可能在较低 tokens/s 下看起来更快，却没有完成同一任务。

上线前还需分别验证程序正确性与缓存隔离。对同一会话回放时，检查请求是否带有完整历史、分支合并是否保留正确 parent、取消后 session reference 是否关闭；对不同租户回放相同 token 前缀时，确认缓存 key 与授权边界符合设计。官方文档给出的 session cache 只管理 KV 引用，不会替应用保存历史或授权，因此这两个责任必须落在宿主。若目标 trace 的共享前缀很少，先用简单的独立请求 serving 路径作 baseline；只有实测节省的 prefill 与任务延迟足以抵消 cache、程序调试和版本维护成本时，再引入程序 runtime。

可以把一个 Agent job 看成带依赖的执行图：先并行生成 3 个候选，三个节点共享同一系统说明；verifier 等候选都返回后评分，最终生成节点只接收胜出候选及必要证据。程序层表达的是“哪些模型调用可以并行、哪些必须等待前一节点”，Radix Cache 可能复用相同前缀的 KV；它不会替 verifier 判定答案，也不会把不同候选后缀变成同一状态。若第一次测得服务端 prefill token 减少，仍需确认 verifier 和工具等待没有成为主耗时，并且并行分支没有让 KV 峰值超过预算。回放时可逐节点记录输入 token、父节点、cache hit、生成耗时和输出质量，再额外核对最终 job 的成功率与延迟。

因此，测试 SGLang 要同时有两个基线：一个是相同模型和模板下的单请求 reference，用于排除协议变化；另一个是把同一 job 展开成普通请求序列的 serving baseline，用于判断程序编排和共享 cache 是否带来净收益。前者回答“每个调用的行为是否可接受”，后者回答“将调用组织成程序后是否改善整体任务”。若只比较单个 generation call 的 tokens/s，就没有测到 SGLang 强调的程序复用；若只比较复杂 Agent 的端到端时间，又难以分辨收益来自模型调度、cache、工具响应还是业务逻辑变化。

## 5.8 TensorRT-LLM：NVIDIA 生态中的优化 runtime

TensorRT-LLM 这个名称容易让人以为当前每次部署都要把 checkpoint 编译成 TensorRT engine。这个说法已经过时。**截至 2026-10-26，官方迁移指南说明 TensorRT engine backend 已移除，PyTorch 是唯一执行 backend；当前 `LLM`/`trtllm-serve` 路径直接加载 Hugging Face checkpoint，不再需要旧的 `trtllm-build` 和 checkpoint conversion 步骤。**旧版 TensorRT engine 文档保留作历史参考，不能与当前 PyTorch backend 的部署流程混写。[Backend 移除迁移指南](https://nvidia.github.io/TensorRT-LLM/latest/legacy/tensorrt-backend-removal.html)；[当前 PyTorch 架构](https://nvidia.github.io/TensorRT-LLM/latest/torch/arch_overview.html)

当前 `PyExecutor` 仍由 scheduler、model engine 和 decoder 等部件组成：scheduler 决定本 step 运行哪些请求并分配 KV 资源，model engine 做单步前向，decoder 根据 logits 产生 token。NVIDIA 仍围绕 CUDA GPU 提供针对模型、精度、kernel、并行和 cache 的优化；变化是优化能力不再等同于旧式“先 build 一个 TensorRT graph engine”。版本升级时还需查 release notes 中的破坏性 API 变更、模型支持矩阵和已知组合限制。

这里要把“执行 backend”和“kernel 优化”分开理解。PyTorch 是当前公开架构里承载 TensorRT-LLM 请求的执行 backend，但模型前向仍可调用针对目标 GPU、模型结构和精度优化的 kernel；这不等于普通 eager `model.generate()`，也不等于以前的 TensorRT engine checkpoint。官方迁移页在 2026-10-26 更新，当前链接是 `latest` 动态文档；本章按 2026-11-02 可读到的这份公开合同描述，不将旧的 `trtllm-build` 教程混入当前路径。若实际部署包或镜像仍在旧 release，先查它自己的版本迁移记录，不能直接把新接口照搬过去。

面向固定 NVIDIA 集群时，优化收益要换算成完整工作负载节省的资源，而不是只看 microbenchmark 的一个 kernel。假设同一台 8-GPU 池、相同模型和请求 trace 下，基线引擎实测聚合输出速率为 500 token/s，候选配置为 600 token/s；每天都要完成 5,000,000 个输出 token，忽略冷启动和排队后的简化账本是：基线需要 $5,000,000/500=10,000$ 秒，$10,000/3,600\approx2.778$ 小时，消耗约 $2.778\times8=22.22$ GPU-hours；候选需要 $5,000,000/600\approx8,333.3$ 秒，约 $2.315$ 小时，消耗约 $2.315\times8=18.52$ GPU-hours，差值约 3.70 GPU-hours/日。这个 20% 吞吐提升是教学假设，只有在模型质量、TTFT/P99、错误率和压测到达过程同时通过后才有决策意义；若输出 token 变少或 schema/tool 成功率下降，不能按相同成功工作量比较。

这个例子也说明何时值得承担专用 runtime 的维护：固定模型、固定 GPU、流量大且基线确实有可优化瓶颈时，长期 GPU-hours 可能覆盖持续适配成本；模型频繁变化、调用量低或大部分时间受外部工具等待限制时，即便某个解码 kernel 更快，整项服务也可能看不到收益。每个 candidate 都应在同一 artifact 和协议 fixture 上先证明正确，再以同一 trace 测整体服务曲线。要观察 CUDA/PyTorch/driver 组合、模型支持、kernel fallback 和 memory usage，而不是把“backend 唯一”理解成“无需选配置”。

从请求路径看，官方 PyExecutor 说明把 scheduler 分成 capacity 与 microbatch 两步：前者判断是否有足够资源容纳请求，后者决定本轮由哪些序列进入模型前向；Model Engine 执行一步计算后，Decoder 根据结果产生 token 并收尾。这样设计意味着“请求能进队列”“KV 资源能分配”“本轮进 batch”是三个不同检查点。直接读 Hugging Face checkpoint 省去了旧转换/engine-build 流程，却不会替模型结构映射、精度支持、并行拓扑或 sampler 行为背书。部署手册应记录加载用的 HF revision、runtime package/image、torch/CUDA/driver、目标 kernel 与 fallback 观测，问题才可复现。

针对较低吞吐的 kernel 优化，profile 结果只能说明某个算子或某个输入 shape 的时间变化。若生成过程中瓶颈实际在长 prompt prefill、KV 分配、host launch 或多卡通信，改一个 decode kernel 可能几乎不改变 E2E。先用端到端 trace 找到时间占比，再在相同输入长度和并发下比较优化前后 TTFT、TPOT、排队、token 吞吐和 GPU-hours；这是把 NVIDIA 硬件专项调优和通用 serving 配置区分开的必要步骤。

选型时应问：

1. 当前 release 是否支持目标模型结构和目标 GPU/数据类型？
2. 目标优化路径是哪个 PyTorch backend、kernel 与 ModelOpt 配置，是否有 fallback？
3. runtime、PyTorch、CUDA、驱动和通信库组合是否在该 release 支持矩阵内？
4. 吞吐、TTFT/TPOT、质量和显存是否在实际 workload 上测过？
5. API、模型加载和 sampler 的升级变更能否纳入回归？

TensorRT-LLM 适合对 NVIDIA GPU 上的推理性能做精细优化，但复杂度现在主要来自依赖/模型/硬件/内核矩阵和低层 profiling；不能再把旧 engine-build/转换步骤写成每个当前部署都必需的成本。若团队的目标是快速覆盖变化中的模型，先比较当前 PyTorch backend 和通用 serving runtime 的适配成本；若目标是固定硬件和高利用率，再用受控 benchmark 证明优化收益。

## 5.9 LMDeploy：面向开源模型部署的另一条路线

LMDeploy 是开源模型部署生态中的一个选项，官方文档描述了面向 LLM/VLM 的推理、量化、TurboMind/PyTorch 后端和服务能力。它在模型接入、量化和 NVIDIA 生态部署上可能有自己的优势，但具体能力和后端支持随版本变化。

它不是一个单一执行路径：官方安装和模型矩阵分别列出 C++/CUDA 的 TurboMind Engine 与 PyTorch Engine。前者偏优化的 CUDA 执行，后者降低开发和接入门槛；同一模型在两种 backend、不同 GPU 平台上的支持项可能不相同。选择 LMDeploy 时应把“模型名称 + backend + device + dtype/量化格式”作为完整坐标，而不是只确认模型出现在总目录里。[安装与 backend 说明](https://lmdeploy.readthedocs.io/en/stable/get_started/installation.html)；[按 backend 划分的模型矩阵](https://lmdeploy.readthedocs.io/en/stable/supported_models/supported_models.html)

选择 LMDeploy 时应核对：

1. 目标模型和多模态输入是否由当前版本支持。
2. 使用哪个 backend，模型是否需要转换。
3. 量化格式、KV Cache dtype 和硬件 kernel 是否匹配。
4. OpenAI-compatible API、streaming、tool/schema 和取消是否满足协议。
5. 与 vLLM/SGLang/TensorRT-LLM 在相同 workload 下的 TTFT、TPOT、P99、显存和质量差异。

LMDeploy 不应被简单归类成“另一个 vLLM”或“量化工具”。它有自己的执行后端和 artifact 流程，工程团队需要以官方版本文档和实际回放为依据。

两种 backend 的公开服务接口相似，能降低应用层切换成本，却不意味着执行特性完全相同。TurboMind 文档用 persistent batch 描述请求槽位和 KV manager；PyTorch engine 文档描述 EngineInstance 把请求发送给 Engine，Scheduler 选择当轮序列并管理 cache/adapter，再由 ModelAgent 执行模型。前者的内核与布局更专用，后者强调开发和新模型接入，但两者都可能受具体架构、attention 变体、adapter、量化布局及 device 限制。服务能用相同客户端发请求，只说明接口可接通，不能推导 token 轨迹、cache 行为和 throughput 等价。

一个组合筛选例子：把候选变量列成 2 种 backend（TurboMind、PyTorch）、2 种目标设备和 3 种 cache/dtype 设定，表面上有 $2\times2\times3=12$ 个配置格。假设目标模型启用了 sliding-window attention，而本次查阅的 LMDeploy stable 矩阵说明对应 TurboMind 路径不支持该开关，那么 TurboMind 的这 6 格先被排除，不能因为模型出现在另一张表就继续当成兼容。剩余 PyTorch 配置仍要核对版本和低精度支持，再用相同请求做质量与服务测量。此处的 12 格是组合检查示例，不是 LMDeploy 当前模型支持数量；官方 stable 矩阵会随 release 变化，正文链接于 2026-11-02 查阅。

最后将候选输出与 reference 回放：先固定模板、stop、量化 artifact 和生成参数，再针对文本、多轮、VLM、schema、工具分别检查事件和任务结果；随后只在通过正确性门槛的配置上测 TTFT/TPOT、吞吐和显存。若不同 backend 结果不同，要先排除模型映射、精度、cache 或模板差异，再讨论速度。第七章会讲量化质量与压缩误差，本节只要求把 backend 和 artifact 组合固定进选型记录。

运行清单还应记录模型 support row 对应的实际 config，而不只抄模型系列名：是否启用 window attention、head dimension、vision encoder、KV dtype、权重量化算法、TP size 和 adapter 数量都会改变可执行路径。发现文档标记为“未验证”或能力缺失时，应把它当作待验证项或排除项，不要由相似模型补齐。这样 LMDeploy 的两个 backend 才能被当成两个有明确条件的候选，而不是一个品牌下可任意互换的实现。

一个稳妥的接入顺序是先按官方矩阵删掉明确不支持的坐标，再验证加载、短文本和协议，然后检查长上下文以及当前支持矩阵列出的多模态输入路径，最后才在通过质量门槛的配置上压测。假设 TurboMind 的某个模型/设备组合因 attention 变体被排除，PyTorch 剩余组合仍需各自检查 dtype、adapter 和 cache；不能把“PyTorch backend 可加载”当作其余组合都成立。每次测试记录配置坐标及版本，不要把 TurboMind 的吞吐数据贴到 PyTorch 配置上，也不要在升级后沿用旧支持表而不复核。

若同一产品同时有文本和视觉请求，可先分开建两份 workload：纯文本测 prefill/decode 与 KV，带图像请求则额外记录图像预处理、视觉编码和多模态 token 占用。若某 backend 在纯文本上通过，却在视觉路径发生回退或无法满足质量门槛，保留双路径或限定路由范围比强行给整个产品选一个总冠军更清晰。跨 backend 共用 OpenAI-compatible 客户端只能减少调用代码差异，不能省去多模态输入、取消和流式事件的分路回归。

## 5.10 llama.cpp：轻量、本地和边缘优先

llama.cpp 以 C/C++ runtime、GGUF 模型格式和较广的本地硬件覆盖著称，常用于 CPU、Apple Metal、CUDA、边缘设备和个人电脑。它的价值不在于与数据中心 serving 引擎争夺所有吞吐记录，而在于把量化模型以较低部署门槛带到本地和受限环境。

### 5.10.1 典型优势

1. 单二进制或轻依赖部署。
2. GGUF 等本地模型 artifact 生态。
3. CPU、Metal 和多种 GPU backend 的可用性。
4. 适合离线、隐私本地和边缘场景。
5. 对资源受限设备有较强的工程实用性。

### 5.10.2 需要接受的边界

在大规模数据中心服务中，真正的瓶颈可能是多请求调度、跨卡并行、服务 API 和运维，而不是单请求能否运行。llama.cpp 也可以提供 server 能力，但实际 concurrency、模型结构支持、grammar、量化和硬件 backend 需按版本测试；“能在笔记本运行”不能推出“适合高并发在线服务”。

这不等于 llama.cpp server 没有 batching：当前官方 server 文档列出 multi-user parallel decoding 和 continuous batching。它用并发 slots 管理请求，并将可兼容的 slot 工作合成 decode batch；不同 LoRA 配置等请求不一定能放进同一个 batch。它的定位仍偏轻量、本地和边缘部署，但“边缘优先”与“无并发 serving”不是一回事，容量要按设备、slot 数、上下文长度、batch 和实际 API 行为测量。[llama.cpp server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

如果 workload 是个人助手、离线文档、边缘设备或数据不能离开本地环境，llama.cpp 的轻量性可能比峰值吞吐更重要。容量报告应使用目标设备的 tokens/s、内存、功耗、首 token 和交互体验，而不是直接套数据中心单位。

GGUF 是模型和量化 artifact 的一种交付格式；选择 `llama.cpp` 时要确认权重文件、tokenizer/chat template 元数据、量化类型、模型架构、CPU 指令集与实际 backend 的组合。GPU offload 的层数、KV cache dtype、上下文长度和 batch 会共同影响显存与速度；即使文件能加载，也仍需检查生成质量、特殊 token、工具格式和长上下文行为。`llama-server` 暴露 HTTP 路由后，访问控制、租户隔离和日志脱敏仍需由部署层负责，不能因模型运行在个人设备上就假设 API 自动安全。

并发 slot 也要转成设备预算来理解。假设一个目标模型每个活跃 token 的 KV 状态约 64 KiB，计划允许 4 个请求各占 4,096 token，则粗略 KV 上限为 $4\times4,096\times64\text{ KiB}=1\text{ GiB}$；把 slot 数加倍到 8，在上下文不变时该部分预算约增至 2 GiB。该数值是按每 token 常量构造的教学假设，实际字节数要按模型层数、KV heads、精度、共享/滑窗机制和实现核算；还要给权重、workspace、图像输入及 runtime 留显存。`--parallel 4` 表示服务槽位配置，不代表设备必然能同时以目标速度完成四个长请求。

当前 server 文档说明 continuous batching 默认开启，并提供并行 multi-user 解码；但请求能否合批还受形状与配置约束。例如不同 LoRA adapter 的请求不会放到同一个 batch，适配器流量不均时实际可用 batch 会小于 slot 总数。对目标 trace 应同时记录活跃 slot、上下文长度、adapter 分布、prompt-cache 命中和 GPU offload 层数。特别是桌面和边缘设备，温度、功耗上限、内存带宽与持续散热会让长时间吞吐低于短跑结果。

因此 llama.cpp 的比较目标应是“在该设备约束下能否持续、可接受地完成这类任务”，而非一定追平数据中心 runtime 的聚合吞吐。用同一批真实化合成输入，先测冷启动、warm steady state、单用户与多 slot，再记录内存、能耗、TTFT/TPOT 和任务成功率；如果模型只能靠缩短上下文或降低精度才能跑起来，就把这些作为服务能力边界明示。当前 README 位于 `master`，本章按 2026-11-02 查阅快照描述，参数默认值应在实际构建 revision 中复核。

设备侧部署还要区分首次加载成本和稳定交互成本。离线批量任务可能容忍较长模型加载、一次性生成许多文本；面向交互的本地助手则更关心冷启动、首 token 和多轮上下文增长。二者即使使用相同 GGUF 文件，也应分别测量并按真实用途设置并发 slot、上下文上限和空闲回收策略。若设备断网，更新权重、模板或二进制的供应链也要有可校验版本和回滚副本；“数据留在本地”解决的是一类数据路径问题，并不自动解决模型更新、鉴权或终端丢失风险。

## 5.11 TGI：历史能力与当前维护状态要分开

Text Generation Inference（TGI）曾是 Hugging Face 生态中重要的文本生成服务方案，提供模型服务、流式输出、batching、量化和常见 API 能力。现有部署仍可能依赖它，迁移需要考虑协议、模型和运维成本。

截至 2026-11-02 查阅的[官方 TGI 文档](https://huggingface.co/docs/text-generation-inference/index)，项目自 2025-12-11 起处于 maintenance mode，只接受小型 bug 修复、文档和轻量维护；[Inference Endpoints 的迁移说明](https://huggingface.co/docs/inference-endpoints/engines/tgi)建议托管新部署评估 vLLM 或 SGLang 等替代引擎。因而新项目不应只因为熟悉 TGI 就默认采用；存量系统则应记录：

1. 当前 TGI 版本、镜像和安全更新策略。
2. 目标模型是否仍有可维护的 backend。
3. vLLM、SGLang 或 TensorRT-LLM 的迁移兼容性。
4. chat template、stop、tool event、metrics 和错误码的差异。
5. 迁移期间如何灰度、双写回放和回滚。

“TGI 过去支持某功能”和“当前新项目适合采用 TGI”是两条不同陈述。官方维护状态比社区文章中的旧 benchmark 更能影响长期选型。

maintenance mode 描述的是项目维护承诺，不等于已部署服务会立即停止，也不表示每个功能当天就失效。存量系统应先盘点当前镜像、模型 artifact、SLA、依赖漏洞处理方式、故障响应负责人和迁移可逆性，再选择原地维持、有限升级或迁移；官方文档的维护提示也没有替你的威胁模型或合同义务作判断。相反，新部署需要把可获得的修复、目标模型支持和团队长期维护能力作为候选条件，不能只复制几年以前的吞吐表。

迁移的核心是重做服务合同，而不是替换容器名。至少比较 tokenizer/template、请求和响应字段、SSE chunk 边界、tool-call parser、finish reason、取消与超时、metrics 名称、错误码、健康检查和模型加载行为。在线系统可先离线回放，再对无副作用请求做影子流量，最后按租户或 workload class 灰度；工具执行、写数据库或支付这类有副作用调用不能在影子路径重复执行，应只比对模型产生的事件或接到隔离的 verifier。

迁移观测面也需要逐项映射。两个引擎即使都暴露名为 `request_latency` 的指标，统计起点、结束事件、取消请求是否入分母、stream chunk 的计数方式也可能不同。先用少量固定请求同时采集客户端与服务端时间戳，核对单位和 request id 关联，再对照旧告警阈值；若语义不一致，就建立明确的新指标或在仪表盘标出断点，不能把新曲线直接拼到旧曲线上解释长期趋势。

例如建立 1,000 条固定回放样本，其中 600 条普通文本、250 条 JSON/schema、150 条工具协议；迁移目标设为至少 99.5% 通过相同的协议/质量门槛。若发现 3 条 schema 解析差异、2 条 stop/finish reason 差异和 1 条取消事件差异，且类别互不重叠，则总失败数为 6，成功率 $994/1,000=99.4\%$，低于设定门槛，不能只因 TTFT 改善而放量。这个例子里的比例是演示验收算法的假设值，不是 TGI 或替代 runtime 的实测。

迁移记录还要保存失败样本和回滚条件：旧服务保留到正在生成的请求能自然结束或被安全取消，回滚时确认重试不会重复触发工具副作用，模型 revision 与模板版本一致。若当前存量 TGI 无法获得足够修复保障，但迁移候选尚未过质量门槛，团队应记录两件事分别推进——风险缓解与替代引擎验收，而不是把项目状态压成“已弃用，所以立即迁移”。截至 2026-11-02 查阅的官方 TGI 文档把新部署建议指向 vLLM/SGLang；那是生态维护方向，不是你的目标配置已经兼容的证据。

迁移也要区分“现在有理由评估”和“现在必须切换”。若服务模型、协议和镜像长期稳定，修复来源明确，故障能被团队承接，原地维护可能是短期风险更低的安排；若安全修复无法获取、模型功能不再支持、升级依赖阻塞，或新增功能只在其他 runtime 中可验证，就应把替代方案列入迁移计划。这个判断依赖组织自身的安全期限和服务合同，不能仅由项目维护标签推出。新引擎上线前，至少完成离线协议回放、工具副作用隔离、目标负载性能测试、灰度观测和可逆回滚；每个门槛都应保留负责人、失败样本和触发条件。

## 5.12 引擎能力矩阵：不要把功能名当成结果

引擎并不是靠品牌名自动获得性能。要理解几种代表路线分别解决了哪个系统瓶颈，再看今天的项目如何组合这些机制。

| 代表方法 | 原问题与核心机制 | 作者报告的证据 | 代价、边界和后续路线 |
| --- | --- | --- | --- |
| Orca | 静态 batch 要等最慢请求结束，新请求只能等整批结束；改为每个模型 iteration 重新调度请求，并只对部分算子做 selective batching。 | GPT-3 175B 的论文设置下，相对 FasterTransformer 在相同 latency 水平报告 36.9× throughput。 | 这是 2022 年特定模型和系统对照，不能当成今天引擎的排名。iteration-level scheduling 解决请求生命周期，KV cache 的动态增长、碎片和共享仍需独立管理。[论文](https://www.usenix.org/conference/osdi22/presentation/yu) |
| PagedAttention / vLLM | KV 长度动态变化，连续分配造成碎片或按最大长度预留；把 KV 放进固定 token block，用 block table 间接寻址，并支持 block 共享。 | SOSP 2023 论文在其模型和 workload 下报告相同 latency 时 throughput 比 FasterTransformer/Orca 提高 2–4×。 | block table 和非连续 KV 布局要求 attention kernel 能读取分页状态。它解决 cache 空间与调度容量问题，但不会自动解决长 prefill 对 decode latency 的干扰。[论文 v1](https://arxiv.org/abs/2309.06180v1) |
| Sarathi-Serve | 大 prefill iteration 会打断正在生成的 decode；将 prompt 切成 chunk，再用 stall-free schedule 把新请求加入而不暂停既有 decode。 | 作者在 SLO 约束下报告 Mistral-7B 单 A100 serving capacity 2.6×，Yi-34B 双 A100 最多 3.7× vLLM。 | chunk token 数、pipeline、上下文长度和 SLO 会改变结果；这是论文实现和 workload 的容量结果，不能直接套到当前 vLLM。后续 runtime 可把 chunked prefill 纳入统一 token budget scheduler。[论文 v3](https://arxiv.org/abs/2403.02310v3) |
| SGLang | 多轮程序、few-shot、树搜索和 Agent 分支反复计算共享前缀；用程序前端表达多次生成，用 RadixAttention 复用 radix tree 中的 KV，并以压缩 FSM 加速约束解码。 | 原论文在所测模型、任务和系统 baseline 上报告最高 6.4× throughput。 | 收益依赖前缀复用和程序形状；唯一 prompt、低 cache hit 或高 eviction 压力会削弱优势。需要一起测复用 token、cache 驻留、会话隔离和端到端任务完成率。[论文 v2](https://arxiv.org/abs/2312.07104v2) |
| vAttention | PagedAttention 的不连续 KV 虚拟布局可能增加 kernel/编程复杂度；以 CUDA VMM 分离虚拟地址预留与物理页映射，保持虚拟地址连续。 | 作者报告在其配置中对 FlashAttention/FlashInfer 的 paged kernels 最高 1.23× throughput。 | 依赖 CUDA VMM 和对应硬件/实现，比较对象也是论文指定 kernel；它替换内存管理路径，不替代请求 scheduler。第 3 章已详细解释其内存机制。[论文 v3](https://arxiv.org/abs/2405.04437v3) |

这几条研究路线并不是五个可直接排名的“引擎版本”，它们针对的是不同层次的瓶颈。Orca 先把调度单位从完整请求改到一次模型 iteration，使先结束的序列能释放位置、新请求可以进入；但仅有动态请求集合，并没有解决 KV cache 因长度变化产生的碎片和重复存储。PagedAttention 用 block 管理 KV，增加可容纳的活动序列，并能共享 cache；它没有自动消除大 prompt 计算对正在 decode 的请求造成的干扰。Sarathi-Serve 将长 prefill 分块，并安排生成请求和 prompt chunk 协同推进；DistServe 进一步研究把 prefill 与 decode 放到独立资源池，在给定 TTFT/TPOT SLO 下配置容量。[DistServe 原论文](https://arxiv.org/abs/2401.09670) 具体的分离路由和通信代价留给第六、八章，这里只把它作为“资源池组织”这一不同轴。

SGLang 的 program/RadixAttention 重点是一次任务包含多个 generation call、分支、共享前缀或结构化输出；它不只是另一种 KV allocator。vAttention 则改变内存映射方式，试图保留虚拟地址连续性；它不是调度器，且其作者的最高 1.23× 来自特定 kernels 对照。实际 serving runtime 会组合多项机制：今天的引擎可能既做 iteration scheduling，也支持分页 cache、chunked prefill 或 prefix reuse。选型时应问“目标问题由哪层机制解决、当前版本哪条路径启用”，而不是把论文算法名和开源项目名当成互斥产品分类。

可以用一个简化队列轨迹把 Orca 的迭代调度与请求级 static batch 分开。假设 batch 有 A、B、C 三个请求，分别还需生成 1、2、4 个 token；新请求 D 在第一个 token step 结束时到达。若系统必须等整组请求都结束才换批次，D 要等 C 的余下 3 个 decode steps；若调度器在 iteration boundary 回收 A 的槽位并接受新请求，D 最早可在下一 step 进入，少等 3 个 step。这个算例只说明调度边界改变排队时间；它没有给出实际毫秒值，也没有计算 D 的 prefill、批次扩缩成本、KV 分配和模型前向，因此不能直接说吞吐会提升某一倍数。

最后要把论文结果、runtime 功能和本机表现分栏记录。论文中的“吞吐提高”可能是在同延迟下比较完成 token，也可能是在固定 SLO 下比较 serving capacity；而产品 benchmark 还要看请求发射方式、输入/输出长度、缓存冷暖、硬件与质量门槛。Orca 的 36.9×、PagedAttention 的 2–4×、Sarathi 的 capacity 倍率、SGLang 的最高 6.4× 和 vAttention 的 1.23×来自不同实验，不能构成同一条排行榜。它们提供的是机制假设，最终结论必须由目标 release 和目标请求 trace 验证。

这些数字来自不同年代、模型、GPU、任务、SLO、baseline 和指标口径，彼此不能排序。它们适合回答“研究者发现了什么瓶颈、做了什么改动、在哪个条件下改善”，不能替代目标环境的回归和容量测试。横向比较之前，应先固定请求长度、到达模式、输出长度、缓存冷热、硬件和完成标准。

## 5.13 Model-protocol fit：兼容性不止是加载成功

### 5.13.1 五层契约

一个模型在目标引擎中“能用”，至少需要检查五层：

| 契约 | 核对内容 | 典型失败 |
| --- | --- | --- |
| weight | checkpoint key、dtype、量化 scale、tie embedding | 加载失败或数值漂移 |
| kernel | attention、MoE、RoPE、MLA/SSM、自定义算子 | 慢路径、错误 shape、性能异常 |
| cache | KV/latent/state、position offset、prefix owner | 长文本偏离、串请求、OOM |
| protocol | tokenizer、template、tool、reasoning、stop、stream | 角色错位、事件丢失、参数解析失败 |
| quality | reference replay、任务正确率、拒答和引用 | 接口成功但能力退化 |

可以把不兼容项写成集合，而不是压成一个总布尔值：

~~~math
D_{\mathrm{compat}}
=
\{d_{\mathrm{weight}},d_{\mathrm{kernel}},d_{\mathrm{cache}},
d_{\mathrm{protocol}},d_{\mathrm{quality}}\}.
~~~

集合中的每一项都应记录“未发现差异、已知降级、未测试或失败”，这样工程人员知道下一步要补什么证据。一个接口返回 200 只说明请求被接受，不说明集合为空。

### 5.13.2 新模型接入的最小回放

普通 Causal LM 的最小回放应覆盖：
1. 空 system、单轮中文、多语言和 Unicode。
2. chat template 的 generation prompt 和 EOS。
3. 短输入、长输入、长输出和取消。
4. 嵌套 JSON 工具参数、未知字段和 schema 错误。
5. reasoning/visible answer 事件（若模型有该协议）。
6. prefix cache 命中与不同用户隔离。
7. 量化与高精度 reference 的质量和 token 对齐。

多模态模型还需要图片/音频占位符、视觉 token 数、预处理耗时和 modality-specific stop。对于混合 attention、MLA、MTP 或 speculative 组件，必须从官方技术报告和当前引擎实现确认状态 layout，不能依据模型名称推测。

### 5.13.3 失败定位顺序

若角色错位或输出乱码，先比对 tokenizer、special token 和 template；若首 token 正常但长文本逐渐偏离，检查 position、cache offset、量化和 kernel；若普通文本正常、工具失败，检查 parser、schema、stop 和授权；若质量相同但速度异常，检查 kernel fallback、batch shape、precision 和通信。这个顺序能把协议错误与性能错误分开。

引擎不支持的能力应有显式回退：reference engine、另一个 backend、较小模型或拒绝请求都可以，但回退原因必须进入 metrics 和日志。不能在 state schema 不兼容时复用旧 cache，也不能把 unknown tool event 当成自然语言继续执行。

五层不是彼此独立的打勾项，它们沿着一次请求依次暴露问题。权重层先确认 checkpoint key、embedding tying、dtype 与量化 metadata 被按预期读取；kernel 层再确认模型结构和张量形状走了正确算子，而不是静默 fallback；cache 层验证位置偏移、窗口状态、prefix owner 和取消后的释放；协议层检查 tokenizer/template、stop、tool/schema、SSE 事件和 usage；质量层最后判断最终任务是否仍正确。若只测一次短文本，最多覆盖其中一小部分：很多 cache offset 问题到长上下文才出现，工具事件丢失也不会反映在 HTTP 200 上。

可以把接入过程实现成逐层缩小的故障定位：先在无并发、短文本上核对模型加载和 greedy token；然后增加长度、batch 和 prefix reuse，观测 cache 与 kernel；接着回放结构化输出、取消、超时和错误响应；最后用真实 workload class 评任务成功和成本。每一层记录固定的模型 artifact hash、runtime revision、backend、device、dtype 和输入 fixture。发现差异时保存最小失败样本，并指出是“已知降级、未测还是失败”，不要把所有差异都归咎于浮点精度。

例如，准备 105 个协议样本：70 条普通文本、20 条 schema、10 条工具调用和 5 条取消。候选引擎分别通过 70、19、9、4 条，则共 $70+19+9+4=102$ 条，整体通过率是 $102/105\approx97.1\%$。若示例门槛为至少 98%，且取消必须 5/5，整体和关键协议两处都不通过；不能因普通文本 70/70 或服务启动成功而宣称模型兼容。这里的样本数、门槛和通过数是教学假设，实际门槛应由业务失败代价与统计把握确定。

失败类型还决定隔离边界：若权重映射不兼容，应拒绝加载该 artifact；若 kernel 有可验证的慢路径，可以按延迟预算选择 fallback 并计入 metrics；若 cache 格式或 position state 不兼容，不能迁移旧 KV；若 tool parser 或授权检查异常，应拒绝执行，不把模型文本猜成调用；若整体任务质量下降，则需暂停灰度并回到 reference 与压缩/模型侧检查。第 24 册讲内部执行路径，本章只要求部署团队知道每层由谁提供证据、失败时如何阻断发布。

## 5.14 用指标比较引擎

### 5.14.1 基本指标

对压测窗口，可记录：

~~~math
\mathrm{QPS}
=
\frac{N_{\mathrm{completed\ requests}}}{T_{\mathrm{wall}}},
~~~

~~~math
\mathrm{TPS}_{\mathrm{out}}
=
\frac{\sum_iO_i}{T_{\mathrm{wall}}},
~~~

~~~math
\mathrm{TTFT}_i
=t_{\mathrm{first},i}-t_{\mathrm{arrive},i}.
~~~

若第 i 个请求输出 O_i 个 token，且 O_i>1，后续 token 的平均间隔可近似为：

~~~math
\mathrm{TPOT}_i
=
\frac{t_{\mathrm{end},i}-t_{\mathrm{first},i}}
{O_i-1}.
~~~

短回答 O_i=1 时，TPOT 应记录为不可用，不要把整个请求 latency 当作 TPOT。报告还应按 workload class 给出 P50/P95/P99、错误率、取消率、OOM/抢占、active tokens、KV bytes、输入 token 吞吐和单位成功任务成本。

### 5.14.2 不同 workload 的压测矩阵

一个有用的压测矩阵至少有：

| 轴 | 桶 |
| --- | --- |
| 输入长度 | 128、512、2k、8k 或真实 P50/P95/P99 |
| 输出长度 | 32、128、512、2k 或真实分布 |
| 并发 | 1、目标平均、目标峰值、过载点 |
| 请求结构 | 短聊天、长 RAG、代码、工具/Agent、结构化 |
| 生成策略 | greedy、sampling、grammar、speculative |
| 精度 | BF16/FP16、FP8、INT8/INT4 等目标格式 |
| 引擎 | reference 与候选 runtime 的固定版本 |

每个格子不要只存 tokens/s。至少保留 request trace、finish reason、质量结果和异常路径；否则一个引擎可能靠截断输出获得更高吞吐，看起来却像性能优越。

压测还必须说清请求是怎样到达的。闭环客户端通常等上一个请求完成才发下一个，请求变慢时客户端会自动降速；这适合测固定并发用户体验，却可能掩盖目标到达率下的排队。开环压测按预设 RPS 或真实到达 trace 发请求，更容易看到队列增长和过载点。vLLM v0.32.0 的 `bench serve` 将 `request-rate`、`burstiness` 和 `max-concurrency` 分开控制，分别对应请求到达率、突发性和客户端并发上限；比较时应选择接近业务流量的模型，而不是只跑“同时发尽可能多请求”。[v0.32.0 Benchmark CLI](https://docs.vllm.ai/en/v0.32.0/benchmarking/cli/)

缓存状态也要成为实验变量。预热后的权重、CUDA graph、prompt prefix 和 KV cache 会让下一轮更快；若同一 prompts 重复回放而未清空 prefix cache，吞吐会因 cache hit 上升。应明确跑冷启动、warm steady state、无 prefix reuse 和目标 prefix hit 四种中的哪一种，并保存服务端 cache 指标。vLLM v0.32.0 benchmark 文档提醒，重复数据可能复用前一次运行的 prefix cache；因此“重跑一次更快”不一定说明引擎代码变快。[v0.32.0 Benchmark CLI](https://docs.vllm.ai/en/v0.32.0/benchmarking/cli/)

报告 SLO goodput 时，可以定义：

~~~math
\mathrm{Goodput}
=
\frac{\left|\left\{i:\,\text{request }i\text{ completed, passed quality checks, and }L_i\leq \mathrm{SLO}\right\}\right|}
{T_{\mathrm{wall}}}.
~~~

这里 $L_i$ 必须明确是 TTFT、TPOT、E2E 还是业务 deadline；质量检查可能是 schema、工具执行、引用验证或任务评分。原始 QPS 只数完成请求，goodput 数满足门槛的请求，两者回答不同问题。latency 的统计单位也要写清：有的工具对每个请求算一次 TPOT，有的把所有 token 间隔合并计算 ITL；speculative decoding 还可能一次 stream chunk 携带多个 token。比较报告应给公式、时间戳位置和样本分母，不能只抄指标名称。

用一组明确的假设数据把口径算一遍：压测窗口 40 秒内完成 100 个请求，输出 token 总数为 44,000；其中 8 个请求未通过质量检查，12 个请求超过所设 latency SLO，且两类有 4 个请求重叠。原始 QPS 是 $100/40=2.5$ request/s，输出吞吐是 $44,000/40=1,100$ token/s；满足两项门槛的请求数则为 $100-8-12+4=84$，goodput 是 $84/40=2.1$ request/s。若只看输出 TPS，候选似乎很强；加入质量和 SLO 后，每秒真正可交付的请求更少。这里的窗口、请求数和失败数全是教学假设，不是引擎测量结果。

再看单请求 TPOT：假设它输出 40 个 token，首 token 在请求到达后 0.40 秒到达，最后一个 token 在 2.74 秒到达，则首 token 之后经过 $2.74-0.40=2.34$ 秒，跨越 39 个相邻 token 间隔，TPOT 为 $2.34/39=0.06$ 秒，即 60 ms。这个数不等于 TTFT，也不包含整项请求的排队前后所有工作；如果工具把多个 token 合在一个 stream event、或把尾部 flush 计时方式不同，ITL histogram 也可能不同。完整指标定义和阶段边界见[第二章《推理基础》](02-推理基础.md)。

要让这些指标能定位问题，服务端最好为同一个 request id 记录到达、进入队列、开始 prefill、首 token、末 token、取消/错误等事件，客户端另外记录收到首末事件的时间。假设请求在 $t=0.00$ 秒到达，$0.18$ 秒进入执行，$0.62$ 秒发出首 token，$1.57$ 秒发出末 token，共生成 20 个 token；则客户端口径 TTFT 是 $0.62$ 秒，排队/准入阶段约 $0.18$ 秒，准入后到首 token 的路径约 $0.44$ 秒，E2E 是 $1.57$ 秒，TPOT 为 $(1.57-0.62)/(20-1)=0.05$ 秒。若只报告“prefill 约 440 ms”，会漏掉排队贡献；若只报告 E2E，也不容易判断是队列还是模型阶段变慢。这里的时间戳和 token 数是教学假设，实际需注明时间由客户端还是服务端采集、首末 event 如何定义，并保证时钟可对齐。

吞吐分母也要固定。在线窗口的输出 token/s 可以按窗口内实际发送的 token 计数，完成请求 QPS 则按完成时间计数；窗口结束时还在生成的请求、被取消的请求和失败请求要单独列明，不能把它们一概丢掉或按完整成功任务计入 goodput。离线 batch 测量可以报告全部工作完成所需时间，但若将结果用于在线选型，还要加入到达间隔、排队和流式交付条件。两种场景可以共享 token 数，却回答不同问题：离线关心任务总处理能力，在线关心负载到来时各类请求是否及时完成。

统计汇总应从样本口径开始。P95 可以是每条请求的 TTFT 分布，也可以是所有 token 间隔的 ITL 分布，不能先对每批次求 P95 再把这些 P95 简单平均；不同长度和不同到达波形的请求也不应默认同权。短聊天、长 RAG、工具调用和长输出最好先分别报告分布与样本量，再按真实流量权重汇总。若只给一个全局均值，长尾失败可能被大量短请求遮住；若只报峰值吞吐，也可能把延迟已越过门槛的请求仍算作成功容量。小样本或短压测只能筛选候选，统计不确定性和正式评估方法留给第七册展开。

成本比较最后要使用相同的“成功工作量”作为分母。若 GPU-hours 按租用价格可换算为成本，就将目标窗口内满足质量、协议和 SLO 的请求数或任务数作为交付量；因重试、回滚、工具失败而消耗的计算仍记入成本。候选 A 即使每秒输出 token 更多，如果 schema 或任务失败率更高，单位成功任务成本可能反而更大。报告可以同时列出 GPU-hours、原始 QPS、output TPS、goodput 与每千个成功任务成本，让读者看见容量、体验和经济性之间的取舍，而不把一个指标伪装成综合质量结论。

指标差异可以帮助提出排查假设，但不能单独证明根因。若候选版本的 P95 TTFT 上升而 TPOT 基本不变，先查看排队、准入和 prefill 阶段；若 TTFT 稳定而 TPOT 变差，再查看 decode 竞争、batch 形状、KV 读取或 stream flush。若两者都变差，可能是到达率超过容量、CPU 入口拥塞、显存压力触发抢占，或硬件时钟和功耗条件不同。每一种解释都要与队列长度、active token、KV 水位、抢占、GPU/CPU 利用率及请求类别的时间序列交叉核对；本章给出的是定位顺序，不是看到某个图形就能断定某个 kernel 出错。

一次公平的引擎比较还要固定运行协议：先声明冷启动是否计入、预热请求如何选、cache 是否清空或按目标 hit rate 保留、压测持续多久、客户端是否开环发请求，以及窗口末尾未完成的请求怎样计数。对每个候选使用同一模型 revision、精度、采样参数和输入输出 trace；如果某个配置无法完成同一输出长度或错误重试更多，要将差异列入结果而不是事后删掉样本。至少重复足以覆盖正常运行波动的多轮，并逐轮保留结果；高风险容量决策再由第七册的统计设计方法评估不确定性，不能把一次短跑的最好值当作稳定能力。

### 5.14.3 把成本和维护纳入选型

可以把一次选型结果表示为证据向量：

~~~math
E_{\mathrm{engine}}
=
(E_{\mathrm{quality}},
E_{\mathrm{latency}},
E_{\mathrm{throughput}},
E_{\mathrm{memory}},
E_{\mathrm{protocol}},
E_{\mathrm{operations}},
E_{\mathrm{cost}}).
~~~

这些项单位不同，不应未经归一化直接相加。一个性能很高的 engine，如果目标模型需要大量手写插件、升级风险高、协议不支持或任务质量退化，单位成功任务成本可能反而更高。团队熟悉度不是软性偏好，它会影响故障恢复时间和长期维护成本。

代码的数据结构把“事实”和“判断”混在同一组字段里，是为了让教学逻辑短小，不适合直接拿来做生产选型表。hardware、serving 和 structured 代表是否满足某条硬条件；out_tps、TTFT、TPOT 是假设测量值；ops_score、model_score、complexity 和 program_score 则是团队主观评定。真实记录应给每个字段补上证据来源、测试环境、版本、评分人和更新时间，否则两个团队输入同样的引擎名称也可能是在比较不同模型或不同请求分布。

最后的加权分数只适合在硬门槛都满足后做偏好排序。把输出吞吐权重调高，可能偏向高并发 API；把程序能力和复杂度权重调高，Agent 场景可能偏向另一候选。若轻微改权重就反转名次，应报告为“当前证据不足以稳定区分”，再补充真实负载或维护成本数据，而不是宣称排行榜有精确答案。此代码也没有建模模型质量门槛、P99、KV 峰值、取消语义、租户隔离、故障恢复或成本价格；这些项目必须在接入清单中逐项补齐。展示的输出与分数由静态手算得到，代码未运行，不能把这段演示当作执行验证。

若把数据中的某个值改成“未知”，实际决策表应保留未知状态，而不是用零分或平均分填上；例如未测过 schema 就应阻止需要结构化输出的 workload 通过硬门槛。一个更完整的审计流程会把每个假设值链接到压测报告，把每个主观分数拆成可解释的子项，并允许团队查看淘汰原因。此 demo 刻意省略了持久化、图表、统计区间和权重敏感性代码，重点是先建立“硬条件过滤—候选排序—失败原因可读”的次序。读者可以替换输入做纸面推演，但在补齐真实证据前，输出只表示该组假设下的程序逻辑，不表示项目可以上线。

例如，`program_score` 在 `agent_program` workload 中才进入加权项，而 `edge_score` 只在 `edge_local` 中参与；同一引擎因此可能在一个 workload 排名靠前，在另一个 workload 根本不合格。把多个 workload 的得分简单平均会丢掉业务流量比例和硬门槛差异，除非团队先定义清晰的流量权重、质量等价条件和合并规则。更可靠的报告保留每类 workload 的候选集合、通过证据和淘汰原因，再由产品目标决定是否部署多条路径。

## 5.16 引擎选型的完整流程

### 5.16.1 第一步：建立 reference path

先用 Transformers 或另一个可信 reference engine 固定 tokenizer、template、stop、采样参数和质量样本。reference path 不需要高吞吐，但要能回答“模型本来应该产生什么 token 和事件”。

### 5.16.2 第二步：验证模型协议

对候选引擎逐项回放：

1. 普通文本和中文/Unicode。
2. EOS、stop string、max output 和取消。
3. 长输入、长输出、prefix cache。
4. JSON schema、工具参数和未知字段。
5. reasoning/visible answer 事件。
6. 量化与高精度结果。
7. 多 GPU、batch、错误和重试。

先排除协议和质量不兼容，再比较性能。否则一个引擎靠忽略工具事件或截断输出获得的“高吞吐”没有意义。

### 5.16.3 第三步：在目标 workload 上压测

固定硬件、driver、engine revision、模型 artifact 和客户端。输入/输出长度、并发、batch token、cache budget 和采样配置要进入报告。至少测：

| 结果 | 解释 |
| --- | --- |
| TTFT P50/P95/P99 | 排队和 prefill 体验 |
| TPOT/ITL P50/P95/P99 | 持续流式速度 |
| E2E P95/P99 | 完整请求尾延迟 |
| input/output tokens/s | prefill 与 decode 的工作量 |
| QPS/goodput | 完成请求和满足 SLO 的请求 |
| KV bytes/watermark | 动态内存压力 |
| OOM/preemption/error | 资源和稳定性 |
| quality/schema/tool pass | 结果可交付性 |

### 5.16.4 第四步：计算维护成本

构建 engine 的时间、插件维护、模型升级、CUDA/driver 兼容、回滚和 on-call 都属于成本。对模型更新频繁的团队，快速适配的价值可能大于峰值 tokens/s；对硬件固定、流量巨大且模型稳定的团队，构建优化 artifact 可能更划算。

这四步应按证据依赖顺序执行：reference path 定义当前接受的行为；协议回放判断候选是否执行同一合同；目标 workload 压测确认在真实负载和目标设备上是否达到服务门槛；维护成本才用于比较已合格方案的长期代价。任一步状态应记为通过、失败或未知，未知不能在汇总表里默认为通过。例如一个模型没有长上下文 cache 回放结果，就不能因为短文本正常而进入生产灰度；需要先补那类证据，或将服务范围明确限制为已测输入。

每个候选的记录至少要包含 artifact hash、runtime/package revision、设备和驱动、dtype/量化、请求 trace、质量集版本、指标时间戳边界、压测持续时间及失败样本。这样升级 runtime 或模型时，团队能区分是输入集变了、配置变了还是代码路径变了。最终选择也应写出淘汰原因和复查触发条件，例如模型结构更新、GPU 型号更换、SLO 调整、维护状态改变或线上 workload 分布明显漂移；单次压测只能支持当前锁定条件下的决定。

## 5.17 常见误解与边界

### 5.17.1 任何模型都能被任何引擎加载

不是。模型可能使用自定义 attention、MoE routing、MLA、递归 state、特殊 tokenizer、量化格式或多模态 projector。加载成功只证明部分权重路径成立，不代表长上下文、工具、cache 和质量都正确。

### 5.17.2 benchmark 第一名永远是最佳引擎

不是。benchmark 的输入长度、输出长度、并发、硬件、精度和是否计入服务开销都会改变排名。一个高 output TPS 的引擎可能牺牲 TTFT、质量或协议完整性。

### 5.17.3 OpenAI-compatible API 等于完全兼容

不是。字段兼容不等于 event、streaming、tool call、reasoning channel、stop、错误码和 usage 口径兼容。要用真实客户端和回放样本检查行为。

### 5.17.4 TGI 仍然是所有新项目的默认选择

不是。TGI 有重要的历史和存量价值，但当前官方文档的 maintenance mode 说明会影响新项目的长期维护选择。存量迁移应评估收益和风险，不应因为一句“已弃用”就跳过协议回归。

### 5.17.5 vLLM 或 SGLang 的功能列表就是性能保证

不是。功能存在只说明 runtime 有实现路径，实际性能取决于模型、kernel、精度、batch、GPU 和 workload。尤其是新模型、自定义算子和结构化/Agent 路径，必须检查是否走慢路径。

### 5.17.6 推理引擎等于完整 AI 平台

不是。引擎负责模型执行，平台还要负责鉴权、限流、路由、审计、质量、安全、灰度、成本和回滚。把 API server 启动起来不等于服务已经具备生产治理。

## 5.18 一个新模型接入与引擎迁移案例

假设团队已经用 Transformers reference path 运行一个 7B 对话模型，准备把它接入 vLLM 作为在线服务；同时，另一个高峰流量场景正在评估 TensorRT-LLM。模型带有 GQA、结构化工具调用和较长上下文，服务要求流式输出、客户端取消、JSON Schema 和租户隔离。这个任务不能从“哪个引擎 benchmark 更高”开始，而应按兼容性和工作负载逐层推进。

第一步冻结 reference artifact。保存权重、模型配置、tokenizer、chat template、generation config、工具 schema、停止规则和评估样本的 revision。对每个样本记录 token ids、assistant 起点、EOS、finish reason、工具事件和最终任务结果。reference 的作用不是追求吞吐，而是定义“这份模型在当前协议下应该怎样行动”。如果模型加载时自动推断了 dtype 或模板，也要把推断后的实际值写入 manifest，不能只记录启动命令。

第二步做五层兼容性回放。weight 层检查权重 key、tie embedding、dtype、量化 scale 和 adapter；kernel 层确认 GQA、RoPE、长上下文和自定义算子没有回退到不适合的路径；cache 层确认 K/V head、position offset、block layout、prefix owner 和取消后的释放；protocol 层回放中文、Unicode、多轮、空 system、工具参数、未知字段、stop 和流式事件；quality 层则比较任务正确率、引用、代码测试、schema 和拒答边界。接口返回 HTTP 200 只说明请求进入了某条执行路径，不能代替这五层证据。

第三步区分“输出不同”和“行为错误”。不同 kernel 的浮点舍入可能让低温采样的某个 token 改变，但如果 token ids 只在非确定性 sampling 下偶尔变化，应该记录统计分布和任务结果；如果 assistant 起点、EOS、tool event 或结构化字段系统性变化，则是协议兼容问题，不能用“浮点误差”解释。长文本逐步偏离时，优先检查 position/cache offset、量化和模型结构映射；普通文本正常而工具失败时，优先检查 parser、schema、stop 和执行器授权。

第四步在目标 workload 上压测。分别准备短聊天、长 RAG、代码生成和 Agent 工具调用四类请求，固定 GPU、驱动、模型 revision、精度、采样配置和客户端。每个引擎都记录 TTFT/TPOT 的 P50/P95/P99、E2E、输入/输出 token 吞吐、KV bytes、抢占、OOM、取消率、schema/tool pass 和单位成功任务成本。特别要观察引擎是否通过截断长输出、忽略工具等待或改变 finish reason 获得较高 tokens/s；这样的数字不能与 reference 的完整任务结果直接比较。

若 vLLM 在通用 serving workload 上满足 SLO，而 TensorRT-LLM 在固定 NVIDIA 集群上进一步降低 TPOT，最终可以采用“双路径”：vLLM 负责快速适配和灰度，TensorRT-LLM 负责稳定的大流量模型。双路径会带来回归和运维成本，因此两个引擎必须共享同一份协议测试、质量集、审计事件和回滚标识；不能让一条路径悄悄使用不同的 chat template 或 stop 规则。

把前面的分钟级 workload 代入容量规划，假设短聊和 RAG 合计需要约 2,933 输出 token/s，且每个副本只计划运行到其同 trace 实测吞吐的 80%，则每副本的安全容量为 $0.8R$，副本数估算为 $N=\lceil2,933/(0.8R)\rceil$。若某候选单副本在固定混合 trace 上测得 $R=1,900$ token/s，则 $N=\lceil2,933/1,520\rceil=2$；若另一个候选 $R=1,800$，则 $N=\lceil2,933/1,440\rceil=3$。这些数值是规模估算假设，尚未覆盖故障冗余、路由不均、token 长尾和 prefill 分布，不能当作生产副本数承诺。更重要的是，只有 TTFT、TPOT、协议质量都过门槛的候选才带入这个公式：若 2,200 token/s 的方案因短聊 TTFT 超标，较高吞吐也不能让它进入选型结果。

副本数算完后还要用实际并发重新回放，因为多副本会改变前缀 cache 命中、负载均衡、热模型内存和请求分布；用单副本的 $R$ 线性外推只是初始估算。灰度时再对比线上 workload class 的 goodput、p95/p99、错误率和单位成功任务成本。若只有少量 Agent/工具流量能从 SGLang 的程序执行或前缀复用获益，可以按已验证的 workload class 单独路由；每条路径都要保留相同的权限、质量、观测和回滚契约。

第五步安排灰度和失败回退。新引擎先做离线 replay，再做影子流量，随后按租户或 workload class 放量。灰度期间若速度提升但长上下文引用率下降，或者 schema 合法率正常但工具权限拒绝事件消失，应立即暂停放量并保留新引擎的完整 trace。回退不只是切换服务地址，还要处理正在生成的请求、prefix cache、模型 revision、客户端重试和工具幂等；旧引擎必须保留到这些状态都能安全结束或取消。

这个案例的结论不是某个引擎永远更好，而是选型需要把“模型能否正确执行”“协议是否兼容”“目标 workload 是否满足 SLO”“长期维护是否可承受”分别证明。引擎功能列表提供候选路径，reference 回放排除语义差异，压测和质量集决定当前选择，灰度与回滚决定它能否进入生产生命周期。

## 5.20 小结

推理引擎的价值不是把一次 generate 调快一点，而是把模型执行变成可调度、可并发、可回收、可观测的 runtime。它要管理请求生命周期、prefill/decode、KV Cache、batch、解码、流式事件、并行、量化和错误。

Transformers 适合 reference、研究和小规模实验；vLLM 常作为通用开源 serving 的候选；SGLang 把结构化 LLM 程序和复杂执行作为重点；TensorRT-LLM 适合 NVIDIA 固定硬件上的深度优化；LMDeploy 需要按 backend 和模型矩阵实测；llama.cpp 更适合本地和边缘；TGI 具有存量历史价值，但当前 maintenance mode 会影响新项目选择。

选型必须从 workload 和协议开始，用 reference 回放排除兼容性问题，再比较 TTFT、TPOT、P99、tokens/s、cache、错误、质量和维护成本。引擎启动成功只是执行链路的一部分，完整生产服务还需要平台层的鉴权、限流、监控、灰度、回滚、安全和成本治理。
