# 第十一章：监控、评估与安全

模型服务返回 HTTP 200，只能说明一次调用在协议层结束了。它没有说明回答是否
正确，是否引用了真实证据，是否泄露了数据，也没有说明这次调用消耗了多少
GPU 时间。大模型线上系统的故障，很多时候不是进程崩溃，而是“看起来正常”
地变慢、变贵、答错或越过了权限边界。

因此，监控、评估和安全不是部署完成后的附属工作。它们共同构成一条反馈回路：
请求产生 trace，trace 形成性能和成本指标，抽样请求进入质量与安全评估，评估
结果反过来决定是否继续放量、暂停变化、修复数据或回滚 artifact。没有这条回路，
系统只能知道“模型已经上线”，却不知道它是否仍然适合当前业务。

本章先从一次请求的完整时间线开始，再分别讨论 SLI/SLO、吞吐和成本、日志与
trace、质量评估、幻觉、安全攻击、隐私、灰度回滚和事故响应。代码示例使用
标准库模拟一小段请求日志，重点是展示怎样保留可解释的诊断字段；它不能代替
真实监控平台、人工抽样和目标硬件上的压测。

## 1. 从“服务活着”到“行为可解释”

### 1.1 四种不同的线上正确性

初学者可以把线上健康先拆成四个问题：

1. 系统能不能接收和完成请求。
2. 请求能不能在用户承诺的时间内完成。
3. 回答能不能解决用户的任务。
4. 系统有没有泄露、越权或产生不可接受的风险。

这四个问题对应的证据不同。HTTP 成功率属于第一个问题，TTFT 和 P99 属于第二
个问题，引用支持率和任务完成率属于第三个问题，攻击成功率和有害输出漏放率
属于第四个问题。一个指标变好，不能自动推断另外三个指标也变好。

例如，系统通过把回答截短而降低了总延迟，但任务完成率下降；通过更激进地
拦截而降低了有害输出漏放率，但正常用户的误报率上升；通过开启更大的上下文
而提高了召回，却让 KV Cache 紧张并拖慢所有租户。只有把指标放在同一条请求
链上，才能解释这些取舍。

### 1.2 四层观测对象

一个大模型服务通常需要四层观测：

| 层次 | 要回答的问题 | 典型证据 |
| --- | --- | --- |
| 基础设施 | 机器和加速器是否健康 | CPU、内存、GPU、网络、磁盘、ECC |
| 推理服务 | 请求怎样被调度和生成 | 队列、batch、prefill、decode、KV |
| 业务语义 | 输出是否完成了任务 | 结构字段、引用、用户反馈、人工评分 |
| 风险治理 | 是否发生越权或危险行为 | 策略版本、拦截、泄漏、攻击样本、审计 |

基础设施指标更接近原因，业务指标更接近结果。GPU 利用率高可能是吞吐充足，
也可能是长请求把卡拖在高负载上；用户点踩率上升可能是模型退化，也可能是
上游检索为空。排查时要沿着 trace 把原因和结果连接起来，不能用单一仪表盘
代替分析。

### 1.3 请求 trace 是共同语言

一次请求的 trace 可以包含如下事件：

~~~text
request_received
  -> authenticated
  -> routed
  -> queued
  -> prompt_assembled
  -> prefill_started / prefill_finished
  -> first_token
  -> decode_finished
  -> safety_checked
  -> response_sent
  -> billing_recorded
~~~

每个事件最好带有 request_id、trace_id、tenant_id、model_revision、prompt_revision、
policy_revision、input/output token 数、队列状态、cache 命中和错误类别。原始
prompt、完整响应和文件内容不应默认进入所有日志；trace 可以保存摘要、内容
哈希、长度和受控的引用，以便在需要时由有权限的系统取回。

日志、metrics、trace 和 profile 的职责不同：

| 数据 | 最擅长回答 | 例子 |
| --- | --- | --- |
| 日志 | 发生了什么离散事件 | OOM、工具失败、策略拦截 |
| Metrics | 某个量随时间怎样变化 | P99、队列长度、token/s |
| Trace | 一次请求慢或错在哪里 | RAG、模型、审核各占多少时间 |
| Profile | CPU/GPU 时间花在哪里 | kernel、解码器、内存拷贝 |

把 prompt 内容直接作为 metrics label 会产生极高的基数，也会把隐私带进监控
系统。标签应使用有限集合，例如模型版本、租户类型、路由、错误类别和任务
类型；请求级细节放在 trace 或受控日志中。

## 2. 延迟、吞吐与 SLO

### 2.1 从请求时间线拆出 TTFT

对第 i 个请求，首 token 延迟可以近似拆成：

~~~math
T_{\mathrm{TTFT},i}
=
T_{\mathrm{route},i}
+T_{\mathrm{queue},i}
+T_{\mathrm{tokenize},i}
+T_{\mathrm{prefill},i}
+T_{\mathrm{first\_decode},i}
~~~

T_route 是鉴权、路由和请求解析，T_queue 是等待调度，T_tokenize 是 tokenizer，
T_prefill 是处理输入上下文，T_first_decode 是产生第一个输出 token 的时间。
RAG 检索、工具调用或多模态预处理如果发生在模型前面，也应作为 trace 的独立
阶段，而不是全部算进一个无法解释的 route 字段。

端到端时间可以写成：

~~~math
T_{\mathrm{E2E},i}
=
T_{\mathrm{TTFT},i}
+T_{\mathrm{decode\_rest},i}
+T_{\mathrm{post},i}
+T_{\mathrm{safety},i}
+T_{\mathrm{network\_tail},i}
~~~

流式接口中，用户先感知 TTFT 和 token 间隔；非流式接口中，用户只看到最终
E2E。两种接口应分别定义 SLO，不能用一个平均 latency 覆盖所有产品形态。

### 2.2 TPOT、ITL 和输出长度

如果第 i 个请求生成了 O_i 个 output token，后续 decode 的平均 token 间隔可以
估算为：

~~~math
\mathrm{TPOT}_i
=
\frac{T_{\mathrm{decode\_rest},i}}{\max(O_i-1,1)}
~~~

单 token 输出时，分母不能写成零；此时 TPOT 只是一个没有太多统计意义的回退
值。更细的指标是每个相邻 token 之间的 ITL，它可以暴露 batch 更新、抢占、
垃圾回收和跨卡通信造成的抖动。

TPOT 受输出长度、batch、KV Cache、采样策略和 GPU 拓扑影响。短回答的平均
TPOT 很好，不代表长回答的 P99 不会抖动；因此报表应按任务类型、输入长度、
输出长度和租户分层。

### 2.3 分位数不是最大值

对一个时间窗口内的延迟随机变量 X，q 分位数可写成：

~~~math
P_q(X)
=
\inf\{x:F_X(x)\ge q\}
~~~

P50 描述中位数，P95 和 P99 关注长尾。少量样本时，P99 的估计非常不稳定；
把八个样本中最大的一个直接称为 P99，会给人一种精确但错误的感觉。监控系统
应使用支持分位数估计的 histogram 或 quantile sketch，并同时报告样本量和
时间窗口。

分位数还要和请求分层一起看。全局 P95 可能正常，但某个长上下文租户、某个
多模态路由或某个地区已经超时。聚合时要避免无限制的高基数标签，却要保留
足够的 cohort 信息用于定位。

### 2.4 SLI、SLO 和错误预算

SLI 是实际测量的指标，SLO 是对该指标的目标。例如，一个服务可以把“在 2 秒
内返回可用首 token 的请求比例”定义为：

~~~math
\mathrm{SLI}_{\mathrm{TTFT}}
=
\frac{\sum_{i=1}^{N} I(T_{\mathrm{TTFT},i}\le \tau)}
{N}
~~~

I 是指示函数，满足条件时取 1，否则取 0，tau 是产品约定的阈值。若目标 SLO
为 99.5%，允许的失败比例就是：

~~~math
B_{\mathrm{error}}
=
1-\mathrm{SLO}
~~~

这个预算不是“只要平均延迟好就可以忽略长尾”的理由。模型服务还应定义可用性、
流式中断、任务完成、引用支持和安全事件等不同 SLI；安全事故不能用更好的
吞吐抵消。

### 2.5 吞吐要用 token 口径

QPS 只告诉你完成了多少次请求，不能告诉你处理了多少工作。常见吞吐指标包括：

1. input tokens/s，主要反映 prefill。
2. output tokens/s，主要反映 decode。
3. total tokens/s，用于整体资源核算。
4. 每卡 tokens/s，用于横向比较副本。
5. 每种模态的像素、音频秒数或视频帧处理量。

两个 QPS 都是 1 的请求可能一个只有 100 个输入 token，另一个有 8000 个输入
token 和 2000 个输出 token。后者对 prefill、KV Cache 和 GPU 时间的压力远大于
前者。容量报表如果只有 QPS，就无法解释流量分布变化。

## 3. GPU、KV Cache 与资源健康

### 3.1 GPU 利用率的正确解读

GPU utilization 低可能是请求不足，也可能是 CPU 解码、对象存储、RPC、batch
等待或调度器没有及时供给数据。GPU utilization 高可能代表吞吐良好，也可能
意味着队列和 P99 已经恶化。必须把利用率和队列长度、TTFT、TPOT、显存、输入
长度一起观察。

可以用一个简化的资源占用率说明排队风险：

~~~math
\rho=\frac{\lambda}{\mu}
~~~

lambda 是进入速率，mu 是稳定服务速率。当 rho 接近 1，微小的输入长度变化、
GPU 抖动或重试就会把等待时间推高。这个公式不能替代真实调度模型，但能帮助
初学者理解“卡还没完全打满，为什么用户已经排队”。

### 3.2 显存账本

线上显存至少拆成：

1. 模型权重。
2. 活跃请求的 KV Cache。
3. activation 和临时 workspace。
4. 多模态 encoder 的中间表示。
5. CUDA allocator 的碎片和保留空间。
6. 监控、通信和运行时的额外缓冲。

长上下文、高并发、多图和长输出都会增加动态部分。显存使用率接近上限时，
需要记录是哪类请求贡献了增长，而不是只记录某一时刻的总字节数。前一章的
KV Cache 公式可以用于粗估；线上 trace 还应记录实际序列长度、block 数、抢占
次数、cache 命中和释放延迟。

### 3.3 OOM 和资源级错误

OOM 可能杀死 worker，使同一副本上的流式请求全部中断，也可能留下需要重启的
GPU 状态。一次 OOM 事件至少应关联：

1. 模型、runtime 和量化版本。
2. 请求输入、输出和多模态序列长度。
3. 当时的并发、batch 和 KV 使用。
4. GPU 总显存、已分配和已保留空间。
5. 触发 OOM 的阶段和错误栈。
6. 受影响的 request_id、attempt_id 和恢复动作。

恢复时要区分单请求超预算、批次组合不当、内存泄漏和节点硬件故障。简单增加
重试会让同一块已经紧张的 GPU 更快进入故障循环。

## 4. Token、GPU 时间与单位成功成本

### 4.1 记录完整的成本组成

成本不是只有供应商发票上的 prompt token。一个自部署请求可能消耗：

1. 输入和输出 token 的 GPU 计算。
2. 视觉 token、音频秒数和视频帧的 encoder 计算。
3. embedding、reranker、OCR、ASR 和安全分类器。
4. GPU 保持在线的闲置时间和副本预留。
5. 网络、对象存储、日志和评估标注。
6. 失败请求、超时重试和 shadow traffic。

可以先用线性模型做内部核算：

~~~math
C_i
=
aP_i+bO_i+cV_i+dE_i
+eG_i+fS_i+gR_i
~~~

P_i 和 O_i 是输入、输出 token，V_i 是视觉或其他模态工作量，E_i 是 embedding
和 reranker 等辅助工作量，G_i 是 GPU 毫秒，S_i 是存储和网络量，R_i 是重试
工作量。a 到 g 是内部成本权重。它不是云厂商账单公式，而是避免把不同资源
混为一次“请求成本”的账本。

### 4.2 按责任边界聚合

成本应该至少按租户、应用、接口、模型版本、路由、任务类型和时间窗口聚合。
进一步还可以区分：

1. 用户主动请求和系统重试。
2. 正式流量和 shadow 流量。
3. cache hit 和 cache miss。
4. 成功任务、业务拒答和基础设施失败。
5. 在线交互和离线批处理。

总成本增加并不一定是系统变贵了，可能只是请求量增加；单位成本增加也不一定
是模型变了，可能是 prompt 模板变长、cache 失效或失败重试。没有这些维度，
告警只能说“贵了”，不能指出责任位置。

### 4.3 单位成功任务成本

对 Agent、RAG 和多模态抽取，成功请求数比总请求数更有意义：

~~~math
C_{\mathrm{success}}
=
\frac{\sum_i C_i}
{N_{\mathrm{successful\ tasks}}}
~~~

成功的定义要与业务契约对应。例如发票抽取需要字段和证据都正确，语音助手
需要完成一次被用户接受的动作，RAG 回答需要被证据支持。把所有 HTTP 200 都
算成成功，会让拒答、幻觉和工具失败的成本被隐藏。

### 4.4 成本异常

成本告警应和性能、质量一起解释。常见信号包括 prompt 长度突增、输出长度
突增、缓存命中下降、失败重试增加、某租户 GPU 毫秒异常、shadow 流量比例
错误和安全分类器被大量触发。对于高风险成本异常，先限制异常租户或任务类型，
再调查原因；不要直接全局关闭安全检查。

## 5. 质量评估的完整闭环

### 5.1 评估样本必须有契约

一个可复现的评估样本不只是问题和答案，还应记录：

1. 任务类型、领域和风险级别。
2. 输入版本、文档版本、权限和时间范围。
3. 期望答案、可接受答案或结构化标签。
4. 证据范围、工具预期和副作用约束。
5. 评估器版本、模型版本和解码参数。
6. 失败分类以及是否允许拒答。

没有输入版本和权限信息，RAG 评估无法判断“没找到”是索引旧了还是本来就不
允许读取；没有工具预期和副作用标签，Agent 评估可能把一次危险的错误动作
误认为“完成任务”。

### 5.2 离线评估和切片

离线评估的优势是可重复，适合比较模型、prompt、检索器、解码参数和安全策略。
但平均分会掩盖切片退化，因此至少要按以下维度切片：

| 切片 | 需要观察的变化 |
| --- | --- |
| 输入长度 | 长上下文、截断、TTFT、引用丢失 |
| 语言和领域 | 术语、数字、代码和多语言差异 |
| 任务类型 | 摘要、抽取、问答、工具和拒答 |
| 风险级别 | 安全召回、误报和人工升级 |
| 模态 | 图片、OCR、ASR、视频和纯文本 |
| 租户或来源 | 数据权限、分布和新鲜度 |

评估集还要防止污染和过拟合。反复用同一批 bad case 调 prompt，最终只能证明
系统记住了这批样本；应保留冻结测试集、时间切分集和新近线上回放集。

### 5.3 在线抽样

线上抽样能观察真实输入分布和新型失败，但涉及隐私和抽样偏差。高满意度用户
更愿意点赞，严重失败用户可能直接离开，因此反馈不是无偏标签。抽样策略应
同时覆盖：

1. 随机请求。
2. 长尾请求。
3. 高成本请求。
4. 被安全策略拦截或拒答的请求。
5. 用户点踩、重试或转人工的请求。
6. 新模型、新租户和新路由的请求。

标注前要做数据分级、脱敏和访问授权；不能为了评估而把合同、源代码或医疗
记录复制给无权限的标注者。

### 5.4 自动指标和人工判断

自动评估适合规模化，人工评估适合复杂语义和高风险样本。常见自动指标有：

1. exact match、字段校验和数值误差。
2. 引用是否存在、是否指向正确文档和时间范围。
3. JSON/schema、工具参数和状态迁移是否符合约束。
4. RAG 的召回、证据支持和答案一致性。
5. 安全分类器、拒答和敏感字段检测。

LLM-as-a-judge 可以帮助处理开放式答案，但 judge 也可能受到答案顺序、长度、
措辞、模型偏好和提示词影响。使用 judge 时应固定 rubric、随机交换候选顺序、
抽取人工复核样本，并报告人与 judge 的一致性。judge 分数是一个测量工具，不
是真值本身。

### 5.5 质量分数和不确定性

若 M 个样本的评分为 s_j，平均分可以写成：

~~~math
\bar{s}
=
\frac{1}{M}\sum_{j=1}^{M}s_j
~~~

对“是否成功”这种二元指标，样本比例为：

~~~math
\hat{p}
=
\frac{k}{M}
~~~

当 M 很小时，0.99 和 0.95 之间的差异可能只是抽样波动。生产发布比较应报告
置信区间或至少报告样本量、分层结果和人工复核数。不要把单次小样本跑出的
最高分写成稳定能力。

### 5.6 用户反馈不能直接当标签

点赞、点踩、重试、复制、转人工和停留时间都是有用信号，但它们的语义不同。
点踩可能表示事实错误、风格不喜欢、等待太久或产品流程不顺。最好把反馈和
请求 trace、任务完成、证据支持和人工标签结合，再形成质量分析，而不是直接
把点踩率当作幻觉率。

## 6. 幻觉、证据支持与拒答

### 6.1 先区分失败来源

“回答错了”可能来自不同层：

1. 文档没有被解析或召回。
2. 权限过滤掉了正确证据。
3. reranker 把噪声排在前面。
4. 上下文组装丢掉了条件、时间或否定。
5. 模型没有忠实使用证据。
6. 后处理或引用绑定发生错误。

如果把所有错误都归因于模型，就会错过切分、索引、权限和 prompt 的改进机会。
反过来，如果召回和证据都正确而回答仍然违背证据，才应重点调查模型和生成
控制。

### 6.2 Claim-level 检查

一段答案可能包含多个事实。可以先把答案拆成 claim，再检查每个 claim 是否
有证据支持：

~~~text
答案
  -> claim_1 / claim_2 / claim_3
  -> 证据 span、文档版本和时间范围
  -> supported / contradicted / unsupported
~~~

证据支持率可定义为：

~~~math
R_{\mathrm{support}}
=
\frac{N_{\mathrm{supported\ claims}}}
{N_{\mathrm{claims}}}
~~~

它不能替代答案正确率。一个答案可能每句话都引用了相关文档，却把文档中的
条件理解反了；因此还需要事实校验、数值规则和人工抽样。

引用质量也要拆开：

1. citation precision：展示的引用是否真的支持对应 claim。
2. citation recall：需要引用的 claim 是否都提供了证据。
3. evidence freshness：证据是否在有效时间内。
4. evidence permission：当前用户是否有权读取证据。

### 6.3 降低幻觉的工程手段

常见手段包括：

1. 提高解析、召回和 rerank 的质量。
2. 让上下文保留来源、标题、时间和权限范围。
3. 要求模型对无证据问题明确说明不知道。
4. 对关键字段使用规则、数据库或第二来源复核。
5. 对高风险答案设置人工升级和更保守的输出格式。
6. 记录未支持 claim，形成后续评估样本。

“提示模型不要幻觉”只能改变一部分行为，不能代替证据链。允许拒答也不是
失败，它可能是高风险任务中更正确的结果；但拒答率突然增加，仍然需要调查
召回、权限、模型和安全策略是否发生了变化。

## 7. 有害输出与安全指标

### 7.1 安全策略是业务契约

有害输出范围取决于业务和用户群。面向公众的聊天产品、代码助手、医疗问答、
金融客服和企业内部搜索的风险边界并不相同。策略至少要定义：

1. 风险类别和严重程度。
2. 输入、输出、流式片段和工具结果的检查位置。
3. 拒答、改写、人工处理和限流动作。
4. 允许的解释、帮助信息和升级路径。
5. 策略版本、评估集和误报处理方式。

### 7.2 混淆矩阵

安全分类器不能只报告拦截率。对已标注的危险样本，漏放率可以写成：

~~~math
\mathrm{FNR}
=
\frac{N_{\mathrm{harmful\ and\ not\ blocked}}}
{N_{\mathrm{harmful}}}
~~~

对安全的正常样本，误拦截率可以写成：

~~~math
\mathrm{FPR}
=
\frac{N_{\mathrm{safe\ and\ blocked}}}
{N_{\mathrm{safe}}}
~~~

对攻击评估集，还可以报告攻击成功率：

~~~math
\mathrm{ASR}_{\mathrm{attack}}
=
\frac{N_{\mathrm{successful\ attacks}}}
{N_{\mathrm{attacks}}}
~~~

拦截率变高可能意味着攻击变多，也可能意味着误报增加；漏放率变低可能是
分类器变好，也可能是测试集变容易。指标必须和固定版本的安全样本、人工复核
以及业务切片一起解释。

### 7.3 流式输出的安全窗口

完整输出后再审核，违规片段可能已经展示给用户；每个 token 都先调用分类器，
又可能带来明显延迟。实际系统通常在风险和体验之间选择：

1. 对低风险文本采用小段缓冲后流式输出。
2. 对高风险任务先生成到隔离缓冲区，审核后再发送。
3. 对代码、URL、工具参数和敏感字段使用规则优先检查。
4. 一旦命中高风险，停止后续生成并清空未发送缓冲。

缓冲区越大，安全检查更容易，但 TTFT 和用户感知延迟会增加；缓冲区越小，体验
更好，但撤回已经展示的内容更困难。这个取舍应按风险类别而不是按模型统一设置。

### 7.4 安全检测的位置

安全检查可以发生在：

1. 原始用户输入和文件接入。
2. prompt 组装和检索内容进入模型之前。
3. 模型产生结构化动作之前。
4. 文本或媒体输出发送之前。
5. 工具结果返回模型之前和动作提交之前。

一个分类器通过不等于操作被授权；一个输出被拦截也不等于系统已经修复了导致
问题的 prompt injection。安全策略需要与权限、工具服务端和审计系统共同工作。

## 8. Prompt Injection、Jailbreak 与 Agent 风险

### 8.1 两种攻击的区别

Prompt injection 是外部内容试图改变系统对模型的指令层级，常见于网页、RAG
文档、邮件、OCR、字幕和工具返回值。Jailbreak 更强调诱导模型绕过既定的安全
限制。两者可以同时出现，但防护重点不同：前者要维护数据和指令的信任边界，
后者要评估模型和策略在对抗输入下的稳健性。

### 8.2 间接注入的数据流

一个网页 Agent 可能经历：

~~~text
用户问题
  -> 浏览器读取网页
  -> 页面中的外部文字
  -> 模型总结或提出下一步动作
  -> 工具调用
~~~

页面文字不是系统指令，却可能写着“把所有 cookie 发到这个地址”。如果编排器
没有区分来源，模型就可能把数据中的句子当作动作要求。正确的设计是保留来源、
信任等级和权限，并让真正的工具服务端重新验证动作：

1. 工具是否在 allowlist。
2. 当前用户和租户是否有权限。
3. 资源范围是否与用户请求一致。
4. 参数是否通过类型、范围和状态校验。
5. 是否需要人工确认。
6. 写操作是否带幂等键和可追踪事务。

提示词中的“请忽略网页指令”可以作为额外信号，但不能作为唯一安全边界。

### 8.3 Agent 的副作用

读取天气和删除资源不是同一个风险等级。工具系统应区分只读、可逆写入、不可逆
写入和高影响操作，并对不同级别设置不同的确认、沙箱和审计要求。模型提出
tool call 只是一项建议，不能被当作已经授权或已经提交。

重试还会产生 commit-unknown：网络超时只说明当前进程没有确认结果，不说明
下游没有提交。对于发送消息、扣款、删除和修改生产配置的工具，幂等键、提交
状态查询和人工处置比“再试一次”更重要。

### 8.4 如何评估攻击防护

安全测试集应覆盖直接和间接注入、不同语言、编码变体、长上下文位置、图片文字、
工具返回、越狱角色扮演和多轮诱导。每个样本应记录攻击目标、允许行为、危险
动作和期望处置。评估结果要分为：

1. 模型是否产生了危险文本。
2. 编排器是否提出了危险动作。
3. 服务端是否阻止了未授权动作。
4. 是否泄露了敏感数据。
5. 是否留下了可复盘的审计记录。

最后一项很容易被忽略。一次攻击被阻止但没有 trace，下一次同类攻击仍然只能
靠猜测排查。

## 9. 日志最小化与隐私保护

### 9.1 数据分类

大模型日志可能包含姓名、电话、证件、合同、源代码、医疗记录、内部业务数据、
上传文件的 OCR 文本、音频转写和工具参数。建议在进入日志和评估系统前先做
数据分类：

| 类别 | 例子 | 默认处理 |
| --- | --- | --- |
| 公共 | 模型版本、状态码、长度 | 可进入聚合指标 |
| 内部 | prompt 摘要、业务标签 | 受限访问和短期保存 |
| 敏感 | 个人信息、合同、代码 | 脱敏、加密、严格授权 |
| 高敏 | 密钥、密码、医疗和支付数据 | 默认不落盘，必要时隔离保存 |

分类不是一次性标签。用户上传的“普通图片”经 OCR 后可能变成高敏文档，缓存
和 trace 应随派生结果提高保护等级。

### 9.2 最小化和可复盘的平衡

“完全不记录”会让事故无法排查，“全量记录”又会制造新的泄露面。可以优先
保存：

1. 内容长度、哈希、类型和版本。
2. 脱敏后的结构化字段。
3. 错误类别、策略决定和时间线。
4. 受控的证据引用，而非全部原文。
5. 经过授权的少量原始样本和访问审计。

文件 URL、临时下载链接、API key、Authorization header 和工具 secret 不应
进入普通日志。调试模式也应有明确的过期时间，不应成为永久绕过隐私策略的
开关。

### 9.3 脱敏不是完美过滤器

规则、正则和 NER 可以识别手机号、邮箱、证件和姓名，但会有漏检和误检。日志
系统需要对脱敏结果本身做抽样审计，特别关注图片 OCR、代码、混合语言和编码
绕过。高敏字段可以使用不可逆替换或结构化掩码；需要回看原文时，通过受控的
访问流程获取，不把解密能力放进普通分析工具。

### 9.4 生命周期和删除

隐私保护还要覆盖：

1. 原始输入、派生 artifact 和缓存保存多久。
2. 谁能读取日志、trace、评估样本和备份。
3. 删除请求是否传播到副本、队列、缓存和标注系统。
4. 评估样本是否允许跨租户复用。
5. 数据是否用于训练、提示优化或人工质检。

删除一条原始记录后，如果派生 OCR 文本、embedding、结果缓存和 trace 仍能被
查询，业务上的删除并没有真正完成。

## 10. 灰度发布、比较与回滚

### 10.1 发布的是一个 artifact bundle

线上行为不只由模型权重决定。一次变化可能同时包含：

1. 权重和 tokenizer。
2. processor、chat template 和 system instruction。
3. runtime、量化和解码参数。
4. RAG parser、embedding、索引和 reranker。
5. tool schema、权限策略和安全分类器。
6. 监控采样、缓存格式和结果后处理。

这些组件应使用可追踪的 bundle revision。只回滚容器而保留新索引或新 prompt，
可能得到一个既不属于旧版本也不属于新版本的混合行为。

### 10.2 Shadow 与 canary

Shadow traffic 把请求复制给新版本，但不把新版本结果交给用户，适合比较：

1. 阶段延迟和资源消耗。
2. token 分布和 cache 命中。
3. 输出结构和引用差异。
4. 安全分类和工具提案差异。

它不能直接测量用户满意度，也可能因为复制请求改变资源负载而影响生产版本；
因此 shadow 流量应计入成本，并限制敏感数据的复制范围。

Canary 则把一小部分真实流量交给新版本。分流最好按稳定 cohort 进行，例如
租户、业务线或请求类型，而不是每个请求随机变化；这样同一个用户在短时间内
不会因为版本跳变而难以解释。

### 10.3 比较信号而不是一个总布尔值

新旧版本比较至少要同时报告：

| 维度 | 绝对值 | 与基线的差异 |
| --- | --- | --- |
| 延迟 | P50/P95/P99、TTFT、TPOT | 是否超过 SLO |
| 可靠性 | 错误、超时、流中断 | 是否集中在某 cohort |
| 质量 | 任务成功、引用支持、人工分 | 哪些切片退化 |
| 安全 | FPR、FNR、攻击成功率 | 正常输入误伤或危险漏放 |
| 成本 | token、GPU 毫秒、单位成功成本 | cache 和重试的贡献 |

这些信号不能互相抵消。例如安全漏放率恶化时，不能因为质量提高就继续扩大
流量；质量下降只发生在一个高价值租户时，也不能因为全局平均分正常而忽略。

### 10.4 回滚和暂停

回滚是把流量和 artifact 恢复到已知版本；暂停是停止继续放量并保留当前流量
以便调查。可回滚的系统需要：

1. 保留旧模型、prompt、索引和安全策略。
2. 记录每个请求使用的 bundle revision。
3. 让缓存 key 包含版本，或提供清晰的失效方式。
4. 预先准备流量切换、停止任务和恢复队列的操作。
5. 演练工具副作用、异步任务和进行中流式请求的处理。

回滚不是删除新版本。事故后仍需要保留新版本的日志、样本、配置和决策，便于
复盘根因；同时应避免继续把新版本产生的敏感数据复制到更多系统。

### 10.5 统计和提前查看

持续查看 canary 指标并在最好的时刻停止，会放大偶然波动。质量和安全比较
应预先定义样本量、分层方式、主要指标和停止规则；延迟则要结合稳定窗口、
负载和输入长度。小流量只是降低影响面，不会自动产生统计可信度。

## 11. 告警与事故响应

### 11.1 好告警对应一个动作

告警应描述用户或系统受到的影响，并附带原因线索和 runbook。比起“GPU 92%”
这样的孤立告警，更有用的是：

~~~text
长上下文请求的 P99 TTFT 连续 10 分钟超过 SLO
并且 KV 使用率上升、waiting queue 增长
-> 检查输入分布、队列和上下文预算
~~~

告警可以按严重程度分级：

1. P0：大面积不可用、持续数据泄露或高影响危险动作。
2. P1：核心业务明显退化，需要立即处置。
3. P2：部分租户或部分任务退化，需要当日处理。
4. P3：趋势异常或低影响问题，进入日常修复。

不是所有指标抖动都应该叫醒工程师。持续时间、业务权重、受影响请求数和恢复
动作都应写进告警规则。

### 11.2 质量告警

质量没有 HTTP 错误码，因此需要组合信号：

1. 任务完成率下降。
2. 点踩、重试和转人工上升。
3. claim 支持率或引用精度下降。
4. 结构化字段校验失败。
5. 新旧版本差异集中在某个切片。
6. 人工抽样发现同一类新 bad case。

自动质量告警应附带样本和版本信息，但样本访问必须遵守隐私权限。只有一个
LLM judge 分数下降时，先检查 judge 版本、提示和样本分布，不能马上判定模型
退化。

### 11.3 事故响应的顺序

事故处理先止血，再定位：

1. 确认影响范围和风险类型。
2. 停止危险动作、暂停放量或切换到已知版本。
3. 保留版本、trace、策略决定和资源指标。
4. 按输入、检索、模型、工具、审核和存储层定位。
5. 修复后用同一批样本和新的对抗样本回放。
6. 记录根因、检测延迟、影响时长、恢复动作和后续责任。

安全事故要优先阻断继续泄露；性能事故要优先恢复服务；质量事故要先确认
是否属于数据分布变化。三类事故都不能只通过重启服务结束，因为重启不会消除
错误 prompt、错误索引或错误权限策略。

### 11.4 三个典型排查路径

延迟突然升高时，先比较流量和输入 token 分布，再看队列、prefill、decode、
KV、GPU、上游检索和安全服务。输出质量下降时，比较模型、prompt、索引、用户
分布、解码参数和评估器版本，并回放具体 claim。成本突然升高时，检查请求量、
输入输出长度、缓存命中、重试、shadow 和异常租户。

## 12. 一个完整的线上质量闭环

以企业知识问答为例，系统可以把一次请求放进如下闭环：

~~~text
用户问题
  -> 鉴权和租户上下文
  -> 检索、重排和证据拼装
  -> LLM 生成
  -> claim 拆分、引用和敏感信息检查
  -> 返回回答
  -> 记录脱敏 trace
  -> 抽样进入质量/安全评估
  -> bad case 回流离线集
  -> 新版本 shadow、canary 和回滚
~~~

trace 记录检索候选、最终证据、模型和 prompt 版本、输入输出长度、引用、策略
决定、延迟阶段和成本。质量评估记录回答是否被证据支持，安全评估记录是否有
注入、泄露或危险动作，用户反馈作为额外信号而不是唯一标签。

如果引用支持率下降，先比较 parser、embedding、索引和 reranker；如果证据
正确但 claim 支持率下降，比较 prompt 和模型；如果安全漏放率上升，检查策略
分类器和外部内容信任边界；如果 P99 上升，检查输入长度、队列和 KV。这样的
归因顺序比“换一个更大的模型”更接近真实生产工作。

对于前一章的多模态服务，这套闭环还要追加媒体 artifact、processor 版本、OCR/
ASR 结果、帧时间范围和缓存身份。对一段视频问答，质量评估不仅判断回答文本，
还要判断引用时间段是否正确；对实时语音，还要记录 partial 稳定、首包、打断
和播放队列。

## 13. 最小可运行的监控诊断示例

下面的示例使用八条脱敏请求记录计算延迟分位数、TTFT、TPOT、token 成本、质量
和安全指标。它还比较一组基线，并输出彼此独立的发布信号和后续动作。代码故意
不把所有信号合并成一个布尔结论，因为安全、质量、错误、延迟和成本的处置优先级
不同。

~~~python
import math
from pprint import pprint


def quantile(values, q):
    if not values or not 0 <= q <= 1:
        raise ValueError("values must be non-empty and q must be in [0, 1]")
    ordered = sorted(values)
    position = (len(ordered) - 1) * q
    lower = math.floor(position)
    upper = math.ceil(position)
    if lower == upper:
        return float(ordered[lower])
    weight = position - lower
    return ordered[lower] + weight * (ordered[upper] - ordered[lower])


def mean(values):
    return sum(values) / len(values) if values else 0.0


def latency_ms(row):
    stages = [
        "route",
        "queue",
        "tokenize",
        "prefill",
        "first",
        "decode",
        "post",
        "safety",
    ]
    return sum(row[stage] for stage in stages)


def ttft_ms(row):
    return row["route"] + row["queue"] + row["tokenize"] + row["prefill"] + row["first"]


def tpot_ms(row):
    if row["completion_tokens"] == 0:
        return 0.0
    return row["decode"] / max(row["completion_tokens"] - 1, 1)


def request_cost(row, prices):
    return (
        row["prompt_tokens"] * prices["prompt"]
        + row["completion_tokens"] * prices["completion"]
        + row["visual_tokens"] * prices["visual"]
        + row["embedding_tokens"] * prices["embedding"]
    )


requests = [
    {
        "id": "r1_chat",
        "prompt_tokens": 320,
        "completion_tokens": 80,
        "visual_tokens": 0,
        "embedding_tokens": 0,
        "route": 20,
        "queue": 35,
        "tokenize": 15,
        "prefill": 120,
        "first": 25,
        "decode": 720,
        "post": 40,
        "safety": 20,
        "error": False,
        "blocked": False,
        "harmful": False,
        "quality": 0.91,
    },
    {
        "id": "r2_long_rag",
        "prompt_tokens": 2200,
        "completion_tokens": 180,
        "visual_tokens": 0,
~~~

## 14. 资料与证据边界

1. [OpenTelemetry Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)：解释 metrics、logs、traces 和可观测性的基本关系；具体采集、采样和隐私策略需要结合部署平台。
2. [Prometheus Histograms and Summaries](https://prometheus.io/docs/practices/histograms/)：说明延迟分布、histogram 和 quantile 的监控背景；小样本分位数仍需报告样本量。
3. [Google SRE Monitoring](https://sre.google/sre-book/monitoring/)：提供监控信号、告警和服务可靠性的一般工程背景；不定义某个大模型业务的 SLO。
4. [Google SRE Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)：说明 SLI、SLO 和错误预算的关系；模型质量和安全仍需额外的语义指标。
5. [vLLM Production Metrics](https://docs.vllm.ai/en/latest/usage/metrics.html)：核对当前推理服务暴露的请求、token 和运行时指标入口；框架指标不等于业务质量指标。
6. [OpenAI Evals Repository](https://github.com/openai/evals)：提供模型评估框架和样本组织的公开入口；自定义业务评估仍需定义数据、标签和隐私边界。
7. [HELM: Holistic Evaluation of Language Models](https://arxiv.org/abs/2211.09110)：说明多维、场景化评估的研究背景；通用 benchmark 不能直接替代线上回放。
8. [Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685)：讨论 LLM judge 的能力和偏差；judge 分数需要人工校准和切片分析。
9. [RAGAS](https://arxiv.org/abs/2309.15217)：RAG 评估的研究入口；自动评估器会受到检索、参考答案和模型偏差影响。
10. [TruthfulQA](https://arxiv.org/abs/2109.07958)：事实性和模仿错误信念的评估背景；单一事实集不能覆盖企业领域知识。
11. [HarmBench](https://arxiv.org/abs/2402.04249)：红队攻击和拒答评估的研究资料；攻击成功率必须按目标策略和业务风险重新定义。
12. [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)：提示注入、数据泄露、供应链和 Agent 风险的治理入口；安全控制仍要落到服务端权限和工具边界。
13. [OWASP LLM01: Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)：提示注入的威胁模型和影响背景；外部文档、OCR、字幕和工具结果都可能携带间接注入。
14. [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：风险识别、测量、管理和治理的通用框架。
15. [NIST Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)：针对生成式 AI 风险的补充资料；它不是某个模型的安全分数或发布阈值。
16. [NIST Privacy Framework](https://www.nist.gov/privacy-framework)：隐私风险识别和治理背景；具体日志保留和删除仍由业务、法规与系统能力共同决定。

论文、标准和官方文档的证明范围不同。论文适合说明评估方法和威胁模型，官方
文档适合确认当前 runtime 指标或框架接口，SRE 和 NIST 资料适合组织可靠性与
治理语言，目标业务的脱敏回放、人工标注和事故记录才适合决定实际发布判断。
尤其要警惕“某个 benchmark 提升”“分类器拦截率上升”被直接翻译成“线上质量
或安全已经提升”。

## 15. 本章小结

线上大模型系统的成熟度，不在于仪表盘上有多少曲线，而在于每条曲线都能连接
到一次请求、一个版本和一个可执行的处理动作。

1. 先用请求 trace 串起路由、排队、prefill、decode、后处理、安全和计费，再
   用 metrics 看趋势、日志看事件、profile 看资源细节。
2. 延迟要区分 TTFT、TPOT、ITL、E2E 和 P99；吞吐要区分输入、输出和多模态
   工作量，不能只报 QPS。
3. 成本要记录 token、GPU、辅助模型、存储、重试和 shadow，并用单位成功任务
   成本衡量真实业务效率。
4. 质量评估要有版本化样本、业务切片、线上抽样、自动指标、人工复核和不确定
   性；LLM judge 是工具，不是真值。
5. 幻觉排查应区分解析、检索、权限、上下文、模型和后处理，并在 claim 层检查
   证据支持、引用精度、新鲜度和访问权限。
6. 安全指标要同时观察 FNR、FPR、攻击成功率和人工审计；流式输出、工具调用
   和多模态外部内容需要不同的检查位置。
7. Prompt injection 防护依赖信任边界、服务端权限、参数校验、幂等和沙箱，
   不能只依赖一句系统提示词。
8. 日志要在可复盘和最小化之间取平衡，覆盖缓存、派生媒体、评估集、备份和
   删除生命周期。
9. 灰度发布要把模型、prompt、索引、runtime、策略和 schema 作为可追踪 bundle，
   让安全、质量、可靠性和成本分别形成发布证据。
10. 事故响应先止血再归因，修复后用固定回放和对抗样本验证，不能把重启服务当
    作根因修复。

当一次异常能够从指标回到 trace，从 trace 回到版本和输入切片，再回到一个明确
的暂停、修复、回滚或继续观察动作时，监控、评估与安全才真正成为生产系统的
一部分。
