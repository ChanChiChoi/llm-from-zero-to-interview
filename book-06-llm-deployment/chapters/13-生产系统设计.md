# 第十三章：生产系统设计

上一章讨论了如何把一次模型调用的资源消耗拆成 token、GPU 时间、缓存、检索、
重试和人工处理成本。本章继续往前走：当模型被真正放进一个每天处理大量请求的
系统时，除了“模型能不能生成”，还必须回答请求怎样进入、资源怎样分配、结果怎样
流出、失败怎样恢复，以及一次发布怎样被证明没有破坏原来的服务。

很多初学者画生产架构时会从一个大大的 `LLM` 方框开始，再在周围加上网关、缓存
和数据库。这种画法容易遗漏最重要的事实：用户看到的是一条完整的请求生命周期，
而模型只是其中一个计算阶段。一个模型即使在离线 benchmark 上很强，如果模板版本
错了、RAG 证据没有权限过滤、KV Cache 被长请求占满、工具重试产生重复扣款，系统
仍然不是一个可靠的生产系统。

## 1. 先理解生产系统到底在解决什么问题

### 1.1 从“调用模型”到“完成任务”

下面两段代码都可以调用模型，但它们代表的工程成熟度完全不同：

~~~python
def answer_request(model, prompt):
    answer = model.generate(prompt)
    return answer
~~~

~~~text
请求
  -> 身份与租户检查
  -> 请求预算和流量控制
  -> 模型、区域与副本选择
  -> 模板和上下文组装
  -> 检索、工具或多模态预处理
  -> 推理调度与生成
  -> 输出格式和安全处理
  -> 流式返回、状态保存、计量与追踪
~~~

第一段代码只描述了计算动作，第二段才描述了用户真正依赖的服务。生产系统设计
的对象不是一个模型函数，而是“在约束下稳定完成任务”的端到端链路。

对小白来说，可以把它理解成餐厅：模型像后厨的一台厨具，API Gateway 是接待和
取号，路由器决定订单送到哪个厨房，Prompt Processor 负责把顾客的自然语言订单
整理成厨房能执行的格式，调度器负责安排灶台，缓存像已经准备好的半成品，安全和
权限系统决定哪些订单可以执行，监控和账单则记录整个过程。后厨速度再快，取号、
配料、出餐和结账出了问题，顾客仍会认为餐厅不可靠。

专家会把这条链路进一步拆成六类契约：

| 契约 | 要回答的问题 | 典型证据 |
| --- | --- | --- |
| 请求契约 | 输入格式、流式协议、最大大小和错误如何表达 | schema、HTTP 状态、request id |
| 资源契约 | 一个请求最多消耗多少 token、显存、工具步数和时间 | token budget、KV 账本、队列指标 |
| 质量契约 | 什么叫任务完成，引用、结构化字段和工具动作怎样判定正确 | 离线集、人工标签、在线采样 |
| 安全契约 | 谁能访问什么数据和工具，哪些输出必须拦截 | ACL、策略版本、审计记录 |
| 状态契约 | 重试、取消、断线和未知提交状态如何恢复 | 幂等键、状态机、事件日志 |
| 发布契约 | 模型、模板、索引和策略如何一起发布与回退 | artifact manifest、灰度记录、回滚目标 |

这六类契约的意义在于，系统设计不再停留在“组件清单”。每增加一个组件，都要
说明它改变了哪一种契约、引入了什么新的失败方式，以及如何从 trace、指标或测试
样本中观察到这个变化。

### 1.2 在线、异步与流式不是同一种服务

一个系统经常同时包含三种 workload：

1. **同步请求**：用户等待一个 JSON 结果，例如短 FAQ 或分类。
2. **流式请求**：服务通过 SSE 或 WebSocket 逐步返回 token，用户关注首 token
   时间和中途断线。
3. **异步任务**：长视频分析、批量文档处理或多步 Agent 任务先返回 job id，
   后台完成后由轮询、回调或事件订阅取得结果。

如果把三者放入同一条队列，只用一个超时和一个副本池，短请求会被长任务拖慢，
流式连接会长期占用连接和 KV 状态，异步任务的峰值又可能在用户无感知时耗尽 GPU。
因此，架构图中需要明确同步和异步的边界：同步链路负责有限时间内的交互反馈，
异步链路负责可恢复的工作流、持久化状态和重试。

### 1.3 一张生命周期图比十个方框更有用

生产设计可以先从一条请求的生命周期开始：

~~~text
client
  -> gateway
  -> identity / tenant policy
  -> request budget / 请求处理决策
  -> router
  -> context assembly
       -> cache
       -> retrieval
       -> tool planning
       -> multimodal preprocessing
  -> scheduler / inference runtime
  -> output validation / safety policy
  -> response stream or job result
  -> trace / billing / evaluation sample
~~~

这里的“请求处理决策”不是一个神秘的总开关，而是根据请求大小、租户预算、
当前队列和服务状态决定“现在处理、排队、降级、转异步还是拒绝”。它应该输出可
解释的原因，例如 `token_budget_exceeded`、`tenant_concurrency_limit` 或
`dependency_unavailable`，而不是只返回一个布尔值。

## 2. 从需求开始，而不是从模型开始

### 2.1 先把 workload 分成几类

容量规划和系统设计都不应该从“系统每秒多少 QPS”开始。至少要区分请求类型、
输入输出长度、是否多步、是否流式、是否有外部依赖。一个企业助手可能有如下
工作负载：

| 类型 | 典型动作 | 输入/输出特征 | 主要瓶颈 | 结果形态 |
| --- | --- | --- | --- | --- |
| FAQ | 一次模型调用或响应缓存 | 短输入、短输出 | 排队和路由开销 | 同步 JSON |
| RAG 问答 | embedding、召回、重排、生成 | 输入受证据数量影响 | 检索、prefill、引用质量 | 流式或同步 |
| Agent | 多次模型调用和工具执行 | 步数和状态不断增长 | 外部依赖、长尾和副作用 | 异步或长流 |
| 多模态 | OCR、视觉/音频编码、生成 | 媒体大小不等 | encoder、文件处理和队列 | 常为异步 |
| 批处理 | 大量独立样本 | 可提前知道总量 | 吞吐和存储带宽 | 离线结果 |

这一分类不是为了让表格好看，而是为了避免错误的平均值。例如 1 秒完成的 100
个短请求和 100 秒完成的 1 个 Agent 任务，平均 QPS 可能相同，但它们对活跃连接、
KV Cache、队列和故障恢复的压力完全不同。

### 2.2 需求要写成可测量的服务目标

“低延迟”“高可用”“回答准确”都不是可以直接拿来规划容量的数字。应该把它们
拆成可测量的指标：

- 交互体验看 TTFT（time to first token）、TPOT（time per output token）、流式
  中断率和完整响应时间。
- 稳定性看成功率、超时率、取消率、依赖错误率和可用性。
- 任务质量看任务成功、引用支持、结构化字段准确率、工具动作正确率和人工升级率。
- 安全看不当输出率、越权工具调用率、敏感信息泄露率和攻击样本成功率。
- 经济性看每请求、每输入/输出 token、每 GPU 秒和每成功任务成本。

指标还要变成用户可理解的服务目标。SLI 是定义清楚的测量值，SLO 是该测量值在
指定窗口内应达到的目标。比如：“滚动 30 天内，至少 95% 的有效同步请求在
3.5 秒内收到完整响应。”它同时限定请求范围、完成事件、阈值和窗口。对应的延迟
SLI 与未达标预算可以写成：

~~~math
\mathrm{SLI}_{3.5s}
=\frac{\#\{r\in D_{\mathrm{eligible}}:L_r\le 3.5\,\mathrm{s}\}}
{|D_{\mathrm{eligible}}|},
\qquad
B_{\mathrm{bad}}=(1-\mathrm{SLO})|D_{\mathrm{eligible}}|
~~~

若一个窗口里有 10,000 个有效请求，目标是 95%，则最多有 500 个请求可以超过
3.5 秒；超时、服务端断连和用户主动取消是否计入，必须在统计前约定，并分别
保留原因，不能在事后把慢请求改标成“用户取消”。错误预算可用于决定是否继续
放量或暂停常规发布。任务质量和安全仍要单独设门槛：回答质量提升不能抵消越权
动作，错误预算也不是允许发生安全事故的配额。[Google SRE 对 SLI/SLO 与错误预算的说明](https://sre.google/sre-book/service-level-objectives/)
强调目标应贴近用户体验，并写明测量范围和窗口。

LLM 服务还要区分吞吐量和 goodput。吞吐量回答“单位时间处理了多少 token”，goodput
回答“有多少请求在满足服务目标和任务条件下完成”。[Revisiting SLO and Goodput
Metrics in LLM Serving](https://arxiv.org/abs/2410.14257) 比较请求级/令牌级 SLO 与
goodput，并讨论 smooth-goodput 作为调度目标的研究方案。它不是行业统一标准；真正
上线仍要明确分子、分母和 SLA/SLO 条件，避免优化器通过放弃长请求、失败请求来提高
表面吞吐。

| 指标 | 典型计数 | 适合回答 | 单独使用的盲点 |
| --- | --- | --- | --- |
| 原始输出吞吐 | 窗口内生成 token / 墙钟秒 | runtime 的 token 处理能力 | 不说明请求是否完整、及时或有用 |
| 请求级 goodput | 满足延迟与任务门槛的请求 / 秒 | 用户任务是否按目标完成 | 必须定义请求集合、成功条件、超时和取消口径 |
| 令牌级 goodput | 满足目标的服务 token / 秒 | token 流式目标和系统效率 | 可能偏向长输出；要说明 request 与 token 的计量单位 |
| smooth-goodput | 按离目标的程度给连续效用的研究指标 | 观察硬阈值附近的调度权衡 | 不是既定业务 SLO；需验证它不会牺牲困难请求或安全边界 |

对于延迟，平均值通常不够。设一批请求的完成时间为 `L_1,...,L_n`，P95 是让
95% 样本不超过它的分位点，P99 则专门观察最慢的 1%。当请求长度差异很大时，
还应该按请求类型、租户、缓存命中状态和模型池分层，否则大量短请求会掩盖少量
长请求的真实体验。

### 2.3 延迟由多个阶段共同组成

对一个流式请求，可以把端到端延迟近似拆成：

~~~math
L_{\mathrm{e2e}}
\approx
L_{\mathrm{queue}}
+L_{\mathrm{route}}
+L_{\mathrm{context}}
+L_{\mathrm{prefill}}
+L_{\mathrm{first\_decode}}
+L_{\mathrm{stream}}
+L_{\mathrm{post}}
~~~

其中 `L_queue` 是排队时间，`L_route` 是鉴权、路由和网络耗时，`L_context` 包含
embedding、召回、重排和媒体预处理，`L_prefill` 是把输入送入模型的计算时间，
`L_first_decode` 是产生首个输出 token 的时间，`L_stream` 是后续 token 的生成和
传输，`L_post` 是结构化校验、审核和落盘。

如果 `TTFT` 表示从请求进入测量边界到首 token 的时间，`TPOT` 表示首 token 之后
相邻输出 token 的平均间隔，生成 `O≥1` 个 token 的近似耗时是：

~~~math
L_{\mathrm{generation}}\approx\mathrm{TTFT}+(O-1)\mathrm{TPOT}
~~~

这是对 `first_decode + stream` 的另一种表达，不能再与这两项重复相加。服务端
TTFT、客户端首 token 时长和完整端到端 TTFT 的起止点可能不同；只有确认边界一致，
才能拿它们做容量或 SLO 比较。OpenTelemetry 当前 GenAI 指标草案将 TPOT 定义为
首 token 之后的 token 间隔，具体 exporter 和 API 仍需逐版本核对。

对小白而言，这个式子说明“模型本身变快”不一定等于用户更快看到答案：如果请求
在队列里等了 2 秒，模型计算只花 0.3 秒，继续优化 kernel 的收益就很有限。专家
则会把每一项关联到 trace span，并区分 CPU、GPU、网络、外部依赖和排队的责任边界。

### 2.4 质量和安全也要有目标

一个客服系统不能把“模型返回了 HTTP 200”当成任务成功。设请求集合为 `D`，每个
请求的任务结果为 `s_i∈{0,1}`，可以定义：

~~~math
\mathrm{TaskSuccess}
=
\frac{1}{|D|}\sum_{i\in D}s_i
~~~

RAG 还需要检查回答中的原子 claim 是否被检索证据支持。工具型 Agent 则要把“动作
是否被授权”“参数是否正确”“外部状态是否最终一致”分开记录。安全指标不能被
质量平均分抵消：一个系统即使回答更流畅，只要越权转账率增加，也不能说整体变好。

## 3. 容量规划：QPS 只是入口数字

### 3.1 用 token 吞吐描述模型压力

设第 `j` 类请求的峰值到达率为 `λ_j`，一次模型调用的平均输入 token 为 `P_j`，
输出 token 为 `O_j`，一次任务平均包含 `s_j` 次模型调用。如果前缀、embedding 或
其他中间结果能够复用，使输入 token 的平均节省比例为 `h_j`，则第一版规划可以写成：

~~~math
R_{\mathrm{in}}
=
\sum_j\lambda_j s_j P_j(1-h_j),
\qquad
R_{\mathrm{out}}
=
\sum_j\lambda_j s_j O_j
~~~

`R_in` 和 `R_out` 的单位是 token/s。`h_j` 不是“缓存请求命中率”的同义词；一次
请求可能只复用前缀的一部分，也可能命中响应缓存而完全跳过模型。把它直接写成
请求命中率会夸大收益，因此应从 trace 中记录真正减少的 prefill token。

如果一个 RAG 请求还包含 embedding 和 reranker，可以再记录：

~~~math
R_{\mathrm{embed}}=\sum_j\lambda_j E_j,
\qquad
R_{\mathrm{rerank}}=\sum_j\lambda_j K_j
~~~

其中 `E_j` 是每个请求需要编码的 token 或文本单元，`K_j` 是送入 reranker 的
候选规模。这样才能知道瓶颈究竟在生成模型、检索服务还是重排模型。

#### 一个具体估算

假设系统每秒收到 20 个短聊天请求，每个请求平均输入 600 token、输出 100 token；
另有每秒 4 个 RAG 请求，输入 2,000 token、输出 200 token，每个请求平均包含
一次模型调用，且前缀缓存只节省 RAG 输入的 25%。则：

~~~math
R_{\mathrm{in}}
=20\times600+4\times2000\times(1-0.25)
=18{,}000\ \mathrm{token/s}
~~~

~~~math
R_{\mathrm{out}}
=20\times100+4\times200
=2{,}800\ \mathrm{token/s}
~~~

如果只看 24 QPS，可能会误以为系统很轻；实际上 18k token/s 的 prefill 和 2.8k
token/s 的 decode 需要不同的硬件和调度关注点。

### 3.2 用 Little's Law 估算活跃请求

排队系统里常用 Little's Law：

~~~math
A=\lambda L
~~~

`A` 是平均系统内请求数，`λ` 是平均到达率，`L` 是平均停留时间。它不是模型
性能公式，而是容量规划的第一版近似。例如 Agent 到达率只有 2 QPS，但平均任务
要在系统中停留 20 秒，那么平均就有 `2×20=40` 个任务处于执行或等待状态。

对流式请求，`A` 还对应连接、调度槽和 KV 状态；对异步任务，`A` 还包括消息队列、
对象存储中的中间文件和状态数据库中的未完成 job。规划时不能只根据在线 QPS
决定副本数。

这个公式的边界也很重要：它描述长期平均关系，无法单独预测突发流量、P99 排队
时间或请求长度分布造成的显存峰值。峰值容量仍需要离线回放或压测验证。

### 3.3 把吞吐和并发合并成副本估算

对模型池 `m`，设单副本的 prefill 吞吐为 `U_in,m`，decode 吞吐为 `U_out,m`，
单副本可承载的活跃序列数为 `S_m`，目标峰值需求为 `R_in,m`、`R_out,m` 和 `A_m`。
用余量系数 `γ>1` 做第一版估算：

~~~math
n_m
=
\left\lceil
\gamma\max\left(
\frac{R_{\mathrm{in},m}}{U_{\mathrm{in},m}},
\frac{R_{\mathrm{out},m}}{U_{\mathrm{out},m}},
\frac{A_m}{S_m}
\right)
\right\rceil
~~~

`n_m` 是模型池的副本数。`γ` 不是固定行业常数，它要覆盖流量波动、长短请求混合、
节点故障、发布期间的容量损失和测量误差。一个只用平均 token 长度得到的 `γ`，
不能替代按 P95/P99 长度分布进行压测。

这里的 `A_m` 指同时驻留在模型调度器中的活跃序列，不是正在等待检索、工具或用户
输入的整个任务数。若第 `j` 类任务到达率为 `λ_j`，平均每个任务有 `s_j` 次模型
调用，单次调用在推理 runtime 中占用序列槽的平均时间为 `τ_{model,j}`，则可用
Little 定律估算：

~~~math
A_m\approx\sum_j\lambda_j s_j\tau_{\mathrm{model},j},
\qquad
J_m\approx\sum_j\lambda_j L_{\mathrm{task},j}
~~~

`J_m` 是端到端任务并发。Agent 等待工具或后台任务时会增加 `J_m`，但在等待期间
不一定占用模型序列槽，因此不能拿 `J_m` 直接除以推理引擎的最大 active sequence。
重试、fallback 和并行工具路径要按实际增加的模型调用计入 `s_j`。此外，prefill
吞吐、decode 吞吐与活跃序列数会互相影响；`U_in,m`、`U_out,m` 和 `S_m` 应在同一
模型版本、硬件、长度分布和混合负载下测出，分别取三个独立压测中的峰值再拼在一起，
可能得到任何一组真实流量都达不到的“容量”。

容量表最好同时列出输入、输出和 active sequence 三种比值。例如：

~~~text
pool      input_need / input_cap    output_need / output_cap    active / active_cap
small     0.08                      0.45                        0.29
large     0.12                      0.68                        0.31
~~~

这样可以看出某个池是受 decode、prefill 还是并发槽限制，而不是只得到一个“需要
几台机器”的数字。

### 3.4 显存账本要把权重和 KV 分开

权重显存的粗略部分为：

~~~math
M_{\mathrm{weight}}
\approx
N_{\mathrm{param}}\frac{b_w}{8}
~~~

其中 `N_param` 是参数数量，`b_w` 是每个参数的 bit 数。实际还要加上 scale、
zero point、alignment、runtime buffer 和 allocator 碎片，所以这个式子只适合
做下界估计。

对采用 MHA、MQA 或 GQA 的 Transformer，KV Cache 可以粗略写成：

~~~math
M_{\mathrm{kv}}
\approx
2N_{\mathrm{layer}}T_{\mathrm{active}}H_{\mathrm{kv}}D_{\mathrm{head}}b
~~~

`2` 表示 K 和 V 两份状态，`N_layer` 是层数，`T_active` 是所有活跃序列的 token
总数，`H_kv` 是 KV head 数，`D_head` 是每个 head 的维度，`b` 是每个元素占用的
字节数。MHA 的 `H_kv` 等于 query head 数；MQA 接近一个；GQA 介于两者之间，
这也是它们在 decode 内存带宽和 KV 显存上有不同表现的原因。

如果有 32 层、8 个 KV head、每个 head 128 维、FP16 每元素 2 字节、活跃 token
总数为 64k，则：

~~~math
M_{\mathrm{kv}}
\approx
2\times32\times64{,}000\times8\times128\times2
\approx8.39\ \mathrm{GB}
~~~

这还没有包括权重、激活、CUDA workspace、通信 buffer 和显存余量。长上下文服务
常见的事故不是模型权重加载失败，而是高并发下 KV Cache 逐渐膨胀，最终触发抢占、
重算、排队或 OOM。

总显存可以按下面的账本先做规划：

~~~math
M_{\mathrm{total}}
\approx
M_{\mathrm{weight}}
+M_{\mathrm{kv}}
+M_{\mathrm{runtime}}
+M_{\mathrm{comm}}
+M_{\mathrm{margin}}
~~~

量化可能显著降低权重项，但并不会自动把 KV、激活、通信和碎片都按同样比例降低。
因此，“模型是 INT4，所以一张卡一定能承载某个并发”是不能直接成立的结论。

### 3.5 故障余量和 N+1

如果计划部署 `n_m` 个副本，单副本 decode 吞吐为 `U_out,m`，峰值输出需求为
`R_out,m`，希望任意一个副本故障后仍能承载流量，就需要满足：

~~~math
(n_m-1)U_{\mathrm{out},m}\ge R_{\mathrm{out},m}
~~~

这只是计算容量条件。真实故障还要考虑故障检测时间、流式请求迁移、KV 状态是否
能重建、旧连接如何结束、模型加载时间和剩余节点的网络拓扑。如果一个生成中的
请求不能迁移 KV，所谓“故障转移”可能只是让新副本从头重算，用户看到的是一次
中断后重试，而不是无缝恢复。

### 3.6 成本也属于容量设计

模型池每小时成本可以粗略表示为：

~~~math
C_{\mathrm{hour}}
=
\sum_m n_m g_m c_{\mathrm{gpu}}
+C_{\mathrm{storage}}
+C_{\mathrm{network}}
+C_{\mathrm{aux}}
~~~

`g_m` 是每个副本占用的 GPU 数，`c_gpu` 是单 GPU 小时成本，`C_aux` 包括 embedding、
reranker、安全审核、日志、对象存储和人工处理等附加成本。容量不足会损害 SLO，
容量过剩会浪费成本；生产设计要把两者放在同一张资源表里，而不是上线后才发现
预算不够。

## 4. 生产请求的完整链路

### 4.1 API Gateway：把外部世界变成可控请求

Gateway 是请求进入内部系统的第一层。它通常承担 TLS 终止、身份信息传递、请求
大小限制、基础限流、超时、request id 注入和协议转换。它不应该承担复杂模型逻辑，
否则网关发布会和模型发布互相牵连。

对普通 JSON 请求，网关可以在读取 body 后进行大小和 schema 检查；对 SSE 或
WebSocket，网关必须支持长连接、心跳、flush 和客户端取消。一个只针对短 HTTP
请求调优的反向代理，可能在模型首 token 之前就关闭连接，或者缓冲了所有 token
后才一次性返回，破坏流式体验。

请求至少应携带以下可追踪字段：

~~~text
request_id       一次外部请求的稳定标识
trace_id         跨服务追踪标识
tenant_id        计费、配额和权限边界
idempotency_key  可能产生副作用的操作键
contract_version 请求与响应 schema 版本
~~~

`request_id` 解决“哪一次请求出错”，`trace_id` 解决“请求在哪一段变慢”，
`idempotency_key` 解决“重试是否会重复执行”。它们不能互相替代。

### 4.2 身份、租户和数据边界

鉴权不只是检查 API key 是否存在，还要把主体映射到权限、租户、区域和数据范围。
同一个用户可能拥有聊天权限，却没有访问某个知识库或调用退款工具的权限。网关
做粗粒度认证，细粒度授权应在真正接触数据和工具的服务边界再次检查。

缓存、日志、检索和工具服务都必须携带租户上下文。只在入口检查一次，然后在内部
服务间使用一个不带权限信息的字符串，是常见的跨租户泄露来源。

### 4.3 限流、配额与反压

LLM 服务不能只按请求数限流，因为一次请求可能消耗 100 token，也可能消耗 1M
token、几十秒 GPU 时间和多个工具调用。一个简单的 token bucket 模型先补充预算，
再决定是否准入：

~~~math
B_{\mathrm{refill}}
=\min\left(B_{\max},B(t)+r\Delta t\right),
\qquad
\mathrm{admit}\iff c(t)\le B_{\mathrm{refill}},
\qquad
B(t+\Delta t)=B_{\mathrm{refill}}-c(t)\quad\text{if admitted}
~~~

其中 `B(t)` 是当前桶中的预算，`B_max` 是桶容量，`r` 是恢复速率，`c(t)` 是本次
请求预估消耗的 token 或成本单位；预算不足时不扣成负数，而是拒绝或排队。LLM
请求的输出长度事前未知，准入时可按最大输出或保守估计先预留，完成后再按实际
usage 结算、释放多余预留。真实系统通常需要多层限制：用户级并发、租户级
token、模型池级 active sequence、工具级调用次数和每日金额预算。

限流和反压的结果不应只有“允许/拒绝”两个选项，还可以是：

1. 进入短队列等待。
2. 选择较小模型或减少非关键上下文。
3. 把长任务转为异步 job。
4. 降低非关键租户的优先级。
5. 返回带 retry-after 的可解释错误。

反压的关键是尽早发生。请求已经排队、分配了 KV、调用了外部工具之后才拒绝，
并不能真正保护系统，反而会增加无效成本。

### 4.4 Request Router：选择模型、区域和副本

路由器至少有三种不同决策，不能混成一个“负载均衡”字段：

1. **能力路由**：根据任务类型、风险和质量要求选择模型池。
2. **位置路由**：根据数据区域、租户合规和模型可用区域选择集群。
3. **负载路由**：在满足前两者的副本中，根据队列、KV 使用量、预计 token 和健康
   状态选择目标。

简单的 round-robin 只解决请求计数均匀，无法处理一条长上下文和一条短 FAQ 的
资源差异。token-aware routing 可以把预计输入输出 token 纳入选择；prefix-aware
routing 则在权限允许时优先把共享前缀送往持有相应 cache 的副本。但 prefix
亲和性不能凌驾于故障转移和租户隔离之上。

路由还要定义 fallback。一个合理的 fallback 需要说明：

- 大模型不可用时能否使用小模型；
- RAG 不可用时能否回答，还是必须明确拒答；
- 工具超时时能否只返回查询结果，还是必须停止整个事务；
- 安全服务不可用时是 fail closed、进入人工审核，还是只允许低风险能力。

“失败就切到另一个模型”并不是通用可靠性策略。不同模型的模板、工具协议、拒答
行为和质量边界可能不同，fallback 本身也要进入评估集和审计记录。

### 4.5 Prompt Processor：输入协议的实现

Prompt Processor 不是简单的字符串拼接器。它要把外部请求转成特定模型能够正确
解释的输入协议，并记录使用了哪个模板、策略和上下文版本。

一个长上下文请求可以抽象为：

~~~math
P_{\mathrm{total}}
=
P_{\mathrm{system}}
+P_{\mathrm{history}}
+P_{\mathrm{retrieval}}
+P_{\mathrm{tools}}
+P_{\mathrm{user}}
+P_{\mathrm{media}}
~~~

还需要为输出、隐藏推理、工具结果或 runtime 保留预算：

~~~math
P_{\mathrm{total}}+O_{\mathrm{visible}}+O_{\mathrm{hidden}}+P_{\mathrm{tool\_result}}
\le W_{\mathrm{model}}
~~~

`W_model` 是具体模型和接口的有效窗口，不一定等于宣传中的最大 context。媒体
位置、工具 schema 和隐藏推理是否计入窗口，要以具体 runtime 或 API 契约为准。

上下文组装的正确顺序通常包括：

1. 先确认用户和租户的权限范围。
2. 按版本读取 system prompt 和输出 schema。
3. 从历史中保留与当前任务有关的状态。
4. 对检索结果记录来源、时间、权限和证据 id。
5. 把工具说明和工具返回值标记为不同的信任边界。
6. 在预算不足时按策略删减，而不是静默截断最前面的 system 约束。
7. 对最终输入做 token 计数和结构化审计。

上下文压缩的目标不是让文本尽可能短，而是在减少 token 的同时保留条件、例外、
时间、来源、权限和操作约束。删除一句重复介绍通常安全，删除“仅适用于某地区”
或“执行前必须确认”则可能改变系统行为。

### 4.6 Cache Layer：四种缓存，四种正确性

缓存至少可以分成四类：

| 缓存 | 复用对象 | 主要收益 | 主要风险 |
| --- | --- | --- | --- |
| response cache | 最终答案 | 跳过完整推理 | 过期、权限和个性化错误 |
| prefix/KV cache | 已处理的前缀状态 | 降低 prefill 和首 token 延迟 | 租户隔离、版本和显存占用 |
| embedding/rerank cache | 中间向量或重排结果 | 减少检索计算 | 文档版本和权限变化 |
| media cache | OCR、视觉编码或音频特征 | 避免重复媒体处理 | 文件替换、访问控制和存储成本 |

response cache 命中后不需要生成；prefix cache 命中后仍然要继续生成，两者在
正确性和成本模型上完全不同。缓存 key 至少应包含影响结果的版本和权限因素，
可以抽象成：

~~~text
cache_key = hash(
  normalized_input,
  model_version,
  prompt_version,
  retrieval_version,
  policy_version,
  tenant_scope
)
~~~

真正的 key 字段依赖业务。把用户权限放在 key 之外，然后只依靠“命中后再检查”
补救，容易在并发或错误路径中泄露数据；把所有内容都放进 key，又可能使命中率
降到没有工程价值。设计时要在隔离和可复用性之间明确取舍。

前缀缓存还带来一个额外问题：热点前缀会占用显存。缓存命中率上升不代表总成本
一定下降，如果命中只节省少量 prefill，却迫使系统频繁淘汰真正有价值的 KV 状态，
整体 P95 甚至可能变差。

### 4.7 推理引擎和调度器的边界

推理引擎负责模型 artifact 的加载、算子执行、batch 组织、KV Cache、采样、流式
输出和多 GPU 通信。vLLM、SGLang、TensorRT-LLM 或自研 runtime 在模型支持、
kernel、量化、调度和协议适配上的重点不同；官方文档能说明某个版本提供了什么
能力，但不能替代目标模型、硬件和 workload 的压测。

平台层则负责引擎之外的事情：租户、路由、策略、版本、队列、审计、评估、账单和
故障恢复。把平台职责全部塞给引擎，会让模型升级、权限变更和服务降级互相影响；
把调度完全留在平台层，又可能失去引擎对 KV 和 batch 的内部可见性。因此常见做法
是两层协作：平台给出请求级预算和优先级，引擎在可用预算内做 token 级调度。

### 4.8 RAG、Agent 和多模态是三条分支

RAG 分支需要记录 query rewrite、embedding、召回、rerank、context assembly 和
引用校验的 span。检索服务返回的内容必须带文档版本、权限范围和证据 id，不能把
任意外部文本直接当作 system instruction。

Agent 分支需要显式状态机：`planned`、`tool_running`、`waiting`、`committed`、
`failed` 等状态应能从事件日志重建。工具调用前检查权限和参数，工具执行后记录
外部请求 id 和结果版本；生成文本不应直接决定高风险副作用。

多模态分支需要先把图片像素、音频秒数、视频帧数和文件大小转成资源预算，再决定
同步处理还是创建异步 job。媒体预处理、OCR、视觉编码和生成模型最好有独立队列，
否则一部视频会把文本服务的 GPU 和连接池占满。

## 5. 组件之间如何形成可靠的边界

### 5.1 API 和响应契约

生产 API 的兼容性不只体现在 URL。还包括角色字段、工具 schema、流式事件类型、
错误码、finish reason、usage 计量和取消语义。客户端可能依赖某个字段始终存在，
也可能在收到 `tool_call` 事件后暂停展示文本；服务端随意改变事件顺序，会导致
客户端状态机失步。

一个流式响应应至少能区分：开始事件、增量文本、工具调用增量、用量信息、完成事件
和错误事件。断线后是否支持 resume、是否允许重新生成、已产生的 token 如何计费，
都应写进协议，而不是让不同 SDK 各自猜测。

### 5.2 组件之间传递“原因”，而不只是传递结果

当一个请求被降级或停止时，下游需要知道原因。推荐在内部事件中保留类似字段：

~~~text
decision      process / queue / degrade / async / reject
reason        queue_budget / dependency_timeout / policy_block / quota
model_version 实际使用的模型
policy_version 实际使用的策略
resource      token、GPU、KV 或工具预算摘要
~~~

对用户可以只返回稳定的错误码，对内部 trace 则保留更细的诊断原因。这样才能区分
“模型回答失败”和“请求根本没有进入模型”，也能避免把所有异常都归因给模型能力。

### 5.3 超时、取消与重试

超时必须按阶段设置。网关总超时、检索超时、模型首 token 超时、单个工具超时和
整个 Agent job 超时不是同一个数字。一个请求在模型已经生成一半后被客户端取消，
服务端需要停止生成并释放 KV；否则用户看不到结果，GPU 仍然被占用。

重试只适合暂时性错误，例如连接重置、可恢复的过载或明确的 503。模型返回内容
不满意通常不是网络重试问题；权限拒绝和参数校验失败也不能重试。全抖动指数退避
的一种写法是：

~~~math
t_k\sim U\!\left(0,\min(t_{\max},t_0 2^k)\right)
~~~

`k` 是重试轮次，`t_0` 是初始上限，`t_max` 是退避上限。随机等待能减少大量客户端
同时重试造成的同步尖峰，但不能代替截止时间、重试预算和幂等性；嵌套的 SDK 与应用
重试还会相乘，例如两层各允许 3 次总尝试，最坏会把一次调用放大为 9 次。每个阶段
应继承端到端 deadline，只在剩余时间足以完成等待和下一次尝试时继续。AWS Builders'
Library 分别讨论了超时边界、抖动退避与过载下的重试放大。[超时、重试与抖动退避](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

错误类型和请求状态决定动作：

| 状态 | 处理方式 | 原因 |
| --- | --- | --- |
| 权限拒绝、schema 错误 | 返回稳定错误，不重试 | 输入或授权条件未改变，重放不会变好 |
| 幂等读取遇到可恢复的 429/503 | 在 deadline 与重试预算内退避，遵守服务端给出的等待提示 | 可能是暂时性故障，但重试也会增加负载 |
| 写工具请求已发出，等待回执时超时 | 标记 `committed_unknown`，用同一个操作键查询状态 | 客户端不知道副作用是否已提交 |
| SSE 已发出部分 token 后上游失败 | 结束为不完整响应并记录已发送 usage；不可静默从头重放 | 重放可能重复内容、费用或外部动作 |

客户端取消也必须传播到下游；只有取消信号到达推理 runtime 并释放序列/KV，才算
真正停止了计算。超时本身只说明调用方停止等待，不证明下游操作停止或回滚。

### 5.4 “已提交但客户端超时”的状态

支付、退款、发邮件、修改数据库这类工具可能出现 commit-unknown：服务已经提交
了外部操作，但响应在返回途中丢失。此时直接重试可能产生两次副作用，直接当失败
又会让用户重复操作。

更可靠的流程是：

1. 生成稳定的操作 id 和幂等键。
2. 在本地事件日志中记录 `intent`。
3. 调用外部服务并传递幂等键。
4. 记录 `accepted`、`rejected` 或 `unknown`。
5. 对 `unknown` 查询外部状态，而不是立即再次提交。
6. 只有状态机确认可重试时才发起下一次动作。

这条原则也适用于 Agent。模型可以重新规划，但不能因为上下文中少了一条工具
结果就把不可逆动作当成普通文本续写。

这些方案提供的保证不同：

| 方案 | 解决的问题 | 仍需处理的边界 |
| --- | --- | --- |
| 幂等键 | 同一调用重放时，业务服务识别相同意图并复用原结果 | 记录必须与副作用原子协调；同一 key 的参数变化应拒绝；保留期要覆盖最长恢复窗口 |
| Transactional Outbox | 在同一数据库事务中保存业务状态和待发 command，再由 worker 持久重试，避免“写入成功但消息丢失” | 投递是至少一次，消费者仍要去重；它不让数据库与外部退款系统变成一个分布式原子事务 |
| Saga/补偿事务 | 多个服务各自提交本地事务，失败后按业务规则执行补偿 | 补偿可能失败，也不总能恢复原状；高影响操作需要人工处置路径 |

一个典型恢复路径是：本地事务同时写 `job=intent` 和 outbox command；dispatcher
至少一次投递；业务工具以 `(tenant, operation_id)` 查重并保存结果；响应丢失时，
恢复 worker 重发同一 command 或查询同一 operation id。幂等键应绑定租户、操作类型
和规范化参数摘要；相同 key、不同参数要报冲突，而不是把新退款误当成旧退款。只有
下游本身支持幂等，或去重记录能与副作用原子更新时，才可以讨论“effectively once”；
不能笼统承诺端到端 exactly-once。[AWS 对幂等 API 的设计](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 说明了 key、重复请求和参数变化的处理；[Microsoft Transactional Outbox](https://learn.microsoft.com/en-us/power-platform/architecture/reference-architectures/transactional-outbox-pattern) 明确 outbox 的投递仍是 at-least-once，因此消费者要能容忍重复。

## 6. 可观测性：把一次回答变成可解释的 trace

### 6.1 日志、指标和 trace 的分工

日志回答“发生了哪个事件”，指标回答“这种事件是否呈现趋势”，trace 回答“同一
次请求在哪个阶段花了时间”。三者应使用同一个 `trace_id` 和 `request_id`，但不
意味着每条日志都要保存完整 prompt 或输出。

对敏感业务，推荐保存 hash、长度、版本和分类标签，只有经过授权的调试流程才读取
原文。日志脱敏不应改变安全审计需要的事实，例如不能把“调用了退款工具”脱敏成
无法区分的“调用工具”。`request_id`、`user_id`、邮件和完整 prompt 不应直接作为
Prometheus 指标标签：每种标签组合都会新增 time series，高基数会增大存储和查询
成本。指标保留有限枚举维度，例如 workload、model pool、status class；单次请求的
ID 和受限上下文留在有访问控制、保留期和脱敏策略的 trace/log。Prometheus 官方
[instrumentation guide](https://prometheus.io/docs/practices/instrumentation/) 给出
标签基数的资源代价和控制建议。

### 6.2 一次请求应该有哪些 span

典型 trace 可以包含：

~~~text
request
  gateway
  auth_policy
  quota_decision
  route
  context_build
    retrieval
    rerank
    media_preprocess
  cache_lookup
  model_prefill
  model_decode
  tool_call[0...n]
  output_validation
  safety_check
  response_stream
  billing_and_audit
~~~

每个 span 至少记录开始和结束时间、状态、版本、输入输出 token、缓存状态、错误
类别和上游 request id。Agent 的 trace 还要记录状态转移和工具授权结果；RAG 的
trace 要记录候选数、最终证据 id 和引用映射；多模态 trace 要记录媒体尺寸、采样
策略和预处理耗时。

OpenTelemetry 的 GenAI 指标约定目前标为 Development；其中的模型服务指标区分
请求时长、TTFT，以及首 token 之后的 TPOT。它们适合作为跨系统对齐名词的入口，
但不是稳定接口，也不保证具体 runtime 已导出这些值。要分清模型服务端 TTFT 与
客户端完整端到端时长：前者通常覆盖排队和 prefill，后者还包括鉴权、RAG、工具、
网络与后处理。部署时应固定语义约定版本，并核对 exporter 的实际计量边界。[GenAI
metrics conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)
记录了当前字段和状态。

### 6.3 指标的分母决定结论

`tool_success_rate` 如果把没有调用工具的请求也放进分母，会得到没有意义的数；
`cache_hit_rate` 如果按请求计算，则不能代表节省了多少 token；`availability` 如果
把用户主动取消算成服务错误，会错误地触发告警。

每个指标都要把分子、分母和过滤条件写清楚。例如缓存真正节省的 token 比例可以写成：

~~~math
H_{\mathrm{token}}
=
\frac{\sum_i T_{\mathrm{saved},i}}
{\sum_i T_{\mathrm{eligible},i}}
~~~

工具安全指标可以按高风险调用集合 `D_tool` 定义：

~~~math
R_{\mathrm{unauthorized}}
=
\frac{\#\{i\in D_{\mathrm{tool}}:\text{动作未授权}\}}
{|D_{\mathrm{tool}}|}
~~~

为避免公式中的代码变量和 Markdown 冲突，正文里的字段名用反引号表示；这里的
集合只表示“高风险工具调用样本”，不是模型所有输出。

### 6.4 从指标到诊断动作

指标本身不会修复系统。P99 升高时，先看请求长度和流量是否变化，再拆队列、prefill、
decode、外部依赖、输出审核和流式传输。如果只有长 RAG 请求变慢，扩大所有模型副本
可能既昂贵又无效；如果 queue time 占比上升，问题更可能是容量、优先级或反压。

告警应绑定观察窗口、分层条件和动作。例如“某模型池 5 分钟 P99 超过目标”只是
触发信号，后续动作可能是停止扩大灰度、降低非关键租户优先级、转异步、启用已验证
fallback 或回滚最近的路由策略。动作本身也必须可审计和可撤销。

## 7. 评估和发布：版本不是只有权重

### 7.1 一个可回滚的发布单元

真正影响回答的对象至少包括：

1. 模型权重和架构配置。
2. tokenizer 和 chat template。
3. system prompt、工具 schema 和输出解析器。
4. RAG 文档快照、embedding 模型、索引和 reranker。
5. 解码参数、路由策略和 fallback。
6. 输入输出安全策略、分类器和人工审核规则。
7. 推理引擎、量化 kernel 和运行时镜像。

只给权重打一个版本号是不够的。模型换了 tokenizer，输入 token 数和上下文边界
可能改变；prompt 换了工具 schema，Agent 的动作空间也会改变；索引变了，回答
引用的证据集合就不再相同。发布记录应保存一个 manifest，把这些 artifact 的版本
绑定在一起。

### 7.2 离线、shadow 和 canary 各自回答不同问题

离线回放可以控制输入、版本和随机种子，适合发现质量、安全和格式回归；shadow
把真实流量复制给候选版本但不影响用户，适合观察真实长度和路由分布；canary 让
小规模用户真正使用候选版本，才能测到连接断开、缓存污染、工具副作用和真实成本。

三者不能互相替代。一个离线集通过的 prompt，可能在真实用户的超长输入上触发
截断；shadow 中没有真实副作用，不能证明工具动作安全；canary 样本太少，也不能
证明长尾质量没有退化。

canary 必须能区分候选组和 control 组。设候选组流量占比为 `p`，两组错误率分别为
`e_c` 和 `e_0`，总体错误率和相对 control 的变化是：

~~~math
e_{all}=p e_c+(1-p)e_0,
\qquad
\Delta e=p(e_c-e_0)
~~~

当候选占 5%、候选错误率为 20%、control 错误率为 0 时，总体错误率是 1%；只盯
全局曲线可能看不见回归。比较时应按同一
时间窗口和 workload 切片分别看两组，保持请求长度、租户、缓存状态和任务类型可比，
并让观察时段覆盖目标负载。SRE Workbook 把 canary 定义为有期限的部分流量部署，
强调按版本分组评估、代表性样本和与 control 的归因；LLM 还要把任务质量及高风险
动作单独设 gate，不能只看 HTTP 成功率。[Google SRE Canarying Releases](https://sre.google/workbook/canarying-releases/)

### 7.3 质量比较要看任务切片

候选版本与基线至少要在以下切片比较：

| 切片 | 重点问题 |
| --- | --- |
| 短 FAQ | 是否保持准确，是否值得路由到小模型 |
| 长 RAG | 证据是否支持 claim，是否因上下文增长而退化 |
| 代码/数学 | 可执行结果和边界样本是否改变 |
| Agent | 工具参数、授权、重试和最终状态是否正确 |
| 多模态 | OCR 字段、视觉定位、音频转写或视频时间段是否退化 |
| 安全 | 误拦截、漏放、注入和隐私样本是否变化 |

把所有切片压成一个平均分会丢失高风险回归。可以报告总体指标，但发布判断需要
同时保留关键切片和失败样本。

### 7.4 回滚要快于继续争论

回滚设计的核心是缩短“发现问题到停止扩大影响”的时间。候选版本应能被路由器
停止接收新流量，正在执行的请求按策略完成、取消或迁移；旧模型、旧模板、旧索引
和旧策略要保持可用到观察窗口结束。

如果一个发布只能通过重新构建镜像、重新下载权重和重新生成索引才能回退，它在
长上下文或大模型服务中可能需要几十分钟。更实用的做法是提前预热经过验证的旧
版本，保存 manifest 和回滚命令，并明确哪些外部副作用无法回滚、只能通过补偿
事务恢复。

## 8. 过载与故障：系统如何在压力下保持可用

### 8.1 过载不是单一故障

过载可能表现为：

- queue time 增长，但 GPU 利用率不高，说明请求被上游或调度器卡住；
- GPU 利用率高、KV 使用率高，说明模型池确实达到容量边界；
- prefill 饱和、decode 空闲，说明长输入压制了生成；
- decode 饱和、prefill 较低，说明大量长输出占用执行槽；
- RAG 或工具服务超时，模型 GPU 反而在等待外部依赖；
- 流式连接数量上升，但每个连接 token 很少，说明网络或客户端消费速度形成了
  backpressure。

因此“加机器”之前要先确认是哪一类资源在饱和。不同瓶颈对应的动作可能是分离
队列、限制输入输出、调整 batch、扩展检索服务、降低媒体分辨率或转异步。

### 8.2 长请求和短请求的公平性

FIFO 队列容易让长请求阻塞短请求；完全优先短请求又可能让长任务无限等待。常见
做法是按预估 token 或任务类型分队列，使用 token budget 调度，并用 aging 防止
低优先级请求永久饥饿。

调度公平不等于所有租户获得相同速度。高价值租户可以有更高预算，但必须记录
优先级、等待时间和资源消耗，防止“优先级”变成无法解释的隐性歧视。

### 8.3 失败重试和熔断

外部依赖失败时，重试会暂时提高成功率，也会把已经拥塞的依赖压得更重。重试策略
需要同时设置次数、退避、超时、请求取消和熔断；只有明确可恢复的错误才重试。

熔断打开后，系统可以返回陈旧但带时间标记的检索结果、转人工、创建异步任务或
拒绝高成本能力。是否允许降级取决于业务：知识库不可用时可以回答“当前无法验证
资料”，但不能把旧内容伪装成最新政策；安全策略服务不可用时，高风险工具通常
应停止执行，而不是跳过安全检查。

熔断器通常有三个状态：

| 状态 | 请求行为 | 状态转换 |
| --- | --- | --- |
| `closed` | 正常调用，按窗口累计失败和超时 | 达到配置阈值且样本量足够时转 `open` |
| `open` | 快速失败或执行已批准的降级，不继续压迫故障依赖 | 冷却时间结束后转 `half_open` |
| `half_open` | 只放少量探测请求 | 探测成功恢复 `closed`；失败则重新 `open` |

熔断阈值、最小样本量、冷却时间和半开探测数都要按依赖特性设置，不能照抄一个
通用数字。重试是针对某个请求再试一次，熔断是依赖级别停止放大失败；两者组合时
必须确保熔断打开后，不会又被应用层或 SDK 自动重试绕过。[Azure Architecture
Center 的微服务模式](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/patterns)
将 retry 与 circuit breaker 作为互补的故障隔离模式。

### 8.4 流式断线和取消

客户端断线后，服务端应收到取消信号并释放模型执行槽和 KV Cache。对于已经生成
的 token，系统可以记录已发送数量和取消原因，但不能把断线自动算成模型质量失败。

如果产品支持断点续传，需要为流式事件分配序号，并保证服务端保存的状态与客户端
最后确认的序号一致。否则恢复时可能重复显示文本或丢失工具调用。对普通聊天，
重新请求通常比保存完整 KV 更简单；对昂贵的长任务，持久化 job 状态可能更合适。

## 9. 扩展：副本、多 GPU 和多区域

### 9.1 横向扩展适合提高服务容量

当模型能放入单个副本时，增加副本通常是提高 QPS 和可用性的直接办法。它需要
健康检查、请求排空、模型预热、负载均衡和共享的版本 manifest。健康检查不能只
判断进程还活着，还应区分：

1. 进程是否存活。
2. 模型是否已经加载。
3. runtime 是否能接受新请求。
4. KV 和队列是否已经超过保护水位。
5. 当前副本是否处于 draining 或发布状态。

把所有状态都映射为一个 `healthy=true` 会让路由器把流量送给“进程活着但已经
不能接新请求”的副本。

若运行在 Kubernetes 上，startup、readiness 和 liveness probe 不能互换：startup
允许权重加载和 warmup；readiness 决定是否接新流量；liveness 只应判断进程是否
卡死到需要重启。把队列过长或下游短暂超时设成 liveness 失败，会让多个 GPU Pod
同时重启，反而削弱剩余容量。过载优先通过限流、排队和 admission control 处理，
只有确实不能继续服务时才从 readiness 池摘除。[Kubernetes probes 文档](https://kubernetes.io/docs/concepts/workloads/pods/probes/)
分别定义了三类 probe 的用途，也提醒错误的 liveness 设置会造成级联重启。

### 9.2 多 GPU 扩展适合装下更大的模型

Tensor Parallel 将层内矩阵切分到多个 GPU，Pipeline Parallel 将层按阶段分配，
Expert Parallel 则常用于 MoE 专家分布。选择哪一种取决于模型结构、batch、拓扑、
通信带宽和故障域。多 GPU 并不自动提高单请求速度：如果跨节点通信成为瓶颈，
更大的并行度可能降低有效吞吐。

部署时要把 GPU 拓扑记录下来。NVLink、PCIe 和跨节点网络的带宽差异会改变 TP、
PP 和 KV 传输的取舍。压测应覆盖单请求、短 batch、长 batch 和混合长度，不能只
报告一个理想输入长度下的吞吐。

### 9.3 多区域扩展改变了数据和状态问题

多区域部署除了就近接入，还要回答：

- 哪些请求可以跨区域发送；
- 租户数据和日志是否允许离开原区域；
- 模型、prompt、索引和安全策略怎样同步；
- response/prefix cache 是否跨区共享；
- Agent 状态和工具操作由哪个区域拥有；
- 区域故障时恢复目标是 RTO 还是 RPO 优先。

跨区域复制缓存看似能提高命中率，却可能扩大隐私和删除传播的复杂度。对带副作用
的 Agent，区域切换前必须确认状态所有权，否则两个区域可能同时推进同一个工作流。

## 10. 多租户资源和成本模型

### 10.1 租户配额需要多个维度

单一 QPS 配额无法表达长上下文和多模态成本。可以把租户 `u` 的资源消耗抽象成：

~~~math
q_u+\alpha T_u+\beta A_u+\delta K_u+\eta M_u\le B_u
~~~

`q_u` 是请求数，`T_u` 是 token，`A_u` 是 active sequence 时间，`K_u` 是工具
调用或检索成本，`M_u` 是媒体像素、音频秒数或视频帧等模态资源，`B_u` 是租户
预算，系数把不同单位换成统一的内部预算点数。这不是对外计费公式，而是帮助
调度器保护共享资源的近似模型。

预算模型不能取代权限模型。一个租户即使还有预算，也不应访问另一个租户的文档；
一个用户即使有文档读取权限，也不一定有执行写操作工具的权限。

### 10.2 单 token 成本不是单成功任务成本

如果某个路由方案需要更多重试、人工升级或补偿事务，便宜的 token 单价可能反而
更贵。更完整的指标是：

~~~math
C_{\mathrm{success}}
=
\frac{
C_{\mathrm{model}}
+C_{\mathrm{retrieval}}
+C_{\mathrm{tool}}
+C_{\mathrm{retry}}
+C_{\mathrm{storage}}
+C_{\mathrm{human}}
}{N_{\mathrm{success}}}
~~~

`N_success` 必须按照预先定义的任务完成标准统计。对 Agent，成功意味着外部状态
正确提交；对 RAG，成功可能还要求关键 claim 有可定位证据；对发票抽取，成功是
字段和金额都符合业务规则。只看模型 token 账单会漏掉大量辅助成本。

### 10.3 Autoscaling 要围绕资源信号

QPS 适合衡量请求量，却不适合单独驱动 LLM 扩缩容。更有信息量的信号包括：

- 等待队列中的 token 数；
- active sequence 数和 KV Cache 水位；
- prefill 与 decode 的利用率；
- TTFT 和 P99 趋势；
- 模型加载、预热和 draining 时间；
- 每个租户的预算和未完成任务数。

扩容动作也有延迟。若模型加载需要数分钟，等 P99 已经恶化后才创建 Pod，用户
体验可能已经受损。warm pool、预加载权重、异步扩容和保守缩容可以减少冷启动，
但会增加空闲 GPU 成本。扩缩容策略应把冷启动和发布期间的容量损失计入预算。

## 11. 一个企业知识助手的完整设计

### 11.1 需求和限制

假设要设计一个企业客服系统，包含 FAQ、知识库问答、代码片段解释和 Agent 退款
查询。业务方给出以下初始条件：

- FAQ 峰值 35 QPS，输入约 900 token，输出约 180 token；
- RAG 峰值 12 QPS，输入约 2,800 token，输出约 240 token，前缀复用比例估计为
  25%；
- 退款 Agent 峰值 3 QPS，平均 3 次模型调用，完整任务平均约 12 秒；
- FAQ 和 RAG 需要交互式响应，Agent 可以异步完成；
- 同步路径的目标 P95 为 3.5 秒，Agent job 的最长等待目标为 30 秒；
- 需要租户隔离、引用、退款权限检查和可审计的操作状态；
- 两个模型池分别使用 1 张和 2 张 GPU，容量规划预算为 14 张 GPU。

这里的数字是教学案例，不是某个厂商的承诺。真实容量表必须用目标模型、目标
硬件、实际模板和代表性输入回放得到。

### 11.2 选择两条不同的路径

FAQ 先经过意图分类和 response cache。未命中时优先走 small model；如果质量评估
或风险策略认为答案不够可靠，再 fallback 到 large model。fallback 事件必须记
录原因，否则成本账本会把它误认为普通大模型流量。

RAG 请求依次经过权限过滤、混合召回、低置信度时的 reranker、context builder 和
large model。回答输出前做 claim 与证据的对应检查，无法支持的内容要降低确定性
或明确说明资料不足。

退款 Agent 先创建 job 和操作 id，再由状态机推进查询、确认和提交。查询可以自动
重试，提交必须使用幂等键；模型只提出工具参数，权限服务和业务工具共同决定是否
执行。这样即使模型输出语言发生变化，退款权限仍不由自然语言单独决定。

### 11.3 容量计算

对 small pool，FAQ 的有效输入吞吐为：

~~~math
R_{\mathrm{in,small}}=35\times900\times(1-0.20)=25{,}200
~~~

输出吞吐为 `35×180=6,300 token/s`。端到端任务并发近似为 `35×2=70`，但它不等同于
GPU 活跃序列数。

对 large pool，RAG 的有效输入为 `12×2,800×(1-0.25)=25,200 token/s`，Agent
的输入为 `3×3×1,600=14,400 token/s`。所以：

~~~math
R_{\mathrm{in,large}}=39{,}600,
\qquad
R_{\mathrm{out,large}}=12\times240+3\times3\times360=6{,}120
~~~

RAG 的端到端任务并发约为 `12×3.2=38.4`，Agent 任务并发约为 `3×12=36`；两者
相加的 74.4 是业务 job 数，不是 GPU 活跃序列数。按示例的模型服务时间假设估算，
small pool 约有 `35×1.010=35.3` 个活跃序列；large pool 中 RAG 约
`12×2.204=26.5` 个，Agent 约 `3×3×3.157=28.4` 个，合计约 54.9。只有这组
runtime 序列数与 `S_m` 比较。使用 small pool `150k/7k/120`、large pool
`65k/1.8k/48` 的同一混合负载教学基准，并取 20%
余量，计算得到 small 两个副本、large 五个副本。large 的输出吞吐是主限制：

~~~math
\left\lceil1.2\times\frac{6{,}120}{1{,}800}\right\rceil=5
~~~

small 每个副本 1 张 GPU，large 每个副本 2 张 GPU，总 GPU 数是 `2+5×2=12`，
在 14 张的规划预算内。若任意一个 large 副本故障，剩余四个副本仍提供
`4×1,800=7,200 token/s`，高于 6,120；但这只说明 decode 容量满足 N+1，不能
证明网络、KV 重建和恢复时间也满足业务要求。

### 11.4 失效路径

这个系统至少需要提前写出四种失效路径：

1. **large pool 过载**：优先停止扩大非关键流量，保留 FAQ 小模型，长 RAG 转
   异步或减少候选证据；不直接删除权限和引用检查。
2. **向量库不可用**：RAG 回答进入“无法验证资料”的状态，或转人工；不能把旧缓存
   当作最新政策，除非缓存携带明确的时间和版本。
3. **退款工具超时**：把操作标记为 `unknown`，查询外部状态；不能依据模型上下文
   直接重复提交。
4. **安全策略服务不可用**：高风险工具停止，低风险纯文本能力可以按预先批准的
  降级策略处理，并把策略缺失记录到 trace。

失效路径写清楚以后，架构图中的每个箭头才有含义：它不只是表示数据流动，也表示
超时、取消、重试、审计和恢复信息怎样传播。

### 11.5 发布和回滚路径

一次候选发布包含模型、tokenizer、模板、路由、RAG 索引、reranker、安全策略和
runtime 镜像。先用固定回放比较任务质量、引用和安全切片，再 shadow 观察真实
输入长度和 cache 分布，最后把一个低风险租户放入 canary。若 P95 变差，先判断
是候选模型、路由、缓存污染还是上游依赖；若确认是候选版本，停止扩大流量并恢复
上一份 manifest。

对于退款操作，回滚模型并不能撤销已经提交的退款；业务系统仍需要补偿事务或人工
处置。因此回滚设计必须区分“软件版本回退”和“外部副作用恢复”。

## 12. 最小可运行的容量与可靠性诊断示例

下面的 demo 使用标准库，输入是三类工作负载和两个模型池。它分别计算端到端任务
并发与模型 runtime 中的活跃序列、token 吞吐、副本数量和 N+1 输出容量，再检查
组件/可观测性/安全/回滚清单与 GPU 预算。清单项只表示“方案声明了该组件”，不
证明它已经实现或有效。教学输入没有目标服务的 P95、任务质量或安全评估证据，代码
会明确暂停，而不会把线性延迟估算当成发布结论。示例吞吐和耗时是假设值；目标容量
需要在同一模型版本、硬件和混合 workload 下压测。

为使账本中的活跃序列和 prefill 容量使用同一组假设，单次模型调用的服务时间按
下面的近似式计算：

~~~math
\tau_{model}
\approx
1000\frac{P_{effective}}{U_{prefill}}
+T_{first}
+\max(O-1,0)\,TPOT
~~~

这里 `U_prefill` 是模型池给定的输入 token/s，乘数 1000 把秒换成毫秒；`T_first`
是一个教学用的 prefill 后首 token 固定开销，`TPOT` 只计首 token 之后的生成间隔。
真实系统的 TTFT 还受到排队、批处理、kernel、网络和调度影响；以下常数只是用于
说明计算关系，不能作为目标服务的延迟预测。

def aggregate_pool_needs(items, pools):
    needs = {}
    for item in items:
        pool = item["pool"]
        steps = item.get("steps", 1)
        needs.setdefault(
            pool,
            {
                "input_tps": 0.0,
                "output_tps": 0.0,

        needs[pool]["input_tps"] += item["qps"] * steps * effective_prompt
        needs[pool]["output_tps"] += item["qps"] * steps * item["completion"]
        needs[pool]["active_seq"] += (
            item["qps"] * steps * model_service_ms(item, pools[pool]) / 1000
        )
        needs[pool]["active_jobs"] += item["qps"] * item["task_latency_s"]
    return needs

        need["input_tps"] / pool["prefill_tps"],
        need["output_tps"] / pool["decode_tps"],
        need["active_seq"] / pool["active_seq"],
    ]
    return max(1, math.ceil(headroom * max(ratios)))

    return round(one_call * item.get("steps", 1))

## 13. 系统运行日：六个关键决策案例

前面的章节已经给出了组件、公式和接口边界，但生产系统不会按照章节顺序发生故障。真实的一天可能先遇到长请求挤压，再遇到 P99 变慢，下午上线候选模型，随后检索服务短暂不可用，最后还要处理一个外部工具的未知提交。把这些事件放在同一条时间线上，才能看出容量、质量、安全和状态之间怎样相互影响。

下面继续使用本章的企业助手作为案例。它同时承载短 FAQ、长文档问答、代码解释、退款 Agent 和发票图片问答。每一次处理都先读取请求的任务类型、租户、输入输出预算和风险级别，再决定同步完成、排队、降级、转异步或拒绝。这个决定会写入 trace，后面的恢复和计费都以它为依据。

### 13.1 早高峰：长请求不能把短请求挤出队列

月末上午，财务政策更新后，用户集中询问报销规则。短 FAQ 的输入不到 1,000
token，可以在一秒左右完成；另一批用户把几十页合同和发票说明一起上传，RAG
请求的上下文超过 20,000 token。两类请求共用一个 large model 队列时，GPU 利用率
看起来很高，但 FAQ 的 TTFT 从 300 毫秒升到 4 秒。

第一步不是立刻增加副本，而是确认压力来自哪里。系统按请求类型计算 token 到达率、
活跃序列和队列等待，并把 trace 分成 short_faq、long_rag、agent 和 multimodal。
如果 FAQ 的到达率为 \(\lambda_f\)，平均停留时间为 \(L_f\)，则其平均活跃数近似为：

~~~math
A_f=\lambda_f L_f
~~~

其中 \(A_f\) 是正在排队、执行或等待结果的 FAQ 数量。这个关系说明了为什么长 RAG
会伤害短 FAQ：长请求增大的是自身的停留时间和 KV 占用，也会让短请求在共享队列
中等待。它不能告诉我们突发流量下的 P99，但足以帮助调度器把“请求数相同、资源
工作不同”区分开。

第二步是按资源和体验目标拆队列。短 FAQ 使用专用的小模型池或保留容量，长 RAG
进入带 token 预算的队列；持续时间超过同步目标的请求转为异步 job。continuous
batching 可以在 decode 迭代之间重新分配机会，但它不是无限公平机制，仍需限制
单个请求每轮占用的 token、最大输出和 KV block 数。一个请求不能因为上下文很长，
就让同一批中的其他请求长时间得不到 decode 机会。

| 观察 | 可能原因 | 当班动作 |
| --- | --- | --- |
| FAQ queue time 上升，large GPU 近满 | 长 RAG 占用执行槽和 KV | 拆分短请求池，限制长上下文并发 |
| prefill 饱和，decode 空闲 | 大量长输入同时进入 | 降低候选证据数，分批 prefill 或转异步 |
| decode 饱和，prefill 正常 | 输出过长或 Agent 循环 | 限制输出/步骤，检查是否重复工具调用 |
| GPU 利用率低但 queue time 高 | CPU 解码、依赖或路由堵塞 | 查看上游 span，不盲目增加 GPU |

超长请求的处理还要区分“不能处理”和“现在不适合处理”。前者是输入超过模型
有效窗口、文件超过资源上限或租户没有权限，应该返回稳定的输入错误；后者是当前
容量不足，可以排队、减少非关键上下文或转成异步任务。两者都返回一个模糊的
“服务繁忙”，用户无法知道是修改请求还是等待更合适。

最终的处理决策应带原因，例如 queue_budget_exceeded、long_context_async 或
short_pool_reserved。用户可以只看到“请求较长，已转为后台处理”，内部则能知道
是哪个预算触发了这条路径。这样做也使容量实验可回放：如果增加副本后 TTFT 没
改善，trace 能证明问题原本不在模型池，而在上游解析、检索或网络等待。

### 13.2 午间告警：P99 变慢要沿 trace 找到阶段

午间监控发现同步接口的 P99 从 3.2 秒升到 6.1 秒，而平均延迟只从 1.1 秒升到
1.3 秒。平均值没有明显变化，说明可能只有长上下文、某个租户或某一条路由受到
影响。先固定告警的时间窗口、分母、请求切片和版本，避免把采样变化误认为性能
回归。

然后将端到端延迟拆成阶段：

~~~text
P99 E2E
  -> queue
  -> retrieval / rerank
  -> media preprocessing
  -> prefill
  -> decode
  -> tool / safety / network
~~~

如果只有 queue span 变长，优先调查副本健康、优先级老化和队列反压；如果 prefill
变长，比较输入 token、视觉位置、缓存命中和模板版本；如果 decode 变长，比较
输出长度、采样参数、KV 抢占和 batch 形状；如果工具 span 变长，应先隔离外部
依赖，而不是更换语言模型。一个能解释原因的 trace 比一张只有 P99 曲线的仪表盘
更有价值。

检查还要覆盖错误的分母。用户主动取消不应自动算作服务错误，缓存命中率不能把
短前缀和长前缀当成同一种收益，工具成功率不能把没有调用工具的请求放进分母。
如果指标定义改变，告警趋势也会改变，值班人员必须在事件记录里保留计算版本。

一次完整的诊断记录可以包含：

~~~text
window=12:00-12:10
cohort=long_rag
baseline_p99_ms=3200
observed_p99_ms=6100
queue_delta_ms=+40
prefill_delta_ms=+2100
input_tokens_p95=18400 -> 26700
cache_saved_token_ratio=0.42 -> 0.18
candidate_index=index-1842
action=reduce_context_and_hold_rollout
~~~

这里的动作先限制上下文并暂停继续放量，而不是立即把所有流量迁移到更大的模型。
如果回放证明是索引返回了过多重复证据，修复检索和缓存比扩充 GPU 更有效；如果
确实是副本不足，再根据输入/输出吞吐和活跃序列重新计算容量。

### 13.3 下午发布：模型能力变强，系统未必变好

候选模型在离线代码和复杂问答集上的分数提高了，但它的输出平均长 30%，工具
调用步骤多了一步，输入模板也增加了新的系统说明。直接全量切换会同时改变质量、
延迟、显存、成本和副作用概率，因此发布单元必须包含权重、tokenizer、模板、
runtime、路由、索引、工具 schema 和安全策略。

先固定四类证据：正常任务、长上下文、权限边界和高风险工具。比较时至少记录：

| 维度 | 基线 | 候选 | 解释 |
| --- | --- | --- | --- |
| C_success | 模型、检索、工具、重试和人工成本 | 同口径计算 | 输出变长可能抵消单价下降 |
| TTFT/P99 | 按长度和租户分层 | 同样分层 | 全局平均会隐藏长尾 |
| 工具行为 | 参数、授权、提交状态 | 同样检查 | 模型生成 call 不等于动作成功 |
| 安全 | 漏放、误拦、越权 | 固定攻击集和人工复核 | 安全回归不能被质量提升抵消 |

候选模型先进入 shadow 流量，确认输入长度、缓存命中和工具提案的分布没有异常，
再进入一个稳定的低风险租户。canary 期间要观察新旧版本的同一批任务，而不是把
不同租户、不同日期和不同输入规模的结果直接平均。只有这样，质量变化才可能归因
到候选 bundle，而不是归因到 workload 变化。

若候选模型只在高价值代码任务上提高成功率，可以先把这类任务路由给候选，其余
流量继续使用基线。若长 RAG 的证据支持度提高但单位成功成本超过预算，则先检查
上下文压缩、候选数和响应长度，而不是把模型质量提升简单归因于模型权重。

一个成熟的 canary 结果还要回答“谁受益、谁退化”。例如总体质量上升 2%，但中文
表格抽取下降 5%，高风险工具的未知提交上升，仍然应暂停扩大流量。切片和失败
样本比一个漂亮的全局平均更接近发布决策。

### 13.4 下午故障：RAG 不可用时怎样表达未知

向量库维护期间，RAG 请求无法取得当前证据。系统不能为了保持 HTTP 200 而让模型
用参数记忆补写企业政策。首先区分任务的真实性要求：

| 任务 | 资料不可用时的结果 |
| --- | --- |
| 普通闲聊 | 可以回答，但标明未使用企业资料 |
| FAQ 政策问答 | 返回资料暂不可验证，提供重试或转人工 |
| 合同/医疗/财务判断 | 不给确定结论，创建异步复核或升级 |
| 退款提交 | 不执行依赖规则证据的动作 |
| 已有明确时效的缓存 | 只有版本和有效期满足条件时允许读取，并标明时间 |

系统可以把证据状态建模为 verified、stale、unavailable 和 forbidden。stale
不是 verified 的弱化写法：它表示有一份旧资料，但资料的时间范围可能不足以
支持当前结论；forbidden 表示用户没有权限，不能告诉用户“系统找到了但不能给
你看”的内部内容。

降级结果要携带来源状态、索引版本和时间戳。前端可以把“资料暂不可用”显示为
可重试状态，后台则记录依赖错误、受影响的租户和未完成任务。恢复向量库后，先
回放受影响请求，再决定是否补发答案；不能因为服务恢复就自动执行之前被阻止的
写操作。

### 13.5 傍晚事务：工具超时不能变成重复退款

用户请求退款时，模型先提出工具参数，权限服务确认主体、订单和金额，业务工具
收到带有稳定操作 ID 的请求。若下游完成退款但响应在网络中丢失，当前执行器只
知道“没有收到回执”，并不知道退款是否已经提交。这就是 committed_unknown，
不是失败，也不是成功。

状态机可以按以下顺序运行：

~~~text
intent
  -> authorized
  -> dispatched
  -> committed / rejected / committed_unknown
  -> status_queried
  -> final_response
~~~

committed_unknown 状态至少保存操作 ID、幂等键、下游 request ID、最后一次错误、
查询时间和当前用户可见的提示。恢复任务使用原幂等键查询外部状态；确认已提交后
才能生成“退款已完成”，确认未提交且协议允许重试时，才可以继续同一个操作。绝不
因为模型上下文缺少一条工具结果就生成新的业务请求 ID。

查询型工具和写型工具的处理策略不同。查询可以在有限次数和超时上限内重试；退款、
删除、发邮件和修改权限需要状态查询、幂等语义和必要的人工介入。模型可以重新
规划下一步，但不能获得绕过业务服务授权的能力。

### 13.6 跨租户公平：预算不等于无限资源

月末高峰时，某个大租户有足够预算，连续提交大量长文档任务。如果调度器只看预算，
它会占满 prefix cache、KV block 和异步队列，其他租户即使提交短 FAQ 也要长时间
等待。公平设计需要同时考虑请求数、token、active sequence、媒体工作量和任务
优先级。

一个租户 \(u\) 的内部资源预算可以写成：

~~~math
q_u+\alpha T_u+\beta A_u+\delta M_u\le B_u
~~~

\(q_u\) 是请求数，\(T_u\) 是 token，\(A_u\) 是活跃序列时间，\(M_u\) 是像素、
音频秒数或视频帧等媒体工作量，\(B_u\) 是预算点数。系数只是把不同资源换成可
比较的内部单位，必须通过目标 workload 校准；它不是对外计费公式。

调度器可以采用加权公平队列、租户并发上限和优先级老化。高优先级任务获得更快
服务不等于可以无限占用资源；每个租户仍需有 token、KV、工具调用和 wall-time
上限。日志应记录优先级、等待时间、实际资源和降级原因，避免“优先级”变成无法
解释的隐性差异。

租户隔离还必须覆盖数据和派生状态。一个租户的 prefix cache、检索结果、媒体
embedding 和错误日志不能因为调度器共享 GPU 就对另一个租户可见；预算检查也不
能替代 ACL。若一个租户超过预算，系统可以排队、降级或转异步，但不能通过删除
权限检查来换取吞吐。

一天结束时，平台应能回答六个问题：哪类 workload 消耗了资源，哪一层造成了长尾，
候选版本是否真的改善任务，资料不可用时是否诚实表达未知，外部动作是否最终一致，
以及不同租户是否都获得了可解释的服务。这六个答案共同构成生产系统的运行证据，
而不是某一个组件的健康状态。

## 14. 常见误区与修正

### 14.1 误区：系统 QPS 高低能直接决定 GPU 数量

QPS 没有携带输入输出 token、请求停留时间和模型池信息。正确做法是先按 workload
计算 token 吞吐、active sequence 和显存，再用目标硬件的压测数据换算副本。

### 14.2 误区：推理引擎就是生产平台

引擎解决模型执行效率，平台还要解决身份、租户、版本、路由、策略、审计、账单和
故障恢复。把所有问题都寄托在引擎参数上，会让权限和发布边界变得模糊。

### 14.3 误区：缓存命中率越高越好

应该看命中 token、实际减少的 GPU 时间、失效成本和任务成功率。错误缓存可能带来
跨租户泄露，prefix cache 还会占用显存并造成真正热点的淘汰。

### 14.4 误区：所有错误都重试

重试对暂时性网络错误有帮助，对模型质量失败、权限拒绝和不可逆写操作可能有害。
没有幂等键的写重试会把一次超时变成两次业务动作。

### 14.5 误区：输出后过滤就足够安全

安全边界必须覆盖输入、检索内容、工具 schema、工具参数、工具结果、流式输出和
审计。Prompt injection 可能藏在文档或网页中，单纯检查用户输入并不能保护工具。

### 14.6 误区：灰度只需要切换模型名称

Prompt、tokenizer、chat template、索引、reranker、安全策略、路由和 runtime 都
可能改变行为。灰度和回滚应以 manifest 为单位，否则“回滚模型”后服务仍可能使用
新模板或新索引。

### 14.7 误区：平均质量和平均延迟足以代表系统

高风险工具、长上下文、少数语言和多模态输入往往只占小比例，却决定事故严重度。
必须保留切片、尾部延迟、失败样本和安全样本，不能只看全局平均值。

## 15. 资料、实现与证据边界

本章的公式是容量规划和系统沟通用的近似模型，不是任何服务的性能保证。资料按
证据类型使用：

1. 官方 API 和平台文档用于确认接口、生产运维和计费语义；供应商公开文档不能
   推导出所有本地模型或私有部署的性能。
2. vLLM、Kubernetes 和 OpenTelemetry 官方文档用于确认 runtime 指标、资源声明、
   扩缩容和 trace 的工程入口；具体效果仍需在目标模型、硬件和 workload 上实测。
3. NIST AI RMF、GenAI Profile 和 OWASP 资料用于组织风险、控制和威胁语言，不是
   对某个系统安全性的认证。
4. RAG、speculative decoding 和排队理论的论文用于理解方法和公式来源；论文中的
   benchmark、硬件和输入分布不能直接替代线上数据。
5. 本章中的吞吐、延迟、缓存节省和 GPU 数量都是教学案例，必须标明假设，不能
   写成厂商或框架的普遍承诺。

延伸阅读：

1. [OpenAI Production Best Practices](https://platform.openai.com/docs/guides/production-best-practices)：生产部署、密钥、可靠性和运维边界的官方资料。

## 16. 本章小结

生产系统设计的核心不是画出最多的组件，而是让每一个组件都处在清楚的契约和
故障边界中。

1. 先区分同步、流式、异步、RAG、Agent 和多模态 workload，再谈 QPS 和副本。
2. 用输入/输出 token 吞吐、active sequence、KV 显存和目标硬件压测做容量规划；
   QPS 只是到达率，不能代表计算量。
3. Gateway、身份、配额、路由、上下文、缓存、推理引擎和响应协议共同决定请求
   是否能正确完成，推理引擎本身不是完整平台。
4. 缓存要区分 response、prefix/KV、embedding/rerank 和媒体缓存，并同时处理版本、
   权限、TTL、失效和显存成本。
5. Trace、指标和评估必须保留分母、切片和版本，P95/P99 不能被平均值或单次压测
   结果替代。
6. 重试、取消、幂等、commit-unknown、补偿事务和多区域状态所有权决定系统能否
   在失败后恢复，而不是只在 happy path 中运行。
7. 发布单元应绑定模型、tokenizer、模板、索引、策略和 runtime；离线回放、shadow、
   canary 与回滚分别提供不同证据。
8. 成本要按单成功任务计算，把模型、检索、工具、重试、存储和人工处置放进同一
   账本，同时保留质量、安全和可靠性原始信号。

当读者能从一次请求出发，说明它经过哪些边界、消耗哪些资源、哪些状态需要持久化、
哪些失败可以重试、哪些副作用必须查询确认，并能用压测和评估证据验证设计时，才
算真正理解了生产系统，而不是背下了一张架构图。
