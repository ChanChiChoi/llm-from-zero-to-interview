# 第六章：批处理与调度

在线服务中的 GPU 很少真正“空闲”或“满载”这么简单。一个长 RAG 请求刚开始做 prefill 时，需要大量矩阵计算；另一个已经生成了几百个 token 的请求，每一轮只需要读写自己的 KV Cache；第三个请求刚刚到达，只想尽快看到首个 token。如果把这三个请求当成同一种工作，系统要么让 GPU 等待，要么让某一类请求长期牺牲延迟。

批处理解决的是“哪些请求一起计算”，调度解决的是“什么时候让哪些请求消耗多少资源”。这两个词经常一起出现，却不是同一个问题：batch 是某一轮执行的工作集合，scheduler 还要决定排队、是否接收、优先级、预算、抢占、取消和租户公平性。一个批次很大，不代表调度是好的；它可能只是把等待时间和显存压力推给了用户。

初学者可以先记住一个画面：传统模型通常把一批样本送进一次 forward，LLM 却要让每个请求经历输入处理和逐 token 生成两个阶段，而且每个请求的结束时间都不同。因此，高性能服务会在每轮迭代重新安排活动请求。专家需要进一步追问：本轮消耗的是 prompt token 预算还是 decode token 预算？新请求是否会挤占已有请求的 TPOT？KV block 是否足够？高优先级策略是否造成低优先级饥饿？这些问题才决定一个 scheduler 是否真的适合生产。

本章从一个请求的生命周期开始，依次建立 static batching、dynamic batching 和 continuous batching 的差异，再讨论 token/KV 预算、prefill 与 decode 的混合调度、队列论、公平性、多租户、抢占和过载保护。代码 demo 只模拟调度决策，不模拟真实 GPU kernel；它用于验证账本和状态转换，不能替代目标模型上的压测。

## 本章资料边界

本章用 Orca 论文解释 iteration-level scheduling 的研究背景，用 Hugging Face、vLLM、TensorRT-LLM 和 SGLang 的官方文档核对当前公开的 serving 抽象。论文说明一种调度思想及其论文实验条件，官方文档说明某个项目当前版本的接口或能力，二者都不能单独证明目标模型、目标硬件和真实 workload 的性能。文末列出资料链接，并把版本敏感的参数和未测结论明确标成待实测事项。

## 1. 先建立调度问题的坐标系

### 1.1 LLM batching 为什么比普通模型复杂

普通分类模型常见的路径是“收集样本、补齐形状、执行一次 forward、返回结果”。LLM 的在线请求至少包含两个阶段：

1. prefill：把 prompt 的 token 一次或分块送入模型，建立后续生成所需的状态。
2. decode：每轮根据已有状态生成下一个 token，直到 EOS、stop、长度上限或取消。

输入长度和输出长度都不固定。请求 A 可能有 128 个 prompt token、只生成 16 个 token；请求 B 可能带 32k token 的检索上下文、生成 2k 个 token。A 的首 token 可能很快，但 B 会长时间占用 prefill 计算和 KV Cache。decode 期间，虽然每轮新计算的 token 很少，批次却要反复访问所有活动请求的状态。

对请求 r_i，记：

- P_i：已经经过 tokenizer 的 prompt token 数；
- O_i：最终输出 token 数；
- D_i(k)：第 k 轮开始前已经生成的 token 数；
- S_i：它是否占用一个 active sequence 槽位；
- K_i(k)：该请求在第 k 轮占用的 KV token 或物理 cache block。

在最粗的账本里，逻辑上下文长度是：

~~~math
L_i(k)=P_i+D_i(k).
~~~

这个式子不是完整的显存模型。不同 attention 结构、张量并行、量化和分页方式会改变每个 token 的实际字节数；它的用途是提醒我们：调度成本随着 token 和状态增长，而不是随着请求数等比例增长。

### 1.2 批次大小有三个不同含义

“batch size”在讨论中经常造成误会，至少要拆成三种量：

1. sequence count：当前同时活动的请求数。
2. prefill token count：本轮新处理的 prompt token 数。
3. decode token count：本轮为活动请求生成的 token 数，通常接近活动请求数，但在 speculative decoding 或特殊 kernel 中可能不同。

一个 32-request 的 batch 可能包含 32 个很短的 prompt，也可能包含 32 个很长的 prompt；一个只有 8 个活动请求的 decode batch 也可能占用大量 KV Cache。只报 sequence count，无法解释显存和延迟；只报 tokens/s，也无法解释请求是否在队列里等待。

## 2. Batching 的目标不是 batch 越大越好

批处理让一次 kernel 调用承担更多工作，通常有利于矩阵乘法的利用率和整体吞吐；但它也会增加等待、显存占用和尾延迟。在线服务应同时报告吞吐和用户实际看到的延迟。

对压测窗口内的 N 个完成请求，可以定义输出吞吐：

~~~math
\mathrm{TPS}_{\mathrm{out}}
=\frac{\sum_{i=1}^{N}O_i}{T_{\mathrm{wall}}}.
~~~

若只有满足业务 SLO 的请求才算交付，则更接近业务价值的 goodput 是：

~~~math
\mathrm{Goodput}
=\frac{N_{\mathrm{SLO}}}{T_{\mathrm{wall}}}.
~~~

其中 N_SLO 是在规定时间内完成、且结果没有触发业务失败条件的请求数。

对请求 i，排队等待和首 token 延迟分别为：

~~~math
W_i=t_{\mathrm{start},i}-t_{\mathrm{arrive},i},
\qquad
\mathrm{TTFT}_i=t_{\mathrm{first},i}-t_{\mathrm{arrive},i}.
~~~

当 O_i>1 时，decode 阶段的平均 token 间隔可近似写成：

~~~math
\mathrm{TPOT}_i
=\frac{t_{\mathrm{end},i}-t_{\mathrm{first},i}}{O_i-1}.
~~~

若只输出一个 token，TPOT 没有足够的间隔样本，应记为 N/A；不能把 E2E latency 误报成 TPOT。还要区分 TPOT/ITL 的项目口径：有的系统把首 token 到末 token 的平均间隔称 TPOT，有的系统按相邻 token 计算 P50/P99 ITL。报告必须写清分母和时间端点。

调度目标可以表达为一个带约束的优化问题：

~~~math
\max\ \mathrm{Goodput}
\quad\mathrm{s.t.}\quad
P99(\mathrm{TTFT})\le \tau_{\mathrm{first}},
\quad
P99(\mathrm{TPOT})\le \tau_{\mathrm{token}},
\quad
K_{\mathrm{peak}}\le K_{\mathrm{budget}}.
~~~

这不是要求线上系统求解一个精确的全局最优问题，而是提供判断框架。调大 batch 只有在吞吐收益没有违反 TTFT、TPOT、显存和公平性约束时才有意义。平均延迟很好看但 P99 超标，或者 output TPS 很高但大量请求被截断，都不能算作成功的调度优化。

## 3. Static、dynamic 与 continuous batching

### 3.1 Static batching：简单但容易被最长请求绑架

Static batching 先固定一组请求，再让这组请求一起执行，直到整组结束。它适合离线推理、形状稳定的任务和容易预估的批量作业。

假设一个 batch 有 B 个输入，长度分别为 l_1,\ldots,l_B，使用 padding 对齐到最长长度 l_{\max}，仅从输入侧看，补齐 token 数是：

~~~math
N_{\mathrm{pad}}
=B\,l_{\max}-\sum_{j=1}^{B}l_j.
~~~

补齐 token 不一定都产生同样的实际 kernel 成本，因为不同 runtime 可能使用 packed input 或专门的变长 kernel；这个式子是解释浪费来源的上界式账本。输出长度差异还会带来另一种浪费：已经完成的短请求仍占着批次位置，或者运行代码不得不以 EOS/padding 继续维持统一步数。

初学者可以把它想成一辆必须等所有乘客到终点才回站的班车。专家还要检查两个细节：输入 padding 是否真的进入计算图，以及完成请求的 cache block 是否及时释放。只看到“batch=32”不能判断 static batching 的实际浪费。

### 3.2 Dynamic batching：用一个等待窗口换聚合收益

Dynamic batching 在短时间窗口内收集新到达请求，然后组成一次或少数几次 batch。设调度时刻为 t、最大等待窗口为 \Delta，则候选请求可以抽象为：

~~~math
\mathcal{C}(t)
=\{r_i\mid 0\le t-t_{\mathrm{arrive},i}\le\Delta\}.
~~~

候选集合仍要满足序列数、prompt token 和显存约束：

~~~math
|\mathcal{B}(t)|\le B_{\max},\qquad
\sum_{r_i\in\mathcal{B}(t)}P_i\le T_{\mathrm{prefill}},\qquad
K_{\mathrm{after}}\le K_{\mathrm{budget}}.
~~~

\Delta 越大，通常越容易形成更饱满的 batch，但每个请求的 TTFT 至少会多出一段等待；在低流量时，等待窗口可能直接成为首 token 延迟的主导项。高流量时，窗口不一定是主要问题，真正的瓶颈可能是 prefill 计算、KV Cache 或下游网络。

Dynamic batching 的关键是“何时停止等待”。固定 5ms 只是实现选择，不是普适答案。更稳妥的做法是把等待时间和队列长度、剩余 SLO、当前 token budget 以及服务优先级一起记录，再用目标 workload 做实验。动态 batching 也不自动消除 padding 或长请求拖慢短请求的问题。

### 3.3 Continuous batching：在迭代边界重排活动集合

LLM decode 每轮只推进一个或一小组 token，因此 scheduler 可以在迭代边界移除已经结束的请求，并把等待队列里的请求加入下一轮。对只讨论 decode 的简化模型，第 k 轮的活动集合为：

~~~math
\mathcal{B}_k
=\{r_i\mid \mathrm{state}_i=\mathrm{decode},
\ D_i(k)<O_i^{\max}\}.
~~~

若 \mathrm{Done}_k 是本轮结束的请求，\mathrm{New}_k 是通过资源检查并加入的请求，则：

~~~math
\mathcal{B}_{k+1}
=(\mathcal{B}_k-\mathrm{Done}_k)\cup\mathrm{New}_k.
~~~

真实 scheduler 往往还要把新请求的 prefill、chunked prefill、decode 和可能的重算放进同一轮预算。因此上式是说明“可增量替换”的教学抽象，不应理解为任何框架的源码算法。

一个典型 iteration 的顺序是：

1. 读取活动请求的状态，决定本轮 decode 或 prefill 工作。
2. 执行模型计算并产生 token。
3. 检查 EOS、stop、长度上限、取消和错误。
4. 释放完成请求的 sequence 槽位与 cache block。
5. 在 token、序列数和显存预算内从等待队列加入请求。
6. 记录本轮的排队、计算、cache 和输出事件。

Continuous batching 的收益来自减少“等整组结束”的空洞；它的代价是 scheduler、KV Cache、取消和流式事件都必须在迭代级别保持一致。加入新请求也不是免费操作：它可能带来新的 prefill 峰值，挤占 decode 请求的 kernel 时间，使已有请求的 TPOT 变差。

### 3.4 Chunked prefill：不要让一个长 prompt 独占一轮

如果一个 prompt 有几十万 token，直接把完整 prefill 插入在线 decode 轮次，可能让正在流式输出的请求长时间没有下一个 token。Chunked prefill 把 prompt 切成多个片段，在多个 iteration 中处理：

~~~math
P_i=\sum_{c=1}^{C_i}P_{i,c},
\qquad
P_{i,c}\le T_{\mathrm{chunk}}.
~~~

较大的 T_{\mathrm{chunk}} 有利于减少调度开销和提高 prefill 的计算效率，但会让 decode 请求等待更久；较小的 T_{\mathrm{chunk}} 有利于交错服务，却可能增加 kernel launch、状态管理和通信开销。chunk 边界还必须正确维护 position、attention mask、KV block table 和取消状态。

因此，“支持 continuous batching”不等于“长上下文在线体验一定好”。需要单独测长 prompt 的 TTFT、chunk 间隔、decode 请求的 TPOT P99、cache 峰值和取消后的回收时间。

## 4. 请求生命周期：队列不是一个抽象盒子

调度器要做出正确决定，必须知道请求现在处于哪个状态。一个简化的生命周期可以写成：

~~~text
received
  -> tokenize and validate
  -> waiting
  -> prefill
  -> decoding
  -> completed / cancelled / timeout / error
  -> release state and record metrics
~~~

工具调用或外部检索会在 decoding 与下一次模型执行之间插入 tool wait。此时请求仍然是业务上的活动任务，但不应继续占用 GPU decode 槽位；如果系统把 tool wait 误记成 decoding，就会虚增 active sequence，过早拒绝新请求。

每个状态对应不同的资源和计时含义：

1. received：连接、鉴权和请求体可能已经占用网关资源，但还没有消耗模型计算。
2. waiting：请求在本地队列中等待，主要消耗队列容量和少量元数据。
3. prefill：需要为 prompt 计算并分配状态，通常直接影响 TTFT。
4. decoding：每轮生成 token，持续读取和扩展 KV Cache，通常直接影响 TPOT。
5. cancelled：客户端不再需要结果，scheduler 应在下一个安全迭代尽快停止计算并释放状态。
6. completed/error：写入 finish reason、usage 和 trace，确认所有 cache block、流式连接和工具事务都已收束。

对每个请求同时记录 t_arrive、t_queue_end、t_prefill_end、t_first、t_end，才能把端到端延迟拆开：

~~~math
T_{\mathrm{E2E}}
=T_{\mathrm{queue}}
+T_{\mathrm{prefill}}
+T_{\mathrm{decode}}
+T_{\mathrm{tool}}
+T_{\mathrm{network}}.
~~~

这里的加法是观测口径，不是说所有阶段在系统中永远严格串行。例如网络发送可能与 decode 重叠，工具等待可能与其他请求的 GPU 计算并行。拆分的价值在于定位问题：队列变长要看过载或公平性，prefill 变慢要看输入长度和计算 kernel，decode 变慢要看活动请求数和 cache，network 变慢则不应盲目调 batch。

### 4.1 Little 定律给出的容量直觉

在稳定、长期平均的队列中，Little 定律把平均在途请求数、到达率和平均停留时间联系起来：

~~~math
L=\lambda W.
~~~

L 是平均在途请求数，\lambda 是平均到达率，W 是请求从进入该系统到离开的平均时间。若只讨论等待队列，就应把 L 和 W 都定义为等待队列的量；若把 prefill、decode 和 tool wait 全部算进去，则三者必须使用同一边界。

这个定律不能直接给出 P99，也不能告诉 scheduler 应该使用什么优先级，但它能提供一个重要警告：当有效服务率接近到达率时，平均等待时间会迅速上升；继续接收请求并不会凭空增加 GPU 服务能力。线上应设置有限队列和明确的 backpressure，例如返回可重试错误、降低低优先级流量、拒绝超过上下文预算的请求，或把离线任务移到异步队列。

无限增长的等待队列看起来没有丢请求，实际上会把故障变成更长的 TTFT、更多超时和客户端重试。重试又会增加到达率，形成 retry storm。服务端和客户端要共同设置超时、Retry-After、指数退避、随机抖动和幂等键，不能只在 scheduler 内部“再等一会儿”。

## 5. 请求队列

请求队列不是一个只保存字符串的 FIFO 容器，而是 scheduler 的决策输入。至少要保存 request id、tokenized prompt 的长度、最大输出长度、到达时间、截止时间、租户、优先级、是否流式、是否允许抢占、取消状态和当前 cache 账本。若请求包含工具调用，还要保存工具事务是否已经产生副作用；一个已经写入数据库的工具动作，不能像纯文本生成一样随意重试。

最简单的 FIFO 适合负载均匀、没有租户差异的场景。真实服务通常会先做几项硬约束检查，再在剩余候选中排序：

1. 请求是否超过上下文、输出、租户并发和预算上限。
2. 预计加入后是否超过本轮 prefill token、active sequence 和 KV Cache 预算。
3. 请求距离超时还有多久，是否有更高优先级的交互请求。
4. 该租户近期已经消耗多少 token，是否需要让其他租户获得服务机会。
5. 请求是否可以被取消、分块、抢占或转移到异步队列。

这里的“先检查资源，再排序”不是绝对的框架实现顺序，但它揭示了一个常见错误：如果只按优先级挑选，挑中的长请求可能根本放不进显存；如果只按 prompt 短挑选，又可能让长请求永久得不到服务。调度记录应保留候选、落选原因和最终选择，才能解释 P99 的变化。

### 5.1 队头阻塞与分队列

Head-of-line blocking 指队列最前面的请求阻止后面的请求前进。LLM 中它特别明显：一个长 prompt 可能独占 prefill 预算，一个长输出可能长期占用活动槽位。常见应对方式是按输入长度、业务类型或服务等级拆分队列，再在队列之间分配 token 预算。

分队列不是免费优化。短请求队列可能获得更低 TTFT，却让长请求队列积压；长度估计不准时，短队列也会混入昂贵请求；过多队列会降低 batch 形成机会。评估时要同时看每个队列的排队时间、SLO 达成率和 token 份额，不能只看总体平均值。

## 6. Prefill / Decode 分离

Prefill 和 decode 常有不同的资源画像，但“prefill 一定计算密集、decode 一定内存密集”只能作为起点，不能作为测量结论。模型规模、序列长度、batch、kernel、硬件和并行方式都会改变实际瓶颈。

Prefill 一般一次处理较多 prompt token，矩阵乘法的并行度更高，prompt 越长越容易占据较长的计算时间，所以更直接影响 TTFT。Decode 每轮只追加一个 token，却要读取每个活动序列的历史状态，并反复执行许多轮，因此更容易受到 KV Cache 带宽、活动序列数和调度开销影响，最终表现为 TPOT 和 E2E 变差。

如果把二者放在同一个 GPU 上，scheduler 需要决定本轮给 prefill 多少 token，给 decode 留多少计算时间。prefill 配额过大，已有流式请求会出现 token 间隔尖峰；decode 配额过大，新请求 TTFT 会变长。chunked prefill 正是把这个选择变成可控制的交错单位。

如果采用 prefill/decode disaggregation，可以把两类工作放在不同 GPU 池甚至不同节点。这样做有机会分别扩容，也能减少长 prefill 对 decode 的直接干扰；代价是需要传输或重建 KV/latent state，增加网络带宽、路由、故障恢复和 cache 一致性复杂度。只有当 workload 中长 prompt、长输出和 SLO 组合确实形成稳定瓶颈时，分离部署才可能抵消这部分成本。不能只因为架构图更复杂就推断吞吐一定更高。

判断分离是否值得，至少比较四项：

| 观察项 | 合并部署要问什么 | 分离部署要增加什么 |
| --- | --- | --- |
| 首 token | prefill 是否拖慢已有 decode | state 传输是否拖慢首 token |
| 持续输出 | prefill 插入时 TPOT 是否抖动 | decode 池是否有足够活动请求 |
| 资源利用 | 一个池能否同时填满计算和显存 | 两个池是否出现一边空、一边排队 |
| 故障恢复 | 单池重启和重试如何处理 | state 丢失、路由和跨节点恢复如何处理 |

判断是否需要分离，不能只说“prefill 偏算力、decode 偏带宽”，还要给出 trace、cache bytes、网络传输和 P99 证据。

## 7. Token budget 调度

LLM 请求的成本不能只看请求数。一个短请求和一个长上下文请求各占一个 sequence，但它们的 prefill 工作、KV Cache 和后续持续时间可能相差几个数量级。scheduler 因此需要同时维护三本账：

1. 本轮新增的 prefill token 账。
2. 当前活动 sequence 账。
3. 物理 KV block 或其他状态的显存账。

令 \mathcal{P}_k 表示第 k 轮进入 prefill 的请求集合，P_{i,k} 表示请求 i 在本轮新增的 prompt token 数，\mathcal{B}_k 表示本轮活动请求，T_prefill 表示本轮允许的新 prefill token 数，S_max 表示 active sequence 上限，则常见的资源约束可写为：

~~~math
\sum_{r_i\in\mathcal{P}_k}P_{i,k}\le T_{\mathrm{prefill}},
\qquad
|\mathcal{B}_k|\le S_{\max}.
~~~

若每个物理 block 能保存 b 个逻辑 token，忽略 prefix sharing 时，加入候选后的 block 需求可以粗略估计为：

~~~math
K_{\mathrm{after}}
\approx
\sum_{r_i\in\mathcal{B}_k}
\left\lceil\frac{P_i+D_i(k)+\Delta_i}{b}\right\rceil,
\qquad
K_{\mathrm{after}}\le K_{\mathrm{budget}}.
~~~

\Delta_i 是本轮预计新增的 token 数。这个估算要说明两个边界：第一，物理实现可能按层、按张量并行分片或按不同 state layout 计算 block；第二，共享前缀、滑动窗口和压缩 state 会让物理 block 数小于简单求和。公式用于做容量方向判断，真正的分配器必须以实际 block table 和 allocator 状态为准。

### 7.1 max_new_tokens 不是当前 cache 长度

请求通常带有最大输出长度，但 scheduler 不一定需要一开始就为全部 O_i 预留物理空间。过度预留会降低并发，完全不预留又可能在生成中途 OOM。常见做法是按当前逻辑长度分配 block，在每轮追加 token 时检查剩余预算，并在必要时进行抢占、排队、截断或拒绝。

prefix cache 命中还会改变 prefill 账。若 prompt 有 H_i 个 token 已由合法且版本一致的前缀状态覆盖，本次真正需要计算和新增的部分近似是：

~~~math
P_{i,\mathrm{new}}=\max(P_i-H_i,0).
~~~

H_i 不能只按字符串前缀计算，还要绑定模型 artifact、tokenizer/template、采样或状态版本、租户权限和 cache owner。不同用户的私密前缀不能因为文本相同就共享。cache 命中减少 prefill 工作，也不代表 decode 的 KV bytes、输出长度和公平性成本消失。

### 7.2 按 token 调度仍然要看工作类型

两个 1k-token 的请求并不一定等价：一个可能是首次 prefill，另一个可能是已经运行很久的 decode；一个可能命中 prefix cache，另一个需要完整计算；一个是交互请求，另一个是可延后的离线任务。因此 token budget 是必要的资源单位，不是完整的调度策略。

实用的调度记录至少应分开保存：

| 账本 | 代表量 | 影响 |
| --- | --- | --- |
| 新增 prefill | prompt 或 chunk token | 计算、TTFT |
| 活动请求 | sequence count | 调度开销、decode batch |
| 逻辑状态 | prompt + generated token | KV 增长 |
| 物理状态 | block、latent 或递归 state | 显存与迁移 |
| 预算债务 | 租户已用 token、等待时间 | 公平性与限额 |

按请求数限流仍有价值，例如保护连接和 CPU；但它不能替代 token、KV 和租户预算。

## 8. 优先级调度

生产系统通常有交互请求、离线批处理、内部评估和不同服务等级。严格优先级队列能降低高等级请求的等待，却可能让低等级请求永远排不到前面。更危险的是，优先级往往只看用户等级，不看 prompt 长度和 KV 成本，结果是一个高等级的超长请求仍能阻塞许多短请求。

一种可解释的动态排序分数可以写成：

~~~math
Q_i
=p_i+\alpha A_i+\beta U_i-\gamma D_{\mathrm{tenant}(i)}.
~~~

p_i 是业务优先级，A_i 是等待年龄，U_i 是距离截止时间的紧迫程度，D_tenant 是该租户相对于配额已经积累的服务债务，\alpha、\beta、\gamma 是权重。这个式子不是推荐某个固定算法，而是把“优先级、等待公平、截止时间和租户债务”放进同一张决策表。若请求已经等待很久，A_i 应逐渐提高；若租户近期消耗过多 token，D_tenant 应抑制继续插队。

常见策略有三类：

1. Strict priority：高等级队列有工作时优先服务，延迟简单可控，但低等级可能饥饿。
2. Priority with aging：等待越久优先级越高，能降低饥饿，但要防止大量低等级请求突然一起抢占。
3. Weighted fair sharing：按租户或队列权重分配 token 或 iteration 份额，更适合多租户长期公平，但实现和解释成本更高。

重试次数不应简单地增加优先级。否则一个失败请求会因为反复重试获得更多资源，形成正反馈。重试应由失败类型、剩余预算、幂等性和截止时间共同决定。

## 9. 多租户隔离

多租户场景下，不同团队或用户共享同一推理集群。隔离至少有四层：

1. 到达率：QPS、连接数和突发大小。
2. 计算：prompt/output token 配额、active sequence 和优先级。
3. 内存：上下文长度、KV block 上限、prefix cache namespace 和淘汰策略。
4. 数据与运营：鉴权、日志、计费、质量样本和取消权限。

只按请求数限流会失真。一个租户发出 100 个短请求，可能比另一个租户发出 1 个超长 RAG 请求便宜；反过来，短请求对 TTFT 的敏感性又可能更高。实际配额应同时记录请求数、输入 token、输出 token、峰值 KV bytes 和单位成功任务成本。

共享 prefix cache 时尤其要检查权限边界。相同的系统提示词可以在同一模型版本和同一安全范围内复用，但包含租户私有资料、用户身份或授权结果的前缀不能被另一个租户命中。cache key、日志脱敏和回收策略应在设计中明确，而不是等串数据事故后再补。

多租户系统还需要选择隔离位置：网关可以提前拒绝超额请求，scheduler 可以限制 token 和 sequence，allocator 可以限制物理 block，模型 worker 可以限制 kernel 并发。每一层的限制都要有清晰的错误码和 metrics，否则用户只会看到“偶尔很慢”。

## 10. Head-of-line blocking 与长短请求混跑

队头阻塞是调度中常见问题。如果一个长请求排在前面，后面的短请求可能被拖住；即使使用 continuous batching，长请求仍可能长期占用 KV block 和 decode 槽位。continuous batching 减少了整批等待，不等于消除了资源竞争。

可以从三层处理：

1. 请求层：限制最大上下文和输出，给短交互与长 RAG 使用不同队列或服务等级。
2. 调度层：使用 token budget、chunked prefill、aging 和 deadline-aware 排序，避免单个请求独占一轮。
3. 资源层：使用分页 cache、抢占/重算、prefill/decode 分离或独立的离线 worker。

每种办法都改变了别的指标。长度分队列提高可预测性，却降低了混合 batch 的机会；抢占释放显存，却要付出重算或 state 搬运成本；降低长请求优先级可以保护短请求，却可能让长任务超时。报告中应展示长请求和短请求各自的 P95/P99，而不是只报总体平均。

## 11. 调度指标

调度系统要持续监控完整链路，而不是只看 GPU 利用率。GPU 很忙但用户排队很久，或者 GPU 利用率不高但网络和工具等待很长，都可能是正常现象或严重故障，必须结合 trace 判断。

建议按下面的层次记录：

| 层次 | 指标 | 说明 |
| --- | --- | --- |
| 到达与队列 | arrival rate、queue length、queue time、drop/reject | 判断过载和等待来源 |
| 模型阶段 | prefill time、decode time、TTFT、TPOT/ITL | 区分输入处理和持续生成 |
| 尾延迟 | E2E、TTFT、TPOT 的 P50/P95/P99 | 观察用户体验和长尾 |
| 资源 | active sequences、batch token、KV watermark、OOM | 判断预算是否成为瓶颈 |
| 调度动作 | preemption、recompute、swap、cancel release | 判断优化是否付出代价 |
| 结果 | finish reason、截断率、错误率、goodput | 防止用失败请求换吞吐 |
| 租户 | token share、等待最大值、配额拒绝、成本 | 判断是否公平和可计费 |

对租户服务份额 x_1,\ldots,x_n，可以用 Gini 系数做粗略比较：

~~~math
G
=\frac{\sum_{i=1}^{n}\sum_{j=1}^{n}|x_i-x_j|}
{2n\sum_{i=1}^{n}x_i}.
~~~

G 越大表示份额越不均匀，但它不告诉我们某个租户是否本来就拥有更高权重，也不能替代 SLO 和优先级语义。因此应同时报告目标权重、实际 token share、最大等待时间和 SLO 成功率。

## 12. 常见调度策略的取舍

| 策略 | 作用 | 风险 |
| --- | --- | --- |
| FIFO | 规则简单，容易解释 | 长请求阻塞短请求，无法体现租户权重 |
| Strict priority | 保护高等级交互 SLO | 低等级饥饿，突发时尾延迟恶化 |
| Aging priority | 让长期等待请求逐步获得机会 | 需要选择老化速度，可能造成批次突变 |
| Token budget | 用真实计算和 cache 成本限制批次 | 要估计输入、输出和物理 block |
| Length-aware | 减少长短混跑和 padding 浪费 | 短请求可能长期占优 |
| Deadline-aware | 优先处理即将超时的请求 | 需要可靠的剩余时间估计 |
| Weighted fair sharing | 让租户长期获得可解释份额 | 调度状态、记账和实现都更复杂 |
| Tenant quota | 防止 noisy neighbor | 配额过低会降低整体利用率 |

没有一种策略在所有 workload 上都最好。线上选择应先写清楚服务目标，再用同一套 workload 对比吞吐、尾延迟、cache 水位、公平性和失败恢复；不能把某个 runtime 的策略名称当成性能保证。

## 13. 最小 Python demo：continuous batching 调度器

下面的 0 依赖 demo 模拟一个很小的 continuous batching scheduler。它展示请求到达、decode iteration、active sequence limit、prefill token budget、KV budget、完成释放和新请求加入。

```python
REQUESTS = [
    {"id": "short_a", "tenant": "paid", "arrival": 0, "prompt": 80, "out": 3, "priority": 2},
    {"id": "long_rag", "tenant": "free", "arrival": 0, "prompt": 1800, "out": 5, "priority": 1},
    {"id": "short_b", "tenant": "paid", "arrival": 1, "prompt": 120, "out": 2, "priority": 2},
    {"id": "tool_call", "tenant": "internal", "arrival": 2, "prompt": 300, "out": 3, "priority": 3},
]

LIMITS = {
    "max_active": 3,
    "prefill_token_budget": 2200,
    "kv_token_budget": 2500,
}


def sort_waiting(req):
    return (-req["priority"], req["prompt"], req["arrival"])


waiting = []
running = []
done = {}
trace = []

for time in range(20):
    for req in REQUESTS:
        if req["arrival"] == time:
            item = dict(req)
            item.update({"start": None, "first": None, "generated": 0, "end": None})
            waiting.append(item)

    decoded = []
    for req in list(running):
        req["generated"] += 1
        decoded.append(req["id"])
        if req["first"] is None:
            req["first"] = time
        if req["generated"] >= req["out"]:
            req["end"] = time
            done[req["id"]] = req
            running.remove(req)

    scheduled = []
    budget = LIMITS["prefill_token_budget"]
    waiting.sort(key=sort_waiting)
    for req in list(waiting):
        if len(running) >= LIMITS["max_active"]:
            break
        kv_if_added = sum(r["prompt"] + r["generated"] for r in running)
        kv_if_added += req["prompt"]
        if req["prompt"] <= budget and kv_if_added <= LIMITS["kv_token_budget"]:
            req["start"] = time
            running.append(req)
            waiting.remove(req)
            scheduled.append(req["id"])
            budget -= req["prompt"]

    kv_tokens = sum(req["prompt"] + req["generated"] for req in running)
    active_count = len(running)
    trace.append((time, decoded, scheduled, active_count, kv_tokens))

    if len(done) == len(REQUESTS):
        break


def metric(req):
    tpot = None
    if req["out"] > 1:
        tpot = round((req["end"] - req["first"]) / (req["out"] - 1), 2)
    return {
        "wait": req["start"] - req["arrival"],
        "ttft": req["first"] - req["arrival"],
        "tpot": tpot,
        "end": req["end"],
    }


summary = {req_id: metric(req) for req_id, req in sorted(done.items())}
tenant_tokens = {}
for req in done.values():
    tenant_tokens[req["tenant"]] = tenant_tokens.get(req["tenant"], 0) + req["out"]

print("trace_first4=", trace[:4])
print("summary=", summary)
print("tenant_output_tokens=", tenant_tokens)
print("max_active=", max(step[3] for step in trace))
print("max_kv_tokens=", max(step[4] for step in trace))
```

一组可能输出：

```text
trace_first4= [(0, [], ['short_a', 'long_rag'], 2, 1880), (1, ['short_a', 'long_rag'], ['short_b'], 3, 2002), (2, ['short_a', 'long_rag', 'short_b'], [], 3, 2005), (3, ['short_a', 'long_rag', 'short_b'], ['tool_call'], 2, 2103)]
summary= {'long_rag': {'wait': 0, 'ttft': 1, 'tpot': 1.0, 'end': 5}, 'short_a': {'wait': 0, 'ttft': 1, 'tpot': 1.0, 'end': 3}, 'short_b': {'wait': 0, 'ttft': 1, 'tpot': 1.0, 'end': 3}, 'tool_call': {'wait': 1, 'ttft': 2, 'tpot': 1.0, 'end': 6}}
tenant_output_tokens= {'paid': 5, 'free': 5, 'internal': 3}
max_active= 3
max_kv_tokens= 2105
```

这个 demo 要看三件事：

1. 新请求可以在旧请求尚未完成时加入 running batch，这就是 continuous batching 的核心。
2. `tool_call` 因为 active sequence limit 等待了 1 个 iteration，TTFT 变成 2。
3. `max_kv_tokens` 体现调度器不能只看请求数，还要看 prompt + generated token 占用。

这里的 tool_call 只是一个带有工具语义名称的普通 toy 请求，代码没有模拟工具等待、外部副作用或重试；真实系统应在 tool wait 状态释放 decode 槽位，并使用幂等键保护工具动作。demo 每轮重新计算可接收的 prefill token budget，也没有实现租户加权公平、抢占和 backpressure，读者可以在这些位置继续扩展。trace 中的 active_count 是本轮完成释放和新请求加入之后的活动数，decoded 列表则记录本轮曾经执行过 decode 的请求，两者有意分开。

## 14. 抢占、取消与重试的正确性

只按当前请求的 token 数排序并不能自动得到好的调度器。长请求可能长期占用 KV block，短请求可能被反复插队；工具调用失败后，如果网关、Agent runtime 和模型 worker 各自重试，又会把同一业务动作复制成重试风暴。scheduler 需要同时看剩余 token、已等待时间、优先级、截止时间、租户服务债务、KV 占用和副作用状态。

一个可解释的排序分数可以写成：

~~~math
Q_i
=p_i+\alpha A_i+\beta U_i-\gamma D_{\mathrm{tenant}(i)}.
~~~

p_i 是基础优先级，A_i 是等待年龄，U_i 是截止时间紧迫度，D_tenant 是租户已经超出目标份额的服务债务。剩余 token 数通常更适合作为资源估计和同分时的 tie-break，而不是简单地让长请求永远低优先级。具体权重必须用长短混合、突发和多租户 workload 回放。

### 14.1 抢占必须保存完整的状态契约

抢占不是把请求从 running 列表删除。被抢占请求至少要保留：

1. 已消费的 token position 和 attention position offset。
2. KV block table、物理 block 所属设备和逻辑长度。
3. 采样随机状态、解码参数、stop 状态和已发送事件。
4. 模型版本、tokenizer/template 和 cache layout 版本。
5. 工具事务状态、幂等键、租户预算和取消信号。

重算会释放 cache，但恢复时需要从一致的 token 前缀重新 prefill；swap/offload 可以保留更多状态，却要付出 device-to-device 或 host transfer 延迟，还要处理校验和、版本与容量。两条路径都不能把一个 runtime 的 state 直接交给 layout 不兼容的另一个 worker。

抢占策略应在安全的 iteration 或 chunk 边界生效。若 token 已经发送给客户端，恢复后不能再次发送同一个 token；若工具已经产生副作用，恢复模型文本也不能自动再次执行工具。需要在 trace 中记录 preempt、recompute、swap、resume 和 duplicate-token 事件，才能判断抢占到底减少了 OOM 还是制造了隐蔽错误。

### 14.2 取消和重试要有明确的边界

客户端断开、服务超时、模型错误、工具超时和网络重试不是同一种失败。建议至少分为：

1. 可以安全重试的瞬时资源错误，例如 worker 暂时不可用。
2. 需要重新构造请求的协议错误，例如 tokenizer/template/schema 不一致。
3. 不应自动重试的副作用错误，例如写数据库、扣款或发送外部消息。

模型生成重试不等于工具执行可以重试。工具调用应使用 idempotency key、事务状态或补偿动作，重试预算也要由一个明确的 owner 管理：

~~~math
N_{\mathrm{retry}}\le N_{\max},\qquad
C_{\mathrm{request}}\le C_{\max},\qquad
T_{\mathrm{wall}}\le T_{\max}.
~~~

可以用重试放大倍数观察风暴：

~~~math
A_{\mathrm{retry}}
=\frac{N_{\mathrm{all\ attempts}}}{N_{\mathrm{original\ requests}}}.
~~~

A_retry 大于 1 并不一定错误，但它必须能按错误类型、租户和时间窗口解释。压测除了吞吐、TTFT、TPOT 和 P99，还应记录抢占恢复成功率、重复 token 率、重试放大倍数、取消后的 KV 回收时间和副作用工具的重复执行数。一个平均吞吐更高但长任务永远得不到服务的策略，不是合格的生产调度器。

## 15. 一个高峰期多租户调度故障的分析

考虑一个共享推理集群。付费交互租户需要短聊天和代码补全，内部分析租户提交长 RAG，离线租户运行批量摘要。平时三类请求都能完成，但在业务高峰期出现了三个现象：短聊天 TTFT P99 从 400 ms 上升到 2.8 s，长 RAG 超时率上升，GPU output TPS 却提高了 18%。如果只看吞吐，调度器似乎变好了；把请求 trace、KV 水位和 finish reason 对齐后，才会发现它正在用用户体验和失败请求换吞吐。

第一步是分解工作类型。短聊天的输入通常小于 512 token，输出小于 256 token；长 RAG 的输入可能超过 8k token，输出约 512 token；离线摘要可以等待更长的 batch，但不应占用交互请求的尾延迟预算。调度器需要同时记录三类账：本轮新增 prefill token、active sequence 数和物理 KV block。仅按请求数设置 `max_batch=32`，无法表达一个 32k token 请求与一个 128 token 请求的差异。

第二步检查队列和 iteration trace。假设调度器使用 5 ms 等待窗口，并在每轮优先填满 prefill token budget。长 RAG 到达后，若一次性把 8k token 全部送入 prefill，正在 decode 的短请求可能在一个或多个 iteration 中没有机会产生 token；短请求的 TTFT 增长并不是模型变慢，而是长 prefill 挤占了 decode 配额。将长 prompt 切成 chunk 后，若 `T_chunk` 过大，问题仍会出现；若过小，又会增加 kernel launch 和状态管理开销。

可以把每一轮的选择写成约束，而不是只按优先级排序。对候选集合 `B_k`，令 `P_i,k` 为本轮新增 prompt token，`D_i,k` 为 decode token，`K_after` 为加入后的物理状态需求，则至少要满足：

~~~math
\sum_{i\in B_k}P_{i,k}\le T_{\mathrm{prefill,budget}},
\qquad
\sum_{i\in B_k}D_{i,k}\le T_{\mathrm{decode,budget}},
\qquad
K_{\mathrm{after}}\le K_{\mathrm{budget}}.
~~~

实际系统还要保留取消、抢占和新请求的余量。`T_prefill,budget` 与 `T_decode,budget` 不必固定相等：交互高峰期可以降低单轮 prefill 配额，保护正在流式输出的请求；离线窗口则可以提高 prefill 配额，提高总吞吐。预算变化必须在 trace 中记录，否则同一个 runtime 的两个结果无法公平比较。

第三步处理公平性。若严格按付费优先级，内部长任务可能永远得不到服务；若严格 FIFO，长 RAG 会阻塞短交互；若只按 prompt 长度，短任务会持续插队。可以用带老化和租户债务的排序分数：

~~~math
Q_i=p_i+\alpha A_i+\beta U_i-\gamma D_{\mathrm{tenant}(i)}-eta C_i,
~~~

其中 `p_i` 是业务优先级，`A_i` 是等待年龄，`U_i` 是截止时间紧迫度，`D_tenant` 是租户相对目标份额的服务债务，`C_i` 是预计的本轮资源消耗。这个式子不是必须照搬的算法，而是迫使系统同时表达优先级、等待、公平和成本。长请求不应因为贵就永久饿死，等待时间应逐步提高其获得服务的机会。

第四步决定是否分队列。短交互、长 RAG 和离线摘要可以拥有不同的 prefill 配额和优先级；短队列保护 TTFT，长队列获得明确但较低的吞吐份额，离线队列只在剩余容量中运行。分队列并非免费：它可能让某个池空闲而另一个池排队，也可能降低共享 batch 的饱满度。因此要同时观察每个队列的 queue time、goodput、token share、KV watermark 和 SLO 达成率。

第五步处理重试和副作用。高峰期超时会让客户端重试，重试增加到达率，形成 retry storm。纯文本生成可以在明确预算内重试，但工具写入、数据库提交和外部消息发送必须携带幂等键和事务状态；调度器不能把一次“工具等待超时”当成可无条件重新执行的普通请求。应记录：

~~~math
A_{\mathrm{retry}}
=\frac{N_{\mathrm{all\ attempts}}}{N_{\mathrm{original\ requests}}},
\qquad
N_{\mathrm{retry}}\le N_{\max}.
~~~

如果吞吐提高同时 `A_retry`、length finish reason 和工具重复执行数也提高，说明系统可能只是把失败转化成了更多计算。调度器的 goodput 应只统计在 SLO 内完成且任务结果有效的请求，而不是所有生成过 token 的请求。

最后做反事实压测：保持模型、GPU、输入输出长度和流量不变，只改变等待窗口、chunk size、prefill/decode 配额、队列分流和公平策略。每次实验都比较短请求与长请求的 P95/P99、总 output TPS、goodput、KV 峰值、抢占/重算率、取消回收时间、租户 token share 和 retry amplification。如果只改变一个 batch 参数却同时改变了最大输出或超时规则，结果就无法归因。

这个案例最终可能得到“长短请求分池 + chunked prefill + aging fair share”的组合，也可能发现 prefill/decode 分离的 state 传输成本过高而继续使用合并池。选择不由 batching 名称决定，而由请求状态、token 和 cache 账本、SLO、公平性、失败语义以及真实压测共同决定。

## 16. 资料与证据边界

1. [Orca: A Distributed Serving System for Transformer-Based Generative Models](https://www.usenix.org/conference/osdi22/presentation/yu)：iteration-level scheduling 和生成式模型 serving 的原始研究资料；论文实验条件不能直接替代当前硬件压测。
2. [Hugging Face: Optimizing LLMs for Speed and Memory](https://huggingface.co/docs/transformers/en/llm_tutorial_optimization)：Transformers 生态对推理优化、cache 和 serving 相关概念的官方说明；它不是某个专用 runtime 的容量保证。
3. [Text Generation Inference Documentation](https://huggingface.co/docs/text-generation-inference/en/index)：核对 TGI 当前文档和维护状态，存量部署与新项目的判断应分开。
4. [vLLM Engine Arguments](https://docs.vllm.ai/en/stable/configuration/engine_args.html)：核对当前版本的调度、并发、token budget 和资源相关参数；参数名称和默认值随版本变化。
5. [vLLM Metrics](https://docs.vllm.ai/en/stable/usage/metrics/)：核对 serving metrics 的公开口径；实际业务仍需补充租户、工具和 SLO 指标。
6. [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180)：理解分页式 KV Cache 与 serving 资源管理的研究背景。
7. [TensorRT-LLM Documentation](https://nvidia.github.io/TensorRT-LLM/) 和 [Build Workflow](https://nvidia.github.io/TensorRT-LLM/architecture/workflow.html)：核对 NVIDIA runtime 的构建、执行和版本边界。
8. [TensorRT-LLM Attention](https://nvidia.github.io/TensorRT-LLM/advanced/gpt-attention.html)：理解 MHA、MQA、GQA 和相关 attention 实现的官方说明；不能据此推断目标模型的端到端性能。
9. [SGLang Documentation](https://docs.sglang.ai/)：核对结构化程序、prefix/radix 类缓存和 serving 配置的当前公开能力。

资料的使用层次要分开：论文用于解释机制和实验假设，官方文档用于确认当前接口与维护状态，源码用于定位实现路径，项目实测用于决定目标 workload 的选择。一个文档页面写着支持 continuous batching，只能证明存在某条实现路径；是否满足目标模型的协议、质量、P99、公平性和单位成功成本，仍需回放和压测。

## 17. 本章小结

本章核心结论：

1. Batching 是提升吞吐的基础，但会带来排队延迟。
2. Static batching 适合离线任务，在线服务中容易浪费。
3. Dynamic batching 用等待窗口换更高吞吐。
4. Continuous batching 是 LLM serving 的核心优化。
5. Prefill 和 decode 资源特征不同，调度策略也不同。
6. LLM 调度要看 token budget 和 KV Cache，而不是只看请求数。
7. 优先级和多租户隔离是生产系统必须考虑的问题。
8. 调度优化要同时看吞吐、TTFT、TPOT、P95/P99 和公平性。
