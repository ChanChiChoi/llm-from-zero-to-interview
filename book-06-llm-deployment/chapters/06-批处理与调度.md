# 第六章：批处理与调度

在线服务中的 GPU 很少真正“空闲”或“满载”这么简单。一个长 RAG 请求刚开始做 prefill 时，需要大量矩阵计算；另一个已经生成了几百个 token 的请求，每一轮只需要读写自己的 KV Cache；第三个请求刚刚到达，只想尽快看到首个 token。如果把这三个请求当成同一种工作，系统要么让 GPU 等待，要么让某一类请求长期牺牲延迟。

批处理解决的是“哪些请求一起计算”，调度解决的是“什么时候让哪些请求消耗多少资源”。这两个词经常一起出现，却不是同一个问题：batch 是某一轮执行的工作集合，scheduler 还要决定排队、是否接收、优先级、预算、抢占、取消和租户公平性。一个批次很大，不代表调度是好的；它可能只是把等待时间和显存压力推给了用户。

初学者可以先记住一个画面：传统模型通常把一批样本送进一次 forward，LLM 却要让每个请求经历输入处理和逐 token 生成两个阶段，而且每个请求的结束时间都不同。因此，高性能服务会在每轮迭代重新安排活动请求。专家需要进一步追问：本轮消耗的是 prompt token 预算还是 decode token 预算？新请求是否会挤占已有请求的 TPOT？KV block 是否足够？高优先级策略是否造成低优先级饥饿？这些问题才决定一个 scheduler 是否真的适合生产。

本章从一个请求的生命周期开始，依次建立 static batching、dynamic batching 和 continuous batching 的差异，再讨论 token/KV 预算、prefill 与 decode 的混合调度、队列论、公平性、多租户、抢占和过载保护。代码 demo 只模拟调度决策，不模拟真实 GPU kernel；它用于验证账本和状态转换，不能替代目标模型上的压测。

## 本章资料边界

本章用 Orca、FastServe、Sarathi-Serve、DistServe 等原始论文解释迭代调度、抢占、chunked prefill 与阶段分离的不同问题，再用 vLLM v0.32.0 与访问日的 SGLang 官方参数文档核对预算和优先级接口。2026 年的 LAPS、P-PAS、PPD 等预印本用于补充长短 prefill 与调度压力变化的研究候选。论文说明作者提出的机制及其评测条件，官方文档说明指定版本公开的参数语义；二者都不能单独证明目标模型、目标硬件和真实 workload 的性能。文末列出资料入口，并把版本敏感的参数和未测结论明确标成需在目标配置复核。

## 1. 先建立调度问题的坐标系

### 1.1 LLM batching 为什么比普通模型复杂

普通分类模型常见的路径是“收集样本、补齐形状、执行一次 forward、返回结果”。LLM 的在线请求至少包含两个阶段：

1. prefill：把 prompt 的 token 一次或分块送入模型，建立后续生成所需的状态。
2. decode：每轮根据已有状态生成下一个 token，直到 EOS、stop、长度上限或取消。

输入长度和输出长度都不固定。请求 A 可能有 128 个 prompt token、只生成 16 个 token；请求 B 可能带 32k token 的检索上下文、生成 2k 个 token。A 的首 token 可能很快，但 B 会长时间占用 prefill 计算和 KV Cache。decode 期间，虽然每轮新计算的 token 很少，批次却要反复访问所有活动请求的状态。

对请求 r_i，记：

- P_i：已经经过 tokenizer 的 prompt token 数；
- O_i：最终输出 token 数；
- D_i(k)：第 k 轮开始前已经生成的 token 数；
- S_i：它是否占用一个 active sequence 槽位；
- K_i(k)：该请求在第 k 轮占用的 KV token 或物理 cache block。

在最粗的账本里，逻辑上下文长度是：

~~~math
L_i(k)=P_i+D_i(k).
~~~

这个式子不是完整的显存模型。不同 attention 结构、张量并行、量化和分页方式会改变每个 token 的实际字节数；它的用途是提醒我们：调度成本随着 token 和状态增长，而不是随着请求数等比例增长。

### 1.2 批次大小有三个不同含义

“batch size”在讨论中经常造成误会，至少要拆成三种量：

1. sequence count：当前同时活动的请求数。
2. prefill token count：本轮新处理的 prompt token 数。
3. decode token count：本轮为活动请求生成的 token 数，通常接近活动请求数，但在 speculative decoding 或特殊 kernel 中可能不同。

一个 32-request 的 batch 可能包含 32 个很短的 prompt，也可能包含 32 个很长的 prompt；一个只有 8 个活动请求的 decode batch 也可能占用大量 KV Cache。只报 sequence count，无法解释显存和延迟；只报 tokens/s，也无法解释请求是否在队列里等待。

## 2. Batching 的目标不是 batch 越大越好

批处理让一次 kernel 调用承担更多工作，通常有利于矩阵乘法的利用率和整体吞吐；但它也会增加等待、显存占用和尾延迟。在线服务应同时报告吞吐和用户实际看到的延迟。

对压测窗口内的 N 个完成请求，可以定义输出吞吐：

~~~math
\mathrm{TPS}_{\mathrm{out}}
=\frac{\sum_{i=1}^{N}O_i}{T_{\mathrm{wall}}}.
~~~

若只有满足业务 SLO 的请求才算交付，则更接近业务价值的 goodput 是：

~~~math
\mathrm{Goodput}
=\frac{N_{\mathrm{SLO}}}{T_{\mathrm{wall}}}.
~~~

其中 N_SLO 是在规定时间内完成、且结果没有触发业务失败条件的请求数。

对请求 i，排队等待和首 token 延迟分别为：

~~~math
W_i=t_{\mathrm{start},i}-t_{\mathrm{arrive},i},
\qquad
\mathrm{TTFT}_i=t_{\mathrm{first},i}-t_{\mathrm{arrive},i}.
~~~

当 O_i>1 时，decode 阶段的平均 token 间隔可近似写成：

~~~math
\mathrm{TPOT}_i
=\frac{t_{\mathrm{end},i}-t_{\mathrm{first},i}}{O_i-1}.
~~~

若只输出一个 token，TPOT 没有足够的间隔样本，应记为 N/A；不能把 E2E latency 误报成 TPOT。还要区分 TPOT/ITL 的项目口径：有的系统把首 token 到末 token 的平均间隔称 TPOT，有的系统按相邻 token 计算 P50/P99 ITL。报告必须写清分母和时间端点。

调度目标可以表达为一个带约束的优化问题：

~~~math
\max\ \mathrm{Goodput}
\quad\mathrm{s.t.}\quad
P99(\mathrm{TTFT})\le \tau_{\mathrm{first}},
\quad
P99(\mathrm{TPOT})\le \tau_{\mathrm{token}},
\quad
K_{\mathrm{peak}}\le K_{\mathrm{budget}}.
~~~

这不是要求线上系统求解一个精确的全局最优问题，而是提供判断框架。调大 batch 只有在吞吐收益没有违反 TTFT、TPOT、显存和公平性约束时才有意义。平均延迟很好看但 P99 超标，或者 output TPS 很高但大量请求被截断，都不能算作成功的调度优化。

用一组假设数据把“吞吐更高”与“服务更好”分开。某次 60 秒回放完成 100 个请求，共生成 9,500 个 token，其中 95 个请求同时满足 TTFT、TPOT 和业务有效性门槛，则 output TPS 为 $9{,}500/60\approx158.3$ token/s，goodput 为 $95/60\approx1.58$ 个合格请求/s。另一配置生成 11,000 个 token，却只有 70 个合格请求，output TPS 升到 $183.3$ token/s，goodput 反而降到 $1.17$ 个请求/s。两组数据是教学输入，不是某个引擎的实测结果；它说明调度的目标要绑定 SLO 和任务有效性，不能把 token 计数直接当成用户价值。

等待窗口也可以沿请求时间线手算。假设三个请求分别在 0、1、8 ms 到达，dynamic batch 固定等 10 ms 后发车，则三者仅排队等待就分别是 10、9、2 ms。这个窗口聚合了三个请求，但最早到达者的 TTFT 至少被多加 10 ms；若窗口内只有一个请求，聚合没有形成，等待却照样发生。因而窗口参数必须放回到达 trace 与 TTFT 预算中评估：看均值会掩盖最早请求的代价，单独看 batch utilization 又会忽略未赶上当前窗口的请求。

## 3. Static、dynamic 与 continuous batching

### 3.1 Static batching：简单但容易被最长请求绑架

Static batching 先固定一组请求，再让这组请求一起执行，直到整组结束。它适合离线推理、形状稳定的任务和容易预估的批量作业。

假设一个 batch 有 B 个输入，长度分别为 l_1,\ldots,l_B，使用 padding 对齐到最长长度 l_{\max}，仅从输入侧看，补齐 token 数是：

~~~math
N_{\mathrm{pad}}
=B\,l_{\max}-\sum_{j=1}^{B}l_j.
~~~

补齐 token 不一定都产生同样的实际 kernel 成本，因为不同 runtime 可能使用 packed input 或专门的变长 kernel；这个式子是解释浪费来源的上界式账本。输出长度差异还会带来另一种浪费：已经完成的短请求仍占着批次位置，或者运行代码不得不以 EOS/padding 继续维持统一步数。

初学者可以把它想成一辆必须等所有乘客到终点才回站的班车。专家还要检查两个细节：输入 padding 是否真的进入计算图，以及完成请求的 cache block 是否及时释放。只看到“batch=32”不能判断 static batching 的实际浪费。

例如一批四个 prompt 的长度是 32、64、64、256 token。若使用需要补齐到最长长度的 dense 张量，批次形状会容纳 $4\times256=1{,}024$ 个位置；有效输入只有 $32+64+64+256=416$ 个位置，补齐部分为 $1{,}024-416=608$，即批次位置中的 $608/1{,}024=59.375\%$。这个比例只是 dense-padding 账本：packed/ragged kernel 可以避免把所有补齐位置都算成同等工作，但它仍要处理长度不齐、掩码和不同结束时间。生成阶段若四个请求分别再输出 4、8、32、128 个 token，按最长输出保持整组执行时，前三个请求在结束后不再贡献有效 token，却仍受固定批次生命周期约束。该例把“padding 浪费”和“等待最长请求”拆成两种成本，实际测量时应分别看 prompt 计算量和完成后的空槽时间。

### 3.2 Dynamic batching：用一个等待窗口换聚合收益

Dynamic batching 在短时间窗口内收集新到达请求，然后组成一次或少数几次 batch。设调度时刻为 t、最大等待窗口为 \Delta，则候选请求可以抽象为：

~~~math
\mathcal{C}(t)
=\{r_i\mid 0\le t-t_{\mathrm{arrive},i}\le\Delta\}.
~~~

候选集合仍要满足序列数、prompt token 和显存约束：

~~~math
|\mathcal{B}(t)|\le B_{\max},\qquad
\sum_{r_i\in\mathcal{B}(t)}P_i\le T_{\mathrm{prefill}},\qquad
K_{\mathrm{after}}\le K_{\mathrm{budget}}.
~~~

\Delta 越大，通常越容易形成更饱满的 batch，但每个请求的 TTFT 至少会多出一段等待；在低流量时，等待窗口可能直接成为首 token 延迟的主导项。高流量时，窗口不一定是主要问题，真正的瓶颈可能是 prefill 计算、KV Cache 或下游网络。

Dynamic batching 的关键是“何时停止等待”。固定 5ms 只是实现选择，不是普适答案。更稳妥的做法是把等待时间和队列长度、剩余 SLO、当前 token budget 以及服务优先级一起记录，再用目标 workload 做实验。动态 batching 也不自动消除 padding 或长请求拖慢短请求的问题。

把上一节的 0、1、8 ms 到达再加上 prompt 长度 64、128、512 token，10 ms 发车时总输入为 704 token。若本轮 prefill 预算是 600，三者即使都赶上窗口也不能完整放进同一轮；scheduler 还得决定是先服务 64+128 的短 prompt（合计 192），还是给 512-token 请求分块并保留其他请求的份额。若只报告“dynamic batch 收到了 3 个请求”，既看不出是否触碰 token 上限，也看不出谁被推迟。等待窗口、批次形成和每轮计算预算是三个相关但不同的控制量，调参时应至少记录候选数、实际入批数、累计 prompt token、等待毫秒和被推迟原因。

### 3.3 Continuous batching：在迭代边界重排活动集合

LLM decode 每轮只推进一个或一小组 token，因此 scheduler 可以在迭代边界移除已经结束的请求，并把等待队列里的请求加入下一轮。对只讨论 decode 的简化模型，第 k 轮的活动集合为：

~~~math
\mathcal{B}_k
=\{r_i\mid \mathrm{state}_i=\mathrm{decode},
\ D_i(k)<O_i^{\max}\}.
~~~

若 \mathrm{Done}_k 是本轮结束的请求，\mathrm{New}_k 是通过资源检查并加入的请求，则：

~~~math
\mathcal{B}_{k+1}
=(\mathcal{B}_k-\mathrm{Done}_k)\cup\mathrm{New}_k.
~~~

真实 scheduler 往往还要把新请求的 prefill、chunked prefill、decode 和可能的重算放进同一轮预算。因此上式是说明“可增量替换”的教学抽象，不应理解为任何框架的源码算法。

一个典型 iteration 的顺序是：

1. 读取活动请求的状态，决定本轮 decode 或 prefill 工作。
2. 执行模型计算并产生 token。
3. 检查 EOS、stop、长度上限、取消和错误。
4. 释放完成请求的 sequence 槽位与 cache block。
5. 在 token、序列数和显存预算内从等待队列加入请求。
6. 记录本轮的排队、计算、cache 和输出事件。

Continuous batching 的收益来自减少“等整组结束”的空洞；它的代价是 scheduler、KV Cache、取消和流式事件都必须在迭代级别保持一致。加入新请求也不是免费操作：它可能带来新的 prefill 峰值，挤占 decode 请求的 kernel 时间，使已有请求的 TPOT 变差。

### 3.4 Chunked prefill：不要让一个长 prompt 独占一轮

如果一个 prompt 有几十万 token，直接把完整 prefill 插入在线 decode 轮次，可能让正在流式输出的请求长时间没有下一个 token。Chunked prefill 把 prompt 切成多个片段，在多个 iteration 中处理：

~~~math
P_i=\sum_{c=1}^{C_i}P_{i,c},
\qquad
P_{i,c}\le T_{\mathrm{chunk}}.
~~~

较大的 T_{\mathrm{chunk}} 有利于减少调度开销和提高 prefill 的计算效率，但会让 decode 请求等待更久；较小的 T_{\mathrm{chunk}} 有利于交错服务，却可能增加 kernel launch、状态管理和通信开销。chunk 边界还必须正确维护 position、attention mask、KV block table 和取消状态。

因此，“支持 continuous batching”不等于“长上下文在线体验一定好”。需要单独测长 prompt 的 TTFT、chunk 间隔、decode 请求的 TPOT P99、cache 峰值和取消后的回收时间。

Continuous batching 的收益来自减少“等整组结束”的空洞；它的代价是 scheduler、KV Cache、取消和流式事件都必须在迭代级别保持一致。加入新请求也不是免费操作：它可能带来新的 prefill 峰值，挤占 decode 请求的 kernel 时间，使已有请求的 TPOT 变差。

沿一条短 trace 看清动态成员变化：第 0 轮活动集为 A、B；第 1 轮 A 达到输出上限并释放槽位，等待中的 C 通过 token 与 KV 检查后加入；第 2 轮活动集变为 B、C，而不是继续保留已结束的 A。若每个 decode 请求每轮产出一个 token，A 在第 1 轮产生的最后一个 token 仍要记在其输出账本里，结束后才释放其 sequence slot 和不再共享的 KV block。该轨迹解释了 continuous batching 的成员更新，却没有证明 C 的 prefill 不会让 B 的下一个 token 变慢；因此延迟评估仍要把“请求能否加入”和“加入后已有请求的 TPOT 变化”同时记录。

## 4. 请求生命周期：队列不是一个抽象盒子

调度器要做出正确决定，必须知道请求现在处于哪个状态。一个简化的生命周期可以写成：

~~~text
received
  -> tokenize and validate
  -> waiting
  -> prefill
  -> decoding
  -> completed / cancelled / timeout / error
  -> release state and record metrics
~~~

工具调用或外部检索会在 decoding 与下一次模型执行之间插入 tool wait。此时请求仍然是业务上的活动任务，但不应继续占用 GPU decode 槽位；如果系统把 tool wait 误记成 decoding，就会虚增 active sequence，过早拒绝新请求。

每个状态对应不同的资源和计时含义：

1. received：连接、鉴权和请求体可能已经占用网关资源，但还没有消耗模型计算。
2. waiting：请求在本地队列中等待，主要消耗队列容量和少量元数据。
3. prefill：需要为 prompt 计算并分配状态，通常直接影响 TTFT。
4. decoding：每轮生成 token，持续读取和扩展 KV Cache，通常直接影响 TPOT。
5. cancelled：客户端不再需要结果，scheduler 应在下一个安全迭代尽快停止计算并释放状态。
6. completed/error：写入 finish reason、usage 和 trace，确认所有 cache block、流式连接和工具事务都已收束。

对每个请求同时记录 t_arrive、t_queue_end、t_prefill_end、t_first、t_end，才能把端到端延迟拆开：

~~~math
T_{\mathrm{E2E}}
=T_{\mathrm{queue}}
+T_{\mathrm{prefill}}
+T_{\mathrm{decode}}
+T_{\mathrm{tool}}
+T_{\mathrm{network}}.
~~~

这里的加法是观测口径，不是说所有阶段在系统中永远严格串行。例如网络发送可能与 decode 重叠，工具等待可能与其他请求的 GPU 计算并行。拆分的价值在于定位问题：队列变长要看过载或公平性，prefill 变慢要看输入长度和计算 kernel，decode 变慢要看活动请求数和 cache，network 变慢则不应盲目调 batch。

可以给同一个请求做一份纯示例时间账本：它在 0 ms 到达，20 ms 离开等待队列，prefill 结束于 95 ms，首 token 在 100 ms 送达，末 token 在 500 ms 送达，工具等待累计 120 ms，客户端发送/接收相关网络区间估计 15 ms。按这些假设值，队列为 20 ms，prefill 到首 token 的阶段（含采样/首 token 交付）为 80 ms，首末输出间隔覆盖的 decode 观测为 400 ms，工具为 120 ms；若简单把五段相加成 635 ms，会与 500 ms 的端到端墙钟时间冲突，说明这些字段有重叠或边界不同，不能不经 trace 定义就相加。更可靠的做法是让每段记录明确的起止时间，并用时间线检查是否串行；若阶段可重叠，就报告关键路径区间或重叠时长，而不是把所有 span duration 相加。

工具等待是状态归属的典型例子。请求 A 在 t=100 ms 产生工具调用并等待 800 ms，期间模型不需要为它生成 token；若运行队列仍把 A 计为 GPU decode 活动请求，`active sequences` 会比实际多 1，并可能让服务端错误地认为槽位已满。反过来，若业务层把 A 从 GPU 槽位移出，却没有保留 tool transaction、取消令牌和会话状态，工具返回时也可能无法安全续跑。请求的“业务仍在进行”与“当前占用模型执行槽位”必须用不同状态表达。

### 4.1 Little 定律给出的容量直觉

在稳定、长期平均的队列中，Little 定律把平均在途请求数、到达率和平均停留时间联系起来：

~~~math
L=\lambda W.
~~~

L 是平均在途请求数，\lambda 是平均到达率，W 是请求从进入该系统到离开的平均时间。若只讨论等待队列，就应把 L 和 W 都定义为等待队列的量；若把 prefill、decode 和 tool wait 全部算进去，则三者必须使用同一边界。

Little 定律只约束平均量，本身不能推出某个系统的等待时间曲线。为了看清“接近容量时延迟为何会陡增”，可以暂时用单服务台 M/M/1 队列作直觉例子：请求按泊松过程到达，服务时间服从指数分布，服务率为 \mu，且到达率 \lambda<\mu。该模型的平均系统停留时间是：

~~~math
W=\frac{1}{\mu-\lambda}.
~~~

若服务率为 10 req/s，到达率 5 req/s 时平均停留时间为 0.2 s；按 Little 定律，系统平均在途请求数为 $L=5\times0.2=1$。到达率升到 9 req/s 时平均停留时间为 1 s，在途数为 $L=9\times1=9$。这个 5 倍增长不是 LLM 服务的容量预测：真实请求长短不一，prefill、decode、KV、batch 和 GPU 并行也不符合单服务台假设。它只说明当负载逼近服务能力时，小幅增加到达率就可能大幅推高延迟。线上仍需用目标请求 trace 测量，并设置有限队列和明确的 backpressure，例如返回可重试错误、降低低优先级流量、拒绝超过上下文预算的请求，或把离线任务移到异步队列。

无限增长的等待队列看起来没有丢请求，实际上会把故障变成更长的 TTFT、更多超时和客户端重试。重试又会增加到达率，形成 retry storm。服务端和客户端要共同设置超时、Retry-After、指数退避、随机抖动和幂等键，不能只在 scheduler 内部“再等一会儿”。

## 5. 请求队列

请求队列不是一个只保存字符串的 FIFO 容器，而是 scheduler 的决策输入。至少要保存 request id、tokenized prompt 的长度、最大输出长度、到达时间、截止时间、租户、优先级、是否流式、是否允许抢占、取消状态和当前 cache 账本。若请求包含工具调用，还要保存工具事务是否已经产生副作用；一个已经写入数据库的工具动作，不能像纯文本生成一样随意重试。

最简单的 FIFO 适合负载均匀、没有租户差异的场景。真实服务通常会先做几项硬约束检查，再在剩余候选中排序：

1. 请求是否超过上下文、输出、租户并发和预算上限。
2. 预计加入后是否超过本轮 prefill token、active sequence 和 KV Cache 预算。
3. 请求距离超时还有多久，是否有更高优先级的交互请求。
4. 该租户近期已经消耗多少 token，是否需要让其他租户获得服务机会。
5. 请求是否可以被取消、分块、抢占或转移到异步队列。

这里的“先检查资源，再排序”不是绝对的框架实现顺序，但它揭示了一个常见错误：如果只按优先级挑选，挑中的长请求可能根本放不进显存；如果只按 prompt 短挑选，又可能让长请求永久得不到服务。调度记录应保留候选、落选原因和最终选择，才能解释 P99 的变化。

### 5.1 队头阻塞与分队列

Head-of-line blocking 指队列最前面的请求阻止后面的请求前进。LLM 中它特别明显：一个长 prompt 可能独占 prefill 预算，一个长输出可能长期占用活动槽位。常见应对方式是按输入长度、业务类型或服务等级拆分队列，再在队列之间分配 token 预算。

分队列不是免费优化。短请求队列可能获得更低 TTFT，却让长请求队列积压；长度估计不准时，短队列也会混入昂贵请求；过多队列会降低 batch 形成机会。评估时要同时看每个队列的排队时间、SLO 达成率和 token 份额，不能只看总体平均值。

例如每秒到达 8 个短请求（平均 100 prompt token）和 1 个长请求（8,000 prompt token），按请求数看长请求只占到达量的 $1/9$；按首次 prefill token 看，它占 $8{,}000/(8{,}000+800)\approx90.9\%$。如果服务只用请求 FIFO 和 `queue_length`，就会误以为长请求不是主要负载；如果把长度队列拆开，又必须给长队列一个最低份额或等待老化规则，否则短队列持续到达时它仍可能饥饿。队列的分类键应尽量来自可观测字段（prompt token、任务类型、deadline、租户），且每个类都要有独立的到达、服务、排队和完成计数，才能分辨“分类更准确”与“把慢请求挪到看不见的队列”。

## 6. Prefill / Decode 分离

Prefill 和 decode 常有不同的资源画像，但“prefill 一定计算密集、decode 一定内存密集”只能作为起点，不能作为测量结论。模型规模、序列长度、batch、kernel、硬件和并行方式都会改变实际瓶颈。

Prefill 一般一次处理较多 prompt token，矩阵乘法的并行度更高，prompt 越长越容易占据较长的计算时间，所以更直接影响 TTFT。Decode 每轮只追加一个 token，却要读取每个活动序列的历史状态，并反复执行许多轮，因此更容易受到 KV Cache 带宽、活动序列数和调度开销影响，最终表现为 TPOT 和 E2E 变差。

如果把二者放在同一个 GPU 上，scheduler 需要决定本轮给 prefill 多少 token，给 decode 留多少计算时间。prefill 配额过大，已有流式请求会出现 token 间隔尖峰；decode 配额过大，新请求 TTFT 会变长。chunked prefill 正是把这个选择变成可控制的交错单位。

如果采用 prefill/decode disaggregation，可以把两类工作放在不同 GPU 池甚至不同节点。这样做有机会分别扩容，也能减少长 prefill 对 decode 的直接干扰；代价是需要传输或重建 KV/latent state，增加网络带宽、路由、故障恢复和 cache 一致性复杂度。只有当 workload 中长 prompt、长输出和 SLO 组合确实形成稳定瓶颈时，分离部署才可能抵消这部分成本。不能只因为架构图更复杂就推断吞吐一定更高。

DistServe 把这个思路做成独立 prefill/decode GPU 池，并根据 TTFT、TPOT 约束分别优化资源分配和并行配置，再按集群带宽安排两阶段位置。论文在其测试条件下报告最多服务 7.4 倍请求量，或在请求 SLO 达成率高于 90% 时满足 12.6 倍更紧的 SLO；这不是“拆池后通用吞吐提升 7.4 倍”，而是特定模型、workload、硬件配置与 SLO 下的 goodput 结果。[DistServe 原论文](https://arxiv.org/abs/2401.09670)

多轮会话还要区分“重算完整历史”与“复用已有 KV 后只处理新增 token”。2026 年的 PPD 研究指出，后者 append-prefill 对 decode 的干扰可能小得多，并提出按负载与 SLO 动态决定是否在 decode 节点本地处理后续轮次；作者报告 Turn 2+ TTFT 约降低 68%，同时保持有竞争力的 TPOT。[PPD 论文](https://arxiv.org/abs/2603.13358) 这项工作说明固定的“所有 prefill 都去 prefill 池”策略未必适合多轮 Agent，但它依赖前缀状态可用、传输成本和 SLO，不能直接当作现有框架的默认行为。

判断分离是否值得，至少比较四项：

| 观察项 | 合并部署要问什么 | 分离部署要增加什么 |
| --- | --- | --- |
| 首 token | prefill 是否拖慢已有 decode | state 传输是否拖慢首 token |
| 持续输出 | prefill 插入时 TPOT 是否抖动 | decode 池是否有足够活动请求 |
| 资源利用 | 一个池能否同时填满计算和显存 | 两个池是否出现一边空、一边排队 |
| 故障恢复 | 单池重启和重试如何处理 | state 丢失、路由和跨节点恢复如何处理 |

判断是否需要分离，不能只说“prefill 偏算力、decode 偏带宽”，还要给出 trace、cache bytes、网络传输和 P99 证据。

可以用一个明确标为假设的资源账本检查“独立扩缩容”是否有意义。假设每秒到达 2 个请求，每个请求平均消耗 0.15 GPU·s 的 prefill 工作、0.35 GPU·s 的 decode 工作；忽略并行效率变化时，需求分别是 $2\times0.15=0.30$ GPU 等价、$2\times0.35=0.70$ GPU 等价，合计 1.00 GPU 等价。一个共享池理论上可用接近 1 个 GPU 等价的计算能力承接，但会在阶段间争抢；若拆成两个各有 1 GPU 的池，prefill 池的简化利用率约 30%，decode 池约 70%，总分配却是 2 个 GPU。这个算术不能预测真实卡数，因为模型权重是否能放下、batch 非线性、TP 拓扑和最小副本数都未纳入；它只提醒我们：阶段分离可能用额外闲置换更稳定的 SLO，不能把利用率和 latency 收益当成同一指标。

再给 state transfer 加上可复算成本。若每个请求交接 1.6 GB KV，链路有效带宽假设为 20 GB/s，则仅按字节除带宽的理想传输时间为 $1.6/20=0.08$ s，即 80 ms；真实时间还要加协议、拥塞、同步与排队。如果共置时实测 P99 因阶段干扰增加 120 ms，拆池后传输为 80 ms 加 15 ms 路由/同步，仍可能有余量；若干扰只增加 50 ms，拆池反而把关键路径拉长。两组数据都是用于算账的假设值，未包含带宽共享和分布式 cache 布局差异。决策时应分别量化“共置的干扰时间”和“拆池的状态交接关键路径”，而不是拿 GPU 利用率替代两者。

长短 prompt 的差异还可能留在 prefill 池内部。LAPS 预印本把多轮长 prefill 和短 prefill 分队列，再对短请求做 length-aware batching；这说明 P/D disaggregation 解决的是阶段间资源争用，不自动解决阶段内部的长度异质性。其报告的延迟与 SLO 收益绑定预印本中的 workload、Qwen2.5-32B、H200 和具体 SGLang 配置，适合作为设计假设，不是上线承诺。[LAPS 预印本](https://arxiv.org/abs/2601.11589)

拆池以后，请求不是“从一张 GPU 图标走到另一张图标”这么简单，而是一次跨资源池的状态交接。典型数据流是：入口先完成鉴权和准入；router 选择 prefill worker；prefill worker 建立 token position 与 KV block，完成需要的 prompt 计算；connector 发送 KV payload 及层、block、dtype、量化 scale、序列长度和模型/cache-layout revision 等元数据；decode worker 为目标状态预留空间并校验收到的 block；只有交接成功，decode 才能从正确的 position 继续采样和流式输出。具体协议字段依 runtime 而异，但部署设计必须回答这些状态由谁创建、谁拥有、谁可释放，以及部分 transfer 失败后由谁清理。若只重试 router 而没有取消源端传输和释放 destination 的部分 block，重试本身就会造成缓存泄漏或错误复用。

可把阶段分离收益写成一个便于复核的账本：

~~~math
\Delta T
=T_{\mathrm{interference\ removed}}
-T_{\mathrm{KV\ transfer}}
-T_{\mathrm{routing\ and\ synchronization}}
-T_{\mathrm{pool\ imbalance}}.
~~~

若沿用前面的假设，并假设 transfer 与 route/synchronization 在请求关键路径上串行，共置干扰增加 120 ms、KV 传输为理想 80 ms、路由与同步为 15 ms，则剩余收益为 $120-80-15=25$ ms；若干扰只有 50 ms，则 $50-80-15=-45$ ms，拆池拉长关键路径。真实实现可能把传输、计算和路由部分重叠，因此不能把各段 span duration 不加区分地相加；应从 trace 找到交接前后请求真正等待的关键路径区间。`pool imbalance` 可以是 decode 池缺请求而 prefill 池排队，也可以是 decode backlog 变长；它要按请求等待时间和空闲资源观测，不能按 GPU 数量比例想当然地折算。这个差额是示例决策式，不是论文公式，也没有覆盖质量变化与故障概率；最终还要检查 P99、goodput、transfer failure、重算和成本。

多轮请求进一步改变这个边界。假设一轮新 prompt 共 4,000 token，其中 3,200 token 来自同一模型/template/权限域下可复用的 KV 前缀，则逻辑上的新增 prefill 是 $4{,}000-3{,}200=800$ token，预处理工作量可少 80%；但如果这 3,200 token 的 KV 当前只在远端 prefill pool，服务仍可能要传输它们，节省的计算不一定覆盖传输。PPD 论文关注的正是多轮 append-prefill：当 decode worker 已有可用前缀，较短的后续追加部分可能留在本地处理；若新增内容很长或本地 decode SLO 已紧张，仍可能选择送往 prefill pool。该策略以 cache locality、state version、transfer cost 和 TTFT/TPOT 为条件，不能只由“第几轮”决定。此处算出的 800 token 只展示复用后的输入差额，不代表总 KV 占用也减少 80%，因为已复用的上下文状态仍须被保留或传输。

因此部署团队至少需要分别做三个回放切片：长 prompt/短输出用于观察 prefill 是否成为队列瓶颈；短 prompt/长输出用于观察 decode pool 是否饱和；多轮高 prefix-hit 用于检查状态 owner 与 transfer 是否抵消复用收益。每个切片固定模型和 tokenizer revision、输入/输出长度、prefix hit tokens、到达时间、GPU/网络、目标 SLO 与并发，再比较共置、chunked prefill 和 P/D split。相同的总 token 数也可能有不同的阶段比例和 cache locality；不固定这些条件，拆池前后的结果无法解释。

## 7. Token budget 调度

LLM 请求的成本不能只看请求数。一个短请求和一个长上下文请求各占一个 sequence，但它们的 prefill 工作、KV Cache 和后续持续时间可能相差几个数量级。scheduler 因此需要同时维护三本账：

1. 本轮新增的 prefill token 账。
2. 当前活动 sequence 账。
3. 物理 KV block 或其他状态的显存账。

令 \mathcal{P}_k 表示第 k 轮进入 prefill 的请求集合，P_{i,k} 表示请求 i 在本轮新增的 prompt token 数，\mathcal{B}_k 表示本轮活动请求，T_prefill 表示本轮允许的新 prefill token 数，S_max 表示 active sequence 上限，则常见的资源约束可写为：

~~~math
\sum_{r_i\in\mathcal{P}_k}P_{i,k}\le T_{\mathrm{prefill}},
\qquad
|\mathcal{B}_k|\le S_{\max}.
~~~

若每个物理 block 能保存 b 个逻辑 token，忽略 prefix sharing 时，加入候选后的 block 需求可以粗略估计为：

~~~math
K_{\mathrm{after}}
\approx
\sum_{r_i\in\mathcal{B}_k}
\left\lceil\frac{P_i+D_i(k)+\Delta_i}{b}\right\rceil,
\qquad
K_{\mathrm{after}}\le K_{\mathrm{budget}}.
~~~

\Delta_i 是本轮预计新增的 token 数。这个估算要说明两个边界：第一，物理实现可能按层、按张量并行分片或按不同 state layout 计算 block；第二，共享前缀、滑动窗口和压缩 state 会让物理 block 数小于简单求和。公式用于做容量方向判断，真正的分配器必须以实际 block table 和 allocator 状态为准。

### 7.1 max_new_tokens 不是当前 cache 长度

请求通常带有最大输出长度，但 scheduler 不一定需要一开始就为全部 O_i 预留物理空间。过度预留会降低并发，完全不预留又可能在生成中途 OOM。常见做法是按当前逻辑长度分配 block，在每轮追加 token 时检查剩余预算，并在必要时进行抢占、排队、截断或拒绝。

prefix cache 命中还会改变 prefill 账。若 prompt 有 H_i 个 token 已由合法且版本一致的前缀状态覆盖，本次真正需要计算和新增的部分近似是：

~~~math
P_{i,\mathrm{new}}=\max(P_i-H_i,0).
~~~

H_i 不能只按字符串前缀计算，还要绑定模型 artifact、tokenizer/template、采样或状态版本、租户权限和 cache owner。不同用户的私密前缀不能因为文本相同就共享。cache 命中减少 prefill 工作，也不代表 decode 的 KV bytes、输出长度和公平性成本消失。

用一组输入把“少算多少”与“还占多少状态”分开。请求 prompt 长 1,600 token，其中经过授权且 revision 一致的 cache 命中 1,200 token，则本轮新增 prefill 为 $1{,}600-1{,}200=400$ token，输入计算量按 token 账本减少 75%。若某个 prefill 路径在该 shape 下处理速度假设为 20,000 token/s，线性估算 1,200 token 对应 $1{,}200/20{,}000=0.06$ s 的计算需求；真实 TTFT 节省还取决于 batch、kernel、queue、cache lookup 与并发，因此这只是服务工作量估算。请求最终仍要看到 1,600-token 上下文，若旧 KV 被保留则占用相应 block；cache reuse 节省重算并不自动消除内存占用。假设另一个 prompt 长 900 token、命中 700 token，本轮新增只有 200；按新 token 排序它看起来更轻，但如果其 prefix blocks 即将被淘汰或需跨节点拉取，实际访问成本可能更高。scheduler 需要同时记录 prompt tokens、cached tokens、saved prefill tokens、cache bytes、owner 与 transfer bytes，才能解释命中率为何没有等比例变成 TTFT 收益。

### 7.2 按 token 调度仍然要看工作类型

两个 1k-token 的请求并不一定等价：一个可能是首次 prefill，另一个可能是已经运行很久的 decode；一个可能命中 prefix cache，另一个需要完整计算；一个是交互请求，另一个是可延后的离线任务。因此 token budget 是必要的资源单位，不是完整的调度策略。

实用的调度记录至少应分开保存：

| 账本 | 代表量 | 影响 |
| --- | --- | --- |
| 新增 prefill | prompt 或 chunk token | 计算、TTFT |
| 活动请求 | sequence count | 调度开销、decode batch |
| 逻辑状态 | prompt + generated token | KV 增长 |
| 物理状态 | block、latent 或递归 state | 显存与迁移 |
| 预算债务 | 租户已用 token、等待时间 | 公平性与限额 |

按请求数限流仍有价值，例如保护连接和 CPU；但它不能替代 token、KV 和租户预算。

沿一轮调度手算三本账。假设 `max_num_batched_tokens=1,024`，在普通逐 token decode 下已有 6 个请求各需要本轮推进 1 个 token；本轮先为它们保留 6 token，剩余 1,018。等待队列中有长 prompt L=900 token 和短 prompt S=256 token。若按完整请求一次 prefill 且 L 先入，L 消耗 900，剩 118，S 进不来；若允许把 L 切成 512-token chunk，先处理这个 chunk 后剩 506，S 可以消耗 256，仍剩 250。这里没有假设两个计划的 kernel 时间相同；它只展示 token 预算怎样改变队列推进。若 active limit 是 8、当前 RUNNING 已有 7 个请求，即便 token 仍有 250，另一个新请求也会被 sequence cap 阻挡；若 KV block 不够，它仍不能进入。调度器应记录每个候选被哪一本账卡住，避免把所有延迟都归到“batch 太小”。

KV 账也可以在逻辑层做一次保守估算。令 block 容纳 16 个 token，某运行请求有 950 个 prompt token、已经生成 40 个 token，`max_new_tokens=160` 表示输出总上限而不是“还要再生成 160 个”。当前上下文为 $950+40=990$ token，需要 $\lceil990/16\rceil=62$ 个逻辑 block；最坏上下文为 $950+160=1{,}110$ token，需要 $\lceil1{,}110/16\rceil=70$ 个 block，差 8 个。完整预留最安全但可能降低 admission，逐 token 分配提高并发却要准备 block 增长、抢占或拒绝路径。具体 runtime 的块分片、prefix sharing、混合 attention state 和 allocator 水位不由这笔逻辑账本决定。

框架参数也要按资源层次理解。vLLM v0.32.0 的 `max_num_batched_tokens` 限制单次 iteration 的 token 工作量，`max_num_seqs` 限制单轮处理的 sequence 数并参与 model-runner buffer/CUDA graph capacity sizing；`max_num_active_seqs` 可以进一步限制真正进入 RUNNING 的请求数，而不缩小已配置的 runner capacity。API server 侧的 `max_num_queued_reqs` 限制跨其路由 DP ranks 的 in-flight 请求，`max_num_queued_tokens` 限制 prefill 队列中的 prompt token，达到门槛会拒绝新请求；后者在 chunked prefill 期间按完整 prompt 长度计数，可能偏保守。它们分别作用于 step 工作预算、运行形状、engine admission 和 API queue，不能互相替代，也不能仅凭数值与另一框架的参数做一对一映射。[vLLM v0.32.0 `serve` CLI](https://docs.vllm.ai/en/v0.32.0/cli/serve/)

压力还会改变 token 预算的收益方向。P-PAS 预印本研究长上下文、短输出请求，报告在低 scheduling pressure 下较大 MBT 可能让 prefill 执行更有效；当 prefill 与 decode 并发压力升高时，较小 chunk 可能减少对活动 decode 的干扰。本文把“调度压力”作为工作负载观察概念，而非跨框架标准分数：至少要同时看等待中的 prefill token、正在运行的 decode 请求、token budget 是否经常耗尽，以及 TPOT 尾部怎样变化。由此不能得出“高负载时预算一定越小越好”：kernel、模型和 GPU 组合会改变效率，实际控制需要依到达 trace 观测压力并重放比较。这里列出的观测量是本章用于设计本地回放的建议，不是 P-PAS 论文披露的通用信号定义。[P-PAS 预印本](https://arxiv.org/abs/2608.15171)

`max_num_queued_tokens` 还可以和 TTFT 目标做一笔近似的队列准入账。vLLM v0.32.0 文档给出的 sizing 直觉是“目标 TTFT × prefill throughput”。假设一个 prefill pool 在目标长度分布下稳定处理 20,000 prompt token/s，等待预算希望不超过 100 ms，则粗略的队列 token 上限为 $20{,}000\times0.1=2{,}000$ prompt token。若当前排队 prompt 共 1,700 token，再到一个 500-token 请求会超过这个门槛，可以在 API 层拒绝或路由到其他实例。这个近似忽略到达突发、长度异质、缓存命中和服务时间分布；文档说明 chunked prefill 的部分请求会按完整 prompt 计数，prefix hit 也可能在 prefill 完成前不可知，因此实际计数偏保守。它只能作为保护 TTFT 的初始限额，不是精确的排队时延预测。

三本账还要落实到容量所有权。API server 通常更适合约束连接、in-flight requests 和排队的 prompt token；engine scheduler 负责每轮 token 与 active sequence；KV allocator 负责真实 block 是否可分配；router 则知道各 worker 的负载和健康状态。API 的排队 token 上限不会替代 engine KV admission，engine 的 active sequence 上限也不能限制所有 router 入口的重试风暴。排查准入错误时，要记录拒绝发生在哪一层、当时的配置 revision、已计数的范围和返回给客户端的语义；否则同一个 503 可能代表队列保护、KV 不足或 worker 健康失败，客户端会做出错误的重试。

容量评审可以按一个明确的准入顺序复盘：先检查模型上下文与输出上限；再看服务入口是否仍有 in-flight 与 prefill queue headroom；然后在 engine step 中预留本轮 decode 进度并分配剩余 prefill tokens；接着预测候选加入后的逻辑状态与物理 KV blocks；最后才按 priority、deadline、等待年龄和租户债务选出本轮候选。实际 runtime 可以采用不同内部顺序，但上线审计至少要能回答每个请求在哪项约束下通过或等待。例：活动 decode 8 条、本轮 token 上限 1,024，给每条保留 1 token 后余 1,016；长请求的 900-token chunk 加短请求 256-token prompt 合计 1,156，超出预算 140，因此两者不能在同一轮完整入批；如果短请求先占 256，长请求本轮只能拿 760，而不能假装其 900 个 token 已全算完。分配了多少才推进多少，必须持续更新 `num_computed_tokens`、position 与 KV block 账本。

## 8. 优先级调度

生产系统通常有交互请求、离线批处理、内部评估和不同服务等级。严格优先级队列能降低高等级请求的等待，却可能让低等级请求永远排不到前面。更危险的是，优先级往往只看用户等级，不看 prompt 长度和 KV 成本，结果是一个高等级的超长请求仍能阻塞许多短请求。

一种可解释的动态排序分数可以写成：

~~~math
Q_i
=p_i+\alpha A_i+\beta U_i-\gamma D_{\mathrm{tenant}(i)}.
~~~

p_i 是业务优先级，A_i 是等待年龄，U_i 是距离截止时间的紧迫程度，D_tenant 是该租户相对于配额已经积累的服务债务，\alpha、\beta、\gamma 是权重。这个式子不是推荐某个固定算法，而是把“优先级、等待公平、截止时间和租户债务”放进同一张决策表。若请求已经等待很久，A_i 应逐渐提高；若租户近期消耗过多 token，D_tenant 应抑制继续插队。

常见策略有三类：

1. Strict priority：高等级队列有工作时优先服务，延迟简单可控，但低等级可能饥饿。
2. Priority with aging：等待越久优先级越高，能降低饥饿，但要防止大量低等级请求突然一起抢占。
3. Weighted fair sharing：按租户或队列权重分配 token 或 iteration 份额，更适合多租户长期公平，但实现和解释成本更高。

重试次数不应简单地增加优先级。否则一个失败请求会因为反复重试获得更多资源，形成正反馈。重试应由失败类型、剩余预算、幂等性和截止时间共同决定。

真实框架暴露的 priority 语义并不统一。vLLM v0.32.0 默认按 FCFS；启用 priority 时，较小的整数先处理，同优先级按到达时间排序。SGLang 访问日的官方参数文档默认也是 FCFS，但 priority scheduling 需要启用，且默认较大的整数先处理；配置 `--schedule-low-priority-values-first` 后才反转方向。SGLang 还把“新请求是否能抢占运行中请求”的 priority 差阈值，与 KV 满时按长度或 priority 选择 retraction 分成不同参数。[vLLM v0.32.0 `serve` CLI](https://docs.vllm.ai/en/v0.32.0/cli/serve/)；[SGLang Server Arguments，访问于 2026-11-02](https://docs.sglang.io/docs/advanced_features/server_arguments)

| 文档中的路径 | 排队优先级语义 | 资源压力下的相关机制 | 接入时的检查 |
| --- | --- | --- | --- |
| vLLM | 默认 FCFS；priority 模式下数值越小越早，同值按到达时间 | `max_num_batched_tokens`、`max_num_seqs`、`max_num_queued_reqs` 分别控制 step token、step sequence 和 in-flight 请求 | 锁定 release；区分 API queue admission 与 GPU scheduler admission |
| SGLang | 默认 FCFS；可启用 priority，默认数值越大越早，也可反转 | priority preemption threshold 控制抢占差值；KV 满时可按长度或 priority retraction | 在 API adapter 中显式转换优先级方向，并分别回放排队与 KV 压力 |

因此，统一服务 API 应定义自己的优先级合同，再映射到引擎具体语义；不能把 `priority=1` 原样转发到所有后端。框架有“priority”参数也不代表有等待老化、加权公平或截止时间保证，这些性质需要检查实现或由上层 scheduler 提供。

把排序策略与资源门禁分开，可以手算一个插队例子。假设只有一个运行槽位空出，候选 A 的业务级别为 3、等待 2 秒、租户服务债务为目标份额的 1.5 倍；候选 B 的级别为 2、等待 20 秒、债务为目标的 0.2 倍。为了说明字段如何起作用，定义一个任意的教学分数 $Q=10p+0.5A-4D$，其中 A 用秒、D 是无量纲的 debt ratio，分数越大越先：$Q_A=30+1-6=25$，$Q_B=20+10-0.8=29.2$，于是 B 因等待更久且租户欠服务而先运行。系数没有经过拟合，不能直接用于生产；它把“谁应该先”变成可审计的规则。调度器仍要先检查 B 是否能装入 token/KV 预算，并在预算不足时保留拒绝原因，而不能让一个高分但不可执行的请求挡住后续可行候选。

## 9. 多租户隔离

多租户场景下，不同团队或用户共享同一推理集群。隔离至少有四层：

1. 到达率：QPS、连接数和突发大小。
2. 计算：prompt/output token 配额、active sequence 和优先级。
3. 内存：上下文长度、KV block 上限、prefix cache namespace 和淘汰策略。
4. 数据与运营：鉴权、日志、计费、质量样本和取消权限。

只按请求数限流会失真。一个租户发出 100 个短请求，可能比另一个租户发出 1 个超长 RAG 请求便宜；反过来，短请求对 TTFT 的敏感性又可能更高。实际配额应同时记录请求数、输入 token、输出 token、峰值 KV bytes 和单位成功任务成本。

共享 prefix cache 时尤其要检查权限边界。相同的系统提示词可以在同一模型版本和同一安全范围内复用，但包含租户私有资料、用户身份或授权结果的前缀不能被另一个租户命中。cache key、日志脱敏和回收策略应在设计中明确，而不是等串数据事故后再补。

多租户系统还需要选择隔离位置：网关可以提前拒绝超额请求，scheduler 可以限制 token 和 sequence，allocator 可以限制物理 block，模型 worker 可以限制 kernel 并发。每一层的限制都要有清晰的错误码和 metrics，否则用户只会看到“偶尔很慢”。

用一个十秒窗口说明配额与实际服务份额的区别。假设三个租户权重为 6:3:1，目标记账单位为 output token，窗口内可计量服务量为 10,000 token，则一个简单的加权份额账本是 6,000、3,000、1,000 token。若实际分配为 9,000、1,000、0，实际/目标比分别是 1.5、约 0.33、0；总量看似用满，第二和第三租户却未获得目标份额。相反，如果三者请求的 prompt、输出长度和 SLO 完全不同，token share 本身也不足以判定公平；还要看等候时间、成功任务数、KV 峰值和每单位任务成本。配额不是把 GPU 切成固定份额的同义词，而是一项资源记账与争议处理合同。

## 10. Head-of-line blocking 与长短请求混跑

队头阻塞是调度中常见问题。如果一个长请求排在前面，后面的短请求可能被拖住；即使使用 continuous batching，长请求仍可能长期占用 KV block 和 decode 槽位。continuous batching 减少了整批等待，不等于消除了资源竞争。

可以从三层处理：

1. 请求层：限制最大上下文和输出，给短交互与长 RAG 使用不同队列或服务等级。
2. 调度层：使用 token budget、chunked prefill、aging 和 deadline-aware 排序，避免单个请求独占一轮。
3. 资源层：使用分页 cache、抢占/重算、prefill/decode 分离或独立的离线 worker。

每种办法都改变了别的指标。长度分队列提高可预测性，却降低了混合 batch 的机会；抢占释放显存，却要付出重算或 state 搬运成本；降低长请求优先级可以保护短请求，却可能让长任务超时。报告中应展示长请求和短请求各自的 P95/P99，而不是只报总体平均。

把“长请求变慢”分成 admission 和已运行两种路径。若长 prompt 还在 waiting，问题可能是长度队列没有最低服务份额，或短队列持续到达造成 starvation；若它已在 prefill，问题可能是每轮 token budget 太小、chunk 排得过稀，导致完成时间拖长；若它已进入 decode，可能是 KV 水位过高、每 token 状态读取变慢或抢占重算。三者都可能表现成相似的端到端超时，但修复方向不同。一个实用的 trace 至少要为每次调度保存请求进入候选队列的时间、被延迟/跳过的理由、实际消耗的 prompt/decode token、KV 分配变化和恢复次数；然后按 prompt/output 长度分桶计算 TTFT、TPOT 与完成率。若服务采用两个长度队列，还要对照每队列的到达率和 service rate，而不是只看池中当前请求数。

长度分队列时可使用“保底份额 + 空闲借用”，避免把公平和利用率做成二选一。假设每 100 ms 有 2,048 个 prefill token 的调度容量，先给长请求队列保留 512 token 的最低份额，短请求可以使用其余 1,536 token；若长队列为空，短请求临时借用空闲额度，但下一轮长队列重新有积压时，借用不能变成永久占用。一个 8,192-token 长 prompt 在其他工作不竞争、每轮都拿到 512 token 的理想算术下需要 $8{,}192/512=16$ 轮，约 1.6 秒的调度窗口；这只是预算推算，不是模型真实 prefill latency。它明确展示了最低份额可以防止无限饥饿，却不能保证长请求的绝对 TTFT；份额太低会延迟长任务，份额过高则会让短队列损失 batch 机会。线上应按最老等待时间和目标 SLO 调整保底，并在空闲借用、归还和队列切换时记录每轮预算。

## 11. 调度指标

调度系统要持续监控完整链路，而不是只看 GPU 利用率。GPU 很忙但用户排队很久，或者 GPU 利用率不高但网络和工具等待很长，都可能是正常现象或严重故障，必须结合 trace 判断。

建议按下面的层次记录：

| 层次 | 指标 | 说明 |
| --- | --- | --- |
| 到达与队列 | arrival rate、queue length、queue time、drop/reject | 判断过载和等待来源 |
| 模型阶段 | prefill time、decode time、TTFT、TPOT/ITL | 区分输入处理和持续生成 |
| 尾延迟 | E2E、TTFT、TPOT 的 P50/P95/P99 | 观察用户体验和长尾 |
| 资源 | active sequences、batch token、KV watermark、OOM | 判断预算是否成为瓶颈 |
| 调度动作 | preemption、recompute、swap、cancel release | 判断优化是否付出代价 |
| 结果 | finish reason、截断率、错误率、goodput | 防止用失败请求换吞吐 |
| 租户 | token share、等待最大值、配额拒绝、成本 | 判断是否公平和可计费 |

对租户服务份额 x_1,\ldots,x_n，可以用 Gini 系数做粗略比较：

~~~math
G
=\frac{\sum_{i=1}^{n}\sum_{j=1}^{n}|x_i-x_j|}
{2n\sum_{i=1}^{n}x_i}.
~~~

G 越大表示份额越不均匀，但它不告诉我们某个租户是否本来就拥有更高权重，也不能替代 SLO 和优先级语义。因此应同时报告目标权重、实际 token share、最大等待时间和 SLO 成功率。

例如两个租户的服务量为 `x=(80,20)`，则 G=0.3；若为 `(50,50)`，则 G=0。这里的 `x_i` 必须是非负、同单位且总和大于零的观测量。若租户目标配额本来是 4:1，实际 `80:20` 是完全按权重分配，原始 token share 的 Gini 却仍为 0.3；此时还应计算“实际服务量/目标权重”的归一化比值，并报告各租户 SLO 与最大等待，才知道系统是否公平。

## 12. 常见调度策略的取舍

| 策略 | 作用 | 风险 |
| --- | --- | --- |
| FIFO | 规则简单，容易解释 | 长请求阻塞短请求，无法体现租户权重 |
| Strict priority | 保护高等级交互 SLO | 低等级饥饿，突发时尾延迟恶化 |
| Aging priority | 让长期等待请求逐步获得机会 | 需要选择老化速度，可能造成批次突变 |
| Token budget | 用真实计算和 cache 成本限制批次 | 要估计输入、输出和物理 block |
| Length-aware | 减少长短混跑和 padding 浪费 | 短请求可能长期占优 |
| Deadline-aware | 优先处理即将超时的请求 | 需要可靠的剩余时间估计 |
| Weighted fair sharing | 让租户长期获得可解释份额 | 调度状态、记账和实现都更复杂 |
| Tenant quota | 防止 noisy neighbor | 配额过低会降低整体利用率 |

没有一种策略在所有 workload 上都最好。线上选择应先写清楚服务目标，再用同一套 workload 对比吞吐、尾延迟、cache 水位、公平性和失败恢复；不能把某个 runtime 的策略名称当成性能保证。

### 12.1 代表性系统分别解决了什么

下表把研究路线放在同一张问题图上。它们解决的是不同层次的调度瓶颈，不能只按论文倍率排名。

| 研究 | 针对的问题与机制 | 作者报告的证据 | 设计代价、边界与可组合点 |

这张路线图还要区分“跨阶段资源冲突”和“阶段内部工作差异”。Sarathi-Serve 以 chunk 为交错单位，控制长 prefill 对 decode 的阻塞；DistServe 把 P 与 D 放进独立资源池；LAPS 继续追问为什么分离后短 prefill 仍被长 prefill 拖慢；P-PAS 则把本轮预算作为随并发压力变化的控制旋钮。它们在系统位置和作用对象上不同，可以组合成候选设计，但不能把论文中的加速倍率相乘，也不能只凭某一篇论文为线上容量规划定值。一个可复核的回放应保持模型、输入/输出长度 trace、到达时间和 SLO 不变，逐个改变 chunk、P/D 池、队列规则或预算策略，并把 TTFT、TPOT、goodput、KV bytes、等待尾部和抢占成本一并比较。

Agentix 把调度上下文扩展到 Agent 程序及其调用依赖，属于第九章应用工作流的边界；Raincheck 通过多模态 deferred prefill 在回答期间或回答后补处理输入，属于第十章的媒体输入/质量主题。本章只借它们提醒读者：程序级完成时间和多模态输入恢复不是普通单请求队列的同义问题，不在这里展开其系统机制。Agentix 的正式会议页和 Raincheck 预印本分别报告特定 agentic workload 与特定视觉/视频数据集上的结果，不能外推为所有 serving scheduler 的收益。

## 13. 最小 Python demo：continuous batching 调度器

下面的 0 依赖 Python 3 demo 模拟一个很小的 continuous batching scheduler。输入是四条带到达时间、prompt/output 长度、tenant 和 priority 的合成请求，输出每轮 trace、等待时间、TTFT、TPOT、租户输出 token 和活动/KV 峰值。为保持代码短小，它假设每个 prompt 在一个 iteration 完成 prefill，不实现 chunked prefill；KV 预算用逻辑 token 的保守 reservation 近似，不是物理 block allocator。代码没有外部依赖，可保存为 `.py` 文件后用 Python 运行；下方输出是按代码逐步手算的预期值，没有执行本段代码。

> 代码状态：静态审阅，未运行（2026-11-02）。

```python
REQUESTS = [
    {"id": "short_a", "tenant": "paid", "arrival": 0, "prompt": 80, "out": 3, "priority": 2},
    {"id": "long_rag", "tenant": "free", "arrival": 0, "prompt": 1800, "out": 5, "priority": 1},
    {"id": "short_b", "tenant": "paid", "arrival": 1, "prompt": 120, "out": 2, "priority": 2},
    {"id": "tool_call", "tenant": "internal", "arrival": 2, "prompt": 300, "out": 3, "priority": 3},
]

LIMITS = {
    "max_active": 3,
    "prefill_token_budget": 2200,
    "kv_token_budget": 2500,
}

if any(value <= 0 for value in LIMITS.values()):
    raise ValueError("all scheduler limits must be positive")
if len({req["id"] for req in REQUESTS}) != len(REQUESTS):
    raise ValueError("request ids must be unique")
if any(req["prompt"] > LIMITS["prefill_token_budget"] for req in REQUESTS):
    raise ValueError("this demo requires each full prompt to fit one prefill step")
if any(req["prompt"] + req["out"] > LIMITS["kv_token_budget"] for req in REQUESTS):
    raise ValueError("a request's prompt plus output reservation exceeds the KV budget")


def sort_waiting(req):
    return (-req["priority"], req["prompt"], req["arrival"])


waiting = []
running = []
done = {}
trace = []

for time in range(20):
    for req in REQUESTS:
        if req["arrival"] == time:
            item = dict(req)
            item.update({"start": None, "first": None, "generated": 0, "end": None})
            waiting.append(item)

    decoded = []
    for req in list(running):
        req["generated"] += 1
        decoded.append(req["id"])
        if req["first"] is None:
            req["first"] = time
        if req["generated"] >= req["out"]:
            req["end"] = time
            done[req["id"]] = req
            running.remove(req)

    scheduled = []
    budget = LIMITS["prefill_token_budget"]
    waiting.sort(key=sort_waiting)
    for req in list(waiting):
        if len(running) >= LIMITS["max_active"]:
            break
        kv_if_added = sum(r["prompt"] + r["out"] for r in running)
        kv_if_added += req["prompt"] + req["out"]
        if req["prompt"] <= budget and kv_if_added <= LIMITS["kv_token_budget"]:
            req["start"] = time
            running.append(req)
            waiting.remove(req)
            scheduled.append(req["id"])
            budget -= req["prompt"]

    kv_tokens = sum(req["prompt"] + req["generated"] for req in running)
    active_count = len(running)
    trace.append((time, decoded, scheduled, active_count, kv_tokens))

    if len(done) == len(REQUESTS):
        break

if waiting or len(done) != len(REQUESTS):
    raise RuntimeError("demo ended with requests that were never completed")


def metric(req):
    tpot = None
    if req["out"] > 1:
        tpot = round((req["end"] - req["first"]) / (req["out"] - 1), 2)
    return {
        "wait": req["start"] - req["arrival"],
        "ttft": req["first"] - req["arrival"],
        "tpot": tpot,
        "end": req["end"],
    }


summary = {req_id: metric(req) for req_id, req in sorted(done.items())}
tenant_tokens = {}
for req in done.values():
    tenant_tokens[req["tenant"]] = tenant_tokens.get(req["tenant"], 0) + req["out"]

print("trace_first4=", trace[:4])
print("summary=", summary)
print("tenant_output_tokens=", tenant_tokens)
print("max_active=", max(step[3] for step in trace))
print("max_kv_tokens=", max(step[4] for step in trace))
```

一组可能输出：

```text
trace_first4= [(0, [], ['short_a', 'long_rag'], 2, 1880), (1, ['short_a', 'long_rag'], ['short_b'], 3, 2002), (2, ['short_a', 'long_rag', 'short_b'], [], 3, 2005), (3, ['short_a', 'long_rag', 'short_b'], ['tool_call'], 2, 2103)]
summary= {'long_rag': {'wait': 0, 'ttft': 1, 'tpot': 1.0, 'end': 5}, 'short_a': {'wait': 0, 'ttft': 1, 'tpot': 1.0, 'end': 3}, 'short_b': {'wait': 0, 'ttft': 1, 'tpot': 1.0, 'end': 3}, 'tool_call': {'wait': 1, 'ttft': 2, 'tpot': 1.0, 'end': 6}}
tenant_output_tokens= {'paid': 5, 'free': 5, 'internal': 3}
max_active= 3
max_kv_tokens= 2105
```

这个 demo 要看三件事：

1. 新请求可以在旧请求尚未完成时加入 running batch，这就是 continuous batching 的核心。
2. `tool_call` 因为 active sequence limit 等待了 1 个 iteration，TTFT 变成 2。
3. `max_kv_tokens` 展示当前逻辑 prompt + generated token；准入时另为请求的最大输出预留空间，避免 toy 请求在后续 decode 中超过预算。

这里的 tool_call 只是一个带有工具语义名称的普通 toy 请求，代码没有模拟工具等待、外部副作用或重试；真实系统应在 tool wait 状态释放 decode 槽位，并使用幂等键保护工具动作。demo 的准入条件假设每个完整 prompt 可在一个 step 处理，因此会拒绝超过单轮 prefill budget 的请求；真实服务可用 chunked prefill 处理长 prompt。demo 每轮重新计算可接收的 prefill token budget，也没有实现租户加权公平、抢占和 backpressure，读者可以在这些位置继续扩展。trace 中的 active_count 是本轮完成释放和新请求加入之后的活动数，decoded 列表则记录本轮曾经执行过 decode 的请求，两者有意分开。

手工走一遍 trace 可核对输出字段。时间 0 时 short_a 与 long_rag 到达，按 `sort_waiting` 的 priority 降序先放入两者；它们的当前逻辑 KV 合计 $80+1{,}800=1{,}880$ token。时间 1 时两者各 decode 一个 token，`first=1`；short_b 同时到达并被加入，所以本轮后活动数为 3，KV 账为 $81+1{,}801+120=2{,}002$。时间 2 时三者再各推进一个 token，逻辑 KV 为 $82+1{,}802+121=2{,}005$；tool_call 已到达，但 active limit 已满，因此仍排队。时间 3 时 short_a 达到 3-token 上限，short_b 达到 2-token 上限，两者在本轮产生的最后 token 被计入后才释放；tool_call 随即进入，long_rag 已生成 3 个 token，因此 KV 账为 $1{,}803+300=2{,}103$。这个过程说明 trace 中的 `decoded` 是本轮开始前正在推进的请求，`scheduled` 是本轮末尾新接纳的请求，不能把两列当作同一时点的 batch。

demo 的 `time` 是离散 iteration 序号，不是毫秒。short_a 在时间 0 到达、时间 0 开始、时间 1 产生首 token，故 waiting 是 0 个 iteration、TTFT 是 1 个 iteration；它在时间 3 结束、输出 3 个 token，所以 TPOT 为 $(3-1)/(3-1)=1$ 个 iteration/token。short_b 在时间 1 到达但到时间 1 末才进入活动集，时间 2 才有首 token，因而输出的 waiting=0、TTFT=1；tool_call 在时间 2 到达、时间 3 开始、时间 4 首 token，waiting=1、TTFT=2。三者的数字只验证计时边界和队列状态，不代表毫秒级 serving 延迟。租户账本也只是输出 token：paid 为 $3+2=5$，free 为 5，internal 为 3；它没有把长输入的 prefill 成本或 300-token tool_call prompt 计入，因此不能当成本分配器或公平性指标。

这个 demo 的能力边界还可以由它的变量反向读出。`prefill_token_budget` 每个时间步重置，只扣除新请求的 prompt；代码在解码之前推进全部 running requests，所以没有模拟 decode-first 与大 prefill 同轮时的 TPOT 干扰。`sort_waiting` 使用一个固定优先级，再按 prompt 长度和到达时间排序；它不实现 deadline、等待 aging 或 tenant weight。四条请求的租户 output token 合计可以算出，却不能代表实际 GPU time：long_rag 输入 1,800 token、输出 5 token，而 paid 租户合计输入仅 200 token、输出 5 token。若把计费单位换成总 token，paid 为 205、free 为 1,805、internal 为 303；若按 GPU seconds 或成功任务计费，还需要真实服务时间和结果有效性。代码输出 `max_active` 与 `max_kv_tokens` 也没有 P95/P99 样本能力；四条 toy trace 只能检查状态转移和局部算术，不能证明调度公平或容量达标。

代码还把两种 KV 口径分开：准入时将活动请求的最大输出上限预留，以免 toy 请求随后超过总预算；trace 的 `kv_tokens` 则只列当前 prompt + 已生成 token。最大 reservation 的短时峰值和当前逻辑状态峰值并非同一个数，后者在时间 4 达到 2,105。实际分页 allocator 还要处理 block rounding、共享前缀引用和 block free；本 demo 没有呈现这些细节。若改成“只按当前状态准入”，读者需要添加增长失败时的退避/抢占/重试状态；若把 `max_active` 从 3 改成 4，tool_call 可以提前进入，但是否改善 goodput 仍取决于它给已有 decode 带来的 TPOT 变化和剩余 KV。

## 14. 抢占、取消与重试的正确性

只按当前请求的 token 数排序并不能自动得到好的调度器。长请求可能长期占用 KV block，短请求可能被反复插队；工具调用失败后，如果网关、Agent runtime 和模型 worker 各自重试，又会把同一业务动作复制成重试风暴。scheduler 需要同时看剩余 token、已等待时间、优先级、截止时间、租户服务债务、KV 占用和副作用状态。

一个可解释的排序分数可以写成：

~~~math
Q_i
=p_i+\alpha A_i+\beta U_i-\gamma D_{\mathrm{tenant}(i)}.
~~~

p_i 是基础优先级，A_i 是等待年龄，U_i 是截止时间紧迫度，D_tenant 是租户已经超出目标份额的服务债务。剩余 token 数通常更适合作为资源估计和同分时的 tie-break，而不是简单地让长请求永远低优先级。具体权重必须用长短混合、突发和多租户 workload 回放。

### 14.1 抢占必须保存完整的状态契约

抢占不是把请求从 running 列表删除。被抢占请求至少要保留：

1. 已消费的 token position 和 attention position offset。
2. KV block table、物理 block 所属设备和逻辑长度。
3. 采样随机状态、解码参数、stop 状态和已发送事件。
4. 模型版本、tokenizer/template 和 cache layout 版本。
5. 工具事务状态、幂等键、租户预算和取消信号。

重算会释放 cache，但恢复时需要从一致的 token 前缀重新 prefill；swap/offload 可以保留更多状态，却要付出 device-to-device 或 host transfer 延迟，还要处理校验和、版本与容量。两条路径都不能把一个 runtime 的 state 直接交给 layout 不兼容的另一个 worker。

抢占策略应在安全的 iteration 或 chunk 边界生效。若 token 已经发送给客户端，恢复后不能再次发送同一个 token；若工具已经产生副作用，恢复模型文本也不能自动再次执行工具。需要在 trace 中记录 preempt、recompute、swap、resume 和 duplicate-token 事件，才能判断抢占到底减少了 OOM 还是制造了隐蔽错误。

### 14.2 取消和重试要有明确的边界

客户端断开、服务超时、模型错误、工具超时和网络重试不是同一种失败。建议至少分为：

1. 可以安全重试的瞬时资源错误，例如 worker 暂时不可用。
2. 需要重新构造请求的协议错误，例如 tokenizer/template/schema 不一致。
3. 不应自动重试的副作用错误，例如写数据库、扣款或发送外部消息。

模型生成重试不等于工具执行可以重试。工具调用应使用 idempotency key、事务状态或补偿动作，重试预算也要由一个明确的 owner 管理：

~~~math
N_{\mathrm{retry}}\le N_{\max},\qquad
C_{\mathrm{request}}\le C_{\max},\qquad
T_{\mathrm{wall}}\le T_{\max}.
~~~

可以用重试放大倍数观察风暴：

~~~math
A_{\mathrm{retry}}
=\frac{N_{\mathrm{all\ attempts}}}{N_{\mathrm{original\ requests}}}.
~~~

A_retry 大于 1 并不一定错误，但它必须能按错误类型、租户和时间窗口解释。假设窗口内有 100 个原始请求，20 个遇到瞬时错误并各重试一次，则总尝试数为 120，$A_{\mathrm{retry}}=120/100=1.2$；若 12 次重试最终成功，合格请求最多从 80 个首轮成功增加到 92 个，不能把 120 次 attempt 当作 120 个业务完成。若 20 个错误里含有已提交的工具副作用，重复调用还可能造成数据损坏；此时把 retry budget 限为 1 次也不能替代幂等键和事务状态。压测除了吞吐、TTFT、TPOT 和 P99，还应记录抢占恢复成功率、重复 token 率、重试放大倍数、取消后的 KV 回收时间和副作用工具的重复执行数。一个平均吞吐更高但长任务永远得不到服务的策略，不是合格的生产调度器。

## 15. 一个高峰期多租户调度故障的分析

构造一组假设的共享推理集群事故数据。付费交互租户需要短聊天和代码补全，内部分析租户提交长 RAG，离线租户运行批量摘要。平时三类请求都能完成，但在业务高峰期出现了三个现象：短聊天 TTFT P99 从 400 ms 上升到 2.8 s，长 RAG 超时率上升，GPU output TPS 却提高了 18%。这些数字用于演示排查顺序，不来自生产测量。如果只看吞吐，调度器似乎变好了；把请求 trace、KV 水位和 finish reason 对齐后，才会发现它正在用用户体验和失败请求换吞吐。

第一步是分解工作类型。短聊天的输入通常小于 512 token，输出小于 256 token；长 RAG 的输入可能超过 8k token，输出约 512 token；离线摘要可以等待更长的 batch，但不应占用交互请求的尾延迟预算。调度器需要同时记录三类账：本轮新增 prefill token、active sequence 数和物理 KV block。仅按请求数设置 `max_batch=32`，无法表达一个 32k token 请求与一个 128 token 请求的差异。

第二步检查队列和 iteration trace。假设调度器使用 5 ms 等待窗口，并在每轮优先填满 prefill token budget。长 RAG 到达后，若一次性把 8k token 全部送入 prefill，正在 decode 的短请求可能在一个或多个 iteration 中没有机会产生 token；短请求的 TTFT 增长并不是模型变慢，而是长 prefill 挤占了 decode 配额。将长 prompt 切成 chunk 后，若 `T_chunk` 过大，问题仍会出现；若过小，又会增加 kernel launch 和状态管理开销。

可以把每一轮的选择写成约束，而不是只按优先级排序。对候选集合 `B_k`，令 `P_i,k` 为本轮新增 prompt token，`D_i,k` 为 decode token，`K_after` 为加入后的物理状态需求，则至少要满足：

~~~math
\sum_{i\in B_k}P_{i,k}\le T_{\mathrm{prefill,budget}},
\qquad
\sum_{i\in B_k}D_{i,k}\le T_{\mathrm{decode,budget}},
\qquad
K_{\mathrm{after}}\le K_{\mathrm{budget}}.
~~~

实际系统还要保留取消、抢占和新请求的余量。`T_prefill,budget` 与 `T_decode,budget` 不必固定相等：交互高峰期可以降低单轮 prefill 配额，保护正在流式输出的请求；离线窗口则可以提高 prefill 配额，提高总吞吐。预算变化必须在 trace 中记录，否则同一个 runtime 的两个结果无法公平比较。

第三步处理公平性。若严格按付费优先级，内部长任务可能永远得不到服务；若严格 FIFO，长 RAG 会阻塞短交互；若只按 prompt 长度，短任务会持续插队。可以用带老化和租户债务的排序分数：

~~~math
Q_i=p_i+\alpha A_i+\beta U_i-\gamma D_{\mathrm{tenant}(i)}-\eta C_i,
~~~

其中 `p_i` 是业务优先级，`A_i` 是等待年龄，`U_i` 是截止时间紧迫度，`D_tenant` 是租户相对目标份额的服务债务，`C_i` 是预计的本轮资源消耗。这个式子不是必须照搬的算法，而是迫使系统同时表达优先级、等待、公平和成本。长请求不应因为贵就永久饿死，等待时间应逐步提高其获得服务的机会。

第四步决定是否分队列。短交互、长 RAG 和离线摘要可以拥有不同的 prefill 配额和优先级；短队列保护 TTFT，长队列获得明确但较低的吞吐份额，离线队列只在剩余容量中运行。分队列并非免费：它可能让某个池空闲而另一个池排队，也可能降低共享 batch 的饱满度。因此要同时观察每个队列的 queue time、goodput、token share、KV watermark 和 SLO 达成率。

第五步处理重试和副作用。高峰期超时会让客户端重试，重试增加到达率，形成 retry storm。纯文本生成可以在明确预算内重试，但工具写入、数据库提交和外部消息发送必须携带幂等键和事务状态；调度器不能把一次“工具等待超时”当成可无条件重新执行的普通请求。应记录：

~~~math
A_{\mathrm{retry}}
=\frac{N_{\mathrm{all\ attempts}}}{N_{\mathrm{original\ requests}}},
\qquad
N_{\mathrm{retry}}\le N_{\max}.
~~~

如果吞吐提高同时 `A_retry`、length finish reason 和工具重复执行数也提高，说明系统可能只是把失败转化成了更多计算。调度器的 goodput 应只统计在 SLO 内完成且任务结果有效的请求，而不是所有生成过 token 的请求。

最后做反事实压测：保持模型、GPU、输入输出长度和流量不变，只改变等待窗口、chunk size、prefill/decode 配额、队列分流和公平策略。每次实验都比较短请求与长请求的 P95/P99、总 output TPS、goodput、KV 峰值、抢占/重算率、取消回收时间、租户 token share 和 retry amplification。如果只改变一个 batch 参数却同时改变了最大输出或超时规则，结果就无法归因。

这个案例最终可能得到“长短请求分池 + chunked prefill + aging fair share”的组合，也可能发现 prefill/decode 分离的 state 传输成本过高而继续使用合并池。选择不由 batching 名称决定，而由请求状态、token 和 cache 账本、SLO、公平性、失败语义以及真实压测共同决定。

[FastServe: Iteration-Level Preemptive Scheduling for Large Language Model Inference](https://www.usenix.org/conference/nsdi26/presentation/wu-bingyang) 与 [较早 arXiv 版本](https://arxiv.org/abs/2305.05920)：token 级抢占、skip-join 多级反馈队列和 KV 主机换入换出；正文采用 NSDI 2026 正式发表版本的 6.1×，不与 arXiv v3 曾报告的 31.4×/17.9×混用。

8. [P-PAS: Prefill-Pressure Adaptive Scheduling for Long-Context LLM Serving](https://arxiv.org/abs/2608.15171)：讨论 scheduling pressure 与 max batched tokens 的负载依赖关系；自适应 budget 结果仍需在目标设备和到达 trace 上复核。

10. [vLLM v0.32.0 Benchmark CLI](https://docs.vllm.ai/en/v0.32.0/benchmarking/cli/)：核对目标服务压测的请求率、burstiness、并发及 latency 指标定义；目标部署仍须补充租户、工具与业务 SLO 指标。

资料的使用层次要分开：论文用于解释机制和实验假设，官方文档用于确认当前接口与维护状态，源码用于定位实现路径，项目实测用于决定目标 workload 的选择。一个文档页面写着支持 continuous batching，只能证明存在某条实现路径；是否满足目标模型的协议、质量、P99、公平性和单位成功成本，仍需回放和压测。

## 17. 本章小结

本章核心结论：

1. Batching 是提升吞吐的基础，但会带来排队延迟。
2. Static batching 适合离线任务，在线服务中容易浪费。
3. Dynamic batching 用等待窗口换更高吞吐。
4. Continuous batching 是在线 LLM serving 的重要基础，但它不会自动消除 prefill 干扰、KV 压力、饥饿或过载。
5. Prefill 和 decode 资源特征不同，调度策略也不同。
6. LLM 调度要看 token budget 和 KV Cache，而不是只看请求数。
7. 优先级和多租户隔离是生产系统必须考虑的问题。
8. Orca、FastServe、Sarathi-Serve 与 DistServe 分别处理 iteration 排程、长任务抢占、prefill chunking 和阶段资源隔离；它们针对不同瓶颈，论文倍率不能横向排名。
9. 调度优化要同时看吞吐、TTFT、TPOT、P95/P99、goodput、公平性和失败恢复。
