# 第十四章：部署面试题

部署面试题看起来经常只是几个名词：70B、KV Cache、PagedAttention、INT4、
continuous batching、RAG、prompt injection。真正被追问的却不是名词解释，而是
你能不能把一个请求的资源、延迟、质量、安全和故障恢复连起来。

例如，“如何部署 70B 模型”并不等于回答“使用多张 GPU 和 tensor parallel”。
还要知道权重和 KV Cache 各占多少显存，输入和输出 token 吞吐分别是多少，长短请求
如何共存，模型故障时如何恢复，量化会损失什么，以及上线后用哪些证据判断方案仍
然可靠。名词是入口，推理链才是答案。

本章把常见问题写成独立的知识单元。每一节先解释问题本身，再给出公式、工程
取舍、一个可以直接组织成面试回答的完整叙述，最后说明继续追问时应该补充什么。
示范答案不是让读者死记的台词，而是把需求、机制、指标和边界串起来的一个样例。

## 1. 先学会识别部署题的真正问题

### 1.1 面试官不是在收集框架名称

当题目问“你用过哪些推理框架”，表面上是在问工具，实际可能在考察：

1. 你是否知道模型 artifact、tokenizer、chat template 和 runtime 必须匹配。
2. 你是否能区分 prefill、decode、KV Cache、调度和网关的责任。
3. 你是否用目标模型、硬件和输入分布做过压测，而不是背公开 benchmark。
4. 你是否知道低延迟、高吞吐、低成本和高可靠性之间不能同时无限优化。
5. 你是否能说明失败时怎样限流、降级、回滚和恢复外部状态。

因此，部署题的回答要像一段小型设计评审，而不是一串产品名。一个可迁移的顺序
是：先界定 workload，再计算资源，再画请求路径，接着讨论瓶颈和故障，最后说明
质量、安全、成本、监控和发布证据。

### 1.2 四层回答深度

对刚入门的读者，至少要能讲清四层：

| 层次 | 读者需要说清什么 |
| --- | --- |
| 直觉 | 模型服务为什么会被输入长度、输出长度和并发拖慢 |
| 机制 | prefill、decode、KV Cache、batch 和并行怎样工作 |
| 工程 | 指标、队列、显存、版本、权限和故障如何落地 |
| 判断 | 为什么在这个 workload 下选择某个方案，什么时候应换方案 |

专家回答还会主动标注证据类型：论文说明方法原理，官方文档说明某个版本的能力，
源码和压测说明实现行为，业务回放才说明是否适合当前服务。把某个框架的宣传吞吐
直接当成自己的 SLO，是证据边界越界。

### 1.3 一张回答草图

面对一条陌生部署题，可以先在草稿上写：

~~~text
需求：请求类型、QPS、token 分布、流式/异步、质量和安全
资源：权重、KV、prefill、decode、active sequence、GPU 和网络
链路：gateway -> policy -> router -> context -> cache -> runtime -> response
瓶颈：排队、prefill、decode、显存、依赖、连接或外部副作用
证据：压测、离线回放、shadow、canary、trace、回滚和成本账本
~~~

这张草图不是需要在面试中逐字念出的模板，而是防止回答漏掉关键约束的思考工具。

## 2. 如何部署一个 70B 模型

### 2.1 先把“70B”翻译成资源问题

70B 只表示大约 700 亿个参数，不直接告诉我们模型需要几张卡。第一步是确认：

- 权重使用 FP16、BF16、INT8 还是 INT4；
- 是否有 scale、zero-point、group metadata 和 runtime 对齐开销；
- 上下文窗口是多少，平均和 P99 输入输出 token 是多少；
- 目标是单用户低延迟、批处理吞吐，还是多租户在线服务；
- GPU 显存、GPU 间互联和跨节点网络是什么；
- 是否需要 LoRA adapter、视觉编码器、工具 schema 或 RAG。

权重的下界可以用：

~~~math
M_{\mathrm{weight}}
\approx
N_{\mathrm{param}}\frac{b_w}{8}
~~~

`N_param` 是参数数量，`b_w` 是每个参数的 bit 数。70B FP16 的十进制字节数约为
`70×10^9×16/8=140×10^9`，换算为 GiB 约为 130.4；70B INT4 的理论权重下界
约为 32.6 GiB。两者都没有计入 KV Cache、激活、通信 buffer、量化元数据和显存
余量，因此不能把 130.4 GiB 或 32.6 GiB 当成整机需求。

对小白来说，权重像“把模型搬进显存的固定房租”，KV Cache 像“每个正在处理的
住户都要占用的动态空间”。模型越大，固定房租越高；上下文越长、并发越高，动态
空间越容易成为真正限制。

### 2.2 决定并行还是量化

如果 FP16 权重无法放进一张 GPU，可以选择：

1. **Tensor Parallel**：把层内矩阵和 attention 计算切到多张 GPU，适合需要共同
   完成一个请求的模型副本，但每次迭代都有 collective communication。
2. **Pipeline Parallel**：把连续层分到不同阶段，适合模型很深或显存需要分段的
   情况；微批、流水线气泡和跨阶段调度会影响在线延迟。
3. **量化**：降低权重存储和带宽，可能让模型用更少的 GPU，但需要校准、kernel 和
   任务质量验证。
4. **混合方案**：例如量化权重加多 GPU，或不同模型池使用不同精度。

TP 的 GPU 数不能只根据“140GB 除以 80GB”做整除。还要留出 KV 和 runtime 空间，
并确认模型的 attention、MLP、embedding、输出头和通信实现支持目标切分。一个
理论上能够加载的配置，可能在第一个长请求到来时因为 KV 没有空间而失败。

### 2.3 用吞吐和并发决定副本数

设某类请求到达率为 `λ`，输入输出 token 分别为 `P`、`O`，每个任务包含 `s` 次
模型调用，则：

~~~math
R_{\mathrm{in}}=\lambda sP,
\qquad
R_{\mathrm{out}}=\lambda sO
~~~

如果前缀只复用输入的比例 `h`，把输入需求改成 `λsP(1-h)`，但要确认 cache
lookup、哈希、权限检查和缓存维护的成本仍然存在。

若单副本实测 prefill 吞吐是 `U_in`，decode 吞吐是 `U_out`，活跃序列容量是 `S`，
初始副本数可以估算为：

~~~math
n
=
\left\lceil
\gamma\max\left(
\frac{R_{\mathrm{in}}}{U_{\mathrm{in}}},
\frac{R_{\mathrm{out}}}{U_{\mathrm{out}}},
\frac{A}{S}
\right)
\right\rceil
~~~

`A≈λL` 是平均活跃请求数，`L` 是请求在系统内停留的时间。`γ` 需要覆盖峰值波动、
故障和发布余量。对 70B 服务，通常 decode 或 KV 会先达到压力边界，但长 RAG 的
输入也可能先把 prefill 推满，不能只凭模型参数量猜瓶颈。

### 2.4 一个完整的示范性回答

“我不会直接给出‘8 张卡’这样的固定答案。先确认上下文、QPS、输入输出分布、
流式要求、GPU 型号、互联拓扑和质量底线。然后分别计算权重、KV、prefill 和
decode 的资源需求。70B FP16 权重约 140GB 十进制字节，实际需要更多显存；若
单卡放不下，就在 TP、PP、量化或混合方案中选择。对于线上服务，我会用目标硬件
测出单副本的输入/输出 token 吞吐和活跃序列容量，再按峰值和故障余量计算副本。
调度层限制上下文、输出、并发和 KV，推理引擎负责 continuous batching、KV 管理、
解码和多 GPU。最后用 TTFT、TPOT、P95/P99、OOM、质量切片、安全样本、成本和
回滚 manifest 做发布验证。这样回答的是一个 workload 下的部署方案，不把某个
模型的静态显存数字冒充完整容量结论。”

### 2.5 继续追问：为什么不全用 INT4

INT4 可能明显降低权重显存，但质量退化不是均匀的。代码、数学、少数语言、长
上下文和工具参数等切片可能比普通闲聊更敏感；某些硬件没有高效的 INT4 kernel，
理论带宽节省也可能无法转化为实际 TPOT 改善。正确的回答应回到目标任务回放：
比较质量、结构化正确率、拒答、TTFT、TPOT、显存、吞吐和单位成功任务成本，而
不是只比较模型文件大小。

## 3. 如何降低首 token 延迟

### 3.1 TTFT 到底测了什么

TTFT 是从服务接受请求到用户收到第一个可展示 token 的时间。它不等于模型生成
完整答案的时间，也不等于纯 GPU prefill 时间。可以写成近似分解：

~~~math
T_{\mathrm{TTFT}}
=
T_{\mathrm{gateway}}
+T_{\mathrm{queue}}
+T_{\mathrm{route}}
+T_{\mathrm{context}}
+T_{\mathrm{prefill}}
+T_{\mathrm{first\_decode}}
+T_{\mathrm{flush}}
~~~

其中 `T_context` 可能包含 RAG、工具前置检查、OCR 或视觉编码，`T_flush` 是
代理、网关和客户端把首个事件真正传给用户的时间。若把这些阶段都记在 model
latency 里，模型团队和平台团队会互相误判；若完全不记，又无法解释用户体验。

### 3.2 按 trace 排查，而不是先改参数

TTFT 升高时，先比较正常样本和慢样本的每个 span：

1. Gateway 和身份检查是否出现排队。
2. Router 是否因为健康检查或 cache 亲和性把请求集中到少数副本。
3. `T_queue` 是否随 active sequence 或 KV 水位一起增长。
4. `T_context` 是否因历史、RAG 证据、工具 schema 或媒体 token 变长。
5. Prefill batch 是否等待更多请求，或者长输入阻塞了短输入。
6. 首 token 生成后是否被代理缓冲，导致 GPU 已经完成但用户还没收到。

只有定位到阶段，优化才有方向。队列导致的 TTFT 不应靠改 temperature 修复；
代理缓冲导致的 TTFT 不应靠量化模型修复。

### 3.3 常见优化和副作用

**减少输入**：去重历史、压缩检索证据、缩短工具 schema 可以降低 prefill，但必须
保留条件、来源、权限和例外，否则质量和安全会退化。

**复用前缀**：system prompt、固定工具说明和共享文档前缀适合 prefix cache。它
减少的是可复用前缀的 prefill，仍要支付 cache 查找、权限检查和剩余输入计算。

**分离队列**：短请求和长请求分池或分优先级，通常可以改善短请求 P95，但低优先级
长请求可能等待更久，需要 aging 或异步转换。

**并行外部步骤**：互不依赖的 embedding、权限查询、检索和安全预检可以并行；但
并行会增加下游峰值并发，必须同时检查数据库、向量库和审核服务的容量。

**流式传输**：尽早发送首个 token 改善感知延迟，却不会减少完整答案时间；如果
首 token 只是无意义的占位文本，用户体验和任务成功率未必真的改善。

### 3.4 一个适合追问的边界

如果 TTFT 降了，但完整响应时间、引用支持或安全审核延迟上升，不能把优化称为
整体成功。应该同时报告 TTFT、TPOT、端到端时间、取消率和任务指标。在线服务还
应按缓存命中和 miss 分层，因为大量命中样本可能让总体 TTFT 看起来很好，却掩盖
了冷请求无法达到目标的问题。

## 4. 如何提高吞吐

### 4.1 先区分 prefill 和 decode

Prefill 一次处理整段输入，矩阵计算密集，长 prompt、RAG evidence、工具 schema
和多模态 token 会增加它的工作量。Decode 一次通常生成一个或少量 token，需要反复
读取权重和 KV Cache，常受显存带宽、batch 形态和调度影响。

输入输出 token 吞吐为：

~~~math
R_{\mathrm{in}}=\sum_j\lambda_j s_jP_j,
\qquad
R_{\mathrm{out}}=\sum_j\lambda_j s_jO_j
~~~

一个服务可能 prefill 很空闲但 decode 饱和，也可能因为长上下文使 prefill 先饱和。
只报“每秒处理多少请求”无法解释这两种情况。

### 4.2 Continuous batching 为什么有效

静态 batch 要等一批请求都准备好，并且通常按最长序列的形状分配计算；生成长度
不同的请求会产生 padding、空转或等待。Continuous batching 在生成循环中允许
完成的请求离开、等待的请求加入，调度器按 token 和 KV 预算重新安排执行。

它不是免费加速：调度器更复杂，短请求公平性、chunked prefill、抢占、取消、优先级
和流式事件都需要定义。若 batch 中混入极长 prompt，短请求仍可能在 prefill 阶段
被拖慢，因此还需要 chunked prefill 或长短请求分队列。

### 4.3 其他吞吐手段的取舍

- Prefix cache 减少重复 prefill，适合共享 system prompt 或长文档前缀，但会占用
  cache 空间并要求严格版本、租户和权限隔离。
- Paged KV Cache 减少动态分配的碎片，让更多活跃序列共存，但不改变 attention
  的理论计算量，也不自动解决 decode 带宽瓶颈。
- Speculative decoding 用 draft model 提议多个 token，再由 target model 验证；
  接受率、draft 开销和实现 kernel 决定真实收益，低接受率 workload 可能没有加速。
- 量化降低权重带宽和显存，蒸馏降低模型规模；两者都必须做任务切片质量验证。
- 多副本提高总吞吐，但会复制权重和 warm cache，增加 GPU、发布和跨副本路由成本。

### 4.4 吞吐指标应和失败率一起看

如果系统通过截断输出、丢弃超时请求或增加拒答来提高 output tokens/s，单纯的吞吐
指标会奖励错误优化。至少应同时报告 input tokens/s、output tokens/s、TTFT、TPOT、
P95/P99、成功率、超时率、取消率和单位成功任务成本。

## 5. KV Cache 为什么占显存，如何优化

### 5.1 从重复计算理解 KV Cache

自回归模型在生成第 `t` 个 token 时，需要让新 query 与历史 token 的 key/value
交互。如果每一步都重新计算完整历史，计算量和延迟会不断增长。KV Cache 把已经
计算过的 K、V 保存下来，下一步只计算新 token 的 K、V，并读取历史状态。

对 `L` 层、`B` 个活跃序列、平均上下文 token 数 `T`、`H_kv` 个 KV head、head
维度 `D_h`、每元素 `b` 字节，可以做近似显存估算：

~~~math
M_{\mathrm{kv}}
\approx
2LBTH_{\mathrm{kv}}D_hb
~~~

`2` 是 K/V 两份状态。这个式子解释了为什么长上下文和并发会共同放大 KV 显存，
也解释了 GQA/MQA 通过减少 `H_kv` 能降低状态大小。模型权重是相对固定的，KV
则随活跃请求增长和释放，是线上容量的动态部分。

### 5.2 优化方法不是同一种交换

1. 限制最大输入和输出：最直接，但可能伤害长文档任务。
2. GQA/MQA：从模型架构层减少 KV head，通常需要模型本身支持。
3. Paged KV Cache：减少碎片和过度预留，不会改变每个 token 的理论状态大小。
4. KV 量化：减少每个元素的字节数，需验证注意力数值误差和长上下文质量。
5. Prefix cache：复用共享前缀，减少重复 prefill，但会额外占用可管理的缓存空间。
6. 抢占和重算：把低优先级请求的 KV 释放，之后重新 prefill；节省显存但增加延迟
   和计算成本。

专家回答时还要补一句：KV Cache 的理论字节数不等于 runtime 的实际分配。block
大小、对齐、KV dtype、碎片、跨 GPU 分片和 allocator 行为都可能改变结果，最终要
用 runtime 指标和长短请求混合压测确认。

## 6. PagedAttention 解决了什么问题

### 6.1 先说明它没有改变什么

PagedAttention 主要改变 KV Cache 的内存组织方式，不是提出一种新的 attention
概率公式。朴素实现常按请求最大长度预留连续空间；真实请求的长度不同、完成时间
不同，连续预留会产生内部碎片和未使用空间，动态 batch 越大越明显。

PagedAttention 将 KV Cache 分成固定大小的 block，并用逻辑 block 到物理 block 的
映射管理状态。一个序列可以由多个物理 block 拼成，完成或被抢占时，runtime 可以
回收相应 block。这样把“逻辑序列长度”和“物理显存位置”分开。

### 6.2 为什么它适合 serving

在线生成有三个特点：请求长度不可完全预知、请求会在不同时间结束、多个请求需要
动态加入和离开 batch。按 block 分配可以减少按最大长度连续预留带来的浪费，也让
共享前缀、copy-on-write、抢占和重算有更清楚的内存操作单位。

但它不是所有吞吐问题的答案：

- 如果瓶颈是模型计算或 decode 带宽，分页只改善内存管理；
- block 太小会增加映射和管理开销，太大又会增加内部浪费；
- prefix sharing 仍需处理版本、租户和权限；
- 高并发下 block 仍然可能耗尽，需要队列预算和反压。

### 6.3 一段完整的回答

“我会先区分 attention 算法和 KV Cache 管理。自回归 decode 需要保存历史 K/V，
如果每个请求按最大长度预留连续显存，就会在变长、高并发和动态 batch 下产生碎片
和浪费。PagedAttention 把 KV 分成 block，通过逻辑到物理的映射按需分配和释放，
因此更适合 serving；它可以提高 KV 的利用率，并为共享前缀、抢占和重算提供管理
基础，但不改变 attention 的数学复杂度，也不保证任何 workload 都自动提速。实际
收益要看 block 配置、KV dtype、请求长度分布、runtime 和目标硬件。”

## 7. 如何选择 INT8 和 INT4 量化

### 7.1 先区分量化对象

“INT8 还是 INT4”是不完整的问题。至少要区分：

- weight-only quantization：主要压缩权重，activation 保持较高精度；
- weight-activation quantization：权重和激活都量化，可能获得更大计算收益，但
  对校准和 kernel 要求更高；
- KV Cache quantization：压缩动态状态，直接影响长上下文和并发；
- 混合精度：对敏感层、输出头或特定通道保留更高精度。

每种方式的误差位置、kernel 支持和部署代价不同。不能拿一个 weight-only INT4
的显存数字去推断 activation 和 KV 都是 INT4。

### 7.2 精度、硬件和质量的三角取舍

量化可以把每参数存储从 16 bit 降到 8 或 4 bit，但真实存储还包含 scale、group
metadata、padding 和 runtime buffer。理论权重节省不等于实际延迟下降，因为硬件
可能需要反量化，或缺少适合该模型形状的高效 kernel。

INT8 通常更容易保持通用能力，适合对质量风险敏感的服务；INT4 的压缩力度更强，
适合显存紧张或吞吐优先的场景，但代码、数学、长上下文、多语言、工具参数和拒答
行为都可能出现切片退化。这个“通常”不是保证，必须由目标模型回放验证。

### 7.3 一套可辩护的选择方式

假设有 FP16 基线、INT8 候选和 INT4 候选，至少测量：

1. 显存峰值和可承载 active sequence。
2. TTFT、TPOT、P95/P99 和 output tokens/s。
3. 普通问答、代码、数学、长上下文、多语言和结构化输出质量。
4. RAG 引用支持、工具参数正确率和安全样本。
5. 量化校准时间、部署复杂度和回滚成本。

最后比较的是成功任务成本，而不是单次 token 价格：

~~~math
C_{\mathrm{success}}
=
\frac{C_{\mathrm{model}}+C_{\mathrm{retry}}+C_{\mathrm{fallback}}+C_{\mathrm{human}}}
{N_{\mathrm{success}}}
~~~

如果 INT4 使单次调用便宜 60%，却让失败重试和人工升级增加 30%，应把这些成本
放回同一账本。对高风险工具，质量和安全回归比几张 GPU 的节省更重要。

## 8. 如何设计高并发 ChatGPT 类服务

### 8.1 先写请求的路径

一个可扩展的在线聊天服务可以这样组织：

~~~text
client
  -> API Gateway
  -> identity / tenant quota
  -> request router
  -> prompt and context builder
  -> response/prefix cache
  -> scheduler / inference runtime
  -> streaming protocol
  -> safety, trace, billing and evaluation sample
~~~

如果加入 RAG，检索和重排位于 context builder 内；如果加入 Agent，工具执行要有
独立的权限和状态边界；如果加入图片、音频或视频，文件接入和预处理最好与低延迟
文本池分离。

### 8.2 容量要按混合 workload 计算

设第 `j` 类请求的 QPS 为 `λ_j`，输入输出 token 为 `P_j`、`O_j`，模型调用步数
为 `s_j`，则：

~~~math
R_{\mathrm{in}}=\sum_j\lambda_js_jP_j,
\qquad
R_{\mathrm{out}}=\sum_j\lambda_js_jO_j
~~~

活跃请求可以用 `A_j≈λ_jL_j` 做第一版估算。若服务有长 Agent，`L_j` 会很大；
它可能只占很小 QPS，却占用连接、状态和调度槽。副本估算还要加入 prefill、decode、
active sequence 和故障余量，不能只按 QPS 做 round-robin。

### 8.3 流式服务的特别问题

流式输出要考虑：

- 网关和代理是否会缓冲 chunk；
- 客户端消费慢时是否形成 backpressure；
- 取消请求能否释放 KV 和调度槽；
- tool call 增量和文本增量是否有稳定事件顺序；
- 断线后是重试、恢复还是返回已完成的 job；
- usage、finish reason 和错误能否被客户端可靠解析。

为了降低首 token 延迟而提前发送空白或无意义文本，可能只改善了一个计时指标，
却没有改善用户完成任务的时间。因此 TTFT 必须和完整响应时间、用户取消率和任务
成功率一起看。

### 8.4 一个完整的系统回答

“我会先澄清聊天请求的同步/流式比例、QPS、输入输出 token 分布、上下文长度、
质量和安全要求。入口层负责身份、租户、请求大小、token/并发配额、超时和 request
id；路由层按任务能力、区域和副本负载选择模型；上下文层负责 chat template、历史
裁剪、RAG、工具 schema 和 token budget；缓存层区分 response cache 和 prefix/KV
cache；推理层负责 continuous batching、KV 管理、解码、量化和多 GPU；流式协议
处理背压、取消、断线和用量事件。容量上分开 prefill、decode、active sequence
和 KV 显存估算，部署多副本并保留 N+1 余量。上线前用回放、shadow 和 canary 比较
TTFT、TPOT、P99、任务质量、安全和成功成本，并把模型、模板、索引和策略绑定为
可回滚版本。”

这段回答的价值不在于组件数量，而在于每个组件都和一个可测量问题相连。

## 9. 如何部署 RAG 系统

### 9.1 离线链路决定在线上限

RAG 的线上检索只是最后一步。离线链路包括文档解析、规范化、结构感知切分、
metadata、权限标签、embedding、索引构建和版本发布。切分时如果把标题、表格
条件和脚注拆开，向量召回即使命中了片段，模型也可能无法理解适用范围。

每个 chunk 至少应能追溯到：

~~~text
document_id
document_version
chunk_id
source_location
acl_scope
embedding_model_version
index_version
~~~

索引迁移要支持旧版本和新版本短暂共存。新 embedding 模型改变向量空间，不能把
新旧向量混在一个索引里然后只修改配置名；否则召回质量和线上回滚都无法解释。

### 9.2 在线链路和上下文预算

在线路径通常是 query rewrite、hybrid retrieval、reranker、context builder、
生成和引用检查。证据数量受上下文预算约束：

~~~math
T_{\mathrm{evidence}}
\le
T_{\mathrm{window}}
-T_{\mathrm{system}}
-T_{\mathrm{history}}
-T_{\mathrm{query}}
-T_{\mathrm{tool}}
-T_{\mathrm{output}}
~~~

更多证据不必然带来更高质量。无关片段会增加 prefill 成本和噪声，冲突片段会让
模型难以判断版本和优先级。应该在固定问题集上同时比较 Recall@k、引用支持、
unsupported claim、输入 token、延迟和单位成功成本。

### 9.3 一段完整的回答

“我会把 RAG 拆成离线和在线两条链路。离线负责文档解析、结构化切分、权限元数据、
embedding、索引版本和回滚；在线先做身份和 ACL 过滤，再召回、混合检索、低置信
度时 rerank，最后按 token budget 组装证据并生成。每条证据带文档版本和位置，输出
后检查关键 claim 是否有支持。检索文档属于不可信外部内容，不能直接改变 system
指令或工具权限。延迟要拆 retrieval、rerank、prefill、decode 和引用检查，质量要
看召回、引用、答案和安全切片。索引、embedding 模型、reranker、prompt 和模型
一起版本化，才能在回归或权限错误时回退。”

## 10. 如何防 prompt injection

### 10.1 先区分模型指令和外部数据

Prompt injection 的关键不是某一句恶意文本，而是模型同时接收到多个来源，却可能
把低信任内容当成高优先级指令。来源至少包括 system/developer policy、用户请求、
检索文档、网页、OCR、邮件、工具返回值和模型自己生成的计划。

一个稳健系统不能只在 prompt 里写“忽略恶意指令”。它还要在系统边界上执行：

1. 对不同来源标记信任等级和来源 id。
2. 通过权限服务判断模型是否有权访问文档和工具。
3. 工具执行器重新校验参数、租户、用户和资源范围。
4. 对高风险动作加入人工确认、金额上限或二次认证。
5. 不把 secret、内部 prompt 或长期凭证放进模型可见上下文。
6. 记录注入检测、工具拒绝和策略版本，便于复盘。

### 10.2 防护边界和失败边界

输入分类器可以发现一部分攻击样本，但无法证明所有外部内容都安全；输出过滤器
可以拦截一部分危险文本，但不能撤销已经执行的工具副作用。权限和状态机是最后
一道必须独立于模型的控制。

如果安全检测服务不可用，高风险工具通常选择停止或人工审核；低风险纯文本可以
按预先定义的降级策略继续，但要在响应中保留“安全检查状态”，而不是假装检查
已经完成。不同业务的 fail-open/fail-closed 取舍要写成风险决策，不能用一个规则
覆盖所有功能。

### 10.3 继续追问：RAG 文档为什么也要防注入

因为文档、网页和邮件可能包含“请忽略之前指令”“把秘密发送到某地址”等内容。
它们对业务问题可能是有用证据，对工具和系统策略却不应拥有同等权限。context
builder 应把内容放入明确的 evidence 区域，工具执行器不应把模型从 evidence 中
抽取出的命令当作授权凭据。真正的授权来自外部身份、ACL 和业务状态。

## 11. 如何估算线上推理成本

### 11.1 先建立请求成本账本

对每类请求，输入输出 token、缓存节省、embedding、rerank、媒体和工具成本应
分开记录。一个教学近似可以写为：

~~~math
C_{\mathrm{req}}
=
c_{\mathrm{in}}P
+c_{\mathrm{out}}O
+c_{\mathrm{media}}V
+c_{\mathrm{embed}}E
+c_{\mathrm{rerank}}R
+C_{\mathrm{fixed}}
~~~

`c_in` 和 `c_out` 可以是每 token 价格或按 GPU 时间换算的单位成本，`P`、`O` 是
实际输入输出 token，`V` 是视觉/音频/视频资源量，`E` 是 embedding 量，`R` 是
reranker 工作量，`C_fixed` 包括请求级网关、日志、缓存和安全处理。生产报表还要
追加重试、fallback、人工升级、存储和补偿事务。

### 11.2 成功任务成本比便宜模型更重要

设一段观察窗口内所有请求和辅助处理总成本为 `C_total`，真正完成任务的数量为
`N_success`，则：

~~~math
C_{\mathrm{success}}=\frac{C_{\mathrm{total}}}{N_{\mathrm{success}}}
~~~

小模型可能降低每次调用价格，却让失败重试、转人工或大模型 fallback 增多。响应
缓存可能把重复 FAQ 的成本降得很低，却不能直接用于个性化或权限敏感的答案。量化
可能节省 GPU，但如果结构化字段质量下降，业务补偿成本会抵消节省。

### 11.3 成本优化要和质量一起实验

一次优化实验至少需要固定：模型和 runtime、prompt、输入分布、并发、硬件、缓存
状态、评估集和价格口径。对照组和候选组同时记录：

- 每请求和每成功任务成本；
- input/output tokens、缓存节省和辅助模型调用；
- TTFT、TPOT、P95/P99、超时和取消；
- 任务、引用、结构化输出和用户反馈；
- 安全漏放、误拦和工具副作用。

如果成本下降来自更早拒答或排除慢请求，就不能把它当作服务变好了；要把拒答、
人工升级和失败任务留在分母和账本中。

## 12. 一个跨题目的生产故障追问

面试官可能把前面的题合在一起：“你部署的高并发服务 P99 突然升高，质量暂时看
不出问题，你怎么处理？”

一个可解释的排查过程如下：

1. 先确认指标口径、时间窗口和最近发布，避免把统计变化误认为系统变化。
2. 按模型池、租户、请求类型、缓存命中、输入/输出长度拆分 P99。
3. 从 trace 查看 queue、router、context、prefill、decode、外部依赖和流式发送。
4. 如果 queue 变长，检查 QPS、token 吞吐、active sequence、KV 水位和调度公平。
5. 如果 prefill 变长，检查 RAG 证据、历史、工具 schema、媒体 token 和 cache miss。
6. 如果 decode 变长，检查输出长度、batch、KV 带宽、量化 kernel 和多 GPU 通信。
7. 如果外部依赖变慢，启用符合业务风险的降级、熔断或异步化，不绕过权限和安全。
8. 如果与候选发布相关，停止扩大 canary，保存现场 trace，恢复上一份 manifest。
9. 事后用固定回放和故障样本复现，并把修复加入长期评估和 runbook。

这段过程体现了部署工程师的判断力：先定位资源阶段，再选择局部动作；先保护
用户和外部状态，再追求恢复吞吐；先保存证据，再下结论。

## 13. 最小可运行的部署面试诊断示例

下面的示例同时做资源计算和回答覆盖检查，但不会把结果压成一个不可解释的总分。
`rubric` 表示每个问题需要讨论的主题，`candidate` 是一份故意漏掉一个维度的
示例回答。程序分别输出覆盖率、缺失主题、公式估算、容量余量、成本敏感性和安全
边界信号，帮助读者知道下一步应该补哪里。

~~~python
import math
from pprint import pprint


def gib(bytes_value):
    return round(bytes_value / (1024 ** 3), 2)


def weight_gib(params_billion, bits):
    bytes_value = params_billion * 1_000_000_000 * bits / 8
    return gib(bytes_value)


def kv_cache_gib(layers, batch, tokens, kv_heads, head_dim, bytes_per_value):
    total = 2 * layers * batch * tokens * kv_heads * head_dim * bytes_per_value
    return gib(total)


def required_replicas(
    qps,
    prompt_tokens,
    output_tokens,
    prefill_tps,
    decode_tps,
    cache_saved=0.0,
    headroom=1.0,
):
    input_need = qps * prompt_tokens * (1 - cache_saved)
    output_need = qps * output_tokens
    ratios = [input_need / prefill_tps, output_need / decode_tps]
    base = math.ceil(headroom * max(ratios))
    return {
        "input_need": round(input_need),
        "output_need": round(output_need),
        "base_replicas": max(1, base),
        "nplus1_replicas": max(1, base) + 1,
    }


def hourly_cost(
    qps,
    prompt_tokens,
    output_tokens,
    price_in,
    price_out,
    cache_saved=0.0,
):
    effective_prompt = prompt_tokens * (1 - cache_saved)
    per_request = (
        effective_prompt / 1000 * price_in
        + output_tokens / 1000 * price_out
    )
    return round(per_request * qps * 3600, 2)


rubric = {
    "70b_deploy": {
        "memory",
        "parallel",
        "quant",
        "kv_cache",
        "engine",
        "monitoring",
        "rollback",
    },
    "ttft": {
        "queue",
        "prefill",
        "prefix_cache",
        "prompt_length",
        "rag_tools",
        "streaming",
    },
    "throughput": {
        "continuous_batching",
        "decode_tps",
        "kv_budget",
        "replicas",
        "routing",
    },
    "kv_cache": {"formula", "gqa_mqa", "paged", "long_context", "eviction"},
    "rag": {
        "offline_index",
        "retrieval",
        "rerank",
        "context_budget",
        "citation",
        "injection",
    },
    "safety": {
        "untrusted_content",
        "tool_permission",
        "input_output_filter",
        "logging",
    },
    "cost": {
        "token_accounting",
        "model_routing",
        "cache",
        "quantization",
        "autoscaling",
    },
}

candidate = {
    question: set(required)
    for question, required in rubric.items()
}
candidate["throughput"].remove("kv_budget")

coverage = {}
missing = {}
for question, required in rubric.items():
    hit = candidate.get(question, set()) & required
    coverage[question] = round(len(hit) / len(required), 3)
    gap = sorted(required - candidate.get(question, set()))
    if gap:
        missing[question] = gap

formula_checks = {
    "fp16_weight_gib_70b": weight_gib(70, 16),
    "int4_weight_gib_70b": weight_gib(70, 4),
    "kv_cache_gib": kv_cache_gib(80, 16, 4096, 8, 128, 2),
}
capacity = required_replicas(
    qps=60,
    prompt_tokens=1500,
    output_tokens=200,
    prefill_tps=80000,
    decode_tps=2500,
    cache_saved=0.25,
    headroom=1.2,
)
cost_baseline = hourly_cost(60, 1500, 200, 0.003, 0.010)
cost_cached = hourly_cost(60, 1500, 200, 0.003, 0.010, cache_saved=0.25)

signals = {
    "answer_coverage_floor": min(coverage.values()) >= 0.85,
    "nplus1_capacity_is_visible": capacity["nplus1_replicas"] > capacity["base_replicas"],
    "cost_sensitivity_is_visible": cost_cached < cost_baseline,
    "safety_boundary_is_visible": len(candidate["safety"]) >= 4,
}

actions = []
for question, topics in missing.items():
    actions.append(f"expand_answer:{question}:{','.join(topics)}")
if not signals["nplus1_capacity_is_visible"]:
    actions.append("explain_failure_capacity")
if not signals["cost_sensitivity_is_visible"]:
    actions.append("explain_cost_accounting")

decision = "continue_practice" if not actions else "rewrite_weak_sections"
summary = {
    "coverage": coverage,
    "missing": missing,
    "formula_checks": formula_checks,
    "capacity": capacity,
    "hourly_cost_baseline": cost_baseline,
    "hourly_cost_cached": cost_cached,
    "cost_saving_rate": round(1 - cost_cached / cost_baseline, 3),
    "signals": signals,
    "actions": actions,
    "decision": decision,
}
pprint(summary, sort_dicts=False)
~~~

 'missing': {'throughput': ['kv_budget']},

这里的 `decision` 只是这个练习程序对样例回答的诊断，不是对候选人的总评分。
它指出吞吐回答缺少 `kv_budget`，但并不说明读者完全不会吞吐；读者还要回到正文，
把 batch、KV、输入输出 token、长短请求和失败率之间的关系补成自己的叙述。真实
面试中也应保留这种具体缺口，而不是只说“整体回答 80 分”。

## 14. 常见误区和追问边界

### 14.1 只报“几张 GPU”

GPU 数量必须由权重、KV、吞吐、并发、拓扑、故障余量和成本共同推导。换模型精度、
上下文或请求分布后，答案可能完全不同。

### 14.2 把 TTFT 和 TPOT 混为一个延迟

TTFT 更容易受排队、输入长度和 prefill 影响，TPOT 更容易受 decode、KV 读取、
batch 和输出长度影响。优化一个不一定改善另一个，必须按 trace 和分位数拆开。

### 14.3 把 PagedAttention 说成新的 attention 算法

它主要是 KV Cache 的分页式内存管理。它可以减少碎片和过度预留，但不改变模型
注意力公式，也不自动解决算力、带宽、权限和队列问题。

### 14.4 把缓存命中率当成质量和成本结论

response cache、prefix cache、embedding cache 和媒体缓存的复用对象不同。要同时
检查版本、权限、TTL、实际节省 token 和任务成功率。

### 14.5 把安全写成“加一个过滤器”

输入、外部文档、工具参数、工具结果、输出流和审计需要不同控制。模型拒绝文字
不能撤销已经发生的业务副作用。

### 14.6 把 demo 的教学参数当成生产 benchmark

代码中的 prefill/decode 吞吐、价格和线性延迟只用于演示计算。生产决策需要目标
模型、硬件、runtime、输入输出分布、缓存状态、故障样本和质量评估。

## 15. 资料与证据边界

本章的回答组织方式来自部署工程中的通用问题；公式是容量和成本的近似表达；框架
能力和指标名称以对应版本的官方资料为准；真实性能、质量和安全结论必须由目标
workload 的回放、压测、故障注入和线上观察支持。

1. [PagedAttention 论文](https://arxiv.org/abs/2309.06180)：解释分页式 KV Cache 管理的研究背景；论文 benchmark 不能直接替代目标硬件压测。
2. [vLLM Metrics](https://docs.vllm.ai/en/latest/usage/metrics.html)：确认当前 vLLM 监控指标入口；具体指标含义要随版本核对。
3. [vLLM Online Serving](https://docs.vllm.ai/en/latest/serving/online_serving.html)：确认在线服务和 API 入口；不代表所有模型都具备相同性能。
4. [vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html)：说明前缀缓存的实现边界和适用条件。
5. [Hugging Face KV Cache](https://huggingface.co/docs/transformers/en/kv_cache)：说明 Transformers 中 KV Cache 的接口和实现概念；本地 serving runtime 可能有不同布局。
6. [Hugging Face Text Generation](https://huggingface.co/docs/transformers/en/main_classes/text_generation)：确认生成参数、cache 和 generation config 的接口语义。
7. [TensorRT-LLM](https://nvidia.github.io/TensorRT-LLM/)：NVIDIA 官方推理优化与 serving 资料入口；kernel 和硬件支持必须实测。
8. [TensorRT-LLM GPT Attention](https://nvidia.github.io/TensorRT-LLM/advanced/gpt-attention.html)：说明 paged KV、in-flight batching 等实现方向。
9. [OpenAI Production Best Practices](https://platform.openai.com/docs/guides/production-best-practices)：生产服务运维与可靠性资料；供应商 API 规则不能直接泛化到自建服务。
10. [OpenAI Latency Optimization](https://platform.openai.com/docs/guides/latency-optimization)：延迟分解和优化入口；收益取决于请求分布。
11. [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)：供应商 prompt caching 语义；不等于本地 prefix/KV cache。
12. [Kubernetes Horizontal Pod Autoscaler](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)：通用扩缩容机制；LLM 还要接入 token、队列和 KV 信号。
13. [OpenTelemetry Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)：日志、指标和 trace 的可观测性基础。
14. [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)：LLM 应用威胁线索；不能替代业务级权限和工具威胁建模。
15. [Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401)：RAG 基础论文；召回、引用和生成质量需在目标数据上复现。
16. [OpenAI Evals](https://github.com/openai/evals)：评估框架和样例入口；业务质量标准仍需自己定义。

## 16. 本章小结

部署面试题的答案不应是框架名词的堆叠，而应是一条可以被检查的工程推理链：

1. 先说明 workload、QPS、token 分布、流式/异步、SLO、质量和安全边界。
2. 用权重、KV、prefill、decode、active sequence、并行和故障余量估算资源。
3. 解释 TTFT 和 TPOT 的不同来源，分别讨论队列、prefill、decode、网络和外部依赖。
4. 把 PagedAttention、continuous batching、prefix cache、量化和模型路由放回它们
   真正解决的资源问题，不夸大单项技术的效果。
5. 对 RAG、Agent 和多模态任务说明索引、证据、权限、工具副作用、异步状态和媒体
   预算。
6. 用 trace、分层评估、成本账本、灰度和 manifest 回滚说明系统如何持续运行。
7. 遇到追问时，先定位阶段和责任边界，再给局部修复，同时说出可能的副作用。

如果读者能把“70B 部署”“TTFT 变慢”“KV 显存不足”“RAG 不可用”和“成本超支”
看成同一条生产请求链上的不同问题，就已经从背答案进入了系统设计。面试中的
表达只是这种理解的外显形式，真正可迁移的是资源模型、故障模型和证据意识。
