# 第二章 推理基础：一个 token 如何生成，以及性能数字从哪里来

把一个大模型部署成服务，最容易的部分是让它返回一段文本，最难的部分是解释这段文本为什么在这个时间返回、为什么换一类请求就变慢，以及一个优化到底改善了什么。只调用一次 `generate`，只能证明一条前向路径可以执行；它不能说明并发、长上下文、流式输出和尾延迟下的行为。

初学者可以先把一次推理想成两段工作。第一段把用户已经输入的内容读完，建立后续生成所需的状态；第二段每次只决定一个新的 token，再把这个 token 接到上下文末尾，重复这个过程。第一段通常叫 prefill，第二段通常叫 decode。专家则需要再往下拆：请求是否在队列中等待，输入是否命中前缀缓存，prefill 和 decode 是否争用同一批 GPU，KV Cache 读写了多少字节，量化和并行改变了哪一项，以及指标的计时起点和分位数定义是什么。

本章建立这些概念之间的因果关系。第 3 章会专门展开 KV Cache 的布局、分页和内存回收，第 4 章讨论采样与生成控制，第 6 章讨论批处理和调度；这里先回答它们共同依赖的基础问题：模型如何生成，推理为什么有两个阶段，如何计算延迟和吞吐，以及怎样从 trace 判断瓶颈。

## 2.1 推理到底在计算什么

### 2.1.1 从条件概率到逐 token 生成

给定输入 token 序列

~~~math
x=(x_1,x_2,\ldots,x_{T_{\mathrm{in}}}),
~~~

模型要生成输出序列

~~~math
y=(y_1,y_2,\ldots,y_{N_{\mathrm{out}}}).
~~~

自回归模型把整个输出序列的条件概率分解为：

~~~math
P(y\mid x)=
\prod_{t=1}^{N_{mathrm{out}}}
P(y_t\mid x,y_{<t}).
~~~

`y_<t` 表示已经生成的前 `t-1` 个 token。模型在第 `t` 步接收当前上下文，输出词表上的 logits `z_t`，再由生成策略把 logits 变成下一个 token：

~~~math
z_t=f_\theta(x,y_{<t}),qquad
p_t=\operatorname{softmax}(z_t),qquad
y_t\sim p_t.
~~~

这里的 `f_\theta` 是参数为 `theta` 的模型前向计算，`p_t` 是词表上的概率分布。greedy 取最大概率 token，temperature 改变分布的尖锐程度，top-k 和 top-p 缩小候选集合；这些是对同一个 `p_t` 的不同决策方式，而不是改变 Transformer 主干计算的两个阶段。采样细节放在第 4 章，本章只保留理解计时所需的抽象。

这条概率分解带来一个非常重要的事实：输出 token 之间存在顺序依赖。第 `t+1` 步必须知道第 `t` 步选了什么，因此单个请求的输出不能像训练时那样一次性并行得到。服务可以同时处理很多请求，但不能把同一个请求尚未生成的未来 token 当成已知输入。

### 2.1.2 一次请求的完整生命周期

线上请求通常经过下面的阶段：

~~~text
client sends request
  -> authentication, validation and rate limiting
  -> chat template and tokenization
  -> prefill the input tokens
  -> decode one output token at a time
  -> stop, stream, or execute a tool
  -> detokenize, post-process and release state
~~~

“模型推理时间”可能只指 GPU kernel 的运行时间，也可能从网关收到请求开始计时。两种口径都可以，但不能混用。比如 tokenizer 在 CPU 上耗时 30 ms、队列等待 100 ms、GPU prefill 耗时 200 ms，如果监控只记录 GPU span，工程师会误以为用户只等待了 200 ms；如果压测客户端从发送到收完计时，又需要把网络和客户端缓冲说明清楚。

聊天模板也属于推理计算的输入协议。相同的自然语言消息，经过不同模板可能得到不同的 token 序列；system、user、assistant、tool 的标记可能参与模型条件概率，`add_generation_prompt` 可能改变生成起点。部署时应记录模板 revision 和实际 token 数，而不能只记录原始字符串长度。Hugging Face 的 Chat Templates 文档可以核对这类消息到 token 序列的转换，但具体模型的模板仍必须用该模型自己的配置和回归样本验证。

停止条件同样会影响性能数字。模型可能因为 EOS、最大新 token 数、stop string、结构化输出完成或客户端取消而结束。若 stop string 要等 detokenize 后才能识别，模型可能已经多生成了几个 token；若客户端断开但服务没有及时取消 decode，GPU 仍会为一个没人接收的请求工作。因此 `N_out` 应记录实际生成的 token 数，并同时记录结束原因。

## 2.2 Prefill：先把输入读完

### 2.2.1 Prefill 的工作对象

假设输入有 `T_in` 个 token，模型在 prefill 阶段把它们作为一个序列送入 Transformer。对某一层，隐藏状态可以表示为：

~~~math
X\in\mathbb{R}^{B\times T_{\mathrm{in}}\times d},
~~~

其中 `B` 是同时处理的序列数，`d` 是 hidden size。self-attention 先产生：

~~~math
Q=XW_Q,qquad K=XW_K,qquad V=XW_V,
~~~

再计算带因果掩码的注意力：

~~~math
\operatorname{Attention}(Q,K,V)=
\operatorname{softmax}\left(
\frac{QK^\mathsf{T}}{\sqrt{D_h}}+M_{\mathrm{causal}}
\right)V.
~~~

因果掩码 `M_causal` 只允许位置看到自己和之前的位置。它限制了信息流，但不意味着 prefill 必须一个 token 一个 token 地运行；矩阵运算仍然可以在满足掩码的前提下并行计算整段输入。对初学者来说，可以把它理解成“同时批改一整页题目，只是不允许每道题偷看后面的题”。

prefill 的另一个结果是建立上下文状态。每一层的 key 和 value 会被写入后续 decode 使用的 KV Cache；因此 prefill 结束之后，模型已经“读过”输入，但还没有完成输出。首个输出 token 通常还需要一次以最后位置为中心的 decode 计算，所以 prefill 结束时间和首 token 发出时间不是同一时间点。

### 2.2.2 Prefill 的计算量为什么对长输入敏感

设 query head 数为 `H_q`，每个 head 的维度为 `D_h`，则 attention 中 `QK^T` 和 `AV` 两次矩阵乘法的主项，在把一次乘加计为两个 FLOPs 时，可粗略写成：

~~~math
C_{\mathrm{attn,prefill}}
\approx
4B H_q T_{mathrm{in}}^2D_h.
~~~

线性投影、输出投影和 MLP 还会带来近似线性于 token 数、但与 hidden size 平方有关的项。用复杂度而不是某个具体实现的 FLOPs 表示，通常写成：

~~~math
C_{\mathrm{prefill}}
=O\left(BT_{mathrm{in}}d^2
+BH_qT_{mathrm{in}}^2D_h\right).
~~~

第一项概括投影和 MLP 的工作，第二项概括 attention 的 token 两两交互。这个式子解释了两个常见现象：

1. 在短上下文或较小模型上，投影和 MLP 可能占主要部分，输入长度增加不一定严格呈平方增长。
2. 当上下文足够长时，attention 的平方项会迅速变重；输入从 512 token 增至 2048 token，attention 主项理论上增加约 16 倍，而不是 4 倍。

这只是计算量模型，不是延迟公式。实际延迟还取决于 kernel 是否融合、矩阵是否落在高效 tile、GPU 是否有足够 batch、数据类型、通信和调度。FlashAttention 的核心贡献是避免显式 materialize 巨大的 attention 矩阵、改善片上存储与显存之间的数据移动；它不会把标准全注意力的理论 token 交互从平方复杂度自动变成线性复杂度。

### 2.2.3 Prefill 为什么通常更像计算密集

prefill 同时拥有许多 token 位置，矩阵乘法的维度更大，GPU 可以让 tensor core 或其他矩阵单元保持较高利用率，所以在合适 batch 和足够长输入下通常更接近 compute-bound。这里的“通常”很重要：

1. 极短 prompt 的矩阵太小，kernel launch 和调度开销可能占主导。
2. batch 很小、模型切分跨 GPU 时，通信可能比算术运算更重要。
3. 长上下文写入 KV Cache、读取权重和中间激活会带来显存流量。
4. 未融合的算子、CPU tokenizer 或数据搬运可能让 GPU roofline 判断失效。

所以不能根据阶段名称直接断言瓶颈。阶段名称是诊断的起点，计数器、trace 和按长度分桶的压测才是证据。

### 2.2.4 Prefill 的优化要回答什么问题

如果 TTFT 随输入 token 数上升，至少有四类可能原因：

| 观察 | 更值得检查的对象 | 可能的方向 |
| --- | --- | --- |
| GPU 矩阵单元很忙 | 投影、MLP、attention kernel | 更好的 kernel、融合、并行和精度 |
| attention 中间空间和显存访问很重 | attention 实现 | FlashAttention、分块和更合适的 tile |
| GPU 等待请求组成 batch | 调度策略 | 限制等待时间、chunked prefill、按长度分组 |
| GPU 很闲但 TTFT 仍高 | tokenizer、模板、队列、网络 | CPU 并行、队列和协议链路优化 |

长 prompt 不能简单通过“加大 batch”解决。加大 batch 可能提高矩阵利用率，却同时延长短请求等待、增加 KV 写入和显存占用。第 6 章会讨论 chunked prefill 与 decode 的调度取舍；本章只需要记住，prefill 的优化对象既有算子，也有请求到达和批形状。

## 2.3 Decode：每次只走一步

### 2.3.1 单请求的串行约束

prefill 完成后，模型根据最后一个位置的 logits 选择第一个输出 token。接下来第 `t` 步只输入新 token 的表示，并让它的 query 访问已有上下文。设已经输入 `T_in` 个 token、已经生成 `t` 个 token，则当前上下文长度为：

~~~math
T_{\mathrm{ctx}}(t)=T_{\mathrm{in}}+t.
~~~

下一步的输出又依赖 `y_t`，因此时间顺序是：

~~~text
logits_1 -> y_1 -> logits_2 -> y_2 -> logits_3 -> ...
~~~

这不是说 GPU 每一步只能服务一个请求。多个请求可以把各自的一个 decode token 放进同一批次，从而让 GPU 并行处理不同请求；但同一个请求的 `y_t` 和 `y_{t+1}` 之间仍然有串行依赖。这一差异解释了为什么增加并发常能提升总 token 吞吐，却不能让一个请求的生成速度无限增长。

### 2.3.2 Decode 的计算和数据移动

对于一个 decode step，新增 query 与长度为 `T_ctx` 的历史 key/value 交互，attention 主项可粗略写成：

~~~math
C_{\mathrm{attn,decode}}
\approx
4B H_qT_{\mathrm{ctx}}D_h.
~~~

它对上下文长度是线性的，但每一步还要读取历史 KV Cache。若 K 和 V 都用 `b` 字节存储，`L` 层、`H_kv` 个 KV head，则只从数量级估算，单步 cache 读取量为：

~~~math
M_{\mathrm{KV,read/step}}
\approx
2LB T_{\mathrm{ctx}}H_{\mathrm{kv}}D_h b.
~~~

实际读取量可能因为 cache block、kernel 重用、量化格式、tensor parallel 和硬件访问合并而不同。公式的用途是解释趋势：上下文越长，decode 每一步需要接触的历史状态越多；`H_kv` 越小，K/V 存储和读取压力越低。

decode 还必须读取模型权重、执行投影、MLP、归一化、采样和调度。低 batch 时，每个 token 分摊到的矩阵计算量不够大，但权重和 cache 的移动仍然存在，因此 decode 经常表现为 memory-bound 或 memory/latency 混合瓶颈。高 batch、短上下文或高算力 GPU 上，它也可能转向计算受限。不要把“decode 通常 memory-bound”写成不需要测量的定律。

### 2.3.3 为什么长输出和长上下文是两种不同的慢

长输出增加 decode step 的数量；长上下文增加每个 decode step 要读取和交互的历史长度。二者可以同时发生，也可以分别发生：

1. 输入 8k、输出 8 token：首 token 可能很慢，但完整响应未必很久。
2. 输入 128、输出 2k token：TTFT 可能很低，但总 latency 主要由大量 decode step 累积。
3. 输入 8k、输出 2k token：prefill、KV Cache 和长时间 decode 都会成为压力。

因此线上报表至少要按 `T_in` 和 `N_out` 分桶。只报告“平均响应耗时”，无法判断应该缩短上下文、减少最大输出、优化 cache 访问，还是改调度。

## 2.4 KV Cache：推理状态的第一笔账

KV Cache 的细节放在第 3 章，本节先建立性能模型所需的最小概念。

在第 `l` 层，历史 token 的 K 和 V 常见形状为：

~~~math
K_l,V_l\in
\mathbb{R}^{B\times H_{\mathrm{kv}}\times T_{\mathrm{ctx}}\times D_h}.
~~~

历史 token 的 K/V 在后续生成中不会因为新 token 到来而改变，因此可以保存并复用。若有 `L` 层，所有活跃请求的上下文长度之和为 `S_ctx`，则未考虑复制、分页元数据和对齐浪费时，KV Cache 显存近似为：

~~~math
M_{\mathrm{KV}}
\approx
2L S_{\mathrm{ctx}}H_{\mathrm{kv}}D_h b.
~~~

`2` 来自 K 和 V 两份状态，`b` 是每个 cache 数值占用的字节数。这个公式比把 `B` 和一个统一的最大序列长度相乘更可靠，因为线上请求通常是变长的：

~~~math
S_{\mathrm{ctx}}=\sum_{i=1}^{B}T_{\mathrm{ctx},i}.
~~~

例如，假设模型有 `L=32` 层、`H_kv=8`、`D_h=128`，KV 使用 BF16/FP16 的 `b=2` 字节，一个请求上下文为 8192 token，则：

~~~math
M_{\mathrm{KV}}
\approx
2\times32\times8192\times8\times128\times2
=1{,}073{,}741{,}824\text{ bytes}
\approx1024\text{ MiB}.
~~~

如果是普通 MHA，K/V head 数为 32，同样条件下约为 4 GiB。MQA 把 K/V head 压到 1，GQA 使用介于 1 和 query head 数之间的 head 数；这解释了它们为什么能降低 cache 成本，但也会引入表达能力、兼容性和质量取舍。实际服务还要为权重、激活、临时 workspace、通信缓冲和碎片预留显存，所以“公式算出 1 GiB”不等于可以把一张 1 GiB 空闲显存完全分给 cache。

没有 KV Cache 时，第 `t` 步需要重新为整个历史序列计算 K/V；有 cache 时，只需为新 token 计算新的 K/V，再读取历史状态。它用显存换掉重复计算，但没有消除 `query` 对历史 K/V 的访问。因此 KV Cache 能显著减少重复的投影计算，却不能保证长上下文 decode 的每步时间不变。

本章只使用“状态大小”和“读写趋势”这两个抽象。连续物理内存、分页 block、prefix cache、cache eviction、量化、跨 GPU 拆分和碎片率，会在第 3 章单独讲清。

## 2.5 从时间戳定义性能指标

### 2.5.1 TTFT：用户什么时候看到第一步结果

Time To First Token（TTFT）通常表示从请求发送到客户端收到第一个输出 token 的时间。客户端口径可以写成：

~~~math
T_{\mathrm{TTFT,client}}
=t_{\mathrm{first\_byte}}-t_{\mathrm{request\_sent}}.
~~~

服务端为了定位模型路径，可以进一步拆成：

~~~math
T_{\mathrm{TTFT,server}}
=T_{\mathrm{queue}}
+T_{\mathrm{tokenize}}
+T_{\mathrm{prefill}}
+T_{\mathrm{first\_decode}}
+T_{\mathrm{serialize}}.
~~~

若网络和客户端缓冲未计入 server span，两者就不会相等。`T_queue` 是等待调度的时间，`T_tokenize` 包含模板展开和 tokenization，`T_prefill` 是输入前向，`T_first_decode` 是取出首 token 所需的一步，`T_serialize` 是协议编码和发送前处理。实际系统还可能有鉴权、限流、缓存查找和安全检查，这些应通过 trace 另列，而不是悄悄塞进某一个阶段。

TTFT 对长 RAG 特别敏感，因为检索到的文档会增加输入 token；对短聊天则可能主要受队列和 batch 等待影响。一个优化如果只减少 prefill，却让 scheduler 为了组成更大 batch 多等 100 ms，最终 TTFT 可能反而变差。

### 2.5.2 TPOT 与 ITL：后续 token 的间隔

Time Per Output Token（TPOT）在不同工具中的精确定义可能不同。最常见的平均口径是排除首 token 后，剩余 decode 时间除以剩余 token 数：

~~~math
T_{\mathrm{TPOT,avg}}
=
\frac{t_{\mathrm{last}}-t_{\mathrm{first}}}
{N_{\mathrm{out}}-1},qquad N_{\mathrm{out}}>1.
~~~

如果更关心流式体验，应记录每个相邻 token 到达之间的 Inter-Token Latency（ITL）：

~~~math
\mathrm{ITL}_j=t_{j+1}-t_j,qquad
T_{\mathrm{TPOT,avg}}=\frac{1}{N_{\mathrm{out}}-1}\sum_{j=1}^{N_{\mathrm{out}}-1}\mathrm{ITL}_j.
~~~

`t_first` 和 `t_last` 必须来自同一个时钟和同一计时边界。若一次网络 flush 携带多个 token，客户端 ITL 会受到 flush 策略影响；服务器内部每一步的时间和用户实际看到的 token 间隔可能不同。报告 TPOT 时应写明是 server-side decode time、client-side inter-arrival time，还是某个 benchmark 工具的定义。

`N_out=1` 时没有后续 token 间隔，TPOT 应记为不可用，而不是把整个请求的 latency 当作一个 token 的 TPOT。把这两个指标混在一起，会让短回答看起来异常慢或让长回答看起来异常快。

### 2.5.3 端到端延迟与结束原因

完整请求的端到端 latency 可以粗略分解为：

~~~math
T_{\mathrm{E2E}}
=T_{\mathrm{TTFT}}
+(N_{\mathrm{out}}-1)T_{\mathrm{TPOT,avg}}
+T_{\mathrm{post}}.
~~~

`T_post` 包括剩余 token 的发送、detokenization、结构化输出校验、内容过滤、工具结果处理和网络收尾。这个分解不是要求每个 token 的 ITL 都相同，而是方便把总时间映射到可观测 span。

每条请求还应记录 `finish_reason`：EOS、长度上限、stop string、工具调用、客户端取消、超时或内部错误。不同结束原因的输出长度分布不同，若把它们混成一个平均值，生成控制或服务故障可能被误诊为模型速度变化。

### 2.5.4 吞吐和百分位数

请求吞吐与 token 吞吐是两类不同指标：

~~~math
\mathrm{QPS}
=\frac{N_{\mathrm{completed\ requests}}}{T_{\mathrm{wall}}},
~~~

~~~math
\mathrm{TPS}_{\mathrm{out}}
=\frac{N_{\mathrm{completed\ output\ tokens}}}{T_{\mathrm{wall}}}.
~~~

离线批处理还应报告输入 token 吞吐和总 token 吞吐；在线聊天通常更关心输出 token 吞吐、TTFT 和 TPOT。两个系统 QPS 相同，并不意味着成本相同：一个系统每个请求输出 20 token，另一个输出 2000 token，它们对 GPU 的工作量完全不同。

P50、P95、P99 是请求级样本的分位数，不是把所有 token 的时间混在一起后的数字，也不是“最后一个样本”自动得到的结果。假设排序后的延迟为 `x_(1),...,x_(n)`，一种线性插值定义把位置写成：

~~~math
r=(n-1)p,qquad
Q_p=(1-\delta)x_{\lfloor r\rfloor+1}
+\delta x_{\lfloor r\rfloor+2},
~~~

其中 `p` 是 0 到 1 之间的分位点，`delta=r-floor(r)`；工程系统也可能采用 nearest-rank 或 histogram 近似。因此报表必须注明统计实现，并提供样本量。只有 3 条压测样本时，“P95”几乎没有稳定统计意义；把最大值标成 P95 更会误导读者。

分位数还必须按 workload 分层。短聊天、长 RAG、代码生成和 Agent 工具调用的输入输出长度与等待链路不同。一个总体 P95 可能看起来正常，但长 RAG 的 P99 已经不可用；一个平均 TPOT 正常，也可能有一小部分请求在 cache 抢占时出现很大的 ITL。

## 2.6 Batch size、sequence length 与 token 数

### 2.6.1 `batch size` 不是唯一的工作量单位

在训练教材里，batch size 常常指一次送入的样本数。推理服务中至少有三种容易被混叫的量：

1. sequence batch：同时处理的请求数。
2. prompt token 数：本轮 prefill 要读取的输入 token 总数。
3. active decode token 数：本轮 decode 中每个活跃请求贡献的一个新 token。

一个 batch 有 32 个短请求，可能比一个含 4 个 16k 长请求的 batch 更容易处理；因此只报 `batch_size=32` 没有充分信息。更可用的记录是：请求数、prefill token 数、decode active sequences、总上下文 token 数、输出 token 数和 padding token 数。

### 2.6.2 变长请求造成的 padding 浪费

如果把不同长度的输入填充到同一最大长度 `T_max`，一个 batch 的理论 padding 比例可以估算为：

~~~math
\rho_{\mathrm{pad}}
=1-
\frac{\sum_{i=1}^{B}T_i}{B\,T_{\max}}.
~~~

`T_i` 是第 `i` 个请求的真实长度。长度分别为 128、256、2048 的三个请求若直接 pad 到 2048，大部分计算都在处理填充位置。现代推理 runtime 往往使用 ragged 或 paged 结构减少这种浪费，但不同 kernel、mask 和模型架构的支持程度不同。若服务把长短请求硬塞进同一个静态 batch，TTFT 和显存估算都可能比平均长度模型差很多。

### 2.6.3 活跃上下文与 KV Cache

对第 `i` 个请求，当前上下文长度是：

~~~math
T_{\mathrm{ctx},i}=T_{\mathrm{in},i}+t_i,
~~~

其中 `t_i` 是已经生成的 token 数。所有活跃请求的 cache token 总数为：

~~~math
S_{\mathrm{ctx}}=\sum_{i=1}^{B_{\mathrm{active}}}T_{\mathrm{ctx},i}.
~~~

于是基础显存估算为：

~~~math
M_{\mathrm{KV}}
\approx2L S_{\mathrm{ctx}}H_{\mathrm{kv}}D_h b.
~~~

注意，`S_ctx` 是状态总量，不等于本轮 decode 新生成的 token 数。一个长请求即使本轮只生成一个 token，也可能占据数千个 cache token，并在每一步读取它们。反过来，一个刚进入 prefill 的请求可能正在消耗算力，但尚未拥有完整的 decode 状态。把“本轮 token 数”和“所有上下文 token 数”混为一谈，是容量规划中非常常见的错误。

### 2.6.4 静态 batch、动态 batch 与 continuous batching

静态 batch 要等一批请求准备好，再共同运行若干步。它实现简单，但请求长度差异大时容易出现空槽和等待。动态 batch 在请求到达时重新组成批次；continuous batching 更进一步，以迭代或 token step 为粒度把新请求加入、把完成请求移出，使 decode 空槽可以被其他请求利用。

这类调度会改变两个方向相反的量：

1. 批次更满，矩阵和权重读取可能更高效，系统 token 吞吐增加。
2. 等待组成批次、长请求占用 cache 或短请求被延迟，单请求 TTFT 和 P99 可能恶化。

所以 continuous batching 不是“无条件降低 latency”的开关。它解决的是服务中请求生命周期不同步的问题，最终效果取决于到达率、长度分布、最大 batch token、KV 预算和调度策略。Orca 论文以 iteration-level scheduling 讨论了生成式模型服务中这种调度粒度变化；vLLM、TensorRT-LLM 和其他 runtime 又用各自的实现和配置把它落到生产系统中。论文结论、框架功能和当前硬件收益需要分开验证。

## 2.7 Latency、throughput 与排队

### 2.7.1 为什么吞吐和延迟会互相牵制

当 GPU 还有空闲计算资源时，增加并发和 batch 往往能提高 token 吞吐。接近容量上限后，新的请求需要排队，cache 分配变得紧张，长请求还可能阻塞短请求。此时继续追求更大 batch，可能让总吞吐只增加很少，却让 P95/P99 快速上升。

从单请求角度看，延迟是等待和服务时间之和：

~~~math
T_{\mathrm{E2E}}
=T_{\mathrm{wait}}+T_{\mathrm{service}}+T_{\mathrm{network}}.
~~~

从系统角度看，吞吐是单位时间完成的工作。一个服务可以在高吞吐状态下让每个请求等待很久，也可以用很低并发获得漂亮的 latency、却没有足够的 GPU 利用率。部署目标必须写成 workload 下的约束，例如“P95 TTFT 小于 500 ms、P99 完整响应小于 5 s、错误率小于某个比例”，而不是只写“尽可能高的 TPS”。

### 2.7.2 Little 定律提供一个容量直觉

在近似稳定、统计口径一致的系统中，Little 定律给出：

~~~math
L=\lambda W.
~~~

`L` 是系统中的平均请求数，`lambda` 是平均完成/到达率，`W` 是平均停留时间。比如平均每秒完成 20 个请求、平均每个请求在系统中停留 2 秒，那么系统中平均约有 40 个请求处于排队或执行状态。

这个关系不是一个 GPU 性能预测器，也不能直接给出 P99。它帮助我们检查容量叙述是否自洽：如果目标 QPS 不变而平均延迟突然增加，活跃请求和 KV Cache 占用通常也会增加；如果系统没有相应的内存或队列预算，所谓“支持更高并发”只是把请求推迟到更长的队列中。

### 2.7.3 过载时先发生什么

令单个工作单元的平均服务时间为 `E[S]`，到达率为 `lambda`，一个非常粗略的利用率直觉是：

~~~math
\rho\approx\lambda E[S].
~~~

在多 GPU 服务中还要除以有效并行服务能力，并考虑请求长度、调度和通信。`rho` 接近 1 时，排队延迟对小的流量波动非常敏感；实际服务还会因为长请求和变长 batch 比简单 M/M/1 模型更早出现尾延迟问题。常见的过载表现包括：

1. TTFT 先上升，因为请求在 scheduler 前等待。
2. KV Cache 达到水位后出现抢占、换入换出或拒绝。
3. P99 先于平均值恶化。
4. 客户端超时触发重试，重试又增加到达率。
5. 流式连接占用 worker，短请求的等待更不稳定。

因此限流、backpressure、最大输入/输出长度和取消语义不是外围功能，而是推理性能模型的一部分。重试还必须区分纯推理请求和带工具副作用的请求；后者不能只因为超时就盲目重放。

## 2.8 Compute-bound 与 memory-bound：用 roofline 建立第一层判断

### 2.8.1 算术强度是什么

算术强度（arithmetic intensity）表示每搬运一个字节的数据，完成了多少计算：

~~~math
I=\frac{C_{\mathrm{FLOPs}}}{M_{\mathrm{bytes}}}.
~~~

若设备峰值计算能力为 `P_peak`、显存带宽为 `BW_mem`，两者的交叉点为：

~~~math
I_{\mathrm{roof}}
=\frac{P_{\mathrm{peak}}}{BW_{\mathrm{mem}}}.
~~~

一个简化 roofline 上界是：

~~~math
P_{\mathrm{achievable}}
\le
\min\left(P_{\mathrm{peak}},I\,BW_{\mathrm{mem}}\right).
~~~

当 `I` 低于交叉点时，增加计算单元通常不能直接解决问题，数据搬运更可能是限制；当 `I` 高于交叉点时，计算能力和 kernel 执行效率更值得关注。这里的 `M_bytes` 必须是实际内存层级中搬运的数据量，而不是只把某一块张量大小代入。权重读取、K/V 读取、激活读写、通信和临时 workspace 都可能进入真实分母。

### 2.8.2 一个数量级例子

假设教学设备峰值为 120 TFLOP/s、显存带宽为 1.6 TB/s，则：

~~~math
I_{\mathrm{roof}}
=\frac{120\times10^{12}}{1.6\times10^{12}}
=75\ \mathrm{FLOPs/byte}.
~~~

本章 demo 会用一个明确标注为“有效激活流量”的简化分母，观察 prefill attention 强度随 `T_in` 增加，而 decode 的 K/V 读取强度保持很低。它只用于建立趋势，不是对具体 GPU 的 benchmark。实际排障应结合 Nsight Compute、runtime trace、GPU 利用率、显存吞吐、kernel 时间和跨卡通信计数器。

### 2.8.3 阶段经验不是诊断结论

“prefill 偏 compute-bound、decode 偏 memory-bound”是一条很好的面试第一句，但完整回答应加上边界：

1. prefill 的大矩阵可能计算密集，也可能被队列、CPU 或通信拖慢。
2. decode 的低 token 并行度和 cache 读取常导致访存受限，但高 batch 可能提高计算利用率。
3. 量化减少字节数，可能提高 arithmetic intensity；如果没有匹配的 kernel，也可能因为反量化开销而收益有限。
4. GQA/MQA 减少 K/V 状态，不等于减少所有模型权重和 MLP 计算。
5. TP/PP 或 disaggregated prefill/decode 会引入通信，单卡 roofline 不能独立解释整体 latency。

判断瓶颈的顺序应是：先看请求 trace，再按阶段看 GPU kernel 与内存计数，最后用理论式解释观测结果。反过来先贴上“memory-bound”标签，容易把队列、网络和 CPU 问题错误地交给 CUDA kernel。

## 2.9 一个可手算的请求 trace

假设两个请求同时进入服务。请求 A 是长 RAG：输入 2,000 token，队列等待 40 ms，prefill 260 ms，生成 100 token，首 token 后每个 token 平均 18 ms。请求 B 是短问答：输入 200 token，队列等待 10 ms，prefill 35 ms，生成 40 token，首 token 后每个 token 平均 12 ms。先忽略后处理和网络时间。

按 server-side 口径，两个请求的 TTFT 分别是：

~~~math
T_{\mathrm{TTFT},A}=40+260=300\text{ ms},
\qquad
T_{\mathrm{TTFT},B}=10+35=45\text{ ms}.
~~~

若首 token 计入 TTFT，后续分别有 `99` 和 `39` 个 token，则完整响应时间近似为：

~~~math
T_{\mathrm{E2E},A}\approx300+99\times18=2082\text{ ms},
~~~

~~~math
T_{\mathrm{E2E},B}\approx45+39\times12=513\text{ ms}.
~~~

A 的首 token 慢，主要可以从长输入和队列中寻找原因；A 的完整响应更慢，还叠加了长输出和长上下文下更高的每步读取成本。若只看两个请求的平均 latency，A 的长输入和 B 的短输入会互相抵消，无法告诉我们服务对哪一类用户不友好。

这个例子还揭示了一个常被忽略的事实：优化目标必须带请求分布。把所有请求的 prompt 截断到 512 token 可能降低 TTFT，却可能损失 RAG 所需证据；把最大输出从 2048 限制到 256 可能改善尾延迟，却可能使代码和 Agent 任务无法完成。性能优化不能脱离任务契约。

## 2.10 用 trace 做阶段诊断

线上排障时，至少为每条请求记录下面的时间戳和状态：

| 字段 | 含义 | 能回答的问题 |
| --- | --- | --- |
| `request_received` | 网关收到请求 | 网络和入口是否已慢 |
| `queue_start/end` | 进入和离开调度队列 | TTFT 是否主要消耗在等待 |
| `prefill_start/end` | 输入前向范围 | 长 prompt 是否主导首 token |
| `first_token` | 首 token 生成/发送时间 | server/client TTFT 差异多大 |
| `decode_step` | 每个 decode 迭代的时间 | TPOT、ITL 是否随上下文变化 |
| `cache_tokens/bytes` | 当前状态大小 | 是否接近显存水位 |
| `preempted` | 是否被抢占或重排 | 尾延迟是否来自资源争用 |
| `finish_reason` | EOS、长度、取消、超时等 | 输出分布和失败原因是什么 |
| `response_complete` | 客户端/服务端完成时间 | 完整响应尾延迟多大 |

这些字段能够构成一个最小请求 trace。然后按输入长度、输出长度、是否命中 prefix cache、batch token 数、GPU rank 和模型 revision 分桶。不要只看整机 GPU utilization：一个 GPU 利用率 60% 的服务可能在等 CPU tokenizer，也可能被小 batch 的 kernel launch 限制，还可能因为请求都在队列中而没有足够工作。

可以用下面的现象--证据关系开始排查：

| 现象 | 第一组证据 | 不应直接推断 |
| --- | --- | --- |
| TTFT 随输入长度一起升高，TPOT稳定 | prefill span、attention kernel、输入 token 分布 | 不一定是 decode 慢 |
| 只有高并发时 TTFT 升高 | queue span、active sequences、cache 水位、抢占次数 | 不一定要换更大模型 |
| TPOT 随上下文长度升高 | 每步 K/V 读取、cache layout、GQA/MQA、batch 形状 | 不一定是生成质量下降 |
| 平均 latency 正常但 P99 很高 | 长请求、HOL blocking、工具等待、重试链路 | 不应只提高平均 batch |
| GPU 利用率低且 QPS 低 | kernel 尺寸、CPU/网络 span、请求是否足够 | 利用率低不等于没有瓶颈 |
| tokens/s 提升但任务成功率下降 | 量化、模板、停止原因、质量回放 | 不应把性能提升直接视为服务提升 |

### 2.10.1 TTFT 随输入长度增长意味着什么

如果对多个输入长度桶画出 TTFT 曲线，斜率可以帮助定位 prefill 成本，但不能单独证明 attention 是平方复杂度。模型的投影和 MLP、kernel 选择、长度 padding 和 scheduler 都会改变曲线形状。更稳妥的实验是固定模型、精度、GPU、输出长度和并发，只改变输入长度；同时记录 prefill token/s、GPU kernel 时间、显存读写和队列时间。

### 2.10.2 TPOT 随上下文增长意味着什么

固定输出长度和并发，改变 `T_in`，观察后续 token 的 ITL。若 ITL 与上下文一起升高，应检查 KV Cache 读取和访问布局；若 GPU 内存带宽并不高但 CPU 或 scheduler span 升高，问题可能是调度而不是 cache；若只在特定长度跳变，可能涉及 block 分配、kernel shape、并行拓扑或显存水位。

### 2.10.3 P99 爆炸意味着什么

尾延迟经常由少数长请求、队头阻塞、cache 抢占、跨卡通信、GC/内存分配、工具调用和客户端重试造成。把平均 batch 做大可能进一步放大这些影响。应先把长输入、长输出和工具等待分开，再决定是否需要长度上限、优先级、分离队列、prefill/decode 分离或单独副本。

## 2.11 Prefix Cache 与推理状态的边界

当许多请求共享完全相同的 token 前缀时，runtime 可以尝试复用前缀对应的计算结果或 KV 状态，从而减少重复 prefill。这里的“相同”通常指 token id、位置编码条件、模型 revision、精度和 cache 相关配置兼容，而不是人眼看起来相同的字符串。

例如，下面两条消息的 system 文本看起来相同，但只要 chat template 的空格、特殊 token、工具 schema 或 generation prompt 不同，最终 token 前缀就可能不同：

~~~text
system: You are a helpful assistant.
user:   Explain caching.
~~~

~~~text
system: You are a helpful assistant.
user:   Explain caching.
tool:   {"name": "lookup"}
~~~

工具 schema 可能被放在 user 之前，或者被序列化成 system 内容；这会改变可复用的前缀边界。prefix cache 的命中率应记录为 token 数或字节数，而不是只记录“命中请求数”：命中一个 20 token 前缀和命中一个 20k token 前缀，对 prefill 的价值完全不同。

本章只把 prefix cache 作为请求生命周期中的一个变量。缓存的 block 分配、租户隔离、失效、隐私和跨实例共享属于第 3 章与生产系统章节；不要因为复用了前缀，就把后续用户的可见内容或权限状态一起复用。

## 2.12 推理与训练为什么不能用同一套直觉

训练和推理都调用 Transformer，但资源账本不同：

| 维度 | 训练 | 推理 |
| --- | --- | --- |
| 主要目标 | 更新参数 | 生成或评分结果 |
| token 并行性 | 给定完整 target，可并行计算多个位置 | 一个请求的未来 token 依次产生 |
| 主要状态 | 权重、梯度、优化器状态、激活 | 权重、KV Cache、临时 workspace |
| 计算阶段 | forward、backward、optimizer step | prefill、decode、采样和后处理 |
| 常用指标 | loss、吞吐、稳定性、收敛 | TTFT、TPOT、P95/P99、tokens/s、成本 |
| 主要风险 | 数值发散、数据错误、恢复失败 | 排队、OOM、长尾、协议和安全失败 |

训练中常说的 global batch、序列并行和 activation checkpointing，不能直接变成线上服务的 batch 配置。推理还要面对请求随时到达、长度不同、客户端取消和生成提前结束。反过来，推理中的 KV Cache 不是训练中保存所有历史状态的同一个问题；训练的反向传播需要激活和梯度，在线 decode 主要需要复用历史 K/V。

## 2.13 不同 workload 的性能主线

同一个模型在不同任务上会呈现不同瓶颈。下面的分类不是固定定律，而是压测设计的起点：

| workload | 输入特征 | 输出特征 | 首先观察 |
| --- | --- | --- | --- |
| 短聊天 | 输入短，重复率可能高 | 输出中短，流式敏感 | queue、TTFT、ITL、连接数 |
| 长 RAG | 文档使输入变长，前缀可能部分重复 | 输出中等 | prefill、prefix hit、KV bytes、TTFT |
| 代码生成 | 输入包含代码和约束 | 输出可能长，stop 规则重要 | TPOT、格式/测试通过率、输出上限 |
| 离线合成 | 可积累大 batch | 长度分布可控 | 总 token 吞吐、GPU 利用率、单位成本 |
| Agent | 多轮模型调用与工具等待 | 每轮输出未必长 | 端到端 wall time、取消、重试和副作用 |
| 多模态 | 前处理和视觉/音频 token 成本不同 | 可能是文本或语音 | 编码时间、模态 token、TTFT、质量 |

例如，短聊天服务提高 batch 可能主要改善 token 吞吐，却未必值得牺牲 100 ms 的 TTFT；离线数据合成则可能愿意等待更大的 batch，只要总成本和完成时间下降。长 RAG 既要控制输入长度，也要验证检索证据没有因为截断而丢失。Agent 的用户体验还包括工具等待，模型 TPOT 不能代表整个任务时间。

## 2.14 一个零依赖的推理指标估算 demo

下面的代码不运行真实模型，也不读取 GPU 计数器。它用可解释的 toy 公式，对 8 条不同长度的请求估算 prefill attention 强度、decode 的 K/V 读取强度、TTFT、TPOT、端到端延迟和 cache 状态大小。这样做的目的不是预测某张 GPU 的绝对性能，而是让读者看见变量变化如何传导到指标。

代码中的 `prefill_activation_bytes` 是“有效激活流量”的教学近似，不是完整的 DRAM traffic；`prefill_ms` 和 `tpot_ms` 也是人为设置的趋势模型。真实 benchmark 必须替换为同一硬件、同一 runtime、同一 tokenizer/template、同一精度和代表性 workload 的测量值。

~~~python
from math import floor


requests = [

def prefill_attention_flops(tokens):
    # QK^T and AV, with one multiply-add counted as two FLOPs.
    return 4 * attention_heads * tokens * tokens * head_dim


def prefill_activation_bytes(tokens):
    # Effective activation traffic for this teaching model, not a hardware counter.
    return 8 * tokens * hidden_size * bytes_per_value


def decode_attention_flops(context_tokens):
    return 4 * attention_heads * context_tokens * head_dim


def decode_kv_read_bytes(context_tokens):
    return 2 * kv_heads * context_tokens * head_dim * bytes_per_value


def kv_cache_mib(tokens):
    return 2 * layers * tokens * kv_heads * head_dim * bytes_per_value / 1024**2


def percentile(values, probability):
    """Linear-interpolated percentile for a small teaching sample."""
    ordered = sorted(values)
    position = (len(ordered) - 1) * probability
    lower = floor(position)
    upper = min(lower + 1, len(ordered) - 1)
    fraction = position - lower
    return ordered[lower] + fraction * (ordered[upper] - ordered[lower])
~~~

## 2.15 常见误解与边界

### 2.15.1 “prefill 就是一次前向，decode 就是另一个模型”

不是。两者通常使用同一个模型参数和同一套 Transformer block，区别在于输入形状、已缓存状态和调用时序。runtime 可能为两种形状选择不同 kernel，甚至在架构上拆成不同 worker，但这不改变模型的条件概率定义。

### 2.15.2 “decode 每步只有一个 token，所以计算量可以忽略”

不是。它虽然没有长序列的 token 并行，却要重复执行每层投影、MLP、归一化和 attention，并反复读取权重与历史 K/V。长输出的总成本是许多 decode step 的累积；高并发服务还要把多个请求的单 token 工作合并起来。

### 2.15.3 “GPU 利用率高，所以服务一定快”

不是。GPU 利用率是整机或时间窗口的聚合指标，可能掩盖某些请求的队列等待和 P99。GPU 很忙也可能是在做无效 padding 或为已经取消的请求继续生成。必须把 GPU 事件和请求 trace 对齐。

### 2.15.4 “batch 越大，吞吐一定越高”

不是。batch 增大到一定程度后，显存压力、通信、调度和 cache 访问会抵消矩阵利用率收益；请求长度差异还会增加 padding 或调度空洞。应画出 batch token 数与 tokens/s、TTFT、P99、OOM/抢占率的曲线，而不是只测一个 batch。

### 2.15.5 “P95 就是最慢的请求”

不是。P95 是样本分布的一个分位点，只有在样本量很小或极端分布下才可能接近最大值。报告应同时给样本数、计算方法和最大值；生产系统常用 histogram 近似，客户端原始样本和服务端聚合值也可能不同。

### 2.15.6 “量化只改变权重大小”

不是。量化可能作用于权重、激活或 KV Cache，改变显存、带宽、数值误差、kernel 路径和质量。权重 INT4 不代表 KV Cache 也是 INT4；FP8 KV Cache 也不等于整个模型使用 FP8。量化专题会进一步说明格式和硬件支持。

### 2.15.7 “相同 prompt 文本一定能命中 prefix cache”

不是。命中判断通常依赖最终 token id 和兼容的模型、模板、位置与缓存配置。工具 schema、空格、特殊 token、租户策略和版本变化都可能使前缀失效。命中率还应按复用 token 数计算。

## 2.16 把本章知识用于一次真实压测

一次可解释的压测应先固定实验变量，再改变一个主要因素。一个最小流程如下：

1. 固定权重 revision、tokenizer、chat template、精度、GPU 型号、驱动和 runtime revision。
2. 准备短聊天、长 RAG、代码生成和 Agent 等 workload class，并记录真实输入/输出 token 分布。
3. 分别控制并发、最大 batch token、最大上下文和最大新 token，不要同时修改所有开关。
4. 记录客户端和服务端时间戳，至少包含 queue、prefill、first token、decode step、finish reason 和 response complete。
5. 计算 TTFT、ITL/TPOT、E2E、P50/P95/P99、QPS、输入/输出 token 吞吐、错误率和取消率。
6. 同步采集 KV Cache bytes、水位、抢占、GPU kernel、显存带宽、通信和 CPU/网络时间。
7. 把吞吐曲线与质量回放配对，确认量化、截断、模板和停止策略没有造成能力回归。

实验结果应写成“在什么 workload、什么硬件、什么口径下得到什么数字”。例如，“在 4 张某型号 GPU、输入 P95 为 2k、输出 P95 为 512、并发 64、流式客户端口径下，TTFT P95 为多少，输出 token 吞吐为多少”。脱离条件的“模型每秒多少 token”无法迁移到另一个服务。

## 2.17 面试中如何把推理基础讲完整

面试官问“为什么 prefill 和 decode 的瓶颈不同”时，完整回答可以按因果链组织：prefill 处理整段输入，拥有较大的矩阵并行度，attention 主项随输入长度的平方增长，在合适 batch 下通常更偏计算密集；decode 每次为一个请求生成一个 token，单请求存在串行依赖，同时要读取随上下文增长的 KV Cache，所以通常更容易受显存访问、权重搬运和调度影响。但这是经验起点，不是结论，最终要用 trace 和硬件计数器确认。

如果追问“TTFT 和 TPOT 怎么测”，应先说明计时边界。TTFT 是请求发送到首 token 到达，TPOT 通常是首 token 之后相邻 token 间隔的平均值，但不同 benchmark 可能采用 server-side 或 client-side 口径。需要报告输入/输出长度、并发、P95/P99、停止原因和样本量，不能只给平均值。

如果追问“batch size 如何选择”，答案不应是一个固定数字。应先按输入/输出长度和 SLO 建立 workload，再测不同 active sequences 和 batch token 上限的 throughput--latency 曲线；观察 KV Cache 水位、抢占、OOM、队列等待和质量回归。在低负载时提高 batch 可能提升 GPU 利用率，在高负载时继续提高 batch 可能只会推高尾延迟。

如果追问“如何判断 memory-bound”，可以先用 roofline 的 `I=C/M` 建立数量级判断，再结合 kernel 时间、显存带宽和 cache 读取确认；并说明权重、激活、KV、通信和调度都可能进入真实数据移动量。这样回答比简单背诵“prefill 计算密集、decode 访存密集”更可靠。

## 2.19 小结

LLM 推理的核心不是一次性算出一段文本，而是先以 prefill 读完整个输入，再在 decode 中逐 token 地延续条件概率。prefill 通常拥有更高的 token 并行度，长输入会放大 attention 和输入处理成本；decode 受单请求串行约束，并需要反复读取历史 KV Cache，长上下文和长输出会以不同方式增加延迟。

性能分析必须从时间戳和分母开始。TTFT 衡量首 token，TPOT/ITL 衡量后续 token 间隔，E2E 衡量完整请求；QPS、输入/输出 token 吞吐和 P95/P99 描述不同侧面。batch size 不能脱离 token 数、上下文长度和 KV 状态讨论，compute-bound 与 memory-bound 也只能由理论模型和实测证据共同判断。

当你能把“用户看到的慢”拆成队列、tokenizer、prefill、decode、cache、网络和工具等待，并能说明每个数字的统计口径，这才算真正理解了推理基础。后续章节的分页 cache、调度、量化和生产系统，都是在这条请求生命周期上继续增加工程细节。
