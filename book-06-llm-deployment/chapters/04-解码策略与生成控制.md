# 第四章 解码策略与生成控制：从 logits 到可交付输出

模型完成一次前向计算后，得到的不是一句话，而是词表上每个 token 的一组分数。服务必须决定从这些分数中选出什么，什么时候停止，是否允许某个 token 进入 JSON 或工具参数，以及是否值得用一个小模型先猜几步来加速大模型。

这一步叫 decoding。它不更新模型参数，却会明显改变模型在产品中的表现。同一份权重、同一个输入，greedy 可能稳定地给出同一答案，sampling 可能给出多个不同答案，结构化约束可能保证语法合法，错误的 stop 配置则可能让模型输出下一轮角色标记。解码参数还会影响输出 token 数、KV Cache 生命周期、重试次数和单位任务成本，所以它不是简单的“生成后处理”。

初学者可以把 decoding 想成从候选词中做下一步选择：temperature 决定分布有多尖锐，top-k 和 top-p 决定候选范围，penalty 改变已经出现过的词的分数，stop 决定什么时候结束。专家则需要进一步确认这些操作的顺序、数值稳定性、随机数口径、约束状态、beam/cache 成本，以及它们在真实任务上的质量和延迟取舍。

本章先讲单步 logits 如何变成 token，再讲搜索、采样、重复控制、停止、结构化输出、推理预算和 speculative decoding。第 5 章会展开 runtime kernel 和引擎差异，第 9 章会把这些控制放进 RAG/Agent 生命周期；这里的目标是让读者能够解释每个控制点改变了什么，以及它不能保证什么。

## 4.1 一步 decoding 在做什么

### 4.1.1 Logits 和概率

对一个请求，在当前上下文上完成模型前向后，会得到词表大小为 V 的 logits：

~~~math
z=(z_1,z_2,\ldots,z_V)\in\mathbb{R}^{V}.
~~~

logits 是未归一化分数，不是概率。没有额外处理时，概率分布由 softmax 给出：

~~~math
p_i=\frac{\exp(z_i)}
{\sum_{j=1}^{V}\exp(z_j)}.
~~~

实际计算会先减去最大 logit 以避免指数溢出：

~~~math
p_i=
\frac{\exp(z_i-\max_j z_j)}
{\sum_{j=1}^{V}\exp(z_j-\max_j z_j)}.
~~~

在第 t 步，模型根据上下文 x 和此前生成的 token $y_{1:t-1}$ 得到 $z_t$；当 $t=1$ 时，前缀为空。解码器可以修改 $z_t$、过滤候选 token，再从剩余分布中取最大值或随机抽样。这里有三个容易混淆的层次：

1. 模型前向产生 logits，决定模型在当前上下文下的偏好。
2. logits processor 或约束器修改/屏蔽候选，施加任务规则。
3. sampler 决定从修改后的分布中如何选 token。

温度、top-k、top-p 和 penalty 属于第二、三层附近的控制；它们不会重新训练模型，也不会凭空增加模型没有学到的事实。

### 4.1.2 统一的候选分布

设经过处理的 logit 为 z_tilde，最终允许的候选集合为 C，则：

~~~math
p_i^{\mathrm{decode}}
=
\frac{\exp(\widetilde z_i)}
{\sum_{j\in\mathcal{C}}\exp(\widetilde z_j)},
\qquad i\in\mathcal{C}.
~~~

如果某个 token 不在 C 中，它的概率应为 0。工程实现通常把它的 logit 设为负无穷或用等价的 mask。greedy 选择概率最大的 token；sampling 按 p_decode 抽样；beam search 则把多个历史序列的累计对数概率一起比较。

这些公式都有定义域。词表大小 `V` 必须为正，参与 softmax 的 logits 必须是有限数；过滤后的候选集合 `C` 必须非空，且归一化分母必须为正。若 grammar mask、bad-word 规则或数值异常使候选集为空，服务应返回可诊断的错误或使用明确记录的回退策略，不能把空集合交给 softmax 后再把 NaN 当成正常 token。

不同框架可能采用不同的 processor 顺序。例如某个 runtime 先应用 repetition penalty 再做 temperature，另一个实现可能在过滤后才归一化。参数名称相同，不代表最终分布相同。复现一个结果时，应记录模型、tokenizer、chat template、generation config、processor 顺序、随机种子和 runtime revision。

## 4.2 Greedy decoding：把当前最可能的 token 拿出来

greedy decoding 每一步都选择当前概率最大的 token：

~~~math
y_t=\arg\max_i p_i.
~~~

它的优点是简单、确定、容易回放。输入 token、模型版本、计算精度和前向路径都一致时，通常可以得到相同输出。分类、信息抽取、格式转换、低随机性问答和某些代码补全基线经常从 greedy 开始。

但 greedy 是局部选择。某一步概率最高的 token，可能把后续带到一个糟糕的语义分支；它没有搜索未来，也不保证整段序列的全局概率最高。开放式对话中，greedy 还可能产生模板化、保守或重复表达。

greedy 适合“稳定优先”的基线，不等于“正确率永远最高”。如果任务有可执行验证器，代码通过率、数学答案准确率或 schema 合法率才是比较依据，而不是解码方式的名声。

## 4.3 Beam search：在序列层面保留多个候选

### 4.3.1 累计分数

beam search 维护 k 条候选序列。对候选 y_1:t，常见累计对数概率是：

~~~math
s(y_{1:t})
=
\sum_{\tau=1}^{t}
\log P(y_\tau\mid x,y_{1:\tau-1}).
~~~

若只比较累计分数，长序列会因为多加了许多通常为负的 log probability 而天然吃亏。实现因此可能使用长度归一化：

~~~math
s_{\mathrm{norm}}(y_{1:t})
=
\frac{s(y_{1:t})}{t^\alpha},
\qquad \alpha\ge0.
~~~

长度惩罚的具体形式在不同库中并不完全一样；它只是搜索目标的一部分，不是对真实答案长度的普适校正。beam size 越大，搜索候选越多，计算、KV Cache 和排序开销也越高。

这里要求候选长度 `t>0`，beam size 是正整数，且长度指数 `\alpha\geq0`。如果系统允许空序列作为特殊初始状态，应把它作为搜索初始化状态处理，而不是对 `t=0` 直接计算 `0^\alpha` 的长度归一化分数。

### 4.3.2 为什么 beam 不是“更强的 greedy”

greedy 每一步只保留一条路径；beam 保留多条路径，允许某条当前分数略低的路径在后续反超。对翻译、ASR、摘要等目标较明确的序列任务，beam 可能有价值。

对开放式 decoder-only 对话，beam 的目标仍是最大化模型给出的序列概率，而高概率并不等价于事实性、帮助性或多样性。多个 beam 还可能高度相似，显存使用按候选数增长；如果 beam 在服务层与多请求 batching 叠加，实际吞吐和 TTFT 会明显变化。

使用 beam 时要单独记录：

1. beam size、length penalty 和 early stopping 语义。
2. 每条 beam 是否复制完整 KV Cache，是否有共享前缀。
3. 最终返回的是最高分 beam，还是经过 rerank/验证的候选。
4. 评价的是 sequence log-prob，还是任务成功率和人工偏好。

“beam 搜索范围更大”只说明搜索过程更复杂，不能直接推出输出质量更高。

### 4.3.3 手算一次局部选择与序列排名

假设第一步有两个候选 A、B，概率分别为 0.6 和 0.4；第二步，A 后接 A1/A2 的条件概率为 0.55/0.45，B 后接 B1/B2 为 0.9/0.1。greedy 先选 A，再选 A1，整条路径概率为 $0.6\times0.55=0.33$。宽度为 2 的 beam 在第一步保留 A、B，第二步得到四条路径的概率 0.33、0.27、0.36 和 0.04，因此最高的是 B→B1，概率 0.36。这个小例子只说明“保留备选路径”可能改变结果；若 token 概率来自不同生成状态，实际 beam 的分数要逐步相加对数概率，且长度终止和约束器也会影响候选。

长度惩罚还会改变排名，具体公式必须和所用实现一起记录。GNMT 论文的一种长度因子为 $lp(Y)=((5+|Y|)^\alpha)/(6^\alpha)$，序列分数以 $s(Y)/lp(Y)$ 归一化，并另外使用 coverage penalty；这不是本节 $t^\alpha$ 简式的同一公式。[GNMT 原论文 §7 式 (14)](https://arxiv.org/abs/1609.08144v2#S7)

用两个合成候选隔离长度项：短候选长度 2 的逐 token 对数概率为 $-0.8,-1.2$，所以 $s=-2.0$；长候选长度 3 的逐 token 对数概率为 $-0.6,-0.7,-0.8$，所以 $s=-2.1$。取 $\alpha=0.6$，短候选 $lp=(7/6)^{0.6}\approx1.097$，归一化分数约 $-2.0/1.097=-1.823$；长候选 $lp=(8/6)^{0.6}\approx1.188$，分数约 $-2.1/1.188=-1.768$。因为分数越大越好，长度归一化后长候选反超。这里省略 coverage 项，数字只展示排序机制；它不说明长答案更正确，也不表示所有 beam 实现都采用 GNMT 公式。

## 4.4 Sampling：用受控随机性换取多样性

sampling 按概率分布随机选择下一个 token：

~~~math
y_t\sim p_t^{\mathrm{decode}}.
~~~

它适合创意写作、头脑风暴、开放式对话、多候选生成和 self-consistency。随机性也带来代价：同一输入可能得到不同答案，低概率 token 可能把生成带到错误或格式不稳定的路径。

sampling 不是“完全随机”。temperature、top-k、top-p、min-p 和结构化约束共同定义了可采样的分布。一个好的默认策略通常先从 greedy 或低温 sampling 建立基线，再一次改变一个参数，观察质量、长度、格式合法率和尾延迟。

## 4.5 Temperature：改变分布的尖锐程度

### 4.5.1 公式和直觉

temperature 为 T 且 T>0 时：

~~~math
p_i(T)
=
\frac{\exp(z_i/T)}
{\sum_{j=1}^{V}\exp(z_j/T)}.
~~~

用三个 logits $(2,1,0)$ 手算。$T=1$ 时 softmax 约为 $(0.665,0.245,0.090)$；$T=2$ 时先除以 2，得到 logits $(1,0.5,0)$，概率约为 $(0.507,0.307,0.186)$；$T=0.5$ 时 logits 变为 $(4,2,0)$，概率约为 $(0.867,0.117,0.016)$。三种温度下最大值仍是第一个 token，因为除以正数保持 logit 次序；sampling 的概率质量却明显变化。数值按三位小数取整，求和误差来自舍入。

T 小于 1 时，logit 差异被放大，分布更尖；T 大于 1 时，差异被压平，分布更均匀。极限上，T 趋近于 0 时趋向 argmax，但实际 runtime 通常把 temperature=0 解释为 greedy，而不是执行浮点除以零。

temperature 改变的是选择分布，不改变模型前向的 hidden state 或 logits。它也不保证温度越低事实性越好：如果模型的最高概率答案本身是错的，低温会更稳定地重复这个错误；高温则增加探索，也可能增加幻觉。

### 4.5.2 用熵理解随机性

分布熵为：

~~~math
H(p)=-\sum_i p_i\log p_i.
~~~

一般而言，温度升高会让分布熵上升，但经过 top-k/top-p 过滤后，这个关系会受到候选集合变化影响。两个请求使用相同 T，若一个上下文让模型非常确定、另一个让模型很不确定，它们的有效候选数和输出多样性仍可能不同。

### 4.5.3 任务边界

结构化抽取、工具参数和需要可复现的回归通常从低温或 greedy 开始；创作和多候选探索可以提高温度，但必须有长度、敏感内容和成本限制。代码生成即使使用低温，也需要编译、测试或静态分析验证；温度不是代码正确性的证明。

## 4.6 Top-k、top-p 与 min-p：如何截断长尾

### 4.6.1 Top-k 固定候选数

top-k 只保留 logit 最大的 k 个 token。记候选集合为 C_k：

~~~math
\mathcal{C}_k=\mathrm{TopK}(z,k).
~~~

过滤后重新归一化：

~~~math
p_i^{(k)}
=
\begin{cases}
\displaystyle\frac{\exp(z_i)}
{\sum_{j\in\mathcal{C}_k}\exp(z_j)}, & i\in\mathcal{C}_k,\\[6pt]
0, & i\notin\mathcal{C}_k.
\end{cases}
~~~

k 小时生成更集中，k 大时保留更多长尾。固定候选数的优点是直观，缺点是没有根据模型当前的不确定性调整：模型很确定时可能保留过多，模型不确定时又可能截断得过早。

本章的定义取 `1\leq k\leq V`。有些 runtime 会把超过词表大小的 k 自动截断为 V，但这属于接口约定，不能让不同实现悄悄产生不同实验条件。

还要处理第 k 位并列。设 logits 为 A=1、B=0、C=0，k=2；若 tie-break 把 B 纳入，重归一化后 A、B 的概率约为 0.731、0.269；若把 C 纳入，则 C 替代 B。概率数值看似相同，但候选语义不同；若后续还有 grammar mask 或 token 专属规则，输出分支也会不同。回归集中应加入并列 logits，并记录 tie policy 与 runtime revision；固定随机 seed 本身不能决定并列候选如何选择。

### 4.6.2 Top-p 按概率质量自适应

先按概率降序排列 token，得到 i_1,i_2,...。top-p 取累计概率达到 p 的最小集合：

~~~math
\mathcal{C}_p=\{i_1,\ldots,i_m\},\qquad
m=\min\left\{r:
\sum_{a=1}^{r}p_{i_a}\ge p\right\}.
~~~

p 较低时，候选集合更小；分布变平时，集合会自动扩大。它比固定 k 更能适应上下文不确定性，这也是 nucleus sampling 的主要动机。

top-p 的 p 是概率质量，不是“保留 p 个 token”。过滤后的分布必须重新归一化；如果实现只把低概率 token 置零却忘记归一化，采样阈值会产生错误。

同一个 top-p 值也不会在整段输出里固定保留相同数量。假设一步的分布为 $(0.80,0.10,0.05,0.05)$，取 $p=0.90$ 时前两个候选已达到阈值；另一步分布为 $(0.30,0.25,0.20,0.15,0.10)$，需保留前四项才累计到 0.90。模型越不确定，候选集合通常越大，采样的选择和实现的筛选开销会随上下文变化；因此不能只按一个平均候选数估算输出行为。

这里要求 `0<p\leq1`，输入概率是非负且总和为正的有限数。`p=0` 没有“最小候选集合”这一通常语义，`p>1` 则无法达到累计阈值；服务应在配置解析阶段拒绝它们，或者明确记录自己的兼容行为。

### 4.6.3 Min-p 与其他长尾策略

在讨论 min-p 前，先看一条不同的路线：locally typical sampling 不按概率从大到小排，而是看一个 token 的 surprisal 是否接近当前分布的熵。它针对的观察是：极高概率 token 可能过于可预测，贪心或窄候选集容易重复；但极低概率 token 又可能太意外。Meister 等人在摘要和故事生成实验中报告，locally typical sampling 的质量与 top-k/nucleus 有竞争力，并减少了所测设置中的退化重复；这是特定模型和任务下的证据，不意味着它对所有对话都更自然。[Locally Typical Sampling](https://aclanthology.org/2023.tacl-1.7/)

若当前分布为 p，先计算熵 H(p)，再按每个正概率 token 的 surprisal 与熵的距离排序：

~~~math
H(p)=-\sum_{i:p_i>0}p_i\log p_i,
\qquad
d_i=\left|-\log p_i-H(p)\right|.
~~~

locally typical sampling 按 d_i 从小到大加入候选，直到候选累计概率达到阈值 tau，再对候选重新归一化。它希望保留“信息量接近本步平均值”的 token，不是单纯挑最高概率 token。例：若 p=(0.40,0.30,0.20,0.10)，则 H(p) 约为 1.280 nat；按 surprisal 与熵的距离排序，候选顺序是概率 0.30、0.20、0.40、0.10。取 tau=0.40 时会保留前两个，概率 0.30 和 0.20；top-p=0.40 则只保留概率 0.40 的 token。候选集合不同，说明参数值不能跨策略互换。

min-p 用当前最大概率 p_max 作为参照，保留相对概率不低于阈值 alpha 的 token：

~~~math
\mathcal{C}_{\mathrm{min\text{-}p}}
=
\left\{i:p_i\ge\alpha\max_jp_j\right\},
\qquad 0\le\alpha\le1.
~~~

当模型非常确定时，只有接近第一名的 token 被保留；当分布比较平时，更多 token 可能留下。它和 top-p 的控制变量不同，不能把参数数值直接互换。原始 min-p 论文在 GPQA、GSM8K 和创意写作等实验中报告高温度下的质量/多样性改善；2025 年一篇独立复核论文重新分析其人评和 benchmark，认为在控制超参数数量后，现有证据不足以支持它普遍优于只用温度或 top-p。两者的设置与分析存在争议，稳妥结论是 min-p 提供了另一种截断规则，质量优势应在固定任务、模型和调参预算下实测，不能从论文摘要或 runtime 支持推出来。[原始研究 v8](https://arxiv.org/abs/2407.01082v8)；[批判性复核 v2](https://arxiv.org/abs/2506.13681v2)。

公式中的 `0\leq\alpha\leq1` 是常见参数域；候选概率必须来自非空、有限且总和为正的分布，因此最大概率必须存在且为正。alpha=0 会保留所有候选，alpha=1 通常只保留达到最大概率的候选，但并列最大值可能不止一个。

将四种方法放在同一个玩具分布上逐步计算。设 token A、B、C、D 的概率为 $(0.40,0.30,0.20,0.10)$：

1. `top-k=2` 保留 A、B，原质量为 $0.40+0.30=0.70$；重归一化后是 $0.40/0.70=4/7\approx0.571$ 与 $0.30/0.70=3/7\approx0.429$。
2. `top-p=0.40` 从最高概率开始累加，只需 A 就达到阈值，因此过滤后 A 的新概率为 1。它不是保留 40% 的 token，也不是保留 40% 的总候选数量。
3. locally typical 的熵约为 $H=1.280$ nat，按 surprisal 距离排序为 B、C、A、D。取阈值 $\tau=0.40$，先留下 B、再留下 C，原质量为 0.50；重归一化后 B、C 分别为 $0.30/0.50=0.60$ 和 $0.20/0.50=0.40$。
4. `min-p=0.30` 的门槛是 $0.30\times0.40=0.12$，所以 A、B、C 入选，原质量为 0.90；重归一化后概率约为 0.444、0.333、0.222。

同一个分布因此产生不同候选和不同抽样概率：top-p 按累计质量截断，typical 按 surprisal 接近熵排序，min-p 按相对最大概率设底线。组合多个过滤器时，保留下来的集合相当于各规则的交集，采样前必须对交集里的概率重新归一化；过滤的先后顺序仍可能改变集合。Transformers v5.20.0 与 vLLM v0.32.0 文档均公开相关参数，但默认值、处理顺序和组合语义属于各自版本契约，部署时应固定版本核对。[Transformers v5.20.0 GenerationConfig](https://huggingface.co/docs/transformers/v5.20.0/en/main_classes/text_generation)；[vLLM v0.32.0 SamplingParams](https://docs.vllm.ai/en/v0.32.0/api/vllm/sampling_params/)。

顺序差异可以直接改变候选集。设 logits 为 $(2,1,0)$、阈值 top-p=0.85：先用 $T=1$ 得到约 $(0.665,0.245,0.090)$，累计前两项为 0.910，因此只留下前两个 token；先把 temperature 改为 $T=2$，分布变为约 $(0.506,0.307,0.186)$，前两项只有 0.813，top-p 必须再留下第三项。也就是说，即使 top-p 数值不变，temperature 顺序也会改变哪些 token 能被抽中。

top-p 的边界是离散的：在 $p=(0.40,0.30,0.20,0.10)$ 上，阈值 0.70 恰好由 A、B 达到；把阈值提高到 0.71，算法必须把整个 C 一并留下，不能只从 C 的概率里“借”0.01。过滤后候选数会跳变，重归一化也随之改变整个分布。因此线上回归除了检查最终文本，还应记录抽样配置与 processor 顺序；若需要诊断随机差异，应在可观测时记录候选/概率摘要，不能只靠最终字符串反推是哪一步造成变化。

| 策略 | 选择规则 | 代表研究解决的问题 | 证据和边界 |
| --- | --- | --- | --- |
| Top-p / nucleus | 按 p_i 从高到低，保留累计质量达到 p 的最小集合 | Holtzman 等人针对神经文本生成中高概率解码容易枯燥、重复的问题，提出按上下文概率质量自适应截断 | 候选数会随分布变化，但效果依赖温度和 p；论文任务结论不能替代目标模型上的调参。 |
| Locally typical | 按 token surprisal 与当前熵的距离排序，再累计到 tau | 用局部信息量而不是单纯概率排名选择 token；作者在故事生成/摘要中报告与 nucleus/top-k 质量相近并减少特定退化重复 | 这是信息论动机和特定任务结果，不保证适用于代码、结构化输出或任意聊天。 |
| Min-p | 保留 p_i >= alpha * max(p) 的 token | 以当前模型置信度缩放阈值，避免固定概率质量阈值在不同分布下行为不合适 | 原论文声称高温度下收益；后续复核对其人评与调参公平性提出反证。作为可选候选策略比较，不默认其质量优于 top-p。 |

eta/epsilon 截断等方法仍是相关文献和部分库接口中的支持性知识点：eta 结合绝对概率底线与熵尺度，epsilon 使用绝对概率阈值；本章不展开推导，接口和参数范围见 Transformers 文档及 [Truncation Sampling as Language Model Desmoothing](https://arxiv.org/abs/2210.15191)。

### 4.6.4 组合顺序会改变结果

常见组合是先对 logits 应用 penalty，再做 temperature，再做 top-k/top-p，最后归一化和采样；也有实现使用不同顺序。由于 temperature 会改变相对概率，先过滤还是后过滤会改变候选集合。工程上不要只记录“temperature=0.7, top_p=0.9”，还要记录 processor 顺序和是否设置 min_tokens、logit bias、bad words 或 grammar mask。

如果 top-k、top-p 或 min-p 过滤后候选为空，runtime 必须有明确回退策略：无 grammar 的普通采样可以保留原始最高概率 token；启用 grammar 时则须在合法集合内回退或返回 no-valid-token 错误。不能把越过 grammar 的 token 当作正常回退，也不能让空集合流入 softmax 产生 NaN。这个边界应由运行时回归覆盖。

约束 mask 与截断规则组合时，回退还不能破坏语法。假设概率为 A=0.50、B=0.30、C=0.20，而 grammar 只允许 B、C；若先用 top-k=1 选中 A，再与 grammar 集合取交集，候选就会变空。无条件回退到全词表最高概率 A 会违背 grammar。实现可以先构造合法集合再截断，使 B、C 内的质量归一化为 0.30/0.50=0.60 和 0.20/0.50=0.40；也可以报告 no-valid-token，但不能默默放宽协议。真正选择哪种顺序是 runtime 合同，需与 grammar 和 sampler 一起做回归。

## 4.7 Repetition、presence 和 frequency penalty

### 4.7.1 三个概念不是同一个参数

设历史中 token i 出现次数为 c_i：

1. presence penalty 只关心 c_i 是否大于 0。
2. frequency penalty 随 c_i 增大而增强。
3. repetition penalty 通常是对已出现 token 的 logit 做乘法式变换，具体规则取决于实现。

一个便于理解的 additive 抽象是：

~~~math
\widetilde z_i
=z_i
-\lambda_{\mathrm{presence}}\mathbf{1}[c_i>0]
-\lambda_{\mathrm{frequency}}c_i.
~~~

presence 项对首次出现过的 token 一次性扣分，frequency 项每重复一次继续扣分。它们更像鼓励新内容或压低高频重复，并不理解词语在句法、代码或数学中的必要性。

还要核对“历史”从哪里开始计数。Transformers v5.20.0 的 decoder-only repetition penalty 默认把 prompt token 纳入历史，并提供忽略输入前缀的配置；vLLM v0.32.0 文档则把 presence/frequency 描述为针对已生成文本，把 repetition penalty 描述为针对 prompt 与生成文本。用户提示里若包含必须原样复述的专名、代码或法条，计数范围会改变后续 logit，应记录 history scope 和对应 runtime 参数，而不是只保存 penalty 数值。[Transformers v5.20.0](https://huggingface.co/docs/transformers/v5.20.0/en/main_classes/text_generation)；[vLLM v0.32.0 SamplingParams](https://docs.vllm.ai/en/v0.32.0/api/vllm/sampling_params/)。

在这个 additive 抽象中，`c_i` 是非负整数，两个 penalty 通常取非负数；如果业务确实要奖励重复，也应把它记录为另一种明确的策略，而不是把负 penalty 与常规参数混在一起。repetition penalty 的乘除式实现还要求 `r>0`，常见的“惩罚”区间是 `r\geq1`。

### 4.7.2 Repetition penalty 的符号敏感性

Hugging Face 一类实现常见的 repetition penalty 直觉是：对历史 token，如果 logit 为正则除以 r，如果 logit 为负则乘以 r，r>1：

~~~math
\widetilde z_i=
\begin{cases}
z_i/r,&z_i>0,\\
z_i r,&z_i\le0,
\end{cases}
\qquad i\in\mathcal{H}.
~~~

H 是已经出现过的 token 集合。因为负 logit 乘以 r 会变得更负，这个变换与简单减常数不同。OpenAI 风格的 presence/frequency 参数、Transformers 的 RepetitionPenaltyLogitsProcessor 和其他 runtime 可能使用不同接口；不要把它们的数值当成同义参数。

### 4.7.3 过度惩罚的失败模式

代码中的括号、变量名、缩进标记、JSON 的引号和列表结构可能需要重复；数学证明中的符号、引用中的专名也可能合法重复。penalty 太强会造成：

1. 句法不自然，模型为了避开重复而换用错误词。
2. JSON key 或工具字段被改写，schema 校验失败。
3. 代码变量和 API 名称被错误替换。
4. 长文本为了追求新 token 而出现主题漂移。

应按任务和 token 类型评估重复率、格式合法率、事实性和测试通过率，而不是把 repetition rate 越低当成越好。

### 4.7.4 逐 token 算一次惩罚

设三个候选 token A、B、C 的原始 logits 分别为 2.0、1.5、1.2，历史里 A 出现两次、B 出现一次，取 presence penalty 0.4、frequency penalty 0.3。A 的新分数为 $2.0-0.4-2\times0.3=1.0$，B 为 $1.5-0.4-0.3=0.8$，C 没出现过，仍为 1.2。原先 greedy 会选 A；惩罚后会选 C。概率归一化后 C 的相对优势还会取决于词表中其他 logits，但这一步已说明 penalty 是对每个 token ID 的历史计数作变换，不是理解句意后删掉“坏重复”。

若改用 repetition penalty $r=1.5$，A 的正 logit 2.0 会变成 $2.0/1.5\approx1.33$；一个未出现过但 logit 为 $-1.0$ 的 D 不应被此规则修改，若 D 已在历史集合中才会变成 $-1.0\times1.5=-1.5$。所以同样写成“1.5”的参数与上面的 additive penalty 完全不是同一量纲。这个局部例子不能预测文本质量；代码标识符、JSON 键和标点如果已出现，恰恰可能需要保留。

惩罚按 token ID 和计数生效，不会识别词义或相似字符串。例如 prompt 含 `New York`，若配置把 prompt 纳入历史，后续回答该地名时复用到的 token ID 会受罚；若 tokenizer 把词首、词内空格拆成不同 piece，实际受影响的也只是重用的 piece。排查专名被改写时，应并列检查历史 token IDs、history scope 与惩罚前后 logits，再评估字段或标识符准确率，不能只看表面重复率。前例的 logits $(2.0,1.5,1.2)$ 经惩罚后变成 $(1.0,0.8,1.2)$；softmax 概率从约 $(0.486,0.295,0.219)$ 变成 $(0.329,0.269,0.402)$，于是 C 从第三位升到第一位。惩罚不仅可能翻转 greedy 选择，也会重分配后续 sampling 的概率质量。

## 4.8 Stop、EOS 和最大输出

### 4.8.1 EOS 是模型 token，stop 是服务协议

EOS 是词表中的特殊 token，模型可以在生成它时表达“序列结束”。stop string 通常是服务侧根据 token 序列或 detokenized 文本判断的协议边界；它未必是词表中的单个 token。max_new_tokens 是硬上限，用于限制 GPU 工作、响应大小和成本。

一个请求可能因为不同原因结束：

| finish reason | 说明 | 处理重点 |
| --- | --- | --- |
| eos | 模型生成 EOS | 检查 EOS 配置和训练模板 |
| stop | 匹配业务停止序列 | 记录匹配位置和是否泄漏 stop 文本 |
| length | 达到最大新 token | 区分合理截断与预算不足 |
| schema_complete | 结构化状态已完成 | 还要做语义校验 |
| tool_call | 进入工具调用阶段 | 取消当前生成并验证参数 |
| cancel/timeout/error | 外部或内部中止 | 释放 cache，决定是否重试 |

把所有结束原因都记成“生成完成”，会掩盖 max token 太小、stop 错配和服务超时。

若 EOS、stop 和 max-token 上限在同一轮都可能触发，runtime 的优先级会决定返回的 finish reason、stop 字符是否被隐藏以及客户端是否看到完整对象。跨产品名称也不保证同义：有的接口返回 `length`，有的返回 incomplete 及其原因，有的工具状态单独成为一个响应项。调用方应把实际 API 的终态映射成自己的内部状态机，并保留原始 provider/runtime reason；否则两个“完成率”报表可能把截断、拒答和正常结束混在一起。

### 4.8.2 字符 stop 和 token stop 的差异

字符串 stop 需要经历 token 到文本的增量拼接。一个 stop 字符串可能跨越两个 token，UTF-8 多字节字符也可能分散在不同输出片段中；如果服务每次收到一小段 token 就立即发送，客户端可能短暂看到本应被截断的 stop 内容。token 序列 stop 可以更早判断，但必须为目标 tokenizer 预先编码，且不能假设人眼看到的字符串只对应一个 token。

生产系统应定义：stop 是否包含在最终响应、是否在流式发送前缓冲若干字符、匹配失败时如何结束、以及 stop 与 JSON/工具 grammar 哪个优先。这个协议应在客户端和服务端回归测试中固定。

一旦发现完整 stop，增量输出器还要处理同一 chunk 中 stop 后面的字节。例如配置 `#DONE` 时，当前块可能一次带回 `NE)more`；服务应依合同决定是否保留 stop 标记，丢弃其后的内容，停止追加 token，并把 `finish_reason=stop` 记入终态，不能把整块原样送给客户端。若使用方需要查看原始生成片段，应放在受控 trace 中并遵守敏感数据保留策略，不能与用户可见文本混为一份。

### 4.8.3 最大输出是成本和正确性的边界

输出上限同时影响 KV Cache 增长、GPU 时间、网络大小和任务完成率。过小会截断代码、JSON 或推理结果；过大则可能让异常循环消耗大量资源。应按 workload 设置不同上限，并记录达到 length 的比例。

对于 Agent，max_new_tokens 只是模型单轮上限，整个任务还可能包含多轮模型调用和工具等待；对 reasoning model，还应单独记录隐藏 reasoning token 或服务公开的推理预算。不要用单轮文本长度替代完整任务预算。

### 4.8.4 stop 缓冲与硬上限的请求轨迹

设服务配置 stop string 为 `#DONE`，流式解码器先收到 `lookup(#DO`，下一块才收到 `NE)`。如果每到一个 chunk 就原样推给客户端，第一块里的 `#DO` 会先泄漏，之后才发现它是停止标记的一部分。可靠的增量匹配器应保留当前输出尾部中仍可能构成 stop 前缀的部分；对单个五字符 ASCII stop，最多需要暂存其前四个字符，再把确定安全的前缀发送出去。若同时有多个 stop，应按最长候选维护匹配状态；真实 tokenizer 还要按它的解码边界处理跨 token 字符。

硬上限则是另一条终止路径。假设教学 tokenizer 把一份有效工具对象编码成 9 个新 token，且没有提前产生 EOS 或 stop：`max_new_tokens=8` 时第八个 token 后必须以 `length` 结束，哪怕前缀已像 JSON；改成 9 才有机会进入完整对象状态。服务不能把这个被截断的前缀当作 `schema_complete` 来执行。上线要分开统计 stop 命中、EOS、length、取消和 timeout，并把 stop 文本是否保留、schema complete 与 tool call 的优先级定义在同一个状态机里。输出 token 上限同时限制 KV 增长和成本，容量估算可回看第三章；上限过低会损害任务完成率，过高则扩大异常循环的资源预算。

stop 条件还可能和语法边界冲突。对嵌套 JSON 使用 `}` 作为普通 stop 时，模型可能在内层对象闭合后就被截断，外层对象尚未完成；即使前缀能 parse，也可能缺少必填字段。应优先让结构化解码器报告完整状态，或使用只在协议末尾出现的专用边界，并在服务端对最终对象重新 parse/schema-check。惩罚历史、stop 字符串和 grammar 状态共同作用于同一生成循环，配置必须作为一个整体回归。

## 4.9 Structured output：语法合法不等于业务正确

### 4.9.1 JSON mode 和 JSON Schema 的区别

JSON mode 通常表达“输出应当是可解析 JSON”；它不一定保证字段齐全、类型正确、枚举值合法或满足业务约束。JSON Schema 进一步规定对象结构、字段类型、必填项、枚举、数组和嵌套关系，但最终还需要业务层验证数值范围、权限和事实来源。

OpenAI 当前文档将 JSON mode 与 strict Structured Outputs 区分：前者保证 JSON 语法层，后者只对支持的 JSON Schema 子集承诺 schema adherence；拒答与输出不完整仍是独立终态。工具调用时应使用 function calling，面向用户返回结构化文本时使用 `text.format` 一类的响应格式。strict 函数 schema 对 object 的额外属性和 required 字段还有接口约束。以上是 OpenAI API 的公开合同，其他 provider 和开源 grammar backend 需要各自核验。[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)；[Function calling](https://developers.openai.com/api/docs/guides/function-calling)。

例如 OpenAI 的 strict function schema 要求 object 声明 `additionalProperties: false`，且 properties 中的字段都列入 required；若一个字段在业务上可选，可以把值域设计成“具体类型或 null”，但这与字段完全省略并不相同。报销工具若收到 `policy_id: null`，虽然它可能满足 schema，仍应要求制度检索或拒绝创建草稿。Responses 对不兼容的 schema 可能使用 best-effort 非 strict 行为，因此还要检查响应所采用的 strict 状态。这里是特定 API 的字段合同，不能复制成所有 JSON Schema backend 的通用规则。

可以把结构化生成拆成三层：

1. 语法层：括号、引号、逗号和 JSON lexical grammar 正确。
2. schema 层：字段、类型、required 和枚举符合约定。
3. 语义层：数值、引用、权限、业务状态和外部事实正确。

只测试第一层，会得到“能 parse 但不能用”的输出。

### 4.9.2 Constrained decoding 如何屏蔽非法 token

设当前解析器状态为 s，允许的下一 token 集合为 A(s)。约束解码可以写成：

~~~math
\widetilde z_i=
\begin{cases}
z_i,&i\in A(s),\\
-\infty,&i\notin A(s).
\end{cases}
~~~

采样一个 token i 后，解析器转移到新状态：

~~~math
s'=\delta(s,i).
~~~

其中 delta 是 grammar/JSON schema 的状态转移函数。这样可以在 token 选择时阻止明显非法的结构，而不是生成后才发现逗号或括号错误。代价是 grammar 编译、合法 token mask、词表扫描和特殊 token 处理；复杂 schema 还可能让每步约束计算变重。

沿一个只有 action 字段的 schema 看状态怎样变化：字段值只能是 lookup_policy 或 create_draft。解析器从空对象开始，允许生成左花括号；读完字段名和冒号后，只允许两个枚举字符串的合法延续；读完其中一个完整字符串后，才允许结束对象。若词表 token 是子词片段，解码器判断的是 token 解码后的字节串能否让解析器从当前状态前进，不能简单把“一个可见字符”当作“一个 token”。

| 已生成内容 | 解析状态 | 下一个 token 的约束直觉 |
| --- | --- | --- |
| 空 | 对象尚未开始 | 允许左花括号及 schema 允许的空白。 |
| {"action": | 等待枚举字符串 | 只允许 lookup_policy 或 create_draft 的合法前缀；submit 不能成为合法续写。 |
| {"action":"lookup_policy" | 枚举值已闭合 | 只允许对象结束；若 schema 还有必填字段，则允许逗号和下一个必填键。 |
| {"action":"create_draft"} | 完成状态 | 只允许约定的结束 token，之后由服务进入工具校验和执行阶段。 |

这个状态轨迹只描述语法可达性，不表示 lookup_policy 适用于当前用户，也不表示模型理解了业务意图。实际 grammar 还要处理 tokenizer 片段可能跨越引号、转义、UTF-8 或字段边界的情况；grammar 编译器必须使用与模型相同的 tokenizer/vocabulary 语义。

约束引擎也有不同的工程路线。通用 CFG 可以表达递归 JSON、SQL 等结构，但朴素实现需要在每一步对词表 token 和 parser stack 做检查。XGrammar 将 token 划分为可预处理的 context-independent 与需运行时解释的 context-dependent 两类，缓存部分 mask，并用 persistent stack 支持分支/回滚，再把 grammar 计算与 GPU 推理重叠；论文在 Llama-3.1-8B-Instruct、AMD Ryzen 9 7950X + RTX 4090 的约束引擎测量中报告 JSON Schema 最多约 3 倍、CFG JSON 超过 100 倍于各自最佳对照的 token-mask 速度，端到端结果绑定其 SGLang/MLC-LLM、batch、硬件和语法 workload。[XGrammar 原论文 v3](https://arxiv.org/abs/2411.15100v3)。

另一项 grammar-constrained decoding 研究把重点放在 subword tokenizer 与 CFG 边界的 sound alignment，报告常见 grammar 的离线 preprocessing 比既有方法快 17.71 倍，同时保持有竞争力的在线 mask 计算。这个 17.71 倍是预处理时间，不是每 token decode 或端到端服务加速。[Flexible and Efficient Grammar-Constrained Decoding v2](https://arxiv.org/abs/2502.05111v2)。

| 路线 | 核心问题 | 主要代价与边界 |
| --- | --- | --- |
| JSON Schema/regex 转 grammar | 用相对紧凑的接口描述常见对象、字段和模式 | 各后端支持的 schema 子集不同；编译成功也不等于所有业务语义已编码。 |
| 通用 CFG/PDA 约束 | 处理递归、嵌套和领域语法 | 要维护 parser stack，并解决 token 字节与语法终结符的对齐；朴素逐步扫描词表开销可能明显。 |
| XGrammar mask cache | 降低 CFG 每步 mask 生成成本，并与模型执行重叠 | 收益取决于 grammar、tokenizer、batch、引擎和瓶颈；论文中的最高倍率不能外推为所有请求都近零开销。 |
| tokenizer/grammar sound alignment | 缩短 grammar 初始化预处理，同时保证子词边界判定正确 | 论文报告的 17.71 倍只针对离线预处理；在线和端到端服务仍须单独测量。 |

框架也可能在不同版本切换后端或不支持部分 JSON Schema keyword。vLLM v0.32.0 的指南列出 XGrammar 和 Guidance 两个 backend，并说明 `auto` 会依请求选择；regex 方言和支持范围随 backend 而异。上线时应固定 vLLM/grammar backend 版本，对实际 schema 做编译和输出回归，而不能从“支持 JSON Schema”推断全量标准覆盖。[vLLM v0.32.0 structured outputs](https://docs.vllm.ai/en/v0.32.0/features/structured_outputs/)。

### 4.9.3 约束解码的失败边界

约束器不能自动保证：

1. 模型填写的数值真实。
2. 引用的文档支持它的 claim。
3. 工具参数拥有调用权限。
4. 输出不会泄漏敏感字段。
5. schema 本身没有表达错误。

约束过严还可能造成“没有合法 token”的状态，或使模型为了满足语法而输出无意义字段。服务需要区分 grammar compile error、no-valid-token、schema parse failure、semantic validation failure 和工具执行失败，并在 trace 中分别记录。

grammar compile error 应在部署检查或请求配置阶段暴露，不能伪装成模型生成失败。上线前用实际 schema、tokenizer 和 backend 做编译/生成回归，并记录 schema hash、runtime revision 与 backend 名称；运行时测量则分别报告首次编译耗时和后续每 token 约束耗时。XGrammar 论文的 token-mask 吞吐对照与端到端服务延迟是不同指标，只有在确认 grammar 阶段确为瓶颈后，才有理由为缓存或并行化投入工程成本。

看首编译能否摊销，可做一组明确标注的串行假设：若每份 schema 首次编译需 120 ms、每个请求生成需 600 ms，100 个请求都重新编译总计为 $(120+600)\times100=72{,}000$ ms；同一 schema 命中缓存后，只有一次编译，合计 $120+600\times100=60{,}120$ ms，少 11.88 秒，约为前者的 16.5%。这是把编译和生成串行相加的教学账本，不是并发服务的吞吐预测。缓存键至少要区分 schema hash、tokenizer/model revision 和 backend；多租户 schema 若含用户权限约束，还须避免因错误复用而跨租户共享规则。

还要处理模型拒答、用户取消、长度上限截断和 schema/backend 不支持等非正常终态；它们不能被计入 schema 成功率，也不能把不完整前缀交给有副作用的工具执行。

### 4.9.4 工具调用是一个状态机

工具调用不是把 JSON 字符串传给任意函数。更合理的状态转换是：

~~~text
assistant text
  -> tool-call schema
  -> parse and validate arguments
  -> authorization and policy check
  -> execute tool in its allowed scope
  -> append result with provenance
  -> resume model or return
~~~

模型输出的 name、arguments、版本和权限域都要验证；超时重试还要考虑工具是否有副作用。OpenAI 当前 function calling 文档说明 strict mode 有额外 schema 要求；Responses 在未明确指定 strict 时可能尝试规范化 schema，不兼容时会退回 best-effort 行为。调用方应检查实际启用的合同，解析参数并独立校验权限、金额范围、状态和幂等键。[OpenAI Function calling guide](https://developers.openai.com/api/docs/guides/function-calling)。结构化解码改善的是协议正确率，不会自动解决 prompt injection 或越权，安全边界放在工具执行层。

生成与执行之间还隔着时间和版本边界。假设请求开始时绑定的 schema v4 允许 `create_draft`，但模型返回后账户策略已经切到 v5 并暂停该动作：输出即使严格符合 v4，也不能据此执行。trace 应记录生成时的 schema hash 和 runtime revision；真正执行前仍按当下用户身份、账户状态和策略版本重新授权。schema hash 是解释模型为何产生该结构的证据，不是授权凭证；发生策略变更时应拒绝、重新规划或让调用方显式重试，不能只因语法通过就沿用旧权限。

### 4.9.5 从可解析对象走到可执行动作

假设 schema 规定 `action` 只能取 `lookup_policy` 或 `create_draft`，`amount` 是数字，`currency` 是 `USD` 或 `EUR`，而应用另规定单笔草稿金额不能超过 5,000。模型返回 `{"action":"create_draft","amount":6800,"currency":"USD"}`：JSON parser 能读出一个对象；schema 检查发现 action、number 和 currency 类型/枚举均合法；业务检查却因 $6800>5000$ 拒绝该动作。grammar 可以让生成过程避开字段拼写和类型错误，但若金额上限没有进入受支持的 schema 约束，不能凭语法合法性把 6,800 当成可报销金额。即使把上限写入 schema，权限仍要查当前用户身份和账户状态。

再看一组明确标为假设的 100 条测试请求。92 条通过 JSON parse；其中 86 条通过 schema，72 条通过业务语义校验，68 条通过授权，最终 65 条工具调用成功。按总体请求数，成功率为 $65/100=65\%$；按阶段分母，parse 失败为 $8/100$，schema 失败为 $6/92\approx6.5\%$，语义失败为 $14/86\approx16.3\%$，授权失败为 $4/72\approx5.6\%$，执行失败为 $3/68\approx4.4\%$。若 grammar 只修复前两类格式问题，它不能据此声称解决剩下 21 条业务、权限和执行失败；报告时要保留每级分母，并把 refusal、incomplete、取消和 schema/backend 编译错误另列，避免把它们混进有效输出分母。这个漏斗是教学计数，不是产品测量值。

## 4.10 Reasoning effort 与普通随机性

`reasoning.effort`、`thinking_level` 或 low/high/max 一类字段是 model/provider 定义的运行时控制面。官方文档可能公开档位、默认值、预算上限或计费行为；未公开的内部 token 分配、工具/验证器调度和服务路由不能从字段名称推断。它不是 temperature、top-k 或 top-p 的同义参数，也不能仅凭同名档位推断各 provider 执行了相同的计算。

官方 API 的定义说明它是独立控制面，但不同产品的名字不代表相同计算量。OpenAI 当前 Responses 文档使用 `reasoning.effort`，列出的值和默认值依模型而异；Gemini 文档提供 `thinking_level`，且其 `max_output_tokens` 上限包含 thought tokens，触顶时可能以 incomplete 结束。具体支持值、默认值和影响会变化，不能把一个产品的 low 与另一产品的 low 当作等价档位。[OpenAI Reasoning guide](https://developers.openai.com/api/docs/guides/reasoning)；[Gemini thinking guide](https://ai.google.dev/gemini-api/docs/thinking)。

若所选口径能定义互不重复的成本分项，可以把一次任务的成本粗略拆成：

~~~math
C_{\mathrm{request}}
=c_{\mathrm{visible}}N_{\mathrm{visible}}
+c_{\mathrm{reason}}N_{\mathrm{reason}}
+c_{\mathrm{verifier}}N_{\mathrm{verifier}}
+c_{\mathrm{tool}}N_{\mathrm{tool}}
+c_{\mathrm{wall}}T_{\mathrm{wall}}.
~~~

N_visible 是用户可见输出 token，N_reason 是隐藏或内部推理 token，N_verifier 是验证器调用次数，N_tool 是工具调用次数，T_wall 是任务占用的墙钟时间，c_* 是对应单位成本。这个式子不是供应商计费公式；若 token/tool 项已含同一段 GPU 资源费用，就不能再把它重复计入墙钟项。它要表达的是：降低 temperature 不一定减少 reasoning token，提高 reasoning effort 也不一定只增加可见文本。

上线比较 reasoning model 时，应固定模型版本、effort/level、最大输出、工具配置、chat template 和 harness，同时记录任务正确率、过程/结果 verifier、P95、总 token 和单位成功任务成本。不同供应商字段不能直接互换，模型公开说明与服务 API 语义也要分开引用。

把成本账本落到数字上。假设一组 100 个请求中，low 设置完成 82 个任务，累计使用 5,000 个 reasoning token 和 3,000 个可见 token；high 设置完成 90 个任务，分别使用 12,000 和 3,200 个 token。为课堂演算，设 reasoning token 每千个计 2 个成本点、可见 token 每千个计 1 点，且暂不计算输入、工具、验证器和墙钟费用，则 low 的总成本为 $2\times5+3=13$ 点，单位成功成本为 $13/82\approx0.159$ 点；high 为 $2\times12+3.2=27.2$ 点，单位成功成本为 $27.2/90\approx0.302$ 点。这个假设场景里成功率从 82% 升到 90%，但单位成功成本约为 1.9 倍；若产品目标是最低延迟或预算上限，high 未必是更好的选项。

这组数字不是供应商价格或模型测量。reasoning token 只有在 API usage 明确提供时才能直接使用；若 provider 不公开，不能从可见文本长度反推内部 token 数，应以可得的账单、总 token 字段和墙钟时间分别记录。上线还要固定同一测试集、输出上限和工具预算，按模型分别绘制成功率、P95 与成本曲线；增加 effort 的收益须由目标任务的评测决定，不能从官方参数名称直接推断。

还要区分“计算档位”和“硬 token 上限”。假设一项 Gemini 请求的 `max_output_tokens` 设为 512，某次运行已经消耗 390 个 thought token，最多只剩 $512-390=122$ 个位置给可见输出；若对象必须再生成 200 个 token，接口可能以 incomplete 结束。这个算术是容量上界，不表示模型会固定花 390 个 thought token；下一次请求的内部使用量可能不同。Gemini 文档也说明，达到上限会硬截断，并仍按已经生成的思考 token 计费。因此不能只看最终可见文本少于 512 就以为预算充足。

在服务侧，可以先按任务难度路由，再比较每个档位的边际收益：简单分类先测低档，涉及多条件判断的任务测试 medium/high；若高档只改善少数边界样本，却让大多数请求 P95 和单位成功成本明显上升，可以只对高风险类别使用它，或加 verifier 兜底。当前接口还可能让同一 effort 对不同输入自适应分配不同数量的推理 token，所以预算应记录分布和尾部，不把 low/high 当作一个固定 token 额度。[Gemini thinking guide](https://ai.google.dev/gemini-api/docs/thinking)；[OpenAI Reasoning guide](https://developers.openai.com/api/docs/guides/reasoning)。

还可以把“总成本/成功数”和“多投入后新增一个成功的成本”分开计算。沿用上例，high 比 low 多花 $27.2-13=14.2$ 个假设成本点，多完成 $90-82=8$ 个任务，边际成本为 $14.2/8=1.775$ 点/新增成功；high 的平均单位成功成本仍是 $27.2/90\approx0.302$ 点。若预算决策只关注新增成功值不值得，应报告前一个分母；若比较两个方案整体效率，则报告后一个分母。两者都不能替代 P95、失败类别和任务切片。

接口兼容也要按 model revision 列表核对。某模型可能不接受 `none` 或某个 effort level，另一个模型的默认值也可能不同；服务若把不支持的值静默映射到相邻档位，实验配置和线上行为就会分离。部署 manifest 应保存 provider、model snapshot、API mode、实际发送的字段和返回状态；这让预算变更能回放，也避免把一项供应商的推理档位直接映射成另一 runtime 的 token budget。

## 4.11 Speculative decoding：用小模型猜，大模型验

### 4.11.1 为什么它属于解码控制

普通 decode 每生成一个 token 就要调用一次大模型。speculative decoding 让一个较小的 draft model 先提出 k 个候选 token，再由 target model 一次前向并行验证这段候选。若多个 token 被接受，target model 的一次工作就推进了多个位置，减少了大模型逐 token 调用的串行开销。

基本流程是：

~~~text
target context
  -> draft proposes y_1 ... y_k
  -> target scores all proposed positions
  -> accept a prefix, or sample a correction token
  -> append accepted tokens
  -> repeat
~~~

draft model 不需要和 target 完全相同，但必须共享兼容的 tokenizer 或有可靠的映射。草稿越接近 target，接受长度越长；草稿越慢、越不准，额外工作可能抵消收益。

### 4.11.2 接受率和吞吐直觉

令 a_j 表示前 j 个草稿 token 全部依次被 target 接受的联合概率。一轮验证通过后，算法提交已接受的草稿前缀；若没有提前遇到 EOS/stop，通常还会从 target 的下一位置分布提交一个 bonus token。因此平均提交 token 数为：

~~~math
E[N_{\mathrm{committed}}]
=
1+\sum_{j=1}^{k}a_j.
~~~

额外的 1 是拒绝时的 target correction token，或全部接受后的 bonus token；a_j 必须是“前 j 个连续候选都接受”的联合概率，不能把每个位置的独立/条件接受率直接相加。若第 j 个位置在前面都接受的条件下接受率为 alpha_j，则 $a_j=\prod_{m=1}^{j}\alpha_m$。若一轮 target 验证成本为 C_target(k)，draft 生成 k 个 token 的成本为 k C_draft，则粗略吞吐直觉是：

~~~math
\mathrm{tokens\ per\ round}
\approx
\frac{E[N_{\mathrm{committed}}]}
{C_{\mathrm{target}}(k)+kC_{\mathrm{draft}}}.
~~~

这不是硬件 benchmark。target 的一次并行验证、draft 的 KV Cache、额外 kernel、通信和 batch 调度都会影响真实成本。接受率不应单独报告，必须和 target/draft latency、最终 TPOT、显存和质量一起看。

用一组假设成本看 break-even。设 $k=3$，前缀接受率分别为 $\alpha_1=0.8$、$\alpha_2=0.6$、$\alpha_3=0.5$，则连续接受概率为 $a_1=0.8$、$a_2=0.8\times0.6=0.48$、$a_3=0.8\times0.6\times0.5=0.24$，平均每轮提交 $1+0.8+0.48+0.24=2.52$ 个 token。再假设 target 对这三个位置的并行验证花 1.3 个成本单位，draft 每个候选花 0.15 单位，则一轮总成本为 $1.3+3\times0.15=1.75$，单位成本提交量约为 $2.52/1.75=1.44$ token/单位。若普通 target 每 token 花 1 单位，相同平均产出成本是 2.52 单位；这个玩具账本显示有加速空间，但只有在实际 target 批验证确实花 1.3 单位、draft 有效成本确实为 0.15 时才成立，不能把 1.44 当成实测 speedup。

这个期望还假设候选链长度固定为 $k$，验证过程没有被 EOS、stop 或请求上限提前截断，并且每轮都能产生定义中的 correction/bonus token。若第三个草稿位置常常就是 EOS，则它后面的位置对用户输出没有价值，实际提交量要按停止状态截短；若 stop string 可以在候选内部出现，也要在验证时回滚或终止后续候选。部署评估应从真实请求 trace 统计每轮接受长度、EOS/stop 位置和部分轮成本，而不是把理论均值直接乘以平均轮数估算整段输出。

### 4.11.3 Sampling 下如何保持分布

在 greedy 模式下，可以直接比较 target 的 argmax 与 draft token；在 sampling 模式下，如果要求最终分布仍等于 target 分布，典型 rejection sampling 会用 target 分布 p 和 draft 分布 q 做接受概率：

~~~math
a_i=\min\left(1,\frac{p_i}{q_i}\right).
~~~

拒绝某个 draft token 后，可从残差分布采样：

~~~math
r_i=
\frac{\max(0,p_i-q_i)}
{\sum_j\max(0,p_j-q_j)}.
~~~

这里的残差归一化分母记为 $Z_r=\sum_j\max(0,p_j-q_j)$。只有 $Z_r>0$ 时上式才定义；若 $Z_r=0$，精确算术下拒绝概率应为零，因此不应进入残差采样分支。若实现仍然进入该分支，说明概率计算、候选支持或浮点处理不一致，应记录为 invariant failure 并使用明确定义的 target fallback，不能把除零后的 NaN 当成 token 概率。若只在截断后的候选集合上计算残差，还要记录被截断的质量和分布保持假设。

实现可能使用不同的高效近似或限制候选集合；工程师不能把“speculative”自动理解成分布完全不变。应核对 runtime 文档、随机数口径和与无 speculative baseline 的分布/质量回归。

用一个小分布手算接受与回退。令 target 分布 p=(0.50,0.30,0.20)，draft 分布 q=(0.20,0.50,0.30)，token 依次为 A、B、C。draft 提议 B 的概率是 0.50；target 给 B 的概率是 0.30，因此接受概率是 0.30/0.50=0.60。若拒绝，残差 max(p-q,0)=(0.30,0,0)，归一化后只能回退到 A。

把三个可能的 draft 提议都列出，能看到最终分布为何仍等于 p：A 以 0.20 的概率直接接受；B 以 0.30 的概率接受，另外 0.20 的拒绝概率回退到 A；C 以 0.20 的概率接受，另外 0.10 的拒绝概率回退到 A。最终 A 的总概率为 0.20+0.20+0.10=0.50，B 为 0.30，C 为 0.20。该算例说明的是单步分布校正，不是吞吐实验。推导假设 p、q 是同一词表上的合法分布，draft token 按 q 提议，拒绝时使用未归一化残差；若 p=q，则残差总和为零且不会发生理论拒绝。实际系统需要覆盖浮点误差和有限精度下的零残差路径。

这里的“分布不变”表示每一步提交 token 的概率分布与 target 一致，不表示给定同一个随机 seed 必定逐 token 重现普通 decode 的那条输出。p 还必须是目标解码策略真正想执行的分布；若目标使用 temperature、top-p、grammar mask 或 logit bias，必须明确定义这些处理在 target 与 verifier 中怎样组合。固定 seed、相同 API 参数或相同模型名字都不足以证明分布等价。

### 4.11.4 Speculative decoding 的边界

它可能没有收益的情况包括：

1. draft model 与 target 差异大，接受率低。
2. draft 调用、tokenizer 映射或通信成本高。
3. target batch 已足够大，主要瓶颈不在单请求串行。
4. 结构化 grammar 使 draft 大量提出非法 token。
5. 长上下文 cache 读取和显存已是瓶颈，额外 draft state 让显存更紧。
6. 工具调用或动态 stop 使候选很快失效。

并行验证减少串行前向，不会消除候选状态管理。target 要为草稿位置计算分数，系统还可能暂存 draft 与 target 两侧的 KV；拒绝发生在第 j 个 token 时，后续提议状态不能被误当成已提交前缀。树状提议还要区分各分支共享的前缀与分支私有块。它们会影响峰值显存、回滚工作量和 cache 生命周期，所以评估必须观察临时 draft state 与请求原有 KV 的总账，而不能只用 $E[N_{\mathrm{committed}}]$ 估算容量；普通 KV 分配、共享与回收见第三章。

因此，“接受”需要绑定正确性目标。精确 sampling 下的 rejection sampling 用 target 分布 $p$ 和 draft 分布 $q$ 校正，目标是每一步仍从指定 target 分布抽样；greedy 下比较两边的 argmax，判断的是确定性 token 是否一致。relaxed acceptance、typical acceptance 或 tree/top-m 覆盖可能放宽逐 token 条件，追求相近质量、命中 target 首选或更高接受率，不能因此声称严格保持 target 分布。2026 年的一篇理论预印本分析多种局部接受判据，并在限定的分布差异条件下给出接受证书；证书不是端到端速度或普遍质量承诺。[When Is a Draft Accepted?](https://arxiv.org/abs/2606.30265)

批处理又增加跨请求的状态一致性要求：同一轮里各请求可能接受不同长度的草稿，形成 ragged 前缀；若实现没有同步 position IDs、attention mask 和 KV 状态，就可能改变后续计算。一个 2025 年提交、当前版本标注被 Findings of EMNLP 2026 接收的实现审查报告了其所检查方案中的这类风险。它不证明所有 runtime 都有问题，但说明验收应比较 greedy token 结果或 sampling 分布，并检查 cache/位置状态。批调度和内部修复细节留给第 6 章与第二十四册。[Batch Speculative Decoding Done Right](https://arxiv.org/abs/2510.22876)

“谁来提议”形成几条不同的系统路线，不能只比较接受率：

| 路线 | 谁提出候选 | 解掉的瓶颈 | 新成本与主要限制 | 分布口径 |
| --- | --- | --- | --- | --- |
| 独立 draft model | 较小的自回归模型逐 token 提议，再由 target 并行验证 | 不改 target 架构即可复用额外空闲算力，原始方法可用拒绝采样保持 target 分布 | 需训练/选配 draft、持有其权重和 KV；draft 延迟太高或与 target 不匹配会抵消收益。Leviathan 等人在 T5-XXL 11B 的翻译/摘要设置报告约 2.3–3.4 倍加速，绑定论文实现和任务。 |
| N-gram / prompt lookup | 从输入 prompt 中寻找重叠 n-gram 并复制后续 token | 高重合的摘要、翻译、代码编辑等场景不必额外加载 draft 模型 | 无匹配就回退普通 decode；生成内容缺少重复结构时接受率低。Hugging Face 文档明确将其定位为 input-grounded workload。 |
| Medusa | 在 target 上增加多个 prediction heads，树状展开并并行验证分支 | 避免维护独立 draft，并把多个未来位置的候选合并进一次验证 | 需要增加/微调 heads；Medusa-1 冻结 backbone、Medusa-2 联合训练的成本不同。论文的 rejection sampling 可保持 target 分布但加速较少；typical acceptance 报告相近生成质量，不等于严格分布相同。 |
| EAGLE | 自回归预测 target 倒数第二层 feature，再结合前移 token 形成候选并由 target 验证 | feature 序列比直接 token draft 更易预测，试图提高接受率并降低小模型 draft 的开销 | 需要训练与 target 配套的 feature drafter，依赖内部 hidden state 接口；论文加速比只适用于其模型、任务、batch 和硬件。 |
| Checkpoint MTP | checkpoint 自带的 multi-token prediction heads 预测后续 token | 复用训练时加入的预测层，减少额外模型装载 | 只有带匹配 MTP 权重/接口的 checkpoint 可用；实际效果由 verifier、树宽、batch 和引擎实现决定，不能凭模型名称推断。 |

独立 draft 路线的原始算法证明了拒绝校正可以保持 target 分布；EAGLE 使用 feature-level drafter 并报告 LLaMA2-Chat 70B 上 2.7–3.5 倍延迟加速；Medusa 论文明确区分严格 rejection sampling 和以“相近质量”为目标的 typical acceptance；Hugging Face 的 assisted decoding 文档分别说明 prompt lookup、self-speculative 和 MTP 的接口边界。[Speculative Decoding 原论文 v2](https://arxiv.org/abs/2211.17192v2)；[Medusa v3](https://arxiv.org/abs/2401.10774v3)；[EAGLE v3](https://arxiv.org/abs/2401.15077v3)；[Transformers v5.20.0 assisted decoding](https://huggingface.co/docs/transformers/v5.20.0/assisted_decoding)。

论文里的单请求 acceleration 不能代替服务容量评测。一项在 vLLM 上比较 n-gram、EAGLE/EAGLE-3、draft model 和 MTP 的研究覆盖 CNN/DailyMail、ShareGPT、InstructCoder、GSM8K、AIME 22–24、GPQA-Main 六个数据集；目标包括 Llama3.1-8B、Llama3-70B、Qwen3-8B/Thinking 和 GLM-4.5-Air，均在 H100 系统测量。多数非 reasoning 设置的 batch 范围为 1–128，reasoning 配置则按模型和数据集为 1–16 或 1–4。作者在所测配置中报告 target verification 约占执行时间的 42%–95%，相对加速通常随 batch 增大而收窄，且不同方法在不同任务胜出。它提示调度负载上升后，verification 的计算成本和 draft 占用的显存可能改变收益；这些数字绑定论文配置，不能替代目标环境测量。[Speculative Decoding: Performance or Illusion?](https://arxiv.org/abs/2601.11580)。

## 4.12 随机性、复现与线上回归

### 4.12.1 seed 只是复现条件的一部分

固定随机种子通常可以让同一进程、同一 batch 形状和同一 kernel 路径下的 sampling 更容易复现，但不能保证跨硬件、跨 dtype、跨 runtime 或跨 batch 调度得到完全相同的 token。原因包括：

1. logits 的浮点舍入和归约顺序不同。
2. batch 合并改变了随机数消耗顺序。
3. CUDA kernel 或通信存在非确定性。
4. tokenizer、模板、special token 和 stop 版本变化。
5. speculative、beam 或工具重试改变了调用次数。

回归记录应包含 seed、request id、模型/模板 revision、精度、采样参数、processor 顺序、候选过滤策略和 finish reason。不要只在报告里写“seed=42”。

### 4.12.2 流量变化也会改变输出

即使每条请求有独立 seed，动态 batching 可能改变 kernel 形状和浮点路径；如果随机数发生器按 batch 而不是 request 管理，新增一条并发请求还可能改变其他请求的随机序列。服务要么采用 request-scoped RNG，要么明确承认跨并发回放只保证统计分布而不保证逐 token 一致。

### 4.12.3 稳定性应该如何评估

对随机生成任务，不应把一次输出当作能力结论。至少应在多个 seed、多个长度桶和多个 workload 上记录：

~~~math
\mathrm{PassRate}
=
\frac{\#\{\text{任务成功的 runs}\}}
{\#\{\text{有效 runs}\}}.
~~~

该比率只有在有效 runs 数严格大于 0 时才有定义；没有有效 run 时应返回 `not_applicable` 并记录原因，而不是用 epsilon 或默认 0 伪造失败率。无效 run 的判定（超时、工具崩溃、配置错误是否剔除）必须在实验协议中预先固定，并同时报告剔除数量。

若任务有代码测试、数学 verifier 或 schema validator，使用它们作为主要结果；人工偏好和 LLM-as-a-judge 可以补充，但不能替代可执行正确性。与此同时要报告 token 成本和 P95，因为多采样提高 pass rate 可能让单位成功任务成本上升。

## 4.13 不同任务如何选择控制策略

| workload | 默认起点 | 主要约束 | 需要观察 |
| --- | --- | --- | --- |
| 分类/抽取 | greedy 或低温 | 字段和枚举 | exact match、schema、拒答 |
| 代码生成 | 低温或多候选低温 | 编译、测试、停止序列 | pass@k、长度、工具成本 |
| 数学推理 | 低温单次或多轨迹 | verifier、预算 | answer accuracy、过程成本 |
| 创意写作 | 中高温 + top-p/min-p | 安全、长度 | 多样性、人工质量、复读率 |
| 普通问答 | 低到中温 | 事实和引用 | grounded accuracy、P95 |
| 工具调用 | 低温 + schema/grammar | 权限和幂等 | 参数合法率、执行成功率 |
| JSON/SQL | constrained decoding | 语法、schema、数据库权限 | parse/schema/semantic 三层正确率 |
| 长 Agent | 受控采样 + 预算 | wall-clock、取消、重试 | 任务完成率、工具副作用 |

这张表只是实验起点。代码任务低温仍可能错，创作任务高温也不必然更好，工具调用的 schema 合法也不代表参数安全。每一类 workload 应有自己的参数模板、回归集合和成本报表。

多候选生成尤其要把“至少一个候选成功”和“服务最终交付成功”分开。假设单个代码候选通过测试的概率为 0.4，且四个候选彼此独立，则至少一个通过的概率是 $1-(1-0.4)^4=0.8704$；但调用和生成成本近似变成单候选的四倍。真实候选往往共享模型偏差，独立假设可能高估提升；若 verifier 无法选出正确候选，pass@4 也不等于线上成功率。应在同一批任务上记录候选数、验证器成本、最终选中率和单位成功成本，而不是只报采样后“最好的一条”。

## 4.14 一套可解释的调参方法

### 4.14.1 先定义目标函数

解码调参至少同时关注质量、协议、性能和成本。可以用一个证据向量表示：

~~~math
E_{\mathrm{decode}}
=
(E_{\mathrm{quality}},
E_{\mathrm{format}},
E_{\mathrm{latency}},
E_{\mathrm{cost}},
E_{\mathrm{safety}}).
~~~

这不是把不同单位强行加总，而是提醒评估者不要只优化一个数字。对代码任务，quality 可以是测试通过率；对 RAG，quality 可以包含引用支持率；对工具，format 是 schema 合法率，safety 是权限和参数检查结果。

### 4.14.2 一次只改变一组相关参数

一个稳妥的实验顺序是：先用 greedy 或低温建立 baseline，再改变 temperature；固定 temperature 后比较 top-p、top-k 或 min-p；之后才加入 penalty、logit bias、grammar 或 speculative。每次记录真实输出长度、finish reason、token 分布和失败样本。

如果同时把 temperature 从 0.7 改为 0.2、top-p 从 0.95 改为 0.8、repetition penalty 改为 1.2，最终效果无法归因。上线参数还要经过长输入、高并发、客户端取消和异常 JSON 回归，因为解码器与服务调度会相互影响。

逐项调参适合定位方向，但两个参数可能相互作用。比如先固定模型、prompt、stop、输出上限和 grammar，用 temperature 的 0.2/0.7 与 top-p 的 0.80/0.95 组成四组小网格；每组都跑同一批输入和相同数量的种子，再对照格式、任务正确率、输出长度、P95 和成本。若 temperature=0.2 时两种 top-p 几乎相同、temperature=0.7 时差距变大，说明 top-p 的效果取决于温度下形成的分布，不能用单因素排序直接选参数。这个实验只改变两个有关联的过滤控制，并不要求把所有参数做全组合搜索。

假设测试集有 50 道任务，每题跑 4 个 seed，共 200 次请求。基线成功 160 次，即 $160/200=80\%$，累计成本 2,000 个假设成本点，单位成功成本为 $2000/160=12.5$ 点；候选配置成功 172 次，即 86%，成本 2,600 点，单位成功成本为 $2600/172\approx15.12$ 点，约高 21%。如果产品硬门槛是成功率至少 85%、单位成功成本不高于 16 点，候选满足两项；若预算上限是 14 点，则候选不能上线，即使它的成功率更高。数字是演示计算的假设输入，不是模型实验结果。

统计时不要把同一题的 4 个 seed 当成 4 道独立题目：它们共享题目难度，只覆盖了随机生成差异。保留每题每 seed 的结果、失败类别和成本，再按预先定义的无效 run 规则统计；小样本的 12 次 pass 差异不能直接宣称普遍提升。需要置信区间或显著性判断时，应使用评估设计章节的方法；本章的目标是让读者先把分母、运行条件和单位成功成本算对。

### 4.14.3 先筛失败类型，再决定调哪个控制

把同一组 200 次结果按失败原因拆开，常能发现单一平均分掩盖的反向变化。若候选多出 12 次成功，却也多出 7 次 JSON schema 失败和 4 次 length 截断，先检查 sampler 与 stop/预算的交互，不要只看 pass rate。若多出的失败都集中在一个长度桶，可能是 max token 或 context 预算；若集中在某个 grammar 状态，应检查 tokenizer/backend 支持；若只有工具权限失败，调低 temperature 或提高 reasoning effort 都不是正确修复点。

因此调参结果要同时回答三个问题：变化作用在哪一层，哪类失败随之变化，以及该变化是否达到目标 SLO。对 code，用编译/测试通过和执行成本；对 RAG，用可追溯答案质量与引用支持率；对 tool call，用 schema、语义、授权和执行成功各自的分母。某一项变好但另一项越过硬约束时，应回滚、收窄流量或增加独立校验，而不能通过把多个指标压成单一平均值隐藏失败。

调参集也会被反复观察。若 12 组配置都在同一批 50 道题上比较，再把分数最高的一组当作最终结果，这 50 题已经参与了选择，不能再当作独立验收证据。把它们作为 tuning split，另留未参与选择的验收 split；发布后再用小流量监控任务正确率、格式失败、P95 和单位成本。第 11 章会展开服务发布与回滚；本章的参数选择在交接前至少要留一个未被反复调参污染的确认集。

验收集还要按真实流量切片。若 90% 请求是短分类、10% 是长工具规划，未加权的总体平均可能让短任务掩盖长任务的 timeout 或高成本；反过来，等权平均也未必代表实际业务负载。应先保留每类的独立成功率、finish reason、长度和 P95，再按已声明的流量权重计算总体指标。这样才知道调参改善了哪类请求、是否把负担转移到少数长上下文或高风险任务。

### 4.14.4 失败样本比平均分更有信息

应把失败分成：事实错误、格式错误、过早停止、无限重复、预算耗尽、schema 无合法 token、工具参数错误、工具超时和安全拒绝。不同失败对应不同控制点：

1. 事实错误不能只靠降低 temperature 修复。
2. 重复可以尝试 penalty，但要检查是否破坏专名和代码。
3. JSON 语法问题优先检查 grammar 和 tokenizer，而不是盲目加 penalty。
4. 工具参数错误要检查 schema、授权和重试幂等。
5. 预算耗尽要区分输出上限、reasoning budget 和工具 wall-clock。

## 4.15 一个零依赖的 logits 控制 demo

下面的 demo 演示 temperature、top-k、top-p、min-p、presence/frequency penalty 和 EOS 停止。它把每一步候选集合打印出来，方便读者修改参数后观察分布变化；它不是生产级 tokenizer、grammar 或采样器。

完整规则和主文手算见 [§4.6](#46-top-ktop-p-与-min-p如何截断长尾)、[§4.7](#47-repetitionpresence-和-frequency-penalty) 与 [§4.8](#48-stopeos-和最大输出)。代码额外使用五个 token，其中 EOS 用来展示终止路径；它是这些教学单元的附加观察例，不是独立讲解。

依赖 Python 3 标准库。将完整代码块复制到 `.py` 文件后可用 `python3 demo.py` 运行；它不加载模型，也不代表真实 serving runtime 的 processor 顺序。

`softmax` 先从每个 logit 减去最大值，再除以温度；差值不为正，即使温度很小，低分项下溢为负无穷后也只会贡献 0，不会让最大项先溢出为正无穷。它仍是面向本教学输入的简化实现，不涵盖框架张量、并行归约或 runtime 的数值路径。

代码状态：静态审阅，未运行（2026-11-02）。

~~~python
import math
import random
from collections import Counter


VOCAB = ["alpha", "beta", "gamma", "delta", "EOS"]


def softmax(logits, temperature=1.0):
    if not logits or any(not math.isfinite(value) for value in logits):
        raise ValueError("logits must be a non-empty finite sequence")
    if not math.isfinite(temperature) or temperature <= 0:
        raise ValueError("temperature must be a finite positive number")
    max_logit = max(logits)
    scaled = [(value - max_logit) / temperature for value in logits]
    exps = [math.exp(value) for value in scaled]
    total = sum(exps)
    return [value / total for value in exps]


def apply_presence_frequency_penalty(
    logits, history, presence=0.0, frequency=0.0
):
    if len(logits) != len(VOCAB):
        raise ValueError("logits length must match VOCAB")
    if any(not math.isfinite(value) for value in logits):
        raise ValueError("logits must be finite")
    if not math.isfinite(presence) or presence < 0:
        raise ValueError("presence must be a finite non-negative number")
    if not math.isfinite(frequency) or frequency < 0:
        raise ValueError("frequency must be a finite non-negative number")
    if any(token not in VOCAB for token in history):
        raise ValueError("history contains an unknown token")
    counts = Counter(history)
    adjusted = list(logits)
    for index, token in enumerate(VOCAB):
        adjusted[index] -= (
            presence * (counts[token] > 0) + frequency * counts[token]
        )
    return adjusted


def top_k_indices(logits, k):
    if not logits or any(not math.isfinite(value) for value in logits):
        raise ValueError("logits must be a non-empty finite sequence")
    if isinstance(k, bool) or not isinstance(k, int) or not 1 <= k <= len(logits):
        raise ValueError("k must be an integer in [1, len(logits)]")
    return sorted(range(len(logits)), key=lambda i: logits[i], reverse=True)[:k]


def top_p_indices(probs, p):
    if not probs or any(not math.isfinite(value) or value < 0 for value in probs):
        raise ValueError("probs must be a non-empty finite non-negative sequence")
    if not math.isfinite(p) or not 0 < p <= 1:
        raise ValueError("p must be in (0, 1]")
    if sum(probs) <= 0:
        raise ValueError("probs must have positive mass")
    ordered = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)
    kept = []
    mass = 0.0
    for index in ordered:
        kept.append(index)
        mass += probs[index]
        if mass >= p:
            break
    return kept


def min_p_indices(probs, min_p):
    if not probs or any(not math.isfinite(value) or value < 0 for value in probs):
        raise ValueError("probs must be a non-empty finite non-negative sequence")
    if not math.isfinite(min_p) or not 0 <= min_p <= 1:
        raise ValueError("min_p must be in [0, 1]")
    if max(probs) <= 0:
        raise ValueError("probs must contain positive mass")
    threshold = max(probs) * min_p
    return [index for index, probability in enumerate(probs) if probability >= threshold]


def sample_from_indices(probs, indices, rng):
    if not probs or any(not math.isfinite(value) or value < 0 for value in probs):
        raise ValueError("probs must be a non-empty finite non-negative sequence")
    if not indices:
        raise ValueError("indices must be non-empty")
    if any(
        not isinstance(index, int)
        or isinstance(index, bool)
        or index < 0
        or index >= len(probs)
        for index in indices
    ):
        raise ValueError("indices contain an out-of-range value")
    total = sum(probs[index] for index in indices)
    if not math.isfinite(total) or total <= 0:
        raise ValueError("selected probabilities must have positive finite mass")
    threshold = rng.random() * total
    mass = 0.0
    for index in indices:
        mass += probs[index]
        if mass >= threshold:
            return index
    return indices[-1]
~~~

## 4.16 常见误解与边界

### 4.16.1 低温等于更正确

不等于。低温通常降低随机性，可能提高格式稳定性，却可能更稳定地输出模型最偏好的错误答案。事实、代码和数学任务需要独立检索、测试或 verifier。详见 [§4.5 temperature 的数值例子](#45-temperature改变分布的尖锐程度)。

### 4.16.2 top-p=0.9 就是保留 90% 的 token

不是。它保留的是按概率排序后累计质量达到 0.9 的最小候选集合，候选数量会随分布变化。过滤后还要重新归一化，见 [§4.6 的同分布推演](#46-top-ktop-p-与-min-p如何截断长尾)。

### 4.16.3 repetition penalty 越高越好

不是。代码、JSON、公式和专名需要合法重复；过强惩罚会造成字段错误、语法损坏和主题漂移。应比较任务成功率和重复坏例，而不是只追求重复率下降。逐 token 计算见 [§4.7.4](#474-逐-token-算一次惩罚)。

### 4.16.4 JSON mode 等于业务对象正确

不是。JSON mode 主要解决语法层，schema 约束解决字段和类型层，业务校验还要检查范围、权限、引用和事实。三层都通过才是可交付结果，见 [§4.9 的阶段门槛](#49-structured-output语法合法不等于业务正确)。

### 4.16.5 speculative decoding 改变了模型答案

精确 rejection sampling 可以在假设成立时保持 target 分布，但 relaxed acceptance、候选截断、随机数顺序或 grammar 组合可能改变结果。正确性口径和吞吐门槛见 [§4.11](#411-speculative-decoding用小模型猜大模型验)。

### 4.16.6 stop string 一定对应一个 token

不一定。它可能跨多个 token，甚至跨流式 chunk。服务需要使用目标 tokenizer 或增量文本匹配，并明确 stop 内容是否在发送前被缓冲和移除。请求轨迹见 [§4.8.4](#484-stop-缓冲与硬上限的请求轨迹)。

### 4.16.7 seed=42 就能跨环境复现

不一定。浮点路径、batch 形状、kernel、tokenizer、模板、采样器和工具调用次数变化都可能改变结果。seed 是复现条件的一部分，不是复现保证本身，参见 [§4.12](#412-随机性复现与线上回归)。

## 4.17 一个结构化工具任务的解码方案

考虑一个企业报销助手。模型需要根据用户描述生成一个工具调用，工具名只能是 `lookup_policy` 或 `create_draft`；前者读取制度，后者只创建草稿，不允许直接提交付款。任务同时要求参数满足 JSON Schema、金额使用数字、币种来自枚举，并且所有制度结论附带文档编号。这个例子能把解码控制的几个层次放在同一条请求链上。

先建立不带复杂控制的 baseline。对工具名和参数使用 greedy 或低温采样，模型输出后再做 JSON parse、schema、业务字段和权限检查。失败样本要分类：JSON 语法错误、缺少字段、枚举错误、金额类型错误、引用缺失、工具名越权和工具执行超时。不能把它们都记成“模型答错”，因为只有前几类可能由解码协议直接改善，权限和工具状态必须由执行层处理。

把 §4.9.5 的假设漏斗应用到这个报销助手：100 条请求最终只有 65 条通过工具执行；其中 parse 与 schema 两级共 14 条格式失败，业务、授权和执行阶段另有 21 条失败。若 grammar 在其他行为不变的假设下修复全部格式失败，整体成功数至多从 65 增到 79，而不是 100；剩余失败需要制度检索、金额规则、用户授权或执行重试策略处理。这个上限是漏斗上的算术推演，不是 grammar 会真实修复 14 条的预测。它帮助团队决定先做哪种改动，也防止把结构化输出的成功率误报为报销任务成功率。

如果 baseline 的主要失败是逗号、引号和字段边界，应该在 token 选择阶段使用 grammar 或 schema mask。设解析器状态为 s，合法的下一 token 集合为 A(s)，解码器只让这些 token 保留：

~~~math
\widetilde z_i=
\begin{cases}
z_i,&i\in A(s),\\
-\infty,&i\notin A(s).
\end{cases}
~~~

采样后由状态转移函数更新解析器：

~~~math
s_{t+1}=\delta(s_t,y_t).
~~~

这能显著减少语法级失败，但不能证明金额真实、引用支持结论或当前用户有权创建草稿。因此完整检查仍需按三层进行：先 parse，再 schema，再执行前的业务和权限校验。若 grammar 编译失败或某一状态没有合法 token，服务必须返回明确错误并记录状态，而不是把空候选交给 softmax 产生 NaN。

接着选择随机性。工具名和字段名属于协议 token，通常应使用低温或受约束 greedy；字段值中的自然语言摘要可以在同一个请求的不同状态下使用更高温度，但不能让它影响工具名、枚举和权限字段。若把全局 temperature 从 0.7 降到 0.1，可能让格式更稳定，却不能修复模型对报销规则的事实误解；制度检索和引用验证仍然必要。若需要探索多个可行草稿，可以生成多个低温候选，再由制度 verifier 和业务规则筛选，而不是单纯提高温度。

重复惩罚也应按字段区分。自然语言说明中重复句子可能是坏例，但 JSON key、币种、日期格式和代码字段的合法重复不能被任意惩罚。一个全局 repetition penalty 可能把 `amount`、`currency` 或文档编号改写成非法 token，因此应优先在语法约束和字段级验证上解决格式问题，只有在确实观察到自然语言循环时才做局部调节。

停止语义需要和工具状态机配合。模型生成完整 JSON 并通过 schema 后，服务应在 `tool_call` 状态停止当前文本生成；工具执行结果追加回上下文后，模型才进入下一轮。EOS、stop string、`max_new_tokens`、schema complete、用户取消和工具超时要分别记录。若只依赖 stop string，模型可能在 JSON 完成前提前结束，或者把下一轮 assistant 标记一起输出；若只依赖 `max_new_tokens`，又可能把预算耗尽误认为工具调用成功。

最后评估是否值得使用 speculative decoding。若工具参数段高度格式化、target 和 draft 的 tokenizer/schema 兼容，draft 可以先提出多个 token，target 逐段验证；但 grammar mask 可能让 draft 大量提出非法候选，工具状态也可能在中途改变。应在相同请求、相同随机策略和相同输出分布要求下比较：接受长度、target 调用次数、最终 TPOT、显存、schema 合法率、工具执行成功率和单位成功成本。接受率高但 schema 失败率也高的实现，不是加速成功；速度提升却改变了需要保持的 target 分布，也不能直接替换 baseline。

这个案例的决策结果通常是分层的：协议字段使用 constrained decoding 和低温，开放说明使用受控 sampling，业务正确性依靠检索与 verifier，权限依靠执行器，停止依靠状态机，speculative 只有在分布、格式和工具生命周期都验证后才启用。解码器负责选择候选，不负责替系统承担事实、权限和副作用责任。

## 4.19 小结

解码从 logits 开始，经过温度、惩罚、候选过滤和约束，最后选择一个 token 并检查停止条件。greedy 稳定而局部，beam search 在序列层面保留多条路径，sampling 用随机性换多样性；temperature 改变分布尖锐程度，top-k 固定候选数量，top-p 按概率质量自适应，min-p 以最大概率为参照。

locally typical sampling 依 surprisal 到当前熵的距离选候选；min-p 的参数规则有清楚定义，但其质量/多样性优势受到后续复核质疑，所以应和 top-p 在同一任务、模型与调参预算下比较，而不是预设它更好。

penalty 能控制重复，却不能理解代码、公式和专名的必要重复；EOS、stop、max_new_tokens 和工具结束状态共同定义一次请求何时结束。JSON mode、schema grammar 和业务语义验证是三层不同保证，结构化语法合法不等于事实正确或权限安全。

reasoning budget 控制的是额外计算和工具/验证成本，不能与随机性参数混用；speculative decoding 则通过 draft 提议、target 验证来减少大模型串行调用，拒绝采样能在明确假设下保持 target 的分布，但不能保证同 seed 逐 token 一致。独立 draft、n-gram、Medusa、EAGLE 和 checkpoint MTP 的提案成本、训练依赖、分布保证与 batch 收益不同。真正可用的解码配置，必须在目标 workload 上同时解释质量、格式、延迟、成本、复现和安全结果。
