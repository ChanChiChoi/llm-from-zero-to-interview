# 第十二章：成本优化

在线推理成本和训练成本有一个根本差别：训练成本通常集中在一段时间内，在线
成本则随着每一次请求持续发生。一个模型每天多处理一亿个 token，任何一个看似
很小的冗余，都会在账单、GPU 资源和运维负担上反复出现。

但成本优化不是把模型换成最小的版本，也不是把输出长度一刀切到很低。省下的
GPU 如果换来更多重试、转人工、错误动作或安全事故，单位成功任务成本可能
更高。真正的优化要回答三个问题：钱花在哪里，哪种改动能改变这笔钱，以及
质量、延迟、安全和可靠性是否仍然满足业务契约。

本章以成本账本为起点，分别讨论 GPU 容量、模型路由、prompt 和上下文压缩、
prefix/response/embedding cache、speculative decoding、量化和蒸馏、batch
与 autoscaling、限流和预算，以及 RAG、Agent 和多模态任务的专项成本。最后
用一个可运行的 toy 诊断示例把成本变化和独立的质量、延迟、安全信号放在一起。
具体模型价格、云厂商折扣和 runtime 参数都可能变化，正文只保留可迁移的计算
口径和证据边界。

## 1. 先建立成本账本

### 1.1 一次请求消耗了什么

一次简单的文本问答，表面上只有一次 LLM 调用，实际可能包含：

~~~text
请求
  -> 网关、鉴权和限流
  -> tokenizer 和 prompt 组装
  -> RAG embedding、召回和 reranker
  -> LLM prefill / decode
  -> 安全检测、后处理和日志
  -> 存储、网络和重试
~~~

多模态请求还要加入媒体解码、OCR、ASR、vision encoder 或视频抽帧；Agent 请求
还会重复调用模型和工具。成本分析如果只取供应商返回的 completion token，
会漏掉大量真正的资源消耗。

初学者可以先把每次调用的成本拆成五本账：

1. 模型账：输入、输出、视觉、音频和推理中间状态。
2. 辅助模型账：embedding、reranker、OCR、ASR、安全分类和 judge。
3. 平台账：GPU、CPU、内存、对象存储、网络和日志。
4. 可靠性账：失败请求、超时、重试、shadow 和预热副本。
5. 人工账：质检、标注、人工确认和事故处理。

这五本账不一定都能精确换算成货币，但必须能与 request_id、tenant_id、model
revision 和 workload 关联。否则总账单上升时，只能猜测是流量增长、prompt
变长、缓存失效还是重试风暴。

### 1.2 先分清资源向量和货币账本

输入 token、图像 patch、音频秒数、GPU 毫秒和人工分钟不是同一种单位，不能
直接相加后称作“总 token”。每个请求先记录一个资源向量：

~~~math
\mathbf{x}_i =
(P_{in},P_{cached},O,I_{patch},A_{sec},V_{frame},
E_{embed},E_{rerank},G_{ms},CPU_{sec},S_{byte},R_i,H_{min})
~~~

这些分量回答“消耗了多少”。再用实际价格或内部核算率把它们分别换算成货币：

~~~math
C_i =
C_{model,i}+C_{aux,i}+C_{compute,i}+C_{storage/network,i}
+C_{retry,i}+C_{human,i}
~~~

例如 API 部署通常以供应商发票中的输入、输出、缓存输入和多模态费用作为模型
直接成本；自托管部署则把 GPU/CPU 小时、常驻副本、网络、存储和维护成本按
明确规则分摊到请求。不要把同一份推理同时按 API 账单和 GPU 小时记两次。
如果同时呈现“供应商支出”和“内部资源分摊”，要把它们标为两种核算视图，
说明它们是否互斥，不能混成一个未经审计的总数。

资源向量仍然有用：prompt 压缩改变输入 token，prefix cache 改变重复 prefill
工作和缓存驻留，量化改变权重/KV 字节与 GPU 时间，路由改变模型路径，限流
改变重试和队列工作。它帮助定位成本变化来自哪里，但不会假装这些量纲可以
彼此抵消。

总成本和单位 token 成本可以写成：

~~~math
C_{\mathrm{total}}=\sum_{i=1}^{N}C_i
~~~

~~~math
C_{\mathrm{token}}
=
\frac{C_{\mathrm{model}}}
{\sum_i(P_{in,i}+O_i)}
~~~

这个分母只适合比较 token 口径和模态组成相近的文本 workload。缓存输入应依
供应商的实际计费规则单独报告；图像、音频、视频、embedding 和 reranker 不
能偷偷折成“文本 token”等价量。对 RAG、Agent 和文档抽取，更重要的是单位
成功任务成本：

~~~math
C_{\mathrm{success}}
=
\frac{C_{\mathrm{total}}}
{N_{\mathrm{successful\ tasks}}}
~~~

分子包括失败请求、重试、人工升级和必要的共享资源分摊，分母按业务契约定义
成功任务。零个成功任务时该指标是未定义，而不是零。若一项请求的账单从
0.010 降到 0.007，但成功率从 0.90 降到 0.60，则旧的每成功任务成本是
0.010/0.90=0.0111，新方案是 0.007/0.60=0.0117；单次调用便宜 30%，每个成功
结果反而贵约 5%。发票抽取需要字段和证据都正确，Agent 需要动作获授权且
结果提交，RAG 回答需要被有效证据支持。

### 1.3 直接成本和分摊成本

直接成本容易归因，例如某个 API 调用的 token 账单或某个 GPU worker 的运行时长。
分摊成本更容易被忽略：

1. 常驻副本在低峰时的闲置 GPU。
2. 预热模型和保留的 warm pool。
3. 监控、日志、trace 和对象存储。
4. 失败任务留下的临时文件和重试。
5. 离线评估、shadow traffic 和人工标注。

如果只把活跃 GPU 时间计入成本，autoscaling 可能看起来很有效，却把冷启动、
预热和长尾维护成本藏到了平台账单里。成本报告应同时展示 active、reserved、
idle、evaluation 和 retry 等类别。

## 2. GPU 容量和单位 token 经济学

### 2.1 GPU 小时如何转换成 token 成本

有两种口径可以使用，但不能把已经含空闲时间的吞吐再乘一次利用率。若
R_wall 是在一个明确的计费窗口内完成的输出 token 数除以整个墙钟秒数，它已经
把该窗口里的排队、空闲和低利用时间计入，单位输出 token 的粗略成本为：

~~~math
C_{\mathrm{gpu\_tok}}
=
\frac{C_{\mathrm{gpu\_hour}}}
{3600R_{\mathrm{wall}}}
~~~

如果 R_active 只统计 worker 忙碌时的输出速率，则应乘以同一计费窗口中的生产
性利用率 U：

~~~math
C_{\mathrm{gpu\_tok}}
=
\frac{C_{\mathrm{gpu\_hour}}}
{3600R_{\mathrm{active}}U}
~~~

两种写法等价的前提是 R_wall=R_active×U，且 U 的窗口、分子和分母一致。
R_active 不是厂商峰值；它要在目标输入/输出长度、并发、模型版本和 SLO 下
测量。U 应由同一窗口内真正完成且满足任务门槛的工作量定义，不能把
nvidia-smi 的瞬时繁忙率直接当成有用吞吐。

举一个纯假设的算例：单卡成本为 2 美元/GPU 小时，忙碌时完成 100 输出
token/s，生产性利用率为 50%，则 R_wall=50 token/s，成本约为
2/(3600×50)=0.0000111 美元/token，即每百万输出 token 约 11.11 美元。
如果直接把 R_wall 再乘 50% 利用率，会把成本错误地翻倍。这里没有计入输入
prefill、额外副本、人工、网络或质量损失；实际报告要另列这些项。

这个公式能解释为什么单纯把 GPU 利用率拉高并不一定是好事。如果利用率上升
来自把大量长请求混在一起，P99 和失败率可能同时上升，最终 C_success 变差。
成本优化必须把资源利用率和用户可用结果放在同一张表里。

### 2.2 prefill 和 decode 的成本不同

prefill 一次处理整段输入，受 prompt token、矩阵计算和批次形状影响；decode
每一步只生成少量 token，却要反复读取权重和 KV Cache。两者的硬件瓶颈不同：

| 阶段 | 主要工作 | 成本敏感因素 |
| --- | --- | --- |
| prefill | 一次处理输入上下文 | 输入长度、视觉位置、batch、attention |
| decode | 逐 token 生成 | 输出长度、KV Cache、batch、带宽 |
| 后处理 | 解码、审核和结构化 | 输出格式、规则、外部服务 |

长 prompt 不一定产生长回答，但会让 prefill 和 KV 初始状态变贵；短 prompt
配上长回答则更可能受 decode 影响。优化时要先确认是哪一段占用了 GPU 时间，
再决定是压缩上下文、控制输出、提高 batch，还是换模型。

### 2.3 显存是容量约束，不只是成本数字

一块 GPU 能否承载更多副本，取决于权重、KV Cache、临时 buffer 和碎片。量化
权重可能让模型放进更小的 GPU，却不一定降低输出阶段的 KV 成本；prefix cache
提高命中率，也可能让缓存占用更多显存。成本账本必须同时记录：

1. 权重字节。
2. 每个活跃请求的输入和输出序列长度。
3. KV block 数和命中 token。
4. batch 等待时间。
5. 被抢占或淘汰的请求。

前几章的 KV Cache、分页和调度模型在这里有一个经济学解释：更高的并发不自动
等于更低的单位成本，只有在不突破显存和 SLO 的前提下提高有效吞吐，才会降低
每个成功任务的 GPU 分摊。

### 2.4 API 与自托管的流量交叉点

“流量大了自托管就便宜”只有在固定模型质量和服务目标下比较才有意义。令 N
为一个核算周期内的请求数，API 的固定接入成本为 F_api、每请求可变成本为
c_api；自托管的固定成本为 F_self、每请求边际成本为 c_self：

~~~math
C_{api}(N)=F_{api}+Nc_{api}
~~~

~~~math
C_{self}(N)=F_{self}+Nc_{self}
~~~

若 c_api>c_self 且 F_self>F_api，交叉点为：

~~~math
N^*=
\frac{F_{self}-F_{api}}{c_{api}-c_{self}}
~~~

例如假设自托管每月固定成本 48,000 美元、边际成本 0.0008 美元/请求；API
没有额外固定成本、边际成本 0.0024 美元/请求，交叉点为每月 30,000,000 个
请求。20M 请求时 API 约 48,000 美元、自托管约 64,000 美元；40M 时分别约
96,000 和 80,000 美元。这里的自托管固定成本必须包含最低常驻容量、运维和
折旧，边际成本要包含闲置分摊、峰值扩容、失败请求和网络；API 费用也要按
真实缓存、多模态和折扣规则计算。

如果 c_api≤c_self 且 F_self>F_api，自托管在这个线性模型里没有正向交叉点；
若 F_self≤F_api，交叉关系则不同。交叉点不是迁移决定。比较的两侧还要达到相同的成功率、TTFT/TPOT、可用性、
安全和数据合规目标；如果自托管需要更大模型或额外人工，c_self 会变化。
流量突发、容量预留、折扣和工程人力使成本曲线不再是简单直线，因此还要用
真实流量回放做敏感性分析。

## 3. 模型选择与请求路由

### 3.1 大模型不是所有请求的默认答案

大模型适合复杂推理、代码修改、高价值客户、复杂文档和高风险专业任务，但
它的权重、显存、TTFT 和输出成本都更高。小模型适合意图分类、字段抽取、
简单 FAQ、query rewrite、安全初筛和模板化生成；在边界清晰的任务上，小模型
可能比大模型更稳定、更容易审计。

真正的选择单位不是“模型大小”，而是任务能力契约：

1. 输入是否需要长上下文或视觉理解。
2. 输出是否需要结构化和工具参数。
3. 错误的代价有多高。
4. 是否允许拒答或人工升级。
5. 需要什么 TTFT、TPOT 和吞吐。
6. 该模型在目标切片上的成功率和单位成本。

### 3.2 路由的三种形态

规则路由适合边界明确、可解释的请求，例如根据接口、语言、文件类型和权限
选择模型。分类器路由可以使用历史样本判断复杂度，但要监控分类漂移。级联
路由先让低成本模型回答或打分，不确定时再升级到更强模型；它节省平均成本，
却增加一次路由延迟和错误路由风险。

对直接路由，若请求 x 以概率 p(k|x) 选择模型 k，期望成本可以写成：

~~~math
E[C|x]
=
C_{router}(x)+\sum_k p(k|x)C_k(x)
~~~

p(k|x) 是路由器把请求送到模型 k 的概率，C_k 是该模型路径成本，C_router
包含路由分类、prompt 改写和必要的评估开销。若路径还可能升级，应把触发概率
与后续完整调用分开列出，而不是再叠加一个含义不明的“fallback 罚项”。例如
先调用小模型、以概率 q(x) 判断需要升级，则：

~~~math
E[C_{cascade}|x]
=C_{router}+C_{small}(x)
+q(x)\left(C_{large}(x)+C_{recovery}(x)\right)
~~~

质量不能通过从离线分数里减去任意一个 Q_routing_error 来估算。应在一组按
真实流量分布抽样并人工/规则标注的请求上，分别测最终路径的任务成功率、引用
支持、结构化正确、拒答和安全结果；级联质量要统计升级后最终答案，不把小
模型的第一次尝试误当成最终任务。只有当成功定义和样本集合一致时，才能把
成本除以成功数。

代表性路线解决的问题不同：

| 方案 | 主要机制 | 解决什么 | 代价与边界 |
| --- | --- | --- | --- |
| [FrugalGPT](https://arxiv.org/abs/2305.05176) | prompt adaptation、模型近似和按阈值级联；容易题走低价路径，难题升级 | 在可控任务集里寻找成本与质量的组合 | 级联会增加串行延迟；阈值和候选模型需用目标分布学习。论文报告的 50%—98% 节省来自 2023 年 API 价格和 HEADLINES、OVERRULING、COQA 等具体任务，不能外推为通用收益 |
| [RouteLLM](https://arxiv.org/abs/2406.18665) | 用偏好数据学习强/弱模型的选择器 | 避免每条请求都按固定级联顺序调用，直接在成本较低的模型间分流 | 路由质量依赖偏好数据代表性；论文中仅用 Arena 偏好训练的 router 在 MMLU 上接近随机，加入目标 benchmark 的 gold-label 数据后才改善，说明跨域迁移需要验证 |
| 规则/任务分类器 | 根据格式、风险、长度、任务标签或置信度选择模型 | 规则边界清楚时提供可审计的低开销路径 | 分类错误可能把高风险难题送到弱模型；漂移和标签误差要监控 |

选择路由器时要一起比较路由本身成本、额外串行延迟、错误路径、fallback
完成率和分域成功率。FrugalGPT 与 RouteLLM 的论文报告回答的是“在作者的
模型、数据、价格和评测下能否改善权衡”；本地任务是否适用仍需固定回放与
canary 验证。

### 3.3 复杂度判断和 fallback

复杂度可以由规则和轻量模型共同估计：

1. 输入 token 和模态位置是否超过阈值。
2. 是否包含代码、数学、表格或多步工具需求。
3. 是否命中高风险领域。
4. 历史相似请求在小模型上的成功率。
5. 用户是否允许异步或人工处理。

路由器不应只输出一个模型名，还应输出理由、风险级别、预算和 fallback 条件。
例如：

~~~text
kind = invoice_extraction
route = document_model
reason = table_and_numeric_fields
quality_floor = field_f1 >= 0.98
fallback = human_review
~~~

如果小模型已经产生了错误或不完整的答案，再把这个答案无条件交给大模型，
大模型可能被错误内容带偏。升级时应保留原始输入和证据，而不是只传递小模型
的结论。

### 3.4 路由的公平和安全

按用户等级或业务价值分配不同模型可以符合商业目标，但高风险请求不应因为
低优先级而失去必要的安全检查。资源分级应明确：

1. 哪些任务可以使用小模型。
2. 哪些任务必须使用高质量或可审计模型。
3. 哪些任务只能进入异步或人工流程。
4. 哪些输入无论成本如何都必须拒绝。

路由日志不应记录敏感原文，但要能解释为何选择了某模型、是否发生 fallback
以及最终任务是否成功。

## 4. Prompt 和上下文压缩

### 4.1 压缩的对象

prompt token 会增加 prefill、KV Cache 和输入计费。可压缩对象包括：

1. system prompt 中重复或矛盾的规则。
2. few-shot 示例和已经掌握的格式说明。
3. 历史对话和工具返回。
4. RAG 的重复证据和无关段落。
5. OCR 产生的版面噪声。
6. Agent 的中间观察和浏览器页面。

压缩不是单纯删除字符，而是在固定任务契约下减少模型必须读取的序列位置。
安全策略、权限范围、数字条件、否定、单位、时间和证据来源不能因为看起来
重复而被随手删掉。

### 4.2 结构化压缩优先

优先把重复文本变成结构化字段，通常比让另一个模型自由摘要更容易审计：

~~~text
原始工具结果：
  订单 A-100，状态为已发货，承运商为 X，更新时间为 2026-08-10 09:00，
  页面还包含大量导航和推荐内容。

结构化结果：
  order_id=A-100
  status=shipped
  carrier=X
  updated_at=2026-08-10T09:00:00
~~~

结构化裁剪要保留来源和 schema 版本。对代码要保留文件路径、函数签名和相邻
上下文；对法律、金融和医疗文本要保留条件、例外和时间；对多模态结果要保留
坐标、帧时间和置信度。

### 4.3 历史对话和 Agent 状态

历史摘要节省 token，却可能丢失用户偏好、未完成任务、工具提交状态和拒绝条件。
更稳妥的状态分层是：

1. 当前 turn 的原始输入。
2. 可验证的结构化用户状态。
3. 最近若干轮的对话文本。
4. 更早历史的带版本摘要。
5. 外部数据库中的完整事件和工具结果。

摘要应有版本和生成来源，关键事实还要能回到原始事件。不能让一个摘要同时
承担审计记录、权限凭证和模型上下文的全部职责。

### 4.4 压缩率和质量损失

prompt 压缩率可以写成：

~~~math
\rho_{\mathrm{compress}}
=
1-\frac{P_{\mathrm{new}}}{P_{\mathrm{old}}}
~~~

P_old 和 P_new 是同一输入在压缩前后的 token 数。压缩带来的直接输入成本节省
近似为：

~~~math
\Delta C_{\mathrm{prompt}}
=
a(P_{\mathrm{old}}-P_{\mathrm{new}})
~~~

但完整评估还应测任务成功率、引用支持、拒答、工具参数和安全漏放。压缩率高
而质量下降时，节省的输入 token 可能被重试和人工处理吞掉。

几条代表路线解决的是不同的压缩问题：

| 方法 | 核心做法 | 主要改善 | 代价与边界 |
| --- | --- | --- | --- |
| [LLMLingua](https://arxiv.org/abs/2310.05736) | 粗到细分配预算，再用语言模型概率/重要性估计筛 token，并做分布对齐 | 通用长 prompt 的 token 级压缩 | 压缩器本身需要计算；删词可能破坏否定、数字关系和引用边界 |
| [LongLLMLingua](https://arxiv.org/abs/2310.06839) | 把问题与文档相关性用于粗、细粒度筛选，并处理长上下文中的位置偏置 | 长文档 QA 中关键证据稀释和 middle-position 丢失 | 收益依赖问题可用、证据可定位；换任务后必须重新看召回和引用支持 |
| [LLMLingua-2](https://arxiv.org/abs/2403.12968) | 用蒸馏数据训练双向编码器做 token 分类，减少逐 token 自回归打分 | 更快的 task-agnostic 压缩器 | 蒸馏语料会影响保留偏好；论文在 MeetingBank 等设置上的跨域结果不能替代业务校准 |

压缩器是否划算，可以先算直接成本的盈亏线。令 a 为每个输入 token 的价格，
ΔP=P_old−P_new，C_comp 为压缩器成本，ΔC_recovery 为质量变化带来的额外
重试、fallback 和人工处置期望成本，则：

~~~math
\Delta C_{net}
=a\Delta P-C_{comp}-\Delta C_{recovery}
~~~

只有 ΔC_net 为正，且任务质量、安全和延迟门槛仍通过，压缩才同时有经济与
业务价值。举例：价格假设为每百万输入 token 2 美元，压缩把 10,000 token
降到 6,000，直接省 0.008 美元；若压缩器花 0.0015 美元，额外失败恢复的
期望成本为 0.002 美元，净省 0.0045 美元。若恢复成本升到 0.009 美元，
即使压缩率仍为 40%，总成本也会上升。

论文数据集和目标业务的冗余结构不同。应把这些方法当作候选工具，固定原始
prompt、模型、检索结果和任务标签，在业务样本上同时测压缩器延迟、输入 token、
关键事实召回、引用支持、拒答与最终成功成本；不能把论文中的压缩比例写成
线上承诺。

## 5. Cache：复用计算而不是复用错误

### 5.1 Prefix cache

prefix cache 复用已经计算出的前缀 KV 状态，适合固定 system prompt、稳定的
业务模板、公共文档前缀和多轮对话历史。请求必须在最终渲染后的 token 前缀上
真正一致；模板、工具 schema、模型/adapter 或媒体处理变化都会改变可复用边界。
它主要跳过重复 prefill，不会自动减少新输出的 decode，也不等于供应商一定按
相同规则降低缓存输入的账单。

请求命中率和 token 命中率应分开：

~~~math
H_{\mathrm{req}}
=
\frac{N_{\mathrm{hit}}}{N_{\mathrm{req}}}
~~~

~~~math
H_{\mathrm{token}}
=
\frac{\sum_i P_{\mathrm{hit},i}}
{\sum_i P_i}
~~~

一个请求命中很短的前缀，和一个请求复用了几千 token，不应在成本报表中被视为
同样的收益。以当前 vLLM 文档为例，Automatic Prefix Caching 复用同一前缀的
KV 并减少 prefill；当输出 decode 占主要耗时或请求没有共享前缀时，性能收益
很小。这里的“减少计算”也不意味着 KV 驻留免费：缓存块会占显存并可能挤掉
活跃请求；必须同时测命中 token、prefill 时间、KV 占用、淘汰和请求 goodput。
厂商 API 的 prefix caching 可能有最小前缀长度、缓存计费价和保留时长等合同，
应按目标模型当前文档核对，不能直接套成本地 KV cache。

前缀必须是语义和权限上都可共享的内容。用户私有文档、会话中的敏感信息和
租户策略不能因为字节序列相同就跨用户复用。缓存身份至少应包括内容 hash、
模型和 tokenizer revision、processor、模板、权限域和过期版本。

### 5.2 Response cache

response cache 直接返回之前的回答，收益比 prefix cache 更大，但正确性条件
也更严格。适合缓存的请求通常具有：

1. 输入完全相同或语义等价。
2. 答案不依赖用户身份或实时状态。
3. 知识和权限在 TTL 内不会变化。
4. 输出不包含个性化或敏感数据。

响应缓存 key 不能只使用用户问题。至少要加入模型、prompt、知识索引、权限
策略、语言、工具状态和数据时间版本。对于“今天的库存”“我的订单状态”
和私有文档问答，默认应绕过或严格缩短 TTL。

把一次查找成本计入每个请求，并把维护开销按请求摊销后，期望成本为：

~~~math
C_{cache}
=
C_{lookup}+(1-H_{resp})C_{model}+C_{maintenance}
~~~

C_lookup 是每次请求的查找成本，C_model 是未命中时的完整模型路径成本，
C_maintenance 是按请求摊销的版本更新、删除和失效成本。相较于不缓存的
C_model，纯成本上的回本条件是：

~~~math
H_{resp}C_{model}>C_{lookup}+C_{maintenance}
~~~

例如模型路径每次 0.01 美元，查找为 0.0001 美元，维护摊销为 0.0002 美元，
最低经济命中率是 3%；但这个不等式不包含过期、权限错误和质量损失。只要
缓存回答不满足新鲜度、授权或正确性契约，就应绕过缓存，无论命中率和账面
节省多高。

### 5.3 Embedding、OCR 和视觉缓存

RAG 可缓存文档 embedding、query embedding、OCR 和 reranker 结果；多模态系统
还可以缓存规范化图像和 vision encoder 输出。缓存 key 要覆盖：

1. 内容摘要和规范化版本。
2. embedding、OCR 或 encoder 模型版本。
3. tokenizer、processor 和尺寸参数。
4. 语言、检索策略和索引版本。
5. 租户、权限和删除状态。

embedding 升级后，旧向量可能仍能被索引读取，却不再与新 query 向量兼容。
缓存失效和索引迁移应作为一个 artifact revision 发布，不要只替换其中一个文件。

### 5.4 缓存一致性和 stampede

缓存的难点不只是命中率，还包括：

1. TTL 和主动失效。
2. 删除请求传播。
3. 多副本之间的一致性。
4. 并发 miss 造成的 thundering herd。
5. 失败结果是否可缓存。
6. 缓存占用的显存、磁盘和网络。

single-flight 可以让同一个 key 在 miss 时只由一个请求构建，其他请求等待；
等待也要有超时，构建失败要清理占位。短暂缓存“无结果”有时能防止热 key
反复打爆后端，但必须区分真正的空结果、权限拒绝和暂时性故障。

## 6. Speculative decoding

### 6.1 基本机制

自回归模型通常每次生成一个 token。speculative decoding 让 draft model 先
提出一段候选，再由 target model 批量验证：

~~~text
已有前缀
  -> draft model 生成 K 个候选
  -> target model 一次计算候选位置
  -> 按算法接受连续候选
  -> 遇到不接受的位置由 target 采样或回退
~~~

它的主要目标是减少 target model 的串行 decode step，而不是减少最终输出
token 数。draft model 的计算、候选验证、KV 状态维护和通信都属于总成本。

### 6.2 接受率和收益

如果 draft 每轮提出 K 个 token，标准 speculative sampling 会在被拒绝时从
target 分布中采一个 token；若 K 个候选全部接受，还会额外输出一个 target
bonus token。因此每轮的期望输出 token 数不是“接受的 draft token 数”，还要
加上这个保证输出。设第 j 个位置在前面都接受条件下的接受概率为 α_j：

~~~math
E[L]
=
1+\sum_{j=1}^{K}\prod_{i=1}^{j}\alpha_i
~~~

如果把各位置接受近似为独立、且使用同一个接受率 α，则：

~~~math
E[L]=1+\alpha+\alpha^2+...+\alpha^K
=\frac{1-\alpha^{K+1}}{1-\alpha}
~~~

例如 K=4、α=0.8，期望每轮生成 3.3616 个 token。这个期望值不是加速比；它
只近似说明 target 验证轮次可能怎样减少。目标输出长度为 O 时，可把

~~~math
N_{\mathrm{target}}
\approx
\frac{O}{E[L]}
~~~

拿来估算轮数，再直接比较完整路径的 draft、target 验证、KV 更新、调度和
通信 GPU 时间。标准拒绝采样在匹配的 p(target)、q(draft) 分布时按
min(1,p/q) 接受候选，并从归一化的 max(0,p−q) 残差分布中修正拒绝位置，因而
保持 target 的采样分布；某些为了速度改变 verifier 的实现会明确放弃这一
精确性，不能把它们和 exact speculative sampling 混称为等价方案。

真实接受概率受上下文、温度、top-p、任务类型和 draft/target 分布差异影响。
如果 draft 过慢、α 很低或每轮调度开销很大，少跑几轮 target 也可能不省总
成本。应该直接测：

1. draft tokens/s。
2. 每轮验证耗时。
3. 接受率及其按任务切片的分布。
4. target 调用次数。
5. TTFT、TPOT、总 GPU 时间和质量。

### 6.3 什么时候收益不稳定

speculative decoding 对代码、模板化输出和高概率文本可能很有效，对需要复杂
推理、随机采样或 draft 与 target 能力差距大的任务可能收益很小。代表方法的
选择取决于候选从哪里来：

| 候选来源 | 解决的问题 | 主要限制 |
| --- | --- | --- |
| 独立 draft model | 用较小模型便宜地产生候选，再由 target 并行校验 | 需要额外常驻权重/显存；draft 和 target tokenizer、采样设置及分布要兼容 |
| MTP head | target 训练时增加多 token 预测头，利用模型自身的未来 token 信号 | 依赖模型训练与接口支持；不是任意 checkpoint 都能直接添加 |
| EAGLE 类方法 | 用 target 的中间特征辅助构造更贴近 target 的候选 | 需要匹配模型结构和专门训练/集成；额外特征与树验证会增加实现复杂度 |
| n-gram / suffix | 从本次 prompt、检索文本或历史输出中找重复片段，不另放 draft 模型 | 对代码模板、重复文档有效，对开放式新内容缺少可提议的高接受候选 |

这些方法减少串行 decode 的机会不同，性能排序不能离开 QPS、模型、硬件和
采样配置。vLLM 当前文档把 speculative decoding 定位于中低 QPS、memory-bound
工作负载，并明确提示真实收益依赖模型家族、流量和硬件；它还将 FLy verifier
标为 lossy，因此选择时要先决定能否接受分布变化，再做 benchmark。

验证时要固定 target、draft、tokenizer、停止条件和随机种子，分别比较无加速
与加速路径。不能因为某个短 prompt 的 tokens/s 提升，就推断所有长上下文和
高并发 workload 都降本。

## 7. 量化与蒸馏的经济收益

### 7.1 量化省的是哪一笔账

量化可以降低权重、激活或 KV Cache 的存储精度。它可能带来：

1. 模型能放进更小或更少的 GPU。
2. 权重读取和显存带宽压力下降。
3. 同一节点可以运行更多副本。
4. KV Cache 能容纳更高并发。

但“bit 数下降”不等于“单位 token 成本按比例下降”。如果 runtime 没有匹配的
kernel，反量化开销可能抵消收益；如果瓶颈在 CPU、网络或排队，GPU 权重缩小
也不会显著降低端到端时间。

几类常见方法压缩的张量和误差处理方式并不相同：

| 方法 | 压缩对象与机制 | 更适合解决的瓶颈 | 主要代价与限制 |
| --- | --- | --- | --- |
| [GPTQ](https://arxiv.org/abs/2210.17323) | 权重后训练量化；利用近似二阶/Hessian 信息和误差补偿，逐层拟合量化权重 | 权重显存/带宽受限的部署 | 校准样本、量化分组和 kernel 实现影响质量与速度；理论低 bit 不保证 runtime 有高效 kernel |
| [AWQ](https://arxiv.org/abs/2306.00978) | 权重后训练量化；根据激活统计识别显著通道并缩放以保护重要权重 | 权重压缩且希望避免对少数敏感通道造成过大误差 | activation-aware 不代表量化激活；其具体收益绑定模型、校准和推理 kernel |
| [SmoothQuant](https://arxiv.org/abs/2211.10438) | 通过等价通道缩放把部分 activation 量化难度迁移到 weight，常用于 W8A8 路径 | 需要权重与激活都低精度的矩阵乘 | 权重更难量化；需要匹配的 W8A8 kernel 和校准数据 |
| [KIVI](https://arxiv.org/abs/2402.02750) | KV Cache 非对称 2-bit 量化：K 按通道、V 按 token 分组量化；未凑满分组的 residual 区保留全精度，积累到阈值后再量化 | 长上下文或高并发下 KV 显存成为瓶颈，同时避免把最新局部上下文过早压成低精度 | 论文实验用 `G=32`、`R=128`，不是通用最优值；精度窗口增加显存，收益依赖目标 attention/runtime、任务难度和 kernel，需本地测量 |

所以“INT4 比 FP8 更省”不是充分的选型结论：前者可能指权重，后者可能是
权重、激活或 KV；scale、zero point、group metadata、对齐和临时 buffer 都会
改变实际 bytes。部署比较要列出被量化的张量、有效 bits/weight、峰值显存、
目标 kernel、prefill/decode 性能和同一组任务切片上的质量、安全与结构化输出。
若只减少权重却让吞吐变慢、GPU 数不变，成本收益可能为负。

量化评估至少分开：

1. 权重显存和加载时间。
2. prefill 与 decode 吞吐。
3. KV Cache 容量。
4. TTFT、TPOT 和 P99。
5. 通用、代码、数学、长上下文和多模态质量。
6. 结构化输出、安全和拒答行为。

### 7.2 蒸馏的持续成本

蒸馏把大模型行为迁移到小模型，部署成本可能下降，但训练和数据维护成本
会上升。teacher 的错误、偏好和安全边界可能被复制；领域数据变化后，还需要
刷新蒸馏集和重新评估。

蒸馏是否划算，应比较整个生命周期：

~~~math
C_{\mathrm{lifecycle}}
=
C_{\mathrm{distill}}
+T_{\mathrm{serve}}C_{\mathrm{small}}
+C_{\mathrm{eval}}
+C_{\mathrm{refresh}}
~~~

与继续使用大模型的

~~~math
C_{\mathrm{large\ baseline}}
=
T_{\mathrm{serve}}C_{\mathrm{large}}
+C_{\mathrm{fallback}}
~~~

其中 T_serve 是预期服务期，C_refresh 是数据和再训练成本。小模型的平均成本
很低，但如果复杂请求频繁 fallback，最终可能不如直接使用一个适中的模型。

[Minitron](https://arxiv.org/abs/2407.14679) 提供了一个有边界的案例：NVIDIA
从 Nemotron-4 15B 做结构化剪枝和蒸馏，得到 8B/4B 模型；论文称每个派生模型
相对从头训练最多少用 40 倍训练 token，15B/8B/4B 整个模型族按作者的同 token
基线计算可节省约 1.8 倍训练 FLOPs。这是特定模型族、剪枝/蒸馏流程和成本
假设下的结果。它说明共享大模型再派生小模型可能降低重复训练成本；不证明
任意 15B 模型都能以相同预算得到等价能力。做业务决策时仍需把训练、评测、
领域刷新和 fallback 成本代入生命周期公式。

## 8. Batch、队列与 Autoscaling

### 8.1 Batch 是成本和体验的共同杠杆

continuous batching 可以把多个请求放进同一轮 decode，提高 GPU 利用率；但
长请求和短请求混跑会改变每个请求的 ITL，等待窗口过长又会损害 TTFT。成本
优化不能只看 tokens/s，还要看在目标 SLO 下的有效 tokens/s。

请求可以按输入长度、输出长度、模态、优先级和模型分组。分组更规整，可能
提高 kernel 效率，却降低了跨组的合并机会；最优点要通过 workload 回放找到。

代表性调度方案处理的是不同层次的问题：

| 方案 | 机制 | 主要收益 | 代价/限制 |
| --- | --- | --- | --- |
| Continuous batching（Orca/vLLM 类运行时） | 每轮 decode 重新调度，完成的序列退出、等待序列加入 | 减少静态 batch 的 padding 和空槽 | 长 prefill、长 decode 和优先级会互相干扰；要同时控制 token budget、KV 和尾延迟 |
| [Sarathi-Serve](https://arxiv.org/abs/2403.02310) | 把长 prefill 切成 chunk，并让 chunk 与 decode 调度协作 | 降低长 prompt 对正在 decode 请求的阻塞，在吞吐和延迟间找折中 | chunk 太大仍会造成停顿，太小会增加调度/kernel 开销；结果绑定模型、硬件和负载 |
| [DistServe](https://arxiv.org/abs/2401.09670) | 将 prefill 与 decode 放到不同 GPU pool，分别按 TTFT/TPOT goodput 配置 | 减少两阶段资源争用，并允许两类容量独立扩展 | 需要额外 KV 状态传输和资源切分；突发流量比例变化时可能出现一侧闲置、另一侧排队 |

这几类工作不能按论文中的单一 tokens/s 排名：要在同一到达 trace、提示/输出
长度分布、硬件和 TTFT/TPOT 门槛下，比较满足 SLO 的 goodput、GPU 小时、
KV 峰值、排队和 P99。

### 8.2 排队预算

如果到达率为 λ、单队列平均服务率为 μ，利用率为 ρ=λ/μ。作为直觉示例，在
单服务台、稳定条件 λ<μ、Poisson 到达、指数服务时长和 FIFO 的 M/M/1 假设
下，平均排队时延为 Wq=ρ/(μ−λ)。令 μ=10 请求/秒：λ=8 时，ρ=0.8、Wq=0.4 秒；λ=9.5 时，
ρ=0.95、Wq=1.9 秒。利用率只从 80% 增到 95%，模型推导的平均排队时间就变成
原来的 4.75 倍。

这个算例不是 LLM 容量公式。真实请求有不同输入/输出长度，服务时间受 batch、
KV、抢占和 SLO 影响，且调度器不是 M/M/1 的独立服务台。它说明的是为什么
接近饱和时不能拿平均利用率当安全容量；应以真实 trace 回放测队列 age、
TTFT/TPOT 和超时。成本优化不能把所有请求都接收进无限队列：

1. 队列满时返回 backpressure。
2. 低优先级任务进入异步或延后队列。
3. 长任务单独计量并设置时长上限。
4. 失败重试使用指数退避和幂等键。
5. 取消后释放 KV、GPU 和临时文件。

队列中的请求已经消耗了状态库、网络连接和调度资源。过长的队列会把成本和
延迟一起放大，而不是免费吸收流量。

### 8.3 扩容指标

LLM worker 冷启动可能需要拉取镜像、加载权重、初始化 kernel、分配显存和
warmup，耗时从几十秒到数分钟不等。扩缩容应结合：

1. waiting queue length 和 queue age。
2. 预计输入/输出 token。
3. KV Cache 使用和活跃序列数。
4. TTFT、TPOT、P95/P99。
5. GPU 利用率、显存和 worker 健康。
6. 预计流量和时间段。

只按 CPU 或 QPS 扩容会忽略模型服务的真正工作量。Kubernetes HPA 的基础控制
公式是 desiredReplicas=ceil(currentReplicas×currentMetric/desiredMetric)；有
多项指标时，控制器按各指标算出的副本建议取较大值。举例当前 4 个 worker、
队列 token 指标为目标的 1.8 倍，建议数为 ceil(4×1.8)=8。HPA 只执行控制环，
不替你决定“正确的 LLM 指标”：可接自定义 queue age、待处理 token 或 KV
压力指标，但需处理采集延迟、冷启动、预热期、缩容稳定窗口和短时尖峰。

可以保留少量 warm pool，在可预测的高峰前预热，低峰期再逐步缩容。

### 8.4 缩容和 draining

缩容不是直接删除 pod。一个流式请求可能正在发送音频或 token，一个 Agent
可能已经调用外部工具。安全的 draining 流程是：

~~~text
停止接收新请求
  -> 继续服务短请求
  -> 对长请求返回迁移/取消信号
  -> 等待或重算可迁移状态
  -> 确认工具和对象存储状态
  -> 释放 worker
~~~

无副作用的 prefill 或 encoder 可以重算；有副作用的工具动作必须查询提交
状态。扩容数量应包括冷启动期间的容量缺口，而不是等队列增长后才行动。

## 9. 限流、预算和多租户治理

### 9.1 限流单位不能只有 QPS

一个请求可能只消耗几十 token，也可能包含长文档、图片、视频和多步工具调用。
更合理的预算单位包括：

1. input/output token。
2. active sequences 和 KV blocks。
3. GPU milliseconds。
4. 图片像素、音频秒数和视频帧。
5. Agent steps、tool calls 和外部执行时间。

每个租户可以同时拥有请求速率、并发、每日 token、GPU 时间和任务时长预算。
预算用尽时，应返回明确的限流或异步排队状态；不要通过静默截断上下文来隐藏
预算耗尽。

### 9.2 长请求和异常请求

成本攻击不一定需要恶意代码。超长 prompt、极大图片、长视频、重复 cache
miss、工具循环和失败重试都可能耗尽资源。入口应限制：

1. 最大输入 token 和输出 token。
2. 最大图片像素、PDF 页数、音频时长和视频帧数。
3. 最大 Agent step、工具次数和总 wall time。
4. 单租户并发和队列长度。
5. 单次请求能够产生的缓存和日志大小。

这些限制不是质量指标的替代品，而是防止一个请求把共享资源拖垮的工程边界。

### 9.3 多租户公平

如果只按全局成本优化，流量大的租户可能占满 prefix cache、队列和 GPU，低流量
但高价值的请求反而得不到服务。可以使用加权公平队列、租户级并发上限和优先级
老化，让优先级差异不会变成无限饥饿。

成本报表还要显示租户分摊和共享资源分摊。把所有缓存、预热和安全服务成本
平均摊给每个请求，会掩盖哪个 workload 真正需要优化。

## 10. RAG、Agent 与多模态专项优化

### 10.1 RAG 的成本链路

RAG 的成本可以拆成：

~~~text
query rewrite
  -> embedding
  -> sparse / dense retrieval
  -> reranker
  -> context assembly
  -> LLM prefill / decode
~~~

最有效的优化往往不是让向量库每次快几毫秒，而是减少无关证据进入 LLM。可以
按任务和检索置信度分层：

1. 高置信度 FAQ 直接使用稀疏或向量召回。
2. 候选冲突或置信度低时启用 reranker。
3. 高价值问题保留更多证据和引用检查。
4. 低价值问题使用较小上下文预算。
5. 文档 embedding、query embedding 和规范化结果按版本缓存。

top-k 越大不一定越好。无关证据会增加 prefill、KV 和幻觉机会；但过度压缩
也会丢失条件和例外。应在固定检索集上比较召回、引用支持、输入 token 和
单位成功任务成本。

### 10.2 Agent 的循环成本

一个 Agent 任务的成本可以近似写成：

~~~math
C_{\mathrm{agent}}
=
\sum_{t=1}^{T}
\left(C_{\mathrm{llm},t}+C_{\mathrm{tool},t}+C_{\mathrm{retrieve},t}\right)
+C_{\mathrm{state}}
+C_{\mathrm{failure}}
~~~

T 是实际步骤数，C_state 是状态存储、摘要和上下文增长成本，C_failure 是失败、
重试和人工升级成本。限制 max steps 很有用，但不能只把 T 写死；如果每一步把
完整历史重新塞给模型，C_llm,t 仍会随时间增长。

这类增长可以直接算出来。假设 Agent 第一次调用带 P0 个历史 token，之后每步
新增 Δ 个 token，且每次都重发完整历史，执行 T 步时总输入量为：

~~~math
P_{total}
=
TP_0+\Delta\frac{T(T-1)}{2}
~~~

例如 P0=1,000、每步增加 Δ=400、T=6，则六次调用合计发送
6×1,000+400×(0+1+2+3+4+5)=12,000 个输入 token。若外部状态保存完整事件、
每步只带固定 1,000-token 摘要和当前观察，则约为 6,000 个 token。这个简化
账本还没计入摘要调用自身的成本，摘要若遗漏工具提交状态或权限条件，也会
提高失败与恢复成本；所以应在同一 trace 中统计历史输入、摘要生成、工具输出
和最终成功。

降低 Agent 成本的顺序通常是：

1. 简单任务不使用 Agent。
2. 让工具返回结构化、短而可定位的结果。
3. 把完整事件存外部状态，只把当前必要字段放入上下文。
4. 为重复读取使用安全缓存。
5. 对无副作用步骤有限重试，对写操作使用幂等状态。
6. 设置步骤、时间、token 和金额预算。
7. 失败后尽快停止或转人工，而不是无限反思。

### 10.3 多模态成本

前一章的视觉 token、OCR、ASR、TTS 和视频采样都有成本账本。常见控制方式是：

1. 以任务质量所需的最小分辨率处理图像。
2. 缓存规范化图像、OCR 和 vision encoder 输出。
3. 视频先粗采样，再按问题局部加密。
4. 长音频和长视频使用异步 worker。
5. 生成视频按分辨率、时长、帧数和采样步数计量。
6. 把多模态 worker 与低延迟文本 worker 分开调度。

文件大小、像素数、音频秒数和帧数应与请求 trace 关联。只看“多模态请求数”
无法比较一张小截图和一部一小时视频的成本。

## 11. 一套可复用的优化实验方法

### 11.1 先写假设

每次优化前先写清：

1. 现在的主要成本来源是什么。
2. 哪个变量会被改变。
3. 预计降低哪一项成本。
4. 可能损失哪类质量、延迟或安全。
5. 用哪些固定样本和线上指标判断。

例如，“把 FAQ 路由到小模型后，普通 FAQ 的单位成功任务成本下降 40%，引用
支持率不下降，P95 TTFT 下降 20%”。这比“试试小模型”更容易验证和回滚。

### 11.2 固定基线

基线应固定模型、prompt、数据、并发、硬件、随机种子、缓存状态和评估器版本。
缓存命中和 miss 不能混在一个结果里，否则一次实验可能只是命中率变化。
基线还要记录失败、拒答、人工升级和重试，不能只记录成功请求的平均成本。

### 11.3 分离离线和线上证据

离线回放能控制变量，适合发现质量和安全回归；shadow 能观察真实输入分布，
但会增加资源消耗；canary 能测真实用户体验，却必须限制影响范围。三者不是
相互替代的阶段，而是不同证据：

~~~text
固定回放
  -> shadow 观察真实分布
  -> 小 cohort canary
  -> 分层扩大或暂停
  -> 结果回写成本和质量账本
~~~

### 11.4 先看成功成本

优化后至少比较四组数据：

| 组别 | 需要回答 |
| --- | --- |
| 成本 | 每请求、每 token、每成功任务是否下降 |
| 性能 | TTFT、TPOT、P95/P99 和吞吐是否改善 |
| 质量 | 任务、引用、结构化和用户反馈是否退化 |
| 安全 | 漏放、误拦、越权和工具副作用是否变化 |

基线和候选要对相同 request ID 成对回放，按任务、长度、租户、缓存 hit/miss
和风险切片给出分布与置信区间。报告应包括失败请求和人工介入，而不是只算
成功答案的平均价格。可把期望总成本作为优化目标，同时将任务成功率、TTFT、
TPOT 和安全策略设为硬门槛；这里的安全门槛不能用更低成本抵消。若某一门槛
未通过，暂停继续放量并定位原因。第 14.5 节把这种决策写成受约束优化式。

## 12. 完整的成本优化设计案例

假设一个企业客服系统有四类请求：FAQ、知识库问答、代码片段解释和发票图片
问答。初始方案所有请求都使用大模型，RAG 每次都 rerank，重复 FAQ 不缓存，
Agent 任务允许四步工具调用。

第一步是建立账本，按请求记录输入输出 token、视觉位置、embedding、rerank、
GPU 时间、cache 状态、任务成功和转人工。回放后可能发现：

1. FAQ 占请求量的大部分，但只需要中小模型。
2. 长 RAG 的主要成本是上下文和 reranker，不是 query embedding。
3. 发票问答的视觉位置和 OCR 重复计算明显。
4. Agent 任务的长尾来自失败重试和重复工具结果。

第二步是设计分层：

~~~text
FAQ / 意图分类
  -> small model 或 response cache

一般知识问答
  -> hybrid retrieval
  -> 低置信度时 reranker
  -> 中等模型

代码和复杂推理
  -> code/large model

发票问答
  -> OCR/版面缓存
  -> VLM 只处理不确定区域

Agent
  -> 步骤、token、工具和 wall-time 预算
~~~

第三步是为每一层设定自己的质量和延迟观察方式。FAQ 看 exact match 和投诉，
RAG 看引用支持，发票看字段 F1 和坐标，Agent 看授权动作和成功提交。不能用
所有请求的平均质量替代这些任务指标。

第四步是逐步实验。先在固定回放上比较路由和缓存，再用 shadow 检查真实输入，
然后只对一个稳定租户做 canary。若成本下降但发票字段召回下降，回滚 VLM
分辨率策略，而不是回滚整个客服系统。若 Agent 的成本下降来自提前停止，却
使可逆操作完成率下降，应调整状态机和工具结果摘要。

这个案例的核心不是某个具体阈值，而是把优化变成可解释的因果链：

~~~text
成本异常
  -> 找到 workload 和资源账
  -> 提出一个局部改动
  -> 固定回放和安全样本
  -> shadow / canary
  -> 比较成本、质量、延迟和安全
  -> 扩大、暂停或回滚
~~~

## 13. 最小可运行的成本诊断示例

下面的 demo 用标准库比较“所有请求都走大模型、没有缓存”的基线，以及“模型
路由、prompt 压缩、response cache 和 Agent 步骤限制”的优化方案。示例把质量、
延迟、安全和成本分别报告，不把它们压成一个不可解释的布尔结论。

代码中的模型价格和 success_prob 都是合成教学值：后者表示对每类任务成功概率
的假设，用来演示期望成功数和每成功任务成本，不能冒充样本评测结果。FAQ 缓存
仅在显式 cache_eligible 且版本化 key 相同的情况下命中；示例给它单独的
cache_success_prob。安全信号明确标为“缺少证据”，因此即使成本与质量假设
通过，也会暂停扩量。

~~~python
import math
from pprint import pprint


MODELS = {
    "large": {"in": 0.003, "out": 0.010, "success_prob": 0.92, "ttft": 220, "tpot": 13},
    "small": {"in": 0.0005, "out": 0.0015, "success_prob": 0.84, "ttft": 80, "tpot": 5},
    "code": {"in": 0.0015, "out": 0.004, "success_prob": 0.88, "ttft": 160, "tpot": 9},
}
EXTRA = {"visual": 0.001, "embedding": 0.0001, "rerank": 0.0002}


def model_cost(model_name, prompt_tokens, completion_tokens):
    model = MODELS[model_name]
    return (
        prompt_tokens / 1000 * model["in"]
        + completion_tokens / 1000 * model["out"]
    )


def extra_cost(visual_tokens=0, embedding_tokens=0, rerank_tokens=0):
    return (
        visual_tokens / 1000 * EXTRA["visual"]
        + embedding_tokens / 1000 * EXTRA["embedding"]
        + rerank_tokens / 1000 * EXTRA["rerank"]
    )


def latency_ms(model_name, prompt_tokens, completion_tokens, visual_tokens=0, steps=1):
    model = MODELS[model_name]
    one_step = (
        model["ttft"]
        + prompt_tokens * 0.04
        + completion_tokens * model["tpot"]
        + visual_tokens * 0.02
    )
    return round(one_step * steps)


def baseline_prompt_tokens(row):
    if row["kind"] != "agent":
        return row["prompt"]
    steps = row.get("steps", 1)
    growth = row.get("prompt_growth", 0)
    return steps * row["prompt"] + growth * steps * (steps - 1) // 2


def baseline_cost(row):
    steps = row.get("steps", 1)
    prompt_tokens = baseline_prompt_tokens(row)
    completion_tokens = row["completion"] * steps
    return (
        model_cost("large", prompt_tokens, completion_tokens)
        + extra_cost(row.get("visual", 0), row.get("embedding", 0), row.get("rerank", 0))
    )


def baseline_latency(row):
    if row["kind"] != "agent":
        return latency_ms(
            "large",
            row["prompt"],
            row["completion"],
            row.get("visual", 0),
        )
    steps = row.get("steps", 1)
    growth = row.get("prompt_growth", 0)
    return sum(
        latency_ms(
            "large",
            row["prompt"] + growth * step,
            row["completion"],
        )
        for step in range(steps)
    )


def optimized_plan(row, seen_cache_keys, max_agent_steps=2):
    cache_key = row.get("cache_key")
    cache_eligible = row.get("cache_eligible", False)
    if cache_eligible and cache_key in seen_cache_keys:
        return {
            "model": "cache",
            "cost": 0.00005,
            "latency_ms": 20,
            "success_prob": row["cache_success_prob"],
            "prompt_saved": baseline_prompt_tokens(row),
            "cache_hit": True,
            "steps_used": 0,
        }

    if cache_eligible and cache_key:
        seen_cache_keys.add(cache_key)

    if row["kind"] == "simple":
        model = "small"
        prompt = row["prompt"]
        completion = row["completion"]
        steps = 1
        visual = 0
        embedding = 0
        rerank = 0
        success_prob = MODELS[model]["success_prob"]
    elif row["kind"] == "rag":
        model = "large"
        prompt = math.floor(row["prompt"] * 0.75)
        completion = row["completion"]
        steps = 1
        visual = 0
        embedding = row["embedding"]
        rerank = math.floor(row["rerank"] * 0.5)
        success_prob = 0.90
    elif row["kind"] == "code":
        model = "code"
        prompt = row["prompt"]
        completion = row["completion"]
        steps = 1
        visual = 0
        embedding = 0
        rerank = 0
        success_prob = MODELS[model]["success_prob"]
    elif row["kind"] == "vqa":
        model = "large"
        prompt = row["prompt"]
        completion = row["completion"]
        steps = 1
        visual = min(row["visual"], 920)
        embedding = 0
        rerank = 0
        success_prob = 0.86
    elif row["kind"] == "agent":
        model = "large"
        prompt = row["summary_prompt"]
        completion = math.floor(row["completion"] * 0.80)
        steps = min(row.get("steps", 1), max_agent_steps)
        visual = 0
        embedding = 0
        rerank = 0
        success_prob = 0.87
    else:
        raise ValueError(row["kind"])

    prompt_tokens = prompt * steps if row["kind"] == "agent" else prompt
    completion_tokens = completion * steps
    cost = model_cost(model, prompt_tokens, completion_tokens) + extra_cost(
        visual, embedding, rerank
    )
    return {
        "model": model,
        "cost": cost,
        "latency_ms": latency_ms(model, prompt, completion, visual, steps),
        "success_prob": success_prob,
        "prompt_saved": baseline_prompt_tokens(row) - prompt_tokens,
        "cache_hit": False,
        "steps_used": steps,
    }


requests = [
    {"id": "faq_1", "kind": "simple", "prompt": 700, "completion": 100, "quality_need": 0.80, "cache_key": "faq:v4:refund_policy:public", "cache_eligible": True, "cache_success_prob": 0.82},
    {"id": "faq_2", "kind": "simple", "prompt": 700, "completion": 100, "quality_need": 0.80, "cache_key": "faq:v4:refund_policy:public", "cache_eligible": True, "cache_success_prob": 0.82},
    {"id": "rag_invoice", "kind": "rag", "prompt": 2600, "completion": 180, "embedding": 900, "rerank": 1200, "quality_need": 0.87},
    {"id": "code_fix", "kind": "code", "prompt": 1100, "completion": 220, "quality_need": 0.86},
    {"id": "vqa_chart", "kind": "vqa", "prompt": 500, "completion": 120, "visual": 1452, "quality_need": 0.85},
    {"id": "agent_refund", "kind": "agent", "prompt": 900, "prompt_growth": 300, "summary_prompt": 700, "completion": 260, "steps": 4, "quality_need": 0.86},
]

seen_cache_keys = set()
rows = []
for row in requests:
    optimized = optimized_plan(row, seen_cache_keys)
    rows.append(
        {
            "id": row["id"],
            "kind": row["kind"],
            "baseline_cost": baseline_cost(row),
            "optimized_cost": optimized["cost"],
            "baseline_latency_ms": baseline_latency(row),
            "model": optimized["model"],
            "latency_ms": optimized["latency_ms"],
            "success_prob": optimized["success_prob"],
            "quality_need": row["quality_need"],
            "baseline_success_prob": row.get("baseline_success_prob", MODELS["large"]["success_prob"]),
            "prompt_saved": optimized["prompt_saved"],
            "cache_hit": optimized["cache_hit"],
            "steps_used": optimized["steps_used"],
        }
    )

baseline_total = sum(row["baseline_cost"] for row in rows)
optimized_total = sum(row["optimized_cost"] for row in rows)
baseline_expected_successes = sum(row["baseline_success_prob"] for row in rows)
optimized_expected_successes = sum(row["success_prob"] for row in rows)
route_counts = {}
for row in rows:
    route_counts[row["model"]] = route_counts.get(row["model"], 0) + 1

        isinstance(value, bool)
        or not isinstance(value, (int, float))
        or not math.isfinite(value)
        for value in values
    ):
        raise ValueError("percentile values must all be finite")
    ordered = sorted(values)
    position = (len(ordered) - 1) * quantile
    lower = math.floor(position)
    upper = math.ceil(position)
    if lower == upper:
        return ordered[lower]
    weight = position - lower
    return round(ordered[lower] + (ordered[upper] - ordered[lower]) * weight)
~~~

## 14. 常见误区和失败模式

### 14.1 小模型一定更便宜

小模型单次调用便宜，却可能需要重试、转人工或再调用大模型。比较时要把路由
器、fallback、失败和人工处理算进 C_success，而不是只看小模型的 token 单价。

### 14.2 压缩越多越好

删掉重复说明通常有收益，删掉条件、例外、时间、来源和安全规则则会制造错误。
压缩应以任务样本和 claim 支持率验证，并保留可回溯的原始上下文。

### 14.3 缓存命中率高就一定省钱

短前缀命中率高可能只省下很少 prefill；错误缓存则会扩大数据泄露和人工处置
成本。要看命中 token、实际 GPU 时间、失效维护和成功任务成本。

### 14.4 Autoscaling 能解决所有成本问题

扩容只能把等待分摊到更多副本，不能修复单请求 token 过长、模型选择错误、
工具循环和无效重试。低峰缩容还会引入冷启动、预热和流式 draining 成本。

### 14.5 用一个总指标做优化决定

成本、质量、延迟和安全的度量单位不同，不能随意相加成一个分数。优化问题
可以写成带硬约束的形式：

~~~math
\min_\theta E[C_\theta]
\quad
\text{s.t.}\quad
P(success_\theta)\ge q_{min},
P(TTFT_\theta\le t_{max})\ge s_{TTFT},
P(TPOT_\theta\le d_{max})\ge s_{TPOT},
SafetyViolation_\theta\le \epsilon
~~~

θ 是路由、压缩、缓存、量化、调度和容量等可调配置。真实系统可用分位数/阈值
表达相同约束；这里的概率式只是说明“降本”受质量、延迟和安全门槛约束。
安全策略与发布门禁不能仅作为可被成本收益抵消的加权项。实验结果应同时报告
成本、质量、TTFT/TPOT/P99、失败/重试和安全原始信号；任一硬门槛未通过就
暂停或回滚。

## 15. 资料与证据边界

1. [OpenAI Prompt Caching Guide](https://developers.openai.com/api/docs/guides/prompt-caching)：说明 OpenAI 接口中 prompt caching 的当前使用边界；供应商的缓存计费规则不能直接泛化到本地 KV Cache。
2. [vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html)：说明 vLLM 前缀缓存的工程入口；命中收益仍取决于 workload、块管理和权限设计。
3. [vLLM Speculative Decoding](https://docs.vllm.ai/en/latest/features/speculative_decoding/)：核对当前 speculative decoding 的引擎配置与实现边界；真实加速需要目标模型和硬件压测。
4. [Speculative Sampling](https://arxiv.org/abs/2211.17192)：介绍 draft/target 验证思想的经典研究；论文加速结果不能替代线上接受率和成本测量。
5. [FrugalGPT](https://arxiv.org/abs/2305.05176)：模型级联和成本/质量权衡的研究背景；路由器在目标业务上的错误和 fallback 成本需要单独评估。
6. [RouteLLM](https://arxiv.org/abs/2406.18665)：成本敏感的模型路由研究资料；公开数据集和路由阈值不等于所有领域的最优点。
7. [LLMLingua](https://arxiv.org/abs/2310.05736)：长 prompt 压缩的研究入口；压缩比例和质量保持需要在目标任务上复现。
8. [LongLLMLingua](https://arxiv.org/abs/2310.06839)：长上下文场景的 prompt 压缩研究；不能把论文 benchmark 直接当成生产上下文契约。
9. [MQA: Multi-Query Attention](https://arxiv.org/abs/1911.02150)：减少 KV head、缓解 decode 内存带宽的研究背景；前文已讨论其 cache 机制，具体收益仍依赖 runtime。
10. [GPTQ](https://arxiv.org/abs/2210.17323)：后训练量化研究入口；量化后的质量、kernel 和吞吐必须在目标模型上验证。
11. [AWQ](https://arxiv.org/abs/2306.00978)：activation-aware weight quantization 研究背景；论文质量结果不能证明所有任务不退化。
12. [Kubernetes Horizontal Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)：确认基础比例控制公式、多指标建议和稳定行为；LLM 自定义指标与扩容延迟仍需按目标部署设计。
13. [Kubernetes Resource Management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)：容器资源请求、限制和调度的官方资料；LLM 服务还需要增加队列、显存和模型冷启动约束。
14. [RAG: Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401)：RAG 的基础研究资料；检索质量和上下文 token 成本要在业务数据上测量。
15. [OpenTelemetry Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)：成本、延迟和缓存追踪的可观测性基础；敏感数据仍需要最小化和访问控制。
16. [LLMLingua-2](https://arxiv.org/abs/2403.12968)：核对 token 分类压缩器的蒸馏与评估；其 MeetingBank 训练来源和论文的跨域任务不是目标业务保证。
17. [SmoothQuant](https://arxiv.org/abs/2211.10438)：权重/激活 W8A8 的等价通道缩放路线；需与权重专属 GPTQ/AWQ 和 KV 专属 KIVI 区分。
18. [KIVI](https://arxiv.org/abs/2402.02750)：核对 K-per-channel、V-per-token、分组与 residual window 的 KV Cache 量化设计；论文质量结果绑定其模型、硬件与任务。
19. [Minitron](https://arxiv.org/abs/2407.14679)：结构化剪枝与知识蒸馏生成模型族的研究；40× token 与 1.8× FLOPs 数字绑定 Nemotron-4 15B/8B/4B 的作者计算基线。
20. [Sarathi-Serve](https://arxiv.org/abs/2403.02310) 与 [DistServe](https://arxiv.org/abs/2401.09670)：分别核对 chunked prefill/stall-free scheduling 与 prefill/decode 分离；论文性能数字不能脱离其 GPU、流量和 SLO 使用。
21. [A Survey of LLM Inference Systems](https://arxiv.org/abs/2506.21901)：用作 batching、调度、KV 管理、量化和多副本的文献地图，具体方法仍回到原论文和实现版本核对。

论文用于理解压缩、路由、量化和 speculative decoding 的方法，官方文档用于
确认当前 API 和 runtime 能力，目标 workload 的回放、价格、GPU 小时、成功
任务和人工处置才用于决定是否值得采用。任何“降低 20% 成本”“提升 2 倍吞吐”
的说法都应标明模型、硬件、输入输出分布、缓存状态、质量样本和时间范围。

## 16. 本章小结

成本优化的对象不是一个数字，而是一条从请求输入到成功任务的资源链。

1. 先建立 token、GPU、辅助服务、存储网络、重试和人工处理的成本账本，再定位
   最大的 workload 和最贵的阶段。
2. GPU 利用率、显存、prefill、decode、队列和 SLO 必须一起看；高利用率不一定
   代表用户体验好。
3. 模型路由要按任务能力、风险和质量底线选择，并把路由器、fallback 和错误
   路由成本算进期望成本。
4. prompt 压缩应优先结构化去重，保留条件、来源、权限、例外和状态；压缩率
   不能替代任务成功和证据支持。
5. prefix、response、embedding、OCR 和视觉缓存的收益不同，都需要版本、权限、
   TTL、删除和并发 miss 处理。
6. speculative decoding、量化和蒸馏能降低 decode 或显存成本，但收益取决于
   接受率、kernel、质量切片和完整生命周期成本。
7. batching、队列、autoscaling 和 warm pool 要围绕 token、KV、冷启动和流式
   draining 设计，而不是照搬无状态 Web 服务。
8. RAG、Agent 和多模态任务应各自控制 reranker、步骤、工具、视觉位置、音频
   秒数和视频帧，并用单位成功任务成本比较。
9. 每个优化都要经过固定基线、离线回放、shadow、canary 和线上监控，成本下降
   不能掩盖质量、安全或可靠性退化。

当一个优化方案既能说明省下了哪一笔钱，又能说明哪些用户任务没有被牺牲、哪
些风险仍被控制、出现异常如何暂停和回滚时，成本优化才从参数调节变成了工程
决策。
