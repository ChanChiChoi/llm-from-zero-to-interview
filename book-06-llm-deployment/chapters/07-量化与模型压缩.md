# 第七章：量化与模型压缩

量化不是把模型文件上的数字统一替换成更小的整数，而是重新安排“信息精度、内存带宽、计算 kernel 和任务质量”之间的预算。一个 7B 模型的权重从 FP16 换成 INT4，确实可能让单卡装下更大的模型；如果目标 kernel 不支持这种布局，或者量化误差让代码和工具调用失败，文件变小并不等于服务变好。

初学者可以把量化理解为有刻度的近似：原来每个数都用高精度记录，现在用一个较小的整数和一组 scale 共同表示。scale 决定整数刻度，zero point 决定非对称区间的起点，分组方式决定局部异常值会不会把整层的刻度拉宽。专家则需要继续追问：量化的是权重、激活、KV Cache 还是训练状态？误差发生在存储、反量化、累加还是状态复用？硬件是否真的走了低精度 kernel？校准样本是否覆盖线上任务？

本章按这条因果链展开：先建立推理显存账本和数值格式，再解释量化映射、粒度、校准与 PTQ/QAT；随后分别讨论 weight-only、activation、GPTQ、AWQ、SmoothQuant 和 KV Cache quantization，最后讲蒸馏、剪枝、稀疏化、可复现 demo 和部署评估。每种方法都同时说明“解决了什么、没有解决什么”。

本章负责通用原理、代表算法和压缩决策；格式和部署专题沿用本章的概念，但各有更完整的主讲位置：[第十五章](15-fp4-mxfp4-nvfp4.md)解释 FP4、MXFP4、NVFP4 及其 kernel 路径，[第十六章](16-fp8-kv-cache.md)解释 FP8 KV Cache 的 scale、allocator 和生命周期，[第十七章](17-native-int4与原生量化部署.md)解释 native INT4 artifact、packing、kernel 覆盖和发布回滚。本章只在需要区分决策对象时提到这些专题，不重复它们的格式与部署细节。

## 本章资料边界

本章用 GPTQ、AWQ、SmoothQuant、LLM.int8()、ZeroQuant 和知识蒸馏论文解释机制，用 Hugging Face Transformers、bitsandbytes、Quanto、NVIDIA TensorRT-LLM、vLLM 和 llama.cpp 的官方资料核对当前公开的格式与 runtime 边界。论文中的实验数字只属于论文模型、校准集和硬件；官方文档中的支持矩阵也不能替代目标模型的质量、kernel 和协议回归。FP4、MXFP4、NVFP4 等新格式放在趋势小节中，明确区分标准定义、厂商实现和本项目实测。

## 1. 先问量化要解决哪个瓶颈

### 1.1 推理显存的四本账

推理显存至少由四部分组成：

1. 模型权重：随参数量和存储 bit 数增长。
2. KV Cache：随层数、KV head、上下文长度、活动请求数和 cache dtype 增长。
3. 激活与临时 buffer：随 batch、序列长度、kernel 和并行策略变化。
4. runtime、通信和 allocator 元数据：包括 scale、block table、workspace、CUDA graph 和碎片。

量化可以分别作用于这些账本，但作用位置不同。权重 INT4 主要减少模型常驻显存；KV Cache FP8 主要增加长上下文并发；激活 INT8 需要低精度矩阵计算与累加路径；训练状态量化则属于训练内存问题，不能直接当成在线推理优化。

若模型参数量为 N、权重存储使用 b_w bit，忽略元数据时：

~~~math
M_{\mathrm{weight,raw}}
=\frac{N b_w}{8}.
~~~

若每 g 个权重共享一个 scale，scale 用 b_s bit 存储，则一个粗略账本是：

~~~math
M_{\mathrm{weight}}
\approx
\frac{N b_w}{8}
+\frac{N}{g}\frac{b_s}{8}
+M_{\mathrm{zero}}
+M_{\mathrm{layout}}.
~~~

以 7B 参数为例，FP16 权重约为 13.04 GiB，INT8 约为 6.52 GiB，INT4 原始权重约为 3.26 GiB；实际文件和运行时还会加入 scale、zero point、padding、embedding、lm_head、分片和 workspace。GiB 与十进制 GB 也不能混用，容量报告应明确单位。

这些数量级可以从同一个输入复算：把 7B 视为 $N=7×10^9$ 个参数，FP16 payload 为 $7×10^9×16/8=14×10^9$ bytes，再除以 $1024^3$，得到约 13.04 GiB。INT8 与 INT4 分别把 16 换成 8、4，得到 6.52 GiB 和 3.26 GiB。这里假设所有参数都按同一精度紧密存储，不含任何 scale 或运行时开销；它是原始 payload 下界，不是模型文件大小或可部署容量承诺。

### 1.2 权重变小不等于请求容量按比例增加

如果权重从 16 bit 变成 4 bit，常驻权重账本大约减少四分之三；KV Cache、激活和 runtime buffer 没有自动减少。长上下文服务可能仍然被 KV Cache 限制，高 batch decode 可能仍然被带宽或 kernel launch 限制。

因此量化前先回答：

- 当前故障是模型权重放不下，还是 KV Cache 不够？
- 目标是单请求首 token、持续 token 间隔、并发、功耗还是单位成功任务成本？
- 低精度 kernel 是否存在，还是只把 packed weight 解包成高精度后再计算？
- 哪些任务对误差最敏感，是否有结构化输出、工具和安全约束？

只有第一个问题是显存容量时，weight-only 往往是很好的第一步；如果瓶颈是 KV Cache，单纯把权重压到 INT4 不会解决并发问题。

同一张卡的可用量还会随阶段变化：prefill 可能需要更大的临时 activation/workspace，decode 则随着活动序列持有 KV，并反复读取模型权重。即使量化释放了权重空间，runtime 也必须把这部分空间交给 cache allocator，且 admission policy 允许接入更多请求，才会转成并发收益；若瓶颈是计算吞吐或网络同步，单纯腾出显存不会降低每轮计算时间。

## 2. FP16、BF16、FP8、INT8 与 INT4

| 格式 | 每个值 bit 数 | 特点 |
| --- | --- | --- |
| FP16 | 16 | 浮点基线，尾数较多但指数范围小于 BF16 |
| BF16 | 16 | 指数范围接近 FP32，尾数较少，动态范围更宽 |
| FP8 | 8 | E4M3/E5M2 等变体，依赖 scale、硬件和 kernel |
| INT8 | 8 | 整数刻度较稳，常用于 W8A8 或激活路径 |
| INT4 | 4 | 权重压缩明显，误差、scale 和 kernel 风险更高 |

### 2.1 FP16 / BF16

FP16 和 BF16 都占 16 bit，但 bit 的分配不同。FP16 给尾数更多 bit，BF16 给指数更多 bit，因此 BF16 能覆盖更宽的数值范围，却牺牲了一部分相对精度。推理时选择哪一个不是抽象地比较“谁更高级”，而是看目标 kernel、累加精度、模型训练产物和硬件支持。

如果模型权重已经以 BF16 保存，转换成 FP16 可能在极端值附近产生溢出；反过来，FP16 权重转 BF16 会减少尾数精度。两者的质量差异往往小于 INT4 的量化误差，但仍应在真实模型上回放。

### 2.2 INT8

INT8 用整数乘以 scale 表示原值，存储和访存约为 FP16 的一半。它可以只作用于权重，也可以同时作用于权重和激活。后者常写作 W8A8，但 W8A8 只是精度配置，不代表任何硬件都能以 INT8 矩阵指令运行。

INT8 相对 INT4 通常更容易保持质量，然而 activation outlier、scale 更新、累加位宽和反量化位置仍会影响结果。若 kernel 先把 INT8 解包并转回高精度，显存收益可能仍然存在，延迟收益却未必存在。

### 2.3 INT4

INT4 让原始权重存储约变成 FP16 的四分之一，但实际还要加上每组 scale、zero point、对齐和索引。低比特可表示的离散等级更少，异常值会占用更大的刻度，导致同组其他权重的相对误差增加。

因此 INT4 更依赖校准数据、量化算法、分组大小、权重布局和 kernel 支持。它首先解决“模型能否装下”和“权重带宽是否成为瓶颈”，不自动解决 KV Cache、prefill 计算或任务质量。

初学者可以把 INT8 看作较宽的整数刻度，把 INT4 看作更窄的刻度；专家需要区分存储 bit、乘法输入 bit、累加 bit 和输出 cast 的位置。

### 2.4 基本量化公式与误差

设浮点值为 x_i，使用 b bit 的有符号对称整数，并采用对称范围 [-Q,Q]，其中：

~~~math
Q=2^{b-1}-1,\qquad
s=\frac{\max_i|x_i|}{Q},\qquad
q_i=\mathrm{clip}\left(\mathrm{round}\frac{x_i}{s},-Q,Q\right),
\qquad
\hat{x}_i=sq_i.
~~~

这里采用的是对称范围的教学约定；有些 INT4 实现使用 [-8,7] 的不对称整数范围，不能只根据“INT4”三个字推断 qmin 和 qmax。全零张量时 max 为 0，实际实现必须选择安全的 scale 并直接返回全零量化结果，不能除以 0。

若浮点范围不是围绕零对称，可使用 zero point z：

~~~math
s=\frac{x_{\max}-x_{\min}}{q_{\max}-q_{\min}},
\qquad
z=\mathrm{round}\left(q_{\min}-\frac{x_{\min}}{s}\right),
~~~

~~~math
q_i=\mathrm{clip}\left(
\mathrm{round}\left(\frac{x_i}{s}+z\right),
q_{\min},q_{\max}\right),
\qquad
\hat{x}_i=s(q_i-z).
~~~

最基本的量化误差可以用均方误差表示：

~~~math
\mathrm{MSE}
=\frac{1}{n}\sum_{i=1}^{n}(x_i-\hat{x}_i)^2.
~~~

沿用后文 demo 的八个权重 $[-1.2,-0.7,-0.1,0,0.2,0.9,1.4,2.2]$，做对称 INT4 量化时 $Q=2^{4-1}-1=7$，最大绝对值是 2.2，因此 scale 为 $s=2.2/7\approx0.3143$。逐个除以 scale 并舍入后得到整数 $[-4,-2,0,0,1,3,4,7]$，反量化得到约 $[-1.2571,-0.6286,0,0,0.3143,0.9429,1.2571,2.2]$。八个平方误差相加约为 0.05367，除以 8 后 MSE 约为 0.00671。若每四个数各用一组 scale，两个 scale 分别约为 0.1714 和 0.3143，整数为 $[-7,-4,-1,0]$ 与 $[1,3,4,7]$，该例 MSE 约为 0.00508。局部刻度降低了这个小样本的重建误差，但 scale 数量翻倍；小例子说明误差与 metadata 的交换，不代表任意张量或任务都能得到同样收益。

但对线性层 Y=XW，权重 MSE 并不等价于输出误差。校准输入 X 作用下的误差更接近：

~~~math
E_X=\|XW-X\hat{W}\|_2^2
=\|X(W-\hat{W})\|_2^2.
~~~

可以用一个两权重线性层看出校准输入为什么重要。设原权重为 $[1.01,0.01]$，量化后为 $[1,0]$：若输入是 $[1,0]$，输出从 1.01 变为 1，误差是 0.01；若输入是 $[0,10]$，输出从 0.1 变为 0，误差是 0.1。权重误差没有变化，误差却随输入方向放大十倍。校准激活不是替模型质量打分，而是帮助发现哪些权重误差更可能沿真实输入方向传到层输出。

再看一个 outlier 对统一刻度的影响。用四 bit 对称范围 $[-7,7]$ 量化 $[-1,-0.5,0.5,1]$，scale 为 $1/7$，量化整数为 $[-7,-4,4,7]$；若同组再加入一个值 8，scale 被拉到 $8/7$，原来的 $-0.5$ 和 $0.5$ 都会舍入到 0。若先把 8 裁剪到 1，普通值能使用更细的刻度，却会让该 outlier 产生很大的重建误差。裁剪因此是在尾部误差和主体分辨率之间换预算；应从校准分布选择阈值，再在独立评估集检查长尾样本是否饱和，不能把低权重 MSE 当成模型质量保证。

这就是为什么 GPTQ、AWQ 等方法要看校准激活，而不是只把每个权重独立四舍五入。最终还要测任务成功率、长上下文、代码、数学、结构化输出和工具参数；数值 MSE 只是诊断量，不是质量结论。

### 2.5 量化粒度：误差和元数据的交换

若一个张量只使用一组 scale，称为 per-tensor；若线性层 W 的每个输出通道各自使用 scale，常称 per-channel；若把权重按连续 g 个元素分组，则是 group-wise；activation 还可能按 token 或小 block 动态计算 scale。

| 粒度 | scale 数量 | 优势 | 代价 |
| --- | --- | --- | --- |
| per-tensor | 1 | metadata 少，kernel 简单 | 容易被 outlier 拉宽 |
| per-channel | 通道数 | 能适应通道范围差异 | 分片、转置和 activation 对齐更复杂 |
| group-wise | 约 N/g | 局部误差较小，适合低 bit 权重 | scale 访存与布局要求更高 |
| per-token / per-block | 随 token 或 block 增长 | 对动态 activation 更灵活 | 计算、同步和 metadata 成本高 |

若每个 scale 使用 c bytes、共有 n_s 个 scale，metadata 至少有：

~~~math
M_{\mathrm{scale}}=n_s c.
~~~

真实 artifact 还可能保存 zero point、二级 scale、padding 和索引。group size 不能脱离矩阵布局讨论：同样的 g，沿输出通道分组和沿输入通道分组会产生不同的误差传播和 tensor parallel 通信。读量化配置时，必须同时确认 scale 的轴、分组方向、存储 dtype 和 kernel 读取方式。

以 4,096 个权重为例，per-tensor 只有 1 个 scale；group size 为 128 时有 32 个 scale，group size 为 64 时有 64 个 scale。更细的刻度能让局部范围不必服从整张矩阵的极值，但 scale 字节、读取和分片边界也随之增加。比较粒度时应同时报告重建误差、scale/zero-point 数量和目标 kernel 的执行时间，不能只拿前两个格式的 MSE 作决定。

## 3. Weight-only quantization

量化对象决定误差从哪条数据路径进入服务：weight-only 先减少常驻权重与 decode 读带宽，activation quantization 再把低精度扩到动态输入，最后还要选择在训练完成后校准（PTQ）还是让训练过程适应 fake quant（QAT）。按“量化什么”再到“何时适配”逐步决策，可以避免把 W/A/KV 几个字母当成完整部署规格。

Weight-only quantization 只量化权重，激活和累加通常保持 FP16、BF16 或更高精度。常见配置会写成 W4A16、W8A16：W4/W8 描述权重存储，A16 描述激活输入或主要计算精度。这个记号不是完整 kernel 规格，还要说明累加精度、scale 粒度和输出 cast。

它在 LLM serving 中常见有三个原因。第一，模型权重是常驻显存，参数量大；第二，decode 每轮都要参与线性层计算，权重带宽可能成为瓶颈；第三，保持激活高精度通常比同时量化激活更容易维持质量。成熟实现会把 packed low-bit weight、scale 和高精度 activation 送进融合 kernel，尽量避免先完整解包成 FP16。

但 W4A16 的实际路径可能有三种：

1. 真正的低精度权重乘法，硬件使用对应矩阵指令。
2. 低精度存储、kernel 内部按 group 解包并以高精度累加。
3. runtime 只接受低精度 artifact，随后回退到通用高精度 kernel。

三条路径都可能返回正确文本，只有前两条通常带来明显的权重带宽收益，第三条可能只节省显存。必须用 profiler、kernel 名称、显存读写和目标 batch 证实路径，而不是从模型文件后缀推断速度。

weight-only 的边界还包括 lm_head、embedding、MoE router、norm 和小矩阵。有些模型只量化线性层而保留 norm/embedding 高精度；有些 kernel 对 group size、权重转置和 tensor parallel 分片有硬性要求。量化报告应列出实际被量化的模块集合。

同一份权重量化也可能在不同负载下呈现不同速度：小 batch decode 常受每 token 的权重读取影响，压缩可能降低读入字节；长 prompt prefill 会一次处理许多 token，矩阵计算和临时 workspace 的占比可能更高。因而应分别报告 TTFT、TPOT 和 E2E，并把 batch、输入输出长度和实际 kernel 一起固定；一个负载下的 decode 加速不能替代另一个负载下的 prefill 结论。

如果 profiler 显示权重读取不是唯一瓶颈，或 activation 本身占据显存、带宽与矩阵计算成本，就要把 activation 纳入候选；这会把静态权重映射扩展成依赖输入分布的在线路径。

把 W4A16 当成一个部署数据流看，会比只看 checkpoint 更清楚：离线转换器读取基线权重和校准激活，按模块生成 packed weight、scale、可选 zero point 与分片元数据；加载器核对这些字段和当前 runtime 的解释是否一致；执行 kernel 再按 group 取出整数权重、融合反量化与高精度 activation 的乘法，并在累加后恢复输出尺度。某个阶段若不认识 scale 轴或分片边界，系统可能拒绝加载，也可能回退到通用路径。排查时要分别看 artifact 大小、加载日志、实际 kernel、GPU 内存读写和端到端时延；前两者正确不能代替后几项。

## 4. Activation quantization

Activation quantization 会把线性层输入、中间结果或 attention 相关张量也映射到低 bit。若权重和激活都量化，可用 W8A8 等记号描述；量化收益可能扩展到激活显存、带宽和矩阵乘，但误差路径也从一处变成多处。

activation 的困难在于它依赖输入。不同语言、位置、任务、batch 和 reasoning 轨迹可能产生不同范围；少量 outlier 会让 per-tensor scale 变大，绝大多数普通值只占用很少的整数等级。per-channel、token-wise、group-wise 或动态 scale 可以缓解这一点，却会增加 metadata、同步和 kernel 复杂度。

部署时至少要回答：

1. scale 是离线校准、每 batch 更新，还是每 token/每 channel 动态计算？
2. outlier 是被裁剪、保留高精度，还是转移到另一个张量？
3. 矩阵乘的乘法和累加分别用什么精度？
4. scale 是否与 tensor parallel、sequence parallel 和流水线边界一致？

用合成激活 $[-3,-0.5,0,0.8,2.5,8]$ 手算一次非对称 INT8：取 $q_{\min}=0$、$q_{\max}=255$，且范围包含零，则 $s=(8-(-3))/255=11/255\approx0.04314$，$z=\mathrm{round}(0-(-3)/s)=70$。逐个计算并裁剪 $q_i=\mathrm{clip}(\mathrm{round}(x_i/s+z),0,255)$，得到 $[0,58,70,89,128,255]$；反量化约为 $[-3.0196,-0.5176,0,0.8196,2.5020,7.9804]$。整数刻度把实际输入映射到 256 个等级，舍入产生小误差；本例只说明映射步骤，不代表模型激活或业务质量的测量结果。

刻度在哪里计算，会改变运行时的成本和误差相关性。静态 scale 可在加载前准备，推理时少做统计，但对超出校准范围的新输入更敏感；动态 token scale 会跟随当前向量的范围，减轻不同 token 混用一个范围的问题，却要在执行中求最大值、更新 scale 并让后续矩阵乘读取它。per-channel scale 更适合通道分布差异明显的张量，但在转置或 tensor parallel 切片后必须保持相同的通道映射。实现常把整数乘积累加到更宽的 accumulator，再按 activation 与 weight scale 恢复数值；偏置、残差和归一化的执行顺序也会影响舍入点。因而 W8A8 不能只写两个数字，必须记录刻度刷新时机、累加精度和输出转换位置。

activation 量化更可能带来真正的端到端加速，但也更容易在数学、代码、长上下文和结构化输出上出现非均匀退化。若只在平均语言建模 loss 上回归，可能漏掉业务最敏感的失败。

确定目标张量后，还需决定误差统计来自已训练模型的校准样本，还是在训练中显式适应量化噪声。PTQ 与 QAT 的成本和风险不同，但两者都必须把训练/校准时使用的数值规则与部署 artifact、kernel 对齐。

## 5. PTQ 和 QAT

### 5.1 PTQ

Post-Training Quantization 在训练完成后用校准样本估计 scale、zero point、敏感通道或误差补偿，不更新原始模型的训练目标。它适合已有 checkpoint 的快速试验和多格式 artifact 构建，代价是模型没有机会重新学习如何抵消量化噪声。

PTQ 质量取决于三件事：校准样本是否覆盖部署分布，误差目标是否反映真实激活，以及转换后的 kernel 是否与校准假设一致。只用少量短英文样本校准一个多语言、长上下文、工具调用模型，可能在离线 toy 评估上正常，线上却出现格式或事实性退化。

### 5.2 QAT

Quantization-Aware Training 在训练或微调期间插入 fake quantization，让前向看到近似的量化误差，反向通常用 straight-through estimator 近似不可导的 round。模型因此有机会调整权重和激活分布，但训练中使用的 fake quant、部署时的真实 kernel 和 scale 更新策略必须保持一致，否则训练适应的是一种误差，线上执行的是另一种误差。

QAT 适合低 bit 质量目标明确、模型生命周期较长、可以承担额外训练和回归成本的场景。它不适合未经验证就当作“低比特质量必然恢复”的保险。训练数据、学习率、冻结模块、scale 学习方式和部署格式都会影响结果。

选择 PTQ 还是 QAT，可以按时间和风险判断：需要快速比较候选格式时先做 PTQ；PTQ 在关键任务上出现稳定且可归因的退化、同时模型值得长期维护时，再考虑 QAT 或量化感知微调。

若模型和部署目标还在频繁变化，先用 PTQ 快速筛除不兼容格式，避免为短期候选承担长训练周期；若硬件、任务和量化格式稳定，且关键任务的 PTQ 退化可复现，才有理由评估 QAT 的训练成本。这里的判断依赖维护周期与业务损失，不存在“QAT 一定更准”的通用结论；即使 fake quant 训练损失下降，也要在真实导出格式和目标执行路径上重新回归。

一个可追溯的量化产物还要绑定基础 checkpoint revision、模型配置、tokenizer 与 chat template、校准样本清单及其去重规则、量化工具版本、目标模块、bit width、group size、scale 轴和导出 hash。否则即使两份配置都写 W4A16，也无法判断它们是否从同一权重生成，或者是否覆盖了相同模块。PTQ 的比较应先固定这些输入，再一次只改变量化算法或粒度；QAT 则另外记录训练数据、fake-quant 规则、学习率和训练步数，并确认导出后的真实量化 kernel 使用相同范围和舍入约定。这个记录让失败能回溯到校准、算法、artifact 或执行路径，而不是把所有差异都归因成“低 bit 精度不够”。

## 6. GPTQ

下面三节回答同一个问题：不做完整重训练时，怎样利用已训练模型的结构和激活来控制低比特误差？GPTQ 从层输出重建误差出发补偿已量化权重；AWQ 把校准激活用于敏感通道和等价缩放；SmoothQuant 面向 W8A8，把 activation outlier 的动态范围迁移到权重侧。它们优化的变量不同，适合放在同一条“误差来源—变换方式—部署约束”链上比较。

GPTQ 是一种面向大语言模型的 post-training weight quantization 方法。它不重新训练完整模型，而是逐层或逐块选择低 bit 权重，使校准输入经过该层后的输出误差尽量小，再利用近似二阶信息补偿已经产生的误差。

对线性层 Y=XW，一个简化目标是：

~~~math
\min_{\hat W}
\|XW-X\hat W\|_F^2
=\min_{\hat W}
\|(W-\hat W)\|_{X^\top X}^2.
~~~

H=X^\top X 可以看作校准激活诱导的曲率近似。若某个输入方向经常出现，沿该方向的权重误差会更影响层输出；GPTQ 因此不把所有权重看作独立同等重要。实际算法会使用块级处理、Hessian 近似、阻尼和误差回填，以在离线量化时间与质量之间取舍。

把它展开成一轮计算，可以这样理解：先把代表性 token 输入该层，累积输入特征的二阶统计 H；按列取一个权重向量并将它投影到低比特网格；量化误差随后沿 H 的逆矩阵所描述的耦合方向分摊给尚未量化的列；处理完一块后再更新块间误差。阻尼项用于避免校准样本不足或相关性过强时 H 近似奇异。它因此是“先量化、再用剩余自由度补偿输出误差”，而不是逐参数找最近整数。

GPTQ 常见于 4-bit weight-only artifact，但“使用 GPTQ”仍然不完整。报告应写明 bit width、group size、是否 act-order、是否使用 double quant、权重布局、保留高精度的模块以及目标 kernel。group size 较小通常能降低局部误差，却增加 scale 元数据和访问开销：

~~~math
M_{\mathrm{group}}
\approx
\frac{N b_w}{8}
+\frac{N}{g}\frac{b_s}{8}
+M_{\mathrm{zero}}.
~~~

GPTQ 论文在 OPT-175B 的 WikiText-2 困惑度实验中报告：4-bit GPTQ 相对 FP16 的困惑度只增加 0.03，而 Round-to-Nearest 增加 2.2；论文还报告在单张 A100 上量化 OPT-175B 约需数小时。另一个端到端速度结果是 A100 上约 3.25×、A6000 上约 4.5×，但这些倍率绑定论文当时的 kernel、batch、矩阵形状和 FP16 对照实现，不能当成“GPTQ 算法本身加速 3.25×”。其主要收益来自更小权重带来的显存和带宽变化。GPTQ 的边界仍包括离线量化成本、校准分布偏移、对新 attention/MoE/量化 layout 的适配，以及最终 kernel 是否匹配；校准集未覆盖代码、数学、长上下文或多语言时，层输出误差小也不能证明业务质量。 [论文实验 §5](https://arxiv.org/abs/2210.17323)

GPTQ 的完整逐列误差补偿数例与 W4A16 执行路径放在[第十七章](17-native-int4与原生量化部署.md)主讲；本章只保留“校准输入诱导二阶误差、量化后把一部分误差分摊给剩余权重”的选型直觉，避免把算法复算和 artifact 部署讲成两遍。

## 7. AWQ

AWQ（Activation-aware Weight Quantization）从另一个角度处理 weight-only 量化：用校准样本中的激活幅度估计哪些输入通道对层输出更敏感，再搜索通道尺度或保护策略，使这些 salient channels 在低 bit 权重下受到的误差更小。

它的关键不是宣称某些参数在语义上“重要”，而是说在给定校准激活分布和线性层上，某些输入通道出现得更强、更频繁，其对应权重误差更容易放大到层输出。AWQ 搜索通道缩放系数，并用保持浮点线性层乘积不变的变换把量化难度从敏感通道重新分配到权重；这样可以保护这些通道，而不必把一小部分权重单独留成 FP16、迫使 kernel 执行混合精度分支。论文的表述是约 1% salient weights 对误差影响很大；“保护”指通过缩放降低其量化误差，不是把这 1% 原样存成高精度。 [AWQ 论文](https://arxiv.org/abs/2306.00978)

GPTQ 和 AWQ 都需要校准数据，但优化侧重点不同：GPTQ 更直接地最小化逐层输出误差并利用二阶近似做补偿，AWQ 更强调激活驱动的敏感性和硬件友好的权重处理。两者的最终速度都取决于 artifact 与 serving kernel 是否匹配，不能只根据论文名称排序。

AWQ 的失败模式包括校准样本不能代表线上分布、特殊模块没有正确转换、tensor parallel 切分破坏 scale 对齐，以及 runtime 回退到通用 kernel。AWQ 论文中的 TinyChat 还把 4-bit 权重与 kernel fusion、平台专用 weight packing 一起设计，并报告相对 Hugging Face FP16 实现超过 3× 的桌面及移动 GPU 加速；这个数字说明“量化格式 + kernel”可共同改变性能，不能单独归因于 AWQ 权重误差算法。比较时应同时记录层输出误差、任务质量、显存、TTFT、TPOT 和 kernel 路径。

AWQ 的完整等价变换与小例子也在[第十七章](17-native-int4与原生量化部署.md)展开。本章比较它与 GPTQ 的重点是：两者都利用校准信息，但 GPTQ 主要调整量化顺序中的剩余权重，AWQ 搜索激活敏感通道的缩放；它们都生成权重 artifact，是否变快还要看运行时有没有匹配的 W4A16 kernel。

如果权重量化已能保持质量，但 activation outlier 仍迫使矩阵乘使用高精度或混合精度旁路，决策对象就从“哪些权重更敏感”转为“如何让输入范围适合低精度计算”，这引出 SmoothQuant。

后续 PTQ 工作继续改变“在哪一层做文章”。SliderQuant（ICLR 2026）把浅层、深层及首末层的敏感度差异纳入逐层/层内滑窗量化；AAAC 是 ICML 2026 AdaptFM workshop 论文，它不只调整固定格点上的映射，而是为每层学习两个标量 codebook，再让每组按 activation-weighted 重建误差选表。当 codebook 选择组与 scale 组大小相同，选择位可以复用正 scale 未使用的符号位；两种分组不一致时则可能增加元数据。前者调整层间与层内的量化组织，后者调整组内可用的重建值；论文结果仍绑定其模型、位宽和任务，不能据论文名称推断目标 runtime 有兼容 kernel。 [SliderQuant，ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/b08ac1692309611b6f1adce96e96816f-Abstract-Conference.html)；[AAAC 预印本](https://arxiv.org/html/2605.08692)；[AdaptFM workshop 论文页](https://openreview.net/pdf?id=ddOlFn6d0B)

## 8. SmoothQuant

SmoothQuant 主要面向 weight-activation 量化中的 activation outlier。LLM 激活可能在少数通道出现很大的幅值；若按统一范围做 INT8，scale 会被 outlier 拉大，普通值的整数分辨率变差。

对线性层 Y=XW，可以引入对角矩阵 D：

~~~math
Y=XW=(XD^{-1})(DW).
~~~

浮点数学结果不变，但量化前的两个分布被重新分配。用 A_j 表示校准激活通道 j 的幅值，用 B_j 表示对应权重通道的幅值，可以用平滑系数 \alpha 构造一种教学级尺度：

~~~math
D_{jj}
=\frac{A_j^{\alpha}}{B_j^{1-\alpha}},
\qquad 0\le\alpha\le1.
~~~

例如取两个输入通道的校准幅值 $A=[8,1.5]$、对应权重幅值 $B=[0.5,3]$，并令 $\alpha=0.5$，则 $D=[\sqrt{8/0.5},\sqrt{1.5/3}]\approx[4,0.7071]$。变换后 activation 幅值约为 $[2,2.1213]$，weight 幅值也约为 $[2,2.1213]$，而每个通道的 activation 与 weight 乘积保持不变。这说明变换如何把量化难度重新分配；它还没有量化张量，也没有证明真实模型的精度或速度会改善。

实际实现会根据具体定义、转置方向和统计方式选择尺度，并对 A_j、B_j 加下限避免除零；公式的重点是说明 trade-off：\alpha 越大，越多尺度被转移到权重侧，activation 更容易量化，但权重侧的动态范围和量化误差可能变难。SmoothQuant 常用于 INT8 W8A8 路径，不是把任意 INT4 weight-only 都自动变好的通用开关。

它的边界包括校准 outlier 的稳定性、不同输入分布的尺度漂移、分片后 scale 的一致性和 fused kernel 的实现。验证时应分别比较变换前后的浮点等价性、量化后的层误差、端到端任务质量和真实 kernel 性能。

论文还把迁移强度 $\alpha$ 当成需要选择的变量，而不是无关紧要的默认项。在 OPT-175B 的消融中，$\alpha<0.4$ 时 activation 仍难量化，$\alpha>0.6$ 时权重侧误差变大，论文的较优区间约在 0.4—0.6。作者在 OPT-13B、OPT-30B、batch size 4 的一组 PyTorch 延迟对照中，OPT-13B、序列长 256 时报告 FP16 152.6 ms、LLM.int8 237.1 ms、SmoothQuant-O3 112.1 ms；这是特定实现的单次矩阵/阶段配置，不能外推为任意模型上的服务加速比。 [SmoothQuant 实验与消融](https://arxiv.org/abs/2211.10438)

### 8.1 激活 outlier 的三种处理路线

`LLM.int8()`、`ZeroQuant` 和 `SmoothQuant` 都试图让激活进入低精度矩阵乘，但它们改变的变量不同。理解差异比记住“它们都能做 INT8”更有用。

| 路线 | outlier 怎么处理 | 主要收益 | 代价与边界 |
| --- | --- | --- | --- |
| [LLM.int8()](https://arxiv.org/abs/2208.07339) | 大多数值走 vector-wise INT8；检测到的少数 outlier 特征维度额外走 FP16 矩阵乘，再与 INT8 路径合并 | 论文称超过 99.9% 的值仍走 INT8，并在最大 175B 模型上维持全精度表现 | 双路径、额外算子和融合要求可能抵消加速；SmoothQuant 论文的某组 OPT 延迟中它比 FP16 慢，说明质量保持与吞吐提升是两个不同结论 |
| [ZeroQuant](https://arxiv.org/abs/2206.01861) | activation 按 token 动态估计 scale，权重按组量化 | scale 跟随当前 token，减少单个跨 token 极值对整批刻度的影响 | 动态计算 scale 有运行时成本；在 SmoothQuant 论文采用的 OPT-175B 对照中，该基线未保持准确率，不能只根据小模型结果外推到大模型 |
| [SmoothQuant](https://arxiv.org/abs/2211.10438) | 利用等价通道缩放把一部分 activation 极值迁移到较易量化的权重，再让 W、A 都走 INT8 | 避免显式 FP16 outlier 矩阵分支；论文在特定 OPT/Megatron 配置中报告最高约 1.56× 延迟改善、接近 2× 显存节省 | 迁移强度、校准分布、静态/动态 scale、GEMM kernel 都影响结果；不能将论文数值当成当前硬件的保证 |

这三条路线不是同一算法的三个名字：LLM.int8()保留高精度旁路，ZeroQuant在运行时适配 token 范围，SmoothQuant在离线改写通道尺度。若目标硬件的 INT8 GEMM 很快但不能高效融合 outlier 分支，SmoothQuant可能更合适；若输入范围漂移很大，动态 scale 可能更稳但增加运行开销；若离线缩放后仍出现极端 outlier，显式旁路也可能值得测试。以上是由机制推导出的实验假设，最终需在目标 runtime 上做同负载对照。

## 9. KV Cache quantization

KV Cache 量化降低的是已经写入显存、并在每轮 decode 中反复读取的 K/V 状态。它与权重量化的生命周期不同：权重通常随 worker 常驻，KV Cache 随请求创建、增长、共享、抢占和释放。长上下文高并发时，即使权重已经是 INT4，KV 仍可能成为主要瓶颈。

设 batch 为 B、层数为 L、上下文长度为 T、KV head 数为 H_kv、每个 head 的维度为 d_h，每个 K/V 元素使用 b_q bytes，若同时保存 K 和 V，一个教学级账本是：

~~~math
M_{\mathrm{kv}}(b_q)
\approx
2BLTH_{\mathrm{kv}}d_hb_q.
~~~

用 $L=32$、$B=1$、$T=4096$、$H_{\mathrm{kv}}=8$、$d_h=128$ 估一次：BF16 每元素 $b_q=2$ bytes，则 KV payload 约为 $2×32×1×4096×8×128×2=536{,}870{,}912$ bytes，即 512 MiB 或 0.5 GiB。若改为 1-byte FP8，理想 payload 为 256 MiB；scale、分页、padding 和运行时余量尚未计入。这个账本只帮助判断 KV 是否可能成为瓶颈，FP8 的编码、scale 与真实部署路径见[第十六章](16-fp8-kv-cache.md)。

这里的 2 表示 K 和 V，b_q 是字节而不是 bit。真实实现还要加入 batch 中不同长度的 padding/分页、tensor parallel 分片、scale、block metadata、滑动窗口和 allocator 碎片。

KV 量化的执行位置也很重要：

1. 写入路径量化：prefill 或 decode 产生 K/V 后立即压缩。
2. 读取路径反量化：attention kernel 读取低精度 K/V，并用 scale 恢复近似值。
3. 混合精度：最近 token、敏感层或 K/V 的一部分保持高精度，其余使用低精度。

per-tensor、per-head、per-channel、per-token 和 per-block scale 各有取舍。粒度越细，误差通常越小，但 scale 读写、同步和 metadata 越多；粒度越粗，kernel 简单，却更容易被 outlier 影响。K 和 V 的分布、attention 对误差的敏感性可能不同，不能默认使用同一 scale。

适合场景是长上下文、高并发、cache bytes 或 cache 带宽已经在 trace 中成为瓶颈。风险包括 attention 权重变化、长序列误差积累、最近 token 与远端 token 的敏感性差异、prefix cache 复用不一致，以及量化 cache 被不兼容的 worker 恢复。

还要把 cache 的请求生命周期串起来看：prefill 写入第一批 K/V，decode 每生成一个 token 就追加状态，后续请求可能通过 prefix cache 复用已有块，调度器也可能因显存压力暂停或迁移请求。量化 scale 与 block layout 若没有随 cache 一起保存，恢复后的 attention 就可能读错解释；若不同 worker 的 dtype 或格式合同不一致，最安全的结果可能是拒绝复用并重新计算。上线验证因此要覆盖写入、追加、复用、迁移和回收，而不只比较一段静态张量的量化误差。

### 9.1 KIVI：为什么 K 和 V 使用不同量化轴

K 和 V 虽然成对缓存，进入 attention 的方式不同。对单个 query，K 先参与 $QK^\top$ 产生注意力分数；这些分数经过 softmax 后，再乘 V 得到输出。因此同一套 scale 粒度不一定适合两者。

KIVI 在其分析的模型中观察到：K cache 的少数固定 feature channel 常出现较大 outlier；若每个 token 把所有 channel 共用一个 scale，某个 outlier channel 会把同一 token 内普通 channel 的可用刻度挤窄。KIVI 因此对 K 按 channel 量化，让每个 channel 的刻度分开估计。V 没有同样明显的固定 channel outlier；它被 attention 权重加权求和，按 token 量化能把某个 token 的误差限制在该 token 的向量上，避免该 token 的极值把其它 token 的 scale 拉宽。论文在 Llama-2-13B 上报告，K 按 token 量化时的 attention-score 相对误差为 47.00，按 channel 为 9.60；V 按 token 时的输出相对误差为 3.55，按 channel 为 49.89。这些是论文定义的相对误差统计，不是百分比或跨模型结论。 [KIVI §3.2](https://arxiv.org/abs/2402.02750)

K 的按 channel 量化需要跨多个 token 共同估计 scale，而生成中的 cache 是逐 token 追加的。KIVI 用“已成组部分 + 高精度 residual”解决这个张力；V 也保留最近的一段高精度窗口，把更旧 token 按 token 量化并追加。以教学用的分组跨度 4、recent window 4、prefill 已有 6 个 token 为例：K 的前 4 个 token 可以成组量化，后 2 个暂存 BF16；再生成 2 个 token 后，4 个 residual 一起量化。V 则先保留最近 4 个 token 为高精度，第 5 个新 token 到来时，把最旧的窗口 token 转成按 token 量化表示。这里的 4 是为了手推状态变化而设的假设参数，不是论文或 runtime 的默认配置。实际实现的分组维度、残差长度和 page 布局必须与 attention kernel 对齐。

论文报告 KIVI 在 Llama、Falcon、Mistral 等模型上的 2-bit cache 路线，将包含权重在内的峰值显存降至约 2.6 分之一，最多支持 4× batch，并在论文真实 workload 上报告 2.35—3.47× 吞吐。提升吞吐的中间原因主要是更小的 cache 允许更大 batch，不代表 2-bit 运算本身必然更快。论文还指出，高精度 recent window 对数学等难生成任务很重要；把每个 cache token 都直接压到 2-bit 的简化版本会损失质量。scale、zero point、分组尾部、残差窗口以及融合反量化都要计入成本。 [KIVI 论文实验](https://arxiv.org/abs/2402.02750)

### 9.2 精度格式、活跃状态和冷数据不是同一层

看到低精度名称时，先确定它描述的是数值编码、活跃 GPU 状态、冷数据表示，还是已打包的权重 artifact。它们影响的内存位置和执行路径不同：

| 对象/路线 | 保存与读取位置 | 完整主讲 |
| --- | --- | --- |
| FP4、MXFP4、NVFP4 | 权重或 activation payload 与 scale；是否进入低精度矩阵 kernel 取决于实现 | [第十五章](15-fp4-mxfp4-nvfp4.md) |
| FP8 或低 bit 活跃 KV | GPU 中按请求增长；attention 路径读取这些状态 | [第十六章](16-fp8-kv-cache.md) |
| Native INT4 权重 | artifact 的量化权重、scale、packing 与兼容 kernel | [第十七章](17-native-int4与原生量化部署.md) |
| Cold-page KV 压缩 | 仅在 KV Page 移到 Host/Disk 冷层时改变存储表示；回到 GPU 后恢复为 runtime KV dtype | [TensorRT-LLM 文档](https://nvidia.github.io/TensorRT-LLM/features/kv-cache-compression.html) 与[第十六章](16-fp8-kv-cache.md) |
| KV token retention | 减少保留的历史 token 数，而不是降低每个 token 的数值位宽 | [TensorRT-LLM 文档](https://nvidia.github.io/TensorRT-LLM/features/kv-cache-compression.html) 与[第十六章](16-fp8-kv-cache.md) |

所以“4-bit”不表示每个参数连同 scale 和 metadata 恰好只占 4 bit；“KV 压缩”也可能是在活跃 cache 量化、冷 Page 编码和 token retention 之间作选择。TensorRT-LLM 当前文档把 NVFP4 cold-page quantization 与 TriAttention 分列：前者压缩迁移到 Host/Disk 的 KV Page，后者在生成中选留部分 KV token 并压紧 cache；文档说明 TriAttention 需要离线校准文件。该页面是随版本变化的框架能力说明（访问于 2026-11-02），不能外推为所有 runtime 的通用 cache 行为。FP4 格式和 scale 数例见[第十五章](15-fp4-mxfp4-nvfp4.md)，FP8 KV 的 scale、allocator 和 active cache 路径见[第十六章](16-fp8-kv-cache.md)，native INT4 权重的打包与 kernel 兼容见[第十七章](17-native-int4与原生量化部署.md)。

量化评测至少切分短/长上下文、普通问答、数学、代码、工具参数、reasoning effort 档位、取消/抢占恢复和 speculative decoding 接受率。若量化 cache 改变了 token 接受率或格式成功率，应把这些变化归因到 cache 误差和解码路径，而不是只记录一个总吞吐。

### 9.3 TurboQuant、InnerQ 与“论文量化率”到“服务吞吐”的落差

TurboQuant 把 KV Cache 看成向量内积近似问题：先对向量做随机正交变换，让坐标分布更集中，再逐坐标做标量量化；论文还提出对第一步的残差加一位 QJL 校正，使内积估计无偏。这个目标针对 K 与 query 的内积失真，和只最小化元素 MSE、或直接衡量最终任务正确率不是同一个指标。论文报告在其 KV Cache 测试中，约 3.5 bit/channel 达到绝对质量中性，2.5 bit/channel 只有轻微退化，并给出接近理论失真下界的分析。 [TurboQuant ICLR 2026 论文](https://arxiv.org/abs/2504.19874)

论文的向量计算收益不能直接当成端到端 serving 收益。Google Research 的介绍中，“4-bit 比 32-bit key 快至 8×”测量的是 H100 上 attention logits 的计算，不是同一服务的 P99、TPOT 或每秒成功请求数。 [Google Research 对实验的说明](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/)

一个有价值的工程对照来自 vLLM 团队 2026 年的评测：固定 vLLM 0.20.2 commit `6ec9bbec3`，在 2×H100 的 Qwen3-30B-A3B 与 4×H100 的 Llama-3.3-70B 上测 retrieval、AIME25/GPQA/MATH500/LiveCodeBench、延迟、离线吞吐和在线服务。该评测的 TurboQuant preset 与论文的理论向量结果不是同一指标；例如 Qwen3-30B-A3B-Instruct 在最长 256k 的 MRCR 检索评测中，BF16 的 AUC 为 45.8，最激进的 `3bit-nc` 为 31.2，约下降 31.9%（相对值）；这是多个长度桶的聚合检索指标，不是通用准确率。Qwen reasoning/coding 上激进 3-bit preset 的准确率最多下降约 20 个百分点；延迟开销约 10%—68%，离线吞吐约为 BF16 的 66%—80%。但当 Llama 70B 的 BF16 cache 在 burst load 下饱和、P99 TTFT 接近 17 秒时，压缩 cache 可让请求留在 GPU 而不是排队，把 TTFT 降到 3.5 秒以内；同一评测中的 FP8 约 1.3 秒。这里的结论不是某格式普遍更快，而是低 bit cache 可能用 TPOT/吞吐换容量，并在内存成为准入瓶颈时改善 TTFT。数字仅属于该 runtime revision、GPU、模型和 workload。 [vLLM 评测与配置](https://vllm.ai/blog/2026-05-11-turboquant)

InnerQ 是 2026 年公开的 KV 量化预印本，处理的是另一种瓶颈：低 bit cache 虽然减少读入字节，但若 scale 的分组方向不顺着 decode 的向量—矩阵乘，反量化与 scale 访问本身可能拖慢 kernel。InnerQ 把分组放在计算的 inner dimension 以复用 scale，并用 fused dequantization-GEMV；质量侧还组合 K 的逐 channel normalization、按组选择对称/非对称量化，以及 sink/recent 高精度窗口。作者报告的 Jetson Xavier NX、batch 1 单层 kernel 测量平均比 FP16 cache 快 2.7×，该结果是固定序列长度下的 kernel microbenchmark，不是完整模型的端到端服务加速或吞吐结论；论文不同位置对所测 Llama 8B 版本的标注不一致，因此这里不把型号写成确定值。 [InnerQ 预印本](https://arxiv.org/abs/2602.23200)

部署上还要分清“active cache quantization”和“cold-page compression”。active quantization 让 GPU 上的 KV cache 以 FP8/NVFP4 等低精度保存，并由 forward/attention 路径读取；TensorRT-LLM 的 cold-page NVFP4 则只压缩迁移到 Host/Disk 的冷 Page，Page 回到 GPU 后先解码到模型的 runtime KV dtype。后者节省冷层容量和传输字节，但不会直接把仍驻留 GPU 的活跃 cache 变小，也不要求 attention kernel 读取 NVFP4。TensorRT-LLM 文档当前列出的 cold-page 支持条件包括 PyTorch backend、KVCM V2、NVIDIA SM100/SM103/SM107 GPU，以及 native C++ KVCM V2 backend 和非零 Host 或 Disk cache；这些是特定框架功能的硬件/运行配置条件，不是 NVFP4 格式本身的通用要求。 [TensorRT-LLM KV Cache Compression](https://nvidia.github.io/TensorRT-LLM/features/kv-cache-compression.html)

## 10. 校准数据

量化离不开校准数据。校准数据不是用来证明模型质量的测试集，而是用来估计 scale、zero point、激活分布、敏感通道和误差补偿方向的观察样本。它不需要覆盖所有线上请求，却必须覆盖会改变数值分布的主要因素。

一个可解释的校准集应记录：

1. 语言、领域和 prompt/chat template 版本。
2. 输入长度、输出长度和是否命中 prefix cache。
3. 普通问答、代码、数学、长上下文、结构化输出和工具调用比例。
4. 多轮对话、reasoning effort 和多模态占位符等特殊路径。
5. 样本时间、过滤规则、去重规则和是否包含评估集。

校准和评估必须分开。可以从同一线上分布抽样，但不能把用来选择 scale 的答案再用于报告量化质量，否则会把校准过拟合误认为泛化能力。对于激活量化，校准时还应观察 per-layer/per-channel 的 min、max、分位数和 outlier 频率；单个全局 max 往往对长尾过于敏感，盲目裁剪又会产生饱和。

校准数据还必须和量化对象匹配。Weight PTQ 通常需要让模型在真实 prompt/template 下产生层输入激活；KV Cache 方法则要覆盖 prefill 和生成过程中的不同长度、位置与请求状态，否则只统计 prompt 可能没有观察到 decode 期间 cache 的分布。TurboQuant 等数据无关方法不需要拟合业务 scale，但仍需要任务评估证明误差在目标数据上可接受。一个可复核的校准 manifest 至少绑定基础权重 revision、tokenizer/template、样本来源与 hash、采样规则、最大长度、量化工具版本、量化目标模块、bit/group/scale 轴和导出 artifact hash。

如果校准分布和线上分布差异很大，量化后线上质量可能明显下降。上线后仍要做 drift 监控：语言比例、长度桶、工具 schema、激活范围和量化饱和率发生变化时，应重新抽样和回归，而不是默认旧 scale 永远有效。

例如，一个知识助手可先按短问答、长文档检索、代码/数学和 JSON/工具调用分桶，再检查各桶的语言、输入长度、生成长度与模板版本。若线上 80% 是短问答、15% 是长文档、5% 是结构化调用，只按流量随机抽样可能几乎看不到极端长请求；校准时可以额外保留少量长文档和工具样本，使 scale 对这些路径可观察，同时记录这种有意过采样。校准集的比例不必复制线上权重，但必须公开采样规则，评估集则应按目标流量另行抽取，避免把过采样后的分布误当成服务总体质量。

一个可审计的校准流程会保存原始样本 ID 或合成样本生成规则、脱敏与去重策略、tokenizer/template revision、最大上下文长度，以及每个候选量化方案实际读取了哪些 token。对 weight PTQ，应明确模型是否进入生成阶段、层输入从哪些位置采样；对 KV PTQ，应区分 prefill 写入和 decode 追加的 cache 状态。然后按层记录 min/max、分位数、饱和率或尺度变化，并抽查最敏感层是否由少数异常样本决定。若改了模板、上下文长度或模型 revision，就应检查旧统计能否继续代表新输入，不能只因为工具能读旧 scale 就自动复用。

## 11. 量化评估

量化评估应把高精度 reference 与候选 artifact、runtime、硬件和 workload 固定下来。至少比较：

1. 权重、KV Cache、workspace 和峰值显存。
2. TTFT、TPOT/ITL、E2E、吞吐、并发和 P95/P99。
3. 普通问答、事实性、数学、代码、长上下文和多语言任务。
4. JSON/schema、tool call、stop、取消和 reasoning channel 的协议成功率。
5. 量化前后 token 对齐、logits 差异、finish reason 和错误类型。
6. OOM、kernel fallback、抢占、cache 量化恢复和版本升级风险。
7. 单位成功任务成本，而不是单位生成 token 成本。

评估还要把“平均表现”拆成可解释的失败桶。设一组纯教学用的分桶任务中，短问答占 80%、长文档占 15%、JSON/工具占 5%；高精度 reference 的成功率分别为 98%、95%、96%，加权总成功率为 $0.8×0.98+0.15×0.95+0.05×0.96=97.45\%$。候选量化若保持短问答 98%、把长文档降到 88%、结构化任务仍为 96%，总体是 96.4%，只低 1.05 个百分点，但长文档单桶已经下降 7 个百分点。若业务把文档引用设为硬门槛，总体均值不能抵消该桶失败；应回看该桶的长度、激活饱和层和 cache 状态，再决定换校准、提高敏感层精度或拒绝发布。以上数字是合成例子，不是论文或服务测量。

质量对照应尽量按同一条请求成对回放：固定模型和 tokenizer revision、提示模板、采样参数、输入样本与 runtime，再分别保存 reference/candidate 的 token、finish reason、schema 校验、工具参数和错误类别。对随机采样任务，要固定 seed 或报告采样方差；对有限样本的成功率，应保留每桶的样本数与置信区间，避免把几条样本的波动写成稳定退化。数值差异、任务正确性、协议合法性和服务性能是不同证据层，发生冲突时先定位失败路径，再按预先声明的硬约束决策，而不是挑一个最有利的总体指标。

实验启动前还要写下基线、候选 revision、输入集 hash、采样配置、预期改善的瓶颈和停止条件。例：若当前拒绝请求主要由 active KV 不足引起，就把可接纳并发、OOM/拒绝率和长上下文质量设为主要观察量；若只报告平均 tokens/s，压缩后即使多接入请求仍因 KV 质量退化而失败，也可能被误判为成功。指标选择必须跟随问题，而不是先拿一套方便采集的数据再倒推结论。

离线质量过门槛后，还要在影子流量或低风险灰度中观察真实长度和并发分布；用低风险请求验证缓存重建、取消、抢占与回滚是否保持正确。若流量分布或量化饱和率偏离校准假设，就先暂停扩量、收集失败桶，再决定重校准或恢复高精度 artifact。质量门槛不是发布后一次性打勾，而是随输入分布、runtime 和硬件 revision 重新确认的条件。

可以把一轮评估记录成证据向量：

~~~math
E_{\mathrm{quant}}
=
(E_{\mathrm{memory}},
E_{\mathrm{latency}},
E_{\mathrm{throughput}},
E_{\mathrm{quality}},
E_{\mathrm{format}},
E_{\mathrm{operations}}).
~~~

各项量纲不同，不应未经归一化直接相加。发布决策至少要显式写出硬约束，例如：

~~~math
P99(\mathrm{TTFT})\le\tau_{\mathrm{TTFT}},
\quad
P99(\mathrm{TPOT})\le\tau_{\mathrm{TPOT}},
\quad
\Delta\mathrm{Quality}\ge-\epsilon,
\quad
\mathrm{SchemaPass}\ge\rho.
~~~

其中 \epsilon 是业务可接受的质量下降幅度，\rho 是结构化输出成功率目标。安全拒答、权限错误和工具副作用不能用吞吐或平均质量抵消；一个普通聊天 benchmark 没有退化，不代表关键业务路径可以发布。

跨论文比较同样要固定对照口径。2025 年首版、2026 年 10 月更新至 arXiv v4 并标注已被 Pattern Recognition 接收的统一条件评估，把 PTQ 方法拆成“量化前变换”和“误差补偿”两步，并分别分析旋转/缩放、校准、对称性、分组粒度和 scale 精度；它发现更细粒度通常改善质量但增加存储，NVFP4/MXFP4 的 scale 形式和精度会明显影响结果，而在 INT4 上有用的旋转并不一定迁移到 FP4。这个结论提醒读者：把论文中全部 trick 打包成单一方法名，再比较最终 benchmark 分数，很难知道收益来自哪一步。它是该论文模型与配置下的研究结果，不是任何新格式的普遍规律。 [统一条件评估 arXiv v4](https://arxiv.org/abs/2507.17417v4)

## 12. Distillation

若改变数值表示仍不能满足容量、任务质量或运行成本目标，可以把模型压缩路线扩展到“改变学生模型”或“减少冗余权重”。以下两节是本章的支持性分支：蒸馏改变学生模型所承担的函数与参数规模，剪枝/稀疏化改变权重结构；这里聚焦它们怎样改变 serving 账本和部署验证。软目标、学生模型与结构改造的完整入口见[第二十一册第 23 章](../../book-21-transformer-architecture-evolution/chapters/23-小模型边缘模型与高效Transformer.md)，学生自身状态分布上的 on-policy 蒸馏见[第五册第十七章](../../book-05-llm-training/chapters/17-on-policy-distillation.md)。

蒸馏和量化解决的是不同层次的问题。量化尽量保持模型函数不变，只改变数值表示；蒸馏则训练一个 student 去逼近 teacher 的输出分布、行为或任务轨迹，可能同时改变模型结构和参数量。

从服务账本看，蒸馏的关键价值是把一部分能力迁到更小的 student，而不是让同一组权重占用更少 bit。假设 teacher 有 70B 参数、student 有 7B 参数，两者都按 FP16 原始 payload 估算，权重分别约为 130.4 GiB 和 13.04 GiB；这个十倍差异说明小模型可能改变单卡装载与 decode 的权重读取量，但不意味着它保留了 teacher 的全部能力。两者的 KV Cache 也受层数、KV heads 和上下文长度影响，不能单靠参数比推断并发倍率。服务团队应先确定哪些任务可迁移、哪些能力必须保留，再用蒸馏去训练候选模型。

因此蒸馏适合“模型结构和推理成本都值得改变、且能承担训练与质量回归”的场景；若只需快速降低已有 checkpoint 的显存，先试 PTQ 更直接。teacher 生成数据、logit 蒸馏和轨迹蒸馏也会保留不同信息：没有 logits 时不能声称做了分布蒸馏，工具轨迹还须验证权限、环境和副作用。student 上线前要用与 teacher 相同的业务分桶测质量、延迟、KV 峰值和单位成功成本，并把 teacher/student revision 与样本清单绑定，避免训练过程的改进被误认成部署 kernel 的收益。

最基础的 logit 蒸馏使用温度 T 平滑 teacher 和 student 的分布：

~~~math
\mathcal{L}_{\mathrm{KD}}
=
T^2\,
\mathrm{KL}\left(
p_T^{\mathrm{teacher}}(\cdot\mid x)
\;\|\;
p_T^{\mathrm{student}}(\cdot\mid x)
\right),
\qquad
p_T=\mathrm{softmax}(z/T).
~~~

用温度 $T=1$ 的三 token 分布做一次可复算的对照：teacher 为 $p=[0.7,0.2,0.1]$，student 为 $q=[0.6,0.3,0.1]$，则 $\mathrm{KL}(p\|q)=0.7\ln(0.7/0.6)+0.2\ln(0.2/0.3)+0.1\ln(1)\approx0.0268$ nats；因为 $T^2=1$，这也是该例的 KD loss。它说明蒸馏会比较完整分布，而不是只要求 student 复制 teacher 的最大概率 token；训练信号仍不保证 student 在未覆盖任务上与 teacher 等价。

T 越高，分布中的“次优 token”相对信息越明显；T^2 是常见的梯度尺度补偿约定。实际蒸馏还可能混合 hard label、SFT loss、偏好损失、过程轨迹或 verifier：

~~~math
\mathcal{L}
=\lambda_{\mathrm{hard}}\mathcal{L}_{\mathrm{hard}}
+\lambda_{\mathrm{KD}}\mathcal{L}_{\mathrm{KD}}
+\lambda_{\mathrm{task}}\mathcal{L}_{\mathrm{task}}.
~~~

三种常见路线的风险不同：

1. Teacher 生成数据：扩充 instruction/代码/工具样本，但 teacher 的事实错误、偏见和拒答模式会进入数据。
2. Logit/分布蒸馏：保留更丰富的 token 级信号，但需要 teacher logits、tokenizer 对齐和较高调用成本。
3. 轨迹或结果蒸馏：可以迁移推理/Agent 行为，但长轨迹中的工具权限、环境状态和副作用不能只当作文本标签。

student 的容量上限决定了它不可能在所有任务上等价于 teacher。评估应拆成知识、推理过程、工具交付、延迟和成本，并保留 teacher 的版本、采样配置、过滤规则和失败样本。蒸馏后的模型还要重新做安全、污染和分布外测试，不能把“训练数据来自强模型”当作正确性证明。

这三条路线也不是同一种训练信号的不同叫法：教师生成数据是在固定示范上做监督；logit 蒸馏要比较 token 分布，通常需要学生与教师词表、token 对齐；on-policy 蒸馏让教师对学生实际走到的状态提供信号，会多出 rollout、教师调用和策略分布变化的成本。反向 KL、学生状态覆盖、verifier 和训练稳定性已在[第五册第十七章](../../book-05-llm-training/chapters/17-on-policy-distillation.md)展开，本章只保留它们作为压缩路线的选型入口。

蒸馏后的 student 也可能仍需量化；这时要把“训练造成的能力差异”和“低精度造成的额外误差”分开评估。先测高精度 student，再测其量化版本，分别对比 teacher 与 student 的质量、显存和延迟，才能知道收益是否来自模型缩小或数值表示。

## 13. 剪枝和稀疏化

剪枝可以去掉权重、通道、attention head、层或专家；稀疏化则让参数矩阵中一部分值为零。稀疏率可以写成：

~~~math
\mathrm{Sparsity}
=1-\frac{N_{\mathrm{nonzero}}}{N_{\mathrm{total}}}.
~~~

例如一个 10 个权重的 toy 矩阵若有 6 个值被置零，稀疏率为 $1-4/10=60\%$。这个比例本身不说明文件减少 60%，也不说明 dense GEMM 会跳过这些零值；还要考虑索引/掩码、结构模式和实际 kernel。

但稀疏率不是速度。非结构化稀疏把零散权重置零，理论 FLOPs 下降，通用 dense GEMM 可能仍按稠密矩阵计算；结构化剪枝直接删除通道或层，速度更容易体现，却会改变张量形状、残差连接、并行分片和模型容量；N:M 稀疏在固定块内保留 N 个非零值，只有硬件和 kernel 支持该模式时才可能获得实际收益。

剪枝还会改变 KV Cache 和调度画像。删除层会改变每个 token 的 KV 层数，删除 head 可能影响 GQA/MHA 布局，删除 MoE expert 可能改变路由负载和容量。部署 artifact 必须重新导出和校验，不能只把零写进 checkpoint 就宣称服务变快。

SparseGPT 给出了大模型 one-shot 剪枝的代表路线：用校准激活形成近似二阶统计，逐块选择要置零的权重，并把误差补偿到保留权重；它不是按绝对值排序后直接删掉。论文在 OPT-175B、BLOOM-176B 上报告，在无需 retraining 的前提下可做到 60% 非结构化稀疏且困惑度增加很小，量化时间在 4.5 小时以内；还研究 2:4 与 4:8 半结构化模式，并说明可与权重量化组合。这里有两个限制：困惑度和 zero-shot 结果不等于工具/代码任务质量；非结构化零值若没有稀疏 kernel，普通 GEMM 仍可能按 dense 路径计算。 [SparseGPT 论文](https://arxiv.org/abs/2301.00774)

一个完整实验至少比较稠密 baseline、稀疏率、实际 kernel 时间、显存带宽、任务质量、长上下文和结构化输出。若没有匹配的 sparse kernel，剪枝可能只有模型文件变小的收益；如果目标是边缘存储而不是 GPU 计算，它仍可能有价值，但要把目标说清楚。

对存储也要区分“含零的稠密矩阵”和“编码后的稀疏 artifact”。前者继续为零值保留浮点槽位，文件大小可能毫无变化；后者要保存非零值及位置编码，矩阵越小或稀疏块越短，索引占比越可能抵消收益。剪枝算法选择目标时应连同压缩格式、加载器和 kernel 一起确定。若只为减少传输，可以在导出或归档层压缩稀疏权重；若要降低 GPU 计算，则必须证明运行时确实按结构跳过乘法，并测带有 scale、mask 和索引的完整执行路径。

要从稀疏率走到可部署收益，还需经过“产生零值—导出稀疏表示—加载匹配 kernel—测量真实路径”四步。若一个 4×4 权重块采用 2:4 模式，每组四个值保留两个非零值，理论上可以把乘法数减半；但格式还要说明保留位置如何编码，kernel 必须读取这些索引并跳过零值。若仅把两个位置写成数值 0、仍以普通 FP16 稠密矩阵保存，16 个元素还是占 32 bytes，计算也可能照常执行。因此非结构化 60% 稀疏并不等于文件或延迟减少 60%。

结构化剪枝的验证点不同：删除通道、head 或层会改变张量形状与残差连接，必须重新导出模型并确认并行切片、KV 布局和 runtime 对新结构的支持。N:M 稀疏则必须确认目标 GPU 的稀疏指令、对齐要求和训练/剪枝格式一致。评估时将模型压缩前后放到相同输入上做分桶质量回归，再用 profiler 确认稀疏 kernel 确实运行；若 kernel 退回 dense 路径，就把目标改为文件/传输收益或停止该候选。稀疏路线由此与量化共享同一发布门禁，但需要不同的 artifact 与执行证据。

## 14. 量化选型建议

| 目标 | 推荐方向 |
| --- | --- |
| 快速压缩部署 | PTQ weight-only |
| 稳健质量、低实现风险 | FP8 或 INT8；是否优于 BF16 取决于目标硬件的 native kernel |
| 显存极紧 | INT4 GPTQ/AWQ |
| decode 权重带宽受限 | GPTQ/AWQ 等 W4A16，优先确认 packed-weight kernel 与实际 batch |
| prefill/计算吞吐受限 | 测 W8A8、FP8 或目标硬件支持的 FP4 路径；activation outlier 再比较 SmoothQuant、动态 scale 或 QAT |
| 长上下文 KV 容量受限 | 先测当前 runtime 的 FP8 KV；仍不足再评估 KIVI/TurboQuant/更低 bit，并单独回归数学、代码与长上下文 |
| 冷 KV 在主存/磁盘容量或传输受限 | 测 cold-page compression；不要把它记成 active GPU KV 预算减少 |
| 稀疏计算优化 | 只选目标硬件和 kernel 支持的结构化模式；非结构化稀疏先以存储或传输收益衡量 |
| 边缘模型存储 | 选和设备后端匹配的 GGUF/llama.cpp 路线，并比较实际 decode kernel，而非文件名上的 Q4/Q5 |

这张表只是实验起点，不是自动选择器。选量化之前先用 profiler 与显存水位定位瓶颈；然后只改对应的权重、激活、cache 或稀疏路径。所有候选都要和 FP16/BF16 reference 在同一基础权重、tokenizer/template、输入输出分布、runtime revision、GPU 和采样设置下成对回放。

观察信号要能指出压缩对象对应的账本。如果模型加载阶段就 OOM，先核对权重 payload、scale 和常驻 buffer；如果短上下文正常、请求长度上升时可准入的活动请求数迅速下降，再看 KV 占用和 page 水位；如果内存仍有余量但 prefill 或 decode 计算时间占主导，才把 activation 格式、矩阵指令或稀疏 kernel 放进候选。前两类问题可能只改善可装载模型数或并发，第三类才可能改变计算时延。目标也要分别写成“峰值低于上限”“长文档质量达标”或“TPOT 至少改善多少”，不能把显存减少自动换算成速度收益。

用一组纯教学假设说明先过硬门槛：任务成功率至少 97%，峰值显存不超过 20 GiB。FP16 reference 的成功率为 98%、峰值 22 GiB、TPOT 为 180 ms；候选 A 为 97.5%、18 GiB、185 ms，候选 B 为 97.8%、19 GiB、170 ms。A 和 B 都过质量与容量门槛，但 A 更省显存、B 的 TPOT 更低，两者互不支配，应按当前目标选取；候选 C 即使有 96.8% 成功率、17 GiB 和 160 ms，也因质量门槛失败而直接淘汰。数字是合成例子，不是论文或 runtime 测量。它说明评估要先筛掉不合格候选，再在剩余的质量、内存和延迟之间比较。

实际决策可以按三步收窄。先把峰值显存拆成权重、active KV、workspace 和碎片，并用 trace 判断瓶颈发生在加载、prefill 还是 decode；再选只会改变这本账的表示。若权重常驻压住模型装载，先试 weight-only；若活跃请求数随上下文增长而下降，先试 KV 路线；若矩阵计算本身成为瓶颈，才把 activation 格式和硬件指令纳入候选。冷页压缩只有在 Host/Disk 容量或迁移流量重要时才对应目标，剪枝只有匹配稀疏执行路径时才以计算速度为验收项。最后把“必须保持的质量和协议”写成硬门槛，再比较剩余候选的速度、容量和成本。

这个顺序能避免同时改变权重、激活和 KV 后无法定位收益来源。也能防止把不同实验条件下的论文倍率直接排序：方法论文回答算法在作者设置下怎样工作，runtime 文档说明某接口可能接受什么配置，目标回放才回答它是否适合当前模型和流量。低位宽名称相同，也可能因为 scale 轴、pack 格式和 kernel 不同而形成不同 artifact；候选进入评估前应先过可加载、模块覆盖、分片一致和无 fallback 这几道技术检查。

### 14.1 从方法限制设计下一轮实验

读完代表方法后，面试和方案评审常会追问：“已知它解决什么问题，接下来怎样改？”可以从失败原因反推实验，而不是笼统地说“扩大数据、继续优化”。下表的下一步是依据方法机制推导出的实验假设，不是论文已经证明的普遍改进；只有完成同设置消融，才能把它升级为结论。

把改进建议写成可证伪的假设时，要同时写出观察量和反例。例如“更小 group 会改善质量”还不完整；可改成“固定基础权重、校准集、kernel 和输入桶，只把 GPTQ group size 从 128 改为 64，若长文档任务成功率提高且 scale 访存没有让 TPOT 超出门槛，则保留该候选”。若质量没有变化、只在某一个桶变化，或 runtime kernel 被换成 fallback，实验就没有支持原先的泛化说法。表中的验证项应服务于这种对照，而不是成为离线报告中的装饰指标。

每轮只允许把实测结果归因到实际改变的变量；根据机制推导出的下一步仍是待检验假设，需保留为对照实验计划，不能回写成方法已经证明的收益。

| InnerQ | cache 分组轴与 decode GEMV 的数据复用不匹配会增加 scale 读取与反量化开销 | 固定 cache bit budget、窗口大小和输入长度，对照 KIVI/TurboQuant 与 FP16，并测层 kernel 与完整服务 | 论文报告的 Jetson 单层 batch 1 kernel 结果不等于端到端收益；目标后端要另行测 kernel、TTFT、TPOT、容量和任务质量。 [InnerQ 预印本](https://arxiv.org/abs/2602.23200) |
| SparseGPT | 非结构化剪枝能降低非零权重数，但 dense kernel 未必跳过零值 | 若目标 GPU 和 runtime 支持，比较 2:4 半结构化模式及匹配稀疏 kernel；否则只把文件/传输收益作为目标 | 对照真实稀疏 kernel 延迟、显存和任务质量；非零率本身不是加速证据。 [SparseGPT](https://arxiv.org/abs/2301.00774) |
| 知识蒸馏 | 学生容量有限，教师样本质量和训练分布可能一起带入偏差 | 按目标任务补高质量覆盖，并比较离线轨迹与学生 on-policy 状态上的教师反馈；为高风险输出增加独立 verifier | 不只看训练 loss：固定 teacher/student revision，在独立任务集测能力保留、失败类型、延迟和成本；on-policy 机制见[第五册第十七章](../../book-05-llm-training/chapters/17-on-policy-distillation.md)。 |

实验应从可归因的最小改动开始：先保存高精度基线和一份配置 manifest，只改变一种量化算法或一个 group size；每次记录导出时间、文件/scale 字节、加载路径、实际 kernel、峰值显存和分桶质量。若更细 group 降低了层误差，却增加 scale 访存并使 TPOT 变差，下一步应测试目标 kernel 能否融合读取，而不是直接把 group size 继续缩小。以 7B 个 INT4 权重和 16-bit scale 粗算，group size 128 约有 5,469 万个 scale，占约 0.10 GiB；改成 64 后 scale 数和这一项开销约翻倍。这个估算忽略对齐与特殊模块，但足以提示“误差改善”也要计入元数据账本。

把这笔账展开：7,000,000,000 个权重除以 128，约有 54,687,500 个 scale；每个 scale 假设 2 bytes，约为 109,375,000 bytes，即 104.3 MiB 或 0.102 GiB。group size 改为 64 后，scale 约为 208.6 MiB，增加约 104.3 MiB。若一个候选原本只比内存准入线多出 150 MiB，这种改变会吃掉大部分余量，零点、对齐和二级 scale 还可能继续增加文件与 workspace 成本。这里的数字只按 7B、INT4、每组单个 FP16 scale 估算；真实 artifact 必须从布局和导出文件核对，不能把“参数数除 group size”直接当作完整 metadata 大小。

这也说明 group size 的比较至少要同时回答三个问题：层输出/任务质量是否改善、scale 的额外字节和访问是否可接受、目标 kernel 是否能以这种布局执行。若只有 MSE 下降而业务分桶不变，且内存与时延都更差，就没有理由因为误差数字更小而保留候选；若质量持平但容量越过一个明确准入门槛，则它仍可能有价值，但收益应登记为容量而非质量或速度。采用同一基线的质量、存储和运行轨迹，才能识别这几种结果。

每轮实验都应事先写出失败后会采取的动作：质量只在长上下文下降，就检查校准位置、cache dtype 和最近 token 策略；JSON 或工具参数失败，就查看对应层误差及协议样本，不用普通问答平均分替代；质量达标而速度不变，就用 profiler 确认是否 kernel fallback 或瓶颈不在权重带宽；内存下降但并发未增加，就拆查 KV、workspace 与 admission budget。完整的 24 GiB 长上下文决策示例见下一节；它展示怎样把这些分桶证据转为发布门槛。

每轮记录应保留 baseline 与候选的 checkpoint/revision、量化工具版本、校准样本和去重规则、被量化模块、bit/group/scale 轴、导出 hash、runtime/GPU、输入长度桶及采样参数。候选有任何一项不一致，都不能把差异只归因于 group size。论文指标只回答作者配置下的研究问题，runtime 文档只回答公开支持条件；本地回放才回答当前 workload 是否合格。若不同研究的精度集、长度、硬件或 serving 负载不同，就分别比较各自的质量—存储—延迟边界，不把数值拼成单一排行榜。门槛还要写清 P50/P95/P99 所用的测量窗口、请求分母和流量组合；只报一次短压测均值无法判断 burst 下的尾延迟。若候选结果贴近质量底线，应扩大对应桶样本或重复回放，再作 go/no-go 判断。

## 15. 最小 Python demo：量化误差和存储审计

下面的 0 依赖 demo 演示 INT4 对称量化、group-wise INT4、activation INT8 非对称量化、SmoothQuant 的 outlier 平滑直觉，以及 7B 权重的粗略存储估算。

> 状态：静态审阅，未运行（2026-11-02）。仅依赖 Python 标准库；下方是手算预期输出，未执行。

所有输入都是可读的一维小数组：8 个权重、4 个元素一组、6 个 activation，以及一个用于数量级估算的 7B 参数数值。量化函数返回 scale、整数值、反量化值和 MSE，读者可把它们与 §2.4、§4 的手算过程逐步比对。若要自行查看输出，可将代码块另存为 Python 3 脚本后运行；脚本只使用标准库，不需要模型权重、GPU、PyTorch 或 NumPy。

```python
import math


def symmetric_quantize(values, bits):
    if not isinstance(values, (list, tuple)) or not values:
        raise ValueError("values must be non-empty and bits must be >= 2")
    if any(isinstance(x, bool) or not isinstance(x, (int, float)) or not math.isfinite(x) for x in values):
        raise ValueError("values must contain finite numbers")
    if isinstance(bits, bool) or not isinstance(bits, int) or bits < 2:
        raise ValueError("bits must be an integer >= 2")
    qmax = 2 ** (bits - 1) - 1
    qmin = -qmax
    max_abs = max(abs(x) for x in values)
    scale = max_abs / qmax if max_abs else 1.0
    q = [max(qmin, min(qmax, round(x / scale))) for x in values]
    deq = [scale * x for x in q]
    mse = sum((a - b) ** 2 for a, b in zip(values, deq)) / len(values)
    return scale, q, deq, mse


def groupwise_quantize(values, bits, group_size):
    if not isinstance(values, (list, tuple)) or not values:
        raise ValueError("values must be non-empty")
    if isinstance(group_size, bool) or not isinstance(group_size, int) or group_size < 1:
        raise ValueError("group_size must be >= 1")
    qs, deqs, scales = [], [], []
    for start in range(0, len(values), group_size):
        group = values[start:start + group_size]
        scale, q, deq, _ = symmetric_quantize(group, bits)
        scales.append(scale)
        qs.extend(q)
        deqs.extend(deq)
    mse = sum((a - b) ** 2 for a, b in zip(values, deqs)) / len(values)
    return scales, qs, deqs, mse


def asymmetric_quantize(values, bits):
    if not isinstance(values, (list, tuple)) or not values:
        raise ValueError("values must be non-empty and bits must be >= 1")
    if any(isinstance(x, bool) or not isinstance(x, (int, float)) or not math.isfinite(x) for x in values):
        raise ValueError("values must contain finite numbers")
    if isinstance(bits, bool) or not isinstance(bits, int) or bits < 1:
        raise ValueError("bits must be an integer >= 1")
    qmin, qmax = 0, 2 ** bits - 1
    data_min, data_max = min(values), max(values)
    if data_min == data_max:
        if data_min > 0:
            scale, zero_point, q = data_min / qmax, 0, [qmax] * len(values)
        elif data_min < 0:
            scale, zero_point, q = -data_min / qmax, qmax, [qmin] * len(values)
        else:
            scale, zero_point, q = 1.0, 0, [0] * len(values)
        deq = [scale * (x - zero_point) for x in q]
        return scale, zero_point, q, deq, 0.0
    vmin, vmax = min(data_min, 0.0), max(data_max, 0.0)
    scale = (vmax - vmin) / (qmax - qmin)
    zero_point = max(qmin, min(qmax, round(qmin - vmin / scale)))
    q = [max(qmin, min(qmax, round(x / scale + zero_point))) for x in values]
    deq = [scale * (x - zero_point) for x in q]
    mse = sum((a - b) ** 2 for a, b in zip(values, deq)) / len(values)
    return scale, zero_point, q, deq, mse


def gib(num_bytes):
    return num_bytes / (1024 ** 3)


weights = [-1.2, -0.7, -0.1, 0.0, 0.2, 0.9, 1.4, 2.2]
scale4, q4, deq4, mse4 = symmetric_quantize(weights, bits=4)
g_scales, g_q4, g_deq4, g_mse4 = groupwise_quantize(weights, bits=4, group_size=4)

activations = [-3.0, -0.5, 0.0, 0.8, 2.5, 8.0]
a_scale, zp, aq, adeq, act_mse = asymmetric_quantize(activations, bits=8)
constant_scale, constant_zp, constant_q, constant_deq, constant_mse = asymmetric_quantize([5.0, 5.0], bits=8)

act_max = [8.0, 1.5]
weight_max = [0.5, 3.0]
smooth = [math.sqrt(a / w) for a, w in zip(act_max, weight_max)]
smoothed_activation = [a / s for a, s in zip(act_max, smooth)]
smoothed_weight = [w * s for w, s in zip(weight_max, smooth)]

params = 7_000_000_000
fp16_gib = gib(params * 16 / 8)
int4_weight_gib = gib(params * 4 / 8)
int4_scale_gib = gib((params / 128) * 2)

print("int4_scale=", round(scale4, 4), "q=", q4, "mse=", round(mse4, 5))
print("group_scales=", [round(x, 4) for x in g_scales], "group_mse=", round(g_mse4, 5))
print("act_int8=", {"scale": round(a_scale, 4), "zero_point": zp, "q": aq, "mse": round(act_mse, 5)})
print("constant_act_int8=", {"scale": round(constant_scale, 4), "zero_point": constant_zp, "q": constant_q, "deq": constant_deq, "mse": constant_mse})
print("smooth_max=", {"activation": [round(x, 3) for x in smoothed_activation], "weight": [round(x, 3) for x in smoothed_weight]})
print("memory_gib=", {
    "fp16": round(fp16_gib, 2),
    "int4_weight": round(int4_weight_gib, 2),
    "int4_scales": round(int4_scale_gib, 2),
    "int4_total": round(int4_weight_gib + int4_scale_gib, 2),
})
diagnostics = {
    "group_mse_lower": g_mse4 < mse4,
    "int4_storage_lower": int4_weight_gib + int4_scale_gib < fp16_gib,
    "activation_mse_finite": math.isfinite(act_mse),
    "constant_activation_exact": constant_mse == 0.0 and constant_deq == [5.0, 5.0],
}
print("diagnostics=", diagnostics)
```

这段 demo 要观察三件事：

1. group-wise scale 可以降低 toy 权重量化 MSE，但会增加 scale 元数据和 kernel 复杂度。
2. activation outlier 会拉大量化范围；SmoothQuant 的直觉是把 activation 最大值压低，把部分难度转移到 weight。
3. INT4 权重存储显著低于 FP16，但真实上线还必须看质量、latency、kernel 和结构化输出回归。
4. `diagnostics` 分别报告 MSE、存储和数值有限性；它们是 toy 观察量，不是量化后模型质量的总判定。

代码对全零张量和常量激活增加了退化分支，避免把除零错误误当成量化算法结论。7B 的 scale 账本假设每 128 个 INT4 权重使用一个 16-bit scale，真实格式可能使用不同 group size、zero point 和元数据布局。

读输出时可沿正文已有的手算例子逐项核对：第一行的 scale、整数和 MSE 对应 §2.4 的八个权重；第二行只把相同向量按 4 个值分组，便于看局部刻度如何改变重建误差；activation 行复用 §4 的非对称映射输入；SmoothQuant 行比较变换前后 activation 与 weight 的最大幅值；memory 行则按参数量与 scale 假设比较 raw payload。diagnostics 只把这些局部关系变成布尔值，例如分组 MSE 是否更低、估算 INT4 存储是否小于 FP16；它不能判断代码、工具或长上下文任务是否正确。

函数返回值也对应同一条核对链：symmetric 路线返回一个 scale、整数数组、反量化数组和均方误差；group-wise 路线返回多个 scale 并按原顺序拼回整数/反量化结果；asymmetric 路线还额外返回 zero point。print 时把 scale 和 MSE 四舍五入只用于显示，内部值仍是浮点近似，所以手算与打印结果末位可能略有差异。检查时应先对照整数码和 scale，再对照反量化误差，避免只看最后一个布尔值。

读者可以分别改一个输入观察机制：把 group size 从 4 改成 8，会让两组 scale 变成一个全局 scale；向权重数组加入更大的 outlier，会扩大对称刻度并改变小值的整数等级；把常量激活改成全零，则应走安全退化分支而不发生除零。每次只改一个条件，才能把输出变化归到粒度、范围或边界处理。这里的 MSE 用 Python 浮点与语言内置舍入计算，真实 kernel 可能有不同舍入约定、打包布局和融合次序；代码也没有执行 GPU 矩阵乘、导出 artifact 或读取模型，因此只能帮助理解映射和账本。

特别注意 memory_gib 输出是根据“参数数 × bit 数”直接估算的 payload 账本，Python 列表和整数对象本身的内存没有参与，也没有模拟 nibble packing、scale 对齐、embedding、workspace、并行分片或 allocator。它回答的是“理论字节量级怎样计算”，不是进程 RSS、显存峰值或部署容量。若把参数数换成真实模型配置，仍须从实际 manifest 读取参数总量和格式，再由目标 runtime 测峰值。

边界分支也有明确教学目的：空数组和非法 bit width 会抛出错误，group-wise 最后一组可以短于 group size，常量 activation 会选择特殊 scale，避免除零。真实量化库还可能使用 tie-to-even 以外的舍入、非对称 INT4 码域、硬件专用 packing 或二级 scale；本例没有实现这些兼容层。读者可以先改变 toy 输入并手工复算，再把关注点带到真实 artifact 的格式和 kernel 文档中，不应把短脚本的布尔输出当成完整质量 gate。

## 17. 一个长上下文服务的量化决策

考虑一台显存 24 GiB 的 GPU，准备部署一个 7B 企业知识助手。服务要求输入 P95 为 8k token，输出 P95 为 512 token，支持 16 个活跃请求；它既要回答普通问题，也要生成 JSON、调用只读工具并给出文档引用。团队提出三个候选：W4A16 权重量化、W8A8 激活量化，以及保持权重 W4A16 但把 KV Cache 从 BF16 改成 FP8。正确的选择不能从“4 bit 最省”开始，而要先找出真正的显存和质量约束。

第一步建立高精度 reference 的显存账本。7B 参数的 FP16 权重约为 13.04 GiB，原始 INT4 权重约为 3.26 GiB；再按“16 个请求同时接近总上下文 P95”的压力情形估算 KV Cache。输入 P95 约 8,192 token，输出 P95 约 512 token，所以单请求按 8,704 个已缓存 token 估算。若模型有 32 层、8 个 K/V heads、head dimension 为 128、cache 使用 BF16，则单 token 的理论 cache 成本是：

~~~math
m_{\mathrm{KV/token}}
=2\times32\times8\times128\times2
=131072\text{ bytes}.
~~~

16 个请求各保留 8,704 个 token 时，理论 KV Cache 约为：

~~~math
M_{\mathrm{KV}}
\approx131072\times16\times8704
\approx17\text{ GiB}.
~~~

这还没有计入 workspace、激活、通信、block metadata 和 headroom。FP16 权重加 BF16 KV 的理论小计约为 30 GiB，显然超过 24 GiB；压到 INT4 后，若按每 128 个权重增加一个 16-bit scale，权重约 3.36 GiB，和 17 GiB KV 合计约 20.36 GiB，只剩约 3.64 GiB 给其它运行内存。是否装得下 16 个并发请求，必须以目标 runtime 峰值和必要 headroom 实测，不能只从权重与 KV 两项账本下结论。这个账本说明 W4A16 解决权重常驻显存，却不自动保证长上下文并发可行。

这里把每个活动请求都置于单请求 P95 长度，是容量压力场景，不是由分位数直接推出的并发分布。按每 token 128 KiB 计算，8,192 个输入 token 占 1 GiB，512 个输出 token 占 64 MiB，单请求合计 1.0625 GiB，乘以 16 得到 17 GiB。真实容量应从同一段到达 trace 读取同时活跃请求的输入与输出长度，并纳入 prefix 共享、page 粒度舍入和抢占状态；不能把 16 个单请求 P95 当成真实 P95 并发。

还可以把余量写成可执行的准入条件。假设团队暂定至少预留 4 GiB 给 workspace、碎片和运行波动，那么 INT4 权重与上述 KV 小计 20.36 GiB 后只余 3.64 GiB，仍差 0.36 GiB，候选即使能加载也不满足这项容量门槛。4 GiB 是用于说明决策过程的假设阈值，不是通用部署建议；目标 runtime 的 workspace 峰值、allocator 行为和故障余量应由同一硬件与请求 trace 实测后确定。

第二步分别计算候选能够改变哪一本账。W4A16 主要降低 `M_weights`，如果 runtime 使用真正匹配的低比特 kernel，还可能降低权重读取；W8A8 同时改变权重和激活路径，潜在收益更广，但要处理 activation outlier、累加精度和硬件指令；FP8 KV 只改变 `M_KV` 的数据部分，理想情况下从 2 bytes 降到 1 byte，约把 cache 数据减少一半，但 scale、metadata 和反量化访问会减少实际收益。不能把三者的 bit 数直接相加，也不能用权重量化后的文件大小推断并发上限。

第三步准备彼此独立的校准集和评估集。校准集要覆盖中文和英文、短问题与 8k 长文档、代码、数学、JSON、工具参数、引用和多轮对话；评估集必须使用未参与 scale、GPTQ 或 AWQ 搜索的样本。对 activation 或 KV 量化，还要记录每层、每 head 或每 block 的范围、饱和率和 outlier 频率。只用短英文问答校准，然后用平均语言模型 loss 证明 8k RAG 没有退化，会漏掉最重要的业务错误。

第四步分离“数值误差”和“runtime 路径”。对 W4A16，确认哪些模块被量化，group size、scale 轴、zero point、权重布局和 tensor parallel 分片是否与 kernel 一致；对 W8A8，确认乘法、累加、输出 cast 和动态 scale 的精度；对 FP8 KV，确认 K 和 V 是否使用相同格式，scale 是 per-head、per-token 还是 per-block，以及 cache 是否能在抢占、prefix reuse 和跨 worker 恢复时保持一致。用 profiler 检查实际 kernel；如果 packed INT4 进入后先完整解包为 FP16，文件变小仍可能没有速度收益。

第五步做分层回归。先比较 reference 和候选的 token ids、logits 差异、finish reason、stop 和 JSON parse；再比较 schema 合法率、引用支持率、工具参数合法率、代码测试和数学正确率；最后在目标并发下测显存峰值、TTFT、TPOT、P99、OOM、抢占恢复和单位成功任务成本。结果应按输入长度、任务类型和生成预算分桶。一个候选在短聊天上只下降 0.2 个百分点，却在长文档引用上下降 8 个百分点，不能用总体平均把风险隐藏掉。

回归要使用同一批 request id、输入、tokenizer、chat template、采样设置和 runtime 配置，让 reference 与候选之间只有待测压缩变量不同。确定性解码固定相同参数；带随机采样时按 request id 配对随机种子，并同时保留未配对的自然流量回放，避免把抽样波动误认为量化误差。token 或 logits 差异是定位线索，最终是否可用仍由引用、schema、工具和任务成功率的预先定义门槛决定；应记录各桶样本分母和失败例，不能只报一个平均分。

可以把发布候选写成带硬约束的集合。对量化方案 q，要求：

~~~math
\mathcal{Q}_{\mathrm{valid}}=
\left\{q\middle|
\begin{array}{l}
M_{\mathrm{peak}}(q)\le M_{\mathrm{GPU}}-M_{\mathrm{headroom}},\\
P99(\mathrm{TTFT},q)\le b_{\mathrm{TTFT}},\\
P99(\mathrm{TPOT},q)\le b_{\mathrm{TPOT}},\\
\mathrm{SchemaPass}(q)\ge r_{\mathrm{schema}},\\
\mathrm{ToolSafety}(q)\ge r_{\mathrm{safety}},\\
\Delta\mathrm{Quality}(q)\ge-\epsilon
\end{array}\right\}.
~~~

只有进入 `Q_valid` 的候选才值得比较成本和吞吐。若 W4A16 满足显存却让工具参数错误率上升，不能把它列为“可接受但稍差”；若 FP8 KV 满足容量却让长上下文引用下降，则应调整量化粒度、保留敏感层/最近 token 的高精度，或退回 BF16，而不是只增加重试。

第六步安排灰度和回滚。量化 artifact、scale、runtime、GPU 驱动和质量基线必须绑定到同一个 revision。先用离线 replay，再用影子流量，最后按低风险租户灰度；监控 cache 饱和率、引用支持率、schema/tool pass、P99 和错误类别。回滚时不能只换权重文件，还要清理不兼容的 active/prefix cache，确认正在生成的请求能够完成或安全取消，并防止客户端因为超时重复执行工具。

读结果时要按“先硬门槛、再优化目标”分支：显存和任务质量过关但 TPOT 没变，先查 profiler 是否走了 packed-weight kernel、瓶颈是否其实在 KV 或调度；W4A16 只改善装载容量时，把它记录为存储/并发收益，不能声称单 token 更快；FP8 KV 改善准入却损伤长文档引用，则只调整 KV 的 scale、保留窗口或敏感层精度，再对同一桶回放。若 JSON 或工具参数门槛失败，候选直接退出发布集合，不能用更多重试或平均分补偿协议错误。这样每次迭代都能把容量、数值误差、kernel 和业务失败分开定位。

具体验收顺序可按验证成本递增：先检查 artifact、分片与 kernel 是否匹配，加载路径不成立就停止；再做小批量数值和协议回放，排除格式、模板及输出约定错误；通过后才进入目标并发压测和灰度。每个阶段记录候选 revision、输入分桶、峰值和淘汰理由，便于回溯方案为何被保留或拒绝。正式切换前保留 FP16/BF16 基线及可恢复的模型、量化参数和 cache schema；若 cache 表示不兼容，先排空旧请求或隔离旧 worker，避免新旧状态交叉读取。这个顺序把高成本线上验证留给已通过底层正确性门槛的方案。

这个案例的结论是分层的：如果权重放不下，先考虑 W4A16/W8A16；如果长上下文 KV 成为瓶颈，再测 FP8/INT8 KV；如果 activation outlier 阻止 W8A8，才考虑 SmoothQuant、动态 scale 或 QAT；如果低比特 kernel 不存在，压缩可能只带来存储收益。量化不是一个模型文件转换动作，而是数值表示、硬件路径、任务协议和发布生命周期共同组成的系统变更。

## 19. 本章小结

本章核心结论：

1. 量化用低精度换显存、带宽和成本收益。
2. FP16/BF16 是常见基线，INT8 更稳，INT4 更省但风险更高。
3. Weight-only quantization 是 LLM 推理常见路线。
4. Activation quantization 更难，常受 outlier 影响。
5. PTQ 适合从既有 checkpoint 快速试验；QAT 可以让模型适应量化误差，但需要训练和匹配部署 fake/real quant 路径。
6. GPTQ 用近似二阶统计补偿权重量化误差；AWQ 用 activation 统计与等价缩放保护敏感通道；两者的实际速度都受 kernel 和 workload 控制。
7. LLM.int8()以 FP16 旁路处理 outlier；SmoothQuant 把部分 activation 难度迁移到权重；效果目标和执行代价不同。
8. KIVI 的 K-per-channel、V-per-token 与高精度 residual 是对 cache 分布和逐 token 写入的联合设计；不能只看名义 bit 数。
9. TurboQuant 等低 bit KV 研究要分开看向量失真、下游任务质量和服务吞吐；有损 cache 在内存受限 burst 下可能改善准入与 TTFT，但不保证单 token 更快。
10. MXFP4、NVFP4、FP8 与设备专用 INT4 必须按 element、scale、artifact、kernel 和 runtime 支持分别核对。
11. 蒸馏、剪枝和稀疏化保留了不同知识/计算对象；稀疏率、模型文件大小和实际速度不能互相替代。
