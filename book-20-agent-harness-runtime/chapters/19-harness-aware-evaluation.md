# 第 19 章 Harness-Aware Evaluation：成绩属于系统配置

## 19.1 同一个模型，为什么会有两种成绩

想象两组人都用同一模型修复同一个程序缺陷。第一组给模型终端和文件编辑器；第二组先把仓库结构、测试命令和错误日志放进上下文，还允许它在测试失败后重试。最后，第二组通过的任务更多。

这并不能直接说明模型变强了。变化可能来自模型，也可能来自工具接口、提示、重试、执行环境或验收器。Agent 的分数描述的是一次完整配置在指定任务上的表现。只写模型名称，读者看不出这次测量究竟包含了什么。

一次 Agent 评测至少涉及以下对象：

| 对象 | 例子 | 为什么会改变结果 |
| --- | --- | --- |
| 模型 | provider、准确 snapshot、生成参数与 reasoning effort | 改变模型接收的条件和生成动作 |
| Agent harness | system prompt、工具定义、控制循环、记忆、重试、多 Agent 编排 | 改变模型能看到什么、能做什么，以及宿主怎样响应 |
| 任务与环境 | 样本版本、仓库 revision、初始状态、依赖、权限、网络和时限 | 改变问题本身与可用行动 |
| 验收与预算 | 独立 verifier、运行次数、token/调用上限、截止条件 | 改变什么算成功，以及系统可花多少资源 |

Agent harness 控制 Agent 怎样接收上下文、调用工具和结束运行；evaluation harness 则初始化任务、限制资源、保存证据、运行评分器并汇总结果。两者会相互作用，但职责不同。第十章已经讲了怎样构造任务夹具、Runner、verifier 和可复查的评估记录；本章在此基础上追问：当模型、Agent harness 和环境组合发生变化时，成绩差异能归因到什么范围？

## 19.2 先说清你要比较哪一个变化

“A 比 B 好”需要先补上 A、B 是什么，以及读者想从比较中得出什么结论。若一次同时换了模型、工具、环境和预算，结果仍能回答“哪套系统对当前任务更合适”，却不能单独回答“哪一个模型更强”。

| 想回答的问题 | 改变什么 | 其余部分怎样处理 | 结论能说到哪里 |
| --- | --- | --- | --- |
| 换模型有没有帮助？ | 模型版本 | 固定 Agent harness、任务、环境、验收和预算 | 对所测 harness 与任务分布，结果如何变化 |
| 换 harness 有没有帮助？ | prompt、工具或编排中明确的一项，或整套 harness | 固定模型、任务、环境、验收和预算 | 该模型与所测 harness 配置下的变化 |
| 新产品整体是否更适合？ | 产品自带的模型、工具和运行方式可能同时变化 | 明确记录每项配置 | 哪套完整产品配置在所测任务上更合适；不能自动拆成模型因果 |
| 哪种配对更合适？ | 模型和 harness 都改变 | 让多个模型与多个 harness 交叉运行 | 配对之间是否出现主效应以外的差异 |

如果配置 A 使用一个模型、harness 和任务集，配置 B 又同时更换三者，观测差异就混合了多个变化。要估计某个组件的作用，先定义它的对照组：相同的任务、环境、验收和预算下，只改目标组件。若目标是比较原生产品，则应把原生运行方式当作完整配置的一部分来测量；若目标是隔离某项 harness 功能，就需要共同的外部条件，并说明适配器或标准化接口本身可能改变行为。

例如，评估第十八章的 context folding 改动时，可以固定模型、工具、任务、工作区版本和预算，只比较两种折叠策略；同时查看任务是否完成、硬约束是否留在上下文中、关键事实能否回到来源，以及折叠造成的 token 与恢复成本。若把模型和工具循环也一起换掉，就只能判断整套新配置的结果，不能把变化单独归给折叠策略。

## 19.3 交叉比较才能看见配对差异

下面是一个教学构造：两个模型 M1、M2 分别搭配两个 harness H1、H2，在同一组四个任务上各运行一次。数字只为说明读法，不是实验数据。

|  | H1 | H2 |
| --- | ---: | ---: |
| M1 | 2/4 | 3/4 |
| M2 | 3/4 | 3/4 |

在 M1 上，换成 H2 多通过一个任务；在 M2 上，总通过数没有变化。若只报告两个模型上的平均成绩，读者可能会得到“H2 略好”的总结，却看不到它对 M1 和 M2 的作用不同。这种“某个 harness 与某个模型配在一起，效果偏离各自平均变化”的现象，就是模型与 harness 的交互。

四个任务不足以判断真实系统中是否有稳定提升，也没有显示重复运行时的随机波动。它只帮助读者看见：一个配对的总体分数，可能同时藏着模型表现、harness 表现和配对差异。要估计这些量，需要更多任务、足够的交叉配置、重复运行和合适的统计分析；完整的实验设计与不确定性计算见[第七册第十章《统计显著性与实验设计》](../../book-07-evaluation-experiments/chapters/10-统计显著性与实验设计.md)。

把多个模型下切换 harness 的平均变化称为 harness 的**主效应**；把某个模型与某个 harness 配对后，额外偏离这个平均变化的部分称为**交互**。只看主效应会回答“平均而言哪种配置变化更好”，却可能掩盖“它只适合某些模型”。是否应采用某种配置，取决于产品是固定使用一类模型，还是要服务多个模型。

真实比较常会遇到不完整矩阵：某些模型只在一个 harness 上运行，另一些 harness 又只搭配少数模型。这样的稀疏数据可以描述观察到的组合，但更难区分组件效应和模型—harness 交互。Han 与 Sun 对 Terminal-Bench 2.0 leaderboard 的分析，整体使用 105 个 harness–LLM 配对；他们把交互模型限制在完整交叉的 3 个 harness × 9 个模型子集上。该分析报告的模型效应和 harness 效应在所选数据中量级相近，但 leaderboard 是观察性数据，不能读成随机受控的普遍因果排名。[论文与设计边界](../../research/model-harness-interaction-attribution-2026-11-18.md#harness-与模型的统计分解)

## 19.4 配对任务，重复运行，并说明实验单位

评估 Agent 时，几个看起来相似的计数实际上回答不同问题：

- **Task（任务）**描述目标、初始状态和验收条件，例如“在指定仓库中修复登录重定向并通过相关测试”。
- **Trial（试验）**是系统在该任务上的一次运行，通常包含该配置允许的内部重试。
- **Trajectory（轨迹）**记录这次运行看到的观察、发出的动作、工具回执和状态变化。
- **Outcome（结果）**是结束时的答案、artifact 或环境状态，由任务验收规则判定。

Harvard CS2680 的课程讲义也用这四个层次介绍 Agent evaluation，并提醒读者：同一任务上的多次 trial 用于观察运行波动，不能当成新增任务数。比较时，应让配置使用同一批任务和等价初始状态；否则一组恰好抽到更容易的任务，也可能显得更强。[课程讲义](https://cs2680.seas.harvard.edu/notes/agent-evaluation)

重复次数也要与比较目标相符。模型生成、工具服务、网络和评分器都可能有波动；单次运行只告诉我们这一次发生了什么，无法估计同一条件下的运行变异。每个任务多次运行时，需记录 task ID、trial ID、随机种子、状态重置方式和是否发生内部重试。同一运行里的三次 agent retry 仍是一条 trial 的内部策略，不等于三条独立 trial。

条件对齐也不代表必须抹平产品差异。若比较两个完整产品，就固定任务和外部预算，保留各自原生的工具与循环，并把它们记入系统配置。若要回答某一项技术改动的作用，则把其它条件固定或交叉设计。报告应先写明采用哪种比较，再解释结果。

## 19.5 任务成功与 harness 履约分别记录

一个 Agent 可能完成用户任务，却没有遵守 harness 的运行要求；也可能按规则执行，但最后没有交付正确 artifact。只看一个 task-success 数字会把这两种情况合在一起。

| 结果层 | 要问的问题 | 证据例子 |
| --- | --- | --- |
| 任务结果 | 目标答案或交付物是否满足任务要求？ | 独立测试、结构化结果校验、最终 artifact |
| Harness 履约 | 系统是否按约定使用工具、权限、预算、恢复和终止流程？ | 工具调用与回执、权限事件、停止原因、状态版本 |
| 评测装置 | 环境是否成功启动，验收器是否按预期执行？ | 环境预检、模型/API 错误、verifier 错误和输入输出记录 |

先把三层结果分开，再按各自适用的样本报告成功、失败、错误和无法判断。若环境在 Agent 启动前失败，这不是 Agent 解题失败；若 verifier 不能判断结果，也不能把它算作成功。不要默认把上述层次加权合成一个分数或上线门槛。

《Trial by Trace》用 95 个机制任务比较 4 个 harness 和 9 个模型，并把任务结果与 harness criteria 分开评分；论文摘要报告，在其 3,420 个选中执行中，31.1% 完成了任务但至少违反一项 harness criterion。这个数字说明两层结果可以分离，适用范围仍是该预印本的任务、系统与判定标准；每个 cell 只有一个被选中的执行，不能用来估计各配置的随机方差。[论文版本与限制](../../research/model-harness-interaction-attribution-2026-11-18.md#trial-by-trace任务结果与-harness-履约分层)

怎样定义任务夹具、配置身份、Runner、独立验收、分母和运行故障分类，回看[第十章《Evaluation Harness》](10-evaluation-harness.md)。本章不重复建立一套新的评估脚手架。

## 19.6 Trace 帮助提出原因，还不能替原因作证

Trace 能告诉我们一次运行按什么顺序发生了什么，但“先发生”不一定代表“导致了失败”。假设 Agent 最终没有提交修复，至少有几种可能：模型没有提出编辑；adapter 丢弃了有效工具请求；命令执行在另一个工作目录；进程已写入文件但回执超时；或 verifier 检查了错误版本的文件。

为了区分这些解释，轨迹和 artifact 至少要能连接到同一任务与运行身份，并保留：

1. 模型实际收到的输入与它生成的动作；
2. Router 或 policy 对动作作出的决定；
3. 工具请求、执行回执和可观察副作用；
4. 当时的 workspace 或环境版本；
5. 验收器读取的对象、判定结果与失败信息。

如果 trace 只保存模型文本，或只有“工具调用成功”这类摘要，就无法判断成功指的是模型发出请求、宿主接受请求，还是外部状态真的改变。反过来，完整 trace 仍然只是一次运行的记录。要把候选原因提高为归因结论，需要核对机制所需的事件和状态证据、检查竞争解释，并在条件可控时通过单项消融、受控重放或定向故障注入检验它。重放如果依赖随机生成或外部服务，也要保留这部分不确定性。

《Trial by Trace》会把轨迹中的候选机制链与人工核验过的失败传播分开；论文把端点、事件顺序、中间变化和竞争解释列为人工复核重点。OpenAI 当前 Agent Evals 文档则展示了一种供应商工作流：调试时从 trace grading 找问题，定义好“good”之后再用 datasets 和 eval runs 做重复比较。前者是预印本方法，后者是产品文档；它们都不证明自动 grader 单独就能确定因果根因。[来源与适用边界](../../research/model-harness-interaction-attribution-2026-11-18.md#其他归因与分层结果研究)

## 19.7 把质量和资源成本并列看

重试、长思考和多个 Agent 都是额外的资源策略。一个方案在同一组任务上多通过几个案例，可能是因为它消耗了更多 token、工具调用和时间。此时“成绩更高”成立，但“更有效率”还需要另一组证据。

至少分别报告：

- 任务结果与 harness 履约情况；
- 输入、缓存、输出及子 Agent 的 token 与调用数；
- 墙钟时间和工具执行时间；
- 运行费用或基础设施成本；
- 人工复核、接管与失败恢复所需的工作量。

重试或多 Agent 若属于被比较的 harness，就把其全部消耗纳入预算，包括失败、超时和子 Agent 的调用。若两个系统资源预算不同，要明确写出；可以并列展示质量和成本，或在多个预算点比较质量—成本关系，不要把二者藏进一个不透明的总分。

《Do More Agents Help?》用统一执行、工具、评分和 token 记账方式，在固定 GPT-4.1 上比较六种 multi-agent 工作流与单 Agent 参考。其主研究跨十组任务运行三次，每种配置每次评估 3,302 个样本。LLM-Debate 在 HumanEval 上比单 Agent 高 9.67 个百分点，但汇总准确率低 1.96 个百分点、token 用量为 1.39 倍；ChatEval 在 IFEval 有局部优势，汇总准确率较低且 token 用量为 4.34 倍。这说明单一 benchmark 的提升不能代表整体质量—成本结论；这些数字只属于论文所测配置和任务。[论文协议与数字边界](../../research/model-harness-interaction-attribution-2026-11-18.md#do-more-agents-help固定协议下的质量与-token-成本)

## 19.8 检查改进是否只发生在被调过的题目上

Prompt、工具、retry policy 或 orchestration 经过 benchmark 反复调优后，原测试集就不再是独立的“新题”。Harness 可能真的学会了更好的通用过程，也可能记住了任务模板、测试线索、常见仓库结构，或者只是用更多 test-time compute 换取分数。

因此，要把调试和选择用的任务，与最终报告用的留出任务分开。若同一仓库、题目模板或模拟器机制在多个集合间重复，单纯隐藏测试样本未必就提供独立检验；可按仓库、任务族、模板或环境机制留出，并记录是否经过开发者多轮查看。对比时还要控制或报告额外推理、retry 和工具调用预算。

《Harness-Delta Attribution》在固定模型权重的 harness 演化实验中，提出分别估计 benchmark overfitting、test-time scaling 和剩余收益的方法。作者在 21 个 search-set 显著提升的设置里，报告前两类收益平均分别占 54% 与 14%；其余部分是该方法定义下的可泛化改进上界。论文还发现，held-out 转移依任务、模型与演化框架而变化，validation 选择也没有稳定解决过拟合。这些数值是作者方法在特定研究设置中的分解，不是任意 Agent 项目的通用配比。[论文及其方法边界](../../research/model-harness-interaction-attribution-2026-11-18.md#harness-delta-attributionharness-演化后的收益来源)

## 19.9 近期研究各自回答了不同问题

几篇研究都在谈 harness，但它们的评估对象、实验设计和证据层并不相同。读者先看“它实际改变了什么、测量了什么”，再看结果数字。

| 研究 | 可以用来理解什么 | 不能据此推出什么 |
| --- | --- | --- |
| Han 与 Sun，Terminal-Bench 2.0 leaderboard | 稀疏交叉设计下，怎样估计模型和 harness 的平均效应，并在完整子矩阵研究交互 | 随机分配下的因果效应或普遍模型/harness 排名 |
| Harness-Bench v2 | 原生 model–harness 配置在实际工作流、artifact 与成本上的差异 | 未测系统和生产任务的普遍表现；其固定 v2 正文与摘要页的任务数存在版本口径差异 |
| Trial by Trace v1 | 将任务完成与 harness criteria 分开，并把候选失败链与人工核验结果分层 | 每配置多次运行下的随机性估计，或未经核验的根因解释 |
| Harness-Delta Attribution v1 | 在固定模型权重下，检查 harness 演化收益是否来自过拟合或额外 test-time compute | 对其它基准、模型或方法直接套用同一比例 |

Harvard 讲义和 Buffalo 课程大纲提供了组织评测知识的例子：先定义 task-level 对象与评分，再讨论任务集、指标、可靠性和成本；Buffalo 的 Lab 4 还要求把 success criteria、failure taxonomy 与可复现评测脚本一起交付。这些资料展示课程怎样组织实践任务，并非“这样安排已被证明对所有读者效果最好”的证据。[组织样本记录](../../research/model-harness-interaction-attribution-2026-11-18.md#评测组织样本)

## 19.10 写出别人能够复查的结果

每份结果至少应让读者重建“谁在什么条件下、对什么任务、按什么规则运行”。下面的记录项可以放在评估报告或随附 manifest 中：

| 记录项 | 必须能复查的内容 |
| --- | --- |
| 系统身份 | 模型 provider 与 snapshot、参数，harness 版本、prompt/tool schema 和代码 revision |
| 比较问题 | 哪项变量改变；哪些模型、环境、任务和评分条件固定 |
| 任务与环境 | 数据集及 split、task ID、仓库/环境 revision、初始化和权限策略 |
| 运行规则 | trial 数、seed、内部 retry、终止条件、token/调用/时间预算 |
| 判定规则 | verifier 版本、task outcome、harness criteria、运行错误与无法判定怎样分类 |
| 结果与成本 | 各切片的分子/分母、重复运行分布或不确定性、失败与成本；不只给一个平均分 |
| 证据材料 | 可访问的 trace、artifact、环境结果和报告版本；说明删失、缺失或无法复核的记录 |

离线评估验证的是固定任务和环境下的表现；它不能单独证明线上请求分布、真实服务依赖和用户行为下也会得到相同结果。进入线上时应单独说明流量选择、版本与 rollout 范围，并分别记录任务结果、延迟、成本和人工接管；线上监控可发现新问题，但不能替代受控离线对照。两种数据回答不同问题，不应把它们拼成一个分数。

面对一条“某 Agent 得分 70%”的报告，你可以按顺序问：这测的是裸模型还是完整系统？模型和 harness 是否交叉？任务是否匹配、运行是否重复？verifier 与 harness 履约是否分开？成本有没有包括失败与重试？测试集是否参与过调优？报告能否回到具体 artifact 和 trace？回答这些问题后，成绩才有清楚的适用范围。

这章把归因停在实验比较和证据解释上；任务 fixture、执行环境与 verifier 的详细构造仍在第十章。统计区间与实验设计回到第七册第十章；provider 的状态、工具和安全合同分别由本册第二十、二十三、二十四章结合其官方版本材料说明。
