# 第 18 章 Context Folding：上下文变短，任务状态不能失真

Agent 做一个代码任务时，会读文件、查日志、运行测试、尝试修改。每次观察都可能对下一步有用，但整段轨迹会不断变长，最终装不进一次模型调用的上下文窗口。最早的消息里也许有“不要改测试”的限制，最近的工具结果则可能已经绑定到一个较新的文件版本。只删最早消息会忘掉约束；把全部历史改写成一段顺口摘要，又可能把猜测说成事实，或把尚未确认的外部动作写成已完成。

本章把长任务轨迹转成较小、可继续使用的模型输入，这个过程称为**上下文折叠**（context folding）。折叠要回答三个实际问题：什么必须在下一轮模型输入里，什么可以缩短或以后再查，什么必须继续由任务状态和外部系统负责。这里的“上下文折叠”是本章用于讲解这一类工作的名称，不是所有 Agent 共用的 API 或数据格式。

第七章讲 Runtime 每一轮如何选择输入材料；第十七章讲任务 checkpoint 和副作用如何持久化；本章聚焦历史增长后的压缩、来源保留和恢复。折叠摘要只是帮助下一轮决策的派生视图，不能替代 checkpoint、workspace、Trace 或服务端回执。

## 18.1 一次模型输入不是整项任务的全部状态

先区分几个容易混淆的对象：

| 对象 | 它回答什么问题 | 它不能单独证明什么 |
|---|---|---|
| 模型上下文 | 这一次调用实际会看到哪些指令、工具说明、历史、文件内容或检索结果？ | 会话里保存了哪些完整消息；文件或外部服务现在是什么状态 |
| 会话 transcript | 用户、模型和工具历史记录了什么？ | 每一条旧消息都会再次送进模型；历史里写的状态仍然有效 |
| 任务 checkpoint | Runtime 保存了哪个任务阶段、工作区版本、预算和待处理动作？ | 第三方服务已提交某项动作；workspace 没有变化 |
| Trace | 运行过程记录了哪些提议、调用、回执与状态变化？ | 记录完整、没有丢失，或其中描述的外部对象仍存在 |
| Workspace / 外部服务 | 文件、测试、代码审查或其他对象当前实际是什么状态？ | 当前模型输入已经包含这些事实 |

折叠改变的是“下一轮给模型看的内容”。系统可以保留完整 transcript 和原始工具结果，却只把必要部分放进新上下文；也可以在外部存储原始资料，只将可检索的引用带入上下文。保存了某条摘要，不等于保存了它所描述的真实状态。

这一区分也解释了折叠的边界：若摘要写着“CI 通过”，Runtime 仍要知道结果来自哪个 job、对应哪个 workspace revision；若摘要写着“代码审查已创建”，就要核对权威服务回执。模型输入是一份有限视图，不是任务的事实数据库。

## 18.2 沿用 `task-42`，观察折叠前都有什么

第十七章的教学构造 `task-42` 是一项代码升级任务：仓库从 `r41` 开始，用户要求不得修改测试文件；修改完成后，工作区来到 `r42`。持续集成服务的 job `ci-884` 已针对 `r42` 成功结束，但执行该任务的 worker 在写回结果前中断。恢复时，Runtime 按本例约定查询原 job 并确认结果。随后，用户批准为这份改动创建代码审查；请求已派发，但响应丢失。本例作者知道远端对象 `review-481` 实际存在，恢复中的 Runtime 没有回执，因此只能把 effect 状态记为 `unknown`。

运行历史中还留下了重复的代码搜索、多个版本的测试输出、已被新证据推翻的根因猜测，以及很长的 CI 日志。模型下一步需要知道的远少于这些原文，但不能把它们一概删掉：

- “不要修改测试文件”是仍有效的用户硬约束。
- `ci-884` 通过的事实要绑定到 `r42`，不能套用到之后修改过的版本。
- `review-481` 是作者掌握的测试真值；Runtime 不知道该对象存在，不能把它写成已确认事实。
- CI 完整日志可能很长；如果需要进一步诊断，可通过 job 或 artifact 引用重新读取。
- 重复搜索结果可以删减；被证据推翻的猜测可压缩成“已排除”及其理由，避免恢复后重复探索。

本章的其余内容沿着这个例子回答：如何留下足够短的工作状态，让新一轮模型接着查证，又不把 Runtime 并不知道的事情当成事实。

## 18.3 先判定信息是什么，再决定怎样缩短

不同信息承担的作用不同。把它们统称为“摘要重点”，模型就容易把规则、观察和猜测混在一起。一个可恢复的折叠至少要能区分下表中的类别；实际存储不必照搬这张表的字段。

| 信息类别 | `task-42` 中的例子 | 折叠时要保留什么 |
|---|---|---|
| 任务目标与约束 | 升级依赖；不得修改测试；满足条件后才申请代码审查 | 约束原意、适用范围、来源与当前状态。否定条件不能弱化成一般偏好 |
| 用户批准 | 允许为 `r42` 上的改动申请一次代码审查 | 谁批准了什么目标和内容；批准不能扩大到另一分支或另一份 patch |
| 已验证事实 | workspace 为 `r42`；`ci-884` 对 `r42` 返回成功 | 值、来源、观察时间、对应 revision/job，以及是否仍可能过期 |
| 假设与被排除解释 | 起初怀疑兼容层问题，后来测试证据排除了它 | 当前是否仍是猜测、由什么证据支持或推翻；不要升级成事实 |
| 决策与待办 | 先核对 CI，再处理代码审查；回执丢失时不盲目再建 | 决策理由、当前阶段、下一项检查及其依赖 |
| 工具观察与事件 | 多次搜索、测试输出、请求发出、响应丢失 | 哪个动作实际发生、返回什么、对应哪个调用或事件 ID |
| Artifact 与原始来源 | patch、CI 日志、测试报告、diff | 稳定引用、内容摘要或校验值、revision 和取回方式；引用本身不代替检查内容 |
| 未决副作用 | 创建审查的 effect 回执缺失 | 保留准确状态 `unknown`、原操作身份和允许的查询/人工对账路径 |

“新消息比较新”并不代表它可以覆盖所有旧规则。只有在相同授权层级下，用户的后续明确指令才可能更新较早的任务要求；高优先级系统规则仍然有效。若两条同级指令确实冲突，应保留冲突和来源，按规则处理或请用户澄清，不要由摘要器自行挑一条。

## 18.4 对每类信息选择不同的处理方式

折叠不是统一的“缩短文字”。对一段内容，Runtime 可以保留、聚合、概括、外置后按需读取，也可以丢弃。选哪一种，取决于下一步是否需要它、能否从可信来源重新取得，以及它是否会改变安全或任务结论。

| 处理方式 | 适合的材料 | 例子与边界 |
|---|---|---|
| **固定保留** | 当前任务的硬约束、必要授权、未决副作用 | 保留“测试文件不得修改”和授权对应的 `r42` patch。对于关键否定限制，可以保留原文或可检查的结构化条件，避免转述漏掉“不”字或范围 |
| **验证后压缩** | 已确认且来源明确的事实、重要决定 | 把“job `ci-884` 对 `r42` 成功”保留为一项事实，并记录查询结果引用；不要只写“测试通过” |
| **聚合重复内容** | 重复搜索结果、相同警告、同一测试的大量无差别行 | 可写明重复次数、时间范围、命令和 artifact 引用；仍需保留会改变判断的首个错误、退出状态和最后一次结果 |
| **概括过程** | 已结束的探索、失败尝试和较长解释 | 记录哪些路径已试、为何排除、适用的代码 revision；结论若影响下一步，要能回到支持它的原文 |
| **外置并按需检索** | 不必每轮看到、但之后可能要核对的长日志、文件或报告 | 把完整输出留在有权限保护的 artifact/workspace 中，摘要带稳定 ID 和取回方式；取回时检查它属于哪个任务与版本 |
| **丢弃** | 礼貌性往返、完全重复且可重建的输出、与当前目标无关的旧内容 | 丢弃前先确认它不包含独有约束、决定、授权、证据或待处理动作；“模型以后可以猜回来”不是可重建证明 |

约束和事实的区别很关键：用户说“不要修改测试”是规则，diff 显示“当前测试文件未变”是观测。后者需要随 workspace 版本更新；前者在任务被明确改变前仍约束动作。一个完整摘要不能用前者替代后者，也不能因当前 diff 没有测试文件而删掉用户约束。

## 18.5 把折叠做成一次可检查的交接

下面的过程把原始历史变成下一轮工作输入。它不是任何框架的固定协议；Runtime 可以把一些步骤自动化，但每一步的依据都应能说清。

1. **选一个安全时点。** 在阶段结束、工具输出累积过多或预计下一次输入会逼近预算时检查是否折叠。若仍有正在执行的工具调用，先记录它的真实状态或等待回执，不能把“请求已发出”压成“结果已知”。
2. **读取当前权威状态。** 查看任务 checkpoint、最新用户指令、workspace revision、最近 Trace、权限决定和 effect ledger。模型先前的文字只能作为历史记录，不能单独更新这些权威状态。
3. **给候选信息分类。** 标出硬约束、授权、已验证事实、假设、决策、观察、Artifact 与未决副作用；同时标记来源、时间、版本和是否可能过期。
4. **按类型压缩。** 固定保留必要规则；合并重复观察；压缩已结束的探索；为长材料保留受权限控制的引用；将过期或被推翻的事实标成旧状态，不与当前状态合并。
5. **组装下一轮输入。** 把系统与开发者规则、工具说明、当前任务状态、折叠后的工作摘要和最近的原始事件分开组织。还要为下一条用户消息、工具回执和模型输出预留空间。
6. **逐项检查后再发布。** 对照原始任务合同、checkpoint 和来源核验规则、事实、授权、冲突及 effect 状态。确认引用仍指向正确 artifact，且摘要长度确实符合这次调用的预算。
7. **保留原始回查路径。** 新上下文可只带摘要，但日志、diff、用户请求和服务回执仍应按各自权限与保留策略存放；需要时取回具体来源，不能把摘要当成唯一档案。

第 2 步和第 7 步把“模型看到什么”与“任务事实存在哪里”分开。折叠可以重排模型输入，不能静默改写 checkpoint 或删除正在承担审计责任的事件记录。

## 18.6 算一遍本次调用能用多少输入

模型窗口的标称大小不等于全都能拿来放历史。系统提示、工具定义、当前用户输入、检索结果会占空间；运行时还要为回答和可能的工具结果留位置。各 Provider 的计数和限制不同，下面只用一组明确的教学数字说明怎样核算。

假设某个配置的窗口为 128K token，Runtime 为模型输出预留 24K，为协议差异和估算误差再预留 8K。因此本例设定的输入预算是 96K。当前固定规则与工具定义占 14K，累计历史与工具材料占 77K，合计 91K，只余 5K。如果下一项工具输出约 8K，就可能超过本例的输入预算；Runtime 可在发起该调用前处理历史。

折叠后，固定规则和工具定义仍占 14K；任务摘要、约束、来源与 effect 状态占 6K；最近未折叠的事件保留 7K；为即将到来的用户输入预留 1K。合计 28K，在 96K 输入预算内还剩 68K。以上数字和分配仅用于演示算术，不是推荐的窗口水位或固定压缩比例；真实系统要按所用模型/API的 token 计数、输出上限、工具结果大小和任务分布测量。

折叠触发不应只看一个百分比。若任务已完成一段探索、下一阶段需要较少旧日志，提前整理可能更清楚；若长工具输出随时可能突然到达，系统就要留出相应空间。论文中的 `80%` 或产品文档的默认阈值只描述各自实现，不自动成为其他 Runtime 的最佳配置。

## 18.7 用一份摘要交接 `task-42`

结合前面各类信息，一个教学用的折叠结果可以这样写。它是给恢复中的模型看的工作视图，不是代码格式，也不是服务方认可的 schema。

```text
任务：task-42，升级 parser 并修复兼容问题。
硬约束：用户明确要求不得修改测试文件。来源：初始用户消息 u-1。当前授权：仅允许为 workspace r42 上的改动申请一次代码审查，来源：批准消息 u-7。
工作区：基线 repo@r41；当前 patch/workspace 为 r42。来源：workspace manifest 与 patch artifact。
已验证：CI job ci-884 对 r42 返回成功；查询时间 t-12。结果引用：artifact://ci-884。若 workspace revision 变化，该测试结果不再自动适用。
假设/旧探索：早期提出的兼容层猜测已被 r42 上的 CI 和代码检查排除；细节引用：trace events e-18—e-24。
未决 effect：代码审查创建请求已派发但响应丢失；状态 unknown。原操作身份 effect_id=task-42:review:1。不能用新 ID 盲目重复创建。
下一步：读取当前 workspace revision；按代码托管服务合同查询原请求。若没有可靠查询或幂等合同，转人工对账。没有核实前不得声称审查已创建。
回查入口：原始用户/批准消息、workspace manifest、CI job 与 artifact、effect ledger、Trace 均保留在各自受权限保护的存储中。
```

这份摘要刻意保留 `unknown`，没有把本例作者知道的 `review-481` 写成 Runtime 已知事实。它也没有直接写“测试文件没改”：恢复者应检查当前 diff；用户的禁止要求则仍单独保留。CI 的成功结果绑定 `r42`，之后如果用户把工作区推进到 `r43`，应重新判断哪些检查需要对新版本运行。

## 18.8 验证摘要后，再让它成为新的工作视图

模型写出的摘要不能自己证明摘要正确。发布前，Runtime 或独立检查步骤要对照原始任务和当前持久状态，至少回答以下问题：

- 用户禁止或要求的事情是否仍以原意出现？否定条件、作用对象、时间范围和适用范围有没有被删掉？
- 每个重要事实能否回到来源？日志、测试或文件结论是否绑定正确的任务、revision 和时间？
- 假设是否仍标为假设？被新证据推翻的结论有没有与旧值、旧版本分开？
- 用户批准了哪一次动作、什么目标和什么内容？摘要是否意外扩大批准范围？
- 任何已派发、待回执或 `unknown` 的副作用是否保留原操作身份和实际状态？
- Artifact 引用能否在有权限的情况下取回？它是否仍是当前任务需要的版本？
- 新摘要与最近保留的原始事件是否冲突？预算是否同时留有新输入、输出和工具回执空间？

对关键规则，可以将原始规则保留在单独的结构化字段或原文区，并用确定性检查确认没有漏项；单靠另一个模型评判“摘要看起来不错”不足以保证规则和否定条件完整。对自由文本解释，则检查支持来源与适用条件。

折叠记录应区分“生成中”和“可供恢复使用”。例如先写入 `fold_pending`，通过来源、约束和状态检查后，再将它提交为当前版本；失败时沿用上一份已验证摘要或回读原始来源。若校验期间 checkpoint 或事件游标已变化，就基于新版本重新收集，不能拿旧输入覆盖并发产生的新事件。这与第十七章所讲的条件写入和恢复版本检查相衔接。

## 18.9 折叠后的模型先检查易过期事实，再行动

恢复输入包含折叠摘要，并不意味着所有事实都还是最新的。每种材料需要不同的“重新核对”方式：

| 折叠条目 | 恢复时先核对什么 |
|---|---|
| 用户约束与授权 | 当前指令是否更新了它；授权是否仍覆盖这份任务、目标和动作 |
| Workspace、diff、测试结果 | revision 是否与结果绑定的一致；暂停后是否有人修改了文件 |
| CI、工单或远端状态 | 使用稳定对象 ID 或原请求身份查询；不要把旧摘要当成服务端当前值 |
| Artifact 与日志 | 来源可访问、内容与校验标记一致、适用于当前版本 |
| 假设与下一步 | 依据是否仍成立；新观察是否让该假设过期 |
| `unknown` 副作用 | 按服务合同查询或转人工；不得通过自然语言摘要把它改为成功或失败 |

回到 `task-42`：先检查 workspace 仍是 `r42` 还是已经到 `r43`；再确认 CI 结果对应的 job 和 revision；然后按代码托管服务实际支持的查询合同核实原审查请求。若能查询到对象，就记录服务端对象 ID 和回执；若无安全查询或幂等合同，保留 `unknown` 并交人工核对。不能因为压缩后的摘要方便阅读，就跳过第十七章规定的恢复证据。

## 18.10 摘要只是若干折叠策略中的一种

可以采用的策略包括删除冗余材料、裁剪旧工具结果、对部分历史做摘要、把不常用材料外置后按需检索、清空轨迹从外部 checkpoint 重启，或为独立探索开多个新上下文。它们会丢掉不同信息，因此要先问：下一步是否仍需要原始内容？任务进度和约束是否在其他可信位置？副作用状态能否独立恢复？

| 策略 | 可能的好处 | 主要损失或成本 |
|---|---|---|
| 清理可从 artifact 重读的旧工具输出 | 省空间，保留必要引用即可在需要时取回 | 之后必须保证引用可访问、权限正确、内容版本匹配 |
| 总结已结束的探索 | 缩短过程，同时保留结论、排除原因和下一步 | 摘要会遗漏或误述；要检查约束、证据和当前状态 |
| 丢弃部分旧工具轨迹 | 快速释放上下文 | 可能丢掉早期证据、尝试过的路径或来源，需要其他记录能补回 |
| 清空工具历史并从 task state 重启 | 可摆脱过期的长轨迹 | 若 checkpoint、约束或 effect ledger 不完整，任务会失去连续性 |
| 并行启动独立轨迹 | 可用更多计算探索互补路径 | 额外成本；结果必须按 Artifact、来源和当前 workspace 状态合并 |

[DeepSeek-V3.2 技术报告](https://arxiv.org/html/2512.02556v1) 的 Search Agent 实验对照了 `Summary`、`Discard-75%`、`Discard-all` 与 `Parallel-fewest-step`。其设置在工具轨迹使用超过 128K 窗口的 80% 后触发策略；报告中的 BrowseComp Pass@1 是不使用 context management 时 51.4、采用管理时 67.6*。§4.4 的 Figure 6 中，`Summary` 在平均约 364 steps 处对应约 60.2 的 BrowseComp 分数；这不是 `+60.2%`。这些数字属于特定 Search Agent、商业搜索 API、模型和预算，不能证明摘要在其他任务中最好，也不能把 80% 当作通用触发线。更详细的图表口径见[第二十一册第 19.35 节](../../book-21-transformer-architecture-evolution/chapters/19-Sliding-Window与稀疏注意力.md)。

策略还可以组合：先移除可重复取得的长输出，再整理已完成阶段，最后把仍可能影响后续决策的材料放到带权限的检索入口。每次组合都要对同一任务检查恢复所需的证据和状态是否还在。

## 18.11 Provider 的压缩合同不能互相套用

产品接口能说明真实 Runtime 怎样传递或筛选上下文，但它只代表对应版本与 Provider 的实现。两个例子体现了不同责任边界：

- 当前 Anthropic Messages API 的按需压缩会返回带签名的 `compaction` block；其文档要求后续请求按合同原样带回，并注明模型、beta 和云平台支持范围。调用方不能把签名 block 当成任意可编辑的普通摘要。阈值压缩是另一条产品路径。细节及图片、文档等原始负载的边界见[第七章的 API 对照](07-上下文管理与记忆压缩.md#7183-anthropic-messages-api两类压缩是不同合同)。
- OpenAI Agents SDK 的 `session_input_callback` 能在模型调用前筛选或重排取回的历史，但官方文档说明，它仍只将新 turn 的项目作为新输入持久化；`SessionSettings(limit=N)` 则限制取回的最近 session item 数。这些操作不能自动等同于“生成一份已验证的任务摘要”，也不会因此成为任务 checkpoint。[Agents SDK Sessions](https://openai.github.io/openai-agents-python/sessions/)描述的是 SDK/session 合同。

若 Provider 管理了服务端 conversation state，Runtime 仍要从相应 API 合同核对保留时间、历史内容、压缩产物和续接方式。Responses API 与 Gemini Interactions 的具体状态合同见第二十、二十三章；不应把一个产品的 `compaction` block、SDK session 或对话 ID 当成跨供应商的通用 memory。

## 18.12 评测要同时看任务结果、约束和外部事实

折叠效果不能只看摘要是否流畅、事实问答是否相似，或模型最终有没有交出一个 patch。用户约束可能在压缩后消失，但固定 benchmark 的文件和目标仍能让任务侥幸通过。因此，评估时至少要分别检查：

1. **任务结果：** 独立 verifier 对当前 workspace/artifact 的判断，以及它对应的 revision。
2. **约束遵守：** 每条 must / must-not 规则是否进入下一轮输入，模型是否实际遵守，授权是否仍限于原范围。
3. **证据支持：** 重要事实和决策能否回到正确来源，来源是否过期或版本不符。
4. **恢复行为：** 遇到未知回执时是否先查询，是否重复执行了副作用，是否对新 revision 重跑必要检查。
5. **资源开销：** 上下文与输出 tokens、摘要调用、工具调用、延迟和重做成本。
6. **折叠过程：** 使用的策略、每任务折叠次数、验证失败与人工接管情况。

2026 年的研究进一步说明这些观察不能合成一项“压缩质量”就算完成：

- [Benchmarks Are Surprisingly Compaction-Friendly](https://arxiv.org/html/2610.31778) 在固定 OpenCode scaffold 上评估四个模型和三个长任务 benchmark，每个任务/配置运行两次。作者报告这些设置中没有一种策略显著优于默认 self-summarization；但另行检查约束时，在 44 个 SWE-chat 会话抽取的 269 条指令中，过程要求与范围排除比功能要求更容易从摘要中消失。论文认为任务目标可从文件重建的 benchmark 会低估某些行为约束丢失。该结论限于论文样本、模型、judge 和固定 scaffold。
- [The Compaction Cliff](https://arxiv.org/html/2608.22752) 展示了另一种问题表述：把配置项分类为约束、程序、偏好、信念和经历，对关键约束采用单独的保留和验证路径。作者报告在其公开配置样本和预算下，多轮普通压缩会累计丢失规则；类型化方案的约束分类器也可能漏标，而且预算不足时不能声称规则仍被完整保留。
- [AutoCompact](https://arxiv.org/html/2610.02163) 训练一个特定 coding agent 学习何时调用压缩、工作状态该保留什么、压缩后如何继续。它在固定 Qwen3-Coder-30B-A3B-Instruct 与单一 REPL scaffold 的 SWE-bench Verified、SWE-PolyBench Verified 设置中，相对该研究 base 的通过率提高 9.2 和 5.0 个百分点。它说明“何时折叠”和“折叠后怎样行动”也可能是策略的一部分，不代表所有模型或 Agent 都会得到相同收益。

这些研究回答的问题、分母和方法不同，数字不能合并成通用成绩。它们共同提醒：任务通过、约束保留、过程安全、来源可追溯和 token 成本应分别报告。

做对照时，尽量固定任务、模型 revision、提示和工具、workspace 初态、verifier 与成本预算，只改变待比较的折叠策略；同一任务应使用配对初态。若完整历史已经超出窗口，不能把它假装成可运行的基线，可以明确与截断、滚动窗口或可检索外置等实际方案对比。还要加入“工作方式规则只在初始消息出现，不能从文件恢复”的任务，否则评测会漏掉真实限制。报告每项观察的样本范围与分母；无法查明的结果保留 `unknown`，没有对应操作的指标标为不适用，不应并入总分或固定发布 gate。评估设计的统计方法可回到第七册。

## 18.13 折叠失败时，恢复来源并暂停危险动作

| 发现的问题 | 为什么会出错 | 恢复方式 |
|---|---|---|
| “不得修改测试”变成“尽量少动测试” | 否定约束被软化，模型得到不同授权 | 对照用户原文恢复规则；检查当前 diff；在确认前停止相关写入 |
| 假设被写成已验证根因 | 下一轮会略过仍需执行的验证 | 标明假设来源和状态，重新读取证据或运行所需检查 |
| 旧测试结果没有绑定 revision | 改过代码后可能误用过期结果 | 检查结果对应的 workspace 和配置；对新版本重跑受影响的验证 |
| `unknown` effect 被摘要成“已完成” | 恢复时可能重复提交或错误报告 | 查 effect ledger 和服务端；无查询合同则交人工对账 |
| 冲突事实被合并成单一结论 | 时间、来源或权限差异被抹掉 | 两条记录分别保留来源和时间，明确说明冲突并请求复核 |
| 来源引用失效或越权 | 摘要虽然有 ID，恢复者却无法验证原件 | 用有权限的恢复路径重新取回；无法取得时停止依赖该结论 |
| 折叠期间有新事件或新用户指令 | 新旧输入不一致，摘要可能覆盖更新状态 | 对照当前事件游标和用户消息重新生成折叠；提交时检查版本仍有效 |

验证失败时不要连续生成更长的摘要来遮住缺失。保留上一份有效工作状态，回读需要的原始事件或 artifact；若系统无法恢复约束、来源或副作用状态，就暂停自动动作，按任务风险请求用户输入或人工接手。暂停不会自动撤销已经派发的副作用，仍须按第十七章核查。

## 18.14 复述一次可靠折叠

读完后，应能拿一份折叠摘要回答：当前任务和有效约束是什么？哪些事实已验证、来自哪里、适用于哪个版本？哪些仍是假设或 `unknown`？下一步能做什么，做之前要查哪些外部事实？原始依据从哪里取回？

如果恢复者只会复述摘要，却无法指出测试结果绑定的 revision、用户批准的范围或未知 effect 的查询路径，那么这次折叠还没有交好任务。折叠的目标是让模型在较短输入下继续工作，同时让 Runtime 和人仍能从权威状态与来源核对它说的每一件重要事实。
