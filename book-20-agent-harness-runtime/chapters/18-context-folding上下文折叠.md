# 第 18 章 Context Folding：上下文变短以后，任务还剩下什么

## 18.1 上下文不够时，删掉最早消息并不等于压缩

一个 Agent 连续读取文件、调用工具和生成测试报告，很快会接近模型的 context limit。最简单的处理是删除最早的消息，但旧消息里可能包含任务约束、用户授权、关键证据和未完成动作。删除后模型仍然可以生成流畅文字，却可能忘记“只读”“不要修改测试”或“哪个结论还没有验证”。

Context folding 是把长历史转换成更紧凑、可继续执行的状态。它不是把所有文本做摘要，而是重新组织事实、证据、假设、决策、artifact 和待办事项，并保留能回到原文的引用。

## 18.2 先区分压缩对象

上下文里至少有四类东西：

- 约束：用户目标、权限、格式和不可做的事情；
- 事实：工具确认的文件、数字、时间和环境状态；
- 假设：尚未验证的根因、候选方案和置信度；
- 轨迹：工具调用、错误、测试和外部副作用。

它们不能用同一种摘要策略。约束丢失会造成安全问题，事实丢失会造成错误答案，假设丢失会让 Agent 重复探索，轨迹丢失会造成重复执行。

## 18.3 一个结构化折叠状态

可以把折叠后的状态写为：

```math
F(H)=\big(C,\,E,\,Q,\,A,\,P,\,R\big)
```

`H` 是原始历史，`C` 是约束，`E` 是已确认证据，`Q` 是未决问题，`A` 是 artifact，`P` 是 pending actions，`R` 是来源引用和恢复信息。

折叠不是要求 `F(H)` 逐字等价于 `H`，而是要求对后续任务足够充分。对于每条事实，保留 source id、时间和 revision；对于每条假设，保留验证状态；对于每个动作，保留 call id 和是否提交。

## 18.4 一个调试任务的折叠过程

原始历史里有几十轮：读取日志、搜索代码、运行失败测试、提出两个根因、修改一次 patch。折叠后可以保留：

```text
目标：修复发布后偶发 500，不修改测试。
已确认：revision r17 在 cache.py:81 出现并发访问；trace-42 显示 timeout=3s。
假设：刷新线程与读取线程存在竞态，尚未由并发测试确认。
已完成：候选 patch 存于 artifact patch-3，单元测试通过。
未完成：运行并发测试，检查回滚路径。
约束：只读生产日志；提交前需人工确认。
```

这比一段“我们怀疑缓存有问题，已经修复”的摘要更可靠。它区分了证据和假设，保留了下一步动作和安全约束。

## 18.5 信息保真与预算

压缩越激进，token 越少，但丢失重要信息的概率越高。可以把折叠质量看成一个受预算约束的优化问题：

```math
\min_F\;L_{\mathrm{context}}(F(H))
\quad\mathrm{s.t.}\quad
P(\mathrm{critical\ fact\ lost})<\delta
```

`L_context` 是折叠后占用的 token 或存储，关键事实丢失概率则通过回放任务测量。不同任务的 `\delta` 不同：闲聊可以允许更多摘要，生产变更和安全审计应更保守。

## 18.6 什么时候折叠

折叠触发可以来自 token 水位、工具结果累积、任务阶段变化或上下文中出现大量重复。不要等到超过限制后临时摘要；应在达到安全水位时进行，并把原始历史保存为可审计的冷数据。

折叠后的摘要要有版本和 checksum。若摘要生成失败，系统应暂停或切换到检索原始事件，而不是继续生成一个失去约束的答案。

## 18.7 与 RAG 和 memory 的边界

Context folding 是当前任务状态的压缩，RAG 是从外部数据中按问题检索证据，memory 是跨任务或跨会话保存的长期信息。三者都可能返回文本，但生命周期和可信度不同。

一条旧记忆“用户喜欢部署在周末”不能覆盖当前请求“今天立即发布”；一段折叠摘要“测试待运行”不能替代测试结果；RAG 返回的文档也不能自动变成系统指令。恢复时要保留来源和优先级，不能把三种内容混为一个长字符串。

## 18.8 可回溯的折叠

好的系统让每个摘要条目能回到原始事件。可以为摘要创建引用图：

```math
\mathrm{summary\ item}\rightarrow
\{\mathrm{event\ ids},\mathrm{artifact\ ids}\}
```

用户质疑“根因是什么”时，系统能展示对应日志和测试；模型需要重新核对时，可以按需读取原文，而不必把整个历史重新塞回 context。

## 18.9 评估折叠是否伤害任务

建立同一批任务的两个条件：完整历史和折叠历史。比较最终成功率、证据引用、约束遵守、恢复、重复工具调用和 token 成本。

重点测试边界情况：关键约束在最早消息、证据分散在中间、假设后来被推翻、外部动作已提交、权限在折叠后变化。平均答案质量不变并不代表安全没问题；一条被折叠掉的“不要提交”足以造成严重事故。

## 18.10 常见失败

只保留最近消息，丢掉长期约束；把模型生成的假设写成事实；摘要没有来源导致无法审计；把不同租户或不同任务的 memory 混入当前上下文；折叠时删掉工具 call id，恢复后重复调用；压缩结果不可版本化，无法定位质量回归。

## 18.11 面试回答与练习

回答“context folding 怎么做”时，应先分类约束、事实、假设、轨迹和 artifact，再为每类设计压缩和来源引用；在安全水位触发，保留原始事件和摘要版本；用完整历史与折叠历史的回放比较成功率、引用、约束遵守、成本和副作用。

练习一：给一个多轮代码任务写折叠后的 facts、hypotheses、open questions 和 pending effects。

练习二：说明 context folding、RAG 和长期 memory 的生命周期差异。

练习三：设计一个测试，专门检查折叠后“不要修改测试文件”的约束是否仍然有效。

### 18.11.1 折叠对象不是同一种信息

对话消息、事实、约束、假设、工具观察、失败轨迹、artifact 和待提交副作用的生命周期不同。可以压缩旧的闲聊和重复观察，却不能把“不要修改测试文件”与普通讨论一起摘要成一句模糊背景；可以把已经验证的日志聚合，却要保留来源 ID 和时间范围。

一种实用的折叠输出是：

```text
facts: verified values with source
constraints: must / must-not rules
hypotheses: pending explanations with confidence
decisions: accepted or rejected and why
artifacts: uri, checksum, revision
pending_effects: external actions and status
open_questions: unresolved items
```

### 18.11.2 折叠的触发和水位

折叠可以由 token 水位、KV 预算、任务阶段或人工触发。若只在达到硬上限后压缩，系统可能已经没有足够预算保存原始证据；若过早压缩，摘要本身会反复累积误差。应设安全水位，并保留最近一段原始事件和可检索的完整日志。

假设上下文预算为 `B`，当前使用 `u`，折叠成本为 `c_f`，安全水位为 `\rho B`，则可以在 `u>\rho B` 时启动，而不是等 `u=B`。`c_f` 也要计入延迟和单位任务成本。

### 18.11.3 provenance 和摘要验证

折叠后的每个事实都应指向原始事件，摘要应带版本和生成时间。可以抽样检查事实覆盖、约束覆盖、引用有效和冲突保留；若摘要说“测试通过”，但原始日志中只是某个子测试通过，就应判定为折叠错误。

对于高风险任务，原始事件不可被摘要替代。摘要可以作为模型上下文，最终审计仍需能回放原文、工具输出、权限决策和状态 diff。

### 18.11.4 worked example：折叠后的代码任务

原始历史包含用户约束、三次测试失败、两次错误 patch、一次成功测试和待提交 pull request。折叠后应保留“测试文件不可修改”、成功 patch 的基线和 checksum、失败原因的演化、当前测试结果、待审批动作；不必保留每次重复询问的寒暄。

如果把失败 patch 删除，模型可能再次走同一条路；如果把待审批动作摘要成“已完成”，恢复时会产生未经批准的提交。这就是为什么 context folding 必须和状态机、artifact 和权限一起设计。

## 18.12 折叠的损失函数

折叠不是单纯减少 token。它要在上下文成本、事实保真、可恢复性和引用完整之间取平衡：

~~~math
L_{\mathrm{fold}}
=\lambda_c C_{\mathrm{context}}
+\lambda_f E_{\mathrm{fact}}
+\lambda_p E_{\mathrm{provenance}}
+\lambda_s E_{\mathrm{state}}
~~~

高风险任务提高 provenance 和 state 权重，普通闲聊才可以接受更强摘要。不同折叠策略应在同一恢复任务上做对照。

## 18.13 折叠对象的类型系统

上下文中的消息、用户约束、已验证事实、模型假设、工具观察、失败轨迹、artifact 和待审批副作用不应被压成同一种摘要。每类对象有不同的保留、覆盖和删除规则。

可以把折叠条目写成：

~~~text
FoldItem {
  kind
  content
  source_event_ids
  priority
  status
  revision
  expires_at
}
~~~

恢复时按类型和优先级重建，而不是把所有字符串拼在一起。用户最新指令应覆盖旧偏好，工具事实不能自动升级为系统指令，假设必须保留不确定标记。

## 18.14 折叠质量的回放指标

折叠之后要在同一批任务上比较完整历史和折叠历史：任务成功率、约束遵守、事实召回、引用支持、重复工具调用、错误副作用、恢复时间和 token 成本。

可以定义关键事实覆盖率：

~~~math
R_{\mathrm{fact}}
=\frac{\#\{\text{折叠后仍可正确恢复的关键事实}\}}
{\#\{\text{关键事实总数}\}}
~~~

普通闲聊可以接受较低覆盖，高风险修改、发布和安全审计则应设置严格验收条件，并保留原始事件可回放。

## 18.15 触发、失败和恢复

折叠可以由 token 水位、工具日志、阶段切换、重复率或人工触发。折叠过程中若模型生成摘要失败，系统应暂停或回读原始事件，不能继续执行一个缺少约束的摘要。

摘要版本、checksum、生成模型和源事件 ID 要进入 trace。模型升级后重新折叠时，旧摘要不能与新策略无条件混用。

## 18.16 分层折叠流水线

折叠不应由一个提示词把几万条消息压成一段“请记住重点”。真实系统可以分四层处理：先按事件类型切分，再在每个类型内部去重和聚合，随后生成带来源的摘要，最后用独立检查器验证摘要没有改变约束和事实。

```text
raw events
  -> typed partition
  -> deduplication and aggregation
  -> fact/constraint/hypothesis summary
  -> provenance and contradiction check
  -> recovery context
```

第一层解决“哪些信息不应混在一起”，第二层减少重复日志，第三层才进行语言压缩。比如十次相同的编译警告可以聚合为一个带时间范围的 observation，但“测试文件不可修改”必须保留为独立 constraint。若先把所有内容混合，再让模型自己区分，摘要往往会把安全规则写成普通背景。

折叠还要预留回放窗口。上下文预算为 `B` 时，不能把 `B` 全部交给业务内容，应为新用户消息、工具结果和折叠失败留出容量：

```math
B_{mathrm{usable}}
=B-B_{mathrm{reserve}}-B_{mathrm{new\ input}}-B_{mathrm{fold\ overhead}}
```

`B_reserve` 太小，折叠刚完成就会再次触顶；太大则浪费可用上下文。高风险任务还可以固定保留最近的原始约束和最近一次外部副作用事件，不让它们进入不可逆摘要。

## 18.17 事实、约束与矛盾的合并规则

摘要最危险的错误不是漏掉一句闲聊，而是把互相冲突的事实合并成一个确定结论。折叠器应为每条记录保留来源、时间、状态和置信度，并定义冲突优先级：用户最新明确约束通常覆盖旧偏好；文件和工具的可验证结果优先于模型猜测；两个工具结果冲突时保留冲突并要求复查。

可以把一条折叠记录表示为：

```text
item = {
  kind: fact | constraint | hypothesis | observation | effect,
  value,
  source_event_ids,
  observed_at,
  status,
  confidence,
  supersedes,
  expires_at
}
```

`supersedes` 表示一条新事实替代了哪条旧事实，不能只把旧文本删除。比如第一轮日志显示“测试失败”，第二轮日志显示“修复后通过”；折叠结果应同时保存修复前后的 revision 和测试命令，而不是只写“测试通过”。这样恢复后的模型知道当前结论依赖哪个版本，也能在环境变化时重新验证。

对于约束，可以使用硬验收条件和软偏好两种类型。`must_not_modify_tests` 是硬性条件，摘要验证失败就不能继续写入；“优先使用简洁实现”是软偏好，资源不足时可以降级。把两者都写成“用户希望……”会导致高风险规则被普通语言风格稀释。

## 18.18 worked example：从 128K 压到 32K

假设一个代码任务的原始历史包含 80K token 的对话、35K token 的工具日志、10K token 的 patch 和 5K token 的系统元数据，总量为 130K，已超过服务可用的 128K。简单删除最早消息可能删掉用户的禁止事项；简单保留最后 32K 又可能只剩最后一次失败日志。

一个分层折叠结果可以是：

| 类别 | 原始量 | 折叠后 | 保留内容 |
| --- | ---: | ---: | --- |
| 硬约束 | 2K | 1K | 用户禁止修改的目录、发布条件 |
| 已验证事实 | 25K | 5K | 文件 revision、测试结果和来源 |
| 失败轨迹 | 35K | 4K | 每种根因一条代表性证据 |
| artifact | 10K | 2K | URI、checksum、diff 摘要 |
| 工具观察 | 35K | 6K | 未解决错误和最近状态 |
| 闲聊/重复 | 23K | 0.5K | 仅保留影响决策的偏好 |
| 最近原始窗口 | - | 10K | 最新请求和未完成事件 |

折叠后总量约为 28.5K，仍留有 3.5K 处理新输入和异常。关键不在于某个压缩比例，而在于每一类信息都有删除和保留理由。若“不要修改测试文件”找不到来源事件，折叠验收条件应失败，宁可重新读取原始日志，也不能输出一个看似完整的摘要。

## 18.19 摘要验证与回放

摘要验证可以分为三种测试。覆盖测试检查关键事实和硬约束是否仍存在；支持测试检查每个事实是否能回指原始事件；行为测试则把完整历史和折叠历史分别交给相同的 Agent，在隔离环境中比较最终动作。

可以定义折叠造成的约束损失：

```math
E_{\mathrm{constraint}}
=1-\frac{N_{\mathrm{constraints\ obeyed\ after\ folding}}
             {\max(1,N_{\mathrm{constraints\ tested}})}
```

对高风险任务，行为测试还要加入“摘要中明确写了不要做”的反例：模型收到一个看似合理的工具调用请求时，是否仍能拒绝；外部动作已经 `unknown` 时，是否先查询；workspace revision 变化时，是否避免覆盖。平均答案相似度很高，却在这些验收条件上失败，仍然说明折叠不合格。

折叠器自身也需要版本。trace 中记录原始事件范围、折叠算法、模型 revision、摘要 checksum 和验证结果。上线新折叠策略时，用同一批历史做 shadow replay，比较事实覆盖、约束遵守、token 成本、恢复时间和重复工具调用。这样可以定位回归来自摘要算法，而不是模型或工具变化。

## 18.20 失败时的回退和恢复

折叠过程可能因为上下文不足、摘要模型超时、来源日志不可读或事实冲突而失败。回退策略应按风险分层：普通问答可以减少最近窗口并提示用户补充；代码修改可以只保留已验证 artifact 并暂停写入；支付、删除、发布等动作应停止自动执行，要求人工确认或重新建立任务。

如果摘要已经生成但验证尚未完成，状态应是 `fold_pending`，不能直接作为新的事实源。验证通过后再写入 `fold_committed`；验证失败则保留原始历史和失败原因。新摘要替换旧摘要也要使用版本号和 compare-and-swap，避免两个并发折叠器互相覆盖。

## 18.21 折叠策略的选择顺序

上下文逼近上限时，不能直接把最早消息截掉。先移除重复的工具原文，保留引用和 hash；再把已验证事实、约束和未决问题结构化；最后才对仍然过长的历史做摘要。高风险动作前，优先保留权限、状态版本、失败原因和最近的证据，而不是保留模型的修辞性解释。

可以把每个上下文片段视为带价值和成本的对象：

```math
U_i=\frac{\mathrm{decision\ value}_i
\cdot\mathrm{freshness}_i
\cdot\mathrm{trust}_i}{\mathrm{tokens}_i}.
```

这不是让摘要器机械按分数排序，而是提醒我们：低成本的状态事实可能比高成本的长篇聊天更重要，过期或不可信内容即使很详细也不应占据预算。

## 18.22 折叠后的可逆性和人工检查点

对普通问答，摘要丢失少量措辞可能可以接受；对代码修改、财务审批和安全事件，必须能回到原始证据。系统可保存摘要、输入片段 hash、来源位置和压缩版本，在发生争议时按权限回读原文。摘要本身不能拥有比原文更高的可信等级。

当折叠发现事实冲突、权限变化或工具结果未知，应创建人工检查点，而不是继续压缩直到冲突消失。把冲突压平会让模型在恢复后得到一个看似一致、实际错误的世界。

## 18.23 折叠的发布条件

发布前用未折叠上下文作为基线，比较折叠后事实问答、引用、工具选择、代码 patch、恢复和安全拒答。至少报告关键信息保留率、幻觉新增率、token 节省、p95、恢复成功率和人工接管率。若平均问答分不变但高风险动作错误增加，折叠仍不能上线。

## 18.24 折叠摘要的最小 schema

摘要至少应区分已确认事实、用户约束、工具 observation、未决问题、冲突、artifact 引用、权限和下一步候选。每条事实带来源和时间，不能把模型推断混进事实列表。恢复器可以按任务需要读取原文，而不是把一份没有 provenance 的长摘要当作真相。

## 18.25 压缩失败时的回退

若摘要验证失败、关键引用丢失、冲突无法合并或剩余预算不足，系统应扩大上下文、检索原文、转异步或人工接管。继续生成更长摘要并不能修复缺失证据；回退动作要记录丢失范围和成本。

## 18.26 上下文折叠的阶段性判断与资料边界

Context folding 的目标不是让历史看起来更短，而是以更少 token 保留继续执行所需的约束、证据、假设和副作用状态。任何折叠都应分层处理、保留来源、显式表示矛盾、可回溯、可版本化，并通过中断和安全回放。折叠失败时，系统必须知道该降级、重读原文还是停止副作用。

本章的状态压缩、摘要引用和上下文管理是通用架构方法；具体 harness 如何实现 context compaction、summary item 或 hidden state，需要以其公开文档和版本实现为准。
