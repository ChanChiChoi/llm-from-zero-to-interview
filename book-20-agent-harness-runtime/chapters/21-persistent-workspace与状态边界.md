# 第 21 章 Persistent Workspace：任务文件与外部事实的边界

昨天，Agent 在 task-42 中读取了 src/parser.py 的版本 r17，生成了一个尚未验证的 patch-41。任务暂停期间，用户又在 IDE 里改了同一个函数，工作区变成 r18。今天恢复时，模型上下文仍写着“patch 已准备好”。这句话能证明当前文件还是昨天的版本吗？不能。它只说明模型曾经这样描述过；当前文件要从工作区读取，测试结果要从执行测试的系统读取。

这一章要解决的就是长任务交接时的事实归属：对话记录、模型记忆、任务检查点、文件、测试结果和外部服务各自能证明什么。恢复任务时，先找对事实来源，再决定旧结果能否继续使用。

## 21.1 不同状态，各有自己的事实来源

“Agent 记住了”可能指模型输入中还带着旧对话，也可能指应用保存了摘要、任务进度、文件，或外部系统中的结果。这些状态彼此相关，却不能互相代替。

| 状态 | 通常保存什么 | 它能证明什么 | 恢复时应查哪里 |
| --- | --- | --- | --- |
| 模型上下文与对话记录 | 当前传给模型的消息、工具结果或摘要 | 模型本轮实际看到了什么 | 本轮请求和保留的对话记录 |
| 长期记忆或检索视图 | 从历史任务或文件整理出的摘要、索引 | 有哪些线索值得回查 | 原始文件、来源版本及记忆记录的更新时间 |
| 任务检查点 | 任务阶段、待办、已记录的动作结果和恢复位置 | 编排器认为任务进行到哪里 | 检查点及其关联的工具或服务回执 |
| Workspace | 文件、目录、分支或快照 | 某个工作区当前有哪些文件内容 | 实际工作目录及其当前 revision |
| 测试或后台任务服务 | CI、构建、测试等任务的运行状态和结果 | 指定任务是否结束，以及该次运行报告了什么 | 执行器中的 job 和结果记录 |
| 外部业务系统 | 工单、数据库、云资源或部署状态 | 该系统当前记录的业务事实 | 对应服务的查询接口或审计记录 |

每种状态只对自己拥有的事实负责。检查点写着“集成测试待运行”，不能替代 CI 的实际结果；模型摘要写着“修复完成”，不能证明文件已经改好；工作区里有部署配置，也不能证明生产环境已经部署。系统不需要争出一个覆盖所有事实的“最高优先级”，而要在每次判断时找出负责该事实的来源。

这里的“模型记忆”是应用额外保存、供后续检索的内容，不等于模型权重里永久存入了这项任务。摘要和索引能帮系统找到线索，但可能过期；重要结论要回到其来源核对。

## 21.2 一轮会话不等于一个工作区

会话是模型交互的记录；工作区是工具读写文件和运行命令的环境。它们可以绑定，也可以分别创建和恢复。一个模型会话结束，不会自动删除或保存文件；恢复了对话，也不保证原来的运行环境、进程或依赖仍在。

OpenAI Agents API 的预热环境文档把 environment 描述为工具运行的 workspace，把 session 描述为 Agent 配置和 conversation。多个 session 可以附着到同一个 environment，共享其中的文件、进程、已安装包和环境配置，但各自保留独立的对话历史。这说明共享工作区和共享对话是两种不同设置；这是该 API 的具体合同，不是所有 Agent 产品的通用规则。[官方文档](https://developers.openai.com/api/docs/guides/agents-api/environments/prewarmed)

产品的恢复期限也必须按具体功能理解。比如，Codex Cloud 帮助文档说明每个 task 使用独立 workspace，同一 task 可以继续；保存的 VM 状态从最近一次启动或恢复起最多有 7 天的恢复窗口。文档同时说明，这个窗口不是对话历史保留期限。[Codex Cloud 文档](https://help.openai.com/en/articles/20001545-using-codex-cloud) 这个例子不能推导出其他产品也保存七天，也不能把 VM、workspace 和 conversation 视作同一份数据。

## 21.3 Git 展示了“当前文件”可能有几个版本

以 Git 为例，HEAD 指向当前检出的提交；index（暂存区）记录下一次提交准备包含的内容；working tree（工作树）是磁盘上的实际文件，可能包含还未暂存或提交的改动。执行 git add 后再编辑同一个文件，工作树会继续变化，而 index 仍保留上一次暂存的内容。git diff --cached 比较 HEAD 与 index，git diff 比较 index 与工作树。[Git 用户手册](https://git-scm.com/docs/user-manual.html) [Pro Git：Recording Changes](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)

因此，“代码已提交”只说明某个提交快照已进入历史；它不代表当前工作树没有其他改动。恢复 Agent 任务时，提交号、暂存内容和磁盘文件可能对应不同状态。Git 的 linked worktree 还允许同一仓库连接多个工作目录，各自拥有 HEAD 和 index 等工作区状态，同时共享仓库对象数据。[git-worktree 文档](https://git-scm.com/docs/git-worktree) 仓库相同，不等于工作目录相同，更不等于模型对话相同。

MIT Missing Semester 的 2026 Git 讲义也从“下一份快照应包含哪些改动”引出 staging area，再介绍相关命令；这是一个把快照概念接到操作的课程组织样本，不是对某种讲法效果的实验结论。[课程讲义](https://missing.csail.mit.edu/2026/version-control/)

## 21.4 派生检索视图也要说明它依据哪个文件版本

有些工作区会把 PDF、表格或文档解析成可搜索的文本和索引。解析视图便于查找，原始文件则保留版式、公式或可执行内容。文件修改后，如果索引仍指向旧文件，Agent 就可能根据旧数据作答，却在新文件上提交修改。

2026 年的 StagedWorkspace 预印本提出一种版本绑定做法：解析记录带有源路径和内容 hash；若源文件的 hash 已变化，旧记录会被标为 stale，待重新解析后再作为当前视图使用。该研究在固定 harness 下比较了不同文件视图和差异审阅方式，但只覆盖所选模型、系统和两个 benchmark；它提供的是一种设计实例，不是通用标准或普遍效果保证。[StagedWorkspace](https://arxiv.org/abs/2608.18050)

hash 能帮助判断内容是否仍与某个文件版本一致，却不能证明文件含义正确。可搜索的解析文本、实际编辑的原文件、展示给人的 diff 和最终提交的 artifact，应尽可能指向同一版本；如果它们暂时不同，就要显示差异和新鲜度，不能让读者误以为它们描述同一状态。

## 21.5 用 task-42 复走一次中断后的恢复

回到开头的合成例子。Agent 基于 r17 生成 patch-41，尚未运行测试。暂停期间，用户把同一函数改到 r18。恢复时，编排器需要把检查点中的基线 r17 与工作区当前版本 r18 对上。发现不一致后，patch-41 仍可作为候选保留，但不能当成已应用、已验证的当前文件。

接下来先比较用户改动和候选 patch：若两者修改同一处，就保留两边的内容并处理冲突；若改动位置不同，也要判断用户修改是否影响相关接口、配置或测试。合并或重做后得到新的候选版本 r19，再在与任务相关的范围内验证 r19。昨天即使有一份针对 r17 的测试报告，它也不能直接证明 r19 正确，因为测试对象已经改变。精确的文件 patch、diff 和冲突处理见[第五章](05-文件系统与代码编辑.md)；检查点和任务副作用的恢复责任见[第十七章](17-long-running-agent与checkpoint.md)。

有关用户在 Agent 运行中改动代码的受控研究，也把“与任务冲突的修改”和“方向一致的修改”分开评估。它提示系统不能把任何外部变更都判成同一种冲突；仍须检查改动内容是否改变任务要求，并在新状态上验证。该研究使用的是模拟的、定向注入的编辑，不能代表真实协作修改的全部情况。[SWE-Touch 预印本](https://arxiv.org/abs/2608.02499)

如果任务已经触及数据库、工单或部署系统，本地工作区只能保存相关引用和观察结果，不能替这些系统确认状态。恢复时要查询对应服务，特别是曾经提交但回执不明的动作；具体的 unknown、重试和副作用核验路径见第十七章。

## 21.6 交付 artifact 时，把证据和版本一起交出去

任务结束时，用户需要的不只是“完成了”，还要能知道交付物来自哪个工作区版本、经过什么检查、目前处于什么状态。一次交接可以包含：

| 交接信息 | 读者用它判断什么 |
| --- | --- |
| task 与 workspace 身份、来源 revision | 结果属于哪个任务、基于哪个文件状态 |
| 修改文件或 artifact，以及 diff/hash | 哪些内容改变了，交付物是否仍是同一份内容 |
| 生成者、时间和必要的工具链信息 | 结果从哪里产生，环境是否影响复核 |
| 检查名称、运行环境、目标 revision 和结果 | 哪些验证确实针对交付的版本 |
| 当前状态及未解决事项 | 这是候选、已复核、已提交，还是仍有未知结果 |

这张表是帮助读者看清交接证据的示例，不要求所有系统实现同一份固定 manifest。关键是测试报告要对应明确的 revision，交付状态要说明是否已经合并或被外部系统接受。CI 的通过状态可以支持“该次 CI 对某版本报告通过”，不能单独证明业务需求全部满足；整体验收与评测口径见[第十章](10-evaluation-harness.md)和[第十九章](19-harness-aware-evaluation.md)。

## 21.7 权限、租户与保留期限也是状态边界的一部分

能写临时工作区，不代表有权修改生产数据库；能访问一个项目目录，也不代表能读取其他租户的文件。权限要落在实际读写和外部提交动作上，工作区隔离本身不能替代授权策略。具体权限、确认和沙箱边界见[第八章](08-权限模型与安全沙箱.md)。

持久状态还可能包括派生索引、摘要、日志、备份和外部 artifact。删除一段对话，不一定同时删除这些对象；保留期限和删除承诺应按产品及其数据类别核对，不能从“workspace 可恢复”推断“所有副本会永久保留”，也不能反向推断对话删除会清除已经提交的外部记录。若 Agent 使用检索记忆，记录来源和更新时间能帮助判断它是否过期；涉及隐私和跨租户读取时，应按第八章的安全边界处理。

## 21.8 恢复任务时，先核对来源再继续动作

面对一个中断任务，可以依次问：

1. 我需要确认的是模型看过什么、文件现在是什么、检查点走到哪里，还是外部服务发生了什么？
2. 这条记录来自权威来源，还是模型摘要、缓存或派生索引？
3. 文件和验证结果分别对应哪个 revision？来源变化后，旧结果还适用吗？
4. 是否存在未确认的外部动作？应该查哪个服务的回执或当前状态？
5. 我交付的是候选 artifact 还是已验证结果？验证针对的是哪一版？

这样，模型换了、上下文折叠了或工作进程重启了，任务仍可通过各自的持久事实继续；而摘要、索引或旧测试结果不会被误当成当前文件和外部系统的事实。上下文折叠怎样保留必要线索见[第十八章](18-context-folding上下文折叠.md)。
