# 第七章：分布式训练：把一次更新放到多张设备上

## 7.0 一次更新为什么会变成一个系统问题

单卡训练时，读者可以把一次更新想象成：

~~~text
读取一个 batch
  -> forward
  -> loss
  -> backward
  -> optimizer.step()
~~~

当模型和数据分布到多张 GPU 后，这条链会变成：

~~~text
rank 读取自己的数据 shard
  -> 局部 forward/backward
  -> rank 之间交换梯度、参数、激活或 token
  -> 得到全局一致或分片的更新
  -> 保存与恢复分布式状态
~~~

分布式训练的核心不是“把 GPU 数量乘大”，而是回答四个问题：

1. 什么被复制，什么被切分？
2. 每张设备在什么时候需要别的设备的数据？
3. 这些数据通过哪一种 collective communication 交换？
4. 通信、计算、显存和故障恢复的代价是否值得？

初学者可以先记住这些切分对象：

| 并行方式 | 主要切分对象 | 典型收益 | 主要代价 |
| --- | --- | --- | --- |
| Data Parallel | 样本或 batch | 增加吞吐和 global batch | 梯度同步 |
| ZeRO/FSDP | 参数、梯度、optimizer state | 降低单卡常驻显存 | 参数和梯度通信 |
| Tensor Parallel | 层内矩阵或 hidden 维度 | 让单层跨设备计算 | 高频层内通信 |
| Pipeline Parallel | 模型层 | 让深模型分布到多个 stage | 空泡、激活传递和调度 |
| Sequence Parallel | 序列方向的激活 | 降低逐 token 激活显存 | 序列布局通信 |
| Context Parallel | 长上下文 token 区间 | 分摊长序列 attention | 跨区间 K/V 或 attention 通信 |
| Expert Parallel | MoE expert 和路由 token | 分摊专家计算和参数 | all-to-all 与负载不均 |

本章先从 rank 和一次 distributed update 建立共同语言，再分别展开 DDP、ZeRO/FSDP、TP、PP、SP/CP、EP 和混合并行。最后把通信、显存、流水线空泡、checkpoint 和故障恢复放在同一个资源账本中。

## 7.1 分布式训练的基本对象

### 7.1.1 world、rank 和 local rank

一个分布式作业通常有：

- world size：所有进程或 rank 的总数；
- rank：某个进程在全局进程组中的编号；
- local rank：某个进程在当前节点上的编号；
- node：承载一组设备的机器；
- process group：参与某种 collective 的 rank 子集。

例如，4 台机器各有 8 张 GPU：

~~~text
world_size = 32
node_0 local_rank = 0..7
node_1 local_rank = 0..7
global rank = 0..31
~~~

local rank 只表示当前机器内的设备位置，不能拿它代替 global rank。一个 TP group、PP group 或 DP group 通常只包含 world 中的一部分 rank；同一个 rank 可以同时属于多个正交的 process group。

### 7.1.2 为什么要显式建立 process group

假设 16 张 GPU 被组织成：

~~~text
DP = 4
TP = 2
PP = 2
DP * TP * PP = 16
~~~

一个 rank 可能同时参与：

- 同一 TP 组内的层内 all-reduce；
- 同一 PP 相邻 stage 之间的 send/recv；
- 同一 DP 复制组内的梯度 reduce；
- 训练控制面上的全局 broadcast。

如果把所有通信都错误地发到 default world group，通信量会增加，甚至会因为不同 rank 的调用顺序不同而死锁。并行设计不仅是切分公式，也包括 rank mapping 和通信组的定义。

### 7.1.3 一次更新的全局时间线

一次数据并行更新可以抽象为：

~~~text
每个 rank:
  1. 取本地 micro-batch
  2. 计算 local loss 和 local gradient
  3. 按有效 token 数形成局部统计
  4. 对梯度或统计量做 collective
  5. 得到全局梯度或本 rank 的 shard
  6. 执行 optimizer update
  7. 推进 scheduler 和 data cursor
~~~

在 TP、PP、FSDP 或 MoE 中，步骤 2 到 5 还会插入参数 all-gather、激活 send/recv、token all-to-all 或 reduce-scatter。要排查性能问题，必须把时间拆到这些事件，而不能只记录一个 step time。

## 7.2 全局 batch 的正确分母

### 7.2.1 样本 batch 与 token batch

在等长样本下，数据并行的样本 batch 可以写成：

~~~math
B_{\mathrm{sample}}
=
B_{\mathrm{micro}}
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

其中 B_micro 是每个 DP rank 每个 micro-step 的样本数，A 是 accumulation 次数，N_dp 是 data parallel group 的大小。

对语言模型更重要的是有效 token：

~~~math
B_{\mathrm{token}}
=
\sum_{r=1}^{N_{\mathrm{dp}}}
\sum_{a=1}^{A}
N_{\mathrm{valid}}(r,a)
~~~

等长、无 padding 时才可以简化为：

~~~math
B_{\mathrm{token}}
=
B_{\mathrm{micro}}
\cdot
T
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

如果数据使用 packing、动态 padding 或 assistant-only label mask，就必须用真实有效 token 计数。只记录每卡样本数，会把不同实验的有效训练量混在一起。

这里的 N_valid(r,a) 是非负整数，而总和必须大于零才构成一次有监督的更新。某个 rank 的局部有效 token 可以是 0，但所有 rank 与所有累积 micro-step 都为 0 时，B_token 和后续的 loss/gradient 平均没有定义；不能把分母替换成 1 后把这次窗口记成正常训练。

### 7.2.2 不等长 rank 的 loss 归一化

假设第 r 个 rank 的有效 token 数是 n_r，未归一化损失是 s_r。全局 token-level loss 应为：

~~~math
L_{\mathrm{global}}
=
\frac{\sum_r s_r}{\sum_r n_r}
~~~

相应的全局梯度是各 rank 未归一化梯度的加权和：

~~~math
g_{\mathrm{global}}
=
\frac{\sum_r G_r}{\sum_r n_r}
~~~

如果每个 rank 先把自己的 loss 除以 n_r，再对 rank mean 做简单平均，得到的是：

~~~math
\frac{1}{N_{\mathrm{dp}}}
\sum_r \frac{G_r}{n_r}
~~~

它会让短 batch 和长 batch 在 rank 层面权重相同。只有所有 n_r 相等时，这才与 token-level 目标一致。分布式训练框架的 loss reduction 语义必须核对，不能看到 all-reduce 就假设分母正确。

这两个全局公式要求 n_r>=0 且 sum_r n_r>0，并要求 G_r 是与未归一化损失 s_r 同一 token 口径下累加的梯度。若局部 loss 已经先除以 n_r，或框架已经做了 rank mean，再把它们按本式求和会产生二次归一化；先确定张量里保存的是 sum、mean 还是已缩放的 gradient，才谈 collective。

### 7.2.3 accumulation 和 DP 的组合

梯度累积时，局部梯度、DP 同步和有效 token 分母有多个实现顺序：

1. 每个 micro-step 先 all-reduce，再在本地累积；
2. 每个 rank 先累积未归一化统计，再在窗口末尾同步；
3. 使用 no_sync 暂缓部分梯度通信，最后一次统一同步。

它们的通信量和数值路径不同。使用 no_sync 时，不能忘记最后一个 micro-step 必须执行同步；最后一个不完整 accumulation window 也必须使用实际 token 数。

## 7.3 Data Parallelism：复制模型，切分数据

### 7.3.1 DDP 的数据流

最直观的 data parallel 是每个 DP rank 持有完整模型副本：

~~~text
rank 0: full model + batch shard 0
rank 1: full model + batch shard 1
rank 2: full model + batch shard 2
rank 3: full model + batch shard 3
~~~

每个 rank 独立执行 forward 和 backward，然后通过 all-reduce 或等价 collective 让梯度一致。若 optimizer、参数初始值和更新顺序一致，各 rank 在同步后会保持相同参数。

设第 r 个 rank 的局部梯度为 g_r，等权且等 token 时，同步后的梯度是：

~~~math
\bar g
=
\frac{1}{N_{\mathrm{dp}}}
\sum_{r=1}^{N_{\mathrm{dp}}}
g_r
~~~

这里 N_dp 是正整数，所有 g_r 的 shape、dtype、语义和 collective 顺序必须一致。只有各 rank 的有效 token 相同，简单除以 N_dp 才与 7.2 的 token-weighted 全局梯度一致；变长 batch 应同步未归一化统计与 token count，或采用等价的预缩放协议。

### 7.3.2 数据 shard 不是简单切数组

数据并行需要保证：

- 不同 rank 尽量读取不重叠样本；
- 每个 epoch 的 shuffle 可复现；
- drop_last 或补齐规则一致；
- 所有 rank 的 collective 调用次数一致；
- 恢复时能够定位到每个 rank 的 data cursor。

如果某个 rank 比其他 rank 少一个 batch，它可能提前结束 dataloader，而其他 rank 继续进入 all-reduce，最终表现为整个作业 hang。分布式 sampler 的长度和 padding 规则是训练正确性的一部分。

### 7.3.3 DDP 的优势与边界

DDP 的优势是实现直观、工具成熟、计算和通信边界清楚。它适合完整模型和 optimizer state 能够放进单卡的场景。

它的边界也很明确：

1. 每个 rank 都需要完整参数；
2. 每个 rank 通常都需要完整梯度；
3. 每个 rank 通常都需要完整 optimizer state；
4. 每次更新需要同步梯度；
5. 单卡放不下模型时，DDP 无法单独解决问题。

所以“增加 GPU 后吞吐提高”与“模型能否装下”是两个不同问题。DDP 主要解决前者。

## 7.4 Collective communication：设备如何交换数据

### 7.4.1 All-reduce

all-reduce 把所有 rank 的输入聚合，并把结果返回给所有 rank。对求和形式：

~~~math
y_r
=
\sum_{q=1}^{N}
x_q
\qquad
\text{for every }r
~~~

DDP 常用它同步梯度。之后可以再除以 rank 数得到平均梯度。

### 7.4.2 Reduce-scatter

reduce-scatter 先对各 rank 的对应分片求和，再把不同分片分发给不同 rank：

~~~text
每个 rank 有完整或分片输入
  -> 对每个位置求和
  -> 每个 rank 只接收一个结果 shard
~~~

ZeRO/FSDP 可以使用它让每个 rank 只保留自己的梯度分片，从而减少常驻显存。

### 7.4.3 All-gather

all-gather 把每个 rank 的 shard 收集并让所有 rank 得到完整集合。FSDP 在计算某个 wrapped module 前，可能需要把参数 shard all-gather 成完整参数。

all-gather 的结果不只会增加通信时间，还可能制造暂时的显存峰值。分析 FSDP OOM 时，不能只看稳态参数 shard，还要看某层 all-gather 时的 transient memory。

### 7.4.4 All-to-all

all-to-all 让每个 rank 给其他 rank 发送不同数据，并同时接收来自其他 rank 的数据。MoE token dispatch 是典型场景：

~~~text
router 产生 token -> expert id
  -> 按目标 expert 所在 rank 分桶
  -> all-to-all 发送 token hidden states
  -> 本地 expert 计算
  -> all-to-all 发送结果回原 token 所在 rank
~~~

all-to-all 的负载不仅由总字节数决定，还由路由偏斜、消息数量、分桶和拓扑决定。

### 7.4.5 Broadcast、send/recv 和 barrier

- broadcast：一个 rank 把对象或张量发送给组内所有 rank；
- send/recv：指定发送方和接收方，流水线 stage 常用；
- barrier：等待所有 rank 到达某个同步点。

barrier 本身通常不是计算通信的主要数据路径，却很容易掩盖真正的慢 rank。生产代码不能滥用 barrier 来“修复”竞态，否则会把性能问题变成更长的等待。

### 7.4.6 Ring all-reduce 的量级

令每个 rank 要同步的梯度 payload 大小为 S，ring all-reduce 的单 rank 发送/接收量可粗略写成：

~~~math
C_{\mathrm{ring}}
\approx
2\frac{N-1}{N}S
~~~

这是传输量模型，不包含启动延迟、协议开销、链路争用和实际拓扑。它能帮助比较 rank 数变化的量级，不能直接当成 step time。

### 7.4.7 alpha-beta 通信模型

一个更完整的粗略模型是：

~~~math
T_{\mathrm{comm}}
\approx
\alpha n_{\mathrm{msg}}
+
\frac{\beta B_{\mathrm{bytes}}}{\mathrm{link\ bandwidth}}
~~~

alpha 表示每条消息的启动和同步开销，n_msg 是消息或 collective 分片数量，beta 是协议效率相关因子。小消息很多时，第一项可能占主导；大 payload 在跨节点链路上则通常受带宽限制。

为避免量纲混淆，也可把 beta 写成无量纲的效率损失因子 eta_protocol>=1：传输项就是 eta_protocol B_bytes / bandwidth。无论采用哪种写法，alpha>=0、n_msg 为非负整数、B_bytes>=0 且有效带宽大于 0；模型只能用于比较量级，不能把测不出的协议效率当作固定常数。

## 7.5 训练状态显存：DDP、ZeRO 和 FSDP

### 7.5.1 DDP 的常驻状态

设参数量为 P，参数、梯度和 optimizer state 每元素字节数分别为 b_w、b_g、b_o。忽略激活和临时 buffer，DDP 单卡常驻训练状态约为：

~~~math
M_{\mathrm{DDP}}
\approx
P(b_w+b_g+b_o)
~~~

如果 AdamW 的一阶和二阶状态均为 FP32，则 b_o 约为 8 字节；如果还有 FP32 master weights，需要把它们单独加入。这个公式不能代表峰值显存，因为 forward/backward 还会产生激活和工作区。

以下 ZeRO 量级式假设 P>0、各字节数非负、N_dp 为正整数，且参数、梯度和状态在 DP rank 间均匀分片。padding、参数扁平化、通信 bucket、all-gather 和 allocator 保留都会使真实峰值偏离这个稳态估计。

### 7.5.2 ZeRO-1

ZeRO-1 只切分 optimizer state。假设 DP group 有 N_dp 个 rank：

~~~math
M_{\mathrm{ZeRO1}}
\approx
P(b_w+b_g)
+
\frac{Pb_o}{N_{\mathrm{dp}}}
~~~

参数和梯度仍然在每个 rank 上复制。它通常是从 DDP 迁移时相对容易理解的一步。

### 7.5.3 ZeRO-2

ZeRO-2 继续切分 gradient：

~~~math
M_{\mathrm{ZeRO2}}
\approx
Pb_w
+
\frac{P(b_g+b_o)}{N_{\mathrm{dp}}}
~~~

梯度 reduce-scatter 后，每个 rank 只保留自己负责的 shard。参数仍然是完整副本，因此对“参数本身放不下”的模型，ZeRO-2 仍可能不够。

### 7.5.4 ZeRO-3

ZeRO-3 进一步切分参数：

~~~math
M_{\mathrm{ZeRO3}}
\approx
\frac{P(b_w+b_g+b_o)}{N_{\mathrm{dp}}}
~~~

这是一种稳态量级。forward 或 backward 计算某个模块时，rank 可能需要 all-gather 当前模块的完整参数；计算完成后再 reshard 或释放。因此显存收益和通信代价必须一起理解。

### 7.5.5 FSDP 的模块生命周期

FSDP 的一个 wrapped module 可以抽象成：

~~~text
常态：本 rank 保存 parameter shard
  -> pre-forward all-gather
  -> 用完整参数执行 forward
  -> 按策略释放或 reshard
  -> backward 前再次 all-gather
  -> 计算梯度
  -> reduce-scatter 得到 gradient shard
  -> optimizer 只更新本 rank 的状态
~~~

实际实现会根据 forward_prefetch、reshard_after_forward、mixed precision、wrap policy 和 backward 顺序变化。这里最重要的不是记一个 API 参数，而是理解完整参数只在局部时间窗口出现。

### 7.5.6 Wrap 粒度的取舍

wrap 粒度太细：

- all-gather 次数变多；
- 小通信消息增加；
- kernel 和 collective 更难重叠。

wrap 粒度太粗：

- 一次 all-gather 的参数更多；
- 峰值显存变高；
- 释放时机更晚。

因此 FSDP 的性能和显存不是只由“是否使用 FSDP”决定，还由模块边界和实际张量形状决定。

### 7.5.7 Offload 与分片不是一回事

CPU offload 或 NVMe offload 把参数、梯度或 optimizer state 移到其他介质；ZeRO/FSDP shard 则改变每个 rank 保存的份额。一个系统可以同时使用分片和 offload，但报告显存时应区分：

| 现象 | 需要报告什么 |
| --- | --- |
| 单卡 GPU 峰值下降 | GPU memory peak |
| 总设备内存增加 | CPU/NVMe usage |
| 计算等待数据 | PCIe/NVLink/网络传输时间 |
| 稳态显存下降但峰值未降 | transient all-gather peak |

## 7.6 Tensor Parallelism：切分层内矩阵

### 7.6.1 列切分线性层

考虑线性层：

~~~math
Y=XW
~~~

若把输出维度切成 N_tp 份：

~~~math
W
=
[W_1,W_2,\ldots,W_{N_{\mathrm{tp}}}]
~~~

每个 TP rank 计算：

~~~math
Y_i
=
XW_i
~~~

最后按最后一维拼接 Y_i。这种切分适合产生独立输出分片的矩阵乘法。

若 W 的输出维度不能被 N_tp 整除，实现必须明确采用不等分 shard 或 padding；不能在每个 rank 假设同形状的 W_i。X 的最后一维、W 的输入维度和 batch/sequence 前缀维也必须相容，才有 Y=XW 这一步。

### 7.6.2 行切分线性层

若输入维度被切分：

~~~math
W
=
\begin{bmatrix}
W_1\\
W_2\\
\vdots\\
W_{N_{\mathrm{tp}}}
\end{bmatrix},
\qquad
X=[X_1,X_2,\ldots,X_{N_{\mathrm{tp}}}]
~~~

则：

~~~math
Y
=
\sum_{i=1}^{N_{\mathrm{tp}}}X_iW_i
~~~

不同 TP rank 需要对局部结果求和，通常需要 all-reduce 或 reduce-scatter。因而矩阵切分不是“每张卡各算一块就结束”，输出布局决定了下一次通信。

这里要求输入维度同样可按 N_tp 分配，或使用经过明确 padding 的布局。rank 间局部结果的 shape 和累加 dtype 必须一致；否则 collective 即使没有报错，也可能把不同坐标相加。

### 7.6.3 Attention 中的 TP

多头 attention 可以沿 head 维分给不同 rank。每个 rank 计算一部分 Q、K、V 和 attention heads，再根据输出 projection 的布局进行拼接或归约。

TP 的收益来自：

- 单层矩阵参数和计算分摊；
- 每张卡处理更小的 hidden 维度；
- 让单层超过单卡容量的模型可以执行。

TP 的代价来自：

- 每层或每个 block 的 collective；
- TP group 内部需要高带宽、低延迟互连；
- TP degree 增大后，局部矩阵变小，kernel 效率可能下降。

### 7.6.4 词表和 embedding 的特殊情况

大词表 embedding 和 lm head 也可以做 vocabulary parallel。输入 token id 只对应某个词表分片时，需要处理局部 lookup、mask 和输出 logits 的聚合。最后的 cross entropy 如果只需要真实 token 的 logit，可能使用更节省通信的并行损失实现；如果需要完整 logits，则通信量更大。

因此，TP 设计不能只看 Transformer block，还要检查 embedding、输出 head、loss 和权重共享是否保持了正确布局。

### 7.6.5 TP 的拓扑边界

TP 通信通常发生在每个 layer 或 block 内，频率高而消息模式稳定。把 TP group 放在同一节点的 NVLink 或同等级高速互连上，通常更有利；跨节点 TP 会把大量层内通信压到网络上，只有在网络带宽、拓扑和 kernel 足够匹配时才值得。

## 7.7 Pipeline Parallelism：切分模型层

### 7.7.1 Stage 和 micro-batch

Pipeline Parallel 将模型层划分到 N_pp 个 stage：

~~~text
stage 0: embedding + early blocks
stage 1: middle blocks
stage 2: later blocks
stage 3: final blocks + loss
~~~

一个 global batch 会被拆成多个 micro-batch。第一个 micro-batch 完成 stage 0 的 forward 后，把 activation 发送给 stage 1；同时 stage 0 可以开始下一个 micro-batch。

### 7.7.2 Pipeline bubble

当流水线启动和排空时，部分 stage 没有可计算的 micro-batch，形成 bubble。对简单的 p stage、m 个 micro-batch 的 schedule，一个常见量级模型是：

~~~math
r_{\mathrm{bubble}}
\approx
\frac{p-1}{m+p-1}
~~~

这个比例依赖具体的 1F1B、深度优先、交错或其他 schedule。公式表达的直觉是：micro-batch 数越多，启动/排空开销在总工作中的比例越低。

该近似要求 p>=1、m>=1 的整数；p=1 时没有 pipeline bubble，m=0 则没有可调度的训练工作。它假定各 stage 时间近似均衡，不能替代包含不均衡 stage、通信和交错 schedule 的 trace。

### 7.7.3 为什么不能无限增加 micro-batch

更多 micro-batch 可以降低 bubble，但会增加：

- micro-batch 调度和通信事件；
- backward 前需要保留的 activation 数；
- 梯度累积和 loss 归一化复杂度；
- 可能的 kernel 小批量效率损失。

实际选择要同时看 bubble、activation memory、tokens/sec 和 global batch。

### 7.7.4 1F1B 的基本思路

1F1B 表示 one forward followed by one backward。流水线进入稳态后，一个 stage 交替处理 forward 和 backward，尽量减少 activation 的长期驻留。

训练中的 backward 依赖后一个 stage 传回的梯度；stage 之间既要传 activation，也要传 activation gradient。send/recv 的顺序、micro-batch id 和异常处理必须一致，否则某个 rank 可能等待永远不会到来的张量。

### 7.7.5 Stage 划分不均

如果某个 stage 的层计算更重、参数更多或 activation 更大，整个 pipeline 的速度由最慢 stage 决定。平均分层数不等于平均工作量。

划分时应考虑：

- 每层 forward/backward 时间；
- 参数和 optimizer state；
- activation size；
- stage 间传输量；
- embedding、loss 和 MoE 层的特殊成本。

## 7.8 Sequence Parallel 与 Context Parallel

### 7.8.1 Sequence Parallel 的位置

在 Tensor Parallel 中，矩阵乘法通常沿 hidden 或 head 维切分，但 LayerNorm、dropout 和 residual 等逐 token 操作可能仍在每个 TP rank 上保留完整序列激活。Sequence Parallel 可以进一步沿 sequence 维切分这些激活：

~~~text
完整 activation [batch, sequence, hidden]
  -> 各 rank 保存 sequence 的不同区间
  -> 局部 LayerNorm/dropout/residual
  -> 在需要矩阵布局时重新交换或聚合
~~~

它常常是 TP 的配套激活布局优化，而不是独立替代 TP 的模型切分方式。

### 7.8.2 Context Parallel 的目标

Context Parallel 面向长上下文，把同一个样本的 token 区间分给不同 rank。它的目标是减少每个 rank 需要常驻的序列相关激活和 attention 工作。

但普通 full attention 中，位置 i 可能需要看到全序列的 K/V。仅仅把 token 切开并不会消除全局依赖。实现可能采用 ring attention、分块 K/V 交换、all-gather 或特定的稀疏可见性。

### 7.8.3 attention 规模和通信

完整 attention 的分数矩阵在教学层面有 O(L^2) 的序列关系。Context Parallel 可以降低每个 rank 的局部计算和存储，但要付出跨 rank K/V 或中间结果交换。局部窗口、稀疏 attention、FlashAttention 和 context parallel 改变的是不同层次：

| 机制 | 主要改变 |
| --- | --- |
| FlashAttention | 片上 IO 和中间矩阵物化 |
| Local/sparse attention | 可见性和计算关系 |
| Sequence Parallel | activation 的序列布局 |
| Context Parallel | 长上下文 token 的设备分布 |

不能因为四者都与长序列有关，就把它们当成同一个技术。

## 7.9 混合并行与 rank mapping

### 7.9.1 3D parallel 的乘积

当 DP、TP、PP 使用正交 rank 维度时：

~~~math
N_{\mathrm{world}}
=
N_{\mathrm{dp}}
\cdot
N_{\mathrm{tp}}
\cdot
N_{\mathrm{pp}}
~~~

例如：

~~~text
DP = 4
TP = 2
PP = 2
world size = 16
~~~

TP 负责层内矩阵，PP 负责层间 stage，DP 负责不同数据副本。若加入 context parallel 或 expert parallel，还要明确这些维度是否与已有 group 正交，以及每个 rank 的实际成员关系。

### 7.9.2 为什么 world size 相等还不够

两个配置都可能使用 64 张 GPU：

~~~text
配置 A: DP=16, TP=2, PP=2
配置 B: DP=4, TP=8, PP=2
~~~

它们的 global batch、层内通信频率、单卡参数量、pipeline bubble 和跨节点流量都不同。只报告 world size 无法解释训练速度或显存。

### 7.9.3 拓扑感知的 rank mapping

一个常见原则是把高频、大带宽通信放在更快的链路内：

~~~text
同机高速互连：优先承载 TP 或高频 CP
跨机高速网络：承载可接受的 DP 或部分 PP
MoE all-to-all：按 expert/rank 位置和网络带宽布局
~~~

这不是绝对规则。实际 mapping 要结合 GPU 数量、NVLink/PCIe 拓扑、节点间网络、交换机 oversubscription、NUMA 和数据加载路径。

### 7.9.4 并行维度与 batch

在等长且正交的设置中：

~~~math
B_{\mathrm{token}}
=
B_{\mathrm{micro}}
\cdot
T
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

TP、PP 和 CP 通常不直接扩大 data batch；它们改变的是一个 batch 如何被计算。若把 TP 或 PP degree 错算进 global batch，会导致学习率和 token budget 计算错误。

乘积关系要求各并行度为正整数，并且 rank mapping 真正覆盖每一个 world rank 一次。若 CP 或 EP 嵌套在 TP/DP group 内而非正交维度，不能把它们机械地继续相乘，应以实际 process-group 成员表为准。

## 7.10 Expert Parallelism：动态路由带来的分布式问题

### 7.10.1 MoE 的 token 路由

一个 MoE layer 通常有 router 和多个 expert。对每个 token，router 产生 expert logits，再选择 top-k expert：

~~~math
p(e\mid x)
=
\operatorname{softmax}(W_r x)_e
~~~

选择集合为：

~~~math
\mathcal{E}(x)
=
\operatorname{TopK}_{e}
p(e\mid x)
~~~

token 需要被送到选中的 expert。若 expert 分布在不同 rank，就需要跨 rank dispatch。

### 7.10.2 Expert capacity

设一个 dispatch batch 有 T_tok 个 token，每个 token 选择 k 个 expert，共有 E 个 expert，capacity factor 为 alpha。在均匀路由假设下，每个 expert 的容量可以粗略写成：

~~~math
C_{\mathrm{expert}}
=
\left\lceil
\alpha
\frac{T_{\mathrm{tok}}k}{E}
\right\rceil
~~~

alpha>1 为路由偏斜预留空间。如果实际分配超过 capacity，系统可能：

- drop 超额 token；
- 用 padding 填满 dispatch buffer；
- 使用 dropless 或动态容量实现；
- 让部分 token 走其他路径。

不同策略会改变训练质量、通信量和 kernel 形状。

这个容量式要求 T_tok 是非负整数，E>=1、1<=k<=E 且 alpha>0。它给出的是均匀路由下的 buffer 量级；top-k 的多路副本、padding 约定和 dropless 实现都会改变实际每 expert 的可用 slot，容量不能脱离 dispatch 实现比较。

### 7.10.3 All-to-all 的两次交换

典型 expert parallel 路径是：

~~~text
本地 token hidden states
  -> 根据 expert 所在 rank 分桶
  -> all-to-all 发送
  -> 本 rank expert 计算
  -> 按原 token 位置重新分桶
  -> all-to-all 返回
  -> combine top-k expert outputs
~~~

因此 MoE 的通信量取决于 token 数、hidden size、top-k、expert parallel group、路由偏斜和是否发送 padding。仅根据总参数量估计 MoE 训练成本会严重低估通信。

### 7.10.4 负载均衡不是只看辅助 loss

路由均衡可以通过 router loss、importance loss、load loss、capacity 和实际计数共同观察。应分别记录：

~~~text
expert token count
expert overflow count
token drop rate
padding ratio
router entropy
all-to-all time
per-expert compute time
~~~

一个辅助 loss 下降，不代表实际 GPU 工作已经均衡；某些 rank 仍可能因为通信或 kernel 形状变慢。

## 7.11 Activation checkpointing：用重计算换显存

### 7.11.1 为什么激活会成为瓶颈

训练 backward 需要 forward 的中间结果。对长序列和深 Transformer，激活可能比参数更快成为单卡显存瓶颈，尤其当 batch 和 context length 同时增大时。

Activation checkpointing 的策略是只保存部分边界激活，丢弃中间激活，在 backward 时重新执行对应的 forward：

~~~text
forward:
  保存 segment boundary
  丢弃 segment 内部中间结果

backward:
  从 boundary 重新计算 segment
  立即使用重算结果计算梯度
~~~

### 7.11.2 显存与计算的量级

如果把网络切成 K 个 checkpoint segment，理想化地可以把部分激活常驻量从 M_act 降到接近 M_act/K，但真实结果取决于 segment 边界和流水线：

~~~math
M_{\mathrm{act,ckpt}}
\not\equiv
\frac{M_{\mathrm{act}}}{K}
~~~

额外计算可以写成一个大于 1 的因子：

~~~math
R_{\mathrm{compute}}
=
\frac{T_{\mathrm{with\ recompute}}}
{T_{\mathrm{without\ recompute}}}
>
1
~~~

这两个量都应通过 profiler 测量，而不是只使用一个理想比例。

这里 K 是正整数，M_act 表示同一测量口径下的正激活量，且分母 T_without_recompute>0。checkpoint segment 不是越多越好：当 segment 过小，重算、调度和通信边界本身也会成为成本。

### 7.11.3 与 FSDP、TP、PP 的组合

Activation checkpointing 可以和 FSDP、TP、PP 叠加，但它们释放和重新获取的对象不同：

- FSDP 主要分片参数、梯度和 optimizer state；
- TP 分片层内张量；
- PP 分片层；
- checkpointing 丢弃并重算激活。

组合后要检查峰值时刻：某层参数 all-gather、activation 重算、通信 buffer 和 optimizer step 可能在同一时间重叠，稳态公式无法直接给出峰值。

## 7.12 通信与计算重叠

### 7.12.1 不重叠的时间模型

若一次更新的计算时间为 T_comp，通信时间为 T_comm，完全串行的时间近似为：

~~~math
T_{\mathrm{step}}
\approx
T_{\mathrm{comp}}+T_{\mathrm{comm}}
~~~

### 7.12.2 理想重叠

若通信和计算完全重叠，理论下界接近：

~~~math
T_{\mathrm{step}}
\approx
\max(T_{\mathrm{comp}},T_{\mathrm{comm}})
~~~

真实系统位于两者之间，受以下因素限制：

- collective 是否异步；
- backward 的梯度产生顺序；
- bucket 大小；
- 网络和计算是否使用不同 stream；
- collective 是否争用同一带宽；
- 参数 all-gather 与 kernel 的边界；
- 某个慢 rank 是否拖住全局。

### 7.12.3 DDP bucket overlap

DDP 可以把梯度按 bucket 分组。当某个 bucket 的梯度已经完成，通信可以先开始，同时 backward 继续计算还未完成的 bucket。bucket 太小会产生大量小消息，太大则要等待更多梯度形成。

调优时应记录：

~~~text
bucket size
gradient ready order
collective start/end time
backward kernel time
overlap ratio
network utilization
~~~

### 7.12.4 FSDP 的 overlap

FSDP 可以尝试把当前模块的计算与后续模块的参数 prefetch 或梯度通信重叠。若预取过早，会增加峰值显存；若过晚，计算会等待 all-gather。最优点依赖 wrap 粒度、模块大小和网络。

### 7.12.5 overlap 不是免费加速

即使时间线看起来有重叠，通信也可能占用计算所需的内存带宽、PCIe 或 GPU copy engine。报告“通信与计算重叠”时，应给出实际 step time、通信占比和 GPU kernel 时间，而不是仅凭异步 API 的存在作结论。

## 7.13 Checkpoint 与分布式恢复

### 7.13.1 需要保存哪些状态

分布式训练的可恢复 checkpoint 至少需要：

~~~text
model parameter shards
gradient or optimizer shards when needed
optimizer states
scheduler state
scaler state
global optimizer step
micro-step and accumulation position
data sampler state
RNG state for each rank
world-size and parallel topology
model/config/tokenizer version
~~~

对于 FSDP、ZeRO、TP、PP、EP 或 GaLore 等系统，还可能需要：

- parameter flattening 和 shard metadata；
- TP/PP/EP rank mapping；
- projection basis 或其他特殊 optimizer state；
- expert layout 和 router 相关配置；
- checkpoint format version。

### 7.13.2 global checkpoint 与 sharded checkpoint

一个 global checkpoint 试图把完整模型和状态聚合成统一文件；它方便某些加载场景，但保存时会产生聚合内存和通信压力。

sharded checkpoint 让每个 rank 或一组 rank 保存自己的 shard，并用 manifest 描述：

~~~text
tensor name
global shape
dtype
shard offsets
file name
checksum
parallel topology
creation step
~~~

分片保存更适合大模型，但恢复时需要知道旧 shard 如何映射到新 world size 或新并行拓扑。不能只把文件名按 rank 编号复制到新集群。

### 7.13.3 异步 checkpoint 的一致性

异步写盘可以减少训练线程等待，但必须定义 snapshot 时刻。若参数、optimizer state 和 data cursor 在不同时间采样，恢复出来的状态可能不属于同一个 optimizer step。

一种安全思路是：

1. 在明确的 optimizer step 边界冻结逻辑状态；
2. 生成不可变的 snapshot metadata；
3. 后台写入 shard；
4. 所有 shard 完成后提交 manifest；
5. 只有提交成功的 manifest 才被视为可恢复版本。

### 7.13.4 改变 world size 后恢复

改变 DP degree 可能需要重新分片 optimizer state 和 data sampler；改变 TP 或 PP degree 还可能需要重新布局参数和 stage。恢复流程应先验证：

- 参数 global shape；
- shard 覆盖无空洞无重叠；
- optimizer state 与参数映射；
- 新 topology 的 group；
- scheduler step；
- data cursor 和有效 token 计数。

## 7.14 故障模型与恢复语义

### 7.14.1 一个 rank 失败为什么会影响全局

collective 要求参与 rank 按相同顺序进入通信。如果一个 rank OOM、数据读取失败或 kernel 崩溃，其他 rank 可能仍在等待它进入 all-reduce。于是单点异常表现为全局 hang。

故障日志应包含：

~~~text
rank and host
current collective name
sequence number
global step and micro-step
batch/data cursor
GPU memory and NCCL error
last completed checkpoint
~~~

只有“程序卡住了”不足以定位是慢 rank、通信不一致还是硬件故障。

### 7.14.2 collective 顺序不一致

典型错误包括：

- 某个分支只在 rank 0 调用了 broadcast；
- 某个 rank 的 empty batch 跳过了 all-reduce；
- MoE 路由导致不同 rank 调用不同次数的 collective；
- exception 被局部捕获，其他 rank 不知道；
- PP 的 send/recv micro-batch id 不匹配。

所有会影响 collective 次数和顺序的控制流都必须跨 rank 一致，或使用明确的协议处理空输入。

### 7.14.3 恢复点的选择

如果故障发生在一个尚未提交 manifest 的 step，通常应从上一个完整 checkpoint 恢复，而不是尝试拼接半写入状态。恢复后可能重复少量数据；重复范围必须由 data cursor 和 checkpoint step 明确记录。

### 7.14.4 数据一致性与样本重复

恢复时只恢复模型而不恢复 sampler state，可能导致：

- 某些 shard 重复；
- 某些 shard 被跳过；
- rank 之间重新分配不一致；
- validation 时间点发生偏移。

训练 token budget 和数据去重统计都应该以恢复后的真实 cursor 为准。

## 7.15 分布式训练的可观测性

### 7.15.1 训练级指标

每个 optimizer step 至少记录：

~~~text
global step
micro-step
effective tokens
train loss
learning rate
grad norm
parameter norm
tokens per second
step time
checkpoint id
~~~

### 7.15.2 rank 级指标

每个 rank 或每类 process group 还应记录：

~~~text
rank and host
GPU memory allocated/reserved
forward time
backward time
optimizer time
collective time by type
data wait time
communication payload
kernel idle time
~~~

只记录 rank 0 的平均吞吐，会掩盖某个慢 rank 让所有其他 rank 等待的情况。应记录最大、最小、平均和分位数。

### 7.15.3 MoE 和 PP 的专用指标

MoE：

- 每 expert token count；
- overflow/drop；
- all-to-all time；
- expert compute time；
- router entropy。

PP：

- 每 stage forward/backward time；
- stage idle time；
- send/recv time；
- micro-batch queue；
- activation memory。

TP/FSDP：

- all-gather/reduce-scatter 时间；
- shard size；
- transient memory；
- wrap/module 级别事件。

### 7.15.4 用时间线而不是单一平均数

一个 step 的平均耗时可能相同，但原因完全不同：

~~~text
实验 A：计算占主导，通信已重叠
实验 B：通信占主导，GPU 等待网络
实验 C：某个 rank 慢，其他 rank 在 collective 等待
实验 D：pipeline bubble 很大
~~~

需要用 profiler trace、collective 日志和 rank 时间线来区分这些情况。

## 7.16 如何选择并行方式

### 7.16.1 先确认瓶颈

选择前先测：

1. 单卡能否容纳参数、梯度、optimizer state 和激活？
2. 单卡 forward/backward 的计算时间是多少？
3. data loader 是否已经让 GPU 等待？
4. 目标网络的节点内、节点间带宽如何？
5. sequence length、batch 和 MoE 路由的分布是什么？

如果数据加载已经占大部分 step time，先堆叠更复杂的并行方式通常不会解决问题。

### 7.16.2 一个保守的决策顺序

可以按以下顺序建立基线：

~~~text
模型和状态能放单卡
  -> DDP baseline

状态放不下但单层可切
  -> ZeRO/FSDP，再测通信

单层矩阵放不下或算力不足
  -> Tensor Parallel

模型层太深或参数总量过大
  -> Pipeline Parallel

长序列激活成为瓶颈
  -> activation checkpointing，再考虑 SP/CP

MoE 动态路由成为瓶颈
  -> Expert Parallel 和 all-to-all 优化

仍然不足
  -> 组合 DP/TP/PP/CP/EP，并做拓扑映射
~~~

这不是固定流程，而是一个可解释的实验顺序。每加入一个并行维度，都应保留上一个配置的 quality、显存和 throughput baseline。

### 7.16.3 64 张 GPU 的两个对照

假设有 64 张 GPU：

~~~text
配置 A: DP=16, TP=2, PP=2
配置 B: DP=4, TP=8, PP=2
~~~

配置 A 的 data batch 更大，TP 通信组更小；配置 B 的单层计算被切得更细，TP collective 更频繁。若跨节点网络较慢，B 可能比 A 更差，即使两者 world size 相同。

比较时应记录：

~~~text
per-rank parameter state
effective tokens per update
TP/PP/DP group topology
communication time
pipeline bubble
GPU utilization
validation loss per token
checkpoint throughput
~~~

## 7.17 一个分布式资源账本示例

下面的 Python 示例只用标准库，不启动真实进程。它计算：

- 64 GPU 的 DP/TP/PP world size；
- DDP 与 ZeRO 各阶段的状态量级；
- ring all-reduce 通信量和理想传输时间；
- global effective token batch；
- pipeline bubble；
- MoE expert capacity 与偏斜路由溢出；
- activation checkpointing 的理想化显存变化。

示例中的数值是教学构造，不能替代目标硬件的 profiler 和实际 collective 测量。

~~~python
import math


GIB = 1024 ** 3


def finite_number(name, value, *, positive=False, nonnegative=False):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError(f"{name} must be a finite number")
    value = float(value)
    if not math.isfinite(value):
        raise ValueError(f"{name} must be finite")
    if positive and value <= 0.0:
        raise ValueError(f"{name} must be positive")
    if nonnegative and value < 0.0:
        raise ValueError(f"{name} must be nonnegative")
    return value


def positive_int(name, value):
    if isinstance(value, bool) or not isinstance(value, int) or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def nonnegative_int(name, value):
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise ValueError(f"{name} must be a nonnegative integer")
    return value


def required_config(config, name, *, integer=False, positive=False,
                    nonnegative=False):
    if name not in config:
        raise ValueError(f"missing config field: {name}")
    if integer:
        return (positive_int if positive else nonnegative_int)(name, config[name])
    return finite_number(
        name,
        config[name],
        positive=positive,
        nonnegative=nonnegative,
    )


def gib(byte_count):
    byte_count = finite_number("byte_count", byte_count, nonnegative=True)
    return byte_count / GIB


def memory_estimates(config):
    params = required_config(config, "params", integer=True, positive=True)
    weight_bytes = required_config(config, "weight_bytes", positive=True)
    grad_bytes = required_config(config, "grad_bytes", positive=True)
    optimizer_bytes = required_config(
        config, "optimizer_state_bytes", nonnegative=True
    )
    dp = required_config(config, "dp", integer=True, positive=True)
    weights = params * weight_bytes
    gradients = params * grad_bytes
    optimizer = params * optimizer_bytes
    return {
        "ddp_gib": gib(weights + gradients + optimizer),
        "zero1_gib": gib(weights + gradients + optimizer / dp),
        "zero2_gib": gib(weights + (gradients + optimizer) / dp),
        "zero3_gib": gib((weights + gradients + optimizer) / dp),
        "weights_gib": gib(weights),
        "gradients_gib": gib(gradients),
        "optimizer_gib": gib(optimizer),
    }


def ring_all_reduce_gib(payload_gib, ranks):
    payload_gib = finite_number("payload_gib", payload_gib, nonnegative=True)
    ranks = positive_int("ranks", ranks)
    return 2.0 * (ranks - 1) / ranks * payload_gib


def ideal_transfer_seconds(payload_gib, bandwidth_gbps):
    payload_gib = finite_number("payload_gib", payload_gib, nonnegative=True)
    bandwidth_gbps = finite_number(
        "bandwidth_gbps", bandwidth_gbps, positive=True
    )
    bytes_sent = payload_gib * GIB
    return bytes_sent / (bandwidth_gbps * 1e9)


def pipeline_bubble(stage_count, micro_batch_count):
    stage_count = positive_int("stage_count", stage_count)
    micro_batch_count = positive_int(
        "micro_batch_count", micro_batch_count
    )
    return (stage_count - 1) / (
        micro_batch_count + stage_count - 1
    )


def expert_capacity(tokens, top_k, experts, capacity_factor):
    tokens = nonnegative_int("tokens", tokens)
    top_k = positive_int("top_k", top_k)
    experts = positive_int("experts", experts)
    capacity_factor = finite_number(
        "capacity_factor", capacity_factor, positive=True
    )
    if top_k > experts:
        raise ValueError("top_k cannot exceed experts")
    return math.ceil(
        capacity_factor * tokens * top_k / experts
    )


def effective_token_batch(config):
    micro_batch = required_config(config, "micro_batch", integer=True, positive=True)
    sequence_length = required_config(
        config, "sequence_length", integer=True, positive=True
    )
    accumulation_steps = required_config(
        config, "accumulation_steps", integer=True, positive=True
    )
    dp = required_config(config, "dp", integer=True, positive=True)
    return micro_batch * sequence_length * accumulation_steps * dp


config = {
    "params": 6_000_000_000,

effective_tokens = effective_token_batch(config)

diagnostics = {
~~~

## 7.18 常见故障：从现象回到切分和通信

### 7.18.1 GPU 数量增加但吞吐不变

先把 step time 拆成：

~~~text
data wait
forward
backward
optimizer
collective
checkpoint
~~~

如果 collective 占比上升，检查 DP/TP group、bucket、拓扑和通信 overlap；如果 data wait 占比上升，检查数据 shard、预取和存储；如果 pipeline idle 占比上升，检查 micro-batch 数和 stage 平衡。

### 7.18.2 某个 rank 显存特别高

可能原因包括：

- FSDP wrap 粒度导致该 rank 瞬时 all-gather 更大的模块；
- PP stage 参数和激活不均；
- rank 0 额外保存完整 state 或日志对象；
- MoE 路由偏斜；
- 某个 rank 的 batch padding 更多；
- checkpoint 聚合只在少数 rank 进行。

要同时记录稳态和峰值显存，并关联具体 module、rank 和时间点。

### 7.18.3 作业 hang

优先查看最后一个 collective：

1. 是否所有 rank 都执行到同一个 collective；
2. collective 的 group 和顺序是否一致；
3. 某个 rank 是否在数据加载、OOM 或异常处理里停住；
4. PP send/recv 的 micro-batch id 是否匹配；
5. MoE all-to-all 的 token count 和 buffer shape 是否一致。

不要先通过增加 timeout 掩盖问题。更长 timeout 只会让诊断等待更久。

### 7.18.4 loss 与单卡不一致

对照以下口径：

- global 有效 token 分母；
- DP rank 是否重复或遗漏数据；
- gradient accumulation 是否按 token 归一化；
- TP/PP 的局部 loss 是否正确聚合；
- dropout、RNG 和数据顺序；
- 混合精度和 collective reduction 顺序。

小规模模型上运行单卡和分布式的同一 batch，是定位 loss 口径错误的最快办法之一。

### 7.18.5 FSDP 省了稳态显存却仍然 OOM

可能是：

- all-gather transient peak；
- activation 未 checkpoint；
- optimizer step 时临时 buffer；
- mixed precision cast 同时保留两份参数；
- wrap 粒度不合理；
- allocator fragmentation。

需要用 memory snapshot 和 module 时间线定位峰值，而不是只看参数 shard 大小。

### 7.18.6 MoE overflow 很高

检查：

- top-k 和 capacity factor；
- router logits 和 entropy；
- expert token count 的长尾；
- token dispatch 是否按 expert rank 正确分桶；
- padding 是否吞噬了容量；
- 辅助负载均衡损失是否与实际计数一致。

提高 capacity factor 可能减少 drop，却会增加 padding、显存和通信。它不是只调大就结束的单向旋钮。

## 7.20 章节练习：从切分公式到系统设计

### 练习一：全局 token 分母

有 4 个 DP rank，某次更新每个 rank 的有效 token 数分别为 100、100、200、400，未归一化损失分别为 50、60、110、220。计算全局 token-level loss，并说明简单平均四个 rank mean 会怎样改变权重。

### 练习二：collective 选择

为 DDP 梯度同步、FSDP 参数获取、FSDP 梯度分片和 MoE token dispatch 分别选择 all-reduce、all-gather、reduce-scatter 或 all-to-all，并说明每个操作的输入输出布局。

### 练习三：ZeRO 状态账本

假设参数量为 7B，权重和梯度是 BF16，AdamW 状态是两个 FP32 张量，DP size 为 8。分别估计 DDP、ZeRO-1、ZeRO-2 和 ZeRO-3 的常驻状态量级，再列出 transient all-gather 和 activation 未计入的部分。

### 练习四：TP 矩阵布局

把一个 4096 x 11008 的 MLP up projection 按列切到 4 个 TP rank，再把 down projection 按行切分。写出每个 rank 的局部矩阵形状，并指出哪一步需要拼接、哪一步需要求和。

### 练习五：Pipeline bubble

有 8 个 pipeline stage，分别使用 8、16、32 个 micro-batch。用简化 bubble 公式估计空泡比例，再讨论增加 micro-batch 对 activation 和 global batch 的影响。

### 练习六：MoE capacity

一个 dispatch batch 有 4096 个 token，top-k=2，16 个 expert，capacity factor=1.25。计算均匀路由下的每 expert capacity；再假设一个 expert 收到全部 routed slots 的 30%，估计 overflow，并讨论 padding 和 drop 的代价。

### 练习七：恢复测试

让一个两 rank toy 训练在第 10 个 optimizer step 保存参数 shard、optimizer state、scheduler、RNG、sampler cursor 和 rank mapping。改变 DP size 后恢复，检查参数拼接、数据位置和下一步 loss 是否与预期一致。

### 练习八：定位吞吐回退

比较两个配置：A 使用 DP=16、TP=2、PP=2；B 使用 DP=4、TP=8、PP=2。若 B 的 GPU utilization 更低，设计一个 profiler 计划，区分是 TP collective、跨节点拓扑、kernel 变小还是 pipeline stage 不均造成的。

## 7.21 本章小结

分布式训练把一次 optimizer update 拆成多个 rank 之间协作的计算和通信过程。Data Parallel 复制模型并切分数据，DDP 用梯度 collective 保持副本一致；ZeRO/FSDP 分片参数、梯度和 optimizer state，用显存换取参数 gather、梯度 reduce-scatter 和更复杂的 checkpoint。

Tensor Parallel 切层内矩阵，Pipeline Parallel 切模型层并需要 micro-batch 调度，Sequence Parallel 和 Context Parallel 处理长序列激活与跨区间 attention，MoE 的 Expert Parallel 则把动态路由 token 通过 all-to-all 发送到不同专家。它们解决的是不同瓶颈，不能只看 world size 或模型总参数量选择。

一次可信的分布式训练记录，至少要包含 global 有效 token 分母、parallel degree、rank mapping、显存峰值、collective 时间、计算通信重叠、pipeline bubble、MoE 负载、checkpoint manifest 和恢复行为。公式可以建立量级直觉，profiler 和目标集群实测才决定最终系统结论。
