# 第七章：分布式训练：把一次更新放到多张设备上

## 7.0 一次更新为什么会变成一个系统问题

先看四张 GPU 处理四条训练样本的情况。若采用数据并行，每张卡持有同一模型的一份副本，各自计算本地梯度；接下来要解决两件事：怎样把四份梯度合成一次全局更新？如果模型放不进单卡，又该把哪些状态或计算切分到其他卡？

在单卡上，一次更新通常是：

~~~text
读取一个 batch（批次）
  -> forward（前向计算）
  -> loss（损失）
  -> backward（反向传播，计算梯度）
  -> optimizer.step()（优化器更新参数）
~~~

到了多张 GPU 上，四张卡仍要完成同一次更新，但每张卡只看到了部分数据，或只保存了部分模型。于是计算链变成：

~~~text
rank 读取自己的数据 shard（分片）
  -> 局部 forward/backward
  -> rank 之间通过 collective communication（集合通信）交换梯度、参数、激活或 token
  -> 得到全局一致或分片的更新
  -> 保存与恢复分布式状态
~~~

本章沿着这次更新追踪四件事：

1. 什么被复制，什么被切分？
2. 每张设备在什么时候需要别的设备的数据？
3. 这些数据通过哪一种 collective communication 交换？
4. 通信、计算、显存和故障恢复的代价是否值得？

不同并行方式的名字，来自它们切开的对象不同。先看下表：

| 并行方式 | 主要切分对象 | 典型收益 | 主要代价 |
| --- | --- | --- | --- |
| Data Parallel（数据并行，DP） | 样本或 batch | 扩大数据并行处理能力；固定每卡 batch 时可扩大 global batch（全局批次） | 梯度同步 |
| ZeRO / Fully Sharded Data Parallel（完全分片数据并行，FSDP） | 参数、梯度、optimizer state（优化器状态） | 降低单卡常驻显存 | 参数和梯度通信 |
| Tensor Parallel（张量并行，TP） | 层内矩阵或 hidden dimension（隐藏维度） | 让单层跨设备计算 | 高频层内通信 |
| Pipeline Parallel（流水线并行，PP） | 模型层 | 让深模型分布到多个 stage（阶段） | 空泡、激活传递和调度 |
| Sequence Parallel（序列并行，SP） | 序列方向的激活 | 降低逐 token 激活显存 | 序列布局通信 |
| Context Parallel（上下文并行，CP） | 长上下文 token 区间 | 分摊长序列 attention（注意力） | 跨区间 K/V 或 attention 通信 |
| Expert Parallel（专家并行，EP） | Mixture of Experts（专家混合，MoE）的专家网络和路由 token | 分摊专家计算和参数 | all-to-all 与负载不均 |

接下来先认清“哪张卡是谁”和“谁与谁通信”，再沿一轮更新看数据并行、模型切分和集合通信怎样配合。后半章再把显存、流水线、长上下文、MoE、保存恢复和故障放进同一张资源账本。这里关心训练更新怎样在 rank 间正确推进；机器、网络和集群平台本身的细节，可接读[第二十三册 GPU 集群架构](../../book-23-ai-infra/chapters/07-gpu集群架构-单机多卡-多机多卡和机柜级互联.md)、[网络与集合通信](../../book-23-ai-infra/chapters/08-网络基础-infiniband-roce-以太网和集合通信.md)及[训练平台工程](../../book-23-ai-infra/chapters/guide-大模型训练平台工程.md)。

## 7.1 分布式训练的基本对象

### 7.1.1 world、rank 和 local rank

一个分布式作业通常有：

- world size（全局 rank 数）：整个作业启动了多少个进程；
- rank（全局编号）：某个进程在整个作业中的编号；
- local rank（本机编号）：某个进程在当前 node（机器节点）中的编号；
- node：承载一组设备的机器；
- process group（进程组/通信组）：参与某种集合通信的 rank 子集。

例如，4 台机器各有 8 张 GPU。若每张 GPU 启动一个 rank，全作业就有 32 个 rank。启动器按机器顺序、再按机器内设备顺序编号时，一种可能的编号是：

~~~text
world_size = 32
node_0 local_rank = 0..7
node_1 local_rank = 0..7
global rank = 0..31
~~~

在这个编号约定下，node 1 上的 local rank 3 对应 global rank 11：前一台机器占了 rank 0–7，第二台机器从 rank 8 开始。local rank 3 只告诉你“这台机器里的第 4 张卡”；global rank 11 才告诉分布式程序“这是整个作业里的第 12 个 rank”。实际编号由启动器和 rank mapping 决定，不能只凭 local rank 推出 global rank。

所有 rank 合起来叫 world。一次通信通常只需要其中一部分 rank 参加；这些参与者组成 process group。7.1.2 会沿用前面已经出现的 DP、PP、TP，用 16 张卡把这些组逐个列出来。

### 7.1.2 为什么要显式建立 process group（通信组）

沿用 7.0 的定义，先按总卡数看这三个数的关系： $DP=4$，就是把 16 张卡分成 4 份处理不同数据的模型布局，每份 4 张卡。每份布局按 $PP=2$ 分成前后两个 stage；每个 stage 内有 $TP=2$ 张卡合作计算。因此一份布局占 $PP\times TP=2\times2=4$ 张卡，4 份布局合计 $16 = DP\times PP\times TP = 4\times2\times2$。从外到内看，就是 DP 分成 4 份、每份有 2 个 PP stage、每个 stage 有 2 张 TP 卡。

例如，把一个 24 层模型的第 1–12 层放在 stage 0，把第 13–24 层放在 stage 1。一个 micro-batch 先后经过这两个 stage；每个 stage 内，两张 TP 卡合作计算该 stage 的层。训练多个 micro-batch 时，两个 stage 可以同时处理不同的 micro-batch。

下面用一种连续编号列出 4 份布局。每行是一份 DP 布局；箭头表示同一个 micro-batch 先后经过两个 PP stage，方括号里的两张卡组成该 stage 的 TP 组：

| DP 副本 | 该副本中的 PP stages（每个 stage 内是 TP ranks） |
| --- | --- |
| 0 | stage 0 `[0, 1]` → stage 1 `[2, 3]` |
| 1 | stage 0 `[4, 5]` → stage 1 `[6, 7]` |
| 2 | stage 0 `[8, 9]` → stage 1 `[10, 11]` |
| 3 | stage 0 `[12, 13]` → stage 1 `[14, 15]` |

同一个 rank 会因为不同操作，和不同的 rank 通信。以 rank 0 为例，它既和 rank 1 一起计算 stage 0，也要把 stage 0 的激活传给 rank 2，还要和其他三份布局中负责同一部分模型的 rank 同步梯度：

| 操作 | rank 0 所属的组 | 这组 rank 在做什么 |
| --- | --- | --- |
| TP | `[0, 1]` | 在同一副本、同一 stage 内合作计算层内矩阵 |
| PP | `[0, 2]` | 在同一副本、同一 TP 位置上连接前后两个 stage；前一 stage 把激活传给后一 stage |
| DP | `[0, 4, 8, 12]` | 在四份布局中找到相同 stage、相同 TP 分片，对应参数的梯度在这里同步 |

这三类组共享同一批 rank，并不是三批互不相干的卡：rank 0 同时属于一个 TP 组、一个 PP 组和一个 DP 组。进程组就是把每种通信实际要用的 rank 成员明确登记下来。做 TP collective 时用 TP 组，跨 stage 传激活时用 PP 组，同步四份数据布局中对应参数的梯度时用 DP 组。rank 0 的梯度若放到 world group 归约，就会和其他 stage 或 TP 分片上代表不同参数的梯度混在一起；即使张量形状相同，它们也未必是同一参数。world group 只用于确实需要全体 rank 参与的操作。各 rank 还必须以一致的顺序调用对应 group 上的通信，否则可能互相等待而挂起。

### 7.1.3 一次更新的全局时间线

回到四张卡、四条样本的例子。每张卡先读自己的数据并算出局部结果；但在更新模型前，四张卡要按约定合并梯度。一次数据并行更新可以按下面的顺序追踪：

~~~text
每个 rank:
  1. 取本地 micro-batch（微批次）
  2. 前向计算得到预测，loss（损失）比较预测与目标，反向传播得到梯度
  3. 数出这批数据里有多少个预测目标参与了 loss
  4. 按并行方式，通过通信组交换需要共享的梯度、参数或统计量
  5. 得到全局梯度，或得到本 rank 负责的梯度分片
  6. 优化器根据梯度更新参数
  7. 更新学习率调度状态，并记录数据读取位置
~~~

如果模型还按 TP、PP 或 FSDP 切开，局部计算前后会多出相应的数据交换：有时要先把参数分片聚齐，有时要把一个 stage 的激活送到下一个 stage，有时要把 MoE token 送到专家所在的 rank。它们都发生在“算局部结果”和“得到本次更新”之间。排查速度时，应把 step time 拆成这些可观察的动作，才能知道卡在算、传、等，还是保存。

## 7.2 一次更新的 loss 分母怎样算

### 7.2.1 样本 batch 与 token batch

在等长样本下，设每个 DP rank 的每次 micro-step（微步）处理 $B_{\mathrm{micro}}$ 个样本，累积 $A$ 次，DP group 有 $N_{\mathrm{dp}}$ 个 rank。一次 optimizer update（优化器更新）处理的样本总数为：

~~~math
B_{\mathrm{sample}}
=
B_{\mathrm{micro}}
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

这个式子只数样本条数；样本长度不同时，它不会告诉我们有多少个 token 真的参与 loss。

语言模型还要区分“模型读了多少 token”和“有多少个位置真的参与了 loss”。以序列 `[我, 喜欢, 蓝, 色, EOS]` 为例，模型读入 5 个 token；自回归训练会用前面的位置预测下一个 token，所以最多有 4 个预测目标：`喜欢、蓝、色、EOS`。如果训练目标只监督回答部分，或某些位置是 padding、跨文档边界被 mask，那么参与 loss 的目标还会少于 4。

因此日志里的 input tokens（输入 token 数）和 loss 分母里的有效目标数不能混为一谈。对长度为 L 的序列，模型内部做 next-token shift 时通常有 L 个输入位置、至多 L−1 个预测目标；若数据管线已经先做了 shift，就按实际 logits、labels 和 loss mask 对齐后的数量统计，不要再机械减一。

令 $N_{\mathrm{valid}}(r,a)$ 表示 DP rank $r$ 在第 $a$ 个 micro-step 中，经过 shift 和 loss mask 后实际参与 loss 的预测目标数。把所有 DP rank 和累积 micro-step 的有效目标加起来，得到：

~~~math
B_{\mathrm{token}}
=
\sum_{r=1}^{N_{\mathrm{dp}}}
\sum_{a=1}^{A}
N_{\mathrm{valid}}(r,a)
~~~

因果 LM 输入长度统一为 L、内部 shift、无 padding 且每个可预测位置都参与 loss 时，才可以简化为：

~~~math
B_{\mathrm{token}}
=
B_{\mathrm{micro}}
\cdot
(L-1)
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

如果数据使用 packing、动态 padding、跨样本边界 mask 或 assistant-only label mask，就必须用对齐后真实有效的 target 计数。只记录每卡样本数或输入 token 数，会把不同实验的有效训练量混在一起。吞吐日志可以同时报告输入 token/s 与有效 target token/s，并说明 padding 是否包含在前者中。

每个 $N_{\mathrm{valid}}(r,a)$ 都是非负整数；总和必须大于零，才构成一次有监督的更新。某个 rank 的局部有效目标可以是 0，但若所有 rank、所有累积 micro-step 都是 0，后续的 loss/gradient 平均没有定义，不能把分母替换成 1 后把窗口记成正常训练。

### 7.2.2 不等长 rank 的 loss 归一化

继续看刚才的预测目标。假设三个 rank 分到的有效目标数分别是 100、200、400；它们各自把这些目标的损失加起来，得到 50、110、220。全局平均要把 700 个目标放在同一个分母里，而不是把三个 rank 当成三票：

~~~text
三个 rank 的 loss sum: 50 + 110 + 220 = 380
三个 rank 的有效目标：$100+200+400=700$。
全局 token-mean loss: 380 / 700 ≈ 0.5429
~~~

一般地，设第 r 个 rank 的有效 token 数是 $n_{r}$，未归一化损失和为 $s_{r}$。全局 token-level loss 是：

~~~math
L_{\mathrm{global}}
=
\frac{\sum_{r} s_{r}}{\sum_{r} n_{r}}
~~~

要让参数更新也对应这个全局平均，各 rank 对未归一化损失求出的梯度也必须用同一个全局 token 数作分母：

~~~math
g_{\mathrm{global}}
=
\frac{\sum_{r} G_{r}}{\sum_{r} n_{r}}
~~~

一种常见错误是：每个 rank 先除以自己的 $n_{r}$ 得到局部平均，再把三个局部平均等权相加。这样实际计算的是：

~~~math
\frac{1}{N_{\mathrm{dp}}}
\sum_{r} \frac{G_{r}}{n_{r}}
~~~

这样，只有 100 个目标的 rank 和有 400 个目标的 rank 权重相同。只有各 rank 的 $n_{r}$ 相等时，先做局部平均再等权平均才与全局 token 平均一致。框架执行 all-reduce 并不自动保证分母符合训练目标，必须查清它归约的是 sum、mean 还是已经缩放过的梯度。

这两个全局公式要求 $n_{r}\ge0$ 且 $\sum_{r} n_{r}>0$，并要求 $G_{r}$ 是与未归一化损失 $s_{r}$ 同一 token 口径下累加的梯度。若局部 loss 已经先除以 $n_{r}$，或框架已经做了 rank mean，再把它们按本式求和会产生二次归一化；先确定张量里保存的是 sum、mean 还是已缩放的 gradient，才谈 collective。

局部平均再等权平均的结果是：

~~~text
(50/100 + 110/200 + 220/400) / 3
= (0.50 + 0.55 + 0.55) / 3
≈ 0.5333
~~~

这一步让短 batch 和长 batch 权重相同，所以训练目标已经变了。

PyTorch DDP 默认把各 rank 的梯度做 rank 平均。这个默认规则也要纳入分母换算：DDP 最后还会除以 rank 数。若 $S_{r}$ 是 rank r 的局部 token-loss sum， $N=\Sigma_{r} n_{r}$ 是整个 DP group 在完整累积窗口中的有效目标数，那么每个 rank 可对 $S_{r} \times N_{\mathrm{dp}} / N$ 做 backward。DDP 再把这些梯度除以 $N_{\mathrm{dp}}$，两步合起来正好得到全局 token 平均：

~~~math
\frac{1}{N_{\mathrm{dp}}}
\sum_{r} \nabla\left(S_{r}\frac{N_{\mathrm{dp}}}{N}\right)
=
\frac{\sum_{r} G_{r}}{N}
~~~

这里的 $N_{\mathrm{dp}}$ 是实际参与梯度平均的数据并行 rank 数，不是 world size；TP/PP/CP rank 不应重复算进去。若目标里还有 router auxiliary loss、weight regularizer 或 sequence-level loss，应先分别确定它们的归一化方式，再组合。若框架的 loss API、累积插件或通信 hook 已经缩放梯度，也要按实际约定重新推导。PyTorch DDP 文档指出，直接对 summed loss 求梯度再跨 rank 平均，会比把同一批数据放在一个进程中计算得到的梯度小一个 world-size 因子。[PyTorch DDP 2.15](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html)

### 7.2.3 accumulation 和 DP 的组合

梯度累积就是先处理多个小批次，再把它们作为一次 optimizer update。举个不等长的例子：rank 0 的两个 micro-batch 分别有 100、80 个有效目标；rank 1 的两个 micro-batch 分别有 50、170 个。完整窗口共有 400 个目标。无论框架逐个 micro-step 同步，还是把同步留到最后，都必须让 400 成为这一次更新的分母。

实现时常见三种顺序：

1. 每个 micro-step 先 all-reduce，再在本地累积；
2. 每个 rank 先累积未归一化统计，再在窗口末尾同步；
3. 使用 `no_sync` 暂缓部分梯度通信，最后一次统一同步。

它们的通信量和数值路径不同，但目标不变：对完整 optimizer window 中的有效预测目标求平均。先把每个 rank 的 loss sum 和目标数加起来，得到全局 $N$，再按同一分母缩放梯度贡献。使用 `no_sync` 延迟通信时，最后一个 micro-step 仍要完成同步；epoch 末尾若只剩不完整窗口，分母必须用窗口里的实际目标数。

若 rank 0 的某个 micro-step 没有有效目标，它可以贡献一个连在计算图上的零 loss sum，并继续按约定参加 collective。这样 rank 1 不会在 all-reduce 中一直等它。若整个 DP group 在完整窗口里都没有有效目标，则没有可定义的平均损失；应跳过这次 optimizer 和 scheduler 更新，不要把分母改成 1 后假装完成了一次正常更新。

## 7.3 Data Parallelism：复制模型，切分数据

### 7.3.1 DDP 的数据流

数据并行（Data Parallelism，DP）最直观的做法，是每个 DP rank 都保存一份完整模型，只把训练样本分开。PyTorch 把这种实现封装为 DistributedDataParallel（分布式数据并行，DDP）。以四张卡、四份数据为例：

~~~text
rank 0: full model + batch shard 0
rank 1: full model + batch shard 1
rank 2: full model + batch shard 2
rank 3: full model + batch shard 3
~~~

四张卡从相同参数开始，各自用本地样本完成前向和反向，得到四份局部梯度。对齐的参数梯度通过 all-reduce 合并后，每张卡都得到同一份结果。只要 optimizer、初始参数和更新顺序也一致，四张卡就会继续保持相同参数；下一步再各自处理不同样本。

设第 $r$ 个 DP rank 算出的局部梯度为 $g_{r}$，DP group 有 $N_{\mathrm{dp}}$ 个 rank，且各 rank 有效 token 数相同。同步后每张卡拿到的平均梯度为：

~~~math
\bar g
=
\frac{1}{N_{\mathrm{dp}}}
\sum_{r=1}^{N_{\mathrm{dp}}}
g_{r}
~~~

这里 $N_{\mathrm{dp}}$ 是 DP group 中的 rank 数。做逐项相加前，各 rank 的梯度必须指向同一参数，并具有兼容的 shape 和 dtype，collective 的调用顺序也必须一致。只有各 rank 有效 token 数相同时，简单除以 $N_{\mathrm{dp}}$ 才与 7.2 的全局 token 平均一致；变长 batch 要同时处理 loss sum 和 token count，或使用等价的预缩放方法。

### 7.3.2 数据 shard 不是简单切数组

仍用四张卡的例子。若 rank 0 已经没有下一个 batch，而 rank 1–3 还在反向传播，它们会进入梯度 all-reduce 并等待 rank 0。于是数据读取的差异看起来像“通信挂起”。为避免这种情况，数据管线要保证：

- 不同 rank 尽量读取不重叠样本；
- 每个 epoch 的 shuffle 可复现；
- drop_last 或补齐规则一致；
- 所有 rank 的 collective 调用次数一致；
- 恢复时能够定位到每个 rank 的 data cursor。

如果每个 rank 的 batch 数不同，必须明确是补齐、丢弃尾部，还是使用支持不等长输入的协议；这些选择会改变样本权重或数据覆盖，属于训练正确性的一部分。

PyTorch DDP 提供 `join()` 来处理不等长输入：提前耗尽数据的 rank 会 shadow 仍在工作的 rank 所发出的 DDP collectives。`divide_by_initial_world_size=True`（默认）让尾部样本仍除以作业启动时的 DP size；设为 `False` 则除以当前仍活跃的 rank 数，尾部样本权重会变大。若 forward 中另有 DDP 不知道的 collective（例如 SyncBatchNorm 或自定义 MoE 通信），`join()` 不能替它们自动补齐，需启用 `throw_on_early_termination` 并由应用处理。[PyTorch DDP 2.15 uneven-input 语义](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html)

### 7.3.3 DDP 的优势与边界

DDP 的优势是实现直观、工具成熟、计算和通信边界清楚。它适合完整模型和 optimizer state 能够放进单卡的场景。

它的边界也很明确：

1. 每个 rank 都需要完整参数；
2. 每个 rank 通常都需要完整梯度；
3. 每个 rank 通常都需要完整 optimizer state；
4. 每次更新需要同步梯度；
5. 单卡放不下模型时，DDP 无法单独解决问题。

所以“增加 GPU 后吞吐提高”与“模型能否装下”是两个不同问题。DDP 主要解决前者。

## 7.4 Collective communication：数据怎样合并、分发和收集

先看两张卡上的一小组数字。把通信组里的卡暂时叫 rank 0 和 rank 1：rank 0 手里有 [1, 10]，rank 1 手里有 [2, 20]。如果把相同位置的数字相加，结果是 [3, 30]。接下来要问的不是“通信名词有哪些”，而是：谁参与这次相加，结果又要送到谁手里？这决定了该用哪一种 collective。

### 7.4.1 All-reduce

在刚才的例子里，rank 0 和 rank 1 都得到完整的 [3, 30]。这种“大家一起聚合，再让每个 rank 都拿到结果”的操作叫 all-reduce：reduce 是合并，all 表示组内每个 rank 都收到结果。设通信组有 $N$ 个 rank，第 $q$ 个 rank 的输入为 $x_{q}$；求和形式下，每个 rank $r$ 收到的结果 $y_{r}$ 是：

~~~math
y_{r}
=
\sum_{q=1}^{N}
x_{q}
\qquad
\text{for every }r
~~~

DDP 用这种方式同步对应模型参数的梯度：每张卡根据本地数据算梯度，all-reduce 后按框架约定求和或平均，再用合并后的梯度更新。例子里的 [1, 10] 和 [2, 20] 可以看成两张卡上对应参数的梯度；若它们代表不同参数，就不能相加。

### 7.4.2 Reduce-scatter

还是用刚才的数字。相加后得到 [3, 30]；如果不需要每张卡都保留完整结果，就把它切成两段：rank 0 只拿 [3]，rank 1 只拿 [30]。先合并对应位置，再把不同结果分给不同 rank，这叫 reduce-scatter：

~~~text
输入: rank 0 [1, 10]，rank 1 [2, 20]
逐位置相加: [1+2, 10+20] = [3, 30]
切成两片: rank 0 收到 [3]，rank 1 收到 [30]
~~~

名字可以按动作理解：reduce 是把数值合起来，scatter 是把结果分片发开。ZeRO-2/FSDP 可以用 reduce-scatter 分发梯度；每张卡只留下自己负责的那一片，不必都存完整梯度。

### 7.4.3 All-gather

现在反过来：rank 0 手里只有 [3]，rank 1 手里只有 [30]。把两段收集起来，并让两张卡都拿到 [3, 30]，叫 all-gather。每个 rank 交出自己的那一片（shard），组内每个 rank 都收到完整集合。FSDP 计算一个被它管理的模块前，常要把这个模块的参数分片 all-gather 成完整参数。

完整参数会暂时出现在 GPU 上，所以判断显存够不够，不能只看平时留下的那份 shard；还要看模块聚齐参数时的峰值。

### 7.4.4 All-to-all

all-to-all 可以从“每个 rank 按收件人分包”来理解。假设 rank 0 上有 token A、B，rank 1 上有 token C、D；路由器把 A、C 分给 rank 0 上的 expert，把 B、D 分给 rank 1 上的 expert。交换后，rank 0 收到 A、C，rank 1 收到 B、D。每个 rank 都把不同数据发给不同 rank，也从它们那里收到各自的数据，这就是 all-to-all。MoE 的一轮 token dispatch 按这个顺序发生：

~~~text
router 给每个 token 选 expert
  -> 按 expert 所在的 rank 把 token 的模型内部表示（hidden state）分组
  -> all-to-all 把每组送到对应 rank
  -> expert 处理收到的 token
  -> 再按原来的归属把结果送回去
~~~

因此，MoE 的 all-to-all 不能只看总共传了多少字节。如果多数 token 都去了同一个 rank，它要处理的工作就会更多；分组、消息数量和卡之间的连接方式也会影响速度。

### 7.4.5 Broadcast、send/recv 和 barrier

- **broadcast**：rank 0 有一个配置值，比如学习率 0.001；broadcast 把这个值发给组内所有 rank。它解决“大家都要拿到同一份数据”的问题。
- **send/recv**：rank 0 把一份张量发给指定的 rank 1，rank 1 接收它。Pipeline Parallel 的相邻 stage 常用它传递激活值。
- **barrier**：所有 rank 都到达同一个同步点后，才一起继续。可以把它想成一群人约好在路口等齐再走；如果 rank 1 先到，它仍要等较慢的 rank 0。barrier 不会减少工作量，也不会修正错误的通信组或调用顺序。排查慢任务时，先找出谁在等谁，不要随手加 barrier 把等待藏起来。

### 7.4.6 Ring all-reduce 的量级

先用 4 个 rank 手里的小向量看清 ring all-reduce 的两个阶段。约定数据沿着 `rank 0 → rank 1 → rank 2 → rank 3 → rank 0` 传递，每个元素按 4 字节计算：

~~~text
rank 0: [1, 10, 100, 1000]
rank 1: [2, 20, 200, 2000]
rank 2: [3, 30, 300, 3000]
rank 3: [4, 40, 400, 4000]
~~~

目标是把相同位置的数相加，得到 `[10, 100, 1000, 10000]`。第一阶段叫 reduce-scatter（归约后分片）：把每个向量切成 4 段，让每一段沿环传递；每到一张卡，就加上这张卡上相同位置的数。先跟踪第一段：rank 0 把 `1` 传给 rank 1，rank 1 加上自己的 `2` 得到 `3`；`3` 再传给 rank 2，加上 `3` 得到 `6`；最后传给 rank 3，加上 `4` 得到 `10`。走完 3 步，这一段的总和 `10` 留在 rank 3。其他三段同时沿环传递，只是起点错开；走完后，每个 rank 各留一段已经求完和的数据：

~~~text
rank 0: 第 2 段 = 10 + 20 + 30 + 40 = 100
rank 1: 第 3 段 = 100 + 200 + 300 + 400 = 1000
rank 2: 第 4 段 = 1000 + 2000 + 3000 + 4000 = 10000
rank 3: 第 1 段 = 1 + 2 + 3 + 4 = 10
~~~

此时每张卡只拿到总和的一段，还没有完整向量。第二阶段叫 all-gather（收集全部分片）：每张卡把自己这一段沿环发给下一个 rank；收到新分片后，再把它继续传下去。以 rank 0 为例，它起初有第 2 段 `100`；第一步后收到第 1 段 `10`，接下来两步又收到第 4 段 `10000` 和第 3 段 `1000`，最后也得到 `[10, 100, 1000, 10000]`。其他 rank 同样收齐这四段。这样，两个阶段合起来就是：先分头算完各段的总和，再把各段拼回每张卡。

这个小例子里，每个 rank 的向量有 4 个数，也就是 16 字节。每一步每张卡发送一个数（4 字节）；reduce-scatter 走 3 步，发送 12 字节，all-gather 再走 3 步，也发送 12 字节。把同样的过程放大到每个 rank 同步一个 8 MiB（8×1024² 字节）的向量：每一步发送向量的四分之一，也就是 2 MiB；每个阶段走 3 步，因此每个阶段发送 6 MiB，两阶段合计每个 rank 发送 12 MiB，接收量也约为 12 MiB。对一般的 N 个 rank、每 rank 同步 S 字节，单个 rank 的发送量约为：

~~~math
C_{\mathrm{ring}}
\approx
2\frac{N-1}{N}S
~~~

这里的 $S$ 是每个 rank 要参与同步的数据大小。公式把每阶段的 $N-1$ 步、每步 $S/N$ 字节，以及 reduce-scatter 和 all-gather 两个阶段加在一起。代入 $N=4$、 $S=8\ \mathrm{MiB}$，得到 $2\times3/4\times8=12\ \mathrm{MiB}$，正好是每个 rank 的发送量；接收量也约为 $12\ \mathrm{MiB}$。公式没有把发送和接收加成一个数，也不是全系统的总流量。固定 $S$ 时， $N$ 越大，每个 rank 的发送量越接近 $2S$。它只是经典 ring 算法的流量估算，不能直接告诉我们训练一步要花多久，也不是所有 collective 的统一通信下界。启动延迟、链路争用、节点内外拓扑和与反向传播的重叠都会影响时间；NCCL 也会按拓扑选择算法，因此这个公式不是对所有 NCCL 运行时间的承诺。[NCCL collective overview](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html)

### 7.4.7 $\alpha$-$\beta$ 通信模型

上面的 ring 例子只数“要搬多少字节”。实际通信还要花时间启动消息。比如同样传 4 MiB，作为一条大消息发送只付一次启动成本；切成四条 1 MiB 消息，就要付四次启动成本。小消息很多时，启动成本可能很显眼；大消息则更容易受链路带宽限制。令 $\alpha$ 表示每条消息的启动/同步成本， $n_{\mathrm{msg}}$ 表示消息数， $B_{\mathrm{bytes}}$ 表示传输字节数， $\beta$ 表示协议对有效带宽的影响系数。这个简化时间模型写成：

~~~math
T_{\mathrm{comm}}
\approx
\alpha n_{\mathrm{msg}}
+
\frac{\beta B_{\mathrm{bytes}}}{\mathrm{link\ bandwidth}}
~~~

用一组假设值代入：令 $\alpha=0.25$ ms、 $\beta=1$，有效链路带宽为 4 GiB/s；此处取 $\beta=1$，不额外计协议折损。4 GiB 等于 4096 MiB，所以搬运 4 MiB 的传输时间约为 $4/4096$ 秒，即 0.977 ms。传一条 4 MiB 消息，总时间约为 $0.25+0.977=1.23$ ms；若把相同的 4 MiB 分成四条 1 MiB 消息，并假设它们依次发送，总时间约为 $4\times0.25+0.977=1.98$ ms。两种情况传的字节数相同，差别来自四条消息要付四次启动成本。这里的数值只为演示公式，且假设消息串行；真实通信可能并行分块或与计算重叠，不能用这笔账精确预测训练时间。

模型把固定启动成本和随字节数增长的传输成本分开，适合比较量级，不足以精确预测单步训练耗时，因为通信可能分块、并行或与计算重叠。

## 7.5 训练状态显存：DDP、ZeRO 和 FSDP

### 7.5.1 DDP 的常驻状态

先只看一个参数：BF16 权重占 2 字节，BF16 梯度占 2 字节；AdamW 保存的一阶、二阶优化器状态各用 FP32，就各占 4 字节。这样一项参数连同它的梯度和 Adam 状态一共占 12 字节。

DDP 会在每张卡上各放一整份权重、梯度和优化器状态。所以 7B 参数的模型即使有 8 张卡，每张卡上这三类状态仍约占 7B × 12 = 84 GB。想象 8 个人各拿了一本完整的同样的书：卡变多了，但每张卡上那本书没有变薄。

把这个账本写成通用公式。设参数量为 $P$，参数、梯度和优化器状态每元素分别占 $b_{w}$、 $b_{g}$、 $b_{o}$ 字节；忽略激活值和临时缓冲区，DDP 单卡常驻状态约为：

~~~math
M_{\mathrm{DDP}}
\approx
P(b_{w}+b_{g}+b_{o})
~~~

这里 AdamW 的两个状态都是 FP32，所以 $b_{o}=8\ \mathrm{bytes}$；若实现还保存 FP32 主权重副本，也要另外加上。这个公式只算参数、梯度和优化器状态，不是完整峰值：前向和反向还会产生激活值和工作区。

下面的 ZeRO 估算都假设参数、梯度和状态能在 $N_{\mathrm{dp}}$ 个 DP rank 间均匀分片。实际框架可能为了对齐补空位、把小参数合并到缓冲区、为通信临时留空间，显存分配器也可能保留暂时未使用的显存，所以真实峰值会高于这笔稳态账。

### 7.5.2 ZeRO-1

ZeRO-1 只把优化器状态分给不同 rank，权重和梯度仍各存一整份。用 8 个 rank 算一个参数：权重占 2 字节、梯度占 2 字节；Adam 的 8 字节状态平均由每个 rank 负责 1 字节。因此每个 rank 为这个参数留下 2+2+8/8=5 字节：

~~~math
M_{\mathrm{ZeRO1}}
\approx
P(b_{w}+b_{g})
+
\frac{Pb_{o}}{N_{\mathrm{dp}}}
~~~

这就是 ZeRO-1 比 DDP 少占显存的来源；如果放不下的主要是权重或梯度，这一阶段还没有把它们切开。

### 7.5.3 ZeRO-2

ZeRO-2 再把梯度也分片。还是 8 个 rank：权重仍占 2 字节；梯度与 Adam 状态共 2+8=10 字节，平均每 rank 负责 10/8=1.25 字节。每个 rank 合计约 2+1.25=3.25 字节：

~~~math
M_{\mathrm{ZeRO2}}
\approx
Pb_{w}
+
\frac{P(b_{g}+b_{o})}{N_{\mathrm{dp}}}
~~~

reduce-scatter 后，每个 rank 只保留自己负责的梯度 shard。权重仍是完整副本，所以如果单卡连权重都放不下，ZeRO-2 仍不够。

### 7.5.4 ZeRO-3

ZeRO-3 连权重也切分。同一个参数的 12 字节状态由 8 个 rank 分担，每个 rank 平均留下 12/8=1.5 字节：

~~~math
M_{\mathrm{ZeRO3}}
\approx
\frac{P(b_{w}+b_{g}+b_{o})}{N_{\mathrm{dp}}}
~~~

这是平时的分片量，不表示每张卡永远只会看到 1/8 的权重。计算某个模块前，rank 可能要 all-gather 该模块的完整参数，算完再 reshard 或释放。常驻显存少了，但需要额外通信，因此显存和速度要一起看。

### 7.5.5 FSDP 的模块生命周期

以一个 wrapped Transformer block 为例：每张卡平时只保存这个 block 的参数 shard。数据走到这个 block 时，计算需要完整参数，于是各 rank 先交换分片、临时聚齐；forward 算完后按策略重新分片或释放。backward 时可能再次聚齐参数，算出梯度后再把梯度 shard 分回各 rank：

~~~text
平时：每张卡只保存这个 block 的一片参数
  -> 前向计算前：all-gather，临时拿到完整参数
  -> 执行这个 block 的前向计算
  -> 按策略重新分片或释放完整参数
  -> 如果前向后重新分片，反向计算前再次 all-gather
  -> 计算梯度，再用 reduce-scatter 分回各自的梯度分片
  -> 每张卡更新自己负责的参数和优化器状态
~~~

因此，平时看到的参数 shard 不是全部显存故事；block 正在计算时，完整参数会短暂出现。具体何时 gather 和释放，会受 FSDP 版本、配置和执行顺序影响。例如，forward_prefetch 会提前准备下一个模块的参数；reshard_after_forward 决定 forward 后是否重新分片；mixed precision 会改变计算时使用的数值精度；wrap policy 决定哪些模块各自成为通信单元。上面是帮助理解的生命周期，不能代替具体版本的 API 行为。

### 7.5.6 Wrap 粒度的取舍

假设模型有 12 个 Transformer block。若把 12 个 block 一起包成一个大单元，开始计算时要一次聚齐更多参数，峰值会更高；若每个 block 各自包成小单元，一次只聚齐一个 block，峰值通常较低，但需要发起更多次通信。

wrap 是划定 FSDP 每次聚齐、计算和释放哪一组参数的边界。

wrap 太细时：

- all-gather 次数变多；
- 小通信消息增加；
- GPU 计算和通信更难重叠。

wrap 太粗时：

- 一次 all-gather 的参数更多；
- 峰值显存变高；
- 释放时机更晚。

该选多大的单元，要看实际模块大小、峰值显存和通信能否与计算重叠；“用了 FSDP”本身不能确定显存和速度。

### 7.5.7 Offload 与分片不是一回事

两种办法都可能让 GPU 显存下降，但做法不同。假设一份模型的 Adam 状态要占 8 GB：offload 是把这份状态从 GPU 挪到 CPU 内存或 NVMe；若 8 个 rank 对它做分片，每个 rank 平时只保存约 1 GB。两者可以一起用，但后果不同：offload 要在 GPU 和主存/磁盘之间搬数据，分片要在 rank 之间交换数据。报告结果时应区分：

| 现象 | 需要报告什么 |
| --- | --- |
| 单卡 GPU 峰值显存下降 | GPU 峰值显存 |
| CPU/NVMe 占用增加 | 主机内存或磁盘占用 |
| 计算等待数据 | PCIe/NVLink/网络传输时间 |
| 常驻显存下降但峰值未降 | 临时 all-gather 造成的峰值 |

### 7.5.8 用一组数字比较 DDP、ZeRO 与 FSDP

现在把每参数账本乘以 7B，并设 DP size 为 8。不计 FP32 master weights、激活、通信 buffer 和临时 all-gather。按前面算出的每参数占用量，逐项得到：

~~~text
DDP:    12 bytes × 7B                    = 84 GB
ZeRO-1: (2 + 2 + 8/8) bytes × 7B         = 35 GB
ZeRO-2: (2 + (2 + 8)/8) bytes × 7B       = 22.75 GB
ZeRO-3: (2 + 2 + 8)/8 bytes × 7B         = 10.5 GB
~~~

下面把结果并排列出。GB 按十进制计算；GiB 按 1024³ 字节计算，所以 84 GB 约为 78.2 GiB：

| 方案 | 每卡参数、梯度和优化器状态估计 | 仍然完整复制的状态 |
| --- | ---: | --- |
| DDP | $84\ \mathrm{GB}=78.2\ \mathrm{GiB}$ | 参数、梯度、优化器状态 |
| ZeRO-1 | $35\ \mathrm{GB}=32.6\ \mathrm{GiB}$ | 参数、梯度 |
| ZeRO-2 | $22.75\ \mathrm{GB}=21.2\ \mathrm{GiB}$ | 参数 |
| ZeRO-3 / FSDP full shard | $10.5\ \mathrm{GB}=9.8\ \mathrm{GiB}$ | 平时无完整副本；计算时仍会短暂聚齐模块参数 |

这组数回答的是“参数、梯度和优化器状态的稳态占用是多少”，不保证训练峰值能装进卡。ZeRO-3/FSDP 还要为 all-gather、激活值、CUDA/NCCL 工作区和显存分配器预留空间；即使状态只占 9.8 GiB，实际运行仍可能 OOM。ZeRO 原论文也逐步切分优化器状态、梯度和参数，但论文表格采用自己的精度和主权重账本，不能把其中的数字直接与这组假设对比。[ZeRO 原论文 §3、Table 1](https://arxiv.org/abs/1910.02054)

说 FSDP 时还要说清接口版本。PyTorch FSDP1 用 `FullyShardedDataParallel` wrapper，把许多参数展平成较大的参数块（flat parameter）再分组；FSDP2 用 `fully_shard`，以 `DTensor` 等方式表示分片参数，通常按 Transformer 子模块一层层设置。两者都可能在计算前 all-gather、在梯度阶段 reduce-scatter，但参数表示、状态字典和分组边界不同。看代码时应按具体版本解释，不能把 FSDP1 的设置直接当作 FSDP2 的行为。[PyTorch FSDP2 2.15：FSDP1 对照、`fully_shard` 分组](https://docs.pytorch.org/docs/2.15/distributed.fsdp.fully_shard.html)

## 7.6 Tensor Parallelism：把一层矩阵运算分给多张卡

### 7.6.1 列切分线性层

用两张卡算一个很小的线性层。输入 $X=[1,2]$，权重矩阵有两行、四列；不切分时，每一列给出一个输出：

~~~text
X = [1, 2]
W = [[1, 0, 2, 1],
     [2, 1, 0, -1]]
第 1 个输出: 1×1 + 2×2 = 5
第 2 个输出: 1×0 + 2×1 = 2
第 3 个输出: 1×2 + 2×0 = 2
第 4 个输出: 1×1 + 2×(-1) = -1
XW = [5, 2, 2, -1]
~~~

把 W 的前两列给 rank 0，后两列给 rank 1：

~~~text
rank 0 用前两列 -> [5, 2]
rank 1 用后两列 -> [2, -1]
按列拼接       -> [5, 2, 2, -1]
~~~

两张卡算的是四个不同输出位置，所以要把两段按顺序拼起来。

用公式表示，这一层做的是：

~~~math
Y=XW
~~~

若把输出维度切成 $N_{\mathrm{tp}}$ 份：

~~~math
W
=
[W_{1},W_{2},\ldots,W_{N_{\mathrm{tp}}}]
~~~

每个 TP rank 计算：

~~~math
Y_{i}
=
XW_{i}
~~~

最后按最后一维拼接 $Y_{i}$。关键是：列切分产生不同的输出坐标，所以要拼接，不能把各卡的结果相加。

要让 $XW$ 有定义， $X$ 的最后一维必须和 $W$ 的行数相等。如果 $W$ 的输出列数不能被 $N_{\mathrm{tp}}$ 整除，实现必须采用不等长分片或 padding；不能假设每个 $W_{i}$ 都一样宽。

### 7.6.2 行切分线性层

接着看下一层如何用刚才的 [5,2,2,-1]。假设下一层把四个输入数都乘以 1 再相加，完整结果是 5+2+2+(-1)=8。rank 0 负责前两项，得到 5+2=7；rank 1 负责后两项，得到 2+(-1)=1。它们算的不是两个不同输出，而是同一个输出的两部分，因此必须把 7 和 1 相加，得到 8：

~~~text
rank 0: [5, 2]  -> 7
rank 1: [2, -1] -> 1
归约: 7 + 1 = 8
~~~

这就是行切分：输入维度被切开，每张卡算同一个输出的一部分。一般形式是：

~~~math
W
=
\begin{bmatrix}
W_{1}\\
W_{2}\\
\vdots\\
W_{N_{\mathrm{tp}}}
\end{bmatrix},
\qquad
X=[X_{1},X_{2},\ldots,X_{N_{\mathrm{tp}}}]
~~~

其中 $X_{i}$ 和 $W_{i}$ 是相互对应的输入片段和权重行片段：

~~~math
Y
=
\sum_{i=1}^{N_{\mathrm{tp}}}X_{i}W_{i}
~~~

因此，列切分把不同输出拼起来；行切分把同一输出的部分结果加起来。两种布局对应不同的数学关系，拼接和求和不能互换。实际做归约时，各 rank 的局部结果必须代表相同输出位置，形状（shape）要对得上，累加时使用的数值类型（dtype）也要兼容。

### 7.6.3 Attention 中的 TP

假设 attention 有 16 个 head，TP 使用 2 个 rank。可以让 rank 0 计算 head 0–7，rank 1 计算 head 8–15。每张卡得到的是不同 head 的结果；输出 projection 再把这些结果组合起来。常见做法把输出 projection 按输入维切开，让每个 rank 算出同一输出的一部分，再把部分结果归约相加；具体通信方式要看这一层采用的矩阵布局。

TP 让每张卡只存、只算一部分层内矩阵，但这些分片不能各自独立完成整层。切分有这些好处：

- 单层矩阵参数和计算分摊；
- 每张卡处理更窄的层内向量；
- 让单层超过单卡容量的模型可以执行。

也会增加这些成本：

- 每层或每个 block 的 collective；
- TP 通信发生得频繁，组内需要高带宽、低延迟互连；
- TP 并行度增大后，每张卡上的矩阵可能太小，GPU 利用率反而下降。

### 7.6.4 词表和 embedding 的特殊情况

词表也可以切给不同 rank。假设词表有 8 个 token id：rank 0 存 id 0–3 的 embedding 行，rank 1 存 id 4–7。在一种按词表分片的实现里，输入 id 6 时，rank 0 在自己的分片里找不到它，就对这个位置贡献零向量；rank 1 取出 id 6 对应的 embedding 行。两个 rank 合并后，序列中就有了正确的向量。

输出层也类似：rank 0 算 id 0–3 的 logits（softmax 前的分数），rank 1 算 id 4–7 的 logits。计算全词表的 softmax 交叉熵仍然需要目标 token 的分数和全词表的归一化信息，但各 rank 可以只交换全局最大值、指数和等必要统计量，不一定把所有 logits 都复制到每张卡。若后续操作确实需要完整 logits，再执行相应的收集。

因此检查 TP 布局时，不能只看 Transformer block；embedding、输出 head、loss 和权重共享也要沿着数据经过的顺序一起检查。

### 7.6.5 TP 的拓扑边界

回到 16 个 attention head 的例子：这种切分会出现在许多层里，每层都可能交换一次或多次结果。如果两个 TP rank 在同一台机器上，数据可以走 NVLink 等高速互连；如果它们跨机器，层层通信都会经过网络。因此 TP group 通常优先放在同节点的高速互连内。跨节点是否值得，要看网络带宽、拓扑、消息大小和计算能否覆盖通信时间。

## 7.7 Pipeline Parallelism：切分模型层

### 7.7.1 Stage 和 micro-batch

Pipeline Parallel（流水线并行，PP）沿模型的前后顺序切分层。下面把模型分成两个 stage：前几层放在 stage 0，后几层放在 stage 1。一个样本先在 stage 0 计算，再把中间激活传给 stage 1。

~~~text
stage 0: embedding + 前半段 Transformer blocks
stage 1: 后半段 Transformer blocks + loss
~~~

如果只送一个 micro-batch，stage 0 把激活送走后可能要等很久。把一个 global batch 拆成多个 micro-batch 后，stage 0 可以继续处理后面的 micro-batch，stage 1 则处理先到的 micro-batch。这样两个 stage 有机会同时工作。

### 7.7.2 Pipeline bubble

先把两个 stage、三个 micro-batch 摆在时间线上。`F1` 表示 micro-batch 1 的前向，`B1` 表示它的反向；`—` 表示这个 stage 正在等数据。GPipe flush 会先把所有 micro-batch 前向送完，再开始反向：

| 时间槽 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| stage 0 | F1 | F2 | F3 | — | — | B3 | B2 | B1 |
| stage 1 | — | F1 | F2 | F3 | B3 | B2 | B1 | — |

启动时，stage 1 还没收到 stage 0 的结果；前向结束后，stage 0 又要等 stage 1 的梯度回来。表中每个 stage 有 6 个有效计算槽、2 个空闲槽。空闲槽就是 pipeline bubble（流水线空泡）。micro-batch 增多时，同样的启动和排空等待由更多有效工作分摊。

对 stage 时间相同的简单 flush schedule，设 $p$ 为 stage 数、 $m$ 为 micro-batch 数。常见资料会用两种分母描述同一批空闲时间：

~~~math
r_{\mathrm{bubble/ideal}}
=
\frac{p-1}{m}
\qquad
r_{\mathrm{idle/total}}
\approx
\frac{p-1}{m+p-1}
~~~

第一种把空闲时间除以理想计算时间，所以叫 bubble overhead；第二种把空闲时间除以“有效计算时间加空闲时间”，所以叫 idle fraction。用上面的 $p=2,m=3$ 代入，前者是 $1/3\approx33.3%$，后者是 $1/4=25\%$。同一张时间线得到不同百分数，是因为分母不同。

再看 $p=8,m=16$：两种比例分别是 $7/16\approx43.8%$ overhead 和 $7/23\approx30.4%$ idle fraction。Megatron-LM 使用前一种口径；GPipe 给出的空闲占比量级与后一种口径对应。比较报告时先看分母，不能把这两个百分数当成同一指标。[Megatron-LM §2.2、§5.3](https://arxiv.org/abs/2104.04473)；[GPipe §2](https://arxiv.org/abs/1811.06965)

这些近似要求 $p$、 $m$ 是正整数；只有一个 stage 时没有流水线空泡。公式假定每个 stage 花费近似相同，也没有算入通信等待和不同 schedule 的交错效果。它适合先估量空泡，不能代替实际时间线。

### 7.7.3 为什么不能无限增加 micro-batch

增加 micro-batch 数可以把启动和排空成本分摊到更多计算上，但训练也会改变其他方面：

- micro-batch 调度和通信事件；
- backward 前需要保留的 activation 数；
- 梯度累积和 loss 归一化步骤；
- 可能的 kernel 小批量效率损失。

如果 micro-batch 大小不变，增加 micro-batch 数也会增加 global batch；如果 global batch 固定，就要把它拆成更多、更小的 micro-batch，小矩阵可能降低 GPU 利用率。实际选择时同时看空泡比例、activation 峰值、有效 token/s 和 global batch。

### 7.7.4 1F1B 的基本思路

1F1B 是 one forward, one backward（一次前向、一次反向）的简称。流水线启动一段时间后，stage 已经有较新的 micro-batch 可以前向，也有较早的 micro-batch 收到反向梯度。调度器就交替安排两类工作，不必等所有 micro-batch 都完成前向才开始反向。

这样可以更早释放已经完成反向的 activation。每个 stage 仍要把前向 activation 发给下一段，并把反向梯度发回上一段。两边必须对齐 micro-batch 编号和 send/recv 顺序；比如下一段在等 micro-batch 3 的梯度，而上一段却发送 micro-batch 2，作业就可能一直等不到匹配的数据。

### 7.7.5 流水线 schedule 的取舍

| schedule | 可以怎样理解它的执行 | 对空泡和激活的影响 | 额外代价 / 适用边界 |
| --- | --- | --- | --- |
| GPipe flush | 所有 micro-batch 先前向，再按依赖做反向 | 启动和排空时有空泡；较早产生的 activation 要等反向才能释放 | 顺序直观，容易核对；显存可能限制 micro-batch 数 |
| non-interleaved 1F1B | 预热后，让前向和反向交替进入流水线 | 更早完成的反向可以释放 activation；仍有启动和排空空泡 | 激活量较容易控制；整体速度受最慢 stage 限制 |
| interleaved 1F1B | 一张卡负责多个不连续的模型块，并交错处理它们 | 可以缩短空转时间 | 每个样本要经过更多块间传递，通信和调度更复杂；额外通信可能抵消空泡收益 |
| ZB1P（ZeroBubble 1P） | 把反向拆成输入梯度和权重梯度，尝试把可延后的权重梯度计算填进空档 | 在满足依赖时有机会减少空泡 | 调度和状态管理更复杂；名称不表示所有配置都能消除空泡 |
| DualPipe（DeepSeek-V3 报告） | 从流水线两端送入 micro-batch，并把前向、反向和通信交错 | 针对跨节点 MoE all-to-all 与 PP 通信重叠 | 报告按 2 倍参数副本、`PP+1` 激活计；stage 数与 micro-batch 数须为偶数；结果属于该系统设计 |

Megatron-LM 的实验说明，interleaved schedule 的收益会随 batch、chunk 数和通信实现变化：较小 batch 时，它可以减少空泡；batch 增大后，普通 1F1B 的空泡已经变小，更多块间通信会缩小甚至抵消差距。该论文在关闭特定 scatter/gather 优化后，也观察到大 batch 下默认 schedule 更快。因此不能只凭“空泡更少”判断吞吐更高；还要量 micro-batch 数、chunk 数、stage 负载和通信时间。[Megatron-LM §2.2、§5.3](https://arxiv.org/abs/2104.04473)；[GPipe §2](https://arxiv.org/abs/1811.06965)

ZeroBubble 的出发点是把 backward 看成两项工作：先计算传回更早 stage 所需的输入梯度，再计算更新参数所需的权重梯度。前一项会影响上游何时能继续；后一项在依赖满足后可以尝试排到空闲槽里。原论文报告了特定模型、调度和显存条件下的结果，不能据此推断任意 pipeline 都没有空泡。DeepSeek-V3 表格中的 ZB1P 公式也只应用于该表的比较口径。[Zero Bubble Pipeline Parallelism](https://arxiv.org/abs/2401.10241)

跨节点 MoE 让两种等待同时出现：micro-batch 要经过不同 PP stage，路由后的 token 还要通过 all-to-all 找到 expert。DeepSeek-V3 技术报告中的 DualPipe 把一个前向/反向 chunk 拆成 attention、dispatch、MLP、combine；反向里的 attention/MLP 又拆成输入梯度和权重梯度，再把这些计算与 all-to-all、pipeline send/recv 重新排布。报告的布局使用 16 路 PP、跨 8 个节点的 64 路 EP、ZeRO-1 DP，不使用 TP；作者称该设置中的通信与计算量约为 1:1。

DualPipe 从流水线两端同时送入 micro-batch，目的是让一部分跨节点传输落在计算时间里。论文 Figure 5 展示 8 个 PP rank 和 20 个 micro-batch；两者都是偶数，可以从两端各推进一组。它不证明 micro-batch 越多就一定越快。论文 Table 2 以 $F$、 $B$、 $W$ 和可重叠的 `F&B` 记 bubble，并把参数副本计为 $2\times$、峰值激活计为 `PP+1`。这些数字依赖作者的布局和记账方法，不能直接套到不同网络、模型分块或 runtime。[DeepSeek-V3 技术报告 §3.2.1–3.2.2](https://arxiv.org/abs/2412.19437)

把论文表中的公式代入一组教学时间，可以看清它比较的是什么。假设 8 个 stage、20 个 micro-batch，测得前向 $F=4\ \mathrm{ms}$、完整反向 $B=7\ \mathrm{ms}$、权重梯度部分 $W=2\ \mathrm{ms}$，以及 `F&B` 对应的重叠时间 $T_{\mathrm{overlap}}=8\ \mathrm{ms}$。按报告的口径：

~~~text
1F1B:     (8-1) × (4+7)        = 77 ms
ZB1P:     (8-1) × (4+7-2×2)    = 49 ms
DualPipe: (8/2-1) × (8+7-3×2)  = 27 ms
~~~

这里的 $T_{\mathrm{overlap}}=8\ \mathrm{ms}$ 是独立测得或假设的重叠时间，不能直接用 $F+B$ 代替。这些公式也没有算 stage 不均、共享资源争用和额外参数副本的完整显存影响，所以它们适合解释论文内的比较，最终选择仍要看目标作业的 trace 和峰值显存。

### 7.7.6 Stage 划分不均

如果某个 stage 的层计算更重、参数更多或 activation 更大，整个 pipeline 的速度由最慢 stage 决定。平均分层数不等于平均工作量。

划分时应考虑：

- 每层 forward/backward 时间；
- 参数和 optimizer state；
- activation size；
- stage 间传输量；
- embedding、loss 和 MoE 层的特殊成本。

## 7.8 Sequence Parallel 与 Context Parallel

### 7.8.1 Sequence Parallel 的位置

先看 TP 已经切分了什么：两张卡可能各算一部分 hidden/head 维度，但在 LayerNorm、dropout 和 residual 这类逐 token 操作处，每张卡仍可能各自保存整段序列的激活。若 batch 为 1、序列长 4,096、hidden 为 8,192、 $TP=8$，这类完整激活的形状是 `[1,4096,8192]`。Sequence Parallel（序列并行，SP）把这些位置再分给 8 个 TP rank：每张卡只保留 512 个位置，局部形状变为 `[1,512,8192]`。

这个切分过程可以画成：

~~~text
完整 activation [batch, sequence, hidden]
  -> 各 rank 保存 sequence 的不同区间
  -> 局部 LayerNorm/dropout/residual
  -> 在需要矩阵布局时重新交换或聚合
~~~

SP 是 TP 常用的激活布局配套。Megatron 的实现会在需要时用 all-gather 或 reduce-scatter 改变布局：逐 token 操作时各卡持有不同位置，进入需要完整或不同切分方式的矩阵计算时再交换。上面的 shape 只说明这类激活怎样切分，不表示 Transformer 的所有张量都具有同一形状。SP 减少 TP rank 间重复保存的逐 token 激活；它本身不会替 attention 交换完整长上下文所需的 K/V。[Megatron-LM activation memory study §3](https://arxiv.org/abs/2205.05198)

### 7.8.2 Context Parallel 的目标

Context Parallel（上下文并行，CP）处理的是另一件事：把同一个样本的长序列区间分给不同 rank。假设一个样本有 16,384 个 token、 $CP=4$，每个 rank 先负责其中连续的 4,096 个位置。这样本地 query 和序列激活变短，单卡常驻的这部分数据也随之减少。

难点在于，普通 full attention 中，一个 query 可能要和其他 rank 保存的 key/value（K/V）计算注意力。用 8 个 token、 $CP=2$ 看一次因果注意力：rank 0 保存位置 0–3 的 query 和 K/V，rank 1 保存位置 4–7 的 query 和 K/V。

| rank | 本地 query | 因果注意力需要的 key 位置 | 为什么需要跨 rank 数据 |
| --- | --- | --- | --- |
| 0 | 0–3 | 0–3 | 这些 query 不能看未来的 4–7；本 rank 已有需要的 K/V |
| 1 | 4–7 | 0–7 | 这些 query 既要看本 rank 的 4–7，也要看 rank 0 的 0–3 |

因此，rank 1 要取得 rank 0 的 K/V `[0,4)`，才能算位置 4–7 的完整因果注意力。这里的 `[0,4)` 表示位置 0、1、2、3。CP 的 ring 路径让每个 rank 保留自己的 query，并按轮次交换 K/V 区间；收到一块后，把它纳入本地 query 的注意力计算。反向传播时，其他 rank 对这块 K/V 产生的梯度还要送回它的所有者。这个 8-token 例子只展示因果可见范围；实际系统可采用不同 rank 布局、通信协议或稀疏可见性，具体路线要看框架与 attention 算法。

把同一过程放大到 16,384 个 token、 $CP=4$：每个 rank 先负责连续的 4,096 个 query 位置和对应 K/V 区间，再通过通信取得本地 query 所需的其他区间。四个 rank 都处理完所需区间后，各自才得到本地 query 的完整 attention 结果。

把 SP 和 CP 的名字分开还不够，关键要看一层里的张量和通信轨迹：

| 路线 | 每 rank 持有什么 | attention 中交换什么 | 主要收益与代价 |
| --- | --- | --- | --- |
| TP 配套 SP | 按 sequence 切 LayerNorm/dropout 等激活，TP 参数按 hidden/head 切分 | 普通 attention 的 Q/K/V 仍按 TP layout 处理 | 降低逐 token 激活冗余；引入布局转换 collective |
| Megatron CP 的 ring P2P 路径 | 序列区间及该区间的 Q/K/V | 保留本地 Q，按环逐块传 K/V；反向把 K/V 梯度归还相应分片 | 每卡只保留局部序列激活；依赖通信与 attention kernel 重叠，CP group 中权重仍复制 |
| Ring Attention | sequence block 与本地 Q/K/V block | 环形传递 K/V block，并用 online softmax 累积局部 query 的 attention | 不必把完整 score 矩阵放在单卡；长序列扩展受每轮通信、因果 mask 利用率和设备链路制约 |

Megatron Core 文档中的 `p2p` CP 路径会沿 ring 交换 K/V，并在反向阶段归还 K/V 梯度；同一指南也列出 all-gather、a2a 等配置。因此 ring 只是可选通信协议之一。[Megatron Core Context Parallelism](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/context_parallel.html) Ring Attention 则把分块 attention 和 ring 调度作为完整算法提出，不能把它等同于“启用 CP”。[Ring Attention 论文 §3](https://arxiv.org/abs/2310.01889)

回到 16,384 token 的例子：每个 rank 的本地 Q 和序列激活约为完整序列的四分之一；它处理其他 rank 的 K/V 时，仍要为当前传入的块和通信 buffer 留显存。全局 attention 的 token-pair 关系仍然存在。CP 分摊每张卡要保存和计算的部分，并增加卡间的数据交换；它本身不会把 full attention 的全局二次关系变成线性关系。

### 7.8.3 attention 规模和通信

序列长为 $L$ 时，full attention 中每个 query 都可能与 $L$ 个 key 比较，整体关系随 `L²` 增长。CP 把这些 query/key 分到多卡，减少每张卡的局部工作，却要传 K/V。另一些方法改变的是 attention 本身怎么算或能看见哪些位置：

| 机制 | 主要改变 |
| --- | --- |
| FlashAttention | 片上 IO 和中间矩阵物化 |
| Local/sparse attention | 可见性和计算关系 |
| Sequence Parallel | activation 的序列布局 |
| Context Parallel | 长上下文 token 的设备分布 |

因此，长序列都能受益于这些方法，但它们动手的位置不同：FlashAttention 减少中间矩阵的读写，稀疏 attention 减少可见位置，SP 改变逐 token 激活的存放位置，CP 改变 token 区间所在的设备。

## 7.9 混合并行：这些卡怎样排成一份布局

### 7.9.1 3D parallel 的乘积

沿用 7.1.2 的 16 卡例子：4 份数据布局，每份分成 2 个 PP stage，每个 stage 用 2 张卡做 TP。数 rank 时，要把每一种坐标组合各数一次，所以是 $4\times2\times2=16$。一般地，当 DP、TP、PP 各自对应独立的 rank 坐标时：

~~~math
N_{\mathrm{world}}
=
N_{\mathrm{dp}}
\cdot
N_{\mathrm{tp}}
\cdot
N_{\mathrm{pp}}
~~~

7.1.2 的 rank 表展示了一个具体布局。TP、PP、DP 分别描述层内切分、层间 stage 和数据副本；加入 CP 或 EP 时，还要明确它们是否对应额外的独立维度，以及每个 rank 实际属于哪些通信组。

### 7.9.2 为什么 world size 相等还不够

下面两种布局都用 64 张 GPU，但每张卡周围的工作并不相同：

~~~text
配置 A: DP=16, TP=2, PP=2
配置 B: DP=4, TP=8, PP=2
~~~

配置 A 有 16 份数据布局；每份 4 张卡，按 2 个 PP stage 排模型层，每个 stage 用 2 张卡做 TP。配置 B 有 4 份数据布局；每份 16 张卡，按 2 个 stage 切层，每个 stage 用 8 张卡做 TP。A 每次更新可让更多数据布局参与，B 把每层切得更细、需要更多 TP rank 一起交换结果。两种布局的 batch、单卡状态、通信频率和流水线空泡都可能不同。报告“用了 64 张卡”本身，无法说明这些差异。

### 7.9.3 拓扑感知的 rank mapping

TP 会在每一层多次交换结果；PP 主要在 stage 边界传激活；DP 通常在更新时同步梯度。因为交换的频率和数据不同，rank mapping 会影响等待时间。常见做法是先把高频通信放进更快的链路：

~~~text
同机高速互连：优先承载 TP 或高频 CP
跨机高速网络：承载可接受的 DP 或部分 PP
MoE all-to-all：按 expert/rank 位置和网络带宽布局
~~~

这只是排布局的起点。比如一台机器内有高速 NVLink，而跨机器网络带宽较低，就应检查高频 TP 是否被放到了跨机链路上。最终还要结合 GPU 数量、NVLink/PCIe 拓扑、节点间网络、交换机超额订阅、NUMA 和数据加载路径。

DP 也能分成内外两层。例如，节点内的 rank 先分片参数、梯度和优化器状态；跨节点再复制模型状态，或按特定策略继续分片。这样可以让参数 gather/reduce 多发生在本地高速链路上，同时把跨节点显存与通信作为另一项取舍。Megatron Core 的 hierarchical data parallelism（分层数据并行）提供了这类配置；具体 group 成员和 `outer-dp-sharding-strategy` 是框架接口行为，不能只凭“分层 DP”这个名字断言吞吐会提高。[Megatron Core 并行策略指南](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/parallelism-guide.html)

### 7.9.4 并行维度与 batch

TP 和 PP 让卡共同完成一份模型布局；只有 DP 布局的份数直接乘进处理不同数据的有效 batch。若每个样本都含有相同数量 $n_{\mathrm{target}}$ 的有效预测目标，且每个 DP rank 的 micro-batch 大小相同：

~~~math
B_{\mathrm{token}}
=
B_{\mathrm{micro}}
\cdot
n_{\mathrm{target}}
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

内部执行 next-token shift、序列长度为 $L$ 且没有 padding 或其他 mask 时， $n_{\mathrm{target}}=L-1$；其他数据格式应按 7.2.1 的有效目标计数。TP、PP 和 CP 通常不直接扩大 data batch；它们改变的是一个 batch 如何被计算。若把 TP 或 PP degree 错算进 global batch，会导致学习率和 token budget 计算错误。

这个乘积关系要求各并行度是正整数，每个 world rank 恰好映射到布局中的一个坐标。若 CP 或 EP 嵌在已有的 TP/DP 组里，而不是新增加一条互相独立的坐标轴，就不能机械地继续相乘；应回到 rank 成员表，逐个看实际有哪些卡参加每个通信组。

## 7.10 Expert Parallelism：路由 token 怎样找到专家

### 7.10.1 MoE 的 token 路由

Mixture of Experts（专家混合，MoE）层里有一个 router（路由器）和多个 expert（专家网络）。router 为每个 token 给各个 expert 打分，再把 token 送给得分最高的 $k$ 个 expert。先看一个 token：它选中 expert 2 和 expert 5；若这两个 expert 分别在 rank 1 和 rank 3，token 的 hidden state（隐藏状态）就要从当前 rank 发到这两张卡。

一般地，设 token 表示为 $x$，router 的参数为 $W_{r}$，expert 编号为 $e$。router 先算分数并转成概率：

~~~math
p(e\mid x)
=
\mathrm{softmax}(W_{r} x)_{e}
~~~

分数最高的 $k$ 个 expert 组成这个 token 的路由集合：

~~~math
\mathcal{E}(x)
=
\mathrm{TopK}_{e}
p(e\mid x)
~~~

若一个 token 选中多个 expert，各 expert 分别计算后，系统再按 router 权重组合它们的输出。只要选中的 expert 分布在不同 rank，输入和输出就要在这些 rank 之间往返，这也是 MoE 需要 all-to-all 的原因。

### 7.10.2 Expert capacity

设一个 dispatch batch 有 $T_{\mathrm{tok}}$ 个 token，每个 token 选择 $k$ 个 expert，共有 $E$ 个 expert，capacity factor 为 $\alpha$。在均匀路由假设下，每个 expert 的容量可以粗略写成：

~~~math
C_{\mathrm{expert}}
=
\left\lceil
\alpha
\frac{T_{\mathrm{tok}}k}{E}
\right\rceil
~~~

$\alpha>1$ 为路由偏斜预留空间。如果实际分配超过 capacity，系统可能：

- drop 超额 token；
- 用 padding 填满 dispatch buffer；
- 使用 dropless 或动态容量实现；
- 让部分 token 走其他路径。

不同策略会改变训练质量、通信量和 kernel 形状。

这个容量式要求 $T_{\mathrm{tok}}$ 是非负整数， $E\ge1$、 $1\le k\le E$ 且 $\alpha>0$。它给出的是均匀路由下的 buffer 量级；top-k 的多路副本、padding 约定和 dropless 实现都会改变实际每 expert 的可用 slot，容量不能脱离 dispatch 实现比较。

沿用常见的 capacity 记法做一次手算：dispatch batch 有 4096 个 token， $k=2$， $E=16$， $\alpha=1.25$，则总路由 assignment 数为 $4096\times2=8192$，均匀时每个 expert 期望收到 512 个 assignment，固定容量是 $\lceil1.25\times512\rceil=640$。所有 expert 的 buffer 共 $16\times640=10240$ 个 slot，理想均匀时有 2048 个 slot 是 padding 余量。若某个 expert 实际收到全部 assignment 的 30%，就是约 2458 个，固定容量将超出约 1818 个；若实现选择 drop，超出 token 的该层专家计算会被跳过，若改为动态/无 drop dispatch，则会改变 buffer 形状、通信和 kernel 假设。

这说明 $\alpha$ 不是“越大越保险”的免费参数：增大它降低 overflow 的概率，却增加静态 buffer 和潜在空算；减小它节省资源，却提高 drop 风险。Switch Transformer 明确展示了固定容量中空 slot 浪费通信/计算，超额 token 则可能直接跳过该层 expert；GShard 的 top-2 gating 则用第二专家和辅助负载目标处理容量受限路由。它们解决的都是稀疏路由负载，但 top-1 与 top-2 的每 token expert 数、容量预算和计算/通信账本不同，不应只比“expert 数”。[Switch Transformer §2.1](https://arxiv.org/abs/2101.03961)；[GShard §2.2](https://arxiv.org/abs/2006.16668)

### 7.10.3 All-to-all 的两次交换

典型 expert parallel 路径是：

~~~text
本地 token hidden states
  -> 根据 expert 所在 rank 分桶
  -> all-to-all 发送
  -> 本 rank expert 计算
  -> 按原 token 位置重新分桶
  -> all-to-all 返回
  -> combine top-k expert outputs
~~~

因此 MoE 的通信量取决于 token 数、hidden size、top-k、expert parallel group、路由偏斜和是否发送 padding。仅根据总参数量估计 MoE 训练成本会严重低估通信。

### 7.10.4 负载均衡不是只看辅助 loss

路由均衡可以通过 router loss、importance loss、load loss、capacity 和实际计数共同观察。应分别记录：

~~~text
expert token count
expert overflow count
token drop rate
padding ratio
router entropy
all-to-all time
per-expert compute time
~~~

一个辅助 loss 下降，不代表实际 GPU 工作已经均衡；某些 rank 仍可能因为通信或 kernel 形状变慢。

## 7.11 Activation checkpointing：重计算如何影响分布式布局

激活重算会在反向阶段重新执行部分前向计算。第八章解释哪些张量可以重算以及如何估算显存与 FLOPs；本节只追踪重算跨过 FSDP、TP、PP 等分布式边界时，对通信、调度和峰值显存的影响。

### 7.11.1 为什么激活重算会影响并行执行

重算不是与分布式布局无关的一段额外算力。若重算区域经过已分片的模块，运行时可能要再次聚齐该模块参数；若区域内包含 TP 或 CP 操作，相应 collective 或点对点交换仍受原通信组与调用顺序约束；若区域位于 PP stage 内，重算还会延长该 stage 的工作时间，改变各 stage 的等待关系。是否发生额外通信及其次数，取决于 checkpoint 边界、FSDP 的 reshard 策略和具体运行时。

以 FSDP2 为例，`fully_shard` 会在模块前向/反向前聚齐参数，并按配置在计算后重新分片或暂时保留未分片参数。若前向后已经释放参数，而 checkpoint 在反向阶段重新调用该模块，运行时可能需要再次 all-gather。因而同一重算策略在不同 wrap 粒度和 `reshard_after_forward` 设置下，会产生不同通信轨迹。[PyTorch FSDP2 2.15](https://docs.pytorch.org/docs/2.15/distributed.fsdp.fully_shard.html)

### 7.11.2 计算与峰值显存的联合账本

比较是否启用重算时，要把额外计算、暴露在关键路径上的通信和同时存活的临时张量放在同一时间线上：

| 布局 | 重算可能改变的执行 | 需要一起观察的量 |
| --- | --- | --- |
| FSDP | 重进模块时重新 all-gather 参数；预取可能与重算同时占显存 | all-gather 次数与时长、未分片参数窗口、重算峰值 |
| TP / CP | 重放区域中的层内 collective 或 K/V 交换 | collective 时长、通信组等待、可被计算覆盖的比例 |
| PP | 每个 stage 增加重算工作，改变最慢 stage 和流水线空闲槽 | stage 计算时间、bubble、在途 micro-batch 激活 |

因此，“状态分片减少了常驻参数”和“重算减少了保存的激活”都不能单独预测峰值。峰值取决于参数聚集、重算临时量、在途通信 buffer 与其他激活在同一时刻的重叠。

### 7.11.3 与 FSDP、TP、PP 的组合

为组合策略做对照时，应固定模型、有效 token batch、并行布局和计时边界，然后逐项比较重算关闭、选择性重算和目标配置下的重算方案。记录各 rank 的峰值 allocated/reserved 显存、FSDP all-gather 与 TP/CP collective 时间、PP stage 时间、暴露通信量、step time 和有效 target tokens/s。

checkpoint 区域应与模块包装和并行边界一起检查：FSDP 需核对重算会不会触发额外参数聚集；TP/CP 需保证参与者按相同顺序重放通信；PP 需检查重算是否把原本均衡的 stage 变成瓶颈。激活重算的分段、选择对象与额外 FLOPs 详见[第八章显存优化与数值精度](08-显存优化与数值精度.md)。

## 7.12 通信与计算重叠

### 7.12.1 不重叠的时间模型

若一次更新的计算时间为 $T_{\mathrm{comp}}$，通信时间为 $T_{\mathrm{comm}}$，完全串行的时间近似为：

~~~math
T_{\mathrm{step}}
\approx
T_{\mathrm{comp}}+T_{\mathrm{comm}}
~~~

### 7.12.2 理想重叠

若通信和计算完全重叠，理论下界接近：

~~~math
T_{\mathrm{step}}
\approx
\max(T_{\mathrm{comp}},T_{\mathrm{comm}})
~~~

假设同一更新的独立计算段合计 80 ms、通信段合计 30 ms，完全串行需 110 ms，理想全重叠的下界为 $\max(80,30)=80\ \mathrm{ms}$，相对串行的理论加速上限是 $110/80=1.375\times$。若 trace 显示其中 15 ms 通信被隐藏，且这些分段时长按可相加的未重叠工作量测得，则仍暴露 15 ms，估算为 $80+30-15=95\ \mathrm{ms}$。这是一个简化账本；真实通信会争用内存带宽、copy engine 或 GPU SM，不能只从异步 API 调用推断实际隐藏了多少。

真实系统位于两者之间，受以下因素限制：

- collective 是否异步；
- backward 的梯度产生顺序；
- bucket 大小；
- 网络和计算是否使用不同 stream；
- collective 是否争用同一带宽；
- 参数 all-gather 与 kernel 的边界；
- 某个慢 rank 是否拖住全局。

### 7.12.3 DDP bucket overlap

反向传播会按层逐步产生梯度。假设一共有 4 层：第 4 层梯度先就绪，第 3 层随后就绪。DDP 可以把已经就绪的梯度装入 bucket；一个 bucket 装满后，就开始通信，同时 GPU 继续计算更早层的梯度。这样通信有机会躲在后续计算时间里。

bucket 太小时，4 层梯度可能被拆成许多小消息，每条消息都要单独付启动成本；bucket 太大时，系统要等更多梯度就绪才开始发送，可用于重叠的时间变短。

PyTorch DDP 2.15 的 `bucket_cap_mb` 控制 bucket 大小，文档默认 25 MiB。它只是默认起点：变小会增加小 collective 数量，变大可能延后 bucket ready、缩短能与 backward 重叠的窗口；最终要按真实梯度 ready 顺序和 trace 调整。[PyTorch DDP 2.15](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html)

调优时应记录：

~~~text
bucket size
gradient ready order
collective start/end time
backward kernel time
overlap ratio
network utilization
~~~

### 7.12.4 FSDP 的 overlap

FSDP 也能提前准备后面模块的参数。比如当前正在算 block 3，后台可以开始 all-gather block 4 的参数，让它在数据到达 block 4 前准备好。若预取太早，block 3 还没算完时，block 4 的完整参数就占着显存；若预取太晚，block 4 会停下来等 all-gather。合适时机取决于 wrap 粒度、模块大小和网络速度。

PyTorch 2.15 的发布说明给出一些版本化例子：FSDP2 可让精度敏感的参数（如 router gate、norm weight）保留 FP32，同时让其余参数使用 BF16；还支持 CUDA graph 捕获梯度累积并调整逐参数 gradient dtype。Pipeline Parallel 则改为在每次接收前分配 receive buffer，并在发送完成后释放 forward output。这些变化说明 overlap 与峰值行为会受 runtime 版本和缓冲区生命周期影响；它们是 2.15 的接口/实现能力，不代表其他框架或旧版本具有相同机制。[PyTorch 2.15 发布说明，2026-10-28](https://pytorch.org/blog/pytorch-2-15-release-blog/)

### 7.12.5 overlap 不是免费加速

即使时间线看起来有重叠，通信也可能占用计算所需的内存带宽、PCIe 或 GPU copy engine。报告“通信与计算重叠”时，应给出实际 step time、通信占比和 GPU kernel 时间，而不是仅凭异步 API 的存在作结论。

## 7.13 Checkpoint 与分布式恢复

### 7.13.1 需要保存哪些状态

把训练检查点（checkpoint）想成一次可复走的训练现场。若只保存模型权重，恢复后可以继续做推理，却未必能继续同一条训练轨迹。要接着训练，至少还要知道：

~~~text
model parameter shards
gradient or optimizer shards when needed
optimizer states
scheduler state
scaler state
global optimizer step
micro-step and accumulation position
data sampler state
RNG（随机数生成器）state for each rank
world-size and parallel topology
model/config/tokenizer version
~~~

保存时机决定是否还要保存梯度。若在 optimizer step 100 完成后保存，这一步的梯度已经用于更新，通常不需要为恢复下一步另存梯度；若在一个 4-micro-step 累积窗口的第 2 步后保存，则要保留已经累积的梯度、当前累积位置，以及按当前归一化口径累计的有效目标数。否则恢复后若从 micro-step 1 重来，会重复一部分梯度；若直接从 micro-step 3 接着算，却丢了前两步的梯度，更新也会变。因此，最简单的保存边界是一次 optimizer update 完成之后；只有确实要在累积窗口中间保存，才需要一并恢复未完成的梯度累积现场。正文清单中的 gradient shard 因此是“按保存边界需要”，不是每个 checkpoint 都无条件保存。

若使用 FSDP、ZeRO、TP、PP、EP 或 GaLore 等布局，还要保存能解释这些分片的附加信息：

- parameter flattening 和 shard metadata；
- TP/PP/EP rank mapping；
- projection basis 或其他特殊 optimizer state；
- expert layout 和 router 相关配置；
- checkpoint format version。

### 7.13.2 global checkpoint 与 sharded checkpoint

保存方式有两类。global checkpoint 会把各 rank 的分片聚成较完整的状态，读者恢复时容易看到一个统一对象，但保存瞬间可能需要额外内存和通信。

sharded checkpoint（分片检查点）则让每个 rank 或 rank 组保存自己负责的部分。比如全局向量 `[0,1,2,3,4,5,6,7]` 由两个 rank 分别保存 `[0,1,2,3]` 和 `[4,5,6,7]`。恢复时，manifest（清单）告诉系统每段数据属于哪个全局张量位置：

~~~text
tensor name
global shape
dtype
shard offsets
file name
checksum
parallel topology
creation step
~~~

分片保存适合大状态分布在多个 rank 上的场景。恢复时要按 manifest 中的全局位置重组数据；不能把 `rank0.pt` 直接复制成新集群的 `rank0.pt`，因为新旧 rank 可能负责不同位置。

### 7.13.3 异步 checkpoint 的一致性

异步写盘让训练线程可以继续工作，后台再把状态写到存储。但先要确定“这一份 checkpoint 代表哪一步”。如果参数来自 step 100，optimizer state 来自 step 101，data cursor 又已经前进到 step 102，恢复后会把不同时间的现场拼在一起，无法复现一致的下一步。

若训练系统还要把 DCP 之外的数据游标、配置版本或外部状态声明为同一现场，应用可以维护一份自己的提交标记：

1. 在明确的 optimizer step 边界冻结逻辑状态；
2. 生成不可变的 snapshot metadata；
3. 后台写入 shard；
4. 所有 shard 和必要的外部状态完成后，提交应用层标记；
5. 恢复流程只选择标记确认的同一步现场。

应用层标记用于把模型、optimizer、数据游标等状态绑定到同一训练步，不能与 DCP 自身的 checkpoint metadata 混为一谈。PyTorch DCP 2.15 会并行保存各 rank 的分片，并支持 load-time resharding（加载时重分片）；`async_save` 的 `staging_completion` 表示本地状态副本已准备好，`upload_completion` 表示这次 DCP 保存已完成。文件系统 writer 还会写入全局 `.metadata`，并假设文件创建是原子的。DCP 不负责判断应用另外保存的数据游标是否与模型、optimizer 来自同一步，也不保证不同 PyTorch 版本的 state_dict 向后兼容。恢复测试因此要逐项确认：保存完成、shard 和 metadata 可读、optimizer 与数据游标属于同一步、目标 topology 能读出预期张量。[PyTorch Distributed Checkpoint 2.15](https://docs.pytorch.org/docs/2.15/distributed.checkpoint.html)

### 7.13.4 改变 world size 后恢复

换 DP 数量时，参数和 optimizer state 的分片边界可能要重排；换 TP 或 PP 数量时，权重还可能要按新的矩阵分片或层段布局重组。看一个长度为 12 的向量：旧 $DP=4$ 时，每个 rank 保存 3 个连续元素；新 $DP=3$ 时，每个 rank 应保存 4 个元素。

~~~text
旧 rank 0: [0,3)   旧 rank 1: [3,6)   旧 rank 2: [6,9)   旧 rank 3: [9,12)
新 rank 0: [0,4)   新 rank 1: [4,8)   新 rank 2: [8,12)
~~~

新 rank 0 要从旧 rank 0 取 3 个元素，再从旧 rank 1 取 1 个；新 rank 1 也要跨旧分片取数据。这才是 resharding（重新分片），不是按 rank 文件名复制。与参数同形的一阶、二阶 optimizer state 也要按相同全局位置重组。DCP 可以处理张量布局的 load-time resharding，应用仍要核对 optimizer state 的映射和 data cursor。

例如保存点为 global step 100，固定长度数据的排列 seed 和全局样本 cursor 48 都写进 manifest。恢复后从同一排列的样本 48 开始，可以避免这个玩具顺序里漏读或重复样本。但如果 reduction 顺序、batch 组成或 RNG 映射变化，浮点运算顺序也会变化；不能承诺下一步结果逐位相同。

恢复流程还应验证：

- 参数 global shape；
- shard 覆盖无空洞无重叠；
- optimizer state 与参数映射；
- 新 topology 的 group；
- scheduler step；
- data cursor 和有效 token 计数。

2026 年的一项早期研究进一步尝试在训练进行中直接改变并行布局，不停在“从 checkpoint 重新启动”。DynaTrain 预印本提出 Virtual Parameter Space（虚拟参数空间：以全局逻辑张量坐标描述参数和状态，不把语义绑定到当前 rank 切片）、rank-local state routing（按目标布局迁移各 rank 拥有的状态片段）和并行布局切换机制；作者在 70B dense 与 235B MoE 案例中报告重配置时间分别低于 2 秒和 4.36 秒。这是论文作者在所测系统和配置下的结果，不是 PyTorch DCP 的默认能力、标准恢复流程或已被多集群复现的性能保证；读者可把它视为弹性训练研究候选，而不是生产默认方案。[DynaTrain，arXiv v1，2026-05](https://arxiv.org/abs/2605.18815)

## 7.14 故障与恢复：一个 rank 出错，为什么整组训练会停下来

### 7.14.1 一个 rank 失败为什么会影响全局

设 rank 0 和 rank 1 正要做一次 all-reduce。rank 0 已经算完梯度并进入通信；rank 1 却在读取数据时发生异常并退出，没有进入 collective。rank 0 此时没有办法单独完成这次归约，只能等待 rank 1。一个 rank 的异常就会表现成整个作业卡住。

排查时要知道每个 rank 卡在什么动作，因此故障日志至少要留下：

~~~text
rank and host
current collective name
sequence number
global step and micro-step
batch/data cursor
GPU memory and NCCL error
last completed checkpoint
~~~

如果只留下“程序卡住了”，就分不清 rank 1 是运行较慢、走了不同通信分支，还是设备真的失联。

### 7.14.2 collective 顺序不一致

all-reduce、broadcast、send/recv 等操作要能一一对应。下面任一情况都可能让某些 rank 永远等不到匹配操作：

- 某个分支只在 rank 0 调用了 broadcast；
- 某个 rank 的 empty batch 跳过了 all-reduce；
- MoE 路由导致不同 rank 调用不同次数的 collective；
- exception 被局部捕获，其他 rank 不知道；
- PP 的 send/recv micro-batch id 不匹配。

所有会影响 collective 次数和顺序的控制流都必须跨 rank 一致，或使用明确的协议处理空输入。

### 7.14.3 恢复点的选择

假设 step 101 的 checkpoint 只写完 3 个 rank 的 shard，第 4 个 rank 在写盘时失败。DCP 保存尚未完成，或应用层提交标记还未写出，因此不能把这个目录当作 step 101 的可恢复现场。通常从上一个完整 checkpoint 恢复，并根据 data cursor 记录哪些样本可能重跑。

### 7.14.4 数据一致性与样本重复

若恢复时只加载模型权重，没有加载 sampler state（采样器状态），训练数据也会改变。比如模型回到 step 100，但 dataloader 从新 epoch 的开头继续，就可能：

- 某些 shard 重复；
- 某些 shard 被跳过；
- rank 之间重新分配不一致；
- validation 时间点发生偏移。

因此 token budget 和数据去重统计要看恢复后的真实 cursor，而不能只看 optimizer step。

## 7.15 怎样看出训练慢在哪里：分布式训练的可观测性

### 7.15.1 训练级指标

如果训练突然变慢，先要确认慢的是整步、数据输入还是某类通信。因此每个 optimizer step 至少记录：

~~~text
global step
micro-step
effective tokens
train loss
learning rate
grad norm
parameter norm
tokens per second
step time
checkpoint id
~~~

### 7.15.2 rank 级指标

全局平均值会掩盖慢 rank。假设三个 rank 用时 1 秒，第四个 rank 用时 2 秒；all-reduce 必须等第四个 rank，其他三张卡也不能提前开始下一步。因此每个 rank 或 process group 还应记录：

~~~text
rank and host
GPU memory allocated/reserved
forward time
backward time
optimizer time
collective time by type
data wait time
communication payload
kernel idle time
~~~

至少同时看最大、最小、平均和分位数，并把异常 rank 对到所在 host、group 和 step。

### 7.15.3 MoE 和 PP 的专用指标

不同并行方式还要补各自的局部量。MoE 看每个专家是否收到相近数量的 token：

- 每 expert token count；
- overflow/drop；
- all-to-all time；
- expert compute time；
- router entropy。

PP 看哪个 stage 先完成、哪个 stage 让其他 stage 等待：

- 每 stage forward/backward time；
- stage idle time；
- send/recv time；
- micro-batch queue；
- activation memory。

TP/FSDP 则看参数和梯度分片交换了多久、交换时额外占了多少显存：

- all-gather/reduce-scatter 时间；
- shard size；
- transient memory；
- wrap/module 级别事件。

### 7.15.4 用时间线而不是单一平均数

即使两个实验的平均 step time 都是 1 秒，时间线也可能很不一样：

~~~text
实验 A：计算占主导，通信已重叠
实验 B：通信占主导，GPU 等待网络
实验 C：某个 rank 慢，其他 rank 在 collective 等待
实验 D：pipeline bubble 很大
~~~

只看平均值无法判断应该调 batch、调通信还是重新分配 stage。要把 profiler trace、collective 日志和 rank 时间线对齐，找到等待真正发生的位置。

### 7.15.5 MFU、HFU 与吞吐口径

Tokens/s（每秒处理的 token 数）回答“训练推进得多快”，但不能单独说明设备的计算单元利用得怎样。PaLM 论文定义了 Model FLOPs Utilization（模型浮点运算利用率，MFU）：用观测到的 token throughput 乘以模型完成前向和反向所需 FLOPs，再除以所有设备的理论峰值算力。activation rematerialization（激活重算）等额外算术不计进 MFU。Hardware FLOPs Utilization（硬件浮点运算利用率，HFU）则把实际执行的算术也计入，包括重算。因此 HFU 会受实现、编译器和 FLOPs 计数方法影响。[PaLM §4.1、Appendix B](https://arxiv.org/abs/2204.02311)

令 $R_{\mathrm{observed}}$ 为实测 token/s， $F_{\mathrm{model/token}}$ 为按既定口径计算的每 token 必要 FLOPs， $F_{\mathrm{executed,step}}$ 为一步实际执行的 FLOPs， $t_{\mathrm{step}}$ 为 step time， $P_{\mathrm{peak,aggregate}}$ 为所有设备峰值算力之和。MFU 和 HFU 可用下面的账本表达：

~~~math
\mathrm{MFU}
=
\frac{R_{\mathrm{observed}}\,F_{\mathrm{model/token}}}
{P_{\mathrm{peak,aggregate}}}
\qquad
\mathrm{HFU}
=
\frac{F_{\mathrm{executed,step}}/t_{\mathrm{step}}}
{P_{\mathrm{peak,aggregate}}}
~~~

计算 $F_{\mathrm{model/token}}$ 时，要说明是否计入 attention、embedding、MoE active experts、padding 和非矩阵运算；峰值算力也要绑定硬件和 dtype。报告 MFU 时，还要写清吞吐分母是输入 token 还是有效目标 token。

PaLM 540B 在其 6144 张 TPU v4 的设置中报告 MFU 46.2%、HFU 57.8%；差距主要来自 activation rematerialization 的额外 FLOPs。HFU 较高只说明按该口径实际执行了更多算术，不能推出训练时间更短。是否值得重算，还要看重算是否让系统容纳更大 batch、提高有效 token/s 或更快完成目标训练；这两个数不应被当作跨硬件排行榜。[PaLM Appendix B](https://arxiv.org/abs/2204.02311)

再用一个纯教学账本核对定义。假设观测吞吐为 1,600 token/s，按约定每 token 必需前向与反向 FLOPs 为 $2\times10^12$，汇总设备峰值为 $8\times10^15 FLOP/s$，则 $MFU=1600\times2\times10^12/(8\times10^15)=0.40$，即 40%。若实测实现还为每 token 执行了额外 $1\times10^12$ FLOPs 的重算，则 $HFU=1600\times3\times10^12/(8\times10^15)=0.60$，即 60%。本例数值全是演示假设：较高 HFU 只表示实际执行算术占峰值比例较高；判断训练是否更快，仍比较目标质量下的 token/s、step time 和完成训练所需墙钟时间。

## 7.16 如何选择并行方式

### 7.16.1 先确认瓶颈

先观察一次更新具体卡在哪里。比如 GPU 利用率低，并不自动说明 GPU 太少；它也可能在等数据、等网络或等前一个 stage。选择并行方式前，先测：

1. 单卡能否容纳参数、梯度、optimizer state 和激活？
2. 单卡 forward/backward 的计算时间是多少？
3. data loader 是否已经让 GPU 等待？
4. 目标网络的节点内、节点间带宽如何？
5. sequence length、batch 和 MoE 路由的分布是什么？

若多数 step time 花在 data wait，增加 TP 或 PP 不会让数据更早到达。先把当前最长的等待找出来，再选针对该等待的办法。

### 7.16.2 一个保守的决策顺序

可以按下面的顺序建立基线。每一步只加入一种主要切分，观察它是否解决当前瓶颈：

~~~text
模型和状态能放单卡
  -> DDP baseline

状态放不下但单层可切
  -> ZeRO/FSDP，再测通信

单层矩阵放不下或算力不足
  -> Tensor Parallel

模型层太深或参数总量过大
  -> Pipeline Parallel

长序列激活成为瓶颈
  -> activation checkpointing，再考虑 SP/CP

MoE 动态路由成为瓶颈
  -> Expert Parallel 和 all-to-all 优化

仍然不足
  -> 组合 DP/TP/PP/CP/EP，并做拓扑映射
~~~

这是一种便于定位因果的试验顺序，不是每个模型都必须照着走。每加入一种并行方式，就把它与上一版的验证集质量、峰值显存和吞吐量比较；若吞吐变了，也能知道是哪一步引起的。

### 7.16.3 64 张 GPU 的两个对照

假设有 64 张 GPU：

~~~text
配置 A: DP=16, TP=2, PP=2
配置 B: DP=4, TP=8, PP=2
~~~

配置 A 有更多份数据布局，TP 组较小；配置 B 的每层分给更多卡，TP collective 也更频繁。若 B 的 TP rank 跨节点，而节点间链路较慢，增加的层内通信可能超过它带来的计算收益。即使两者都用 64 张卡，也不能只看 GPU 数就判断哪一个更快。

比较时应记录：

~~~text
per-rank parameter state
effective tokens per update
TP/PP/DP group topology
communication time
pipeline bubble
GPU utilization
validation loss per token
checkpoint throughput
~~~

## 7.17 一个分布式资源账本示例

在前面的章节里，读者已经分别算过有效 token、ZeRO 状态、ring 通信和 MoE capacity。下面把同一类计算放进一个小账本，检查几个数字是否彼此一致。配置用了 6B 参数、 $DP=8$、 $TP=4$、 $PP=2$，因此 $8\times4\times2=64$ 张 GPU。假设 TP/PP 均匀切分参数，每张 TP/PP rank 负责 $6B/(4\times2)=0.75B$ 个参数；8 个 DP rank 对应每个这样的模型分片做复制或状态分片。每个 DP rank 的 micro-batch 有 2 个样本、每个样本 4,095 个有效目标、累积 4 次，所以整次更新有 $2\times4095\times4\times8=262{,}080$ 个有效目标。

代码只用 Python 标准库，不启动真实分布式进程。它把这些输入代入函数，估算：

- 64 GPU 的 DP/TP/PP world size；
- DDP 与 ZeRO 各阶段的状态量级；
- ring all-reduce 每 rank 的发送量和理想传输时间；
- input-token 与有效 prediction-target batch；
- pipeline bubble；
- MoE expert capacity 与偏斜路由溢出；
- activation checkpointing 的分段 toy 峰值代理。

例如，在这组 TP/PP 布局下，状态账本给每卡 DDP 约 8.4 GiB、ZeRO-3 约 1.05 GiB；这仍不包含激活和临时 all-gather。若每个 DP rank 归约一个 1 GiB 梯度 bucket，ring 函数给出每 rank 约发送 1.75 GiB，按 200 GB/s 理想带宽估算约 0.0094 秒；真实通信还会有消息启动、协议和链路争用。示例中的数值都是教学输入，用来检查单位和量级，不能替代目标硬件 profiler 或真实 collective 测量。

> **代码状态：静态审阅，未运行（2026-11-24）。** 仅依赖 Python 标准库；不执行分布式通信。

~~~python
import math


GIB = 1024 ** 3


def finite_number(name, value, *, positive=False, nonnegative=False):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError(f"{name} must be a finite number")
    value = float(value)
    if not math.isfinite(value):
        raise ValueError(f"{name} must be finite")
    if positive and value <= 0.0:
        raise ValueError(f"{name} must be positive")
    if nonnegative and value < 0.0:
        raise ValueError(f"{name} must be nonnegative")
    return value


def positive_int(name, value):
    if isinstance(value, bool) or not isinstance(value, int) or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def nonnegative_int(name, value):
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise ValueError(f"{name} must be a nonnegative integer")
    return value


def required_config(config, name, *, integer=False, positive=False,
                    nonnegative=False):
    if name not in config:
        raise ValueError(f"missing config field: {name}")
    if integer:
        return (positive_int if positive else nonnegative_int)(name, config[name])
    return finite_number(
        name,
        config[name],
        positive=positive,
        nonnegative=nonnegative,
    )


def gib(byte_count):
    byte_count = finite_number("byte_count", byte_count, nonnegative=True)
    return byte_count / GIB


def memory_estimates(config):
    params = required_config(config, "params", integer=True, positive=True)
    weight_bytes = required_config(config, "weight_bytes", positive=True)
    grad_bytes = required_config(config, "grad_bytes", positive=True)
    optimizer_bytes = required_config(
        config, "optimizer_state_bytes", nonnegative=True
    )
    dp = required_config(config, "dp", integer=True, positive=True)
    tp = required_config(config, "tp", integer=True, positive=True)
    pp = required_config(config, "pp", integer=True, positive=True)
    model_parallel_size = tp * pp
    if params % model_parallel_size:
        raise ValueError("params must divide evenly across TP and PP")
    local_params = params // model_parallel_size
    weights = local_params * weight_bytes
    gradients = local_params * grad_bytes
    optimizer = local_params * optimizer_bytes
    return {
        "ddp_gib": gib(weights + gradients + optimizer),
        "zero1_gib": gib(weights + gradients + optimizer / dp),
        "zero2_gib": gib(weights + (gradients + optimizer) / dp),
        "zero3_gib": gib((weights + gradients + optimizer) / dp),
        "weights_gib": gib(weights),
        "gradients_gib": gib(gradients),
        "optimizer_gib": gib(optimizer),
    }


def ring_all_reduce_sent_gib_per_rank(payload_gib, ranks):
    payload_gib = finite_number("payload_gib", payload_gib, nonnegative=True)
    ranks = positive_int("ranks", ranks)
    return 2.0 * (ranks - 1) / ranks * payload_gib


def ideal_transfer_seconds(payload_gib, bandwidth_gb_per_second):
    payload_gib = finite_number("payload_gib", payload_gib, nonnegative=True)
    bandwidth_gb_per_second = finite_number(
        "bandwidth_gb_per_second",
        bandwidth_gb_per_second,
        positive=True,
    )
    bytes_sent = payload_gib * GIB
    return bytes_sent / (bandwidth_gb_per_second * 1e9)


def pipeline_idle_fraction_total(stage_count, micro_batch_count):
    stage_count = positive_int("stage_count", stage_count)
    micro_batch_count = positive_int(
        "micro_batch_count", micro_batch_count
    )
    return (stage_count - 1) / (
        micro_batch_count + stage_count - 1
    )


def expert_capacity(tokens, top_k, experts, capacity_factor):
    tokens = nonnegative_int("tokens", tokens)
    top_k = positive_int("top_k", top_k)
    experts = positive_int("experts", experts)
    capacity_factor = finite_number(
        "capacity_factor", capacity_factor, positive=True
    )
    if top_k > experts:
        raise ValueError("top_k cannot exceed experts")
    return math.ceil(
        capacity_factor * tokens * top_k / experts
    )


def effective_token_batch(config):
    micro_batch = required_config(config, "micro_batch", integer=True, positive=True)
    valid_targets_per_sample = required_config(
        config,
        "valid_targets_per_sample",
        integer=True,
        positive=True,
    )
    accumulation_steps = required_config(
        config, "accumulation_steps", integer=True, positive=True
    )
    dp = required_config(config, "dp", integer=True, positive=True)
    return micro_batch * valid_targets_per_sample * accumulation_steps * dp


config = {
    "params": 6_000_000_000,
    "weight_bytes": 2,
    "grad_bytes": 2,
    "optimizer_state_bytes": 8,
    "dp": 8,
    "tp": 4,
    "pp": 2,
    "micro_batch": 2,
    "input_tokens_per_sample": 4096,
    "valid_targets_per_sample": 4095,
    "accumulation_steps": 4,
    "gradient_bucket_gib": 1.0,
    "bandwidth_gb_per_second": 200.0,
    "pipeline_micro_batches": 8,
    "routing_tokens": 8192,
    "experts": 8,
    "top_k": 2,
    "capacity_factor": 1.25,
}

memory = memory_estimates(config)
tp = required_config(config, "tp", integer=True, positive=True)
pp = required_config(config, "pp", integer=True, positive=True)
world_size = config["dp"] * tp * pp
effective_tokens = effective_token_batch(config)
ring_sent_gib_per_rank = ring_all_reduce_sent_gib_per_rank(
    config["gradient_bucket_gib"],
    config["dp"],
)
all_reduce_seconds = ideal_transfer_seconds(
    ring_sent_gib_per_rank,
    config["bandwidth_gb_per_second"],
)
idle_fraction_total = pipeline_idle_fraction_total(
    config["pp"],
    config["pipeline_micro_batches"],
)
capacity = expert_capacity(
    config["routing_tokens"],
    config["top_k"],
    config["experts"],
    config["capacity_factor"],
)
ideal_routed_slots = config["routing_tokens"] * config["top_k"]
skewed_peak = math.ceil(ideal_routed_slots * 0.40)
skewed_overflow = max(0, skewed_peak - capacity)

layer_count = positive_int("layer_count", 24)
checkpoint_segment_layers = positive_int("checkpoint_segment_layers", 4)
activation_gib_per_layer = finite_number(
    "activation_gib_per_layer", 1.0, positive=True
)
checkpoint_boundary_count = math.ceil(
    layer_count / checkpoint_segment_layers
)
full_saved_activation_gib = layer_count * activation_gib_per_layer
checkpointed_peak_activation_gib = (
    checkpoint_boundary_count + min(layer_count, checkpoint_segment_layers)
) * activation_gib_per_layer
# A full transformer forward is approximated as 2N FLOPs and training as 6N.
recompute_factor = 8.0 / 6.0

diagnostics = {
    "world_size_ok": world_size == 64,
    "zero3_uses_less_than_zero2": (
        memory["zero3_gib"] < memory["zero2_gib"]
    ),
    "zero2_uses_less_than_zero1": (
        memory["zero2_gib"] < memory["zero1_gib"]
    ),
    "zero1_uses_less_than_ddp": (
        memory["zero1_gib"] < memory["ddp_gib"]
    ),
    "effective_tokens_ok": effective_tokens == 262080,
    "balanced_capacity_ok": (
        capacity * config["experts"] >= ideal_routed_slots
    ),
    "skewed_routing_overflows": skewed_overflow > 0,
    "checkpoint_reduces_activation": (
        checkpointed_peak_activation_gib < full_saved_activation_gib
    ),
}

print("world_size=", world_size)
print(
    "memory_gib=",
    {name: round(value, 2) for name, value in memory.items()},
)
print(
    "zero3_to_ddp_ratio=",
    round(memory["zero3_gib"] / memory["ddp_gib"], 3),
)
print("effective_tokens=", effective_tokens)
print(
    "input_tokens=",
    config["micro_batch"]
    * config["input_tokens_per_sample"]
    * config["accumulation_steps"]
    * config["dp"],
)
print(
    "all_reduce_sent_gib_per_rank=",
    round(ring_sent_gib_per_rank, 3),
)

print("pipeline_idle_fraction_total=", round(idle_fraction_total, 4))
print("expert_capacity=", capacity)
print("ideal_routed_slots=", ideal_routed_slots)
print("skewed_peak_slots=", skewed_peak)
print("skewed_overflow=", skewed_overflow)
print(
    "full_saved_activation_gib=",
    round(full_saved_activation_gib, 2),
)
print(
    "checkpointed_peak_activation_gib=",
    round(checkpointed_peak_activation_gib, 2),
)
print("recompute_factor=", round(recompute_factor, 2))
print("diagnostics=", diagnostics)

assert all(diagnostics.values())
print("distributed ledger toy: ok")
~~~

这个示例中的网络带宽单位是十进制 GB/s（byte/s），不是 Gbps（bit/s）；若输入的是链路标称 Gbps，需要先除以 8，并考虑协议效率。40% 路由偏斜是假设某个 expert 收到全部 routed slots 的 40%，用于展示 capacity overflow；它不是任何真实模型的负载统计。ideal_all_reduce_seconds 只用理想链路带宽除 payload，没有包含启动延迟、协议效率、其他通信和计算重叠。

代码中的 activation 账本再做了一个更明确的简化：24 层、每层 1 GiB 等大激活、每 4 层存一个 checkpoint 边界；峰值粗算为 6 个段输入加正在重算的 4 层，即约 10 GiB，对照保存全部层输出的 24 GiB。它忽略 attention 中间张量、segment 边界细节、micro-batch 流水、TP/SP 以及通信 buffer； $4/3$ 只来自 dense Transformer 的训练约 `6N` FLOPs 加一次额外前向约 `2N` 的粗略口径，不是框架普遍实测比例。

## 7.18 常见故障：从现象回到切分和通信

### 7.18.1 GPU 数量增加但吞吐不变

假设从 8 张卡扩到 16 张卡，step time 仍是 1 秒。先把这 1 秒拆开：

~~~text
data wait
forward
backward
optimizer
collective
checkpoint
~~~

若原来 0.2 秒在通信、扩卡后变成 0.5 秒，就检查 group、bucket、链路拓扑和通信重叠；若 data wait 从 0.1 秒升到 0.4 秒，检查数据 shard、预取和存储；若某个 PP stage 大部分时间空闲，就检查 micro-batch 数和 stage 工作量。相同的 step time 可能由不同瓶颈造成，先拆时间再选调法。

### 7.18.2 某个 rank 显存特别高

若 rank 3 峰值显存比其他 rank 高，先在同一时间点查它正在处理什么。常见原因包括：

- FSDP wrap 粒度导致该 rank 瞬时 all-gather 更大的模块；
- PP stage 参数和激活不均；
- rank 0 额外保存完整 state 或日志对象；
- MoE 路由偏斜；
- 某个 rank 的 batch padding 更多；
- checkpoint 聚合只在少数 rank 进行。

把稳态和峰值显存都记下来，再关联具体 module、rank 和时间点。只看训练开始时的占用，看不到 all-gather、MoE 路由或 checkpoint 聚合时出现的尖峰。

### 7.18.3 作业 hang

两张卡都显示“在 all-reduce”，不代表它们真的进入了同一次通信。先比较每个 rank 最后完成的 collective：

1. 是否所有 rank 都执行到同一个 collective；
2. collective 的 group 和顺序是否一致；
3. 某个 rank 是否在数据加载、OOM 或异常处理里停住；
4. PP send/recv 的 micro-batch id 是否匹配；
5. MoE all-to-all 的 token count 和 buffer shape 是否一致。

如果 rank 0 在等 all-reduce，而 rank 1 的最后一条记录停在 dataloader，就找到了第一处不同。不要先延长 timeout；更长等待时间不会补上缺失的 rank。

使用 PyTorch 2.15 时还可检查该版本的 backend-agnostic flight recorder：官方发布说明称，重写后的 NCCL backend 成为 `nccl` process group 的默认实现，collective hang 可触发事后诊断记录。排查时应把每个 rank 的记录和本章列出的 host、collective 序号、step/micro-step、最后完成的 checkpoint 一起对齐。此能力和开关属于 PyTorch 2.15 的版本行为；旧版、非 NCCL backend 或不同 vendor runtime 不能据此假设有相同记录。[PyTorch 2.15 发布说明，2026-10-28](https://pytorch.org/blog/pytorch-2-15-release-blog/)

### 7.18.4 loss 与单卡不一致

若分布式 loss 与单卡不一致，先让两边使用同一组小数据，再逐项对齐：

- global 有效 token 分母；
- DP rank 是否重复或遗漏数据；
- gradient accumulation 是否按 token 归一化；
- TP/PP 的局部 loss 是否正确聚合；
- dropout、RNG 和数据顺序；
- 混合精度和 collective reduction 顺序。

对同一小 batch 比较局部 loss sum、有效目标数、归约后的梯度和 optimizer 更新，差异第一次出现的位置通常就是口径或布局问题所在。

### 7.18.5 FSDP 省了稳态显存却仍然 OOM

FSDP 让平时保存的参数分片变小，但计算期间仍可能临时聚齐参数。若状态账本显示能放下、真实训练却 OOM，先检查峰值发生的步骤：

- all-gather transient peak；
- activation 未 checkpoint；
- optimizer step 时临时 buffer；
- mixed precision cast 同时保留两份参数；
- wrap 粒度不合理；
- allocator fragmentation。

用 memory snapshot 和 module 时间线把峰值对应到某个模块或 optimizer step；参数 shard 的大小只说明平时保存多少，不能代表峰值。

### 7.18.6 MoE overflow 很高

若 overflow 很高，先看实际 token 被路由到了哪些 expert，再检查：

- top-k 和 capacity factor；
- router logits 和 entropy；
- expert token count 的长尾；
- token dispatch 是否按 expert rank 正确分桶；
- padding 是否吞噬了容量；
- 辅助负载均衡损失是否与实际计数一致。

提高 capacity factor 可能减少 drop，却会增加 padding、显存和通信。调整后要同时看 drop 数、padding、通信时间和 expert 工作量，不能只看 overflow 是否下降。

## 7.20 章节练习：从切分公式到系统设计

### 练习一：全局 token 分母

有 4 个 DP rank，某次更新每个 rank 的有效 token 数分别为 100、100、200、400，未归一化损失分别为 50、80、110、220。计算全局 token-level loss，并比较简单平均 rank means 与按有效 token 加权的结果。

### 练习二：collective 选择

为 DDP 梯度同步、FSDP 参数获取、FSDP 梯度分片和 MoE token dispatch 分别选择 all-reduce、all-gather、reduce-scatter 或 all-to-all，并说明每个操作的输入输出布局。

### 练习三：ZeRO 状态账本

假设参数量为 7B，权重和梯度是 BF16，AdamW 状态是两个 FP32 张量，DP size 为 8。分别估计 DDP、ZeRO-1、ZeRO-2 和 ZeRO-3 的常驻状态量级，再列出 transient all-gather 和 activation 未计入的部分。

### 练习四：TP 矩阵布局

把一个 4096 x 11008 的 MLP up projection 按列切到 4 个 TP rank，再把 down projection 按行切分。写出每个 rank 的局部矩阵形状，并指出哪一步需要拼接、哪一步需要求和。

### 练习五：Pipeline bubble

有 8 个 pipeline stage，分别使用 8、16、32 个 micro-batch。用简化 bubble 公式估计空泡比例，再讨论增加 micro-batch 对 activation 和 global batch 的影响。

### 练习六：MoE capacity

一个 dispatch batch 有 4096 个 token， $k=2$，16 个 expert，capacity factor $\alpha=1.25$。计算均匀路由下的每 expert capacity；再假设一个 expert 收到全部 routed slots 的 30%，估计 overflow，并讨论 padding 和 drop 的代价。

### 练习七：恢复测试

让一个两 rank toy 训练在第 10 个 optimizer step 保存参数 shard、optimizer state、scheduler、RNG、sampler cursor 和 rank mapping。改变 DP size 后恢复，检查参数拼接、数据位置和下一步 loss 是否与预期一致。

### 练习八：定位吞吐回退

比较两个配置：A 使用 $DP=16$、 $TP=2$、 $PP=2$；B 使用 $DP=4$、 $TP=8$、 $PP=2$。若 B 的 GPU utilization 更低，设计一个 profiler 计划，区分是 TP collective、跨节点拓扑、kernel 变小还是 pipeline stage 不均造成的。

### 练习九：pipeline schedule 选型

固定 8 个物理 pipeline stage、16 个 micro-batch，比较 GPipe flush、non-interleaved 1F1B 和 interleaved 1F1B。分别画一个简化执行时间线，计算 bubble/ideal 与 idle/total 两种比例并注明分母，标出哪些 micro-batch 激活何时释放；再根据 Megatron-LM 论文讨论 interleaving 的通信代价，以及什么 profiler 证据会让你放弃 interleaving。

### 练习十：MFU/HFU 报告

PaLM 540B 在论文设置中报告 MFU 46.2%、HFU 57.8%。解释两者分子为何不同；设计一个训练报告模板，固定 token 计数、模型 FLOPs/token、是否计 attention、峰值 dtype、设备数和 step time，并说明为什么不能只凭 HFU 更高就断言系统更快。

### 练习十一：长上下文并行路径

对比 TP 配套 SP、Megatron CP 的 ring P2P 路径与 Ring Attention：逐一标出本地持有的 Q/K/V 分片、前向通信、反向通信和能解决的显存项。假设总 GPU 数固定，说明哪些通信适合节点内高速互连，并设计一个同时看 activation peak、通信占比和 MFU 的对照实验。

## 7.21 本章小结

现在可以把一次分布式更新重新走一遍。先说清楚每张卡拿到哪些样本、模型的哪些部分；再确认局部计算何时要向其他 rank 发送梯度、参数、激活或路由 token；然后用有效预测目标数确定 loss 分母，按需要同步或分片状态。保存时还要把 rank 映射、数据位置和优化器现场一起记录，才能从同一个训练位置恢复。

不同并行方式解决不同问题：DP 让多份模型布局处理不同数据；ZeRO/FSDP 把训练状态分给多个 rank；TP 把一层矩阵分开算；PP 把模型层排成流水线；SP/CP 分别改变序列激活和长上下文的分布；EP 把路由 token 送到专家所在的 rank。组合它们时，rank mapping 决定谁和谁通信，通信组决定哪些数据能合并，rank 的执行顺序决定 collective 能否继续。

设计方案时，把“能否装下”和“能否更快”分开核算：分片可能减少常驻显存，却增加 all-gather 或 reduce-scatter；更多 micro-batch 可能降低空泡，却改变 activation 峰值或 batch；更高 MFU/HFU 也要结合 token/s 和训练总时长看。公式给出量级和检查方法，profiler、有效 token 统计、峰值显存和恢复测试才说明目标集群实际发生了什么。
