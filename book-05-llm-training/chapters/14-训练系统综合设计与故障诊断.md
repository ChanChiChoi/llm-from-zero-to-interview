# 第十四章：训练系统综合设计与故障诊断

训练一个语言模型，真正困难的地方不在于列出 Transformer、AdamW、FSDP 这些名称，而在于把目标、数据、模型、优化、硬件、评估和风险连接成一条可验证的因果链。一个局部配置即使看起来合理，也可能因为数据分布、有效 token 分母、恢复状态或评估协议不一致而失去意义。

本章把前面各章的知识放到几个完整场景中重新组织。先用一个 7B 级别的预训练设计建立总账本，再分别讨论 loss spike、能力回归、数据污染、batch 与学习率、分布式切分、显存、SFT、VLM、成本、模型阶段和偏好优化。每个主题都同时给出直觉、公式、工程证据和失败边界。公式用于建立量级关系，论文用于说明公开机制，框架文档用于说明接口边界，目标系统实测才是具体项目的最终证据。

## 0. 从三个层次理解训练设计

### 0.1 初学者先分清三件事

第一件事是**目标**。预训练模型的目标通常是降低语言建模损失；SFT 的目标是学习示范中的任务行为；偏好优化的目标是提高相对偏好；VLM 还要让文本输出依赖正确的视觉证据。没有目标，参数量、token 数和训练时长都没有可解释的方向。

第二件事是**分母**。训练 loss 的分母可能是有效 label token，吞吐可能是输入 token，GPU-hours 是硬件时间，评估分数又可能是样本级准确率。很多“模型变快了”或“模型变好了”的争议，最后都来自分子分母没有对齐。

第三件事是**证据**。配置文件证明“计划是什么”，日志证明“运行发生了什么”，评估证明“能力是否变化”，恢复演练证明“实验是否连续”。其中任何一种证据都不能替代其他证据。

### 0.2 专家需要额外记录四条边界

专家视角下，一个训练结论至少要注明四条边界：

1. 这是论文机制、框架实现、模型卡声明，还是目标集群实测。
2. 这是理论 FLOPs、有效模型 FLOPs，还是硬件实际执行 FLOPs。
3. 这是某个 checkpoint 的结果，还是跨多个随机种子和数据版本的稳定结果。
4. 这是平均能力变化，还是某个重要领域、风险类别或长尾样本的局部变化。

把这些边界写进实验 manifest，后续才可能解释“同一个配置为什么在另一台机器上不一样”。

## 1. 训练账本：把局部配置连接成系统

训练系统可以看成一条有向链：

```text
目标能力
  -> 数据 mixture 与版本
  -> tokenizer 与样本协议
  -> 架构、上下文和精度
  -> 训练目标与优化器
  -> 并行、显存和吞吐
  -> checkpoint 与恢复
  -> 分层评估与成本决策
```

这条链不是流程图装饰，而是排错时的因果顺序。例如，某个领域 loss 下降但代码能力下降，原因可能不在优化器，而在 mixture 改变；某个节点吞吐上升但有效训练 token 没增加，原因可能是 padding 统计口径变化；恢复后 loss 看起来连续但数据顺序改变，实验就不再是同一次训练。

### 1.1 目标契约

目标契约应明确模型属于哪一阶段、服务哪些任务、哪些能力不能退化，以及资源限制是什么。一个通用 base model 的契约可以包含：语言覆盖、代码比例、数学数据比例、上下文长度、目标验证集和最大训练预算。一个领域模型还要写出领域数据覆盖、术语准确率、关键格式和隐私限制。

目标不能只写“训练一个 7B 模型”。`7B` 只是参数规模，不能说明要优化的能力、训练 token 数、上下文长度和验收标准。相同规模的模型，若一个服务代码补全、另一个服务长文档抽取，它们的数据、序列长度、评估集和成本结构都不同。

### 1.2 证据账本

一个可审计的训练记录至少应包含：

| 记录 | 要回答的事情 | 典型证据 |
| --- | --- | --- |
| 目标记录 | 为什么训练、能力如何衡量 | 任务定义、回归集、约束 |
| 数据记录 | 看到什么数据、哪些 token 有效 | manifest、hash、比例、污染报告 |
| 模型记录 | 哪些参数被计算和更新 | config、参数计数、冻结表 |
| 优化记录 | 每次更新如何产生 | optimizer、scheduler、精度、梯度日志 |
| 系统记录 | 资源如何分摊 | world size、并行拓扑、吞吐、通信 |
| 状态记录 | 中断后能否从同一状态继续 | checkpoint、RNG、数据游标、版本 |
| 评估记录 | 能力变化是否真实 | 分层分数、置信区间、坏例子 |

配置文件只属于计划证据。只有当训练日志、checkpoint manifest 和评估 artifact 互相引用，才形成可追溯的运行证据。

### 1.3 三类数字不能混用

训练规划里常见三种数字：

1. **模型数字**：参数量、层数、hidden size、序列长度。
2. **优化数字**：有效 token batch、学习率、更新次数、梯度范数。
3. **系统数字**：GPU 数量、tokens/s、通信时间、保存时间、GPU-hours。

模型数字决定潜在计算和状态规模，优化数字决定参数如何移动，系统数字决定这些更新多久完成。仅凭系统数字不能推出能力，仅凭模型数字不能推出墙钟时间，只有把三者连接起来，训练计划才有工程含义。

## 2. 7B 预训练设计：从目标到 checkpoint

### 2.1 先定义模型的用途

7B 级别模型可以用于通用语言建模、代码、数学、领域知识或对话底座。用途会改变数据配比、tokenizer、上下文长度和后续阶段。代码模型需要保留缩进、注释、依赖关系和编译反馈；数学模型需要保留推导过程与可验证答案；领域模型需要关注术语、版本和事实时效性；对话底座还要为后续 SFT 保留足够的通用语言覆盖。

若目标是多个能力的组合，应在训练前写出每个能力的独立回归集和最低可接受变化。只写一个整体 validation loss，会让大体量的普通网页数据掩盖小体量但重要的代码或领域退化。

### 2.2 数据 mixture 不是文件拼盘

数据 mixture 的单位应优先使用有效 token，而不是文件数或样本数。设第 `k` 个数据域的有效 token 数为 `D_k`，总有效 token 数为 `D`，则：

```math
w_k=\frac{D_k}{D},
\qquad
\sum_k w_k=1
```

这里要求每个 `D_k\geq0`、总有效 token `D=\sum_kD_k>0`，并在同一 tokenizer、mask 和过滤版本下计数。某个域原始文件很多但所有样本在过滤后没有有效标签时，它的 `D_k` 应为 0，而不是保留旧的文件占比。`w_k` 只是采样比例，不等于最终能力贡献。数据质量、重复率、样本难度、label mask 和训练阶段都会改变一个 token 的实际影响。一个低质量域如果重复十次，可能占据大量更新，却没有带来等量能力；一个小但高价值的代码域可能需要过采样，才能在总 loss 中留下可观测信号。

数据记录至少要保存来源、抓取时间、授权状态、清洗规则、去重 hash、语言或领域标签、有效 token 数和评估隔离关系。数据版本变化后，不能只比较训练 loss，因为输入分布已经改变；应重新计算 per-domain loss、重复率和污染风险。

### 2.3 tokenizer 与上下文预算

tokenizer 影响三件事：同一文本需要多少 token，哪些字符被切碎，以及训练和推理时如何表达代码、数字、多语言和特殊标记。若一个领域的文本被切成更多 token，它会同时增加训练 FLOPs、序列长度压力和有效数据量的估算误差。

上下文长度也不能只写一个最大值。训练时应记录序列长度分布、平均有效长度、padding 比例、packing 规则和截断率。对于固定序列长度 `S` 的训练，单个 batch 的 attention 交互随 `S^2` 增长；对于变长 packing，实际成本取决于每个 packed sequence 的 token 数及 attention mask，而不是样本数量。

### 2.4 架构选择必须绑定约束

decoder-only Transformer 可以作为基线，但层数、hidden size、FFN expansion、head 数、RoPE、RMSNorm、SwiGLU、GQA 和上下文长度都要关联到约束：

| 选择 | 主要影响 | 需要观察的证据 |
| --- | --- | --- |
| 层数与 hidden size | 参数分配、深度、激活和通信 | 参数账本、单步时间、收敛曲线 |
| FFN expansion | 计算量和表达容量 | FLOPs、显存、领域回归 |
| RoPE 与位置方案 | 位置泛化和长上下文 | 长度外推、位置扰动测试 |
| GQA/MQA | KV 状态和推理带宽 | 训练质量、KV 大小、解码吞吐 |
| 上下文长度 | attention 计算、激活和数据覆盖 | 长度分布、padding、长文任务 |

架构名称不是训练方案。一个模型即使采用相同的 block 结构，只要上下文、精度、并行策略或数据配比不同，资源和能力结果都可能不同。

### 2.5 训练目标与优化策略

预训练通常以 next-token prediction 为主。对于 token 序列 `x_1,\ldots,x_T`，目标可以写成：

```math
\mathcal{L}_{\mathrm{LM}}
=-\frac{1}{|M|}\sum_{t\in M}
\log p_\theta(x_t\mid x_{<t})
```

`M` 是真正参与 loss 的位置集合，`|M|` 是有效 label token 数，必须满足 `|M|>0`；被选中的 label 必须是词表内的合法 token，模型在该位置的条件概率为正。这个分母解释了为什么 padding、assistant-only mask、packed 文档边界和变长 batch 会影响 loss。若不同 rank 的有效 token 数不同，不能先算每个 rank 的平均 loss 再简单平均，而应汇总 loss numerator 和有效 token denominator。空 `M` 应被作为数据或模板异常记录，不能报告成 loss 为 0 的正常 step。

AdamW、warmup、decay、gradient clipping 和 BF16 可以构成稳定基线。它们不是互相独立的开关：改变 global token batch 往往需要重新评估学习率；启用梯度累积会改变 optimizer update 的频率；使用 FP16 还要记录 scaler 状态；使用 activation checkpointing 会减少激活存储但增加重计算。

### 2.6 并行与长期吞吐

并行方案由显存、层结构、节点互联和目标墙钟时间共同决定。FSDP/ZeRO 主要分片训练状态，TP 分片层内矩阵，PP 分片层和 stage，sequence/context parallel 进一步拆分序列或激活，MoE 还要处理专家路由和 all-to-all。

训练时长的第一近似是：

```math
T_{\mathrm{wall}}
\approx\frac{D}{R_{\mathrm{steady}}a}
```

`D>0` 是有效训练 token，`R_{\mathrm{steady}}>0` 是目标配置的长期吞吐，`0<a\leq1` 是扣除保存、评估、恢复和数据等待后的 wall-clock availability。单卡峰值、单个稳定 step 或只包含 forward 的 benchmark 都不能直接作为 `R_steady`；零吞吐或没有覆盖完整保存周期的 availability 不是可用于推导完成日期的普通输入。

### 2.7 监控、checkpoint 与评估

训练监控至少应同时记录 train loss、validation loss、per-domain loss、learning rate、grad norm、非有限值、有效 tokens/s、通信时间、数据等待、checkpoint 写入和恢复时间。每个指标都要有口径：例如 tokens/s 是输入 token、有效 label token 还是包括 padding 的 token。

checkpoint 不能只保存模型权重。若要恢复同一训练状态，还应保存 optimizer、scheduler、精度 scaler、RNG、数据游标、gradient accumulation 位置、并行拓扑、配置和数据 manifest。恢复演练应比较恢复前后的若干 step，而不是只验证 `load_state_dict` 没报错。

## 3. 训练量级公式：把方案变成数字

### 3.1 FLOPs 粗估

dense decoder-only Transformer 常用的量级估算是：

```math
C_{\mathrm{train}}\approx6ND
```

`N>0` 是有效参与前向的参数量，`D>0` 是有效训练 token 数；二者必须来自同一阶段和同一 dense/稀疏计算口径。这个常数把前向、反向和梯度计算放在同一近似里，不包含完整的通信、数据管道、checkpoint 和失败重跑。

更一般的写法是：

```math
C_{\mathrm{model}}\approx c_{\mathrm{tok}}D
```

`c_tok` 应由具体架构计数或 profiler 得到。长上下文 attention、MoE、视觉编码器、重计算和额外奖励模型都会使 `c_tok` 偏离 `6N`。

### 3.2 Global batch 与有效 token batch

如果每张卡的 micro-batch 为 `B_micro`，梯度累积步数为 `A`，data parallel world size 为 `W`，等长样本的 global batch 是：

```math
B_{\mathrm{global}}=B_{\mathrm{micro}}\cdot A\cdot W
```

其中 `B_micro`、`A` 和 `W` 都是正整数，`W` 指真正参与同一次数据并行梯度归约的 world size，而不是所有 TP/PP rank 的盲目乘积。变长语言模型更应使用：

```math
D_{\mathrm{step}}
=\sum_{i\in\mathrm{batch}}L_i^{\mathrm{valid}}
```

`L_i^{valid}` 是样本 `i` 真正参与目标更新的 token 数，要求非负；全局 `D_step` 应在所有会参与同一次更新的 data-parallel rank 上汇总，且必须大于 0 才能形成可解释的 loss/update。padding、prompt-only token 和无效 label 都不应被误计为有效学习量。

### 3.3 AdamW 状态与训练状态

若权重和梯度分别使用 `b_w`、`b_g` 字节，每个 Adam moment 使用 `b_m` 字节，另有 `b_master` 字节的 master weight，则全量训练状态的粗略存储量为：

```math
S_{\mathrm{AdamW}}
\approx N(b_w+b_g+2b_m+b_{\mathrm{master}})
```

这里 `N>0`，各 `b` 都是以同一字节单位表示的非负有限数；某些 BF16-only 或无 master weight 的实现应把 `b_master` 明确置为 0，而不是沿用 16 bytes 的口头估算。这个式子只算参数、梯度和 optimizer state，不包含 activation、通信 buffer、临时 workspace 和显存碎片。分片会降低单卡份额，不会消灭总状态；量化底座或 LoRA 会改变可训练参数集合，但不自动消灭激活与运行时开销。

### 3.4 单位能力成本

如果训练总支出为 `C_total`，可以先计算每个有效 token 的成本：

```math
C_{\mathrm{token}}=\frac{C_{\mathrm{total}}}{D_{\mathrm{eff}}}
```

这里 `D_eff>0`，并且成本和 token 必须覆盖相同的训练阶段与时间窗口。对 SFT、RL 或领域适配，更有意义的分母可能是通过固定回归的任务数、成功的领域样本数或上线请求中的有效成功数。分母必须固定定义，否则“成本下降”可能只是把有效任务换成了更多无效 token。

## 4. Loss spike：从时间线而不是直觉开始

loss spike 是一种观测现象，不是一个原因。它可能来自坏 batch、label mask、学习率、梯度爆炸、混合精度、通信状态、checkpoint 恢复或数据分布切换。正确的排查顺序是先定位第一次异常，再缩小变量范围。

### 4.1 第一次异常的时间线

对第一次 spike 的 step，至少保存以下信息：

1. global step、epoch、数据 shard 和样本 ID。
2. 每个 rank 的 loss、有效 label 数和输入长度。
3. grad norm、learning rate、optimizer step 和 scaler 状态。
4. forward、backward、unscale、clip、optimizer update 是否完成。
5. 最近一次 checkpoint、恢复事件、数据版本和配置 hash。

如果只保留一条 loss 曲线，异常发生后就很难判断它是输入问题还是更新问题。

### 4.2 用固定 batch 隔离数据与优化

固定 batch 是最小反事实实验。把发生 spike 的样本保存下来，用同一个 checkpoint 在以下条件下重放：

| 实验 | 变化 | 可以排除的方向 |
| --- | --- | --- |
| A | 原 batch、原优化器 | 重现基线 |
| B | 清洗或替换可疑样本 | 数据与 decode |
| C | 固定 batch、降低学习率 | 更新尺度 |
| D | 固定 batch、关闭异常 kernel | 数值与实现 |
| E | 单卡或少量卡重放 | 通信与 rank 差异 |

一次只改变一个变量，才能把“修好了”与“换了实验”区分开。

### 4.3 根据观测组合定位

| 观测组合 | 更可能的方向 | 首先保存或重放的证据 |
| --- | --- | --- |
| 单 rank 异常 | rank-local batch、解码或局部状态 | 样本 ID、文本、mask、局部梯度 |
| 所有 rank 同时异常且接近 lr 峰值 | 学习率、warmup 或全局更新 | lr、global grad norm、固定 batch |
| loss 为 NaN 且 grad 非有限 | overflow、非法输入或 update | forward 输出、unscale、optimizer state |
| 恢复后出现台阶 | optimizer、RNG 或数据游标不连续 | manifest、游标、连续 step 对比 |
| 只有一个领域异常 | 领域格式、比例或 loss 分母 | per-domain token、mask、回归集 |

### 4.4 修复与恢复

可能的修复包括隔离坏样本、降低 peak learning rate、延长 warmup、调整 clipping、改用 BF16、修正 mask 或恢复到更早 checkpoint。每个修复都应在固定回归集上检查能力损失，因为 spike 即使短暂，也可能造成一次异常参数更新。

恢复时不要把“训练重新跑起来”和“恢复了同一实验”混为一谈。若 optimizer、scheduler、RNG 或数据游标缺失，后续轨迹可能已经不同；这应被记录为新实验或恢复语义不完整，而不是继续沿用原实验编号。

## 5. Loss 与能力：为什么平均曲线不够

### 5.1 训练目标和下游目标的映射缺口

next-token loss 测量的是当前训练分布上的概率预测。它可能与指令遵循、事实性、代码执行、工具调用、拒答边界或长上下文检索相关，但不是这些能力的同义词。训练数据重复会让记忆更容易，模板化数据会让格式 loss 下降，低质量答案也可能让模型学会稳定地产生错误模式。

validation loss 下降仍然重要，它可以反映优化是否在目标分布上进展；但它必须与 per-domain loss、独立任务、人工抽样、污染分析和安全回归一起解释。

### 5.2 分层评估

设能力集合为 `\mathcal{K}`，第 `k` 层分数为 `S_k`，业务权重为 `w_k`，可以记录加权汇总：

```math
S_{\mathrm{eval}}
=\sum_{k\in\mathcal{K}}w_kS_k,
\qquad
\sum_{k\in\mathcal{K}}w_k=1
```

这里 `\mathcal{K}` 非空，`w_k\geq0`，权重和为 1，并且每个正权重分项都要有足够的可评分样本；缺失的安全或代码切片不能用默认 0/1 填入汇总。汇总分数只是排序工具，不能替代每个分项。提高容易任务的权重可以让总分上升，同时掩盖关键领域退化。因此发布记录应同时保存每个分项、样本数、置信区间、评估 prompt、模型 checkpoint 和数据版本。

### 5.3 能力回归的定位

发现 loss 降低但能力下降时，可按以下顺序比较：

1. 训练前后相同 checkpoint 评估协议是否一致。
2. 整体 validation 与 per-domain loss 是否方向一致。
3. 数据 mixture、重复率和领域采样是否变化。
4. 训练步数、学习率、mask 和模板是否改变。
5. 关键任务的错误类型是知识缺失、格式变化、事实错误还是安全策略变化。

只有把错误类型分开，才能决定应调整数据、训练强度、回放数据、adapter 范围还是评估协议。

## 6. Benchmark contamination：把高分和泛化分开

### 6.1 污染的几种形态

评估集可能以原题、答案、解析、代码测试样例、网页快照、合成改写或模板变体进入训练数据。污染不只发生在题面完全相同的情况：一个数学题的解析、一段代码的隐藏测试、一个发布日期之后抓取的网页，都可能让模型利用记忆而不是泛化。

### 6.2 分层检测

检测可以分层进行：

1. exact match：低成本发现完全重复。
2. n-gram、MinHash 或 SimHash：发现表面改写和长片段重复。
3. 编辑距离或结构化 AST：适合代码和模板文本。
4. embedding 检索：发现语义近邻，但需要人工复核。
5. 时间、来源和版本隔离：从数据生成流程上降低泄漏可能。

近似匹配不是确定污染。常见数学模板、法律措辞和 API 说明可能自然相似；embedding 命中应记录为疑似，需要结合来源、时间、关键实体和答案结构判断。

### 6.3 风险标注与报告

可以定义一个教学级风险比例：

```math
\mathrm{ContamRate}
=\frac{N_{\mathrm{high\ risk\ matches}}}
{N_{\mathrm{eval\ items}}}
```

这里 `N_eval_items>0`，分子必须说明匹配规则、阈值和人工复核标准。没有完成覆盖性检测的评估集，其 contamination rate 应报告为 unknown，而不是 0。报告应区分 confirmed、suspected 和 unknown，不应把所有近似命中都当成确定泄漏，也不应在没有检测证据时把 benchmark 分数称为纯泛化结果。

若风险较高，可以使用时间切分、来源隔离的新评估集，报告污染前后分数，并增加新题、执行型测试和人工抽样。数据 manifest 需要保存抓取时间、来源 hash、过滤规则和评估隔离策略；污染检测日志也应控制访问权限，避免把评估内容再次扩散。

## 7. Batch size 与 learning rate：同一个更新的两面

### 7.1 样本 batch 与 token batch

若 `B_micro=2`、梯度累积 `A=8`、data parallel world size `W=16`，则等长样本的 global batch 为：

```math
B_{\mathrm{global}}=2\times8\times16=256
```

但语言模型通常是变长输入。假设一个更新包含有效长度 `L_1,\ldots,L_m` 的样本，真正参与目标的 token batch 是：

```math
D_{\mathrm{step}}=\sum_{i=1}^{m}L_i
```

若使用 assistant-only SFT，`L_i` 还要排除 prompt；若存在 padding，padding 不能进入有效 token 分母。比较两个实验时，必须同时报告样本 batch、有效 token batch、序列长度分布和 loss reduction。

### 7.2 Batch 变大改变了什么

增大 global batch 通常能提高硬件吞吐、降低梯度估计噪声，但也会改变每次 optimizer update 看到的数据量、学习率尺度、更新次数和泛化行为。固定 token 预算时，batch 变大意味着 update 次数减少；如果 scheduler 仍按旧的 step 数衰减，实际学习率轨迹就已经改变。

梯度累积也有边界：如果 dropout、batch normalization、动态 loss scaling 或随机数据增强在每个 micro-step 发生，累积结果未必等价于一个更大的单步 batch。语言模型中通常没有 batch normalization，但随机数状态、有效 token 分母和梯度 clipping 仍需要明确。

### 7.3 Learning rate 的搜索

线性 scaling 或平方根 scaling 可以作为初始假设，不能作为跨架构、跨数据和跨 batch 的定律。调整时应同时记录 peak learning rate、warmup token/step、decay 规则、optimizer、global token batch 和 gradient clipping。

warmup 的作用是避免模型参数和 optimizer 状态尚未稳定时产生过大的更新；decay 则控制训练后期的更新尺度。若 scheduler 按 optimizer step 计数，而实验按 token 计数，改变 batch 后必须重新换算 schedule。一个更稳妥的比较表至少应包含：

| 变量 | 记录方式 | 不能忽略的变化 |
| --- | --- | --- |
| batch | 样本数和有效 token 数 | padding、mask、rank 汇总 |
| lr | 每个 optimizer update 的值 | warmup、decay、step/token 口径 |
| update | optimizer step 和总 token | 累积次数、跳过 step |
| 稳定性 | grad norm、NaN、loss spike | scaler、clip、数据异常 |
| 质量 | val/per-domain/regression | 过拟合、领域退化 |

## 8. 分布式切分：切了什么，省了什么，又付出什么

### 8.1 DDP 的复制模型

DDP 通常在每个 rank 保留完整模型副本，每个 rank 处理不同数据，反向后通过 collective 聚合梯度。它实现简单、通信模式清晰，但参数、梯度和 optimizer state 都可能在每张卡重复保存。当模型状态已经超过单卡容量，单纯增加 data parallel rank 并不能解决单卡 OOM。

### 8.2 ZeRO 与 FSDP 的状态分片

ZeRO 和 FSDP 主要解决数据并行下训练状态复制的问题。可以用对象来理解它们：

| 方法 | 主要切分对象 | 单卡收益 | 新增代价 |
| --- | --- | --- | --- |
| ZeRO-1 | optimizer state | 降低状态复制 | optimizer 相关通信和管理 |
| ZeRO-2 | optimizer state、gradient | 进一步降低梯度/状态 | gradient reduce-scatter 等通信 |
| ZeRO-3 | optimizer state、gradient、parameter | 参数也按 rank 分片 | forward/backward 按需 gather/reshard |
| FSDP | 参数、梯度、optimizer state | 与 PyTorch 模块封装结合 | wrap、all-gather、保存策略 |

FSDP 的具体行为还取决于 wrapping、mixed precision、prefetch、状态保存和版本实现。官方接口文档能说明 API 和状态字典边界，不能替代目标模型的性能 benchmark。

### 8.3 Tensor Parallel 与 Pipeline Parallel

TP 把层内矩阵按行或列切分。它可以让一个层的参数和计算分布到多张卡，但每层可能发生高频 collective，因此通常依赖高速互联和适合的矩阵维度。PP 按层或模块切成 stage，能放下更深模型，但会有 pipeline bubble、micro-batch 调度和 stage 不均衡。

如果 pipeline 有 `P` 个 stage、一个 batch 被拆成 `M` 个 micro-batch，简单的流水线 bubble 比例会随 `P/M` 增大而变差；具体公式依赖 1F1B、交错 schedule 和负载平衡，不能用一个固定比例代表所有实现。规划时应直接测每个 stage 的计算时间、空闲时间和激活存储。

### 8.4 混合并行与拓扑

真实训练常组合 data、tensor、pipeline、sequence/context 和 expert parallel。并行度的乘积应与 world size 对齐，但“能启动”不代表“值得运行”。TP 跨越低带宽节点会让每层通信变成瓶颈，PP stage 不均衡会让部分卡长期空闲，MoE all-to-all 会受到专家负载和拓扑影响。

选择方案时同时比较显存峰值、step time、通信占比、有效 tokens/s、恢复复杂度和 checkpoint 格式，不能只比较启动所需的卡数。

## 9. 显存账本：稳态占用和瞬时峰值

### 9.1 训练状态

以 AdamW mixed precision 为例，若权重和梯度为 BF16，两个 moment 和 master weight 为 FP32，则每参数的粗略字节数是：

```math
2+2+4+4+4=16\ \mathrm{bytes/parameter}
```

其中两个 `4` 分别是 moment，另一个 `4` 是 master weight。7B 参数的全量状态约为：

```math
7\times10^9\times16/1024^3
\approx104.3\ \mathrm{GiB}
```

这不是单卡需求，因为 FSDP/ZeRO 会分片；它也不是完整训练显存，因为 activation、通信 bucket、temporary workspace 和碎片还要另加。

### 9.2 激活和长上下文

激活显存通常随 micro-batch、sequence length、hidden size、层数和需要保存的中间张量增长。长上下文尤其容易使 activation 成为峰值来源。activation checkpointing 只保存部分中间状态，反向时重新计算被丢弃的部分，从而以额外 FLOPs 换显存；FlashAttention 减少 attention 中间矩阵的物化和 IO，但不自动消除其他层的激活。

因此 OOM 的第一步不是盲目降低 batch，而是识别峰值属于哪一类：

1. 权重、梯度或 optimizer state：检查分片、精度和冻结范围。
2. activation：检查 sequence length、micro-batch、checkpointing 和 pipeline in-flight 数量。
3. 通信 bucket 或 temporary workspace：检查 kernel、bucket size、all-gather 时机和显存碎片。

### 9.3 量化与参数高效微调的边界

QLoRA、低比特权重和 LoRA 可以减少底座权重或可训练参数的存储，但 activation、输入 embedding、KV-like 中间状态和 optimizer state 仍然可能占用显存。冻结底座也不代表 forward 免费；如果序列长度很长，激活仍可能成为主要峰值。任何“显存降低了多少”的数字都要注明底座精度、可训练参数、micro-batch、序列长度和测量窗口。

## 10. SFT 后能力回归：先定义“变差”

### 10.1 把模糊退化拆成指标

“模型变笨”不是可复现的指标。应分别测数学、代码、事实问答、多语言、长上下文、格式遵循、工具调用、安全拒答和目标领域任务。对每类任务保存固定 prompt、解码参数、参考答案或执行器版本，并记录错误类型。

同一个输出变化可能有不同解释：答案更短可能是效率提高，也可能是推理被截断；拒答增加可能是安全策略变强，也可能是过度拒答；格式更严格可能提升解析率，却损害自然语言质量。只有分层回归和人工抽样同时存在，才能判断能力变化。

### 10.2 SFT 数据和监督边界

SFT 常把 system、user、assistant 和工具消息拼成一个序列，但不是每个 token 都应该承担同样的监督。若 prompt token、padding、image placeholder 或工具返回内容被错误地纳入 label，模型可能学会复读输入、模仿模板或生成不应生成的工具结果。

可用 mask `m_t\in\{0,1\}` 表示第 `t` 个位置是否参与 loss：

```math
\mathcal{L}_{\mathrm{SFT}}
=-\frac{1}{\sum_t m_t}
\sum_t m_t\log p_\theta(y_t\mid x_{<t})
```

这里要求 `\sum_tm_t>0`，被监督的目标 token 合法且对应的概率为正。截断或模板渲染后没有 assistant token 的样本应被跳过或报错并留下 id，不能用一个人为稳定项把它当作零 loss。排查时应打印模板渲染结果、token 边界、assistant 起止位置、padding mask、有效 label 数和每个数据域的长度分布。只看 SFT loss 下降，不能证明监督边界正确。

### 10.3 训练强度与回放

领域数据过窄、学习率过高、epoch 过多或答案风格过于单一，都可能造成底座能力回归。候选修复包括降低学习率和训练步数、提高数据质量、混入通用 replay、冻结部分底座、使用 LoRA 或调整领域采样比例。

每个修复都要同时观察新领域收益和通用回归损失。若收益和损失同时存在，应显式记录 trade-off；不能用一个平均分把它们抵消掉。

## 11. VLM 训练：视觉 token 必须有证据作用

### 11.1 三个模块和三条数据流

典型 VLM 包含 vision encoder、connector 和 LLM。图像经过视觉编码器得到视觉特征，connector 将其映射到 LLM 的 hidden size，随后通过 prefix 拼接、cross-attention 或 query resampler 与文本交互。

若图像产生 `N_v` 个视觉 token，文本有 `T` 个 token，直接拼接后的序列长度大致为：

```math
L_{\mathrm{joint}}=N_v+T
```

多图、视频帧和高分辨率会增加 `N_v`，进而影响 attention、KV 状态和 batch。视觉 token 压缩可以降低成本，但也可能丢失小字、空间关系和细粒度目标，因此不能只按 token 数优化。

### 11.2 分阶段训练

常见阶段包括：

1. 图文对齐或视觉表征预训练。
2. 冻结视觉塔和语言模型，只训练 connector。
3. 多模态 instruction tuning。
4. OCR、图表、空间、grounding、视频或工具任务的专项训练。
5. 安全、事实性和反事实评估。

冻结范围和学习率应写进参数表。视觉塔、connector、LLM 采用相同学习率未必合理；数据量不足时全面解冻可能破坏视觉或语言底座。

### 11.3 监督与反事实证据

多模态 label mask 必须区分图片 placeholder、用户问题、assistant 答案、padding 和工具返回。caption 流畅不代表小字 OCR 正确，VQA 得分上升不代表模型真的读取了图像。

一个简单反事实是替换图片而保持文本不变。如果答案几乎不变，说明需要调查文本先验、图片是否真正进入计算图、视觉 token 是否被截断，或 connector 是否没有学到有效映射。评估还应覆盖 OCR 字段、计数、空间关系、图表数值、grounding、幻觉和安全风险。

## 12. 训练成本：选择资源而不是堆资源

### 12.1 从目标能力倒推规模

成本规划应先问目标能力是否需要更大模型、更多 token、更长上下文或更强后训练。对固定计算预算，模型参数量和 token 数存在共同分配关系；Chinchilla 的结论说明不能只追求参数量，也不能把论文中的比例直接当作所有数据和任务的定律。

预训练、SFT、RL 和多模态阶段的 token 不应简单相加。SFT 的有效 token 受 label mask 影响，RL 的 rollout token 可能重复生成，VLM 的视觉 token 还要计入编码和联合 attention。资源表应分阶段记录 `D_pretrain`、`D_sft`、`D_rollout`、视觉 token 和通过回归的有效任务数。

### 12.2 计算与实测

纸面计算可用：

```math
C_{\mathrm{train}}\approx6ND
```

然后用真实配置测单卡长期吞吐和扩展效率：

```math
R_{\mathrm{cluster}}(G)
\approx G r_1\eta(G)
```

`r_1` 是与目标模型、序列长度、精度和 batch 匹配的单卡吞吐，`\eta(G)` 是候选规模的实测扩展效率。它不能由单卡 benchmark 线性外推。通信、保存、评估、数据等待和故障恢复还要通过 `a` 进入墙钟时间。

### 12.3 失败和 checkpoint 成本

若故障发生近似均匀，checkpoint 间隔为 `\Delta` 小时，训练期间预期故障次数为 `n_fail`，GPU 数为 `G`，平均丢失的 GPU-hours 可以粗估为：

```math
H_{\mathrm{lost}}
\approx n_{\mathrm{fail}}\frac{\Delta}{2}G
```

这里 `n_fail\geq0`、`\Delta>0`、`G>0`，并且 `n_fail` 若是期望次数，结果也是期望 GPU-hours，不是某次事故的精确损失。缩短间隔会降低回滚损失，却增加保存次数、写带宽和墙钟开销。checkpoint 还必须验证 optimizer、RNG、数据游标和版本 manifest，否则只是保存了一个可推理权重，而不是可连续训练状态。

## 13. Base、Instruct 与 Chat：阶段名称不是算法名称

### 13.1 Base model

Base model 主要通过预训练 next-token objective 学习语言、知识和模式。它擅长续写和作为下游适配底座，但不保证按照用户指令组织答案，也不保证拒答、工具调用或多轮状态管理。

### 13.2 Instruct model

Instruct model 通常经过 SFT，将角色、任务、答案和格式变成监督数据。它的行为取决于示范覆盖、label mask、模板和训练强度。一个模型可能在指令遵循上提升，同时在代码或多语言上退化，因此阶段转换必须配合回归评估。

### 13.3 Chat model

Chat 更像交互协议和产品形态，而不是严格的单一训练算法。多轮数据、系统消息、偏好优化、安全对齐、工具协议和推理时模板都可能影响 chat 行为。有些行为来自参数更新，有些行为来自 chat template、system prompt 或 runtime tool；不能根据名称反推内部训练流程。

判断一个模型属于哪个阶段，应查看模型卡、训练报告、tokenizer/chat template、可用 checkpoint 和评估协议。名称只提供线索，不提供训练证据。

## 14. DPO 与 PPO：离线偏好与在线策略更新

### 14.1 PPO 的闭环

PPO 通常包含当前 policy 采样、reward model 或环境给分、reference model 的 KL 约束、value/critic 和 clipped policy update。对动作 `a_t`，新旧策略概率比为：

```math
r_t(\theta)=
\frac{\pi_\theta(a_t\mid s_t)}
{\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t)}
```

这要求旧策略在该动作上给出正概率，新旧策略采用同一动作空间、tokenizer 和模板，`\hat A_t` 为有限数，且裁剪半径满足 `0<\epsilon<1`。实现通常在 log-probability 空间计算 ratio；若旧策略的动作概率为零，重要性比没有定义，不能用极小常数替代后继续更新。

常见 clipped objective 可以写成：

```math
L_{\mathrm{PPO}}
=-\mathbb{E}_t\left[
\min\left(
r_t(\theta)\hat A_t,
\operatorname{clip}(r_t(\theta),1-\epsilon,1+\epsilon)\hat A_t
\right)\right]
```

`\hat A_t` 是 advantage，`\epsilon` 限制单次策略变化。旧 policy ratio、reference KL 和 reward model 是不同角色：前者约束更新相对旧策略，reference 约束行为漂移，reward/环境提供优化方向。

PPO 的优点是可以在当前 policy 分布上探索，并接入代码执行、数学验证或其他环境；代价是 rollout、reward、critic、采样稳定性和资源成本更高。

### 14.2 DPO 的离线目标

DPO 使用同一 prompt 下的 `chosen` 与 `rejected`，直接优化当前 policy 相对于 reference policy 的偏好差异：

```math
L_{\mathrm{DPO}}
=-\log\sigma\left(
\beta(\Delta_\theta-\Delta_{\mathrm{ref}})
\right)
```

其中：

```math
\Delta_\theta
=\log\pi_\theta(y_{\mathrm{chosen}}\mid x)
-\log\pi_\theta(y_{\mathrm{rejected}}\mid x)
```

`\Delta_ref` 是 reference model 的对应差值，`\beta` 控制偏好信号的尺度。序列 log probability 如何做 token mask、长度归一化和 batch reduction，会改变不同样本的实际权重。

chosen 和 rejected 必须各有至少一个参与比较的 response token，policy/reference 的四个 log probability 必须在同一 tokenizer、chat template 和 mask 下计算且为有限数，`\beta>0`。若答案被截断为空、reference 使用了不同模板，或一侧用 token sum、另一侧用 token mean，公式仍会给出一个数，却不再是同一偏好对的可解释比较。

DPO 不需要单独的在线 rollout 和 reward model，适合已有偏好对；但它依赖离线偏好覆盖，当前 policy 与数据分布偏离时可能过拟合，也不会自动探索数据集中没有的轨迹。DPO 更简单不等于总成本更低：偏好数据收集、清洗、长度偏差和能力回归仍然需要评估。

### 14.3 如何选择

| 条件 | 更适合优先考虑的方向 | 主要风险 |
| --- | --- | --- |
| 已有高质量偏好对、无需探索 | DPO 类离线目标 | 数据覆盖和分布偏移 |
| 有可靠环境或 verifier | PPO、RLVR 或其他在线路线 | rollout、奖励设计和稳定性 |
| 需要严格 KL/行为约束 | 带 reference 的策略更新 | reference、KL 和 reward 口径 |
| 预算有限、先做行为对齐 | SFT 后离线偏好优化 | 过拟合和能力回归 |

选择依据应包括 reward/verifier 可靠性、在线探索价值、数据规模、rollout 成本、分布偏移和单位成功任务成本，而不是方法名称的新旧。

## 15. 一个完整训练方案的审计示例

下面的例子把前面的概念放在同一份教学账本中。它不模拟真正的 GPU，也不声称给出行业阈值；它只检查一个训练方案是否同时记录了目标、数据、模型、优化、系统、评估和风险，并计算三个容易混淆的量级：有效 token batch、训练 FLOPs 和 AdamW 状态大小。

### 15.1 方案账本

账本应把假设和证据分开。例如 `mfu` 是短程实测值还是预计值，`contamination` 是已确认命中还是疑似命中，`checkpoint` 是只含权重还是可恢复状态，都应有字段说明。下面用最小字典表达这种结构。

```python
import math
from math import isclose


def require_text(value, name):
    if not isinstance(value, str) or not value.strip():
        raise ValueError(f"{name} must be non-empty text")
    return value


def require_positive_int(value, name):
    if type(value) is not int or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def require_finite(value, name, minimum=None, maximum=None):
    if isinstance(value, bool) or not isinstance(value, (int, float)) or not math.isfinite(value):
        raise ValueError(f"{name} must be finite")
    value = float(value)
    if minimum is not None and value < minimum:
        raise ValueError(f"{name} must be >= {minimum}")
    if maximum is not None and value > maximum:
        raise ValueError(f"{name} must be <= {maximum}")
    return value


plan = {
    "target": {
        "stage": "base",
        "domains": ["web", "code", "math", "multilingual"],
        "regression_sets": ["general", "code", "math", "safety"],
    },
    "data": {
        "train_tokens": 1_000_000_000_000,
        "effective_token_definition": "non_padding_next_token_labels",
        "manifest_hash": "toy-data-v3",
        "contamination_status": "screened_with_review",
    },
    "model": {
        "parameters": 7_000_000_000,
        "sequence_length": 4096,
        "dtype": "bf16",
    },
    "optimization": {
        "micro_batch": 2,
        "grad_accumulation": 8,
        "data_parallel_world": 16,
        "optimizer": "adamw",
        "warmup_tokens": 10_000_000_000,
    },
    "system": {
        "gpu_count": 128,
        "steady_tokens_per_second": 1_219_048,
        "wall_clock_availability": 0.92,
        "resume_checkpoint": True,
    },
    "evidence": {
        "throughput": "target-shape-long-run-benchmark",
        "mfu": "target-shape-measurement",
        "recovery_probe": "passed",
    },
}

def adamw_state_gib(parameters):
    # BF16 weights/gradients; FP32 moments and master weights.
    parameters = require_positive_int(parameters, "parameters")
    bytes_per_parameter = 2 + 2 + 4 + 4 + 4
    return parameters * bytes_per_parameter / 1024**3


def validate_plan(plan):
    required_top_level = {"target", "data", "model", "optimization", "system", "evidence"}
    if not isinstance(plan, dict) or set(plan) != required_top_level:
        raise ValueError("plan must contain exactly the required top-level sections")

    target = plan["target"]
    data = plan["data"]
    model = plan["model"]
    optimization = plan["optimization"]
    system = plan["system"]
    evidence = plan["evidence"]
    if not isinstance(target.get("domains"), list) or not target["domains"]:
        raise ValueError("target domains must be non-empty")
    if not isinstance(target.get("regression_sets"), list) or not target["regression_sets"]:
        raise ValueError("regression_sets must be non-empty")
    require_text(target.get("stage"), "target stage")

    require_positive_int(data.get("train_tokens"), "train_tokens")
    require_text(data.get("effective_token_definition"), "effective_token_definition")
    require_text(data.get("manifest_hash"), "manifest_hash")
    if data.get("contamination_status") not in {"screened_with_review", "confirmed_clean", "unknown"}:
        raise ValueError("contamination_status must use the recorded vocabulary")

    require_positive_int(model.get("parameters"), "parameters")
    require_positive_int(model.get("sequence_length"), "sequence_length")
    if model.get("dtype") not in {"bf16", "fp16", "fp32"}:
        raise ValueError("dtype must be a recorded training dtype")

    for field in ("micro_batch", "grad_accumulation", "data_parallel_world", "warmup_tokens"):
        require_positive_int(optimization.get(field), field)
    if optimization.get("optimizer") != "adamw":
        raise ValueError("toy accounting expects adamw")

    require_positive_int(system.get("gpu_count"), "gpu_count")
    steady_tokens_per_second = require_finite(
        system.get("steady_tokens_per_second"), "steady_tokens_per_second", minimum=0
    )
    if steady_tokens_per_second == 0:
        raise ValueError("steady_tokens_per_second must be positive")
    availability = require_finite(
        system.get("wall_clock_availability"), "wall_clock_availability", minimum=0, maximum=1
    )
    if availability == 0:
        raise ValueError("wall_clock_availability must be positive")
    if type(system.get("resume_checkpoint")) is not bool or not system["resume_checkpoint"]:
        raise ValueError("resume_checkpoint must be true for this recovery plan")

    for key in ("throughput", "mfu", "recovery_probe"):
        require_text(evidence.get(key), f"evidence {key}")
    if evidence["recovery_probe"] != "passed":
        raise ValueError("recovery_probe must pass before planning a continuous run")


validate_plan(plan)


micro_batch = plan["optimization"]["micro_batch"]
accumulation = plan["optimization"]["grad_accumulation"]
world = plan["optimization"]["data_parallel_world"]
global_sample_batch = micro_batch * accumulation * world
sequence_length = plan["model"]["sequence_length"]
valid_token_fraction = require_finite(1.0, "valid_token_fraction", minimum=0, maximum=1)
if valid_token_fraction == 0:
    raise ValueError("valid_token_fraction must be positive")
effective_token_batch = int(global_sample_batch * sequence_length * valid_token_fraction)
if effective_token_batch <= 0:
    raise ValueError("effective_token_batch must be positive")

parameters = plan["model"]["parameters"]
train_tokens = plan["data"]["train_tokens"]
train_flops = 6 * parameters * train_tokens
state_gib = adamw_state_gib(parameters)
ideal_seconds = train_tokens / plan["system"]["steady_tokens_per_second"]
wall_seconds = ideal_seconds / plan["system"]["wall_clock_availability"]

required_sections = {
    "target": bool(plan["target"]["regression_sets"]),
    "data": bool(plan["data"]["manifest_hash"]),
    "model": parameters > 0,
    "optimization": bool(plan["optimization"]["optimizer"]),
    "system": plan["system"]["gpu_count"] > 0,
    "evidence": plan["evidence"]["recovery_probe"] == "passed",
}

diagnostics = {
    "required_sections_complete": all(required_sections.values()),
    "global_sample_batch": global_sample_batch,
    "effective_token_batch": effective_token_batch,
    "valid_token_fraction": valid_token_fraction,
    "train_flops": f"{train_flops:.2e}",
    "adamw_state_gib": round(state_gib, 2),
    "planned_wall_days": round(wall_seconds / 86400, 2),
    "all_evidence_named": all(plan["evidence"].values()),
}

assert diagnostics["required_sections_complete"]
assert global_sample_batch == 256
assert effective_token_batch == 1_048_576
assert isclose(state_gib, 104.31, abs_tol=0.01)
assert diagnostics["all_evidence_named"]

print(f"global_sample_batch={global_sample_batch}")
print(f"effective_token_batch={effective_token_batch}")
print(f"train_flops={train_flops:.2e}")
print(f"adamw_state_gib={state_gib:.2f}")
print(f"planned_wall_days={diagnostics['planned_wall_days']:.2f}")
print(f"diagnostics={diagnostics}")
```

运行结果应接近：

```text
global_sample_batch=256
effective_token_batch=1048576
train_flops=4.20e+22
adamw_state_gib=104.31
planned_wall_days=10.32
diagnostics={'required_sections_complete': True, 'global_sample_batch': 256, 'effective_token_batch': 1048576, 'valid_token_fraction': 1.0, 'train_flops': '4.20e+22', 'adamw_state_gib': 104.31, 'planned_wall_days': 10.32, 'all_evidence_named': True}
```

这个示例有三个刻意的边界。第一，`effective_token_batch` 用 `valid_token_fraction` 显式表达有效 label 占比；真实的变长或 assistant-only SFT 应从每个样本的 mask 汇总，不能随意设成 1。第二，`adamw_state_gib` 是全量训练状态，不是单卡显存，也没有加入激活和通信 buffer。第三，`planned_wall_days` 只使用长期吞吐和可用率，真实系统还应加入 checkpoint 写入、评估和故障恢复的单独测量。

### 15.2 如何阅读审计结果

如果 `required_sections_complete` 为假，说明训练账本缺少目标、数据、模型、优化、系统或证据中的至少一项；这不是说训练一定失败，而是说明结果无法被完整解释。如果 `all_evidence_named` 为假，说明某个数字没有标记来源，不能把它与实测结果等价对待。

如果有效 token batch 发生变化，需要同步检查学习率、warmup、decay、训练 update 数和显存。若 `train_flops` 改变，需要重新估算 GPU-hours 和 wall-clock；若状态大小改变，需要重新检查分片和 checkpoint 存储。审计脚本的价值是让这些依赖显式化，而不是用一个总分替代工程判断。

## 16. 常见概念误区

### 16.1 把模型名称当成训练方案

模型名称通常只提供架构或产品线索，不能告诉你数据配比、训练 token、优化器状态、对齐阶段和评估协议。要判断公开结论的证据强度，应区分论文、模型卡、框架 API 和目标系统日志。

### 16.2 把 token 数当成有效学习量

输入 token、padding token、prompt token、assistant label token 和 rollout token 的作用不同。统一报一个总 token 数会掩盖 mask、重复率和阶段差异。训练报告应同时记录 raw token、valid token、loss numerator 和 denominator。

### 16.3 把能启动当成能训练

能启动只证明初始化、显存和通信在某个瞬间可用。还要验证长期吞吐、loss 稳定、checkpoint 保存、恢复连续性、评估回归和数据游标。分布式配置尤其需要长时间稳定性，而不是只跑几个 step。

### 16.4 把高利用率当成高能力

MFU、HFU 和 GPU busy 主要描述计算执行，不能直接证明数据质量、收敛质量或下游能力。一个系统可以提高硬件利用率，却因为错误 mask 或污染数据而得到更差的模型。

### 16.5 把方法名当成选择结论

AdamW、DPO、PPO、FSDP、TP 和 VLM connector 都是机制或工具，不是脱离目标的最佳答案。选择应回到约束、证据、失败边界和单位有效能力成本。

5. 设计一个 VLM 图片替换实验，要求能够区分视觉证据被使用、文本先验主导和视觉 token 被截断三种结果。

## 18. 本章小结

训练系统设计的核心不是堆叠方法名称，而是建立可复核的因果链。目标决定数据 mixture 和评估；数据和 tokenizer 决定有效 token 与输入分布；架构和上下文决定 FLOPs、激活和状态；batch、学习率和优化器决定参数轨迹；并行决定显存、通信和吞吐；checkpoint 决定故障后的实验连续性；分层评估决定 loss 是否真的转化成能力；成本账本决定方案能否持续。

遇到异常时，先保留第一次异常的时间线和证据，再用固定 batch、局部替换和单变量实验隔离原因。遇到能力变化时，不要让平均 loss 或总分掩盖领域回归、污染和安全风险。遇到资源选择时，同时比较有效 token、长期吞吐、GPU-hours、存储、恢复和单位成功任务成本。
