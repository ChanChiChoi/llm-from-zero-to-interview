# 第十三章：训练成本与资源规划：从纸面 FLOPs 到单位成功成本

当有人说“训练一个 7B 模型需要 128 张卡”时，这句话还缺少至少五个条件：训练多少 token，序列长度是多少，使用什么精度和并行方式，集群长期吞吐是多少，以及失败和评估时间是否算在内。只给 GPU 数量，既不能推出训练时长，也不能推出账单，更不能说明模型是否会按计划得到有用能力。

训练成本规划的价值在于尽早发现量级错误。初学者可以先用参数量、token 数、吞吐和卡时做一轮粗算；专家则要继续拆开模型有效 FLOPs、通信和重计算、数据管道、checkpoint、故障恢复、人力以及“每个成功任务”的成本。粗算不是为了假装精确，而是为了让每个假设都能被实测替换。

本章主要讲预训练和大规模继续训练的资源框架，SFT、RL 和多模态阶段会在涉及处说明它们为什么不能直接套用同一个公式。具体云厂商价格不写死，因为区域、实例类型、折扣、合约和时间都会改变账单；文中的价格符号只表示计费接口，不代表某家供应商的报价。Chinchilla 和 PaLM 的公开论文用于说明计算最优和利用率的经典口径，Megatron-LM、MLPerf Training 以及 PyTorch/分布式文档用于补充工程边界；toy demo 的阈值只是假设，不能当作行业标准。

## 为什么成本和资源规划很重要

大模型训练不是“想训就训”。

一次训练往往要消耗：

1. 大量 GPU 时间。
2. 存储和网络资源。
3. 工程和调试人力。
4. 失败实验的机会成本。

如果前期没有做粗略估算，可能会出现：

1. 模型太大，训练 token 不够。
2. GPU 不够，训练周期太长。
3. checkpoint 过大，存储和恢复成为瓶颈。
4. 失败一次损失巨大。

所以资源规划的核心不是精确到小数点后几位，而是知道量级是否可行，并且知道哪一个假设最值得先测。一个好的规划表会同时给出乐观、基准和保守三种情景；当实际吞吐、故障率或 checkpoint 带宽偏离时，可以快速更新结论，而不是重新凭感觉估算。

## 1. 训练成本由哪些部分组成

训练成本通常分成四类：

| 成本类别 | 内容 |
| --- | --- |
| 计算成本 | GPU / TPU 时间 |
| 存储成本 | 数据、checkpoint、日志、artifact |
| 网络成本 | 多机通信、存储读写、checkpoint 传输 |
| 人力成本 | 调试、监控、实验管理、故障恢复 |

很多团队只看 GPU 成本，但实际上存储和重跑成本也很高。

如果一个训练实验经常失败，真正的成本可能远超硬件账单。

更完整的账本可以写成：

```math
C_{\mathrm{total}}
=C_{\mathrm{compute}}+C_{\mathrm{storage}}+C_{\mathrm{network}}
+C_{\mathrm{data}}+C_{\mathrm{engineering}}+C_{\mathrm{retry}}
```

这不是会计科目表，而是防止漏项的模型。`C_compute` 是 GPU/TPU 的运行费用，`C_storage` 包括热存储、冷存储和副本，`C_network` 包括跨节点通信和 checkpoint 传输，`C_data` 包括清洗、标注和数据供应，`C_engineering` 是人力和调试机会成本，`C_retry` 则来自失败、回滚和重跑。不同团队可能把数据和人力作为固定成本，但在实验决策中仍然应保留这些维度。

还要区分一次训练的总成本和单位产出成本。若训练消耗 `C_total`，有效训练 token 数为 `D_eff`，可以记录：

```math
C_{\mathrm{per\ token}}=\frac{C_{\mathrm{total}}}{D_{\mathrm{eff}}}
```

这里要求 `D_{\mathrm{eff}}>0`，而且它的计数口径必须与成本覆盖的训练阶段相同。空监督、被丢弃的 rollout、padding 和只用于评估的 token 不能悄悄进入这个分母；若这一阶段没有有效更新 token，应报告为不可计算，而不是把单位成本写成 0。对于后训练或领域适配，token 数不是最有意义的产出单位，更有用的指标可能是每个通过回归集的任务、每个上线请求或每个成功的领域样本。只有把成本和能力收益放在同一个分母下，才能比较“多训一轮”是否真的值得。

若计费口径是每张卡每小时 `p_gpu`，运行 `G` 张卡、墙钟时间 `T_wall` 小时，则计算费用的第一近似为：

```math
C_{\mathrm{compute}}
\approx G\,T_{\mathrm{wall}}\,p_{\mathrm{gpu}}
```

这个近似要求 `G>0`、`T_{\mathrm{wall}}\geq0`、`p_{\mathrm{gpu}}\geq0`，并明确卡是否在排队、暂停和恢复期间继续计费。存储费用还要乘以容量和保留时间。若热存储容量为 `S_hot`、保留 `t_hot`、单位容量时间价格为 `p_hot`，冷存储同理，则：

```math
C_{\mathrm{storage}}
\approx S_{\mathrm{hot}}t_{\mathrm{hot}}p_{\mathrm{hot}}
+S_{\mathrm{cold}}t_{\mathrm{cold}}p_{\mathrm{cold}}
```

容量、保留时间和价格都应为非负有限数，并统一容量单位和计费周期。`C_total` 只有在各项可加、没有重复计入预留资源或共享固定成本时才能直接相加；这两个式子仍然没有包含折扣、最小计费时长、跨区流量和副本策略，但它们能把“需要 128 张卡”和“需要多少预算”连接起来。真正报价应把价格表版本、区域、实例可用性和中断策略记录在实验计划中，而不是把一个过期单价写进通用公式。

## 2. 粗略 FLOPs 估算

训练成本常从 FLOPs 开始估算，因为 FLOPs 能把模型结构、数据量和硬件能力放在同一个量纲中。它的用途是判断数量级，而不是替代 profiler。一个规划表如果没有 FLOPs，通常很难解释为什么某个模型需要这么多训练时间；一个规划表如果只有 FLOPs，又无法解释通信、数据等待和保存任务为什么会让实际时间偏离纸面结果。

### 2.1 `6ND` 从哪里来

对于 dense decoder-only Transformer，常见的第一近似是：

```math
C_{\mathrm{train}}\approx 6ND
```

这个近似至少要求 `N>0`、`D>0`，且二者使用同一训练阶段的有效定义。若一个 batch 没有有效标签，或 MoE 因容量限制丢弃了部分 token，不能仍把原始输入长度完整计入 `D`。其中：

- `N` 是每个 token 参与主要前向计算的有效参数量；
- `D` 是真正进入训练主循环的 token 数；
- `C_train` 是模型前向、反向和梯度计算的近似 FLOPs。

这个常数来自矩阵乘法的数量级估算。一个参数在前向中通常参与一次乘加，在反向中还要为输入梯度和权重梯度做数量级相近的计算，因此训练 FLOPs 常被估为前向 FLOPs 的约三倍，而前向 FLOPs 又大致与 `2ND` 同阶，合在一起就得到约 `6ND`。不同论文对乘法、加法、激活和通信的计数方法并不完全一致，所以这里的 6 不是物理常数，也不是可以跨模型直接比较的精确账单。

`N` 的定义尤其容易被忽略。共享输入嵌入和输出头的模型不能简单地把所有存储参数重复计数；带 MoE 的模型不能把所有专家参数都视为每个 token 都执行；带检索、视觉编码器或额外奖励模型的系统又不止一个参数集合。更稳妥的记法是先写成：

```math
C_{\mathrm{model}}\approx c_{\mathrm{tok}}D
```

其中 `c_tok` 是通过架构计数或短程 profiler 得到的每 token 有效 FLOPs。只有在 dense、序列长度处于常见范围、训练目标与模型结构相近时，才用 `c_tok\approx6N` 代替它。

### 2.2 参数项和序列项

`6ND` 把计算量主要看成参数量和 token 数的乘积，但 Transformer 还包含随序列长度增长的 attention 项。设每次 micro-batch 有 `B` 个序列、每个序列长度为 `S`、隐藏维度为 `d`、层数为 `L`，教学级的单层估算可以写成：

```math
C_{\mathrm{layer}}
\approx k_1 B S d^2+k_2 B S^2d
```

第一项包括 Q、K、V 投影、输出投影和 FFN 等线性层；第二项对应 attention score 与 value 聚合的序列交互；`k_1`、`k_2` 由 FFN expansion、head 数、GQA/MQA、前向/反向计数和实现方式决定。式中 `B,S,d,L` 应为正，`k_1,k_2` 应是与实现口径绑定的非负系数；padding 或 packed 的无效位置必须先从实际 `S` 或 token 计数中剥离。整个模型还要乘上层数，并加上 embedding、输出头、归一化和其他辅助操作。

这个式子揭示了一个实际规划中的转折点：当 `S` 增大时，`B S d^2` 只与有效 token 数线性相关，而 `B S^2d` 对单条序列是二次增长。FlashAttention 等 kernel 主要减少显存读写和中间 attention 矩阵的物化，不会自动把标准全连接 attention 的基本序列交互从二次复杂度变成线性。只有稀疏 attention、滑动窗口、线性 attention 或其他结构性改变，才会改变这一项的算法形态。

因此，两个参数量相同的模型，如果一个以 2K 序列训练、另一个以 128K 序列训练，它们不能仅凭 `N` 和 `D` 比较成本。实际报告至少要同时给出平均有效序列长度、padding 比例、packed token 比例和 attention 实现。

### 2.3 MoE 的激活计算与总状态

MoE 把“每个 token 做多少计算”和“模型总共存了多少参数”拆开了。假设共有 `N_total` 个参数，每个 token 只路由到 `k` 个专家，每个专家数为 `E`，粗略的激活参数量可以写成：

```math
N_{\mathrm{active}}
\approx N_{\mathrm{shared}}+N_{\mathrm{router}}
+\frac{k}{E}N_{\mathrm{expert\ total}}
```

这只是均匀路由的近似，要求 `E>0`、`1\leq k\leq E`，并且各参数项和 token 路由统计使用同一个模型版本。专家容量限制、token dropping、共享专家、top-k 路由和负载偏斜都会改变实际执行量。用于 `6ND` 的 `N` 更接近 `N_active`，而不是 `N_total`；但权重存储、专家加载、通信、checkpoint 和故障恢复仍然受到 `N_total` 影响。一个只用总参数量估算 FLOPs 的 MoE 计划会高估每 token 计算量，一个只用激活参数量估算显存和存储的计划则会低估系统状态。

路由不均衡还会把最慢专家所在的 rank 变成整个 step 的决定因素。即使平均 token 数没有变化，最大专家负载、dispatch/all-to-all 通信和容量溢出也可能让 tokens/s 下降。因此 MoE 的资源表至少应记录激活参数量、总参数量、top-k、专家容量因子、最大/平均专家负载和 all-to-all 时间。

### 2.4 一个量级例子

假设模型有 `N=7e9` 个 dense 参数，训练 `D=1e12` 个 token，则主循环粗算为：

```math
C_{\mathrm{train}}
\approx6\times7\times10^9\times10^{12}
=4.2\times10^{22}\ \mathrm{FLOPs}
```

若集群在目标精度和目标 batch 下测得长期有效计算能力为 `5e16 FLOPs/s`，理想主循环时间为：

```math
T_{\mathrm{ideal}}
=\frac{4.2\times10^{22}}{5\times10^{16}}
\approx8.4\times10^5\ \mathrm{s}
\approx9.7\ \mathrm{days}
```

这里的 `5e16` 必须是与 FLOPs 口径匹配的正的有效计算能力，而不是把卡的宣传峰值随意相加。如果数据等待、评估、保存和节点恢复使 wall-clock availability 为 `a=0.8`，则：

```math
T_{\mathrm{wall}}
\approx\frac{T_{\mathrm{ideal}}}{a}
\approx12.1\ \mathrm{days}
```

这里 `0<a\leq1`；可用率为零、超出 1 或没有覆盖完整保存/评估周期的样本，都不能用于推导墙钟完成日期。这个例子把三个层次分开：`C_train` 是模型工作的纸面量，`5e16` 是目标集群的有效执行能力，`a` 是训练过程真正保持在主循环中的时间比例。把三者混成一个“GPU 理论算力”数字，后续的时长和费用都会失真。

### 2.5 FLOPs 估算的证据边界

FLOPs 估算适合回答“量级是否可能”和“哪个变量最值得先测”，不适合直接回答“这次训练一定会在某天完成”。以下因素通常不在 `6ND` 中完整体现：

1. activation checkpointing 带来的重计算。
2. 通信、同步和 all-to-all 等非算术时间。
3. 数据解码、shuffle、host-to-device 传输和 cache miss。
4. validation、checkpoint、日志、人工介入和节点恢复。
5. padding、无效 label、token dropping 与重复数据。

所以实际流程应是：先用 `6ND` 或架构计数做纸面估算，再在真实序列长度、micro-batch、精度和并行拓扑下测长期吞吐，最后用测量结果替换纸面假设。FLOPs 是规划的起点，而不是最终证据。

## 3. Tokens/s 和训练时长

训练时长最实用的估算方式之一是看吞吐。

如果知道每秒训练多少 token：

```text
training_time ≈ total_tokens / tokens_per_second
```

写成公式是：

```math
T_{\mathrm{sec}}=\frac{D}{R_{\mathrm{tok}}}
```

其中 `D>0` 是总训练 token 数，`R_{\mathrm{tok}}>0` 是长期平均训练吞吐。零吞吐不是“训练时间无限大后仍可规划”的普通数值，而是集群、数据或计数管道故障；注意这里应该用长期平均值，而不是短 benchmark 里的峰值。

吞吐的口径必须先写清楚。`R_tok` 可以指输入 token、有效监督 token、经过 padding 的 token，或者所有 rank 汇总的 token；这些数字可能不同。预训练通常以 global valid token 计数，SFT 则可能只统计 assistant label，RL 还会同时产生 prompt、completion、rollout 和 verifier token。若分子分母口径不一致，两个团队报告的 `tokens/s` 即使数值相同，也没有可比性。

例如：

```text
总训练 token = 2e12
吞吐 = 200k tokens/s
```

则训练时长大约是：

```text
2e12 / 2e5 = 1e7 秒 ≈ 115 天
```

这还没有考虑恢复、评估、调试和低利用率。若长期运行可用比例是 `a`，则墙钟时间的粗估应写成：

```math
T_{\mathrm{wall}}
\approx\frac{D}{R_{\mathrm{steady}}a}
```

这里 `R_{\mathrm{steady}}>0` 且 `0<a\leq1`。`a` 不是 MFU，而是把 checkpoint、validation、节点重启、队列等待和其他停顿合在一起的 wall-clock availability。把 `a` 和 MFU 相乘会重复或漏算，必须明确每个因子来自哪一层测量。

### 3.1 影响 tokens/s 的因素

1. 模型大小。
2. sequence length。
3. batch size。
4. 并行策略。
5. 网络带宽。
6. FlashAttention 等 kernel 优化。
7. 数据加载速度。

吞吐测量最好至少覆盖一个完整保存周期，并把 warm-up、通信同步和数据读取包含在计时里。还应分别记录：模型 forward/backward 的 step time、optimizer step time、dataloader wait time、collective communication time 和 checkpoint time。这样才能判断是 batch 太小、kernel 不够快、网络拥塞，还是数据供应不足。

### 3.2 不能只看峰值吞吐

某次 benchmark 中 tokens/s 很高，不代表整个训练过程都这么高。

真实训练中还要考虑：

1. checkpoint 保存暂停。
2. validation 停顿。
3. 节点故障重启。
4. 低利用率阶段。

训练时长估算要基于包含暂停和同步的长期平均 `tokens/s`，而不是实验里的峰值吞吐。

## 4. GPU 数量怎么估

GPU 数量取决于：

1. 模型能不能放下。
2. 想要多快训练完。
3. 想要多大 global batch。
4. 并行策略效率如何。

### 4.1 从单卡显存倒推

先判断单卡是否能放下：

```text
模型权重 + 梯度 + optimizer state + activation
```

如果不行，就要上 FSDP、ZeRO、TP、PP 或 checkpointing。

可以用一个分解式先定位显存来源：

```math
M_{\mathrm{gpu}}
\approx M_{\mathrm{weights}}+M_{\mathrm{grad}}
+M_{\mathrm{optim}}+M_{\mathrm{act}}+M_{\mathrm{temp}}
```

分片方法会改变前四项在单卡上的分布，但不会让总状态消失；pipeline parallel 还会引入多个 in-flight micro-batch，tensor parallel 会用通信换单卡矩阵规模。`M_act` 和 `M_temp` 随序列长度、micro-batch、视觉 token、checkpointing 方式和 kernel 变化，不能只用参数量推导。规划时应保留安全余量，用真实 batch 做峰值显存测试，并把显存碎片和框架临时 buffer 当作风险项，而不是把卡的标称容量全部当成可用空间。

### 4.2 从时长倒推

如果目标是 1 个月内训练完，就必须估算所需 tokens/s，再倒推需要多少 GPU。

设目标训练时长是 `T_day` 天，运行 overhead 比例是 `rho`，则最低平均吞吐需求是：

```math
R_{\mathrm{need}}
=
\frac{D}{86400\cdot T_{\mathrm{day}}\cdot (1-\rho)}
```

其中 `D>0`、`T_{\mathrm{day}}>0`，并且 `0\leq\rho<1`；若计划中有维护、评估和保存，`\rho=0` 只是未经验证的乐观假设。真实规划里不要把 `rho` 设成 0。

如果在小规模 benchmark 中测得 `r_1` 是单卡长期吞吐，假设扩展到 `G` 张卡的并行效率为 `eta(G)`，则集群吞吐可以先写成：

```math
R_{\mathrm{cluster}}(G)
\approx G\,r_1\,\eta(G)
```

因此满足目标吞吐的最小 GPU 数量是满足下面不等式的最小 `G`：

```math
G\,r_1\,\eta(G)\ge R_{\mathrm{need}}
```

关键在于 `eta(G)` 随规模变化，不能把单卡吞吐线性乘到几百张卡上。数据并行会遇到 all-reduce，张量并行会遇到每层 collective，流水线并行还会有 bubble 和调度约束；MoE 另有 token dispatch 和专家负载不平衡。最可靠的做法是为候选 GPU 数量各测一个短但代表性的 benchmark，再把实测曲线放入规划表。

### 4.3 资源冗余

不要把 GPU 预算卡得太死。

因为训练中会有：

1. 节点故障。
2. 机器掉线。
3. 调试占用。
4. benchmark 和 checkpoint 评估占用。

GPU 数量规划要同时满足显存可行性、训练时长和故障冗余。若为了赶墙钟时间把集群扩到通信效率急剧下降的区间，增加 GPU 反而可能同时提高卡时和网络压力；如果为了省卡选择过小 global batch，又可能让优化器统计和训练稳定性发生变化。

## 5. MFU 与 HFU：不要把三个百分比混在一起

训练监控里经常同时出现 GPU busy、MFU 和 HFU。它们回答的是不同问题：GPU busy 只说明设备在某个时间窗口内有没有执行 kernel；MFU 关注完成目标模型计算的速度占理论峰值的比例；HFU 则更接近硬件实际执行的全部浮点工作。把三者都叫“利用率”，很容易把监控现象误读成训练效率。

### 5.1 MFU 的定义

如果单个 token 的有效模型计算量为 `c_tok` FLOPs，所有 GPU 合计的长期有效吞吐为 `R_tok`，GPU 数量为 `G`，每张卡在目标精度下的理论峰值为 `F_peak`，则一种常见的 MFU 写法是：

```math
\mathrm{MFU}
=
\frac{c_{\mathrm{tok}}R_{\mathrm{tok}}}
{G F_{\mathrm{peak}}}
```

这里的分子是“模型为了完成训练目标本来需要做的工作”，分母是硬件手册给出的峰值算力乘以卡数。它要求 `c_{\mathrm{tok}}>0`、`R_{\mathrm{tok}}>0`、`G>0`、`F_{\mathrm{peak}}>0`，并且理论峰值与实际精度、稀疏性和时间窗口匹配。若用 `6ND` 作为 dense 模型的近似，那么 `c_tok\approx6N`；对于长上下文、MoE、视觉编码器或重计算，`c_tok` 必须改用与目标架构相符的计数。反过来，给定 MFU 可以得到吞吐的第一近似：

```math
R_{\mathrm{tok}}
\approx
\frac{G F_{\mathrm{peak}}\mathrm{MFU}}
{c_{\mathrm{tok}}}
```

这个反推只有在分子、分母、精度和时间窗口一致时才有意义。比如用 BF16 的模型 FLOPs 去除以 FP8 的峰值，或者用单个稳定 step 的吞吐去配整个训练阶段的 token 计数，都会得到看似漂亮但不能复核的数字。

### 5.2 MFU、HFU 和 GPU busy 的差别

PaLM 论文把 MFU 和 HFU 分开报告，背后的核心区别是是否把额外执行的工作计入分子。activation recomputation 会让硬件再次执行部分前向计算：这些计算占用了 GPU 时间，属于 HFU 更愿意计入的实际工作，却不代表模型在 token 目标上取得了同等多的有效进展，因此 MFU 与 HFU 可能不同。两者都不是 loss，也不能单独证明模型训练质量更好。

可以用下面的关系帮助理解：

```math
\mathrm{MFU}
=\frac{\text{目标模型 FLOPs}}{\text{理论峰值 FLOPs}},
\qquad
\mathrm{HFU}
=\frac{\text{实际执行 FLOPs}}{\text{理论峰值 FLOPs}}
```

GPU busy 更底层。一个 kernel 可能让 GPU 处于 busy 状态，却受限于显存带宽、访存模式或低算术强度，实际浮点吞吐并不接近峰值；通信 kernel、同步等待和数据拷贝也会让监控看起来很忙。反过来，GPU busy 较低也可能是短暂的通信或保存阶段，不足以描述整个训练周期。

### 5.3 如何解释一个低 MFU

低 MFU 不是“把 batch 调大”这么简单。需要把 step 时间拆成几类：

1. GEMM、attention 和其他计算 kernel。
2. data loader、解码和 host-to-device 等输入等待。
3. all-reduce、all-gather、reduce-scatter、all-to-all 等 collective。
4. optimizer、梯度同步和参数更新。
5. checkpoint、validation、重启和其他非主循环时间。

如果计算 kernel 占比低，可能是矩阵形状太小或 kernel 没有融合；如果通信占比高，可能是并行度超过互联拓扑的甜点区；如果数据等待高，优化 attention 不会解决问题；如果只在保存时下降，应报告长期 wall-clock availability，而不是把保存阶段的低 MFU 归因于模型结构。

### 5.4 报告 MFU 所需的最小上下文

一个可复核的 MFU 数字至少应同时记录模型配置、有效 FLOPs 公式、有效 token 定义、精度、硬件峰值、GPU 数量、global batch、序列长度、padding/packing 规则和测量时间窗。MoE 还要记录激活参数量与专家负载；启用 checkpointing 时要说明 MFU/HFU 是否包含重计算。

MFU 的价值在于帮助定位“模型有效进展”和“硬件做了多少工作”之间的差距。它应和 tokens/s、通信占比、数据等待、显存峰值和 loss 曲线一起解释，不能作为独立的训练质量分数。

## 6. 数据规模和 token 规划

训练成本的核心之一是你要喂多少 token。

很多训练方案问题本质上是：

```text
参数规模和 token 规模不匹配
```

如果模型太大但 token 不够，训练就会 under-train。

如果 token 太多但模型太小，容量不够也浪费。

Chinchilla 的重要启发是：在固定训练计算预算下，参数量和训练 token 数应该共同增长，不能只追求更大的参数量。可以把某个计算最优假设抽象成：

```math
D_{\mathrm{opt}}\approx kN
```

`k>0` 是由数据质量、模型结构、优化器、上下文长度和目标损失决定的经验系数。公开论文中的系数只适用于相近的训练设定，不能把它当成所有语言、多模态、MoE 或后训练任务的普适比例。对一个 7B 模型，若采用某个 `k` 估出预训练 token 预算，还要检查可获得的高质量数据是否足够，以及数据重复、污染和领域覆盖是否会改变有效 token 数。

预训练、继续预训练、SFT 和 RL 的 token 不能简单相加。预训练 token 主要改变基础知识和语言建模损失；SFT token 受到 assistant label mask 和样本长度影响；RL 的 rollout token 可能重复生成、并且只有部分轨迹带来有效奖励。资源表应分别记录 `D_pretrain`、`D_sft`、`D_rl_rollout` 和真正参与目标更新的有效 token，避免用一个总数字掩盖阶段差异。

### 6.1 资源规划要回答

1. 目标总 token 数多少。
2. 训练阶段是否分阶段。
3. 数据配比怎么分。
4. 是否需要继续预训练。
5. 是否有多轮后训练。

### 6.2 数据成本

数据本身也有成本：

1. 采集。
2. 清洗。
3. 去重。
4. 标注。
5. 存储。
6. 版本管理。

不要只把成本理解成 GPU 消耗。低质量数据会以训练 token、评估回归和后续清洗的形式重复收费；一个便宜但污染严重的数据集，可能让模型训练更快，却让有效能力和调试时间变差。

## 7. Checkpoint 存储成本

Checkpoint 会占用大量存储。

如果保存频率太高，长期存储和传输成本会非常可观。

### 7.1 需要考虑的点

1. checkpoint 大小。
2. 保存频率。
3. 保留策略。
4. 是否需要 sharded checkpoint。
5. 是否需要压缩。
6. 是否需要异步保存。

如果只保存推理权重，大小近似为：

```math
S_{\mathrm{eval}}\approx N b_w
```

其中 `b_w` 是每个参数的存储字节数，例如 BF16/FP16 通常是 2 bytes。若要恢复训练，通常还要保存梯度、optimizer state、scheduler、RNG、dataloader position 和配置。对 AdamW mixed precision 训练，一个很粗的训练恢复 checkpoint 估算是：

```math
S_{\mathrm{resume}}
\approx
N(b_w+b_g+2b_m+b_{\mathrm{master}})
```

其中 `b_g` 是梯度字节数，`b_m` 是 Adam 一阶/二阶矩每个状态的字节数，`b_master` 是 FP32 master weights 字节数。这个式子不需要死记，关键是知道 resume checkpoint 可能是推理权重的数倍。

保留策略也要估算：

```math
S_{\mathrm{retain}}
=n_{\mathrm{latest}}S_{\mathrm{resume}}
+n_{\mathrm{milestone}}S_{\mathrm{eval}}
+n_{\mathrm{archive}}S_{\mathrm{eval}}
```

保存太少会增加重跑损失，保存太多会把存储和网络打爆。

存储容量够用也不代表保存能按时完成。若一个分片 checkpoint 的总字节数为 `S`，可用聚合写带宽为 `B_write`，最低保存时间约为：

```math
T_{\mathrm{save}}\ge\frac{S}{B_{\mathrm{write}}}
```

这里 `S\geq0`、`B_{\mathrm{write}}>0`，并且两者使用相同的字节单位；带宽未知或为零时，保存日期无法从容量推导。实际时间还会受到 metadata、并发写入、对象存储分片、校验和、网络争用以及异步快照语义影响。若 `T_save` 接近 checkpoint 间隔，保存任务会和训练任务重叠，造成吞吐抖动；若异步保存直接读取正在更新的 tensor，又可能得到无法恢复的混合状态。因此要把“容量预算”和“发布一个完整可恢复版本的时间/语义”分开。

推理 checkpoint、评估 checkpoint 和恢复 checkpoint 也不应混为一类。前者只需要模型推理所需的权重和 tokenizer，后者可能还要保留 optimizer、scheduler、RNG、数据游标、并行拓扑和版本 manifest。量化权重或 LoRA adapter 可以减少发布体积，却不能自动替代恢复训练所需的全精度状态。

### 7.2 存储生命周期

常见策略：

```text
latest -> 短期保存，用于恢复
milestone -> 中期保存，用于评估
best -> 长期保存，用于发布
archive -> 冷存储，用于追溯
```

checkpoint 存储规划是训练成本和故障恢复策略的一部分：它同时决定保存期间的吞吐损失、故障时的重跑窗口和实验是否可追溯。

## 8. 失败和重跑成本

训练失败的代价不仅是重新跑几个小时，而是：

1. 已消耗的 GPU 时间。
2. 产出的无效 checkpoint。
3. 人工排查时间。
4. 重新同步调度资源。
5. 可能错过实验窗口。

因此需要估算失败预算。

### 8.1 重跑风险

如果训练过程很脆弱，失败率高，那么实际成本远高于理论成本。

设单次成功训练需要 `H_success` GPU-hours，完整训练失败概率是 `q`，一个粗略的期望成本放大因子是：

```math
E[H]\approx \frac{H_{\mathrm{success}}}{1-q}
```

这个极粗近似要求 `H_{\mathrm{success}}\geq0`、`0\leq q<1`，并把每次失败视为独立且会让完整训练从头开始；当 `q=1` 或恢复语义未知时，不能报告有限的期望成本。如果训练能从 checkpoint 恢复，更实用的是估算每次失败平均丢失多少小时。设训练周期内预期失败次数为 `n_fail`，checkpoint 间隔是 `\Delta_{\mathrm{ckpt}}` 小时，GPU 数是 `G`，如果故障发生时间近似均匀，则平均丢失半个 checkpoint 间隔：

```math
H_{\mathrm{lost}}
\approx
n_{\mathrm{fail}}\cdot \frac{\Delta_{\mathrm{ckpt}}}{2}\cdot G
```

这里 `n_{\mathrm{fail}}\geq0`、`\Delta_{\mathrm{ckpt}}>0`、`G>0`；`n_fail` 是期望次数时，`H_lost` 也是期望 GPU-hours，不应和某次事故的实际损失混为一谈。这就是为什么 checkpoint 间隔、自动恢复和 smoke test 都是成本规划的一部分。

checkpoint 间隔并不是越短越好。把间隔从 4 小时缩短到 1 小时，平均故障丢失时间会下降，但保存次数、网络写入和训练暂停会增加。一个简单的选择可以比较两项：每次保存带来的墙钟开销，和故障后平均丢失的 GPU-hours。若保存一次耗时 `t_save` 小时、故障率近似为每小时 `\lambda_{\mathrm{fail}}`、集群有 `G` 张卡，则单位时间的保存成本约为 `t_{\mathrm{save}}/\Delta_{\mathrm{ckpt}}`，故障重跑成本的期望量级约为 `\lambda_{\mathrm{fail}}\Delta_{\mathrm{ckpt}}G/2`。这些量都需要非负、有限，且 `\Delta_{\mathrm{ckpt}}>0`；真实故障不是均匀独立分布时，这只是起点，节点级、机架级和存储级故障要分开测量。

完整训练失败概率 `q` 和单次 checkpoint 恢复失败概率不是同一个变量。如果恢复能从最近版本继续，训练成本更接近“成功主循环 + 每次故障丢失的尾部 + 恢复和验证开销”，而不是简单地把整个训练重复一遍。反过来，如果 checkpoint 只保存了模型权重，没有 optimizer 或 data cursor，表面上恢复成功，实际上可能改变学习率、数据顺序和梯度状态，导致后续实验不可比。

### 8.2 降低重跑成本的方法

1. 定期 checkpoint。
2. 自动恢复。
3. 异常监控。
4. 单变量实验。
5. 小规模预实验。
6. 关键配置先做 smoke test。

训练成本不只是成功一次的成本，还要考虑失败概率、恢复点质量、重跑窗口和恢复后的行为偏差。

## 9. 资源规划流程

可以按下面顺序做规划：

```text
1. 明确目标：要做 base model、SFT、对齐、VLM 还是 reasoning model？
2. 估算参数规模和 token 数。
3. 估算显存：参数、梯度、optimizer、激活。
4. 估算 tokens/s 和训练时长。
5. 判断 GPU 数量和并行策略。
6. 估算 checkpoint 存储和恢复成本。
7. 估算失败重跑成本。
8. 给出冗余和评估时间预算。
```

这个流程比单纯问“有几张卡”更接近真实项目。

规划时最好同时维护三张表。第一张是**计算表**：参数量、token 数、序列长度、有效 FLOPs、实测 tokens/s 和预计墙钟时间；第二张是**状态表**：权重、梯度、optimizer、激活、checkpoint、数据游标和版本 manifest 的显存/存储占用；第三张是**风险表**：节点故障率、保存时间、评估停顿、数据等待、恢复时间、回归失败和人工介入。三张表互相影响：提高 checkpoint 频率会改变计算表的可用时间，提高序列长度会同时改变计算表和状态表，增加冗余节点会提高成本却可能降低失败重跑风险。

一个有用的实验顺序是先用单机或少量卡做三个 benchmark：

1. **单步效率**：固定真实序列长度和 micro-batch，测 forward/backward、optimizer 和通信。
2. **扩展效率**：逐步增加 GPU，测 `eta(G)`、collective 时间和有效 global token 吞吐。
3. **长时间稳定性**：至少覆盖一次 checkpoint、validation 和人为恢复，测 wall-clock availability、保存/恢复时间和数据游标连续性。

只有第一项通过，不能推出大规模训练可行；只有第二项吞吐高，也不能推出恢复和长期成本可控。

## 10. 一个粗略规划示例

假设你要训练一个中等规模模型，目标是：

```text
1. 训练 token：1e12
2. 训练时长：60 天
3. 预算：若干 GPU 集群
4. 需要中途评估和容错
```

你至少要估：

1. 每秒需要多少 token 吞吐。
2. 单卡能否放下模型。
3. 需要多少并行。
4. checkpoint 存储要多少 TB。
5. 如果失败一次，能否接受重跑。

如果实际 tokens/s 远低于目标，那就要么扩 GPU，要么降模型，要么调整序列长度、并行和优化策略。

把这个例子算一遍会更直观。若 `D=10^{12}`、目标墙钟时间为 60 天、预留 20% 的非训练时间，则：

```math
R_{\mathrm{need}}
=\frac{10^{12}}{60\times86400\times0.8}
\approx2.41\times10^5\ \mathrm{tokens/s}
```

假设小规模实测单卡长期吞吐为 `r_1=4000 tokens/s`，128 卡的扩展效率为 `eta(128)=0.55`，则预计集群吞吐为 `281600 tokens/s`，纸面上满足目标；但如果长序列评估、保存和节点恢复让可用比例从 `0.8` 降到 `0.65`，实际需要的 steady throughput 会升到约 `296300 tokens/s`，原方案就不再宽裕。这个差异说明冗余不是把一个固定百分比加到 GPU 数量上，而是要从时间预算和实测可用率倒推。

最后还要把能力收益放进决策。若增加 20% token 只让验证集 loss 改善，却不改善目标领域的关键任务，单位成功任务成本可能上升；若多保留一份恢复 checkpoint 能显著减少失败后的回滚损失，它即使增加存储费也可能是合理支出。资源规划的终点不是“算出一串 GPU 数”，而是解释每项资源如何换来训练进展、可靠性或可复现性。

### 10.1 最小可运行训练成本审计 demo

下面这个 0 依赖 demo 用一个 toy 训练计划做量级诊断。输入包括参数量、训练 token 数、GPU 数、单卡峰值、MFU、目标训练天数、运行 overhead 和 checkpoint 策略；输出包括训练 FLOPs、长期 tokens/s、训练天数、GPU-hours、checkpoint 存储和失败重跑的预期损失。示例中的存储上限和 MFU 区间只是为了演示如何记录假设，不是通用标准。

```python
import math


def require_positive_int(value, name):
    if type(value) is not int or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def require_nonnegative_int(value, name):
    if type(value) is not int or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")
    return value


def require_finite(value, name, minimum=None, maximum=None):
    if isinstance(value, bool) or not isinstance(value, (int, float)) or not math.isfinite(value):
        raise ValueError(f"{name} must be finite")
    value = float(value)
    if minimum is not None and value < minimum:
        raise ValueError(f"{name} must be >= {minimum}")
    if maximum is not None and value > maximum:
        raise ValueError(f"{name} must be <= {maximum}")
    return value


def gib(num_bytes):
    num_bytes = require_finite(num_bytes, "num_bytes", minimum=0)
    return num_bytes / 1024**3


params = require_positive_int(7_000_000_000, "params")
train_tokens = require_positive_int(1_000_000_000_000, "train_tokens")
gpus = require_positive_int(128, "gpus")
peak_tflops_per_gpu = require_finite(1_000, "peak_tflops_per_gpu", minimum=0)
if peak_tflops_per_gpu == 0:
    raise ValueError("peak_tflops_per_gpu must be positive")
mfu = require_finite(0.40, "mfu", minimum=0, maximum=1)
if mfu == 0:
    raise ValueError("mfu must be positive for a finite plan")
target_days = require_finite(14, "target_days", minimum=0)
if target_days == 0:
    raise ValueError("target_days must be positive")
runtime_overhead = require_finite(0.08, "runtime_overhead", minimum=0, maximum=1)
if runtime_overhead == 1:
    raise ValueError("runtime_overhead must be below 1")

weight_bytes = require_positive_int(2, "weight_bytes")
grad_bytes = require_positive_int(2, "grad_bytes")
adam_state_bytes = require_positive_int(8, "adam_state_bytes")
master_weight_bytes = require_positive_int(4, "master_weight_bytes")
latest_resume_count = require_nonnegative_int(2, "latest_resume_count")
milestone_inference_count = require_nonnegative_int(10, "milestone_inference_count")
failure_rate_per_day = require_finite(0.05, "failure_rate_per_day", minimum=0)
checkpoint_interval_hours = require_finite(4, "checkpoint_interval_hours", minimum=0)
if checkpoint_interval_hours == 0:
    raise ValueError("checkpoint_interval_hours must be positive")
example_storage_budget_gib = require_finite(500, "example_storage_budget_gib", minimum=0)

train_flops = 6 * params * train_tokens
peak_flops = gpus * peak_tflops_per_gpu * 1e12
effective_flops = peak_flops * mfu
tokens_per_s = effective_flops / (6 * params)
base_train_seconds = train_flops / effective_flops
base_train_days = base_train_seconds / 86400
availability = 1 - runtime_overhead
required_tokens_per_s = train_tokens / (target_days * 86400 * availability)

weight_gib = gib(params * weight_bytes)       # BF16/FP16 inference weights.
grad_gib = gib(params * grad_bytes)           # BF16/FP16 gradients, rough estimate.
adam_gib = gib(params * adam_state_bytes)     # FP32 m and v.
master_gib = gib(params * master_weight_bytes)
resume_ckpt_gib = weight_gib + grad_gib + adam_gib + master_gib
inference_ckpt_gib = weight_gib
retained_storage_gib = (
    latest_resume_count * resume_ckpt_gib
    + milestone_inference_count * inference_ckpt_gib
)

gpu_hours_success = gpus * base_train_seconds / 3600
expected_failures = failure_rate_per_day * base_train_days
expected_lost_gpu_hours = (
    expected_failures * (checkpoint_interval_hours / 2) * gpus
)
planned_main_loop_seconds = base_train_seconds / availability
expected_recovery_seconds = expected_lost_gpu_hours / gpus * 3600
planned_wall_days = (
    planned_main_loop_seconds + expected_recovery_seconds
) / 86400

diagnostics = {
    "throughput_meets_target": tokens_per_s >= required_tokens_per_s,
    "storage_under_example_budget": retained_storage_gib <= example_storage_budget_gib,
    "planned_under_target": planned_wall_days <= target_days,
    "mfu_in_example_range": 0.25 <= mfu <= 0.6,
    "recovery_assumption_recorded": expected_failures >= 0 and checkpoint_interval_hours > 0,
}

print(f"train_flops={train_flops:.2e}")
print(f"effective_cluster_pflops={effective_flops / 1e15:.1f}")
print(f"tokens_per_s={tokens_per_s:.0f}")
print(f"required_tokens_per_s={required_tokens_per_s:.0f}")
print(f"base_train_days={base_train_days:.2f}")
print(f"planned_wall_days={planned_wall_days:.2f}")
print(f"gpu_hours_success={gpu_hours_success:.0f}")
print(f"resume_ckpt_gib={resume_ckpt_gib:.2f}")
print(f"retained_storage_gib={retained_storage_gib:.2f}")
print(f"expected_failures={expected_failures:.2f}")
print(f"expected_lost_gpu_hours={expected_lost_gpu_hours:.1f}")
print(f"diagnostics={diagnostics}")

assert 0 < availability <= 1
assert tokens_per_s > 0
assert planned_wall_days >= base_train_days
assert expected_recovery_seconds >= 0
```

读这段输出时要注意：`base_train_days` 只来自模型主循环，`planned_wall_days` 才把 checkpoint/评估 overhead 和期望故障损失纳入了计划；`resume_ckpt_gib` 远大于推理权重，是因为训练恢复需要 optimizer state 和 master weights；`diagnostics` 中的每个布尔值只回答一个局部假设，不能替代真实集群 benchmark、稳定性测试或成本报价。

## 11. 常见资源规划错误

### 11.1 只看模型参数量

忽略 token 数、训练时长和激活显存。

### 11.2 只看峰值吞吐

忽略 checkpoint、评估和故障重启。

### 11.3 不考虑失败率

训练一旦不稳定，实际成本会成倍上升。

### 11.4 不考虑存储和网络

checkpoint 和数据流会成为瓶颈。

### 11.5 不留余量

所有资源卡满后，调试和容错空间很小。

这些错误可以用“错误假设 -> 观测症状 -> 先测什么”来定位：

| 错误假设 | 常见症状 | 优先补的证据 |
| --- | --- | --- |
| 单卡吞吐可以线性扩展 | GPU 数增加后 tokens/s 几乎不涨 | all-reduce、TP/PP collective 和扩展效率曲线 |
| MFU 等于 GPU busy | 监控显示很忙，训练仍然很慢 | 有效 FLOPs、通信时间、数据等待和重计算时间 |
| checkpoint 只有权重 | 能加载模型，却无法复现下一步训练 | optimizer、RNG、data cursor、配置和版本 manifest |
| 失败概率可以忽略 | 理论计划能完成，实际反复延期 | 节点级故障率、恢复时间和平均丢失窗口 |
| token 数就是有效学习量 | loss 下降，关键领域能力不涨 | label mask、重复率、数据配比和分任务收益 |
| 存储容量足够就能保存 | 训练周期被保存任务拖长 | 聚合写带宽、保存耗时和异步一致性 |

资源规划的 debug 也应遵循最小假设原则。先固定数据、序列长度和 checkpoint 策略，测出单步和长时间基线；再一次只改变 GPU 数、并行方式或 kernel。否则所有变量同时变化，最后只能知道“这次更贵”或“这次更快”，却不知道原因。

## 12. 常见误判与诊断路径

资源规划中的错误通常不是不会套公式，而是把一个局部指标当成了整个系统的结论。下面把常见误判改写成可以执行的诊断路径。

### 12.1 “参数量已经告诉我需要多少卡”

参数量首先影响权重、梯度和优化器状态，但它不能单独决定激活显存、序列项、通信拓扑或训练期限。遇到 OOM 时，先区分稳态状态和瞬时峰值：如果是 optimizer state 超限，应检查分片、状态精度和参数分组；如果是 activation 超限，应检查 sequence length、micro-batch、pipeline in-flight 数量和重计算；如果是 temporary buffer 超限，应查看 kernel、通信 bucket 和显存碎片。

### 12.2 “GPU busy 很高，所以训练效率很好”

先把 step 分解为计算、通信、数据等待和其他停顿，再把 MFU/HFU 的分子写出来。若 GPU busy 高而 MFU 低，可能是访存受限、通信 kernel 或低效矩阵形状；若 MFU 高而 wall-clock 吞吐低，可能是频繁保存、评估或恢复占用了大量时间。只有将 `tokens/s`、有效 FLOPs、通信占比和时间窗口放在一起，才知道瓶颈属于哪一层。

### 12.3 “checkpoint 能加载模型，就说明训练可以恢复”

加载模型权重只验证了发布状态的一小部分。恢复训练还应检查 optimizer 和 scheduler 状态、随机数状态、数据游标、并行拓扑、梯度累积步数、配置版本以及 checkpoint manifest。最小恢复演练应从保存点复制出一个短分支，比较恢复前后若干 step 的 loss、学习率、数据样本 ID 和参数更新；只要其中一项不一致，就应把它记录为恢复语义差异，而不是用“加载成功”掩盖。

### 12.4 “token 数越多，能力一定越好”

首先确认 token 是输入 token、有效 label token 还是 rollout token；然后检查重复率、数据污染、领域配比、padding 和样本权重。预训练的 scaling law 是在特定数据、模型和优化设置下观察到的经验关系，不能推出 SFT、RL 或多模态数据的固定比例。若总 loss 下降而关键任务没有改善，应把成本分配到数据子集和目标任务，而不是只增加总 token。

### 12.5 “把 GPU 数翻倍，训练时间就减半”

先测候选规模的扩展效率 `eta(G)`，再检查 global batch 是否改变了优化路径、并行拓扑是否跨越低带宽链路、通信是否与计算重叠、数据管道是否能供满。Megatron-LM 的公开实验已经显示大规模并行效率需要实测，不能由单卡峰值线性外推。扩容决策应同时比较墙钟时间、GPU-hours、网络压力和收敛所需 token 数。

### 12.6 “存储容量足够，checkpoint 就不会影响训练”

容量只回答“放不放得下”，不回答“能否在训练窗口内写完并验证”。测量聚合写带宽、metadata 开销、校验和、对象存储并发、异步保存的快照语义和恢复时间。如果保存耗时接近保存间隔，应该先减少状态副本、改变保存策略或提高带宽，而不是盲目增加容量。

资源规划的 debug 应遵循最小假设原则：固定数据版本、序列长度、精度和保存策略，先建立单步与长时间基线；再一次只改变 GPU 数、并行方式或 kernel。这样得到的每条结论都能回溯到一个可测变量。

## 13. 本章小结

本章的核心不是记住一个“多少卡”的答案，而是建立一条可复核的推理链：先把参数量和有效 token 换成 FLOPs，再用实测吞吐和扩展效率换成墙钟时间；同时为显存状态、数据管道、checkpoint 带宽、故障恢复、评估停顿和人力保留预算。最后用单位成功任务或有效能力收益检查这些支出是否值得。

当一个计划从纸面走向集群，最先失真的通常是三个地方：单卡峰值被误当成长时间吞吐，GPU 数被误当成线性加速，恢复 checkpoint 被误当成只有模型权重。把这些假设和实测证据分开记录，成本规划才能指导工程决策，而不是训练结束后的解释。

## 14. 资料与进一步阅读

1. [Training Compute-Optimal Large Language Models（Chinchilla）](https://arxiv.org/abs/2203.15556)：参数量、训练 token 和固定计算预算之间的 compute-optimal 关系；论文结论依赖其训练设定，不能直接当成所有任务的固定比例。
2. [Scaling Laws for Neural Language Models](https://arxiv.org/abs/2001.08361)：损失、模型规模、数据量和计算量之间的经验 scaling law，适合理解为什么要用曲线而不是单点猜测。
3. [PaLM: Scaling Language Modeling with Pathways](https://arxiv.org/abs/2204.02311)：公开报告中的训练系统规模、并行训练和 MFU/HFU 讨论，可用于核对利用率口径。
4. [Megatron-LM](https://arxiv.org/abs/1909.08053)：张量并行和大规模 Transformer 训练系统的经典公开资料。
5. [ZeRO: Memory Optimizations Toward Training Trillion Parameter Models](https://arxiv.org/abs/1910.02054)：参数、梯度和 optimizer state 分片对显存与通信的影响。
6. [MLPerf Training](https://mlcommons.org/benchmarks/training/)：公开训练 benchmark 的任务、规则和结果入口；不同系统的结果必须结合模型、精度、数据和收敛标准解读。
7. [PyTorch Fully Sharded Data Parallel](https://docs.pytorch.org/docs/stable/fsdp.html)：核对 FSDP 的参数、梯度和 optimizer state 分片实现边界。

这些资料适合核对机制和公开测量方法；真实项目仍需要用目标模型、目标序列长度、目标数据 pipeline 和目标集群做短程 benchmark，再把实测 `tokens/s`、扩展效率、保存带宽和恢复时间替换进本章公式。
