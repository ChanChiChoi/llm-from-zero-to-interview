# 第八章：显存优化与数值精度：预算、峰值与数值轨迹

## 8.0 先问显存峰值发生在哪里

“一个 7B 模型需要多少显存？”没有一个脱离训练阶段、精度、并行方式和 batch 的单一答案。推理、全参数训练、参数高效微调和量化加载占用的是不同的对象；即使是同一种训练，forward、backward、optimizer step、evaluation 和 checkpoint 也可能在不同时间产生不同峰值。

一次训练 step 的资源可以先画成：

~~~text
parameters + gradients + optimizer states
  + activations saved for backward
  + attention/intermediate tensors
  + communication and kernel workspaces
  + allocator reserve and fragmentation
~~~

初学者可以把显存优化理解成“让同一张 GPU 能承载更多有效训练工作”。专家必须继续区分：

1. 是总字节数减少，还是只是被 shard 到别的 GPU？
2. 是稳态显存下降，还是 transient all-gather 峰值仍然存在？
3. 是激活减少，还是只减少了 optimizer state？
4. 是存储精度降低，还是计算和累积精度也降低？
5. 是 FP16/BF16/FP8 的格式变化，还是量化底座的权重编码？
6. 是真实吞吐提高，还是因为把计算搬到 CPU/NVMe 而 GPU 峰值下降？

本章先建立显存账本，再分别讨论激活、attention 中间结果、混合精度、loss scaling、FP8、activation checkpointing、gradient accumulation、ZeRO/FSDP、LoRA/QLoRA、FlashAttention、OOM 和 NaN/Inf。每种方法都说明它改变了哪一项，以及没有改变什么。

## 8.1 训练显存的五类账本

先区分三个不同的问题：模型需要多少逻辑状态、当前有哪些张量仍活着、allocator 向设备申请了多少内存。参数字节数只能回答第一个问题的一部分。

### 8.1.1 参数

如果模型有 P 个参数，每个参数占 b_w 字节，权重存储量是：

~~~math
M_{\mathrm{weight}}
=
P b_w
~~~

7B 参数使用 BF16 权重时，理论权重大小约为：

~~~math
7\times10^9\times2
\approx
14\times10^9\ \text{bytes}
~~~

换算成 GiB 约为 13.04。这个数字只描述一份权重，不包含模型副本、梯度、optimizer state、激活、通信 buffer 或 runtime reserve。

这里 P 是正整数，b_w 是非负的每元素字节数；若只是在比较多个 dtype，必须先统一 GB（10 的幂）或 GiB（2 的幂）的单位。把 14e9 bytes 当成 14 GiB，会在容量规划中凭空少算约 7%。

### 8.1.2 梯度

全参数训练通常需要为可训练参数保存梯度。若梯度元素平均占 b_g 字节：

~~~math
M_{\mathrm{grad}}
=
P_{\mathrm{train}}b_g
~~~

P_train 等于全参数训练时的 P，但在 LoRA 等参数高效微调中只等于可训练增量参数的数量。冻结底座不代表 forward 不经过它，只代表底座参数通常不需要保存梯度。

### 8.1.3 Optimizer state

AdamW 通常保存一阶矩 m 和二阶矩 v。若二者都是 FP32：

~~~math
M_{\mathrm{Adam\ state}}
\approx
P_{\mathrm{train}}\times(4+4)
=
8P_{\mathrm{train}}
~~~

某些训练还需要 FP32 master weights：

~~~math
M_{\mathrm{master}}
=
P_{\mathrm{train}}b_{\mathrm{master}}
~~~

因此一个简化的持久训练状态是：

~~~math
M_{\mathrm{state}}
\approx
P b_w
+
P_{\mathrm{train}}b_g
+
M_{\mathrm{optimizer}}
+
M_{\mathrm{master}}
~~~

### 8.1.4 激活和 attention 中间结果

forward 为 backward 留下的激活通常依赖：

~~~math
M_{\mathrm{act}}
\propto
B_{\mathrm{micro}}
\cdot
T
\cdot
d
\cdot
N_L
\cdot
b_{\mathrm{act}}
~~~

其中 B_micro 是 micro-batch，T 是序列长度，d 是 hidden size，N_L 是层数。实际实现会因为保存哪些张量、融合哪些 kernel 和是否使用 checkpoint 而有不同常数。

### 8.1.5 临时空间、通信和 allocator

还要保留：

- GEMM、softmax、归一化和量化 kernel 的 workspace；
- FSDP/ZeRO 参数 all-gather 和梯度 reduce-scatter buffer；
- DDP gradient bucket；
- activation recompute 的临时张量；
- CUDA caching allocator 已保留但当前未使用的块；
- 内存碎片和对齐浪费。

这些量会随时间变化。正确的峰值定义是先在同一时刻统计仍活着的分配，再在整个 step 中取最大值：

~~~math
M_{\mathrm{allocated}}(t)
=
\sum_{x\in\mathcal{L}(t)}\operatorname{bytes}(x),
\qquad
M_{\mathrm{peak,allocated}}
=
\max_{t\in\mathrm{step}}M_{\mathrm{allocated}}(t)
~~~

这里 $\mathcal{L}(t)$ 是时刻 $t$ 仍被张量引用的设备分配。workspace、通信 buffer 和重计算临时值只有在和其它活张量同时存在时才计入这个峰值；不能把各自独立测得的峰值简单相加。上述公式描述张量分配峰值，未必包括第三方库直接向 CUDA 申请而没有经过 PyTorch allocator 的内存。

PyTorch allocator 的 `allocated` 和 `reserved` 也不能相加：前者是当前张量占用，后者是 allocator 管理的缓存段，通常满足 allocated 不大于 reserved。设备还可能有 CUDA context、NCCL、其它进程或自定义 kernel 的内存。每个指标都要绑定同一 device、rank、时间窗口和单位；不要用平均值替代峰值，也不要把预计 buffer 写成已测量值。

## 8.2 一个 7B 全参数训练的量级账本

假设：

~~~text
weights: BF16, 2 bytes/parameter
gradients: BF16, 2 bytes/parameter
Adam m/v: FP32, 8 bytes/parameter in total
FP32 master weights: 4 bytes/parameter
~~~

忽略激活和临时空间时：

~~~math
M_{\mathrm{state}}
\approx
P(2+2+8+4)
=
16P\ \text{bytes}
~~~

对 P=7B：

~~~math
M_{\mathrm{state}}
\approx
112\times10^9\ \text{bytes}
\approx
104.31\ \text{GiB}
~~~

这个例子假定 optimizer 另外保留 FP32 master weights。若没有 master copy，同一组 BF16 参数、BF16 梯度和 FP32 m/v 是 12 bytes/parameter，即 84 GB = 78.23 GiB。实际实现还可能把梯度保留为 FP32、使用分片 optimizer state，或让参数与 optimizer state 使用不同 dtype；所以“每参数 16 bytes”是一个明确配方的账本，不是 AdamW 的定律。Mixed Precision Training 原论文介绍了 FP16 参数副本、FP32 master weights、FP32 累积和 loss scaling 的组合；框架与训练栈后来出现了多种变体。[原论文](https://arxiv.org/abs/1710.03740)

104.31 GiB 只是一份参数、梯度、optimizer state 和 master copy 的持久量级；它尚未计入激活、workspace 和通信。80 GiB GPU 无法容纳这份状态，更不能据此断言 80 GB 标称容量的 GPU 能否训练。更可靠的估算要把“全局有多少状态”与“每个 rank 暂时拿到多少参数”分开。ZeRO/FSDP 的分片阶段、瞬时 all-gather 和拓扑边界已在[第五册第七章](07-分布式训练.md)展开；这里继续关注它们如何改变本章的单卡峰值。

实际方案可能使用：

- ZeRO/FSDP，把状态 shard 到多个 DP rank；
- activation checkpointing，降低激活峰值；
- BF16/FP16，降低张量存储；
- FlashAttention，避免显式保存完整 attention score；
- 更小 micro-batch 加 gradient accumulation；
- LoRA/QLoRA，在微调时减少可训练状态。

每种手段作用在不同账本上，不能把它们当成互相替换的开关。

## 8.3 稳态显存和瞬时峰值

### 8.3.1 为什么平均值会误导

一个训练进程可能在大多数时间只使用 60GB，却在某一层 all-gather、optimizer step 或 evaluation 时瞬间需要 82GB。GPU OOM 由峰值触发，不由平均占用触发。

应分别记录：

~~~text
allocated bytes
reserved bytes
peak allocated bytes
peak reserved bytes
allocation event
module or kernel
rank
timestamp or step
~~~

`torch.cuda.memory_allocated()` / `max_memory_allocated()` 记录张量占用，`memory_reserved()` / `max_memory_reserved()` 记录 PyTorch caching allocator 管理的内存。`nvidia-smi` 可能显示 reserved；reserved 明显高于 allocated 不自动等于泄漏。`torch.cuda.empty_cache()` 只把未被张量占用的缓存块交还给其它 GPU 应用，不会释放活张量，也不会增加 PyTorch 自己可用的活张量预算。[PyTorch 2.14 CUDA memory 说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html)

一个常见诊断顺序是：先复位峰值统计，再运行一个完整、代表性的 step，并在测量边界同步设备；分别记录 allocated、reserved 和设备总占用。若 allocated 本身触顶，先找活张量和生命周期；若 reserved 接近容量但 allocated 低很多，再检查缓存块分布、碎片和外部分配。snapshot 只看经过 PyTorch allocator 的 CUDA 分配；NCCL 或自定义扩展直接申请的内存可能不在图里。[PyTorch CUDA memory snapshot 说明](https://docs.pytorch.org/docs/2.14/torch_cuda_memory)

### 8.3.2 FSDP/ZeRO 的 transient all-gather

参数分片降低的是常驻 shard。计算模块前，完整参数可能被临时聚合：

~~~text
parameter shard
  -> all-gather full module parameters
  -> forward/backward
  -> release or reshard
~~~

因此：

~~~math
M_{\mathrm{all-gather\ phase}}(t)
=
M_{\mathrm{other\ live}}(t)
+
M_{\mathrm{unsharded\ current\ module}}(t)
+
M_{\mathrm{collective\ workspace}}(t)
~~~

`M_other live` 是否包含本地参数 shard、激活和梯度，取决于该实现当时保留了哪些对象；公式要求它们在同一时刻统计，不能把独立峰值叠加。wrap 粒度越粗，单次 unsharded module 可能越大；wrap 粒度越细，通信次数和小 buffer 可能更多。报告“ZeRO-3 只占全量状态的 1/N”时，必须说明这是理想稳态分片量级，不能把它当成峰值保证。

### 8.3.3 evaluation 和 checkpoint 的额外峰值

evaluation 可能因为没有 no_grad、保留 logits、累积 hidden states 或使用更长样本而产生额外显存。checkpoint 可能暂时聚合参数、转换 dtype、复制 state 或压缩 tensor。

训练和评估使用同一张 GPU 时，必须单独测：

~~~text
train forward peak
train backward peak
first optimizer step peak
steady-state optimizer step peak
validation peak
checkpoint peak
~~~

第一次 optimizer step 与后续 step 应分开测。以 PyTorch 2.14 的 Adam 实现为例，`exp_avg` 和 `exp_avg_sq` 在 optimizer 第一次接触有梯度的参数时惰性创建；这会让“第一次 step 才 OOM”表现为持久状态首次落地，而不一定是一次短暂 workspace。[PyTorch v2.14 Adam 源码](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/optim/adam.py)

## 8.4 激活显存：batch 和 context 的乘积

### 8.4.1 影响激活的变量

激活显存通常随以下因素增加：

1. micro-batch 增大；
2. sequence length 增大；
3. hidden size 增大；
4. 层数增多；
5. 保存更多中间张量；
6. 使用更高存储精度。

一个教学级关系是：

~~~math
M_{\mathrm{act}}
\propto
B_{\mathrm{micro}} T d N_L b_{\mathrm{act}}
~~~

它用于判断哪个旋钮影响最大，不应被当成所有 Transformer 实现的精确显存公式。

用一个具体张量看它的量级：B=1、T=4096、d=4096、BF16 时，一个 hidden-state 张量有 $BTd$ 个元素，占 32 MiB。若每一层都为 backward 保留一个这样的张量，32 层就是 1 GiB；T 增至 32K 时，相同这一项变为 8 GiB。真实每层通常保留多个形状不同的张量，融合 kernel、重计算、并行切分和张量生命周期都会改变结果，所以这个推演只计“一个 hidden-sized 张量/层”，不是完整模型预算。

### 8.4.2 为什么长上下文特别昂贵

如果 B_micro、d 和 N_L 不变，把 T 从 4K 增加到 32K，线性激活项可能增加约 8 倍；如果实现显式保存 full attention score，attention 中间项还可能随 T^2 增长。

这使得“只把 context length 调长”经常比“把 batch 加倍”更容易触发 OOM。长上下文训练需要同时考虑：

- packing 和 padding 利用率；
- attention kernel；
- activation checkpointing；
- sequence/context parallel；
- 实际有效 token；
- 训练吞吐和通信。

把两种项放在同一张表里更容易看出 FlashAttention 的价值与边界。仍取 B=1、H=32、BF16，且假设内核显式物化完整 score 矩阵：

| 序列长度 T | 一个 hidden-sized 张量/32 层 | 一个 attention score 矩阵/单层 |
| ---: | ---: | ---: |
| 4,096 | 1 GiB | 1 GiB |
| 32,768 | 8 GiB | 64 GiB |

hidden-state 项随 T 线性增长，单层 score 项随 T 平方增长。表中 score 列只数一层的一份 score，不包含 softmax 输出、dropout mask、其它层激活或临时 buffer；causal kernel 是否实际分配完整方阵取决于实现。FlashAttention 解决的是避免将这类完整中间矩阵写回 HBM，不会让其 attention 乘加次数从平方量级消失。

### 8.4.3 激活不是参数

ZeRO/FSDP 主要切分参数、梯度和 optimizer state，不会自动把每个 micro-batch 的所有激活变小。反过来，activation checkpointing 可以降低激活，却不减少 AdamW 的 m/v。

这一边界很重要：

| OOM 来源 | 首先考虑 |
| --- | --- |
| 参数/optimizer state | ZeRO/FSDP、offload、低比特 state |
| micro-batch 激活 | 减小 micro-batch、checkpointing |
| full attention 中间结果 | FlashAttention、稀疏/局部 attention |
| 单层计算临时 buffer | kernel、dtype、wrap 粒度 |
| evaluation 缓存 | no_grad、分批评估、及时释放 |

## 8.5 Attention 中间结果与 FlashAttention

### 8.5.1 标准 attention 的 score 矩阵

对 batch size B、head 数 H、序列长度 T，显式 attention score 的元素规模是：

~~~math
N_{\mathrm{score}}
=
BHT^2
~~~

如果每个元素占 b 字节：

~~~math
M_{\mathrm{score}}
=
BHT^2b
~~~

例如 B=1、H=32、T=4096、BF16 时，单层单份 score 矩阵约为：

~~~math
1\times32\times4096^2\times2
\approx
1\ \text{GiB}
~~~

真实训练还可能保存 dropout mask、softmax 结果和其他张量，因此不能只用这一项作完整预算。

该式要求 B、H、T 为正整数，b>0，并假设 score 在给定 dtype 中真的被显式物化。带 causal mask、padding mask 或 block-sparse 布局仍可能有不同的实际张量形状；不能只凭模型配置把所有 attention kernel 都按 BHT^2 分配。

### 8.5.2 FlashAttention 改变什么

FlashAttention 的核心是 IO-aware、分块的 attention kernel。它在片上存储中分块计算 Q/K/V 和 softmax，避免把完整 T x T score 矩阵物化并写回高带宽显存。

为什么分块后还能得到同一个 softmax？对一行 score，处理过一部分 key 后只需保存三个量：当前最大值 m、稳定的指数和 l、加权 value 和 o：

~~~math
m=\max_j s_j,
\qquad
l=\sum_j e^{s_j-m},
\qquad
o=\sum_j e^{s_j-m}v_j,
\qquad
\mathrm{output}=o/l
~~~

现在加入一个新 tile，里面的 score 为 $s'$、value 为 $v'$。令新最大值 $m'=\max(m,\max s')$，旧累积量必须先换到新基准，再加新 tile：

~~~math
\alpha=e^{m-m'},
\qquad
l'=\alpha l+\sum_j e^{s'_j-m'},
\qquad
o'=\alpha o+\sum_j e^{s'_j-m'}v'_j
~~~

这个更新既保持 softmax 归一化，又避免直接对很大的 logits 取指数。手算 score $[1,2]$、value $[10,20]$ 后，再加入 score $0$、value $30$：第一块的 $m=2$、$l=e^{-1}+1\approx1.3679$、$o=10e^{-1}+20\approx23.6788$；第二块不改变最大值，增加 $e^{-2}\approx0.1353$ 和 $30e^{-2}\approx4.0601$，得到 $l'\approx1.5032$、$o'\approx27.7389$，输出约 $18.45$。它与一次性对三个 score 做 softmax 的结果一致。FlashAttention 将该递推放进 tile kernel；反向还会重算局部 score，而不是把全量 score matrix 留在 HBM。[FlashAttention 原论文 §3](https://arxiv.org/abs/2205.14135)

它主要改变：

- HBM 与片上存储之间的读写；
- 中间 score/softmax 的物化方式；
- attention kernel 的吞吐和峰值工作区。

它不自动改变：

- full attention 的全局可见性；
- 理论上的二次 token 关系；
- MLP、embedding 和其他层的激活；
- checkpoint、optimizer state 和通信 buffer。

更准确地说：朴素实现把 $T^2$ 大小的 score/probability 中间量物化；FlashAttention 把中间存储压到输出、每行统计量和 tile 工作区，减少 HBM 读写，并在 backward 重算局部 score。完整 attention 仍计算所有可见 query-key 对，因此算术量仍是 $O(BHT^2d_h)$。所以“attention 的中间存储与 HBM 流量减少”是准确的，“FlashAttention 把精确 full attention 的算术复杂度变成线性”是不准确的。原论文证明的是 IO 复杂度改进，并在其硬件和序列长度下报告端到端训练收益；不能把论文速度数字当成当前任意 kernel 的保证。

### 8.5.3 FlashAttention 与 checkpointing 的区别

二者都可能减少 attention 相关峰值，但机制不同：

| 方法 | 主要手段 | 主要代价 |
| --- | --- | --- |
| FlashAttention | 不物化完整中间矩阵，优化 IO | 依赖 kernel/硬件 |
| Activation checkpointing | backward 时重算 forward | 增加计算 |
| Sparse/local attention | 减少可见 token 关系 | 改变模型结构和质量边界 |

一个系统可以同时使用三者，结果不能把各自的理想节省比例直接相乘。

## 8.6 FP32、FP16、BF16 与 FP8 的表示边界

### 8.6.1 字节数不是全部

对 n 个元素，存储空间是：

~~~math
M_{\mathrm{tensor}}
=
n b_{\mathrm{dtype}}
~~~

但数值格式还决定：

- 最大有限值；
- 最小 normal 值；
- subnormal 是否可用；
- 有效尾数位；
- 舍入误差；
- 乘加累积精度。

两个 dtype 都占 2 bytes，不代表训练行为相同。

表中的 `spacing at 1` 表示 1 附近相邻可表示数的间隔，`min normal` 不包含更小的 subnormal。硬件和 kernel 可能对 subnormal 采用不同处理；它们也可能使用低精度乘法、FP32 累积，因此不能从输入 dtype 单独推断整个运算的累积精度。

| 格式 | 位布局 | 最大有限值 | 最小 normal | 1 附近间隔 |
| --- | --- | ---: | ---: | ---: |
| FP32 | 1 sign + 8 exponent + 23 fraction | $3.40\times10^{38}$ | $1.18\times10^{-38}$ | $1.19\times10^{-7}$ |
| FP16 | 1 + 5 + 10 | 65,504 | $6.10\times10^{-5}$ | $9.77\times10^{-4}$ |
| BF16 | 1 + 8 + 7 | $3.39\times10^{38}$ | $1.18\times10^{-38}$ | $7.81\times10^{-3}$ |

由此能直接看出选择差异：FP16 的尾数比 BF16 更细，但指数范围窄；BF16 的指数位和 FP32 一样多，能容纳更大范围，代价是在 1 附近的舍入间隔约为 FP16 的 8 倍。BF16 因而较少发生范围型溢出/下溢，但它的舍入误差更粗，不能被叫作“更精确”。PyTorch 可用 `torch.finfo(dtype)` 查看当前实现公开的 `max`、`tiny`、`eps`；这些数值不替代对目标 kernel 的测量。[PyTorch 2.14 type info](https://docs.pytorch.org/docs/2.14/type_info.html)

### 8.6.2 FP32

FP32 具有较大的动态范围和较高尾数精度，常用于 optimizer state、master weights、部分归一化、统计累积或需要稳定累加的路径。全程使用 FP32 会增加显存和带宽，现代大模型训练通常采用混合精度，而不是把所有张量都改成同一种低精度。

### 8.6.3 FP16

FP16 每元素 2 bytes，显存和 Tensor Core 吞吐较好，但动态范围较小。大于最大有限值的结果会 overflow，小于可表示范围的梯度可能 underflow 或被硬件 flush 到零。

FP16 训练常使用 loss scaling：

~~~math
\tilde L
=
sL,
\qquad
\tilde g
=
\nabla_\theta \tilde L
=
s\nabla_\theta L
~~~

更新前还原：

~~~math
g
=
\frac{\tilde g}{s}
~~~

### 8.6.4 BF16

BF16 每元素也是 2 bytes，但指数位接近 FP32，动态范围更大。它通常更能承受大模型训练中的 activation 和梯度尺度变化，因此很多训练 recipe 不需要像 FP16 那样依赖动态 loss scaling。

BF16 的尾数位较少，舍入误差并不会消失。softmax、归一化、累加、optimizer state 和自定义 kernel 仍然需要检查。

### 8.6.5 FP8

FP8 进一步减少每元素字节数和带宽，但它不是简单地把 FP16 截断为 8 bit。通常需要：

- 为 tensor、channel 或 block 维护 scale；
- 统计 amax 或历史最大值；
- 在乘法前后执行缩放或反缩放；
- 选择不同 FP8 格式；
- 在更高精度中进行关键累积；
- 依赖支持相应 Tensor Core 和 kernel 的硬件。

E4M3 与 E5M2 把 8 位预算分给了不同部分：E4M3 用 4 位 exponent、3 位 fraction，有限值范围较窄、精度较高；E5M2 用 5 位 exponent、2 位 fraction，范围较宽、精度较粗。FP8 论文给出的标准格式最大有限值分别约为 448 与 57,344；E4M3 对特殊值的编码也与 E5M2 不同。[FP8 Formats for Deep Learning](https://arxiv.org/abs/2209.05433)

一个简化的 scale-quantize 关系是：

~~~math
q
=
\operatorname{clip}
\left(
\operatorname{round}\frac{x}{s},
q_{\min},
q_{\max}
\right),
\qquad
\hat{x}=sq
~~~

其中 s 是 scale，q 是低精度编码，hat{x} 是计算时恢复的近似值。scale 粒度越细，表示适应性可能越好，但元数据、更新和通信逻辑更复杂。

这条抽象要求 x 有限且 s>0，q_min<=q_max；s=0 不是“零量化误差”，而是无定义的除法。实际 FP8 格式、饱和规则和 amax 延迟更新由实现决定，公式只说明 scale 在数值路径中的位置。

缩放策略会决定 FP8 是否保留住极值。以 Transformer Engine 2.20.2 的 delayed-scaling recipe 为例，前向通常用 E4M3、反向用 E5M2；每个量化张量维护 scale 和 amax history。第 t 步用历史 amax 算出的 scale 量化当前张量，再把当前最大绝对值写入 history，供后续步骤更新 scale。它省去了为了当前 tensor 单独扫描并重新量化的额外通读，但如果分布突然变大，旧 scale 仍可能令当前值饱和；`amax_history` 长度、取 max 还是 most-recent 都会改变响应速度与稳定性。[Transformer Engine FP8 Primer 2.20.2](https://docs.nvidia.com/deeplearning/transformer-engine/examples/fp8_primer.html)

更新的 block scaling 把一个 scale 扩展成局部 scale。Transformer Engine 文档描述的 MXFP8 对每 32 个连续值使用 E8M0 scale；这降低单个 scale 要覆盖的动态范围，但需目标硬件和内核布局支持，训练时还可能需要分别保存正向与转置布局的量化张量。文档也描述 NVFP4：每 16 个值一组的 E4M3 scale，再加 per-tensor FP32 scale。这里的 FP4/NVFP4 是数值计算格式；QLoRA 的 NF4 是按权重分布设计的 4-bit 存储格式，二者不能因都叫“四位”而混为一谈。[Transformer Engine MXFP8/NVFP4 说明](https://docs.nvidia.com/deeplearning/transformer-engine/examples/fp8_primer.html)

FP8 是否有收益要同时看：

~~~text
hardware tensor core support
format choice
scale granularity
amax history or delayed scaling
accumulation dtype
overflow/saturation statistics
validation quality
~~~

还要分别报告权重/激活/梯度是否以 FP8 存储，哪些运算用 FP8，累加与 optimizer state 用什么 dtype，以及 scale、amax buffer 的开销。不能把“FP8 占 1 byte”直接等同于训练显存和训练时间都减半。

## 8.7 Mixed precision：不同张量使用不同精度

### 8.7.1 典型精度分工

一个常见的混合精度训练分工是：

~~~text
forward matmul: BF16 or FP16
activation storage: BF16 or FP16
  gradient: dtype follows op policy; FP16 path may be scaled then unscaled
optimizer m/v: FP32 or low-bit state
master weights: optional FP32
critical reductions: FP32 or higher-precision accumulation
~~~

实际分工由框架、硬件和训练 recipe 决定。混合精度不是“所有低精度张量一起计算”，而是根据数值敏感性选择位置。

### 8.7.2 autocast 不等于所有操作降精度

PyTorch autocast 根据算子策略选择执行 dtype；它不是把模型参数永久转换成低精度的命令。线性层等算子可能转成低精度，reduction 或 loss 算子可能保留 FP32；未列出的操作按输入 dtype 运行或依照常规类型提升。autocast 一般围住 forward 与 loss，backward 在上下文外调用。工程检查要分别看 parameter dtype、算子输入输出 dtype 和 kernel 的累积方式，而不能只看一个 `mixed_precision=true`。[PyTorch 2.14 AMP 算子规则](https://docs.pytorch.org/docs/2.14/amp.html)

### 8.7.3 梯度裁剪和 unscale 的顺序

FP16 loss scaling 时，正确顺序通常是：

~~~text
scaler.scale(loss).backward()
scaler.unscale_(optimizer)       # 如需读取或裁剪未缩放梯度
clip_grad_norm_(parameters, max_norm)
scaler.step(optimizer)           # 检查非有限梯度；必要时跳过更新
scaler.update()
~~~

若在 unscale 前裁剪，范数会乘上 loss scale，阈值就不再是原始梯度阈值。`scaler.step(optimizer)` 会在梯度非有限时跳过 optimizer 更新；若手动 `unscale_`，仍要通过 `scaler.step` 执行检查和跳过逻辑。若发现 clipping 几乎每步触发，先检查顺序及记录的是 scaled 还是 unscaled norm。PyTorch 2.14 还要求每个 optimizer 在一次 step 前只调用一次 `unscale_`，并且要等本次 effective batch 的所有 micro-batch 梯度累积完成后再调用。[PyTorch 2.14 AMP examples](https://docs.pytorch.org/docs/2.14/notes/amp_examples.html)

### 8.7.4 scaler 如何处理异常

动态 scaler 通常在检测到 Inf/NaN 时跳过该次参数更新，并调整 scale。训练日志应保留：

~~~text
current scale
scale growth/backoff events
skipped optimizer steps
overflow count
first offending rank
batch and sequence statistics
~~~

跳过一次更新不等于问题已经解决。若 scale 持续下降，可能存在学习率、数据或 kernel 层面的系统性异常。

一次有效的动态 loss scaling 更新包含四步：保持同一 scale 完成整个 effective batch 的反向累积；检查反缩放后的梯度是否有限；若有限则更新参数，若有 Inf/NaN 则跳过该次 optimizer 更新并降低 scale；连续若干次有限后按 scaler 策略提高 scale。scale 本身应为有限正数。若 scale 太大而 forward/backward 出现 overflow，它只会让溢出更多；若输入 loss 已是 NaN、监督 token 数为零或 reduction 分母错误，scale 也修不好目标定义。PyTorch 文档明确指出 GradScaler 的 scale 不保证大于 1；BF16 预训练模型转 FP16 时可能超出 FP16 的 65,504 上界。[PyTorch 2.14 gradient scaling](https://docs.pytorch.org/docs/2.14/amp.html)

## 8.8 Activation checkpointing：用重计算换激活

### 8.8.1 普通 forward/backward

普通训练会保存许多中间激活：

~~~text
forward:
  save intermediate activations
backward:
  read saved activations and compute gradients
~~~

checkpointing 只保留边界：

~~~text
forward:
  save segment boundaries
  discard selected intermediates

backward:
  recompute segment forward
  use recomputed activations for gradients
~~~

“checkpoint”在这里指 activation checkpointing，也叫重计算；它与保存训练进度、模型和 optimizer state 的训练 checkpoint 是两种不同操作。前者决定 backward 时保留哪些中间张量，后者决定进程中断后恢复哪些状态。

### 8.8.2 理想模型与真实峰值

把 L 层链式网络切成 K 个等长 segment，每层某一组要重算的中间激活大小记为 A。一次 backward 处理一个 segment 时，显存要保留约 K 个 segment 边界，并暂时重建一个 segment 内约 L/K 层的中间量，因此一个简化模型是：

~~~math
M_{\mathrm{act,segment}}
\approx
\left(K+\frac{L}{K}\right)A
~~~

例如 L=32：K=4 时约 $12A$，K=8 时约 $12A$，K=16 时约 $18A$；不分段则约 $32A$。连续近似的最小点在 $K\approx\sqrt L$。这就是“深网络 activation memory 可以从线性层数降到约平方根层数”的来源之一；Chen 等人的工作给出 $O(\sqrt L)$ feature-map memory 和一次额外 forward 量级的计算代价。它是线性链教学模型，不包含 Transformer 每种张量的不同 shape 和生命周期。[Training Deep Nets with Sublinear Memory Cost](https://arxiv.org/abs/1604.06174)

实际值仍不能从这个式子直接推出，因为：

- segment 边界仍要保存；
- embedding、输出 head 和 attention 形状不同；
- backward 重算时会出现临时峰值；
- kernel workspace 和通信可能与重算重叠；
- pipeline 或 FSDP 的参数获取可能同时发生。

所以不应把 checkpointing 写成“激活显存精确变成 $1/K$”。它改变的是哪些张量跨层保留、哪些在 backward 重新计算；实际峰值要用同一输入和 batch 对照测量。

### 8.8.3 重计算代价

checkpointing 增加 forward 计算。可以定义：

~~~math
R_{\mathrm{recompute}}
=
\frac{T_{\mathrm{with\ checkpoint}}}
{T_{\mathrm{baseline}}}
>
1
~~~

如果显存节省没有换来更大的有效 batch、上下文或可运行性，吞吐下降可能不值得。应报告：

~~~text
peak memory reduction
tokens/sec change
step time change
recompute FLOPs
maximum context or batch enabled
~~~

重算策略也不只有“全层重算”这一档。Korthikanti 等人把显存大的 attention 中间操作（$QK^T$、softmax、dropout、attention×V）作为 selective recomputation 的对象，因为它们占激活多、每个输入元素的 FLOPs 相对少；再结合 sequence parallel，避免为省内存而重复整层的线性矩阵乘法。[论文 §5–6](https://arxiv.org/abs/2205.05198)

该论文提供了可比较的证据，而不是一个通用倍率：在 22B 模型的一层 forward+backward 测量中，无重算为 19.6 ms，全层重算为 27.2 ms（+39%），selective recompute 为 20.9 ms（+7%），selective recompute+sequence parallel 为 20.3 ms（+4%）。论文对 22B、175B、530B、1T 配置报告 sequence parallel 与 selective recomputation 合用可把 activation memory 降到 TP baseline 的约 20% 以下；530B、2,240 张 A100 的配置中，端到端吞吐相对 full recompute/no sequence parallel 提高约 29.7%。这些数字绑定论文的 Megatron 实现、模型配置和 A100 集群，不是单卡 checkpoint 的独立效果。

论文同一组 GPT-3 / MT-NLG 分析还报告 selective recompute 单项分别减少约 70% / 65% 激活，并增加约 2.7% / 1.6% FLOPs；与 sequence parallel 的组合收益不能算成两项比例简单相乘。它解释了为何“存什么”和“重算什么”要按每个张量的大小与计算代价选择，而不能统一把每 N 层包一个 checkpoint。

### 8.8.4 与 selective checkpointing

不一定需要对所有层使用同样的 checkpoint。可以选择激活最重的 attention、MLP 或长序列 block，保留计算便宜但重算收益低的部分。选择依据应来自 profiler，而不是“层数平均分段”。

在 PyTorch 2.14 中，`torch.utils.checkpoint.checkpoint(..., use_reentrant=False)` 是文档推荐的实现；参数应显式给出。带 dropout 的重算默认保存并恢复 RNG 状态，以便重算随机 mask；这会有额外开销。若函数依赖会变化的全局状态、重新计算时走了不同分支，或把张量移动到 checkpoint 输入中未出现的新设备，前向和重算可能不等价。`use_reentrant=False` 也支持更完整的 autograd 用法和 early-stop recompute。[PyTorch 2.14 checkpoint 文档](https://docs.pytorch.org/docs/2.14/checkpoint.html)

## 8.9 Gradient accumulation：降低 micro-batch，不降低单次激活

### 8.9.1 它改变什么

如果单卡放不下目标 batch，可以用较小 micro-batch 连续进行多次 backward，最后一次 optimizer update：

~~~math
B_{\mathrm{sample}}
=
B_{\mathrm{micro}}
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

等长 token 口径：

~~~math
B_{\mathrm{token}}
=
B_{\mathrm{micro}}
\cdot
T
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

它降低单次 forward/backward 的激活峰值，却不降低单个 micro-batch 的峰值。A 增大后，wall-clock 到一次参数更新的时间也会增加。

### 8.9.2 归一化

等有效 token 的 micro-batch 可以把每次 loss 除以 A。变长情况下，更严格的窗口损失是：

~~~math
L_{\mathrm{window}}
=
\frac{\sum_a s_a}{\sum_a n_a}
~~~

其中 s_a 是第 a 个 micro-batch 的未归一化 loss，n_a 是有效 label token 数。直接平均 s_a/n_a 会让不同长度窗口权重相同，可能与 full batch token-level 目标不一致。

这里 n_a 是非负整数，sum_a n_a 必须大于 0。窗口里可以有局部空监督 micro-batch，但整个窗口没有任何有效 label 时，L_window 未定义，应跳过或上报数据契约错误，而不是产生一条 loss=0 的训练记录。

例如两个 micro-batch 的 token-mean loss 分别为 0.60（2 个有效 target）和 0.90（6 个有效 target）。简单平均得到 $(0.60+0.90)/2=0.75$；按 token 目标求和再除总 token 数则是 $(2\times0.60+6\times0.90)/8=0.825$。前一种算法让短 batch 的每个 token 获得更大的权重。

若要把该目标扩展到 R 个 DDP rank，先定义每个 rank 的未归一化 loss sum $s_r$ 和有效 target 数 $n_r$，全局目标为 $\sum_r s_r/N$，其中 $N=\sum_r n_r$。DDP 默认还会对 rank 梯度取平均，因此可以让每个 rank backward $s_r\times R/N$，再做 DDP 的 rank 平均，得到全局 token mean 的梯度。梯度累积要把所有 micro-batch 的 numerator 和 denominator 都纳入同一个窗口；不同 rank 不能各自先除本地 token 数，再让 DDP 等权平均。第五册第七章的 DDP 变长 token 推导和本章的 accumulation 公式是一套分母问题，应一起看。

### 8.9.3 no_sync 与通信

在 DDP 中，前 A-1 个 micro-step 可以暂缓梯度 all-reduce，最后一个 micro-step 再同步，以减少通信次数。这不等于可以跳过最后同步；同时需要确认：

- 梯度是否已按正确分母缩放；
- 异常退出是否清理未同步梯度；
- 日志中的 micro-step 和 optimizer step 没有混淆；
- 最后一个不完整窗口如何处理。

实际调用 `no_sync()` 时，PyTorch 要把该 context 同时包住本 micro-step 的 forward 和 backward；只包 backward 不能表达同样的同步开关范围。每个 rank 必须以一致顺序进入同步 step，且最后一个 micro-step 确实执行 collective。

使用 FP16 GradScaler 时，PyTorch 2.14 的规则是整个 accumulation window 都保持 scaled gradients 且 scale 不变；累计完成后才 unscale、检查 Inf/NaN、裁剪、step 和 update。每个 micro-step 都更新 scaler 会把不同尺度的梯度加在一起，无法再用一次 unscale 还原。若 epoch 结束只剩不完整窗口，按窗口实际 token 数重算分母，并明确是否执行该次 update。[PyTorch 2.14 AMP accumulation 示例](https://docs.pytorch.org/docs/2.14/notes/amp_examples.html)

## 8.10 Optimizer state sharding、offload 和低比特状态

### 8.10.1 Sharding 改变单卡份额

ZeRO/FSDP 可以把 optimizer state、gradient 和 parameter 分片。若 DP size 为 N_dp，一个理想化状态份额是：

~~~math
M_{\mathrm{shard}}
\approx
\frac{M_{\mathrm{state}}}{N_{\mathrm{dp}}}
~~~

真实峰值还要考虑 all-gather、reduce-scatter、通信 buffer 和模块 wrap。

### 8.10.2 Offload 改变存储位置

CPU/NVMe offload 可能降低 GPU 峰值，却增加：

- PCIe 或网络传输；
- CPU/NVMe 内存压力；
- optimizer step 等待；
- 异步预取和一致性复杂度。

报告时应分别给 GPU peak、CPU usage、NVMe bandwidth 和 step time。把状态搬出 GPU 不等于状态消失。

### 8.10.3 8-bit optimizer state

全参数 AdamW 的 m 和 v 若都是 FP32，占 $8P$ bytes。若一个 8-bit optimizer 把这两组状态各以 1 byte/参数保存，理想 payload 变成 $2P$ bytes，节省 $6P$ bytes；对 7B 参数约从 52.15 GiB 降到 13.04 GiB，节省约 39.11 GiB 的**optimizer state**。scale 元数据、异常处理、参数/梯度、激活和 workspace 不在这个差值里。

这类方法不是把 Adam 的计算都变成 INT8。Dettmers 等人的方法每 2,048 个元素分块，以该 block 的绝对最大值归一化，使用 dynamic-tree quantization 保存状态；更新时在寄存器中反量化为 FP32 做 Adam update，再量化回 8-bit。block 级 scale 把离群值的影响限制在一个小块内；论文还指出 embedding 的梯度分布特别不均匀，因此其实验用了 stable embedding 及该层更高精度状态。该方法的收益是 optimizer-state 容量，代价是量化误差和特定模型/embedding 的稳定性处理；它不等价于 QLoRA 的 4-bit frozen-weight storage。[8-bit Optimizers via Block-wise Quantization](https://arxiv.org/abs/2110.02861)

论文的消融也说明，不能只挑“8-bit”这个标签推断稳定：209M 参数语言模型中，dynamic + blockwise quantization + stable embedding 的 8-bit Adam 报告 0% unstable runs、median perplexity 16.4；使用 stable embedding 的 32-bit Adam 报告 0%、16.3。这个差异绑定 RoBERTa-corpus 实验、作者定义的 instability 和超参，不是通用质量保证。该研究明确把 blockwise、dynamic quantization 和 embedding 处理作为方案的一部分。

为了看出“局部 scale”做了什么，可以用一个更简单的对称均匀量化教学例子，而不要把它误认成论文的 dynamic-tree 算法。将 $[-0.1,0.1,0.2,5.0]$ 整体用 int8 的 $[-127,127]$ 编码，scale 为 $5/127\approx0.03937$，$0.1$ 只能映射到约 3 格；若分成 $[-0.1,0.1]$ 和 $[0.2,5.0]$ 两组，各自用 max-abs scale，第一组使用约 $0.000787$ 的步长，低幅值状态拥有更多编码分辨率。块越小越能隔离 outlier，但需要更多 scale 元数据，且不会自动保证训练轨迹与 FP32 相同。

一个通用量化抽象是：

~~~math
q
=
\operatorname{round}(x/s),
\qquad
\hat{x}=sq
~~~

但生产实现还需要分块 scale、异常值处理、反量化位置和状态更新规则。低比特状态的误差会进入后续动量和自适应分母，因此应比较长期 loss、参数范数、overflow/saturation 和恢复行为。

同样要求 s>0 且状态 x 有限。若某个 block 的 scale 未初始化、为零或已经溢出，量化状态不能被当作普通 m/v 继续更新；应记录 block、step 和恢复策略。

## 8.11 LoRA 与 QLoRA：微调时缩小可训练状态

### 8.11.1 LoRA 的参数量

对一个全量矩阵 W，LoRA 令增量为：

~~~math
\Delta W
=
BA
~~~

其中：

~~~math
A\in\mathbb{R}^{r\times d_{\mathrm{in}}},
\qquad
B\in\mathbb{R}^{d_{\mathrm{out}}\times r}
~~~

新增参数量为：

~~~math
P_{\mathrm{LoRA}}
=
r(d_{\mathrm{in}}+d_{\mathrm{out}})
~~~

当 r 远小于两个维度时，LoRA 梯度和 optimizer state 大幅小于全量矩阵。

这里 d_in、d_out、r 都是正整数，且 r 通常不大于 min(d_in,d_out) 才符合低秩适配的设计意图。若底座权重与 LoRA 矩阵的 dtype 或矩阵方向不匹配，Delta W 虽有“低秩”形状也无法安全合并到 W。

把常见的矩阵尺寸代入：$d_{in}=4096$、$d_{out}=11008$、$r=16$ 时，原线性层有 $4096\times11008=45,088,768$ 个权重，LoRA 增加 $16\times(4096+11008)=241,664$ 个参数，约为原矩阵的 0.536%。若只按 BF16 adapter + BF16 梯度 + FP32 Adam m/v + FP32 master copy 的 16 bytes/参数计，adapter 的这部分训练状态约 3.69 MiB；该数字不含其前向激活、底座权重和 kernel 临时量。

### 8.11.2 LoRA 没有消除激活

冻结底座后，底座参数不需要全量梯度和 optimizer state，但 forward/backward 仍需经过底座计算。对长上下文、大 micro-batch 和视觉/语音输入，激活仍可能是主要瓶颈。

因此 LoRA 解决的是“可训练状态”问题，不是所有训练显存问题。

### 8.11.3 QLoRA 的量化底座

QLoRA 把冻结底座以 NF4 低比特格式存储，在计算需要时反量化到计算 dtype；梯度仍穿过冻结底座，以便求出 LoRA adapter 的梯度，但不为冻结权重保存 optimizer state 或更新其权重。一个粗略账本是：

~~~math
M_{\mathrm{QLoRA}}
\approx
P b_q
+
P_{\mathrm{LoRA}}
(b_w+b_g+b_o)
+
M_{\mathrm{act}}
+
M_{\mathrm{workspace}}
~~~

其中 b_q 是量化底座的平均存储字节数。这个式子没有展开 scale、双重量化元数据、分页 optimizer 和反量化 workspace。

QLoRA 的方法组合各自解决不同问题：

| 组件 | 做法 | 它针对的瓶颈 | 主要边界 |
| --- | --- | --- | --- |
| LoRA adapter | 冻结 $W$，训练低秩 $A,B$ | 全参数梯度和 optimizer state | 激活仍会沿冻结底座反传 |
| NF4 | 按近似零中心正态权重分布设计 4-bit quantile bins | 冻结底座权重存储 | 分布假设和量化误差影响结果 |
| Double Quantization | 再量化第一层 block 的 scale 常量 | 4-bit block scale 的元数据开销 | 只省 scale 开销，不省激活 |
| Paged optimizer | 内存压力时通过 CUDA Unified Memory 管理 optimizer page | 长序列 batch 带来的瞬时显存尖峰 | page migration 可能引入传输/等待，论文未给罕见分页事件的完整性能分布 |

NF4 并不是把 FP32 数值均匀切成 16 个区间。它先利用目标权重近似零中心正态的假设，用分位点构造有相近期望样本数的量化桶，再把权重映射为 4-bit code。对每个 64 个权重的 block，论文的一级 scale 若用 FP32，单是 scale 就平均多占 $32/64=0.5$ bits/parameter。Double Quantization 再对这些 scale 常量量化；论文用 8-bit scale code、每 256 个常量再放一个 FP32 二级常量，元数据变成 $8/64+32/(64\times256)\approx0.127$ bits/parameter，平均节省约 0.373 bits/parameter，65B 模型约省 3 GB。[QLoRA §3](https://arxiv.org/abs/2305.14314)

这让“4 bit”不等于精确 $0.5$ bytes/parameter。以 7B 参数作理论账本，权重 payload 是 $3.5\times10^9$ bytes = 3.26 GiB；按论文 Double Quantization 的二级元数据约再加 0.10 GiB，仍未包含其它对象。论文实际报告 7B LLaMA 的 4-bit base model 为 5,048 MB，已经说明真实存储会比纯 payload 更大，且报告单位和具体实现都应保留。QLoRA 对 65B 模型的单张 48GB GPU 结果是作者方案和评测条件下的可行性证明，不代表所有 65B 微调任务都能用 48GB 完成。

QLoRA 论文还给出一个重要反例，说明 adapter 参数量并非一定是微调峰值的主因：LLaMA-7B 在 FLAN v2、batch size 1 的设置中，adapter 权重约 26 MB、LoRA 的 input-gradient 约 567 MB，而 4-bit 底座约 5,048 MB；配 activation checkpointing 后 input-gradient 平均降到每序列 18 MB。也就是说，rank 再缩小一点只减少很小的一项，长序列激活或底座存储才可能是更大的预算项。[QLoRA §3.1](https://arxiv.org/abs/2305.14314)

计算路径可概括为：输入和 adapter 计算使用 BF16；NF4 底座按 block scale 反量化为 BF16 参与前向；反向计算需要穿过底座来求输入/adapter 梯度，但冻结底座本身不产生参数更新梯度；optimizer 只保存 adapter 状态。这里的“4-bit weights”说的是存储 dtype，不是整个 GEMM 都在 NF4 上计算。

QLoRA 的边界：

- 低比特底座仍影响前向数值；
- 反量化和 kernel 仍有计算成本；
- 激活没有自动消失；
- 不适用于从零训练冻结不存在的底座；
- NF4 的量化质量受 block size、scale 表示、权重分布与计算 dtype 影响；
- 最终任务质量要在目标数据上与 BF16/FP16 LoRA、全量微调对照，不能只凭“QLoRA”名称推断。

## 8.12 OOM：按发生阶段定位

OOM 日志中的“发生阶段”是定位线索，不是根因。比如第一次 `optimizer.step()` 失败，可能是 Adam 懒创建 m/v 的持久状态，也可能是 foreach/fused update 的临时空间；要用 allocator 时间线、参数规模和 step 前后峰值区分。下面按“先看什么、怎样解释”来排查：

| 现象 | 优先检查 | 可区分的解释 |
| --- | --- | --- |
| 模型加载即 OOM | 单卡权重 dtype、重复副本、加载时临时转换 | 常驻权重超预算，或加载同时保留旧/新副本 |
| forward OOM | B、T、激活 dtype、score shape、all-gather、kernel workspace | 激活随 $BTdL$ 增长，score 可能随 $BHT^2$ 增长 |
| backward OOM | 保留的 activation、重算峰值、梯度 bucket、参数 gather | backward 同时活着的张量比 forward 多，或重算又构造一段中间值 |
| 第一次 optimizer step OOM | m/v/master state 是否首次分配、optimizer 实现、foreach/fused 模式 | 首次状态落地造成长期增长，或 update 临时 buffer 短暂峰值 |
| 后续 optimizer step OOM | 每步状态增长、梯度未清空、保留计算图、optimizer 临时量 | 如果 allocated 随 step 单调增长，优先找持有 tensor 的引用 |
| evaluation OOM | 是否 `no_grad`、是否缓存 logits/hidden states、样本长度 | 评估输出保留或更长序列，而不是训练状态 |
| checkpoint OOM | full-state gather、dtype 转换、复制/序列化缓冲 | 训练峰值之外的聚合与复制导致瞬时峰值 |

### 8.12.1 forward OOM

常见原因：

- micro-batch 或 sequence length 太大；
- attention score 或中间 tensor 被物化；
- 参数 all-gather 与激活峰值重叠；
- runtime workspace 超出预算。

优先记录 module、dtype、shape、allocated/reserved 和 peak 时刻。

### 8.12.2 backward OOM

反向可能同时持有：

- 尚未释放的激活；
- 参数和梯度；
- 重计算产生的临时张量；
- collective buffer。

可以尝试 checkpointing、减小 micro-batch、改善释放和 overlap，但要测吞吐代价。

### 8.12.3 optimizer step OOM

这通常指向：

- AdamW 的 m/v 或 master weights；
- optimizer state 初始化时的临时复制；
- FSDP/ZeRO 状态 gather；
- 低比特状态转换；
- checkpoint 前的 state 聚合。

优先核对 optimizer state dtype、shard 份额和 transient allocation。

### 8.12.4 evaluation OOM

常见错误：

- 没有 no_grad；
- 把每个 batch 的 logits 放进 Python list；
- 评估序列更长；
- 只在 rank 0 聚合完整输出；
- 忘记释放临时 cache。

验证代码也应该做显存预算，不是训练主循环之外的“免费操作”。

### 8.12.5 一套可复现的 OOM 记录

每次 OOM 保存：

~~~text
step and phase
rank and device
batch shape and valid token count
parameter/gradient/optimizer dtypes
allocated and reserved bytes
memory snapshot
last collective
checkpoint id
software and kernel versions
~~~

没有这些信息，换一张更大 GPU 可能暂时绕过症状，却无法说明真正的预算问题。

若怀疑碎片，snapshot 要看 block/segment 的空闲与分配历史，而不是只看 `reserved - allocated` 这个总差。该差可能是可复用的缓存，也可能由多段碎片组成；是否能满足一个大连续 allocation 要看 allocator 的块布局。PyTorch memory snapshot 只覆盖 PyTorch allocator 管理的设备分配，工具调用、NCCL 或自定义 CUDA malloc 不可见时，要结合 `nvidia-smi`、库自身统计和设备侧日志排查。

## 8.13 NaN、Inf、overflow 和 underflow

### 8.13.1 数值异常的时间点

先找第一次异常，而不是等整个 loss 变成 NaN。记录：

~~~text
first bad step
first bad rank
loss and logits range
raw and unscaled grad norm
learning rate and warmup phase
loss scale
parameter norm
input source and sequence length
~~~

第一次异常之前的 batch 往往比最后一个 NaN checkpoint 更有诊断价值。

对异常做最小分类，避免把不同问题都叫“loss 爆了”：

| 首次非有限值 | 可能机制 | 下一步证据 |
| --- | --- | --- |
| logits/activation | 输入异常、attention logits 极值、指数溢出、激活 dtype 范围 | 首个坏层、输入范围、attention score/softmax 中间值 |
| loss | 无效 label、全 mask、错误 reduction、FP16 前向 overflow | 有效 target 数、loss numerator/denominator、logits 范围 |
| scaled gradient | loss scale 太大、backward overflow | 当前 scale、首个坏参数/rank、GradScaler skip 计数 |
| unscaled gradient | 上游真实梯度异常、scale/unscale 顺序错误、数据或优化超参异常 | raw 与 unscaled norm、学习率、输入 batch、clip 前后 norm |
| optimizer state/parameter | m/v 溢出、低比特状态量化异常、权重更新过大 | 第一次坏的 state tensor、参数 norm、optimizer step 和 checkpoint |

检查顺序应沿计算图向后追：每个 rank 的第一处 `isfinite` 失败，往往比全局 reduce 后的 NaN 更能保留来源。梯度裁剪只能限制有限且已正确 unscale 的梯度；它不能让已变成 Inf/NaN 的更新恢复成有效值。

### 8.13.2 Overflow

overflow 可能来自：

- FP16/BF16/FP8 表示范围；
- attention logits 或 exp；
- 学习率过大；
- loss scaling 过高；
- 异常输入；
- 自定义 kernel 累加。

处理方式包括降低学习率、延长 warmup、调整 scale、使用更高动态范围的 dtype、改进 softmax/归一化和隔离异常 batch。但每个动作都应通过对照实验验证。

### 8.13.3 Underflow

underflow 可能让小梯度变为 0，造成参数长期没有有效更新。FP16 loss scaling 可把反向梯度暂时放大；BF16 的动态范围通常更大，但尾数和累加精度仍可能造成误差。

一个简单的教学判断是比较梯度与 dtype 的可表示范围，但真实硬件还涉及 subnormal、flush-to-zero 和 kernel 累加，不应把 min_normal 当作唯一判定。

例如梯度 $2\times10^{-8}$ 小于 FP16 的最小 normal 约 $6.10\times10^{-5}$，但标准 FP16 仍有更小的 subnormal 编码；某些硬件路径会把 subnormal flush 到 0，所以不能只从“低于 min normal”断言它一定丢失。乘以 4096 后得到 $8.192\times10^{-5}$，高于 FP16 min normal；反向缩放后恢复原梯度尺度。这个示例展示 loss scaling 的可用范围，不说明真实网络中 scale 可任意增大，因为相同 scale 也可能把其它大梯度推过 FP16 最大值。

### 8.13.4 Gradient clipping 的边界

clipping 可以限制异常大梯度：

~~~math
g'
=
g\cdot
\min\left(
1,
\frac{c}{\lVert g\rVert_2+\epsilon}
\right)
~~~

它不能修复：

- 错误的 label shift；
- padding 参与 loss；
- 未来 token 泄漏；
- 错误的 loss scaling；
- 持续过大的学习率；
- 非法输入或 kernel bug。

如果 clipping 几乎每步触发，应把它当作诊断信号，而不是把阈值不断调大。

该式要求 c>=0、epsilon>0，且 g 的元素有限。c=0 会把所有有限梯度清零，只适合测试；在尚未执行过 optimizer step 时，clipping ratio 的分母为零，应报告未定义而不是 0。

## 8.14 显存优化策略的对应关系

| 首要瓶颈 | 先看的证据 | 可能有效的手段 | 仍要复测的代价/边界 |
| --- | --- | --- | --- |
| 参数/optimizer state 常驻超预算 | 参数数、dtype、optimizer 首次状态分配 | ZeRO/FSDP、CPU offload、低比特 optimizer state、LoRA | gather 峰值、通信、host memory、状态量化误差 |
| micro-batch activation 高 | forward/backward peak、T、micro-batch | 降 micro-batch、activation checkpointing、sequence/context parallel | 重算 FLOPs、通信和更慢的 update 周期 |
| attention 中间量高 | $BHT^2$ shape、是否物化 score/probability | FlashAttention、经质量评估的稀疏/局部 attention | full attention 计算量仍平方；稀疏改变可见关系 |
| optimizer 第一次 step 才超限 | step 前后 allocated/reserved 增量 | 分片/低比特状态、逐参数组加载 | 需区分持久 m/v 和一次性 workspace |
| allocator reserved 大但 allocated 小 | snapshot 的 block/segment 时间线 | 处理活引用、测 allocator 配置、让空闲块可复用 | `empty_cache()` 不释放活张量，碎片不由总差值判断 |
| forward/backward 首次 NaN/Inf | 首个非有限 tensor、dtype、scale、输入范围 | 对应的精度/scale/输入/算子修复 | 降精度可能降低数值余量；clip 不修复非有限值 |

选方案前先判断 OOM 的阶段和账本项。以同一基线逐项测量策略的峰值、吞吐、质量和恢复结果，才能把收益归因到对应机制并发现回归。

## 8.15 一个显存与数值预算审计示例

下面的 Python 示例只用标准库，使用 7B 参数、BF16 权重/梯度、FP32 AdamW 状态、4096 序列长度和 80 GiB GPU 作为教学构造。为了能在一个账本里比较策略，它明确假定展示的 proxy 项在同一时刻同时存活；现实峰值必须依生命周期取 max，allocator 和未纳入的外部分配也会改变结果。它比较：

- 全参数状态；
- ZeRO-3 的理想状态份额；
- activation checkpointing；
- FlashAttention 工作区与显式 score 矩阵；
- FP16/BF16 的动态范围直觉；
- loss scaling；
- LoRA 可训练状态。

代码中的 hidden-sized activation factor、模块 all-gather、workspace 和 80 GiB 设备都是假设，不是任何具体 GPU 或框架的显存预测或性能保证。`checkpointed_activation` 按本章的 $(K+L/K)/L$ 教学关系计算，并未模拟真实 autograd 保存集。

> **代码状态：已验证（2026-10-26，Python 标准库；解释器小版本未记录）。** 输出与正文账本一致；真实 GPU、kernel 和分布式峰值未验证。

~~~python
import math


GIB = 1024 ** 3


def finite_number(name, value, *, positive=False, nonnegative=False):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError(f"{name} must be a finite number")
    value = float(value)
    if not math.isfinite(value):
        raise ValueError(f"{name} must be finite")
    if positive and value <= 0.0:
        raise ValueError(f"{name} must be positive")
    if nonnegative and value < 0.0:
        raise ValueError(f"{name} must be nonnegative")
    return value


def positive_int(name, value):
    if isinstance(value, bool) or not isinstance(value, int) or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def required(config, name, *, integer=False, positive=False,
             nonnegative=False):
    if name not in config:
        raise ValueError(f"missing config field: {name}")
    if integer:
        if positive:
            return positive_int(name, config[name])
        raise ValueError("integer fields in this toy must be positive")
    return finite_number(
        name,
        config[name],
        positive=positive,
        nonnegative=nonnegative,
    )


def gib(byte_count):
    byte_count = finite_number("byte_count", byte_count, nonnegative=True)
    return byte_count / GIB


config = {
    "params": 7_000_000_000,
    "weight_bytes": 2,
    "grad_bytes": 2,
    "activation_bytes": 2,
    "adam_state_bytes": 8,
    "master_weight_bytes": 4,
    "micro_batch": 1,
    "sequence_length": 4096,
    "hidden_size": 4096,
    "layers": 32,
    "activation_factor": 6,  # hidden-sized saved tensors/layer; score is separate
    "attention_heads": 32,
    "gpu_gib": 80.0,
    "dp": 8,
    "checkpoint_segments": 4,
    "buffer_gib": 4.0,
    "transient_gather_gib": 8.0,
    "flash_workspace_gib": 0.25,
    "lora_rank": 16,
    "lora_in": 4096,
    "lora_out": 11008,
}


def state_memory(config):
    params = required(config, "params", integer=True, positive=True)
    weight_bytes = required(config, "weight_bytes", positive=True)
    grad_bytes = required(config, "grad_bytes", positive=True)
    adam_state_bytes = required(config, "adam_state_bytes", nonnegative=True)
    master_weight_bytes = required(
        config, "master_weight_bytes", nonnegative=True
    )
    values = {
        "weights": params * weight_bytes,
        "gradients": params * grad_bytes,
        "adam_states": params * adam_state_bytes,
        "master_weights": params * master_weight_bytes,
    }
    values["total"] = sum(values.values())
    return {name: gib(value) for name, value in values.items()}


def activation_memory(config):
    micro_batch = required(config, "micro_batch", integer=True, positive=True)
    sequence_length = required(
        config, "sequence_length", integer=True, positive=True
    )
    hidden_size = required(config, "hidden_size", integer=True, positive=True)
    layers = required(config, "layers", integer=True, positive=True)
    activation_bytes = required(config, "activation_bytes", positive=True)
    activation_factor = required(config, "activation_factor", positive=True)
    values = (
        micro_batch
        * sequence_length
        * hidden_size
        * layers
        * activation_bytes
        * activation_factor
    )
    return gib(values)


def attention_score_memory(config):
    micro_batch = required(config, "micro_batch", integer=True, positive=True)
    attention_heads = required(
        config, "attention_heads", integer=True, positive=True
    )
    sequence_length = required(
        config, "sequence_length", integer=True, positive=True
    )
    activation_bytes = required(config, "activation_bytes", positive=True)
    values = (
        micro_batch
        * attention_heads
        * sequence_length
        * sequence_length
        * activation_bytes
    )
    return gib(values)


state = state_memory(config)
activation = activation_memory(config)
attention_scores = attention_score_memory(config)
gpu_gib = required(config, "gpu_gib", positive=True)
buffer_gib = required(config, "buffer_gib", nonnegative=True)
transient_gather_gib = required(
    config, "transient_gather_gib", nonnegative=True
)
dp = required(config, "dp", integer=True, positive=True)
checkpoint_segments = required(
~~~

## 8.16 OOM 和数值异常的实验流程

### 8.16.1 OOM 流程

1. 固定数据和随机种子，记录第一次 OOM 的 step 与 phase。
2. 保存 batch shape、有效 token、dtype、rank 和最后一个 collective。
3. 读取 memory snapshot，找到峰值 tensor 或 workspace。
4. 判断属于状态、激活、attention、通信还是 evaluation。
5. 只改一个策略，例如 micro-batch、checkpointing、sharding 或 kernel。
6. 比较峰值、tokens/sec、质量和恢复行为。

### 8.16.2 NaN/Inf 流程

1. 找到第一次非有限 loss、logit、activation 或 gradient。
2. 关联输入数据、序列长度、mask 和 token count。
3. 检查学习率、warmup、grad norm、clip ratio 和 loss scale。
4. 分开检查 FP16/BF16/FP8 路径和 optimizer state。
5. 从最近健康 checkpoint 重放异常 batch。
6. 记录修复后的长期曲线，而不是只看下一步 loss 恢复。

### 8.16.3 结果应该怎样报告

一次有意义的资源实验至少报告：

~~~text
model and parameter count
hardware and world size
parallel strategy
parameter/gradient/optimizer dtypes
micro-batch and valid tokens
sequence length
peak allocated/reserved memory
OOM phase if failed
tokens/sec and step time
validation quality
first non-finite step if failed
checkpoint restore result
~~~

### 练习三：FlashAttention 账本

### 练习四：FP16 loss scaling

## 8.19 本章小结

训练显存由参数、梯度、optimizer state、激活、attention 中间结果、通信 buffer、kernel workspace 和 allocator 峰值共同决定。7B 权重的字节数只是起点，不能代表全参数训练的可运行性。

Activation checkpointing 的内存—计算权衡取决于切段与重算对象；gradient accumulation 降低单次 micro-batch 但必须按全局有效 target 数加权；ZeRO/FSDP 降低单卡训练状态份额却可能产生 transient gather 峰值。FlashAttention 用在线 softmax和分块计算避免物化 full attention 的 $T^2$ 中间矩阵，减少 HBM 读写，但仍对可见 query-key 对做精确计算。LoRA/QLoRA 缩小微调时的可训练状态或底座存储，仍保留底座 forward、必要的输入梯度和激活成本。

FP16、BF16 和 FP8 的差别不只在字节数，还在动态范围、尾数、scale 粒度、累积精度和硬件路径。FP16 GradScaler 要在整次 effective batch 中维持同一 scale，并在 unscale 后通过 `scaler.step` 决定是否跳过更新；loss、gradient、optimizer state 中第一次非有限值和第一次 optimizer-state 分配都是数值/显存证据链的一部分。

真正可靠的显存结论必须绑定发生阶段、dtype、micro-batch、有效 token、并行方式、kernel、峰值 allocated/reserved、吞吐、质量和恢复结果。下一章进入训练稳定性与 debug，把这些资源和数值信号放进更系统的故障定位流程。
