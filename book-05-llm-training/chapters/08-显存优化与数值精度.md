# 第八章：显存优化与数值精度：预算、峰值与数值轨迹

## 8.0 先问显存峰值发生在哪里

“一个 7B 模型需要多少显存？”没有一个脱离训练阶段、精度、并行方式和 batch 的单一答案。推理、全参数训练、参数高效微调和量化加载占用的是不同的对象；即使是同一种训练，forward、backward、optimizer step、evaluation 和 checkpoint 也可能在不同时间产生不同峰值。

一次训练 step 的资源可以先画成：

~~~text
parameters + gradients + optimizer states
  + activations saved for backward
  + attention/intermediate tensors
  + communication and kernel workspaces
  + allocator reserve and fragmentation
~~~

初学者可以把显存优化理解成“让同一张 GPU 能承载更多有效训练工作”。专家必须继续区分：

1. 是总字节数减少，还是只是被 shard 到别的 GPU？
2. 是稳态显存下降，还是 transient all-gather 峰值仍然存在？
3. 是激活减少，还是只减少了 optimizer state？
4. 是存储精度降低，还是计算和累积精度也降低？
5. 是 FP16/BF16/FP8 的格式变化，还是量化底座的权重编码？
6. 是真实吞吐提高，还是因为把计算搬到 CPU/NVMe 而 GPU 峰值下降？

本章先建立显存账本，再分别讨论激活、attention 中间结果、混合精度、loss scaling、FP8、activation checkpointing、gradient accumulation、ZeRO/FSDP、LoRA/QLoRA、FlashAttention、OOM 和 NaN/Inf。每种方法都说明它改变了哪一项，以及没有改变什么。

## 8.1 训练显存的五类账本

### 8.1.1 参数

如果模型有 P 个参数，每个参数占 b_w 字节，权重存储量是：

~~~math
M_{\mathrm{weight}}
=
P b_w
~~~

7B 参数使用 BF16 权重时，理论权重大小约为：

~~~math
7\times10^9\times2
\approx
14\times10^9\ \text{bytes}
~~~

换算成 GiB 约为 13.04。这个数字只描述一份权重，不包含模型副本、梯度、optimizer state、激活、通信 buffer 或 runtime reserve。

这里 P 是正整数，b_w 是非负的每元素字节数；若只是在比较多个 dtype，必须先统一 GB（10 的幂）或 GiB（2 的幂）的单位。把 14e9 bytes 当成 14 GiB，会在容量规划中凭空少算约 7%。

### 8.1.2 梯度

全参数训练通常需要为可训练参数保存梯度。若梯度元素平均占 b_g 字节：

~~~math
M_{\mathrm{grad}}
=
P_{\mathrm{train}}b_g
~~~

P_train 等于全参数训练时的 P，但在 LoRA 等参数高效微调中只等于可训练增量参数的数量。冻结底座不代表 forward 不经过它，只代表底座参数通常不需要保存梯度。

### 8.1.3 Optimizer state

AdamW 通常保存一阶矩 m 和二阶矩 v。若二者都是 FP32：

~~~math
M_{\mathrm{Adam\ state}}
\approx
P_{\mathrm{train}}\times(4+4)
=
8P_{\mathrm{train}}
~~~

某些训练还需要 FP32 master weights：

~~~math
M_{\mathrm{master}}
=
P_{\mathrm{train}}b_{\mathrm{master}}
~~~

因此一个简化的持久训练状态是：

~~~math
M_{\mathrm{state}}
\approx
P b_w
+
P_{\mathrm{train}}b_g
+
M_{\mathrm{optimizer}}
+
M_{\mathrm{master}}
~~~

### 8.1.4 激活和 attention 中间结果

forward 为 backward 留下的激活通常依赖：

~~~math
M_{\mathrm{act}}
\propto
B_{\mathrm{micro}}
\cdot
T
\cdot
d
\cdot
N_L
\cdot
b_{\mathrm{act}}
~~~

其中 B_micro 是 micro-batch，T 是序列长度，d 是 hidden size，N_L 是层数。实际实现会因为保存哪些张量、融合哪些 kernel 和是否使用 checkpoint 而有不同常数。

### 8.1.5 临时空间、通信和 allocator

还要保留：

- GEMM、softmax、归一化和量化 kernel 的 workspace；
- FSDP/ZeRO 参数 all-gather 和梯度 reduce-scatter buffer；
- DDP gradient bucket；
- activation recompute 的临时张量；
- CUDA caching allocator 已保留但当前未使用的块；
- 内存碎片和对齐浪费。

因此实际峰值应写成：

~~~math
M_{\mathrm{peak}}
=
M_{\mathrm{live}}
+
M_{\mathrm{workspace}}
+
M_{\mathrm{comm}}
+
M_{\mathrm{fragmentation}}
~~~

这是一个测量对象，不是只用参数量推出来的常数。

各项都应在同一 device、同一 rank、同一时间窗口和同一单位下统计；对单次峰值而言，M_workspace、M_comm 和 fragmentation 可以为 0 或正数，但不能用平均值替代峰值，也不能把尚未分配的预估 buffer 当成已测得内存。

## 8.2 一个 7B 全参数训练的量级账本

假设：

~~~text
weights: BF16, 2 bytes/parameter
gradients: BF16, 2 bytes/parameter
Adam m/v: FP32, 8 bytes/parameter in total
FP32 master weights: 4 bytes/parameter
~~~

忽略激活和临时空间时：

~~~math
M_{\mathrm{state}}
\approx
P(2+2+8+4)
=
16P\ \text{bytes}
~~~

对 P=7B：

~~~math
M_{\mathrm{state}}
\approx
112\times10^9\ \text{bytes}
\approx
104.31\ \text{GiB}
~~~

这解释了为什么 80GB 单卡通常无法直接承载这种全参数训练状态。实际方案可能使用：

- ZeRO/FSDP，把状态 shard 到多个 DP rank；
- activation checkpointing，降低激活峰值；
- BF16/FP16，降低张量存储；
- FlashAttention，避免显式保存完整 attention score；
- 更小 micro-batch 加 gradient accumulation；
- LoRA/QLoRA，在微调时减少可训练状态。

每种手段作用在不同账本上，不能把它们当成互相替换的开关。

## 8.3 稳态显存和瞬时峰值

### 8.3.1 为什么平均值会误导

一个训练进程可能在大多数时间只使用 60GB，却在某一层 all-gather、optimizer step 或 evaluation 时瞬间需要 82GB。GPU OOM 由峰值触发，不由平均占用触发。

应分别记录：

~~~text
allocated bytes
reserved bytes
peak allocated bytes
peak reserved bytes
allocation event
module or kernel
rank
timestamp or step
~~~

allocated 更接近当前仍被 tensor 使用的空间，reserved 还包含 allocator 缓存。两者都高可能是实际 live tensor 多；reserved 明显高于 allocated 则可能存在缓存和碎片问题，但不能简单把所有 reserved 都当成泄漏。

### 8.3.2 FSDP/ZeRO 的 transient all-gather

参数分片降低的是常驻 shard。计算模块前，完整参数可能被临时聚合：

~~~text
parameter shard
  -> all-gather full module parameters
  -> forward/backward
  -> release or reshard
~~~

因此：

~~~math
M_{\mathrm{peak}}
\ge
M_{\mathrm{shard}}
+
M_{\mathrm{full\ module\ gather}}
~~~

wrap 粒度越粗，单次 gather 可能越大；wrap 粒度越细，通信次数和小 buffer 可能更多。报告“ZeRO-3 只占全量状态的 1/N”时，必须说明这是稳态量级，不能把它当作峰值保证。

### 8.3.3 evaluation 和 checkpoint 的额外峰值

evaluation 可能因为没有 no_grad、保留 logits、累积 hidden states 或使用更长样本而产生额外显存。checkpoint 可能暂时聚合参数、转换 dtype、复制 state 或压缩 tensor。

训练和评估使用同一张 GPU 时，必须单独测：

~~~text
train forward peak
train backward peak
optimizer step peak
validation peak
checkpoint peak
~~~

## 8.4 激活显存：batch 和 context 的乘积

### 8.4.1 影响激活的变量

激活显存通常随以下因素增加：

1. micro-batch 增大；
2. sequence length 增大；
3. hidden size 增大；
4. 层数增多；
5. 保存更多中间张量；
6. 使用更高存储精度。

一个教学级关系是：

~~~math
M_{\mathrm{act}}
\propto
B_{\mathrm{micro}} T d N_L b_{\mathrm{act}}
~~~

它用于判断哪个旋钮影响最大，不应被当成所有 Transformer 实现的精确显存公式。

### 8.4.2 为什么长上下文特别昂贵

如果 B_micro、d 和 N_L 不变，把 T 从 4K 增加到 32K，线性激活项可能增加约 8 倍；如果实现显式保存 full attention score，attention 中间项还可能随 T^2 增长。

这使得“只把 context length 调长”经常比“把 batch 加倍”更容易触发 OOM。长上下文训练需要同时考虑：

- packing 和 padding 利用率；
- attention kernel；
- activation checkpointing；
- sequence/context parallel；
- 实际有效 token；
- 训练吞吐和通信。

### 8.4.3 激活不是参数

ZeRO/FSDP 主要切分参数、梯度和 optimizer state，不会自动把每个 micro-batch 的所有激活变小。反过来，activation checkpointing 可以降低激活，却不减少 AdamW 的 m/v。

这一边界很重要：

| OOM 来源 | 首先考虑 |
| --- | --- |
| 参数/optimizer state | ZeRO/FSDP、offload、低比特 state |
| micro-batch 激活 | 减小 micro-batch、checkpointing |
| full attention 中间结果 | FlashAttention、稀疏/局部 attention |
| 单层计算临时 buffer | kernel、dtype、wrap 粒度 |
| evaluation 缓存 | no_grad、分批评估、及时释放 |

## 8.5 Attention 中间结果与 FlashAttention

### 8.5.1 标准 attention 的 score 矩阵

对 batch size B、head 数 H、序列长度 T，显式 attention score 的元素规模是：

~~~math
N_{\mathrm{score}}
=
BHT^2
~~~

如果每个元素占 b 字节：

~~~math
M_{\mathrm{score}}
=
BHT^2b
~~~

例如 B=1、H=32、T=4096、BF16 时，单层单份 score 矩阵约为：

~~~math
1\times32\times4096^2\times2
\approx
1\ \text{GiB}
~~~

真实训练还可能保存 dropout mask、softmax 结果和其他张量，因此不能只用这一项作完整预算。

该式要求 B、H、T 为正整数，b>0，并假设 score 在给定 dtype 中真的被显式物化。带 causal mask、padding mask 或 block-sparse 布局仍可能有不同的实际张量形状；不能只凭模型配置把所有 attention kernel 都按 BHT^2 分配。

### 8.5.2 FlashAttention 改变什么

FlashAttention 的核心是 IO-aware、分块的 attention kernel。它在片上存储中分块计算 Q/K/V 和 softmax，避免把完整 T x T score 矩阵物化并写回高带宽显存。

它主要改变：

- HBM 与片上存储之间的读写；
- 中间 score/softmax 的物化方式；
- attention kernel 的吞吐和峰值工作区。

它不自动改变：

- full attention 的全局可见性；
- 理论上的二次 token 关系；
- MLP、embedding 和其他层的激活；
- checkpoint、optimizer state 和通信 buffer。

因此“FlashAttention 让 attention 更省显存”是准确的，“FlashAttention 把 attention 复杂度变成线性”通常是不准确的。

### 8.5.3 FlashAttention 与 checkpointing 的区别

二者都可能减少 attention 相关峰值，但机制不同：

| 方法 | 主要手段 | 主要代价 |
| --- | --- | --- |
| FlashAttention | 不物化完整中间矩阵，优化 IO | 依赖 kernel/硬件 |
| Activation checkpointing | backward 时重算 forward | 增加计算 |
| Sparse/local attention | 减少可见 token 关系 | 改变模型结构和质量边界 |

一个系统可以同时使用三者，结果不能把各自的理想节省比例直接相乘。

## 8.6 FP32、FP16、BF16 与 FP8 的表示边界

### 8.6.1 字节数不是全部

对 n 个元素，存储空间是：

~~~math
M_{\mathrm{tensor}}
=
n b_{\mathrm{dtype}}
~~~

但数值格式还决定：

- 最大有限值；
- 最小 normal 值；
- subnormal 是否可用；
- 有效尾数位；
- 舍入误差；
- 乘加累积精度。

两个 dtype 都占 2 bytes，不代表训练行为相同。

### 8.6.2 FP32

FP32 具有较大的动态范围和较高尾数精度，常用于 optimizer state、master weights、部分归一化、统计累积或需要稳定累加的路径。全程使用 FP32 会增加显存和带宽，现代大模型训练通常采用混合精度，而不是把所有张量都改成同一种低精度。

### 8.6.3 FP16

FP16 每元素 2 bytes，显存和 Tensor Core 吞吐较好，但动态范围较小。大于最大有限值的结果会 overflow，小于可表示范围的梯度可能 underflow 或被硬件 flush 到零。

FP16 训练常使用 loss scaling：

~~~math
\tilde L
=
sL,
\qquad
\tilde g
=
\nabla_\theta \tilde L
=
s\nabla_\theta L
~~~

更新前还原：

~~~math
g
=
\frac{\tilde g}{s}
~~~

### 8.6.4 BF16

BF16 每元素也是 2 bytes，但指数位接近 FP32，动态范围更大。它通常更能承受大模型训练中的 activation 和梯度尺度变化，因此很多训练 recipe 不需要像 FP16 那样依赖动态 loss scaling。

BF16 的尾数位较少，舍入误差并不会消失。softmax、归一化、累加、optimizer state 和自定义 kernel 仍然需要检查。

### 8.6.5 FP8

FP8 进一步减少每元素字节数和带宽，但它不是简单地把 FP16 截断为 8 bit。通常需要：

- 为 tensor、channel 或 block 维护 scale；
- 统计 amax 或历史最大值；
- 在乘法前后执行缩放或反缩放；
- 选择不同 FP8 格式；
- 在更高精度中进行关键累积；
- 依赖支持相应 Tensor Core 和 kernel 的硬件。

一个简化的 scale-quantize 关系是：

~~~math
q
=
\operatorname{clip}
\left(
\operatorname{round}\frac{x}{s},
q_{\min},
q_{\max}
\right),
\qquad
\hat{x}=sq
~~~

其中 s 是 scale，q 是低精度编码，hat{x} 是计算时恢复的近似值。scale 粒度越细，表示适应性可能越好，但元数据、更新和通信逻辑更复杂。

这条抽象要求 x 有限且 s>0，q_min<=q_max；s=0 不是“零量化误差”，而是无定义的除法。实际 FP8 格式、饱和规则和 amax 延迟更新由实现决定，公式只说明 scale 在数值路径中的位置。

FP8 是否有收益要同时看：

~~~text
hardware tensor core support
format choice
scale granularity
amax history or delayed scaling
accumulation dtype
overflow/saturation statistics
validation quality
~~~

不能把“FP8 占 1 byte”直接等同于训练显存和训练时间都减半。

## 8.7 Mixed precision：不同张量使用不同精度

### 8.7.1 典型精度分工

一个常见的混合精度训练分工是：

~~~text
forward matmul: BF16 or FP16
activation storage: BF16 or FP16
gradient: BF16 or FP16, then unscaled
optimizer m/v: FP32 or low-bit state
master weights: optional FP32
critical reductions: FP32 or higher-precision accumulation
~~~

实际分工由框架、硬件和训练 recipe 决定。混合精度不是“所有低精度张量一起计算”，而是根据数值敏感性选择位置。

### 8.7.2 autocast 不等于所有操作降精度

autocast 通常根据操作类型选择适合的 dtype。有些 matmul 可以用低精度，某些 reduction、softmax 或归一化可能保留更高精度。工程检查应查看真实 kernel 和 tensor dtype，而不能只看配置中一个 mixed_precision=true。

### 8.7.3 梯度裁剪和 unscale 的顺序

FP16 loss scaling 时，正确顺序通常是：

~~~text
scaled_loss = loss * scale
scaled_loss.backward()
unscale_(optimizer)
clip_grad_norm_(parameters, max_norm)
optimizer.step()
scaler.update()
~~~

如果在 unscale 前裁剪，范数包含 scale，阈值就不再是原始梯度的阈值。若发现 clipping 几乎每步触发，先检查顺序和记录的 norm 是否是 scaled norm。

### 8.7.4 scaler 如何处理异常

动态 scaler 通常在检测到 Inf/NaN 时跳过该次参数更新，并调整 scale。训练日志应保留：

~~~text
current scale
scale growth/backoff events
skipped optimizer steps
overflow count
first offending rank
batch and sequence statistics
~~~

跳过一次更新不等于问题已经解决。若 scale 持续下降，可能存在学习率、数据或 kernel 层面的系统性异常。

loss scale 本身应为有限正数；缩放只是在低精度反向路径中扩大可表示的梯度，unscale 后的参数更新仍必须以原始梯度语义进行。全是 ignore label 的 batch、NaN loss 或错误的 reduction 不能靠增大 scale 修复。

## 8.8 Activation checkpointing：用重计算换激活

### 8.8.1 普通 forward/backward

普通训练会保存许多中间激活：

~~~text
forward:
  save intermediate activations
backward:
  read saved activations and compute gradients
~~~

checkpointing 只保留边界：

~~~text
forward:
  save segment boundaries
  discard selected intermediates

backward:
  recompute segment forward
  use recomputed activations for gradients
~~~

### 8.8.2 理想模型与真实峰值

如果把网络分成 K 个近似均匀 segment，教学直觉可能写成：

~~~math
M_{\mathrm{act,ideal}}
\approx
\frac{M_{\mathrm{act}}}{K}
~~~

但真实值不等于这个式子，因为：

- segment 边界仍要保存；
- embedding、输出 head 和 attention 形状不同；
- backward 重算时会出现临时峰值；
- kernel workspace 和通信可能与重算重叠；
- pipeline 或 FSDP 的参数获取可能同时发生。

所以应通过 memory snapshot 和 profiler 测量 peak allocated，而不是直接套 1/K。

### 8.8.3 重计算代价

checkpointing 增加 forward 计算。可以定义：

~~~math
R_{\mathrm{recompute}}
=
\frac{T_{\mathrm{with\ checkpoint}}}
{T_{\mathrm{baseline}}}
>
1
~~~

如果显存节省没有换来更大的有效 batch、上下文或可运行性，吞吐下降可能不值得。应报告：

~~~text
peak memory reduction
tokens/sec change
step time change
recompute FLOPs
maximum context or batch enabled
~~~

### 8.8.4 与 selective checkpointing

不一定需要对所有层使用同样的 checkpoint。可以选择激活最重的 attention、MLP 或长序列 block，保留计算便宜但重算收益低的部分。选择依据应来自 profiler，而不是“层数平均分段”。

## 8.9 Gradient accumulation：降低 micro-batch，不降低单次激活

### 8.9.1 它改变什么

如果单卡放不下目标 batch，可以用较小 micro-batch 连续进行多次 backward，最后一次 optimizer update：

~~~math
B_{\mathrm{sample}}
=
B_{\mathrm{micro}}
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

等长 token 口径：

~~~math
B_{\mathrm{token}}
=
B_{\mathrm{micro}}
\cdot
T
\cdot
A
\cdot
N_{\mathrm{dp}}
~~~

它降低单次 forward/backward 的激活峰值，却不降低单个 micro-batch 的峰值。A 增大后，wall-clock 到一次参数更新的时间也会增加。

### 8.9.2 归一化

等有效 token 的 micro-batch 可以把每次 loss 除以 A。变长情况下，更严格的窗口损失是：

~~~math
L_{\mathrm{window}}
=
\frac{\sum_a s_a}{\sum_a n_a}
~~~

其中 s_a 是第 a 个 micro-batch 的未归一化 loss，n_a 是有效 label token 数。直接平均 s_a/n_a 会让不同长度窗口权重相同，可能与 full batch token-level 目标不一致。

这里 n_a 是非负整数，sum_a n_a 必须大于 0。窗口里可以有局部空监督 micro-batch，但整个窗口没有任何有效 label 时，L_window 未定义，应跳过或上报数据契约错误，而不是产生一条 loss=0 的训练记录。

### 8.9.3 no_sync 与通信

在 DDP 中，前 A-1 个 micro-step 可以暂缓梯度 all-reduce，最后一个 micro-step 再同步，以减少通信次数。这不等于可以跳过最后同步；同时需要确认：

- 梯度是否已按正确分母缩放；
- 异常退出是否清理未同步梯度；
- 日志中的 micro-step 和 optimizer step 没有混淆；
- 最后一个不完整窗口如何处理。

## 8.10 Optimizer state sharding、offload 和低比特状态

### 8.10.1 Sharding 改变单卡份额

ZeRO/FSDP 可以把 optimizer state、gradient 和 parameter 分片。若 DP size 为 N_dp，一个理想化状态份额是：

~~~math
M_{\mathrm{shard}}
\approx
\frac{M_{\mathrm{state}}}{N_{\mathrm{dp}}}
~~~

真实峰值还要考虑 all-gather、reduce-scatter、通信 buffer 和模块 wrap。

### 8.10.2 Offload 改变存储位置

CPU/NVMe offload 可能降低 GPU 峰值，却增加：

- PCIe 或网络传输；
- CPU/NVMe 内存压力；
- optimizer step 等待；
- 异步预取和一致性复杂度。

报告时应分别给 GPU peak、CPU usage、NVMe bandwidth 和 step time。把状态搬出 GPU 不等于状态消失。

### 8.10.3 8-bit optimizer state

低比特 optimizer state 通过量化 m/v 或其他状态减少每元素字节数。一个通用量化抽象是：

~~~math
q
=
\operatorname{round}(x/s),
\qquad
\hat{x}=sq
~~~

但生产实现还需要分块 scale、异常值处理、反量化位置和状态更新规则。低比特状态的误差会进入后续动量和自适应分母，因此应比较长期 loss、参数范数、overflow/saturation 和恢复行为。

同样要求 s>0 且状态 x 有限。若某个 block 的 scale 未初始化、为零或已经溢出，量化状态不能被当作普通 m/v 继续更新；应记录 block、step 和恢复策略。

## 8.11 LoRA 与 QLoRA：微调时缩小可训练状态

### 8.11.1 LoRA 的参数量

对一个全量矩阵 W，LoRA 令增量为：

~~~math
\Delta W
=
BA
~~~

其中：

~~~math
A\in\mathbb{R}^{r\times d_{\mathrm{in}}},
\qquad
B\in\mathbb{R}^{d_{\mathrm{out}}\times r}
~~~

新增参数量为：

~~~math
P_{\mathrm{LoRA}}
=
r(d_{\mathrm{in}}+d_{\mathrm{out}})
~~~

当 r 远小于两个维度时，LoRA 梯度和 optimizer state 大幅小于全量矩阵。

这里 d_in、d_out、r 都是正整数，且 r 通常不大于 min(d_in,d_out) 才符合低秩适配的设计意图。若底座权重与 LoRA 矩阵的 dtype 或矩阵方向不匹配，Delta W 虽有“低秩”形状也无法安全合并到 W。

### 8.11.2 LoRA 没有消除激活

冻结底座后，底座参数不需要全量梯度和 optimizer state，但 forward/backward 仍需经过底座计算。对长上下文、大 micro-batch 和视觉/语音输入，激活仍可能是主要瓶颈。

因此 LoRA 解决的是“可训练状态”问题，不是所有训练显存问题。

### 8.11.3 QLoRA 的量化底座

QLoRA 进一步把冻结底座以低比特形式存储，在计算需要时反量化到计算 dtype，并训练 LoRA 增量。一个粗略画像是：

~~~math
M_{\mathrm{QLoRA}}
\approx
P b_q
+
P_{\mathrm{LoRA}}
(b_w+b_g+b_o)
+
M_{\mathrm{act}}
+
M_{\mathrm{workspace}}
~~~

其中 b_q 是量化底座的平均存储字节数。这个式子没有展开 scale、双重量化元数据、分页 optimizer 和反量化 workspace。

QLoRA 的边界：

- 低比特底座仍影响前向数值；
- 反量化和 kernel 仍有计算成本；
- 激活没有自动消失；
- 不适用于从零训练冻结不存在的底座；
- 最终质量依赖量化格式、校准和 LoRA recipe。

## 8.12 OOM：按发生阶段定位

### 8.12.1 forward OOM

常见原因：

- micro-batch 或 sequence length 太大；
- attention score 或中间 tensor 被物化；
- 参数 all-gather 与激活峰值重叠；
- runtime workspace 超出预算。

优先记录 module、dtype、shape、allocated/reserved 和 peak 时刻。

### 8.12.2 backward OOM

反向可能同时持有：

- 尚未释放的激活；
- 参数和梯度；
- 重计算产生的临时张量；
- collective buffer。

可以尝试 checkpointing、减小 micro-batch、改善释放和 overlap，但要测吞吐代价。

### 8.12.3 optimizer step OOM

这通常指向：

- AdamW 的 m/v 或 master weights；
- optimizer state 初始化时的临时复制；
- FSDP/ZeRO 状态 gather；
- 低比特状态转换；
- checkpoint 前的 state 聚合。

优先核对 optimizer state dtype、shard 份额和 transient allocation。

### 8.12.4 evaluation OOM

常见错误：

- 没有 no_grad；
- 把每个 batch 的 logits 放进 Python list；
- 评估序列更长；
- 只在 rank 0 聚合完整输出；
- 忘记释放临时 cache。

验证代码也应该做显存预算，不是训练主循环之外的“免费操作”。

### 8.12.5 一套可复现的 OOM 记录

每次 OOM 保存：

~~~text
step and phase
rank and device
batch shape and valid token count
parameter/gradient/optimizer dtypes
allocated and reserved bytes
memory snapshot
last collective
checkpoint id
software and kernel versions
~~~

没有这些信息，换一张更大 GPU 可能暂时绕过症状，却无法说明真正的预算问题。

## 8.13 NaN、Inf、overflow 和 underflow

### 8.13.1 数值异常的时间点

先找第一次异常，而不是等整个 loss 变成 NaN。记录：

~~~text
first bad step
first bad rank
loss and logits range
raw and unscaled grad norm
learning rate and warmup phase
loss scale
parameter norm
input source and sequence length
~~~

第一次异常之前的 batch 往往比最后一个 NaN checkpoint 更有诊断价值。

### 8.13.2 Overflow

overflow 可能来自：

- FP16/BF16/FP8 表示范围；
- attention logits 或 exp；
- 学习率过大；
- loss scaling 过高；
- 异常输入；
- 自定义 kernel 累加。

处理方式包括降低学习率、延长 warmup、调整 scale、使用更高动态范围的 dtype、改进 softmax/归一化和隔离异常 batch。但每个动作都应通过对照实验验证。

### 8.13.3 Underflow

underflow 可能让小梯度变为 0，造成参数长期没有有效更新。FP16 loss scaling 可把反向梯度暂时放大；BF16 的动态范围通常更大，但尾数和累加精度仍可能造成误差。

一个简单的教学判断是比较梯度与 dtype 的可表示范围，但真实硬件还涉及 subnormal、flush-to-zero 和 kernel 累加，不应把 min_normal 当作唯一判定。

### 8.13.4 Gradient clipping 的边界

clipping 可以限制异常大梯度：

~~~math
g'
=
g\cdot
\min\left(
1,
\frac{c}{\lVert g\rVert_2+\epsilon}
\right)
~~~

它不能修复：

- 错误的 label shift；
- padding 参与 loss；
- 未来 token 泄漏；
- 错误的 loss scaling；
- 持续过大的学习率；
- 非法输入或 kernel bug。

如果 clipping 几乎每步触发，应把它当作诊断信号，而不是把阈值不断调大。

该式要求 c>=0、epsilon>0，且 g 的元素有限。c=0 会把所有有限梯度清零，只适合测试；在尚未执行过 optimizer step 时，clipping ratio 的分母为零，应报告未定义而不是 0。

## 8.14 显存优化策略的对应关系

| 方法 | 主要减少什么 | 没有自动减少什么 |
| --- | --- | --- |
| BF16/FP16 | 张量字节数和带宽 | 所有数值风险、所有 workspace |
| FP8 | 部分张量字节数和带宽 | scale 元数据、激活结构、量化误差 |
| Activation checkpointing | 常驻激活 | 重计算、参数和 optimizer state |
| Gradient accumulation | 单次 micro-batch 激活 | 一次 update 的总计算 |
| ZeRO/FSDP | 单卡状态份额 | 激活和 transient gather 峰值 |
| Offload | GPU 常驻份额 | 总内存、传输和等待 |
| FlashAttention | attention 中间物化和 IO | full attention 可见性和其他层 |
| LoRA | 可训练参数的梯度/state | 底座 forward 和激活 |
| QLoRA | 冻结底座存储 | 反量化、激活、任务质量风险 |
| 8-bit optimizer | state 每元素字节数 | 量化误差和 optimizer 语义 |

选方案前先判断 OOM 的阶段和账本项。把所有技术一起打开，虽然可能让程序运行，但无法知道收益来自哪里，也不利于恢复和质量回归。

## 8.15 一个显存与数值预算审计示例

下面的 Python 示例只用标准库，使用 7B 参数、BF16 权重、FP32 AdamW 状态、4096 序列长度和 80 GiB GPU 作为教学构造。它比较：

- 全参数状态；
- ZeRO-3 的理想状态份额；
- activation checkpointing；
- FlashAttention 工作区与显式 score 矩阵；
- FP16/BF16 的动态范围直觉；
- loss scaling；
- LoRA 可训练状态。

代码中的激活系数、workspace 和 80 GiB 设备都是假设，不是任何具体 GPU 或框架的性能保证。

~~~python
import math


GIB = 1024 ** 3


def finite_number(name, value, *, positive=False, nonnegative=False):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError(f"{name} must be a finite number")
    value = float(value)
    if not math.isfinite(value):
        raise ValueError(f"{name} must be finite")
    if positive and value <= 0.0:
        raise ValueError(f"{name} must be positive")
    if nonnegative and value < 0.0:
        raise ValueError(f"{name} must be nonnegative")
    return value


def positive_int(name, value):
    if isinstance(value, bool) or not isinstance(value, int) or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def required(config, name, *, integer=False, positive=False,
             nonnegative=False):
    if name not in config:
        raise ValueError(f"missing config field: {name}")
    if integer:
        if positive:
            return positive_int(name, config[name])
        raise ValueError("integer fields in this toy must be positive")
    return finite_number(
        name,
        config[name],
        positive=positive,
        nonnegative=nonnegative,
    )


def gib(byte_count):
    byte_count = finite_number("byte_count", byte_count, nonnegative=True)
    return byte_count / GIB


config = {
    "params": 7_000_000_000,
    "weight_bytes": 2,
    "grad_bytes": 2,
    "adam_state_bytes": 8,
    "master_weight_bytes": 4,
    "micro_batch": 1,
    "sequence_length": 4096,
    "hidden_size": 4096,
    "layers": 32,
    "activation_factor": 6,
    "attention_heads": 32,
    "gpu_gib": 80.0,
    "dp": 8,
    "checkpoint_segments": 4,
    "buffer_gib": 4.0,
    "flash_workspace_gib": 0.25,
    "lora_rank": 16,
    "lora_in": 4096,
    "lora_out": 11008,
}


def state_memory(config):
    params = required(config, "params", integer=True, positive=True)
    weight_bytes = required(config, "weight_bytes", positive=True)
    grad_bytes = required(config, "grad_bytes", positive=True)
    adam_state_bytes = required(config, "adam_state_bytes", nonnegative=True)
    master_weight_bytes = required(
        config, "master_weight_bytes", nonnegative=True
    )
    values = {
        "weights": params * weight_bytes,
        "gradients": params * grad_bytes,
        "adam_states": params * adam_state_bytes,
        "master_weights": params * master_weight_bytes,
    }
    values["total"] = sum(values.values())
    return {name: gib(value) for name, value in values.items()}


def activation_memory(config):
    micro_batch = required(config, "micro_batch", integer=True, positive=True)
    sequence_length = required(
        config, "sequence_length", integer=True, positive=True
    )
    hidden_size = required(config, "hidden_size", integer=True, positive=True)
    layers = required(config, "layers", integer=True, positive=True)
    weight_bytes = required(config, "weight_bytes", positive=True)
    activation_factor = required(config, "activation_factor", positive=True)
    values = (
        micro_batch
        * sequence_length
        * hidden_size
        * layers
        * weight_bytes
        * activation_factor
    )
    return gib(values)


def attention_score_memory(config):
    micro_batch = required(config, "micro_batch", integer=True, positive=True)
    attention_heads = required(
        config, "attention_heads", integer=True, positive=True
    )
    sequence_length = required(
        config, "sequence_length", integer=True, positive=True
    )
    weight_bytes = required(config, "weight_bytes", positive=True)
    values = (
        micro_batch
        * attention_heads
        * sequence_length
        * sequence_length
        * weight_bytes
    )
    return gib(values)


state = state_memory(config)
activation = activation_memory(config)
attention_scores = attention_score_memory(config)
gpu_gib = required(config, "gpu_gib", positive=True)
buffer_gib = required(config, "buffer_gib", nonnegative=True)
dp = required(config, "dp", integer=True, positive=True)
checkpoint_segments = required(
    config, "checkpoint_segments", integer=True, positive=True
)
flash_workspace_gib = required(
    config, "flash_workspace_gib", nonnegative=True
)
full_total = (
    state["total"]
    + activation
    + attention_scores
    + buffer_gib
)
zero3_state = state["total"] / dp
checkpointed_activation = (
    activation / checkpoint_segments
)
optimized_total = (
    zero3_state
    + checkpointed_activation
    + flash_workspace_gib
    + buffer_gib
)

fp16 = {
    "max": 65504.0,
    "min_normal": 2 ** -14,
}
bf16 = {
    "max": 3.389e38,
    "min_normal": 2 ** -126,
}
small_gradient = finite_number("small_gradient", 2e-8, nonnegative=True)
loss_scale = finite_number("loss_scale", 4096, positive=True)
scaled_gradient = small_gradient * loss_scale
loss_scaling = {
    "small_below_fp16_normal": (
        small_gradient < fp16["min_normal"]
    ),
    "scaled_reaches_fp16_normal": (
        scaled_gradient > fp16["min_normal"]
    ),
    "bf16_range_contains_small_gradient": (
        small_gradient > bf16["min_normal"]
    ),
}

lora_rank = required(config, "lora_rank", integer=True, positive=True)
lora_in = required(config, "lora_in", integer=True, positive=True)
lora_out = required(config, "lora_out", integer=True, positive=True)
if lora_rank > min(lora_in, lora_out):
    raise ValueError("lora_rank cannot exceed the matrix dimensions")
lora_trainable = lora_rank * (
    lora_in + lora_out
)
lora_state = lora_trainable * (
    required(config, "weight_bytes", positive=True)
    + required(config, "grad_bytes", positive=True)
    + required(config, "adam_state_bytes", nonnegative=True)
    + required(config, "master_weight_bytes", nonnegative=True)
)
lora_total = (
    state["weights"]
    + gib(lora_state)
    + checkpointed_activation
    + flash_workspace_gib
    + buffer_gib
)

diagnostics = {
    "full_training_exceeds_gpu": (
        full_total > gpu_gib
    ),
    "zero3_checkpoint_flash_fits": (
        optimized_total < gpu_gib
    ),
    "checkpoint_reduces_activation": (
        checkpointed_activation < activation
    ),
    "flash_workspace_below_score_matrix": (
        flash_workspace_gib < attention_scores
    ),
    "bf16_has_larger_range": (
        bf16["max"] > fp16["max"] * 1e20
    ),
    "loss_scaling_reaches_fp16_normal": (
        loss_scaling["small_below_fp16_normal"]
        and loss_scaling["scaled_reaches_fp16_normal"]
    ),
    "lora_state_is_small": gib(lora_state) < 0.01,
}

print("state_gib=", {k: round(v, 2) for k, v in state.items()})
print("activation_gib=", round(activation, 2))
print("attention_score_gib=", round(attention_scores, 2))
print("full_total_gib=", round(full_total, 2))
print("zero3_state_gib=", round(zero3_state, 2))
print(
    "checkpointed_activation_gib=",
    round(checkpointed_activation, 2),
)
print("optimized_total_gib=", round(optimized_total, 2))
print("fp16=", {k: f"{v:.2e}" for k, v in fp16.items()})
print("bf16=", {k: f"{v:.2e}" for k, v in bf16.items()})
print("loss_scaling=", loss_scaling)
print("lora_trainable_params=", lora_trainable)
print("lora_state_gib=", round(gib(lora_state), 6))
print("lora_total_gib=", round(lora_total, 2))
print("diagnostics=", diagnostics)

assert all(diagnostics.values())
print("memory precision toy: ok")
~~~

这个 toy 的重点是把“省显存”拆成账本项。它没有实现真实 FlashAttention、FP8 kernel、量化反量化、FSDP all-gather 或 CUDA allocator，因此不能用它预测生产训练是否 OOM。

## 8.16 OOM 和数值异常的实验流程

### 8.16.1 OOM 流程

1. 固定数据和随机种子，记录第一次 OOM 的 step 与 phase。
2. 保存 batch shape、有效 token、dtype、rank 和最后一个 collective。
3. 读取 memory snapshot，找到峰值 tensor 或 workspace。
4. 判断属于状态、激活、attention、通信还是 evaluation。
5. 只改一个策略，例如 micro-batch、checkpointing、sharding 或 kernel。
6. 比较峰值、tokens/sec、质量和恢复行为。

### 8.16.2 NaN/Inf 流程

1. 找到第一次非有限 loss、logit、activation 或 gradient。
2. 关联输入数据、序列长度、mask 和 token count。
3. 检查学习率、warmup、grad norm、clip ratio 和 loss scale。
4. 分开检查 FP16/BF16/FP8 路径和 optimizer state。
5. 从最近健康 checkpoint 重放异常 batch。
6. 记录修复后的长期曲线，而不是只看下一步 loss 恢复。

### 8.16.3 结果应该怎样报告

一次有意义的资源实验至少报告：

~~~text
model and parameter count
hardware and world size
parallel strategy
parameter/gradient/optimizer dtypes
micro-batch and valid tokens
sequence length
peak allocated/reserved memory
OOM phase if failed
tokens/sec and step time
validation quality
first non-finite step if failed
checkpoint restore result
~~~

## 8.18 章节练习：从显存账本到数值排查

### 练习一：全参数状态

假设模型有 7B 参数，权重和梯度为 BF16，AdamW 的 m/v 为 FP32，另有 FP32 master weights。计算忽略激活时的状态大小，并说明为什么不能把结果直接当成单卡峰值。

### 练习二：峰值定位

设计一个实验区分 forward OOM、backward OOM、optimizer step OOM 和 evaluation OOM。每种情况要记录哪些 tensor、dtype、rank 和 phase 字段？

### 练习三：FlashAttention 账本

对 B=2、H=32、T=8192、BF16，计算显式 score 矩阵的元素量和字节数。再说明 FlashAttention 改变了哪一项，以及为什么它没有把 full attention 变成线性关系。

### 练习四：FP16 loss scaling

给定一个梯度值和 FP16 的保守范围，比较不缩放与缩放后的表示结果。再讨论 unscale 前 clipping 为什么会改变阈值含义。

### 练习五：LoRA 与 QLoRA

## 8.19 本章小结

训练显存由参数、梯度、optimizer state、激活、attention 中间结果、通信 buffer、kernel workspace 和 allocator 峰值共同决定。7B 权重的字节数只是起点，不能代表全参数训练的可运行性。

Activation checkpointing 通过重计算降低常驻激活，gradient accumulation 降低单次 micro-batch 但不降低一次 update 的总计算，ZeRO/FSDP 降低单卡训练状态份额却可能产生 transient gather 峰值，FlashAttention 优化 attention 的 IO 和中间物化但不改变 full attention 的可见性。LoRA/QLoRA 缩小微调时的可训练状态，仍然保留底座 forward 和激活成本。

FP16、BF16 和 FP8 的差别不只在字节数，还在动态范围、尾数、scale、累积精度和硬件路径。loss scaling、unscale、clipping、overflow 统计和第一次 NaN 的 batch 都是数值证据链的一部分。

真正可靠的显存结论必须绑定发生阶段、dtype、micro-batch、有效 token、并行方式、kernel、峰值 allocated/reserved、吞吐、质量和恢复结果。下一章进入训练稳定性与 debug，把这些资源和数值信号放进更系统的故障定位流程。
