# 第一章：训练总览：从目标到可复现的 checkpoint

## 1.0 训练不是一次运行，而是一条证据链

拿到一个可用的 checkpoint，表面上看到的是一组模型权重，实际上看到的是一个训练项目留下的结果。这个结果受到目标定义、数据来源、文本切分方式、模型结构、优化算法、硬件并行、评估协议和后训练策略共同影响。只知道“它是 decoder-only Transformer”远远不足以解释模型为什么有某种能力，也不足以解释它为什么在另一个任务上失败。

初学者可以把训练理解成一个逐层加工过程：数据先被清洗并切成 token，token 进入模型，模型根据损失函数调整参数，训练系统把这个过程扩展到许多 GPU，评估系统判断模型是否真的变好，后训练再把一个会续写文本的 base model 组织成更像助手的行为。每一层都有输入、输出和可能的错误。

专家还需要追问更多问题：训练 token 是按样本数还是按有效 token 统计的？checkpoint 是否包含 optimizer state 和数据游标？验证集是否和训练集去重？吞吐下降来自数据读取、通信还是 checkpoint 写盘？一个 reasoning model 的提升来自预训练、可验证奖励、搜索，还是只是输出格式发生了变化？

因此，本章不把训练写成一串名词，而是建立一张可以回溯的地图。读者读完后，应该能从一个模型产物反推它依赖的训练阶段，也能从一个训练异常定位应该检查哪一类证据。

本章覆盖以下主线：

1. 如何把产品目标转成训练目标和评估目标。
2. 数据、tokenizer、架构、优化器和系统为什么互相制约。
3. 自回归预训练目标、batch token、训练步数和算力如何计算。
4. base、instruct、chat 和 reasoning model 的训练阶段有什么不同。
5. 如何组织训练循环、监控、checkpoint、评估和恢复。
6. 如何区分论文结论、早期估算、教学示例和目标集群实测。

## 1.1 从一个 checkpoint 反推训练项目

### 1.1.1 权重只是结果，不是完整实验

模型权重 `theta` 记录了参数当前的数值，但它通常不能单独回答以下问题：

| 问题 | 需要的额外证据 |
| --- | --- |
| 模型看过什么数据 | 数据版本、来源、配比、过滤和去重报告 |
| 文本如何进入模型 | tokenizer 文件、special token 和 chat template |
| 模型如何被训练 | 模型配置、优化器、学习率、精度和并行配置 |
| 当前权重处于什么阶段 | global step、token 游标、训练阶段和父 checkpoint |
| 训练是否健康 | loss、梯度、吞吐、数值和故障记录 |
| 为什么选择它 | 验证集、能力评估、安全评估和成本数据 |
| 能否继续训练 | optimizer state、scheduler state、随机数状态和数据游标 |

一个可部署的模型目录至少需要权重、模型配置、tokenizer 和推理配置。一个可恢复的训练状态还需要 optimizer state、学习率调度器状态、梯度累积状态、随机数状态、数据分片位置和版本信息。二者经常被混为一谈：能够加载权重并生成文本，不代表能够从上次的 optimizer 动量状态继续训练。

### 1.1.2 从产物反推阶段

同一个 Transformer 架构，可能处在完全不同的训练阶段。一个只经过 next-token 预训练的 checkpoint 通常是 base model；加入指令-回答监督后，可能成为 instruct model；经过多轮对话数据、安全数据和偏好优化后，才可能成为 chat model；若使用推理轨迹、可验证奖励或额外的测试时计算，则可能形成 reasoning model。

这些名称不是严格的文件格式，也不是仅由参数量决定的等级。它们描述的是训练数据、目标函数和行为协议的组合。判断一个 checkpoint 属于哪个阶段，应查看训练记录和行为评估，而不能只看模型名称。

### 1.1.3 一个最小的可追溯关系

训练项目可以先用下面的关系表示：

~~~text
目标与约束
    -> 数据版本与 tokenizer
    -> 模型配置与初始化
    -> 预训练运行
    -> base checkpoint 与验证报告
    -> SFT / 偏好 / 强化训练
    -> 候选 checkpoint 与回归报告
    -> 部署配置与线上观测
~~~

箭头不是不可回头的流水线。验证发现代码能力不足，可能回到代码数据和 tokenizer；发现上下文成本过高，可能重新考虑架构和序列长度；发现后训练造成通用能力退化，可能回到数据混合、损失权重或 checkpoint 选择。训练项目的成熟度，体现在这些回溯关系是否有记录，而不是体现在流程图画得多复杂。

## 1.2 先定义问题，再决定训练方法

### 1.2.1 目标要包含输入、输出和约束

“训练一个大模型”不是一个足够具体的目标。至少要说明：

| 维度 | 需要明确的内容 |
| --- | --- |
| 输入分布 | 语言、领域、长度、噪声、模态和用户群体 |
| 输出任务 | 补全、问答、抽取、代码、数学、规划或工具调用 |
| 输出协议 | 自由文本、JSON、函数参数、代码补丁或语音 token |
| 质量目标 | 正确性、覆盖率、事实性、风格、延迟和稳定性 |
| 资源约束 | 训练 GPU、显存、存储、网络和时间预算 |
| 部署约束 | batch、并发、上下文长度、端侧或云端环境 |
| 风险约束 | 隐私、版权、越权、误触发和高影响动作 |

例如，“做一个企业助手”至少可能包含三种不同任务：

1. 一个通用对话模型负责语言理解和表达。
2. 一个 RAG 系统负责从企业文档中检索证据。
3. 一个工具调用系统负责执行审批、查询或修改动作。

如果把三者混成“训练一个更大的模型”，就会错误地把数据问题、检索问题和权限问题都交给参数规模解决。目标拆开后，才能判断哪些能力应该由预训练获得，哪些能力应该由检索、工具和系统策略提供。

### 1.2.2 能力目标必须有切片

平均分数不等于目标能力。代码模型至少应按语言、仓库规模、测试通过率和安全缺陷切片；中文模型要区分普通文本、专业文本、数字、姓名和方言转写；企业助手要区分知识召回、引用准确、权限判断和动作成功。

可以把一个任务集写成若干输入切片：

~~~math
\mathcal{E}
=
\bigcup_{k=1}^{K}\mathcal{E}_k
~~~

其中 `mathcal{E}_k` 是一个有明确条件的子集，例如长文档、代码、低资源语言或高风险动作。总分只能描述整体平均现象，切片结果才能说明模型在哪些输入上失效。训练目标、数据配比和评估切片应尽量使用同一套术语，否则团队会在不同分母上争论“模型变好了没有”。

### 1.2.3 小白视角与专家视角

小白可以先记住：目标决定数据，数据和预算决定模型规模，模型和序列长度决定系统成本，评估决定是否值得继续训练。

专家还要检查目标是否可观测。例如“更聪明”无法直接作为训练信号；“代码测试通过率提高”需要固定执行环境、测试集和超时规则；“更安全”需要定义有害请求、正常请求误拒和高风险漏放的分母。没有可观测目标，就无法区分模型能力变化和评估脚本变化。

## 1.3 训练方法的历史脉络

### 1.3.1 从统计语言模型到神经语言模型

早期语言模型用 n-gram 近似下一个词的概率，只能看到固定长度的局部历史，稀有组合会造成严重的数据稀疏。神经语言模型用连续向量表示词和上下文，把相似模式映射到相近空间，缓解了完全依赖计数的问题。

随后，循环神经网络和 LSTM 通过递归状态处理更长序列，但训练难以充分并行，长距离信息仍可能衰减。Transformer 用 self-attention 让序列位置直接交互，并且适合在大规模硬件上并行训练。GPT-3 等工作展示了大规模自回归预训练和上下文学习的能力，Scaling Laws 研究则把参数量、数据量和计算量之间的经验关系量化。

这条历史线解释了今天训练总览中的第一个核心事实：next-token prediction 看起来目标单一，但当数据、参数和计算规模足够大时，它会成为语言、代码、知识和部分推理能力的共同训练接口。

### 1.3.2 从 base model 到可交互模型

预训练模型擅长根据上下文续写，但续写行为不等于遵循用户指令。InstructGPT 展示了从示例监督、偏好数据到强化学习的人类反馈链路；DPO 则把一类偏好学习目标写成直接优化策略的形式，减少显式 reward model 和在线 PPO 的工程复杂度。

这并不意味着后训练可以替代预训练。后训练更像是把已有能力放进交互协议、偏好和安全约束中。如果底座缺少目标领域知识或基本推理能力，少量 SFT 和偏好数据通常只能改善表达方式，不能稳定补齐所有能力。

### 1.3.3 从结果奖励到过程和可验证奖励

数学、代码和工具任务可以提供比主观偏好更清晰的反馈：答案是否通过测试、公式是否满足约束、工具参数是否符合 schema。这推动了 verifiable reward、过程监督和 reasoning-oriented training 的发展。

但“有奖励”不代表“奖励可靠”。奖励程序可能被投机，单元测试可能覆盖不足，格式正确可能掩盖事实错误，推理轨迹的长度也可能被错误地当成推理质量。因此现代训练需要把奖励来源、验证覆盖和失败样本一起记录。

## 1.4 完整训练链路的输入与输出

### 1.4.1 阶段总表

| 阶段 | 主要输入 | 主要输出 | 要回答的问题 |
| --- | --- | --- | --- |
| 目标定义 | 业务任务、用户和约束 | 能力与成本目标 | 什么叫成功 |
| 数据工程 | 原始网页、书籍、代码、对话、领域数据 | 有版本的训练语料 | 模型将学习什么 |
| Tokenizer | 代表性文本和词表预算 | vocab、merge 和编码规则 | 文本如何变成 token |
| 架构设计 | 目标能力、算力和部署约束 | 模型配置 | 容量和计算如何分配 |
| 初始化 | 配置和随机种子 | 初始权重 | 如何从可训练状态开始 |
| 预训练 | token、mask 和优化器 | base checkpoint | 如何形成能力底座 |
| Base 评估 | checkpoint 和固定评估集 | 能力与退化报告 | 预训练是否健康 |
| SFT | 指令、对话和格式样本 | instruct checkpoint | 如何遵循任务协议 |
| 偏好或强化训练 | 偏好、规则、验证器和红队数据 | aligned checkpoint | 如何选择更有用、更安全的行为 |
| 综合评估 | 自动、人工、对抗和业务测试 | 候选比较报告 | 哪个版本值得使用 |
| 部署准备 | 候选模型和服务约束 | 量化、并行和服务配置 | 能否在预算内稳定提供服务 |

这些阶段通常会循环进行。比如，评估显示模型在中文代码上表现差，可能需要回到数据和 tokenizer；评估显示长上下文效果下降，可能需要重新检查位置表示、训练长度、检索策略和评测构造；服务端吞吐不足，可能需要调整 batch、量化、并行或模型规模，而不是简单增加训练步数。

### 1.4.2 训练项目不是只有一个 loss

训练时至少同时存在四类信号：

1. 优化信号：train loss、gradient norm、学习率和更新量。
2. 泛化信号：validation loss、领域 loss 和固定能力集。
3. 系统信号：tokens/s、显存、通信、数据等待和 checkpoint 时间。
4. 产品信号：任务成功率、引用正确率、工具副作用、延迟和成本。

它们的变化可能不一致。train loss 下降而 validation loss 上升，可能是过拟合或数据分布差异；validation loss 下降而代码执行成功率不变，可能是目标任务覆盖不足；tokens/s 上升但有效 token 比例下降，可能只是 padding 或过滤统计发生变化。训练总览的价值，就是避免只看一个信号作出全局结论。

## 1.5 自回归预训练目标

### 1.5.1 概率分解

把 token 序列记为 `x_1,x_2,\ldots,x_T`，自回归模型把整段序列的概率分解为：

~~~math
p_\theta(x_1,\ldots,x_T)
=
\prod_{t=1}^{T}
p_\theta(x_t\mid x_{1:t-1})
~~~

其中 `theta` 是模型参数，`x_{1:t-1}` 表示当前位置之前的 token。训练时，模型在每个位置看到真实前缀，并预测下一个 token；这称为 teacher forcing。生成时，前缀的一部分来自模型自己生成的结果，因此训练和推理之间存在暴露偏差。

### 1.5.2 交叉熵与困惑度

对一段长度为 `T` 的序列，常见的平均负对数似然为：

~~~math
L_{\mathrm{lm}}
=
-\frac{1}{T}
\sum_{t=1}^{T}
\log p_\theta(x_t\mid x_{1:t-1})
~~~

如果不同 token 等权，`T` 是有效目标 token 数，而不是包含 padding 的张量宽度。困惑度可以写成：

~~~math
\mathrm{PPL}=\exp(L_{\mathrm{lm}})
~~~

困惑度直观上表示模型面对每个位置时的不确定程度，但它依赖 tokenizer、数据分布、分词规范化和评估上下文。中文 tokenizer 和英文 tokenizer 的 token 单位不同，不能不加说明地直接比较两个模型的 PPL。

### 1.5.3 label shift 与 padding mask

给定输入：

~~~text
input:  x_0  x_1  x_2  x_3
label:      x_1  x_2  x_3  EOS
~~~

模型在位置 `t` 的 logits 预测 `x_{t+1}`。padding、文档边界和不应计算损失的区域需要使用 mask。若有效目标位置集合为 `I`，更准确的 batch loss 是：

~~~math
L
=
-\frac{1}{\sum_{i\in I}m_i}
\sum_i m_i\log p_\theta(y_i\mid x_i)
~~~

这里 `m_i` 为有效位置指示量，`y_i` 是目标 token，并且必须满足 `\sum_{i\in I}m_i>0`。全 padding batch、标签全部被忽略或 mask 错位时，loss 没有定义；训练程序应跳过并记录这类 batch，而不是把它记成零损失。若把 padding 也放进分母，短样本和长样本的权重会被改变；若在 packed sequence 中忘记文档边界，模型可能把一个文档末尾当成下一个文档的自然前缀。

### 1.5.4 从预训练到 SFT 的损失范围

预训练通常对所有有效文本 token 计算 next-token loss。对话 SFT 往往只对 assistant 输出部分计算损失，把 user prompt 和 system message 作为条件而不是学习目标。两者都可以写成 masked cross entropy，但 mask 语义不同。

这一区别会影响数据效率和行为：如果把用户问题也当成目标，模型可能更重视复现输入格式；如果只训练很短的 assistant 输出，模型可能缺少长上下文处理和复杂推理的梯度信号。读取训练代码时，要同时检查 label shift、special token、loss mask 和有效 token 统计。

## 1.6 Token 数、batch 和训练步数

### 1.6.1 为什么按 token 计算

样本长度可能相差很大。一个由 2,048 个短句组成的 batch，和一个由 2,048 个长文档片段组成的 batch，样本数相同但计算量完全不同。因此大模型训练通常同时记录样本数、序列数和有效 token 数。

设每张 GPU 的 micro-batch 样本数为 `B_micro`，GPU 数量为 `G`，每条序列长度为 `T_seq`，梯度累积次数为 `A`，则一次 optimizer update 的理想 global batch token 数为：

~~~math
B_{\mathrm{tok}}
=
B_{\mathrm{micro}}\cdot G\cdot T_{\mathrm{seq}}\cdot A
~~~

这个理想式要求 `B_micro`、`G`、`T_seq` 和 `A` 都是正整数，且明确 `T_seq` 是每个序列的实际可训练长度而非带 padding 的张量宽度。当样本长度不同或 packing 不完整时，应把 `T_seq` 换成实际有效 token 数的平均值或直接从数据统计得到。若 `B_seq` 已经是所有 GPU 每个 micro-step 合计的序列数，则不要再次乘 `G`。

训练 token 总数为 `D` 时，理想 optimizer update 次数为：

~~~math
S
=
\left\lceil
\frac{D}{B_{\mathrm{tok}}}
\right\rceil
~~~

这里 `D\ge0` 且 `B_{\mathrm{tok}}>0`；没有训练 token 时计划步数为零，global batch 为零则是配置错误而不是无穷多步。最后一个 batch 可能不足一个完整 global batch，实际系统可能丢弃、补齐或改变损失权重，因此公式是规划量，不是日志的替代品。

### 1.6.2 梯度累积改变了什么

梯度累积把多个 micro-batch 的梯度加起来，再执行一次 optimizer update。它可以在显存不足时模拟更大的 global batch，但不会完全等价于真正的大 batch：dropout 随机性、动态 padding、通信时机、归一化统计和数据顺序都可能不同。

如果每个 micro-batch 的有效 token 数不同，简单平均每个 batch 的 loss 再累积，可能让短 batch 和长 batch 权重相同。更稳妥的做法是累积未归一化的 token loss 和有效 token 数，最后按总 token 数归一化，具体实现要与框架的梯度缩放方式一致。

### 1.6.3 Epoch 在 web-scale 训练中的含义

传统监督学习常用 epoch 表示完整遍历一遍数据。web-scale 预训练往往按 token budget、数据 mixture 和重复策略定义训练计划，未必恰好遍历一次所有语料。

如果数据集有效 token 数为 `D_data`，计划训练 token 为 `D_train`，粗略的 token 重复倍数为：

~~~math
R_{\mathrm{repeat}}
=
\frac{D_{\mathrm{train}}}{D_{\mathrm{data}}}
~~~

该比值只在 `D_{\mathrm{data}}>0` 时有定义；数据清洗后为空时，不能把重复倍数记成零并继续训练。这个比值不能直接告诉我们模型真正看过多少独立信息，因为近重复、不同顺序和不同切片会改变有效学习信号。数据工程必须同时记录 token 量、文档量、去重后规模和重复策略。

## 1.7 参数量、训练算力与 scaling law

### 1.7.1 `6ND` 是什么

设 dense 模型参数量为 `N`，训练 token 数为 `D`。在一组简化假设下，训练 FLOPs 常用：

~~~math
C_{\mathrm{train}}
\approx
6ND
~~~

这里的 `N` 是实际参与计算的正参数量，`D` 是正的有效训练 token 数；对 MoE，通常更接近每 token active 参数而不是总参数。直觉上，前向和反向传播都需要处理参数与 token 的交互，反向的计算量通常高于前向；`6` 是把这些项合并后的量级常数。它适合在项目早期做数量级估算，不是 profiler 的输出。

实际计算还会受到以下因素影响：

| 因素 | 影响 |
| --- | --- |
| attention 和 MLP 的具体比例 | 改变每 token 的 FLOPs |
| 序列长度 | attention 和 kernel 访问模式变化 |
| MoE | 总参数量与每 token active 参数量不同 |
| 激活重计算 | 减少显存，增加计算 |
| 低精度 kernel | 改变有效吞吐和数值路径 |
| 通信 | 纯 FLOPs 不包含跨 GPU 等待 |
| padding 与 packing | 影响有效 token 与实际 token 的比值 |
| checkpoint 和评估 | 增加非训练阶段时间 |

因此，`6ND` 能回答“是不是同一个数量级”，不能回答“这组 GPU 几天一定能完成”。

### 1.7.2 Scaling Laws 提供什么信息

Scaling Laws 研究表明，在特定数据、模型和优化条件下，损失会随模型规模、数据规模和计算量呈现经验规律。这类规律可用于早期资源规划和模型尺寸选择，但它不是跨数据分布、跨架构和跨目标任务的物理定律。

Chinchilla 风格的 compute-optimal 研究进一步强调：在固定计算预算下，参数量和训练 token 数需要共同规划，训练不足的大模型可能不如充分训练的较小模型。这个结论不等于“所有模型都必须遵循一个固定 token/parameter 比例”。数据质量、上下文长度、MoE active 参数、后训练预算和部署约束都会改变最优点。

### 1.7.3 Dense 与 MoE 的参数账本

Dense 模型每个 token 大致经过全部层和全部参数。MoE 模型拥有较大的总参数量，但每个 token 只路由到部分 expert。比较两者时应至少分开记录：

1. 总参数量：影响 checkpoint 存储和可能的知识容量。
2. active 参数量：影响每 token 的计算量。
3. expert 路由与负载均衡：影响通信、吞吐和训练稳定性。
4. 总训练 token：影响数据暴露量。
5. 服务阶段的并发和显存：影响真实成本。

只用一个“参数量”数字比较 Dense 和 MoE，容易得出错误的速度和质量结论。

## 1.8 训练时间、GPU 小时和显存

### 1.8.1 从吞吐估算总时间

如果有效训练吞吐为 `R_tok` tokens/s，计划处理 `D` 个 token，则：

~~~math
T_{\mathrm{train}}
=
\frac{D}{R_{\mathrm{tok}}}
~~~

如果使用 `G` 张 GPU，纯训练阶段的 GPU 小时为：

~~~math
H_{\mathrm{gpu}}
=
\frac{T_{\mathrm{train}}}{3600}\cdot G
~~~

这两式要求 `D\ge0`、`R_{\mathrm{tok}}>0` 和 `G>0`。吞吐为零意味着数据、设备或训练循环没有推进，训练时间应报告为不可完成而不是一个可比较的有限数。这里的 `R_tok` 必须明确是单卡、单节点还是全局有效吞吐，是否包含 padding，是否包含评估和 checkpoint。将 benchmark kernel 吞吐直接当成端到端训练吞吐，是资源估算最常见的错误之一。

### 1.8.2 权重、梯度和 optimizer state

若参数量为 `N`，每个权重占 `b_w` 字节，只保存权重时的理论大小为：

~~~math
M_{\mathrm{weight}}
\approx
N b_w
~~~

这里 `N` 和 `b_w` 必须为正；`b_w` 是存储字节数，不等同于每次 kernel 实际读写的所有字节。训练显存还要加上梯度、optimizer state、master weights、激活、临时 buffer、通信 buffer 和框架缓存。以 AdamW 为例，除了模型权重，通常还需要一阶和二阶动量；在混合精度训练中还可能保留更高精度的 master weights。实际显存取决于参数分片、激活重计算、sequence length、micro-batch 和实现细节。

一个 1.3B 参数模型即使以 2 字节保存权重，权重本身也不等于训练所需显存。把 `1.3B × 2 bytes` 当成训练显存，是把部署账本误当成训练账本。

### 1.8.3 训练成本不止 GPU 价格

训练成本可以拆为：

~~~math
C_{\mathrm{train}}
=
C_{\mathrm{gpu}}
+C_{\mathrm{storage}}
+C_{\mathrm{network}}
+C_{\mathrm{data}}
+C_{\mathrm{evaluation}}
+C_{\mathrm{failure}}
+C_{\mathrm{engineering}}
~~~

`C_failure` 包括节点故障、坏 checkpoint、错误配置和重跑；`C_engineering` 包括数据处理、监控、调试和评估平台。一个单次实验的 GPU 小时很低，但若需要多轮消融、失败重跑和人工检查，总成本可能显著增加。

## 1.9 Tokenizer、数据和架构的联动

### 1.9.1 Tokenizer 影响训练预算

同一段文本被不同 tokenizer 切成不同数量的 token。token 更长，序列处理和 embedding/输出层的成本都会变化；切分过细还可能使代码、数学符号和中文短语需要更多预测步骤。

设同一数据集合在 tokenizer `A` 和 `B` 下的 token 数分别为 `D_A` 和 `D_B`，则在相同参数量和硬件吞吐假设下，训练时间的第一阶比例约为：

~~~math
\frac{T_A}{T_B}
\approx
\frac{D_A}{D_B}
~~~

这只是量级关系。词表更大可能增加 embedding 和输出层参数，序列更短可能改善 attention 成本，切分规则还会影响跨语言公平和下游格式稳定。因此 tokenizer 选择不能只看词表大小。

### 1.9.2 数据 mixture 不是样本列表

设不同数据域的 token 数为 `D_1,D_2,\ldots,D_K`，总 token 数为 `D`，则 token-level mixture 为：

~~~math
w_k=\frac{D_k}{D},
\qquad
\sum_{k=1}^{K}w_k=1
~~~

这里每个 `D_k\ge0`，总量 `D=\sum_kD_k>0`；只要某个权重来自手工配置，仍应在采样后重新统计实际 token 比例。空数据混合不存在“全为零但总和为一”的合法解释。如果采样器按文档数而不是 token 数混合，长文档域的有效比例会不同；如果数据域经过重复采样，`w_k` 表示的是进入训练的 token 比例，而不是原始数据集的占比。

代码、数学、中文、多语言、对话和安全数据都可能需要不同的采样温度和重复策略。提高某个域的比例可能改善该域能力，也可能挤压通用数据、增加过拟合或改变模型风格。配比必须和 per-domain loss、目标能力和回归评估一起解释。

### 1.9.3 架构是目标和约束的折中

decoder-only Transformer 适合统一的自回归文本建模；encoder-decoder 可以把输入理解和输出生成分离；稀疏 MoE 通过路由扩展总容量；GQA/MQA 主要改善推理阶段的 KV cache 和带宽账本；更长上下文的训练会改变显存、数据构造和评估成本。

架构选择要回答具体问题：

| 目标 | 需要关注的架构变量 |
| --- | --- |
| 通用文本能力 | 层数、宽度、训练 token 和稳定性 |
| 长上下文 | 位置表示、训练长度、attention 成本和检索基线 |
| 低延迟服务 | active 参数、KV cache、量化和解码路径 |
| 多语言 | tokenizer、数据覆盖、共享表示和语言切片 |
| 代码和工具 | 格式约束、长程依赖、执行反馈和 schema 训练 |
| 多模态 | connector、模态 token rate、损失平衡和解码器 |

“更大的模型”只是其中一个旋钮。若瓶颈是数据覆盖或评估污染，扩大模型不会自动解决；若瓶颈是推理显存，扩大模型可能让产品更不可行。

## 1.10 一次 optimizer update 内部发生什么

训练循环可以拆成以下事件：

1. 数据加载器取出一个或多个 micro-batch。
2. tokenizer 结果、attention mask 和 label mask 送入模型。
3. 前向计算产生 logits 和 loss。
4. 对 loss 做缩放或归一化，执行反向传播。
5. 累积梯度，必要时做梯度裁剪。
6. optimizer 更新参数，scheduler 更新学习率。
7. 记录 token、loss、梯度、吞吐、显存和异常。
8. 按策略保存 checkpoint，或异步执行评估。

可以用一个简化的参数更新表示：

~~~math
\theta_{s+1}
=
\mathrm{Optimizer}
\left(
\theta_s,\nabla_\theta L_s,\eta_s
\right)
~~~

其中 `s` 是 optimizer step，`eta_s` 是当前学习率。这个公式隐藏了混合精度、梯度缩放、权重衰减、动量和分布式同步，但提醒我们：loss 只是更新的输入之一，optimizer state 和学习率状态也决定了下一步发生什么。

### 1.10.1 梯度裁剪不是修复所有异常

若梯度向量为 `g`，裁剪阈值为 `c`，全局范数裁剪可写成：

~~~math
g'
=
g\cdot
\min\left(1,\frac{c}{\lVert g\rVert_2+\epsilon}\right)
~~~

它可以限制过大的更新，但不能修复错误 label、损坏输入、学习率调度错误、NaN 或通信不同步。监控 clipping ratio 很有用：如果几乎每一步都被强烈裁剪，说明训练配置或数据分布可能不合适。

### 1.10.2 训练步、数据步与评估步

代码中常见的 `step` 可能表示 micro-step、optimizer step、日志 step 或数据读取次数。实验记录必须明确口径。学习率通常按 optimizer step 更新，吞吐可能按处理 token 统计，评估可能按 checkpoint step 标记。

一个可靠日志事件至少包含：

~~~text
run_id, global_step, data_cursor, effective_tokens,
loss, grad_norm, learning_rate, tokens_per_second,
gpu_memory, overflow_count, checkpoint_id
~~~

没有统一 step 语义，两个实验即使都写着“step 10000”，也可能处理了不同数量的 token。

## 1.11 Base、Instruct、Chat 与 Reasoning Model

### 1.11.1 Base model

Base model 主要通过大规模 next-token prediction 学习文本分布。它能续写网页、论文、代码和对话，但不一定理解用户正在发出一个任务，也不一定主动遵守输出格式。

Base model 的主要能力来源包括数据覆盖、数据质量、tokenizer、模型容量、训练 token 和优化稳定性。它是后训练的起点，但不是一个天然的聊天产品。

### 1.11.2 Instruct model

Instruct model 使用指令、输入和目标回答进行监督微调。一个样本通常包含 system、user 和 assistant 等角色，训练时往往只对 assistant 区域计算损失。它学习的是任务协议，例如摘要、分类、抽取、解释和代码生成。

SFT 的基本目标可以写成：

~~~math
L_{\mathrm{SFT}}
=
-\frac{1}{|I_{\mathrm{assistant}}|}
\sum_{i\in I_{\mathrm{assistant}}}
\log p_\theta(y_i\mid x_i)
~~~

`I_assistant` 表示 assistant 目标 token 的位置集合，并且必须非空。若模板、截断或 label mask 让一个 batch 没有任何 assistant token，训练应报告数据契约错误，而不是把 loss 当作零。SFT 数据质量、回答多样性和 mask 规则会直接影响模型的表达风格与任务稳定性。

### 1.11.3 Chat model

Chat model 在 instruct 基础上更强调多轮上下文、角色边界、安全行为、拒答策略和对话状态。chat template 会把结构化消息转换成模型训练和推理时看到的 token 序列。若训练时的 template 与服务时不同，模型可能出现角色混淆、工具格式错误或回答位置偏移。

“Chat”不是一个单独的模型层，也不是只加一个 system prompt。它通常涉及数据构造、模板、偏好、安全、流式生成和服务协议的整体变化。

### 1.11.4 Reasoning model

Reasoning model 的训练可能包含数学和代码轨迹、过程监督、结果验证、强化学习、拒绝采样、蒸馏和更高的测试时计算。它的关键不是输出更长，而是在复杂任务上生成、检查和选择更可靠的中间过程。

应区分三个现象：

1. 输出变长：只说明 token 数增加。
2. 答案更有条理：可能是 SFT 风格变化。
3. 正确率在受控任务中提高：才是能力证据的一部分。

如果奖励只检查最终字符串格式，模型可能学会投机；如果验证器覆盖不足，推理训练可能优化错误目标。因此 reasoning model 必须同时评估最终答案、过程可靠性、计算成本和失败样本。

## 1.12 后训练：把能力组织成行为

### 1.12.1 SFT 先建立协议

SFT 适合教模型“输入长什么样，输出应该遵循什么结构”。它可以学会 JSON、工具调用、领域术语、拒答格式和多轮角色，但会受到示例覆盖和标注质量限制。

低质量 SFT 可能造成模板化、过度冗长、事实错误被复制或单一语言风格。SFT 还可能覆盖预训练中形成的开放能力，因此需要在通用能力和目标任务之间做回归评估。

### 1.12.2 偏好优化改变选择倾向

偏好数据通常包含同一输入下的 preferred 和 rejected 输出。DPO 的一个常见形式是：

~~~math
L_{\mathrm{DPO}}
=
-\mathbb{E}
\left[
\log\sigma
\left(
\beta
\left(
\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\mathrm{ref}}(y_w\mid x)}
-
\log\frac{\pi_\theta(y_l\mid x)}{\pi_{\mathrm{ref}}(y_l\mid x)}
\right)
\right]
~~~

`y_w` 是偏好回答，`y_l` 是非偏好回答，`pi_ref` 是参考策略，`beta` 控制偏离参考策略的尺度。这个目标说明偏好优化不只是把 chosen 当作普通监督答案；它比较两个回答相对于参考模型的对数概率变化。

PPO、DPO、IPO、KTO、GRPO、GSPO、DAPO 等方法的目标和数据假设不同。训练时不能只按名称判断效果，应记录 reward 来源、采样策略、参考模型、优势或相对分数、长度处理和安全约束。

### 1.12.3 偏好和验证器的边界

人类偏好可以覆盖帮助性、清晰度和风格，但成本高且一致性有限；程序验证器可以检查代码和数学结果，但覆盖范围有限；模型 judge 可以扩大标注规模，但会受到偏差和 prompt 敏感性影响。

训练信号越接近目标，越容易优化；但目标越窄，越可能牺牲没有被记录的能力。后训练必须同时保留通用能力、目标任务、安全和成本回归，不能用单一 reward 代替完整评估。

## 1.13 训练监控：四张互相连接的仪表盘

### 1.13.1 优化健康

优化健康回答“参数是否按预期更新”：

| 指标 | 观察内容 |
| --- | --- |
| train loss | 训练数据上的拟合趋势 |
| validation loss | 未见数据上的泛化趋势 |
| learning rate | 当前更新尺度和 schedule 位置 |
| grad norm | 梯度规模和异常变化 |
| update norm | 参数实际变化大小 |
| clipping ratio | 梯度是否频繁被裁剪 |

只看 train loss 可能看不到过拟合；只看 validation loss 可能看不到领域能力和系统问题。loss 的横轴也应使用 optimizer step、有效 token 或 wall-clock 时间中的明确一种。

### 1.13.2 数值健康

数值健康回答“计算是否仍然可信”：

1. logits、loss、gradient 中是否出现 NaN 或 Inf。
2. 混合精度是否发生 overflow。
3. loss scale 是否频繁回退。
4. 梯度是否在某一批数据突然异常。
5. softmax、归一化和除法是否存在极端输入。

NaN 出现后继续保存 checkpoint，可能把坏状态传播到后续实验。训练循环应在发现异常时记录 batch 标识、数据样本引用、参数摘要、精度状态和最近一个可恢复 checkpoint。

### 1.13.3 系统健康

系统健康回答“GPU 是否在有效工作”：

| 指标 | 可能暴露的问题 |
| --- | --- |
| effective tokens/s | 全局训练进度 |
| GPU utilization | 数据等待或 kernel 低效 |
| MFU 或近似 FLOPs 利用率 | 计算路径效率 |
| dataloader wait | 存储、解码或网络瓶颈 |
| communication time | collective 或拓扑瓶颈 |
| checkpoint duration | 写盘和同步压力 |
| memory allocated/reserved | 显存增长和碎片 |
| node health | 单节点故障或降频 |

增加 GPU 不一定提升吞吐。若输入 pipeline 供不上数据、通信占比过高或 checkpoint 频繁阻塞，集群规模增大可能只增加成本。

### 1.13.4 能力健康

能力健康回答“模型对目标任务是否真的变好”：

1. 通用 validation loss 和 per-domain loss。
2. 代码执行、数学验证、多语言和长上下文切片。
3. 格式、工具调用和结构化输出。
4. 事实性、拒答、越狱和隐私测试。
5. 目标业务 golden set 和人工复核。

评估脚本也可能出错。prompt 模板、答案规范化、随机种子、few-shot 示例和工具环境都要版本化。一个分数变化如果不能追溯到模型、数据或评估代码，就不应直接解释成能力变化。

## 1.14 Checkpoint、恢复和选择

### 1.14.1 三类 checkpoint

训练项目常见三类产物：

| 类型 | 内容 | 主要用途 |
| --- | --- | --- |
| 权重快照 | 模型参数、配置和 tokenizer | 推理、评估、发布候选 |
| 训练恢复快照 | 权重、optimizer、scheduler、随机数和数据位置 | 从中断处继续训练 |
| 评估候选快照 | 权重及与评估绑定的元数据 | 比较版本和回归分析 |

三者可以合并，但概念上要区分。只保存权重的快照通常无法严格复现下一步 optimizer update；只保存恢复状态却没有 tokenizer 和配置，部署端也无法正确解释输入。

### 1.14.2 为什么最后一步不一定最好

预训练后期的 validation loss 可能继续下降，但某个领域能力、长上下文能力或安全行为可能已经退化。后训练中，继续优化可能让模型更偏向某种回答风格、过度拒答或遗忘通用任务。

checkpoint 选择应该同时查看：

| 维度 | 问题 |
| --- | --- |
| 基础收敛 | validation loss 是否稳定 |
| 目标能力 | 目标任务是否提高 |
| 回归 | 通用、代码、多语言和长上下文是否退化 |
| 安全 | 漏放、误拒和越权是否变化 |
| 稳定性 | 多 seed、不同长度和不同用户切片是否一致 |
| 成本 | 延迟、显存、吞吐和重试率是否可接受 |

这不是把多个指标随意加权成一个总分，而是明确候选版本的取舍。最终选择应保留评估集、版本和决策理由。

### 1.14.3 恢复验证

训练恢复不能只检查“文件能否打开”。应至少验证：

1. 恢复后 optimizer step 和学习率与中断前连续。
2. 随机数和数据游标不会导致意外重复或跳过。
3. 分布式 rank 对 checkpoint 的读取一致。
4. 恢复后的 loss 和吞吐没有异常跳变。
5. 小规模恢复实验与完整训练使用相同的版本和配置。

最小恢复测试可以先在少量数据和少量 step 上进行。等训练跑到数万 step 后才发现保存格式不能恢复，代价通常远高于早期写一个小测试。

## 1.15 常见失败链：从现象追到根因

### 1.15.1 Loss 不下降

可能原因包括 label shift 错误、loss mask 全为零、tokenizer 与 embedding 不匹配、学习率过低、数据为空、参数被冻结或分布式梯度没有同步。排查顺序应从最接近数据的地方开始：打印一批 input、label、mask 和有效 token 数，再在极小模型和极小数据上确认模型能过拟合。

### 1.15.2 Loss spike 或 NaN

可能原因包括异常 batch、学习率过大、梯度爆炸、混合精度 overflow、除零、错误的归一化和通信不同步。一次 spike 本身不是根因；需要把 spike 对应的 batch、序列长度、来源域、loss mask、梯度范数和精度状态关联起来。

如果只有某个数据域触发异常，应优先检查数据和预处理；如果所有域在学习率变化处同时异常，应检查 schedule 和更新尺度；如果只有一个 rank 异常，应检查分片数据、硬件和 collective。

### 1.15.3 吞吐下降

吞吐下降可来自：

1. 数据读取、解压、tokenize 或 host-to-device copy 变慢。
2. 序列长度分布改变，padding 增加。
3. collective 通信等待增加。
4. 某个节点降频、掉卡或网络重传。
5. checkpoint、评估或日志同步阻塞。
6. 动态 batch 或异常长样本触发更大显存压力。

因此“GPU 利用率低”只是现象，不是修复方案。要把 step time 拆成数据、前向、反向、通信、optimizer、同步和写盘阶段。

### 1.15.4 评估分数异常

分数异常可能来自 benchmark contamination、prompt 格式不一致、答案规范化、few-shot 顺序、随机采样、工具环境、评估代码或模型 checkpoint 混用。评估报告必须包含模型版本、tokenizer、prompt、解码参数、数据版本和脚本 commit。

### 1.15.5 后训练能力退化

后训练后通用能力下降，可能是目标数据太窄、训练过久、学习率过大、拒答数据比例过高、偏好标签偏差或参考模型设置不当。解决办法不是默认增加训练量，而是做数据切片、混合比例、学习率、checkpoint 和回归任务的对照实验。

## 1.16 一个可复现训练项目应交付什么

### 1.16.1 数据与 tokenizer 产物

至少应保存：

| 产物 | 关键字段 |
| --- | --- |
| 数据 manifest | id、来源、许可、语言、领域、时间和版本 |
| 清洗报告 | 保留率、过滤原因、抽检结果和风险 |
| 去重报告 | exact/near duplicate 方法、阈值和统计 |
| mixture 配置 | 域、token 数、采样权重和重复策略 |
| tokenizer | vocab、special token、规范化和 hash |
| template | system/user/assistant/tool 的序列化规则 |

### 1.16.2 模型与训练产物

应保存模型配置、初始化种子、参数量、上下文长度、attention 结构、优化器、学习率、精度、并行策略、global batch、gradient accumulation、数据游标和 checkpoint 关系。

训练日志至少需要关联 run id、代码版本、容器或依赖版本、硬件拓扑、数据版本和评估脚本版本。只保留最终 loss 曲线，无法替代这些元数据。

### 1.16.3 评估与事故产物

评估报告应保留原始预测、规范化规则、切片统计、人工评审协议、错误样例和置信区间。事故报告应包含时间线、最后正常 checkpoint、触发条件、影响范围、修复动作和回归测试。

这些资料的作用不是增加文档负担，而是让下一轮实验能够回答“改变了什么，观察到什么，为什么相信这个结论”。

## 1.17 一个最小训练规划账本

下面的示例不训练模型，只把训练方案中的 token、步数、吞吐、存储、评估和风险信息放在一起。代码使用 Python 标准库，数字是教学构造，不代表任何具体硬件的真实性能。

~~~python
import math


def require_positive_int(name, value):
    if not isinstance(value, int) or isinstance(value, bool) or value <= 0:
        raise ValueError(f"{name} must be a positive integer")


def require_finite_positive(name, value):
    if not isinstance(value, (int, float)) or isinstance(value, bool):
        raise ValueError(f"{name} must be a finite positive number")
    if not math.isfinite(value) or value <= 0:
        raise ValueError(f"{name} must be a finite positive number")


training = {
    "goal": "1.3B domain base model candidate",
    "params_b": 1.3,
    "train_tokens_b": 120.0,
    "seq_len": 2048,
    "micro_batch": 2,
    "num_gpus": 8,
    "grad_accum": 16,
    "tokens_per_sec_per_gpu": 1800,
    "weight_bytes": 2,
    "checkpoints": 5,
    "data_mix": {
        "web": 0.45,
        "code": 0.20,
        "math": 0.15,
        "domain": 0.15,
        "safety": 0.05,
    },
    "monitor": {
        "train_loss",
        "valid_loss",
        "grad_norm",
        "learning_rate",
        "tokens_per_sec",
        "gpu_memory",
        "nan_inf",
    },
    "evaluations": {"general", "code", "math", "domain", "safety"},
    "risks": {"contamination", "loss_spike", "oom", "checkpoint_failure"},
}


def summarize_training(training):
    for name in (
        "seq_len",
        "micro_batch",
        "num_gpus",
        "grad_accum",
        "weight_bytes",
        "checkpoints",
    ):
        require_positive_int(name, training[name])
    for name in ("params_b", "train_tokens_b", "tokens_per_sec_per_gpu"):
        require_finite_positive(name, training[name])
    if not isinstance(training["data_mix"], dict) or not training["data_mix"]:
        raise ValueError("data_mix must be a non-empty mapping")
    if any(
        not isinstance(weight, (int, float))
        or isinstance(weight, bool)
        or not math.isfinite(weight)
        or weight < 0
        for weight in training["data_mix"].values()
    ):
        raise ValueError("data_mix weights must be finite and non-negative")
    params = training["params_b"] * 1_000_000_000
    tokens = training["train_tokens_b"] * 1_000_000_000
    global_batch_tokens = (
        training["micro_batch"]
        * training["num_gpus"]
        * training["grad_accum"]
        * training["seq_len"]
    )
    updates = math.ceil(tokens / global_batch_tokens)
    global_tokens_per_sec = (
        training["tokens_per_sec_per_gpu"] * training["num_gpus"]
    )
    seconds = tokens / global_tokens_per_sec
    weight_gib = params * training["weight_bytes"] / 1024**3
    mixture_total = sum(training["data_mix"].values())
    if not math.isclose(mixture_total, 1.0, rel_tol=0.0, abs_tol=1e-9):
        raise ValueError("data_mix weights must sum to 1")

    required_monitor = {
        "train_loss",
        "valid_loss",
        "grad_norm",
        "learning_rate",
        "tokens_per_sec",
        "gpu_memory",
        "nan_inf",
    }
    required_evaluations = {"general", "code", "math", "domain", "safety"}
    required_risks = {"contamination", "loss_spike", "oom", "checkpoint_failure"}

    return {
        "global_batch_tokens": global_batch_tokens,
        "optimizer_updates": updates,
        "train_days": round(seconds / 86400, 2),
        "gpu_hours": round(seconds / 3600 * training["num_gpus"], 2),
        "estimated_flops": f"{6 * params * tokens:.2e}",
        "weight_gib": round(weight_gib, 2),
        "checkpoint_weight_gib": round(
            weight_gib * training["checkpoints"], 2
        ),
        "mixture_total": round(mixture_total, 4),
        "missing_monitor": sorted(required_monitor - training["monitor"]),
        "missing_evaluations": sorted(
            required_evaluations - training["evaluations"]
        ),
        "missing_risks": sorted(required_risks - training["risks"]),
    }


summary = summarize_training(training)
assert summary["global_batch_tokens"] == 524288
assert summary["optimizer_updates"] == 228882
assert summary["mixture_total"] == 1.0
assert summary["missing_monitor"] == []
assert summary["missing_evaluations"] == []
assert summary["missing_risks"] == []
bad_plan = dict(training)
bad_plan["data_mix"] = {"web": 0.0, "code": 0.0}
try:
    summarize_training(bad_plan)
except ValueError:
    pass
else:
    raise AssertionError("empty token mixture must not be accepted")
print("training ledger: ok")
~~~

这个例子给出的 `6ND`、权重大小和 GPU 小时只是规划账本。示例会拒绝零或非有限的训练量、吞吐、设备数和数据混合，避免把“不可能推进的训练”伪装成一张预算表。真实训练还要加入 optimizer state、激活、通信、checkpoint 写盘、评估、故障恢复、数据处理和有效 token 利用率。它的价值在于把容易混淆的 per-device batch、global batch、gradient accumulation、训练 token 和 GPU 小时放在同一套口径下。

## 1.18 证据边界：什么可以由资料确认

不同资料支持的结论范围不同：

| 资料类型 | 可以支持 | 不能直接支持 |
| --- | --- | --- |
| 原始论文 | 目标函数、架构、训练设置和论文实验 | 当前项目的所有输入分布和生产质量 |
| 官方技术报告 | 模型方向、公开数据和评估协议 | 未披露的训练细节和全部安全保证 |
| 官方文档/代码 | API、配置、实现语义和版本行为 | 不同硬件上的稳定吞吐 |
| benchmark | 固定数据和协议下的横向结果 | 真实用户任务、污染外的泛化和单位成功成本 |
| 教学估算 | 公式、shape 和量级关系 | 集群实测时间、显存和可靠性 |
| 产品宣传 | 功能方向和演示范围 | 训练数据、内部架构和所有输入的能力 |

本章涉及的公开资料：

- [Scaling Laws for Neural Language Models](https://arxiv.org/abs/2001.08361)：模型规模、数据和计算的经验关系。
- [Training Compute-Optimal Large Language Models](https://arxiv.org/abs/2203.15556)：参数与训练 token 的联合规划。
- [Language Models are Few-Shot Learners](https://arxiv.org/abs/2005.14165)：大规模自回归预训练与上下文学习。
- [Training Language Models to Follow Instructions with Human Feedback](https://arxiv.org/abs/2203.02155)：SFT、奖励模型和 RLHF 链路。
- [Direct Preference Optimization](https://arxiv.org/abs/2305.18290)：直接偏好优化的目标函数。
- [DeepSeek-R1](https://arxiv.org/abs/2501.12948)：推理强化学习、可验证奖励和蒸馏的公开案例。

这些资料可以支持训练目标、计算估算、偏好优化和公开推理训练路线的基本事实，不能替代目标项目的数据授权、集群 benchmark、事故记录和人工评估。特别是 `6ND`、Chinchilla 风格关系和论文 benchmark，都应绑定适用条件，不能直接变成某个项目的保证。

## 1.19 章节练习：把训练链路变成可计算对象

### 练习一：检查 token 口径

某训练任务使用 4 张 GPU，每张 GPU 的 micro-batch 为 2，序列长度为 4,096，gradient accumulation 为 8。计算一次 optimizer update 的理想 token 数。再说明当真实序列长度不固定且存在 padding 时，应该额外记录什么。

### 练习二：比较两种 tokenizer

同一语料在 tokenizer A 下产生 100 亿 token，在 tokenizer B 下产生 75 亿 token。先按第一阶近似计算训练时间比例，再列出至少三个会破坏这个近似的因素，例如词表输出层、序列长度分布、packing 和 kernel 利用率。

### 练习三：定位 loss 不下降

设计一个最小复现：只使用几十条样本和很小的模型，要求模型能够过拟合。依次检查 input、label shift、loss mask、有效 token 数、参数是否更新和学习率。说明每一个检查排除了什么原因。

### 练习四：比较 base 和 instruct checkpoint

固定 tokenizer、解码参数和评估集，比较一个 base checkpoint 与一个 SFT checkpoint。分别观察补全、指令跟随、结构化输出、通用能力和拒答行为，说明为什么 SFT 可能提高任务协议却造成某些能力回归。

### 练习五：设计 checkpoint 选择实验

从同一训练运行中选择三个 checkpoint，建立通用、代码、数学、长上下文、安全和延迟六类评估。不要先规定一个总分，先画出各指标的变化，再说明不同选择对应的用户和成本取舍。

### 练习六：拆解一次吞吐下降

假设训练在第 30,000 step 后 tokens/s 下降 25%。为数据读取、序列长度、通信、GPU 健康、checkpoint 和评估同步各设计一个可观察证据，并安排最小的排查顺序。

### 练习七：恢复训练一致性

让一个小模型运行 20 个 optimizer step，在第 10 步保存权重、optimizer、scheduler、随机数和数据游标。分别比较连续运行与恢复运行的 loss、学习率、参数摘要和数据样本，找出只保存权重时的差异。

## 1.20 本章总结

大模型训练是一项从目标开始、以可复现产物结束的全链路工程。预训练通过 next-token prediction 形成能力底座；tokenizer 和数据配比决定模型实际接触到什么；架构、参数量、序列长度和 active 参数决定计算路径；优化器、batch 和精度决定参数如何更新；分布式系统决定这件事能否在预算内完成。

SFT、偏好优化、强化训练和可验证奖励负责把底座能力组织成更符合任务协议的行为，但不能替代数据覆盖和基础能力。loss、评估、系统吞吐和安全指标必须同时观察；checkpoint 选择是多目标比较，最后一步不天然最好。

一个可信的训练结论，至少要能追溯到数据版本、tokenizer、模型配置、训练状态、硬件吞吐、评估脚本和失败实验。论文公式和 scaling law 可以帮助我们建立量级直觉，只有目标集群实测、固定评估和事故回放，才能支持具体项目的工程结论。
