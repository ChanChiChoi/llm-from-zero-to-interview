# 第 13 章 Encoder-Free Unified Multimodal：统一 token 流如何改变多模态模型

## 13.1 传统多模态模型的拼接方式

早期视觉语言模型常把图像交给独立 vision encoder，再通过 projector 把视觉特征映射到语言模型 hidden space。语言模型继续处理文字 token 和一串视觉 embedding。语音、视频和图像生成又有各自的 encoder、decoder 或 diffusion backbone。

这种模块化设计容易理解、便于复用，但接口之间存在损失：视觉信息先被压成特征，模态切换需要特殊 token，生成路径和理解路径可能不是同一个语言空间。

Encoder-free unified multimodal 的方向，是让不同模态更直接地进入统一 token/latent 序列，或者使用一个更统一的主干处理理解与生成。具体模型可能仍然有 tokenizer、patchifier、projection 或模态适配器，因此“encoder-free”不能简单解释成“完全没有任何前端编码器”。

## 13.2 统一序列的抽象

将文本 token、图像 patch、音频片段或视频块映射成序列元素：

```math
z=\mathrm{Interleave}(z_{\mathrm{text}},z_{\mathrm{vision}},z_{\mathrm{audio}},z_{\mathrm{video}})
```

统一主干计算：

```math
h=\mathrm{Transformer}(z,\mathrm{mask},\mathrm{position})
```

输出根据任务头或生成器产生文本、离散视觉 token、连续 latent 或工具动作。这个抽象的重点是统一的信息路由，不是宣称所有模态使用相同的 tokenizer。

## 13.3 为什么统一可能有优势

如果图像中的文字、空间关系和用户问题在同一序列中交互，模型可以减少模态间桥接损失；理解与生成共享表示，也可能让“看图—编辑—解释”任务更自然。训练和 serving 还可能复用一部分主干、cache 和工具协议。

代价是序列长度和计算复杂度。一个高分辨率图像可能对应大量 patch token，视频还要乘以帧数；不同模态的噪声、位置和采样频率也不同。统一不等于便宜。

## 13.4 一个图文问答例子

用户上传一张包含表格的截图，问“第三行的数值比第二行高多少，并解释原因”。系统需要同时处理视觉布局、文字识别、数字计算和语言回答。

若视觉信息被压缩过度，模型可能读对主题却读错数字；若文字 token 和图像 patch 的位置 mask 不对，第三行和第二行的对应关系会错。评估要把 OCR、空间定位、算术、引用和最终回答拆开。

## 13.5 多模态位置和 mask

文本 position、二维图像位置、时间帧位置和音频时间轴不能简单共用一个整数。统一序列需要定义模态标记、二维/三维位置、跨模态可见性和 causal mask。

例如图像理解可以让文本 query 访问整张图，而视频生成可能需要因果时间 mask。mask 错误会导致信息泄露、未来帧可见或模态对齐失败。

## 13.6 训练数据和目标

统一模型需要图文交错、图像描述、视觉问答、OCR、视频时间关系、音频转写、生成目标和工具任务。数据比例会影响模型是更擅长文字聊天还是视觉推理。

多模态数据还要处理版权、隐私、敏感图像、重复、分辨率和 OCR 噪声。只把大量图片转成 caption 不等于学会空间和数值关系。

## 13.7 计算和 token budget

若文本长度为 `T_text`，图像 patch 数为 `N_img`，视频帧为 `F`、每帧 patch 数为 `N_frame`，统一序列近似为：

```math
T_{\mathrm{total}}=T_{\mathrm{text}}+N_{\mathrm{img}}+F N_{\mathrm{frame}}+T_{\mathrm{audio}}
```

全 attention 的 prefill 和 KV 大小都会随总 token 增长。分辨率、帧率和音频采样策略直接影响成本，不能只按文字 token 计费。

## 13.8 部署接口

processor 要稳定地把图片、音频、视频、文件和文本序列化；runtime 要知道模态 placeholder、position、dtype、KV/state、stream event 和取消。一个只支持文本 chat 的兼容 server 不能因为能接收图片 URL 就声称支持统一多模态。

golden cases 应保存媒体 hash、processor revision、token/patch 数、序列化结构、输出 item、引用和错误。

## 13.9 评估与失败模式

测试 OCR、空间关系、图表数值、长视频时序、图文冲突、图像安全、生成质量和工具调用。按分辨率、模态组合、长度和 batch 分桶，记录准确、引用、延迟、显存和成本。

失败包括图片被静默缩放、媒体 token 超预算、mask 错、音视频时间轴错、模型只依赖 OCR 文本、统一主干导致模态干扰、敏感图片进入日志和不支持的 processor 静默降级。

## 13.10 面试回答与练习

回答“encoder-free unified multimodal 的价值”时，应说它尝试让多模态信息在更统一的 token/latent 主干中交互，减少模块桥接，但不意味着没有任何 tokenizer/patchifier，也不自动降低成本。关键是模态序列化、位置/mask、token budget、训练数据、评估和协议支持。

练习一：为图表问答设计文本、视觉、数值三层指标。

练习二：计算一段视频加入统一序列后的 token 增长。

练习三：列出多模态 golden request 的字段。

### 13.10.1 模态统一到底统一了什么

“统一”至少有三个层次。第一是接口统一：客户端使用同一套消息和流式事件传递文本、图片、音频和视频；第二是表示统一：不同模态进入相同或可互相访问的 token/latent 主干；第三是目标统一：理解、生成、编辑和工具动作共享一部分训练或推理路径。

一个模型可能只做到第一层，却被产品描述成统一多模态；也可能理解和生成共享主干，但图像仍通过 patchifier 进入。阅读资料时要分别问：统一的对象是什么，哪些模块仍然专用，哪些路径可以共享 KV/state，哪种模态组合真正经过端到端训练。

### 13.10.2 worked example：表格截图问答

任务是从截图中读取第三行金额，和第二行比较，并指出差异来源。一个可靠的处理链路需要同时保留图像区域、OCR 字符、行列位置、问题和计算结果：

```text
image -> visual tokens + OCR spans + region coordinates
      -> multimodal reasoning -> numeric verifier -> answer
```

若只评价最后一句，模型可能在 OCR 错误时碰巧给出正确差值。更细的评估应分别检查第三行定位、金额识别、减法、引用区域和最终解释。这个例子也说明统一 token 流不等于所有问题都由语言模型单独解决，数值和几何验证仍然有价值。

### 13.10.3 模态之间的干扰

统一主干会让不同模态共享容量，也会带来竞争。高分辨率图像产生大量 patch，可能稀释文本问题；视频的重复帧可能占满窗口；OCR 噪声可能覆盖真实图像证据。训练数据比例和 attention mask 决定模型是学会互补还是互相干扰。

可以做模态消融：只给图像、只给 OCR、图像加 OCR、图像加错误 OCR、低分辨率和高分辨率。若加入 OCR 后总体分数升高但图文冲突任务下降，说明模型过度依赖文字转写；若高分辨率只提高局部 OCR 而显著增加延迟，路由应按任务选择分辨率。

### 13.10.4 训练与部署的共同约束

统一模型的训练样本必须记录模态顺序、分辨率、帧率、音频采样和目标类型。部署的 processor 也必须复现这些约定。训练时图像 token 在文本之前，线上却把 placeholder 放在文本之后，模型可能仍能生成回答，但位置和引用行为会发生变化。

因此 golden request 不仅保存原始媒体，还要保存媒体 hash、processor revision、token/patch 数、position、mask、输出 item 和验证结果。只保存图片 URL 不足以复现一次多模态事故。

### 13.10.5 统一不是免除专用模块

高风险 OCR、音频转写、视频时间定位、内容安全和工具权限仍可能需要专用模型或规则。统一主干的价值是减少不必要的模态桥接、共享信息路由和能力组合，不是把所有专用验证器都删除。工程选择要以任务质量、token budget、延迟、隐私和可维护性共同决定。

## 13.11 统一 token 流的信息损失

统一序列把视觉、音频和文本交给共同 backbone，但统一不代表每种模态都保留同样的细节。图像 patch、音频帧和视频 token 仍需要采样、压缩和位置标记；压缩过度会损害 OCR、时间定位和空间关系。

评估时分别测主题理解、细粒度数字、坐标、时间戳和跨模态冲突。若主题分数高而坐标低，优先检查 processor、token budget 和位置，而不是只换语言模型。

## 13.12 统一 token 流的训练接口

统一序列的关键不是把图片文件名插入文本，而是定义媒体 token 的生成、位置、损失和生成目标。理解任务可能只监督文本答案，生成任务则还要监督图像、音频或视频 token；不同目标的梯度路径会影响共享主干学到什么。

一个抽象训练序列可以写成：

~~~text
text tokens + media tokens + instruction tokens + target tokens
~~~

需要明确哪些 token 参与 causal attention、哪些 token 只作为条件、哪些位置可以跨模态读取。接口统一之后，模态边界反而更容易被错误模板和 token budget 隐藏。

## 13.13 encoder-free 的代价与补偿

取消专用 encoder 可能减少桥接层和模态间的信息损失，但会把视觉/音频的局部结构、压缩和分辨率处理交给统一主干。主干需要处理更长序列和不同统计分布，训练数据、位置机制、计算量和 serving 都会变复杂。

对图中文字、空间坐标、长视频时间点等任务，仍可能需要 OCR、区域 token、时间检索或专用解析器。统一主干不等于所有模态任务共享同一有效分辨率。

## 13.14 多模态统一的证据验收条件

评估至少拆成接口、解析、对齐、推理和生成五层。对同一媒体改变分辨率、帧采样、token 顺序和问题表述，分别测 OCR、空间/时间定位、跨模态冲突、引用和输出格式。

缓存和恢复还要绑定媒体 processor、采样参数、模态 position、用户权限和媒体 revision。只有自然语言答案正确而无法回放原始区域的系统，不适合高风险多模态任务。

## 13.15 统一 token 流与专用模块的取舍

统一序列并不意味着所有模态都必须使用同一种处理方式。图像 patch、音频 codec、视频帧和文本 token 的统计结构、时间尺度和噪声不同。统一流可以让模型在一个自回归接口中处理跨模态关系，但预处理、压缩、对齐和质量检查仍可能需要专用模块。

工程上可以把系统拆成“统一生成主干”和“模态输入适配层”。适配层负责媒体解码、分辨率/帧率选择、特殊 token、时间戳和错误检测；主干负责跨模态建模。这样做的代价是接口更复杂，但比把所有媒体错误都归因于语言模型更容易排查。

## 13.16 一个表格截图的端到端例子

用户上传一张财务表并询问“第二季度毛利率是否高于第一季度”。系统首先检查图片是否完整、方向是否正确、分辨率是否足够；随后将表格区域转成视觉 token，并保留行列位置、单位和页码。模型输出不仅要有结论，还要能指出使用了哪些单元格。

如果统一 token 流把小数点、负号或列标题压缩掉，语言模型可能生成语法正确但数值错误的答案。评测应分别测文字识别、表格结构、数值计算、证据定位和最终结论，而不是只用一个 VQA accuracy。需要高可信度时，数值计算可以交给受限工具，模型负责解释和引用。

## 13.17 统一多模态的证据边界

“encoder-free”或“unified”描述的是公开架构口径，不自动说明所有视觉/音频处理都没有任何专用编码、压缩或预处理。模型卡明确披露的 token 流、训练模态和接口可以作为事实；具体层间融合、媒体 tokenizer 细节和内部 kernel 若未公开，应保持限定语。

部署时还要同时验证 processor、tokenizer、special token、媒体占位符、位置编码、mask、stream event 和最大预算。模型权重能加载不等于图像问答、视频时间定位和音频流式协议都兼容。

## 13.18 统一多模态的回放契约

统一 token 流上线前，要把媒体处理和文本生成放进同一个可回放请求。最小 manifest 应保存媒体 hash、媒体类型、尺寸或采样率、processor revision、special token、token 数、模态位置、attention mask、模型 revision、输出事件和验证结果。只保存原始图片 URL 或音频路径，无法证明线上是否使用了同一份输入。

总 token 预算可以先做一个保守账本：

```math
T_{\mathrm{total}}
=T_{\mathrm{text}}+T_{\mathrm{image}}
 +T_{\mathrm{audio}}+T_{\mathrm{video}}+T_{\mathrm{output}}
\le T_{\mathrm{context}}.
```

当 `T_total` 超预算时，系统要明确是缩小图片、减少帧、压缩音频、截断文本、转异步，还是拒绝请求。静默截断会让“模型没有理解”与“媒体根本没有送进去”混在一起。

## 13.19 模态消融必须保留反事实

评估统一模型时，至少保留四个反事实：原始媒体、只给文本转写、媒体加转写、媒体加错误转写。它们能区分模型依赖的证据路径。若加入错误 OCR 后答案仍然跟随 OCR，而不是图像，说明统一主干存在文字捷径；若去掉 OCR 后空间定位骤降，可能需要专用视觉区域 token，而不是简单扩大语言模型。

对视频还要改变帧率和证据帧位置；对音频要改变采样率、背景噪声和说话人重叠。每个变体记录 OCR 字段召回、时间定位误差、空间 IoU、数值 exact match、引用支持率和 token/秒成本。平均 VQA 分数无法暴露这些模态之间的替代关系。

## 13.20 统一多模态事故的归因顺序

出现“图像问答突然变差”时，按以下顺序定位：先检查媒体是否可解码，再检查 processor 是否产生预期 token 数，然后检查 placeholder、position 和 mask，接着比较模态 encoder/统一主干的中间表示，最后才检查生成和后处理。若只看最终文本，所有问题都会看起来像模型幻觉。

例如，同一版本的文本问题正常、图片问题在高分辨率时失败，优先查视觉 token budget、显存和截断；同一图片在离线正常、流式线上失败，优先查 chunk 顺序、事件拼接和媒体缓存；只有某一租户失败，则还要查媒体权限和缓存隔离。每类故障都应有一个能重放的 golden request。

## 13.21 一个统一序列的容量账本

假设一张图片被切成 `32 x 32` 个 patch，视频有 16 帧，每帧使用同样的 patch 数，文本和输出各占 1,000 token，则仅图像和视频就有 `1024 + 16 x 1024 = 17,408` 个视觉 token。若上下文预算是 32K，留给历史、系统提示和输出的空间已经很有限。这个数量关系说明，统一 token 流首先是预算问题，其次才是架构口号。

工程上应分别记录媒体 token、文本 token、输出 token、KV bytes 和 processor 时间。降低分辨率可能提高容量，却损失小字；减少帧数可能降低成本，却丢失关键动作。正确做法是按任务选择分辨率、帧率和区域，而不是给所有请求固定最大配置。

## 13.22 模态对齐的反事实检查

图表问答可以设计四组输入：原图、原图加正确 OCR、原图加一处错误 OCR、只给 OCR。若模型在错误 OCR 版本中稳定跟随错误数字，说明统一主干存在文字捷径；若只给 OCR 就已经完成任务，图像路径可能没有贡献；若原图和正确 OCR 都失败，优先查布局 token、分辨率和 mask，而不是立即扩大语言模型。

视频任务还要移动关键帧位置，音频任务要改变采样率、背景噪声和说话人重叠。记录字段级 exact match、坐标误差、时间定位误差、引用支持率、token 数和 p95，比一条自然语言总分更能解释统一架构的真实收益。

## 13.23 生成目标与理解目标的冲突

理解任务通常只要求模型根据媒体生成文本答案，生成任务还要预测图像、音频或视频 token。若共享主干的损失写成：

```math
\mathcal{L}
=\lambda_{\mathrm{text}}\mathcal{L}_{\mathrm{text}}
 +\lambda_{\mathrm{media}}\mathcal{L}_{\mathrm{media}}
 +\lambda_{\mathrm{align}}\mathcal{L}_{\mathrm{align}},
```

不同权重会改变模型对细节、流畅度和跨模态对齐的偏好。只看到统一接口不能推出统一目标；需要检查训练数据、哪些 token 参与 loss、理解/生成是否共享参数以及有没有模态专用 decoder。

## 13.24 事故回放与证据边界

多模态事故回放必须包含媒体 hash、尺寸/帧率/采样率、processor revision、special token、模态位置、attention mask、模型 revision、输出事件和验证结果。若只保存一张被后处理过的图片，无法判断线上是否发生了缩放、裁剪、帧丢失或静默截断。

“encoder-free”只能写到公开资料明确支持的层级。论文或模型卡若只说明统一 token/latent 主干，正文就不能进一步断言完全没有 patchifier、codec、投影或专用安全模块。架构判断应把已披露事实、受控实验观察和未公开内部细节分开。

## 13.25 统一 token 流的训练冲突

理解和生成可以共享 token/latent 主干，但它们的监督信号不同。理解任务希望模型从视觉、音频或文本中抽取可判定事实，生成任务希望输出连续、可控且高质量的序列。若所有模态和目标都用同一种 loss，数据比例、序列长度和梯度尺度会改变模型的偏好。

教学上可以把总目标写成：

```math
\mathcal{L}
=\lambda_{\mathrm{understand}}\mathcal{L}_{\mathrm{understand}}
+\lambda_{\mathrm{generate}}\mathcal{L}_{\mathrm{generate}}
+\lambda_{\mathrm{align}}\mathcal{L}_{\mathrm{align}}.
```

具体模型是否使用这些独立项要以公开资料为准；公式的作用是说明“统一表示”不等于“统一训练目标”。

## 13.26 encoder-free 口径的三层判断

第一层是接口：输入是否被转成统一序列；第二层是结构：是否存在独立视觉 encoder、patch projection、audio codec 或专用 decoder；第三层是训练：模态是否共享主干和目标。产品页通常只能确认第一层，模型卡或代码可能确认第二层，完整技术报告才可能解释第三层。

因此看到“encoder-free”时，不能据此推断没有任何模态预处理，也不能推断所有模态完全共享参数。严谨写法应把公开事实、受控实验和未知内部细节分开。

## 13.27 统一多模态的容量和安全实验

同一请求中加入图片、音频或视频会消耗 token/latent budget，也会扩大隐私和 prompt injection 面。评测要按媒体尺寸、帧数、模态组合、OCR 密度、敏感内容和输出任务分桶，记录关键信息召回、跨模态一致性、TTFT、显存、拒答和媒体留存。

## 13.28 小结与资料边界

统一多模态的核心是信息路由和表示共享，不是简单删除 encoder。它可能提高跨模态交互，却把 token budget、位置 mask、processor、隐私和 serving 成本推到前台。具体模型是否真正 encoder-free，以官方模型卡、技术报告和 processor 实现为准。
