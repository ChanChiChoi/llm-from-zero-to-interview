# 第 14 章 Native Multimodal Token Budget：一张图片到底占多少上下文

## 14.1 文字 token 不是全部输入

当模型同时接收文字、图片、音频和视频时，context budget 不能只看 tokenizer 生成的文字 token。图片会被切成 patch 或视觉 token，视频还要乘以帧数，音频可能经过时间下采样。不同 processor、分辨率和 detail 设置会改变最终长度。

“支持 128K context”如果没有说明媒体 token 如何计数，就无法直接判断能放多少图片、视频或工具历史。Native multimodal token budget 的重点，是把模态内容放入同一个可计算、可限制、可观测的预算。

## 14.2 一个总长度公式

设文字 token 数为 `T_text`，图像数量为 `m`，第 `i` 张图产生 `N_i^{img}` 个视觉 token，音频/视频 token 为 `N_j^{media}`，则：

```math
T_{\mathrm{total}}
=T_{\mathrm{text}}+\sum_{i=1}^{m}N_i^{\mathrm{img}}
+\sum_jN_j^{\mathrm{media}}+T_{\mathrm{special}}
```

如果图像 patch 大小为 `p\times p`，分辨率近似为 `H\times W`，理想 patch 数约为：

```math
N_{\mathrm{patch}}\approx\left\lceil\frac{H}{p}\right\rceil\left\lceil\frac{W}{p}\right\rceil
```

真实 processor 可能 resize、合并 patch、插入换行/行列 token 或使用多尺度，因此公式只是预算起点。

## 14.3 分辨率和 detail 的 trade-off

低分辨率减少 token、显存和延迟，却可能无法读取小字体和表格；高分辨率提高细节，代价是 prefill、KV、带宽和上下文占用。产品常把 `low/high detail` 作为策略，但它必须与任务匹配。

例如头像分类不需要高分辨率，发票 OCR 和代码截图可能需要局部放大。盲目把所有图片设为 high，会让多轮 Agent 更快触及 context limit。

## 14.4 一个预算例子

用户文字 4K token，上传 4 张图，每张 processor 产生 2K 视觉 token，再有 20K 工具历史：

```math
T_{\mathrm{total}}=4K+4\times2K+20K=32K
```

如果服务的有效预算是 32K，还要给 system prompt、输出和 reasoning 留空间，实际请求可能已经超限。应用应在发送前计数，决定压缩工具历史、降低图片分辨率、分批处理或切换异步路径。

## 14.5 Native budget 与 RAG/切图

长文档图像或视频可以先做检索/关键帧选择，再送入模型。这样降低 token，却可能漏掉关键证据。全量输入适合需要完整关系的审计，选择性输入适合重复查询和成本敏感场景。

预算路由要记录被丢弃的页面、帧和图像区域，不能让模型在不知情的情况下把“没有看到”当成“没有发生”。高风险结论应显示覆盖范围并支持人工查看原图。

## 14.6 多模态 KV 和缓存

视觉 token 一旦进入 decoder，也会占用 KV 或其他 state。prefix cache 能否复用图像前缀取决于媒体 hash、processor revision、resize、position 和租户权限。图片相同但 detail 不同，不能复用同一表示。

视频逐帧处理会快速放大 cache；可以采用滑动窗口、关键帧、latent cache 或异步摘要，但每条路径都要测时序信息和引用。

## 14.7 评估 token budget

按文字长度、图片数、分辨率、视频帧数、音频时长和工具历史分桶。记录 processor token 数、实际模型 token 数、截断、OCR/空间准确、引用、TTFT、峰值显存、p99 和单位成功成本。

测试预算边界：刚好能接收、接收后输出空间不足、媒体被截断、工具历史被压缩和取消。客户端声称的文件大小不能替代服务端实际 token 记录。

## 14.8 常见失败

按字符数计费；忽略 special/media token；图片静默 resize；超过预算后静默删图；prefix cache hash 不含 processor；视频帧采样不稳定；只测图文单轮不测多轮和工具；模型“支持图片”却不支持目标分辨率/格式。

## 14.9 面试回答与练习

回答“多模态输入如何计算 context”时，应把文字、图像 patch、音频/视频 token 和 special token 相加，结合 processor、分辨率、帧率和输出/推理预算；发送前预估，服务端记录实际 token，超预算选择降采样、检索、分批或人工，并报告覆盖范围。

练习一：给定图像分辨率和 patch size 估算视觉 token。

练习二：设计高分辨率发票 OCR 的预算路由。

练习三：列出媒体 prefix cache 的 key 字段。

### 14.9.1 多模态 token 预算的四个组成

服务端的总预算至少包括文字 token、媒体 token、协议 token 和输出/推理预留：

```math
T_{\mathrm{request}}
=T_{\mathrm{text}}+T_{\mathrm{media}}+T_{\mathrm{protocol}}
+T_{\mathrm{output}}+T_{\mathrm{reason}}
```

若只计算用户输入而不预留输出，服务端可能在生成中途截断；若把产品文档中的“文本 context”直接当作媒体 token 预算，图片、视频和音频会静默触发降采样或丢弃。

### 14.9.2 worked example：一张发票和一段视频

设图像被切成 `32 x 32` patch，输入尺寸为 `2048 x 1536`，则视觉 patch 数约为：

```math
N_{\mathrm{patch}}
=\left\lceil\frac{2048}{32}\right\rceil
 \left\lceil\frac{1536}{32}\right\rceil
=64\times48=3072
```

如果 processor 还加入缩略图、边界 token 和 OCR 辅助 token，实际媒体 token 会更高。视频再乘以帧数，预算很快被消耗。系统应在发送前做估算，在服务端记录 processor 后的真实数量，并在用户可接受的质量损失范围内选择分辨率、帧率或分块。

### 14.9.3 分辨率和帧率不是越高越好

高分辨率提高小字体和细节识别，但增加 prefill、KV 和显存；高帧率提高动作覆盖，但会引入相邻重复帧和时序噪声。可按任务做预算路由：票据 OCR 保留局部高分辨率，长视频先做低帧率检索再对候选时间段精采样，普通图片问答使用中等分辨率。

路由必须注明覆盖范围。若系统只看了视频的 10% 帧，回答应知道这个限制；不能把“未采样到关键事件”写成“视频中没有该事件”。

### 14.9.4 processor 是协议的一部分

同一张图片用不同 processor revision、resize 策略、颜色空间或 patchifier，得到的媒体 token 可能不同。缓存 key 要包含媒体 hash、processor revision、分辨率、帧采样、语言和模型 revision。否则旧的视觉 embedding 或 prefix cache 可能被错误复用。

多模态流式接口还要处理媒体上传、编码、首个文本事件、取消和部分输出。取消时应释放媒体 buffer、临时视觉状态和 KV；健康检查应验证真实 processor 和目标模态，而不是只测试一条文本请求。

### 14.9.5 超预算后的用户可见语义

超过预算时可以降采样、分批、检索、摘要、转异步或请求用户缩小输入。每种路径都要说明信息损失：哪些区域被跳过、哪些帧没有分析、摘要是否替代原文。对安全和医疗任务，宁可转人工或拒绝，也不能静默丢掉关键媒体。

## 14.10 token budget 的动态分配

静态按比例分配文本、图像、音频和视频 token 可能浪费预算。查询如果要求读取发票数字，应提高图像细节和 OCR 预算；如果只要视频主题摘要，可以降低帧率并保留关键帧。

一个风险感知的预算可以写成：

~~~math
B_m=\frac{w_m I_m}{\sum_j w_j I_j}B_{\mathrm{total}}
~~~

I_m 表示模态对当前任务的信息重要度。实际系统还要限制最小分辨率、最大帧数和回退成本。

## 14.11 token budget 的组成

多模态上下文预算不能只用图片数量估算。总预算至少包括文本 token、视觉 patch 或视觉 token、音频帧、视频帧、特殊分隔符、工具结果和输出预算：

~~~math
T_{\mathrm{total}}
=T_{\mathrm{text}}+T_{\mathrm{vision}}
+T_{\mathrm{audio}}+T_{\mathrm{video}}
+T_{\mathrm{special}}+T_{\mathrm{tool}}+T_{\mathrm{output}}
~~~

同一张图片在不同分辨率、裁剪策略和 processor 下可能占用不同 token。长视频还要在帧数、时间覆盖和局部细节之间取舍。

## 14.12 动态分辨率和质量曲线

动态 token budget 可以先低分辨率扫描，再对疑似关键区域或时间段提高分辨率。这样把预算从平均分配改成 query-driven 分配，但会增加采样器、回读、缓存和可复现性要求。

评估应画 token 数与 OCR、空间定位、图表数值、时间定位、延迟和显存的曲线。压缩 token 后主题回答保持不变，不代表关键数字和坐标仍然可靠。

## 14.13 多模态 cache 和预算约束

媒体 token、encoder 输出、projector 输出和文本 KV 的缓存生命周期不同。复用前要检查媒体 revision、processor、分辨率、帧采样、position、租户和模型版本。请求预算不足时应降采样、回读关键区域、排队或拒绝，而不是静默截断关键证据。

线上 trace 记录每种模态的 token 数、编码耗时、cache 命中、回读次数、输出长度和失败原因，才能解释“同一图片为什么这次更慢或更不准”。

## 14.14 token budget 和质量回退

预算不足时不能只按序列末尾截断，因为关键视觉区域、时间点和文本限定条件可能被删掉。更稳妥的策略是保留问题相关区域、证据窗口和来源字段，再对低价值媒体做降采样或摘要。

每种预算策略都要报告被保留和被删除的证据范围。若模型仍能回答主题却无法指出数字或坐标，说明预算策略损害了高价值字段。

## 14.15 端到端预算实验

固定模型和任务，逐步改变文本、图片分辨率、视频帧数、音频窗口和输出预算，记录：

~~~text
input tokens
media encode time
cache bytes
TTFT
TPOT
OCR/grounding accuracy
citation support
~~~

实验应包括单模态、混合模态、长媒体、中间证据和缓存复用。接口接受更长输入不等于这些任务都能在可接受成本内完成。

## 14.16 动态预算不是简单截断

当输入超出预算时，系统可以缩小图片、降低视频帧率、摘要一部分文本、切换检索或请求用户补充范围。但每种策略损失的信息不同：缩小图片可能损失小字，减少帧率可能丢掉动作变化，摘要可能丢掉否定条件，直接截断则可能删除关键证据。

一个动态控制器可以把预算分成文本、图像、音频、视频和输出五个桶：

```math
\sum_m B_m+B_{\mathrm{out}}\le B_{\mathrm{context}},
\qquad
m\in\{\mathrm{text},\mathrm{image},\mathrm{audio},\mathrm{video}\}
```

调整 `B_m` 时应参考任务类型和证据风险，而不是只按媒体大小比例分配。审计发票时文字和局部清晰度可能优先；视频动作识别时帧间变化和时间覆盖更重要。

## 14.17 用质量曲线决定回退路径

预算实验应改变一个因素并记录质量曲线：分辨率、帧数、音频采样、文本 chunk、输出预算和并发。对每个配置测输入保真率、证据召回、答案正确、引用支持、格式合法、TTFT、TPOT 和成本。

如果降低分辨率只影响 OCR，而降低帧率影响事件顺序，就可以按任务路由不同回退，而不是统一把所有媒体压缩到同一个档位。用户可见的降级也要明确说明，例如“已按 2 秒间隔抽帧，可能遗漏短暂动作”，不能悄悄改变语义后仍声称完整理解。

## 14.18 先测 processor，再谈媒体 token

模型卡中的 context length 是上限口径，processor 产生多少视觉、音频或视频 token 则是输入协议口径。两者之间还隔着 resize、crop、patchify、帧采样、特殊 token、模态分隔符和模型内部压缩。工程上应为每个 processor revision 建立一个可运行的 token audit：给定固定媒体，记录预处理后的尺寸、帧数、媒体 token、文本 token 和最终序列长度。

即使两个模型都宣传支持图像输入，也不能假设同一张图片占用相同预算。一个系统如果只用图片文件大小估算成本，会漏掉“压缩后的 JPEG 很小但分辨率很高”的情况；如果只用原始像素估算，又可能过度保守。真正可用的估算必须调用目标 processor 或与其完全一致的离线实现。

## 14.19 用质量曲线而不是单点选择预算

设预算配置为 `b`，任务质量为 `Q(b)`，延迟和成本分别为 `L(b)`、`C(b)`。部署选择不是寻找质量最高的配置，而是在约束下选择可接受点：

~~~math
b^*=\arg\max_b Q(b)
\quad\mathrm{s.t.}\quad
L(b)\le L_{\max},\quad
C(b)\le C_{\max},\quad
T(b)\le T_{\max}.
~~~

`Q` 还要拆成关键字段准确率、空间/时间证据召回、引用支持和安全召回。低分辨率可能只损害小字 OCR，高帧率下降可能只损害短暂动作；一个总分会掩盖这种差异。部署前画出配置到质量、延迟和显存的曲线，才能为不同任务选择不同回退。

## 14.20 多模态 cache 的 key 和失效

多模态缓存至少有媒体字节、视觉 encoder 输出、projector 输出、文本 prefix 和完整请求状态几种层次。它们不能共享一个模糊的 `image_id`。一个可审计的 cache key 可以抽象为：

~~~math
K=H(\mathrm{media\_digest},\mathrm{processor\_revision},
\mathrm{resize},\mathrm{sampling},\mathrm{model\_revision},
\mathrm{tenant},\mathrm{position\_schema}).
~~~

其中 `H` 是稳定哈希。只要 processor、模型、帧采样、位置 schema 或租户隔离边界变化，就应视为不同 key。共享公共图片的视觉 embedding 也不等于可以共享包含私有文本、用户问题或工具结果的 KV。

缓存命中率高但答案变旧，通常是失效策略错误；缓存命中率低但每次都重新编码，通常是 key 过度包含请求级字段。排查时要把媒体编码时间、cache 层级、命中/失效原因和最终质量一起记录。

## 14.21 worked example：长视频的两阶段采样

假设一段 20 分钟视频以每秒 2 帧扫描，再从候选时间段抽取 8 帧/秒。第一阶段有 `20\times60\times2=2400` 帧，第二阶段只对 30 秒候选窗口精采样，新增 `30\times8=240` 帧。这样的路线节省了大部分媒体 token，但它不能声称对全视频每个瞬间都做了同等精度分析。

输出必须携带覆盖说明：粗扫的时间间隔、候选窗口、精采样版本和未覆盖区域。若用户问“视频中是否出现过一个只持续半秒的动作”，系统应先判断粗采样是否可能漏掉它；必要时扩大候选窗口或转异步精查，而不是把采样遗漏回答成否定事实。

对于发票、合同和医学影像，策略相反：先确定关键页、字段或区域，再提升局部分辨率。媒体预算应该追随信息密度和错误代价，而不是简单地对所有像素平均分配。

## 14.22 多模态 RAG 中的预算边界

多模态 RAG 常见的错误是先把所有图片、表格和文本检索结果拼进上下文，再让模型自行取舍。更可靠的流程是：先保存媒体 provenance，再按问题检索候选区域，之后执行预算分配和证据压缩，最后把来源、页码、坐标或时间戳随证据传入模型。

如果一张图被压缩成一句摘要，摘要可以帮助主题检索，却不能替代原图中的精确数字、布局和坐标。系统要区分 `discovery representation` 与 `answering representation`：前者可以便宜和粗糙，后者必须满足当前任务的证据精度。

## 14.23 预算回退的失败模式

最危险的回退不是报错，而是静默改变语义：截掉合同最后的否定条款、跳过视频中间的关键帧、把低清小字当作没有内容、丢失音频中的时间顺序，或在 trace 中只记录“输入过长”而不记录实际删掉了什么。

每种回退都要生成 `coverage report`，至少包含保留范围、删除范围、采样间隔、压缩版本、估计 token、实际 token 和是否仍满足关键字段验收条件。对安全、医疗、财务和法律任务，若无法证明关键证据被覆盖，应拒绝自动结论或转人工。

## 14.24 评测和面试的最小闭环

面试中回答“如何控制多模态 token 成本”时，可以按四步展开：先用 processor 测真实 token，再按任务信息密度做分辨率、帧率和区域路由，再用质量曲线决定 cache 和回退，最后用输入保真率、关键字段准确率、证据召回、TTFT、TPOT、显存和单位成功成本验收。

实验至少固定模型 revision、processor revision、媒体内容、文本问题、输出上限和并发，分别比较单模态、混合模态、长媒体、缓存命中和超预算回退。这样得到的结论才可复现，也不会把某次产品接口的 token 计费数字误写成多模态模型的普遍规律。

## 14.25 token budget 的真实分母

多模态请求的总预算可以抽象成：

```math
B_{\mathrm{total}}
=B_{\mathrm{text}}+B_{\mathrm{image}}
+B_{\mathrm{audio}}+B_{\mathrm{video}}
+B_{\mathrm{tool}}+B_{\mathrm{output}}.
```

各项不一定都以同一种 token 计费，但都竞争上下文、显存、prefill 时间和注意力容量。图像分辨率、视频采样、音频帧率和 processor 版本改变了输入预算，不能只看 API 的文字 context limit。

## 14.26 信息密度路由

缩小图片或降低视频帧率可以省预算，也可能删掉关键证据。路由器应先用廉价预览估计信息密度，再决定全图、局部 crop、关键帧或异步处理；对合同金额、坐标、细小文字等高价值区域，宁愿保留局部高分辨率，也不要平均压缩所有内容。

## 14.27 超预算时的明确退化

当预算不足，系统可以分块、先检索、降低媒体采样、转异步或请求用户缩小范围，但必须记录遗漏范围和质量损失。不能把被截断的视频分析写成看过完整视频，也不能把 processor 失败后的空 placeholder 当作真实媒体。

## 14.28 多模态预算的压测矩阵

固定模型、processor、媒体版本、硬件和并发，逐步增加分辨率、帧数、文本历史和工具结果，绘制质量/成本曲线。记录关键字段准确率、证据召回、TTFT、TPOT、显存、p95、cache hit 和失败原因，才能找到可上线的预算而不是最大可接受长度。

## 14.29 小结与资料边界

Native multimodal token budget 把媒体输入变成可管理的上下文资源。真正的长度取决于 processor、分辨率、帧率、special token、工具历史和输出预算；模型卡的文字 context 数字不能单独决定多模态容量。

具体视觉 token 化、音频/视频采样、缓存语义和计费口径以对应模型的 processor、模型卡和 API 文档为准。章节中的两阶段视频采样、质量曲线和 cache key 是通用教学模型，不是某一家模型的内部实现。
