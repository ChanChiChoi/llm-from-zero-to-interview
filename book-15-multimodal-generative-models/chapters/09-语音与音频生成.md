# 第九章：语音与音频生成——从连续波形到实时对话

上一章讨论视频如何把空间信号扩展到时间信号。本章继续研究另一类连续时间信号：声音。语音不仅包含“说了什么”，还包含谁在说、怎么说、在什么环境中说，以及说话过程中的停顿、重音、情绪和非语言声音。音乐、环境音和音效还会引入旋律、节奏、和声、声源混合和长程结构。

语音系统因此不能只被描述成一个文本输入、音频输出的黑盒。一个真正可用的系统必须回答：

1. 连续 waveform 如何被采样、分帧、压缩和重建？
2. ASR 如何从声音中恢复文字，TTS 如何从文字构造语音？
3. audio codec 为什么能把高采样率波形变成可被 Transformer 建模的离散 token？
4. 语义、音色、韵律和声学细节如何分工，又在哪里发生纠缠？
5. 级联语音助手和端到端 speech-to-speech 在延迟、可控性和安全上如何取舍？
6. 如何用 WER、MOS、FAD、说话人相似度、首包延迟和真实任务成功率分别评估系统？

本章的目标不是让读者背诵模型名称，而是建立从信号到系统的责任链。读者应能看出一个音频模型的输入输出、训练目标和适用边界，也应能解释为什么“声音听起来像真人”不能替代内容正确、获得授权和实时可靠。

本章按三条连续链阅读：§§9.0–9.5 从波形、声学表示走到识别与误差测量；§§9.6–9.9 从文本、说话人和韵律条件走到 codec token 生成；§§9.10–9.16 再把这些组件放进实时会话、评估、安全和排障。§9.17 用同一组输入复算前两条链中的采样、帧、codec、WER/CER 和延迟，§9.18 提供迁移练习。

## 9.0 研究对象、资料层级与术语边界

### 9.0.1 语音与音频不是同一个任务

语音是音频的一种，主要由人类发声和语言内容构成；音频还包括音乐、环境声、机械声、动物声和混合录音。语音系统通常关心内容、说话人和交互，通用音频系统还要处理多个声源同时存在的情况。

下面几个任务的输入输出不同：

| 任务 | 输入 | 输出 | 主要难点 |
| --- | --- | --- | --- |
| ASR | 语音或混合录音 | 文本与时间戳 | 口音、噪声、专名、重叠说话 |
| TTS | 文本、说话人或风格条件 | 语音 waveform | 内容、音色、韵律、自然度 |
| 语音转换 | 源语音与目标说话人 | 保留内容的目标音色语音 | 内容和身份解耦 |
| 语音翻译 | 源语音 | 目标文本或目标语音 | 跨语言、延迟和韵律 |
| speech-to-speech | 语音输入 | 语音输出 | 轮次、打断、非语言信息 |
| 音频描述 | 音频 | 文本描述 | 多声源、事件时序、细粒度语义 |
| 音乐生成 | 文本或旋律条件 | 音乐 | 长程结构、版权、风格一致 |
| 音效生成 | 文字或视频动作 | 短音效或环境声 | 事件对齐、声源和空间感 |

把这些任务全部称为“语音生成”会掩盖评估对象的差异。ASR 的主要错误是转写内容不对，TTS 的主要错误可能是读错字、音色漂移或重音不自然，音乐生成则要关注段落结构和重复模式。

### 9.0.2 资料如何支持结论

本章使用不同等级的公开资料：

| 资料 | 能支持的结论 | 不能直接支持的结论 |
| --- | --- | --- |
| 原始论文 | 论文中的模型结构、目标、数据和实验 | 后续产品版本的全部行为 |
| 官方代码与模型卡 | 某个版本的接口、采样率、权重和运行方式 | 任意硬件上的延迟和质量 |
| 评估标准或指标论文 | 指标定义、误差口径和适用边界 | 一个指标等于整体听感 |
| 演示页面 | 公开样例和能力范围 | 样例代表所有语言和输入 |
| 本章教学 demo | 采样点、token、编辑距离和延迟算术 | 真实音质、说话人授权和安全结论 |

阅读模型案例时，要把论文、实现和测量协议分开。原始论文支持作者描述的方法及论文实验，例如 [Whisper](https://arxiv.org/abs/2212.04356v1) 的弱监督 encoder-decoder 路线；模型报告或固定版本代码补充特定实现的输入、输出和运行路径，例如 [Qwen3-ASR 技术报告 v2](https://arxiv.org/abs/2601.21337v2)；评测论文只支持其数据、提示、评估器和测量端点下的结果，例如 [InteractionBench v1](https://arxiv.org/abs/2611.02430v1)。本章的手算值是为解释机制而构造的输入，demo 结果只验证这段教学代码，不代表音质、识别能力、线上延迟或授权状态。

### 9.0.3 初学者地图与工程地图

初学者可以把语音系统理解为三次转换：

~~~text
声音波形
    -> 可学习的声学或语义表示
    -> 文本、音频 token 或共享 latent
    -> waveform、文本或另一种模态
~~~

工程上还要加入时钟和权限：

~~~text
microphone
    -> resample / normalize / VAD
    -> encoder or log-mel features
    -> ASR / speech model / LLM
    -> TTS or codec decoder
    -> speaker, policy, provenance
~~~

每个箭头都可能改变系统行为。重采样会影响高频细节，VAD 会决定是否截断句首，codec 会决定音质和 token 速率，LLM 会改变文本内容，TTS 会改变说话人身份和情绪，发布层还要确认是否有授权和来源记录。

## 9.1 任务总览：内容、身份、韵律和环境

### 9.1.1 语音中有多种信息

一段语音 waveform 同时承载：

1. 语言内容：说了哪些词。
2. 说话人身份：音色、声道特性和发声习惯。
3. 韵律：时长、重音、语调、停顿和节奏。
4. 情绪与副语言信息：笑声、叹气、犹豫和语气。
5. 声学环境：房间混响、背景噪声、麦克风和距离。
6. 事件信息：敲门、脚步、雨声或音乐。

ASR 通常希望保留第一项并弱化其他项；说话人识别关注第二项；TTS 需要按条件重建第一到第四项；音频增强还要处理第五项；音频描述要识别第六项。没有一种表示能在所有任务上都最优。

### 9.1.2 任务条件分布

TTS 可以写成在文本、说话人和风格条件下生成 waveform：

~~~math
x\sim p_\theta(x\mid y,s,r,e),
~~~

其中 y 是文本内容，s 是说话人条件，r 是韵律条件，e 是环境或音频风格条件。ASR 则更像从 waveform 或特征 M 预测文本：

~~~math
y\sim p_\theta(y\mid x)\quad\text{或}\quad y\sim p_\theta(y\mid M).
~~~

同一个模型可能同时支持多项任务，但训练数据和 loss 必须标明每个条件的含义。把“参考音频”同时当作说话人、内容和环境条件，会导致 TTS 复制了参考音频中的词或噪声。

### 9.1.3 语音系统的失败不能只归因于模型

语音错误可能来自：

- 采样率和声道处理错误；
- VAD 过早截断或把噪声当成语音；
- ASR 的语言、标点或词表配置；
- 文本前端没有处理数字、缩写和专名；
- speaker prompt 不足或未授权；
- codec 码率太低；
- streaming 缓冲和打断逻辑错误；
- 评估把中文、英文和代码混用，导致 WER 口径失真。

所以本章每种模型都同时讨论输入契约、输出契约和失败诊断。

## 9.2 Waveform：连续音频的最小表示

### 9.2.1 采样率和采样点

单通道离散 waveform 可以写为：

~~~math
x[0],x[1],\ldots,x[N-1],\qquad x[n]\in\mathbb{R}.
~~~

采样率 r 表示每秒采样点数。时长 D 秒的单通道音频，理想化采样点数为：

~~~math
N=rD.
~~~

16 kHz、3.2 秒的单通道音频有：

~~~math
N=16000\times3.2=51200
~~~

个采样点。双声道会把存储元素量再乘以 2。实际文件还包含容器、编码、padding 和可能的元数据。

### 9.2.2 Nyquist 频率和混叠

采样率 r 能无混叠表示的最高理想频率接近 Nyquist 频率：

~~~math
f_{\mathrm{Nyquist}}=\frac r2.
~~~

16 kHz 采样的理论上限是 8 kHz。若输入包含更高频率而没有在采样前做抗混叠滤波，高频会折叠到低频，采样后无法恢复。重采样不能简单地丢弃或复制数组，还要配合低通滤波。

语音系统常使用 16 kHz 或 24 kHz，音乐和高保真音频可能使用 44.1 kHz、48 kHz 或更高。采样率是模型契约的一部分，不能把一个按 24 kHz 训练的 codec 直接当成 16 kHz codec 使用。

### 9.2.3 量化和削波

文件中的 PCM 通常把连续幅度量化为有限 bit。若 bit depth 为 b，每个采样点可表示的离散级数约为：

~~~math
L=2^b.
~~~

16 bit PCM 每声道约有 65536 个量化级。量化误差会形成噪声；当波形超过允许幅度时会发生 clipping，波峰被截平，后续模型无法知道原来的峰值形状。

工程预处理应记录：

- 输入幅度范围是 [-1,1] 还是整数 PCM；
- 是否做 peak normalization 或 loudness normalization；
- 是否出现 clipping；
- 左右声道是否分别归一化；
- 归一化是否改变了音量关系和说话人特征。

### 9.2.4 原始 waveform 的成本

若 batch 为 B、声道数为 C、采样率为 r、时长为 D，原始元素量是：

~~~math
N_{\mathrm{raw}}=BCrD.
~~~

若每个元素使用 q bit，原始比特数为：

~~~math
S_{\mathrm{raw}}=BCrDq.
~~~

音频的时间长度会线性增加采样点数。与图像不同，采样率通常很高，因此直接在 waveform 上使用标准 token-by-token Transformer 会产生极长序列。

## 9.3 STFT、log-mel 与声学帧

### 9.3.1 短时傅里叶变换

声音的频率随时间变化。STFT 使用窗口 w[n] 在局部时间片上做傅里叶变换：

~~~math
X(m,k)=\sum_{n=0}^{W-1}x[n+mH]w[n]e^{-i2\pi kn/K}.
~~~

W 是窗口长度，H 是 hop size，K 是 FFT 点数，m 是时间帧索引，k 是频率 bin。窗口越长，频率分辨率通常越高，但时间定位更粗；hop 越小，时间帧更多，计算和 token 数更大。

### 9.3.2 帧数的不同口径

若采样点数为 N、窗口长度 W、hop 为 H，不使用 center padding 时，有效帧数可近似为：

~~~math
T_{\mathrm{valid}}=1+\left\lfloor\frac{N-W}{H}\right\rfloor.
~~~

一些实现会在两端 padding，使中心位置覆盖整个音频，此时帧数常近似为：

~~~math
T_{\mathrm{center}}\approx\left\lceil\frac{D}{h}\right\rceil,
~~~

其中 h 是 hop 的秒数。两种数值不一致并不一定是 bug，关键是训练和推理要使用同一套 padding、center 和边界定义。

### 9.3.3 Mel 频谱

先取功率谱或幅度谱，再用 mel filterbank 聚合频率 bin，得到：

~~~math
M\in\mathbb{R}^{F\times T_{\mathrm{audio}}},
~~~

其中 F 是 mel bins 数，T_audio 是时间帧数。常见的 log-mel 特征可以写成：

~~~math
M_{f,t}=\log\left(\epsilon+\sum_k G_{f,k}|X(t,k)|^2\right).
~~~

G_f,k 是第 f 个 mel 滤波器对频率 bin k 的权重，epsilon 防止取对数时出现零。log 压缩动态范围，让强弱差异更适合神经网络。

log-mel 不是 waveform 的无损替代。相位通常没有直接保留，细粒度波形重建需要另一个 vocoder 或 codec。ASR 可以依赖这种特征，因为识别主要需要声学和语言信息；高保真 TTS 则需要更丰富的声学表示。

### 9.3.4 声学帧与 token 速率

若 hop 为 10 ms，声学帧率约为 100 Hz。3.2 秒音频约有 320 个中心填充帧。与 16 kHz 的 51200 个采样点相比，声学帧已经把序列长度压缩了 160 倍，但每帧仍有 80 个 mel bins 或更高维特征。

这解释了为什么 ASR encoder 常先用卷积或下采样进一步减少时间长度；如果直接对 100 Hz 特征做长文本级 self-attention，长录音仍然很贵。

## 9.4 ASR：从声音恢复文字

### 9.4.1 ASR 的概率模型

给定声学特征 M 和文本 token y_1,...,y_U，encoder-decoder ASR 可以写成：

~~~math
p(y_{1:U}\mid M)=\prod_{u=1}^{U}p_\theta(y_u\mid y_{<u},M).
~~~

训练目标是 token 级负对数似然：

~~~math
L_{\mathrm{ASR}}=-\sum_{u=1}^{U}\log p_\theta(y_u\mid y_{<u},M).
~~~

推理时，模型要在准确率、延迟和搜索宽度之间取舍。贪心解码便宜，beam search 可能改善部分准确率，但在流式交互中会增加延迟，并不保证所有语言和噪声条件都更好。

### 9.4.2 CTC、encoder-decoder 和 RNN-T

CTC 为输入帧和输出 token 引入 blank。先把一条帧级路径中的重复标签合并、删除 blank，再映射成文本；训练时把所有能映射到目标文本的路径概率相加，因此不需要逐帧标注对齐。标准 CTC 对给定输入的帧级输出分布作条件独立假设，没有显式的文本前缀预测器；这会限制它直接建模长程标签依赖的方式，但不代表它不能与外部语言模型、上下文偏置或更强 encoder 组合。

encoder-decoder 模型由声学 encoder 和自回归 text decoder 组成，能够利用完整的历史文字上下文，适合离线转写、翻译和多任务输出。代价是 decoder 生成依赖串行 token，流式延迟和长音频缓存需要专门设计。

RNN-T 或其他 transducer 路线在声学输入与已生成文本前缀之间建模联合转导，因而常用于增量识别。它是否真的能流式输出，仍取决于 encoder 能否增量计算、每块可见的未来上下文、预测网络状态缓存、解码策略和端点判断。CTC、RNN-T 这些目标名称本身都不保证低延迟；离线双向 encoder 也可以训练 CTC，而流式模型仍可能需要 lookahead 并延后最终确认。

### 9.4.3 Whisper 与配置化流式 encoder-decoder

[Whisper](https://arxiv.org/abs/2212.04356v1) 公开的是大规模弱监督语音处理路线。其基本数据流是：

~~~text
waveform
    -> log-mel spectrogram
    -> audio encoder
    -> text decoder
    -> transcript / language / task output
~~~

论文摘要报告了多语言、多任务和大规模互联网音频转录训练。这里可以支持的结论是：该论文采用 encoder-decoder 和大规模弱监督训练，并在公开实验中展示鲁棒性；不能把论文中的数据规模或 benchmark 结果直接等同于任何部署版本对所有口音、领域和专名的准确率。

encoder-decoder 也可以在明确的分块和缓存设计下支持流式。例如 [Qwen3-ASR 技术报告 v2](https://arxiv.org/abs/2601.21337v2) 描述了对 Fbank 声学帧做下采样、使用动态 1–8 秒 attention window，并把 streaming 与 offline 都作为其实现路径。这里的关键不是记住一个窗口长度，而是看窗口、块边界和 encoder 状态如何共同决定可见未来与等待时间。报告只支持该模型和推理路径的设计，不能推成所有 encoder-decoder 都可流式，也不能把论文首 token 计时当作客户端首音延迟。

### 9.4.4 自监督声学表征

[wav2vec 2.0](https://arxiv.org/abs/2006.11477) 先从无标注语音学习表征，再使用较少的转写数据微调。它在 latent space 中遮挡输入并进行对比学习，说明语音表示可以从未标注波形中获得，而不必所有小时都带人工文字。

[WavLM](https://arxiv.org/abs/2110.13900) 把 masked speech prediction 与 denoising 结合，目标不只覆盖 ASR，也覆盖说话人、韵律和其他全栈语音任务。自监督表征的关键边界是：预训练目标决定表示保留什么。只优化语音内容的表示，未必保留足够的说话人和情绪信息。

### 9.4.5 口音、噪声和专名

ASR 的错误不能只用一个总体 WER 描述。应按切片记录：

- 语言和方言；
- 近场、远场和电话带宽；
- 背景噪声、混响和重叠说话；
- 数字、单位、代码和专有名词；
- 语速、停顿和口吃；
- 标点、大小写和数字归一化。

模型可能在普通句子上 WER 很低，却把药品名、合同编号和金额读错。业务系统要把高风险词的召回和编辑错误单独计算。

## 9.5 WER、CER 与说话人分离指标

### 9.5.1 编辑距离

给定参考序列 R 和假设序列 H，最小编辑距离允许替换、删除和插入。词错误率为：

~~~math
\mathrm{WER}=\frac{S+D+I}{N_{\mathrm{ref}}},
~~~

其中 S 是替换数，D 是删除数，I 是插入数，N_ref 是参考词数。WER 可能超过 100%，因为插入错误可以多于参考词数。

这个公式要求参考序列至少包含一个词，即 $N_{\mathrm{ref}}>0$。如果没有参考词，系统没有可用于归一化的错误分母，应报告“未定义”并单独记录该样本，而不是把它当成错误率 0。CER 同样要求参考字符数大于零；中文、英文和混合文本还必须先固定字符切分、空格、大小写和标点规范化规则。

字符错误率为：

~~~math
\mathrm{CER}=\frac{S_c+D_c+I_c}{N_{\mathrm{char}}}.
~~~

中文、日文、短命令和混合文本通常需要明确字符切分与规范化规则；英文 WER 也会受到大小写、标点和 contractions 处理影响。

### 9.5.2 WER 不是理解成功率

一个插入逗号的错误与把“开灯”转成“关灯”的错误，在 WER 中可能都只贡献一次编辑，但业务风险完全不同。2026 年的 [mu-bench v1](https://arxiv.org/abs/2609.32082v1) 用电话场景中的姓名、联系方式、日期、金额和确认码补充普通转写指标，并提出依赖 rubric 和 LLM judge 的 utterance error rate（UER）。作者在 1,847 条人工评分样本上报告 UER 与人工重大/非重大错误标签的 Cohen’s κ 为 0.779；另报告 normalized exact-match WER 为 0.533。更重要的是，reference-guided normalizer 曾把人工判为重大错误的 263 条样本中的 12 条改写成参考答案。这个例子说明：规范化器可以修正格式差异，也可能掩盖识别错误，所以评估必须保留原始识别、规范化后文本和高风险字段的独立结果。该预印本只覆盖其虚构银行通话、五种 locale、人工评分子集和指定 judge/normalizer，不是通用 ASR 排名。

对于指令系统，应同时测：

- 指令意图准确率；
- 槽位和实体准确率；
- 否定词和数值准确率；
- 高风险命令的误触发率；
- 端点和时间戳质量。

如果下游 LLM 能从错误转写中恢复一部分意图，整体任务成功率可能高于 WER 直觉；如果错误触发了错误工具，低 WER 也不能证明安全。

### 9.5.3 多说话人和 DER

多说话人转写需要同时判断“说了什么”和“谁在说”。说话人分离常用 diarization error rate：

~~~math
\mathrm{DER}=\frac{T_{\mathrm{miss}}+T_{\mathrm{false}}+T_{\mathrm{conf}}}{T_{\mathrm{speech}}}.
~~~

T_miss 是漏检语音时间，T_false 是把非语音当成语音的时间，T_conf 是说话人标签错误时间，T_speech 是参考语音时间。DER 依赖 collar、重叠说话处理和说话人数量设定，比较时必须记录口径。

## 9.6 TTS：文本、音色和韵律的联合生成

### 9.6.1 TTS 的条件分解

TTS 输入文本不只决定 phoneme 序列，还要经过文本前端处理数字、缩写、标点、多音字和语言。一个更完整的数据流是：

~~~text
raw text
    -> normalization / grapheme-to-phoneme
    -> content representation
    -> duration and prosody condition
    -> acoustic or codec generator
    -> vocoder / codec decoder
    -> waveform
~~~

系统需要分别回答：

1. 文字有没有读对；
2. 谁在说；
3. 语速、重音和停顿是否符合句法；
4. 情绪和风格是否符合条件；
5. waveform 是否有噪声、金属感和断裂；
6. 生成速度能否支撑实时播放。

### 9.6.2 传统声学模型与 vocoder

传统 TTS 常先预测 mel spectrogram，再由 vocoder 生成 waveform：

~~~math
\hat{M}=A_\theta(y,s,r),\qquad \hat{x}=V_\psi(\hat{M}).
~~~

A_theta 是 acoustic model，V_psi 是 vocoder，y 是文本，s 是说话人条件，r 是韵律条件。分阶段的好处是模块可替换、错误容易定位；代价是声学特征成为接口，信息损失和误差会在阶段之间传递。

### 9.6.3 自回归、非自回归、diffusion 与 flow

自回归 TTS 逐步生成声学帧或 audio token，长文本的延迟较高，但可以使用历史上下文塑造连贯韵律。非自回归 TTS 并行生成多个时间位置，速度更快，但需要额外的 duration、alignment 或 teacher 机制。

扩散或 flow matching 可以在连续 latent 或声学表示上生成多样化结果，对自然度、韵律和零样本说话人适配有帮助，但采样步数、ODE 求解和条件一致性会影响延迟。系统应报告实际采样步数和硬件，不把算法名称直接当成速度保证。

同一代 TTS 也可能采用不同 token 组织。[Qwen3-TTS 技术报告 v1](https://arxiv.org/abs/2601.15621v1) 描述了 25 Hz 单码本、分块 flow-matching DiT 路线，以及 12.5 Hz 多码本语义/声学双轨与 MTP 路线；两者的解码器和并行方式也不同。作者报告的首包延迟绑定其 checkpoint、chunk、推理设置和首包定义。这个对照表明“用了 flow”或“用了 codec token”不能单独回答生成速度、流式稳定性或韵律质量；需要跟踪 token 帧率、每帧码本数、后端 decoder 和首包关键路径。

### 9.6.4 Vocoder 的责任

vocoder 把中间声学表示变成波形，常见路线包括自回归 WaveNet 类模型、GAN vocoder、diffusion vocoder 和 neural codec decoder。它直接影响：

- 高频细节；
- 音色和噪声底；
- 爆破音、齿音和呼吸；
- 长时稳定性；
- 推理速度和内存。

当 TTS 输出有金属声时，原因可能在文本和声学模型，也可能只在 vocoder。应分别评估 mel 重建、waveform 质量和最终听感。

## 9.7 说话人条件与 voice cloning

### 9.7.1 说话人条件的几种形式

说话人条件可以是：

1. 预先注册的 speaker id；
2. 说话人 embedding；
3. 一段参考 waveform；
4. 参考语音的 codec 或 semantic token；
5. 文本和参考音频组成的 in-context prompt。

参考音频可能同时包含音色、环境、情绪和说话内容。模型必须学习哪些信息应该迁移，哪些信息应该丢弃。若参考音频中有背景音乐，生成结果可能把音乐也带入；若参考音频内容与目标文本混淆，可能出现读词泄漏。

### 9.7.2 相似度、内容和风格的冲突

可把 TTS 质量抽象为：

~~~math
Q_{\mathrm{TTS}}=
\lambda_cQ_{\mathrm{content}}+
\lambda_sQ_{\mathrm{speaker}}+
\lambda_pQ_{\mathrm{prosody}}+
\lambda_aQ_{\mathrm{audio}}.
~~~

提高 speaker similarity 不一定提高内容可懂度；强行保持参考语音的 prosody 可能与新文本的句法冲突；过度追求音频高频细节可能增加噪声和不稳定。真实评估要分别测每项，不把一个总分当作唯一目标。

若要把加权式转成可计算目标，四个分数必须先映射到可比较的尺度，并说明权重如何选；否则相加的数值没有稳定含义。工程评估通常保留各分项和约束，例如先要求内容错误低于门槛，再在通过的候选中比较音色和韵律，而不是让音色高分抵消读错文本。

### 9.7.3 VALL-E 的 codec language model 思路

[VALL-E](https://arxiv.org/abs/2301.02111) 把 TTS 组织成基于 neural codec 离散代码的条件语言建模，并使用短参考录音作为 acoustic prompt。论文支持的核心思想是：说话人和环境信息可以通过 codec token prompt 进入语言模型，而不是只用固定 speaker id。

这条路线让零样本和 in-context 说话人适配更自然，也把 TTS 的风险扩展到“任何短录音都可能成为身份条件”。论文中的实验和样例不等于目标产品已取得所有说话人的授权，也不等于跨语言、长文本和情绪控制都稳定。

### 9.7.4 NaturalSpeech 2 与连续 latent

[NaturalSpeech 2](https://arxiv.org/abs/2304.09116) 论文摘要描述了在 neural audio codec 的量化 latent 上使用 diffusion 生成，并通过 speech prompt 和 duration/pitch predictor 提升零样本语音和歌声合成。它代表的不是“离散 token 一定更好”或“连续 latent 一定更好”，而是把内容、韵律和声学生成拆到适合各自建模的空间。

选择离散或连续表示要看：序列长度、可控性、重建质量、长程结构、采样速度和数据标注。单独比较模型参数量没有意义。

### 9.7.5 授权应成为模型输入的一部分

在允许使用参考声音的系统中，授权信息不能只放在产品文档里。样本或请求应至少带有：

- 说话人身份和授权主体；
- 授权范围：合成、编辑、商业发布或内部测试；
- 有效期和撤回状态；
- 参考音频的来源和版本；
- 生成结果的 provenance；
- 高风险文本和发布渠道限制。

如果授权状态是布尔值，模型和服务层都应检查；仅在 UI 上显示一个“已同意”复选框不能形成可审计的授权链。

## 9.8 Audio codec：把波形压缩成可建模的 token

### 9.8.1 Codec 的基本数据流

neural audio codec 可以写成：

~~~text
waveform
    -> encoder
    -> continuous latent
    -> quantizer / codebooks
    -> discrete codec tokens
    -> decoder
    -> reconstructed waveform
~~~

编码器把高采样率 waveform 压缩成低速率 latent，量化器把连续向量映射到 codebook entries，解码器再恢复音频。codec 的目标不是理解语言，而是在给定码率下尽量保留听感和任务相关信息。

### 9.8.2 Residual vector quantization

残差向量量化使用多个 codebook 逐层逼近 latent。对输入向量 z，第一层选择最接近的 code e_1，残差为：

~~~math
r_1=z-e_1.
~~~

第 k 层继续量化残差：

~~~math
r_k=r_{k-1}-e_k.
~~~

最终重建向量约为：

~~~math
\hat{z}=\sum_{k=1}^{K}e_k.
~~~

K 是 codebook 数。增加 codebook 可以提高重建能力和码率，却会让每个时间位置有更多 token，语言模型的序列也更长。

看一个二维教学例子：设输入 latent 为 $z=[1.2,0.1]$，第一码本候选为 $[1,0]$ 和 $[0,0]$，最近项是 $e_1=[1,0]$，所以残差 $r_1=[0.2,0.1]$。第二码本候选为 $[0,0.1]$ 和 $[0,0]$，最近项是 $e_2=[0,0.1]$；重建为 $[1,0.1]$，残差为 $[0.2,0]$，平方误差为 $0.2^2+0^2=0.04$。若只有第一码本，平方误差是 $0.2^2+0.1^2=0.05$。这个玩具例子说明增加一层码本能继续逼近 latent；真实 codec 的码本通过训练得到，听感是否改善还取决于码率、损失和数据分布。

### 9.8.3 token 速率和码率

若 codec 帧率为 q Hz，每个时间位置有 K 个 codebook，每个 codebook 的大小为 V，则每秒 token 数约为：

~~~math
R_{\mathrm{token}}=qK.
~~~

若每个 code 用 $\log_2 V$ bit，且不考虑熵编码和容器开销，理想化固定长度码率为：

~~~math
R_{\mathrm{bit}}=qK\log_2V.
~~~

3.2 秒、50 Hz、4 个 codebook 的 token 数为：

~~~math
N_{\mathrm{codec}}=\lceil3.2\times50\rceil\times4=640.
~~~

这 640 个 token 只是 codec 层 token，不包含文本、speaker prompt、semantic token 和模型控制 token。

若每个 codebook 有 $V=1024$ 个条目，则每个索引需要 $\log_2 1024=10$ bit；码率为 $50\times4\times10=2000$ bit/s，即理想化 2 kbit/s。3.2 秒需 $640\times10=6400$ bit，也就是 6.4 kbit。这个固定索引账本能解释码率和序列长度怎样随帧率、码本数变化，但不等于实际文件大小或重建质量；具体 codec 还会受 stride、padding、chunk 边界和熵编码影响。

### 9.8.4 SoundStream 与 EnCodec

[SoundStream](https://arxiv.org/abs/2107.03312) 公开了端到端 neural audio codec 和 residual vector quantizer，并讨论可变码率、流式推理和语音、音乐、通用音频的压缩。[EnCodec](https://arxiv.org/abs/2210.13438) 公开了高保真实时 neural audio compression、量化 latent 和多尺度频谱判别训练，并提供开源实现。

这些工作支持“codec 可以成为音频生成模型的离散接口”这一技术路线。它们不支持以下过强结论：所有 codec token 都具有语言语义、所有 codebook 都可以独立解释，或者低码率一定在语音和音乐上同时最优。

### 9.8.5 codec token 不等于 speech semantic token

codec token 主要承担波形重建和声学细节。语义 token 可能更关注内容、事件和长程结构。一个 token 同时包含多种信息时，语言模型很难在长序列中同时保持内容、音色、韵律和高频细节。

因此系统可能使用分层表示：

~~~text
semantic tokens
    -> content and long-range structure
acoustic / codec tokens
    -> speaker, prosody and waveform detail
decoder
    -> audio
~~~

分层表示的代价是两个 token stream 需要时间对齐、条件传递和一致性约束。

## 9.9 Codec language model 与 audio language model

### 9.9.1 语音生成的自回归目标

若文本条件为 u，音频 token 为 a_1,...,a_M，codec language model 可以学习：

~~~math
p(a_{1:M}\mid u)=\prod_{m=1}^{M}p_\theta(a_m\mid u,a_{<m}).
~~~

当每秒有 qK 个 codec token 时，几秒语音也会形成很长的序列。自回归模型需要逐步生成，实时性取决于每秒生成 token 数、模型吞吐和解码并行方式。

### 9.9.2 AudioLM 的分层 token

[AudioLM](https://arxiv.org/abs/2209.03143) 把音频生成视为离散 token 的语言建模，并结合捕捉长程结构的 semantic token 与保留高质量声学细节的 codec token。这个设计解决了一个核心矛盾：低速语义序列适合建模长期结构，高速 codec 序列适合重建听感。

AudioLM 的论文实验还展示了无文字标注的语音延续和音乐延续。这里的关键知识点是 token 层级和功能分工，而不是把一段演示样例当作所有长音频都能保持一致。

### 9.9.3 生成顺序和 codebook 组织

多个 codebook 可以按时间交错、按 codebook 分组，或使用专门的多流模型。不同组织方式会改变：

- 条件依赖的方向；
- 当前 token 能看到多少未来声学信息；
- 生成的并行程度；
- codebook 间的一致性；
- streaming 输出的复杂度。

把二维 codebook 矩阵简单 flatten 成一维序列，会让序列顺序承担额外含义。训练和推理必须使用相同的 flatten、mask 和位置编码规则。

### 9.9.4 SoundStorm 的并行解码

[SoundStorm](https://arxiv.org/abs/2305.09636) 论文描述了从 semantic token 生成 neural audio codec token 的非自回归路线，并使用双向注意力和基于置信度的并行解码。它说明音频 token 生成不一定只能严格逐 token 串行，也可以通过迭代填充换取速度。

并行解码的代价是调度、置信度校准和错误修复更复杂。若某个早期声学 token 被高置信度地填错，后续并行步骤可能围绕错误结果稳定下来。

### 9.9.5 SpeechT5、AudioPaLM 与统一接口

[SpeechT5](https://arxiv.org/abs/2110.07205) 通过共享 encoder-decoder 和模态专用前后端探索语音与文本的统一表示。[AudioPaLM](https://arxiv.org/abs/2306.12925) 把文本语言模型与 AudioLM 路线结合，用于语音理解、生成和语音到语音翻译。

统一架构的价值是共享语言知识和跨模态迁移；困难是文本 token、semantic token 和 codec token 的时间尺度不同，训练数据的标注质量和版权范围也不同。统一接口并不意味着所有模态有相同的信息密度。

### 9.9.6 CosyVoice 的监督 semantic token

[CosyVoice](https://arxiv.org/abs/2407.05407) 论文摘要提出使用来自多语言 ASR 模型、带向量量化的监督 semantic token，再用 LLM 生成 token，并以 conditional flow matching 模型完成 token 到语音的合成。它代表一个值得单独记住的变化：语音 token 不一定完全由无监督 codec 学习，也可以借助监督语义信号提高内容和说话人条件的对齐。

这并不意味着监督 token 在所有场景都优于 codec token。监督信号可能把语言偏置带入音乐、非语言声音和跨域说话人任务，需要按目标任务重新评估。

## 9.10 Speech-to-speech、语音翻译与实时对话

### 9.10.1 级联路线

最常见的语音助手链路是：

~~~text
speech
    -> VAD
    -> ASR
    -> text LLM
    -> text response
    -> TTS
    -> speech
~~~

它的优点是模块职责清晰，可以分别替换 ASR、LLM 和 TTS，也容易保留文本日志和安全审计。缺点是 ASR 错误会传递给 LLM，LLM 输出再经过 TTS，笑声、语气、重叠说话和环境声可能在文本中丢失。

### 9.10.2 端到端路线

端到端 speech-to-speech 可以在音频 token 或共享 latent 中直接建模：

~~~text
input speech tokens + context
    -> multimodal speech model
    -> output speech tokens
    -> codec decoder
~~~

它有机会保留非语言信息，减少显式文本中间层和部分轮次延迟，但安全、可解释性、训练数据、内容审计和错误定位更难。端到端并不自动意味着更低延迟，模型仍受音频 token 速率和生成吞吐限制。

### 9.10.3 Moshi 与 full-duplex 对话

[Moshi](https://arxiv.org/abs/2410.00037) 论文把实时语音对话建模为 speech-text foundation model 和 full-duplex speech-to-speech 框架，讨论并行的用户与系统语音流、重叠说话、打断和语音 token。论文摘要给出的延迟和样例属于该论文系统的实验声明，不能直接外推到其他硬件、网络和模型。

另一种流式设计是协调文本与合成语音的节奏。[Qwen3.5-Omni 技术报告 v2](https://arxiv.org/abs/2604.15804v2) 描述 ARIA 将文本和语音单元动态交织到一个受约束的输出流中，针对两种 tokenizer 速率不匹配造成的增量生成不稳定。ARIA 的文本/语音交织不等于 full-duplex：前者描述系统输出如何对齐，后者要求系统在说话时仍接收并处理用户输入。该报告支持其模型提出的设计和测量定义，不证明此方案对所有模型或目标服务都有相同收益。

full-duplex 的难点不是“把两个流并行计算”这么简单，还包括：

- 系统是否能区分自己播放的声音和用户输入；
- 用户插话时正在生成的声音如何停止；
- 语音重叠时哪一段内容优先；
- 模型是否在用户还没有说完时过早响应；
- 录音、缓存和日志是否包含第三方声音。

### 9.10.4 SeamlessM4T 与语音翻译

[SeamlessM4T](https://arxiv.org/abs/2308.11596) 论文公开了支持语音识别、语音到文本翻译、文本到语音翻译和 speech-to-speech 翻译的多语言路线。它说明统一语音翻译可以共享跨语言和跨模态表示，但多语言系统必须单独检查语言覆盖、性别偏差、毒性、安全和音色迁移。

翻译评估不能只测 BLEU 或文本 WER。语音到语音还要检查：译文内容、语言识别、说话人或音色政策、语气、专名、时间延迟以及是否错误地翻译了背景声音。

## 9.11 实时语音助手的时钟和延迟

### 9.11.1 端到端延迟拆分

对级联系统，若将测量起点设为用户语音结束、终点设为客户端实际播放首个可听采样，则在完全串行的近似下：

~~~math
L_{\mathrm{TTFA,client}}\approx
L_{\mathrm{capture\ flush}}+
L_{\mathrm{VAD}}+
L_{\mathrm{ASR}}+
L_{\mathrm{LLM}}+
L_{\mathrm{TTS}}+
L_{\mathrm{network}}+
L_{\mathrm{playback\ buffer}}.
~~~

这里的 $L_{\mathrm{capture\ flush}}$ 只表示用户说完后客户端等待最后一个采集块封口或提交的时间，不含整段讲话时长；$L_{\mathrm{network}}$ 包括最后输入块上传和首个输出块返回的传输等待。若把时钟起点改为服务端收到最后输入块，就应从账本中移除起点之前的采集与上行时间。这个式子只是串行账本，不是把模块完整运行时间相加的固定定律，因为 streaming ASR、增量 LLM 和 streaming TTS 可以重叠执行。服务端首包指标与用户端首音也不是同一端点：例如 time to first text token（TTFT）计文本首 token，time to first audio chunk/packet（TTFC/TTFP）计模型或服务输出首个音频块，而客户端 time to first audible audio（TTFA）还受传输、缓冲和播放调度影响。每次报告都要定义共同起点、终点、时钟位置和请求/输出长度；全程平均 RTF 不能替代这些首包时钟。

应分别报告：

- time to first partial transcript；
- time to final transcript；
- 服务端 time to first audio packet 和客户端 time to first audible sample；
- response completion；
- 用户打断后的停止时间；
- 首次播放后的持续生成速度。

例如，如果四个串行处理阶段的示例耗时为 VAD 30 ms、ASR 180 ms、LLM 220 ms、TTS 190 ms，它们的阶段和是 $30+180+220+190=620$ ms。这个算例没有采集、传输、客户端播放缓冲或并行重叠项，因此只能叫“配置阶段串行和”，不能直接称作真实 TTFA 或线上服务承诺。

### 9.11.2 Real-time factor

对一段时长为 D 的音频，处理耗时为 L 秒，可以定义 real-time factor：

~~~math
\mathrm{RTF}=\frac{L}{D}.
~~~

RTF 小于 1 表示处理速度快于实时，但它不等于交互首包延迟。一个模型可能批量处理整段音频时 RTF 很低，却无法在用户说到一半时输出部分结果。

### 9.11.3 VAD 和端点检测

VAD 判断当前帧是否可能含有语音。端点检测进一步判断用户是否说完。过早结束会截断句尾，过晚结束会增加等待时间。可以把端点策略看作两个错误的权衡：

~~~math
L_{\mathrm{endpoint}}=\lambda_{\mathrm{cut}}P_{\mathrm{cut}}+\lambda_{\mathrm{wait}}E_{\mathrm{wait}}.
~~~

P_cut 是截断概率，E_wait 是额外等待秒数；若将 L_endpoint 解释为代价，λ_cut 表示每次截断的代价尺度，λ_wait 表示每秒等待的代价尺度，二者负责把不同单位映射到同一决策目标。客服、车载和无障碍场景的权重不同，不能用一个固定阈值覆盖所有环境。

### 9.11.4 Barge-in 和回声

用户在系统播放语音时开始说话，称为 barge-in。系统需要回声消除、播放参考信号、用户语音检测和可中断 TTS。若只依赖文本端的终止标记，系统会在用户已经插话后继续播放，造成明显的交互失效。

回声消除错误还可能让 ASR 把系统自己的回答当作用户命令。应使用真实扬声器、不同房间、不同音量和重叠说话测试，而不只在干净耳机录音上评估。

### 9.11.5 流式状态管理

流式系统需要维护：

- audio buffer；
- feature cache；
- ASR encoder cache；
- 已确认和待修订的 transcript；
- LLM 对话状态；
- TTS 已播放和未播放 token；
- 用户和系统的 speaker channel；
- 中断与恢复状态。

缓存边界是常见故障来源。若每个 chunk 重置声学状态，音素在边界处会被误识别；若把已播放 token 再次送入 TTS，系统会重复说话。

生产推理还会把模型拆成多个执行阶段。[vLLM-Omni 技术报告 v1](https://arxiv.org/abs/2610.09307v1) 以 Thinker → Talker → Code2Wav 为例，分别产生文本/条件、codec code 和 waveform；async-chunk 让下游 decoder 在上游完成整段输出前先消费已到达的 chunk。报告区分文本 TTFT、音频 TTFP、完成延迟和 RTF，说明同一请求可以有多个互不替代的时钟。该报告的数值受固定 commit、H100/H200、并发数、输入长度和运行配方限制；这里仅借它解释状态与数据流，不把作者测得的延迟当作普遍 serving 能力。

## 9.12 音频生成：音乐、环境声和音效

### 9.12.1 文本到音频

[AudioGen](https://arxiv.org/abs/2209.15352) 研究了以文字描述为条件的 audio generation，并在离散音频表示上进行自回归生成。它面对的困难与语音不同：

- 文本描述不一定精确指定声源；
- 多个声源会混合在同一 waveform 中；
- 录音环境、混响和背景噪声影响很大；
- 高保真音频的 token 序列很长；
- 文本-音频配对数据比文本-图像数据稀缺。

例如“街道上有雨声，一辆自行车从左向右经过”同时包含事件、空间和时间顺序，单一句子很难完全规定声场。

### 9.12.2 音乐的长程结构

音乐生成要同时建模局部声学细节和段落结构。局部 token 模型可以生成像音乐的短片段，却可能在较长时间内重复和弦、忘记主题或破坏节拍。

可以把音乐结构分为：

1. 低速结构：段落、主歌、副歌、主题和调性。
2. 中速结构：乐句、节拍、和声进行。
3. 高速结构：音符、音色、瞬态和混音细节。

类似 AudioLM 的层级 token 思路说明不同时间尺度可以使用不同表示。音乐模型仍需独立评估版权、旋律相似、风格模仿和可编辑性。

### 9.12.3 音效与视频同步

视频的脚落地、门关闭和物体碰撞需要音效与视觉事件对齐。设视频事件时间为 τ_v，音频事件时间为 τ_a，可以定义同步误差：

~~~math
\Delta\tau=|\tau_a-\tau_v|.
~~~

小的固定偏移可能可以校正；变化的漂移则说明生成、剪辑或重采样的时钟不一致。音频“听起来不错”不能替代音画同步。

### 9.12.4 空间音频

双耳、环绕和多声道音频还包含声源方向、距离和房间响应。把多声道 waveform 简单平均成单声道会丢失空间信息；把单声道生成结果复制到左右声道也不会得到真实空间感。

空间音频评估应包括声源定位、通道一致性、移动声源轨迹和耳机/扬声器播放差异。codec 训练和解码器也必须明确支持的声道数。

## 9.13 语音与音频评估

### 9.13.1 ASR 评估

ASR 至少需要 WER 或 CER，但要固定文本规范化、语言、说话人分段、标点和专名规则。对于多说话人录音，增加 DER；对于实时系统，增加 partial transcript 延迟、端点错误和修订次数。

可以把任务成功写成事件而非平均分：

~~~math
E_{\mathrm{command}}=
\mathbf{1}[
\mathrm{intent\ correct}
\land
\mathrm{slots\ correct}
\land
\mathrm{no\ unsafe\ trigger}
].
~~~

命令型系统应报告 E_command 的比例，而不是只报告总体 WER。

### 9.13.2 TTS 的自然度和可懂度

MOS 是让听者对自然度或质量进行评分的平均意见分。它反映人类感知，却依赖标注者、播放设备、评分说明和样本顺序。应报告样本数、置信区间和标注一致性，不把一次小样本 MOS 当作精确真值。

还需要分别测：

- 内容可懂度和文本一致性；
- speaker similarity；
- 韵律和情绪控制；
- 音频伪影；
- 长文本稳定性；
- 首包和整体延迟。

### 9.13.3 MUSHRA、FAD 与客观指标

对适用的中等音质比较，可以按 [ITU-R BS.1534-3](https://www.itu.int/rec/r-rec-bs.1534/en) 设计 MUSHRA 多刺激主观测试，使用隐藏参考和锚点比较多个系统；听者筛选、刺激、播放条件和统计报告都属于协议的一部分。[Fréchet Audio Distance（FAD）](https://arxiv.org/abs/1812.08466v4) 最初针对音乐增强：它用 VGGish 提取评估输出与干净背景音乐集合的音频嵌入，分别估计两组嵌入的高斯统计，再计算 Fréchet 距离。它衡量的是集合分布差异，不是单条音频的内容或自然度分数；原论文在 MagnaTagATune 数据上的人工失真实验不能证明 FAD 对所有生成音频任务都有效。

FAD 依赖特征提取器、样本数量、音频长度和预处理。它不能告诉我们一条语音是否读对金额，也不能直接测说话人授权和声音冒充风险。客观指标应与内容、身份、韵律和人工听感组合使用。

### 9.13.4 延迟、吞吐和成本

语音系统需要同时记录：

- 每秒处理音频的计算量；
- 首个 partial transcript 延迟；
- 首个可听音频延迟；
- 端到端 response latency；
- 生成音频秒数与计算秒数；
- GPU/CPU/网络成本；
- 并发数和缓存占用。

一个离线 batch benchmark 的吞吐不能替代真实全双工交互的延迟。硬件、量化、音频 chunk 大小和网络 jitter 都要纳入实验记录。

### 9.13.5 组合评估表

| 维度 | 评估对象 | 适合的指标或方法 | 主要盲点 |
| --- | --- | --- | --- |
| 转写 | 内容是否正确 | WER、CER、实体召回 | 规范化和语言切分影响大 |
| 多说话人 | 说话人和分段 | DER、重叠语音测试 | collar 与重叠口径 |
| TTS 内容 | 是否读对、错在何处 | ASR 回转写后的 WER/CER、关键字段检查；forced alignment 可定位时间段 | 对齐成功本身不证明文本正确，也不代表自然度 |
| 说话人 | 音色是否保持 | speaker embedding、人工 | 特征模型偏差 |
| 韵律 | 停顿和重音 | 专项标注、人工听评 | 难以完全自动化 |
| 音质 | 噪声和伪影 | MOS、MUSHRA、FAD | FAD 是集合级距离，不能定位单句内容错误 |
| 实时性 | 是否能对话 | TTFA、RTF、打断恢复 | batch 结果不可替代 |
| 安全 | 是否滥用 | 授权、冒充、注入测试 | 需要长期治理 |
| 长 prompt 韵律 | 音色之外是否复现说话习惯 | [LP-TTS-Bench v1](https://arxiv.org/abs/2610.19774v1) 的 timing、prominence、intonation 与韵律相似度 | 中文/英语 37 位说话人和其参考系统，不代表所有 TTS 的收益规律 |
| 长文/多轮生成 | 跨句、跨说话人和场景是否连贯 | [SwanBench-Speech v1](https://arxiv.org/abs/2605.28618v1) 的长文场景维度；[DRAMA-Eval v1](https://arxiv.org/abs/2610.31796v1) 的内容、说话人一致性、局部指令和整段场景评估 | 评估器、语种、文本长度与模型可用条件会影响结果；不能混成单一排名 |
| 实时交互 | 何时说、说什么、是否听从音量要求、是否记住对话 | [InteractionBench v1](https://arxiv.org/abs/2611.02430v1) 的实时共同 harness、任务分数和客户端时序 | 合成英语、少数场景、提示与 API 协议差异；hosted timing 含网络，不是 SLA |

这些新协议把评测单位从一条 utterance 扩展到长 prompt、完整场景或实时会话，回答的问题彼此不同。[SwanBench-Speech v1](https://arxiv.org/abs/2605.28618v1) 报告 1,101 个样本、17 种场景和 7 个声学/语义/表现力指标，并用用户研究核对部分自动评估；[DRAMA-Eval v1](https://arxiv.org/abs/2610.31796v1) 在 1,038 个中英文场景案例上评估内容、说话人一致性、逐轮指令和整段场景质量。DRAMA-Eval 场景平均约 43 秒、7.25 轮，不能代表长篇叙事；其自动 judge 是专有音频语言模型，不同模型类别拿到的条件也不同，因此跨类别分数不是同条件模型排名。InteractionBench 则在相同录音和客户端时间轴上检查轮次时机、口语任务、声音表达和长对话 groundedness；其论文报告 1,519 次 graded runs，但有系统缺失项，使用合成英语并把 hosted 网络时延计入客户端时间。比较前须确认输入条件、分母、自动 judge 与人工核验关系；这些论文只支持各自协议下的观察。

## 9.14 语音安全、隐私与来源

### 9.14.1 voice cloning 的风险

声音包含可用于辨认说话人和表达身份的声学线索；一段参考录音还可能被模型当作音色或风格条件，例如 [VALL-E](https://arxiv.org/abs/2301.02111v1) 所讨论的 codec prompt 路线。风险包括：

- 未经同意的音色克隆；
- 冒充亲友、客服或管理者；
- 伪造录音和证据；
- 通过短录音推断身份或隐私；
- 把真实说话人的情绪和背景带入不当内容；
- 生成高风险指令或误导性播报。

安全措施不能只依赖一个声音检测器，因为转码、噪声和二次录音都会影响检测。

### 9.14.2 授权和撤回

声音数据治理应保存采集目的、授权范围、使用期限、撤回机制和训练版本。撤回并不只是删除数据库中的原文件，还要说明已训练权重、缓存 embedding、生成样例和发布内容如何处理。

对公众人物、未成年人、员工录音和医疗/客服录音，授权和发布条件应更严格。内部测试也不能默认允许把录音用于模型训练。

### 9.14.3 语音 prompt injection

音频输入可能包含背景中的第三方讲话、播放设备回声，或经过构造的对抗性指令。[AudioHijack 预印本 v1](https://arxiv.org/abs/2604.14604v1) 在一组 audio-language models 和若干商业语音代理实验中报告了音频注入攻击；这是受控条件下的安全研究结果，不能据此断言任意录音、模型或现实环境都可被同样操纵。它揭示的系统边界是：模型识别到的语音内容不自动等于当前用户授权。多模态 Agent 不能把所有听到的内容都当成用户指令。

权限边界应区分：

1. 用户直接说出的任务；
2. 录音中的第三方内容；
3. 播放出来的系统或网页音频；
4. 需要确认的高风险工具调用；
5. 仅供引用而非执行的语音内容。

在调用支付、开锁、发送消息或删除数据前，应要求可验证的用户确认，而不是只依赖 ASR 结果。

### 9.14.4 provenance、水印与检测

语音水印和内容凭证可作为来源记录或检测信号。[C2PA 2.5 技术规范](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html)定义了以签名保护的声明与资产关联验证；凭证缺失也不能证明内容未经生成或修改，签名有效更不能证明录音描述的事件真实发生。检测器也会有漏报和误报，应与授权记录、发布日志、人工审核和风险场景限制结合。

安全系统还要测试声音变调、速度变化、压缩、混响、混音和跨语言合成后的鲁棒性。

## 9.15 与 LLM、VLM 和 Agent 的结合

### 9.15.1 级联接口

级联系统中，ASR 把连续声音转换为文本，LLM 负责语言推理，TTS 把结果转回语音。这种接口有利于日志、引用和工具调用，但会丢失原始韵律和非语言信息。

如果任务是会议记录，文本中间层通常足够；如果任务是情绪敏感的陪伴、客服打断或跨语言语音翻译，纯文本中间层可能不够。

### 9.15.2 Audio encoder 接入语言模型

另一种方式是 audio encoder 产生连续表示，再通过 projector 或 cross-attention 接入 LLM：

~~~text
audio waveform
    -> audio encoder
    -> projector / resampler
    -> language model
    -> text or tool action
~~~

这使模型可以处理语调、环境声和声学事件，但上下文预算需要按音频时间估算。若 audio encoder 每 20 ms 产生一个 token，1 分钟音频约有 3000 个时间位置，还没有计算多层特征。

### 9.15.3 统一 speech token

把文本 token、semantic speech token 和 acoustic codec token 放进统一序列，可以支持语音问答、speech-to-speech 和跨模态生成。需要明确每种 token 的：

- 时间分辨率；
- 词表和特殊 token；
- stream 之间的对齐；
- mask 和 causal 方向；
- 生成结束条件；
- 解码器和安全过滤位置。

如果只为了“统一”而把所有音频展平成一条长序列，模型可能浪费上下文在高频细节上，反而削弱语言和长期结构。

### 9.15.4 Agent 的音频权限

Agent 可以使用麦克风、播放音频、发送语音消息或控制电话。权限系统应把“听见”与“执行”分开，把“模仿音色”与“获得授权”分开。工具调用记录要包含触发的音频片段、ASR 转写、用户确认和最终输出，而不是只存一段无法审计的 waveform。

## 9.16 从失败音频反推系统问题

### 9.16.1 采样和预处理层

首先检查：

- sample rate 是否与模型契约一致；
- 左右声道是否交换或丢失；
- 音频是否削波、静音或过度归一化；
- STFT window、hop、center、mel bins 是否一致；
- 训练和部署是否使用相同的语言和文本规范化；
- VAD 是否截断了句首句尾。

许多“模型突然听不清”的问题，其实是 24 kHz 音频被当作 16 kHz 读取，或者把整数 PCM 当成 [-1,1] 浮点。

### 9.16.2 表示和 codec 层

如果 codec 重建有明显金属声或爆音，应分别比较：

1. 原 waveform 和 codec decode 的重建；
2. 不同码率和 codebook 数；
3. 单声道与多声道；
4. 训练和推理采样率；
5. 长片段和短片段的边界。

如果重建已经失败，后面的 codec language model 不可能恢复丢失的高频信息。若重建正常而生成失败，再检查 token 顺序、codebook mask 和条件对齐。

### 9.16.3 交互和延迟层

语音助手出现重复、抢话或无响应时，应记录事件时间线：

~~~text
capture -> VAD start -> partial ASR -> endpoint
        -> LLM first token -> TTS first audio
        -> user barge-in -> stop playback
~~~

逐事件测量比只看端到端平均延迟更有用。平均值还可能掩盖少数极慢请求，实时系统应报告 p50、p95、p99 和最坏中断恢复时间。

### 9.16.4 最小对照实验

可以用下面的单变量对照定位原因：

- 固定 waveform，只改变采样率声明；
- 固定采样率，只改变 STFT center 和 padding；
- 固定文本，只更换 speaker prompt；
- 固定 speaker，只改变目标文本中的数字和专名；
- 固定模型，只改变 codec 的 codebook 数；
- 固定输入，只关闭 streaming，比较离线与流式；
- 固定回答，只让用户在不同时间点 barge-in；
- 固定语音，分别测试耳机、扬声器和远场麦克风。

## 9.17 可运行的音频 token、WER 与实时性审计

下面的 demo 不执行真实 ASR、TTS 或 codec，只计算采样点、声学帧、编辑距离、codec token、码率、处理阶段串行和、TTS token 和授权状态。阈值是教学配置，不能直接当作产品标准。

先把同一请求的输入条件列清：单声道采样率与时长决定 PCM 样本数，window/hop 决定声学帧，codec 帧率与码本数决定 token 数。参考文本与假设文本只用于演示编辑距离；四个延迟数是串行阶段的假设输入，不是一次线上测量。最后的文本 token 和 speaker prompt token 与生成目标音频的 codec token 相加，得到一个简单上下文预算。所有值都能手工复算，代码只重复这些账本并检查边界。

from math import ceil, isfinite, log2


def edit_distance(a, b):
    if not isinstance(a, list) or not isinstance(b, list):
        raise TypeError("edit distance inputs must be lists")
    dp = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i in range(len(a) + 1):
        dp[i][0] = i
    for j in range(len(b) + 1):
        dp[0][j] = j
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            cost = 0 if a[i - 1] == b[j - 1] else 1
            dp[i][j] = min(
                dp[i - 1][j] + 1,
                dp[i][j - 1] + 1,
                dp[i - 1][j - 1] + cost,
            )
    return dp[-1][-1]


def word_error_rate(reference, hypothesis):
    reference_words = reference.split()
    hypothesis_words = hypothesis.split()
    if not reference_words:
        return None
    return edit_distance(reference_words, hypothesis_words) / len(reference_words)


def char_error_rate(reference, hypothesis):
    reference_chars = list(reference.replace(" ", ""))
    hypothesis_chars = list(hypothesis.replace(" ", ""))
    if not reference_chars:
        return None
    return edit_distance(reference_chars, hypothesis_chars) / len(reference_chars)


def is_finite_real(value):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        return False
    try:
        return isfinite(value)
    except OverflowError:
        return False


def require_nonnegative_int(value, name):
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise ValueError(f"{name} must be a non-negative integer")


def audio_audit(config):
    for field in (
        "sample_rate",
        "window_ms",
        "hop_ms",
        "n_mels",
        "codec_hz",
        "codebooks",
        "bits_per_code",
        "pcm_bits",
        "context_limit",
    ):
        if (
            isinstance(config[field], bool)
            or not isinstance(config[field], int)
            or config[field] <= 0
        ):
            raise ValueError(f"{field} must be a positive integer")
    require_nonnegative_int(config["text_tokens"], "text_tokens")
    require_nonnegative_int(
        config["speaker_prompt_tokens"], "speaker_prompt_tokens"
    )
    if not is_finite_real(config["duration_s"]) or config["duration_s"] <= 0:
        raise ValueError("duration_s must be a positive finite number")
    if (
        not is_finite_real(config["target_speech_s"])
        or config["target_speech_s"] <= 0
    ):
        raise ValueError("target_speech_s must be a positive finite number")
    if config["window_ms"] <= config["hop_ms"]:
        raise ValueError("window_ms must be greater than hop_ms")
    latencies = config["latency_ms"]
    if (
        not isinstance(latencies, dict)
        or not latencies
        or any(not is_finite_real(value) or value < 0 for value in latencies.values())
    ):
        raise ValueError("latencies must be finite and non-negative")
    if not isinstance(config["speaker_authorized"], bool):
        raise ValueError("speaker_authorized must be boolean")
    samples = int(config["sample_rate"] * config["duration_s"])
    window_samples = int(
        config["sample_rate"] * config["window_ms"] / 1000
    )
    hop_samples = int(config["sample_rate"] * config["hop_ms"] / 1000)
    if window_samples <= 0 or hop_samples <= 0:
        raise ValueError("window and hop must each span at least one sample")
    centered_frames = ceil(
        config["duration_s"] * 1000 / config["hop_ms"]
    )
    valid_frames = 1 + max(
        0, (samples - window_samples) // hop_samples
    )
    if samples < window_samples:
        valid_frames = 0

    codec_frames = ceil(
        config["duration_s"] * config["codec_hz"]
    )
    codec_tokens = codec_frames * config["codebooks"]
    raw_bits = samples * config["pcm_bits"]
    if config["bits_per_code"] <= 0:
        raise ValueError("bits_per_code must be positive")
    codec_bits = codec_tokens * config["bits_per_code"]
    codec_ratio = codec_bits / raw_bits

    wer = word_error_rate(
        config["reference"],
        config["hypothesis"],
    )
    cer = char_error_rate(
        config["reference"],
        config["hypothesis"],
    )
    serial_stage_sum_ms = sum(config["latency_ms"].values())
    tts_tokens = ceil(
        config["target_speech_s"] * config["codec_hz"]
    ) * config["codebooks"]
    codec_lm_context = (
        config["text_tokens"]
        + config["speaker_prompt_tokens"]
        + tts_tokens
    )

    report = {
        "samples": samples,
        "window_samples": window_samples,
        "hop_samples": hop_samples,
        "centered_mel_frames": centered_frames,
        "valid_mel_frames": valid_frames,
        "mel_shape": (config["n_mels"], centered_frames),
        "codec_frames": codec_frames,
        "codec_tokens": codec_tokens,
        "raw_kbits": round(raw_bits / 1000, 2),
        "codec_kbits": round(codec_bits / 1000, 2),
        "codec_ratio": round(codec_ratio, 6),
        "wer": None if wer is None else round(wer, 3),
        "cer": None if cer is None else round(cer, 3),
        "serial_stage_sum_ms": serial_stage_sum_ms,
        "tts_tokens": tts_tokens,
        "codec_lm_context": codec_lm_context,
    }
    checks = {
        "centered_frames_expected": centered_frames == 320,
        "valid_frames_expected": valid_frames == 318,
        "codec_tokens_expected": codec_tokens == 640,
        "codec_ratio_under_demo_limit": codec_ratio < 0.01,
        "wer_under_demo_limit": wer is not None and wer < 0.30,
        "cer_under_demo_limit": cer is not None and cer < 0.20,
        "serial_stage_sum_under_demo_limit": serial_stage_sum_ms < 700,
        "context_within_limit": codec_lm_context <= config["context_limit"],
        "speaker_authorized": config["speaker_authorized"],
    }
    report["checks"] = checks
    report["audit_consistent"] = all(checks.values())
    return report

这里有三个值得注意的边界：

1. centered_mel_frames 是带中心 padding 的教学口径，valid_mel_frames 是不补齐的有效窗口口径；两者不同不代表代码必然错误。
2. codec_ratio 只比较理想化 bit 数，没有计算文件容器、帧头、模型权重和解码缓存。
3. serial_stage_sum_ms 只把 VAD、ASR、LLM 和 TTS 四个示例值相加；它没有采集、网络、播放缓冲，也不表示真实客户端 TTFA。streaming 系统可以让这些阶段重叠执行，需要从同一请求的事件时间线测量。

如果参考文本为空，WER/CER 没有定义；如果音频短于一个不补齐的分析窗口，valid_mel_frames 可以是 0。这两种情况都不是“模型表现为 0 分”，而是评估分母或输入窗口不足，报告应保留这种状态。

把 speaker_authorized 改成 False，或把 reference/hypothesis 改得更不相似，报告会分别显示授权或转写检查失败。实际阈值应从目标语言、噪声切片、设备和高风险命令的验证集估计。

读代码时先核对单位和口径。输入 `sample_rate=16000`、`duration_s=3.2` 表示单声道 16 kHz、3.2 秒；因此样本数是 $16000\times3.2=51200$。25 ms 窗口对应 $16000\times0.025=400$ 个采样点，10 ms hop 对应 $160$ 个采样点。不做两端补齐时，帧数为 $1+\lfloor(51200-400)/160\rfloor=318$；用 10 ms 帧移并加中心 padding 的教学口径则有 $3.2/0.01=320$ 帧。代码把两者都输出，避免把实现约定当成同一个公式。

codec 配置为 50 帧/秒、每帧 4 个码本，所以 3.2 秒产生 $\lceil3.2\times50\rceil=160$ 帧、$160\times4=640$ 个 code。每 code 假设 10 bit，总量是 6400 bit；16 bit PCM 原始样本量是 $51200\times16=819200$ bit，即 819.2 kbit。二者比值 $6400/819200=0.0078125$ 只是理想化 bit 数比例。真实 codec 可能有 padding、chunk、码率控制与容器开销，不能把此比值作为压缩器实测结果。

参考句有 5 个空格分词后的英文词，假设 hypothesis 只把 `lights` 改成 `light`，编辑距离是 1，所以 WER=$1/5=0.2$。移除空格后参考字符数为 22，同样只有一次删除，所以 CER=$1/22\approx0.0455$。这段 demo 没有做大小写、标点、数字或 Unicode 规范化；实际评测必须固定这些规则。若参考为空，函数返回 `None`，表示分母为零且指标未定义，而不是模型得分为 0。

延迟输入只包含四个串行阶段：$30+180+220+190=620$ ms；它用于演示如何求“阶段和”，并不覆盖采集、传输和播放。生成目标音频 2.4 秒时，$\lceil2.4\times50\rceil\times4=480$ 个 codec token；再加 18 个文本 token 和 120 个 speaker prompt token，教学上下文总数为 618。真实模型还可能有语义 token、控制 token、特殊分隔符和不同的多码本生成顺序。

边界检查验证空参考的未定义状态、短音频没有完整有效窗口、零采样率/无效窗口/每 hop 不足一个采样点会被拒绝、负延迟会被拒绝，以及未获授权的说话人会让审计门失败。这里的阈值和布尔门只是教学配置；它们没有听取任何声音，也没有测量真实 ASR、TTS、codec、授权记录或服务延迟。

读输出时先把账本分成三层：样本数和帧数核对采样、分窗与 padding；codec token、理想 bit 和比例核对表示成本；WER/CER 只核对给定文本对的编辑差异。`checks` 与 `audit_consistent` 只是把示例值和代码里的教学阈值比较；全部布尔项通过也不代表声音自然、命令执行正确或授权凭证有效。真实评估应按样本 ID 关联原始 waveform、参考文本、模型版本、规范化规则、授权状态和事件时钟，保存逐条结果后再按语言、噪声、说话人和任务切片汇总。

代码用 `int(sample_rate * duration_s)` 从时长估算样本数；3.2 秒在 16 kHz 下正好得到 51,200，但任意小数秒会被向下截断。部署时应以解码后 waveform 的实际长度为准。codec 帧数使用向上取整，等于假设尾部不足一帧时仍保留一个 token 帧；真实 encoder 的 stride、padding、chunk 规则可能丢弃或补齐尾部，因此 token 预算也应从目标 codec 的实际输出 shape 核对。

## 9.19 本章小结

音频是高采样率的连续时间信号。waveform 保留最完整的信息，但序列很长；STFT 和 log-mel 适合声学建模，neural audio codec 则把音频压缩为可被 Transformer 处理的离散 token。采样率、window、hop、padding、声道和幅度范围都是模型契约，不是无关紧要的预处理细节。

ASR 的核心是从声学表示恢复内容，Whisper 代表大规模弱监督 encoder-decoder 路线，wav2vec 2.0 和 WavLM 代表自监督语音表征路线。WER、CER 和 DER 能描述不同类型的识别错误，但不能替代命令成功率、高风险词检查和实时延迟。

TTS 同时要处理文本、音色、韵律、情绪和 waveform 细节。codec language model、AudioLM、VALL-E、SoundStorm、NaturalSpeech 2、CosyVoice 和 SpeechT5 展示了离散 token、分层表示、连续 latent、流式生成和统一模态接口的不同取舍。选择路线时必须同时看序列长度、控制能力、音质、长程结构和推理成本。

级联语音助手容易调试和审计，端到端 speech-to-speech 有机会保留更多非语言信息，但会提高训练、解释和安全评估难度。实时系统还要处理 VAD、端点、回声、打断、缓存和双工时钟。voice cloning、语音指令注入和录音隐私要求授权、来源和高风险动作确认进入系统设计，而不是在生成之后补一个检测器。

### 资料与阅读顺序

1. [Whisper](https://arxiv.org/abs/2212.04356)：大规模弱监督语音识别与多任务 encoder-decoder。
2. [wav2vec 2.0](https://arxiv.org/abs/2006.11477)：自监督语音表征和少量标注微调。
3. [WavLM](https://arxiv.org/abs/2110.13900)：masked prediction 与 denoising 的全栈语音表征。
4. [SoundStream](https://arxiv.org/abs/2107.03312)：端到端 neural audio codec 和 residual vector quantizer。
5. [EnCodec](https://arxiv.org/abs/2210.13438)：高保真、实时神经音频压缩和开源实现。
6. [AudioLM](https://arxiv.org/abs/2209.03143)：semantic token 与 acoustic codec token 的分层语言建模。
7. [VALL-E](https://arxiv.org/abs/2301.02111)：codec language model TTS 和 acoustic prompt。
8. [SpeechT5](https://arxiv.org/abs/2110.07205)：共享 encoder-decoder 的语音/文本统一预训练。
9. [NaturalSpeech 2](https://arxiv.org/abs/2304.09116)：codec latent diffusion、speech prompt 和零样本合成。
10. [AudioPaLM](https://arxiv.org/abs/2306.12925)：文本语言模型与音频语言模型的统一接口。
11. [SeamlessM4T](https://arxiv.org/abs/2308.11596)：多语言 ASR、翻译和 speech-to-speech。
12. [SoundStorm](https://arxiv.org/abs/2305.09636)：codec token 的非自回归并行生成。
13. [AudioGen](https://arxiv.org/abs/2209.15352)：文字条件通用音频生成。
14. [Moshi](https://arxiv.org/abs/2410.00037)：full-duplex 实时 speech-to-speech 对话。
15. [CosyVoice](https://arxiv.org/abs/2407.05407)：监督 semantic token、LLM 和 flow matching TTS。
16. [Fréchet Audio Distance v4](https://arxiv.org/abs/1812.08466v4) 与 [ITU-R BS.1534-3 MUSHRA](https://www.itu.int/rec/r-rec-bs.1534/en)：对照集合级音频分布指标与受控主观音质协议。
17. [Qwen3-ASR 技术报告 v2](https://arxiv.org/abs/2601.21337v2) 与 [mu-bench v1](https://arxiv.org/abs/2609.32082v1)：对照流式路径配置和业务关键字段评估。
18. [Qwen3-TTS 技术报告 v1](https://arxiv.org/abs/2601.15621v1) 与 [LP-TTS-Bench v1](https://arxiv.org/abs/2610.19774v1)：对照 codec/tokenizer 路线与长 prompt 韵律复现。
19. [SwanBench-Speech v1](https://arxiv.org/abs/2605.28618v1) 与 [DRAMA-Eval v1](https://arxiv.org/abs/2610.31796v1)：长文、跨说话人及场景级语音生成评估。
20. [Qwen3.5-Omni 技术报告 v2](https://arxiv.org/abs/2604.15804v2) 与 [vLLM-Omni 技术报告 v1](https://arxiv.org/abs/2610.09307v1)：对照流式文本/语音对齐和多阶段音频数据流。
21. [InteractionBench v1](https://arxiv.org/abs/2611.02430v1)：实时语音交互共同 harness 与客户端时序。
22. [AudioHijack v1](https://arxiv.org/abs/2604.14604v1)：大型音频语言模型的第三方音频注入威胁研究；阅读攻击假设、评估范围和限制，不把作者成功率当作普遍风险率。
