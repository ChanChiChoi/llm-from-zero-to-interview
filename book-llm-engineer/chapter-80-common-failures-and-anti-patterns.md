# 第80章：常见失败案例与反面教材

上一章讨论了模拟面试训练与刻意练习。

这一章从反面看问题。

很多大模型工程师候选人不是因为完全不会而失败，而是踩中了非常典型的坑。

这些坑包括：项目包装过度、只会讲框架、没有指标、忽视安全、不会复盘、面试中硬编经验、入职后急于重构等。

反面教材的价值在于：它能帮助你提前避坑。

## 80.1 失败一：把 demo 当生产项目讲

很多候选人做过 demo，但在简历和面试中讲成生产项目。

面试官一追问：

- 有多少真实用户？
- 评测集怎么构建？
- 如何灰度？
- 如何回滚？
- 线上失败怎么处理？
- 成本如何控制？

候选人就答不上来。

demo 可以讲，但要讲清边界。

正确表达是：

```text
这是一个个人项目或原型验证，重点验证 RAG 链路和评测方法。它没有真实线上流量，所以我主要用公开数据和自建评测集验证 retrieval、rerank 和 generation 的效果。生产化还需要补权限、监控、灰度、成本和反馈闭环。
```

诚实边界比夸大更可信。

## 80.2 失败二：简历堆满技术名词

“熟悉 RAG、Agent、LangChain、vLLM、LoRA、MCP、向量数据库”不是项目能力。

面试官关心的是：

- 你解决了什么问题？
- 你负责哪一块？
- 你如何验证效果？
- 你遇到什么失败？
- 你做了什么取舍？

堆技术名词会让候选人看起来像在追热点。

简历要从工具清单改成结果清单。

## 80.3 失败三：没有指标

大模型项目没有指标，很难证明有效。

常见空泛表达：

```text
显著提升回答质量。
大幅降低延迟。
优化用户体验。
提升系统稳定性。
```

更好的表达是：

```text
citation accuracy 从 71% 提升到 86%。
P95 TTFT 从 3.4s 降到 1.9s。
格式合法率从 92% 提升到 98%。
人工接管率下降 18%。
单次成功任务成本下降 27%。
```

如果没有精确指标，也要给出样本规模、评测方式和相对变化。

没有指标的项目，很难形成说服力。

## 80.4 失败四：只会讲框架，不会讲原理

候选人说用了 LangChain、LlamaIndex、vLLM、SGLang。

面试官继续问：

- chunk size 为什么这样选？
- rerank 解决什么问题？
- PagedAttention 不是 sparse attention 吗？
- continuous batching 和 dynamic batching 有什么区别？
- Agent 工具调用失败怎么恢复？

如果答不上来，框架名会变成扣分项。

框架是工具。

面试要讲清工具背后的机制和取舍。

## 80.5 失败五：忽视安全和权限

很多候选人讲 Agent 时只讲智能。

但不讲权限、审计、确认和回滚。

这在生产面试中很危险。

如果模型能调用工具，就必须问：

- 工具是否有副作用？
- 参数如何校验？
- 权限在哪里执行？
- 高风险操作是否确认？
- 调用日志如何审计？
- prompt injection 怎么防？

只讲“模型会自动调用工具”是不够的。

生产系统里，模型可以建议，系统必须校验。

## 80.6 失败六：不会讲失败

完美项目故事通常不真实。

成熟候选人应该能讲失败。

例如：

- 最初判断错了瓶颈。
- 某次 prompt 改动导致格式回退。
- rerank 提升质量但增加延迟。
- 长上下文方案成本不可接受。
- Agent 自主性过高导致误调用风险。

关键不是失败本身。

关键是你如何发现、定位、修正和复盘。

不会讲失败的人，面试官会怀疑你没有真实生产经验。

## 80.7 失败七：面试中硬编经验

大模型面试追问很深。

如果硬编经验，很容易露馅。

例如你说做过 vLLM 生产优化，面试官可能问：

- TTFT 和 TPOT 如何拆？
- KV cache block 如何估算？
- prefix cache 命中率是多少？
- prefill 和 decode 如何调度？
- OOM 时看哪些指标？

如果没有真实经验，很难持续回答。

正确做法是承认边界。

可以说：

```text
我没有在生产中维护过 vLLM 集群，但我做过本地 benchmark，并系统学习过 serving engine 的请求生命周期、KV cache、batching 和 TTFT/TPOT 指标。如果要上线，我会重点补容量测试、监控、灰度和故障演练。
```

诚实边界不会一定扣分。

硬编通常会严重扣分。

## 80.8 失败八：入职后急于证明自己

有些人刚入职就想重构系统。

但没有理解历史约束，就容易破坏已有系统。

正确做法是：

- 先理解业务和历史决策。
- 跑通链路。
- 看线上指标。
- 和相关方沟通。
- 选择小闭环建立可信度。
- 再提出中期改进。

前 30 天最重要的不是证明自己比前人聪明。

而是证明自己可靠、能学习、能协作、能形成闭环。

## 80.9 失败九：只追热点，不沉淀资产

今天学 RAG，明天学 Agent，后天学 MCP，大后天学推理框架。

但每个方向都没有项目复盘、指标、代码、文档和面试表达。

这会导致知识很散。

正确做法是每学一个方向，都沉淀一个资产：

- 一篇项目复盘。
- 一个可运行 demo。
- 一个评测集。
- 一个 debug checklist。
- 一个标准回答。

职业成长靠资产累积，不靠热点堆积。

## 80.10 从失败表象追到系统原因

失败案例不能只按“候选人做错了什么”分类，还要区分触发条件、可见信号和真正的根因。比如“回答质量下降”是结果，不是根因；它可能来自文档版本没有同步、召回过滤变严、模型路由改变、评测集污染或用户问题分布变化。

一个实用的复盘表至少有五列：现象、影响范围、最近变更、证据、修复后的回归。影响范围决定优先级，最近变更决定排查顺序，证据决定能否把猜测升级为结论，回归决定修复是否真的有效。

可以把一次失败写成因果链：

```text
变更 -> 中间状态 -> 可见指标 -> 用户影响 -> 修复 -> 回归证据
```

例如，prompt 增加了一个长格式示例，导致输入 token 增长；prefill 时间上升，队列等待增加；p99 超过 SLO，用户开始取消请求；删掉示例后延迟恢复，但格式合法率下降。真正的修复不是简单撤销 prompt，而是把格式约束迁移到结构化输出或更短的 schema，并重新测质量与延迟。

## 80.11 案例：RAG 项目为什么会在“看起来更聪明”后变差

某候选人把检索 top-k 从 5 提高到 20，模型回答中的背景信息变多，于是把方案描述为“召回增强，效果显著提升”。上线后用户发现引用经常指向旧制度，回答也更长。这个案例的错误不在于提高 `k` 一定错误，而在于没有把证据质量、版本过滤、上下文位置和成本拆开。

排查时可以先固定 query 和文档版本，比较 `k=5` 与 `k=20` 的 evidence recall、citation support、旧版本命中率、输入 token 和 p95。若 recall 提升但 citation support 下降，说明更多候选没有经过时间/权限过滤或 rerank；若离线正常而线上变差，则继续检查索引更新、缓存 key 和模板。

面试中更可信的表达是：“我最初把 top-k 增大，召回率上升但引用支持下降。通过按版本切片和回放 trace，发现旧文档混入以及上下文预算被稀释。后来加入元数据过滤、rerank 和长文档路由，并用固定回归集验证质量、token 和 p95。”这段话既说明失败，也说明你知道指标之间的冲突。

## 80.12 案例：推理优化收益为什么可能只是分母游戏

另一个常见失败是只报告 tokens/s。某 serving 实验启用 speculative decoding 后，单请求短文本的 tokens/s 提高 35%，但线上工具调用任务的成功成本上升。原因可能是候选在自然语言上容易接受，在 JSON 或工具参数上频繁拒绝；候选和验证的额外显存还造成长请求抢占。

完整比较至少要同时记录 target calls、平均和分位接受长度、候选成本、TTFT、TPOT、p99、显存、fallback、结构化输出错误和单位成功任务成本。若工具任务存在副作用，还要检查 rejected token 是否被误执行。只有把分母固定为“完成一个成功任务所需的资源”，才知道优化是在服务用户，还是只改变了一个局部计数器。

## 80.13 经验边界、简历声明和可验证证据

职业材料中的每一条强声明都应该有证据等级。可以把经历分成四类：亲自负责过的生产改动、参与过并能说明边界的团队项目、独立完成的实验或 demo、读过但没有实现的技术。它们都可以写进简历，但动词和指标不能混用。

例如，“负责线上 KV cache 调度并将 p99 降低 20%”需要变更记录、监控和回滚证据；“实现 toy KV cache 并在三种长度上验证 logits 一致”是很好的学习项目，但不能写成线上优化。建立一个 claim ledger 会迫使候选人回答：这句话的对象、时间、基线、样本、我的贡献和证据在哪里。

这也是面试中的保护机制。遇到没有直接经验的追问，可以明确说自己掌握的是论文或本地实验，再给出上线时的验证计划。诚实不会消除所有风险，但能避免一个细节错误扩散成整段经历失真。

## 80.14 复盘练习：把一个失败讲成可学习的工程故事

选择一个真实或教学失败，按以下顺序写一页复盘：

1. 任务目标和成功指标是什么。
2. 初始方案和隐含假设是什么。
3. 什么时候、通过什么信号发现异常。
4. 影响了哪些用户或评测切片。
5. 哪些假设被证据否定。
6. 修复改变了哪些变量，保留了哪些对照。
7. 修复后的质量、延迟、成本和风险如何变化。
8. 如果再次遇到同类问题，哪一个验收条件会更早发现。

面试回答可以压缩成两分钟，但复盘原稿不能压缩成“调了参数所以好了”。真正有价值的是让别人看见你怎样从结果反推原因、怎样控制变量，以及怎样把一次事故转化成长期验收条件。

## 80.15 从表象到根因的故障树

“效果变差”“延迟变高”“工具调用失败”都是表象，不能直接作为修复对象。一个可迁移的排查方式，是把故障先放进五层：数据、模型、协议、运行时、治理。

| 层次 | 典型问题 | 第一份证据 |
| --- | --- | --- |
| 数据 | 文档旧、解析错、污染、权限过滤漏掉 | 数据版本、样本和 provenance |
| 模型 | 路由、量化、模板或训练版本变化 | model revision、输入输出回放 |
| 协议 | schema、chat template、tool result 对不上 | 原始请求、响应和 parser 日志 |
| 运行时 | 队列、KV、网络、重试、资源不足 | trace、指标、状态账本 |
| 治理 | 权限、审批、灰度、回滚或审计缺失 | policy revision、变更单、事故记录 |

同一个错误可能跨越多层。例如 Agent 返回“已经发布”，原因可能是工具结果被 parser 截断（协议层），executor 实际已经提交（运行时层），而用户没有看到提交状态（治理层）。只修改 prompt，通常只是把症状推到下一次请求。

可以把排查写成一棵故障树：

```text
用户结果异常
├─ 输入是否正确到达？        -> 数据/协议
├─ 模型是否按预期生成？      -> 模型/模板
├─ 工具是否真实执行？        -> 运行时/状态
├─ 权限和审批是否仍有效？    -> 治理
└─ 修复后是否在同一分母回归？ -> 评测
```

这张树的价值不在于覆盖所有情况，而在于阻止“看到输出就直接归因于模型”的习惯。

## 80.16 “修好了”可能只是一次假恢复

一次回归通过不等于问题被修复。常见的假恢复有三种：把测试输入记住了，把流量限制到不会暴露问题的水平，或者用更激进的拒绝策略把所有危险和正常请求一起挡掉。

例如 RAG 的引用错误在十个固定问题上消失，可能只是把这十个问题加入了缓存；推理 p99 恢复，可能是把长请求全部拒绝；工具重复执行消失，可能是把工具整体关闭。它们都能让单一指标变好，却没有恢复真实能力。

修复验收至少需要三个对照：

1. 原故障样本：确认触发条件真的消失。
2. 邻近样本：输入长度、语言、权限、工具和版本略有变化时仍然成立。
3. 正常样本：确认修复没有把帮助性、延迟或可用性一起牺牲。

如果修复改变了路由、拒答、采样、缓存或权限，报告必须把这些变化写出来。一个更保守的系统可能更安全，但不能被描述成“模型质量提升”。

## 80.17 用分母和对照判断优化是否真实

大模型工程中最容易被误读的不是数字，而是数字的分母。设某项优化前后完成的成功任务数分别为 `S_0`、`S_1`，总成本为 `C_0`、`C_1`，则单位成功成本是：

~~~math
c_{\mathrm{success}}=\frac{C}{\max(1,S)}.
~~~

只报告 tokens/s、单轮延迟或生成长度，不能说明用户是否更快完成了任务。RAG 还要固定引用支持和权限正确率；Agent 还要固定副作用正确率和人工接管；推理服务还要固定长短请求混合比例与 p99。

一个可信的实验记录应同时保存 baseline、变更项、样本版本、模型/引擎版本、硬件、并发、质量验收条件、失败数和回滚条件。若优化只在短 prompt 或空 cache 下有效，就应把它写成条件结论，而不是“线上整体提升”。

## 80.18 失败故事要能承受面试追问

面试官通常会沿着五个方向追问失败：为什么当时这样设计、你看到什么信号、如何排除其他原因、修复带来了什么副作用、之后怎样防止复发。准备失败案例时，可以先写一条完整因果链：

```text
约束 -> 假设 -> 变更 -> 观测 -> 反证 -> 修复 -> 回归 -> 长期验收条件
```

比如“把 top-k 从 5 调到 20”只是变更；完整故事还要说明当时假设召回不足，观察到 evidence recall 上升但 citation support 下降，通过版本切片发现旧制度混入，最后增加有效期过滤和 rerank，并用固定回归集验证。这样追问每一环都有对象和证据。

如果某个细节没有亲自做过，正确回答是明确边界，然后说明验证计划：“这一部分我没有直接负责，只做过 toy 实验；如果上线，我会先固定版本和权限，在 shadow 模式比较副作用，再决定是否放量。”这比临时编造一个吞吐数字更能体现工程判断。

## 80.19 完整复盘例子：一次看似成功的 Agent 修复

某代码 Agent 在测试仓库中经常把修复提交到错误分支。第一版修复是在 prompt 中增加“请确认分支”，错误率在十个样例上下降。扩大到多仓库后，错误仍然发生，因为分支信息来自一个可能过期的自然语言上下文。

第二次排查把提交过程拆开：读取当前 repository revision，生成 patch artifact，运行测试，向服务端查询 branch protection，最后由 executor 以 revision 条件提交。测试不再只断言回复里出现了分支名，而是断言实际 commit 的 repository、branch、parent revision 和用户可见链接一致。

这次修复的成本是多一次状态查询和提交前校验，低风险草稿延迟略有上升；收益是错误副作用下降，而且权限和回滚边界变得清楚。复盘中应同时写出这项成本，否则读者会误以为可靠性可以无代价获得。

## 80.20 经验边界也属于工程能力

经验不是“做过某个热门组件”的标签，而是对作用域、证据和风险的准确描述。可以给每条简历或面试声明加上一个 claim ledger：

| 项目 | 必须回答 |
| --- | --- |
| 对象 | 哪个模型、服务、数据集或仓库 |
| 时间 | 哪个版本和时间窗口 |
| 个人贡献 | 我亲自改了什么、没有负责什么 |
| 基线 | 和什么方案比较 |
| 指标 | 质量、延迟、成本或安全如何定义 |
| 证据 | 代码、日志、报告、变更单或复盘在哪里 |
| 限制 | 哪些结论仍未在生产验证 |

这个账本不是为了让简历变长，而是为了防止一句强声明在追问中变成多个无法证明的细节。诚实地说“这是论文结论”“这是本地实验”“这是团队结果，我负责其中一段”，本身就是可靠性信号。

## 80.21 复盘练习：从一个坏指标开始

选择一个你曾经看到的“变好”指标，完成下面的练习：

1. 写出这个指标的分子和分母。
2. 找出至少两种不改变真实能力也能让它变好的方式。
3. 为每种方式设计一个反例或邻近样本。
4. 增加一个用户结果指标和一个安全/回滚指标。
5. 写出停止实验、回滚和继续放量的条件。

最后把练习压缩成两分钟回答，但保留完整记录。能指出指标可能骗人的地方，比背一个漂亮的提升百分比更能说明你真正理解了系统。

## 80.22 小结

常见失败并不复杂，但它们不能靠一句“多测试一下”解决。可靠的排查需要把表象分层到数据、模型、协议、运行时和治理，再用同一分母的对照实验确认修复；可靠的面试表达需要说清假设、证据、个人边界、代价和长期验收条件。

把 demo 当生产、堆术语、没有指标、只讲框架、忽视安全、硬编经验和只追热点，最终都指向同一个问题：没有把结论绑定到作用域和证据。真正可靠的候选人不是永远不犯错，而是能知道哪里错、为什么错、修复是否真的有效，以及下一次如何更早发现。
