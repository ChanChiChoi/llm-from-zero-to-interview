# 第81章：完整求职作战路线图

前面几章分别讨论了材料、模拟面试、offer 选择和失败案例。

这一章把所有内容整合成一条完整求职路线图。

目标是让你知道：从准备到投递，从面试到 offer，从入职到成长，每一步应该做什么。

## 81.1 第一阶段：定位目标岗位

先不要急着投简历。

先确定目标岗位。

大模型岗位至少分几类：

- 大模型应用工程师。
- RAG 工程师。
- Agent 工程师。
- 大模型算法工程师。
- 推理部署工程师。
- AI Infra 工程师。
- 评测平台工程师。
- 大模型产品工程师。

不同岗位准备重点不同。

应用工程师重 RAG、Agent、工具调用、上线和反馈。

算法工程师重模型原理、训练、微调、数据和实验。

推理工程师重 serving、KV cache、batching、并行、延迟和成本。

负责人岗位重路线图、跨团队协作、风险、成本和业务价值。

定位不清，简历和面试都会散。

## 81.2 第二阶段：补齐核心能力

根据目标岗位补能力。

最低公共能力包括：

- Transformer 和 LLM 基础。
- Prompt、RAG、Agent 基础。
- Python 和工程能力。
- 评测和实验方法。
- API、服务化和日志。
- 安全、权限和成本意识。

不要无限学习。

围绕目标岗位补最短路径。

例如投 RAG 岗位，就优先补：文档解析、chunk、embedding、hybrid retrieval、rerank、citation、评测、bad case。

例如投推理岗位，就优先补：prefill、decode、KV cache、PagedAttention、continuous batching、TTFT、TPOT、vLLM/SGLang。

## 81.3 第三阶段：做一个可讲项目

至少准备一个主项目。

主项目要能讲 30 分钟。

它应该包括：

- 背景。
- 问题。
- 架构。
- 数据。
- 模型。
- 评测。
- 指标。
- 风险。
- 成本。
- 失败和改进。

如果没有公司项目，可以做个人项目。

但个人项目要尽量生产化：

- 有 README。
- 有评测。
- 有错误分析。
- 有日志。
- 有安全边界说明。
- 有后续计划。

一个完整项目胜过五个浅 demo。

## 81.4 第四阶段：准备求职材料包

材料包包括：

- 一份目标岗位简历。
- 一个项目一页纸。
- 一个项目复盘。
- 一个 GitHub 或代码样例。
- 一个面试题库。
- 一个反向提问清单。

如果目标岗位不同，准备不同版本。

不要一份简历投所有岗位。

## 81.5 第五阶段：投递和内推

投递时要记录。

表格字段包括：

- 公司。
- 岗位。
- JD 要点。
- 投递渠道。
- 简历版本。
- 当前状态。
- 面试轮次。
- 面试问题。
- 复盘。
- 结果。

内推时不要只发简历。

最好附上：

- 目标岗位。
- 你和岗位匹配的三点。
- 一页纸项目摘要。
- GitHub 或作品链接。

让内推人更容易帮你。

## 81.6 第六阶段：面试准备

按轮次准备。

HR 面：讲动机、背景、期望、稳定性。

技术一面：讲原理和项目细节。

技术二面：讲系统设计、debug、实验和工程深度。

交叉面：讲协作、安全、成本、业务理解。

主管面：讲成长、owner 意识、路线图和影响力。

每轮都要准备反向问题。

面试是双向选择。

## 81.7 第七阶段：面试复盘和迭代

每场面试后立刻复盘。

记录：

- 问了什么。
- 答得如何。
- 追问在哪里。
- 暴露了什么短板。
- 团队有什么信息。
- 下一场如何改。

复盘后更新题库和标准回答。

求职过程本身就是训练过程。

越复盘，越稳定。

## 81.8 第八阶段：Offer 选择和谈薪

offer 选择看：

- 岗位真实性。
- 项目阶段。
- 团队能力。
- 个人职责。
- 资源支持。
- 成长空间。
- 组织稳定性。
- total compensation。

谈薪前明确底线。

拿到完整结构后再比较。

不要只看 base。

也不要只看短期薪资，忽略长期职业资产。

## 81.9 第九阶段：入职前准备

接受 offer 后，准备：

- 复习岗位相关技术。
- 整理 30-60-90 天计划。
- 确认汇报对象和第一个项目。
- 了解团队技术栈。
- 准备 onboarding 问题。

入职不是求职结束。

真正的职业收益要靠入职后兑现。

## 81.10 把求职看成一个有损漏斗

求职结果不是“投得越多越好”。每个阶段都会损失一部分机会：岗位筛选、简历通过、初面、技术面、终面和 offer。可以用一个简化漏斗估算需要补哪一环：

```math
N_{\mathrm{offer}}=N_{\mathrm{apply}}
\times p_{\mathrm{screen}}
\times p_{\mathrm{phone}}
\times p_{\mathrm{technical}}
\times p_{\mathrm{final}}
```

这不是预测个人命运的公式，而是诊断工具。如果投递很多但几乎没有面试，优先检查岗位匹配和简历证据；如果能过筛选却在技术一面失败，优先训练原理和项目深挖；如果终面很多却没有 offer，可能需要检查岗位选择、沟通、风险边界或团队匹配。

每周记录申请数、有效回复数、各轮通过率、拒绝原因和复盘完成率，比记录“今天投了多少份”更有用。样本还很小时，不要过度解读百分比；至少积累若干个同类岗位，再观察漏斗变化。

## 81.11 岗位矩阵与证据矩阵

目标岗位不能只按职位名称分类，要把 JD 的要求转成能力矩阵。以推理部署岗位为例，能力可能包括 prefill/decode、KV cache、batching、GPU/通信、SLO、故障恢复和成本。每项能力旁边再放证据：项目、代码、实验报告、指标、面试题和待补缺口。

| 能力 | 目标深度 | 可展示证据 | 当前缺口 |
| --- | --- | --- | --- |
| KV cache | 能估算并解释生命周期 | toy 实现、压测表、事故复盘 | 缺少抢占演练 |
| 调度 | 能说明连续 batching 取舍 | serving 设计图、p99 分桶 | 缺少多租户案例 |
| 评测 | 能定义质量和 SLO 验收条件 | 固定回归集、报告 | 需补成本分母 |
| 安全 | 能说清权限和回滚 | tool audit、故障演练 | 需补高风险场景 |

“学过”不等于“可证明”。当一个知识点没有任何可复述的证据时，它应该进入本周的补课任务，而不是继续扩充新的热点清单。

## 81.12 从一个项目生成整套材料

一个真实项目可以生成多种材料，但每种材料服务的阅读时间不同。30 秒介绍回答“做了什么”；一页纸回答“为什么可信”；代码仓库回答“能否复查”；项目复盘回答“遇到什么失败”；系统设计回答“能否迁移到更大规模”。它们应共享事实账本，却不能复制同一段宣传语。

以企业 RAG 项目为例，事实账本应保存数据规模、评测集版本、基线、变更、质量、延迟、成本、权限和个人贡献。简历只选两三个最有区分度的结果；面试深挖时再展开检索错误、版本冲突和回滚。这样可以避免简历数字与口头回答互相矛盾。

一个项目的证据闭环可以写成：

```text
问题 -> 方案 -> 对照 -> 指标 -> 失败 -> 修复 -> 回归 -> 个人贡献
```

缺少对照或回归的“提升”，只是一次观测；缺少个人贡献的完整架构，也不能证明候选人真正做过。

## 81.13 一周冲刺和阶段门

求职准备适合使用阶段门，而不是无限学习。第一阶段的门是“目标岗位和拒绝条件明确”；第二阶段的门是“一个项目能在 2 分钟、10 分钟和追问下保持一致”；第三阶段的门是“必考主题有固定回答和至少一个证据”；第四阶段的门是“至少完成一次完整模拟并修复最高风险缺口”。

每个阶段只保留有限的工作项。例如一周冲刺可以安排：周一岗位矩阵和简历事实账本，周二项目讲解和指标核对，周三原理与代码题，周四系统设计和 debug，周五安全/成本/行为面，周六完整模拟，周日复盘与投递。若某天暴露了一个关键缺口，应减少新主题，把时间转给修复和复测。

冲刺计划还要留出真实生活约束。每天学习时间、面试安排、睡眠和通勤都会影响输出；把不可执行的 12 小时计划写得很完整，并不会提高通过率。可持续的节奏比短期堆量更容易形成稳定表达。

## 81.14 Offer 的多目标决策

offer 比较不能只看 base salary。岗位真实性、技术成长、团队质量、业务稳定性、职责边界、管理风险和总收入共同决定长期结果。可以先建立约束，再做加权比较：

```math
U(o)=\sum_i w_i v_i(o)-\sum_j \lambda_j r_j(o)
```

其中 `v_i` 是岗位价值维度，`r_j` 是风险维度；权重反映个人阶段，不能把它当作客观排名。若一个岗位的关键职责、汇报关系或业务来源无法确认，就应作为硬风险记录，而不是用高薪直接抵消。

谈薪前列出总包构成、归属周期、奖金条件、试用期、办公地点、加班和岗位取消风险。向团队确认入职后的前三个月目标、可用资源、评测口径和技术决策权。好的 offer 决策不是选择一个听起来最先进的模型，而是选择一个能够持续形成真实交付和可迁移证据的环境。

## 81.15 学习投入要服从岗位证据缺口

求职期最容易出现的浪费，是继续阅读已经熟悉的主题，却不修复面试中真正暴露的缺口。可以给每项能力记录三个值：岗位重要度 `w`、当前证据缺口 `g`、补齐所需时间 `t`。一个简单的优先级为：

~~~math
P_i=\frac{w_i g_i}{\max(1,t_i)}.
~~~

高优先级不一定是最热门的技术，而是“岗位会问、你说不清、短时间可以形成证据”的交集。比如目标是推理工程岗，已经看过很多模型新闻，但不会估算 KV、解释 p99 或设计回滚，那么继续收集模型名称的收益通常低于完成一次可复现压测。

## 81.16 项目选择要看可交付闭环

一个项目是否适合求职，不取决于名字听起来是否前沿，而取决于能否形成问题、方案、对照、失败和结果的闭环。选择候选项目时可以检查：数据是否可合法获得，问题是否有可测指标，基线是否能运行，个人贡献是否足够独立，失败是否能在有限时间内复现，最终资产是否能被别人检查。

“做一个大模型平台”通常太大；“在固定数据集上比较三种检索策略，加入引用校验，并测质量、延迟和成本”更适合形成证据。项目越小，越容易把因果链讲清；项目不是越大越有说服力。

## 81.17 一份材料包要共享事实而不是共享宣传语

求职材料至少有五种阅读场景：简历筛选、30 秒自我介绍、10 分钟项目深挖、系统设计迁移和行为面复盘。它们可以来自同一事实账本，但不应复制同一段形容词。

| 材料 | 读者要判断什么 | 最小内容 |
| --- | --- | --- |
| 简历 bullet | 你做过什么并产生了什么结果 | 对象、动作、指标、边界 |
| 项目一页纸 | 结果是否可信 | 问题、基线、对照、失败、证据 |
| 代码仓库 | 能否复查 | 环境、入口、配置、测试、限制 |
| 口头回答 | 是否真的理解 | 机制、取舍、个人贡献、追问 |
| 复盘文档 | 是否能从失败学习 | 时间线、根因、修复、回归 |

材料之间的数字、版本和个人贡献必须一致。若简历写“降低延迟 40%”，一页纸应能说明是 TTFT 还是 p99、基线是什么、样本和硬件是什么；否则数字越大，越容易成为风险。

## 81.18 投递漏斗需要按原因分流

每一轮失败都有不同修复动作。筛选通过率低，可能是目标岗位不匹配或简历证据不足；技术面失败，可能是原理、代码或项目深挖；终面失败，可能是沟通、边界、团队匹配或风险判断。把所有拒绝都归因于“竞争激烈”，不会产生下一步动作。

每周可以记录：有效申请数、回复数、筛选通过数、各面试轮通过数、拒绝原因、复盘完成率和材料版本。样本很少时只保留事件记录，不要用几个样本算出看似精确的概率；随着同类岗位增多，再观察哪一段漏斗持续偏低。

## 81.19 面试准备要覆盖三种深度

同一个项目至少要准备 30 秒、2 分钟和 10 分钟三个版本。30 秒只讲问题、动作和结果；2 分钟补基线、个人贡献和关键取舍；10 分钟准备数据、代码、失败、上线约束、权限、成本、回滚和替代方案。

原理题也有类似层次：先用直觉回答，再给公式/流程，再落到实现和边界。面试官把 batch size、硬件、数据分布或目标指标换掉时，回答仍应保持一致的因果关系，而不是依赖背诵模板。

## 81.20 Offer 尽调要验证“工作是否真实存在”

Offer 比较不只看薪资，还要验证岗位承诺是否能落地。可以在接受前确认：前三个月目标、真实数据和用户、模型/服务的 ownership、上线评测、事故责任、汇报关系、团队流动、资源配额、工作地点和岗位取消条件。

如果一个岗位只描述“负责最前沿模型”，却说不清问题、用户、指标、代码 ownership 和决策边界，应把它作为不确定性记录。高薪可以补偿一部分短期风险，但不能自动补偿无法形成真实交付和可迁移证据的环境。

## 81.21 入职后的第一个闭环

求职路线在入职后才真正接受验证。前 30 天应先理解系统、指标、权限和风险边界；接着选择一个小而可回滚的改进，建立 baseline、变更记录和回归；再决定是否扩大范围。不要刚入职就根据面试中的架构印象重写核心系统。

一个好的第一个项目不一定是最大项目，而是能让你看到完整链路：需求、数据、模型、运行时、监控、评测、发布和复盘。这个闭环会把求职阶段的“可证明能力”转化为真实的技术信任。

## 81.22 小结

完整求职路线不是“投简历、刷题、面试”，而是围绕目标岗位建立证据系统：定位岗位，识别缺口，做可交付项目，维护事实一致的材料包，按漏斗原因迭代，准备不同深度的表达，审慎选择 offer，再用入职后的第一个闭环兑现承诺。

每一步都要形成资产，但资产不是文字数量，而是别人能复查、你能解释、结果有边界的证据。当求职被当成一个有指标、有阶段门、有失败复盘的系统，短期面试准备和长期职业成长才会连接起来。
