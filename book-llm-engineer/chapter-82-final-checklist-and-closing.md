# 第82章：最终自检清单与补充篇总结

这一章是大模型工程师面试补充篇的收束章。

从第 60 章到第 82 章，我们讨论了从项目包装、面试表达、入职成长、技术判断、跨团队影响、路线图、指标复盘、安全风险、成本 ROI、长期成长，到求职材料、模拟面试、offer 选择和完整求职路线。

这套内容的目标不是制造焦虑，而是帮助你把“大模型工程师”从一个模糊岗位，拆成一套可训练、可证明、可成长的能力系统。

## 82.1 项目能力自检

你应该能回答：

- 我最核心的 1-2 个项目是什么？
- 每个项目解决了什么真实问题？
- 我的具体贡献是什么？
- 系统架构是什么？
- 数据链路是什么？
- 使用了哪些模型和工具？
- 如何评测？
- 指标如何变化？
- 失败 case 是什么？
- 安全和成本如何处理？
- 如果重做一次，我会怎么改？

如果这些问题答不清，先补项目复盘。

## 82.2 技术能力自检

你应该能解释：

- Transformer 和 attention。
- tokenization 和 position encoding。
- pretraining、SFT、RLHF、DPO。
- LoRA 和参数高效微调。
- RAG 的完整链路。
- embedding、hybrid retrieval、rerank。
- Agent、function calling、tool use。
- LLM eval 和 LLM-as-a-judge。
- KV cache、prefill、decode。
- vLLM、SGLang、PagedAttention、continuous batching。
- prompt injection、权限、审计和安全边界。

不要求每个方向都源码级深入。

但至少要能讲清核心机制、适用场景和 trade-off。

## 82.3 工程能力自检

你应该能讲清：

- 如何设计一个生产级 RAG 系统。
- 如何设计一个安全 Agent 系统。
- 如何设计一个推理服务。
- 如何设计评测平台。
- 如何做灰度和回滚。
- 如何做日志和 trace。
- 如何排查质量下降。
- 如何排查延迟上升。
- 如何做成本归因。
- 如何处理线上事故。

大模型工程师不是只调 prompt。

你要能把模型放进真实系统。

## 82.4 面试表达自检

你应该准备：

- 30 秒自我介绍。
- 2 分钟自我介绍。
- 30 秒项目介绍。
- 2 分钟项目介绍。
- 10 分钟项目深挖版本。
- 5 个行为面故事。
- 3 个系统设计模板。
- 5 个 debug 排查模板。
- 1 份反向提问清单。
- 1 份英语项目介绍。

所有回答都要结构化。

不要临场组织。

## 82.5 求职材料自检

你应该有：

- 一份目标岗位简历。
- 一个项目一页纸。
- 一个项目复盘文档。
- 一个 GitHub README 或代码样例。
- 一个面试题库。
- 一个公司投递跟踪表。
- 一个 offer 对比表。
- 一个 30-60-90 天计划。

材料不是一次性准备。

每次面试和项目后都要更新。

## 82.6 职业判断自检

你应该能判断：

- 这个岗位是真大模型工程，还是 API 包装？
- 这个团队是否有真实用户？
- 是否有评测闭环？
- 是否有安全和成本意识？
- 是否有技术 owner？
- 是否有资源支持？
- 我能否负责完整问题？
- 未来 1-2 年能否形成职业资产？

好的职业选择，不只是拿到 offer。

而是进入一个能持续成长和交付的环境。

## 82.7 最后一版求职前检查

投递前，检查：

- 简历是否匹配目标岗位。
- 项目是否有指标。
- 是否有一页纸。
- 是否能讲失败和取舍。
- 是否准备反向问题。
- 是否知道自己的薪资底线。
- 是否准备好面试复盘表。

面试前，检查：

- 核心项目是否能 2 分钟讲完。
- 高频原理题是否能讲清。
- 系统设计是否有模板。
- debug 是否有排查顺序。
- 行为故事是否有结果和反思。
- 英语表达是否练过。

拿 offer 前，检查：

- 岗位职责是否清楚。
- 前 90 天目标是否清楚。
- 汇报对象是否清楚。
- 薪酬结构是否完整。
- 成长空间是否真实。
- 风险是否可接受。

## 82.8 自检表必须有证据和通过条件

“我会 RAG”“我懂 Agent”“我熟悉推理优化”都不是可审计的自检结果。每个条目至少要绑定一个对象、一个动作和一个证据。例如：能否在固定数据集上算出 Recall@k；能否解释一次工具调用失败并指出权限 gate；能否根据层数、KV head、head dimension 和 dtype 估算单请求 cache；能否展示一次回滚或故障演练。

自检表可以采用三档状态：`已理解`、`可独立实现`、`可在追问/事故中解释`。只有第一档的知识适合继续阅读，第二档才适合写进项目能力，第三档才足以承担资深面试或生产设计。状态必须附日期和证据链接，否则几周后很容易把“看过”误认为“掌握”。

## 82.9 一次完整自审的顺序

自审不要从最喜欢的模型架构开始，而应从最能暴露风险的项目开始。先随机抽一个项目，用 2 分钟讲清目标和个人贡献；然后追问数据、指标、失败、安全、成本和回滚。接着随机抽一个核心原理，现场写公式或伪代码；最后做一个系统设计变体，检查知识能否迁移。

如果回答中出现“应该”“一般来说”“效果很好”这类没有对象和条件的句子，继续追问：在哪个版本、什么数据、什么基线、什么硬件、哪个 SLO、用什么证据。自审的价值不是把每个答案变长，而是把无条件的断言变成有作用域的工程结论。

## 82.10 最后七天的行动安排

最后一周不适合再开一套全新的课程。第一天核对简历和项目事实，第二天做原理与代码抽查，第三天做系统设计，第四天做质量/安全/成本 debug，第五天完整模拟，第六天修复三个最高风险缺口，第七天准备设备、材料、反向问题和休息。

每一天结束时只保留三项记录：已经通过的门、尚未通过的门、下一次可验证的动作。这样能够避免在焦虑中不断收集资料，却没有任何能力状态发生变化。

## 82.11 常见的“假通过”

有几种状态看起来像准备充分，实际上不能支撑面试。背熟一段标准答案但经不起改变数字，是记忆不是理解；能跑通 demo 但说不清输入、输出和失败路径，是使用不是掌握；能复述 benchmark 名称但不知道 grader 和数据污染，是见闻不是评估能力；能讲架构图但不知道成本、权限和回滚，是设计表面而不是系统判断。

另一个假通过是把所有缺口都归因于模型。RAG 的错误可能来自解析和权限，Agent 的错误可能来自工具 schema，延迟可能来自队列和 KV，量化退化可能来自 kernel fallback。最终自检要强制自己把问题分到数据、模型、协议、运行时和治理五层，再给出验证动作。

## 82.12 一个可复用的项目自审记录

可以用下面的格式写最后一份项目自审：

```text
项目：企业知识库 RAG
目标：回答必须有可追溯引用，P95 <= 3s
基线：dense retrieval + 单一生成模型
我的贡献：解析、hybrid retrieval、citation verifier
证据：固定评测集 v3，n=240；citation support 0.71 -> 0.86
失败：旧版本文档混入，p99 在高并发下超时
修复：版本过滤、rerank、队列监控、灰度回滚
未知：真实删除传播和跨租户容量仍需生产验证
下一步：补多租户权限回放和长文档成本分桶
```

这份记录同时服务简历、项目介绍、系统设计和行为面。它没有假装所有问题都已解决，但清楚地说明了哪些结果已经证实、哪些只是实验、哪些仍需验证。

## 82.13 把自检表变成证据矩阵

最终自检不应是“我会/我不会”的勾选，而要记录能力、动作、证据、作用域和下一步。一个可复用的矩阵如下：

| 能力 | 可观察动作 | 证据 | 作用域 | 下一步 |
| --- | --- | --- | --- | --- |
| KV cache | 估算指定模型和长度的显存 | 计算表、压测日志 | toy/本地服务 | 补抢占回放 |
| RAG | 解释引用错误并修复 | 固定评测集、diff | 公开文档 | 补权限切片 |
| Agent | 处理工具半成功 | 状态机和演练 | 沙箱 | 补真实工具契约 |
| 安全 | 说明高风险动作验收条件 | policy trace | 模拟场景 | 做红队回放 |

“作用域”非常重要。一个本地 demo 的证据不能自动升级为生产经验；一篇论文的理解不能自动升级为实现能力；一次线上事故的参与也不能自动升级为独立 owner。自检表只有把作用域写出来，才不会产生虚假的确定感。

## 82.14 五层审计：数据、模型、协议、运行时、治理

任何一个项目都可以用五层审计做最后检查：

1. **数据**：来源、版本、权限、污染、切分和脱敏是否清楚。
2. **模型**：revision、输入输出、训练/量化、上下文和能力边界是否清楚。
3. **协议**：tokenizer、template、schema、tool result、错误和流式事件是否一致。
4. **运行时**：队列、KV、缓存、重试、超时、资源、日志和回滚是否可观测。
5. **治理**：身份、最小权限、审批、审计、人工接管、隐私和事故责任是否明确。

面试中遇到任何“效果为什么变差”的问题，都可以沿这五层排查；项目自检中如果完全没有某一层的证据，就不要把项目描述成完整生产系统。

## 82.15 随机抽查比重复背诵更能发现缺口

自检时不要只挑最熟悉的题。可以随机抽一个项目、一个公式、一个失败案例和一个系统设计变体：

```text
项目：2 分钟说明目标、基线、个人贡献和结果
公式：现场写出变量、假设和一个数量例子
失败：说明信号、根因、修复、副作用和回归
设计：改变流量、权限或模型版本后重新画边界
```

如果只能在原始数字下回答，说明是记忆；如果改了约束仍能从原则推导，才说明理解已经迁移。随机抽查还应记录耗时、缺失证据和下次练习，而不是只记录“今天复习过”。

## 82.16 声明审计：每一句强结论都有边界

简历、项目文档和面试回答里的强断言需要逐句审计。对“提升”“负责”“上线”“支持”“实时”“生产级”“低成本”等词，分别问：对象是什么，基线是什么，版本和硬件是什么，样本多大，谁做了什么，是否可回滚，哪些条件没有验证。

例如“支持百万上下文”至少要区分接口可接受、模型训练过、能检索中间证据、能完成跨段推理和单位成功成本可接受。把营销口径压缩成一个绝对结论，会让后续所有回答失去可信度。

## 82.17 最后一周的修复顺序

最后阶段不应平均补所有缺口。优先修复会导致硬失败的项目：个人贡献说不清、核心公式不会、关键代码不能运行、指标没有分母、权限边界缺失、失败路径没有回滚。之后再修复表达长度、补充前沿名词和美化文档。

可以用一个简单的风险排序：

~~~math
R_i=I_i\times P_i\times\frac{1}{\max(1,e_i)},
~~~

其中 `I_i` 是失败影响，`P_i` 是被追问或触发的可能性，`e_i` 是现有证据强度。这个式子不是精确概率，而是帮助把时间投入到“最可能让整段回答失效”的缺口。

## 82.18 行动合同和停止条件

每次复习结束时写下一条可验证行动，例如“在固定三种长度上跑 KV 估算并保存输出”“用两个权限版本回放工具半成功”“把项目 bullet 的 p99 分母补进一页纸”。同时写停止条件：输出一致、回归通过、能在两分钟内解释，或明确记录为未知。

没有停止条件的学习会不断收集新资料，却不产生能力变化；没有未知记录的自检会迫使人用猜测填空。把未知写出来并不等于失败，而是让下一步有明确对象。

## 82.19 结业练习：交付一份最终能力包

最后交付物至少包括：一页简历事实账本、一个可运行项目、一次固定评测报告、一份失败复盘、一个系统设计图、一个安全/权限演练记录、三组不同深度的项目回答和一张证据矩阵。每项都标明版本、日期、个人贡献和未验证边界。

交付前请找一个不了解项目的人，只给他看 README、评测报告和两分钟讲稿，观察他是否能回答：你解决了什么问题，为什么相信结果，失败在哪里，谁能复现，下一步风险是什么。如果他只能看到宣传语，说明材料还没有变成证据。

## 82.20 补充篇总结

大模型工程师的竞争力，不是一组孤立技能，而是一套能被复查的系统能力：理解模型原理，完成工程落地，设计评测，处理线上问题，承担安全和成本责任，跨团队沟通并沉淀资产。

面试是这套能力的一次展示，求职是职业路径的一段。真正长期有效的是把真实问题转化成项目，把项目转化成复盘，把复盘转化成能力，再用新的交付检验能力。读完材料之后，最终动作不是继续收集名词，而是交付证据、接受追问、记录未知并持续修复。
