# 第 6 章（第二部分）：量化与推测解码

如果前面的显存估算显示权重或 KV Cache 占用过高，量化可能释放空间。但“4 bit”只描述一部分数值怎样存储，不能直接推出运行速度、总显存或任务质量。本节先用对称量化的公式说明 scale 与误差，再分别检查权重、计算激活和 KV Cache 的占用；最后用同一评估集确认质量变化是否可接受。

## 6.4 量化：分别看权重、计算和 KV Cache 的占用

### 6.4.1 4 bit 只说明一种存储表示

浮点权重可以用 16 bit、8 bit 或 4 bit 等更少的位数表示。直觉上，位数越少，权重越小，模型越容易放入显存；但模型运行时还需要把量化权重用于矩阵乘法，可能在 kernel 内部反量化，也可能使用专门的低精度计算指令。

“这是 4 bit 模型”至少可能在说：

```text
权重存储是 4 bit；
权重按组共享 scale；
激活仍然是 BF16/FP16；
累加在 FP16/FP32 或某种低精度中；
KV Cache 仍然是 BF16/FP8/INT8；
部分层（embedding、lm_head、norm）没有量化；
scale 和零点使用额外的高精度元数据。
```

所以位数标签不能单独回答“显存多少、延迟多少、质量损失多少”。需要把存储、反量化、计算、KV 和未量化部分分开记录。

### 6.4.2 对称量化的基本公式

对一组浮点权重 $w$，以有符号整数范围 $[-q_{\max},q_{\max}]$ 为例，常见的对称量化步骤是：

```math
s
=
\frac{\max_{i} |w_{i}|}{q_{\max}}
```

```math
q_{i}
=
\mathrm{clip}
\left(
\mathrm{round}\left(\frac{w_{i}}{s}\right),
-q_{\max},q_{\max}
\right)
```

反量化为：

```math
\widehat w_{i}=sq_{i}
```

量化误差可以用均方误差衡量：

```math
\mathrm{MSE}
=
\frac{1}{N}
\sum_{i=1}^{N}
(w_{i}-\widehat w_{i})^2
```

这里要求 $N>0$，并且每个 $w_{i}$ 与 $\widehat w_{i}$ 都是有限数；空权重集合没有均方误差可言。

如果整层共享一个 scale，极端 outlier 会把 scale 拉大，使大多数普通权重只能使用很少的有效离散级别。按 channel、按 group 或采用更适合分布的编码，可以改善误差，但会增加 scale 数量和 kernel 复杂度。

对于 group size 为 $g$ 的 per-group quantization，权重参数量为 $P$，scale 数量大约是：

```math
N_{\mathrm{scale}}
\approx
\left\lceil\frac{P}{g}\right\rceil
```

若每个量化值占 $b$ bit、每个 scale 占 $s_{\mathrm{scale}}$ 字节，则忽略零点的存储近似为：

```math
M_{\mathrm{weight}}
\approx
\frac{Pb}{8}
+
\left\lceil\frac{P}{g}\right\rceil
s_{\mathrm{scale}}
```

这说明 4 bit 并不意味着每个参数恰好只占 0.5 字节。

### 6.4.3 FP16、BF16、INT8、INT4 和 NF4 的差异

这些格式解决的问题不完全相同：

```text
FP16/BF16：
  浮点存储与计算格式，通常不称为权重量化；BF16 指数范围较大。

INT8：
  整数量化；需要 scale，可能按 tensor、channel 或 group。

INT4：
  更低比特整数权重；误差和 kernel 支持更敏感。

NF4：
  面向近似正态权重分布设计的 4 bit codebook，不是简单的均匀整数刻度；
  常与 QLoRA 的低显存训练路径一起讨论。

FP8/FP4：
  浮点或自定义低精度表示；具体 exponent、mantissa、scale 和硬件支持
  取决于格式标准与 runtime。
```

如果权重存储为 INT4，但每次矩阵乘法都将其反量化到 BF16，再调用 BF16 kernel，收益主要来自权重显存和内存带宽；如果硬件有高效的低比特 GEMM，延迟收益可能更明显；如果反量化和 kernel 融合不好，可能出现“显存下降但速度没有提升”。

### 6.4.4 粗略估算 7B 模型的权重显存

只按约 70 亿个参数估算，暂不计词表头以外的状态、量化元数据和运行时工作区：

```math
M_{\mathrm{FP16}}
\approx
7\times10^9\times2
=14\times10^9\ \mathrm{bytes}
\approx13.04\ \mathrm{GiB}
```

```math
M_{\mathrm{INT8}}
\approx
7\times10^9\times1
=7\times10^9\ \mathrm{bytes}
\approx6.52\ \mathrm{GiB}
```

```math
M_{\mathrm{INT4,raw}}
\approx
7\times10^9\times0.5
=3.5\times10^9\ \mathrm{bytes}
\approx3.26\ \mathrm{GiB}
```

实际 INT4 还要计入 scale、zero point、未量化层、权重对齐、runtime buffer 和 KV Cache。只估算权重不能判断模型能否在某张卡上运行，还需要把其余显存占用也算进去。

再把分组 scale 单独算出来。每组 128 个参数共需要 $\lceil7{,}000{,}000{,}000/128\rceil=54{,}687{,}500$ 个 scale。若每个 scale 用 2 字节，额外约 109,375,000 bytes，即 0.102 GiB；只计 4-bit 权重与这些 scale，约为 $3.26+0.10=3.36\ \mathrm{GiB}$。零点、未量化层、对齐和加载时临时缓冲仍未计入。这里用十进制 GB 表示文件字节数，用二进制 GiB 表示显存；两种单位不要混写。不同格式的 scale 粒度和零点编码不同，实际大小要看 checkpoint 文件与加载后的 runtime 分配。

### 6.4.5 无依赖的分组量化 demo

下面的 demo 对一维权重做 per-group 对称量化，输出误差随 group size 的变化。它只验证公式，不模拟真实 fused kernel。

> 代码状态：静态审阅，未运行（2026-10-29）
```python
import math


def quantize_group(values, bits):
    values = list(values)
    if not values:
        raise ValueError("a quantization group must not be empty")
    if type(bits) is not int or bits < 2:
        raise ValueError("bits must be an integer of at least 2")
    if any(
        not isinstance(value, (int, float))
        or not math.isfinite(value)
        for value in values
    ):
        raise ValueError("values must be finite numbers")
    qmax = (1 << (bits - 1)) - 1
    if qmax <= 0:
        raise ValueError("qmax must be positive")
    peak = max(abs(value) for value in values)
    # An all-zero group has no meaningful data-dependent scale.  Keep a
    # non-zero sentinel scale so dequantization remains well-defined.
    scale = peak / qmax if peak else 1.0
    quantized = [
        max(-qmax, min(qmax, round(value / scale)))
        for value in values
    ]
    restored = [scale * value for value in quantized]
    return restored, scale


def grouped_quantize(values, group_size, bits=4):
    values = list(values)
    if not values:
        raise ValueError("values must not be empty")
    if type(group_size) is not int or group_size <= 0:
        raise ValueError("group_size must be a positive integer")
    restored = []
    scales = []
    for start in range(0, len(values), group_size):
        group = values[start:start + group_size]
        decoded, scale = quantize_group(group, bits)
        restored.extend(decoded)
        scales.append(scale)
    mse = sum(
        (left - right) ** 2 for left, right in zip(values, restored)
    ) / len(values)
    if not math.isfinite(mse):
        raise ValueError("MSE must be finite")
    return restored, scales, mse


weights = [0.02, -0.11, 0.24, 0.47, 2.8, -0.32, 0.18, -0.07]
for group_size in (8, 4, 2):
    decoded, scales, mse = grouped_quantize(weights, group_size)
    print(
        "group_size=", group_size,
        "scale_count=", len(scales),
        "mse=", round(mse, 8),
        "decoded=", [round(value, 3) for value in decoded],
    )
```
当同一组里出现 2.8 这样的 outlier 时，小权重的量化误差会变大；缩小 group size 可以让普通值使用更合适的 scale，但 scale 元数据增加。toy demo 的 MSE 不对应某个语言模型的困惑度变化。

### 6.4.6 QLoRA、NF4 和 double quant 的位置

QLoRA 的工程组合通常包含：

```text
冻结的低比特基座权重
      ↓
反量化到计算数据类型
      ↓
LoRA adapter 参与前向与反向
      ↓
只更新 adapter 参数
```

LoRA 增量写成：

```math
W_{\mathrm{eff}}
=
W_{\mathrm{base}}
+
\frac{\alpha}{r}BA
```

低比特基座的量化主要减少模型参数的存储和训练显存；它不等于 adapter 也使用低比特，也不等于优化器状态完全消失。NF4、double quant 和 paged optimizer 的具体实现需要跟随 bitsandbytes/PEFT/Transformers 版本确认。

下面只展示量化基座模型的加载片段，便于观察 NF4 配置如何进入模型加载；它不是完整 QLoRA 训练脚本，未包含 LoRA adapter、数据、optimizer 或训练循环。模型快照固定为第三册前文使用的 [Qwen2.5-0.5B revision](https://huggingface.co/Qwen/Qwen2.5-0.5B/tree/b937cc073b55e980e6f21d5f8b7a77818efcf0eb)，单 GPU 场景让训练框架负责设备放置：

> 代码状态：静态审阅，未运行（2026-10-29）
```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig


if not torch.cuda.is_available():
    raise RuntimeError("this quantized loading example requires CUDA")
compute_dtype = (
    torch.bfloat16
    if torch.cuda.is_bf16_supported()
    else torch.float16
)

quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=compute_dtype,
    bnb_4bit_use_double_quant=True,
)
model_name = "Qwen/Qwen2.5-0.5B"
model_revision = "b937cc073b55e980e6f21d5f8b7a77818efcf0eb"
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    revision=model_revision,
    quantization_config=quant_config,
)
```
这段片段依赖 Transformers、PyTorch、bitsandbytes 和 GPU 上可用的 4-bit kernel；计算 dtype 在 BF16 可用时选 BF16，否则退到 FP16。省略 `device_map="auto"` 是因为此处讨论训练加载；Transformers v5.17.0 的 bitsandbytes 文档把自动设备映射限定为推理路径，训练应交由所选训练框架管理设备或采用其支持的并行策略。不能因为配置对象能成功构造，就推断目标模型所有层都已用 NF4，或推断推理延迟一定下降。完整的 QLoRA 训练流程见[微调实战的 QLoRA 部分](04-huggingface微调实战-2-lora与qlora.md#45-qlora量化基座上的低秩训练)。

### 6.4.7 KV Cache 量化是另一条链路

权重量化与 KV Cache 量化的对象不同：

```text
权重量化：
  影响模型参数的存储和 GEMM 输入。

激活量化：
  影响中间激活的表示和计算路径。

KV Cache 量化：
  影响每个请求随上下文增长的历史状态存储与读取。
```

KV Cache 量化的显存公式可以沿用：

```math
M_{\mathrm{KV}}
=
2BLTn_{\mathrm{kv}}d_{h}s_{\mathrm{kv}}
+
M_{\mathrm{scale}}+M_{\mathrm{metadata}}
```

其中 $s_{\mathrm{kv}}$ 可以低于 FP16 的 2 字节，但 scale 的粒度、量化误差、反量化 kernel 和不同层/不同通道的动态范围都需要测量。长上下文场景中，KV Cache 量化可能比继续压缩已经很小的权重更直接地改善并发容量；短 prompt、低并发场景则未必如此。

例如前一部分按 BF16 算出的 1 GiB cache，若只把每个 K/V 元素改成 8 bit，理想 payload 会降到约 512 MiB；这还没有加入 scale、对齐和元数据，也没有说明注意力 kernel 能否高效读取这种格式。

UltraQuant 是 2026 年提出的 4-bit KV 路线之一。论文在 context-heavy Agent trace 上比较了 BF16、FP8 和其低比特方案，并把并发下的驻留容量、满足 TTFT SLO 的 goodput 与目标硬件 kernel 一起测量。该结果说明“压缩元素”只是链路一段：如果低比特格式没有高效解量化路径，或工作负载本来没有 cache 容量压力，goodput 不一定随位数降低而提升。论文实验使用 AMD MI355X 和特定模型、trace 与 SLO，具体数字不能外推到其他设备或 runtime；vLLM v0.32.0 文档中列出相应 dtype 也只表示配置入口，不构成兼容性或性能保证。见 [UltraQuant v3](https://arxiv.org/abs/2606.20474v3) 与 [vLLM EngineArgs](https://docs.vllm.ai/en/v0.32.0/configuration/engine_args/)。

### 6.4.8 量化质量回归应该测什么

量化评估至少要包含四层：

1. 数值层：权重/激活重构误差、logits 最大差、KL 或校准集 perplexity；
2. 任务层：分类、抽取、数学、代码、工具参数解析和长上下文检索；
3. 生成层：长度、重复、格式、停止、拒答和事实性；
4. 系统层：显存峰值、TTFT、TPOT、吞吐、p95、功耗和失败率。

只测一组通用 benchmark，可能漏掉量化对结构化输出或少数语言的影响。可以按层或模块做消融：只量化 attention、只量化 MLP、保留 lm_head、改变 group size、改变 calibration data，再记录行为回归。

### 6.4.9 失败模式

量化项目常见的失败原因包括：

```text
量化后显存下降，但 kernel 不支持，运行时退回高开销路径；
权重是 INT4，激活和 KV 仍是 BF16，实际总显存没有按标签比例下降；
校准数据只覆盖通用英文，领域术语、代码或中文质量回归；
outlier 集中在少数层，统一量化策略让这些层损失过大；
embedding、norm、lm_head 的处理与主干不同，却被当作全部量化；
只比较平均 latency，没有比较 p95、长 prompt 和并发；
量化误差造成 JSON、tool call 或 stop token 解析失败；
把 toy MSE 直接解释成真实模型能力下降百分比。
```

排查时看显存在哪个阶段增长：加载时失败，先核权重和量化元数据；prefill 时失败，检查临时激活与 workspace；decode 中途失败，再看 KV、并发和缓存池。只有同一请求分布下质量护栏通过、显存或延迟确有改善，量化才是有效的服务优化。若主要瓶颈转为逐 token 的串行计算，下一节再看推测解码。

量化主要改变权重或缓存的数值表示；推测解码改变的是生成算法。目标模型仍决定最终分布，小模型或 draft head 先提出若干候选，目标模型再并行核验。它只有在少做的目标模型串行计算足以抵消 draft、验证和调度开销时才有价值。

本节先区分贪心生成和采样生成的正确性要求，再推导接受率与每轮成本，最后给出怎样比较单请求收益与服务级吞吐的方法。读者会得到一个“是否值得启用”的测量清单，而不是只记住一个接受率数字。

## 6.5 Speculative Decoding：让小模型先提议，大模型批量验证

### 6.5.1 一次核验为什么可能接受多个 token

目标模型通常很大，生成一个 token 就要运行一次昂贵的 decode。另一个更小的 draft model 可以先连续生成若干 token；目标模型把这段候选作为一个小序列一次性计算并验证。如果候选大部分正确，就能用一次 target forward 接受多个 token。

```text
已有前缀
  ↓
draft：提出 d1, d2, d3, d4
  ↓
target：并行计算这些位置的概率
  ↓
接受共同前缀，例如 d1, d2
  ↓
在第一个不一致位置使用 target 的结果继续
```

收益来自两个事实：

1. 小模型生成多个 token 的成本低于目标模型逐 token 生成；
2. target 可以在更适合并行的形状上同时验证多个候选位置。

如果 draft 与 target 差异太大，接受率低，额外的 draft 计算、候选整理和验证 kernel 可能抵消收益。

### 6.5.2 Greedy 验证的教学版

对于贪心解码，可以用较直观的规则说明：

```math
\hat y_{i}^{\mathrm{draft}}
=
\arg\max_{v} q_{i}(v)
```

```math
\hat y_{i}^{\mathrm{target}}
=
\arg\max_{v} p_{i}(v)
```

如果从当前前缀开始的前 $k$ 个候选满足：

```math
\hat y_{i}^{\mathrm{draft}}
=
\hat y_{i}^{\mathrm{target}},
\qquad i=1,\ldots,k
```

就可以接受这段共同前缀；遇到第一个不一致位置时，输出 target 的 token，而不是 draft 的 token。

这只是机制演示。真实 target 会用因果 mask 和 cache 计算每个候选位置的 logits，处理 EOS、stop、logits processor 和 batch 元数据；不能把对每个 token 单独调用 target 的 Python 循环当成高性能实现。

### 6.5.3 采样时的分布校正

如果 draft token $x$ 来自分布 $q(x)$，target 分布为 $p(x)$，简单地“相等就接受、不相等就换成 target argmax”不能保证最终样本仍来自 $p$。经典 speculative sampling 使用接受概率：

```math
a(x)
=
\min\left(1,\frac{p(x)}{q(x)}\right)
```

若拒绝，需要从 residual distribution 采样：

```math
r(x)
=
\frac{\max(p(x)-q(x),0)}
{\sum_{v}\max(p(v)-q(v),0)}
```

这里的 $p$ 和 $q$ 都是在同一个有限词表上的非负归一化分布；只有当 draft 实际采样的 token 满足 $q(x)>0$ 时，接受概率中的比值才有定义。residual 分母记为 $D$。当 $D=0$ 时，说明这一步没有需要补偿的质量差异，应直接从共同的 target 分布采样，不能执行除以零；当 $D>0$ 时才按上式归一化 residual。实现还应检查概率有限、非负且归一化误差在容忍范围内。

这套规则需要在每一步正确维护 draft/target 的条件分布、随机数和已接受前缀。temperature、top-k、top-p、repetition penalty、bad words、grammar constraint 等处理器必须在两个模型的分布计算中保持一致或采用 runtime 明确支持的方案。

### 6.5.4 接受率与期望收益

设一次 draft 提议长度为 $\gamma$，每个位置近似以概率 $a$ 被接受。接受的 draft token 数的一个简化期望是：

```math
\mathbb{E}[K]
\approx
\sum_{i=1}^{\gamma}a^i
```

验证步骤通常还能产生一个 target token，因此一次循环的输出 token 数可以粗略表示为：

```math
\mathbb{E}[N_{\mathrm{cycle}}]
\approx
1+\sum_{i=1}^{\gamma}a^i
```

若 draft 生成 $\gamma$ 个 token 的成本为 $C_{d}(\gamma)$，target 验证一段候选的成本为 $C_{t}(\gamma+1)$，则每循环的近似时间为：

```math
T_{\mathrm{cycle}}
\approx
C_{d}(\gamma)+C_{t}(\gamma+1)+C_{\mathrm{overhead}}
```

相对普通 target 单 token decode 的速度比可以粗略写成：

```math
S
\approx
\frac{
\mathbb{E}[N_{\mathrm{cycle}}]/T_{\mathrm{cycle}}
}{
1/C_{t}(1)
}
```

这个式子不是 runtime 的精确性能模型。 $a$ 会随任务、语言、temperature、位置和输出阶段变化；target 的批量验证成本也不等于 $(\gamma+1)C_{t}(1)$。它的作用是提醒我们必须同时测接受长度、draft 成本、target 验证成本和调度开销。

例如设 $\gamma=4$，为方便手算，假设每个候选位置独立地以概率 $a=0.8$ 被接受，则每轮期望输出 $1+0.8+0.8^2+0.8^3+0.8^4=3.3616$ 个 token。假设 draft 用 16 ms 提出四个候选、target 批量验证用 25 ms，暂不计额外调度开销，那么一轮需 41 ms，约为 $41/3.3616=12.2$ ms/token。若普通 target decode 是 20 ms/token，理想化单请求速度约提升 1.64 倍。把接受率降到 0.4，期望输出变为 $1+0.4+0.16+0.064+0.0256=1.6496$ 个 token，同一轮成本约为 $41/1.6496=24.9$ ms/token，反而慢于普通 decode。这个算例忽略了接受率随位置变化和调度开销，只能说明成本与接受长度要一起测，不能预测真实 runtime 收益。

这里的 $0\leq a\leq1$、 $\gamma$ 为正整数，且 $C_{d}(\gamma)$、 $C_{t}(\gamma+1)$ 和普通 decode 的单位成本都必须为正数；否则“接受率”和速度比没有定义。

### 6.5.5 无依赖接受率 demo

下面用两个确定性 token 序列模拟 greedy 验证，输出接受前缀长度和循环数。它不表示真实模型的接受率。

> 代码状态：静态审阅，未运行（2026-10-29）
```python
def verify_greedy(draft_tokens, target_tokens):
    draft_tokens = list(draft_tokens)
    target_tokens = list(target_tokens)
    if len(target_tokens) < len(draft_tokens) + 1:
        raise ValueError("target must contain a token after every draft position")

    accepted = 0
    while accepted < len(draft_tokens):
        if draft_tokens[accepted] != target_tokens[accepted]:
            return accepted, target_tokens[accepted]
        accepted += 1
    return accepted, target_tokens[accepted]


cases = [
    ([], ["a"]),
    (["a", "b", "c"], ["a", "b", "c", "d"]),
    (["a", "x", "c"], ["a", "b", "c", "d"]),
    (["x", "b"], ["a", "b", "c"]),
]

for draft, target in cases:
    accepted, replacement = verify_greedy(draft, target)
    print(
        "draft=", draft,
        "accepted=", accepted,
        "replacement=", replacement,
    )
```
第一组的共同前缀较长，第二组在第二个位置发生分歧，第三组一开始就分歧。真实系统还要处理“target 验证到第一个分歧后是否已经算出了后继位置”的细节，因此接受 token 数和 target forward 次数要从 runtime trace 读取。

### 6.5.6 Transformers assisted generation 的工程位置

Transformers v5.17.0 提供 assisted generation 接口，常规 assistant-model 路线要求 target 与 draft 使用同一个 tokenizer，并且文档注明该路线不支持 batched inputs。下面用 Pythia-160M 与 Pythia-70M 的固定 Hub commit 展示单条贪心生成；[Pythia 项目说明](https://github.com/EleutherAI/pythia)该系列使用共享的 GPT-NeoX tokenizer。小模型对只演示接口和身份固定，不构成速度收益证据。

> 代码状态：静态审阅，未运行（2026-10-29）
```python
from transformers import AutoModelForCausalLM, AutoTokenizer


target_id = "EleutherAI/pythia-160m-deduped"
target_revision = "582159a2dfe3e712a8d47ae83dec95ae3bde8e7e"
assistant_id = "EleutherAI/pythia-70m-deduped"
assistant_revision = "e93a9faa9c77e5d09219f6c868bfc7a1bd65593c"

tokenizer = AutoTokenizer.from_pretrained(
    target_id,
    revision=target_revision,
)
target = AutoModelForCausalLM.from_pretrained(
    target_id,
    revision=target_revision,
)
assistant = AutoModelForCausalLM.from_pretrained(
    assistant_id,
    revision=assistant_revision,
)
inputs = tokenizer("Explain KV cache briefly.", return_tensors="pt")
outputs = target.generate(
    **inputs,
    assistant_model=assistant,
    max_new_tokens=64,
)
text = tokenizer.decode(outputs[0], skip_special_tokens=True)
```
这段代码需要 Transformers v5.17.0 和 PyTorch；示例为单条 CPU/GPU 生成，模型需放在可相互配合的设备上。默认路线使用共同 tokenizer；若目标与 draft tokenizer 不同，v5.17.0 另提供 Universal Assisted Decoding (UAD)，通过候选重编码和最长公共子序列对齐处理 token 边界，但这会引入额外步骤，也不表示任意模型对都兼容。启用 UAD 时须同时传入 target 与 assistant tokenizer，并按该版本文档确认模型和解码设置。具体见[Transformers v5.17.0 assisted decoding](https://huggingface.co/docs/transformers/v5.17.0/assisted_decoding) 与[Generation API](https://huggingface.co/docs/transformers/v5.17.0/en/main_classes/text_generation)；Pythia 模型快照见[160M](https://huggingface.co/EleutherAI/pythia-160m-deduped/tree/582159a2dfe3e712a8d47ae83dec95ae3bde8e7e)和[70M](https://huggingface.co/EleutherAI/pythia-70m-deduped/tree/e93a9faa9c77e5d09219f6c868bfc7a1bd65593c)。

### 6.5.7 Draft 来源不止一种

draft 可以来自不同路线：

```text
独立的小语言模型：
  部署简单，词表和分布兼容性需要检查。

同一模型的轻量副本：
  tokenizer 更容易一致，但仍可能存在结构或配置差异。

额外训练的 draft head：
  与 target 共享部分表示，减少独立模型成本。

多 token prediction 或相关辅助头：
  直接学习未来多个位置的候选，验证机制和训练目标更紧密。

树状候选或多分支提议：
  提高候选覆盖，但验证和调度复杂度增加。
```

这些方法都可能被归到“推测解码”附近，但 draft 参数来源、训练目标、验证图和适用 runtime 并不相同。资料中写成一个统称时，正文仍应说明具体实现。

### 6.5.8 失败模式：接受率高也不代表总收益高

需要同时检查：

1. draft 本身是否占用了过多 GPU 或 CPU 时间；
2. target 验证候选的 kernel 是否真的比逐 token 更高效；
3. 接受率是否随输出位置、任务类别和采样温度变化；
4. batch 并发下 draft 与 target 是否争抢资源；
5. streaming 是否必须等待一整个验证循环才发 token；
6. EOS、stop sequence、grammar 和 tool call 是否在分歧位置正确处理；
7. 采样 residual 是否实现了分布校正；
8. 输出 token 是否与不使用 speculative 的参考实现一致或在分布上相符；
9. 取消请求后 draft 和 target 的中间状态是否释放；
10. 失败回退到普通 decode 时是否出现 cache 或随机状态污染。

质量测试可以分成两类。贪心模式比较逐步 token；采样模式比较大量样本的分布统计、长度、停止和任务指标。不能因为一条文本看起来相同，就宣布采样分布保持不变。

还有一条明确改变质量边界的可选路线：Transformers 当前文档将它称为 static ensemble verification。标准 speculative sampling 通过校正保留 target 分布；该路线则按 target 与 draft 的混合分布验证候选，以更高接受率换取不再严格服从 target 分布。Transformers 暴露的参数名是 `assistant_ensemble_weight`；该功能需要 assistant 返回候选 logits，因此不适用于 prompt lookup decoding。只有产品明确接受这种分布变化，并用任务质量护栏验证后，才应把它列入候选优化；不能把接受率增加直接说成无损加速。接口和支持条件应按所用 Transformers 版本复核，当前实现细节见[官方 assisted decoding 文档](https://huggingface.co/docs/transformers/main/assisted_decoding)和[Generation API 参数说明](https://huggingface.co/docs/transformers/v5.23.0/en/main_classes/text_generation)。
