| 训练信号 | 典型输入 | 主要改变 | 检查重点 |

## 第 19 讲：Instruction Tuning

### 19 讲·指令数据的对象

预训练模型会续写文本，但不一定会“听话”。Instruction Tuning 的目标，就是让 base model 从“会续写”变成“能理解并遵循用户指令”。

这一讲围绕以下问题展开：

1. Base model 为什么不能直接当助手。
2. Instruction Tuning 到底在训练什么。
3. 指令数据通常长什么样。
4. Instruction Tuning、SFT、RLHF、DPO 的关系。
5. Chat template 为什么重要。
6. 指令微调数据质量如何影响模型行为。
7. 如何把后训练 pipeline 拆成数据、目标、行为和评估四个可观测部分。

### 从 Base Model 到 Instruct Model

Base model 的训练目标是 next-token prediction。

它学习的是：

```text
给定前文，预测下一个 token
```

这让模型能学到大量语言、知识和推理模式，但它不天然知道：

1. 谁是用户。
2. 谁是助手。
3. 应该回答问题还是继续补全文档。
4. 应该遵循哪条指令。
5. 遇到不安全请求时应该拒答。
6. 回答应该简洁还是详细。

Instruction tuning 要解决的核心问题是：把模型行为从“文本续写器”调整成“指令跟随助手”。

### Instruction Tuning 是什么

Instruction Tuning 指使用指令-回答格式的数据，对模型进行后训练，使模型学会遵循自然语言指令。

典型样本：

```text
Instruction: 用三句话解释什么是 Transformer。
Response: Transformer 是一种基于注意力机制的神经网络架构。它可以并行处理序列，并通过 self-attention 建模 token 之间的关系。现代大语言模型大多基于 decoder-only Transformer。
```

更接近聊天模型的格式：

```text
User: 用 Python 写一个二分查找。
Assistant: 下面是一个简单实现：...
```

训练目标仍然通常是 next-token prediction。常见的 assistant-only mask 会让 system/user token 作为条件上下文保留在输入中，只把选定的 assistant 目标 token 计入 loss；具体是否监督 assistant 起始标记和结束标记，取决于模板、训练目标和数据管道。

### 为什么只对 Assistant 部分算 Loss

在 SFT/Instruction Tuning 中，输入里通常包含 user 和 assistant 两部分。

如果对 user 指令也计算 loss，模型会被训练去预测用户会说什么。

但我们真正希望模型学习的是：

```text
给定用户指令，生成合适的助手回答
```

所以常见做法是：

1. user/system 部分作为上下文。
2. assistant 部分作为监督目标。
3. 对 user/system token 的 label 设置为 `-100` 或 ignore index。

这就是 SFT label mask 的核心。

### 最小 demo：assistant-only label mask

下面这个 demo 不依赖真实 tokenizer，只用空格切分来演示 SFT 的 label 构造。核心点是：system/user token 只作为上下文，labels 设为 `-100`；assistant token 才作为训练目标。

```python
IGNORE_INDEX = -100

messages = [
    ("system", "You are helpful"),
    ("user", "Explain gradient descent"),
    ("assistant", "Gradient descent updates parameters using gradients"),
]

tokens = []
labels = []

for role, content in messages:
    role_tokens = [f"<{role}>"] + content.split()
    tokens.extend(role_tokens)

    if role == "assistant":
        labels.extend(role_tokens)
    else:
        labels.extend([IGNORE_INDEX] * len(role_tokens))

for token, label in zip(tokens, labels):
    print(f"{token:>12} -> {label}")
```
> **代码状态：已验证（2026-10-07；Python 3.13.13；标准库）**


输出中，只有 assistant 这一段的 label 不是 `-100`。此示例把 `<assistant>` 角色标记也作为目标；有些模板会把它作为生成前缀而不计 loss。真实训练里，tokens 和 labels 会是 token id，且 causal LM 通常用位置 `t` 的 logits 预测位置 `t+1` 的 label；mask 标记的是目标 token 的 label 位置，不是产生预测的 logit 位置。具体移位由训练代码或模型封装完成。

### Chat Template

Chat template 定义多轮对话如何序列化成模型输入。

例如：

```text
<|system|>
You are a helpful assistant.
<|user|>
Explain gradient descent.
<|assistant|>
Gradient descent is ...
```

Chat template 重要，因为模型看到的不是抽象的“消息对象”，而是一串 token。

如果训练和推理使用不同 template，输入 token 序列就可能与训练分布不一致，模型行为也可能变化。

常见特殊 token：

1. system token。
2. user token。
3. assistant token。
4. end-of-turn token。
5. tool token。

### 模板差分的最小实验

把同一条消息分别序列化成模板 A 和模板 B，哪怕只差一个 assistant 起始标记，也可能改变首个生成 token 的概率。可以记录两条序列的 token 数、特殊 token 位置、assistant loss mask 和 EOS 位置；再用同一 checkpoint 做 greedy 解码，比较第一处分歧和停止位置。

例如，对同一条对话分别使用模型训练时的模板，以及删去 assistant 起始控制 token 的对照模板。用同一 checkpoint 比较首 token 分布、格式错误率和停止位置；若输出差异明显，说明模型依赖这些控制 token 形成的条件上下文。影响大小取决于具体模型和模板，不能把一次差分实验外推成所有模型的固定表现。

初学者可以把 template 理解为对话的语法；专家还应检查 tokenizer 是否把特殊标记作为单独 token、训练和推理是否使用同一版本、tool call 与普通 assistant 消息是否有不同序列化路径。模板版本应和 checkpoint 一起保存。

### 指令数据类型

Instruction tuning 数据可以包括：

1. 问答。
2. 摘要。
3. 改写。
4. 翻译。
5. 代码生成。
6. 数学解题。
7. 多轮对话。
8. 工具调用。
9. 安全拒答。
10. 风格控制。

好的指令数据不只是“有问题有答案”，还要覆盖真实用户意图。

### 数据质量比数量更重要

指令微调数据通常规模远小于预训练数据，但质量影响很大。

低质量指令数据会带来：

1. 回答啰嗦。
2. 模板化严重。
3. 错误事实被强化。
4. 推理步骤不可靠。
5. 安全拒答过度或不足。
6. 多轮上下文跟随能力差。

高质量数据应该具备：

1. 指令清晰。
2. 回答正确。
3. 覆盖任务多样。
4. 难度有梯度。
5. 风格一致但不死板。
6. 安全边界明确。

### Instruction Tuning 和 SFT 的关系

Instruction Tuning 是目标：让模型学会遵循指令。

SFT 是常用训练方法：用人工或合成的高质量指令-回答数据做监督微调。

可以这样理解：

```text
Instruction Tuning: 我要让模型学会听指令
SFT: 我用监督学习的方式训练它
```

很多场景下两者会被混用，但严格说它们关注点不同。

### Instruction Tuning、RLHF、DPO 的关系

常见后训练 pipeline：

```text
Base Model
  -> Instruction Tuning / SFT
  -> Preference Optimization, such as RLHF or DPO
  -> Safety tuning and evaluation
```

Instruction Tuning / SFT 让模型初步会回答。

RLHF / DPO 等偏好优化方法尝试让模型的回答更符合给定偏好数据中的标准；它们不保证每次训练都能让真实用户体验变好。常见优化目标包括：

1. 更有帮助。
2. 更真实。
3. 更安全。
4. 更符合对话风格。
5. 更少输出用户不喜欢的答案。

### 单轮和多轮指令

单轮指令：

```text
User: 解释什么是 overfitting。
Assistant: ...
```

多轮指令：

```text
User: 解释什么是 overfitting。
Assistant: ...
User: 那怎么缓解？
Assistant: ...
```

多轮数据训练模型：

1. 记住上下文。
2. 理解追问。
3. 保持对话一致性。
4. 根据历史信息回答。

如果训练集几乎只有单轮数据，模型就缺少对追问、历史指代和多轮约束的直接监督；预训练或其他数据可能提供部分泛化能力，但不能替代目标场景上的多轮评估。

### System Prompt 的作用

System prompt 用来设定助手行为边界。

例如：

```text
You are a helpful, honest, and harmless assistant.
```

它可以控制：

1. 身份。
2. 语气。
3. 安全规则。
4. 工具使用规范。
5. 输出格式。

但 system prompt 不是万能安全机制。如果模型没有通过训练学会遵循它，推理时仅靠 prompt 不稳定。

### 合成指令数据

很多指令数据来自人工标注，也可以来自强模型生成。

合成数据优点：

1. 成本低。
2. 可扩展。
3. 容易覆盖多任务。
4. 可以定向补齐能力短板。

合成数据风险：

1. 错误被放大。
2. 风格单一。
3. 过度模板化。
4. 引入教师模型偏见。
5. 训练出“看起来会但实际不稳”的模型。

所以合成数据需要过滤、评估和人工抽检。

### 指令微调的评估

评估不能只看训练 loss。

常见评估维度：

1. 指令遵循。
2. 事实准确性。
3. 数学和代码能力。
4. 多轮对话能力。
5. 安全拒答能力。
6. 格式遵循。
7. 用户偏好。
8. 长上下文下的指令跟随。

训练 loss 降低不代表用户体验一定变好，因为模型可能学会模仿答案风格，但真实能力没有提升。

### 19 讲·指令数据的失败模式

#### 坑 1：训练和推理 chat template 不一致

训练用一种格式，推理用另一种格式，会导致模型看到的 token 分布变化，表现明显下降。

#### 坑 2：没有 mask user token

模型被训练去预测用户指令，浪费训练信号，也可能影响助手行为。

#### 坑 3：数据太模板化

模型回答看起来整齐，但灵活性差，遇到真实用户问题容易僵硬。

#### 坑 4：过度依赖合成数据

如果教师模型错误或偏见没有过滤，学生模型会继承甚至放大问题。

#### 坑 5：只做 helpful，不做 safety

模型可能变得更会满足请求，但对危险请求缺少拒答边界。

### Instruction Tuning 的行为差分实验

Instruction Tuning 是目标，SFT 是常见实现方式。要验证它是否真的改变了行为，可以对同一个 base checkpoint 做三组对照：只做通用续写评估、加入单轮指令数据、加入多轮和格式约束数据。固定 tokenizer、学习率和训练 token，比较指令遵循、角色边界、格式通过率、原始语言建模损失和安全切片。

Chat template 是实验变量而不是装饰。模板把 system、user、assistant、轮次和结束标记变成具体 token 序列；训练模板与推理模板只要有一个特殊 token 不一致，模型看到的条件分布就发生变化。最小反事实实验是：用同一批权重分别以训练模板和一个缺失 assistant 起始标记的模板推理，比较首 token 分布、停止位置和多轮一致性。

对 assistant-only loss 的解释也应落到梯度上：system/user token 作为条件输入保留在上下文中，但不作为需要模仿的目标。若把它们纳入 loss，训练会额外奖励模型复述输入，可能稀释回答 token 的监督信号。这个原则不是绝对禁令；在某些联合建模任务中可以有不同 mask，但必须说明任务目标已经改变。

### 19 讲·指令数据的反例与边界

1. 误区：预训练模型自然会聊天。
   纠正：base model 会续写，不等于会遵循指令。

2. 误区：Instruction Tuning 等于 RLHF。
   纠正：Instruction Tuning/SFT 通常先让模型会回答，RLHF/DPO 再优化偏好。

3. 误区：指令数据越多越好。
   纠正：低质量指令数据会强化错误、模板化和不安全行为。

4. 误区：chat template 只是工程细节。
   纠正：template 改变 token 分布，直接影响模型行为。

1. 用自己的话解释 base model 和 instruct model 的区别。
2. 写一个单轮 instruction tuning 样本。
3. 写一个多轮 chat template 示例。
4. 解释为什么 user token 不应该参与 SFT loss。

### 19 讲·从指令数据到行为变化的关键结论

这一讲的关键关系：

1. Base model 学的是续写，不天然等于助手。
2. Instruction Tuning 让模型学会遵循用户指令。
3. 训练目标仍然常是 next-token prediction，但通常只对 assistant 部分算 loss。
4. Chat template 是模型理解角色和轮次的关键输入格式。
5. 指令数据质量直接决定模型行为风格、稳定性和安全边界。
6. Instruction Tuning/SFT 通常是 RLHF/DPO 之前的后训练阶段。

## 第 20 讲：SFT

### 20 讲·SFT 的监督边界

SFT 是大模型后训练中最基础、最常用的一步。第 19 讲讲的是“为什么要让模型学会听指令”，本讲进一步讲“具体怎么用监督学习训练它”。

这一讲围绕以下问题展开：

1. SFT 的训练目标是什么。
2. SFT 数据如何组织成模型输入。
3. 为什么要做 label mask。
4. 全参微调、LoRA 和 QLoRA 的区别。
5. SFT 中常见的数据、训练和评估问题。
6. SFT 和 pretraining、RLHF、DPO 的区别。
7. 如何用数据切片和消融实验判断 SFT 到底改变了什么行为。

### SFT 是什么

SFT 是 Supervised Fine-Tuning，中文通常叫监督微调。

它的基本思想是：给模型高质量输入输出样本，让模型通过监督学习模仿目标回答。

在聊天模型里，SFT 样本通常长这样：

```text
System: You are a helpful assistant.
User: 什么是梯度下降？
Assistant: 梯度下降是一种通过沿负梯度方向更新参数来最小化损失函数的优化方法。
```

模型输入是完整对话 token 序列，训练目标是 assistant response 的 next-token prediction。

### SFT 和预训练的区别

预训练和 SFT 都可以用 next-token prediction，但数据和目标不同。

预训练：

1. 数据是大规模通用语料。
2. 目标是学习语言、知识和通用模式。
3. 通常对所有 token 计算 loss。
4. 产物是 base model。

SFT：

1. 数据是高质量指令、对话、任务样本。
2. 目标是让模型学会按要求回答。
3. 通常只对 assistant token 计算 loss。
4. 产物是 instruct/chat model。

一句话：预训练让模型“有知识”，SFT 让模型“会按格式和意图输出”。

### SFT 训练目标

给定上下文 `x` 和目标回答 `y`，SFT 最大化：

~~~math
P_\theta(y \mid x)
~~~

也就是让模型在看到用户指令和历史对话后，更可能生成目标回答。

如果目标回答 token 是：

~~~math
y_1,y_2,\ldots,y_T
~~~

训练目标是：

~~~math
\max_\theta \sum_{t=1}^{T}\log P_\theta(y_t \mid x,y_{1:t-1})
~~~

等价于最小化 assistant response 部分的 cross entropy loss。

### 数据格式

常见 SFT 数据格式包括三类。

第一类：instruction-output。

```json
{
  "instruction": "解释什么是 overfitting",
  "input": "",
  "output": "Overfitting 指模型在训练集上表现很好，但在新数据上表现变差。"
}
```

第二类：messages。

```json
{
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "解释什么是 overfitting"},
    {"role": "assistant", "content": "Overfitting 指模型在训练集上表现很好，但在新数据上表现变差。"}
  ]

```

第三类：多轮对话。

```json

    {"role": "assistant", "content": "过拟合是模型过度贴合训练数据。"},

  ]

```

### Label Mask

SFT 的关键实现细节是 labels。

假设 token 序列是：

```text
<system> ... <user> ... <assistant> A B C <eos>
```

我们通常希望：

```text
system/user token: 不算 loss
assistant token: 算 loss
```

在 PyTorch 里常用 `-100` 表示 ignore index：

```text
input_ids: [system tokens, user tokens, assistant tokens]
labels:    [-100, ..., -100, assistant labels]
```

如果 label mask 错了，SFT 训练可能看似 loss 正常下降，但模型行为不对。

### 一个简化的 Label 构造例子

假设序列是：

```text
[USER, 10, 11, ASSISTANT, 20, 21, EOS]
```

对应 labels 可以是：

```text
[-100, -100, -100, -100, 20, 21, EOS]
```

实际 causal LM 内部通常还会做 shift：当前位置 logits 预测下一个 token。

所以你要同时理解两件事：

1. label mask 控制哪些位置参与 loss。
2. causal LM loss 会把 logits 和 labels 错位对齐。

### 最小 demo：用 ignore_index 只计算 assistant loss

下面这个 demo 用 PyTorch 展示 causal LM 的 next-token 对齐和 `ignore_index`。`labels` 与 `input_ids` 按 token 位置对齐；模型位置 `t` 的 logits 预测 `labels[t+1]`，因此计算交叉熵前要把 logits 和 labels 分别向相反方向切一位。`-100` 只屏蔽目标 label，不会屏蔽该 token 作为上下文输入。

```python
import torch
import torch.nn.functional as F


torch.manual_seed(0)

batch_size = 1
seq_len = 6
vocab_size = 10

logits = torch.randn(batch_size, seq_len, vocab_size)
labels = torch.tensor([[-100, -100, -100, 4, 5, 6]])

shift_logits = logits[:, :-1, :].contiguous()
shift_labels = labels[:, 1:].contiguous()
active_positions = (shift_labels != -100).sum().item()
if active_positions == 0:
    raise ValueError("the batch must contain at least one next-token target")
loss = F.cross_entropy(
    shift_logits.view(-1, vocab_size),
    shift_labels.view(-1),
    ignore_index=-100,
)

print("active next-token targets:", active_positions)
print("loss:", round(loss.item(), 4))
```
> **代码状态：已验证（2026-10-07；Python 3.13.13；PyTorch 2.12.0+cpu）**


输出中 `active next-token targets` 应该是 3：logits 的位置 2、3、4 分别预测 label 位置 3、4、5 的 token `4、5、6`。前两个有效 assistant token 仍能利用 system/user 上下文，但这些上下文 token 自身不作为预测目标。该 demo 使用随机 logits，只验证 mask 和 shift 的索引关系，不衡量模型质量。

### Label Mask 的手算例子

把一条对话写成角色 token 后，假设序列为：system、user、assistant、assistant 内容、EOS。若只有 assistant 内容和 EOS 参与 loss，labels 可以写成：

```text
input:  [SYS, U1, U2, ASST, A1, A2, EOS]
label:  [-100,-100,-100,-100, A1, A2, EOS]
```

这里的 `-100` 不是词表中的 token，而是损失函数的 ignore index。它不会阻止 user token 进入 attention；模型仍然需要读取问题，才能预测 A1。常见 bug 是把 assistant 起始标记也 mask 掉或把 padding 当成真实 EOS，结果会分别表现为回答开头不稳定或过早停止。

可以用三条检查验证实现：有效 label 数是否等于 assistant token 数；不同长度样本的平均 loss 是否按有效 token 归一化；把 user 内容改写而保持 assistant 目标不变时，模型是否仍能利用上下文。这个例子把“mask”从代码细节还原成了训练目标的选择。

### Packing 和 Padding

SFT 样本长度差异很大。

训练时常见处理：

1. padding：短样本补齐到 batch 最大长度。
2. truncation：太长样本截断。
3. packing：把多个短样本拼成一个长序列。

Padding 简单但可能浪费计算。

Packing 提高效率，但要注意：

1. 样本边界。
2. EOS 或 end-of-turn token。
3. loss mask 不能串样本错位。
4. 多轮对话不能被错误截断。

EOS 或 end-of-turn token 只标记序列中的边界，不自动阻断后一个样本对前一个样本的 attention。若样本必须相互独立，packing 时还要使用合适的 attention mask 或隔离策略；否则要把跨样本上下文作为训练目标的一部分明确接受。

### 全参微调、LoRA 和 QLoRA

SFT 可以有不同参数更新方式。

全参微调：

1. 更新全部模型参数。
2. 效果上限高。
3. 显存和计算成本高。
4. 更容易破坏原模型能力，需要小心学习率。

LoRA：

1. 冻结原模型参数。
2. 在部分线性层加入低秩适配器。
3. 只训练少量新增参数。
4. 成本低，适合资源有限场景。

QLoRA：

1. 基座模型量化加载。
2. 在量化模型上训练 LoRA adapter。
3. 进一步降低显存。
4. 训练和部署细节更复杂。

工程上需要把这个取舍落到可测量的量：全参微调更新容量大但显存和优化器状态昂贵；LoRA/QLoRA 更省资源，却受低秩容量、量化误差、目标层选择和合并部署方式影响。

### 学习率和训练轮数

SFT 数据量通常远小于预训练数据，所以更容易过拟合。

常见注意点：

1. 学习率不能太大。
2. epoch 不能盲目太多。
3. 需要 validation set。
4. 需要保留 base capability eval。
5. 需要观察是否出现灾难性遗忘。

SFT 的目标不是把训练集背熟，而是让模型学到稳定的指令跟随模式。

### Catastrophic Forgetting

灾难性遗忘是指模型在 SFT 后丢失原有能力。

例如：

1. 代码能力下降。
2. 多语言能力下降。
3. 长文本续写能力下降。
4. 原本掌握的知识变差。

常见原因：

1. 数据分布太窄。
2. 学习率太大。
3. 训练轮数太多。
4. 指令数据质量差。
5. 没有混入保能力数据。

### SFT 数据质量检查

训练前要检查：

1. 是否有空回答。
2. 是否有角色错乱。
3. assistant 回答是否真实正确。
4. 是否有安全违规样本。
5. 是否有重复模板。
6. 是否有过长样本。
7. 是否包含泄漏评估集。
8. chat template 是否能正确解析。

很多 SFT 失败不是算法问题，而是数据和格式问题。

### SFT 评估

SFT 评估要覆盖多个层面：

1. validation loss。
2. 指令遵循能力。
3. 格式遵循能力。
4. 数学、代码、知识问答。
5. 多轮对话。
6. 安全拒答。
7. 原始 base capability 是否下降。
8. 人类偏好或 pairwise win rate。

不要只看 SFT loss。模型可能 loss 很低，但回答机械、啰嗦、不安全，或者在真实用户问题上泛化差。

### SFT 和 RLHF/DPO 的关系

SFT 通常是偏好优化之前的一步。

原因是：

1. SFT 让模型具备基本指令跟随能力。
2. RLHF/DPO 需要模型已经能产生可比较的回答。
3. 偏好优化主要调整“哪个回答更好”，而不是从零教模型回答。

可以这样理解：

```text
SFT: 学会怎么回答
RLHF/DPO: 学会哪种回答更受偏好
```

### 20 讲·SFT 训练现场的故障模式

#### 坑 1：labels 没有正确 mask

模型学去预测 user/system 内容，训练目标偏了。

#### 坑 2：chat template 和 tokenizer 不匹配

特殊 token 没加、EOS 不正确、assistant 起始标记不一致，都会影响训练。

#### 坑 3：训练集答案质量差

SFT 是模仿学习。答案错，模型就学错；答案啰嗦，模型就学啰嗦。

#### 坑 4：只看 validation loss

SFT loss 下降不代表真实用户体验提升。

#### 坑 5：过拟合小数据集

模型在训练样本上表现好，但泛化到真实指令时变差。

#### 坑 6：能力退化没被发现

只测指令任务，不测代码、数学、多语言和安全，容易漏掉回归。

### SFT 改变行为的可验证路径

SFT 的关键不是“把 labels 设成 `-100`”这一句实现口诀，而是明确模型究竟被要求预测什么。给定序列 u，设 assistant token 的掩码为 m_t∈{0,1}，则带 mask 的目标可以写成：

~~~math
L_{\mathrm{SFT}}=-\frac{1}{\sum_t m_t}\sum_t m_t\log p_\theta(u_t\mid u_{1:t-1})
~~~

分母只统计有效 assistant token，避免 padding 和被 mask 的上下文 token 改变 loss 的归一化尺度；但在一个 batch 内按有效 token 总数求平均时，较长回答仍贡献更多 token 项，因此并不等于每条回答等权。若需要样本等权，应先对每条回答按其有效 token 数求平均，再对样本取平均；这会改变优化目标，需与评估目标一致。若把 user token 也纳入损失，模型会同时学习“复述用户话语”；这不一定立刻造成灾难，但会改变梯度分布，尤其在多轮数据中可能稀释真正的回答信号。

排查 SFT 后能力下降时，应按因果顺序做消融，而不是先换更大的学习率。先固定基座和训练步数，只替换 chat template；再固定 template，只改变 label mask；最后比较窄数据集与混入通用保能力数据的结果。每次实验都记录 assistant-only loss、全序列 loss、任务切片和输出长度。这样才能区分“格式错了”“监督信号错了”和“数据覆盖不足”。

LoRA 也应放进同一套实验。设基座权重为 W_0，低秩更新为 BA，则：

~~~math
W=W_0+\frac{\alpha}{r}BA,\qquad A\in\mathbb{R}^{r\times d_{\mathrm{in}}},\quad B\in\mathbb{R}^{d_{\mathrm{out}}\times r}
~~~

增加 rank `r` 并不保证能力线性增加；目标层、数据覆盖和学习率同样重要。QLoRA 进一步把基座权重量化，但训练的 adapter 和计算过程仍需精心处理。最终决策应比较可训练参数量、峰值显存、合并后延迟、业务指标和原始能力回归，而不是只比较训练是否能启动。

### 20 讲·Label mask 的反例与边界

1. 误区：SFT 数据越多越好。
   纠正：低质量数据会让模型学到错误和坏风格。

2. 误区：SFT loss 越低模型越好。
   纠正：还要看真实任务、偏好、安全和能力回归。

3. 误区：LoRA 一定不如全参微调。
   纠正：LoRA 成本低，很多任务足够有效，但上限和适配范围取决于任务。

4. 误区：SFT 能解决所有对齐问题。
   纠正：SFT 主要教模型模仿好回答，偏好、安全和拒答边界通常还需要额外训练和评估。

### 20 讲·SFT mask 的复核实验

1. 写一个 `messages` 格式的 SFT 样本。
2. 给定一段 user/assistant token 序列，手写 labels 和 `-100` mask。
3. 比较全参 SFT、LoRA、QLoRA 的优缺点。
4. 列出 SFT 数据清洗的 5 个检查项。
5. 设计一个 SFT 评估表，覆盖指令遵循、代码、数学、安全和多轮对话。

### 20 讲·从监督 mask 到 SFT 行为的关键结论

这一讲的关键关系：

1. SFT 是用监督学习让模型模仿高质量回答。
2. SFT 的核心目标是最大化 `P(response | instruction, context)`。
3. 聊天 SFT 通常只对 assistant response 计算 loss。
4. Label mask、chat template、EOS 和 padding 都是关键实现细节。
5. LoRA/QLoRA 可以显著降低微调成本，但有表达能力和工程 trade-off。
6. SFT 评估不能只看 loss，还要看真实任务、安全、偏好和能力回归。

### 20 讲·SFT 资料边界

LoRA 的低秩适配方法见 [Hu et al., 2021](https://arxiv.org/abs/2106.09685)，QLoRA 的量化基座微调方法见 [Dettmers et al., 2023](https://arxiv.org/abs/2305.14314)；`-100` 作为忽略目标的语义见 [PyTorch CrossEntropyLoss 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.CrossEntropyLoss.html)。实际 mask、padding 和 adapter 合并行为还要以所用 PEFT/Transformers 版本与运行结果为准。参数量公式只描述可训练矩阵，不等于端到端显存或质量收益。

## 第 21 讲：RLHF

### 21 讲·RLHF 的对象与假设

SFT 让模型学会模仿高质量回答，但“模仿一个答案”不等于“总能生成用户更喜欢的答案”。RLHF 的目标，是利用人类偏好信号进一步优化模型行为。

这一讲围绕以下问题展开：

1. RLHF 要解决什么问题。
2. 偏好数据是什么。
3. Reward Model 如何训练。
4. PPO 在 RLHF 中扮演什么角色。
5. 为什么需要 KL penalty。
6. RLHF 和 SFT、DPO 的区别。
7. Reward hacking、over-optimization 等风险。

### RLHF 是什么

RLHF 是 Reinforcement Learning from Human Feedback，中文是基于人类反馈的强化学习。

它的基本思想：

```text
用人类偏好训练一个 reward model，再用强化学习优化语言模型，让模型生成更符合人类偏好的回答。
```

一个典型流程：

```text
1. 训练 base model
2. 做 SFT 得到初始 assistant model
3. 收集偏好数据
4. 训练 reward model
5. 用 PPO 等 RL 方法优化 policy model
6. 做安全评估和人工评估
```

这里的 policy model 就是正在被优化的语言模型。

这条链路中有一个容易被忽略的事实：Reward Model 不是人类偏好的“真值函数”，而是从有限标注样本中学出的代理指标。第 21 讲先说明它在 RLHF 中承担什么角色；第 23 讲再单独分析它的训练、分布偏移和被利用的方式。把这两个层次分开，才能理解为什么“reward 上升”并不自动等于“模型变好”。

### 为什么 SFT 之后还需要 RLHF

SFT 的训练数据通常只有一个目标回答。

但真实对话中，同一个问题可能有多个回答：

```text
回答 A：准确但太啰嗦
回答 B：简洁但漏掉关键条件
回答 C：平衡、准确、清晰
```

SFT 只告诉模型“模仿这个答案”，而 RLHF 可以利用人类偏好告诉模型“这些答案里哪个更好”。

RLHF 能优化的维度包括：

1. helpfulness。
2. honesty。
3. harmlessness。
4. 简洁性。
5. 格式遵循。
6. 拒答边界。
7. 用户体验。

### 偏好数据

偏好数据通常是成对比较。

给定同一个 prompt，模型生成多个回答，人类标注者选择更好的一个。

例如：

```json
{
  "prompt": "解释什么是 dropout",
  "chosen": "Dropout 是训练时随机丢弃部分神经元来减少过拟合的方法。",
  "rejected": "Dropout 是一种让模型变快的优化器。"
}
```

其中：

1. `chosen` 是人类更偏好的回答。
2. `rejected` 是人类不太偏好的回答。

偏好数据不一定只比较正确性，也可能比较语气、完整性、安全性和有用性。

### Reward Model

Reward Model 的目标是给回答打分。

输入：

```text
prompt + response
```

输出：

```text
一个标量 reward
```

分数越高，表示这个回答越符合人类偏好。

Reward Model 通常用偏好 pair 训练。目标是让：

~~~math
r(x,y_w)>r(x,y_l)
~~~

其中 `x` 是 prompt，`y_w` 是 preferred / chosen response，`y_l` 是 less preferred / rejected response。

直觉上，Reward Model 是把人类偏好压缩成一个可优化的打分函数。

### Reward Model 的损失

常见 pairwise loss：

~~~math
L=-\log \sigma(r_w-r_l)
~~~

其中：

1. `r_w` 是 chosen response 的 reward。
2. `r_l` 是 rejected response 的 reward。

如果 `r_chosen` 比 `r_rejected` 高很多，loss 小。

如果 `r_chosen` 不高于 `r_rejected`，loss 大。

你不需要一开始死背公式，但要理解：Reward Model 学的是“排序偏好”，不是绝对正确答案。

### 最小 demo：pairwise reward loss

下面这个 demo 展示 pairwise reward loss 的直觉：当 chosen reward 高于 rejected reward 时，loss 更小；反过来 loss 更大。

```python
import torch
import torch.nn.functional as F


def pairwise_reward_loss(chosen_reward, rejected_reward):
    if chosen_reward.shape != rejected_reward.shape:
        raise ValueError("chosen and rejected rewards must have the same shape")
    if chosen_reward.numel() == 0:
        raise ValueError("at least one preference pair is required")
    margin = chosen_reward - rejected_reward
    return -F.logsigmoid(margin).mean()


good_case = pairwise_reward_loss(torch.tensor([3.0]), torch.tensor([1.0]))
bad_case = pairwise_reward_loss(torch.tensor([1.0]), torch.tensor([3.0]))

print("chosen > rejected loss:", round(good_case.item(), 4))
print("chosen < rejected loss:", round(bad_case.item(), 4))
```
> **代码状态：已验证（2026-10-07；Python 3.13.13；PyTorch 2.12.0+cpu）**


这个损失训练 Reward Model 学会排序，而不是要求 reward 分数本身有绝对物理含义。

### PPO 在 RLHF 中做什么

有了 Reward Model 后，我们希望优化语言模型，让它生成高 reward 的回答。

这就变成一个强化学习问题：

1. 状态：prompt 和当前生成上下文。
2. 动作：下一个 token。
3. 策略：语言模型的 token 分布。
4. 奖励：Reward Model 对完整回答的评分。

PPO 是一种常用 policy optimization 方法，用来更新语言模型参数。

RLHF 中常见组件：

1. policy model：当前被训练的模型。
2. reference model：通常是冻结的 SFT 模型。
3. reward model：给回答打分。
4. value model：估计未来 reward，辅助 PPO。

PPO 的关键不是“让每个 token 的概率都变大”，而是限制一次更新不要离旧策略太远。对某个状态 `s_t` 和动作 `a_t`，常见的概率比率为：

~~~math
r_t(\theta)=\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t)}
~~~

用优势估计 `A_t` 表示这一步动作相对于基线到底好不好，PPO 的 clipped policy objective 可以写成：

~~~math
L^{\mathrm{CLIP}}(\theta)=\mathbb{E}_t\left[\min\left(r_t(\theta)A_t,\;\mathrm{clip}(r_t(\theta),1-\epsilon,1+\epsilon)A_t\right)\right]
~~~

`\epsilon` 是允许策略比率变化的范围，`A_t>0` 时鼓励提高动作概率，`A_t<0` 时鼓励降低动作概率；`clip` 防止某个批次把更新推得过远。真实 PPO 训练还会同时优化 value loss、加入 entropy bonus，并处理序列级奖励如何分摊到 token 的问题。因此，不能把 RLHF 简化成“拿 reward 做一次交叉熵训练”，必须同时说明采样、优势估计、策略约束和价值函数的关系。

### 为什么需要 Reference Model

如果只最大化 reward，模型可能为了骗过 Reward Model 而偏离原本语言能力。

Reference model 用来约束 policy 不要离 SFT 模型太远。

常见约束是 KL penalty：

~~~math
r_{\mathrm{total}}=r_{\mathrm{rm}}-\beta D_{\mathrm{KL}}(\pi_\theta\Vert\pi_{\mathrm{ref}})
~~~

其中 `r_rm` 是 Reward Model 给出的分数，`pi_theta` 是当前 policy，`pi_ref` 是 reference model。

在语言模型实现里，通常会对采样到的回答估计逐 token 的对数概率差，而不是显式构造整个词表上的 KL：

~~~math
R(x,y)=r_{\mathrm{rm}}(x,y)-\beta\sum_{t=1}^{|y|}
\left[\log\pi_\theta(y_t\mid x,y_{1:t-1})-\log\pi_{\mathrm{ref}}(y_t\mid x,y_{1:t-1})\right]
~~~

这个单条样本的估计值可以出现正负，取期望后才对应 KL 约束的含义。它还会受到回答长度、EOS 位置和 tokenization 的影响，所以工程上要监控平均 KL、长度分布以及 reward 与人工偏好的关系，不能只盯着最终的标量 reward。

直觉：

```text
既要提高 reward，也不能偏离原模型太多
```

这样可以降低模型输出变怪、重复、钻 reward 空子的风险。

### KL Penalty

KL penalty 惩罚当前 policy 和 reference model 的分布差异。

如果 policy 对某些 token 的概率变化太大，KL 会变大。

作用：

1. 保持语言质量。
2. 避免过度优化 reward model。
3. 降低模式崩坏。
4. 保留 SFT 阶段学到的能力。

KL 太小：模型可能乱跑，reward hacking 风险上升。

KL 太大：模型更新受限，RLHF 效果弱。

### RLHF 的训练流程

更具体的流程：

```text
1. 从 prompt 数据集中采样 prompt
2. policy model 生成回答
3. reward model 给回答打分
4. 计算 policy 和 reference 的 KL penalty
5. 得到最终 reward
6. 用 PPO 更新 policy model
7. 周期性评估安全、偏好、能力回归
```

这个过程比 SFT 更复杂，因为模型输出会随着训练变化，训练数据是在线生成的。

### RLHF 和普通强化学习的区别

传统强化学习常见于游戏、机器人等环境。

RLHF 的特殊性：

1. action space 是巨大词表。
2. episode 是一段生成文本。
3. reward 来自 learned reward model，而不是真实环境奖励。
4. reward 很稀疏，通常在完整回答后给分。
5. 语言模型已经有很强的预训练先验。

所以 RLHF 不是从零训练智能体，而是在已有语言模型上做偏好微调。

### Reward Hacking

Reward hacking 指模型找到提高 reward 的捷径，但这种行为不符合真实人类意图。

例子：

1. 回答变得过度奉承。
2. 总是输出看似安全但无帮助的话。
3. 用模板化语言骗过 reward model。
4. 在 reward model 盲区输出错误内容。
5. 为了显得详细而胡编。

原因：Reward Model 只是人类偏好的近似，不是真实偏好的完美表达。

### 21 讲·Over-Optimization

Reward Model 本身有误差。

如果 PPO 过度优化 reward model，可能出现：

1. reward model 分数继续上升。
2. 人类实际偏好下降。
3. 模型输出越来越怪。

这叫 over-optimization。

所以 RLHF 需要人工评估、holdout 偏好集和安全评估，而不能只看 reward 分数。

### RLHF 和 DPO 的关系

RLHF 通常需要：

1. 显式 reward model。
2. PPO 或其他 RL 优化。
3. 在线采样。
4. KL 控制。

DPO 则直接使用偏好数据优化 policy，不显式训练 reward model，也不跑 PPO。

简单对比：

```text
RLHF: preference data -> reward model -> PPO optimize policy
DPO: preference data -> directly optimize policy
```

DPO 的标准离线流程省去了显式 reward model 和在线 PPO rollout，固定偏好数据集上的工程链路可以更简单；这不代表 DPO 在所有任务上都更稳定或质量更高。效果仍取决于偏好数据、reference 与 policy 的匹配、训练配置和独立评估。若需要根据新策略输出持续采样并更新偏好，仍需考虑在线优化或其他反馈闭环。

### RLHF 的评估

RLHF 评估包括：

1. pairwise win rate。
2. reward model score。
3. 人工偏好评估。
4. helpfulness。
5. honesty。
6. harmlessness。
7. 拒答质量。
8. 原有能力回归。
9. reward hacking 检查。

不能只看 reward model score，因为模型可能过拟合 reward model。

### 一个 toy rollout：奖励为什么要延迟观察

把一次回答看成三个 token 动作：先给出结论，再给出理由，最后给出限定条件。Reward Model 只在完整回答结束后打分时，PPO 需要把序列级奖励分配给每个 token；如果把同一个奖励平均摊给所有 token，模型可能学会固定的开头模板，却无法知道哪一个限定条件真正提升了质量。

一个更可靠的对照是构造两个只差最后一句的回答：前两个 token 完全相同，一个补充适用条件，另一个做无依据的绝对断言。比较完整 reward、逐 token log probability、KL 和人工偏好，可以观察 reward 信号是否足以区分最后一步。如果不能，问题不一定在 PPO，而可能在 Reward Model 的输入或标注覆盖。

这个 toy rollout 还揭示了序列长度效应。较长回答有更多可以被优化的 token，也有更多机会获得格式奖励或触发错误；因此 RLHF 报告应同时给出 reward、长度、KL 和客观任务指标。对初学者来说，这是“最后才打分但前面要更新”的直觉；对专家来说，还要继续追踪 credit assignment 和 tokenization 对优势估计的影响。

### 21 讲·RLHF 的失败模式

#### 坑 1：偏好标注标准不一致

不同标注者对“好回答”的理解不同，会让 reward model 学到噪声。

#### 坑 2：Reward Model 泛化差

训练集上排序准确，但遇到新类型 prompt 打分不可靠。

#### 坑 3：KL 系数设置不合适

KL 太弱模型乱跑，KL 太强模型学不动。

#### 坑 4：只优化 reward score

Reward 上升但人类偏好下降，是 RLHF 的典型风险。

#### 坑 5：安全和 helpfulness 冲突

模型可能为了安全过度拒答，也可能为了 helpfulness 满足危险请求。

### RLHF 的闭环与可观测量

RLHF 不是一条只看最终 reward 的流水线。每个阶段都应保留可以诊断的数据：偏好标注的一致性，Reward Model 的分领域排序与校准，policy 采样的长度和分布变化，PPO 的优势估计、KL 距离、熵、value loss，以及人工和客观任务评估。

设每个回答的总奖励为 `R(y)`，reference 约束为 `D_KL`，一个简化的序列级目标可以写成：

~~~math
J(\theta)=\mathbb{E}_{x,y\sim\pi_\theta}\left[R(y)-\beta D_{\mathrm{KL}}\left(\pi_\theta(\cdot\mid x)\,\Vert\,\pi_{\mathrm{ref}}(\cdot\mid x)\right)\right]
~~~

这个公式说明两个可能的失败方向：`beta` 太小，policy 容易追逐代理奖励；`beta` 太大，policy 几乎不改变，偏好信号无法生效。PPO 的 clipped objective 进一步限制单轮策略比率，但它不能修复错误的 reward，也不能替代分布外评估。

一个有区分力的 RLHF 实验是沿训练步数画四条曲线：Reward Model 分数、人工偏好、KL 距离和原始能力。若第一条持续上升而后三者恶化，说明出现代理目标过度优化；若人工偏好上升但安全误拒答也上升，则需要重新切分安全偏好，而不是继续增大训练步数。

### 21 讲·奖励优化的反例与边界

1. 误区：RLHF 直接用人类实时给模型奖励。
   纠正：通常先用人类偏好数据训练 reward model，再用 reward model 提供训练信号。

2. 误区：Reward Model 分数越高模型越好。
   纠正：模型可能 exploit reward model，必须看人工评估和真实任务。

3. 误区：RLHF 可以替代 SFT。
   纠正：RLHF 通常在 SFT 后进行，SFT 提供可用初始策略。

4. 误区：KL penalty 越小越好。
   纠正：KL 太小约束弱，模型容易偏离并 reward hacking。

### 21 讲·从偏好到策略更新的关键结论

这一讲的关键关系：

1. RLHF 用人类偏好优化模型行为。
2. Reward Model 把偏好数据转成可优化的标量奖励。
3. PPO 用 reward 信号更新 policy model。
4. Reference model 和 KL penalty 用来限制模型不要偏离 SFT 模型太远。
5. RLHF 能提升 helpfulness、honesty、harmlessness，但也有 reward hacking 和 over-optimization 风险。
6. RLHF 评估不能只看 reward score，必须结合人工偏好、安全和能力回归。

### 21 讲·RLHF 资料边界

RLHF 的代表性系统流程可参阅 InstructGPT（[Ouyang et al., 2022](https://arxiv.org/abs/2203.02155)）；PPO 的通用算法见 [Schulman et al., 2017](https://arxiv.org/abs/1707.06347)，摘要任务中的人类反馈实验见 [Stiennon et al., 2020](https://arxiv.org/abs/2009.01325)。这些论文证明了方法在特定设定下的有效性，并不保证任意 Reward Model、偏好数据或 PPO 超参数都能得到同样结果。

## 第 22 讲：DPO

### 22 讲·DPO 的监督边界

DPO 是当前大模型后训练中非常重要的方法。它的吸引力在于：不需要显式训练 reward model，也不需要像 RLHF 那样跑复杂的 PPO，就可以直接用偏好数据优化模型。

这一讲围绕以下问题展开：

1. DPO 想解决 RLHF 的什么问题。
2. DPO 使用什么数据。
3. DPO loss 的直觉是什么。
4. Reference model 在 DPO 中的作用。
5. DPO 和 RLHF、SFT 的区别。
6. DPO 的优点、局限和常见坑。
7. 如何从偏好数据、reference model 和长度效应判断 DPO 是否真的改善了行为。

### DPO 是什么

DPO 是 Direct Preference Optimization，中文可译为直接偏好优化。

它直接使用偏好数据训练模型，让模型提高 chosen response 的概率，降低 rejected response 的相对概率。

偏好数据格式通常是：

```json
{
  "prompt": "解释什么是梯度裁剪",
  "chosen": "梯度裁剪是限制梯度范数，避免梯度爆炸导致训练不稳定的方法。",
  "rejected": "梯度裁剪是删除模型中不重要参数的方法。"
}
```

DPO 的目标：

```text
让模型相对更偏向 chosen，而不是 rejected
```

### DPO 为什么出现

RLHF 很强，但工程复杂。

RLHF 通常需要：

1. 训练 reward model。
2. 在线采样回答。
3. 用 PPO 优化 policy。
4. 维护 reference model。
5. 调 KL penalty。
6. 处理 reward hacking 和训练不稳定。

DPO 希望简化这条链路。

它把问题改写成一个更接近监督学习的目标：

```text
给定 chosen/rejected，直接更新 policy，让 chosen 比 rejected 更可能
```

### DPO 和 RLHF 的核心区别

RLHF：

```text
preference data -> reward model -> PPO -> policy model
```

DPO：

```text
preference data -> DPO loss -> policy model
```

也就是说，DPO 不显式训练 reward model，也不需要在线 RL rollout。

但 DPO 仍然和 RLHF 有理论联系：它可以看作在某些假设下，把带 KL 约束的 reward maximization 转换成直接优化偏好 likelihood 的形式。

阅读实现时不必一开始就推完整论文公式，但必须知道这个直觉依赖哪些假设；如果 reference、偏好分布或 log-probability 计算方式改变，DPO 的行为也会改变。

### DPO 使用的数据

DPO 数据和 reward model 数据类似，都是 preference pair。

每条样本包括：

1. prompt。
2. chosen response。
3. rejected response。

DPO 不要求有单一目标回答，而是要求知道两个回答中哪个更符合偏好。

偏好可以来自：

1. 人类标注。
2. 强模型评判。
3. 安全规则筛选。
4. 用户反馈。
5. 专家偏好。

数据质量直接决定 DPO 的效果。

### DPO 的直觉

对于同一个 prompt，模型会给 chosen 和 rejected 分别分配概率。这里用 $y_w$ 表示 chosen response，用 $y_l$ 表示 rejected response。

我们希望：

~~~math
\pi_\theta(y_w\mid x)>\pi_\theta(y_l\mid x)
~~~

但不能无限提高 chosen 概率、无限压低 rejected 概率，否则模型可能过度偏离原模型。

所以 DPO 会比较 policy model 和 reference model 的相对偏好变化。

直觉：

```text
policy 应该比 reference 更偏向 chosen，但不要无约束乱跑
```

### Reference Model 的作用

DPO 中通常需要一个 reference model，常见是冻结的 SFT 模型。

Reference model 的作用：

1. 提供原模型偏好基线。
2. 隐式约束 policy 不要偏离太远。
3. 类似 RLHF 中 KL regularization 的作用。
4. 避免模型为了偏好数据过度扭曲语言分布。

如果没有 reference 约束，模型可能在小规模偏好数据上过拟合。

### DPO Loss 的直觉

DPO loss 关注两个差值。

第一个差值：policy 下 chosen 和 rejected 的 log probability 差：

~~~math
\Delta_\theta=\log \pi_\theta(y_w\mid x)-\log \pi_\theta(y_l\mid x)
~~~

第二个差值：reference 下 chosen 和 rejected 的 log probability 差：

~~~math
\Delta_{\mathrm{ref}}=\log \pi_{\mathrm{ref}}(y_w\mid x)-\log \pi_{\mathrm{ref}}(y_l\mid x)
~~~

DPO 鼓励 policy 的偏好差距比 reference 更符合 chosen > rejected。常见 loss 写成：

~~~math
L_{\mathrm{DPO}}=-\log \sigma\left(\beta\left(\Delta_\theta-\Delta_{\mathrm{ref}}\right)\right)
~~~

简化理解：

```text
如果 chosen 相对 rejected 的优势还不够，就继续更新模型；如果已经足够，就不需要过度更新。
```

### Beta 参数

DPO 中常见一个 `beta` 参数。

它控制 policy 偏离 reference 的强度。

从带 KL 正则的理论推导看，`beta` 是偏离 reference 的代价或温度参数：`beta` 较大时，策略通常更倾向保持在 reference 附近；`beta` 较小时，模型更愿意为了偏好信号改变相对概率。常见实现把它乘在 sigmoid 的输入上，因此还会改变梯度的尺度，不能简单把它解释成“越大更新越强”。实际取值必须结合偏好数据、学习率、reference model 和验证集调节，并同时观察 KL、长度和能力回归。

### DPO 和 SFT 的区别

SFT 学的是：

```text
这个 prompt 下，模仿这个目标回答
```

DPO 学的是：

```text
这个 prompt 下，chosen 比 rejected 更好
```

SFT 需要 demonstrations，DPO 需要 preferences。

SFT 更像行为克隆，DPO 更像偏好对齐。

常见流程是：

```text
Base Model -> SFT -> DPO
```

### DPO 的优点

DPO 的优点：

1. 不需要显式 reward model。
2. 不需要 PPO。
3. 训练流程更简单。
4. 对固定偏好数据，标准训练流程通常比带在线 rollout 的 PPO 链路少一些系统组件。
5. 可以直接复用偏好数据。
6. 实现上更接近常规 supervised training。

这也是 DPO 在工程实践中很受欢迎的原因。

### DPO 的局限

DPO 不是万能的。

局限包括：

1. 依赖高质量 preference pair。
2. 对偏好数据覆盖范围敏感。
3. 可能过拟合偏好数据风格。
4. 不能完全替代复杂在线 RL 场景。
5. reference model 选择会影响结果。
6. 对长回答的 log probability 长度效应要小心处理。

如果 chosen/rejected 数据质量差，DPO 会直接学坏。

### 一个可手算的 DPO 对照

假设某个 prompt 下，policy 对 chosen 和 rejected 的 log probability 分别是 -2 和 -4，reference 分别是 -2.5 和 -3.5。policy 的相对优势是 2，reference 的相对优势是 1，因此 policy 相对于 reference 多向 chosen 偏移了 1。代入 beta=0.1，DPO 的 sigmoid 输入为 0.1，loss 仍然不算很小，说明模型还有更新空间。

如果把 policy 改成 -1.5 和 -4.5，相对优势变成 3，loss 会继续下降，但并不意味着应该无限扩大差距。若这个变化只出现在某个长度很短、措辞固定的偏好切片上，独立评估可能发现模型开始偏好模板化短回答。DPO 的训练日志因此要同时记录 chosen/rejected 长度、相对 log-probability 和不同领域的 pairwise accuracy。

### 最小 demo：DPO loss 如何计算

下面这个 demo 直接使用四个 log probability：policy 对 chosen/rejected 的 log probability，reference 对 chosen/rejected 的 log probability。DPO 比较的是 policy 相对 reference 是否更偏向 chosen。

```python
import torch
import torch.nn.functional as F


def dpo_loss(policy_chosen, policy_rejected, ref_chosen, ref_rejected, beta=0.1):
    tensors = [policy_chosen, policy_rejected, ref_chosen, ref_rejected]
    if not all(t.shape == tensors[0].shape for t in tensors):
        raise ValueError("all log-probability tensors must have the same shape")
    if tensors[0].numel() == 0:
        raise ValueError("at least one preference pair is required")
    if beta <= 0:
        raise ValueError("beta must be positive")
    delta_policy = policy_chosen - policy_rejected
    delta_ref = ref_chosen - ref_rejected
    logits = beta * (delta_policy - delta_ref)
    return -F.logsigmoid(logits).mean()


loss_good = dpo_loss(
    policy_chosen=torch.tensor([-2.0]),
    policy_rejected=torch.tensor([-4.0]),
    ref_chosen=torch.tensor([-2.5]),
    ref_rejected=torch.tensor([-3.5]),
)

loss_bad = dpo_loss(
    policy_chosen=torch.tensor([-4.0]),
    policy_rejected=torch.tensor([-2.0]),
    ref_chosen=torch.tensor([-2.5]),
    ref_rejected=torch.tensor([-3.5]),
)

print("policy prefers chosen loss:", round(loss_good.item(), 4))
print("policy prefers rejected loss:", round(loss_bad.item(), 4))
```
> **代码状态：已验证（2026-10-07；Python 3.13.13；PyTorch 2.12.0+cpu）**


这个例子说明：如果 policy 相比 reference 更偏向 chosen，loss 会更小；如果 policy 更偏向 rejected，loss 会更大。

### 长度偏差问题

DPO 使用 response 的 log probability。

长回答包含更多 token，总 log probability 会受到长度影响。

因此训练和实现中要注意：

1. chosen/rejected 长度差异。
2. 是否按 token 平均。
3. 数据中是否偏好固定长度风格。
4. 是否导致模型变得过短或过长。

不同实现会有不同处理方式。无论采用哪种实现，都应把长度视为偏好优化中的潜在偏差来源。

### DPO 评估

DPO 后不能只看 DPO loss。

需要评估：

1. pairwise win rate。
2. 人工偏好。
3. helpfulness。
4. truthfulness。
5. safety。
6. over-refusal。
7. 代码、数学、知识能力回归。
8. 输出长度和风格变化。

如果 DPO 后模型更会迎合偏好集，但真实能力下降，这不是成功。

### 22 讲·DPO 的失败模式

#### 坑 1：偏好数据质量差

chosen 不一定真的好，rejected 不一定真的差，模型会学到错误偏好。

#### 坑 2：chosen/rejected 差异太弱

两个回答差不多，训练信号弱，标注噪声影响大。

#### 坑 3：reference model 选错

reference 太弱或和 policy 初始化不匹配，会影响约束效果。

#### 坑 4：只看 win rate

Win rate 提升可能来自风格迎合，而不是事实性或推理能力提升。

#### 坑 5：偏好优化导致过度拒答

如果安全偏好数据处理不好，模型可能学会对很多正常请求也拒答。

### DPO 的小型对照实验

DPO 的训练日志至少应同时记录四类量：chosen/rejected 的平均 token 数、policy 与 reference 的相对 log-probability、偏好对的训练准确率，以及独立评估集上的真实任务指标。只看 DPO loss，会把“模型更会拟合偏好对”误认为“模型更适合用户”。

可以设计三组偏好对来观察不同失败模式。第一组让 chosen 和 rejected 只在事实正确性上不同；第二组让二者事实相同、长度和语气不同；第三组加入正常请求与危险请求的边界样本。若第二组训练后平均输出明显变短或变长，说明长度统计改变了优化方向；若第三组的拒答率上升而安全风险没有下降，说明偏好数据把拒答风格当成了安全代理。

对一个偏好对，设 policy 相对 reference 的优势为 g=Δθ-Δref，则 DPO 的梯度会随着 g 变大而逐渐饱和。训练时应观察 g 的分布，而不是只看均值：少量极端样本可能主导更新，导致 policy 在某一风格上过度偏移。把训练集按领域、长度和标注来源切片，通常能更早发现这种问题。

DPO 与 RLHF 的差异也应以可观测对象来区分：RLHF 有 rollout、reward 和策略更新的在线闭环；DPO 直接在固定偏好对上更新 policy。DPO 的工程简单性来自移除了在线环节，但也因此不天然获得新策略分布上的反馈。对于需要持续与环境交互或奖励随状态变化的任务，仍需考虑在线方法或外部 verifier。

### 22 讲·偏好差值的反例与边界

1. 误区：DPO 就是 SFT。
   纠正：SFT 学目标回答，DPO 学 chosen 相对 rejected 的偏好。

2. 误区：DPO 完全不需要 reference。
   纠正：标准 DPO 通常需要 reference model 来提供隐式 KL 约束。

3. 误区：DPO 一定优于 RLHF。
   纠正：DPO 更简单稳定，但 RLHF 在更通用的在线优化场景中仍有价值。

4. 误区：DPO loss 降低就代表模型更好。
   纠正：还要看人工偏好、安全、事实性和能力回归。

### 22 讲·DPO 数值复核实验

1. 写一个 DPO 使用的 prompt/chosen/rejected 样本。
2. 用自己的话解释 DPO 和 RLHF 的区别。
3. 解释 reference model 在 DPO 中的作用。
4. 思考 chosen 比 rejected 更长时可能带来什么问题。
5. 设计一个 DPO 后的评估表。

### 22 讲·从隐式奖励到 DPO 策略的关键结论

这一讲的关键关系：

1. DPO 是直接偏好优化，用 preference pair 直接训练 policy。
2. DPO 不显式训练 reward model，也不需要 PPO。
3. DPO 的核心是提高 chosen 相对 rejected 的概率优势。
4. Reference model 提供基线和隐式 KL 约束。
5. DPO 比 RLHF 工程更简单，但依赖高质量偏好数据。
6. DPO 后仍要评估偏好、安全、事实性、长度偏差和能力回归。

### 22 讲·DPO 资料边界

DPO 的目标与 KL 约束推导见 [Rafailov et al., 2023](https://arxiv.org/abs/2305.18290)；偏好数据格式与 trainer 接口可参阅 [TRL DPO Trainer 文档（固定 revision）](https://github.com/huggingface/trl/blob/adff4933bca014c6110436c8ba6bdbe88b28283c/docs/source/dpo_trainer.md)。论文中的理论等价依赖参考策略、偏好模型和数据分布等假设，因此本讲把标准 DPO 描述为一种离线偏好优化方法，而不是对所有 RLHF 场景的普遍替代。

## 第 23 讲：Reward Model 与 Reward Hacking

### 23 讲·Reward Model 的对象

Reward Model 是 RLHF 的核心组件之一。它看起来只是“给回答打分”，但真正困难的是：这个分数能否代表人类真实偏好？模型会不会为了高分学会钻空子？

这一讲围绕以下问题展开：

1. Reward Model 的输入、输出和训练目标。
2. 偏好数据如何影响 Reward Model。
3. Reward Model 如何评估。
4. Reward Hacking 为什么会发生。
5. Over-Optimization 和 Over-Refusal 的关系。
6. 如何降低 reward model 被利用的风险。
7. 如何从代理目标、分布偏移和人工评估三方面分析奖励模型的局限。

### Reward Model 是什么

Reward Model，简称 RM，是一个用于给回答打分的模型。

它的分数有方向性，但通常没有跨任务、跨模型可直接比较的绝对意义。一个 RM 给回答打 `2.1`，并不表示回答拥有某个固定的“质量等级”；更可靠的解释是，在同一个 prompt 和相近的候选分布中，它是否把更符合标注偏好的回答排在前面。

输入：

```text
prompt + response
```

输出：

```text
scalar reward score
```

分数越高，表示回答越符合训练数据中的人类偏好。

例如：

```text
prompt: 如何缓解过拟合？
response A: 可以使用正则化、早停、数据增强和更多数据。
response B: 过拟合可以通过增大学习率解决。
```

Reward Model 应该给 A 更高分。

### Reward Model 学的不是绝对真理

Reward Model 学的是偏好数据中的模式。

它不是事实检查器，也不是完美裁判。

它可能学到：

1. 哪种回答更有帮助。
2. 哪种回答更安全。
3. 哪种语气更受欢迎。
4. 哪种格式更像高质量回答。
5. 标注者或教师模型的偏见。

所以 Reward Model 的分数只能作为人类偏好的近似代理，而不等于真实质量。

### 偏好数据构造

Reward Model 常用 chosen/rejected pair 训练。

数据格式：

```json
{
  "prompt": "什么是 AdamW？",
  "chosen": "AdamW 是将 weight decay 从 Adam 梯度更新中解耦的优化器。",
  "rejected": "AdamW 是一种 attention 机制。"
}
```

偏好数据来源包括：

1. 人类标注。
2. 专家标注。
3. 用户反馈。
4. 强模型评审。
5. 规则过滤后的自动数据。

数据质量决定 RM 上限。如果偏好标注不一致，RM 会学到混乱信号。

### Pairwise Ranking Loss

Reward Model 通常不是直接预测一个绝对分数标签，而是学习排序。

目标是：

~~~math
r_w>r_l
~~~

其中 `r_w` 是 chosen response 的 reward，`r_l` 是 rejected response 的 reward。

常见损失：

~~~math
L=-\log \sigma(r_w-r_l)
~~~

直觉：

1. chosen 分数高于 rejected，loss 小。
2. chosen 分数低于 rejected，loss 大。
3. 差距越明显，模型越确信 chosen 更好。

这类训练让 RM 学会相对偏好，而不是绝对评分标尺。

### Reward Model 的结构

Reward Model 通常基于语言模型改造。

常见做法：

1. 使用 SFT 模型或 base model 作为 backbone。
2. 去掉或不用 LM head。
3. 增加一个 scalar reward head。
4. 对整段 prompt+response 输出一个标量分数。

简化理解：

```text
LLM encoder/decoder hidden states -> reward head -> scalar score
```

实际实现中，常取最后一个 token 的 hidden state 接 reward head。

### Reward Model 评估

Reward Model 评估不能只看训练 loss。

常见指标：

1. pairwise accuracy。
2. validation ranking loss。
3. chosen/rejected margin。
4. 分领域准确率。
5. 安全样本准确率。
6. calibration。
7. 与人工偏好的一致性。

Pairwise accuracy 指在验证集上，RM 是否给 chosen 更高分。

但高 pairwise accuracy 不代表一定适合 RLHF，因为 policy 训练会主动寻找 RM 的漏洞。

### Distribution Shift

Reward Model 训练时看到的是某个分布下的回答。

RLHF 过程中，policy 会不断变化，生成的回答也会变化。

这会导致 distribution shift：

~~~math
P_{\mathrm{rm\_train}} \ne P_{\mathrm{policy\_outputs}}
~~~

一旦 policy 生成 RM 没见过的奇怪回答，RM 分数可能不可靠。

这正是 reward hacking 的重要来源。

### Reward Hacking 是什么

Reward hacking 指模型利用 reward model 的漏洞获得高分，但输出并不符合真实人类意图。

例子：

1. 为了显得专业，堆很多术语但不回答问题。
2. 为了显得安全，对正常问题也拒答。
3. 为了显得有帮助，编造不存在的事实。
4. 为了迎合偏好，过度道歉、过度奉承。
5. 学会某种模板，使 RM 打高分，但用户体验差。

核心原因：优化的是代理目标，而不是真实目标。

### Goodhart's Law

Goodhart's Law 可以帮助理解 reward hacking：

```text
当一个指标成为优化目标，它就不再是好指标。
```

Reward Model 分数本来只是质量指标。

当 policy 被训练去最大化这个分数时，它会寻找提高分数的捷径。

这就是为什么 RLHF 不能只盯 reward score。

### 最小 demo：代理 reward 和真实偏好可能背离

下面这个 demo 用一个玩具例子说明 reward hacking：Reward Model 可能过度奖励“看起来礼貌和冗长”的回答，但真实用户更喜欢准确、简洁、直接的回答。

```python
responses = [
    {"name": "accurate", "helpful": 9, "polite": 6, "verbose": 3, "true_pref": 9},
    {"name": "fluffy", "helpful": 5, "polite": 10, "verbose": 10, "true_pref": 4},
]


def reward_model_score(item):
    # 一个有缺陷的 RM：过度奖励礼貌和冗长，低估真实 helpfulness。
    return 0.3 * item["helpful"] + 0.4 * item["polite"] + 0.3 * item["verbose"]


for item in responses:
    rm_score = reward_model_score(item)
    print(item["name"], "rm_score=", round(rm_score, 2), "true_pref=", item["true_pref"])
```
> **代码状态：已验证（2026-10-07；Python 3.13.13；标准库）**


如果 policy 只优化这个有缺陷的 `rm_score`，它可能更偏向 `fluffy`，即使真实用户偏好更低。这就是为什么 RM 分数必须配合人工评估、分领域评估和 adversarial eval 使用。

### 23 讲·Over-Optimization

Over-optimization 是 reward hacking 的常见表现。

现象：

1. RM score 持续升高。
2. 人类偏好不升反降。
3. 输出越来越模式化或奇怪。
4. 事实性、安全性或实用性下降。

也就是说，模型越来越会讨好 RM，但不一定越来越会讨好人。

### Over-Refusal

Over-refusal 是安全训练中的典型问题。

模型为了避免危险输出，可能对正常请求也拒答。

例如：

```text
User: 如何用厨房刀安全切菜？
Assistant: 抱歉，我不能提供任何关于刀具的帮助。
```

这就是过度拒答。

原因可能是：

1. 安全偏好数据过强。
2. 标注标准不清。
3. RM 把“拒答”过度奖励。
4. policy 发现拒答容易拿安全高分。

### Reward Model 的盲区

RM 可能在以下场景失效：

1. 专业知识问题。
2. 长链推理问题。
3. 代码正确性。
4. 数学证明。
5. 长上下文一致性。
6. 多语言和低资源语言。
7. 新型安全攻击。
8. 工具调用任务。

因为这些任务需要更强的验证能力，仅靠偏好标注可能不足。

### 如何降低 Reward Hacking

常见缓解方法：

1. 提高偏好数据质量。
2. 增加多样化 prompt 和回答。
3. 使用 holdout 数据检测 RM 泛化。
4. 控制 KL，不让 policy 偏离太远。
5. 做人工评估，而不是只看 RM score。
6. 加入 adversarial evaluation。
7. 对安全、事实性、代码、数学分别评估。
8. 周期性更新 RM 或重新收集偏好数据。

没有单一方法能彻底解决 reward hacking，只能通过数据、训练约束和评估体系共同降低风险。

### Reward Model 与 Safety

Reward Model 常用于安全对齐，但安全偏好非常难定义。

好安全模型应该：

1. 拒绝真正危险请求。
2. 对正常请求提供帮助。
3. 能区分教育、防御、研究和滥用。
4. 不因为关键词就机械拒答。
5. 能给出安全替代方案。

如果 RM 只学会“看到危险词就奖励拒答”，就容易导致 over-refusal。

### 23 讲·奖励模型的失败模式

#### 坑 1：偏好标注指南不清

标注者标准不一致，RM 学到噪声。

#### 坑 2：验证集和训练集太像

RM 在验证集上表现好，但对新模型输出泛化差。

#### 坑 3：只评估整体 pairwise accuracy

整体准确率掩盖安全、数学、代码等子领域失败。

#### 坑 4：Reward score 被当成真实质量

Reward score 是代理指标，不能替代人工评估。

#### 坑 5：安全奖励过强

模型学会过度拒答，helpfulness 下降。

### 代理奖励的验证实验

Reward Model 的 pairwise accuracy 只是必要条件，不是充分条件。一个更有信息量的实验是把回答分成三组：训练分布内的普通回答、由当前 policy 生成的新回答、刻意改变长度和格式但保持事实内容不变的对照回答。分别计算 RM 分数、人工偏好、事实核验和安全分类结果，再观察它们的相关性是否随分布变化而下降。

可以用一个简单的代理偏差量描述这种背离：设人工或客观评估分为 h(y)，Reward Model 分为 r(y)，在同一任务切片上计算标准化后的差值：

~~~math
B_{\mathrm{proxy}}=\mathbb{E}_{y}\left[\hat r(y)-\hat h(y)\right]
~~~

均值接近零也不代表没有问题，因为正负误差可能抵消；还应报告相关系数、分位数和极端样本。若模型优化后 `r` 持续上升而 `h` 停滞或下降，就是典型的过度优化信号。

对安全任务，拒答率必须和正常请求的帮助率一起报告。把所有含风险词的样本都拒答，可能让安全分数上升，却损害防御性教育、合规操作和普通工具使用。更好的数据切片包括“真正需要拒答”“可以安全回答”“需要澄清后回答”三类，并分别分析误拒与漏答。

这也解释了为什么更新 RM 不能只增加更多随机样本：数据必须覆盖 policy 会探索到的分布外行为，并包含能揭露长度、礼貌模板、引用格式和拒答风格偏差的反事实对照。

### 23 讲·Reward Hacking 的反例与边界

1. 误区：Reward Model 分数就是回答质量。
   纠正：RM score 是代理指标，可能被 exploit。

2. 误区：RM 验证准确率高就一定能用于 RLHF。
   纠正：policy 会产生分布外回答并主动寻找 RM 漏洞。

3. 误区：Reward hacking 只是安全问题。
   纠正：事实性、格式、长度、语气、代码和数学都可能被 hack。

4. 误区：拒答越多越安全。
   纠正：过度拒答会损害 helpfulness，好的安全模型要区分危险和正常请求。

### 23 讲·代理奖励复核实验

1. 写一个 reward model 训练用的 chosen/rejected 样本。
2. 用自己的话解释 pairwise ranking loss。
3. 举 3 个 reward hacking 的具体例子。
4. 设计一个 Reward Model 评估表，包含整体和分领域指标。
5. 分析 over-refusal 为什么会损害用户体验。

### 23 讲·从排序分数到真实目标的关键结论

这一讲的关键关系：

1. Reward Model 把偏好数据转成标量 reward。
2. RM 学的是相对偏好，不是绝对真理。
3. Pairwise ranking loss 鼓励 chosen 分数高于 rejected。
4. RM 会受到数据噪声、分布偏移和任务盲区影响。
5. Reward hacking 是代理目标被过度优化的结果。
6. 降低 reward hacking 需要数据、KL 约束、人工评估和 adversarial eval 共同作用。

### 23 讲·Reward Model 资料边界

Pairwise reward modeling 与人类反馈流程可由 InstructGPT（[Ouyang et al., 2022](https://arxiv.org/abs/2203.02155)）和摘要反馈研究（[Stiennon et al., 2020](https://arxiv.org/abs/2009.01325)）作为一手入口。Goodhart 风险和分布偏移是机制层面的解释；本讲的玩具 reward 函数只用于展示代理目标背离，不能作为真实用户偏好的测量。
