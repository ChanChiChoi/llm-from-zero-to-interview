# 第三部分：训练、对齐与推理

## 本文件的阅读路径

前面的讲次介绍了模型、训练和服务中的关键部件。这一章练习把它们用于处理一个具体工程问题：知识助手引用了旧版流程，究竟是文档没更新、索引没刷新、检索拿错资料，还是模型拿到新资料后仍然答错？实际工作中，工程师需要先找到能区分这些原因的证据，再决定改哪一段。

贯穿本章的知识助手仍是教学假设。文档、问题和结果均为构造示例，不代表真实企业数据或线上测量。我们会把一次技术改动组织成“明确任务—定位链路—提出假设—小范围验证—检查代价—记录结论”的闭环。遇到不了解的新模型或方法时，本章把它作为待验证的工程假设来查证：回到原始资料、任务和测量条件，不要求读者撰写论文或复现大型模型。

~~~mermaid
flowchart LR
    A["用户报告的问题"] --> B["确认任务与影响"]
    B --> C["沿数据和请求链路定位"]
    C --> D["列出可区分的原因"]
    D --> E["运行最小验证"]
    E --> F["检查质量、成本和风险"]
    F --> G["修复、继续调查或回退"]
~~~

## 第 29 讲：从故障现象到可验证的问题

### 29 讲·先把“答错了”说清楚

“助手最近不可靠”还不能指导排查。它可能指答案不正确、引用不支持结论、漏掉关键步骤、输出格式不合约定，也可能是新版本变慢或拒答变多。每种问题需要不同的样本、指标和修复位置。

先把报告改写成能复查的描述：哪个版本、哪些请求、什么时间范围、具体出现什么错误、用户因此受到什么影响。然后明确本次要改善的目标和不可突破的约束。例如，教学中的目标可以是“回答设备故障问题时，引用当前有效手册；资料不足时明确说无法确认”，约束则包括不泄露员工信息、不能给出无手册依据的维修步骤。

| 需要说清的内容 | 示例问题 |
| --- | --- |
| 输入和用户 | 哪类员工提出什么问题？是否附带截图、表格或录音？ |
| 期望结果 | 回答要解决问题、引用资料，还是只返回字段？ |
| 失败定义 | 答案错误、证据过期、引用不支持、漏步骤，哪一种算失败？ |
| 质量和风险 | 哪些错误可以接受，哪些必须拒答或交给人工？ |
| 服务约束 | 请求量、最长等待时间、单次成本和可用硬件是什么？ |
| 判断证据 | 要保存原始问题、检索结果、模型版本、提示、输出和人工标签中的哪些？ |

面试时先复述问题并补齐缺失条件，体现的是你在定义工作目标，不是在拖延回答。条件暂时未知时，把它列成假设，并说明哪项测量会改变方案。

### 29 讲·沿请求链路定位

一个答案经过多个环节才到用户。知识助手的简化链路可以写成：

```text
手册与权限 -> 清理和切分 -> 索引更新 -> 查询改写与检索
    -> 提示组装 -> 模型生成 -> 引用/格式校验 -> 用户界面
```

看到最终答案错了，先保留一条请求的完整记录，再逐段核对输入输出。比如答案引用了旧版流程，至少有几种不同原因：

| 假设 | 应该能观察到什么 | 最小检查 |
| --- | --- | --- |
| 新手册还没入库 | 原始文档目录已有新版本，但索引没有对应文档 ID | 对照源文件清单、入库时间和索引文档 ID |
| 查询检索到旧手册 | 新旧版本都在索引中，但返回结果包含旧版本或排序靠前 | 固定同一查询，查看 top-k 文档、版本字段和分数 |
| 提示没有区分版本 | 检索结果里有新旧资料，模型收到的上下文仍未标出有效时间 | 查看实际送入模型的完整提示和文档元数据 |
| 模型忽略了新资料 | 上下文只有新版本，回答却沿用旧步骤 | 在相同上下文下重放请求，检查输出与引用对应关系 |
| 评估标签或展示错了 | 原始输出正确，界面或评测器判为错误 | 将模型原始响应、引用解析和最终 UI 展示逐一对照 |

表中的检查顺序不是固定规定。先做读日志、查版本等低成本检查；找到证据后再决定是否改检索、提示、模型或前端。不要一开始就重训模型，因为这既昂贵，也会同时改变太多因素。

### 29 讲·把故障拆成可观测指标

“准确率”不能单独说明 RAG 系统哪里坏了。至少把检索过程与最终回答分开观察：

| 阶段 | 要检查的问题 | 可记录的结果 |
| --- | --- | --- |
| 文档接入 | 应用的资料是否进入当前索引？版本、权限、时间戳是否保留？ | 入库覆盖率、索引延迟、无权限文档命中数 |
| 检索 | 相关且有效的资料是否出现在候选结果中？ | 相关文档是否召回、排名位置、版本正确率 |
| 回答 | 回答是否解决问题，重要陈述是否有对应证据？ | 任务正确率、完整度、引用支持率、无依据断言数 |
| 服务 | 系统能否在约束内完成请求？ | 首 token 延迟、总延迟、失败率、单次成本 |
| 风险 | 不该回答或不该执行的请求是否被拦截？ | 高风险错误、误拒、人工接管率、权限违规数 |

检索效果和生成结果是相关但不同的测量。检索阶段可以用标注过的相关文档检查召回或排序；系统阶段再分别检查回答是否相关、完整、受上下文支持。微软的 RAG 评估文档也将文档检索列为过程评估，将 groundedness、relevance 等列为系统评估，并说明这些量回答不同问题。[Microsoft Foundry RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators)

自动评估器可以帮助筛查大量样本，但它自身也可能误判。高风险或边界样本应抽样人工复核；如果用了 LLM judge，要先用一批人工标注样本核对它的漏判、误判和偏好。一个分数只支持它实际测量的内容，不能自动证明系统“可靠”。

### 29 讲·选择能区分原因的最小实验

候选原因列出来后，问三个实际问题：

1. 哪个检查最便宜，能排除最多不相关的猜测？
2. 怎样固定其他条件，避免同时改检索、提示和模型？
3. 出现什么结果时，我会放弃当前假设？

比如，先查看这 20 条失败请求的索引版本和 top-k 文档，不需要调用模型或训练。如果失败请求中大多数没有取到新版本，先调查接入和检索；如果新版本已进入上下文，再对原请求做固定提示回放。回放仍然给出旧步骤时，才进一步检查提示约束、模型生成和引用校验。

每次实验写清对照、只改变的因素、样本、指标和通过条件。若一周后出现多个改动，仍然分不清哪个改变带来结果，就把实验拆小，而不是用一个复杂总分把效果合并起来。

### 29 讲·完整示例：知识助手引用了旧版流程

下面是教学构造，不是生产事故记录。某位员工询问“电机 E17 报错后是否可以继续运行”，助手给出旧版手册里的处理步骤。排查目标不是“让模型回答得更好听”，而是让当前手册进入正确请求，并且让答案引用它支持的内容。

| 排查动作 | 观察 | 结论边界与下一步 |
| --- | --- | --- |
| 核对源文件 | 共享目录存在新版手册，索引清单仍显示旧版本 | 支持“接入/索引更新未完成”，尚不能解释其他请求 |
| 检查失败请求的 top-k | 结果只含旧版文档 | 问题发生在生成之前，先修索引和版本过滤 |
| 重建索引后重放固定查询 | 新版文档进入 top-k，回答仍引用旧步骤 | 已排除单纯缺文档，继续检查提示输入和引用校验 |
| 查看发送给模型的上下文 | 提示同时包含两版内容，但没有清晰版本标记 | 提示组装有问题；明确有效日期后再做配对回放 |
| 对比最终输出与引用 | 回放改正，但 UI 仍展示旧引用链接 | 检查引用解析和前端缓存，不能只盯着模型文本 |

这条记录把故障定位到不同环节。每修好一处，都用相同请求和一组相邻回归样本重跑，并检查准确性、引用支持和延迟。不要只挑一条成功案例，也不要因本例通过就声称所有文档版本问题都已解决。

### 29 讲·判断新方法和新模型的信息

做项目或面试时，常会听到“某新模型解决了长上下文问题”或“新方法能显著减少成本”。先把陈述拆成可查内容：来源是谁、模型/框架版本是什么、测了什么任务、用哪个基线、代价和失败样本是什么。

| 资料 | 可以帮助确认 | 不能自动证明 |
| --- | --- | --- |
| 论文或技术报告 | 作者公开的方法、实验条件和报告结果 | 所有业务任务都能复现同样收益 |
| 官方文档或模型卡 | 公开接口、配置和说明的限制 | 未公开的训练细节或内部架构 |
| 固定版本源码 | 某个 revision 的具体实现 | 其他版本或生产部署的表现 |
| 独立评估和团队自有回归 | 指定评测设置下的比较结果 | 未覆盖任务、用户和安全风险 |
| 社区讨论或演示 | 值得继续查证的线索 | 已确认的机制或普遍效果 |

面试中可以把已知、推断和未知分开说。比如“文档确认该接口支持长输入；我们还没有证据证明它在本项目的表格问答上优于检索方案，下一步会用相同问题集、相同预算和证据指标做对照”。承认边界并给出验证动作，比猜测隐藏实现更专业。

### 29 讲·质量、成本与风险要一起判断

不同方案通常各有取舍。下面的比较用于确定需要测什么，不能替代目标环境的测量：

| 候选方案 | 可能改善什么 | 需要同时观察什么 |
| --- | --- | --- |
| 更新索引和版本过滤 | 减少过期或不相关资料 | 接入时延、误过滤、权限条件 |
| 调整 chunk 和检索参数 | 提高相关资料进入上下文的机会 | top-k 噪声、提示长度、检索延迟 |
| 修改提示和引用格式 | 提醒模型按证据回答 | 可解析率、漏答、无依据陈述 |
| 使用更强模型或增加验证 | 复杂问题可能更容易处理 | 单次成本、P95 延迟、误报和新增故障点 |
| 训练适配模型 | 可能改善稳定的格式或领域行为 | 数据准备、回归、过拟合、维护成本 |

对每个候选方案都设一个不回归的底线，例如高风险错误不能增加，文档权限不能绕过，服务延迟不能超预算。先用离线回放或沙箱测试；如果改动涉及外部动作、个人信息或不可逆影响，应增加权限检查和人工确认。

### 29 讲·常见排查误区

| 误区 | 为什么不够 | 改成什么动作 |
| --- | --- | --- |
| 一看到幻觉就微调 | 错误可能来自检索、过期数据、提示或 UI | 保存失败请求的完整链路记录，先定位出错阶段 |
| 只报告整体准确率 | 一个切片变好可能掩盖高风险切片回归 | 同时看按任务、版本、语言和风险分层的结果 |
| 新旧版本用了不同评测集 | 分数差可能来自样本差异 | 固定样本快照、提示、解码和评分口径 |
| 只看 judge 分数 | 评估器可能与模型共享偏差 | 用人工标签、程序校验和原始样本抽查交叉核对 |
| 一个改动同时换了模型、检索和提示 | 无法归因，回归后也难回退 | 拆成可独立复现的小实验，保留配置和基线 |
| 把一次通过当作修复完成 | 可能只覆盖了单一样本 | 用原失败样本、相邻样本和负例建立回归集 |

### 29 讲·练习：写出下一步而不是列术语

1. 助手引用了一份已废止的流程。画出从源文件到 UI 的链路，写出至少三个可区分的原因，并为每个原因指定一个最小检查。
2. 线上回答变慢但答案质量没变。列出需要先收集的请求长度、队列、工具、首 token 和生成时延信息，说明哪类证据能区分模型计算与系统等待。
3. 新模型在公开 benchmark 得分较高，业务评测没有改善。写出公平对照所需的固定条件和至少两个不能由公开分数推出的结论。
4. 为“回答遗漏关键步骤”设计一组有标准答案的样本，分别检查检索是否召回、答案是否完整，以及 judge 是否与人工标注一致。

### 29 讲·资料边界

微软 RAG 评估文档说明检索评估与回答评估各自关注的对象，并列出依赖标注、模型评估或预览能力的不同评估器。具体 API、区域可用性、模型和指标名称会变动，本文引用它说明“分阶段测量”的区别，不要求采用某一云服务。[Microsoft Foundry RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators)

前沿模型与研究的证据应回到对应论文、官方文档、固定版本实现和目标任务评测；单一排行榜、宣传页或一次演示都不够。这里的助手案例、故障记录和候选方案是教学构造，不代表真实企业事故或生产最佳实践。

## 第 30 讲：综合实验与项目复盘

### 30 讲·一次改动怎样才可复核

上一讲练习了定位问题。本讲把定位结果整理为可重复、可解释的实验。项目实验的交付不只是一个分数，而是让同事能回答：改了什么、为什么改、比较条件是否公平、哪些样本变好或变差、有没有更便宜的解释、出了问题怎样回退。

### 一次综合实验的基本节奏

1. **定义任务和失败代价**：写明输入、期望输出、样本范围、失败标准和硬约束。
2. **保存基线**：记录模型 revision、数据快照、索引、提示、解码、硬件、软件、评测器和随机设置。
3. **提出可被推翻的假设**：说明改动影响哪一段链路，以及什么结果会让你放弃这个解释。
4. **拆分对照**：每轮只改一个主要因素；若需要联动多个因素，用小型消融保留归因能力。
5. **同时检查质量和运行代价**：按切片看正确性、证据、格式、风险、延迟、吞吐与成本。
6. **抽查失败样本**：保留原始输入、检索/工具记录、输出、标签和版本，避免均分遮住新故障。
7. **做决定并留回退路径**：明确采用、继续验证、暂缓或回滚，并保存恢复所需配置。

这套过程不要求每个小改动都写长报告。最少应有一个能让下个人重跑的记录，以及一个清楚的上线/停止条件。

### 综合实验的组织方式

按故障位置拆任务，而不是按技术名词堆实验：

| 实验块 | 固定什么 | 可以比较什么 | 典型观察 |
| --- | --- | --- | --- |
| 文档与检索 | 同一问题、模型、提示和评分规则 | 入库版本、切分、检索器、top-k | 相关文档是否进入上下文 |
| 回答与引用 | 同一检索结果和模型版本 | 提示、解码、引用校验 | 回答是否受证据支持、是否完整 |
| 模型适配 | 同一训练/验证切分和服务配置 | SFT 数据、mask、训练轮数或适配方法 | 目标行为与通用能力是否变化 |
| 服务性能 | 同一请求分布和输出上限 | batching、量化、缓存配置 | 延迟、吞吐、显存和质量回归 |
| 风险控制 | 同一风险样本和权限设置 | 过滤、拒答、验证器和人工确认 | 错误动作、误拒和回退是否变化 |

阶段性比较便于找原因；完成后仍要用同一端到端任务回放，确认单项改善没有破坏系统目标。

### 综合结果如何报告

不要把不同性质的结果硬加成一个“项目总分”。逐项写清口径、基线和结果：

| 检查项 | 必须交代 | 例子 |
| --- | --- | --- |
| 任务质量 | 样本范围、分母、标签方法、切片 | 100 个问题中，多少条回答完整且正确 |
| 证据质量 | 关键陈述与来源怎样对应 | 过期引用、缺少引用、证据不支持各有多少 |
| 服务表现 | 硬件、请求长度、并发、延迟统计 | P50/P95、超时比例、单次成本 |
| 风险表现 | 风险定义和严重程度 | 越权、误拒、不安全回答、人工接管 |
| 不确定性 | 样本量、随机性、评估器局限 | 哪些结论只在本次构造集成立 |
| 回退能力 | 旧版本、配置和数据能否恢复 | 如何回滚模型、索引和提示 |

如果两个方案差异很小，样本也少，应说“当前证据不足以确定优劣”，并说明需要补哪类样本或复测。不要把点估计包装成确定结论；比较的统计方法要与样本是否配对、是否重复和指标类型相匹配。

### 失败复盘模板

```text
问题与影响：哪类用户遇到什么失败，影响范围多大？
基线：模型、数据/索引、提示、服务和评估版本是什么？
现象证据：原始请求、检索结果、响应、日志和标签在哪里？
当前解释：哪些原因仍可能成立，哪些已被检查排除？
实验：本轮只改变什么，成功或失败如何判定？
结果：质量、证据、风险和资源各发生了什么变化？
决定：采用、继续验证、暂停或回滚；理由是什么？
下一步：谁需要补什么样本、配置或复核？
```

### 从技术记录到项目说明

面试官追问项目时，先用一两句话说明任务、约束和个人职责，再说明方案和证据。只讲模型名或“提升了准确率”不够；要说清基线、样本口径、失败样例和 trade-off。没有真实项目经历时，可以明确说这是学习实验或设计练习，不把教学示例说成生产经验。

一段可信的说明通常包含：

1. 用户需要什么，原方案在哪些请求上失败；
2. 你负责的范围、能使用的数据和服务约束；
3. 选了什么方案，为什么先做它，备选方案是什么；
4. 用什么固定样本和指标比较，结果的证据边界在哪里；
5. 哪类错误仍没解决，出现什么信号时会回退或换方案。

资深工程师常继续问：“如果检索 recall 已经足够，为什么还会答错？”“你如何排除评估数据泄漏？”“多花两倍推理成本能换来多少可靠改进？”“这次结果在哪些用户或版本上不成立？”回答时把问题接回数据、机制、指标和当前证据，不必假装已经知道未披露的内部细节。

### 练习：完成一份可复核的实验单

为“知识助手偶尔引用旧流程”填写一份实验单。至少包含一条原失败样本、一个当前有效文档、三个可区分假设、固定条件、检查顺序、分阶段指标、回归样本和回退条件。不要只写“改 prompt”或“换大模型”，要说明什么结果会支持或推翻你的选择。

### 七天小型项目计划

下面是学习计划样例，可按设备和时间缩小任务。使用公开或自行编写的合成文档，不上传公司资料；不需要训练大模型，也不把这个练习包装成生产系统。

| 天 | 任务 | 当天留下的证据 |
| --- | --- | --- |
| 1 | 写需求、用户问题和失败定义 | 任务契约与 10 条合成问题 |
| 2 | 准备带版本/日期的短文档和可核对答案 | 文档清单、答案及引用标签 |
| 3 | 搭建最小检索或人工模拟的候选检索结果 | 固定输入、候选资料和版本记录 |
| 4 | 检查检索是否拿到正确证据 | 每题命中/未命中与错误分类 |
| 5 | 生成回答并检查支持、完整和拒答 | 原始提示、回答、引用核验结果 |
| 6 | 修改一个环节，重跑同一批请求 | 新旧配置差异、回归表和失败样本 |
| 7 | 整理限制、成本和下一步 | 一页复盘与五分钟口头说明 |

这是一个可复核的学习练习，不是上线标准。它的价值是让你亲手走过证据链，知道何时该用检索、何时要查生成、怎样报告一次失败。

### 本讲小结：从方法名回到可验证的决定

每个技术选择都要接上目标、作用位置、对照、测量和边界。改动失败不代表没有学到东西：如果它排除了一个原因、留下可重跑记录并缩小下一步范围，仍然有价值。相反，只有“效果提升”的句子却没有基线、分母和失败样本，不能支撑可靠判断。

## 本阶段交接

文本模型的综合实验从请求目标和数据链路出发，逐步检查训练、生成、证据与服务约束。下一部分把同样的分析方法扩展到图片、语音和视频：先辨认模态进入系统的方式，再检查信息保留、时间关系、质量和成本。无论输入是什么，仍要把任务目标、证据和失败处理写清楚。
