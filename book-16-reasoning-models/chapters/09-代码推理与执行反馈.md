# 第九章：代码推理与执行反馈：从程序文本到可验证修复

代码是 reasoning model 的重要训练场景，因为代码不只是可以阅读的文本，还可以被解析、编译、运行和测试。模型先提出程序，执行环境再返回错误、输出、测试结果或资源状态，模型根据这些观察修改程序，这就形成了一条比“生成一段看起来像代码的文本”更具体的反馈链。

但“代码可以执行”并不等于“执行结果就是可靠真值”。测试可能覆盖不足，公开样例可能泄漏，环境可能不一致，候选程序可能利用测试漏洞，执行器本身也可能成为安全攻击面。一个通过公开测试的程序，仍然可能在隐藏边界条件上失败；一个能反复修改代码的 agent，仍然可能只是不断试错而没有定位根因。

本章把代码推理拆成几个相互连接、但不能混为一谈的对象：任务规格、程序候选、执行环境、测试 oracle、反馈信号、修复轨迹、候选选择、训练目标、评估指标和安全边界。初学者可以先把它理解成“写代码、跑代码、读反馈、改代码”；专家则需要进一步问：反馈是否代表真实规格，测试是否独立，候选是否相关，修复是否只针对公开样例，环境是否可重放，成本和风险是否记录完整。

## 0.1 一个公开测试全过、隐藏测试失败的例子

任务是实现 `count_positive(nums)`，返回列表中严格大于零的元素个数。公开测试只给出两个样例：

~~~text
count_positive([1, -2, 3]) = 2
count_positive([-1, 5]) = 1
~~~

模型生成下面的程序：

~~~text
def count_positive(nums):
    return sum(1 for x in nums if x >= 0)
~~~

它能通过公开测试，因为公开样例没有包含零。但隐藏测试包含：

~~~text
count_positive([0, 1, -1]) = 1
count_positive([0, 0]) = 0
~~~

此时程序返回 2 和 2，两个结果都错误。执行反馈告诉我们一个重要事实：测试通过只证明“在给出的输入上通过”，不证明程序满足完整规格。模型若只把公开测试得分当作任务真值，就会学到“只要样例通过就停止”。

把 `>= 0` 改成 `> 0` 是一个有效修复，但训练系统还应记录修复为什么有效：错误来自边界条件理解，而不是语法、循环结构或计数器初始化。只有记录错误类型和修复后的行为，后续模型才可能把反馈迁移到 `is_valid`、区间判断或权限边界等其他代码任务。

## 0.2 初学者视角：执行反馈究竟告诉了什么

初学者可以把一次代码任务分成五步：

1. 先读懂需求，明确输入、输出和特殊条件。
2. 写出一个候选程序。
3. 在受控环境里执行程序。
4. 根据报错或测试失败定位问题。
5. 修改后重新执行，并确认不是只修好了一个样例。

编译错误通常说明程序还没有进入运行阶段；运行时异常说明某条执行路径触发了问题；测试失败说明程序行为和测试 oracle 不一致；超时说明程序可能不满足复杂度要求；资源或安全拦截说明候选程序不适合继续执行。不同反馈对应不同的修复动作，不能把所有失败都归结为“再生成一段代码”。

## 0.3 专家视角：代码能力至少有四层

专家需要把下面四层分开记录：

- 生成能力：候选程序能否表达需求，并通过解析或编译。
- 功能能力：候选程序在独立测试和完整规格上是否产生正确行为。
- 反馈利用能力：模型能否从错误信息和失败用例定位原因并产生有效补丁。
- 工程能力：程序是否满足复杂度、依赖、可维护性、权限和部署环境约束。

pass@k 主要反映候选池里是否存在正确程序；测试通过率反映某个测试集合上的行为；修复成功率反映反馈闭环；沙箱违规率和资源超限率反映执行安全。它们不是同一个分数，也不能用一个平均值替代。

## 0.4 资料与证据边界

HumanEval 提供了函数级代码生成和 pass@k 评估的经典入口；它适合说明候选生成与功能测试，但不能代表真实仓库维护。AlphaCode 论文展示了大规模候选生成、过滤、聚类和选择的竞赛编程路线；论文实验不能直接证明所有生产代码任务都能用相同预算解决。CodeRL 研究了把执行结果用于代码生成强化学习的路线，Self-Debugging 研究了让模型根据执行反馈进行迭代修复的路线。

APPS 和 MBPP 代表不同规模与风格的程序题数据；SWE-bench 一类真实仓库修复评测则把问题扩展到代码库导航、依赖、补丁回归和项目测试。它们的任务契约、测试环境和指标口径不同，比较时必须同时记录数据切分、语言版本、测试可见性和执行预算。

Docker 的安全文档可以作为容器隔离、权限和资源控制的工程入口；Python 的 `ast` 文档说明如何解析语法树，但语法树检查不是安全沙箱。正文中的代码、公式和数字是教学构造或目标系统审计口径，除非明确标注，否则不应理解为上述论文或官方文档报告的生产系统结果。

## 1. 代码任务的完整对象

### 1.1 任务不只是自然语言提示

一个代码任务至少包含需求文本、接口签名、输入输出约束、测试集合、执行环境和资源预算。可以写成：

~~~math
c_i=(x_i,\sigma_i,T_i^{\mathrm{pub}},T_i^{\mathrm{hid}},E_i,B_i,\mathcal{P}_i)
~~~

其中：

- `x_i` 是自然语言需求、示例和业务规则；
- `sigma_i` 是函数签名、命令行接口、输入 schema 或返回值约束；
- `T_i^pub` 是模型可以看到的公开测试；
- `T_i^hid` 是用于独立评估的隐藏测试；
- `E_i` 是语言、编译器、依赖、操作系统和运行限制组成的环境；
- `B_i` 是时间、内存、候选数、修复轮数和工具调用预算；
- `P_i` 是针对该任务生成的候选程序集合。

这个对象的价值在于把“模型没写对”拆成可定位的原因。可能是需求解析错，也可能是签名不匹配、测试 oracle 错、依赖版本不同或执行环境超时。如果只保存 prompt 和最终代码，后续无法判断失败究竟发生在哪里。

### 1.2 规格、实现和执行环境

自然语言规格描述“应该发生什么”，程序实现描述“如何实现”，执行环境决定“这段实现实际如何运行”。同一段代码在 Python 版本、浮点库、时区或数据库配置不同的环境中，结果可能不同。

可以把一次执行抽象为：

~~~math
o=\operatorname{run}(p,\tau;E)
~~~

`p` 是程序，`tau` 是输入或测试用例，`E` 是环境，`o` 可以是返回值、异常、标准输出、退出码、耗时、内存峰值和安全事件。只有在 `E` 固定或差异被记录时，两个候选的执行结果才具有可比性。

### 1.3 功能正确性的理想定义

如果 `Spec_i` 表示任务的完整规格，理想正确性可以写成：

~~~math
p\models\operatorname{Spec}_i
\quad\Longleftrightarrow\quad
\forall \tau\in\mathcal{D}_i,
\operatorname{run}(p,\tau;E_i)\text{ satisfies }\operatorname{Spec}_i(\tau)
~~~

`D_i` 是规格允许的全部输入空间。真实系统通常无法穷举 `D_i`，只能抽取测试集近似判断。因此测试通过是有限证据，不是数学意义上的普遍证明。对形式化规格、有限状态空间或可证明算法，才可能进一步使用形式验证；普通单元测试不能承担这个结论。

### 1.4 文本相似度为什么不够

两个程序的变量名、注释和控制流可以完全不同，却产生相同的行为；两个程序也可能在文本上非常相似，却都漏掉同一个边界条件。因此 BLEU、编辑距离或 embedding 相似度只能作为辅助信号，不能替代功能测试。

在训练中，如果把参考实现的文本相似度当成主目标，模型会更愿意复制常见写法；如果把执行结果和规格测试作为主要反馈，模型才有机会学习多种等价实现。后者仍需要测试覆盖和安全控制，不能简单理解成“运行一次就解决所有评价问题”。

## 2. 解析、编译和运行反馈

### 2.1 语法解析反馈

解析器检查字符是否能组成合法的语法树。括号不匹配、缩进错误、关键字位置错误和字符串未闭合，都属于解析阶段失败。这个阶段的反馈通常局部而明确，适合训练模型学习格式和语言语法，但不能说明程序逻辑正确。

Python 的 `ast.parse` 可以把源代码转换成抽象语法树，用于教学检查、风格分析和静态规则匹配。它能识别 `import`、`while`、函数调用和属性访问等语法节点；它不能判断任意代码在操作系统、网络和解释器漏洞上的安全性。

### 2.2 编译反馈

编译型语言还会经历类型检查、名称解析、链接和目标代码生成。编译失败可以告诉模型类型不匹配、符号缺失或接口调用错误，但编译通过只说明程序符合某一编译器和编译选项接受的语言约束。

训练数据应保留编译器版本、命令行参数和完整错误位置。只保存“编译失败”这个布尔值，会丢掉对修复最有用的上下文；只保存完整原始日志，又可能把大量无关路径和环境信息喂给模型，增加上下文成本与隐私风险。

### 2.3 运行时反馈

运行时错误包括除零、空引用、越界、类型错误、死循环、资源耗尽和未捕获异常。它们说明某条实际执行路径失败，但不一定指出需求层面的根因。例如 `IndexError` 可能来自错误的边界假设，也可能来自前面漏掉的输入校验。

反馈摘要应保留：异常类型、失败位置、调用栈的必要部分、触发输入、此前的状态和资源使用。摘要过短会丢失因果信息，摘要过长则会让模型把注意力浪费在路径、时间戳和重复日志上。

### 2.4 测试反馈

单元测试把一个输入和期望行为组成可执行断言。当测试集合 `T` 非空，候选程序在 `T` 上的通过率可以定义为：

~~~math
S(p,T)=
\frac{1}{|T|}
\sum_{\tau\in T}
\mathbb{1}\left[
\operatorname{run}(p,\tau;E)=\operatorname{oracle}(\tau)
\right]
~~~

这里的 `oracle` 可以是精确答案、性质检查器、参考实现或人工确认函数。`T` 为空时通过率没有定义，不能把“没有测试”当成 1 或 0。`S(p,T)=1` 只表示该候选通过 `T` 中的测试；如果 `T` 很小、oracle 有误或输入分布偏窄，这个分数仍可能高估能力。

### 2.5 静态、类型和安全反馈

静态分析可以发现未使用变量、潜在空值、不可达分支、危险 API 和复杂度迹象；类型检查可以发现接口和数据类型不一致；安全扫描可以发现密钥硬编码、命令拼接、路径穿越或危险依赖。它们提供的是风险信号，不是完整功能证明。

多个反馈可能冲突。例如一个为了快速修复而写的补丁通过全部功能测试，但增加了 SQL 拼接风险；一个类型安全的实现可能不满足业务的舍入规则。系统应分别记录功能、性能、可维护性和安全结果，不要把它们无条件加成一个不可解释的总分。

### 2.6 资源反馈

代码的行为不仅是返回值，还包括时间、内存、磁盘、进程、文件和网络。算法复杂度不合适时，程序可能在小样例上通过，在大输入上超时；依赖缓存或全局状态时，单独执行通过，连续执行却出现污染。

资源反馈至少应包含墙钟时间、CPU 时间、峰值内存、退出原因和限制值。不同平台的时间不能直接比较，必须说明硬件、并发度、容器限制和是否包含编译时间。

## 3. 测试为什么能当 verifier，又为什么不能独断

### 3.1 测试 oracle 的三种来源

第一类是精确 oracle，例如排序后的数组、解析后的整数或有限状态的预期输出。第二类是性质 oracle，例如输出必须有序、总和守恒、结果满足不变量。第三类是参考实现或人工判断，适合复杂业务，却可能把参考实现的 bug 和标注分歧带进评价。

选择 oracle 时应问：它检查的是最终值、性质、异常行为还是资源边界；它是否和需求独立；它能否被候选程序投机；失败时能否给出足够有用的反馈。

### 3.2 公开测试和隐藏测试的分工

公开测试适合训练反馈、调试和候选初筛。隐藏测试适合检查泛化、边界条件和是否过拟合公开样例。若隐藏测试被用于模型每一步修复，模型就会逐渐把隐藏集合当成公开集合，独立性会消失。

理想的实验应至少区分训练可见测试、开发测试、最终隐藏测试和新任务测试。报告中还应说明测试是否来自同一模板、同一作者、同一仓库或同一参数族。

### 3.3 测试覆盖率

当程序包含至少一条可执行语句、测试集合非空时，语句覆盖率的教学定义是：

~~~math
C_{\mathrm{stmt}}(p,T)=
\frac{|\operatorname{StmtCovered}(p,T)|}
{|\operatorname{Stmt}(p)|}
~~~

如果程序没有可执行语句，覆盖率没有定义；分支覆盖率同样要求可执行分支分母非空。覆盖率只能说明测试执行过哪些路径，不能说明断言是否足够严格。一套测试可以有很高的语句覆盖，却没有检查边界输出；也可以覆盖率不高，却准确检查了最危险的权限分支。

### 3.4 变异测试

变异测试把程序做一个小改动，例如把 `>` 改成 `>=`、删除一个条件或改变返回值，再看测试能否发现这个变异。若有效变异数 `M>0`，其中 `K` 个被测试杀死，变异分数可以写成：

~~~math
M_{\mathrm{mutation}}=\frac{K}{M}
~~~

当 `M=0` 时变异分数没有定义。它适合暴露测试对边界和局部逻辑的敏感度，但变异器、等价变异和运行成本会影响结果。高变异分数不等于覆盖所有真实缺陷，低分也可能只是测试设计不适合该语言或项目。

### 3.5 公开测试过拟合

过拟合有几种形式：硬编码样例输出、根据输入字符串匹配公开案例、只实现最常见分支、忽略文档中的非显式约束，或让模型根据错误信息反复针对某一测试补丁。隐藏测试和改写测试可以区分真正理解规格与样例投机。

一个有效的反事实测试只改变一个关键条件。例如把数组中的 `0` 加入正数统计，把奇数长度字符串改成偶数长度，把美元单位改成日元，把合法文件名换成包含路径分隔符的输入。测试应记录改变了什么，以及规格预期如何随之改变。

### 3.6 测试结果的因果边界

测试失败是“实现和 oracle 在某个输入上不一致”的证据，不自动说明模型的解释是真实原因；测试通过也不自动说明解释正确。训练 self-debug 时，应把执行结果和人类或程序分析出的根因分开标注，避免模型只学习生成看似合理的错误解释。

## 4. 候选生成和 pass@k

### 4.1 候选池的意义

代码生成通常不是只产生一个程序，而是采样多个候选，再用测试、静态分析、排序器或人工复核选择。这样做利用了模型分布中可能存在的正确程序，但代价是更多 token、执行和选择延迟。

设从同一任务获得 `n` 个候选，其中 `c` 个通过完整目标测试，且 `n>0`、`0\le c\le n`、`1\le k\le n`。经典的无放回估计为：

~~~math
\operatorname{pass@}k=
1-\frac{\binom{n-c}{k}}{\binom{n}{k}}
~~~

`n` 是候选总数，`c` 是被判定正确的候选数。分子表示抽出的 `k` 个候选全部错误的组合数，因此整个式子表示至少抽到一个正确候选的估计概率。`n=0` 或 `k` 不在定义域内时，`pass@k` 没有定义；不能用 0 代替“没有候选”。

### 4.2 公式的适用条件

这个组合估计把已生成的 `n` 个候选视为可抽样池，并假设抽样不放回。它适合离线估计候选池潜力；若候选是高度相关的、生成过程有强烈重复或测试判定不可靠，数值仍然会高估真实多样性。

如果每次独立生成候选且单个候选正确概率近似为 `p`，理想化覆盖概率可以写成：

~~~math
P(\text{至少一个正确})=1-(1-p)^k
~~~

现实中的候选通常不独立。模型可能重复同一个错误、共享训练污染或受同一提示偏置影响，所以增加 `k` 的收益会比独立公式更低。

### 4.3 pass@k 和最终选择准确率

当评估任务数 `N>0`，且每个任务都有一个经过独立检查的最终选择时，候选池里存在正确答案并不代表系统最后选中了它。最终选择准确率是：

~~~math
A_{\mathrm{select}}=
\frac{1}{N}
\sum_{i=1}^{N}
\mathbb{1}[p_{i,\operatorname{select}}\models\operatorname{Spec}_i]
~~~

`N=0` 时 `A_select` 没有定义。`pass@k` 主要观察生成覆盖，`A_select` 同时包含生成器和选择器。如果测试不完整，选择器可能偏爱短代码、格式漂亮的代码或刚好通过公开样例的错误代码。实验应同时报告候选存在率、选择后准确率和选择失败案例。

### 4.4 候选多样性不是越大越好

候选可以在变量名上不同，却共享完全相同的算法错误；也可以在实现路线、数据结构和边界处理上真正不同。简单的文本去重只能删除重复字符串，不能衡量行为或结构多样性。

可以按规范化 AST、算法标签、测试失败集合和输出行为做分组。若四个候选的失败测试完全相同，继续生成更多相似候选的边际价值可能很低；若失败集合互补，执行和修复预算更可能带来收益。

### 4.5 采样参数的工程含义

温度、top-k、top-p、随机种子和停止条件会影响候选重复率、长度和错误类型。较低温度可能提高单个候选稳定性，却降低探索；较高温度可能产生新算法，也可能增加语法错误和不安全 API。

不能只记录“采样了 10 个候选”。应记录模型版本、采样参数、上下文长度、候选 token、重复率、执行调用数和最终选择规则。否则不同实验的 pass@k 不可公平比较。

### 4.6 候选成本

一次候选策略的成本可以粗略拆成：

~~~math
C_{\mathrm{candidate}}=
C_{\mathrm{generation}}
+C_{\mathrm{compile}}
+C_{\mathrm{test}}
+C_{\mathrm{selection}}
~~~

生成成本受候选数和代码长度影响，编译与测试成本受语言和测试规模影响，选择成本受 verifier 或排序器影响。若候选并行执行，延迟接近最慢分支而不是所有分支时间之和；若资源有限，排队时间又会成为主要成本。

## 5. Self-debug：把失败变成修复轨迹

### 5.1 轨迹不是一串文字

一次 self-debug 过程可以写成：

~~~math
\tau_i=(s_0,a_0,o_0,s_1,a_1,o_1,\ldots,s_R)
~~~

`s_r` 是第 `r` 轮的任务状态、代码版本和历史摘要；`a_r` 是生成、修改、运行测试或查询文档等动作；`o_r` 是编译器、测试器、解释器或工具返回的观察；`R` 是实际轮数。

把轨迹结构化很重要。如果只保存最后补丁，就无法知道模型是否读到了失败用例、是否重复修同一行、是否改变了无关接口，也无法训练“从反馈到最小修复”的能力。

### 5.2 状态转移和交错工具调用

代码 agent 的一个状态转移可抽象为：

~~~math
s_{t+1}=F(s_t,a_t,o_t),\qquad
a_t\sim\pi_\theta(\cdot\mid x,s_t)
~~~

`F` 是环境更新函数，`pi_theta` 是模型策略，`x` 是原始需求。状态中可能包含工作区文件、当前测试结果、依赖信息、已知限制和历史补丁。模型的推理并不总是一段连续文本，而是与读文件、运行命令、读取 observation 和修改代码交替进行。

这种交错过程带来新的错误：模型可能在修改文件后仍使用旧测试结果，可能把工具输出中的无关文本当成需求，也可能在多轮摘要中丢掉关键约束。因此系统要为每次工具调用保存输入、输出、退出码和工作区版本。

### 5.3 先分类失败，再生成补丁

一个有效的修复器通常先判断失败类型：

- 解析或编译错误：先修语法、类型和接口。
- 运行时异常：定位触发路径和状态不变量。
- 断言失败：比较实际值、期望值和输入边界。
- 超时：检查算法复杂度、循环终止和数据结构。
- 资源失败：检查内存、文件句柄、并发和缓存。
- 安全失败：删除危险权限或改用受控接口。

分类不一定完全正确，但它可以减少盲目重写。修复数据中应记录分类置信度和后来验证的真实错误类型，便于分析“模型解释错但碰巧修好”的情况。

### 5.4 最小修复和大范围重写

最小补丁容易审查，也容易判断反馈是否被正确利用；大范围重写可能真正改变算法，但会同时引入新的回归。可以把补丁大小写成修改行数、AST 节点数或受影响文件数，并报告它与测试收益的关系。

最小修复不是绝对规则。若初始程序的数据结构选择根本错误，修改一个条件无法修好复杂度问题；若需求理解错误，局部补丁可能掩盖根因。系统需要让模型解释为什么选择局部修复或重构，并用独立测试验证选择。

### 5.5 修复收益

在两轮都执行了同一测试集合 `T`，并且 `S` 的分母非空时，第 `r` 轮的测试收益可以定义为：

~~~math
\Delta S_r=S(p^{(r)},T)-S(p^{(r-1)},T)
~~~

如果 `T` 为空，`S` 和 `\Delta S_r` 都没有定义。如果 `\Delta S_r` 长期为零，可能已经没有有效信息，或者模型没有理解反馈；如果公开测试持续上升而隐藏测试下降，说明修复正在过拟合可见 oracle。修复评价应同时保存公开、隐藏、回归和安全测试的变化。

### 5.6 停止策略

修复循环需要有明确停止条件：全部目标测试通过、达到最大轮数、连续若干轮无新增通过测试、成本超过预算、出现安全拦截或状态发生不可逆变化。无限重试既会浪费成本，也会让模型在同一错误上震荡。

停止并不等于成功。系统应区分“测试通过”“预算耗尽”“安全拒绝”“环境失败”和“模型主动请求澄清”。把所有非正常结束都标为代码错误，会掩盖执行基础设施问题。

## 6. 代码搜索、重排和修复控制

### 6.1 代码修复是搜索问题

可以把当前代码、测试结果和环境状态看成搜索节点，把一次补丁、重写函数或改变依赖看成动作。一个节点的评分可以包含测试通过率、错误类型减少、复杂度、安全和补丁大小，但这些项必须保留独立记录。

搜索的难点是分支数很大、反馈昂贵、候选相关，而且局部测试高分不一定通向完整正确。只保留当前分数最高的候选，可能误删暂时低分但最终能修好的路径；保留过多分支，则会迅速增加执行成本。

### 6.2 软评分和硬约束

软评分适合排序：测试通过率、错误数量、延迟、补丁大小和风格可以形成一个可解释的加权分数。硬约束适合过滤：解析失败、明显危险调用、越权文件访问、资源超限和不满足接口的候选不能因为其他分数高而被保留。

如果把安全违规和功能得分简单相加，功能高分可能抵消安全风险，这是危险的。工程系统应在数据结构上分开记录“可执行”“功能通过”“安全允许”“资源合格”等状态。

### 6.3 测试选择和早期反馈

大型项目不应每次补丁都运行全部测试。可以先运行与修改文件、失败栈和依赖关系相关的快速测试，再运行回归集和完整测试。但测试选择器本身可能漏掉跨模块回归，所以最终候选仍需要完整独立验证。

早期测试的目标是快速提供方向，不是替代最终证据。实验需要记录测试顺序、每类测试触发次数、跳过原因和最终完整测试结果。

### 6.4 状态合并和缓存

不同轨迹可能产生相同的代码状态。可以用规范化文件内容、依赖锁定和环境指纹构造缓存键，避免重复编译和测试。缓存键若遗漏环境版本、测试配置或生成文件，可能把旧结果错误复用到新状态。

一个教学上的环境指纹可以写成：

~~~math
h(E)=\operatorname{hash}(\text{language},\text{compiler},\text{dependencies},\text{OS},\text{limits},\text{test\_config})
~~~

这不是要求使用某一种 hash 算法，而是强调缓存和可复现性必须覆盖真正影响行为的字段。

### 6.5 与搜索论文的关系

Tree-of-Thought 和一般搜索章节讨论的是状态、动作、转移、评分和终止；代码任务的特殊之处在于状态可以被编译器和测试器执行，动作可能改变真实文件和依赖，错误反馈比自然语言自评更具体。AlphaCode 的公开路线说明大规模候选和过滤在竞赛任务中有价值，但它使用的任务、资源和评估环境不能直接套用到仓库修改。

### 6.6 交错推理的工程边界

模型可能需要先阅读仓库，再定位入口，再编辑局部文件，最后运行测试。这种流程不能只用一条长 prompt 描述，因为工具结果会改变下一步状态。应把工作区版本、工具观察、补丁和测试结果放在可重放的轨迹中，并限制模型对真实系统的权限。

## 7. 用执行反馈训练模型

### 7.1 监督微调：学习规格到程序

监督微调样本可以包含需求、接口、参考实现、解释、测试和执行日志。目标输出通常只计算 assistant 的代码和必要解释，不能把题目、隐藏测试答案或内部 metadata 当作模型要复制的目标。

高质量参考程序不等于唯一写法。训练集应包含多种可验证实现，并说明它们满足同一规格的原因。若只保存一种模板，模型会把变量名和固定控制流当成任务本质。

### 7.2 执行反馈蒸馏

可以先让更强的生成器产生候选，再运行测试和静态分析，只保留通过独立检查的样本；也可以保存失败样本，让学生模型学习错误定位和修复。保留策略不能只看最终通过，因为过程错误、危险调用和公开测试过拟合本身也是重要训练信号。

### 7.3 Rejection sampling 的边界

拒绝采样把候选送入 verifier，保留满足条件的结果。它能提升训练集平均质量，却可能丢掉稀有题型、难例和错误纠正样本，导致训练分布过于容易。应保存被拒绝的原因、题型、难度、来源和测试覆盖，定期检查过滤后分布是否失衡。

### 7.4 用执行结果构造 reward

一个教学性的组合奖励可以写成：

~~~math
R(p)=
\lambda_1 S(p,T)
+\lambda_2\mathbb{1}[\operatorname{compile}(p)=1]
-\lambda_3\operatorname{timeout}(p)
-\lambda_4\operatorname{unsafe}(p)
~~~

`S` 是测试通过率，编译项鼓励程序进入可执行状态，超时和安全项是惩罚。`lambda` 只表示权重，不是跨任务通用常数。不同奖励的尺度必须校准，否则一个安全事件可能被大量普通测试分数抵消，或者模型只追求格式和短代码。

### 7.5 Reward hacking

执行反馈也会被利用。模型可能硬编码公开样例、修改测试文件、读取隐藏测试路径、依赖未声明环境变量、无限生成日志，或通过未受控的系统调用获得答案。修复方法不是简单增加 reward，而是隔离测试、隐藏 oracle、只读输入、记录文件变化、限制网络和进程，并用反投机测试检查候选。

### 7.6 过程数据和错误标签

修复样本可以用下面的 schema 表达：

~~~json
{
  "task_id": "count_positive_001",
  "spec": "统计严格大于零的元素数量",
  "signature": "solve(nums)",
  "initial_code": "...",
  "feedback": [
    {
      "kind": "hidden_test_failure",
      "input": [0, 1, -1],
      "expected": 1,
      "actual": 2
    }
  ],
  "root_cause": "boundary_condition",
  "patch": "replace >= with >",
  "regression_tests": ["zero_is_not_positive"],
  "environment": {
    "language": "python",
    "version": "recorded_elsewhere"
  },
  "security_events": []
}
~~~

`root_cause` 不是由模型自动解释就能确定的真值，最好由独立分析、人工复核或反事实测试支持。`actual` 和 `expected` 的字段必须保留类型与单位，否则模型可能只学会文字格式。

### 7.7 数据泄漏和 benchmark 污染

公开代码题、参考实现、测试和论坛解析可能进入预训练语料。近重复题、变量重命名、同一仓库不同提交和模板变体也会造成污染。代码 benchmark 分数上升时，应检查训练数据时间、仓库来源、题目模板、测试文件和近邻 AST，而不是只检查字符串。

### 7.8 论文结论如何使用

HumanEval 适合说明函数级功能评估，AlphaCode 适合说明候选规模化和过滤，CodeRL 适合说明执行反馈与强化学习的结合，Self-Debugging 适合说明反馈驱动修复。它们提供的是不同环节的研究证据，不是一套可以原样复制的生产方案。真实仓库任务还需要导航、依赖、回归、权限和人工审查。

## 8. 执行环境、可复现性和成本

### 8.1 环境契约

每次运行应记录语言版本、编译器、操作系统、依赖锁文件、环境变量白名单、测试命令、随机种子、CPU/内存限制、网络状态和时间限制。环境契约如果不完整，模型收到的反馈可能只是基础设施差异。

### 8.2 依赖与构建

依赖安装本身可能改变结果。版本范围过宽会导致不同机器解析出不同包；构建脚本可能执行网络请求或任意安装钩子；缓存可能让第一次运行和后续运行路径不同。训练和评估应优先使用锁定依赖、预构建镜像和无网络执行，并把镜像或依赖摘要记录到运行日志。

### 8.3 非确定性

随机数、线程调度、GPU 算子、时间、文件顺序和网络响应都可能造成非确定性。重跑一次得到不同结果时，不应马上把变化归因于模型能力。应至少报告重复运行的均值、方差、失败率和随机种子覆盖。

### 8.4 延迟和并发

若修复轨迹有 `R` 轮，每轮依次生成、执行和反馈，端到端延迟近似为：

~~~math
L_{\mathrm{serial}}=\sum_{r=1}^{R}
\left(L_{\mathrm{gen},r}+L_{\mathrm{exec},r}+L_{\mathrm{feedback},r}\right)
~~~

候选并行执行时，单轮执行延迟更接近最大分支时间：

~~~math
L_{\mathrm{parallel}}\approx
L_{\mathrm{gen}}+\max_j L_{\mathrm{exec},j}+L_{\mathrm{select}}
~~~

并行可以降低墙钟时间，却会增加峰值 CPU、内存和并发隔离成本。报告平均延迟时，还应报告 P95、超时率和排队时间。

### 8.5 代码执行成本

一次任务的成本可以按 token、编译、执行和人工复核拆分：

~~~math
C_i=
n_i^{\mathrm{gen}}c_{\mathrm{gen}}
+n_i^{\mathrm{exec}}c_{\mathrm{exec}}
+n_i^{\mathrm{repair}}c_{\mathrm{repair}}
+c_i^{\mathrm{review}}
~~~

`n_gen`、`n_exec` 和 `n_repair` 分别是生成、执行和修复调用次数，`c` 是相应单位成本。若任务最终通过独立目标测试，才把它计入成功数，并且 `N_{\mathrm{correct}}>0`，则单位成功成本为：

~~~math
C_{\mathrm{per\ success}}=
\frac{\sum_i C_i}{N_{\mathrm{correct}}}
~~~

`N_{\mathrm{correct}}=0` 时，单位成功成本没有定义，应报告 `None` 或“没有成功任务”。这个指标不能替代质量，但可以揭示“准确率只提高很少、执行成本却增加数倍”的策略。

### 8.6 可重放日志

完整日志至少应包含原始需求版本、候选源码摘要、补丁序列、每次命令、退出码、标准输出摘要、测试版本、环境指纹、资源峰值和安全事件。日志中可能含有用户代码、密钥或个人数据，需要脱敏、访问控制和保留期限。

## 9. 执行沙箱和安全边界

### 9.1 威胁模型

模型生成的代码应被视为不可信输入，即使它来自“推理模型”。风险包括读写敏感文件、访问网络和云凭证、启动子进程、消耗全部资源、修改测试、污染工作区、窃取其他任务状态和利用依赖漏洞。任务 prompt、仓库文件和工具输出也可能包含提示注入，诱导模型请求超出任务范围的操作。

### 9.2 静态检查不是沙箱

AST 规则、黑名单和正则可以在执行前拦截明显的 `import os`、`open`、`eval` 或子进程调用，但 Python 的动态特性、反射、依赖行为和解释器漏洞使静态检查无法承担完整隔离。静态检查适合做第一层快速筛选，不能替代操作系统级权限和资源限制。

### 9.3 进程和容器隔离

执行器应使用专用身份、只读输入挂载、临时输出目录、最小文件权限和独立工作区。容器可以帮助隔离文件系统、进程和网络，但容器配置错误、宿主机共享、过宽 capability 和挂载 socket 都会破坏隔离。Docker 文档中的安全配置是工程入口，不代表任何默认容器都适合运行不可信代码。

### 9.4 网络、凭证和系统调用

默认关闭外网，显式允许必要的本地依赖；不把云凭证、数据库密码和宿主机 socket 放入执行环境；限制系统调用、子进程、设备访问和内核接口。网络关闭不等于风险归零，因为候选仍可能耗尽 CPU、修改共享文件或读取同一工作区的其他任务结果。

### 9.5 资源和时间限制

必须限制 CPU 时间、墙钟时间、内存、磁盘、进程数、文件大小、输出大小和并发数。超时应终止整棵进程树，而不是只停止父进程。资源限制命中后保存事件类型和使用量，避免把资源异常误标成算法逻辑错误。

### 9.6 测试器本身也是攻击面

测试 oracle、构建脚本、依赖安装器和日志收集器都可能执行代码或接触敏感信息。若测试文件来自不可信仓库，运行测试本身就需要隔离；若模型可以修改测试，必须把测试目录和配置设为只读，并在执行前后比较工作区状态。

### 9.7 安全事件的记录指标

设候选总数 `M>0`，触发静态或运行时安全拦截的候选数为 `U`，且 `0\le U\le M`，教学上的违规率可以定义为：

~~~math
R_{\mathrm{unsafe}}=\frac{U}{M}
~~~

`M=0` 时违规率没有定义。它只能说明当前候选集合触发了多少拦截，不能代表真实攻击概率。还应按事件类型、任务来源、模型版本和执行阶段分组，并统计拦截是否发生在代码执行前。

## 10. 评估代码 reasoning 的完整指标

### 10.1 Greedy 和单候选准确率

单候选准确率是每个任务只取一个候选时的功能正确比例。它容易解释，但无法区分模型没有生成正确候选，还是生成了正确候选却被选择器丢掉。

### 10.2 公开与隐藏测试差距

当两套评估使用同一组且非空的任务时，设 `A_pub` 和 `A_hid` 分别是选择后候选在公开、隐藏测试上的任务级准确率，则：

~~~math
\Delta_{\mathrm{pub-hid}}=A_{\mathrm{pub}}-A_{\mathrm{hid}}
~~~

如果评估集为空，两个准确率及差距都没有定义。差距大通常说明公开测试过拟合、隐藏测试覆盖不足或选择器偏向样例投机。差距为负也可能发生，说明隐藏集合更容易或两套测试分布不同，不能机械把负值解释成优秀泛化。

### 10.3 修复成功率

设 `F` 是初始候选失败、且确实进入修复流程的任务集合，且 `|F|>0`；最终修复通过独立测试的数量为 `K`：

~~~math
A_{\mathrm{repair}}=\frac{K}{|F|}
~~~

当 `|F|=0` 时，修复成功率没有定义，应报告 `None`。分母必须明确是公开失败、隐藏失败还是所有初始失败。只把容易修的语法错误放进分母，会高估模型的反馈利用能力；只把复杂仓库回归放进分母，则是另一种更严格但不同的指标。

### 10.4 首次通过轮数

设评估任务数 `N>0`，第 `i` 个任务在第 `r` 轮第一次通过目标测试，记为 `r_i`：

~~~math
\bar R_{\mathrm{first}}=\frac{1}{N}\sum_{i=1}^{N}r_i
~~~

当 `N=0` 时该平均值没有定义。对从未通过的任务，必须规定如何处理，例如记录为预算上限加一，或单独报告删失比例。不能只对成功任务求平均，否则失败任务会被悄悄排除。

### 10.5 资源和安全切片

至少按语言、题型、代码长度、依赖数量、测试数量、难度、是否需要仓库导航、是否允许网络、失败类型和资源级别切片。平均 pass@k 上升但安全拦截遗漏增加，或者简单函数题提升而真实仓库修复下降，都应作为回归报告。

### 10.6 人工和程序评价的边界

程序测试适合判断可执行行为；人工评价适合判断可读性、解释是否支持修复、架构取舍和业务约束。人工 judge 也可能受代码长度、格式和自信语气影响，应该使用明确 rubric、盲评、多人一致性和独立功能结果。

### 10.7 置信区间和重复实验

准确率是样本比例，样本量较小时单个百分点没有稳定意义。可以对任务按样本重采样得到 bootstrap 分布，并报告百分位区间：

~~~math
\operatorname{CI}_{1-\alpha}=
\left[q_{\alpha/2}(\hat A^{\ast}),
q_{1-\alpha/2}(\hat A^{\ast})\right]
~~~

`A*` 是重复重采样得到的指标，`q` 是分位数。代码任务常有同一仓库或同一模板的相关样本，最好按任务族或仓库分组重采样，避免把相关题目当成独立样本。

## 11. 常见失败模式

### 11.1 公开样例硬编码

候选程序只识别公开输入，或直接返回公开答案。修复方法包括隐藏改写样例、输入生成、工作区只读、测试文件隔离和行为相似性检查。

### 11.2 只修当前错误

模型看到一个失败输入就增加一个特判，当前测试通过，其他输入和代码可维护性变差。需要回归测试、反事实样例和补丁复杂度记录。

### 11.3 长解释掩盖错误

模型输出很长的“调试分析”，但补丁没有改变失败行为。解释文本必须和执行结果分开评价，不能把长度当作反馈利用能力。

### 11.4 反复震荡

模型在两个补丁之间来回切换，通常是历史状态摘要丢失、测试反馈不完整或选择器只看局部得分。轨迹需要保存版本、差异和已经尝试过的补丁。

### 11.5 测试器不稳定

时间、随机性、网络和共享状态造成同一候选结果不一致。应先修执行基础设施，不能把不稳定反馈直接用于训练。

### 11.6 环境投机

候选依赖本地包、环境变量、缓存文件或未记录的网络响应。用锁定依赖、无网络、干净工作区和环境重放检查环境投机。

### 11.7 选择器偏差

选择器偏好短代码、特定格式或公开测试得分，可能放弃更通用的候选。应报告候选池潜力与最终选择差距，并增加 hard negative。

### 11.8 安全拦截不足

静态黑名单通过，但运行时仍访问文件、网络或资源。把静态扫描当作唯一防线是架构错误，必须使用多层隔离和独立红队测试。

## 12. 综合案例：合同金额计算器的执行闭环

### 12.1 从业务规则到程序规格

合同金额计算器接收基础金额、折扣率、税率、币种和舍入规则，返回折后金额、税额、含税总额以及审计字段。需求不能只写“算出最终金额”，还要明确：折扣和税率的单位，税前还是税后计税，金额在每一步还是最后一步舍入，负数和空值如何处理，币种是否允许混用。

### 12.2 示例实现与测试设计

公开测试可以覆盖普通金额和零折扣；隐藏测试应覆盖小数舍入、税率为零、最大允许金额、非法币种、负数输入和折扣达到上限。若把所有这些边界都公开给模型，公开测试的反馈会变成规格泄漏；若一个都不提供，模型又很难定位基本接口错误。测试设计需要在可调试性和独立评估之间平衡。

### 12.3 反馈与修复

如果模型把 `0.05` 当成 `5`，测试反馈应同时展示输入单位、实际结果、期望结果和相关字段；如果舍入位置错误，单个金额样例可能不足，需要加入能区分“中间舍入”和“最后舍入”的反事实。修复成功后，必须重新运行金额、币种、权限和 schema 回归测试。

### 12.4 代码正确不等于可以付款

即使金额函数通过独立测试，真实付款仍需要合同版本、证据页码、审批状态、权限和人工确认。执行反馈只能证明某段程序在某个环境中的行为，不能授权模型直接调用付款接口。高风险动作应使用只读预览、结构化审批和可回滚的工具边界。

## 13. 最小可运行实验：代码推理与执行反馈审计

下面的 demo 使用四个 toy 任务，模拟候选生成、公开测试筛选、隐藏测试评估、公开失败后的修复和静态安全拦截。它只执行文档中硬编码的候选，不接受外部输入；静态 AST 检查只是教学用第一层过滤，不能当作生产沙箱。

~~~python
import ast
import math


TASKS = [
    {
        "id": "count_positive",
        "public": [(([1, -2, 3],), 2), (([-1, 5],), 1)],
        "hidden": [(([0, 1, -1],), 1), (([0, 0],), 0)],
        "candidates": [
            "def solve(nums):\n    return sum(1 for x in nums if x >= 0)",
            "def solve(nums):\n    return sum(1 for x in nums if x > 0)",
            "import os\ndef solve(nums):\n    return len(nums)",
        ],
    },
    {
        "id": "left_middle",
        "public": [(("abc",), "b"), (("hello",), "l")],
        "hidden": [(("abcd",), "b"), (("xy",), "x")],
        "candidates": [
            "def solve(s):\n    return s[len(s) // 2]",
            "def solve(s):\n    return s[(len(s) - 1) // 2]",
        ],
    },
    {
        "id": "clamp_values",
        "public": [(([-2, 0, 3], 0, 5), [0, 0, 3]), (((1, 2), 0, 5), [1, 2])],
        "hidden": [(([9, -1, 4], 0, 5), [5, 0, 4])],
        "candidates": [
            "def solve(nums, lo, hi):\n    return [min(max(x, lo), hi) for x in nums]",
            "def solve(nums, lo, hi):\n    return [max(x, lo) for x in nums]",
        ],
    },
    {
        "id": "parse_ints",
        "public": [(("1 2 -3",), [1, 2, -3])],
        "hidden": [(("4, 5 -6",), [4, 5, -6])],
        "candidates": [
            "def solve(text):\n    return [int(x) for x in text.split(',')]",
            "def solve(text):\n    return [int(x) for x in text.replace(',', ' ').split()]",
            "def solve(text):\n    while True:\n        pass",
        ],
    },
]

ALLOWED_BUILTINS = {
    "sum": sum,
    "len": len,
    "int": int,
    "range": range,
    "list": list,
    "set": set,
    "sorted": sorted,
    "enumerate": enumerate,
    "min": min,
    "max": max,
}
BANNED_CALLS = {"open", "eval", "exec", "compile", "input", "__import__"}


def require(condition, message):
    if not condition:
        raise ValueError(message)


def validate_tests(tests):
    require(isinstance(tests, list) and tests, "tests must be a non-empty list")
    for test in tests:
        require(isinstance(test, tuple) and len(test) == 2, "each test must be (args, expected)")
        args, _ = test
        require(isinstance(args, tuple), "test args must be a tuple")


def validate_tasks(tasks):
    require(isinstance(tasks, list) and tasks, "tasks must be a non-empty list")
    task_ids = []
    for task in tasks:
        require(isinstance(task, dict), "each task must be a dictionary")
        require(isinstance(task.get("id"), str) and task["id"], "task id must be non-empty")
        require(task["id"] not in task_ids, "task ids must be unique")
        task_ids.append(task["id"])
        validate_tests(task.get("public"))
        validate_tests(task.get("hidden"))
        candidates = task.get("candidates")
        require(isinstance(candidates, list) and candidates, "candidates must be a non-empty list")
        require(all(isinstance(source, str) and source for source in candidates), "candidate source must be non-empty text")


validate_tasks(TASKS)


def inspect_source(source):
    try:
        tree = ast.parse(source)
    except SyntaxError as exc:
        return False, f"syntax:{exc.__class__.__name__}"
    for node in ast.walk(tree):
        if isinstance(node, (ast.Import, ast.ImportFrom)):
            return False, "blocked_import"
        if isinstance(node, ast.While):
            return False, "blocked_loop"
        if isinstance(node, ast.Attribute) and node.attr.startswith("__"):
            return False, "blocked_dunder"
        if isinstance(node, ast.Name) and node.id.startswith("__"):
            return False, "blocked_dunder"
        if isinstance(node, ast.Call) and isinstance(node.func, ast.Name):
            if node.func.id in BANNED_CALLS:
                return False, f"blocked_call:{node.func.id}"
    return True, "ok"


def load_function(source):
    allowed, reason = inspect_source(source)
    if not allowed:
        return None, reason
    environment = {"__builtins__": ALLOWED_BUILTINS}
    local_namespace = {}
    exec(compile(source, "<candidate>", "exec"), environment, local_namespace)
    function = local_namespace.get("solve") or environment.get("solve")
    if not callable(function):
        return None, "missing_solve"
    return function, "ok"


def run_tests(function, tests):
    validate_tests(tests)
    passed = 0
    failures = []
    for args, expected in tests:
        try:
            actual = function(*args)
            ok = actual == expected
        except Exception as exc:
            actual = f"error:{exc.__class__.__name__}"
            ok = False
        passed += int(ok)
        if not ok:
            failures.append({"args": args, "expected": expected, "actual": actual})
    return passed, len(tests), failures


def pass_at_k(candidate_count, correct_count, k):
    require(type(candidate_count) is int and candidate_count >= 0, "candidate_count must be a non-negative integer")
    require(type(correct_count) is int and 0 <= correct_count <= candidate_count, "correct_count must be in [0, candidate_count]")
    if candidate_count == 0:
        return None
    require(type(k) is int and 1 <= k <= candidate_count, "k must be in [1, candidate_count]")
    if correct_count == 0:
        return 0.0
    if candidate_count - correct_count < k:
        return 1.0
    return round(
        1 - math.comb(candidate_count - correct_count, k)
        / math.comb(candidate_count, k),
        3,
    )


reports_by_task = {}
blocked = []
selected = []
public_fail_repairs = []
pass1_values = []
pass2_values = []
attempts_to_public = []
all_reports = []

for task in TASKS:
    task_reports = []
    for index, source in enumerate(task["candidates"]):
        function, status = load_function(source)
        report_id = f"{task['id']}:c{index}"
        if function is None:
            report = {
                "id": report_id,
                "status": status,
                "public_pass": 0,
                "public_total": len(task["public"]),
                "hidden_pass": 0,
                "hidden_total": len(task["hidden"]),
            }
            blocked.append(report_id)
        else:
            public_pass, public_total, public_errors = run_tests(
                function, task["public"]
            )
            hidden_pass, hidden_total, hidden_errors = run_tests(
                function, task["hidden"]
            )
            report = {
                "id": report_id,
                "status": "ok",
                "public_pass": public_pass,
                "public_total": public_total,
                "hidden_pass": hidden_pass,
                "hidden_total": hidden_total,
                "first_public_error": public_errors[:1],
                "first_hidden_error": hidden_errors[:1],
            }
        task_reports.append(report)
        all_reports.append(report)

    reports_by_task[task["id"]] = task_reports
    executable = [report for report in task_reports if report["status"] == "ok"]
    hidden_correct = sum(
        report["hidden_pass"] == report["hidden_total"]
        for report in executable
    )
    require(executable, "a task must have at least one executable candidate")
    pass1_values.append(pass_at_k(len(executable), hidden_correct, 1))
    pass2_values.append(pass_at_k(len(executable), hidden_correct, min(2, len(executable))))

    best = max(
        executable,
        key=lambda report: (
            report["public_pass"] / report["public_total"],
            -int(report["id"].split(":c")[-1]),
        ),
    )
    selected.append(best)

    first_success = None
    for position, report in enumerate(task_reports, start=1):
        if report["status"] == "ok" and report["public_pass"] == report["public_total"]:
            first_success = position
            break
    attempts_to_public.append(first_success or len(task_reports) + 1)

    greedy = task_reports[0]
    if greedy["status"] == "ok" and greedy["public_pass"] < greedy["public_total"]:
        public_fail_repairs.append(
            {
                "task": task["id"],
                "repaired": best["hidden_pass"] == best["hidden_total"],
                "chosen": best["id"],
            }
        )

greedy_accuracy = sum(
    reports_by_task[task["id"]][0]["status"] == "ok"
    and reports_by_task[task["id"]][0]["hidden_pass"]
    == reports_by_task[task["id"]][0]["hidden_total"]
    for task in TASKS
) / len(TASKS)
selected_public_accuracy = sum(
    report["public_pass"] == report["public_total"]
    for report in selected
) / len(selected)
selected_hidden_accuracy = sum(
    report["hidden_pass"] == report["hidden_total"]
    for report in selected
) / len(selected)
repair_success_rate = (
    sum(item["repaired"] for item in public_fail_repairs)
    / len(public_fail_repairs)
    if public_fail_repairs
    else None
)

summary = {
    "greedy_accuracy": round(greedy_accuracy, 3),
    "public_rerank_accuracy": round(selected_hidden_accuracy, 3),
    "selected_public_pass_rate": round(selected_public_accuracy, 3),
    "public_hidden_gap": round(
        selected_public_accuracy - selected_hidden_accuracy, 3
    ),
    "pass_at_1_est": round(sum(pass1_values) / len(pass1_values), 3),
    "pass_at_2_est": round(sum(pass2_values) / len(pass2_values), 3),
    "repair_success_rate": round(repair_success_rate, 3),
    "avg_attempts_to_public_success": round(
        sum(attempts_to_public) / len(attempts_to_public), 3
    ),
    "blocked_candidate_rate": round(len(blocked) / len(all_reports), 3),
}
hidden_failures_after_public = [
    report["id"].split(":c")[0]
    for report in selected
    if report["public_pass"] == report["public_total"]
    and report["hidden_pass"] < report["hidden_total"]
]
review = {
    "public_signal_ok": summary["selected_public_pass_rate"] >= 0.9,
    "hidden_generalization_ok": summary["public_rerank_accuracy"] >= 0.75,
    "gap_ok": summary["public_hidden_gap"] <= 0.25,
    "repair_ok": (
        summary["repair_success_rate"] is not None
        and summary["repair_success_rate"] >= 0.8
    ),
    "sandbox_blocks_unsafe": len(blocked) == 2,
}

print(f"summary={summary}")
print(f"selected={[report['id'] for report in selected]}")
print(f"hidden_failures_after_public={hidden_failures_after_public}")
print(f"public_fail_repairs={public_fail_repairs}")
print(f"blocked={blocked}")
print(f"review={review}")
print(f"all_review_checks_pass={all(review.values())}")
~~~

selected=['count_positive:c0', 'left_middle:c0', 'clamp_values:c0', 'parse_ints:c1']
hidden_failures_after_public=['count_positive', 'left_middle']
public_fail_repairs=[{'task': 'parse_ints', 'repaired': True, 'chosen': 'parse_ints:c1'}]
blocked=['count_positive:c2', 'parse_ints:c2']
review={'public_signal_ok': True, 'hidden_generalization_ok': False, 'gap_ok': False, 'repair_ok': True, 'sandbox_blocks_unsafe': True}
all_review_checks_pass=False
~~~

### 13.1 先检查代码和执行结果

这个 demo 的四个任务分别展示四种情况：`count_positive` 和 `left_middle` 暴露了公开测试不足，`clamp_values` 展示公开和隐藏测试都通过的候选，`parse_ints` 展示公开失败后修复候选被选中，两个危险候选则在执行前被静态规则拦截。

`pass_at_2_est=1.0` 只说明每个任务的可执行候选池中都存在一个通过隐藏测试的程序；公开测试重排后隐藏准确率只有 `0.5`，说明选择器不能从公开信号中可靠识别正确候选。`repair_success_rate=1.0` 只来自一个进入公开失败修复集合的任务，分母很小，不能外推到一般代码修复。

### 13.2 为什么故意保留失败结果

如果把所有风险样本过滤掉，demo 只会输出漂亮的准确率，读者看不到测试覆盖和选择器的盲点。这里保留 `hidden_failures_after_public`、`blocked` 和 `review`，是为了让审计结果能指导下一步：增加零值和偶数长度测试，改进候选选择器，扩大修复样本，并验证静态规则之外的运行时隔离。

### 13.3 为什么这个 demo 不是生产沙箱

示例使用受限 builtins 和 AST 规则执行硬编码源码，没有真实的进程超时、内存限制、系统调用隔离、容器边界和网络控制。任何现实系统都不能把这段 `exec` 代码直接用于不可信输入；它只演示指标和数据流，安全执行必须由独立的操作系统级服务负责。

## 14. 把执行结果转成工程决策

### 14.1 生成器问题还是选择器问题

若 pass@k 很低，候选池中没有正确程序，应该改进需求理解、训练数据、采样策略或模型能力；若 pass@k 很高而最终选择准确率低，应该改进测试、verifier、排序器和隐藏边界覆盖；若选择后公开高、隐藏低，应该优先修测试设计和数据污染，而不是盲目增加采样数。

### 14.2 修复收益还是重复试错

报告每一轮新增通过测试、回归失败、补丁大小和错误类型。如果模型只是把同一测试从失败改成通过，却没有提高独立测试，不能把这称为泛化修复。若连续多轮没有新增证据，应返回澄清请求、切换算法路线或终止，而不是无限延长轨迹。

### 14.3 质量和成本一起看

候选数、测试数和修复轮数增加通常会提高机会，但也会增加 token、CPU、内存和延迟。对每种策略都应记录准确率、pass@k、公开隐藏差距、P95、超时率、安全事件和单位成功成本。只有在目标任务、风险等级和预算相同的条件下，策略比较才有意义。

### 14.4 高风险动作单独处理

代码生成、测试运行、文件写入、数据库修改和付款调用不是同一风险级别。即使代码任务本身通过测试，涉及外部状态的动作仍应使用只读预览、显式参数、最小权限、人工确认和回滚机制。模型的执行反馈能力不能替代业务授权。

## 15. 小练习

### 练习一：设计公开和隐藏测试

为 `count_positive(nums)` 设计至少四个公开测试和四个隐藏测试。说明哪些边界故意只放在隐藏集合，以及如何避免隐藏测试被修复循环泄漏。

### 练习二：解释 pass@k

有 `n=20` 个候选，其中 `c=3` 个通过独立测试。计算 `pass@1` 和 `pass@5`，再说明为什么最终选择准确率可能低于这两个数暗示的候选池潜力。

### 练习三：构造 self-debug schema

为一个排序函数保存初始代码、失败输入、期望输出、实际输出、根因、补丁、回归测试、环境指纹和资源使用。说明哪些字段不能由模型自报后直接当作真值。

### 练习四：找出测试过拟合

设计一个能通过公开样例但会在隐藏样例失败的程序，要求它不是简单硬编码字符串。解释它利用了哪一个未覆盖的边界条件。

### 练习五：沙箱分层

分别列出 AST 检查、进程隔离、容器权限、网络控制和资源限制能解决与不能解决的问题。说明为什么单独使用黑名单不足以执行不可信代码。

### 练习六：运行 demo

把 `count_positive` 的一个公开测试改成包含 `0`，重新运行 demo，比较公开隐藏差距、选择结果和隐藏失败列表的变化。解释为什么测试变强后，选择器变好不等于生成器本身变好。

## 16. 本章总结

代码 reasoning 的核心不是输出更长的程序，而是把规格、程序、环境、执行反馈和修复动作连接成可验证的闭环。解析和编译反馈帮助修复语言层错误，运行时反馈暴露实际路径问题，单元测试和性质检查提供行为信号，隐藏测试检验泛化，修复轨迹则记录模型是否真正利用了反馈。

候选生成、pass@k、测试重排和搜索分别回答“正确程序是否出现”“选择器是否选中”“测试是否覆盖”和“额外计算是否值得”。它们必须分开报告。执行反馈可以用于 SFT、拒绝采样、过程监督和强化学习，但也会带来公开测试过拟合、reward hacking、环境投机和数据污染。

代码执行的安全边界同样属于模型能力的一部分。静态 AST 检查只能拦截明显模式，不能替代进程、文件、网络、系统调用和资源隔离。任何会改变真实外部状态的工具调用，都需要独立权限、审计和回滚。

最终要问的不是“模型能否生成一段能跑的代码”，而是：它是否理解规格，是否在独立测试上稳定，是否能从反馈定位根因，是否在受控环境中可重放，是否在合理成本内完成，并且不会因为追求测试分数而突破安全边界。

下一章将进入 reasoning 评估，讨论如何把候选生成、过程质量、verifier、污染、统计不确定性和安全指标放在同一套评估设计中。
