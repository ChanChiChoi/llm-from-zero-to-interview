# 第 20 章 GLM-5.3：长任务环境、验证器与后训练边界

> 资料边界：本章依据 [Z.ai GLM-5.3 官方文档](https://docs.z.ai/guides/llm/glm-5.3)、[迁移指南](https://docs.z.ai/guides/overview/migrate-to-glm-new)、[Hugging Face 模型仓库与固定配置](https://huggingface.co/zai-org/GLM-5.3/blob/ba32f8c19c8738e2c57c71798c601d477a7bf844/config.json)、[slime](https://github.com/THUDM/slime)、[IndexCache](https://arxiv.org/abs/2603.12201) 与 [SAO](https://arxiv.org/abs/2607.07508) 等公开资料，核验日期为 2026-11-13。官方文档支持接口和发布方披露的长任务训练流程；固定模型配置支持检查公开架构字段，但不等于完整训练配方或托管 API 的实现。SAO 与 IndexCache 是关联技术证据，不能改写成 GLM-5.3 独有实现。

## 20.1 本章要解决的问题

长任务 Agent 不是把一个问题问得更长。以“修复线上训练任务吞吐下降”为例，模型需要先读日志，定位可能的瓶颈，修改实现，运行实验，比较新旧指标，再决定交付还是继续排查。每一步的真实结果都会改变下一步应该做什么。

这类能力不能只用一段漂亮的最终回答衡量。训练和评测都必须回答四个更具体的问题：

1. Agent 在什么环境里读、改、跑和测？
2. 什么结果算真正完成，谁来检查？
3. 验证器会不会把“什么也没做”或“绕过检查”误判为成功？
4. 模型、工具、上下文与预算怎样共同构成长任务系统？

GLM-5.3 官方文档提供了一个有价值的公开案例：它称 GLM-5.3 沿用 GLM-5.2 的基础模型，能力变化来自后训练；训练环境扩展到生产工程和研究工作流，并描述了环境生成、judge agent 与验证器检查。即使不掌握内部配方，我们仍可以从中学习怎样把长任务训练和评测设计得可审计。

## 20.2 先把公开事实和教学推导分开

截至 2026-11-13，[Z.ai 文档](https://docs.z.ai/guides/llm/glm-5.3)将 GLM-5.3 描述为文本输入模型，标称 1M context window 与 128K maximum output；推理始终开启，`thinking.type` 只支持 `enabled`；`reasoning_effort` 提供 `low`、`high`、`max`，默认 `max`。文档还称 GLM-5.3 复用 GLM-5.2 基础模型，改进来自后训练。[Hugging Face 上的公开模型仓库](https://huggingface.co/zai-org/GLM-5.3) 已提供模型文件和配置；固定 revision `ba32f8c19c8738e2c57c71798c601d477a7bf844` 可用于核对模型类型及配置字段。公开权重与配置扩大了可检查范围，却仍不揭示完整训练配方、托管服务内部或该型号的 compaction 细节。

官方对训练环境的描述更重要：研究 Agent 收集工作模式并生成可运行环境；judge agent 尝试求解以检查任务是否可解；部分任务奖励也由管线生成；生成验证器时不访问参考解，并以求解轨迹发现奖励捷径。文档提到 oracle、no-op 与 unsolved-state 检查，并承认环境和验证仍需要显著人工参与。

下面三类话不能混在一起：

| 类型 | 可以说什么 | 不能说什么 |
| --- | --- | --- |
| 官方接口事实 | 1M context、128K output、指定 effort 档位 | 1M 一定能可靠完成任意长任务 |
| 官方流程描述 | 有环境生成、judge 尝试求解、验证器检查 | 生成管线已经无人工、验证器绝对正确 |
| 本章教学抽象 | 用状态、动作、反馈和门禁解释任务环境 | 该抽象就是 GLM-5.3 的内部训练算法 |

文档使用了 “SAO with compaction” 的说法，但本轮可读一手资料没有定义 SAO 全称、优化目标或压缩算法。它只能被记录为待核验的名称。把它强行解释成某种 advantage、summary 或 attention 算法，会把猜测伪装成知识。

## 20.3 为什么训练环境比一条指令更接近真实能力

一个静态问答样本通常形如 `(prompt, answer)`。可执行长任务则要跟踪环境如何随行动改变。令 \(t\) 为非负整数步骤，\(s_t\) 为当前环境状态（如代码版本、配置和测试结果），\(a_t\) 为 Agent 动作，\(e_t\) 为工具返回或外部事件，\(T\) 为环境状态转移函数：

```math
s_{t+1}=T(s_t,a_t,e_t),
```

状态还可以包含实验指标、剩余预算和权限；因此，环境状态不是一整段聊天历史，而是可随动作和外部事件更新的对象。

例如吞吐优化任务的初始状态可以是：仓库中有一个低效数据加载器，基线吞吐为 80 samples/s，隐藏测试要求修改后至少达到 100 samples/s 且所有正确性测试通过。Agent 可读取文件、编辑实现、运行测试和运行基准。它若只把阈值改成 100，却没有改善代码，应当失败；它若获得 120 samples/s 但弄坏了样本顺序，也应当失败。

这解释了为什么“任务很长”不是长任务训练的充分条件。真正的长程困难来自：

- **依赖**：修改能否通过测试，依赖此前读取到的实际代码；
- **反馈**：运行错误会排除一部分假设，并引出新的排查路径；
- **状态**：当前 diff、已失败的实验与未满足的约束必须持续保留；
- **可验证性**：完成必须由任务契约判断，而不是模型自称完成；
- **恢复**：超时、工具失败或上下文折叠后，系统要知道可以从哪里继续。

## 20.4 任务契约：先定义什么叫完成

一个可训练任务至少要有目标、允许动作、初始状态、结束条件和观察规则。可以用以下教学契约表示：

```text
goal: 修复吞吐回归，同时保持输出顺序
initial_state: repo@r1, baseline=80 samples/s
allowed_actions: read, edit, run_unit_test, run_benchmark
success: unit_test_pass and throughput >= 100 and output_order_preserved
terminal_failures: timeout, forbidden_write, invalid_artifact
```

目标不是只写给模型看的自然语言愿望。`success` 必须被环境外部的检查器解释。若任务涉及文件、数据库或线上资源，契约还应写明沙箱、权限范围、数据副本、超时、资源上限、清理逻辑与 artifact 保存位置。

对初学者而言，可以把 verifier 想成验收测试，而不是老师的主观印象。它并不需要理解所有过程，但必须可靠检查任务的关键约束。对专家而言，任务契约也定义了奖励函数的支持集：验证器没有观察到的行为，奖励就无法直接约束。

## 20.5 Oracle、no-op 与未完成状态分别在防什么

官方文档列出的三类检查很适合拆开理解。

### Oracle check：任务本身能否被完成

oracle check 的目标是确认存在一个能够通过验收的解或参考路径。没有它，环境可能因依赖缺失、阈值错误、隐藏配置冲突而根本无解。训练数据若混入大量无解任务，模型会被惩罚于自己无法控制的失败。

但 oracle 存在不证明 verifier 完备。一个参考实现能通过，只说明至少有一条路径成功；它不能证明所有通过 verifier 的路径都真的满足业务目标。

### No-op check：什么也不做不能得分

no-op check 在初始状态就运行验收。若初始仓库已经满足所有成功条件，Agent 可以不理解任务、也不做任何工作便获得奖励。这会把“静止”变成一条高分捷径。

no-op 失败是必要条件，却不足以排除所有捷径。例如 Agent 可能删除测试、修改评分脚本、把基准数据替换为空数据，仍然让表面指标变好。因此验收器及其依赖应放在受保护路径，并对动作范围设置权限。

### Unsolved-state check：半成品不能提前宣布完成

未完成状态检查会构造或保留一个明显未达标的中间状态，确保 verifier 不会把“命令退出 0”“生成了补丁”或“写了报告”误当作任务成功。它能捕获过于宽松的结束条件。

三者组合的逻辑是：有可完成解、起点不应白得分、半成品不能误过关。它们都只是必要检查。一个可靠系统还需要对抗样本、独立实现、隐藏测试、人工抽检、版本绑定与失败分类。

## 20.6 一个零依赖的验证器门禁 demo

下面的例子不调用模型、不修改真实文件。它用 toy artifact 演示三类检查和一个容易忽略的权限条件。输入是任务开始前、已完成 artifact 和半成品 artifact；输出说明每个状态为何通过或失败。目标是 100 samples/s：初始的 80 比目标少 20；完成态的 120 比目标多 20，相对基线提升 `(120-80)/80=0.5`，即 50%。这些数字只说明构造任务的验收算术；正确性测试、顺序和 verifier 完整性仍是独立门槛。

```python
from dataclasses import dataclass
import math


@dataclass(frozen=True)
class Artifact:
    throughput: float
    unit_tests_pass: bool
    order_preserved: bool
    modified_protected_test: bool = False


def verify(artifact, target_throughput=100.0):
    if not isinstance(artifact, Artifact):
        raise TypeError("artifact must be an Artifact")
    finite_real = lambda value: type(value) is int or (
        type(value) is float and math.isfinite(value)
    )
    if not finite_real(target_throughput) or target_throughput <= 0:
        raise ValueError("target_throughput must be finite and positive")
    if not finite_real(artifact.throughput) or artifact.throughput < 0:
        raise ValueError("throughput must be finite and non-negative")
    for field in (artifact.unit_tests_pass, artifact.order_preserved,
                  artifact.modified_protected_test):
        if type(field) is not bool:
            raise ValueError("artifact flags must be booleans")
    if artifact.modified_protected_test:
        return "invalid: protected verifier changed"
    if not artifact.unit_tests_pass:
        return "invalid: unit tests failed"
    if not artifact.order_preserved:
        return "invalid: output order changed"
    if artifact.throughput < target_throughput:
        return "incomplete: throughput target not met"
    return "success"


initial = Artifact(throughput=80.0, unit_tests_pass=True, order_preserved=True)
completed = Artifact(throughput=120.0, unit_tests_pass=True, order_preserved=True)
shortcut = Artifact(throughput=130.0, unit_tests_pass=True,
                    order_preserved=True, modified_protected_test=True)

assert verify(initial) == "incomplete: throughput target not met"  # no-op check
assert verify(completed) == "success"                              # completed state
assert verify(shortcut) == "invalid: protected verifier changed"   # reward shortcut
assert verify(Artifact(120.0, False, True)) == "invalid: unit tests failed"
assert verify(Artifact(120.0, True, False)) == "invalid: output order changed"

for invalid_throughput in (float("nan"), float("inf"), -1.0, True, "120"):
    invalid = Artifact(invalid_throughput, True, True)
    try:
        verify(invalid)
    except ValueError:
        pass
    else:
        raise AssertionError("invalid throughput was accepted")

for invalid_target in (float("nan"), float("inf"), 0, True, "100"):
    try:
        verify(initial, invalid_target)
    except ValueError:
        pass
    else:
        raise AssertionError("invalid target was accepted")

try:
    verify(Artifact(120.0, 1, True))
except ValueError:
    pass
else:
    raise AssertionError("non-boolean test status was accepted")

print(verify(initial), verify(completed), verify(shortcut), sep=" | ")
```

代码状态：已验证（2026-11-13，CPython 3.12.9，Python 标准库）。

运行方法：使用 CPython 3 和标准库，将代码保存为 `verifier_demo.py` 后运行 `python3 verifier_demo.py`。

输出是：

```text
incomplete: throughput target not met | success | invalid: protected verifier changed
```

这个 demo 不是 GLM-5.3 的训练代码，也没有证明真实验证器只检查四个字段。它表达的是可迁移的工程原则：成功条件、完整性条件和 verifier 完整性必须分开；否则奖励会向容易伪造的代理指标漂移。

## 20.7 验证器为什么会被“奖励捷径”欺骗

令 \(S\in\{0,1\}\) 表示任务契约定义的真实成功事件，\(r\in\{0,1\}\) 表示验证器奖励；在评估样本中成功和失败两类都存在时，理想一致关系是：

```math
r=1 \Longleftrightarrow S=1.
```

现实中通常只能近似：

```math
P(r=1\mid S=0)>0
\quad\text{或}\quad
P(r=0\mid S=1)>0.
```

前者是假阳性：任务其实失败了，却得到奖励；后者是假阴性：正确工作被错误拒绝。生成模型会在训练中寻找让 `r=1` 的轨迹，不会自动理解人类真正想要优化的 `S`。因此，验证器的漏洞会被放大成策略偏好。

常见捷径包括：只匹配输出格式、只测公开样例、在错误目录写入 artifact、修改测试自身、利用环境残留、跳过慢测试、把异常吞掉后返回成功。防御要配合任务类型，而不是只加一条“不得作弊”的 prompt：

| 风险 | 更接近问题根源的防御 |
| --- | --- |
| 只匹配格式 | 用程序语义或独立结果校验 |
| 只过公开样例 | 加隐藏切片和反事实输入 |
| 改写验收脚本 | 保护 verifier 路径，限制写权限 |
| 使用残留状态 | 每次 reset 环境，记录版本与 hash |
| 无意义高指标 | 同时检查正确性、资源消耗和业务约束 |
| 超时结果未知 | 记录状态，查询后再重试，不能直接计成功 |

这里的重点不是把 Agent 当作攻击者，而是承认任何被优化的分数都可能与目标脱钩。长任务后训练把这个问题从“答案格式”扩大到了代码、工具、文件、实验和环境状态。

## 20.8 上下文压缩：能省 token，不等于保存了任务状态

当任务持续很久时，原始 trace、日志和工具输出会超过上下文预算。压缩需要保留的不是“看起来最像摘要的句子”，而是后续决策所依赖的事实：任务契约、当前版本、已修改文件、失败测试、尚未验证的假设、权限、剩余预算和可恢复 artifact。

令 \(h_{\leq t}\) 表示截至步骤 \(t\) 的历史轨迹，\(K_t\) 表示后续决策必须保留的状态键，\(G\) 表示压缩映射，\(c_t\) 表示供下一步使用的压缩表示：

```math
c_t=G(h_{\leq t},K_t),
```

好压缩不是 \(c_t\) 越短越好，而是在 token 预算内让下一步动作仍接近使用完整历史时的选择。若 diff 丢失、测试版本错位或权限被摘要成模糊文字，后续 Agent 可能在错误世界状态上继续工作。

GLM-5.3 文档说它继承 “SAO with compaction”，但没有公开这个 `G` 的定义。因此本章只能解释一般性压缩评测：比较完整 history 与 compressed history 下的任务完成率、关键状态召回、错误恢复率、工具重复率、成本与延迟；不能将上面的数学教学符号归为 GLM 的实现。

## 20.9 协议迁移：模型名相同，请求仍可能失败

GLM-5.3 文档说明 `thinking.type` 只支持 `enabled`。一个旧客户端若仍发送 `thinking.type: disabled`，不能假定服务器会静默忽略；官方文档警告迁移前应调整，否则请求会失败。它反映了更一般的迁移原则：模型迁移是能力契约迁移，不是替换字符串。

迁移测试至少覆盖：

1. 请求 schema：模型 ID、thinking 字段、reasoning effort、工具字段和结构化输出字段。
2. 响应 schema：内容、reasoning 相关字段、工具 call ID、usage、错误格式与流式事件。
3. 行为指标：成功率、TTFT、TPOT、输出长度、工具轮数、重试率与单位成功成本。
4. 安全与运行时：权限是否保持收缩、unknown 工具状态是否可恢复、审计字段是否齐全。

`low`、`high`、`max` 是该文档的接口档位。即使不同服务也有同名字段，也不可直接认为它们使用相同 token 数、搜索深度、工具策略或质量曲线。公平比较需要固定任务集、harness、工具、超时、输出预算和版本。

## 20.10 面向专家：从训练环境到可识别的能力结论

令 \(M\)、\(P\)、\(E\)、\(V\)、\(H\)、\(B\) 和 \(D\) 分别表示模型、后训练、环境、verifier、harness、预算和数据分布；\(R\) 是固定任务与指标下观测到的表现，\(F\) 表示这些因素与结果之间的总体关系，而不是已识别的因果分解：

```math
R=F(M,P,E,V,H,B,D).
```

若只报告最终成功率 `R`，很难判断提升来自模型后训练、任务变简单、verifier 放宽、工具更强、预算变多，还是环境 reset 修复。一个可复核的实验记录应至少绑定模型 revision、prompt/template、环境镜像、工具版本、权限策略、验证器 commit、输入分布、effort、token/时间上限和随机种子。

验证器有另一个常被忽略的统计问题：只用能完成任务的 judge 轨迹构造环境，可能过滤掉困难但有效的任务；只用某一种专家工作流，又会让模型过拟合那种操作顺序。环境多样性、任务可解性、奖励可靠性和人类覆盖之间是四个不同指标。它们不应合成一个漂亮总分后失去诊断能力。

## 20.11 常见误区

**误区一：1M context 等于模型会记住一百万 token。** 窗口是接口容量，实际有效利用仍取决于任务结构、位置、检索、压缩、输出预算和评测。

**误区二：有 oracle check 就说明验证器正确。** oracle 只说明存在成功路径；它不排除错误路径绕过验收。

**误区三：no-op 不能通过，就没有奖励捷径。** no-op 只能排除最简单的空操作捷径；还要防测试篡改、环境残留和代理指标。

**误区四：上下文 compaction 一定是某种特定算法。** 不应从 GLM 文档的 SAO 缩写猜测全称或损失。压缩方法必须以原始论文、模型卡或实现为准。

**误区五：推理档位提高就自动获得更多权限。** 预算控制与工具授权是两套状态；高 effort 仍应受相同或更严格的策略约束。

## 20.12 面试问答

**问：为什么长任务 Agent 训练要使用可执行环境，而不只用长 CoT 数据？**

答：长 CoT 能教模型表达步骤，却通常不给真实状态转移和执行反馈。可执行环境让模型面对版本、错误、测试、artifact 和恢复；验证器可以奖励实际完成。但环境质量和 verifier 质量会直接决定训练信号，因此需要可解性、no-op、未完成状态、隐藏测试和人工审计等门禁。

**问：如何判断一个代码任务 verifier 是否值得用于后训练？**

答：先写任务契约，再检查 oracle 能完成、初始 no-op 不通过、典型未完成状态不通过；之后用隐藏测试、对抗 artifact、权限隔离、环境 reset、独立实现和人工抽样测假阳性/假阴性。还要将 verifier 版本绑定到每条训练轨迹，避免奖励定义漂移。

**问：GLM-5.3 的 SAO with compaction 到底是什么？**

答：目前已核验的官方文档只称其继承该策略，没有给出 SAO 全称、损失或压缩机制。严谨回答应明确这一证据边界，并说明需要技术报告、论文或官方实现才能展开；可以讨论一般上下文压缩评测，但不能把教学抽象归因给该模型。

**问：如何迁移一个旧 Agent 到只能 `thinking.type: enabled` 的模型？**

答：把它当作协议迁移：先更新 schema 和 feature flag，再对请求/响应、流式、错误、usage、工具 call ID、effort、权限 trace 和质量成本做回归；禁用 thinking 的旧路径应明确失败或改路由，不能默默丢弃字段。

## 20.14 小结：环境与 verifier 门禁

到这里，我们建立了长任务训练的基础审计链：任务必须可执行，成功条件必须可观察，验证器要经受 no-op、未完成状态和捷径检查，客户端还要正确处理模型接口。后续各节把这套门禁用于榜单读数、训练/rollout 系统和轨迹恢复；发布方披露、公开实现与教学推导仍然分开判断。

## 20.16 可执行环境与 reference-free verifier 的训练门禁

官方[模型文档](https://docs.z.ai/guides/llm/glm-5.3)把后训练环境描述成接近真实研究或工程工作的长周期系统：任务可能需要读取代码、文档、集群、存储和实验结果，修改实现、运行实验、诊断瓶颈并交付可测量 artifact。环境中还可能有多步依赖与 hidden state。这个描述的关键变化是，奖励对象从“回答像不像正确”变成“状态和 artifact 是否满足任务契约”。

一个不读取 reference solution 的 verifier 仍然可能被错误设计欺骗，因此要分层检查：

1. `judge agent` 先检查任务是否可解、资源和工具是否足够。
2. `oracle check` 确认至少有一条合法路径能完成任务。
3. `no-op check` 确认初始状态什么也不做不能得分。
4. `unsolved-state check` 确认半成品、只改表面文件或未运行测试的状态不能提前通过。
5. hidden tests、权限隔离、reset 和人工抽样继续检查更隐蔽的 reward shortcut。

`reference-free` 不是“无需规格”。它只表示 verifier 不拿一份标准答案逐字比较；任务契约、外部测试、业务不变量和 artifact digest 仍要独立定义。验证器版本、环境镜像和权限策略也必须与轨迹绑定，否则同一奖励在不同版本上没有可比性。

## 20.17 slime：训练、rollout 和数值一致性是一个系统问题

Z.ai [发布方资料](https://z.ai/blog/glm-5.3)把 `slime` 描述为 RL scaling framework：Megatron 负责训练，SGLang 负责 rollout，training、rollout 和 data buffer 处在同一 dataflow。它能把数学、代码、sandbox、verifier 和长周期环境接入统一循环，但不意味着这些环境共享同一奖励定义或同一失败率。

长轨迹 RL 的一个工程风险是训练端和 rollout 端对同一 token 的 logprob 不一致。若差异足够大，优势估计看到的不是实际采样 policy，训练会把数值误差误当成策略变化。官方博客报告平均 logprob 差约 `1e-7`，并称相对旧 setup 降低超过 `99.99%`；这是发布方系统测量，不能脱离硬件、精度、batch、并发、序列长度和代码版本复现。

教学审计可以记录：

```text
sample_id, policy_revision, rollout_logprob, train_logprob,
abs_delta, token_mask, verifier_result, sample_age, retry_count
```

然后分别观察 policy lag、样本过期、失败重试和 verifier 延迟。训练吞吐提升也要分解 prefill/decode ratio、concurrency、有效样本率和每个成功 artifact 的成本；“端到端 throughput > 2.3x”不能直接翻译成模型质量提升。

## 20.18 tool_stream 与结构化工具调用的迁移门禁

GLM-5.3 的[官方迁移指南](https://docs.z.ai/guides/overview/migrate-to-glm-new)要求同时启用 `stream=true` 与 `tool_stream=true` 才能接收工具参数增量，并说明 `delta.tool_calls[*].function.arguments` 应按 `tool_call.index` 拼接。官方示例展示了 `name`、`call_id` 和 arguments 字段，但明确写出的增量重组逻辑是按 index 累加 arguments；客户端应保留服务端提供的 call ID 和工具名，不能假设所有字段都会跨任意 chunk 逐字符流出。迁移文档还要求 reasoning 开启，并支持 `low/high/max` 的 `reasoning_effort`；旧客户端若发送 `thinking.type: disabled` 可能直接失败。

流式重组不能简单地对每个 delta 做 `json.loads`。宿主可按 call index 建立临时 buffer，并保留响应给出的 call ID 和名称；响应流结束、确认参数增量收齐后，再做 JSON 解析、schema 校验、权限校验和幂等检查：

```text
delta(index, arguments_fragment; call_id/name as supplied)
    -> per-index buffer with retained metadata
    -> response stream complete and arguments collected
    -> JSON parse
    -> schema + business validation
    -> permission gate
    -> execute / reject
    -> tool result with call_id
```

断流、重复 delta、乱序 call、坏 JSON、未知工具和执行超时都应进入可恢复的 error state，不能因为模型输出了“完成”文本就提交副作用。Structured Output 只约束结构，不保证业务参数正确；最终成功仍由宿主执行结果和独立 verifier 决定。

## 20.19 SAO、IndexCache 与 GLM-5.3 的证据边界

GLM-5.3 [官方页面](https://docs.z.ai/guides/llm/glm-5.3)称其继承 GLM-5.2 的 `SAO with compaction`，但没有公开 5.3 独有的全称、loss、压缩格式或实现。公开的 [SAO 论文](https://arxiv.org/abs/2607.07508)直接讨论 GLM-5.2（750B-A40B）的 single-rollout asynchronous RL、off-policy、value-model design 和 double-side token clipping。面试回答可以把它作为关联算法背景，但必须说清“论文对象不是 GLM-5.3”。

[IndexCache 论文](https://arxiv.org/abs/2603.12201)讨论 DSA lightning indexer 的跨层 top-k 复用：少数 Full layers 运行 indexer，多数 Shared layers 复用邻近选择，以降低 indexer 计算。它是 DSA serving 的关联证据，不是 GLM-5.3 已公开架构变更的证明。[固定 HF config](https://huggingface.co/zai-org/GLM-5.3/blob/ba32f8c19c8738e2c57c71798c601d477a7bf844/config.json) 中的 `index_topk=2048`、`index_topk_freq=4` 和 `index_share_for_mtp_iteration=true` 是实现配置字段，也不能替代生产 kernel、召回曲线或硬件 profiling。

可以用[SAO 机制玩具脚本](../../research/model-update-2026-09/code/sao_async_rl_toy.py)把部分关系算出来。三条构造 rollout 分别耗时 1、3、2 秒，同步组的等待量为 `(3-1)+(3-3)+(3-2)=3` 秒。四个合成 token 的新旧 log-prob 差为 `0.02`、`-0.30`、`0.25`、`0`；逐个取指数得到 ratio `1.0202`、`0.7408`、`1.2840`、`1.0000`，在对称 ±0.2 clip 下分别落在区间、下界外、上界外、区间内。两步标量 critic proxy 的 MSE 从 `1.00` 降至 `0.64`。代码状态：已验证（2026-11-13，CPython 3.12.9，Python 标准库）。这些是合成机制示例，简化了论文中的目标和异步训练过程，不是 SAO 实现或 GLM-5.3 复现。

网络安全能力至少分三层：

| 层次 | 博客中的基准 | 应该怎样解释 |
|---|---|---|
| 发现与验证 | CyberGym，白盒源码、触发故障、Pass@1 84.5% | 定位并验证漏洞，不等于完整利用链 |

### 20.20.2 评测脚注是结论的一部分

面试中不能只复述分数。至少要同时说出：DeepSWE 使用 mini-swe-agent、temperature 0.95、top-p 1.0、400K context 和 6 小时 timeout；Terminal-Bench 3.0 使用 Claude Code 2.1.207、max effort、avg@3、隔离 task image、600 turns、10 小时、Tool Search disabled 和官方 verifier；ALE 使用 105 个隔离 Docker task、4 小时默认 timeout、任务卡最多 8 小时；CyberGym 使用 1,507 tasks、no web、域名白名单和 single-run Pass@1；ExploitGym 使用 869 tasks、2 小时/6 小时 TPS 归一化；ExploitBench 使用 41 tasks、3 revisions 和最多 300 interaction rounds。

如果面试官问“GLM-5.3 的新技术是什么”，可以按四层回答：第一，模型身份和接口层是沿用 GLM-5.2 基座、强制 thinking、三档 effort、工具流式和缓存/结构化输出；第二，后训练层是可执行长周期环境、judge、reference-free verifier 与 reward-shortcut audit；第三，系统层是 slime 的 train/rollout/data-buffer dataflow 和数值一致性；第四，评测层必须把 DataCurve 的 model+harness+environment+verifier 与 Z.ai 自报 benchmark 分开。SAO with compaction、IndexCache 和完整训练 recipe 仍有证据边界，不能把关联资料写成 GLM-5.3 独有内部实现。

## 20.21 用协议 toy 审计 compaction，而不是猜内部实现

截至 2026-11-13，[Z.ai 官方资料](https://docs.z.ai/guides/llm/glm-5.3)仍没有给出 GLM-5.3 compaction 的状态 schema、序列化格式或切分阈值。可以先用[通用 compaction 合同审计脚本](../../research/model-update-2026-09/code/glm53_compaction_contract_audit.py)检查恢复状态；它只依赖 Python 标准库，不调用模型，也不是 GLM-5.3 实现。

一个可继续执行的压缩状态至少要保留：

| 状态 | 为什么不能只放在自然语言摘要里 |
| --- | --- |
| `goal`、`current_plan`、已完成步骤 | 恢复后要知道任务目标和当前阶段，而不是重新猜测 |
| 工具 call/result lineage、权限 scope、幂等键 | 防止把已执行副作用重复执行，或在权限变化后错误重放 |
| `pending_effects`、artifact digest、verifier status | 区分“已经改了文件”“等待测试”“验收通过”和模型自称完成 |
| `schema_version`、cut marker、remaining budget | 让版本迁移、截断位置和预算消耗可审计 |

脚本构造三种截断点：工具调用前、call 已开始但 result 未到、result 已落盘；只有中间状态保留 pending effect 和幂等键，恢复器才能把外部副作用标为待核对，而不是盲目重放。脚本还构造缺失 pending effect 和孤立 effect 的坏状态，验证即使 JSON 合法也会被拒绝。这里的 token 预算应由目标 tokenizer 与实际 prompt 计算；脚本只验证协议字段，不声称测量压缩率。

代码状态：已验证（2026-11-13，CPython 3.12.9，Python 标准库）。运行命令：`python3 research/model-update-2026-09/code/glm53_compaction_contract_audit.py`。

面试回答应明确证据级别：官方只证明 GLM-5.3 沿用 `SAO with compaction`；toy 证明的是通用协议门禁；只有拿到 Z.ai 公开实现或可复现 API/权重实验，才可以讨论真实触发策略、压缩质量、工具重复率、artifact 成功率和生产 SLO。

## 20.22 Compaction 如何变成 RL 训练轨迹的分叉

截至 2026-09-28，Z.ai 对 GLM-5.3 的公开说法仍止于“继承 `SAO with compaction`”；官方资料没有展开其专属实现。固定 revision [`8ee9c1e`](https://github.com/THUDM/slime/tree/8ee9c1e1c8871ccd6dc8ec812edfaefa3dd1156b) 的 `THUDM/slime` 提供一个有用的训练侧案例。这是通用 Agent RL 数据管线，不是 GLM-5.3 的 compaction 实现。

### 20.22.1 为什么压缩会影响训练样本

一个 coding agent 的消息历史是可读字符串，训练目标却必须对应 rollout 模型实际采样的 token。工具输出、终端观察和压缩后的上下文都可能重写或替换既有消息；如果把重渲染后的对话重新 token 化，再假定它等价于此前模型采样的 token，就会破坏 token 与 rollout log-probability 的来源对应关系。

固定 `slime` example 采用两层结构：先为每个 session 按 role/message 构造路由树；再用保存的 token ID 前缀把每条根到叶路径变成一个或多个 `Sample`。因此 compaction 的关键不只是“摘要写得像不像”，还包括上下文改写后如何切分样本、保留模型生成来源，并防止把环境文字误当作模型动作反传。

| 管线对象 | pinned implementation 的处理 | 面试解释 |
|---|---|---|
| 精确 rollout 轨迹 | 保存 `prompt_ids`、`output_ids` 和每 token log-probs；解码 `response` 不用于重建训练目标 | 训练数据应保留可追溯的采样 token，而非只留文本 |
| 新增上下文 | user/tool/environment/template 文本进入上下文但 `loss_mask=0` | observation 是继续任务所需状态，不因此成为模型 action |
| 可证明来源的输出 | rollout 实际生成的 assistant token 通常 `loss_mask=1` | 仅在 token provenance 完整时保留训练信号 |
| 前缀分叉 | 消息树保留不同 history；共享 assistant 输出只在首个分支训练，其他分支将它作为 loss-zero context | 分叉样本不能把共享前缀重复算作新生成 |

### 20.22.2 短漂移重对齐与长漂移分叉

在上述固定 revision 的 `TrajectoryManager` 中，消息路由先按 message equality 找共同节点，然后另行比较 token ID 前缀。用一个合成输入看阈值：若最近一条新 assistant 响应共 700 tokens，其中 684 tokens 与旧前缀一致、尾部 16 tokens 发生漂移，`700<1,024`，实现可改写该响应尾部，并把被替换的旧 token 改作 `loss_mask=0` 上下文；若新响应长 1,100 tokens，或漂移位于更早历史，则会 fork 出新 sample。这个阈值只属于该 revision 的实现，不是 GLM API 或当前 main 的通用保证。

因此，`1,024` 不是模型 context compaction 的触发阈值，也不能迁移到 GLM-5.3 服务端。该层实现只负责把发生过的历史改写表示为可训练的数据边界；它不定义何时压缩、摘要生成方式、压缩保真度或 GLM 的长任务成功率。

### 20.22.3 `rollout_id` 与 reward 不能靠推测

多个 segment 共享 `rollout_id`，目的是保留它们属于同一原始 rollout 的分组关系；这个 ID 本身不说明 reward 是否按 segment 平分。固定 revision 内部对此存在明确不一致：`customization.md` 给出 `reward/K` 这一常见模式，coding-agent README 也称每条 chain 分 `reward/K`；但 `TrajectoryManager.get_trajectory()`、调用它的 `generate()` 路径和固定单测均显示完整 reward 被赋给每个 sample。除非锁定目标代码 revision 并审清 loss/advantage 归约，否则不要将任一文档句子概括成 slime 或 GLM 的通用规则。

这带出一个有用的工程检查：除任务成功率外，还要检查分叉前后样本数、每条训练 token 的 provenance、共享前缀的 loss mask、rollout 分组、reward/advantage 权重和样本平均口径。当前工作区没有安装 pytest，因此本轮只核对了固定源码与测试断言，没有声称这些上游测试已运行。

## 20.23 训练 checkpoint、rollout queue 与可索引 archive

Z.ai [官方博客](https://z.ai/blog/glm-5.3)把 `slime` 描述为训练/rollout 框架。2026-09-29 可见的提交 [`8088a4b`](https://github.com/THUDM/slime/commit/8088a4b) 增加 Straw checkpoint rollback 与 indexed archive；前序 [`6857224`](https://github.com/THUDM/slime/commit/6857224) 支持分布式 fully async rollout。它们是通用训练基础设施的源码案例，时间晚于 GLM-5.3 的发布资料，不能倒推成该模型实际使用的内部实现。

### 20.23.1 为什么要把模型与数据队列放在同一恢复边界

在异步 Agent RL 里，下一步训练输入不仅由权重和 optimizer 决定，也受 dataset cursor、pending/partial tasks、ready groups 顺序、batch builder 状态、queue ID 和 rollout weight version 影响。若只保存模型，恢复后可能重复采样、漏掉已完成任务，或把不同时间点的 queue 状态错误拼接。

固定实现先保存 actor/critic 与 rollout manager，再写 `committed_<step>.json` 作为逻辑联合提交标记。标记要求模型、`queue_state`、`builder_state` 都存在；缺 optimizer/RNG 时不允许标为可训练恢复。模型文件记录 size，并只对 JSON / `.metadata` 做 SHA-256；queue/builder snapshot 有 SHA-256。因此它提供明确的完成边界和部分完整性检查，不等于共享存储上的原子事务或全部权重 shard 的全量 hash。

### 20.23.2 回滚要 fork，不能覆盖旧未来

选定历史 step 后，新训练在独立 branch 和新 queue ID 中继续，旧 branch 与其 committed checkpoint 保留。queue snapshot 恢复 cursor、pending/partial work 和 ready group；payload 通过 immutable reference/copy-on-write 共享，减少重复存储，但分支拥有新的 task/receipt authority。若 checkpoint 没有 queue snapshot，系统进入空 queue 恢复；有可用 dataset cursor 时只恢复 cursor，否则从 offset 0 开始，这不是精确 replay。

这也解释了“恢复状态”与“确定性重放”的区别：optimizer 和训练 RNG 必须存在；但 GPU KV cache 与生成 RNG 不恢复，恢复之后新生成的 token 可能变化。checkpoint 目录本身也不足以搬迁任务，引用的 Straw shared pool 必须继续可用。

### 20.23.3 Archive 索引、queue authority 和 GC retention

`RolloutArchive` 按 chunk 保存样本，并用 sample/task key 定位数据。读取时保留训练 provenance，却剥离原 queue 的 lease/receipt 控制字段，避免调试归档获得修改原队列的权限。`.straw.json` 是索引，payload 仍在 Straw pool；`.pt` 导出才是自包含拷贝。

关闭 archive reader 与释放 archive 的数据所有权是两件事：先 `close()` 结束读取，所有 reader 完成后再 `release()`。在线 GC 只有在 task、queue、checkpoint、archive 等引用都释放后才能回收 pack；仅删除索引不释放 retention。这个模型可用于讲清不可变数据、copy-on-write、引用计数式保留和安全回收之间的关系。

### 20.23.4 全异步调度不是“丢弃旧样本”

Straw guide 的调度优先级为 completed groups、partial groups、fresh prompts。样本携带生成时的 weight version；系统据当前 serving version 计算 staleness 并排序，但不自动删除 stale samples。Fully async worker 在权重同步时暂停接收新任务，并先持久化 in-flight 结果。面试实验应记录 staleness 分布、policy lag、任务成功率、队列等待、失败恢复和 token 成本，而不是只报告 rollout throughput。

### 20.23.5 测试场景与证据等级

slime 的 fork integration test 使用 Qwen2.5-0.5B 和 4 张 GPU，设计覆盖显式/自动回滚分支、ready samples/cursor 恢复、旧 archive 不变、缺 queue snapshot 的空队列路径，以及 `.straw.json` 与 `.pt` replay。它是上游测试源码，不是 GLM-5.3 benchmark，也不是本机执行结果；当前没有运行该 4-GPU 集成测试。commit、固定文件哈希和证据边界见 [GLM-5.3 研究笔记](../../research/model-update-2026-09/glm-5.3-source-notes.md)。

## 20.24 本章小结：把长任务结果还原到证据链

长任务评估要同时追踪模型、环境、工具、预算、验证器和版本。一个可训练的环境不只要能执行，还要证明任务可解、起点不会白得分、半成品不会通过，并持续寻找会钻奖励空子的轨迹。Agent 遇到工具流和上下文压缩时，则必须保留 call/result 关系、待处理副作用、artifact 与 verifier 状态；丢失这些状态后，合法文本也未必能安全恢复。

GLM-5.3 的公开材料支持其接口、发布方训练流程和 benchmark 说明；Hugging Face 配置支持核对公开模型字段；第三方榜单支持有日期、有配置的外部观察；固定 slime revision 展示通用训练系统实现。它们回答的是不同问题。读者应保留这些证据边界，再把本章的 verifier 门禁、数值账本和恢复检查迁移到自己的长任务系统。
