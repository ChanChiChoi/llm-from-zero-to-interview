# 第 20 章 GLM-5.3：长任务环境、验证器与后训练边界

> 资料边界：本章以 [Z.ai GLM-5.3 官方文档](https://docs.z.ai/guides/llm/glm-5.3)、[迁移指南](https://docs.z.ai/guides/overview/migrate-to-glm-new)、[slime](https://github.com/THUDM/slime)、[IndexCache](https://arxiv.org/abs/2603.12201) 与 [SAO](https://arxiv.org/abs/2607.07508) 等公开资料为依据，核验日期为 2026-09-20。它们支持关于接口、长任务环境、验证器、训练/rollout dataflow 和关联 serving/RL 技术的讨论；不支持推断参数量、基础架构、完整训练配方或把 SAO/IndexCache 改写成 GLM-5.3 独有实现。

## 20.1 本章要解决的问题

长任务 Agent 不是把一个问题问得更长。以“修复线上训练任务吞吐下降”为例，模型需要先读日志，定位可能的瓶颈，修改实现，运行实验，比较新旧指标，再决定交付还是继续排查。每一步的真实结果都会改变下一步应该做什么。

这类能力不能只用一段漂亮的最终回答衡量。训练和评测都必须回答四个更具体的问题：

1. Agent 在什么环境里读、改、跑和测？
2. 什么结果算真正完成，谁来检查？
3. 验证器会不会把“什么也没做”或“绕过检查”误判为成功？
4. 模型、工具、上下文与预算怎样共同构成长任务系统？

GLM-5.3 官方文档提供了一个有价值的公开案例：它称 GLM-5.3 沿用 GLM-5.2 的基础模型，能力变化来自后训练；训练环境扩展到生产工程和研究工作流，并描述了环境生成、judge agent 与验证器检查。即使不掌握内部配方，我们仍可以从中学习怎样把长任务训练和评测设计得可审计。

## 20.2 先把公开事实和教学推导分开

官方文档明确写出的信息包括：GLM-5.3 为文本输入模型，标称 1M context window 与 128K maximum output；推理始终开启，`thinking.type` 只支持 `enabled`；`reasoning_effort` 提供 `low`、`high`、`max`，默认 `max`。文档还称 GLM-5.3 复用 GLM-5.2 基础模型，改进来自后训练。

官方对训练环境的描述更重要：研究 Agent 收集工作模式并生成可运行环境；judge agent 尝试求解以检查任务是否可解；部分任务奖励也由管线生成；生成验证器时不访问参考解，并以求解轨迹发现奖励捷径。文档提到 oracle、no-op 与 unsolved-state 检查，并承认环境和验证仍需要显著人工参与。

下面三类话不能混在一起：

| 类型 | 可以说什么 | 不能说什么 |
| --- | --- | --- |
| 官方接口事实 | 1M context、128K output、指定 effort 档位 | 1M 一定能可靠完成任意长任务 |
| 官方流程描述 | 有环境生成、judge 尝试求解、验证器检查 | 生成管线已经无人工、验证器绝对正确 |
| 本章教学抽象 | 用状态、动作、反馈和门禁解释任务环境 | 该抽象就是 GLM-5.3 的内部训练算法 |

文档使用了 “SAO with compaction” 的说法，但本轮可读一手资料没有定义 SAO 全称、优化目标或压缩算法。它只能被记录为待核验的名称。把它强行解释成某种 advantage、summary 或 attention 算法，会把猜测伪装成知识。

## 20.3 为什么训练环境比一条指令更接近真实能力

一个静态问答样本通常形如 `(prompt, answer)`。而一个可执行长任务更接近状态转移系统：

```math
s_{t+1}=T(s_t,a_t,e_t),
```

其中 `s_t` 是第 `t` 步环境状态，`a_t` 是 Agent 动作，`e_t` 是工具返回或外部事件，`T` 是环境的状态转移。状态可以包含代码版本、配置、测试结果、实验指标、剩余预算和权限；它不是一整段聊天历史。

例如吞吐优化任务的初始状态可以是：仓库中有一个低效数据加载器，基线吞吐为 80 samples/s，隐藏测试要求修改后至少达到 100 samples/s 且所有正确性测试通过。Agent 可读取文件、编辑实现、运行测试和运行基准。它若只把阈值改成 100，却没有改善代码，应当失败；它若获得 120 samples/s 但弄坏了样本顺序，也应当失败。

这解释了为什么“任务很长”不是长任务训练的充分条件。真正的长程困难来自：

- **依赖**：修改能否通过测试，依赖此前读取到的实际代码；
- **反馈**：运行错误会排除一部分假设，并引出新的排查路径；
- **状态**：当前 diff、已失败的实验与未满足的约束必须持续保留；
- **可验证性**：完成必须由任务契约判断，而不是模型自称完成；
- **恢复**：超时、工具失败或上下文折叠后，系统要知道可以从哪里继续。

## 20.4 任务契约：先定义什么叫完成

一个可训练任务至少要有目标、允许动作、初始状态、结束条件和观察规则。可以用以下教学契约表示：

```text
goal: 修复吞吐回归，同时保持输出顺序
initial_state: repo@r1, baseline=80 samples/s
allowed_actions: read, edit, run_unit_test, run_benchmark
success: unit_test_pass and throughput >= 100 and output_order_preserved
terminal_failures: timeout, forbidden_write, invalid_artifact
```

目标不是只写给模型看的自然语言愿望。`success` 必须被环境外部的检查器解释。若任务涉及文件、数据库或线上资源，契约还应写明沙箱、权限范围、数据副本、超时、资源上限、清理逻辑与 artifact 保存位置。

对初学者而言，可以把 verifier 想成验收测试，而不是老师的主观印象。它并不需要理解所有过程，但必须可靠检查任务的关键约束。对专家而言，任务契约也定义了奖励函数的支持集：验证器没有观察到的行为，奖励就无法直接约束。

## 20.5 Oracle、no-op 与未完成状态分别在防什么

官方文档列出的三类检查很适合拆开理解。

### Oracle check：任务本身能否被完成

oracle check 的目标是确认存在一个能够通过验收的解或参考路径。没有它，环境可能因依赖缺失、阈值错误、隐藏配置冲突而根本无解。训练数据若混入大量无解任务，模型会被惩罚于自己无法控制的失败。

但 oracle 存在不证明 verifier 完备。一个参考实现能通过，只说明至少有一条路径成功；它不能证明所有通过 verifier 的路径都真的满足业务目标。

### No-op check：什么也不做不能得分

no-op check 在初始状态就运行验收。若初始仓库已经满足所有成功条件，Agent 可以不理解任务、也不做任何工作便获得奖励。这会把“静止”变成一条高分捷径。

no-op 失败是必要条件，却不足以排除所有捷径。例如 Agent 可能删除测试、修改评分脚本、把基准数据替换为空数据，仍然让表面指标变好。因此验收器及其依赖应放在受保护路径，并对动作范围设置权限。

### Unsolved-state check：半成品不能提前宣布完成

未完成状态检查会构造或保留一个明显未达标的中间状态，确保 verifier 不会把“命令退出 0”“生成了补丁”或“写了报告”误当作任务成功。它能捕获过于宽松的结束条件。

三者组合的逻辑是：有可完成解、起点不应白得分、半成品不能误过关。它们都只是必要检查。一个可靠系统还需要对抗样本、独立实现、隐藏测试、人工抽检、版本绑定与失败分类。

## 20.6 一个零依赖的验证器门禁 demo

下面的例子不调用模型、不修改真实文件。它用 toy artifact 演示三类检查和一个容易忽略的权限条件。输入是任务开始前、已完成 artifact 和半成品 artifact；输出说明每个状态为何通过或失败。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Artifact:
    throughput: float
    unit_tests_pass: bool
    order_preserved: bool
    modified_protected_test: bool = False


def verify(artifact, target_throughput=100.0):
    if not isinstance(artifact, Artifact):
        raise TypeError("artifact must be an Artifact")
    if target_throughput <= 0:
        raise ValueError("target_throughput must be positive")
    if artifact.modified_protected_test:
        return "invalid: protected verifier changed"
    if not artifact.unit_tests_pass:
        return "invalid: unit tests failed"
    if not artifact.order_preserved:
        return "invalid: output order changed"
    if artifact.throughput < target_throughput:
        return "incomplete: throughput target not met"
    return "success"


initial = Artifact(throughput=80.0, unit_tests_pass=True, order_preserved=True)
completed = Artifact(throughput=120.0, unit_tests_pass=True, order_preserved=True)
shortcut = Artifact(throughput=130.0, unit_tests_pass=True,
                    order_preserved=True, modified_protected_test=True)

assert verify(initial) == "incomplete: throughput target not met"  # no-op check
assert verify(completed) == "success"                              # oracle-like path
assert verify(shortcut) == "invalid: protected verifier changed"   # reward shortcut
print(verify(initial), verify(completed), verify(shortcut), sep=" | ")
```

输出是：

```text
incomplete: throughput target not met | success | invalid: protected verifier changed
```

这个 demo 不是 GLM-5.3 的训练代码，也没有证明真实验证器只检查四个字段。它表达的是可迁移的工程原则：成功条件、完整性条件和 verifier 完整性必须分开；否则奖励会向容易伪造的代理指标漂移。

## 20.7 验证器为什么会被“奖励捷径”欺骗

设真实任务成功事件为 `S`，验证器给出的二值奖励为 `r`。理想情况是：

```math
r=1 \Longleftrightarrow S=1.
```

现实中通常只能近似：

```math
P(r=1\mid S=0)>0
\quad\text{或}\quad
P(r=0\mid S=1)>0.
```

前者是假阳性：任务其实失败了，却得到奖励；后者是假阴性：正确工作被错误拒绝。生成模型会在训练中寻找让 `r=1` 的轨迹，不会自动理解人类真正想要优化的 `S`。因此，验证器的漏洞会被放大成策略偏好。

常见捷径包括：只匹配输出格式、只测公开样例、在错误目录写入 artifact、修改测试自身、利用环境残留、跳过慢测试、把异常吞掉后返回成功。防御要配合任务类型，而不是只加一条“不得作弊”的 prompt：

| 风险 | 更接近问题根源的防御 |
| --- | --- |
| 只匹配格式 | 用程序语义或独立结果校验 |
| 只过公开样例 | 加隐藏切片和反事实输入 |
| 改写验收脚本 | 保护 verifier 路径，限制写权限 |
| 使用残留状态 | 每次 reset 环境，记录版本与 hash |
| 无意义高指标 | 同时检查正确性、资源消耗和业务约束 |
| 超时结果未知 | 记录状态，查询后再重试，不能直接计成功 |

这里的重点不是把 Agent 当作攻击者，而是承认任何被优化的分数都可能与目标脱钩。长任务后训练把这个问题从“答案格式”扩大到了代码、工具、文件、实验和环境状态。

## 20.8 上下文压缩：能省 token，不等于保存了任务状态

当任务持续很久时，原始 trace、日志和工具输出会超过上下文预算。压缩需要保留的不是“看起来最像摘要的句子”，而是后续决策所依赖的事实：任务契约、当前版本、已修改文件、失败测试、尚未验证的假设、权限、剩余预算和可恢复 artifact。

可以把压缩器写成一个教学函数：

```math
c_t=G(h_{\leq t},K_t),
```

`h_{≤t}` 是历史轨迹，`K_t` 是必须保留的状态键，`c_t` 是用于下一步的压缩表示。好压缩不是 `c_t` 越短越好，而是在 token 预算内让下一步动作仍接近使用完整历史时的选择。若 diff 丢失、测试版本错位或权限被摘要成模糊文字，后续 Agent 可能在错误世界状态上继续工作。

GLM-5.3 文档说它继承 “SAO with compaction”，但没有公开这个 `G` 的定义。因此本章只能解释一般性压缩评测：比较完整 history 与 compressed history 下的任务完成率、关键状态召回、错误恢复率、工具重复率、成本与延迟；不能将上面的数学教学符号归为 GLM 的实现。

## 20.9 协议迁移：模型名相同，请求仍可能失败

GLM-5.3 文档说明 `thinking.type` 只支持 `enabled`。一个旧客户端若仍发送 `thinking.type: disabled`，不能假定服务器会静默忽略；官方文档警告迁移前应调整，否则请求会失败。它反映了更一般的迁移原则：模型迁移是能力契约迁移，不是替换字符串。

迁移测试至少覆盖：

1. 请求 schema：模型 ID、thinking 字段、reasoning effort、工具字段和结构化输出字段。
2. 响应 schema：内容、reasoning 相关字段、工具 call ID、usage、错误格式与流式事件。
3. 行为指标：成功率、TTFT、TPOT、输出长度、工具轮数、重试率与单位成功成本。
4. 安全与运行时：权限是否保持收缩、unknown 工具状态是否可恢复、审计字段是否齐全。

`low`、`high`、`max` 是该文档的接口档位。即使不同服务也有同名字段，也不可直接认为它们使用相同 token 数、搜索深度、工具策略或质量曲线。公平比较需要固定任务集、harness、工具、超时、输出预算和版本。

## 20.10 面向专家：从训练环境到可识别的能力结论

长任务提升的归因至少受模型 `M`、后训练 `P`、环境 `E`、verifier `V`、harness `H`、预算 `B` 与数据分布 `D` 影响：

```math
R=F(M,P,E,V,H,B,D).
```

若只报告最终成功率 `R`，很难判断提升来自模型后训练、任务变简单、verifier 放宽、工具更强、预算变多，还是环境 reset 修复。一个可复核的实验记录应至少绑定模型 revision、prompt/template、环境镜像、工具版本、权限策略、验证器 commit、输入分布、effort、token/时间上限和随机种子。

验证器有另一个常被忽略的统计问题：只用能完成任务的 judge 轨迹构造环境，可能过滤掉困难但有效的任务；只用某一种专家工作流，又会让模型过拟合那种操作顺序。环境多样性、任务可解性、奖励可靠性和人类覆盖之间是四个不同指标。它们不应合成一个漂亮总分后失去诊断能力。

## 20.11 常见误区

**误区一：1M context 等于模型会记住一百万 token。** 窗口是接口容量，实际有效利用仍取决于任务结构、位置、检索、压缩、输出预算和评测。

**误区二：有 oracle check 就说明验证器正确。** oracle 只说明存在成功路径；它不排除错误路径绕过验收。

**误区三：no-op 不能通过，就没有奖励捷径。** no-op 只能排除最简单的空操作捷径；还要防测试篡改、环境残留和代理指标。

**误区四：上下文 compaction 一定是某种特定算法。** 不应从 GLM 文档的 SAO 缩写猜测全称或损失。压缩方法必须以原始论文、模型卡或实现为准。

**误区五：推理档位提高就自动获得更多权限。** 预算控制与工具授权是两套状态；高 effort 仍应受相同或更严格的策略约束。

## 20.12 面试问答

**问：为什么长任务 Agent 训练要使用可执行环境，而不只用长 CoT 数据？**

答：长 CoT 能教模型表达步骤，却通常不给真实状态转移和执行反馈。可执行环境让模型面对版本、错误、测试、artifact 和恢复；验证器可以奖励实际完成。但环境质量和 verifier 质量会直接决定训练信号，因此需要可解性、no-op、未完成状态、隐藏测试和人工审计等门禁。

**问：如何判断一个代码任务 verifier 是否值得用于后训练？**

答：先写任务契约，再检查 oracle 能完成、初始 no-op 不通过、典型未完成状态不通过；之后用隐藏测试、对抗 artifact、权限隔离、环境 reset、独立实现和人工抽样测假阳性/假阴性。还要将 verifier 版本绑定到每条训练轨迹，避免奖励定义漂移。

**问：GLM-5.3 的 SAO with compaction 到底是什么？**

答：目前已核验的官方文档只称其继承该策略，没有给出 SAO 全称、损失或压缩机制。严谨回答应明确这一证据边界，并说明需要技术报告、论文或官方实现才能展开；可以讨论一般上下文压缩评测，但不能把教学抽象归因给该模型。

**问：如何迁移一个旧 Agent 到只能 `thinking.type: enabled` 的模型？**

答：把它当作协议迁移：先更新 schema 和 feature flag，再对请求/响应、流式、错误、usage、工具 call ID、effort、权限 trace 和质量成本做回归；禁用 thinking 的旧路径应明确失败或改路由，不能默默丢弃字段。

## 20.14 本章总结

GLM-5.3 的公开资料提示我们：长任务能力的后训练不应只关注模型生成了多少推理文本，还要关注任务环境是否可执行、验收信号是否可靠、状态能否恢复，以及预算与权限是否可审计。公开文档可以支持这一工程知识链，但尚不足以支持对 SAO、压缩算法或内部训练配方的具体断言。保留这种边界，才能让前沿模型资料真正成为可迁移的学习材料。

## 20.15 本轮榜单结果：先记录配置，再谈能力

2026-09-20 的 Artificial Analysis 精确条目是 `glm-5-3` 的 `max` 配置；详情快照为 3,928,329 bytes，SHA-256 为 `090279e870a3ebb72c7a69f24963f87fe10d63595642a4c61959b911f2a3c3a2`。页面给出 1M context、约 72.1152 tokens/s、约 2.99s TTFT、`$1.40/$4.40` 和 Intelligence Index `44.777392385614`。这些数字属于第三方目录和 provider 测量，不能单独证明参数量、训练方法或内部推理深度。

DataCurve 的精确行为配置是 `mini_swe_agent_glm_5_3_max`：4 次 run、451 次 attempted、311 次 passed、Pass@1 `68.9579%`、Pass@4 `87.6106%`、平均成本约 `$3.9934`、平均输出约 80.4K token、平均 124.47 agent steps。这里被测的是：

```text
model revision + max effort + mini-swe-agent + tools
             + task repositories + environment + timeout + verifier
```

因此面试中应说“GLM-5.3 在该配置和 harness 下得到这个结果”，不能说“GLM-5.3 裸模型 Pass@1 是 68.96%”。也不能把 GLM-5.3-Flash、GLM-5.2 或 Z.ai 自报 benchmark 的数字迁移到这条 DataCurve 行。

## 20.16 可执行环境与 reference-free verifier 的训练门禁

官方资料把后训练环境描述成接近真实研究或工程工作的长周期系统：任务可能需要读取代码、文档、集群、存储和实验结果，修改实现、运行实验、诊断瓶颈并交付可测量 artifact。环境中还可能有多步依赖与 hidden state。这个描述的关键变化是，奖励对象从“回答像不像正确”变成“状态和 artifact 是否满足任务契约”。

一个不读取 reference solution 的 verifier 仍然可能被错误设计欺骗，因此要分层检查：

1. `judge agent` 先检查任务是否可解、资源和工具是否足够。
2. `oracle check` 确认至少有一条合法路径能完成任务。
3. `no-op check` 确认初始状态什么也不做不能得分。
4. `unsolved-state check` 确认半成品、只改表面文件或未运行测试的状态不能提前通过。
5. hidden tests、权限隔离、reset 和人工抽样继续检查更隐蔽的 reward shortcut。

`reference-free` 不是“无需规格”。它只表示 verifier 不拿一份标准答案逐字比较；任务契约、外部测试、业务不变量和 artifact digest 仍要独立定义。验证器版本、环境镜像和权限策略也必须与轨迹绑定，否则同一奖励在不同版本上没有可比性。

## 20.17 slime：训练、rollout 和数值一致性是一个系统问题

Z.ai 公开资料把 `slime` 描述为 RL scaling framework：Megatron 负责训练，SGLang 负责 rollout，training、rollout 和 data buffer 处在同一 dataflow。它能把数学、代码、sandbox、verifier 和长周期环境接入统一循环，但不意味着这些环境共享同一奖励定义或同一失败率。

长轨迹 RL 的一个工程风险是训练端和 rollout 端对同一 token 的 logprob 不一致。若差异足够大，优势估计看到的不是实际采样 policy，训练会把数值误差误当成策略变化。官方博客报告平均 logprob 差约 `1e-7`，并称相对旧 setup 降低超过 `99.99%`；这是发布方系统测量，不能脱离硬件、精度、batch、并发、序列长度和代码版本复现。

教学审计可以记录：

```text
sample_id, policy_revision, rollout_logprob, train_logprob,
abs_delta, token_mask, verifier_result, sample_age, retry_count
```

然后分别观察 policy lag、样本过期、失败重试和 verifier 延迟。训练吞吐提升也要分解 prefill/decode ratio、concurrency、有效样本率和每个成功 artifact 的成本；“端到端 throughput > 2.3x”不能直接翻译成模型质量提升。

## 20.18 tool_stream 与结构化工具调用的迁移门禁

GLM-5.3 的迁移资料要求 reasoning 开启，并支持 `low/high/max` 的 `reasoning_effort`。旧客户端若发送 `thinking.type: disabled` 可能直接失败。工具调用还可通过 `tool_stream=true` 与 `stream=true` 组合，把函数名、call ID 和 JSON arguments 分成多个 delta 返回。

流式重组不能简单地对每个 delta 做 `json.loads`。宿主应按 call ID 建立 buffer，分别拼接函数名和 arguments，等到结束事件后再做 JSON 解析、schema 校验、权限校验和幂等检查：

```text
delta(call_id, name_part, args_part)
    -> per-call buffer
    -> end-of-call
    -> JSON parse
    -> schema + business validation
    -> permission gate
    -> execute / reject
    -> tool result with call_id
```

断流、重复 delta、乱序 call、坏 JSON、未知工具和执行超时都应进入可恢复的 error state，不能因为模型输出了“完成”文本就提交副作用。Structured Output 只约束结构，不保证业务参数正确；最终成功仍由宿主执行结果和独立 verifier 决定。

## 20.19 SAO、IndexCache 与 GLM-5.3 的证据边界

GLM-5.3 官方页面称其继承 GLM-5.2 的 `SAO with compaction`，但当前没有公开 5.3 独有的全称、loss、压缩格式或实现。公开的 SAO 论文直接讨论 GLM-5.2（750B-A40B）的 single-rollout asynchronous RL、off-policy、value-model design 和 double-side token clipping。面试回答可以把它作为关联算法背景，但必须说清“论文对象不是 GLM-5.3”。

IndexCache 论文讨论 DSA lightning indexer 的跨层 top-k 复用：少数 Full layers 运行 indexer，多数 Shared layers 复用邻近选择，以降低 indexer 计算。它是 DSA serving 的关联证据，不是 GLM-5.3 已公开架构变更的证明。HF config 的 `index_topk=2048`、`index_topk_freq=4` 和 `index_share_for_mtp_iteration=true` 是实现配置字段，也不能替代生产 kernel、召回曲线或硬件 profiling。

## 20.20 面试版总结

### 20.20.1 官方博客新增的能力阶梯

GLM-5.3 官方博客把编码 Agent 的发布方结果和网络安全结果拆成不同测量对象。Z.ai Code Bench 相对 GLM-5.2 的 50% 提升，以及 Max/High effort 下完成率和 output-token efficiency 的对照，说明后训练评估同时关心任务结果和轨迹成本；它们仍绑定私有任务集、checklist、effort、harness 和统计口径。

网络安全能力至少分三层：

| 层次 | 博客中的基准 | 应该怎样解释 |
|---|---|---|
| 发现与验证 | CyberGym，白盒源码、触发故障、Pass@1 84.5% | 定位并验证漏洞，不等于完整利用链 |
| 更深利用推理 | ExploitBench，Pass@1 54.4% | 任务语义和分母不同，不能与 CyberGym 合并 |
| 时间归一化完成 | ExploitGym，2 小时/6 小时完成 105/130 个任务 | 结果依赖模型 TPS、时间预算、任务集和 harness |

博客还报告合作代码库经专家复核、筛选和去重后，在 269 个项目中识别 2,436 个漏洞，其中 1,097 个为中高危。这个数字是发布方合作统计，不等于模型单独完成全量发现，也不等于所有漏洞都已经公开或完成利用验证。

### 20.20.2 评测脚注是结论的一部分

面试中不能只复述分数。至少要同时说出：DeepSWE 使用 mini-swe-agent、temperature 0.95、top-p 1.0、400K context 和 6 小时 timeout；Terminal-Bench 3.0 使用 Claude Code 2.1.207、max effort、avg@3、隔离 task image、600 turns、10 小时、Tool Search disabled 和官方 verifier；ALE 使用 105 个隔离 Docker task、4 小时默认 timeout、任务卡最多 8 小时；CyberGym 使用 1,507 tasks、no web、域名白名单和 single-run Pass@1；ExploitGym 使用 869 tasks、2 小时/6 小时 TPS 归一化；ExploitBench 使用 41 tasks、3 revisions 和最多 300 interaction rounds。

这些条件构成 benchmark manifest。模型版本、effort、工具、环境、超时、隔离、域名策略、verifier 和聚合方法缺一项，结果就不能与另一条 benchmark 或 DataCurve 行直接比较。

如果面试官问“GLM-5.3 的新技术是什么”，可以按四层回答：第一，模型身份和接口层是沿用 GLM-5.2 基座、强制 thinking、三档 effort、工具流式和缓存/结构化输出；第二，后训练层是可执行长周期环境、judge、reference-free verifier 与 reward-shortcut audit；第三，系统层是 slime 的 train/rollout/data-buffer dataflow 和数值一致性；第四，评测层必须把 DataCurve 的 model+harness+environment+verifier 与 Z.ai 自报 benchmark 分开。SAO with compaction、IndexCache 和完整训练 recipe 仍有证据边界，不能把关联资料写成 GLM-5.3 独有内部实现。

## 20.21 用协议 toy 审计 compaction，而不是猜内部实现

截至 2026-09-23，Z.ai 公开资料仍没有给出 GLM-5.3 compaction 的状态 schema、序列化格式或切分阈值。可以先用 [`glm53_compaction_contract_audit.py`](../../research/model-update-2026-09/code/glm53_compaction_contract_audit.py) 做一个不依赖模型的恢复审计。这个 toy 不是 GLM-5.3 实现，而是把面试中应追问的质量门禁具体化。

一个可继续执行的压缩状态至少要保留：

| 状态 | 为什么不能只放在自然语言摘要里 |
| --- | --- |
| `goal`、`current_plan`、已完成步骤 | 恢复后要知道任务目标和当前阶段，而不是重新猜测 |
| 工具 call/result lineage、权限 scope、幂等键 | 防止把已执行副作用重复执行，或在权限变化后错误重放 |
| `pending_effects`、artifact digest、verifier status | 区分“已经改了文件”“等待测试”“验收通过”和模型自称完成 |
| `schema_version`、cut marker、remaining budget | 让版本迁移、截断位置和预算消耗可审计 |

toy 对一个完整候选做确定性 JSON 序列化再反序列化，并检查上述字段是否保真、token 预算是否下降、原始历史 ID 是否与 canonical tool ID 混淆。另一个候选故意删除待执行副作用、artifact digest、verifier 状态和幂等键，虽然仍能生成合法 JSON，却被审计拒绝。这个差异说明“能解析”不等于“可恢复”。

面试回答应明确证据级别：官方只证明 GLM-5.3 沿用 `SAO with compaction`；toy 证明的是通用协议门禁；只有拿到 Z.ai 公开实现或可复现 API/权重实验，才可以讨论真实触发策略、压缩质量、工具重复率、artifact 成功率和生产 SLO。
