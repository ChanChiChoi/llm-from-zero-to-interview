# 第 19 章 Interleaved Thinking：工具观察如何改变推理轨迹

## 19.1 不是先想完再调用工具

传统的工具调用示例通常是：模型先生成一个完整计划，调用工具，最后把工具结果填进答案。真实任务往往不是这样。模型只有看到搜索结果、编译错误、网页状态或数据库返回值之后，才知道下一步应该做什么。

Interleaved thinking 描述的就是这种交错循环：一小段推理提出动作，工具返回观察，模型根据观察重新推理，再决定继续调用、修正假设或结束。它比“先生成一段长思考”更接近 Agent 的实际执行。

## 19.2 一个带状态的循环

可以把状态写成：

```text
think -> propose action -> authorize -> execute
  -> observe -> update state -> think
```

状态 `s_t` 在第 `t` 轮包含上下文、已确认事实、候选假设、预算、权限和外部资源版本。动作 `a_t` 可能是搜索、读取文件、运行测试或请求人工。观察 `o_{t+1}` 回来后，模型更新状态：

```math
s_{t+1}=F(s_t,a_t,o_{t+1})
```

这条式子看似简单，却解释了为什么工具协议不能只把结果拼成一条普通 user message。系统需要知道哪个 call 产生了观察、哪个版本的工具返回了它、动作是否实际提交，以及下一轮是否允许继续。

## 19.3 为什么交错比长思考有效

如果模型在没有外部信息时一次写出很长计划，计划中的事实可能已经过时，或者一开始的假设就是错误的。交错过程让模型在关键节点获得反馈，把计算花在减少不确定性上。

例如调试时，模型可以先提出“查看错误堆栈”，然后根据实际文件决定是否需要搜索调用链；研究时先检索论文元数据，再决定是否读取方法章节；浏览器任务先观察页面当前状态，再选择点击或输入。

交错也会增加成本和风险。每一轮工具都有网络、权限、解析和副作用问题；如果模型在没有新信息时反复调用，系统就会陷入循环。因此交错推理必须和预算、去重、验证及安全策略一起设计。

## 19.4 Tool call 不是普通文本

一个结构化工具事件通常包括工具名、参数、call id、schema 版本和调用来源。工具结果包括对应 call id、状态、内容、错误类型、来源和是否可重试。

若只把工具结果拼成文本，模型可能把旧结果当成新结果，把错误消息当成数据，或在重试时失去幂等信息。流式协议还要保证部分输出不会在回滚后被客户端误认为已经提交。

一个安全的状态表可以这样设计：

| 状态 | 含义 | 是否允许重试 | 是否允许外部副作用 |
| --- | --- | --- | --- |
| proposed | 模型提出动作 | 由策略决定 | 否 |
| authorized | 权限已通过 | 由 executor 决定 | 尚未发生 |
| executing | 工具正在执行 | 需查询或幂等 | 可能已发生 |
| observed | 已获得结果 | 通常不重试 | 已知 |
| committed | 副作用已提交 | 不可盲重试 | 已发生 |
| failed | 已确认失败 | 依错误类型 | 未知或未发生 |

## 19.5 代码调试的交错例子

用户说“昨天发布后接口偶发 500”。模型不应立即写一篇根因报告。它可以先读取部署 revision 和错误样本，再查看对应时间段的日志；如果日志指向缓存刷新，则读取刷新代码和最近 diff；提出 patch 后运行单元测试，再用一个并发测试确认假设。

每一步都应该把事实和假设分开。例如“日志显示 timeout=3s”是观察；“timeout 导致连接池耗尽”是待验证假设；“将 timeout 改为 10s 后隐藏测试通过”才是较强证据。交错协议应保留这些来源，避免最后一轮模型把假设写成事实。

## 19.6 研究 Agent 的交错例子

研究任务中，模型先搜索题目和作者，观察结果决定是否存在多个版本；再读取论文摘要和实验表，发现结果不可比时继续读取数据设置；最后引用原文并说明限制。

如果模型在第一次搜索后就生成结论，它可能把预印本摘要、博客和正式论文混为一谈。工具协议应让每个 observation 带 URL、版本、时间和内容 hash，便于最后的引用验证。

## 19.7 预算与停止条件

交错循环需要至少四个硬性条件：最大工具轮次、最大 reasoning token、总 wall-clock 和最大外部副作用。继续条件还要检查最近观察是否带来新信息。

可以定义一个信息增益近似：

```math
I_t=H(\mathcal{H}_t)-H(\mathcal{H}_{t+1})
```

其中 `\mathcal{H}` 表示当前假设空间，`H` 是不确定性。真实系统不一定显式计算熵，但可以用新增证据、候选变化或 verifier 分数改善作为 proxy。当连续几轮 `I_t` 低于阈值，应该停止或转人工。

## 19.8 与安全协议的关系

工具返回的内容不一定可信。网页、issue、文件和数据库字段都可能包含提示注入，告诉模型绕过系统规则或把秘密发送出去。交错循环不能把 observation 当成高优先级指令；它是外部数据，必须经过来源标记和工具权限。

高风险动作应采用两阶段提交：模型提出动作，策略和用户批准，executor 执行并返回结果。即使模型在上一轮已经“想清楚”，下一轮也不能跳过授权。失败恢复时还要区分“未执行”和“可能已执行”，防止重复支付或重复发布。

## 19.9 评估 interleaved thinking

评测任务应包含工具成功、工具空结果、超时、部分返回、权限拒绝、页面变化、测试失败和用户中断。指标包括最终成功率、平均工具轮次、无效调用率、信息增益、恢复成功率、重复副作用率、p95 和人工接管。

比较时要和“先生成完整计划再执行”做对照。交错路径如果成功率更高但每个任务要调用十倍工具，可能只适合高价值任务；如果在工具延迟高的环境中造成 p99 爆炸，则需要批量读取或更强的规划。

## 19.10 常见失败模式

模型把工具 schema 当成自然语言建议，导致参数错误；协议只回传文本，没有 call id，导致流式拼接和重试错位；工具结果没有版本和来源，导致旧证据污染当前结论；没有停止条件，导致重复搜索；没有两阶段提交，导致模型草稿变成实际副作用。

另一个失败是把所有 observation 全量塞回 context。长工具结果会挤压真正相关信息，应让工具返回结构化摘要、分页和可引用 artifact，必要时再按需读取原文。

## 19.11 面试回答与练习

回答“什么是 interleaved thinking”时，可以说它是推理、工具动作和观察交错进行的闭环；模型不是先生成完整答案，而是根据外部反馈更新状态。实现上要有结构化 tool event、call id、权限、预算、回滚和引用；评估要看工具成功、无效调用、恢复、成本和副作用，而不只是最后一段文本。

练习一：为代码 Agent 画出“读取文件—测试—patch—回归”的状态机。

练习二：设计一个工具超时协议，区分未知、空结果和明确失败。

练习三：给一个浏览器 Agent 列出三种提示注入，并说明 observation 层如何隔离它们。

### 19.11.1 一次交错循环的事件语义

一次 interleaved loop 至少包含 `reasoning_started`、`tool_call_proposed`、`policy_checked`、`tool_started`、`tool_result`、`verification` 和 `response_completed` 等事件。每个事件要有 `trace_id`、`turn_id`、`call_id`、时间、输入摘要、状态和版本，不能只把最终工具结果拼成文本。

工具返回是 observation，不是新的系统指令。它要带来源、可信等级、大小限制和可执行字段；网页中的文字、文件中的注释和第三方 API 的自然语言都应默认当作不可信数据，策略层不能因为它们写了“请执行”就提高权限。

### 19.11.2 worked example：测试驱动的代码修复

模型先提出“检查 `parser.py` 的边界条件”，工具读取文件；模型根据观察提出 patch；执行器在沙箱运行测试；测试返回失败日志；模型再更新假设。每轮都要记录 patch 基线、测试命令、输出 hash 和当前 workspace revision。

若测试工具超时，状态是 `unknown`，不是“测试失败”；若 patch 已写入但没有通过 policy，不能把它交给下一个模型继续执行；若用户在中途修改文件，旧 patch 的基线失效，系统应要求重新读取和合并。

### 19.11.3 协议的停止条件

交错循环要有最大轮数、最大工具时间、最大副作用数和无进展检测。下列信号可以触发停止或升级：连续相同调用、观察没有新信息、verifier 分数不变、预算耗尽、权限变化、用户取消和外部状态未知。没有停止条件的 interleaved thinking 只是更容易形成 Agent 循环。

## 19.12 交错轨迹的提交语义

思考 token、工具请求、工具结果和最终回答的状态不能混为一个字符串。工具调用提交后，外部副作用可能已经发生；模型生成的下一段思考只是解释，不能覆盖事实。

轨迹应区分 draft、approved、executed、verified 和 committed。工具失败时，只回滚未提交的模型状态；已经执行的写操作要按工具事务处理。

## 19.13 事件协议决定状态能否恢复

交错推理如果只在服务端内部循环，客户端仍需要知道哪些事件已经发生。一个最小事件链可以包含 `reasoning_started`、`tool_call_proposed`、`policy_checked`、`tool_started`、`tool_result`、`verification`、`approval_required` 和 `response_completed`。每个事件应有 `trace_id`、`turn_id`、`call_id`、模型/工具版本、时间和状态。

事件序列比最终文本更接近真实事实。例如客户端收到 `tool_call_proposed` 但没有收到 `tool_started`，不能认为工具已经执行；收到 `tool_started` 但连接断开，状态应是未知，恢复时要查询执行器。流式协议还要保证重放不重复提交副作用，事件需要有顺序号或幂等消费键。

## 19.14 工具观察的来源与可信等级

工具返回内容要分成数据和指令。网页中的“请忽略之前规则”、代码注释中的命令、数据库字段里的自然语言都属于数据，不会自动获得系统或开发者消息的优先级。协议可以给 observation 增加 `source`、`retrieved_at`、`revision`、`content_hash`、`trust_level` 和 `executable_fields`，让后续模型和策略层知道它是什么。

```json
{
  "call_id": "c17",
  "source": {"kind": "repository", "revision": "r42"},
  "content_hash": "...",
  "trust_level": "untrusted_data",
  "facts": [{"field": "test_status", "value": "failed"}],
  "instructions": []
}
```

这样既能保留证据，也能避免把整段网页重新塞进上下文。大结果应使用分页、结构化字段和受控 artifact 引用；需要审计时按 hash 读取原文。引用来源、时效和权限也必须在最终答案生成前重新检查。

## 19.15 两阶段提交与外部副作用

交错推理中的模型输出可能是草稿、建议或真正的动作请求。协议应明确区分 `draft`、`approved`、`executed`、`verified` 和 `committed`。高风险动作采用两阶段提交：第一阶段生成并展示动作摘要、目标、参数和影响范围；第二阶段由 policy 或用户批准后执行。

```text
proposal -> policy check -> user/automatic approval
         -> execute with idempotency key
         -> query result -> verify -> commit
```

工具超时后不能直接重试写操作。先查询 idempotency key 或外部状态；如果状态未知，暂停并人工接管。对多工具工作流，可以使用 saga：每一步定义补偿动作，但要承认某些外部副作用不可逆，补偿不是“回到从未发生过”。

## 19.16 交错 Agent 的端到端验收

验收不能只测工具调用成功的 happy path。至少要覆盖空结果、部分返回、结构化参数错误、权限拒绝、超时、页面变化、用户取消、模型重试、外部状态未知和提示注入。每个 case 要验证事件顺序、最终状态、工具副作用和用户可见解释。

可用以下指标组成验收条件：最终任务成功率、有效工具调用率、无效调用率、单位成功成本、工具等待占比、恢复成功率、重复副作用率、未授权动作率和 p99。对研究任务再加引用支持率；对代码任务加测试通过率和无关 diff 比例；对生产动作加人工确认覆盖率。

如果交错路径比“一次性生成完整计划再执行”更准确，但工具轮次增加十倍，应按业务价值决定是否采用。它更适合外部反馈能显著改变下一步的任务，不适合每一步都已知且工具延迟极高的简单流水线。

## 19.17 事件类型决定状态能否恢复

交错循环至少要区分 `reasoning_started`、`tool_call_proposed`、`policy_checked`、`tool_started`、`tool_result_received`、`reasoning_resumed`、`answer_committed` 和 `request_cancelled`。事件之间的顺序比最后一段文本更接近真实状态。

每个事件应有单调序号、request id、call id、状态版本和幂等消费键。客户端收到 `tool_call_proposed` 但没有 `tool_started`，不能认为工具已经执行；收到 `tool_started` 但没有结果，状态应为未知。恢复器必须先查询执行器，再决定重试、补偿或人工接管。

## 19.18 observation 不是 instruction

工具观察可能来自网页、仓库、数据库、终端或用户上传文件。它们都是外部数据，除非经过策略层明确提升，否则不会获得系统指令的优先级。一个结构化 observation 可以包含：

```json
{
  "call_id": "c17",
  "source": {"kind": "repository", "revision": "r42"},
  "content_hash": "...",
  "trust_level": "untrusted_data",
  "facts": [{"field": "test_status", "value": "failed"}],
  "instructions": []
}
```

把事实、指令、来源、版本和可执行字段分开，可以减少 prompt injection 和误执行。大结果应通过分页或受控 artifact 引用传递，而不是无界地重新放进上下文。证据过期、权限变化或 hash 不匹配时，应阻止继续执行。

## 19.19 checkpoint 要保存“下一步是什么”

长任务 checkpoint 不能只保存最近一段文本。至少要保存当前状态、事件序号、未完成工具 call、已提交副作用、待验证 artifact、剩余预算、权限版本和用户取消状态。否则恢复后模型可能把已执行动作当成未执行，再次提交。

可以把恢复条件写成：

~~~math
\mathrm{resume}=1
\iff
\mathrm{event\_log\_valid}
\land\mathrm{state\_schema\_compatible}
\land\mathrm{policy\_still\_valid}
\land\mathrm{side\_effects\_reconciled}.
~~~

任何条件不满足，都应重新评估或人工接管。恢复成功表示状态可继续，不表示上一次请求的最终业务目标已经完成。

## 19.20 高风险动作采用两阶段提交

交错推理中的模型输出可能是草稿、建议或真正动作。协议应明确区分 `draft`、`approved`、`executed`、`verified` 和 `committed`。高风险动作可以使用两阶段提交：先展示目标、参数、影响范围和证据，再由 policy 或用户批准，最后以幂等键执行并查询结果。

```text
proposal -> policy check -> user/automatic approval
         -> execute with idempotency key
         -> query result -> verify -> commit
```

工具超时后不能直接重试写操作。对不可逆外部动作，补偿流程也不能假装回到未发生状态；用户应看到真实的已提交、处理中、失败或未知状态。

## 19.21 交错路径的成本账本

交错推理会增加 tool round、上下文回填、序列化、网络等待和 verifier 成本。对每个任务记录模型 token、工具调用数、工具等待、观察 token、重试、验证、人工等待和成功/失败。只比较最终回答质量，可能把十倍工具调用误判为免费能力提升。

与一次性计划相比，交错路径适合外部反馈会显著改变下一步的任务，例如调试、浏览、研究和状态恢复；对步骤固定且工具延迟极高的流水线，可以用预先编译的工作流减少 round trip。选择标准是单位成功成本和失败恢复，而不是“能不能多调用工具”。

## 19.22 端到端回归和对抗样本

golden suite 要覆盖空结果、部分返回、schema 错误、权限拒绝、页面变化、用户取消、模型重试、外部状态未知、缓存失效和提示注入。每个 case 验证事件顺序、最终状态、工具副作用、引用支持和用户可见解释。

发布前做 shadow 时可以计算交错路径，但不得执行真实外部副作用；canary 要限制工具 allowlist 和租户范围。高风险协议错误、重复副作用、未经授权动作和无法恢复的状态都应是 hard gate，不能用平均成功率抵消。

## 19.23 observation 的可信度和新鲜度

工具返回不是天然真相。网页可能过期，数据库可能在查询后发生变化，用户上传的文档可能包含诱导指令，外部 API 也可能返回部分成功。交错推理应为 observation 保存来源、时间、请求参数、权限、完整性校验和错误状态，并区分“工具声称成功”和“系统验证成功”。

可以把 observation 的可用性写成一个验收条件：

```math
V(o)=\mathbf{1}[\mathrm{source\_ok}]
\mathbf{1}[\mathrm{freshness\_ok}]
\mathbf{1}[\mathrm{schema\_ok}]
\mathbf{1}[\mathrm{permission\_ok}].
```

当 `V(o)=0` 时，模型可以知道证据不可用，但不能把它当作普通文本继续推理。这样既减少 prompt injection，也让“工具失败后继续猜”的行为变得可检测。

## 19.24 交错协议的最小事件序列

一个可审计的循环至少包含 `reasoning_started`、`tool_requested`、`tool_authorized`、`tool_returned`、`observation_verified`、`reasoning_resumed` 和 `action_committed`。事件必须带 request id、step id、tool call id、状态版本和幂等键。流式输出可以展示进度，却不能在 `action_committed` 之前宣称外部动作已经完成。

若客户端断开，runtime 应决定是取消、继续后台任务还是等待恢复，而不是默认重试最后一条 tool call。对于扣款、发信和写库等动作，只有在幂等状态明确时才允许恢复重试。

## 19.25 交错推理的成本归因

长思考、工具往返、解析、验证和人工审批都可能贡献延迟。报告端到端时间时应拆成 `T_model`、`T_tool`、`T_queue`、`T_verify` 和 `T_human`，并按成功任务而不是请求平均。一个看似模型变快的优化，可能只是把时间转移到了工具重试或人工队列。

## 19.26 交错循环的终止条件

循环应在目标已验证、预算耗尽、工具连续失败、没有新增证据、权限改变或达到最大步数时终止。把“模型还想继续”当作唯一继续条件，会让系统在没有信息增益时不断消耗资源。每种终止都应给出用户可理解的状态和内部 trace。

## 19.27 事件回放的最小断言

回放至少断言：tool call id 不重复、未授权工具不执行、observation 版本正确、grammar 状态与可见 token 一致、已提交副作用只出现一次、取消后没有新动作。最终文本相同但事件断言失败，仍应判定协议回归。

## 19.28 小结与资料边界

Interleaved thinking 的核心是让外部观察参与推理，而不是把模型关在一次长文本生成里。它带来更强的适应性，也带来协议、权限、幂等、成本和状态恢复问题。可验证的事件链、可信 observation 和可恢复 checkpoint 比可见的长思考文本更重要。

本章的状态机、工具调用和 Agent tracing 是通用工程抽象；具体 provider 如何表示 reasoning item、tool event 和 preserve state，应以版本化官方协议为准，未公开的内部推理表示不作推断。
