# 新知识扩充

本流程用于用户明确发起“新知识扩充”时，从新模型与能力评测信号中发现书系尚未覆盖的知识，并将经过证据核验、书系定位和章节设计的内容落实到合适书册及配套材料。它与“常态化全书精修”是两类独立任务：全书精修按现行规范系统检查已有书稿；新知识扩充以新模型/新能力为发现入口，最终交付的是可迁移的新知识及其书系落点，不是模型发布新闻汇编。

## 一、触发与范围

用户明确提出“新知识扩充”或同义任务时，按本流程执行，不将其误作全书精修。默认检查 24 册主书、`book-llm-engineer/` 补充篇及相关配套资料；本轮覆盖范围、时间窗口和优先主题写入对应 `progress/` 记录。用户指定厂商、主题或书册时按指定范围执行，同时标出因此未覆盖的部分。

常规关注的模型厂商/系列包括 OpenAI（GPT）、Google（Gemini）、Anthropic（Claude）、xAI（Grok）、Alibaba（Qwen）、DeepSeek、Moonshot（Kimi）和 Zhipu/Z.ai（GLM）。此列表是最低关注范围而非封闭名单；有重要新模型或技术的其他团队也可纳入。每轮记录实际检查到的厂商、模型、版本和未检查范围，不因模型未出现在榜单就推断没有新知识。

## 二、候选发现：榜单作雷达，不作结论

每轮检查以下发现入口，并记录访问日期、所用页面/榜单、模型标识及其展示的版本或配置。榜单的名称、分区、方法和更新状态可能变化，必须按当次页面核对，不沿用旧版排名或本规范中的历史描述。

| 入口 | 主要发现用途 | 使用边界 |
| --- | --- | --- |
| [Artificial Analysis](https://artificialanalysis.ai/) | 发现综合能力、特定任务表现、速度、价格和可用性变化明显的新模型 | 指数、单项评测、价格和速度口径各不相同；不能把综合分当成技术机制证据 |
| [Arena](https://arena.ai/)（原 LMArena / Chatbot Arena） | 发现匿名对战偏好、不同任务/模态或交互场景中用户体验突出的模型 | 核对具体榜单、投票量、置信区间、模型版本和当期排名方法；偏好信号不等于事实准确性、专业能力或生产可靠性 |
| [LiveBench](https://livebench.ai/) | 发现公开基准中近期题目、可验证任务或长程工作流表现值得追查的模型 | 记录具体版本、任务类别、数据/题目时间、评分和工具设置；不能把基准分数外推为普遍能力 |
| [OpenCompass / 司南](https://opencompass.org.cn/) | 发现中文及多维能力评测中的候选，覆盖其当期提供的语言、多模态、学术或竞技榜单 | 先确认具体榜单规则、数据集版本、评测协议和模型快照；不同子榜不可混为一个综合结论 |

可按主题使用其他专业榜单或评测入口作补充，例如代码、Agent、推理、长上下文、多模态、效率或安全评测。榜单只负责暴露候选和问题线索；榜单名次本身不能证明模型采用了某种新架构、训练配方、部署栈或 harness。

发现阶段既检查榜单中首次出现的模型，也检查已知厂商的新版本及其新披露。候选不必都位列榜首；关注显著能力变化、此前没有的任务能力、开源权重/代码发布、产品/API 行为变化，以及引发新术语或新工程实践的模型。

## 三、核验候选与挖掘新知识

### 1. 固定模型身份和评测条件

对每个候选建立可辨识的身份记录：厂商、模型家族、准确模型 ID/版本或快照、公开日期、访问日期、API/provider、模型配置、thinking/effort、工具权限、上下文限制、榜单/基准版本、harness、任务集和硬件/推理环境（若公开）。区分正式发布、预览、别名/滚动更新、开放权重与仅 API 可用；身份不清时不得把不同版本合并成同一证据对象。

排名比较先确认是否为同一任务、版本、prompt、工具、采样、预算及评分协议。不同榜单或榜单版本的数字不直接横比；缺失参数标为未知，不猜测或用厂商宣传补齐。

### 2. 从模型回溯一手资料

对候选模型检索并阅读可获得的原始资料，优先级按主张类型决定：

- 模型卡、技术报告、论文、官方发布/工程博客和官方文档：核对明确披露的模型、训练、能力与限制。
- 官方代码仓库、配置、权重说明、推理框架及固定 revision：核对可见实现和可复现配置。
- API、产品和服务文档：核对调用接口、工具、上下文、状态、计费、速率限制、兼容性和服务行为。
- 高质量研究者/工程博客、独立技术分析、课程 notes 与主流技术博客：发现机制解释、工程细节、术语关系、复现观察和争议，再将关键事实追溯至其可支持的原始依据。
- 榜单/基准论文、方法说明、数据集与 harness：核对排名结果究竟测量什么，以及版本、协议和边界。

对闭源模型严格区分官方披露、独立评测、代码观察、合理推断和社区猜测。没有公开证据的参数、训练配方、数据组成、硬件、生产 kernel、服务端实现和模型内部状态应明确记为未知，不以逆向推测写成事实。

### 3. 提取可迁移知识点

围绕新模型寻找技术增量，而不是复述产品特点。提取时采用“**先扫新名词，再按知识领域复核**”的双轨方式，不能只依赖下面的领域分类表，以免分类表没有预先列出的新机制、新流程或新接口被漏掉。

**新名词是高优先级的知识候选信号。** 新模型发布材料中首次出现、含义发生变化或被赋予特定技术含义的名词/短语，通常意味着需要调查的知识点，应先记录、查证和对照全书，而不是因它看起来像产品命名就跳过。优先收集：新造词、缩写及展开形式、方法/训练配方名称、架构组件与内部机制名称、推理/Serving runtime 名称、Agent/harness/工具协议对象、数据或评测集名称、API 对象/模式/功能名，以及厂商为既有技术采用的新标签。不要仅从标题抽词；应结合技术报告、模型卡、官方博客、文档、论文、仓库和主流技术分析中的定义、上下文与版本变化。

为每个候选术语建立可追溯条目，至少记下原始写法、来源与日期/版本、来源对术语的定义或实际用法、相关对象/机制/流程、与已有术语的关系、在书系中的查重结果和当前判断。用大小写、连字符、缩写/全称、中英文译法、旧称/别称及相近拼写扩展检索，防止术语变体漏检或重复建项。术语状态可判为：新概念/新机制、已知概念的新名称或变体、产品/API 合同、评测/harness 名称、营销性命名、含义未明/证据不足；状态允许随证据更新。

新名词提高的是“调查优先级”，不是“技术创新已证实”。如果它指向可核验的新机制、流程、约束、接口行为或工程决策，进一步提炼成可迁移知识点；如果只是品牌名、版本名或已知机制的重新包装，保留其命名与机制的对应关系，按读者需要记录产品/API 合同或别名，不把名称本身夸大为新方法。若来源未解释该词，记录“未公开/含义未核实”，继续寻找原始资料，不靠猜词补全。

然后再按以下开放式领域视角复核候选模型及术语。分类是帮助发现的透镜，不是封闭清单；任何未被下列分类覆盖、但经核验对读者有价值的新概念、流程、约束、接口、度量或系统实践，都必须保留为候选：

- **架构与模型机制**：新的层/模块、注意力或状态设计、MoE/路由、记忆、上下文扩展、多模态编码与信息流。
- **数据与训练**：数据合成/筛选、预训练目标、课程或配方、并行训练、数值精度、稳定性和可复现性。
- **后训练与对齐**：SFT、偏好优化、RL/RLVR、过程监督、蒸馏、合成数据闭环、奖励/验证器及其失效边界。
- **推理与部署**：解码、KV cache、量化、投机/并行推理、Serving、调度、硬件/内核、吞吐—延迟—成本取舍。
- **Agent、工具与 harness**：工具调用协议、执行环境、状态/轨迹管理、并行或多 Agent 协作、重试/恢复、评估与安全边界。
- **多模态、评测与可靠性**：新的输入输出或交互形态、长程任务、基准/harness 变化、校准、拒答、安全和真实使用限制。
- **新名词与产品/API 合同**：解释词语指向的机制或能力；判断它是稳定技术概念、厂商命名、产品功能还是临时营销标签。

上述领域是互相交叉的扫描维度，不要求每个模型都填满，也不限制新知识的范围。新名词必须逐项筛查；除名词扫描外，还要发现没有新命名、但技术实质已经变化的内容。经过证据核验后，能形成可迁移定义、机制、工程决策、适用条件、接口约束或重要争议的，才作为知识点纳入设计；纯型号、排名和无技术含义的宣传名称不自动构成技术知识，但其产品身份或合同若影响读者决策，仍可作为产品/API 信息记录。

## 四、对照全套书并决定去向

先建立候选知识点和候选新名词清单，再检查全套书的有效设计与正文，不得因榜单排名或新名称直接决定新增章节。新名词逐项检索书系目录、大纲、正文、术语表、研究记录及配套资料；同时按概念/机制而非只按字面查重，确认它是知识真正新增、已知概念新称、现有内容缺少该别名，还是产品/API 新合同。至少检索并阅读相关书册的 `总纲.md`、`目录.md`、章节大纲和正文；跨册候选还须检查相邻及配套资料。扫描记录应说明现有覆盖是充分、部分、仅提及、缺失、重复、过时还是边界不清，并记录检索路径、术语别名和判断依据，避免因只查概念或只查名称而漏项或重复。

每个知识点作出一种主要处置，并说明读者价值、理由和证据边界：

1. 更新现有正文中的过时事实或版本边界。
2. 深化现有章节中仅被提及或缺少机制/工程解释的内容。
3. 在现有章节结构可容纳时，先修订 02a 大纲，再由 02 补正文。
4. 当主题具有独立读者问题、足够知识深度且无法合理并入现有章节时，新建章节。
5. 当多个相关主题共同形成现有书系没有承接的独立读者任务，且现有书册定位无法容纳时，按 01 流程论证新书册；不得只为单一新模型或一个营销名称新建书册。
6. 主要落点已在别册时，在相关章节补必要回顾和交叉引用；避免重复主讲，并明确主讲册与协同册的职责。
7. 证据或成熟度不足、读者价值尚不明确时，暂存观察或排除，注明复查条件。

**结构决策顺序：**

- 仅更新现有正文事实、补充已有章节承诺内的机制，不改变章节职责：按有效 02a 大纲由 02 修订正文。
- 需要改变章节范围、标题、分工、顺序、拆并或新增章节：先确认书册定位仍支持该主题，再按 02a 修订设计，随后由 02 实施正文。
- 影响读者、书册核心承诺、知识版图、体量或跨册职责：先按 01 研究并修订书册总纲，再按 02a 设计目录/章节，最后由 02 写作。
- 新建书册：先完成 01 总纲与跨册论证，再开展 02a 全书设计及 02 正文，不跳过阶段门禁。

结构与正文方案需覆盖前后关联：指定知识主讲位置、前置回顾、相邻章节承接、跨册链接，以及必要的反向引用；判断是否同步简介、目录、摘要、面试题、练习、术语、项目、论文索引和知识图谱。

## 五、分阶段执行与交付

### 阶段 A：发现和研究

交付候选模型表、榜单/版本快照、来源检索记录和可迁移知识点清单。每项知识标注来源支持的事实、推断、边界、成熟度、时效风险和未解问题。联网发现的新知识和证据写入相应 `research/` 专题笔记；不把全书审阅进度写入 research。

### 阶段 B：书系映射和设计决策

在 `progress/` 建立全书覆盖矩阵和决策记录：候选知识点、现有落点、主要责任书册/章节、协同位置、处置决定、理由、影响范围、待办和验收条件。明确本轮是仅更新正文、修订 02a、修订 01 后重做 02a，还是新建书册。未经证据和结构映射，不批量生成貌似定稿的正文或章节。

### 阶段 C：设计与正文实施

按上述顺序分别执行 01、02a、02；不需要改变的上游阶段可以沿用现行设计，但要记录核对结论。新章节/书册在实施时写入 `写作规范/全套书不同册的章节大纲结构/<book-目录名>/` 中相应设计文件，并同步书稿目录和导航。正文按 02 及相关规范完成研究、机制解释、证据边界和适用条件。

### 阶段 D：协同同步与验收

更新主讲章节及协同章节的交叉引用；按读者价值同步面试题、练习、术语、项目、论文索引、知识图谱和其他手册。检查目录/大纲/正文一致性、链接、引用、公式、代码、版本日期和配套导航。公式/代码/图表依 04、05 验收。

每轮结束时交付：

- 本轮覆盖的榜单、厂商、模型/版本、时间窗和未覆盖范围。
- 新知识点及来源证据记录位置，以及各知识点纳入、暂存或排除决定。
- 更新后的书册/章节/配套落点；说明是否触发 01、02a、02，以及跨册协同情况。
- 执行和验收状态、未完成项、风险及复查条件。

## 六、证据、记录和停止条件

- 榜单快照、发现过程和编辑决定属于本轮工作记录，写入对应 `progress/`；可复用的新知识及来源、版本、证据等级和未验证边界写入 `research/`。不将研究事实堆入 `plan.md`。
- 使用源头材料支持源头能证明的主张；作者报告结果、独立重测、社区观察和实现推断分开标注。每条关键新知识应能回到具体原文、版本和相关段落/章节。
- 对候选的技术新颖性，需与全套书现行目录、大纲、正文和已存研究记录交叉检索。已有但过时的内容应标“需更新”，不能冒充“书系未提及”。
- 证据不足时可以继续观察，不为凑更新数量硬纳入。停止条件是关键事实与范围已核验、全书落点和决定已明确、继续检索预计不再改变结论或结构；这不代表穷尽所有公开信息。
- 新模型发布频繁时按影响和证据成熟度排序，记录时间截点。计划更新是截至该日期的有界扫描，不承诺实时捕获所有发布。
