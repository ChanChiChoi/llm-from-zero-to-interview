# 04：图表、公式、代码与引用

本模块规定表达形式的选择、技术写法和验证。是否需要某种形式由模块 02 的读者结果决定；本模块不设图、公式或代码配额。

## 6. 图表、公式、代码与引用呈现

### 6.1 图表与视觉表达

当关系难以从长段文字看清时，选择能显示该关系的形式：流程/因果用流程图，组件和数据传递用结构图，时序用时间线或时序图，状态变化用状态图/表，取舍用对齐的比较表，趋势/分布用带单位和条件的数据图，逐步过程用执行轨迹。

图表须在正文中引出，说明读法、关键条件和应观察的关系。不要依赖颜色传递唯一含义，不把推断画成事实，不把无关知识塞进一张表。图不能替代正文的因果解释。

GitHub Markdown 中的 Mermaid 使用顶层 `mermaid` 围栏和目标平台支持的语法。中文、空格或标点标签优先加引号，例如 `A["数据、目标与预算"]`；带字箭头使用 `A -.->|发现问题| B`。检查围栏和语法；若 GitHub 是交付平台，确认页面实际渲染。

可使用与主题直接相关的论文、报告、博客或官方材料图片。图片附近标明作者/机构、材料标题、图号/页码和链接；裁剪、翻译或添加标记时说明“改编自”。使用前核对版本、条件和结论。适用许可或版权要求时遵守其规定。

### 6.2 公式

公式须服务于准确表达关系、目标/约束、计算、比较、推导或一般化。方法定义、结论或推理依赖的公式应保留并讲清；若文字、图或例子已足够，就不为形式添公式。外部公式核对来源、假设和符号口径；自拟公式说明来源关系和用途。

公式放在读者知道它回答什么问题之后。使用前定义必要变量、对象、取值范围和假设；使用后说明它表示什么，以及它在当前流程中对应哪个机制。方法公式须区分模型、优化目标和算法计算。按主题补充会改变含义的数据口径、形状、单位、token/sequence/batch、mask 和求和/平均规则。需要推导时交代关键步骤；数值例子只有在帮助理解或复算时才需要。

#### MathJax 与 Markdown 约定

- 行内公式使用单美元定界 `$...$`，不得在公式内部换行，定界符内侧不加空格；不要用 `\\(...\\)`。复杂或多行表达式使用独立的 `math` 围栏。
- 块级 `math` 围栏顶格书写，前后留空行，不缩进放在列表或引用中。列表中的推导可将块公式移出列表，并在邻近文字说明对应步骤。
- 一切承担数学含义的变量、条件、算式、元组、向量、矩阵、比例、带单位计算和尺寸都用数学定界符；不要用反引号包数学表达式。反引号仅用于程序标识符、命令、文件名及按字面展示的代码。
- 连续列举的行内公式合并表达，或调整语序，避免公式定界符紧贴全角标点；必要时可在标点与 `$` 之间留一个普通空格。不要通过在定界符内加空格修复解析问题。
- 数学下标用下划线和大括号。避免 `x_{<t}` 等以 `<` 开头的下标，改用明确范围如 `x_{1:t-1}`；公式中小于号紧跟字母时可写 `\\lt`。希腊字母后的文字下标用分组，如 `\\Delta_{\\mathrm{ref}}`。
- 优先使用基础 TeX 函数和 `\\mathrm`；不用 `\\operatorname`。核对 `\\left`/`\\right` 成对且括号类型匹配；不要在 `\\text` 中放带下划线的程序变量或混入 HTML。
- 多个下标放在同一组，如 `$X_{i,j}$`；不要连续下标。矩阵放独立块公式，核对每行列数、`&` 列分隔符及 `\\\\` 行分隔符。
- 避免行内公式中的 Markdown/HTML 冲突字符。若必须保留字面 `&` 等字符，可用 GitHub 支持的 ``$`...`$``，并检查页面渲染。渲染异常时检查定界符相邻标点、HTML 冲突、下标和 TeX 配对，不要盲目改公式空格。

修改后检查定界符、围栏、变量定义、括号和 TeX 命令。若 GitHub 是读者入口，静态源码检查不能代替页面渲染确认。

### 6.3 代码与实验

代码不是每个知识点的必需形式。若章节承诺编码、API 调用、程序复现或操作任务，须交付相称代码/步骤、环境条件、输入输出和完成信号。其他代码可用于观察状态、复现小例子或比较实现；若代码不是最清楚的方式，改用过程追踪、图表或文字。

代码应与正文解释的任务和机制对应，并说明必要依赖、运行方式、关键 shape 和预期结果。声明范围内应能运行；按风险检查语法、正常路径和相关边界，不机械要求短例子套完整测试套件。片段或伪代码须标清，避免被误认为已执行。代码不能单独代替机制解释。

对独立运行或承担关键机制说明的代码块，标注状态：

- **已验证**：实际运行；正文简标日期、环境和必要依赖。
- **静态审阅，未运行**：只做阅读或 shape 推演。
- **待验证**：尚无可靠检查。

详细验证记录写入对应 `progress/` 条目，包括代码块标识、命令、环境、输入、预期/实际结果、检查范围和日期。正文代码及紧邻说明不出现维护路径或内部工作流。

已有验证可在代码执行语句、接口/输入输出约定、依赖/API、声明环境和承诺结果均未改变时沿用。可执行语句变化（纯空白排版除外）须重新验证该块；只验证受变化影响的依赖部分。环境、依赖或 API 改变时也只复验受影响范围。找不到可靠记录且未实际运行时，标为“待验证”或“静态审阅，未运行”，不得声称已验证。

### 6.4 引用、术语与正文边界

引用放在相关主张附近并直达原始论文、官方页面、固定 revision、release 或具体 benchmark。说明来源支持什么及其限制；引用列表不能替代证据解释。引用和证据边界按模块 03 管理。

只引入理解当前内容所需的术语。首次必要使用时给出一致的中文名、英文名或缩写，后续保持口径；model、configuration、revision、provider、effort、harness、benchmark 和 verifier 等层次不可混称。

目录承担索引和导航，不承载长篇正文。正式正文面向读者，可以含解释、推导、代码、限制、引用、教程、排障、面试题和练习；不得保留任务分派、联网计划、代理日志、会话状态、修改轮次或内部审计。这类记录归入 `progress/`。
