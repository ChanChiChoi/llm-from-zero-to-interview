# 图表、公式、代码与引用

> 本文件是《项目写作规范》的正式细则模块。原规范章节编号保留，供跨模块引用；本模块与总纲共同构成完整规范。

## 6. 图表、公式、代码与引用呈现

### 6.1 把视觉表达作为结构设计的一部分

整册审视和单篇精修都要检查：哪些关系用长段文字不容易看清，视觉表达能否让读者更快理解顺序、因果、依赖、状态、差异或数量。适合时应制作或引用图表；不设机械图数，也不为满足数量硬塞装饰图。

- 步骤、因果链和分支决策：流程图；
- 系统组件、张量变换和数据传递：结构图或数据流图；
- 调用顺序和时间演化：时序图或时间线；
- 状态变化：状态图或状态表；
- 方案取舍：对比表或决策表；
- 趋势、分布和数值关系：带坐标、单位、条件和来源的数据图；
- 逐步计算或实验过程：执行轨迹表、切片表或结果图。

需要在 GitHub Markdown 中展示的 Mermaid 图应放在 `mermaid` 代码围栏中，并使用目标平台支持的标准语法。节点标签含中文、空格或标点时，优先给标签加引号，例如 `A["数据、目标与预算"]`；带文字的箭头统一使用管道标签，例如 `A -.->|发现问题| B`，不要把文字直接夹在 `-.` 和 `.->` 之间。修改后检查代码围栏是否配对、图的语法是否有效；若 GitHub 是读者入口，应在 GitHub 页面确认图能正常渲染。遇到渲染错误时先检查对应图块及其语法，不能只因源码可见就视为图示验收通过。

图表需在正文中引出并说明读法、关键条件和读者应观察的关系。不能依赖颜色传达唯一含义，也不能把推断画成事实。表格应呈现有意义的维度关系，不能把不相关的知识点塞进同一行。

与主题高度契合的论文、技术报告、博客或官方材料图片，可以直接用于本书系的个人学习笔记，不必为了原创性重复绘制。图片附近标明作者或机构、材料标题、图号或页码和链接；裁剪、翻译或增加标记时注明“改编自”。使用前核对原图表达的条件、版本和结论与正文一致。

### 6.2 公式

公式不是每个知识点的必备形式；先按模块 02 §6 判断它是否能帮助读者从例子推广到一般关系、准确表达必要目标或约束，或支撑推导和计算。方法的定义、结论或推理依赖的公式应保留并讲清；若文字、图或算例已经能准确表达当前关系，就不必再添公式。论文或其他外部资料中的公式，只要服务于本章目标，可以核实来源、假设和符号口径后保留，并注明出处。作者自行整理或推导的公式，要能说明它从哪种关系概括而来、读者会用它做什么；没有明确作用时，用文字、图或例子说明，不要为了形式造公式。

优先使用 GitHub Markdown 可稳定渲染的 MathJax：行内公式统一使用单美元符号 `$...$`，不要用 `\(...\)` 作行内分隔符；复杂公式使用 `math` 围栏。公式要放在读者已经知道它要回答什么问题之后。写出公式前，定义读者理解它所需的变量、取值范围、数据对象和假设；公式后用普通语言说明它表达什么关系，以及它在当前训练、推理或系统流程中的位置。方法公式还要说清它描述的是模型、学习目标还是算法中的计算；比较不同方法时先对齐任务、数据条件和符号口径。涉及大模型时，补充会改变公式含义的 token/序列/batch 口径、形状、单位、求和/平均或 mask 条件。需要推导时交代关键推理；具体代入例子仅在能帮助读者理解或复算时使用，不把数值例子设为每个公式的门槛。单有公式、变量清单、直觉类比或代码输出都不算完成讲解。

行内公式必须完整写在同一物理行，不要在 `$...$` 中间换行；开闭 `$` 与公式内容之间不留空格，例如写 `$x_t$`，不要写成 `$ x_t $`。在中文句子里，避免让新公式的开头 `$` 紧跟全角标点，尤其不要写成 `、$a_3=1$`；连续列举多个量时，把它们合并到同一组公式中，例如 `$a_1=a_2=0,\;a_3=1$`，或调整语序，让公式出现在说明文字之后；若语义上仍需紧接标点，可在标点与开公式的 `$` 之间加一个普通空格，例如 `说明， $x$ 表示变量`。这个空格放在定界符外，不要塞进公式内部。若定界符成对、公式单行且内侧无空格，GitHub 仍显示 `$`，先检查定界符紧邻的中英文标点和连续公式边界，不要先往公式内部添加空格。需要换行的公式改用块级 `math` 围栏。块级公式应独立成块、围栏顶格书写，前后各留空行；为获得稳定的 GitHub 渲染，不要把 `math` 围栏缩进嵌在有序列表、项目列表或引用块中，以免 Markdown 容器解析使公式只显示源码。若步骤讲解中需要块级公式，可将步骤写成顶层的“步骤 N”段落，或把公式移出列表，并在相邻文字中说明它对应哪一步。

正文中凡是承担数学含义的符号、变量、条件、算式、元组、向量或矩阵，都必须明确放进 `$...$` 或块级 `math` 围栏；即使表达式很短、没有 TeX 命令，或看起来像普通括号与字母，也不能裸放在正文里。例如源码应写成 `前提： $\sum_{i,t}m_{i,t}>0$`、`对偏好样本 $(x,y^+,y^-)$`，而不是省略数学定界符。数学符号、变量、条件和算式也不要用反引号包成行内代码；反引号会让 GitHub 按字面显示其中的 `\sum`、下标和上标，不会交给 MathJax 渲染。行内数学应写成 `$\sum_{i,t}m_{i,t}>0$`、`$(x,y^+,y^-)$` 这样的 `$...$`；较长表达式使用块级 `math` 围栏。反引号只用于代码标识符、命令、配置键、文件名以及需要按原样展示的字面文本。若代码变量同时承担数学记号含义，正文中的变量表达仍用数学定界符；只有在讨论它作为程序里的具体标识符时才用反引号。也不要把 `\sum` 这类 TeX 源码裸放在普通正文中，除非明确是在讲解源码字符本身。

数学下标使用下划线和大括号。避免在下标中直接写以尖括号开头的表达式，例如 `x_{<t}` 或 `y_{<t}`。GitHub Markdown 在 MathJax 渲染前还会处理 Markdown/HTML；这种写法可能让 `<t` 被当作标签处理，造成 `Extra open brace or missing close brace` 一类看似大括号不匹配的错误。若源码中的花括号已经配对而页面仍报告括号错误，应重点检查下标中是否出现以 `<` 开头的片段，不要只反复补改花括号。优先改成明确的索引范围，例如 `y_{1:t-1}`，并在正文需要时说明范围含义。公式中的小于号若紧跟字母，也用 MathJax 命令 `\lt` 表示（例如把 `0<a` 写成 `0\lt a`），避免其被提前识别为 HTML 标签。优先使用基础函数和 `\mathrm`，不使用 `\operatorname`。希腊字母等 TeX 命令后不要直接拼接文字下标：TeX 会把连续字母解析为同一个控制词，例如应写 `\Delta_{\mathrm{ref}}`，不要写成 `\Deltaref`。含 `\left` 和 `\right` 的公式要按嵌套顺序逐层配对并核对括号类型，例如 `\left[\log\sigma\left(\cdots\right)\right]`；普通 `]` 不能代替 `\right]`。不要在 `\text` 中放带下划线的代码变量，也不要在公式中混入 HTML。修改后检查围栏配对、花括号、变量定义和渲染兼容性；若 GitHub 是读者入口，还要在 GitHub 页面确认实际渲染，源码静态检查不能代替页面核对。

### 6.3 代码与实验

代码作为讲解工具是可选的，不是每个知识点的必备配件。若小规模手算或过程跟踪已经更清楚，就不必为了配额写代码；若代码能让读者观察状态变化、复现例子或比较实现，则可用它加深理解。但章节一旦承诺读者要完成编码、调用 API 或复现程序，就必须提供与目标相称的代码，并说明环境条件和预期结果；若承诺的是配置或操作任务，就给出可执行步骤、环境条件和完成信号。不能把“代码可选”当作省略实作教学的理由。代码的目的在于帮助读者观察机制，不必伪装成完整论文复现、生产系统或硬件 benchmark。基础算法可以使用清晰的短实现；深度学习优先选择与概念直接对应、读者容易运行的框架。高频核心机制可先展示手写实现，再用成熟库说明工程封装。

代码若被选作讲解工具，说明它要完成的问题、输入输出、关键 shape、依赖、运行方式和预期结果；代码本身应与正文中的锚点或行为逻辑对应。代码用来加深和核对理解，不能单独代替讲解。若代码不是最清楚的表达方式，就用适合主题的例子、步骤、图表、状态变化或连贯文字解释，不要求一律补数值演算。代码应能在声明范围内执行；按规模和风险检查语法、正常路径及相关边界路径。低风险短例子不要求机械套用完整测试套件。

对可独立运行或承担关键机制说明的代码块，在代码块旁标明当前状态。首次完成执行验证后，标注“已验证”、验证日期、运行环境及必要依赖版本。状态标记只提供读者判断代码适用范围所需的信息，应简短清楚；正文的主要篇幅仍用于解释代码在解决什么问题、关键语句怎样对应机制。代码块及其紧邻的状态标记、说明和注释中，不得出现 `progress/` 等维护位置、内部记录路径或“复核记录见……”一类工作流引用；这类追溯信息只写入 `progress/` 中对应书册和章节的维护条目。代码块不适合写注释时，将状态标记放在代码围栏紧邻处。验证记录说明代码块位置或标识、运行命令、输入范围、预期与实际结果，以及检查过的关键边界。只有静态阅读或 shape 推演时，标为“静态审阅，未运行”；尚未检查时标为“待验证”。不得把静态审阅写成已验证。非独立可运行的片段应标明它是片段或伪代码，避免让读者误以为已执行。

后续精修先对照代码块及其验证记录，判断原验证是否仍适用。可执行语句、接口或输入输出约定、依赖/API、声明运行环境、正文承诺的预期结果均未改变时，沿用原验证记录，不重复运行；纯文字、空白排版或注释调整也不使验证失效。可执行语句只要发生变化（纯空白排版除外），就重新验证该代码块；若其变化影响其他代码块，再验证确实依赖它们的部分。环境、依赖或 API 变化也只复验受影响范围，不默认重跑整章。章节结构调整导致代码需要修改时，按修改后的范围重新验证并更新标记和记录。旧代码没有状态标记时，先查找 `progress/` 中已有的代码验证记录；不得仅因开始新一轮精修就批量重跑。找不到可靠执行证据时，如实标为“待验证”或“静态审阅，未运行”，在本轮实际改动代码或关键结论需要运行证据时再验证。

### 6.4 术语、目录与正文边界

只引入读者理解当前问题所需的术语，不为显示覆盖全面而罗列相邻概念。首次必要使用的术语应提供中文名、英文名或缩写，后续统一使用；model、configuration、revision、provider、effort、harness、benchmark 和 verifier 等层次不得混称。目录文件负责索引、阅读方式和导航，不承载长篇正文解释；章节拆分后应同步目录、交叉引用和入口链接。

正式正文面向读者，可以包含解释、推导、代码、案例、限制、引用、操作步骤、排障流程、面试问题和练习。不得包含作者指令、任务分派、联网计划、代理日志、修改轮次、会话状态、未完成任务或内部审计。发现有价值的工作要求时，应转换成读者能用的知识；进度和审计写入维护文件。
