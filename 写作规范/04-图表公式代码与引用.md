# 图表、公式、代码与引用

> 本文件是《项目写作规范》的正式细则模块。原规范章节编号保留，供跨模块引用；本模块与总纲共同构成完整规范。

## 6. 图表、公式、代码与引用呈现

### 6.1 把视觉表达作为结构设计的一部分

整册审视和单篇精修都要检查：哪些关系用长段文字不容易看清，视觉表达能否让读者更快理解顺序、因果、依赖、状态、差异或数量。适合时应制作或引用图表；不设机械图数，也不为满足数量硬塞装饰图。

- 步骤、因果链和分支决策：流程图；
- 系统组件、张量变换和数据传递：结构图或数据流图；
- 调用顺序和时间演化：时序图或时间线；
- 状态变化：状态图或状态表；
- 方案取舍：对比表或决策表；
- 趋势、分布和数值关系：带坐标、单位、条件和来源的数据图；
- 逐步计算或实验过程：执行轨迹表、切片表或结果图。

需要在 GitHub Markdown 中展示的 Mermaid 图应放在 `mermaid` 代码围栏中，并使用目标平台支持的标准语法。节点标签含中文、空格或标点时，优先给标签加引号，例如 `A["数据、目标与预算"]`；带文字的箭头统一使用管道标签，例如 `A -.->|发现问题| B`，不要把文字直接夹在 `-.` 和 `.->` 之间。修改后检查代码围栏是否配对、图的语法是否有效；若 GitHub 是读者入口，应在 GitHub 页面确认图能正常渲染。遇到渲染错误时先检查对应图块及其语法，不能只因源码可见就视为图示验收通过。

图表需在正文中引出并说明读法、关键条件和读者应观察的关系。不能依赖颜色传达唯一含义，也不能把推断画成事实。表格应呈现有意义的维度关系，不能把不相关的知识点塞进同一行。

与主题高度契合的论文、技术报告、博客或官方材料图片，可以直接用于本书系的个人学习笔记，不必为了原创性重复绘制。图片附近标明作者或机构、材料标题、图号或页码和链接；裁剪、翻译或增加标记时注明“改编自”。使用前核对原图表达的条件、版本和结论与正文一致。

### 6.2 公式

优先使用 GitHub Markdown 可稳定渲染的 MathJax：行内公式使用单美元符号，复杂公式使用 math 围栏。公式前定义变量、取值域和假设；公式后解释直觉、推导意图和适用条件。核心公式必须配一组完整的数值代入和逐步计算，让读者能从输入复算到结果；复杂公式可先用小规模数值例子拆开，再配表格或状态关系。只写公式、符号解释或代码结果不算完成数值讲解。

数学下标使用下划线和大括号。避免可能被 Markdown 当作 HTML 的尖括号下标，例如 x_{<t}，改用明确的索引范围。优先使用基础函数和 \mathrm，不使用 \operatorname；不要在 \text 中放带下划线的代码变量，也不要在公式中混入 HTML。修改后检查围栏配对、花括号、变量定义和渲染兼容性。

### 6.3 代码与实验

代码的目的在于帮助读者观察机制，不必伪装成完整论文复现、生产系统或硬件 benchmark。基础算法可以使用清晰的短实现；深度学习优先选择与概念直接对应、读者容易运行的框架。高频核心机制可先展示手写实现，再用成熟库说明工程封装。

每段代码说明它要回答的问题、输入输出和关键 shape、依赖及必要版本、运行方法、预期结果，以及教学实现没有覆盖什么。适合代码呈现的核心机制，应尽量复用正文手算例子的输入，让读者对照手算中间量、代码输出和公式；差异来自浮点精度或实现约定时要说明。代码用来加深和核对理解，不能代替可跟随的数字推演。读者还应知道改变哪个输入会如何影响结果。代码应能在声明范围内执行；按规模和风险检查语法、正常路径及相关边界路径。低风险短例子不要求机械套用完整测试套件。没有适合代码的主题，应提供可核对的数值推演、表格、状态轨迹或文本示意，不能只留抽象判断。

对可独立运行或承担关键机制说明的代码块，在代码块旁标明当前状态。首次完成执行验证后，标注“已验证”、验证日期、运行环境及必要依赖版本。代码块及其紧邻的状态标记、说明和注释中，不得出现 `progress/` 等维护位置、内部记录路径或“复核记录见……”一类工作流引用；这类追溯信息只写入 `progress/` 中对应书册和章节的维护条目。代码块不适合写注释时，将状态标记放在代码围栏紧邻处。验证记录说明代码块位置或标识、运行命令、输入范围、预期与实际结果，以及检查过的关键边界。只有静态阅读或 shape 推演时，标为“静态审阅，未运行”；尚未检查时标为“待验证”。不得把静态审阅写成已验证。非独立可运行的片段应标明它是片段或伪代码，避免让读者误以为已执行。

后续精修先对照代码块及其验证记录，判断原验证是否仍适用。可执行语句、接口或输入输出约定、依赖/API、声明运行环境、正文承诺的预期结果均未改变时，沿用原验证记录，不重复运行；纯文字、空白排版或注释调整也不使验证失效。可执行语句只要发生变化（纯空白排版除外），就重新验证该代码块；若其变化影响其他代码块，再验证确实依赖它们的部分。环境、依赖或 API 变化也只复验受影响范围，不默认重跑整章。章节结构调整导致代码需要修改时，按修改后的范围重新验证并更新标记和记录。旧代码没有状态标记时，先查找 `progress/` 中已有的代码验证记录；不得仅因开始新一轮精修就批量重跑。找不到可靠执行证据时，如实标为“待验证”或“静态审阅，未运行”，在本轮实际改动代码或关键结论需要运行证据时再验证。

### 6.4 术语、目录与正文边界

首次出现的术语应提供中文名、英文名或缩写，后续统一使用。model、configuration、revision、provider、effort、harness、benchmark 和 verifier 等层次不得混称。目录文件负责索引、阅读方式和导航，不承载长篇正文解释；章节拆分后应同步目录、交叉引用和入口链接。

正式正文面向读者，可以包含解释、推导、代码、案例、限制、引用、操作步骤、排障流程、面试问题和练习。不得包含作者指令、任务分派、联网计划、代理日志、修改轮次、会话状态、未完成任务或内部审计。发现有价值的工作要求时，应转换成读者能用的知识；进度和审计写入维护文件。
