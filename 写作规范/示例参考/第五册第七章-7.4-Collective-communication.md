## 7.4 Collective communication：数据怎样合并、分发和收集

先看两张卡上的一小组数字。把通信组里的卡暂时叫 rank 0 和 rank 1：rank 0 手里有 [1, 10]，rank 1 手里有 [2, 20]。如果把相同位置的数字相加，结果是 [3, 30]。接下来要问的不是“通信名词有哪些”，而是：谁参与这次相加，结果又要送到谁手里？这决定了该用哪一种 collective。

### 7.4.1 All-reduce

在刚才的例子里，rank 0 和 rank 1 都得到完整的 [3, 30]。这种“大家一起聚合，再让每个 rank 都拿到结果”的操作叫 all-reduce：reduce 是合并，all 表示组内每个 rank 都收到结果。设通信组有 $N$ 个 rank，第 $q$ 个 rank 的输入为 $x_q$；求和形式下，每个 rank $r$ 收到的结果 $y_r$ 是：

~~~math
y_r
=
\sum_{q=1}^{N}
x_q
\qquad
\text{for every }r
~~~

DDP 用这种方式同步对应模型参数的梯度：每张卡根据本地数据算梯度，all-reduce 后按框架约定求和或平均，再用合并后的梯度更新。例子里的 [1, 10] 和 [2, 20] 可以看成两张卡上对应参数的梯度；若它们代表不同参数，就不能相加。

### 7.4.2 Reduce-scatter

还是用刚才的数字。相加后得到 [3, 30]；如果不需要每张卡都保留完整结果，就把它切成两段：rank 0 只拿 [3]，rank 1 只拿 [30]。先合并对应位置，再把不同结果分给不同 rank，这叫 reduce-scatter：

~~~text
输入: rank 0 [1, 10]，rank 1 [2, 20]
逐位置相加: [1+2, 10+20] = [3, 30]
切成两片: rank 0 收到 [3]，rank 1 收到 [30]
~~~

名字可以按动作理解：reduce 是把数值合起来，scatter 是把结果分片发开。ZeRO-2/FSDP 可以用 reduce-scatter 分发梯度；每张卡只留下自己负责的那一片，不必都存完整梯度。

### 7.4.3 All-gather

现在反过来：rank 0 手里只有 [3]，rank 1 手里只有 [30]。把两段收集起来，并让两张卡都拿到 [3, 30]，叫 all-gather。每个 rank 交出自己的那一片（shard），组内每个 rank 都收到完整集合。FSDP 计算一个被它管理的模块前，常要把这个模块的参数分片 all-gather 成完整参数。

完整参数会暂时出现在 GPU 上，所以判断显存够不够，不能只看平时留下的那份 shard；还要看模块聚齐参数时的峰值。

### 7.4.4 All-to-all

all-to-all 可以从“每个 rank 按收件人分包”来理解。假设 rank 0 上有 token A、B，rank 1 上有 token C、D；路由器把 A、C 分给 rank 0 上的 expert，把 B、D 分给 rank 1 上的 expert。交换后，rank 0 收到 A、C，rank 1 收到 B、D。每个 rank 都把不同数据发给不同 rank，也从它们那里收到各自的数据，这就是 all-to-all。MoE 的一轮 token dispatch 按这个顺序发生：

~~~text
router 给每个 token 选 expert
  -> 按 expert 所在的 rank 把 token 的模型内部表示（hidden state）分组
  -> all-to-all 把每组送到对应 rank
  -> expert 处理收到的 token
  -> 再按原来的归属把结果送回去
~~~

因此，MoE 的 all-to-all 不能只看总共传了多少字节。如果多数 token 都去了同一个 rank，它要处理的工作就会更多；分组、消息数量和卡之间的连接方式也会影响速度。

### 7.4.5 Broadcast、send/recv 和 barrier

- **broadcast**：rank 0 有一个配置值，比如学习率 0.001；broadcast 把这个值发给组内所有 rank。它解决“大家都要拿到同一份数据”的问题。
- **send/recv**：rank 0 把一份张量发给指定的 rank 1，rank 1 接收它。Pipeline Parallel 的相邻 stage 常用它传递激活值。
- **barrier**：所有 rank 都到达同一个同步点后，才一起继续。可以把它想成一群人约好在路口等齐再走；如果 rank 1 先到，它仍要等较慢的 rank 0。barrier 不会减少工作量，也不会修正错误的通信组或调用顺序。排查慢任务时，先找出谁在等谁，不要随手加 barrier 把等待藏起来。

### 7.4.6 Ring all-reduce 的量级

先用 4 个 rank 手里的小向量看清 ring all-reduce 的两个阶段。约定数据沿着 `rank 0 → rank 1 → rank 2 → rank 3 → rank 0` 传递，每个元素按 4 字节计算：

~~~text
rank 0: [1, 10, 100, 1000]
rank 1: [2, 20, 200, 2000]
rank 2: [3, 30, 300, 3000]
rank 3: [4, 40, 400, 4000]
~~~

目标是把相同位置的数相加，得到 `[10, 100, 1000, 10000]`。第一阶段叫 reduce-scatter（归约后分片）：把每个向量切成 4 段，让每一段沿环传递；每到一张卡，就加上这张卡上相同位置的数。先跟踪第一段：rank 0 把 `1` 传给 rank 1，rank 1 加上自己的 `2` 得到 `3`；`3` 再传给 rank 2，加上 `3` 得到 `6`；最后传给 rank 3，加上 `4` 得到 `10`。走完 3 步，这一段的总和 `10` 留在 rank 3。其他三段同时沿环传递，只是起点错开；走完后，每个 rank 各留一段已经求完和的数据：

~~~text
rank 0: 第 2 段 = 10 + 20 + 30 + 40 = 100
rank 1: 第 3 段 = 100 + 200 + 300 + 400 = 1000
rank 2: 第 4 段 = 1000 + 2000 + 3000 + 4000 = 10000
rank 3: 第 1 段 = 1 + 2 + 3 + 4 = 10
~~~

此时每张卡只拿到总和的一段，还没有完整向量。第二阶段叫 all-gather（收集全部分片）：每张卡把自己这一段沿环发给下一个 rank；收到新分片后，再把它继续传下去。以 rank 0 为例，它起初有第 2 段 `100`；第一步后收到第 1 段 `10`，接下来两步又收到第 4 段 `10000` 和第 3 段 `1000`，最后也得到 `[10, 100, 1000, 10000]`。其他 rank 同样收齐这四段。这样，两个阶段合起来就是：先分头算完各段的总和，再把各段拼回每张卡。

这个小例子里，每个 rank 的向量有 4 个数，也就是 16 字节。每一步每张卡发送一个数（4 字节）；reduce-scatter 走 3 步，发送 12 字节，all-gather 再走 3 步，也发送 12 字节。把同样的过程放大到每个 rank 同步一个 8 MiB（8×1024² 字节）的向量：每一步发送向量的四分之一，也就是 2 MiB；每个阶段走 3 步，因此每个阶段发送 6 MiB，两阶段合计每个 rank 发送 12 MiB，接收量也约为 12 MiB。对一般的 N 个 rank、每 rank 同步 S 字节，单个 rank 的发送量约为：

~~~math
C_{\mathrm{ring}}
\approx
2\frac{N-1}{N}S
~~~

这里的 $S$ 是每个 rank 要参与同步的数据大小。公式把每阶段的 $N-1$ 步、每步 $S/N$ 字节，以及 reduce-scatter 和 all-gather 两个阶段加在一起。代入 $N=4$、 $S=8\ \mathrm{MiB}$，得到 $2\times3/4\times8=12\ \mathrm{MiB}$，正好是每个 rank 的发送量；接收量也约为 $12\ \mathrm{MiB}$。公式没有把发送和接收加成一个数，也不是全系统的总流量。固定 $S$ 时， $N$ 越大，每个 rank 的发送量越接近 $2S$。它只是经典 ring 算法的流量估算，不能直接告诉我们训练一步要花多久，也不是所有 collective 的统一通信下界。启动延迟、链路争用、节点内外拓扑和与反向传播的重叠都会影响时间；NCCL 也会按拓扑选择算法，因此这个公式不是对所有 NCCL 运行时间的承诺。[NCCL collective overview](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html)

### 7.4.7 $\alpha$-$\beta$ 通信模型

上面的 ring 例子只数“要搬多少字节”。实际通信还要花时间启动消息。比如同样传 4 MiB，作为一条大消息发送只付一次启动成本；切成四条 1 MiB 消息，就要付四次启动成本。小消息很多时，启动成本可能很显眼；大消息则更容易受链路带宽限制。令 $\alpha$ 表示每条消息的启动/同步成本， $n_{\mathrm{msg}}$ 表示消息数， $B_{\mathrm{bytes}}$ 表示传输字节数， $\beta$ 表示协议对有效带宽的影响系数。这个简化时间模型写成：

~~~math
T_{\mathrm{comm}}
\approx
\alpha n_{\mathrm{msg}}
+
\frac{\beta B_{\mathrm{bytes}}}{\mathrm{link\ bandwidth}}
~~~

用一组假设值代入：令 $\alpha=0.25$ ms、 $\beta=1$，有效链路带宽为 4 GiB/s；此处取 $\beta=1$，不额外计协议折损。4 GiB 等于 4096 MiB，所以搬运 4 MiB 的传输时间约为 $4/4096$ 秒，即 0.977 ms。传一条 4 MiB 消息，总时间约为 $0.25+0.977=1.23$ ms；若把相同的 4 MiB 分成四条 1 MiB 消息，并假设它们依次发送，总时间约为 $4\times0.25+0.977=1.98$ ms。两种情况传的字节数相同，差别来自四条消息要付四次启动成本。这里的数值只为演示公式，且假设消息串行；真实通信可能并行分块或与计算重叠，不能用这笔账精确预测训练时间。

模型把固定启动成本和随字节数增长的传输成本分开，适合比较量级，不足以精确预测单步训练耗时，因为通信可能分块、并行或与计算重叠。
