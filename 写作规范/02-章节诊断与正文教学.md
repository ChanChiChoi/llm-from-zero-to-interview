# 章节诊断与正文教学

> 本模块的首要检查对象是读者能否跟着讲解得到一个结果。事实、来源、公式、代码和维护门禁分别见模块 03—05。

## 1. 先诊断读者卡在哪里

| 读者表现 | 常见原因 | 修改方向 |
| --- | --- | --- |
| 记住了很多名词，却说不出它们的关系 | 缺少一个贯穿本节的问题或整体图 | 先用几句话或一张图说明输入、目标、机制和结果，再展开细节 |
| 看懂了每个公式，但不知道为什么要写它 | 符号和目标突然出现，动机或推导跳步 | 先解释要计算什么，再定义符号、代入例子并解释结果 |
| 读到实现细节就失去主线 | 核心机制与版本、配置、边界混在同一层 | 先讲完主线，把非必要的实现深度标为选读 |
| 每节都认识，但章节结束后不能复述 | 小节互不承接，结论没有回收 | 重排因果顺序，节首说明问题，节末回扣主线并过渡 |
| 代码能运行，却不知代码在算什么 | 代码替代了数值推演或输入输出解释 | 先手算一轮，再让代码复现同一组输入 |
| 前置章节看过，仍不知道当前术语 | 把跨章引用当作当前讲解的替代 | 在需要处用一两句话唤回必要概念，再提供深入链接 |
| 知道本章讲了什么，却不明白它为什么属于这册书 | 章节目标没有连接到书册承诺 | 写清书册能力目标、本章贡献和本章结果，再决定小节取舍与顺序 |

## 2. 一篇只回答一个主要问题

改写前先回看本册目标，并写出两句话：“本章怎样帮助读者达到本册承诺的能力？”“读者读完本篇后，应该能解释、推算或完成什么？”正文中的每一节都要推进本章结果；每个核心知识点都要说明它在回答主问题中承担什么作用。若一篇同时承担多个独立问题，应拆章、分讲或明确主线与选读。

建议先列出：

- 读者进入本篇时已知的概念；
- 本篇新引入的一个核心想法；
- 各节或知识点分别贡献什么，哪些内容可以移至选读或其他入口；
- 必须经过的推理步骤；
- 最后一个完整例子和读者结果；
- 本篇没有展开、但读者可能想继续读的内容。

开篇应从读者遇到的现象、问题或小例子引入；说明为什么需要当前概念，以及本篇将回答什么。避免先堆缩写、文献名或技术分支，再要求读者自行拼出问题。这里的规划清单用于作者备课，不要求正文按清单顺序展开。

## 3. 方法章节的默认顺序：问题—定义—目标—推导—算例—局限

讲解算法、训练方法或统计学习方法时，默认沿着读者理解一个方法所需的因果顺序组织：

1. **问题**：先说明要解决的具体问题、输入和预期输出，以及现有做法为什么不够。可以用一个小场景引出，但先让读者知道问题是什么。
2. **定义与假设**：定义本节要用的对象、变量和关键术语；说明模型假设、数据条件、固定量与待学习量。只引入后续推理需要的内容。
3. **目标函数**：说明怎样才算把问题解决得更好，再写出损失、奖励、约束或其他优化准则。解释它和任务目标的对应关系，以及优化方向。若方法没有显式目标函数，应说明实际使用的判断准则，不要为了套模板虚构公式。
4. **推导**：从定义、假设和目标出发，逐步说明公式或机制为何成立。保留影响理解的中间步骤，交代关键假设在哪里起作用；不能只给结论公式或口头声称“可得”。
5. **算法步骤（适用时）**：在推导之后说明怎样计算、训练或生成，把目标转成可执行的步骤。区分目标函数规定“什么结果更好”，算法规定“怎样得到结果”。
6. **算例**：用一组小而完整的数据复算关键量，列出必要的中间结果，并解释数值意味着什么。算例应复用前文的变量和对象；若讲的是大模型方法，应指出这些数对应训练或生成流程中的哪一步。
7. **局限**：说明方法依赖哪些假设、适用于什么条件、会付出什么代价、在哪些情况下可能失败，以及这个算例或证据不能证明什么。
8. **回收**：简短回答开篇问题，并交代本方法与下一步内容的关系。

以上顺序是方法讲解的默认推理路线，不是固定目录模板。按内容和读者前置调整顺序没有问题；只要把关键因果关系讲清，让读者知道问题怎样引出定义、目标怎样引出求解、例子和局限又说明了什么。标题应服务于这条讲述，不必逐项照搬八个步骤。

理解或比较一种方法时，反复用三问把思路串起来：

- **模型表示什么？** 它接收什么输入、给出什么输出，假设了数据或任务中的什么关系？
- **学习目标（优化准则）是什么？** 什么结果被认为更好？使用什么损失、奖励、约束或判断准则，为什么与任务目标相符？
- **算法怎样实现这个目标？** 它怎样用数据和目标得到参数或结果？关键步骤、资源代价和可能的近似是什么？

这三问是跨章节理解和比较方法的共同坐标，不是要求各册采用同一种章节模板。比较方法时，先对齐共同问题和条件，再比较它们的表示与假设、目标、求解过程、证据、适用场景、优势、代价和失败边界。若一种新方法声称改进旧方法，应说明它改了表示、目标还是算法，解决了旧方法的哪个限制，又引入什么代价或未解决问题。

以深度学习为例，模型可以是网络结构或概率分布，目标可以是损失、正则项或奖励，算法可以是反向传播、优化器更新或采样流程；三者不要混称。

## 4. 其他内容类型使用合适结构

| 内容类型 | 建议讲解顺序 |
| --- | --- |
| 概念或架构 | 现象/问题 → 直觉 → 对象和术语 → 机制与因果 → 小例子/图 → 能解释什么、不能解释什么 |
| 系统或工程机制 | 请求/数据从哪里来 → 经过哪些状态和组件 → 资源或接口怎样变化 → 观察什么信号 → 失败时如何定位 |
| 项目或实战 | 任务目标 → 输入与验收条件 → 数据/状态 → 实现步骤 → 输出与评估 → 失败、复现和交付 |
| 论文解读 | 研究问题 → 前人方法的限制 → 作者提出的机制 → 证据支持什么 → 局限与未验证问题 |
| 方案比较 | 共同问题和条件 → 各方案机制 → 可比较证据 → 成本与适用场景 → 无法比较的部分 |

这些是读者路径，不是必须逐项写成标题。小节标题应表达问题或推进步骤，不应机械地重复“背景、定义、优缺点、总结”。

## 5. 控制阅读节奏和术语密度

- 先用普通语言说明要点，再引入术语；首次出现时给中文名、英文名或缩写，并立即说明它在当前问题中的作用。
- 一次只引入后续推理必需的新概念。术语、符号和缩写集中出现时，拆开讲或先给一个具体例子。
- 对大模型初学者，不能假设读者已经熟悉大模型数据流。按本节需要解释术语，不要求一口气补成术语表。例如，可先用一段话交代文本如何经分词器变成 token 和 token ID，模型如何给下一个 token 计算分数与概率，训练如何把预测和目标 token 比较成损失并更新参数，生成时又如何选出 token 并接回上下文。引入 prompt、上下文窗口、logits、注意力掩码、监督微调、偏好对、策略模型、参考模型、奖励模型等术语时，要说明它在当前流程中的位置，并区分容易混淆的相邻概念：token 不等于词或汉字，logits 是归一化前的分数而不是概率，模型给出的高分或偏好奖励也不等于回答已被事实验证；prompt 是输入上下文，completion 是模型续写的回答。
- 解释目标函数时，把数学量对应到训练信号或生成行为。例如讲 next-token 交叉熵时，说明模型给正确目标 token 的概率越低，惩罚通常越大；说明多 token 损失如何从各位置汇总，以及 padding 或被 mask 的位置是否计入。讲偏好或强化学习目标时，说明它比较哪些回答、优化哪个模型、奖励方向是什么，以及策略模型、参考模型和奖励模型各自负责什么；有参考约束时解释其作用，不把偏好分数说成真实性标签。具体公式仍按本节方法的定义和假设推导，不以这些直觉句替代数学说明。
- 公式出现前说明它在当前问题中要计算或约束什么，并把变量对应到真实对象；出现后解释每一项、优化方向和它在训练或生成流程中的作用。大模型公式应特别说清按 token、序列还是 batch 计算，求和还是平均，padding 或被 mask 的位置是否参与，以及概率、log 概率、分数、损失和奖励各自代表什么。推导保留会改变理解的中间步骤。
- 核心内容先讲完，再放非必要的版本差异、研究分歧、罕见边界或工程配置。确需提前说明的边界留在主线。
- 关键 caveat 必须贴近结论；一般性背景、深入实现和延伸研究可放进清楚标记的“进阶”或“继续阅读”部分。
- 对同一机制，尽量贯穿同一个小例子和同一套符号。新例子要说明它比前例多展示了什么。

不是所有段落都需要类比。类比能帮读者建立直觉时使用，同时说明它在哪一步失效；不能用类比代替定义或推导。

## 6. 公式与可复算例子

每篇核心知识讲解至少要有一个完整例子，使读者能从给定输入走到结果。方法和算法适合手算时，列出变量、单位、每一步和关键中间量；系统内容可追踪一条请求、一次状态变化或一份资源账本。代码不代替讲解，代码与例子适合时使用同一组输入。

公式必须回答正文中的一个具体问题，而不是作为知识装饰。解释概率、向量、目标函数和梯度时，用读者已知的数学概念作必要连接；大模型公式还要把符号接回具体的 token、序列、模型输出、训练信号或生成步骤。近似值、玩具数据和假设条件须标明。

篇幅没有统一的字符数门槛。过短时检查是否省略了动机、术语、关键步骤或例子；过长时找出重复、并列主题和非必要深度。修改目标是完整但不累赘的解释，不是达到字数。

## 7. 深度内容怎样进入主线

核心知识点应根据主题，把它的背景和来龙去脉、要解决的问题、必要假设、工作机制、适用场景、优势、代价、局限和可改进之处连起来讲，并说明它们怎样服务于章节结果。这是组织解释的思路，不是每篇都要逐项设标题的清单；不适用的维度不必硬凑。模型、学习目标和算法三问用于方法讲解，其他内容类型按自身机制说明目的、过程、条件和结果。专家关心的证据、替代方法、实现差异和失败边界也沿着前文的问题出现。只有会改变读者对核心结论的理解时才放入主线；否则列为进阶，保留准确链接。

来龙去脉不是按年份罗列技术名词。需要讲技术演进时，说明前一种方法面对什么问题、新方法改变了哪项表示/目标/算法、证据支持什么改进、还留下哪些限制。不得把改进说成无条件进步，也不得把来源支持的局部结果写成普遍规律。

## 8. 章节完成前做一次读者检查

不用字符数、标题数、引用数或代码块数量代替可读性判断。沿本篇主线检查：

1. 只具备本篇声明前置的读者，能否说出开篇问题和本篇结果？
2. 读者能否说出本章怎样推进本册承诺的能力，各节是否都在帮助本章回答中心问题？
3. 读者能否用自己的话解释核心机制，而不只是复述术语？
4. 对方法类内容，读者能否回答模型表示什么、优化什么目标、算法怎样实现目标？
5. 读者能否复算本篇例子，或追踪具体输入经过系统后的变化？
6. 每个小节是否说明它怎样接上前文、交给后文什么？
7. 初读者读主线时，是否会被可选的专家细节打断？
8. 专家需要的来源、假设和边界是否仍可追溯？

若答案是否定的，优先重排和补桥接解释；不要先添加更多术语、例子或资料。

## 9. 让正文保留作者的讲述声音

读者看到的应是一段有人在解释、有判断、讲得通的正文，而不是把规范项目逐条填满的报告。作者可以用清楚的判断和过渡带路，不必刻意写成聊天，也不必频繁自称“我们”。

- 在读者最可能产生疑问的地方停一下，把疑问说具体并回答它。不要只给定义或结论，也不要用一串问题代替解释。
- 让段落之间有真实的关系：前一段提出的困难，如何引出下一段的定义、公式或例子；例子又验证或修正了什么直觉。少用没有实际承接作用的“下面我们来介绍”“综上所述”“为后文打下基础”等套句。
- 让作者的判断落在具体内容上：说明哪个假设在这里起作用、某个例子能支持什么结论、一个限制会影响谁。判断要有理由和证据；不能用虚构的亲身经历或夸大的口吻制造亲切感。
- 术语、表格、标题和清单只在能帮读者看清关系时使用。规范里的提问是作者检查理解的工具，可以在一段连贯解释中同时回答多个问题，不必逐项设标题，也不要把同一层意思反复改写成段首提示、段末总结和章节小结。
- 朗读关键段落，听听是否像一个耐心的教师在解释眼前这个问题：句子是否接得上，例子是否真的做了说明，结论是否来得自然。若一句话可以原样放进很多不相关的章节，通常需要换成针对本章对象的解释，或删去。

“有人味”来自作者愿意替读者作取舍、把推理说完整、诚实交代边界，不等于随意口语、拟人化模型或堆叠故事。检查清单是写作后台，正文负责把知识讲成一条读者愿意跟下去的路。
