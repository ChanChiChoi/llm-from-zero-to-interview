# 章节诊断与正文教学

> 本模块的首要检查对象是读者能否跟着讲解得到一个结果。事实、来源、公式、代码和维护门禁分别见模块 03—05。

## 1. 先诊断读者卡在哪里

| 读者表现 | 常见原因 | 修改方向 |
| --- | --- | --- |
| 记住了很多名词，却说不出它们的关系 | 缺少一个贯穿本节的问题或整体图 | 先用几句话或一张图说明输入、目标、机制和结果，再展开细节 |
| 看懂了每个公式，但不知道为什么要写它 | 符号和目标突然出现，动机或推导跳步 | 先解释要计算什么，再定义符号、代入例子并解释结果 |
| 读到实现细节就失去主线 | 核心机制与版本、配置、边界混在同一层 | 先讲完主线，把非必要的实现深度标为选读 |
| 每节都认识，但章节结束后不能复述 | 小节互不承接，结论没有回收 | 重排因果顺序，节首说明问题，节末回扣主线并过渡 |
| 代码能运行，却不知代码在算什么 | 代码替代了数值推演或输入输出解释 | 先手算一轮，再让代码复现同一组输入 |
| 前置章节看过，仍不知道当前术语 | 把跨章引用当作当前讲解的替代 | 在需要处用一两句话唤回必要概念，再提供深入链接 |
| 知道本章讲了什么，却不明白它为什么属于这册书 | 章节目标没有连接到书册承诺 | 写清书册能力目标、本章贡献和本章结果，再决定小节取舍与顺序 |

## 2. 用中心问题串起多个知识点

改写前先回看本册目标，并写出两句话：“本章怎样帮助读者达到本册承诺的能力？”“读者读完本篇后，应该能解释、推算或完成什么？”一章应有一个中心问题和一条清楚主线，但中心问题可以由多个前后相连的小问题构成，也可以需要多个知识点才能回答。正文中的每一节都要推进本章结果；每个核心知识点都要说明它在回答主问题中承担什么作用。中心问题用于组织知识，不用来限制知识点数量或章节覆盖面。

若一章承担多个互不依赖的读者结果，应考虑分章。若这些结果彼此相关，但为讲清所需的知识、推导、实现或评估已超出一章能连贯承载的范围，也应扩章或拆成连续篇章；可以用上、中、下篇，也可以采用更自然的章节标题。拆分的目的在于让每篇都能讲清一个阶段并交付读者结果，不能把必要内容降为选读或删掉来维持原有章数。只有主题和依赖确实适合时才拆分，不按篇幅机械切段；拆分后说明各篇边界、依赖、承接和导航。

建议先列出：

- 读者进入本篇时已知的概念；
- 本篇需要讲清的核心知识点（可以有多个），它们之间的依赖关系，以及各自对读者结果的贡献；
- 各点需要达到的解释层级：核心内容、理解主线所需的支撑内容、进阶支线，以及有明确去向的范围外内容；
- 哪些内容可以移至选读或其他入口，移出后读者是否仍能完成本章承诺；
- 必须经过的推理步骤；
- 最后一个完整例子和读者结果；
- 本篇没有展开、但读者可能想继续读的内容。

开篇应从读者遇到的现象、问题或小例子引入；说明为什么需要当前概念，以及本篇将回答什么。避免先堆缩写、文献名或技术分支，再要求读者自行拼出问题。这里的规划清单用于作者备课，不要求正文按清单顺序展开。

## 3. 方法章节的默认顺序：问题—定义—目标—推导—算例—局限

讲解算法、训练方法或统计学习方法时，默认沿着读者理解一个方法所需的因果顺序组织：

1. **问题**：先说明要解决的具体问题、输入和预期输出，以及现有做法为什么不够。可以用一个小场景引出，但先让读者知道问题是什么。
2. **定义与假设**：定义本节要用的对象、变量和关键术语；说明模型假设、数据条件、固定量与待学习量。只引入后续推理需要的内容。
3. **目标函数**：说明怎样才算把问题解决得更好，再写出损失、奖励、约束或其他优化准则。解释它和任务目标的对应关系，以及优化方向。若方法没有显式目标函数，应说明实际使用的判断准则，不要为了套模板虚构公式。
4. **推导**：从定义、假设和目标出发，逐步说明公式或机制为何成立。保留影响理解的中间步骤，交代关键假设在哪里起作用；不能只给结论公式或口头声称“可得”。
5. **算法步骤（适用时）**：在推导之后说明怎样计算、训练或生成，把目标转成可执行的步骤。区分目标函数规定“什么结果更好”，算法规定“怎样得到结果”。
6. **算例**：用一组小而完整的数据复算关键量，列出必要的中间结果，并解释数值意味着什么。算例应复用前文的变量和对象；若讲的是大模型方法，应指出这些数对应训练或生成流程中的哪一步。
7. **局限**：说明方法依赖哪些假设、适用于什么条件、会付出什么代价、在哪些情况下可能失败，以及这个算例或证据不能证明什么。
8. **回收**：简短回答开篇问题，并交代本方法与下一步内容的关系。

以上顺序是方法讲解的默认推理路线，不是固定目录模板。按内容和读者前置调整顺序没有问题；只要把关键因果关系讲清，让读者知道问题怎样引出定义、目标怎样引出求解、例子和局限又说明了什么。标题应服务于这条讲述，不必逐项照搬八个步骤。

理解或比较一种方法时，反复用三问把思路串起来：

- **模型表示什么？** 它接收什么输入、给出什么输出，假设了数据或任务中的什么关系？
- **学习目标（优化准则）是什么？** 什么结果被认为更好？使用什么损失、奖励、约束或判断准则，为什么与任务目标相符？
- **算法怎样实现这个目标？** 它怎样用数据和目标得到参数或结果？关键步骤、资源代价和可能的近似是什么？

这三问是跨章节理解和比较方法的共同坐标，不是要求各册采用同一种章节模板。比较方法时，先对齐共同问题和条件，再比较它们的表示与假设、目标、求解过程、证据、适用场景、优势、代价和失败边界。若一种新方法声称改进旧方法，应说明它改了表示、目标还是算法，解决了旧方法的哪个限制，又引入什么代价或未解决问题。

以深度学习为例，模型可以是网络结构或概率分布，目标可以是损失、正则项或奖励，算法可以是反向传播、优化器更新或采样流程；三者不要混称。

## 4. 其他内容类型使用合适结构

| 内容类型 | 建议讲解顺序 |
| --- | --- |
| 概念或架构 | 现象/问题 → 直觉 → 对象和术语 → 机制与因果 → 小例子/图 → 能解释什么、不能解释什么 |
| 系统或工程机制 | 请求/数据从哪里来 → 经过哪些状态和组件 → 资源或接口怎样变化 → 观察什么信号 → 失败时如何定位 |
| 项目或实战 | 任务目标 → 输入与验收条件 → 数据/状态 → 实现步骤 → 输出与评估 → 失败、复现和交付 |
| 论文解读 | 研究问题 → 前人方法的限制 → 作者提出的机制 → 证据支持什么 → 局限与未验证问题 |
| 方案比较 | 共同问题和条件 → 各方案机制 → 可比较证据 → 成本与适用场景 → 无法比较的部分 |

这些是读者路径，不是必须逐项写成标题。小节标题应表达问题或推进步骤，不应机械地重复“背景、定义、优缺点、总结”。

## 5. 初学者讲解：替读者搭出台阶

本规范所说的“说人话”，不是只换成短词、短句或聊天口吻，也不是删掉必要的术语、数学和工程深度。它要求作者站在目标读者刚走到这一页的位置，把读者需要走的台阶摆出来：先让读者看见要解决的问题，再说明眼前有哪些对象、对它们做了什么、为什么会发生变化、结果意味着什么；随后把具体过程接到正式术语、定义、公式、代码或一般规则。读者不应靠猜来补齐作者省略的前置知识、缩写、对象对应关系和推理步骤。

“初学者”也不是一个知识完全相同的人群。作者要说清本节假定读者已经会什么、可能误解什么，以及读完应能解释、计算、判断或操作什么。内容不同，讲解顺序也可以不同；下面是解释抽象概念、方法和机制时的默认脚手架，不是每段正文都要套用的固定模板。

### 5.1 用一个具体例子带读者走完过程

- 讲核心概念、方法或系统机制时，应该先找一个足够小、但确实能显示关键机制的例子。例子要给出读者看得见的起点和终点；不要只在开头提到一个场景，后面仍只列术语和结论。
- 沿例子逐步讲：先说当前要解决什么，再给必要输入或初始状态；每一步只做一个关键动作，展示中间结果，并说明结果为什么变化。读者应能指出“刚才对什么做了什么，为什么下一步这样做”，而不是只看到一串操作后得到的答案。
- 例子走完后，再概括一般规则。把术语、公式中的符号和例子里的对象逐一对上，说明哪些步骤对其他输入仍然成立，哪些数值只是为了演示而设。例子不能代替定义、推导、实现或证据。
- 例子应尽量贯穿本节；如需换例子，要说清新例子比前一个多展示了什么。不要为每个术语各换一套场景，增加读者需要记住的对象。
- 例如讲循环，可以先给列表 `[红, 蓝, 绿]`，逐轮写出程序当前读取的元素、循环变量怎样变化、何时停止，再说明“迭代”这个术语和任意长度列表上的一般规则。讲解要展示过程，不能只把“循环会重复执行”换成更口语的说法。

### 5.2 用类比搭桥，再回到真实机制

- 只有当类比能让目标读者借助熟悉经验看见一个原本抽象的关系时才使用。选择类比时，要考虑读者是否真的熟悉这个日常经验；不熟悉的故事会再添一层新概念。
- 说明类比两端分别是什么、哪些动作或因果关系相对应。类比要突出与当前结论有关的关系，不靠表面相似来推导技术结论。
- 紧接着交代类比能帮助理解什么、哪里不再对应。随后用本节的真实对象、术语或公式重述机制；不能让读者把故事本身当成技术定义，也不能让类比替代数值例子或推导。
- 类比不是必选项，也不应连续堆叠。若一个小例子已经把过程讲清，就不必再加比喻；若类比会遮住机制、引出错误联想或增加解释负担，就不用。

### 5.3 术语、句子和公式跟着讲解走

- 先确认目标读者已经会什么、还缺什么；不要把作者熟悉的上下文当成读者的前置知识。若本节依赖前文，只唤回理解当前推理必需的内容。面向初学者不等于把内容“降级”，而是把缺失的桥接步骤补出来。
- 先用当前例子说清正在发生的事，再在读者需要时引入术语。首次出现时给中文名、英文名或缩写，并立刻说明它在本例和当前问题中的作用。只引入后续推理需要的新概念；术语、符号或缩写集中出现时，应拆开讲。
- 段落围绕一个主要意思展开，开头让读者知道本段要解释什么。关键步骤较多时拆成短句或编号步骤；一句里不要同时塞进多个动作、条件和结论。解释至少要让读者知道“是什么、为什么要关心、怎么知道或怎么做”。
- 对大模型初学者，不能假设读者已经熟悉大模型数据流。按本节需要解释术语，不要求一口气补成术语表。例如，可先用一段话交代文本如何经分词器变成 token 和 token ID，模型如何给下一个 token 计算分数与概率，训练如何把预测和目标 token 比较成损失并更新参数，生成时又如何选出 token 并接回上下文。引入 prompt、上下文窗口、logits、注意力掩码、监督微调、偏好对、策略模型、参考模型、奖励模型等术语时，要说明它在当前流程中的位置，并区分容易混淆的相邻概念：token 不等于词或汉字，logits 是归一化前的分数而不是概率，模型给出的高分或偏好奖励也不等于回答已被事实验证；prompt 是输入上下文，completion 是模型续写的回答。
- 解释目标函数时，把数学量对应到训练信号或生成行为。例如讲 next-token 交叉熵时，说明模型给正确目标 token 的概率越低，惩罚通常越大；说明多 token 损失如何从各位置汇总，以及 padding 或被 mask 的位置是否计入。讲偏好或强化学习目标时，说明它比较哪些回答、优化哪个模型、奖励方向是什么，以及策略模型、参考模型和奖励模型各自负责什么；有参考约束时解释其作用，不把偏好分数说成真实性标签。具体公式仍按本节方法的定义和假设推导，不以这些直觉句替代数学说明。
- 公式出现前说明它在当前问题中要计算或约束什么，并把变量对应到真实对象；讲解时先让读者知道公式在例子里算哪一步，再解释每一项、优化方向和它在训练或生成流程中的作用。大模型公式应特别说清按 token、序列还是 batch 计算，求和还是平均，padding 或被 mask 的位置是否参与，以及概率、log 概率、分数、损失和奖励各自代表什么。推导保留会改变理解的中间步骤。
- 核心内容先讲完，再放非必要的版本差异、研究分歧、罕见边界或工程配置。确需提前说明的边界留在主线。关键 caveat 贴近它限制的结论；一般性背景、深入实现和延伸研究可放进清楚标记的“进阶”或“继续阅读”部分。

### 5.4 把不同表示接成同一条解释

- 初学者常见的断点不是单个名词太难，而是作者从一种表示跳到另一种表示时没有搭桥：从生活场景跳到架构图，从口头直觉跳到公式，从公式跳到代码，或从单个例子跳到通用结论。每次换表示，都要说明“刚才的对象在新表示里对应哪里”以及“新表示多告诉了我们什么”。
- 讲图时先给读者一个观察任务，例如“跟着这条请求看数据经过哪些组件”，再解释图中的框、箭头、颜色或分区。图题或图注应说出图要帮助读者看见的关系。图中元素多时分步揭示，避免把所有实现细节挤在一张图里。
- 讲表格时先说明行、列和比较维度各代表什么；比较对象必须在同一组条件下对齐。表格适合并列差异，不适合代替有因果顺序的解释。流程适合用有序步骤，概念关系适合用图或小表格；选形式的标准是减少读者来回搜索，而不是让页面显得丰富。
- 讲代码时先交代它要完成的任务、输入和输出，再解释不直观的状态变化或关键语句。读者需要理解一个复杂机制时，先用正文讲清思路，再给代码验证；不要让读者从代码注释中反推出整段原理。示例代码应从最小可运行版本开始，再增加参数、分支或真实工程约束；只有能澄清误用时才配反例。
- 对数字、张量形状、单位、索引和 rank 编号，始终沿用同一套对象和记号。若更换例子或编号约定，应先说清换了什么、为什么换，避免读者误以为数值差异来自机制本身。

### 5.5 控制一次引入的信息量，并逐步撤掉支架

- 一段或一个步骤集中完成一个主要动作或解释任务。读者必须同时记住多个新对象时，先把它们分组，说明组内关系，再继续推演；不要连续抛出多个缩写、参数和子系统，指望读者读完后自行拼图。
- 用有意义的小节、段落、编号步骤、留白或图示标出推理的自然分界。标题应告诉读者这一段解决什么问题或完成哪一步。短句和列表能帮助读者追踪复杂步骤，但不是越短越好；不要把存在因果关系的内容切成一串没有连接的口号，也不要为满足统一字数上限拆坏定义或推导。
- 初学者通常先需要一个完整示范，才能看清每一步如何服务于目标。合适时，可以随后给一个只留关键空缺的半成品，让读者补一步；再给一个略有变化的练习，看他能否迁移规则。例子、半成品、练习的数量和次序应随主题、读者经验和目标调整，不是所有章节的硬性配额。
- 逐步增加例子的复杂度时，每次只增加当前要解释的一个关键因素，并指出它带来的变化。已有经验的读者可能不需要完整示范或基础复述；可用简短回顾、清楚的进阶入口或分层讲解照顾不同起点。避免让进阶内容重复初学者已经掌握的步骤。
- 阅读难度分数、句长和词长可以帮助发现表面问题，却不能单独判断技术解释是否讲懂。不要为降低分数而删掉必要术语、公式或限定条件。

### 5.6 用具体因果关系写出耐心的讲解声音

- 站在读者的疑问处停下来，把疑问说具体并回答。例如，不只说“使用 DP 组同步梯度”，还要说明在一个小布局里哪些卡属于同一份模型副本、它们各自算出什么、为什么要合并这些梯度，以及合并后模型参数如何变化。小例子应承担解释，不只是给术语配一个数字。
- 用“因为、所以、此时、这一步改变了”等词明确表示因果或先后；但连接词后面必须有真实理由。不要把“是什么、为什么、怎么做”改写成三个空泛小标题，再用一句话填满每格。
- 需要澄清相邻概念时，先说清它们比较的同一维度，再给一对小例子说明差异。反例只用于揭示容易误判的边界，不要为了制造对比而堆很多未经解释的名词。
- “简单来说”“显然”“只要……就……”不能用来跨过推理。如果结论需要条件，就把条件写出来；如果一个词仍需要读者猜测，就补定义或例子。对模型、工具和组件尽量写清实际输入、操作和输出，不用拟人化替代机制。
- 作者的判断应落到本节对象上：说明某个假设在例子哪一步起作用、某个结果支持什么结论、一个限制会改变什么。这样比泛泛地说“这很重要”或反复加“值得注意的是”更能建立讲述声音。

### 5.7 检查读者能否复述、复走和迁移

- 对核心解释至少做三种检查：读者能否用自己的话说出本节问题和结论；能否沿例子指出每一步的输入、动作、中间结果和原因；把一个输入、参数或条件稍作改变后，能否预测哪些结果会变、哪些规则仍成立。概念、方法、工程机制可分别选择合适的复述、重算、追踪、辨析或小操作，不要求每节都有同一种练习。
- 有条件时找目标读者试读，让对方先按自己的理解复述或走例子，再观察具体卡在哪里。不要先把正确答案讲给对方再问“懂了吗”；这种回答不能检验正文是否独立讲清。读者卡住是定位文中隐含台阶的线索，不是对读者能力的评分。
- 没有目标读者试读时，作者可以做“初次接触检查”：遮住后文结论，按正文顺序复走例子；标出首次出现的术语、隐含条件、记号切换和没有说明原因的跳步。朗读可检查句子是否拗口、段落是否顺，但不能单独证明读者理解了机制。
- 发现读者不能复述或复走时，先找断点属于前置知识、对象对应、步骤、因果、记号还是边界，再补最缺的那一层。不要只在难句周围堆同义句，也不要简单把专业概念替换成模糊的口语。

本节写作原则的来源、研究发现和适用边界见 [面向初学者的清楚讲解：写作指南与教学资料](../research/plain-language-and-beginner-teaching-guidance-2026-11-17.md)。参考样本也包括 O’Reilly 的具体技术书：可查看《Learning Python》《Learning Perl》《Programming Perl》等动物封面书，以及《Head First Python》等不同教学形式的作品，借鉴其中的问答开篇、持续示例、即时运行与解释、自测安排等具体做法。应按书名、版次和章节判断，不把出版社或封面动物当成统一的写作规范。这些具体流程是本项目综合写作指南、教学资料、书籍样章和相关研究形成的编辑规范，不是任何单一来源逐字规定的普适教学定律。

## 6. 公式与可复算例子

每篇核心知识讲解至少要有一个完整例子，使读者能从给定输入走到结果。例子应按 §5.1 展开关键步骤，不要只列输入和最终答案。方法和算法适合手算时，列出变量、单位、每一步和关键中间量；系统内容可追踪一条请求、一次状态变化或一份资源账本。代码不代替讲解，代码与例子适合时使用同一组输入。

公式必须回答正文中的一个具体问题，而不是作为知识装饰。解释概率、向量、目标函数和梯度时，用读者已知的数学概念作必要连接；大模型公式还要把符号接回具体的 token、序列、模型输出、训练信号或生成步骤。近似值、玩具数据和假设条件须标明。

篇幅没有统一的字符数门槛，这不等于章节没有覆盖范围。过短时检查是否省略了动机、术语、关键步骤、例子或本章目标要求的知识点；过长时找出重复、并列主题和非必要深度。修改目标是完整但不累赘的解释，不是达到字数，也不是尽可能缩短。

大幅压缩或完全重写已有章节时，先列出原有重要知识点及其读者作用，再按当前章节目标判断哪些保留、合并、改为进阶、迁移到其他明确入口或删除，并在 `progress/` 记录主要取舍和理由。这份清单用于发现缺口，不是逐项照搬或保留所有旧内容的配额：重复、过细或超出本章承诺的内容可以删减；仍支撑读者完成本章目标的重要知识不能只因压缩篇幅而消失。“重写”允许重组和改写，不自动表示缩小范围。若章节定位或用户要求确实发生变化，再按新的目标调整覆盖面。

必要时把清单整理成覆盖图：逐项写明知识点对读者结果的作用、正文讲到什么深度，以及保留、合并、进阶、迁移或删除的去向。覆盖面看本章承诺需要哪些知识点；深度看读者能否理解这些点的定义、作用机制和关键推理，或按本章目标完成实现、判断与评估。标题出现过不等于覆盖，段落很多也不等于讲深。评估改写是否丰满时，同时检查覆盖图中的必要知识是否齐全、核心知识是否解释到位；不以章节字数或段落数代替这两项判断。

## 7. 深度内容怎样进入主线

核心知识点应根据主题，把它的背景和来龙去脉、要解决的问题、必要假设、工作机制、适用场景、优势、代价、局限和可改进之处连起来讲，并说明它们怎样服务于章节结果。这是组织解释的思路，不是每篇都要逐项设标题的清单；不适用的维度不必硬凑。模型、学习目标和算法三问用于方法讲解，其他内容类型按自身机制说明目的、过程、条件和结果。专家关心的证据、替代方法、实现差异和失败边界也沿着前文的问题出现。

区分章节的**覆盖面**和单个知识点的**讲解深度**：覆盖面检查本章目标要求的主题是否都得到交代；深度检查每个核心主题是否把问题、机制、推理、例子与边界讲完整。建立主线是为了安排先后和解释关系，不是通过删去其他核心主题来获得表面连贯；一条主线可以串起多个彼此依赖的知识点，也可以跨越连续章节。单章无法在可读的顺序中兼顾必要覆盖面和解释深度时，扩写或拆章，重新安排章节结果、依赖与过渡。核心范围内的实现细节可组织为“进阶实作”或选读路径，让读者选择阅读次序；若它仍是本章承诺的一部分，就应保留正文入口，不能只留一个外链或无去向地删掉。重复、过细或不再服务本章目标的内容可合并、删减或迁移，并说明去向。

来龙去脉不是按年份罗列技术名词。需要讲技术演进时，说明前一种方法面对什么问题、新方法改变了哪项表示/目标/算法、证据支持什么改进、还留下哪些限制。不得把改进说成无条件进步，也不得把来源支持的局部结果写成普遍规律。

## 8. 章节完成前做一次读者检查

不用字符数、标题数、引用数或代码块数量代替可读性判断。沿本篇主线检查：

1. 只具备本篇声明前置的读者，能否说出开篇问题和本篇结果？文中有没有把作者熟知但读者未必掌握的知识误当成默认前提？
2. 读者能否说出本章怎样推进本册承诺的能力，各节是否都在帮助本章回答中心问题？
3. 读者能否用自己的话解释核心机制，而不只是复述术语；文中是否把专家容易略过、初学者却需要的对象、动作、条件和因果步骤讲出来？
4. 对方法类内容，读者能否回答模型表示什么、优化什么目标、算法怎样实现目标？
5. 读者能否沿例子说清每一步的输入、动作、中间结果和原因，并把例子对应到术语、公式、代码或图中的对象，而不只是复算最终答案或看懂最终图表？
6. 每个小节是否说明它怎样接上前文、交给后文什么？
7. 初读者读主线时，是否会被可选的专家细节打断？
8. 专家需要的来源、假设和边界是否仍可追溯？
9. 若使用了类比，读者能否说出类比中哪些关系对应真实机制、哪些部分不对应，并能用真实术语或公式重新说明机制？
10. 改动一个输入或条件后，读者能否根据刚学到的规则判断哪些结果会变化？若不能，正文是否只展示了答案，没有帮助读者看出可迁移的机制？
11. 如果没有目标读者试读，作者是否做过一次不看后文结论的复走检查，并明确这只是作者自检、不能冒充用户测试？

若答案是否定的，先定位断点：顺序或承接不清时重排并补桥接；知识覆盖不足时补上必要概念、机制、推导、实现或评估；单章承担过多学习结果或无法讲到所需深度时，调整为多章或连续篇章。添加的每段都应承担明确的解释、推演、证据、操作、例子或收束作用；删去重复结论、空泛过渡和不推进理解的篇幅。

## 9. 让正文保留作者的讲述声音

读者看到的应是一段有人在解释、有判断、讲得通的正文，而不是把规范项目逐条填满的报告。作者可以用清楚的判断和过渡带路，不必刻意写成聊天，也不必频繁自称“我们”。

- 在读者最可能产生疑问的地方停一下，把疑问说具体并回答它。可以先拿一个眼前的例子回答，再说明一般规则。不要只给定义或结论，也不要用一串问题代替解释；不要用“简单来说”掩盖没有讲出的步骤。
- 让段落之间有真实的关系：前一段提出的困难，如何引出下一段的定义、公式或例子；例子又验证或修正了什么直觉。例子要在后文继续承担解释作用，不能只是开头的装饰。少用没有实际承接作用的“下面我们来介绍”“综上所述”“为后文打下基础”等套句。
- 让作者的判断落在具体内容上：说明哪个假设在这里起作用、某个例子能支持什么结论、一个限制会影响谁。判断要有理由和证据；不能用虚构的亲身经历或夸大的口吻制造亲切感。
- 术语、表格、标题和清单只在能帮读者看清关系时使用。规范里的提问是作者检查理解的工具，可以在一段连贯解释中同时回答多个问题，不必逐项设标题，也不要把同一层意思反复改写成段首提示、段末总结和章节小结。
- 朗读关键段落，听听是否像一个耐心的教师在解释眼前这个问题：句子是否接得上，例子是否真的做了说明，结论是否来得自然。若一句话可以原样放进很多不相关的章节，通常需要换成针对本章对象的解释，或删去。

“有人味”来自作者愿意替读者作取舍、把推理说完整、诚实交代边界，不等于随意口语、拟人化模型或堆叠故事。说人话的关键是把读者需要走的推理台阶摆出来；检查清单是写作后台，正文负责把知识讲成一条读者愿意跟下去的路。
