# Step 3.5 Flash：S3F1、MTP-3 与 11B 激活参数

本章以 Step 3.5 Flash 为案例，说明长上下文注意力、MoE 参数激活和多 token 预测如何分别改变注意力计算、每 token 的前馈计算与自回归解码路径。读者应能读懂该模型的 45 层局部/全局布局和参数账本，解释 MTP 训练头与推测解码运行时的区别，并判断哪些公开实验真正支持结构取舍。MoE 的一般路由与通信原理回链第 21—22 章，滑动窗口的通用 pattern 回链第 19 章；本章不扩展成 Agent harness 或推理服务教程。

## 80.1 先读参数账本：backbone 与 MTP 的口径

本节建立模型层数、总参数、激活参数和专家选择之间的关系，避免把 11B 激活参数误读成权重存储或整次请求的显存需求。核心统计以技术报告的 backbone 口径为主，同时保留报告对含 MTP-3 配置的单独统计，以及模型卡参数表中的不同口径，供后文解释 MTP 额外路径的成本。

### 80.1.1 45 层 backbone、196B 总参数与 11B 激活参数

说明报告中的 196B/11B 指 backbone 总参数与每 token 激活参数；激活参数主要刻画一次 token 前向涉及的参数规模，不代表驻留权重、KV cache、通信缓冲或并发工作区。关联 45 层、4096 hidden size 和公开的 256K 位置上限，避免把配置上限当成所有任务的实测有效长度。

### 80.1.2 42 个 MoE 层如何选择 288 个 routed experts 中的 top-8

说明前三层使用 dense FFN，后 42 层使用稀疏 MoE；每个 MoE 层公开 288 个 routed experts 和 1 个 shared expert，每 token 选择 8 个 routed experts。将专家总存储、每 token 激活计算、专家并行通信和路由负载分开，正文只补足本案例所需关系，不重讲一般 MoE 算法。

### 80.1.3 MTP 参数如何进入总量与激活量

区分报告表格中的 backbone 196B/11B 与含 MTP-3 的约 198B/13B，以及模型卡写出的 196.81B 与单个 0.81B head 口径。公开材料没有完全对齐这些参数计数；应保留来源和统计范围，不能把 11B 当成使用全部 MTP 路径后的无条件计算总量。

## 80.2 S3F1 排布怎样组织 45 层

本节把 3:1 的抽象比例落实到发布配置中的实际顺序。读者应能从首个 Full 层开始读出后续 11 组 SWA×3、Full×1，并理解局部窗口与周期全注意力各自提供的信息通路；不把单个四层 motif 简化成脱离起始层和层编号的模糊周期描述。

### 80.2.1 首个 Full 层之后的 11 组 S3F1

说明总层数由 1 个 leading Full 加 11 组各含 3 个 SWA 和 1 个 Full 组成，因此 backbone 有 33 个 SWA 层和 12 个 Full 层。配置的 `layer_types` 明确了首层和后续顺序，是核对重复公式或示意图的直接来源。

### 80.2.2 512-token 窗口、GQA-8 与两类 query-head 数

说明 SWA 使用窗口大小 512，Full attention 使用 GQA-8；每层 8 个 KV heads，而配置区分 Full 与 SWA 的 query-head 数量，SWA 由 64 增至 96。这里区分查询头数、KV 头数和层类型，避免把 GQA-8 误作 query-head 数。

### 80.2.3 周期 Full 层怎样补充跨窗口信息路径

解释 SWA 层让位置直接聚合最近窗口内的表示，Full 层让当前位置读取全部先前位置；局部层仍可沿多层隐状态传递已混合的信息，但不会因此等价于每层全局可见。明确长距离访问机会与精确检索质量不是同一指标。

## 80.3 注意力计算账与混合结构的质量边界

本节比较局部窗口和因果 Full attention 的可见 pair 数，并把复杂度估算、论文中的 attention-side FLOPs 和实际服务延迟分开。结构的计算节省存在于特定注意力项；端到端收益仍取决于层型、头数、序列阶段、投影与其他模块，不能由渐近量级直接推出硬件加速比。

### 80.3.1 因果窗口的可见 pair 数怎样随长度增长

以当前 token 是否包含在窗口的明确约定，讨论 Full layer 的因果二次 pair 数和固定窗口 SWA 的线性 pair 数；再将模型的 33 个局部层与 12 个全局层合并为一份理论账本。该账本忽略头数、投影、内存移动和 kernel 效率，因此只表示可见交互规模。

### 80.3.2 选择 SWA 而非线性注意力的作者动机

说明技术报告的判断范围：作者选择 SWA，是因为标准 attention 语义与 KV mask 更便于并行验证推测候选；报告同时认为当时缺少线性注意力在 agentic long-context 任务上更优的稳健证据。将其写作该模型的设计动机，不上升为线性注意力的普遍缺陷或所有任务的结论。

### 80.3.3 30B-A3B 注意力消融显示的成本—质量取舍

准确交代消融的 30B-A3B 模型、固定窗口、训练预算、评测类别和关闭 MTP 的设置。对齐 FFFF、S1F1、S3F1 与扩展 SWA query heads 的结果，说明单纯 S3F1 降低报告中的 attention-side FLOPs 但存在质量变化，扩头可以在给定实验中补回部分指标；不把该 proxy 实验冒充 196B 发布模型的端到端证明。

### 80.3.4 Prefill、decode、理论 FLOPs 与 wall-clock 延迟

区分长 prompt prefill 与逐步 decode 中的工作形态，核对报告分别归一化的计算口径和其理想化性能模拟。指出理论 pair/FLOP 比例、作者模拟的 latency 与某硬件某负载上的实测服务结果属于不同证据层级。

## 80.4 两类注意力补偿：扩展 SWA query heads 与 head-wise gate

本节说明较稀疏的全局交互图为何同时使用更高的 SWA query-head 数与输入相关的逐头门控。它们针对的不是同一对象：前者增加局部查询表示能力，后者调整每个头输出的幅度；其收益和代价只能按相应消融与模型规模描述。

### 80.4.1 从 64 到 96 个 SWA query heads

说明 query head 增加而 KV heads 仍为 8 的配置关系，以及固定窗口使局部 head 增量的注意力范围不随总上下文长度扩大。报告把这项增强用于缓解 S3F1 的质量退化；正文需同时指出更多 query head 仍增加计算，不能称为绝对免费。

### 80.4.2 Head-wise gate 怎样抑制无用注意力输出

说明每个注意力头从当前位置表示生成输入相关的标量 gate，并用它缩放注意力输出；可将其与固定 sink token 的区别概括为数据相关的 sink mass。公式解释 gate 对真实输出所做的变化，不扩写成一般 gated-attention 综述。

### 80.4.3 扩头、门控和 ideal-workload 模拟的证据边界

区分 30B-A3B 的布局/扩头消融、100B-A10B 的 sink 与 head-wise gate 比较，以及附录中的理想工作负载模拟。列明各自能支持的结论和不可外推的范围，特别是不能据此保证任意硬件、长度、batch 或 196B 权重下的 wall-clock 收益。

## 80.5 MTP-3 训练目标与三个未来偏移

本节从 next-token prediction 出发说明 Step 3.5 的三个额外预测偏移、各 MTP 模块结构与训练安排。它把训练时的多偏移监督与推理时的 speculative drafting 分开；“三个 MTP 模块”不被写成每轮必定接受三枚 token 的服务语义。

### 80.5.1 标准下一 token 与 MTP-1/2/3 的目标位置

按技术报告给出的 offset 定义，区分普通 LM head 的 $x_{t+1}$ 与 MTP-$h$ 对 $x_{t+1+h}$ 的预测，即额外目标落在 $x_{t+2}$、$x_{t+3}$、$x_{t+4}$。解释从一个骨干位置附加多种预测监督的含义，并区分“总共四个预测位置”和“MTP-3 三个额外偏移”。

### 80.5.2 SWA 与 dense FFN 构成的轻量 MTP 模块

说明报告为 MTP 模块选择 SWA 与 dense FFN，和 backbone 中大规模稀疏专家层形成计算路径对照。结合报告和模型配置说明预测层数量与头参数账；不把名称中的“轻量”理解成没有计算或服务成本。

### 80.5.3 先训练 MTP-1，再初始化并联合微调 MTP-2/3

说明大部分训练阶段只启用 MTP-1，backbone 接近完成后用 MTP-1 初始化 MTP-2/3，再在轻量阶段共同训练三者。交代 position-dependent loss reweighting 针对不同预测距离的作用及报告实际披露范围。

## 80.6 从 MTP 预测到推测解码：草稿仍须经过目标验证

本节连接训练出的预测能力与部署时的 draft/verify 路径。读者应跟踪候选序列如何由目标模型并行评分、可接受前缀如何提交、首个不匹配处如何恢复目标分布，并理解接受长度只是吞吐因子之一；具体补偿算法依实现而异，不重讲第 79 章的 EAGLE 特定树与量化制品。

### 80.6.1 Draft—verify—accept 的状态关系

说明草稿器提出候选 token，目标模型对候选的条件分布作并行验证，系统只提交连续可接受前缀，并按具体推测采样算法处理首个拒绝位置。把提议模型、目标模型和验证规则区分开，保证讨论不会把预测头本身当成已接受输出。

### 80.6.2 接受长度影响每次目标调用的有效输出量

定义草稿长度、接受前缀长度和一次验证后提交的 token 数；在标准 speculative sampling 的停止条件外，目标调用可提交 $A+1$ 个 token。把接受长度、draft/verify 时间、同步与 batch 负载一起纳入有效吞吐判断，不将 MTP-3 名称或模块数换算成倍速。

### 80.6.3 checkpoint 中三层 MTP 与 runtime 可用路径

对照固定模型配置中的 `num_nextn_predict_layers=3`、模型卡对于 full MTP3 的说明，以及 2026-11-25 检查到的 vLLM recipe 将其设置为 1、`num_speculative_tokens=1` 的命令。只据此说明公开配置展示的路径差异；没有实际加载和 profiling 时不宣称某个 runtime 已达到完整三头加速。

### 80.6.4 发布方 tokens/s 与框架示例 benchmark 的归因

记录发布方报告的 100–300 tokens/s 常态区间与单流编码峰值等主张，并把它们限定为发布方设置。分清 SWE 任务、硬件、量化、batch 和后端等条件；框架 recipe 的随机输入 benchmark 不是 MTP 开关前后对照，不能单独证明 MTP 的增益。

## 80.7 Agent benchmark 与 Context Manager 的归属

本节只保留解释结构主张所需的评测背景。它说明 Context Manager 怎样改变 BrowseComp 的有效轨迹管理，以及为何带 harness 的分数不能被归因于模型内部注意力、MTP 或记忆；不重述通用 Agent 工程清单。

### 80.7.1 Context Manager 是超过阈值后重启 agent loop 的 harness 策略

说明模型卡所写机制是有效上下文超过阈值时重置上下文并重新开始 agent loop；它是 harness 层策略，不是模型持久记忆或 attention 层结构。将成绩标签中的该协议显式写出。

### 80.7.2 benchmark 结果不能替代架构因果证据

用发布方的 BrowseComp、SWE-bench Verified 或 Terminal-Bench 2.0 结果说明模型与评测协议的组合成绩。指出独立的注意力消融、MTP 运行时对照和带 harness 的任务分数回答不同问题；没有相应消融不能将 agent 成绩归因给单一架构部件。

## 80.8 面试追问

围绕实际 45 层排布、MoE 参数账本、MTP 目标偏移与 serving 接受长度、published benchmark 的 harness 归属设置问题。回答要求读者用具体层型、参数统计范围或一次 draft/verify 状态解释结论，不靠“更快”“更省”之类的总括语。

## 80.9 小练习

练习要求读者根据公开配置还原 45 层类型和窗口/全注意力 pair 账，区分可见 pair 与 FLOPs/服务延迟；按偏移标注 MTP 目标并解释配置与 vLLM 配方差异；最后设计有固定 checkpoint、任务、后端和负载的 attention 或 MTP 对照，明确记录质量、接受前缀和实测时延，不能将公开代理实验当成本地复现。
