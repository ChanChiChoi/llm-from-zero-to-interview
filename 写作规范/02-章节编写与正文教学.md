# 模块 02：章节编写与正文教学

> 本细则用于章节定位和结构已明确后的正文编写、例子与公式取舍、读者理解检查。若改写中发现章节职责、范围或依赖有问题，返回模块 02a；研究新事实时按模块 03，处理公式/代码/图表时按模块 04。

## 1. 诊断正文讲解断点

| 读者表现 | 常见原因 | 修改方向 |
| --- | --- | --- |
| 记住名词，却说不出关系 | 缺少贯穿问题或整体图 | 先交代输入、目标、机制和结果，再展开 |
| 看懂公式，却不知道为何要写 | 符号、目标或推导突然出现 | 先说要算什么，再定义符号；需要时用例子代入并解释 |
| 读到实现细节就失去主线 | 核心机制和版本、配置、边界混在一起 | 先讲完主线，非必要实现深度标为选读 |
| 读完整章却不能复述 | 小节不承接，结论未回收 | 重排因果顺序，节首交代问题，节末回扣并过渡 |
| 代码能运行，却不知在算什么 | 代码未接上问题、输入或过程 | 先讲任务和输入输出，再按需对照代码结果 |
| 看过前置章节，仍不懂当前术语 | 把跨章引用当成当前解释 | 补一两句必要概念，再链接深入内容 |
| 不明白本章为何属于本册 | 章节目标未连接书册承诺 | 写清书册能力、本章贡献和结果，再决定取舍与顺序 |

## 2. 方法章节：围绕核心问题选择讲解路径

讲算法、训练方法或统计学习方法时，先说明它处理的问题、提出背景和目标，再按读者卡点选锚点或步骤路线，解释关键动作及影响结论的条件。涉及提出或演进时，交代相关前人做法在哪个关键问题上不足、当前方法回应了什么；只选解释当前方法所需的前置工作，不罗列论文。历史和方法主张按模块 03 核实。若没有真实冲突，就写核心任务或难点，不要为了套格式编造“核心矛盾”或技术前史。

常用讲解顺序如下，可按读者前置、数学依赖和本节任务调整：

1. **背景、目的与前人做法**：说明任务、方法为何出现，以及必要前置做法和不足；与理解无关的技术史不必补写。
2. **锚点、定义与假设**：用小数据、输入输出、训练过程、对象轨迹或状态变化呈现关键关系；据此说明变量、术语、模型假设、数据条件、固定量和待学习量。保留决定机制的条件，不适合算术演示时不硬造数字。
3. **目标或判断准则**：说明怎样算更好，再介绍损失、奖励、约束或其他准则及优化方向；没有显式目标函数时不虚构公式。
4. **算法骨架（适用时）**：若步骤、循环、分支或状态容易混淆，可用简短伪代码或编号步骤交代输入、输出和关键动作。保留影响算法的条件、状态和停止规则；框架配置、日志、API 等只有改变行为、结论或本章承诺时才展开。
5. **沿锚点解释关键步骤**：说明每步处理什么、为何这样做、结果如何变化；在难点处补必要定义、计算和推理。公式、算例和文字尽量对应同一数据或过程。伪代码只给路线，不能替代本章承诺所需的计算、实现教学或正确性论证。
6. **说明条件并收束**：交代影响结论和正确使用的假设、证据边界、适用条件；效果主张不得超出证据。回到开篇问题，总结当前方法解决什么、相对前人改变什么、仍有哪些限制，以及它如何连接下一步。

是否写伪代码，看读者是否需要先弄清算法顺序、循环或分支。数值演算已揭示关键关系时可省略；步骤容易混淆时再用简短骨架。例如 SFT 可沿一条短示范回答说明目标 token 与损失，PPO 可追踪一次回答的训练信号、更新和评估。例子需经研究核对并与方法假设一致，后续沿同一锚点解释；不必把每种形式都用齐。

### 可选模板：伪代码先搭路线，贯穿算例再讲细节

当读者既需要看清流程衔接，又会卡在局部计算时，可采用此写法。以下步骤和 [PPO-RLHF 范例](示例参考/PPO-RLHF-伪代码锚点与贯穿算例.md)展示一种让小白看见全局路线、跟住关键计算的方式，不是必选格式；可按知识特点调整、合并、省略，不必照搬标题、顺序、案例或符号。若流程直观、伪代码无助理解，或例子无法保留关键条件，就改用更合适的讲法。

1. **交代方向**：按需说明背景、目的、待解决问题和要追踪的对象；可用显式标签分区。
2. **选贯穿例子**：给出可走过主要流程的 prompt、样本、状态或数据，并说明简化和假设。假设的 token 切分、奖励或状态值须标明是教学设定，不代表真实 tokenizer、模型输出或通用配方。
3. **给流程地图**：用框架无关的短伪代码显示必要准备、关键动作、循环顺序、输入输出；相关时标出模型初始化、冻结和更新角色。不扩成工程程序，也不以伪代码代替推导。
4. **说明对象职责**：交代模型、数据和状态的来源、职责、输出粒度及衔接，只补读者下一步所需关系，不逐行复述代码。
5. **沿流程走例子**：按函数或步骤解释输入、操作、输出和原因；只在易混处用小表、公式或手算展示中间量。同一流程沿用同一数据、token/位置、变量和数值，不要求每步计算量相同。
6. **概括规则与边界**：指出可推广机制、教学简化、适用条件、评估方式、优点和代价。教学分数或简化状态不代表方法保证或生产配置；证据、公式和实现仍按模块 03、04 处理。

伪代码负责给出全局路线，算例负责解释局部怎样发生；若两者重复表达同一层信息，保留更有助于理解的一种。

如果某个知识点确实能具体说明背景、目的、解决的问题、意义、适用场景或优缺点，而且分区便于初学者定位，可用固定标签、小标题或列表，不必融进连续叙述。各栏目应回答不同问题：背景交代来由和必要前置；目的说明目标；解决的问题点明针对的不足；意义说明新增能力或价值；适用场景写清任务和成立条件；优缺点说明收益、代价或失败边界。只保留有实质内容且适用的栏目，重复项可合并，不适用项可省略，不为凑格式泛写。背景、效果和比较主张仍须核实证据。

理解或比较方法时，可用三问作共同坐标，而非统一章节模板：

- **模型表示什么？** 输入、输出是什么，假设了数据或任务中的什么关系？
- **学习目标（优化准则）是什么？** 什么结果更好？损失、奖励、约束或判断准则为何符合任务目标？
- **算法怎样实现这个目标？** 如何用数据和目标得到参数或结果？只展开影响结论、方法选择或读者结果的步骤、代价和近似。

比较时先对齐问题和条件，再比较表示与假设、目标、求解过程、证据、适用场景、优势、代价和失败边界。若新方法声称改进旧方法，要说明改了表示、目标还是算法，解决旧限制的同时带来什么代价或未解问题。以深度学习为例，模型可指网络结构或概率分布，目标可指损失、正则项或奖励，算法可指反向传播、优化器更新或采样流程；三者不要混称。

## 3. 按本章的主要读者任务选择讲解路径

先判断本章主要帮助读者学概念、懂机制、完成任务、做项目还是查询规格。可兼有多种任务，但应有主导任务；任务切换处用标题、过渡或导航提示。整章路径确定后，还要按每个知识点的卡点选择锚点（见 §4.1）。

| 内容类型 | 读者问题 | 建议顺序 | 完成结果 | 常见失误 |
| --- | --- | --- | --- | --- |
| 概念或架构 | 概念是什么？现象为何发生？ | 现象/疑问 → 小例子或状态 → 对象关系 → 术语定义 → 机制因果 → 规则与边界 | 能用自己的例子区分概念并解释结果 | 用术语解释术语；只给比喻或定义，不回到真实对象 |
| 方法、算法或推导 | 为何需要此法？回应什么问题？每步做什么？ | 问题和前人做法 → 锚点 → 定义、假设、目标 → 需要时给算法骨架 → 解释关键步骤/计算 → 条件、结果和边界 | 能说明方法来由、行为、重要计算和改变 | 伪代码堆框架细节；公式、算例各讲一套；只给结论 |
| 系统或工程机制 | 请求、张量或数据经过什么？ | 小数据变换或单对象追踪 → 起点、动作、结果 → 数据流图/表/文字 → 并发、拓扑或规模 → 失败与取舍 | 能复述运行过程并定位状态变化 | 罗列组件；图文各讲一套；只讲理想路径 |
| 操作教程 | 怎样完成明确任务？ | 目标和前置 → 可复制环境/输入 → 分步操作及预期输出 → 错误恢复 → 完成验证 | 能完成任务并判断结果 | 一步塞多动作；漏版本、依赖、输出或恢复方法 |
| 项目或实战 | 怎样组合技术交付作品？ | 任务、约束、验收 → 最小版本 → 逐轮扩展 → 选择与状态 → 测试评估、故障复现 → 交付 | 能复现、解释取舍并迁移方案 | 只展示最终仓库；步骤与理由脱节；情景遮住机制 |
| 论文、证据或方案比较 | 解决了什么？证据多强？差异何在？ | 对齐问题条件 → 原方法及限制 → 新机制 → 可比证据 → 结果、代价和适用条件 → 未验证处 | 能区分主张、观察和可推广结论 | 条件不对齐就比数字；把局部结果说成普遍事实 |
| 参考或查询 | 参数、接口或限制准确值是什么？ | 按对象/任务建入口 → 定义、输入输出、版本、约束和错误 → 最小示例 → 链接教程与机制 | 能查准规格并判断适用性 | 只列名称；漏前提、版本或交叉入口 |

这些路径用于选择顺序，不要求逐项做成标题。教程可讲必要原理，机制章也可含操作；应让读者知道自己正读什么。背景、目的、问题、意义、场景和优缺点只有在各自有具体内容且显式分区有帮助时才分别标出，不套用全部标题或填空。

## 4. 初学者讲解：从读者问题出发，用锚点带路

核心主线面向具备本节声明前置知识的初学者；不能以“有经验的工程师看得懂”代替主线讲解。“说人话”不是单纯换短词、短句或聊天口吻，也不是删除必要术语、数学和工程深度，而是让读者不靠猜就能跟完关键过程。

可先说明问题、背景、目的或意义，再选合适锚点呈现抽象知识怎样运作；方法还要交代必要前置、相关前人做法及不足、当前回应。沿锚点解释对象、步骤、输入输出、状态变化及因果，再概括一般规则或行为逻辑。此顺序可调整，相关知识可共用锚点；直接解释或追踪过程已足够时，不必另造例子。没有有意义的前史时，说明真实前置和问题，不虚构技术史。影响理解或结论的假设、证据和边界要留在主线；代码、公式和比喻按需使用，代码仅在本章承诺编码或 API 操作时成为交付要求。

### 4.1 按读者卡点选择讲解锚点

“讲解锚点”是把抽象知识接到具体问题、对象或过程上的抓手。按读者卡点选用；可以是例子、数据流、步骤、状态变化或对照。不同知识点可用不同锚点，相关知识点可共用。

| 读者卡点 | 合适锚点 | 要让读者看见什么 |
| --- | --- | --- |
| 数值从何而来、结果为何变化 | 小型数值例子，逐步演算 | 初值、操作、中间与最终结果，及符号对应 |
| 算法顺序、循环、分支或更新对象不清 | 短伪代码/编号步骤，必要时追踪例子 | 每步处理什么、条件如何触发、状态怎样变；不扩成框架实现 |
| 数据、请求或消息经过哪些组件不清 | 流程图/数据流图，追踪一次请求或数据块 | 节点的输入、操作、输出及箭头含义 |
| 变量、张量、请求或资源持续变化 | 执行轨迹、状态表或资源账本 | 每步原状态、动作、新状态和原因 |
| 方法相似或边界不明 | 条件对齐的成对例子，必要时给反例 | 共同条件、关键差异及其影响 |
| 关系抽象且读者确有熟悉经验 | 精确映射的类比，再回到机制 | 对应关系、失效处和真实机制；类比不代替定义 |
| 需要亲自操作或动态观察 | 最小可运行代码、交互或模拟（任务需要时） | 先预测，再观察输入、动作与输出 |

选一个最能显示关键关系的主锚点；辅助形式只有在补充新信息时才加。同一内容不换形式重复讲。例子或过程要展示起点、动作、变化、原因和结果，并在后文继续承担解释；术语、公式和图中对象须能对应到锚点。随后说明一般规则、可推广部分和教学设定。相关概念尽量共用一例；换例时说明它多展示了什么。若算术例子不适用，就追踪状态、消息、请求或决策过程，不退回抽象术语堆叠。

例如讲 collective 通信，可令 rank 0、rank 1 分别持有 `[1, 10]`、`[2, 20]`，逐位置相加得 `[3, 30]`，再用同一组数比较结果是复制给每个 rank，还是切片分发。读者应看见数据怎样变化、由谁持有及不同操作的差异。第五册第七章 §7.4 的[完整范例](示例参考/第五册第七章-7.4-Collective-communication.md)展示了这种讲法；它只是面向小白读者的参照，不要求照搬向量、rank、顺序或形式。若小例子会遮住条件、流程或规模效应，应改用或补充其他表示。

### 4.2 用类比搭桥，再回到真实机制

只在读者确实熟悉该经验、且类比能看见抽象关系时使用。说明两端对应的对象和因果、类比帮助理解什么及不再适用之处，然后用真实对象、术语和必要推理重述机制。类比不是必选项，不应连续堆叠；若例子已讲清，或类比遮住机制、引出错误联想、增加负担，就不用。

### 4.3 术语、公式和句子跟着例子走

具备本节声明前置知识的读者，读完核心讲解后应能说清知识点要解决什么、在本章中的作用、关键对象或步骤如何起作用、结论为何成立；不要求掌握专家证明、变体或争议。若仍会问“这是什么”“符号指什么”“为何做这一步”，补足术语、前置或推理台阶。影响主线结论的假设、证据和边界不能列为可选专家内容。

- 先确认读者前置，只唤回当前推理必需的内容。术语可在问题或锚点之后引入；若标题就是搜索术语，尽快解释其作用；搭锚点前必需的对象或符号可先定义。一次只引入后续理解需要的新概念，缩写集中时拆开讲。
- 段落围绕一个主要解释任务，开头让读者知道本段要解决什么；步骤复杂时拆句或编号，别在一句中塞进多个动作、条件和结论。说明“是什么、为何关心、如何判断或操作”。
- 不假设读者熟悉大模型数据流。按需说明文本经分词器变成 token 和 token ID、模型怎样为下一个 token 算分数/概率、训练如何比较预测与目标形成损失并更新参数、生成如何选择 token 并接回上下文。解释 prompt、上下文窗口、logits、注意力掩码、监督微调、偏好对、策略/参考/奖励模型等术语时，说明其流程位置及易混差别：token 不等于词或汉字；logits 是归一化前的分数，不是概率；模型分数或偏好奖励不证明事实正确；prompt 是输入上下文，completion 是模型续写。
- 解释目标函数时，把数学量对应到训练信号或生成行为。例如讲 next-token 交叉熵，说明目标 token 概率越低通常惩罚越大，以及多 token 损失如何汇总、padding/mask 是否计入；讲偏好或强化学习目标，说明比较哪些回答、优化哪个模型、奖励方向及策略/参考/奖励模型职责。参考约束要说明作用，偏好分数不能说成真实性标签。直觉不能替代按定义和假设进行的公式说明。
- 公式及外部/自拟公式按 §5 和模块 04 处理。核心讲完后再决定是否补版本差异、研究分歧、罕见边界或工程配置；影响结论的边界留在主线，其余只在解决明确读者需要时作为进阶内容加入，并把 caveat 放在它限制的结论附近。

### 4.4 把不同表示接成同一条解释

从场景到图、直觉到公式、公式到代码或例子到一般规则时，都说明对象在新表示中对应哪里、新表示多提供什么信息。讲图先给观察任务，再解释框、箭头、颜色和分区；元素多时分步呈现。讲表先解释行列和比较维度，并在相同条件下对齐对象；表适合并列差异，不替代因果流程。代码先交代任务和输入输出，再解释关键语句或状态变化；复杂机制先讲思路再给代码验证，示例从最小可运行版本逐步加参数和约束。数字、张量形状、单位、索引和 rank 编号保持一致；换例或编号时说明原因，避免把表示变化误当成机制变化。

### 4.5 控制信息量，并逐步撤掉支架

- 每段或步骤集中处理一个主要任务；新对象较多时先分组并说明关系，避免连续抛出缩写、参数和子系统。
- 首次讲方法时先交代必要输入、目标、状态变化和结果，再深入关键推导、语义、条件或本章承诺的实现。伪代码不扩成工程程序，各步骤不必等长；必要假设和边界不能因控篇幅删去。
- 用标题、段落、编号、留白或图示标记自然推理分界。短句和列表服务追踪，不要拆成无因果的口号，也不为求短拆坏定义或推导。
- 合适时先完整示范，再给关键空缺的半成品和略有变化的练习；数量、顺序随主题和读者目标决定。增加例子复杂度时，每次只增加一个关键因素并指出影响。有经验的读者可用简短回顾或进阶入口，无须重复基础步骤。
- 难度分数、句长和词长只能发现表面问题，不能证明技术解释已讲清；不能为降低分数删除必要术语、公式或条件。

### 4.6 用具体因果关系写出耐心的讲解声音

- 在读者可能疑惑处具体回答。例如讲 DP 组同步梯度，要说明哪些卡属于同一模型副本、各自算什么、为何合并、合并后参数怎样变。例子要解释机制，不能只给术语配数字。
- 用“因为、所以、此时”等词明确因果和先后，并说出真实理由；不要把“是什么、为什么、怎么做”列成空标题。
- 比较相邻概念时先对齐维度，再用成对例子显示差异；反例只用于揭示易误判边界。
- 不用“简单来说”“显然”“只要……就……”跳过推理。结论有条件就写出；模型、工具和组件尽量说明实际输入、动作和输出，不用拟人化替代机制。
- 判断落到当前对象：说明假设在哪一步起作用、结果支持什么、限制影响什么，并给出理由和证据；避免泛称重要或反复铺垫。

### 4.7 检查读者能否复述、复走和迁移

- 按本节目标检查读者能否复述问题与结论、追踪关键变化或预测条件变化的结果；不同内容选用不同方式，不设固定数量。
- 有条件时请目标读者先独立复述或走例子，再观察卡点；不要先讲答案再问“懂了吗”。卡点用于发现正文缺失的台阶，不用于给读者评分。
- 无试读时做“初次接触检查”：沿正文路线复走锚点或过程，标出首次术语、隐含条件、记号切换和无理由跳步。朗读可检查句子和段落是否顺，不能单独证明机制已懂。
- 若读者无法复述或复走，定位断点属于前置、对象对应、步骤、因果、记号还是边界，再补缺失部分；不要只堆同义句或换成模糊口语。

本节原则的来源、研究发现和适用边界见[面向初学者的清楚讲解：写作指南与教学研究](参考资料/plain-language-and-beginner-teaching-guidance-2026-11-17.md)。参考样本包括《Learning Python》《Learning Perl》《Programming Perl》《Head First Python》等不同教学形式的技术书，可借鉴从读者问题切入、用短程序或小数据演示、紧接结果解释、逐步增加难度和安排自测等做法；不照搬漫画、角色对话、版式或铺陈，也不把出版社或封面当作统一规范。应按具体书名、版次和章节判断。不同来源分别支持读者分析、示例、分段、术语或理解检查，并未共同规定固定顺序；本项目的路径是编辑综合，须按章节任务、读者前置和数学逻辑调整，不能称为单一来源验证的普适定律。

## 5. 讲解锚点、例子与公式取舍

核心知识应让读者看见它做什么、为何这样做、结果怎样产生。小例子是常用锚点但不是配额；也可用过程、步骤、状态、图示或对照，相关知识可共用锚点。贯穿案例须在正文中继续解释机制。代码按读者需要提供；本章承诺编码、API 调用或程序复现时，才须交付相应实作。

公式也不是必备形式。只有在有助于理解、推广、推算、表达必要目标/约束或支撑推理时使用；是否加代入算例，看它能否让关系更清楚。外部公式核对来源、条件和符号口径后注明来源；自拟或整理的公式须说明表达的关系及用途，否则改用文字、图或过程。

使用公式时，说明它回答什么、主要符号、适用条件，并接回当前对象或过程。只展开会改变含义的取值范围、token/序列/batch 口径、mask 和求和/平均方式；玩具数据与假设值须标明。渲染及引用方式见模块 04。

正文没有统一字数或页数上下限。简单处简洁说明；若会留下“是什么、为何、如何发生”的疑问，就补背景、定义、因果、桥接或中间步骤。背景、目的、意义应具体回答来由和学习价值，交代清楚即收住。删重复、离题和不推进理解的铺陈，不删核心机制所需的锚点、桥接、中间计算、背景或推理；仍无法连贯承载时扩写或拆章，不压成专家摘要。

大幅压缩或重写章节前，列出重要知识点及其读者作用，检查前置背景、方法目的、相关前人做法及不足、当前回应和总结是否构成必要路径；再决定保留、合并、选读、迁移到明确入口或删除，并在 `progress/` 记录主要取舍和理由。清单用于发现缺口，不是保留配额：重复、过细、过时、无可靠依据或超出章节承诺的内容可删，支撑理解来龙去脉或完成目标的内容不能只因篇幅而删。“重写”允许重组，不自动代表缩小范围；只有章节定位或用户要求改变时才调整覆盖面。

章节正文的实质修订不只是转述现有稿件：凡涉及方法机制、核心技术结论、时效事实、效果主张，或发现读者需要的知识缺口，都应按模块 03 联网核对原始论文、技术报告或官方资料，并判断是否需要补充知识。正文引用要说明来源支持什么、不能推出什么；新增知识及来源证据记入 `research/`，本轮修订决定与结果记入 `progress/`。若任务仅修正公式定界符、排版、错字或其他不改变含义的局部表达，可按模块 03 免做新检索；若改动公式语义、推导或适用条件，则须核对其依据。

必要时用覆盖图记录知识点对读者结果的作用、讲解重点和去向。覆盖面看本章承诺的主题是否交代；深度看读者能否理解机制、关键推理，或按目标完成实现、判断和评估。标题出现不等于覆盖，段落多不等于讲深；覆盖图也不要求逐点配例子、公式、代码或其他形式。

## 6. 必要深度与可选加深

核心知识须让初学者理解对象和机制；可由目的、背景或意义引入，用合适锚点展开，再说明步骤、行为逻辑和一般规则。具体采用哪些步骤、顺序如何，取决于主题和读者前置，不必填满固定栏目。影响结论或正确使用的条件、证据和边界属于主线。更深推导、替代方法、实现差异、研究证据或失败分析，仅在解释重要差异、支持本章结果或回答明确问题时加入；方法可用“模型—目标—算法”组织，其他内容按自身逻辑。

覆盖面与深度要分别判断：本章承诺的主题是否都有交代，读者是否能跟住核心过程和推理，或按目标完成实现、判断、评估。例子、边界、公式和代码按其理解作用选择，不逐点配齐。主线用于安排先后，不可删去其他核心主题来换取表面连贯；若必要覆盖和深度无法在一章中兼顾，就扩写或拆为连续篇章，说明结果、依赖和过渡。本章承诺范围内的实现细节要有正文入口；额外实现可选读。重复、过细或不再服务目标的内容可合并、删除或迁移，并说明去向。

方法的来龙去脉不是按年份罗列术语。按需交代必要前置和目标、相关前人做法及不足、当前方法改变的表示/目标/算法、运作机制、证据支持的改进和限制，再回到开篇问题。只保留帮助理解当前主题的前置工作，不穷举文献或搬运 Related Work。历史和效果主张按模块 03 核实，不凭记忆补技术史，也不把局部证据写成普遍进步。基础概念若无有意义的前史，就说明真实依赖和使用背景，不杜撰演进。

## 7. 章节完成前做整体读者检查

验收单位是章节整体及其承诺的读者结果，不是逐点清点教学形式。沿阅读路径复读，确认：

- 读者知道本章和关键知识为何值得学、要解决什么问题，以及它们怎样服务书册目标。
- 背景和方向足够，锚点或过程能帮助理解关键关系；先后顺序可以变化，只要整体路线清楚。
- 读者能沿解释看懂对象如何变化、结果为何产生，并用自己的话说出结论；仍会问“这是什么”或“为何做这一步”时，补定义、对象对应或推理台阶。
- 简单处不反复铺陈，困难处不省略必要解释；背景、目的和意义具体而不空泛重复。
- 章节兑现承诺、前后衔接，事实可靠；方法提出/比较所需的背景、前人做法、不足、当前回应和结论都清楚，影响结论的假设、证据和边界放在读者需要处。

例子、公式、代码、图表、伪代码、类比和练习都是可选教学方式；有它们不代表讲清，没有它们也不自动构成缺陷。仅当它们是章节承诺的交付物或理解所必需时，才按具体需要验收；代码缺失只有在承诺编码、API 调用或程序复现时才可能阻断。

发现断点后，先定位是读者方向、前置、锚点、术语、步骤、因果、证据还是结构，再补最关键处。不要为填形式项目新增无用内容或只堆同义句。单章无法连贯交付读者结果时调整结构或拆章；读者结果、可读性和事实可靠性优先于清单。

## 8. 让正文保留作者的讲述声音

正文应像作者在解释一个真实问题，而不是逐项填规范。可用清楚判断和过渡带路，不必刻意聊天或频繁自称“我们”。

- 核心主线须让具备声明前置的初学者跟得上。适合时用真实技术对象演示动作和结果，再引出术语、规则和有用公式；不要只在开头给初学者入口，随后堆专家术语。
- 例子优先选主题本身的小数据、向量、请求、状态或短代码。无关背景、角色和对话不因“亲切”而添加；生活类比确实更省力时才用，并及时回到真实机制。
- 在读者最可能疑惑处具体回答，可由眼前例子推广到一般规则。不要只给定义或结论，不用连续设问代替解释，也不以“简单来说”掩盖跳步。
- 段落间要有真实承接：困难怎样引出定义、公式或例子，例子又验证或修正什么。少用无实际作用的“下面介绍”“综上”“为后文打基础”等套句。
- 判断落在当前对象上：说明假设何处起作用、结果支持什么、限制影响谁，并给理由和证据；不编造亲身经历或夸大口吻。
- 术语、表格、标题和清单只在帮助看清关系时使用。检查问题可在连贯解释中一并回答，不必逐项设标题或重复段首提示、段末总结和章节小结。
- 朗读关键段落，检查句子衔接、例子作用和结论过渡。若一句话可原样放进许多无关章节，改成针对本章对象的解释或删去。

讲述声音来自替读者作取舍、讲完整推理并诚实交代边界，不等于随意口语、拟人化或堆故事。检查清单是写作后台；正文要把读者需要走的推理台阶摆出来。
