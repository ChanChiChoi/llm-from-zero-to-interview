# 模块 02：章节正文写作规范

本模块读取 02a 已确认的章节、小节标题及各部分的中心思想与知识范围，负责联网研究、选择讲解形式并编写正文。02a 决定讲什么与知识分工，02 自主决定怎样讲：切入点、段落组织、叙述步骤、锚点、例子、公式、图和代码都根据具体知识选择。不要把本模块的流程、表格或检查项原样变成正文标题。

02 的核心工作是将各小节中心思想扩展为具体、完整、面向读者的讲解，而不是再从头规划章节。小节焦点应由 02a 明确，02 通过研究补足细节并讲透；若大纲把多个独立主题杂糅在同一小节、导致正文无法聚焦，应返回 02a 细分知识任务，不能自行另编结构，也不能在宽泛标题下不断堆入不同主题。

02 对讲解形式及其理解效果负责：先让具备声明前置的小白读懂对象、过程和因果，再按本册深度推进到能够与企业面试官讨论算法执行、设计理由、实际场景、失败问题和成本收益。写作自由以读者真正理解为前提，不能用“列公式—解释符号—宣告结论”代替具体机制与实践认识。公式及必要推导用于准确表达、归纳和升华理解；面试能力来自解释、追问与条件分析，不是背答案或假装拥有未做过的项目经验。

章节职责、依赖或范围不清时，先回到[模块 02a：章节定位与组织结构](02a-章节定位与组织结构.md)；正文涉及事实、方法、效果或时效信息时，按[模块 03：研究与证据管理](03-研究与证据管理.md)核验；公式、代码、图表和引用按[模块 04：图表公式代码与引用](04-图表公式代码与引用.md)处理；交付记录与验收按[模块 05：维护同步与完成门禁](05-维护同步与完成门禁.md)执行。

## 一、先确定修改类型

正文任务分为“主题推翻重写”“主题思想不变重写”和“打补丁”。开始前明确本轮涉及整章、若干小节还是局部内容，并选择对应方式。两种重写都以有效的 02a 大纲为依据；区别在于是否参考旧正文，不在于是否可以自行改变大纲。

| 类型 | 适用任务 | 交付要求 |
| --- | --- | --- |
| 主题推翻重写 | 用户明确要求从头写，或已明确旧正文不能继续作为写作基础，需放弃原有讲法 | 重新完整读取 02a 对应大纲，不参考旧正文，从研究和中心思想出发重新写作 |
| 主题思想不变重写 | 中心思想仍适用，但存在段落或上下文矛盾、补丁累积、承接不畅、锚点粗浅或不适合、讲解方式或正文组织失当等问题 | 读取 02a 大纲与旧正文，旧稿可以参考；围绕既定中心思想重新组织和书写，不沿旧段落逐项补缺 |
| 打补丁 | 公式修正、代码或链接修复、局部事实更正、限定段落修改等局部任务 | 阅读受影响内容及关联上下文，修改限定范围并验证；不因此宣称整章精修完成 |

用户要求“全书精修”“章节精修”而未指定模式时，默认采用主题思想不变重写，不自动进入主题推翻重写，也不能降为零散补缺。参考旧稿不意味着保留旧段落：可以放弃不合适的锚点、叙述路线和表达，重新建立连贯正文。

尚无旧正文的首次写作按主题推翻重写中的从头写作流程执行，无须诊断不存在的旧稿，也无须证明旧稿不可用。

“主题推翻”指推翻旧正文的写法和内容组织，不是推翻 02a 已确认的中心思想。两种重写都遵循当前有效的 02a 标题、层级、顺序和中心思想；旧正文与大纲不一致时以有效大纲为准。若中心思想、知识分工或标题结构本身需要改变，先返回 02a，不在 02 中自行重定主题。

前两种重写都必须在本轮联网研究知识事实、适合小白的讲法和相关实践，按第三节执行；02a 已研究、旧稿有引用或作者熟悉主题，都不能代替本轮研究，也不能只围绕旧稿找佐证。

三类任务均可用补丁工具编辑文件；这里的“打补丁”指内容修改策略，不指编辑工具。局部修复是合理任务，但不能充当任一种重写的完成依据。

联网要求按修改的实质判断，不按三类任务的名称或改动大小判断。凡涉及知识修正、讲解意图或读者目标修正、概念关系、机制、例子含义、推导、适用条件或内容取舍，都必须按模块 03 联网获取资料后再写；只改一个段落也不例外。只有不改变知识含义、条件和讲解意图的语句润色、错字、排版、链接格式及公式显示修复可免新检索。公式修正若改变数学含义、假设或计算口径，也必须联网核验。

## 二、三类任务的执行流程

### 主题推翻重写：读取 02a，从头写正文

按用户明确要求或已确认的重写必要性采用，并在 `progress/` 记录原因。重新完整读取当前有效的 02a 章节大纲，包括章、小节标题及中心思想和知识范围，结合当册总纲理解读者与深度要求。不为诊断而通读旧正文，不摘取旧稿段落、例子、公式或讲解路线作为写作参考。若此前已经读过旧稿，也应将其排除为本轮底稿，不做逐段改写。

按第三节完成研究、锚点选择与正文展开，从头写出本轮范围内的完整正文。以有效大纲、研究与第三至第五节的要求验收，不通过对照旧稿判断是否完成。

### 主题思想不变重写：旧稿可参考，围绕中心思想重新讲清

按以下顺序完成。顺序是工作流程，不是固定的章节结构；可根据主题合并或调整讲解步骤，但不得跳过相应判断。

#### 1. 读取大纲和旧稿，定位理解断点

动笔前先完整读取 02a 对应章节大纲，明确各小节的中心思想和知识范围，再完整阅读本轮重写范围的旧正文，包括例子、公式、图表、代码及引用。整章精修须通读整章；限定小节重写须读全相关小节，并核对上下游承接。不能仅靠标题、摘要、搜索命中或局部片段判断。

从读者的理解路径定位问题：章节究竟要教会什么，现有顺序是否合适，前置和定义是否在需要处出现，机制是否完整，是否被公式逐项释义取代，例子是否真正承载解释，是否有重复、拼接、跳步和前后口径变化。句子通顺不代表整章教学连贯；重点检查读者能否持续跟上对象、问题和推理的变化。

形成简短的问题诊断与重写方向，写入对应 `progress/`。诊断应指出主线和理解断点，不只是列“缺少例子”“公式没有代入数值”等形式缺项；此时不要开始逐项往旧稿塞补充段。

对照 02a 的中心思想梳理必要知识与关键关系，区分可参考的可靠材料和应放弃的旧表达。旧稿不能反过来替代 02a 决定主题；也不能因为中心思想不变，就保留前后矛盾的段落、失配锚点或反复拼接的组织。

#### 2. 研究、选择支架并重写各主题

按第三节研究并重建讲解路径、锚点和正文组织。旧稿中可靠且适合的材料可以参考，但须核对正确性及其在新讲解中的作用；失配锚点与不当组织可以整体替换。重新写出连贯解释，不按旧段落逐项补缺，也不只为公式变量填几个值。

#### 3. 整章复读

检查各主题是否兑现 02a 的中心思想、前后是否自然承接、符号与例子是否一致，并根据研究检查必要知识是否遗漏。按第五节及模块 04、05 验收；限定小节重写还须复读关联上下文，整章精修须整章验收。若大纲无法承载必要知识，返回 02a；若必须排除旧稿重新起草，再明确切换为主题推翻重写，二者不能混同。

### 打补丁：限定范围，修复局部

1. **确定范围**：明确需重写的段落或待修缺陷，阅读相关上下文及关联定义。
2. **核验并修改**：部分段落可以整体重写，公式或代码可以定点修正；凡涉及知识、讲解意图、目标或其他实质内容变化，均按第一节的联网规则先研究再修改，不能因属于打补丁任务而跳过。
3. **复验关联内容**：检查修改处与前后衔接，执行相应公式、代码和链接门禁，记录局部交付范围。局部修复不等于整章已经精修。

若局部修改已牵连多个段落或主题的解释路径，应重新判断是否需要主题思想不变重写，不持续堆补充段。若讲解路线本身可行，只需修复一处公式或有限表达，仍采用打补丁。用户限定局部任务时先完成可独立交付的修复，记录其余问题；不能仅因发现整体问题就自行升级为主题推翻重写。

## 三、重写的共同写作要求

本节适用于主题推翻重写和主题思想不变重写；局部任务按修改所涉及的要求执行。旧稿是否参考按第二节执行，两种重写均以有效 02a 大纲为准。

### 1. 确认写作契约

开始写正文前，读取有效的 02a 章节大纲、各小节中心思想与知识范围，并结合当册总纲确认读者前置、深度和读者结果：

- 本章解决什么问题，属于全书或本册的哪项承诺。
- 读者是谁，默认具备哪些知识；哪些必要前置需在本章简短唤回。
- 读者读完应能解释、判断、操作或完成什么。
- 本章必须覆盖什么，哪些内容不属于本章，哪些实现或推导是选读。

若契约缺失或互相冲突，不要靠扩写正文猜定范围，返回模块 02a 澄清。重写允许调整讲解顺序和表达，不自动意味着可以缩小或扩大章节承诺。

为讲清既定中心思想而补充必要定义、前置、内部细节、证据、反例和实践材料，属于 02 的正常职责，不必每发现一个新知识点就返回 02a。改变小节中心思想、知识归属或标题结构时才返回 02a。正文可以用段落、列表、步骤标签组织解释，但新增或调整编号标题层级须先更新大纲。

### 2. 联网研究并确定必要内容

实质编写或修订前，必须按模块 03 联网研究本章涉及的方法机制、关键事实、时效信息、效果与比较主张，并判断读者是否需要尚未覆盖的知识。检索要面向“弄清知识并找到好讲法”，并行查找知识证据与教学解释来源，不把论文当成正文的唯一底稿。论文、技术报告、官方文档、博客、课程讲义、公开 notes、教材和源码分别按其能支持的主张使用；具体检索入口见[联网数据来源](联网数据来源.md)，证据核验按模块 03 执行。借鉴教学材料的解释方法后，要用自己的结构讲清，不能摘抄拼接。

将本章承诺拆成必要知识点，标明它们服务的读者结果、依赖关系和去向。此清单用于发现遗漏、重复和错位，不是保留配额。删、并、移内容时，确保必要前置、因果桥接、关键中间步骤、证据和边界没有随篇幅一起消失。新增知识与来源证据写入 `research/`；本轮编辑决定、状态和未解问题写入 `progress/`。

对抽象、复杂或旧稿讲不清的知识点，主动搜索通俗解释、可视化讲解、从零实现、课程笔记和讲义，不把检索停在论文摘要、公式及符号释义上。可以借鉴这些材料呈现对象关系、建立直觉、连接机制与具体过程的方式，再根据本章读者和知识点重新组织。白话表达仍须准确，不能用类比替代真实机制，也不能为通俗省略关键条件；没有必要为每个知识点凑齐所有来源类型，但不能整章只读论文、再把论文逐句改写当作面向小白的讲解。

对有工程应用的知识点，主动检索业内同行的实际经验：工程团队技术博客、实践笔记、实现说明、案例复盘、性能测试和失败分析。重点寻找实际怎样做、为何如此选择、遇到什么问题、如何诊断，以及效果和代价怎样测量。这类材料是理解真实使用的重要来源，不只是正文末尾的装饰；论文中的理想设置不能替代实践条件，同行经验也不能直接外推为通用结论。找到适用材料时将其融入机制和工程判断，交代任务、规模、版本、约束与来源；未找到可靠经验时明确资料边界，不虚构生产案例、参数经验或收益数字。

先读取上游交接的相关研究入口及支持范围，再补查当前知识与讲法，不能丢弃已有资料重新盲搜，也不能以复用为由免除本轮联网。研究同时区分原始方法、框架实现、作者实践和教学简化，避免把某个实现的选择写成算法必然要求。

研究触发与免检索范围统一按第一节执行；已有材料可用于研究，但不能以旧稿、记忆或模型自身判断替代本轮所需的联网资料。

### 3. 选择主导讲解路径

依据研究与 02a 大纲安排解释过程。主题推翻重写从头建立讲解路线；主题思想不变重写可参考旧稿，但可以重新安排小节内部的段落、必要前置、例子和过渡。02a 不规定这些形式，两种方式都应自主判断，并兑现相同的中心思想与必要知识范围。

判断本章或当前小节主要帮助读者完成哪类任务。内容可以混合，但应有清楚的主导任务；任务切换时用结构和过渡让读者知道阅读目标已改变。

| 主要任务 | 读者要回答的问题 | 常见组织路径 |
| --- | --- | --- |
| 概念或架构 | 这是什么？现象为何发生？ | 现象或疑问 → 对象关系 → 必要术语 → 机制与边界 |
| 方法、算法或推导 | 为何需要此法？它怎样工作？ | 问题与必要前置 → 关键过程 → 目标/规则 → 必要推导 → 条件与限制 |
| 系统或工程机制 | 请求、数据或状态经过什么？ | 输入与初态 → 关键动作 → 中间状态 → 输出 → 并发、失败与取舍 |
| 操作教程 | 怎样完成一个明确任务？ | 目标与前置 → 环境和输入 → 操作及预期输出 → 错误恢复 → 验证 |
| 项目或实战 | 怎样组合技术交付成果？ | 任务与验收 → 最小实现 → 逐步扩展 → 评估、故障与取舍 → 交付 |
| 论文、证据或方案比较 | 主张是什么？证据支持到哪里？ | 对齐问题和条件 → 方法差异 → 可比证据 → 结果、代价和边界 |
| 参考或查询 | 参数、接口或限制的准确值是什么？ | 对象入口 → 定义、输入输出、版本、约束和错误 → 最小示例及相关入口 |

这些路径只帮助选择讲解顺序，不要求逐项变成标题。操作教程可以解释必要原理，机制章节也可以包含操作。参考型内容可直接围绕真实对象、用途和约束说明，不必虚构情境。

方法章节可用“模型表示什么、目标是什么、算法怎样实现目标”作为检查坐标，避免把表示、优化准则和求解过程混为一谈。这是分析方法的工具，不是每章都要出现的固定三段式。比较方法时先对齐任务、数据和假设，再比较机制、证据、适用条件、代价及失败边界。

### 4. 按知识复杂度选择讲解支架

不要把“锚点”理解成每个知识点都要配一个小故事或玩具算例。先判断读者需要看清的是一个局部关系，还是一条跨阶段、跨组件的完整机制，再选能承载该复杂度的主支架。主支架是读者理解内容时可持续追踪的对象、关系或过程；相关知识点可以共用支架，但必须说明各自对应的部分。

锚点是让小白获得具体理解的方法约束，不是可随意删去的装饰。核心机制必须落到可追踪的对象、过程或关系上，不能仅说“根据优势更新策略”“计算损失并优化”就认为已经讲清。形式可以不同，但读者应能指认输入、参与对象、关键动作、中间变化与结果，并理解为什么这样做。简单概念可用短例子或对照；复杂算法既要有主要机制的全貌，也要有具体执行的落点。

| 内容复杂度 | 主支架选择 | 讲解要求 |
| --- | --- | --- |
| 单一概念、局部规则或简单操作 | 一个贴近真实用途的短例子、对象关系或对比 | 例子直接揭示概念或规则；不为凑形式扩成故事 |
| 有先后步骤但状态较少的过程 | 状态追踪、编号步骤、简短流程图；必要时配一个例子 | 交代起点、动作、状态变化、原因和结果 |
| 多阶段算法、含循环/分支/多个更新对象的方法，或组件协作机制 | 呈现关键结构的伪代码、流程图、状态图、数据流/时序图、分阶段说明或组合形式，并配合具体执行过程 | 让读者建立机制全貌，沿锚点说明阶段职责、条件、输入输出与更新对象，并用贯穿实例、执行轨迹或状态变化走过关键阶段。入口和顺序可以调整，但不能只给抽象骨架或孤立算例，不因复杂就默认套用伪代码 |
| 多方并发、资源调度、消息传递或时间关系 | 时序图、数据流图、状态表或执行轨迹 | 标清参与者、顺序、同步点、状态变化和边界；局部小例子只能辅助说明 |
| 参数、接口或准确事实查询 | 真实对象、定义表或最小示例 | 给出准确值、版本、约束和错误边界；无需虚构故事 |

根据读者卡点选择具体表达形式；只有在提供新信息时才增加辅助形式：

| 锚点形式 | 适用情况 | 写作要求 |
| --- | --- | --- |
| 真实问题或小场景 | 读者不知道知识为何出现、要处理什么 | 交代真实任务、输入、目标和困难；场景简短并服务于机制 |
| 贯穿算例或完整小例子 | 需要把抽象机制映射到具体对象，或追踪变量、状态与结果 | 交代任务、输入/初态、假设、关键动作和结果；复杂方法中用于走查主支架，不替代全局算法或机制结构 |
| 数值演算 | 读者需要复算损失、更新或中间结果 | 说明玩具数值和假设；展示必要中间量及原因，并嵌入能解释整个知识点的例子 |
| 状态表或执行轨迹 | 变量、张量、请求、资源或参与者逐步变化 | 按初态、动作、新状态和原因追踪；表格之外仍需解释因果 |
| 伪代码或编号步骤 | 伪代码适合表达算法控制流、循环、分支、阶段顺序或停止条件；简单过程可用编号步骤 | 算法伪代码优先采用代码式结构：用有意义的变量、函数调用、循环/条件和明确的更新语句呈现输入到输出的主要路径，并用简短注释解释目的、约定或省略项。避免把每一步写成自然语言句子后仅缩进排列。省略工程实现可以，但不得省略改变算法含义的阶段或依赖。若图示、状态轨迹或分阶段说明更清楚地呈现机制，可选用那些形式，不必为了形式完整另加伪代码 |
| 流程图、架构图、数据流或时间线 | 组件关系、数据去向或时序难以用段落呈现 | 标清对象、起止点和箭头含义，并追踪代表性对象；图不能代替因果解释 |
| 对齐的多种表示 | 从例子、图、公式到代码时容易断开 | 指出同一对象在各表示中的对应关系，以及新表示增加了什么信息 |
| 类比 | 关系抽象且读者确实熟悉对应经验 | 说明对应关系和失效边界，随后回到真实对象和机制 |
| 代码、交互或模拟 | 读者需要观察执行或变量变化 | 先提出观察问题，再比较输入与输出，并把模拟状态连回真实系统或模型 |

复杂算法的全局支架呈现阶段、条件、更新与结束路径，贯穿实例或执行轨迹展示它们怎样作用于具体输入；两者相互对应，不能互相替代。数值不是必要条件，算术会遮住机制时可追踪对象、状态、消息或决策。公式、代码、图与术语要能对应回锚点，多种形式各自增加什么信息也应清楚。教学简化、假设值和模拟输出须标明，不得冒充真实数据、通用配置或效果保证。

PPO-RLHF 范例展示了执行机制应达到的具体程度：伪代码抓住模型角色、采样、训练信号和更新，正文沿动作解释，再让同一条回答走过关键步骤。可借鉴的是“骨架可见、细节可追踪、例子与机制对应”，不是固定标题或伪代码配额；它的工程经验与成本收益讨论仍不完整，不能作为全部写作要求的完成样板。函数封装可以隐藏无关实现，但不能遮住本节正要解释的核心关系。

### 5. 沿讲解路径展开正文

按照新组织从头到尾书写正文，让知识点、支架、公式和推理相互衔接。不是先保留旧稿、再逐项补例子或定义；例子和演算应进入新的解释过程，必要时连同前后段落一起重写。为公式变量赋几个数值，只能验证某个计算环节，不能自动补足概念、完整机制和章节教学路径。

让读者从问题走到能复述、走查并应用的一般机制。以下是需要完成的理解任务，不是固定叙述顺序或正文栏目：

1. 交代问题、目标或读者当前要理解的现象。
2. 呈现与复杂度相称的主支架，建立对整体机制的认识，说明必要对象、输入、初始状态和假设。可以从真实问题、具体执行或机制全貌切入，但不能让读者只见局部计算、不知整体怎样运行。
3. 沿主支架解释关键步骤、状态变化、因果和输出；复杂算法通过贯穿实例、执行轨迹或状态变化走查关键阶段，并补齐必要术语、前置和中间推理。具体执行的落点不能因“形式自由”而省略。
4. 加入有助于理解或使用的公式、伪代码、图表或代码，并明确各自与主支架的对应关系。选定的全局支架必须足以呈现机制；不要用局部算例替代全局结构，也不要为了形式完整而重复添加不能增加理解的表示。
5. 概括可推广的规则，说明适用条件、证据边界、代价和失败情况。
6. 收束到当前中心思想并自然连接后续内容；采用问题开篇时回应相应问题，不强制每小节设问或重复总结。

“背景、目的、意义、问题、使用场景、优缺点”不是每个章节或小节都必须设置的栏目。讲解具体知识点时，若这些信息有助于理解，就融入知识点本身：例如介绍 Reward Model 时，可以在说明它如何把回答比较转成整条回答的分数时，一并讲清它解决的问题及在训练流程中的作用，不必再分列“目的”“使用场景”“意义”等小节。像章节承接、路线说明或概念过渡这类衔接小节，只需完成衔接任务，不要为了形式完整补写这些栏目或一段小例子。只有信息彼此不同且显式分区有助定位时才单独展开；重叠项合并，不适用项省略。没有真实技术前史时说明必要依赖和问题，不编造冲突或演进故事。

### 6. 从工程使用与面试追问补足理解

算法或方法不能只交代定义和优化目标。围绕当前知识点，把它解决的问题、执行机制和实际取舍连起来，让读者能够从“是什么”回答到“为什么这样做、实际怎么用、何时不值得用”。下表提供可结合主题展开的内容方面，不是每小节必须设置的栏目；核心算法应覆盖相关的重要方面，衔接小节不套用这些要求。

| 内容方面 | 面向读者需要讲清的内容 |
| --- | --- |
| 提出背景与原有问题 | 原有做法遇到什么具体困难，新方法针对什么矛盾；区分技术动机与有来源的历史，不编造演进故事 |
| 内部执行与设计理由 | 谁接收什么输入、执行什么计算、改变什么状态、产生什么输出；关键步骤为什么存在，去掉或改变会有什么影响 |
| 适用任务与进入条件 | 什么问题值得采用，需要什么数据、反馈、模型或环境；什么场景不适合，替代方案是什么 |
| 实际工作做法 | 同行如何准备数据、配置流程、组织实现、观察指标、调试和处理失败；指出其与教学简化的差别 |
| 效果、准确度与质量 | 相对什么基线、在什么任务与评价口径下改善什么；按任务采用正确率、偏好胜率、召回、误差或其他适当指标，不笼统说“准确度更高” |
| 性能与资源代价 | 训练或推理的时间、延迟、吞吐、显存、计算、通信、数据标注、存储和工程维护等相关成本，说明主要瓶颈来自哪个机制 |
| 收益与取舍 | 用哪些成本换取哪些质量、速度、稳定性或可控性收益，条件变化时是否仍值得，不能将某项指标提升等同于整体更优 |
| 注意事项与失败分析 | 关键假设、常见误用、异常信号、排查方向和能力退化，解释问题如何产生而不只列警告 |
| 方法比较与选择 | 对齐任务、数据和约束后比较机制与取舍，说明为什么选此方法、何时应换另一种 |

有可靠测试或实践数据时给出相应条件与数字，核对基线、模型规模、数据、硬件、版本、指标和测量口径。证据不足时，可以根据机制解释定性的成本来源及待测事项，不能虚构精确收益，也不能把理论复杂度直接当成实测加速比。没有统一“性能”或“准确度”数字，并不妨碍讲清适用性，但应明确不能作出的比较。

面试能力应从上述理解中自然形成。读者应能沿关键对象讲出算法执行，说明设计理由，分析条件变化，并讨论一个实际选择或失败问题；不要求正文处处变成问答题库，不把现场推导公式作为所有知识点的默认学习终点。总纲承诺关键推导或数学分析时仍须完成，并把它与机制及使用条件联系起来。

### 7. 让公式深化理解，并决定代码与扩展内容的去向

公式用于准确表达关系、目标或约束，承担计算、关键推理及知识提炼的作用。默认先让读者认识问题、对象和具体过程，再用公式归纳或深化；推导型内容可以较早引入公式，但仍须同步建立具体含义，不能将符号释义当成全部解释。研究中找到能揭示关系或推广认识的公式，可以作为升华引入，说明它与已讲机制的对应及增加的新理解，不能只因来源有公式就照录。

公式中的对象应能对应回锚点、执行过程或具体任务。读者不仅应知道每个符号叫什么，还应理解关系为什么这样写、改变某项会影响什么、何时成立。目标函数不等于算法执行，公式代入几个数也不等于完整实践认识。必要公式和承诺的关键推导不能为追求白话而删除；复杂算法的机制与具体执行要求仍按第四、第五项落实。来源、适用条件、符号口径、mask 及求和/平均方式按模块 03 和模块 04 核对。

代码只在本章承诺读者完成编码、API 操作或程序复现时作为必需交付；其他情况下可作为辅助验证。代码段须说明任务、输入输出和关键状态，不能只因可运行就算讲清机制。实现版本、配置、日志、API 和更深推导仅在影响本章结果、读者任务或结论时进入主线；其余内容可移入明确标识的进阶入口。影响结论或正确使用的条件、证据和限制始终属于主线。

正文没有统一字数或页数配额。删去重复、离题和不推进理解的内容，但不删必要前置、锚点、因果桥接、中间步骤、证据和边界。可在既定结构内充分展开；若仍无法连贯兼顾覆盖与深度，应返回 02a 调整结构或拆章，而不是压缩成专家摘要。调整内容去向时，在 `progress/` 记录主要取舍和理由。


## 四、讲解质量规则

### 面向声明前置的初学者

“初学者”指具备本章明确声明的前置知识，不代表毫无基础。不能用有经验的工程师能猜懂来替代必要解释，也不能以简化语言为由删掉必要术语、数学、实现深度或证据。读者完成核心阅读后，应能说明知识点解决什么、关键对象或步骤如何工作、结果为何成立；专家证明、变体和争论只在本章承诺或读者结果需要时展开。

只唤回当前推理需要的前置。新术语在读者需要处解释其对象、作用和易混点；连续出现多个缩写时分组介绍。跨章链接不能代替本章理解所必需的一两句说明。涉及大模型数据流时，按主题需要解释文本、token 与 token ID，模型分数与概率，训练目标与参数更新，生成与上下文延续之间的关系；不要默认这些关系读者已经掌握。

### 说明对象、动作和真实因果

段落围绕一个主要解释任务。告诉读者当前要看什么，并解释动作为何发生、产生何种变化、结论由什么支持。步骤复杂时拆开或编号；不要把多个动作、条件和结论塞进一句。避免用“显然”“简单来说”“只要……就……”跳过推理，也不要用拟人化、空泛设问或同义句堆叠代替机制。

比较概念时先对齐维度，再说明差别；使用反例是为了揭示容易误判的边界。判断要落到当前对象：假设在哪一步起作用，证据支持什么，限制影响什么。结论有条件就写出条件，不把局部结果推广成普遍事实。

### 控制信息量和讲述声音

每段或步骤处理一个主要任务。新对象较多时先分组并说明关系；短句、列表和步骤标签服务于追踪，不要拆成没有因果的口号。沿用已确认的标题层级，具体解释可使用段内提示、表格和列表，但不能借此另编一套目录。

正文要像作者在解释真实问题，而不是逐项填规范。段落之间应沿对象、机制与推理真实承接；问题、锚点、术语、公式和边界的出现顺序按理解需要决定，不套用统一叙述路线。避免重复段首提示、段末总结和“下面介绍”“为后文打基础”等无实际作用的套句。讲述声音来自完整推理、具体取舍和诚实边界，不来自聊天口吻或故事数量。

## 五、章节验收

交付前沿章节整体复读，并按本章承诺检查：

- **任务类型**：主题推翻重写已重新读取 02a 大纲且未参考旧正文；主题思想不变重写已读取有效大纲与重写范围内的旧稿，并重新组织连贯正文；打补丁仅声明实际修复范围。两种重写均兑现 02a 的标题结构和中心思想，章节精修默认采用主题思想不变重写。

- **契约**：读者、前置、目标和范围与已确认的章节定位一致；本章说明其对书册目标的贡献。
- **覆盖**：本章承诺的重要知识点都有正文入口；标题出现不等于讲清，段落多也不等于讲深。
- **讲解支架**：支架与复杂度相称；局部概念不被扩成多余故事，复杂算法不被缩成孤立公式、局部演算或单个小例子。
- **算法完整性**：复杂算法既有输入输出、阶段职责、关键条件、状态与更新对象、结束路径的整体认识，也有具体输入或状态经过关键阶段的执行落点；锚点、正文与实例或轨迹相互对应，函数名没有遮住核心机制。伪代码不是固定要求，具体理解是要求。
- **理解**：读者能沿主支架复述关键对象、动作、变化和结果；仍会问“这是什么”或“为什么做这一步”时，补上定义、对应关系或推理台阶。
- **表达形式**：锚点使机制具体可追踪；各例子明确承担局部说明还是整体走查，整体讲解完整，不要求单个例子包办全部知识；公式对应已有理解并带来深化，代码与图表不脱离正文。不能仅以公式、符号释义和结论交付核心算法。
- **工程与面试理解**：按本册深度，读者能解释问题、执行细节与设计理由，讨论场景、选择和成本收益，并依据机制分析追问，而不只会背公式、优缺点或例子数值。行业实践已主动检索，有材料时交代条件，没有可靠材料时不虚构；效果比较有基线和口径，不冒充实践经历。
- **事实**：关键方法、事实、效果与比较主张有相称证据；影响结论的假设、条件和限制出现在读者需要的位置。
- **取舍**：没有为满足模板新增空洞栏目；删减没有破坏必要覆盖、因果、证据或边界；选读内容有明确入口。
- **连贯**：章节前后承接，各部分围绕中心思想展开；采用问题开篇时有相应回应，不机械要求处处设问和总结。

有目标读者时，观察其独立复述、复走过程或预测条件变化时卡在哪里；不要先给答案再问是否理解。没有试读时做初次接触检查：沿正文路线复走锚点，标出未解释术语、隐含条件、记号切换和无理由跳步。朗读可检查句段衔接，但不能单独证明机制已理解。

发现断点时先定位问题属于契约、前置、对象对应、步骤、因果、证据还是范围，再修正文中缺失环节。不要只堆近义句或改成模糊口语。单章无法连贯交付约定读者结果时，返回模块 02a 调整结构或拆章。
