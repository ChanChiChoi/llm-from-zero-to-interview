# 第一章：产品化总览

大模型项目最容易犯的错误，是把 demo 当产品。一个 demo 能在演示时回答几个问题、生成几段文本、调用一次工具，并不代表它可以稳定服务真实用户。产品化要解决的不只是模型效果，还包括用户需求、体验设计、成本、稳定性、安全、合规、运营反馈和商业价值。

本章是第十八册的总览。我们从“demo 到产品”的差距开始，系统讲大模型产品化需要关注哪些问题：用户价值、场景选择、产品体验、稳定性、成本、ROI、安全合规、上线运营和反馈闭环。对算法工程师来说，理解这些内容能让你在面试和项目复盘中不只会讲模型，也能讲清楚技术如何产生业务价值。

## 0. 本讲范围与资料

本章参考 OpenAI Evals / evaluation 公开文档、OpenAI 延迟优化与生产应用相关文档、Google SRE 中 SLI / SLO / error budget 的可靠性口径，以及 NIST AI RMF / Generative AI Profile 的风险管理资料边界。

本章聚焦产品化总览：如何把大模型能力转成用户价值、业务指标、单位经济账、可靠性指标、安全合规和反馈闭环。它不替代后续章节的用户研究、ROI 细算、企业应用、RAG / Agent / 多模态落地、隐私合规或上线运营细节。

大模型产品化的判断标准不是“是否接入了模型 API”，而是是否围绕真实用户任务建立了可衡量、可运营、风险可控且能够持续迭代的产品系统。

## 1.1 为什么算法工程师要懂产品化

很多算法同学习惯从模型出发：模型准确率、benchmark、推理速度、训练方法、RAG、Agent、微调。但真实公司更关心：这个系统解决了谁的问题，节省了多少成本，带来了多少收入，是否稳定，是否安全，用户是否愿意用。

产品化能力要求算法工程师能够回答这些问题：

1. 这个场景是否值得做大模型。
2. 模型能力如何转化为用户体验。
3. 指标提升是否能带来业务收益。
4. 成本是否可接受。
5. 风险是否可控。
6. 上线后如何持续改进。

这意味着，算法工程师不能只报告模型在离线数据上的分数，还要说明模型能力通过哪一个用户动作产生价值。例如，客服助手的检索质量只有在用户更快找到可用答案、减少转人工或缩短处理时间时，才完成了从技术指标到业务结果的转换。

## 1.2 Demo 和产品的区别

Demo 的目标是证明“能做”。产品的目标是稳定地为用户创造价值。

Demo 常见特点：

1. 样例少。
2. 边界可控。
3. 人工挑选输入。
4. 失败可以解释。
5. 成本不敏感。
6. 安全要求低。

产品要求：

1. 面对真实多样输入。
2. 长期稳定运行。
3. 失败可恢复。
4. 成本可控。
5. 用户体验一致。
6. 安全合规。
7. 有监控和反馈。

很多 demo 看起来惊艳，是因为输入被精心选择。产品必须面对真实用户的模糊表达、错误操作、恶意输入和长尾需求。

## 1.3 产品化的核心问题

大模型产品化至少要回答八个问题：

1. 用户是谁。
2. 痛点是什么。
3. 大模型为什么适合。
4. 成功如何衡量。
5. 成本如何控制。
6. 风险如何管理。
7. 上线后如何监控。
8. 如何持续迭代。

如果这些问题答不清楚，只是“把大模型接进来”，项目很容易变成技术展示，而不是可持续产品。

### 1.3.1 用一套账本描述候选场景

一个大模型产品候选场景可以抽象成一条记录，而不是一个孤立的模型分数：

```math
s_i=(u_i,p_i,f_i,v_i,q_i,c_i,r_i,w_i)
```

变量含义：

1. `u_i` 是目标用户或使用人群，通常是类别字段，不应被当作可加总的数值。
2. `p_i` 是痛点强度，若使用归一化评分，约定范围为 `[0,1]`。
3. `f_i` 是观察窗口内的合格任务数，例如一个月内真正需要该能力的任务数。
4. `v_i` 是一次额外成功任务带来的货币价值或可换算价值。
5. `q_i` 是系统质量向量，至少应区分任务成功率、错误类型和安全结果，不能用一个未经定义的“模型分数”代替。
6. `c_i` 是单次任务的增量成本，必须说明是否包含检索、工具、人工审核和失败重试。
7. `r_i` 是风险成本或风险状态；高风险场景不能只靠提高 `v_i` 抵消。
8. `w_i` 是工作流适配程度，例如是否能接入现有权限、审批和记录系统。

技术指标到产品指标的基本链路是：

```math
q_{\mathrm{tech}}\rightarrow q_{\mathrm{task}}\rightarrow m_{\mathrm{user}}\rightarrow b_{\mathrm{biz}}
```

例如检索召回率提升只是 `q_tech`，真正要证明的是任务成功率、用户采纳率、自助解决率、成本下降或收入提升。

任务成功率提升：

```math
\Delta R_{\mathrm{succ}}=R_{\mathrm{succ,new}}-R_{\mathrm{succ,base}}
```

月度业务收益可以粗略估算为：

```math
B=f\cdot a\cdot \Delta R_{\mathrm{succ}}\cdot v
```

其中 `f` 是观察窗口内的合格任务频次，`a` 是采用率，`v` 是单次额外成功任务的价值。`a` 和成功率都应限定在 `[0,1]`；`\Delta R_{\mathrm{succ}}` 可以为负，表示新系统比基线更差，不能为了让收益公式看起来非负而把它截断为 0。如果没有足够的基线或线上样本，`\Delta R_{\mathrm{succ}}` 应记为 `unknown`，月度收益也不能伪造为 0。

月度总成本：

```math
C=f\cdot a\cdot(c_{\mathrm{model}}+c_{\mathrm{ops}}+c_{\mathrm{risk}})+C_{\mathrm{fixed}}
```

其中 `c_model` 是模型或推理成本，`c_ops` 是检索、工具、审核、监控和运维等单次成本，`c_risk` 是在观察窗口内按任务分摊的预期风险损失，`C_fixed` 是固定研发、平台和治理成本。所有成本和收益必须使用同一货币或可解释的价值单位；没有记录人工审核或失败重试时，成本账本是不完整的。

净收益：

```math
N=B-C
```

收益成本比：

```math
R_{\mathrm{bc}}=\frac{B}{C}
```

只有 `C>0` 时，收益成本比才有定义；`C=0` 不是“收益成本比为 0”，而是分母不适用，通常应记为 `unknown` 并检查成本是否漏记。为了避免不同团队混用术语，本书采用下面的口径：`R_bc` 表示收益成本比，ROI 表示扣除成本后的净收益率。

常见 ROI 口径：

```math
\mathrm{ROI}=\frac{B-C}{C}
```

产品化判断可以形式化为：

```math
G_{\mathrm{prod}}=\mathbf{1}[\Delta R_{\mathrm{succ}}>0\land R_{\mathrm{bc}}\ge \tau_b\land L_{95}\le \tau_l\land G_{\mathrm{risk}}=1\land G_{\mathrm{workflow}}=1\land G_{\mathrm{eval}}=1]
```

其中 `L_95` 是 P95 延迟，`G_risk` 是安全合规验收条件，`G_workflow` 是工作流适配验收条件，`G_eval` 是评估和反馈验收条件。这个二值表达只适用于所有数据都已经取得的情况：若延迟样本为空、收益成本比没有定义、风险评估尚未完成或反馈数据不足，不能默认把对应条件当作真。

在实际评审中，更稳妥的是保留三种结果。设每个条件 `g_j` 属于 `{1,0,unknown}`，分别表示已通过、已失败和证据不足：

```math
\mathrm{status}_{\mathrm{prod}}=
\begin{cases}
\mathrm{failed}, & \exists j,\;g_j=0\\
\mathrm{passed}, & \forall j,\;g_j=1\\
\mathrm{unknown}, & \text{otherwise}
\end{cases}
```

`passed` 只表示当前范围和当前证据下可以进入下一阶段验证，不代表已经证明能在所有用户和所有流量下盈利；`unknown` 也不能自动升级为 `passed`。产品评审应该同时记录基线、样本量、时间窗口、分群和失败案例。

直觉是：产品化判断不是“模型分数高不高”，而是收益、成本、延迟、风险、工作流和反馈闭环是否在同一任务定义下得到证据。任何一项缺失，都应该成为下一轮实验或试点的明确问题。

## 1.4 从模型能力到用户价值

模型能力本身不是用户价值。

例如：

```text
模型能总结文档
```

这只是能力。用户价值可能是：

```text
法务人员审合同时间从 30 分钟降到 10 分钟
客服人员查知识库时间从 2 分钟降到 20 秒
销售人员生成方案初稿效率提升 50%
```

产品化要把能力翻译成业务指标。常见指标包括：

1. 节省时间。
2. 降低人工成本。
3. 提高转化率。
4. 提高解决率。
5. 降低错误率。
6. 提升用户满意度。
7. 缩短交付周期。

## 1.5 什么场景适合大模型

适合大模型的场景通常有这些特点：

1. 输入是自然语言、文档、代码、图片或多模态内容。
2. 任务需要理解、生成、总结、推理或交互。
3. 传统规则难覆盖长尾。
4. 人工成本高。
5. 容错空间存在。
6. 可以通过人审或工具验证降低风险。
7. 有足够数据或知识库支持。

不适合的场景：

1. 强确定性、低延迟、低成本规则就能解决的问题。
2. 错误代价极高且无法复核的问题。
3. 没有明确价值指标的问题。
4. 数据质量很差且无法治理的问题。
5. 用户不愿改变流程的问题。

大模型不是万能工具，选错场景会导致投入大、收益小。

## 1.6 用户体验不是模型输出

很多人以为大模型产品体验就是“回答得好”。实际体验还包括：

1. 是否知道能问什么。
2. 响应是否足够快。
3. 错误时是否能解释。
4. 是否能引用来源。
5. 是否能让用户修改和追问。
6. 是否能接入现有工作流。
7. 是否能处理用户不完整输入。
8. 是否能稳定保持风格和格式。

例如企业知识库问答，答案质量重要，但引用来源、权限控制、无法回答时的表达和反馈入口同样重要。

## 1.7 稳定性

大模型输出具有不确定性。产品化要解决稳定性问题。

常见稳定性挑战：

1. 同样问题多次回答不一致。
2. Prompt 稍变输出大变。
3. 模型版本升级导致行为变化。
4. 外部工具失败。
5. RAG 召回不稳定。
6. 长上下文下遗漏关键信息。
7. 并发高时延迟上升。

稳定性措施：

1. 固定关键 prompt 和参数。
2. 使用结构化输出。
3. 对关键任务加 verifier。
4. 监控线上指标。
5. 建立回归测试集。
6. 版本灰度发布。
7. 失败降级。

## 1.8 成本

大模型产品的成本不仅是 API 调用费。

成本包括：

1. 输入 token。
2. 输出 token。
3. 多次采样和重试。
4. RAG 检索和向量库。
5. reranker 和 verifier。
6. 工具调用。
7. GPU 推理资源。
8. 日志和监控。
9. 人工审核。
10. 数据治理。

产品化必须算单位经济账。例如每处理一个客服问题成本是多少，节省多少人工时间，是否值得。

## 1.9 ROI

ROI 不是一个脱离口径的漂亮数字。本文把收益成本比和 ROI 分开：收益成本比回答“每投入一单位成本带来多少收益”，ROI 回答“扣除成本后，相对于成本净增了多少”。因此二者分别写成：

```math
R_{\mathrm{bc}}=\frac{B}{C},\qquad
\mathrm{ROI}=\frac{B-C}{C}=R_{\mathrm{bc}}-1
```

它们都要求 `C>0`，并且 B、C 的统计窗口、用户范围和成本边界一致。研发投入、人工审核、数据治理、失败重试和风险损失若被排除，就必须在报告中明确说明，不能把一个局部账本命名成完整 ROI。

大模型项目收益可能来自：

1. 降低人工成本。
2. 提高效率。
3. 增加收入。
4. 提升留存。
5. 降低风险。
6. 提升客户满意度。

成本可能来自模型调用、研发、数据、审核、运维、合规和失败风险。

真实评估也要区分“节省了时间”和“实际减少了现金支出”。例如，助手让每个客服每天少花 30 分钟，只有在工作量减少、接待量增加或人员不再扩张时，这部分时间才可以直接换算成现金收益；否则它更适合记录为生产率指标。产品决策不要求一开始就有精确财务模型，但要求说明假设、数据来源和不确定性。

## 1.10 安全与合规

大模型产品会处理用户输入、企业数据和生成内容，因此必须考虑安全合规。

常见问题：

1. 隐私数据泄露。
2. 权限越界。
3. 幻觉导致错误决策。
4. 生成不合规内容。
5. 数据跨境或存储问题。
6. 日志中保存敏感信息。
7. 工具调用产生真实风险。

安全合规不是上线前临时补丁，而应该从产品设计阶段就纳入。

## 1.11 人在回路

Human-in-the-loop 是很多大模型产品落地的关键。

适合加入人工审核的场景：

1. 高风险决策。
2. 对外发送内容。
3. 法律、医疗、金融场景。
4. 删除或修改重要数据。
5. 模型低置信度。
6. 新系统试运行阶段。

人工不是失败，而是风险控制和数据积累方式。人工审核也会产生延迟、成本和一致性问题，因此要记录送审比例、平均处理时间、审核改写率和漏审事件。随着系统成熟，可以在明确的风险边界内扩大自动化范围，但不能只因为模型置信度变高就跳过外部验收。

## 1.12 上线不是终点

大模型产品上线后还需要运营。

要持续监控：

1. 使用量。
2. 成功率。
3. 用户满意度。
4. 延迟。
5. 成本。
6. 幻觉率。
7. 投诉和人工接管。
8. 安全事件。
9. 反馈样本。

没有反馈闭环，产品无法持续变好。真实产品通常通过日志、用户反馈、人工标注、失败案例分析和 A/B 测试持续迭代。这里要区分使用量与有效使用量：一次请求被发出，不代表用户采纳了答案；一次点击“满意”，也不代表任务已经正确完成。反馈样本需要带任务类型、版本、权限、是否经过人工修改和最终结果，才能用于定位退化。

## 1.13 从技术指标到产品指标

技术指标和产品指标要连接起来。

例如 RAG：

```text
召回率 -> 答案正确率 -> 用户自助解决率 -> 客服成本下降
```

例如 Code Agent：

```text
测试通过率 -> 修复成功率 -> 开发节省时间 -> 交付效率提升
```

例如客服机器人：

```text
意图识别准确率 -> 首次解决率 -> 转人工率下降 -> 用户满意度提升
```

只讲技术指标，会显得项目没有业务闭环；只讲业务指标，不讲技术支撑，也会显得不专业。中间至少需要一个可追溯的任务层：定义任务成功、失败、人工接管和未知结果，再把技术变化与任务变化、用户行为和业务结果连接起来。否则“召回率提升导致成本下降”只是相关性叙述，不能说明因果。

## 1.14 常见产品化失败模式

1. 为了用大模型而用大模型。
2. 只做 demo，不做真实用户验证。
3. 没有定义成功指标。
4. 忽略成本，越用越亏。
5. 忽略长尾输入和失败恢复。
6. 没有权限和合规设计。
7. 用户工作流接入差。
8. 上线后没有监控和反馈。
9. 模型升级没有回归测试。
10. 把产品问题误认为纯模型问题。

产品化失败往往不是因为模型完全不行，而是因为场景、体验、成本和运营没有设计好。

## 1.15 最小可运行产品化审计 demo

下面这个 demo 不调用外部模型，而是构造 4 个候选大模型产品场景，估算任务成功率提升、月度收益、月度成本、ROI、收益成本比，并检查痛点、工作流、评估、反馈、安全、隐私、延迟和单位经济账。它采用“合格任务数 × 采用率”的口径；任务成功率、采用率和所有成本字段都必须是有限的非负数，成功率和采用率还必须不超过 1。

它演示的问题是：产品化不能只看“能不能做”，还要看“值不值得做、能不能稳定做、风险是否可控、上线后能不能迭代”。

```python
import math
from dataclasses import dataclass
from typing import Optional


def require_text(value, field_name):
    if not isinstance(value, str) or not value.strip():
        raise ValueError(f"{field_name} must be non-empty text")


def require_rate(value, field_name, allow_unknown=False):
    if value is None and allow_unknown:
        return
    if not isinstance(value, (int, float)) or isinstance(value, bool):
        raise TypeError(f"{field_name} must be a finite number")
    if not math.isfinite(value) or not 0 <= value <= 1:
        raise ValueError(f"{field_name} must be between 0 and 1")


def require_nonnegative(value, field_name):
    if not isinstance(value, (int, float)) or isinstance(value, bool):
        raise TypeError(f"{field_name} must be a finite number")
    if not math.isfinite(value) or value < 0:
        raise ValueError(f"{field_name} must be finite and non-negative")


def require_bool(value, field_name):
    if type(value) is not bool:
        raise TypeError(f"{field_name} must be bool")


@dataclass(frozen=True)
class ProductCase:
    case_id: str
    scenario: str
    user_pain: float
    monthly_tasks: int
    value_per_success: float
    baseline_success_rate: Optional[float]
    llm_success_rate: Optional[float]
    adoption_rate: float
    p95_latency_s: Optional[float]
    model_cost_per_task: float
    ops_cost_per_task: float
    risk_cost_per_task: float
    fixed_monthly_cost: float
    safety_ready: bool
    privacy_ready: bool
    workflow_fit: bool
    eval_ready: bool
    feedback_ready: bool

    def __post_init__(self):
        require_text(self.case_id, "case_id")
        require_text(self.scenario, "scenario")
        if type(self.monthly_tasks) is not int or self.monthly_tasks < 0:
            raise ValueError("monthly_tasks must be a non-negative integer")
        require_rate(self.user_pain, "user_pain")
        require_rate(self.baseline_success_rate, "baseline_success_rate", True)
        require_rate(self.llm_success_rate, "llm_success_rate", True)
        require_rate(self.adoption_rate, "adoption_rate")
        if self.p95_latency_s is not None:
            require_nonnegative(self.p95_latency_s, "p95_latency_s")
        for field_name in (
            "value_per_success",
            "model_cost_per_task",
            "ops_cost_per_task",
            "risk_cost_per_task",
            "fixed_monthly_cost",
        ):
            require_nonnegative(getattr(self, field_name), field_name)
        for field_name in (
            "safety_ready",
            "privacy_ready",
            "workflow_fit",
            "eval_ready",
            "feedback_ready",
        ):
            require_bool(getattr(self, field_name), field_name)

def round3(value):
    return round(value, 3)


def audit_case(case):
    if case.baseline_success_rate is None or case.llm_success_rate is None:
        success_uplift = None
        monthly_benefit = None
    else:
        success_uplift = case.llm_success_rate - case.baseline_success_rate
        monthly_benefit = (
            case.monthly_tasks
            * case.adoption_rate
            * success_uplift
            * case.value_per_success
        )
    variable_cost = case.monthly_tasks * case.adoption_rate * (
        case.model_cost_per_task + case.ops_cost_per_task + case.risk_cost_per_task
    )
    monthly_cost = variable_cost + case.fixed_monthly_cost
    net_benefit = None if monthly_benefit is None else monthly_benefit - monthly_cost
    benefit_cost_ratio = (
        None
        if monthly_benefit is None or monthly_cost <= 0
        else monthly_benefit / monthly_cost
    )
    roi = None if net_benefit is None or monthly_cost <= 0 else net_benefit / monthly_cost
    monthly_margin_before_fixed = (
        None if monthly_benefit is None else monthly_benefit - variable_cost
    )
    payback_months = (
        round3(case.fixed_monthly_cost / monthly_margin_before_fixed)
        if monthly_margin_before_fixed is not None and monthly_margin_before_fixed > 0
        else None
    )

    gates = {
        "pain": case.user_pain >= 0.60,
        "quality_uplift": (
            "unknown" if success_uplift is None else success_uplift >= 0.10
        ),
        "unit_economics": (
            "unknown"
            if benefit_cost_ratio is None
            else benefit_cost_ratio >= 1.20
        ),
        "latency": (
            "unknown" if case.p95_latency_s is None else case.p95_latency_s <= 10.0
        ),
        "risk": case.safety_ready and case.privacy_ready,
        "workflow": case.workflow_fit,
        "eval": case.eval_ready,
        "feedback": case.feedback_ready,
    }
    score = None
    if (
        success_uplift is not None
        and benefit_cost_ratio is not None
        and case.p95_latency_s is not None
    ):
        score = (
            0.18 * case.user_pain
            + 0.20 * min(max(success_uplift, 0.0) / 0.30, 1.0)
            + 0.20 * min(max(benefit_cost_ratio, 0.0) / 2.0, 1.0)
            + 0.12 * case.adoption_rate
            + 0.10 * (1.0 if gates["latency"] else 0.0)
            + 0.10 * (1.0 if gates["risk"] else 0.0)
            + 0.05 * (1.0 if case.workflow_fit else 0.0)
            + 0.05 * (1.0 if case.eval_ready and case.feedback_ready else 0.0)
        )
    status = (
        "failed"
        if any(value is False for value in gates.values())
        else "passed"
        if all(value is True for value in gates.values())
        else "unknown"
    )
    return {
        "case_id": case.case_id,
        "success_uplift": None if success_uplift is None else round3(success_uplift),
        "monthly_benefit": None if monthly_benefit is None else round(monthly_benefit, 2),
        "monthly_cost": round(monthly_cost, 2),
        "net_benefit": None if net_benefit is None else round(net_benefit, 2),
        "benefit_cost_ratio": (
            None if benefit_cost_ratio is None else round3(benefit_cost_ratio)
        ),
        "roi": None if roi is None else round3(roi),
        "payback_months": payback_months,
        "gates": gates,
        "status": status,
        "ship_gate": status == "passed",
        "score": None if score is None else round3(score),
    }


audits = [audit_case(case) for case in cases]
ranked = sorted(
    ((item["case_id"], item["score"], item["status"]) for item in audits),
    key=lambda item: (item[1] is None, -(item[1] or 0), item[0]),
)
rejected = {
    item["case_id"]: [name for name, state in item["gates"].items() if state is not True]
    for item in audits
    if not item["ship_gate"]
}
ship_candidates = [item["case_id"] for item in audits if item["ship_gate"]]

print(f"ranked={ranked}")
print(f"ship_candidates={ship_candidates}")
print(f"rejected={rejected}")
for item in audits:
    print(

            "success_uplift": item["success_uplift"],
            "monthly_benefit": item["monthly_benefit"],
            "monthly_cost": item["monthly_cost"],

            "benefit_cost_ratio": item["benefit_cost_ratio"],
            "roi": item["roi"],

        },
    )
```

## 1.16 用产品语言复盘一个技术项目

把一个项目讲清楚，不能从“我们用了某个模型”开始，而要从任务契约开始。一个完整复盘至少说明五件事：目标用户是谁，用户在什么任务中遇到什么瓶颈，系统改变了哪一个可观察的任务结果，代价和风险如何测量，下一阶段准备扩大、限制还是停止。

例如，一个客服知识库助手可以这样组织证据链：先定义“用户在一次会话中得到有依据的答案且不需要重复转人工”为任务成功；再分别记录检索命中、答案正确、引用有效、用户采纳和最终转人工；最后把这些结果与人工处理时间、单位成本和投诉率关联。这样，模型升级导致的召回率变化，才有机会与真实业务结果建立可检验的联系。

复盘还必须说明反例。若离线准确率提升但线上采纳率下降，可能是答案更长、响应更慢、引用位置不清或接入流程变复杂，而不一定是模型本身退化。若单位成本下降但人工接管率上升，节省的 API 费用可能只是把成本转移给了运营团队。把失败切片，通常比只报一个平均分更能指导下一步工作。

## 1.17 从候选场景到受控试点

产品化不是在“开发”和“全量上线”之间做二选一，而是逐步减少未知。一个稳妥的试点可以按以下顺序推进：

1. 固定任务定义、基线、用户群和成功判据。
2. 用历史样本和人工标注建立离线回归集，标出安全和高风险样本。
3. 在隔离环境验证权限、引用、降级、人工接管和日志字段。
4. 以小规模真实流量观察任务成功、采纳、延迟、成本和异常。
5. 按用户类型、任务类型、模型版本和失败原因切片比较。
6. 只有在证据充分时扩大流量；出现安全或严重质量退化时，回退版本并保留事件。

这里的“通过”只是允许进入下一阶段，不是对未来收益的保证。一个候选场景可以同时满足技术质量和单位经济，却因权限审计未完成而停留在离线阶段；也可以在短期 ROI 不明显时继续小规模试点，因为它正在验证高价值但低频的任务。关键是把每一次投入对应到一个明确的未知问题。

## 1.18 资料入口与证据边界

- [OpenAI Evals 指南](https://developers.openai.com/api/docs/guides/evals)：官方评估文档，可支持任务、数据集、指标和持续评估的接口与流程讨论；它不提供任何具体业务的收益保证。
- [OpenAI 延迟优化指南](https://developers.openai.com/api/docs/guides/latency-optimization)：官方工程文档，可支持 token、模型调用、并行和响应延迟之间的优化讨论；具体 P95 仍需在目标流量下实测。
- [Google SRE Monitoring](https://sre.google/sre-book/monitoring/)：SRE 经典教材中的监控章节，可支持指标、目标和告警的可靠性讨论；它不替代大模型任务正确性和安全评估。
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：官方风险管理框架入口，可支持风险识别、测量、管理和治理的讨论；它不自动完成某个产品的合规判断。

本章的收益、成本和试点 demo 是教学构造，不是财务预测；官方文档、可靠性教材和风险框架属于不同证据层级。实际项目还要记录样本量、基线窗口、采用率定义、人工成本、失败重试、风险事件、版本和分群结果。

## 1.19 本章小结

大模型产品化的核心，是把模型能力转化为真实用户价值。Demo 证明“能做”，产品要求“稳定、可控、可持续地创造价值”。算法工程师要能把模型指标和业务指标连接起来，理解成本、体验、安全、合规、运营和反馈闭环。

下一章会进入用户需求与场景选择，进一步讨论如何从真实业务问题中筛选适合大模型落地的场景，避免为了技术而技术。
