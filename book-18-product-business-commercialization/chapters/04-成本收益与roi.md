# 第四章：成本收益与 ROI

[第二章《用户需求与场景选择》](02-用户需求与场景选择.md)的试点判断了一个任务是否值得尝试，[第三章《模型能力到产品体验》](03-模型能力到产品体验.md)把任务写成了体验和质量要求。接下来还要回答：当真实用户开始使用时，每个完成的任务要花多少，能带来哪些可归因的价值，规模扩大后账会怎样变化？我们还会把内部单位经济连接到价格、包装和真实付费行为，形成投资回报率（Return on Investment, ROI）判断。所有数字最终都要回到可检验的用户任务和业务条件，而不是人工智能（artificial intelligence, AI）能力本身。

一笔可用的产品账，不能只把模型调用价格除以请求数。用户可能没有采用回答，失败请求仍消耗了模型和人工时间；相反，节省的分钟数也不一定会变成现金。我们需要先选对核算单位，再把完整成本、可验证收益、质量与风险条件放在同一任务和时间范围内。

本章沿用客服政策查询作为例子，展示怎样从一次 AI 尝试一路核算到月度单位经济、回本时间和价格假设。示例中的金额与任务量都是教学假设，不是市场报价或前几章小样本试点的外推。

## 4.1 先决定“每一单”指什么

核算前先说清单位。客服系统里，“一次请求”“一次模型回答”“一个被客服采用的草稿”和“一个正确解决的问题”不是同一件事。如果分子记了所有花费，分母却只记成功请求，或者把没有采用的回答也算成解决任务，结果就会失真。

可以同时跟踪几个单位：

| 单位 | 计算口径 | 它回答什么问题 |
| --- | --- | --- |
| 每次 AI 尝试成本 | AI 相关变动支出 ÷ 所有进入 AI 流程的任务 | 每次调用平均消耗多少资源 |
| 每个采用结果成本 | 所有相关支出 ÷ 用户或业务流程实际采用的结果数 | 为一个被使用的结果付出多少 |
| 每个合格完成任务成本 | 所有相关支出 ÷ 达到任务验收标准的完成数 | 为真正完成目标的任务付出多少 |
| 每位活跃用户或客户成本 | 一段时间内相关支出 ÷ 同期活跃用户或客户 | 这种单位是否适合该产品的价值与收费方式 |

通常应至少报告每次尝试成本和每个合格完成任务成本。前者暴露无效调用、重试和未采用结果的浪费；后者更接近业务结果。若系统只在特定任务上调用模型，还应同时报告符合条件的任务数、路由比例、采用率、验收通过率和人工接管率，避免一个单位成本把流程中断点藏起来。

云财务运营（FinOps）Foundation 的单位经济框架也强调先让技术开支与组织目标、业务单位和成本分摊规则相连，并区分每个请求、客户、案例或词元（token）等不同口径。资源效率指标可以帮助工程师优化，但每 token 成本下降不自动意味着每个有效任务更便宜。[FinOps Framework 的 Unit Economics 指南](https://www.finops.org/framework/capabilities/unit-economics/)提供了单位经济与完整成本的框架；它不规定本章的收益公式或任何项目的通过门槛。

## 4.2 把成本按驱动因素分开

成本分类的关键不是给费用贴上“模型”或“工程”的标签，而是找到它随什么变化、在什么时候发生。可以先分为三类：

1. **按任务变化的成本：** 每次调用的模型费用、查询时的检索和工具费用、按量计费的人工审核、重试以及可合理估算的失败处置成本。
2. **按周期发生的成本：** 服务容量、监控告警、固定许可证、数据维护、值班、合规复核和持续工程维护。任务量暂时下降时，这些支出未必同步下降。
3. **一次性投入：** 原型和系统集成、数据清理、评估集建设、迁移、培训等。它们进入项目总投资和回本核算；若为单位成本展示而摊销，必须说明摊销期和预计使用量，并确保没有再把同一笔钱计入一次性投入。

同一项资源可能有不同驱动方式。例如，按调用收费的人工复核接近变动成本；固定班次的质检团队可能是周期成本；新建知识库的整理成本则是一次性投入。分类应看实际合同和资源安排，不能仅凭名称决定。

在同一比较中，应用程序编程接口（API）、自部署、检索增强生成（RAG）和智能体（Agent）方案必须用相同任务定义、质量门槛、时间范围与成本边界。共同基础设施、团队工作和管理成本可以按清楚的规则分摊；分摊规则本身是管理约定，不是精确的因果测量。FinOps 框架建议记录指标假设、成本纳入范围和分摊规则，并把直接技术成本逐步扩展为适用的完整成本。

对立项决策而言，还要区分现金支出和资源机会成本。现有员工做了系统开发，未必当月增加工资支出；但这段时间也不能同时投入别的项目。财务报表和“这项工作是否值得占用团队能力”是两个不同问题，必要时分别列出，不要把工资和机会成本重复相加。

## 4.3 API 和 token 账要从实际用量开始

模型费用通常随输入、输出、调用次数及其他计费单位变化。文本经分词器切分后的基本计费单位常称为词元（token）。一次客服任务可能包含固定指令、用户问题、历史对话、检索片段、工具结果和最终回答；多轮规划或重试会重复处理其中一部分。只记录“平均一次请求多少钱”，很难找出长上下文、异常任务和重复调用造成的成本。

对线性按量计费的项目，可以用下式估算一个 AI 尝试的模型费用：

```math
C_{\mathrm{model}}=\sum_{j=1}^{J} n_j r_j
```

这里 $j$ 表示一种计费项目，$J$ 是账本中不同计费项目的数量；$n_j$ 是该次任务在这一项目下的计费数量，$r_j$ 是同一计费单位的价格。项目可以是输入 token、输出 token、缓存命中 token、工具调用或其他明确收费单位。若计价有阶梯、最低消费、批量折扣、预留容量或套餐额度，应按合同和账单规则计算，不能硬套线性式。

例如，假设一次客服尝试需要一个模型调用，平均输入 2,000 个 token、输出 500 个 token；教学用单位价分别设为每 1,000 个输入 token ¥0.02、每 1,000 个输出 token ¥0.04，则模型费用为 $2\times ¥0.02+0.5\times ¥0.04=¥0.06$。这组费率纯为教学设定，不能当作任何供应商报价；它与 §4.9 成本表中的模型费用假设相同。

实际账单和请求用量字段（usage）是比静态 token 估算更好的校准入口。比较时应记录模型和版本、计费项目、调用次数、输入输出分布及失败/重试情况；平均数之外还要看 p50（第 50 百分位）和 p95（第 95 百分位）等分位数，因为少量长对话或重试链可能拖高每个有效任务的成本。

应用程序编程接口（API）供应商的计费项目与价格会变化。以 2026-11-16 查阅的 OpenAI 公开文档为例，价目表分别列出模型、输入/输出、缓存输入、批处理和工具等计费项目；这说明预算要按实际端点与 usage 字段逐项对齐，而不是只保存一个“每 token 价格”。[OpenAI API Pricing](https://developers.openai.com/api/docs/pricing)是供应商当前价目入口，不是长期价格承诺，也不能替代组织自己的账单和合同。

## 4.4 自部署图形处理器（GPU）的成本来自容量安排

自部署时，图形处理器（GPU）账单也不是“GPU 小时数 ÷ 请求数”这么简单。需要把为服务保留的容量、实际有效负载、峰值冗余、故障切换和空闲时段放在一起看，还要计入机器或云实例、网络、电力、存储、推理平台、值班和版本维护。

预填充与逐 token 解码的资源形态不同；显存、上下文长度和并发也会限制同一组卡能承载的任务数。因此，裸 token 吞吐或 GPU 利用率都不等于业务产出。更有用的指标是目标服务等级下每个**合格完成任务**的完整推理成本，并同时报告高峰延迟和失败率。

API 与自部署要使用相同的请求分布、模型质量门槛、峰值负载、服务时间和故障备用条件来比较。自部署方案可能把按调用成本改成固定容量成本，也可能因低利用率、冗余和维护团队而变贵；应以实际负载和财务口径测量，不把某种架构预先当作更便宜。

## 4.5 RAG 和 Agent 会把一次任务拆成一条成本链

检索增强生成（Retrieval-Augmented Generation, RAG）的成本分布在离线和在线两侧。文档解析、分块、嵌入（embedding）、索引更新和权限整理可能是周期成本；在线查询还会使用过滤、向量检索、重排（reranking）、上下文拼接、引用校验和模型调用。文档更新频率、权限粒度与版本管理会改变这笔账。

减少检索片段或缩短上下文确实可能降低模型费用，但如果关键证据因此漏掉，人工复核、返工和错误损失就会上升。RAG 优化应一起看召回覆盖、引用支持、任务验收、延迟、人工接管和权限错误，而不是只看 token 数。

智能体（Agent）则把一个请求变成带状态的多步执行：规划和结果整合可能多次调用模型，过程中会有搜索、检索、代码或浏览器工具、权限检查、执行轨迹（trace）存储、人类确认以及失败后的重试。某一步失败有时会使后续步骤全部作废，因此平均单步价格不能代替每个完整任务的成本。

估算 Agent 成本时，记录每个任务的模型调用数、工具调用数、运行时长、重试原因、成功/部分成功/失败状态以及人工接管。工具预算和最大运行时间既是成本上限，也是产品体验与安全边界；不能为了省钱而取消必要的权限或验证步骤。

## 4.6 人审、数据和持续运营也要入账

人工审核的成本不仅是审核分钟数，还包括人员培训、抽检、争议样本复核、投诉处理、反馈标注和错误后返工。若一部分 AI 尝试需要人审，可以用“需要审核的比例 × 平均审核时间 × 单位时间成本”估算平均每次尝试的审核费用，再用账单或工时记录校准。

还要为数据收集、授权、清洗、脱敏、更新与质量检查留出成本。企业产品可能需要固定的身份权限、审计、监控、安全审查、故障处理与供应商管理支出。系统模型、提示、索引和工具接口会变化，评估集维护、回归、灰度发布与回滚也需要持续投入。

没有必要把每个成本拆到小数点后很多位。先建立完整但可复核的边界，标出估算项和未知项；样本与账单成熟后再细化。对尚无证据的失败损失、运维工时或共享成本，应标记待估，并开展敏感性分析，而不能当作零。

## 4.7 收益必须有基线和归因链

没有系统时，同类用户任务会花多少时间、达到什么质量、失败或返工多少？这是比较收益的起点。上线后同时发生的季节变化、人员经验、流程重组、价格调整或营销活动都可能影响结果。若没有对照组、分阶段上线或其他可解释的比较设计，不能把同期改善全部算在 AI 头上。

尽量把数据沿一条链记录下来：

> 符合条件的任务 → 路由到 AI 的任务 → 已生成结果 → 实际采用结果 → 达到验收条件的完成任务 → 业务后果

每一步都要保留分母。模型生成率高不代表用户采用率高；采用率高也不代表任务按要求完成。将任务定义、基线、采用率、成功标准和质量保护指标与[第三章的体验合同](03-模型能力到产品体验.md)一致，避免财务账用“已生成”，质量评估却用“成功完成”。

人工省下的时间首先是**释放的产能**。只有当组织能减少按小时或按件支付的工作、避免已计划的招聘，或用释放出的时间完成更多有价值任务时，才可以按相应方式记作经济收益。若固定工资不变，不能把释放的 200 小时直接叫作节省了 200 小时工资；可以记录产能、交付时间或服务覆盖变化，但那不是同一类现金收益。

质量变化、用户满意度、风险与收入也需要各自的证据路径。若质量改进价值难以货币化，就先作为体验或保护指标报告；若收入提升可能来自多个同时发生的变化，就只纳入可归因的增量贡献利润。收益项目应逐项写清测量基线、样本、归因设计和适用范围。

## 4.8 不同收益不能重复计价

收益可以分成几种，但不一定都适合换算成货币：

- **可兑现的人工或处理成本减少：** 以减少的实际支出或释放产能的后续用途为证据。
- **效率和交付改善：** 观察合格任务吞吐、周期时间、等待时间和返工；若没有转成支出减少或新增产出，先作为运营结果。
- **用户体验、知识复用与服务覆盖：** 可以观察用户是否更快完成任务、是否减少重复咨询、组织知识是否被稳定复用，以及是否能服务更多用户或时段。这些结果可能对产品有长期价值，但指标改善本身不等于已经实现现金收益，应说明对象、基线和归因，并避免与时间或收入收益重复计算。
- **质量变化：** 可以观察错误、返工、投诉和验收率。若基线成功率为 $p_0$，上线后为 $p_1$，每多完成一个合格任务的增量价值为 $V$，且没有在其他收益项重复计算，则质量收益可估为 $(p_1-p_0)V$。例如成功率从 90% 到 92%，每个额外合格任务的教学估值为 ¥50，则每个可比任务的期望质量收益为 $(0.92-0.90)\times ¥50=¥1$。这里的成功率和价值只是算例；若 $V$ 未经业务数据估计，就保留质量指标，不要硬换成钱。
- **收入变化：** 估算可归因的增量贡献利润，而非直接把新增流水当成利润。贡献利润是新增收入减去随该收入发生的直接履约、渠道和退款等成本后留下的金额。例如，100 个可归因的新订单每单收入 ¥120、每单直接履约成本 ¥40，则这批订单带来 ¥8,000 贡献利润，而不是把 ¥12,000 收入全额当成利润。
- **风险变化：** 美国国家标准与技术研究院（NIST）的生成式 AI 风险画像将风险放在具体情境中，考虑事件可能性与后果；它不提供本企业的概率或金额。[NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/AI/NIST.AI.600-1.pdf) 对单一、可描述的损失事件，可把下面的乘法作为一个明确的估算假设，而不是通用风险量表：

```math
E_{\mathrm{loss}}=p_{\mathrm{event}}L_{\mathrm{event}}, \qquad
B_{\mathrm{risk}}=E_{\mathrm{loss,base}}-E_{\mathrm{loss,AI}}
```

这里 $p_{\mathrm{event}}$ 是一个可比案例在规定观察期内发生该事件的概率，$L_{\mathrm{event}}$ 是事件每次发生的货币损失，二者相乘得到每个案例的预期损失。$E_{\mathrm{loss,base}}$ 与 $E_{\mathrm{loss,AI}}$ 分别表示同一事件、观察期和分母下的基线流程与 AI 流程预期损失。若一项审核遗漏事件的发生概率从 2% 降到 1%，每次损失假设为 ¥10,000，则每个同类案例的预期损失差为 $(0.02-0.01)\times ¥10{,}000=¥100$。这是教学算术，不是行业事故率或真实损失估值；若概率、严重度、系统对暴露的影响缺少证据，收益应记为未知。风险损失如果已放在变动成本或质量损失里，也不能再次加成收益。

一笔收益只能记一次。例如，同一批节省的客服工时不能同时算作“工资削减”“新增处理能力”和“服务速度提升”的现金收益；若质量改善已包含在增量利润中，不要再加一遍质量收益。潜在的严重安全或法律风险还需要作为独立的发布约束处理，不能因为预期 ROI 很高就抵消硬性门槛。

## 4.9 一张月度账本怎样从任务推到收益

现在用客服政策查询走一遍。假设一月有 10,000 个符合条件的任务，其中 40% 由系统路由到 AI，AI 采用率为 75%，所以有 4,000 次 AI 尝试和 3,000 个实际采用的结果。

以下数字全是假设。第三章客服例子中，基线组和 AI 组各有 12 项观察，且 AI 结果经人工复核；这样的样本不能推出月度效果。为演示账本，另作一组独立的教学假设：企业采用按小时可调节的外包客服，每个采用结果平均**净减少** 4 分钟人工处理时间。若减少的时间不能改变实际外包工时或业务产出，这笔钱就不能作为已实现现金节省。

| 每次 AI 尝试的平均成本 | 教学假设 |
| --- | ---: |
| 模型调用 | ¥0.06 |
| 检索 | ¥0.04 |
| 工具 | ¥0.02 |
| 人工审核 | ¥0.08 |
| 重试与返工 | ¥0.05 |
| **合计变动成本** | **¥0.25** |

在这个简化账本里，$3{,}000$ 个采用结果各净省 4 分钟，合计 $12{,}000$ 分钟，也就是 200 小时。若可变外包工时每小时值 ¥60，时间收益就是 $200\times ¥60=¥12{,}000$，等价于每个采用结果 $4/60\times ¥60=¥4$。这里按小时值只用于那些确实转成可减少支出的工时。

变动成本按所有 AI 尝试计算，包括未被采用的 1,000 次：$4{,}000\times ¥0.25=¥1{,}000$。再假设月固定运行成本为 ¥2,000，一次性接入与数据治理投入为 ¥6,000。未计一次性投入前，月持续成本为 ¥3,000，月运营净收益为 ¥9,000。若把一次性投入也放入首月，首月总成本为 ¥9,000，首月净收益为 ¥3,000。

这个结果有明确条件：任务质量与安全要求必须先通过试点验收；四分钟是扣除返工后的平均净节省；按小时外包工时确实随任务减少；所有成本单位一致。如果这 200 小时只变成闲置时间，现金收益应改为未知或零，而不能因为表格算出了 ¥12,000 就宣称项目省了这么多钱。

## 4.10 从月度账本定义 ROI

为了避免项目间口径不同，本章把**评价期 ROI**定义为评价期内净收益除以同一评价期全部成本。设评价期有 $H$ 个月；第 $t$ 月符合条件的任务数为 $N_t$，AI 路由比例为 $A_t$，采用率 $U_t$ 是已采用结果数占 AI 尝试数的比例，每次尝试平均变动成本为 $C_{\mathrm{var},t}$，周期固定成本为 $F_t$，每个采用结果的平均可归因收益为 $B_t$；$I$ 是一次性投入。$B_t$ 应是所有采用结果的平均净货币收益，返工或失败造成的损失会降低这个平均值；若某项价值只属于通过验收的任务，就应使用相应合格任务数，不要把它套到所有采用结果上。假设这些项目没有重叠计价，且每一项金额都使用同一货币和一致的会计边界：

```math
B_H=\sum_{t=1}^{H}N_t A_t U_t B_t
```

```math
C_H=I+\sum_{t=1}^{H}\left(N_t A_t C_{\mathrm{var},t}+F_t\right)
```

```math
\mathrm{ROI}_H=\frac{B_H-C_H}{C_H}, \qquad
\mathrm{BCR}_H=\frac{B_H}{C_H}, \quad C_H>0
```

$B_H$ 是评价期可归因收益，$C_H$ 是一次性投入、所有 AI 尝试的变动成本和周期固定成本之和。收益成本比（BCR）说明每投入一元对应多少收益；ROI 则说明扣除这些成本后的净额占成本的比例。按这个定义，ROI 为 $0$ 表示评价期内刚好收支平衡；BCR 为 $1$ 也对应收支平衡。企业若采用其他 ROI 口径，应在报告中明确分子、分母、时间范围和是否计入一次性投入，不能只写一个百分数。

使用上一节的假设，首月 $B_1=¥12{,}000$，$C_1=¥6{,}000+¥1{,}000+¥2{,}000=¥9{,}000$。因此首月 $\mathrm{ROI}_1=(¥12{,}000-¥9{,}000)/¥9{,}000=33.3\%$，$\mathrm{BCR}_1=1.33$。这不是“项目的永久 ROI”，只是这些教学假设下第一个月、计入初始投入的结果。

本章公式假设评价期内金额可以直接相加。若项目跨多年、成本收益发生时间不同、需求爬坡或资金占用明显，就需要财务团队指定现金流时间表与折现口径，不能把一个稳定月份简单复制成全生命周期收益。

## 4.11 单位贡献、盈亏平衡和回本时间

月总账回答是否有总体收益，单位贡献则帮助判断规模扩大是否会改善结果。设每个采用结果平均带来 $B$ 元可归因收益，每次 AI 尝试成本为 $C_{\mathrm{var}}$ 元，采用率为 $U$，则每次 AI 尝试的预期贡献为：

```math
m=UB-C_{\mathrm{var}}
```

在客服示例里，$m=0.75\times ¥4-¥0.25=¥2.75$。即每路由一个任务平均产生 ¥2.75 的贡献，还没扣月固定成本。每个符合条件任务按 40% 路由，则预期贡献为 $0.4\times ¥2.75=¥1.10$。

设月固定成本 $F=¥2{,}000$。在路由率、采用率和单位价值保持稳定、$m>0$ 的条件下，运营盈亏平衡任务量为：

```math
N_{\mathrm{BE}}=\frac{F}{A(UB-C_{\mathrm{var}})}
```

代入示例可得 $N_{\mathrm{BE}}=¥2{,}000/¥1.10\approx1{,}819$ 个符合条件任务/月。任务量高于此数时，才开始覆盖月固定运行成本。若要在首月就连 ¥6,000 一次性投入也收回，首月需约 $(¥2{,}000+¥6{,}000)/¥1.10\approx7{,}273$ 个任务。两个数字回答不同问题，不能混称一个“盈亏平衡点”。

若 $A=0$ 或 $m\le 0$，增加任务量不能覆盖固定成本；如果 $m>0$ 但预计需求不足，项目可能在单位上有贡献、在规模上仍不可行。盈亏平衡也不代表质量、安全或用户体验合格。

当月持续净收益稳定为 $P_{\mathrm{op}}>0$、没有启动爬坡且不折现时，简单回本月数可以估作 $I/P_{\mathrm{op}}$。示例为 $¥6{,}000/¥9{,}000\approx0.67$ 月。现实里任务量、价格、采用率和成本会波动，应按每月实际现金流累计，找累计净现金流首次抵消初始投入的时点。若持续净收益不为正，则当前假设下没有有限回本时间；若关键数据缺失，则写“未知”，不要以极小分母制造一个巨大但看似精确的期限。

## 4.12 哪些假设最容易改变结论

单点预测会给人一种不恰当的确定感。先选出最影响结论的变量，例如采用率、路由比例、可兑现时间、每次尝试成本、任务量和固定成本，再一次只改变其中一个变量，观察结果对它是否敏感。单变量敏感性有助于找脆弱假设；保守、基准和乐观情景则可展示多个假设一起变化时的范围。

| 情景（其余数值不变） | 采用率 | 每次尝试成本 | 月可归因收益 | 月持续成本 | 月持续净收益 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基准教学假设 | 75% | ¥0.25 | ¥12,000 | ¥3,000 | ¥9,000 |
| 采用率偏低 | 50% | ¥0.25 | ¥8,000 | ¥3,000 | ¥5,000 |
| 单次成本偏高 | 75% | ¥0.45 | ¥12,000 | ¥3,800 | ¥8,200 |
| 时间只释放、未兑现 | 75% | ¥0.25 | ¥0 现金收益 | ¥3,000 | −¥3,000 |

前三行沿用 10,000 个符合条件任务、40% 路由和每个采用结果 ¥4 的现金收益。最后一行强调：若释放的时间没有减少支出或转成可归因产出，现金 ROI 不能记入这项收益；可以另行报告释放产能等非现金结果。这里的变化是教学敏感性，不是概率预测。

敏感性结果为负不应被“平均”掉；结果可能说明需要先提高采用率、改进任务路由、降低成本或换一个场景。若风险损失、价格接受或增量利润数据薄弱，应把该变量保留为范围或未知，而不是填入单个乐观数字。

## 4.13 用质量和安全约束成本优化

成本优化的目标是减少每个合格完成任务的总成本，并维持本章任务所需的质量、延迟、可靠性和安全条件。更便宜但导致用户不采用、人工返工或风险增加的方案，不是有效优化。

可以按成本来源选择改动：减少不必要调用；让简单任务使用足够好的较小模型；移除重复上下文；修复造成重试的工具错误；调整 Agent 步数预算；按真实负载改进容量安排；或让稳定格式减少人工整理。每次变化都应和[第三章的任务验收、采用率、人工接管、错误与延迟保护指标](03-模型能力到产品体验.md)一起比较。

缓存和异步批处理有适用条件。缓存只有在请求满足供应商缓存规则并实际命中时才可能减少计算或费用；不同模型的读写计费可能不同，不能只按理论命中率估算。[OpenAI Prompt Caching 文档](https://developers.openai.com/api/docs/guides/prompt-caching)说明前缀复用与模型相关的命中和计费条件。允许延迟返回的离线任务可评估批处理；同步交互、严格时限或任务失败后无法恢复的流程未必适合。[OpenAI Batch API 文档](https://developers.openai.com/api/docs/guides/batch)展示了该供应商当前的异步接口、适用端点和完成窗口，具体计费与时限应在项目决策时重新核对。

一次优化至少要记录变更假设、试点任务、前后成本口径、用户结果、失败与接管、延迟分布、安全事件、回滚条件和后续监控。不要把每请求平均 token 降低、GPU 利用率提高或账单下降单独当成成功；应观察每个合格任务的总成本是否下降且保护条件仍满足。

## 4.14 单位经济如何帮助定价和包装

单位经济帮助产品团队判断服务一位客户或完成一个任务要付出什么；它不会自动决定客户愿意付多少。若本书谈商业化，就要把内部成本账连接到客户获得的结果、付费对象和收费单位，但不用扩展成销售或合同谈判教材。

先区分三个问题：

1. **服务成本：** 一个客户、任务、座席或使用量实际给产品带来多少变动与固定成本？
2. **客户价值：** 客户完成任务后节省的支出、增加的贡献利润或改善的业务结果是什么？证据来自哪里？
3. **付费行为：** 哪一类买方会以什么价格购买、使用、续约或扩容？目前有真实行为证据还是只有口头表态？

收费单位可以按座席、完成任务、用量或可验证结果设计。每种方式都影响客户如何预测预算、产品如何承担用量波动，以及收费量是否能被双方审计。比如，按 token 收费和供应商成本接近，但未必对应客户感知价值；按任务收费更容易对照工作量，但需定义什么算“完成”；按结果收费看似与客户价值一致，却需要可靠归因并明确无效结果如何处理。不存在脱离产品、买方和交付成本的万能计费单位。

设每个付费单位实际收入为 $P$，单位变动服务成本为 $C_{\mathrm{serve}}$，则单位贡献利润是 $P-C_{\mathrm{serve}}$；如果有固定成本，还需要足够的付费单位来覆盖它。这个简单关系只是成本可持续性的检查，不是最佳定价算法。客户价值可以高于成本，却不等于客户会付出相同金额；价值估计还须区分买方、使用者、预算持有人以及替代方案。

支付意愿（willingness to pay, WTP）不能只靠“你会付多少钱”一个问题来确定。Wertenbroch 与 Skiera 在 2002 年的三项研究比较了不同测量方式，发现研究方法和购买情境会影响 WTP 估计；其研究对象是低价消费品，不能直接外推到企业 AI 采购。[论文作者稿](https://faculty.wharton.upenn.edu/wp-content/uploads/2012/05/Wertenbroch-and-Skiera-2002.pdf)支持的是“测量方法会影响答案”这一边界，而非某一种访谈或实验对所有产品都有效。产品团队可把陈述偏好当作探索线索，再逐步用有明确对象和条件的试用报价、实际购买/续约、使用量和服务成本校准；样本、折扣、渠道和同期产品变化都要记录。若只是免费试点或口头意向，不应记成已验证收入。

价格与包装决策还应检查成本暴露：高用量用户、长上下文、多轮 Agent、人工审核和数据存储是否会让某个套餐长期亏损；限额或分层是否会损害用户完成核心任务。将价格测试与[第二章的用户研究](02-用户需求与场景选择.md)相连，将采用、留存和任务结果与[第三章的体验指标](03-模型能力到产品体验.md)相连，再用本章的单位服务成本检查可持续性。具体费率、计费方式和合同仍需按产品所在地、供应商及实际合同核实。

## 4.15 复盘时避免的几种误读

- **只看 API 账单：** 它漏掉检索、工具、人审、数据、工程、运维和失败处置。
- **把释放时间当现金：** 只有兑现为支出减少或有证据的增量产出，才按相应货币收益计入。
- **把生成当成功或采用：** 记录尝试、采用、验收和任务完成的不同分母。
- **把流水当利润：** 收入增加要扣除对应的履约、渠道、退款和其他直接成本，尽量用增量贡献利润。
- **把未知填零或填乐观值：** 未知成本、价值、风险或归因应保留范围与待验证状态；它既不自动等于通过，也不自动等于失败。
- **重复计算同一收益：** 节省时间、减少人力支出、提升产能、质量价值和风险下降可能指向同一结果，必须检查重叠。
- **把 ROI 当唯一门槛：** ROI 不能补偿任务质量、安全、合法使用、用户体验或可靠性条件不达标。
- **只比较平均值：** 长尾请求、重试、采用差异和高峰容量可能改变单位经济。查看适合任务分布的分位数和失败样本。

一份可复核的 ROI 记录至少交代：任务与单位定义、基线、时间范围、尝试和采用样本、全成本边界、收益归因、质量/安全条件、主要假设、敏感性范围，以及结论的使用限制。应让财务、产品和工程读者看出每个数从哪里来，并知道哪些仍需试点核实。

## 4.16 本章小结

判断一个大模型产品是否能持续，不是比较供应商单价，而是把每次 AI 尝试的成本、每个采用结果的价值、固定投入、质量保护和真实现金收益放进同一条账本。合格完成任务的单位成本能显示服务效率；ROI、盈亏平衡和回本时间则说明不同时间范围内的投资结果。每项结论都要受数据边界、归因强度和业务条件约束。

成本账也会改变技术和产品选择：自部署、RAG、Agent、审核比例、缓存、批处理与价格包装都可能转移成本或风险。下一章进入[企业级 LLM 应用](05-企业级llm应用.md)，继续检查身份权限、系统集成、组织责任和上线条件怎样改变这笔账。
