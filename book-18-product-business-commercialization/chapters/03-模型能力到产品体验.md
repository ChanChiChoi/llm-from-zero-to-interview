# 第三章：模型能力到产品体验

## 0. 本讲范围与资料

本章重点讨论如何把模型能力转化为可观察、可验证的产品体验。联网资料主要核对四类口径：OpenAI evals / evaluation best practices 强调上线前要把任务、样本、指标和回归集定义清楚；OpenAI latency optimization 和 structured outputs 资料提示延迟、流式返回、缓存、结构化格式会直接影响体验；Google HEART 框架强调从用户目标拆出可观测 signals 和 metrics；Google SRE 的 SLI / SLO / error budget 口径提醒我们不能只看平均延迟，要看尾延迟和可接受失败率；NIST AI RMF / Generative AI Profile 提醒产品体验还要包含透明性、风险提示、人审和治理边界。

本章不展开具体 prompt 模板、RAG 检索算法、Agent 工具协议、前端设计系统或线上 A/B 实验平台。这里的核心问题是：如何把模型的理解、生成、检索、推理和工具能力，转成用户能感知的“快、准、稳、可控、可信、可恢复”的产品体验。

模型能力不等于产品体验。一个模型 benchmark 很高，但如果响应太慢、回答不稳定、无法引用来源、格式不可控、拒答策略混乱、用户不知道怎么追问，产品体验依然会很差。大模型产品化的关键，是把理解、生成、检索、推理和工具调用能力，转化为用户可感知、可信任、可持续使用的体验。

本章系统讲模型能力到产品体验的转化：延迟、准确性、可控性、解释性、拒答、风格、交互设计、引用、置信度、用户反馈、体验指标和常见失败模式。

## 3.1 为什么模型能力不等于体验

模型能力是技术侧概念，产品体验是用户侧感受。

例如模型有很强的总结能力，但用户体验可能受这些因素影响：

1. 等待时间太长。
2. 摘要太长或太短。
3. 重点不符合用户工作流。
4. 无法追溯原文。
5. 风格不符合业务场景。
6. 结果每次不一致。
7. 用户不知道如何修改输出。

因此，模型能力需要经过任务定义、交互设计和系统约束才能变成体验。用户感知到的不是 benchmark，而是任务是否更快完成、答案是否可信、交互是否顺畅、错误是否可恢复、成本是否合理。产品化时要把准确率、延迟、可控性、解释性、拒答和反馈机制一起设计，而不是只替换更强模型。

## 3.2 延迟体验

延迟是用户最直接感知的指标之一。

大模型产品的延迟来自：

1. 模型推理。
2. RAG 检索。
3. reranker。
4. 工具调用。
5. 多轮 Agent 循环。
6. 网络传输。
7. 排队和限流。

延迟不是越低越好，而是要和任务价值匹配。闲聊需要快；复杂报告可以慢一点；高价值分析可以等待，但要给用户进度反馈。

## 3.3 如何改善延迟感知

产品上可以降低用户对延迟的负面感受。

方法：

1. 流式输出。
2. 显示进度。
3. 先返回摘要，再补充细节。
4. 后台执行长任务。
5. 给用户可取消选项。
6. 缓存常见结果。
7. 对简单问题走快速路径。

例如 Agent 执行复杂任务时，可以展示“正在检索资料、正在生成草稿、正在检查引用”，而不是让用户空等。

## 3.4 准确性体验

用户感知的准确性不只是最终答案对不对。

还包括：

1. 是否理解了用户意图。
2. 是否覆盖关键约束。
3. 是否引用正确来源。
4. 是否承认不确定性。
5. 是否避免编造。
6. 是否能被用户验证。
7. 是否在追问中保持一致。

对于企业应用，准确性往往比“回答得流畅”更重要。流畅但错误的答案会损害信任。

## 3.5 可控性

可控性指用户能否影响输出结果。

常见控制维度：

1. 长度。
2. 风格。
3. 格式。
4. 语气。
5. 受众。
6. 数据范围。
7. 引用来源。
8. 是否保守或发散。

大模型默认输出可能不符合用户预期。产品可以提供模板、参数、选项、示例和编辑入口，让用户更容易控制结果。

## 3.6 结构化输出

结构化输出能显著提升体验和稳定性。

例如：

```text
结论：...
依据：...
风险：...
下一步建议：...
```

结构化输出适合：

1. 报告生成。
2. 工单总结。
3. 合同审查。
4. 客服回复。
5. 数据分析。
6. 面试反馈。

结构化输出的价值是降低用户理解成本，也便于后续系统处理。

## 3.7 解释性

用户需要知道答案为什么可信，但“可信”不等于让模型展示一段未经验证的内部推理。产品应优先提供能够被复查的证据和检查结果。

解释可以包括：

1. 依据来源。
2. 推理摘要。
3. 关键假设。
4. 不确定点。
5. 反例或限制。
6. 工具验证结果。

但解释不是越长越好。产品中更重要的是可验证解释，而不是完整内部推理。对于 RAG 产品，引用原文通常比长篇自我解释更有价值。

## 3.8 引用和来源

引用是建立信任的重要机制。

好的引用应该：

1. 指向具体文档或段落。
2. 支持对应结论。
3. 标明时间或版本。
4. 区分事实和推断。
5. 允许用户跳转查看原文。

坏引用包括：

1. 引用不相关文档。
2. 引用只支持部分结论。
3. 编造来源。
4. 用过期文档支持新结论。

引用准确率是很多企业 RAG 产品的重要指标。

## 3.9 拒答体验

拒答不是简单说“不行”。好的拒答应该说明原因，并给出可行替代方案。

例如：

```text
我不能直接给出医疗诊断，但可以帮你整理症状、列出需要咨询医生的问题，并提醒你尽快就医。
```

拒答体验要处理：

1. 安全限制。
2. 权限不足。
3. 信息不足。
4. 任务超出能力。
5. 数据不可访问。
6. 高风险建议。

拒答太少会有风险；拒答太多会降低可用性。产品需要平衡安全和帮助性。

## 3.10 风格一致性

风格是产品体验的一部分。

不同产品需要不同风格：

1. 客服：礼貌、简洁、可执行。
2. 法务：谨慎、严谨、保留条件。
3. 编程助手：直接、技术准确。
4. 教育产品：循序渐进、有引导。
5. 销售助手：有说服力但不能夸大。

风格一致性可以通过系统 prompt、模板、示例、后处理和评估来保证。

## 3.11 交互设计

大模型产品不一定只有聊天框。

常见交互形态：

1. 聊天式问答。
2. 文档侧边栏助手。
3. 表单自动填写。
4. 一键生成草稿。
5. 批量处理。
6. 工作流节点。
7. IDE 插件。
8. 浏览器插件。
9. 报告生成器。

聊天框灵活，但不一定最高效。很多企业场景更适合把模型嵌入现有流程，而不是让用户专门打开一个聊天页面。

## 3.12 用户引导

用户需要知道如何使用 AI 功能。

可以提供：

1. 示例问题。
2. 推荐任务。
3. Prompt 模板。
4. 输入字段。
5. 可选参数。
6. 结果编辑入口。
7. 反馈按钮。

不要假设用户会写好 prompt。好的产品应该把 prompt 工程隐藏在体验设计里。

## 3.13 错误恢复

模型错误不可避免，关键是能否恢复。

恢复方式：

1. 允许用户追问。
2. 提供重新生成。
3. 支持修改约束。
4. 显示引用让用户检查。
5. 给出“哪里不对”的反馈入口。
6. 对低置信答案提醒用户。
7. 高风险场景转人工。

产品体验中，错误恢复比假装永远正确更重要。

## 3.14 信任校准

信任校准是让用户既不过度信任，也不过度怀疑。

方法：

1. 标注不确定性。
2. 展示来源。
3. 区分事实和建议。
4. 对高风险内容提醒复核。
5. 不夸大能力。
6. 对无法完成的任务明确说明。

如果产品总是自信地给错答案，用户会失去信任；如果产品总是保守拒答，用户也不会继续使用。

## 3.15 个性化体验

大模型可以根据用户角色和偏好调整体验。

例如：

1. 给新手更多解释。
2. 给专家更短结论。
3. 给销售输出客户化话术。
4. 给工程师输出代码和命令。
5. 根据企业规范调整格式。

个性化要注意隐私和可控性。用户应该知道哪些偏好被记住，并能修改或删除。

## 3.16 体验指标

常见体验指标：

1. 任务完成率。
2. 首次成功率。
3. 平均完成时间。
4. 用户满意度。
5. 追问率。
6. 重新生成率。
7. 人工接管率。
8. 结果采纳率。
9. 引用点击率。
10. 留存率。

技术指标要和体验指标关联。例如延迟下降是否提升留存，引用准确率是否提升采纳率。

### 3.16.1 关键公式与能力到体验指标速查

为了避免只说“模型更强所以体验更好”，可以把一次产品交互记成结构化样本：

```math
e_i=(x_i,u_i,m_i,\hat y_i,y_i,z_i,\ell_i,c_i,r_i,h_i)
```

其中，$x_i$ 是用户输入，$u_i$ 是用户角色或场景，$m_i$ 是产品形态，$\hat y_i$ 是模型输出，$y_i$ 是期望结果或人工标注，$z_i$ 是可用证据或工具结果，$\ell_i$ 是端到端延迟，$c_i$ 是成本，$r_i$ 是风险标签，$h_i$ 是用户反馈或人工审核结果。

模型能力可以先抽象成一个能力向量：

```math
a_i=(U_i,G_i,R_i,Q_i,T_i,F_i,S_i)
```

其中，$U_i$ 是意图理解，$G_i$ 是生成质量，$R_i$ 是检索和引用能力，$Q_i$ 是复杂推理能力，$T_i$ 是工具调用能力，$F_i$ 是格式稳定性，$S_i$ 是安全和拒答能力。这个向量本身还不是体验，它必须映射到用户可观测指标。

任务成功率是最基础的体验指标：

```math
R_{\mathrm{succ}}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}(\hat y_i\ \mathrm{passes}\ V_i)
```

其中，$V_i$ 是任务验收函数，可以是单元测试、人工 rubric、引用检查、业务规则或用户采纳。验收函数必须贴近真实任务，而不是只看模型输出是否流畅；如果验收函数没有定义或任务样本为空，$R_{\mathrm{succ}}$ 应记为 `unknown`。

延迟满意度可以按 SLO 粗略归一化：

```math
L_i=\max(0,1-\frac{\ell_{p95,i}}{\tau_i})
```

其中，$\ell_{p95,i}$ 是在非空、明确分群的延迟样本上计算的 P95 端到端延迟，$\tau_i>0$ 是该产品形态的可接受延迟阈值。若没有延迟样本，$L_i$ 无定义，不应填 0。这个线性函数只是教学近似，而且当延迟达到阈值后被截为 0；闲聊、客服、IDE 补全和长报告的 $\tau_i$ 不一样，复杂任务可以慢，但需要进度反馈和可取消机制。

引用支持率衡量“用户为什么敢信”：

```math
C_{\mathrm{cite}}=\frac{\sum_i n_{\mathrm{sup},i}}{\sum_i n_{\mathrm{claim},i}}
```

其中，$n_{\mathrm{sup},i}$ 是被证据支持的关键结论数，$n_{\mathrm{claim},i}$ 是需要证据支持的关键结论数。只有任务确实产生了需要引用的 claim 时，该比率才适用；没有 claim 的代码补全不能把引用支持率记为 1，而应记为 `None` 或从综合分母中排除。对 RAG 和企业知识助手来说，引用支持率通常比“回答很像正确答案”更重要。

结构化输出稳定率衡量产品能否接入工作流：

```math
F_{\mathrm{fmt}}=\frac{N_{\mathrm{valid}}}{N}
```

其中，$N_{\mathrm{valid}}$ 是符合 JSON、表格、字段或业务模板要求的输出数，$N>0$。如果某个产品没有结构化输出契约，该指标应标记为不适用，而不是把所有输出默认当作有效；结构化输出失败会导致后续系统无法消费，即使文本内容看起来不错，也会破坏体验。

错误恢复率衡量用户遇到错误后能否继续完成任务：

```math
R_{\mathrm{rec}}=\frac{N_{\mathrm{recovered}}}{N_{\mathrm{failed}}}
```

其中，$N_{\mathrm{failed}}$ 是用户发现或系统检测到的失败次数，$N_{\mathrm{recovered}}$ 是通过追问、重新生成、修改约束、人工接管或工具校验恢复成功的次数，且 $0\le N_{\mathrm{recovered}}\le N_{\mathrm{failed}}$。没有失败样本时，恢复率是 `unknown`，不是 1；好产品不是永远不犯错，而是错误可见、可解释、可恢复。

信任校准可以用预测置信度和实际正确率的差距表示：

```math
K_{\mathrm{cal}}=1-\frac{1}{B}\sum_{b=1}^{B}|p_b-a_b|
```

其中，$p_b$ 是第 $b$ 个置信度桶的平均预测置信度，$a_b$ 是该桶真实正确率，$B>0$ 且每个桶都应有可用样本。若没有置信度或真实标签，校准分数是 `unknown`；过度自信会让用户误信错误答案，过度保守会造成过度拒答和低采用率。

综合体验分可以写成：

```math
S_{\mathrm{ux}}=0.25R_{\mathrm{succ}}+0.15L+0.15C_{\mathrm{cite}}+0.15F_{\mathrm{fmt}}+0.10C_{\mathrm{ctrl}}+0.10R_{\mathrm{rec}}+0.10K_{\mathrm{cal}}-0.15R_{\mathrm{over}}-0.20R_{\mathrm{unsafe}}
```

其中，$C_{\mathrm{ctrl}}$ 是用户可控性满意度，$R_{\mathrm{over}}$ 是过度拒答率，$R_{\mathrm{unsafe}}$ 是不安全或不合规输出率。只有适用指标都已观测时才计算该线性分数；不适用或未知指标应从分子、分母和报告中明确区分。权重可以按产品调整，核心思想是：体验必须同时看质量、延迟、可信、格式、可控、恢复和风险。

上线判断可以形式化为：

```math
G_{\mathrm{ux}}=\mathbb{1}[R_{\mathrm{succ}}\ge \tau_s\land \ell_{p95}\le \tau_l\land C_{\mathrm{cite}}\ge \tau_c\land F_{\mathrm{fmt}}\ge \tau_f\land R_{\mathrm{unsafe}}\le \tau_u]
```

这组条件提醒我们不要只说“换更强模型”。如果 P95 延迟、引用支持、格式稳定、安全和恢复不满足目标条件，高分模型也不该直接进入生产体验。任一适用指标没有样本或验收函数未定义时，条件结果应为 `unknown`；不适用指标则要从该产品的评审条件中明确移除，不能自动当作通过。

## 3.17 常见失败模式

1. 模型能力强，但交互入口复杂。
2. 回答准确，但太慢。
3. 输出格式不稳定，无法接入流程。
4. 拒答策略过度保守或过度宽松。
5. 没有引用，用户不敢信。
6. 错误后没有反馈入口。
7. 风格不符合业务场景。
8. 用户不会写 prompt。
9. 产品只追求炫技，不解决任务。
10. 体验指标和模型指标脱节。

产品体验是模型、系统、交互和业务流程共同作用的结果。

## 3.18 建立能力到体验的评审链

把能力映射到体验时，先明确用户任务和成功标准，再为每个能力指定可观察结果。意图理解可以对应任务路由和首次成功率，生成能力可以对应草稿质量和采纳率，检索能力可以对应引用支持率，推理能力可以对应复杂任务成功率，工具能力可以对应执行完成率和外部状态验证。每一个映射都要说明验收函数、样本来源和失败后的处理方式。

例如，客服助手的检索召回提升，并不自动说明用户体验变好。若新增文档带来更多无关候选，答案会变长，延迟会上升，用户反而更难找到可执行结论。只有当引用支持、任务成功、采纳和处理时长同时改善，才能把检索变化解释为产品收益。

## 3.19 为什么高分模型仍可能带来差体验

benchmark 通常只覆盖一组固定任务和单次输出，而产品体验还受尾延迟、版本漂移、格式稳定性、交互入口、引用、拒答、风格、成本和错误恢复影响。一个模型离线分数高，但如果线上响应慢、输出格式不稳定、不能解释来源、错误时无法恢复，用户仍然会把它判断为不好用。

因此，模型替换实验不能只比较离线准确率。至少要固定任务定义和流量分层，同时观察任务成功、采纳、重试、人工接管、P95/P99 延迟、结构化失败、引用支持、安全事件和单位成本。模型分数的提升只有在这些指标中形成可重复的变化，才有产品意义。

## 3.20 最小可运行能力到体验审计 demo

下面的 0 依赖 demo 演示一个教学版 experience audit：输入若干产品形态的 toy 观测指标，输出任务成功、P95 延迟、引用支持、格式稳定、错误恢复、信任校准、综合体验分、失败原因和体验验收条件。它的目的不是替代真实 A/B test，而是帮助你把“模型能力”翻译成“用户体验是否过线”。

```python
import math


def require_count(value, field_name):
    if type(value) is not int or value < 0:
        raise ValueError(f"{field_name} must be a non-negative integer")


def require_rate(value, field_name):
    if not isinstance(value, (int, float)) or isinstance(value, bool):
        raise TypeError(f"{field_name} must be a finite number")
    if not math.isfinite(value) or not 0 <= value <= 1:
        raise ValueError(f"{field_name} must be between 0 and 1")


def safe_div(num, den):
    require_count(num, "numerator")
    require_count(den, "denominator")
    if num > den:
        raise ValueError("numerator cannot exceed denominator")
    return None if den == 0 else num / den


def require_product(product):
    if not isinstance(product, dict):
        raise TypeError("product must be a dict")
    require_count(product.get("interactions"), "interactions")
    count_fields = (
        "task_success",
        "adopted",
        "claims",
        "supported_claims",
        "structured_outputs",
        "control_satisfied",
        "failures",
        "recovered",
        "over_refusals",
        "unsafe_outputs",
    )
    for field_name in count_fields:
        require_count(product.get(field_name), field_name)
    for field_name in (
        "task_success",
        "adopted",
        "structured_outputs",
        "control_satisfied",
        "failures",
        "over_refusals",
        "unsafe_outputs",
    ):
        if product[field_name] > product["interactions"]:
            raise ValueError(f"{field_name} cannot exceed interactions")
    if product["supported_claims"] > product["claims"]:
        raise ValueError("supported_claims cannot exceed claims")
    if product["recovered"] > product["failures"]:
        raise ValueError("recovered cannot exceed failures")
    for field_name in ("p95_latency_ms", "latency_slo_ms", "avg_cost"):
        value = product.get(field_name)
        if not isinstance(value, (int, float)) or isinstance(value, bool):
            raise TypeError(f"{field_name} must be a finite number")
        if not math.isfinite(value) or value < 0:
            raise ValueError(f"{field_name} must be finite and non-negative")
    if product["latency_slo_ms"] <= 0:
        raise ValueError("latency_slo_ms must be positive")


def weighted_mean(parts):
    applicable = [(value, weight) for value, weight in parts if value is not None]
    if not applicable:
        return None
    return sum(value * weight for value, weight in applicable) / sum(
        weight for _, weight in applicable
    )

def calibration_score(bins):
    if not isinstance(bins, (list, tuple)):
        raise TypeError("confidence_bins must be a list or tuple")
    if not bins:
        return None
    for predicted, actual, count in bins:
        require_rate(predicted, "predicted_confidence")
        require_rate(actual, "actual_accuracy")
        require_count(count, "bin_count")
    total = sum(count for _, _, count in bins)
    if total == 0:
        return None
    error = sum(abs(pred - actual) * count for pred, actual, count in bins)
    return round(max(0.0, min(1.0, 1.0 - error / total)), 3)


def audit(product):
    require_product(product)
    n = product["interactions"]
    success = safe_div(product["task_success"], n)
    adoption = safe_div(product["adopted"], n)
    latency_score = (
        None
        if n == 0
        else max(
            0.0,
            min(1.0, 1.0 - product["p95_latency_ms"] / product["latency_slo_ms"]),
        )
    )
    citation = (
        None
        if product["claims"] == 0
        else safe_div(product["supported_claims"], product["claims"])
    )
    format_stability = safe_div(product["structured_outputs"], n)
    controllability = safe_div(product["control_satisfied"], n)
    recovery = safe_div(product["recovered"], product["failures"])
    calibration = calibration_score(product["confidence_bins"])
    over_refusal = safe_div(product["over_refusals"], n)
    unsafe_rate = safe_div(product["unsafe_outputs"], n)
    ux_score = weighted_mean(
        [
            (success, 0.25),
            (latency_score, 0.15),
            (citation, 0.15),
            (format_stability, 0.15),
            (controllability, 0.10),
            (recovery, 0.10),
            (calibration, 0.10),
            (adoption, 0.05),
            (None if over_refusal is None else 1.0 - over_refusal, 0.15),
            (None if unsafe_rate is None else 1.0 - unsafe_rate, 0.20),
        ]
    )
    metrics = {
        "success_rate": None if success is None else round(success, 3),
        "adoption_rate": None if adoption is None else round(adoption, 3),
        "latency_score": None if latency_score is None else round(latency_score, 3),
        "citation_support": None if citation is None else round(citation, 3),
        "format_stability": None if format_stability is None else round(format_stability, 3),
        "controllability": None if controllability is None else round(controllability, 3),
        "recovery_rate": None if recovery is None else round(recovery, 3),
        "calibration": calibration,
        "over_refusal_rate": None if over_refusal is None else round(over_refusal, 3),
        "unsafe_rate": None if unsafe_rate is None else round(unsafe_rate, 3),
        "avg_cost": product["avg_cost"],
        "ux_score": None if ux_score is None else round(ux_score, 3),
    }

    failed = []
    unknown = []
    not_applicable = []
    if metrics["success_rate"] is None:
        unknown.append("task_success")
    elif metrics["success_rate"] < 0.72:
        failed.append("task_success")
    if n == 0:
        unknown.append("p95_latency")
    elif product["p95_latency_ms"] > product["latency_slo_ms"]:
        failed.append("p95_latency")
    if product["claims"] == 0:
        not_applicable.append("citation")
    elif metrics["citation_support"] is None:
        unknown.append("citation")
    elif metrics["citation_support"] < 0.80:
        failed.append("citation")
    if metrics["format_stability"] is None:
        unknown.append("format")
    elif metrics["format_stability"] < 0.82:
        failed.append("format")
    if metrics["controllability"] is None:
        unknown.append("control")
    elif metrics["controllability"] < 0.65:
        failed.append("control")
    if metrics["recovery_rate"] is None:
        unknown.append("recovery")
    elif metrics["recovery_rate"] < 0.55:
        failed.append("recovery")
    if metrics["calibration"] is None:
        unknown.append("calibration")
    elif metrics["calibration"] < 0.82:
        failed.append("calibration")
    if metrics["over_refusal_rate"] is None:
        unknown.append("over_refusal")
    elif metrics["over_refusal_rate"] > 0.08:
        failed.append("over_refusal")
    if metrics["unsafe_rate"] is None:
        unknown.append("unsafe")
    elif metrics["unsafe_rate"] > 0.0:
        failed.append("unsafe")

    metrics["status"] = (
        "failed"
        if failed

        if unknown or metrics["ux_score"] is None

    )
```

## 3.22 资料入口与证据边界

- [OpenAI Evals 指南](https://developers.openai.com/api/docs/guides/evals)：官方评估入口，可支持任务、样本、指标和持续回归的讨论；它不替代具体产品的用户体验研究。
- [OpenAI 延迟优化指南](https://developers.openai.com/api/docs/guides/latency-optimization)：官方工程文档，可支持 token、模型调用、缓存、并行和延迟优化的讨论；具体 P95/P99 必须在目标流量下实测。
- [Google HEART 论文入口](https://research.google/pubs/pub4806)：用户体验指标框架入口，可支持 goals、signals 和 metrics 的讨论；框架本身不能证明模型输出正确。
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：官方风险治理框架，可支持透明性、风险和责任的讨论；它不自动完成具体产品的安全验收。
- [NIST Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)：官方生成式 AI 风险画像，可支持生成内容、数据、评估和治理边界的讨论；实际产品仍需结合行业和数据流验证。

本章的体验分和 demo 是教学构造，不是用户满意度或上线结果的预测。代码助手没有引用 claim 时，引用指标不适用；没有失败样本时，恢复率未知；没有真实标签时，校准分数未知。实际评估还应记录任务定义、用户分群、版本、人工审核、成本、反馈偏差和失败样本。

## 3.23 本章小结

大模型产品体验不是模型能力的简单外显，而是模型、系统和交互设计共同塑造的结果。延迟、准确性、可控性、解释性、引用、拒答、风格、错误恢复和用户引导，都会决定用户是否愿意持续使用。
