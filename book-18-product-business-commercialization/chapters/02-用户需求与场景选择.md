# 第二章：用户需求与场景选择

## 0. 本讲范围与资料

本章重点讨论如何在开发前判断一个候选场景是否值得试点。联网资料主要核对四类口径：OpenAI evals 与生产评估强调先定义任务、样本、指标和反馈闭环；Google HEART 框架强调把用户目标拆成 goals、signals、metrics；Google SRE 的 SLI / SLO / error budget 口径提醒我们把可靠性和可接受失败率放进上线条件；NIST AI RMF / Generative AI Profile 提醒我们在场景筛选阶段就评估风险、可控性和治理责任。

本章不讨论具体模型选型、prompt 模板、RAG 架构、Agent 工具协议或企业销售合同细节。这里的核心问题只有一个：在动手做大模型应用前，如何判断一个候选场景是否有真实用户、真实痛点、可衡量收益、可控风险和可试点路径。

大模型落地的第一步不是选模型，而是选场景。场景选错，再强的模型也很难产生价值；场景选对，即使模型方案不复杂，也可能带来明显收益。很多失败的大模型项目，不是技术完全做不出来，而是需求不真实、用户不用、成本不划算或风险不可控。

本章系统讲用户需求与场景选择：如何判断需求是否真实，如何筛选高价值场景，如何评估任务频率、容错率、数据可得性、自动化空间、ROI、组织阻力和落地优先级。对算法工程师来说，这一章能帮助你把项目从“技术可行”讲到“业务值得做”。

## 2.1 场景选择为什么重要

同样的大模型能力，在不同场景中的价值完全不同。

例如“文档总结”：

1. 给用户总结一篇普通新闻，价值有限。
2. 给律师总结合同风险，价值较高。
3. 给客服总结用户历史工单，能节省时间。
4. 给医生总结病历，价值高但风险也高。

技术能力相似，但用户、价值、风险、合规和验收标准完全不同。

把上述判断落到一个具体项目上，可以按这样的顺序叙述：先说明谁在什么任务中遇到什么瓶颈，再说明当前替代方案的时间、成本和错误，接着解释大模型提供的增量能力，最后给出收益、风险、验证方式和试点范围。这样，场景选择就不是一句“这个需求适合大模型”，而是一条可以被业务方、工程方和治理方共同检查的证据链。

## 2.2 真实需求和伪需求

真实需求通常有几个特征：

1. 用户现在已经在花时间或花钱解决。
2. 问题高频或高价值。
3. 用户愿意改变工作流。
4. 解决后有明确收益。
5. 失败后用户会明显不满。

伪需求常见表现：

1. 只是觉得“大模型很酷”。
2. 用户说想要，但实际不用。
3. 没有明确使用场景。
4. 没有可衡量指标。
5. 传统规则已经足够。
6. 只是内部展示项目。

判断需求时，不要只听用户说什么，还要看用户现在怎么做、痛点出现频率、愿意为解决方案付出什么成本。

## 2.3 用户是谁

同一个产品，不同用户的需求不同。

例如企业知识库问答：

1. 一线客服关心快速查到答案。
2. 客服主管关心解决率和转人工率。
3. IT 团队关心权限和系统集成。
4. 法务关心合规。
5. 管理层关心成本收益。

场景选择必须明确主用户和决策者。很多项目失败，是因为使用者觉得麻烦，决策者只看概念，技术团队只看模型指标，三方目标不一致。

## 2.4 用户任务链路

不要只看单点功能，要看完整任务链路。

例如“帮销售写方案”不是一个单步任务。它可能包括：

1. 了解客户行业。
2. 查询历史案例。
3. 选择产品卖点。
4. 生成方案初稿。
5. 人工修改。
6. 审批。
7. 发给客户。

大模型可以介入哪个环节？哪个环节最耗时？哪个环节最容易出错？哪个环节最能衡量收益？这些问题比“模型能不能写方案”更重要。

## 2.5 高频场景和高价值场景

高频场景：每天大量发生，单次价值可能不高，但总收益大。

例如：

1. 客服问答。
2. 工单分类。
3. 文档检索。
4. 会议纪要。
5. 邮件草稿。

高价值场景：发生频率不一定高，但单次价值大。

例如：

1. 合同风险审查。
2. 重大故障排查。
3. 投研报告分析。
4. 代码迁移。
5. 企业知识沉淀。

优先级不只看频率，也看单次收益、风险和落地难度。

## 2.6 容错率

容错率决定产品形态。

高容错场景：

1. 头脑风暴。
2. 文案初稿。
3. 会议摘要草稿。
4. 内部知识探索。

低容错场景：

1. 医疗诊断。
2. 法律结论。
3. 财务报表。
4. 权限修改。
5. 自动下单或支付。

高容错场景可以更自动化；低容错场景需要人审、引用、验证、权限和审计。不能把低容错场景做成完全自动化黑盒。

## 2.7 数据可得性

大模型应用离不开数据。

要评估：

1. 是否有知识库。
2. 数据是否结构化。
3. 数据是否最新。
4. 数据质量如何。
5. 是否有权限访问。
6. 是否包含隐私。
7. 是否能用于评估。
8. 是否有历史反馈。

很多 RAG 项目失败，不是模型不会答，而是知识库混乱、文档过期、权限不清、没有标准答案。

## 2.8 任务是否可验证

可验证性决定落地难度。

容易验证：

1. 代码测试是否通过。
2. 表单字段是否填对。
3. 答案是否来自文档。
4. 分类是否匹配标签。
5. 数据分析结果是否符合计算。

难验证：

1. 创意是否好。
2. 战略建议是否正确。
3. 用户是否满意。
4. 开放式分析是否全面。

可验证场景更适合自动化和规模化；难验证场景更需要人工反馈、评价体系和灰度上线。

## 2.9 大模型是否必要

不是所有智能需求都需要大模型。

可以先问：

1. 规则能否解决？
2. 搜索能否解决？
3. 传统分类模型能否解决？
4. 模板能否解决？
5. 工作流优化能否解决？

如果规则和搜索已经足够，大模型可能增加成本和不确定性。大模型适合处理自然语言、多样表达、长尾问题、生成式任务和复杂上下文。

## 2.10 自动化空间

大模型不一定要完全自动化。可以分层：

1. Assist：辅助用户生成草稿。
2. Recommend：给出建议和候选。
3. Review：帮助检查和发现问题。
4. Automate with approval：自动执行但需确认。
5. Fully automate：完全自动执行。

很多场景适合先做辅助，而不是一开始就全自动。随着数据和信任积累，再逐步提高自动化程度。

## 2.11 ROI 初步估算

场景选择要做粗略 ROI 估算。

可以先使用同一观察窗口做粗估：

```text
月收益 = 合格任务量 * 采用率 * (单次节省时间 * 小时价值 + 单次结果增量价值)
月成本 = 模型调用 + 检索 + 工具 + 人审 + 运维 + 研发摊销 + 预期风险损失
```

这里的“合格任务量”必须和成功率、采用率的统计口径一致；如果任务量、基线或收益估计缺失，结果应记为 `unknown`，不能把缺失值当成 0。若收益远小于成本，就算技术可行也不值得优先做；如果收益估计依赖未经验证的用户意愿，也只能进入小规模验证，不能直接据此扩容。

ROI 不是只算钱，也可以记录风险降低、客户满意度、交付速度等非货币结果。但这些结果不能和现金收益无说明地相加；要么转换到共同价值单位，要么分别报告，最终仍要连接到业务目标。

## 2.12 落地难度

落地难度来自多个方面：

1. 数据治理难度。
2. 系统集成难度。
3. 用户习惯改变。
4. 权限和合规要求。
5. 评估标准不清。
6. 延迟要求。
7. 成本约束。
8. 组织协作成本。

一个高价值但落地极难的场景，不一定适合作为第一个项目。早期可以选择价值中等但可快速验证的场景建立信任。

## 2.13 场景优先级矩阵

可以用二维矩阵评估：

```text
业务价值高 + 落地难度低：优先做
业务价值高 + 落地难度高：拆分试点
业务价值低 + 落地难度低：可做 demo 或辅助功能
业务价值低 + 落地难度高：不做
```

更细一点，可以打分：

1. 用户痛点：1 到 5 分。
2. 任务频率：1 到 5 分。
3. 单次价值：1 到 5 分。
4. 数据可得性：1 到 5 分。
5. 可验证性：1 到 5 分。
6. 风险可控性：1 到 5 分。
7. 集成难度：反向 1 到 5 分。
8. 成本可控性：1 到 5 分。

评分不是为了假装精确，而是帮助团队把隐含判断显性化。

### 2.13.1 把场景判断写成可复盘的模型

为了让场景选择不只停留在主观讨论，可以把每个候选场景记成一个结构化样本：

```math
s_i=(u_i,j_i,p_i,f_i,v_i,d_i,e_i,l_i,k_i,w_i,a_i,h_i)
```

其中，$u_i$ 是用户和利益相关方，$j_i$ 是任务链路，$p_i$ 是痛点强度，$f_i$ 是月任务频次，$v_i$ 是单次任务价值，$d_i$ 是数据可得性，$e_i$ 是结果可验证性，$l_i$ 是大模型适配度，$k_i$ 是剩余风险，$w_i$ 是工作流适配度，$a_i$ 是自动化层级，$h_i$ 是落地难度。这个 tuple 不是要背诵的评分表，而是一份防遗漏清单：只要用户、任务、价值、数据、验证、风险或工作流中的一项没有证据，场景就不应该被描述成“已经准备好”。

真实需求不是一句“用户说想要”，而是痛点、当前替代方案和组织承诺共同成立。可以把痛点粗略归一化为：

```math
P_i=0.4p_i+0.3q_i+0.3r_i
```

其中，$p_i$ 是问题严重度，$q_i$ 是任务紧急度，$r_i$ 是当前方案的不满意程度，三者都归一化到 $[0,1]$，且权重需要在项目开始前固定。这个式子只是把不同访谈信号放到同一张表里，不会自动证明需求真实。如果缺少访谈、行为日志或当前替代方案中的任一关键输入，$P_i$ 应标为 `unknown`；不能用 0 代替“尚未调查”。如果用户没有当前替代方案，也没有愿意投入的时间、数据或预算，即使口头兴趣很强，也要降低真实需求判断。

月度收益可以先做粗估：

```math
B_i=f_i(h_i c_i+v_i g_i)
```

其中，$f_i$ 是月任务量，$h_i$ 是单次节省小时数，$c_i$ 是小时成本或机会成本，$v_i$ 是单次任务价值，$g_i$ 是成功率、质量或转化率提升带来的增量比例。该式只有在两项都能转换成同一价值单位、并且没有重复计算同一收益时才成立；真实项目还要乘以采用率，并扣除审核、失败重试和运维成本。$g_i$ 可以为负，表示方案使结果变差；若基线或线上结果没有足够样本，$B_i$ 应为 `unknown`。

大模型适配度可以写成一个加权分：

```math
L_i=0.35n_i+0.25c_i+0.20g_i+0.20o_i-0.30r_i
```

其中，$n_i$ 表示自然语言表达变化程度，$c_i$ 表示上下文依赖，$g_i$ 表示生成、总结、改写或推理需求，$o_i$ 表示长尾输入比例，$r_i$ 表示规则、搜索或模板已经足够的程度。五项应在 `[0,1]` 内，权重和惩罚项要在评审前固定。这个分数提醒你：不是所有智能需求都该上 LLM；如果规则和搜索稳定解决，LLM 可能只是增加成本和不确定性。它也不是质量保证，只有与任务成功率、延迟和风险实验结合时才有决策意义。

为了把“业务价值”和“落地可行性”放在一起，常把收益映射到一个参考区间：

```math
V_i=\min(1,\max(0,\frac{B_i}{B_{\mathrm{ref}}}))
```

其中，$B_{\mathrm{ref}}>0$ 是团队约定的参考收益阈值，且这个映射只服务于排序。它把负收益在排序分量中压到 0，但不能覆盖原始的负 `B_i`；财务账本必须同时保留原值。如果 `B_i` 未知，`V_i` 也未知，不能把未知收益按 0 分处理。然后给候选场景一个优先级分：

```math
S_i=0.25P_i+0.20V_i+0.15L_i+0.15D_i+0.10E_i+0.10W_i+0.05A_i-0.15H_i-0.10K_i
```

其中，$D_i$ 是数据准备度，$E_i$ 是可验证性，$W_i$ 是工作流适配度，$A_i$ 是自动化层级合理性，$H_i$ 是落地难度，$K_i$ 是剩余风险。各项都应在 `[0,1]` 内；权重不是固定真理，真实项目可以按行业调整，但必须在比较候选前固定，并保留原始分项。若任意关键分项未知，$S_i$ 只能标为 `unknown`，不能通过把缺失项设为 0 或默认高分来强行排序。

进入试点的基本条件可以形式化为：

```math
G_{\mathrm{pilot},i}=\mathbb{1}(P_i\ge \tau_p\land B_i\ge \tau_b\land L_i\ge \tau_l\land D_i\ge \tau_d\land E_i\ge \tau_e\land K_i\le \tau_k)
```

其中，$\tau_p,\tau_b,\tau_l,\tau_d,\tau_e,\tau_k$ 是团队预先设定的阈值。这个二值式只适用于所有分项都有定义的情况。实际评审可以把每个条件记成 `passed`、`failed` 或 `unknown`：有一项明确失败时暂缓或拒绝；没有失败但存在未知项时要求补证据；只有全部条件通过，才适合进入受控试点。它表达的不是“分数高就一定成功”，而是“痛点、收益、LLM 适配度、数据、验证和风险至少要同时有证据”。

## 2.14 试点场景

大模型产品通常适合先试点。

好的试点场景：

1. 用户明确。
2. 数据可得。
3. 任务边界清楚。
4. 风险可控。
5. 指标可衡量。
6. 能在短周期看到效果。
7. 成功后可以扩展。

试点不是做玩具 demo，而是用受控范围验证真实价值。

## 2.15 和业务方沟通的问题清单

和业务方沟通时，可以问：

1. 现在这个任务谁在做？
2. 每天或每月发生多少次？
3. 单次大约耗时多久？
4. 当前错误率或投诉点是什么？
5. 成功后希望提升哪个指标？
6. 可接受的错误是什么，不可接受的错误是什么？
7. 是否有历史数据和标准答案？
8. 是否需要审批或合规评估？
9. 用户是否愿意改变工作流？
10. 如果只能辅助一部分，最希望辅助哪一步？

这些问题比直接问“你想要一个 AI 功能吗”更有效。

## 2.16 常见失败模式

1. 没有真实用户。
2. 痛点不够痛。
3. 任务频率太低。
4. 数据不可用或质量差。
5. 风险不可控。
6. 评估指标不清。
7. 用户工作流接不进去。
8. 成本高于收益。
9. 一开始就追求全自动。
10. 技术团队和业务团队目标不一致。

场景选择阶段发现问题，是好事。越早发现不值得做，越能节省成本。

## 2.17 把需求证据说清楚

判断场景时，不能只把用户访谈中的愿望记录下来。至少要把四类证据放在一起：用户是否已经采取替代行动，任务实际发生的频率和成本，解决后哪个结果会变化，以及用户和组织是否愿意承担迁移成本。比如客服说“希望有一个聊天机器人”只是产品形式的偏好；如果进一步观察到客服每天在多个系统之间复制检索、平均每单耗时两分钟、主管已经关注转人工率，那么需求才开始具备可验证的任务定义。

需求证据也可能互相矛盾。管理者认为任务高频，日志却显示只有少数复杂工单；用户说愿意使用，试点中却不愿意离开原系统；离线答案很好，实际工作流没有可插入的位置。此时不应挑选最有利的数字，而应把矛盾记录为试点问题，并设计能够区分假设的观测。

## 2.18 从场景筛选到试点决策

一个可复用的筛选流程可以分成五步。第一步锁定主用户、决策者和受影响的其他角色；第二步画出当前任务链路，标出耗时、重复劳动、错误和审批节点；第三步比较规则、搜索、传统模型、人工和大模型的替代方案；第四步估算价值、成本、风险和验证难度；第五步确定最小试点范围、退出条件和需要补齐的证据。

最终输出不应该只有一个总分，而应至少包含三部分：候选场景的分项证据、推荐动作（试点、拆分试点、补证据、暂缓或拒绝）和推荐理由。高风险场景即使总分很高，也不能绕过权限、人工确认和外部验收；低风险场景即使收益有限，也可能适合作为验证工作流和反馈闭环的第一步。

## 2.19 最小可运行场景选择审计 demo

def require_rate(value, field_name, allow_unknown=False):
    if value is None and allow_unknown:

def require_delta(value, field_name, allow_unknown=False):

def validate_scenario(s):
    if not isinstance(s, dict):
        raise TypeError("scenario must be a dict")
    require_text(s.get("name"), "name")
    if type(s.get("monthly_frequency")) is not int or s["monthly_frequency"] < 0:
        raise ValueError("monthly_frequency must be a non-negative integer")
    for field_name in (
        "user_pain",
        "language_variability",
        "context_need",
        "generation_need",
        "long_tail",
        "rule_sufficiency",
        "data_readiness",
        "verifiability",
        "risk_control",
        "workflow_fit",
        "implementation_difficulty",
        "stakeholder_alignment",
    ):
        require_rate(s.get(field_name), field_name, allow_unknown=True)
    require_delta(s.get("quality_uplift"), "quality_uplift", allow_unknown=True)
    for field_name in ("time_saved_hours", "hourly_cost", "value_per_task"):
        value = s.get(field_name)
        if value is not None:
            require_nonnegative(value, field_name)
    require_text(s.get("automation_level"), "automation_level")
    if s["automation_level"] not in AUTOMATION_SCORE:
        raise ValueError(f"unsupported automation level: {s['automation_level']}")
    if type(s.get("current_workaround")) is not bool:
        raise TypeError("current_workaround must be bool")


def reality_score(s):
    validate_scenario(s)
    required = (
        s["user_pain"],
        s["workflow_fit"],
        s["stakeholder_alignment"],
    )
    if any(value is None for value in required):
        return None
    observed = 1.0 if s["current_workaround"] else 0.0
    freq_score = min(1.0, s["monthly_frequency"] / 1000.0)
    score = (
        0.35 * s["user_pain"]
        + 0.25 * freq_score
        + 0.20 * s["workflow_fit"]
        + 0.10 * observed
        + 0.10 * s["stakeholder_alignment"]
    )
    return round(score, 3)


def monthly_benefit(s):
    validate_scenario(s)
    if any(s[field] is None for field in ("time_saved_hours", "hourly_cost", "value_per_task", "quality_uplift")):
        return None
    time_value = s["time_saved_hours"] * s["hourly_cost"]
    quality_value = s["value_per_task"] * s["quality_uplift"]
    return round(s["monthly_frequency"] * (time_value + quality_value), 2)


def llm_fit_score(s):
    validate_scenario(s)
    fields = ("language_variability", "context_need", "generation_need", "long_tail", "rule_sufficiency")
    if any(s[field] is None for field in fields):
        return None
    score = (
        0.35 * s["language_variability"]
        + 0.25 * s["context_need"]
        + 0.20 * s["generation_need"]
        + 0.20 * s["long_tail"]
        - 0.30 * s["rule_sufficiency"]
    )
    return round(max(0.0, min(1.0, score)), 3)


def audit(s, benefit_ref=20000.0):
    validate_scenario(s)
    require_nonnegative(benefit_ref, "benefit_ref")
    if benefit_ref <= 0:
        raise ValueError("benefit_ref must be positive")
    benefit = monthly_benefit(s)
    benefit_score = None if benefit is None else max(0.0, min(1.0, benefit / benefit_ref))
    llm_fit = llm_fit_score(s)
    automation = AUTOMATION_SCORE[s["automation_level"]]
    numeric_fields = (
        "user_pain",
        "data_readiness",
        "verifiability",
        "workflow_fit",
        "risk_control",
        "implementation_difficulty",
        "stakeholder_alignment",
    )
    known = all(s[field] is not None for field in numeric_fields) and benefit_score is not None and llm_fit is not None
    priority = None
    if known:
        residual_risk = 1.0 - s["risk_control"]
        priority = (
            0.25 * s["user_pain"]
            + 0.20 * benefit_score
            + 0.15 * llm_fit
            + 0.15 * s["data_readiness"]
            + 0.10 * s["verifiability"]
            + 0.10 * s["workflow_fit"]
            + 0.05 * automation
            - 0.15 * s["implementation_difficulty"]
            - 0.10 * residual_risk
        )
        priority = round(max(0.0, min(1.0, priority)), 3)
    real_demand = (
        None
        if reality_score(s) is None or s["value_per_task"] is None
        else reality_score(s) >= 0.60
        and s["current_workaround"]
        and s["monthly_frequency"] * s["value_per_task"] > 0
    )

    rejected_reasons = []
    if real_demand is None:
        rejected_reasons.append("real_demand_unknown")
    elif not real_demand:
        rejected_reasons.append("real_demand")
    if s["user_pain"] is None:
        rejected_reasons.append("pain_unknown")
    elif s["user_pain"] < 0.60:
        rejected_reasons.append("pain")
    if benefit_score is None:
        rejected_reasons.append("business_value_unknown")
    elif benefit_score < 0.18:
        rejected_reasons.append("business_value")
    if llm_fit is None:
        rejected_reasons.append("llm_fit_unknown")
    elif llm_fit < 0.55:
        rejected_reasons.append("llm_fit")
    if s["data_readiness"] is None:
        rejected_reasons.append("data_unknown")
    elif s["data_readiness"] < 0.55:
        rejected_reasons.append("data")
    if s["verifiability"] is None:
        rejected_reasons.append("verifiability_unknown")
    elif s["verifiability"] < 0.55:
        rejected_reasons.append("verifiability")
    if s["risk_control"] is None:
        rejected_reasons.append("risk_unknown")
    elif s["risk_control"] < 0.60:
        rejected_reasons.append("risk_control")
    if s["workflow_fit"] is None:
        rejected_reasons.append("workflow_unknown")
    elif s["workflow_fit"] < 0.55:
        rejected_reasons.append("workflow")
    if s["implementation_difficulty"] is None:
        rejected_reasons.append("difficulty_unknown")
    elif s["implementation_difficulty"] > 0.70:
        rejected_reasons.append("difficulty")

    if real_demand is False or (s["risk_control"] is not None and s["risk_control"] < 0.45):
        recommendation = "reject"
    elif real_demand is None or priority is None:
        recommendation = "collect_evidence"
    elif not rejected_reasons and priority is not None and priority >= 0.70:
        recommendation = "pilot"
    elif priority is not None and priority >= 0.58 and s["user_pain"] is not None and s["user_pain"] >= 0.65 and benefit_score is not None and benefit_score >= 0.35:
        recommendation = "split_pilot"
    elif priority is not None and priority >= 0.43:
        recommendation = "defer"
    else:
        recommendation = "reject"

    return {
        "real_demand": real_demand,
        "monthly_benefit": benefit,
        "benefit_score": None if benefit_score is None else round(benefit_score, 3),
        "llm_fit": llm_fit,
        "priority_score": priority,
        "recommendation": recommendation,
        "rejected_reasons": rejected_reasons,
    }


audits = {s["name"]: audit(s) for s in SCENARIOS}
ranked = sorted(

print("rejected=", {name: a["rejected_reasons"] for name, a in audits.items() if a["recommendation"] == "reject"})

## 2.21 资料入口与证据边界

- [OpenAI Evals 指南](https://developers.openai.com/api/docs/guides/evals)：官方评估入口，可支持任务、样本、指标和持续反馈的讨论；它不替代具体场景的用户研究或财务验证。
- [Google HEART 论文入口](https://research.google/pubs/pub4806)：Google Research 的用户体验指标框架入口，可支持 goals、signals 和 metrics 的讨论；框架本身不能证明某个 AI 场景有真实需求。
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：官方风险治理框架，可支持在场景筛选阶段讨论风险识别、测量和责任；它不自动完成具体产品的合规判断。
- [NIST Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)：官方生成式 AI 风险画像，可支持生成式系统特有风险的分类讨论；文档中的风险类别仍需结合目标行业和数据流落地。

本章的分数和 demo 是教学构造。场景评估应补充访谈记录、行为日志、基线窗口、样本量、用户分群、权限边界、人工审核成本和失败案例；评分器只能整理证据，不能替代证据。

## 2.22 本章小结

大模型产品化首先要选对场景。好的场景通常有真实用户、明确痛点、高频或高价值、数据可得、风险可控、结果可验证，并且能接入现有工作流。场景选择不是拍脑袋，而是对用户、任务、数据、成本、风险和 ROI 的综合判断。

下一章会进入“模型能力到产品体验”，讨论如何把模型的理解、生成、检索、推理和工具调用能力，转化为用户真正感受到的产品体验。
