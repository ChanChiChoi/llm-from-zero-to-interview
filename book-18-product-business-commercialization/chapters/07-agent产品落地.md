# 第七章：Agent 产品落地

一封回答写错，用户还可以先读出来；一封邮件发错、一个订单改错，系统状态已经改变。Agent（智能体）产品因此多了一项必须设计的能力：让模型提出的动作经过授权、确认、执行和结果验收，才算完成任务。

本章沿一项客服工单任务回答这个问题：什么时候值得让模型动态选择步骤，怎样限制它能做的事，动作失败或结果不确定时怎么处理，最后又凭什么决定扩大自动化范围。第十七册的[工具调用](../../book-17-agent-tool-use/chapters/02-tool-use与function-calling.md)和[ReAct、Plan-Act-Observe](../../book-17-agent-tool-use/chapters/03-react与plan-act-observe.md)解释机制；这里把这些机制接到用户任务、企业权限和产品验收上。

## 7.1 先定义任务，再谈 Agent

一个可交付的 Agent 任务至少要说清六件事：谁发起、目标资源是什么、允许做什么、哪些结果算完成、预算和截止时间是多少、异常时由谁接手。它们构成任务契约。缺少完成标准时，模型可以写出像完成了的答复，系统却无法判断业务是否真的完成。

例如，“处理这张退款工单”太宽。更可控的契约可以写成：读取当前用户有权查看的一张工单和对应订单；根据当前政策核实退款条件；生成回复草稿；不得发出回复或发起退款；若订单与政策冲突，转人工。此时任务结果可通过工单、订单、政策版本和草稿逐项核对。

Agent 的产品对象也不只是模型。它还包括运行状态、工具执行器、身份与授权、人工确认、外部业务系统、验收器和审计记录。模型可以提出“查询订单”或“发送回复”，是否执行由这些系统决定。模型成功生成工具参数，只能说明它产出了一项提议。

## 7.2 只有动态选择能解决的问题才需要 Agent

如果每个请求都按相同次序读取固定字段、执行固定规则并产出固定格式，确定性工作流通常更容易测试和维护。只有当输入会改变必要步骤，且系统必须根据查询结果、例外或错误选择下一步时，Agent 的灵活性才可能值得额外的评估、观测和恢复成本。

可以从四个问题开始判断：

1. 固定 API、规则或工作流是否已经能处理大多数目标任务？
2. 不同输入是否真的需要不同路径，且下一步取决于刚观察到的结果？
3. 每种重要结果是否有独立的业务验收条件？
4. 出错时能否限制副作用、查明状态并转人工或恢复？

每周从三个系统导出同一张报表，路径固定，适合工作流。根据工单描述查找不同系统、解释数据冲突并提出处理草稿，可能需要有限的动态选择。若目标无法说清、结果无法核验、外部状态不可查询或动作不可恢复，Agent 应停留在建议或草稿角色，不能以“需要多步”为由自动执行。

Anthropic 的工程文章把工作流（workflow）描述为预先编排的代码路径，把 Agent 描述为模型动态选择过程和工具，并建议只在简单方案不足时增加复杂度；该文发表于 2024 年且页面已提示工具生态发生变化，因此这里只用它支持架构区分，不把它当成当前框架评测或行业结论。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

## 7.3 自动化模式由任务风险决定

建议、草稿、审批和受限自动执行是不同的产品模式，不是一条每个产品都必须走完的升级阶梯。一个产品可以自动完成低风险查找，同时把发送、删除或退款交给人；权限、资源和风险级别变化时，自动化范围也应随之变化。

| 模式 | Agent 可以做什么 | 系统如何交付结果 |
| --- | --- | --- |
| 建议 | 分析信息并提出方案，不写入外部系统 | 用户自行判断和执行 |
| 草稿 | 准备文本、参数或待处理记录，不提交 | 用户核对后在原系统提交 |
| 人工审批 | 准备一项具体动作并等待有权人员确认 | 执行器只提交被确认的动作版本 |
| 分级混合 | 自动处理已验证的低风险步骤，高影响步骤停下来等人 | 每个动作按自己的权限、验收和确认策略处理 |
| 受限自动执行 | 在明确资源、权限、预算和验收范围内执行低风险动作 | 系统检查结果并保留停止、回滚或转人工路径 |

决定一个动作属于哪种模式时，要看副作用而非模型的离线分数。查询当前订单可以是只读；生成回复草稿不会对外发送；发信、退款、改权限和生产配置变更会改变外部状态，需要更严格的控制。某个场景暂时不具备动作验收或状态对账能力，就应维持低自动化范围。

OWASP 的 Agentic Top 10 2026 将工具滥用、身份和权限滥用、人机信任利用等列为独立风险，并提出避免不必要自主性、保持运行可观察性；它是风险分类和缓解指南，不是产品认证或某个系统的风险评级。[OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/download/52117/?tmstv=1765059207)

## 7.4 工具提议和业务授权要分开

每次工具调用都应由模型之外的执行器重新核验身份和任务范围。执行器至少要知道：当前用户或服务主体、租户、目标资源、动作类型、字段与参数、资源当前版本，以及这个动作是否属于本次任务契约。用户有权访问某个系统，不代表该任务里的 Agent 可以改动系统中的任意资源。

可以先按副作用划分工具，再为每个工具定义具体权限：

| 工具效果 | 常见例子 | 执行前要核验什么 |
| --- | --- | --- |
| 只读 | 搜索政策、查订单、读取状态 | 主体、租户、数据范围和资源 ACL |
| 可撤销准备 | 建立草稿、写入临时工作区 | 资源归属、写入范围、过期时间和撤销方式 |
| 业务变更 | 更新工单、提交审批 | 当前版本、允许字段、状态转移和幂等语义 |
| 高影响副作用 | 对外发送、付款、删除、改权限、生产变更 | 明确授权、动作参数、确认或审批、执行回执和独立验收 |

结构化参数（schema）只证明输入符合某种格式，不证明目标客户、订单或租户归属正确。路径、金额、收件人、SQL、文件名和权限集合都要在工具层校验；提示词里的“不要越权”不能替代执行前的授权检查。OWASP《Securing Agentic Applications V2》把上下文准入检查与副作用执行前的动作检查分开，并要求模型输出经过确定性授权和范围校验后才能影响外部系统。[指南第 3.1.7 节](https://genai.owasp.org/download/58383/?tmstv=1794198262)

网页、检索结果、工具响应和外部 Agent 消息也可能带有恶意指令。它们可以提供任务数据，不能自行获得系统指令或执行权限；工具返回后，仍应按数据来源、Schema 和业务规则检查。第六章解释了 RAG 证据链的版本与权限，本章重点看这些信息如何进入有副作用的动作。

## 7.5 确认按钮必须绑定到实际动作

“允许 Agent 操作”没有说明用户批准了什么。需要确认时，界面应展示具体对象、租户、收件人或金额、完整参数或内容摘要、动作依据、不可逆影响和确认有效期。执行器要记录确认人、动作版本和结果，并在提交前重新检查授权及外部状态。对象或参数已经变化时，旧确认不能继续使用。

确认也不能变成让用户替 Agent 兜底的橡皮图章。用户应有足够信息判断动作，能修改、拒绝、取消或转交；高频审批还要限制数量并观察用户是否有时间复核。OWASP 2026 Agentic Top 10 将用户对流畅回答的过度信任和未核验的批准列为人机信任风险。因此审批记录不能单独证明动作正确，也不能代替独立验收。

具体 SDK 可以实现暂停和恢复。例如 OpenAI Agents SDK 文档说明工具可配置人工审批，并通过可序列化的运行状态恢复；同一文档提醒序列化状态包含工具参数和审批信息，必须由可信服务端保存并在提交决策时重新鉴别、授权，审批本身也不保证外部副作用只发生一次。[人工审批与恢复说明](https://openai.github.io/openai-agents-python/human_in_the_loop/)。这只是一个供应商 SDK 的接口行为，实际产品仍需检查自己的身份、存储和目标系统。

## 7.6 出错时先判断外部状态

失败处理先看动作有没有发生，再决定能否重试。读请求、参数错误、权限拒绝和外部写入超时需要不同处理：

| 观察到的情况 | 合理的下一步 | 不应默认做什么 |
| --- | --- | --- |
| 暂时网络错误或限流 | 检查重试预算和动作幂等性，再退避重试 | 无上限循环 |
| 参数错误或权限拒绝 | 修正输入、请求补充或转人工 | 重放相同请求 |
| 缺少对象、日期等信息，或用户目标互相冲突 | 暂停并澄清；把人工答复追加到任务状态 | 由模型自行猜一个优先级 |
| 资源版本或业务状态变化 | 重新读取并按当前状态重算 | 继续提交过期动作 |
| 写入调用超时，结果未知 | 查目标系统回执或幂等键；无法确定时暂停并标记 `unknown` | 盲目再发一遍 |
| 工具返回成功但业务验收失败 | 保存失败证据，修复、补偿或交人工 | 因 HTTP 成功就宣布任务完成 |

幂等键用于将重试关联到同一业务意图；同一键和同一参数重复提交时，目标服务应返回同一业务结果而不重复产生副作用。前提是目标服务能原子去重，且去重记录覆盖恢复时间。补偿动作也不等于回滚：已经发出的邮件无法收回，退款可能需要反向交易。对于超时后可能已执行的外部操作，先做权威对账；还不能判断时保留未知状态，等待人工处理。OpenAI Agents SDK 的恢复文档也明确指出审批恢复不能独自保证外部动作恰好执行一次，并建议用目标系统幂等键或先对账再恢复。[恢复与幂等边界](https://openai.github.io/openai-agents-python/human_in_the_loop/)

## 7.7 运行状态要存在模型上下文之外

上下文可以被截断、压缩或重建，不应充当唯一任务数据库。系统要持久化任务目标、权限范围、资源版本、已执行动作及回执、失败原因、待审批动作、预算余额和验收状态。每次状态转换都要有事件和责任主体。

客服工单可以沿着“收到请求 → 核对身份与资源 → 查询政策和订单 → 形成草稿 → 等待确认 → 执行发送 → 回读回执 → 验收完成”变化。系统还需要 `paused`、`failed` 和 `external_state_unknown` 等终态或暂停态。只有业务系统回执与验收条件一致，任务才能标为完成；模型不能通过生成一句“已处理”改变任务状态。

长任务通过检查点（checkpoint）保存恢复所需的最小信息。恢复时重新校验用户权限、策略版本、资源状态、运行配置和未决副作用；并发任务要检查资源版本或锁，避免两个 Agent 覆盖同一变更。若运行状态通过客户端传回，必须绑定用户、任务与完整性校验，不能信任客户端提交的工具参数或审批记录。

## 7.8 轨迹让用户和运营人员看见发生了什么

执行轨迹（trace）是可关联任务 ID、发起主体、Agent/模型和工具版本、权限判定、参数摘要、确认事件、执行结果、观察与状态转移、预算消耗、验收结论和最终业务回执的事件记录。通过稳定的任务 ID 关联模型、工具和业务系统事件，才能判断一次失败发生在目标理解、权限、执行、恢复还是验收环节。

不需要把模型隐藏推理全文当作审计凭据。产品需要展示的是可验证的状态、动作、依据和结果，例如“已读取 2 条订单记录，政策版本 v12；回复草稿等待确认”，而不是未经核验的内心独白。原始提示、工具参数和返回值可能含客户数据或凭据，日志应按目的最小化、脱敏、设访问权限和保留期。第九章会展开数据治理与保留边界。

用户界面应允许暂停、取消、补充信息和转人工，并明确报告已经发生的副作用。取消后停止后续步骤不等于撤销已发送邮件或已完成扣款；页面要把二者分开说明。长任务还应显示当前状态、最近更新时间、待用户操作和剩余预算，外部结果未确认时显示“结果待核实”。OpenAI Agents SDK 是可参考的一个实现例子：其常规服务端路径能输出结构化的模型、工具、handoff 和 guardrail trace；这不代表其他 SDK 默认具备相同审计能力。[SDK tracing 文档](https://developers.openai.com/api/docs/guides/agents/integrations-observability)

## 7.9 按验收成功的任务核算成本

一次 Agent 任务可能调用模型多次、执行多个工具、发生重试、等待人工并保存长期轨迹。只看单次模型 token 价格会漏掉执行成本。周期内合格任务的平均成本可写成：

```math
C_{\mathrm{accepted}} = \frac{C_{\mathrm{period}}}{N_{\mathrm{accepted}}}
\quad \text{当 } N_{\mathrm{accepted}} > 0
```

`C_{\mathrm{period}}` 包含周期内模型、检索、工具、重试、人审、存储和可归属运维成本；`N_{\mathrm{accepted}}` 是通过独立业务验收的任务数。没有成功任务时，单位成功成本是 `unknown`，不能记成零。若同时比较自动化模式，还要统一任务范围、人工基线和质量标准。

运行时预算至少要约束总步骤、工具调用、并发、模型 token、时间、外部费用和重试。接近上限时可以停下、降到只读、转人工或请求用户选择。服务延迟要单独定义：机器处理时间与等待人工确认的墙钟时间分别报告；机器请求的 95 分位延迟（p95）与人工等待不能汇总成一个数字，否则会掩盖用户实际等待原因。

## 7.10 用不同分母解释评估结果

Agent 评估同时看最终任务和中间动作，但指标不能互相替代。任务成功率说明业务目标是否验收；工具调用成功率说明执行是否符合接口契约；授权测试说明控制层是否能拦截规定的负例。具体口径应随任务定义，并保存样本、模型/工具版本、评估规则和证据。

| 评估对象 | 一种可复核的口径 | 不能据此推出什么 |
| --- | --- | --- |
| 任务验收 | 达到预先定义验收标准的任务数 / 有完整评估结果的任务数 | 不能只凭最终回答自然语言判断 |
| 工具执行 | 符合参数契约、权限、执行回执和后置检查的调用数 / 已执行调用数 | 工具成功不等于任务成功 |
| 人工确认 | 带有新鲜且匹配的动作确认的高影响执行数 / 高影响执行数；未确认提议是否被阻断另测 | 没有高风险样本时不能记为 100% |
| 授权 | 负向测试中被正确阻断的越权提议数 / 预设越权提议数；线上另记越权副作用事件 | 测试通过或“未观察到事件”不证明永远不会越权 |
| 失败恢复 | 在规定窗口内恢复到可验收状态的失败数 / 需要恢复的失败数 | 状态未知不算恢复成功 |
| 观察使用 | 后续动作符合所需工具观察的决策数 / 必须依赖观察的决策数；用状态断言或人工复核判断 | 不能只凭 Agent 自己声称“已考虑结果” |
| 状态更新 | 成功持久化的必要状态变更数 / 任务要求的状态变更数 | 不能用最终对话文本代替外部状态 |
| 轨迹完整 | 包含该任务所需字段与结果的 trace 数 / 应有 trace 的任务数 | 缺失日志不能解释为没有失败 |
| 预算与延迟 | 超限任务 / 有预算任务；按统一服务口径计算的 P95 | 不说明业务质量是否合格 |
| 成功任务成本 | 周期全成本 / 验收成功任务数 | 不可直接与任务范围不同的方案横比 |

每项结果同时记录样本数量和 `unknown` 条件；`unknown` 表示证据或分母不足，不等同于零失败。没有合格样本、分母为零、追踪缺失或外部状态不清时都不能写成通过。权限错误、高影响动作绕过确认、未经核验就报告完成等既定阻断项也不能由高任务成功率抵消。评估结论应带可回放的轨迹和原始证据，不用自定权重拼成一个通用 Agent 分数。

任务覆盖还要列出正常输入、边界输入、权限负例、工具错误、注入内容、并发和恢复路径，以及各项使用的人工标注或系统验收器。上线后再把采用率、人工接管、投诉和业务结果与客观验收并列；用户满意不证明权限正确，接管率低也不代表任务质量高。

## 7.11 贯穿案例：退款工单 Agent 能否扩大范围

假设一个客服 Agent 只能查看当前用户授权的工单和订单，读取有效的退款政策，生成回复草稿。它不能自行批准退款；对外发送必须经人工核对，退款操作仍走既有审批流程。所有数字和本地目标都是教学假设。

单条任务“查订单是否符合政策并准备回复”按以下状态推进：

| 阶段 | 系统记录与检查 | 决策 |
| --- | --- | --- |
| 任务接收 | 任务 ID、当前用户、租户、工单 ID、只读政策和订单范围、禁止退款 | 契约不完整则先问用户，不启动工具 |
| 读取信息 | 订单状态、政策版本、访问决策、工具回执 | 权限不足或版本冲突时暂停 |
| 形成草稿 | 回复内容、引用的政策段、支持该结论的订单字段 | 验证器检查证据和目标工单是否匹配 |
| 等待确认 | 收件人、完整邮件内容及内容版本 | 用户拒绝则不发送，修改后重新展示并确认 |
| 执行与验收 | 重新核验授权和订单版本；用稳定动作 ID 发送；读取邮件系统回执 | 收到匹配回执后更新状态；超时则对账，状态未知时不重发 |

现在看 24 条合成评估任务。20 条通过业务验收，任务成功为 `20/24 = 83.3%`；6 条高影响动作都带有匹配确认，执行确认覆盖是 `6/6`。预设的 12 条越权负例测试全部被拦截，授权测试通过 `12/12`；另一个合成试点日志记录了 48 次策略检查，没有观察到越权副作用。最后一个数字只描述该样本，不能证明越权风险为零。

五次需要恢复的失败中，四次恢复到验收条件，`4/5 = 80%`；剩下一次写入超时，外部系统仍未确认，保持 `unknown` 并交人工核对。要求持久化的 32 个状态变化中有 31 个记录完整，`31/32 = 96.9%`；24 条任务中有 22 条轨迹字段完整，`22/24 = 91.7%`。两项缺失都限制事故复盘与放量判断。

另有 30 个决策点必须使用工具观察结果，其中 27 个后续动作与所需状态相符，观察使用率为 `27/30 = 90%`。这需要逐条检查工具回执与状态转移；不能只读取 Agent 的文字说明来计数。

24 条任务有 2 条超出预算，`2/24 = 8.3%`。另有 100 条合成服务请求记录，机器处理 p95 为 4.2 秒，低于本例预设的 5 秒目标；等待人工确认的中位时间另记为 18 分钟。周期全成本为 ¥7.20，20 条验收成功任务的单位成本为 `¥7.20/20 = ¥0.36`，高于本例预设的 ¥0.35 目标。

团队事先把 24 条任务中至少 22 条验收成功、每次高影响动作均有匹配确认、所有越权负例被阻断、任务状态完整且单位成本不高于 ¥0.35 作为当前试点的局部条件。这些条件不是行业门槛；它们只说明这一轮是否达到该团队事先约定的目标。当前结果在成功数、一个未知外部状态、状态/轨迹完整性和成本上都留有缺口，因此保持草稿模式，修复缺失记录和恢复路径，再以冻结的任务集复评。不能因为授权负例全通过、延迟合格，就扩大到自动退款或免审发送。

## 7.12 逐步放量与事故定位

关键流程通常让工作流负责身份与任务接收、状态转移、审批、提交、超时、回滚和审计；Agent 负责分类、检索、草稿和依赖外部观察的有限判断。这样的混合方式把自由度放在输入变化的节点，把确定性控制留在每次副作用的边界。

上线前，先用固定版本的任务集核对正确资源、工具选择、参数、业务验收和拒绝边界；再在隔离环境测试恶意网页或工具返回、权限负例、重复执行、超预算和取消/恢复；最后进入建议或草稿试点。只有线上任务、权限、回执、成本、等待和人工接管都有可追踪证据，才决定是否开放一种新的动作。

新增工具、改变权限、升级模型或调整状态结构都会改变运行边界，应触发相应回归。可用熔断策略在异常调用增长、任务偏离范围或系统状态不一致时撤销工具能力、暂停任务、退回只读或转人工。《Securing Agentic Applications V2》提出按信号、触发条件、响应、回滚和审计快照设计运行时熔断；这是安全工程指南，实际触发条件要用本系统的负例和演练校准。[OWASP 指南](https://genai.owasp.org/download/58383/?tmstv=1794198262)

事故定位先找轨迹中第一处与任务契约不符的变化：目标资源选错就核对任务和资源绑定；权限范围过大就查逐次授权；超时后重复写入就查幂等键与对账；高影响动作未暂停就查风险分类和确认版本；中途丢约束就查持久化状态；成本飙升就查循环、重试和工具预算；结果流畅却无法验收就查外部回执和业务验证器；事故无法复盘就查 trace 字段、版本和保留策略。先确认外部副作用是否发生，再选择回滚、补偿、人工协调或只读降级；不要先改提示词掩盖执行器的授权和状态问题。

## 7.13 本章小结

Agent 是否适合产品化，取决于它解决的任务是否需要动态选择步骤，以及系统能否限定动作、核验结果并处理失败。模式选择应跟着任务风险变化；每次动作都由模型外的执行器重新授权；人工确认绑定具体动作；状态未知时先对账；成本和评估都以可验收任务为单位。

这些边界让产品团队能根据证据扩大某些动作，同时保留另一些动作的人工控制。下一章转向多模态产品：当输入从文本扩展到图像、语音和视频时，怎样保持任务证据和用户验收同样清楚。
