# 第十二章：数据面试题

本章是第九册《大模型数据工程与数据智能》的收束章。前面 11 章已经系统讲过 web-scale 采集、清洗过滤、去重污染、data mixture、代码数学领域数据、合成与蒸馏、偏好与安全、多模态数据、data attribution、dataset governance。本章用面试题作为入口，把这些知识重新组织成可以解释、量化、验证和复盘的工程判断。

大模型数据面试和普通数据工程面试不一样。普通数据工程更关注 ETL、存储、调度、数据仓库和实时链路；大模型数据工程还要关注训练效果、模型行为、安全边界、评估污染、数据配比、合规治理和训练可复现。

面试官真正想听的不是“我会用某个工具清洗数据”，而是你是否理解：数据如何塑造模型能力，数据问题如何变成模型问题，数据工程如何和训练、评估、安全、产品形成闭环。工具名只能说明你见过某个组件，不能说明你知道输入是什么、输出如何验证、失败后会影响哪些结论。

本章高频问题包括：如何构建预训练数据？如何做去重？如何检测数据污染？如何设计 reasoning 数据？如何证明一个数据源有价值？如何在规模、质量、风险和成本冲突时做取舍？每道题都先解释问题，再给出适合在有限时间内复述的表达。

合规边界：本章只讨论合法合规的数据工程、风险治理和面试表达，不提供绕过访问控制、抓取未授权数据、复原训练数据、规避安全策略或生成有害内容的方法。

## 0. 本章范围与资料

本章参考 C4 / T5、The Pile、RefinedWeb、FineWeb、Dolma、DCLM 等公开数据集和数据配方工作，也复核了 Datasheets for Datasets、Model Cards、W3C PROV、OpenLineage、Hugging Face Dataset Cards、NIST AI RMF / Generative AI Profile 和 OWASP LLM Top 10 中与数据污染、数据治理、文档透明度相关的公开资料。

本章是第九册收束章，不重复前 11 章的全部算法推导，而是把它们连接成一条可迁移的判断链：先澄清目标，再确定数据对象和处理动作，之后用实验和指标建立证据，最后说明治理、风险和未知边界。所谓“标准回答”只是这条链路的短表达，不能替代正文中的机制和案例。

```text
面试题 -> 目标澄清 -> 数据来源 -> 处理验收条件 -> 配比实验 -> 评估证据 -> 治理边界 -> 复盘改进
```

本讲不把任何公开数据集的具体比例写成唯一标准。真实训练数据配方会随模型目标、语言覆盖、授权边界、数据质量、评估集和训练阶段变化；面试中更重要的是讲清可审计的数据工程方法，而不是背某个固定比例。

## 1. 面试总框架：大模型数据题怎么答？

遇到大模型数据题，建议用一个固定框架：目标、来源、处理、配比、评估、治理。

1. 目标：模型要解决什么问题？通用 base model、代码模型、数学模型、行业模型、多模态模型还是安全对齐模型？
2. 来源：数据从哪里来？网页、书籍、代码、数学、领域文档、合成数据、偏好数据、多模态数据。
3. 处理：如何清洗、过滤、去重、脱敏、对齐、质量评分和污染检测？
4. 配比：不同数据源如何混合？哪些上采样，哪些下采样？不同训练阶段如何变化？
5. 评估：如何判断数据策略有效？小模型 ablation、validation loss、benchmark、人工评测、安全评估、线上反馈。
6. 治理：数据版本、lineage、license、权限、删除请求、datasheet、model card。

这个框架适用于绝大多数数据面试题。

### 1.1 关键公式与指标速查

数据面试不要求你现场推复杂公式，但优秀回答应该能把“我会清洗、去重、配比、治理”落到可量化指标。下面这些公式覆盖本章大多数追问。

训练候选集可以抽象为：

```math
D=\bigcup_{m=1}^{M}D_m,\qquad x_i=(u_i,b_i,q_i,r_i,a_i,v_i)
```

其中 `D_m` 是第 `m` 个数据池，`u_i` 是来源或样本 id，`b_i` 是 token 数，`q_i` 是质量分，`r_i` 是风险分或风险标记，`a_i` 是授权和访问状态，`v_i` 是数据版本。这个抽象刻意把内容、质量、风险、授权和版本放在同一个样本记录中，因为训练候选不是“文本字段加一个分数”，而是一个带责任和来源的对象。

Token 保留率：

```math
R_{\mathrm{keep}}=\frac{\sum_i b_i g_i}{\sum_i b_i}
```

其中 `g_i=1` 表示样本通过准入条件，`g_i=0` 表示被过滤或隔离。回答清洗题时，只说删掉多少不够，还要解释保留下来的 token 是否覆盖目标语言、领域和能力。

某类风险命中率：

```math
R_{\mathrm{risk}}(k)=\frac{\sum_i b_i h_{ik}}{\sum_i b_i}
```

其中 `h_ik=1` 表示样本命中第 `k` 类风险，例如 PII、secret、license、contamination 或 safety risk。

Near dedup 常用 Jaccard 直觉：

```math
J(A,B)=\frac{|A\cap B|}{|A\cup B|}
```

其中 `A` 和 `B` 是两段文本的 shingle 集合。MinHash / LSH 的面试重点是用签名近似 Jaccard，并减少全量两两比较。

Benchmark contamination 命中率：

```math
R_{\mathrm{contam}}=\frac{N_{\mathrm{train\ eval\ overlap}}}{N_{\mathrm{query}}}
```

这里的 query 不只包括题目原文，还应包括答案、选项、解析、代码签名、测试样例和近重复变体。

Data mixture 对应的训练目标可以写成：

```math
L_{\mathrm{mix}}(\theta)=\sum_{m=1}^{M}\alpha_m\mathbb{E}_{x\sim D_m}[L_{\theta}(x)],\qquad \sum_{m=1}^{M}\alpha_m=1
```

其中 `alpha_m` 是第 `m` 个数据池的采样权重。这个公式帮助你解释：data mixture 不是拼文件，而是在改变模型实际优化的训练分布。

一种可解释的采样权重草案：

```math
p_m=\frac{b_m^{\tau}q_m(1-r_m)}{\sum_j b_j^{\tau}q_j(1-r_j)}
```

其中 `b_m` 是清洗后 token 数，`q_m` 是池级质量分，`r_m` 是风险惩罚，`tau` 控制大池和小池之间的平滑。真实系统还要叠加 license、语言覆盖、目标能力和人工审计结果。

Effective epoch：

```math
e_m=\frac{T p_m}{b_m}
```

其中 `T` 是计划训练 token 总数。如果小数据池 `e_m` 很高，要警惕记忆、过拟合和污染放大。

偏好数据标注一致率和长度偏置：

```math
A_{\mathrm{pair}}=\frac{N_{\mathrm{agree}}}{N_{\mathrm{pair}}},\qquad
B_{\mathrm{len}}=\frac{1}{N}\sum_i(\ell_i^{+}-\ell_i^{-})
```

其中 `ell_i+` 和 `ell_i-` 分别表示 chosen / rejected 的长度。长度偏置不能单独证明数据坏，但它是偏好数据审计必须检查的信号。

安全数据的漏拒率和误拒率：

```math
R_{\mathrm{leak}}=\frac{N_{\mathrm{unsafe\ accepted}}}{N_{\mathrm{high\ risk}}},\qquad
R_{\mathrm{over}}=\frac{N_{\mathrm{safe\ refused}}}{N_{\mathrm{safe\ allowed}}}
```

高质量安全模型不是拒答率最高，而是在漏拒和误拒之间保持稳定边界。

多模态对齐分的基本形式：

```math
s_{\mathrm{align}}=\frac{u_{\mathrm{image}}\cdot u_{\mathrm{text}}}{\lVert u_{\mathrm{image}}\rVert_2\lVert u_{\mathrm{text}}\rVert_2}
```

这个分数只能辅助判断图文相关性，不能替代 OCR、时序、grounded QA、隐私和版权审计。

数据源价值的面试级表达：

```math
V_s=\Delta U_s-\lambda_r R_s-\lambda_c C_s
```

其中 `Delta U_s` 是目标效用提升，`R_s` 是风险，`C_s` 是清洗、标注、存储和治理成本。数据价值不是绝对属性，而是相对于目标、阶段和约束的边际贡献。

治理状态向量：

```math
C_{\mathrm{data}}=(C_{\mathrm{license}},C_{\mathrm{pii}},C_{\mathrm{contam}},C_{\mathrm{lineage}},C_{\mathrm{delete}},C_{\mathrm{doc}})
```

每个分量表示对应证据的覆盖、正确性、时延或未解决对象，不能把它们压成一个总布尔值。比如 lineage 记录完整而删除请求尚有未解析目标时，版本可能适合内部排查，却不适合据此写出完整的发布声明。回答治理题时，应说清哪些分量已经核验、哪些仍是风险信号，以及下一步动作是什么。

最后，面试回答本身也可以量化复盘：

```math
S_{\mathrm{ans}}=w_c C+w_e E+w_m M+w_g G+w_b B-P
```

其中 `C` 是框架覆盖，`E` 是工程证据，`M` 是指标和公式，`G` 是治理边界，`B` 是 trade-off 深度，`P` 是错误表述和超时惩罚。这个分数只是自我复盘的启发式，不是面试质量的客观测量；更重要的是根据缺失项回到具体题目，补一个机制、一个反例或一个可验证的指标。准备面试时，不要只问“我记住了吗”，要问“我的回答有没有目标、证据、指标、边界和取舍”。

## 2. 高频题一：如何构建大模型预训练数据集？

### 2.0 目标、来源与处理的快速表达

我会把预训练数据建设看成一个端到端数据系统，而不是简单拼接文本。

第一步，明确模型目标和覆盖范围。比如是通用中文/英文 base model，还是偏代码、数学、多语言或行业模型。目标不同，数据来源和配比不同。

第二步，设计数据源。通用文本包括网页、书籍、百科、新闻、论坛、问答和技术文档；专项数据包括代码、数学、论文、领域文档；后续还要考虑合成数据、偏好数据和安全数据，但预训练阶段要控制比例。

第三步，建立采集合规流程。记录来源、license、时间、robots/ToS、授权状态和风险等级。不采集未授权、访问受限或高隐私风险数据。

第四步，做解析和清洗。HTML、PDF、代码、文档、多模态数据分别使用不同 parser；去乱码、模板、广告、低质量文本、PII 和高风险内容。

第五步，做语言识别、领域分类和质量评分。不要对所有数据用同一阈值，代码、数学、多语言和专业领域要单独规则。

第六步，做去重和污染检测。包括 exact dedup、near dedup、段落级重复、代码 fork、benchmark contamination。

第七步，设计 data mixture。按目标能力设置采样权重，控制通用文本、代码、数学、多语言、领域和合成数据比例。

第八步，做评估闭环。用小模型训练、数据 ablation、validation loss、下游 benchmark、安全评估和人工样例验证数据策略。

第九步，做版本治理。保存 manifest、lineage、schema、过滤规则、数据版本、删除请求和审计记录。

### 2.1 把“构建数据集”拆成可验证的对象

这道题的难点不在于列出九个步骤，而在于说明每一步产生了什么对象。采集阶段产生原始对象和来源登记；解析阶段产生结构化文档和解析事件；清洗阶段产生新的样本版本与过滤原因；去重阶段产生簇关系和保留/隔离决定；配比阶段产生数据池和采样配置；训练阶段消费的是某个不可变 manifest，而不是一个会变化的目录。这样回答，面试官可以继续追问每个对象如何存储、如何回放以及谁负责确认。

可以用一个小规模例子说明数量关系。假设原始抓取得到 100 TB，解析后只有 70 TB 是可读正文，PII、许可未确认和重复处理后剩下 40 TB，按 tokenizer 估算为 8T tokens。此时不能把 100 TB 直接称作“训练数据规模”，应该分别报告原始量、解析保留量、训练候选量和实际采样量。若最终训练只消费其中 2T tokens，还要说明 2T 是一次遍历、重采样后的有效 token，还是包含重复曝光的 token。

对于专家追问，关键是把数据流水线与模型目标连接起来。通用 base model 需要覆盖语言、领域和时间分布；代码模型需要可执行测试和 license；推理模型需要答案、过程和 verifier；行业模型需要来源权威性、时效和引用。相同的清洗规则可能对不同目标产生相反结果，例如删除所有短文本会减少噪声，却可能误删 API 说明、数学定义和对话边界样本。

### 2.2 证据如何闭环

一段成熟的回答应至少给出三类证据。第一类是数据证据，如保留率、语言/领域分布、重复率、风险命中和 lineage 覆盖；第二类是训练证据，如小模型消融、validation loss、训练稳定性和 token 消费；第三类是能力证据，如下游任务、人工样例、安全评估和污染审计。单看其中一类容易误判：保留率高不说明质量高，loss 下降不说明 benchmark 没污染，benchmark 提升也不说明真实任务受益。

如果结果变差，排查顺序应从数据版本、mixture 和评测集引用开始，再看处理器版本、分桶统计和训练运行，最后才把变化归因于模型结构或优化器。这样的因果顺序比“先换模型再看效果”更能体现数据工程的系统理解。

### 2.3 面试中的关键取舍

不要只说“爬网页 + 清洗 + 去重”。要强调数据目标、合规、配比、污染检测和版本可复现。

## 3. 高频题二：如何做 web-scale 数据采集？

### 3.0 采集链路的快速表达

Web-scale 采集要先确定合法来源和目标语料范围。采集不是越多越好，而是要保证来源合规、可追溯、可清洗和可评估。

我会先做 source planning，把来源分为通用网页、百科、新闻、技术文档、论坛、问答、论文、代码和多语言来源，并记录来源元数据。

然后建立采集 pipeline：source registry、采集任务、原始数据存储、解析、正文抽取、语言识别、质量过滤、去重、版本化。

合规上，要记录来源 URL、采集时间、license、使用限制和删除机制；对于用户数据、登录后内容、访问受限内容和隐私风险高的数据，不能随意进入训练集。

最后用统计和抽样审计监控来源质量，包括有效文本比例、语言分布、重复率、PII 命中率、低质量比例和下游训练收益。

### 3.1 采集系统不只是爬虫

Web-scale 采集至少有四个状态层：source registry 记录来源身份和使用边界，scheduler 决定抓取顺序和预算，raw layer 保存可回放的原始对象，processing layer 把原始对象变成训练候选。每一层都要有失败状态和重试策略。网络超时、robots/ToS 变化、内容类型异常、重复抓取和解析器升级不能被统一记成“抓取失败”，否则后续无法判断是来源不可达、内容不合格还是处理器有问题。

原始层最好保存足够的响应元数据和内容 hash，使同一对象能够被重新解析；训练层则不应直接把未经版本化的原始目录交给 sampler。解析器升级时可以在相同 raw snapshot 上做反事实比较，判断正文抽取、语言识别和 token 数的变化来自 parser 还是来源本身。

### 3.2 规模、质量与合规的冲突

一个规模很大的来源不一定值得优先接入。它可能带来更多覆盖，也可能带来更高的重复、PII、版权争议和解析成本。回答“规模大但质量一般怎么办”时，可以进一步说明分层处理：先将来源隔离成独立池，记录风险和许可证状态；再做抽样、质量评分和下游小模型实验；最后决定保留高质量子集、低权重采样、只用于检索，或完全不进入训练。

还要说明停止条件。若删除请求无法定位、授权范围不清或高风险内容无法可靠隔离，系统应暂停该来源的训练消费，而不是用“规模很大”抵消责任缺口。这样既体现工程判断，也避免把合法性问题误答成性能优化问题。

### 3.3 常见追问：规模大但质量一般

面试官可能问：“如果某个来源规模很大但质量一般，怎么办？”

回答：先单独建池，不直接混入主训练集；做质量评分、去重、抽样审计和小模型 ablation；如果有价值则低权重采样或只保留高质量子集。

## 4. 高频题三：如何做数据清洗和质量评分？

### 4.0 清洗分层的快速表达

清洗过滤分层做。

第一层是基础有效性过滤：空文本、乱码、异常字符、极端长度、重复行、编码错误。

第二层是正文抽取和模板去除：去导航栏、页脚、广告、cookie 提示、推荐链接和 boilerplate。

第三层是语言和领域识别：按语言、领域、来源类型分桶，不同桶使用不同规则。

第四层是规则质量过滤：长度、符号比例、链接比例、重复 n-gram、低信息密度等。

第五层是模型质量评分：训练质量分类器或用 LLM judge 辅助，对可读性、信息密度、结构、来源可信度和安全风险打分。

第六层是安全和隐私过滤：PII、毒性、高风险内容、版权和敏感数据处理。

最后要做人工抽样审计和小模型训练验证，评估误删、漏删和下游收益。

### 4.1 阈值不是质量的同义词

规则和质量模型输出的是信号，不是事实本身。比如链接比例高可能意味着模板噪声，也可能是高质量参考文档；困惑度高可能是乱码，也可能是数学公式、代码或低资源语言。阈值需要在语言、领域、模态和来源桶内校准，并通过人工标注估计误删与漏删。一个全局阈值往往会优先保留英语长文和常见网页，误伤短文本、代码、数学和低资源语言。

可以把一次质量筛选写成两个实验。第一实验比较过滤前后的数据统计，检查语言/领域覆盖是否异常坍缩；第二实验固定训练配置，只替换过滤版本，观察目标能力、通用能力和安全切片。若过滤率下降但能力也下降，说明“删得少”不等于“质量变好”；若 validation loss 变好而专项能力变差，可能是数据分布被过度收窄。

### 4.2 回答中的失败归因

当面试官给出“过滤后模型变差”的现象时，不要直接说阈值太高。至少要排查四种可能：关键领域被误删，重复或污染比例改变，tokenizer/packing 造成有效 token 变化，或者评估集与训练数据的关系发生了改变。把每种假设对应到一个统计或消融实验，回答就从清单变成了诊断。

### 4.3 面试中的关键取舍

强调清洗不是越狠越好。过度过滤会损失口语、多语言、低资源语言、专业符号、代码和数学数据。

## 5. 高频题四：如何做去重？

### 5.0 去重层次的快速表达

去重要按粒度分层。

第一，文档级 exact dedup。对规范化文本做 hash，相同 hash 只保留一份。

第二，段落级重复统计。识别网页模板、免责声明、页脚、广告段落和高频重复片段。

第三，near dedup。用 shingling、MinHash、SimHash、LSH 或 embedding 检索识别转载、改标题、加页脚、轻微改写的重复。

第四，代码专项去重。处理 fork、vendor、自动生成文件、函数级重复、题库答案和 benchmark 泄漏。

第五，去重后重新统计 data mixture，因为去重会改变来源、语言和领域分布。

### 5.1 去重的目标函数

去重不是追求一个尽可能低的重复率，而是在减少无效重复、保留自然多样性和控制计算成本之间取平衡。文档级 exact dedup 适合消除完全相同的对象；段落级统计适合清理网页模板；near dedup 需要把相似阈值、候选生成、聚类代表选择和误合并代价一起说明。代码 fork、版本更新和同一 API 的不同实现不能简单当作重复删除。

一个可手算的例子是：两段文本各有 100 个 shingle，共享 80 个，Jaccard 为 `80 / (100 + 100 - 80) = 0.667`。这个分数只能说明候选相似，不自动说明应该删除；还要看它们是否来自同一来源、是否是同一版本、是否包含不同测试、语言或时间信息。若把相似度当作删除命令，系统会把有价值的改进版本合并掉。

### 5.2 去重后的连锁影响

去重改变的不只是样本数。代表样本的选择会改变来源分布、语言分布、质量分布和 license 统计，进而改变 mixture 和 effective epoch。评估集附近的重复还会改变污染判断。因此，去重作业应输出被合并的 cluster、保留代表、被隔离对象、删除原因和新版本统计，并用小模型或分层评估检查“减少重复”是否真的改善了目标，而不是只改善了一个仪表盘数字。

### 5.3 常见追问：去重是不是越彻底越好

面试官问：“去重是不是越彻底越好？”

回答：不是。目标是控制不合理重复，而不是删除所有相似内容。常见概念、API 用法、数学标准题型和用户意图多样表达都需要一定 exposure。过度去重会损害泛化和常见模式学习。

## 6. 高频题五：如何检测 benchmark contamination？

### 6.0 污染判断的快速表达

污染检测要区分训练集内部重复和 train-eval overlap。benchmark contamination 重点是训练集与评测集重叠。

我会把评测集题目、答案、选项、解析、代码签名、测试样例都作为 query，而不只查题目原文。

检测方法包括 exact match、n-gram overlap、MinHash/LSH、embedding 检索、代码函数签名匹配、答案泄漏检测和人工审计。

对于高相似候选，要判断污染程度：只有题目、题目加答案、完整解析、改写版本、同源题库变体，风险等级不同。

处理方式包括从训练集中移除、隔离、降低权重、重新划分评测集或在评测报告中标注风险。

### 6.1 污染证据的强弱

污染判断可以按证据强弱分层。题目和答案完全匹配通常是强信号；题目与解析的近重复是中强信号；只共享通用短语或题型结构则可能只是自然相似。代码任务还要检查函数签名、测试样例、注释和题解，不应只对源码做字符串搜索。高相似候选需要保留命中的具体片段、版本、来源和人工复核状态，才能在评估报告中说明残余不确定性。

### 6.2 污染后的处理选择

如果评测集已经进入训练，简单删除当前目录并不能恢复评估可信度。应先冻结受影响的数据和训练运行，判断命中发生在哪个版本、哪个阶段和哪个派生对象，再决定移除、隔离、降低权重、替换私有 holdout 或重新解释结果。发布报告至少要说明检测方法、查询组成、匹配阈值、人工抽检和未解决候选。这样回答的重点就从“我会用 MinHash”转向“我知道证据如何影响结论”。

### 6.3 面试中的关键取舍

强调污染检测是评估可信度问题，不只是数据清洗问题。公开 benchmark 越流行，污染风险越高。

## 7. 高频题六：如何设计 data mixture？

### 7.0 配比问题的快速表达

Data mixture 是训练目标的一部分。模型最终优化的是 mixture 分布上的 loss，所以配比会影响能力、风格和安全表现。

我会先定义模型目标，然后把数据按来源、语言、领域、能力、质量和风险打标签。通用文本提供世界知识和语言能力；代码增强结构化和程序能力；数学增强推理；多语言增强语言覆盖；领域数据增强行业能力；合成数据补长尾和格式。

初始配比可以参考经验，但必须通过小规模 ablation 验证。实验时要看多维评估：通用能力、代码、数学、多语言、安全、事实性、风格和人工样例。

配比不是固定不变的。预训练、继续预训练、SFT、DPO、安全训练的 mixture 应该不同。

### 7.1 配比是预算分配问题

假设训练总预算为 1T tokens，代码池只有 20B tokens，却被设置为 10% 采样权重，那么它的有效 epoch 约为 `1T * 0.1 / 20B = 5`。这可能提升代码能力，也可能让模型反复看到相同仓库、题库和风格，增加记忆、污染和 license 风险。回答配比题时，要同时说采样权重、数据池规模、有效 epoch 和验证结果，而不是只报“代码占 10%”。

配比实验还要固定比较条件。至少记录总 token、训练步数、batch、学习率、tokenizer、数据版本和评估集版本；否则一个配比看起来更好，可能只是消费了更多有效 token 或使用了不同的重复程度。对多个数据池，可以先做粗粒度 ablation，再对高价值区间做局部搜索，最后观察混合后的能力覆盖和风险变化。

### 7.2 配比失败时如何解释

如果代码能力提升但通用语言下降，可能是代码 token 占比过高，也可能是评估切片或 tokenizer 改变；如果数学提升但安全误拒增加，可能是 reasoning/拒答数据的风格迁移，也可能是评估样本覆盖不足。成熟回答应先做分桶和反事实实验，再选择下调权重、补自然数据、分阶段训练或把一部分知识交给 RAG/工具。单一 benchmark 的变化不足以决定配方。

### 7.3 常见追问：代码比例越高越好吗

面试官问：“代码数据比例越高越好吗？”

回答：不一定。代码比例高通常提升代码和结构化能力，但会占用 token budget，可能影响自然语言、多语言和对话风格，还会增加 license、secrets、重复和题库污染风险。

## 8. 高频题七：如何建设代码数据？

### 8.0 代码数据的快速表达

代码数据不能只收 `.py`、`.java` 源文件，还应包括 README、文档、issue、PR、commit message、测试、API reference 和编程问答。

清洗上要做语言识别、语法解析、license 检查、secrets 过滤、fork 去重、vendor 处理、自动生成文件过滤、benchmark contamination 检测。

结构化上可以按仓库、文件、函数、类、AST、测试粒度组织样本。训练样本可以构造 docstring-code、test-code、bug-fix、code-explanation、API usage。

评估上不能只看文本相似度，要看功能正确性、编译运行、单测通过率、安全和依赖版本。

### 8.1 代码样本的最小契约

一个可训练的代码样本至少要能关联仓库、文件、语言、license、提交或时间版本、函数/类范围、依赖和测试状态。`docstring-code` 适合学习局部映射，`bug-fix` 需要区分修改前后和测试结果，`test-code` 需要知道测试是否真正覆盖目标行为。只保存一段代码字符串，会丢失上下文和运行条件，模型学到的可能是表面格式而不是可执行约束。

### 8.2 代码数据的评估闭环

文本相似度只能检查表达，不能证明功能。编译通过、单元测试通过、隐藏测试通过、安全扫描通过和依赖可安装分别回答不同问题；一个样本可能能运行但有危险副作用，也可能测试通过但只覆盖简单路径。回答时可以把 repo/file/function/test 四个粒度对应到四类评估，并说明沙箱、超时、网络权限和依赖缓存，避免把执行评估说成无条件运行任意代码。

代码数据还要注意时间泄漏。旧版本 API、已废弃依赖和未来测试样例可能让离线分数虚高。source commit、发布时间和评测 cutoff 应进入版本记录，评估结果才有时间语义。

### 8.3 面试中的关键取舍

强调单测价值：测试提供可执行约束，能训练和评估模型是否真正写出能运行的代码。

## 9. 高频题八：如何设计数学和 reasoning 数据？

### 9.0 数学与 reasoning 的快速表达

数学数据要按题目、答案、步骤、难度、领域和验证方式组织。来源包括教材、题库、竞赛题、课程、论坛、合成题、人工 step-by-step 解答和 verifier 数据。

清洗重点是题解对齐、公式解析、答案校验、步骤质量、重复题检测和 benchmark 污染。

Reasoning 数据不能只要最终答案。高质量数据应包含过程、约束、检查和错误候选。对于代码和数学，可以用测试、计算器、CAS 或 verifier 辅助验证。

配比上要谨慎，过多低质量 reasoning 数据会让模型学会伪推理和模板化解释。

### 9.1 最终答案正确不等于过程可靠

数学题至少有三个可分开的对象：题目是否清楚，过程是否遵守约束，最终答案是否正确。一个过程写得很长但中间算错，不能因为结论碰巧正确就作为高质量监督；一个只给答案的样本可以用于结果学习，却不能证明模型学会了可检查的推理。代码的测试、数学的符号计算或 verifier 可以提供外部约束，但 verifier 覆盖不足时仍可能放过投机解。

难度和验证方式也要进入数据分桶。简单题重复曝光会让模型看起来进步很快，却不代表复杂题推理能力提升；只保留容易自动验证的题，会让数据分布偏向可判定任务。较好的实验同时报告答案准确率、过程错误率、verifier 通过率、难度切片和未见题型表现。

### 9.2 reasoning 数据的安全边界

推理轨迹可能包含敏感信息、错误的危险建议或不应公开的内部过程。数据工程上要记录来源、权限和脱敏状态，不能因为“这是 reasoning 数据”就降低隐私和安全要求。回答时应把过程监督、结果验证和发布内容分开讨论，避免把是否公开完整推理轨迹混同于是否使用过程信号训练。

### 9.3 常见追问：CoT 数据越多越好吗

面试官问：“CoT 数据越多越好吗？”

回答：不是。CoT 质量比数量重要。错误过程、跳步过程和模板化过程会伤害模型。要用答案校验、过程审计、难度分桶和下游评估控制质量。

## 10. 高频题九：如何建设 synthetic data？

### 10.0 合成数据的快速表达

Synthetic data 要先定义目标能力，而不是为了生成而生成。常见目标包括指令跟随、数学、代码、工具调用、多语言、安全和领域问答。

Pipeline 包括：种子设计、生成策略、teacher 选择、多样性控制、格式检查、去重、质量评分、正确性验证、安全过滤、配比实验和版本记录。

不同任务验证方式不同：数学可校验答案，代码可跑测试，事实问答要检索证据，领域问答要专家审计，安全数据要检查边界。

合成数据风险包括 teacher 偏差、错误放大、同质化、数据退化、污染和过拟合。不能无追踪地大规模混入。

### 10.1 合成数据的血缘与验证

合成数据最重要的字段不是“这是合成的”这一标签，而是生成器或 teacher 版本、seed/prompt、采样参数、生成时间、输入种子集合、验证器版本和人工复核状态。没有这些字段，错误样本无法定位来源，多轮生成还会把同一个偏差复制到新的数据池。

验证要与目标能力匹配。数学可以做答案或符号校验，代码可以在受限沙箱运行测试，事实问答要保留检索证据，工具调用要检查 schema 和副作用，安全样本要看允许/拒绝/转向边界。通过一个通用 LLM judge 不能替代这些任务专属验证，尤其不能把 judge 自己的偏好当成事实正确性。

### 10.2 synthetic 与 distillation 的不同风险

synthetic data 关注生成来源和数据分布，distillation data 还要关注 teacher 到 student 的能力映射。teacher 输出的错误、风格和盲点可能被学生吸收；teacher 生成大量相似答案会降低多样性；teacher 访问了评测题或私有资料还会造成污染。回答中把这三类风险分开，才能说明为什么要保留自然数据锚点和版本化 teacher。

### 10.3 面试中的关键取舍

说清 synthetic data 和 distillation data 区别：synthetic 强调生成来源，distillation 强调 teacher-student 能力迁移。

## 11. 高频题十：如何建设 preference data？

### 11.0 偏好数据的快速表达

Preference data 常见形式是 prompt、chosen、rejected，也可以是多个回答排序和标注理由。

构造方式包括同模型多采样、不同模型对比、人工写 chosen、模型生成 rejected、LLM judge 辅助和专家标注。

标注规范要明确 helpful、honest、harmless 的优先级，以及事实性、完整性、简洁性、语气、专业边界和安全性。

数据质量要检查标注一致性、长度偏置、拒答偏置、迎合偏置、rejected 是否太弱、多语言一致性和专业标注质量。

Preference data 可用于 reward model、RLHF、DPO 等方法。算法不同，但都依赖偏好数据质量。

### 11.1 偏好对的比较对象

一个偏好对不是“长答案胜短答案”的简单排序。标注者要知道任务目标、允许的事实来源、专业边界和安全规则；chosen 与 rejected 应该在难度、长度和信息量上尽量可比较，否则模型可能只学会更长、更自信或更模板化的风格。对于安全任务，优选答案还可能是安全转向，而不是一律拒绝。

数据审计可以做长度匹配、顺序交换、标注者一致性、领域分层和 hard negative 检查。若 rejected 太弱，训练信号容易变成“不要犯明显错误”；若 chosen 含有事实错误，DPO 或 reward model 会稳定地放大错误偏好。算法降低了在线 RL 的复杂度，却没有消除偏好定义和采样偏差。

### 11.2 从偏好数据到训练结论

回答 DPO 题时，要说明 prompt、chosen、rejected 的格式、截断和 mask；回答 RLHF 题时，还要说明 reward model、reference、KL 或其他稳定机制；回答安全偏好题时，要说明帮助性、安全性、诚实性冲突如何标注。最后用独立的人工、事实和安全评估验证偏好数据是否带来目标改进，而不是只看训练 loss。

### 11.3 常见追问：DPO 数据如何构造

面试官问：“DPO 数据随便构造 chosen/rejected 可以吗？”

回答：不可以。噪声大、rejected 太弱或标注标准不一致，会让模型学到错误偏好。DPO 简化优化，不降低对数据质量的要求。

## 12. 高频题十一：如何建设安全数据？

### 12.0 安全数据的快速表达

安全数据不只是拒答数据。它包括风险分类、拒答、边界允许、误拒修复、漏拒修复、安全替代建议、红队回归、多语言安全和专业高风险场景。

我会按风险分层：明确安全、敏感但可答、高风险、边界模糊、紧急风险、专业高风险。

拒答数据要训练模型不提供危险细节，同时提供安全替代方向。边界允许数据要训练模型在教育、防御、科普、治理场景中安全帮助，避免看到关键词就拒绝。

评估上同时看误拒和漏拒。好的安全模型不是拒答最多，而是边界最稳定。

### 12.1 安全数据的三种动作

安全样本至少应区分允许回答、拒绝和安全转向三种动作。允许回答训练模型在正常、教育、防御和治理语境下提供有用帮助；拒绝回答处理确实不应提供的内容；安全转向则在拒绝危险细节的同时给出风险说明、求助渠道、预防或合规方向。只有拒答样本，模型容易把关键词当作风险代理，形成误拒。

安全数据还要按风险严重度、用户意图、工具权限、语言和专业领域切片。一个在普通聊天中安全的回答，在拥有写入工具或医疗决策上下文时可能不安全。数据记录应保存上下文和允许动作，不要只保存孤立 prompt；评估应分别报告 unsafe compliance、over-refusal、safe alternative 和工具越权。

### 12.2 红队数据如何进入正常工程

红队样本不是一次性攻击清单，而是失败模式、环境条件、预期动作、实际动作和回归结果的记录。生成或收集时应遵守授权、沙箱和最小暴露原则；进入训练前要去除不必要的可操作细节，保留足够的模式和防御信号。每次修复后用未见变体和正常任务做双向评估，避免安全提升只是把所有请求都拒绝。

### 12.3 合规边界

回答红队数据时，强调用于发现失败模式、防御训练和回归测试，不传播可操作风险细节。

## 13. 高频题十二：如何建设多模态数据？

### 13.0 多模态数据的快速表达

多模态数据工程的核心是对齐，而不是拼接。

图文数据要处理 image-caption、alt text、周围文本、OCR、图文相似度、图片质量、版权和隐私。

语音数据要处理音频质量、VAD、speaker diarization、ASR 转录、forced alignment、采样率、口音、噪声和声纹隐私。

视频数据要处理切片、关键帧、字幕、音频、OCR、镜头变化、事件对齐和时间戳。

多模态指令数据要保证回答 grounded in modality，不能只凭语言先验猜测。

### 13.1 对齐要落到时间、空间和来源

图文对齐不只是计算一对 embedding 的相似度。图表、文档截图、商品图和自然图像需要不同的质量对象：图表要保留坐标、图例和数值关系，文档要保留版面与 OCR 坐标，视频要把字幕、关键帧和事件绑定到时间区间，语音要把转录片段和说话人、时间戳关联起来。任何一个对齐关系都应能回到原始媒体和处理版本。

### 13.2 多模态失败如何归因

模型答错时，要先区分媒体质量、跨模态对齐、视觉/语音编码器、文本先验和评估协议。图文相似度高但 OCR 错误，可能让模型学会错误文字；视频帧采样太稀，可能漏掉关键动作；ASR 转录正确但 speaker diarization 错，可能把发言归给错误的人。回答中给出模态专属评估和人工抽样，比只说“用 CLIP 过滤”更完整。

### 13.3 常见追问：图文相似度高就代表好吗

面试官问：“图文相似度高就说明数据好吗？”

回答：不一定。相似度只是信号。新闻图、商品图、图表、文档截图和 OCR 场景都需要结合结构和人工审计。

## 14. 高频题十三：如何评估数据价值？

### 14.0 数据价值的快速表达

数据价值不是固定属性，而是相对于目标模型、训练阶段、已有数据分布和评估指标的边际贡献。

我会从源级、簇级和样本级做估值。预训练更适合源级和簇级；SFT、偏好、安全数据可以做样本级分析。

方法包括数据消融、上采样/下采样实验、小模型 proxy、validation loss、embedding 相似度、gradient similarity、influence 思路、Data Shapley 近似和人工审计。

最终要输出多维价值：目标能力收益、通用能力副作用、安全风险、隐私风险、版权成本、清洗成本和治理成本。

### 14.1 价值是反事实问题

“这个数据源有价值吗”必须隐含一个比较对象：不加入它、减少它、换成另一个来源，模型会怎样。源级消融适合回答大范围方向，簇级分析适合定位重复或同质数据，样本级方法适合偏好和安全数据，但它们都受训练随机性、评估噪声和目标选择影响。相似度或 influence 分数只能生成候选，不能单独证明因果贡献。

### 14.2 一个可解释的价值报告

价值报告可以同时给出目标能力变化、通用能力变化、风险变化和单位成本。例如某来源使数学准确率增加 2 个百分点，却让多语言下降 1 个百分点、清洗成本增加 30%，那么它不是“高价值”或“低价值”的绝对标签，而是一个依赖产品目标的取舍。面试中说明这种多维报告，并指出如何做下一轮 ablation，比直接背 Data Shapley 更可信。

### 14.3 面试中的关键取舍

不要说“直接用 Shapley 算”。大模型全量 Shapley 不现实，应该讲近似和工程证据链。

## 15. 高频题十四：如何做 dataset versioning 和 governance？

### 15.0 治理问题的快速表达

大模型训练数据必须有不可变快照、manifest、lineage、schema 和 pipeline version。

每条样本应记录 source、license、language、domain、quality_score、safety_label、pii_label、dedup_cluster、contamination_flag、dataset_version、deletion_status。

Manifest 记录 shard、hash、token 数、样本数、来源分布、语言分布、质量统计和风险摘要。

Governance 包括权限控制、访问日志、删除请求、license 审计、PII 处理、benchmark 保护、datasheet 和 model card 支撑。

训练日志要记录数据版本、mixture、sampler、tokenizer、评测集版本和 pipeline 版本，否则模型不可复现。

### 15.1 治理问题的判断边界

回答治理题时，不要把 manifest、license、PII、删除和文档写成一张“全部通过/全部失败”的表。应分别说明版本身份是否稳定、lineage 是否能回到来源、访问是否按用途控制、删除请求处于定位/隔离/回放哪个状态，以及发布文档的事实是否有引用。一个样本被排除出新训练版本，不等于旧 shard、缓存或模型影响已经全部处理。

### 15.2 治理回答的证据链

可以给出一个小例子：删除请求命中旧供应商的一个样本，系统已经把它排除出新版本，但另一个请求没有解析到任何对象。此时应报告命中、未解析和未来排除三个独立状态，说明需要回放哪些派生对象，而不是说“删除已完成”。这类细节能体现你理解治理是可复查的状态系统，而不是文档名词集合。

### 15.3 常见追问：删除请求为什么难

面试官问：“删除请求为什么难？”

回答：因为数据可能存在于原始数据、清洗数据、shard、缓存、索引、embedding、旧版本和已训练模型中，需要 lineage、hash、source_id 和版本记录支持。

## 16. 系统设计题：给你 100TB 原始 web 数据，如何做成训练集？

### 16.0 端到端架构回答

我会按“数据湖 + 处理 pipeline + 质量评估 + 版本治理”的方式设计。

第一层是 raw data lake，保存原始数据和元信息，记录来源、时间、授权和 hash。

第二层是解析层，对 HTML、PDF、代码、多模态分别解析，抽取正文、结构、OCR、语言和元数据。

第三层是清洗过滤层，做基础有效性过滤、模板去除、质量评分、PII、安全过滤和领域分类。

第四层是去重污染层，做 exact dedup、near dedup、段落重复、代码 fork、benchmark contamination。

第五层是数据分桶层，按语言、领域、来源、质量、安全和模态分桶，形成可采样数据池。

第六层是 mixture sampler，根据训练目标设置采样权重。

第七层是评估闭环，小模型 ablation、validation loss、benchmark、安全评估和人工审计。

第八层是治理，manifest、lineage、schema、license、权限、删除请求和 datasheet。

### 16.1 先做容量和状态账本

100 TB 是原始存储量，不是计算和训练容量。设计时要分别估算原始副本、解析中间结果、索引/临时空间、清洗后候选、隔离对象和最终 shard，并为重试、版本保留和删除回放预留空间。若原始数据平均压缩比、解析膨胀率和 token 密度没有测量，容量数字只能作为粗估，不能直接承诺机器数量。

系统还要围绕状态设计，而不是围绕一串脚本设计。每个对象应能处于 discovered、raw、parsed、filtered、deduped、eligible、isolated、published 等状态，并记录失败原因和处理器版本。任务重试必须幂等，不能因为一个 worker 重跑就把同一对象重复计入 token 或 manifest。

### 16.2 100TB 方案的评估与回滚

处理完成后不能只看 pipeline 成功率。要检查各层数量守恒、语言/领域分布漂移、风险命中、重复簇、污染候选和抽样正文；训练入口再核验 manifest、schema 和授权状态。若模型回归，先按数据版本和来源分桶做小规模回放，必要时回滚到上一份 manifest，而不是删除 raw layer 后重新猜测发生了什么。

### 16.3 故障定位与深挖回答

如果训练结果异常，我会先看数据版本和 mixture 是否变化，再看对应评估集相关数据源、污染检测、质量分布和小规模 ablation，而不是直接改模型。

## 17. 系统设计题：如何构建一个代码大模型的数据体系？

### 17.0 代码数据架构回答

代码模型数据要分成源码、文档、测试、issue/PR、问答、教程和合成任务几个池。

采集时记录 license、仓库元数据、语言、star、更新时间、依赖和路径结构。

清洗时过滤二进制、自动生成文件、vendor、fork、secrets、过时或低质量项目。

结构化时按 repo-file-function-class-test 组织，构造 docstring-code、test-code、bug-fix、explain-code、API usage 样本。

污染检测要重点查 HumanEval、MBPP、竞赛题、题解、测试样例和参考答案。

评估要看功能正确性、单测通过率、代码安全、API 时效、多语言编程语言覆盖和自然语言能力副作用。

### 17.1 代码数据系统的特殊边界

代码仓库同时是语料、软件供应链和可执行对象。系统设计要把 license 和依赖风险放在数据对象旁边，把源码、测试和文档的 lineage 保留下来，并在执行评估时使用隔离环境、资源限制和无网络或最小网络权限。只谈存储与 tokenizer，会遗漏代码数据最重要的可执行性和安全性。

还要管理时间切分。训练截止时间、仓库 commit、依赖版本和评测题发布时间共同决定一个样本是否泄漏未来信息；`HumanEval`、`MBPP` 或内部任务的题面、测试和参考解都需要作为污染查询对象。这样才能把“代码模型分数高”与“它在实际新仓库上能正确修改代码”区分开。

## 18. 系统设计题：如何构建一个医疗领域模型的数据体系？

### 18.0 医疗数据架构回答

医疗领域数据要优先考虑安全、权威性、时效性和隐私。

数据来源包括医学教材、指南、药品说明、综述、公开医学知识库、经授权的专业问答和专家标注数据。真实病历必须严格授权、脱敏和审计。

数据要记录来源、发布日期、适用地区、证据等级、版本和过期时间。清洗时处理 PII、错误 OCR、过期指南、低质量论坛和不可靠建议。

训练策略上，继续预训练用于学习医学术语和表达；SFT 用于学习问答格式和安全边界；RAG 用于最新指南和可引用知识；安全数据用于急症提示、免责声明和避免越权诊断。

评估上要有专家审计、事实性、引用正确性、拒答边界、风险提示和多语言能力。

### 18.1 医疗数据的证据和时效

医疗数据的关键不是把领域文本尽可能多地放进训练集，而是让每条可用于回答的事实带有来源、发布日期、适用地区、证据等级和版本。指南更新后，旧版本不能简单与新版本混在同一池中；对需要最新内容的场景，RAG 的检索版本、引用片段和更新时间通常比继续预训练更容易审计。继续预训练可以帮助术语和表达，不能自动把旧知识变成当前临床建议。

### 18.2 风险动作与评估

医疗系统要把普通信息说明、需要进一步澄清、建议寻求专业帮助和拒绝越权诊断等动作分开评估。专家评审事实性和临床安全，自动检查引用和时效，人工样例检查语言与用户理解，红队检查隐私和危险建议。一个整体“准确率”无法替代这些分层结果，尤其不能掩盖严重但低频的错误。

## 19. 行为面试题：数据策略和模型效果冲突怎么办？

### 19.0 数据冲突处理回答

我会先明确冲突指标。比如某个数据策略提升数学 benchmark，但降低通用问答或增加安全误拒。

然后检查是否存在污染、过拟合或评估偏差。接着做分桶分析，看影响来自哪个来源、语言、领域或质量区间。

再通过小模型 ablation、采样权重调整和人工样例评估确认因果方向。

最后给出取舍方案：调整 mixture、隔离数据池、提高质量阈值、补边界数据、改变训练阶段或把部分能力交给 RAG/工具处理。

核心是不要只追单一 benchmark，而要看多目标 trade-off。

### 19.1 用反事实实验定位冲突

先把现象写成可比较的表：数据版本 A/B、目标能力、通用能力、安全切片、污染状态、训练 token、成本和置信区间。然后固定代码与训练配置，只替换数据版本；再固定数据，替换评估或采样规则。若只有一种变化能重复带来回归，才能把它作为较强的归因线索；否则要保留“评估噪声、随机性或多项变量同时变化”的不确定性。

最终方案可以是降低某数据池权重、补充受损切片、改变训练阶段、隔离有风险的来源，或把时效性知识转移到 RAG/工具。回答中明确谁承担代价、如何验证回归不会回来，比笼统说“综合权衡”更有说服力。

## 20. 专家追问：为什么数据质量比数据规模更重要？

严格说不是“质量一定比规模重要”，而是二者共同决定有效训练信号。

规模提供覆盖和多样性，质量提供有效信息密度和可靠监督。低质量大规模数据会浪费 token budget、引入噪声、增加记忆和污染风险；高质量但过窄的数据会导致覆盖不足和风格单一。

所以更准确的回答是：在固定 compute budget 下，我们关心的是有效 token，而不是原始 token。有效 token 由质量、去重、多样性、配比和目标相关性共同决定。

这里的“有效”不能只用一个质量分数表示。一个样本可能语言通顺，却重复很多；可能事实可靠，却与目标领域无关；可能对能力有帮助，却带来无法接受的隐私或授权风险。实际决策可以把质量、覆盖、边际收益、风险和成本分开报告，再按场景设定约束。对一个高风险来源，即使平均质量很高，也可能因为授权证据不足而不能进入训练。

因此，专家回答不应把“质量”和“规模”变成二选一。更好的表达是：在可接受的治理和成本约束下，用分层质量、有效 token、目标能力增益和分布覆盖判断下一单位数据是否值得保留，并通过多尺度消融验证规模扩大是否仍然带来收益。

## 21. 专家追问：为什么数据问题会表现成模型问题？

因为模型是在训练分布上学习统计规律。数据中的重复会表现为记忆，低质量网页会表现为幻觉和差风格，污染会表现为 benchmark 虚高，偏好数据噪声会表现为对齐不稳定，安全数据过度保守会表现为误拒，多语言过滤误伤会表现为语言能力差。

因此，排查模型问题时不能只看架构、优化器和 prompt，也要看数据来源、版本、清洗、配比和后训练数据。

这是一条从统计规律到产品现象的传播链。重复样本提高某些模式的曝光，可能表现为记忆或过拟合；过滤器误伤一个语言桶，可能表现为跨语言能力下降；偏好标签不一致，可能表现为回答风格漂移；评测污染则会让离线分数与真实任务脱钩。每种现象都需要回到对应的数据分桶、版本和处理事件，不能只凭表面现象改变 prompt。

一个有用的排查记录应同时保存模型版本、数据 manifest、训练配置、评估集版本、异常切片和复现实验。这样才能回答“是数据变化造成模型变化，还是模型变化暴露了原有数据问题”，也能避免不同团队用不同版本的评测样本争论同一回归。

## 22. 专家追问：小模型数据实验能外推到大模型吗？

不能保证，但有参考价值。

小模型实验适合快速筛选明显好坏的数据策略，比如去重、清洗阈值、数据源质量和合成数据版本。但大模型可能出现不同 scaling behavior，某些数据在小模型上无效，在大模型上有效，反之亦然。

所以成熟做法是多尺度验证：小模型快速探索，中模型确认趋势，大模型谨慎放大，并持续监控训练曲线和下游评估。

小模型实验尤其适合比较方向和发现明显坏数据，但不能直接外推绝对收益。随着模型规模变化，数据重复的影响、长尾覆盖、能力涌现、优化稳定性和上下文使用方式都可能变化。验证时应尽量保持数据处理、tokenizer、评估切片和训练目标一致，并报告每个尺度的 token 预算和不确定性。

如果小模型与大模型结论相反，不能简单选择更符合预期的结果。先检查数据是否在不同尺度被不同程度地重复消费、loss 和 benchmark 是否测量了不同能力，再做中间尺度和目标切片实验。规模外推是证据累积问题，不是一个固定倍率。

## 23. 专家追问：如何避免数据工程过度优化 benchmark？

第一，做污染检测，确保 benchmark 原题、答案和解析不进入训练。

第二，评估集多样化，不只看单个公开 benchmark。

第三，保留人工评测、产品样例、holdout set 和红队评估。

第四，数据选择不要只按与 benchmark 相似度，而要保留多样性和真实分布。

第五，评估报告中记录数据版本、污染检测方法和残余风险。

还要防止评估设计本身被优化。模型团队可能反复查看公开 benchmark 的题型，选择与题型最相似的数据，或者根据 judge 的偏好调格式。保留私有 holdout、时间外推、真实产品样例和人工审计，才能检验能力是否超出评测集表面分布。报告应把已知污染、评测可见性和未覆盖能力写在结果旁边，而不是只给一个排名。

---

## 24. 专家追问：数据治理会不会拖慢训练迭代？

短期看，治理需要额外成本；长期看，它会加快迭代。

没有治理时，模型变好或变坏都无法解释，删除请求无法处理，实验无法复现，安全事件无法追溯。团队会在问题出现后花更多时间补救。

好的治理不是繁文缛节，而是把 manifest、lineage、schema、权限、审计和版本记录自动化，让训练迭代可追踪、可回滚、可比较。

治理成本也需要按风险分配。低风险公开样本可以更多依赖自动校验和抽样，高风险、可能收到删除请求或会影响安全评估的对象需要更细的 lineage、权限和人工复核。这样做比对所有数据使用同样昂贵的审批更可持续，也比完全没有证据更容易解释速度与风险的取舍。

## 25. 开放题：如果让你从零搭建数据团队，你怎么分工？

可以分为：

1. 数据采集与平台：source registry、数据湖、调度、存储、权限。
2. 数据清洗与质量：解析、过滤、质量评分、去重、污染检测。
3. 数据策略与实验：data mixture、ablation、数据估值、训练反馈。
4. 专项数据：代码、数学、领域、多模态、合成数据。
5. 后训练数据：SFT、preference、安全、红队回归。
6. 治理与合规：license、PII、删除请求、datasheet、model card。
7. 标注与评估：标注规范、专家审计、人工评测、线上反馈。

这个回答体现你理解数据工程不是单一 ETL，而是跨训练、评估、安全和治理的系统。

### 25.1 组织接口比组织名称更重要

团队名称会因公司而变，但交接对象不会消失。采集团队要交出来源登记和 raw snapshot，质量团队要交出过滤版本与抽样报告，数据策略团队要交出 mixture 和消融结果，治理团队要交出授权、权限和删除状态，训练团队要保存实际消费引用，评估团队要固定评测版本。每个交接都应有 owner、输入、输出和失败处理。

如果一个字段没有明确 owner，最终会出现“license 有字段但没人确认”“lineage 有图但不能回放”“评估集可读取但没人负责污染”的情况。回答分工题时，说明交接和异常升级路径，通常比罗列七个部门更有信息量。

## 26. 面试中的常见错误表达

错误一：我们把网上数据爬下来清洗一下就能训。

问题：忽略合规、质量、去重、污染、配比和治理。

错误二：数据越多越好。

问题：忽略有效 token、重复、噪声、风险和 compute budget。

错误三：去重就是 hash 去重。

问题：忽略 near dedup、段落重复、代码 fork 和 benchmark contamination。

错误四：安全数据就是拒答数据。

问题：忽略边界允许、误拒修复、多语言和专业高风险场景。

错误五：合成数据可以无限扩。

问题：忽略 teacher 偏差、同质化、数据退化和验证。

错误六：数据治理是上线后的事。

问题：没有 lineage 和版本，训练阶段就已经不可复现。

这些错误之所以危险，是因为它们看起来都像效率很高的结论，实际上跳过了目标、分母、证据和适用边界。纠正错误时，不要只把句子换成相反的口号，而要补上可验证动作：数据多不一定好，就报告有效 token 和分层收益；去重不只是 hash，就增加近重复和误合并审计；安全不只是拒答，就加入正常任务和安全转向评估。

在真实交流中，也要区分事实、假设和建议。事实应有版本或测量，假设应说明如何验证，建议应说明代价和回滚方式。这个区分能避免为了显得确定而把未核验的模型发布信息、法律判断或 benchmark 结论说成事实。

## 27. 有限时间下的结构化表达

没有准备过的题目也可以用固定顺序组织，但这只是对已经理解的知识做压缩，不是用口号代替分析。先用一句话确认目标，再选择与目标相关的数据对象和证据，最后说明取舍、风险和下一步验证。

第一，我会先明确模型目标和评估指标，因为数据质量和价值都是目标相关的。

第二，我会把数据按来源、语言、领域、模态、质量和风险分池，而不是混成一个大文件。

第三，我会建立清洗过滤流程，包括解析、正文抽取、质量评分、PII、安全过滤、去重和污染检测。

第四，我会设计 data mixture 和采样权重，通过小模型 ablation 和多维评估验证。

第五，我会关注专项数据，比如代码、数学、领域、多模态、合成、偏好和安全数据，它们要单独治理。

第六，我会建立版本和治理体系，包括 manifest、lineage、license、权限、删除请求和 datasheet。

第七，我会用训练结果、评估结果、人工审计和线上反馈反向迭代数据策略。

这套顺序可以覆盖大多数大模型数据工程题，但具体内容要随任务变化。医疗数据要强调证据和时效，代码数据要强调可执行性和供应链，安全数据要强调动作边界，预训练配方要强调 token 预算和分布。若题目没有给出足够信息，先明确假设，不要假装存在唯一比例或唯一工具。

### 27.1 最小可运行数据面试复盘 demo

下面这个 demo 不依赖外部库，也不读写文件。输入是一次 toy mock interview 的 4 道数据工程题回答记录；输出包括每题得分、平均分、指标覆盖率、缺失框架、缺失风险和下一步修正计划。

它演示的不是自动评分面试官，而是把复盘从“感觉没答好”变成可执行清单。真实面试准备时，可以把 `covered`、`metrics`、`evidence`、`risks`、`tradeoffs` 换成你自己的录音复盘结果。

```python
from collections import Counter


FRAMEWORK = {"target", "source", "processing", "mixture", "evaluation", "governance"}
RISK_KEYS = {"license", "pii", "contamination", "safety", "deletion"}
WEIGHTS = {"framework": 0.30, "metrics": 0.18, "evidence": 0.18, "risk": 0.16, "depth": 0.18}

answers = [
    {
        "id": "q_pretrain_dataset",
        "topic": "pretraining data",
        "covered": {"target", "source", "processing", "mixture", "evaluation", "governance"},
        "metrics": {"token_retention", "risk_hit_rate", "contamination_rate", "lineage_coverage"},
        "evidence": {"small_model_ablation", "manual_audit", "version_manifest"},
        "risks": {"license", "pii", "contamination", "deletion"},
        "tradeoffs": {"quality_vs_coverage", "dedup_vs_diversity"},
        "red_flags": set(),
        "time_sec": 165,
    },
    {
        "id": "q_near_dedup",
        "topic": "dedup and contamination",
        "covered": {"processing", "evaluation"},
        "metrics": {"jaccard", "duplicate_rate"},
        "evidence": {"toy_minhash_demo"},
        "risks": {"contamination"},
        "tradeoffs": {"dedup_vs_diversity"},
        "red_flags": {"said_dedup_more_is_always_better"},
        "time_sec": 150,
    },
    {
        "id": "q_preference_safety",
        "topic": "preference and safety data",
        "covered": {"target", "source", "processing", "evaluation", "governance"},
        "metrics": {"annotator_agreement", "length_bias", "unsafe_leak_rate", "over_refusal_rate"},
        "evidence": {"rubric", "red_team_regression"},
        "risks": {"pii", "safety", "contamination"},
        "tradeoffs": {"helpfulness_vs_safety", "judge_cost_vs_human_review"},
        "red_flags": set(),
        "time_sec": 178,
    },
    {
        "id": "q_governance",
        "topic": "dataset versioning",
        "covered": {"source", "processing", "mixture", "governance"},
        "metrics": {"lineage_coverage", "license_completion", "datasheet_completion"},
        "evidence": {"manifest"},
        "risks": {"license", "deletion"},
        "tradeoffs": {"iteration_speed_vs_traceability"},
        "red_flags": set(),
        "time_sec": 205,
    },
]


def score_answer(item):
    framework_score = len(item["covered"] & FRAMEWORK) / len(FRAMEWORK)
    metric_score = min(len(item["metrics"]) / 3, 1.0)
    evidence_score = min(len(item["evidence"]) / 2, 1.0)
    risk_score = len(item["risks"] & RISK_KEYS) / len(RISK_KEYS)
    depth_score = min(len(item["tradeoffs"]) / 2, 1.0)
    penalty = 0.10 * len(item["red_flags"])
    if item["time_sec"] > 180:
        penalty += 0.05
    total = (
        WEIGHTS["framework"] * framework_score
        + WEIGHTS["metrics"] * metric_score
        + WEIGHTS["evidence"] * evidence_score
        + WEIGHTS["risk"] * risk_score
        + WEIGHTS["depth"] * depth_score
        - penalty
    )
    return round(max(total, 0.0), 3)


scores = {item["id"]: score_answer(item) for item in answers}
missing_framework = Counter()
missing_risks = Counter()
revision_plan = []

for item in answers:
    missing = sorted(FRAMEWORK - item["covered"])
    for name in missing:
        missing_framework[name] += 1
    for risk in sorted(RISK_KEYS - item["risks"]):
        missing_risks[risk] += 1
    if scores[item["id"]] < 0.72 or item["red_flags"]:
        revision_plan.append(
            {
                "id": item["id"],
                "add_framework": missing[:3],
                "add_metrics": max(0, 3 - len(item["metrics"])),
                "fix_red_flags": sorted(item["red_flags"]),
            }
        )

average_score = round(sum(scores.values()) / len(scores), 3)
metric_coverage = round(sum(min(len(item["metrics"]), 3) for item in answers) / (3 * len(answers)), 3)

checks = {
    "average_score_floor": average_score >= 0.78,
    "metric_coverage_floor": metric_coverage >= 0.85,
    "revision_items_empty": not revision_plan,
    "time_budget": all(item["time_sec"] <= 180 for item in answers),
}
signals = {
    "low_score_ids": [item_id for item_id, score in scores.items() if score < 0.72],
    "missing_framework": dict(sorted(missing_framework.items())),
    "missing_risks": dict(sorted(missing_risks.items())),
    "over_time_ids": [item["id"] for item in answers if item["time_sec"] > 180],
}
actions = []
if signals["low_score_ids"]:
    actions.append("revise_low_scoring_answers")
if signals["missing_framework"]:
    actions.append("add_missing_framework_topics")
if signals["missing_risks"]:
    actions.append("add_missing_risk_topics")
if signals["over_time_ids"]:
    actions.append("rehearse_within_time_budget")
decision = "revise_answers_and_retest" if actions else "continue_to_next_mock_round"

report = {
    "scores": scores,
    "average_score": average_score,
    "metric_coverage": metric_coverage,
    "missing_framework": dict(sorted(missing_framework.items())),
    "missing_risks": dict(sorted(missing_risks.items())),
    "revision_plan": revision_plan,
    "checks": checks,
    "signals": signals,
    "actions": actions,
    "decision": decision,
}

for key, value in report.items():
    print(f"{key}=", value)

assert scores == {
    "q_pretrain_dataset": 0.968,
    "q_near_dedup": 0.332,
    "q_preference_safety": 0.886,
    "q_governance": 0.574,
}
assert average_score == 0.69
assert metric_coverage == 0.917
assert checks == {
    "average_score_floor": False,
    "metric_coverage_floor": True,
    "revision_items_empty": False,
    "time_budget": False,
}
assert signals["low_score_ids"] == ["q_near_dedup", "q_governance"]
assert signals["over_time_ids"] == ["q_governance"]
assert decision == "revise_answers_and_retest"
```

运行后会看到类似输出：


## 28. 资料与证据边界

本章引用的数据集、论文、标准和工具文档承担不同作用。C4、The Pile、RefinedWeb、FineWeb、Dolma 和 DCLM 主要帮助理解公开语料的构成、过滤、规模和配方实验；它们的具体统计属于各自论文和版本的实验事实，不能直接变成所有模型的通用比例。Datasheets 和 Model Cards 说明应该如何记录数据与模型的动机、限制和风险，但不替代当前项目的授权审查或实测。

去重、污染和评估相关的论文可以支持方法原理，OpenLineage、DVC 和 W3C PROV 更接近工程对象、事件和血缘的建模方式，NIST AI RMF / Generative AI Profile 与 OWASP LLM Top 10 提供风险管理和威胁分类语言。工具文档能证明某个接口或能力如何工作，却不能证明数据已经合法、评测已经无污染，或模型已经适合某个高风险场景。

继续核对时，优先阅读以下原始入口：

1. [C4 文档论文](https://arxiv.org/abs/2104.08758)、[The Pile](https://arxiv.org/abs/2101.00027)、[RefinedWeb](https://arxiv.org/abs/2306.01116)、[Dolma](https://arxiv.org/abs/2402.00159) 和 [DCLM](https://arxiv.org/abs/2406.11794)：公开语料、过滤和配方研究。
2. [Datasheets for Datasets](https://arxiv.org/abs/1803.09010) 与 [Model Cards for Model Reporting](https://arxiv.org/abs/1810.03993)：数据集与模型文档框架。
3. [W3C PROV](https://www.w3.org/TR/prov-overview/)、[OpenLineage](https://openlineage.io/docs/) 与 [DVC](https://dvc.org/doc)：血缘和版本工程入口。
4. [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) 与 [OWASP LLM Top 10](https://owasp.org/www-project-top-10-for-large-language-model-applications/)：风险管理和应用安全入口。

面试表达中应区分论文实验、模型卡自述、官方接口说明、团队自己的实测和法律/合规判断。若资料只支持“某方法曾在某数据和模型上有效”，就不能说成“该方法必然提升所有模型”；若当前项目没有样本级授权或删除证据，就不能用一个数据集名称替代治理结论。

## 29. 本章收束

大模型数据题的核心不是背工具，而是建立从目标到证据的系统视角。一个完整回答应能说明数据从哪里来、经过哪些处理、为什么保留、如何配比、怎样验证收益、风险如何控制，以及模型出现回归时如何回放和修复。

本章反复出现的主线可以整理为：

1. 数据决定模型能力和行为。
2. 数据工程必须和训练、评估、安全、产品闭环。
3. 预训练、SFT、DPO、安全、多模态和 RAG 需要不同数据策略。
4. 去重、污染、配比、合成、偏好和治理都是一体化问题。
5. 好的数据系统不仅能训练模型，还能解释、复现、审计和迭代模型。

当题目没有给出完整上下文时，先声明假设和评估目标；当结论依赖数据版本或法律适用范围时，明确证据边界；当多个指标冲突时，说明取舍和反事实实验。大模型数据工程不是“收集更多数据”，而是在目标、质量、覆盖、风险、配比、评估和治理之间做可复查的系统优化。
