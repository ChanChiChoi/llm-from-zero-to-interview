# 第 13 章 AgentWorld：模型只有进入环境，才真正面对任务

## 13.1 从会回答到会完成

让模型回答“如何修复一个文件”与让它在真实仓库中完成修复，是两种不同能力。后者需要看到目录和工具状态，读取文件，执行命令，处理错误，修改工作区，并通过测试。模型输出的一段文字只是行动建议，任务是否成功要由环境状态判断。

AgentWorld 可以作为理解这类系统的抽象：Agent 通过 observation 看到环境，通过 action 改变环境，再根据新的 observation 继续决策。这里的 world 不一定是游戏，也可以是代码仓库、浏览器、数据库沙箱、文件系统或仿真器。

## 13.2 把 Agent 写成一个闭环

在离散时间 `t`，环境状态为 `s_t`，Agent 观察到 `o_t`，选择动作 `a_t`，环境转移到下一状态并返回结果：

```math
o_t\sim O(\cdot\mid s_t),\qquad
s_{t+1}\sim P(\cdot\mid s_t,a_t),\qquad
r_t=R(s_t,a_t,s_{t+1})
```

Agent 的轨迹是：

```math
\tau=(o_0,a_0,o_1,a_1,\ldots,o_T)
```

任务成功不是“最后一句话包含关键词”，而是环境满足目标谓词 `G(s_T)=1`。例如代码任务要求隐藏测试通过，浏览器任务要求订单状态正确，数据任务要求生成文件存在且 schema 合法。

## 13.3 为什么环境决定能力的含义

同一个模型在只读代码问答和可写仓库中表现不同。只读环境里它可能凭记忆给出合理建议；可写环境里，错误的 patch 会留下真实 artifact，测试失败也会改变下一步计划。

环境还决定反馈质量。编译器和单元测试提供相对清晰的信号，开放网页的错误提示可能模糊，真实生产系统的反馈则可能不可逆。Agent 评估因此不能脱离 environment、工具权限和 reset 机制谈模型分数。

## 13.4 AgentWorld 的四个组成部分

一个可复现的环境至少需要四部分。第一是初始状态，例如仓库 commit、浏览器页面、数据库快照。第二是 observation 接口，规定 Agent 能看到什么、是否分页、是否包含隐藏信息。第三是 action 接口，规定可执行动作和参数 schema。第四是 success、failure 和 reset 规则。

如果没有固定初始 commit，代码任务可能因为依赖更新而变简单或变难；如果 observation 偷偷包含隐藏答案，评测就失去意义；如果 reset 不彻底，前一个 Agent 的文件修改会污染后一个任务。

## 13.5 一个代码环境例子

给 Agent 一个 issue、仓库 commit 和测试命令。它先执行只读目录和搜索动作，观察到错误调用链；然后读取相关文件，生成 patch；测试工具返回失败堆栈；Agent 根据堆栈修改 patch，最后运行完整测试。

环境的成功判据可以写成：

```math
G(\tau)=
\mathbf{1}[\mathrm{hidden\_tests\_pass}]
\mathbf{1}[\mathrm{forbidden\_files\_unchanged}]
\mathbf{1}[\mathrm{no\_policy\_violation}]
```

这说明“测试通过”还不够。若 Agent 修改了测试文件或读取了不允许的秘密目录，任务仍应失败。

## 13.6 浏览器和业务环境

浏览器环境的状态不断变化。页面可能加载失败、元素位置变化、登录状态过期，点击动作可能有延迟。Agent 不能只依赖页面截图中的文字，还要从 DOM、可访问性树或结构化页面状态中获得可验证 observation。

业务环境还要处理外部副作用。查询订单可以在沙箱执行，取消订单则必须进入确认或模拟模式。评测系统要区分“成功导航到确认页”和“已经提交取消”，避免为了提高成功率而允许危险动作。

## 13.7 环境设计的隔离

研究和评测环境通常采用容器、虚拟机或临时 workspace。网络、文件系统、密钥、进程和资源额度都应最小化。每个任务保存环境镜像、初始状态 hash、工具版本和结束状态，才能复现轨迹。

隔离不是只为了安全，也为了公平。一个 Agent 如果能访问外部搜索而另一个不能，两者的结果就不能直接比较；一个环境缓存了前一个任务的依赖，可能让后一个任务获得隐式信息。

## 13.8 评测轨迹而不是只评测答案

一次轨迹可以记录：

```text
observation -> action -> tool result -> state diff -> verifier result
```

报告至少包含最终成功率、动作合法率、工具恢复率、任务成本、时间、环境重置失败和安全违规。部分成功也要保留，例如 Agent 生成了正确 patch 但没有运行测试，或者找到了根因但没有完成提交。

可以定义带成本的任务效用：

```math
U(\tau)=\mathbf{1}[G(\tau)=1]
-\lambda C(\tau)-\mu R(\tau)
```

高成功率但大量越权动作的 Agent，不应被一个平均分掩盖。

## 13.9 常见环境漏洞

第一，reset 不彻底，文件、cookie 或数据库状态泄漏到下一题。

第二，隐藏测试被 Agent 读取，模型学会针对测试而不是完成需求。

第三，observation 含有比生产实际更多的内部字段，导致评测高估能力。

第四，工具错误没有结构化类别，Agent 无法区分权限拒绝、网络超时和业务失败。

第五，成功只看最终文本，没有验证环境 artifact 和副作用。

## 13.10 面试回答与练习

回答“AgentWorld 和普通 prompt eval 有什么区别”时，应说 AgentWorld 把模型放进可观察、可行动、可重置的环境中，评估的是带工具和状态的轨迹。成功必须由环境谓词、测试或 artifact 验证，报告还要覆盖动作合法性、成本、恢复和安全。

练习一：设计一个代码修复环境的 observation、action、reset 和 success schema。

练习二：解释为什么浏览器 Agent 的最终 URL 不能单独证明任务成功。

练习三：列出一个数据库沙箱必须隔离的五类资源。

### 13.10.1 环境闭环比 prompt 多了哪些状态

普通 prompt 评估通常只比较输入和输出；环境闭环还要处理状态、动作、观察、奖励、权限和重置。模型可能回答得很好，但没有把文件写入正确位置，或者在浏览器中点击了错误按钮。环境必须提供机器可判定的成功谓词，而不是让模型自己声称成功。

可以把一轮交互抽象为：

```math
s_{t+1}=F(s_t,a_t,o_{t+1}),\qquad
o_{t+1}\sim P(\cdot\mid s_t,a_t)
```

`s_t` 是环境真实状态，`a_t` 是受策略约束的动作，`o` 是模型看到的观察。模型的自然语言计划只是对状态的假设，只有环境返回和 artifact 才能更新事实。

### 13.10.2 观察空间与隐藏状态

环境不应把所有内部状态都直接暴露给模型。代码任务可以暴露文件、测试结果和编译错误，但不应暴露隐藏测试答案；浏览器任务可以暴露页面和可交互元素，但不应把后台数据库权限直接写进页面。隐藏状态使评测更接近真实工作，也能防止模型利用测试答案。

观察还要带来源和时间。缓存的网页、旧的文件内容和已经失效的工具结果不能被当成当前状态。对长任务，observation 应记录 `source_revision`、`timestamp`、`content_hash` 和是否经过权限过滤。

### 13.10.3 worked example：浏览器任务的成功谓词

任务要求在后台系统中把工单状态改为“已处理”。打开正确 URL 只能说明导航成功；真正成功还要检查工单 ID、状态字段、审计记录和用户权限。若页面加载失败但 URL 正确，任务仍然失败；若状态改了但审计记录显示其他用户，可能是权限或环境隔离事故。

因此环境评估可以返回：

```text
success = page_state_ok
       and target_record_ok
       and audit_actor_ok
       and no_forbidden_action
```

### 13.10.4 reset 和副作用隔离

每条任务开始前要恢复初始状态，清除文件、浏览器 session、数据库记录和工具缓存。对于不可逆动作，使用模拟服务、事务回滚或带 canary 的隔离环境。reset 本身也要测试：如果 reset 不完整，后一个任务可能继承前一个任务的登录状态或文件修改，结果不再可比较。

环境越接近真实系统，成本和安全风险越高。教学 benchmark 可以用小型 sandbox；生产前评估要加入权限、网络、密钥、审计和灾难回滚，而不是直接把 Agent 放到真实生产。

## 13.11 环境的可验证性

环境不仅要返回观察，还要提供可判断任务是否完成的成功谓词。代码环境可以运行测试，浏览器环境可以检查 DOM 或业务状态，数据库环境可以检查事务和约束。只让模型自己说“完成了”，无法评价 Agent。

环境版本、初始状态、随机种子和外部依赖必须可记录。否则同一轨迹在下一次运行中可能因为页面、数据或工具变化而无法复现。

## 13.12 环境状态和部分可观测性

AgentWorld 类系统的任务状态不只存在于 prompt。环境可能包含文件、网页、数据库、时间、权限和外部事件，模型每次只能通过 observation 看到其中一部分。可以用状态转移表示：

~~~math
s_{t+1}=T(s_t,a_t,\xi_t),\qquad
o_t=O(s_t)
~~~

模型根据 observation 选择 action，而不是直接读取完整 s_t。测试环境必须明确哪些状态可见、哪些副作用可逆、哪些事件随机，否则任务成功率无法复现。

## 13.13 模型能力和环境能力要分开

一个 Agent 完成任务可能依赖强模型、强工具、宽权限、丰富初始数据或宽松 grader。评估至少做 oracle tool、受限 tool、无工具和不同权限的对照，记录模型决策、工具执行、环境变化和最终状态。

如果环境允许自动修复、隐藏答案或过度宽松的成功判定，分数会高估模型能力。反之，工具 schema 或网络故障也可能把环境问题误算成推理失败。

## 13.14 长任务的安全闭环

长周期 Agent 需要 checkpoint、租约、幂等、副作用确认、回滚和人工接管。每个 action 应带权限、目标资源、预计副作用和 trace id；失败后要知道是模型重试、工具异常还是环境状态已改变。

高风险环境应使用沙箱、最小权限和合成数据。测试真实任务时，外部副作用必须可审计、可撤销或由人工确认，不能为了提高 benchmark 让 Agent 获得无限权限。

## 13.15 reset 正确性本身也是评测对象

很多环境只验证任务执行，却没有验证 reset。可以在任务结束后计算环境状态与初始快照的差异，检查文件、数据库、cookie、进程、队列、缓存和外部 mock 是否恢复。若 reset 失败，下一条任务可能继承上一条的登录状态或文件修改，成功率就不再是独立样本。

reset 还应区分可逆和不可逆副作用。教学环境可以用快照、事务回滚或临时目录；涉及真实外部系统时，应使用模拟服务、幂等 key、人工确认和清理任务。评测框架必须把 reset failure 单独报告，不能把它隐藏在总失败率里。

## 13.16 部分可观测任务如何公平比较

两个 Agent 的观察空间必须明确。若一个 Agent 看到 DOM、可访问性树和结构化错误，另一个只看到截图，它们比较的是不同环境接口；若一个环境自动把失败动作重试，另一个不重试，任务成功率也不能直接比较。

评测配置应固定 observation schema、工具权限、网络、时间、随机种子、初始状态和 grader 版本。可以做三组消融：完整观察、受限观察、带 oracle 工具，分别测动作合法率、证据使用率、成功率、成本和恢复率。这样才能区分模型能力、环境信息量和工具实现质量。

## 13.17 轨迹质量的分层验收

最终成功率之外，环境闭环还要分别检查 observation 是否完整、action 是否合法、工具是否成功、状态是否按预期改变、验证器是否运行、成本是否超预算以及 reset 是否恢复。可以把一次任务的硬性条件写成：

```math
G(\tau)=G_{\mathrm{observation}}
G_{\mathrm{action}}
G_{\mathrm{state}}
G_{\mathrm{verifier}}
G_{\mathrm{reset}}.
```

任一项失败时，任务不能只凭最终自然语言宣布完成。报告中应保留“正确 patch 但未验证”“工具调用合法但状态未改变”“环境 reset 失败”等部分成功类别，它们比一个模糊的失败率更能指导修复。

## 13.18 worked example：模型、工具和环境的三组对照

对一个代码修复任务，分别运行：完整工具集、只读工具集、带 oracle 搜索工具和无工具模型。若完整工具成功率高但只读版本骤降，说明任务依赖环境行动；若 oracle 工具显著提高成功率，说明检索或工具接口是瓶颈；若所有版本都失败，才更可能是模型计划或代码推理问题。

每组都要固定初始 commit、隐藏测试、网络、时间、权限、随机种子和预算。比较时同时报告任务成功、动作合法率、测试执行率、修复回合数、token/工具成本和安全违规，不能把工具增强后的结果直接当成模型裸能力。

## 13.19 环境变更也需要版本治理

环境镜像、依赖、浏览器版本、数据库快照、工具 schema、grader 和 reset 脚本都属于评测输入。任意一项改变，都可能改变任务难度。任务记录应包含环境版本、初始状态 hash、工具权限、observation schema、grader revision 和结束状态 diff。

生产 Agent 还要把外部副作用与评测 artifact 分开。发送邮件、修改订单或写入数据库必须使用模拟服务、事务回滚、幂等 key 或人工确认；不能为了让 benchmark 更容易通过而放宽真实权限。

## 13.20 环境反馈的质量决定学习信号

AgentWorld 的环境反馈并不天然等于正确标签。编译器错误通常结构清晰，网页中的“操作失败”可能同时包含权限、网络、业务状态和过期页面；如果把所有错误都映射成同一个负奖励，模型学不到该修复哪一层。工具返回应至少区分可重试、参数错误、权限拒绝、业务规则失败和未知执行状态。

这也影响训练和评测。一个 Agent 可能在错误反馈上重复调用工具，直到预算耗尽；另一个 Agent 能识别未知状态并请求人工确认。若只看最终成功率，后者的谨慎行为可能被误判为能力不足。环境应记录错误类别、恢复动作、恢复后状态和是否产生副作用。

## 13.21 轨迹成功的分解与数字例子

设 100 个代码任务中，90 个 patch 可以应用，75 个通过公开测试，60 个通过隐藏测试，其中 3 个修改了禁止文件。若发布准入要求隐藏测试通过且无策略违规，最终安全成功数最多为 57 个，而不是 75 个。可以把任务成功近似拆为：

```math
P_{\mathrm{safe\ success}}
\approx P_{\mathrm{apply}}
P_{\mathrm{verify}}
P_{\mathrm{policy\ pass}}
P_{\mathrm{artifact\ valid}}.
```

这些项不一定统计独立，但分解能指出瓶颈。`apply` 低说明工具或格式问题，`verify` 低说明推理/实现问题，`policy pass` 低说明权限和数据流问题，`artifact valid` 低说明环境或清理契约问题。

## 13.22 观察空间的公平性实验

要验证 Agent 是否真正具备能力，可以做 observation ablation：先给完整目录和结构化测试结果，再只给命令输出，再加入过期缓存或模糊错误；动作集合、预算和初始状态保持不变。若性能只在“泄露了隐藏状态”的版本上高，说明环境信息过强；若结构化错误显著提高恢复率，说明工具协议是系统瓶颈，而不是简单换模型。

浏览器任务也应固定页面快照、账号权限和网络响应。最终 URL、截图相似度和自然语言自述都只能作为辅助信号，真正成功应由目标记录、审计 actor、状态字段和副作用检查共同决定。

## 13.23 复现契约：环境版本和证据范围

一个可复现环境要绑定初始状态 hash、镜像或依赖版本、工具 schema、观察过滤策略、权限、超时、reset 结果、模型 revision 和 verifier 版本。公开 Agent benchmark 的分数只能支持其公开 harness 条件下的观察；换环境、工具和 reset 策略后，不能直接外推为模型能力。

阅读或设计 AgentWorld 时，最重要的证据不是“轨迹很长”，而是每一步 action 是否有授权、observation 是否可信、状态转移是否可验证、失败是否可恢复以及最终 artifact 是否满足目标。环境、模型和 harness 三者必须同时进入结论。

## 13.24 环境反馈不是越多越公平

如果一个环境把数据库内部状态、隐藏测试答案或额外的调试日志直接暴露给模型，轨迹成功率会变高，但测到的是 observation 泄露，不是规划能力。反过来，如果环境完全不告诉模型失败原因，任务会退化成盲目试错。公平的观察空间应模拟真实操作者能看到的信号，并把隐藏信息留给 verifier。

可以把观察空间写成一个投影：

```math
o_t=\Pi_{\mathrm{allowed}}(s_t),
```

其中 `s_t` 是环境完整状态，`Pi_allowed` 由角色、权限和任务规则共同决定。不同模型比较时，投影、工具 schema、超时和 reset 都必须相同；否则所谓模型对比其实是在对比环境信息量。

## 13.25 成功状态和完成文本必须分开

Agent 可能输出“已修复”，但仓库测试仍失败；也可能返回一份看起来完整的报告，却没有写入规定位置。环境应提供独立的完成判据，例如隐藏测试、数据库状态、文件 checksum、业务流程状态或人工验收。文本只是一种 artifact，不是状态转移本身。

一个任务成功可以拆成：

```math
P(\mathrm{success})
=P(\mathrm{authorized})
\cdot P(\mathrm{state\_transition})
\cdot P(\mathrm{artifact\_valid}).
```

任一项为零，都不应因为模型给出流畅总结而记为成功。这种分解也帮助定位问题：授权失败不是规划失败，状态转移失败也不一定是语言理解失败。

## 13.26 AgentWorld 的最小复现包

一个能被复现的环境包应包含镜像或依赖锁定、初始状态 hash、工具定义、观察过滤、权限策略、随机种子、时间和网络策略、reset 脚本、成功 verifier 与失败样本。只保存 prompt 和最终答案，无法重放 agent 的关键决策。

重放时还要记录环境版本是否变化。若环境升级改变了网页、依赖或隐藏测试，结果差异应标记为环境变化，而不是直接归因于模型。对于长周期任务，checkpoint 还要保存外部状态版本和未提交动作。

## 13.27 环境难度要和真实工作流对应

增加工具数量、页面数量或任务步数，不一定增加有意义的难度。真正的难度可能来自不完整观察、状态变化、权限限制、错误反馈、长周期依赖和需要验证的 artifact。环境设计应先写真实工作流，再决定哪些信息隐藏、哪些动作允许、哪些状态可重置。

## 13.28 一次环境回归的判定

环境升级后，用固定模型和固定轨迹检查工具 schema、初始状态、reset、隐藏测试、时间、网络和成功判据。若成功率变化，先判断环境变化是否改变了任务；只有在环境契约稳定时，才能把差异归因给模型或 harness。

## 13.29 小结与资料边界

AgentWorld 不是某一个必然统一的产品名称，而是理解 Agent 环境闭环的一种模型。它把“生成答案”扩展成“在受控世界中观察、行动、恢复并达到目标”。环境的初始状态、权限、反馈、重置和验证规则决定了评测是否可信。

本章的 POMDP、sandbox、benchmark harness 和 Agent tracing 是通用概念；具体项目的环境 API、任务集合和成功定义必须以其官方文档和可复现配置为准。
