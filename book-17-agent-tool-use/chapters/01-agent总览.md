# 第一章：Agent 总览：让模型在受控环境中完成任务

大语言模型擅长根据上下文生成内容。Agent 系统在此基础上多了一层工作：它要围绕一个目标选择动作，交给工具或外部环境执行，再根据返回结果决定下一步。系统因此必须回答一组比“答案写得对不对”更具体的问题：动作是否合适、参数和权限是否有效、观察是否进入状态、任务是否真的完成，以及何时应当停止。

本章用一个报销核对任务建立这幅系统图。读完后，你应能区分 Agent、一次模型调用、检索增强和固定工作流，画出最小的状态—动作—观察闭环，并指出模型建议、系统授权和外部执行分别由谁负责。工具 schema、ReAct 循环、规划、记忆、评估和安全的细节分别留给后续章节。

## 1. 先说明本书怎样使用“Agent”

“Agent”在论文和产品中没有唯一、普遍接受的定义。一次工具调用也可能被产品称为 Agent；另一些讨论则专指持续多步的自主系统。本书采用一个便于分析工程责任的工作定义：Agent 是围绕明确目标，由模型或其他策略提出动作、通过受控接口影响外部环境，并依据环境反馈更新任务状态的系统。

这个定义强调三个观察点：

1. **动作会影响系统边界之外的状态。** 检索、计算和读取文件可以是只读动作；发信、修改代码或提交审批会产生写入副作用。
2. **下一步可能随反馈改变。** 如果每次都照预定分支执行，主控制逻辑属于 workflow；如果新观察会改变后续决策，Agent 策略就承担了实质工作。
3. **模型建议不等于执行授权。** 模型可以提出“发送邮件”，执行器仍须按身份、资源范围、参数、预算和确认规则决定是否允许。

[ReAct 论文](https://arxiv.org/abs/2210.03629)研究了语言模型如何交替生成 reasoning trace 与面向任务的 action；[Toolformer](https://arxiv.org/abs/2302.04761)研究模型如何学习调用哪个 API、何时调用、传入什么参数以及如何使用返回结果。这些是有代表性的研究路线，不是所有 Agent 系统必须遵循的结构或生产保证。[MRKL Systems](https://arxiv.org/abs/2205.00445)则讨论了语言模型与离散知识、推理模块组合的系统思路。详细的动作循环在第三章展开。

## 2. 从报销核对任务看系统边界

用户提出：“请检查这张差旅报销单是否符合当前制度，计算可报销金额，列出依据；不要提交审批。”

这句话里既有任务，也有动作边界。若系统只生成一段答案，模型可能依赖过时记忆；若它调用审批接口，还可能越过“不要提交”的约束。开始执行前，宿主应把用户意图转成可检查的任务契约：

| 字段 | 本例中的值 |
| --- | --- |
| 目标 | 按当前制度核对住宿费用并报告可报销金额和依据 |
| 禁止事项 | 不修改报销单，不提交审批 |
| 可用动作 | 读取制度、读取报销凭证、调用计算器、向用户追问 |
| 完成条件 | 制度版本和计算依据可追溯；缺失资料被标出；没有执行写入动作 |

这里的制度和数字是合成教学数据，不代表真实企业规则。假设当前制度版本 D-2026-07 规定住宿上限为每晚 500 元，凭证显示住宿 3 晚、总额 1,680 元。Agent 先查制度，再读凭证，最后调用计算器：可报上限为 $3\times500=1{,}500$ 元，超出部分为 $1{,}680-1{,}500=180$ 元。系统可以据此给出核对结果，但仍不能提交审批。

| 步骤 | 动作与环境观察 | 状态如何改变 | 下一步为何如此选择 |
| --- | --- | --- | --- |
| 1 | 读取当前差旅制度；返回 D-2026-07 和每晚 500 元上限。 | 记录制度版本、条款位置和读取时间。 | 先固定规则版本，避免凭模型记忆判断。 |
| 2 | 读取凭证；返回 3 晚、合计 1,680 元。 | 记录凭证来源、日期范围、金额和未核对字段。 | 现在有足够输入进行金额计算。 |
| 3 | 调用计算器；返回上限 1,500 元、超额 180 元。 | 将计算结果和输入字段关联保存。 | 计算结果还要与制度条款一起核验。 |
| 4 | 检查任务契约和已收集证据。 | 标记核对完成，保持“未提交”状态。 | 完成条件已满足，系统停止并报告依据。 |

真正有用的结果不只是“超额 180 元”，还包括这个结论用的是哪个制度版本、来自哪张凭证、如何计算，以及审批状态没有改变。如果制度或凭证缺失，系统应转为追问或标明无法确认，而不是补造事实。

## 3. Agent、模型调用、RAG 与 workflow

这些名称描述的是系统的不同侧面，不是互斥的产品标签。

| 形态 | 主任务 | 下一步通常怎样决定 | 需要重点核对什么 |
| --- | --- | --- | --- |
| 单次模型调用 | 根据输入生成回答或结构化输出 | 请求结束后返回结果 | 答案、格式与拒答行为 |
| RAG | 找到外部证据并据此生成回答 | 由检索流程或检索结果决定 | 来源、版本、引用是否支持结论 |
| Workflow | 执行预先定义的步骤和分支 | 按规则、事件或状态推进 | 分支覆盖、权限和失败路径 |
| Agent | 在目标和环境反馈之间选择后续动作 | 新观察可能改变计划或动作 | 状态、动作、授权、结果、停止条件 |

一个系统可以用 workflow 固定授权和审批节点，用 RAG 提供证据，再让 Agent 在“继续检索、调用计算器、向用户追问”之间选择。若一轮工具调用之后没有新的决策，只是把固定函数的结果交给模型改写，称它为 Agent 未必能帮助读者理解其实际控制逻辑。反过来，Agent 内部也可以调用 workflow 或 RAG 子系统。

~~~mermaid
flowchart LR
    A["任务目标与约束"] --> B["策略提出动作"]
    B --> C{"参数、权限和预算检查"}
    C -->|允许| D["执行器调用工具"]
    D --> E["环境返回观察"]
    E --> F["系统更新任务状态"]
    F --> G{"满足完成条件？"}
    G -->|否| B
    G -->|是| H["整理结果与证据"]
    C -->|拒绝| I["追问或安全停止"]
~~~

图中关键边界是“提出动作”和“执行动作”之间的检查。工具 schema 和参数校验在第二章展开；观察怎样改变后续决策在第三章展开；MCP、handoff 等具体接口和协议分别在第二十、二十二册深入。

## 4. 用状态、动作和观察描述最小闭环

为了分析一个 Agent，先把容易混在自然语言里的信息分开。令第 $t$ 轮开始时的系统状态为 $s_t$，它至少记录任务目标 $g$、已确认事实与中间产物 $x_t$、当前身份和授权规则 $p_t$，以及剩余资源预算 $b_t$。令 $a_t$ 表示通过系统检查、实际交给执行器的动作；执行后环境返回观察 $o_{t+1}$。系统把观察写入下一轮状态：

~~~math
\begin{aligned}
s_t&=(g,x_t,p_t,b_t)\\
s_{t+1}&=U(s_t,a_t,o_{t+1})
\end{aligned}
~~~

$U$ 是宿主实现的状态更新规则。$s_t$ 不是 prompt：prompt 是某次模型调用实际收到的消息，系统状态则可以包含不交给模型的权限字段、版本记录和审计信息。执行器拒绝某个动作时，拒绝结果也应成为观察；系统不能把模型说“已完成”当作外部状态的证明。

同一组概念可以串起刚才的报销例子：目标约束是 $g$，制度和凭证是逐步确认的 $x_t$，只读限制属于 $p_t$，可用调用数和时限属于 $b_t$；读取制度、读取凭证和调用计算器是动作，工具返回的版本、金额和错误是观察。只有当观察更新了状态，下一步才能根据新证据合理选择。

## 5. 组件分别负责什么

| 组件 | 它维护或产生什么 | 不能单独证明什么 | 深入入口 |
| --- | --- | --- | --- |
| 目标与完成条件 | 用户要解决的问题、禁止事项、验收结果 | 模型正确理解了目标 | 第 3、4 章 |
| 状态与记忆 | 已确认事实、来源、版本、未解决项 | 记忆内容仍然新鲜或有权限 | 第 5 章 |
| 策略与规划 | 候选动作或阶段安排 | 候选动作可以执行 | 第 3、4 章 |
| 工具描述与执行器 | 输入输出契约、参数检查、实际调用 | 工具返回值满足任务目标 | 第 2、7、8 章 |
| 观察处理 | 返回值、错误、部分结果和来源被转成状态事件 | 外部文本可信或已经被正确使用 | 第 3、6 章 |
| 控制器 | 预算、权限、重试、停止和人工接管 | 最终任务结果真实正确 | 第 10、11、20 册 |
| 轨迹记录 | 动作、观察、状态变化与决策原因 | 日志完整就代表系统质量合格 | 第 10 章与第二十册 |

这张表是责任划分的起点，不要求每个产品都使用同名模块。小型应用可以把几个职责放在同一个服务里，但仍要能指出谁验证权限、谁执行动作、谁记录结果，以及出现不确定状态时由谁阻止后续副作用。

### 5.1 上下文、状态、记忆和轨迹不是同一份文本

模型每轮看到的上下文，是宿主从系统信息、用户输入、任务状态、工具描述和观察中挑选并组装出来的当前视图。任务状态记录本次任务已经确认的事实、约束和进度；长期记忆保存可能跨任务复用的信息，需要注明来源、范围、时间和权限；轨迹则记录实际发生的动作和结果，用于审计与复盘，不应未经筛选就全部注入下一轮上下文。

这一区分可以避免两种错误：把“模型看过”误当成“系统已经验证”，以及把旧对话中的偏好或事实误当成当前任务的权威状态。第五章会讲记忆的生命周期；第二十册会讲长任务状态、压缩、checkpoint 和恢复。

### 5.2 预算包括多种资源

长任务可能消耗模型 token、工具调用、等待时间、外部服务费用和人工复核。它们不一定能用一个可靠系数换算；没有共同单位时，应分别记录资源，而不是把不同单位直接相加。控制器需要在执行过程中更新剩余额度，并在任务结束或失败时保留实际消耗。第十六册讨论推理预算，第二十册讨论 Runtime 的任务级资源与恢复。

### 5.3 多 Agent 也要纳入同一条账

多个 Agent 可以并行处理相互独立的子任务，但会增加通信、状态同步、重复工作、冲突合并和最终验证成本。若协作者共享同一错误证据，数量增加并不会产生独立验证；若任务有强顺序依赖或高影响副作用，集中调度和串行确认可能更容易控制。第九章讨论何时协作，第十四章讨论如何隔离并行工作并合并结果。

## 6. 什么时候需要 Agent

考虑使用 Agent，通常要同时满足三个条件：

1. 任务确实需要多个步骤，且下一步可能取决于外部观察。
2. 每一步有可用工具或信息来源，结果能被检查。
3. 动作范围、预算和停止条件能够被系统限制。

固定 FAQ、格式转换和稳定的数据管道通常用单次调用或 workflow 更简单，也更容易测量。如果一个任务只需要一次检索和一次回答，增加开放式循环可能只会增加延迟和失败路径。支付、发信、删除等高影响动作也不应因模型能生成调用就自动开放；应将权限、预览和确认交由系统控制。

选择的依据应是实际任务中的反馈需求、验收方式和失败代价，而不是产品名中有没有“Agent”。本书后续会分别讨论工具、规划、不同任务环境、多 Agent、评估和安全，让这些条件可以具体判断。

## 7. 失败、评估与安全边界

Agent 的失败可以先按发生位置分类，再到对应章节学习机制和修复方法。

| 观察到的失败 | 优先检查哪一层 | 深入入口 |
| --- | --- | --- |
| 把“检查并建议”扩成“直接提交” | 目标契约、禁止事项和确认规则 | 第 3、4、11 章 |
| 工具或参数选错 | 工具描述、schema、参数与任务状态 | 第 2—4 章 |
| 工具已返回结果，后续决策却没有变化 | observation 解析和状态更新 | 第 3、5 章 |
| 使用过期知识或上一任务的事实 | 记忆来源、作用域、时间和权限 | 第 5、6 章 |
| 超时后重复发送或报告“已成功” | 外部副作用状态、幂等和恢复 | 第 3、11 章及第二十册 |
| 多个 Agent 互相覆盖或重复工作 | 任务依赖、共享状态和合并规则 | 第 9、14 章 |
| 答案看起来正确但缺乏证据，或越过权限 | verifier、证据和权限边界 | 第 10、11、13 章 |

排查时至少分别检查任务结果、动作、观察使用、状态变化、资源和权限。任务成功率不能说明某一步工具调用是否越权；日志齐全也不能证明动作正确。第十章会定义这些指标并给出 trace 审计程序，本章只建立读懂这些指标所需的系统边界。

Agent 的一次运行至少要能回答以下问题：

- 任务是否达到事先定义的完成条件？
- 动作是否符合工具契约、当前身份和用户约束？
- 环境返回了什么观察，哪些事实因此写入状态？
- 超时、拒绝或部分成功后，系统怎样恢复或停止？
- 资源用了多少，结果是否依赖特定模型、工具、环境或 verifier？

任务成功、动作质量、观察使用、状态更新、权限、成本和停止行为是不同的观察维度。最终答案正确不能抵消一次未经授权的副作用；调用成功也不能证明来源足以支持结论。具体指标定义和完整 trace 案例放在第十章，纵深安全机制放在第十一章，长任务 Harness 实现放在第二十册。

研究报告和产品数字还须区分模型、工具、环境和 Harness。模型提出动作，工具接口规定可调用能力，环境决定动作后的真实状态，Harness 负责执行、恢复和记录；换其中任何一项，都可能改变结果。第十三章会深入任务环境与 verifier，第十五章用模型发布案例练习证据分层。

## 8. 本章小结

在本书的工作定义中，Agent 是一个依照目标、根据外部观察选择动作的系统。它与模型调用、RAG、workflow 可以组合；判断其职责时，要看外部反馈是否会改变下一步，以及工具动作由谁校验、授权和执行。

报销核对例子展示了最小闭环：固定任务约束，获取带版本的证据，执行可复算的计算，更新状态，再按完成条件停止。模型可以提出动作，但系统必须保留对权限、预算和真实外部状态的控制。

下一章转向工具 schema 与 function calling：把动作从一句自然语言变成有名称、参数、约束和执行结果的接口。

## 9. 延伸阅读与证据边界

- [ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629)：推理轨迹与任务动作交错的研究案例；论文实验绑定其任务与环境。
- [Toolformer: Language Models Can Teach Themselves to Use Tools](https://arxiv.org/abs/2302.04761)：模型学习选择 API 和使用返回结果的研究案例；不是通用 Runtime 设计。
- [MRKL Systems](https://arxiv.org/abs/2205.00445)：语言模型与离散知识/推理模块组合的架构讨论。
- [OpenAI Agents SDK 文档](https://openai.github.io/openai-agents-python/)：公开 SDK 中的 Agent、工具、guardrail、orchestration 与 trace 概念；动态文档只支持对应公开接口，不说明闭源模型内部实现。
- [NIST AI RMF Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)：组织级生成式 AI 风险管理资料，不是 Agent 产品验收标准。
- [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)：风险类别入口，不代替具体系统的威胁建模。

报销阈值和费用为合成教学数据。以上资料没有在本地复现；产品系统仍须在自己的模型版本、工具实现、权限、数据和环境中验证。
