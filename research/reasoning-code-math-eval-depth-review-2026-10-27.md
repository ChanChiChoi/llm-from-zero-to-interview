## 研究问题

1. 数学最终答案相同，如何进一步测出模型是否对题目数值、无关条件和结构变化敏感？
2. outcome supervision、process supervision 与“定位最早错误”的 benchmark 分别解决什么问题？
3. HumanEval/EvalPlus、LiveCodeBench 和 SWE-bench 代表哪些不同代码任务，测试增强、时间新鲜度和仓库级评估分别改变了什么？
4. 如何把题目、判定器、测试强度、版本时效与模型能力分开归因？
5. 现有教学 demo 是否把测试用例数量当成覆盖充分性，并且是否为每个失败门禁提供后续动作？

## 来源与证据映射

| 来源 | 读到的设计与实验 | 它解决的问题及可支持判断 | 限制与本章用法 |
| --- | --- | --- | --- |
| [MATH 数据集原论文](https://arxiv.org/abs/2103.03874) | 阅读构造与评分：12,500 道竞赛数学题，七个主题，难度 1—5，提供完整逐步解答；归一化最终答案后 exact-match 评分。 | 相比年级应用题，提供更广的高中竞赛数学题型与难度切片；为过程监督提供参考解答。 | 最终答案 exact match 不检查证明每一步是否成立；学科分布仍是竞赛数学，不能代表全部数学/科学推理。正文用它说明最终答案指标与过程正确性的边界。 |
| [GSM-Symbolic, arXiv v2 / ICLR](https://arxiv.org/abs/2410.05229) | 阅读符号模板生成、数值实例变化和 GSM-NoOp 实验。模板让同一类题可控制数字/表面实体；NoOp 在问题中加入看似相关但与运算无关的句子。作者报告数值变体间的表现波动、复杂条件增多时性能退化，以及特定设置下加入无关句子导致显著下降（最高 65%）。 | 固定 GSM8K 只能给一个静态题集分数；受控变体能分别观察题面/数值敏感性和相关信息筛选。错误若只出现在 NoOp 切片，下一步应查干扰条件过滤，而不是笼统归为数学能力下降。 | 论文实验不能证明模型内部是否“真正推理”；不同变体仍须核验答案和难度等价。65% 是作者所测模型与协议中的最大降幅，不是通用预期，也不能直接归因为数据污染。正文将其解释为可观察的稳健性信号。 |
| [Let's Verify Step by Step, arXiv 2305.20050 / ICLR 2024](https://arxiv.org/abs/2305.20050)、[OpenAI PRM800K 数据说明](https://github.com/openai/prm800k) | 对照 outcome supervision（只标最终结果）与 process supervision（逐推理步骤标注）；论文公开 800,000 条步骤级人工反馈，并报告 process-supervised 模型在其 MATH 设置的代表性测试子集上解出 78%。 | 展示步骤反馈能提供比最终成败更密集的训练信号，可支持该研究配置下的结果；帮助解释为何需要分别评估答案与中间步骤。 | 人工步骤标注昂贵，步骤切分和替代解法增加歧义；论文训练结论不等于 process score 在任意任务上更好，也不能当成现有目标模型的准确率。正文保留模型/数据/任务限定。 |
| [ProcessBench, ACL 2025](https://aclanthology.org/2025.acl-long.50/) | 阅读样本定义、标注、结果和 limitations：3,400 条数学过程样本，来源覆盖 GSM8K、MATH、OlympiadBench、Omni-MATH；人类专家标注最早错误步骤或“没有错误”。作者先统一段落步骤粒度；分歧样本最多扩充至五位标注者仍未达成多数时会丢弃，整体约 30% 被丢弃。 | 把“最终答案判断”改成“给定解答中的第一处错误定位”，测量可监督性/过程批判能力。作者报告已有 PRM 在更难题上的泛化有困难，若干 prompted critic 与其 PRM800K 微调模型优于已有 PRM。 | 过程切分、第一错标签仍可能有争议；难题更易被丢弃可能改变分布。它测的是错误定位，不是模型独立解题能力；论文内 PRM 排序不能外推为所有 PRM/critic 的普遍排名。 |
| [EvalPlus / HumanEval+，NeurIPS 2023](https://papers.neurips.cc/paper_files/paper/2023/hash/43e9d647ccd3e4b7b5baab53f0368686-Abstract-Conference.html)、[论文全文](https://arxiv.org/html/2305.01210) | 阅读测试生成和实验：先用 LLM 构造有效边界输入 seed，再做类型感知变异，拿候选程序与参考实现做 differential testing；可用 set cover/mutation 相关信息缩减测试。HumanEval 测例扩为原来的 80 倍；研究观察到旧测试不足会漏错并改变模型排序。 | 解决小规模手写测试对函数行为覆盖不足的问题；把“通过样例”推进为对输入域的系统探测。 | 参考实现可能有 bug，生成的输入可能违反任务契约，更多测试也不构成形式证明；测试缩减目标函数会影响保留哪些行为。80 倍和论文模型排名只绑定原研究设置。正文解释 seed→变异→差分执行→人工核验的路径，并强调测试数量不能代替覆盖审查。 |
| [LiveCodeBench](https://arxiv.org/abs/2403.07974) | 阅读 benchmark 任务范围与首版数据快照：持续从 LeetCode、AtCoder、Codeforces 收录新题；除生成外，还评估自我修复、执行结果预测等能力。论文初始版本覆盖 2023-05 至 2024-05 的 400 题。 | 相对长期固定的公开题集，时间戳新题可减少旧题长期公开造成的暴露；多任务模式可拆开评估代码行为。 | “新鲜”只对已钉住的日期和模型 cutoff 成立；公开后仍可能被训练，滚动版本也改变题目分布。不同快照之间需做版本记录和共同题/校准，不能当完全同一考试。 |
| [SWE-bench Verified 初始说明](https://openai.com/index/introducing-swe-bench-verified/) | 阅读 issue→仓库补丁任务与评分：500 个人工筛选样本；93 位 Python 开发者参与标注。候选补丁既要使 `FAIL_TO_PASS` 测试通过，也要保持 `PASS_TO_PASS` 测试通过；使用容器化环境运行。 | 把评估从独立函数扩展为理解 issue、探索多文件仓库、实现改动并避免回归的端到端任务。两种测试分别覆盖目标修复和已有行为回归。 | 测试可能过窄或错误，issue 描述可能欠规格，环境差异也会导致伪失败；具体结果还绑定 agent scaffold、工具、预算、镜像与 harness。 |
| [OpenAI 关于停止报告 SWE-bench Verified 的审计](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) | 阅读 2026-02-23 官方审计：在模型常失败题目中抽审的 27.6% 子集中，至少 59.4% 存在会拒绝功能正确答案的缺陷测试；审计还称前沿模型能重现原 gold patch 或问题细节，并据此停止报告 Verified、建议报告 SWE-bench Pro。 | 说明 benchmark 有效性会随题目公开、模型训练数据和测试实现而变化；旧的高分增长未必继续测到能力进步。 | 这是 OpenAI 自身的审计和建议，不是独立社区共识；结论只说明被抽审数据与其检测流程。SWE-bench Pro 也不是完美或已证明无污染。正文同时写出来源身份和边界，不把推荐写成永久规则。 |

## 代表性方案解决的问题对照

| 评测路线 | 改动了测量链的哪一环 | 适合回答 | 主要失效边界 | 后续补强 |
| --- | --- | --- | --- | --- |
| GSM8K 固定题集 | 固定题面，按标准答案计分 | 同一版本同一协议下模型解这些应用题的比例 | 单点分数不揭示数字变体、干扰信息、步骤错误；长期公开有暴露风险 | 固定回归集之外加符号变体和私有 holdout |
| GSM-Symbolic / GSM-NoOp | 参数化题面，分别改变数字、条款结构或加入无关句 | 错误是否由特定表面变化/干扰条件触发 | 变体生成可能改变难度或语义；单次失败不能判定内部机制 | 重新核答案、匹配难度，报告配对差与切片置信区间 |
| Outcome RM | 用最终答对/错训练或评分 | 最终结果和候选排序 | 不告诉哪步错；错误路径偶然答对可能得高分 | 与步骤标签、规则 verifier 和人工抽样并列 |
| PRM / ProcessBench | 对步骤给分，或标注最早错误的位置 | 错误定位和过程监督信号是否可用 | 标签成本/路径歧义；PRM 可能跨题型泛化失败 | 在独立难度与来源切片验证，报告过程标注一致性 |
| HumanEval+ / EvalPlus | 用 seed、变异输入和差分执行增强测试 | 原基准测试是否漏掉函数行为错误 | 参考实现/输入契约可能错；测试不等于证明 | 抽样人工审阅、变异覆盖和 reference audit |
| LiveCodeBench | 用按时间收集的新竞赛题和多种代码任务 | 新近公开题上的代码生成/修复等能力 | 发布即产生后续污染风险；数据快照改变分布 | 每次报告固定题目日期、模型 cutoff 和任务类型 |
| SWE-bench Verified | 仓库 issue、完整补丁、目标测试和回归测试 | agent 在指定仓库/harness 下能否修复 issue | 测试有缺陷、题目暴露、agent scaffold 与预算影响很大 | 审计可接受补丁而非只复现 gold patch；保留私有任务、版本与环境 |

这些路线不是逐代替代关系。数学/代码最终结果、步骤错误、单函数行为与仓库修改
是不同构念。用法应由任务决定：验证函数契约可用测试增强；评估跨时间公开竞赛
能力需要带日期的题集；评估代码 Agent 要增加仓库、工具和回归条件；定位数学推理
错误则需要第一错标签或过程审阅。最终报告把每种任务各自的分母和资源预算说清，
不要把指标相加成一个“推理总分”。

## 正文改动映射

- §3.8 比较 GSM8K、GSM-Symbolic 和 GSM-NoOp，并用同一道题的数值变体/无关条件变体演示从“错误分数”走到错误原因；将论文结论限定为可观察行为，不断言内部思维机制。
- §4.8—§4.9 说明 EvalPlus 的 seed→类型变异→差分 oracle→人工审查链路；对照 LiveCodeBench 的时间新鲜度和 SWE-bench Verified 的 issue/仓库级目标修复与回归测试，并补入 2026 官方后续审计的时效变化。
- §8.4 明确 ORM 训练最终结果评分，PRM 提供步骤信号，ProcessBench 测“第一处错误定位”；给出第一错位置定义和错因轨迹，避免把过程分说成普遍能力。
- §9.6 将固定回归题集与滚动新题分开版本管理，并解释公开新题也会在发布后暴露。
- §12 demo 静态审阅发现：`hidden_tests < 8` 是任意阈值，不能说明测试契约覆盖；现改为显式的 required/covered slices 差集。答案解析器只适用于本例有限格式；self-consistency 结果改作预算诊断，不再当通用发布门禁；accuracy、parser、代码、测试覆盖、过程和污染各 gate 都要映射到动作；污染 flag 缺失不被当成“已证明无污染”。输出标为静态手工核对的预期摘要，本轮没有执行代码。
- §14 增加“测试条数不等于测试覆盖”与“不同 benchmark 分数不共享量尺”；§15 增加代表性方法选择和反例分析练习；§16 补齐上述原始来源。
