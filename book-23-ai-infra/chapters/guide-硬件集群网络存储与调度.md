# 第二章：硬件、集群、网络、存储与调度

## 2.1 为什么算法结果会被基础设施改写

同一个模型、同一批数据，放在不同集群上运行，可能得到完全不同的训练时间、吞吐、失败率和单位成本。原因不在于 GPU 只是“更快或更慢”，而在于一次训练任务同时依赖计算、显存、卡间通信、数据供给和调度策略。

例如，八张 GPU 的理论算力很高，但如果每一步都在等待跨机 `all-reduce`，GPU 利用率仍然可能很低；存储带宽不足时，数据 loader 会让计算卡空转；调度器把长任务和短任务混在同一队列，又会让交互式实验长期排队。因此，AI Infra 的基本单位不是某种硬件名词，而是一条可测量的资源路径：

```text
数据源 -> 存储 -> 数据加载 -> GPU 计算 -> 卡间通信 -> checkpoint -> 调度与恢复
```

本章从这条路径出发，建立硬件、网络、存储和调度之间的关系。后续各章会分别深入实现细节；这里的内容本身解决一个独立问题：给定一个训练或推理任务，如何判断瓶颈属于哪类资源，以及如何用数量关系验证判断。

## 2.2 一次训练 step 的资源分解

可以把单个训练 step 的墙钟时间粗略写成：

```math
T_{step}=T_{compute}+T_{communication}+T_{input}+T_{checkpoint}+T_{stall}
```

`T_compute` 是 GPU 执行 forward、backward 和 optimizer 的时间；`T_communication` 包括 data parallel 的梯度同步、tensor/pipeline parallel 的中间结果传输；`T_input` 是读取、解码、tokenize 和搬运 batch 的时间；`T_checkpoint` 是保存状态的时间；`T_stall` 则包含排队、同步不平衡、页面错误和其他无法归类的等待。

这个式子不是精确性能模型，但它能防止一个常见错误：看到 GPU 利用率下降就立即增加 GPU 数量。如果下降来自 `T_input`，增加计算卡只会让更多卡一起等待；如果下降来自通信，应该先检查拓扑、消息大小、collective 算法和并行策略。

## 2.3 GPU、显存和互联的分工

GPU 的计算吞吐通常由矩阵乘法单元、数据类型和时钟共同决定。训练大模型时，显存不仅存放权重，还要存放激活、梯度、优化器状态、通信 buffer 和临时 workspace。一个教学级显存预算可以写成：

```math
M_{device}
\approx M_{weight}+M_{grad}+M_{optimizer}+M_{activation}+M_{workspace}+M_{comm}
```

不同并行方式会改变这些项的归属。数据并行让每张卡保留模型副本，通信主要是梯度同步；张量并行把一个层切到多张卡，减少单卡权重但增加层内通信；流水线并行按层切分，减少单卡模型容量但引入 stage 间的激活传输和 bubble。

卡内显存带宽、GPU 之间的链路带宽、主机到 GPU 的 PCIe 带宽和跨节点网络带宽不是一回事。下面这个简化判断很有用：

```text
同一 GPU 内的 HBM 访问：主要受显存带宽和 kernel 访存模式影响
同一主机多 GPU：主要受 NVLink/NVSwitch 或 PCIe 拓扑影响
跨主机通信：还要叠加 NIC、交换机、协议栈和拥塞控制
```

当并行组跨越慢链路时，计算和通信的重叠能力就会成为决定性因素。NCCL 文档中的 collective 操作和 CUDA 文档中的异步执行语义，是分析这些问题的基础资料；具体带宽必须用当前硬件和拓扑实测。

## 2.4 网络不是“有带宽就够了”

以 `all-reduce` 为例，若每个 rank 要同步大小为 `S` 的梯度，环形算法的通信量会随 rank 数增加而变化。一个常用的教学近似是每个 rank 发送和接收约：

```math
V_{rank}\approx2\frac{N-1}{N}S
```

实际时间还受链路带宽 `B`、启动延迟 `\alpha`、消息分片、拓扑和算法选择影响：

```math
T_{comm}\approx\alpha\cdot K+\frac{V_{rank}}{B_{effective}}
```

`K` 可以理解为通信轮数，`B_effective` 不是网卡标称带宽，而是扣除协议、拥塞和竞争后的有效带宽。小消息更容易受启动延迟影响，大消息更容易受带宽和拥塞影响。

InfiniBand、RoCE 和普通以太网的差异，不应只用“快/慢”概括。需要同时看网络语义、RDMA 配置、交换机无损策略、队列、ECN/PFC、故障恢复和运维能力。一个配置不完整的 RoCE 集群，可能在小规模测试中正常，在多任务并发时因为丢包和重传出现长尾；一个低带宽网络也可能通过更合理的并行策略获得稳定结果。

## 2.5 存储和数据供给的数量关系

假设训练有 `W` 个 worker，每个 worker 每秒需要消费 `r` 个样本，每个样本经过解码后平均占 `s` 字节，那么数据路径至少要提供：

```math
B_{read}\ge W\cdot r\cdot s
```

这只是平均吞吐门槛。真实系统还要考虑 shuffle、重复读取、缓存命中率、压缩解码、对象存储请求数和故障重试。若一个样本平均 1 MiB，128 个 worker 每秒各消费 4 个样本，理论读取需求已经是：

```math
128\times4\times1\mathrm{MiB}=512\mathrm{MiB/s}
```

如果解码、网络和缓存只能稳定提供 300 MiB/s，GPU 利用率下降是必然的。此时应先确认是对象存储吞吐不足、单文件过大、metadata 请求过多，还是 worker 端预取和缓存策略不合理。

本地 NVMe 适合高速临时数据和 cache；共享文件系统适合多节点访问和统一目录；对象存储适合大规模 artifact、checkpoint 和版本化数据，但通常需要客户端缓存、分片和重试。训练数据、checkpoint 和日志的生命周期不同，不能把它们都放在同一种存储上。

## 2.6 调度器管理的是资源和公平性

队列调度不是简单的 FIFO。一个任务提交时，调度器至少要考虑 GPU 类型和数量、显存、节点拓扑、网络域、优先级、租户 quota、抢占成本、数据位置和 checkpoint 可恢复性。

可以把一次准入判断抽象成：

```math
Admit(j)=I(G_j\le G_{free})\land I(M_j\le M_{free})
\land I(Q_j\le Q_{tenant})\land I(P_j\text{ matches topology})
```

其中 `G_j` 是任务请求的 GPU 数，`M_j` 是显存要求，`Q_j` 是租户配额使用量，`P_j` 表示并行组对拓扑的要求。实际策略还要加入优先级和等待时间，避免高优先级任务把低优先级任务永久饿死。

抢占也不是免费操作。若任务已经训练了数小时但最近 checkpoint 很旧，抢占会造成重复计算；若任务没有保存可恢复状态，抢占可能等价于丢失实验。调度器应把“释放资源的收益”和“恢复任务的成本”放在同一个决策中。

## 2.7 一个端到端排障例子

某团队把训练从 8 卡扩到 32 卡后，step time 从 1.2 秒变成 2.4 秒，GPU utilization 从 82% 降到 48%。排查不应先换更大的机器，而应按路径记录：

1. 比较单卡、8 卡、32 卡的 forward/backward 时间，确认计算量是否改变。
2. 记录 `all-reduce` 的实际耗时、消息大小和 effective bandwidth。
3. 检查 32 卡是否跨越了不同网络域，rank mapping 是否尊重拓扑。
4. 查看 data loader wait、page fault、CPU 利用率和存储吞吐。
5. 检查是否有 straggler rank，某一节点是否出现降频、ECC 或链路重试。
6. 对比同步点前后的时间线，判断通信是否与计算重叠。

如果 8 卡通信只占 8%，32 卡通信升到 55%，说明扩展瓶颈主要在通信；如果通信仍为 10% 但 data wait 升高，则应检查数据供给。这个例子说明，扩容后的回归必须以时间分解和 trace 为证据，不能只看总 step time。

## 2.8 设计取舍与失败模式

高带宽互联能降低通信时间，但成本、机柜布局和故障域会增加；本地 cache 能改善读取速度，但会产生数据一致性和容量管理问题；抢占能提高集群利用率，但会增加恢复开销；优先级能服务紧急实验，却可能破坏长期公平性。

常见失败模式包括：把标称带宽当成有效带宽，把 GPU 利用率当成训练效率，把共享文件系统当成无限吞吐，把 checkpoint 当成“保存模型权重”而遗漏 optimizer/RNG/data position，把调度器的资源准入和租户权限混在一起，以及在没有恢复测试的情况下宣称支持容错。

真正的验收应同时覆盖 tokens/s、step time、通信占比、数据等待、GPU 利用率、checkpoint 恢复时间、队列等待、租户公平性和故障后的任务成功率。单一指标无法代表 AI Infra 的质量。

## 2.9 资源故障的级联路径

GPU 降速可能源于显存、PCIe、网络、存储或调度，而不是 GPU 本身。训练 step 的时间线要把 data wait、host-to-device、forward、collective、checkpoint 和 queue time 分开记录。

容量规划还要留故障余量：单卡、单机、交换机和存储故障时，剩余集群是否仍能满足最低吞吐和 checkpoint 恢复时间。

## 2.10 拓扑感知的容量例子

假设 16 个 worker 分布在两台 8 卡机器上。单机内 NVLink 的有效带宽为 `B_intra`，跨机 RoCE 的有效带宽为 `B_inter`，而梯度同步的消息总量为 `S`。如果 rank mapping 让通信大部分留在机内，跨机阶段的关键路径近似由 `B_inter` 决定；如果 rank 被随机分散，更多消息会走跨机链路，理论上 GPU 数增加了，实际 step time 却可能上升。

排查时要同时保存 rank-to-device 映射、交换机端口、链路重传、NCCL collective 时间和每个 rank 的 step 时间。只看平均带宽会漏掉一个慢 rank；同步训练的迭代时间通常由最慢 rank 决定：

```math
T_{step}=\max_{r\in\mathrm{ranks}}T_{r}.
```

因此，某一节点降频、PCIe 错误或数据加载变慢，即使其他 GPU 都很快，也会把全局吞吐拉低。拓扑设计还要考虑故障域：把所有副本放在同一交换机内可能最快，却让一个交换机故障同时影响整个并行组。

## 2.11 存储、checkpoint 与恢复窗口

存储规划不能只回答“能否把文件放下”。训练数据读取、checkpoint 写入、日志上传和容器镜像拉取可能同时争用网络和对象存储。若一个 checkpoint 大小为 `S`、可用写带宽为 `B_w`，理想写入时间是：

```math
T_{ckpt}\ge\frac{S}{B_w}.
```

实际时间还要加 manifest、校验、重试、元数据请求和并发竞争。异步 checkpoint 可以减少训练线程停顿，但会形成“训练进度已经前进、最近完整恢复点还在旧 step”的恢复窗口。调度器抢占前必须读取 checkpoint 完成状态，不能只看任务报告的当前 step。

数据、checkpoint 和日志应使用不同的生命周期策略。训练数据需要版本和权限，checkpoint 需要原子提交和长期可读，临时日志可以短期保留并脱敏。把三者都写进一个共享目录，容易出现清理误删、权限放大和 I/O 互相干扰。

## 2.12 调度器的验收与决策条件

### 2.12.1 调度决策需要留下什么证据

一次“等待”不是一个足够的故障原因。调度器至少要记录任务在提交、排队、准入、分配、启动、抢占、恢复和结束时的状态，以及每个状态转移对应的资源和策略版本。否则当队列变长时，平台只能告诉用户“资源不足”，无法区分 GPU 不够、拓扑不匹配、配额不足、镜像拉取慢还是 checkpoint 尚未完成。

可以把一次准入决策写成审计记录：

```text
job_id / tenant / priority / requested_gpu
memory / topology / data_locality / quota
available_snapshot / policy_revision
decision / rejection_reason / assigned_devices
```

其中 `available_snapshot` 很重要。资源是动态变化的，同一个任务在不同时间被拒绝，原因可能不同。保存快照还能帮助解释为什么一个任务在重试后成功，以及抢占是否真的释放了目标资源。

### 2.12.2 worked example：扩容为什么没有带来吞吐提升

假设 8 卡任务的每步时间为 `1.2 s`，32 卡任务的每步时间为 `2.4 s`，每步有效 token 数分别为 `16K` 和 `48K`。虽然 32 卡的 step 更慢，但 token 吞吐仍可能从约 `13.3K/s` 提升到 `20K/s`。如果业务目标是缩短单次实验时间，它可能值得；如果目标是共享集群的单位 GPU 成本，则还要计算：

```math
\mathrm{tokens/GPU\text{-}s}
=\frac{\mathrm{tokens\ per\ step}}
 {\mathrm{GPU\ count}\times T_{\mathrm{step}}}
```

8 卡方案约为 `1.39K tokens/GPU-s`，32 卡方案约为 `0.625K tokens/GPU-s`。这说明“总吞吐增加”和“扩展效率变好”不是同一个结论。决策应同时报告 wall-clock、tokens/s、tokens/GPU-s、队列等待和失败重试成本。

### 2.12.3 故障演练要覆盖资源路径

最小演练矩阵至少包含：一张 GPU 降频、一条跨机链路丢包、对象存储部分读取、共享文件系统短暂不可用、任务被抢占、checkpoint manifest 损坏和租户配额在运行中变化。每次演练记录检测延迟、任务是否自动重试、重复计算 token、资源释放时间和最终恢复点。

如果故障发生在 checkpoint 提交前，平台应把任务标成“可重试但恢复点较旧”；如果 manifest 已提交而某个 shard 缺失，则不能把任务伪装成成功，必须进入 artifact 校验失败状态。恢复正确性和性能指标同等重要：一个恢复后 loss 正常但数据游标重复的任务，仍可能污染实验结论。

调度器的验收要同时覆盖准入、公平、拓扑、抢占和恢复：固定任务能否得到符合拓扑的资源；高优先级任务是否会让低优先级任务永久饥饿；抢占后是否能从完整 checkpoint 恢复；单机、交换机和存储故障时，任务是否进入可解释的状态。对每次调度决策保存请求资源、可用资源、策略版本、拒绝原因和最终分配。

硬件、网络、存储和调度共同决定任务的有效性能。分析问题时先画出数据和控制路径，再用时间、带宽、容量和队列公式建立粗模型，最后用 profiler、通信日志、存储指标和调度 trace 验证。

## 2.13 拓扑是资源的一部分

“有 32 张 GPU”不等于任何 32 张 GPU 都能提供相同性能。GPU 之间可能通过 NVLink、PCIe、不同 NUMA 节点或跨交换机连接；网络带宽、跳数和拥塞会直接影响 all-reduce、all-to-all、checkpoint 和参数广播。调度器如果只按卡数分配，可能把一个强通信任务放到最差拓扑上。

对任务 `j`，资源请求至少应包含数量、显存、互联要求、NUMA、网络域、存储亲和性和故障域。一个简单的通信时间模型为：

```math
T_{\mathrm{comm}}
\approx \alpha H+\frac{S}{B_{\mathrm{eff}}},
```

其中 `H` 是消息经过的跳数/阶段数，`S` 是通信量，`B_eff` 受拓扑、并发和拥塞影响。公式不能替代 NCCL 或网络 profiler，但能解释为什么增加 GPU 后 step time 反而上升。

## 2.14 网络、存储和计算的瓶颈会互相转移

训练启动时瓶颈可能是对象存储读取；数据缓存热起来后，瓶颈可能转移到 all-reduce；扩大 batch 后，显存和 checkpoint 写入成为限制。排查要把一个 step 拆成输入、计算、通信、同步和写盘，而不是看单一 GPU utilization。

例如 GPU 利用率低可能是数据读取慢，也可能是通信等待；网络带宽高可能是有效 all-reduce，也可能是 checkpoint 与训练争抢链路。需要同时查看 kernel timeline、NCCL 日志、文件系统吞吐、队列等待和任务 trace，并用同一时间窗口对齐。

## 2.15 Checkpoint 是存储协议而不是一个文件

checkpoint 写入应有临时前缀、分片清单、checksum、完成标记和原子提交。读取方只接受带完成标记且所有分片校验通过的 manifest。若直接覆盖 `latest`，训练中断或对象存储部分成功时，恢复逻辑可能读到混合版本。

设模型和优化器总字节数为 `S`，有效写带宽为 `B_w`，则下界是：

```math
T_{\mathrm{write}}\ge S/B_w.
```

实际时间还包括元数据、校验、重试和竞争。调度器抢占前应查询 manifest 状态和最近完整 step；只看训练进程报告的 step，可能把未完成 checkpoint 当作恢复点。

## 2.16 抢占、公平与碎片化

抢占能够提高高优先级任务响应，但会产生 checkpoint、重算、缓存冷启动和低优先级任务饥饿。公平性不能只按 GPU 小时分配，还要考虑任务已经等待多久、已消耗多少资源、是否可恢复、剩余工作量和租户配额。

资源碎片也会让“总空闲资源”失去意义。四张分散的 GPU 可能无法满足一个需要同机 NVLink 的四卡任务；空闲显存不一定能装下连续 page；一台故障域中的卡不能简单拼成高可用副本。调度器需要记录拒绝原因和资源快照，让用户知道是数量、拓扑、配额还是碎片造成等待。

## 2.17 硬件故障的可解释恢复

当 GPU 降频、链路丢包或存储短暂不可用时，系统要区分可重试、可恢复和不可恢复失败。无状态预处理可以重试；训练任务依赖 checkpoint；写入型工具或注册动作要先查执行状态；损坏的 artifact 不能无限重试。

故障演练至少记录：发现时间、隔离时间、资源释放时间、最近完整 checkpoint、重复计算 token、恢复后 loss/评估和人工介入。恢复快但重复读取错误数据的任务并不算成功。硬件和调度章节的重点，是把拓扑、带宽、存储一致性、抢占和状态恢复放进同一条因果链。

## 2.18 小结

训练基础设施的性能来自计算、显存、网络、存储、拓扑和调度的共同约束。容量规划要保留故障余量，调度要解释拒绝和抢占，checkpoint 要能校验和恢复；任何带宽或吞吐结论都必须绑定硬件、驱动和 workload，不能脱离系统条件传播。
