# 第七章：分布式训练入门

单卡训练能帮助你理解模型和训练循环，但大模型工程很快会遇到单卡装不下、训练太慢、数据太多的问题。分布式训练的目标是把计算、数据、参数、梯度或优化器状态拆到多张 GPU、多台机器上，让训练规模和速度突破单卡限制。

本章是入门章节，不追求覆盖所有 Megatron、DeepSpeed、ZeRO、FSDP 细节，而是先建立分布式训练的核心概念：rank、world size、process group、DDP、all-reduce、DistributedSampler、torchrun、FSDP 的基本直觉，以及常见 debug 方法。只要这些概念清楚，后续学习训练系统和大模型训练框架会容易很多。

## 0. 本章范围与资料

本章参考已核对 PyTorch 官方 `torch.distributed`、`DistributedDataParallel`、`torchrun` / elastic launch、`DistributedSampler`、collective communication、`all_reduce` 和 Fully Sharded Data Parallel 文档口径。

本章聚焦 PyTorch 分布式训练入门中最常用、也最容易被误解的内容：rank / local rank / world size、process group、DDP 梯度同步、all-reduce、torchrun 环境变量、DistributedSampler 数据切分、global batch size、DDP 与 DataParallel / FSDP 的边界、`no_sync()`、rank 0 checkpoint 和分布式 debug。

本章不展开 ZeRO / DeepSpeed、Megatron-LM、tensor parallel、pipeline parallel、sequence parallel、MoE expert parallel、NCCL 拓扑调优、RDMA / InfiniBand、分布式 checkpoint shard 格式或生产级集群调度。这些内容会在大模型训练系统、AI Infra 和性能优化章节中继续展开。

## 7.1 为什么需要分布式训练

单卡训练有两个主要限制：

1. 显存不够。
2. 速度不够。

显存不够时，一个 GPU 放不下模型参数、梯度、优化器状态和激活。速度不够时，即使能放下模型，训练一个 epoch 或一轮预训练也可能太慢。

分布式训练试图解决这些问题：

1. 数据并行：每张卡放一份模型，处理不同 batch，最后同步梯度。
2. 参数分片：把参数、梯度或优化器状态拆到不同卡上。
3. 张量并行：把单层大矩阵计算拆到多卡。
4. 流水线并行：把模型层切到多卡，像流水线一样执行。

本章重点先讲数据并行和 DDP，因为它是最常用、最容易入门的分布式训练方式。

分布式训练首先要回答两个不同问题：一是“多张卡能不能共同处理同一个训练任务”，二是“单卡放不下的状态能不能被拆开”。DDP 主要回答前一个问题：每个进程保留一份完整模型副本，处理不同数据并同步梯度；它不会自动把参数和 optimizer state 分摊到各卡。FSDP 等分片方案才进一步改变单卡常驻状态的组成。把这两类收益混在一起，是估算显存和吞吐时最容易犯的错误。

把两张卡想成两个同时解题的学生，可以先看清数据并行的收益和限制：两人各持有一份相同的模型，分别计算不同样本的梯度，再合并梯度；单步读到的样本变多，计算可以并行，但两人桌上的模型、梯度和优化器状态仍各有一份。若模型本身已经超过一张卡的容量，增加数据并行副本并不能解决“放不下”的问题。相反，张量并行会把某些矩阵运算切片，流水线并行会把层分给不同设备，FSDP 会分片训练状态；这些办法改变的是模型或状态如何跨设备放置，通信方式也随之不同。

这些并行方式可以组合，例如大模型训练可能同时使用数据并行和张量/流水线并行，但组合后的 rank 不再都承担同一种职责。本章先把最小数据并行单元讲透：一个 rank 负责一份模型副本和一组数据，梯度在指定进程组内同步。读者之后看到 TP、PP 或混合并行时，可以继续追问“哪些进程共享哪组参数、哪种状态、在哪个边界通信”，不必把所有多卡都误称为 DDP。

### 7.1.1 关键公式与分布式调试速查

第一，`rank`、`local_rank` 和机器编号的关系可以粗略写成：

~~~math
r = r_{\mathrm{node}} W_{\mathrm{local}} + r_{\mathrm{local}}
~~~

其中 `r` 是全局 rank，`r_node` 是节点编号，`W_local` 是每个节点启动的进程数，`r_local` 是本机进程编号。该乘法关系假设各节点的本地进程数一致；实际启动后以 `torchrun` 设置的 `RANK`、`LOCAL_RANK` 和 `WORLD_SIZE` 为准，不要在弹性或非均匀拓扑里仅凭 GPU 数自行推算 rank。

第二，DDP 数据并行的梯度同步可以写成：

~~~math
\bar{g}_t=\frac{1}{W}\sum_{r=0}^{W-1} g_{t,r}
~~~

其中 `g_t,r` 是第 `r` 个 rank 在第 `t` 次更新前得到的本地梯度，`\bar{g}_t` 是 all-reduce 后每个 rank 都拿到的平均梯度。

第三，每个 rank 用同一个平均梯度更新参数：

~~~math
\theta_{t+1}=\theta_t-\eta \bar{g}_t
~~~

因此只要初始参数一致、梯度同步一致、optimizer step 顺序一致，各 rank 的参数会保持一致。

第四，global batch size 是：

~~~math
B_{\mathrm{global}}=B_{\mathrm{device}}\cdot W\cdot A
~~~

其中 `B_device` 是每个 rank 的 micro-batch size，`W` 是 world size，`A` 是 gradient accumulation steps。从单卡切到多卡时，如果每卡 batch 不变，global batch 会变大，学习率、warmup、训练步数和日志统计都要重新核对。

第五，在样本数可整除或 sampler 丢尾的 map-style 数据集里，DistributedSampler 让不同 rank 看到不重叠的索引子集：

~~~math
I_r \cap I_s=\varnothing,\quad r\ne s
~~~

默认补齐时，为了让各 rank 等长，尾部可能重复样本，因此集合不一定互斥；不丢样本与完全不重复也不能同时保证。真实实现还要处理 shuffle、补齐或 `drop_last`。

第六，DDP 单卡状态显存不因 world size 自动下降：

~~~math
M_{\mathrm{DDP,rank}}\approx M_{\mathrm{param}}+M_{\mathrm{grad}}+M_{\mathrm{opt}}+M_{\mathrm{act}}
~~~

DDP 主要提升吞吐；如果单卡装不下完整参数、梯度和 optimizer state，需要进一步考虑 FSDP / ZeRO 等分片方法。

第七，梯度累积配合 `no_sync()` 的通信次数可以近似理解为：

~~~math
C_{\mathrm{sync,no\_sync}}\approx \frac{C_{\mathrm{sync,naive}}}{A}
~~~

也就是 `A` 个 micro-step 只在最后一次同步，而不是每个 micro-step 都 all-reduce。

这些公式默认了一个重要前提：各 rank 的 loss reduction 和有效样本数相同。若 rank 0 处理 100 个有效 token、rank 1 只处理 50 个有效 token，而每个 rank 先算本地 mean loss 再 all-reduce 梯度，得到的往往是“两个 rank 等权的平均”，不一定是 150 个 token 的全局平均。更严格的实现需要同步 `loss_sum` 和 `valid_count`，并按全局分母构造梯度，或通过固定长度 packing / 丢弃不完整 batch 让各 rank 的监督项一致。

同样，`B_global` 是样本数口径；语言模型更适合同时记录：

~~~math
T_{\mathrm{global}}=\sum_{r=0}^{W-1}\sum_{k=1}^{A} n_{r,k},
~~~

其中 `n_{r,k}` 是 rank `r` 在第 `k` 个 micro-step 中的有效 token 数。吞吐和 loss 聚合都不应把 padding token 当成有效工作量。

### 7.2 rank、local rank 和 world size

分布式训练里最先要理解几个概念。

#### 7.2.1 world size

`world_size` 表示总进程数。通常一个 GPU 对应一个训练进程。

如果一台机器有 8 张 GPU，并且每张 GPU 一个进程：

```text
world_size = 8
```

如果 2 台机器，每台 8 张 GPU：

```text
world_size = 16
```

#### 7.2.2 rank

`rank` 是全局进程编号，范围是：

```text
0, 1, ..., world_size - 1
```

通常 `rank=0` 负责打印日志、保存 checkpoint、汇总指标等，避免所有进程重复写文件。

#### 7.2.3 local rank

`local_rank` 是当前机器内的 GPU 编号。

单机 8 卡时，local rank 通常是：

```text
0, 1, ..., 7
```

训练时通常用它设置当前进程使用哪张 GPU：

```python
torch.cuda.set_device(local_rank)
device = torch.device("cuda", local_rank)
```

核心区别：

1. `rank` 是全局编号。
2. `local_rank` 是本机编号。
3. `world_size` 是总进程数。

在多机环境中，`rank` 不是 GPU 编号的简单别名，而是整个 process group 内的唯一进程身份；`local_rank` 只在当前节点范围内有意义。一个节点上进程数、可见 GPU 数和 `LOCAL_RANK` 不一致时，可能出现两个进程绑定同一设备，或某些设备根本没有进程。启动后应把 `RANK`、`LOCAL_RANK`、`WORLD_SIZE`、hostname 和 `torch.cuda.current_device()` 一起记录，不能只打印 local rank。

例如两台同构机器各启动 4 个 worker，`W_local=4`：节点 0 的 local rank 0–3 对应全局 rank 0–3；节点 1 的 local rank 0–3 对应全局 rank 4–7。节点 1 上 `LOCAL_RANK=0` 的进程因而是 `RANK=4`，不是另一个 `RANK=0`。一个进程通常绑定一个设备，所以设备编号要按当前节点可见设备解释；容器设置了 `CUDA_VISIBLE_DEVICES` 后，local rank 0 指的是进程看到的第 0 张卡，不一定是宿主机物理编号 0。

### 7.3 process group 是什么

process group 可以理解为一组参与通信的进程。

初始化分布式环境：

```python
import torch.distributed as dist

dist.init_process_group(backend="nccl")
```

> 代码片段，静态审阅，未运行；需要自定义模型/数据对象及 PyTorch 2.15 多进程环境。

常见 backend：

1. `nccl`：GPU 训练最常用。
2. `gloo`：CPU 或某些调试场景常用。

初始化后，进程之间就可以执行通信操作，例如 all-reduce、broadcast、barrier。

训练结束时通常销毁：

```python
dist.destroy_process_group()
```

collective 通信有一个硬约束：同一个 group 中的进程必须以相同顺序参与匹配的 collective。一个 rank 进入 `all_reduce` 而另一个 rank 进入 `barrier`，即使两边代码都没有异常，也可能永久等待。`barrier()` 不是“让所有代码自动同步”的万能锁，它只是一个 collective；加入新的 barrier 必须保证所有 rank 都会执行。

进程组回答的是“这次通信由谁共同参加”，不是“谁负责算模型”。默认进程组包含本次 job 的所有 worker；更复杂的并行会创建子组，让一部分 rank 在组内归约或交换张量。每个 rank 必须用一致的顺序创建这些组，并按相同顺序调用对应 collective。某个 rank 走了提前 return、某个 batch 触发了独有异常，或者条件分支让一部分 rank 跳过某次通信，其他 rank 往往只能等到超时才暴露问题。

还要区分阻塞位置和程序状态：`all_reduce` 返回通常代表通信结果可供后续使用；它不意味着整个训练脚本中任意 rank 的 Python 代码都已经走到同一行。排查时应记录“谁在哪个组、哪个 step、哪个 collective 前后”，而不是靠在可疑位置不断插入 `barrier()`。额外 barrier 自己也要求所有 rank 按同序参与，放在一个原本不一致的条件分支里只会制造第二个等待点。

GPU 训练通常选 NCCL，CPU 或部分调试路径可选 Gloo；backend 和设备必须匹配。对于 NCCL，先让每个进程设置自己的当前 GPU，再初始化进程组和构造 DDP，可避免未绑定设备时通信库选错设备。这个顺序也让第一次报错时能从日志直接看到 local rank 到设备的映射。进程组、collective 和 shutdown 的版本边界见 [PyTorch 2.15 distributed 文档](https://docs.pytorch.org/docs/2.15/distributed.html)。

## 7.4 数据并行的核心直觉

数据并行的流程：

1. 每张 GPU 上放一份相同模型。
2. 每张 GPU 处理不同 mini-batch。
3. 每张 GPU 独立 forward 和 backward。
4. backward 后每张 GPU 得到一份梯度。
5. 通过 all-reduce 对梯度求平均。
6. 每张 GPU 用相同平均梯度更新参数。

这样更新后，每张 GPU 的模型参数仍然保持一致。

如果没有梯度同步，每张 GPU 会基于不同数据更新出不同模型，训练就不再是一个统一模型。

可把一次 DDP step 看成一个有明确先后顺序的数据流：先由 sampler/loader 给每个 rank 提供该 rank 的 batch；每个进程把 batch 移到本地 device，独立执行 forward，算出本地 loss；Autograd 从 loss 反向传播，在梯度 ready 时通知 DDP reducer；reducer 在进程组里归约对应 bucket；当 backward 完成时，参数 `.grad` 已带有跨 rank 的结果；最后每个进程各自调用 optimizer。DDP 不会替你搬运 batch，也不会替你调用 optimizer。说“DDP 在 backward 过程中自动同步”是对的，但准确位置是梯度归约而不是 optimizer step。

下表按执行次序把 rank 本地状态和跨 rank 动作分开；读日志时可沿着“batch 到达 → 梯度就绪 → 参数更新”检查哪一步没有完成。

| 阶段 | 每个 rank 本地执行 | 跨 rank 机制 | 结束时应成立的状态 |
| --- | --- | --- | --- |
| 输入与 forward | 读取自己的 batch 并计算本地 loss | sampler 分数据；DDP 可能同步 buffer | 输入不同，初始模型一致 |
| backward | Autograd 计算本地参数梯度 | reducer 按 bucket 做梯度 all-reduce | 各 rank 得到同一归约梯度 |
| optimizer step | 各自更新参数和 optimizer state | 通常没有额外参数广播 | 配置一致时副本保持相同 |
| 日志与验证 | 计算本地 loss sum、token 数等 | 对指标分子/分母分别聚合 | rank 0 输出的是全局口径 |

模型应在每个 rank 上先创建并放到本地 GPU，再被 DDP 包装；默认初始化同步会让权重起点一致。之后各 rank 必须以相同的参数注册顺序运行。训练 loop 中 `loss.backward()` 才触发梯度 reducer；若只调用 `torch.autograd.grad()` 得到局部返回值、没有把梯度累积到参数 `.grad`，就不符合标准 DDP reducer 的路径。运行日志最好同时输出 `rank`、当前 step、batch 的样本数/有效 token 数、本地 loss 分子分母、每个 group 的 collective 状态和 optimizer step 计数。这样一旦 rank 间分叉，能判断是输入不同、梯度不同还是更新时机不同。

梯度归约同步的是梯度张量，不是输入 batch，也不会把 rank 0 的数据广播给其他 rank。若四个 rank 错误地读取相同样本，DDP 仍可能正常完成 all-reduce，只是四份相同数据被重复计算，名义 global batch 变大而有效样本数没有增加。相反，数据正确分片但 rank 的 loss mask 不一致，也会让得到的平均梯度对应另一种权重目标。于是 DDP 正常运行只证明通信调用完成，不证明数据语义正确；要把样本 id、有效目标数和梯度统计一起审计。

### 7.4.1 “等价大 batch”的条件

DDP 常被解释为把 `W` 个本地 batch 拼成一个 global batch，但这只在若干条件下近似成立：初始参数相同、每个 rank 的有效监督项权重一致、梯度 reduction 口径一致、随机层的影响可接受、optimizer 在同步后同时 step。若每个 rank 的 batch size、有效 token 数或 loss denominator 不同，all-reduce mean 只是 rank mean 的平均，不一定是样本/ token mean。

举一个 token loss 的例子。rank 0 有 4 个 token、平均 loss 为 2；rank 1 有 16 个 token、平均 loss 为 1。按 rank 平均得到 `1.5`，按 token 汇总得到：

~~~math
L_{\mathrm{global}}=\frac{4\times2+16\times1}{4+16}=1.2.
~~~

如果训练循环只对本地 mean loss 做 DDP 梯度同步，它优化的是前一种目标。工程上要么保证每个 rank 的有效 token 数相等，要么让模型返回 unreduced loss 并用全局 token 数做归一化；分布式指标也必须使用同样的分母。

再用一个可以手算的标量模型检查“等价大 batch”到底依赖什么。令模型只有一个参数 `θ`，单个样本的预测为 `θx`，损失定义为 `0.5(θx-y)^2`，因此梯度为 `(θx-y)x`。取当前 `θ=2`，并令所有样本的 `x=1`：rank 0 收到标签 `[0, 2]`，两个样本的梯度是 `[2, 0]`，本地 mean gradient 为 `1`；rank 1 收到标签 `[1, 3]`，梯度是 `[1, -1]`，本地 mean gradient 为 `0`。DDP 对两个 rank 的本地均值求平均，得到 `(1+0)/2=0.5`。直接把四个样本放在一起求平均也得到 `(2+0+1-1)/4=0.5`。若学习率 `η=0.1`，这一步之后参数为 `θ'=2-0.1×0.5=1.95`。中间的样本梯度、本地均值、跨 rank 平均和参数更新都能逐项复算。

这个等价性要求两个 rank 各自对同样数量的监督项取 mean。如果 rank 0 的本地 batch 含 2 个有效 token、rank 1 含 6 个，先在 rank 内求 token mean，再让 DDP 按 rank 等权平均，就会给每个 rank 一半权重，短 batch 中单个 token 的权重更大。若两边的 token loss sum 分别为 `S_0`、`S_1`，有效 token 数分别为 `n_0`、`n_1`，目标应是 `(S_0+S_1)/(n_0+n_1)`。在默认按 `W` 个 rank 平均梯度的 DDP 中，各 rank 对自己的 `loss_sum` 做 backward 前可乘 `W/(n_0+n_1)`，让通信后的梯度等于全局 token mean 的梯度；使用自定义 communication hook、其他并行组或 trainer 自动缩放时，要按实际 reduction 重新推导。第五章已讲过单进程窗口分母，本章把同一分母扩展到跨 rank。

DDP 构造时默认检查各 rank 的参数形状并同步初始参数；训练过程中不会在每一步广播参数。每个 rank 在同一初始权重上计算梯度，DDP 把梯度归约到相同结果，各 rank 再运行相同 optimizer 更新，参数才会保持一致。若某 rank 额外做了一次 `optimizer.step()`、使用了不同学习率，或参数顺序/结构在构造前不一致，梯度通信正常也不能保证训练状态相同。像 BatchNorm 这类 buffer 另有同步规则：DDP 默认在 forward 前把 rank 0 的 buffer 广播给其他副本，但这不等于把每个 rank 的 batch statistics 合并；需要全局 batch statistics 时应评估 SyncBatchNorm，或确认模型使用的归一化层是否依赖跨样本统计。[PyTorch 2.15 DDP 文档](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html)列出了初始化同步、参数注册顺序和 buffer 同步边界。

### 7.5 all-reduce 是什么

all-reduce 是分布式训练中最核心的通信操作之一。

假设有 4 张 GPU，每张 GPU 上某个参数的梯度分别是：

```text
g0, g1, g2, g3
```

all-reduce sum 后，每张 GPU 都得到：

```text
g0 + g1 + g2 + g3
```

如果要平均梯度，就再除以 `world_size`。

DDP 内部会自动处理这个过程。用户通常不需要手写 all-reduce 梯度，但要理解它的代价：通信开销会随着参数量、网络带宽、GPU 拓扑和同步频率变化。

从时间上看，一次 all-reduce 不只是“除以 world size”这一行数学操作。它需要把梯度 bucket 在进程之间传输、归约并把结果分发回来。粗略地说，通信时间同时受消息大小、链路带宽、拓扑和 collective 算法影响；小 bucket 可能带来更多启动开销，大 bucket 又可能延迟通信与 backward 重叠。DDP 的 bucket 和 autograd hook 正是为了在梯度逐步 ready 时尽早发起通信。

### 7.6 DDP 的基本用法

PyTorch 推荐使用 DistributedDataParallel，也就是 DDP。

基本结构：

```python
import os
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP


def setup_distributed():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    dist.init_process_group(backend="nccl")
    return local_rank


local_rank = setup_distributed()
device = torch.device("cuda", local_rank)

model = MyModel().to(device)
model = DDP(model, device_ids=[local_rank])
```

> 代码片段，静态审阅，未运行；需要自定义模型/数据对象及 PyTorch 2.15 多进程环境。

这里的 `device_ids=[local_rank]` 适用于每个 CUDA 进程管理一张 GPU 的常见模式；每个进程都要绑定自己的本地卡。模型必须在构造 DDP 之前创建好全部参数和 buffer，包装后不要再动态加层或替换参数，否则 reducer 注册的梯度路径会与模型当前结构脱节。若各 rank 在不同条件分支中创建不同结构，或者参数登记顺序不一致，常见结果可能是构造校验失败、梯度 bucket 对不上或某次 backward 等不到匹配通信。

DDP 训练的“平均梯度”也要和损失函数约定一起读。`CrossEntropyLoss(reduction="mean")` 已经在每个 rank 内除以本地 target 数；DDP 再把 rank 的梯度平均。若 rank 内 target 数相同，这等价于把各 rank 的 target 合在一起做 mean；若不相同，就要对齐全局有效项分母。相反，若本地返回的是 `reduction="sum"` 的 loss，直接让 DDP 平均 rank 梯度会额外除以 world size，相对全局样本总和的梯度尺度不同。不要只看 loss 标量看起来在 `[0, 1]` 就判断缩放正确，应核对 `reduction`、有效项计数和 DDP reduction。

训练循环中：

```python
for batch in train_loader:
    batch = move_to_device(batch, device)
    optimizer.zero_grad(set_to_none=True)
    outputs = model(**batch)
    loss = outputs["loss"]
    loss.backward()
    optimizer.step()
```

DDP 会在 backward 过程中自动同步梯度。

保存 checkpoint 时常用：


## 7.7 torchrun 启动训练

现代 PyTorch 常用 `torchrun` 启动分布式训练。它是 worker launcher：按每个节点的进程数启动子进程，准备 rendezvous（让各 worker 找到同一训练组的会合点），并给训练脚本注入 rank 和通信所需的环境变量；它不会替应用选择模型、切分数据或保存检查点。[PyTorch 2.15 `torchrun` 文档](https://docs.pytorch.org/docs/2.15/elastic/run.html)列出本地/全局 rank 与 rendezvous 参数。

单机 4 卡：

```bash
torchrun --standalone --nnodes=1 --nproc-per-node=4 train.py
```

> 启动命令，静态审阅，未运行；需在声明的 torchrun、CUDA 与集群环境验证。

`torchrun` 会为每个进程设置环境变量，例如：

1. `RANK`
2. `LOCAL_RANK`
3. `WORLD_SIZE`

固定规模、每个节点进程数相同的作业中，通常有 `WORLD_SIZE = 节点数 × 每节点进程数`。`LOCAL_WORLD_SIZE` 表示本节点 worker 数；多机 rendezvous 还需要各节点共同使用同一 `rdzv_id`、`rdzv_endpoint` 和进程数配置。启动配置不一致时，worker 可能一直等待其他成员到达，也可能进入了另一个作业的会合组。弹性重启还可能改变 rank 编号和 world size，因此 rank 应被当成当前 worker group 内的身份，而不是持久的样本或检查点 ID。

训练脚本通过这些变量初始化分布式环境。

读取示例：

```python
rank = int(os.environ["RANK"])
local_rank = int(os.environ["LOCAL_RANK"])
world_size = int(os.environ["WORLD_SIZE"])
```

程序启动后先核对一个小表：节点名、`RANK`、`LOCAL_RANK`、`LOCAL_WORLD_SIZE`、`WORLD_SIZE`、本地当前设备、`MASTER_ADDR` 和 `MASTER_PORT`。单机 4 卡的 rank 应为 0–3，local rank 也应各不相同；两机每机 4 卡时 world size 应为 8，每台机器都各自出现 local rank 0–3。若 world size 对不上，先检查 launcher 参数和 rendezvous；若 rank 对了但设备重复，检查 `CUDA_VISIBLE_DEVICES`、每节点进程数和设置 device 的代码。这样可以在第一次训练前把“脚本绑定错误”与“collective 通信故障”分开。

如果以两机四卡为例启动固定规模作业，每台机器各执行一次 launcher，双方都声明相同的节点总数、每节点进程数、rendezvous backend、endpoint 和 job id；各自的节点身份不同，但加入的是同一个 worker group。实际启动前可先用无训练计算的短脚本打印这些环境变量，并确认 8 个全局 rank 唯一且连续、两个节点各自有 4 个 local rank。若两个独立 job 共用了同一会合 id/端点，它们可能误加入同一组；若每台机器各自随意挑 endpoint，则 worker 永远等不到伙伴。这类启动错误应在进程组初始化阶段排查，不要用修改模型 batch 或 DDP 参数来掩盖。

不要手动让多个进程抢同一张 GPU。最常见的正确方式是：每个进程绑定一个 `local_rank` 对应的 GPU。

多机启动还需要 rendezvous 地址、端口、节点总数和当前节点编号。`torchrun` 注入环境变量并不等于网络已经可用；如果 master 地址不可达、端口被占用或节点的 `WORLD_SIZE` 不一致，进程可能在初始化阶段等待。生产脚本应把启动配置、PyTorch/CUDA/NCCL 版本和可见设备写入日志，方便把“代码问题”和“集群启动问题”分开。

### 7.8 DistributedSampler

DDP 里每个进程应该看到不同数据子集。否则每张卡都训练同样样本，就浪费了多卡。

使用 `DistributedSampler`：

```python
from torch.utils.data import DataLoader, DistributedSampler

sampler = DistributedSampler(
    dataset,
    shuffle=True,
    seed=base_seed,  # 所有 rank 使用相同 seed。
    drop_last=False,  # 这是 sampler 的尾部策略。
)
loader = DataLoader(
    dataset,
    batch_size=batch_size,
    sampler=sampler,
    drop_last=False,  # 这是每个 rank 的尾 batch 策略。
    num_workers=4,
)
```

注意：使用 sampler 时通常不要再设置 `shuffle=True` 给 DataLoader，因为 shuffle 由 sampler 管理。

每个 epoch 要调用：

```python
sampler.set_epoch(epoch)
```

> 代码片段，静态审阅，未运行；需要自定义模型/数据对象及 PyTorch 2.15 多进程环境。

`DistributedSampler` 还要处理数据量不能被 `world_size` 整除的情况。为了让每个 rank 拥有相同数量的索引，默认策略会在打乱后的索引序列中补入重复样本；sampler 的 `drop_last=True` 则截掉序列尾部，使样本数可整除。设样本数为 `N`、rank 数为 `W`：

~~~math
N_{\mathrm{per\ rank}}=
\begin{cases}
\lfloor N/W\rfloor, & \text{sampler 尾部截断策略}\\
\lceil N/W\rceil, & \text{补齐到等长 rank 的口径}
\end{cases}
~~~

这不是实现细节而是数据权重选择。若最后一批样本具有特殊时间分布或高风险标签，补样本和丢样本会改变 epoch 的经验分布。应记录实际消费的样本数、重复 id 和丢弃 id；对流式数据集，`DistributedSampler` 不会自动为你完成跨 rank/worker 分片。

看一个小的索引账本。令 `N=10`、`W=3`、关闭 shuffle，数据索引为 `0…9`。sampler 默认补齐时每 rank 拿 4 个位置，补入 `0、1` 后，按 rank 交错分配可得到 rank 0：`[0,3,6,9]`，rank 1：`[1,4,7,0]`，rank 2：`[2,5,8,1]`。共有 12 个 index 位置，重复了 2 个，但原数据集 10 个 id 至少都出现一次。sampler `drop_last=True` 时先截去索引 `9`，三 rank 分别拿 3 个位置，共消费 9 个原样本。若保持默认 sampler、再让 `DataLoader(batch_size=3, drop_last=True)`，它是在每个 rank 收到的 4 个位置中各丢掉最后 1 个位置；这和 sampler 截断不是同一层操作，留下的数据也不同。小数据集上应该把最终 id 列出来，不能只凭两个参数都叫 `drop_last` 就认为它们等价。

上述 sampler 只适用于长度稳定、按索引读取的 map-style dataset。若使用 `IterableDataset` 或自定义流式输入，DDP 不会自动拆分 iterator；还要把 rank 和 DataLoader worker id 组成全局分片身份，避免每个 rank 内无重复、跨 rank 却读到同一 shard。反过来，过度切分也会使某些 rank 更早耗尽数据。数据分片必须同时检查每个 rank 的步数、实际样本 id、有效 token 数和 epoch 末尾处理。

否则每个 epoch 的 shuffle 顺序可能一样。

完整结构：

```python
for epoch in range(num_epochs):
    sampler.set_epoch(epoch)
    for batch in loader:
        ...
```

> 代码片段，静态审阅，未运行；需要自定义模型/数据对象及 PyTorch 2.15 多进程环境。

同一分布式组里的所有 rank 应使用相同的 sampler `seed`，再通过不同 rank 参数拿到同一全局排列的不同位置；如果每个 rank 各自使用不同 seed，它们会从不同排列中切片，索引交集就可能变大。`set_epoch(epoch)` 把 epoch 混入确定性 shuffle，使“同一个 epoch 各 rank 对齐、不同 epoch 顺序变化”同时成立。恢复训练时要保存 epoch 和已消费位置；只恢复一个 seed 而把 iterator 从头开始，会重复训练已消费的样本。该用法和 sampler `drop_last` 定义见 [PyTorch 2.15 `DistributedSampler` 文档](https://docs.pytorch.org/docs/2.15/data.html#torch.utils.data.distributed.DistributedSampler)。

如果 `DataLoader` 设置了 `drop_last=True`，它丢弃的是每个 rank 的尾 batch，而不是把全局数据先拼成一个大 batch 再丢尾。默认的 `DistributedSampler` 会令各 rank 索引数量一致，配合同一 `batch_size` 后通常能保持迭代次数一致；自定义数据源则必须自己保证相同步数，或明确使用 DDP 的 uneven-input 处理机制。若一个 rank 提前离开训练循环，其他 rank 可能在下一次 all-reduce 等待。对于 BatchNorm 一类依赖本地 batch 统计的模块，多卡下还要另行考虑 `SyncBatchNorm` 或模型是否本来就使用 LayerNorm；DDP 不会自动修正所有跨卡统计。

### 7.9 global batch size 怎么算

分布式训练里要区分：

1. 每卡 batch size。
2. world size。
3. gradient accumulation steps。
4. global batch size。

公式：

```text
global_batch_size = per_device_batch_size * world_size * accumulation_steps
```

例如：

```text
per_device_batch_size = 4
world_size = 8
accumulation_steps = 2
global_batch_size = 4 * 8 * 2 = 64
```

这会影响学习率、warmup steps、训练步数和日志统计。

常见错误：从单卡切到 8 卡后，没有意识到 global batch size 变大，导致优化行为变化。

例如每个 rank 的 micro-batch 是 2 个样本、`W=4`、累积 3 次，在每 rank 每步样本数相同且窗口完整时，一个 optimizer update 覆盖 `2×4×3=24` 个样本。若改成 8 个 rank，其他设置不动，global batch 变成 48；即使每卡的代码完全没变，每个参数更新看到的数据量已经翻倍。比较单卡与多卡实验时要先决定要保持什么不变：global batch、每次更新的 token 数、训练 token 总量还是墙钟时间。不同目标对应不同 micro-batch、累积次数、学习率 schedule 和 step 数，不能只把 GPU 数写进配置后声称实验等价。

对语言模型，样本数只是名义口径。设本轮各 rank、各 micro-step 的有效目标 token 数为 `n_{r,k}`，则实际参与 loss 的总 token 是 `T_global=Σ_rΣ_k n_{r,k}`。padding 长度相同不代表有效 token 数相同；packing 或变长样本会让 token 数随 rank 变化。global batch 用来说明样本组织，global valid tokens 更直接决定 token-mean loss 的分母和每秒有效工作量。窗口末尾若不足 `A` 个 micro-step，实际样本数还要用真实窗口长度计算，不能继续套满窗口的名义公式。

再比较两种配置：目标是每次 update 覆盖 64 个等长样本，配置甲为 `W=2`、每 rank batch 4、累积 `A=8`，得到 `2×4×8=64`；配置乙为 `W=4`、每 rank batch 4、累积 `A=4`，仍得到 64。若每 rank batch 都是 4 且累积不变，把 rank 从 2 增到 4 则 global batch 直接翻倍为 128。即使名义 global batch 一样，两种配置的同步次数、每卡 activation memory、输入 worker 数和设备拓扑仍不同，所以还要测吞吐与稳定性，不能只用一个乘积断言两次训练完全等价。

尾窗也会改变真实更新大小。假设每个 rank 一个 epoch 有 10 个 micro-batch，累积 `A=4`，每个 micro-batch 有 2 个样本；各 rank 会做 3 次 optimizer update，窗口包含 `4、4、2` 个 micro-step。若 `W=3`，这三次 update 的名义样本数分别为 `24、24、12`。日志若只显示固定的 `global_batch=24`，最后一次就报大了；更稳妥的记录是每个 optimizer step 的实际样本数、有效 token 数和累计步数。训练总量对齐时也要数见过的 token，而不只是 scheduler 走过多少 step。

## 7.10 DDP 和 DataParallel 的区别

PyTorch 早期有 `DataParallel`，但现在训练更推荐 DDP。

区别：

1. `DataParallel` 通常单进程多线程，主卡负担重。
2. DDP 是多进程，每个 GPU 一个进程，性能和扩展性更好。
3. DDP 梯度同步更高效。
4. DDP 更适合多机多卡。

`DataParallel` 的主进程需要负责 scatter、gather 和部分调度，容易让主卡成为瓶颈；DDP 让每个进程独立驱动一张卡，通信通过 process group 完成。选择 DDP 也不是保证线性加速：有效吞吐还取决于通信/计算比、输入管线、global batch、负载均衡和模型是否存在跨 rank 分支。

二者的程序组织不同。`DataParallel` 通常把一个 Python module 包在单个进程里，在一次 forward 中把输入切到多张卡，再把输出汇回主卡；它的调度、输出汇总和梯度处理集中在一个进程。DDP 则由 launcher 启动多个独立 Python 进程，每个进程各有自己的模型实例和数据 batch，梯度通过通信后端同步。DDP 多了进程启动、rank 配置、数据切分和日志聚合的责任，但单卡的 forward/backward 路径更直接，也能扩展到多机。选择时先看训练程序和故障排查是否需要独立进程、模型是否适合复制，再测目标模型上的 step time；框架文档的普遍推荐不等于你的 workload 一定能加速。

### 7.11 DDP 的通信时机

DDP 不是等所有 backward 完成后才一次性同步全部梯度。它会把参数分成 bucket，并在某些梯度 ready 后触发通信。

这样可以让通信和反向计算重叠：

1. 后面层的梯度先算出来。
2. DDP 开始同步这些梯度 bucket。
3. 同时 backward 继续计算前面层梯度。

这叫 communication overlap。

理解这个机制有助于解释：

1. 为什么 DDP 比朴素手写同步更高效。
2. 为什么参数使用路径不一致会导致卡住。
3. 为什么梯度同步与 autograd hook 有关。

如果某些参数在一个 rank 上参与了 forward，而在另一个 rank 上没有参与，梯度 ready 的顺序和 bucket 状态就可能不同。静态图、固定分支和一致的输入 shape 更容易获得稳定的 overlap；动态路由、条件退出和 MoE 类稀疏路径则需要额外处理 unused parameters、通信顺序和负载不均。`find_unused_parameters=True` 可以帮助某些动态图场景完成遍历，但会增加 autograd 开销，也不能修复 rank 之间不一致的业务逻辑。

可以用一个两层网络观察重叠发生的时点。反向传播先算出离 loss 最近一层的梯度；当该层所在 bucket 的所有梯度都 ready，reducer 就能在通信流上开始 all-reduce。与此同时，Autograd 仍在计算更早层的梯度。若通信在计算结束前完成，这段时间被计算隐藏；若网络慢、bucket 大或模型很小，backward 结束后仍有等待，step time 就会暴露通信尾部。于是“梯度同步在 backward 内发生”并不代表通信免费，它只说明存在可重叠的窗口。

DDP 按注册顺序组织 bucket，bucket 过大时可能要等更多参数梯度 ready 才开始通信；bucket 过小则可能增加 collective 启动次数。固定 bucket 参数不是通用提速按钮，动态计算图、不同参数使用路径或不同输入 shape 都会影响何时 ready。调优时要先测稳态 backward 与通信时间，再看 bucket 统计和各 rank 负载是否一致；如果 rank 3 的序列更长导致它晚结束，其他 rank 的等待时间并不能靠改 bucket 完全消除。

### 7.12 梯度累积下的 no_sync

梯度累积时，如果每个 micro-step 都同步梯度，会为一次 optimizer update 重复同步中间梯度。将 `A` 个 micro-step 累成一次更新时，普通 DDP 在每个 backward 都触发 reducer；`no_sync()` 让前 `A-1` 次只保留本地梯度，最后一次 backward 才把本窗口的梯度一起同步。它减少的是窗口内重复的梯度通信，不会改变需要执行的 forward/backward 次数，也不会自动扩大有效 batch 或修正 loss 分母。

DDP 提供 `no_sync()`：

```python
from contextlib import nullcontext


total_micro_steps = len(loader)  # 需要 DataLoader 能报告长度。
optimizer.zero_grad(set_to_none=True)
for step, batch in enumerate(loader):
    window_start = (step // accum_steps) * accum_steps
    window_size = min(accum_steps, total_micro_steps - window_start)
    should_sync = (
        (step + 1) % accum_steps == 0
        or (step + 1) == total_micro_steps
    )

    if should_sync:
        context = nullcontext()
    else:
        context = model.no_sync()

    with context:
        outputs = model(**batch)
        loss = outputs["loss"] / window_size
        loss.backward()

    if should_sync:
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```

> 代码片段，静态审阅，未运行；需要自定义模型/数据对象及 PyTorch 2.15 多进程环境。

这段教学片段假设各 rank 的 `loader` 长度一致，且一个 micro-batch 的 loss 是本地样本/目标的 mean、每个 micro-batch 的有效监督项数也相同。因此每个 micro-loss 除以窗口内 micro-step 数，就能得到窗口 mean；最后不足 `accum_steps` 时，`window_size` 使用剩余步数。以 `A=3`、epoch 内 5 个 micro-step 为例，前 3 步组成第一窗，每步 loss 梯度权重为 `1/3`；后 2 步组成尾窗，每步权重为 `1/2`。否则若尾窗仍除以 3，更新梯度就会缩成正确值的 `2/3`。对变长语言模型，如果每步的有效 token 数不等，就要按该窗口跨 rank 的 token 总数归一化，而不是对 micro-step 的 mean loss 再取平均；分母的推导见本章 7.4.1 和第五章训练循环。

这里 `no_sync()` 会跳过当前 micro-step 的梯度同步，只在真正更新前同步一次。forward 和 backward 都必须处于上下文中；在上下文内累积的梯度会在离开它后的同步 forward/backward 中一起参与归约，详见 [PyTorch 2.15 DDP `no_sync()`](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html#torch.nn.parallel.DistributedDataParallel.no_sync)。

`no_sync()` 只影响 DDP 梯度通信，不会自动改变 loss 的归一化，也不会替你处理最后一个不完整窗口。若 `accum_steps=4` 但 epoch 最后只有 2 个 micro-batch，应按实际窗口大小或有效 token 数缩放；若忘记缩放，最后一次更新会偏小。正确的通信逻辑是“窗口内不通信、窗口末通信并 step”，而不是“把所有 backward 都放到 no_sync 中”。

使用时还要保证 forward 也在 `no_sync()` 上下文中；只包住 backward 或在上下文外产生梯度，会让预期的通信抑制失效。遇到性能异常时记录每个 optimizer step 的 all-reduce 次数和窗口 token 数，不能只根据代码缩进推断通信已经减少。

把通信量也换成可读的单位：一个含 16M 个 FP32 参数的模型，一份 dense gradient 有 `16M×4 bytes=64 MB`，约 `61 MiB`。若 4 个 micro-step 每次都同步，逻辑上每 rank 会对这份梯度张量做 4 次同步；若前三步处于 `no_sync()`，本窗口只同步一次。实际网络传输字节还取决于 collective 算法、bucket、拓扑和通信是否与计算重叠，所以这个数只用于比较重复同步的次数，不是 NVLink 或网络的带宽预测。测量时应将通信次数、有效 token/s、每步墙钟时间和显存一起记录，避免只看到 all-reduce 次数下降就认为训练更快。

将测量结果压缩成一个小例子：假设同一个固定 global batch 和训练 token 总量，单卡平均 update 用时 120 ms，四卡 DDP 用时 50 ms，则观察到的 step speedup 为 `120/50=2.4`，相对四卡线性加速的效率为 `2.4/4=60%`。这两个值是按假设测量值计算的教学结果，不是 PyTorch 性能承诺。若多卡配置用了更大的 global batch，却只比较每步时间，分子分母代表的工作量不同；若计时包含进程启动或首次初始化，也会混入冷启动成本。比较时固定 token 量、warmup、precision 和数据管线，并记录最慢 rank 的同步尾部，才知道缩放效率来自计算、通信还是输入等待。

优化顺序应从观测信号出发：若 backward 后的通信尾部占比高，先检查 bucket-ready 顺序、是否每个 micro-step 都同步以及网络拓扑；若 forward 前长期等 batch，回第四章看 worker、解码和 rank 数据负载；若只有一个 rank 明显慢，先看序列长度、样本预处理和局部分支。`no_sync()` 适合通信明显、累积窗口可控的情形；它会延迟梯度汇总并增加本地梯度驻留时间，不能解决数据等待或算力不均。只有通信是主瓶颈且分母正确时，少做同步才可能改善稳态时间。

## 7.13 FSDP 的基本直觉

DDP 每张卡都有一份完整模型参数、梯度和优化器状态。模型变大后，单卡显存仍然可能不够。

FSDP 的直觉是把参数、梯度和优化器状态分片到不同 GPU 上。

可以这样理解：

1. DDP：每张卡都有完整模型副本。
2. FSDP：每张卡只长期持有一部分参数状态，需要计算某层时再临时 gather。

优点：

1. 降低单卡显存。
2. 支持更大模型。

代价：

1. 通信更复杂。
2. 对模块边界更敏感。
3. checkpoint、调试和性能优化更复杂。

更具体地说，FSDP 通常在计算某个 wrapped module 前 all-gather 该模块需要的参数，计算完成后再释放或重新分片；反向阶段还会发生 reduce-scatter 等通信。于是单卡常驻状态下降了，但某些时刻仍存在临时 full parameter 和通信 buffer，不能用“参数除以 world size”直接当作峰值显存。wrapper 粒度决定了 gather 的大小、通信次数和 overlap 机会。

用同一份模型状态做一个理想预算。假设有 `P=120,000,000` 个参数，参数和梯度都用 BF16（每个 2 bytes），AdamW 的一阶、二阶 moment 用 FP32（各 4 bytes），暂不计 FP32 master parameters、激活、临时 buffer 和 allocator 开销。参数占 `120M×2=240 MB`，梯度也占 `240 MB`，两个 optimizer moment 合计 `120M×(4+4)=960 MB`，一份状态约 `1,440 MB≈1.34 GiB`。DDP 的每个 rank 都放完整副本，所以四卡时每卡仍需约 1.34 GiB，四卡合计约 5.36 GiB。若使用覆盖全部状态的 full-shard FSDP，理想常驻分片约为 `1.34/4≈0.335 GiB` 每卡；但前向/反向要临时 all-gather 当前模块参数，梯度 reduce-scatter 也有工作 buffer，激活仍由当前 rank 计算并持有。这个估算说明状态分片改变了常驻账本，不能直接预测峰值或声称一定能装下模型。

FSDP 的主要取舍是用更多参数通信换更小的状态副本。切分粒度过粗时，一次 gather 的参数过多、峰值内存高，通信较难与计算重叠；切得过细时，collective 次数上升，启动开销可能变成瓶颈。DDP 的 replica 路径在模型可放下时较简单；FSDP 更适合单卡状态确实放不下的情况。此时还要根据框架版本和 wrapper API 说明 optimizer state 与 checkpoint 是全量、每 rank 本地还是分片格式，因为这些格式的加载目标和内存代价不同。

因此，选择分片前要先量单卡训练状态，而不是只看参数文件大小。模型权重文件往往不包含梯度、optimizer moment、激活峰值、通信 workspace 和 CUDA context；即便 BF16 权重能加载，第一次 backward 或 AdamW 的第一个 step 仍可能 OOM。先用第六章的方法分别测参数、梯度、optimizer、activation 和峰值，再估计哪些状态可分片。若主要峰值来自长序列 activation，FSDP 只分片参数状态可能不够，还要结合 micro-batch、activation checkpointing 或 sequence parallel 等其他策略；后两项超出本章实现范围。

FSDP 的具体 API 也有版本分层：早期 `FullyShardedDataParallel` wrapper 与较新的 `fully_shard` 接口在参数表示、模块分组和状态字典方面存在差异。它们共享“持久状态按 rank 分片、计算时按需要 gather、反向后 reduce-scatter”的大体直觉，但不能据此把两种接口的代码或 checkpoint 格式混写。查代码前先确认导入路径、PyTorch 版本、当前采用的 sharding strategy，以及每个 rank 是否得到同样的模块结构；若只需要读者知道何时越过 DDP 能力边界，本册用上述显存账本即可，不展开 wrapper 配置清单。参考 [PyTorch 2.15 FSDP](https://docs.pytorch.org/docs/2.15/fsdp.html) 与 [`fully_shard`](https://docs.pytorch.org/docs/2.15/distributed.fsdp.fully_shard.html)。

选择 DDP 还是 FSDP，应先回答模型是否能以完整状态放入每卡显存。如果能，DDP 的调试和性能路径通常更简单；如果不能，FSDP/ZeRO 等分片才是结构性方案。分片还会改变 checkpoint 语义：full state dict、local state dict 和 sharded state dict 的目标不同，加载方必须知道自己拿到的是哪一种。

本章只要求建立直觉：DDP 主要解决速度扩展，FSDP 进一步解决大模型显存分片问题。

### 7.14 分布式 checkpoint

DDP 场景通常只让 `rank=0` 保存：

```python
if dist.get_rank() == 0:
    torch.save({
        "model": model.module.state_dict(),
        "optimizer": optimizer.state_dict(),
        "step": global_step,
    }, "checkpoint.pt")
```

原因：所有 rank 的模型参数同步后相同，没必要每个 rank 都写一份。

但 FSDP 或分片训练场景下，checkpoint 可能是 sharded checkpoint，保存和加载要复杂很多。入门阶段先掌握 DDP 的保存方式。

注意：只让 rank 0 写日志和 checkpoint，避免多个进程同时写同一个文件。

对 DDP 的复制状态，rank 0 保存一份完整模型和 optimizer state 通常足够，因为各 rank 从同一参数起步、接收相同同步梯度并执行相同 optimizer step。保存时要选清楚训练边界：在 optimizer step 完成后保存最容易恢复；若在梯度累积窗口中途保存，还得保存尚未同步的 `.grad`、窗口位置、loss 分母和 AMP scaler 等状态，否则重新开始会改变该次更新。若在同一程序里让所有 rank 立即读取刚写的文件，可以在保存边界使用 collective 协调；该同步只保证进程顺序，不保证共享文件系统已完成跨节点可见性，后者必须单独核验。

“只在 rank 0 保存”也不等于“rank 0 的所有状态代表整个作业”。模型/optimizer 副本在 DDP 假设下相同，但每个 rank 的 RNG、随机数据增强、worker 状态、数据游标和局部计数可以不同。若目标是尽量精确恢复，应逐 rank 保存这些局部状态（例如独立小文件或合并到带 rank key 的 checkpoint）；第五章列出的 sampler seed、已消费 batch 数和 DataLoader generator 状态仍适用。只存 rank 0 的随机状态可以恢复一个可继续训练的 run，却不能声称多 rank 的随机序列和样本顺序完全接续。

一个可恢复的 DDP checkpoint 至少应带有 `world_size`、模型/数据配置、`epoch`、`global_step`、sampler seed 和数据进度。用不同 world size 恢复可能改变 global batch 和 sampler 分片，即使权重成功加载，也不应默认训练轨迹等价。

例如 8 个 rank、每 rank micro-batch 4、梯度累积 2 时，保存的 `global_step=100` 表示 100 次 optimizer 更新，不等于每个 rank 已处理 100 个样本；一个完整 update 的名义样本数是 `8×4×2=64`。恢复后若改成 4 个 rank、其余不变，名义 batch 变成 32，sampler 的分片也重算了。模型权重可以加载，但学习率 schedule 的 token/step 口径、训练总 token 和数据顺序都可能改变。checkpoint 因此要记录拓扑及 batch 配置，并在恢复日志里显式比较，而不是只看模型权重键是否匹配。

如果从 DDP 切换到 FSDP，单个 `model.module.state_dict()` 的 rank 0 保存方式也不能直接照搬：每个 rank 可能持有不同分片，必须按所选 FSDP API 的 state-dict 类型和目标拓扑保存、加载。教学章节只建立这个边界；高效的多 rank checkpoint、并行拓扑变化后的 reshard 和大规模异步存储交由分布式训练系统章节。

设计恢复流程时，可以按一个明确的事务顺序复查：先规定 checkpoint 只发生在完整 optimizer update 后；所有 rank 在相同 `global_step` 到达保存条件；rank 0 将模型、optimizer、scheduler 和共享配置写入同一个版本化目录；每 rank 的 RNG、采样位置和 loader 状态分别保存或汇总；完成写入后记录成功标记；恢复时再由所有 rank 读取相同模型/optimizer 状态，并各自恢复本地随机与数据进度。失败发生在“文件写到一半”时，应让恢复逻辑识别未完成产物，而不是只检查路径存在。目录原子化、manifest、checksum 和对象存储提交语义属于第五章 checkpoint 的扩展；本章强调这些状态必须对应同一更新边界。

最后用两种目标判断保存粒度。若目标只是部署推理，可以只保存模型权重、tokenizer 和配置；若目标是训练续跑，至少需要 optimizer/scheduler/step 及与数据顺序有关的状态；若目标是严格复现实验，还要保存每 rank RNG、worker/ sampler 状态、代码/数据版本和运行环境。保存范围越大，跨 rank 汇总和写入成本越高，但恢复时可声称的连续性也越强。应明确标注 checkpoint 是“可推理”“可继续训练”还是“尽量精确恢复”，不要只用一个 `checkpoint.pt` 文件名暗示保证。

## 7.15 分布式训练常见 bug

### 7.15.1 程序卡住

常见原因：

1. 某些 rank 没走到同一个 collective 操作。
2. 条件分支导致不同 rank 执行路径不同。
3. 某些参数在部分 rank 没参与 forward。
4. 数据集长度或 batch 数在不同 rank 不一致。
5. 网络或 NCCL 通信异常。

定位卡住时，先给每个 collective 前后打印带 rank 和 step 的事件，例如 `before_all_reduce`、`after_all_reduce`；如果只看到某些 rank 的 before，说明其他 rank 没有走到同一操作；如果所有 rank 都有 before、但没有 after，问题更可能在通信、设备、网络或某个 rank 的 CUDA 异常。日志必须带 global step、epoch、micro-step 和 collective 名称，否则多个并发请求的输出很难对齐。

用四个 rank 的一次故障演练说明怎样读这些日志。假设 rank 0、1、3 都打印了 `step=20 before_backward`，随后三个进程都卡在梯度 bucket 的同步；rank 2 最后一条却是 `step=20 dataloader_decode_error`。此时首先要修的是 rank 2 的数据异常或让它以所有 rank 可见的方式失败退出，不应先调大 NCCL timeout。若四个 rank 都打印了同一个 bucket 的 `before_all_reduce`，却没有任何 `after_all_reduce`，再看各 rank 的设备映射、backend、网络接口、CUDA 错误和 collective tensor 的 shape/dtype。日志能把“有人没进入同步”与“所有人进入了但通信没有完成”分成两个不同假设。

自定义 collective 也要记录进程组名称、操作类型、tensor 元素数与 dtype；两个 rank 即使都调用 `all_reduce`，如果一个使用了另一个 process group，或张量 shape 不一致，仍然不是同一项匹配通信。错误堆栈最后显示 NCCL timeout 时，往往只是等待端发现超时，不一定是最先出错的 rank。应先找时间线上最早的异常，再解释后续 rank 的 hang。

如果 map-style 数据确实有不等长输入，`DistributedSampler` 的补齐/丢尾通常能让 rank 步数相同；自定义 loader 仍可能令某些 rank 提前结束。DDP 提供 `join()` 让已经耗尽数据的 rank 代替其他 rank 执行匹配的 DDP 通信，从而避免典型的 uneven-input hang，但它不能自动“影子执行”训练脚本里的任意其他 collective。若模型 forward 还含 `SyncBatchNorm` 或应用代码手动调用 collective，应考虑 `throw_on_early_termination=True`，让所有 rank 在早退时一致报错，再调整数据或恢复策略。`join()` 还涉及梯度按初始 world size 还是剩余 rank 数归一化，需把它纳入有效 batch 的分母约定。

### 7.15.2 某些参数没有梯度

常见原因：

1. 模型分支没被当前 batch 使用。
2. 参数 `requires_grad=False`。
3. loss 不依赖该参数。
4. 误用了 `detach()`。

DDP 中如果存在未使用参数，可以尝试设置：

```python
DDP(model, device_ids=[local_rank], find_unused_parameters=True)
```

但这通常有额外开销，不应作为长期默认修复。更好的方式是理解为什么参数未使用。

### 7.15.3 每张卡数据重复

常见原因：

1. 没用 DistributedSampler。
2. sampler 配置错。
3. iterable dataset 没按 rank 切分。

不要只比较每个 rank 的样本数量，还要比较样本 id 的交集、并集、重复次数和 epoch 间变化。补齐策略下“交集不为空”不一定是 bug，因为 sampler 可能为了等长而有意重复；真正要问的是重复是否符合配置、是否被 loss 权重或 epoch 统计记录。对 IterableDataset，要把 `rank` 和 `worker_id` 一起纳入全局分片函数，否则每个 rank 内部不重复，跨 rank 仍可能重复。

### 7.15.4 只有 rank 0 正常，其他 rank 报错

可能是：

1. 只有 rank 0 创建了某些文件或目录。
2. 数据路径在不同机器不可见。
3. 某些初始化逻辑只在 rank 0 执行，但其他 rank 也依赖结果。

但不要滥用 barrier。barrier 可以帮助定位同步点，也可能掩盖真实性能问题。

用普通 `barrier()` 做定位之前，先确认所有 rank 都会到达同一行；若某个 rank 已在前面的 CUDA kernel 或 Python 数据读取处挂住，其他 rank 的 barrier 只会让等待更明显。需要在有超时的情况下找出未到达的 rank 时，可了解 `monitored_barrier()` 的诊断能力；PyTorch 的 host-side monitored barrier 需要 Gloo process group，不能把它无条件当成 NCCL barrier 替换。正式训练里不应把逐 step barrier 留作永久修复，因为它会强迫 ranks 在每步等待最慢者，改变性能特征。

PyTorch 自带的分布式 debug logging 可以在定位阶段提供更丰富的信息。`TORCH_DISTRIBUTED_DEBUG=INFO` 会增加初始化诊断，`DETAIL` 还能记录选定迭代的 forward/backward/通信时间和同步检查；需要同时设置 `TORCH_CPP_LOG_LEVEL=INFO` 才能得到文档说明的日志。`DETAIL` 有额外开销，应只在排障时启用。它可以帮助查看框架 reducer 的状态，但仍要保留应用层的 rank/step/batch 日志，才能把 API 层 collective 与数据处理异常对齐；完整选项与 `monitored_barrier()` 条件见 [PyTorch 2.15 分布式 debug 文档](https://docs.pytorch.org/docs/2.15/distributed.html#debugging-torch-distributed-applications)。

例如先用如下方式重跑一次很短的复现，保存所有 rank 的标准输出和标准错误，再关闭 verbose 配置做性能测量：

```bash
TORCH_CPP_LOG_LEVEL=INFO TORCH_DISTRIBUTED_DEBUG=DETAIL \
  torchrun --standalone --nnodes=1 --nproc-per-node=2 train.py
```

该命令只在诊断时使用；它不是训练速度基线。若现象仅在真实多机出现，还需把单机无法复现的网络接口、容器设备映射和共享文件系统作为独立变量记录，不能由纯 Python 模拟或 Gloo 单机运行替代 NCCL 多机验证。

指标聚合也属于分布式 debug 的一部分。不要让 rank 0 只读取自己的 loss 就代表全局训练；对于 token loss、样本数、正确数和吞吐，应先用 `all_reduce` 汇总分子/分母，再在 rank 0 做除法和打印。例如：

```python
stats = torch.tensor(
    [local_loss_sum, local_valid_tokens],
    dtype=torch.float64,
    device=device,
)
dist.all_reduce(stats, op=dist.ReduceOp.SUM)
global_loss = (stats[0] / stats[1].clamp_min(1)).item()
if dist.get_rank() == 0:
    print({"global_token_loss": global_loss, "valid_tokens": int(stats[1])})
```

吞吐同样要明确统计范围：单 rank 的 GPU 时间、所有 rank 合计的有效 token/s 和墙钟时间不是同一个指标。报告多卡加速比时，使用相同数据量、相同 global batch 解释和相同 warmup 后的稳定窗口。

### 7.17 一个最小 DDP 训练骨架

```python
import os
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, DistributedSampler


def setup():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    dist.init_process_group(backend="nccl")
    return local_rank


def cleanup():
    dist.destroy_process_group()


def main():
    local_rank = setup()
    device = torch.device("cuda", local_rank)
    try:
        seed = 42  # 各 rank 共用 sampler seed；模型和 worker RNG 仍应按任务设计初始化。
        dataset = MyDataset()
        sampler = DistributedSampler(dataset, shuffle=True, seed=seed)
        loader = DataLoader(
            dataset,
            batch_size=8,
            sampler=sampler,
            num_workers=4,
            multiprocessing_context="spawn",
        )

        model = MyModel().to(device)
        model = DDP(model, device_ids=[local_rank])
        optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)

        for epoch in range(3):
            sampler.set_epoch(epoch)
            model.train()

            for batch in loader:
                batch = move_to_device(batch, device)
                optimizer.zero_grad(set_to_none=True)
                outputs = model(**batch)
                loss = outputs["loss"]
                loss.backward()
                optimizer.step()

            if dist.get_rank() == 0:
                torch.save(model.module.state_dict(), "model.pt")
    finally:
        cleanup()


if __name__ == "__main__":
    main()
```

启动：

```bash

```

> 启动命令，静态审阅，未运行；需在声明的 torchrun、CUDA 与集群环境验证。

这个骨架包含初始化、设备绑定、DistributedSampler、DDP 包装、epoch shuffle、rank 0 保存和清理。`MyDataset`、`MyModel`、`move_to_device` 与输出字典是依赖调用者提供的占位接口，不是可复制后直接运行的完整程序。示例每个 rank 启动 4 个 DataLoader worker，故选择 `spawn`；worker 函数和 dataset 要满足 multiprocessing 的可序列化与 `__main__` 入口约定。训练 loop 为易读起见没有包含 AMP、token 加权 loss、验证和完整恢复状态；这里只保存 `model.pt` 权重，不能将它当作第 5 章所述的可恢复训练 checkpoint。

checkpoint 加载也有设备映射边界：一个 rank 保存的 CUDA tensor 若由其他进程加载，需显式设置合适的 `map_location`，否则 `torch.load` 可能尝试恢复到保存时的设备编号。检查权重可移植性时，还要区分 `model.module.state_dict()` 与整个 DDP wrapper 的 `state_dict()` 前缀；本例保存未包装 module 的状态，方便之后由普通模型读取。若保存整个 wrapper，加载回普通 module 时要处理 `module.` 前缀。具体规则以 [PyTorch 2.15 DDP checkpoint 说明](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html)为准。

### 7.18 纯 Python 分布式机制审计 demo

下面的脚本只用 Python 标准库，模拟分布式训练中的几项账本：各 rank 的索引分片、all-reduce 平均梯度、`no_sync()` 的同步次数、rank 事件序列和 checkpoint 写入者。它不是 PyTorch `DistributedSampler` 的实现，也没有启动多进程、执行 DDP、运行 collective 或测量网络；实际 API 行为以本章前面的 PyTorch 2.15 官方文档和目标环境验证为准。

```python
from itertools import combinations
import math
import random


def toy_distributed_indices(num_samples, world_size, rank, epoch=0, seed=0):
    if num_samples <= 0:
        raise ValueError("num_samples must be positive")
    if world_size <= 0 or not 0 <= rank < world_size:
        raise ValueError("rank must be in [0, world_size)")
    indices = list(range(num_samples))
    random.Random(seed + epoch).shuffle(indices)
    per_rank = math.ceil(num_samples / world_size)
    total_size = per_rank * world_size
    needed = total_size - num_samples
    if needed:
        repeats = math.ceil(needed / num_samples)
        indices.extend((indices * repeats)[:needed])
    return indices[rank:total_size:world_size]


def find_overlaps(parts):
    overlaps = []
    for left, right in combinations(parts, 2):
        common = sorted(set(parts[left]) & set(parts[right]))
        if common:
            overlaps.append((left, right, common))
    return overlaps


def audit_event_sequence(traces, expected_events):
    mismatched = {
        rank: events
        for rank, events in traces.items()
        if events != expected_events
    }
    return {
        "ok": not mismatched,
        "mismatched": mismatched,
    }


def padded_shards(num_samples, world_size):
    if num_samples < 0 or world_size <= 0:
        raise ValueError("num_samples must be non-negative and world_size positive")
    if num_samples == 0:
        return {rank: [] for rank in range(world_size)}
    indices = list(range(num_samples))
    per_rank = (num_samples + world_size - 1) // world_size
    total_size = per_rank * world_size
    needed = total_size - num_samples
    if needed:
        repeats = (needed + num_samples - 1) // num_samples
        indices.extend((indices * repeats)[:needed])
    return {
        rank: indices[rank * per_rank : (rank + 1) * per_rank]
        for rank in range(world_size)
    }


def dropped_shards(num_samples, world_size):
    if num_samples < 0 or world_size <= 0:
        raise ValueError("num_samples must be non-negative and world_size positive")
    indices = list(range(num_samples))
    per_rank = num_samples // world_size
    usable = per_rank * world_size
    indices = indices[:usable]
    return {
        rank: indices[rank * per_rank : (rank + 1) * per_rank]
        for rank in range(world_size)
    }


world_size = 4
per_device_batch_size = 2
accum_steps = 3
dataset_size = 16

epoch0_parts = {
    rank: toy_distributed_indices(dataset_size, world_size, rank, epoch=0, seed=7)
    for rank in range(world_size)
}
epoch1_parts = {
    rank: toy_distributed_indices(dataset_size, world_size, rank, epoch=1, seed=7)
    for rank in range(world_size)
}

all_epoch0_indices = sorted(index for part in epoch0_parts.values() for index in part)
sampler_overlap = find_overlaps(epoch0_parts)
global_batch_size = per_device_batch_size * world_size * accum_steps
uneven_padded = padded_shards(num_samples=10, world_size=3)
uneven_dropped = dropped_shards(num_samples=10, world_size=3)
tiny_padded = padded_shards(num_samples=1, world_size=8)

local_token_counts = [4, 16]
local_mean_losses = [2.0, 1.0]
rank_mean_loss = sum(local_mean_losses) / len(local_mean_losses)
global_token_loss = sum(
    count * loss for count, loss in zip(local_token_counts, local_mean_losses)
) / sum(local_token_counts)

rank_grads = [0.2, 0.4, -0.1, 0.3]
avg_grad = sum(rank_grads) / world_size
theta0 = 1.0
lr = 0.5
synced_params = [round(theta0 - lr * avg_grad, 3) for _ in rank_grads]
unsynced_params = [theta0 - lr * grad for grad in rank_grads]
unsynced_param_drift = round(max(unsynced_params) - min(unsynced_params), 3)

micro_steps = 6
sync_without_no_sync = micro_steps
sync_with_no_sync = sum(
    1 for step in range(micro_steps)
    if (step + 1) % accum_steps == 0
)

ok_trace = {
    rank: ["forward", "backward", "all_reduce", "optimizer_step"]
    for rank in range(world_size)
}
bad_trace = {
    0: ["forward", "backward", "all_reduce", "optimizer_step"],
    1: ["forward", "backward", "all_reduce", "optimizer_step"],
    2: ["forward", "backward", "optimizer_step"],
    3: ["forward", "backward", "all_reduce", "optimizer_step"],
}
expected_events = ["forward", "backward", "all_reduce", "optimizer_step"]
ok_collective = audit_event_sequence(ok_trace, expected_events)
bad_collective = audit_event_sequence(bad_trace, expected_events)

def should_write_checkpoint(rank):
    return rank == 0


checkpoint_writers = [
    rank for rank in range(world_size) if should_write_checkpoint(rank)
]
checks = {
    "sampler_no_overlap": sampler_overlap == [],
    "sampler_full_coverage": all_epoch0_indices == list(range(dataset_size)),
    "sampler_epoch_changed": epoch0_parts[0] != epoch1_parts[0],
    "tiny_dataset_padded_to_all_ranks": all(len(shard) == 1 for shard in tiny_padded.values()),
    "synced_params_equal": len(set(synced_params)) == 1,
    "unsynced_would_drift": unsynced_param_drift > 0,
    "no_sync_reduces_calls": sync_with_no_sync < sync_without_no_sync,
    "detects_event_mismatch": not bad_collective["ok"],
    "only_rank0_writes": checkpoint_writers == [0],
    "token_weighting_differs": rank_mean_loss != global_token_loss,
}

print("global_batch_size=", global_batch_size)
print("sampler_epoch0=", epoch0_parts)
print("sampler_overlap=", sampler_overlap)
print("sampler_coverage=", len(all_epoch0_indices))
print("sampler_epoch_changed=", checks["sampler_epoch_changed"])
print("uneven_padded=", uneven_padded)
print("uneven_dropped=", uneven_dropped)
print("tiny_padded=", tiny_padded)
print("rank_mean_loss=", round(rank_mean_loss, 3))
print("global_token_loss=", round(global_token_loss, 3))
print("all_reduce_avg_grad=", round(avg_grad, 3))
print("synced_params=", synced_params)
print("unsynced_param_drift=", unsynced_param_drift)
print("no_sync_calls=", {
    "without_no_sync": sync_without_no_sync,
    "with_no_sync": sync_with_no_sync,
})
print("collective_audit=", {
    "ok": ok_collective["ok"],
    "bad": bad_collective["ok"],
    "bad_ranks": sorted(bad_collective["mismatched"]),
})
print("rank0_writers=", checkpoint_writers)
print("checks=", checks)
```

> 代码块，已验证（2026-11-09；Python 3.12.9；仅使用标准库，在 CPU 环境执行；不代表 PyTorch、CUDA、NCCL 或多进程 DDP 已验证）。

这段 demo 要抓住几个点：

1. `sampler_overlap=[]` 和 `sampler_coverage=16` 说明该 toy 输入在样本数可整除时分片互斥且覆盖完整；函数使用 Python `random` 演示一致 seed/epoch 的关系，不逐字复刻 PyTorch 的 `DistributedSampler`。
2. `global_batch_size=24` 说明多卡和梯度累积会改变真实 batch。
3. all-reduce 平均后所有 rank 的参数更新一致；如果各自用本地梯度更新，`unsynced_param_drift` 会大于 0。
4. `no_sync()` 的直觉是多个 micro-step 只同步一次，demo 中通信次数从 6 次降到 2 次。
5. 事件序列 audit 能发现 rank 2 缺少 `all_reduce`，用于示意分布式训练卡住的一种常见前兆；它不是对真实进程通信的监控器。
6. `rank_mean_loss=1.5` 而 `global_token_loss=1.2`，说明 rank 等权和有效 token 等权是两个不同目标。
7. `uneven_padded` 中会出现补样本，`uneven_dropped` 中会丢掉尾部样本；二者都需要记录数据权重影响。
8. checkpoint 写入者只有 rank 0，避免多进程同时写同一个文件；它只检查写入者策略，不模拟 checkpoint 文件内容或恢复。

### 7.19 从分布式现象反推根因

#### 7.19.1 多卡 loss 与单卡不一致

先确认比较的是同一口径：相同的 global batch、相同的有效 token 数、相同的 reduction、相同的随机性和相同的学习率步数。若每卡本地 mean loss 不同，直接在 rank 0 打印 rank 0 的值没有意义；应汇总 loss sum 和 valid count。若参数在同步后仍分叉，再检查 optimizer step 是否有 rank 条件分支、是否有本地 BatchNorm 统计或某些参数只在一部分 rank 使用。

#### 7.19.2 训练速度随卡数增加不明显

把 step 时间拆成计算、数据等待、host-to-device 拷贝、all-reduce 和 optimizer 五部分。若 all-reduce 占比高，查看 bucket、梯度累积和通信拓扑；若等待 batch 占比高，回到 DataLoader 和每 rank 的 worker 配置；若某些 rank 明显更慢，检查序列长度、动态 batch、数据解码和稀疏路由造成的负载不均。加速比应使用稳定窗口的有效 token/s，而不是启动阶段或单次 step。

#### 7.19.3 只有某个 rank 报错或提前结束

一个 rank 先抛异常退出后，其他 rank 往往会在下一次 collective 中表现为 hang 或通信错误。日志中要保留最早的 Python exception、rank、step 和 batch id；不要只追最后一个 NCCL 报错。数据文件路径、环境变量、可见设备和随机增强也要按 rank 逐一比较。

## 7.20 常见误区

1. 以为多卡就是自动变快。通信开销、数据加载和 batch 配置都会影响加速比。
2. 以为 DDP 会自动处理数据切分。数据切分要用 DistributedSampler 或自己实现。
3. 以为每张卡 batch size 不变时训练完全等价。global batch size 变大后优化行为会变化。
4. 以为所有 rank 都可以写同一个 checkpoint。通常只让 rank 0 写。
5. 以为 `find_unused_parameters=True` 是万能修复。它有开销，应该理解参数为什么没被使用。
6. 以为 FSDP 只是更快的 DDP。FSDP 主要解决显存分片问题，复杂度也更高。

## 7.23 本章总结

分布式训练的入门主线是：多进程、多 GPU、每个进程一个 rank，DDP 负责梯度同步，DistributedSampler 负责数据切分，torchrun 负责启动和环境变量设置。

需要记住：

1. `rank` 是全局进程编号，`local_rank` 是本机 GPU 编号，`world_size` 是总进程数。
2. DDP 是最常见的数据并行方式，每张卡处理不同数据，backward 后 all-reduce 梯度。
3. `DistributedSampler` 按 rank 切分 map-style 数据；为了等长，默认可能补重复索引，sampler 的 `drop_last` 会截尾，需与 DataLoader 的 batch `drop_last` 区分。
4. 在每 rank 样本数相同的完整窗口里，global batch size 等于每卡 batch、world size 和梯度累积步数的乘积；变长语言模型还要统计实际有效 token 数。
5. DDP 的同一 optimizer step 通常由 rank 0 写一份模型/optimizer 副本；若要严格续训，还要保存每个 rank 的随机数和数据游标。
6. FSDP 进一步把参数、梯度和优化器状态分片，用于更大模型。
7. 分布式 debug 要关注 rank 是否一致进入同步点、数据是否切分正确、通信是否卡住。
