# 第十章：工程问题与判断

前九章分别讲了 PyTorch 的张量、自动求导、模块组织、数据加载、训练循环、混合精度、分布式训练、调试与 profiling，以及 Transformer 组件实现。本章不再把这些内容压缩成一组“题目—标准答案”。真正的工程能力也不是在限定时间内说出最多术语，而是面对一个现象时，能够先定义成功条件，再用最小实验区分候选原因，最后用可复现证据支持结论。

例如，loss 不下降可能来自错误的 label shift、学习率、数据内容、梯度没有进入 optimizer，也可能只是日志把不同分母的 loss 放在了一起。说出“检查学习率和梯度”只是起点；有价值的判断必须说明检查什么、预期看到什么、如果结果相反下一步做什么。又例如，多卡训练的 loss 看起来正常，并不代表全局 token 的统计正确；每个 rank 的有效 token 数不同时，简单平均 rank loss 会改变训练目标。

本章用一个小型语言模型训练系统作为贯穿案例。它不追求训练出有意义的语言能力，而是让读者在一条完整链路中观察数据、模型、梯度、优化器、checkpoint、分布式统计和推理缓存之间的关系。最后的可运行 demo 会报告 shape、有效 token、参数更新、checkpoint 恢复和分布式统计等事实，不会用关键词数量代替理解。

## 10.0 本章的阅读边界与资料等级

本章适合已经读过本册前九章、希望把局部知识组织成工程判断的人。初学者可以沿着一次小模型训练的故事阅读；有经验的读者可以把每一节看成一次代码审查：哪些假设被写进了函数签名，哪些状态需要保存，哪些数字只能在目标硬件上实测。

本章会覆盖：

1. shape、dtype、device、stride 和模块状态如何组成程序契约。
2. autograd、Parameter、buffer、train/eval 和 checkpoint 如何共同决定训练状态。
3. 变长数据、padding、shift loss、有效 token 和梯度累积之间的统计关系。
4. 混合精度、激活、优化器状态和 OOM 的资源账本。
5. DDP、DistributedSampler、FSDP 以及多 rank 指标的分母问题。
6. loss 不下降、NaN、OOM、吞吐下降和 cache 不一致的最小排查实验。
7. 如何把前面章节的 Transformer 实现转化为可审查、可回归的工程组件。

本章不替代 PyTorch API 手册，也不展开 CUDA kernel、编译器内部、NCCL 网络调优、生产级分布式 checkpoint 或集群运维。正文中的公式用于解释数量关系，代码是教学实现，真实速度、显存和恢复时间必须在目标模型、硬件、PyTorch 版本和数据管线上复测。

资料优先级如下：

1. PyTorch 官方文档用于确认 API 的调用语义，例如 tensor view、autograd、Module、DataLoader、AMP、DDP、DistributedSampler、checkpoint 和 profiler。
2. Transformer、RoFormer 等论文用于确认 attention、位置编码和模型结构的公开定义。
3. 本章的小实验和合成事故用于说明如何验证一个工程假设；它们不是对任何生产系统性能的统计结论。

## 10.1 工程问题不是名词题，而是契约题

一个工程问题通常可以写成五个对象：

1. 输入是什么，形状、dtype、device 和版本如何定义。
2. 输出是什么，哪些值是模型结果，哪些值是日志或估计量。
3. 状态是什么，下一次执行需要从哪里继续。
4. 不变量是什么，哪些条件一旦被破坏就会让结果失去意义。
5. 证据是什么，如何区分“代码跑完”和“目标成立”。

以 causal language model 为例，输入 token id 的契约不是“一个整数矩阵”这么简单。它还必须满足词表范围、padding 约定、attention mask 与 label mask 的对齐，以及 tokenizer 版本和 special token 的一致性。输出 logits 的契约也不只是 [B,T,V]，还包括第 t 个位置究竟对应哪个 label。

### 10.1.1 初学者视角：先把现象翻译成可观察量

初学者遇到“训练不对”时，容易直接问“是不是模型太小”。更稳妥的顺序是把模糊现象拆成可观察量：

~~~text
loss 不下降
  -> 有效 label 数是否大于零？
  -> logits 和 labels 是否按同一位置对齐？
  -> loss 是否依赖参数？
  -> 梯度是否有限且进入 optimizer？
  -> 参数更新后输出是否变化？
  -> 数据、学习率和模型容量是否仍是候选原因？
~~~

每一步都可以通过一个 batch、一个参数或一个 checkpoint 验证。这样即使最后结论是“学习率确实太小”，也知道它是在排除数据和实现错误之后得到的。

### 10.1.2 工程师视角：结论必须带条件

“BF16 更稳定”“DDP 能线性加速”“KV Cache 能降低延迟”都可能在某些条件下成立，但它们不是无条件定律。更完整的说法应该包含适用条件：

| 结论 | 必须同时说明的条件 |
| --- | --- |
| BF16 溢出更少 | 硬件支持、算子覆盖、累积精度和 loss/梯度监控 |
| DDP 结果一致 | 参数初始一致、数据切分、collective 顺序和 loss 权重口径一致 |
| checkpoint 可恢复 | 模型、优化器、scheduler、随机状态和数据进度都被保存 |
| cache 能加速 | decode 占主要工作、cache 可容纳、backend 没有被内存带宽限制 |
| loss 下降代表学习 | 数据切分独立、分母一致、没有 label 泄漏或 benchmark 污染 |

这也是阅读公开资料时的证据边界：官方文档能证明 API 的语义，论文能支持特定实验，模型卡能支持公开配置；它们不能直接替代目标系统的实测。

## 10.2 一条 shape 契约贯穿模型

对 decoder-only 语言模型，最基本的数据流是：

~~~math
I\in\mathbb{Z}^{B\times T},\qquad
H\in\mathbb{R}^{B\times T\times d},\qquad
Z\in\mathbb{R}^{B\times T\times V}.
~~~

I 是输入 token id，H 是隐藏状态，Z 是 logits；B、T、d、V 分别是 batch size、序列长度、hidden size 和词表大小。这个公式本身很短，但它规定了 embedding、block、norm 和 LM head 之间的接口。

进入 attention 后，d=H_head D_h。为避免与 hidden state 的符号混淆，本章把 head 数记为 H_head：

~~~math
Q,K,V\in\mathbb{R}^{B\times H_{\mathrm{head}}\times T_q\times D_h},
\qquad
S\in\mathbb{R}^{B\times H_{\mathrm{head}}\times T_q\times T_k}.
~~~

完整序列训练时 T_q=T_k=T；cache decode 时常见的是 T_q=1、T_k=T_cache+1。因此，一个只打印 [B,H,T,D_h] 的测试并没有覆盖 decode 的矩形 attention。

### 10.2.1 一个可手算的 shape 例子

取 B=2、T=5、d=16、V=32、H_head=4，则 D_h=4：

1. embedding 输出是 [2,5,16]。
2. Q/K/V 投影后仍是 [2,5,16]。
3. reshape 和 transpose 后是 [2,4,5,4]。
4. score 是 [2,4,5,5]。
5. 合并 head 后回到 [2,5,16]。
6. LM head 输出 [2,5,32]。

如果在第 4 步得到 [2,5,4,4]，说明 head 维和时间维没有按约定交换；如果 score 是 [2,4,5,4]，说明矩阵乘法没有在最后两维进行。

### 10.2.2 dtype 和 device 也是 shape 以外的契约

两个张量形状相同，不代表可以相乘。模型权重在 CUDA 而输入在 CPU，会得到 device mismatch；embedding 的 input id 使用浮点 dtype，会违反索引要求；fp16 的 mask 常数不在可表示范围内，则可能产生 Inf。调试日志至少应同时记录：

~~~text
name, shape, dtype, device, requires_grad, min, max, isfinite
~~~

对大张量直接打印全部值通常不合适。记录最小值、最大值、均值、非有限计数和少量样本，既能定位问题，也不至于把日志变成新的内存负担。

## 10.3 view、stride 与模块状态

### 10.3.1 为什么一个 reshape 可能改变性能

PyTorch tensor 不仅有 shape，还有 stride。transpose 经常只改变 stride，不移动底层数据；如果之后的 view 需要连续布局，代码可能报错或触发复制。安全并不等于便宜：reshape 在必要时会复制，复制的大张量会增加时间和显存峰值。

~~~python
x = torch.arange(12).view(3, 4)
y = x.transpose(0, 1)
z = y.contiguous().view(12)
~~~

在 Transformer 中，[B,H,T,D] 合并回 [B,T,d] 经常走同样的路径。代码审查不应只看最终 shape，还要问这次布局转换是否发生在每一层、是否需要返回 attention 权重、是否会在长上下文中产生不可接受的复制。

### 10.3.2 Parameter、buffer 和普通属性

nn.Module 会递归注册 Parameter 和子模块。普通 Python list 中的子模块不会自动出现在 parameters、state_dict、to(device) 或 DDP 递归遍历中；应使用 ModuleList 或 ModuleDict。不参与训练但属于模型状态的 tensor，例如固定频率、running statistics 或预计算的 mask，应使用 register_buffer。

这个区别可以用三个问题检查：

1. optimizer 是否能看到需要更新的 Parameter？
2. model.to(device) 后，buffer 是否也到了正确 device？
3. checkpoint 加载后，非参数状态是否和模型权重一致？

如果一个 RoPE cache 被普通属性持有，它可能仍留在 CPU；如果一个随机层被误放在普通 list，训练可能表面运行却没有更新它。

### 10.3.3 train、eval、no_grad 与 inference_mode

model.train() 和 model.eval() 主要切换模块行为，例如 Dropout 和 BatchNorm；它们不会自动关闭梯度。验证通常需要同时使用 eval() 与 torch.no_grad() 或 torch.inference_mode()。反过来，推理时使用 no_grad 也不会替代 eval()。

detach() 作用于一个 tensor，把它与已有计算图断开；no_grad() 作用于一个代码作用域，使其中的新操作不记录 autograd 图。把带图的 loss 或 hidden state 存进 Python list，会让图沿着列表生命周期保留，形成隐蔽的显存增长。日志值应使用 item、detach 或在无梯度上下文中计算。

## 10.4 数据、padding 与 causal LM loss

### 10.4.1 Dataset 与 DataLoader 的职责分离

Dataset 负责描述一个样本如何读取；DataLoader 负责 batch、shuffle、sampler、worker 和 collate。变长 token 序列不能直接 stack，需要在 collate 阶段决定 padding 方向、pad id、attention mask 和 label mask。

一个 batch 的输入可能是：

~~~text
sample 1: [11, 7, 4, 9]
sample 2: [11, 6]
sample 3: [12, 8, 5]
~~~

右 padding 后，输入矩阵可以是：

~~~text
11 7 4 9
11 6 0 0
12 8 5 0
~~~

但 labels 不能把两个 0 当成要预测的真实 token。对应位置应使用 ignore_index，例如 -100。如果使用 left padding 或不同的 chat template，attention mask 和 position id 还要遵循目标模型的协议。

### 10.4.2 shift loss 的分母

因果语言模型在位置 t 预测 t+1，因此：

~~~math
Z_{\mathrm{shift}}=Z[:,0:T-1,:],\qquad
Y_{\mathrm{shift}}=Y[:,1:T].
~~~

展平后：

~~~math
N_{\mathrm{row}}=B(T-1),\qquad
Z_{\mathrm{shift}}\in\mathbb{R}^{N_{\mathrm{row}}\times V},\qquad
Y_{\mathrm{shift}}\in\mathbb{Z}^{N_{\mathrm{row}}}.
~~~

交叉熵的实际有效分母是未被忽略的 label 数，而不是必然等于 B(T-1)。一个全是 -100 的 batch 没有有效监督，不应把它当作一个正常的零损失 batch。

### 10.4.3 变长 batch 的 token 加权

第 k 个 micro-batch 有 n_k 个有效 token，单 batch 平均 loss 为：

~~~math
\bar L_k=\frac{1}{n_k}\sum_{i=1}^{n_k}\ell_{k,i}.
~~~

如果希望每个 micro-batch 等权，累积窗口的目标是：

~~~math
L_{\mathrm{batch}}=\frac{1}{m}\sum_{k=1}^{m}\bar L_k.
~~~

如果希望每个有效 token 等权，目标是：

~~~math
L_{\mathrm{token}}=
\frac{\sum_{k=1}^{m}\sum_{i=1}^{n_k}\ell_{k,i}}
{\sum_{k=1}^{m}n_k}.
~~~

当所有 n_k 相同，二者相等；变长序列、packing 和 prompt mask 会使它们不同。训练循环应保存 loss sum 和 valid count，而不是把几个 mean loss 机械平均。

## 10.5 autograd、梯度累积与一次更新

### 10.5.1 一次 optimizer step 的状态转移

设参数为 theta_t，当前 batch 的目标为 L_t，则：

~~~math
g_t=\nabla_{\theta_t}L_t,\qquad
\theta_{t+1}=U(\theta_t,g_t,\eta_t,s_t).
~~~

s_t 包含 AdamW 的一阶矩、二阶矩等 optimizer 状态。训练循环不仅改变参数，还改变 optimizer、scheduler、随机数和数据进度；因此“保存模型”与“恢复原训练轨迹”是两个不同目标。

最小顺序是：

~~~text
zero_grad
    -> forward
    -> loss
    -> backward
    -> unscale（使用 scaler 时）
    -> clip（需要时）
    -> optimizer.step
    -> scheduler.step（按真实 optimizer step）
~~~

梯度裁剪必须在 unscale 之后，否则裁剪的是被放大的梯度。梯度累积时 scheduler 也应按 optimizer update 次数推进，而不是按每个 micro-batch 次数推进。

### 10.5.2 梯度累积的两个分母

若一个窗口包含 K 个等大小 micro-batch，平均梯度可以近似写成：

~~~math
g_{\mathrm{acc}}=\frac{1}{K}\sum_{k=1}^{K}g_k.
~~~

最后一个窗口可能只有 m<K 个 batch，仍除以固定 K 会把它额外缩小 m/K。如果使用有效 token 加权，则应先累加各 batch 的 loss sum，窗口结束时除以总 token 数；这意味着代码可能需要延迟 backward 或者按精确分母重新缩放每个 micro-batch 的梯度。

“梯度累积等价于更大的 batch”也有条件：模型没有依赖 batch 统计的随机行为，数据顺序、loss reduction、随机数和 optimizer step 语义一致；Dropout、BatchNorm、动态 padding 和非线性 scheduler 都可能让这种等价变成近似而不是恒等式。

### 10.5.3 训练不动时先证明梯度链存在

一个极小的检查顺序是：

1. loss 是有限数，且有效 token 数大于零。
2. 至少一个参数的 grad 非 None。
3. 梯度范数非零且有限。
4. optimizer 的参数列表包含该参数。
5. optimizer.step() 前后参数确实变化。

如果第 2 步失败，先查 detach、no_grad、冻结参数和 loss 是否脱离 logits；如果第 3 步失败，查 mask、饱和激活和 label；只有前几步成立后，学习率和模型容量才是主要候选。

## 10.6 checkpoint 是一组状态，不是一份权重

### 10.6.1 推理 checkpoint 与训练 checkpoint

只做推理时，模型权重、配置、tokenizer 和必要的 special token 规则通常是核心资产。要恢复训练，还应保存：

~~~text
model state
optimizer state
scheduler state
global step / epoch
训练配置和数据版本
随机数状态
sampler 或数据游标
混合精度 scaler（如果使用）
~~~

可以把它抽象为：

~~~math
C_t=(\theta_t,s_t,h_t,e_t,r_t,d_t,c_t),
~~~

其中 theta 是模型参数，s 是 optimizer state，h 是 scheduler state，e 是训练位置，r 是随机状态，d 是数据进度，c 是配置和版本信息。缺少其中一项，恢复后都可能不是原轨迹。

### 10.6.2 原子保存与 best/last

直接覆盖唯一 checkpoint 文件时，进程中断可能留下半个文件。更稳妥的流程是写入临时路径、flush/fsync（按存储系统需要），再原子 rename，并保留 last 和 best 的不同语义：

1. last 表示最近一次可恢复状态。
2. best 表示按明确验证指标选择的状态。
3. 指标、分母和数据版本必须随 best 一起保存，否则无法解释“最好”。

保存 checkpoint 不是越频繁越好。保存间隔应和重算成本、存储带宽、故障概率以及可接受的数据损失共同决定。

### 10.6.3 恢复验证不能只看文件存在

恢复测试应至少包含：

1. 加载后参数与保存前一致。
2. 固定输入下的 forward 输出一致。
3. optimizer step 计数和 scheduler 学习率一致。
4. 随机状态恢复后，下一次随机操作符合预期。
5. 数据游标没有重复或跳过超出约定范围。

如果模型含 Dropout，比较输出时要在 eval 模式或同时恢复 RNG；如果使用分布式 sharded checkpoint，还要额外验证 world size、shard metadata 和重分片策略。

## 10.7 混合精度与显存：先建立资源账本

训练显存可以粗略拆成：

~~~math
M_{\mathrm{train}}\approx
M_{\mathrm{param}}+M_{\mathrm{grad}}+M_{\mathrm{opt}}
 +M_{\mathrm{act}}+M_{\mathrm{tmp}}+M_{\mathrm{input}}.
~~~

AdamW 通常至少有一阶矩和二阶矩，所以 optimizer state 可能比参数和梯度加起来还大。长序列 attention 的中间量带有 T^2，activation checkpointing 则用重算换保存。

### 10.7.1 FP16、BF16 与 AMP

FP16 和 BF16 都是 16 位浮点，但指数位分配不同。BF16 的动态范围更接近 FP32，通常更不容易因为大值溢出；FP16 的精度分布不同，在一些硬件上吞吐很好，但梯度下溢风险更高。最终选择受硬件、算子、模型和训练稳定性影响。

AMP 的 autocast 是按算子选择 dtype 的执行策略；它不等同于把整个模型永久改成低精度。GradScaler 通过放大 loss 保护 FP16 小梯度，反向后必须 unscale，再做梯度检查和裁剪。即使使用 BF16，也应监控非有限值，不能把 dtype 名称当成稳定性证明。

### 10.7.2 activation checkpointing 的代价

checkpointing 不保存某些 forward 中间激活，backward 时重算。重算粒度越大，显存可能越省，但计算越多；含随机算子的模块还需要正确处理 RNG，否则重算与原 forward 不一致。一个微型实验应分别记录：

~~~text
peak allocated
peak reserved
forward time
backward time
是否出现非有限梯度
~~~

只报告“显存下降”而不报告时间和结果一致性，无法支持工程决策。

### 10.7.3 OOM 的分层定位

先区分：

1. 第一个 batch 就 OOM：静态容量或单次峰值问题。
2. 运行一段时间后 OOM：可能保存了带图 tensor、缓存增长或碎片。
3. 训练能跑、验证 OOM：验证没有关闭梯度或返回了过多中间量。
4. 只有长序列 OOM：attention/activation 的序列平方或 cache 预算问题。
5. 只有多卡 OOM：每 rank batch、optimizer state、FSDP materialization 或通信 buffer 问题。

allocated、reserved 和峰值统计回答的是不同问题，不能只截一张 nvidia-smi 快照就判断泄漏。

## 10.8 分布式训练：一致的参数不等于一致的统计

### 10.8.1 DDP 的基本同步

数据并行中，每个 rank 拥有模型副本，处理自己的 batch。理想化地写：

~~~math
\bar g=\frac{1}{W}\sum_{r=0}^{W-1}g_r,\qquad
\theta_{t+1}=\theta_t-\eta\bar g.
~~~

DDP 的 all-reduce 使各 rank 得到同步梯度，再分别更新本地参数。前提包括初始参数一致、所有 rank 以相同顺序进入 collective、数据切分不意外重复，以及每个 rank 的梯度表达了同一个训练目标。

### 10.8.2 rank mean 与 global token mean

设 rank 0 有 loss sum 4、有效 token 4，rank 1 有 loss sum 12、有效 token 16。两个 rank 的本地 mean 分别是 1 和 0.75：

~~~math
L_{\mathrm{rank\ mean}}=\frac{1+0.75}{2}=0.875,
\qquad
L_{\mathrm{global\ token}}=\frac{4+12}{4+16}=0.8.
~~~

当有效 token 数相同，这两个值才相等。日志如果只 all-reduce 本地 mean 再除以 world size，会报出 0.875；如果训练目标是每个有效 token 等权，则应 all-reduce loss sum 和 valid count，再计算 0.8。梯度本身还要按照同一目标缩放，不能只修正日志而留下错误更新。

### 10.8.3 DistributedSampler 的补样本与丢弃

数据量 N 不能整除 W 时，sampler 可能通过补样本使每个 rank 长度一致，也可能使用 drop_last 丢弃尾部样本。两者都会改变一个 epoch 的实际样本分布：

1. 补样本可能重复少量样本。
2. drop_last 会丢失尾部样本。
3. 每个 epoch 必须调用 set_epoch，才能在 shuffle 时使用不同顺序。
4. 训练记录应说明有效样本数，而不是只记录名义 epoch。

### 10.8.4 DDP 与 FSDP 的工程差异

DDP 主要复制完整模型并同步梯度；FSDP 对参数、梯度和 optimizer state 进行分片，在更大模型上减少单卡常驻显存，但会引入 all-gather、reshard、wrap policy 和 sharded checkpoint 的复杂度。选择 FSDP 不是“换一个类名”，而是改变参数生命周期、保存格式和 debug 方法。

### 10.8.5 collective hang 的最小证据

分布式卡住时，不要只记录“程序无响应”。每个 rank 的事件日志至少带：

~~~text
rank, step, batch_id, collective_name, enter_time, exit_time
~~~

若某个 all-reduce 只有部分 rank 记录了 enter，通常是控制流、异常 batch 或数据长度不一致；若所有 rank 都 enter 但没有 exit，再检查 backend、device、网络和 collective 参数。每个 rank 写独立日志，最后由 rank 0 汇总，避免主进程自己成为新的阻塞点。

## 10.9 Debug 与 profiling：从假设到最小实验

### 10.9.1 四步排查循环

可靠的排查可以写成：

~~~text
假设 -> 最小实验 -> 观测 -> 下一步
~~~

例如假设“label shift 写反导致 loss 异常低”：

1. 固定一个只有几个 token 的 batch。
2. 手工列出位置、logits 和 labels。
3. 比较正确 shift、错误 shift 和去掉 mask 的 loss。
4. 如果只有错误版本异常低，修正数据路径并加入断言。

这个循环比同时改学习率、batch size、模型层数和 mask 更有信息量，因为一次实验保留了因果差异。

### 10.9.2 loss 不下降

按信息增益排序，可以检查：

1. 样本与 label：打印少量 token，确认任务目标不是空的。
2. 有效分母：确认 valid token 大于零且日志分母一致。
3. forward：确认 logits 形状、dtype 和有限性。
4. autograd：确认 loss 与参数相连，至少一个参数的梯度非 None。
5. 更新：记录梯度范数和参数变化量。
6. 优化器：确认参数在 optimizer 中，学习率和 scheduler step 正确。
7. 数据与容量：前面成立后，再检查分布、初始化和模型容量。

### 10.9.3 NaN 的首次出现位置

NaN 不是一个根因。应区分输入、embedding、attention score、softmax、loss、unscaled gradient、clipped gradient 和参数中的首次非有限值。可用 forward hook、torch.autograd.set_detect_anomaly、有限性断言和分段日志缩小范围；但 anomaly detection 有额外开销，应在最小复现上使用。

常见组合包括：FP16 溢出、mask 使一整行没有可见 key、loss 分母为零、学习率过大、异常数据、梯度裁剪顺序错误。每种原因都需要一个反事实实验，例如把 dtype 换成 fp32、移除一个 mask、限制学习率或替换单个 batch，然后观察 NaN 是否消失。

### 10.9.4 GPU 利用率低

低利用率不是单一指标。需要分开测量 DataLoader、host-to-device copy、forward、backward、optimizer、同步和通信：

~~~math
T_{\mathrm{step}}=
T_{\mathrm{input}}+T_{\mathrm{forward}}+T_{\mathrm{backward}}
 +T_{\mathrm{optimizer}}+T_{\mathrm{sync}}.
~~~

CUDA kernel 是异步提交的，CPU 端的计时若没有同步，可能只测到提交时间。Profiler 适合捕捉短窗口，不能默认代表完整训练；应记录 warmup、active steps、batch shape、dtype 和是否启用了 compile。

## 10.10 Transformer 组件的工程审查

第九章已经给出完整实现，本节只保留审查时最容易遗漏的联系。

### 10.10.1 attention 的四个同时条件

一个 attention 实现要同时满足：

1. Q/K/V 的 head 形状正确。
2. score 除以 sqrt(D_h)，softmax 在 key 维。
3. 完整训练使用下三角 mask，不能读取未来。
4. decode 时 T_q 和 T_k 可不同，历史 cache 和 RoPE position offset 一致。

只满足第 1 条的代码可能完全能运行，却在训练目标或生成结果上错误。

### 10.10.2 RoPE 与 cache 的一致性

prefill 的位置通常是 0...P-1；长度为 P 的 cache 之后，新 token 的位置从 P 开始。历史 K 已经旋转过，不能再次旋转；新 Q/K 必须用当前位置旋转。最有信息量的测试不是“cache 长度变大”，而是：

~~~text
一次性计算 [token 0 ... token 4]
与
先计算 [token 0 ... token 3]，再用 cache 计算 token 4
~~~

两者最后位置的 logits 应在 dtype 容许误差内一致。若 shape 通过但数值不一致，优先检查位置偏移、历史 K 重复旋转和矩形 causal mask。

### 10.10.3 loss、mask 和 tokenizer 的边界

模型代码可以正确地执行 shift，但如果 tokenizer 的 special token、padding side、chat template 或 assistant-only label mask 与数据版本不匹配，结果仍然错误。模型实现、数据管线和评估脚本必须把这些协议作为同一版本的 artifact 保存，不能只保存权重文件。

## 10.11 三个综合事故：如何把判断落到行动

### 10.11.1 事故一：loss 异常低，验证却失败

训练日志中的 loss 从 2.1 快速降到 0.2，但独立验证没有提升。第一反应不应是“模型过拟合”，而是检查监督信号：

1. 是否把 label 原位作为输入，导致模型看到要预测的 token？
2. causal mask 是否写成了允许未来的上三角？
3. padding 或 prompt-only 部分是否错误地被当作目标？
4. 训练和验证的 tokenizer/template 是否一致？
5. 日志是否在不同有效 token 分母下比较？

最小实验是用四个 token 构造手算样本，打印每个位置的可见 key 和 target label，再分别运行正确与错误版本。只有复现了异常差异，才有理由修改完整数据管线。

### 10.11.2 事故二：恢复训练后出现 loss spike

恢复后第一步 loss 突然变大，可能是只加载了模型权重，丢失 AdamW 的动量/二阶矩；也可能 scheduler 从零开始，数据游标重复，或者随机状态改变了 dropout。排查顺序：

1. 比较恢复前后的 optimizer state 数量和 step。
2. 打印恢复前后学习率和 scheduler last step。
3. 确认下一批数据 id 与中断前约定一致。
4. 在 eval 模式比较固定 batch 的 logits。
5. 在小规模环境中恢复两次，比较下一次随机操作。

如果固定 batch 的 logits 一致但训练仍 spike，问题更可能在 optimizer、scheduler、数据进度或随机状态，而不是模型权重。

### 10.11.3 事故三：多卡 loss 比单卡好看

单卡报告 0.9，四卡报告 0.7，不能直接说多卡训练更好。先确认：

1. 报告的是 local mean、rank mean 还是 global token mean？
2. global batch 是否改变，学习率和 warmup 是否按约定缩放？
3. DistributedSampler 是否补样本或重复数据？
4. 每个 rank 的有效 token 数是否相同？
5. 评估集和 reduction 是否完全一致？

用合成的两个 rank 例子计算 0.875 与 0.8，通常比先跑完整模型更快地暴露统计口径问题。

## 10.12 最小可运行工程审计 demo

下面的 demo 把上述不变量放进一个很小的语言模型训练步骤。它不试图测量 GPU 性能，而是验证：

1. 变长样本经过 collate 后，padding 不进入 loss。
2. shift loss 有正确的有效 token 分母。
3. backward 产生有限梯度，optimizer 确实改变参数。
4. checkpoint 恢复后，固定输入的 logits 与保存时一致。
5. transpose 后显式修复 layout。
6. rank mean 与 global token mean 的分母不同。

~~~python
import copy
from dataclasses import dataclass

import torch
import torch.nn.functional as F
from torch import nn


@dataclass
class TinyConfig:
    vocab_size: int = 19
    hidden_size: int = 12
    pad_id: int = 0
    ignore_index: int = -100


def collate_token_samples(samples, pad_id, ignore_index):
    if not samples:
        raise ValueError("samples must not be empty")
    if any(len(sample) == 0 for sample in samples):
        raise ValueError("empty samples are not valid training examples")
    max_len = max(len(sample) for sample in samples)
    input_ids = torch.full((len(samples), max_len), pad_id, dtype=torch.long)
    labels = torch.full((len(samples), max_len), ignore_index, dtype=torch.long)
    for row, sample in enumerate(samples):
        values = torch.tensor(sample, dtype=torch.long)
        input_ids[row, : len(sample)] = values
        labels[row, : len(sample)] = values
    return {"input_ids": input_ids, "labels": labels}


def shifted_token_loss(logits, labels, ignore_index=-100):
    if logits.ndim != 3 or labels.ndim != 2:
        raise ValueError("logits must be [B,T,V] and labels must be [B,T]")
    if logits.shape[:2] != labels.shape:
        raise ValueError("logits and labels have incompatible batch/sequence shapes")
    shift_logits = logits[:, :-1, :].contiguous()
    shift_labels = labels[:, 1:].contiguous()
    valid_tokens = int((shift_labels != ignore_index).sum().item())
    if valid_tokens == 0:
        raise ValueError("the batch has no valid next-token labels")
    loss = F.cross_entropy(
        shift_logits.view(-1, shift_logits.size(-1)),
        shift_labels.view(-1),
        ignore_index=ignore_index,
    )
    return loss, valid_tokens


class TinyLM(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.embed = nn.Embedding(config.vocab_size, config.hidden_size)
        self.norm = nn.LayerNorm(config.hidden_size)
        self.head = nn.Linear(config.hidden_size, config.vocab_size, bias=False)
        self.head.weight = self.embed.weight

    def forward(self, input_ids, labels=None):
        hidden = self.norm(self.embed(input_ids))
        logits = self.head(hidden)
        loss = None
        valid_tokens = None
        if labels is not None:
            loss, valid_tokens = shifted_token_loss(logits, labels)
        return {"logits": logits, "loss": loss, "valid_tokens": valid_tokens}


def train_step(model, optimizer, batch):
    model.train()
    optimizer.zero_grad(set_to_none=True)
    output = model(batch["input_ids"], labels=batch["labels"])
    loss = output["loss"]
    if not torch.isfinite(loss):
        raise FloatingPointError("loss is not finite")
    loss.backward()
    grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    if not torch.isfinite(grad_norm):
        raise FloatingPointError("gradient norm is not finite")
    optimizer.step()
    return {
        "loss": float(loss.detach()),
        "valid_tokens": output["valid_tokens"],
        "grad_norm": float(grad_norm.detach()),
    }


def clone_state_dict(state_dict):
    return {key: value.detach().clone() for key, value in state_dict.items()}


def make_checkpoint(model, optimizer):
    return {
        "model": clone_state_dict(model.state_dict()),
        "optimizer": copy.deepcopy(optimizer.state_dict()),
        "rng": torch.get_rng_state().clone(),
    }


def restore_checkpoint(model, optimizer, checkpoint):
    model.load_state_dict(checkpoint["model"])
    optimizer.load_state_dict(checkpoint["optimizer"])
    torch.set_rng_state(checkpoint["rng"])


torch.manual_seed(13)
torch.set_num_threads(1)
config = TinyConfig()
samples = [[1, 2, 3, 4], [2, 3], [4, 5, 6, 7, 8]]
batch = collate_token_samples(samples, config.pad_id, config.ignore_index)
model = TinyLM(config)
optimizer = torch.optim.AdamW(model.parameters(), lr=0.05)

before_state = clone_state_dict(model.state_dict())
before = model(batch["input_ids"], labels=batch["labels"])
step_info = train_step(model, optimizer, batch)
after_state = clone_state_dict(model.state_dict())
checkpoint = make_checkpoint(model, optimizer)

with torch.no_grad():
    saved_logits = model(batch["input_ids"])["logits"].clone()

with torch.no_grad():
    for parameter in model.parameters():
        parameter.add_(0.25)
restore_checkpoint(model, optimizer, checkpoint)
with torch.no_grad():
    restored_logits = model(batch["input_ids"])["logits"]

matrix = torch.arange(12).view(3, 4)
transposed = matrix.transpose(0, 1)
layout_fixed = transposed.contiguous().view(12)

rank_loss_sums = [4.0, 12.0]
rank_valid_tokens = [4, 16]
rank_means = [
    loss_sum / token_count
    for loss_sum, token_count in zip(rank_loss_sums, rank_valid_tokens)
]
rank_mean = sum(rank_means) / len(rank_means)
global_token_mean = sum(rank_loss_sums) / sum(rank_valid_tokens)

summary = {
    "batch_shape": tuple(batch["input_ids"].shape),
    "valid_tokens": step_info["valid_tokens"],
    "loss_finite": bool(torch.isfinite(before["loss"])),
    "gradient_norm": round(step_info["grad_norm"], 4),
    "parameters_changed": any(
        not torch.equal(before_state[name], after_state[name])
        for name in before_state
    ),
    "checkpoint_restored": bool(torch.allclose(saved_logits, restored_logits)),
    "layout_fixed_shape": tuple(layout_fixed.shape),
    "rank_mean": round(rank_mean, 4),
    "global_token_mean": round(global_token_mean, 4),
}

checks = {
    "batch_is_padded": summary["batch_shape"] == (3, 5),
    "valid_token_count": summary["valid_tokens"] == 8,
    "finite_loss": summary["loss_finite"],
    "finite_gradient": torch.isfinite(torch.tensor(summary["gradient_norm"])).item(),
    "optimizer_updated": summary["parameters_changed"],
    "checkpoint_round_trip": summary["checkpoint_restored"],
    "layout_contract": summary["layout_fixed_shape"] == (12,),
    "different_reductions": summary["rank_mean"] != summary["global_token_mean"],
}

signals = []
actions = []
if summary["valid_tokens"] != (sum(len(sample) for sample in samples) - len(samples)):
    signals.append("valid-token denominator mismatch")
    actions.append("inspect collate and shift labels")
if not checks["finite_loss"] or not checks["finite_gradient"]:
    signals.append("non-finite training signal")
    actions.append("inspect input, mask, dtype and learning rate")
if not checks["optimizer_updated"]:
    signals.append("optimizer did not update parameters")
    actions.append("inspect graph, optimizer parameter list and zero_grad")
if not checks["checkpoint_round_trip"]:
    signals.append("checkpoint round trip mismatch")
    actions.append("inspect model, optimizer, RNG and version state")
if checks["different_reductions"]:
    signals.append("rank mean differs from global token mean")
    actions.append("choose and document the intended reduction")

decision = "continue_to_next_experiment" if all(checks.values()) else "repair_contract"
print("summary=", summary)
print("checks=", checks)
print("signals=", signals)
print("actions=", actions)
print("decision=", decision)
~~~

这里有效 token 数是 4-1 + 2-1 + 5-1 = 8。padding 后输入长度为 5，但第二条样本的 padding label 不会计入 shift loss。demo 中的 rank mean 是 0.875，global token mean 是 0.8；两者不同不是 bug，而是告诉我们必须先选择训练和日志所需的统计对象。

在项目虚拟环境中运行这段代码后，预期得到 loss_finite=True、parameters_changed=True、checkpoint_restored=True、rank_mean=0.875、global_token_mean=0.8，所有 checks 为 True，decision 为 continue_to_next_experiment。如果输出不同，先检查 PyTorch 版本、代码块是否完整，以及是否把 demo 的随机状态或模型模式改掉。

## 10.13 如何把一个工程判断写成可复现结论

一个成熟的复盘记录至少应包含：

~~~text
问题现象
基线版本
候选原因
最小实验
观测值和分母
结论的适用条件
仍未证实的部分
下一次回归测试
~~~

例如，“梯度累积修复了 loss 波动”还不够。应记录 accumulation steps、每个窗口的有效 token 数、loss reduction、学习率 schedule、是否使用 AMP、修复前后的 seed，以及在独立验证切片上的变化。若只在一个 seed、一个 batch 上看到改善，结论应写成“该合成实验支持这个实现差异”，不能写成普遍性能提升。

### 10.13.1 代码审查的优先级

审查一个训练脚本时，可以按以下顺序：

1. 数据和 label 是否有明确版本与分母。
2. shape、dtype、device 和 mask 是否有断言。
3. forward、loss、backward 和 optimizer step 的状态是否闭合。
4. AMP、梯度裁剪和梯度累积的顺序是否正确。
5. checkpoint 是否能在固定输入上完成 round trip。
6. 分布式 sampler、collective 和指标聚合是否有 rank 证据。
7. 日志、profiler 和异常路径是否不会改变被测行为。
8. 性能数字是否绑定硬件、版本、batch、序列长度和 dtype。

这个顺序先排除会让结果失去意义的实现错误，再讨论速度和模型质量。没有契约和回归测试支撑的微优化，通常很难解释收益来自哪里。

### 10.13.2 一次小型工程评审的输出

对于本章贯穿的 tiny language model，一份有用的评审结论应类似：

~~~text
shape 和有效 token 契约已通过最小 batch 验证；
loss、梯度和参数更新均为有限且可观察；
checkpoint 在固定输入上完成 round trip；
多 rank 例子显示 rank mean 与 global token mean 不同，生产实现必须选定 reduction；
Transformer cache 还需使用第九章的 prefill/decode 一致性测试；
真实吞吐和显存尚未由该 CPU demo 证明。
~~~

这段结论既没有夸大，也没有把一个 demo 当成生产验收。它指出了已经被实验支持的部分和需要继续实测的部分。

## 10.14 练习：把口述变成实验

1. 构造一个长度为 4 的 token 样本和一个长度为 2 的样本，手算 shift 后的有效 label 数。
2. 故意把 labels[:,1:] 改成 labels[:,:-1]，比较一个固定 batch 的 loss，并说明为什么这不是简单的数值误差。
3. 写一个 collate 函数，分别支持 right padding 和 left padding；列出 attention mask、position id 和 labels 的变化。
4. 在一个包含 Dropout 的 tiny model 上比较 train/eval 与 no_grad/inference_mode 的作用。
5. 将本章 optimizer 改为梯度累积，分别实现 micro-batch 等权和有效 token 等权，使用不同长度样本比较更新方向。
6. 只保存模型权重后恢复训练，再保存完整 optimizer/scheduler 状态；比较两次恢复的下一步学习率和参数变化。
7. 用两个 rank 的 loss sum 和有效 token 数构造三个不同分布，比较 rank mean、sample mean 与 global token mean。
8. 写一个事件日志记录器，模拟某个 rank 没有进入 all-reduce 的 collective hang，并由日志推断最后一个共同事件。
9. 让一个 fp16 toy computation 产生非有限值，分别使用更小学习率、fp32 accumulation 和梯度裁剪验证候选原因。
10. 对第九章的 Transformer 实现运行一次完整 forward，再运行 prefill/decode；故意把 RoPE start position 固定为零，观察哪一个一致性检查失败。
11. 为 checkpoint 增加数据版本、tokenizer 版本和 git revision；设计一个版本不匹配时的恢复错误信息。
12. 用 profiler 只采集 warmup 后的两个 active step，说明这个 trace 能证明什么、不能证明什么。

这些页面可以支持 API 的调用和状态语义。梯度累积是否改变最终质量、AMP 的速度、DDP 的扩展效率、FSDP 的峰值显存、checkpoint 的恢复耗时，都依赖具体模型、数据、硬件、版本和调度方式，需要目标环境实验。第九章引用的 Transformer 与 RoFormer 论文支持 attention 和 RoPE 的公开定义，但不能证明所有现代 LLM 都采用完全相同的配置。

## 10.16 本章总结

工程知识的核心不是把术语排列成一段流畅的话，而是把现象、机制、状态、数量关系和证据连接起来。读者应能从一个最小 batch 开始，确认 shape 和有效 token，再确认梯度和参数更新；从一个 checkpoint 开始，确认模型、优化器、scheduler、随机状态和数据进度；从一个多卡指标开始，确认 rank mean 和 global token mean 的分母；从一个 Transformer cache 开始，确认矩形 mask、RoPE position 和 prefill/decode 的一致性。

本册前九章提供了这些组件的实现基础，本章把它们组织成工程判断和回归实验。教学 demo 证明的是一组局部不变量，不是目标生产系统的吞吐、稳定性或模型质量。凡是涉及真实性能、公开模型结构、价格、上下文长度和 benchmark 的结论，都应绑定版本、配置、硬件、数据和评测协议，并保留资料与实测之间的边界。
