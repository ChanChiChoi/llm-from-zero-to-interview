# 第六章：混合精度与显存优化

大模型训练最常见的两个资源瓶颈是显存和算力。本章讨论如何在尽量不损失模型质量的前提下，降低显存占用、提高吞吐并避免数值不稳定。核心手段包括混合精度训练、梯度缩放、activation checkpointing、梯度累积、参数和激活的显存规划，以及对 OOM 的系统性排查。

很多训练脚本不是模型不对，而是显存吃不下：batch size 太大、序列太长、激活太多、优化器状态太重、没有用 AMP、梯度没有及时释放、保存了多余中间 tensor、DataLoader 把 batch 预取得过多、验证时忘了关梯度。本章的目标是建立一个对显存有感知的训练思维。

## 0. 本讲范围与资料

本章参考已核对 PyTorch 官方 AMP / `torch.amp.autocast` / `torch.amp.GradScaler`、Automatic Mixed Precision examples、`torch.utils.checkpoint.checkpoint`、CUDA memory management 和 `torch.cuda.memory_allocated` / `memory_reserved` / `max_memory_allocated` 文档口径。

本章聚焦大模型训练中最常见的混合精度与显存优化问题：FP32 / FP16 / BF16 的存储和数值边界、`autocast`、`GradScaler`、loss scaling / unscale、activation checkpointing、梯度累积、参数 / 梯度 / optimizer state / activation 显存估算、显存泄漏和 OOM 排查。

本章不展开 FP8 训练、ZeRO / FSDP 参数分片、Tensor Parallel、Sequence Parallel、FlashAttention kernel 内部、CUDA allocator 细节、NVIDIA Nsight profiling 或生产级显存调度器。这些内容会在分布式训练、推理框架、AI Infra 和性能 profiling 章节中展开。

## 6.1 显存到底花在什么地方

训练时显存通常分成几类：

1. 模型参数。
2. 梯度。
3. 优化器状态。
4. 前向激活。
5. 临时 workspace 和 kernel buffer。
6. 输入 batch 和中间缓存。

粗略理解：

1. 参数是模型本体。
2. 梯度是 backward 的结果。
3. 优化器状态通常比参数还大，尤其是 Adam 系列。
4. 激活和序列长度、batch size、层数强相关。
5. 临时 buffer 取决于算子实现和 kernel。

在大模型训练里，很多时候真正的瓶颈不是参数，而是激活和优化器状态。

同一个模型在“参数能放进显存”和“能够完成一次训练 step”之间，可能相差很远。推理通常只需要参数和少量临时张量；训练还要保留梯度、优化器状态和反向传播需要的激活。因此排查 OOM 前，先判断失败发生在模型加载、forward、backward、optimizer step 还是验证阶段，后面的可行方案才有意义。

### 6.1.1 关键公式与显存调试速查

第一，单个 tensor 的存储量可以粗略写成：

~~~math
M(X)=n(X)\cdot b(X)
~~~

其中 `n(X)` 是元素个数，`b(X)` 是每个元素的字节数。这里假定 tensor 已经确定 dtype，且只估算数据载荷，不计对象元数据、对齐和 allocator 的额外开销。常见情况下，FP32 是 4 bytes，FP16 / BF16 是 2 bytes。

第二，训练显存可以粗略分解为：

~~~math
M_{\mathrm{train}}
\approx M_{\mathrm{param}}+M_{\mathrm{grad}}+M_{\mathrm{opt}}+M_{\mathrm{act}}+M_{\mathrm{tmp}}
~~~

其中 `M_param` 是参数，`M_grad` 是梯度，`M_opt` 是 optimizer state，`M_act` 是前向激活，`M_tmp` 是临时 workspace、kernel buffer 和缓存。

第三，AdamW 常见状态显存大致是：

~~~math
M_{\mathrm{AdamW}}\approx 2P b_{\mathrm{state}}
~~~

其中 `P` 是参数个数，`b_state` 是一阶矩和二阶矩的存储字节数。如果状态使用 FP32，则每个参数额外需要约 8 bytes 的 optimizer state。

第四，Transformer 激活显存可以粗略理解为随 batch、序列长度、hidden size 和层数线性增长：

~~~math
M_{\mathrm{act}}\propto B T d L b_{\mathrm{act}}
~~~

其中 `B` 是 batch size，`T` 是 sequence length，`d` 是 hidden size，`L` 是层数，`b_act` 是激活 dtype 字节数。实际 attention、中间 MLP、checkpointing 和 kernel 实现会改变常数项。

这里的线性式只适用于某一类保存的 hidden state，不能拿来估算所有 attention 内存。朴素全注意力还会产生形状近似为 `[B, H, T, T]` 的 score/probability 中间量，因此其元素数包含：

~~~math
N_{\mathrm{attn}}\propto B H T^2,
~~~

其中 `H` 是 attention head 数。序列长度从 `T` 增加到 `2T` 时，若实现显式保留这个矩阵，相关中间量可能增加约 4 倍；FlashAttention 一类实现通过分块计算减少对完整 `T\times T` 矩阵的保存，但并不意味着 attention 的计算复杂度自动变成线性。估算显存时应区分“理论 score 矩阵”“kernel 实际 workspace”和“反向所需保存的统计量”。

第五，activation checkpointing 的核心取舍是：

~~~math
M_{\mathrm{act}}^{\mathrm{ckpt}} < M_{\mathrm{act}},\qquad
C_{\mathrm{backward}}^{\mathrm{ckpt}} > C_{\mathrm{backward}}
~~~

也就是用反向时额外重算一部分 forward，换取更低的前向激活保存量。

第六，loss scaling 的数值直觉是：

~~~math
\tilde{L}=sL,\qquad
\nabla_\theta \tilde{L}=s\nabla_\theta L,\qquad
g=\frac{1}{s}\nabla_\theta \tilde{L}
~~~

其中 `s` 是 scale factor。FP16 中先放大 loss 可以减少小梯度下溢风险；optimizer step 前要 unscale 回真实梯度，再做 gradient clipping。

这些公式是数量级估算，不是显存报告。参数可能以 FP32 master weight、BF16/FP16 compute weight 或量化格式分别存在；optimizer state 可能被分片、懒初始化或放在 CPU；allocator 还会保留已经申请过的缓存。因此必须把公式估算和运行时的 `allocated`、`reserved`、`peak` 读数放在一起看。

### 6.1.2 一个数量级例子

假设模型有 `P=1,000,000,000` 个参数，参数和梯度使用 2 bytes，AdamW 的一阶矩和二阶矩使用 FP32。仅这三项的理想下界约为：

~~~math
M_{\mathrm{param}}=P\times2\text{ bytes}\approx1.86\text{ GiB},
\quad
M_{\mathrm{grad}}\approx1.86\text{ GiB},
\quad
M_{\mathrm{opt}}=P\times2\times4\text{ bytes}\approx7.45\text{ GiB}.
~~~

合计已经接近 `11.17 GiB`，还没有包含激活、临时 buffer、CUDA context、碎片和模型可能保留的 FP32 master copy。这个例子说明，单纯把 batch size 调小并不能解决 optimizer state 在加载阶段就超出显存的问题；此时要考虑状态分片、CPU offload、不同 optimizer 或更大显存设备。

## 6.2 为什么需要混合精度

传统上很多训练用 fp32。fp32 精度高，但显存和带宽开销大。

混合精度训练的思路是：

1. 用较低精度存储和计算大部分张量。
2. 保留少数关键位置使用较高精度。
3. 在数值敏感环节保持稳定。

常见组合：

1. fp16。
2. bf16。
3. fp32 + amp。

它的目标不是“全部变低精度”，而是找到质量、性能和显存之间的平衡点。

优势：

1. 显存更省。
2. 带宽压力更小。
3. 通常训练更快。

代价：

1. 数值更脆弱。
2. 某些算子容易溢出或下溢。
3. 需要更多工程控制。

混合精度不是简单执行 `model.half()`。后者会把模型参数和许多运算强制改成 FP16，可能让归一化、softmax、损失和优化器状态同时落入不合适的精度；AMP 则根据算子策略选择计算 dtype，并允许敏感路径保持更高精度。最终是否有收益，还取决于硬件是否有对应的低精度矩阵乘法吞吐、输入搬运是否成为瓶颈，以及额外的 cast 是否抵消了收益。

## 6.3 FP16 和 BF16 的区别

fp16 和 bf16 都是 16 位浮点，但表示方式不同。

### 6.3.1 FP16

fp16 的优点是：

1. 计算和存储都省。
2. 在很多 GPU 上支持成熟。

缺点是：

1. 指数范围较小。
2. 更容易溢出、下溢。
3. 训练时通常要配合 GradScaler。

### 6.3.2 BF16

bf16 的指数范围接近 fp32，动态范围更大。

优点是：

1. 更不容易数值溢出。
2. 大模型训练通常更稳。
3. 在很多现代硬件上支持很好。

缺点是：

1. 尾数精度比 fp16 低。
2. 某些硬件或旧环境支持不如 fp16 普遍。

### 6.3.3 用表示范围理解差异

FP16 使用 5 位指数和 10 位小数位，BF16 使用 8 位指数和 7 位小数位。前者有更细的尾数精度，后者保留了接近 FP32 的指数范围。用通常的 IEEE 754 规格作数量级理解，FP16 的最大有限值约为 `6.55\times10^4`，最小正规格正数约为 `6.10\times10^{-5}`；BF16 的最大有限值接近 `3.39\times10^{38}`，动态范围接近 FP32，但相邻可表示数的间隔更粗。

因此“BF16 更稳”主要指溢出/下溢边界更宽，不表示 BF16 对所有运算都更精确。模型中如果某条路径需要细粒度小数差异，仍可能需要 FP32 累加；如果硬件不支持 BF16 的高效 kernel，理论上的数值优势也可能换来更低吞吐。

工程上常见判断：

1. 如果硬件和框架支持良好，bf16 往往更省心。
2. 如果只能用 fp16，通常要配合 GradScaler。

选择精度时应记录至少四个观测量：训练 loss 是否非有限、梯度裁剪触发比例、有效 token/s 和验证指标。不能只因为 BF16 能运行就断定它比 FP16 更好，也不能只比较单步耗时而忽略 loss scale 频繁回退或最终质量下降。

## 6.4 autocast：自动混合精度

PyTorch 的 AMP 通过 `autocast` 自动把合适的算子放到低精度执行。

示例：

```python
import torch

with torch.amp.autocast("cuda", dtype=torch.float16):
    logits = model(input_ids)
    loss = criterion(logits, labels)
```

直觉：

1. 某些算子适合低精度，比如大部分矩阵乘法。
2. 某些算子更适合保留高精度，比如 softmax、归一化、loss 计算中的敏感部分。
3. `autocast` 负责自动选择。

工程意义：

1. 减少手动 dtype 管理。
2. 更容易获得性能收益。
3. 降低写错精度策略的概率。

但要记住：`autocast` 不是万能的。它只是帮助管理前向中的算子精度，仍然需要结合模型结构和具体异常去判断。

`autocast` 的作用范围也必须说清楚：它主要包住 forward 和 loss 计算，不负责清梯度、缩放 loss、裁剪梯度或更新参数。进入上下文前后的输入 dtype 不一定改变，某个算子的输出 dtype 由 AMP 的算子策略决定。需要手工恢复高精度的局部计算可以使用嵌套上下文：

```python
with torch.amp.autocast("cuda", dtype=torch.float16):
    hidden = model_backbone(input_ids)
    with torch.amp.autocast("cuda", enabled=False):
        stable_value = sensitive_loss(hidden.float(), labels)
```

示例中的 `sensitive_loss` 只是说明边界，实际是否需要禁用 autocast 要通过异常复现和指标验证决定。不要在每个算子周围随意切换 dtype，否则 cast 开销和代码复杂度可能超过收益。

## 6.5 GradScaler：解决 fp16 的数值问题

fp16 训练容易遇到梯度太小导致下溢。`GradScaler` 的做法是先放大 loss，再反向传播，再把梯度缩回去。

典型结构：

```python
import torch

scaler = torch.amp.GradScaler("cuda")

for batch in train_loader:
    optimizer.zero_grad(set_to_none=True)

    with torch.amp.autocast("cuda", dtype=torch.float16):
        outputs = model(**batch)
        loss = outputs["loss"]

    scaler.scale(loss).backward()
    scaler.unscale_(optimizer)
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)
    scaler.update()
```

关键步骤：

1. `scale(loss)` 放大 loss。
2. `backward()` 在放大后的尺度上计算梯度。
3. `unscale_(optimizer)` 把梯度缩回来。
4. 必要时再做梯度裁剪。
5. `step` 和 `update` 完成参数更新和缩放因子调整。

为什么要先 `unscale_` 再裁剪？因为裁剪的是实际梯度，不是被放大的临时梯度。

bf16 通常不那么依赖 GradScaler，但代码结构上仍可以保持一致。

### 6.5.1 为什么必须在 unscale 后裁剪

假设真实梯度范数为 `0.8`，loss scale 为 `1024`。缩放后的梯度范数是 `819.2`。若直接执行 `clip_grad_norm_(..., max_norm=1.0)`，得到的缩放梯度会被压到约 `1.0`，随后再 unscale 后只剩约 `0.00098`，真实梯度被错误缩小了 1024 倍。先 `unscale_` 再裁剪，裁剪对象才是 `0.8` 这个真实范数。

此外，一个 optimizer 在同一 iteration 内通常只能调用一次 `unscale_`；如果有多个 optimizer，要分别处理。`scaler.step(optimizer)` 会在检测到非有限梯度时跳过这次参数更新，`scaler.update()` 再根据结果调整 scale。训练日志应记录“是否真正执行了 optimizer step”，不能把每次循环都算作一次参数更新。

## 6.6 mixed precision 训练的推荐模板

一个常见训练模板：

```python
scaler = torch.amp.GradScaler("cuda", enabled=use_fp16)

for batch in train_loader:
    batch = move_to_device(batch, device)
    optimizer.zero_grad(set_to_none=True)

    with torch.amp.autocast("cuda", dtype=torch.float16, enabled=use_amp):
        outputs = model(**batch)
        loss = outputs["loss"]

    if use_fp16:
        scaler.scale(loss).backward()
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(optimizer)
        scaler.update()
    else:
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
```

这里要注意：

1. `autocast` 控制前向精度。
2. `GradScaler` 主要服务 fp16。
3. `bf16` 训练通常不需要缩放，但也可以保留统一结构。

如果把本章的梯度累积也加入进来，缩放顺序是：先用窗口定义把 loss 除以 `accum_steps` 或有效 token 总数，再交给 `scaler.scale()`。在真实梯度层面，流程应是：

~~~math
L_{\mathrm{micro}}\rightarrow
\frac{L_{\mathrm{micro}}}{D_W}\rightarrow
s\frac{L_{\mathrm{micro}}}{D_W}\rightarrow
\text{backward}\rightarrow
\text{unscale}\rightarrow
\text{clip}\rightarrow
\text{step}.
~~~

其中 `D_W` 是当前窗口的正确分母，`s` 是 GradScaler 的 scale。若先累积未归一化的梯度再临时除以 `accum_steps`，代码会更容易在最后不完整窗口或动态 token 数上出错。使用 AMP 时还要在 checkpoint 中保存 `scaler.state_dict()`；否则恢复训练时 loss scale 可能突然回到初始值或与此前轨迹不同。

带梯度累积的结构示意：

```python
scaler = torch.amp.GradScaler("cuda", enabled=use_fp16)
optimizer.zero_grad(set_to_none=True)

for micro_step, batch in enumerate(train_loader):
    with torch.amp.autocast("cuda", dtype=amp_dtype, enabled=use_amp):
        outputs = model(**batch)
        raw_loss = outputs["loss"]
        loss = raw_loss / window_size

    if use_fp16:
        scaler.scale(loss).backward()
    else:
        loss.backward()

    if is_window_end:
        if use_fp16:
            scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        if use_fp16:
            scaler.step(optimizer)
            scaler.update()
        else:
            optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```

代码还应在非有限 `raw_loss`、全忽略 label、梯度裁剪返回非有限值时停止或保存坏 batch；AMP 不是异常数据的过滤器。

## 6.7 activation checkpointing

activation checkpointing 的核心思想是：前向时少存一部分激活，反向时再重新计算这部分前向，从而用计算换显存。

直觉：

1. 普通训练保留很多中间激活，方便 backward。
2. checkpointing 只保留关键节点。
3. backward 时重新跑部分 forward 来恢复中间值。

PyTorch 里可以这样用：

```python
from torch.utils.checkpoint import checkpoint


def forward_block(x, block):
    return checkpoint(block, x, use_reentrant=False)
```

或者在模型里包住某些子模块。

优点：

1. 明显省显存。
2. 可以支持更长序列或更大 batch。

缺点：

1. backward 更慢，因为要重算前向。
2. 代码结构更复杂。

### 6.7.1 重算与随机性的边界

checkpointing 的 backward 会再次执行被包裹的 forward。若 block 内有 Dropout，第二次执行必须使用与第一次一致的随机状态，才能得到与普通 autograd 接近的梯度。PyTorch checkpoint 接口会处理一部分 RNG 状态保存与恢复，但这会增加额外开销；如果设置 `preserve_rng_state=False`，可能获得更低开销，却不再保证与非 checkpoint 路径相同的随机序列。跨 device、使用自定义随机源或在 checkpoint 函数外改变状态时，不能假设自动恢复覆盖所有情况。

还要满足 autograd 的输入边界：被 checkpoint 的函数至少应接收参与梯度计算的输入，且函数内部不要依赖每次调用都变化的外部可变状态。`use_reentrant=False` 是当前 PyTorch 文档推荐优先考虑的实现路径；具体版本的参数和限制仍应以目标环境文档为准。

### 6.7.2 checkpoint 粒度

把整个模型包成一个 checkpoint，可能节省更多激活，但会重复计算大量不必要的层；按每个 Transformer block 包装，通常在显存和重算时间之间更容易调节。实际应测量：峰值显存下降多少、单 step 时间增加多少、有效 token/s 变化多少，以及固定 seed 下 logits/梯度误差是否在可接受范围。checkpointing 是一种资源交换，不是无代价的开关。

适合：

1. Transformer block 很深的模型。
2. 长上下文训练。
3. 显存非常紧张的实验。

## 6.8 梯度累积和显存

梯度累积不仅是优化 batch size 的办法，也是显存优化手段。

如果一次只能放很小的 batch，就把多个 micro-batch 的梯度累积起来再更新。

示意：

```python
accum_steps = 8
optimizer.zero_grad(set_to_none=True)

for step, batch in enumerate(train_loader):
    with torch.amp.autocast("cuda", dtype=torch.float16, enabled=use_amp):
        outputs = model(**batch)
        loss = outputs["loss"] / accum_steps

    loss.backward()

    if (step + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```

优点：

1. 降低单次 forward/backward 的激活峰值。
2. 模拟更大 batch。

缺点：

1. 更新频率变低。
2. 训练吞吐不一定线性提升。

梯度累积只降低单次 forward/backward 的激活峰值，不会自动减少参数、梯度或 optimizer state 的常驻显存；并且保留梯度的时间更长。若 micro-batch 已经足够小而 OOM 发生在 optimizer 初始化或 `optimizer.step()`，继续增加 `accum_steps` 没有帮助。若 OOM 发生在 forward，才应优先考虑 batch、序列长度、AMP 或 checkpointing。

另外，梯度累积的有效 batch 计算应同时记录：

~~~math
B_{\mathrm{eff}}=B_{\mathrm{micro}}\times K\times W\times R,
~~~

其中 `K` 是累积步数，`W` 是每个 micro-batch 中的样本数，`R` 是 data-parallel rank 数。若使用 token 预算，还要改用有效 token 数而不是样本数；序列长度不同的两个 batch 即使样本数相同，也不等价。

## 6.9 影响显存的关键因素

显存不是只由 batch size 决定，还包括：

1. 序列长度。
2. 模型层数。
3. hidden size。
4. 注意力头数。
5. 精度。
6. optimizer 类型。
7. 是否保留中间激活。
8. 是否开启 checkpointing。
9. 是否存了额外的日志或缓存。

尤其对 Transformer 来说，序列长度增加往往会显著推高激活和 attention 相关开销。

可以把显存调参拆成两条曲线。参数/优化器曲线主要由参数量、dtype 和 optimizer 决定；激活曲线主要由 `B`、`T`、层数和实现决定。减小 `B` 会降低两者中的激活部分，但不会改变参数和 optimizer 常驻项；减小 `T` 会降低 hidden state 和 attention 中间量，尤其可能显著降低 `T^2` 项；改用 BF16/FP16 主要降低计算张量字节数，却不会自动把 FP32 optimizer state 变成 16 位。

一个实用判断：如果显存爆了，先问自己是参数太大、batch 太大、序列太长、还是优化器状态太重。

## 6.10 optimizer 状态为什么也占很多显存

以 Adam 为例，除了参数本身，还要保存一阶矩和二阶矩。

直觉上，每个参数可能对应：

1. 参数值。
2. 梯度。
3. 一阶矩。
4. 二阶矩。

所以 Adam 类优化器的总显存压力明显高于 SGD。

这也是为什么在超大模型训练里，经常会考虑：

1. 参数分片。
2. 优化器状态分片。
3. 更低精度状态。
4. 更省显存的训练策略。

本章重点不是展开分布式分片，而是先建立“optimizer 状态本身也很贵”的意识。

要避免把“理论上每参数 8 bytes”当成所有 AdamW 实现的精确答案。某些训练保留 FP32 master parameters，某些实现把状态放在 CPU 或按 rank 分片，某些状态在第一次 `step()` 前还没有创建。正确做法是先用公式估算上界，再在 optimizer 初始化、第一次 step 后分别读取内存，观察状态何时实际出现。若 OOM 恰好发生在第一次 optimizer step，激活可能已经释放，新增的 optimizer state 反而是主要原因。

## 6.11 训练中常见的显存优化顺序

当你遇到 OOM，可以按下面顺序试：

1. 减小 batch size。
2. 减小 sequence length。
3. 开启 mixed precision。
4. 开启 gradient accumulation。
5. 开启 activation checkpointing。
6. 检查是否保留了多余 tensor。
7. 检查 validation 是否忘了关梯度。
8. 检查 DataLoader 预取和 batch 缓存。

这个顺序的逻辑是：

1. 先改最直接影响显存的变量。
2. 再上混合精度和 checkpointing。
3. 最后排查代码层面的泄漏。

这个顺序不是固定处方。若模型参数本身已无法加载，应先处理参数/状态分片或量化；若只有长序列 forward OOM，优先减少 `T` 或使用更节省中间矩阵的 attention 实现；若显存随 step 单调增长，优先检查计算图引用；若 `reserved` 很高但 `allocated` 稳定，先判断是 allocator 缓存还是实际泄漏，再决定是否调整 allocator 配置。每次只改变一个变量，并记录峰值显存、step 时间和验证指标。

## 6.12 显存泄漏的常见来源

不是所有显存增长都是“模型太大”。很多是代码把图保留下来了。

常见来源：

1. 把带计算图的 loss 存进 list。
2. 把中间 activation 长期缓存。
3. 验证时没用 `no_grad` 或 `inference_mode`。
4. hook 里保存了未 detach 的 tensor。
5. 每步都把大 batch 的输出堆到内存里。
6. 重复创建没有释放的大 tensor。

如果怀疑泄漏，可以每隔几步打印：

```python
print(torch.cuda.memory_allocated() / 1024**2)
print(torch.cuda.memory_reserved() / 1024**2)
```

还可以更系统地用 PyTorch 的显存统计接口排查。

三个统计量含义不同：`memory_allocated()` 是当前仍被 tensor 使用的分配量，`memory_reserved()` 是 PyTorch caching allocator 向 CUDA 保留的总量，`max_memory_allocated()` 是从上次 reset 以来的 tensor 分配峰值。`reserved - allocated` 较大不一定是泄漏，可能只是缓存池；更有价值的实验是调用 `reset_peak_memory_stats()` 后执行固定 workload，比较每个阶段的峰值和 tensor 引用是否增长。不要在训练循环中无条件调用 `empty_cache()` 作为“修复”，它可能增加分配开销，且不能释放仍被 Python 引用的 tensor。

```python
torch.cuda.reset_peak_memory_stats()

# 执行一个固定的 forward/backward 或 validation 区间
peak_mib = torch.cuda.max_memory_allocated() / 1024**2
reserved_mib = torch.cuda.memory_reserved() / 1024**2
allocated_mib = torch.cuda.memory_allocated() / 1024**2
print({
    "peak_allocated_mib": round(peak_mib, 2),
    "allocated_mib": round(allocated_mib, 2),
    "reserved_mib": round(reserved_mib, 2),
})
```

## 6.13 OOM 排查方法

当出现 OOM 时，不要只盯着最后一行报错，要分层排查。

### 6.13.1 先看是训练还是验证

1. 如果训练 OOM，关注 batch、seq len、激活、梯度和 optimizer state。
2. 如果验证 OOM，重点看是否忘记关梯度、是否缓存了输出、是否 batch 过大。

### 6.13.2 先缩小 batch 和 sequence length

这是最直接的验证手段。若缩小后能跑，说明问题和激活/序列长度强相关。

### 6.13.3 检查是否在累积图

例如：

```python
losses.append(loss)
```

如果长期保存带图对象，显存会持续增长。

应该改成：

```python
losses.append(loss.item())
```

### 6.13.4 检查验证流程

验证时应：

1. `model.eval()`。
2. `torch.inference_mode()`。
3. 不做 backward。
4. 不把大输出长期保存在 GPU 上。

### 6.13.5 用峰值位置定位

可以在固定 batch 上给四个边界打点：模型加载后、forward 后、backward 后、optimizer step 后。若使用 CUDA，建议在计时和读峰值前同步设备，否则异步 kernel 可能让时间和峰值归属错位：

```python
def cuda_memory_snapshot(tag):
    if not torch.cuda.is_available():
        return {"tag": tag, "cuda": False}
    torch.cuda.synchronize()
    return {
        "tag": tag,
        "allocated_mib": round(torch.cuda.memory_allocated() / 1024**2, 2),
        "reserved_mib": round(torch.cuda.memory_reserved() / 1024**2, 2),
        "peak_mib": round(torch.cuda.max_memory_allocated() / 1024**2, 2),
    }
```

如果 forward 后峰值最高，优先看激活、`T` 和 attention；如果 backward 后才最高，查看反向临时 buffer 和 checkpoint 粒度；如果 optimizer step 后突然跳高，优先检查 Adam state 或 master copy；如果每一步结束后的 `allocated` 都上升，检查 Python 容器、hook 和日志是否仍持有计算图。这个时间线比笼统地说“显存不够”更接近可修复的根因。

## 6.14 一个完整 AMP + checkpointing 的训练骨架

```python
import torch
from torch.utils.checkpoint import checkpoint


def train_step(model, batch, optimizer, scaler, use_amp=True):
    optimizer.zero_grad(set_to_none=True)

    with torch.amp.autocast("cuda", dtype=torch.float16, enabled=use_amp):
        outputs = model(**batch)
        loss = outputs["loss"]

    if use_amp:
        scaler.scale(loss).backward()
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(optimizer)
        scaler.update()
    else:
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()

    return loss.item()
```

如果模型内部某些 block 需要 checkpointing，可以把对应子模块包装起来。重点是要理解：

1. AMP 解决的是精度和带宽问题。
2. checkpointing 解决的是激活显存问题。
3. 梯度累积解决的是单步 batch 太大的问题。

这三者经常一起用。

## 6.15 最小可运行 AMP 与显存审计 demo

下面这个 demo 不依赖 GPU，也可以在 CPU 上运行。它演示四件事：显存组成估算、`autocast` 会让适合的算子输出 BF16、`GradScaler` 的 scale / unscale / step 结构，以及 activation checkpointing 会在 backward 阶段重算部分 forward。

```python
import warnings

import torch
import torch.nn.functional as F
from torch import nn
from torch.utils.checkpoint import checkpoint

warnings.filterwarnings("ignore", message="CUDA initialization.*")

DTYPE_BYTES = {
    "fp32": 4,
    "fp16": 2,
    "bf16": 2,
}


def mib(num_bytes):
    return round(num_bytes / 1024**2, 3)


def estimate_memory(param_count, activation_elements, param_dtype="bf16", activation_dtype="bf16"):
    param_bytes = param_count * DTYPE_BYTES[param_dtype]
    grad_bytes = param_count * DTYPE_BYTES[param_dtype]
    adamw_state_bytes = 2 * param_count * DTYPE_BYTES["fp32"]
    activation_bytes = activation_elements * DTYPE_BYTES[activation_dtype]
    return {
        "params_mib": mib(param_bytes),
        "grads_mib": mib(grad_bytes),
        "adamw_states_mib": mib(adamw_state_bytes),
        "activations_mib": mib(activation_bytes),
        "total_mib": mib(param_bytes + grad_bytes + adamw_state_bytes + activation_bytes),
    }


class TinyMLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 4))

    def forward(self, x):
        return self.net(x)


torch.manual_seed(0)
model = TinyMLP()
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)
scaler = torch.amp.GradScaler("cpu")

x = torch.randn(6, 8)
y = torch.tensor([0, 1, 2, 3, 1, 0])
optimizer.zero_grad(set_to_none=True)
with torch.amp.autocast("cpu", dtype=torch.bfloat16):
    logits = model(x)
    loss = F.cross_entropy(logits, y)

autocast_dtype = str(logits.dtype).replace("torch.", "")
scale_before = scaler.get_scale()
scaler.scale(loss).backward()
scaler.unscale_(optimizer)
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
scaler.step(optimizer)
scaler.update()


class CountBlock(nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = nn.Linear(8, 8)
        self.calls = 0

    def forward(self, z):
        self.calls += 1
        return torch.relu(self.linear(z))


plain_block = CountBlock()
z = torch.randn(4, 8, requires_grad=True)
plain_block(z).sum().backward()
plain_calls = plain_block.calls

ckpt_block = CountBlock()
ckpt_block.load_state_dict(plain_block.state_dict())
z2 = torch.randn(4, 8, requires_grad=True)
checkpoint(ckpt_block, z2, use_reentrant=False).sum().backward()
ckpt_calls = ckpt_block.calls

estimate = estimate_memory(param_count=1_000_000, activation_elements=2_000_000)
print("memory_estimate=", estimate)
print("autocast_dtype=", autocast_dtype)
print("scaler_enabled=", scaler.is_enabled())
print("scale_before=", float(scale_before))
print("grad_norm_before_clip=", round(float(grad_norm), 4))
print("scale_after=", float(scaler.get_scale()))
print("checkpoint_calls=", {"plain": plain_calls, "checkpoint": ckpt_calls})
print("checkpoint_recomputed=", ckpt_calls > plain_calls)
print("cuda_available=", torch.cuda.is_available())
```

期望输出类似：

```text
memory_estimate= {'params_mib': 1.907, 'grads_mib': 1.907, 'adamw_states_mib': 7.629, 'activations_mib': 3.815, 'total_mib': 15.259}
autocast_dtype= bfloat16
scaler_enabled= True
scale_before= 65536.0
grad_norm_before_clip= 0.746
scale_after= 65536.0
checkpoint_calls= {'plain': 1, 'checkpoint': 2}
checkpoint_recomputed= True
cuda_available= False
```

这段输出要检查几件事：

1. AdamW 的两个 FP32 state 在估算中比 BF16 参数和梯度更大，说明 optimizer state 是训练显存大头之一。
2. `autocast_dtype=bfloat16`，说明 CPU autocast 已让线性层输出进入 BF16。
3. `scale_before=65536.0` 展示 GradScaler 的初始 loss scale；本例无溢出，所以 `scale_after` 不变。
4. `checkpoint_calls` 中 checkpoint 版本调用两次 forward，说明 backward 阶段发生了重算。
5. `cuda_available=False` 只是当前机器状态，不影响本 demo 解释 AMP 和 checkpointing 的核心机制。

## 6.16 工程中怎么选 fp16 和 bf16

简单经验：

1. 如果硬件支持良好且你希望更稳，优先 bf16。
2. 如果环境主要支持 fp16，使用 fp16 + GradScaler。
3. 如果发现训练频繁 NaN，先看学习率、初始化、loss、mask，再看换 bf16 是否更稳。

不要把“混合精度”理解成固定 recipe。它仍然要和模型结构、数据分布和硬件一起权衡。

## 6.17 常见误区

1. 以为 fp16 一定比 bf16 更好。实际上 bf16 往往更稳。
2. 以为 AMP 等于自动省一切显存。它主要解决精度和部分带宽问题，不是万能。
3. 以为 GradScaler 对所有混合精度都必须。bf16 通常不一定需要。
4. 以为 checkpointing 没有代价。它会增加 backward 计算量。
5. 以为 OOM 都是 batch 太大。也可能是 optimizer state、保存图或验证没关梯度。
6. 以为 loss 降低说明显存问题消失。数值稳定和显存问题是两个不同维度。

## 6.20 本章总结

混合精度与显存优化的核心不是背几个 API，而是建立资源感知的训练思维。

要记住的主线：

1. 显存主要花在参数、梯度、优化器状态、激活和临时 buffer。
2. fp16 和 bf16 都是混合精度方案，但 bf16 通常更稳。
3. `autocast` 管前向精度，`GradScaler` 主要解决 fp16 的数值问题。
4. activation checkpointing 用计算换显存。
5. 梯度累积可以模拟更大 batch 并缓解单步显存压力。
6. OOM 排查要区分训练、验证、显存泄漏和配置错误。
7. 一个好的训练脚本要同时考虑数值稳定、吞吐和显存峰值。
