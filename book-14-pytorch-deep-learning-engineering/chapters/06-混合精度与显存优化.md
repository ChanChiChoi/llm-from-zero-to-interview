# 第六章：混合精度与显存优化

大模型训练最常见的两个资源瓶颈是显存和算力。本章讨论如何在尽量不损失模型质量的前提下，降低显存占用、提高吞吐并避免数值不稳定。核心手段包括混合精度训练、梯度缩放、activation checkpointing、梯度累积、参数和激活的显存规划，以及对 OOM 的系统性排查。

很多训练脚本不是模型不对，而是显存吃不下：batch size 太大、序列太长、激活太多、优化器状态太重、没有用 AMP、梯度没有及时释放、保存了多余中间 tensor、DataLoader 把 batch 预取得过多、验证时忘了关梯度。本章的目标是建立一个对显存有感知的训练思维。

## 0. 本章范围与资料

本章的 PyTorch API 语义按固定的 [PyTorch 2.15 AMP](https://docs.pytorch.org/docs/2.15/amp.html)、[AMP examples](https://docs.pytorch.org/docs/2.15/notes/amp_examples.html)、[checkpoint](https://docs.pytorch.org/docs/2.15/checkpoint.html) 和 [CUDA memory management](https://docs.pytorch.org/docs/2.15/notes/cuda.html#memory-management) 文档说明；目标版本或设备不同，应核对对应文档并重新验证代码。

本章聚焦大模型训练中最常见的混合精度与显存优化问题：FP32 / FP16 / BF16 的存储和数值边界、`autocast`、`GradScaler`、loss scaling / unscale、activation checkpointing、梯度累积、参数 / 梯度 / optimizer state / activation 显存估算、显存泄漏和 OOM 排查。

本章不展开 FP8 训练、ZeRO / FSDP 参数分片、Tensor Parallel、Sequence Parallel、FlashAttention kernel 内部、CUDA allocator 细节、NVIDIA Nsight profiling 或生产级显存调度器。这些内容会在分布式训练、推理框架、AI Infra 和性能 profiling 章节中展开。

## 6.1 显存到底花在什么地方

训练时显存通常分成几类：

1. 模型参数。
2. 梯度。
3. 优化器状态。
4. 前向激活。
5. 临时 workspace 和 kernel buffer。
6. 输入 batch 和中间缓存。

粗略理解：

1. 参数是模型本体。
2. 梯度是 backward 的结果。
3. 优化器状态通常比参数还大，尤其是 Adam 系列。
4. 激活和序列长度、batch size、层数强相关。
5. 临时 buffer 取决于算子实现和 kernel。

在大模型训练里，很多时候真正的瓶颈不是参数，而是激活和优化器状态。

同一个模型在“参数能放进显存”和“能够完成一次训练 step”之间，可能相差很远。推理通常只需要参数和少量临时张量；训练还要保留梯度、优化器状态和反向传播需要的激活。因此排查 OOM 前，先判断失败发生在模型加载、forward、backward、optimizer step 还是验证阶段，后面的可行方案才有意义。

### 6.1.1 关键公式与显存调试速查

第一，单个 tensor 的存储量可以粗略写成：

~~~math
M(X)=n(X)\cdot b(X)
~~~

其中 `n(X)` 是元素个数，`b(X)` 是每个元素的字节数。这里假定 tensor 已经确定 dtype，且只估算数据载荷，不计对象元数据、对齐和 allocator 的额外开销。常见情况下，FP32 是 4 bytes，FP16 / BF16 是 2 bytes。

第二，训练显存可以粗略分解为：

~~~math
M_{\mathrm{train}}
\approx M_{\mathrm{param}}+M_{\mathrm{grad}}+M_{\mathrm{opt}}+M_{\mathrm{act}}+M_{\mathrm{tmp}}
~~~

其中 `M_param` 是参数，`M_grad` 是梯度，`M_opt` 是 optimizer state，`M_act` 是前向激活，`M_tmp` 是临时 workspace、kernel buffer 和缓存。

第三，AdamW 常见状态显存大致是：

~~~math
M_{\mathrm{AdamW}}\approx 2P b_{\mathrm{state}}
~~~

其中 `P` 是参数个数，`b_state` 是一阶矩和二阶矩的存储字节数。如果状态使用 FP32，则每个参数额外需要约 8 bytes 的 optimizer state。

第四，Transformer 激活显存可以粗略理解为随 batch、序列长度、hidden size 和层数线性增长：

~~~math
M_{\mathrm{act}}\propto B T d L b_{\mathrm{act}}
~~~

其中 `B` 是 batch size，`T` 是 sequence length，`d` 是 hidden size，`L` 是层数，`b_act` 是激活 dtype 字节数。实际 attention、中间 MLP、checkpointing 和 kernel 实现会改变常数项。

这里的线性式只适用于某一类保存的 hidden state，不能拿来估算所有 attention 内存。朴素全注意力还会产生形状近似为 `[B, H, T, T]` 的 score/probability 中间量，因此其元素数包含：

~~~math
N_{\mathrm{attn}}\propto B H T^2,
~~~

其中 `H` 是 attention head 数。序列长度从 `T` 增加到 `2T` 时，若实现显式保留这个矩阵，相关中间量可能增加约 4 倍。[FlashAttention](https://arxiv.org/abs/2205.14135) 是 IO-aware 的精确 attention 算法，通过分块减少 HBM 与片上 SRAM 之间的数据读写；它避免按朴素路径物化完整注意力矩阵，但不把稠密 self-attention 的计算复杂度从 $T^2$ 自动变成线性。估算显存时应区分“理论 score 矩阵”“kernel 实际 workspace”和“反向所需保存的统计量”。

第五，activation checkpointing 的核心取舍是：

~~~math
M_{\mathrm{act}}^{\mathrm{ckpt}} < M_{\mathrm{act}},\qquad
C_{\mathrm{backward}}^{\mathrm{ckpt}} > C_{\mathrm{backward}}
~~~

也就是用反向时额外重算一部分 forward，换取更低的前向激活保存量。

第六，loss scaling 的数值直觉是：

~~~math
\tilde{L}=sL,\qquad
\nabla_\theta \tilde{L}=s\nabla_\theta L,\qquad
g=\frac{1}{s}\nabla_\theta \tilde{L}
~~~

其中 `s` 是 scale factor。FP16 中先放大 loss 可以减少小梯度下溢风险；optimizer step 前要 unscale 回真实梯度，再做 gradient clipping。

这些公式是数量级估算，不是显存报告。参数可能以 FP32 master weight、BF16/FP16 compute weight 或量化格式分别存在；optimizer state 可能被分片、懒初始化或放在 CPU；allocator 还会保留已经申请过的缓存。因此必须把公式估算和运行时的 `allocated`、`reserved`、`peak` 读数放在一起看。

### 6.1.2 一个数量级例子

假设模型有 `P=1,000,000,000` 个参数，参数和梯度使用 2 bytes，AdamW 的一阶矩和二阶矩使用 FP32。仅这三项的理想下界约为：

~~~math
M_{\mathrm{param}}=P\times2\text{ bytes}\approx1.86\text{ GiB},
\quad
M_{\mathrm{grad}}\approx1.86\text{ GiB},
\quad
M_{\mathrm{opt}}=P\times2\times4\text{ bytes}\approx7.45\text{ GiB}.
~~~

合计已经接近 `11.17 GiB`，还没有包含激活、临时 buffer、CUDA context、碎片和模型可能保留的 FP32 master copy。这个例子说明，单纯把 batch size 调小并不能解决 optimizer state 在加载阶段就超出显存的问题；此时要考虑状态分片、CPU offload、不同 optimizer 或更大显存设备。

## 6.2 为什么需要混合精度

传统上很多训练用 fp32。fp32 精度高，但显存和带宽开销大。

混合精度训练的思路是：

1. 用较低精度存储和计算大部分张量。
2. 保留少数关键位置使用较高精度。
3. 在数值敏感环节保持稳定。

常见组合：

1. fp16。
2. bf16。
3. fp32 + amp。

它的目标不是“全部变低精度”，而是找到质量、性能和显存之间的平衡点。

优势：

1. 显存更省。
2. 带宽压力更小。
3. 通常训练更快。

代价：

1. 数值更脆弱。
2. 某些算子容易溢出或下溢。
3. 需要更多工程控制。

混合精度不是简单执行 `model.half()`。后者会把模型参数和许多运算强制改成 FP16，可能让归一化、softmax、损失和优化器状态同时落入不合适的精度；AMP 则根据算子策略选择计算 dtype，并允许敏感路径保持更高精度。最终是否有收益，还取决于硬件是否有对应的低精度矩阵乘法吞吐、输入搬运是否成为瓶颈，以及额外的 cast 是否抵消了收益。

## 6.3 FP16 和 BF16 的区别

fp16 和 bf16 都是 16 位浮点，但表示方式不同。

### 6.3.1 FP16

fp16 的优点是：

1. 计算和存储都省。
2. 在很多 GPU 上支持成熟。

缺点是：

1. 指数范围较小。
2. 更容易溢出、下溢。
3. 训练时通常要配合 GradScaler。

### 6.3.2 BF16

bf16 的指数范围接近 fp32，动态范围更大。

优点是：

1. 更不容易数值溢出。
2. 大模型训练通常更稳。
3. 在很多现代硬件上支持很好。

缺点是：

1. 尾数精度比 fp16 低。
2. 某些硬件或旧环境支持不如 fp16 普遍。

### 6.3.3 用表示范围理解差异

FP16 使用 5 位指数和 10 位小数位，BF16 使用 8 位指数和 7 位小数位。前者有更细的尾数精度，后者保留了接近 FP32 的指数范围。用通常的 IEEE 754 规格作数量级理解，FP16 的最大有限值约为 `6.55\times10^4`，最小正规格正数约为 `6.10\times10^{-5}`；BF16 的最大有限值接近 `3.39\times10^{38}`，动态范围接近 FP32，但相邻可表示数的间隔更粗。

因此“BF16 更稳”主要指溢出/下溢边界更宽，不表示 BF16 对所有运算都更精确。模型中如果某条路径需要细粒度小数差异，仍可能需要 FP32 累加；如果硬件不支持 BF16 的高效 kernel，理论上的数值优势也可能换来更低吞吐。PyTorch AMP 文档还提醒，部分 BF16 预训练模型不能在 FP16 的数值范围（最大有限值约 65,504）内稳定运行；遇到 Inf/NaN 时应先验证模型与 FP16 的兼容性，而不是只提高 loss scale。动态 `GradScaler` 的 scale 也不保证始终大于 1。[官方 AMP 边界说明](https://docs.pytorch.org/docs/2.15/amp.html)

工程上常见判断：

1. 如果硬件和框架支持良好，bf16 往往更省心。
2. 如果只能用 fp16，通常要配合 GradScaler。

选择精度时应记录至少四个观测量：训练 loss 是否非有限、梯度裁剪触发比例、有效 token/s 和验证指标。不能只因为 BF16 能运行就断定它比 FP16 更好，也不能只比较单步耗时而忽略 loss scale 频繁回退或最终质量下降。

## 6.4 autocast：自动混合精度

PyTorch 的 AMP 通过 `autocast` 自动把合适的算子放到低精度执行。

示例：

以下是嵌入训练循环的前向片段，`model`、`input_ids`、`criterion` 和 `labels` 由调用方提供；它不包含反向传播或参数更新。

```python
import torch

with torch.amp.autocast("cuda", dtype=torch.float16):
    logits = model(input_ids)
    loss = criterion(logits, labels)
```

代码状态：静态审阅，未运行（前向片段；依赖调用方提供模型、输入和损失函数）。

直觉：

1. 某些算子适合低精度，比如大部分矩阵乘法。
2. 某些算子更适合保留高精度，比如 softmax、归一化、loss 计算中的敏感部分。
3. `autocast` 负责自动选择。

工程意义：

1. 减少手动 dtype 管理。
2. 更容易获得性能收益。
3. 降低写错精度策略的概率。

但要记住：`autocast` 不是万能的。它只是帮助管理前向中的算子精度，仍然需要结合模型结构和具体异常去判断。使用 autocast 时，模型参数和输入保持常规 dtype，让算子策略选择计算 dtype；不要为了配合 autocast 再对整个模型或输入调用 `.half()` / `.bfloat16()`。具体哪些算子会被降精度由设备与 PyTorch 版本的 autocast 策略决定。[PyTorch AMP autocast 说明](https://docs.pytorch.org/docs/2.15/amp.html)

`autocast` 的作用范围也必须说清楚：它主要包住 forward 和 loss 计算，不负责清梯度、缩放 loss、裁剪梯度或更新参数。进入上下文前后的输入 dtype 不一定改变，某个算子的输出 dtype 由 AMP 的算子策略决定。需要手工恢复高精度的局部计算可以使用嵌套上下文：

```python
with torch.amp.autocast("cuda", dtype=torch.float16):
    hidden = model_backbone(input_ids)
    with torch.amp.autocast("cuda", enabled=False):
        stable_value = sensitive_loss(hidden.float(), labels)
```

代码状态：静态审阅，未运行（上下文片段；`model_backbone`、`sensitive_loss` 和输入由调用方提供）。

示例中的 `sensitive_loss` 只是说明边界，实际是否需要禁用 autocast 要通过异常复现和指标验证决定。不要在每个算子周围随意切换 dtype，否则 cast 开销和代码复杂度可能超过收益。

## 6.5 GradScaler：解决 fp16 的数值问题

fp16 训练容易遇到梯度太小导致下溢。`GradScaler` 的做法是先放大 loss，再反向传播，再把梯度缩回去。

典型结构：

这是 CUDA FP16 训练 step 的关键调用片段，假设模型、optimizer、scaler 和 batch 已准备好；完整的 dtype 开关见下一节。

```python
import torch

scaler = torch.amp.GradScaler("cuda")

for batch in train_loader:
    optimizer.zero_grad(set_to_none=True)

    with torch.amp.autocast("cuda", dtype=torch.float16):
        outputs = model(**batch)
        loss = outputs["loss"]

    scaler.scale(loss).backward()
    scaler.unscale_(optimizer)
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)
    scaler.update()
```

代码状态：静态审阅，未运行（训练循环片段；模型、损失函数和数据由调用方提供）。

关键步骤：

1. `scale(loss)` 放大 loss。
2. `backward()` 在放大后的尺度上计算梯度。
3. `unscale_(optimizer)` 把梯度缩回来。
4. 必要时再做梯度裁剪。
5. `step` 和 `update` 完成参数更新和缩放因子调整。

为什么要先 `unscale_` 再裁剪？因为裁剪的是实际梯度，不是被放大的临时梯度。

bf16 通常不需要 GradScaler；CPU BF16 autocast 通常也只用 autocast。FP16 下，GradScaler 会在检测到非有限梯度时跳过 optimizer 更新，并调整下一轮 scale。scale 不保证始终大于 1：若模型本身不适配 FP16 的动态范围，scale 下降也不一定能修复前向溢出，需检查 dtype 选择、loss 与梯度来源。[PyTorch AMP 文档](https://docs.pytorch.org/docs/2.15/amp.html)

### 6.5.1 为什么必须在 unscale 后裁剪

假设真实梯度范数为 `10`，loss scale 为 `1024`。缩放后的梯度范数是 `10,240`。若直接执行 `clip_grad_norm_(..., max_norm=1.0)`，缩放梯度会被压到约 `1.0`，随后 unscale 后只剩约 `0.00098`；而正确顺序应先 unscale，再把范数 `10` 裁到 `1.0`。错序因此把本应为 `1.0` 的裁剪结果缩小了 1,024 倍。

此外，一个 optimizer 在同一 iteration 内通常只能调用一次 `unscale_`；如果有多个 optimizer，要分别处理。`scaler.step(optimizer)` 会在检测到非有限梯度时跳过这次参数更新，`scaler.update()` 再根据结果调整 scale。训练日志应记录“是否真正执行了 optimizer step”，不能把每次循环都算作一次参数更新。

## 6.6 mixed precision 训练的推荐模板

先用 `amp_dtype` 明确 autocast 的 dtype，再从它推导 FP16 分支，避免 autocast 与 scaler 使用不同精度。下面是 CUDA 训练循环片段，假设已导入 `torch`，且 `model`、`optimizer`、`train_loader`、`device`、`move_to_device` 和 `use_amp` 已由训练脚本定义；默认选 BF16 时不启用 GradScaler。

```python
amp_dtype = torch.bfloat16  # 若改为 torch.float16，则启用 GradScaler
use_fp16 = use_amp and amp_dtype == torch.float16
scaler = torch.amp.GradScaler("cuda", enabled=use_fp16)

for batch in train_loader:
    batch = move_to_device(batch, device)
    optimizer.zero_grad(set_to_none=True)

    with torch.amp.autocast("cuda", dtype=amp_dtype, enabled=use_amp):
        outputs = model(**batch)
        loss = outputs["loss"]

    if use_fp16:
        scaler.scale(loss).backward()
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(optimizer)
        scaler.update()
    else:
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0, error_if_nonfinite=True)
        optimizer.step()
```

代码状态：静态审阅，未运行（训练循环片段；需由调用方提供模型、optimizer、device 和数据）。

这里要注意：

1. `autocast` 控制前向精度。
2. `GradScaler` 主要服务 fp16。
3. `bf16` 训练通常不需要缩放；本例只在 dtype 为 FP16 且 AMP 启用时走 scaler 分支。

如果把本章的梯度累积也加入进来，缩放顺序是：先按窗口定义把 loss 除以 `accum_steps` 或有效 token 总数，再交给 `scaler.scale()`。当各 micro-batch 的有效目标数不同，应像[第五章《训练循环工程》](05-训练循环工程.md)那样按窗口分母归一化，不能简单平均局部 mean。在真实梯度层面，流程应是：

~~~math
L_{\mathrm{micro}}\rightarrow
\frac{L_{\mathrm{micro}}}{D_W}\rightarrow
s\frac{L_{\mathrm{micro}}}{D_W}\rightarrow
\text{backward}\rightarrow
\text{unscale}\rightarrow
\text{clip}\rightarrow
\text{step}.
~~~

其中 `D_W` 是当前窗口的正确分母，`s` 是 GradScaler 的 scale。若先累积未归一化的梯度再临时除以 `accum_steps`，代码会更容易在最后不完整窗口或动态 token 数上出错。使用 AMP 时还要在 checkpoint 中保存 `scaler.state_dict()`；否则恢复训练时 loss scale 可能突然回到初始值或与此前轨迹不同。

下面是带梯度累积的**训练循环片段**：`window_size` 表示当前窗口的 micro-batch 数，`is_window_end` 应由窗口边界逻辑给出，并须正确处理 epoch 尾窗。累积期间梯度保持缩放状态且 scale 不变；所有 micro-batch 完成后才对该 optimizer 调用一次 `unscale_`，再裁剪、step 和 update。若按有效 token 求均值，窗口的 loss 分母应由第五章的规则确定，而不是直接使用 `window_size`。

```python
scaler = torch.amp.GradScaler("cuda", enabled=use_fp16)
optimizer.zero_grad(set_to_none=True)

for micro_step, batch in enumerate(train_loader):
    with torch.amp.autocast("cuda", dtype=amp_dtype, enabled=use_amp):
        outputs = model(**batch)
        raw_loss = outputs["loss"]
        loss = raw_loss / window_size

    if use_fp16:
        scaler.scale(loss).backward()
    else:
        loss.backward()

    if is_window_end:
        if use_fp16:
            scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        if use_fp16:
            scaler.step(optimizer)
            scaler.update()
        else:
            optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```

代码状态：静态审阅，未运行（训练循环片段；窗口边界、batch 和模型由调用方提供）。

代码还应在非有限 `raw_loss`、全忽略 label、梯度裁剪返回非有限值时停止或保存坏 batch；AMP 不是异常数据的过滤器。

FP16 路径中若 GradScaler 检测到 Inf/NaN，它可能跳过底层 `optimizer.step()`；因此 `global_step` 和按 update 调度的 scheduler 必须以真实参数更新为准，不能每个 micro-step 或每次尝试都递增。第五章已说明 update 计数与 scheduler 的边界。

若使用默认动态 scale 且没有手动覆写 scale，可在窗口末记录 `scale_before`，执行 `scaler.step()` 和 `scaler.update()` 后再读 `scale_after`：scale 下降表示本次 optimizer step 因非有限梯度被跳过，未下降时才计作一次真实更新。多个 optimizer 的 step 可独立跳过，需分别记录；自定义 scale 更新逻辑应采用显式 step 观测，而不要套用这个判断。[GradScaler 的 skip 与 scale 更新语义](https://docs.pytorch.org/docs/2.15/amp.html)

## 6.7 activation checkpointing

activation checkpointing 的核心思想是：前向时少存一部分激活，反向时再重新计算这部分前向，从而用计算换显存。

直觉：

1. 普通训练保留很多中间激活，方便 backward。
2. checkpointing 只保留关键节点。
3. backward 时重新跑部分 forward 来恢复中间值。

PyTorch 里可以这样用：

```python
from torch.utils.checkpoint import checkpoint


def forward_block(x, block):
    return checkpoint(block, x, use_reentrant=False)
```

代码状态：静态审阅，未运行（包装片段；`x` 和 `block` 由模型前向提供）。

或者在模型里包住某些子模块。

优点：

1. 明显省显存。
2. 可以支持更长序列或更大 batch。

缺点：

1. backward 更慢，因为要重算前向。
2. 代码结构更复杂。

### 6.7.1 重算与随机性的边界

checkpointing 的 backward 会再次执行被包裹的 forward。若 block 内有 Dropout，第二次执行必须使用与第一次一致的随机状态，才能得到与普通 autograd 接近的梯度。PyTorch 2.15 默认保存 CPU 和一种从张量参数推断出的非 CPU device type 的 RNG 状态；若函数涉及多个设备类型，其余类型不会全部保存，且接口无法追踪函数内部新搬到的设备。`preserve_rng_state=False` 会省去这部分状态保存/恢复，随机路径可能改变；在 `torch.compile` 下该参数不生效，RNG 状态始终保留。[checkpoint RNG 边界](https://docs.pytorch.org/docs/2.15/checkpoint.html)

函数在重算时应沿用与原前向相同的参数、状态和随机语义，避免依赖会变化的外部可变状态。[PyTorch 2.15 文档推荐显式采用 `use_reentrant=False`](https://docs.pytorch.org/docs/2.15/checkpoint.html)，且该路径不要求输入/输出必须带 `requires_grad`；旧的 reentrant 实现对此有更严格的要求。具体版本的参数和限制仍应以目标环境文档为准。

### 6.7.2 checkpoint 粒度

把整个模型包成一个 checkpoint，可能节省更多激活，但会重复计算大量不必要的层；按每个 Transformer block 包装，通常在显存和重算时间之间更容易调节。实际应测量：峰值显存下降多少、单 step 时间增加多少、有效 token/s 变化多少，以及固定 seed 下 logits/梯度误差是否在可接受范围。checkpointing 是一种资源交换，不是无代价的开关。

适合：

1. Transformer block 很深的模型。
2. 长上下文训练。
3. 显存非常紧张的实验。

## 6.8 梯度累积和显存

梯度累积不仅是优化 batch size 的办法，也是显存优化手段。

如果一次只能放很小的 batch，就把多个 micro-batch 的梯度累积起来再更新。

这个片段只演示等大小 micro-batch 的梯度累积，不启用 AMP；叠加 FP16 时须使用 §6.6 的 GradScaler 顺序，BF16 通常可直接反向。实际训练还需处理尾窗及 loss 分母；完整处理见[第五章《训练循环工程》](05-训练循环工程.md)。

```python
accum_steps = 8
optimizer.zero_grad(set_to_none=True)

for step, batch in enumerate(train_loader):
    outputs = model(**batch)
    loss = outputs["loss"] / accum_steps

    loss.backward()

    if (step + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```

代码状态：静态审阅，未运行（循环片段；模型、数据、device 与尾窗逻辑由调用方提供）。

优点：

1. 降低单次 forward/backward 的激活峰值。
2. 模拟更大 batch。

缺点：

1. 更新频率变低。
2. 训练吞吐不一定线性提升。

梯度累积只降低单次 forward/backward 的激活峰值，不会自动减少参数、梯度或 optimizer state 的常驻显存；并且保留梯度的时间更长。若 micro-batch 已经足够小而 OOM 发生在 optimizer 初始化或 `optimizer.step()`，继续增加 `accum_steps` 没有帮助。若 OOM 发生在 forward，才应优先考虑 batch、序列长度、AMP 或 checkpointing。

另外，梯度累积的有效样本 batch 应按每个 rank、每个 micro-batch 的样本数计算：

~~~math
B_{\mathrm{eff}}=B_{\mathrm{micro}}\times K\times R,
~~~

其中 `B_micro` 是每个 rank 的单个 micro-batch 样本数，`K` 是累积 micro-batch 数，`R` 是 data-parallel rank 数；该简式假设各 rank 每次拿到相同样本数且参与同一轮同步。举例：每个 rank 每个 micro-batch 有 2 个样本，累积 4 次、共 3 个 rank，则 nominal effective batch 为 `2×4×3=24` 个样本。若最后窗口不足 4 个 micro-batch，实际窗口更小；`drop_last`、不等长输入或动态 batch 也会改变真实样本数。使用 token 预算时，应按有效目标 token 数和相同 loss 分母规则核算；样本数相同不代表监督 token 数相同，多 rank 的局部 token 均值也不能简单等权平均，见[第五章](05-训练循环工程.md)。

## 6.9 影响显存的关键因素

显存不是只由 batch size 决定，还包括：

1. 序列长度。
2. 模型层数。
3. hidden size。
4. 注意力头数。
5. 精度。
6. optimizer 类型。
7. 是否保留中间激活。
8. 是否开启 checkpointing。
9. 是否存了额外的日志或缓存。

尤其对 Transformer 来说，序列长度增加往往会显著推高激活和 attention 相关开销。

可以把显存调参拆成两条曲线。参数/优化器曲线主要由参数量、dtype 和 optimizer 决定；激活曲线主要由 `B`、`T`、层数和实现决定。减小 `B` 会降低两者中的激活部分，但不会改变参数和 optimizer 常驻项；减小 `T` 会降低 hidden state 和 attention 中间量，尤其可能显著降低 `T^2` 项；改用 BF16/FP16 主要降低计算张量字节数，却不会自动把 FP32 optimizer state 变成 16 位。

一个实用判断：如果显存爆了，先问自己是参数太大、batch 太大、序列太长、还是优化器状态太重。

用一个构造预算看 batch 与长度的不同影响。假设 `B=2`、`T=2048`、hidden size `d=4096`、层数 `L=32`、attention heads `H=32`，并以 BF16 的 `b=2 bytes` 估算；只计算每层一个 hidden state 和朴素 attention 的一个 score 矩阵：

| 估算对象 | 代入 | 结果 |
| --- | --- | ---: |
| 各层一个 `[B,T,d]` hidden state | `2×2048×4096×32×2` bytes | `1 GiB` |
| 一层一个 `[B,H,T,T]` score 矩阵 | `2×32×2048×2048×2` bytes | `0.5 GiB` |
| 32 层都保存一个完整 score 矩阵 | `0.5×32 GiB` | `16 GiB` |

若把 `T` 减半到 1,024，hidden state 估算降到 `0.5 GiB`，score 矩阵则降到每层 `0.125 GiB`、32 层合计 `4 GiB`；这是因为前者对 `T` 线性，后者对 `T` 平方。若改为把 `B` 减半，二者都只减半。这组数只说明维度敏感性，不是一个训练 step 的峰值预测：真实模型会保存多种激活和梯度、使用临时 workspace，并可能通过 fused/分块 attention 不物化完整矩阵。FlashAttention 的 IO 与存储行为见前面的[论文入口](https://arxiv.org/abs/2205.14135)；实际显存仍须在目标实现上测量。

## 6.10 optimizer 状态为什么也占很多显存

以 Adam 为例，除了参数本身，还要保存一阶矩和二阶矩。

直觉上，每个参数可能对应：

1. 参数值。
2. 梯度。
3. 一阶矩。
4. 二阶矩。

所以 Adam 类优化器的总显存压力明显高于 SGD。

这也是为什么在超大模型训练里，经常会考虑：

1. 参数分片。
2. 优化器状态分片。
3. 更低精度状态。
4. 更省显存的训练策略。

本章重点不是展开分布式分片，而是先建立“optimizer 状态本身也很贵”的意识。

要避免把“理论上每参数 8 bytes”当成所有 AdamW 实现的精确答案。某些训练保留 FP32 master parameters，某些实现把状态放在 CPU 或按 rank 分片，某些状态在第一次 `step()` 前还没有创建。正确做法是先用公式估算上界，再在 optimizer 初始化、第一次 step 后分别读取内存，观察状态何时实际出现。若 OOM 恰好发生在第一次 optimizer step，激活可能已经释放，新增的 optimizer state 反而是主要原因。

## 6.11 训练中常见的显存优化顺序

当你遇到 OOM，可以按下面顺序试：

1. 减小 batch size。
2. 减小 sequence length。
3. 开启 mixed precision。
4. 开启 gradient accumulation。
5. 开启 activation checkpointing。
6. 检查是否保留了多余 tensor。
7. 检查 validation 是否忘了关梯度。
8. 检查 DataLoader 预取和 batch 缓存。

这个顺序的逻辑是：

1. 先改最直接影响显存的变量。
2. 再上混合精度和 checkpointing。
3. 最后排查代码层面的泄漏。

这个顺序不是固定处方。若模型参数本身已无法加载，应先处理参数/状态分片或量化；若只有长序列 forward OOM，优先减少 `T` 或使用更节省中间矩阵的 attention 实现；若显存随 step 单调增长，优先检查计算图引用；若 `reserved` 很高但 `allocated` 稳定，先判断是 allocator 缓存还是实际泄漏，再决定是否调整 allocator 配置。每次只改变一个变量，并记录峰值显存、step 时间和验证指标。

## 6.12 显存泄漏的常见来源

不是所有显存增长都是“模型太大”。很多是代码把图保留下来了。

常见来源：

1. 把带计算图的 loss 存进 list。
2. 把中间 activation 长期缓存。
3. 验证时没用 `no_grad` 或 `inference_mode`。
4. hook 里保存了未 detach 的 tensor。
5. 每步都把大 batch 的输出堆到内存里。
6. 重复创建没有释放的大 tensor。

如果怀疑泄漏，可以每隔几步打印：

```python
print(torch.cuda.memory_allocated() / 1024**2)
print(torch.cuda.memory_reserved() / 1024**2)
```

代码状态：静态审阅，未运行（CUDA 诊断片段；`torch` 已导入，需在 CUDA 设备上调用）。

还可以更系统地用 PyTorch 的显存统计接口排查。

三个统计量含义不同：`memory_allocated()` 是当前仍被 tensor 使用的分配量，`memory_reserved()` 是 PyTorch caching allocator 管理的总量，`max_memory_allocated()` 默认是程序启动以来的 tensor 分配峰值，也可由 `reset_peak_memory_stats()` 重设起点。`reserved - allocated` 较大不一定是泄漏，可能只是缓存池；更有价值的实验是在固定 workload 前重设 peak，再比较阶段峰值和 tensor 引用是否增长。`empty_cache()` 只把 allocator 未使用的缓存块释放给其他 GPU 应用，不能释放仍由 tensor 占用的内存，也不会增加 PyTorch 自身可用的显存；不要在训练循环里把它当作 OOM 修复。[PyTorch CUDA 显存统计说明](https://docs.pytorch.org/docs/2.15/notes/cuda.html#memory-management)

```python
torch.cuda.synchronize()
torch.cuda.reset_peak_memory_stats()

# 执行一个固定的 forward/backward 或 validation 区间
torch.cuda.synchronize()
peak_mib = torch.cuda.max_memory_allocated() / 1024**2
reserved_mib = torch.cuda.memory_reserved() / 1024**2
allocated_mib = torch.cuda.memory_allocated() / 1024**2
print({
    "peak_allocated_mib": round(peak_mib, 2),
    "allocated_mib": round(allocated_mib, 2),
    "reserved_mib": round(reserved_mib, 2),
})
```

代码状态：静态审阅，未运行（CUDA 显存统计片段；在 CUDA 环境中、每个待比较区间开始前重置 peak）。

PyTorch 给 `memory_allocated` 和 `max_memory_allocated` 的口径是 tensor 占用，`memory_reserved` 和 `max_memory_reserved` 的口径是 caching allocator 管理量；因此 `nvidia-smi`、allocator 读数和 tensor 活跃量可能不同。读数差异是诊断线索，不足以单独证明泄漏或碎片；应结合固定区间的峰值、进程级显存和 allocator snapshot 判断。[官方 CUDA memory 说明](https://docs.pytorch.org/docs/2.15/notes/cuda.html#memory-management)

## 6.13 OOM 排查方法

当出现 OOM 时，不要只盯着最后一行报错，要分层排查。

先用失败阶段缩小假设集合，再决定要改哪个变量。下表中的阶段只是诊断入口，不能单凭阶段名称直接下结论；例如第一次 `optimizer.step()` 既可能创建 Adam 状态，也可能仍被延迟释放的激活挤占。

| 失败阶段或现象 | 优先假设 | 首要观测与下一步 |
| --- | --- | --- |
| 模型加载时 OOM | 参数、master copy 或常驻 optimizer 状态预算过高 | 核对参数 dtype/数量和 load placement；降低 batch 通常无效，需评估状态分片、offload 或模型大小。 |
| Forward 期间 OOM | 单个 micro-batch 的激活、序列长度或 attention 中间量过大 | 固定模型后分别缩小 `B`、`T`；再比较 AMP、attention 实现和 checkpointing。 |
| Backward 期间 OOM | 反向临时 buffer 或保存激活峰值过高 | 对齐 forward/backward 峰值；检查重计算粒度、张量生命周期和实现是否物化完整 attention 中间量。 |
| 第一次 optimizer step 才 OOM | 延迟创建的 Adam 状态、master 参数或 step 临时张量 | 对比 step 前后的 allocated/reserved；确认优化器状态何时初始化，再考虑降低状态精度、offload 或分片。 |
| Validation OOM | 梯度图未关闭、输出累积或验证 batch 太大 | 确认 `eval()` 与 `inference_mode()`、及时转 CPU/标量、缩小验证 batch。 |
| 每个 step 结束后的 allocated 持续增长 | 容器、hook 或闭包仍引用带图 tensor | 记录稳定边界的 allocated 和对象持有关系；标量日志用 `.item()`，输出需要留存时先 `detach()` 并按需移到 CPU。 |

例如，`B` 减半能使 forward 的激活预算大致按比例下降，却无法解决加载时参数和 optimizer 状态已超过设备容量的问题；checkpointing 可能降低 backward 所需保存的激活，却不会缩小常驻参数和状态。先按阶段找因，再一次只改一个变量，才能判断修复是否针对根因。

### 6.13.1 先看是训练还是验证

1. 如果训练 OOM，关注 batch、seq len、激活、梯度和 optimizer state。
2. 如果验证 OOM，重点看是否忘记关梯度、是否缓存了输出、是否 batch 过大。

### 6.13.2 先缩小 batch 和 sequence length

这是最直接的验证手段。若缩小后能跑，说明问题和激活/序列长度强相关。

### 6.13.3 检查是否在累积图

例如：

```python
losses.append(loss)
```

代码状态：静态审阅，未运行（错误示例片段；`loss` 由训练循环产生）。

如果长期保存带图对象，显存会持续增长。

应该改成：

```python
losses.append(loss.item())
```

代码状态：静态审阅，未运行（标量日志片段；`losses` 和 `loss` 由调用方提供）。

### 6.13.4 检查验证流程

验证时应：

1. `model.eval()`。
2. `torch.inference_mode()`。
3. 不做 backward。
4. 不把大输出长期保存在 GPU 上。

### 6.13.5 用峰值位置定位

可以在固定 batch 上给四个边界打点：模型加载后、forward 后、backward 后、optimizer step 后。若要比较每个阶段自身的 peak，需要在阶段开始前先同步设备并重设峰值统计；阶段结束后再次同步，再读取 peak。若不重设，`max_memory_allocated()` 仍是自上次 reset 以来的累计高水位，不能解释成当前阶段的局部峰值：

```python
def reset_cuda_peak(device=None):
    if not torch.cuda.is_available():
        return False
    torch.cuda.synchronize(device)
    torch.cuda.reset_peak_memory_stats(device)
    return True


def cuda_memory_snapshot(tag, device=None):
    if not torch.cuda.is_available():
        return {"tag": tag, "cuda": False}
    torch.cuda.synchronize(device)
    return {
        "tag": tag,
        "allocated_mib": round(torch.cuda.memory_allocated(device) / 1024**2, 2),
        "reserved_mib": round(torch.cuda.memory_reserved(device) / 1024**2, 2),
        "peak_since_reset_mib": round(torch.cuda.max_memory_allocated(device) / 1024**2, 2),
    }
```

代码状态：静态审阅，未运行（CUDA 专用片段；假设已导入 `torch`，每个阶段先调 `reset_cuda_peak()`，结束后再调用 snapshot）。

如果 forward 后峰值最高，优先看激活、`T` 和 attention；如果 backward 后才最高，查看反向临时 buffer 和 checkpoint 粒度；如果 optimizer step 后突然跳高，优先检查 Adam state 或 master copy；如果每一步结束后的 `allocated` 都上升，检查 Python 容器、hook 和日志是否仍持有计算图。这个时间线比笼统地说“显存不够”更接近可修复的根因。

## 6.14 AMP 训练 step 与 activation checkpointing 的组合

下面只展示训练 step；它假设 `model.forward()` 已在需要的 block 上使用 `checkpoint(..., use_reentrant=False)`，并由外层训练脚本准备模型、batch、optimizer 和 scaler，本函数负责清零梯度。这个例子不再导入未使用的 checkpoint 函数。

```python
import torch

device_type = "cuda"
amp_dtype = torch.bfloat16  # 可切换为 torch.float16
use_amp = True
use_fp16 = use_amp and amp_dtype == torch.float16
scaler = torch.amp.GradScaler(device_type, enabled=use_fp16)


def train_step(model, batch, optimizer):
    optimizer.zero_grad(set_to_none=True)

    with torch.amp.autocast(device_type, dtype=amp_dtype, enabled=use_amp):
        outputs = model(**batch)
        loss = outputs["loss"]

    if use_fp16:
        scaler.scale(loss).backward()
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(optimizer)
        scaler.update()
    else:
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0, error_if_nonfinite=True)
        optimizer.step()

    return loss.item()
```

若 AMP 使用 FP16，`scaler.step()` 可能跳过含 Inf/NaN 梯度的更新；只有真实更新后才应推进 `global_step` 和 update-based scheduler，恢复状态时也要保存 scaler。BF16 autocast 通常不使用启用的 GradScaler。AMP 管前向数值路径，checkpointing 管激活保留与重算，梯度累积管单个 micro-batch 的激活峰值；三者可以组合，但解决的账本项不同。

## 6.15 最小可运行 BF16 autocast 与显存审计 demo

这个 CPU demo 展示三件事：一个合成的显存组成估算、BF16 autocast 的前向/反向 step，以及 activation checkpointing 在 backward 中的重算。BF16 路径不使用 GradScaler；FP16 的 scaler 调用顺序见 §6.5–6.6。显存估算仅是公式演示，不读取 GPU，也不构成实测。

```python
import torch
import torch.nn.functional as F
from torch import nn
from torch.utils.checkpoint import checkpoint

DTYPE_BYTES = {
    "fp32": 4,
    "fp16": 2,
    "bf16": 2,
}


def mib(num_bytes):
    return round(num_bytes / 1024**2, 3)


def estimate_memory(param_count, activation_elements, param_dtype="bf16", activation_dtype="bf16"):
    param_bytes = param_count * DTYPE_BYTES[param_dtype]
    grad_bytes = param_count * DTYPE_BYTES[param_dtype]
    adamw_state_bytes = 2 * param_count * DTYPE_BYTES["fp32"]
    activation_bytes = activation_elements * DTYPE_BYTES[activation_dtype]
    return {
        "params_mib": mib(param_bytes),
        "grads_mib": mib(grad_bytes),
        "adamw_states_mib": mib(adamw_state_bytes),
        "activations_mib": mib(activation_bytes),
        "total_mib": mib(param_bytes + grad_bytes + adamw_state_bytes + activation_bytes),
    }


class TinyMLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 4))

    def forward(self, x):
        return self.net(x)


torch.manual_seed(0)
model = TinyMLP()
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)
x = torch.randn(6, 8)
y = torch.tensor([0, 1, 2, 3, 1, 0])
optimizer.zero_grad(set_to_none=True)
with torch.amp.autocast("cpu", dtype=torch.bfloat16):
    logits = model(x)
    loss = F.cross_entropy(logits, y)

autocast_dtype = str(logits.dtype).replace("torch.", "")
loss.backward()
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
optimizer.step()


class CountBlock(nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = nn.Linear(8, 8)
        self.calls = 0

    def forward(self, z):
        self.calls += 1  # instrumentation only; not part of the model computation
        return torch.relu(self.linear(z))


plain_block = CountBlock()
z = torch.randn(4, 8, requires_grad=True)
plain_block(z).sum().backward()
plain_calls = plain_block.calls

ckpt_block = CountBlock()
ckpt_block.load_state_dict(plain_block.state_dict())
z2 = z.detach().clone().requires_grad_(True)
checkpoint(ckpt_block, z2, use_reentrant=False).sum().backward()
ckpt_calls = ckpt_block.calls

estimate = estimate_memory(param_count=1_000_000, activation_elements=2_000_000)
print("memory_estimate=", estimate)
print("autocast_dtype=", autocast_dtype)
print("grad_norm_before_clip=", round(grad_norm.item(), 4))
print("checkpoint_calls=", {"plain": plain_calls, "checkpoint": ckpt_calls})
print("checkpoint_recomputed=", ckpt_calls > plain_calls)
```

这段输出要检查几件事：AdamW 的两个 FP32 状态在估算中比 BF16 参数和梯度更大；CPU autocast 让适合的线性算子输出 BF16；checkpoint 版本在 backward 中再次调用 block。`CountBlock.calls` 只是观察重算次数的教学计数器，不属于实际模型算子，也不能据此推导真实速度或显存节省。这个 CPU demo 不验证 CUDA 性能或设备显存。

## 6.16 工程中怎么选 fp16 和 bf16

选 dtype 时先问硬件和算子路径是否支持，再看数值范围与模型兼容性，最后用固定输入比较性能和质量。BF16 指数范围大，较少因范围窄而溢出；FP16 尾数更细，但范围窄，训练时通常要配 GradScaler。若 BF16 kernel 在目标设备不可用或性能不佳，BF16 的范围优势不会自动变成吞吐收益。反过来，不能只凭 FP16 的单步速度判断它更适合训练：scale 回退、非有限梯度和验证退化都可能抵消速度。

一个可复核的选择流程是固定模型 revision、batch、序列长度、seed 和数据顺序，分别运行 FP32 基线、支持时的 BF16 autocast，以及 FP16 autocast + GradScaler。先看前向 loss、反向梯度和参数更新是否有限，再比较同一批次的输出差异、一个短训练窗口的有效 token/s、peak allocated 和验证指标。只在相同 workload 下比较；kernel warm-up 或编译冷启动应与稳定后的 step 时间分开记录。若 FP16 loss scale 反复下降或出现 NaN/Inf，应验证模型是否超出 FP16 数值范围、检查 mask/loss 与学习率，并可尝试 BF16 或对敏感路径局部 FP32；不能仅靠持续缩小 scale 宣称兼容。

结论仍受设备型号、PyTorch/cuDNN 版本、算子覆盖和模型预训练 dtype 影响。需要迁移到新硬件或升级框架时，应重复这组固定输入的数值与性能比较，而不是把一次本地结果推广到所有 GPU。

## 6.17 常见误区

1. 以为 fp16 一定比 bf16 更好。实际上 bf16 往往更稳。
2. 以为 AMP 等于自动省一切显存。它主要解决精度和部分带宽问题，不是万能。
3. 以为 GradScaler 对所有混合精度都必须。bf16 通常不一定需要。
4. 以为 checkpointing 没有代价。它会增加 backward 计算量。
5. 以为 OOM 都是 batch 太大。也可能是 optimizer state、保存图或验证没关梯度。
6. 以为 loss 降低说明显存问题消失。数值稳定和显存问题是两个不同维度。

## 6.20 本章总结

混合精度与显存优化的核心不是背几个 API，而是建立资源感知的训练思维。

要记住的主线：

1. 显存主要花在参数、梯度、优化器状态、激活和临时 buffer。
2. fp16 和 bf16 都是混合精度方案，但 bf16 通常更稳。
3. `autocast` 管前向精度，`GradScaler` 主要解决 FP16 梯度下溢，并可能跳过非有限更新。
4. activation checkpointing 用计算换显存。
5. 梯度累积可以模拟更大 batch 并缓解单步显存压力，但窗口分母与真实 update 数要和第五章一致。
6. OOM 排查要区分加载、forward、backward、optimizer、验证和随 step 增长等失败阶段，并按 measurement window 重置峰值。
7. 一个好的训练脚本要同时考虑数值稳定、吞吐和显存峰值。
