# 第五章：训练循环工程

训练循环是把模型、数据、损失函数和优化器连成一个可持续实验系统的地方。前面几章分别讲了 tensor、autograd、`nn.Module` 和 DataLoader，但真实训练不是把它们简单拼起来就结束。一个可靠的训练循环还要处理 device 搬运、loss 计算、反向传播、梯度裁剪、梯度累积、学习率调度、日志、验证、checkpoint、恢复训练、异常检测和可复现性。

很多新手训练脚本能跑，但不稳定：loss 记录不准、验证时忘记 `no_grad`、scheduler step 时机错、梯度累积没有缩放 loss、checkpoint 只保存模型没有保存 optimizer、恢复训练后学习率不对、训练中断无法续跑、NaN 出现后不知道从哪里查。本章目标是建立一套从最小训练 step 到工程化训练循环的完整框架。

## 0. 本讲范围与资料

本章参考已核对 PyTorch 官方 `Optimizer.zero_grad`、`AdamW`、`LRScheduler` / `StepLR`、`clip_grad_norm_`、`no_grad`、`inference_mode`、`Module.train()` / `eval()`、模型保存加载教程和 checkpoint 相关文档口径。

本章聚焦大模型训练最常见的训练循环工程问题：forward、loss、backward、optimizer step、scheduler step、`zero_grad(set_to_none=True)`、梯度累积、梯度裁剪、语言模型 shift loss、batch 到 device、日志、验证循环、完整 checkpoint、恢复训练、随机状态和非有限 loss 检查。

本章不展开 AMP / GradScaler、FSDP / DeepSpeed / ZeRO、DDP 梯度同步、activation checkpointing、编译优化、生产级实验追踪平台或分布式 checkpoint shard。这些内容会分别放到混合精度、分布式训练、AI Infra 和训练平台章节中展开。

## 5.1 训练循环解决什么问题

一个训练循环的本质是反复执行：

1. 从 DataLoader 取一个 batch。
2. 把 batch 移到正确 device。
3. 执行 forward。
4. 计算 loss。
5. 执行 backward。
6. 更新参数。
7. 清理梯度。
8. 记录指标。
9. 定期验证和保存 checkpoint。

最小形式看起来很简单：

```python
for batch in train_loader:
    optimizer.zero_grad()
    outputs = model(batch["input_ids"])
    loss = criterion(outputs, batch["labels"])
    loss.backward()
    optimizer.step()
```

但真实工程会多出很多约束：

1. batch 里可能有多个字段。
2. 不同 tensor 要移动到 GPU。
3. loss 可能来自模型内部，也可能来自外部 criterion。
4. 需要梯度裁剪防止 loss spike。
5. 大 batch 可能要用梯度累积模拟。
6. 学习率 scheduler 要和 optimizer step 对齐。
7. 验证必须关闭梯度并切换 eval 模式。
8. checkpoint 要能恢复完整训练状态。

训练循环可以看成一个状态转移系统。模型参数只是其中一部分状态，优化器的动量、学习率调度器的位置、随机数生成器、数据采样位置和当前步数同样会影响下一次更新。只保存模型参数，能够得到一个“从当前权重开始的新训练”，却不一定能够得到“原训练过程在中断处继续运行”。后面每一节都会围绕这个区别展开。

### 5.1.1 关键公式与训练循环调试速查

第一，普通单 step 的参数更新可以抽象为：

~~~math
g_t=\nabla_{\theta_t} L_t(\theta_t),\qquad
\theta_{t+1}=U(\theta_t,g_t,\eta_t,s_t)
~~~

其中 `theta_t` 是第 `t` 次 optimizer step 前的参数，`g_t` 是当前 step 使用的梯度，`eta_t` 是学习率，`s_t` 是 optimizer 内部状态，例如 AdamW 的一阶矩和二阶矩。训练循环的目标是保证 `g_t` 来自正确 batch、正确 loss、正确 scale，并且 `s_t` 和 `eta_t` 能随 checkpoint 恢复。

第二，梯度累积到底在平均什么，必须先说清楚。设第 `k` 个 micro-batch 的平均 loss 为 `\bar L_k`，它包含 `n_k` 个有效监督项。若训练目标是让每个 micro-batch 权重相同，那么一个窗口 `W` 的梯度是：

~~~math
g_W^{\mathrm{batch}}=\frac{1}{m}\sum_{k=1}^{m}\nabla_{\theta}\bar L_k(\theta),
\qquad
\bar L_k=\frac{1}{n_k}\sum_{i=1}^{n_k}\ell_{k,i}
~~~

这里 `m` 是当前窗口实际包含的 micro-batch 数，不一定等于配置中的 `accum_steps`；最后一个不完整窗口可能只有 `m<K` 个 batch。代码里应使用 `\bar L_k/m` 再 `backward()`。如果最后一个窗口仍除以固定的 `K`，它的梯度会被额外缩小 `m/K`。

但语言模型通常更希望每个有效 token 权重相同。此时窗口目标是：

~~~math
L_W^{\mathrm{token}}=\frac{1}{N_W}\sum_{k=1}^{m}\sum_{i=1}^{n_k}\ell_{k,i},
\qquad
N_W=\sum_{k=1}^{m}n_k
~~~

只有当每个 micro-batch 的 `n_k` 相同，`\bar L_k/m` 才与 token 平均等价。变长序列、padding 或动态 packing 会使 `n_k` 不同，所以应让 loss 返回 `loss_sum` 和 `valid_count`，再按窗口总 token 数归一化。这个分母问题不是数值细节，而是在决定哪些样本对参数更新拥有更大权重。

第三，梯度裁剪常见口径是 global norm clipping：

~~~math
\hat{g}=
\begin{cases}
g, & \lVert g\rVert_2 \le c \\
g\cdot \frac{c}{\lVert g\rVert_2}, & \lVert g\rVert_2 > c
\end{cases}
~~~

其中 `c` 是 `max_norm`。PyTorch 的 `clip_grad_norm_` 会在已有梯度上原地裁剪，并返回裁剪前的总范数。

第四，按 optimizer step 更新的 scheduler 应跟随真实更新次数，而不是 micro-step 次数：

~~~math
\eta_t=S(t_{\mathrm{opt}})
~~~

其中 `t_opt` 是已经执行的 optimizer step 数。如果梯度累积 `K=4`，每个 micro-step 都调用 scheduler，学习率会比预期快 4 倍变化。

第五，语言模型训练常见 loss 是 shift 后的 token-level 平均：

~~~math
L=\frac{1}{N_{\mathrm{valid}}}\sum_{i=1}^{B}\sum_{j=1}^{T-1}
\mathbf{1}[y_{i,j+1}\ne -100]\cdot
\mathrm{CE}(p_{i,j},y_{i,j+1})
~~~

其中 `p_{i,j}` 是第 `j` 个位置预测下一个 token 的词表分布，`y_{i,j+1}` 是下一个位置的 label，`N_valid` 是未被 ignore 的有效 label 数。训练循环若要跨 micro-batch 做精确 token 平均，不能只拿每个 batch 的 mean loss 再做简单平均；必须累加分子和分母。

第六，完整训练 checkpoint 可以抽象为：

~~~math
C_t=(\theta_t,s_t,h_t,e_t,r_t,c)
~~~

其中 `theta_t` 是模型权重，`s_t` 是 optimizer state，`h_t` 是 scheduler state，`e_t` 是 epoch / global step，`r_t` 是随机状态，`c` 是训练 config。实际工程还应记录数据游标或 sampler 位置 `d_t`，因此更完整地写成 `C_t=(theta_t,s_t,h_t,e_t,r_t,d_t,c)`。只保存 `theta_t` 不能严格恢复训练轨迹；只保存 `global_step` 也不能保证恢复后读取的是同一批数据。

## 5.2 最小训练 step

先看一个最小分类训练 step。

```python
import torch
from torch import nn


model = nn.Linear(10, 3)
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)
criterion = nn.CrossEntropyLoss()

x = torch.randn(32, 10)
labels = torch.randint(0, 3, (32,))

optimizer.zero_grad(set_to_none=True)
logits = model(x)
loss = criterion(logits, labels)
loss.backward()
optimizer.step()
```

关键顺序：

1. `zero_grad` 清掉旧梯度。
2. forward 得到 logits。
3. loss 连接 logits 和 labels。
4. `backward` 计算梯度。
5. `optimizer.step` 更新参数。

为什么通常先 `zero_grad` 再 forward？因为 PyTorch 梯度默认累积。只要确保每个 step 的 backward 前旧梯度被清掉，放在 step 末尾也能工作，但工程里更常见的是放在 forward 前，语义更清楚。

推荐：

```python
optimizer.zero_grad(set_to_none=True)
```

`set_to_none=True` 会把梯度设为 `None`，通常更省内存，性能也更好。

## 5.3 batch 到 device

模型和数据必须在同一个 device 上。

```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = model.to(device)
```

训练循环中：

```python
def move_to_device(batch, device):
    out = {}
    for key, value in batch.items():
        if torch.is_tensor(value):
            out[key] = value.to(device, non_blocking=True)
        else:
            out[key] = value
    return out
```

使用：

```python
for batch in train_loader:
    batch = move_to_device(batch, device)
```

如果 DataLoader 使用 `pin_memory=True`，配合 `non_blocking=True` 通常可以让 CPU 到 GPU 的搬运更高效。

这里有两个容易被混淆的条件。第一，`non_blocking=True` 只是允许在满足设备和内存条件时异步提交拷贝，不会把普通 pageable CPU 内存自动变成 pinned memory，也不会让 CPU 预处理凭空变快。第二，batch 不一定是简单的字典；多模态样本可能嵌套字典、列表和 tuple，工程代码要递归搬运，或者让 collate_fn 产出统一的扁平结构：

```python
def move_value(value, device):
    if torch.is_tensor(value):
        return value.to(device, non_blocking=True)
    if isinstance(value, dict):
        return {key: move_value(item, device) for key, item in value.items()}
    if isinstance(value, list):
        return [move_value(item, device) for item in value]
    if isinstance(value, tuple):
        return tuple(move_value(item, device) for item in value)
    return value


def move_to_device(batch, device):
    return move_value(batch, device)
```

调试时不要只打印一个 batch 的 device。要检查模型参数、所有浮点/整数 tensor 字段，以及 labels 的 dtype 是否符合 loss 的要求；例如 `CrossEntropyLoss` 的类别索引通常应是 `torch.long`，而不是和 logits 相同的浮点 dtype。

常见错误：

```text
Expected all tensors to be on the same device
```

排查时先打印：

```python
print(next(model.parameters()).device)
print(batch["input_ids"].device)
```

## 5.4 loss 在哪里计算

loss 可以在模型内部计算，也可以在训练循环外部计算。

### 5.4.1 模型外部计算 loss

```python
logits = model(input_ids)
loss = nn.functional.cross_entropy(
    logits.view(-1, logits.size(-1)),
    labels.view(-1),
)
```

优点：

1. 模型只负责 forward，职责清楚。
2. 便于复用同一个模型做不同任务。
3. loss 逻辑在 trainer 里更明显。

缺点：

1. 每个训练脚本都要写 loss 细节。
2. 对语言模型 shift logits/labels 容易重复出错。

### 5.4.2 模型内部计算 loss

```python
outputs = model(input_ids=batch["input_ids"], labels=batch["labels"])
loss = outputs["loss"]
```

优点：

1. 训练脚本更简洁。
2. loss shift、mask 等逻辑封装在模型里。
3. 接近 Hugging Face 风格。

缺点：

1. 模型和训练目标绑定更紧。
2. 多任务或研究实验中可能不够灵活。

工程建议：一个项目内保持一致。教学代码可以外部算 loss，便于理解；较完整的语言模型项目可以让 `forward(labels=...)` 返回 loss，降低训练循环复杂度。

## 5.5 语言模型 loss 的标准形态

因果语言模型通常用当前位置预测下一个 token。假设：

```text
logits: [B, T, V]
labels: [B, T]
```

需要错位：

```python
shift_logits = logits[:, :-1, :]
shift_labels = labels[:, 1:]
```

再展平：

```python
loss = nn.functional.cross_entropy(
    shift_logits.reshape(-1, shift_logits.size(-1)),
    shift_labels.reshape(-1),
    ignore_index=-100,
)
```

这里的关键点：

1. `logits[:, :-1, :]` 用第 `0` 到第 `T-2` 个位置预测后一个 token。
2. `labels[:, 1:]` 是目标 token。
3. padding 或不需要训练的位置应设为 `-100`。
4. `ignore_index=-100` 会跳过这些位置。

常见 bug：

1. 忘记 shift，导致模型预测当前位置 token。
2. labels padding 用了 pad token id 而不是 `-100`。
3. logits 和 labels 展平维度不一致。
4. attention_mask 和 loss mask 混淆。

## 5.6 梯度裁剪

大模型训练中，loss spike 和梯度爆炸并不少见。梯度裁剪是常见稳定手段。

```python
loss.backward()
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
optimizer.step()
```

顺序很重要：

1. 先 `backward()` 得到梯度。
2. 再 clip grad。
3. 最后 optimizer step。

如果使用混合精度和 GradScaler，需要先 unscale 再裁剪，这会在下一章详细展开。

记录梯度范数很有用：

```python
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
logger["grad_norm"] = float(grad_norm)
```

如果训练突然发散，优先查看：

1. loss 是否突然变大。
2. grad norm 是否突然变大。
3. 学习率是否在异常区间。
4. batch 是否包含异常样本。

裁剪不是修复错误梯度的替代品。若梯度已经是 NaN/Inf，裁剪只能传播或掩盖问题；若每一步都触发很强的裁剪，说明学习率、损失尺度、数据异常或模型初始化可能不合理。记录返回的裁剪前范数，并同时记录裁剪后的比例：

~~~math
r_t=\min\left(1,\frac{c}{\lVert g_t\rVert_2+\epsilon}\right)
~~~

如果 `r_t` 长期接近 0，优化器看到的几乎总是被压扁的梯度；如果只有少数 batch 的 `r_t` 很小，则更像是异常样本或偶发的数值尖峰。这个比例比单独看“裁剪后的梯度是否小于阈值”更能帮助判断训练状态。

## 5.7 梯度累积：显存换取有效 batch

显存有限时，可以先处理多个 micro-batch，只在一个窗口结束时更新一次参数。假设每个 micro-batch 有 4 个样本，`accum_steps=4`，一次 optimizer step 看过的样本数量大约是 16；但这只是“样本数量相加”，不等于所有情况下都严格复现一个 batch size 为 16 的单次 forward。随机层、动态 padding、不同的 loss 分母以及 BatchNorm 等状态都会造成差异。对于 Transformer 语言模型，最常见的差异来自有效 token 数。

### 5.7.1 固定 micro-batch 大小时的写法

当每个 micro-batch 的有效监督项数量近似相同，或者项目明确采用“每个 micro-batch 等权”的目标，可以把每个 loss 除以窗口大小：

```python
accum_steps = 4
optimizer.zero_grad(set_to_none=True)

for step, batch in enumerate(train_loader):
    outputs = model(**batch)
    raw_loss = outputs["loss"]
    (raw_loss / accum_steps).backward()

    if (step + 1) % accum_steps == 0:
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```

如果不除以 `accum_steps`，梯度会从多个 micro-batch 直接相加，尺度约为窗口平均梯度的 `accum_steps` 倍。对 SGD 来说这近似于放大学习率；对 AdamW 来说自适应归一化会改变部分影响，但权重衰减、梯度裁剪和非线性优化状态仍然会受到影响，因此不能把“AdamW 似乎不敏感”当成正确性证明。

### 5.7.2 最后一个不完整窗口

假设 DataLoader 有 10 个 micro-batch，`accum_steps=4`。完整窗口是 `1--4` 和 `5--8`，最后 `9--10` 只有两个 batch。如果最后两个 batch也要贡献一次更新，当前窗口的平均梯度应除以 2，而不是除以 4：

~~~math
g_{\mathrm{tail}}=\frac{1}{2}(g_9+g_{10}),
\qquad
\frac{1}{4}(g_9+g_{10})=\frac{1}{2}g_{\mathrm{tail}}
~~~

后一种写法会让 epoch 尾部的更新比完整窗口小一半。最简单的等权实现是先把窗口内的 loss 保存在列表中，知道实际窗口大小后再反向传播；更常用的在线实现则把最后一个窗口单独处理，或者让 sampler / `drop_last` 保证窗口完整。对于语言模型，若有效 token 数不同，还应采用下一小节的 token 归一化。

### 5.7.3 按有效 token 归一化

`F.cross_entropy(..., reduction="mean")` 返回的是当前 micro-batch 有效位置的平均值。设两个 micro-batch 的有效 token 数分别是 4 和 16，loss 均值分别为 2 和 1：

~~~math
\text{简单平均}=\frac{2+1}{2}=1.5,
\qquad
\text{token 平均}=\frac{4\times2+16\times1}{4+16}=1.2
~~~

简单平均让短 batch 和长 batch拥有相同权重；token 平均让每个有效 token拥有相同权重。对于 causal LM，后者通常更符合“所有有效预测位置共同构成训练目标”的定义。

如果模型只返回 mean loss，可以在每个 micro-batch 乘回有效 token 数，再在窗口结束时重新缩放：

```python
optimizer.zero_grad(set_to_none=True)
window_token_count = 0
window_losses = []

for step, batch in enumerate(train_loader):
    outputs = model(**batch)
    mean_loss = outputs["loss"]
    valid_tokens = int(batch["labels"][:, 1:].ne(-100).sum().item())
    if valid_tokens == 0:
        continue

    # 先暂存图和分子；窗口结束后按总有效 token 数反传。
    window_losses.append((mean_loss, valid_tokens))
    window_token_count += valid_tokens
    is_window_end = (step + 1) % accum_steps == 0
    is_last = (step + 1) == len(train_loader)

    if is_window_end or is_last:
        for micro_loss, count in window_losses:
            (micro_loss * count / window_token_count).backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
        window_losses.clear()
        window_token_count = 0
```

这段代码强调了分母的含义，但会在窗口结束前保留多个计算图，显存占用可能接近把整个有效 batch 一次性前向的效果。生产实现通常让模型返回 unreduced loss 或 `loss_sum`，在每个 micro-batch 立即反向；不过要提前知道窗口总 token 数，或者采用两遍统计、固定长度 packing、近似归一化等策略。工程选择应明确写入实验配置，而不能把不同分母的结果放在同一条 loss 曲线上直接比较。

## 5.8 optimizer 和 scheduler 的 step 时机

优化器更新参数，scheduler 更新学习率。

常见结构：

```python
loss.backward()
optimizer.step()
scheduler.step()
optimizer.zero_grad(set_to_none=True)
```

大多数按 step 更新的 scheduler，`scheduler.step()` 放在 `optimizer.step()` 后。某些特殊 scheduler 或旧版本示例可能不同，要看文档。

梯度累积时，scheduler 通常应该只在真实 optimizer step 后更新，而不是每个 micro-step 都更新。

```python
if should_step:
    optimizer.step()
    scheduler.step()
    optimizer.zero_grad(set_to_none=True)
```

常见错误：

1. 每个 micro-step 都 scheduler step，导致学习率衰减过快。
2. 恢复训练时没加载 scheduler state，学习率从头开始。
3. warmup steps 按 batch 数算错，没有考虑梯度累积。

这里还要区分两个概念：`micro_step` 是读过一个 micro-batch 的次数，`global_step` 通常是参数真正更新的次数。学习率、训练总步数、checkpoint 命名和 TensorBoard 横轴应统一采用其中一种口径；本章把 `global_step` 定义为 optimizer step 次数。若配置写的是 1000 个 optimizer steps，而代码却在每个 micro-step 调度学习率，实际 warmup 和 decay 都会提前 `accum_steps` 倍结束。

## 5.9 日志记录：不要只看 loss

训练日志至少应包含：

1. step 或 epoch。
2. train loss。
3. learning rate。
4. grad norm。
5. tokens/s 或 samples/s。
6. GPU 显存。
7. validation loss 或任务指标。

最小日志：

```python
if global_step % log_every == 0:
    lr = optimizer.param_groups[0]["lr"]
    print({
        "step": global_step,
        "loss": loss.item(),
        "lr": lr,
    })
```

注意，梯度累积时 `loss.item()` 可能是除以 `accum_steps` 后的值。如果想记录原始 loss，可以在缩放前保存：

```python
raw_loss = outputs["loss"]
loss = raw_loss / accum_steps
```

不要把带计算图的 loss tensor 长期保存到 list 里：

```python
losses.append(loss)  # 风险：保留计算图
```

应保存数值：

```python
losses.append(loss.item())
```

## 5.10 validation 循环

验证循环和训练循环不同。`model.eval()` 会切换 Dropout、BatchNorm 等模块的行为，但它不会自动关闭 autograd；`torch.inference_mode()` 会进一步关闭推理过程中的 autograd 记录。验证时应该：

1. `model.eval()`。
2. 使用 `torch.no_grad()` 或 `torch.inference_mode()`。
3. 不调用 backward。
4. 不调用 optimizer step。
5. 验证结束后切回 `model.train()`。

如果指标是样本级分类 loss，可以按样本数加权；如果指标是 causal LM 的 token loss，则必须按有效 token 数加权：

```python
def evaluate(model, val_loader, device):
    was_training = model.training
    model.eval()
    total_loss_sum = 0.0
    total_valid_tokens = 0

    with torch.inference_mode():
        for batch in val_loader:
            batch = move_to_device(batch, device)
            outputs = model(**batch)
            loss = outputs["loss"]

            valid_tokens = int(batch["labels"][:, 1:].ne(-100).sum().item())
            total_loss_sum += loss.item() * valid_tokens
            total_valid_tokens += valid_tokens

    if was_training:
        model.train()
    return total_loss_sum / max(total_valid_tokens, 1)
```

为什么不能直接平均每个 batch 的 loss？因为最后一个 batch 可能更小；在语言模型中，即使 batch size 相同，不同 padding 比例也会让有效 token 数不同。设第 `b` 个 batch 的有效 token 数为 `n_b`、平均 loss 为 `\bar L_b`，整个验证集的 token loss 应为：

~~~math
L_{\mathrm{val}}=\frac{\sum_b n_b\bar L_b}{\sum_b n_b}
~~~

而不是 `\frac{1}{B}\sum_b\bar L_b`。两者在每个 batch 的有效 token 数相等时才相同。

计算有效 token 数时要与模型的 shift 规则一致：

```python
valid_tokens = (batch["labels"][:, 1:] != -100).sum().item()
```

## 5.11 checkpoint 保存什么

一个 checkpoint 首先要回答“将来要拿它做什么”。推理发布只需要模型结构所需的权重和配置；从中断处继续训练，则需要保存所有会影响下一次参数更新或数据顺序的状态。把这两类文件都叫作 checkpoint，恢复时就容易误用。

### 5.11.1 训练恢复所需的状态

推荐保存：

```python
checkpoint = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "scheduler": scheduler.state_dict() if scheduler is not None else None,
    "epoch": epoch,
    "global_step": global_step,
    "micro_step": micro_step,
    "data_progress": data_progress,
    "config": config,
    "rng_state": torch.get_rng_state(),
}

torch.save(checkpoint, "checkpoint.pt")
```

如果使用 CUDA，还可以保存：

```python
checkpoint["cuda_rng_state"] = torch.cuda.get_rng_state_all()
```

如果训练代码使用 Python、NumPy、随机增强或多 worker 数据读取，还应分别保存对应状态：

```python
import random
import numpy as np


checkpoint["python_rng_state"] = random.getstate()
checkpoint["numpy_rng_state"] = np.random.get_state()
checkpoint["cuda_rng_state"] = (
    torch.cuda.get_rng_state_all() if torch.cuda.is_available() else None
)
```

`data_progress` 不是一个可以凭空由 `epoch` 推导出的字段。map-style 数据集通常至少要记录 epoch、sampler seed、rank/world size 和已经消费的 batch 数；流式数据集还可能要记录 shard 名称、文件偏移或样本 id。多 worker 预取意味着进程已经取到内存中的 batch 可能尚未真正被主训练循环消费，因此严格断点恢复要么让数据管线提供可恢复游标，要么接受从最近安全边界重新消费一小段数据。

完整保存的好处：

1. 参数能恢复。
2. optimizer 动量和二阶矩能恢复。
3. scheduler 学习率位置能恢复。
4. step 和 epoch 能恢复。
5. 随机状态尽量一致。
6. 数据进度和实验配置有迹可查。

如果只保存模型权重，恢复后虽然能继续训练，但 optimizer、scheduler、随机性和数据顺序可能已经改变。即使验证 loss 没有立刻 spike，也不能据此声称恢复是严格等价的。

## 5.12 checkpoint 加载和恢复训练

恢复训练的顺序也有约束：先按相同配置构造模型、optimizer 和 scheduler，把模型放到目标 device，再加载状态；加载后检查 optimizer 的学习率、参数组数量、scheduler 的 `last_epoch` 和 checkpoint 中的 global step。不要只看 `load_state_dict` 没抛异常就认为恢复正确。

恢复训练：

```python
checkpoint = torch.load("checkpoint.pt", map_location="cpu")

model.load_state_dict(checkpoint["model"])
optimizer.load_state_dict(checkpoint["optimizer"])

if scheduler is not None and checkpoint["scheduler"] is not None:
    scheduler.load_state_dict(checkpoint["scheduler"])

start_epoch = checkpoint["epoch"]
global_step = checkpoint["global_step"]

torch.set_rng_state(checkpoint["rng_state"])
```

若 checkpoint 中保存了额外随机状态，应一并恢复：

```python
import random
import numpy as np


if checkpoint.get("python_rng_state") is not None:
    random.setstate(checkpoint["python_rng_state"])
if checkpoint.get("numpy_rng_state") is not None:
    np.random.set_state(checkpoint["numpy_rng_state"])
if torch.cuda.is_available() and checkpoint.get("cuda_rng_state") is not None:
    torch.cuda.set_rng_state_all(checkpoint["cuda_rng_state"])
```

如果 optimizer state 加载后在 CPU，而模型在 GPU，通常 optimizer 会在下一次 step 时处理，但更稳妥的做法是确保模型先移动到 device，再加载或迁移 optimizer state。真实项目中要根据框架行为检查。

推理只需要模型：

```python
state = torch.load("model.pt", map_location="cpu")
model.load_state_dict(state)
model.eval()
```

训练恢复和推理加载是两个不同目标，不要混在一起。

恢复之后至少做三项廉价检查：第一，打印每个参数组的当前学习率并与 checkpoint 记录比较；第二，取一个固定验证 batch，确认恢复前后 logits 或 loss 一致；第三，让恢复后的循环再执行一个 optimizer step，确认 step、scheduler 和数据游标按预期递增。若使用分布式训练，还要确认所有 rank 对恢复边界的理解一致，不能由 rank 0 单独恢复后让其他 rank 继续使用旧数据状态。

## 5.13 原子保存与 best / last checkpoint

工程里常保存两类 checkpoint：

1. `last.pt`：最近一次状态，便于中断恢复。
2. `best.pt`：验证指标最好的模型，便于最终评估或上线。

两者的决策条件不同：`last.pt` 按训练进度更新，`best.pt` 按验证指标更新。`best.pt` 的指标必须来自固定、可追踪的验证集和明确的聚合分母；否则“最佳”可能只是某次统计误差。若 `best.pt` 还承担恢复训练职责，就保存完整状态；若只用于推理发布，可以另存一个精简的权重文件，避免把训练随机状态和优化器私有状态带入发布包。

示例：

```python
best_val_loss = float("inf")

val_loss = evaluate(model, val_loader, device)
save_checkpoint("last.pt")

if val_loss < best_val_loss:
    best_val_loss = val_loss
    save_checkpoint("best.pt")
```

保存文件本身也可能失败：进程被终止、磁盘写满或对象存储上传中断，都可能留下一个存在但不完整的文件。因此本地文件通常先写入同一目录下的临时路径，关闭并校验后再用原子替换更新目标名：

```python
from pathlib import Path
import os
import tempfile
import torch


def atomic_torch_save(state, target):
    target = Path(target)
    target.parent.mkdir(parents=True, exist_ok=True)
    fd, tmp_name = tempfile.mkstemp(
        prefix=f".{target.name}.", suffix=".tmp", dir=target.parent
    )
    os.close(fd)
    tmp_path = Path(tmp_name)
    try:
        torch.save(state, tmp_path)
        os.replace(tmp_path, target)
    finally:
        tmp_path.unlink(missing_ok=True)
```

原子替换只能保护单个文件的可见性，不能自动保证远程对象存储、多文件 shard 或元数据索引的一致性。更大规模的训练系统需要 manifest、校验和以及“已提交 step”的记录；本章先把单文件语义讲清楚。

注意：

1. `best.pt` 如果用于继续训练，也要保存完整训练状态。
2. 如果只用于推理，可以只保存模型权重。
3. 文件名里可以带 step，便于回滚。

## 5.14 可复现性

可复现性不是绝对的，但可以尽量提高。

常见设置：

```python
import random
import numpy as np
import torch


def set_seed(seed):
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)
```

还可以设置：

```python
torch.backends.cudnn.benchmark = False
torch.backends.cudnn.deterministic = True
```

但要知道：

1. 完全确定性可能降低性能。
2. 某些 CUDA 算子本身可能非确定。
3. 分布式训练、DataLoader 多 worker、混合精度都会增加复现难度。
4. 可复现性应记录“环境、配置、数据顺序和随机状态”四类信息，而不是只记录一个 seed。

## 5.15 训练中的异常检测

训练循环要主动检查异常。

### 5.15.1 NaN 和 Inf

```python
if not torch.isfinite(loss):
    print("non-finite loss", loss.item())
    break
```

检查梯度：

```python
for name, param in model.named_parameters():
    if param.grad is not None and not torch.isfinite(param.grad).all():
        print("bad grad", name)
```

发现非有限值后不应只打印一句字符串然后继续训练。继续执行 `optimizer.step()` 可能把一个坏梯度扩散到全部参数，使真正的根因难以定位。更有用的做法是保留当前 batch 的样本 id、输入长度、有效 token 数、学习率、上一次正常 step 的 checkpoint，并在确认策略后跳过或中断：

```python
if not torch.isfinite(loss):
    torch.save(
        {"batch": batch, "global_step": global_step},
        "bad_batch.pt",
    )
    optimizer.zero_grad(set_to_none=True)
    raise RuntimeError(f"non-finite loss at step {global_step}")
```

还要区分三种位置：输入已经含有 NaN/Inf，forward 输出先坏，或者 loss 是有限的但 backward 后梯度变坏。分别在输入、logits、loss 和参数梯度处检查，才能缩小范围。对全被忽略的 label，`CrossEntropyLoss` 可能无法提供有意义的监督；应在进入 backward 前检查 `valid_tokens > 0`，不要把“无监督 batch”当成正常零损失。

### 5.15.2 loss spike

如果 loss 突然变大，排查顺序：

1. 当前 batch 是否异常。
2. 学习率是否过大或 warmup 配置错误。
3. grad norm 是否突然变大。
4. 混合精度是否溢出。
5. mask 是否出现全忽略或全 `-inf`。

一个可操作的诊断顺序是先回到最近一个正常 checkpoint，在相同 batch 上复现；再固定随机种子和数据顺序，分别改变学习率、裁剪阈值和异常 batch。若只替换 batch 后恢复，问题更可能在数据或 mask；若所有 batch 都在同一 global step 变坏，优先检查 scheduler、optimizer state 和数值精度。这样得到的是可证伪的排查路径，而不是“把学习率调小试试”。

### 5.15.3 OOM

如果出现 CUDA OOM：

1. 减小 batch size。
2. 减小 sequence length。
3. 使用梯度累积。
4. 使用混合精度。
5. 使用 gradient checkpointing。
6. 检查是否保存了带图 tensor。

## 5.16 一个工程化训练循环骨架

下面给出一个较完整但仍然可读的训练循环。这个骨架采用“每个 micro-batch 等权”的简化口径，因此适合固定长度或有效监督项近似相等的数据。若是动态 padding 的 causal LM，应把模型接口扩展为同时返回 `loss_sum` 和 `valid_count`，再使用 5.7.3 节的 token 归一化实现。

```python
def train(
    model,
    train_loader,
    val_loader,
    optimizer,
    scheduler,
    device,
    num_epochs,
    accum_steps=1,
    log_every=10,
    eval_every=100,
):
    model.to(device)
    model.train()

    global_step = 0
    optimizer.zero_grad(set_to_none=True)

    for epoch in range(num_epochs):
        window_loss_sum = 0.0
        window_micro_count = 0
        for micro_step, batch in enumerate(train_loader):
            batch = move_to_device(batch, device)

            outputs = model(**batch)
            raw_loss = outputs["loss"]
            window_start = (micro_step // accum_steps) * accum_steps
            window_size = min(accum_steps, len(train_loader) - window_start)
            loss = raw_loss / window_size

            if not torch.isfinite(raw_loss):
                raise RuntimeError(f"non-finite loss: {raw_loss.item()}")

            loss.backward()
            window_loss_sum += raw_loss.item()
            window_micro_count += 1

            should_step = (micro_step + 1) % accum_steps == 0
            is_last = (micro_step + 1) == len(train_loader)

            if should_step or is_last:
                # window_size 对最后一个不完整窗口使用实际 batch 数。
                grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
                optimizer.step()
                if scheduler is not None:
                    scheduler.step()
                optimizer.zero_grad(set_to_none=True)

                global_step += 1

                if global_step % log_every == 0:
                    lr = optimizer.param_groups[0]["lr"]
                    print({
                        "epoch": epoch,
                        "step": global_step,
                        "loss": window_loss_sum / window_micro_count,
                        "lr": lr,
                        "grad_norm": float(grad_norm),
                    })

                window_loss_sum = 0.0
                window_micro_count = 0

                if val_loader is not None and global_step % eval_every == 0:
                    val_loss = evaluate(model, val_loader, device)
                    print({"step": global_step, "val_loss": val_loss})
                    model.train()
```

这个骨架覆盖了：

1. device 搬运。
2. loss 缩放。
3. 梯度累积。
4. 非有限 loss 检查。
5. 梯度裁剪。
6. optimizer 和 scheduler step。
7. 日志和验证。

真实项目还会继续加入 checkpoint 保存、分布式同步、混合精度、进度条、实验追踪、异常恢复和配置管理。

## 5.17 最小可运行训练循环审计 demo

下面这个 demo 用一个极小 causal LM 串起训练循环的关键动作：shift loss、`ignore_index=-100`、梯度累积、梯度裁剪、scheduler 跟随 optimizer step、token 加权验证、完整 checkpoint 和恢复验证。

```python
import math
import tempfile
import warnings
from pathlib import Path

import torch
import torch.nn.functional as F
from torch import nn

warnings.filterwarnings("ignore", message="CUDA initialization.*")
IGNORE_INDEX = -100


def set_seed(seed=0):
    torch.manual_seed(seed)


class TinyCausalLM(nn.Module):
    def __init__(self, vocab_size=16, hidden_size=12):
        super().__init__()
        self.embed = nn.Embedding(vocab_size, hidden_size)
        self.lm_head = nn.Linear(hidden_size, vocab_size)

    def forward(self, input_ids, labels=None):
        hidden = self.embed(input_ids)
        logits = self.lm_head(hidden)
        out = {"logits": logits}
        if labels is not None:
            shift_logits = logits[:, :-1, :].reshape(-1, logits.size(-1))
            shift_labels = labels[:, 1:].reshape(-1)
            out["loss_sum"] = F.cross_entropy(
                shift_logits,
                shift_labels,
                ignore_index=IGNORE_INDEX,
                reduction="sum",
            )
            valid_tokens = shift_labels.ne(IGNORE_INDEX).sum()
            out["valid_tokens"] = valid_tokens
            out["loss"] = out["loss_sum"] / valid_tokens.clamp_min(1)
        return out


def make_batches():
    batches = []
    raw = [
        [[1, 2, 3, 4, 5, 6], [1, 2, 3, 4, 5, 0]],
        [[2, 3, 4, 5, 6, 7], [2, 3, 4, 5, 0, 0]],
        [[3, 4, 5, 6, 7, 8], [3, 4, 5, 0, 0, 0]],
        [[4, 5, 6, 7, 8, 9], [4, 5, 0, 0, 0, 0]],
    ]
    for pair in raw:
        input_ids = torch.tensor(pair, dtype=torch.long)
        labels = input_ids.clone()
        labels[input_ids == 0] = IGNORE_INDEX
        attention_mask = input_ids.ne(0)
        batches.append({
            "input_ids": input_ids,
            "labels": labels,
            "attention_mask": attention_mask,
        })
    return batches


def move_to_device(batch, device):
    return {k: v.to(device) if torch.is_tensor(v) else v for k, v in batch.items()}


def evaluate(model, batches, device):
    was_training = model.training
    model.eval()
    token_loss_sum = 0.0
    token_count = 0
    with torch.inference_mode():
        for batch in batches:
            batch = move_to_device(batch, device)
            out = model(batch["input_ids"], labels=batch["labels"])
            valid = int(out["valid_tokens"].item())
            token_loss_sum += out["loss_sum"].item()
            token_count += valid
    if was_training:
        model.train()
    return token_loss_sum / max(token_count, 1)


def train_one_pass(model, batches, optimizer, scheduler, device, accum_steps=2):
    model.train()
    optimizer.zero_grad(set_to_none=True)
    optimizer_steps = 0
    raw_losses = []
    grad_norms = []
    batch_token_counts = [
        int(batch["labels"][:, 1:].ne(IGNORE_INDEX).sum().item())
        for batch in batches
    ]
    window_token_counts = []

    for micro_step, batch in enumerate(batches):
        batch = move_to_device(batch, device)
        out = model(batch["input_ids"], labels=batch["labels"])
        raw_loss = out["loss"]
        if not torch.isfinite(raw_loss):
            raise RuntimeError("non-finite loss")

        window_start = (micro_step // accum_steps) * accum_steps
        window_end = min(window_start + accum_steps, len(batches))
        window_tokens = sum(batch_token_counts[window_start:window_end])
        if window_tokens == 0:
            optimizer.zero_grad(set_to_none=True)
            continue
        (out["loss_sum"] / window_tokens).backward()
        raw_losses.append(round(raw_loss.item(), 4))

        should_step = (micro_step + 1) % accum_steps == 0
        is_last = (micro_step + 1) == len(batches)
        if should_step or is_last:
            grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=0.5)
            optimizer.step()
            scheduler.step()
            optimizer.zero_grad(set_to_none=True)
            optimizer_steps += 1
            grad_norms.append(round(float(grad_norm), 4))
            window_token_counts.append(window_tokens)

    return raw_losses, grad_norms, optimizer_steps, window_token_counts


set_seed(123)
device = torch.device("cpu")
model = TinyCausalLM().to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=0.08, weight_decay=0.01)
scheduler = torch.optim.lr_scheduler.StepLR(optimizer, step_size=1, gamma=0.8)
batches = make_batches()

initial_val = evaluate(model, batches, device)
losses, grad_norms, optimizer_steps, window_token_counts = train_one_pass(
    model, batches, optimizer, scheduler, device, accum_steps=2
)
final_val = evaluate(model, batches, device)

with tempfile.TemporaryDirectory() as tmpdir:
    ckpt_path = Path(tmpdir) / "last.pt"
    torch.save({
        "model": model.state_dict(),
        "optimizer": optimizer.state_dict(),
        "scheduler": scheduler.state_dict(),
        "global_step": optimizer_steps,
        "rng_state": torch.get_rng_state(),
    }, ckpt_path)

    restored = TinyCausalLM().to(device)
    restored_optimizer = torch.optim.AdamW(restored.parameters(), lr=0.08, weight_decay=0.01)
    restored_scheduler = torch.optim.lr_scheduler.StepLR(restored_optimizer, step_size=1, gamma=0.8)
    checkpoint = torch.load(ckpt_path, map_location="cpu", weights_only=False)
    restored.load_state_dict(checkpoint["model"])
    restored_optimizer.load_state_dict(checkpoint["optimizer"])
    restored_scheduler.load_state_dict(checkpoint["scheduler"])
    torch.set_rng_state(checkpoint["rng_state"])
    restored_val = evaluate(restored, batches, device)

print("initial_val_loss=", round(initial_val, 4))
print("micro_losses=", losses)
print("grad_norms=", grad_norms)
print("window_valid_tokens=", window_token_counts)
print("optimizer_steps=", optimizer_steps)
print("scheduler_last_epoch=", scheduler.last_epoch)
print("final_lr=", round(optimizer.param_groups[0]["lr"], 5))
print("final_val_loss=", round(final_val, 4))
print("loss_decreased=", final_val < initial_val)
print("restored_val_matches=", math.isclose(final_val, restored_val, rel_tol=0, abs_tol=1e-7))
print("restored_global_step=", checkpoint["global_step"])
print("model_training_after_eval=", model.training)
```

期望输出类似：

```text
initial_val_loss= 2.7991
micro_losses= [2.7366, 2.5374, 1.891, 2.2682]
grad_norms= [1.7231, 1.4695]
window_valid_tokens= [17, 13]
optimizer_steps= 2
scheduler_last_epoch= 2
final_lr= 0.0512
final_val_loss= 1.1381
loss_decreased= True
restored_val_matches= True
restored_global_step= 2
model_training_after_eval= True
```

这段输出要检查几件事：

1. `micro_losses` 有 4 个值，但 `optimizer_steps=2`，说明 `accum_steps=2` 生效。
2. `window_valid_tokens=[17, 13]`，说明每个窗口的 token 分母被显式统计，而不是假定所有 batch 长度相同。
3. `scheduler_last_epoch=2`，说明 scheduler 只在真实 optimizer step 后更新。
4. `final_lr=0.0512`，对应 `0.08 * 0.8^2`。
5. `loss_decreased=True`，说明训练循环确实更新了参数。
6. `restored_val_matches=True`，说明模型、optimizer、scheduler 和随机状态可以从 checkpoint 恢复到一致验证结果。
7. `model_training_after_eval=True`，说明验证函数结束后恢复了原本的训练模式。

## 5.18 训练循环常见 bug

### 5.18.1 loss 不下降

排查顺序：

1. 数据和 labels 是否正确。
2. loss 是否真的依赖模型参数。
3. 参数是否进入 optimizer。
4. 学习率是否过大或过小。
5. 梯度是否为 None、0、NaN 或 Inf。
6. 是否忘记 `optimizer.step()`。
7. 是否在 forward 中误用了 `no_grad()` 或 `detach()`。

### 5.18.2 训练速度很慢

可能原因：

1. DataLoader 太慢。
2. batch 到 device 阻塞。
3. 频繁打印日志。
4. 验证太频繁。
5. 保存 checkpoint 太频繁。
6. Python 逻辑太重。

### 5.18.3 恢复训练后 loss spike

可能原因：

1. 没加载 optimizer state。
2. 没加载 scheduler state。
3. 学习率从初始值重新开始。
4. 混合精度 scaler 状态丢失。
5. 数据顺序或随机状态变化。

### 5.18.4 验证结果不稳定

可能原因：

1. 忘记 `model.eval()`。
2. 忘记 `torch.no_grad()` 或 `inference_mode()`。
3. 验证集 shuffle 或采样不稳定。
4. 生成评估使用了随机采样。
5. 指标聚合方式错误。

## 5.19 从训练现象反推根因

### 5.19.1 loss 不下降

先用一个极小数据集做过拟合实验。若模型连 1--8 个固定样本都不能把 loss 压低，问题通常在训练闭环，而不是泛化能力。按以下顺序缩小范围：

1. 取一个 batch，确认 labels、shift 和 `ignore_index` 后确实存在有效监督项。
2. 在 `backward()` 后检查至少一个参数的梯度既不是 `None` 也不是全 0。
3. 比较 `optimizer.step()` 前后的参数差异，确认参数确实被 optimizer 管理。
4. 暂时关闭 scheduler、weight decay 和复杂数据增强，减少变量。
5. 固定学习率和随机种子，观察 loss 是否至少在小数据集上下降。

如果梯度存在但参数不变，优先检查 optimizer 参数组是否引用了错误的模型实例；如果参数改变但 loss 不变，检查 labels 是否随机、模型输出是否没有参与 loss，或者评估阶段仍在读取旧模型。

### 5.19.2 恢复训练后出现尖峰

恢复后的第一步应记录恢复前后四个值：参数摘要、optimizer 参数组学习率、scheduler `last_epoch`、optimizer state 中任意一个参数的 step。若学习率回到了初始值，说明 scheduler 没有恢复或创建顺序错误；若学习率正确而尖峰只发生在数据切换处，检查 sampler epoch、数据游标和 worker 随机状态；若 logits 在固定 batch 上都不一致，先检查模型权重、dtype、device 和评估模式。

### 5.19.3 训练变慢但 GPU 利用率不高

把一个 step 的墙钟时间拆成“等待 batch、CPU 到 device、forward/backward、optimizer、日志和保存”几个区间。若等待 batch 占比高，回到第四章检查 Dataset、collate、worker 和 pinned memory；若搬运占比高，检查 batch 是否过于碎片化以及是否真的使用 pinned memory；若计算占比高，再考虑混合精度、序列长度、梯度检查点等模型侧手段。只看 samples/s 会误导变长语言模型，必须同时记录有效 token/s：

~~~math
\mathrm{effective\ tokens/s}
=\frac{\sum \mathrm{valid\ tokens}}{\mathrm{wall\ time}}
~~~

### 5.19.4 验证指标波动

先确认 `model.eval()` 和推理上下文，再确认验证集顺序、采样策略、分布式聚合和 loss 分母。一个常见错误是每个 rank 先得到本地 mean loss，再对 rank mean 做平均；当各 rank 有效 token 数不同，这仍然会产生偏差。正确做法是跨 rank 汇总 loss sum 和 valid token count，再做一次除法。生成任务还需固定 decoding 参数，否则“验证波动”可能来自采样而不是模型。

## 5.20 常见误区

1. 以为训练循环只要能跑就行。工程训练循环必须可观测、可恢复、可排查。
2. 忘记 `optimizer.zero_grad()`，导致梯度跨 step 累积。
3. 梯度累积时没有缩放 loss。
4. 每个 micro-step 都 scheduler step，导致学习率变化过快。
5. 验证时只写 `model.eval()`，忘记关闭梯度。
6. checkpoint 只保存模型，不保存 optimizer 和 scheduler。
7. 日志里保存带图 tensor，导致显存增长。
8. 只看平均 loss，不看 grad norm、lr、tokens/s 和验证指标。
9. 恢复训练后不检查学习率，导致训练轨迹异常。

## 5.21 小练习

1. 写一个最小分类训练循环，包含 `zero_grad`、forward、loss、backward 和 step。
2. 给训练循环加 `move_to_device`，支持 batch dict。
3. 给语言模型 logits 和 labels 写 shift loss。
4. 给训练循环加入梯度裁剪，并打印 grad norm。
5. 实现梯度累积，确认 optimizer step 次数减少。
6. 写一个验证函数，正确使用 `eval()` 和 `inference_mode()`。
7. 保存完整 checkpoint，并写恢复训练代码。
8. 故意把 scheduler step 放到 micro-step，观察学习率变化是否符合预期。
9. 在日志中记录 loss、lr、grad norm 和 samples/s。
10. 构造一个 NaN loss，并写出排查打印代码。
11. 构造有效 token 数为 4 和 16 的两个 micro-batch，验证简单平均 loss 与 token 加权 loss 的差异。
12. 令 DataLoader 产生 `accum_steps=4` 但总 batch 数为 10，验证最后窗口按 2 而不是 4 归一化。
13. 保存 Python、NumPy、Torch 和 CUDA 随机状态，恢复后比较固定 batch 的 logits。
14. 故意截断一个 checkpoint 文件，说明原子保存和 manifest 能分别解决什么问题。

## 5.23 本章总结

训练循环是深度学习工程的主干。一个合格的训练循环不仅要完成 forward、loss、backward 和 optimizer step，还要处理 device、梯度累积、梯度裁剪、scheduler、日志、验证、checkpoint、恢复训练和异常检测。

需要记住的主线：

1. 每个 step 都要明确清梯度、前向、反向和更新参数的顺序。
2. 语言模型 loss 要正确 shift，并用 `ignore_index` 忽略不该训练的位置。
3. 梯度裁剪放在 backward 后、optimizer step 前。
4. 梯度累积要缩放 loss，并且 scheduler 通常只跟随真实 optimizer step。
5. 验证需要 `eval()` 和 `no_grad` 或 `inference_mode()`。
6. 完整 checkpoint 应保存模型、optimizer、scheduler、step、config 和随机状态。
7. 稳定训练依赖可观测性：loss、lr、grad norm、吞吐、显存和验证指标都要看。
