# 第一章：岗位画像

很多人准备大模型算法岗时，第一反应是列一张知识点清单：Transformer、RLHF、LoRA、RAG、KV Cache、MoE、FlashAttention、SFT、DPO、benchmark。清单越长，心里越踏实，仿佛面试是一场覆盖率考试。

但招聘不是在寻找一座会背术语的词典。一个团队真正需要的是：有人能把不清楚的问题变成可验证的实验，有人能把实验变成稳定的训练或服务，有人能分辨模型看起来变好和实际上变好之间的差异，还有人能在成本、安全、时间和组织协作的限制下把结果交付出来。

这就是岗位画像的意义。岗位画像不是把职位名称换一种说法，而是把一个职位背后的问题、产出、约束和证据说清楚。读者最终要获得的，不是“我应该背哪几个热门词”，而是一种判断能力：看到一份职位描述，能够推断团队要解决什么问题；回看自己的经历，能够判断哪些内容是真正的证据；安排准备时间时，能够把力气放在最可能产生结果的地方。

## 1.0 先建立两个视角

### 1.0.1 小白视角：同样叫“大模型算法岗”，工作可能完全不同

假设有两家公司都招聘“大模型算法工程师”。

第一家公司让你参与 70B 模型预训练，工作内容包括数据配比、分布式训练、loss 异常分析、checkpoint 恢复和 GPU 利用率优化。第二家公司让你为客服助手构建知识库问答，工作内容包括文档解析、检索、引用、拒答、线上指标和人工转接。两份职位名称相似，日常工作却分别更接近训练系统工程和应用算法工程。

如果求职者把两者都准备成“熟悉 Transformer、会使用 Hugging Face、了解 RAG”，面试时就会出现错位。前者会追问并行通信、混合精度和训练故障，后者会追问权限过滤、引用支持和任务成功率。知识点本身没有错，错的是没有把知识点放回岗位要解决的问题里。

因此，读岗位时先问三个简单问题：

1. 这个团队交付的主要对象是什么，是论文、模型权重、数据集、评估结论、推理服务，还是用户功能？
2. 这个对象最容易在哪里失败，是能力不足、训练不稳、评估失真、服务太慢、成本太高，还是行为不安全？
3. 这个职位要求我提供什么证据，才能让团队相信我能处理这些失败？

这三个问题比职位描述中的技术名词更接近真实工作。

### 1.0.2 专家视角：岗位画像是一个隐含的优化问题

从专家角度看，岗位不是技术标签的集合，而是一个带约束的目标函数。团队希望某个方向的结果更好，同时又不能无限增加算力、延迟、风险或协作成本。

可以用一个教学化的模型表达这种关系：

~~~math
V = w_c C + w_e E + w_r R + w_i I
~~~

其中，`C` 表示能力提升，例如模型在目标任务上的质量；`E` 表示执行能力，例如实验速度、代码质量和系统交付；`R` 表示可靠性与风险控制，例如回归、稳定性、安全和可审计性；`I` 表示实际影响，例如用户任务成功率、成本下降或研究结论被采用。`w_c`、`w_e`、`w_r`、`w_i` 是团队在当前阶段对这些维度的相对重视程度。

这个式子不是任何公司的真实评分表，也不能用来预测面试分数。它的作用是提醒读者：同一个技术动作在不同团队里的价值不同。把模型从 70B 改到 80B 可能提升能力，却可能使推理成本不可接受；把安全策略变得更严格可能降低高风险输出，却可能增加正常请求的误拒；把评估集做得更难可能降低表面分数，却可能提高对真实能力变化的辨别力。

岗位画像的工作，就是推断这几个权重和约束的大致形状，然后用自己的经历证明你能在这种目标函数下工作。

## 1.1 职位名称为什么不够用

### 1.1.1 名称是入口，产出才是边界

“研究员”“算法工程师”“机器学习工程师”“应用算法”“模型评估”这些名称在不同组织中并不稳定。有的研究员每天写训练代码和评估脚本，有的算法工程师主要负责数据和产品实验；有的评估岗位需要设计 benchmark，有的评估岗位其实是质量运营与标注系统。

区分它们最可靠的办法，是看职位最后要交付什么。

| 主要交付物 | 更可能关注的能力 | 典型问题 |
| --- | --- | --- |
| 新的模型方法或研究结论 | 问题定义、假设、实验、机制解释 | 为什么这个方法应该有效 |
| 可复现的训练 run 或模型权重 | 数据、优化、并行、稳定性、监控 | 为什么这次训练可信且能继续扩大 |
| 对齐后的模型行为 | 数据、偏好优化、行为分析、安全 | 模型为什么更有用却没有出现严重副作用 |
| 评估集、评测系统或行为报告 | 测量理论、数据构造、统计、错误分析 | 我们怎么知道模型真的变好了 |
| 高吞吐推理服务 | 性能、硬件、调度、可靠性、容量 | 如何在约束下服务更多请求 |
| Agent 或应用功能 | 任务分解、工具、状态、权限、产品指标 | 模型能否完成真实任务并在失败时恢复 |
| 训练或评估数据资产 | 数据质量、分布、标注、治理、血缘 | 数据变化如何影响模型能力和风险 |

同一个项目可能产生多种交付物。一个企业知识库项目可以产生检索模型、评估集、线上服务和产品指标，因此可以被不同岗位采用。但求职者必须说明自己负责哪一个交付物，以及对它承担了什么结果责任。

### 1.1.2 “会用工具”不等于“能够承担结果”

工具名称常常出现在职位描述里，但工具只是工作中的一个局部。会使用 vLLM，不等于能定位服务的尾延迟；会调用 Hugging Face Trainer，不等于能解释训练数据和 loss 曲线；会搭建 LangChain demo，不等于能让 Agent 在权限、幂等和故障恢复约束下完成任务。

可以把能力分成四层：

1. 认识：知道概念和名词，能够解释大致用途。
2. 复现：在受控数据和公开代码上跑通，并能改变一个变量观察结果。
3. 负责：在不完整条件下做方案选择、排查问题并对结果负责。
4. 影响：让结果被团队、产品或后续研究采用，并且能说明代价和边界。

这四层不是人格评价，而是证据强度的差别。刚入门的读者通常从第一层进入；面向研究或工程岗位时，至少要把关键方向推进到第二层或第三层；所谓“高级”也不是会更多术语，而是能处理第四层涉及的规模、协作和不确定性。

### 1.1.3 相邻岗位的交叉是正常现象

不要期待每个岗位都只有一种能力。训练研究员可能需要理解推理瓶颈，因为架构选择会影响部署；推理工程师需要理解模型结构，因为 KV Cache、量化和算子优化都依赖模型计算图；Agent 研究员需要懂评估和产品，因为长程任务的离线分数不一定等于用户成功；安全岗位需要懂数据和系统，因为风险可能通过训练数据、检索文档和工具链传播。

判断岗位时，应该区分“主责能力”和“协作能力”。主责能力决定你每天要交付什么，协作能力决定你能否把工作接到上下游。例如推理岗的主责可能是吞吐和稳定性，评估能力是它与研究和产品团队协作时必须具备的共同语言，但不一定要求你独立设计所有行为 benchmark。

## 1.2 一份岗位描述应该怎样读

### 1.2.1 从动词识别责任范围

职位描述中的名词容易让人分心，真正有信息量的通常是动词。

“read papers”只表示接触研究材料；“design and run experiments”表示需要独立形成假设并执行实验；“own”通常意味着结果责任更完整；“debug”表示岗位不是只做新功能，还要处理反常行为；“ship”或“deploy”表示结果必须穿过工程和产品约束。

把动词翻译成责任范围，可以得到比关键词更准确的判断：

| 描述中的动词 | 可能隐含的责任 | 需要准备的证据 |
| --- | --- | --- |
| explore / investigate | 从模糊问题中找方向 | 研究假设、探索过程、负结果 |
| design | 设计方法、实验或系统 | 方案比较、变量控制、取舍 |
| implement | 把想法变成代码或流水线 | 代码结构、测试、复现 |
| evaluate | 测量效果和风险 | 数据集、指标、统计和错误分析 |
| debug | 对反常结果进行归因 | 日志、排查顺序、最小复现 |
| optimize | 在约束下改善某项指标 | 基线、瓶颈、代价、回归 |
| own | 对方向或结果持续负责 | 目标设定、决策记录、后续迭代 |
| launch / deploy | 让系统进入真实使用 | 监控、灰度、回滚、事故处理 |

如果一份职位描述反复出现“design、evaluate、debug、ship”，它通常需要完整闭环，而不是只需要某个局部技术的熟练工。

### 1.2.2 从对象识别团队所处的阶段

同一项技术在不同阶段的工作方式不同。研究探索阶段容忍失败，重视问题新颖性和实验信息量；训练规模化阶段重视稳定性、数据版本和资源效率；上线阶段重视尾延迟、回滚、隐私、安全和用户影响。

可以从名词判断团队的阶段：

| 对象或措辞 | 更可能处于的阶段 | 读者应追问的问题 |
| --- | --- | --- |
| prototype、proof of concept、research agenda | 探索 | 假设是什么，怎样判断值得继续 |
| training run、data mixture、checkpoint | 训练生产 | 如何保证 run 可复现、可恢复、可比较 |
| eval suite、grader、regression | 测量与迭代 | 指标反映什么，哪些行为仍不可见 |
| latency、throughput、GPU memory、availability | 服务生产 | 瓶颈在哪里，尾部指标如何控制 |
| user feedback、adoption、task completion | 产品闭环 | 离线结果如何连接到真实价值 |
| abuse、privacy、red team、monitoring | 风险治理 | 风险怎样被检测、处置、复盘 |

初学者可以把它理解成“实验室、工厂、质检室、物流系统和门店”的区别。专家则要进一步判断这些阶段是否已经连成闭环，以及岗位负责的是其中哪一段。

### 1.2.3 区分必需条件、加分项和宣传语

职位描述通常同时包含三种内容。

第一种是必需条件，例如能写可靠代码、理解机器学习、能处理分布式系统。第二种是加分项，例如特定硬件、某个框架或某种论文经历。第三种是组织和品牌表达，例如“推动前沿”“改变世界”。第三种并不是没有意义，但不能直接转化成学习计划。

可以把每条要求改写成一个验证问题：

```text
原文：Experience with large-scale training and post-training of foundation models.
验证问题：我能否解释一次训练或后训练实验的目标、数据、规模、关键配置、失败模式、评估和个人贡献？

原文：Build evaluations for model behavior and safety.
验证问题：我能否定义行为类别，构造样本和 rubric，说明自动评估的偏差，并把结果连接到模型迭代？

原文：Improve product experiences using frontier models.
验证问题：我能否从用户任务出发，处理质量、延迟、成本、安全和交互之间的冲突？
```

验证问题越具体，准备就越容易。它会迫使读者准备可追问的经历，而不是继续增加技能栏中的词。

## 1.3 八类岗位的真实边界

本节把大模型相关岗位分成八类。这个分类是为了帮助读者建立地图，不是行业统一标准。现实中一个团队可能同时承担其中两三类工作，岗位名称也可能与下面的名称不同。

### 1.3.1 基础模型研究岗：从现象走向可检验的机制

基础模型研究岗的核心问题是：模型为什么在某些能力上变好或变差，以及怎样用新的架构、目标、数据或推理方式改变这种边界。

#### 小白视角：研究不是“看论文然后提出一个点子”

研究工作的起点往往不是“我要发明一个方法”，而是一个值得解释的现象。例如：

- 增加训练数据后，某类任务没有继续变好。
- 训练损失下降了，但长上下文问答反而变差。
- 一个模型在公开 benchmark 上提升，却在真实任务中更容易过度拒答。
- 更长的推理过程提高了数学正确率，却让工具调用任务变得更慢、更贵。

研究者要把现象变成问题，再把问题变成能够区分不同解释的实验。仅仅提出“加入注意力机制”“换一个位置编码”不构成有价值的研究，因为还没有说明原有方法失败在哪里、新方法为什么可能修复它、怎样排除只是参数量或数据量增加带来的收益。

#### 专家视角：研究岗位的产出是减少不确定性

研究岗位的产出不一定总是 SOTA 数字。一个高质量负结果也可能很有价值，只要它清楚地限定了某个方法的适用条件，或者排除了一个看似合理的解释。

一个完整研究链条通常包含以下关系：

```text
现象 -> 问题定义 -> 机制假设 -> 最小实验 -> 受控比较 -> 错误分析 -> 结论边界
```

例如，要研究某种长上下文方法是否提高了“跨段证据合并”，不能只把上下文窗口从 32K 改成 128K，然后比较一个总分。更好的实验会分别控制模型、训练数据、推理预算和文档长度，再构造单跳检索、跨段合并、位置变化、干扰段落和冲突证据等切片。这样即便总分没有提升，也能知道方法改善了哪一类能力、损害了哪一类能力。

#### 这个岗位通常交付什么

研究岗位可能交付新方法、原型代码、实验报告、模型检查点、评估集、论文、内部技术决策或对下一轮训练的建议。职位名称中“research”并不意味着可以不写工程代码；在大模型规模下，实验管线、数据处理、训练和评估本身就是研究的一部分。

#### 它与训练工程岗的边界

研究岗位更关注“什么方法值得试以及结果意味着什么”；训练工程岗位更关注“怎样让大规模训练稳定、高效、可恢复”。两者可以由同一个人承担，但叙述重点不同。

如果你讲的是“我把吞吐提高了 25%”，这更像训练系统证据；如果你还能讲清“为什么这个优化改变了可探索的实验范围，以及在同等计算预算下它改变了哪个结论”，才更接近研究证据。

#### 求职证据应该长什么样

强证据通常不是论文数量，而是能完整讲清一个研究问题：为什么重要，已有方法哪里不足，你负责哪部分，如何控制变量，哪些结果不支持原假设，最终结论能推广到哪里。

应届生可以用公开论文复现、消融实验和负结果建立这种证据。没有大规模资源时，研究深度可以来自变量控制、错误分析和诚实的边界说明，而不是伪装成工业规模。

### 1.3.2 预训练与训练工程岗：把昂贵的实验变成可靠的模型产出

训练岗位解决的不是“如何运行一个训练脚本”这么简单，而是如何让数据、模型、优化器、并行系统和硬件在长时间、大规模和故障频繁的条件下共同工作。

#### 小白视角：训练岗位面对的是一条生产链

可以把预训练想象成一座工厂。原始数据是原料，清洗和去重是来料检验，tokenizer 是加工规格，模型和优化器是生产设备，loss 和梯度是过程监控，checkpoint 是中间库存，评估是质量检验，最终模型是产品。

工厂里任何一环出问题，都可能表现为模型质量下降。数据污染可能让 benchmark 虚高，重复数据可能降低有效覆盖，学习率不合适可能导致 loss spike，通信拥塞可能让吞吐下降，checkpoint 损坏可能让数天训练无法恢复。因此“会写训练循环”只是起点。

#### 专家视角：训练工程的中心是资源、状态和可归因性

训练工程师需要同时管理三个状态。

第一是模型状态，包括参数、优化器状态、梯度缩放器和随机数状态。第二是数据状态，包括 shard 顺序、采样比例、数据版本和已经消费的位置。第三是系统状态，包括 rank、通信组、节点、GPU 健康、编排器和存储。

如果只保存模型权重而没有保存数据游标、随机数状态和配置，恢复出来的 run 可能并不等价于中断前的 run。它可能仍然能继续训练，却无法与原实验公平比较。

#### 训练岗位的核心诊断路径

遇到 loss spike 时，成熟的排查不会直接“把学习率调小”。它会先确认异常的时间范围和影响范围，再沿着数据、优化、数值和系统四条路径取证：

1. 数据路径：异常 batch 来自哪个 shard，是否有超长样本、乱码、重复或标签异常。
2. 优化路径：学习率、梯度范数、权重范数、梯度裁剪和 warmup 是否发生变化。
3. 数值路径：混合精度、loss scaling、溢出、NaN、异常激活是否同步出现。
4. 系统路径：某些 rank 是否掉速、通信是否重试、读取是否超时、checkpoint 是否不一致。

这四条路径的价值在于可归因。没有归因的修复可能暂时消除症状，却会把真正的故障带到下一次 run。

#### 训练岗位常见交付物

交付物可以是稳定的训练配置、数据质量报告、并行策略、性能分析、监控告警、checkpoint 机制、故障复盘、训练平台组件或最终模型。职位描述中的“训练经验”需要进一步问清是单机微调、数十卡实验、长周期预训练，还是训练平台建设；这些经历的证据强度不同。

#### 它与基础模型研究岗的边界

研究者可能提出一个新架构，训练工程师要判断这个架构是否能在目标硬件上稳定训练、是否改变通信和显存、是否值得纳入大规模 run。前者不能忽略后者，否则研究结果无法落地；后者也不能把所有问题简化为吞吐，否则可能错过真正的能力瓶颈。

#### 求职证据应该长什么样

可信的训练经历至少应能回答：训练规模是多少，数据如何组织，如何监控，遇到过什么故障，如何定位，修复后怎样验证没有引入回归，个人负责哪部分。不能公开规模时，可以说明相对规模、约束和故障类型，但不要把“调用了 DeepSpeed”写成“大规模训练负责人”。

### 1.3.3 Post-training 与对齐岗：把基础模型变成可使用、可控制的模型

基础模型能够预测下一个 token，不等于它会按用户意图完成任务，也不等于它在安全边界内稳定行动。Post-training 与对齐岗位处理的正是从“能生成”到“能使用”的转换。

#### 小白视角：不同训练阶段解决不同问题

预训练主要让模型学习语言、知识、模式和一定的推理基础；监督微调让模型学会遵循示范格式；偏好优化让模型在多个可接受答案中更倾向于有用、准确、符合要求的答案；安全训练和行为评估则处理拒答、滥用、隐私和风险边界。

这些阶段不是互相替代的按钮。把 DPO 换成另一个算法，不能自动修复低质量偏好数据；增加拒答样本，可能减少有害回答，也可能提高正常问题的误拒；提高某个 judge 的 win rate，不一定提高事实性或真实任务成功率。

#### 专家视角：对齐岗位处理的是目标、反馈和副作用

对齐工作的难点是目标通常不止一个，而且反馈信号不完美。可以把优化目标写成一个简化的多目标形式：

~~~math
J(\theta) = \lambda_h H(\theta) + \lambda_s S(\theta) + \lambda_f F(\theta) - \lambda_r R(\theta)
~~~

其中，`H` 可以表示 helpfulness，`S` 表示 safety，`F` 表示 factuality 或任务完成质量，`R` 表示风险或代价；`\theta` 是模型参数，`\lambda` 是不同目标的权重。这不是生产训练的完整目标，而是帮助我们理解为什么一个指标变好时，另一个指标可能变差。

成熟的对齐实验必须同时回答两件事：目标行为是否提高，以及副作用是否扩大。只报告 win rate 而不报告误拒、事实性、长度、风格、不同语言和不同风险等级的切片，无法说明模型整体变好。

#### 偏好数据比算法名字更重要

偏好数据中包含哪些候选答案、标注者看到什么上下文、比较标准是否一致、是否存在位置偏差和长度偏差，都会影响训练结果。一个 DPO 项目如果没有解释数据来源、正负样本构造、过滤规则和 holdout 评估，算法名称本身并不能证明工作深度。

例如，若 chosen 答案普遍比 rejected 答案长，模型可能学到“写得更长就更好”；若安全样本占比过高，模型可能学到“遇到不确定问题就拒答”；若训练集和评估集来自同一模板，离线提升可能只是格式记忆。

#### 对齐岗位的交付物

交付物可能是 SFT 数据集、偏好数据协议、reward model、DPO 或 RL 训练流程、行为评估、红队报告、拒答策略、模型卡、线上反馈闭环或安全修复方案。岗位边界可能跨研究、数据和产品，因此候选人要明确自己对哪个环节承担主要责任。

#### 它与安全工程岗的边界

对齐岗更多从模型训练和行为改变出发，安全工程岗可能更关注策略执行、检测器、审计、权限、滥用监测和事故响应。两者都需要理解风险，但一个主要改变模型行为，一个主要控制系统在真实环境中的风险暴露。

#### 求职证据应该长什么样

强证据不是“我做过 DPO”，而是能讲清一个行为问题：原模型在哪些场景失败，数据怎样表达目标，训练后哪些指标变化，哪些切片退化，如何验证收益不是评估偏差造成，最后为什么选择继续训练、调整数据还是回滚方案。

### 1.3.4 评估与模型行为岗：建立“真的变好了”的证据

评估岗位的核心问题是：面对一个复杂、会变化、可能被污染的模型，我们怎样知道它的能力、风险和用户价值发生了什么变化。

#### 小白视角：分数不是能力本身

如果模型在某个 benchmark 上从 70 分升到 75 分，至少有几种可能：模型真的学会了更多；训练数据泄漏了题目；提示模板更适合这个 benchmark；评测程序改变了；模型变得更愿意猜而不是更准确。分数是观测结果，不是能力的同义词。

因此评估工作要先定义行为，再设计测量。比如“代码能力”可以拆成语法正确、测试通过、边界处理、依赖安装、解释质量和安全性；“RAG 质量”可以拆成召回、证据支持、答案正确、引用完整和拒答适当。拆解之后，改进才有可能归因。

#### 专家视角：评估是测量系统，不是脚本集合

一个评估系统至少包含构念、样本、协议、评分器和决策五部分。

构念是想测什么，例如事实性或工具成功；样本是用什么任务代表它；协议规定模型输入、采样参数、工具环境和停止条件；评分器决定怎样把输出转成指标；决策定义什么变化足以影响训练或上线。

如果只换模型而不固定协议，比较就不公平；如果只看平均值而不看置信区间和切片，少数严重退化可能被掩盖；如果使用 LLM-as-judge 却不做人工校准，评分器自身的偏差可能成为结论。

最基本的变化量可以写成：

~~~math
\Delta m = m_{new} - m_{base}
~~~

但 `\Delta m` 只有在样本、协议、随机种子和评分规则可比时才有解释。对于比例指标，最好进一步报告样本量和不确定性。例如一个 100 个样本的 5 个百分点提升，和一个 10000 个样本的 5 个百分点提升，证据强度并不相同。

#### 评估岗位的交付物

交付物可以是 benchmark、行为 taxonomy、rubric、grader、回归集、评测平台、线上质量指标、模型行为报告、数据污染审计或训练决策建议。高水平评估岗位还会建立“发现失败 -> 生成样本 -> 修复 -> 回归”的闭环，而不是只在版本发布时跑一次榜单。

#### 它与对齐岗的边界

对齐岗位可能使用评估判断训练是否有效，评估岗位则要保持足够的独立性，避免为了证明某个训练方案有效而不断修改指标。二者最重要的区别不是会不会写评分脚本，而是是否能够把测量误差和模型改进分开。

#### 求职证据应该长什么样

可以讲一个指标和用户反馈不一致的案例：你怎样确认变化真实存在，如何分桶，怎样检查数据污染和协议变化，如何定位是能力下降、格式变化、过度拒答、延迟增加还是用户预期改变，最后如何把线上样本沉淀为回归集。

### 1.3.5 多模态岗：处理不同信号之间的对齐和损失

多模态岗位把文本、图像、音频、视频、布局和动作等信号放到同一个任务里。真正的难点不是“模型能不能接收图片”，而是不同模态的时间尺度、空间结构、噪声分布和评价标准都不同。

#### 小白视角：多模态不是把几个编码器拼起来

图像可以用 patch 表示，音频有采样率和时间轴，视频同时有空间和时间，文档还包含版面、表格和阅读顺序。把它们简单转成 token 并输入语言模型，只解决了接口问题，不保证模型理解了区域关系、时序变化或证据来源。

例如用户问“表格第三行的同比变化是多少”，系统不仅要识别数字，还要识别表头、行列关系、单位和计算规则；用户问“视频中人物何时拿起杯子”，系统需要处理动作发生的时间区间，而不是只判断视频里是否出现杯子。

#### 专家视角：多模态岗位要明确表示、融合和任务三层

第一层是表示：图像、语音或视频如何编码，分辨率和采样如何选择。第二层是融合：不同模态在什么阶段交互，是对比学习、交叉注意力、统一 token，还是后期组合。第三层是任务：模型怎样被训练和评估，是否需要 grounding、OCR、对话、生成或动作预测。

每一层都有预算。提高图像分辨率可能改善小字 OCR，却增加视觉 token 和延迟；增加视频帧数可能改善动作识别，却带来更高显存和冗余；更强的语言模型可能提高描述流畅度，却掩盖视觉证据不足造成的幻觉。

#### 多模态岗位的交付物

可能包括跨模态数据集、图像或语音编码器、对齐训练、视觉问答模型、文档理解链路、语音识别和生成系统、视频评估集、区域引用、数据质量报告或多模态服务。

#### 它与基础模型研究岗的边界

多模态也可以是研究岗位，但多模态岗位的特殊约束来自数据和评价。一个语言模型研究者可能更关注架构和训练目标，多模态研究者还必须解释标注粒度、时空采样、模态缺失和跨模态错误。

#### 求职证据应该长什么样

好的经历不只说“完成图文模型微调”，还要说明数据如何构造，模型在哪些空间关系、OCR、时序或跨模态推理上失败，如何设计评估，如何平衡分辨率、质量和延迟。若使用公开数据，应说明许可和处理方式；若使用内部素材，应说明隐私和删除边界。

### 1.3.6 推理与部署岗：在硬件和服务约束下交付模型能力

推理部署岗的中心问题是：模型已经训练出来之后，如何以可接受的延迟、吞吐、成本和可靠性向真实请求提供服务。

#### 小白视角：平均速度不是服务质量

一次请求的平均耗时很低，并不代表用户体验好。服务还要看首 token 延迟、生成速度、p95/p99 尾延迟、超时率、错误率和不同请求长度下的表现。高峰期大量长请求可能让平均值看起来正常，却让一小部分用户等待很久。

推理还分为 prefill 和 decode。prefill 处理输入上下文，通常计算密集；decode 逐步生成 token，通常更受内存访问、KV Cache 和调度影响。短问题、长文档和长输出的瓶颈可能不同，因此“把 batch 调大”不是普遍有效的答案。

#### 专家视角：部署优化是完整账本

可以用一个简化的单位请求成本表示资源取舍：

~~~math
Cost_{req} = Cost_{compute} + Cost_{memory} + Cost_{network} + Cost_{storage} + Cost_{failure}
~~~

其中，`Cost_failure` 代表超时、重试、错误输出、人工接管和信誉损失等间接代价。量化、批处理、缓存、投机解码、模型路由和并行策略都可能降低某一项，却增加另一项。

例如量化可能降低显存并提高吞吐，但需要检查精度退化；更大的 continuous batching 可能提高 GPU 利用率，但会增加排队和尾延迟；缓存可能降低重复请求成本，但必须处理权限、版本和新鲜度；模型路由可能降低平均成本，却要求路由错误时有回退和审计。

#### 推理岗位的诊断思路

遇到延迟问题时，应先把端到端延迟拆开：排队、输入处理、prefill、decode、网络、后处理和重试。再把资源利用率和请求分布对齐：GPU 是否算力不足，还是显存带宽受限；通信是否成为瓶颈，还是请求长度分布改变；平均吞吐提升是否以 p99 恶化为代价。

容量估算可以从 Little 定律开始：

~~~math
L = \lambda W
~~~

其中，`L` 是系统中平均在途请求数，`\lambda` 是平均到达率，`W` 是平均停留时间。这个关系不能替代详细压测，但能帮助初学者理解：在到达率不变时，延迟上升会使在途请求堆积；在容量接近上限时，少量抖动就可能造成排队放大。

#### 推理岗位的交付物

可能是推理 runtime、算子和 kernel 优化、量化方案、服务编排、批处理调度、模型路由、容量规划、监控、灰度发布和事故复盘。岗位可能偏底层 CUDA/NCCL，也可能偏服务架构；要看职位描述中的硬件、软件栈和结果责任。

#### 它与训练工程岗的边界

训练工程通常优化离线长任务和集群利用率，推理部署优化在线请求和服务协议。二者共享 GPU、并行和可观测性知识，但指标、故障模式和恢复方式不同。训练中一次重启可能只影响 run，在线服务中的同样问题还可能影响用户、计费和数据一致性。

#### 求职证据应该长什么样

可信的部署项目应该包含基线、流量或压测分布、硬件、优化动作、质量变化、p50/p95/p99、吞吐、显存、成本和回滚方案。只写“使用 vLLM 部署模型，延迟降低”不足以说明你理解瓶颈。

### 1.3.7 Agent 与应用算法岗：让模型在真实任务中完成闭环

Agent 岗位把模型接入检索、工具、记忆、状态和业务流程。它的核心问题不是“模型回答得像不像人”，而是“在权限和失败约束下，模型能不能完成有价值的任务”。

#### 小白视角：Agent 是任务系统，不是更长的 prompt

一次真实任务可能包含读取资料、判断下一步、调用工具、检查结果、修改参数、等待异步任务和向用户汇报。任何一步出错，都可能让最后结果失败。把更多工具描述塞进 prompt，不会自动解决权限、幂等、状态丢失或副作用重复执行。

可以把 Agent 任务看成状态转换：

~~~math
State_{t+1} = T(State_t, Action_t, Observation_t)
~~~

`State_t` 是当前任务状态，`Action_t` 是模型决定执行的动作，`Observation_t` 是工具或环境返回的结果，`T` 是状态更新逻辑。实际系统必须记录这些状态，才能在超时、重试或人工接管后恢复，而不能只依赖模型记忆对话文本。

#### 专家视角：Agent 质量要拆成多个概率

一个任务成功通常同时依赖规划、工具选择、参数正确、权限允许、工具执行、结果解释和最终交付。可以用教学化的近似表示：

~~~math
P(success) \approx P(plan) \times P(tool) \times P(param) \times P(exec) \times P(verify)
~~~

这不是严格的独立概率模型，因为各项往往相关，但它解释了为什么单步工具准确率很高时，长任务成功率仍可能很低。五个环节各自达到 0.9，五步相乘只有约 0.59；任务越长，错误累积越明显。

因此 Agent 岗位会关注任务分解、工具 schema、权限交集、幂等键、unknown 状态、重试预算、人工确认、审计、注入防护和结果验证。只展示一次成功 demo，无法证明系统具备长程可靠性。

#### Agent 岗位的交付物

交付物可能是工具调用策略、任务状态机、环境和 grader、记忆机制、检索和上下文编排、计算机使用能力、长任务恢复、Agent harness、线上任务指标或产品功能。

公开招聘样本中，Agent post-training 相关岗位已经把 coding、tool use、computer use、多智能体协作、long-horizon tasks、factuality、instruction following、graders、environments 和 evals 放在同一条工作链上。这说明现代 Agent 岗位往往同时包含研究、数据、评估、系统和产品，而不是单纯的提示词工程。

#### 它与 RAG 工程岗的边界

RAG 主要解决证据获取和上下文注入，Agent 还要处理动作和状态。一个知识库问答可以在生成前结束；一个报销 Agent 需要查询、校验、提交、等待审批和处理重复提交。RAG 是 Agent 的常见组件，却不是 Agent 的全部。

#### 求职证据应该长什么样

要说明任务定义、成功判定、工具和权限、失败分类、恢复策略、线上或仿真环境、成本和安全边界。比“做了一个自动化 Agent”更有说服力的是：在某类任务中把一次成功定义清楚，记录失败轨迹，并解释哪种修复真正提升了端到端成功率。

### 1.3.8 数据岗与数据智能岗：把数据变成可解释的能力来源

大模型数据岗位不是简单地“收集更多文本”。它处理的是数据分布、质量、版权、隐私、标注、偏好、污染、版本、血缘和模型反馈之间的关系。

#### 小白视角：数据质量不是一个通过或不通过的标签

一条数据可能在事实性上很好，却不适合指令微调；一段高质量代码可能含有不能使用的许可证；一组偏好样本可能标注一致，却只覆盖一种语言和一种用户风格；一份安全数据可能提高拒答，却没有覆盖误拒场景。

所以数据质量必须和任务目标绑定。对预训练数据，去重、覆盖度和污染很重要；对 SFT 数据，指令清晰、答案可执行和格式一致很重要；对偏好数据，比较标准、困难样本和分歧处理很重要；对评估数据，独立性、代表性和泄漏控制很重要。

#### 专家视角：数据是能力分布的控制面

可以把训练数据看成多个子分布的混合：

~~~math
P_{train}(x) = \sum_{k=1}^{K} \pi_k P_k(x)
~~~

其中，`P_k` 是第 `k` 类数据分布，`\pi_k` 是它在混合数据中的权重。改变 `\pi_k` 不只是改变数据数量，还会改变模型在不同能力、语言、风格和风险区域上的学习机会。

这也解释了为什么“数据越多越好”是错误的通用结论。低质量或重复数据可能挤占高价值数据的预算，某类数据占比过高可能造成能力偏置，评估数据混入训练集会制造虚假的提升。数据岗位的技术深度，体现在能把分布变化和模型行为变化连接起来。

#### 数据岗位的交付物

交付物可能是采集和清洗管线、去重和污染检测、数据说明书、标注协议、偏好数据、合成数据、质量报告、版本和血缘系统、隐私处理、数据混合实验或能力归因报告。

#### 它与训练岗和评估岗的边界

数据岗关注“喂什么以及为什么”，训练岗关注“怎样让模型学到”，评估岗关注“怎样测到并解释变化”。三者必须互相连接。数据岗位如果不看模型反馈，容易把静态质量分数当成价值；训练岗位如果不理解数据分布，容易把数据问题误判成优化问题；评估岗位如果不追踪数据来源，难以判断污染和代表性。

#### 求职证据应该长什么样

应说明数据来源、许可和隐私边界，清洗和去重规则，标注分歧如何处理，数据版本如何回溯，模型指标如何随数据变化，以及哪些结果只是相关性而不是因果性。能指出一次“增加数据没有带来收益”的失败，比只展示一个过滤率通常更有信息量。

## 1.4 八类岗位之外的共同能力

岗位方向不同，但高水平团队通常会反复验证几种共同能力。它们不是额外背诵的八个章节，而是贯穿每类工作的底层方法。

### 1.4.1 从模糊问题开始，而不是从工具开始

真实工作很少把问题写成“请实现 DPO”或“请使用 FlashAttention”。更常见的表达是：“最近版本在长文档任务上变差了”“用户觉得助手不可靠”“训练预算不够”“模型上线后尾延迟升高”。

强候选人会先界定现象和目标，再提出假设。比如“用户觉得不可靠”至少可能包含事实错误、引用不支持、过度自信、响应慢、格式不稳定和权限泄露。不同原因对应不同数据和修复，不应直接进入模型训练。

### 1.4.2 实验设计比结果数字更能说明问题

一个结果只有在基线、对照、评估协议和误差范围清楚时才有意义。无论是训练、对齐、评估还是部署，都应该能够回答：改变了什么，保持了什么，观察到了什么，是否存在其他解释。

教学上可以把实验可信度看成几个因素的共同约束：

~~~math
Q_{evidence} \propto Q_{baseline} \times Q_{control} \times Q_{measurement} \times Q_{reproducibility}
~~~

这不是统计学定理，而是一种审查习惯。某一项为零时，漂亮的数字也很难支撑结论。例如没有基线就无法判断提升，没有控制就无法归因，没有可靠测量就不知道测到什么，没有复现就无法知道结果是否偶然。

### 1.4.3 失败经历是信息，不是污点

面试中讲失败并不意味着主动暴露弱点。对研究和工程岗位而言，失败实验往往最能展示候选人的排查能力。关键是要说明失败发生在什么约束下，你如何发现它，哪些假设被排除，修复为什么有效，以及保留了什么边界。

例如，reranker 在离线召回上提升但线上延迟恶化，最后只对高风险请求或有限候选集启用；DPO 提升偏好胜率但造成过度拒答，后来按风险和 helpfulness 分层重建数据；量化后吞吐改善但某类代码任务退化，于是采用混合精度或按模型层做选择性量化。这样的叙述比“最终成功上线”更能体现判断。

### 1.4.4 事实、假设和推测要分开

大模型领域变化快，公开资料往往不完整。成熟的技术表达会明确说：这是日志已经证明的事实，这是目前最合理的假设，这是还需要实验验证的推测。

这种区分并不会显得不自信，反而能减少错误决策。尤其在研究和安全工作中，把未验证的解释当成事实，可能导致错误训练、错误回滚或风险低估。

## 1.5 公开资料能告诉我们什么，不能告诉我们什么

### 1.5.1 资料来源有不同证据等级

岗位研究不能只依赖二手面经或社交媒体传闻。可以按来源类型区分证据：

| 来源 | 能支持的判断 | 不能直接支持的判断 |
| --- | --- | --- |
| 公司官方职位页面 | 该岗位公开写出的职责和要求 | 所有面试官都按同一标准打分 |
| 公司技术博客或论文 | 公开项目方向、方法和术语 | 候选人一定会被问到这些细节 |
| 招聘平台的岗位快照 | 职位名称、团队和时间截面 | 当前组织永远保持相同结构 |
| 论文和开源项目 | 方法、实验和实现证据 | 某岗位一定要求完整复现 |
| 多名候选人的面经 | 某些人的流程体验 | 对所有团队、级别和时间都成立 |
| 个人博客和培训清单 | 学习路径和经验 | 公司官方要求或行业统一标准 |

本章引用官方职位页面，是为了核对公开职责，不是为了制造“某家公司有一张神秘评分表”的错觉。

### 1.5.2 本章对 OpenAI 岗位样本的使用边界

本章写作时核验了 OpenAI 公开招聘页面中的多个职位样本，包括 Research Engineer、Researcher, Training、Research Engineer / Research Scientist, Personal AGI (Post Training)、Software Engineer, Model Inference、Agent Post-Training Research 和 Agent Post-Training, Frontier Evals and Environments Research。

这些页面公开展示出的共同信号包括：可靠编程和分布式系统，训练与推理的模型直觉，实验和评估，模型行为与产品影响，Agent 的工具和长程任务，环境与 grader，以及安全和现实部署意识。这些信号与本章的岗位分类相互印证。

但这些页面有三个限制。第一，职位会随时间变化，页面是某个时间点的快照。第二，同一家公司内部不同团队、级别和地点的要求可能不同。第三，公开职位描述不会完整披露面试流程、团队文化和内部优先级。因此书中使用“公开样本显示”“可能更看重”“常见信号”，而不写成“官方统一标准”。

### 1.5.3 读者应如何核验自己的目标岗位

拿到具体职位后，至少做四项核验：

1. 读取职位描述中的动词和交付对象，标出主责能力。
2. 查看团队主页、公开论文、技术博客和产品信息，判断工作所处阶段。
3. 比较同一团队的多个职位，区分稳定要求和单个职位的偶然要求。
4. 在招聘沟通中确认级别、面试轮次、地点、语言、代码题和项目深挖范围。

最后一项尤其重要。公开资料可以帮助你提出好问题，但不能替代对具体职位的确认。

## 1.6 把岗位要求翻译成证据

### 1.6.1 四层证据模型

简历和面试的共同任务，是把经历转成证据。可以用四层模型审视每个知识点或项目。

| 层次 | 读者能证明什么 | 示例 |
| --- | --- | --- |
| 概念理解 | 知道方法解决什么问题 | 能解释 LoRA 为什么节省可训练参数 |
| 受控复现 | 能运行并观察变量变化 | 在公开数据上比较 rank、学习率和数据量 |
| 独立负责 | 能在约束下做选择并排查 | 负责数据、训练、评估和失败修复中的一段闭环 |
| 真实影响 | 结果被使用并改变了指标或决策 | 线上任务成功率提升，或研究方向因实验结论调整 |

越靠后的证据越稀缺，但不意味着所有人都必须有生产级经历。学生可以用严谨复现和研究型项目证明潜力；工程转算法的人可以用可观测性、性能优化和模型实验建立迁移证据；有工业经验的人则需要说清个人贡献和保密边界。

### 1.6.2 证据必须和责任匹配

一个常见问题是证据规模与责任表述不匹配。

在个人电脑上跑通 7B 模型量化，可以证明你理解基本流程，但不能直接证明你设计过大规模推理平台。参与团队的模型训练，可以证明你接触过流程，但不能自动证明你负责了训练稳定性。写过评估脚本，可以证明实现能力，但还要说明样本、协议、评分和错误分析，才能证明评估判断。

因此叙述时要使用准确的责任动词：参与、负责模块、主导方案、独立完成、推动上线、维护长期运行，各自对应不同的证据强度。诚实地说清边界，不会削弱项目，反而能让后续追问落在你真正掌握的部分。

### 1.6.3 一个项目怎样服务不同岗位

假设你做过企业知识库助手。同一个项目可以有不同的岗位叙述：

- 投 RAG/应用算法岗，重点讲检索召回、重排、引用支持、任务成功和用户转接率。
- 投评估岗，重点讲问题类型、人工 rubric、引用正确性、数据泄漏和回归集。
- 投推理岗，重点讲上下文长度、prefill、缓存、p95 延迟、吞吐和成本。
- 投 Agent 岗，重点讲工具调用、权限、状态、失败恢复和人工接管。
- 投数据岗，重点讲文档解析、去重、版本、标注、隐私和数据变化带来的模型行为差异。

这不是“包装成不同项目”，而是从同一事实中选择与目标岗位相关的因果链。不能凭空添加没有做过的职责；可以调整叙事焦点，但不能改写事实。

## 1.7 量化判断匹配度和准备优先级

### 1.7.1 不要把匹配度理解成一个神秘分数

岗位匹配度不是“我会多少关键词”。更合理的思路是：岗位要求的权重不同，个人证据的强弱不同，准备时间也有限。

可以建立一个个人使用的教学模型。对岗位 `r` 的第 `i` 项能力，令 `w_i\geq0` 表示重要性，`x_i\geq0` 表示你目前的证据水平，`t_i>0` 表示该岗位期望的目标水平，并假设至少有一项权重为正，则：

~~~math
F(r) = \frac{\sum_i w_i \cdot \min(1, x_i / t_i)}{\sum_i w_i}
~~~

当 `x_i` 达到 `t_i` 时，该项贡献被截断为 1，避免某个强项无限抵消另一个关键短板。如果没有任何正权重项，或者某项的目标水平没有定义，就不应计算 `F(r)`，而应先补齐岗位要求表。这里的 `F(r)` 只是帮助排序的个人估算，不是招聘决策，也不应伪装成客观概率。

### 1.7.2 怎样给证据水平赋值

可以把 `x_i` 粗略记录为 0 到 4：

0 表示没有接触；1 表示能读懂和解释；2 表示能在受控环境复现；3 表示独立承担过一个完整模块；4 表示有可验证的真实影响或长期维护经验。

例如，一个投推理部署岗的候选人可能在模型原理上是 3，在 Python 和 PyTorch 上是 4，在 GPU kernel 上是 1，在线上服务容量上是 2，在评估和故障复盘上是 2。这个表格的价值不在于计算出一个漂亮小数，而在于揭示“我最需要补的是哪一种证据”。

### 1.7.3 用重要性乘以缺口分配时间

如果总准备时间为 `H\geq0` 小时，第 `i` 项的目标水平与当前水平差距为 `g_i\geq0`，并且至少有一项 `w_i g_i` 为正，可以用下面的比例安排时间：

~~~math
h_i = H \cdot \frac{w_i g_i}{\sum_j w_j g_j}
~~~

其中 `h_i` 是分配给第 `i` 项的时间。如果所有 `w_i g_i` 都为零，说明当前表格没有可排序的缺口，应把时间用于保持、验证或重新确认目标，而不能用零分母硬算分配比例。这个式子会产生两个有用的提醒：高权重但差距小的项目不一定优先；低权重但差距巨大的项目也不能无限吞噬时间。最后还要考虑证据转换成本，例如从“知道概念”提升到“能复现”可能只需一个周末，从“能复现”提升到“真实影响”可能需要一个长期项目。

### 1.7.4 先补共同底座，再补岗位尖峰

准备顺序通常应分两层。第一层是所有方向都会使用的底座：概率和统计、机器学习基础、Transformer、数据和评估、Python、实验记录、基本系统概念。第二层是岗位尖峰：训练岗的分布式和稳定性，部署岗的性能和容量，对齐岗的偏好数据和行为评估，Agent 岗的工具和状态，多模态岗的跨模态数据与评估。

如果底座完全缺失，直接追逐岗位尖峰会产生“知道名词但无法解释”的脆弱知识；如果只学底座而不做岗位项目，又无法证明自己能把知识转成结果。

## 1.8 三个具体定位案例

### 1.8.1 案例一：有论文但缺乏工程证据的应届生

小林有一篇参数高效微调相关论文，做过三个公开数据集和一些消融实验，但没有工业训练经验。他希望投基础模型研究岗和训练工程岗。

如果他把简历写成“熟悉 PyTorch、Transformers、LoRA、DPO、DeepSpeed、FSDP”，两个岗位都会觉得方向模糊。更好的定位是把论文的研究证据和工程缺口分开：

```text
主线：参数高效适配与小样本实验设计。
已有证据：方法动机、消融、失败结果、代码复现和论文写作。
缺口：长周期训练、分布式故障、checkpoint、吞吐和多节点调试。
近期准备：补一个可复现的多卡训练项目，并记录通信、显存、恢复和评估，而不是再堆新的算法名词。
```

这样的小林可以把研究岗作为主投方向，把训练工程岗作为需要补证据的方向。面试中诚实承认“我没有做过万卡训练，但我在受控规模上验证过哪些问题，下一步怎样扩展”，比冒充大规模训练负责人更可靠。

### 1.8.2 案例二：系统工程师转推理和应用算法

小周长期做高并发服务，熟悉容器、监控、分布式缓存和故障处理，但只做过一次 LoRA 微调。他投递推理部署岗和 Agent 平台岗。

他的优势不是“缺少模型背景”，而是已经具备真实系统的责任经验。简历和面试应该把这些经验翻译到模型系统中：

- 把高并发服务映射到 token 流式请求、排队、p99 和容量。
- 把缓存一致性经验映射到 prompt、KV、检索和工具结果缓存的版本与权限。
- 把故障处理经验映射到模型超时、部分结果、重试、回滚和审计。
- 用一个完整小项目补上模型质量、评估和工具调用，而不是试图在短期内变成训练研究员。

他的岗位画像可能是“推理与 Agent 平台工程”，而不是泛泛的“大模型算法”。清晰的主线能让既有经验产生价值。

### 1.8.3 案例三：应用项目很多但研究证据不足

小陈做过多个 RAG 和 Agent demo，能快速接模型 API，但每个项目都缺少固定评估、失败记录和线上指标。他希望投前沿模型研究岗。

他需要先接受一个事实：项目数量不等于研究能力。当前最有价值的补充不是再做一个 Agent，而是选择一个已有项目，建立问题切片、基线、对照、错误 taxonomy 和可复现实验。

例如把“RAG 回答质量不好”拆成召回缺失、权限过滤、证据冲突、引用不支持、生成幻觉和拒答不当，分别构造样本并比较 chunk、reranker、上下文预算和提示策略。即使最后结论是“更复杂的链路没有普遍收益”，也能形成研究和评估证据。

小陈如果最终更适合应用算法岗，也不意味着准备失败。岗位画像的作用之一，就是帮助他发现自己真正拥有的优势，而不是强迫所有人去竞争同一种岗位。

## 1.9 常见错位，以及为什么会发生

### 1.9.1 把热门词当成能力

热门词容易记忆，也容易写进简历，但它们没有说明你能完成什么。解决办法是每个关键词后面补一个动作和一个结果：用什么数据，解决什么问题，如何评估，个人贡献是什么。

### 1.9.2 把 benchmark 分数当成真实价值

公开 benchmark 能帮助比较，但不能替代任务定义、错误分析和产品指标。尤其是 Agent、RAG、安全和多模态任务，单一平均分很容易掩盖关键失败。

### 1.9.3 把“参与”写成“负责”

团队项目天然有协作。面试官并不要求一个人完成所有模块，但会追问你的边界。把数据、训练和线上指标全部写成个人成果，短期可能增加关键词，长期会降低可信度。

### 1.9.4 把 demo 规模误写成生产规模

在本地跑通一个工具调用流程很有价值，但它证明的是原型实现。要证明生产能力，还需要环境隔离、权限、重试、可观测性、容量和事故处理。不同证据都可以写，不能把它们混在一起。

### 1.9.5 只讲成功，不讲代价

模型效果、延迟、成本、安全和覆盖面经常互相牵制。只讲单项提升会让方案显得不真实。强叙述应该说明选择了什么，放弃了什么，以及在什么约束下这个选择合理。

### 1.9.6 用过时的团队印象替代当前资料

大模型组织变化很快。几年前的“某公司只看论文”或“某岗位一定考某道题”都可能失效。面经可以作为待核验线索，不能作为定论；目标岗位的最新描述和招聘沟通应优先。

## 1.10 从岗位画像连接到简历、项目和面试

本章建立的是选择框架，后续章节分别处理不同的证据载体。

简历要解决的是：在有限篇幅里让读者看出方向、责任和影响。项目包装要解决的是：把真实经历展开成问题、方案、实验、失败、取舍和边界。Coding、基础、training、deployment、alignment、多模态和 system design 章节要解决的是：在现场交流或实现中证明底层能力。行为面试和 mock interview 要解决的是：让技术证据能够在协作和压力下被清楚表达。

因此，岗位画像不应单独阅读后就结束。每当后续章节要求准备一个项目或一类问题，都要回到本章问一句：它服务于哪个岗位主线，证明的是哪一层证据，是否存在相邻方向的错位。

## 1.11 本章学习练习

### 练习一：把职位描述改写成产出表

选择一份真实职位描述，列出其中所有重要动词，并把它们改写成“对象、动作、指标、约束”四列。例如“improve inference efficiency”不能停在“优化推理”，而要继续问对象是哪个服务，动作是量化、调度还是算子，指标是吞吐还是 p99，约束是质量、显存还是成本。

### 练习二：制作个人证据矩阵

对研究、训练、评估、系统、产品、安全和协作七个维度，分别写出你拥有的最高证据层级、一个具体事实和一个尚未验证的地方。禁止用“熟悉”“了解”“有经验”代替事实。

### 练习三：做一次相邻岗位改写

选一个真实项目，分别用研究、部署和应用算法三个角度写三段说明。写完后标出哪些句子是共同事实，哪些句子只是叙事重点变化，检查是否在任何版本中添加了没有做过的职责。

### 练习四：写出一个失败实验的证据链

用“现象、假设、排查、对照、修复、残余风险”六个小标题记录一次失败。没有真实项目时，可以使用公开数据做一个小实验，但必须把合成结果和真实工程经历区分开。

## 1.13 小结：岗位画像是一张决策地图

大模型算法岗不是一个单一职业，而是一组围绕模型能力、训练、对齐、评估、多模态、推理、Agent 和数据的工作。区分它们时，职位名称只能提供入口，真正有用的是交付物、失败模式、约束和责任范围。

准备求职时，不要先问“还缺哪些热门知识点”，而要先问：

1. 目标团队交付什么对象？
2. 这个对象最容易在哪里失败？
3. 岗位要求我提供哪一层证据？
4. 我的经历中哪些事实能支持这个判断？
5. 哪些能力是当前短板，补齐它们需要什么实验或项目？

当这些问题有了答案，简历、项目叙述、基础复习和模拟面试就会围绕同一条主线组织起来。岗位画像不是求职包装术，也不是一张静态标签表，而是帮助你分配时间、选择证据和理解工作的决策地图。
