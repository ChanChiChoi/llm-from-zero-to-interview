# 第三章：项目叙事

简历让别人知道你做过什么，项目叙事让别人理解你为什么这样做，以及这些结果是否真的属于你的经验。

很多候选人的项目本身并不差，但讲出来很弱。常见情形是从公司背景讲到技术栈，再讲到一个漂亮数字，中间没有清楚的问题、没有基线、没有失败，也没有说明个人贡献。听者最后只知道“这个人参与过一个大模型项目”，却不知道他是否能定义问题、判断瓶颈、设计实验和承担结果。

把项目讲清楚，不等于把普通项目吹成宏大项目。项目叙事的本质，是把真实经历恢复成一条可以被检查的因果链：

~~~text
场景和约束
    -> 原系统在哪里失败
    -> 你提出了什么解释
    -> 采取了什么干预
    -> 用什么协议比较
    -> 结果改变了什么
    -> 仍然有哪些边界
~~~

这条链既服务于求职交流，也服务于工程复盘和研究报告。它迫使你区分观察与解释、团队结果与个人贡献、相关变化与因果结论。第 2 章讲的是如何把项目压缩成简历中的证据，本章讲的是进入技术对话后，怎样把这份骨架展开成一个可信的项目故事。

## 3.0 两个视角：项目不是故事，而是被解释的证据

### 3.0.1 小白视角：听众不是想听技术名词

初学者往往从自己最熟悉的部分开始讲，例如“我们用了 LoRA、DPO、RAG、FAISS 和 vLLM”。但听众还不知道项目要解决什么问题，所以这些名词没有落点。

更容易理解的讲法是先给出一个具体场景：

~~~text
这个项目服务企业制度问答。原系统能够检索文档，但回答经常引用过期版本，或者在没有证据时继续编造。我的工作是定位问题来自检索、上下文组织还是生成，并在延迟约束下验证改动是否真的改善了任务完成。
~~~

这几句话还没有讲算法，却已经说明了对象、失败、约束和个人任务。听众知道后面应该关注什么。

### 3.0.2 专家视角：项目叙事是在表达一个因果模型

专家会下意识地问：结果变化是由什么造成的？有没有其他同时发生的变化？测量协议是否稳定？项目是否能在不同数据或流量下复现？

可以用教学化的因果链表示：

~~~math
X_{context} -> A_{intervention} -> M_{mechanism} -> Y_{outcome}
~~~

X_context 是项目所处的上下文和约束，A_intervention 是你采取的干预，M_mechanism 是你认为干预通过什么机制产生作用，Y_outcome 是观察到的结果。比如“长文档中间位置召回差”是现象和上下文，“重新分块并加入 reranker”是干预，“相关证据更容易进入上下文”是机制，“引用支持率提高”是结果。

如果缺少机制，项目会变成“做了 A，结果是 Y”的相关性报告；如果缺少结果，项目会变成没有验证的想法；如果缺少上下文，结果就无法判断是否值得付出成本。好的项目叙事不是把所有细节都说完，而是让这四个位置都能被追溯。

### 3.0.3 项目叙事与简历的边界

简历只需要留下项目的最小证据骨架：对象、问题、个人动作和结果。项目叙事则要回答选择、实验、失败、协作和边界。

同一个项目可以这样分层：

| 层次 | 主要任务 | 典型内容 |
| --- | --- | --- |
| 简历 bullet | 让项目值得被继续了解 | 场景、动作、结果、证据类型 |
| 一分钟概览 | 建立共同上下文 | 目标、角色、主要方案、最重要结果 |
| 三分钟叙述 | 交代因果链 | 基线、难点、决策、评估、取舍 |
| 深度讨论 | 支撑技术判断 | 数据、实现、失败、统计、边界、替代方案 |
| 复盘材料 | 让团队可学习 | 时间线、证据、根因、行动项、未决风险 |

如果把深度讨论全部塞进简历，读者找不到主线；如果在技术对话中只重复简历，听者也无法判断你是否真正理解项目。层次不同，事实必须一致。

## 3.1 先选择一个能讲深的项目

### 3.1.1 项目数量不是项目证据

拥有十个 demo，不一定比拥有一个能讲清失败和修复的项目更有说服力。选择项目时，不要先看技术热度，而要看能否形成完整证据链。

一个适合深入叙述的项目通常具备至少三项：

1. 有明确的用户任务、研究问题或工程目标。
2. 有可描述的基线和失败模式。
3. 你对其中一个关键环节承担了真实责任。
4. 有实验、日志、评估或线上观察作为结果依据。
5. 做过至少一次取舍、回滚或方向调整。
6. 能说清当前方案不适用的地方。

课程作业、公开复现和个人项目也可以满足这些条件，只是必须准确标出环境和证据层级。没有生产流量不等于没有价值，隐瞒没有生产流量才会造成误导。

### 3.1.2 建立项目事实卡

在练习讲述前，先不要写故事，先写事实卡。事实卡是叙事的底稿，至少包括：

| 字段 | 要记录的内容 |
| --- | --- |
| 时间和环境 | 何时完成，个人电脑、实验室、团队离线、灰度还是生产 |
| 对象 | 模型、数据、服务、用户任务或研究问题 |
| 基线 | 原系统、旧版本、简单方法或人工流程 |
| 目标 | 质量、延迟、成本、稳定性、安全或研究结论 |
| 约束 | 数据、算力、期限、隐私、兼容性和上线条件 |
| 个人责任 | 独立完成、负责模块、协作完成和没有参与的部分 |
| 干预 | 改了什么，为什么改，哪些方案被放弃 |
| 评估 | 样本、指标、协议、时间和分桶 |
| 结果 | 正向变化、负向变化、未知项和置信程度 |
| 证据 | 代码、日志、实验表、报告、公开链接或同事确认 |
| 边界 | 不能推广到哪里，仍需什么验证 |

事实卡可以写得很长。它不是最终答案，而是防止你在压缩故事时把日期、分母、职责和结果混在一起。

### 3.1.3 个人贡献要单独建账

团队项目最常见的叙事问题，是“我们”做了很多事情，“我”到底做了什么不清楚。可以把贡献分成四类：

- 直接实现：你亲自写代码、构造数据、运行实验或维护服务。
- 技术判断：你提出假设、选择方案、决定实验顺序或批准回滚。
- 协作交付：你与数据、平台、产品、安全或标注团队完成接口和交接。
- 结果责任：你负责监控结果、解释异常或推动后续行动。

没有参与的部分要明确标出。比如训练框架由平台同事负责，你负责数据版本和评估，就应当这样说。清楚的边界不会削弱贡献，反而能让讨论集中在你真正能解释的地方。

## 3.2 用一个贯穿案例学习项目叙事

下面使用“澄明企业助手”作为教学案例。案例中的数字和名称用于说明方法，不代表某个真实公司或线上结果。真实项目必须替换成自己的事实。

### 3.2.1 场景：为什么系统需要改变

澄明企业助手为客服人员回答制度和产品政策问题。原系统由关键词检索、模板拼接和通用语言模型组成。它在常见问题上反应很快，但有三类高频失败：

1. 新旧制度并存时，检索结果混入过期版本。
2. 文档表格和例外条款被切碎，模型只看到局部句子。
3. 没有足够证据时，模型仍然生成语气确定的答案。

项目目标不是“让模型更聪明”，而是提高客服在规定流程内完成一次问答任务的成功率，同时保持引用可核对、响应时间和人工转接量在可接受范围内。

### 3.2.2 角色：谁承担了哪一段

在教学案例中，数据团队负责文档授权、解析和版本清单，平台团队负责索引和推理服务，产品团队负责客服流程与灰度，安全团队负责权限和审计。项目叙事者负责：

1. 建立错误分类，确认主要失败来自哪里。
2. 设计 parent-child chunk 和混合检索实验。
3. 负责引用支持率和任务样本评估。
4. 与平台团队协作控制 reranker 延迟。
5. 把线上失败样本整理为回归集。

叙事者没有独立负责文档采集、底层向量数据库或全部模型训练。后面所有“我做了”的句子都遵守这个边界。

### 3.2.3 基线：先知道旧系统是什么

基线是比较的参照。案例基线固定为旧版本生产链路：固定 chunk、单路向量检索、top-k 直接拼接、通用模型生成、没有 claim 级引用评估。基线的模型版本、索引版本、提示模板和采样配置也记录下来。

没有基线就没有“提升”。如果基线在项目中途发生变化，必须把它作为新的实验条件记录，而不能把两个版本的结果直接放在一张表里比较。

### 3.2.4 目标：把“好用”拆成可测量的任务

“回答更好”过于宽泛。案例将一次客服问答拆成三个层次：

- 检索层：相关证据是否进入候选集合。
- 回答层：答案是否正确、完整、符合流程。
- 任务层：客服是否能据此完成下一步操作，是否需要人工转接。

对应的指标包括召回率、引用支持率、答案正确率、任务完成率、p95 延迟和单位任务成本。它们不能相互替代。检索召回提高而任务完成下降，可能说明上下文太长或证据冲突；回答质量提高而 p95 恶化，可能不适合所有流量。

## 3.3 背景：用最少信息建立必要上下文

### 3.3.1 背景不是公司介绍

项目背景只需要解释技术问题为什么存在。一个合格的背景通常包含：

1. 谁在什么任务中使用系统。
2. 原系统怎样工作。
3. 失败造成什么损失。
4. 项目受到哪些约束。
5. 成功意味着什么。

案例的背景可以压缩成：

~~~text
项目面向企业客服制度问答。旧系统采用单路向量检索和通用模型生成，面对新旧制度并存、表格条款和证据不足的问题时容易给出不受支持的答案。项目要求在不扩大模型规模的情况下，提高任务完成率和引用支持率，同时控制 p95 延迟和权限风险。我主要负责错误归因、检索实验和评估回归。
~~~

这段话没有列出所有组件，却建立了足够的共同上下文。

### 3.3.2 研究项目的背景写法

研究项目没有业务用户时，也要说明问题为什么值得研究。可以从已有方法的失败、未解释现象、资源限制或可推广性出发：

~~~text
已有长上下文方法在总分上表现接近，但对证据位于文档中部的任务变化不清楚。项目目标是在固定模型和上下文预算下，区分位置偏置、检索质量和推理能力对结果的影响。我负责构造分位置测试集、实现对照实验并分析负结果。
~~~

“前沿”“重要”“SOTA”都不能代替这个解释。问题的价值要通过任务和缺口体现。

### 3.3.3 工程项目的背景写法

工程项目的背景要交代服务对象、负载和失效代价：

~~~text
流式推理服务在短请求和长请求混合时平均吞吐正常，但 p99 首 token 延迟持续超标。初步日志无法区分排队、prefill 和 decode 的贡献。项目目标是在质量回归不恶化的情况下定位主要瓶颈，并通过调度和容量配置改善尾延迟。我负责请求分布分析、压测协议和批处理策略实验。
~~~

这样听者知道你是在解决服务问题，而不是“使用某个框架部署模型”。

## 3.4 问题：把现象变成可处理的命题

### 3.4.1 先描述现象，再给解释

项目讲述中最危险的跳跃，是把第一种猜测当成问题本身。案例最初看到“回答错误”，团队可能立刻认为模型知识不足；但错误也可能来自召回、版本、权限、上下文冲突、模板或评估。

更稳妥的顺序是：

~~~text
观察：错误率在新制度问题上升高。
分解：错误包含召回缺失、过期证据、冲突合并、生成编造和格式失败。
假设：不同错误由不同链路负责，单纯微调不能覆盖全部原因。
实验：按错误类型抽样，分别改变检索和生成条件。
结论：先修复版本过滤和证据组织，再讨论模型行为训练。
~~~

这个顺序让“问题归因”成为项目能力，而不是事后编出的解释。

### 3.4.2 用错误分类建立共同语言

错误分类不需要一开始就完美，但要能指导下一步动作。案例可以使用：

| 错误类别 | 可观察信号 | 可能责任层 | 首个验证动作 |
| --- | --- | --- | --- |
| 召回缺失 | 相关文档不在 top-k | 解析、索引、检索 | 在全量候选中查找证据 |
| 版本错误 | 旧制度分数更高 | 时间字段、过滤和索引 | 固定版本后重跑 |
| 证据冲突 | 上下文内有互相矛盾条款 | chunk、排序、选择 | 标记冲突并改变证据选择 |
| 生成不支持 | 证据存在但答案添加事实 | 模型、提示、引用约束 | 做证据支持判定 |
| 流程错误 | 答案正确但没有下一步动作 | 产品协议、工具或 UX | 定义任务完成标准 |
| 权限错误 | 用户看到无权文档 | ACL、缓存、索引 | 用租户和角色重放 |

每类错误都应能连接到数据、实验或系统动作。若一个类别只是“模型不行”，它还没有足够可操作性。

### 3.4.3 一个好的问题包含成功和失败定义

“降低幻觉”仍然不够具体。需要说明什么算幻觉、哪些例外排除、谁来判断。比如：

~~~text
当答案中的可核验 claim 无法由当前用户有权访问的证据支持，且答案没有明确标注不确定性时，记为不受支持生成；引用了过期版本也单独记录为版本错误，不与一般幻觉合并。
~~~

定义越清楚，评估和项目叙事越不容易在结果阶段临时改口。

## 3.5 难点：展示你如何分配注意力

### 3.5.1 难点不是组件清单

“数据、模型、系统都很复杂”没有信息量。真正的难点是多个目标相互牵制，或者观察信号不足以直接定位原因。

大模型项目常见的结构性难点包括：

- 质量和成本：更大的 reranker 或更长上下文可能提高证据质量，却增加延迟。
- 安全和帮助性：更严格的拒答可能降低高风险输出，却误伤正常问题。
- 训练和数据：扩大数据可能提高覆盖，却引入重复、偏置或污染。
- 评估和真实价值：固定 benchmark 提升，线上任务可能不变。
- 可靠性和自动化：工具重试可能提高成功率，却重复执行副作用。
- 研究和规模：方法在小模型上有效，不一定能在更大训练中保留收益。

讲难点时，重点不是说“事情很难”，而是说明你选择先解决哪一个冲突，为什么。

### 3.5.2 用成本和影响排序

可以用一个简化的优先级模型帮助整理：

~~~math
Priority_i = \frac{Impact_i \cdot Confidence_i}{Cost_i + Risk_i}
~~~

Impact_i 表示修复第 i 类问题可能带来的影响，Confidence_i 表示当前证据支持该判断的程度，Cost_i 是实现和运行成本，Risk_i 是可能带来的副作用。这个式子不是项目管理标准，也不应当伪装成精确打分；它提醒我们，优先级不能只由技术兴趣决定。

案例中，版本过滤的实现成本较低、影响范围明确，因此先于训练更大的模型；reranker 可能提升召回，但延迟风险更高，所以先用小样本和压测验证；更复杂的 Agent 规划不是当前问题的直接解法，因此暂不引入。

### 3.5.3 约束必须进入叙事

没有约束，方案选择无法判断。至少应说明：

1. 允许的模型和硬件。
2. 数据和隐私限制。
3. 延迟、吞吐或成本目标。
4. 时间和团队边界。
5. 不能接受的失败类型。

“我们选择了 reranker”只有在知道延迟预算、候选规模、质量目标和替代方案时才有意义。

## 3.6 方法：讲决策链，不讲工具栈

### 3.6.1 方案叙述的五个问题

每一个关键技术选择都应该回答：

1. 当时有哪些可行方案？
2. 选择标准是什么？
3. 当前方案利用了什么假设？
4. 可能引入什么新风险？
5. 用什么实验或监控验证？

例如，案例选择 parent-child chunk，而不是简单缩短 chunk：

~~~text
短 chunk 有利于精确召回，但表格和例外条款容易失去上下文；大 chunk 保留语义，却增加无关内容和延迟。我们让 child chunk 负责检索，parent 文档片段负责提供上下文，并在引用时保留原始页码和版本。实验同时记录召回、引用支持、上下文 token 和 p95，避免只看单一质量指标。
~~~

这里的重点不在术语本身，而在方案、假设、代价和验证是连着的。

### 3.6.2 训练方法的决策链

如果项目包含 SFT、DPO 或其他后训练方法，可以这样解释：

~~~text
基础模型首先在任务格式和领域表达上不稳定，所以先用高质量 SFT 示例固定输入输出协议。SFT 后，模型在证据不足时仍然倾向于自信作答，于是构造包含证据支持和适当拒答的偏好对进行 DPO。没有直接使用 RLHF，是因为当时没有足够稳定的 reward model 和在线反馈，先用可审计的偏好数据验证行为方向更符合资源约束。
~~~

这段叙述不宣称 DPO 普遍优于 RLHF，只说明在该项目的目标、数据和资源条件下为何这样选择。

### 3.6.3 推理优化的决策链

~~~text
压测显示短输入长输出和长输入短输出混在同一批次时，排队和 prefill 的尾部相互干扰。我们先按工作量分桶并调整 continuous batching，而不是直接量化。量化实验确实降低显存，但某类代码任务出现回归，所以最终只在质量回归通过且风险较低的路由上启用，并保留原精度回退。
~~~

这里展示了瓶颈定位、优化顺序和回退条件。只说“使用量化降低延迟”无法说明这些判断。

### 3.6.4 Agent 方案的决策链

Agent 项目尤其容易从“接入工具”跳到“任务成功”。应说明状态、权限和副作用：

~~~text
我们没有让模型直接调用写入工具，而是先将任务拆成读取、校验、预览和提交四种动作。读取可以自动执行，提交需要带幂等键和用户确认；工具返回 unknown 时不自动重试，避免重复副作用。评估使用完整任务轨迹，而不是只统计单步函数调用正确率。
~~~

它把安全和可靠性写进了方法，而不是在最后补一句“注意安全”。

## 3.7 实验：把判断变成可比较的证据

### 3.7.1 实验不是结果出现前的仪式

实验的作用是减少不确定性。一个项目实验至少要让听者知道：

1. 比较的对象是什么。
2. 哪些变量保持不变。
3. 结果用什么指标表示。
4. 样本从哪里来。
5. 结果是否可能被污染、偏置或偶然波动解释。

没有这些信息，“我们试了一个方案，效果变好”只是叙述，不是证据。

### 3.7.2 基线、对照和消融

基线回答“和什么比”，对照回答“改变了什么”，消融回答“哪一部分贡献了结果”。

案例可以组织成如下实验矩阵：

| 版本 | 检索 | 证据上下文 | 生成约束 | 目的 |
| --- | --- | --- | --- | --- |
| A | 旧向量检索 | child chunk | 原提示 | 基线 |
| B | 混合检索 | child chunk | 原提示 | 测检索变化 |
| C | 混合检索 | parent-child | 原提示 | 测上下文变化 |
| D | 混合检索 | parent-child | 引用和拒答约束 | 测生成协议 |
| E | 混合检索 | parent-child | 约束加 reranker | 测质量与延迟取舍 |

如果只比较 A 和 E，无法知道收益来自检索、上下文、提示还是 reranker。不是所有项目都能做完整矩阵，但要说明哪些变量无法隔离。

### 3.7.3 数据切分必须能抵抗自我欺骗

评估集最好包含固定 holdout、真实或仿真样本、长尾样本和回归样本。训练、调参和最终报告不能反复使用同一批样本，否则结果会越来越像模板记忆。

对于时间敏感的制度问答，还需要按版本或时间切分。旧制度和新制度混在随机切分中，可能让模型或检索系统看到未来信息。

对于企业数据，不能为了说明方法而泄露原文。可以使用脱敏样本或合成数据，但要明确结果只证明管线行为，不等于真实数据上的性能。

### 3.7.4 自动评估、人评和 LLM judge

自动指标便宜、可重复，但不一定覆盖正确性和安全性；人评能处理复杂质量，却需要协议、一致性和成本控制；LLM judge 扩展快，但可能受到长度、格式、模型偏好和提示的影响。

讲评估时，至少说明三者的职责：

~~~text
自动指标负责格式、引用存在和简单任务检查；人工抽样负责正确性、完整性和是否支持结论；LLM judge 只用于扩大筛查，不单独作为上线依据，并通过一批人工标注样本检查方向一致性。
~~~

不要声称 judge “理解了真实质量”，除非有针对任务的校准证据。

### 3.7.5 结果稳定性和不确定性

两个版本的平均分差异很小，可能只是抽样波动。简历和项目叙事不一定都要给出完整统计检验，但至少要知道样本量、重复运行、置信区间或分桶变化。

对于配对样本，最简单的变化量是：

~~~math
\Delta_i = m_{new,i} - m_{base,i}
~~~

总体平均变化为：

~~~math
\bar{\Delta} = \frac{1}{n}\sum_{i=1}^{n}\Delta_i
~~~

i 表示同一任务或样本，n 是配对样本数。配对比较能减少样本难度差异造成的干扰，但不能自动消除评估协议偏差。项目叙事中应说明这些量是教学计算、内部统计还是正式实验结果。

### 3.7.6 质量、延迟和成本一起报告

系统方案不应只报告一个最好看的指标。可以把结果组织成三张账：

~~~math
Quality = f(correctness, support, safety, task_{success})
~~~

~~~math
Latency = L_{queue} + L_{prefill} + L_{decode} + L_{network} + L_{postprocess}
~~~

~~~math
Cost_{task} = \frac{C_{model} + C_{retrieval} + C_{tool} + C_{human}}{N_{success}}
~~~

第一式表示质量由多个目标共同组成，第二式分解端到端延迟，第三式把资源和失败后的成功任务数联系起来。它们是解释账本，不是某个项目必须使用的唯一公式。

## 3.8 结果：把变化、代价和边界放在一起

### 3.8.1 先说基线，再说新结果

“效果提升 10%”缺少基线。更好的表达是：

~~~text
在固定领域 holdout 上，引用支持率从 62% 提升至 81%，任务完成率从 68% 提升至 76%；p95 延迟从 2.4 秒升至 3.1 秒，因此没有把新链路直接应用到所有请求，而是先用于长尾和高风险查询。
~~~

这段话同时交代了指标、方向和代价。若数字来自教学案例，应明确标记；真实项目必须使用真实口径。

### 3.8.2 相对变化与百分点

设基线指标为 m_base，新指标为 m_new。百分点变化是：

~~~math
\Delta_{pp} = 100 \times (m_{new} - m_{base})
~~~

相对变化是：

~~~math
\Delta_{rel} = \frac{m_{new} - m_{base}}{m_{base}}
~~~

从 0.70 到 0.80 是 10 个百分点、约 14.3% 的相对提升。错误率从 0.20 到 0.10 可以说下降 10 个百分点，也可以说相对下降 50%。面试表达中必须标明是哪一种。

### 3.8.3 不要把同期变化说成因果

如果版本上线后用户满意度上升，可能还有流量、产品流程、客服培训和季节性变化。没有 A/B 或其他控制设计时，可以说“上线后观察到”，不要直接说“该改动导致”。

如果确实有实验，应说明分桶、持续时间、样本排除和主要指标。因果表述越强，所需证据越多。

### 3.8.4 负结果应当进入故事

一个方案失败并不自动降低项目价值。负结果可以说明：

1. 原来的假设被什么证据否定。
2. 哪些解释被排除。
3. 修复改变了哪个环节。
4. 后续工作因此节省了什么成本。

例如，扩大 SFT 数据后幻觉没有下降，错误分析发现问题主要是外部知识缺失；这个结果帮助团队把重点转向检索和引用，而不是继续增加训练数据。失败带来了信息，项目叙事应该保留这份信息。

## 3.9 失败复盘：从“哪里坏了”走向“怎样避免再坏”

### 3.9.1 失败案例的六个阶段

一个可学习的失败案例通常包含：

1. 目标：当时希望改变什么。
2. 假设：为什么认为某种方案会有效。
3. 触发：什么结果表明假设可能错误。
4. 证据：通过哪些日志、样本或实验定位原因。
5. 修复：改了什么，为什么足以覆盖原因。
6. 后续：如何回归，哪些风险仍未关闭。

这比“我们后来修好了”更有技术含量，因为它展示了判断更新的过程。

### 3.9.2 一个 RAG 失败案例

~~~text
目标是降低企业问答中的不受支持生成。我们最初假设主要原因是模型缺少领域知识，因此增加了 SFT 问答样本。固定集上的格式正确率提高，但不受支持生成没有明显下降，部分答案语气变得更确定。

我们按错误类型重新抽样，发现大量问题的相关证据其实没有进入上下文，另有一部分是旧版本和新版本同时被召回。于是先修复版本过滤和 parent-child 上下文，再加入引用支持和证据不足时的拒答约束。修复后，检索召回和引用支持均改善，但 p95 延迟上升，因此 reranker 只在高风险查询启用。

这个结果不能证明 SFT 没有价值，它只说明在该数据和任务中，生成训练不是首个瓶颈。
~~~

### 3.9.3 一个推理失败案例

~~~text
目标是降低流式服务 p99 首 token 延迟。我们先提高 batch 上限，平均吞吐上升，但长输入请求排队更久，p99 反而恶化。进一步按输入 token、输出 token 和请求到达时间分析，发现 prefill 负载和 decode 负载相互争抢。

后续把请求按工作量分桶，并限制长请求在高峰时的并发；吞吐略有下降，但 p99 回到目标范围。这个方案的代价是低峰期 GPU 利用率不再最大，因此根据流量切换配置，而不是永久使用更保守的批处理。
~~~

### 3.9.4 一个 Agent 失败案例

~~~text
报销 Agent 在工具超时后自动重试提交动作，导致同一报销单出现重复草稿。错误不在模型是否会选择工具，而在系统把 unknown 当成 failed 处理，没有确认第一次调用是否已经产生副作用。

修复包括为提交请求增加幂等键，记录工具调用状态，将 unknown 交给查询或人工确认路径，并把重复副作用加入回归集。修复后单步成功率没有明显变化，但端到端任务失败和重复提交显著下降。这个案例说明工具调用成功率不能替代任务可靠性。
~~~

### 3.9.5 复盘要区分根因、诱因和放大器

根因是没有它就不会发生的系统缺陷，诱因是触发问题的条件，放大器是让影响扩大的因素。例如缓存越权事故中，权限未进入缓存键可能是根因，高峰流量可能是诱因，缺少租户分桶监控可能是放大器。

复盘时不要把责任归结为“某个人粗心”。更有用的是修复接口、默认值、测试、监控和发布流程，让同类错误更难再次发生。NIST AI RMF 强调治理、测量和管理 AI 风险应贯穿系统生命周期，这种思路同样适用于项目复盘。

## 3.10 反思：说明下一步，但不要假装没有边界

### 3.10.1 有价值的反思不是“继续优化”

“下一步继续优化效果”没有信息量。好的反思要指出一个具体边界：

- 评估集没有覆盖哪些语言、长度或风险等级。
- 当前方法依赖什么数据版本或硬件。
- 离线指标与线上任务之间还缺哪一层证据。
- 质量提升付出了什么成本。
- 如果规模扩大十倍，哪一个假设最先失效。

例如：

~~~text
当前结论主要来自中短文档和固定知识库，尚未覆盖制度频繁更新、跨租户权限和多轮追问。下一步优先补时间切分和权限分桶，而不是继续增加通用 SFT 数据，因为现有证据还不能说明问题来自模型容量。
~~~

### 3.10.2 把下一步写成实验问题

下一步最好能改写成一个实验：

~~~text
如果把 reranker 只用于 top-50 候选，引用支持率是否保持，而 p95 延迟能否回到目标？
~~~

这个问题包含变量、目标和约束。它比“继续研究 reranker”更容易执行，也更能展示研究和工程的连续性。

### 3.10.3 反思不能篡改当时的决策

站在结果之后，很多选择看起来显而易见。但讲述时要说明当时掌握的证据和资源。不要把事后知道的根因写成“我们一开始就知道”。诚实地复原不确定性，能让听者判断你的决策是否在当时合理。

## 3.11 时间尺度：同一个项目讲出不同深度

### 3.11.1 一分钟版本：只建立坐标

一分钟不是把七个章节各念一句，而是让听者知道对象、目标、角色、主要动作和最重要结果：

~~~text
我做过一个企业制度问答改进项目，目标是降低无证据回答并提高客服任务完成率。我主要负责错误分类、混合检索、证据组织和回归评估。我们先发现主要问题来自版本过滤和召回，而不是单纯模型知识不足；修复后固定集的引用支持率和任务完成率提高，但 p95 延迟增加，所以最终只在长尾和高风险请求上启用更重的链路。
~~~

这个版本不追求讲完，而是给出可展开的入口。

### 3.11.2 三分钟版本：交代因果链

三分钟应包含背景、基线、主要失败、关键选择、评估和代价。建议顺序是：

1. 一句话说明任务。
2. 说明原系统和最主要失败。
3. 说明错误分析怎样改变初始假设。
4. 说明一个或两个关键决策。
5. 给出基线、新结果和代价。
6. 说出当前边界。

三分钟不是固定朗读稿。它的作用是先让听者拥有完整地图，再根据对方关心的方向进入数据、模型或系统细节。

### 3.11.3 十分钟版本：准备证据而不是准备更长的稿子

十分钟讨论通常会进入细节，但不意味着把所有实现逐行讲完。应准备以下材料：

- 数据来源、版本和质量控制。
- 模型、训练或检索配置。
- 基线和替代方案。
- 指标定义、样本量和误差分析。
- 失败实验和修复依据。
- 性能、成本、安全和权限边界。
- 个人贡献与团队协作。
- 如果重做，优先改变什么。

真正的准备不是背十分钟的文字，而是让每个关键判断都能回到事实卡、实验表或日志。

## 3.12 不同类型项目的讲述重点

### 3.12.1 训练项目：把规模写成状态变化

训练项目不要只说模型规模和卡数。听者更关心训练是否稳定、数据是否可信、资源是否有效，以及你如何处理异常。

建议讲清：

1. 训练目标、数据版本和 tokenizer。
2. 模型、序列长度、batch 和有效 token。
3. 并行策略、通信和显存约束。
4. loss、梯度、吞吐和硬件监控。
5. 一次具体故障及其排查。
6. checkpoint 和恢复是否保持实验可比。
7. 训练结果怎样通过能力和回归评估。

一个训练故障可以这样展开：

~~~text
长周期 run 在第 18 小时出现 loss spike。我们先确认异常是否只发生在一个 rank，再检查对应数据 shard、梯度范数、混合精度溢出和读取延迟。最后定位到一个异常长样本叠加 loss scaling 溢出。修复不是简单跳过整个 run，而是隔离样本、调整数值保护并从最近可验证 checkpoint 恢复，再用相同数据游标和配置重跑确认结果可比。
~~~

如果你只负责监控，不要把完整根因分析写成个人工作；可以说明你负责的信号和协作部分。

### 3.12.2 Post-training 项目：把行为变化拆开

Post-training 项目要讲数据、目标和行为，而不只是训练 loss。

需要回答：

1. base model 在什么任务上失败。
2. SFT、偏好或安全数据如何表达目标。
3. chosen 和 rejected 的标准是什么。
4. 训练后哪些行为改善，哪些行为退化。
5. 是否检查长度偏置、过度拒答、奖励投机和事实性。
6. 结果是否跨语言、任务和风险等级稳定。

如果 DPO 后 win rate 上升但正常问题误拒增加，不能只报告前一个指标。项目深度就在于解释这个冲突，以及你怎样重新分桶数据或改变评估。

### 3.12.3 RAG 项目：从答案退回证据

RAG 项目的中心不是“用了哪个向量数据库”，而是证据是否从来源可靠地到达答案。

应分别讲：

- 文档授权、版本和解析。
- chunk、embedding、混合检索和 rerank。
- 权限过滤在检索前还是检索后。
- 上下文选择、冲突和过期处理。
- claim 级引用和证据不足时的行为。
- 召回、引用支持、答案质量、延迟和成本。

一个好的叙述能解释：检索召回高但答案仍错时，是上下文冲突、模型忽略证据还是引用协议不完整；答案流畅但没有来源时，为什么不能把语言质量当作事实性。

### 3.12.4 推理部署项目：从请求分布开始

推理项目要先说明请求工作量：输入和输出 token 分布、并发、流式或非流式、短请求和长请求比例。然后再讲 prefill、decode、KV Cache、batching、量化、并行和路由。

性能结果至少包括 p50、p95 或 p99、吞吐、显存和质量回归。没有请求分布的“延迟降低 30%”无法比较；没有质量回归的吞吐提升也可能只是输出变短。

### 3.12.5 评估项目：证明测量本身可靠

评估项目需要把构念、样本、协议、评分器和决策连接起来。讲述时应说明：

1. 想测的行为是什么。
2. 样本如何覆盖主要和长尾场景。
3. 自动指标和人工 rubric 如何分工。
4. LLM judge 怎样校准。
5. 如何检查污染、提示过拟合和切片退化。
6. 结果怎样改变训练、数据或产品决策。

“支持十个 benchmark”只是覆盖范围，不是评估质量。若你发现某个指标和用户反馈不一致，并通过错误分析推动新回归集，这通常比再接入一个榜单更值得讲。

### 3.12.6 Agent 项目：以完整任务而非单步成功为单位

Agent 项目要讲任务状态、工具契约、权限、幂等、重试、人工接管和最终成功。单步函数调用准确率不等于端到端完成率。

一个任务成功的教学化近似是：

~~~math
P_{task} \approx P_{plan} \times P_{tool} \times P_{argument} \times P_{execution} \times P_{verify}
~~~

这些概率并不真正独立，但它们提醒我们：长任务中的每个环节都会累积失败。项目叙事应使用轨迹和失败分类说明系统如何恢复，而不是只展示一次成功 demo。

### 3.12.7 多模态项目：说明证据来自哪一种模态

多模态项目要区分表示、融合和任务。图像问答可能失败在 OCR、空间关系、视觉编码或语言生成；视频任务还要处理时间采样和动作区间；语音任务要区分识别、端点检测、延迟和语义回答。

讲述时应说明数据来源、标注粒度、分辨率或帧率预算、模态缺失、评估和隐私边界。不要把语言模型回答流畅写成视觉证据正确。

### 3.12.8 研究项目：把想法变成可被反驳的实验

研究项目最重要的是问题、假设和对照。不要只说“提出新方法并取得 SOTA”，而要说明：

1. 原方法的具体缺口。
2. 新方法为什么可能修复它。
3. 哪些变量被控制。
4. 哪些消融能区分不同解释。
5. 失败结果说明什么。
6. 结论能推广到哪里。

没有负结果的研究叙述不一定更强。一个能够解释“方法只在小样本和特定长度下有效”的项目，往往比没有边界的 SOTA 口号更可信。

## 3.13 追问是对因果链的压力测试

### 3.13.1 追问为什么会出现

技术对话中的追问不是一组固定题库，而是在检查前面叙述的连接是否成立。你说“召回提高”，对方自然会问样本和分母；你说“延迟降低”，对方会问请求分布和硬件；你说“我主导训练”，对方会问具体代码和故障；你说“任务成功率提升”，对方会问成功定义和失败轨迹。

把追问理解成压力测试，比背问题更有效。

### 3.13.2 六个最常见的压力点

1. 责任：这项工作中你具体写了什么、决定了什么？
2. 基线：没有你的改动，系统是什么状态？
3. 归因：为什么相信结果来自这个改动？
4. 口径：指标的分母、样本和协议是什么？
5. 代价：质量、延迟、成本或安全是否退化？
6. 边界：换数据、规模、语言或流量后还成立吗？

每个压力点都应在项目事实卡中有材料。答不上来时，不要用更多术语掩盖，可以直接说证据还不足。

### 3.13.3 面对未知问题的表达

如果你不知道一个细节，可以分三层回答：

~~~text
已知事实：这个版本在固定 holdout 上的引用支持率提高了。
合理推测：可能与 parent-child 上下文减少了断句有关，但我没有做独立消融。
下一步验证：我会固定检索结果，只替换上下文组织方式，比较 claim 级支持率和 token 成本。
~~~

这种表达把事实、假设和实验分开，比编造一个确定答案更可靠。

### 3.13.4 讨论替代方案

被问到“为什么不用另一个方案”时，不要只说“当时没考虑”。说明它的优点、当前不适用原因和什么条件下会重新考虑：

~~~text
全参微调可能提供更大的行为改变空间，但当时数据量和算力不足，且需要频繁回归，所以先用 LoRA 做方向验证。如果后续有更多领域数据并且需要改变底层知识，才会重新评估全参或继续预训练。
~~~

承认替代方案的适用条件，说明你理解的是决策边界，而不是对某个工具盲目忠诚。

## 3.14 协作：把“我做的”放回团队系统

### 3.14.1 讲清接口，不贬低他人

大模型项目通常跨越数据、训练、评估、平台、产品、安全和合规。项目叙事不应把团队成果全部归自己，也不应把协作者描述成阻碍。

可以说明接口：

~~~text
数据团队提供了版本化文档和权限字段，我负责把这些字段接入检索评估；平台团队维护索引和推理服务，我负责定义压测协议、错误样本和质量回归；产品团队提供灰度任务样本，我根据结果调整评估分桶。
~~~

这段话同时体现了个人责任、协作关系和系统边界。

### 3.14.2 技术分歧要落到证据

“我说服了团队使用某方案”不是技术论证。更好的叙述是：分歧是什么，双方假设是什么，怎样设计小实验，结果如何改变选择。

如果实验没有完全解决争议，也可以说明剩余不确定性和最终采用的风险控制。团队协作不是把所有人说成同意你，而是让决策有可追溯依据。

### 3.14.3 交接也是项目结果

如果你沉淀了配置、数据协议、评估脚本、回滚说明或故障手册，使其他人能够复现和维护，这属于真实影响。它不一定体现为模型分数，却能减少组织对个人记忆的依赖。

The Turing Way 对可复现研究的讨论强调环境、数据、代码、记录和过程的可追溯性。把这些内容带回项目叙事，可以说明你的结果不是只存在于一次口头演示中。

## 3.15 避免过度包装：让表达强度匹配证据

### 3.15.1 七种常见的事实漂移

1. 把参与写成主导。
2. 把个人实验写成生产系统。
3. 把一次结果写成长期趋势。
4. 把相关变化写成因果。
5. 把团队指标写成个人指标。
6. 把论文阅读写成复现。
7. 把公开方法的能力宣称成自己做过。

这些问题短期内可能让故事听起来更强，长期却会在细节追问时失去可信度。

### 3.15.2 建立表达强度表

| 事实强度 | 合适表达 | 不应使用的表达 |
| --- | --- | --- |
| 读过论文 | 分析了、理解了公开方法 | 提出了、实现了 |
| 跑通公开代码 | 复现了、在公开数据上验证了 | 在生产中落地 |
| 负责一个模块 | 负责、实现、维护该模块 | 独立完成整个系统 |
| 参与线上项目 | 参与、协作、负责某链路 | 主导全部上线 |
| 有灰度结果 | 灰度期间观察到 | 证明普遍提升 |
| 有严格对照 | 在该协议下验证 | 对所有场景有效 |

表达的保守程度应由证据决定，不由自信程度决定。

### 3.15.3 例子、合成数据和真实项目要分开

本章的澄明企业助手使用了教学数字，这是为了演示叙事结构。讲自己的项目时，必须标明哪些是：

- 真实生产数据。
- 团队内部离线实验。
- 公开数据复现。
- 个人合成实验。
- 事后推演而非实际发生。

这条边界也适用于代码和截图。教学代码可以帮助解释机制，但不能被写成生产系统证据。

## 3.16 项目准备工作簿

### 3.16.1 项目一页摘要

先填写一页，不追求漂亮：

| 问题 | 内容 |
| --- | --- |
| 项目一句话 | 面向谁，解决什么 |
| 原始基线 | 没有你的改动时怎样 |
| 主要失败 | 哪类错误最重要 |
| 我的责任 | 我直接做了什么 |
| 关键假设 | 为什么认为方案可能有效 |
| 关键干预 | 改了什么 |
| 评估协议 | 样本、指标、版本和分桶 |
| 主要结果 | 提升、退化和未知 |
| 主要取舍 | 为了什么牺牲什么 |
| 当前边界 | 哪些场景不能外推 |

如果一页摘要无法填出基线、个人责任和评估协议，项目还没有准备好进入深度叙述。

## 3.17 学习练习

### 练习一：把工具句改成问题句

把“我使用了 LoRA、RAG 和 vLLM”改写成三句话：原系统哪里失败，为什么选择这些方法，如何验证每个方法的作用。三句话必须包含至少一个约束和一个负面结果。

### 练习二：重建基线

选择一个项目，写出没有你的改动时系统的完整路径，包括数据、模型、检索、服务和评估。若无法写出，说明你还没有真正理解基线。

### 练习三：做一次反事实比较

写出“如果不采用当前方案，最可能使用的替代方案是什么”，再说明它会改善什么、牺牲什么，以及什么证据会让你改变选择。

### 练习四：为一个数字补齐分母

选择一个最喜欢的结果，写出指标方向、基线、分母、样本、时间、协议、切片和代价。如果不能补齐，降低表达强度。

### 练习五：录制三个时间版本

分别录制一分钟、三分钟和十分钟版本。回放时只检查三件事：主线是否清楚，事实是否一致，是否把假设说成事实。不要先纠结语速和修辞。

### 练习六：用陌生读者测试

让没有参与项目的人听三分钟版本，请他复述：项目解决什么问题，你负责什么，结果如何，最大边界是什么。如果他只能复述工具名词，说明叙事还没有把因果链讲出来。

## 3.19 小结：项目叙事的目标是让判断可追溯

好的项目叙事不是把技术名词排列得更密，而是让听者能够沿着一条事实链理解：项目面对什么场景，原系统怎样失败，你提出了什么解释，做了什么干预，如何比较，结果带来什么变化，代价和边界是什么。

初学者应先学会把工具放回问题，把结果放回基线，把数字放回分母。专家则要进一步说明机制、归因、反事实、协作接口和残余风险。不同类型的项目有不同重点，但都需要对象、责任、证据和边界。

简历中的项目是一张地图，面试中的项目叙事是一段可复核的旅程。前者要简洁，后者要诚实而有深度。下一章进入 Coding Interview，开始讨论如何在现场实现、调试和解释代码，把项目中的工程判断落到可运行的程序上。
