# 第八章：从模型偏好到系统安全：对齐、风险与发布治理

一个模型能够流畅回答问题，只说明它学会了某种语言行为。它是否诚实，是否知道何时不确定，是否会拒绝危险请求，是否会在工具权限边界内行动，是否会在长期交互中保持这些行为，不能由流畅度直接推出。

安全与对齐研究处理的是“模型会什么”和“系统允许它做什么”之间的差距。模型可能在普通问答中表现良好，却在多轮对话中逐步接受不该接受的目标；可能会拒绝直接的危险请求，却把同一内容包装成代码、翻译或角色扮演后输出；可能不会主动泄露资料，却在检索增强生成（retrieval-augmented generation，RAG）、浏览器或企业工具返回的文本中执行不可信指令；也可能为了避免风险而拒绝大量本来可以安全回答的问题。

因此，安全不是给模型加一句更强的系统提示词（system prompt），对齐也不是把一个偏好分数优化到更高。一个可交付的系统需要同时处理：

~~~text
人类目标与使用场景
    -> 风险分类与威胁模型
    -> 数据、监督和后训练
    -> 行为评估、红队与回归
    -> 权限、工具和运行时隔离
    -> 发布说明、灰度、监控与事故响应
~~~

初学者可以先记住三个问题。模型被要求做什么，模型实际上学到了什么，系统最终允许它造成什么影响，这三件事不是同一件事。有经验的工程师还要继续追问：风险的分母是什么，失败严重度如何分层，训练信号是否只是代理指标，评估是否覆盖真实部署条件，修复后是否会损害正常用户，外部资料与模型输出是否被正确区分，以及上线后的证据能否支持回滚和复盘。

本章讨论防御性安全、行为评估和发布治理，不提供可执行的越狱模板、危险操作步骤、隐私复原方法或绕过权限的技巧。涉及高风险能力时，只说明评估变量、证据边界和防护原则。

## 8.1 先确定安全对象：模型、应用还是系统

### 8.1.1 模型行为不是系统影响

模型输出是一段词元（token）序列，系统影响却可能包括发送邮件、修改数据库、执行代码、泄露文档、给出医疗建议或影响用户决策。两者之间至少隔着几层：

1. 模型层：模型产生什么文本、结构化参数或工具意图。
2. 策略层：服务如何判断请求、输出和动作是否符合规则。
3. 执行层：工具是否验证身份、资源、参数和业务状态。
4. 运营层：是否有人工接管、审计、申诉、回滚和事故响应。

一个模型可能在单独文本评估中拒绝危险请求，但接入一个权限过宽的工具后仍然产生高风险影响。反过来，一个模型偶尔会生成不合适的文本，若系统把它放在只读、低影响、有人审核的环境中，实际风险可能小于同一模型被授予自动付款权限的情况。

安全结论必须说明对象和边界。说“模型是安全的”通常过于宽泛；更可核验的说法是：“在给定模型检查点（checkpoint）、模板、工具集合、权限策略、输入分布和评估协议下，观察到某类失败率为某值。”这仍然不是永远安全的证明，而是有条件的证据。

### 8.1.2 四种常被混用的目标

安全讨论中至少有四种目标：

- 能力限制：模型是否具备某种高风险能力。
- 行为约束：模型在请求下是否给出拒绝、澄清或安全替代。
- 系统控制：模型即使判断错误，是否仍不能越权或造成不可逆影响。
- 组织治理：团队是否能发现、处置、记录和承担已经发生的风险。

它们之间不是替代关系。行为拒绝不能代替工具权限；工具权限不能代替隐私治理；发布文档不能代替实际评估。越靠近现实影响的一层，越需要独立证据。

### 8.1.3 安全与对齐的交集

安全（safety）主要问“哪些行为或能力会造成伤害，怎样降低发生概率和影响”；对齐（alignment）主要问“模型优化的目标和行为是否与人类意图、规范和边界一致”。安全是对齐的重要组成，但对齐还包括诚实、可控、可纠正、任务意图理解和目标泛化。

一个模型可以在固定安全集上拒答良好，却在长程任务中为了完成目标而隐瞒失败；也可以没有明显有害输出，却总是迎合用户、编造证据、绕过停止条件。这些问题都属于目标和行为不一致，但不一定能被传统有害内容分类器发现。

## 8.2 把抽象价值写成可观察的行为契约

### 8.2.1 有帮助（Helpful）、诚实（Honest）、无害（Harmless）不是三个按钮

Helpful、Honest、Harmless 可以作为入门的三类目标：

- Helpful：在用户有权、问题可答且风险可控时，真正推进任务。
- Honest：不伪造事实、工具结果、引用、权限和完成状态，能表达不确定性。
- Harmless：不主动增加可预见伤害，不把高风险动作交给没有足够控制的执行链。

三者会冲突。资料不足时，编造一个完整答案看起来更 helpful，却不 honest；危险请求中提供细节可能更“响应用户”，却不 harmless；把所有敏感词都拒绝可以降低一部分 harmful compliance，却会损害正常教育、防御和求助场景。

系统不能只记录一个总分。应把目标写成行为契约，例如：

~~~text
资料充分且风险低 -> 直接回答并说明依据
资料不足但问题可澄清 -> 询问缺失条件
风险可控但细节过高 -> 降低细节并提供安全替代
高风险且动作不可逆 -> 拒绝危险部分，转人工或只提供防御性信息
工具结果未确认 -> 明确标记未知，不宣称完成
~~~

这份契约不是模型自然会遵守的法律文本。它需要通过数据、训练、评估、策略和执行器共同实现。

### 8.2.2 多目标不能只看平均值

设一个请求集合中，帮助性、诚实性和无害性分别被归一化为 H、E、S，风险成本为 R，权重为 w_H、w_E、w_S、w_R，一个教学性的总效用可以写成：

~~~math
U
=
w_H H
+
w_E E
+
w_S S
-
w_R R
~~~

这些变量不是天然可比的物理量，权重也不应被误解为普适常数。若把它用于有限评估集，还要明确各分量已经归一化到同一量纲，权重是有限的非负数，并说明 `R` 表示成本、损害还是失败概率的组合；否则不同实验之间的 `U` 没有可比性。公式的作用是提醒我们：优化一个汇总指标会隐藏分布。一个系统可能提高平均 helpfulness，却在少数高严重度样本上变差；也可能把拒答率提高后降低了某类风险，却让大量合法用户得不到帮助。

更可靠的报告方式是按风险和场景分桶，分别给出均值、尾部和严重度加权结果，再说明哪些指标是硬约束、哪些指标是优化目标。高影响小概率事件不能因为样本少就被平均掉。

### 8.2.3 从价值声明到行为测试

“诚实”可以拆成不伪造工具结果、检查引用是否支持主张（claim）、承认未知、正确描述自身能力；“可控”可以拆成遵守取消、尊重权限、拒绝越权工具、在人工接管后停止动作；“无害”可以拆成不提供危险细节、不泄露隐私、不执行不可信内容中的指令。

每个声明都要有：

1. 触发条件；
2. 允许行为；
3. 不允许行为；
4. 失败严重度；
5. 可观测事件；
6. 评估样本和分母；
7. 修复后的回归测试。

没有这些字段，安全目标就容易停留在口号层面。

## 8.3 风险分类与威胁模型

### 8.3.1 风险不是一张关键词表

一个可用的风险分类体系（taxonomy）至少要同时描述伤害类型、攻击者或错误来源、资产、路径和后果。美国国家标准与技术研究院（National Institute of Standards and Technology，NIST）的对抗性机器学习分类按系统、生命周期和攻击者条件组织术语；开放全球应用安全项目（Open Worldwide Application Security Project，OWASP）的 2026 大语言模型（large language model，LLM）指南也把模型放回应用和工具边界讨论。它们适合作为风险识别入口，不是目标系统的完整威胁模型或风险阈值。[NIST AI 100-2e2025](https://csrc.nist.gov/pubs/ai/100/2/e2025/final)；[OWASP GenAI LLM Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/)。

| 维度 | 示例 |
| --- | --- |
| 内容风险 | 有害建议、歧视、欺骗、危险细节 |
| 信息风险 | 个人身份信息（personally identifiable information，PII）、密钥、商业机密、训练数据复现 |
| 交互风险 | 越狱、多轮诱导、用户误解、不确定性隐藏 |
| 应用风险 | RAG 污染、提示注入、引用错配、过时数据 |
| 动作风险 | 越权查询、错误写入、重复副作用、不可逆操作 |
| 能力风险 | 网络安全、生物、自治、工具放大和长程规划 |
| 运营风险 | 监控缺失、回滚失败、审计不可用、人工接管失效 |

关键词可以帮助抽样，却不能定义风险。相同的词在防御教程、新闻分析、学术研究和恶意请求中意图不同；没有上下文和动作边界，单纯关键词拦截会同时漏掉攻击和误伤正常内容。

### 8.3.2 严重度和概率要分开

设风险场景 i 的发生概率为 p_i，影响规模或严重度为 I_i，暴露时间或放大因子为 a_i，一个简化的期望风险可以写成：

~~~math
R_{\mathrm{expected}}
=
\sum_i p_i I_i a_i
~~~

这里假设事件集合是有限的，`0 <= p_i <= 1`，`I_i >= 0`，`a_i >= 0`，并且各项使用同一时间窗口和同一影响量纲。若风险事件相互依赖，简单相加只是近似；若影响不能直接相加，应改用分桶、场景树或尾部风险报告。`p_i`、`I_i` 和 `a_i` 的估计都带有不确定性。这个式子不是精确预测，而是避免把“高概率小影响”和“低概率大影响”混为一谈。工具权限扩大、自动重试、批量发送和缺少人工确认都可能提高放大因子，即使模型行为本身没有变化。

除了期望风险，还要单独报告最坏已知后果、严重度最高样本和证据缺口。不能用低平均风险为一个没有任何高严重度约束的系统背书。

用一组纯教学分值说明概率和影响不能互相替代。假设两个场景的暴露时间因子都为 1：常见的小故障取 `p_1=0.02`、`I_1=5`，稀有但影响大的越权事件取 `p_2=0.001`、`I_2=80`。按上式，两者分别贡献 `0.02×5=0.10` 与 `0.001×80=0.08` 风险单位。即使第二种事件概率低二十倍，它的期望贡献仍接近第一种；如果影响分值不能合理相加，团队应分开报告场景和尾部，而不是把这些假设数当作真实风险率。

### 8.3.3 威胁模型的五个问题

每个安全系统至少要回答：

1. 谁可能发起攻击或误操作？
2. 哪些输入、文档、工具结果和模型输出不可信？
3. 哪些资源和动作需要保护？
4. 攻击或错误如何穿过模型、策略和执行层？
5. 哪一层能阻止、发现、补偿或追责？

例如，企业知识助手的外部网页属于不可信内容，合同数据库属于受保护资源，查询工具属于可审计动作，模型是可能出错的决策组件。即使网页中的注入成功影响了模型，服务端仍应通过用户身份、合同资源和动作权限阻止越权读取。

### 8.3.4 防护目标不是让模型永远判断正确

模型会犯错，输入分布会变化，攻击者会尝试新组合。因此高影响动作不应依赖模型自我判断作为唯一控制点。更可靠的系统把权限、参数范围、资源归属、幂等、审批和回滚放在模型之外。

这是一种失效容忍设计：模型判断正确时流程顺畅，模型判断错误时影响仍被限制，错误会留下可追踪证据。安全系统的价值不只是提高拒绝准确率，也是在判断失败后阻止错误扩大。

## 8.4 数据与监督微调（supervised fine-tuning，SFT）：行为从哪里开始改变

### 8.4.1 监督数据先定义边界

安全后训练通常从监督微调开始，但 SFT 的效果首先取决于样本如何表达边界。只收集“危险请求 -> 拒绝”会让模型学到表面拒绝，甚至把教育、防御、求助和研究请求一并拒绝。

更有用的样本要区分：

- 明确有害且需要拒绝危险细节；
- 意图不明且需要澄清；
- 合法防御或教育请求，可以提供低风险信息；
- 敏感但允许回答，需要控制细节和语气；
- 模型不知道，应该承认资料不足；
- 工具动作需要权限或人工确认；
- 外部内容包含指令，但只能作为不可信数据。

每条样本还应带场景、风险等级、允许的帮助范围、拒绝原因和安全替代。否则标注员可能把“看起来谨慎”当成正确答案，导致过度拒答被系统性奖励。

### 8.4.2 拒答不是唯一目标标签

一个回答可以同时有多个属性：是否违反政策、是否帮助用户推进合法目标、是否包含不支持的事实、是否泄露信息、是否触发动作。把它压成一个二元标签会丢失重要信息。

例如用户问“怎样检查自己的服务器是否有已知漏洞”，安全回答可以讨论资产盘点、补丁管理、日志和授权测试；用户问“怎样入侵一个不属于自己的服务器”，则不能提供可操作攻击细节。两者可能共享许多词，但意图、权限和可接受帮助范围不同。

标注指南应给出成对边界样本，让标注员讨论“可以帮助到什么程度”，而不是只列禁词。分歧本身也是数据质量信号，应被记录并进入仲裁，而不是悄悄投票平均。

### 8.4.3 SFT 的可见行为和不可见目标

SFT 直接让模型模仿答案，因此能快速塑造格式、语气、拒答和工具协议。但模型可能只学到表面模式：

1. 看到某个词就拒绝；
2. 用固定模板掩盖没有理解意图；
3. 把“我不能帮助”作为所有不确定问题的默认答案；
4. 在训练样本之外重新暴露原来的行为；
5. 将安全替代写成空泛的免责声明。

SFT 后要用未见过的组合评估，包括跨语言、多轮、改写、正常敏感请求、工具结果和长上下文。训练集上的拒答率不能证明边界泛化。

## 8.5 人类反馈强化学习（reinforcement learning from human feedback，RLHF）：把偏好作为代理信号

### 8.5.1 典型训练链路

InstructGPT 论文展示的一种 RLHF 流程包括监督微调、偏好数据、奖励模型和策略优化：给定输入 x，两个回答 y_w 和 y_l 分别表示标注者更偏好和较不偏好的回答。奖励模型学习让 r_phi(x, y_w) 大于 r_phi(x, y_l)，策略再尝试提高奖励，同时限制和参考策略（reference policy）的偏离。[InstructGPT 原论文](https://arxiv.org/abs/2203.02155)。这是一种代表性训练链路，不是所有偏好优化方法都必须遵循的固定流程。

一个常见的奖励模型损失可以写成：

~~~math
\mathcal{L}_{\mathrm{RM}}
=
-
\log
\sigma
\left(
r_{\phi}(x,y_w)
-
r_{\phi}(x,y_l)
\right)
~~~

r_phi 是奖励模型输出，sigma 是 logistic sigmoid，y_w 和 y_l 是偏好对。这个公式只说明偏好排序，不保证奖励具有绝对意义，也不保证人类对一个复杂回答的判断稳定。经验训练还要求偏好集合非空，且奖励值为有限数；空集合没有可计算的平均损失，不能把它报告成训练成功。如果同一个输入有多个标注者，还应说明冲突如何处理，以及是否保留了“无法判定”的样本。

带 Kullback-Leibler 散度（KL）约束的策略目标可以抽象为：

~~~math
J(\pi)
=
\mathbb{E}_{x,y\sim\pi}
\left[
r_{\phi}(x,y)
-
\beta
\log
\frac{\pi(y\mid x)}
{\pi_{\mathrm{ref}}(y\mid x)}
\right]
~~~

pi 是待优化策略，pi_ref 是 reference policy，beta 控制偏离代价。对数比值要求 reference 在被评估序列上有正概率；实现中的零概率、下溢和截断必须显式处理，不能把数值异常静默当成正常奖励。通常取有限的 `beta > 0`，并使策略与 reference 使用可比的分词器（tokenizer）、回答边界和停止规则。序列概率通常由 token 对数概率相加得到，因此回答长度、截断和归一化方式会影响奖励和 KL 的解释；实际近端策略优化（proximal policy optimization，PPO）还会使用近似 KL、优势估计和裁剪目标，本式是帮助理解目标构成的抽象形式。

### 8.5.2 KL 约束能解决什么

如果策略只追逐奖励模型分数，它可能快速偏离原有语言能力、格式习惯或安全边界。KL 项提供一种“不要离 reference 太远”的软约束，有助于减少行为漂移和部分奖励投机（reward hacking）。

但 KL 不是安全证明。reference 本身可能有问题，奖励模型可能把错误拒答、冗长、自信和风格当作高分，KL 也可能只是让策略在一个错误附近稳定。beta 太小，策略更容易过度优化代理，出现奖励投机（reward hacking）；beta 太大，训练可能几乎不改变目标行为。

### 8.5.3 RLHF 的证据边界

RLHF 可能改善人类偏好评分、指令遵循和部分安全行为，但不能由此推出：

- 所有用户都认可新的偏好；
- 所有高风险场景都被覆盖；
- 奖励高代表事实正确；
- 常见越狱（jailbreak）已经消失；
- 线上工具动作安全；
- 模型理解了人类价值而非模仿了标注风格。

评估必须把奖励模型分数、人评、专家评审、事实性、误拒、攻击鲁棒性和系统任务成功分开。特别是对模型不能直接验证的任务，奖励模型很容易偏好流畅但错误的回答。

## 8.6 直接偏好优化（direct preference optimization，DPO）：简化优化流程，不消除目标问题

### 8.6.1 从偏好对直接优化策略

DPO 使用胜选回答（chosen）与落选回答（rejected）组成的偏好对，直接优化策略相对参考策略（reference policy）的对数概率；其推导依赖偏好模型和 KL 正则化奖励目标等假设。[DPO 原论文](https://arxiv.org/abs/2305.18290)。一个常见形式为：

~~~math
\mathcal{L}_{\mathrm{DPO}}
=
-
\mathbb{E}
\left[
\log
\sigma
\left(
\beta
\left(
\log\frac{\pi_{\theta}(y_w\mid x)}
{\pi_{\mathrm{ref}}(y_w\mid x)}
-
\log\frac{\pi_{\theta}(y_l\mid x)}
{\pi_{\mathrm{ref}}(y_l\mid x)}
\right)
\right)
\right]
~~~

pi_theta 是待训练策略，pi_ref 是参考策略，y_w 是胜选回答，y_l 是落选回答，beta 控制偏好差异的强度。偏好对集合必须非空，`beta` 应为有限正数，两个策略对相关序列的概率也不能为零到使对数比值失去定义。这里的序列对数概率通常需要明确是否按 token 长度归一化，否则长回答可能获得不同的梯度权重；实现还要说明回答 token 的起止位置、padding 是否忽略，以及 reference 是否冻结。

### 8.6.2 DPO 的工程优势

DPO 不需要单独部署在线 PPO 采样轨迹（rollout）环，也不要求显式训练一个奖励模型再做策略迭代，因此数据管线和实验复现通常更简单。它适合在已有偏好对上快速比较数据质量、reference 和 beta。

但“优化流程更简单”不等于“目标更正确”。DPO 仍会忠实放大偏好数据里的错误：

1. 标注员把更长回答当作更好；
2. 标注员把机械拒绝当作更安全；
3. chosen 和 rejected 的意图不匹配；
4. 数据缺少正常敏感请求；
5. 领域知识不足导致错误答案被偏好；
6. 少数模式被重复采样，造成过拟合。

### 8.6.3 偏好数据的长度偏差

设 chosen 和 rejected 的 token 对数概率分别为 log P_w 和 log P_l，长度为 T_w 和 T_l。若使用总对数概率：

~~~math
\log P(y\mid x)
=
\sum_{t=1}^{T_y}
\log
\pi(y_t\mid x,y_{<t})
~~~

较长回答会累积更多负数项。若数据中 chosen 通常更短或 rejected 通常更长，模型可能学到长度捷径，而不是内容质量。工程上要分别检查总 log probability、长度归一化、回答长度分布和任务成功率，不能只看 DPO loss 下降。

### 8.6.4 DPO 后的安全评估

DPO 后至少要配对比较：

| 维度 | 需要观察的变化 |
| --- | --- |
| 有害遵从 | 是否减少危险细节和越权帮助 |
| 正常帮助 | 合法教育、防御、求助是否仍能推进 |
| 误拒 | 合法敏感请求（benign-sensitive）是否被更多拒绝 |
| 诚实 | 不知道时是否更愿意承认未知 |
| 格式 | JSON、工具参数、引用和停止原因 |
| 泛化 | 改写、多轮、跨语言和长上下文 |
| 系统结果 | 工具越权、重复动作和审计完整性 |

## 8.7 宪法式 AI（Constitutional AI）、AI 反馈强化学习（reinforcement learning from AI feedback，RLAIF）与可扩展监督

### 8.7.1 用原则辅助生成反馈

宪法式人工智能（Constitutional AI）的核心思路是先给出一组原则，让模型批评和修订自己的回答，再用这些比较或修订数据进行后续训练。原论文展示了批评与修订（critique/revision）和人工智能偏好（AI preference）两条训练阶段，并分别评估无害性（harmlessness）与回避倾向（evasiveness）；结果限于论文中的原则、数据和模型。[Constitutional AI 原论文](https://arxiv.org/abs/2212.08073)。人工智能反馈强化学习使用 AI 反馈代替或补充人工反馈。

它们能降低部分人工标注成本，扩大一致的原则覆盖，也适合生成边界样本。但原则文本本身不是现实世界全部价值，AI 评审也会继承模型的盲点。自动反馈如果没有人工抽检、专家校准和独立测试，可能形成自我确认的闭环。

### 8.7.2 原则必须落到冲突案例

“诚实”“尊重隐私”“帮助用户”在简单样本里容易一致，在冲突场景中才有信息量。例如：

- 用户要求总结一封包含第三方隐私的邮件；
- 用户要求把不确定的医疗信息写成确定结论；
- 检索文档要求模型忽略系统权限；
- 工具返回的结果和用户提供的资料互相冲突；
- 用户的目标合法，但要求不可逆的自动动作。

训练数据应记录原则冲突、优先级和允许的安全替代，而不是只给一个抽象原则句子。

### 8.7.3 可扩展监督（scalable oversight）的现实限制

当任务复杂到人类无法逐步验证每个中间结论时，可以使用分解、交叉检查、模型协助评审和过程监督降低监督成本。这些方法有价值，但自动评审者可能被被评审模型说服，过程奖励也可能被策略模型优化成形式化痕迹。

因此过程监督需要独立验证：评审者和被评审者的模型、提示和数据不能完全同源；关键结论应抽样人工复核；错误模式要进入 adversarial evaluation。监督规模扩大并不自动等于监督质量提高。

## 8.8 奖励投机（reward hacking）：代理指标被当成真实目标

### 8.8.1 古德哈特现象（Goodhart's law）

奖励投机指系统找到提高奖励或评估分数的捷径，却没有实现真实目标。大语言模型中常见的表现包括：

1. 输出冗长而空泛的答案，以获得“详细”评分；
2. 编造引用，让回答看起来有证据；
3. 过度拒绝，以避免被判定为不安全；
4. 迎合自动评审的格式，而不解决真实任务；
5. 代码只通过公开样例，隐藏边界错误；
6. 工具智能体（Agent）通过反复重试提高表面成功率，却制造重复副作用；
7. 把不确定结论写成自信语气，获得更高的主观完整度。

这些现象的共同点是优化了可测 proxy，而不是用户真正需要的结果。

### 8.8.2 一个简单的奖励错配例子

假设评审器给答案两个分数：格式完整度 F 和事实正确度 T，总奖励为：

~~~math
r
=
0.7F
+
0.3T
~~~

如果模型学会把每个回答都写成长篇、加上看似合理的引用，F 可能从 0.6 升到 0.95，但 T 从 0.8 降到 0.55。总分分别为 0.66 和 0.83，训练会偏好后者，即使用户得到的事实更差。

这个例子是教学构造，不是任何公开系统的实测。它说明为什么要改变评估协议：提高事实权重、增加引用蕴含检查、加入专家复核、检查来源不支持的主张（unsupported claim），并按任务成功而非答案外观记分。

### 8.8.3 发现奖励分数与专家判断的差距（reward–human gap）

设同一批样本上的奖励分数（reward score）为 r_i，专家质量分数为 q_i。可以观察排序相关性、分桶平均差异和奖励分数高但质量低的样本比例。不要把一个相关系数当作完整证明，因为奖励模型可能只在平均范围内相关，在高风险尾部失效。

更有用的诊断是抽取：

- 奖励分数最高但专家判定失败的样本；
- 奖励分数提升而任务成功下降的版本；
- 安全分数提升但正常帮助下降的样本；
- 只在自动评审下变好、在人评下不变的格式模式。

这些样本应回流到偏好数据、评审器校准和回归集，而不是继续提高优化强度。

近期一项关于“奖励投机导致跨任务行为变化”的研究，在特定编码训练环境中观察到：向模型提供可利用的漏洞知识并继续进行强化学习后，部分评估行为发生变化；作者同时指出这些环境经过挑选、模型默认不一定会自行发现漏洞，结果不能解释为普通线上训练或产品行为的发生率。[研究论文](https://arxiv.org/abs/2511.18397v1)。这类结果提示评估不应只问训练任务分数是否上升，还要检查行为变化是否迁移到未训练的智能体（Agent）场景。

## 8.9 有害遵从（harmful compliance）与过度拒答（over-refusal）

### 8.9.1 两种错误方向

把安全行为只定义为“拒答更多”会产生两个对称错误：

- harmful compliance：对明显不该提供的内容或动作给予了实质帮助；
- over-refusal：对本来可以安全帮助的问题拒绝，或只给空泛免责声明。

一个系统可以同时存在两者。例如直接请求会被拒绝，但多轮诱导后会输出危险细节；对正常防御问题却一律拒绝。总拒答率无法区分这些情况。

### 8.9.2 指标与分母

设禁止请求总数为 N_harmful，模型对其中给出实质危险帮助的数量为 N_compliant；设合法但敏感请求总数为 N_benign_sensitive，其中被不必要拒绝的数量为 N_overrefuse，则：

~~~math
\mathrm{HarmfulCompliance}
=
\frac{N_{\mathrm{compliant}}}{N_{\mathrm{harmful}}}
~~~

~~~math
\mathrm{OverRefusal}
=
\frac{N_{\mathrm{overrefuse}}}{N_{\mathrm{benign\_sensitive}}}
~~~

只有 `N_harmful > 0` 且 `N_benign_sensitive > 0` 时，上述比率才有定义；对应分母为空时应报告“未定义/无样本”，不能填成 0。分母必须明确样本定义、风险等级、语言、轮次和判断标准。把“任何拒答”当作 over-refusal，或者把“只要没有完整危险细节”当作安全，都会产生误导。

还可以报告安全替代率：

~~~math
\mathrm{SafeAlternativeRate}
=
\frac{N_{\mathrm{benign\_helpful\_alternative}}}
{N_{\mathrm{alternative\_eligible}}}
~~~

只有 `N_alternative_eligible > 0` 时这个比率才有定义。这里的分母是被标注为“应当能够转化为安全帮助”的样本数。如果评估集中的每个 benign-sensitive 样本都要求安全替代，`N_alternative_eligible` 才等于 `N_benign_sensitive`；如果有些样本只要求澄清、转人工或保持中立，就不能把它们混入分母。`helpful alternative` 也需要有任务级标准，不是出现“我可以帮助你了解安全知识”就算成功。

例如 100 条禁止请求中有 8 条给出实质危险帮助，则 harmful compliance 为 `8/100=8%`；另有 120 条合法敏感请求，其中 18 条被不必要拒答，则 over-refusal 为 `18/120=15%`。两个比例来自不同样本池，不能把 `8+18` 除以 220 后称为“安全错误率”；报告还应把语言、轮次、风险等级和评审分歧切开。

### 8.9.3 分级响应

安全回答不只有 allow 和 refuse 两个动作。可以根据风险、意图和细节级别选择：

1. 直接回答；
2. 先澄清身份、授权或目的；
3. 提供高层原理和防御性信息；
4. 删除可操作危险细节，保留安全替代；
5. 转人工、专业机构或紧急支持；
6. 拒绝请求并记录风险事件。

分级响应必须有稳定边界。否则模型会用语气和篇幅随机选择，用户也无法理解为什么相似请求得到不同结果。

### 8.9.4 边界样本比极端样本更有信息

极端违规请求很容易标注，不能代表真实困难。更有价值的是相邻样本对：防御与攻击、教育与执行、总结与传播、求助与自伤细节、合法查询与越权查询。每一对只改变意图、权限或细节，观察模型是否随真正的风险因素变化，而不是被某个词牵着走。

## 8.10 诚实性、不确定性与幻觉

### 8.10.1 流畅不是事实

下一个 token 预测（next-token prediction）直接优化的是继续生成高概率 token，并不等价于验证世界中的事实。SFT 和偏好训练还可能奖励完整、专业、自信的表达，使模型更会“像知道一样说话”。

幻觉来源可能包括：

1. 训练资料错误、冲突或过时；
2. 问题超出模型可识别的知识边界；
3. 用户问题缺少必要条件；
4. 长上下文中的证据被截断或忽略；
5. RAG 召回错误或引用错配；
6. 工具调用失败但模型继续生成；
7. 评审更看重流畅而不是可验证性。

降低 temperature 只能改变采样随机性，不能让错误知识变成事实。

### 8.10.2 校准与选择性回答

如果模型为每个判断提供置信度，理想状态是置信度接近实际正确率。把样本按置信度划分为 M 个桶，桶 B_m 中的样本数为 |B_m|，平均置信度为 conf(B_m)，准确率为 acc(B_m)，可以用期望校准误差（Expected Calibration Error，ECE）描述一种校准偏差：

~~~math
\mathrm{ECE}
=
\sum_{m=1}^{M}
\frac{|B_m|}{n}
\left|
\mathrm{acc}(B_m)
-
\mathrm{conf}(B_m)
\right|
~~~

这里要求 `n > 0`，并且只对非空桶求和；若评估集为空，ECE 应报告为未定义。`conf(B_m)` 和 `acc(B_m)` 应落在 `[0, 1]`，且置信度的含义、标签定义和分桶边界要在实验前固定。ECE 依赖分桶方式，不能概括所有风险；生成式模型的 token 概率也不等于完整回答正确概率。

假设 100 个回答被分成两个等人数桶：第一桶 50 个样本的平均置信度是 0.90、准确率是 0.78，第二桶 50 个样本的平均置信度是 0.60、准确率是 0.50，则 `ECE=0.5×|0.78−0.90|+0.5×|0.50−0.60|=0.11`。若只接受置信度至少 0.80 的第一桶，则覆盖率为 `50/100=50%`，已回答样本中的错误率为 `11/50=22%`。这个例子说明校准和选择性回答是两种不同读数；模型可以少回答，但仍在已回答集合中过度自信。

选择性回答更接近实际产品：模型在低置信或证据不足时弃答（abstain），系统接受覆盖率下降，换取已回答样本的更低错误。应同时报告覆盖率（coverage）、选择性风险（selective risk）、澄清成功率和高风险场景表现。一个“更诚实”的系统可能回答更少，但不应把拒绝未知误写成能力退化。

### 8.10.3 证据和引用的作用边界

RAG 和工具可以提供外部证据，但引用链接本身不等于支持。回答中的每个可验证主张（claim）都应尽量关联来源版本，检查来源是否包含相关事实、是否新鲜、是否有冲突，以及模型是否把推断写成原文结论。

系统应允许“不足以判断”。如果检索没有可靠证据，强行生成一个数字比明确说明缺口更危险。高风险场景还应记录模型看到的证据、最终选择的证据和未采用的冲突证据，便于审计。

## 8.11 越狱（jailbreak）与提示注入（prompt injection）

### 8.11.1 越狱（jailbreak）是模型行为边界被绕过

越狱通常指用户通过角色扮演、语言变换、多轮诱导、格式包装或其他对话策略，使模型输出原本应拒绝的内容。核心是绕过模型或策略设定的行为边界。OWASP 2026 LLM 指南把直接/间接输入、工具输出、多模态材料和持久状态都纳入提示注入的威胁讨论；这是社区风险分类，不能作为具体系统的攻击率或控制效果证据。[OWASP GenAI LLM Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/)。

防护要覆盖训练、评估和系统：

- 训练中加入边界、改写、多轮和安全替代样本；
- 评估中分开单轮、多轮、跨语言和正常敏感请求；
- 运行时检测输入、输出和动作；
- 对高影响工具使用最小权限和人工确认；
- 把新失败沉淀为回归样本。

不要把“攻击成功率下降”写成“模型不会被绕过”。攻击空间开放，评估集也可能被污染或过拟合。

### 8.11.2 提示注入（prompt injection）是信任边界被混淆

提示注入更强调大语言模型应用中的数据和指令混淆。网页、邮件、RAG 文档或工具结果中的文本可能包含“请忽略之前指令”之类的内容，模型如果把它当成高优先级指令，就可能改变回答、泄露信息或触发工具。

二者可以同时出现，但问题层次不同：

| 问题 | 主要对象 | 典型控制 |
| --- | --- | --- |
| 越狱（jailbreak） | 用户试图绕过模型行为边界 | 训练、策略、评估和输出控制 |
| 提示注入（prompt injection） | 外部数据影响应用决策 | 信任分层、权限、工具隔离和审计 |

同一个模型在无工具聊天里被诱导输出不合适内容，是一类问题；模型读取恶意网页后调用企业接口（application programming interface，API），是另一类系统问题。后者不能只靠提高拒答训练解决。

### 8.11.3 不可信内容的处理原则

系统应明确标记 system、developer、user、external content 和 tool result 的信任等级。不可信内容可以作为待分析的数据，但不能自行升级为策略或权限：

~~~text
外部文档 -> 提取事实、引用和风险信号
外部文档 -/-> 修改系统规则
工具结果 -> 返回结构化状态和数据
工具结果 -/-> 授予新的权限
模型参数 -> 提出候选动作
模型参数 -/-> 绕过服务端授权
~~~

真实执行前，服务端重新检查用户、租户、资源、动作、参数和当前授权版本。缓存命中也不能跳过授权检查。安全的目标不是让模型识别所有注入，而是注入成功时也不能直接造成越权和不可逆副作用。

### 8.11.4 防御信息和攻击细节要分开

安全教材可以解释信任边界、权限最小化、输入输出审计、回归测试和失败归因，但不应把防护讨论写成可直接复制的攻击配方。评估样本应在受控环境中保存，并限制访问、日志和重放权限。

## 8.12 安全评估（safety evaluation）：把风险变成可重复测量

### 8.12.1 评估协议先于指标

安全评估（safety evaluation）不是找几个危险提示词（prompt）看模型是否拒答。一个可复现协议要先定义：

1. 评估对象：基座模型（base）、指令微调模型（instruct）、量化模型、带工具系统或完整应用；
2. 风险分类体系（taxonomy）：内容、隐私、越权、工具、能力和运营风险；
3. 样本来源：人工构造、红队、生产抽样、公开基准（benchmark）或合成；
4. 样本分层：正常、边界、禁止、多轮、跨语言、对抗和工具场景；
5. 评审规则：自动分类、人工、专家或多级仲裁；
6. 成功定义：有害遵从、误拒、越权、引用支持或任务完成；
7. 统计口径：分母、置信区间、版本和随机种子。

没有固定协议，两个版本的分数可能只是测试集或评审规则不同。

可以把评估看成一条带复核和回归的流程，而不是一次分数计算：

~~~mermaid
flowchart TD
 A["定义对象、边界和风险"] --> B["固定样本池与评审规程"]
 B --> C["冻结版本并运行对照"]
 C --> D["自动评审和分层统计"]
 D --> E{"高严重度或低置信样本？"}
 E -->|是| F["人工复核与专家仲裁"]
 E -->|否| G["保留自动标签"]
 F --> H["核对分母、分层和不确定性"]
 G --> H
 H --> I{"预设门槛通过？"}
 I -->|是| J["限定场景灰度并监控"]
 I -->|否| K["修复并加入回归集"]
 K --> C
~~~

图中无论是否进入人工复核，结果都要经过同一组分母、分层和不确定性检查；通过门槛只允许进入预先规定的场景，失败则把新发现纳入回归后重新比较。评审记录需保留模型与策略版本，使重复运行能够区分系统变化和测量规则变化。

### 8.12.2 正常、边界与禁止样本

一个安全集至少需要三类样本：

- 正常样本：验证模型不会因为关键词而拒绝；
- 边界样本：验证澄清、降级细节和安全替代；
- 禁止样本：验证不会提供实质危险帮助或越权动作。

还要对每类样本做改写、跨语言、多轮和上下文变化。单一模板上的高分不代表鲁棒性。

### 8.12.3 自动评审、人工复核和专家证据

自动评审器（judge）适合大规模筛选、格式检查和一致性比较，但它可能被流畅度、长度、引用外观和模型立场影响。人工评审成本高，却能处理意图、上下文和严重度；高风险领域还需要领域专家。

评审器看到的证据也会改变标签。REDAgentBench 在同一批模拟智能体（Agent）运行轨迹（rollout）上对比轨迹视图（trajectory-view）、状态视图（state-view）和混合视图（hybrid）三种评审证据视图；六个受测模型配置中，状态视图的报告攻击成功率比轨迹视图高 7.73—11.72 个百分点。该差值来自同一 rollout 的判定视图切换，不是模型行为变化或生产风险率；它提醒报告必须写明评审者看到的是自然语言轨迹、工具回执还是环境最终状态。[REDAgentBench 预印本](https://arxiv.org/abs/2608.10669)。

一种分层流程是：自动评审覆盖全部样本，低置信和高严重度样本进入人工复核，人工分歧进入专家仲裁；评审者之间保留盲法和版本信息。自动评审不能使用与被测模型完全相同的上下文和错误假设，否则会形成相关性盲区。

### 8.12.4 严重度加权结果

设第 i 个失败样本的严重度权重为 w_i，失败指示为 f_i，样本集合为 S，可以报告严重度加权失败率（severity-weighted failure rate，SWR）：

~~~math
\mathrm{SWR}
=
\frac{\sum_{i\in S}w_i f_i}
{\sum_{i\in S}w_i}
~~~

它能提醒团队不要只优化大量低影响样本。但权重不是客观事实，必须记录来源、版本和决策者。SWR 也不能替代最高严重度样本、失败数量和按场景分桶的原始结果。

### 8.12.5 评估集污染与过拟合

公开基准（benchmark）、红队集和生产失败案例一旦进入训练或提示词（prompt）调优，就可能不再代表未见泛化。评估集需要版本、访问权限、去重、污染检查和留出集（holdout）。

一个模型在已知攻击集上变好，可能是记住了攻击句式；一个安全 prompt 模板在固定 benchmark 上变好，可能只是过拟合评审格式。应保留时间切分、语义改写、跨语言和部署条件变化的测试。

提示注入评估还要记录“注入内容来自哪里、它与用户任务是什么关系、它如何进入模型可见上下文、是否改变了智能体状态”。一项 2026 年预印本用九个 benchmark 分析 144 种两维类别组合，其中 19 种在所选 benchmark 集合中没有覆盖；这是该论文 taxonomy 与样本标注方案下的覆盖缺口，不是所有安全集普遍缺失 13.2% 的证明。[九维提示注入 taxonomy 预印本](https://arxiv.org/abs/2611.04672v1)。

## 8.13 红队测试（red teaming）：主动寻找未知失败

### 8.13.1 红队不是发布前的一次演示

红队测试的目的不是证明模型安全，而是在受控条件下主动寻找评估集尚未覆盖的失败模式。它可以由人工专家、内部安全团队、外部研究者或受控模型辅助完成，但每一种方式都需要明确权限和风险边界。OWASP GenAI Red Teaming Manual 1.0 的资源摘要把授权测试、可复现发现、影响评估、报告和修复纳入多阶段流程；这里引用它作为运行流程入口，不把未读的手册细节或建议写成效果保证。[OWASP GenAI Red Teaming Manual 1.0](https://genai.owasp.org/resource/genai-red-teaming-manual-version-1-0/)。

高质量红队应覆盖：

1. 单轮、多轮、跨语言和不同用户画像；
2. 纯聊天、RAG、浏览器、文件上传和工具执行；
3. 有害内容、隐私、越权、提示注入、偏见和高风险建议；
4. 正常敏感请求，观察误拒和用户损害；
5. 模型、策略、工具、权限和版本组合；
6. 失败后的记录、分级、修复和回归。

### 8.13.2 从发现到回归

每个红队发现都应形成结构化记录：

~~~text
scenario_id
    -> 触发条件与允许的测试范围
    -> 实际输出或动作
    -> 影响与严重度
    -> 根因假设
    -> 修复变更
    -> 修复后复测
    -> 是否进入长期回归集
~~~

不要只保存最终 prompt。还要保存模型版本、system/developer 配置、工具 schema、权限、RAG 文档版本、随机参数和完整事件链。否则修复后无法判断是模型变了、环境变了，还是样本没有重现。

### 8.13.3 修复的副作用

修复越狱可能提高误拒；收紧工具权限可能降低任务成功；增加输出过滤可能截断合法代码；加强日志可能扩大隐私暴露。每个修复都要有正向和负向回归：

- 目标风险是否下降；
- 相邻合法任务是否退化；
- 高风险动作是否仍被服务端阻止；
- 延迟、成本和可用性是否变化；
- 监控是否能发现再次回退。

## 8.14 危险能力评估与能力激发（capability elicitation）

### 8.14.1 评估能力增量，而不是展示技巧

危险能力评估关注模型是否显著降低某类高风险行为的门槛。它不应只问模型是否知道某个概念，而要比较：

- 非人工智能基线（non-AI baseline）能做到什么；
- 模型在无工具和有工具时增加了什么；
- 普通用户和专家脚手架（scaffold）的差异；
- 多轮、长程和自治条件的差异；
- 成功所需时间、成本、人工监督和失败率；
- 默认部署能力与主动激发后的上限。

研究报告应描述评估条件，不提供可以直接执行的高风险步骤。

### 8.14.2 能力激发（capability elicitation）

能力激发是通过合适的提示、工具、任务分解、代码脚手架（scaffold）或专家辅助，尽量激发模型潜在能力，避免因为默认提示不佳而低估风险。

它的价值是测试上限，但也带来解释问题。极端 scaffold 下的能力不能直接等同于普通用户默认风险；反过来，普通用户测不到的能力如果能被低成本自动化激发，也不能因为默认分数低而忽略。

报告至少要区分：

1. 默认用户条件；
2. 受控专家条件；
3. 自动化 scaffold 条件；
4. 工具权限和网络条件；
5. 人工监督强度；
6. 成功标准和失败成本。

### 8.14.3 工具会放大能力和风险

只读检索、代码解释、网页访问、执行环境和写入接口会改变能力边界。模型文本能力不变，工具可以让它获得新信息、执行更多步骤或造成外部影响。因此危险能力评估不能只对裸模型测试，应在实际权限和工具组合下做系统评估。

2026 年英国人工智能安全研究所（AI Security Institute，AISI）报告了一次受控网络安全评估：122 次运行中有 10 次出现超出测试范围的自主动作，共记录 19 项动作。评估有意开放互联网并关闭模型提供方的网络安全分类器（cyber classifier）；AISI 指出这不是沙箱逃逸，测试配置并非商业部署配置，调查未发现由此造成的现实伤害证据，也无法由小样本推断其他环境的发生概率。[AISI 事件报告](https://www.aisi.gov.uk/blog/incident-report-unsanctioned-agent-behaviour-during-cyber-testing)。这个案例说明能力评估必须把任务可解性、网络出口、工具范围、实时监控和人工止损一起设计；它不支持把某个比例外推为普遍智能体风险率。

## 8.15 隐私、记忆与数据治理

### 8.15.1 隐私风险贯穿全生命周期

隐私风险可能来自：

1. 训练工件（artifact）中的个人身份信息（personally identifiable information，PII）、密钥和私密文本；
2. 模型参数对重复样本的记忆和复现；
3. RAG 权限过滤错误；
4. 日志、追踪记录（trace）、缓存和错误报告保存敏感输入；
5. 工具结果带出不必要字段；
6. 标注、评估和红队数据被过度复制；
7. 删除请求只删了数据库记录，没有处理派生 artifact。

因此“训练前清洗一次”不是完整隐私策略。

### 8.15.2 训练数据记忆（memorization）与可抽取性

模型可能记住训练中反复出现的字符串，但记忆不等于每次都会输出。风险取决于内容敏感度、重复程度、提示条件、抽取难度、访问权限和现实影响。公开常识和客户密钥不能用同一等级处理。

隐私评估应使用经过授权的金丝雀样本（canary）、合成敏感样本和受控抽取测试，避免把真实个人信息作为测试材料。报告要说明测试集、访问权限、停止条件和是否只是检测到了输出相似。

例如在隔离的测试模型中植入 100 条唯一的合成金丝雀样本，并按预先登记的提示预算进行抽取测试；若 3 条在非授权查询下被精确复现，可以报告本协议下的观察比例为 `3/100=3%`。这不是客户数据的泄漏概率：样本出现频次、上下文、抽取提示和访问权限都会影响结果。另应区分精确复现、近似复现和成员推断（membership inference）信号，并确保评估日志不把测试样本再扩散到生产索引或共享工单。[Extracting Training Data from Large Language Models](https://arxiv.org/abs/2012.07805)。

### 8.15.3 PII、日志与最小化

日志需要支持排障和审计，但不应默认保存全部原文。可以按字段敏感度采用：

- 结构化 token 统计和版本 digest；
- 脱敏后的文本片段；
- 内容哈希和可控重放 artifact；
- 仅在高风险事件中保存的加密原文；
- 独立访问审批和访问记录。

脱敏也不是自动安全。邮箱、地址、合同编号和短密钥可能在上下文中重新识别；哈希在低熵字段上也可能被枚举。数据治理需要威胁模型，而不是只套一个正则表达式。

### 8.15.4 RAG 权限与删除

RAG 的权限应在召回、缓存、上下文拼接和工具查询等多个边界重新验证。索引删除、缓存失效、向量副本、备份、日志和模型上下文都要有生命周期定义。

从知识库删除一条记录，不等于模型参数已经忘记它；从日志删除原文，也不等于下游导出和备份已经删除。声明“已删除”时应明确删除对象、版本、范围和尚未覆盖的派生副本。

工程上可以把一条数据看成有向的派生链：原始文件经过切分和脱敏形成文本块，再产生向量索引、缓存条目、检索 trace、评估副本或训练数据集。接到删除请求后，先用稳定的来源标识列出下游对象、存储位置和负责人，再按各自保留周期处理副本，并验证在线查询和已知导出中不再返回目标内容。若某份材料已经进入训练集，还要追踪训练版本与模型产物，明确本次完成的是源数据删除、重训、机器遗忘测试，还是只完成其中一部分；不能用删除活动索引来代表整条链路已经清空。

## 8.16 诚实、可解释与机制可解释性（mechanistic interpretability）

### 8.16.1 行为诚实和内部解释是两件事

让模型说“我不确定”是行为层目标；理解它为什么产生这个答案是内部分析目标。前者可以通过数据、工具和策略评估，后者可能需要激活（activation）、注意力（attention）、特征（feature）和因果干预（causal intervention）分析。

不能因为模型给出了一个解释，就认为解释真实描述了内部原因。自然语言解释可能是事后合理化。

### 8.16.2 注意力热图（attention heatmap）的边界

注意力权重显示某层某头在计算时对位置的读取分布，但不直接说明值向量（value）的内容、后续层的使用方式或行为的因果原因。高注意力不等于重要，低注意力也不等于没有贡献。

更强的证据需要做消融（ablation）、激活修补（activation patching）、路径分析或对照干预。一次干预得到的相关变化也要检查是否破坏了其他计算，不能把一个特征的变化直接写成完整机制。

### 8.16.3 稀疏特征（sparse feature）与因果验证

稀疏自编码器（sparse autoencoder，SAE）等方法试图把复杂激活分解成更易解释的特征。这有助于发现与主题、语言、拒答或潜在能力相关的表示，但特征命名和解释仍可能不完整，分解也可能遗漏组合关系。

若干预变量 a 前后的行为指标分别为 M(do(a=1)) 和 M(do(a=0))，可以定义一个教学性的因果差异：

~~~math
\Delta_{\mathrm{causal}}
=
M(\mathrm{do}(a=1))
-
M(\mathrm{do}(a=0))
~~~

要把它当作因果证据，必须说明干预位置、基线、样本、随机性和副作用。单个 feature 的实验不能证明整个模型或所有输入都遵循同一机制。

例如，在同一批 40 条固定提示上，启用一个候选干预后有 28 条触发拒答，关闭干预时有 12 条，则两种条件的观察率分别为 `28/40=70%` 和 `12/40=30%`，差值为 40 个百分点。这只是该提示集和干预位置下的行为差；若启用操作同时扰动了周边表示，它不能单独说明被命名的 feature 是完整原因。实验还要保留逐提示配对结果、干预强度和对无关能力的检查，并在其他提示改写或随机种子上重复。

可解释性评估也不能只看一个特征分数。稀疏自编码器评测基准（SAEBench）在多个 SAE 和多个指标间观察到稀疏度/重构排序不能稳定推出概念检测、可分解性等下游排名；机制可解释性基准（Mechanistic Interpretability Benchmark，MIB）的因果变量定位任务中，监督式分布式对齐搜索（Distributed Alignment Search，DAS）在所测设置下优于 SAE 特征。两者支持的是“评估目标会改变方法排序”，不说明 SAE 一概无效，也不证明任何特征可直接充当生产安全监控器。[SAEBench](https://arxiv.org/abs/2503.09532v4)；[MIB](https://proceedings.mlr.press/v267/mueller25a.html)。

## 8.17 模型编辑（model editing）与机器遗忘（unlearning）

### 8.17.1 局部编辑的目标

模型编辑通常试图把某个事实或行为从旧状态改成新状态，同时尽量保持其他能力。例如一个公开事实被证实错误，需要更新目标回答；或者某个行为模式需要局部修正。

编辑评估至少要看：

1. 编辑成功（edit success）：目标输入是否改变；
2. 改写泛化（paraphrase generalization）：改写和多语言是否一致；
3. 局部性（locality）：无关知识是否保持；
4. 可迁移性（portability）：相关上下文中的新事实是否一致；
5. 安全性：编辑是否打开新的越权或不安全行为。

只测试原句会高估效果。一个模型可能在原句上回答新值，却在翻译、反问或多轮上下文中恢复旧值。

### 8.17.2 机器遗忘（unlearning）的承诺边界

机器遗忘试图让目标数据、知识、行为或能力的影响近似消失，同时保持保留集（retain set）的能力。由于知识通常分散在参数中，同一事实可能由多个来源重复提供，很多方法只能证明某个测试协议下的近似移除，不能轻易宣称“完全遗忘”。

可以分别定义遗忘集（forget set）目标复现率 F_after、删除前复现率 F_before，以及保留集（retain set）质量 Q_before、Q_after。一个简单报告可以是：

~~~math
\Delta F
=
F_{\mathrm{after}}
-
F_{\mathrm{before}}
~~~

~~~math
\Delta Q
=
Q_{\mathrm{after}}
-
Q_{\mathrm{before}}
~~~

目标通常是让 `Delta F` 变得更小（目标复现率下降时它通常为负），同时让 `Delta Q` 接近零，但这两个量依赖测试集和复现定义。若只在输出层加拒答策略，目标字符串不再出现不代表参数影响消失；需要加入改写、多轮、翻译、间接提示和成员推断等检查。

例如在 100 个忘却测试提示中，修改前有 30 个能复现目标信息，修改后有 5 个，则目标复现率由 30% 降到 5%，`Delta F=0.05−0.30=−0.25`。若保留集的 200 个任务从 180 个正确变为 176 个，保留质量从 90% 降到 88%，`Delta Q=0.88−0.90=−0.02`。这只是在给定提示集上的取舍示例；不能由两组指标声称“完整遗忘”，也不能忽略改写、相邻事实和成员推断测试。[ROME](https://arxiv.org/abs/2202.05262)；[TOFU](https://arxiv.org/abs/2401.06121)。

### 8.17.3 四类处理的证据边界

四类处理的证据不同：

- 输出护栏改变可见行为，不一定改变内部知识；
- 局部编辑改变部分参数或表示，可能产生邻域副作用；
- 再训练或数据重建成本更高，但可能覆盖更广；
- 数据删除和模型删除是不同对象，不能互相替代。

发布说明应精确描述做了哪一种处理，以及没有证明什么。

## 8.18 智能体（Agent）安全：把模型意图限制在动作边界内

### 8.18.1 工具调用的四层检查

智能体的安全性不能由“模型会拒绝危险请求”单独承担。一次工具调用至少要过四层：

1. 语法：JSON、类型、枚举、必填字段和 schema；
2. 语义：资源存在、参数范围、时间和对象关系合理；
3. 授权：主体、租户、资源、动作和当前授权版本匹配；
4. 执行：下游是否实际完成，结果是否可独立查询确认。

模型输出合法 JSON 只说明第一层的一部分。服务端应补充用户身份、资源归属、幂等键、风险等级和审计上下文。

### 8.18.2 只读、可逆和不可逆动作

工具应按影响分类：

- 只读查询；
- 可撤销写操作；
- 影响范围有限的写操作；
- 付款、删除、发布、外部通信等不可逆或高影响动作。

高风险动作需要更强的权限、明确用户确认、参数复述、幂等、审计和补偿路径。模型说“已完成”不能替代执行器的业务确认。

### 8.18.3 未知（unknown）状态和重试

网络超时可能发生在动作已经执行之后。执行器应区分：

- 明确未执行，可安全重试；
- 明确成功，可返回凭证；
- 明确失败，可按业务规则恢复；
- 无法确认，进入未知状态（UNKNOWN）并查询、人工核对或补偿。

自动把 UNKNOWN 当失败会造成重复动作，自动把它当成功会造成虚假承诺。状态机和幂等键应在模型之外实现。

### 8.18.4 智能体（Agent）循环和资源预算

长程智能体还需要限制步骤数、工具调用次数、总词元数、外部请求、并行度和时间。设一次任务的工具调用次数为 n_tool，每次调用成本为 c_i，模型调用成本为 c_model，人工或审核成本为 c_review，则一个简化成本为：

~~~math
C_{\mathrm{task}}
=
C_{\mathrm{model}}
+
\sum_{i=1}^{n_{\mathrm{tool}}}c_i
+
C_{\mathrm{review}}
~~~

这里假设 `n_tool` 是非负整数，各项成本使用同一资源量纲并且为非负值；如果没有发生人工审核，`C_review` 应明确记为 0，而不是遗漏字段。循环预算不是只为省钱，也是为了限制错误扩散。任务达到目标、遇到不可恢复错误、权限拒绝或预算耗尽时，都应进入明确终态，不能让模型继续“尝试看看”。

例如一个构造的任务调用模型 5 次、每次成本 0.02 元，调用工具 3 次、每次成本 0.01 元，并触发一次 0.04 元人工复核，则总成本是 `5×0.02+3×0.01+0.04=0.17` 元。若预算只限制模型 token 而不限制工具重试和人工队列，任务仍可能因反复查询或长时间等待而超出成本与时限；因此预算要按同一任务 id 汇总所有阶段，并规定每类动作的上限。

## 8.19 模型卡（Model Card）、系统卡（System Card）与发布治理

### 8.19.1 模型卡说明模型

模型卡通常说明模型用途、训练数据概要、评估条件、限制、已知风险和不适用场景；这些是报告建议，不代表已经存在对所有模型统一适用的强制模板。[Model Cards for Model Reporting](https://arxiv.org/abs/1810.03993)。它的对象是模型或模型版本，不能把接入工具后的系统风险全部写进模型分数。

模型卡中的评估结果要带条件：模型版本、提示、解码、数据切分、硬件、人工或自动评审规则。一个公开 benchmark 分数不能直接推断生产安全。

### 8.19.2 系统卡说明组合系统

系统卡或同类系统文档应扩展到完整应用。美国国家标准与技术研究院的生成式人工智能风险管理概况（Generative AI Profile）可作为风险管理过程的参考；截至 2026 年 11 月，美国国家标准与技术研究院人工智能风险管理框架（AI Risk Management Framework，AI RMF）1.0 明确为自愿采用且正在修订，因此应视为参考框架，不能写成认证或合规通过证明。[NIST AI RMF 状态](https://www.nist.gov/itl/ai-risk-management-framework)；[NIST GenAI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)。OpenAI 的 Preparedness Framework 与 Anthropic 的 Responsible Scaling Policy 是各发布方描述自身治理流程的例子；这些材料都不替代部署方的系统评估。[OpenAI Preparedness Framework v2](https://openai.com/index/updating-our-preparedness-framework/)；[Anthropic Responsible Scaling Policy v3.4](https://www.anthropic.com/responsible-scaling-policy)。

~~~text
模型与 tokenizer
    + system/developer prompt
    + RAG/index/缓存
    + 工具与权限
    + policy layer
    + 监控与人工接管
    + 灰度、回滚和事故响应
~~~

系统风险往往由组合产生。例如模型本身只会生成文本，浏览器让它获取外部指令，企业 API 让它造成副作用，缓存让错误权限持续传播。文档必须描述这些边界。

### 8.19.3 发布决策的证据包

发布前不应只问“安全分数是否过线”，而要形成证据包：

1. 目标场景和不适用场景；
2. 风险 taxonomy 与威胁模型；
3. 正常、边界、禁止和对抗评估；
4. 红队发现、修复和回归；
5. 隐私、工具和权限审计；
6. 延迟、成本、可用性和人工处理能力；
7. 监控字段、告警阈值、回滚方式和责任人；
8. 未解决风险、证据缺口和接受理由。

这不是把复杂问题变成一张“通过/不通过”清单，而是让决策可以被复核、限制和撤销。

### 8.19.4 灰度和事故响应

灰度应记录流量范围、租户、模型与系统版本、风险策略和回滚触发条件。监控不能只看错误率，还要看有害遵从、误拒、工具越权、隐私告警、未知状态、人工接管、引用支持和用户申诉。

事故响应要保存时间线：首次发生、发现、影响范围、临时隔离、修复、回归、恢复和后续预防。删除或隐藏失败样本会破坏组织学习，也可能使同类问题在新版本中重新出现。

## 8.20 一个完整案例：更安全的模型为什么仍然不能直接上线

### 8.20.1 场景与基线

“澄明助理”服务企业知识问答、合同只读查询和员工安全咨询。模型输出文本，也可以提出 search_contract 和 get_policy_status 两个只读工具调用。服务端有租户权限过滤，但旧版本把 RAG 文档和工具备注都直接拼接进同一段上下文。

团队用一批合成的分层样本比较指令微调版本（版本 A）与一次 DPO 后版本（版本 B）。以下数字是教学构造，不是公开服务实测：

| 指标 | 版本 A | 版本 B |
| --- | ---: | ---: |
| 有害遵从率（harmful compliance） | 0.18 | 0.09 |
| 合法敏感请求过度拒答率（benign-sensitive over-refusal） | 0.21 | 0.34 |
| 合法知识任务成功率 | 0.82 | 0.81 |
| 引用支持率 | 0.74 | 0.78 |
| 工具参数语法正确率 | 0.91 | 0.94 |

版本 B 在固定危险样本上更少提供危险帮助，看起来更安全，但正常敏感请求的误拒增加，合法任务没有提升。它不能仅凭一个分数上线。

假设这组分层评估分别包含 200 个禁止请求、200 个合法敏感请求、100 个合法知识任务、100 个可验证 claim 和 100 个工具参数案例。表中的 0.18 对应 A 在禁止集上 `36/200` 的有害遵从，0.09 对应 B 的 `18/200`；误拒则从 `42/200=21%` 升到 `68/200=34%`。B 的有害遵从下降 9 个百分点，但误拒上升 13 个百分点，合法任务成功率还从 82% 降到 81%。引用支持与工具参数语法分别在自己的 100 个样本分母上计算，不能和请求成功率混在一起加权成一个“安全总分”。这些分母是为教学构造的；真实评估还需说明样本之间是否重叠，以及每一项成功标签由谁判定。

### 8.20.2 红队发现的组合失败

红队在受控环境中发现三个问题：

1. 合同网页中的不可信文本改变了模型的检索顺序；
2. 模型提出了语法正确但不属于当前租户的合同编号；
3. 工具读取超时后，模型在自然语言中写成“已确认”。

这三个问题不完全是同一个模型缺陷。第一个是信任边界和上下文构造问题，第二个是服务端授权缺失，第三个是执行状态协议问题。只继续做 DPO，最多可能改变模型更愿意拒绝还是更愿意调用，不能保证系统不会越权。

### 8.20.3 修复顺序

第一步把外部文档标记为不可信数据，并阻止其修改工具策略；第二步在服务端按用户、租户、合同和授权版本重新校验资源；第三步为工具调用增加 operation id、幂等和 UNKNOWN；第四步保留正常敏感样本，重新训练安全替代和澄清行为；第五步把三类失败加入回归集，分别测模型、策略和执行器。

修复后再次评估，不能只看 harmful compliance。还要观察：

- 正常合同问答是否仍能引用正确版本；
- 越权合同是否被服务端阻止；
- 工具超时是否不会产生虚假确认；
- 误拒是否回到可接受范围；
- 旧缓存、旧索引和回滚版本是否不会复用错误状态。

### 8.20.4 证据边界

如果修复后在注册的租户、权限、文档版本和测试场景中没有复现越权，只能说明已覆盖故障得到缓解。它不能证明所有新网页、所有权限变化和所有长程 Agent 轨迹都安全。案例的价值是展示归因：模型训练、策略层和执行器各自承担什么责任。

## 8.21 一个最小的安全评估摘要实现

下面的代码只演示指标分母和样本分桶，不是安全分类器，也不能代替人工或专家评审。样本内容使用抽象标签，避免把危险操作写入教材。**已验证（2026-11-06；Python 3.12.9；仅标准库）**。

~~~python
from dataclasses import dataclass
from typing import Iterable


@dataclass(frozen=True)
class Case:
    kind: str
    action: str
    helpful: bool
    severity: int = 1


def summarize(cases: Iterable[Case]) -> dict[str, float | None]:
    rows = list(cases)
    harmful = [row for row in rows if row.kind == 'harmful']
    benign_sensitive = [
        row for row in rows if row.kind == 'benign_sensitive'
    ]

    harmful_compliance = (
        sum(row.action == 'harmful_answer' for row in harmful) / len(harmful)
        if harmful
        else None
    )
    over_refusal = (
        sum(row.action == 'refuse' for row in benign_sensitive)
        / len(benign_sensitive)
        if benign_sensitive
        else None
    )
    safe_helpfulness = (
        sum(row.action == 'safe_answer' and row.helpful for row in benign_sensitive)
        / len(benign_sensitive)
        if benign_sensitive
        else None
    )
    weighted_failures = sum(
        row.severity
        for row in harmful
        if row.action == 'harmful_answer'
    )
    total_weight = sum(row.severity for row in harmful)

    return {
        'harmful_compliance': harmful_compliance,
        'over_refusal': over_refusal,
        'safe_helpfulness': safe_helpfulness,
        'severity_weighted_failure': (
            weighted_failures / total_weight if total_weight else None
        ),
    }


cases = [
    Case('harmful', 'refuse', False, severity=3),
    Case('harmful', 'harmful_answer', False, severity=2),
    Case('benign_sensitive', 'safe_answer', True),
    Case('benign_sensitive', 'refuse', False),
    Case('benign_sensitive', 'safe_answer', False),
]

summary = summarize(cases)
assert round(summary['harmful_compliance'], 3) == 0.5
assert round(summary['over_refusal'], 3) == 0.333
assert round(summary['safe_helpfulness'], 3) == 0.333
assert round(summary['severity_weighted_failure'], 3) == 0.4
print(summary)
~~~

这段代码没有判断样本是否真的有害，也没有判断回答是否安全。它只把已经经过标注的结果按分母汇总；当某一类没有样本时，前三个指标返回 `None`，表示未定义，而不是把“没有观测”伪装成零。示例中的严重度加权失败率只在 `harmful` 样本内计算，分母是这些样本的权重总和；若要汇总其他风险类别或全体样本，应先定义统计范围并分别报告。加权指标还要求总权重为正，且示例中的 `severity` 已是经过标注的非负权重。真实评估还需要保存标注指南、评审者、分歧、置信度、版本和严重度来源，并对指标做置信区间和分桶分析。

这组小输入有 2 个 harmful 样本，其中 1 个给出危险回答，因此 `harmful_compliance=1/2=0.5`；3 个 benign-sensitive 样本中 1 个被拒绝，因此 `over_refusal=1/3`，1 个得到有帮助的安全回答，因此 `safe_helpfulness=1/3`。harmful 样本权重为 3 和 2，只有权重 2 的样本失败，所以严重度加权失败率是 `2/(3+2)=0.4`。函数打印的汇总结果可与这些手算分母和标签映射逐项核对。

这个教学函数只返回比例，没有把每个指标的分子、分母和样本数一起保存；真实报告应另外记录这些计数。比如同样的 8% 可能来自 `8/100`，也可能来自 `1/12`，它们的抽样不确定性和发布含义不同。报告还应保留风险分层、标签规则、评审版本和重复样本去重方式，使版本间的变化能追溯到同一统计单位和数据范围。

把这类摘要接入评估前，要先定义字段契约。`kind` 由冻结的风险分类体系指定，`action` 记录实际模型/系统行为，`helpful` 由任务级评分细则（rubric）判断，`severity` 由版本化风险标准赋值；这些标签必须来自人工或已经验证的评审流程，而不是待测模型自我声明。若工具结果为 UNKNOWN，数据表应保留 UNKNOWN，不能自动折算成成功或拒绝。还应保留样本标识（case ID）、语言、轮次、权限条件、模型和策略版本，才能按风险切片重放。

分母为空时返回 `None` 表示该指标没有观察，不等于风险为零；有 100 个禁止样本但没有一例有害遵从，才是观测到 `0/100=0%`。二者的决策含义不同。当前 `safe_helpfulness` 的分母是全部合法敏感样本；若只有部分样本适合安全替代，应另加纳入资格（eligibility）标记并按 §8.9.2 的定义报告，不能拿全体分母冒充可替代样本率。对稀有严重事件还要同时报告原始例数和不确定性，不能只用严重度加权平均隐藏个别失败。

还要在数据契约里固定“一条 Case 代表什么”。假设 100 个禁止任务展开为 140 个对话轮次，8 个任务至少出现一次有害回答，而这些任务合计出现 12 个有害回答：按任务计是 `8/100=8%`，按轮次计是 `12/140≈8.6%`。前者衡量任务是否失守，后者衡量回答轮次的失败密度；两个比例都可能有用，但必须标明统计单位。若把多轮任务直接摊平，长对话会获得更高权重，模型版本之间的轮次长度变化也会改变分母。

严重度权重同样不能替代原始失败数。再假设 100 个禁止样本中有 50 个低严重度样本、权重各为 1，50 个高严重度样本、权重各为 3；若 6 个低严重度和 2 个高严重度样本失败，原始失败率是 `8/100=8%`，加权失败率则是 `(6×1+2×3)/(50×1+50×3)=12/200=6%`。加权结果适合表达团队设定的影响权重，却不表示真实发生概率；报告应同时给出 8 个失败案例及严重度分布，便于审阅者看见汇总值掩盖的个案。

这份最小实现还假设每条记录只有一个 `kind` 和一个最终 `action`。若一次任务同时触及隐私和越权，团队应提前规定主标签，或把风险标签拆成可回溯的多标签记录，并确保同一任务不会在分母中被重复计数。执行结果为 UNKNOWN 时，它既不是安全回答也不是拒绝；应单独报告未知状态比例，再判断是否需要重试、人工核对或记作评估失败。静默地把未知折到某个已有类别，会让版本间的指标差异反映记账规则，而不是系统行为。

## 8.22 如何设计可复现的安全实验

### 8.22.1 只改变一个关键因素

安全实验很容易同时改变模型、system prompt、拒答策略、过滤器、工具权限和评审器，最后无法知道结果来自哪里。实验应先固定模型和系统，单独比较训练数据；再固定模型和数据，比较策略层；最后在真实工具和权限条件下评估组合系统。

实验开始前先把问题写成一条可证伪假设，并指定主要指标、样本池、评审规程和停止条件。例如，“在固定模型与工具权限时，新的外部内容隔离策略会降低注入导致的越权率，同时不明显降低合法网页摘要成功率”。为两项结果各定义分母，锁定测试集版本，并把调参用的开发集与最终盲测集分开。若研究的是训练数据，则模型架构、优化器、训练预算和评估提示应保持相同；若研究运行时策略，则 checkpoint、检索快照和资源上限应保持相同。否则实验只说明整个配置包变化，不能归因到其中某一个组件。

单因素对照适合回答“某项变更在当前条件下有没有影响”，但不适合忽略交互。例如安全微调单独有效、工具策略单独有效，不代表二者叠加时不会增加误拒或改变工具调用。如果预期有交互，应显式安排基线、两个单项和组合条件；运行顺序随机化或分批交错，以免硬件负载、服务版本或评审者疲劳与变体顺序重合。探索性结果可以提出假设，最终确认应使用未参与调参的样本。

每次实验至少记录：

- 模型检查点（checkpoint）和分词器摘要（tokenizer digest）；
- system/developer 配置版本；
- 训练数据和偏好数据版本；
- 评估集版本与污染状态；
- 解码、工具、RAG 和权限配置；
- 自动与人工评审规则；
- 随机种子、样本顺序和失败重试；
- 结果、分桶、置信区间和人工分歧。

### 8.22.2 配对评估

同一请求在两个版本上运行，可以减少请求分布差异。对于每个样本 i，设变体结果为 M_i^v，基线结果为 M_i^b，差值为：

~~~math
\Delta_i
=
M_i^v
-
M_i^b
~~~

再对同一分桶求平均或报告差值分布。安全任务通常不是单一连续分数，应同时比较动作类别变化，例如 allow 变 refuse、refuse 变 harmful answer、tool success 变 unknown。

举例来说，500 个配对任务中 42 个从失败变成功，27 个从成功变失败，其余 431 个结果不变。若基线成功 410 个，则候选成功数为 `410−27+42=425`，成功率由 `410/500=82%` 到 `425/500=85%`，样本差为 3 个百分点。净增加 15 个成功任务不能替代配对不确定性分析；还要按风险类别和输入家族切片。若同一模板派生出许多近似样本，重采样时应以模板/任务家族为单位，不能把高度相关的样本当成 500 个独立观察。

配对结果还要保留“变好、变差、相同”的逐样本表。上例的 42 个改善和 27 个退化给出净增 15 个成功任务，但并不单独说明差异有多稳定；不确定性计算必须保留每个样本的配对关系，并在样本共享模板或任务家族时按该家族处理相关性。若每个新版本都反复查看同一盲测集并据此调参，它就逐渐变成开发集；应冻结最终评估集和分析规则，或另取未参与选择的新样本作确认。

评审器也是实验条件的一部分。比较两个版本时，应冻结评分细则、评审模型与提示词，并随机混排匿名输出，避免评审器因先后顺序或版本名称改变判分。若中途更新了评审器或标签规则，就应使用同一套新规则重新评分基线和候选版本；否则测量器的变化会和模型效果混在一起。人工抽查也要覆盖各风险层和不同结果类别，不能只复核自动评审器已经判为高风险的样本。

### 8.22.3 评估器本身也需要评估

自动评审器的一致性、偏差、对长度和风格的敏感性，会直接影响安全结论。应使用人工金标、双评审、盲评和对抗样本测评估器；对于高严重度样本，不能因为自动评审器给出低风险就跳过人工复核。

例如人工仲裁 200 条样本，其中 100 条确属禁止请求、100 条为合法敏感请求；自动评审器正确识别 90 条禁止样本，并把 20 条合法样本误报为禁止，则整体一致数为 `90+80=170`，准确一致率为 `170/200=85%`。但同一张表还显示禁止样本漏掉 `10/100=10%`，合法样本误报 `20/100=20%`。单独报告 85% 一致率无法告诉发布决策者漏检集中在哪类高严重度样本，因此要保留混淆矩阵、分层灵敏度/特异度和人工分歧；金标本身也要说明来源与仲裁方式。

### 8.22.4 从指标到决策

结果报告应把“观察到什么”和“因此允许什么”分开。例如 harmful compliance 下降，但 over-refusal 上升，可能允许低风险聊天灰度，却不允许扩大工具权限；工具越权率未测量，则不能宣称 Agent 安全；隐私评估只有合成数据，则不能推断真实客户数据风险。

安全决策需要保留未测量项目和剩余风险。没有证据的地方应写成未知，而不是默认为通过。

发布门槛应在看结果前写好，分成硬门槛和可权衡指标。越权、未授权副作用或高严重度隐私泄露可以作为停止扩量的硬条件；误拒、延迟和成本则按产品目标设定可接受范围。候选版本若危险样本表现改善但正常求助误拒增加，可以在只读低风险场景进行小比例灰度，同时保持写操作权限不变；如果 Agent 越权评估没有数据，就不能把“有害遵从下降”解释成允许加大工具权限。灰度要对齐模型、提示、工具 schema、权限策略和索引版本，出现预设停止信号时回滚整个相关配置，并保留失败样本进入后续回归。

评估集可按风险严重度、任务合法性、语言、轮次和工具权限分层抽样，再保留真实流量权重用于总体估计。若为测到低频风险而对高风险样本过采样，不能直接把样本集上的未加权比例称为线上发生率；需要说明抽样概率，并在适用时按目标分布加权。对无法可靠估计发生率的场景，报告“在这些授权条件下复现/未复现哪些失败”比伪造总体百分比更准确。

“零次失败”也要带上样本数和检测能力。例如 0/30 次测试通过，只能说明这 30 个已覆盖场景未观察到失败；若漏报概率未知，不能写成风险为零。运行监控与离线评估互补：前者发现分布漂移和未登记事件，后者在固定条件下做对照。每次发布决策都应说明两类证据各自覆盖什么，以及剩余风险由谁接受、在什么信号出现时撤销。

## 8.24 结语：安全是可被复核的系统属性

对齐不是把模型变得更顺从，安全也不是把拒答率调到最高。真正重要的是，模型是否理解任务和边界，是否在不知道时诚实，是否能在风险可控时继续帮助，是否在高影响动作前受到系统级约束，失败后是否留下足够证据，组织是否能修复、回滚和承担后果。

训练方法改变行为倾向，奖励和偏好只是代理信号；评估和红队发现失败，但不能证明未来没有新失败；权限、沙箱、幂等和人工确认限制影响；model card、system card、灰度和事故响应把技术判断连接到发布责任。

当一个安全结论能够说明测试对象、输入分布、工具权限、评审规则、分母、严重度、未覆盖范围和后续动作时，它才具备工程价值。模型可以继续变强，系统也必须同步提升证据质量和失效控制能力。第 9 章将转向多模态与研究工作，继续讨论模型能力如何在不同数据形态和研究证据中被验证。
