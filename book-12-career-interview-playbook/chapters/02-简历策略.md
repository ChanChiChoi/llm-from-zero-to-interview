# 第二章：简历策略

简历是求职者和一个陌生团队第一次交换信息的地方。它既不是自传，也不是知识点目录，更不是把所有做过的事情按时间顺序堆在一起的档案袋。它是一份有明确读者、有限篇幅和现实后果的证据文档：读者需要在很短时间内判断你适合什么方向，哪些经历值得继续追问，以及你对自己写下的内容是否负得起责任。

这件事在大模型岗位上尤其困难。候选人使用的词汇高度相似，几乎每份简历都可能出现 Transformer、PyTorch、RAG、LoRA、DPO、vLLM 或多模态。技术名词能说明你进入过某个领域，却不能说明你曾经在什么约束下做过什么决定，也不能说明结果是否可信。真正有区分度的内容往往藏在名词后面：数据是怎样来的，基线是什么，瓶颈如何定位，指标的分母是什么，失败后改了什么，个人贡献和团队成果如何分开。

第 1 章负责帮助读者判断目标岗位，第 3 章会继续讨论进入面试后怎样展开一个项目。本章解决一个更具体的问题：怎样让简历在有限空间里准确地告诉对方，哪些问题你做过、做到什么程度、为什么值得进一步了解。

## 2.0 简历先要回答：为什么是你

### 2.0.1 小白视角：简历不是把“我会的”全部列出来

刚开始找工作的读者常常把简历理解成一张技能证明表。学过一个技术，就想把它写上去；跑过一个 demo，就想写“熟悉”；读过一篇论文，就想写“掌握”。这种做法很自然，因为学习过程本来就是按知识点积累的。

招聘阅读却是反过来的。读者先看到一个岗位要解决的问题，再寻找候选人是否有相关证据。一个研究岗位会寻找问题定义、实验和机制判断；一个推理岗位会寻找性能瓶颈、硬件约束和线上可靠性；一个 Agent 岗位会寻找任务成功、工具权限和失败恢复。简历如果只有技能名词，读者还得自己猜这些名词和岗位的关系，很多信息会在猜测之前就被略过。

因此，写简历前先完成一次转换：

~~~text
我学过什么
        -> 我用它解决过什么问题
        -> 我在什么约束下做出什么选择
        -> 结果如何被测量
        -> 哪些结果可以由我本人解释和承担
~~~

最后一行非常重要。简历上的内容不是为了让读者相信你无所不知，而是为了让读者知道从哪里开始和你进行一次真实的技术对话。

### 2.0.2 专家视角：简历是在有限带宽上优化信号

可以把简历阅读看成一个有限带宽的信息传输问题。页面空间有限，读者时间有限，候选人的经历又包含大量只有在追问中才有意义的细节。简历需要选择那些既与岗位相关、又足够具体、还能被核验的信号。

一个帮助写作者自查的教学化表达是：

~~~math
S(b) = \frac{R(b) \cdot D(b) \cdot V(b)}{K(b)}
~~~

这里的 b 表示一条简历 bullet；R(b) 表示与目标岗位的相关性，D(b) 表示具体程度，V(b) 表示可验证性，K(b) 表示读者理解它所需要的阅读成本。这个式子不是招聘系统的真实评分函数，也不能计算出录用概率。它只是说明为什么“我熟悉很多工具”通常不如“在长上下文请求的 p99 延迟约束下，我定位到 prefill 排队是主要瓶颈，并通过长度分桶和批处理调整降低了尾延迟”更有信息量。

相关性低，技术再先进也不一定有用；具体程度低，读者无法区分你的贡献；可验证性低，数字和结论无法承受追问；阅读成本太高，重要信息可能还没有出现就被跳过。简历策略的核心就是在这四者之间取得平衡。

### 2.0.3 简历和项目讲述的边界

简历不能承载一个项目的全部历史。它只需要留下足以建立判断的骨架：场景、问题、关键动作、结果和个人边界。面试中的项目讲述再去展开候选方案、失败实验、日志、数据切片和下一步。

可以用一个简单的比喻理解两者关系。简历像一本书的目录和封面之间的导读，读者从中判断先读哪一章；项目讲述像真正打开某一章，沿着因果链把事实讲完整。导读不能写成空洞广告，正文也不能只重复导读。

本章后文会反复提醒这一点：简历中的一句话必须足以让人知道项目值得问什么，但不应把无法在一页中证明的宏大结论写死。

## 2.1 先做一份主简历，再生成目标版本

### 2.1.1 为什么不应该只有一份固定简历

同一个人的经历，对不同岗位有不同的解释重点。一个企业知识库项目，投评估岗时可以突出评测集、人工 rubric、引用支持和错误分析；投推理岗时可以突出上下文长度、prefill、缓存、p95 延迟和成本；投 Agent 岗时可以突出工具调用、权限、状态和任务恢复。这不是虚构经历，而是让读者先看到与职位最相关的那条因果链。

Harvard College 和 MIT Career Advising 的公开简历资料都建议根据目标职位调整内容，而不是把所有经历原样投给所有岗位。这个建议并不意味着每次都要重写事实。更稳妥的做法是维护一份内容完整、事实经过核对的主简历，再根据岗位选择顺序、篇幅和表述重点。

主简历可以包含：

1. 所有教育、工作、研究、开源和个人项目的真实记录。
2. 每个项目的完整事实卡，包括规模、时间、基线、方法、指标、个人贡献和保密等级。
3. 每项技术的证据等级，是读过、复现过、独立负责过，还是产生过真实影响。
4. 指标的原始口径和计算方式，避免以后凭记忆改写数字。
5. 公开链接、论文状态、代码仓库和可展示材料。

目标简历只是主简历的一个视图。它不应增加主简历中不存在的事实，也不应因为职位描述里出现某个词，就把浅尝辄止的经历升级成“精通”。

### 2.1.2 把职位描述转换成选择规则

第 1 章已经把职位描述中的动词、交付物和失败模式拆开。现在要把它们落到简历编辑上。

假设目标岗位的公开描述反复出现 design experiments、debug regressions 和 improve model behavior。三组动词对应的简历证据不是三个技术名词，而是：

- 设计实验：写出假设、对照和结果，说明你不是只执行别人给的配置。
- 调试回归：写出异常表现、排查信号和修复后的验证，说明你能处理反常结果。
- 改善行为：写出行为指标、错误切片和副作用，说明你关注的是模型在任务中的表现。

再假设另一个岗位反复出现 latency、throughput、GPU memory 和 production distributed systems。简历优先展示的应是请求分布、性能基线、瓶颈定位、服务指标和线上稳定性，而不是把 SFT、DPO、RAG 全部放在最上方。

可以为每个目标岗位建立一张选择表：

| 岗位要求 | 简历中应出现的证据 | 不足时的诚实写法 |
| --- | --- | --- |
| 大规模训练 | 训练规模、并行、稳定性、恢复和监控 | “在多卡受控实验中负责并行和恢复，尚无长周期预训练经验” |
| 模型行为改进 | 行为问题、数据、训练方法、分桶评估和副作用 | “完成公开数据复现，尚未负责线上模型行为迭代” |
| 评估系统 | 构念、样本、评分协议、校准和回归 | “实现自动评测流水线，正在补人工一致性分析” |
| 推理优化 | 输入输出分布、瓶颈、延迟、吞吐、质量和成本 | “在本地压测验证量化影响，尚未承担生产流量” |
| Agent 可靠性 | 任务成功、工具契约、权限、幂等和恢复 | “完成原型状态机和仿真轨迹，尚无真实副作用工具上线” |

最后一列不是自我贬低，而是防止把证据边界隐藏在漂亮的标题后面。明确缺口后，读者反而更容易判断你适合什么级别和什么团队。

### 2.1.3 一个岗位版本只保留一条主线

一页简历不适合同时承担八个方向的主要证明责任。它可以展示跨领域能力，但读者应当在第一页的前几行就看出你的主线。

一个实用原则是：选择一个主方向，最多保留一个相邻方向。比如训练研究加训练系统，Post-training 加评估，推理部署加系统设计，Agent 应用加 RAG，多模态研究加评估。

主方向回答“我希望被如何理解”，相邻方向回答“我能和哪些团队协作”。如果把所有方向都写成主方向，读者得到的不是广度，而是缺少优先级。

## 2.2 简历的结构：先让信息可见，再让事实有说服力

### 2.2.1 顶部区域要完成定位

简历顶部通常包含姓名、联系方式、所在地或工作许可信息，以及一行简短定位。定位不是口号，而是读者接下来应采用的阅读视角。

空泛的定位：

~~~text
热爱人工智能，具有扎实算法基础和强烈学习能力。
~~~

它没有提供可比较的事实，也没有告诉读者你适合哪个方向。

更具体的定位：

~~~text
大模型 post-training 方向候选人，主要经历包括 7B 模型 SFT/DPO、偏好数据构建和安全行为评估。
~~~

或者：

~~~text
偏训练与推理工程方向，做过 PyTorch/FSDP 多卡训练、自动评估和流式推理延迟优化。
~~~

定位最好由方向、证据和边界组成。若还没有工业经验，可以明确写“公开模型复现”“研究型项目”或“课程项目”，让读者不要用生产级标准误读你的经历。

### 2.2.2 经历排序服务于阅读顺序

简历的阅读顺序不是履历的自然顺序。最相关、最能代表目标方向的经历应该更早出现，即使它不是时间上最近的一段。

常见结构可以是：

1. 联系方式和一句话定位。
2. 最匹配岗位的教育或工作经历。
3. 两到四个最强项目。
4. 论文、开源、竞赛或公开技术产出。
5. 技能和补充信息。

对研究岗位，论文或研究项目可能比一段无关的实习更应该靠前；对工程岗位，生产系统和性能贡献可能比课程成绩更重要；对在读学生，教育经历和研究项目通常应放在前部。顺序不是固定模板，原则是让重要证据最先被看到。

### 2.2.3 一页还是两页，要看证据密度

简历页数没有脱离场景的绝对答案。MIT 的公开资料建议多数候选人使用一页，只有经历较多或拥有高级学位等情况才考虑更长版本；Harvard 的资料强调简洁、易扫读、结果明确和格式一致。对于研究人员、博士后或拥有多年工业经历的人，两页可能是合理的；对于只有几个项目的初学者，两页往往只是把空泛内容拉长。

决定页数时可以问：第二页是否包含新的、与岗位相关且可追问的证据？如果只是重复技能、课程和形容词，就应该删掉。宁可留下一个能讲深的项目，也不要用低信息量段落填满页面。

### 2.2.4 让人和解析软件都能找到信息

很多公司会使用简历管理或解析系统，但不同系统的实现和容错能力并不相同。不能把“通过某个解析器”当成录用条件，也不能因为担心机器解析就使用复杂的图形设计。更稳妥的做法是采用标准标题、清晰的文本层次、单栏或简单双栏结构，避免把关键经历放进图片、复杂表格、页眉页脚或无法复制的文本框。

提交 PDF 前，至少做一次文本抽取检查：复制全文到纯文本编辑器，看姓名、日期、职位、项目标题、指标和链接是否仍按合理顺序出现。再用不同阅读器打开，检查字体替换、换行、中文字符、英文大小写和链接是否正常。

这不是为了迎合一个神秘的筛选规则，而是为了降低机器和人共同面对的解析歧义。视觉上很漂亮但复制后顺序混乱的简历，往往也会让人工读者难以定位事实。

### 2.2.5 日期、地点和格式要保持一致

读者不应该把注意力花在猜测日期格式上。所有经历使用同一套年月格式，职位、团队和项目名称的层级一致，指标的单位统一，英文技术名词的大小写稳定。Harvard 的公开建议也强调格式一致、信息易读和按重要性组织。

一致性不代表把所有内容排成没有重点的网格。标题可以强调，关键结果可以突出，但强调规则应固定。一个项目的年份在右侧，另一个项目的年份藏在描述中，会增加阅读成本，也可能让经历顺序产生误解。

## 2.3 一条简历 bullet 怎样构成完整证据

### 2.3.1 从职责句到结果句

最弱的简历句子通常只是岗位描述的复制：

~~~text
负责模型训练、数据处理和效果评估。
~~~

它可能完全真实，却没有回答规模、目标、个人动作和结果。更具体的写法是：

~~~text
负责 13B 模型预训练的异常定位模块，关联 loss、梯度范数、数据 shard、吞吐和显存曲线，定位坏样本与混合精度溢出两类 loss spike，使长周期训练中断次数下降约 40%。
~~~

这条句子仍然可以被继续追问，但它已经提供了追问入口：异常如何定义，怎样区分两类原因，告警的误报情况是什么，下降的分母是什么，作者个人写了哪些组件。

### 2.3.2 一条 bullet 的六个部件

可以把一条高质量经历句拆成六个部件：

1. 场景或对象：什么模型、数据、服务或用户任务。
2. 问题或约束：质量、延迟、成本、稳定性、安全或研究不确定性。
3. 个人动作：你实际设计、实现、分析或推动了什么。
4. 方法依据：用了什么方法，以及为什么适合这个问题。
5. 结果和口径：哪个指标发生了怎样的变化，怎样测出来。
6. 证据边界：这是公开实验、内部离线结果、线上 A/B，还是项目实测。

不必每条句子都把六个部件写满。一页简历需要压缩，但至少要让对象、个人动作和结果可见。背景很复杂时，可以把约束放在项目标题或第一条 bullet，把方法和结果分到后续句子。

### 2.3.3 用动作动词，但不要用动词掩盖贡献

Harvard 和 MIT 的简历资料都建议使用具体的主动动作词。对大模型岗位，动作词可以帮助读者区分工作类型：

| 动作 | 更适合描述的事实 |
| --- | --- |
| defined / framed | 定义问题、构造目标和成功标准 |
| designed | 设计实验、数据协议、系统或评估 |
| implemented | 编写代码、流水线、服务或工具 |
| diagnosed | 通过信号定位异常和根因 |
| compared / ablated | 做受控对比和消融 |
| optimized | 在约束下改善性能、成本或质量 |
| evaluated | 构造样本、评分、校准和错误分析 |
| deployed / operated | 灰度、监控、回滚和长期维护 |
| documented / enabled | 沉淀规范、工具和团队复用能力 |

这些词只有在后面的事实支持时才有价值。“主导”“推动”“负责”都不是结果本身。比如“主导模型优化”不如“设计三组数据配比实验并负责评估和回归分析”具体；“推动上线”不如“完成灰度监控、回滚演练并将 p99 超时率控制在目标内”可核验。

### 2.3.4 把技术名词嵌入因果链

关键词需要出现，但应当服务于事实：

~~~text
基于 PyTorch 和 FSDP 完成 7B 模型 SFT，使用 LoRA 控制可训练参数规模，并通过 sequence packing 和梯度累积提升有限显存下的有效 token 吞吐。
~~~

这句话仍需要在面试中补充数字，但已经说明了工具、方法和约束之间的关系。相反，下面的技能列表没有告诉读者任何使用场景：

~~~text
熟悉 PyTorch、FSDP、DeepSpeed、LoRA、DPO、RAG、MoE、vLLM 和 FlashAttention。
~~~

技能栏可以存在，但它应该是正文经历的索引，而不是正文的替代物。一个很好的自查方法是删除技能栏后，读者是否仍能从项目描述中看出你的主线；如果完全看不出，说明项目句子还没有承载足够事实。

## 2.4 指标不是装饰：先审计口径，再决定写不写

### 2.4.1 一个数字至少要带着五个问题

“准确率提升 15%”看起来有冲击力，但它可能有多种含义。写进简历前，至少要能回答：

1. 基线是什么，是旧模型、旧系统、人工流程还是未经处理的数据？
2. 分母是什么，15% 是相对提升还是 15 个百分点？
3. 样本是什么，规模、来源、时间和切片如何？
4. 协议是什么，自动指标、人评、A/B、压测还是日志统计？
5. 代价是什么，延迟、成本、安全、覆盖或另一个任务是否退化？

如果这些问题无法回答，数字可能仍然可以保留，但应降低表述强度，例如写成“在内部验证集上观察到约 15% 的相对改善”，并准备在面试中说明它不是线上结论。

### 2.4.2 相对提升和百分点不是一回事

假设旧版本准确率为 0.70，新版本为 0.80。百分点变化是 10 个百分点，相对提升则是：

~~~math
\Delta_{pp} = 100 \times (m_{new} - m_{base})
~~~

~~~math
\Delta_{rel} = \frac{m_{new} - m_{base}}{m_{base}},
\qquad m_{base}\ne0
~~~

因此这个例子对应 10 个百分点和约 14.3% 的相对提升。二者都可以报告，但必须写清楚。对于错误率从 0.20 降到 0.10，通常说“下降 10 个百分点”或“相对下降 50%”；不能把两种说法混成“提升 50 个百分点”。

### 2.4.3 质量指标要说明正负方向

有些指标越高越好，例如任务成功率和召回率；有些指标越低越好，例如延迟、成本、幻觉率和误拒率；有些指标需要同时看，例如安全拒答率和正常请求误拒率。

可以用统一的变化记法避免歧义：

~~~math
Gain_{good} = \frac{m_{new} - m_{base}}{m_{base}},
\qquad m_{base}\ne0
~~~

~~~math
Gain_{bad} = \frac{m_{base} - m_{new}}{m_{base}},
\qquad m_{base}\ne0
~~~

对于低值更好的指标，第二个式子在下降时为正。简历不一定要展示公式，但写作者必须知道自己在说什么。尤其是安全项目，单独写“拒答率提升”并不能说明系统更安全，因为正常请求的误拒也可能同步提升。

### 2.4.4 业务指标和模型指标要连起来

模型指标是中间证据，业务指标是更远的结果。二者之间通常有多层转换，不应直接写成因果关系。

例如：

~~~text
引用支持率从 0.62 提升到 0.81
        -> 人工评审中的可信回答比例上升
        -> 客服转人工率下降
~~~

中间每个箭头都需要证据。离线引用支持率提升，可能没有改变转人工率；转人工率下降，也可能受到培训或流程变化影响。更谨慎的简历写法是：

~~~text
在固定知识库和人工抽样评估中，将 claim 级引用支持率从 62% 提升至 81%；灰度期间客服转人工率下降 18%，同时监测到 p95 延迟保持在 3.2 秒以内。
~~~

如果没有 A/B 或足够的因果设计，就不要写“因此导致”。写“同期观察到”或“与……同时变化”更准确。

### 2.4.5 用任务成功成本衡量系统价值

大模型项目经常出现“每次请求更便宜，但用户更难完成任务”的情况。仅写 token 成本会把失败请求和人工接管的代价隐藏起来。

一个教学化的单位成功任务成本可以写成：

~~~math
Cost_{success} = \frac{C_{model} + C_{retrieval} + C_{tool} + C_{human} + C_{failure}}{N_{success}}
~~~

分子包含模型、检索、工具、人工和失败处理的总成本，分母是成功完成任务的数量，因而要求 `N_success > 0`。若观察窗口内没有成功任务，应写“无成功任务，单位成功成本未定义”，不能把它填成零；若连请求样本都没有，则连总成本也不能解释为零。这个式子不要求求职者在简历中披露所有内部成本，但它帮助你选择更有意义的指标：如果模型路由把平均 token 成本降了 20%，同时任务成功率从 80% 降到 60%，单位成功任务成本可能反而上升。

### 2.4.6 指标数字的可信度等级

可以给自己的每个数字标上证据等级：

| 等级 | 典型来源 | 简历中的合适表述 |
| --- | --- | --- |
| A | 公开论文或开源复现实验，有固定协议 | “在公开数据和固定协议下……” |
| B | 团队离线实验，有版本和基线记录 | “在团队离线评估中……” |
| C | 灰度或 A/B，有分桶和持续时间 | “在灰度期间，按……分桶观察到……” |
| D | 线上长期指标，口径和个人贡献清晰 | “上线后……指标从……变为……” |
| E | 个人印象或一次 demo | 不宜写成确定的量化成果 |

等级不是价值排序。研究型岗位可能更看重 A，部署岗位更看重 C 和 D；关键是表述不能超过证据等级。一次 demo 可以作为项目事实，但不应写成“提升线上效果”。

## 2.5 把论文、工程和数据贡献写成不同类型的证据

### 2.5.1 论文经历：强调问题和你真正做的部分

论文条目不应只包含题目、会议和 SOTA。读者更关心你在论文中承担了什么工作，以及你能否解释方法和实验。

一条研究经历可以包含问题、方法差异、实验和个人角色：

~~~text
针对低资源领域适配中的过拟合问题，设计基于验证集不确定性的 LoRA rank 分配策略；负责方法实现、训练代码和消融实验，在 5 个领域分类任务上平均提升 2.3 个百分点，并验证该收益主要出现在小样本分桶。
~~~

这里的“平均提升”仍需要在附加材料或面试中说明基线、任务数量、方差和是否为百分点。如果论文正在投稿，应写“研究项目”“预印本”或“投稿中”，不要把状态写成已发表。

论文贡献还要区分作者身份和实际贡献。一作不意味着每个模块都是一人完成；共同作者也可能承担核心方法或实验。简历中最有价值的不是把作者顺序放大，而是把你负责的事实写清楚。

### 2.5.2 工程经历：强调改变了什么状态

工程贡献的价值不在于代码行数，而在于系统状态发生了可验证变化。可以从五种状态变化中寻找证据：

1. 更快：吞吐提高，构建或评估时间缩短，尾延迟下降。
2. 更省：显存、GPU 小时、存储或单位请求成本下降。
3. 更稳：故障率、恢复时间、数据丢失和回滚风险下降。
4. 更清楚：日志、追踪、配置和实验血缘让问题可定位。
5. 更可复用：组件、数据协议或评估流水线被其他项目采用。

例如，单写“搭建自动评估平台”信息不足；如果事实确实存在，可以写成：

~~~text
构建覆盖知识问答、代码、数学和安全行为的自动评估流水线，固定 prompt、采样参数、模型版本和结果存储，使一次迭代评估从人工约 2 天缩短至约 3 小时，并将错误样本回流到回归集。
~~~

这条经历仍然需要在面试中回答“自动评估怎样校准”。简历的目的不是替你完成回答，而是准确指出你做过的工作。

### 2.5.3 数据经历：强调分布、质量和后果

数据岗位的简历很容易写成“采集、清洗、标注、去重”。这些动作只有和目标及模型结果连接起来才有区分度。

~~~text
负责领域 SFT 数据管线，按来源、语言、任务类型和风险等级建立版本统计；通过近重复检测和人工抽检清理高频模板，补充长尾拒答与工具轨迹样本，并在固定 holdout 上验证数据配比变化对任务成功率和误拒率的影响。
~~~

如果没有模型训练结果，也可以诚实写数据资产本身的影响，例如版本可追溯、标注一致性提高或重复劳动减少，但不要把数据清洗直接写成“模型能力提升”。

### 2.5.4 产品影响：区分相关变化和因果结果

用户采纳率、留存、转人工率和满意度通常受到多个因素影响。简历可以报告它们，但需要说明是 A/B 结果、灰度观察还是同期变化。

当无法公开完整实验时，可以写：

~~~text
在固定模型、提示和知识库版本的灰度实验中，按用户类型和任务类别分层比较；目标流程的任务完成率提高 8 个百分点，p95 延迟无显著变化，长尾问题仍未纳入结论。
~~~

如果只是一次发布后的前后对比，应写清“发布后观察到”，不要暗示严格因果。专家读者会更看重这种边界意识，而不是一个未经说明的大数字。

## 2.6 技术关键词：让检索找到你，让证据留住人

### 2.6.1 关键词有三种用途

技术关键词通常承担三种不同作用。

第一，帮助招聘人员快速判断领域，例如 training、post-training、inference 或 evals。第二，帮助简历解析和搜索系统定位候选人。第三，为面试深挖提供入口。三种用途不能混为一谈：关键词可以帮助你被找到，却不能替代经历；一个词写在技能栏里，也不等于你能够承担它代表的工作。

可以把关键词分三层：

| 层次 | 示例 | 写作要求 |
| --- | --- | --- |
| 原理层 | attention、optimization、distributed systems、evaluation | 用项目或论文说明理解了什么机制 |
| 方法层 | LoRA、QLoRA、SFT、DPO、RAG、MoE、quantization | 说明在哪个问题和数据上使用 |
| 工具层 | PyTorch、FSDP、DeepSpeed、vLLM、Kubernetes | 说明负责的组件、指标或运行环境 |

例如“PyTorch、FSDP、LoRA”三个词本身几乎没有信息；“基于 PyTorch/FSDP 完成多卡 SFT，使用 LoRA 控制显存，并通过梯度累积和 packing 提升有效 token 吞吐”才建立了上下文。

### 2.6.2 不同熟练程度要用不同动词

简历不需要把所有技术都写成“熟悉”。可以使用更精确的表达：

- 读过：理解方法提出的动机和适用边界。
- 复现：在公开数据和固定配置上复现实验，记录资源和结果。
- 使用：在一个项目中调用或集成某工具，负责明确模块。
- 负责：独立设计、实现、排查并维护某部分。
- 贡献：结果被团队采用，或对质量、成本、稳定性产生可核验影响。

“使用”并不比“负责”低级，只是事实不同。一个诚实的“在公开数据上复现 DPO 并完成偏好偏差分析”，比模糊的“精通 RLHF/DPO”更能建立信任。

### 2.6.3 不要为了关键词创造不存在的经历

职位描述里出现一个新模型或新框架时，最危险的反应是把博客阅读改成项目经验。正确的做法是区分：

~~~text
看过：理解方法提出的动机和公开实验。
跑过：在公开实现上复现实验，记录资源和结果。
改过：修改实现并做了受控实验。
用过：在自己的项目中将它接入一个真实任务。
负责过：对模块和结果承担长期责任。
~~~

这五种说法都可以写入主简历的证据卡，但目标简历只选择和岗位相关、且足够强的层次。不能因为某个关键词很热门，就把低层证据写成高层证据。

## 2.7 保密、隐私和可核验性之间的平衡

### 2.7.1 不能公开的数字不等于不能写经历

大模型项目常常涉及未发布的模型规模、内部数据、客户名称、流量、成本和安全事件。简历既不能泄露机密，也不应因为不能写精确数字就把整个项目删掉。

可以采用四种替代方式：

1. 区间：例如“十亿级参数”“数十卡”“日均百万级 token”。
2. 相对变化：例如“p95 延迟下降约 30%”。
3. 脱敏对象：例如“企业知识库”“高风险客服场景”“内部评估集”。
4. 证据类型：例如“在固定离线集上”“灰度期间”“公开数据复现”。

但脱敏不能改变事实。如果原项目只有离线压测，就不能把“生产流量”隐藏；如果你只负责数据评估，就不能因为团队模型上线而写成“推动模型上线”。

### 2.7.2 PII 和客户信息要从源头排除

简历是公开传播概率很高的文档。客户姓名、电话号码、内部 URL、访问令牌、真实对话、未脱敏截图和安全漏洞细节都不应出现在其中。即使读者是潜在雇主，也不意味着你可以把前公司的机密当成能力证明。

一个安全的项目描述应当让读者理解问题和规模，但不能通过它反推出个人、客户或系统的敏感信息。截图尤其容易泄露信息，因为打码区域可能被复制、图层可能仍然存在，或者上下文中包含其他字段。优先使用文字描述和经过确认的公开材料。

### 2.7.3 可核验不等于必须公开全部证据

可核验是指你能在适当的后续环节解释结果来源，而不是把内部日志上传到公共仓库。准备主简历时，可以为每条经历记录内部证据位置、可展示版本和保密限制；投递版本只呈现允许公开的部分。

例如：

| 事实 | 主简历记录 | 投递简历表述 |
| --- | --- | --- |
| 内部 13B 训练 | 具体 run、配置、事故记录 | “13B 级模型多卡训练稳定性优化” |
| 客户知识库 | 客户名称和合同不可公开 | “企业制度问答场景” |
| 线上指标 | 精确流量受保密约束 | “灰度期间任务完成率提高约 8 个百分点” |
| 安全事件 | 细节不能公开 | “修复一类越权缓存问题并补充回归测试” |

这样既保留了真实性，也避免把保密义务变成装饰。

## 2.8 不同背景的简历应当证明什么

### 2.8.1 应届生：证明学习和研究可以转成结果

应届生没有工业级流量或万卡训练并不意味着简历没有内容。真正需要证明的是：你能理解问题，写出可靠实现，控制实验变量，解释失败，并且能把结果记录下来。

不要写“阅读多篇大模型论文”，因为阅读数量很难核验。可以写：

~~~text
复现 LoRA、QLoRA 和 DPO 在 7B 开源模型上的训练流程，比较 rank、学习率和数据规模对效果、显存和过拟合的影响，整理 20 余组失败配置并完成跨领域 holdout 评估。
~~~

如果使用合成数据或公开代码，应明确说明；如果没有真实产品影响，可以写实验结论、代码质量、公开复现和报告，不要把个人实验包装成生产系统。

### 2.8.2 有算法经验但非大模型背景：证明迁移能力

推荐系统、搜索、传统 NLP、CV 或语音背景都可以迁移到大模型岗位，但迁移不是把旧项目强行换成新名词。

推荐系统经历中的召回、排序、分层评估和在线实验，可以帮助申请 RAG、评估或应用算法岗位；CV 经历中的表示学习、数据增强、时空建模，可以帮助申请多模态岗位；分布式服务经历中的容量、可观测性和故障处理，可以帮助申请推理部署或 Agent 平台岗位。

好的写法先保留旧领域的事实，再突出可迁移的机制：

~~~text
负责推荐排序模型迭代，建立离线指标、线上 CTR 和用户分层分析闭环；通过实验对照定位长尾用户退化，并据此调整采样与排序特征。
~~~

这条经历不需要冒充大模型项目。它已经证明了实验、分层分析和线上闭环，是后续补大模型实现时可以复用的能力。

### 2.8.3 工程背景转算法岗：补上模型行为证据

工程背景是大模型团队需要的能力，但工程转算法不能只证明“我会写服务”。至少要补充一个完整的模型项目和一个评估或错误分析项目，说明你理解模型目标、数据变化和行为结果。

工程经历可以突出分布式系统、高并发、GPU 性能、数据平台、可观测性和自动化，然后在大模型项目里把这些能力落到具体约束。例如：

~~~text
在流式推理服务中负责请求调度和观测，按输入长度拆分 prefill 与 decode 负载，定位排队时间是 p99 延迟主要来源；通过长度分桶和批处理策略调整降低尾延迟，同时用固定质量集检查输出退化。
~~~

这里同时出现了系统和模型证据。没有质量回归时，性能优化可能只是在更快地产生错误答案；没有系统约束时，模型实验也可能无法服务真实请求。

### 2.8.4 已有大模型工业经验：把规模写成判断

有工业经验的候选人容易出现两个极端。一种是只写“参与大模型项目”，把真正的规模和影响藏起来；另一种是把团队所有成果写成个人主导，导致一追问就无法解释。

工业经历应当写出规模、复杂度、关键决策、影响和个人边界。不能公开时使用区间或相对变化，但仍要说明评估类型和责任范围：

~~~text
负责企业助手的混合检索与引用评估，针对实时制度更新设计版本化索引和权限后过滤；在固定离线集与灰度样本上分别观察引用支持率和任务完成率，发现新版 reranker 虽提高召回但使 p95 延迟上升，最终只对长尾高风险查询启用。
~~~

这条经历没有泄露客户或模型细节，却保留了问题、决策、评估和取舍，足以支撑技术交流。

## 2.9 一页简历的取舍方法

### 2.9.1 删除不是损失，而是选择读者的路径

一页简历放不下所有经历。删除内容时不要按“我喜不喜欢”决定，而要问三件事：

1. 它是否支持目标岗位主线？
2. 它是否提供新的证据，而不是重复另一条经历？
3. 它是否值得读者为它付出阅读和追问成本？

如果三个问题中有两个答案是否定的，通常应该删掉、合并或移到补充材料。一个无关的奖项可能比一条高质量失败实验更占空间，却不能帮助读者理解你的技术判断。

### 2.9.2 先保留不可替代的事实

不可替代的事实包括：你独立提出的研究问题、负责过的故障修复、可验证的性能变化、公开论文或代码、长期维护的系统、跨团队采用的工具和真实的产品结果。

可替代的内容包括：泛泛的课程列表、没有结果的职责、重复出现的技能、和目标岗位无关的早期经历以及“热爱、积极、优秀”等没有证据的形容词。

### 2.9.3 第一页应当形成闭环

第一页最好让读者能回答：你投什么方向，最强证据是什么，结果有多大，个人贡献在哪里。不是所有人都需要在第一页放完整教育经历或全部论文；应届生和研究候选人的排序可以不同，但第一屏必须有主线。

可以把第一页想象成一个最小可行判断：即使读者暂时不看第二页，也能知道是否值得继续了解你。第二页再承载补充论文、工具、早期经历或更完整的技术细节。

## 2.10 四类经历的简历条目示例

下面的例子都是教学示例，数字用于展示口径写法，不代表真实项目结果。真实简历只能使用自己的数据。

### 2.10.1 Post-training 项目

职责式写法：

~~~text
参与 7B 模型微调，使用 LoRA 和 DPO 优化问答效果。
~~~

证据式写法：

~~~text
负责企业问答模型的 SFT/DPO 数据与评估，清理近重复问答并补充证据不足时的拒答样本；在固定领域 holdout 上将可用率从 71% 提升至 84%，同时按任务类型检查误拒和引用支持，未将结果外推为线上提升。
~~~

后一种写法的重点不是句子更长，而是它说明了数据动作、评估边界和副作用检查。若候选人没有负责训练，只负责数据和评估，应把“负责”进一步改为“负责数据与评估”，不要借算法名词扩大职责。

### 2.10.2 推理优化项目

职责式写法：

~~~text
使用 vLLM 部署模型，优化推理速度。
~~~

证据式写法：

~~~text
负责流式推理服务的长度分桶与批处理实验，按输入和输出 token 分布拆解排队、prefill 和 decode 延迟；在固定质量回归集上无明显退化的条件下，使 p95 延迟下降 28%，吞吐提高 19%，并保留高风险长请求的独立限流策略。
~~~

它没有把 vLLM 当成成果，而是把工具放在问题、测量和约束中。如果没有线上流量，应写“压测”或“离线基准”，不能省略环境。

### 2.10.3 评估项目

职责式写法：

~~~text
搭建大模型自动评测平台，支持多个 benchmark。
~~~

证据式写法：

~~~text
设计覆盖知识问答、代码、数学和安全行为的评测协议，固定模型版本、提示、采样参数和评分规则，并用人工抽样校准 LLM judge；将模型回归从发布前一次性检查改为每次迭代自动执行，沉淀 300 余条带错误类别的回归样本。
~~~

如果评测平台没有改变模型分数，不代表没有价值。自动化、协议固定和错误样本回流本身就是工程影响；只要不要把“覆盖多个 benchmark”写成“证明模型全面提升”。

### 2.10.4 数据项目

职责式写法：

~~~text
负责数据采集、清洗和标注。
~~~

证据式写法：

~~~text
维护领域 SFT 数据版本，按来源、语言、任务类型和风险等级记录分布；通过近重复检测、许可证筛查和人工抽检清理高频模板，发现新增长尾数据提升跨域 holdout 但降低格式一致性，遂将数据配比调整作为独立消融变量。
~~~

它展示的是数据如何影响模型和实验，而不是把清洗动作本身写成价值。

## 2.11 不同岗位版本怎样保持真实

### 2.11.1 同一事实可以有不同焦点

同一项目为不同岗位生成不同版本时，应该保留事实不变，只改变以下内容：

1. 项目排序。
2. 第一条 bullet 的主题。
3. 哪些指标放在前面。
4. 哪些技术细节保留在技能栏。
5. 一句话定位和项目标题。

例如一个 RAG 项目有召回、延迟和产品三类结果。投评估岗时先写评估集和引用支持，投部署岗时先写请求分布和 p95，投应用岗时先写任务成功和转人工率。若把同一数字在不同版本中改成不同数值，或者把团队工作换成个人工作，就不再是针对性编辑，而是事实漂移。

### 2.11.2 每个版本都要通过事实回放

维护多个版本时，最容易发生的是数字、日期和责任动词不一致。可以保留一张事实回放表：

| 事实字段 | 主简历记录 | 研究版 | 部署版 | 应用版 |
| --- | --- | --- | --- | --- |
| 项目时间 | 2025.03-2025.08 | 相同 | 相同 | 相同 |
| 个人责任 | 数据、评估 | 方法分析、评估 | 压测接口协作 | 任务指标协作 |
| 主要结果 | 固定 holdout 变化 | 研究结论 | p95/吞吐变化 | 灰度任务变化 |
| 证据类型 | 混合 | 离线 | 压测/线上 | 灰度/A-B |
| 保密等级 | 内部脱敏 | 内部脱敏 | 内部脱敏 | 内部脱敏 |

如果某个版本无法解释某一列，就删掉那项内容，而不是用更强的形容词补足空白。

### 2.11.3 目标岗位变化时，不能只换标题

把“算法工程师”改成“研究科学家”不会改变证据。研究版需要看到问题、假设和实验；部署版需要看到性能、可靠性和系统责任；应用版需要看到用户任务和业务约束。标题只是门面，证据顺序和事实颗粒度才是版本差异。

## 2.12 常见失败写法，以及它们为什么不起作用

### 2.12.1 关键词堆满技能栏

这会让读者知道你见过许多名词，却不知道哪些能独立完成。技能栏可以短而准确，正文经历要承担主要证明责任。

### 2.12.2 只有职责，没有改变

“负责训练、评估和部署”描述的是活动，不是结果。应至少补一个改变：指标变化、时间缩短、故障减少、系统被复用或研究结论改变。

### 2.12.3 只有结果，没有比较

“效果达到 86%”没有基线、数据和协议。即便篇幅不允许写完整口径，也应保留“相对哪个版本、在哪类数据上、用什么方法测”的线索。

### 2.12.4 把相关变化写成因果

模型上线后用户满意度上升，不代表模型一定是唯一原因。产品流程、用户群和流量都可能改变。没有 A/B 或相应控制时，使用“观察到”“同期变化”比“导致”更严谨。

### 2.12.5 把精确小数当成可信度

指标写到小数点后四位不等于实验更科学。若样本量、误差和协议不清，过度精确反而会暴露口径不稳。简历写近似值即可，底稿保留原始统计。

### 2.12.6 把个人项目写成生产系统

个人项目完全可以成为有力证据，但必须标明公开复现、仿真压测、本地实验或线上服务。不同环境对应不同结论，不能把“跑通”写成“长期运营”。

### 2.12.7 忽视合作和沟通

技术岗位并不只奖励单人编码。NACE 的职业准备框架把沟通、批判性思考、团队协作、技术能力和持续发展都视为可以在经历中证明的能力。大模型项目跨越数据、研究、平台、产品和安全，能够说明如何交接、记录决策和处理分歧，本身就是工程证据。

## 2.13 投递前的人工审阅

### 2.13.1 第一遍只看阅读路径

把简历交给一个没有项目背景的人，或者自己在几秒内只看标题、粗体和数字，回答以下问题：目标方向是否清楚，最强项目是否出现，最近经历是否可理解，数字是否有方向，联系方式是否明显。

这一遍不改技术细节，只检查信息架构。若第一遍看不出主线，继续增加内容不会解决问题。

### 2.13.2 第二遍只查事实和指标

逐条对照主简历和项目底稿，检查姓名、日期、模型规模、数据规模、百分比、单位、职责动词和论文状态。把相对提升、百分点、下降率、p95 和 QPS 的含义全部写回指标卡。

这一遍要特别检查“我们”是否被误写成“我”。团队做了什么和你做了什么可以同时出现，但句子要让边界清楚：

~~~text
团队负责训练框架，我独立负责数据版本和评估回归；我参与了模型错误分析，但没有主导训练目标设计。
~~~

这比把所有内容压缩成“主导模型训练”更有长期价值。

### 2.13.3 第三遍只查读者能否追问

对于每个关键词，准备一句事实回答：在哪里用过，解决了什么问题，为什么选它，结果如何，失败是什么。无法回答的词有三种处理方式：删除，降级为“阅读/了解”，或者先完成一个真实的小实验再写入。

这里的目标不是把简历写成问答册，而是保证每条内容都有根。具体的项目展开留在第 3 章和面试准备中。

### 2.13.4 第四遍检查公开和隐私边界

检查客户名、内部 URL、真实用户文本、日志截图、访问凭证、未公开模型信息、许可证受限数据和安全漏洞细节。能公开的项目链接要确认链接确实指向你的贡献；不能公开的内容使用范围或相对变化，但不要用脱敏掩盖责任边界。

### 2.13.5 第五遍检查文件本身

导出 PDF 后复制全文，确认文字顺序、中文字符、日期和链接正常；检查文件名、页数、字体、空白和大小；用另一台设备或另一个阅读器打开。Harvard 的公开资料明确提醒格式在转换为 PDF 后仍应保持正确，MIT 的资料也强调标准、一致且易于快速阅读的格式。

这一遍看起来不如改模型参数有技术感，却能避免一个真实而低级的失败：读者看不到你的联系方式，或者复制后项目顺序完全错乱。

## 2.14 一个完整的简历制作流程

### 第一步：建立事实库

不要直接在空白模板上凭记忆写。先为每段经历记录时间、对象、问题、动作、结果、证据类型、个人责任和保密等级。把公开链接、论文状态和指标底稿放在同一个地方。

### 第二步：选择岗位主线

依据第 1 章的方法，选择一个目标方向和一个相邻方向。把职位描述改写成三到五条验证问题，再从事实库中寻找能回答它们的经历。

### 第三步：写项目骨架

每个项目先写一条对象和结果，再补约束、关键动作和评估协议。不要一开始就纠结句子是否漂亮；先保证事实完整。

### 第四步：压缩成阅读顺序

把最相关的项目放在前面，删除重复经历和没有证据的形容词，控制每条 bullet 的信息量。每个项目保留一到四条最强事实，详细失败和技术过程交给第 3 章。

### 第五步：做指标与责任审计

逐个核对基线、分母、评估方式、时间范围、切片、代价和个人贡献。将无法公开或无法证明的内容降级表述。

### 第六步：做机器和人工可读性审阅

检查 PDF 文本层、链接、日期、标题、字体和页面顺序；再用目标岗位读者的视角快速阅读，确认前几秒能看出主线。

### 第七步：让项目讲述与简历一致

为每个项目准备第 3 章所述的展开材料，但不要在简历里加入你无法在口头解释的细节。简历和面试材料应该是一套事实的不同层次，不是两套互相矛盾的故事。

## 2.15 学习练习：把经历变成可审阅的文档

### 练习一：从职位描述提取证据

选择一份目标职位描述，圈出其中的动词和交付对象。为每条要求写出“我已有的事实、证据等级、缺口和下一步”，不要写“我应该学习某某课程”作为唯一答案。

### 练习二：制作三条不同类型的 bullet

为同一个项目分别写一条研究、工程和产品 bullet。三条句子只能使用同一组事实，不能擅自增加职责或指标。然后标出每条句子服务的岗位主线。

### 练习三：审计一个数字

选简历中最有冲击力的一个数字，补齐指标名称、方向、基线、分母、协议、时间、切片、代价和个人责任。如果其中三项以上无法回答，降低数字的表述强度。

### 练习四：做一次文本抽取

将最终 PDF 的全部文字复制到纯文本文件，检查标题、日期、项目顺序、中文、英文技术名词和链接。发现顺序错乱时先修文件结构，再修视觉样式。

## 2.16 资料与证据说明

本章的简历结构建议结合大模型岗位特点和公开职业服务资料形成。不同国家、行业、级别和组织的简历习惯可能不同，下面的资料用于支持一般性写作原则，不是招聘结果保证。

1. Harvard College, Guide to Creating a Strong Resume: [https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)
2. MIT Career Advising and Professional Development, Resumes: [https://capd.mit.edu/resources/resumes/](https://capd.mit.edu/resources/resumes/)
3. National Association of Colleges and Employers, Career Readiness Competencies: [https://www.naceweb.org/career-readiness/competencies/career-readiness-defined/](https://www.naceweb.org/career-readiness/competencies/career-readiness-defined/)
4. U.S. Department of Labor O*NET OnLine, Data Scientists: [https://www.onetonline.org/link/summary/15-2051.00](https://www.onetonline.org/link/summary/15-2051.00)

Harvard 的页面把简历描述为对能力、教育和经历的简洁总结，并强调针对职位调整、具体表达、主动动词、事实与结果；MIT 的页面强调招聘者快速浏览、标准一致的格式、根据职位描述选择内容和记录成就而非只写职责；NACE 的框架提供沟通、批判性思考、团队协作、技术能力和持续发展的通用能力语言；O*NET 则提供数据科学职业的公开职责和任务描述。它们支持的是写作方法和职业能力框架，不支持“某家公司一定按某个模板筛选”这样的结论。

涉及大模型岗位的具体职责，应回到第 1 章列出的最新公开职位页面核验。职位会变化，团队之间也会不同；简历版本应根据实际职位描述和招聘沟通更新，而不是永久相信某个旧模板。

## 2.17 小结：简历是事实的压缩，不是事实的替代

一份有效的大模型简历，首先要有清晰的岗位主线，然后用有限的文字呈现对象、问题、个人动作、结果、评估协议和责任边界。技术关键词要嵌入经历，数字要带着基线和分母，业务结果要区分因果和同期变化，研究、工程、数据与产品影响要用不同证据表达。

简历可以很短，但底稿不能很薄。你应该维护完整事实库，再生成针对不同岗位的版本；应该压缩项目骨架，再把失败、取舍和推理过程留给面试中的项目讲述；应该保护客户和公司信息，同时保留足够的可核验性。

当读者读完第一页，能够准确回答“你想做什么、你做过什么、做到什么程度、为什么值得继续问”，简历就完成了它最重要的工作。下一章将从这份骨架出发，继续展开项目如何在面试对话中变成完整的技术叙事。
