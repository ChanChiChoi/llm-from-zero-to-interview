# 第 14 章：Frontier Model 证据等级：从发布材料到可辩护的技术结论

## 14.1 “官方说了”究竟证明了什么

前沿模型发布时，信息往往在很短时间内同时出现：模型卡、技术报告、产品博客、
API 文档、权重配置、排行榜截图、开发者帖子和媒体转述。它们可能都在谈同一个
模型，却承担不同的证明责任。

模型卡可以说明公开配置和作者报告的测试；产品页面可以说明一个接口字段；技术
报告可能解释训练路线和实验设置；代码仓库可以确认某个参数是否存在；媒体文章
只能告诉我们有人公开讨论过这个名称。没有一种材料会自动证明“模型在所有任务
上更强”。

写书、做研究或参加面试时，最危险的不是没听过一个新模型，而是把线索写成事实，
把厂商自测写成独立复现，把模型名称推断成内部架构，把一个版本的结果扩展到整
个产品家族。证据等级是一种写作和实验纪律：每个判断都要知道由什么支持、支持
到什么范围、还缺什么证据。

本章要建立的不是一个给模型永久打分的排行榜，而是一套能随着新资料更新的 claim
ledger。它要求作者把最小命题、来源、条件、实验、作用域和未知项放在一起，最后
才决定句子可以写多强。

## 14.2 先把宣传句拆成最小 claim

不要直接复制一段宣传文字。先把句子拆成读者能够单独验证的最小命题。

例如：

> 新的 MoE 模型在百万上下文下推理更强。

至少包含以下命题：

1. 有一个可唯一识别的模型和 revision；
2. 它是 MoE，或至少发布方如此声明；
3. 它能够接收百万级输入；
4. “推理更强”对应一个定义清晰的任务；
5. 存在可比较的基线；
6. 两个系统使用了可比的工具、预算、数据和判定器；
7. 提升不是由污染、重试或评估器偏差造成；
8. 结论适用于哪种任务、时间和运行条件。

如果来源只写“支持 1M context”，它最多支持第 3 条中的接口或产品声明，不能独
立支持第 4 至第 7 条。

### 14.2.1 最小 claim 的记录字段

一条 claim 至少应有：

~~~text
claim_id:
subject:
model_id:
model_revision:
statement:
claim_type:
source_type:
source_url:
publication_or_access_date:
exact_context:
scope:
conditions:
reported_result:
independent_result:
unknowns:
inference:
status:
~~~

这些字段不是为了增加表格工作，而是为了防止一句话承担太多隐含结论。claim_type
可以是 interface、artifact、architecture、training、task_result、production
或 inference；source_type 可以是 paper、technical_report、model_card、
official_doc、repository、vendor_report、independent_eval 或 community_signal。

### 14.2.2 事实、实验和推断要分栏

审计时至少分三层记录：

第一层是来源事实：文档原文、版本、日期、链接和可引用上下文。

第二层是实验结果：任务、模板、工具、预算、样本、判定器、统计和失败样例。

第三层是本书推断：从这些事实可以合理推出什么，不能推出什么。

例如页面称模型为 frontier reasoning model，可以作为产品定位事实；不能据此推
断它使用了某个 RL 算法。若报告给出数学分数，要保存题目版本、采样、reasoning
effort、工具、去污染和 judge 规则。

## 14.3 五层证据链

一个 frontier model claim 通常要经过五层。层次越高，要求的证据越接近真实任务
和真实系统。

### 14.3.1 接口层

接口层回答：

- API 或 SDK 是否接受某个字段；
- context window 的计数单位是什么；
- 输入和输出预算如何分配；
- 模型 ID 和发布日期是什么；
- 是否支持工具、图像、音频或结构化输出。

官方 API 文档和产品文档通常是接口层最直接的来源。它们不能证明模型会有效使用
全部输入，也不能证明不同区域、版本和路由始终一致。

### 14.3.2 Artifact 层

Artifact 层回答：

- 权重是否公开；
- config 中有哪些层、head、expert、vocabulary 和 position 字段；
- tokenizer 和 chat template 是什么；
- checkpoint、量化包和 serving artifact 是否匹配；
- model revision 和代码 commit 是否可复现。

官方仓库、权重配置和开发者文档适合确认这些内容。能加载权重不等于它在生产
并发、长上下文和安全约束下可靠。

### 14.3.3 方法层

方法层回答：

- 论文或技术报告公开了什么架构；
- 训练目标、数据处理、长上下文扩展或后训练方法是什么；
- 哪些细节明确披露，哪些仍然是内部信息；
- 实验使用了什么数据、基线和预算。

论文和技术报告可以支持作者公开的方法描述及其论文实验条件。它们不自动保证
闭源模型的完整训练配方，也不自动保证另一套 runtime 能复现相同结果。

### 14.3.4 任务层

任务层回答：

- 模型在什么任务上被测；
- 成功标准和判定器是什么；
- 是否有独立基线和不确定性；
- 是否包含关键切片、污染控制和失败分析；
- 结果是否来自模型本身，还是来自工具和 Agent harness。

任务层是从“它声称具备某能力”走向“在指定条件下观察到某行为”的关键。公开
benchmark、内部 golden set 和独立复现需要明确分开。

### 14.3.5 生产层

生产层回答：

- 真实用户或真实流量是否获得价值；
- 延迟、吞吐、成本和错误率是否满足 SLO；
- 权限、隐私、安全和审计是否可接受；
- 失败能否降级、回滚和恢复；
- 模型更新后结论是否仍成立。

生产证据的范围也不能无限扩大。一个客服场景的线上提升，不等于数学、代码和
医疗任务都提升；一个低并发异步任务的成本，也不等于交互式默认路由可接受。

### 14.3.6 五层不能互相替代

“模型卡写了 1M”可能只覆盖接口层；“跑通了一次 1M prompt”增加了运行证据；
“训练报告包含长样本”增加了方法证据；“多证据引用任务成功”才进入任务层；
“线上 P95、成本和安全稳定”才进入生产层。

不能因为前一层成立，就把后一层当作自然推论。证据链的价值恰恰在于把这种跳跃
暴露出来。

## 14.4 四类常见材料及其证明责任

### 14.4.1 论文和技术报告

论文通常提供问题定义、方法、实验设置、基线和结果。技术报告可能比论文更接近
产品，但披露方式和审稿程度不同。阅读时要区分：

- 作者提出的方法；
- 作者在特定数据上的实验；
- 其他人复现的结果；
- 读者对未披露部分的推断。

论文能支持“在该实验条件下观察到 X”，不能自动支持“所有实现都能得到 X”。
如果数据集、prompt、工具和基线不公开，复现难度会进一步上升。

### 14.4.2 Model Card 和 System Card

Model card 适合记录模型用途、限制、训练或评测信息、风险和版本。System card
通常更强调部署系统、风险分析、红队和缓解措施。它们对公开声明是重要的一手
材料，但仍可能缺少完整内部数据和独立复现。

阅读 model card 时至少提取：

1. model ID、revision 和发布日期；
2. 输入模态、上下文和输出限制；
3. 训练或微调阶段的公开信息；
4. benchmark、prompt、采样和工具条件；
5. 已知限制、风险和不适用场景；
6. 是否区分模型、系统和产品结果。

### 14.4.3 官方仓库、配置和开发者文档

这类资料适合确认：

- tokenizer 文件和 special token；
- chat template 和默认 generation 参数；
- config 中的层数、head、expert 和 position 字段；
- 权重分片、量化格式和启动命令；
- 版本兼容、硬件要求和已知限制。

配置字段是很好的结构证据，但不能从字段名称推断未公开的训练过程。一个名为
rope_scaling 的字段只能说明配置存在相关参数，不能独立证明长上下文任务有效。

### 14.4.4 产品页、官方博客和厂商 benchmark

产品页和博客可以证明发布信号、定位、价格、接口和发布方自报结果。它们通常是
了解新模型的最快入口，也是最容易被误读的入口。

正确引用厂商自报结果时，应保留：

- prompt 和 system message；
- 工具和 Agent harness；
- reasoning budget 或 effort；
- 采样次数和选择器；
- benchmark revision；
- 污染检测和过滤；
- 硬件、日期和版本。

不能为了看起来中立而删掉条件，也不能把自报数字改成跨模型无条件排名。

### 14.4.5 社区帖子、截图和媒体转述

媒体、社区帖子、截图和未署名榜单适合发现模型别名、争议和线索。没有二次核验
时，只能写成观察项：

> 社区资料在某日期转述了一个未在官方目录确认的名称；目前缺少 model ID、版本
> 和原始发布材料，暂不把它作为事实。

“有人发过截图”证明的是截图存在，不证明截图中的模型、日期、分数和条件。

## 14.5 证据强度的多个维度

来源类别有帮助，但不够。相同类型的资料也可能存在版本、范围和独立性差异。可
以从以下维度检查一条 claim。

### 14.5.1 来源可追溯性

是否能定位原始 URL、commit、版本、发布日期和原文上下文？只有一个被转发多次的
截图，追溯性低；有固定 revision 的文档，追溯性高。

### 14.5.2 命题贴合度

来源是否真的回答当前最小命题？API 文档对字段语义贴合度高，对训练数据贴合度
几乎为零；代码 config 对层数贴合度高，对实际推理质量贴合度有限。

### 14.5.3 条件完整性

是否记录模型版本、数据、模板、工具、预算、硬件、时间和判定器？条件越缺失，结
论作用域越窄，措辞越需要保守。

### 14.5.4 独立性

模型卡、产品博客、发布演讲和媒体文章可能都复制同一份厂商表格。它们数量增加
不等于独立证据增加。独立性要问来源是否使用了不同数据、不同运行链路和不同评
估团队。

### 14.5.5 可复现性

权重、输入、代码、评测集、判定器和环境是否可获得？闭源 API 也可以通过固定调用
日期、返回 usage、版本字段和最小任务增加可复现性，但无法达到开放权重的同等
程度。

### 14.5.6 时效性

价格、API 路由、模型 ID、上下文限制和排行榜会变化。旧资料不一定错误，但必须
绑定日期和版本。一个 2025 年的模型页不能无条件代表 2026 年同名 API 的行为。

## 14.6 一个内部证据分数，但不要把它当真值

团队可以给 claim 定义内部审计分数：

~~~math
E(c)=
\frac{\sum_{j=1}^{m}w_j s_j(c)}
{\sum_{j=1}^{m}w_j},
\qquad 0\le s_j(c)\le1
~~~

其中 s_j 可以表示可追溯性、命题贴合度、条件完整性、独立性或可复现性，w_j 是
团队给这些维度的权重。这个分数不是学术标准，也不是 claim 为真的概率。它的
作用只是提醒团队：某个核心结论是否只有一张截图支持，是否缺少版本和条件。

更重要的是保存作用域：

~~~math
\mathrm{scope}(c)=
(\mathrm{model\_revision},\mathrm{task},\mathrm{harness},
\mathrm{budget},\mathrm{date})
~~~

作用域越窄，句子越不能被改写成通用能力。一个分数很高但作用域只有单次内部
实验的 claim，仍然不能写成所有用户都能观察到的模型定律。

### 14.6.1 证据覆盖率

如果一个结论由 k 个最小命题组成，可以定义有足够证据支持的命题覆盖率：

~~~math
\mathrm{Coverage}(C)=
\frac{\sum_{i=1}^{k}w_i\mathbb{I}[\mathrm{supported}(c_i)]}
{\sum_{i=1}^{k}w_i}
~~~

高风险命题可以有更高权重。覆盖率为 1 也不代表命题正确，因为 supported 只表
示来源与命题匹配；来源本身可能错误，实验可能有偏差。覆盖率要与来源审查、独
立复现和不确定性一起使用。

### 14.6.2 条件完整率

如果一个实验要求记录 r 个条件字段，实际记录了 q 个，可以用：

~~~math
\mathrm{ConditionCompleteness}=\frac{q}{r}
~~~

这同样是审计信号，不是科学质量分数。缺少一个决定性条件，可能比缺少三个无关
字段更严重，因此实际报告还要列出缺失字段名称。

## 14.7 从来源到结论的工作流

### 14.7.1 第一步：收集原始来源

从官方目录、模型卡、技术报告、仓库、配置和论文开始。记录访问日期和版本。社
区资料可以作为线索，但不要让线索成为唯一来源。

### 14.7.2 第二步：规范化名称

同一个模型可能有产品名、API 名、权重名、内部别名和社区简称。需要分别记录：

- 展示名称；
- 官方 model ID；
- 权重仓库名；
- revision 或发布时间；
- API endpoint；
- 是否为 base、instruct、reasoning、quantized 或服务封装。

同名不代表同一个 artifact，同一权重名也不代表不同服务的模板和路由相同。

### 14.7.3 第三步：摘录最小上下文

不要只保存 URL。保存能支持命题的原文片段、标题、表格行、版本和前后句。截图
需要保留完整页面、日期和来源地址；若页面是动态生成的，记录抓取时间和页面
版本。

### 14.7.4 第四步：写出不超过一句的最小命题

例如不要写“模型是下一代高效推理架构”，而写：

> 官方 config 中存在 num_experts=64 和 num_experts_per_tok=8 字段。

这条命题可以由 config 验证。训练时如何路由、实际激活参数、吞吐和质量则是另
外的命题。

### 14.7.5 第五步：绑定条件和作用域

把任务、数据、模板、工具、预算、硬件、日期和版本写进 scope。没有条件时，可
以把结论降级为“发布方声称”或“观察到线索”，不能隐藏缺失信息。

### 14.7.6 第六步：寻找独立证据

独立证据不一定要完全复现全部系统。可以先复现影响最大的最小任务：

- 1M 声明先测输入完整、位置、多证据和引用；
- 代码能力先测相同仓库任务和隐藏测试；
- 工具能力先测权限、参数和副作用；
- reasoning 声明先固定 budget、采样和 verifier。

### 14.7.7 第七步：写出能说和不能说

每条记录最后都应有两句话：

- 当前资料支持什么；
- 当前资料不能推出什么。

第二句话不是附加免责声明，而是作用域的一部分。

## 14.8 Worked Example：审计“某模型使用 NoPE”

社区帖子说“这个模型没有 RoPE”。不能据此直接断定模型没有顺序机制，而要检查
官方模型卡、config、论文、源码和 attention 路径。

可能的结果是：某一分支不施加 RoPE，但 causal mask、递归 state 或其他层仍然提供
顺序信息。也可能是社区把“没有显式 RoPE”误写成“没有位置编码”，或者把某个
实验分支误认为完整模型。

### 14.8.1 逐层核验

可以按下表核验：

| 问题 | 证据入口 | 能支持的结论 |
| --- | --- | --- |
| config 是否有 position 字段 | 官方配置 | 公开 artifact 的字段事实 |
| attention 如何接收顺序 | 代码/论文 | 公开路径的机制解释 |
| 是否所有层都相同 | 完整 config/源码 | 结构范围 |
| 长度如何扩展 | 技术报告/训练说明 | 方法和训练条件 |
| 远距任务是否成功 | 独立评测 | 指定任务下的行为 |
| 生产状态如何保存 | runtime/profile | 资源和 serving 条件 |

### 14.8.2 严谨写法

如果公开资料只支持局部路径，可以写：

> 公开资料支持某个路径不显式使用 RoPE 或 ALiBi；“没有显式位置变换”不等于
> 没有顺序机制。完整层表、训练方法和 runtime 状态布局仍需官方技术报告、代码
> 或独立复现确认。

这句话保留了知识点，同时没有把一个局部观察扩大成整套架构结论。

## 14.9 Benchmark 结果为什么难以比较

模型 A 使用长 thinking，模型 B 使用短回答；A 可以搜索，B 不允许工具；A 用厂
商 harness，B 用公开脚本。即使分数不同，也不知道差异来自模型、预算、工具、
数据还是判定器。

比较表至少要保存：

| 字段 | 内容 |
| --- | --- |
| model | id、revision、量化、template |
| data | benchmark revision、过滤、污染处理 |
| decoding | temperature、top-p、max tokens、effort |
| tools | 搜索、代码、浏览器、verifier |
| harness | retry、folding、memory、judge、stop |
| resources | hardware、batch、并发、timeout |
| date | API、价格和运行日期 |

没有这些元数据，差异只能叫“在该条件下观察到”，不能叫“模型能力排序”。

### 14.9.1 比较对象必须先对齐

比较时要先决定你比较的是：

1. 裸模型；
2. 模型加固定提示；
3. 模型加工具；
4. 完整 Agent 系统；
5. 产品端到端体验。

这些对象可以都值得测，但不能放在同一张 leaderboard 中而不标边界。完整系统
分数更高，可能来自检索、重试、代码执行、人工审核或更大的推理预算。

### 14.9.2 评测差异的分解

设观察到的结果差异为 ΔY，可以把它抽象成：

~~~math
\Delta Y=
\Delta Y_{\mathrm{model}}+
\Delta Y_{\mathrm{data}}+
\Delta Y_{\mathrm{harness}}+
\Delta Y_{\mathrm{budget}}+
\Delta Y_{\mathrm{evaluator}}+
\varepsilon
~~~

这不是可以直接计算的唯一分解，而是实验设计的提醒。要估计模型因素，就要尽
量固定其他项；要研究工具因素，就做有工具/无工具的消融；要研究 judge 因素，
就用人工 gold set 和程序判定器校准。

## 14.10 如何处理厂商自报结果

厂商结果很有价值，因为它展示了发布方重视的任务、产品暴露的能力和未来评测线
索。正确写法是保留原始条件，标注“发布方自测”，再用公开任务或独立复现核对
关键结论。

不要为了看起来中立而删掉条件，也不要把自报数字改成跨模型无条件排名。更严谨
的句式是：

> 在发布方给出的模板、工具和预算下，页面报告了 X；本书把它作为发布信号，不
> 把它直接解释为跨任务普遍能力。

### 14.10.1 自报分数的最小记录

至少记录：

- model ID 和 revision；
- benchmark 和版本；
- prompt、few-shot 和 system message；
- reasoning effort、采样次数和选择器；
- 工具、检索、代码执行和 Agent harness；
- 输出长度、重试、超时和失败计数；
- 污染处理和数据过滤；
- 硬件、并发、价格和日期；
- 是否由发布方完成判定。

如果这些条件缺失，应该降低结论强度，而不是填入社区默认值。

### 14.10.2 自报结果与独立结果冲突

冲突不一定意味着有人故意造假。常见原因包括：

1. 模型变体不同；
2. benchmark revision 不同；
3. 采样和 thinking budget 不同；
4. 工具或 verifier 不同；
5. judge 或成功判定不同；
6. 量化、runtime 和超时不同；
7. 数据污染或重复调参。

先对齐条件，再判断是否真的冲突。不能把两个不同实验条件的数字强行平均。

## 14.11 未确认名称与前沿模型观察项

对 GPT-5.5、GPT-5.6 Sol/Terra/Luna、GLM-5.5、DeepSeek-V4-Flash、Qwen3.8-Max
或其他社区流传名称，第一步是查官方 model ID、模型卡、技术报告、权重和 API
文档。查不到时，可以记录名称、已访问的官方目录、目前缺少的证据以及未来要
核对的字段。

### 14.11.1 “查不到”与“不存在”

“没有查到”不等于模型一定不存在，可能是：

- 名称是内部代号；
- 只在某个地区或产品中出现；
- 尚未公开；
- 社区拼写或转述错误；
- 旧名称已经映射到新 model ID；
- 搜索结果被缓存或页面已下线。

同样，产品页出现一个名字也不等于公开了架构。可信的技术叙述必须把观察项和
确定事实分开。

### 14.11.2 观察项记录模板

~~~text
名称:
首次发现日期:
发现来源:
已访问的官方目录:
官方 model id:
模型卡或技术报告:
权重/配置:
公开 benchmark:
独立复现:
仍缺少的证据:
当前结论:
~~~

当前结论可以是“已核验的产品名称”“官方未确认的社区观察项”“同名但版本不明”
或“已确认模型但架构细节未知”。不要为了填满模型清单而把未知项写成新模型事实。

## 14.12 证据链和不确定性

一个可辩护的结论可以表示为：

~~~text
source -> claim -> protocol -> measurement -> uncertainty -> scope
~~~

例如“长上下文检索变强”需要说明模型版本、文档构造、证据位置、工具和预算；给
出召回率、置信区间和 judge 误差；最后限定结论适用的任务和日期。

### 14.12.1 把不确定性写进句子

可以使用三种强度不同的句式：

- 资料明确说明：用于来源事实；
- 在给定条件下的实验显示：用于带协议的测量；
- 这可能暗示，但公开资料不足以确认：用于推断和未知。

“可能”不是万能的缓冲词。后面仍应写出替代解释和下一步验证，否则它只是模糊
措辞。

### 14.12.2 置信区间与来源不确定性

实验分数的置信区间只描述抽样或测量波动，不能自动表示来源是否独立、版本是否
正确或 claim 是否被污染。一个公开 benchmark 的 95% 区间很窄，仍可能因为数据
污染而不可信；一个独立小样本的区间很宽，仍可能是有价值的早期证据。

因此要把两种不确定性分开：

- measurement uncertainty：样本、标注、judge、随机解码和统计；
- provenance uncertainty：来源、版本、数据血缘和独立性。

## 14.13 Claim Ledger 的完整记录

为了让发布信息可以被复查，可以为每条 claim 建立一个小型记录：

| 字段 | 示例 | 作用 |
| --- | --- | --- |
| claim_id | model-x-nope-v1 | 让后续修订能定位同一命题 |
| 最小命题 | 公开资料明确写出某位置路径 | 避免多个推断混成一句 |
| 来源 | model card、发布日期、版本 | 说明证据从哪里来 |
| 观察条件 | 训练结构/产品接口/benchmark | 限定适用范围 |
| 结论类型 | 事实、实测、推断、未知 | 控制措辞强度 |
| 反证与空白 | 未公开层数和内部 kernel | 防止过度外推 |

一条记录不必追求形式上的高分。若来源只有产品页，它可以支持产品接口声明；
不能凭此证明训练配方或内部架构。若社区逆向结果与官方资料冲突，应并列记录并
进入待核验状态，而不是把分数加总后宣布“更可信”。

### 14.13.1 证据覆盖率

如果一个结论由 k 个最小命题组成，可以定义有足够证据支持的命题覆盖率：

~~~math
\mathrm{Coverage}(C)=
\frac{\sum_{i=1}^{k}w_i\mathbb{I}[\mathrm{supported}(c_i)]}
{\sum_{i=1}^{k}w_i}
~~~

高风险命题可以有更高权重。覆盖率为 1 也不代表命题正确，因为 supported 只表
示来源与命题匹配；来源本身可能错误，实验可能有偏差。覆盖率要与来源审查、独
立复现和不确定性一起使用。

### 14.13.2 条件完整率

如果一个实验要求记录 r 个条件字段，实际记录了 q 个，可以用：

~~~math
\mathrm{ConditionCompleteness}=\frac{q}{r}
~~~

这同样是审计信号，不是科学质量分数。缺少一个决定性条件，可能比缺少三个无关
字段更严重，因此报告还要列出缺失字段名称。

### 14.13.3 状态转移

一条 claim 的状态可以从 observed、reported、replicated、contradicted 和
deprecated 之间变化。状态变化需要保存原因和时间：

| 状态 | 含义 |
| --- | --- |
| observed | 看到了名称或行为，但尚未完成来源核验 |
| reported | 一手来源明确报告了命题 |
| replicated | 在记录的条件下获得独立复现 |
| contradicted | 另一条高质量证据与当前命题冲突 |
| deprecated | 只适用于旧版本或页面已明确失效 |

状态不是模型真值概率。它是编辑和实验团队共享的工作状态，必须与证据摘要一起
保存。

## 14.14 证据冲突如何处理

不同来源可能报告不同参数量、上下文长度或 benchmark 分数。先不要用“哪个看起
来更可信”解决冲突，而要比较版本、模型变体、量化、模板和发布日期。有时两个
数字分别对应 base 模型和 API 模型，或对应不同输出预算。

冲突记录至少保存：

| 字段 | 含义 |
| --- | --- |
| source A/B | 两个来源的类别和链接 |
| claim | 它们实际在说哪个最小命题 |
| revision | 模型、代码或文档版本 |
| condition | benchmark、工具、预算、硬件 |
| resolution | 已解决、并存或待核验 |

若冲突无法解决，可信的结论应同时呈现范围并说明未知，不要为了整齐选择一个未
经解释的数字。技术写作的可信度往往来自对未知的准确标注。

### 14.14.1 两个冲突数字的处理

假设产品页写参数为 X，模型卡写参数为 Y。先检查二者是否对应不同模型变体、总
参数/激活参数、量化前后或发布日期不同；如果仍无法对齐，就并列记录来源、版本
和未知项。正文可以写：

> 两个一手来源分别报告 X 和 Y，公开资料不足以确认其口径差异。

同样，benchmark 分数的比较必须记录 prompt、工具、reasoning budget、采样次数、
评估集版本、污染规则、硬件和 judge。缺失条件时，结论最多是“发布方在其条件
下报告了结果”，不能写成无条件领先。

## 14.15 复现不只是重新请求一次 API

复现实验要固定输入数据、文档顺序、tokenizer/template、模型 revision、temperature、
工具、重试、judge、超时和硬件。对闭源 API，还要记录调用日期、服务区域、返回的
usage、系统版本和价格，因为服务端可能在不改变 model ID 的情况下更新实现。

### 14.15.1 先复现影响最大的最小任务

独立复现不一定要机械重跑所有 benchmark。优先复现影响结论的最小任务：

- 声称长上下文有效，先测输入完整、位置、多证据、引用和成本；
- 声称代码能力强，先测相同仓库任务、隐藏测试和安全沙箱；
- 声称工具能力强，先测参数、权限、幂等和副作用；
- 声称 reasoning 强，先固定 budget、采样和 verifier；
- 声称多模态强，先测 grounding、OCR、图表和反事实干扰。

复现的目标是检验 claim 的适用范围，不是替厂商再做一次营销海报。

### 14.15.2 复现失败的解释

独立结果比发布结果低，不必立即断言发布结果错误。应先比较：

1. 模型和服务 revision；
2. prompt、few-shot 和模板；
3. 工具、检索、缓存和重试；
4. 输出预算、采样和 effort；
5. benchmark 版本、过滤和判定器；
6. 硬件、并发、超时和价格；
7. 测试日期和数据污染。

如果条件无法对齐，结论应是“在两个不同条件下观察到不同结果”，而不是给两方
贴上真假标签。

## 14.16 一个发布材料审计案例

假设一个发布页写着：

> 我们的新模型在代码和 reasoning benchmark 上达到领先水平，并支持超长上下文。

第一轮只把它登记为发布信号。第二轮检查 model ID、revision、是否开放权重、评
测集版本、是否使用工具、reasoning budget、采样次数、去污染规则和上下文输入形
态。

### 14.16.1 可能得到的三种结果

第一种，发布页有完整表格、模型卡有版本、评测脚本公开，独立团队用相同条件得到
相近结果。此时可以写“在指定 benchmark 和协议下得到可重复结果”，仍不能泛化
到所有任务。

第二种，官方表格有分数，但没有 prompt、工具、采样和上下文任务细节。此时可以
写“发布方在给定条件下报告了结果”，不能写跨 harness 的普遍领先。

第三种，只有博客、截图和社区转述，没有官方 model ID 和原始表格。此时只能把它
登记为观察项，列出需要核对的字段。

### 14.16.2 一条可辩护的结论

如果资料只支持第二种情况，正文可以写：

> 发布方在其给定的模型版本、评测配置和预算下报告了这些结果；公开资料不足以
> 推出跨 harness 的普遍领先，也不足以由接口长度推出有效理解长度。

这句话没有否认结果，而是保留了结果的作用域。未来出现独立复现时，可以在同一
个 claim ID 下补证据，而不是重写整章。

## 14.17 当前模型名称与待核验清单

对 GPT-5.5、GPT-5.6 Sol/Terra/Luna、GLM-5.5、DeepSeek-V4-Flash、Qwen3.8-Max
或其他社区流传名称，第一步是查官方 model ID、模型卡、技术报告、权重和 API
文档。查不到时，可以记录名称、已访问的官方目录、目前缺少的证据以及未来要
核对的字段。

### 14.17.1 观察项记录模板

~~~text
名称:
首次发现日期:
发现来源:
已访问的官方目录:
官方 model id:
模型卡或技术报告:
权重/配置:
公开 benchmark:
独立复现:
仍缺少的证据:

~~~

当前结论可以是“已核验的产品名称”“官方未确认的社区观察项”“同名但版本不明”
或“已确认模型但架构细节未知”。不要为了填满模型清单而把未知项写成新模型事实。

### 14.17.2 “查不到”与“不存在”

“没有查到”不等于模型一定不存在，可能是内部代号、地区产品、尚未公开、社区
拼写错误、旧名称映射或页面下线。同样，产品页出现一个名字也不等于公开了架构。

对当前日期的模型清单，必须保留抓取日期。模型目录、价格、上下文和 API 字段都
会变化，不能把今天的搜索结果写成永久事实。

## 14.18 证据更新的回归流程

模型、API 和产品页会更新。维护时应保留 claim ID，并在新资料到达后比较原句的
适用范围：

1. 哪些事实仍成立；
2. 哪些数字只对旧 revision 成立；
3. 哪些推断被新技术报告否定；
4. 哪些未知变成可核验事实；
5. 哪些结论需要新增独立实验。

只在文章末尾堆新链接，不会自动修复正文中的过强结论。

### 14.18.1 证据冲突的最小复现实验

当两个来源给出不同结论时，先把冲突缩小成一个可测试命题。例如“支持 1M
context”可以拆成输入接口、tokenizer/runtime、长位置训练和有效证据任务四个
实验；“使用某种新架构”可以拆成权重结构、配置字段、运行时 profile 和行为反
事实。每个实验只改变一个主要条件，并保留失败样本。

如果可观察行为与公开结构声明冲突，不应立即断言一方错误。可能原因包括版本、
量化、模板、服务端路由、缓存或评估器不同。正文应写清当前实验支持到哪一层，
再把无法区分的替代解释列为待核验项。

### 14.18.2 维护动作

一条 claim 失效时有三种处理：

- 改写适用范围；
- 降级为观察项；
- 删除或移入历史记录。

若新资料只否定了一个推断，不应连带删除同一段中仍由论文支持的事实；若一个数字
没有版本口径，应保留冲突记录而不是擅自取平均。

## 14.19 最小可运行的 Claim Ledger 审计 Demo

下面的程序用一组教学 claim 展示如何把“来源、作用域、独立复现和未知项”拆成
信号。它不是自动决定事实真伪，也不把证据分数当概率；它的作用是发现一条句子
是否跨越了当前证据能支持的范围。

~~~python
claims = [
    {
        "id": "ctx-interface",
        "type": "interface",
        "source": "official_doc",
        "scope_complete": True,
        "independent": False,
        "task_tested": False,
        "unknowns": 0,
    },
    {
        "id": "ctx-task",
        "type": "task_result",
        "source": "independent_eval",
        "scope_complete": True,
        "independent": True,
        "task_tested": True,
        "unknowns": 1,
    },
    {
        "id": "architecture",
        "type": "architecture",
        "source": "community_signal",
        "scope_complete": False,
        "independent": False,
        "task_tested": False,
        "unknowns": 3,
    },
]

signals = {
    "all_scopes_recorded": all(
        claim["scope_complete"] for claim in claims
    ),
    "task_claim_has_independent_evidence": any(
        claim["type"] == "task_result"
        and claim["independent"]
        and claim["task_tested"]
        for claim in claims
    ),
    "architecture_claim_is_confirmed": all(
        not (
            claim["type"] == "architecture"
            and claim["source"] == "community_signal"
        )
        for claim in claims
    ),
    "unknowns_recorded": all(claim["unknowns"] >= 0 for claim in claims),
}

actions = []
if not signals["all_scopes_recorded"]:
    actions.append("补齐模型版本、任务、harness、预算和日期")
if signals["task_claim_has_independent_evidence"]:
    actions.append("保留任务结论，并按任务范围引用")
if not signals["architecture_claim_is_confirmed"]:
    actions.append("把架构说法降级为观察项，寻找配置或技术报告")
if signals["unknowns_recorded"]:
    actions.append("在 claim ledger 中保留未知项")

if not signals["architecture_claim_is_confirmed"]:
    decision = "publish_scoped_task_claim_and_hold_architecture"
elif signals["task_claim_has_independent_evidence"]:
    decision = "publish_scoped_claim"
else:
    decision = "collect_more_evidence"

print("signals=", signals, sep="")
print("actions=", actions, sep="")
print("decision=", decision, sep="")
~~~

运行输出为：

~~~text
signals={'all_scopes_recorded': False, 'task_claim_has_independent_evidence': True, 'architecture_claim_is_confirmed': False, 'unknowns_recorded': True}
actions=['补齐模型版本、任务、harness、预算和日期', '保留任务结论，并按任务范围引用', '把架构说法降级为观察项，寻找配置或技术报告', '在 claim ledger 中保留未知项']
decision=publish_scoped_task_claim_and_hold_architecture
~~~

这里的结果表达了一个重要取舍：有独立任务证据时，可以发布受作用域限制的任务
结论；社区架构线索没有得到确认，不能因为同一个模型还有一条强证据就顺便升级。
一条 claim 的证据强度不能传递给另一条不同命题。

## 14.20 什么时候应该主动写“未知”

“未知”不是资料不足时的尴尬占位，而是一个有边界的技术结论。例如某闭源模型
的公开页面只说明支持 extended thinking，那么可以写接口行为、预算字段和可观
察事件；不能把它改写成内部使用了某种搜索树或训练时一定采用了某种 RL。

同样，厂商报告的 benchmark 数字可以作为发布条件下的结果，但如果缺少 prompt、
工具、采样、输出预算和 harness，就不能与另一个模型的独立复现实验直接排序。正
确写法是保留条件，并提出下一步最小复现实验：固定任务、固定模型版本、固定预算，
比较成功判据和成本。

## 14.21 资料与证据边界

### 14.21.1 模型卡和数据说明

- Model Cards for Model Reporting；
  https://arxiv.org/abs/1810.03993
- Datasheets for Datasets；
  https://arxiv.org/abs/1803.09010
- Hugging Face Model Cards 文档；
  https://huggingface.co/docs/hub/model-cards

这些资料支持模型卡、数据血缘和限制披露的写作方法，不支持某个具体模型的任务
结果。模型卡是来源类型，不是自动通过的质量证明。

## 14.22 本章小结

证据等级不是给模型贴永久标签，而是限定当前句子可以说多强。官方 API 文档适合
支持字段语义和调用约束；模型卡适合支持公开结构、训练规模或评测条件；论文适
合支持方法定义；独立复现适合检验结果是否跨实现成立；线上实验还要加入真实分
流、延迟、成本、安全和治理。

一个可信的技术结论要经过：

1. 把宣传句拆成最小 claim；
2. 规范化模型名称、ID、revision 和日期；
3. 保存原文上下文、来源类型和作用域；
4. 对齐 prompt、工具、预算、数据、harness 和判定器；
5. 区分来源事实、实验结果和本书推断；
6. 记录统计不确定性和来源不确定性；
7. 对关键命题做最小独立复现；
8. 明确当前资料不能推出什么；
9. 在新资料出现时维护 claim ID，而不是只追加链接。

越新的模型，越应该明确哪些是事实、哪些是实验、哪些是推断、哪些仍然未知。能
够准确写出未知，不会削弱技术判断，反而让已经被证据支持的部分更可信。
