# 第十二章：评估体系综合设计与工程落地

当团队准备替换一个大模型时，真正需要回答的不是“新模型的总分是多少”，而是
它是否在目标任务上带来了可复核的改善，以及这项改善是否值得承担新的延迟、成
本和风险。

例如，一个企业知识库助手的新版本在公开问答集上提升了 3 个百分点，但同时出现
了三种现象：引用位置变得不准确，回答平均长度增加，少数租户的敏感文档被错误
带入上下文。此时只报总分没有帮助。我们必须知道评估的对象是什么、哪些用户被
覆盖、分数由什么判定、结果有多大不确定性、失败发生在哪一层，以及下一步应该
改数据、改模型、改提示词、改检索系统还是暂缓发布。

本章以企业知识助手从模型 A 迁移到模型 B 为贯穿案例，把前面学过的方法接成一条
可审计的工程流程：先写任务契约和数据清单，再冻结执行配置与测量器，最后把统计
结果、失败分析和发布规则落到同一份证据链上。各方法的完整原理分别由第 2—11 章
主讲；本章聚焦它们在系统中的接口、产物和交接，并链接回对应章节。读者读完后，
应能设计一轮可重评分、可追踪、可解释且能触发明确行动的评估运行。

## 1. 评估的核心：把分数变成证据

### 1.1 先从一次模型发布说起

假设团队要把企业知识助手的模型 A 换成模型 B。B 在离线问答集上的正确率提高了
3 个百分点，但引用支持率下降 7 个百分点，P95 延迟增加 18%；安全复核还发现，
少数请求把另一租户的敏感文档带入了上下文。这里的数字和事件是用于讲解流程的
合成情境，不是实测结论。

这不是“平均分和工程指标谁更重要”的简单争论。它至少包含四个不同问题：

1. 模型 B 是否在目标任务上真的更准确；
2. 提升是否来自样本分布变化、评估器偏差或数据污染；
3. 退化是否集中在关键场景，而不是被大样本平均掉；
4. 提升带来的价值是否足以支付延迟、成本和风险。

优秀的评估设计会把这四个问题分别测量，再用事先约定的决策规则组织证据。它不
会用一个神奇的总分把所有差异隐藏起来。

### 1.2 五层评估对象

可以把一次模型评估拆成五层。它们相互关联，但不能互相代替。

第一层是目标层。我们先明确模型要帮助谁完成什么任务。例如企业知识助手的目标
可以是让员工更快找到权限范围内、有文档依据的答案，而不是单纯让回答更流畅。

第二层是任务层。目标需要被转成输入、上下文、允许的工具、输出契约和成功标准。
“回答正确”对开放式写作太粗，对数据库查询又不够精确。任务契约必须说明什么
是可接受答案，什么是必须拒绝，什么情况下应请求澄清。

第三层是测量层。测量层决定使用程序判定、参考答案、人工标注、成对偏好、模型
评审还是线上行为。不同测量方式观察的是不同变量，不能因为它们都输出一个
0 到 1 的数字就把它们视为同一件事。

第四层是分析层。分析层处理样本权重、切片、置信区间、显著性、多重比较、聚类
和延迟结果。一个差异是否可信，往往取决于分析单位和不确定性，而不是小数点
后的位数。

第五层是决策层。决策层把主指标、关键切片、安全风险、成本、延迟和回滚能力
放在一起，决定继续实验、扩大灰度、修复后再测，还是保留旧版本。评估的终点
是一个可追溯的工程决定，而不是一张漂亮的排行榜。

### 1.3 一条评估记录应该包含什么

对于离线样本 i，可以用下面的抽象记录描述一次完整测量：

~~~math
e_i=(x_i,k_i,y_i,a_i,v_i,h_i,s_i,r_i,w_i)
~~~

其中：

- x_i 是用户输入、上下文和任务约束；
- k_i 是任务契约，例如允许的工具和输出格式；
- y_i 是模型输出，必要时还包括工具调用轨迹；
- a_i 是参考答案、程序结果或期望行为；
- v_i 是模型、提示词、数据、评估器和代码版本；
- h_i 是运行环境，包括路由、权限、缓存、沙箱和硬件；
- s_i 是评分或成功状态；
- r_i 是错误类型、严重度和证据来源；
- w_i 是业务价值、样本代表性或严重度权重。

初学者可以把它理解为“题目、答案、标准、版本、分数和错误原因”的一行记录。
专家需要进一步注意：h_i 不能被省略。一个 RAG 答错，可能不是模型不会回答，
而是租户过滤误删了文档；一个 Agent 失败，可能不是模型不会调用工具，而是
协议适配器把参数字段改错。

只存一个 score 会让评估变成不可诊断的数字。存下误差向量，才能在版本比较时
回答以下问题：

1. 哪些样本从正确变成错误；
2. 哪些错误是模型输出造成的；
3. 哪些错误来自检索、工具、协议或运行时；
4. 哪些 judge 与人工或程序判定不一致；
5. 修复后是否在未见样本上恢复。

### 1.4 总体分数和切片分数

如果每个样本的分数为 s_i，权重为 w_i，加权总体分数为：

~~~math
S=\frac{\sum_{i=1}^{n}w_i s_i}{\sum_{i=1}^{n}w_i}
~~~

这里的权重可能表示真实流量占比、业务价值或风险严重度。三种含义不能混用。
用流量权重回答“用户平均体验如何”，用业务权重回答“核心任务完成得怎样”，
用严重度权重回答“风险损失有多大”。报告中要明确权重的语义。

对切片 g，分数为：

~~~math
S_g=
\frac{\sum_i w_i s_i\mathbb{I}[z_i=g]}
{\sum_i w_i\mathbb{I}[z_i=g]}
~~~

z_i 可以是语言、领域、任务、长度、风险、租户、证据位置或工具类型。切片分
数的分母必须单独报告；一个只有 8 个样本的切片即使达到 100%，也不能和几千
样本的总体结论拥有相同可信度。

版本差异是：

~~~math
\Delta_g=S_{g,\mathrm{new}}-S_{g,\mathrm{old}}
~~~

实践中最有价值的往往不是最大提升的切片，而是高价值切片中出现的负差异。评估
方案应主动说明“我会做切片和样本级 diff”，这比再列出三个 benchmark 名字更能
证明测量链条是完整的。

### 1.5 从目标到证据的叙事顺序

当评估目标很开放时，可以沿着以下因果顺序组织方案，而不是背一串名词：

1. 先说产品或研究目标；
2. 再说任务契约和样本来源；
3. 接着说评分器以及它能、不能测量什么；
4. 然后说切片、不确定性和污染控制；
5. 最后说失败分析、发布规则和后续动作。

例如评估一个 chat model，完整的方案应包含：目标场景、公开和内部数据、自动指
标与人工偏好、judge 校准、关键风险、线上实验和失败闭环。如果只运行 MMLU、
GSM8K、HumanEval，团队仍然不知道开放式质量、真实流量、成本和安全是否改善。

这不是固定模板。不同任务会改变指标和证据来源，但测量链条不会消失。代码任务
会把程序测试放在核心位置，写作任务会增加人工或成对评估，RAG 任务会拆分检索
和引用，安全任务会同时记录漏拒与误拒。

## 2. 如何设计完整的大模型评估体系

### 2.1 能力、行为、系统和风险不是一个维度

一个通用模型的评估通常至少包括以下五类。

能力评估关注模型能做什么，包括知识问答、指令遵循、推理、数学、代码、多语言、
多模态、长上下文和多轮任务。公开 benchmark 适合提供可比较的参考，但不一定
代表产品分布。

行为评估关注模型如何完成任务，包括帮助性、诚实性、不确定性表达、拒答质量、
格式稳定性、对用户约束的遵守，以及是否会把没有证据的猜测写成事实。

系统评估关注模型嵌入产品之后的表现，包括任务完成率、工具调用成功率、检索
质量、延迟、吞吐、可用性、取消、重试和单位任务成本。

安全与鲁棒性评估关注模型在危险、对抗、模糊和分布外输入上的行为，包括有害
内容、越权工具、隐私泄露、prompt injection、jailbreak、偏见、扰动稳定性和
过度拒答。

线上实验关注真实用户是否得到价值，包括采纳、任务完成、后续修改、投诉、留存、
人工转接和长期结果。线上行为不是模型能力的纯测量，因为它还受产品界面、用户
分流、网络和业务流程影响；但它是判断系统价值不可缺少的证据。

### 2.2 从目标建立测量契约

先写一句目标陈述：

> 对于某类用户，在某种输入和工具条件下，系统要把哪一个结果从什么水平提升到
> 什么水平，同时不能让哪类风险超过可接受范围？

例如，企业知识助手的目标可以是：

> 在权限过滤后的公司文档上，帮助员工更快找到有依据的答案；若证据不足，应
> 明确说明无法确认，而不是编造结论。

这句话会导出不同的测量对象：

- “更快”需要首 token 延迟、完成时延或完成任务时间；
- “找到答案”需要检索召回和最终正确性；
- “有依据”需要原子主张与引用支持关系；
- “权限过滤”需要越权文档暴露率；
- “无法确认”需要 abstention 的正确率，而不是单纯提高拒答率。

没有目标契约时，团队很容易选择手边最容易跑的指标，最后优化的是测量工具而
不是用户任务。

### 2.3 五层评估矩阵

可以把评估计划整理成一张矩阵：

| 层次 | 问题 | 例子 | 主要证据 |
| --- | --- | --- | --- |
| 能力 | 模型能否完成任务 | 数学、代码、抽取 | 程序判定、参考答案 |
| 证据 | 结论是否有依据 | RAG 引用、图像区域 | 文档、框、时间段 |
| 行为 | 是否遵守契约 | 格式、拒答、澄清 | rubric、规则判定 |
| 系统 | 用户是否能用 | 延迟、成本、工具成功 | trace、日志、压测 |
| 风险 | 失败代价是否可接受 | 越权、泄露、危险输出 | 红队、人工、审计 |

一个任务可以同时占据多行。例如企业知识助手既要检索到权限范围内的正确文档，
也要让最终主张得到引用支持；证据不足时应说明限制，并满足任务时延与成本预算。

### 2.4 评估计划中的样本分层

随机抽样适合估计平均用户体验，但不能替代关键场景采样。至少应记录：

1. 任务类型和业务流程；
2. 语言、地域和用户群体；
3. 输入长度、文档数量和多模态类型；
4. 难度、证据数量和冲突程度；
5. 是否调用检索、代码执行或外部工具；
6. 风险等级和失败代价；
7. 是否属于历史事故或新发现的边界样本。

如果企业知识助手中普通查询占 95%，权限敏感查询占 5%，简单的流量加权总分可能
让少数但高代价的权限退化几乎不可见。可以同时发布流量加权分数和风险切片结果，
但要告诉读者它们回答的是不同问题，不能拿平均体验抵消越权事件。

### 2.5 离线和线上为什么可能相反

离线评估在固定输入、固定 prompt 和固定环境中测量，优点是可复现、便于比较和
快速迭代；线上实验面对真实用户、真实噪声和真实产品流程，优点是接近业务价
值。二者结果不一致并不自动说明某一方错误。

常见原因包括：

- 离线样本没有覆盖真实意图；
- 线上用户会追问、修改和放弃，离线只看一次回答；
- 新模型回答更长，自动指标改善但完成时间变长；
- 安全策略减少了危险输出，也误伤了正常问题；
- 线上 RAG 索引、权限和 prompt 与离线环境不同；
- 用户分流、季节性或新奇效应改变了样本构成。

排查顺序应从曝光和分布开始，再到任务结果、样本级 diff、系统 trace 和人工复
核。不要在没有检查分母的情况下把线上指标直接解释成模型智能变化。

### 2.6 一个企业知识助手案例

团队准备把模型 A 替换为模型 B。下表是合成的离线点估计，未给出样本量和区间，
只能用于演示怎样展开评估证据，不能据此判断真实版本效果：

| 指标 | A | B | 变化 |
| --- | ---: | ---: | ---: |
| 答案正确率 | 0.78 | 0.81 | +0.03 |
| 引用支持率 | 0.86 | 0.79 | -0.07 |
| 证据不足时的正确拒答 | 0.62 | 0.74 | +0.12 |
| P95 完成时延 | 5.1 s | 6.0 s | +0.9 s |
| 单次任务成本 | 1.00 | 1.30 | +30% |

如果产品只要求“答案正确”，B 看起来更好；如果目标是“有依据的企业问答”，
引用支持率和权限风险就不能放在附录里。更合理的后续动作是抽取 B 的引用错误
样本，确认是检索、上下文排序还是生成引用的问题；同时做小流量实验，观察任务
完成率是否足以抵消成本和延迟。

### 2.7 什么时候一个总体分数仍然有用

总体分数并不是没有价值。它可以：

- 快速观察同一任务、同一协议下的总体趋势；
- 在样本权重和分母稳定时支持版本排序；
- 作为仪表盘的入口，帮助定位需要展开的切片；
- 参与成本与质量的曲线分析。

它不适合单独承担以下结论：

- “模型在所有场景都更强”；
- “模型已经可以上线”；
- “安全没有退化”；
- “长上下文或推理能力已被证明”。

## 3. 先把评估资产分开管理：Benchmark、Golden Set 与 Regression Suite

本章的贯穿案例是企业知识助手从模型 A 迁移到模型 B。围绕同一项发布决策，团队
需要三类互补资产：公开 benchmark 用来理解外部能力位置；golden set 覆盖目标员
工真实任务和重要切片；regression suite 保存已经确认的事故与高风险边界。它们
不是同一份数据的三个名字。公开 benchmark 不能代表私有文档权限，golden set
不一定能稳定复现每个历史事故，regression suite 也不代表未知流量。

每条样本都应保存稳定 ID、输入和上下文版本、任务/语言/风险切片、来源与标注血
缘、预期行为、判定器版本、使用历史，以及是否进入训练、prompt 调优或发布报告。
企业文档还要记录允许使用的租户范围和知识库快照。数据或 rubric 改动后增加版本，
并判断它是否改变了原来的测量对象。具体任务契约和样本设计见
[第二章：Benchmark 设计](02-benchmark设计.md)；失败样本进入回归集的维护条件见
[第十一章：Error Analysis 与回归测试](11-error-analysis与回归测试.md)。

发布前仍要保留未用于调参的 holdout 和新样本探索。一个样本一旦被团队反复查看并
据此修复，就适合成为回归测试，但不应继续被称作未知泛化证据。关于构念、抽样、
污染和数据血缘的完整方法分别由相应主讲章节负责，本章只说明它们在同一评估计划
中的接口。

## 4. 为不同问题选择测量器

企业助手的一条回答可能同时需要判断事实是否正确、引用是否支持主张、用户是否有
权限、信息不足时是否应该拒答，以及完成任务花了多少时间。测量器要对应具体问
题，不能因为它们都输出分数就混为一谈。

| 要回答的问题 | 优先测量器 | 需要保存的证据 |
| --- | --- | --- |
| JSON、权限字段或工具参数是否符合契约 | 程序规则和 schema 检查 | 输入、解析结果、规则版本和失败原因 |
| 数字、日期或数据库结果是否正确 | 可复算程序、固定快照或可靠 verifier | 参考快照、执行结果和容差 |
| 依据是否支持开放式回答 | 原子主张与文档片段的人工审查，或经校准的辅助 grader | 主张、证据位置、支持标签和仲裁意见 |
| 两个版本哪一个更有帮助 | 隐藏版本名并随机左右顺序的成对比较 | 两个回答、展示顺序、平局/跳过和标注员 |
| 少见的高风险请求是否泄露或越权 | 权限规则、红队样本和专家复核 | 威胁条件、权限状态、工具动作和严重度 |
| 用户是否真正完成任务 | 预先定义分母和成熟窗口的线上指标 | 资格、分配、曝光、完成和结果成熟状态 |

人工和成对评估能观察程序难以定义的质量，但依赖明确的标注协议；自动 judge
适合承担一致、可重复的初筛，不能作为自身正确的证明。样本不确定、测量器冲突
或可能造成高影响损害时，先保留分歧并升级复核，而不是把不同证据简单平均。人
工抽样、成对比较和标注质量的完整推导见
[第三章：Human Eval 与 Pairwise Eval](03-human-eval与pairwise-eval.md)。

## 5. 把 Judge 当成有误差的测量器

只有当目标不能由程序、参考答案或规则稳定判定时，才需要用 LLM judge 补充判断。
团队应先写清 rubric 中的可观察条件，再用人工 gold 样本检查 judge 是否理解每个
条件。校准集需包含普通样本、边界样本、等价表达、证据缺失和容易受长度/位置影
响的样本；报告总体一致性以外，还要看高风险切片和主要错误类型。

版本、模型、prompt、温度、输入字段或参考资料格式一旦变化，就应重看校准样本，
不能把旧 judge 的验证结果自动沿用到新配置。对顺序敏感的比较要交换候选位置；对
置信不足或与规则判定冲突的结果要保留人工路由。尤其是权限、隐私和安全行为，
judge 的自然语言解释不能代替实际工具状态和数据访问证据。rubric 构造、偏差诊断
和人工校准的主讲位置是
[第四章：LLM-as-a-Judge](04-llm-as-a-judge.md)。

## 6. 让数据血缘和污染控制进入运行流程

数据集是否可信，取决于它在构造、训练、调参、判分和报告中的使用历史。团队应
区分开发集、固定回归集、私有 holdout 和新样本探索；日志记录数据集版本、答案/
rubric 版本、访问权限、prompt 搜索和训练使用记录。若回归样本后来进入训练或人
工迭代，它仍可以检查已知问题是否复发，但不能再单独支持“对未见问题泛化”的声
明。

近重复、时间切分和私有访问只能降低部分风险，不能证明绝对没有污染。企业助手
还要区分“训练中接触过同一事实”与“评测题/答案进入了优化链路”；需按来源和使
用方式判断证据是否仍独立。检测方法与结论边界见
[第五章：污染检测与可信评估](05-污染检测与可信评估.md)。

## 7. 按任务结构拆开证据，而不是套一个通用总分

专项任务的共同问题是：最终答案之外，还要核对任务真正依赖的中间证据和约束。
因此为企业知识助手选测量器时，不能只测答案字符串或 judge 总分：

| 任务结构 | 主要拆分 | 典型失败证据 |
| --- | --- | --- |
| RAG 问答 | 召回、重排、上下文构造、原子主张正确性、引用支持、拒答 | 文档未召回、证据被截断、引用不支持主张 |
| 工具型 Agent | 任务交付、工具选择/参数、权限、状态变化、副作用和预算 | 越权调用、错误参数、重复写入、最终产物不完整 |
| 数学与代码 | 结果、可执行契约、边界输入、隐藏测试、资源与安全限制 | 结果偶然正确、判定器漏测、harness 不稳定 |
| 多模态与长上下文 | 模态证据位置、长度/位置、跨片段组合、引用或时间定位 | 只凭语言先验猜中、漏掉中间证据、冲突版本未识别 |
| Safety 与 Robustness | 危险请求错误满足、正常请求误拒、权限泄露和分布变化 | 平均拒答率看似提高但高严重度切片恶化 |

本章只把这些维度接入同一份评估契约，不重讲每一领域的完整构念和算法。Reasoning、
Math、Code 与 Agent 的判定细节见
[第六章](06-reasoning-code-math-eval.md)；多模态和长上下文见
[第七章](07-多模态与长上下文评估.md)；安全与鲁棒性见
[第八章](08-safety与robustness-eval.md)。

## 8. 从离线证据过渡到线上实验

离线集适合固定输入、版本和判定器，线上实验回答的是系统在真实曝光条件下对用户
任务造成了什么变化。进入小流量实验前，先写出目标估计量、随机化单位、资格与曝
光定义、主要结果、护栏指标和结果成熟窗口。用户或组织有跨请求状态时，随机单位
要与依赖结构匹配；降级、重试、取消和未成熟结果必须保留在各自分母中。

对企业知识助手，主要指标可以是权限范围内有依据地完成任务的比例，护栏则包括错
误引用、越权访问、过度拒答、P95 延迟和单位任务成本。遇到隐私或安全严重事件时，
暂停并复核应由风险规则触发，不能等待平均指标达到显著性。线上实验的随机化、
SRM、结果成熟和干扰问题由
[第九章：在线实验与 A/B Test](09-在线实验与ab-test.md)主讲。

例如，在另一组合成点估计中，任务完成率从 0.41 升到 0.43，P95 时延从 4.8 秒升
到 5.7 秒，单位成本从 1.00 升到 1.28。完成率提高 2 个百分点并不能单独回答是否
值得上线；还要查看样本量、区间、曝光分母、结果成熟度和成本上限。这里的数字只
演示质量与成本可能同时变化，不是实测，也没有提供显著性证据。

## 9. 在实验前固定分析问题

分析计划至少写明估计对象、分析单位、主指标和关键护栏、最小有意义差异、样本量
依据、聚类单位、多重比较家族、停止规则和发布动作。若同一题有多次随机解码，要
把题目抽样变异与生成运行变异分开；若同一用户有多条请求，不能把请求数直接当作
独立样本数。对低频高严重度事件，应报告适用分母和不确定性，零次观测不等于零风
险。

统计检验只说明特定抽样与假设下的证据强弱。发布决定还要结合效果大小、成本、延
迟、风险、回归样例和恢复能力。完整区间、功效、配对差异、聚类和多重比较方法见
[第十章：统计显著性与实验设计](10-统计显著性与实验设计.md)。

## 10. 让失败分析改变下一轮运行

当总分变化时，先对齐样本、判定器和配置，再看旧对新错、旧错新对及稳定失败分别
落在哪些任务和严重度切片。每条高价值失败要记录可观察症状、证据、模型/harness/
协议/评估器等候选假设及能区分这些假设的干预。某次干预恢复答案，只支持相应样
本条件下的解释；要在相似样本和未见变体上复验，才能提高根因判断的可信度。

确认过且可稳定判定的失败再沉淀到 regression suite，并保留来源、owner、版本、
预期行为和退休原因；新样本探索与线上观察继续负责发现回归集不知道的问题。这样
回归测试服务于证据链，而不是取代新的能力评估。taxonomy、对照干预、样本级 diff
和生命周期维护的完整讲解见
[第十一章：Error Analysis 与回归测试](11-error-analysis与回归测试.md)。

## 11. Eval Platform 的系统设计

### 11.1 系统边界

一个支持模型、prompt、RAG 索引和 Agent 工具链的评估平台，至少要支持离线运行、
人工评估、回归测试和发布决策。它的核心任务是保证一次评估可复现、可追踪、可
分析、可审计，而不是单纯展示一个 dashboard。

平台的边界应包括数据、执行、评分、分析、报告和治理六个部分。若只建设执行脚
本和可视化页面，却没有版本清单、样本血缘、评分器校准和权限控制，平台只能产
生数字，不能解释数字，也不能保护评估数据。

把这些模块连成一次实际运行，可以看到平台要保存的不是一个最终分数，而是一条
带版本和证据引用的对象链：

~~~mermaid
flowchart LR
    A["任务契约与数据快照"] --> B["Run manifest"]
    B --> C["调度与预算检查"]
    C --> D["模型执行 attempt"]
    D --> E["原始输出与 trace"]
    E --> F["评分器运行与样本证据"]
    A --> F
    F --> G["聚合报告与差异分析"]
    G --> H["人工复核与发布决策"]
    B -.->|版本/权限| C
    D -.->|错误与重试记录| C
~~~

图中的箭头表示数据或决策依赖。调度器重试时要创建新的 `attempt_id`，不能覆盖
原始 attempt；评分结果要同时引用样本、attempt、评分器版本和支持该分数的证据；
报告与发布决定则引用固定的 run 和评分结果。这样一次结果才可以从结论反向走回
输入、配置、原始输出与判定过程。

### 11.2 数据层

数据层需要管理：

- benchmark、golden set、regression suite 和线上抽样；
- 样本输入、参考答案、rubric 和判定器；
- 任务、难度、语言、风险和租户等元数据；
- 数据版本、来源、标注和使用历史；
- 脱敏、权限和私有 holdout。

样本 ID 应稳定，但内容版本必须可变更且可追踪。一个报告必须能回溯到它使用
的样本清单、判定器和 rubric，而不是只能看到最终平均数。

### 11.3 执行层

执行层负责把一个版本配置运行在样本上，至少记录：

1. 模型 artifact 和 tokenizer；
2. system、developer、user prompt；
3. decoding 参数和随机种子；
4. RAG retriever、reranker、索引和过滤条件；
5. Agent 工具 schema、权限和模拟环境；
6. 重试、超时、降级和取消；
7. 输入输出 token、延迟、显存和成本；
8. 完整 trace 和错误状态。

执行层应支持幂等重跑。重跑必须说明是相同随机种子、不同采样、失败重试还是环境
修复；否则两个结果无法解释。

具体来说，一次样本可以有多个 attempt，每个 attempt 单独保存开始时间、结束状态、
错误类别、重试原因、服务端请求 ID（若有）、token 与成本、输出 artifact 和 trace
引用。调度任务的幂等键用于避免队列重复投递创建重复工作；它不自动保证模型调用
或外部工具副作用幂等。若请求已发出但客户端超时，系统可能不知道远端是否已经执
行，应记录 `unknown_outcome` 一类状态并保留原请求证据，而不是假定“没发生”后
直接覆盖重试。

### 11.4 评分层

评分层可以按确定性逐渐增加不确定性：

1. schema 和字段检查；
2. exact match、数值误差和规则；
3. 编译、单元测试、隐藏测试和 verifier；
4. 引用、grounding 和权限判定；
5. LLM judge；
6. 人工标注和专家仲裁。

高成本的人工和专家资源应集中在高风险、低一致性、程序判定失败和版本分歧样本，
而不是让所有样本都走最昂贵路径。

### 11.5 分析层

分析层输出：

- 总体和加权指标；
- 任务、语言、难度、长度和风险切片；
- 置信区间和显著性；
- 样本级 old/new diff；
- 错误类型与严重度；
- judge 与人工的一致性；
- 成本、延迟和资源曲线；
- 结果成熟度和 pending 样本；
- 失败后续动作。

报告应该支持从柱状图点击到具体样本，并能查看原始证据和版本 manifest。否则
分析人员仍然需要手工拼日志，平台没有缩短诊断路径。

### 11.6 决策层和治理层

决策层不能只输出一个总布尔值。更好的报告包含三列：

| signals | actions | decision |
| --- | --- | --- |
| 哪些主指标、切片和护栏通过或异常 | 需要复核、修复、补测或继续灰度什么 | 继续实验、受限发布、修复后重测或保留旧版 |

治理层负责权限、脱敏、审计、holdout 保护、模型和 judge 版本冻结、数据使用历史
和报告可追溯性。评估数据经常含有用户内容、企业文档和安全样本，平台不能为了
方便调试而让所有人读取原文。

### 11.7 一份可复现的评估 manifest

可以用如下结构描述一次运行：

~~~yaml
run_id: eval-2026-08-10-042
spec_digest: sha256:...
model:
  provider: provider-x
  requested_name: model-b
  resolved_revision: sha256:...
  endpoint_api_version: 2026-08
prompt:
  name: enterprise-rag
  revision: 17
  content_digest: sha256:...
data:
  set: enterprise-golden
  revision: 9
  manifest_digest: sha256:...
  split: holdout
  sampling_recipe: stratified-v3
retrieval:
  retriever_revision: retriever-5
  index_revision: 2026-08-09
  index_digest: sha256:...
  reranker: reranker-3
judge:
  artifact: judge-2
  rubric_revision: 4
  evaluator_code_revision: git:abc123
runtime:
  container_digest: sha256:...
  temperature: 0
  max_output_tokens: 1024
  seed: 7
  retry_policy: max-2-network-transient
metrics:
  - name: answer_correctness
    definition_revision: 3
    implementation_digest: sha256:...
  - name: citation_support
    definition_revision: 2
    implementation_digest: sha256:...
  - name: p95_latency
    definition_revision: 1
  - name: unit_cost
    definition_revision: 5
~~~

这里的省略号表示运行时应填入真实且不可变的 artifact 摘要，不是让系统接受任意
文本。托管模型的别名和 API 版本也要记录；若服务方不提供可固定的权重版本，就
明确记录请求别名、响应中的模型标识和调用日期，并承认复跑不保证得到逐 token
相同结果。模型权重没变，prompt、评估器、数据或 reranker 变了，结果都不应被
误标成相同实验条件。

还应区分两个经常被统称为“可复现”的目标：**可重评分**是保存了模型输出和评分
证据，之后能在新版本评分器上重新计算；**可重跑**是尽量用同一输入和运行配置再
调用系统。前者依赖完整 artifact 和血缘，后者还受随机采样、托管服务更新和外部
工具状态影响。只保存总分，两种能力都没有；只保存随机种子，也不能保证托管模型
在不同日期产生完全相同的输出。

### 11.8 失败恢复和结果状态

`completed`、`model_error`、`evaluator_error`、`pending` 和 `invalid_data` 不
是同一条状态轴：有的描述执行，有的描述输入校验或评分，`pending` 描述结果是否
成熟。把它们放在同一个枚举里，后续很难统计“模型正常返回但 judge 挂了”或
“线上请求已完成但转化窗口未结束”。可以把状态拆成相互独立的维度：

| 维度 | 示例状态 | 它回答的问题 |
| --- | --- | --- |
| input_validation | unchecked、valid、invalid_data | 输入是否符合任务契约、权限和数据要求？ |
| execution | queued、running、succeeded、failed、cancelled、unknown_outcome | 这次 attempt 的调用走到了哪一步？ |
| scoring | not_started、scored、evaluator_error、not_applicable | 是否成功生成了有效评分？ |
| maturity | pending、final、not_applicable | 当前指标所需的观察窗口是否结束？ |

例如，输入校验失败应记录 `input_validation=invalid_data`，并把评分记为
`not_applicable`；模型返回成功但 judge 超时应记为 `execution=succeeded`、
`scoring=evaluator_error`；线上转化尚在归因窗口内则可以是 `execution=succeeded`、
`maturity=pending`。面向用户的 `completed` 可以作为这些底层状态的派生视图，但
不能替代它们。

重试策略必须记录原因和 attempt 顺序。对随机采样任务，重试会改变测量对象：
评估“单次生成成功率”“固定次数内至少成功一次”还是“best-of-k”必须预先定义；
对服务质量评估，重试本身还会影响时延、成本和副作用风险。网络超时可能发生在
请求已被远端接受之后，因此应保留每次 attempt，分别计入调用可用性、最终任务结
果或两者，而不能只保留最好答案。若报告只评价成功返回的样本，应同时报告超时、
取消和无效结果的分母，否则会产生幸存者偏差。

### 11.9 代表性评估方案各自解决什么问题

评估平台并不是一个单一产品类别。研究框架、应用评估工作流、实验追踪系统和遥测
规范解决的是不同层次的问题，不能拿它们的指标或功能列表直接排名。

| 方案与层次 | 它主要解决的问题 | 关键机制或产物 | 收益与证据 | 代价、限制与适用边界 |
| --- | --- | --- | --- | --- |
| [HELM](https://arxiv.org/abs/2211.09110)：研究评测框架 | 不同模型各用不同场景和指标，导致横向结果难比较，也难检查模型表现的其他维度 | 用 scenarios、adaptations 和 metrics 描述评测条件；对 16 个核心场景尽可能同时测量多类指标，并公开 prompts 与 completions | 论文报告把模型间共同核心场景覆盖从既有研究平均 17.9% 提高到 96%，并发布逐样本输入输出，提升可比性和可检查性 | 统一配置提高的是相同条件下的可比性，不等于场景代表目标产品；论文明确按可行性取舍覆盖，仍有未覆盖领域和污染风险 |
| [OpenAI Eval-Driven System Design](https://developers.openai.com/cookbook/examples/partners/eval_driven_system_design/receipt_inspection)：应用开发工作流 | Prompt 和应用规则容易因小改动退化，工程团队缺少从失败例子到有针对性改进的循环 | 先分析失败样本，再把案例变成数据集和 grader，比较修改前后的运行结果并继续迭代 | 官方示例把质性分析、量化测量和针对性改进连成连续工作流，适合应用团队从 prototype 走向验收 | CookBook 是一个官方案例，不是普适收益的对照实验；其平台 API 会变化，不能把特定界面或产品能力写成稳定架构依赖 |

## 12. 评估体系完整性诊断 Demo

下面的程序不是模型质量的真值判定器，也不会因为一个数字达到阈值就替代人工审
查。它把一份评估计划拆成若干可观察的组成部分，再把质量、风险、成本和后续行
动并列输出。这样做的重点是让读者看到：评估覆盖可以看起来完整，却仍然缺少
judge 校准、多模态与长上下文证据，或者超出成本预算。

**代码状态：静态审阅，未运行（2026-11-03）。** 下面的代码仅演示完整性信号与
发布评审门禁；所有输入和阈值均为教学用合成值。

~~~python
from collections import Counter


plan_rubric = {
    "goal": 2,
    "data_slices": 2,
    "metrics": 2,
    "human_eval": 1,
    "judge_calibration": 2,
    "contamination": 2,
    "reasoning_code_math": 2,
    "multimodal_longctx": 2,
    "safety": 2,
    "online_ab": 2,
    "statistics": 2,
    "error_analysis": 2,
    "regression_suite": 2,
    "release_decision": 2,
}

plan_tags = {
    "goal",
    "data_slices",
    "metrics",
    "human_eval",
    "contamination",
    "reasoning_code_math",
    "safety",
    "online_ab",
    "statistics",
    "error_analysis",
    "regression_suite",
    "release_decision",
}

missing = [name for name in plan_rubric if name not in plan_tags]
score = sum(points for name, points in plan_rubric.items() if name in plan_tags)
max_score = sum(plan_rubric.values())

cases = [
    {"id": "qa", "score": 0.86, "weight": 1.0, "slice": "chat"},
    {"id": "rag", "score": 0.74, "weight": 1.5, "slice": "rag"},
    {"id": "code", "score": 0.68, "weight": 1.2, "slice": "code"},
    {"id": "safety", "score": 0.92, "weight": 2.0, "slice": "safety"},
]

weighted_score = sum(
    case["score"] * case["weight"] for case in cases
) / sum(case["weight"] for case in cases)
slice_scores = {case["slice"]: case["score"] for case in cases}

pairwise = Counter({"win": 7, "tie": 2, "loss": 3})
pairwise_total = sum(pairwise.values())
win_rate = (
    pairwise["win"] + 0.5 * pairwise["tie"]
) / pairwise_total

risk_metrics = {
    "attack_success": 0.02,
    "over_refusal": 0.08,
    "p95_latency_delta": 0.18,
    "cost_delta": 0.30,
    "high_regressions": 0,
}

signals = {
    "plan_coverage": score / max_score >= 0.85,
    "weighted_score": weighted_score >= 0.80,
    "pairwise_win_rate": win_rate >= 0.60,
    "safety": (
        risk_metrics["attack_success"] <= 0.05
        and risk_metrics["over_refusal"] <= 0.10
    ),
    "latency": risk_metrics["p95_latency_delta"] <= 0.20,
    "cost": risk_metrics["cost_delta"] <= 0.25,
    "regression": risk_metrics["high_regressions"] == 0,
}

actions = []
if missing:
    actions.append("补充评估组件: " + ", ".join(missing))

signal_actions = {
    "plan_coverage": "补齐评估计划覆盖并复核 rubric 定义",
    "weighted_score": "检查主指标差异、分母和关键切片",
    "pairwise_win_rate": "复核成对样本、盲评顺序和人工校准",
    "safety": "复核高风险样本并进行人工安全审查",
    "latency": "检查负载条件、尾延迟和降级路径",
    "cost": "复核单位成本、输出长度和路由预算",
    "regression": "调查高严重度版本回归并补充回归用例",
}
failed_signals = [name for name, passed in signals.items() if not passed]
for name in failed_signals:
    actions.append(signal_actions[name])

if missing or failed_signals:
    decision = "hold_release_and_resolve_blockers"
else:
    decision = "eligible_for_release_review"

print(
    "coverage=",
    {
        "score": score,
        "max": max_score,
        "ratio": round(score / max_score, 3),
        "missing": missing,
    },
    sep="",
)
print("weighted_score=", round(weighted_score, 3), sep="")
print("slice_scores=", slice_scores, sep="")
print("pairwise_win_rate=", round(win_rate, 3), sep="")
print("risk_metrics=", risk_metrics, sep="")
print("signals=", signals, sep="")
print("failed_signals=", failed_signals, sep="")
print("actions=", actions, sep="")
print("decision=", decision, sep="")
~~~

按给定输入和代码逻辑手算，关键输出应为：

~~~text
coverage={'score': 23, 'max': 27, 'ratio': 0.852, 'missing': ['judge_calibration', 'multimodal_longctx']}
weighted_score=0.812
slice_scores={'chat': 0.86, 'rag': 0.74, 'code': 0.68, 'safety': 0.92}
pairwise_win_rate=0.667
risk_metrics={'attack_success': 0.02, 'over_refusal': 0.08, 'p95_latency_delta': 0.18, 'cost_delta': 0.3, 'high_regressions': 0}
signals={'plan_coverage': True, 'weighted_score': True, 'pairwise_win_rate': True, 'safety': True, 'latency': True, 'cost': False, 'regression': True}
failed_signals=['cost']
actions=['补充评估组件: judge_calibration, multimodal_longctx', '复核单位成本、输出长度和路由预算']
decision=hold_release_and_resolve_blockers
~~~

这些输出可以逐项手算。计划 rubric 的最高分是 27，缺失的 judge 校准和多模态/长
上下文各值 2 分，所以得分为 23，覆盖率 `23/27≈0.852`，高于示例阈值 0.85。加权
质量分子为 `0.86×1+0.74×1.5+0.68×1.2+0.92×2=4.626`，权重和为 5.7，故
`4.626/5.7≈0.812`。成对偏好率为 `(7+0.5×2)/(7+2+3)=8/12≈0.667`。安全和延迟
信号分别满足示例门槛；成本变化 0.30 高于上限 0.25，因此 `cost=False`。计划缺项
另生成补充评估组件的动作，成本门禁生成复核成本、输出长度和路由预算的动作，最终
进入 hold。0.85、0.80、0.60、0.05、0.10、0.20 和 0.25 都是这份合成案例中的策略
输入，不是通用行业阈值。

这里有三个值得注意的地方。

第一，coverage 只检查评估计划是否覆盖 rubric 中的组成部分，不检查计划中的指标
定义、数据质量和证据是否真的正确。因此它是完整性审计工具，不是模型质量证明。

第二，weighted_score、pairwise_win_rate 和 risk_metrics 观察的是不同对象。不能
因为前两个信号通过，就抹掉成本超预算。

第三，decision 不是永久结论。补充 judge 校准和多模态长上下文后，还要用事实、
案例和追问重新审查；成本问题则需要另一个工程实验验证。

这个例子也修复了一个容易被忽略的门禁漏洞：每个失败 signal 都进入
`failed_signals` 并生成对应动作，任一组件缺失或门禁失败都会阻止“进入发布评审”。
即便返回 `eligible_for_release_review`，也只是允许进入有责任人的发布评审，代码
没有批准发布的权限。真实系统还应检查输入范围、空分母、无效样本和不确定区间；
本 demo 只展示证据汇总和门禁流向，不替代这些数据校验。

## 13. 常见设计误区与修正路径

### 13.1 只报 benchmark 名字

问题不在于提到 benchmark，而在于没有说明它测量什么、样本是否代表目标、判定
是否可靠、有没有污染和外部有效性风险。

修正方式是先说任务目标，再把 benchmark 放到证据组合中。例如代码能力可以同时
使用公开函数集、内部仓库任务、隐藏测试、静态安全检查和人工可维护性评估。

### 13.2 只看平均分

平均分会遮住用户群体、语言、风险和长度切片。修正时至少给出关键切片、样本数、
分母和 old/new diff；低频高影响任务要单独报告。

### 13.3 把 LLM judge 当作真值

Judge 需要人工 gold set、顺序交换、版本冻结和不确定样本路由。可执行任务应
优先使用程序判定器，judge 适合补充开放式质量而不是替代外部证据。

### 13.4 把显著等同于值得发布

先报告效果大小和区间，再考虑业务最小差异、成本、延迟、安全、回归和灰度结果。
统计显著只说明随机波动不是唯一的合理解释。

### 13.5 忽略分母和结果成熟

任务完成率、采纳率、延迟和安全事件的分母不同。曝光失败、降级请求、重复请求
和尚未成熟的结果都要有明确状态，不能为了让数字好看而删除。

### 13.6 用最终结果掩盖工具和协议错误

Agent 最终回答错误时，先查看工具参数、权限、返回内容、重试和解析。RAG 回答
错误时，先区分检索没召回、上下文被截断和生成超出证据。错误分类应该能导出
下一步实验。

### 13.7 只优化已知测试集

Regression suite 能保护已知修复，却不能证明未知泛化。必须保留独立 holdout、
时间切分或线上抽样，并记录数据使用历史。

## 15. 资料与证据边界

下面的资料按证据性质分组。论文和官方规范可以支持方法定义与实验结论，但不能
自动证明某个闭源模型在生产环境中的表现。社区实现适合帮助理解工程接口，使用
时要核对版本、配置和复现实验。

### 15.1 评估框架与人工评估

- OpenAI Evals：官方开源评估框架，适合查看 eval 数据和运行结构；
  https://github.com/openai/evals
- HELM：Stanford CRFM 的多维度语言模型评估框架；
  https://crfm.stanford.edu/helm/latest/
- MT-Bench：研究多轮对话和模型评审的论文；
  https://arxiv.org/abs/2306.05685
- Chatbot Arena：成对用户偏好和排名方法的研究资料；
  https://arxiv.org/abs/2403.04132
- CheckList：通过行为测试发现 NLP 系统能力缺口的方法；
  https://arxiv.org/abs/2005.04118
- G-Eval：使用 LLM 进行文本评估的研究论文；
  https://arxiv.org/abs/2303.16634

这些资料的证据范围不同。HELM 和 benchmark 论文支持评估维度与实验设计，不能
替代目标产品的内部样本；MT-Bench 和 Arena 展示了成对偏好与 judge 的实践，但
也需要结合人工校准、时间变化和任务切片理解。

### 15.2 推理、代码和数学

- HumanEval：函数级代码生成评估；
  https://arxiv.org/abs/2107.03374
- APPS：更接近编程问题解决的评估数据；
  https://arxiv.org/abs/2105.09938
- MATH：分层数学问题数据集；
  https://arxiv.org/abs/2103.03874
- Self-Consistency：多条推理路径聚合的方法；
  https://arxiv.org/abs/2203.11171
- Let's Verify Step by Step：训练和使用数学过程验证器的研究；
  https://arxiv.org/abs/2305.20050

这些资料可以支持“为什么要执行验证、为什么要区分 pass@1 和 pass@k、为什么
要测试过程和泛化”等方法论。它们不应被直接改写成“某模型一定具备推理能力”。

### 15.3 多模态与长上下文

  https://arxiv.org/abs/1505.00468

## 16. 本章小结

评估工作的核心不是堆叠更多 benchmark，而是构造一条可信的证据链：

1. 明确用户目标和任务契约；
2. 设计有血缘、分层和版本的数据；
3. 选择与任务匹配的程序、人工、judge 和线上测量；
4. 控制污染、偏差、相关性和统计不确定性；
5. 把结果拆到关键切片、样本和错误根因；
6. 同时报告质量、风险、延迟、成本和结果成熟度；
7. 用灰度、修复、回归和 holdout 把评估接到后续决策；
8. 以版本清单、独立 attempt、评分证据和状态记录连接整条运行血缘，保留每次
   失败与重试，让结论能够回到原始样本和调用轨迹。

Human eval、pairwise eval、LLM judge、自动指标和 A/B test 都只是测量工具。它们
观察的对象不同，误差结构不同，适用边界也不同。推理、代码、数学、RAG、多模态、
长上下文、Agent 和安全任务都不能被一个总分概括。

当分数相反、污染无法排除，或错误可能来自检索也可能来自模型时，评估结论不应
停在一句判断，而应该给出分母、对照、证据、失败边界和下一步实验。能把分数变
成可复核行动，才是评估体系的价值。
