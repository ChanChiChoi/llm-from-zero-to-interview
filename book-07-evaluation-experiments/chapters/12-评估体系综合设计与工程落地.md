# 第十二章：评估体系综合设计与工程落地

当团队准备替换一个大模型时，真正需要回答的不是“新模型的总分是多少”，而是
它是否在目标任务上带来了可复核的改善，以及这项改善是否值得承担新的延迟、成
本和风险。

例如，一个企业知识库助手的新版本在公开问答集上提升了 3 个百分点，但同时出现
了三种现象：引用位置变得不准确，回答平均长度增加，少数租户的敏感文档被错误
带入上下文。此时只报总分没有帮助。我们必须知道评估的对象是什么、哪些用户被
覆盖、分数由什么判定、结果有多大不确定性、失败发生在哪一层，以及下一步应该
改数据、改模型、改提示词、改检索系统还是暂缓发布。

本章把前面介绍的评估方法组织成一套可以落地的工作流。每个单元都从初学者能理
解的直觉开始，再进入工程实践需要掌握的机制、公式、实验设计、取舍和失败边界。
读者读完之后，应当能为一个真实系统写出任务契约，选择合适的测量器，解释分数
背后的不确定性，并把错误分析接到下一轮模型迭代。

## 1. 评估的核心：把分数变成证据

### 1.1 先从一次模型发布说起

假设团队要把模型 A 换成模型 B。产品负责人说：“B 的平均准确率更高，应该
直接切全量。”工程师却发现 B 的回答更长，P95 延迟增加 18%，代码任务的隐藏
测试通过率下降，安全团队还发现一个高严重度的越权工具调用。

这不是“平均分和工程指标谁更重要”的简单争论。它至少包含四个不同问题：

1. 模型 B 是否在目标任务上真的更准确；
2. 提升是否来自样本分布变化、评估器偏差或数据污染；
3. 退化是否集中在关键场景，而不是被大样本平均掉；
4. 提升带来的价值是否足以支付延迟、成本和风险。

优秀的评估设计会把这四个问题分别测量，再用事先约定的决策规则组织证据。它不
会用一个神奇的总分把所有差异隐藏起来。

### 1.2 五层评估对象

可以把一次模型评估拆成五层。它们相互关联，但不能互相代替。

第一层是目标层。我们先明确模型要帮助谁完成什么任务。例如客服助手的目标可能
是减少人工转接，代码助手的目标可能是让开发者更快完成可测试的修改，而不是
让回答看起来更流畅。

第二层是任务层。目标需要被转成输入、上下文、允许的工具、输出契约和成功标准。
“回答正确”对开放式写作太粗，对数据库查询又不够精确。任务契约必须说明什么
是可接受答案，什么是必须拒绝，什么情况下应请求澄清。

第三层是测量层。测量层决定使用程序判定、参考答案、人工标注、成对偏好、模型
评审还是线上行为。不同测量方式观察的是不同变量，不能因为它们都输出一个
0 到 1 的数字就把它们视为同一件事。

第四层是分析层。分析层处理样本权重、切片、置信区间、显著性、多重比较、聚类
和延迟结果。一个差异是否可信，往往取决于分析单位和不确定性，而不是小数点
后的位数。

第五层是决策层。决策层把主指标、关键切片、安全风险、成本、延迟和回滚能力
放在一起，决定继续实验、扩大灰度、修复后再测，还是保留旧版本。评估的终点
是一个可追溯的工程决定，而不是一张漂亮的排行榜。

### 1.3 一条评估记录应该包含什么

对于离线样本 i，可以用下面的抽象记录描述一次完整测量：

~~~math
e_i=(x_i,k_i,y_i,a_i,v_i,h_i,s_i,r_i,w_i)
~~~

其中：

- x_i 是用户输入、上下文和任务约束；
- k_i 是任务契约，例如允许的工具和输出格式；
- y_i 是模型输出，必要时还包括工具调用轨迹；
- a_i 是参考答案、程序结果或期望行为；
- v_i 是模型、提示词、数据、评估器和代码版本；
- h_i 是运行环境，包括路由、权限、缓存、沙箱和硬件；
- s_i 是评分或成功状态；
- r_i 是错误类型、严重度和证据来源；
- w_i 是业务价值、样本代表性或严重度权重。

初学者可以把它理解为“题目、答案、标准、版本、分数和错误原因”的一行记录。
专家需要进一步注意：h_i 不能被省略。一个 RAG 答错，可能不是模型不会回答，
而是租户过滤误删了文档；一个 Agent 失败，可能不是模型不会调用工具，而是
协议适配器把参数字段改错。

只存一个 score 会让评估变成不可诊断的数字。存下误差向量，才能在版本比较时
回答以下问题：

1. 哪些样本从正确变成错误；
2. 哪些错误是模型输出造成的；
3. 哪些错误来自检索、工具、协议或运行时；
4. 哪些 judge 与人工或程序判定不一致；
5. 修复后是否在未见样本上恢复。

### 1.4 总体分数和切片分数

如果每个样本的分数为 s_i，权重为 w_i，加权总体分数为：

~~~math
S=\frac{\sum_{i=1}^{n}w_i s_i}{\sum_{i=1}^{n}w_i}
~~~

这里的权重可能表示真实流量占比、业务价值或风险严重度。三种含义不能混用。
用流量权重回答“用户平均体验如何”，用业务权重回答“核心任务完成得怎样”，
用严重度权重回答“风险损失有多大”。报告中要明确权重的语义。

对切片 g，分数为：

~~~math
S_g=
\frac{\sum_i w_i s_i\mathbb{I}[z_i=g]}
{\sum_i w_i\mathbb{I}[z_i=g]}
~~~

z_i 可以是语言、领域、任务、长度、风险、租户、证据位置或工具类型。切片分
数的分母必须单独报告；一个只有 8 个样本的切片即使达到 100%，也不能和几千
样本的总体结论拥有相同可信度。

版本差异是：

~~~math
\Delta_g=S_{g,\mathrm{new}}-S_{g,\mathrm{old}}
~~~

实践中最有价值的往往不是最大提升的切片，而是高价值切片中出现的负差异。评估
方案应主动说明“我会做切片和样本级 diff”，这比再列出三个 benchmark 名字更能
证明测量链条是完整的。

### 1.5 从目标到证据的叙事顺序

当评估目标很开放时，可以沿着以下因果顺序组织方案，而不是背一串名词：

1. 先说产品或研究目标；
2. 再说任务契约和样本来源；
3. 接着说评分器以及它能、不能测量什么；
4. 然后说切片、不确定性和污染控制；
5. 最后说失败分析、发布规则和后续动作。

例如评估一个 chat model，完整的方案应包含：目标场景、公开和内部数据、自动指
标与人工偏好、judge 校准、关键风险、线上实验和失败闭环。如果只运行 MMLU、
GSM8K、HumanEval，团队仍然不知道开放式质量、真实流量、成本和安全是否改善。

这不是固定模板。不同任务会改变指标和证据来源，但测量链条不会消失。代码任务
会把程序测试放在核心位置，写作任务会增加人工或成对评估，RAG 任务会拆分检索
和引用，安全任务会同时记录漏拒与误拒。

## 2. 如何设计完整的大模型评估体系

### 2.1 能力、行为、系统和风险不是一个维度

一个通用模型的评估通常至少包括以下五类。

能力评估关注模型能做什么，包括知识问答、指令遵循、推理、数学、代码、多语言、
多模态、长上下文和多轮任务。公开 benchmark 适合提供可比较的参考，但不一定
代表产品分布。

行为评估关注模型如何完成任务，包括帮助性、诚实性、不确定性表达、拒答质量、
格式稳定性、对用户约束的遵守，以及是否会把没有证据的猜测写成事实。

系统评估关注模型嵌入产品之后的表现，包括任务完成率、工具调用成功率、检索
质量、延迟、吞吐、可用性、取消、重试和单位任务成本。

安全与鲁棒性评估关注模型在危险、对抗、模糊和分布外输入上的行为，包括有害
内容、越权工具、隐私泄露、prompt injection、jailbreak、偏见、扰动稳定性和
过度拒答。

线上实验关注真实用户是否得到价值，包括采纳、任务完成、后续修改、投诉、留存、
人工转接和长期结果。线上行为不是模型能力的纯测量，因为它还受产品界面、用户
分流、网络和业务流程影响；但它是判断系统价值不可缺少的证据。

### 2.2 从目标建立测量契约

先写一句目标陈述：

> 对于某类用户，在某种输入和工具条件下，系统要把哪一个结果从什么水平提升到
> 什么水平，同时不能让哪类风险超过可接受范围？

例如，企业知识助手的目标可以是：

> 在权限过滤后的公司文档上，帮助员工更快找到有依据的答案；若证据不足，应
> 明确说明无法确认，而不是编造结论。

这句话会导出不同的测量对象：

- “更快”需要首 token 延迟、完成时延或完成任务时间；
- “找到答案”需要检索召回和最终正确性；
- “有依据”需要原子主张与引用支持关系；
- “权限过滤”需要越权文档暴露率；
- “无法确认”需要 abstention 的正确率，而不是单纯提高拒答率。

没有目标契约时，团队很容易选择手边最容易跑的指标，最后优化的是测量工具而
不是用户任务。

### 2.3 五层评估矩阵

可以把评估计划整理成一张矩阵：

| 层次 | 问题 | 例子 | 主要证据 |
| --- | --- | --- | --- |
| 能力 | 模型能否完成任务 | 数学、代码、抽取 | 程序判定、参考答案 |
| 证据 | 结论是否有依据 | RAG 引用、图像区域 | 文档、框、时间段 |
| 行为 | 是否遵守契约 | 格式、拒答、澄清 | rubric、规则判定 |
| 系统 | 用户是否能用 | 延迟、成本、工具成功 | trace、日志、压测 |
| 风险 | 失败代价是否可接受 | 越权、泄露、危险输出 | 红队、人工、审计 |

一个任务可以同时占据多行。例如报销助手既需要字段抽取准确率，也需要金额
计算正确、引用原始票据、拒绝未经授权的报销操作，并满足交互时延。

### 2.4 评估计划中的样本分层

随机抽样适合估计平均用户体验，但不能替代关键场景采样。至少应记录：

1. 任务类型和业务流程；
2. 语言、地域和用户群体；
3. 输入长度、文档数量和多模态类型；
4. 难度、证据数量和冲突程度；
5. 是否调用检索、代码执行或外部工具；
6. 风险等级和失败代价；
7. 是否属于历史事故或新发现的边界样本。

如果产品流量中普通闲聊占 95%，医疗问答占 5%，简单平均分会让医疗退化几乎
不可见。可以同时发布流量加权分数和风险加权分数，但要告诉读者这两个数字回答
的是不同问题。

### 2.5 离线和线上为什么可能相反

离线评估在固定输入、固定 prompt 和固定环境中测量，优点是可复现、便于比较和
快速迭代；线上实验面对真实用户、真实噪声和真实产品流程，优点是接近业务价
值。二者结果不一致并不自动说明某一方错误。

常见原因包括：

- 离线样本没有覆盖真实意图；
- 线上用户会追问、修改和放弃，离线只看一次回答；
- 新模型回答更长，自动指标改善但完成时间变长；
- 安全策略减少了危险输出，也误伤了正常问题；
- 线上 RAG 索引、权限和 prompt 与离线环境不同；
- 用户分流、季节性或新奇效应改变了样本构成。

排查顺序应从曝光和分布开始，再到任务结果、样本级 diff、系统 trace 和人工复
核。不要在没有检查分母的情况下把线上指标直接解释成模型智能变化。

### 2.6 一个企业知识助手案例

团队准备把模型 A 替换为模型 B。离线结果如下：

| 指标 | A | B | 变化 |
| --- | ---: | ---: | ---: |
| 答案正确率 | 0.78 | 0.81 | +0.03 |
| 引用支持率 | 0.86 | 0.79 | -0.07 |
| 证据不足时的正确拒答 | 0.62 | 0.74 | +0.12 |
| P95 完成时延 | 5.1 s | 6.0 s | +0.9 s |
| 单次任务成本 | 1.00 | 1.30 | +30% |

如果产品只要求“答案正确”，B 看起来更好；如果目标是“有依据的企业问答”，
引用支持率和权限风险就不能放在附录里。更合理的后续动作是抽取 B 的引用错误
样本，确认是检索、上下文排序还是生成引用的问题；同时做小流量实验，观察任务
完成率是否足以抵消成本和延迟。

### 2.7 什么时候一个总体分数仍然有用

总体分数并不是没有价值。它可以：

- 快速观察同一任务、同一协议下的总体趋势；
- 在样本权重和分母稳定时支持版本排序；
- 作为仪表盘的入口，帮助定位需要展开的切片；
- 参与成本与质量的曲线分析。

它不适合单独承担以下结论：

- “模型在所有场景都更强”；
- “模型已经可以上线”；
- “安全没有退化”；
- “长上下文或推理能力已被证明”。

## 3. Benchmark、Golden Set 和 Regression Suite

### 3.1 三者分别解决什么问题

Benchmark 试图在相对稳定的任务定义下，测量某类能力水平，并允许不同系统进行
比较。它重视覆盖、可重复和外部可比性。

Golden set 是经过较高质量审查的内部样本集合。它可以来自真实用户任务、专家构
造、历史事故和领域流程，重点是代表产品目标和关键边界。

Regression suite 是为了防止已知问题再次出现而维护的可重复测试集合。它重视
稳定的判定器、历史失败和版本差异，不追求代表所有未知能力。

三者可以有交集，但不能互相替代：

| 集合 | 主要问题 | 更新方式 | 典型风险 |
| --- | --- | --- | --- |
| Benchmark | 能力水平如何 | 版本化、定期重测 | 过拟合、污染 |
| Golden set | 目标用户任务是否完成 | 专家审查、流量抽样 | 过于主观、分布窄 |
| Regression suite | 已知错误是否复发 | 每次事故或修复后添加 | 只会测试旧问题 |

### 3.2 Benchmark 设计从任务开始

设计 benchmark 的第一步不是搜集题目，而是写任务契约。契约至少包括：

1. 输入格式和可用上下文；
2. 用户真正要完成的结果；
3. 允许或禁止的工具；
4. 成功、部分成功、拒答和格式失败的定义；
5. 参考答案、程序判定器或 rubric；
6. 输出是否需要引用、解释或结构化字段；
7. 结果观察窗口和成本限制。

例如，评估数据库查询生成时，文本与参考 SQL 完全相同不是必要条件。只要查询
在同一数据库快照上返回等价结果，且不包含危险写操作，就可能是成功答案。若把
字符串相似度当作唯一标准，会把正确的不同写法误判成错误。

### 3.3 样本来源和数据血缘

样本来源会影响结论的外部有效性。常见来源包括：

- 脱敏后的真实用户日志；
- 领域专家根据任务流程构造的样本；
- 公开数据集；
- 受约束的合成数据；
- 红队和事故样本；
- 历史错误分析沉淀的案例。

每个样本应有数据血缘记录：来源、生成或改写方式、标注人、审查时间、允许用途、
是否进入训练或 prompt 调优、是否进入过公开报告。一个看似干净的测试集，如果
题目来自团队长期调参使用的内部文档，也可能已经被流程污染。

合成数据不是天然不可信。它适合扩大边界覆盖、控制变量和构造反事实，但模型生
成的题目可能过于规整，答案也可能带有同源偏差。合成样本应通过人工抽检、外部
分布比较和独立判定器校准。

### 3.4 覆盖、难度和区分度

覆盖率回答“重要任务有没有被测到”，难度回答“题目是否能区分不同能力水平”，
区分度回答“高低能力系统的表现是否真的不同”。

设任务类型集合为 T，目标场景集合为 G，样本集合为 E。一个简单的覆盖矩阵可以
定义为：

~~~math
\mathrm{Coverage}(t,g)=
\frac{|\{i:z_i^t=t\land z_i^g=g\}|}
{|\{i:z_i^g=g\}|}
~~~

这不是唯一的覆盖定义，但它迫使我们说明分母。只有总样本数，没有任务和用户群
体标签，无法知道哪些区域空白。

难度不能只由人工感觉决定。可以结合基线模型的通过率、专家判断、步骤数量、
证据冲突数、输入噪声和所需工具数量。一个题目让所有模型都答对，可能太容易；
让所有模型都答错，可能是题目或判定器有问题。区分度高的样本通常更值得进入
开发集或诊断集，但不应把“难”本身当成“重要”。

### 3.5 Rubric 和程序判定器

开放式回答需要 rubric。一个好的 rubric 不是“写得好”“有帮助”这种模糊形容词，
而是把目标拆成可观察条件：

| 维度 | 通过示例 | 失败示例 |
| --- | --- | --- |
| 事实 | 关键数字和版本与来源一致 | 编造没有出现的数字 |
| 证据 | 每个关键主张都有支持段落 | 引用存在但不支持主张 |
| 完整性 | 覆盖任务要求的全部字段 | 只回答最容易的一部分 |
| 行为 | 证据不足时说明不确定 | 用确定语气补全空白 |
| 格式 | 可被下游解析 | JSON 缺字段或混入说明文字 |

能写程序判定时，优先写程序判定器。代码生成可以编译和运行，数学答案可以用
符号或数值验证，结构化输出可以做 schema 校验，RAG 可以把原子主张与引用段落
交给检索或人工标注核对。LLM judge 和人工评估应当补充程序无法观察的部分，而
不是替代已有的确定性证据。

判定器本身也需要测试。要准备正确、错误、边界、等价写法和恶意格式样本，测量
它的漏判、误判和解析失败。一个有 bug 的 oracle 会把系统优化带到错误方向。

### 3.6 Benchmark 的维护

Benchmark 是有生命周期的资产，不是一次性的 Markdown 表格。维护时要记录：

1. 数据和答案版本；
2. 判定器、rubric 和 judge 版本；
3. 训练、调参和报告使用历史；
4. 样本的失效原因；
5. 新增样本的来源和审查；
6. 结果能否与旧版本直接比较。

如果修改了题目、参考答案或评分方式，应该增加版本号，并说明变化是否改变了
estimand。否则一个“分数上升”可能只是测试规则变了。

### 3.7 Benchmark 与 regression suite 的边界

两者的差异首先是测量目标，其次是维护方式。Benchmark 关注某类能力的可比测量；
regression suite 关注历史失败不复发。前者需要尽量代表目标分布，后者可以刻意保
留罕见但高代价的边界样例。前者适合看总体和切片趋势，后者适合做版本 diff 和
快速复验。

一个实际项目常常同时拥有三套数据：公开 benchmark 用来理解外部位置，内部
golden set 用来理解产品任务，regression suite 用来保护历史修复。只运行公开
benchmark，无法证明关键客户场景没有退化。

## 4. Human Eval 与 Pairwise Eval

### 4.1 为什么开放式任务需要人

自动指标擅长判断明确的程序结果，却难以完整判断一段回答是否真正解决了用户
问题。写作、复杂解释、多轮澄清、拒答质量和风格适配通常需要人判断。人工评估
不是“人凭感觉打分”，而是一种需要任务定义、标注指南、随机化和一致性检查的
测量实验。

小白可以这样理解：如果题目有唯一答案，程序像一把尺子；如果答案有多个合理
版本，人工标注员需要先知道“要量什么”，否则每个人拿的都是不同的尺子。

### 4.2 绝对评分和成对偏好

Pointwise eval 让标注员独立给每个回答打分，例如 1 到 5 分。它适合同时记录
多个维度，也适合需要判断是否达到最低质量的场景，但不同标注员的尺度可能不同。

Pairwise eval 给标注员两个回答，询问哪个更好，或是否平局。相对判断常比绝对
分数更容易稳定，因为标注员不必先定义自己的“3 分”和“4 分”之间的边界。但
它需要更多比较，且不保证偏好具有传递性。

设候选版本在 N_win 个样本上胜过基线，在 N_loss 个样本上失败，在 N_tie 个样
本上平局，平局折半计算，则偏好胜率为：

~~~math
W=
\frac{N_{\mathrm{win}}+0.5N_{\mathrm{tie}}}
{N_{\mathrm{win}}+N_{\mathrm{tie}}+N_{\mathrm{loss}}}
~~~

分母只包含有效比较。跳过、无法判断和标注冲突应单独统计，不能悄悄作为失败或平
局。若安全样本和普通样本的业务价值不同，还要按切片分别报告。

### 4.3 Elo 和 Bradley--Terry 不是魔法

当系统数量增加时，逐对胜率不容易汇总。Elo 把每个系统表示为一个动态评分，根
据比赛结果更新；Bradley--Terry 模型则假设系统 i 胜过系统 j 的概率与潜在能力
差异有关：

~~~math
P(i\succ j)=
\frac{\exp(\beta_i)}
{\exp(\beta_i)+\exp(\beta_j)}
~~~

β_i 是系统 i 的潜在质量参数。模型可以从成对结果估计参数，但结果仍然依赖抽
样、比较图是否连通、时间漂移、标注员偏差和 tie 处理。一个只和弱系统比较很多
次的模型，不能仅凭排名证明它在核心任务上更可靠。

如果线上用户不断产生新比较，时间也会进入模型。早期的系统可能因为用户偏好、
问题分布和版本不同而有不可比的比赛记录。报告排名时应保留样本数、置信区间、
比较时间和切片，而不是只展示一个小数。

### 4.4 标注协议决定人工结果的上限

人工评估开始前要先写标注协议。协议至少说明：

1. 标注员看到哪些输入、上下文和工具结果；
2. 是否隐藏模型名称、版本和生成顺序；
3. correctness、faithfulness、style、safety 各自的定义；
4. 两个答案都不好时如何选择；
5. 信息不足或题目有歧义时如何标记；
6. 何时升级给领域专家；
7. 哪些样本不能让标注员直接接触。

盲评和随机交换顺序可以减少品牌与位置偏差。对同一批样本安排部分交叉标注，
可以估计一致性；争议样本应保存原始意见和仲裁理由，而不是只保留最终标签。

### 4.5 一致性、偏差和标注员质量

简单一致率为：

~~~math
A=\frac{\#\{\text{相同标签}\}}{n}
~~~

但类别极不平衡时，一致率可能看起来很高。例如 99% 样本都安全，所有人都选
“安全”，并不能说明他们能识别少数危险边界。Cohen's kappa、Krippendorff's
alpha 或成对任务的专门一致性指标可以校正部分随机一致，但没有一个指标能够
替代协议审查。

常见偏差包括：

- 长度偏差：更长的答案更像“认真回答”；
- 位置偏差：左侧或先出现的答案更容易被选中；
- 风格偏差：流畅、自信、礼貌掩盖了事实错误；
- 领域偏差：不同背景的标注员对专业正确性判断不同；
- 疲劳偏差：后半程更快、更宽松或更严格；
- 参考答案偏差：标注员把参考答案的表达方式误当成唯一正确方式。

可以通过隐藏版本、交换顺序、插入已知 gold 样本、限制批次长度、统计标注时长
和复核低一致性样本来减轻这些问题。质量控制不是为了淘汰所有意见不同的人，
而是为了识别协议不清、题目有歧义和真实价值冲突。

### 4.6 成本和抽样

人工标注成本可以粗略表示为：

~~~math
C_{\mathrm{human}}=
n_{\mathrm{sample}}\times
n_{\mathrm{judge}}\times
t_{\mathrm{sample}}\times
c_{\mathrm{minute}}
~~~

增加标注员数量可以降低方差，却不能修复错误的任务定义。更有效的策略通常是分
层抽样：普通样本采用较少标注，高风险、低一致性和版本分歧样本采用更多标注或
专家复核。对开放式任务，先用自动判定筛选明显正确和明显错误，再把不确定样本
送给人，能降低成本，但筛选器不能被当作最终真值。

### 4.7 Pairwise 与绝对评分的取舍

成对比较可以降低评分尺度差异，适合偏好和模型版本比较；但它增加标注量，可能
受到位置偏差、长度偏差和不可传递偏好的影响。可靠的设计需要随机交换顺序、保
留 tie、做交叉标注和分层置信区间，不能把 pairwise 自动等同于更准确的测量。

## 5. LLM-as-a-Judge：把模型当作测量仪器

### 5.1 Judge 测量的不是“真理”

LLM judge 接收任务、参考资料、待评回答和 rubric，输出分数、偏好或结构化判断。
它的优点是速度快、成本较低、能处理开放式文本；它的缺点是自身会错，也可能
受到输入顺序、回答长度、格式风格、待评文字中的指令和模型家族的影响。

把 judge 当成真值，会产生一个危险的闭环：被评模型生成更像 judge 喜欢的回答，
judge 又因为风格相似给高分，最终分数提升但任务质量没有提升。更准确的理解是：
judge 是一个带测量误差的评估器，需要像人工标注器一样校准。

### 5.2 从自然语言目标到 rubric

一个可用 rubric 要把“好回答”拆成独立维度。例如 RAG 回答可以拆成：

| 维度 | 需要判断的事实 | 可观察证据 |
| --- | --- | --- |
| 正确性 | 结论是否与证据和参考结果一致 | 原子主张与文档 |
| 忠实性 | 是否引入证据没有支持的内容 | claim-evidence 对齐 |
| 完整性 | 是否回答用户提出的每个子问题 | 任务字段 |
| 引用 | 引用是否指向正确来源 | 文档 ID、位置 |
| 行为 | 证据不足时是否说明限制 | abstention 标签 |

rubric 应说明边界样例和扣分理由。只给 judge 一句“请评价答案质量”，通常会
让它依赖自己的风格偏好，且难以定位分歧。

### 5.3 结构化输出和解析失败

Judge 的输出应有明确 schema，例如：

~~~text
{
  "dimensions": {
    "correctness": {"score": 0, "reason": "..."},
    "faithfulness": {"score": 0, "reason": "..."}
  },
  "overall": 0,
  "uncertain": false,
  "evidence": ["doc-17#p4"]
}
~~~

这段结构只是示意，实际字段应由任务契约决定。系统需要分别记录：

- judge 是否返回；
- 输出是否能解析；
- 字段是否齐全；
- 理由是否引用了允许的证据；
- 是否触发不确定或人工复核；
- judge 本身的 token、延迟和成本。

解析失败不能自动按 0 分处理，因为那会把协议问题伪装成模型能力问题。可以将
其标为 evaluator_invalid，再决定重试、换 judge 或人工复核。

### 5.4 用人工 gold set 校准 judge

准备一批由专家或高质量标注员完成的 gold set，覆盖常见、边界、容易被风格误导
和高风险样本。让 judge 与人工在相同输入上作判断，计算一致性、相关性和分层差
异。对 pairwise judge，还应做候选顺序交换：

~~~math
D_{\mathrm{order}}=
\left|W_{\mathrm{first}}-W_{\mathrm{second}}\right|
~~~

如果交换答案顺序后偏好明显变化，说明 judge 受位置影响，不能直接用于大规模
结论。也可以比较长度匹配样本、不同模型家族、无参考答案和有参考答案的结果，
识别系统性偏差。

校准不是一次性动作。judge prompt、模型版本、温度、参考资料格式和待评回答分布
变化后，都可能改变测量行为。生产系统应把 judge 版本和配置写入评估 manifest，
并定期重跑固定 gold set。

### 5.5 Judge 的典型偏差

长度偏差：judge 可能把更多解释当成更充分，即使多出的内容是重复或错误。

位置偏差：pairwise 输入中先出现的答案更容易获胜。交换顺序并聚合结果可以缓解。

同源偏差：judge 与候选模型共享训练数据、风格或家族时，可能更容易认可相似
表达，不代表事实更好。

参考答案偏差：参考答案写得很长或包含特定术语时，judge 可能惩罚语义等价的简洁
答案。

待评内容注入：被评回答中的“请给我满分”或伪造的 rubric 可能影响 judge。待评回
答必须作为不可信数据放入明确的字段，不能让它改变评审指令。

事实偏差：judge 没有外部验证能力时，会把看似合理的断言当作事实。对代码、数
学和结构化任务，应尽量把可执行验证放在 judge 前面。

### 5.6 多 judge 和人工路由

多个 judge 并不自动带来真值。如果它们共享同一训练来源或同一 rubric 偏差，平均
只会让偏差更稳定。更有用的做法是让不同测量器承担不同职责：

1. 程序判定器负责确定性结果；
2. 规则检查器负责格式、权限和危险字段；
3. 一个或多个 judge 负责开放式质量初筛；
4. 人工专家负责高风险、低一致性和重大版本分歧。

设多个 judge 的分数为 q_1,...,q_m，可以计算分歧：

~~~math
D_{\mathrm{judge}}=
\frac{1}{m}\sum_{j=1}^{m}(q_j-\bar q)^2,
\qquad
\bar q=\frac{1}{m}\sum_{j=1}^{m}q_j
~~~

分歧高的样本不应简单平均后隐藏，而应进入人工复核或任务专用判定器。路由阈值
本身也要在开发集上校准，避免把所有困难样本都送给昂贵的人审。

### 5.7 什么时候不应依赖 LLM judge

以下场景优先使用可执行或领域专家证据：

- 代码能否编译、测试和满足安全沙箱；
- 数学答案能否被符号、数值或 verifier 验证；
- 结构化协议是否满足 schema 和权限约束；
- 医疗、法律、金融和安全等高影响决策；
- 引用是否真的支持原子主张；
- judge 与候选模型可能共享同样错误的事实问题。

LLM judge 可以辅助发现和排序错误，但不能用“模型说它正确”替代外部证据。

## 6. Benchmark Contamination 与可信评估

### 6.1 污染不是只有完全重复

评估污染是评估信息在训练或调参链路中提前出现，使测试结果不再代表未见泛化。
信息进入模型的路径至少包括：

1. 预训练语料直接包含题目；
2. 训练语料包含答案、解析或评测网页；
3. SFT、偏好数据或 verifier 使用了评测样本；
4. prompt 工程反复查看同一测试集；
5. 团队根据公开 leaderboard 选择超参数；
6. judge 的参考答案或 rubric 泄露给待评系统；
7. regression 样本被反复加入训练，最后仍被当作未知测试。

完全相同的字符串是最容易发现的一类。改写题目、交换实体、改变数字、泄露答案
结构和长期人工反馈则更难发现。污染检测的目标不是证明绝对没有泄露，而是估计
哪些结论仍然可信。

### 6.2 数据侧检测

Exact match 可以发现完全相同的题目、答案或段落。n-gram overlap 适合发现局部
复制，near-duplicate 检测适合发现少量改写，embedding similarity 能发现语义相
近，但可能把同一领域的正常共性误判为泄露。

设评估样本 e_i 与训练文档集合 D 的相似度为 sim，最大相似度为：

~~~math
c_i=\max_{d\in D}\mathrm{sim}(e_i,d)
~~~

c_i 只是筛查信号，不是污染证明。阈值需要用人工核验样本校准；对于数学题和代码，
还要检查变量替换后的结构、测试用例、函数签名和解析。对于 RAG 或企业任务，
训练数据与内部知识库的业务事实相同不一定是污染，关键是评估问题和答案是否在
模型优化链路中被使用过。

### 6.3 时间切分和私有 holdout

时间切分的直觉很简单：用过去数据开发，用未来数据测试。它不能解决所有污染，
但能减少团队无意中看到最终样本的机会。对于更新很快的产品，还需要按时间滚动
维护测试集，并记录每次使用。

高价值测试集可以采用私有 holdout，只让评估服务返回聚合结果或经过审计的错误
样本，限制原题、答案和逐样本分数的访问。这样会降低调试便利，却提高最终结论的
可信度。开发集仍应足够大，否则团队会绕过流程，在 holdout 上反复试错。

### 6.4 一个污染调查案例

某代码模型在公开函数生成集上突然从 48% 提升到 73%。调查不能只看训练日期：

1. 对题目、函数签名、答案和测试用例做 exact 与近重复检测；
2. 检查训练数据、SFT 数据和代码仓库是否包含评测原文；
3. 回看 prompt 和超参数搜索日志，确认是否反复使用了测试结果；
4. 用变量、函数名和输入输出约束都变化的新题测试；
5. 在时间更晚、来源独立的仓库任务上复测；
6. 报告受影响的样本比例和剩余不确定性。

如果只有公开集提升，而独立新题没有提升，结论应改成“公开集表现提高”，不能
写成“代码泛化能力提高”。如果污染范围无法精确确定，应降低报告中的证据等级，
而不是选择最有利的样本继续宣传。

### 6.5 可信报告应该写什么

一个可信的 benchmark 报告至少说明：

- 数据来源、版本和时间；
- 训练与评估数据的隔离方式；
- 检测过哪些形式的重复和泄露；
- 哪些样本无法审计；
- 是否使用该测试集调 prompt、超参数或模型选择；
- 判定器和 judge 的版本；
- 总体、切片、置信区间和失败样例；
- 仍然存在的污染和外部有效性风险。

“未发现污染”通常只能表示“在指定方法和范围内未发现”，不能表示逻辑上的零
风险。把方法、范围和限制写清楚，比给出一个绝对保证更专业。

## 7. Reasoning、Math、Code 与 Agent 评估

### 7.1 Reasoning 的结果、过程和泛化

推理题的最终答案正确，是必要但不总是充分的证据。对于开放式解释，模型可能
先猜到答案，再生成一段听起来合理的过程；对于可验证任务，过程中的关键中间
结果则可以帮助定位错误。

推理评估可分为三层：

1. Outcome：最终答案是否正确；
2. Process：中间步骤是否满足约束，是否存在无法支持的跳跃；
3. Generalization：改写、反事实、组合和分布外题目是否仍然正确。

如果最终答案正确率为：

~~~math
A_{\mathrm{out}}=
\frac{\sum_i\mathbb{I}[\mathrm{answer}_i\ \mathrm{correct}]}{n}
~~~

过程一致率可以在有可靠过程标注时定义为：

~~~math
A_{\mathrm{process}}=
\frac{\sum_i\mathbb{I}[\text{所有关键步骤满足契约}]}{n_{\mathrm{audited}}}
~~~

两个指标的分母可能不同。没有过程金标准时，不能把生成出来的解释直接当作真实
思维轨迹；它更适合做错误分析或可读性检查。

### 7.2 Test-time compute 和 self-consistency

推理模型可能通过增加采样次数、思考预算、搜索深度或 verifier 调用提高结果。
因此评估时要记录质量和成本的曲线，而不是只报告最好的一个点。

如果一次问题生成 n 个候选，其中 c 个通过可靠判定器，抽取 k 个候选至少有一个
正确答案的估计量常写为：

~~~math
\mathrm{pass@k}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}
~~~

它描述的是采样机会增加后的成功概率，不等于一次请求的默认质量。若产品只能
生成一次，pass@1 才接近用户体验；若系统允许并行采样和选择，必须把额外 token、
延迟和选择器错误一起计入。

Self-consistency 对同一问题采样多个推理路径，再用多数答案或 verifier 选择结
果。它可能提升正确率，也可能把一个系统性错误重复很多次。报告中应同时给出：

- 每次尝试的通过率；
- 候选数量和总 token；
- 聚合器或 verifier 的准确率；
- 延迟、并行资源和失败重试；
- 改写题和新结构题上的泛化。

### 7.3 Math Eval：最终值、等价形式和证明

数学评估常见的错误是用字符串匹配判断答案。分数、根式、集合、矩阵和证明有
很多等价表达，判定器必须先规范化或使用符号/数值验证。

对数值答案，可设绝对误差为 |ŷ-y|，相对误差为：

~~~math
e_{\mathrm{rel}}=\frac{|\hat y-y|}{\max(|y|,\epsilon)}
~~~

epsilon 用来避免真实答案接近 0 时分母不稳定。对于证明题，单一最终结论不足以
证明每个推理步骤正确；应把命题、条件、关键引理、边界情况和结论分别标注，或
使用可靠 verifier 检查可形式化部分。

数学题还要测试：

1. 数字变化后是否重新计算；
2. 条件顺序变化后是否保持；
3. 题目加入无关信息时是否稳健；
4. 不可解或信息不足时是否承认；
5. 答案格式是否可解析；
6. 推理预算增加是否真的带来边际收益。

### 7.4 Code Eval：从函数通过到仓库任务

代码评估应优先执行候选代码，而不是比较文本表面相似度。函数级任务至少要看
编译、公开测试、隐藏测试、边界输入、资源限制和安全隔离。仓库级任务还要看：

- 是否理解需求和现有接口；
- 是否搜索了正确文件；
- 修改是否覆盖所有调用方；
- 是否通过原有测试并避免回归；
- 是否引入依赖、权限或数据泄露问题；
- 代码是否可维护，而非只为测试投机。

隐藏测试决定结论的很大一部分。如果隐藏测试覆盖不足，pass rate 可能高估真实
正确性；如果测试依赖网络、时间或随机状态没有固定，失败可能来自 harness。
执行环境必须限制文件、网络、进程和资源，并保留测试日志。

Agent 代码任务还要把轨迹拆开：搜索、计划、编辑、运行测试、读取错误和修复。最
终补丁正确不代表过程高效或安全；一个会反复覆盖用户文件、执行不必要命令的
Agent，即使完成率高，也有很高的实际风险。

### 7.5 RAG Eval：检索命中不等于答案可信

RAG 系统至少包括 query understanding、retrieval、reranking、context
construction 和 grounded generation。评估时应逐段测量。

若相关文档集合为 R，前 k 个检索结果为 K，检索召回率可以写为：

~~~math
\mathrm{Recall@k}=\frac{|R\cap K|}{|R|}
~~~

如果一个问题需要多个证据，单文档命中不能代表足够召回。最终回答还要拆成原子
主张。设支持的主张数为 n_supported，总主张数为 n_claim，则引用支持率为：

~~~math
\mathrm{CitationSupport}
=\frac{n_{\mathrm{supported}}}{n_{\mathrm{claim}}}
~~~

每个主张的支持关系需要人工、规则或可信检索工具核对。引用了一个相关文档但
该文档没有支持具体数字，不能计为支持。

RAG 错误定位可以用消融：

1. 人工提供正确文档，只测试生成和引用；
2. 固定生成模型，更换 retriever；
3. 固定检索结果，更换 reranker；
4. 固定证据，比较不同 prompt 和上下文顺序；
5. 删除一个关键证据，观察模型是否应当拒答；
6. 注入权限边界样本，检查是否泄露其他租户内容。

如果提供正确文档后答案仍然错误，检索不是唯一根因；如果模型在正确证据下能答
对，而线上答错，则应检查召回、重排、截断、权限和引用映射。

### 7.6 Agent Eval：完成任务之外还有副作用

Agent 的一次成功不能只定义为“最终文字正确”。任务契约还要描述：

- 工具调用是否必要；
- 参数是否正确；
- 权限是否合适；
- 失败后是否安全重试；
- 外部写操作是否幂等；
- 是否在预算内完成；
- 是否向用户清楚报告了实际执行结果。

可以把一次 Agent 结果拆成：

~~~math
S_{\mathrm{agent}}=
S_{\mathrm{task}}\land
S_{\mathrm{tool}}\land
S_{\mathrm{permission}}\land
S_{\mathrm{sideeffect}}\land
S_{\mathrm{protocol}}
~~~

这仍然只是分析框架，不应把所有维度压成一个不可解释的布尔值。报告中要分别
列出任务完成、工具正确、权限正确和副作用安全。

测试 Agent 时，应使用仿真环境或最小权限账号。真实写操作、发信、支付、删除和
权限变更必须有隔离、审批或可回滚机制。一个评估 harness 如果让危险动作真实
发生，评估本身就成为事故来源。

### 7.7 多模态 Eval：答案之外要核对证据位置

多模态任务的输入可能是图像、文档、图表、音频或视频。评估要问模型是否真的使
用了正确模态证据，而不是只凭语言先验猜答案。

常见维度包括：

- 物体是否存在；
- 数量、颜色和属性是否正确；
- 空间关系是否正确；
- OCR 字段和表格结构是否正确；
- 图表趋势、数值和单位是否正确；
- 视频事件顺序和说话人时间段是否正确；
- 回答能否定位到区域、页码或时间片段。

OCR 字符错误率可写为：

~~~math
\mathrm{CER}=\frac{S+D+I}{N}
~~~

S、D、I 分别是替换、删除和插入数，N 是参考字符数。视频时序任务可以使用事件
区间的交并比：

~~~math
\mathrm{tIoU}=
\frac{|I_{\mathrm{pred}}\cap I_{\mathrm{gold}}|}
{|I_{\mathrm{pred}}\cup I_{\mathrm{gold}}|}
~~~

对图表问答，不能只看最终数字，还要检查单位、方向、比较基准和从图中取数的证
据。对视觉幻觉，最好把回答拆成原子主张并进行区域或时间段 grounding。

### 7.8 Long-context Eval：从可放入到可使用

长上下文至少有三类不同测试：

1. 定位：能否在开头、中间、结尾找到指定信息；
2. 组合：能否把分散在多段的证据合并；
3. 约束：能否区分版本、权限、冲突来源，并给出引用或正确拒答。

Needle-in-a-haystack 主要测定位，不能代表多证据推理。Lost-in-the-middle
测试提醒我们，证据位置会影响表现。更接近真实工作的测试应包含多文档、相似
干扰、时间版本冲突、长表格、跨章节引用和证据不足样本。

设证据位置为 p，正确率为 A(p)，可以画位置曲线：

~~~math
A(p)=
\frac{\#\{\text{位置为 }p\text{ 且成功的样本}\}}
{\#\{\text{位置为 }p\text{ 的有效样本}\}}
~~~

同时要记录输入 token、输出 token、prefill 时间、峰值显存、队列等待和单位成功
成本。一个只测短 prompt 的“长上下文能力”没有说服力；一个只测单 needle 的
百万 token 成功率也不能推导出跨文档研究能力。

### 7.9 Safety 和 Robustness Eval

安全评估不能只问“拒绝了多少危险问题”。至少同时看：

- unsafe compliance：危险请求被错误满足；
- over-refusal：正常请求被错误拒绝；
- safe completion：拒绝时是否给出适当的低风险帮助；
- prompt injection：不可信内容是否改变权限或系统指令；
- privacy：是否泄露不应暴露的信息；
- tool safety：是否产生越权或不可逆副作用；
- robustness：改写、拼写、语言和多轮上下文变化后是否稳定。

危险请求的错误满足率为：

~~~math
\mathrm{UCR}=
\frac{N_{\mathrm{unsafe\ accepted}}}
{N_{\mathrm{unsafe\ valid}}}
~~~

正常请求的过度拒答率为：

~~~math
\mathrm{OR}=
\frac{N_{\mathrm{benign\ refused}}}
{N_{\mathrm{benign\ valid}}}
~~~

两个分数不能合并后只报一个数。安全风险还应按严重度加权，因为低频的高影响
错误不能被大量低风险样本淹没。对攻击评估，正文和报告应使用抽象意图、合成
载荷或安全标识，不把可直接复制的危险操作步骤放入公开练习。

## 8. 在线 A/B Test：从离线差异到真实因果证据

### 8.1 先定义实验对象和 estimand

A/B test 不是把用户随机分成两组然后看谁的数字大。实验开始前要写清楚：

1. 实验单位是用户、会话、请求还是组织；
2. 谁符合曝光资格；
3. 什么事件算真正曝光；
4. 主指标的分子和分母；
5. 结果要观察多久；
6. 哪些指标是护栏；
7. 哪些行为会触发降级、暂停或回滚。

假设 treatment 组的任务完成率为 p_t，control 组为 p_c，最基本的差异为：

~~~math
\hat\tau=\hat p_t-\hat p_c
~~~

这个差异回答的是“在当前分流、产品界面和观察窗口下， treatment 对目标结果的
平均影响”。它不等于模型在所有场景的纯能力差异。

### 8.2 随机单位和曝光分母

如果同一用户在不同请求中被随机到不同版本，用户记忆、连续追问和任务跨请求
状态会造成干扰。对聊天助手，通常按用户或会话稳定分桶；对单次独立 API 请求，
按请求分桶可能更合适。实验单位应与结果产生的依赖结构匹配。

分母必须是有资格且真正看到 treatment 的对象，而不是所有进入路由的请求。例
如模型加载失败后被降级到旧版本，如果仍把这次请求计为 B 曝光，B 的任务完成率
会被错误估计。应记录 eligible、assigned、exposed、completed 和 observed 等
状态，并明确每个指标使用哪一个分母。

稳定分桶可以使用：

~~~text
bucket = hash(experiment_id + stable_user_id) mod 10000
~~~

这里的 stable_user_id 必须满足隐私和跨设备策略，实验切换时还要避免同一用户在
短时间内反复进入不同条件。哈希只是实现方式，不能替代 SRM 检查和曝光审计。

### 8.3 主指标、护栏和结果成熟窗口

主指标应直接对应用户目标，例如任务完成率、有效采纳率、正确解决率或后续人工
转接率。护栏指标用于限制副作用，例如安全事件、错误率、P95 延迟、成本、投诉
和过度拒答。

LLM 结果经常不是在请求结束时就成熟。用户可能几小时后才采纳代码，客服任务
可能在一周后才知道是否重开，安全事故可能需要人工审查才能确认。将实验在主指
标尚未成熟时停止，会产生删失偏差。应设定观察窗口和 pending 状态，并区分：

- 立即结果：解析成功、首 token、工具调用；
- 短期结果：回答采纳、任务完成、人工修改；
- 延迟结果：重开、留存、投诉、事故确认。

### 8.4 SRM、干扰和新奇效应

如果计划 treatment/control 各占 50%，实际分流是 65%/35%，首先要检查 Sample
Ratio Mismatch，而不是先做显著性检验。可能原因包括缓存、路由、资格过滤、重试、
客户端版本或日志丢失。

用户之间还可能互相影响，例如一个组织共享知识库，部分用户用新版本生成的
答案会被另一组用户阅读。此时请求级独立性假设不成立，需要按组织聚类、限制
共享或使用更合适的实验设计。

新模型刚上线时，用户可能因新鲜感更愿意点击，也可能因为不熟悉格式而暂时降低
采纳。实验至少覆盖完整业务周期，并把短期新奇效应与长期结果分开。

### 8.5 CUPED、比例指标和聚类

如果实验前的用户行为 X 与实验结果 Y 相关，可以用协变量调整降低方差：

~~~math
Y'=Y-\theta(X-\bar X),
\qquad
\theta=\frac{\mathrm{Cov}(Y,X)}{\mathrm{Var}(X)}
~~~

X 必须来自实验曝光前，不能把 treatment 之后的行为放入协变量，否则会改变要估
计的因果对象。CUPED 可能减少所需样本量，但不能修复随机化失败或指标定义错误。

平均响应时延、每次会话 token 和每用户成本常常是比例指标。直接把所有请求的
分子相加再除以分母，和先按用户求比例再平均，回答的对象不同。前者更偏向请求
级总体，后者更偏向典型用户。必须在实验契约里写清楚。

一个用户产生多个会话时，观测之间不独立。朴素标准误会过小，置信区间会过窄。
可以按用户、组织或会话进行 cluster bootstrap，或使用能表达层级结构的模型。

### 8.6 一个在线实验案例

新模型 B 的离线答案正确率比 A 高 3 个百分点，团队做了 10% 灰度。实验数据
显示：

| 指标 | A | B | 差异 |
| --- | ---: | ---: | ---: |
| 任务完成率 | 0.41 | 0.43 | +0.02 |
| 代码采纳率 | 0.36 | 0.38 | +0.02 |
| P95 延迟 | 4.8 s | 5.7 s | +0.9 s |
| 单任务成本 | 1.00 | 1.28 | +28% |
| 高严重度安全事件 | 2 | 2 | 0 |

下一步不能只看 +2 个百分点是否显著。应检查：

1. 真实曝光是否按用户稳定分桶；
2. 任务完成窗口是否已经成熟；
3. 提升是否集中在低价值任务；
4. 延迟和成本是否超过业务预算；
5. 是否有尚未成熟的投诉或安全审查；
6. 是否可以通过路由、缓存或输出预算降低成本。

如果主要指标提升但成本超过预算，合理决策可以是继续受限实验并优化成本，而
不是把统计显著误写成“可以全量”。

## 9. 统计显著性与实验设计

### 9.1 差异、噪声和不确定性

样本中的分数差异来自真实效果和随机波动的混合。统计分析的任务不是证明模型
“绝对变强”，而是在明确假设和抽样机制下，估计差异及其不确定性。

显著性不等于重要性。几百万样本可以让 0.1% 的提升达到很小的 p-value，但如果
成本增加 30%，这点提升未必值得。反过来，小样本不显著也不等于没有效果，可能
只是区间太宽。

报告至少应同时给出：

- 效果估计；
- 置信区间；
- 样本量和有效分母；
- 分层结果；
- 实验停止规则；
- 业务最小有意义差异；
- 成本、安全和延迟影响。

### 9.2 比例指标的近似区间

如果 n 个独立样本中有 x 个成功，比例为 p_hat=x/n。在样本量足够、近似条件合
适时，简单区间可写成：

~~~math
\hat p\pm z_{1-\alpha/2}
\sqrt{\frac{\hat p(1-\hat p)}{n}}
~~~

真实工程中更推荐 Wilson 区间或 bootstrap，尤其是比例接近 0 或 1、样本较少或
安全事件很低频时。公式的作用是说明方差如何随 n 变化，不是让读者机械套用。

两组比例差的标准误还取决于两组各自的样本量和比例。若用户存在重复观测，不能
直接把请求数当成独立样本数；有效样本量会小于原始请求数。

### 9.3 Pairwise 的配对分析

同一个问题同时由旧模型和新模型回答时，结果是配对的。对二元正确/错误结论，
可以统计：

- b：旧模型正确、新模型错误；
- c：旧模型错误、新模型正确。

McNemar 检验主要关注不一致对 b 和 c，而不是把两组独立样本的比例硬套进去。差
异的方向可以看：

~~~math
\Delta_{\mathrm{paired}}
=\frac{c-b}{n}
~~~

如果 b 和 c 很接近，总体差异可能只是噪声；如果 c 明显多于 b，还要查看这些改变
是否集中在特定领域或由判定器偏差造成。

Pairwise preference 不是天然独立的二项样本。多个比较可能来自同一用户、同一题
目或同一标注员，需要使用配对、分层或聚类方法处理。

### 9.4 Bootstrap、重复解码和聚类

Bootstrap 的基本做法是从观测样本中有放回重采样，每次计算目标差异，重复很多次
后用经验分布估计区间。它适合复杂指标、分层加权和非正态分布，但重采样单位必
须与独立性假设一致。

如果一个问题做了多次随机解码，解码结果不是互相独立的业务任务。可以按原始问
题聚类重采样；如果想研究采样预算，就把问题作为实验单位，把候选集合的聚合结
果作为该单位的结果。

线上一个用户有多个请求时，按请求 bootstrap 会低估相关性。按用户或组织聚类
通常更合理，但仍需检查实验单位、指标产生方式和用户跨组干扰。

### 9.5 样本量和功效

在实验前做样本量估计，是为了知道“如果真实提升达到业务关心的最小差异，我有
多大概率发现它”。它不是为了实验后挑一个最有利的假设。

样本量受以下因素共同影响：

1. 基线成功率；
2. 最小有意义差异；
3. 显著性水平；
4. 统计功效；
5. 分流比例；
6. 指标噪声和用户聚类；
7. 多重比较和分层数量。

低频安全事件通常需要更多样本，或者采用富集抽样、红队离线测试和风险加权分析。
不能因为线上自然流量中事件少，就把没有观测到事件写成风险为零。

### 9.6 多重比较和提前停止

同时看几十个指标和切片，至少有一些结果会因为随机波动显著。应预先指定主指
标、关键护栏和探索性指标；多重比较可使用 Bonferroni、Holm 或 FDR 等方法，
具体选择取决于错误控制目标。

实验进行中不断查看结果，看到显著就停止，会放大假阳性。可以采用预先声明的
固定样本量，或使用经过设计的序贯分析。临时停止可以出于安全事故，但要记录原
因并把它与普通效果确认区分开。

### 9.7 消融和因果解释

如果新系统同时换了模型、prompt、retriever、reranker 和 UI，就算总体提升，
也不能知道哪个变化起作用。消融实验通过固定其他因素，逐个移除或替换组件，估
计贡献。

设完整系统的结果为 Y_full，去掉组件 j 的结果为 Y_-j，则最简单的消融差异为：

~~~math
\Delta_j=Y_{\mathrm{full}}-Y_{-j}
~~~

它只有在实验条件、数据和随机性受控时才有解释力。多个组件之间存在交互时，单
独消融的差异不能简单相加；可以使用析因实验或明确把结论限定为该配置下的局部
差异。

### 9.8 统计证据与发布决策

统计显著并不自动意味着应该发布。发布判断应先查看效果大小和区间，再检查目标
切片、严重度加权风险、成本、延迟、协议成功率、回归样例和灰度结果。统计显著
只是证据的一部分，最终决定还需要业务约束、结果成熟度和可恢复能力。

## 10. Error Analysis 与 Regression Suite

### 10.1 分数为什么必须回到样本

如果新版本总分从 0.80 变成 0.83，我们还不知道：

- 是普通问题提升，还是核心任务提升；
- 是旧错新对，还是旧对新错；
- 是答案错，还是引用错；
- 是模型错，还是检索和工具错；
- 是真实改善，还是 judge 版本变化。

样本级 diff 至少要保存 old output、new output、判定结果、证据、版本和失败标签。
定义旧版本正确而新版本错误的集合：

~~~math
\mathcal{R}_{\mathrm{new}}
=\{i:o_i=1\land n_i=0\}
~~~

回归率为：

~~~math
R_{\mathrm{reg}}=
\frac{|\mathcal{R}_{\mathrm{new}}|}{m}
~~~

分母 m 是有效比较样本数。若有严重度权重，还可以计算：

~~~math
R_{\mathrm{weighted}}=
\frac{\sum_i w_i\mathbb{I}[o_i=1,n_i=0]}
{\sum_i w_i\mathbb{I}[o_i=1]}
~~~

两个指标回答不同问题：前者是样本比例，后者更关心业务损失。

### 10.2 错误 taxonomy 要能导出动作

“模型不聪明”“幻觉”“推理失败”通常太粗。更可行动的标签包括：

- retrieval_miss：相关证据没有召回；
- rerank_error：证据召回但排序或截断丢失；
- evidence_conflict：多个版本冲突且未处理；
- generation_hallucination：输出超出证据；
- citation_error：引用存在但不支持主张；
- protocol_error：结构化字段或工具参数错误；
- tool_failure：工具超时、权限或外部服务错误；
- reasoning_error：中间约束或组合推理失败；
- safety_policy_error：漏拒或误拒；
- evaluator_error：判定器或标注存在问题。

标签应该与修复动作有可检验联系。若标为 retrieval_miss，下一步就应做人工提供
文档或替换 retriever 的对照；若标为 protocol_error，就应检查 schema、解析器和
重试，而不是立刻增加训练数据。

### 10.3 根因分析的对照实验

一个失败样本往往有多个可能原因。可以建立干预矩阵：

| 干预 | 保持不变 | 想区分的假设 |
| --- | --- | --- |
| 人工注入正确证据 | 模型和 prompt | 检索是否是根因 |
| 固定证据更换模型 | 证据和协议 | 模型生成是否是根因 |
| 固定模型更换 prompt | 模型和证据 | 指令契约是否是根因 |
| 关闭工具重跑 | 输入和模型 | 工具链是否引入错误 |
| 使用可靠程序判定 | 输出 | judge 是否误判 |

如果一个干预能恢复结果，它支持某个假设，但仍不能自动证明唯一根因。需要在多
个相似样本和未见样本上重复。错误分析的质量取决于证据和对照，而不是标签数量。

### 10.4 从错误簇到修复优先级

可以用频次、严重度、暴露量和修复成本做资源排序。例如：

~~~math
P_k=
\frac{N_k}{N_{\mathrm{all}}}
\times
\bar w_k
\times
\mathrm{exposure}_k
\times
\mathrm{recoverability}_k
~~~

这个 P_k 只是工作排序分数。高频低风险的格式问题可能先修复，因为它很便宜；
低频高风险的越权问题可能必须立即处理，即使它的总体占比很小。排序规则应在
业务中公开，避免把方便修复误当成最重要。

### 10.5 Regression Suite 的组成

一个有生命力的 regression suite 可以包含：

1. 历史线上事故；
2. 已修复的高严重度失败；
3. 容易受 prompt 变化影响的格式样本；
4. 关键客户的代表性任务；
5. 版本冲突、权限和工具幂等边界；
6. judge 曾经误判的校准样本；
7. 重要但低频的安全样本。

每个样本要有稳定判定器、来源、加入原因、严重度、适用组件和预期行为。把历史
事故的原始敏感内容直接复制到所有开发环境可能造成隐私和安全问题，可以使用
脱敏、合成等价样本，并保留受控的原始审计记录。

Regression suite 不能不断膨胀到每次运行都不可承受。可以按快速集、完整集、高
风险集和发布前集分层；但分层不应让高风险样本在快速迭代中完全消失。

### 10.6 防止回归集反过来污染测试

一个样本加入 regression suite 后，团队通常会看到它并据此修改系统。它从那一
刻起不再是未知泛化测试。可以把评估资产分成：

- 公开或开发集：允许调试；
- 回归集：用于防止已知问题复发；
- 私有 holdout：用于检验未见泛化；
- 线上抽样：用于检验分布变化。

报告中明确每个样本的使用历史，比把所有集合都叫 test set 更可信。

### 10.7 四象限版本差异

逐样本比较旧、新结果，可以得到四类：

| 旧版本 | 新版本 | 解释 |
| --- | --- | --- |
| 对 | 对 | 稳定正确 |
| 错 | 对 | 修复或偶然改善 |
| 对 | 错 | 回归，需要调查 |
| 错 | 错 | 未解决，或判定器仍不可靠 |

进一步按任务和严重度切片，才能知道总分提升是否值得。评估报告中至少应展示
“错到对”和“对到错”的数量、例子和分布。

## 11. Eval Platform 的系统设计

### 11.1 系统边界

一个支持模型、prompt、RAG 索引和 Agent 工具链的评估平台，至少要支持离线运行、
人工评估、回归测试和发布决策。它的核心任务是保证一次评估可复现、可追踪、可
分析、可审计，而不是单纯展示一个 dashboard。

平台的边界应包括数据、执行、评分、分析、报告和治理六个部分。若只建设执行脚
本和可视化页面，却没有版本清单、样本血缘、评分器校准和权限控制，平台只能产
生数字，不能解释数字，也不能保护评估数据。

### 11.2 数据层

数据层需要管理：

- benchmark、golden set、regression suite 和线上抽样；
- 样本输入、参考答案、rubric 和判定器；
- 任务、难度、语言、风险和租户等元数据；
- 数据版本、来源、标注和使用历史；
- 脱敏、权限和私有 holdout。

样本 ID 应稳定，但内容版本必须可变更且可追踪。一个报告必须能回溯到它使用
的样本清单、判定器和 rubric，而不是只能看到最终平均数。

### 11.3 执行层

执行层负责把一个版本配置运行在样本上，至少记录：

1. 模型 artifact 和 tokenizer；
2. system、developer、user prompt；
3. decoding 参数和随机种子；
4. RAG retriever、reranker、索引和过滤条件；
5. Agent 工具 schema、权限和模拟环境；
6. 重试、超时、降级和取消；
7. 输入输出 token、延迟、显存和成本；
8. 完整 trace 和错误状态。

执行层应支持幂等重跑。重跑必须说明是相同随机种子、不同采样、失败重试还是环境
修复；否则两个结果无法解释。

### 11.4 评分层

评分层可以按确定性逐渐增加不确定性：

1. schema 和字段检查；
2. exact match、数值误差和规则；
3. 编译、单元测试、隐藏测试和 verifier；
4. 引用、grounding 和权限判定；
5. LLM judge；
6. 人工标注和专家仲裁。

高成本的人工和专家资源应集中在高风险、低一致性、程序判定失败和版本分歧样本，
而不是让所有样本都走最昂贵路径。

### 11.5 分析层

分析层输出：

- 总体和加权指标；
- 任务、语言、难度、长度和风险切片；
- 置信区间和显著性；
- 样本级 old/new diff；
- 错误类型与严重度；
- judge 与人工的一致性；
- 成本、延迟和资源曲线；
- 结果成熟度和 pending 样本；
- 失败后续动作。

报告应该支持从柱状图点击到具体样本，并能查看原始证据和版本 manifest。否则
分析人员仍然需要手工拼日志，平台没有缩短诊断路径。

### 11.6 决策层和治理层

决策层不能只输出一个总布尔值。更好的报告包含三列：

| signals | actions | decision |
| --- | --- | --- |
| 哪些主指标、切片和护栏通过或异常 | 需要复核、修复、补测或继续灰度什么 | 继续实验、受限发布、修复后重测或保留旧版 |

治理层负责权限、脱敏、审计、holdout 保护、模型和 judge 版本冻结、数据使用历史
和报告可追溯性。评估数据经常含有用户内容、企业文档和安全样本，平台不能为了
方便调试而让所有人读取原文。

### 11.7 一份可复现的评估 manifest

可以用如下结构描述一次运行：

~~~yaml
run_id: eval-2026-08-10-042
model:
  artifact: model-b
  revision: sha256:...
prompt:
  name: enterprise-rag
  revision: 17
data:
  set: enterprise-golden
  revision: 9
  split: holdout
retrieval:
  index_revision: 2026-08-09
  reranker: reranker-3
judge:
  artifact: judge-2
  rubric_revision: 4
runtime:
  temperature: 0
  max_output_tokens: 1024
  seed: 7
metrics:
  - answer_correctness
  - citation_support
  - p95_latency
  - unit_cost
~~~

这里的省略号表示真正的不可变 artifact 标识，不是让系统接受任意文本。manifest
的价值在于把“同一个模型”扩展成完整实验条件。模型权重没变，prompt 或 reranker
变了，结果也不应被标为同一次运行。

### 11.8 失败恢复和结果状态

平台需要区分：

- completed：任务完成且结果可评分；
- model_error：模型或 runtime 失败；
- protocol_error：输出无法解析；
- evaluator_error：判定器失败；
- pending：结果仍在观察窗口；
- invalid_data：样本或标签有问题。

重试策略必须记录原因。对随机采样任务，重试可能改变 estimand；对网络超时，
重试可能只是恢复一次本来应计入可用性的失败。把重试后的最好结果直接覆盖原始
结果，会高估系统表现。

## 12. 最小可运行的评估体系完整性诊断 Demo

下面的程序不是模型质量的真值判定器，也不会因为一个数字达到阈值就替代人工审
查。它把一份评估计划拆成若干可观察的组成部分，再把质量、风险、成本和后续行
动并列输出。这样做的重点是让读者看到：评估覆盖可以看起来完整，却仍然缺少
judge 校准、多模态与长上下文证据，或者超出成本预算。

~~~python
from collections import Counter


plan_rubric = {
    "goal": 2,
    "data_slices": 2,
    "metrics": 2,
    "human_eval": 1,
    "judge_calibration": 2,
    "contamination": 2,
    "reasoning_code_math": 2,
    "multimodal_longctx": 2,
    "safety": 2,
    "online_ab": 2,
    "statistics": 2,
    "error_analysis": 2,
    "regression_suite": 2,
    "release_decision": 2,
}

plan_tags = {
    "goal",
    "data_slices",
    "metrics",
    "human_eval",
    "contamination",
    "reasoning_code_math",
    "safety",
    "online_ab",
    "statistics",
    "error_analysis",
    "regression_suite",
    "release_decision",
}

missing = [name for name in plan_rubric if name not in plan_tags]
score = sum(points for name, points in plan_rubric.items() if name in plan_tags)
max_score = sum(plan_rubric.values())

cases = [
    {"id": "qa", "score": 0.86, "weight": 1.0, "slice": "chat"},
    {"id": "rag", "score": 0.74, "weight": 1.5, "slice": "rag"},
    {"id": "code", "score": 0.68, "weight": 1.2, "slice": "code"},
    {"id": "safety", "score": 0.92, "weight": 2.0, "slice": "safety"},
]

weighted_score = sum(
    case["score"] * case["weight"] for case in cases
) / sum(case["weight"] for case in cases)
slice_scores = {case["slice"]: case["score"] for case in cases}

pairwise = Counter({"win": 7, "tie": 2, "loss": 3})
pairwise_total = sum(pairwise.values())
win_rate = (
    pairwise["win"] + 0.5 * pairwise["tie"]
) / pairwise_total

risk_metrics = {
    "attack_success": 0.02,
    "over_refusal": 0.08,
    "p95_latency_delta": 0.18,
    "cost_delta": 0.30,
    "high_regressions": 0,
}

signals = {
    "plan_coverage": score / max_score >= 0.85,
    "weighted_score": weighted_score >= 0.80,
    "pairwise_win_rate": win_rate >= 0.60,
    "safety": (
        risk_metrics["attack_success"] <= 0.05
        and risk_metrics["over_refusal"] <= 0.10
    ),
    "latency": risk_metrics["p95_latency_delta"] <= 0.20,
    "cost": risk_metrics["cost_delta"] <= 0.25,
    "regression": risk_metrics["high_regressions"] == 0,
}

actions = []
if missing:
    actions.append("补充评估组件: " + ", ".join(missing))
if not signals["cost"]:
    actions.append("复核单位成本、输出长度和路由预算")
if not signals["safety"]:
    actions.append("复核安全高风险样本并进行人工审查")
if not signals["regression"]:
    actions.append("调查高严重度版本回归")

if missing or not signals["cost"]:
    decision = "revise_plan_and_review_cost"
else:
    decision = "continue_with_review"

print(
    "coverage=",
    {
        "score": score,
        "max": max_score,
        "ratio": round(score / max_score, 3),
        "missing": missing,
    },
    sep="",
)
print("weighted_score=", round(weighted_score, 3), sep="")
print("slice_scores=", slice_scores, sep="")
print("pairwise_win_rate=", round(win_rate, 3), sep="")
print("risk_metrics=", risk_metrics, sep="")
print("signals=", signals, sep="")
print("actions=", actions, sep="")
print("decision=", decision, sep="")
~~~

运行时，关键输出应接近：

~~~text
coverage={'score': 23, 'max': 27, 'ratio': 0.852, 'missing': ['judge_calibration', 'multimodal_longctx']}
weighted_score=0.812
slice_scores={'chat': 0.86, 'rag': 0.74, 'code': 0.68, 'safety': 0.92}
pairwise_win_rate=0.667
risk_metrics={'attack_success': 0.02, 'over_refusal': 0.08, 'p95_latency_delta': 0.18, 'cost_delta': 0.3, 'high_regressions': 0}
signals={'plan_coverage': True, 'weighted_score': True, 'pairwise_win_rate': True, 'safety': True, 'latency': True, 'cost': False, 'regression': True}
actions=['补充评估组件: judge_calibration, multimodal_longctx', '复核单位成本、输出长度和路由预算']
decision=revise_plan_and_review_cost
~~~

这里有三个值得注意的地方。

第一，coverage 只检查评估计划是否覆盖 rubric 中的组成部分，不检查计划中的指标
定义、数据质量和证据是否真的正确。因此它是完整性审计工具，不是模型质量证明。

第二，weighted_score、pairwise_win_rate 和 risk_metrics 观察的是不同对象。不能
因为前两个信号通过，就抹掉成本超预算。

第三，decision 不是永久结论。补充 judge 校准和多模态长上下文后，还要用事实、
案例和追问重新审查；成本问题则需要另一个工程实验验证。

## 13. 常见设计误区与修正路径

### 13.1 只报 benchmark 名字

问题不在于提到 benchmark，而在于没有说明它测量什么、样本是否代表目标、判定
是否可靠、有没有污染和外部有效性风险。

修正方式是先说任务目标，再把 benchmark 放到证据组合中。例如代码能力可以同时
使用公开函数集、内部仓库任务、隐藏测试、静态安全检查和人工可维护性评估。

### 13.2 只看平均分

平均分会遮住用户群体、语言、风险和长度切片。修正时至少给出关键切片、样本数、
分母和 old/new diff；低频高影响任务要单独报告。

### 13.3 把 LLM judge 当作真值

Judge 需要人工 gold set、顺序交换、版本冻结和不确定样本路由。可执行任务应
优先使用程序判定器，judge 适合补充开放式质量而不是替代外部证据。

### 13.4 把显著等同于值得发布

先报告效果大小和区间，再考虑业务最小差异、成本、延迟、安全、回归和灰度结果。
统计显著只说明随机波动不是唯一的合理解释。

### 13.5 忽略分母和结果成熟

任务完成率、采纳率、延迟和安全事件的分母不同。曝光失败、降级请求、重复请求
和尚未成熟的结果都要有明确状态，不能为了让数字好看而删除。

### 13.6 用最终结果掩盖工具和协议错误

Agent 最终回答错误时，先查看工具参数、权限、返回内容、重试和解析。RAG 回答
错误时，先区分检索没召回、上下文被截断和生成超出证据。错误分类应该能导出
下一步实验。

### 13.7 只优化已知测试集

Regression suite 能保护已知修复，却不能证明未知泛化。必须保留独立 holdout、
时间切分或线上抽样，并记录数据使用历史。

## 14. 综合练习：从目标到实验

### 14.1 评估体系设计练习

1. 设计一个通用 chat model 的评估体系，要求说明目标、数据、指标、人工评估、
   线上实验和发布规则。
2. 解释 benchmark、golden set 和 regression suite 的区别，并说明三者怎样共同
   使用。
3. 说明离线指标提升而线上满意度下降时的排查顺序。

### 14.2 测量器选择练习

1. Human eval、pairwise eval 和 LLM judge 分别适合什么任务？
2. 如何发现 judge 的位置偏差和长度偏差？
3. 什么时候必须使用程序判定器或领域专家？
4. 如何报告人工标注的一致性和分歧？

### 14.3 能力专项评估练习

1. 设计一个 reasoning eval，区分结果、过程和泛化。
2. 设计一个 code eval，覆盖函数、仓库、隐藏测试和安全沙箱。
3. 设计一个 RAG eval，拆分检索、重排、证据构造、生成和引用。
4. 设计一个多模态 hallucination eval，覆盖 OCR、图表、视频和 grounding。
5. 设计一个长上下文 eval，说明 needle 测试的局限和真实多证据任务。
6. 设计 safety 与 robustness eval，同时报告漏拒和误拒。

### 14.4 实验与统计练习

1. 一个新版本胜率为 52%，基线为 48%，如何判断结果？
2. 如何选择随机单位，如何检查 SRM？
3. 如何使用 CUPED，哪些协变量不能使用？
4. 多个切片和指标同时显著时如何控制误报？
5. 一个用户有多个请求时，为什么不能把请求当作独立样本？

### 14.5 评估平台设计练习

1. 设计支持模型、prompt、RAG 和 Agent trace 的评估平台。
2. 设计错误样本从线上日志进入 regression suite 的流程。
3. 设计一个能够保护私有 holdout、防止污染并支持人工审计的评估系统。

### 14.6 小练习：写出自己的任务契约

选择一个你熟悉的任务，补全以下字段：

~~~text
任务名称:
目标用户:
输入和上下文:
允许的工具:
成功定义:
部分成功定义:
必须拒绝的情况:
主要指标:
关键护栏:
结果成熟窗口:
失败后要保存的证据:
~~~

然后分别写出一个自动判定器、一个人工 rubric 和一个线上指标。若三者的分母、
分析单位或成功定义不同，说明差异是有意设计还是契约不一致。

### 14.7 小练习：解释一次相反结果

给定以下结果：

| 证据 | 旧版 | 新版 |
| --- | ---: | ---: |
| 公开问答准确率 | 0.80 | 0.84 |
| 内部高价值任务 | 0.76 | 0.74 |
| 人工偏好 | 0.51 | 0.54 |
| 引用支持率 | 0.87 | 0.78 |
| 单任务成本 | 1.00 | 1.35 |

不要直接回答“新版本好”或“旧版本好”。写出至少三个可区分的假设，并为每个
假设设计一个最小对照实验。好的答案应说明哪些结果已经知道，哪些结果仍然不
能从表格推出。

## 15. 资料与证据边界

下面的资料按证据性质分组。论文和官方规范可以支持方法定义与实验结论，但不能
自动证明某个闭源模型在生产环境中的表现。社区实现适合帮助理解工程接口，使用
时要核对版本、配置和复现实验。

### 15.1 评估框架与人工评估

- OpenAI Evals：官方开源评估框架，适合查看 eval 数据和运行结构；
  https://github.com/openai/evals
- HELM：Stanford CRFM 的多维度语言模型评估框架；
  https://crfm.stanford.edu/helm/latest/
- MT-Bench：研究多轮对话和模型评审的论文；
  https://arxiv.org/abs/2306.05685
- Chatbot Arena：成对用户偏好和排名方法的研究资料；
  https://arxiv.org/abs/2403.04132
- CheckList：通过行为测试发现 NLP 系统能力缺口的方法；
  https://arxiv.org/abs/2005.04118
- G-Eval：使用 LLM 进行文本评估的研究论文；
  https://arxiv.org/abs/2303.16634

这些资料的证据范围不同。HELM 和 benchmark 论文支持评估维度与实验设计，不能
替代目标产品的内部样本；MT-Bench 和 Arena 展示了成对偏好与 judge 的实践，但
也需要结合人工校准、时间变化和任务切片理解。

### 15.2 推理、代码和数学

- HumanEval：函数级代码生成评估；
  https://arxiv.org/abs/2107.03374
- APPS：更接近编程问题解决的评估数据；
  https://arxiv.org/abs/2105.09938
- MATH：分层数学问题数据集；
  https://arxiv.org/abs/2103.03874
- Self-Consistency：多条推理路径聚合的方法；
  https://arxiv.org/abs/2203.11171
- Let's Verify Step by Step：训练和使用数学过程验证器的研究；
  https://arxiv.org/abs/2305.20050

这些资料可以支持“为什么要执行验证、为什么要区分 pass@1 和 pass@k、为什么
要测试过程和泛化”等方法论。它们不应被直接改写成“某模型一定具备推理能力”。

### 15.3 多模态与长上下文

- VQA：视觉问答数据与任务；
  https://arxiv.org/abs/1505.00468
- DocVQA：文档视觉问答；
  https://arxiv.org/abs/2007.00398
- ChartQA：图表问答；
  https://arxiv.org/abs/2010.11416
- LongBench：长上下文语言模型评估；
  https://arxiv.org/abs/2308.14508
- Lost in the Middle：长上下文中证据位置影响的研究；
  https://arxiv.org/abs/2307.03172
- RULER：长上下文合成和能力评估；
  https://arxiv.org/abs/2404.06654
- AgentBench：面向 Agent 的多环境评估；
  https://arxiv.org/abs/2308.03688

Needle 测试、公开长文档 benchmark 和真实业务长任务应被视为互补证据。公开数据
能够帮助横向比较，但不能单独证明某个服务在其 tokenizer、runtime、并发和成本
约束下可用。

### 15.4 安全与治理

- NIST AI Risk Management Framework；
  https://www.nist.gov/itl/ai-risk-management-framework
- NIST AI 600-1 Generative AI Profile；
  https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf
- OWASP Top 10 for Large Language Model Applications；
  https://owasp.org/www-project-top-10-for-large-language-model-applications/

NIST 和 OWASP 适合建立风险类别、治理和应用安全检查；它们不是某个模型安全
分数的统一 benchmark。安全报告仍需说明威胁模型、攻击者能力、样本来源、人工
审查和未覆盖风险。

### 15.5 在线实验与统计

- Kohavi 等人的在线受控实验资料，讨论随机化、指标、实验可靠性和工程陷阱；
  https://www.exp-platform.com/
- CUPED 方法的原始研究入口；
  https://dl.acm.org/doi/10.1145/2433396.2433413
- Sample Ratio Mismatch 诊断论文（ACM DOI）；
  https://doi.org/10.1145/3292500.3330722

这些资料支持实验设计和方差降低的原理。实际项目还要结合产品的曝光定义、用户
依赖、结果成熟窗口和安全响应流程；公式不能替代实验审计。

## 16. 本章小结

评估工作的核心不是堆叠更多 benchmark，而是构造一条可信的证据链：

1. 明确用户目标和任务契约；
2. 设计有血缘、分层和版本的数据；
3. 选择与任务匹配的程序、人工、judge 和线上测量；
4. 控制污染、偏差、相关性和统计不确定性；
5. 把结果拆到关键切片、样本和错误根因；
6. 同时报告质量、风险、延迟、成本和结果成熟度；
7. 用灰度、修复、回归和 holdout 把评估接到后续决策。

Human eval、pairwise eval、LLM judge、自动指标和 A/B test 都只是测量工具。它们
观察的对象不同，误差结构不同，适用边界也不同。推理、代码、数学、RAG、多模态、
长上下文、Agent 和安全任务都不能被一个总分概括。

当分数相反、污染无法排除，或错误可能来自检索也可能来自模型时，评估结论不应
停在一句判断，而应该给出分母、对照、证据、失败边界和下一步实验。能把分数变
成可复核行动，才是评估体系的价值。
