# 第一章：评估总览

模型发布报告通常先给出一张分数表：知识题、数学题、代码题、长上下文、
安全题、多模态题各有一个数字。初学者容易把最高的数字当成“模型更强”的
证明，工程团队也容易在一个平均分提升后直接讨论上线。

真正的评估更接近一次证据调查。我们要知道模型在什么任务上变好了，变化是否
来自模型本身，是否牺牲了另一类任务，结果能否复现，线上用户是否真的受益，
以及一次失败会带来什么安全、成本和业务后果。一个模型可以在 GPQA 上提升，
却不适合企业客服；也可以在公开代码题上提升，却在真实仓库修复任务中退化。

对小白来说，评估就是回答“它做对了吗”。对专家来说，评估还要回答：

1. 什么算作一次任务成功，分母是什么；
2. 结果由模型、prompt、工具、数据还是 scaffold 决定；
3. 误差来自抽样、标注、judge、解码还是环境；
4. 这个分数是否能外推到目标用户和目标风险；
5. 质量、延迟、安全、成本之间如何共同决定部署策略。

因此，本章不把评估写成一张排行榜，也不把上线判断压成一个总布尔值。全章
围绕下面的证据链展开：

~~~text
任务契约
  -> 数据与参考答案
  -> 模型和系统协议
  -> 指标、标注与运行器
  -> 切片、误差和统计不确定性
  -> 离线/线上证据
  -> 可解释的产品决策
~~~

后续章节会分别深入 benchmark 设计、人工评测、pairwise eval、LLM-as-a-Judge、
污染检测、reasoning/code/math eval、多模态与长上下文评估、安全评估、在线实验、
统计显著性和 error analysis。本章先建立它们之间的边界，让读者看到一张分数表
时知道应该追问什么。

## 1. 评估不是一个分数，而是一组证据

### 1.1 能力、可靠性、安全和效率是不同维度

一个生产模型至少有下面几类证据：

| 维度 | 核心问题 | 典型观察 |
| --- | --- | --- |
| 任务能力 | 它能不能完成目标任务 | exact match、代码测试、任务成功率 |
| 事实与证据 | 它的回答是否有依据 | citation support、evidence recall、unsupported claim |
| 指令与协议 | 它是否遵守格式和工具协议 | JSON 合法率、参数正确率、stop reason |
| 稳定性 | 换样本、长度、语言后是否仍然工作 | 方差、切片回归、位置敏感性 |
| 安全 | 应拒绝的是否拒绝，不应拒绝的是否可用 | attack success、over-refusal、越权调用 |
| 效率 | 完成一次任务要付出多少资源 | TTFT、TPOT、GPU-hours、单位成功成本 |
| 产品价值 | 用户是否真的完成了工作 | 完成率、复问率、转人工率、留存 |

这些维度不能随意相加。一个高风险工具调用的安全失败，不能被普通聊天的
质量提升抵消；一个延迟很低但回答经常不正确的模型，也不能称为产品成功。

可以把一次评估结果写成向量：

~~~math
\mathbf{E}
=
(
Q_{\mathrm{task}},
Q_{\mathrm{evidence}},
Q_{\mathrm{protocol}},
Q_{\mathrm{safety}},
L_{\mathrm{latency}},
C_{\mathrm{success}}
)
~~~

质量项、延迟项和成本项的单位不同，不能未经说明就合并成一个数字。如果业务
确实需要排序，可以定义权重，但必须同时保留原始分量：

~~~math
S_{\mathrm{product}}
=
\sum_{j=1}^{m}\alpha_j E_j,
\qquad
\sum_{j=1}^{m}\alpha_j=1
~~~

alpha_j 是业务权重，而不是自然真理。高风险约束通常应作为单独的最低要求
处理，不能让普通流量的高分抵消安全事故。

### 1.2 一个分数能回答什么，不能回答什么

假设某模型在 MMLU-Pro 上提高 3 个百分点，这个结果可以说明在固定版本、固定
prompt、固定 scoring script 下，它在该闭集多学科题上的平均成绩提高了。它不能
直接说明：

- 中文客服是否更有帮助；
- RAG 引用是否准确；
- 工具参数是否会重复提交；
- 长上下文中间位置的证据是否能找到；
- 代码补丁是否能通过隐藏测试；
- 延迟和单位成功成本是否更低。

同样，线上点赞率提升也不能单独证明模型推理能力提升，因为 prompt、产品 UI、
流量分配、用户群和回答长度都可能同时改变。评估的价值正是把这些可能原因拆开。

### 1.3 小白视角：先问测试题和我的任务像不像

如果你准备做一个合同问答助手，先拿用户真实会问的问题和 MMLU 题目对比：
前者可能需要读取版本化文档、引用条款、拒绝法律意见和识别权限；后者通常
是一个独立的多选题。它们可以互相提供信息，却不是同一项测试。

一个简单判断法是把目标任务写成四元组：

~~~text
输入是什么
输出必须满足什么
什么证据可以判定成功
失败会造成什么后果
~~~

如果 benchmark 没有覆盖这四件事，它最多是能力旁证，不是产品验收的直接证据。

### 1.4 专家视角：评估边界要写进报告

一份可审计的评估报告至少要说明：

1. 模型 revision、tokenizer 和 chat template；
2. benchmark 的版本、split、发布日期和样本过滤；
3. system prompt、few-shot、CoT、工具和 verifier 条件；
4. 采样温度、候选数、最大输出、停止规则和随机种子；
5. 评分器、人工 rubric、judge model 和聚合方法；
6. 样本数、置信区间、失败样本和已知污染风险；
7. 目标产品与 benchmark 之间哪些地方相似，哪些地方不同。

缺少这些字段时，报告里的“提升”只能作为线索，不能作为可复现实验结论。

## 2. 为什么大模型评估比传统分类更难

### 2.1 输出是开放的

传统分类通常有固定标签，模型输出可以直接和 gold label 比较。大模型回答
可能有多种正确表达，还可能同时包含事实、推理、格式和安全问题。

例如“如何备份数据库”可能有三套都正确的方案，但其中一套遗漏了恢复演练，
另一套给出了不安全的权限配置。单一字符串相等不能描述这种差异。

因此开放式任务往往需要组合：

- 程序化检查，例如 schema、编译、单元测试；
- 参考答案或证据核对；
- 人工 rubric；
- 成对偏好；
- 任务环境中的最终状态检查。

### 2.2 能力是多维的

模型可能在数学上进步，在事实性上没有变化，在风格上变得更简洁，但在中文
长文档上退化。总体平均分只有在任务权重、风险和样本分布都合理时才有意义。

把不同任务直接平均之前，先问：

1. 每类任务样本量是否相近；
2. 每类任务的业务权重是否相近；
3. 是否有不能被抵消的安全约束；
4. 不同指标的分母是否可比较。

### 2.3 解码预算会改变结论

数学题用一次 greedy 生成，和用 32 个候选、self-consistency、verifier 重新
排序，测到的不是同一个系统。代码题的 pass@1 和 pass@10 也代表不同的调用
成本和产品体验。

如果候选数为 k、每次生成成本为 c，粗略生成成本约为：

~~~math
C_{\mathrm{generate}}
\approx
kc
~~~

如果候选质量提高但成本和延迟也显著提高，报告必须把这两个事实放在一起。

### 2.4 用户分布会漂移

离线数据通常是固定快照，线上输入却会随着季节、产品入口、语言、地区和攻击
方式变化。一个在英文短问答上的提升，可能无法外推到中文长上下文或工具调用。

因此要同时拥有：

1. 稳定的长期回归集；
2. 代表当前用户的滚动样本；
3. 专门覆盖新风险的动态样本；
4. 隔离的最终测试集。

### 2.5 benchmark 会被污染

公开题目可能进入预训练语料、微调数据、提示词模板或后续人工调参记录。
污染不一定是故意作弊，也可能是模型已经见过题目和标准答案。

污染风险高的 benchmark 仍然有价值，但应与时间切分的新题、私有业务集、
动态生成的同分布题、真实任务回放和过程检查一起使用。不能因为一个公开分数
很高，就把它解释成对未来未知任务的泛化证明。

### 2.6 人工和 judge 也有误差

人工标注员可能理解不同，LLM judge 可能偏好长答案、特定风格或自己的生成
习惯。评估系统本身也需要校准：

~~~math
\kappa
=
\frac{p_o-p_e}{1-p_e}
~~~

p_o 是观察到的标注一致率，p_e 是随机一致的期望比例。Kappa 不是所有任务
都适用的唯一指标，但它提醒我们：标注结果也有不确定性，不能把 judge 输出
当成无噪声真值。

### 2.7 系统边界会改变结果

一个裸模型、一个带检索的应用、一个可以搜索和执行代码的 Agent，虽然都可能
被称为“模型评估”，但它们的能力来源不同。报告要明确被测对象：

~~~text
model only
model + prompt
model + retrieval
model + tools
model + agent scaffold
end-to-end product
~~~

否则团队可能把工具或 scaffold 的收益误记到模型权重上。

## 3. 先写任务契约，再选择评估方法

### 3.1 任务契约的六个字段

一个可评估任务至少要描述：

1. 输入格式和上下文边界；
2. 输出格式和允许的多种正确答案；
3. 成功判定器或参考证据；
4. 不可接受的失败；
5. 资源预算和最大尝试次数；
6. 任务风险和用户影响。

例如“生成 SQL”不能只写成“SQL 看起来合理”。更完整的契约是：

~~~text
输入：自然语言问题、只读数据库 schema
输出：一条可解析 SQL
成功：在只读沙箱中结果与 gold query 等价
失败：访问未授权表、修改数据、超时或返回无法解析的 SQL
资源：最多两次生成，不允许外部网络
风险：数据泄露和错误查询成本
~~~

这个契约决定了测试需要 parser、执行沙箱、权限检查、超时记录和结果比较，
而不是只让另一个模型给一句“看起来不错”。

### 3.2 原子声明和证据支持

开放式回答可以拆成 atomic claims。设回答有 N_claim 个可核验声明，其中
N_supported 个能由给定证据支持，则：

~~~math
\mathrm{EvidenceSupportRate}
=
\frac{N_{\mathrm{supported}}}{N_{\mathrm{claim}}}
~~~

空回答或没有可核验声明时，分母处理必须提前约定。RAG 系统还要区分：

- 检索器找到了证据；
- 上下文组装保留了证据；
- 回答引用了正确证据；
- 结论没有超出证据支持范围。

这四层不能用一个 faithfulness 词语全部替代。

### 3.3 评估对象的协议清单

评估运行器至少应保存：

~~~text
model_revision
tokenizer_revision
chat_template_hash
system_prompt_hash
tool_schema_revision
retriever_revision
reranker_revision
decoding_config
judge_revision
dataset_revision
runner_revision
hardware_and_engine
~~~

版本字段不是行政负担。prompt、检索索引、tool schema 或 tokenizer 改变后，
输入和输出分布都可能变化；没有协议清单，旧结果和新结果没有严格可比性。

## 4. 六种评估层各自负责什么

### 4.1 Offline eval：控制变量

离线评估在固定数据和固定运行器上比较模型、prompt、检索器或系统版本。它
适合快速迭代，因为输入、环境和评分可以重复。

典型用途：

- 训练 checkpoint 初筛；
- prompt 和 template 比较；
- RAG chunk、embedding、reranker 比较；
- 量化、蒸馏和解码策略回归；
- 历史 bad case 重放。

优点是成本可控、便于定位；局限是不能完整代表线上分布，也难覆盖真实多轮
交互、用户澄清和外部系统变化。

### 4.2 Online eval：观察真实行为

线上评估把候选版本放入真实或近真实流量，通过 shadow、canary、灰度和 A/B
实验观察任务完成、复问、转人工、延迟、成本和安全事件。

它的优势是覆盖真实用户和真实系统交互，代价是实验风险更高。必须先定义流量
分层和随机化单位、隐私与日志最小化、回滚路径、实验周期和统计方法。

线上指标变好，不代表模型内部能力一定变好；它说明在当前产品、流量和版本
组合下用户结果发生了变化。

### 4.3 Human eval：判断开放质量

人工评估适合事实性、完整性、风格、帮助程度和复杂任务完成度。常见形式有
绝对打分、pairwise preference、排序和错误类型标注。

一个可用 rubric 要说明：

1. 评估对象和上下文；
2. 每个等级的正反例；
3. 哪些错误是致命错误；
4. 不确定时如何标记；
5. 如何处理多个都正确的回答；
6. 如何做标注员训练和仲裁。

人工评估的成本来自阅读、培训、一致性检查和隐私处理。它不能被少量随意
抽检替代，也不能因为标注员喜欢某种文风就被解释成事实准确性提升。

### 4.4 Automatic eval：扩大规模

程序化指标适合 exact match、格式、编译、单元测试、检索命中、延迟和成本。
LLM-as-a-Judge 适合在有 rubric 的开放式任务上扩大覆盖，但需要人工 gold
集校准，并检查位置、长度、风格和自我偏好。

自动指标的强项是可重复和便宜；弱项是容易优化到指标本身，或遗漏答案的
上下文、事实和安全含义。自动化越强，越要保留一组人工和真实任务的锚点。

### 4.5 Safety eval：独立记录伤害和可用性

安全评估不能只是普通质量评估的一列。它同时关注有害请求是否被拒绝、良性
请求是否被误拒、prompt injection 是否越权、工具调用是否超出权限、个人数据
是否泄露，以及多轮诱导、语言切换和上下文污染是否改变策略。

安全评估既要看攻击成功率，也要看 over-refusal 和正常任务完成率。拦截所有
请求并不是安全产品的成功。

### 4.6 Regression eval：保护已经修好的问题

回归集来自历史线上 bad case、事故、客诉、高价值业务任务、关键 benchmark
和人工构造的边界样本。模型、prompt、检索索引、reranker、解码、工具 schema、
safety policy 或 engine 变化时，都可能触发回归。

每条回归样本应保留：

~~~text
原始输入
期望行为
风险等级
可接受答案或判定器
首次发现版本
修复版本
当前版本结果
~~~

回归集不是一张永远固定的名单。已解决的样本要保留，新的线上失败也要经过
脱敏、归因和去重后加入。

## 5. 主流 benchmark 的能力地图

benchmark 的作用是提供可重复的观察窗口，不是替产品自动下结论。公开规模、
题目数量和 leaderboard 会变化，正式报告应以具体版本的原始资料为准。下面
只保留读者需要知道的能力边界。

### 5.1 通用知识、指令遵循与偏好

| Benchmark | 主要观察 | 不应据此推出的结论 |
| --- | --- | --- |
| MMLU | 多学科闭集知识和考试式推理 | 不代表真实客服、写作、工具或长上下文 |
| MMLU-Pro | 更难的多学科选择题和区分度 | 仍然是闭集考试，不等于开放任务 |
| GPQA | 专家级科学问答 | 样本少、方差高，不代表日常产品 |
| IFEval | 格式、长度、包含/排除等显式指令 | 不等于事实准确或深层推理 |
| HELM | 多场景、多指标、整体评估框架 | 不是一个脱离场景就能解释的总分 |
| MT-Bench | 多轮开放式回答和对话质量 | 依赖 judge、风格和问题集 |
| Chatbot Arena | 人类偏好和持续投票 | 偏好不是能力因果解释，样本会漂移 |

读这些结果时要同时看 prompt、对话轮数、judge、投票用户群和版本日期。偏好
提升可能来自更好的表达风格，不一定来自事实或推理能力提升。

### 5.2 数学、科学和 reasoning

| Benchmark | 主要观察 | 关键限制 |
| --- | --- | --- |
| GSM8K | 基础多步算术和文字题 | 强模型容易饱和，不能代表竞赛数学 |
| MATH | 代数、几何、数论和组合等竞赛题 | 最终答案不等于过程正确，公开题有污染风险 |
| AIME | 高难数学和答案格式 | 样本非常小，年度集合方差高 |
| BIG-bench / BBH | 符号规则、反常识和多任务推理 | 任务异质，平均分难解释 |
| Humanity’s Last Exam | 前沿专家知识和多模态难题 | 版本、私有 split 和评测成本需要维护 |

reasoning 分数还要报告候选数、搜索、verifier、工具和单位成本。一次生成
和 64 次生成加 rerank 的结果不应放在同一列而不加说明。

### 5.3 代码生成与软件工程

| Benchmark | 主要观察 | 关键限制 |
| --- | --- | --- |
| HumanEval | 函数级 Python 生成和测试通过 | 规模小、公开、容易污染 |
| MBPP | 初级函数实现和 API 使用 | 难度偏基础，测试覆盖有限 |
| APPS | 输入输出式竞赛编程 | 更接近竞赛，不等于仓库维护 |
| LiveCodeBench | 按时间收集的新题和执行评估 | 需要固定日期、split 和执行环境 |
| SWE-bench | 真实仓库 issue 修复 | 测试覆盖、历史污染和环境依赖显著 |
| SWE-Lancer | 更接近真实软件工程和商业任务 | 授权、复现和评价成本较高 |
| DeepSWE | 长周期 coding agent 和原创任务 | 规模较小，适合观察 frontier agent |
| KernelBench | PyTorch 到 CUDA kernel 的正确性和性能 | 只代表底层性能工程切片 |

代码评估必须区分 pass@1、pass@k、隐藏测试、编译、修改范围、测试覆盖和
运行成本。repo 级任务的成功还依赖工具、状态和补丁应用能力。

### 5.4 Agent、浏览器和工具调用

| Benchmark | 主要观察 | 关键限制 |
| --- | --- | --- |
| WebArena | 可控网站中的浏览器导航和任务完成 | 不等于开放互联网，初始状态要固定 |
| OSWorld | 桌面 GUI、文件和应用的多步操作 | 系统版本、权限和 GUI 状态影响复现 |
| AgentBench | 多环境规划和动作反馈 | 环境差异大，平均分不易解释 |
| GAIA | 真实助理式检索、工具和多步推理 | 外部信息随时间变化 |
| tau-bench | 工具、用户和业务状态的交互 | 依赖模拟器和用户模型 |
| ToolBench | 工具选择、参数和工具链规划 | API 描述与模拟器质量影响结果 |
| BrowseComp | 持久浏览和难检索事实 | 主要是短答案，不覆盖复杂工作流 |

Agent 评估要保存 action trace、观察结果、权限、工具版本、失败恢复、重复
动作和最终状态。只看 Agent 最后的自然语言总结，会漏掉已经发生的副作用。

### 5.5 长上下文、RAG 与事实性

| Benchmark | 主要观察 | 关键限制 |
| --- | --- | --- |
| LongBench | 长文档问答、摘要、多文档、代码和少样本 | 任务和长度分布是固定快照 |
| Lost in the Middle | 证据位置变化带来的性能差异 | 是现象实验，不是完整长上下文评估 |
| Needle-in-a-Haystack | 长文本中的单事实取回 | 过于简单，容易专门优化 |
| RULER | 多针、多跳、聚合和可配置长度 | 合成任务为主，要配合真实文档 |
| FRAMES | 多来源事实检索和答案合成 | 更偏 end-to-end RAG |
| SimpleQA | 短事实回答和知道自己不知道 | 不测长解释，事实会随时间变化 |
| TruthfulQA | 抗常见误解和拒绝编造 | 覆盖面有限，不能替代领域核验 |

“能接收一百万 token”只能说明接口和 runtime 在某种条件下接受输入。真正
要评估的是远距离证据召回、跨段推理、引用支持、位置分桶、长输出稳定性和
单位成本。长上下文指标不能被一个窗口长度数字替代。

### 5.6 安全、偏见与鲁棒性

| Benchmark | 主要观察 | 关键限制 |
| --- | --- | --- |
| BBQ | 社会偏见和歧义场景 | 只覆盖特定偏见维度 |
| HarmBench | 有害行为拒答和红队覆盖 | 需要防御性使用 |
| XSTest | 良性请求的过度拒答 | 主要测 over-refusal |
| RealToxicityPrompts | 毒性续写风险 | 续写不等于完整多轮安全 |
| TruthfulQA | 常见误解下的诚实回答 | 不能覆盖所有事实性和安全问题 |

安全数据要按语言、轮数、攻击策略、工具权限和用户群切片。安全阈值越严格，
越要同时报告误拒和正常任务损失。

### 5.7 多模态、文档、图表和视频

| Benchmark | 主要观察 | 关键限制 |
| --- | --- | --- |
| VQA / TextVQA | 图像问答和图中文字读取 | 不代表复杂视觉推理 |
| DocVQA | 文档 OCR、字段和版面理解 | 图像质量和 OCR 难度强相关 |
| ChartQA | 图表读数、比较和计算 | 图表类型有限，真实截图更复杂 |
| MMMU | 多学科视觉理解和多模态推理 | 需要确认模型是否真正使用图像证据 |
| MathVista | 视觉数学和图形推理 | 偏视觉数学，不等于通用视觉能力 |
| OCRBench | 场景文字和文档文字识别 | OCR 是基础能力，不是完整推理 |
| Video-MME | 视频时序、音频和视觉联合理解 | 帧采样、字幕和音频设置影响很大 |

多模态报告要把输入解码、视觉 token、OCR/ASR、projector、语言推理和输出
格式拆开计时。视频问答分数不能自动证明实时语音助手或文档抽取能力。

### 5.8 新 benchmark 的证据等级

评估领域会持续出现长周期 Agent、终端操作、网络安全、专业科研和自动化任务
的新 benchmark。新并不等于不可信，关键是标记证据成熟度：

| 等级 | 特征 | 使用方式 |
| --- | --- | --- |
| 稳定基准 | 论文、数据、评分脚本和社区复现较充分 | 进入长期回归和模型比较 |
| 活跃基准 | 题目或环境持续更新，公开复现正在增加 | 固定版本后比较 |
| 早期探索 | 样本小、环境复杂或主要来自单方报告 | 作为研究线索 |
| 未核验热词 | 缺少原始数据、评分脚本或权威出处 | 不写入正式结果 |

这一区分能避免书稿把最新名字写成稳定事实，也能让读者知道什么时候需要
回到原始论文、官方仓库和执行环境核对。

## 6. 指标和公式：分数如何真正表达任务

### 6.1 分类或闭集准确率

对于 N 个样本，预测结果为 y_hat_i，参考答案为 y_i，exact accuracy 为：

~~~math
\mathrm{Accuracy}
=
\frac{1}{N}
\sum_{i=1}^{N}
\mathbf{1}[\hat{y}_i=y_i]
~~~

它适合多选题、标签、可规范化的短答案。开放式回答若有多个等价表达，应
先做规范化或使用更合适的判定器，不能强行字符串比较。

### 6.2 切片和加权平均

若样本被分成 S 个切片，第 s 个切片有 n_s 个样本、质量 q_s，按样本量
加权的总体质量为：

~~~math
Q_{\mathrm{micro}}
=
\frac{\sum_{s=1}^{S}n_s q_s}
{\sum_{s=1}^{S}n_s}
~~~

若业务希望每个切片等权，则使用 macro average：

~~~math
Q_{\mathrm{macro}}
=
\frac{1}{S}\sum_{s=1}^{S}q_s
~~~

micro 会让大切片主导结果，macro 会让小切片拥有和大切片相同的权重。报告
必须说明使用哪一种，不能用“平均分”掩盖聚合口径。

### 6.3 Pairwise preference

在 N 个成对比较中，候选胜出 W 次，平局 T 次，则平局折半的偏好率为：

~~~math
\mathrm{PairwiseWinRate}
=
\frac{W+0.5T}{N}
~~~

它依赖比较问题、展示顺序、标注员或 judge。应随机化左右位置，报告平局规则，
并检查长度、风格和位置偏置。偏好率不能直接等价于事实正确率。

### 6.4 pass@k

如果对同一题生成 n 个候选，其中 c 个正确，随机抽取 k 个时至少有一个正确
的无偏估计常写为：

~~~math
\mathrm{pass@}k
=
1-
\frac{\binom{n-c}{k}}{\binom{n}{k}}
~~~

前提是 n 足够且候选采样过程与估计假设相符。pass@1 更接近一次调用体验，
pass@k 允许更多尝试。报告必须把 k、采样温度、执行环境和候选成本写清楚。

### 6.5 RAG 的证据指标

设检索返回 k 个文档，gold evidence 集合为 G，返回集合为 R，检索 recall 为：

~~~math
\mathrm{Recall@k}
=
\frac{|R\cap G|}{|G|}
~~~

如果回答包含 N_claim 个原子声明，其中 N_supported 个得到证据支持：

~~~math
\mathrm{CitationSupport}
=
\frac{N_{\mathrm{supported}}}{N_{\mathrm{claim}}}
~~~

检索 recall 高，不代表回答引用正确；引用 support 高，也不代表回答覆盖了
用户问题。RAG 需要把检索、上下文、引用和最终任务拆开记录。

### 6.6 安全指标

设 unsafe 测试数为 N_unsafe，成功产生不应出现的危险输出的数量为 N_success，
攻击成功率为：

~~~math
\mathrm{ASR}
=
\frac{N_{\mathrm{success}}}{N_{\mathrm{unsafe}}}
~~~

对 N_benign 个良性样本，错误拒绝数量为 N_reject：

~~~math
\mathrm{OverRefusal}
=
\frac{N_{\mathrm{reject}}}{N_{\mathrm{benign}}}
~~~

安全报告应同时提供两者，并按伤害严重度、语言、轮数和工具权限切片。ASR 为
零在小样本下不等于真实风险为零，必须给出样本量和置信区间。

### 6.7 校准和置信

如果模型对答案给出置信度，可以将样本按置信度分成 M 个桶，定义 Expected
Calibration Error：

~~~math
\mathrm{ECE}
=
\sum_{m=1}^{M}
\frac{|B_m|}{N}
\left|
\mathrm{acc}(B_m)-\mathrm{conf}(B_m)
\right|
~~~

B_m 是第 m 个置信度桶。高准确率但过度自信的模型，在开放式事实问答里仍然
可能带来高风险。

### 6.8 延迟、成本与成功任务

线上不能只报平均延迟。应分别记录 TTFT、TPOT、端到端延迟和 P50/P95/P99，
并说明流式和非流式的统计口径。

如果一次服务成本为 C_serve，重试成本为 C_retry，人工复核成本为 C_review，
成功概率为 p_success，则单位成功任务成本可以先估算为：

~~~math
C_{\mathrm{success}}
=
\frac{
C_{\mathrm{serve}}+C_{\mathrm{retry}}+C_{\mathrm{review}}
}{
p_{\mathrm{success}}
}
~~~

一条更便宜但经常失败的路径，可能比一次服务更贵的高质量路径更不划算。

## 7. 人工评估和 LLM Judge

### 7.1 rubric 必须把“好”拆开

开放式答案的 rubric 不应只有 1 到 5 分。至少拆成事实正确、任务完整、证据
充分、指令遵循、表达清楚和风险可接受。不同维度可以有不同分母和致命错误。
例如金融数字错误即使文风很好，也不能被其他维度的分数抵消。

### 7.2 成对比较的顺序和展示方式

人工或 judge 比较 A/B 时，随机化左右顺序，隐藏模型名称，保留上下文和用户
目标，并记录：

~~~text
pair_id
left_version
right_version
order
judge_or_annotator
dimension_scores
winner
tie_reason
confidence
~~~

如果只保存最终胜负，不保存顺序和理由，就无法分析位置偏置和争议样本。

### 7.3 judge 需要人工锚点

用 LLM judge 扩大规模前，先建立人工标注 gold set，覆盖明显正确、明显错误、
长短答案、不同风格和边界案例。比较 judge 与人工的方向一致率、维度级相关、
错误类型、长度和位置偏置，以及不确定样本的转人工比例。

judge 与人工不一致时，不要只调一个 prompt；先判断 rubric 是否含糊、参考
证据是否不足，或者任务本来就不存在唯一偏好。

## 8. 统计不确定性与回归分析

### 8.1 差异比绝对分数更重要

比较旧版本 x_i 和新版本 y_i 时，优先保留配对差：

~~~math
\Delta_i=y_i-x_i,
\qquad
\bar{\Delta}
=
\frac{1}{N}\sum_{i=1}^{N}\Delta_i
~~~

配对比较能抵消样本难度差异。独立抽样时，不能把两组不同样本的差异冒充
同一题上的模型提升。

### 8.2 Bootstrap 置信区间

从 N 个配对差值中有放回重采样 B 次，第 b 次的均值为：

~~~math
\bar{\Delta}^{(b)}
=
\frac{1}{N}
\sum_{i=1}^{N}\Delta_i^{(b)}
~~~

将 B 个均值的 2.5% 和 97.5% 分位数作为近似 95% 区间，可以表达提升的不确定
范围。对于小样本、高度相关或分层数据，还应按用户、会话或任务组进行 cluster
bootstrap，避免把同一用户的许多请求当成完全独立。

### 8.3 线上比例差异

旧版本成功率 p_0，新版本成功率 p_1。比例差异的近似标准误要根据实验设计、
随机化单位和是否独立来计算。若用合并比例 p_pool 做两个独立比例的近似：

~~~math
z
=
\frac{p_1-p_0}
{\sqrt{
p_{\mathrm{pool}}(1-p_{\mathrm{pool}})
\left(\frac{1}{n_0}+\frac{1}{n_1}\right)
}}
~~~

这只是一个近似检验。用户级随机化、重复会话、分层流量、序贯实验和多指标
同时观察都可能需要更严格的方法。不要只因为 z 大于某个数字就忽略实际效应
大小、置信区间和用户风险。

### 8.4 回归矩阵

可以把版本变化和任务切片组织成矩阵：

| 切片 | 质量差 | 安全差 | 延迟差 | 成本差 | 解释 |
| --- | ---: | ---: | ---: | ---: | --- |
| 普通聊天 | + | 0 | - | + | 继续观察 |
| 中文客服 | + | 0 | 0 | 0 | 主要收益切片 |
| 长上下文 | - | 0 | - | - | 单独修复 |
| 工具调用 | 0 | - | 0 | + | 先处理越权风险 |
| 代码 | + | 0 | - | - | 检查候选数和执行成本 |

矩阵比一个总分更容易指导下一轮实验。

## 9. 从离线结果走到线上证据

### 9.1 固定 replay

先用固定数据、固定协议和高精度基线做 replay，确认候选版本的质量、失败类型
和资源账本。此阶段适合发现 prompt、schema、tokenizer 和代码回归。

### 9.2 压力与长尾

加入真实长度分布、并发、缓存命中、工具超时、取消、重试和多租户，观察
P95/P99、队列、峰值显存和单位成功成本。平均值正常不代表长尾正常。

### 9.3 Shadow

shadow 把真实请求复制给候选系统，但不把候选结果返回用户。它能观察真实
输入分布、运行时错误和资源成本，同时降低用户风险。日志必须脱敏，并防止
候选系统执行真实外部副作用。

### 9.4 Canary 和 A/B

canary 让小比例用户使用候选版本，适合验证连接、流式体验、取消、工具和
缓存。A/B 则在定义好的随机化单位上比较用户结果。两者都需要明确流量分层、
随机化单位、主要指标、护栏指标、停止规则和统计分析计划。

### 9.5 回滚和证据保留

回滚不仅是换一个 model id。需要保存请求所属版本、已经发生的工具副作用、
旧 cache 是否可复用、正在生成的流如何结束，以及回滚后的指标变化。高风险
Agent 先处理外部状态，再处理可重算的语言输出。

## 10. 一个客服 RAG 的评估案例

假设团队要把旧版客服模型替换成候选模型。产品目标不是“回答更像人”，而是：

- 用户问题得到正确且可引用的答案；
- 找不到依据时明确说明不确定；
- 不泄露其他用户或内部文档；
- 常见问题首 token 快；
- 复杂问题失败后可转人工；
- 单位成功会话成本不超过预算。

### 10.1 任务切片

| 切片 | 样本来源 | 主要指标 |
| --- | --- | --- |
| 普通 FAQ | 脱敏历史问答 | answer correctness、复问率 |
| 中文长问 | 真实多轮会话 | citation support、长尾延迟 |
| 版本政策 | 版本化内部文档 | evidence recall、版本一致性 |
| 无答案问题 | 人工构造和历史 bad case | abstention accuracy |
| 权限问题 | 不同租户和角色 | unauthorized retrieval、泄露率 |
| 高峰流量 | 线上 replay | P95/P99、队列和成本 |

### 10.2 结果解释

如果候选模型总体正确率提高 3%，但版本政策切片的 citation support 降低 6%，
不能用普通 FAQ 的收益覆盖这个问题。可能的原因包括：

1. chunk 切分让旧版本条款和新版本条款混在一起；
2. reranker 把相似但过时的文档排在前面；
3. 模型更愿意生成答案，却没有承认证据不足；
4. 引用格式改变，评分器误判；
5. 长上下文中间位置召回退化。

下一轮实验应分别固定模型，只替换检索器或只替换 prompt，做配对 replay，
而不是同时升级全部组件。

### 10.3 线上决策

如果候选模型在普通 FAQ 和中文长问上改善，版本政策问题可以通过保守的
abstain、权限过滤和旧版本高风险路由解决，团队可以选择“低风险切片灰度、
政策切片保持旧版本”的策略。这个决策比“全量通过/全量失败”更贴近实际
系统，也保留了后续修复空间。

    "wins": wins,
    "ties": ties,
    "win_rate": (wins + 0.5 * ties) / len(eval_cases),
}

unsafe = [row for row in safety_cases if row["kind"] == "unsafe"]
benign = [row for row in safety_cases if row["kind"] == "benign"]
attack_success_rate = sum(not row["blocked"] for row in unsafe) / len(unsafe)
over_refusal_rate = sum(row["blocked"] for row in benign) / len(benign)

old_rate = online["old_success"] / online["old_total"]
new_rate = online["new_success"] / online["new_total"]
pooled = (online["old_success"] + online["new_success"]) / (
    online["old_total"] + online["new_total"]
)
se = math.sqrt(
    pooled * (1 - pooled)
    * (1 / online["old_total"] + 1 / online["new_total"])
)
z_score = (new_rate - old_rate) / se

signals = {
    "quality_improved": delta >= 0.03,
    "slice_floor": all(
        report["delta"] >= -0.02 for report in slice_report.values()
    ),
    "regression_clean": not regressions,
    "safety_ok": attack_success_rate == 0.0 and over_refusal_rate <= 0.05,
    "online_signal": z_score >= 1.64,
    "latency_ok": latency["new_p95_ttft_ms"] <= latency["budget_p95_ttft_ms"],
    "cost_ok": cost["new_success_cost"] <= cost["budget_success_cost"],
}

actions = []
if slice_report["long"]["delta"] < 0:
    actions.append("keep_long_context_in_canary")
if not signals["regression_clean"]:
    actions.append("inspect_regressions")
if not signals["safety_ok"]:
    actions.append("pause_high_risk_traffic")
if not signals["online_signal"]:
    actions.append("collect_more_online_samples")

recommendation = "conditional_rollout" if actions else "expand_cohort"
summary = {
    "old_score": round(old_score, 4),
    "new_score": round(new_score, 4),
    "delta": round(delta, 4),
    "pairwise": {
        "wins": pairwise["wins"],
        "ties": pairwise["ties"],
        "win_rate": round(pairwise["win_rate"], 4),
    },
    "slice_report": slice_report,
    "regressions": regressions,
    "safety": {
        "attack_success_rate": round(attack_success_rate, 3),
        "over_refusal_rate": round(over_refusal_rate, 3),
    },
    "online": {
        "old_rate": round(old_rate, 4),
        "new_rate": round(new_rate, 4),
        "uplift": round(new_rate - old_rate, 4),
        "z_score": round(z_score, 3),
    },
    "signals": signals,
    "actions": actions,
    "recommendation": recommendation,
}
pprint(summary, sort_dicts=False)
~~~

## 12. 评估结果的版本、污染和可复现性

### 12.1 数据集版本

数据集要记录原始来源、过滤规则、去重规则、语言、时间、split、参考答案和
是否公开。对动态数据，还要保存抓取时间和内容 checksum。

训练集、调参集、开发集和最终测试集要有隔离。最终测试集被反复查看后，
它就不再是干净的最终测试集。

### 12.2 prompt 和 decoding

system prompt、few-shot 示例、是否要求解释、temperature、top-p、候选数、
verifier、max output tokens 和 stop sequence 的变化都可能改变结果。报告
应把它们作为实验协议的一部分，而不是只记录模型名称。

### 12.3 污染检测的边界

污染检测可以使用 n-gram overlap、时间切分、训练数据审计、模型记忆探测和
新题对照，但任何一种方法都不能证明“绝对没有污染”。更稳妥的报告写法是：

1. 公开题可能存在污染风险；
2. 采用了哪些检测和时间隔离；
3. 结果对污染假设是否敏感；
4. 另有哪类私有或动态任务作为补充证据。

### 12.4 输出、trace 和失败样本

只保存最终分数会丢掉最有价值的信息。评估 artifact 应包含：

~~~text
input_hash
raw_output_or_redacted_output
parsed_output
finish_reason
tool_trace
retrieval_trace
judge_trace
latency
token_usage
failure_type
~~~

隐私和安全要求较高时可以只保存哈希、脱敏片段和结构化错误，但仍要保留
足以复现和归因的信息。

## 13. 资料、证据边界与延伸阅读

本章的指标公式用于建立共同口径，不会自动解决标注质量、数据污染或业务
风险。benchmark 论文说明任务和实验条件，官方评测框架说明实现入口，生产
trace 说明目标系统实际发生了什么。三类资料不能互相替代。

下面的链接用于建立阅读入口。具体题目数量、支持的 runner 和页面路径可能
随版本变化，正式报告应记录访问日期和 revision。

1. [HELM](https://crfm.stanford.edu/helm/latest/)：Stanford 的整体评估框架和场景结果。
2. [HELM paper](https://arxiv.org/abs/2211.09110)：Holistic Evaluation of Language Models 的方法和指标背景。
3. [OpenAI Evals](https://github.com/openai/evals)：开放式模型评估和自定义 eval 的实现入口。
4. [Hugging Face Evaluate](https://huggingface.co/docs/evaluate/index)：指标、评估脚本和数据处理入口。
5. [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)：多模型、多 benchmark 的可复现实验框架。
6. [BIG-bench](https://github.com/google/BIG-bench)：多任务和能力探索 benchmark 入口。
7. [MMLU](https://arxiv.org/abs/2009.03300)：多学科知识和考试式推理。
8. [GPQA](https://arxiv.org/abs/2311.12022)：专家级科学问答。
9. [IFEval](https://arxiv.org/abs/2311.07911)：可验证指令遵循。
10. [HumanEval](https://arxiv.org/abs/2107.03374)：函数级代码生成和执行评估。
11. [SWE-bench](https://arxiv.org/abs/2310.06770)：真实 GitHub issue 修复评估。
12. [WebArena](https://arxiv.org/abs/2307.13854)：可控网页环境中的 Agent 任务。
13. [LongBench](https://arxiv.org/abs/2308.14508)：长上下文多任务评估。
14. [RULER](https://arxiv.org/abs/2404.06654)：长上下文检索、聚合和多跳测试。
15. [SimpleQA](https://arxiv.org/abs/2411.04368)：短事实问答和校准。
16. [TruthfulQA](https://arxiv.org/abs/2110.08561)：抗误解和诚实回答评估。
17. [Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)：模型裁判与人类偏好的研究背景。
18. [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)：风险管理和治理语境下的评估边界。

阅读这些资料时，先看原始任务、评分脚本、环境和版本，再看 leaderboard。一个
论文分数可以证明“在论文条件下测到了某个结果”，不能自动证明“你的产品
在真实用户和真实风险下达到了同样结果”。

## 14. 本章小结

评估的目的不是积累 benchmark 名称，而是建立一条可以解释模型行为的证据链。

1. 评估结果是能力、证据、协议、安全、延迟和成本的向量，不是一个天然总分。
2. 先写任务契约和成功判定，再决定数据、指标、judge 和运行器。
3. Offline eval 控制变量，online eval 观察真实用户，human eval 判断开放质量，
   automatic eval 扩大规模，safety eval 记录风险，regression eval 保护已修复
   的问题。
4. benchmark 只能覆盖某个能力窗口；MMLU、GPQA、SWE-bench、WebArena、RULER、
   MMMU 等结果不能互相替代。
5. 每个指标都要说明分母、聚合方式、采样预算和失败处理；pass@k、pairwise、
   citation support、ASR 和 over-refusal 表达的是不同问题。
6. 统计显著不等于业务重要，业务提升也不等于模型内部能力提升；要同时看效应
   大小、置信区间、切片和成本。
7. LLM judge 需要人工锚点，公开 benchmark 需要污染边界，线上实验需要随机化、
   监控和可回滚。
8. 最终决策应保留独立 signals 和 actions，让团队知道哪里可以扩大、哪里需要
   继续观察、哪里必须回退。

当读者能够从“分数提升”追问到任务契约、版本协议、样本分布、统计区间、失败
切片和单位成功成本时，才真正理解了大模型评估。
