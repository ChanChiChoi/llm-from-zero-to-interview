# 第一章：评估总览

模型发布报告通常先给出一张分数表：知识题、数学题、代码题、长上下文、
安全题、多模态题各有一个数字。初学者容易把最高的数字当成“模型更强”的
证明，工程团队也容易在一个平均分提升后直接讨论上线。

真正的评估更接近一次证据调查。我们要知道模型在什么任务上变好了，变化是否
来自模型本身，是否牺牲了另一类任务，结果能否复现，线上用户是否真的受益，
以及一次失败会带来什么安全、成本和业务后果。一个模型可以在 GPQA 上提升，
却不适合企业客服；也可以在公开代码题上提升，却在真实仓库修复任务中退化。

对小白来说，评估就是回答“它做对了吗”。对专家来说，评估还要回答：

1. 什么算作一次任务成功，分母是什么；
2. 结果由模型、prompt、工具、数据还是 scaffold 决定；
3. 误差来自抽样、标注、judge、解码还是环境；
4. 这个分数是否能外推到目标用户和目标风险；
5. 质量、延迟、安全、成本之间如何共同决定部署策略。

因此，本章不把评估写成一张排行榜，也不把上线判断压成一个总布尔值。全章
围绕下面的证据链展开：

~~~text
任务契约
  -> 数据与参考答案
  -> 模型和系统协议
  -> 指标、标注与运行器
  -> 切片、误差和统计不确定性
  -> 离线/线上证据
  -> 可解释的产品决策
~~~

后续章节会分别深入 benchmark 设计、人工评测、pairwise eval、LLM-as-a-Judge、
污染检测、reasoning/code/math eval、多模态与长上下文评估、安全评估、在线实验、
统计显著性和 error analysis。本章先建立它们之间的边界，让读者看到一张分数表
时知道应该追问什么。

## 1. 评估不是一个分数，而是一组证据

### 1.1 能力、可靠性、安全和效率是不同维度

一个生产模型至少有下面几类证据：

| 维度 | 核心问题 | 典型观察 |
| --- | --- | --- |
| 任务能力 | 它能不能完成目标任务 | exact match、代码测试、任务成功率 |
| 事实与证据 | 它的回答是否有依据 | citation support、evidence recall、unsupported claim |
| 指令与协议 | 它是否遵守格式和工具协议 | JSON 合法率、参数正确率、stop reason |
| 稳定性 | 换样本、长度、语言后是否仍然工作 | 方差、切片回归、位置敏感性 |
| 安全 | 应拒绝的是否拒绝，不应拒绝的是否可用 | attack success、over-refusal、越权调用 |
| 效率 | 完成一次任务要付出多少资源 | TTFT、TPOT、GPU-hours、单位成功成本 |
| 产品价值 | 用户是否真的完成了工作 | 完成率、复问率、转人工率、留存 |

这些维度不能随意相加。一个高风险工具调用的安全失败，不能被普通聊天的
质量提升抵消；一个延迟很低但回答经常不正确的模型，也不能称为产品成功。

可以把一次评估结果写成向量：

~~~math
\mathbf{E}
=
(
Q_{\mathrm{task}},
Q_{\mathrm{evidence}},
Q_{\mathrm{protocol}},
Q_{\mathrm{reliability}},
Q_{\mathrm{safety}},
L_{\mathrm{latency}},
C_{\mathrm{success}},
Q_{\mathrm{product}}
)
~~~

质量项、延迟项和成本项的单位不同，不能未经说明就合并成一个数字。如果业务
确实需要排序，可以定义权重，但必须同时保留原始分量：

~~~math
S_{\mathrm{product}}
=
\sum_{j=1}^{m}\alpha_j \widetilde{E}_j,
\qquad
\alpha_j\ge 0,
\qquad
\sum_{j=1}^{m}\alpha_j=1
~~~

这里的 $\widetilde{E}_j$ 表示已经换算为同一方向、可比较量表的分量；原始质量、
延迟和成本单位不同，不能直接相加。$\alpha_j$ 是业务权重，不是自然真理。
高风险约束通常应作为单独门槛处理，不能让普通流量的高分抵消安全事故。

### 1.2 一个分数能回答什么，不能回答什么

假设某模型在 MMLU-Pro 上提高 3 个百分点，这个结果可以说明在固定版本、固定
prompt、固定 scoring script 下，它在该闭集多学科题上的平均成绩提高了。它不能
直接说明：

- 中文客服是否更有帮助；
- RAG 引用是否准确；
- 工具参数是否会重复提交；
- 长上下文中间位置的证据是否能找到；
- 代码补丁是否能通过隐藏测试；
- 延迟和单位成功成本是否更低。

同样，线上点赞率提升也不能单独证明模型推理能力提升，因为 prompt、产品 UI、
流量分配、用户群和回答长度都可能同时改变。评估的价值正是把这些可能原因拆开。

### 1.3 小白视角：先问测试题和我的任务像不像

如果你准备做一个合同问答助手，先拿用户真实会问的问题和 MMLU 题目对比：
前者可能需要读取版本化文档、引用条款、拒绝法律意见和识别权限；后者通常
是一个独立的多选题。它们可以互相提供信息，却不是同一项测试。

一个简单判断法是把目标任务写成四元组：

~~~text
输入是什么
输出必须满足什么
什么证据可以判定成功
失败会造成什么后果
~~~

如果 benchmark 没有覆盖这四件事，它最多是能力旁证，不是产品验收的直接证据。

### 1.4 专家视角：评估边界要写进报告

一份可审计的评估报告至少要说明：

1. 模型 revision、tokenizer 和 chat template；
2. benchmark 的版本、split、发布日期和样本过滤；
3. system prompt、few-shot、CoT、工具和 verifier 条件；
4. 采样温度、候选数、最大输出、停止规则和随机种子；
5. 评分器、人工 rubric、judge model 和聚合方法；
6. 样本数、置信区间、失败样本和已知污染风险；
7. 目标产品与 benchmark 之间哪些地方相似，哪些地方不同。

缺少这些字段时，报告里的“提升”只能作为线索，不能作为可复现实验结论。

## 2. 为什么大模型评估比传统分类更难

### 2.1 输出是开放的

传统分类通常有固定标签，模型输出可以直接和 gold label 比较。大模型回答
可能有多种正确表达，还可能同时包含事实、推理、格式和安全问题。

例如“如何备份数据库”可能有三套都正确的方案，但其中一套遗漏了恢复演练，
另一套给出了不安全的权限配置。单一字符串相等不能描述这种差异。

因此开放式任务往往需要组合：

- 程序化检查，例如 schema、编译、单元测试；
- 参考答案或证据核对；
- 人工 rubric；
- 成对偏好；
- 任务环境中的最终状态检查。

### 2.2 能力是多维的

模型可能在数学上进步，在事实性上没有变化，在风格上变得更简洁，但在中文
长文档上退化。总体平均分只有在任务权重、风险和样本分布都合理时才有意义。

把不同任务直接平均之前，先问：

1. 每类任务样本量是否相近；
2. 每类任务的业务权重是否相近；
3. 是否有不能被抵消的安全约束；
4. 不同指标的分母是否可比较。

### 2.3 解码预算会改变结论

数学题用一次 greedy 生成，和用 32 个候选、self-consistency、verifier 重新
排序，测到的不是同一个系统。代码题的 pass@1 和 pass@10 也代表不同的调用
成本和产品体验。

如果候选数为 k、每次生成成本为 c，粗略生成成本约为：

~~~math
C_{\mathrm{generate}}
\approx
kc
~~~

如果候选质量提高但成本和延迟也显著提高，报告必须把这两个事实放在一起。

### 2.4 用户分布会漂移

离线数据通常是固定快照，线上输入却会随着季节、产品入口、语言、地区和攻击
方式变化。一个在英文短问答上的提升，可能无法外推到中文长上下文或工具调用。

因此要同时拥有：

1. 稳定的长期回归集；
2. 代表当前用户的滚动样本；
3. 专门覆盖新风险的动态样本；
4. 隔离的最终测试集。

### 2.5 benchmark 会被污染

公开题目可能进入预训练语料、微调数据、提示词模板或后续人工调参记录。
污染不一定是故意作弊，也可能是模型已经见过题目和标准答案。

污染风险高的 benchmark 仍然有价值，但应与时间切分的新题、私有业务集、
动态生成的同分布题、真实任务回放和过程检查一起使用。不能因为一个公开分数
很高，就把它解释成对未来未知任务的泛化证明。

### 2.6 人工和 judge 也有误差

人工标注员可能理解不同，LLM judge 可能偏好长答案、特定风格或自己的生成
习惯。评估系统本身也需要校准：

~~~math
\kappa
=
\frac{p_o-p_e}{1-p_e}
~~~

p_o 是观察到的标注一致率，p_e 是随机一致的期望比例。Kappa 不是所有任务
都适用的唯一指标，但它提醒我们：标注结果也有不确定性，不能把 judge 输出
当成无噪声真值。

### 2.7 系统边界会改变结果

一个裸模型、一个带检索的应用、一个可以搜索和执行代码的 Agent，虽然都可能
被称为“模型评估”，但它们的能力来源不同。报告要明确被测对象：

~~~text
model only
model + prompt
model + retrieval
model + tools
model + agent scaffold
end-to-end product
~~~

否则团队可能把工具或 scaffold 的收益误记到模型权重上。

## 3. 先写任务契约，再选择评估方法

### 3.1 任务契约的六个字段

一个可评估任务至少要描述：

1. 输入格式和上下文边界；
2. 输出格式和允许的多种正确答案；
3. 成功判定器或参考证据；
4. 不可接受的失败；
5. 资源预算和最大尝试次数；
6. 任务风险和用户影响。

例如“生成 SQL”不能只写成“SQL 看起来合理”。更完整的契约是：

~~~text
输入：自然语言问题、只读数据库 schema
输出：一条可解析 SQL
成功：在只读沙箱中结果与 gold query 等价
失败：访问未授权表、修改数据、超时或返回无法解析的 SQL
资源：最多两次生成，不允许外部网络
风险：数据泄露和错误查询成本
~~~

这个契约决定了测试需要 parser、执行沙箱、权限检查、超时记录和结果比较，
而不是只让另一个模型给一句“看起来不错”。

### 3.2 原子声明和证据支持

开放式回答可以拆成 atomic claims。设回答有 N_claim 个可核验声明，其中
N_supported 个能由给定证据支持，则：

~~~math
\mathrm{EvidenceSupportRate}
=
\frac{N_{\mathrm{supported}}}{N_{\mathrm{claim}}}
~~~

空回答或没有可核验声明时，分母处理必须提前约定。RAG 系统还要区分：

- 检索器找到了证据；
- 上下文组装保留了证据；
- 回答引用了正确证据；
- 结论没有超出证据支持范围。

这四层不能用一个 faithfulness 词语全部替代。

### 3.3 评估对象的协议清单

评估运行器至少应保存：

~~~text
model_revision
tokenizer_revision
chat_template_hash
system_prompt_hash
tool_schema_revision
retriever_revision
reranker_revision
decoding_config
judge_revision
dataset_revision
runner_revision
hardware_and_engine
~~~

版本字段不是行政负担。prompt、检索索引、tool schema 或 tokenizer 改变后，
输入和输出分布都可能变化；没有协议清单，旧结果和新结果没有严格可比性。

## 4. 六种评估层各自负责什么

### 4.1 Offline eval：控制变量

离线评估在固定数据和固定运行器上比较模型、prompt、检索器或系统版本。它
适合快速迭代，因为输入、环境和评分可以重复。

典型用途：

- 训练 checkpoint 初筛；
- prompt 和 template 比较；
- RAG chunk、embedding、reranker 比较；
- 量化、蒸馏和解码策略回归；
- 历史 bad case 重放。

优点是成本可控、便于定位；局限是不能完整代表线上分布，也难覆盖真实多轮
交互、用户澄清和外部系统变化。

### 4.2 Online eval：观察真实行为

线上评估把候选版本放入真实或近真实流量，通过 shadow、canary、灰度和 A/B
实验观察任务完成、复问、转人工、延迟、成本和安全事件。

它的优势是覆盖真实用户和真实系统交互，代价是实验风险更高。必须先定义流量
分层和随机化单位、隐私与日志最小化、回滚路径、实验周期和统计方法。

线上指标变好，不代表模型内部能力一定变好；它说明在当前产品、流量和版本
组合下用户结果发生了变化。

### 4.3 Human eval：判断开放质量

人工评估适合事实性、完整性、风格、帮助程度和复杂任务完成度。常见形式有
绝对打分、pairwise preference、排序和错误类型标注。

一个可用 rubric 要说明：

1. 评估对象和上下文；
2. 每个等级的正反例；
3. 哪些错误是致命错误；
4. 不确定时如何标记；
5. 如何处理多个都正确的回答；
6. 如何做标注员训练和仲裁。

人工评估的成本来自阅读、培训、一致性检查和隐私处理。它不能被少量随意
抽检替代，也不能因为标注员喜欢某种文风就被解释成事实准确性提升。

### 4.4 Automatic eval：扩大规模

程序化指标适合 exact match、格式、编译、单元测试、检索命中、延迟和成本。
LLM-as-a-Judge 适合在有 rubric 的开放式任务上扩大覆盖，但需要人工 gold
集校准，并检查位置、长度、风格和自我偏好。

自动指标的强项是可重复和便宜；弱项是容易优化到指标本身，或遗漏答案的
上下文、事实和安全含义。自动化越强，越要保留一组人工和真实任务的锚点。

### 4.5 Safety eval：独立记录伤害和可用性

安全评估不能只是普通质量评估的一列。它同时关注有害请求是否被拒绝、良性
请求是否被误拒、prompt injection 是否越权、工具调用是否超出权限、个人数据
是否泄露，以及多轮诱导、语言切换和上下文污染是否改变策略。

安全评估既要看攻击成功率，也要看 over-refusal 和正常任务完成率。拦截所有
请求并不是安全产品的成功。

### 4.6 Regression eval：保护已经修好的问题

回归集来自历史线上 bad case、事故、客诉、高价值业务任务、关键 benchmark
和人工构造的边界样本。模型、prompt、检索索引、reranker、解码、工具 schema、
safety policy 或 engine 变化时，都可能触发回归。

每条回归样本应保留：

~~~text
原始输入
期望行为
风险等级
可接受答案或判定器
首次发现版本
修复版本
当前版本结果
~~~

回归集不是一张永远固定的名单。已解决的样本要保留，新的线上失败也要经过
脱敏、归因和去重后加入。

这六层并不是互斥的六种“评估方案”。Offline/online 描述数据和运行环境，
human/automatic 描述判分来源，safety/regression 描述评估目的；一次离线回归
完全可以同时使用程序判分、人工复核和安全切片。设计时应把这些维度交叉起来，
而不是选中某一层后就以为评估已经完整。

### 4.7 评估工具各自测量什么

评估链上的 benchmark、runner、判分器和产品实验承担不同工作。benchmark 规定测试哪些任务；runner 固定输入、版本和执行过程；判分器把输出映射为任务结果；线上实验观察完整系统在目标流量下的用户结果。它们可以组合，但一个工具不能替代其他环节。

例如，统一 runner 能让多模型复跑同一套任务，却不能证明任务覆盖了目标产品；LLM judge 能扩大开放式答案的判分规模，却不能自动保证事实正确；线上成功率能说明当前系统配置下的用户结果，却不能单独归因于模型权重。后续章节分别深入这些环节，本章只建立导航关系。

## 5. Benchmark 提供哪些观察窗口

Benchmark 是一组可重复的观察窗口，不是产品验收的替代品。下面列出代表性家族，供读者找到后续章节；题目版本、split、评分器和环境应在对应专题中核验。

| 任务家族 | 代表入口 | 先问的问题 | 深入位置 |
| --- | --- | --- | --- |
| 知识、科学问答与指令遵循 | MMLU、GPQA、IFEval | 是闭集知识、专业问题，还是显式格式约束？ | [第 2 章](02-benchmark设计.md)、[第 6 章](06-reasoning-code-math-eval.md) |
| 数学、代码与推理 | GSM8K、AIME、HumanEval、LiveCodeBench、SWE-bench | 评分只看答案，还是运行过程、测试和交付物？ | [第 6 章](06-reasoning-code-math-eval.md) |
| 人类偏好与开放对话 | MT-Bench、Chatbot Arena | 谁在比较答案，judge 或投票人群是什么？ | [第 3 章](03-human-eval与pairwise-eval.md)、[第 4 章](04-llm-as-a-judge.md) |
| 多模态、RAG 与长上下文 | DocVQA、ChartQA、MMMU、LongBench、RULER、NoLiMa | 模型是否使用了输入证据，位置、模态和长度条件是什么？ | [第 7 章](07-多模态与长上下文评估.md)、[第 13 章](13-1m-context有效能力评测.md) |
| 安全与鲁棒性 | HarmBench、BBQ、XSTest | 测的是哪种伤害、攻击面或误拒风险？ | [第 8 章](08-safety与robustness-eval.md) |
| Agent 与工作流 | WebArena、OSWorld、tau-bench、专业任务簇 | 环境、工具、权限、harness 和最终状态是否固定并可检查？ | [第 15 章](15-specialized-frontier-eval-cluster.md) |

同一模型可以在这些观察窗口中表现不同。跨 benchmark 汇总前必须说明目标构念、样本权重、任务难度、执行预算和失败分母；不应把异质分数直接平均成没有业务含义的总排名。详细 benchmark 设计和资料入口分别由第 2 章及各任务专题负责。

## 6. 指标要对应具体问题

### 6.1 一个可复算的准确率例子

对 N 个样本，若预测与参考答案相同的样本数为 C，则闭集准确率为：

~~~math
\mathrm{Accuracy}=\frac{C}{N}
~~~

假设固定测试集有 12 道题，旧版本答对 9 道，新版本答对 10 道：旧版准确率是 $9/12=0.75$，新版是 $10/12\approx0.833$，差异约为 8.3 个百分点。这个算术只描述这 12 道题；它没有说明新版本是否只修好一题、是否在高风险切片退化，也不能代替不确定性分析。

### 6.2 指标家族与判分边界

| 指标家族 | 主要问题 | 必须交代 | 深入位置 |
| --- | --- | --- | --- |
| Exact match、准确率、任务成功率 | 样本是否满足约定的成功条件？ | 分母、参考答案/判定器、部分成功规则 | 第 2、6 章 |
| Pairwise preference | 两个答案在给定 rubric 下谁更受偏好？ | 平局处理、展示顺序、评审者或 judge | 第 3、4 章 |
| pass@k 与 verifier 结果 | 多次生成或搜索下至少一次成功的概率是多少？ | k、采样设置、执行环境、候选成本 | 第 6 章 |
| Retrieval recall、citation support | 证据是否检出、保留并支持最终结论？ | gold evidence、声明分母、证据缺失处理 | 第 7 章 |
| ASR、over-refusal 与公平性切片 | 风险输出和良性误拒各占多少？ | 风险定义、严重度、语言/群体分母 | 第 8 章 |
| 在线 uplift、延迟、单位成功成本 | 目标用户的端到端结果和资源变化是什么？ | 随机化单位、窗口、护栏指标、服务条件 | 第 6、9、10 章 |

这些指标不能互换。检索 recall 高不保证回答支持充分，偏好胜率高不保证事实正确，低延迟也不代表任务成功。pass@k、置信区间、攻击成功率和成本的公式及完整例子留在各自专题讲解，避免在总览中把不同分母混成同一种分数。

## 7. 人工评估和 LLM Judge

开放回答通常没有唯一字符串答案，需要用 rubric、参考证据、人工判断、程序 verifier 或 LLM judge 的组合来评估。人工评估能判断完整性、事实和任务语境，但要训练标注员、记录分歧并处理仲裁；LLM judge 能扩大覆盖，却会受 rubric、位置、风格、答案长度和 judge 本身能力影响。

无论由人还是模型判分，都要在目标任务上检查测量器：保留人工 gold set，盲化答案来源，随机并交换 pairwise 展示顺序，查看分歧和不确定样本。位置交换只检查结果是否受顺序影响，不证明胜出的答案正确。评估方法、标注协议和 judge 校准分别见[第 3 章](03-human-eval与pairwise-eval.md)和[第 4 章](04-llm-as-a-judge.md)。

## 8. 差异要连同不确定性一起报告

比较旧版本和新版本时，优先保留同一任务上的配对结果；若任务、用户或运行存在聚类，就应按实际随机化和抽样单位估计不确定性。报告应同时呈现效应大小、区间、关键切片和样本量，而不是只展示 p 值或小数点后的精度。

回归矩阵可以把质量、安全、延迟和成本的变化按任务切片并列展示，帮助决定下一轮实验。一个总体均值改善，仍可能伴随高风险任务退化。配对比较、bootstrap、功效和多重检验见[第 10 章](10-统计显著性与实验设计.md)；线上实验单位与停止规则见[第 9 章](09-在线实验与ab-test.md)；失败分类和回归集设计见[第 11 章](11-error-analysis与回归测试.md)。

## 9. 离线结果与线上结果各回答一类问题

| 评估方式 | 主要回答 | 典型做法 | 主要边界 |
| --- | --- | --- | --- |
| 离线评估 | 固定任务、样本和协议下，新旧版本有什么差异？ | replay、固定 benchmark、历史 bad case 回归 | 不自动代表当前用户分布，也不能定位因果机制 |
| Shadow | 候选系统处理真实请求时，是否出现运行或长尾问题？ | 脱敏复制请求，不把候选结果返回用户 | 不能测用户反馈，也不能执行真实副作用 |
| Canary | 小比例真实流量下，候选系统是否可安全运行？ | 小范围发布、监控护栏、预设回滚 | 非随机的小流量观察不能单独支持因果结论 |
| A/B 实验 | 随机分配下，当前产品配置对用户结果有什么影响？ | 预先规定随机化单位、主指标、护栏和停止规则 | 结论绑定流量、人群、产品和运行时间窗 |

离线实验更便于控制变量和复现；线上实验更接近真实用户，但风险、混杂和日志责任也更高。shadow、canary、回滚和随机实验的实现细节由[第 9 章](09-在线实验与ab-test.md)主讲；本册只要求报告区分系统结果与模型能力归因。

## 10. 一个客服 RAG 的评估案例

假设团队要把旧版客服模型替换成候选模型。产品目标不是“回答更像人”，而是：

- 用户问题得到正确且可引用的答案；
- 找不到依据时明确说明不确定；
- 不泄露其他用户或内部文档；
- 常见问题首 token 快；
- 复杂问题失败后可转人工；
- 单位成功会话成本不超过预算。

### 10.1 任务切片

| 切片 | 样本来源 | 主要指标 |
| --- | --- | --- |
| 普通 FAQ | 脱敏历史问答 | answer correctness、复问率 |
| 中文长问 | 真实多轮会话 | citation support、长尾延迟 |
| 版本政策 | 版本化内部文档 | evidence recall、版本一致性 |
| 无答案问题 | 人工构造和历史 bad case | abstention accuracy |
| 权限问题 | 不同租户和角色 | unauthorized retrieval、泄露率 |
| 高峰流量 | 线上 replay | P95/P99、队列和成本 |

### 10.2 结果解释

如果候选模型总体正确率提高 3%，但版本政策切片的 citation support 降低 6%，
不能用普通 FAQ 的收益覆盖这个问题。可能的原因包括：

1. chunk 切分让旧版本条款和新版本条款混在一起；
2. reranker 把相似但过时的文档排在前面；
3. 模型更愿意生成答案，却没有承认证据不足；
4. 引用格式改变，评分器误判；
5. 长上下文中间位置召回退化。

下一轮实验应分别固定模型，只替换检索器或只替换 prompt，做配对 replay，
而不是同时升级全部组件。

### 10.3 线上决策

如果候选模型在普通 FAQ 和中文长问上改善，版本政策问题可以通过保守的
abstain、权限过滤和旧版本高风险路由解决，团队可以选择“低风险切片灰度、
政策切片保持旧版本”的策略。这个决策比“全量通过/全量失败”更贴近实际
系统，也保留了后续修复空间。

## 11. 一个可运行的多层评估诊断 demo

下面的程序用标准库模拟一次版本比较。它把质量、切片、回归、安全、线上
统计、延迟和成本保存为独立信号，再列出需要继续观察的动作。所有分数、业务
权重、样本量和阈值都是教学输入；代码不是实际 judge 或 A/B 平台，也不会把
示例数字解释成生产结论。为了演示加权聚合，示例假设各行已经映射到同一方向的
0–1 分数；真实任务若单位或判定含义不同，不得直接加权合成一个总分。

> 代码状态：静态审阅，未运行。

~~~python
import math
from pprint import pprint


eval_cases = [
    {"id": "qa_001", "slice": "normal", "old": 0.82, "new": 0.88, "weight": 1.0},
    {"id": "qa_002", "slice": "zh_customer", "old": 0.78, "new": 0.83, "weight": 1.5},
    {"id": "rag_001", "slice": "citation", "old": 0.76, "new": 0.86, "weight": 1.5},
    {"id": "code_001", "slice": "python", "old": 0.64, "new": 0.68, "weight": 1.0},
    {"id": "math_001", "slice": "reasoning", "old": 0.58, "new": 0.62, "weight": 1.0},
    {"id": "long_001", "slice": "long", "old": 0.70, "new": 0.69, "weight": 1.2},
    {"id": "bad_001", "slice": "p0_badcase", "old": 1.00, "new": 1.00, "weight": 2.0},
    {"id": "bad_002", "slice": "p1_badcase", "old": 0.90, "new": 0.92, "weight": 2.0},
]

safety_cases = [
    {"kind": "unsafe", "blocked": True},
    {"kind": "unsafe", "blocked": True},
    {"kind": "unsafe", "blocked": True},
    {"kind": "benign", "blocked": False},
    {"kind": "benign", "blocked": False},
]

online = {
    "old_success": 480,
    "old_total": 10000,
    "new_success": 535,
    "new_total": 10000,
}

latency = {"new_p95_ttft_ms": 1320, "budget_p95_ttft_ms": 1500}
cost = {"new_success_cost": 0.018, "budget_success_cost": 0.020}


def weighted_score(rows, key):
    total_weight = sum(row["weight"] for row in rows)
    return sum(row[key] * row["weight"] for row in rows) / total_weight


def mean(values):
    return sum(values) / len(values) if values else 0.0


old_score = weighted_score(eval_cases, "old")
new_score = weighted_score(eval_cases, "new")
delta = new_score - old_score

slice_values = {}
for row in eval_cases:
    bucket = slice_values.setdefault(row["slice"], {"old": [], "new": []})
    bucket["old"].append(row["old"])
    bucket["new"].append(row["new"])

slice_report = {
    name: {
        "old": round(mean(values["old"]), 3),
        "new": round(mean(values["new"]), 3),
        "delta": round(mean(values["new"]) - mean(values["old"]), 3),
    }
    for name, values in sorted(slice_values.items())
}

regressions = [
    row["id"] for row in eval_cases if row["new"] + 0.02 < row["old"]
]

tie_margin = 0.02  # 归一化到同一量表后的教学平局阈值
case_wins = sum(
    round(row["new"] - row["old"], 6) > tie_margin for row in eval_cases
)
case_ties = sum(
    abs(round(row["new"] - row["old"], 6)) <= tie_margin
    for row in eval_cases
)
case_score_comparison = {
    "candidate_wins": case_wins,
    "ties": case_ties,
    "candidate_win_rate": (case_wins + 0.5 * case_ties) / len(eval_cases),
}

unsafe = [row for row in safety_cases if row["kind"] == "unsafe"]
benign = [row for row in safety_cases if row["kind"] == "benign"]
attack_success_rate = sum(not row["blocked"] for row in unsafe) / len(unsafe)
over_refusal_rate = sum(row["blocked"] for row in benign) / len(benign)

old_rate = online["old_success"] / online["old_total"]
new_rate = online["new_success"] / online["new_total"]
pooled = (online["old_success"] + online["new_success"]) / (
    online["old_total"] + online["new_total"]
)
se = math.sqrt(
    pooled * (1 - pooled)
    * (1 / online["old_total"] + 1 / online["new_total"])
)
z_score = (new_rate - old_rate) / se

signals = {
    "quality_improved": delta >= 0.03,
    "slice_floor": all(
        report["delta"] >= -0.02 for report in slice_report.values()
    ),
    "regression_clean": not regressions,
    "safety_ok": attack_success_rate == 0.0 and over_refusal_rate <= 0.05,
    # This is a one-sided illustrative signal, not a release test.
    "online_signal": z_score >= 1.64,
    "latency_ok": latency["new_p95_ttft_ms"] <= latency["budget_p95_ttft_ms"],
    "cost_ok": cost["new_success_cost"] <= cost["budget_success_cost"],
}

actions = []
if not signals["quality_improved"]:
    actions.append("inspect_quality_lift")
if not signals["slice_floor"]:
    actions.append("block_slice_regression")
if slice_report["long"]["delta"] < 0:
    actions.append("keep_long_context_in_canary")
if not signals["regression_clean"]:
    actions.append("inspect_regressions")
if not signals["safety_ok"]:
    actions.append("pause_high_risk_traffic")
if not signals["online_signal"]:
    actions.append("collect_more_online_samples")
if not signals["latency_ok"]:
    actions.append("inspect_latency_budget")
if not signals["cost_ok"]:
    actions.append("inspect_success_cost")

recommendation = "conditional_rollout" if actions else "expand_cohort"
failed_gates = [name for name, passed in signals.items() if not passed]
summary = {
    "old_score": round(old_score, 4),
    "new_score": round(new_score, 4),
    "delta": round(delta, 4),
    "case_score_comparison": {
        "candidate_wins": case_score_comparison["candidate_wins"],
        "ties": case_score_comparison["ties"],
        "candidate_win_rate": round(case_score_comparison["candidate_win_rate"], 4),
    },
    "slice_report": slice_report,
    "regressions": regressions,
    "safety": {
        "attack_success_rate": round(attack_success_rate, 3),
        "over_refusal_rate": round(over_refusal_rate, 3),
    },
    "online": {
        "old_rate": round(old_rate, 4),
        "new_rate": round(new_rate, 4),
        "uplift": round(new_rate - old_rate, 4),
        "z_score": round(z_score, 3),
    },
    "signals": signals,
    "failed_gates": failed_gates,
    "actions": actions,
    "recommendation": recommendation,
}
pprint(summary, sort_dicts=False)
~~~

## 12. 版本、污染与可复现性

评估结果必须绑定数据、协议、判分器和执行环境版本。至少记录数据来源与 split、prompt、模型 revision、解码设置、judge/verifier、runner、工具/索引以及运行时间；敏感输出可以脱敏或结构化保存，但应保留足以检查失败的证据。

公开测试集可能因训练、调参或反复查看而失去独立性。近重复、时间切分、canary 和新题对照可以提供不同污染信号，但任何单一检测方法都不能证明“绝对未污染”。私有数据也需要记录来源、版本、访问和泄漏控制。数据血缘、污染类型和可信评估流程由[第 2、5 章](02-benchmark设计.md)深入讲解；本章只把它们作为报告和解释分数的必要条件。

## 14. 本章小结

评估的目的不是积累 benchmark 名称，而是建立一条可以解释模型行为的证据链。

1. 评估结果是能力、证据、协议、安全、延迟和成本的向量，不是一个天然总分。
2. 先写任务契约和成功判定，再决定数据、指标、judge 和运行器。
3. Offline eval 控制变量，online eval 观察真实用户，human eval 判断开放质量，
   automatic eval 扩大规模，safety eval 记录风险，regression eval 保护已修复
   的问题。
4. benchmark 只能覆盖某个能力窗口；MMLU、GPQA、SWE-bench、WebArena、RULER、
   MMMU 等结果不能互相替代。
5. 每个指标都要说明分母、聚合方式、采样预算和失败处理；pass@k、pairwise、
   citation support、ASR 和 over-refusal 表达的是不同问题。
6. 统计显著不等于业务重要，业务提升也不等于模型内部能力提升；要同时看效应
   大小、置信区间、切片和成本。
7. LLM judge 需要人工锚点，公开 benchmark 需要污染边界，线上实验需要随机化、
   监控和可回滚。
8. 最终决策应保留独立 signals 和 actions，让团队知道哪里可以扩大、哪里需要
   继续观察、哪里必须回退。
