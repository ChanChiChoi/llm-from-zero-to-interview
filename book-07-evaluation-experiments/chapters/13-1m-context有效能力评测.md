# 第 13 章：1M Context 的有效能力验证：能接收不等于能使用

## 13.1 一个百万 token 的问题

假设你在做一个研究助手。过去两年的论文、实验日志、代码提交记录和会议纪要
都已经放在系统里，总量约为一百万 token。某天线上指标下降，工程师把这些材料
一次性发给模型，并问：

> 请找出导致错误率上升的三个变更，分别引用证据所在的文档和日期，并说明哪些
> 证据互相矛盾。

服务端返回 HTTP 200，模型也给出了结构完整的回答。这个任务是否成功，不能由
HTTP 状态码决定。模型可能在进入模型前就被应用层截断了旧文档；也可能完整读到
输入，却只在开头和结尾寻找证据；还可能找到了三个相似关键词，却没有把代码提
交、实验结果和监控日志连成因果链。即使答案碰巧正确，引用的段落也可能并不支
持结论。

对于线上服务，还要多问一句：这个答案花了多少时间和显存？它是否让同一批请求
的 p99 延迟超过 SLO？如果一个成功回答需要占用一百多 GiB 的 KV cache，并把
短请求全部挤到队列里，那么它对产品来说仍然可能不可用。

这几个问题共同说明，1M context 不是“模型已经理解一百万 token”的同义词。它
首先是一个输入长度或服务接口声明；真正的能力要经过输入完整性、证据定位、多
段组合、引用归因、扰动鲁棒性以及成本与 SLO 评估之后才能成立。

本章的核心结论可以先写成一句话：

> 长上下文的有效长度不是模型卡上的一个数字，而是任务、证据布局、运行配置和
> 资源预算共同决定的一条能力曲线。

本章中的 1M 表示约 1,000,000 个 tokenizer token，而不是 1,000,000 个汉字、单词
或字节。不同服务对 context window 的口径也可能不同：有的把输入和输出共同计
入窗口，有的在接口层单独公布最大输入和最大输出。比较两个系统前，必须记录
tokenizer、输入上限、输出预留和实际 runtime 长度；否则“支持 1M”可能只是把不
同的计数口径放在了一起。

## 13.2 五种不同的“支持”

看到 context window: 1M 时，最容易把它理解成一个单一数字。实际上至少有五个
不同的判断。

这五个判断还要建立在同一个计数口径上。模型卡中的最大 context、产品 API 的
最大输入、网关转发的 token 数和 runtime 真正接收的 token 数，可能来自不同层，
不能看到其中一个数字就推断其他层也相同。

### 13.2.1 接口支持

tokenizer 能够编码请求，API schema 接受请求，服务端没有立刻返回超长错误。这
只能说明请求没有在入口被拒绝。应用层的历史裁剪、反向代理的 body 限制、SDK
默认的 max input tokens 和输出预算，都可能在这里悄悄改变输入。

接口支持回答的是“请求能否进入系统”，不是“模型是否使用了全部输入”。

### 13.2.2 计算支持

模型的 position、attention mask、kernel、临时 buffer、通信路径和设备内存能够
完成一次 forward。一次请求能跑完，不代表两个请求能同时跑，也不代表峰值流量
下仍满足延迟。

计算支持还要区分 prefill 和 decode。长输入首先增加 prefill 工作量，生成阶段
又需要保存历史状态；只报告生成阶段每秒 token 数，会掩盖长请求在入口等待的成本。

### 13.2.3 训练支持

模型在预训练或长上下文继续训练中见过相近长度，并且训练样本中存在远距离引用、
跨段推理和长文档任务。单纯把位置索引外推到更大的数值，并不会让模型自动学会
使用远处的信息。

训练长度相近也不等于任务分布相近。把十六个互不相关的 4K 网页拼成 64K 序列，
只说明模型看到了更长的序列，不说明它学会了在第 1 段定义变量、第 500 段找实验
结果、第 900 段核对例外条件。

### 13.2.4 任务能力

模型能够在不同位置找到证据，识别相似但错误的材料，将多处证据组合起来，并用
引用或结构化字段把结论绑定回原文。这才接近读者通常说的长上下文理解。

定位一个唯一字符串和比较多个版本的因果证据都可以使用 1M 输入，但前者主要是
检索，后者还要求实体消歧、时间排序、冲突处理、归因和不确定性表达。

### 13.2.5 生产可用性

生产可用性还包括单位成功任务成本、队列等待、峰值显存、取消清理、并发隔离、
重试、降级和权限。研究环境中的单请求成功，不会自动转化成交互式产品能力。

这五种支持之间有先后关系，但没有包含关系。一个模型可以有很大的接口上限，
却没有稳定的跨段推理；也可以在研究环境中完成 1M 任务，却因成本太高不能用于
交互式产品。

## 13.3 一个请求究竟经过了什么

把“模型能不能读一百万 token”拆开以后，可以把一次请求看成一条有边界的流水
线。用户原始文档先经过 tokenizer 和消息模板，网关再把它转换成模型真正看到的
token 序列；模型为序列计算表示，解码器生成答案；应用最后还要验证答案里的引
用、结构化字段和权限。任意一层改变了输入或输出，最终任务就不再是原来那道题。

例如，研究助手的原始材料有 1,000,000 个 token。应用为了给回答预留 8,000
个输出 token，把输入预算设为 992,000；网关又因为默认限制只转发 512,000 个
token；拼接器在截断时保留了最新日志，却丢掉了两年前定义实验指标的文档。模型
收到的并不是同一份一百万 token 的材料，但如果系统只记录用户侧字符数，事故
会被误判成模型长上下文能力不足。

一个可复现的长上下文样本至少应记录下表中的字段：

| 层次 | 要记录的对象 | 典型错误 |
| --- | --- | --- |
| 原始输入 | 文档 ID、版本、字节数、原始顺序 | 上传时漏文件或重复文件 |
| 编码输入 | tokenizer 名称、revision、token 数 | tokenizer 不同导致长度估算偏差 |
| 服务输入 | 网关转发 token、模板、截断策略 | 静默截断、system prompt 被插入中间 |
| 模型计算 | 实际序列长度、attention mask、cache layout | mask 错位、padding 被当作证据 |
| 生成输出 | 输出 token、停止原因、引用字段 | 预算耗尽、引用被截断 |
| 任务结果 | 金标准证据、原子主张、验证结果 | 答案看似合理但证据不支持 |
| 运行成本 | prefill、decode、峰值显存、排队时间 | 长请求拖垮短请求 |

这张表的意义不在于增加日志数量，而在于把“输入没有被模型看到”和“模型看到了
但没有使用”分成两个可检验的假设。前一个假设应在服务边界解决，后一个假设才
属于模型和评测问题。

### 13.3.1 任务成功是多个条件的合取

设 I 表示输入完整，E 表示证据被找到，R 表示推理关系正确，C 表示引用能够
支撑主张，O 表示运行条件满足，那么：

~~~math
S=I\land E\land R\land C\land O
~~~

这不是说每个任务必须有同样严格的五个分量，而是提醒我们：只报一个最终字符串
是否存在，无法知道失败发生在哪一层。对高风险研究助手，C 和 O 不能因为答案
“看起来像对的”而被省略。

一个产品也可以把任务拆成分层结果。例如：

- 基本完成：给出与参考答案一致的结论；
- 证据完成：每个关键主张都有支持来源；
- 协议完成：结构化字段和引用可被下游解析；
- 运行完成：在预算、延迟和权限约束内返回。

分层结果比单一成功标签更适合错误分析，也能避免把服务超时和模型事实错误混
在一起。

## 13.4 长上下文为什么成为独立问题

早期 Transformer 模型的序列长度通常只有几百到几千 token。限制来自三条链路。

在算法上，标准全注意力要让每个位置和其他位置交互，注意力分数矩阵的规模随序
列长度呈平方增长。位置表示也需要覆盖更大的范围，模型不能只在短序列上学会局
部邻接关系，却期待它在百万 token 上自然完成远距离引用。

在训练上，长样本昂贵且稀少。把十六个 4K 文档拼成一个 64K 序列，token 数量虽
然变长了，但不一定形成有意义的长程任务。模型可能学到文档拼接的统计规律，却
没有学到定义、证据、反例和结论之间的远距离关系。

在系统上，prefill 要处理整个输入，KV cache 又要为后续 decode 保存历史表示。
即使 kernel 降低了中间矩阵的读写和峰值显存，长输入仍会占用计算、显存和通信
资源。于是长上下文不是只修改 max_position_embeddings 的配置问题，而是位置
机制、数据、训练、kernel、调度和评估共同变化的问题。

### 13.4.1 局部任务和全局任务不是同一种难度

在短文本问答中，相关信息通常集中在一个段落里。模型只要在局部窗口内建立主题、
实体和结论之间的联系，就能获得不错的结果。上下文变长以后，困难不是简单地
“多读几页”，而是信息的组织方式变了：

1. 定义、证据、反例和结论可能被不同文档隔开；
2. 旧版本和新版本可能同时存在；
3. 关键条件可能在表格、脚注或附录；
4. 问题可能要求模型说明证据之间的关系；
5. 缺失证据本身可能是正确答案的一部分。

可以比较下面两个问题：

1. 在一百万 token 中找出唯一字符串 release-2026-04-17；
2. 在一百万 token 中判断 release-2026-04-17 是否导致错误率上升，并区分它与
   同名旧版本。

第一题主要要求定位，第二题要求定位、实体消歧、时间排序、因果判断和引用。两
题共享一个输入长度，却是不同能力族。前者失败，可能是位置或输入管道问题；后
者失败，还可能是模型不会组合证据。

长上下文的负例也变得重要。在短问答里，把相关段落放进提示通常已经足够；在长
材料里，相似名称、过期配置和重复数字会形成强干扰。真正有诊断价值的样本要同
时包含正确证据、相似错误证据和明确的时间或版本条件。

### 13.4.2 Prefill、decode 和尾延迟

设每个请求的 prefill 时间为 t_p，decode 时间为 t_d，排队时间为 t_q，则用户
感知延迟可以粗略写成：

~~~math
T_{\mathrm{e2e}}=t_q+t_p+t_d
~~~

长输入主要增加 t_p，但它还会影响调度和显存，从而间接增加短请求的 t_q。若只
报告 decode 的每秒 token 数，会把最影响用户等待的部分隐藏起来。

因此至少要分开报告：

- 首 token 延迟；
- 完整回答延迟；
- prefill 计算时间；
- decode 时间；
- 排队时间；
- p50、p95 和 p99；
- 超时、取消和降级比例。

一个 1M 请求的单次延迟可以接受，不代表它在混合流量下可接受。尾延迟和短请求
的受影响程度必须出现在同一份容量报告里。

## 13.5 位置机制与长程学习

### 13.5.1 位置表示解决什么问题

位置机制回答的是“模型如何区分不同位置”。它不直接回答“模型是否愿意在很远
的位置取证”。从 learned absolute position 到 relative position、RoPE、ALiBi，
再到各种 RoPE scaling、position interpolation 和混合位置方案，研究者一直在
解决位置范围、相对距离和外推稳定性之间的矛盾。

对自回归模型来说，位置表示至少影响三件事：

1. 不同位置的表示如何区分；
2. 远近 token 的相对关系如何进入 attention；
3. 超出训练长度后数值是否稳定。

即使三件事都稳定，也不保证模型会把远处证据提取出来，更不保证生成时能把多个
远处证据组合成可验证结论。

### 13.5.2 RoPE 的直觉与公式

以 RoPE 为例，某一对维度上的旋转角度可以抽象为：

~~~math
\theta_{p,i}=p\,\omega_i
~~~

其中 p 是 token 位置，ω_i 是第 i 个二维子空间的频率。两个位置之间的相对角
度为：

~~~math
\Delta\theta_{p,q,i}=(p-q)\omega_i
~~~

这种结构让 attention 内积能够表达相对位移。可是，当长度外推改变了频率或位置
缩放，模型的相对相位结构也随之改变。某些频率在很长距离上可能出现周期性混淆，
某些频率又过度强调局部差异。

位置公式能否计算，只说明数值路径存在；模型是否在长距离任务上稳定，要靠长样
本训练、位置分布和任务评估证明。

### 13.5.3 如果模型宣称不使用 RoPE

“不使用 RoPE”不等于“不使用位置信息”，也不等于“可以无限长地理解文本”。
位置可能通过相对偏置、卷积、递归 state、状态更新、注意力结构或训练数据中的
顺序模式进入模型。读到一个 no-RoPE 或 no-explicit-position 的声明时，应该追
问：

1. 顺序信息从哪条计算路径进入；
2. 最大输入长度由什么 runtime 和状态结构决定；
3. 长度外推是否需要继续训练或特殊采样；
4. 远距离证据和中间位置是否单独评估；
5. state 或 cache 的容量如何随输入增长；
6. 声明来自论文、模型卡、产品文档还是社区转述。

这能避免把一个架构标签直接升级成能力结论。位置机制的创新值得单独研究，但
评价它时仍要回到输入完整性、证据任务和生产成本。

## 13.6 长上下文扩展方法的取舍

### 13.6.1 Position Interpolation

Position Interpolation 的基本思路是把更长序列的位置映射回模型训练时见过的
位置范围。它往往比直接把位置索引外推到更大范围稳定，但映射会改变远近位置的
分辨率，可能影响局部顺序和细粒度定位。

它适合解决“位置数值超出训练范围”的一类问题，不能单独解决长文档任务缺少多
证据监督的问题。验证时应同时测短上下文退化、不同证据位置和多证据组合。

### 13.6.2 RoPE Scaling、YaRN 与 LongRoPE

RoPE scaling 通过调整频率或位置映射扩展可用范围。YaRN 等方法进一步关注不同
频率分量、温度和少量长样本继续训练的组合；LongRoPE 类路线则探索非均匀位置
扩展和分阶段适配。这里的共同点是：它们改变了位置计算或训练分布，不是只改
一个配置字段。

方法比较时要记录：

- 是否需要长上下文继续训练；
- 短上下文精度是否退化；
- 中间位置和多证据任务是否改善；
- 推理 kernel 是否需要特殊支持；
- 训练和推理成本如何变化；
- 对 tokenizer、模板和 checkpoint 是否有兼容要求。

公开论文可以支持方法在论文实验中的结论，但不能直接支持某个生产模型在 1M
任务上的保证。模型版本、训练数据、硬件和评估协议必须对齐。

### 13.6.3 Sliding Window、Sparse Attention 与 Hybrid Attention

滑动窗口和稀疏 attention 可以减少每个 token 需要交互的范围，从而改善长序列的
计算或显存。[Longformer](https://arxiv.org/abs/2004.05150)把局部滑窗与任务相关
的 global attention 结合；[BigBird](https://arxiv.org/abs/2007.14062)把局部、
随机和 global token 的稀疏连接组合起来。它们共同回答“怎样不让每个 token 都
和全序列做两两交互”，但连接图并不相同。

稀疏化的代价是远距离证据必须沿允许的 attention 边传播。纯局部窗口中，跨越很
远的两段信息要经过多层逐步传递；加入 global 或随机边可以缩短某些路径，却让
结果依赖具体 mask、层数和训练任务。模型可能读到每个局部段落，却无法在输出时
把相隔很远的证据放在同一个判断里。

混合注意力可能让部分层使用局部模式、部分层保留全局或稀疏全局 token。评估时
应问的是“远距离信息经过几跳到达输出”，而不是只看理论复杂度。一个复杂度更低
的结构，如果引用支持率在多证据任务上大幅下降，不能被简单写成更高效的替代品。

### 13.6.4 Ring Attention 与 Context Parallelism

Context parallelism 把长输入分到多个设备，设备之间交换必要的 attention 或 state
信息。Ring Attention 代表一种利用环形通信组织长上下文计算的思路。它们主要解
决“单个设备放不下或算不动”的系统问题，但会引入通信、同步、拓扑和故障恢复
成本。

工程评估需要同时测：

1. 单请求输入长度和设备内存；
2. 跨卡通信量和链路利用率；
3. 多请求并发时的尾延迟；
4. 某个设备或链路失败时的恢复；
5. 证据位置、引用支持和质量变化。

把 context parallelism 当作免费扩容，会低估通信和调度代价。把它只当作硬件技
巧，又会忽略它可能改变信息访问路径。

### 13.6.5 FlashAttention、PagedAttention 与状态压缩

FlashAttention 通过分块和在线 softmax 减少中间矩阵的读写与峰值显存，并不等于
把普通全 attention 的数学依赖自动变成线性。PagedAttention 主要改善 KV cache
的分页和共享管理，也不自动提升模型对远距离证据的理解。

KV 量化或状态压缩可以降低存储，但需要测试：

- 压缩误差是否集中在长距离引用；
- 不同层、不同 head 或不同模态是否敏感；
- 量化 scale 和布局是否被 runtime 正确解释；
- 长请求取消后状态是否及时回收；
- 质量收益是否超过重试和人工复核成本。

硬件优化的正确结论应是“在某个 workload 上减少了某类资源”，而不是“因此模型
理解了更长上下文”。

### 13.6.6 代表路线分别解决哪一层瓶颈

把长上下文方法放在一张表里比较时，必须先区分它们改的是位置表示、任务学习，
还是设备上的计算与状态管理。若一种方法把可接收长度从 32K 扩到 128K，另一种
方法把单卡峰值显存降低一半，这两个结果回答的不是同一个问题。

| 代表工作 | 主要改动与所解问题 | 论文报告的证据 | 代价、限制与下一步验证 |
| --- | --- | --- | --- |
| [Position Interpolation（PI）](https://arxiv.org/abs/2306.15595) | 将超出训练长度的位置映射回已见位置区间，减少直接外推到未见位置导致的极端注意力分数；随后用少量长序列微调适配。 | 在 LLaMA 7B—65B 上从 2,048 扩到 32,768，论文报告最多 1,000 步微调，并评估 passkey、语言建模、长文摘要及短任务保持情况。 | 线性插值会压缩各位置间隔，扩展倍数增加时局部位置分辨率也改变；它没有自动教会模型跨文档取证。要分别复测短程任务、位置分桶和组合证据任务。 |
| [YaRN](https://arxiv.org/abs/2309.00071) | 不把所有 RoPE 频率维度同等缩放：按波长在保留局部相对位置信号与扩展低频范围之间平滑过渡，并用 attention logit scaling 调整扩展后的注意力分布。 | 作者在其 LLaMA/Llama 2 配置中报告，达到相近扩展目标所需训练 token 约为先前对照方法的 1/10、训练步数约为 1/2.5；论文也公开了 64K/128K 模型。 | 频率边界、扩展比例和微调语料是 recipe 的组成部分，论文效率比不是所有模型的固定倍率。复核目标 checkpoint 的 RoPE 配置、长短任务回归和对应 runtime 实现。 |
| [LongRoPE](https://arxiv.org/abs/2402.13753) | 搜索不同 RoPE 维度和 token 位置各自适用的非均匀插值；先在 256K 微调，再对扩展模型进行第二次位置插值到 2,048K，并在 8K 重新调整以恢复短上下文表现。 | 作者在 LLaMA 2 与 Mistral 实验中报告非微调时最高 8 倍扩展，以及分阶段扩展到 2,048K；其结果同时报告长文指标和原长度 benchmark。 | “2,048K”依赖分阶段训练、搜索和模型设置，不等于长文推理正确率。要查清模型是否用相同 recipe，并按目标任务测有效长度、短程退化、算力和成本。 |
| [Ring Attention](https://arxiv.org/abs/2310.01889) | 将序列分块放到多个设备，环形传递 K/V 块，并把通信与块级 attention 计算重叠，解决单设备放不下长序列的问题。 | 论文展示了分布式训练/推理可扩展到随设备数增加的长序列，并测量内存和计算利用率。 | 它改变计算的分布位置，不改变位置编码或长程任务监督；对标准 dense attention，总体两两交互工作仍随序列长度平方增长。需测链路带宽、通信重叠、负载不均、尾延迟和设备故障恢复。 |
| [FlashAttention](https://arxiv.org/abs/2205.14135) 与 [PagedAttention](https://arxiv.org/abs/2309.06180) | 前者通过分块与在线 softmax 减少 HBM 中间读写；后者按 block 管理 KV cache，减少碎片并支持缓存共享。 | 两者分别提供 attention IO 优化与 serving KV 管理的算法/系统证据。 | 它们缓解计算数据移动或状态分配，不单独提高证据召回、位置鲁棒性或多步推理。要在目标 kernel、长度、batch 和并发上测资源收益，再配合任务评测。 |

这张表也解释了为什么“上下文扩展算法”和“上下文并行”不能互相替代：PI、YaRN
和 LongRoPE 主要处理位置分布如何延伸；Ring Attention 主要处理长序列如何跨设
备计算；FlashAttention 与 PagedAttention 处理具体的数据移动和缓存管理。一个系
统可以同时采用多条路线，但每条路线的收益都要在它负责的层面单独验收。位置方
法改善了 passkey，并不能证明它改善了冲突归因；KV 占用下降，也不能证明生产
吞吐按同一比例提高。

## 13.7 长上下文训练：长度覆盖不等于任务覆盖

### 13.7.1 三层训练覆盖

长上下文训练可以分成三个层次：

1. 长度覆盖：训练序列数值上达到目标长度，位置和 mask 能正常工作；
2. 信息覆盖：证据分布在不同位置，模型必须访问远处内容；
3. 任务覆盖：监督或奖励要求模型组合证据、处理干扰、给出引用，并在缺证据时
   拒答。

只完成第一层，最多说明模型可以处理长输入；第二层决定是否会找证据；第三层
才接近可用的长文档推理。

### 13.7.2 长样本如何提供有效监督

一个 1M 样本如果只是把许多互不相关的网页连接在一起，模型只是在长序列中看
到了更多 token。只有当目标要求它在远处寻找、比较、合并和引用时，才是在训练
长程使用能力。

有意义的监督可以包括：

- 远距离实体指代；
- 分散证据的多跳问题；
- 版本和时间冲突；
- 证据不足时的 abstention；
- 原子主张到来源的引用；
- 文档级摘要和章节级比较；
- 工具结果跨多轮保持一致。

长度 curriculum、长文档继续训练、位置采样和任务构造共同决定了“见过多长”能
否转化成“会用多长”。训练日志还应记录不同长度和任务族的 token 比例，不能只
写一个最大 sequence length。

### 13.7.3 位置采样和捷径

如果训练集中的长样本大多是“文档前面给标题，最后给答案”，模型可能学到优先
看开头和结尾的捷径。要打破这个捷径，训练任务需要：

1. 轮换关键证据的位置；
2. 增加中间证据和多证据合取；
3. 加入相似错误证据；
4. 改变文档顺序；
5. 加入版本冲突和引用约束；
6. 对信息不足的样本提供正确拒答信号。

训练目标不能只奖励最终文字的流畅度。若答案引用错误不会受到惩罚，模型可能学
到“先猜一个结论，再找看似相关的段落”的策略。

## 13.8 长度数字背后的资源模型

### 13.8.1 KV Cache 的粗略估算

设 batch 为 B，序列长度为 T，层数为 L，每层 KV head 数为 H_kv，每个 head 的
维度为 d_h，每个元素占 b 字节，则普通 K/V cache 可以粗略写成：

~~~math
M_{\mathrm{KV}}
\approx 2 B L T H_{\mathrm{kv}} d_h b
~~~

式中的 2 来自 K 和 V。它忽略 block metadata、对齐、量化 scale、临时 workspace
和不同层的特殊布局，但能看到最重要的关系：在其他条件不变时，KV 占用与 T
近似线性增长。

### 13.8.2 一个教学估算

假设 B=1、L=32、H_kv=8、d_h=128，使用 BF16，即每个元素 2 字节，T=1,000,000：

~~~math
M_{\mathrm{KV}}
=2\times 1\times 32\times 10^6\times 8\times 128\times 2
\approx 131.1\times10^9\ \mathrm{bytes}
\approx 122.1\ \mathrm{GiB}
~~~

这不是某个厂商的部署承诺，而是容量直觉。模型权重、激活、通信 buffer、其他
请求的 cache 和调度余量还没有算进去。如果把 KV 改成 FP8，理论上元素存储可以
近似减半，但 scale、转换 kernel、精度影响和实现布局仍然要实测。

如果采用 MLA、递归 state 或其他压缩表示，保存的对象不再是普通 K/V，公式必须
换成对应的 state layout。不能把普通 K/V 公式直接套到所有新架构上。

### 13.8.3 整机容量预算

KV cache 只是 decode 阶段最容易被忽略的一项。一次真实请求的设备内存还要容纳
模型权重、运行时 workspace、激活、通信缓冲区和其他请求：

~~~math
M_{\mathrm{device}}
\approx M_{\mathrm{weight}}+M_{\mathrm{KV}}
+M_{\mathrm{workspace}}+M_{\mathrm{comm}}+M_{\mathrm{other}}
~~~

如果设备的可用显存为 M_cap，系统不能把 M_device 设计到恰好等于 M_cap，需要
留出碎片和突发请求的余量 M_slack：

~~~math
M_{\mathrm{weight}}+M_{\mathrm{KV}}+M_{\mathrm{workspace}}+M_{\mathrm{comm}}
\le M_{\mathrm{cap}}-M_{\mathrm{slack}}
~~~

假设某个服务使用八张 80 GiB GPU，模型权重和运行时固定占用 420 GiB，通信与
workspace 预留 70 GiB，计划保留 15% 的调度余量，则可给长请求的 KV 预算并不是
8×80-420-70=150 GiB，而更接近：

~~~math
M_{\mathrm{KV,budget}}
\approx 8\times80\times(1-0.15)-420-70
=54\ \mathrm{GiB}
~~~

这个教学数字说明了一个常见误区：把整机显存直接除以单 token 的 KV 大小，会高
估并发和上下文长度。若单请求 KV 估算是 122 GiB，它即使理论上能在另一套设备
上运行，也无法放进这套服务为长请求分配的 54 GiB 预算。

工程上只能选择模型并行、KV 量化、状态压缩、分块处理、低并发专用池或 RAG 路由
等路径。每条路径都要重新测质量和成本。

### 13.8.4 Prefill 的计算复杂度

对标准全注意力，一个粗略的注意力计算量可以写成：

~~~math
C_{\mathrm{attn}}=O(B H T^2 d_h)
~~~

FlashAttention 减少了中间矩阵的读写与峰值显存，并不等于把普通全 attention
的数学依赖自动变成线性。稀疏 attention、滑动窗口、线性 attention 和混合架构
可能改变复杂度，但它们也会改变远距离信息的路径。

评估时应把“省了多少显存”和“还能否准确引用远处证据”放在同一张结果表里。

### 13.8.5 单位成功任务成本

设一次评估批次的 prefill、decode、工具和额外重试成本分别为 C_p、C_d、C_tool、
C_retry，成功任务数为 N_success，则在这些成本都按同一批次汇总、且 C_retry 不
重复计算已经包含在其他项中的尝试时：

~~~math
C_{\mathrm{success}}
=\frac{C_p+C_d+C_{\mathrm{tool}}+C_{\mathrm{retry}}}
{\max(1,N_{\mathrm{success}})}
~~~

如果模型通过十倍的思考 token 和多次重试只提升几个百分点，单位成功成本可能
反而变差。成本应与答案正确、引用支持、p95/p99 和安全风险一起报告。

## 13.9 从 Needle 到真正的证据任务

Needle-in-a-haystack 是一个有用的冒烟测试：在长文档中插入一个唯一字符串，再
让模型找回来。它能够发现输入被截断、位置索引错误或某些区域的信息明显丢失，
因此不应该被完全否定。

问题在于，唯一字符串太容易被局部匹配。模型可能找到 needle，却不知道它和问
题有什么关系，也不需要处理相似但错误的段落。一个完整的长上下文评测至少要逐
步增加四种难度。

第一层是单证据检索。把答案放在开头、四分之一、中间、四分之三和末尾，问题只
依赖一段内容。这一层主要测位置覆盖和输入完整性。

第二层是多证据合取。把定义、实验结果和例外条件分散到三段，只有同时读取三段
才能得到正确答案。此时单点关键词命中不够，模型必须维护实体和关系。

第三层是干扰和版本消歧。加入旧版本日志、同名服务和包含相似数字的无关报告，
要求模型按日期、版本和实体筛选。它测的是检索条件，而非纯粹的记忆。

第四层是冲突与归因。让监控日志显示错误率上升，而发布记录声称修复成功，要求
模型指出冲突、给出各自证据，并说明不能从现有材料推出什么。答案不仅要“像正确”，
还要能回到原文验证。

### 13.9.1 合格样本的标注结构

长上下文评测的样本不能只由“材料、问题、标准答案”组成。为了判断模型究竟做
对了什么，标注还要保存证据的角色和关系。例如：

~~~text
evidence_id: doc_17#p4
role: change
entity: ranking-service
version: v3.2
date: 2026-04-17
claim: replaced cosine threshold with adaptive threshold
~~~

另一个段落可以标为 effect，第三个段落标为 counter_evidence。最终答案若只找到
change 而没有找到 effect，不能记作完整成功；若答案说“该变更导致回滚”，却
只引用了“变更已发布”的段落，也不能记作引用正确。

评测数据还要有对照组。至少可以做四种对照：

| 对照 | 变化 | 能排除的误判 |
| --- | --- | --- |
| 位置对照 | 同一证据轮换到开头、中间、末尾 | 把位置偏差误认为知识不足 |
| 顺序对照 | 文档顺序随机但 ID 保持 | 把固定顺序记忆误认为推理 |
| 干扰对照 | 加入同名实体和旧版本 | 把关键词命中误认为消歧能力 |
| 证据对照 | 删除一条关键证据 | 检查模型是否会在证据不足时继续编造 |

如果没有这些对照，单次高分很难说明模型掌握了可迁移的长程能力。特别是人工构
造的 needle，如果 needle 的格式、词汇和答案高度特殊，模型可能通过表面特征完
成任务，而不是按文档语义检索。

长上下文评测还要防止答案泄漏。问题不能直接包含证据段落的独特词串，测试集不
能与训练或公开 benchmark 重复，生成时的 system prompt 和工具权限要固定。否则
实验测到的可能是模板记忆、数据污染或 harness 的额外帮助。

### 13.9.2 代表 benchmark 分别补上什么证据

长上下文评测不是一个 benchmark 从简单到困难的单行榜单。不同研究改变了不同的
实验因素：有的把证据位置固定下来检查位置偏差，有的提高干扰或跨段依赖，有的
扩大真实任务覆盖。先明确它们各自排除了哪一种误判，再决定如何组合。

| 研究或数据集 | 它设计了什么 | 它补上的评测缺口与论文证据 | 仍然不能证明什么 |
| --- | --- | --- | --- |
| Needle-in-a-Haystack（NIAH） | 在长干扰文本中放入可精确匹配的单条信息，再改变其位置与上下文长度。 | 成本低、容易复现，适合先发现截断、位置区间丢失、模板错误或模型完全找不到显著标记等问题。 | 单一显著 needle 可能靠词面匹配完成，无法代表实体消歧、多证据合取、冲突解释或引用是否支持结论；高分只能作为冒烟证据。 |
| [Lost in the Middle](https://arxiv.org/abs/2307.03172) | 在多文档 QA 和 key-value 检索中控制相关信息所在位置，比较开头、中间与结尾。 | 论文发现多个模型会随证据位置变化显著退化，揭示“长度固定、只移动证据”的位置敏感性；这让位置成为单独的实验变量。 | 它主要识别位置效应，不覆盖所有文档任务或百万 token 长度；复现时仍要控制重复、顺序、证据密度与模型模板。 |
| [RULER](https://arxiv.org/abs/2404.06654) | 可配置长度和任务复杂度；在 NIAH 变体之外加入多 needle、多跳 tracing 与 aggregation，共 13 类任务。 | 作者评测 17 个长上下文模型：很多模型在 vanilla NIAH 接近满分，但随长度和复杂度增加下降；在其 32K 满意度标准下，达到模型自称至少 32K 的模型中只有约一半通过。它把“能找一个针”推进到受控的检索、追踪和聚合。 | 任务是合成的，受模板、needle 格式和任务族影响；“满意”是论文定义的阈值，不是通用产品门槛。它适合控制变量诊断，不能代替目标语料。 |
| [NoLiMa](https://arxiv.org/abs/2502.05167) | 降低问题与目标证据之间的词面重叠，迫使模型通过潜在关联找到 needle，而非直接复用相同词串。 | 作者评测 12 个声称支持至少 128K 的模型；论文报告 32K 时有 10 个模型跌到各自短上下文基线的一半以下，GPT-4o 从约 99.3% 的短程基线降到 69.7%。它针对普通 needle 的词面捷径。 | 仍是人工构造的关联检索任务，不能覆盖开放式因果分析、长篇写作、生产 RAG 或任意领域分布；数值绑定论文模型与提示。 |
| [LongBench v1](https://arxiv.org/abs/2308.14508) | 将 21 个中英文数据集统一为六类长文本任务，包括单文档/多文档 QA、摘要、少样本学习、合成任务和代码补全。 | 提供比单一检索 probe 更宽的任务面；原论文报告英文平均 6,711 words、中文平均 13,386 characters，并用不同任务观察长度扩展、位置扩展及检索压缩。 | 平均长度不是百万 token；数据集、指标和任务难度异质，统一 harness 不会让它们变成同一能力，也不适合作为单个总分。报告必须保留任务和语言切片。 |
| [LongBench v2](https://arxiv.org/abs/2412.15204) | 由近 100 位不同专业背景的受教育参与者协作采集，经过自动与人工难度审查；含 503 道多选题，覆盖单/多文档 QA、长上下文 ICL、对话历史、代码库和结构化数据。 | 试图测现实长任务中的理解与推理，而非只测召回；上下文范围是 8K—2M **words**，作者报告限时 15 分钟的人类专家准确率 53.7%、直接作答最佳模型 50.1%，o1-preview 使用较长推理为 57.7%。 | 长度单位是 words 而不是 tokens，2M words 不能写成 2M-token 窗口；503 题是经过筛选的高难多选集合，分数受模型集合、推理预算和选项格式影响，也不能单独代表业务总体。 |
| [LongBench Pro](https://arxiv.org/abs/2601.02872) | 含 1,500 条中英文自然长上下文样本、11 个主任务和 25 个次任务，长度 8K—256K tokens；按长度、难度和 full/partial context dependency 分层。题目由模型起草并经专家核验。 | 它同时面向任务多样性与长度分层。2026 年 1 月作者预印本报告评估 46 个模型，并提出长上下文优化、有效长度与跨语言差异等观察。 | 当前公开范围止于 256K，不能证明 1M 表现；它是单版预印本，结论仍需独立复核。模型辅助构题与专家筛选也可能影响样本分布。 |
| [MRCR v2](https://github.com/google-deepmind/eval_hub/tree/master/eval_hub/mrcr_v2) | 在合成多轮对话里重复相似请求，每次回答不同；要求先数出目标实例再复现对应回答。官方仓库提供多 needle 和多长度版本，文档称可生成到 8M。 | 固定较简单任务复杂度而扩展长度，可观察长度曲线；8-needle 版本降低随机复制某个相关回答就蒙对的机会，仓库估计此种随机噪声约 15%。 | 它刻意把 reasoning 复杂度保持得较低，适合测长程定位/共指，不等于跨文档推理；公开仓库滚动更新，使用时要固定数据、指标、revision，并说明是否给工具。OpenAI MRCR 与 DeepMind MRCR v2 属于相关但不等同的任务实现，分数不可拼接。 |

这些研究形成的是互补的证据梯子，而不是严格难度排名：NIAH 与 Lost in the
Middle 用于查输入和位置；RULER 与 NoLiMa 用受控任务识别 needle 捷径、长度与
复杂度效应；LongBench 系列增加多任务和自然样本覆盖；MRCR v2 提供更长长度上的
固定复杂度曲线。真实系统仍要加目标语料上的多证据、版本冲突、引用归因和不可
回答样本，并报告同一套 tokenizer、模板、工具权限、推理预算、长度单位、成本
和置信区间。

VQA、DocVQA、ChartQA 和 AgentBench 可以用于多模态输入或 Agent 行为评估，但它们
不是文本 1M context 的直接证据。若目标系统的上下文含图像、表格或工具轨迹，应
把这些任务作为相邻能力单独记账，并额外说明视觉 token、文档解析、工具 scaffold
和状态环境；不能把它们的分数合并进文本长上下文总分。

## 13.10 用条件化指标描述有效能力

一次长上下文任务不是一个长度数字，而是由输入、问题、证据布局、输出和运行条
件组成的样本。可以抽象为：

~~~math
e=(x,q,y,z,p,c,h)
~~~

其中 x 是上下文，q 是问题，y 是输出，z 是标注证据集合，p 是证据位置，c 是
成本记录，h 是模型、模板、工具和评测 harness。

在给定任务类型 τ、长度 T、证据布局 r 和 harness h 后，成功概率才有明确含义：

~~~math
A(T,\tau,r,h)=P(\mathrm{success}\mid T,\tau,r,h)
~~~

这条式子提醒我们，所谓“有效长度”通常是一条曲线而不是一个拐点。模型在 T=256K
的单证据检索上可能保持 0.9 的成功率，在同样长度的冲突归因上却只有 0.5。把
两个结果平均成一个“256K 有效”会掩盖真正的边界。

### 13.10.1 条件还包括干扰和预算

对于任务族 τ，可以把长度、证据布局、干扰强度和运行配置放在同一个条件里：

~~~math
A(T,\tau,r,d,h,b)
=P(\mathrm{success}\mid T,\tau,r,d,h,b)
~~~

其中 r 是证据位置布局，d 是干扰条件，h 是评测 harness，b 是推理预算。模型可
能在 T=256K、单证据、低干扰、短输出时成功率很高，在相同长度但多证据、冲突和
长思考预算下明显下降。把这些样本混成一个均值，得到的“有效 256K”没有足够
解释力。

### 13.10.2 有效长度的定义

假设任务族 τ 有最低答案正确率 a_min、最低引用支持率 c_min、最高 P95 延迟
lat_max 和最高单位成功成本 cost_max，可以在预先指定的长度桶集合中定义条件化
有效长度：

~~~math
L_{\mathrm{eff}}(\tau,r,d,h,b)
=\max\left\{T:
\begin{array}{l}
A_{\mathrm{answer}}(T,\tau,r,d,h,b)\ge a_{\min}\\
S_{\mathrm{support}}(T,\tau,r,d,h,b)\ge c_{\min}\\
\mathrm{P95}(T,\tau,r,d,h,b)\le lat_{\max}\\
C_{\mathrm{success}}(T,\tau,r,d,h,b)\le cost_{\max}
\end{array}
\right\}
~~~

这个定义不是自然定律，而是把业务目标写进“有效”的含义。换一组阈值、证据布局
或硬件，L_eff 就可能改变。因此报告应写完整条件，而不是只写一个数字。式中的
`max` 还隐含了一个前提：能力随长度大体单调，或者所有不超过所选长度的桶都已
通过。如果曲线存在局部波动，应报告通过的长度集合、置信区间和失败桶，而不能
挑出一个偶然通过的孤立点作为有效上限。

### 13.10.3 Ingest、Retrieve、Reason、Attribution、Operate

评测报告可以拆成以下层次：

- Ingest：客户端、服务端和 runtime token 数是否一致；
- Retrieve：金标准证据是否被找到，按位置和干扰桶统计；
- Reason：是否正确组合多个证据，处理实体、时间和版本关系；
- Attribution：引用段落是否支持对应原子结论；
- Robustness：改变顺序、加入干扰或冲突后，结论是否稳定；
- Operate：prefill、decode、峰值显存、并发、尾延迟和单位成功成本。

曲线的形状本身就是诊断信号：

1. ingest 先下降，说明服务边界或 tokenizer 预算有问题；
2. ingest 稳定而 evidence recall 下降，说明位置、训练或证据路径出现问题；
3. evidence recall 尚可而 citation support 下降，说明模型找到材料但没有绑定主张；
4. 质量稳定而 P95 和单位成本爆炸，说明能力存在但服务条件不成立。

## 13.11 指标与可验证输出

### 13.11.1 证据召回和精确

对于证据集合有明确标签的任务，可以计算证据召回率：

~~~math
R_{\mathrm{evidence}}
=\frac{|Z_{\mathrm{gold}}\cap Z_{\mathrm{pred}}|}
{\max(1,|Z_{\mathrm{gold}}|)}
~~~

如果模型找到了很多无关文档，召回率仍可能很高，因此还可以报告证据精确率：

~~~math
P_{\mathrm{evidence}}
=\frac{|Z_{\mathrm{gold}}\cap Z_{\mathrm{pred}}|}
{\max(1,|Z_{\mathrm{pred}}|)}
~~~

两者的平衡可用 F1 或任务特定效用表示，但 F1 不应掩盖某个关键证据缺失。一个
需要三条证据的任务，找中两条可能仍不能支持最终结论。

### 13.11.2 答案准确率和语义等价

答案准确率适合有明确答案的任务：

~~~math
A_{\mathrm{answer}}
=\frac{1}{N}\sum_{i=1}^{N}
\mathbf{1}[\hat y_i\equiv y_i]
~~~

这里使用语义等价符号，而不是简单字符串相等。数据库查询、数学表达式和结构化
字段都可能有多个等价答案，判定器必须先规范化、执行或交给专家复核。

### 13.11.3 引用支持率

开放分析经常包含多个原子主张。可以把每个主张和其引用交给规则或专家检查：

~~~math
S_{\mathrm{support}}
=\frac{N_{\mathrm{claims\ supported}}}
{\max(1,N_{\mathrm{atomic\ claims}})}
~~~

每个主张都应保存证据 ID、来源版本和时间范围。一个引用只支持句子中的第一个
主张，却被放在整句末尾，不能计作整句全部有据。

### 13.11.4 证据不足时的正确保留

在研究、医疗、法律和财务场景中，证据缺失也可以是合法输出。模型回答“现有材
料能确认发布发生，但不能确认它是错误率上升的唯一原因”，可能比强行给出单一
因果解释更可靠。

因此要区分：

- 正确保留：知道哪些结论能确认、哪些不能确认；
- 无依据拒答：明明有证据却没有完成任务；
- 过度自信：证据不足仍给出确定结论；
- 形式拒答：拒绝了任务却没有说明缺少哪类证据。

abstention accuracy 需要同时有可回答和不可回答样本，不能只在缺证据问题上计
算拒答率。

### 13.11.5 单位成功任务成本

设一次评估批次的 prefill、decode、工具和重试总成本分别为 C_p、C_d、C_tool、
C_retry，成功任务数为 N_success，则：

~~~math
C_{\mathrm{success}}
=\frac{C_p+C_d+C_{\mathrm{tool}}+C_{\mathrm{retry}}}
{\max(1,N_{\mathrm{success}})}
~~~

如果模型通过十倍的思考 token 和多次重试只提升几个百分点，单位成功成本可能反
而变差。成本、答案正确、引用支持、P95/P99 和安全风险必须一起报告。

当 N_success=0 时，式中的 `max(1, N_success)` 只是为了让教学程序不发生除零，
不能把得到的批次总成本解释为“单位成功成本”。生产报告应把单位成功成本记为
未定义或无成功任务，并单独报告失败尝试、重试次数和总成本。

## 13.12 一个可复现的分层长上下文诊断实验

现在设计一个比 needle 更接近工作的实验。准备三份互相依赖的实验报告：

- 报告 A 放在上下文前 5%，描述一个配置变更；
- 报告 B 放在约 52%，描述该变更后的中间指标；
- 报告 C 放在约 94%，描述线上错误率和回滚结果。

再加入四份旧版本报告，它们包含相同的服务名和相似的数字。问题要求模型输出
变更 ID、三条证据引用、因果解释以及冲突说明。每个字段都可以单独检查。

如果模型只引用 A 和 C，说明中间位置或跨段连接有问题；如果三条引用都来自同一
份报告，说明模型倾向于局部摘要；如果它选中了旧版本报告，说明时间或实体过滤
失败；如果文字结论正确但引用段落不支持，说明 attribution 失败。

假设一次测试得到以下结果：

| 上下文桶 | 输入完整率 | 证据召回率 | 答案准确率 | 引用支持率 | P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 32K | 1.00 | 0.94 | 0.88 | 0.91 | 4.2 s |
| 256K | 1.00 | 0.82 | 0.71 | 0.68 | 11.8 s |
| 1M | 1.00 | 0.55 | 0.39 | 0.31 | 48.0 s |

这个表不应该被概括成“模型支持 1M 但效果不好”。更有用的判断是：入口和输
入完整性没有问题，证据召回在长长度下降，引用支持率又比答案准确率下降得更多，
同时尾延迟显著增加。下一步应检查位置训练、检索策略、干扰设计、引用解析和服
务预算，而不是笼统地增加最大长度。

### 13.12.1 如何解读这组结果

第一，三个长度桶的输入完整率都是 1.00，说明样本确实抵达了模型，至少在当前
记录范围内没有发生静默截断。它不能证明 tokenizer、模板和服务端完全没有问题，
但可以把“输入根本没送到模型”从首要怀疑列表中移开。

第二，证据召回从 0.94 降到 0.55，说明长输入增加后，模型找到金标准证据的能力
明显下降。由于三个长度桶的任务材料、问题和生成预算应保持可比，优先检查的位
置包括中间证据、文档拼接方式和长上下文训练分布。

第三，引用支持率从 0.91 降到 0.31，下降幅度比答案准确率更大。这意味着部分
“答案正确”可能来自语言先验、局部线索或偶然猜中，不能把答案准确率当作证据
可靠性的替代指标。

第四，1M 桶的 P95 为 48.0 s，是 32K 桶的十倍以上。若产品 SLO 是 P95 小于
20 s，那么即使质量目标勉强达到，1M 也不能进入交互式默认路由。它可以被保留
为异步研究任务，或者先用检索和摘要缩小输入。

好的实验结果应该能导向下一轮实验，而不是在报告结尾停止。这个案例至少导出
三条行动：质量问题查模型/数据/证据路径，引用问题查 attribution 协议，延迟
问题查路由和容量。

## 13.13 长上下文与 RAG 的组合

窗口变大不会自动取消 RAG。RAG 的作用不只是把材料塞进上下文，还包括更新索引、
权限过滤、实体检索、引用定位和成本控制。企业知识库每天更新，如果每次问答都
把一百万 token 全部送入模型，模型仍可能使用旧文档，也会付出稳定的 prefill
成本。

实际系统常把两条路径组合起来：检索器先选出与问题相关的文档并保留出处；长上下
文模型再读取这些文档之间的关系；最终回答带有可验证引用。需要全文审计、文档
之间有大量隐含联系的任务，可以提高长上下文预算；重复问答、权限敏感或数据更
新频繁的任务，RAG 通常更经济。

### 13.13.1 四条路径的选择

| 请求 | 首选路径 | 原因 |
| --- | --- | --- |
| 查询今天的值班表 | RAG | 信息小、更新快、权限敏感 |
| 比较五个版本的完整协议差异 | 长上下文 | 需要保持文档整体结构 |
| 从数十万条日志中定位异常 | 检索 + 聚合 + 长上下文 | 先降低噪声，再组合证据 |
| 生成将要发送给客户的事故报告 | RAG/长上下文 + 人工审核 | 输出带有外部责任和引用风险 |

这里的长上下文不是 RAG 的替代品。检索器可以负责权限过滤、时间新鲜度和候选
缩小；长上下文模型负责读取保留下来的完整章节、比较多个证据和生成跨段解释。
相反，若检索器把关键例外条件过滤掉，再大的窗口也无法恢复丢失的信息。

路由还要考虑证据更新频率和重复查询。如果同一份固定政策被数千个请求反复使用，
prefix cache 可能降低重复 prefill 成本；如果每个用户上传的材料都不同，缓存命
中率就很低。若文档包含个人或薪酬信息，则不能因为“可以放进一个大窗口”就取消
权限过滤。长上下文扩大的是可读范围，不是访问权限。

## 13.14 生产服务的长请求路径

线上长请求一般要经过输入计数、预算检查、路由、prefill、decode、输出验证和取
消清理。服务端可以使用 chunked prefill、context parallelism、prefix cache、
KV 压缩或专门的低并发队列，但每项优化都有边界。

例如 prefix cache 对共享 system prompt 和固定文档前缀很有帮助，但用户每次上
传的材料都不同，命中率可能很低。chunked prefill 可以让短请求插队，缓解队头阻
塞，却会增加调度复杂度。context parallelism 能把长输入分到多个设备，代价是
通信和同步。KV 量化减少显存，必须用长上下文任务确认引用质量没有不可接受的
下降。

一个稳妥的服务设计通常会把短问答、普通文档问答和超长研究任务分到不同资源池。
超预算时可以先做检索或摘要，遇到高风险结论再请求人工复核；不能让系统在没有
预算和验证的情况下无限重试。

### 13.14.1 调度中的隔离与降级

如果所有请求共享一个队列，单个百万 token 请求可能在 prefill 阶段占用大量计算
时间，导致只需要几百 token 的请求等待。一个实用策略是按输入长度和任务风险分
桶：短请求进入低延迟池，普通文档问答进入共享池，超长研究任务进入受控异步池。

可以用一个刻意简化的 M/G/1 先来先服务队列看清“长请求比例不大，也可能抬高其
他请求等待时间”的原因。假设到达服从速率为 λ 的 Poisson 过程、只有一个服务
台、服务时间独立同分布，且系统稳定；Pollaczek–Khinchine 公式给出平均排队时间：

~~~math
u=\lambda E[S]<1,\qquad
E[W_q]=\frac{\lambda E[S^2]}{2(1-u)}
~~~

这里影响排队的不只是平均服务时间 E[S]，还有第二矩 E[S²]。举例：每秒到达 2
个请求，98% 的服务时间为 0.1 秒，2% 为 10 秒，则 `E[S]=0.298 s`、利用率
`u=0.596`、`E[S²]=2.0098 s²`，平均排队时间约为 `4.97 s`。若同样每秒 2 个
请求全部只服务 0.1 秒，则 `u=0.2`，平均排队时间约为 `0.0125 s`。少量长服
务时间通过增大 `E[S²]` 显著抬高平均等待；这正是混合长短请求会伤害短请求的
一个机制解释，而不是简单的“长请求占了 2% 队列”。公式假设与推导可见
[Stanford 的 M/G/1 讲义](https://web.stanford.edu/class/ee384x/EE384X/handouts/H10.pdf)。

这个例子是单服务台 FCFS 理论，不是 GPU 连续批处理的精确预测。实际 serving 会
因 chunked prefill、continuous batching、请求抢占、prefill/decode 分离、并行
拓扑和 kernel 而改变服务时间分布；所以它只能说明方差/长尾为何重要，不能拿
`4.97 s` 作为线上延迟预测。目标系统仍需按长度桶测 queue wait、TTFT 和 P95/P99。

降级顺序也应有明确语义：

1. 先检查输入预算和权限，拒绝无法安全处理的请求；
2. 对低风险任务优先改走检索或分段摘要；
3. 对必须全文审计的任务转入异步队列，并返回可追踪任务 ID；
4. 对高风险结论保留人工复核，不用自动重试掩盖证据缺失；
5. 任何降级都记录原始请求、实际处理路径和丢弃的信息范围。

如果摘要被当成原文替代品，模型可能只看到摘要作者保留的观点。因此降级后的输
出要标记证据层级：哪些结论来自原始文档，哪些来自中间摘要，哪些尚未验证。

## 13.15 失败时先判断是哪一层

长上下文失败并不只有一种表现：

| 现象 | 优先检查 | 不应直接下的结论 |
| --- | --- | --- |
| 输入 token 数不一致 | tokenizer、SDK、网关、静默截断 | 模型不会长上下文 |
| 所有位置都下降 | 模板、训练分布、证据标注 | 只需要改位置编码 |
| 中间位置明显低 | 位置机制、curriculum、attention 路径 | 模型没有知识 |
| 答案对但引用错 | attribution 解析、主张拆分 | 模型理解正确 |
| 质量尚可但 P99 爆炸 | serving、容量、队列、KV | 模型能力不足 |
| 旧版本被频繁引用 | 时间、实体、权限过滤 | 需要更大窗口 |

这种分层诊断比“再换一个更大的模型”更有效。长上下文系统的瓶颈可能在模型之
外：错误的 chat template、把文档顺序打乱的拼接器、没有保留来源 ID 的 chunker，
都能让一个本来具备能力的模型看起来像不会读长文档。

### 13.15.1 一个具体的排查过程

假设线上出现“1M 请求偶尔引用不存在的版本”的事故，可以按下面顺序推进。

第一步，抽取同一请求的四个长度：用户上传 token、模板展开后的 token、网关转发
token、runtime 接收 token。若四者不同，先修输入记录和截断策略，不要开始调模型。

第二步，固定模型 revision、temperature、max output tokens 和文档顺序，离线重
放同一 trace。如果离线成功、线上失败，优先比较 chat template、并发、取消、KV
复用和工具返回；如果离线也失败，才继续分析模型和评测。

第三步，把错误样本分成“找错文档”“找到文档但版本错”“结论正确但引用错”“引
用正确但因果关系过强”四类。四类错误对应的修复完全不同：版本错需要元数据过滤，
引用错需要 attribution 解析，因果过强需要任务提示和验证器，找错文档才可能需
要检索或模型能力变化。

第四步，对证据位置做轮换实验。将同一段证据放在开头、中间和末尾，其他 token
保持不变；如果只有中间位置失败，就不能把问题归咎于知识缺失。再增加一个“删
除关键证据”的对照，检查模型是否会在缺证据时仍然输出确定结论。

第五步，最后才做资源实验。固定质量任务，分别测不同并发、KV 精度、chunked
prefill 和批大小；每次只改一个变量，并记录 p50、p95、p99、峰值显存、取消清
理和成功任务成本。否则质量和性能一起变化，无法判断修复是否有效。

这一过程的核心是保留 trace，而不是只保存最终答案。没有原始输入版本、证据 ID、
服务参数和停止原因，线上事故就无法可靠复现。

## 13.16 如何对外陈述 1M 能力

### 13.16.1 一条可辩护的结论

对外描述某模型的 1M 能力时，可以沿着下面的顺序写：

1. 模型 ID、revision、tokenizer、模板和日期；
2. 产品接口允许的最大输入与输出预算；
3. 实际 runtime 接收的 token 和截断策略；
4. 测试任务、证据布局、干扰、版本冲突和引用要求；
5. 模型、工具、硬件、并发、KV dtype 和预算；
6. evidence recall、answer accuracy、citation support、P95/P99、OOM 和成本；
7. 未测试任务、未知项和回退路径。

例如，严谨的句子是：

> 在模型 X 的 revision Y、固定模板和四卡运行配置下，研究日志多证据归因任务
> 在 256K 输入桶中达到某个证据召回率和引用支持率，P95 满足给定 SLO；1M 桶
> 的输入完整性成立，但引用支持率和单位成功成本尚未达到同样标准，因此当前只
> 将 1M 作为异步实验路径。

这句话比“模型支持 1M”长，却能被复现、反驳和改进。

### 13.16.2 五级证据口径

| 级别 | 能说什么 | 不能顺推什么 |
| --- | --- | --- |
| 接口声明 | 产品或模型卡允许某个最大输入 | 模型会使用所有输入 |
| 运行完成 | 某配置能完成 forward 或返回结果 | 多请求并发和质量稳定 |
| 训练说明 | 训练或继续训练覆盖相近长度 | 真实任务一定泛化 |
| 任务评测 | 指定任务族、证据布局和预算下的曲线 | 所有任务都同样有效 |
| 生产证据 | 真实流量中满足质量、风险和 SLO | 永久不退化或无未知风险 |

模型卡和官方产品文档对接口声明具有最高相关性；论文对方法和受控实验具有较
强证据；社区博客和截图适合提供线索，不应支撑确定性能力结论。

### 13.16.3 如何阅读 no-RoPE 或超长声明

如果某模型声称不使用 RoPE、采用递归状态、支持百万级上下文或具有特殊 cache，
不要先讨论宣传是否“颠覆”。先记录：

- 声明的原始来源和版本；
- 位置或状态信息的计算路径；
- 训练长度和长任务数据；
- 实际可接收的输入、输出和工具预算；
- 证据位置、干扰、引用和冲突测试；
- 状态显存、并发、延迟和错误恢复。

新架构可能带来真实的复杂度或外推改进，但它仍然需要通过任务级和生产级证据
来定义能力边界。架构标签是解释变量，不是最终结论。

## 13.17 最小可运行的 1M 诊断 Demo

下面的程序使用三个长度桶重现前面的诊断思路。它不模拟真正的模型，只把已记录
的评测结果分解成可解释信号，再给出行动和决策。真正的长上下文评估还需要从
runtime trace、证据标注和独立判定器读取数据。

~~~python
buckets = [
    {
        "length": "32K",
        "ingest": 1.00,
        "evidence_recall": 0.94,
        "answer": 0.88,
        "citation": 0.91,
        "p95": 4.2,
        "cost": 1.0,
    },
    {
        "length": "256K",
        "ingest": 1.00,
        "evidence_recall": 0.82,
        "answer": 0.71,
        "citation": 0.68,
        "p95": 11.8,
        "cost": 2.8,
    },
    {
        "length": "1M",
        "ingest": 1.00,
        "evidence_recall": 0.55,
        "answer": 0.39,
        "citation": 0.31,
        "p95": 48.0,
        "cost": 9.6,
    },
]

signals = {
    "ingest_unstable": any(bucket["ingest"] < 0.99 for bucket in buckets),
    "evidence_degrades": (
        buckets[-1]["evidence_recall"]
        < buckets[0]["evidence_recall"] - 0.20
    ),
    "answer_degrades": buckets[-1]["answer"] < buckets[0]["answer"] - 0.20,
    "citation_degrades": (
        buckets[-1]["citation"] < buckets[0]["citation"] - 0.20
    ),
    "interactive_slo_miss": buckets[-1]["p95"] > 20.0,
    "cost_budget_miss": buckets[-1]["cost"] > 4.0,
}

actions = []
if signals["ingest_unstable"]:
    actions.append("核对 tokenizer、网关与 runtime token trace，修复输入链路后重跑")
else:
    if signals["evidence_degrades"]:
        actions.append("检查位置覆盖、长上下文训练数据与证据布局")
    if signals["answer_degrades"]:
        actions.append("按任务切片复核答案判定与多证据组合")
    if signals["citation_degrades"]:
        actions.append("逐原子主张复核 citation attribution")
if signals["interactive_slo_miss"]:
    actions.append("把超长任务转入异步池并复核容量")
if signals["cost_budget_miss"]:
    actions.append("评估 RAG、摘要、缓存和状态压缩的单位成功成本")

if signals["ingest_unstable"]:
    decision = "repair_ingest_then_rerun"
elif signals["interactive_slo_miss"] or signals["cost_budget_miss"]:
    decision = "route_long_tasks_to_async"
elif (
    signals["evidence_degrades"]
    or signals["answer_degrades"]
    or signals["citation_degrades"]
):
    decision = "rework_evidence_path"
else:
    decision = "continue_task_specific_validation"

print("signals=", signals, sep="")
print("actions=", actions, sep="")
print("decision=", decision, sep="")
~~~

预期输出为：

~~~text
signals={'ingest_unstable': False, 'evidence_degrades': True, 'answer_degrades': True, 'citation_degrades': True, 'interactive_slo_miss': True, 'cost_budget_miss': True}
actions=['检查位置覆盖、长上下文训练数据与证据布局', '按任务切片复核答案判定与多证据组合', '逐原子主张复核 citation attribution', '把超长任务转入异步池并复核容量', '评估 RAG、摘要、缓存和状态压缩的单位成功成本']
decision=route_long_tasks_to_async
~~~

这个 demo 的价值是展示诊断路径，而不是自动替工程师做发布决定。输入不稳定时，
先修复计数或截断链路，暂停对模型检索和推理质量的归因；输入稳定后，证据召回、
答案和引用支持分别触发独立调查。P95 和成本超出预算时，路由建议可以转异步，
但不会消除质量问题。这里的决策只选“首要运行路径”，不能理解为发布已通过。
样例以 32K 和 1M 的首末桶差值触发诊断，没有计算中间桶趋势、抽样不确定性、
成对显著性或任务切片，因此 `0.20`、`0.99`、20 秒和 4.0 都只是教学阈值，
不是统计结论或生产发布门槛。

## 13.18 练习

1. 设 L=32、H_kv=8、d_h=128，分别用 BF16 估算 128K、512K 和 1M token
   的单请求 KV cache。再写出为什么真实值可能更大。
2. 设计一个包含开头、中间、末尾证据，带旧版本干扰和冲突日志的测试集。为每道
   题定义金标准证据和原子主张。
3. 解释为什么模型在 needle 测试上得分 1.0，仍可能在跨段冲突诊断上失败。
4. 为研究助手设计 direct、RAG、long-context 和 human-review 四条路由，并为每
   条路由写出触发条件、最大成本和失败后的回退。
5. 如果 1M 请求的 KV cache 估算超过单卡显存，列出三种架构或系统层的解决路径，
   并说明每种路径可能损失什么。

### 13.18.1 练习方向

第 1 题的关键不是只算出三个数字，而是说明 KV 随 T 线性增长，并区分 GiB、GB、
权重显存、workspace 和并发余量。若只把结果写成“1M 需要约 122G”，却没有说明
假设条件，这个答案在工程评审中是不完整的。

第 2 题应给每条证据分配稳定 ID，并同时标注证据角色、版本和时间。测试集至少
有一个开头证据、一个中间证据、一个末尾证据和一个相似旧版本干扰。答案评价要
分别检查 evidence recall、answer accuracy 和 citation support。

第 3 题可以从任务复杂度回答：needle 只需要局部字符串定位，冲突诊断还要求
实体消歧、时间排序、多个证据合取和不确定性表达。两个任务的输入长度相同，
不代表能力相同。

第 4 题的路由条件应包含数据新鲜度、权限、文档整体性、延迟和成本。不要把四条
路由写成模型大小的四个等级，它们是不同的系统路径。

第 5 题可以选择模型并行、KV 量化、压缩或递归状态、分块与检索、异步低并发池等
方案。每个方案都要写出可能损失：精度、远距离信息、延迟、实现复杂度、权限可
追溯性或召回率。

## 13.19 版本比较与证据报告

“有效长度”通常需要比较两个模型、两个位置方案或两个服务配置。比较时不能只
把每个版本分别跑一遍，再拿两个总体平均数相减。若 tokenizer、模板、证据顺序、
输出预算或判定器同时变化，差异可能来自实验条件，而不是模型能力。

### 13.19.1 先固定比较对象

一个有解释力的版本比较至少要固定：

1. 相同的输入文档、问题和证据标注；
2. 相同的 tokenizer 或明确记录 token 数差异；
3. 相同的 system prompt、模板和工具权限；
4. 相同的输出预算、采样策略和重试规则；
5. 相同的硬件、并发和队列策略；
6. 相同的程序判定器、rubric 和 judge 版本；
7. 相同的观察窗口和成本计量口径。

如果要比较不同 tokenizer 的模型，不能强行让字符长度相同就宣布输入规模相同。
应同时报告字符数、字节数、各自 token 数和实际 runtime 长度。

### 13.19.2 用向量而不是一个差值描述变化

对长度桶 T，可以把结果写成质量向量：

~~~math
Q(T)=
\bigl(
R_{\mathrm{evidence}},
A_{\mathrm{answer}},
S_{\mathrm{support}},
\mathrm{P95},
C_{\mathrm{success}}
\bigr)
~~~

两个版本的变化是：

~~~math
\Delta Q(T)=Q_{\mathrm{new}}(T)-Q_{\mathrm{old}}(T)
~~~

但这里的减法要按分量分别解释。证据召回提升而引用支持下降，不能用一个加权
平均掩盖矛盾；P95 的单位是时间，成本可能是金额或 GPU 秒，也不应直接和质量
分数相加，除非权重和效用函数有明确业务含义。

### 13.19.3 一个版本比较示例

固定同一批研究日志、证据标注和输出预算后，得到：

| 长度 | 版本 | 证据召回 | 答案准确 | 引用支持 | P95 | 单位成本 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 256K | A | 0.80 | 0.69 | 0.73 | 10.4 s | 2.5 |
| 256K | B | 0.84 | 0.72 | 0.75 | 11.1 s | 2.9 |
| 1M | A | 0.52 | 0.37 | 0.29 | 44.0 s | 9.1 |
| 1M | B | 0.61 | 0.43 | 0.38 | 47.0 s | 10.8 |

B 在两个长度桶的质量分量都有提升，但 1M 的 P95 和成本仍然可能不满足交互
预算。更准确的结论是“B 在这个任务族和固定 harness 下改善了有效使用曲线”，
而不是“B 已经解决了百万 token 生产问题”。

### 13.19.4 差异需要不确定性

如果同一道题同时由 A 和 B 生成回答，结果通常是配对数据。可以统计旧版正确、
新版错误的数量 b，以及旧版错误、新版正确的数量 c：

~~~math
\Delta_{\mathrm{paired}}=\frac{c-b}{n}
~~~

对证据支持率、答案正确率和引用正确率，可以按任务、证据布局和长度桶做配对
bootstrap 或其他与分析单位匹配的方法。对 P95 和成本，则需要说明 bootstrap
单位、长尾处理、重试和失败请求是否进入分母。

一个版本在 1M 桶提升 2 个百分点，如果样本只有几十条，不能和 256K 桶提升 2
个百分点拥有相同可信度。报告应写样本数、有效分母、区间和未成熟结果。

### 13.19.5 一条完整的报告句子

一条可复核的结果可以写成：

> 在相同 tokenizer、模板、证据布局、输出预算和评估器下，版本 B 相比版本 A
> 在研究日志多证据归因任务的 256K 和 1M 桶分别提高证据召回与引用支持；1M
> 桶的 P95 和单位成功成本仍高于交互式预算，因此后续动作是验证证据路径并将
> 超长请求保留在受控异步路由。

这句话同时交代了比较条件、提升发生在哪里、工程边界和下一步动作。它比单独写
“B 的长上下文更强”更能承受复核。

## 13.20 资料与证据边界

下面的入口按论文、官方工程资料和评测数据分组。论文支持方法在论文实验条件
下的结论，不能自动支持某个闭源或新发布模型的生产能力；官方模型卡支持对应
版本的配置声明，不能替代独立任务评测；社区实现适合帮助理解接口和 kernel，
必须结合具体 revision 和 workload 复现。

### 13.20.1 位置机制与长上下文扩展

- [RoFormer / Rotary Position Embedding](https://arxiv.org/abs/2104.09864)：理解旋转位置表示和相对位置信息的基础。
- [ALiBi: Train Short, Test Long](https://arxiv.org/abs/2108.12409)：通过 attention bias 探索训练短、测试长；与 RoPE 插值是不同位置路线。
- [Position Interpolation](https://arxiv.org/abs/2306.15595)：把超长位置映射回训练位置范围，并在 LLaMA 上做低步数扩展实验。
- [YaRN](https://arxiv.org/abs/2309.00071)：按 RoPE 波长区分插值程度并增加 attention scaling；训练效率数字绑定作者的模型和实验对照。
- [LongRoPE](https://arxiv.org/abs/2402.13753)：非均匀位置搜索、渐进式 256K→2,048K 扩展和短上下文恢复，结果绑定 LLaMA 2/Mistral 配置。
- [Longformer](https://arxiv.org/abs/2004.05150) 与 [BigBird](https://arxiv.org/abs/2007.14062)：局部/全局/随机稀疏连接的代表设计；重点是改变 token 交互图，不是 RoPE 外推。
- [Ring Attention](https://arxiv.org/abs/2310.01889)：把 blockwise attention 分布到多设备并重叠通信与计算；解决设备容量和并行问题。
- [FlashAttention](https://arxiv.org/abs/2205.14135) 与 [PagedAttention](https://arxiv.org/abs/2309.06180)：分别从 HBM 数据移动和 KV cache block 管理改善工程执行。

这些来源分别支持位置表示、位置扩展、稀疏交互、分布式计算和缓存管理的机制
解释。它们不能证明“只要采用某个方法，所有任务都能在百万 token 上保持质量”；
具体差异和论文边界见 §13.6.6。

### 13.20.2 长上下文评测

- [Lost in the Middle](https://arxiv.org/abs/2307.03172)：控制证据位置，识别中间位置退化。
- [LongBench v1](https://arxiv.org/abs/2308.14508) 与 [LongBench v2](https://arxiv.org/abs/2412.15204)：分别提供中英文多任务覆盖，以及高难长文理解/推理题；v2 的长度用 words 报告。
- [RULER](https://arxiv.org/abs/2404.06654)：可配长度、needle 数、multi-hop tracing 与 aggregation 的合成任务套件。
- [NoLiMa](https://arxiv.org/abs/2502.05167)：降低问题和证据的词面重叠，检查依赖潜在关联的检索。
- [LongBench Pro](https://arxiv.org/abs/2601.02872)：中英文自然长文本、多任务、token 长度分桶；截至 2026-10-27 公开的是 2026 年 1 月作者预印本，最大 256K tokens。
- [Google DeepMind MRCR v2 数据与评测代码](https://github.com/google-deepmind/eval_hub/tree/master/eval_hub/mrcr_v2)：多轮共指和多 needle 的固定复杂度曲线；仓库文档截至本轮检索称可扩展至 8M，使用时要记录数据与代码 revision。
- [OpenAI MRCR 与 Graphwalks 发布说明](https://openai.com/index/gpt-4-1/)：厂商公开的多轮共指检索与结构化多跳任务入口。发布方结果用于理解任务设计，不作为独立复核。

VQA、DocVQA、ChartQA 和 AgentBench 适合评估多模态/Agent 相邻任务，不是文本
1M context benchmark。needle 冒烟、位置探针、合成复杂度、自然任务集、供应方自
建评测和目标业务集各自回答不同问题，不能平均为单一长上下文总分；方法差异与
长度单位见 §13.9.2。

### 13.20.3 资源与推理系统

FlashAttention 和 PagedAttention 主要支持计算和状态管理的工程解释。它们不能直

明显不同。

### 13.20.4 模型声明的使用方式

某个模型或产品页面声称 1M、2M 或更大窗口时，记录页应至少保留：

- 原始 URL；
- 模型或产品版本；
- 抓取日期；
- 输入与输出预算；
- 是否说明 tokenizer、模板和 runtime；
- 是否提供任务评测和硬件条件；
- 是否只有单请求结果。

官方页面可以证明“发布方作出了该接口或配置声明”。只有在任务、证据、成本和
生产 trace 也被独立记录后，书稿才可以把它进一步描述成某类任务的有效能力。

### 13.20.5 一个公开 1M 模型条目的阅读示例

Qwen2.5-1M 系列可以作为阅读模型声明的练习入口：

- 技术报告：
  https://arxiv.org/abs/2502.13923
- 官方模型条目：
  https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-1M

这两个入口可以支持“该系列公开讨论了百万级上下文模型和对应配置”这一层事实
记录。读者若要把它写成“在自己的研究助手上有效使用 1M”，仍需补充自己的
tokenizer、模板、硬件、证据布局、判定器、并发、P95 和单位成功成本。论文中的
长文档测试、模型卡中的最大长度和产品 API 的实际限制，可能属于不同实验条件，
不能不加区分地合并。

对于其他模型或社区转述的 no-RoPE、百万级窗口和特殊 state 声明，也应采用相同
方法：先保存原始版本和来源，再把接口事实、方法事实、任务结果和生产结果分开。

## 13.21 本章小结

1M context 首先说明系统愿意接收很长的输入，不能直接说明模型已经学会使用其中
的全部信息。有效能力至少要拆成输入完整性、证据检索、跨段组合、引用归因、干
扰鲁棒性和生产成本。

位置机制、长上下文训练、KV/state 表示、prefill 调度、RAG 和评测协议共同决定
最终结果。RoPE scaling、position interpolation、稀疏或混合 attention、context
parallelism 和状态压缩分别解决不同瓶颈，也分别带来精度、通信、实现和成本取舍。

严谨的结论不是“模型支持 1M”，而是：

> 在某个模型版本、任务类型、证据布局、工具和预算下，成功率曲线延伸到某个长
> 度，并且质量、风险、延迟和单位成功成本满足明确条件。

这句话更长，却是真正可复现、可用于工程决策和后续研究的结论。
