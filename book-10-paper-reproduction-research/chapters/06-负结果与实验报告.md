# 第六章：负结果与实验报告

一个训练实验没有超过 baseline，一个长上下文系统在中间位置丢失证据，一次安全微调让正常请求被更多拒绝，一次离线提升在线上消失。这些结果都不符合“新方法应该变好”的直觉，却比一张漂亮的平均分表更能说明系统的真实边界。

负结果不是一句“失败了”就能概括的状态。它可能表示假设被反驳，也可能表示实验没有足够能力发现一个小效应；可能是实现有 bug，也可能是方法有效但成本不允许；可能是平均数没有变化，却在一个高风险切片上出现了重要改善。把这些情况混在一起，会让团队错误地停止有价值的方向，也会让团队在坏实验上继续浪费算力。

成熟的研究工作要完成三次转换：把异常转换成准确的结果类型，把结果转换成可排查的证据链，再把证据链转换成继续、停止、缩小范围或改变假设的决定。实验报告的作用，就是让这三次转换能够被别人复查，而不是替作者把一个分数重新排版。

## 1. 负结果究竟是什么

### 1.1 “没有提升”不是唯一的负结果

最常见的一类是主指标没有超过 baseline，但实际项目中更值得记录的还有：

1. **目标效应没有出现**：方法在预先指定的主指标上与 baseline 接近，差异区间也没有覆盖实用阈值。
2. **方向反转**：整体指标下降，或者方法在小模型有效、在目标规模无效。
3. **局部提升伴随退化**：数学准确率上升，但代码、对话或多语言能力下降。
4. **稳定性失败**：平均值略高，但不同 seed、任务或时间切片的方向不一致。
5. **测量失败**：评估脚本、judge、后处理或数据分母错误，使结果无法解释。
6. **机制失败**：中间变量没有按假设改变，最终分数的偶然提升没有机制支持。
7. **资源失败**：质量有所改善，但延迟、显存、token 成本或调用次数超出约束。
8. **生产失败**：离线测试有效，上线后受流量、路由、缓存、用户分布或工具状态影响而失效。
9. **安全副作用**：危险输出下降，同时正常请求误拒、越权或隐私暴露上升。
10. **证据不足**：结果波动很大、样本太少或关键 artifact 缺失，当前无法判断方向。

前四类更接近研究结论，后六类可能是测量、机制、工程或证据问题。报告不能只写一个 `failed=true`，因为这个布尔值无法告诉下一位研究者应该修代码、补样本、改变方法还是停止投入。

### 1.2 初学者视角：负结果像一道没有通过的体检

可以把一次实验看成一次体检。体检报告显示某项指标异常，并不等于立刻知道病因。可能是测量仪器不准、抽血前条件不一致、样本处理出错，也可能确实发现了需要处理的问题。研究实验同样如此：分数下降先是一个观察，只有完成校验和归因后，才可能成为关于方法的结论。

比如一个合成 reasoning 数据版本让数学准确率从 41.0 降到 40.6。此时至少有四种解释：题目本身有错误，数据与评估集近重复导致选择偏差，训练实现改变了 label shift，或者合成数据确实让模型学到了模板化而非可迁移的推理。若只记下“合成数据无效”，就把四个不同问题压成了一个不可行动的标签。

### 1.3 专家视角：先确定 estimand 和失败标准

负结果只有在 estimand 清楚时才有研究意义。下面几种说法看起来都叫“没有效果”，但对应的估计对象不同：

| 观察 | 实际要问的问题 | 可能结论 |
| --- | --- | --- |
| 平均分差异接近 0 | 测试集上的平均质量是否改变 | 当前分布下未观察到平均效应 |
| 置信区间很宽 | 设计能否分辨关心的最小效应 | 证据不足，不能判定无效 |
| 主指标上升、护栏下降 | 是否满足多目标约束 | 有质量收益但当前方案不可用 |
| 中间指标未变、最终分数上升 | 机制假设是否得到支持 | 可能是偶然或其他路径产生提升 |
| 线上指标下降、离线不变 | 离线评估能否代表生产分布 | 外推失败或系统协议不一致 |

在实验开始前写出最小实际有意义差异 $\delta$、可接受成本 $C_{max}$、不能越过的风险 $R_{max}$ 和最少证据条件，后续才有明确的停止和继续标准。否则，研究者会在结果出来后临时改变“成功”的定义。

## 2. 先区分有效负结果和坏实验

### 2.1 有效负结果需要满足什么

一个可解释的负结果至少具备四个条件：

1. **问题明确**：实验针对一条具体主张，而不是漫无目的地尝试。
2. **比较可比**：baseline、处理变量、数据、预算和评估协议被记录并且足够公平。
3. **测量可信**：指标、分母、后处理和日志没有已知错误，结果能够重复观察或给出不确定性。
4. **结论有限**：只把结果外推到实际覆盖的模型、数据、任务和资源范围。

例如，在固定模型、数据、训练 token 和测试集的条件下，三个 seed 都没有观察到 DPO 相对 SFT 达到 1 个百分点的提升，配对区间覆盖 `-0.2` 到 `0.4` 个百分点，且 preference 数据和评估脚本已经复核。这可以支持“在当前设置下没有达到预设实用效应”；它不能支持“DPO 在任何任务都无效”。

### 2.2 坏实验会制造假负结果

下列情况更像实验故障，而不是方法负结果：

1. baseline 使用了错误的 tokenizer 或 chat template。
2. candidate 的 label shift、padding mask 或 loss reduction 与 baseline 不一致。
3. 数据过滤器误删了目标领域，或者训练集与测试集版本不对应。
4. 评估脚本把拒答、超时和解析失败从分母中删除。
5. checkpoint 没有加载，模型实际使用了随机初始化或旧版本权重。
6. candidate 运行时允许重试，baseline 不允许重试。
7. 只跑一个有利或不利的 seed，却把它写成稳定结论。
8. 线上实验的路由、缓存命中率和流量组成与离线条件不同，且报告没有记录。

这些问题必须先修复或明确标记为“证据无效”。把故障结果放在论文或团队知识库中并不是诚实，而是让后续读者误以为它完成了方法比较。

### 2.3 一个逐层有效性检查

可以把实验有效性看成从低到高的证据层：

~~~text
测量可运行
  -> 输入与标签正确
  -> baseline 行为正常
  -> 处理变量确实生效
  -> 训练或推理达到可比较状态
  -> 结果在重复与切片中可解释
  -> 结论覆盖目标 claim
~~~

只完成第一层，不应该讨论方法是否有效；只完成总体平均，也不应该自动讨论稳健性和生产价值。负结果报告需要明确停在哪一层，以及没有完成更高层的原因。

## 3. 用结果状态代替二元成败

### 3.1 五种证据状态

实验结束后，可以把结果归入五种状态：

1. **支持**：主张在预先规定的条件和效应阈值内得到支持，且关键替代解释已有对照。
2. **不支持**：实验有效、统计精度足够，但目标效应没有出现或方向与假设相反。
3. **部分支持**：只在某些切片、规模或资源条件下成立。
4. **证据不足**：区间太宽、重复太少、关键对照缺失或 artifact 不完整。
5. **实验无效**：测量、实现、数据或协议错误使结果不能用于判断主张。

这五种状态不是论文风格的标签，而是下一步行动的入口。`不支持` 通常触发改变假设或停止当前方向；`证据不足` 触发补样本、增加 seed 或修复对照；`实验无效` 触发代码、数据和评估排查；`部分支持` 触发切片路由或重新定义目标范围。

### 3.2 “没有拒绝原假设”不等于“证明没有效果”

设 candidate 与 baseline 的差异为 $\Delta$。如果点估计接近 0，但置信区间很宽，说明实验没有足够精度区分小效应；这不是“方法被证明无效”。只有当区间基本落在预先规定的无实际意义区域，或者等效性检验支持“差异小于阈值”，才可以更有力地说当前方法没有达到实用效应。

例如：

- $\Delta=0.2$ 个百分点，95% 区间为 `[-1.5, 1.9]`：证据不足。
- $\Delta=0.2$ 个百分点，95% 区间为 `[0.0, 0.4]`，而实用阈值是 1.0：未达到实用效应，但不代表精确相同。
- $\Delta=-1.8$ 个百分点，95% 区间为 `[-2.2, -1.4]`：当前条件下有稳定退化。

报告应把点估计、区间、最小实际有意义差异和样本/seed 数放在一起，而不是只写一个显著性符号。

## 4. 负结果如何改变研究判断

### 4.1 负结果缩小的是假设空间

实验前可能有四条假设：

1. 新模块通过改善证据质量提高答案正确率。
2. 新模块通过更保守的输出降低无依据回答率。
3. 新模块只是增加了推理 token，质量收益与机制无关。
4. 评估器偏好新模块的输出格式，实际用户质量没有提升。

如果结果是答案正确率不变、无依据率下降、输出 token 增加、独立人工评估不变，那么第一条并没有得到支持，但第二条和第三条仍然有部分证据，第四条仍需要更多校准。负结果的价值不在于宣布“方向结束”，而在于让下一轮不必重复已经被排除的解释。

### 4.2 用信息价值决定下一步

下一次实验应该优先选择能够区分剩余假设、且成本可接受的设计。可以用一个教学用判断式表示实验的价值：

~~~math

V(e)=\frac{\mathrm{ExpectedInformationGain}(e)}{\mathrm{Cost}(e)}.

~~~

这不是要求研究者精确计算信息论量，而是提醒我们不要因为“还能再跑一次”就重复同一个实验。若一次小规模数据审计可以区分“数据错误”和“方法真的无效”，它往往比直接再训练一个更大的模型更有价值。

### 4.3 三种停止理由必须分开

项目会议中“停止这个方向”可能有三种完全不同的含义：

1. **假设被反驳**：实验有效、精度足够，结果与机制预测冲突。
2. **资源不允许**：质量可能有收益，但成本、延迟或算力不满足当前产品条件。
3. **证据不足**：关键条件缺失，暂时无法判断，但当前周期不值得补齐。

第一种是科学结论，第二种是工程决策，第三种是项目管理决策。把三者都写成“方法失败”，会让未来读者误读资源限制；把第二种写成“方法有效”，又会掩盖无法部署的事实。

## 5. 失败归因：从测量层到系统层

### 5.1 第一层：测量和分母

很多所谓负结果其实是指标问题。先问：评估脚本读到了哪一批输出？答案解析是否正确？拒答、超时、工具错误和格式错误的分母是什么？一个系统通过全部拒答来降低危险输出率，如果只统计“已回答请求中的危险率”，结果就会看起来异常优秀。

对生成评估，至少保留原始输出和状态字段：

~~~text
request_id
answer_status
parse_status
tool_status
reference_available
quality_label
safety_label
latency_ms
input_tokens
output_tokens
~~~

如果只保存最终 `score`，无法知道低分来自错误答案、无法解析、超时还是系统没有回答。指标函数应明确分母。例如答案覆盖率可以写为：

~~~math

Coverage=\frac{N_{answered}}{N_{eligible}}.

~~~

其中 $N_{eligible}$ 是符合任务契约、允许系统尝试回答的请求数；不能因为系统拒答就把它从分母中删除，除非评估目标明确只研究已回答样本。

### 5.2 第二层：数据和分布

数据问题不只意味着标签错误，还包括训练和评估分布不一致、重复、污染、领域比例变化、语言比例变化和时间穿越。一个模型在旧时间切分上表现下降，可能是方法退化，也可能是新测试集包含了训练没有覆盖的业务类型。

排查时应把样本按任务、长度、语言、领域、时间、难度和风险分层。整体差异可以写成：

~~~math

\Delta_{overall}=\sum_{k=1}^{K}w_k\Delta_k,
\qquad \sum_{k=1}^{K}w_k=1.

~~~

$\Delta_k$ 是第 $k$ 个切片的差异，$w_k$ 是目标分布中的权重。如果 candidate 改变了样本覆盖，整体差异可能只是 $w_k$ 变了，而不是每个切片都变好。因此报告同时保留切片分数和目标权重。

### 5.3 第三层：实现和状态

训练失败时，最便宜的检查通常比继续训练更有信息量：

1. 在一个小 batch 上过拟合，确认 loss 能下降。
2. 检查 label shift、attention mask、padding 和 loss reduction。
3. 记录参数梯度范数，确认梯度不是全零、NaN 或被错误裁剪。
4. 比较处理前后的有效参数更新量。
5. 用固定输入检查 tokenizer、template、stop condition 和后处理。
6. 用已知答案的 sanity set 检查评估脚本。
7. 比较 checkpoint 的权重 hash 和加载日志。

例如，一个 process supervision 实验结果下降，若每个步骤的 reward 都是 0，不能马上得出“过程监督有害”；应先检查步骤切分、答案对齐和 verifier 输出是否正确。实现有效性是研究结论的前提，不是结论之外的工程细节。

### 5.4 第四层：优化和训练状态

相同的模型和数据，学习率、warmup、有效 batch、训练步数、weight decay、精度、梯度累积和 checkpoint 选择都可能制造差异。一个辅助 loss 让训练曲线下降更快，但最终分数不变，说明它可能改善优化路径而非最终表示；如果训练还没有收敛，负结果更可能是预算不足。

要区分这些情况，至少保留训练曲线、验证曲线、学习率、梯度/更新范数、吞吐和中间 checkpoint。只保存最后一个分数会丢失“方法是否需要更长训练”这一重要信息。

### 5.5 第五层：随机性和重复

训练 seed、数据顺序、kernel 非确定性、采样路径和工具环境都可能影响结果。一个 candidate 在 seed 1 上比 baseline 高，在 seed 2 和 3 上低，不能只挑 seed 1 讲故事。相反，如果三个 seed 都相近地下降，方向反转的证据更强。

PyTorch 官方随机性说明也提醒，跨版本、平台和硬件并不保证完全复现。因此复盘时应区分：

- 同一环境下的 seed 波动。
- 不同 GPU 或 runtime 的实现差异。
- 生成采样随机性。
- 数据加载顺序和多 worker 行为。

这些差异不一定都要消除，但必须知道它们属于哪个层级。

### 5.6 第六层：评估器和解释器

LLM judge、人工标注、程序化 parser 和线上用户反馈各有失真方式。新方法输出更长，judge 可能更喜欢；新方法使用更严格的拒答策略，人工可能把“谨慎”误判成“无帮助”；新模板改变了格式，exact match 可能下降但语义质量不变。

负结果排查应加入独立评估器、盲评、顺序交换、程序化答案检查和高风险样本复核。若不同评估器方向相反，结论应写成“评估协议敏感”，而不是选择最喜欢的一个评估器。

### 5.7 第七层：工程和生产环境

方法在离线集上变好，上线后却变差，常见原因包括：流量分布不同、缓存命中率不同、并发导致队列变长、工具服务超时、模型路由比例变化、用户输入更长、重试和降级策略不同。离线实验没有失败，不代表端到端系统没有负结果。

生产复盘需要把一次请求拆成 trace：网关、路由、检索、模型、工具、后处理、审核和回写。每个节点都记录输入版本、状态、耗时、token、错误和重试。否则“线上质量下降”只能停在猜测层。

## 6. 一条实际可执行的排查顺序

### 6.1 先复现观察，再解释观察

面对一个坏结果，第一轮目标不是找原因，而是确认观察确实存在：

1. 用同一版本重新运行最小复现。
2. 固定输入、输出协议和评估脚本。
3. 保留原始输出，而不是只重算汇总分。
4. 对比 baseline 和 candidate 的请求数、解析率和失败状态。
5. 记录当前结果与原始结果的差异。

如果最小复现都不能得到同样方向，原实验需要标记为不稳定或无效；这时继续讨论机制没有意义。

### 6.2 再做已知正确的 sanity check

sanity check 的作用不是证明方法有效，而是证明测量链路能识别明显正确和明显错误的情况。例子包括：

- 把标签打乱，指标应明显下降。
- 把正确答案直接作为输出，答案指标应接近上限。
- 把检索证据替换为无关文档，grounding 指标应有变化。
- 把模型权重冻结，训练 loss 不应表现为正常更新。
- 把 temperature 设为 0，重复输出应更稳定。
- 把工具返回设置为固定错误，系统应产生可追踪的失败状态。

sanity check 失败时，先修复评估或实现；sanity check 通过且目标实验仍无效，才进入方法归因。

### 6.3 最后才扩展实验规模

一旦确认负结果是真实的，按成本从低到高扩展：

1. 单样本和小 batch 诊断。
2. 小数据短训练或小模型 proxy。
3. 关键切片和多 seed。
4. 预算匹配的对照和替代方案。
5. 目标规模和完整生产 harness。

每一步都应有一个新问题，而不是“再跑一次看看”。如果连续三轮实验既没有减少剩余解释，也没有改变行动选择，就应暂停这条线，把时间用于更有信息量的实验或方向。

## 7. 负结果中的副作用和多目标取舍

### 7.1 质量向量比单一分数更接近真实系统

一个系统的结果可以表示为向量：

~~~math

\mathbf{y}=(Q,\;S,\;L,\;C,\;F),

~~~

其中 $Q$ 是主质量，$S$ 是安全或证据质量，$L$ 是延迟，$C$ 是成本，$F$ 是失败率。candidate 未必在每个维度都优于 baseline；它可能提升 $Q$，却恶化 $L$ 和 $F$。

因此表格至少同时包括主指标、护栏指标、资源和失败样例：

| 变化 | 主质量 | 副作用 | 资源 | 当前判断 |
| --- | --- | --- | --- | --- |
| 安全数据增加 | 漏拒下降 | 误拒上升 | 训练 token 增加 | 需要边界数据 |
| 代码数据增加 | 代码通过率上升 | 对话风格变窄 | mixture 改变 | 需要通用数据回放 |
| RAG reranker | 引用支持率上升 | P95 延迟上升 | 一次额外模型调用 | 按风险路由 |
| 长上下文 | 跨段召回上升 | 中间位置不稳 | KV 和 prefill 增加 | 先做任务分层 |

### 7.2 护栏是约束，不是随手加权

如果系统必须满足延迟和安全上限，可以写成约束优化：

~~~math

\max_{m\in\mathcal{M}}Q(m)
\quad\mathrm{subject\ to}\quad
L(m)\leq L_{max},\quad
C(m)\leq C_{max},\quad
R(m)\leq R_{max}.

~~~

这比把准确率、延迟和安全随意相加更清楚。一个在约束之外的高分方案，不是当前业务中的“最好方案”，而是需要改变预算、流量路由或风险范围的候选方案。

### 7.3 负结果可以是成功的决策

如果实验发现质量只提高 0.2 个百分点，却让单位成功任务成本增加 3 倍，团队停止默认部署并改为高价值请求触发，这次实验完成了它的工程目标。研究成果不是让每个方法都上线，而是用证据避免错误的默认选择。

## 8. 统计功效不足：不确定性本身也是结果

### 8.1 配对差异和区间

如果 baseline 和 candidate 在同一批请求上运行，令第 $i$ 个请求的差异为：

~~~math

d_i=Y_i^{candidate}-Y_i^{baseline},\qquad
\bar d=\frac{1}{n}\sum_{i=1}^{n}d_i.

~~~

均值差异的标准误可以近似为：

~~~math

SE(\bar d)=\frac{\mathrm{sd}(d_1,\ldots,d_n)}{\sqrt n}.

~~~

如果任务有明显的簇结构，应按用户、领域、时间段或任务簇重采样；如果训练 seed 是主要随机单位，应把 seed 结果单独列出。测试样本很多不等于训练结论一定精确，因为 10,000 个样本可能共享同一个 checkpoint 和同一个 seed。

### 8.2 用最小实际有意义差异解释“没提升”

设团队关心的最小实际有意义提升为 $\delta$。如果区间完全低于 $\delta$，可以说当前方案没有达到目标效应；如果区间同时覆盖 0 和 $\delta$，则证据不足；如果区间完全高于 $\delta$，才更接近支持目标。

这三种情况可以画成一条数轴：

~~~text
退化       无实用效应         目标提升
<----------|-------------------|---------->
          0                   delta
~~~

“不显著”只描述某个统计规则下的结果，不能代替这条数轴。实际产品还应把成本和护栏指标放在同一张决策表中。

### 8.3 低频安全事件不能只看平均值

安全事故可能发生率很低，但单次影响很大。若 10,000 个请求中没有观察到危险输出，不代表真实概率为 0；它只说明在当前样本和检测器下没有观察到事件。报告应给出样本数、攻击/正常分母、检测器召回率和严重度，并对零事件使用适合的上界估计或扩大测试规模。

同样，系统没有出现数据泄露不等于不存在泄露路径。负结果报告的价值在于描述“搜索到什么范围”，而不是把未观察到写成不可能发生。

### 8.4 功效分析帮助分配算力

对配对差异，一个简化的样本量近似为：

~~~math

n\approx\left(
\frac{(z_{1-\alpha/2}+z_{1-\beta})\sigma_d}{\delta}
\right)^2.

~~~

其中 $\sigma_d$ 是配对差异标准差，$\delta$ 是最小效应，$\alpha$ 是假阳性水平，$1-\beta$ 是目标功效。大模型实验中这个式子只是资源规划近似，因为 seed、任务簇和指标分布会改变独立性假设；但它能帮助团队说明为什么当前结果只能支持“趋势信号”，而不能支持精细的百分点结论。

## 9. 复盘案例一：合成 reasoning 数据没有带来稳定提升

### 9.1 初始观察

团队希望用合成 reasoning 数据做 continued pretraining，假设更长的推理轨迹会提升数学能力。第一轮结果如下，数字为教学案例：

| 设置 | 数学准确率 | 代码准确率 | 验证 loss | 单步成本 |
| --- | ---: | ---: | ---: | ---: |
| base baseline | 41.0% | 58.2% | 2.91 | 1.00x |
| synthetic-v1 | 40.6% | 59.0% | 2.84 | 1.35x |
| synthetic-v2 | 42.1% | 55.7% | 2.79 | 1.42x |

只看数学指标，v2 似乎提升了 1.1 个百分点；只看 loss，两个合成版本都比 baseline 好；但代码能力和单步成本表明，v2 可能是在更窄的领域上换取局部收益。

### 9.2 排查假设

至少有五个解释需要区分：

1. v2 的题目更难、更接近数学评估集，真实能力确实提高。
2. v2 与数学测试题近重复，提升来自污染。
3. 合成答案中存在错误，模型学到了错误过程，但格式更符合评估器。
4. 代码数据比例下降，代码退化来自 mixture 改变。
5. v2 输出更长，程序判定或 judge 对格式有偏好。

下一轮不应直接生成更大的 v3，而应先审计样本正确率、模板重复率、题目难度、近重复、domain mixture、输出长度和 verifier 一致性。

### 9.3 受控的下一轮

一个更好的设计是固定总训练 token，保持代码回放比例；按 verifier 正确率把合成数据分为高、中、低质量桶；从每桶抽取去重后的样本；在数学、代码、通用指令和格式遵循四个切片上做多 seed 评估；再比较无合成、低质量、高质量和混合回放条件。

如果高质量桶提升数学且不损害代码，支持“数据正确性和配比”比“只要增加合成 reasoning 数据”更接近真实机制。如果所有桶都无效，则更应检查训练阶段、目标函数或模型容量，而不是继续调数据 prompt。

### 9.4 合格的结论

可以这样写：

> 在当前模型、训练 token、合成数据生成器和评估协议下，synthetic-v1 没有带来数学提升；synthetic-v2 在数学切片提高 1.1 个百分点，但代码切片下降 2.5 个百分点且成本增加 42%。当前结果不支持无条件扩大合成数据。下一轮将固定总 token 和代码回放比例，按 verifier 正确率分桶并使用独立去重测试集。

这段话没有宣布“合成数据路线失败”，但已经足够指导资源分配和下一轮实验。

## 10. 复盘案例二：长上下文的平均分没有改变

### 10.1 初始观察

团队把上下文窗口从 32K 扩展到 128K，希望长文档问答整体改善。结果是：平均答案分数基本不变，中间位置证据的引用支持下降，prefill 时间、KV 显存和 P99 延迟上升。

一句“长上下文没用”至少混合了五件事：输入是否真的到达模型、位置机制是否外推稳定、拼接顺序是否变化、任务是否需要跨段合并、成本是否改变了可接受的请求预算。

### 10.2 重新定义问题

长上下文能力可以分成：

1. 接收更多 token。
2. 找到一个明显的局部证据。
3. 找到位于中间的证据。
4. 合并多个分散证据。
5. 处理证据冲突和时间顺序。
6. 在延迟和成本约束下完成以上任务。

如果评估集只测第一和第二类，平均分不变并不能说明第三到第六类。更合理的下一轮按文档长度、证据位置、证据数量、冲突类型和答案可得性分层，并同时记录输入 token、prefill、KV、输出和引用支持。

### 10.3 可能的工程结论

控制实验后可能得到：128K 在完整合同和跨章节审计任务上减少了切块损失，但中间位置引用仍不稳定；对只依赖两段最新记录的请求，RAG 分块更便宜；高风险审计需要 citation verifier 和人工抽样。这个结果不是一个总排名，而是一张路由边界：短任务走普通 RAG，确实需要长文档整合的任务走长上下文，高风险任务增加验证。

## 11. 复盘案例三：RAG 没有降低幻觉

### 11.1 把端到端失败拆开

某企业问答系统加入 RAG 后，答案正确率没有变化，无依据回答率也没有显著下降。此时不能直接说“检索没用”，因为失败可能发生在不同环节：

| 环节 | 要看的证据 | 负结果的含义 |
| --- | --- | --- |
| 召回 | Recall@k、候选覆盖 | 证据根本没有进来 |
| 排序 | nDCG、相关性位置 | 证据在候选中但排得太后 |
| 拼接 | 文档顺序、截断、重复 | 证据被上下文预算丢掉 |
| 生成 | 引用支持、答案依据 | 模型看到了证据却没有使用 |
| 验证 | unsupported 检测、误拒 | 评估器或策略定义不清 |
| 系统 | 超时、缓存、路由 | 线上并未真正执行 RAG |

### 11.2 保留反事实对照

最小反事实集合包括无检索、正确检索、无关检索、只给 gold evidence、加入引用约束和加入 verifier。若 gold evidence 也不能提升答案，问题可能在生成器利用证据；若 gold evidence 有效但真实检索无效，问题在召回或排序；若引用约束降低幻觉却增加误拒，问题是策略取舍而不是检索完全无效。

报告这样组织，负结果才会变成可修复的系统知识，而不是对“RAG”这个过大的词下判断。

## 12. 复盘案例四：安全训练带来误拒

### 12.1 主指标和副作用同时变化

安全微调后，危险请求的安全完成率提高，但正常医疗、代码和政策解释请求的误拒率也提高。若只看攻击成功率，结论会显得成功；若只看用户满意度，又可能忽略低频高严重度风险。

至少要分开报告：

1. 危险请求的拒绝或安全替代质量。
2. 正常请求的正确回答率。
3. 边界允许请求的误拒率。
4. 危险请求的漏拒率。
5. 拒答理由是否准确，是否泄露敏感信息。
6. 工具场景中是否发生越权调用。

### 12.2 下一轮不是简单减少拒答

如果直接降低拒答阈值，可能把误拒换成漏拒。更好的下一轮按风险等级分层，加入允许边界和安全转向数据，使用独立 red-team 集合检查漏拒，同时用正常任务和高风险工具操作分别评估。策略应允许“回答”“安全转向”“拒绝”“升级人工”之间有区别，而不是只有一个拒答概率。

安全负结果通常需要更保守的外推。一次测试集上没有漏拒，不能推出所有攻击都被阻断；一次误拒上升，也不能推出安全训练整体失败。报告必须把分母、严重度和评估范围写清楚。

## 13. 离线有效、线上无效：系统边界的负结果

### 13.1 离线样本不是线上流量

离线评估集往往固定、干净、没有超时和工具失败；线上请求会受到用户语言、上下文长度、峰值并发、缓存、路由、版本灰度和外部服务状态影响。即使模型权重相同，harness 不同也可能产生不同结果。

线上负结果复盘应同时查看：

| 维度 | 离线记录 | 线上需要补充 |
| --- | --- | --- |
| 输入 | 固定测试集 | 用户分布、长度、语言、敏感字段 |
| 路由 | 单模型 | 模型比例、降级、重试、缓存 |
| 资源 | 单次运行 | 并发、队列、P99、GPU 利用率 |
| 工具 | 理想返回 | 超时、空结果、权限和副作用 |
| 评估 | 统一脚本 | 反馈延迟、人工抽样、投诉和回滚 |

### 13.2 不要用线上事故倒推唯一根因

线上质量下降常有多个同时变化：模型版本、prompt、流量、检索索引和服务配置可能一起上线。事故复盘要先冻结时间线和变更清单，再按请求 trace 做分层；必要时回放旧版本、shadow 流量和固定样本。没有这些对照，最容易出现“最新改动一定是根因”的事后叙事。

## 14. 实验日志：让负结果有身份

### 14.1 一个 run 不是一张图

实验日志应把输入、处理、环境、输出和解释连起来：

~~~math

Run=(Claim,\;Treatment,\;Control,\;Data,\;Model,\;Code,\;Env,\;Seed,\;Eval,\;Output).

~~~

任何一个对象发生变化，都应该产生新的 run 标识或新的版本字段。把结果图保存下来，却没有数据 snapshot、配置和评估脚本，几周后就无法知道负结果是否来自当前实现。

### 14.2 最小日志字段

| 类别 | 字段 |
| --- | --- |
| 研究问题 | claim、estimand、预期效应、停止条件 |
| 处理 | 改动文件、组件版本、超参和预算 |
| 对照 | baseline 版本、匹配策略、sanity check |
| 输入 | 数据 snapshot、过滤、去重、污染审计 |
| 模型 | checkpoint、tokenizer、template、精度 |
| 环境 | 代码 revision、依赖、GPU、驱动、runtime |
| 随机性 | seed、数据顺序、采样和重试 |
| 评估 | 测试集、指标、分母、后处理、judge |
| 结果 | 原始输出、曲线、trace、错误和成本 |
| 决策 | 支持/不支持/证据不足/无效、负责人和下一步 |

日志字段不是为了增加文档负担，而是为了让下一次实验从已有信息开始。尤其要保留失败样本和失败配置，因为它们往往包含方法边界的直接证据。

## 15. 如何写一份真正可读的实验报告

### 15.1 从故事顺序写，而不是从字段清单写

一份报告最好按照读者理解问题的顺序展开：

1. **背景**：当前系统或论文遇到了什么具体问题。
2. **主张**：这次实验想支持或反驳哪句话。
3. **预测**：如果机制成立，哪些中间指标和最终指标应如何变化。
4. **设计**：处理、baseline、控制变量、预算和评估单位。
5. **结果**：主指标、区间、seed、切片、护栏和资源。
6. **排查**：哪些替代解释已被检查，检查证据是什么。
7. **解释**：结果支持哪一部分，哪一部分没有支持。
8. **决定**：继续、停止、缩小范围、修实现、换数据或补实验。
9. **边界**：没有验证的规模、分布、时间或风险条件。

空白模板只能提醒人别漏字段，不能替代这条叙事。真正有用的报告应让一个没有参与实验的人读完后，能复述“为什么做、发生了什么、目前相信什么、下一步为什么这样做”。

### 15.2 结果表要同时显示观察和解释所需的背景

| 条件 | 主指标 | 95% 区间 | 关键切片 | 护栏 | 成本/延迟 | 运行数 |
| --- | ---: | --- | --- | --- | --- | ---: |
| baseline |  |  |  |  |  |  |
| candidate |  |  |  |  |  |  |
| matched control |  |  |  |  |  |  |
| sanity case |  |  |  |  |  |  |

主指标如果没有区间，读者不知道差异是否稳定；没有切片，读者不知道平均数掩盖了什么；没有护栏和成本，读者无法做工程选择；没有运行数，读者无法判断重复是否足够。

### 15.3 写结论时保留动词的证据强度

不同动词对应不同证据：

| 证据 | 合适表达 | 不合适表达 |
| --- | --- | --- |
| 单次点估计 | 观察到、出现信号 | 证明、稳定提升 |
| 多 seed 且区间支持 | 支持、在此条件下重复出现 | 普遍有效 |
| 只有部分切片 | 在该切片成立 | 全面改善 |
| 评估器冲突 | 结果依赖评估协议 | 客观质量已确定 |
| 成本超约束 | 质量有收益但当前不可部署 | 方法更好 |
| 证据缺失 | 当前无法判定 | 方法无效 |

科学写作不是把语气变弱，而是让读者知道这句话可以被什么新证据推翻或扩展。

## 16. 保存反事实和失败 artifact

### 16.1 失败实验不能只保存失败配置

至少保留以下对照：

1. 能够工作的 baseline。
2. candidate 的完整配置。
3. 只改变一个关键因素的最小版本。
4. 关闭关键组件的 remove 或恒等替代。
5. 已知正确的 sanity case。
6. 代表性成功、失败、边界和异常样本。

例如 RAG 没有降低幻觉时，保存无检索、正确检索、无关检索、gold evidence 和 verifier 版本；如果安全训练误拒增加，保存正常任务、边界允许和危险任务的原始输出。反事实的意义是帮助未来读者定位差异，而不是让表格看起来更完整。

### 16.2 失败 artifact 也有版本血缘

原始日志、模型输出和错误 trace 应尽量不可变保存，并绑定代码、数据、配置和环境版本。修复后的报告可以引用旧 artifact，但不要覆写旧结果；否则团队会失去“修复前到底发生了什么”的证据。

如果结果涉及用户数据、隐私或安全攻击样本，保存策略还要区分原始敏感内容、脱敏摘要、访问权限和留存期限。可复查不等于无限复制敏感数据。

## 17. 从负结果产生下一步假设

### 17.1 从观察到行动的四列表

把复盘写成下面的结构，能防止“没效果”成为终点：

| 观察 | 尚存解释 | 区分实验 | 决策 |
| --- | --- | --- | --- |
| 数学提升、代码下降 | mixture 改变或数据窄化 | 固定总 token，保持代码 replay | 继续做配比消融 |
| RAG 平均分不变 | 召回差、生成不利用证据 | gold evidence 与无关证据对照 | 先定位链路 |
| 安全漏拒下降、误拒上升 | 规则过宽或边界数据不足 | 风险分层和允许样本 | 修复边界数据 |
| 128K 中间证据下降 | 位置机制或上下文噪声 | 位置/长度/多证据切片 | 收窄长上下文范围 |
| 三个 seed 方向不一致 | 效应小或训练不稳 | 增 seed、看训练曲线 | 暂缓规模扩展 |

每一行都把下一实验与一个替代解释绑定。如果下一实验不能区分任何剩余解释，就不值得仅因为“数据还没跑够”而继续。

### 17.2 假设要能被失败

“继续优化数据质量”不是可检验假设；“在固定总 token、同一代码 replay 和独立数学测试集下，高 verifier 正确率桶比随机桶提高至少 1 个百分点”才是。它有处理、对照、阈值和评估对象，结果不满足时可以停止或改写假设。

### 17.3 不要把每次修复都写成新成功

如果第一次实验因为 label shift 出错，修复后得到提升，正确叙述是“修复了实验实现并重新估计方法效果”，不能把修复前的坏实验和修复后的有效结果合并成一条连续成功故事。版本变化本身就是证据链的一部分。

## 18. 沉没成本、停止条件和资源决策

### 18.1 预先写出停止条件

停止条件可以包括：

1. 在规定 seed 和关键切片上未达到最小实用效应。
2. 质量未提升且成本超过上限。
3. 高严重度副作用超过可接受范围。
4. 关键机制指标与假设相反。
5. 连续实验没有减少解释空间。
6. 缺少数据、模型或权限，继续运行只能制造不可比结果。

条件必须绑定证据质量。例如“连续三次没有提升”只有在三次使用相同有效协议、足够重复和合理 baseline 时才有意义。否则，连续失败可能只是连续重复同一个 bug。

### 18.2 用单位成功成本比较方向

设总资源成本为 $C$，成功任务数为 $S$，则：

~~~math

C_{success}=\frac{C}{S},\qquad S>0.

~~~

如果 candidate 的成功率更高，但成本增加得更快，$C_{success}$ 可能反而变差。对 reasoning、Agent 和工具系统尤其要记录输出 token、调用数、重试、人工升级和失败回滚，不要用一次模型调用的价格代替完整任务成本。

### 18.3 决定“暂停”而不是强行二元化

研究方向可以有三种暂时状态：

- **继续**：证据支持机制或有明确可区分的下一实验。
- **暂停**：当前收益不足或证据不足，但未来有新数据、规模或工具后值得重启。
- **停止**：在目标范围内被反驳，或成本/风险长期不满足，继续投入没有合理信息价值。

暂停不是失败，也不是把问题藏起来。报告要写出触发暂停的证据、重新启动需要什么条件，以及谁负责重新评估。

## 19. 在团队和面试中讲清失败实验

### 19.1 团队评审要围绕证据，而不是围绕责任

负结果复盘容易变成“谁写错了代码”。如果只追责，成员会隐藏失败，团队就失去早期信号。更好的顺序是：先冻结 artifact 和时间线，再确认观察，随后按测量、数据、实现、训练、评估和系统层排查，最后讨论责任和流程改进。

这并不意味着不追究严重的工程失误，而是让责任判断建立在可复查事实之上。一个训练脚本的 bug 如果能推动单 batch sanity check、自动 schema 校验和 artifact manifest，团队从一次事故中得到的收益才不会只停在口头提醒。

### 19.2 面试中的失败案例不应只讲“最后解决了”

一个有说服力的失败实验故事包含：

1. 真实背景和当时的可检验假设。
2. 为什么选择这个 baseline 和评估协议。
3. 负结果的具体指标、区间、切片和资源代价。
4. 如何排除实现、数据和评估问题。
5. 最终保留的解释以及仍未知的部分。
6. 团队选择继续、暂停或停止的依据。
7. 后续改动带来的新证据，而不是只讲结果变好。

例如，不要说“RAG 没效果，后来加 reranker 就好了”；应说明原始召回 Recall@k、gold evidence 对照、生成器利用证据的结果、reranker 引入的延迟，以及为什么最终只对高风险请求启用它。这样表达的重点是判断能力和证据边界，而不是把失败包装成必然成功。

## 20. 可运行的负结果决策 demo

下面的示例构造三个 seed、四个任务切片的 paired 结果，演示如何把“平均提升”与“区间、实用阈值、成本和切片退化”放在一起。数字是合成数据，不代表任何真实模型。

~~~python
from dataclasses import dataclass
from math import sqrt


@dataclass
class Run:
    seed: int
    baseline: float
    candidate: float
    cost_ratio: float


runs = [
    Run(1, 0.720, 0.724, 1.18),
    Run(2, 0.715, 0.716, 1.18),
    Run(3, 0.725, 0.724, 1.18),
]

slices = {
    "general": (0.780, 0.781),
    "code": (0.640, 0.625),
    "math": (0.510, 0.518),
    "high_risk": (0.910, 0.909),
}


def mean(values):
    return sum(values) / len(values)


def sample_sd(values):
    center = mean(values)
    return sqrt(sum((value - center) ** 2 for value in values) / (len(values) - 1))


deltas = [run.candidate - run.baseline for run in runs]
delta_mean = mean(deltas)
delta_se = sample_sd(deltas) / sqrt(len(deltas))
ci_low = delta_mean - 1.96 * delta_se
ci_high = delta_mean + 1.96 * delta_se
slice_deltas = {
    name: candidate - baseline
    for name, (baseline, candidate) in slices.items()
}

minimum_effect = 0.010
cost_ratio = mean([run.cost_ratio for run in runs])
has_guardrail_regression = slice_deltas["code"] < -0.010

if has_guardrail_regression:
    decision = "repair_guardrail_regression"
elif ci_low >= minimum_effect and cost_ratio <= 1.10:
    decision = "continue_to_target_scale"
elif ci_high < minimum_effect:
    decision = "stop_current_configuration"
else:
    decision = "collect_more_evidence"

print(f"delta_mean={delta_mean:.4f}")
print(f"delta_ci=[{ci_low:.4f}, {ci_high:.4f}]")
print(f"minimum_effect={minimum_effect:.4f}")
print(f"slice_deltas={slice_deltas}")
print(f"cost_ratio={cost_ratio:.2f}")
print(f"decision={decision}")
~~~

这个 demo 的关键不是用三个 seed 得出强结论，而是演示决策顺序。即使总体区间可能覆盖正值，代码切片下降超过 1 个百分点也会先触发副作用修复；如果没有副作用，整体区间仍低于预设实用效应，就停止当前配置；只有效应、成本和切片都满足条件，才值得扩展到目标规模。

## 21. 资料与证据边界

关于实验设计、重复、区组、随机化和误差来源，可参考 [NIST/SEMATECH e-Handbook of Statistical Methods：Design of Experiments](https://www.itl.nist.gov/div898/handbook/pri/pri.htm)。它支持实验设计的通用方法，不是某个大模型或某个负结果的性能证据。

关于研究报告、数据、代码、统计和限制的披露，可参考 [NeurIPS Paper Checklist](https://neurips.cc/public/guides/PaperChecklist)。清单能提醒作者记录可复查信息和局限，但不保证实验本身有效，也不替代独立复现。

关于可复现研究的工作流、环境、数据和计算记录，可参考 [The Turing Way：Reproducible Research](https://book.the-turing-way.org/reproducible-research/reproducible-research/)。它是实践型开放教材，适合支持工作流和协作原则；具体项目仍需按照自己的安全、隐私和资源条件落地。

关于机器学习复现实践，可参考 [ML Reproducibility Challenge](https://reproml.org/)。挑战项目展示了复现差异、实现细节和报告边界的重要性，但任何一篇复现报告都只覆盖自己的代码、数据和环境。

训练和硬件随机性应参考 [PyTorch Reproducibility and Randomness Notes](https://docs.pytorch.org/docs/stable/notes/randomness.html)。官方文档明确说明跨版本、平台和设备不保证完全复现，因此本章把环境、seed、数据顺序和 kernel 行为作为证据链的一部分。

关于推断性复现和分析选择，可参考 [Inferential Reproducibility](https://arxiv.org/abs/2302.04054)。它提醒读者，重复得到一个点估计还不够，还要考虑分析路径、数据选择和结论的不确定性。该论文属于方法讨论资料，不是本章合成案例的实证依据。

本章的合成 reasoning、长上下文、RAG、安全和 demo 数字都是教学构造。它们用于演示怎样识别负结果、保留反事实和形成下一步决策，不能被引用为任何公开模型或产品的 benchmark。真实实验应回到自己的论文版本、代码 revision、数据 snapshot、模型 checkpoint、评估 harness 和线上 trace。

## 22. 本章小结

负结果是一种需要分层处理的证据，而不是一个可以直接贴在实验上的失败标签。可靠的处理方式是：

1. 先确定主张、estimand、最小实用效应和资源/风险约束。
2. 区分有效负结果、证据不足和实验无效，不能把三者写成同一句“没有提升”。
3. 按测量、数据、实现、优化、随机性、评估和系统层逐层排查。
4. 同时报告主指标、切片、护栏、成本、延迟、失败率和原始样例。
5. 用配对差异、区间、seed、功效和分母定义说明“不确定”到底意味着什么。
6. 保存 baseline、candidate、sanity check、最小改动和失败 artifact，保留反事实。
7. 把每个负结果转换成可区分剩余解释的下一步假设，或者明确的停止/暂停决定。
8. 结论只覆盖实验实际验证的模型、数据、任务、资源和时间范围。

成熟研究者不是没有负结果，而是能把负结果变成一条可复查的知识链：这次观察是什么，哪些解释已经排除，哪些仍然可能，当前应继续还是停止，以及下一次实验为什么比重复旧实验更有信息量。
