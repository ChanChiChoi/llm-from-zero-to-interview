# 第八章：Scaling 与训练论文线

大模型训练最昂贵的决定，通常在第一步梯度更新之前就已经做出了：模型做多大，准备多少 token，数据从哪里来，使用多少 GPU，允许多长时间训练，以及如何判断训练是否稳定。训练开始以后再用 benchmark 追赶这些决定，成本往往已经很高。

Scaling 论文研究的正是这些决定之间的关系。它们试图回答：在给定计算预算下，参数、数据和训练时间如何分配？小模型曲线能否帮助规划大模型？loss 的下降能否预测下游能力？数据质量和配比如何改变“有效 token”？分布式系统和数值稳定性会不会让纸面上的 scaling 规律失效？

初学者可以把模型参数看成工厂规模，把训练 token 看成原料，把 FLOPs 看成电力和机器时间。工厂太小，可能没有足够容量；工厂很大但原料不足，设备没有被充分训练；原料很多但质量差，模型会稳定地学到错误或低价值模式。专家还要加入几个现实变量：不同 token 的 tokenizer 成本不同，MoE 的总参数和 active parameters 不同，训练吞吐受通信影响，loss 与 reasoning 能力不总是同步，长时间训练还可能被数据污染、重复和灾难性异常打断。

本章不把 scaling law 当成万能公式，而是把它放回实验设计、资源规划和训练工程中阅读。一个可靠结论必须说明模型族、数据分布、训练目标、计算口径、拟合范围、硬件条件和外推边界。

## 1. Scaling 研究到底在估计什么

### 1.1 三个核心变量

对一个 dense decoder-only Transformer，可以先用三个变量描述训练规模：

1. $N$：可训练参数量。
2. $D$：训练 token 数。
3. $C$：训练计算量，通常用 FLOPs 或 GPU 小时近似。

在固定架构和实现下，$C$ 与 $N$、$D$ 大致相关；一个常见的教学近似是：

~~~math

C\approx kND,

~~~

其中 $k$ 汇总每个 token 的前向、反向、优化器和实现常数。不同架构、激活比例、序列长度、精度和重计算策略会改变 $k$，所以它不是跨模型的精确计费公式。

如果一个实验只说“模型是 7B”，读者还不知道它训练了多少 token；只说“训练了 1T token”，也不知道模型容量、数据质量和计算是否相同。Scaling 论文的第一步，就是把这些维度同时放到预算账本中。

### 1.2 Loss、能力和系统结果是三个对象

Scaling 论文通常先研究验证 loss，因为它连续、稳定、容易比较和拟合。实际产品却关心代码通过率、数学正确率、工具成功率、拒答边界、延迟和成本。可以把结果分成三层：

| 层 | 典型结果 | 优点 | 不能自动推出 |
| --- | --- | --- | --- |
| 训练测量 | train/validation loss、困惑度 | 连续、易拟合、成本低 | 具体任务能力一定提升 |
| 下游能力 | benchmark、代码测试、人工偏好 | 接近任务目标 | 生产分布和安全行为 |
| 系统结果 | 成功率、P99、成本、事故率 | 接近部署决策 | 其他模型和其他流量 |

如果 loss 下降而 reasoning benchmark 不变，可能是预训练目标和任务之间存在差距；如果 benchmark 上升而成本翻倍，可能是资源效率变差；如果离线提升而线上下降，可能是 harness 或分布不同。三层结果要并列保存，不能互相替代。

### 1.3 Scaling claim 的最小形式

一句“更大模型更强”缺少条件。更完整的 claim 至少要写成：

> 在模型族、数据分布、训练目标、优化配方和评估协议固定的范围内，增加参数或训练 token 是否使验证 loss 按可预测趋势下降？这种趋势是否能外推到目标规模和目标任务？

这里有两个不同问题：趋势是否存在，以及趋势是否可外推。前一个是拟合问题，后一个是分布迁移和机制稳定性问题。小模型上拟合得很好，不代表跨架构、跨数据质量和跨后训练阶段仍然成立。

### 1.4 计算口径：参数量不等于每个 token 的计算量

参数量是最容易被引用、也最容易被误读的规模指标。对于 dense 模型，几乎每个 token 都会经过同一组参数，因此可以用 $N$ 粗略估计每个 token 的计算量。对于 MoE 模型，模型的总参数可能很大，但一个 token 只路由到部分 expert；此时总参数、active parameters、实际 FLOPs 和通信量是四个不同的对象。

可以用一个教学近似区分它们：

~~~math

C_{dense}\approx kND,
\qquad
C_{MoE}\approx k(N_{shared}+\rho N_{expert})D,
\qquad 0<\rho\leq1.

~~~

$N_{shared}$ 表示所有 token 都会使用的共享参数，$N_{expert}$ 表示 expert 参数总量，$\rho$ 是每个 token 实际经过的 expert 参数量占全部 expert 参数量的平均比例。若有 $E$ 个等宽 expert、每个 token 理想地选择 $k$ 个 expert，且不发生 padding，才可以粗略写成 $\rho\approx k/E$；真实系统中的容量因子、padding、路由丢弃和 expert 宽度差异都会改变这个比例。还要加入 router、dispatch、all-to-all 和负载不均衡，所以第二个式子只能作为记账入口，不能直接当作硬件计费结果。

举例来说，一个 MoE 模型可以拥有更大的总参数和较小的 active parameters。它可能在同样的 active FLOPs 下获得更大的容量，也可能因为跨卡路由通信和热点 expert 失衡而没有得到预期吞吐。阅读论文时至少要分别记录：总参数、每 token 激活参数、每 token 理论 FLOPs、实际 tokens/s、通信占比和显存占用。如果论文只报告“参数规模”，却没有说明激活路径，两个模型的 scaling 点就不能直接比较。

同样的口径问题也出现在 token 上。中文、代码、数学和混合 Unicode 文本的 tokenizer 切分长度不同；“一个网页样本”与“一个 token”也不是同一层对象。因此报告训练预算时，应同时给出原始样本量、tokenizer 后 token 量、去重后的有效 token、每 token FLOPs 和实际训练 wall time。只有这样，参数—数据—计算的三角关系才可复查。

## 2. 经验 scaling law：用曲线替代盲目堆规模

### 2.1 幂律的直觉

在一定规模范围内，语言模型验证 loss 常能用幂律近似：规模增大后继续改善，但边际收益递减。一种教学表达是：

~~~math

L(N)=L_{\infty}+A N^{-\alpha},

~~~

其中 $L_{\infty}$ 是不可约或长期下限的近似，$A$ 是尺度常数，$\alpha$ 是模型规模收益指数。对数据量也可以写成：

~~~math

L(D)=L_{\infty}+B D^{-\beta}.

~~~

真实模型同时受到参数和数据限制，可以用一个简化的联合形式表示：

~~~math

L(N,D)=L_{\infty}+A N^{-\alpha}+B D^{-\beta}.

~~~

这类公式不是自然界的定律，而是对实验区间的压缩描述。它能帮助比较边际收益、规划实验点和发现偏离，但不能越过训练分布、模型架构和目标任务的边界。

### 2.2 如何拟合一条曲线

如果只改变 $N$，可以在合适的变换后观察近似直线关系；但当 $L_{\infty}$ 未知时，不能直接对 $L$ 取对数并把所有点当成直线拟合。更稳妥的做法是在原始 loss 上拟合 $L_{\infty},A,\alpha$，检查残差，再用 log-log 图作为诊断。如果同时改变 $N$ 和 $D$，就需要设计一个实验矩阵，而不是把不同论文和不同数据集的点拼起来。一个基本流程是：

1. 先固定 tokenizer、数据来源、过滤规则、模型家族和优化器。
2. 选择多个参数规模和多个训练 token 点。
3. 在相近硬件和精度条件下记录验证 loss、训练 FLOPs、吞吐和失败状态。
4. 用训练过程中的 checkpoint 观察曲线，而不只保存最终点。
5. 留出规模或数据条件不参与拟合，用来检验外推误差。
6. 检查残差是否随长度、数据类型或模型规模系统变化。

如果曲线在训练早期下降、后期停止，可能是训练不足、数据上限或优化器限制；如果只有一个点远离曲线，可能是异常 run、数据污染或实现 bug。拟合本身不能告诉你原因，必须回到实验记录。

### 2.3 边际收益比单点分数更重要

假设增加参数带来的 loss 改善为：

~~~math

\Delta L_N=L(N,D)-L(\lambda N,D),
\qquad \lambda>1.

~~~

增加 token 的改善同理。资源规划关心的是每单位计算的收益，而不是只看某个最大模型的最终 loss：

~~~math

\mathrm{GainPerCompute}
=\frac{L_{old}-L_{new}}{C_{new}-C_{old}},
\qquad C_{new}>C_{old}.

~~~

当两个候选方案的最终 loss 很接近时，边际收益和系统成本可能决定选择。一个小模型多训练一倍 token，可能比把模型扩大一倍更划算；另一个任务在模型容量不足时，增加 token 可能收效很小。

### 2.4 经验规律的失效信号

下面的现象提醒读者不要机械外推：

1. 验证 loss 曲线在目标规模出现明显拐点。
2. 不同数据质量桶的 scaling 指数不同。
3. 模型架构从 dense 变为 MoE 或混合结构。
4. 训练目标从预训练转为 SFT、RL 或偏好优化。
5. 任务能力出现阈值、突变或与 loss 脱钩。
6. 长上下文、工具和多轮状态让输入/输出成本改变。
7. 评估集存在污染、提示敏感性或 judge 偏差。

遇到失效信号，正确动作不是把异常点删除，而是记录外推失败的条件，并问是否需要分阶段或分任务拟合。

### 2.5 Kaplan 与 Chinchilla 为什么会得到不同的资源直觉

阅读 scaling 文献时，读者常会遇到一个表面矛盾：早期工作让人形成了“扩大模型很重要”的印象，后来的 compute-optimal 工作却强调很多模型参数太多、训练 token 太少。它们并不是简单的互相否定，而是在不同实验设计和预算约束下估计了不同问题。

早期 scaling 实验主要建立了几个重要事实：验证 loss 对模型规模、数据量和计算量在相当范围内呈现可拟合趋势；规模扩大通常带来持续但递减的收益；小规模实验可以为更大规模训练提供规划信息。若实验中的大模型没有被充分训练，观察到的曲线会把“模型还有容量”误读为“应该继续增加参数”。

Chinchilla 类研究重新把参数和 token 放进同一个固定计算约束下，询问的是：在总训练 FLOPs 已经确定时，多少参数配多少 token 才能获得最低验证 loss？它指出，许多此前的模型沿着参数方向投入过多，应该使用更少的参数、更多的训练 token。这里的关键不是替换一条比例，而是改变了优化问题：模型规模不再是单独的目标，数据量也不再是模型训练完之后才补充的变量。

两类结论出现差异，可能来自以下来源：

1. 模型和数据规模的取值范围不同，幂律在边界外可能改变斜率。
2. 计算是否只计算前向/反向，是否包含重计算、通信、评估和失败重试，口径不同。
3. 训练 token 是否足够让每个模型达到可比的训练状态，undertraining 会改变最优点。
4. 数据质量、重复率、tokenizer 和优化配方不同，导致同一 token 数具有不同学习价值。
5. 优化目标不同。验证 loss 的最优点不一定是推理成本、后训练效果或生命周期成本的最优点。

因此，读者不应把两篇论文压缩成“谁的比例正确”。更好的做法是先写清 claim 的约束，再检查实验矩阵是否覆盖目标区域，最后用 held-out 规模验证外推。论文结论看似冲突时，实验范围和 estimand 往往比数字本身更能解释差异。

## 3. GPT-3：规模扩展和 in-context learning

### 3.1 两条线不能混为一谈

GPT-3 的历史影响来自两条相互关联但不等同的线：

1. 更大规模的自回归模型在很多语言任务上表现更强。
2. 模型可以在 prompt 中读取少量示例，而不进行梯度更新，就完成特定任务格式。

第一条是 scaling 现象，第二条是 in-context learning（ICL）现象。ICL 的结果还受示例选择、顺序、格式、标签空间、上下文长度和评估样本影响。不能把某个 few-shot 分数的提升全部归因于参数量。

### 3.2 ICL 是额外的推理预算

few-shot 示例不是免费的。它增加输入 token、prefill 计算和可能的上下文位置压力。比较 zero-shot 和 few-shot 时要记录：

1. 示例数量和总 token。
2. 示例选择算法和是否人工挑选。
3. 示例顺序和标签格式。
4. 生成模型、temperature 和输出上限。
5. 每个任务的有效覆盖率和失败类型。

如果一个方法在 few-shot 下提升，但 prompt 变长 10 倍，应该同时报告质量和单位请求成本。ICL 证明的是模型能利用上下文示例，不等于模型已经通过参数学习了同样的能力。

### 3.3 GPT-3 论文如何读

阅读大规模模型论文时，应把模型规模表、数据表、训练计算、评估 prompt 和污染讨论放在一起。重点问题包括：

- 不同规模模型是否使用相同数据和训练目标？
- 小模型和大模型是否训练到类似的 token 数，还是某些模型明显 undertrained？
- 任务分数是否随着 loss 平滑变化，还是存在 prompt/格式跳变？
- few-shot 示例是否为每个任务手工选择？
- benchmark 题目是否可能进入训练语料？

规模扩展给出了重要能力信号，但它没有证明“只要继续加参数就会自动出现所有需要的能力”。后续的 compute-optimal 工作正是对“参数量单独主导一切”这一直觉的修正。

## 4. Chinchilla：固定计算下参数和数据的平衡

### 4.1 从无约束增长转向预算优化

给定一个训练计算预算 $C_0$，研究者要在参数 $N$ 和 token $D$ 之间分配资源。可以把问题写成：

~~~math

\min_{N,D} L(N,D)
\quad\mathrm{subject\ to}\quad
C(N,D)\leq C_0.

~~~

如果模型很大但 token 太少，模型处于 undertrained 状态；如果模型很小但 token 太多，额外数据可能无法被容量充分吸收。compute-optimal 的目标是在约束下找到一个折中点，而不是追求参数或 token 的单项最大化。

### 4.2 为什么不存在跨场景固定比例

常被转述的某个参数/token 比例，只能对应特定论文的模型族、数据、计算口径和训练范围。比例会受以下因素影响：

1. 每个 token 的真实 FLOPs 和模型结构。
2. 数据质量、重复和污染。
3. 优化器、学习率和 batch。
4. 模型是否 dense、MoE 或混合结构。
5. 目标是预训练 loss 还是下游任务能力。
6. 推理成本和模型发布后的使用量。
7. 训练预算是否包含评估、重试、通信和 checkpoint。

因此，Chinchilla 的核心启发是“参数和 token 必须联合优化”，而不是让读者背一条永恒的数字。

### 4.3 undertrained 与 overtrained

可以用训练曲线直观判断：

- **undertrained**：增加训练 token 后验证 loss 仍明显下降，模型容量尚未充分训练。
- **data-limited**：增加 token 后收益很小，数据质量或重复可能成为上限。
- **capacity-limited**：模型太小，更多 token 的边际收益快速下降。
- **optimization-limited**：曲线被学习率、稳定性或实现问题限制，不能用于判断容量。

这四种状态的修复动作不同。undertrained 可能增加 token；data-limited 需要改善数据；capacity-limited 可能增加参数；optimization-limited 先修训练。只看最终 loss 很难区分它们。

### 4.4 训练最优不等于部署最优

Chinchilla 风格的训练最优点只针对训练目标和计算预算。如果模型要服务数十亿次请求，较大的模型可能在训练上不最优，却在总生命周期成本上更划算；如果延迟极敏感，较小模型和蒸馏可能更合适；如果需要长上下文，KV 和 prefill 成本会改变模型选择。

这类取舍已有直接的 scaling-law 案例。Sardana 等人把推理需求加入训练与部署预算，在 MPT 风格模型上训练了 47 个约 150M—6B 参数的模型，并把 token/parameter 比例扩展到 10,000。论文的成本模型显示，在其高推理需求情景中，较小而训练更久的模型可能降低总 FLOPs 或估算成本；约 10 亿请求的示例依赖输入/输出长度、训练与推理 MFU、硬件价格和延迟简化假设。这个结果提醒我们把服务需求带回训练选型，适用范围仍由论文的质量目标和成本模型决定，见 [Beyond Chinchilla-Optimal](https://arxiv.org/abs/2401.00448)。

生命周期的货币成本可以粗略写成：

~~~math

K_{life}=K_{train}+R\,K_{serve}+K_{storage}+K_{maint},

~~~

其中 $R$ 是预计请求量。训练阶段的 compute-optimal 只是训练计算量的局部最优，不能直接替代产品的总成本决策；$K_{train}$、$K_{serve}$ 等符号表示货币成本，不能与前文的训练计算量 $C$ 混用。

## 5. 数据量之外：质量、配比和有效 token

### 5.1 两个 1T token 不等价

训练 token 的数量容易统计，价值却不只由数量决定。两个训练集都包含 1T token，可能在以下方面完全不同：

1. 网页、书籍、代码、论文、数学、对话和多语言比例。
2. 结构完整性、重复率、模板页、广告和乱码比例。
3. 许可证、隐私和删除血缘。
4. 训练/评估近重复和 benchmark 污染。
5. tokenizer 对不同语言和代码的切分效率。
6. 难度、时效、事实质量和领域覆盖。

可以引入一个教学上的有效 token 概念：

~~~math

D_{effective}=\sum_{i=1}^{n}q_i\,t_i,

~~~

其中 $t_i$ 是第 $i$ 个样本的 token 数，$q_i\in[0,1]$ 是综合质量或可学习性权重。这个式子不是训练框架的真实 loss，而是提醒我们：低质量、重复或污染 token 不能简单等价于干净、有效、覆盖新能力的 token。

### 5.2 配比是能力预算的分配

设数据来源有 $K$ 类，采样权重为 $w_k$：

~~~math

\sum_{k=1}^{K}w_k=1,
\qquad
D_k=w_kD.

~~~

增加代码权重可能提高代码能力，却改变通用语言和对话覆盖；增加数学和 reasoning 数据可能提高特定推理任务，却带来模板化和风格变化；增加低资源语言可能改善覆盖，却在固定总 token 下稀释高资源语言。配比没有脱离目标的“最佳值”。

### 5.3 数据混合论文的证据

读 data mixture 或数据选择论文时，记录：

1. 总 token 是否固定。
2. 删除一类数据后是否补齐其他数据。
3. 各来源的质量和重复是否匹配。
4. 采样权重是静态、温度采样还是动态调整。
5. 评估是否覆盖所有受影响能力。
6. 是否检查污染、版权、隐私和时效。
7. 数据成本是否被算入训练决策。

DoReMi 等方法关注如何根据验证信号调整混合权重，但任何自动配比方法都需要独立验证集和目标分布。一个模型在某个验证集上变好，可能只是把更多预算投向了该验证集相似的数据。

后续数据 mixture 研究把配比也放进可拟合的 scaling 问题。ICLR 2025 的 Data Mixing Laws 用小模型的来源比例实验预测未见 mixture；作者报告，在 RedPajama 的一个 1B 参数、100B token 设置中，优化配比达到与默认 mixture 多训练 48% steps 相近的表现。NeurIPS 2025 的 Scaling Laws for Optimal Data Mixtures 则把目标域、参数量、token 数和域权重共同拟合，并在语言、多模态和视觉预训练设置中验证预测。两类结果说明小规模实验可用于缩小候选范围；其排名和预测仍绑定语料域、目标 loss、预算与固定 mixture 假设。数据工程中的配比、重复与采样操作见[第九册第五章](../../book-09-data-engineering/chapters/05-data-mixture与配比.md)。

### 5.4 有效 token 是目标相关的向量，不是一个万能折算率

把每个样本压成一个 $q_i$，有助于建立直觉，却可能掩盖不同能力之间的冲突。一个代码样本对代码生成有价值，对日常对话未必有同样价值；一段高质量数学证明对形式推理有帮助，却不能自动替代多语言和事实覆盖。因此更稳妥的记账方式是给每个目标能力单独定义有效 token：

~~~math

D_{effective}^{(m)}
=\sum_{i=1}^{n}q_i^{(m)}t_i,
\qquad m\in\{\text{code},\text{math},\text{language},\text{safety},\ldots\}.

~~~

$m$ 是目标能力，$q_i^{(m)}$ 表示样本对该能力的有效性，$t_i$ 是 token 数。同一条数据在不同 $m$ 下可以有不同权重，甚至在安全和可用性两个目标上产生相反影响。这个公式不是声称可以从质量分数精确预测能力，而是提醒研究者不要用单一 aggregate score 把多目标问题伪装成一个标量优化问题。

实践中可以先做能力切片，再比较配比变化：固定总 token，改变代码、数学、自然语言和安全数据权重；对每个切片记录目标能力、通用能力、误拒/漏拒、污染和训练成本。如果代码分数提高但通用语言下降，结果应写成“目标能力与代价发生了可测变化”，而不是笼统地称为“数据质量提升”。只有在目标分布、权重和评估切片都公开时，数据 mixture 的结论才具有可迁移性。

质量也可以显式进入经验模型。ICLR 2026 的质量感知 scaling 研究提出无量纲 $Q$，用 corruption-rate proxy 或 deficiency measure 估计，并将数据项写成 $B/(D^{\beta}Q^{\gamma})$。它在 Paracrawl v8 翻译和 C4 因果语言建模任务中控制噪声与覆盖率；拟合得到的质量指数在两种任务中分别约为 0.173 和 0.401。该研究支持“数据量和数据质量需要共同观察”，但 $Q$ 的定义、估计值和幂指数都绑定论文的质量操作化与任务，不能作为任意语料的通用质量分数，见 [Scaling Laws Revisited](https://proceedings.iclr.cc/paper_files/paper/2026/hash/d0c80a0c294a16190c8904b9809c5fba-Abstract-Conference.html)。

合成数据研究也显示，数据来源和混合比例会改变 scaling 曲线。EMNLP 2025 的研究覆盖超过 1,000 个模型变体和 100,000 GPU 小时；在较大数据预算的特定对照中，约三分之一改写文本与三分之二自然网页文本达到相同验证 loss 的速度提高约 5—10 倍，改写文本单独训练没有同等收益，教材式纯生成数据则在若干下游域退化。数字只适用于论文的改写流程、模型和预算，说明“合成”本身不构成质量标签，见 [Demystifying Synthetic Data](https://aclanthology.org/2025.emnlp-main.544/)。

## 6. 预训练 scaling 与后训练 scaling 不是同一条曲线

### 6.1 训练阶段改变了估计对象

预训练通常追踪 next-token loss，SFT 追踪指令或任务损失，偏好优化追踪选择行为，RL/可验证奖励追踪任务成功或奖励。参数、token 和计算量在不同阶段的含义不相同。

一个预训练 loss 很好的 base model，经过 SFT 后可能获得更强指令遵循；一个后训练模型在某个任务上得分更高，也可能牺牲通用语言覆盖。把不同阶段的 token 简单相加，会掩盖数据质量、目标和梯度信号的差异。

### 6.2 能力不是一条平滑曲线

许多任务能力会受到阈值、格式、工具和后训练影响。loss 的平滑下降可能对应 benchmark 的缓慢提升，也可能在某个规模突然跨过任务所需的表示或推理阈值。这个现象不能直接被解释为“涌现的物理定律”，需要排查：

1. 指标是否离散或样本很少。
2. prompt 是否在不同规模使用了不同模板。
3. benchmark 是否污染或有答案记忆。
4. 评估是否使用 pass@k、self-consistency 或额外工具。
5. 是否存在后训练和 instruction data 的差异。

因此，loss scaling 可以作为训练测量，不能替代能力测量和生产评估。

### 6.3 后训练和 test-time compute 也需要单独记账

当一个模型在后训练阶段变强时，新增资源可能来自多个地方：监督样本 token、偏好对、拒答和安全样本、rollout 轨迹、verifier 计算、拒绝采样以及评估时的多次生成。它们都可以提高最终结果，却不是同一种训练信号，不能简单并入预训练 token 后再声称模型遵循同一条 scaling 曲线。

可以把一个阶段的资源先写成：

~~~math

C_{stage}
\approx n_{example}\,\bar t\,r\,c_{token}
  +C_{rollout}+C_{verify}+C_{eval},

~~~

其中 $n_{example}$ 是样本数，$\bar t$ 是平均输入和输出 token，$r$ 是重复 epoch 或采样次数，$c_{token}$ 是该训练路径的单位 token 计算量。$C_{rollout}$、$C_{verify}$ 和 $C_{eval}$ 分别表示生成轨迹、验证答案和评估候选的计算。它们的量级在 reasoning 或 agent 训练中可能不再是可忽略的附属项。

推理阶段还可能使用 self-consistency、beam search、verifier reranking 或多次工具调用。此时单次回答质量和单次请求成本必须一起报告：

~~~math

C_{request}
=C_{prefill}+k_{decode}C_{decode}+C_{tool}+C_{judge},

~~~

$k_{decode}$ 是候选生成次数。若只比较最高分候选而不报告 $k_{decode}$，就会把额外 test-time compute 隐藏在“模型能力”里。研究者应把预训练、后训练和推理时的计算分别列账，再说明结果提升究竟来自参数、数据、训练信号还是额外搜索。

一个具体研究例子说明，推理计算也需要按题目难度分配。Snell 等人在 PaLM 2-S* 的数学任务中比较过程奖励模型搜索和逐步修订，观察到不同 test-time compute 策略的收益随 prompt 难度变化；按难度自适应选择策略，在其部分设置中可用约四分之一的计算超过 best-of-N，FLOPs 匹配时也有部分题目胜过约 14 倍大的预训练模型。最难题上，额外预训练在一些设定中仍更有效。这些结果覆盖论文中的模型、数学数据、verifier 和预算，不能直接推广为预训练与推理计算可普遍互换，见 [Scaling LLM Test-Time Compute Optimally](https://arxiv.org/abs/2408.03314)。

## 7. 训练稳定性是 scaling 的前提

### 7.1 不稳定的表现

大模型训练中的负结果，很多不是“规模不对”，而是训练没有稳定完成。常见信号包括：

1. loss 突然 spike 后无法恢复。
2. gradient norm 或 update norm 异常放大。
3. FP16/BF16 计算出现 NaN 或 Inf。
4. 某一层激活或权重幅度远超其他层。
5. validation loss 与 training loss 同时反转。
6. 某个 rank 通信或数据读取异常。
7. checkpoint 恢复后 loss 曲线发生不连续跳变。

训练曲线失真后，任何 scaling 拟合都不可靠。先确认训练状态，再谈模型和 token 的最优分配。

### 7.2 数值、优化、架构和系统四类稳定性

| 类型 | 典型原因 | 观察指标 | 典型处理 |
| --- | --- | --- | --- |
| 数值稳定性 | 精度、softmax、溢出、loss scaling | NaN/Inf、激活范围 | BF16/FP32 路径、稳定 kernel、检测与跳过 |
| 优化稳定性 | 学习率、warmup、batch、裁剪 | loss、grad/update norm | 调 schedule、clip、恢复策略 |
| 架构稳定性 | 深度、残差、归一化、初始化 | 层间尺度、梯度传播 | Pre-Norm、RMSNorm、residual scaling |
| 系统稳定性 | 通信、数据、checkpoint、rank | 吞吐、同步、恢复曲线 | 监控、重试、校验、断点恢复 |

同一个 loss spike 可能有不同根因，必须把时间线、rank 日志、数据 batch、精度和 checkpoint 绑定起来。

### 7.3 学习率、warmup 和 batch

AdamW 的参数更新可以抽象为：

~~~math

\theta_{t+1}=\theta_t-\eta_t\,\frac{\hat m_t}{\sqrt{\hat v_t}+\epsilon}-\eta_t\lambda\theta_t.

~~~

$\eta_t$ 是学习率，$\hat m_t$ 和 $\hat v_t$ 是一阶、二阶动量估计，$\lambda$ 是权重衰减系数。大 batch 可能提高吞吐和梯度估计稳定性，但也改变每个 token 对参数更新的次数和噪声结构；学习率不能只按 GPU 数机械线性放大。

Warmup 让训练从较小步长逐渐进入峰值学习率，帮助优化器状态和参数尺度建立稳定轨迹。若 warmup、有效 batch、sequence length 或 gradient accumulation 改变，训练 token 相同也不代表优化过程相同。

### 7.4 batch size 的收益存在临界区

增大 batch 会减少每个 epoch 的参数更新次数，并让一个更新使用更多样本；它不是单纯的“GPU 越多越快”。设单样本梯度为 $g(x)$，可以用一个简化的梯度噪声尺度描述信号和方差的关系：

~~~math

GNS
=\frac{\mathrm{tr}\,\mathrm{Var}[g(x)]}
       {\lVert\mathbb{E}[g(x)]\rVert^2}.

~~~

当有效 batch 小于某个任务和训练阶段相关的临界范围时，增大 batch 往往能减少梯度噪声；超过这个范围后，继续增大 batch 的吞吐收益可能无法抵消更新次数减少、通信增加和泛化变化。这个式子不是告诉我们一个跨模型通用的 batch 数，而是给出诊断问题：当前瓶颈是梯度噪声、设备吞吐、通信还是优化步数？

因此比较两个训练方案时，不能只保持“总 token 相同”。还要记录有效 batch、优化 step 数、每 step token、学习率、warmup token、梯度累积和样本顺序。否则一个方案可能因为做了更少但更大的更新而获得不同的优化轨迹，结果不能归因于模型规模或数据量。

### 7.5 稳定性事故的正确处理

发生 spike 后，不要立刻把异常 checkpoint 删除。应保留：发生时间、step、数据 batch、loss/grad/update、激活统计、精度溢出、通信日志、最近 checkpoint 和恢复尝试。先在小规模复现，再改变一个变量。

如果恢复后曲线重新接近预期，结论可能是某个 transient 系统故障；如果每次在相同 token 类型或长度桶上 spike，可能是数据或长度分布问题；如果只在更深模型出现，可能是架构和优化尺度问题。事故记录本身是 scaling 研究的一部分。

近期预印本还报告了一种更具体的候选机制：在现代化 GPT 结构、较高学习率和远超 Chinchilla token/parameter 比例的长程训练中，LM head 的有限精度误差可能与迟发 loss spike 同时出现。该研究覆盖 28M—1.4B 模型，并比较 BF16、混合精度和 FP32 路径；作者也测试了 LM-head 更新与 logits 稳定化方法。它为诊断提供了一个可检验假设，适用范围仍限于作者的模型、数据和训练设置，见 [The Role of Quantization in Loss Spikes](https://arxiv.org/abs/2610.38277)。更完整的异常检测、梯度裁剪与断点恢复流程见[第五册第九章](../../book-05-llm-training/chapters/09-训练稳定性与debug.md)。

## 8. 分布式训练：把理论规模落到系统路径

### 8.1 五类主要并行

大模型训练通常组合多种并行：

1. **Data Parallel**：每个设备处理不同样本，聚合梯度。
2. **Tensor Parallel**：把单层矩阵和 attention 计算切到多个设备。
3. **Pipeline Parallel**：把不同层放到不同设备，用 micro-batch 填充流水线。
4. **Optimizer/Parameter Sharding**：切分参数、梯度和优化器状态，降低单卡显存。
5. **Expert Parallel**：把 MoE expert 分布到设备，增加 token 路由通信。

这些方式改变的是系统执行路径，不只是显存数字。一个方案可能让单卡显存下降，却因为通信和 pipeline bubble 降低端到端吞吐。

### 8.2 吞吐、利用率和有效计算

训练吞吐可以粗略写成：

~~~math

\mathrm{Throughput}
=\frac{\mathrm{processed\ tokens}}{\mathrm{wall\ time}}.

~~~

如果已知理论峰值 FLOPs 为 $F_{peak}$、实际计算吞吐为 $F_{actual}$，可以定义简化的利用率：

~~~math

U=\frac{F_{actual}}{F_{peak}}.

~~~

MFU、HFU 等指标具体口径不同。常见的 MFU 以模型理论所需 FLOPs 与实际 tokens/s 估出的有效模型计算为分子，HFU 往往还把重计算等实际硬件操作计入分子；但不同论文可能有自己的 FLOPs 估算和稀疏路径约定，必须以原文定义为准。高 GPU utilization 也不一定代表高有效模型计算，kernel 可能在做 padding、通信等待或临时复制。

MegaScale 给出了一组可读的真实系统对照：175B 模型、序列长度 2,048、固定 batch 6,144，在 3,072—12,288 GPU 范围做强扩展实验。论文报告 MFU 从 59.1% 降至 55.2%；在 12,288 GPU 一点，MegaScale 与 Megatron-LM 的吞吐分别约为 1,984k 和 1,466.8k tokens/s，约 1.35 倍。MFU 变化和 tokens/s 比值使用不同的比较口径，不能互换。论文另报告的数周生产作业恢复数据属于作者自报运行记录，应与受控性能对照分开读，见 [MegaScale](https://arxiv.org/abs/2402.15627)。

### 8.3 通信和计算的临界路径

一个训练 step 的墙钟时间更接近关键路径上的非重叠部分，而不是把所有组件时间机械相加。若计算和通信可以部分重叠，一个简化表达是：

~~~math

T_{step}\approx
\max(T_{compute},T_{communication})
+T_{pipeline\ bubble}
+T_{input,\ unoverlapped}
+T_{checkpoint,\ unoverlapped}.

~~~

这里的 $\max$ 只表示计算和通信完全重叠时的理想化近似；真实系统还会有启动开销、同步等待和不完全重叠。网络拓扑、消息大小、并行切分和 batch 形状会改变结果。系统论文只在单层 kernel 上加速，不代表 $T_{step}$ 一定下降；如果通信没有被隐藏，计算 kernel 的局部加速可能只缩短了关键路径中很小的一部分。

下图把一个简化训练 step 中的梯度依赖和状态更新顺序画出来。反向计算产生的梯度可以分桶发送，因此通信可能与剩余计算重叠；同步完成后，优化器才能更新参数与状态。图中把 checkpoint 画在更新之后，便于区分训练状态和存储路径，但实际保存频率及其是否阻塞训练要以论文实现为准。

~~~mermaid
sequenceDiagram
    participant D as 数据流水
    participant C as 计算设备
    participant N as 通信组
    participant O as 优化器与状态
    participant K as Checkpoint 存储
    D->>C: 提供 micro-batch
    C->>C: 前向与反向计算
    par 继续计算
        C->>C: 计算尚未完成的层
    and 梯度通信
        C->>N: 同步已就绪的梯度 bucket
        N-->>C: 返回同步梯度
    end
    C->>O: 提交完整梯度
    O->>O: 更新参数与优化器状态
    opt 到达保存间隔
        O->>K: 写入 checkpoint
        K-->>O: 保存完成
    end
~~~

读图时先沿实线看数据和状态依赖：数据流水提供 micro-batch，计算形成梯度，优化器持有更新后的参数及动量状态，存储接收周期 checkpoint。再看 `par` 区段，它表示部分梯度通信可与剩余反向计算并行，并不意味着通信总能完全隐藏。若输入在计算开始前未准备好，或同步、写盘落在关键路径上，公式中的 input、communication 或 checkpoint 时间就会增加。预取、异步保存和不同并行策略会改变实际时序，因此图是用于读论文的最小路径图，不是所有训练框架的固定实现。

### 8.4 ZeRO 和状态分片的阅读重点

Adam 类优化器通常需要参数、梯度和一阶/二阶状态，混合精度还可能保留 FP32 master weights。ZeRO 等状态分片方法通过把这些对象分布到设备，降低单卡内存，但引入通信、重新聚合和 checkpoint 复杂度。

读这类论文应同时看：单卡显存、通信量、吞吐、扩展效率、容错、断点恢复和参数更新的数值一致性。只说“显存降低”不够，因为系统可能通过更多通信换来了这个空间。

## 9. 训练资源规划：从曲线到预算

### 9.1 时间和成本账本

如果目标训练计算为 $C$，集群理论峰值吞吐为 $F_{peak,cluster}$，有效利用率为 $U$，则训练时间可近似为：

~~~math

T_{train}\approx\frac{C}{F_{peak,cluster}U}.

~~~

若每小时集群成本为 $p$，基础训练的货币成本为：

~~~math

K_{train}=pT_{train}.

~~~

真实预算还要加入失败重试、验证、数据处理、checkpoint、存储、网络和人工排查。一次训练如果没有预留故障恢复和中间评估，理论上“最便宜”的方案可能在实际中最贵。

若训练集含有模型改写生成的数据，还要把生成这些 token 的计算计入预算。2026 年的一篇预印本提出 rewriting scaling law，在 FineWeb-Edu/FinePhrase 与指定 rewriter 的 compute-limited 设置中，估计的最优改写比例从 $3\times10^{18}$ FLOPs 时低于 10%，升到 $10^{22}$ FLOPs 时约 32%，并对最高预算做了 22B 参数外推验证。该拟合没有计入 rewriter 预训练成本，且比例受改写风格、语料和 loss 指标影响；因此它提供的是预算记账案例，不是数据配方，见 [Rewriting Scaling Laws for Synthetic Data](https://arxiv.org/abs/2610.31867v1)。训练成本和利用率的更多定义见[第五册第十三章](../../book-05-llm-training/chapters/13-训练成本与资源规划.md)。

### 9.2 Scaling 实验的阶段性预算

不要一开始就把所有预算投入目标规模。可以按阶段分配：

1. **协议阶段**：验证 tokenizer、数据 loader、loss、mask、checkpoint 和评估。
2. **稳定性阶段**：小模型短训练，故意检查精度、长序列、恢复和异常 batch。
3. **曲线阶段**：多个 $N,D$ 组合，拟合趋势和估计方差。
4. **目标阶段**：只运行最有信息量的候选方案。
5. **确认阶段**：目标规模多 seed、独立评估、成本和系统压测。

每阶段都要有“进入下一阶段需要观察到什么”。否则小规模实验容易变成没有结论的预热，大规模实验容易变成昂贵的盲跑。

## 10. Scaling 论文的复现方法

### 10.1 复现对象要收窄

完整复现一篇大规模 scaling 论文通常不可行，但可以复现一条明确 claim：

- 在固定 compute 下，增加 token 是否比增加参数降低验证 loss？
- 在一个小模型族中，loss 是否接近幂律下降？
- 某种数据配比是否改善指定能力而不损害护栏？
- 某种训练系统在相同硬件和 batch 下是否降低 step time？
- 恢复训练后 loss 是否回到断点前轨迹？

每条 claim 都要指定模型族、数据版本、训练 token、评估对象、资源上限和成功标准。这样一个小规模实验也能产生可复查的证据，而不是只得到“趋势大概类似”。

### 10.2 实验矩阵

一个最小 scaling 矩阵可以让模型规模和 token 数各取三个水平：

| | $D_1$ | $D_2$ | $D_3$ |
| --- | ---: | ---: | ---: |
| $N_1$ | loss/成本 | loss/成本 | loss/成本 |
| $N_2$ | loss/成本 | loss/成本 | loss/成本 |
| $N_3$ | loss/成本 | loss/成本 | loss/成本 |

对每个格子记录训练曲线、最终 loss、验证切片、FLOPs、GPU 时间、吞吐、峰值显存、异常和 checkpoint。只跑对角线，例如小模型少 token、大模型多 token，无法区分模型和数据的边际影响。

### 10.3 外推验证

拟合点和验证点必须分开。可以保留一个未参与拟合的 token 水平，或者在另一个模型规模上验证预测。外推误差可以写成：

~~~math

E_{extrap}=|L_{observed}-L_{predicted}|.

~~~

如果外推误差随着规模增加而变大，不应继续用同一模型规划更大训练；要检查是否进入了新数据、优化、架构或系统 regime。

## 11. Worked case：固定计算预算下的模型/数据选择

### 11.1 教学目标

假设有一个抽象计算预算，候选方案包括小模型多数据、中模型中等数据和大模型少数据。用教学 loss 函数：

~~~math

L(N,D)=1.2+0.8N^{-0.30}+0.55D^{-0.27},
\qquad
C=6ND.

~~~

这里 $N$ 和 $D$ 用同一教学单位，$1.2$、$0.8$、$0.55$ 和指数只是合成参数。比较的重点不是数值，而是同一计算约束下，参数和 token 的分配改变了 loss。

### 11.2 读表而不是背比例

若预算为 $C\leq600$，可以比较：

| $N$ | $D$ | $C=6ND$ | 教学 loss |
| ---: | ---: | ---: | ---: |
| 2 | 50 | 600 | 2.0411 |
| 4 | 25 | 600 | 1.9584 |
| 8 | 12.5 | 600 | 1.9068 |
| 1 | 100 | 600 | 2.1586 |

约束 $C=6ND\leq600$ 可以先化成 $ND\leq100$，所以表中的四个组合都刚好用满预算。以 $N=8,D=12.5$ 为例，$8^{-0.30}\approx0.536$，乘上 0.8 得到约 0.429；$12.5^{-0.27}\approx0.506$，乘上 0.55 得到约 0.278。将两项与 loss floor 1.2 相加，得到约 1.907，与表中 1.9068 的四舍五入结果一致。对照 $N=4,D=25$，两项约为 0.528 和 0.231，proxy loss 约 1.958；在此教学函数中，多给参数、少给 token 的候选低约 0.052 个 loss 单位。

这一步解释的是代理函数本身：$N$ 项的指数和系数决定扩大模型的边际收益，$D$ 项决定增加 token 的边际收益，而预算把二者绑定在同一乘积上。当前例子没有真实训练观测、seed 方差、语料质量或下游切片。表格只比较预先选出的候选点；函数系数、候选网格或目标指标改变后，排序也可能变化。因此教学结论应限定为“该合成函数在当前候选集中偏好 $N=8,D=12.5$”，不延伸到真实模型的 compute-optimal 比例。

在这个合成函数中，$N=8,D=12.5$ 的点在所列候选中得到最低 proxy loss。代码中的名称 `large_fewer_tokens` 只描述相对于其他点的参数/token 分配；训练是否不足要靠真实训练曲线和目标 loss 判断。最优点取决于 loss 曲线参数，数据质量、架构或目标任务变化后，排序也可能变化。这个例子展示如何在预算内选择候选，结果范围限于当前函数和候选集合。

候选点之间的差值也需要正确解释：$N=8,D=12.5$ 比 $N=4,D=25$ 低约 0.052 proxy loss units，但这个函数没有估计随机种子方差和测量误差，所以不能把差值描述成稳健或显著的真实效果。若做真实实验，应该先用小模型点拟合参数，再在固定 compute 的边界附近增加候选，保留一个规模或 token 组合验证预测。每个点还要保存数据版本、训练曲线、真实 FLOPs 估算和下游切片；只有在这些条件相同或可解释时，才把排序用于预算选择。

目标指标也会改写这个选择。如果服务关注代码生成，研究者可以在同一训练预算下并列记录 validation loss、单元测试通过率和生成 token 成本；若代码能力改善但语言 loss 变差，就要明确这是任务之间的预算交换。token 和 FLOPs 的换算还需要公开 tokenizer、序列长度和激活参数口径。这样，读者能从一个代理函数结果走到可执行的复现实验，而不是把 proxy loss 当成全部模型价值。

预算表也应说明失败与评估占用。若某个方案需要更多次稳定性重跑，理论训练 compute 相同，成功交付 checkpoint 的实际成本仍会上升；若下游评估只对一个方案做得更充分，比较也会偏向它。真实计划应在每个候选旁记录预留的验证、checkpoint 和重试预算，并按“每个可用 checkpoint 的总成本”复查排序。

预算约束会形成一条 $ND=100$ 的候选边界，但在实际训练里，算量未必真是 $6ND$：attention 长度、MoE 路由、重计算、通信和失败重试都会改动实际时间。为了让候选公平，先确认 compute 预算是理论 FLOPs 还是实测 GPU 小时，再把各方案换算到同一口径。若一个候选因数据加载较慢而花了更久，即使公式给出相同 $C$，真实总预算也没有用满同样资源。这样读者可以区分“约束下的数学比较”和“训练作业的资源比较”。

### 11.3 训练最优和生命周期最优的分叉

假设大模型的 loss 略低，但每次请求成本高 4 倍；小模型 loss 略高，却能服务更多请求并降低 P99。若产品对质量差异不敏感，生命周期成本可能偏向小模型；若高价值任务每次错误代价很高，大模型可能更合适。Scaling 论文给出的训练点需要进入产品 workload 后重新计算。

## 12. Worked case：训练 spike 的证据链

下面是一个构造的 70B 故障回放，用来示范如何从症状缩小根因；它不是公开训练事故记录。假设 step 179,999 的验证前 loss 为 2.1，step 180,000 输入一批长序列后瞬间到 8.7，下一次更新产生 NaN。单看这两个值，模型规模、数据长度、精度、mask、optimizer 和 kernel 都仍是候选因素。

1. 检查 step 180,000 的数据 batch，发现其中长序列比例异常升高。
2. 检查 attention mask 和 loss reduction，确认实现没有改变。
3. 查看 grad norm 和 activation range，发现某些层在 spike 前已经持续增大。
4. 对比其他 rank，发现所有 rank 同步出现变化，排除单机通信故障。
5. 在小模型上重放该 batch，发现 BF16 路径溢出，FP32 路径正常。
6. 使用稳定 kernel 和裁剪策略重跑，曲线恢复到原趋势。

结论应写为：“当前精度和长序列 batch 组合在该状态范围内数值不稳定；修正 kernel 与异常 batch 处理后，需要重新验证目标规模曲线。”这个表述定位了根因，也保留模型规模和训练配方的证据边界。

要让这段回放真正可复核，先冻结异常前的 checkpoint、数据样本 ID、tokenizer、mask、随机状态、optimizer state、所有 rank 日志和代码 revision。再按时间戳把 loss、grad norm、update norm、激活范围、溢出计数和 sequence-length histogram 对齐。若同一批次的 BF16 重放再次出现 spike，而 FP32 重放没有出现，证据支持有限精度路径参与故障；它仍不能区分具体是 attention kernel、归约顺序还是某层 activation 的数值范围。

接下来每次只改变一个因素：先固定 batch 和 kernel 改精度，再固定精度改 kernel，最后测试长度分桶或梯度裁剪。每个条件都用相同 checkpoint 与 batch replay，保留未失败的完整运行，检查修复是否改变正常短序列的 loss 和吞吐。若只改精度和裁剪后曲线恢复，仍需在目标配置的多个 seed 和长程 token 窗口复验；单次恢复的证据只支持局部诊断，修复的普遍性要由目标配置复验确认。这样，负结果会变成一条“异常信号—隔离变量—反事实重放—目标规模复验”的证据链。

还可以把一个对照窗口具体化。假设前 20 个 step 的长序列占比为 10%，loss 保持在 2.1 左右，grad norm 中位数为 1.2；异常窗口中长序列占比升到 40%，loss 峰值为 8.7，grad norm 达到 18 并随后溢出。这个关联给出重放对象，却尚未证明“长序列导致 spike”，因为长度、精度和 kernel 可能同时变化。用同一批样本逐项重放，并确认其他 rank 的日志和输入完全一致，才能把数据长度和数值路径分开。所有这些比例、阈值和日志数值仍是教学构造输入。

如果只把失败 checkpoint 删除并从更早位置重启，训练曲线可能短暂恢复，却丢失了最有信息量的异常状态。应记录发生概率、恢复所需时间、丢弃 token 和重算成本；若同类失败出现三次，每次重跑前都要说明本轮改变了什么。这样可以判断问题是否集中于特定长度桶、精度模式或训练阶段，并决定是修改数据打包、数值实现还是优化 schedule。事故案例的成果是可检验的故障假设和回归条件，模型大小只是候选因素之一。

本例中 loss 从 2.1 到 8.7，绝对上升 6.6，瞬时比值约为 4.14；这个比值描述异常幅度，仍不能单独识别根因。若 grad norm 从 1.2 到 18，约增至 15 倍，可将梯度放大列为并行信号，并检查每层 update/activation 是否在 loss spike 前已经漂移。若其他 rank 在同一 microbatch、同一 token 区间出现相同波形，数据或共享计算路径更值得优先验证；如果只有一个 rank 先异常，则检查局部输入、显存错误和通信状态。时间对齐能减少把同时发生误当成因果的风险。

操作结束时要保存一份事故摘要：最后稳定 step、最早异常 tensor、复现所需的最小 batch、排除过的替代解释、采用的修复、恢复后损失变化、额外重算 token 和仍未验证的规模范围。下一轮训练先跑小型回归用例，再以目标长度和精度做延长稳定性试验。只有通过这些门槛后，才把当前配方恢复到 scaling 曲线拟合中；失败区间仍留作训练稳定性证据。

## 13. Worked case：分布式扩展没有带来线性加速

下面是一个固定全局 token batch 的构造强扩展示例。训练系统从 64 GPU 扩展到 256 GPU，设备数增加 4 倍；step time 从 10 秒降为 4.2 秒，只有原来的 0.42 倍。吞吐加速比是 $10/4.2\approx2.38$ 倍，相对理想 4 倍的并行效率约为 $2.38/4\approx59.5\%$。若每步都处理 262,144 token，吞吐从约 26,214 token/s 升到约 62,415 token/s，数值与 2.38 倍加速一致。

再看一个与该总时间匹配的 256-GPU 关键路径剖面：计算段 3.1 秒，通信段 2.4 秒，其中 1.5 秒与计算重叠，因此暴露通信时间约 0.9 秒；pipeline bubble 为 0.4 秒，输入等待 0.3 秒，checkpoint 暂停 0.4 秒。按 $\max(3.1,2.4)+0.4+0.3+0.4$ 复算，step time 为 4.2 秒。所有数字均是教学构造值；它展示了为什么只将 GPU 数乘四会高估实际扩展。

理想情况下，64-GPU 的 10 秒 step 扩展到 256 GPU 应接近 2.5 秒；当前示例多出的 1.7 秒落在未隐藏通信、流水线空泡、输入供给和 checkpoint 上。把这段时间视为同一口径下的关键路径，才能决定下一轮要测哪一个变量。如果 all-reduce 暴露量随 tensor-parallel 组增加，先测更好的拓扑或通信融合；如果 pipeline bubble 占比增加，先改变 micro-batch 和 stage 切分；如果输入等待或 checkpoint 占主导，增加 GPU 并不会改善这些路径。

本例属于 strong scaling：总 global batch 固定，设备数增加，问题是同一工作量能缩短多少 wall time。若改成 weak scaling、让每张 GPU 仍处理原来的 batch，总 token 数会随设备数增加，此时要比较 tokens/s、每 token 成本和最终 loss，而不能把 step time 单独当成效率。实际论文还应记录 warmup、测量区间、同步方式、平均值与尾部分位数；单次最快 step 可能避开了数据加载或保存开销。

并行效率也能从原始时长复算：理想设备数增加 4 倍时，10 秒 step 应缩至 2.5 秒；观察到 4.2 秒，实际时长是理想值的 $4.2/2.5=1.68$ 倍，效率为 $2.5/4.2\approx59.5\%$。这与 $10/(4\times4.2)$ 得到的比例一致。报告时应明确这里用的是固定工作量下的 step wall time，不把它和 MFU、GPU utilization 或弱扩展 tokens/s 混为同一指标。

在真实系统中，扩展测试最好选取多个 GPU 数和多次重复 run，记录每个点的均值、波动范围、显存、通信字节、数据 loader 等待和 checkpoint 暂停。若只比较 64 与 256 两点，无法判断效率是逐渐下降，还是某个并行阈值后出现跳变。还要固定 checkpoint 频率、故障注入和保存策略；吞吐以外，长程训练需要知道异常恢复后是否能延续相同 loss 轨迹。

如果研究目标是最终下游质量，也要确认扩展比较期间优化步数、全局 token、学习率 schedule 和训练时长是否固定。缩短 step time 只有在完成同等训练工作量时才代表省时；若大规模配置同时增加有效 batch 或减少更新次数，最终 loss 变化就混入优化策略。系统加速应与训练终点的质量和不确定性一起报告。

系统分析显示：

- tensor parallel 的 all-reduce 占比随设备数增加。
- pipeline parallel 出现更长 bubble。
- data loader 在高并发下供给不足。
- checkpoint 保存暂停时间没有按设备数下降。

该结果表示当前实现的强扩展效率约为 59.5%。下一步应拆开计算、通信、输入、pipeline、checkpoint 和失败恢复的时间；若降低 checkpoint 频率来提高 benchmark 吞吐，也要同时报告恢复风险和实际训练时间。

一个可靠系统论文结果至少需要单步时间分解、端到端 tokens/s、扩展曲线、峰值显存、通信量、网络拓扑和故障恢复，而不是只给一个 kernel speedup。

把同一口径用到真实论文时，还要确认扩展实验固定的是全局 batch、序列长度还是每卡 batch。MegaScale 的 175B 强扩展报告固定 batch 6,144 和 2,048 序列长度，测试 3,072—12,288 GPU，并同时报告 MFU 与端到端 tokens/s；两项指标的增幅并不相同。由此可以把本节构造的 59.5% 理想效率计算与论文的实测扩展分开：前者训练手算，后者绑定其集群、并行策略和测量范围。

如果论文只给出 GPU 数与峰值 MFU，仍要追问测量是稳定训练窗口、单步 kernel，还是包含数据输入和 checkpoint 的端到端时间。相同吞吐可能由不同 batch、序列长度和精度得到，不能直接当成同等训练质量；相同 MFU 也不意味着每秒 token 相同。读表时先找清工作量、设备拓扑和计时边界，再计算每步时间与 tokens/s，最后把质量终点和失败恢复成本接上。若来源没有披露其中一项，就把它写作未报告，而不是从图表反推。

## 14. 可运行的 scaling 预算 demo

下面的代码用合成幂律近似比较候选模型/数据组合。它计算教学 loss 与训练计算 proxy，再筛选给定预算内的方案；所有规模都以无量纲教学单位表示，不换算 GPU 小时。它不拟合真实模型，也没有纳入数据质量、通信和后训练能力。

状态：静态审阅，未运行（2026-11-04；Python 3.7+，仅标准库）

~~~python
from dataclasses import dataclass


@dataclass
class Plan:
    name: str
    params_units: float
    tokens_units: float

    def __post_init__(self):
        if self.params_units <= 0 or self.tokens_units <= 0:
            raise ValueError("parameter and token units must be positive")

    @property
    def compute_units(self):
        return 6.0 * self.params_units * self.tokens_units

    @property
    def proxy_loss(self):
        return (
            1.20
            + 0.80 * self.params_units ** -0.30
            + 0.55 * self.tokens_units ** -0.27
        )


budget = 600.0
plans = [
    Plan("small_more_data", 1.0, 100.0),
    Plan("balanced", 2.0, 50.0),
    Plan("medium", 4.0, 25.0),
    Plan("large_fewer_tokens", 8.0, 12.5),
    Plan("over_budget", 8.0, 20.0),
]

feasible = [plan for plan in plans if plan.compute_units <= budget]
if not feasible:
    raise ValueError("No candidate plan fits the compute budget")

best = min(feasible, key=lambda plan: plan.proxy_loss)

for plan in feasible:
    print(
        f"{plan.name}: compute={plan.compute_units:.1f}, "
        f"proxy_loss={plan.proxy_loss:.4f}"
    )
print(f"best_under_budget={best.name}")
print(f"best_proxy_loss={best.proxy_loss:.4f}")
~~~

手算代码输出时，前四个候选的 compute 都为 600.0，`over_budget` 为 960.0，因而不会进入可行列表。对应 proxy loss 依次为：`small_more_data=2.1586`、`balanced=2.0411`、`medium=1.9584`、`large_fewer_tokens=1.9068`。预期选择是 `best_under_budget=large_fewer_tokens`，`best_proxy_loss=1.9068`；这些值与 §11 的公式和表格使用相同输入。这里的预期是按表达式逐项静态核算，代码没有执行。

逐行看输入输出可以复核实现意图：每个 `Plan` 保存名字、参数单位和 token 单位；`compute_units` 用 $6ND$ 给出 proxy 预算，`proxy_loss` 复用 §11 的函数；列表推导式只保留未超出 budget 的候选，`min` 再按 proxy loss 选最小值。以 `medium` 为例，compute 是 $6\times4\times25=600$；loss 两项约为 $0.8\times0.660=0.528$ 与 $0.55\times0.419=0.230$，加上 1.20 后约为 1.958，与表格一致。这个手算让读者可以把表格计算、函数字段和筛选分支逐项对照。

代码中的名称使用 `params_units`、`tokens_units`，避免把这些合成输入看成真实 B 参数或 B token。若 budget 改为 500，所有候选都不满足约束，代码会明确抛出 `ValueError`；若改为 960，`over_budget` 会进入可行集合，按同一函数得到 1.8737，但它使用了比 600 多 60% 的预算，loss 更低不能被解释成相同资源下的胜出。运行时长还要输入集群吞吐和利用率，本 demo 没有这些字段，因此不会输出小时或美元成本。

`__post_init__` 同时拒绝零或负的参数/token 输入，避免负指数产生无效 proxy loss。代码围栏使用标准库 `dataclasses`，预期运行环境为 Python 3.7+；本轮只检查了字段名、筛选顺序、异常分支和公式输入，没有执行代码。若将候选组合扩展到更大规模，读者还要设置清晰的精度、近似容差和单位，避免把浮点输出的末位差异当作模型差异。

输出把 compute 保留一位小数、loss 保留四位小数，目的是方便预算筛选和读表；它不具备 loss 拟合置信区间或校准误差。复现时可以先检查每个候选的 $C$ 是否满足阈值，再检查 `min` 按哪一个字段排序，最后用 §11 的手算值核对四位输出。如果改了指数或系数，应重新计算每个候选和最优行，正文中的预期输出也要随之更新。把模型点加入列表会改变有限候选集的最优值，程序本身没有搜索连续空间或证明全局最优。

候选筛选还暴露了一个边界：若预算低于 600，列表可能为空，直接调用 `min` 会报错。代码先给出明确的 `ValueError`，避免把无可行解误报成某个最优点。读者可以改变预算、loss 系数或候选组合，观察筛选集合如何变化；改动后的结果仍只属于该合成函数。真实 scaling 实验还要用验证 loss 拟合参数、记录质量切片与 seed 方差，并加入硬件吞吐、训练失败概率、后训练能力和服务成本。

读者还可以做一个小型敏感性检查。预算保持 600，先把 $N$ 项系数 0.80 分别改为 0.75 和 0.85，重算四个可行点；再恢复原值，只扰动 $D$ 项系数 0.55。记录获胜候选和第一、第二名的 proxy loss 差距是否稳定。这里的扰动幅度只是教学输入，不是系数置信区间；若很小的改动就改变胜者，结论应是候选排序对假设敏感，下一轮实验要增加边界附近的模型/数据组合并用独立点校验，而不是把当前最低值写成通用答案。

这也说明 demo 的最优对象是有限列表，不是所有参数和数据组合。在真实项目中，可把每个列表项映射到训练配置，记录版本、预计 token/FLOPs、可用 GPU 时间、评估预算和失败重跑上限。先筛掉违反硬约束的方案，再对剩余方案做受控训练；如果一个方案只有在忽略验证、保存或失败成本时才可行，预算账本应将其标成不满足项目约束。手算与代码输出负责核对筛选逻辑，实测训练负责检验 loss 近似，两者的职责不能互换。

## 15. Scaling 论文的报告结构

一份可复查的 scaling 报告应包含：

1. **目标**：预测 loss、规划 compute、比较数据配比，还是解释能力变化。
2. **模型族**：层数、宽度、参数、架构、tokenizer 和初始化关系。
3. **数据**：来源、质量、配比、去重、污染、时间和有效 token。
4. **计算**：FLOPs 口径、GPU、精度、重计算、通信和失败重试。
5. **训练**：optimizer、batch、学习率、warmup、decay、clip 和 checkpoint。
6. **测量**：loss、下游能力、切片、吞吐、显存、稳定性和成本。
7. **拟合**：函数形式、拟合点、验证点、残差和外推误差。
8. **边界**：模型规模、长度、数据、硬件和后训练阶段的范围。
9. **决策**：选择哪个预算点，放弃了什么，下一步如何验证。

其中“训练了多少 token”远远不够。没有数据版本和训练状态，读者无法判断 token 是否重复；没有硬件和通信，无法判断吞吐；没有拟合范围和 held-out 点，无法判断外推。

用 §11 的合成预算例可以看出报告字段怎样落到具体结果。目标是比较固定 proxy compute 下的参数/token 分配；对象是定义好的 $L(N,D)$ 函数；四个候选都满足 $C=600$，而第 8/12.5 点的 proxy loss 为 1.9068。这个结果只描述教学搜索空间，未涉及真实模型、训练数据、随机种子、硬件或验证集，因此应标作“解析式候选比较”。

如果把相同问题变成真实实验，报告还须把每个点映射到可运行配置：非 embedding 参数如何计数、每个 token FLOPs 怎样估算、训练集的 tokenizer 和去重版本是什么、固定 compute 时数据量如何换算、optimizer 和学习率是否沿同一规则调整。测量栏应保留训练曲线和多次 seed，而非只摘最终 checkpoint；拟合栏应显示哪些点参与估计、哪些点只用于预测检验。这样读者可以判断差异来自规模分配、数据配比还是训练稳定性。

同一报告还要把生命周期目标写出来。若模型主要用于少量实验请求，训练损失可能是主要决策指标；若上线后面对大量请求，输入/输出 token 长度、批处理、推理 MFU、并发和质量容差会改变总成本。可以同时给出训练预算和部署成本两张账本，再说明决策权重来自什么业务要求。报告不需要把所有成本合成一个来历不明的总分；保留单位、分母和约束，才能让读者按不同目标重新计算。

把 §11 的构造例改写成报告时，可以明确写出：目标是比较固定 proxy compute 下的候选分配；四个候选的教学预算均为 600，最低 proxy loss 是 1.9068；输入规模是无量纲单位，数据质量、seed、硬件吞吐和真实训练曲线均未测量。这样读者不会把一个公式筛选结果误读成训练实验。若真实研究也缺少某项指标，应注明“未测量”或“未报告”以及缺失原因，不能用 proxy 值补成实测证据。

对于有多个数据域的研究，报告还要保存每个域的定义、来源版本、抽样或混合比例、重复与过滤规则，以及比例是在 token、样本还是训练步层面定义。仅记录“用了 30% 代码数据”仍无法复现：不同 tokenizer、去重策略或采样顺序可能带来不同有效 token。若对比的是 mixture scaling，应同时报告目标能力的验证切片及混合比例随模型规模、训练阶段的变化；否则总体 loss 可能掩盖某个域变差。这个数据账本使其他团队能区分配比效应与语料版本、质量或训练预算变化。

拟合字段也需要能追溯到具体点：列出哪些模型规模和 token 预算参与拟合，哪些点留作验证，损失函数和参数约束如何选择，残差最大的点是否保留。若先看完所有点再挑一组“更符合幂律”的样本，报告应披露筛点规则及其发生时间。预测误差不能只用训练集残差代替；读者至少要看到拟合范围、验证点偏差和结论适用的规模区间。这样报告表能支持复查，而不只是包装一个最终参数比例。

## 16. 把 scaling 结论写成可审查的研究判断

一张 loss 曲线本身不是结论。研究者需要把曲线转译成一条可以被别人检查的判断链：观察到了什么，在哪些条件下观察到，哪些替代解释被排除了，它能支持哪个决策，又不能支持哪个更强的说法。

### 16.1 先区分观察、解释和决策

假设一个小模型族在固定数据和优化配方下训练，验证 loss 随参数量下降。最弱、也是最可靠的表述是：“在本实验范围内，参数量增加与验证 loss 降低同时出现。”这只是观察。

如果训练曲线、残差、不同 seed 和 held-out 模型规模都支持同一趋势，才可以进一步写成：“在给定模型族、数据分布和计算口径内，幂律模型对验证 loss 提供了有用的近似。”这是带条件的解释。

只有当预测误差、训练成本、系统吞吐和目标任务都被纳入，才能形成资源决策，例如选择某个模型/数据点继续训练。即使决策是合理的，也不能把它改写成“更大模型在所有任务上都更好”。决策的成立范围通常比宣传语窄。

### 16.2 一个 scaling claim 的证据卡

可以为每条重要主张保留一张简短证据卡。它不是流程开关，而是让读者知道结论由哪些材料组成：

| 字段 | 应记录的内容 |
| --- | --- |
| 主张 | 在什么条件下，哪个变量对哪个结果产生什么趋势 |
| 对象 | 模型族、tokenizer、数据版本、训练目标和硬件 |
| 观测 | loss、下游切片、吞吐、显存、成本和失败状态 |
| 对照 | 固定了什么，改变了什么，是否有二维矩阵和强 baseline |
| 不确定性 | seed 差异、测量误差、拟合残差和 held-out 外推误差 |
| 替代解释 | 数据质量、污染、优化不稳、prompt、通信或评估偏差 |
| 边界 | 不能外推到哪些模型、数据、阶段和生产流量 |
| 决策 | 选择、暂停、重做或继续收集哪一种证据 |

这张卡的价值在于把“曲线看起来不错”拆成可复核字段。若替代解释还没有被测量，结论就应保留为证据不足，而不是用更长的文字掩盖缺口。

跨论文比较也要把主张拆开。两篇工作都写“数据效率更高”，不代表它们测量了同一件事：一篇可能按达到某个 validation loss 的训练步数计，另一篇可能按固定 token 下的多域准确率计。只有模型族、数据版本、计算口径、目标指标和测量窗口足够接近，才适合做数值排序；否则应分别陈述各自支持的结论，并指出哪些条件无法对齐。报告若只保留“提升百分比”，读者就无法判断提升来自数据、模型还是分母变化。

### 16.3 从论文结果到项目预算

把论文结果用于项目规划时，可以按三步转换。第一步，将论文的计算单位映射到本项目：确认 FLOPs、精度、重计算、通信和失败重试是否采用相同口径。第二步，将论文的训练目标映射到本项目：确认验证 loss 是否仍是主要目标，还是需要代码、数学、工具、安全和多语言切片。第三步，把训练预算放进生命周期账本，加入服务请求量、推理延迟、存储、维护和回滚成本。

例如，某个候选点在合成幂律上拥有最低 proxy loss，但它使用更大的模型、更多的推理显存和更高的请求成本。研究报告应同时给出“训练目标上的预测优势”和“部署目标上的新增成本”，再说明为什么这个 trade-off 符合项目目标。若只有前一半，读者无法判断这个 scaling 结果是否值得采用。

### 16.4 写出有边界的结论

一段成熟的结论通常包含四个连续句子：先说明观测范围，再说明主要趋势；然后说明最重要的不确定性和替代解释；最后给出下一步验证或资源决策。它不需要把所有数字重复一遍，却必须让读者知道哪些是论文事实、哪些是本次复现实验、哪些只是教学近似。

对 scaling 论文而言，真正有价值的阅读结果不是记住一个参数/token 比例，而是能够判断一条曲线是否回答了当前问题。若研究对象从预训练 loss 换成后训练能力、agent 成功率或线上单位成功成本，原来的曲线必须重新定义数据、计算和评估对象。

把证据卡应用到 §11 的候选选择，可写出一条完整而有限的判断链。第一，观察是四个合成候选都用满 600 个 proxy compute units，proxy loss 依次下降到 1.9068。第二，解释是当前函数中的 $N^{-0.30}$ 项在该候选范围内带来的下降，大于相应的 $D^{-0.27}$ 变化；这不是对真实参数和 token 的因果估计。第三，替代解释包括函数系数是人为设定、候选网格只取四点、没有 seed 方差、没有数据质量差异，也没有 held-out 点检验拟合外推。第四，决策只能是把这一点列为下一轮真实训练候选，并在相同目标 compute 下增加相邻的 $N,D$ 组合。

下一轮若要把候选升级为研究结论，需要先固定模型族、数据 snapshot、tokenizer、训练目标和 FLOPs 口径，再按二维实验矩阵改变 $N,D$。每个预算区域应保留足够的训练曲线和验证切片；从拟合点之外留出一个模型规模或 token 水平，记录预测与实测差异。多个 seed 用来观察训练噪声，质量/语言/代码切片检查总体 loss 改善是否掩盖目标能力回退。若 held-out 点偏离，就把外推范围收回并拟合新的区间，而不是删除不合预期的样本。

最后，报告要让“观察、解释、决策”保持不同强度。观察陈述描述所测模型、预算、数据和指标；解释陈述需要机制或多个受控结果支撑；资源决策还要加入 serving 请求、延迟、显存和维护成本。比如“本拟合预测 N=8、D=12.5 的 loss 最低”只是一项模型输出；“该候选在真实训练中优于其他点”需要新实验；“它适合部署”还需要目标硬件和流量数据。按这三层写结论，读者可以知道哪一部分已经由证据支持、哪一部分仍是下一轮假设。

可以用一个明确标为假设的 held-out 情景检查报告是否保留了预测误差：假设拟合预测验证 loss 为 1.95，而独立训练点测得 2.04，绝对残差是 $|2.04-1.95|=0.09$，以实测值为分母的相对误差约为 $0.09/2.04\approx4.4\%$。这个单点只说明该位置的预测偏差，不能替代多 seed 不确定性，也不能证明更大规模的误差仍是 4.4%。报告要保留残差方向、规模位置和数据条件，再检查相邻验证点是否系统偏离；若高规模点连续低估 loss，应收回外推范围或重新拟合，而不能只强调平均误差较小。

结论还应写出可能推翻它的观察。若某个改进来自数据质量，改变 mixture 后效果应在目标域切片上按预期变化；若来自更大的参数规模，则应在控制数据、token 预算和训练 recipe 后仍可复现。一个声称“总体质量提高”的实验若只看总 loss，却没有代码、多语言或长尾域切片，仍留下重要替代解释。报告可以将这些条件写成下一步对照，而不是把未验证机制放进结论句。

当证据还不够时，决策也可以是暂停扩大训练。比如拟合点表现稳定，但 held-out 预测偏差超过项目容忍度，下一步的价值可能来自增加中间规模点或改进数据切片，而非继续增加 GPU。应记录什么误差会触发重拟合、什么质量退化会触发停止，以及谁承担额外复现实验成本。把停止规则和扩大预算的理由一并报告，才能避免只展示成功曲线、把资源投入本身误当作结论强度。

## 17. 资料与证据边界

经验 scaling law 主要参考 [Scaling Laws for Neural Language Models](https://arxiv.org/abs/2001.08361)。论文支持其特定模型、数据和计算范围内的拟合与预测；幂律公式在本章中用于教学解释，不代表跨架构和跨任务的物理定律。

大 batch 与梯度噪声尺度的讨论参考 [An Empirical Model of Large-Batch Training](https://arxiv.org/abs/1812.06162)。该论文支持把梯度噪声、batch size 和训练效率作为相互关联的研究对象；本章的 $GNS$ 公式和“临界区”表述是教学化记账，不能据此推出所有模型的统一 batch 上限。

GPT-3 的规模和 in-context learning 讨论参考 [Language Models are Few-Shot Learners](https://arxiv.org/abs/2005.14165)。论文支持其公开实验中的规模、few-shot 设置和任务结果；prompt 选择、污染、成本和后续模型的外推需要独立分析。

compute-optimal 讨论参考 [Training Compute-Optimal Large Language Models](https://arxiv.org/abs/2203.15556)。它支持特定训练设置下参数与 token 联合分配的研究结论，不应被压缩为所有模型和所有产品固定适用的参数/token 比例。

训练与推理生命周期成本参考 Sardana 等人的 [Beyond Chinchilla-Optimal](https://arxiv.org/abs/2401.00448)。论文以 47 个 MPT 风格模型拟合质量曲线，并在若干高推理请求情景中比较训练/服务成本；请求长度、MFU、价格和质量约束属于作者模型假设，结果不能直接移植到其他部署预算。

数据混合和数据预算可参考 [DoReMi: Optimizing Data Mixtures Speeds Up Language Model Pretraining](https://arxiv.org/abs/2305.10429) 与 [DataComp-LM](https://arxiv.org/abs/2406.11794)。它们支持数据配比和数据质量需要单独研究的事实；具体 mixture 仍依赖目标能力、数据许可、污染和评估分布。

更近期的配比和质量研究包括 ICLR 2025 的 [Data Mixing Laws](https://proceedings.iclr.cc/paper_files/paper/2025/hash/cc84bfabe6389d8883fc2071c848f62a-Abstract-Conference.html)、NeurIPS 2025 的 [Scaling Laws for Optimal Data Mixtures](https://proceedings.neurips.cc/paper_files/paper/2025/hash/bc1d640f841f752c689aae20b31198c1-Abstract-Conference.html) 和 ICLR 2026 的 [Scaling Laws Revisited](https://proceedings.iclr.cc/paper_files/paper/2026/hash/d0c80a0c294a16190c8904b9809c5fba-Abstract-Conference.html)。它们分别把来源比例、目标域权重或受控的数据质量纳入拟合；指标、域划分和预算仍受各自实验设置约束。EMNLP 2025 的 [Demystifying Synthetic Data in LLM Pre-training](https://aclanthology.org/2025.emnlp-main.544/) 比较自然网页、改写文本、教材式生成数据和混合比例，其 5—10 倍到达同一验证 loss 的结果只适用于论文指定的大预算改写混合。2026 年预印本 [Rewriting Scaling Laws for Synthetic Data](https://arxiv.org/abs/2610.31867v1) 把生成改写的 FLOPs 纳入预算，但没有计入 rewriter 预训练成本，且尚非同行评审后的结论。

预训练与推理时计算的分配参考 Snell 等人的 [Scaling LLM Test-Time Compute Optimally](https://arxiv.org/abs/2408.03314)。其难度自适应搜索和逐步修订结果绑定 PaLM 2-S*、数学提示、verifier 与特定预算；极难题上仍有预训练计算更有效的设置。

分布式训练的系统背景参考 [Megatron-LM](https://arxiv.org/abs/1909.08053)、[ZeRO](https://arxiv.org/abs/1910.02054) 和 [Switch Transformers](https://arxiv.org/abs/2101.03961)。这些论文支持并行、状态分片和稀疏路由的技术脉络；吞吐、P99、通信和成本必须绑定硬件、拓扑、batch、精度和实现版本。

大规模强扩展和故障恢复可参考 [MegaScale](https://arxiv.org/abs/2402.15627)。其 175B 强扩展实验绑定 2,048 序列长度、6,144 batch 和论文集群；生产恢复指标为作者运行报告，应与受控 throughput 对照分开看。

训练稳定性案例参考 Bai 等人的预印本 [The Role of Quantization in Loss Spikes](https://arxiv.org/abs/2610.38277)。其迟发 spike 分析来自 28M—1.4B 的现代化 GPT 结构、高学习率和特定长程训练设置；不能把该 LM-head/有限精度机制作为任意训练 spike 的根因。

LLaMA 作为现代训练配方案例可参考 [LLaMA: Open and Efficient Foundation Language Models](https://arxiv.org/abs/2302.13971)。它支持论文公开版本中的模型和训练描述，但不单独证明某个局部模块对所有后续模型的因果贡献。

本章中的幂律参数、预算点、训练 spike、分布式扩展和 Python demo 均为教学构造。真实项目应保存数据 snapshot、模型配置、代码 revision、训练曲线、硬件/通信 trace、checkpoint、评估脚本和失败记录，并明确区分论文事实、项目实测和教学近似。

## 18. 本章小结

Scaling 与训练论文线研究的不是“模型越大越好”，而是参数、token、数据质量、计算、优化、稳定性和系统执行之间的共同约束。读这类论文时：

1. 先明确研究对象是 loss、下游能力、训练成本还是生命周期成本。
2. 把参数 $N$、数据 $D$ 和计算 $C$ 放在同一预算账本中。
3. 用实验矩阵、幂律拟合、held-out 点和残差判断趋势与外推，而不是背单个比例。
4. 把 GPT-3 的规模现象与 in-context learning 的 prompt 条件分开。
5. 把 Chinchilla 理解为 compute-optimal 的联合分配思想，而不是永恒公式。
6. 把 token 数进一步拆成质量、来源、配比、重复、污染和有效学习信号。
7. 把 loss、下游能力和生产行为分别测量，注意后训练和评估协议的影响。
8. 把训练稳定性、并行通信、checkpoint 和恢复看成 scaling 的前提，而不是事后工程细节。
9. 在小规模实验中控制变量、拟合趋势，在目标规模上确认质量、成本、风险和部署边界。

当你能够说明一条 scaling 曲线在哪个范围内成立、为什么会偏离、预算该如何分配，以及训练系统怎样把理论点变成真实 step，你读到的就不再是一组公式，而是一套可执行的训练决策方法。
