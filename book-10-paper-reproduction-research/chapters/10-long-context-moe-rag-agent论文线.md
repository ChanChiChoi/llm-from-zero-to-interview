# 第十章：Long Context、MoE、RAG、Agent 论文线

大模型的能力不只来自参数。更长的输入、更大的稀疏容量、可更新的外部知识、可执行的工具和环境反馈，都可以成为模型完成任务时使用的计算资源。本章讨论五条经常一起出现、但不应混为一谈的论文线：Long Context、Mixture-of-Experts、Retrieval-Augmented Generation、Tool Use 和 Agent Planning。

它们的共同问题是：当一次固定的 dense 前向传播无法满足任务时，能力应当从哪里来？长上下文扩大模型可以观察的输入范围，MoE 增加总参数而只激活部分专家，RAG 把知识库变成外部记忆，工具把计算和业务动作交给执行器，Agent 则把一次生成扩展为有状态的多步循环。

这些方向的代价也不同。窗口变长不等于模型会使用远处证据，专家总参数变大不等于每个 token 的计算变大，检索到文档不等于答案忠实，生成工具参数不等于动作授权，Agent 能写出计划不等于任务最终成功。阅读论文时，必须把能力来源、计算路径、评估协议和失败责任放在一起。

## 1. 先区分五种能力扩展

### 1.1 一个研究任务的五种实现

假设任务是写一份带来源的行业研究报告。纯参数模型依靠训练时存入参数的知识，可能知识过期或无法给出来源。Long Context 允许它在一次请求中读入长报告和历史材料。RAG 先从资料库中选出与问题相关的片段，再交给模型组织答案。Tool Use 让模型查询实时数据库、运行计算器或执行代码。Agent 则负责把检索、计算、核对和写作组织成多步过程。

MoE 处在另一层：它改变模型内部的容量和计算分配。一个 token 可能被路由到不同专家，从而让模型在相近的 active compute 下拥有更大的总参数空间。MoE 可以作为 Long Context、RAG 或 Agent 所使用的底层模型，但它本身不是外部记忆，也不是规划器。

### 1.2 机制、记忆和执行的边界

| 方向 | 改变的对象 | 能力来源 | 主要失败责任 |
| --- | --- | --- | --- |
| Long Context | 输入序列与注意力计算 | 更多当前请求中的 token | 位置外推、长程利用、干扰和成本 |
| MoE | 模型内部参数路径 | 稀疏激活的专家容量 | 路由、负载、通信和训练稳定性 |
| RAG | 外部知识链路 | 文档、索引和检索结果 | 召回、排序、证据冲突和引用 |
| Tool Use | 模型与执行器接口 | API、代码、数据库和环境 | 参数、权限、幂等、错误和副作用 |
| Agent | 有状态控制循环 | 计划、行动、观察和记忆 | 长程可靠性、循环、停止和恢复 |

Long Context 和 RAG 都可能把文本放进 prompt，但前者主要改变可容纳范围，后者主要改变证据选择和知识更新。Tool Use 和 Agent 都可能多次调用模型，但 Tool Use 关注一次调用的协议和执行，Agent 关注跨步骤的状态与目标。MoE 则是模型内部的条件计算机制。

### 1.3 先写清 claim 的形式

“支持百万上下文”“MoE 更强”“RAG 减少幻觉”“Agent 可以自主完成任务”都不是可直接验证的 claim。更可复查的写法是：

> 在固定模型、数据、硬件和评估协议下，某种机制是否在给定输入长度、检索预算、专家激活计算或工具调用预算内，提高目标任务成功率，同时满足延迟、成本和安全约束？

这个写法迫使研究者说明分母和预算。长上下文要报告输入长度和相关证据位置；MoE 要报告 active FLOPs、负载和通信；RAG 要报告检索候选和引用支持；Tool Use 要报告可用工具和权限；Agent 要报告最大步数、状态和失败恢复。

可以用一个构造任务把这些分母放在同一张实验桌上：回答一份由四十份报告组成的行业材料中的问题，其中一项数据还需查询实时数据库。长上下文方案说明总输入 token 和证据位置；RAG 方案说明四十份材料中有几份包含必需证据、最终召回了哪些片段；工具方案说明数据库调用读到了哪个版本的记录；Agent 方案说明它经过几步才把证据和查询结果合并。MoE 则要放在模型内部的计算账本里，记录总参数、每 token 激活量和通信成本，不能把它和“多找了几份材料”当作同一机制。

这个例子也说明了为什么系统总分不够。若 RAG 提升了答案准确率，至少要再问它是否召回了全部必需证据、是否把证据放进生成上下文、回答里的可核验主张是否被引用支持；若 Agent 完成任务，还要看它有没有在中途越权、重复写入或靠额外调用预算换取成功。论文可以研究完整系统，但实验必须保留能区分这些责任层的观测量。读者看到的不是五个互相竞争的产品类别，而是五种可分别验证、也会在组合处互相影响的能力来源。

## 2. Long Context：能放进去不等于能用起来

### 2.1 上下文窗口的三个含义

“上下文长度”至少有三种含义：

1. **接口上限**：tokenizer、API 或 runtime 接受的最大 token 数。
2. **训练长度**：模型在训练中实际见过并被优化过的序列范围。
3. **有效使用长度**：模型能在该长度下找到证据、组合远距离信息并完成任务的范围。

接口上限只说明输入没有被拒绝。一个模型可以接受很长文本，却在中间位置忽略关键事实，或者因为无关内容过多而输出错误答案。论文和模型卡若只给最大 token 数，读者还需要寻找训练长度、位置编码方案、评估任务和成本。

### 2.2 Self-attention 的长度成本

对 hidden size 为 $d$、序列长度为 $n$ 的 dense self-attention，attention score 的形状大致是 $n\times n$。忽略常数和 head 划分，计算和中间存储可以写成教学近似：

~~~math

C_{attn}=O(n^2d),
\qquad
M_{score}=O(n^2).

~~~

长度从 $n$ 增加到 $2n$ 时，二次项大致变为四倍。真实成本还取决于 batch、head 数、精度、是否 causal、kernel、重计算和硬件带宽，但这个近似解释了为什么长上下文很快成为训练和推理瓶颈。

训练时还要保存反向传播需要的激活；推理时则要保存历史 KV cache。两者都使“只是把 max length 调大”不成为完整的长上下文方案。

一个便于复算的量级例子是：只看 batch 为 1、单个 attention head、单个 score 矩阵，序列长 4096 时，矩阵有 $4096^2=16{,}777{,}216$ 个元素；用 16-bit 浮点存储，需要约 32 MiB。长度变成 8192 后是 $67{,}108{,}864$ 个元素，正好四倍，约 128 MiB。真实实现可能用分块算法而不物化这个矩阵，实际内存还要乘以 head、batch 并计入其他状态；这里计算的是朴素 score 矩阵的尺度，帮助解释二次增长，而不是对某个 kernel 的显存预测。

KV cache 是另一笔账。若构造一个 32 层、8 个 KV head、每个 head 维度 128、缓存 128,000 个 token、每元素 2 字节的单序列模型，近似需要
$2\times32\times8\times128\times128{,}000\times2
=16{,}777{,}216{,}000$ bytes，即约 16.78 GB 或 15.625 GiB。前面的 2 表示 key 和 value 两组张量。这个结果还没有计入 allocator、对齐、并发请求、临时激活和运行时元数据，也不说明模型能正确使用 128K 上下文；它只说明长输入会占用可观的服务内存。

### 2.3 近似 attention 与 exact attention

长上下文研究可以大致分成两类。一类改变注意力连接结构，例如局部窗口、块稀疏、低秩或线性 attention，试图把二次交互减少到更低复杂度。另一类保持数学上的 dense attention，但重新设计实现，减少显存读写和中间张量。

两类方法回答的问题不同。稀疏或线性结构改变了模型的归纳偏置，可能牺牲远距离全连接能力；IO-aware exact attention 不改变 attention 定义，主要改善硬件执行效率。论文不能只用“速度更快”比较它们，还要说明是否改变了计算图和近似误差。

### 2.4 FlashAttention：IO-aware 的精确注意力

标准实现可能显式生成 attention score 矩阵，再做 softmax 和矩阵乘法。这个中间矩阵需要在 GPU 的 HBM 与更快的片上 SRAM 之间读写。长序列下，内存搬运可能比算术操作更限制吞吐。

FlashAttention 的核心思想是 tiling 和 online softmax：把 Q、K、V 分块加载到片上存储，在块内完成必要计算和归一化，不把完整 $n\times n$ attention 矩阵写回 HBM。它仍然计算 exact attention，不是把 token 两两关系近似成稀疏图。

可以把它想成两种记账方式。普通实现反复把大张草稿纸搬到仓库，FlashAttention 尽量把小块材料留在工作台上边算边合并。收益来自减少 IO 和中间存储，而不是把理论上的二次交互改成线性。

FlashAttention-2 进一步调整并行切分、warp 工作分配和非矩阵乘法开销，使 kernel 更接近硬件矩阵乘法的利用方式。阅读这类系统论文时，要同时看 HBM 读写、峰值显存、序列长度、batch、精度和端到端 tokens/s，不能只看一个 kernel speedup。

### 2.5 PagedAttention：推理时的 KV cache 管理

自回归生成的第 $t$ 个 token 需要访问历史 token 的 key 和 value。若每次都重算历史，成本很高，因此 serving runtime 会保存 KV cache。对多层、多头和 batch 请求，KV cache 大致随历史 token 数增长：

~~~math

M_{KV}
\approx
2\,L\,n_{kv}\,d_{head}\,n_{token}\,b,

~~~

其中 $L$ 是层数，$n_{kv}$ 是 KV head 数，$d_{head}$ 是 head 维度，$n_{token}$ 是缓存 token 数，$b$ 是每个元素的字节数。GQA/MQA 可以降低 $n_{kv}$，但长上下文和并发仍会快速消耗显存。

传统连续分配会因为请求长度不同、结束时间不同和前缀共享产生碎片。PagedAttention 把逻辑连续的 KV 序列映射到非连续物理 block，借鉴虚拟内存的分页思想，让 allocator 更容易复用空间和共享前缀。

它解决的是 serving memory management，不是模型的长程理解。一个 PagedAttention 服务可以更高效地承载长请求，但如果模型没有在长长度上训练或评估，服务效率提升不会自动带来答案质量提升。

### 2.6 位置编码与长度外推

模型不仅要存储 token，还要知道 token 的相对或绝对位置。若训练序列长度为 $n_{train}$，推理时直接使用远大于它的 $n_{test}$，位置编码和注意力分布可能落入训练未覆盖的区域。

常见策略包括：

1. 直接用更长序列训练，让模型在目标位置范围内学习。
2. 对 RoPE 进行位置插值或 scaling，改变旋转频率范围。
3. 使用 ALiBi 等相对位置偏置，尝试改善长度外推。
4. 采用滑动窗口、全局 token、分段记忆或递归摘要。
5. 通过 RAG 先筛选证据，减少无关 token 的长度压力。

这些策略的机制不同。位置插值可能保留更多原有能力，但不等同于模型已经学会复杂长距离推理；滑动窗口降低计算，却限制任意远距离交互；递归摘要减少长度，却把原始证据压缩成了新的中间表示。评估必须匹配实际使用的长度和任务。

### 2.7 最大长度与有效长度

可定义一个带证据位置的任务成功率：

~~~math

A(n,p)
=P(\text{task success}
\mid\text{length}=n,\text{relevant position}=p).

~~~

如果只在相关事实位于开头或结尾时测试，得到的平均值可能掩盖中间位置的失败。更完整的评估要改变总长度、相关证据位置、干扰比例、证据数量和推理跨度。

对于多证据任务，还应测量模型是否能同时引用多个远距离片段，而不是只寻找一个“needle”。单点检索通过只能证明局部访问能力，不能证明长文档分析能力。

### 2.8 Lost in the Middle 与长上下文利用率

长上下文模型常见的一类现象是：相关信息位于上下文中间时，性能低于位于开头或结尾。它提示研究者区分“attention 可以访问”与“模型在任务中会利用”。无关文本、相互冲突的证据和不同段落之间的实体对应会进一步放大问题。

因此长上下文评估至少应包括：

1. 单事实定位。
2. 多事实合并。
3. 中间位置和随机位置。
4. 无关 token 和近似干扰。
5. 需要引用原文的答案。
6. 需要跨段推理或时间顺序判断的任务。

如果模型只在长文本末尾的答案位置表现好，可能是位置偏置或提示格式问题，而不是一般的长程理解。

### 2.9 长上下文的单位成本

长上下文的质量提升要与输入成本和延迟一起报告。一个请求的粗略账本可以写成：

~~~math

C_{request}
=C_{prefill}(n_{in})
+C_{decode}(n_{out})
+C_{KV}(n_{in},\text{batch})
+C_{storage}.

~~~

如果把完整知识库全部放入 prompt，输入 token 和 prefill latency 可能远高于 RAG 先筛选片段的方案。长上下文与 RAG 的比较应保持任务证据一致，并同时报告准确率、引用支持、输入 token、TTFT、吞吐和峰值显存。

### 2.10 复现长上下文论文

一个可控的复现路径是先使用合成文档，把唯一事实放在不同位置，并加入可控的干扰段。然后逐步增加：

1. 总 token 长度。
2. 相关事实数量。
3. 证据之间的推理距离。
4. 近似和冲突文档。
5. 输出引用要求。

每个长度点至少保存模型配置、位置编码、推理 kernel、精度、输入 token、输出 token、峰值显存和请求延迟。不能把“runtime 接受输入”当作理解能力的通过条件。

## 3. MoE：总容量与 active compute 的分离

### 3.1 Dense 与 sparse 的差异

Dense Transformer 的每个 token 都经过同一组 FFN 参数。扩大参数通常会增加每 token 计算。MoE 则把 FFN 替换或扩展为多个 experts，由 router 根据 hidden state 选择少数专家。

它的核心目标是 conditional computation：模型总参数可以增加，但一个 token 只激活一部分。对 MoE 账本，至少要分开总参数、共享参数、active parameters、理论 FLOPs、实际通信和存储容量。

### 3.2 Router 与 top-k 路由

设 token 的 hidden state 为 $h$，有 $E$ 个专家。一个简单 router 可以写成：

~~~math

p(h)=\mathrm{softmax}(W_rh),
\qquad
S(h)=\mathrm{TopK}(p(h),k).

~~~

输出可以表示为：

~~~math

h'
=\sum_{e\in S(h)}\tilde p_e(h)E_e(h),

~~~

其中 $E_e$ 是第 $e$ 个专家，$\tilde p_e$ 是选中专家分数重新归一化后的权重。top-1、top-2 和更复杂的路由在通信、容量、冗余和容错上不同。

初学者可以把 router 想成分诊台：先根据 token 特征分配给不同专科。专家不一定天然对应“法律”“数学”或“某种语言”，除非有分析证据证明这种 specialization；看到专家分工可视化不能直接推出因果解释。

### 3.3 Active parameters 与总参数

一个教学近似是：

~~~math

C_{MoE}
\approx
k\left(N_{shared}+\rho N_{expert}\right)D,
\qquad 0<\rho\leq1,

~~~

其中 $N_{expert}$ 是所有专家参数总和，$\rho$ 是平均激活比例，$D$ 是 token 数。这个公式没有计入 router、dispatch、all-to-all、padding 和负载不均衡，因此不能直接当作 GPU 账单。

MoE 可能拥有比 dense baseline 更多的总参数，却只有相近的 active FLOPs。它的收益来自更大的容量和条件路径，代价则转移到了参数存储、路由通信和并行调度。比较 MoE 与 dense 时，只报总参数或只报 active parameters 都不完整。

DeepSeek-V3 技术报告给出的模型规模是总参数 671B、每个 token 激活约 37B，按参数数目计算的比例约为 $37/671\approx5.5\%$。[DeepSeek-V3 Technical Report](https://arxiv.org/abs/2412.19437) 这个比例描述报告中的 active parameter count，不等于 active FLOPs 的精确比例：共享层、embedding、router、padding 和执行开销都可能改变 FLOPs 账目。它也不能用于估算另一个 MoE 的实际单步成本，除非层宽、专家数、路由方式和硬件布局都对齐。

### 3.4 负载均衡

如果所有 token 都被送往少数专家，热点专家会成为瓶颈，其他专家闲置。设 $f_e$ 是路由到专家 $e$ 的 token 比例，$p_e$ 是 router 对专家 $e$ 的平均概率，一个常见的负载均衡思想是让两者都接近 $1/E$：

~~~math

L_{balance}
\propto
E\sum_{e=1}^{E}f_ep_e.

~~~

不同论文的辅助损失、系数和容量策略并不相同。公式的重点是提醒我们同时关注离散路由分配 $f_e$ 和连续 router 概率 $p_e$，而不是只看总 loss。

工程审计中还常用负载变异系数描述专家之间的不均衡。设第 $e$ 个专家实际接收的 token 数为 $q_e$，则可以写成：

~~~math

CV_{load}
=\frac{\mathrm{std}(q_1,\ldots,q_E)}
       {\mathrm{mean}(q_1,\ldots,q_E)},
\qquad
\mathrm{mean}(q_1,\ldots,q_E)>0.

~~~

$CV_{load}$ 越大，通常表示热点专家和空闲专家之间的差距越大；如果一个 batch 没有任何有效 token，均值为零，CV 没有定义，不能把它记成一个正常的低负载结果。

例如一个构造 batch 有四个专家，实际收到的路由 assignment 数为 $[80,50,40,30]$。平均数是 $(80+50+40+30)/4=50$；总体方差是 $(30^2+0^2+(-10)^2+(-20)^2)/4=350$，标准差约为 18.71，因此 $CV_{load}\approx18.71/50=0.374$。这个数表示本 batch 的负载离散程度，不是质量损失率，也不能单独说明应当调大还是调小辅助损失；还要看各专家计算时间、跨卡位置和实际容量策略。

### 3.5 Capacity factor 与 dropped tokens

每个 expert 的处理容量通常有限。若一个 batch 有 $T$ 个 token、$E$ 个专家、每个 token 选 $k$ 个专家，可以用一个教学化容量近似：

~~~math

capacity
=\left\lceil
\gamma\frac{kT}{E}
\right\rceil,

~~~

其中 $\gamma$ 是 capacity factor。容量过小会造成 token 被丢弃、跳过或退化处理；容量过大则浪费显存并降低吞吐。论文应报告 dropped token ratio、每专家负载分布和容量设置，否则读者无法判断质量与系统成本的关系。

沿用四专家例子，取 100 个 token、每个 token 选 $k=2$ 个专家、$\gamma=1.25$，总路由数是 $100\times2=200$，平均分配为每专家 50 个 assignment，容量为 $\lceil1.25\times200/4\rceil=\lceil62.5\rceil=63$。如果请求负载是 $[80,50,40,30]$，第一个专家超过容量 17 个 assignment；按所有请求 assignment 作分母，丢弃比例是 $17/200=8.5\%$。这不是“8.5% 的 token 序列都失败”：不同实现可能把溢出路由给次选专家、只丢弃一个 token 的部分路由，或采取其他回退方式。因此复现时必须读清论文的容量和 overflow 语义，不能仅凭一个百分数推断最终 token 表示是否缺失。

负载平衡方法也不能只按辅助损失名称归类。DeepSeek-V3 技术报告描述了按 batch 专家负载调整 router bias 的 auxiliary-loss-free balancing，同时还保留 sequence-wise 辅助损失以处理单序列失衡；这些选择属于作者模型、路由和集群设计的一部分。[DeepSeek-V3 Technical Report](https://arxiv.org/abs/2412.19437) 支持的是该报告公开的具体方案，不证明这种组合对所有 MoE 规模、数据分布和并行拓扑都更优。比较时要同时检查质量、assignment 分布、drop、通信和 step time。

### 3.6 Sparsely-Gated MoE 与 Switch Transformer

Sparsely-Gated Mixture-of-Experts 奠定了用稀疏 gate 扩大模型容量的路线。Switch Transformer 进一步采用 top-1 routing，减少每个 token 的专家计算和通信，并配合负载均衡和容量管理扩展大模型训练。

top-1 的优点是路径简单、通信少，缺点是路由错误时没有第二个专家提供补偿。top-2 可能增加冗余和质量，但也增加 dispatch、通信和容量压力。论文比较不能只看模型参数，还要保持训练 token、active FLOPs、数据和硬件预算可比。

### 3.7 MoE 的专家分工能否直接解释

训练后观察到某些专家更常处理代码或某种语言，并不自动证明专家被明确训练成这些领域的模块。频率可能来自数据比例、tokenizer、router shortcut 或 batch 结构。要研究 specialization，可以做：

1. 按输入类型统计专家负载。
2. 固定输入做 router 干预或专家替换。
3. 比较去掉某专家前后的任务变化。
4. 在新领域和新语言上做 holdout。
5. 区分 router 选择相关性与专家输出的因果作用。

这使 MoE 论文从“看起来有分工”变成可检验的机制 claim。

例如构造 100 个代码题和 100 个一般问答，观察到专家 1 接收 80 个代码题 token，却只接收 30 个一般问答 token。这是路由与输入类别的相关性，不足以证明该专家导致了代码能力。再在固定计算预算下做专家替换/回退：若代码题准确率从 80/100 降到 68/100，而一般问答从 80/100 降到 79/100，干预结果才为“该专家对这组代码输入有较大功能贡献”提供更强证据。仍需测试其他专家和输入分布，因为路由替换会改变组合表示，不能把它解读为专家内部存放了单一领域知识。

### 3.8 MoE 的训练和部署成本

MoE 的总参数通常需要存储，即使每个 token 只激活少数专家。分布式训练还要把 token 发送到专家所在设备，all-to-all 的成本可能压过省下的算术计算。推理时 batch 组成、路由热点、专家并行拓扑和请求混合会影响实际吞吐。

一个更完整的 step 时间账本是：

~~~math

T_{step}
\approx
T_{compute}
+T_{dispatch}
+T_{all\text{-}to\text{-}all}
+T_{imbalance}
+T_{checkpoint}.

~~~

因此 MoE 论文必须同时报告 quality、active FLOPs、tokens/s、通信占比、专家负载、显存和故障恢复。单卡 FLOPs 降低不代表端到端成本下降。

训练和推理的路由分布也未必相同。训练数据混合比例会改变哪些专家频繁被触发；服务端的用户请求、长上下文和并发 batch 又可能形成新的热点。论文若只报训练平均负载，不能据此声称在线服务均衡；若只报一个合并 batch 的 CV，罕见领域的专家饥饿也可能被平均掉。更有判别力的记录会同时给全局、每层、每序列和按任务切片的请求/执行分布，再观察对应的 step time、排队和质量。路由相关性只能说明哪些 token 被分派到哪里；要声称某专家承担某种能力，还需固定输入做消融、替换或反事实路由实验。

assignment 数也只是负载代理，不是完整计算量：不同层的专家宽度、padding、容量空槽、跨设备路由和 dispatch kernel 都会改变实际 FLOPs 与时延。一个专家平均收到了 50 个 assignment，若 20 个要跨节点通信，另一个专家收到同量但都在本机，二者的 step cost 不会相同。因而负载图应和 topology、专家所在 rank、all-to-all 字节数及实际执行时间配套；只凭 top-k 计数无法计算系统收益。

## 4. RAG：把外部知识变成可追踪证据

### 4.1 参数记忆与非参数记忆

参数记忆的优点是调用快、表达紧凑、可以在生成中直接使用；缺点是更新需要训练或编辑，知识来源难以追踪，私有和新鲜资料不一定覆盖。RAG 引入非参数记忆，把文档或数据库内容保留在外部索引中，在请求时检索并注入上下文。

RAG 的目标不是把模型变成数据库，而是把模型的语言能力与外部证据连接起来。它可以改善时效性、领域覆盖和来源透明度，但引入新的失败环节：正确文档是否被召回，证据是否完整，模型是否忠实使用。

### 4.2 RAG 的基本数据流

一个典型系统包括：

~~~mermaid
flowchart LR
    A["文档采集与版本管理"] --> B["解析、切分、去重与权限标注"]
    B --> C["Embedding 与关键词索引"]
    C --> D["Query 改写与召回"]
    D --> E["重排与权限过滤"]
    E --> F["上下文装配或压缩"]
    F --> G["生成带证据的回答"]
    G --> H["引用核验与审计"]
~~~

图中每一步都可能决定最终结果。一个生成模型在没有正确文档的情况下回答错误，不应简单归因于“模型幻觉”；一个正确文档被召回但未被使用，才更接近上下文利用或生成忠实性问题。流程图也提示了来源血缘的起点：生成端的引用 ID 必须能够回到被解析的文档版本、原文位置和权限判断，否则“附了引用”仍无法复查。

### 4.3 召回与重排

稠密检索用 embedding 相似度寻找语义相关片段，BM25 等关键词检索更擅长精确实体、编号和术语。混合召回、query expansion 和 reranker 可以互补，但每多一层也增加延迟、版本和调参空间。

对一个问题集合，最基本的检索指标是 recall@k：

~~~math

Recall@k
=\frac{\#\{\text{queries with a relevant item in top-}k\}}
       {\#\{\text{queries with an annotated relevant item}\}}.

~~~

分母是已经标注过相关证据的查询数；如果评估集没有任何相关性标注，Recall@k 是未定义，而不是 0。若某些查询确实不需要外部证据，也应在评估协议中单独标注，不能把它们混入相关性分母。若答案需要多个片段，还要定义 multi-hop recall 或 evidence set recall，不能只用“至少召回一段”掩盖缺失的第二个证据。

例如构造 100 个确实需要检索、且都已标注必需证据的问题，其中 72 个至少有一条相关片段出现在 top-5，则 Recall@5 为 $72/100=0.72$。再单独抽取 20 个必须联合两份来源的问题，只有 12 个同时取回两份必要证据，完整证据集合召回率（evidence-set recall）是 $12/20=0.60$。第一个指标回答“是否找到过相关内容”，第二个回答“回答问题所需的证据集合是否齐全”；二者不能互相替代。所有数值都是教学构造值，不代表任何检索器的实测成绩。

### 4.4 Chunking 是证据边界设计

切分不是一个只影响向量库大小的工程参数。chunk 太短，定义、条件和例外可能被拆开；chunk 太长，召回会带入无关内容，reranker 和 generator 的上下文压力增加。

合适的切分应尽量保留文档结构：标题、段落、表格、代码块、页码、时间和权限。对法律条款、代码函数和财报表格，按固定字符数切分往往会破坏语义单元。评估时要保存 chunk 与原文版本的血缘，以便回答引用能够回到确切来源。

### 4.5 RAG 与 Long Context 的关系

Long Context 主要解决“最多可以放多少”，RAG 主要解决“哪些证据值得放进去”。上下文窗口足够大时，把整个知识库塞入 prompt 仍然可能带来高 prefill 成本、干扰和中间位置利用问题。RAG 可以先筛选相关内容，再用长上下文容纳多个候选证据和历史对话。

反过来，RAG 的 top-k 不是越小越好。如果问题需要跨文档聚合，过度压缩会漏掉必要证据；如果模型无法处理长输入，召回太多又会降低利用率。两者应在相同证据覆盖下比较质量、延迟和 token 成本。

### 4.6 生成忠实性与引用支持

RAG 的回答可能看起来合理，却没有被检索内容支持。可以定义一个教学化的 claim support ratio：

~~~math

SupportRatio
=\frac{\#\{\text{answer claims supported by cited evidence}\}}
       {\#\{\text{verifiable answer claims}\}}.

~~~

分母是被识别为可核查的 claim 数；如果回答没有可核查 claim，SupportRatio 应报告为未定义，并同时说明回答类型，而不是把空回答或纯寒暄误记为满分或零分。这个指标需要 claim 抽取和证据标注，不能由答案是否包含引用链接代替。引用存在但与具体句子不匹配，仍然属于 citation misalignment。

还要区分“证据支持”与“答案正确”。文档本身可能过期或错误；模型忠实引用错误文档，仍然会产生错误答案。因此需要同时检查文档质量、时间、权限和冲突处理。

评估 RAG 论文时还要辨别机制路线。[Self-RAG](https://arxiv.org/abs/2310.11511)研究模型按需检索并使用反思标记评估生成内容；[CRAG](https://arxiv.org/abs/2401.15884)在检索后加入 evaluator，并按评价结果采取纠正动作或外部搜索；[RAPTOR](https://arxiv.org/abs/2401.18059)通过递归聚类和摘要构造不同粒度的检索树；[GraphRAG](https://arxiv.org/abs/2404.16130)利用实体关系与社区摘要支持语料层面的全局问题。它们针对的瓶颈不同：前两者改变检索决策或纠错，后两者改变索引组织和证据粒度。比较时要把索引构建、更新、摘要损失、原文定位和检索延迟写进成本表，不能把四种方案统称为“更好的 RAG”。

### 4.7 RAG 的典型失败链

| 现象 | 更可能的责任层 | 需要检查 |
| --- | --- | --- |
| 正确文档不在 top-k | 召回 | query、embedding、BM25、文档覆盖 |
| 证据被切成互不完整的片段 | 解析/切分 | 文档结构、overlap、表格和代码 |
| 相关文档在候选中但未进入 prompt | 重排/预算 | reranker、top-k、权限过滤、压缩 |
| 证据在 prompt 中但答案忽略 | 生成/利用 | 位置、冲突、指令、引用约束 |
| 答案引用了不支持的文档 | 生成/引用 | claim-evidence 对齐、verifier |
| 过期或越权文档被使用 | 治理/权限 | 时间版本、租户、ACL、删除血缘 |

这个表比笼统地说“RAG 有幻觉”更有用，因为每种失败需要不同修复。

检索链路还是一个安全边界。USENIX Security 2026 的一项研究把攻击内容拆成促使检索的触发片段（trigger fragment）与承载目标的攻击片段（attack fragment）；作者在其 11 个 benchmark、8 种 embedding 模型的设定中报告攻击内容几乎总能被检索，在一个多 Agent 邮件摘要设置中还报告了特定密钥外泄结果。[论文页面](https://www.usenix.org/conference/usenixsecurity26/presentation/chang-hongyan) 支持的是其威胁模型和系统配置下的观察，不是所有 RAG 的攻击概率。它对复现实验的启发是：除了测“恶意内容是否进入 top-k”，还应测进入后是否被当成指令、是否触发工具动作、能否阻止敏感状态外流；仅用向量检索过滤率不能代表端到端安全。

### 4.8 RAG 论文的公平 baseline

一个可信的 RAG 实验至少应包含：不检索的 generator、简单关键词检索、稠密检索、rerank 版本和可能的 oracle evidence。所有版本要固定 generator、解码参数、上下文预算、知识库版本和评估 prompt。

如果 RAG 使用了更多输入 token、额外的 reranker 和更强的模型，却只与一个短 prompt baseline 比较，质量提升无法归因于检索本身。报告还要说明查询是否见过答案、索引是否包含评估集近重复和文档权限如何处理。

若目标是定位责任层，可以把最终回答与人工标注的必要证据集合分离评估：先在固定 generator 下比较关键词、dense、hybrid 和 reranker 的召回/排序，再把人工标注的 gold evidence 注入同一 generator，作为估计生成端上限的诊断对照。若 gold evidence 也无法支持正确回答，继续调检索器未必有用；若 gold evidence 明显有效、候选检索无效，才把重点放回召回或排序。oracle 组不是现实部署系统，不能把它的分数算作可达成绩。请求层面还应报告平均和 p95 召回/生成延迟，索引更新成本以及权限过滤后的召回，因为安全过滤可能改变可用证据集合。

### 4.9 RAG 的小规模复现

一个教学闭环可以从几十篇有明确答案出处的文档开始：

1. 建立原文、段落 ID、版本和权限字段。
2. 实现 BM25 或简单关键词 baseline。
3. 加入 embedding retrieval。
4. 固定 top-k 后比较 reranker。
5. 记录 relevant recall、answer accuracy、support ratio 和 latency。
6. 对召回失败、使用失败和引用失败分别采样分析。

不要一开始就追求复杂向量数据库。若不能在小数据集上区分“没召回”和“召回但没用”，扩大系统规模只会把错误埋得更深。

## 5. Tool Use：模型输出变成受约束的动作

### 5.1 为什么需要工具

语言模型擅长把自然语言映射成文本，但不天然擅长精确算术、实时查询、私有数据库访问、代码执行和业务系统操作。工具把这些能力交给外部执行器，让模型负责选择、参数化和结果解释。

工具调用的价值不只是“知道更多”，还包括得到可验证的计算结果和环境反馈。代价是模型输出不再只是文本，错误可能改变外部状态，安全边界因此从回答内容延伸到权限和副作用。

### 5.2 工具调用的协议对象

一个工具调用至少有：

1. 工具名称和版本。
2. 输入 schema 与必填字段。
3. 用户、租户和执行器权限。
4. 超时、重试和幂等语义。
5. 返回值 schema、错误码和敏感字段处理。
6. trace ID、审批状态和状态差分。

模型生成一个正确的函数名只是协议链的第一步。参数类型错误、权限不足、过期状态、重复执行和结果误读都可能让一次调用失败。

因此应将调用拆成不能相互替代的门：schema 校验器（schema validator）检查结构，策略决策点判断当前主体能否对目标资源执行该动作，执行器在受控环境中运行，结果处理层校验错误码、来源和敏感字段，最后才检查模型是否正确使用 observation。OpenID Foundation 的 AuthZEN Authorization API 1.0 为策略决策点（Policy Decision Point，PDP）和策略执行点（Policy Enforcement Point，PEP）交换 subject、action、resource、context 与决定提供接口；它不定义组织内部策略，也不证明部署中的 PDP、PEP 或执行器配置正确。[AuthZEN Authorization API 1.0](https://openid.net/specs/authorization-api-1_0.html) 因而可以作为授权接口的来源，却不能被当成一条“标准通过即安全”的认证结论。

### 5.3 Toolformer 与可学习的调用行为

Toolformer 等工作研究如何让模型学习在需要时插入 API 调用，并把调用结果重新放回上下文。其核心问题不是让模型记住工具说明，而是学会判断：什么时候调用、调用什么、参数是什么，以及结果如何帮助继续生成。

这类论文需要区分 API 选择准确率、参数正确率、结果使用率和端到端任务成功率。模型可能选对工具却传错日期，也可能参数正确却忽略返回值。只报告工具调用格式合法不够。

### 5.4 结构化输出与 schema 约束

function calling 或 JSON schema 可以把自然语言意图限制为结构化对象。约束解码能减少语法错误，但不保证语义正确或动作安全。

例如 `user_id` 字段满足字符串 schema，不代表模型选择了当前用户的 ID；`amount` 是合法数字，也不代表转账金额经过授权。schema validation、业务校验、权限检查和人工审批是不同层次。

### 5.5 工具结果如何进入上下文

工具返回结果通常会被序列化为新的 observation，再交给模型。系统要处理结果长度、字段可信度、错误信息、未授权数据和 prompt injection。工具返回的网页内容或文档也应被视作外部输入，不能自动成为系统指令。

一个稳健的数据流是：

~~~mermaid
flowchart LR
    A["模型提出调用"] --> B["Schema 校验"]
    B --> C["策略与权限检查"]
    C --> D["受控执行器"]
    D --> E["结果清洗、来源标记与敏感字段处理"]
    E --> F["Observation 回传模型"]
    F --> G{"下一步决策"}
    G -->|继续调用| A
    G -->|询问用户| H["澄清或审批"]
    G -->|停止| I["最终回答"]
~~~

图中的策略门应位于真正执行动作的一侧。模型是否有权决定“继续调用”与执行器是否真正允许调用，应保持分离；自然语言中的自信不能提升权限。若返回内容来自网页或用户可编辑文档，结果清洗也不能把它提升为可信指令，而应保留原始来源并作为不可信 observation 处理。

### 5.6 工具使用评估

可以把工具任务拆成几个条件指标：

~~~math

P_{success}
=P_{select}
  \times P_{args\mid select}
  \times P_{exec\mid args}
  \times P_{use\mid result}
  \times P_{final\mid trace}.

~~~

这个乘法是教学化分解，不假设各项真正独立，但它说明端到端成功率下降的原因可能来自任何一段。应分别记录工具选择、参数、执行、结果使用、最终回答和状态副作用。

### 5.7 工具安全与幂等恢复

读操作、计算操作和写操作不应使用同一权限。写操作要有最小权限、参数范围、审批、幂等键、预览和回滚。重试必须知道请求是否已经执行，否则网络超时可能导致重复扣款、重复发信或重复修改。

工具研究论文若只在无副作用的模拟环境中报告成功率，结论不能直接外推到生产。需要说明环境是否可重置、工具是否真实执行、错误是否注入以及权限是否与现实一致。

可以用一次转账作为可复查的失败案例：执行器已经提交请求，但响应在网络中丢失。Agent 只看见 timeout，若不带幂等键再次执行，就可能产生两笔转账；若直接假设失败并继续，又可能在状态已变化的情况下给出错误报告。实验应把“请求是否送达”“业务状态是否变化”“回包是否丢失”分开注入，并验证重试前的状态读取、审批和差分记录。一次成功率数字若没有写操作的副作用定义，只说明模拟器接受了某种调用，不代表生产操作具备安全恢复能力。

## 6. Agent Planning：从单次生成到有状态循环

### 6.1 Agent 的最小状态机

一个 Agent 可以抽象成状态、目标、动作和观察的循环：

~~~math

s_{t+1}=F(s_t,a_t,o_{t+1}),
\qquad
a_t\sim\pi_{\theta}(\cdot\mid s_t,g),

~~~

其中 $s_t$ 是历史、计划、约束和环境状态，$g$ 是任务目标，$a_t$ 是工具或文本动作，$o_{t+1}$ 是环境返回。Agent 的难点在于状态不是静态 prompt，而是在每一步执行后改变。

### 6.2 ReAct：推理与行动交替

ReAct 把 reasoning trace 和 action 交替起来：模型先根据目标和当前观察决定下一步，再调用搜索、数据库或环境，随后读取 observation 更新状态。

~~~mermaid
flowchart LR
    A["目标与当前状态"] --> B["模型选择下一步"]
    B --> C["动作或工具调用"]
    C --> D["环境返回 Observation"]
    D --> E["更新状态与计划"]
    E --> F{"完成、预算耗尽或需人工接管？"}
    F -->|继续| B
    F -->|结束或升级| G["最终回答或人工处理"]
~~~

图中真正推动状态前进的是 observation，而不是模型写出的 reasoning 文本。它比只生成一条 chain-of-thought 多了环境反馈，也比只生成 action 多了对目标和中间结果的显式组织。[ReAct](https://arxiv.org/abs/2210.03629) 的论文价值需要结合具体环境：开放域检索、交互式任务和工具调用的反馈结构不同，不能把一个环境的成功率外推到所有 Agent。复现实验应保存每次 action 前的状态、工具输入、环境返回和状态差分，才能分辨模型是规划错误、工具失败，还是观察到了证据却没有据此调整计划。

### 6.3 Tree of Thoughts：让中间步骤进入搜索

线性推理在早期做错一步后，后续步骤可能围绕错误前提继续展开。Tree of Thoughts 允许生成多个中间 thought，对候选状态进行评估，再选择、扩展或回溯。

设每一步平均保留 $b$ 个分支，搜索深度为 $d$，未经剪枝的候选数近似为：

~~~math

N_{nodes}\approx\sum_{i=0}^{d}b^i.

~~~

这解释了 ToT 的代价：质量可能提高，但模型调用、评估和上下文复制迅速增加。若评估器本身不可靠，搜索会更有效率地放大错误判断。

### 6.4 反思、记忆与计划的区别

Agent 系统常把历史记录称为 memory，把重新评价失败称为 reflection，把未来步骤称为 plan。三者不应混为一个长文本：

| 对象 | 作用 | 主要风险 |
| --- | --- | --- |
| Plan | 描述尚未完成的目标和步骤 | 早期错误计划持续影响后续 |
| Working memory | 保留当前任务的证据和状态 | 上下文增长、信息冲突 |
| Long-term memory | 跨任务保存可复用事实 | 过期、隐私、错误记忆 |
| Reflection | 从失败中提取修复信号 | 语言上的反思不等于实际改进 |

记忆越多不代表 Agent 越强。错误、过期或越权记忆会污染新任务；写入长期记忆也应有来源、权限、时间和删除机制。

研究长期记忆时还要分开考察“该不该写”“后来能不能取回”和“取回后是否适用于当前目标”。AdaMem 等工作探索了按内容选择性写入的策略，但论文对特定记忆任务的收益不能证明任何 agent 都能可靠过滤记忆。[AdaMem](https://aclanthology.org/2026.emnlp-industry.189/)；Mem2ActBench 则把评估放在多轮任务中检验历史信息是否被转化成具体行动参数，而不是只问系统能否复述历史。[Mem2ActBench](https://aclanthology.org/2026.acl-long.370/) 对部署与复现而言，重要的是记录写入来源、时间、租户、置信条件、失效/删除规则和后续使用的任务；只保存一段摘要会丢失这些责任信息。

### 6.5 长程可靠性

若每一步独立成功概率都为 $p$，连续 $T$ 步全部成功的教学近似是：

~~~math

P(\text{all steps succeed})\approx p^T.

~~~

真实 Agent 的步骤并不独立，后一步可能纠正前一步，也可能放大前一步错误。但这个公式说明多步系统为什么需要恢复和检查点：即使单步成功率很高，长链条也会积累失败。

例如用独立同分布只作教学假设，若每步成功概率为 0.95，连续 20 步全成功的概率是 $0.95^{20}\approx0.358$；若单步提高到 0.97，则 $0.97^{20}\approx0.544$。单步只提高 2 个百分点，整链全成功概率在这个玩具模型中提高约 18.6 个百分点。真实步骤相关、可恢复且成功条件也不一定要求“每一步全对”，所以不能把该结果当作实际 Agent 成功率；它说明长链评估必须记录检查点和纠错，而不能只报告单次工具调用准确率。

Agent 评估应记录平均和 P95 步数、每步工具错误率、恢复成功率、循环比例、停止原因、最终任务成功率和单位成功成本。

### 6.6 停止、恢复与人工接管

一个可部署 Agent 必须定义何时结束、何时重试、何时降级、何时询问用户以及何时交给人工。停止条件可以来自目标完成、预算耗尽、风险动作待审批、重复状态或环境不可用。

恢复策略不能只让模型“再试一次”。应区分参数错误、权限错误、瞬时网络错误、业务冲突和未知副作用，并保存执行前后的状态差分。否则 Agent 可能把一个不可逆动作重复多次。

## 7. 组合系统：边界交汇处最容易出错

### 7.1 Long Context + RAG

RAG 可以先过滤候选证据，Long Context 再容纳多份文档、历史对话和引用要求。组合时要处理排序、冲突、重复、权限和上下文预算。

一个长窗口可能让更多证据进入模型，却也让相关片段出现在中间位置；一个强 reranker 可能提高相关性，却误删解决多跳问题所需的第二片段。组合实验要记录 evidence recall、位置、context packing、回答支持率和成本。

### 7.2 RAG + Tool Use

RAG 通常读取版本化文档，Tool Use 可以查询动态数据库或执行计算。一个企业助手可能先检索制度条款，再查询当前用户状态，最后判断是否允许某个动作。

这里不能把文档中的“应该做什么”和数据库中的“当前状态”混成一个无来源文本。每个 observation 应标注来源、时间、权限和可信度，最终回答或动作要能回放到具体证据。

### 7.3 Tool Use + Agent

工具是动作接口，Agent 是跨动作控制器。Agent 的计划可以选择工具，但执行器仍应独立检查权限和参数。Agent 不能因为自己在计划中写了“用户已授权”就获得授权。

评估组合系统时，要同时看任务成功、工具成功、未授权调用、状态变化、恢复率、调用次数和成本。只看最终回答会忽略中间已经发生的危险动作。

### 7.4 MoE + Long Context

MoE 增加模型容量，Long Context 增加输入范围，组合后可能提高多领域长文档任务能力，但也会叠加 expert dispatch、attention IO、KV cache 和跨卡通信。长序列 token 分布还可能改变 router 负载，使训练或服务出现新的热点。

因此组合论文需要拆分贡献：dense/MoE 对照、短/长上下文对照、active FLOPs、专家负载、位置分桶和端到端成本都不能省略。

## 8. 如何评价这类论文的贡献

### 8.1 先判断论文层级

Long Context 论文可能是位置机制、训练配方、attention 结构或 kernel 系统；MoE 论文可能是 router、负载损失、专家并行或规模实验；RAG 论文可能是 retriever、generator、索引或证据评估；Agent 论文可能是 prompting、搜索、工具协议、环境或 benchmark。

不同层级的主要指标不同。算子论文不能只用最终 benchmark，Agent 方法也不能只用单步准确率。先定位贡献层级，才能选择公平 baseline。

### 8.2 计算和数据预算是否公平

比较 Long Context 时，要固定模型、数据、位置编码和评估任务，说明长序列训练 token 是否增加。比较 MoE 时，要给出总参数、active FLOPs、训练 token、通信和存储。比较 RAG 时，要固定 generator、知识库版本、检索预算和上下文 token。比较 Agent 时，要固定模型、工具、最大步数、环境信息和候选搜索预算。

如果一个方法额外使用了更强的 reranker、更多候选、更多工具调用或更长输出，就要把这些资源写进账本。否则“方法提升”可能只是“预算提升”。

### 8.3 评估是否覆盖真实瓶颈

| 方向 | 不能只看 | 还要看 |
| --- | --- | --- |
| Long Context | 最大 token 和单点 needle | 位置、干扰、多证据、延迟和显存 |
| MoE | 总参数和最终 loss | active FLOPs、负载、drop、通信和稳定性 |
| RAG | 最终答案准确率 | recall、排序、证据支持、权限和时效 |
| Tool Use | JSON 合法率 | 工具选择、参数、执行、结果使用和副作用 |
| Agent | demo 成功一次 | 多次重复、步骤、恢复、成本和失败类型 |

### 8.4 Ablation 要能定位责任

系统论文应拆开验证模块：去掉 reranker、改 top-k、换 chunking、限制上下文、移除 memory、限制搜索深度、关闭工具重试、替换 router loss。每个消融都应保持其他预算和接口尽量一致。

若没有消融，读者无法知道提升来自核心机制、数据清洗、提示模板、额外计算还是评估泄漏。

组合模块还要检查交互项，不能只把两个单项结果相加。以构造的 100 个问题为例，固定模型和总 token 预算：无 RAG、短输入的成功率为 70%；只加 RAG 后为 76%；只把证据窗口拉长后为 74%；两者同时加入后为 82%。相对两个单项增益之和的交互差为 $82-76-74+70=2$ 个百分点。这个差值提示组合可能有额外收益，但样本误差、证据集合和提示变化仍需控制；一个构造表不能证明普遍协同。公平的后续实验要逐格复跑同一批任务，并保存每格的证据、token、延迟和失败类别。

Agent 论文还要判断被测对象究竟是模型、harness，还是完整配置。[Agentic CLEAR](https://aclanthology.org/2026.acl-demo.74/) 把诊断分成 system、trace 和 node 三层，并在论文的四个 benchmark、七种 agent setting 和大量调用轨迹上验证其诊断流程；它支持的是这些环境中分层定位错误的可行性，不能直接说明其他业务的根因也会被同一套 grader 找到。[Harness-Bench v2](https://arxiv.org/html/2605.27922v2) 则用共享任务输入、初始环境和最终 artifact 比较模型—harness 配置，作者报告质量与成本会随组合改变。该版本摘要页与固定正文的数量信息存在差异，本章不取其规模或排名数字；它在此处说明一个归因边界：完整配置表现不能自动归因于单个 harness 功能或裸模型。

## 9. Worked case：百万上下文的有效能力分析

### 9.1 表面结果

以下是一组教学构造值，不是任何模型的论文或产品结果。某模型接口接受 1M token 输入，长文档测试中可以找到位于开头和结尾的指定事实。团队据此宣传模型“具备 1M context understanding”。

这个结论过强，因为它没有报告训练长度、证据位置、干扰比例、跨段推理和请求成本。

### 9.2 分层测试

可以把测试拆为四层：

1. **接口层**：输入是否被 tokenizer 和 runtime 接受。
2. **定位层**：不同长度和位置的单事实是否找得到。
3. **组合层**：多个远距离事实是否能合并。
4. **决策层**：在冲突和无关信息中是否能依据证据给出正确结论。

假设每个位置桶各有 100 道题，定位层在开头/结尾成功率为 0.92，中间位置为 0.61，多证据组合为 0.48，且账单记录的每请求成本是 128K 方案的 6 倍。开头/结尾与中间差 $0.92-0.61=0.31$，即 31 个百分点；中间定位与多证据组合再差 13 个百分点。若每题都真的输入 1M token，单把输入长度由 128K 拉至 1M 就约为 $1{,}000/128\approx7.81$ 倍；本例的“成本 6 倍”因此应理解为计入缓存或其他计费项后的另一个假设账目，不能和裸 token 数比率混用。报告应明确成本分子是 token 费、prefill 时间还是整次请求开销。

这组成功率只有在每个桶的题目、解码预算、提示模板和人工评分规则一致时才有可比性。更准确的结论是“接口支持 1M；在本构造协议下定位能力随位置和任务复杂度下降；当前证据不足以证明通用 1M 推理”。若只有 100 题/桶，还应报告逐题配对差异和区间，不能把 31 个百分点直接称为稳定的模型属性。测试集还要把单事实定位与多证据组合分开：前者只需找到一个针，后者要求同时取回数条证据、保留它们之间的关系并回答复合问题。

真实 benchmark 也只能支持其任务边界内的判断。NoLiMa v3 通过降低问题与证据的词面重合来提高检索难度；作者在 32K 设置中报告 13 个模型里有 11 个低于各自短上下文基线的一半，结果绑定其测试任务和模型版本。[NoLiMa v3](https://arxiv.org/abs/2502.05167v3) 不能单独代表真实文档问答。LongBench Pro v1 使用中英文自然样本，报告 8K—256K token 范围和细分长度/依赖类别，但截至本章扫描仍是预印本，样本构造与任务覆盖有边界。[LongBench Pro v1](https://arxiv.org/abs/2601.02872v1) 比较 benchmark 时也须看单位：LongBench v2 的长度以 words 描述，而不是 tokens；二者不能只按数字大小排成长短排名。

### 9.3 修复方案

修复可能包括长序列训练、位置分桶评估、证据重排、RAG 预筛选和上下文压缩。每种修复都要重新比较质量与成本，不能把“更长输入”本身作为目标。

修复实验要逐项变更而不是一次全改：先固定模型和问题集合，把唯一证据随机放到首、中、尾并控制相同干扰长度；再构造需要两份或三份远距离来源的问题；最后加入冲突值、近似实体和不可回答题。证据重排可以改善可见性，却改变了输入分布；RAG 预筛选可能降低 token 成本，却引入召回遗漏；长序列微调改变了训练预算和数据暴露。每一种都要有相应的对照和失败桶。若系统只在筛选后保留的题上好转，应同时报告被筛掉的题和 evidence-set recall，避免把召回器造成的选择偏差误写为模型理解变强。

评估单位也要落到题目而不是一句营销数字。把同一问题复制成开头、中间、结尾三个版本时，应保持事实内容和干扰材料等价，并随机化顺序，避免模型记住答案或评测集模板。若一个题有两处必需证据，答案必须逐项匹配证据 ID；只要少一处，即按事先写好的 rubric 计为组合失败。对无法回答的题，系统应允许声明“不足以回答”，并单独计算无证据时的误答率；否则一味追求 recall 会鼓励模型在证据不全时猜测。最后，把质量曲线按长度与位置分桶，与 token、prefill 延迟、KV cache 和每请求成本并排展示，才能知道何时应选更长窗口、RAG 预筛选或混合方案。

## 10. Worked case：MoE 的质量提升来自哪里

以下数值都是教学构造值。一个 MoE 模型总参数是 dense baseline 的 4 倍，但每 token active FLOPs 接近 baseline。实验显示验证 loss 更低；路由日志显示 40% 的 token，其 top-2 组合落在两个高负载专家上；all-to-all 通信占总 step time 的 28%；另外，3% 的请求 expert assignment 因容量限制被丢弃。这里的 40% 以 token 为分母，3% 以全部请求 assignment 为分母，两者不能互换，也不能仅从这两个比率推断具体有多少 token 的表示受影响。

可以把 assignment 分母算出来。取一个构造 microbatch 的 100 个 token，top-2 路由产生 200 个 assignment；若四专家的 capacity factor 为 1.25，则均衡容量是 $\lceil1.25\times200/4\rceil=63$ 个 assignment/专家。假设路由请求数为 $[69,50,43,38]$，总数仍为 200，第一位专家超过 63 的容量 6 个 assignment，因此 drop ratio 为 $6/200=3\%$。平均负载为 50，总体标准差约 $\sqrt{138.5}=11.77$，所以 CV 约为 0.235。这个小账本说明“3% dropped”可以与整体 CV 并存，但平均或 CV 都不会告诉我们被截断的 assignment 属于哪些 token、它们是否还有次选路由，必须检查逐 token 的 overflow 处理和任务结果。

通信占比也要回到总 step 的分母。假设一个 step 为 100 ms，其中 all-to-all 是 28 ms；即使某项优化让 all-to-all 时间减少 25%，实际节省也只是 $28\times0.25=7$ ms，step 变成 93 ms，吞吐提升约 $100/93-1=7.5\%$，而不是 25%。这个手算例不代表某实现能减少四分之一通信，只说明局部 speedup 不能直接称为端到端收益。验证 loss 更低也可能来自总参数或训练量增加，需要按主张选择公平对照。

此时不能直接写“MoE 用四倍参数换来更高效率”。需要至少做三组对照：

1. 固定 active FLOPs 比较 dense 和 MoE 的质量。
2. 固定总训练 token，改变 capacity factor 和 router loss。
3. 在相同拓扑下记录负载、drop、通信和端到端吞吐。

还应记录验证集、多个 seed、每个专家的请求量/实际执行量、overflow 后的 fallback、每 step 的尾部时延和 checkpoint 成本。把 router bias、capacity、expert placement 分开改，才能判断负载均衡究竟改善了质量、吞吐还是只改变了其中一项。

“公平比较”不能要求一个 baseline 同时匹配所有资源，因为 MoE 的目标正是改变参数存储与激活计算的关系。更诚实的做法是画出两组边界：一组按训练 compute 或 active FLOPs 对齐，回答在相近算力下质量如何；另一组按总参数/权重存储或服务内存对齐，回答部署容量约束下质量如何。另附作者原始配置，可以帮助读者判断论文结论属于哪条边界。训练 token 数、数据去重、更新次数、序列长度和优化器也要写清；若 MoE 因更大的总参数或额外训练 token 获得更低 loss，不能把差异全部归到路由机制。

排查质量时还要看 holdout 的覆盖：验证集若和训练数据近重复，可能看不到稀有专家对新领域的失败；若合并所有领域平均，少量长尾领域可被主流数据盖住。可以预先固定领域切片、每片最小样本数和不可回答问题，按相同 seed 训练多个模型并做配对评估。只有当质量变化在不同 seed 和相应任务切片上保持、同时资源账本可复算，才有理由把观察到的改进归因给特定 MoE 设计。

如果修复负载后质量保持提升、通信占比下降，才有证据说明专家容量对结果有贡献；如果质量提升消失，原始结果可能主要来自不公平的有效训练预算或数据路径。即便修复后有效，也只能说在本模型、训练 token 和拓扑下观察到这项收益，不能由一个 case 推出“稀疏总参数总比 dense 划算”的普遍规则。

对照结果还应按预测解释而不是只看是否“显著”。若 drop 从 3% 降到 1%，但验证 loss、领域切片和 tokens/s 都没有可重复变化，最稳妥的结论是容量策略减少了 assignment 丢弃，尚未观察到相应任务收益；如果吞吐提升而质量不变，则可能是系统效率收益；若质量提升但 all-to-all 占比上升，则要评估质量—成本折中。每个方向对应不同的使用决策，不能压成单一 MoE score。

一个复现报告还应把“未发现提升”与“证据支持等效”分开。若多个 seed 的区间很宽，当前实验可能只是没有足够精度区分两条曲线；若预先设定了实际重要差异界值，并且区间落在等效范围内，才有更直接的等效证据。否则应如实报告估计方向、波动和剩余不确定性，不因某个单次 loss 更低就宣称算法胜出，也不因一个不显著结果断言两种 router 相同。

运行窗口还必须和质量曲线对齐。若一个配置训练 10,000 step、另一个只训练 2,000 step，最终 loss 不是等训练预算比较；若只在无故障窗口记录通信时间，也不能由此声称恢复成本更低。报告应注明预热区间、测量 step 数、有效训练 token、checkpoint/恢复是否计入、掉步和重启次数，使读者能判断负载变化是否只出现在短期。

## 11. Worked case：RAG 的答案正确但引用错误

以下数据是教学构造值。某知识助手在 100 个问题上的答案准确率从 72/100 提高到 81/100，绝对增加 9 个百分点；但在一个单独的引用审计样本中，20 条回答共抽取 100 个可核查主张，只有 55 个能被所附证据支持，因此 claim support ratio 为 $55/100=0.55$。两个分母不同，不能把 55% 解释成“81 个正确答案中有多少被支持”，也不能据此计算二者的交集。

分析 trace 后发现，检索器在不少失败样本中召回了正确文档，generator 却用参数记忆补充了文档中没有的日期和条件；引用只放在段尾，读者误以为整段都有证据。要验证这个解释，需对每条可核查主张标注原文 span、文档版本和支持关系，并保留回答句子到引用 ID 的映射。文档中有同一实体的旧值和新值时，还要标出时间；正确引用过期文档仍不算正确答案。审计样本要明确抽样方式，不能只挑容易找到引用的句子。

修复应拆开进行：对每个可核查 claim 标注证据 span，要求引用与 claim 对齐；对无证据内容要求模型标注不确定；对过期版本和权限文档加入过滤；再分别报告 answer accuracy、support ratio、citation precision 和拒答/澄清率。

随后用相同的 100 个问题和相同 generator 做一组最小对照：不检索、普通检索、带 reranker、注入人工标注的 oracle evidence。若 oracle evidence 明显提高 support ratio，而普通检索没有，主要缺口可能在召回或排序；若 oracle 与普通检索的引用支持都低，则应调查 context packing、证据位置、生成约束或主张抽取，而不是继续盲目扩大 top-k。所有版本还要对齐输入 token 上限和延迟预算；oracle 组用于定位上限，不是可部署 baseline。

报告结果时分开列答案正确率、必要证据召回、可核查主张支持率、引用精度、拒答率、每请求 token 与 p95 延迟，并逐层标注分母。若一个方法提高准确率却降低支持率，决策要看任务是否允许参数记忆补充、是否必须可审计和错误代价多大。这个案例说明“召回正确”和“回答有依据”是两个不同 claim；只有把召回、使用、引用和文档时效接成可回放的证据链，才知道下一步该修检索器、上下文构造还是生成策略。

一次可审计的人工检查可以按“问题—检索候选—最终 context—答案 claim—引用 span”串成五列。标注者先独立判断每个 claim 是否可核验、引用是否蕴含该 claim、来源版本是否在有效时间内；有争议的样本再由第二人按预先约定的规则裁决。报告应保留标注一致率或冲突量，并公开抽样种子和抽样层，而不是仅展示几条成功示例。自动 claim verifier 可以扩大覆盖，但必须用人工样本检查它漏掉的冲突、时间限定和否定关系；若 verifier 只在容易句子上准确，它得到的 support ratio 会系统性偏高。

复现实验还应保留三类错例：检索阶段未找到证据、证据进入上下文但没有支持答案、答案正确却指向错误来源。三者分别对应召回、生成忠实性和引用归因问题。把错例连同文档 snapshot 和原文 span 保存后，下一次换 embedding、reranker 或 citation prompt 才能在同一问题上做配对比较；若换过语料或标注规则，历史百分比不能直接拼成改进曲线。

假设下一轮在同样的 100 个主张审计样本中，支持主张由 55 个升到 70 个，差值是 15 个百分点；若答案准确率仍是 81/100，这表示证据可追溯性改善，但没有观测到准确率变化。只有在抽样、标注规则和文档版本不变时，这个配对差值才有解释价值；若 claim 抽取器换了，分母改变，70% 和 55% 也不能直接相减。该例说明即使“最终正确率没有涨”，RAG 研究仍可能在来源支持、审计性或时效性上改善，只须把它称作正确的目标指标。

## 12. Worked case：Agent 成功率与调用预算

以下数据都是教学构造值。某 Agent 在 100 个任务上完成 72 个，任务成功率为 72%；平均每个任务调用工具 18 次，其中 12 个任务因重复重试造成超时。另一个简单 baseline 完成 66 个，成功率 66%，平均每任务调用 5 次。两者成功率相差 6 个百分点；如果平均数覆盖全部 100 个任务，则 Agent 共约 1,800 次工具调用、baseline 约 500 次。按完成任务归一化，分别约为 $1{,}800/72=25$ 和 $500/66\approx7.58$ 次调用/成功任务，Agent 约为 baseline 的 3.3 倍。

案例还假设按照“模型输入输出费用 + 工具费用 + 重试带来的资源 + 人工接管时间”组成的同一账本，baseline 每个成功任务成本为 Agent 的 0.42 倍。这个成本比是单独给定的构造观测，不能从调用次数直接推出；若报告没有披露各项单价、人工工时和成功任务分母，就无法复算 0.42。调用数、成功率和单位成功成本回答的是不同问题，必须同时保留。

如果任务价值高且允许更长延迟，Agent 多完成的 6 个任务可能值得额外资源；如果是高并发客服，调用次数、p95 延迟和超时可能决定方案不可用。12 个超时占全部任务 12%，但超时是否都属于 28 个未完成任务、是否产生部分副作用，也要在 trace 中说明。报告还应给出每任务步骤分布而非只给均值、成功/失败任务的分位数、错误恢复率、循环次数、状态变化和人工接管；均值会遮住少数极长 trace。

修复可以包括计划检查点、工具错误分类、幂等键、循环检测、预算上限和人工升级。先按失败发生顺序抽样查看 trace：工具是否报错、Agent 是否读到错误、重试是否改变状态、最终判定是否核验了目标。对同一批任务做反事实重放，分别关掉自动重试、加入检查点或限制步数；固定模型、工具版本和初始环境，观察任务成功、成本及副作用如何共同变化。减少调用不能成为唯一目标，否则可能过早停止而降低成功率；一次可复查的比较必须说明哪类失败减少、哪类代价上升。

平均调用次数还会掩盖“成功任务用了多少步、失败任务又烧掉多少资源”。应至少把任务分为直接完成、成功恢复、预算耗尽、工具不可用、状态冲突和人工接管，分别报告成功率、总 token、调用次数和 p95 完成时间。两个 Agent 都是 72/100 成功时，如果一个用 1,800 次调用、另一个用 900 次调用，单看任务准确率会漏掉一半资源差；如果较省的系统把高风险任务转给人工，则还要把人工成本和等待时间计入，不应将它算作模型独立成功。

100 个任务也只是一个教学规模。正式比较要说明任务是如何抽样的、难度和风险是否分层、是否对同一任务配对运行，以及失败是否集中在某类任务。对写操作还应把状态变更正确率、重复执行和错误权限单列，不能让大量只读任务的成功率掩盖少数有副作用的失败。预算策略只有在任务价值、失败代价和人类接管规则明确时才可讨论；否则“值得采用”只是未定价的意见。

若用 $v$ 表示每个成功任务的收益，用 $C_A$ 与 $C_B$ 表示两套系统按相同口径计算的每任务总成本，那么在这个 100 题例子里，Agent 相对 baseline 多完成 6 题，粗略净差可写作 $6v-100(C_A-C_B)$。但现有案例只给了单位成功成本比 0.42，未给 $v$、绝对成本和风险损失，因此不能算出部署的盈亏点。研究报告应把这个“不能决策”写清楚，而不是从 72% 与 66% 单独导出部署建议。

如果成功任务还需人工抽查或审批，人力时间也应进入同一账本；工具失败后的撤销、状态核对和补偿操作则属于失败成本。产品可以把人工协作后的任务计为完成，但报告要区分模型独立完成与人机协作完成。高风险写操作也可能采用拒绝或人工复核门槛，低风险只读查询才允许自动重试。论文实验若没有模拟这些动作，最多支持其任务完成率或工具协议结论，不能直接支持实际业务效益。

## 13. 可运行的组合审计 demo

下面的纯 Python demo 使用合成记录，分别计算长上下文证据定位、MoE 负载、RAG 召回与引用支持，以及 Agent 工具执行成功。它不连接真实模型、索引或工具，只演示为什么一个总分需要拆成多个信号。

代码状态：静态审阅，未运行（2026-11-04；Python 3.7+，仅标准库）。

~~~python
from math import sqrt


def mean(values):
    return sum(values) / len(values) if values else None


def safe_ratio(numerator, denominator):
    return None if denominator == 0 else numerator / denominator


def population_std(values):
    if not values:
        return None
    center = mean(values)
    return sqrt(mean([(value - center) ** 2 for value in values]))


def load_cv(values):
    center = mean(values)
    if center in (None, 0):
        return None
    return population_std(values) / center


long_context = [
    {"position": "start", "success": 1},
    {"position": "middle", "success": 0},
    {"position": "end", "success": 1},
    {"position": "middle", "success": 1},
]
expert_load = [40, 18, 22, 20]
rag_queries = [
    {"relevant_retrieved": True, "claims": 2, "supported": 2},
    {"relevant_retrieved": True, "claims": 3, "supported": 2},
    {"relevant_retrieved": False, "claims": 1, "supported": 0},
]
agent_trace = [
    {"tool_ok": True, "final_ok": True},
    {"tool_ok": True, "final_ok": True},
    {"tool_ok": False, "final_ok": False},
    {"tool_ok": True, "final_ok": False},
]

long_recall = mean([row["success"] for row in long_context])
middle_recall = mean(
    [row["success"] for row in long_context if row["position"] == "middle"]
)
expert_load_cv = load_cv(expert_load)
rag_recall = safe_ratio(
    sum(row["relevant_retrieved"] for row in rag_queries), len(rag_queries)
)
support_ratio = safe_ratio(
    sum(row["supported"] for row in rag_queries),
    sum(row["claims"] for row in rag_queries),
)
tool_success = mean([row["tool_ok"] for row in agent_trace])
agent_success = mean([row["final_ok"] for row in agent_trace])


def rounded(value):
    return None if value is None else round(value, 4)


signals = {
    "long_recall": rounded(long_recall),
    "middle_position_recall": rounded(middle_recall),
    "moe_load_cv": rounded(expert_load_cv),
    "rag_recall_at_k": rounded(rag_recall),
    "citation_support_ratio": rounded(support_ratio),
    "agent_tool_success": rounded(tool_success),
    "agent_task_success": rounded(agent_success),
}
actions = []
if signals["middle_position_recall"] is None or signals["middle_position_recall"] < 0.75:
    actions.append("add_position_and_multi_evidence_tests")
if signals["moe_load_cv"] is None or signals["moe_load_cv"] > 0.30:
    actions.append("repair_router_load_balance")
if (
    signals["rag_recall_at_k"] is None
    or signals["citation_support_ratio"] is None
    or signals["rag_recall_at_k"] < 0.80
    or signals["citation_support_ratio"] < 0.80
):
    actions.append("repair_retrieval_and_claim_citations")
if signals["agent_task_success"] is None or signals["agent_task_success"] < 0.80:
    actions.append("add_trace_recovery_and_budget_tests")
decision = "continue_after_system_repairs" if actions else "continue_to_shadow_eval"

assert mean([]) is None
assert safe_ratio(0, 0) is None
assert load_cv([0, 0]) is None

for name, value in signals.items():
    print(f"{name}={value}")
print(f"actions={actions}")
print(f"decision={decision}")
~~~

下面的结果是对代码输入逐项手算的预期值，不是执行输出。长上下文有 4 条记录，其中 3 条成功，所以整体 recall 为 $3/4=0.75$；中间位置只有两条记录、1 条成功，因此 middle-position recall 是 $1/2=0.50$。两者差 25 个百分点，说明总体值会掩盖位置桶失败。

MoE 负载为 $[40,18,22,20]$，均值是 25；总体方差为 $(15^2+(-7)^2+(-3)^2+(-5)^2)/4=77$，标准差约为 $\sqrt{77}=8.775$，负载 CV 约为 $8.775/25=0.3510$。RAG 有 3 个查询，其中 2 个召回相关项，Recall@k 为 $2/3\approx0.6667$；三个回答共有 $2+3+1=6$ 个可核查主张，支持的有 $2+2+0=4$ 个，因此支持率也为 $4/6\approx0.6667$。相同的小数并不代表两项指标测量同一件事。

Agent trace 中工具执行成功 3 次，所以 tool success 为 $3/4=0.75$；最终任务只成功 2 次，所以任务成功率为 $2/4=0.50$。第四条 trace 的工具成功但最终失败，正好说明工具端成功不能替代任务端验收。按代码中的演示阈值，中间 recall 低于 0.75 会加入位置与多证据测试；CV 高于 0.30 会请求检查 router 负载；RAG recall 或引用支持低于 0.80 会请求修复检索和 claim 引用；任务成功率低于 0.80 会请求加入 trace、恢复和预算测试。因此预期动作字符串包含这四项，decision 为 continue_after_system_repairs。

这些阈值只是程序分支的演示值，不是发布门槛、通用安全阈值或统计显著性判断；输入也不足以估计任何模型的真实能力。断言仅检查空列表、零分母和零负载时的返回约定。代码静态阅读确认指标分母与上述输入相符，但本轮没有执行程序，不能把本段写成“测试通过”或实测结果。

样本量本身就是这个 demo 要提醒读者的另一项信号。middle bucket 只有 2 题、成功 1 题；若暂用独立 Bernoulli 的 plug-in 标准误近似，$p=0.5,n=2$ 时 $\sqrt{p(1-p)/n}\approx0.354$，单次结果极不稳定。Agent 最终成功率也只有 4 条 trace；$p=0.5,n=4$ 的近似标准误仍为 0.25。这里的近似值不是小样本区间估计，更不能据此宣布某系统真实成功率就是 50%；它是在提醒下一步扩大分层样本、按同一问题配对比较，并报告不确定性。

把 demo 接到真实研究时，每条记录还要带上稳定的 task ID、模型和 tokenizer revision、上下文长度/证据位置、文档与索引版本、随机种子、工具 schema 和初始环境。RAG 主张的支持标签要来自明确的标注协议；Agent 成功标签要由环境状态或独立验收确认，不能只看它自己说“完成”。表格中的四个动作是基于预设阈值的排查提醒，研究者仍需打开原始错例，选择一项有判别力的修复实验，并重新按相同问题和预算测量。这样 demo 才能从静态指标计算过渡到可复查的实验设计，而不会把状态摘要误当成结论。

当前输入会同时触发四个排查动作，但这不意味着应一次修改四处。先按目标任务的失败 trace 找到第一处数据流断点，例如若 RAG 证据本来就缺失，先修检索并重新测证据集合召回，再评估生成；如果 evidence 已经完整进入 prompt，再检查 claim 引用。MoE CV 偏高可以并行记录，却不要在同一轮同时改 router loss、capacity 和 expert placement，否则结果无法归因。decision 字符串表示“需要继续诊断”，不代表已经找到根因或系统可继续上线。

对真实实验，固定一组代表性成功、失败和边界样本作为诊断集，再用独立 holdout 估计总体变化。若使用 3 个随机种子，应逐 seed 保留原始记录并报告均值、离散度和异常失败；先平均全部 trace 会把某个 seed 的路由塌缩或环境故障藏起来。静态 demo 没有抽样、置信区间或版本记录，正因为它缺少这些对象，才只能用于讲清指标之间的关系。

## 14. 常见失败模式与修复顺序

### 14.1 Long Context 最大长度很大但中间信息丢失

检查位置分布、训练长度、干扰比例、提示格式和是否只测 single needle。再做多证据、冲突证据和引用测试。若输入成本过高，比较 RAG 预筛选、上下文压缩和更长训练，而不是只增加 max position。

### 14.2 FlashAttention 让 kernel 变快但端到端没有提升

检查 prefill/decode 比例、padding、通信、KV cache、batch、kernel fallback 和数据搬运。算子加速被其他关键路径掩盖时，不能把局部 speedup 写成服务吞吐提升。

### 14.3 MoE 专家塌缩或通信成为瓶颈

检查每专家 token 分布、router entropy、capacity、dropped tokens、all-to-all 和拓扑。降低负载损失不一定解决热点；可能需要改变路由、容量、专家放置或 batch 组织。

### 14.4 RAG 召回好但答案不忠实

检查 context packing、证据位置、冲突文档、引用要求和生成模型是否使用参数记忆。增加 citation verifier、claim-level evaluation 和无证据时的澄清/拒答，而不是盲目增大 top-k。

### 14.5 Tool Use 参数合法但动作错误

把 schema validation、业务校验、权限检查和执行结果分开记录。对写操作增加 preview、审批、幂等键和回滚；对工具返回的外部文本做来源标记和注入隔离。

### 14.6 Agent 进入循环或错误级联

保存每一步 state、action、observation 和状态差分，区分瞬时错误、参数错误、权限错误和未知副作用。加入步数预算、重复状态检测、检查点和人工接管，不能只提高模型温度或让它“再想一遍”。

排查应沿系统数据流从最早可观察的失败点向后走，而不是先给最后答案贴“幻觉”标签。以下是一个教学构造的 RAG 故障样本：200 个问题中有 40 个最终失败；若按“第一处不可恢复错误”互斥标注，12 个在初始召回阶段没有必需证据，8 个候选中有证据却被重排或预算过滤，14 个证据已进入 prompt 但答案未使用，6 个答案内容正确但 citation 映射错误。以 40 个失败为分母，四类占比分别为 $12/40=30\%$、$8/40=20\%$、$14/40=35\%$ 和 $6/40=15\%$。这组假设数字会把修复顺序指向先查召回/排序，再查证据使用与引用映射；若类别允许重叠，比例就不能相加为 100%，报告必须说明标注规则。

每类修复后应回放相同失败案例和一组未失败控制样本，并只改一个影响面明确的因素。若移动证据位置后答案变好，仍要确认它不是同时改变 token 预算或答案泄漏；若关闭 Agent 重试后副作用消失，还要确认任务成功率和人工升级量。trace 能缩小候选根因范围，却不是因果证明；日志缺失、错误标注或 grader 不稳定时，应先修观测协议，并将结论保持为“疑似原因”。

工具链也可以按这个顺序逐层定位。一个教学构造的 batch 有 100 次调用，其中 10 次失败；逐条看 first-failure trace 后，3 次因 JSON 字段缺失被 schema 拒绝，2 次因权限策略拒绝，4 次执行超时，1 次工具已成功但模型误读结果。调用失败率为 $10/100=10\%$，但适用修复完全不同：补字段示例不能解决授权拒绝，放宽权限也不能修复超时，增加重试还可能重复副作用。研究者先修复类别标签，再按每类原始调用数报告比例，并把失败前后状态差异和恢复结果附上。

诊断结论应标明证据等级。若只从最终答案猜“可能是中间位置丢失”，这是候选解释；若 trace 显示目标片段进入了 prompt 而模型没有用它，是更窄的观察；若在随机化位置的配对实验中仅移动证据就稳定改变表现，才有更强的机制证据。每一级结论都不能跳过下一项可证伪测试。若观测系统本身漏记工具返回或截断长 trace，必须先修复日志，再讨论模型根因。

工具链也可以按这个顺序逐层定位。一个教学构造的 batch 有 100 次调用，其中 10 次失败；逐条查看 first-failure trace 后，3 次因 JSON 字段缺失被 schema 拒绝，2 次因权限策略拒绝，4 次执行超时，1 次工具已成功但模型误读结果。调用失败率为 $10/100=10\%$，但适用修复完全不同：补字段示例不能解决授权拒绝，放宽权限也不能修复超时，增加重试还可能重复副作用。研究者先修复类别标签，再按每类原始调用数报告比例，并把失败前后状态差异和恢复结果附上。

## 15. 如何复现一篇组合系统论文

### 15.1 先选择一个窄 claim

不要同时复现 Long Context、RAG 和 Agent 的全部功能。可以选择：

> 在相同 generator、证据集合和输入 token 预算下，reranker 是否提高多证据问题的 claim support ratio？

或：

> 在相同 active FLOPs 和训练 token 下，某种 router loss 是否降低 expert load CV 且不降低任务质量？

窄 claim 能让实验明确知道改变的是检索、路由还是生成。

以第一个问题为例，先定义“多证据问题”要求两份指定来源都出现，并将 claim support ratio 限定为回答中可人工核验的主张。处理组只更换 reranker，query、候选集、generator、解码参数、输出上限和检索后 token 预算保持一致；否则结果变化可能是模型、证据数量或生成长度的变化。还需预先定义如何处理无可核验主张、拒答、超时和缺失引用，避免看到结果后再改分母。

### 15.2 固定接口和预算

至少固定：

1. 模型、tokenizer、位置编码和 checkpoint。
2. 数据、文档版本、索引构建时间和权限字段。
3. 输入/输出 token、top-k、候选数和最大 Agent 步数。
4. 工具 schema、版本、环境状态、错误注入和重置方式。
5. 计算精度、硬件、网络拓扑和 batch。
6. 指标定义、分母、失败状态和成本口径。

组合系统最容易因为隐藏预算不一致而产生虚假提升。一个 Agent 如果多允许十步，一个 RAG 如果多放三倍文档，一个 Long Context 如果使用更长输入，都应该在比较中显式记录。

一个可复算的协议例子是：固定 120 道问题、两个系统配置和 3 个预先选定的随机种子，每题每配置每 seed 运行一次，则每个配置有 $120\times3=360$ 次任务运行，共 720 次；若每个 Agent 最多 6 次工具调用，则每配置的调用上限是 $360\times6=2{,}160$，实际调用仍须从 trace 汇总。将同一题同一种子下的结果配对，任务成功率分母为 360；citation support 的分母则是所有已标注的可核验 claim 数，不能拿 360 个任务数代替。超时和环境错误要保留为指定失败类别或报告排除规则，不得静默删掉。

“相同长度”也要定义单位和语义。tokenizer 不同会让相同字符数转成不同 token 数；有些 benchmark 用 words 描述上下文长度，有些用 tokens。复现时按原协议记录单位，再另报转换后的输入长度，不能把 100K words 写成 100K tokens。对长上下文论文，还要报告真实截断点、相关证据位置及是否启用前缀缓存；对 RAG 论文则固定语料 snapshot、权限过滤、索引构建时间、embedding 与 reranker 版本。

### 15.3 证据分层

可以把复现结果分成四层：

1. **接口复现**：输入、工具或索引能够运行。
2. **机制复现**：观察到预期的 attention IO、router load 或 recall 变化。
3. **任务复现**：目标 benchmark 或真实任务指标改善。
4. **系统复现**：延迟、吞吐、成本、权限和故障恢复也符合主张。

只完成第一层不能声称完成论文主张。系统论文还要保存 trace、硬件和版本，否则别人无法解释差异来自算法还是环境。

证据链还应能从最终数字往回追：任务 ID 对应哪个数据和标注版本；证据片段来自哪个文档、哪次解析和哪版索引；模型请求用了哪个 checkpoint、tokenizer、prompt 与解码配置；工具 action 使用哪个 schema、权限上下文和环境状态；最终评分由哪个 rubric、grader 版本或人工规则给出。对 Agent 至少保存完整 action/observation trace 和状态差分，对 MoE 保存按层/专家聚合前的路由统计，对长上下文保留原始长度与证据 span。脱敏不能改变可复现所需的对象关系，但不得把真实用户数据或凭据写入公开实验包。

复现等级要与窄 claim 对齐：如果 claim 只是“检索召回更多必需证据”，接口和任务复现可能足够回答它；如果 claim 是“用户请求成本更低且安全”，就还需要系统层成本、权限拒绝、故障恢复和副作用测试。单模块测试通过不能替代系统复现；系统复现若与论文不一致，也不应强行把差异归咎于算法，先对齐版本、数据、硬件、预算和评分器。

## 16. 如何写这条论文线的研究报告

一份完整报告可以按以下叙事展开：

1. 问题是输入长度、模型容量、知识时效、外部执行还是多步可靠性。
2. 机制把能力从哪里引入，改变了哪条计算路径。
3. 需要什么额外数据、索引、专家、工具或环境。
4. 在什么预算下与哪个 baseline 比较。
5. 质量、效率、成本和安全指标的分母是什么。
6. 失败来自召回、路由、位置、协议、状态还是生成。
7. 哪些结果能外推，哪些只能留在当前模型和环境。
8. 下一步是优化模型、修数据、改系统、限制权限还是停止扩展。

例如，不能把“1M 输入通过”“RAG recall@10 为 0.9”“Agent 完成一个 demo”并列写成系统具备长程智能。应说明 1M 下的位置分布和任务成功，recall 是否覆盖所有所需证据，Agent 是否在受控环境中完成了真实状态变化，以及这些能力的单位成本。

报告可以用一张 claim—evidence—limit 表收束：每条 claim 写出对象和预算，旁边列支持它的测量、反例/失败桶、证据级别和未回答的问题。比如“在固定 top-5、同 generator、每题 1,200 输入 token 的测试中，reranker 使 360 次运行的任务成功率提高”仍需附上任务配对差、claim-level 支持率、延迟与索引成本；“比所有 RAG 都好”则超出了这个实验。若只有论文自己的 benchmark 和单次运行，应标成作者在该协议下报告，而不是独立复现或稳定提升。

最终决策应回到本章开头的共同问题：增加的是哪一种能力来源，额外预算去了哪里，失败责任是否能从 trace 或证据链中定位，结果是否优于匹配预算的 baseline，剩余风险是否可接受。报告可以得出“继续做针对某失败层的实验”“只在受限场景部署”“先修观测/权限”“当前证据不足”或“停止该路线”；负结果同样有价值，只要清楚说明它排除了什么、没有排除什么，以及下一步最有判别力的实验是什么。

例如一个明确标成教学构造的报告可以写：reranker 让同一组 360 次任务的答案准确率从 68% 到 70%，提高 2 个百分点；人工 claim 审计的支持率从 55% 到 70%，提高 15 个百分点；p95 延迟从 1.2 秒到 1.8 秒，增加 $0.6/1.2=50\%$。这不是一个可以用“总体更好”概括的结果：对需要出处的研究助手，支持率可能更重要；对交互延迟敏感的客服，50% p95 上升可能不可接受。报告还需给出配对区间、索引成本和按任务类型切片，才能决定差异是否稳定、是否值得预算。

与论文结果不一致时，应先列出版本、数据、预算、硬件和 grader 的逐项偏差，再尝试有记录的诊断实验。不能删掉“未复现”的 seed、挑最好 prompt，或在事后改变阈值来制造一致性。一次负结果可以说明某个 claim 在声明条件下没有得到支持，但若样本量不足或实现关键路径尚未对齐，它也不能证明该方法在所有设置下无效。结论强度必须与实验覆盖相匹配。

## 17. 资料与证据边界

长上下文与位置机制可参考 [RoFormer: Enhanced Transformer with Rotary Position Embedding](https://arxiv.org/abs/2104.09864)、[Train Short, Test Long: Attention with Linear Biases Enables Input Length Extrapolation](https://arxiv.org/abs/2108.12409)、[FlashAttention](https://arxiv.org/abs/2205.14135) 和 [FlashAttention-2](https://arxiv.org/abs/2307.08691)。这些论文分别支持 RoPE、ALiBi、IO-aware exact attention 和并行实现的技术脉络；本章关于有效长度、位置分桶和生产成本的结论需要独立测量。

长上下文利用率可参考 [Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172) 和 [LongBench](https://arxiv.org/abs/2308.14508)。它们支持位置、任务和长文档评估的重要性；单一 needle 测试不能代表多证据推理或所有模型的生产行为。

KV cache 服务系统可参考 [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180)。该论文支持分页式 KV cache 管理和 serving 吞吐的系统背景；具体收益依赖模型、硬件、batch、解码和 runtime 版本。

稀疏专家路线可参考 [Sparsely-Gated Mixture-of-Experts](https://arxiv.org/abs/1701.06538)、[GShard](https://arxiv.org/abs/2006.16668) 和 [Switch Transformers](https://arxiv.org/abs/2101.03961)。它们支持稀疏路由、专家并行、负载均衡和容量控制的论文脉络；本章的 active FLOPs 和 step-time 公式是教学记账，不是跨实现的精确成本模型。

RAG 的基础路线可参考 [REALM](https://arxiv.org/abs/2002.08909)、[Dense Passage Retrieval](https://arxiv.org/abs/2004.04906) 和 [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks](https://arxiv.org/abs/2005.11401)。它们支持可学习检索、稠密段落召回和参数/非参数记忆结合的研究背景；具体 chunk、索引、权限和引用结果仍需在目标语料上验证。

工具和交互推理可参考 [Toolformer](https://arxiv.org/abs/2302.04761)、[ReAct](https://arxiv.org/abs/2210.03629) 和 [Tree of Thoughts](https://arxiv.org/abs/2305.10601)。这些论文支持工具调用、reasoning/action 交替和搜索式 thought 的研究方向；它们不自动证明生产工具调用安全，也不能把受控 benchmark 的成功率外推到任意 Agent。

Agent 评估可参考 [WebArena](https://arxiv.org/abs/2307.13854) 和 [AgentBench](https://arxiv.org/abs/2308.03688)。它们支持在环境和多任务上测量 Agent 的必要性；真实业务还要加入权限、状态副作用、隐私、成本、回滚和人工接管。

本章的 worked case、Python demo、合成负载、检索结果、Agent trace 和决策字符串均为教学构造。真实复现实验应保存模型配置、训练长度、位置方案、文档 snapshot、索引版本、router 统计、工具 schema、环境状态、完整 trace、硬件信息和失败记录，并明确区分论文事实、项目实测和教学近似。

## 18. 结语：从单次生成到可复查的系统能力

Long Context 让模型看到更多输入，但有效能力取决于位置、干扰、训练、推理成本和多证据利用。MoE 让模型拥有更大总容量，但 active compute 之外还有路由、负载、通信和存储。RAG 让知识可更新、可引用，但检索和证据链成为新的责任边界。Tool Use 让模型连接计算和业务系统，但结构化参数不等于授权动作。Agent 把任务展开为状态循环，但长程可靠性取决于恢复、停止、权限和成本。

阅读这条论文线时，不要只问“哪个方法更强”。更好的问题是：能力从哪里来，预算转移到了哪里，哪个模块对失败负责，论文的 baseline 是否公平，评估是否覆盖真实瓶颈，以及在什么边界内结论成立。

当研究者能够把模型、上下文、专家、检索、工具和环境拆成不同对象，再用任务成功、证据支持、路由负载、调用轨迹、延迟、成本和安全状态共同验证时，这些方向才不再是新闻式名词，而成为可以复查和迭代的系统工程。
