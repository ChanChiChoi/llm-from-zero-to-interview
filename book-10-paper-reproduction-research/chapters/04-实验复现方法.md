# 第四章：实验复现方法

复现是把论文中的主张重新变成可观察、可比较、可解释的实验。它既不是把作者仓库成功启动，也不是把一个分数追到小数点后一位，而是在明确的条件下回答：论文的核心主张（claim）是否再次出现？如果没有出现，差异来自数据、模型、实现、评估、环境、随机性，还是论文主张本身超出了可重复范围？

复现工作的价值正在于这条因果链。一次运行得到 `0.73`，本身几乎没有解释力；如果知道使用了哪个数据快照、哪个模型检查点（checkpoint）、哪个分词器（tokenizer）、哪个提示词（prompt）、哪个配置（config）、哪个硬件和哪个评估脚本，结果才成为可以复查的工件（artifact）。若还做了强基线（baseline）、多个随机种子（seed）和关键消融，才有机会从“运行过”走向“验证了一个主张”。

初学者常把复现想成重复动作：下载代码、安装依赖、运行命令、比较分数。专家会把它看成控制变量实验和证据工程：先定义复现对象，再固定或记录变量，接着做低成本诊断，最后根据差异证据决定是修实现、收窄结论还是停止投入。

## 1. 复现的对象有四层

### 1.1 代码能运行不等于论文被复现

下面四层是本章用于整理证据范围的操作框架，不是全领域统一的术语标准，也不表示后一层必然包含前一层：

1. **运行复现**：代码可以安装、启动并完成一次运行。
2. **数值复现**：主要指标在预先说明的容差内接近论文结果。
3. **机制复现**：关键曲线、消融、中间变量或失败模式也呈现相同方向。
4. **主张复现**：在相同、相近或新的受控设置下，核心 claim 仍然成立。

运行复现证明的是 artifact 在当前环境可执行；数值复现证明的是一个结果近似出现；机制复现增强了归因证据；主张复现才回答“论文的研究结论是否站得住”。这四层可以分别成功或失败，不能用一个“复现成功”标签覆盖。

例如：

- LoRA 的运行复现是训练脚本完成；数值复现是质量接近论文；机制复现还要看到不同 rank 的折中和与全量微调的对照；主张复现则要判断低秩适配在指定任务范围内是否真的有效。
- DPO 的运行复现是 loss 正常下降；数值复现是偏好指标接近；机制复现要看 reference policy、长度分布和偏好行为；主张复现还要检查独立质量、安全和泛化。
- FlashAttention 的运行复现是 GPU kernel（核函数）加载；数值复现是输出和梯度误差可接受；机制复现是 IO、显存和 kernel 时间方向一致；主张复现要判断目标工作负载的端到端收益是否存在。

### 1.2 直接复现、分析复现和概念复现

当代码、数据和环境都可得时，可以进行直接复现；当关键 artifact 不可得时，需要进行分析复现或概念复现：

| 类型 | 条件 | 结论范围 |
| --- | --- | --- |
| 直接复现 | 同代码、数据和可比环境 | 可比较原始结果和机制 |
| 实现复现 | 依据论文自写实现 | 验证方法描述和趋势 |
| 数据替代复现 | 原数据不可得，使用公开替代 | 验证在替代分布上的行为 |
| 分析复现 | 重新分析公开结果或日志 | 检查统计和结论是否一致 |
| 概念复现 | 小规模实验实现核心思想 | 验证机制候选，不能声称完整复现 |

复现报告必须写清类型。用替代数据得到趋势可能很有价值，但不能写成“完全复现论文”；相反，无法获得私有 checkpoint 也不代表不能验证论文的核心机制，只是结论范围需要收窄。

### 1.3 复现等级不是质量排名

低等级复现不一定没有价值，高等级复现也不意味着论文在所有范围内正确。一个单卡 kernel 复现可能精确回答单卡速度问题，却不能回答集群扩展；一个替代数据的机制实验可能揭示假设，但不能支持原论文绝对分数。等级描述的是证据覆盖，不是研究者能力排名。

## 2. 先写复现目标，再决定实验规模

### 2.1 从核心 claim 开始

完整论文往往包含许多表格、模型和消融，全部复现的成本可能远高于判断需要。先把核心 claim 写成可检验句子：

- 方法相对强 baseline 提高任务质量。
- 方法在相同质量下减少训练或推理成本。
- 某个组件是主要收益来源。
- 方法在模型、数据或长度变化时保持方向。
- 方法解决了过去明确记录的 failure mode。

每条主张都要带上数据、模型、资源和评估协议。比如“更高效”要改成“在相同 GPU、dtype、序列长度、batch 和数值误差约束下，attention 路径的端到端第 95 百分位延迟（P95）下降”。没有这些条件，实验规模和成功标准都不清楚。

### 2.2 主张矩阵

可以用矩阵规划复现目标：

| 主张 | 最小观察 | 关键对照 | 需要的 artifact | 达到哪一层才有意义 |
| --- | --- | --- | --- | --- |
| 质量提升 | 指标方向和效应量 | 强 baseline | 数据、模型、评估脚本 | 数值/主张 |
| 成本下降 | 质量不降且资源下降 | 同硬件系统对照 | benchmark、trace、配置 | 机制/主张 |
| 组件必要 | 去掉或替代后差异 | matched ablation | 同数据和预算配置 | 机制 |
| 泛化 | 外部切片方向 | 时间/领域/规模切分 | 新测试集、统计脚本 | 主张 |
| 失败修复 | 目标 failure rate 下降 | 原系统和安全对照 | failure taxonomy | 机制/主张 |

这张表能阻止“先跑完整表格再想验证什么”。如果核心 claim 是成本收益，单独复现一个质量分数不是有效起点；如果核心 claim 是机制，先做全量规模训练也未必比小模型消融更有信息量。

### 2.3 复现成功标准要预先写

设论文报告值为 `Y_paper`，复现实验值为 `Y_rep`，可以先定义一个教学用容差：

~~~math
Error = |Y_rep - Y_paper|
Tolerance = max(abs_tol, rel_tol * |Y_paper|)
~~~

若 `Error <= Tolerance`，只能说该指标在设定容差内接近。`abs_tol` 和 `rel_tol` 不能随结果事后调整；它们要根据指标噪声、论文报告精度、业务重要性和资源差异预先说明。对于低频安全事件、非线性指标和大规模生成，单一数值容差往往不够，还要比较区间、切片和失败模式。

例如，假设论文准确率为 Y_paper=0.740，预先设绝对容差 abs_tol=0.010、相对容差 rel_tol=0.020。相对容差是 0.020×0.740=0.0148，所以总容差为 max(0.010, 0.0148)=0.0148。若复现值为 0.732，误差为 |0.732−0.740|=0.008，因此它在此规则下数值接近；若复现值为 0.701，误差为 0.039，则不接近。准确率按 0 到 1 记时，0.008 等于 0.8 个百分点。这个判定只回答“是否落入事先规定的数值窗口”，并不自动证明方法有效、多个 seed 稳定或其他主张成立；对接近容差边界的结果，还应结合不确定性和实验条件解释。

### 2.4 先复现 claim，不先复现所有表格

最小实验通过后，再扩大到更多任务、规模、seed 和 ablation。这样做不是降低标准，而是让每一笔昂贵计算都回答一个明确问题。完整表格复现适合在核心机制和协议已经对齐后进行；否则表格差异只能告诉你“不同”，不能告诉你“为什么不同”。

## 3. 建立实验清单（manifest）：让一次运行有身份

### 3.1 运行对象的组成

一次实验不是一个输出文件，而是由一组输入、代码、环境和结果构成的对象：

~~~math
Run = (RunID, Claim, PaperVersion, Code, Config, Data, Model, Tokenizer, Env, Hardware, Seed, Eval, Output)
~~~

其中任一对象发生变化，都应产生新的 RunID 或明确的版本字段。把“论文设置”写在 README 里不够，因为 README 可能更新、默认分支可能改变，数据和模型也可能被重新下载。主张和论文版本负责说明这次运行要检查哪句话、对应论文的哪个版本；配置、数据、模型和评估对象则负责固定实际执行条件。

### 3.2 Manifest 的最小字段

建议至少保存：

~~~text
run_id
claim_id
paper_id
paper_version
repository_url
repository_commit
config_path
config_hash
data_snapshot
data_schema_revision
preprocess_revision
model_checkpoint
tokenizer_id
environment_lock
container_digest
hardware_topology
distributed_strategy
random_seed
evaluation_script
evaluation_version
run_timestamp
output_artifact
raw_metric_artifact
~~~

字段名称可以按项目调整，但语义不能消失。`model_checkpoint` 和 `tokenizer_id` 不能只写一个模型名；`environment_lock` 不能只写“CUDA 环境”；`evaluation_script` 不能只写“官方评估”。

### 3.3 Artifact 的血缘关系

一个可复查的结果需要能沿着下面的关系回溯：

~~~text
paper claim
  -> experiment plan
  -> code commit + config
  -> data/model/environment
  -> raw outputs
  -> evaluation script
  -> metrics + plots
  -> interpretation
~~~

如果只保留最终图表，别人无法判断结果是否由旧缓存、未记录的手工过滤、错误 checkpoint 或评估脚本修改产生。原始输出、日志、配置和评估结果应尽量不可变保存，派生表格可以重新生成。

### 3.4 版本差异要单独报告

有时只能使用新版本依赖、新 GPU 或替代数据。此时不要把版本差异隐藏在“复现环境”一栏，而要写成差异账本：

| 对象 | 论文条件 | 当前条件 | 可能影响 | 处理方式 |
| --- | --- | --- | --- | --- |
| GPU | A100 | H100 | kernel、带宽、精度 | 单独 benchmark |
| 数据 | 私有快照 | 公开替代 | 分布和标签 | 收窄 claim |
| 代码 | commit X | commit Y | 实现和默认值 | 回退或记录 diff |
| tokenizer | v1 | v2 | token 长度和边界 | 固定并做敏感性 |
| judge | model A | model B | 偏好和解析 | 人工抽样校准 |

差异本身不是失败，未记录差异才会让结果失去解释力。

## 4. 复现前先建立强 baseline

### 4.1 Baseline 决定“更好”是否有意义

一个弱基线（baseline）会制造虚假提升，一个强基线才可能检验方法是否真的有增量。至少需要检查：

1. 是否包含论文原始 baseline。
2. 是否包含当前社区更强、功能相同的 baseline。
3. 模型、数据和训练预算是否可比。
4. baseline 是否得到相近的调参机会。
5. 评估 prompt、解码和后处理是否相同。
6. baseline 的实现是否使用了合理的优化和硬件路径。

如果资源有限，优先复现一个最关键且强的 baseline，而不是先运行多个弱对照。否则只能说明新方法能运行，不能说明它更好。

### 4.2 受控比较和完整系统比较

复现时应区分两种实验：

- **受控比较**：固定数据、模型、预算、协议，只改变研究组件，用于判断机制。
- **完整系统比较**：允许各方案使用合理组件，但将预处理、检索、kernel、调度、失败重试和维护成本一起计入，用于判断选型。

例如检索增强生成（RAG）的重排器（reranker）受控比较应使用相同候选文档和上下文预算；完整系统比较则要把重排器延迟、召回变化、缓存命中和答案拒答一起计入。两种实验都可以支持贡献，但回答的问题不同。

### 4.3 资源预算也要对齐

质量差异可能由更多训练 token、更多搜索次数、更长上下文或更大采样预算产生。记录：

~~~math
ResourceLedger = (InputTokens, LossTokens, InferenceTokens, FLOPs, GPUHours, SearchAttempts)
~~~

这个账本是不同单位的向量，不能把 token、浮点运算量（FLOPs）、GPU 小时和搜索次数直接相加。训练 token 还应分清输入 token 与参与 loss 的目标 token；若新方法使用更多预算，应把“额外预算带来的收益”和“方法结构带来的收益”分开。对于 test-time compute、self-consistency、best-of-n 和 Agent 搜索，尝试次数本身就是能力和成本的一部分。

## 5. 数据对齐：一组容易被忽略的实验变量

### 5.1 数据对象不只是一组文件

数据对齐至少包含：

1. 数据集版本、下载日期和许可。
2. train/valid/test 切分和时间边界。
3. 去重、过滤、采样和数据顺序。
4. 标签、答案、测试和 metadata 格式。
5. prompt、system message、角色标记和 stop token。
6. tokenizer、最大长度、截断和 padding。
7. 多轮对话、图像、音频或视频的预处理。
8. 训练/评估污染和 benchmark 题目重叠。

大模型里，一个角色标记、空格、换行或 stop token 都可能改变 token 序列和生成行为。代码任务中，测试执行框架（harness）、依赖版本和超时也属于数据与评估协议的一部分。

benchmark 污染检测的完整方法见第七册[第五章《污染检测与可信评估》](../../book-07-evaluation-experiments/chapters/05-污染检测与可信评估.md)；本章只要求把数据重叠风险纳入复现对象和结论边界。

### 5.2 对齐分词、标签位移（label shift）和损失掩码（loss mask）

语言模型训练常把输入和目标错开一个 token；对话训练还要决定哪些角色 token 参与 loss。复现时需要打印一个小 batch，人工检查：

~~~text
raw text -> chat template -> token ids -> input ids/labels -> loss mask
~~~

如果 label mask 错位，loss 仍然可能下降，最终指标却完全不同。不要只比较 token 数量，还要比较实际序列、有效 loss token 比例和截断位置。

看一个只有五个目标位置的构造例子：模型输入依次是 BOS、用户标记、“7+5”、助手标记和答案“12”；下一 token 标签依次是用户标记、“7+5”、助手标记、“12”和 EOS。若协议只对助手答案及结束符计 loss，五个目标位置的 mask 是 [0,0,0,1,1]，因此有效目标 token 数为 2。若模板改动把助手标记也纳入 loss，mask 会变成 [0,0,1,1,1]，有效目标 token 数变成 3；模型虽读到相同问题，优化目标已不同。实际模板可能按完整助手消息训练，也可能只训练正文，关键是复现前固定规则并打印一条序列核对。

### 5.3 数据替代的边界

原始数据不可得时，可以使用公开替代、同分布小数据或 benchmark 子集。报告必须写清：替代数据保持了哪些属性，改变了哪些属性，结论因此降级到“方法趋势”“机制候选”还是“替代分布上的主张”。

替代数据不是简单的工程妥协。数据分布、标签难度和重复关系可能正是论文收益的原因；如果不做分布和难度对照，替代复现得到的结果不能直接归因于方法。

## 6. 模型、checkpoint 和 tokenizer 对齐

### 6.1 模型名不等于模型对象

需要记录完整的模型身份：架构配置、参数量、上下文长度、词表、量化格式、基础 checkpoint、adapter、权重版本和加载方式。一个同名模型可能有不同 revision、不同 chat template 或不同量化 artifact。

### 6.2 Checkpoint 选择会改变结论

训练中间 checkpoint、最终 checkpoint、最佳验证 loss checkpoint 和作者发布 checkpoint 可能不同。复现时要确认：

- checkpoint 选择是否看过测试集。
- 是否包含 optimizer 和 scheduler 状态。
- 是否恢复了训练步数和随机状态。
- 权重是否合并 adapter 或量化。
- 是否使用了 EMA、平均权重或最佳 epoch。

如果只加载最终权重而论文使用最佳验证 checkpoint，差异未必来自方法。模型对象应在 manifest 中有唯一标识，而不是只记录“加载了作者模型”。

### 6.3 Tokenizer 和 chat template 是模型的一部分

同一文本经过不同 tokenizer，token 数量、边界、特殊 token 和截断位置会变；同一对话经过不同 template，system/user/assistant 角色和 loss mask 也会变。复现报告应该保存 tokenizer 文件或 revision、template 文本、特殊 token 和最大长度，而不是只写模型名称。

## 7. 超参数、训练步数和资源对齐

### 7.1 超参数清单

至少记录：

1. optimizer 和 betas。
2. learning rate、warmup 和 scheduler。
3. batch size、gradient accumulation 和有效 batch。
4. weight decay、dropout 和 gradient clipping。
5. max steps、epoch、训练 token 和数据重复次数。
6. precision、loss scaling 和 checkpoint 间隔。
7. 并行策略、micro-batch、通信和梯度同步。
8. 生成 temperature、top-p、top-k、最大输出长度和停止条件。

论文只给出部分超参时，要从 appendix、配置、训练脚本、issue 和默认值中补齐，并标注哪些是作者明确报告、哪些是复现者推断。

### 7.2 有效 batch 和训练预算

批次大小、输入 token 与参与损失的目标 token 可以这样记账：

~~~math
B_eff = B_micro * G * D
N_input = \sum_{t,b,l} \mathbf{1}[InputMask(t,b,l) = 1]
N_loss = \sum_{t,b,l} \mathbf{1}[LossMask(t,b,l) = 1]
~~~

其中 B_micro 是每个数据并行 rank 的 micro-batch，G 是梯度累积次数，D 是数据并行 rank 数；第一式只在样本均匀且每步累积次数固定时成立，张量并行或流水并行不会把样本再乘一次。t、b、l 分别表示更新步、批内序列和 token 位置；InputMask 与 LossMask 分别标记实际输入位置和参与目标损失的位置。输入 token 更接近前向计算量的账本，loss token 则描述优化目标覆盖范围，两者不能互换。

举例：micro-batch 为 4 条序列，累积 8 次，数据并行 4 路，则有效 batch 为 4×8×4=128 条序列/更新步。若每条序列有 2,048 个输入位置、其中 1,536 个位置参与 loss，完成 1,000 个更新步，简化账本为 N_input=128×2,048×1,000=262,144,000，N_loss=128×1,536×1,000=196,608,000。若有 padding、prompt mask、动态 packing 或最后一个不满 batch，就应从实际 mask 汇总，不能把 token 槽位数冒充有效 token。比较两个复现时，固定 optimizer steps 不一定代表输入 token、目标 token 或 wall-clock 相同。

### 7.3 超参数敏感性

无法完全对齐时，不要只选择一个“看起来合理”的值。对影响最大的变量做小范围敏感性：学习率、batch、warmup、rank、beta、检索 top-k、上下文长度、解码温度和 judge 版本。敏感性实验不要求覆盖所有组合，但要说明结果方向是否依赖一个窄点。

如果方法只在单一精确超参上成立，结论应包含这个脆弱性；如果 baseline 的调参范围更小，也不能把新方法的最佳点直接作为公平比较。

## 8. 环境、硬件和非确定性

### 8.1 环境对象

环境记录至少包括：

1. Python、PyTorch/JAX/TensorFlow 和 Transformers 版本。
2. CUDA、cuDNN、NCCL、编译器和驱动。
3. GPU 型号、显存、互联拓扑和数量。
4. mixed precision、TF32、deterministic 设置。
5. custom op、kernel、推理引擎和容器 digest。
6. 分布式策略、rank、通信和 CPU 线程。

高性能 attention、MoE、量化和推理引擎论文尤其依赖环境。相同代码在不同硬件上可能有不同 kernel 选择、数值路径、通信占比和尾延迟；这不是“结果不真实”，而是结论作用域不同。

### 8.2 PyTorch 随机性边界

PyTorch 2.15 的[随机性说明](https://docs.pytorch.org/docs/2.15/notes/randomness.html)明确限定：跨发行版、提交版本或平台不保证完全相同，CPU 与 GPU 即使使用相同 seed 也可能不同。文档还提醒，确定性算子通常更慢；因此，固定 seed、启用确定性和记录测量性能是三个不同决定，不能把其中一个当作另两个的替代。

随机性来源包括参数初始化、数据乱序、dropout、生成采样、GPU kernel、并行归约、CUDA 算子和评估器。设置随机种子可以控制其中一部分随机数生成器，不能保证这些路径全都确定。

因此，复现报告不能只写“固定了 seed”。还要记录平台和版本，并将确定性开关的性能代价、未确定算子和剩余波动写清楚。为了比较方法，报告多 seed 的分布通常比追求一次完全相同的 bit-level 输出更有意义。

### 8.3 多 seed 和置信范围

对 n 次运行结果 y_i，均值、样本标准差和标准误为：

~~~math
mean = (1/n) * sum_i y_i
s = sqrt( sum_i (y_i - mean)^2 / (n - 1) )
SE = s / sqrt(n)
~~~

这里假设各次运行的结果可作为独立重复；样本标准差要求 n≥2，n=1 时标准差和标准误都无法据此计算。主张“方法稳定”需要说明稳定的对象：训练损失、最终指标、失败率、延迟还是容量。单 seed 结果可以作为探索，但不应被写成稳定收益。资源不足时，至少报告单 seed 限制，并在小模型或短训练上做多 seed 诊断。

以三个 seed 的构造准确率 0.72、0.73、0.71 为例，均值是 (0.72+0.73+0.71)/3=0.72。相对均值的平方差和为 0+0.0001+0.0001=0.0002，样本方差为 0.0002/(3−1)=0.0001，样本标准差 s=0.01，标准误 SE=0.01/√3≈0.0058。这个 SE 描述均值估计的标准误，不是 95% 置信区间；三个 seed 也不足以单独证明稳定性。还要说明 seed 改变了哪些随机源，数据抽样、初始化和解码是否都纳入波动。

## 9. 指标和评估协议对齐

### 9.1 指标名称不代表指标实现相同

复现时要逐项确认：

1. 指标定义、分母和空结果处理。
2. evaluation prompt、system message 和示例。
3. decoding 参数、采样次数和最大长度。
4. normalization、后处理和无效输出过滤。
5. judge 模型、judge prompt、顺序和 tie 处理。
6. 测试集版本、样本顺序和隐藏测试。
7. 是否报告平均、方差、置信范围和切片。

“accuracy”“win rate”“pass rate”都可能有多种实现。没有评估脚本或明确伪代码时，复现者必须把自己的定义写进报告。

### 9.2 代码任务中的 pass@k

代码生成中，单次通过率与多次采样的 `pass@k` 不同。若对同一个问题采样 `n` 个候选，其中 `c` 个通过测试，在随机抽取 `k` 个候选的无放回估计下，常见估计为：

~~~math
pass@k = 1 - C(n-c, k) / C(n, k)
~~~

其中 `C(a,b)` 是组合数，要求 `n >= k`。这个估计依赖候选池、测试 harness、超时、依赖和采样协议。复现 HumanEval 类结果时，必须记录 `n`、`k`、温度、最大 token、测试版本和执行沙箱；不能把 pass@1、pass@10 和“模型能写代码”混成一个结论。

例如，一个题目采样 5 个候选，其中 2 个通过测试，报告 pass@2 时：
~~~math
1 - C(5-2,2) / C(5,2) = 1 - C(3,2) / C(5,2) = 1 - 3/10 = 0.7
~~~
这个结果是从已生成的 5 个候选中无放回抽取 2 个、至少有一个通过的无偏估计；它不表示模型单次生成的通过率是 70%。整套 benchmark 通常先按题目计算，再按论文约定聚合。Chen 等人的 [Codex 论文](https://arxiv.org/abs/2107.03374)给出这一估计，并指出直接用 1−(1−pass@1)^k 替代会产生偏差；测试用例、采样温度和候选数也会改变结果。

### 9.3 LLM judge 和生成任务

生成任务的结果还受采样温度、top-p、长度上限、停止词和随机种子影响。大语言模型评审器（LLM judge）则额外受模型版本、提示、候选顺序、长度和参考答案影响。需要保存原始回答、评审器输入和解析结果，至少抽查人工 gold set 和顺序交换。

如果论文没有公开 judge 配置，复现者只能报告“在当前 judge 协议下观察到的趋势”，而不能声称完全复现人工质量。

judge 校准细节见第七册[第四章《LLM as a Judge》](../../book-07-evaluation-experiments/chapters/04-llm-as-a-judge.md)；代码任务的测试协议和指标边界见[第六章《Reasoning、Code 与 Math Eval》](../../book-07-evaluation-experiments/chapters/06-reasoning-code-math-eval.md)。这里聚焦的是复现时如何固定这些评估对象。

## 10. 最小复现路径：从便宜检查到昂贵实验

### 10.1 第一层：协议和张量形状（shape）冒烟检查（smoke test）

先检查数据字段、tokenizer、mask、label shift、batch shape、输出格式、loss 是否有限、checkpoint 是否能加载。一个 batch 能前向、反向并产生合理梯度，是后续训练的前提。

### 10.2 第二层：小数据过拟合

用很小的数据集让模型过拟合，检查：

- loss 能否下降。
- label mask 是否正确。
- 梯度是否传播到预期参数。
- adapter、冻结层和 optimizer 参数组是否正确。
- 生成结果是否对应输入格式。

如果小数据都不能过拟合，继续扩大数据只会增加成本，不会增加解释力。

### 10.3 第三层：短训练和小模型

短训练用于检查损失曲线、吞吐、显存、学习率和初步指标方向。小模型不一定复制大模型绝对分数，但可以验证核心机制是否出现，例如 rank 变化、reranker 排序、attention 数值误差、DPO loss 方向或过滤策略的验证损失变化。

### 10.4 第四层：关键 ablation

在完整训练前做能区分替代解释的对照：去掉组件、换简单替代、固定更多预算、改变关键超参。每组只回答一个问题，并保存相同输入和配置差异。

### 10.5 第五层：多 seed 和完整规模

只有前面通过，才投入完整模型、更多任务、更多 seed、长上下文、集群 benchmark 或线上 shadow。完整实验的日志应包含中间 checkpoint、曲线、吞吐、峰值显存和失败原因，而不只是最终分数。

前五层组成一条递进路径：先验证协议，再检查训练能否按预期工作，再用消融和多 seed 判断机制，最后才投入完整规模。阶段门的作用是让错误尽量在便宜的实验里暴露。

~~~mermaid
flowchart TD
    A["写明主张与判定规则"] --> B["固定数据、模型、配置和评估"]
    B --> C["协议与 shape 检查"]
    C --> D{"通过？"}
    D -->|否，定位差异| E["修正并记录一个变量"]
    E --> B
    D -->|是| F["小数据过拟合与短训练"]
    F --> G["关键消融与多 seed"]
    G --> H["完整规模或系统测量"]
    H --> I["报告证据层次、边界和未知项"]
~~~

## 11. 复现差异的诊断顺序

### 11.1 先排查协议，再怀疑方法

结果和论文不一致时，建议按成本和影响排序：

1. 指标定义、评估脚本和输出解析。
2. prompt、chat template、tokenizer 和 stop token。
3. 数据版本、切分、过滤、去重和污染。
4. checkpoint、参数冻结和模型配置。
5. batch、学习率、训练步数、warmup 和 precision。
6. baseline、调参预算和资源消耗。
7. seed、随机性、kernel、硬件和分布式通信。
8. 未公开数据、隐藏 trick、作者实现差异或 claim 本身。

先排查协议，是因为一个评估 prompt 错位就可能造成大差异，而且成本远低于重跑完整训练。不是说方法永远无辜，而是要先排除能用证据检验的替代解释。

### 11.2 用差异向量记录排查

可以把论文与复现的差异写成向量：

~~~math
Delta = (Delta_data, Delta_model, Delta_config, Delta_env, Delta_eval, Delta_randomness)
~~~

每修复一个差异，重新运行最小实验并记录结果变化。如果同时修改数据、学习率和评估脚本，最终接近论文也无法知道是哪项修复起作用。

例如，论文与复现的准确率相差 6 个百分点；检查后发现评估 prompt 与论文不同。只替换 prompt、保持数据和模型不变，再在同一批样本上评估，差距缩到 2 个百分点。这个变化说明 prompt 值得继续核查，但如果样本、评分器或版本同时改变，就不能把 4 个百分点的缩小归因给 prompt。把每步的前后指标、代码或协议 revision 和未变条件写进差异账本，才能让排查成为可追溯的证据。

### 11.3 训练曲线和最终指标的组合诊断

| 观察 | 更可能的原因 | 下一步 |
| --- | --- | --- |
| loss 一开始就异常 | 数据、label、mask、精度或学习率 | 打印 batch 和梯度 |
| loss 正常但指标为零 | 评估、解码、后处理或标签映射 | 对照原始输出 |
| 曲线接近但最终差异大 | 数据分布、checkpoint、训练步数 | 比较中间 checkpoint |
| 方法和 baseline 都变差 | 环境、数据或评估协议 | 先复现 baseline |
| 只有一个 seed 变好 | 随机性或选择偏差 | 多 seed 和完整记录 |
| kernel 快但端到端不快 | 其他层、通信、调度或 IO | 端到端 trace |

这张表不是自动诊断器，而是帮助复现者把“分数不同”转化成可检验的假设。

需要继续做样本级错误分层、版本迁移和回归确认时，可接读第七册[第十一章《Error Analysis 与回归测试》](../../book-07-evaluation-experiments/chapters/11-error-analysis与回归测试.md)。

## 12. 没有开源代码时如何复现

### 12.1 先降低复现对象，不降低诚实程度

没有代码时，可以从论文、附录、公式和方法图还原最小实现，参考社区实现，但要清楚区分：自写实现验证的是方法描述，不是作者的具体代码。记录每个自行选择：初始化、padding、归一化、负样本、optimizer、prompt 和后处理。

### 12.2 自写实现的检查顺序

1. 用小例子验证公式的数值结果。
2. 对照一个已知实现检查 shape、mask 和 loss。
3. 在小数据上过拟合或验证梯度方向。
4. 与简单 baseline 比较趋势。
5. 做关键超参敏感性。
6. 只在趋势稳定后扩大规模。

如果多个合理实现都产生相同方向的结果，机制证据更强；如果结果高度依赖一个未公开细节，主张范围应更窄。

自写实现的第一道检查不是跑大训练，而是把方法描述转成一条可逐步核对的数据流：输入是什么、哪些变量被更新、每一步读取哪些状态、输出如何计算。假设论文方法包含一个平方误差目标，先用极小输入检查实现路线：单参数 w=1，输入 x=2，目标 y=5，预测值为 wx=2；半平方误差为 0.5×(2−5)²=4.5，梯度为 (wx−y)x=(2−5)×2=−6。若学习率为 0.1，一步梯度下降得到 w'=1−0.1×(−6)=1.6，更新后的预测是 3.2，误差平方的一半为 0.5×(3.2−5)²=1.62。这个小算例只检查“预测—损失—梯度—更新”是否一致，不声称复现了某篇论文；把论文里的核心模块替换进同样的逐步检查，才能及早发现符号、归一化、mask 或更新方向错误。

若论文给的是伪代码，先逐项标出默认值和形状，再把每个未写明的选择记为复现者假设。例如负样本如何采样、均值在 token 维还是样本维、padding 是否参加归一化、温度是在 softmax 前还是后，都可能形成不同实现。对影响结论的选择，各做一个能区分结果的边界输入；对不影响主张的工程细节，记录后再固定，不需要无目的地穷举所有实现。

社区实现可以帮助发现遗漏，但其 commit 和数据流要独立核对。若借用了它的初始化、默认超参或评估脚本，报告中应写明来源并说明哪些部分与论文文本一致、哪些只是参考实现。比较结果最好并排保留“论文描述”“自己的代码路径”“社区实现路径”，逐层解释差异。即使自写实现趋势与论文一致，也只能支持该实现对论文方法描述的操作化；没有作者代码时，不能把它表述成作者 artifact 的数值复现。

还可以用有限差分检查小规模可微目标的梯度方向：对参数 w 加上很小的正负扰动，比较损失变化是否与解析梯度同号、同量级。这个检查受浮点误差和扰动幅度影响，不能替代目标函数定义或完整梯度测试，但能发现符号、广播和归一化错误。若目标含随机采样，固定输入和采样种子后再做对照；若损失含不可微分支，则应在可解析的局部或替代输入上检查边界。最终报告把这些单元检查视为“实现自检”，不要写成论文结果复现。

如果论文附录给出某个小输入的中间结果，可将它作为实现对照：逐层核对输入张量、归一化前后数值、损失项和更新方向。只对最终分数会把问题压成一个数，无法发现前面几步的约定差异。没有作者中间结果时，仍可用手算值、简单性质或另一份固定 revision 的实现做局部校验；但需要写明校验对象是什么，以及哪些推导仍由复现者自行承担。

因此，每一步实现检查都应绑定输入、预期量和输出位置；后续改动才知道哪些自检结果需要重新确认。

## 13. 没有公开数据时如何复现

### 13.1 替代数据的三种关系

替代数据可以是：

- **同源替代**：原数据的公开版本或相邻时间快照。
- **同任务替代**：任务契约相同，但来源和分布不同。
- **同机制替代**：不能复现任务分布，但保留核心机制所需的结构。

三种替代能支持的结论不同。同源替代可能支持趋势和部分数值，同任务替代主要支持方法适用性，同机制替代主要支持算法机制。不能将三者都称为完整结果复现。

### 13.2 报告数据差异

至少比较样本量、长度、语言、标签比例、难度、重复率、领域、时间和污染风险。如果这些统计差异很大，复现报告要把它们写成限制，而不是隐藏在“使用公开数据”一句话里。

用一个构造例子看总体比例如何改变结论。假设原论文测试集由 90% 简单题和 10% 难题组成：基线在两类上的通过率分别为 90% 和 50%，新方法分别为 92% 和 40%。按原分布，基线总体通过率是 0.9×0.90+0.1×0.50=0.86，新方法是 0.9×0.92+0.1×0.40=0.868，表面增加 0.8 个百分点；若公开替代集变成简单题和难题各占一半，基线变为 0.5×0.90+0.5×0.50=0.70，新方法变为 0.5×0.92+0.5×0.40=0.66，结果反而下降 4 个百分点。所有比例都是教学构造值，不是实测。差异并非算术错误，而是两个分布对同一切片结果赋予了不同权重。

因此，拿到替代数据后应先判断它和原研究保持了什么：任务目标、输入结构、标签定义、难度构成、语言、来源时间或样本去重。能匹配的维度就分层报告；缺失维度要写为未知，不能根据一个相近名称推断数据等价。若确实无法比较分布，实验仍可回答更窄的问题，例如“该算法在这个公开集合上能否运行”或“在这类结构化输入上是否出现预期方向”，但不能追溯原论文的绝对分数。

替代集也必须独立于调参过程。先用开发切分选参数，再对未触碰的测试切分作最终比较；如果每看到一个测试结果就修改过滤阈值、prompt 或采样策略，测试集会逐渐变成开发集。下载日期、来源 revision、许可、预处理脚本和去重方法也应记录，以便后来者判断快照是否变化。数据治理和版本管理可继续阅读第九册[第十一章《Dataset Versioning 与 Governance》](../../book-09-data-engineering/chapters/11-dataset-versioning与governance.md)。

替代数据还可能改变标签噪声和评估难度，而不仅仅是改变样本比例。比如原数据依靠专家标注解释“证据充分”，替代数据却把网页标题匹配当作标签，指标相同也不是同一构念。可以抽取小批样本做人工复核，查看边界样本、标签定义和缺失字段；如果标签可靠性无法确认，就把结果写成输入管线或算法行为观察，而不是任务质量比较。数据许可不清或无法公开时，可记录不可访问对象及其摘要，不能为了形式上的开放而把不允许的数据上传到新位置。

如果已知原数据的分层比例，可以尝试对替代样本按相同切片分别报告，或在明确假设下做重加权；重加权只能调整已观察切片的贡献，不能补出替代集中完全缺失的难例、标签来源或时间范围。比如替代集没有多跳问题，即使其余指标加权后与论文总体相同，也不能推出多跳主张得到复现。报告应列出覆盖到的切片、未覆盖的切片和每个切片样本数，而不是只写一个调整后的总分。

即使完成重加权或切片对照，仍需保留原分布和替代分布的分别结果，方便读者判断结论是否依赖样本构成。

## 14. 复现报告：让别人能复查

### 14.1 报告结构

一份完整复现报告包括：

1. 论文和版本信息。
2. 复现目标与主张矩阵。
3. 复现类型和目标层级。
4. 代码、数据、模型和环境 manifest。
5. baseline 及公平性说明。
6. 最小实验和完整实验的配置。
7. 指标、评估脚本和统计方法。
8. 结果、区间、曲线和失败率。
9. 与论文的差异向量。
10. 排查过程和每次修复的影响。
11. 已复现、部分复现、未复现和未知项。
12. 局限、成本、风险和下一步。

报告最好分成“运行账本”和“主张解释”两层。运行账本按 RunID 指向不可变的代码、配置、数据、模型、环境、评估脚本和原始输出；主张解释则逐条写研究问题、论文给出的条件、复现实际条件、观测指标、与论文的差异、已排除因素和剩余未知。前者让别人能找回实验对象，后者让别人知道这些对象支持什么推断。仅把命令粘贴进报告，读者仍无法判断某个输出来自哪个数据快照或评估 revision。

每条结论应明确标为运行完成、数值接近、机制方向一致、主张在限定范围内得到支持，或当前无法判断。这些标签是证据状态，不是论文整体质量分数。例如，指标 0.732 落在 0.740 的预设容差内，只能先记“数值接近”；如果缺少相同数据、独立评估或多 seed 结果，就不能把状态自动升为“主张复现”。报告也要把未完成的实验和停止原因保留下来，否则读者会把没有呈现的失败当作不存在。

正文可以精简到能读懂的结果和边界，但必须把关键 artifact 连接到原始记录。原始日志和逐样本输出尽量只追加不覆盖，汇总图表保留生成脚本和输入版本；任何手工剔除样本、评审仲裁或异常值处理都要说明规则和数量。后续复查者应能从论文版本和主张，沿实验计划、运行对象、原始结果、评估脚本回到报告中的每个数字，而不是依赖作者记忆。

例如，复现表中的“0.732”至少要能查到它的指标分母、原始样本输出、评估脚本 revision、运行 seed 和聚合规则；若三次运行先各自计算准确率再取平均，这不一定等于把三次输出合并后按总样本数计算。报告要说明实际采用哪一种，并保留足够的原始量供复算。延迟一栏则应说明请求数、warm-up 是否排除、计时点和百分位算法；GPU 小时应注明硬件和计时边界。单位和分母会决定同一个数字是什么意思，缺少它们就不能只靠小数位数表达精确。

提交给读者的报告不必包含每一条终端输出，但应提供稳定的复查入口：论文版本、代码 revision、配置、数据说明、评估步骤和主要原始结果至少能从一个清单找到。若数据或模型因许可不能公开，可说明申请方式、不可共享部分及可替代的检查材料；无法公开的对象要明示，不能将“受限”写成“相同且可复现”。报告中的图表 caption 也应说明数据集、切片、误差线含义和统计单位，使读者离开正文仍不误读。

### 14.2 结果表要包含原始和派生字段

不要只写“论文 74.0，复现 73.2”。假设这里的指标是以 0 到 100 记的准确率百分点；实际报告应写明尺度和单位。至少写：

| 字段 | 论文 | 复现 | 备注 |
| --- | --- | --- | --- |
| 数据版本 | 版本/未知 | 当前快照 | 是否同源 |
| 模型 | checkpoint | checkpoint | 参数和 tokenizer |
| 指标均值 | 74.0 | 73.2 | 分母和解析 |
| seed 数 | 未知/1 | 3 | 方差 |
| 成本 | GPU 小时 | GPU 小时 | 硬件不同 |
| 评估 | 脚本版本 | 脚本版本 | prompt 和后处理 |
| 结论 | 作者主张 | 当前观察 | 作用域不同 |

### 14.3 复现结论的语言

结论可以分成：

- “在相同代码和数据版本下，主指标在容差内接近。”
- “在替代数据上观察到相同方向，但不能声称数值复现。”
- “运行和训练曲线复现，任务指标未复现，差异主要出现在评估协议。”
- “核心组件的消融方向复现，但跨规模泛化没有验证。”
- “当前证据不足以判断论文主张，仍有未公开数据和配置差异。”

这种语言比“复现成功/失败”更准确，也更便于团队决定是否继续投入。

## 15. 负结果复现：失败也要有结构

### 15.1 负结果的最低证据

“没有复现出来”不等于“论文错误”。一个有价值的负结果应说明：

1. 验证的是哪条 claim。
2. 哪些条件已经对齐。
3. 复现值与论文值差多少。
4. 结果区间和 seed 是否支持差异。
5. 已经排除了哪些原因。
6. 仍然有哪些未知因素。
7. 该结果如何改变研究或项目决策。

### 15.2 三类负结果

| 类型 | 现象 | 可能结论 |
| --- | --- | --- |
| 实现负结果 | 代码/曲线异常 | 当前实现或环境未对齐 |
| 条件负结果 | 论文设置有效，替代设置无效 | scope 需要收窄 |
| 主张负结果 | 充分对齐、多 seed、强 baseline 后仍无效 | 核心 claim 需要重审 |

三类结果不能混为一谈。第一类要修实现，第二类要找边界，第三类才可能形成对论文结论的实质性挑战。

这三类是本章便于排查的工作分类，不是判断所有论文的正式标准。NeurIPS 的 [MLRC 2026 官方说明](https://blog.neurips.cc/2026/05/04/mlrc-2026-reproducibility-as-an-official-track-at-neurips/)把复现研究描述为针对具体主张的确认、部分复现或未复现，也欢迎外推研究、跨论文复现模式、方法工具和 AI 辅助复现；说明中特别指出，负结果和部分失败也可以有研究价值。该说明展示的是一个会议 track 的征稿范围，不是对任意负结果的自动认可。

### 15.3 负结果报告的写法

可以写成：“在数据版本 D、模型 M、配置 C、评估协议 P 和三个 seed 下，我们没有观察到论文报告的方向；当前区间包含零差异，因此本实验未能把观察到的差异与零区分开。已排查 tokenizer、label mask 和 checkpoint，尚未排除数据过滤和未公开超参。现有结果不能证明方法无效，也不足以确认原主张；结论暂限定为‘在当前协议下未观察到该方向’，并列出需要补查的条件。”

这段话同时保留观察、证据和未知项，别人可以据此决定复查哪一步。

区间包含零不是“两个方案等价”的证明；等价或非劣结论还需要事先定义有实际意义的界值，并使用与实验设计相符的区间或检验。统计解释和实验设计的完整方法见第七册[第十章《统计显著性与实验设计》](../../book-07-evaluation-experiments/chapters/10-统计显著性与实验设计.md)。

用一组完全构造的数值看这种区别。假设复现研究在 100 个配对问题上估计方法相对基线提高 0.5 个百分点，配对差的 95% 区间为 −1.0 到 2.0 个百分点。由于区间包含 0，当前证据不能区分小幅正向变化与零或小幅负向变化；它并不证明效果恰好为 0。若研究开始前规定“至少提升 3 个百分点才值得采用”，这个区间也没有支持达到该实用门槛。若要证明效果在 ±1 个百分点内等价，区间上界 2.0 又超出了预设等价界，因此同一组数字既不支持有意义的正收益，也不支持等价结论。这样报告比写“没有显著差异，所以两者一样”更准确。

负结果还要区分研究问题和实验失败。若 checkpoint 加载失败、label mask 全零、评估器把答案解析成空串，实验没有真正测到目标主张；这属于实现或协议阻断，应修复后重跑，不能当成“方法无效”。若运行、评估和 baseline 都可核查，但只有替代数据或不同硬件条件下效果消失，这首先是条件边界证据。只有关键条件得到充分对齐、预设主指标和替代解释检查完整后，观察到的差异才可能挑战论文在该范围内的主张；仍不能从有限数据直接推到所有任务都不成立。

一个可操作的负结果决策流程是：先确认失败的是哪一条主张和哪一个复现层级；再把实际条件与论文条件逐项对照；接着看原始输出、训练曲线、分切片与不确定性，确认结果不是评估错误或异常样本造成；然后列出已经排除、尚未排除和资源不足以检查的因素；最后将证据映射到下一步动作。若结果指向某个单独变量，做最小区分实验；若差异只出现在目标范围之外，收窄适用条件；若当前资源不足，报告停止预算和未知项；若重复检查后仍有稳定反向证据，再以限定范围的语言提交负结果。

避免在看到数据后移动判定门槛。若预设成功标准是准确率至少增加 2 个百分点、P95 不超过 500 ms，则结果不达标时不能事后把 1 个百分点说成“基本成功”，也不能把延迟成本从报告里删除。探索性分析可以提出新假设，但要将它标成下一轮待检验的问题，并使用未参与探索的数据或新样本确认。若做了许多切片、prompt 或超参搜索，应披露搜索范围和选择过程，避免只挑出最好的一次作为支持证据。

完整的负结果陈述可以按“目标—条件—观察—排查—未知—决策”六句组织。目标说明要检验的主张和实用门槛；条件写数据、模型、协议、资源和种子；观察给估计值、区间和失败切片；排查逐项说已经测试的替代解释；未知部分明确没法访问的私有数据、隐藏配置或未完成的多 seed；决策说明继续、收窄、暂停或停止及其理由。这样既不把一次运行失败包装成科学发现，也不因结果不符合预期而隐藏有效的反向证据。

若经过多次调参或故障排查才得到一个负结果，还要说明尝试次数与选择过程。只报告最后一组失败配置，会漏掉此前有多少配置被筛选；只报告最好的 seed，又会把随机波动挑成主结论。将探索运行和最终确认运行分开标记，保留预设的停止规则；如果没有预注册，也如实说明判定标准是在何时确定的。失败本身没有统一的“显著性”，证据力来自对照是否合适、数据是否独立、协议是否对齐以及结果是否能排除更简单的解释。对于无法复现的差异，可以先把结果作为可核验的观察发布，后续再由独立团队检验；报告语气应与当前证据强度一致。

若负结果涉及成本或安全边界，还要报告它影响了哪个决策。某方法质量略增但高风险切片恶化，和某方法完全没有增益，是两种不同的观察；前者可能说明存在不可接受的 trade-off，后者可能说明当前预算下没有足够收益。用同一套指标定义和门槛比较，分别列出质量、成本、失败率与风险，避免把它们压成一个总分。负结果最终可以决定修实现、继续实验、缩小部署范围或停止投入；每种动作都要由当前证据和剩余不确定性解释。

## 16. 从复现到改进：先冻结基线

### 16.1 先冻结复现基线

复现成功或部分成功后，先保存一份不可变 baseline，包括代码 commit、配置、数据、checkpoint、评估输出和日志。之后每次改进都创建新的实验对象，明确改变了哪些变量。

如果复现和改进同时进行，任何分数变化都可能来自原实现差异、你的改动或环境变化，无法归因。先冻结 baseline，再做优化，才能让改进结果有研究意义。

冻结的不是一张“最好分数”截图，而是能重新生成该分数的运行对象：代码和配置 revision、数据快照、checkpoint、评估协议、原始输出、资源账本和随机性设置都要关联到同一 RunID。之后每次改进都从这个版本建立新运行，并在报告中注明改了哪一项。若基础模型、数据或评估器变更，应先生成新的比较基线，再谈新方法相对它的增量。

用构造数字示范归因：固定同一请求集和模型，基线质量为 0.732、P95 为 500 ms；只调整缓存策略后，质量为 0.734、P95 为 450 ms。质量增加 0.002，即 0.2 个百分点，P95 减少 50 ms；这是缓存变更下的观察，不是普遍优化承诺。若这次同时换了 tokenizer、prompt 和缓存，无法判断哪个变化带来收益；即使平均质量上升，也要检查高风险切片与失败率是否退化。

改进实验还要决定何时停止。若一项变化没有达到预设质量或延迟门槛，应保留这条结果和失败条件，回到差异假设中选择下一个实验，而不是不断叠加改动直到出现一次好分数。组件必要性、替代方案和交互效应需要明确对照矩阵，完整实验设计接读第五章[Ablation 与 Controlled Experiment](05-ablation与controlled-experiment.md)；本章交给它的是一个冻结、可追溯的基线。

### 16.2 改进实验的对照

每次改进至少保留：

1. 复现 baseline。
2. 你的改进版本。
3. 一个简单替代方案。
4. 关键失败切片。
5. 成本和稳定性记录。

如果改进提高平均分但损害高风险切片，应把它写成 trade-off；如果只提高一个 benchmark，先检查是否改变了模板或数据，而不是立即宣布方法成功。

对一个改进主张，先写清改变与观察之间的映射。例如“新缓存减少端到端 P95”要保持模型、请求集、并发、硬件和评估脚本不变，只改变缓存策略，并同时检查缓存命中率、冷启动与热启动路径。若只在热缓存下变快，结论范围就是热缓存条件；不能把它扩成所有请求都更快。若缓存降低延迟却增加陈旧回答或跨租户串用风险，就把质量、时延和安全作为独立门槛。

另一种常见改动是更换模型或 prompt。此时最初的复现基线仍有价值，但它不再是唯一比较对象；应保留原始论文条件、已复现条件和新方案三列，说明每一步增加了什么。这样读者能区分“论文方法本身的复现”与“在复现系统上提出的新工程方案”。下一章会进一步讨论如何用删除、替换、交互和预算匹配的对照检验组件主张；读到那一章时，沿用这里的 RunID 和差异账本可避免重新定义实验对象。

另一个必须重新建立基线的情形是评估协议升级：更换 judge、数据切分或后处理会改变分数含义，即使模型参数完全相同也不应沿用旧标签。先对旧、新协议做一轮桥接比较，确认哪些指标可以并列，哪些只能分开报告。这样既保留历史结果，也避免把测量尺变化说成模型进步。

只要这三份对象和判定规则能由他人复查，后续控制实验就能从相同的比较条件开始。

## 17. 两个完整复现案例

### 17.1 Case A：RAG reranker 的主张复现

假设论文提出一个范围有限的主张：在长文档问答中，候选集不变时加入 reranker，会提高答案得到检索证据支持的比例。这里要先把“事实错误”拆成可观察对象。证据支持率可以按答案中的可核验断言逐条标注；事实准确率则要求有独立参考答案或专家判断；引用正确率还要确认引用片段是否真的蕴含对应断言。三者可能一起变，也可能相互背离，所以不能只看一个总分。

复现计划先冻结一个版本化文档快照和一组未参与调参的问题。每个问题记录检索到的候选文档、chunk、来源时间、权限过滤结果和答案标准。模型侧记录 embedding 与 reranker 的权重版本、tokenizer、最大长度、候选 top-k 和排序 tie 规则；生成侧固定模型 checkpoint、prompt、解码参数、引用格式和拒答策略。评估侧保留原始回答与引用片段，预先写出支持、不支持、证据不足三类标注规则，并抽样双人复核。若使用 judge 模型，还要记录 judge revision、提示、候选顺序，并用人工样本检查偏差。

对照分成三组：不检索、第一阶段检索后按原排序取文档、在完全相同的候选集合上重排。第一组回答检索总体是否有用；后两组的差异更接近 reranker 的增量。三组都使用同一生成模型和上下文 token 预算。若 reranker 让长文档占据更多 token，就同时记录截断位置和实际进入生成器的证据，而不能把输入变化误称为“只换了排序器”。

下面是一组构造数据，用来演示如何读结果，不是论文结果或本地测量。对同一批 100 个问题，原排序有 64 个答案达到“至少一条核心断言有证据支持”的判定，重排后有 76 个。绝对差是 76/100−64/100=0.12，即增加 12 个百分点；相对基线增幅是 12/64≈18.75%。再查看逐题迁移：16 题从不支持变成支持，4 题从支持变成不支持，净增 12 题。这张迁移账本比只看边际比例多了一层信息，但仍需报告标注规则、评审分歧和区间；100 题上的边际变化不能单独证明对所有长文档任务都成立。

同一构造案例再假设负载测试在固定硬件、并发和请求长度下测得端到端 P95 从 420 ms 变成 500 ms。绝对延迟增加 80 ms，相对增加为 80/420≈19.0%。若上线约束预先规定 P95 不高于 480 ms，重排后的质量指标虽过线，延迟却未过线；不能把 12 个百分点和 80 ms 相加成一个“总收益”。接下来可以测较小候选数、批处理、缓存，或只在长文档路径启用 reranker；每种改动都要重新核算同一质量门槛与延迟门槛。

反例要覆盖 reranker 容易失败的结构，而不是只增加随机问题。构造需要文档 A 和 B 联合回答的问题，检查单文档相关性排序是否把必要证据拆散；再分问题类型、文档长度、时间新旧和权限过滤分析。若只在单跳、短文档切片提升，结论就应限定到该切片。若总体提升但高风险问题的支持率下降，应报告切片退化和样本数，不能用总体平均掩盖它。

最后把复现报告写成条件句：在某个文档快照、问题集、候选 top-k、上下文预算和标注协议下，重排使支持率由 64% 变为 76%，但该构造例的 P95 同时从 420 ms 增到 500 ms，超过 480 ms 的预设门槛。它展示的是一条可复核的研究决策路径，不足以宣称真实系统收益。实际工作还需保留逐题输出、迁移表、延迟 trace、版本 manifest 和不确定性分析。

迁移表可以把上面的边际数字展开成配对计数。两种排序都支持的有 60 题，原排序支持而重排后不支持的有 4 题，原排序不支持而重排后支持的有 16 题，两者都不支持的有 20 题。旧排序的分子为 60+4=64，新排序的分子为 60+16=76；变化题是 4+16=20 题，净增 16−4=12 题。逐题配对可以看出提升来自多少“救回”和多少“回退”，而仅看 64/100 与 76/100 看不到这层结构。若同一问题有多个断言，要预先规定统计单位是问题、断言还是回答，避免把一个回答拆成许多相关断言后虚增样本量。

不确定性也要与随机化单位一致。若 reranker 参数只在开发集调过，最终结果应在独立问题集上测；若评审者判断支持关系，则对系统版本和答案来源尽量盲化，并抽查评审分歧。配对区间或检验应以问题为单位，不能把同一问题里的多个断言当作独立样本。这里没有给出虚构的显著性结果；实际报告要写方法、区间和样本数，统计细节可沿第七册相关章节继续学习。

这个案例还说明如何选择最小下一步。如果延迟门槛是硬约束，先测 rerank 是否能按请求长度分流，或者用缓存和批处理减少增量延迟；如果高风险问题的证据支持率下降，就先查失败样例而不是只调总体权重。每次改动只对一个预先选定的判断作答，并在未触碰的测试问题上复验，避免根据失败样例反复调到测试集上。最后报告里的“提高证据支持率”必须保持原任务和标注定义，不能悄悄扩写成“减少所有事实错误”。

再具体化延迟测量的分母：假设每个系统版本都收集 1,000 个请求，前 100 个请求只作 warm-up，不进入稳态分位数；请求长度、并发和硬件固定，并按同一 nearest-rank 规则取排序后的第 950 个耗时作为 P95。若两组该位置分别是 420 ms 和 500 ms，才得到前述 80 ms 差异。这里的请求数和 warm-up 数也都是教学假设；真实服务应按预先规定的负载分布重复采样，并报告窗口、重试和超时是否计入。若重排组和基线组用不同请求混合，P95 变化可能来自输入构成而不是排序器。

该报告还要说明每条查询是否重新检索、是否命中缓存、是否包含失败重试，以及计时从接收请求还是开始生成算起。若排序器只在检索阶段多花 30 ms，而总 P95 多了 80 ms，应检查排队、批处理和请求组合，不要把全部 80 ms 都归给重排模型。把分段 trace 与端到端请求 ID 关联后，才可以判断哪些系统组件产生了增量成本。

若这 1,000 个请求用于比较 P95，还要说明 warm-up 后到底保留多少请求以及是否按每个输入长度分别报告。若只有 900 个稳态请求，nearest-rank 的 95% 位置约为第 855 个；延迟样本变化时，尾部估计也会变化。这个数值只解释百分位的索引，不代表真实服务有 900 个请求或任何既定时延。对照两个版本时，应让请求分布、重复次数、限流和失败处理保持一致，或者将它们明确列为差异。

### 17.2 Case B：FlashAttention 的系统复现

[FlashAttention 原论文](https://arxiv.org/abs/2205.14135)的主方法把精确 attention 计算与分块、在线 softmax 和 GPU 存储层级联系起来，目标是减少 HBM 与片上 SRAM 之间的数据读写；原论文还把 block-sparse 扩展单独作为近似 attention 方法讨论。复现时因此要分清三个对象：数值计算是否符合目标 attention 定义、kernel 的时间/内存是否改善、完整模型或请求路径是否获益。论文中的实验结果只能作为对应模型、硬件、shape、精度和实现对照下的证据，不能当作新 GPU 上的性能保证。

先固定 Q、K、V、mask、dtype、dropout 和布局，检查输出与梯度。用构造 shape 演示内存账本：batch=1、head 数=8、序列长度 N=512、每头维度 d=64 时，每个 head 的 attention score 矩阵有 N²=512²=262,144 个元素，8 个 head 共 2,097,152 个元素。若每个元素用 2 字节表示，单个完整 score 张量占 2,097,152×2=4,194,304 字节，即 4 MiB。这个数字只表示一个逻辑 score 张量，不包含概率张量、梯度、Q/K/V、临时缓冲区和 allocator 开销；它也不是某个 kernel 实际峰值显存的测量。更长序列会按 N² 增长这一矩阵的元素数，因而要在多个长度上观察，而不是只测一个小 shape。

数值检查应预先按 dtype、mask 和任务容差定义输出误差与梯度误差，并检查 causal/non-causal、短序列、长序列和边界 shape。数学上称为 exact attention 并不意味着不同浮点实现逐 bit 相同：归约顺序和舍入可以不同。比较时应报告绝对误差、相对误差或下游损失变化的定义，确认 NaN、Inf、梯度异常和 mask 语义没有被误差平均掩盖。

再看一组完全假设的性能数值，帮助区分 kernel 与系统结论。假设在固定 GPU、shape 和同步测量下，旧 attention kernel 用时 2.0 ms，新 kernel 用时 1.5 ms；kernel 时间减少 (2.0−1.5)/2.0=25%，速度比为 2.0/1.5≈1.33×。若完整模型中 attention 原来占 2.0 ms、其余层占 6.0 ms，那么总时间从 8.0 ms 变为 1.5+6.0=7.5 ms，总时间只减少 0.5/8.0=6.25%，端到端速度比约 1.07×。这些是假设值，不代表论文或硬件实测；它们说明局部 kernel 加速不能直接改写成同倍率的模型加速。

真正的 kernel benchmark 还需固定 batch、序列长度、head 维度、mask、dtype、布局、warm-up、编译时间、同步点、重复次数和统计量；报告峰值显存、吞吐以及失败或回退到其他 backend 的比例。进入完整 Transformer block 后，要把投影、归一化、残差、通信、调度和数据搬运放回时间线。Serving 场景还要按输入/输出长度、并发和请求混合报告 P50/P95、吞吐及容量，避免只计 attention 子图的平均耗时。

如果数值检查通过、kernel 有稳定速度收益，而完整 block 几乎不变，就已经得到分层结论：当前 shape 下的局部实现收益出现了，端到端收益很小，瓶颈可能转到投影、通信或调度。下一步应先用 profiler 追踪时间，再选择最能区分瓶颈的 shape、batch 或系统对照；不能因为整体提升小就说 kernel 结论“错误”，也不能用局部结果宣称服务一定更快。报告须保留两层测量、硬件与软件 revision、原始 trace 和未覆盖的路径。

编译器、驱动、库和运行时也应纳入对照。一个 fused kernel 可能在不同版本下改变 dispatch、编译缓存或默认精度；因此记录“CUDA 可用”过于粗略，应固定具体版本、设备型号、kernel revision 与编译选项。若目标实现只在特定硬件路径可用，就将该路径写入实验边界；其他硬件上的回退实现应作为另一个运行对象，而不是混进同一组时间里。

实际比较至少保留三份同一输入条件下的记录：参考实现、目标 kernel 和完整 block。参考实现要说明来自作者 artifact、框架默认实现还是自行实现；若是自行实现，还应先核对 mask、缩放、dropout 和梯度语义。对每个 shape 记录首次编译与 warm-up 时间、稳态重复测量、同步方式和统计口径。若一次测量以毫秒级计时却没有设备同步，CPU 端只可能测到异步调用开销，不能当 GPU 执行时间。调度器若会按 shape 选择 backend，还应记录实际选中的实现，否则同一个 API 名称不一定代表同一个 kernel。

把前面的假设数字放进这样的记录中，kernel 从 2.0 ms 降到 1.5 ms，差值是 −0.5 ms，时间比例为 1.5/2.0=0.75，即新时间是原来的 75%；反过来表达速度比才是 2.0/1.5≈1.33×。完整 block 从 8.0 ms 降到 7.5 ms，时间只减少 6.25%，速度比约 1.07×。时间减少率和速度比使用不同分母，口头汇报时不要把“快 33%”和“时间少 33%”混为同一件事。上述数值依旧是算术演示，不是可复用的硬件 benchmark。

显存比较也需对齐测量范围：一个 score 张量的 4 MiB 是理论元素账本，峰值显存还可能包括运行时分配、临时 workspace、反向保存量和缓存分配器保留量。应分别说明“估算的逻辑张量大小”和“工具测到的峰值分配”，再解释二者差异。对于长序列，至少检查多个 N 值以观察增长趋势；对于 serving，增加不同并发和请求长度，统计 P50/P95 与吞吐。均值变快而尾部变慢时，容量结论不能只报均值。

若参考与目标输出有数值差异，先确认它来自浮点舍入还是语义不同：用相同输入逐层对比注意力输出、残差后状态和梯度，再结合下游 loss 与任务指标。对近零的参考元素，单独使用相对误差可能无限放大；对极少数大误差，整体平均又可能把它们遮住。因此要预先选择绝对误差、带分母下限的相对误差、分位数或最大误差，并报告具体判定规则。最终结论分别写清算子数值、局部 kernel 和端到端系统三层，避免一个层面的成功替另两层作答。

还可以用长度翻倍做增长直觉检查。前面的 N=512 时，每个 head 的矩阵有 512²=262,144 个元素；若 N 增为 1,024，则有 1,024²=1,048,576 个元素，恰好是 4 倍。8 个 head、每元素 2 字节时，单个完整 score 张量的账本从 4 MiB 增至 16 MiB。这个计算说明为什么要测不同长度，也展示了显式矩阵的平方增长；它不等于目标 kernel 的峰值显存必然乘四，因为分块实现、临时缓冲和其它层的内存占用都会改变观测值。报告应把“随长度变化的机制预测”和“实际 profiler 观测”分别列出。

若参考调用会根据 shape 自动选择后端，需记录每次调用实际采用的 backend，而不能只记录 API 名称。编译缓存、驱动、库版本、设备拓扑和精度开关也可能改变路径；这些改变一旦出现，就创建新的运行记录。原论文报告的硬件实测值只能作为方法和测量设计的参照，当前设备上的数值仍要由当前实验给出。

即使上述误差规则通过，结果仍需回到目标工作负载和报告的适用范围解释。

重复次数也要按测量对象解释。kernel microbenchmark 应保存每轮原始耗时，明确汇总统计量，并把编译与 warm-up 从稳态样本中分开；迭代过少时，单次抖动可能改变速度排序。Serving trace 则应保留请求到达过程、长度分布和并发，避免用紧密循环调用替代真实负载。前者回答算子实现的局部性能，后者回答服务路径表现，两者不能共用一个未定义的“平均延迟”标签。

## 18. 复现判定的 Python demo

下面的纯 Python 示例只把“指标均值是否落在预设容差内”计算出来，并保留训练 token 预算比例和 seed 数。它不是复现自动判定器：代码不知道数据是否一致、评估协议是否相同、强 baseline 是否公平，也不计算置信区间。输入值都是构造数据，目的是把前文的手算规则变成一个可检查的记录字段。

这段代码还假设论文值和复现值采用相同的指标定义、量纲与刻度，例如都以 0–1 表示准确率；如果一边记录 73.2 个百分点、另一边记录 0.732，程序仍会产生布尔结果，但没有比较意义。绝对误差窗口只表示距离，不编码“越高越好”或改善门槛；方向性结论须由指标契约和单独的实用阈值表达。

代码状态：静态审阅，未运行（2026-11-03；Python 版本未确认）。依赖 Python 3.7+ 标准库中的 dataclasses。

每个 Run 对象在这个教学程序中只代表一项主指标汇总：metric_mean 是多次运行的均值，paper_metric 是论文报告值，train_token_ratio 是本次训练 token 数除以论文条件下 token 数。真实记录还要说明 metric_mean 如何从样本和 seed 聚合；如果论文数值是单次运行、复现数值是三次均值，这两者并非完全同口径。seed_count 只是提醒读者有几次运行，不包含波动大小，因此代码不会据此判断“稳定”。

~~~python
from dataclasses import dataclass


@dataclass
class Run:
    name: str
    metric_mean: float
    paper_metric: float
    train_token_ratio: float
    seed_count: int


def compare(run, abs_tol=0.01, rel_tol=0.02):
    error = abs(run.metric_mean - run.paper_metric)
    tolerance = max(abs_tol, rel_tol * abs(run.paper_metric))
    return {
        "name": run.name,
        "error": error,
        "tolerance": tolerance,
        "metric_close": error <= tolerance,
        "train_token_ratio": run.train_token_ratio,
        "seed_count": run.seed_count,
    }


runs = [
    Run("direct_reproduction", 0.732, 0.740, 1.00, 3),
    Run("alternative_data", 0.701, 0.740, 0.85, 3),
]

for result in map(compare, runs):
    print(
        f"{result['name']}: metric_close={result['metric_close']}, "
        f"error={result['error']:.3f}, tolerance={result['tolerance']:.4f}, "
        f"train_token_ratio={result['train_token_ratio']:.2f}, "
        f"seeds={result['seed_count']}"
    )
~~~

按前文公式手算，第一条记录的误差是 |0.732−0.740|=0.008，容差是 max(0.010,0.020×0.740)=0.0148，所以 metric_close 为 True；第二条误差是 |0.701−0.740|=0.039，大于 0.0148，所以为 False。第一条的 train_token_ratio=1.00 表示记录的训练 token 预算与论文设定相等；第二条 0.85 表示记录为论文设定的 85%，即少 15%，不是“多用了 85%”。代码将容差显示到四位小数，避免把 0.0148 误读为精确等于 0.015。

下面是手算预期输出；本轮没有执行代码：

~~~text

alternative_data: metric_close=False, error=0.039, tolerance=0.0148, train_token_ratio=0.85, seeds=3
~~~

metric_close 只对应单个汇总指标与容差比较。第一条即使数值接近，也仍需要查看 seed 间波动、机制证据和其他资源；它的三次运行均值没有告诉读者标准差，也不证明第三章讨论的核心主张。第二条标为 alternative_data，数据分布发生变化，所以即使方向相同，也只能支持替代数据上的观察。token 比例同样不能代表 FLOPs、推理采样数或硬件成本。

真实复现记录还应链接 RunID、代码 commit、配置摘要、数据快照、checkpoint、tokenizer、容器 digest、GPU 拓扑、评估脚本 revision 和原始输出。若这些字段变化，应该生成新运行记录，而不是覆盖旧值。这个短 demo 有意不把所有字段塞进一个 dataclass；它展示容差计算，不代替 manifest 或报告。读者可手算输入、比较预期输出，再决定项目记录是否需要增加均值之外的区间、失败率和分切片结果。

还可手算一次门槛敏感性来检查规则是否符合用途。当前 paper_metric=0.740、绝对容差 0.010、相对容差 0.020，因此容差是 0.0148，0.732 的误差 0.008 会通过。若事先把相对容差改为 0.010，较小的相对项是 0.0074，绝对容差仍占主导，总容差变为 0.010，结果仍通过；若同时将绝对容差设为 0.005，总容差为 0.0074，误差 0.008 就不通过。这个变化说明阈值代表研究者对“接近”的约定，应在看到最终结果前根据噪声、报告精度和实际意义制定，不能为了让某条记录显示 True 而临时调宽。

最后，比例 0.85 不等于实验公平，也不能告诉程序替代数据分布改变了多少。字段只提供一个待解释的预算信号；如果训练 token 更多但 GPU、候选搜索次数或数据难度不同，仍需分别说明。程序的 True/False 也只是数值窗口输出，不是整体复现状态。使用时应将它放在报告表的一列，而不是让脚本替研究者决定论文主张是否成立。

读者可以只改一项输入观察程序逻辑：把 0.732 改成 0.725，误差会变成 0.015，大于 0.0148，metric_close 随之变为 False；把训练 token 比例从 1.00 改成 1.10，数值接近标记不变，但预算条件变成多出 10%。这说明指标接近和预算可比是两个独立字段。因为没有运行这段程序，本轮给出的这些输出均为手算预期；实际执行时应对照声明的 Python 版本和标准库环境。

## 19. 复现评审中的结论汇报

### 19.1 先给结论范围，再给证据

完整报告仍按第 14 节保存论文、运行对象、协议和结果字段；组会或评审的口头汇报则先说明“这次支持到哪一层”，再讲证据。可以沿以下顺序组织：

1. 论文和核心主张是什么。
2. 为什么选择这条 claim，而不是一开始复现全部表格。
3. 数据、模型、tokenizer、超参、环境和评估如何对齐。
4. 最小实验检查了什么。
5. 结果与论文差多少，区间和成本如何。
6. 你如何用差异向量排查。
7. 最终达到哪一层复现，哪些仍未知。
8. 对项目或研究决策有什么影响。

“我跑了作者代码，结果差不多”不是完整报告，因为它没有说明比较协议和复现层次。口头汇报可以先用一句条件化结论，再展示支撑结论的差异表和运行记录；听众若追问，报告里的 manifest、样本输出、指标定义和日志应能回到同一 RunID。这样既不把十几项环境字段全部读成命令清单，也不会让一句“复现成功”代替证据。

以第 17.1 节的构造例为例，可以这样汇报：“在固定的 100 个问题、同一候选集和相同上下文预算下，reranker 的证据支持率由 64% 到 76%，增加 12 个百分点；在假设的负载数据中，端到端 P95 从 420 ms 增至 500 ms，超过预先设定的 480 ms 门槛。因此，本例支持继续研究质量—延迟取舍，不能支持无条件上线或推广到所有长文档问答。”这句话先报任务和比较条件，再报效果与代价，最后限定决策。所有数字都是教学构造输入，不是生产实测。

### 19.2 面向不同决策者调整重点

向研究组汇报时，优先说明主张、控制条件、对照、区间、失败切片和仍未排除的替代解释；向工程团队汇报时，还要突出目标硬件、端到端延迟、吞吐、容量、依赖和回滚条件。两种汇报可以压缩细节，但不能改写证据对象：研究指标不能冒充用户收益，kernel 时间不能冒充请求延迟，单 seed 均值不能冒充稳定性。

若汇报面向跨学科听众，第一次出现的指标要用一句话说明分子、分母和方向；若讨论者无法从图表看出比较条件，先补条件再读结论。需要展开样本级原因时回到原始记录和差异向量，不要在口头讨论中把“可能解释”说成已经验证的根因。

可以把短汇报写成四句：第一句限定任务、数据、版本和比较对象；第二句说观察到的结果及单位；第三句说最重要的代价、未对齐条件或未覆盖切片；第四句给出下一步能区分替代解释的实验或明确的停止条件。若证据不够，就说“目前无法判断”，并指出缺失的是数据、协议、样本量还是机制观察；不要用更肯定的语气填补资料缺口。

### 19.3 讨论复现失败时回到差异账本

可以按以下顺序说明：先确认指标和评估脚本，再检查数据、prompt、tokenizer、checkpoint、超参、训练预算、环境和随机性；每次只修一个变量；如果仍然不同，报告已排除因素、剩余差异和不确定性。不要把“复现失败”直接写成“论文错了”，因为当前证据可能只说明实现或条件尚未对齐。

### 19.4 没有代码或数据时如何限定结论

应明确把复现目标限定为自写实现、替代数据或机制验证，并记录自行假设。这样的报告不是降低标准，而是准确描述证据范围。研究判断能力体现在能说清楚“已经验证了什么”和“尚未验证什么”，并让后来者知道哪些条件改变后需要重新评估。

汇报结束后，新问题和新假设应回到实验记录中，注明是听众提出的解释还是已有数据支持的结论；后续需要新的区分性实验时，再另建运行对象。

## 20. 常见误区

### 20.1 跑通代码就是复现

运行成功只说明当前 artifact 可执行，还没有证明指标、机制和主张。

### 20.2 只比较最终分数

最终分数无法解释数据、曲线、评估、checkpoint、seed 和成本差异。至少保留中间 artifact 和原始输出。

### 20.3 一开始就训练最大模型

大规模失败通常很难定位。先做协议、shape、过拟合、短训练和小模型，能以更低成本减少不确定性。

### 20.4 复现不出来就否定论文

缺失数据、prompt、配置、环境、随机性和隐藏实现都会造成差异。负结果必须说明排查范围。

### 20.5 只对齐新方法，不对齐 baseline

没有强且公平的 baseline，任何提升都缺少参照。baseline 应享有相近的数据、预算、调参和评估条件。

### 20.6 忽略评估脚本和生成协议

accuracy、pass@k、win rate 和 judge score 的实现细节可能改变结论。评估脚本是实验对象，不是最后随手调用的工具。

### 20.7 把替代数据结果写成完全复现

替代数据可以验证趋势或机制，不能自动支持论文原始数值和分布范围。

### 20.8 只保存图，不保存 manifest

没有代码、数据、配置、环境和运行时间，图表不可追溯，也无法判断后续版本是否真的改善。

## 21. 资料与证据边界

可复现性规范和实践入口包括 [NeurIPS Paper Checklist](https://neurips.cc/public/guides/PaperChecklist)、Pineau 等人的 [Improving Reproducibility in Machine Learning Research](https://arxiv.org/abs/2003.12206) 和 [Machine Learning Reproducibility Challenge](https://reproml.org/)。它们帮助定义数据、代码、超参、统计和 artifact 的记录维度，但不能替代对某篇论文的实际运行。

NeurIPS Communication Chairs 的 [MLRC 2026 track 公告](https://blog.neurips.cc/2026/05/04/mlrc-2026-reproducibility-as-an-official-track-at-neurips/)展示了该会期接纳的复现、部分复现、泛化、meta-reproducibility 和工具研究范围；它是特定会期的征稿说明，不是通用术语定义。

环境与随机性可以参考固定版本的 [PyTorch 2.15 Reproducibility documentation](https://docs.pytorch.org/docs/2.15/notes/randomness.html)；训练实现和配置入口可以参考 [Hugging Face Trainer documentation](https://huggingface.co/docs/transformers/main/en/trainer)；数据版本和实验输入的管理方式可以参考 [DVC Getting Started](https://dvc.org/doc/start)。这些文档说明公开的工具行为和使用方式，不等于任何项目自动可复现。

代码生成的 pass@k 估计来自 Chen 等人的 [Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374)。论文中的指标定义、测试执行框架（harness）和采样协议需要一起阅读；只复制公式而不复制执行环境，不能声称复现代码能力。

本章提到的 LoRA、DPO、RAG 和 FlashAttention 等方法，应回到各自的原始论文、代码 commit 和数据版本。论文报告的是特定研究设定下的事实，复现者自己的实验报告的是当前版本和环境下的观察；两者不应被混成同一条证据。

## 22. 本章小结

实验复现不是启动命令，而是一条带版本和证据的控制变量链：

1. 先区分运行、数值、机制和主张四层复现。
2. 先写核心 claim 和成功标准，再决定实验规模。
3. 用 manifest 固定论文、代码、配置、数据、模型、环境、seed 和评估对象。
4. 先建立强 baseline，明确受控比较和完整系统比较。
5. 对齐数据、prompt、tokenizer、checkpoint、超参、资源、环境和指标。
6. 从 smoke test、小数据过拟合、短训练和关键消融开始。
7. 用差异向量和训练曲线排查，不要同时修改多个变量。
8. 没有代码或数据时降低复现对象，保留替代条件和未知项。
9. 负结果也要报告 claim、对齐条件、排查范围、剩余不确定性和决策影响。
10. 复现完成后冻结 baseline，再进行改进和工程迁移。

最可靠的复现结论不是“成功”或“失败”，而是：“在这些版本、资源和协议下，这条 claim 得到了哪一层支持；差异最可能来自哪里；尚未验证什么；下一步实验如何减少不确定性。”
