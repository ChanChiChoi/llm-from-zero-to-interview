# 第十三章：研究讨论：把论文判断变成可交流的研究能力

研究讨论不是把论文摘要背出来，也不是把模型名、算法名和 benchmark 名称排成一串。它更接近一次被压缩的研究会议：有人给出一个问题、一篇论文、一张结果表或一个反常现象，参与者需要在有限时间内判断研究对象、证据强度、可能的混杂因素和下一步实验。

这类讨论常出现在组会、论文评审、技术方案评审和项目立项等研究交流场合。场合不同，评价标准却相近。参与者想知道的不是你能否复述作者的宣传语，而是：

1. 你是否知道论文要解决的真实瓶颈。
2. 你是否能把方法和因果假设连接起来。
3. 你是否能识别不公平 baseline、隐藏成本和评估偏差。
4. 你是否能把模糊的改进建议变成可运行的实验。
5. 你是否会区分已证实、可推测和还不知道的内容。

小白常把“会讲论文”理解为记住背景、方法和结果。专家更关心的是：如果换数据、换规模、换硬件、换评估协议，这个结论还剩多少？本章因此不提供一套必须逐字背诵的回答，而是把研究讨论拆成可迁移的判断动作，并用 DPO、FlashAttention、Scaling Laws、长上下文、RAG、Agent 和安全研究贯穿说明。

## 13.1 研究讨论究竟在考察什么

### 13.1.1 从名词识别到问题建模

看到一篇论文，第一反应不应是“它属于哪个热门方向”，而应是“它改变了哪个变量”。一个方法可能改变模型结构，也可能改变数据、损失、采样、评估、系统实现或部署协议。

例如“新的 attention”至少可能在解决六种不同问题：

1. 训练时 attention 矩阵的峰值显存。
2. GPU 上的内存读写和 kernel 利用率。
3. decode 阶段的 KV cache 容量。
4. 长序列中的有效信息使用。
5. 稀疏连接带来的计算减少。
6. 多卡训练中的通信和负载。

如果不先确定瓶颈，就会拿一个训练吞吐结果回答推理显存问题，或者拿一个 needle 检索结果回答长文档综合问题。

### 13.1.2 五层判断框架

研究讨论可以分成五层：

| 层次 | 核心问题 | 需要的证据 |
| --- | --- | --- |
| 问题层 | 这个痛点真实且重要吗 | 任务、用户、资源和失败后果 |
| 方法层 | 新增了什么机制 | 计算图、目标函数、数据流程 |
| 因果层 | 为什么它会带来变化 | 反事实、消融、交互和机制证据 |
| 结果层 | 在什么条件下有效 | 多数据、多尺度、多指标结果 |
| 决策层 | 是否值得投入或部署 | 成本、风险、维护和可回滚性 |

小白可以把它理解成从“为什么做”走到“做了什么”，再走到“真的有用吗”。专家会额外追问：方法层的变化是否和结果层的变化对应？如果只改变了数据和模型，能不能把收益归因于新模块？决策层的成本是否包括人工标注、调参、服务迁移和事故处置？

### 13.1.3 研究主张的最小形式

一个可讨论的主张至少包含处理、对象、结果和条件。可以写成：

~~~math
\mathrm{Claim}
=
(\mathrm{object},\mathrm{treatment},\mathrm{outcome},\mathrm{condition}).
~~~

例如：

> 在 7B decoder-only 模型、固定训练 token 和相同 kernel 预算下，FlashAttention 降低了训练峰值显存和 wall-clock time，同时保持验证 loss 在预先定义的容差内。

这句话比“FlashAttention 更快”更好，因为它说明了对象、处理、结果和条件。若论文只证明了 kernel time，而没有证明端到端训练 time，就不能把 claim 扩大成“训练更快”。

### 13.1.4 证据不是观点的装饰

研究讨论里的“我认为”应该紧跟证据类型。可以把说法标记为：

1. 论文实验直接支持。
2. 官方代码或文档直接支持。
3. 自己在替代条件下复现。
4. 根据机制做出的推断。
5. 还缺少证据的假设。

同一句“这个方法适合生产”若没有硬件、流量、失败恢复和维护数据，只能算推测。表达不确定性不是示弱，而是把证据边界说清楚。

## 13.2 把论文讲清楚：从叙述顺序到证据顺序

### 13.2.1 背景不是历史年份列表

一段有用的背景需要回答三个问题：

1. 以前的默认做法是什么。
2. 它在哪个条件下遇到了瓶颈。
3. 这个瓶颈为什么值得单独研究。

讲 DPO 时，背景不是“2023 年提出了 DPO”。更有用的叙述是：RLHF 把偏好数据、奖励模型和策略优化连接起来，但 PPO 训练需要多个模型、在线采样和敏感的动态更新；DPO 研究的是能否利用 KL 正则化目标与最优策略关系，把偏好优化改写成只依赖 chosen/rejected 对的目标。

讲 FlashAttention 时，背景也不是“attention 复杂度是二次”。如果论文目标是 GPU 实现效率，就必须补上标准实现的中间 attention 矩阵如何在高带宽显存和片上存储之间搬运，以及为什么理论 FLOPs 没有直接预测 wall-clock。

### 13.2.2 方法要讲输入、状态和输出

解释一个方法时，至少说清楚：

1. 输入是什么，形状和数据分布是什么。
2. 方法新增了哪一个状态、参数或计算步骤。
3. 输出与 baseline 的接口是否相同。
4. 哪个机制解释了预期收益。
5. 哪个机制可能带来副作用。

例如 RAG reranker 不是“多了一层排序模型”这么简单。它把初始候选文档、查询、排序分数和上下文预算连接起来；收益可能来自更高的证据 precision，代价是 rerank latency、模型调用次数和长文档截断。

### 13.2.3 结果表先看比较对象，再看数字

阅读一张表时，推荐按这个顺序：

1. 比较的是哪个 baseline。
2. 数据和预处理是否相同。
3. 训练和推理预算是否相同。
4. 指标分母和方向是否一致。
5. 结果变化是否超过随机波动或评估误差。
6. 方法是否在关键失败切片上有效。

一个总平均提升 1 分的结果，可能来自简单样本；一个总体没有提升的方法，可能在目标长尾任务上产生关键收益。不能只围绕表格中最醒目的数字构造结论。

### 13.2.4 讨论时的压缩结构

在有限时间内，可以把一篇论文压缩成五个连续段落：

1. 痛点：以前的方法在什么条件下不够。
2. 假设：作者认为哪个变量能改变结果。
3. 机制：方法如何改变这个变量。
4. 证据：实验支持了哪些结果，没支持哪些结果。
5. 下一步：最便宜、最能区分解释的实验是什么。

这不是固定话术，而是研究报告的最小骨架。每一段都应该能被一个追问展开，而不是在最后再补一句“有局限性”。

## 13.3 如何判断“重要论文”

### 13.3.1 重要性不是新颖性的同义词

一篇论文可能很新，却没有解决真实问题；也可能没有改变主干结构，却因为降低系统成本而影响很大。可以把重要性拆成向量：

~~~math
\mathbf{I}
=
(N,S,E,P,C),
~~~

其中：

- $N$ 是 novelty，是否有可识别的新东西。
- $S$ 是 significance，问题是否重要。
- $E$ 是 evidence，证据是否足以支持主张。
- $P$ 是 portability，是否能迁移到相邻设置。
- $C$ 是 practical value，是否改变成本、可靠性或工程路径。

这五项不宜简单平均。对一个安全方法，严重风险切片上的可靠性可能比总体新颖性更重要；对一个 kernel 论文，端到端收益和可部署性可能比模型 benchmark 提升更重要。

### 13.3.2 FlashAttention：重要在 IO 视角

FlashAttention 之前，attention 的讨论容易停留在 FLOPs 和渐近复杂度。论文把问题推进到 IO-aware 计算：即使数学计算量相同，显存和片上存储之间的搬运也可能主导真实时间。

标准 scaled dot-product attention 可以写为：

~~~math
\mathrm{Attention}(Q,K,V)
=
\mathrm{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V.
~~~

其中 $Q,K,V$ 的序列长度为 $n$，$d_k$ 是 head 维度。朴素实现可能产生 $n\times n$ 的中间矩阵。FlashAttention 通过 tiling 和 online softmax 在块内完成计算，减少中间矩阵写入高带宽显存，同时保持精确 attention 的数学结果。

小白可以把它理解为：不是减少了要算的关系，而是减少了大张中间草稿在慢速仓库和工作台之间来回搬运。专家则要区分：

1. exact attention 和近似 attention。
2. 理论复杂度和实际 IO。
3. kernel benchmark 和端到端训练。
4. 单卡收益和多卡通信。
5. 训练 prefill 和 decode serving。

它的重要性在于改变了系统研究的视角。边界也同样明确：它不消除 dense attention 的二次交互，收益依赖序列长度、head dimension、精度、硬件和实现版本；一个 kernel 加速不能直接推出长上下文理解能力提升。

### 13.3.3 DPO：重要在把偏好优化变成可分析目标

DPO 的重要性不是“完全不需要强化学习”，而是把一个包含奖励模型和策略优化的目标转写成了 policy/reference 概率比上的分类式损失。

对 prompt $x$、chosen response $y_w$ 和 rejected response $y_l$，定义 policy 与 reference 的 log-ratio：

~~~math
r_\theta(x,y)
=
\log\pi_\theta(y\mid x)
-
\log\pi_{\mathrm{ref}}(y\mid x).
~~~

一种常见 DPO 目标为：

~~~math
\mathcal{L}_{\mathrm{DPO}}
=
-\mathbb{E}
\left[
\log\sigma
\left(
\beta
\left(
r_\theta(x,y_w)-r_\theta(x,y_l)
\right)
\right)
\right].
~~~

其中 $\beta$ 控制偏好差异的尺度，$\sigma$ 是 logistic sigmoid，response log probability 要对 response token 求和或按实现约定归一化。

它解决的是训练流程复杂性和可复现性问题，但依赖偏好数据、reference、模板和长度分布。若 chosen 总是更长，DPO 可能学到长度相关信号；若 preference pair 的质量不稳定，loss 下降也不能说明真实帮助性提升。

### 13.3.4 Scaling Laws：重要在资源分配，而非能力保证

Scaling Laws 把模型参数、训练数据和计算量与验证 loss 的经验关系联系起来。一个教学化表达可以写成：

~~~math
L(N,D)
\approx
L_\infty
+
A N^{-\alpha}
+
B D^{-\beta},
~~~

其中 $N$ 是参数量，$D$ 是训练 token 数，$L_\infty$ 是不可约损失近似，$\alpha,\beta$ 是拟合得到的指数。

这类规律可以帮助比较资源配置，但它不自动预测事实知识、推理、安全或工具成功率。Chinchilla 类计算最优分析进一步说明，在固定计算预算下，参数和数据需要共同平衡；具体最优点依赖模型结构、训练效率、数据质量和目标定义。

选择 Scaling Laws 作为讨论对象时，不能只说“模型越大越好”。应说明：

1. 拟合的是哪个损失。
2. 训练和推理成本是否被分开。
3. 数据是否重复或受污染。
4. scaling 是否外推到了论文未覆盖的区域。
5. 目标能力是否与 loss 同步变化。

### 13.3.5 重要性判断的 worked case

假设有三篇论文：

- A：在弱 baseline 上提升 2%，没有端到端成本。
- B：模型结构变化很小，但把训练显存降低 35%，并在两种 GPU 上复现。
- C：提出新 benchmark，覆盖真实长文档失败，但自动评分器尚未经过人工校准。

不能只按“新模块数量”排序。A 需要先验证 baseline 公平性；B 可能具有较高的工程重要性；C 的价值取决于 benchmark 是否能区分真实能力、标签是否可靠以及后续研究是否采用它。

## 13.4 DPO 复现：把算法名还原成实验对象

### 13.4.1 复现目标不是复制一个最终数字

复现 DPO 时，真正值得验证的是一组主张：

1. preference pair 是否让 policy 学会区分 chosen 和 rejected。
2. 相对于 SFT-only，偏好指标是否提高。
3. 相对于 PPO 类方法，训练流程是否更简单或更稳定。
4. 提升是否来自偏好质量，而不是长度、模板或评估器偏差。
5. 安全、事实、数学和代码能力是否保持。

这组主张的对象不同，不能由一个 win rate 代表全部。

### 13.4.2 最小实验配置

| 对象 | 最小记录 |
| --- | --- |
| Base | 模型名称、参数规模、tokenizer、chat template |
| Data | prompt、chosen、rejected、长度、来源、去重 |
| Policy | 初始 checkpoint、学习率、batch、beta、训练步数 |
| Reference | checkpoint、冻结状态、模板和 tokenization |
| Baseline | SFT-only，必要时加入一个强偏好优化 baseline |
| Eval | pairwise win、reward score、人工抽检、能力回归 |
| Artifact | seed、配置、日志、checkpoint、失败样本 |

如果 SFT checkpoint、preference 数据和模板没有固定，实验即使能运行，也不能判断差异来自 DPO 还是输入协议。

### 13.4.3 从 token log probability 到 preference margin

对 response 的 token 序列 $y=(y_1,\ldots,y_T)$，自回归模型的 log probability 为：

~~~math
\log\pi_\theta(y\mid x)
=
\sum_{t=1}^{T}
\log\pi_\theta(y_t\mid x,y_{1:t-1}).
~~~

policy/reference 的差异和 chosen/rejected 的偏好 margin 分别为：

~~~math
m
=
\left[
r_\theta(x,y_w)
-
r_\theta(x,y_l)
\right].
~~~

如果训练日志只保存总 loss，不保存 $r_\theta$、chosen/rejected 长度和 margin，就很难诊断长度偏差、reference 漂移或数据问题。

### 13.4.4 DPO 的常见失败

**数据协议失败。** chosen 和 rejected 没有共享相同 prompt，或多轮模板拼接错位，偏好目标不再是同一条件下的比较。

**长度偏差。** chosen 过长，模型可能靠延长回答增加表面偏好。应报告长度分布、按长度分桶的 win rate，并设置长度匹配子集。

**reference 不一致。** policy 和 reference 的 tokenizer、chat template 或 prompt 截断不同，概率比就失去清晰含义。

**评估器偏差。** reward model 或 LLM judge 可能偏爱更长、更自信或更像自己生成风格的回答。

**能力回归。** 偏好指标提高但数学、代码、事实或安全拒答下降，说明目标没有覆盖完整系统质量。

### 13.4.5 DPO 复现的 worked case

假设实验得到：

| 模型 | win rate | 平均长度 | 事实切片 | 安全切片 |
| --- | ---: | ---: | ---: | ---: |
| SFT | 0.50 | 210 | 0.71 | 0.88 |
| DPO | 0.58 | 340 | 0.70 | 0.81 |
| DPO length-matched | 0.53 | 218 | 0.71 | 0.87 |

第一眼会说 DPO 有提升，但长度匹配后提升大幅缩小，安全切片仍下降。这时更稳妥的结论是：原始 DPO checkpoint 的总体偏好分数提高，其中一部分可能来自长度相关信号；在当前数据和训练预算下，没有充分证据说明安全和事实能力同步提升。

下一步可以做 preference noise、beta、长度匹配和人工盲评，而不是直接增加训练步数。

## 13.5 如何判断新的 Attention 方法值得研究

### 13.5.1 先区分训练、prefill 和 decode

同一个 attention 方法在三个阶段的瓶颈可能不同：

1. 训练：需要处理完整序列并保存反向激活。
2. Prefill：一次处理长 prompt，算力和 IO 压力较大。
3. Decode：每次生成一个 token，历史 KV cache 和 kernel launch 可能主导。

论文只测训练吞吐，不能直接推出 decode 延迟下降；论文只测单请求 decode，也不能推出高并发 serving 吞吐提高。

### 13.5.2 理论复杂度与资源账本

对序列长度 $n$、hidden size $d$ 的 dense attention，可以用教学近似表示：

~~~math
C_{\mathrm{attn}}
\approx
c_1 n^2d,
\qquad
M_{\mathrm{score}}
\approx
c_2 n^2,
~~~

其中 $c_1,c_2$ 代表 head、精度和实现常数。KV cache 则大致为：

~~~math
M_{\mathrm{KV}}
\approx
2L n_{\mathrm{kv}}d_{\mathrm{head}}T b,
~~~

其中 $L$ 是层数，$n_{\mathrm{kv}}$ 是 KV head 数，$T$ 是历史 token 数，$b$ 是每个元素的字节数。

一个方法如果把 $n^2$ 改成近似线性，可能牺牲远距离连接；如果只是优化 IO，理论复杂度不变却可能显著减少 wall-clock。必须先说清它改变了计算图还是改变了执行方式。

### 13.5.3 端到端速度模型

单次请求的粗略延迟可以拆成：

~~~math
T_{\mathrm{e2e}}
=
T_{\mathrm{queue}}
+
T_{\mathrm{prefill}}
+
T_{\mathrm{decode}}
+
T_{\mathrm{post}}.
~~~

如果论文只报告某个 kernel 的时间，就没有覆盖队列、tokenizer、通信、采样和后处理。对 Agent，还要乘上调用次数和失败重试；对 RAG，还要加入检索和 rerank。

### 13.5.4 公平 baseline 与系统兼容性

至少检查：

1. 是否与强 kernel 实现比较，而不是朴素 attention。
2. 是否相同模型规模、训练 token、精度和硬件。
3. baseline 是否获得同等超参和调优预算。
4. 是否报告峰值显存、吞吐、延迟和能耗。
5. 是否兼容 RoPE、GQA、KV cache、量化、并行和 continuous batching。
6. 是否在短上下文和真实长上下文任务同时评估。

### 13.5.5 Attention 评价的 worked case

一个新方法在 4K 序列上比强 baseline 快 8%，在 128K 上快 40%，但长文档多证据综合准确率下降 12%，decode 阶段因为额外索引反而变慢。它可能适合训练或 prefill，却不适合当前在线 decode 产品。

研究讨论时应把结论写成条件句：该方法在长 prompt 的 prefill 计算上有潜在收益，但需要补充 decode、高并发和证据综合评估；质量损失是否可接受取决于业务对长程任务的权重。

## 13.6 如何判断一篇论文的真实贡献

### 13.6.1 贡献是相对于已有理解的增量

“我们提出了一个新模块”不是贡献本身。贡献要回答：如果没有这篇工作，社区对问题的理解、可用工具或可达到的系统结果少了什么？

可以把贡献拆成六个维度：

| 维度 | 具体问题 |
| --- | --- |
| Novelty | 是否有可识别的新问题、新方法或新证据 |
| Significance | 问题是否影响能力、成本、可靠性或安全 |
| Correctness | 方法、推导和实验是否自洽 |
| Evidence | 结果是否足够支持主张 |
| Scope | 结论在哪些数据、规模和硬件上成立 |
| Practicality | 训练、推理、维护和风险成本是否可接受 |

小白可以把它理解为“新、重要、正确、有证据、适用范围清楚、值得使用”。专家会注意，这六项之间存在张力：一个结果可能新颖但证据弱，一个系统优化可能不改变模型能力却有很高 practical value，一个 benchmark 可能解决评估盲区却需要严格污染审计。

### 13.6.2 贡献类型和对应证据

**新问题。** 需要说明问题在真实任务中存在，定义可以测量，且不是把已有指标换一个名字。

**新方法。** 需要强 baseline、控制变量、消融和跨设置复现，不能只比较弱实现。

**新系统。** 需要 wall-clock、显存、吞吐、可靠性、成本和工程集成，而不是只报告局部算子。

**新数据或 benchmark。** 需要数据来源、标注协议、污染检查、覆盖切片和与现有测试的互补性。

**新分析。** 需要展示分析能解释现象、预测新结果或改变后续实验，而不只是对结果做事后描述。

### 13.6.3 反事实贡献测试

可以问一个反事实问题：

> 如果去掉论文中最关键的新部分，是否仍能得到主要结果？

这不是简单的 remove ablation。还要考虑：

1. 是否存在一个更简单的替代方法。
2. 数据和训练预算是否已足以解释收益。
3. baseline 是否拥有同样的调优机会。
4. 论文的理论解释是否能预测反事实结果。

如果一个新 loss 去掉后结果几乎不变，可能说明它不是主要贡献；也可能说明这个数据集太容易，或者评估指标没有测到目标行为。反事实只提供线索，不能脱离实验上下文。

### 13.6.4 一个贡献账本

可以用一个简化的贡献效用表示：

~~~math
U_{\mathrm{paper}}
=
w_s\Delta S
+
w_c\Delta C
+
w_r\Delta R
+
w_p\Delta P
-
w_k K,
~~~

其中 $\Delta S$ 是目标质量变化，$\Delta C$ 是成本变化，$\Delta R$ 是可靠性或风险变化，$\Delta P$ 是可迁移性变化，$K$ 是复现和维护成本。权重由项目决定，不能把这个式子当作客观论文排名。

### 13.6.5 Worked case：新 benchmark 的贡献

一个长上下文 benchmark 在固定 needle 任务上与旧测试集高度相关，却新增了多文档冲突和证据综合。它的主要价值不在题目数量，而在于暴露了旧评估未测的能力。要判断贡献，应该检查：

1. 新任务是否真的需要跨文档证据。
2. 标签和引用位置是否可靠。
3. 模型是否能够靠关键词或模板捷径完成。
4. 结果是否与真实长文档失败有关。
5. benchmark 是否会被训练数据污染。

## 13.7 Ablation：把意见改造成因果问题

### 13.7.1 Ablation 不是删模块清单

Ablation 的核心问题是：

> 在其他条件尽量相同的情况下，改变哪个因素会改变结果？

一个因素可以是模块、loss、数据来源、训练阶段、推理策略、上下文长度、检索 top-k 或工具权限。每个消融都应该对应一个明确假设。

例如：

> RAG 的提升来自 reranker 提高证据排序质量，而不是因为它把更多 token 塞进上下文。

这个假设要求固定 retriever、候选数、生成模型和上下文预算，只改变 reranker 或使用长度匹配的候选。

### 13.7.2 四类消融

**组件消融。** 删除或替换模块，适合验证结构作用。

**超参消融。** 扫描 beta、rank、学习率、top-k、窗口长度或专家数量，适合观察敏感区间。

**数据消融。** 改变数据量、来源、质量、去重或合成比例，适合验证监督来源。

**评估消融。** 更换 benchmark、judge、prompt、解码参数和人工协议，适合检查结论稳定性。

把四类混在一张表里，会让读者不清楚是在验证机制、寻找最佳点，还是检查评估偏差。

### 13.7.3 2×2 因子实验与交互项

如果要判断两个因素是否有组合效应，可以使用 2×2 设计。设 $A$ 表示是否使用 reranker，$B$ 表示是否使用 conflict verifier，四个条件均值为 $\mu_{00},\mu_{10},\mu_{01},\mu_{11}$，交互项为：

~~~math
\Delta_{\mathrm{int}}
=
\mu_{11}-\mu_{10}-\mu_{01}+\mu_{00}.
~~~

若 $\Delta_{\mathrm{int}}$ 明显不为零，说明两个组件的联合效果不能由单独收益简单相加解释。它可能反映互补，也可能反映某个组件只在另一个组件存在时才有意义。

### 13.7.4 预算公平

消融比较还要控制预算。若新方法训练更多 token、使用更长上下文、调用更大的 judge 或获得更多调参试验，最终提升不能全部归因于方法。

至少记录：

1. 总训练 token 和有效 epoch。
2. GPU hours、峰值显存和通信量。
3. 推理调用次数、输出 token 和检索 token。
4. 超参试验数量和选择规则。
5. 人工标注、评估和失败重试成本。

### 13.7.5 RAG 消融案例

一个 RAG 系统包含 retriever、reranker、context compressor 和 citation verifier。论文声称 verifier 降低 unsupported claim rate。合理实验至少包括：

| 条件 | Retriever | Reranker | Compressor | Verifier |
| --- | --- | --- | --- | --- |
| A | 固定 | 固定 | 固定 | 关闭 |
| B | 固定 | 固定 | 固定 | 开启 |
| C | 固定 | 更强 | 固定 | 关闭 |
| D | 固定 | 更强 | 更长 | 开启 |

若只比较 A 和 D，就无法判断收益来自 verifier、reranker 还是更长上下文。还要记录 recall、citation support、unsupported claim、拒答和端到端延迟。

## 13.8 负结果：把“没有提升”写成有信息量的结果

### 13.8.1 负结果的四种状态

实验结果不理想时，至少要区分：

1. 方法在当前条件下没有改善目标指标。
2. 方法改善了目标指标，但产生了不可接受副作用。
3. 实验没有足够功效，不能判断有无效应。
4. 实验实现或评估无效，数值没有解释意义。

“失败”只描述结果，不描述原因。研究报告要继续追问数据、实现、优化、随机性、指标和系统条件。

### 13.8.2 差异、区间和实际意义

设 baseline 均值为 $\bar y_0$，method 均值为 $\bar y_1$，配对差异为：

~~~math
\Delta
=
\bar y_1-\bar y_0.
~~~

如果 bootstrap 或重复实验得到区间 $[\Delta_L,\Delta_U]$，则区间跨过零表示证据不足以排除无效应，但不等于方法一定没有实际价值。还需要设定最小实际有意义差异 $\delta_{\mathrm{min}}$，例如延迟降低 2% 在业务上可能不值得增加维护成本。

### 13.8.3 负结果排查顺序

**先查实现。** 数据读取、label、mask、loss、梯度、混合精度、分布式同步和评估 pipeline 都可能让方法没有真正运行。

**再查复现条件。** tokenizer、chat template、checkpoint、数据版本、训练 token、随机性和隐藏超参是否一致。

**再查 baseline。** 你的 baseline 可能比论文更强，或者论文 baseline 没有得到公平调优。

**再查规模。** 有些机制只在一定参数、数据或上下文范围出现；也有方法在规模增大后收益消失。

**最后查指标。** 方法可能改善了事实性、引用或尾部安全事件，但总平均没有变化。

### 13.8.4 负结果案例

某团队在 1B 模型上加入 verifier，数学 benchmark 从 0.42 变成 0.43，区间为 [-0.01, 0.03]；代码任务下降 0.04，推理成本提高 1.6 倍。正确结论不是“verifier 无效”，而是：

1. 当前数学提升证据不足。
2. 代码切片存在回归。
3. 成本增加超过目前可见收益。
4. 下一步应检查 verifier 是否偏向数学格式、是否改变输出长度和是否需要任务路由。

这比只写“实验没有达到预期”提供了更多可复用信息。

## 13.9 从论文到项目：研究价值如何变成系统价值

### 13.9.1 先定义业务或系统目标

论文方法不能直接当项目目标。目标应写成任务成功、质量、成本和风险的组合。例如：

> 在企业长文档问答中，把 unsupported claim rate 降低 30%，保持可回答问题准确率不下降，p95 延迟增加不超过 15%。

这个目标比“把 RAG 做得更强”更容易建立实验契约。

### 13.9.2 最小可行复现

研究项目应该先用小模型、小数据和离线 harness 验证核心机制。一个最小闭环包括：

1. 强 baseline。
2. 最小方法实现。
3. 目标指标和至少一个副作用指标。
4. 一个反事实或消融。
5. 失败样本保存。
6. 成本和环境记录。

如果最小闭环不能区分“方法有效”和“数据/评估变化”，扩大规模只会扩大不确定性。

### 13.9.3 项目成本模型

可以用一个粗略单位成功成本帮助决策：

~~~math
C_{\mathrm{success}}
=
\frac{
C_{\mathrm{train}}
+
C_{\mathrm{serve}}
+
C_{\mathrm{eval}}
+
C_{\mathrm{human}}
}
{N_{\mathrm{successful\ tasks}}}.
~~~

其中各项分别表示训练、服务、评估和人工成本。若方法提高了单次质量但降低任务成功率，重试和人工修正可能让单位成功成本更高。

### 13.9.4 从离线到线上

离线结果到线上之间至少有四个差异：

1. 用户输入分布变化。
2. 流量和并发改变延迟。
3. 工具和权限带来真实副作用。
4. 线上反馈会改变后续数据分布。

因此部署路径应保留 shadow、灰度、线上切片、人工抽检、异常日志和回滚条件。研究结论不是上线授权，系统还需要工程验证。

## 13.10 如何审查 Alignment 论文

### 13.10.1 偏好数据先于算法名称

Alignment 方法的结果很容易被偏好数据的构造方式决定。读论文时先看：

1. 偏好来自人工、模型、规则还是混合流程。
2. chosen/rejected 是否共享 prompt。
3. 是否存在长度、格式、主题和语言偏差。
4. 是否报告标注者一致性和难例。
5. 训练集与评估集是否有污染或模板重叠。

偏好数据若不可靠，换 DPO、IPO、KTO 或 ORPO 可能只是换一种方式拟合噪声。

### 13.10.2 Helpful、harmless、truthful 不能合成一句“更好”

一个模型可能更愿意回答，却更容易编造；更安全，却误拒绝大量正常请求；更符合 judge 偏好，却在数学和代码上退化。至少要分开报告：

~~~math
\mathbf{q}
=
(q_{\mathrm{helpful}},
q_{\mathrm{safe}},
q_{\mathrm{truthful}},
q_{\mathrm{capability}},
q_{\mathrm{cost}}).
~~~

这不是要求每个维度都最大，而是要求读者知道 trade-off 发生在哪里。

### 13.10.3 Judge 可靠性

LLM judge 可能受位置、长度、格式、自我偏好和提示模板影响。一个基本审计包括：

1. 交换 A/B 输出位置。
2. 隐藏模型名称。
3. 使用长度匹配样本。
4. 与人工盲评比较。
5. 报告不同 judge 的一致率。
6. 抽查 judge 置信度高但人工判错的样本。

如果模型只在单一 judge 上变好，而人工和任务结果没有同步，不能把 judge win rate 写成总体质量提升。

### 13.10.4 Alignment 论文的 worked case

某偏好优化方法报告 judge win rate 从 0.51 提高到 0.61，但平均输出长度增加 60%，人工对事实性的评分没有变化，安全切片误拒率上升。复查后发现 judge 偏爱更完整、更有礼貌的长答案。

合理结论是：方法改变了 judge 可见的表达特征，但尚未证明真实帮助性提升；需要做长度匹配、事实验证、正常请求误拒和任务成功评估。

## 13.11 如何审查 RAG 论文

### 13.11.1 把检索、证据和生成分开

RAG 端到端答案可以拆成至少三层：

1. Retriever 是否召回支持答案的文档。
2. Reranker 或 context builder 是否把证据放到合适位置。
3. Generator 是否依据证据回答并正确引用。

检索 recall 提高不等于答案 faithfulness 提高；答案流畅不等于引用支持。

### 13.11.2 主要指标

对真实证据集合 $E^\ast$ 和 top-k 结果 $E_k$，在 $|E^\ast|>0$ 的可回答样本上，检索召回可以写成：

~~~math
\mathrm{Recall}@k
=
\frac{|E^\ast\cap E_k|}
{|E^\ast|}.
~~~

对回答中的 claim 集合 $C$，被证据支持的 claim 数量为 $C_{\mathrm{supported}}$：

~~~math
\mathrm{SupportRate}
=
\frac{|C_{\mathrm{supported}}|}
{|C|}.
~~~

还要报告不可回答问题上的 abstention、冲突证据处理、权限过滤、上下文 token、检索延迟和更新成本。

这里的分母必须先定义。不可回答问题没有可接受的 $E^\ast$，不能把它们的 Recall 记成 0 后与可回答问题直接平均；应单独报告不可回答识别率、误检索率或拒答质量。类似地，若某个回答没有可评估的 claim，$|C|=0$ 时 SupportRate 未定义，不能把空集合机械地当成 0 或 1。实际汇总时，应报告有效样本数，并把无 claim、无标注证据和人工无法判断的样本单列。

### 13.11.3 RAG 论文的常见混杂

1. 新 retriever 同时使用了更长上下文。
2. chunk 数增加但没有控制 token 预算。
3. reranker 使用了与测试集相似的标注。
4. 生成模型版本发生变化。
5. 只测可回答问题，没有 impossible 或冲突样本。
6. 引用存在但并不支持具体 claim。

### 13.11.4 RAG 改进的实验问题

与其说“可以加一个更好的 reranker”，不如提出：

> 在固定 top-k、上下文 token 和生成模型下，reranker 是否提高多证据任务的支持率，并且不增加冲突证据上的错误服从？

这个问题可以通过分层数据集、固定预算和 claim-level 标注来回答。

## 13.12 如何审查 Agent 论文

### 13.12.1 Demo 成功不等于任务可靠

Agent 论文的一个 demo 往往只展示成功轨迹。研究讨论要把任务拆成 outcome、process、safety 和 cost：

| 维度 | 问题 |
| --- | --- |
| Outcome | 最终业务目标是否完成 |
| Process | 中间步骤、工具和证据是否正确 |
| Safety | 是否越权、泄漏或造成不可逆后果 |
| Cost | 步数、token、延迟、工具费用和人工接管 |

一个 Agent 可能最终输出正确答案，却读了不该读的文档；也可能完成任务，但修改了用户未授权的文件。最终字符串不能覆盖过程和权限问题。

### 13.12.2 轨迹级成功率

设第 $i$ 个任务的工具动作是否都满足协议为 $p_i$，最终结果是否正确为 $o_i$，是否产生高严重度安全问题为 $s_i$。对没有工具动作的任务，若任务协议允许直接回答，可将 $p_i$ 定义为 1；若任务要求至少一次工具核验，则应把它标成协议不适用并单独报告，不能悄悄混入同一分母。一个可读的报告应至少给：

~~~math
\mathrm{OutcomeRate}
=
\frac{1}{N}\sum_{i=1}^{N}\mathbf{1}[o_i=1],
~~~

~~~math
\mathrm{SafeOutcomeRate}
=
\frac{1}{N}\sum_{i=1}^{N}
\mathbf{1}[o_i=1]\mathbf{1}[p_i=1]\mathbf{1}[s_i=0].
~~~

两者的差异就是需要调查的过程和安全失败。不能把所有成功轨迹和失败轨迹混成一个“Agent accuracy”。

### 13.12.3 强 baseline 与环境控制

Agent 方法至少要和以下 baseline 中与任务相称的版本比较：

1. 单次模型调用。
2. 固定 workflow。
3. RAG 加结构化模板。
4. 工具约束但无自主规划的版本。
5. 同样最大步数和同样工具权限的简单 planner。

环境状态、工具错误、网络条件、任务随机性和人工干预必须记录。若方法依赖研究者手动修复中间状态，人工修复不能被隐藏在“自动成功率”里。

### 13.12.4 Agent 论文的 worked case

某 Agent 在 100 个任务上最终成功率为 0.70，平均 8 步；固定 workflow 成功率为 0.67，平均 3 步。进一步看，Agent 的高严重度越权动作率为 0.08，固定 workflow 为 0，且 Agent 失败时常常留下未回滚的文件修改。

这不是“Agent 提升了 3 个百分点”这么简单。要比较的是：

1. 每个成功任务的 token 和工具成本。
2. 每次越权动作的潜在损失。
3. 人工接管和回滚成本。
4. 任务类型分布是否偏向 Agent。

如果安全和成本约束更重要，固定 workflow 可能是更好的系统，即使平均任务成功率略低。

## 13.13 面对最新模型和新论文：先审查证据等级

### 13.13.1 新名称不是新事实

大模型研究中经常出现尚未有完整论文、模型卡或官方技术报告的新模型名称。研究讨论时，首先要确认：

1. 名称是否来自模型拥有者的官方页面。
2. 版本、权重和 API 是否真实可访问。
3. 上下文长度、参数量和训练细节是否有来源。
4. benchmark 分数是否给出数据、提示、shots、解码和成本。
5. 社区推测是否被误写成模型架构事实。

如果只有二手帖子或截图，应把它当作待核验线索。它可以帮助寻找资料，但不能支撑“模型使用了某种位置编码”这类确定结论。

### 13.13.2 “支持 1M context”如何讨论

至少区分：

1. API 或 runtime 是否接受这么长的输入。
2. 模型训练是否覆盖目标长度。
3. 长距离证据能否被检索和组合。
4. 多证据冲突、位置变化和噪声下是否稳定。
5. prefill、KV cache、延迟和成本是否可接受。

一个模型能接收一百万 token，只证明接口链路在某些条件下没有拒绝。若没有任务评测，不能直接说它具有一百万 token 的有效推理能力。

### 13.13.3 位置编码和 NoPE 声明

当论文或模型卡说“使用 RoPE”“采用 NoPE”或“支持长度外推”时，需要分别检查：

1. 这是训练架构、推理实现还是某个实验变体。
2. 位置关系由什么状态、偏置或数据顺序提供。
3. 训练长度和测试长度分别是多少。
4. 是否有位置打乱、证据移位和长度分桶结果。
5. 是否同时报告了 attention、KV cache 和吞吐成本。

“不用 RoPE”不等于“不使用任何位置信息”；“支持长上下文”也不等于“能够完成长程综合”。研究讨论应坚持主张范围和证据范围一致。

### 13.13.4 新模型的证据账本

可以给每条新模型 claim 保存以下字段：

| 字段 | 示例 |
| --- | --- |
| Claim | 公开上下文上限为某值 |
| Source | 官方文档、模型卡、论文或 API |
| Scope | 接口、训练、任务或生产 |
| Condition | tokenizer、模板、硬件、采样 |
| Independent check | 自己的测试或第三方复现 |
| Status | confirmed、scoped、uncertain |

这样可以在讨论中明确说“官方接口文档支持这一点，但有效任务能力还没有独立证据”，而不是在不确定时强行选边。

## 13.14 如何阅读一篇完全陌生的论文

### 13.14.1 第零遍：先定位对象

看标题、摘要、图一和结论，回答：

1. 论文研究的是模型、数据、训练、系统还是评估。
2. 主要输入和输出是什么。
3. 目标指标是什么。
4. 需要什么资源。
5. 论文声称改变的是质量、成本、可靠性还是理解。

这一遍不是为了相信摘要，而是为了建立待验证的主张清单。

### 13.14.2 第一遍：还原问题和 baseline

读 introduction 和 related work 时，重点记录：

1. 作者定义的瓶颈。
2. 之前方法的失败条件。
3. 论文选择的最近 baseline。
4. 与 baseline 的数据、模型和预算差异。
5. 论文没有比较的强方法。

如果作者只说“现有方法效率低”，却没有说效率的分母和硬件，问题定义仍然不完整。

### 13.14.3 第二遍：沿计算图追方法

方法部分要画出输入、状态和输出。对每个新模块问：

1. 它接收什么张量或数据。
2. 它改变了什么计算。
3. 它增加了什么参数、内存或通信。
4. 训练时和推理时是否都存在。
5. 如果移除它，哪个主张应该消失。

对 loss，要记录变量、分母、停止梯度和数据采样；对系统，要记录队列、缓存、并发和失败恢复。

### 13.14.4 第三遍：实验和局限

实验表先看 baseline 和预算，再看数字；ablation 看是否对应核心假设；appendix 看方差、超参、失败样本和实现细节；limitations 看作者承认了什么。

一篇论文没有写出局限，不代表它没有局限。研究者要主动检查：

1. 训练和评估是否同源。
2. 是否存在数据或 benchmark 污染。
3. 自动评估是否和目标能力错位。
4. 是否只在单一规模或硬件上有效。
5. 是否省略了失败和维护成本。

### 13.14.5 现场讨论的证据卡

可以把陌生论文压缩成五格：

| 格子 | 内容 |
| --- | --- |
| Problem | 具体瓶颈和失败后果 |
| Mechanism | 新增变量、模块或数据流程 |
| Evidence | 最强结果、最弱环节和关键对照 |
| Boundary | 没有测什么，哪里可能失效 |
| Next test | 最能区分解释的低成本实验 |

这张卡不是背诵模板，而是防止阅读时只记住作者的结论。

## 13.15 如何提出真正可执行的改进点

### 13.15.1 改进点必须指向失败模式

“结合多模态”“加入 RAG”“换更大模型”没有说明哪个失败会被修复。好的改进点包含：

1. 观察到的失败。
2. 关于失败原因的假设。
3. 最小干预。
4. 可观测的成功与副作用指标。
5. 成本和回退方案。

### 13.15.2 三个例子

对 DPO，如果 chosen response 系统性更长，可以构造长度匹配 preference subset，并报告按长度分桶的 margin、win rate 和人工事实性。

对 RAG，如果 hallucination 主要出现在冲突文档，可以加入 evidence conflict detection，构造冲突证据集，同时测支持率、错误服从率和拒答质量。

对长上下文，如果 needle 检索很好但多文档综合很差，可以构造需要跨文档合成的任务，控制证据位置、冗余和冲突，而不是继续增加单点 needle 数量。

这些建议的共同点是先把失败切片固定，再改变一个最小变量。

## 13.16 研究选题：价值、可行性与信息增益

### 13.16.1 选题不是追热点

一个适合研究周期的题目通常同时满足：

1. 对团队或领域有真实价值。
2. 有公开或可获得的数据和工具。
3. 能在有限资源下做最小闭环。
4. 即使结果为负，也能沉淀评估、数据或机制证据。

“热门”只说明关注度，不说明问题适合当前人员、时间和硬件。

### 13.16.2 信息增益视角

把实验看作减少不确定性的动作。假设有多个解释 $H_1,\ldots,H_m$，实验 $e$ 的价值可以粗略写为：

~~~math
V(e)
=
\frac{\mathrm{InformationGain}(H\mid e)}
{C_{\mathrm{run}}(e)+C_{\mathrm{analysis}}(e)}
-
\lambda C_{\mathrm{risk}}(e).
~~~

高价值实验不一定是最大规模实验，而是能以较低成本区分多个解释。比如要判断 DPO 提升来自长度还是偏好质量，长度匹配消融的信息增益可能比再训练一个更大模型高。

### 13.16.3 实习或短周期研究

短周期项目可以分成：

1. 第一阶段：复现 baseline 和数据管线。
2. 第二阶段：复现核心现象。
3. 第三阶段：做一个能区分机制的消融。
4. 第四阶段：整理失败、成本和下一步。

不要把全部时间用在完整重跑作者规模。一个可靠的小结论比一个无法解释的大日志更有价值。

## 13.17 如何展示论文复现项目

### 13.17.1 先讲为什么选它

项目开头要说明真实瓶颈和核心 claim，而不是先报模型参数。听者需要知道你为什么相信这个问题值得资源。

### 13.17.2 再讲你实际复现了什么

至少交代：

1. 模型和 checkpoint。
2. 数据版本和预处理。
3. 训练、推理和评估环境。
4. baseline 与公平比较。
5. 指标、分母和统计方法。
6. 运行、数值、机制和主张复现分别做到哪一层。

### 13.17.3 诚实处理差异

论文结果和复现结果不同并不丢脸。关键是给出差异账本：

| 对象 | 论文 | 复现 | 差异解释 |
| --- | --- | --- | --- |
| 数据 | 原始版本 | 替代版本 | 来源和规模不同 |
| 模型 | 未公开配置 | 开源小模型 | 参数与训练不同 |
| 指标 | 原论文 judge | 人工抽检 | 评估器不同 |
| 成本 | 未完整报告 | 记录 GPU hours | 计算口径不同 |

### 13.17.4 用一个失败案例证明研究能力

最有说服力的项目通常包含一个失败样本：一个看似有效的结果如何被长度匹配、强 baseline、反事实或线上切片重新解释。它说明你不是只会运行代码，而是会检查结论。

## 13.18 研究讨论中的表达：清楚、克制、可追问

### 13.18.1 先结论，再证据

可以先说“我认为它的主要价值在系统效率，而不是模型能力”，然后解释对应的 benchmark、硬件和边界。这样听者先知道你的判断，再决定追问哪一层。

### 13.18.2 主动给出范围

“在当前数据和短上下文任务上”比“这个方法有效”更准确；“论文展示了行为变化”比“论文解释了模型”更准确。

### 13.18.3 不知道时保留可验证路径

没有读过一篇论文时，可以明确说信息不足，并给出会检查的对象：问题定义、最近 baseline、方法假设、数据污染、关键消融和成本。不要用熟悉的模型名填补未知内容。

### 13.18.4 把观点落到实验

“我担心有长度偏差”之后，应补一个长度匹配实验；“我认为收益来自 reranker”之后，应补固定候选和无 reranker 对照；“我怀疑模型只是在拒答”之后，应补 paraphrase、间接问题和能力保持测试。

研究讨论的可信度，最终来自观点能否变成可运行的实验。

## 13.19 综合案例：评审一篇“长上下文 Attention”论文

假设论文提出一种新的 attention 结构，声称支持百万 token、降低显存并提高长文档问答准确率。它给出三组结果：短文本 perplexity 略好，needle 任务提高，单卡吞吐提高。

### 13.19.1 先拆 claim

这篇论文实际上包含至少四个主张：

1. 接口或 runtime 能接受更长输入。
2. attention 或 KV cache 资源消耗下降。
3. 模型能在远处证据位置找到答案。
4. 模型能综合多个证据并保持任务正确。

这四个主张的证据并不相同。接口测试不能证明有效理解，needle 不能证明多证据综合，单卡吞吐不能证明高并发成本。

### 13.19.2 再问机制

要确认它改变了什么：

1. 是稀疏连接、位置编码、状态压缩还是 kernel 实现。
2. 训练和推理是否使用同一机制。
3. 远距离信息如何进入当前 token。
4. 长度增加时信息是否被压缩或丢弃。
5. KV cache、通信和索引成本是否被计入。

如果方法使用局部窗口和少量全局 token，就需要测全局 token 位置、证据被压缩的情况以及跨窗口推理；如果方法只是高效 exact attention，则它可能改善执行效率，却不改变模型的长程归纳偏置。

### 13.19.3 设计最小复现

可以先做四个长度桶和四类任务：

| 长度 | 任务 |
| --- | --- |
| 4K | 单证据问答 |
| 32K | 位置随机的单证据问答 |
| 128K | 多证据合成 |
| 512K 或更长 | 冲突证据、噪声和跨段引用 |

每个桶同时记录准确率、证据位置、unsupported claim、prefill latency、decode latency、峰值显存和每个成功任务的成本。

### 13.19.4 可能的结论

若新方法只在 needle 任务上提升，不能说长上下文推理更强；若长文档准确率保持但 prefill 变慢，可能适合离线分析而非在线服务；若接口能接收但有效成功率在 128K 后骤降，应把“支持百万上下文”限定为接口或容量层 claim。

这个案例展示了研究讨论的核心：不急着赞成或否定，而是把一条宣传句拆成多个可证伪对象。

## 13.20 综合案例：评审一篇“偏好优化提升对齐”的论文

假设论文比较 SFT 和一种新的 preference optimization，报告 helpfulness、harmlessness 和 judge win rate 都提高。

### 13.20.1 先检查数据和评估

要问：

1. preference pair 是否由同一个 prompt 产生。
2. chosen 是否普遍更长或格式更规范。
3. judge 是否知道模型身份。
4. 是否报告正常请求误拒。
5. 是否有事实、数学、代码和工具任务。

### 13.20.2 再做反事实

最小反事实包括：

1. 长度匹配 chosen/rejected。
2. 交换 judge 的候选顺序。
3. 人工盲评少量样本。
4. 用任务结果代替单一偏好分数。
5. 在训练域外做相同评估。

### 13.20.3 判断结果

如果只有 judge win rate 提升，不能称为总体对齐改善；如果 helpfulness 提升而 false refusal 也提升，需要讨论目标权衡；如果安全切片改善但事实性下降，可能是保守拒答，而不是更可靠的知识行为。

## 13.21 可运行的研究讨论审计 demo

下面的纯 Python 示例用合成结果模拟一次研究讨论。它把主张拆成任务效果、成本、风险和证据覆盖，并根据独立信号生成下一步动作。数值不是任何论文的实测结果。

~~~python
from math import sqrt


def mean(values):
    if not values:
        return None
    return sum(values) / len(values)


def proportion(values):
    if not values:
        return None
    return sum(1.0 if value else 0.0 for value in values) / len(values)


def paired_delta(baseline, method):
    if len(baseline) != len(method):
        raise ValueError("paired observations must have the same length")
    if not baseline:
        return None
    differences = [m - b for b, m in zip(baseline, method)]
    return mean(differences)


def standard_error(values):
    if len(values) < 2:
        return None
    center = mean(values)
    variance = sum((value - center) ** 2 for value in values) / (len(values) - 1)
    return sqrt(variance / len(values))


def rounded(value, digits=4):
    return None if value is None else round(value, digits)


baseline = [0.68, 0.72, 0.70, 0.71, 0.69]
method = [0.72, 0.73, 0.71, 0.75, 0.70]
quality_delta = paired_delta(baseline, method)
quality_se = standard_error([m - b for b, m in zip(baseline, method)])

retrieval = [1, 1, 0, 1, 0, 1]
supported_claim = [1, 1, 0, 0, 1, 1]
unsafe_actions = [0, 0, 1, 0, 0, 0]

signals = {
    "baseline_mean": rounded(mean(baseline)),
    "method_mean": rounded(mean(method)),
    "paired_quality_delta": rounded(quality_delta),
    "quality_delta_se": rounded(quality_se),
    "retrieval_recall": rounded(proportion(retrieval)),
    "citation_support": rounded(proportion(supported_claim)),
    "unsafe_action_rate": rounded(proportion(unsafe_actions)),
    "cost_ratio": 1.42,
}

actions = []
if signals["paired_quality_delta"] is None or signals["quality_delta_se"] is None:
    actions.append("collect_at_least_two_paired_observations")
elif abs(signals["paired_quality_delta"]) <= 2 * signals["quality_delta_se"]:
    actions.append("increase_repeated_seeds_or_sample_size")
if (signals["citation_support"] is None or
        signals["retrieval_recall"] is None):
    actions.append("define_valid_evaluation_denominators")
elif signals["citation_support"] < signals["retrieval_recall"]:
    actions.append("separate_retrieval_gain_from_generation_faithfulness")
if signals["unsafe_action_rate"] is None:
    actions.append("collect_tool_trajectory_labels")
elif signals["unsafe_action_rate"] > 0:
    actions.append("repair_tool_authorization_and_repeat_red_team")
if signals["cost_ratio"] > 1.2:
    actions.append("compare_unit_success_cost_before_deployment")

decision = "continue_after_evidence_repairs" if actions else "continue_to_holdout"

for name, value in signals.items():
    print(f"{name}={value}")
print(f"actions={actions}")
print(f"decision={decision}")
~~~

这个 demo 的重点是把不同问题拆开：质量差异是否超过噪声，检索 recall 是否转成引用支持，是否存在危险动作，成本是否增长。它不把四个指标压成一个总分，也不把 decision 字符串当作自动上线授权。

## 13.21 资料与证据边界

DPO 的目标和偏好优化背景可参考 Direct Preference Optimization：[论文原文](https://arxiv.org/abs/2305.18290)。它支持 policy/reference log-ratio 和偏好损失的研究脉络；具体数据、beta、长度偏差和能力回归需要在目标实验中单独测量。

FlashAttention 可参考 FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness：[论文原文](https://arxiv.org/abs/2205.14135)。它支持 tiling、online softmax 和 IO-aware exact attention 的技术事实；硬件上的端到端收益需要按实现、长度和并行方式复现。

Transformer 的基础结构可参考 Attention Is All You Need：[论文原文](https://arxiv.org/abs/1706.03762)。长上下文和检索评估可结合 Lost in the Middle：[论文原文](https://arxiv.org/abs/2307.03172) 与 LongBench：[论文原文](https://arxiv.org/abs/2308.14508)；它们支持位置利用和长任务评估的研究问题，不代表所有长上下文任务都可由 needle 测试覆盖。

RAG 的早期脉络可参考 Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks：[论文原文](https://arxiv.org/abs/2005.11401)。Agent 推理和行动可参考 ReAct：[论文原文](https://arxiv.org/abs/2210.03629)，网页 Agent 评估可参考 WebArena：[论文原文](https://arxiv.org/abs/2307.13854)。这些论文支持方法和 benchmark 的研究背景；真实系统还要加入权限、工具错误、成本和恢复。

Model-written evaluation 可参考 Discovering Language Model Behaviors with Model-Written Evaluations：[论文原文](https://arxiv.org/abs/2212.09251)。多模态研究讨论可参考 Visual Instruction Tuning：[论文原文](https://arxiv.org/abs/2304.08485)。可解释性讨论可参考 Locating and Editing Factual Associations in GPT：[论文原文](https://arxiv.org/abs/2202.05262) 和 Sparse Autoencoders Find Highly Interpretable Features in Language Models：[论文原文](https://arxiv.org/abs/2309.08600)。

论文评审和复现实验规范可参考 [NeurIPS Paper Checklist](https://neurips.cc/public/guides/PaperChecklist)、[ICLR Reviewer Guide](https://iclr.cc/Conferences/2025/ReviewerGuide) 和 [ML Reproducibility Challenge](https://reproducibility-challenge.github.io/)。这些资料帮助定义可复现性、实验透明度和审查维度，不替代某一论文的具体实验结果。

## 13.22 结语：把判断留在证据上

研究讨论能力不是记住更多论文名，而是能在陌生问题中保持顺序：先定义对象和瓶颈，再还原机制，接着检查强 baseline、控制变量和评估分母，然后说明结果边界，最后提出能够区分解释的下一步实验。

这个顺序让不同主题可以互相迁移。DPO 的长度偏差、RAG 的上下文混杂、Agent 的 demo bias、Attention 的硬件差异、SAE 的解释过度和新模型的证据等级，看起来属于不同领域，实际上都在考察同一件事：结论是否超出了证据能够支持的范围。

真正成熟的研究交流不需要把每个问题都回答成确定结论。能够清楚指出已知、未知、假设、风险和最小验证路径，往往比给出一个过度自信的完整答案更接近真实研究。

### 练习

1. 选择一篇你熟悉的论文，用对象、处理、结果和条件四项重写它的主 claim。
2. 对一篇报告“性能提升”的论文，列出三个可能的混杂因素和对应控制实验。
3. 对一个新 attention 方法分别设计训练、prefill 和 decode 三组评估。
4. 对一组 DPO preference pair 计算 response log probability、长度差和偏好 margin，讨论可能的长度偏差。
5. 设计一个 2×2 RAG 消融，区分 reranker 的收益和上下文长度的收益。
6. 把一个 Agent demo 改写成 outcome、process、safety、cost 四组指标。
7. 找一个最新模型的公开 claim，为它建立 source、scope、condition、independent check 和 status 五列证据账本。
8. 复读本章 demo，增加一个随机 seed 或 bootstrap 计算，并说明它改变了哪一个判断。
