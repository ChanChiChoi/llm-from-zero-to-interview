## Scope 与章节职责

- **中心问题**：如何从请求资源和实际账单中定位成本，选择改变工作量或单位资源产能的优化，并在相同任务分布下按质量、尾延迟和安全硬门槛判断是否保留。
- **章节边界**：本章负责 serving 请求级成本账本、优化经济性和实验决策；生产架构的副本、依赖、故障域和多租户总体结构交第 13 章；平台级集群成本与调度交第二十三册；模型压缩训练细节交第五册；统计评估方法链接第七册。本章不承诺具体 provider 价格、目标 GPU 加速或线上质量收益。
- **教学链**：开篇/§§1—2 从 workload 资源向量和计费口径走到 GPU/API 单位经济学；§§3—5 讨论选模、路由、上下文压缩和 cache；§§6—8 讨论 speculative decoding、量化/蒸馏、batch/队列/扩缩容；§§9—10 连接多租户与 RAG/Agent/多模态；§§11—12 把假设、对照、门禁落实为实验案例；§13 用手算对照代码预期，§14—16 收束常见失败、资料和全章结论。
- **简介/目录**：已更新第 12 章摘要，说明物理资源与供应商账单分离、单位成功任务成本和质量/尾延迟/安全约束。

## 定向扫描与候选去向

扫描日期为 2026-11-02。围绕“供应商账单如何表示缓存和 reasoning 用量”“本地 KV 复用能说明什么物理收益”“路由成本/质量目标会不会掩盖难题”“推测解码何时值得”“显存容量和任务成功成本如何连接”“自动扩缩容的指标控制能表达哪些 LLM 约束”查阅了原始论文及 OpenAI、vLLM、Kubernetes 官方动态文档。来源事实及边界只记录于 `research/llm-inference-cost-and-routing-2026.md`。

- **账单 usage 与物理资源**：将 `P_in` 定义为输入总量，cache read/write 是输入子集；visible/reasoning output 是账单 output 的可见/不可见子集，不能重复加总。加入 OpenAI reasoning/token counting 及 prompt cache 文档作为访问日模型合同示例；不推导其他 provider 的字段、价格或 rate limit。
- **路由评估**：纳入 2026-10-02 arXiv v1《Dynamic LLM Routers are Often Misguided》，用于提醒难度盲区、输出长度反转和来源匹配偏差；以匹配成本随机路由基线、难度分层与来源内表现补充评测。结论严格限于作者的单轮英文 benchmark，不写成所有生产路由器无效。
- **缓存与推测解码**：分开本地 APC 的 prefill/KV 占用与供应商 API 的计费类别；增加 cache write/read 费率的日期化合成例。Speculative decoding 的接受率只用于预期 token 轮数，单独计入草稿与验证资源，不把 token 数直接称为加速比。
- **容量与经济性**：HPA 比例公式只作副本建议的控制基础，正文补充 queue age、待处理 token、KV 和模型加载限制；量化、蒸馏、batch 与多租户都按目标任务和总成本/成功任务核算。
- **证据边界与暂缓候选**：Minitron、KIVI、FrugalGPT、RouteLLM 和 speculative sampling 继续绑定原论文模型/数据/硬件设置；修正 Minitron 来源条目，将 1.8× 从 FLOPs 更正为作者报告的成本收益。搜索中出现的其他 routing/KV cache 预印本未纳入本章结论；在未完成原文核验前不据其扩写，若后续扫描确认与现有主线直接相关再复查。

- **账单手算**：20,000 输入 token 中 8,000 普通输入、12,000 缓存读取，1,500 输出中 900 reasoning、600 visible；在 $3/$0.30/$12 每百万 token 的合成费率下为 `$0.0456`，只按可见输出会少记 `$0.0108`。缓存子类与 reasoning 子类均不在总量上重复相加。
- **路由手算**：1,000 请求中 800 FAQ/200 复杂问答；全走大模型 `$10`、期望 956 个成功，分流后 `$3.60`、期望 940 个成功；单位成功成本约 `$0.01046` 降至 `$0.00383`，但 FAQ 成功率由 97% 降至 95%，需先过逐任务质量底线。
- **Prefix/response cache**：10,000-token 前缀共 4 次请求（一次 write、三次 read），假设费率 1.25/0.10，账单等价单位为 15,500 对 40,000，降 61.25%；response cache 示例的纯成本回本命中率 3%，50% 命中时每次 `$0.0053`，节省 47%。质量、权限和新鲜度是先决门槛。
- **Speculative decoding**：`K=4, α=0.8` 时每轮期望输出 `1+0.8+0.64+0.512+0.4096=3.3616` token；400-token 输出的假设普通成本 4,000 GPU-ms，候选 119 轮×(18+6) GPU-ms=2,856 GPU-ms，约省 28.6%，未含并发、显存和实际硬件差异。
- **显存/蒸馏**：7B FP16 权重近似 14 GB，raw W4 约 3.5 GB；24 GB GPU 扣 2 GB workspace、4 GB 余量，按每序列 0.5 GB KV 分别约 8 与 29 序列。蒸馏例固定训练/刷新 `$30,000`，每任务 serving 节省 `$0.006`，约 500 万任务回本；15% fallback、每次 `$0.04` 会耗尽该节省。
- **batch/多租户**：GPU `$2/hour` 下，1,000 个成功任务为 `$0.002/成功任务`；batch throughput 1,450、失败 12% 后成功 1,276，单位成功成本约 `$0.001567`，较基线低约 21.6%，但 P95/TPOT 越线仍不通过。10 分钟 600 GPU-s 留 20% 系统预算后分配 A/B 为 288/192 GPU-s，以 1.2/0.2 GPU-s 每请求换算为 240/960 个请求，说明 QPS 不能替代资源预算。
- **专项账本**：RAG 每千请求 baseline `$15.05`，候选 `$11.00`；加 5% 恢复调用 `$0.50` 后为 `$11.50`，净省约 23.6%。Agent 摘要例每任务少 6,000 输入 token、省 `$0.018`，但摘要本身 `$0.0222`，单次会话增加 `$0.0042`。60 分钟音频、RTF 1.1 与 `$2/GPU-hour` 得 `$2.20`，RTF 0.55 得 `$1.10`；10% 重跑后净 GPU 节省 `$0.99`。
- **实验与综合案例**：按组总成本除以总成功数，`$100/95≈$1.053` 对 `$80/70≈$1.143`，候选总账单虽少 20%，每成功任务反而高约 8.6%。综合客服例 `$13.50/950≈$0.01421` 对 `$12/930≈$0.01290`，成本/成功降低约 9.2%，但 94% 成功门槛下 93% 候选仍暂停。
