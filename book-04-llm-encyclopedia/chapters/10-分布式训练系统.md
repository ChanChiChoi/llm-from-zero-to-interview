# 第 10 章 分布式训练系统：从多卡计算到可恢复的平台

训练一个小模型时，单张 GPU 上的 Python 程序看起来就是全部系统：读一个 batch，执行 forward 和 backward，更新参数，然后保存 checkpoint。当模型、数据和训练时间增长到单机无法承受时，问题会迅速变成系统问题。模型参数要放在哪些设备上，梯度如何汇总，数据如何到达 GPU，某一个进程失败时其他进程怎么办，抢占后能不能恢复，实验结果能不能复现，这些问题彼此牵连。

本章从一次训练 step 出发，逐层建立分布式训练平台的账本。先解释数据并行、张量并行、流水并行和状态分片，再讨论通信、显存、数据、checkpoint、集群调度、平台生命周期、可观测性、安全和成本。初学者可以把它看成“让多个 GPU 一起做同一件事”的完整故事；有经验的读者则需要关注每个公式的适用边界、通信发生的位置和失败后还能保留哪些证据。

本章使用四种证据。论文用于说明算法最初的机制，框架文档用于说明 API 和运行语义，代码示例只验证小规模的数量关系，目标集群上的吞吐和稳定性必须由实测得出。公开论文中的 benchmark 不能直接变成某种 GPU、网络或业务流量下的生产承诺。

~~~text
一次训练任务的主要路径：

提交配置
  -> 校验身份、数据、镜像和资源
  -> 排队与拓扑感知调度
  -> launcher 建立 rank 和通信组
  -> 数据读取与 batch 形成
  -> forward / backward / collective
  -> optimizer 更新
  -> checkpoint 与评估
  -> 记录实验、注册产物、释放资源
~~~

## 10.1 先建立训练账本：计算、显存与全局 batch

### 从单卡训练的一个 step 开始

设模型参数为 `theta`，一个 batch 为 `x`，标签为 `y`。训练 step 的抽象过程是：

~~~math
z = f_{\theta}(x),\qquad
L = \frac{1}{|x|}\sum_{(x_i,y_i)}\ell(z_i,y_i),
\qquad
\theta \leftarrow \operatorname{Optimizer}(\theta,\nabla_{\theta}L).
~~~

分布式训练并没有改变这三个数学对象，但改变了它们的存放位置和产生方式。不同 GPU 可能各自处理一部分样本，也可能各自保存一部分层内矩阵或参数状态。通信操作的目的，是在更新前把其他设备需要的信息交换过来。

### 显存不是只有模型权重

刚接触大模型训练时，最容易犯的估算错误是用“参数量乘以每个参数的字节数”判断能否训练。推理时可能主要关心权重和 KV cache，训练时还要保存梯度、优化器状态、激活和临时通信 buffer。以 AdamW 为例，除了低精度参数和梯度，通常还会有 FP32 master weight、一阶矩和二阶矩。

一个粗略的单卡账本可以写成：

~~~math
M_{\mathrm{card}}
\approx
M_{\mathrm{param}}
+M_{\mathrm{grad}}
+M_{\mathrm{master}}
+M_{\mathrm{moment}}
+M_{\mathrm{activation}}
+M_{\mathrm{temporary}}
+M_{\mathrm{communication}}.
~~~

如果参数量是 `N`，参数、梯度、master weight、一阶矩和二阶矩每个元素分别占 `b_p`、`b_g`、`b_m`、`b_1` 和 `b_2` 字节，那么状态部分可近似为：

~~~math
M_{\mathrm{state}}
\approx
N(b_p+b_g+b_m+b_1+b_2).
~~~

这个式子没有包含激活，因为激活与 batch、序列长度、层数、隐藏维度、checkpoint 策略有关；也没有包含框架的碎片和临时 workspace。因此它适合做数量级判断，不适合替代目标模型的显存 profile。

### 全局 batch 的三个乘数

数据并行训练中，每个数据并行副本先处理一个 micro-batch。经过若干次梯度累积后，才进行一次 optimizer step。若每个副本的 micro-batch 为 `B_micro`，累积次数为 `A`，数据并行副本数为 `D_dp`，则一次 optimizer 更新对应的全局 batch 近似为：

~~~math
B_{\mathrm{global}}
=B_{\mathrm{micro}}\times A\times D_{\mathrm{dp}}.
~~~

例如每张卡一次处理 2 个序列，累积 8 次，数据并行副本为 4，则一次更新使用 64 个序列。这里的 `D_dp` 不是总 GPU 数；如果同时使用 tensor parallel 和 pipeline parallel，总进程数还要拆成不同并行维度：

~~~math
W = D_{\mathrm{dp}}\times T_{\mathrm{tp}}\times P_{\mathrm{pp}}\times E_{\mathrm{ep}},
~~~

其中 `W` 是参与通信的进程数，`T_tp` 是张量并行度，`P_pp` 是流水并行度，`E_ep` 是使用专家并行时的额外维度。不同框架对专家并行组的定义可能不同，不能仅凭进程总数反推有效 batch。

~~~python
def global_batch(micro_batch, accumulation_steps, data_parallel):
    values = (micro_batch, accumulation_steps, data_parallel)
    if (not all(isinstance(value, int) for value in values)
            or any(value <= 0 for value in values)):
        raise ValueError("batch factors must be positive")
    return micro_batch * accumulation_steps * data_parallel


def parallel_product(data_parallel, tensor_parallel, pipeline_parallel, world_size):
    values = (data_parallel, tensor_parallel, pipeline_parallel, world_size)
    if (not all(isinstance(value, int) for value in values)
            or any(value <= 0 for value in values)):
        raise ValueError("parallel dimensions must be positive integers")
    product = data_parallel * tensor_parallel * pipeline_parallel
    if product != world_size:
        raise ValueError("parallel dimensions do not cover world size")
    return product


assert global_batch(2, 8, 4) == 64
assert parallel_product(2, 2, 2, 8) == 8
print("global_batch=", global_batch(2, 8, 4))
~~~

### 参数、样本和 token 的区别

“batch size 变大”可能指序列数变大，也可能指 token 数变大。长短样本混合时，64 条短序列和 64 条长序列的计算量不同；padding、packing 和动态 batch 会让序列数口径进一步失真。训练平台至少应同时保存 `samples`、`tokens`、`non_padding_tokens`、`micro_batches` 和 `optimizer_steps`，并明确学习率是按 optimizer step、token 还是其他单位变化。

对于语言模型，常用的有效 token 吞吐为：

~~~math
R_{\mathrm{token}}
=\frac{N_{\mathrm{nonpad\ token}}}{T_{\mathrm{wall}}}.
~~~

如果只报告 samples/s，长上下文实验和短上下文实验之间很容易形成错误比较。

## 10.2 数据并行与 collective：每个进程到底交换什么

### 数据并行的直觉

数据并行把同一个模型副本放到多个设备，每个副本读取不同的数据切片。每个进程独立执行 forward 和 backward，得到局部梯度 `g_r`。为了让所有副本执行同一个更新，需要得到全局梯度：

~~~math
g=\frac{1}{D_{\mathrm{dp}}}\sum_{r=1}^{D_{\mathrm{dp}}}g_r.
~~~

`DistributedDataParallel` 的典型语义是每个进程拥有一份模型副本，并在 backward 过程中对梯度做同步。这个同步不是“自动把所有 Python 状态变成一致”，它主要针对参与通信的参数梯度。随机数、数据读取位置、非参数缓存、外部副作用和自定义通信都需要额外设计。

### All-reduce、reduce-scatter 和 all-gather

把集体通信拆成三种基本动作，会比背 API 名称更清楚。

* `all-reduce`：所有 rank 得到聚合后的完整张量，常用于 DDP 梯度同步。
* `reduce-scatter`：先聚合，再把不同分片发送给不同 rank，每个 rank 只保留结果的一部分。
* `all-gather`：每个 rank 提供一个分片，所有 rank 收集完整张量。

ZeRO/FSDP 经常把 `reduce-scatter` 与 `all-gather` 组合起来，减少每个 rank 长期保存的状态。通信原语的正确性还依赖调用顺序：如果 rank 0 进入 all-reduce 而 rank 1 进入 all-gather，程序可能挂起，也可能由底层通信库报错。

### Ring AllReduce 的数量级

设每个 rank 要聚合的数据大小为 `D` 字节，参与 rank 数为 `P`。理想 ring 实现中，reduce-scatter 和 all-gather 各传输约 `(P-1)/P` 个 `D`，因此单 rank 的总发送量近似为：

~~~math
V_{\mathrm{ring}}
\approx 2\times\frac{P-1}{P}\times D.
~~~

总时间还受到链路带宽、启动延迟、拓扑、拥塞、消息切分和 overlap 影响。公式适合解释“为什么梯度越大通信越重”，不能直接预测 NCCL 在目标集群上的秒数。

~~~python
import math


def ring_all_reduce_bytes(payload_bytes, ranks):
    if (not isinstance(payload_bytes, (int, float))
            or not isinstance(ranks, int)
            or not math.isfinite(payload_bytes)
            or payload_bytes < 0 or ranks < 1):
        raise ValueError("invalid communication input")
    if ranks == 1:
        return 0.0
    return 2.0 * (ranks - 1) / ranks * payload_bytes


def bandwidth_seconds(bytes_sent, bytes_per_second):
    if (not isinstance(bytes_sent, (int, float))
            or not isinstance(bytes_per_second, (int, float))
            or not math.isfinite(bytes_sent)
            or not math.isfinite(bytes_per_second)
            or bytes_sent < 0 or bytes_per_second <= 0):
        raise ValueError("bandwidth must be positive")
    return bytes_sent / bytes_per_second


volume = ring_all_reduce_bytes(8 * 1024**3, 8)
assert round(volume / 1024**3, 2) == 14.0
assert round(bandwidth_seconds(volume, 1 * 1024**4), 3) == 0.014
print("ring_gib=", round(volume / 1024**3, 2))
~~~

### 梯度平均的细节

如果损失函数已经对本地 batch 求平均，all-reduce 后除以 `D_dp` 通常对应等大小 batch 的全局平均。如果各 rank 的有效 token 数不同，简单的 rank 平均可能产生偏差。更严谨的 token-level loss 需要先聚合有效 token 的损失总和与计数：

~~~math
L_{\mathrm{global}}
=\frac{\sum_r S_r}{\sum_r C_r},
~~~

其中 `S_r` 是 rank `r` 的有效 token 损失和，`C_r` 是有效 token 数。padding、最后一个不完整 batch、动态 packing 和样本过滤都会影响 `C_r`。这也是为什么训练日志必须同时记录有效 token 数，而不能只记录一个 loss 浮点数。

### 数据切分与重复样本

数据并行要求 sampler 在每个 epoch 或数据迭代周期内给不同 rank 分配不同索引。没有正确设置 epoch、seed 或 shard，可能出现每张卡重复读取相同样本，表面上吞吐很高，实际有效数据量却没有增加。恢复训练时还要决定 dataloader cursor 如何保存：只恢复 global step 而不恢复样本位置，可能使实验重复或跳过数据。

## 10.3 张量并行：把一层矩阵分到多张卡

### 列切分和行切分

线性层通常写成：

~~~math
Y=XW.
~~~

设 `W` 的输出维度被切成两块：

~~~math
W=[W_1\;W_2],
\qquad
Y=[XW_1\;XW_2].
~~~

每张卡可以独立计算自己的输出列，这就是 column parallel 的基本直觉。得到下一层时，如果输入维度被切分，则可以把权重按行切分：

~~~math
W=\begin{bmatrix}W_1\\W_2\end{bmatrix},
\qquad
X=[X_1\;X_2],
\qquad
XW=X_1W_1+X_2W_2.
~~~

这里各 rank 先得到部分结果，随后需要 all-reduce 或其他聚合。Transformer 的 attention projection 和 MLP 往往交替使用这两种切法，让中间通信尽量合并或延后。

### 张量并行的收益与代价

张量并行可以把单层矩阵和激活分摊到多个 GPU，适合单层或单个模型副本无法放入一张卡的情况。代价是层内通信频繁，通信发生在每个 Transformer block 的关键路径上。把 tensor parallel group 跨越慢速机间网络，可能比单卡少算一部分矩阵更糟。

张量并行的配置至少需要回答四个问题：

1. 每个权重维度如何切分，切分后的 shape 是否整除。
2. 哪些中间张量需要 all-reduce、all-gather 或 reduce-scatter。
3. 这个通信组映射到 NVLink、PCIe 还是跨节点网络。
4. checkpoint 保存的是完整权重还是分片权重，加载时如何改变并行度。

~~~python
def column_parallel_shape(batch, sequence, hidden, output, parts):
    values = (batch, sequence, hidden, output, parts)
    if (not all(isinstance(value, int) for value in values)
            or not all(value > 0 for value in values)
            or output % parts):
        raise ValueError("output dimension must be divisible")
    return (batch, sequence, hidden), (hidden, output // parts)


def row_parallel_partial_shape(batch, sequence, hidden, output, parts):
    values = (batch, sequence, hidden, output, parts)
    if (not all(isinstance(value, int) for value in values)
            or not all(value > 0 for value in values)
            or hidden % parts):
        raise ValueError("hidden dimension must be divisible")
    return (batch, sequence, hidden // parts), (hidden // parts, output)


x_shape, w_shape = column_parallel_shape(2, 16, 4096, 11008, 8)
assert x_shape == (2, 16, 4096)
assert w_shape == (4096, 1376)
partial_x, partial_w = row_parallel_partial_shape(2, 16, 4096, 4096, 8)
assert partial_x[-1] == partial_w[0] == 512
print("column_weight=", w_shape, "row_partial=", partial_w)
~~~

### Attention 和 MLP 中的通信位置

在 multi-head attention 中，head 可以分配到不同 rank；但 Q、K、V 的投影、attention score、输出投影之间的张量布局必须相互匹配。GQA 或 MQA 改变 KV head 数后，通信和 KV cache 的切分方式也可能变化。MLP 的 gated 结构通常包含两个上投影和一个下投影，切分时必须让门控分支保持相同的 hidden partition。

因此“把线性层除以 GPU 数”不是完整实现。正确的张量并行需要从 shape、collective 顺序、参数布局、通信组和 checkpoint 格式一起验证。一个只在 2 卡上通过 forward 的 toy 代码，并不能证明 16 卡多节点训练可以正确收敛。

## 10.4 流水并行：让不同层同时工作

### 为什么需要 micro-batch

流水并行把连续的模型层分配给多个 stage。一个完整 batch 如果一次从 stage 0 传到 stage 1，再等待反向传播，会让大部分 stage 空闲。于是大 batch 被切成多个 micro-batch，让不同 stage 同时处理不同 micro-batch。

~~~text
时间 ->
stage 0: F0 F1 F2 F3 B3 B2 B1 B0
stage 1:    F0 F1 F2 F3 B3 B2 B1 B0
stage 2:       F0 F1 F2 F3 B3 B2 B1 B0
~~~

这是示意图，不是所有调度器的精确时间表。实际执行可能使用 GPipe 的 fill-drain、1F1B、interleaved schedule 或其他变体。共同问题是流水线开始和结束时存在空闲时间，stage 之间还要传输 activation 和 gradient。

### bubble 的近似关系

在一个简单的 `P` stage、`M` 个 micro-batch 的模型中，流水线 bubble 比例常用数量级近似：

~~~math
R_{\mathrm{bubble}}
\approx\frac{P-1}{M+P-1}.
~~~

当 `M` 增大时，bubble 通常下降，但激活保存、调度开销和全局 batch 约束会增加。这个式子假定各 stage 计算时间接近、通信开销可以被简化；只要 stage 负载不均衡，实际空闲比例可能更高。

~~~python
def pipeline_bubble_ratio(stages, micro_batches):
    if (not isinstance(stages, int) or not isinstance(micro_batches, int)
            or stages < 1 or micro_batches < 1):
        raise ValueError("stages and micro_batches must be positive")
    return (stages - 1) / (micro_batches + stages - 1)


assert round(pipeline_bubble_ratio(4, 12), 4) == round(3 / 15, 4)
assert pipeline_bubble_ratio(4, 48) < pipeline_bubble_ratio(4, 12)
print("bubble_4x12=", round(pipeline_bubble_ratio(4, 12), 4))
~~~

### stage 平衡比 micro-batch 数更重要

如果 stage 0 需要 10 ms，stage 1 需要 20 ms，stage 2 需要 9 ms，那么即使增加 micro-batch，stage 1 仍然会成为流水线节拍。应按层的 FLOPs、激活大小、通信量和实际 profile 重新切分，而不是只按层数平均。embedding、输出 head、MoE 层和长序列 attention 往往会破坏“每层成本相同”的假设。

流水并行还带来版本一致性问题。forward 激活和 backward gradient 必须对应同一份参数版本；optimizer 更新通常在完整的一组 micro-batch 后发生。若在中途错误地更新了某个 stage，可能形成难以复现的异步参数状态。

### 什么时候不应优先选择流水并行

如果模型能通过状态分片放入单个数据并行副本，且高速互联足够，流水并行的调度和激活管理可能增加复杂度。反过来，如果单层就超过单卡容量，或者模型层数很深且可以平衡切分，流水并行才更有必要。最终选择应由显存账本、通信 profile 和恢复复杂度共同决定。

## 10.5 ZeRO 与 FSDP：切分冗余的训练状态

### 数据并行为什么浪费显存

普通数据并行的每个 rank 都保存完整参数、完整梯度和完整 optimizer state。参数副本用于 forward，梯度用于更新，但在很多时刻并不是所有 rank 都需要完整的 optimizer state。ZeRO 的核心思想是切掉这些跨 rank 重复的状态。

可以把状态分片分成三个层次理解：

* 第一层只切 optimizer state，模型参数和梯度仍然复制。
* 第二层继续切 gradient，每个 rank 保存一部分梯度。
* 第三层连 parameter 也切分，forward 或 backward 需要时临时 all-gather。

对于 `D` 个数据并行 rank，理想状态部分的长期存储可从近似 `D` 份降到 1 份，但通信量、临时峰值和实现约束会增加。ZeRO-Infinity 等工作进一步讨论了 CPU 或 NVMe offload；offload 节省的是 GPU 显存，不是凭空消除数据搬运。

### FSDP 的运行语义

PyTorch FSDP 以参数分片为核心，在需要计算某个模块时 all-gather 参数，计算完成后释放或重新分片，并在 backward 中使用 reduce-scatter 聚合梯度。实际行为还受 wrapping policy、mixed precision、预取、状态字典类型和 checkpoint API 影响。

“使用 FSDP”不是一个显存数字。至少要区分：

~~~text
FULL_STATE_DICT：收集完整模型状态，方便小规模导出但可能产生集中式峰值
SHARDED_STATE_DICT：保存分片状态，适合大规模恢复和迁移
参数 all-gather：计算前的临时通信与显存峰值
梯度 reduce-scatter：反向过程中的聚合与分片
wrap policy：决定哪些模块成为分片边界
~~~

### 分片的简化显存账本

若状态总量为 `M_state`，数据并行度为 `D`，理想长期分片下可近似为：

~~~math
M_{\mathrm{sharded\ state}}
\approx\frac{M_{\mathrm{state}}}{D}.
~~~

但某个模块计算前还可能临时持有完整参数：

~~~math
M_{\mathrm{peak}}
\approx
M_{\mathrm{local\ shard}}
+M_{\mathrm{all\ gather\ parameter}}
+M_{\mathrm{activation}}
+M_{\mathrm{workspace}}.
~~~

这解释了为什么“总参数除以 GPU 数”仍然可能 OOM。峰值发生在哪个模块、哪个阶段，必须通过 memory snapshot 或 profiler 确认。

~~~python
import math


def sharded_bytes(total_bytes, ranks):
    if (not isinstance(total_bytes, (int, float))
            or not isinstance(ranks, int)
            or not math.isfinite(total_bytes)
            or total_bytes < 0 or ranks < 1):
        raise ValueError("invalid state size")
    return total_bytes / ranks


def peak_with_gather(local_state, gathered_parameter, activation, workspace):
    values = (local_state, gathered_parameter, activation, workspace)
    if (not all(isinstance(value, (int, float)) and math.isfinite(value)
                for value in values)
            or any(value < 0 for value in values)):
        raise ValueError("memory terms must be non-negative")
    return sum(values)


state = 240 * 1024**3
assert sharded_bytes(state, 8) == 30 * 1024**3
peak = peak_with_gather(30, 16, 8, 2)
assert peak == 56
print("local_state_gib=", sharded_bytes(state, 8) / 1024**3)
~~~

### checkpoint 与并行度变化

保存 checkpoint 时要明确它是按 rank 保存的分片，还是由某个 rank 收集的完整状态。若训练从 8 个数据并行 rank 恢复到 4 个 rank，分片文件不能简单地按文件名加载；需要读取 manifest、重排分片、恢复 optimizer 状态，并重新定义 dataloader 的样本位置。模型权重恢复成功，不代表训练动力学恢复成功。

## 10.6 激活重计算、梯度累积与混合精度

### 激活 checkpoint 是用计算换显存

反向传播需要部分 forward 激活。激活 checkpoint 只保存选定边界，反向时重新执行被省略的 forward。若一段计算原本耗时 `T_f`，重算大约增加一段相近的 forward 成本，但可以显著降低激活存储：

~~~math
T_{\mathrm{step,new}}
\approx T_{\mathrm{step,old}}+T_{\mathrm{recompute}},
\qquad
M_{\mathrm{activation,new}}<M_{\mathrm{activation,old}}.
~~~

重计算不是免费优化。随机算子、dropout mask、非纯函数、自定义 CUDA kernel 和缓存状态如果没有保持一致，重算的 activation 可能与原 forward 不同。实现还需要注意输入是否要求梯度、张量是否被原地修改，以及 checkpoint API 的 reentrant 语义。

### 梯度累积并不改变每个 micro-batch 的显存峰值

梯度累积把多个 micro-batch 的梯度相加，达到一次较大的有效 batch 后才调用 optimizer step。它主要降低单次显存需求，不自动减少总计算，也不一定提高吞吐。若累积 `A` 次，每次 loss 都除以 `A`，则累计梯度近似为：

~~~math
g_{\mathrm{acc}}
=\sum_{a=1}^{A}\frac{1}{A}g_a.
~~~

最后一个不足 `A` 个 micro-batch 的窗口尤其容易出错。若仍然除以固定 `A`，实际梯度会被缩小。可以按当前窗口的有效 token 数重新归一化，或者明确丢弃不完整窗口。

### BF16、FP16 与 loss scaling

混合精度把部分矩阵计算放到低精度，把累积或敏感操作保留在更高精度。BF16 的指数范围通常更接近 FP32，FP16 的动态范围更窄，因此 FP16 训练常使用 loss scaling。设缩放因子为 `s`：

~~~math
\widetilde{L}=sL,
\qquad
\nabla_{\theta}\widetilde{L}=s\nabla_{\theta}L.
~~~

反向结束后需除以 `s`，再检查梯度是否有限；出现 Inf/NaN 时跳过更新并调整 scale。scale 过大容易溢出，过小又可能让小梯度下溢。自动 scaler 是工程实现，不是数值稳定的证明。

~~~python
import math


def accumulated_gradient(gradients, denominator=None):
    if (not gradients
            or any(not isinstance(value, (int, float))
                   or not math.isfinite(value) for value in gradients)):
        raise ValueError("gradients must not be empty")
    if denominator is None:
        denominator = len(gradients)
    if (not isinstance(denominator, (int, float))
            or not math.isfinite(denominator) or denominator <= 0):
        raise ValueError("denominator must be positive")
    return sum(gradients) / denominator


def finite_update(loss, gradient, learning_rate):
    values = (loss, gradient, learning_rate)
    if not all(isinstance(value, (int, float)) and math.isfinite(value)
               for value in values):
        return {"updated": False, "reason": "non_finite"}
    if learning_rate < 0:
        raise ValueError("learning_rate must be non-negative")
    return {"updated": True, "delta": -learning_rate * gradient}


assert accumulated_gradient([2.0, 4.0, 6.0]) == 4.0
assert accumulated_gradient([2.0, 4.0], denominator=2) == 3.0
assert finite_update(1.0, 2.0, 0.1)["updated"]
assert not finite_update(float("nan"), 2.0, 0.1)["updated"]
print("mean_gradient=", accumulated_gradient([2.0, 4.0, 6.0]))
~~~

### 数值稳定性的观测项

训练平台应按 step 保存 loss、有效 token 数、learning rate、gradient norm、parameter norm、非零梯度比例、loss scale、跳过的 update 次数和精度配置。单看 loss 无法判断“模型没有学会”还是“参数根本没有更新”。LoRA 微调中 target module 配错、assistant label 全部被 mask、optimizer 没有包含 adapter 参数，都可能产生看似正常但没有学习的曲线。

## 10.7 训练效率：从 GPU 忙不忙到有效 token 吞吐

### step time 的分解

一个训练 step 可以拆成：

~~~math
T_{\mathrm{step}}
=T_{\mathrm{data}}
+T_{\mathrm{forward}}
+T_{\mathrm{backward}}
+T_{\mathrm{collective}}
+T_{\mathrm{optimizer}}
+T_{\mathrm{checkpoint}}
+T_{\mathrm{other}}.
~~~

这些项可能重叠，因此直接相加通常是 wall time 的上界分解。要知道 overlap 是否有效，需要 trace 或 profiler 的时间线，而不是把每个函数耗时相加。

### 吞吐、利用率与 MFU

有效 token 吞吐：

~~~math
R_{\mathrm{tokens/s}}
=\frac{N_{\mathrm{tokens}}}{T_{\mathrm{wall}}}.
~~~

GPU utilization 只说明 SM 或设备在某个时间窗口内处于活动状态的比例；它可能在做无效 padding、等待通信前的短 kernel，或执行重算。MFU 通常把实际模型 FLOPs 与硬件理论 FLOPs 相比：

~~~math
\mathrm{MFU}
=\frac{F_{\mathrm{model}}/T_{\mathrm{compute}}}
{F_{\mathrm{peak}}}.
~~~

不同论文对 `F_model`、是否包含 backward、是否采用稀疏 FLOPs、时间窗口和峰值精度的定义可能不同。报告 MFU 必须同时给出模型结构、序列长度、batch、精度和公式口径。HFU 则可能用实际硬件执行的 FLOPs 估计来衡量，二者不应混用。

### 读懂“GPU 利用率低”的几种可能

GPU 利用率低可能来自数据读取慢、CPU tokenizer 慢、通信等待、pipeline bubble、checkpoint 写入、频繁同步或请求调度。GPU 利用率高也不一定代表训练有效：如果 loss 已 NaN，或者大量时间在重复计算、padding 和失败重试，资源仍在消耗但有效产出为零。

~~~python
import math


def step_breakdown(step_seconds):
    required = ("data", "forward", "backward", "collective", "optimizer", "checkpoint")
    if not isinstance(step_seconds, dict):
        raise ValueError("step_seconds must be a dictionary")
    if any(name not in step_seconds for name in required):
        raise ValueError("missing step component")
    if (any(not isinstance(step_seconds[name], (int, float))
                   or not math.isfinite(step_seconds[name])
                   or step_seconds[name] < 0 for name in required)):
        raise ValueError("step components must be finite and non-negative")
    total = sum(step_seconds.values())
    if total <= 0:
        raise ValueError("step time must be positive")
    return {
        "total": total,
        "data_ratio": step_seconds["data"] / total,
        "collective_ratio": step_seconds["collective"] / total,
        "checkpoint_ratio": step_seconds["checkpoint"] / total,
    }


sample = step_breakdown({
    "data": 1.0,
    "forward": 3.0,
    "backward": 5.0,
    "collective": 2.0,
    "optimizer": 1.0,
    "checkpoint": 0.0,
})
assert sample["total"] == 12.0
assert round(sample["collective_ratio"], 4) == round(2 / 12, 4)
print("collective_ratio=", round(sample["collective_ratio"], 3))
~~~

### 性能实验的最小设计

一次性能实验应固定模型 commit、数据版本、tokenizer、精度、并行度、硬件、软件版本和 warm-up 规则，然后改变一个因素。至少记录：

~~~text
吞吐：non-padding tokens/s、samples/s、optimizer steps/s
延迟：step time 的 P50/P95，data wait，collective wait
显存：峰值、参数、激活、通信 buffer、碎片
通信：消息大小、collective 类型、链路和重叠比例
结果：loss、有效 token、是否出现 NaN、checkpoint 是否完整
~~~

短跑 benchmark 可能只反映 warm cache 和编译后的 kernel，长跑还会暴露 checkpoint、数据轮转、网络拥塞、节点故障和显存碎片。

## 10.8 训练稳定性与分布式故障定位

### 先区分现象

训练事故可以先分为五类：数值异常、显存异常、通信挂起、数据或 I/O 阻塞、吞吐退化。不同类别的第一证据不同：

~~~text
loss spike / NaN：loss、gradient、logits、学习率、精度、异常 batch
OOM：发生阶段、显存峰值、shape、激活、optimizer、临时 workspace
hang：所有 rank 的 heartbeat、最后 step、collective、进程状态
I/O 慢：data wait、worker queue、存储吞吐、坏 shard、cache hit
通信慢：rank step 分布、NCCL 日志、网络链路、首个异常 rank
~~~

最后一个 traceback 不一定是根因。一个 rank 先 OOM 或数据异常退出后，其他 rank 可能只会在下一次 collective 中等待并报告 timeout。

### loss 异常的证据链

loss 突然升高时，先检查有效 label 数是否变成零或极小值，再检查异常 batch 是否包含超长文本、非法 token、标签错位或数据分布突变。之后看 learning rate、gradient norm、loss scale、optimizer step 和 resume 状态。train loss 与 eval loss 背离还可能来自数据切分、评估 tokenizer、dropout 或训练目标不一致。

### NaN/Inf 的处理顺序

发现非有限值后，应保存触发 step、batch 或 shard 标识、输入长度、logits 范围、梯度范围、精度、loss scale、kernel 配置和最近 checkpoint。之后决定是停止、回滚到最近稳定 checkpoint、隔离坏样本还是降低 scale。单纯跳过 NaN batch 并继续运行可能掩盖系统性数值问题，也会改变有效 token 统计。

### hang 与 straggler

每个 rank 都应周期性报告 `last_progress_step`、`last_event`、`heartbeat`、当前 collective、GPU 利用率和 dataloader 状态。排查时寻找最早停止推进的 rank，而不是只找最后报 timeout 的 rank。常见根因包括：

* 不同 rank 进入了不同的分支，collective 调用顺序不一致。
* 一个 rank 的数据 worker 卡住或读取坏 shard。
* 某个 rank OOM、进程退出，其他 rank 等待通信。
* 跨节点网络丢包、RDMA 错误或 NCCL 拓扑选择异常。
* checkpoint 或外部评估只阻塞了部分进程。

### OOM 要定位到阶段

forward OOM 通常与输入 shape、激活和参数 all-gather 有关；backward OOM 可能来自梯度和反向激活；optimizer OOM 常见于状态或 master weight；eval OOM 可能因为忘记 `no_grad` 或评估 batch 太大；checkpoint OOM 则可能来自收集完整状态。对应动作可能是缩短序列、checkpoint activation、调整 wrap、使用 sharded state 或修改评估路径，不能把所有 OOM 都归结为“减小 batch”。

~~~python
import math


def classify_training_fault(event):
    if not isinstance(event, dict):
        raise ValueError("fault event must be a dictionary")
    for name in ("data_wait_ratio", "collective_ratio"):
        if name in event and (
                not isinstance(event[name], (int, float))
                or not math.isfinite(event[name])
                or event[name] < 0):
            raise ValueError("fault ratios must be finite and non-negative")
    if event.get("non_finite"):
        return "numeric"
    if event.get("oom_phase"):
        return "memory:" + event["oom_phase"]
    if event.get("collective_wait") and event.get("rank_stopped"):
        return "hang_or_straggler"
    if event.get("data_wait_ratio", 0.0) > 0.3:
        return "data_io"
    if event.get("collective_ratio", 0.0) > 0.3:
        return "communication"
    return "needs_more_evidence"


assert classify_training_fault({"oom_phase": "backward"}) == "memory:backward"
assert classify_training_fault({"collective_wait": True, "rank_stopped": True}) == "hang_or_straggler"
assert classify_training_fault({"data_wait_ratio": 0.4}) == "data_io"
print(classify_training_fault({"collective_ratio": 0.35}))
~~~

### 最小复现比经验猜测更可靠

把异常 batch、数据版本、代码 commit、最终配置、随机种子和环境 digest 固定下来，在单卡或少量 GPU 上复现。如果单卡小数据就能复现，优先怀疑代码、数据、配置或数值；只有多机才复现时，才更需要检查通信、拓扑、调度和环境。最小复现不是简单地把 batch 改成 1，而是尽量保留触发问题的 shape、精度、并行语义和输入。

## 10.9 集群拓扑：GPU 之间的距离会改变并行策略

### 一台机器不是一个均匀的设备集合

多 GPU 节点通常存在 GPU-GPU、GPU-NIC、CPU-GPU 和 GPU-存储的不同路径。GPU 之间可能通过 NVLink/NVSwitch 连接，也可能主要经过 PCIe；网卡可能靠近某些 NUMA 节点；磁盘控制器和 CPU socket 也有自己的亲和性。把 8 张卡当成“8 个完全等价端点”，会掩盖通信瓶颈。

~~~text
机内快链路：GPU <-> NVLink/NVSwitch <-> GPU
机内较慢路径：GPU <-> PCIe root complex <-> GPU 或 NIC
跨机路径：GPU <-> NIC <-> RDMA 网络 <-> NIC <-> GPU
数据路径：存储 <-> CPU/NIC <-> GPU，可能与训练共享带宽
~~~

### 并行组应服从拓扑

通常希望通信最频繁的 tensor parallel group 放在机内高速链路，pipeline stage 或 data parallel group 才跨节点，但具体选择取决于模型、消息大小、节点拓扑和网络。MoE 的 all-to-all 对网络压力尤其大，不能只按普通 data parallel 的 all-reduce 经验估计。

拓扑信息要进入调度器和 launcher，而不是只存在于人工运维文档。调度后至少要记录 GPU UUID、节点、NUMA、NIC、并行组映射和 NCCL 拓扑检测结果，这些信息是解释某次吞吐变化的必要上下文。

## 10.10 网络通信：带宽、延迟与 RDMA

### 计算一个通信下界

若某个 collective 在每个 rank 上需要发送 `V` 字节，链路有效带宽为 `B` 字节/秒，最乐观的传输时间下界约为：

~~~math
T_{\mathrm{transfer}}\ge\frac{V}{B}.
~~~

真实时间还包括启动延迟、协议开销、路径竞争、同步等待和不均衡：

~~~math
T_{\mathrm{collective}}
\approx T_{\mathrm{latency}}
+T_{\mathrm{transfer}}
+T_{\mathrm{contention}}
+T_{\mathrm{imbalance}}.
~~~

RDMA、GPUDirect RDMA 和 NCCL 能减少 CPU 拷贝或利用更合适的路径，但是否生效取决于网卡、驱动、权限、拓扑、容器配置和交换网络。看到 NCCL 可用并不等于每次通信都走了理想路径。

### 通信与计算 overlap

如果通信和计算能完全重叠，step wall time 接近两者的最大值；如果不能重叠，则接近两者之和：

~~~math
T_{\mathrm{overlap}}
\in[\max(T_{\mathrm{compute}},T_{\mathrm{comm}}),
T_{\mathrm{compute}}+T_{\mathrm{comm}}].
~~~

异步 collective、bucket 化梯度、预取和 kernel fusion 可以扩大重叠范围，但会增加显存、调度复杂度和调试难度。性能报告应给出通信暴露比例，而不只是理论带宽。

### 网络故障的证据

应把 NCCL 日志、网卡计数器、RDMA 错误、交换机端口、拓扑、rank 日志和 step 时间线关联起来。跨节点吞吐下降可能是网络问题，也可能是一个慢 rank 让所有 collective 等待。先区分链路本身慢与同步暴露，避免替换硬件却没有解决 straggler。

## 10.11 存储、数据供应与 checkpoint 生命周期

### 数据供应是一条流水线

训练数据通常经历对象存储或数据湖、manifest、shard、缓存、解压、tokenize、packing、worker queue，最后才进入 GPU。任何一层速度不足都会表现为 GPU 间歇性空转。数据平台应把样本内容与元数据分开管理：元数据记录来源、许可、版本、质量、敏感等级和删除边界，训练 worker 根据 manifest 读取可复现的 shard。

### 训练读取吞吐

如果每 step 需要 `D_step` 字节，目标 step 时间为 `T_step`，数据供应至少应满足：

~~~math
B_{\mathrm{data,required}}
\ge\frac{D_{\mathrm{step}}}{T_{\mathrm{step}}}.
~~~

实际还需加预取余量、并发读放大、解压和重试开销。缓存命中提升的是存储路径的有效带宽，不代表数据质量变好；坏 shard、重复样本和 schema 漂移仍需单独观测。

### checkpoint 不只是一个权重文件

完整训练 checkpoint 至少应考虑：

~~~text
model parameters 或 parameter shards
optimizer state
learning-rate scheduler state
global step 与 consumed tokens
随机数状态：Python、框架、GPU 和数据 worker
dataloader cursor、epoch、shard 与 sample position
并行度和参数布局
最终配置、代码 commit、数据 manifest、镜像 digest
manifest、checksum、完成标记和版本
~~~

权重文件存在只能说明部分字节写入过。应先写临时目录，完成所有 shard、checksum 和 manifest 后，再以原子方式写 committed 标记。读取端先验证 manifest，再加载文件；发现缺 shard 或 checksum 不一致时不能把目录当作可恢复状态。

### RPO、RTO 与 checkpoint 周期

恢复点目标 RPO 关心最多能丢多少训练进度，恢复时间目标 RTO 关心从故障到重新运行需要多久。若 checkpoint 周期为 `C` 秒，最坏情况下丢失的计算时间接近 `C`，但保存和恢复本身也会消耗时间：

~~~math
T_{\mathrm{recovery}}
=T_{\mathrm{detect}}
+T_{\mathrm{load}}
+T_{\mathrm{rendezvous}}
+T_{\mathrm{warmup}}
+T_{\mathrm{replay}}.
~~~

更频繁保存减少重算，却增加 I/O、存储和训练暂停；异步 checkpoint 可以减少暂停，但要处理一致性、写入失败和内存占用。

~~~python
import hashlib
import json


def manifest_digest(files):
    canonical = json.dumps(files, sort_keys=True, separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(canonical).hexdigest()


def checkpoint_is_committed(manifest, expected_digest):
    required = ("model", "optimizer", "scheduler", "rng", "data_cursor")
    if not isinstance(manifest, dict) or not isinstance(expected_digest, str):
        raise ValueError("manifest and digest have invalid types")
    if not manifest.get("committed"):
        return False
    if any(name not in manifest for name in required):
        return False
    actual = manifest_digest({name: manifest[name] for name in required})
    return actual == expected_digest


payload = {
    "model": "model-0001.safetensors",
    "optimizer": "optim-0001.bin",
    "scheduler": "sched.json",
    "rng": "rng.json",
    "data_cursor": "cursor.json",
}
digest = manifest_digest(payload)
manifest = dict(payload, committed=True)
assert checkpoint_is_committed(manifest, digest)
manifest["committed"] = False
assert not checkpoint_is_committed(manifest, digest)
print("manifest_digest=", digest[:12])
~~~

### 数据质量问题如何进入训练诊断

训练系统要能从异常 step 反查具体 batch、shard、数据版本和生成规则。空文本、非法 JSON、超长样本、标签错位、乱码、重复数据和敏感信息都可能表现成 loss 异常。把数据问题简单归咎于模型结构，会让修复方向完全错误。

## 10.12 容器、CUDA、NCCL 与 Kubernetes GPU

### 软件栈也是训练输入

GPU 训练的行为由驱动、CUDA runtime、通信库、框架、编译器、kernel、镜像和 host 配置共同决定。镜像应固定 digest，记录 Python 与系统依赖；任务状态中还要保存 GPU 型号、driver、CUDA/NCCL 版本和启动参数。只记录“使用某框架最新版”无法复现实验，因为最新版会随时间变化。

容器边界要同时满足可用性与安全性：GPU device 暴露、共享内存、网络和 RDMA 设备需要权限，但 `privileged`、任意 `hostPath`、root 身份和默认外联会扩大风险。训练脚本本质上可以执行任意代码，不能因为它是“内部实验”就忽略 runtime 隔离。

### Kubernetes 如何暴露 GPU

Kubernetes device plugin 把节点上的硬件资源注册为 extended resource，调度器据此分配 GPU。插件负责发现设备、上报资源和在容器启动时注入设备信息；它不自动解决分布式 gang scheduling、跨节点拓扑、训练 checkpoint 或公平队列。

Job 控制器能管理批处理任务的完成与重试，但一个多节点训练任务通常还需要 launcher、rendezvous、pod 间身份和“所有 worker 一起启动”的调度语义。只创建多个独立 Pod，可能先启动的进程永久等待尚未启动的 rank。

### 训练环境的验证顺序

启动任务后先做小规模通信与 CUDA smoke test，再做单卡 forward/backward，最后做多卡短跑。这样可以把“镜像不能启动”“GPU 不可见”“collective 不通”“模型逻辑错误”分开。直接提交长时间大规模训练，会把多个问题叠在一起，诊断成本很高。

## 10.13 多租户调度：公平、利用率与可靠性

### 队列和配额解决不同问题

配额回答“一个项目在一段时间内最多可以使用多少资源”；队列优先级回答“资源有限时谁先运行”；fair share 回答“过去已经使用很多的租户是否应该让出机会”。三者不能互相替代。硬配额能保护资源边界，却可能造成闲置；允许借用能提高利用率，却需要可回收和归还机制。

### dominant share 的直觉

当集群有 GPU、CPU、内存和本地 NVMe 等多种资源时，只看 GPU 数可能不公平。对租户 `i`，可以定义各资源的占用份额，再取最大值：

~~~math
S_i^{\mathrm{dom}}
=\max_k\left(\frac{u_{i,k}}{C_k}\right),
~~~

其中 `u_i,k` 是租户在资源维度 `k` 上的使用量，`C_k` 是集群总容量。调度器可优先考虑 dominant share 较低的租户，但还需加入优先级、任务大小、gang 可行性、拓扑和截止时间。

~~~python
import math


def dominant_share(usage, capacity):
    if (not isinstance(usage, dict) or not isinstance(capacity, dict)
            or not usage or set(usage) != set(capacity)):
        raise ValueError("resource dimensions must match")
    shares = []
    for name in usage:
        if (not isinstance(capacity[name], (int, float))
                or not isinstance(usage[name], (int, float))
                or not math.isfinite(capacity[name])
                or not math.isfinite(usage[name])
                or capacity[name] <= 0 or usage[name] < 0):
            raise ValueError("invalid resource amount")
        shares.append(usage[name] / capacity[name])
    return max(shares, default=0.0)


def can_borrow(usage, request, capacity, reserved):
    if (not all(isinstance(value, dict)
                for value in (usage, request, capacity, reserved))
            or set(usage) != set(capacity)
            or set(reserved) - set(capacity)
            or set(request) - set(capacity)):
        raise ValueError("resource dictionaries are incompatible")
    return all(
        usage[name] >= 0
        and request.get(name, 0) >= 0
        and reserved.get(name, 0) >= 0
        and usage[name] + request.get(name, 0)
        <= capacity[name] - reserved.get(name, 0)
        for name in capacity
    )


assert round(dominant_share({"gpu": 4, "cpu": 32}, {"gpu": 16, "cpu": 256}), 2) == 0.25
assert can_borrow({"gpu": 4, "cpu": 32}, {"gpu": 2, "cpu": 16}, {"gpu": 16, "cpu": 256}, {"gpu": 4, "cpu": 0})
print("dominant_share=", dominant_share({"gpu": 4, "cpu": 32}, {"gpu": 16, "cpu": 256}))
~~~

### gang scheduling 和拓扑约束

训练任务需要一组 GPU 同时获得，只有一部分 worker 启动时，先启动的 worker 可能长期占用资源并等待。gang scheduling 让任务要么获得足够资源一起启动，要么继续等待。它可能降低短期利用率，却避免半启动任务和无意义的通信等待。

bin packing 还要考虑 GPU 型号、节点、NVLink、NIC、rack、故障域、存储路径和 GPU 数量。一个数学上能放下的 placement，如果把 tensor parallel group 放在互不连通的慢链路上，实际 step 可能不可接受。

### 抢占与弹性训练

低优先级任务可以使用空闲资源，但被抢占时必须有 checkpoint 新鲜度、grace period、requeue、重试上限和 owner 通知。否则调度器提高了利用率，训练却不断丢失进度。

弹性训练允许 world size 改变，但这会影响 global batch、learning rate、optimizer state 分片、数据 sampler 和 checkpoint。最简单的安全策略是固定并行规模；只有当训练算法和状态转换都明确时，才让任务动态增减 worker。

## 10.14 训练平台生命周期与 TrainingJob 契约

### 平台控制面与训练数据面

训练平台可以分为两条路径：控制面负责提交、校验、排队、调度、状态和策略；数据面负责真正的 dataloader、forward/backward、collective、checkpoint 和评估。控制面不应把训练脚本内部的每个 tensor 细节都抽象出来，但必须冻结任务身份、资源、数据和产物契约。

一个可复现的 TrainingJob 至少应包含：

~~~text
owner、project、tenant、queue 和 priority
代码 commit、镜像 digest、依赖与启动命令
dataset manifest/version、tokenizer 和数据用途
模型配置、随机种子、精度、并行度与 global batch
GPU/CPU/memory/storage/network 资源
checkpoint 策略、恢复来源和最大重试次数
日志、指标、trace、实验 run 和产物 registry
数据访问、secret、网络与审计策略
~~~

提交接口应支持幂等键。用户重试 HTTP 请求时，不应因为控制面超时而创建两个同名训练任务。任务状态应由控制面持久化，worker 心跳只报告事实，不直接修改任意终态。

### 显式状态机

一个完整状态机可以是：

~~~text
SUBMITTED -> VALIDATED -> QUEUED -> SCHEDULED -> STARTING
STARTING -> RUNNING -> CHECKPOINTING -> RUNNING
RUNNING -> RETRYING -> QUEUED
RUNNING -> COMPLETED
SUBMITTED/QUEUED/RUNNING -> CANCELLED
VALIDATED/STARTING/RUNNING/RETRYING -> FAILED
~~~

每次迁移都应记录 actor、原因、时间、版本和相关事件。`FAILED` 不能覆盖“平台失败”“用户代码失败”“数据失败”“被抢占”和“取消”等不同语义，否则成本、重试和 SLO 都无法正确计算。

### launcher 的职责

launcher 把调度器给出的节点和 GPU 分配转成 `rank`、`local_rank`、`world_size`、rendezvous 地址、GPU 绑定、通信环境和启动命令。它还要处理 worker 重启、超时、信号转发和日志收集。常见错误包括 world size 与实际进程数不一致、local rank 与 GPU UUID 错配、不同节点使用不同代码或启动参数，以及只让 rank 0 保存结果却没有同步其他 rank。

### 数据、配置和产物血缘

训练结果至少要能沿着以下链路回溯：

~~~text
model artifact
  <- checkpoint / optimizer / scheduler / RNG
  <- training run / final config / code commit / image digest
  <- dataset manifest / tokenizer / data transform
  <- source data / license / quality report / access policy
~~~

实验追踪工具可以记录参数、指标、artifact 和运行标签，但平台仍要定义唯一 run id、版本关系和权限。一个 dashboard 上有 loss 曲线，不代表这个曲线对应的代码、数据和 checkpoint 可以找回。

## 10.15 数据版本、实验追踪与模型产物

### 数据版本不是文件夹名称

数据版本应由不可变 manifest 或内容寻址标识。manifest 记录 shard 列表、大小、checksum、来源、过滤规则、采样权重、tokenizer、敏感等级和生成时间。删除请求或许可变化发生后，平台需要知道哪些训练 run、checkpoint、评估报告和发布模型受到影响。

数据质量可以拆成多个维度：schema 合法性、重复率、空值率、语言或领域分布、PII 风险、毒性、许可证、长度分布和标签一致性。一个总质量分不能替代这些切片，因为低重复率不说明许可正确，语言覆盖高也不说明标签无错。

### 实验追踪的最小闭环

每个 run 至少记录：

~~~text
输入：代码、数据、配置、环境、seed、资源和启动命令
过程：loss、learning rate、gradient、吞吐、显存、通信、data wait
事件：resume、checkpoint、retry、node lost、数据异常和配置变更
输出：checkpoint、eval report、日志、profile、模型 registry 版本
~~~

MLflow Tracking 等工具提供参数、指标和 artifact 的记录能力，但“是否可复现”仍取决于是否把数据、代码、环境和随机状态完整绑定。实验追踪不是一个只存曲线的数据库。

### 评估与训练平台的连接

训练完成后应自动触发与模型类型相符的离线评估，并把结果绑定到 model artifact。评估不仅保存总分，还应保留数据版本、提示模板、解码参数、切片、失败样本和安全检查。发布前后模型、tokenizer、adapter、量化包和评估报告的版本必须能互相跳转。

## 10.16 可观测性：让训练系统能回答“慢在哪里、错在哪里”

### metrics、logs、traces 和 events 的分工

Metrics 适合聚合趋势和告警，logs 适合保存带上下文的单次事件，traces 适合观察一次请求或一次训练流程的阶段时间线，events 适合描述状态变更、发布和故障。四者不是互相替代的日志格式。

训练 trace 可以包含：submit、schedule、start、data load、forward、backward、collective、optimizer、checkpoint、eval、retry 和 finish。推理服务则需要 queue、prefill、decode、stream、cache 和 fallback。RAG/Agent 还需要 retrieval、prompt assembly、tool call 和执行步骤，但这些 trace 必须经过字段级脱敏。

### 相关 ID 与高基数

训练 run id、job id、rank、node、trace id、checkpoint version 和 dataset version 应能关联；但 request id、user id、document id 等高基数字段不应直接成为 metrics label，否则时序数量会失控。高基数信息应放到 logs 或 traces，并用采样和访问权限控制成本与隐私。

### 训练指标的最小集合

至少应观察：

~~~text
训练：loss、eval loss、learning rate、gradient norm、有效 token、step time
资源：GPU 利用率、显存峰值、MFU/HFU、CPU、网络、存储
分布式：collective time、rank skew、heartbeat、NCCL error、restarts
数据：读取吞吐、data wait ratio、worker queue、cache hit、坏 shard
生命周期：提交、排队、启动、checkpoint、恢复、失败、取消和完成
~~~

没有这些指标，值班人员看到“训练变慢”时只能猜测是 GPU、网络、数据还是 checkpoint。

## 10.17 SLO、值班与事故响应

### SLI、SLO 和 SLA 的区别

SLI 是实际观测指标，例如成功提交率、排队时间、checkpoint 成功率或推理 TTFT；SLO 是内部目标，例如一个窗口内 99% 的平台错误请求成功；SLA 是对外承诺，可能包含责任边界和补偿。三者混在一起会让工程团队无法决定什么需要告警和止损。

训练平台的 SLO 不应只写“服务可用”。可以分别定义提交、调度、启动、训练过程、checkpoint 保存、恢复和产物注册的指标，并区分用户配置错误与平台错误。推理平台则需要同时看 availability、TTFT、TPOT、p99 和质量/安全约束。

### 错误预算与 burn rate

若 SLO 目标为 `S_slo`，错误预算比例为：

~~~math
B=1-S_{\mathrm{slo}}.
~~~

在窗口 `w` 内，坏事件比例为 `R_bad,w`，则 burn rate 为：

~~~math
\beta_w=\frac{R_{\mathrm{bad},w}}{B}.
~~~

短窗口可以快速发现突发事故，长窗口可以发现慢性退化。告警必须指向 owner、影响范围、runbook 和可执行动作；只有一条曲线超过阈值而没有处理路径，不能形成可靠性闭环。

~~~python
import math


def error_budget(slo):
    if (not isinstance(slo, (int, float)) or not math.isfinite(slo)
            or not 0 < slo <= 1):
        raise ValueError("slo must be in (0, 1]")
    return 1.0 - slo


def burn_rate(bad_ratio, slo):
    if (not isinstance(bad_ratio, (int, float))
            or not math.isfinite(bad_ratio) or not 0 <= bad_ratio <= 1):
        raise ValueError("bad_ratio must be in [0, 1]")
    budget = error_budget(slo)
    if budget == 0:
        return float("inf") if bad_ratio > 0 else 0.0
    return bad_ratio / budget


assert round(error_budget(0.99), 2) == 0.01
assert round(burn_rate(0.02, 0.99), 2) == 2.0
print("burn_rate=", burn_rate(0.02, 0.99))
~~~

### 值班 runbook 应能执行

训练 hang 的 runbook 不应只写“查看日志”。它应给出影响判断、最近变更、所有 rank 状态、collective、数据和 checkpoint 证据，明确哪些动作可以限流、暂停、重试、回滚或隔离，并说明权限和升级路径。事故时间线要记录检测、确认、缓解、恢复和根因，而不是只保留最后一行报错。

复盘行动项需要 owner、截止日期、关闭证据和回归验证。把根因写成“某人操作失误”通常没有足够工程价值，应该追问为什么系统允许错误配置、为什么监控没有及时发现、为什么回滚或恢复没有演练。

## 10.18 成本治理与资源利用率

### 从账单到单位有效产出

GPU 任务的粗略成本可以写成：

~~~math
K_{\mathrm{gpu}}
=G\times T\times P_{\mathrm{gpu}}\times\eta_{\mathrm{bill}},
~~~

其中 `G` 是 GPU 数，`T` 是计费时间，`P_gpu` 是单位价格，`eta_bill` 表示计费规则调整。训练成本还应加入失败重试、存储、网络、checkpoint 和值班成本；推理可以按请求、输入/输出 token 或成功任务归因。

只看 GPU utilization 会把失败训练和无效实验算成收益。可以用一个教学性的有效利用率近似：

~~~math
U_{\mathrm{effective}}
=\frac{\sum_i h_i v_i q_i}{\sum_i h_i},
~~~

其中 `h_i` 是时间窗口内 GPU-hours，`v_i` 是硬件有效工作比例，`q_i` 是有效产出、SLO 成功或可发布结果比例。`q_i` 的定义必须根据业务确定，不能用任意分数替代。

### 碎片与 headroom

如果多个资源域可用 GPU 数为 `f_n`，任务需要 `g` 张卡，简单碎片比例可近似为：

~~~math
R_{\mathrm{frag}}(g)
=1-\frac{\sum_n\lfloor f_n/g\rfloor g}{\sum_n f_n}.
~~~

异构 GPU、拓扑、GPU-NIC 亲和性和 gang scheduling 会让真实碎片更复杂。提高利用率也不能把所有余量用光，因为故障恢复、流量突发、高优先级任务和扩缩容都需要 headroom。

### 成本优化的边界

降低精度、增加 batch、启用抢占、删除旧 checkpoint、缩小 warm pool、跨区域迁移数据都可能降低账单，但可能损害质量、恢复能力、隐私或 SLO。每条优化建议都应写清预计节省、受影响指标、风险、owner、灰度方式和回滚条件。

## 10.19 安全、权限与供应链

### 训练平台保护的资产

训练数据、模型权重、checkpoint、tokenizer、adapter、prompt、日志、trace、embedding、工具参数和评估样本都可能是敏感资产。安全边界不能只放在 API 网关，还要覆盖任务身份、数据读取、容器运行、artifact 下载、网络出站和审计。

### 身份和最小权限

用户身份、项目身份、TrainingJob service account 和 workload identity 应绑定。每个任务只获得当前数据用途、资源池、artifact 和 secret 所需的权限。RBAC 提供角色结构，ABAC 可以结合租户、项目、数据等级、环境和用途做属性约束；两者都不能用通配管理员角色代替。

secret 应由专门的 secret manager 管理，使用短期凭证、轮换、吊销和访问审计。不要把密钥写进镜像层、命令行、代码、checkpoint、日志或 prompt。

### 数据等级和产物传播

数据 manifest 应记录授权、敏感等级、地域、用途、保留周期和删除请求。训练产生的 checkpoint、评估样本、日志和模型通常至少继承输入数据的最高敏感等级，除非有明确的脱敏和重新分类证据。模型输出可能记忆训练数据，不能因为它是“模型生成”就默认公开。

### 运行时和供应链

镜像、依赖、CUDA/NCCL、数据转换程序、模型权重和 tokenizer 都应保留 provenance、digest、扫描和许可证信息。运行时限制 privileged、hostPath、root 和未受控外联；对出站网络使用 allowlist 和审计。模型 artifact 采用安全的序列化格式、校验和签名，下载和部署都要验证来源与权限。

RAG 系统还要在检索和上下文组装前做 ACL 过滤，不能先把无权限文档检索出来，再让模型“不要泄露”。Agent 工具调用则要做参数校验、权限判断、高风险确认、幂等、超时、限流和审计。

## 10.20 审计、变更与恢复

### 审计事件应能说明发生了什么

关键审计事件至少包含：

~~~text
timestamp、actor、tenant、action、resource、version
decision、status、reason、request_id、trace_id
代码/配置 diff、artifact digest、来源和审批记录
~~~

数据访问、任务提交、镜像使用、权限变更、secret 读取、checkpoint 删除、模型下载、发布、回滚和高风险工具调用都应覆盖。审计日志需要可靠写入、防篡改、加密、访问控制和按敏感等级设置保留期限。

### 变更对象比代码更多

AI 训练与推理的高风险变更包括模型权重、tokenizer、prompt、路由、runtime、数据集、RAG 知识库、工具 schema、权限策略、GPU 集群配置和调度规则。变更记录要关联 owner、原因、diff、审批、canary、观测、回滚和影响的 run/artifact。

灰度发布需要可观测的停止条件和回滚权限。错误预算耗尽时可以冻结高风险变更，但紧急安全修复应有明确例外流程。事故、复盘、行动项和回归测试之间要能互相跳转，才能把一次故障变成系统改进。

### 故障分类与恢复策略

不是所有失败都应重试：

~~~text
用户配置错误：快速失败，返回可修复字段
数据或权限错误：隔离版本，保留证据，不盲目重试
可恢复节点故障：从最近 checkpoint 恢复并限制 retry budget
通信暂时异常：退避重试，同时防止重复提交
模型数值异常：保存触发样本，必要时回滚，不继续污染状态
平台控制面故障：保证状态幂等和 worker 不重复创建
~~~

恢复策略要考虑 checkpoint 新鲜度、保存完成标记、optimizer/scheduler/RNG/data cursor、并行度和配置一致性。只加载模型参数会让 learning rate、momentum、随机数和样本位置断裂，恢复后即使 loss 能下降，也不能说实验连续。

## 10.21 一个可落地的训练平台架构

### 从需求到组件

一个通用平台可以由下列职责组成：

~~~text
客户端/Portal/CLI/SDK
  -> API 与 TrainingJob 校验
  -> 身份、数据用途、镜像和资源策略
  -> 队列、配额、公平调度、拓扑与 gang placement
  -> launcher、rendezvous、GPU binding、worker 管理
  -> 数据 manifest、缓存、训练 runtime、collective
  -> checkpoint、实验追踪、评估、artifact registry
  -> metrics/logs/traces/events、成本、审计和事故系统
~~~

这个图不是工具清单。每个箭头都应有输入输出契约。例如 scheduler handoff 需要节点、GPU UUID、并行组和网络信息；launcher handoff 需要 rank 和 rendezvous；训练 runtime 输出 step、checkpoint 和 heartbeat；registry 需要 digest、评估报告和发布状态。

### 关键取舍

* 固定 world size 的恢复较简单，弹性训练提高资源适应性但要求重新定义 batch 和 optimizer 状态。
* gang scheduling 减少半启动任务，却可能增加排队等待。
* 更频繁 checkpoint 降低丢失进度，却提高 I/O 和存储成本。
* 更强的日志和 trace 便于排障，却增加隐私、存储和访问控制负担。
* 更激进的 GPU 混部提升利用率，却可能损害在线 SLO 和训练稳定性。
* 自动重试减少人工值班，却可能放大数据错误、配置错误和预算浪费。

系统设计不应把某一个编排工具当作答案。Kubernetes、Slurm、Kueue、训练 operator、`torchrun`、MLflow 和 OpenTelemetry 都可以成为实现部件，真正需要固定的是状态、契约、证据和失败边界。

### 一次训练任务的完整时间线

~~~text
1. 用户提交 TrainingJob，平台生成幂等 job id。
2. 校验 schema、身份、数据用途、镜像 digest、预算和资源。
3. 任务进入队列，调度器计算 quota、fair share、topology 与 gang fit。
4. worker 一起启动，launcher 建立 rank、world size、GPU/NIC 绑定。
5. 训练读取不可变 manifest，记录有效 token、loss、step time 和 trace。
6. checkpoint 以 manifest/checksum/committed 方式保存，并绑定 run id。
7. 节点故障时分类原因，按 retry budget 从完整 checkpoint 恢复。
8. 训练完成后执行评估，注册模型、tokenizer、配置和报告。
9. 成本、资源利用率、审计事件和变更记录归档，释放资源。
~~~

这条时间线同时回答了“能不能跑”“跑得是否高效”“结果是否可信”“失败是否能恢复”“谁能追溯和负责”五个问题。

## 10.22 综合实验：把训练系统当成可测对象

### 实验一：并行维度与有效 batch

固定 `world_size=16`，比较 `(DP, TP, PP)=(16,1,1)`、`(4,2,2)` 和 `(2,4,2)`。先计算全局 batch，再记录每个并行组的通信量、单卡状态、拓扑位置和 loss 曲线。这个实验能说明“总 GPU 数相同”不等于“训练行为和通信成本相同”。

### 实验二：通信和流水线的数量级

改变梯度 payload、rank 数、micro-batch 数，使用 ring 公式和 bubble 公式得到理论曲线，再在目标硬件上用 NCCL benchmark、训练 trace 和 step time 验证。若理论趋势与实测相反，应检查拓扑、消息大小、overlap、网络拥塞和 stage imbalance，而不是直接否定公式。

### 实验三：checkpoint 恢复连续性

在固定 seed 和数据 manifest 下训练若干 step，保存 checkpoint；随后模拟节点故障，恢复 optimizer、scheduler、RNG、dataloader cursor 和并行配置，比较恢复前后的 loss、learning rate、有效 token 和下一个 batch。再做一个“只加载模型权重”的对照，观察两者是否产生动力学差异。

### 实验四：数据、通信和 checkpoint 故障

分别注入慢 shard、collective 延迟、坏 checkpoint 和一个 rank 提前退出。验证系统是否能记录最早异常、所有 rank 状态、阶段耗时、影响 GPU-hours、恢复动作和最终结果。实验的目标不是让所有故障都自动修复，而是让系统不会把不同根因混在一起。

### 实验五：多租户公平和成本

用不同 GPU/CPU/内存需求的任务模拟队列，计算 dominant share、排队时间、抢占次数、checkpoint 丢失进度和有效产出。比较固定配额、允许借用和带优先级的策略，观察利用率提升是否以某个租户的长尾排队和恢复成本为代价。

## 10.23 资料边界与延伸阅读

以下资料分别对应本章的机制、框架和治理内容：

* ZeRO 原始论文：[ZeRO: Memory Optimizations Toward Training Trillion Parameter Models](https://arxiv.org/abs/1910.02054)。它解释了 optimizer state、gradient 和 parameter 分片的基本动机。
* ZeRO-Infinity：[Breaking the GPU Memory Wall](https://arxiv.org/abs/2104.07857)。它讨论 CPU/NVMe 等层级的 offload，不能直接等同于任意硬件上的生产收益。
* Megatron-LM：[Efficient Large-Scale Language Model Training on GPU Clusters](https://arxiv.org/abs/2104.04473)。它是张量并行、流水并行和数据并行组合的重要原始资料。
* GPipe：[Easy Scaling with Micro-Batch Pipeline Parallelism](https://arxiv.org/abs/1811.06965)。它说明 micro-batch 流水并行的基本方法。
* [PyTorch Distributed](https://pytorch.org/docs/stable/distributed.html) 与 [DistributedDataParallel](https://pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html) 官方文档。它们说明 process group、collective 和 DDP 的框架语义。
* [PyTorch FSDP](https://pytorch.org/docs/stable/fsdp.html) 官方文档。它说明参数分片、通信和状态字典相关接口；具体峰值仍需实测。
* [PyTorch activation checkpoint](https://pytorch.org/docs/stable/checkpoint.html)、[AMP](https://pytorch.org/docs/stable/amp.html) 和 [distributed checkpoint](https://pytorch.org/docs/stable/distributed.checkpoint.html) 文档。它们分别对应重计算、混合精度和分布式保存/恢复。
* [NVIDIA NCCL 文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html)。它介绍多 GPU/多节点 collective 通信，但实际性能取决于目标网络和拓扑。
* [Kubernetes device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)、[Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/) 与 [Kueue](https://kueue.sigs.k8s.io/docs/overview/)。它们分别对应 GPU 资源暴露、批任务控制和队列/配额调度边界。
* [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/) 用于实验参数、指标和 artifact 记录；它不能替代数据、环境和恢复状态的完整血缘。
* [OpenTelemetry observability primer](https://opentelemetry.io/docs/concepts/observability-primer/)。它说明 metrics、logs 和 traces 的基本分工。
* [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) 提供治理和风险管理背景；本章的安全控制还需要结合组织的合规要求和威胁模型。
* [Data Cards](https://arxiv.org/abs/2203.15556) 讨论数据集文档化，适合延伸阅读数据来源、用途和限制的记录方式。

论文结论、框架 API 和组织治理规范的证据等级不同。论文的通信量公式可以帮助建立预期，官方文档可以帮助理解 API，只有目标硬件、目标数据和目标流量下的重复实验，才能支持某个生产配置的性能结论。

## 10.24 小结：把多卡程序提升为系统

分布式训练首先是一个数学和资源问题：参数、梯度、优化器状态、激活和通信 buffer 共同决定显存；global batch 由 micro-batch、梯度累积和数据并行度决定。随后它变成并行策略问题：数据并行复制模型，张量并行切分层内矩阵，流水并行切分层和 micro-batch，ZeRO/FSDP 切分训练状态。

它继续变成数据通路和网络问题：collective 的类型、消息量、拓扑、RDMA、NCCL、存储和数据预取决定 step time。再往外是平台问题：TrainingJob 契约、状态机、launcher、checkpoint、实验追踪和 artifact lineage 决定结果能否复现和恢复。最后是生产治理问题：SLO、值班、成本、公平调度、身份、审计和变更控制决定系统能否长期运行。

真正成熟的训练平台，不是让某一次训练“跑通”，而是能解释每次更新使用了什么数据和配置，资源花在哪里，慢在哪一层，失败时保留了哪些证据，恢复后是否保持了训练动力学，以及最终模型能否被安全、可审计地使用。
