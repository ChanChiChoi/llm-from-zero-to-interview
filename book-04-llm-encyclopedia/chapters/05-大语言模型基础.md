# E. 大语言模型基础：从概率目标到可验证系统

## 阅读边界

大语言模型可以从一个很简单的数学目标开始理解：给定前面的 token，估计下一个 token 的概率。但一个能完成真实任务的 LLM 系统，远不止这个概率目标。它还需要正确的 tokenizer 和 label shift，需要经过预训练与后训练，需要在上下文中识别任务，需要通过解码策略生成结果，并且要面对事实性、成本、权限、延迟、反馈和回滚问题。

本章不把这些概念拆成词典式的“一句话定义”，而是沿着一条从模型到系统的链路展开：

~~~text
token 序列
 -> next-token probability
 -> base model
 -> instruction / preference post-training
 -> prompt / context / ICL
 -> generation
 -> evidence / tool / verification
 -> product workflow
 -> evaluation / monitoring / feedback
~~~

全章分为十四个独立主题。每个主题都说明初学者直觉、专家变量、公式、最小实验、失败边界和资料来源。本章只讨论基础概念；完整的后训练、推理部署、RAG、Agent 和评估方法分别在后续书册展开。章节中的数字是教学构造，不能直接当作任何具体模型的能力或服务指标。

## 5.1 语言模型：给 token 序列分配概率

### 链式法则

设一段 token 序列为 x_1,x_2,\ldots,x_T，语言模型要估计整段序列的概率。链式法则把它分解为：

~~~math
P(x_{1:T})
=\prod_{t=1}^{T}P(x_t\mid x_{1:t-1}).
~~~

x_{1:t-1} 表示位置 t 之前的 token。模型并不需要一次性直接计算整个字符串的概率，而是逐位置产生一个条件分布。

对初学者来说，可以把它理解成一个不断完成句子的过程：给定“今天的天气”，模型为下一个 token 分配概率；得到或选出“很”，再根据“今天的天气很”预测下一步。这个过程重复 T 次，就构成一条序列的概率。

### 从概率到 logits

Transformer 在每个位置产生一个 hidden state h_t，再通过 LM head 得到词表上的 logits：

~~~math
z_t=W_{\mathrm{lm}}h_t+b.
~~~

这里 h_t 表示用于预测目标 x_t 的前缀表示，采用列向量约定，W_lm 为 `[V,d]`。常见实现中位置 t 的输入 token 对应的 hidden 实际预测 x_{t+1}，需按下一节的 shift 对齐。z_t 的维度是 V，V 是词表大小。softmax 把 logits 转成概率：

~~~math
p_\theta(x_t=i\mid x_{1:t-1})
=\frac{\exp(z_{t,i})}
{\sum_{j=1}^{V}\exp(z_{t,j})}.
~~~

实际框架通常直接计算稳定的 log-softmax 或 fused cross entropy，不会先显式构造一个完整概率矩阵再手动取对数。

### 语言模型与搜索的边界

语言模型根据参数和输入上下文生成候选文本；搜索系统从外部文档索引中寻找已有内容。二者可以组合成 RAG：检索系统提供候选证据，语言模型把证据组织成答案。只靠模型参数回答最新价格、内部制度或精确引用，风险会高于有证据的检索和工具查询。

### 语言模型不等于事实数据库

next-token 目标奖励的是训练分布中合理的延续，并没有直接要求输出真实、可验证或最新。一个事实错误的句子可能具有很高的语言概率。要把概率生成器用于高风险任务，必须增加证据、工具、拒答、校验和人工流程，而不是把概率当作真值。

## 5.2 Next-token prediction、Teacher Forcing 与 Label Shift

### 自监督目标

自然文本本身就提供了训练标签。给定 token 序列 x_1,\ldots,x_T，位置 t 的输入上下文是 x_{1:t-1}，目标是 x_t。token 不需要人工逐个标注，因此可以在大规模未标注语料上训练。

常见的平均负对数似然为：

~~~math
L_{\mathrm{NLL}}
=-\frac{1}{N}
\sum_{t\in\mathcal{I}}
\log p_\theta(x_t\mid x_{1:t-1}),
~~~

I 是参与损失的有效位置集合，N=|I|，要求 N>0。采用内部 causal shift 时应在切片、padding 和角色 mask 之后统计目标数量，不能直接数原始 labels。

### Teacher forcing

训练时，模型在每个位置使用真实历史 token，而不是自己前面生成的 token。这叫 teacher forcing。它有两个主要好处：

1. 所有位置可以在一次 forward 中并行计算。
2. 每个位置都能得到稳定且明确的训练目标。

但推理时模型必须使用自己的历史输出。若早期 token 错了，后续条件也会随之变化，这就是训练分布和生成分布之间的暴露偏差。它解释了为什么训练 loss 很低的模型，长文本生成仍可能逐渐漂移。

### Label shift

输入和标签通常相差一个位置：

~~~text
input_ids: [x1, x2, x3, x4]
labels:    [x2, x3, x4, x5]
~~~

在实际实现中，模型可能接收同一个序列，再在内部把 logits 与 labels 分别切成 logits[..., :-1, :] 和 labels[..., 1:]；也可能由训练器在外部完成 shift。必须查清楚责任边界，避免重复 shift 或完全漏掉 shift。

### Assistant-only mask

对话 SFT 常把 system、user 和 padding 作为条件，只让 assistant completion 参与损失。设 A 是 assistant 目标位置：

~~~math
L_{\mathrm{assistant}}
=-\frac{1}{|A|}
\sum_{t\in A}
\log p_\theta(y_t\mid x,y_{1:t-1}).
~~~

这不是所有训练方案的唯一选择。有些数据会对完整对话计算 loss，有些会让角色边界和 EOS 参与训练。关键是目标要被显式定义，而不是看到一个 labels 张量就假定它正确。

### Prompt loss leak 与 PAD loss leak

prompt loss leak 是提示部分错误参与了本应 response-only 的损失；PAD loss leak 是 padding 位置错误参与损失。两者都可能让 loss 下降，但模型学到错误的行为。审计时按 role、padding、EOS 和 assistant span 统计有效 labels，而不是只看总 loss。

### 用标准库计算一个 masked NLL

下面的代码不执行神经网络，只验证忽略位置、对数概率和平均分母的关系。

~~~python
import math


def masked_nll(log_probs, targets, ignore_index=-100):
    if isinstance(ignore_index, bool) or not isinstance(ignore_index, int):
        raise ValueError("ignore_index must be an integer")
    if (not isinstance(log_probs, (list, tuple))
            or not isinstance(targets, (list, tuple))
            or not log_probs):
        raise ValueError("log_probs and targets must be non-empty lists")
    if len(log_probs) != len(targets):
        raise ValueError("length mismatch")
    values = []
    vocab_size = None
    for row, target in zip(log_probs, targets):
        if not isinstance(row, (list, tuple)) or not row:
            raise ValueError("each log-probability row must be non-empty")
        if any(isinstance(value, bool) or not isinstance(value, (int, float))
               or not math.isfinite(value) for value in row):
            raise ValueError("log probabilities must be finite numbers")
        if vocab_size is None:
            vocab_size = len(row)
        if len(row) != vocab_size:
            raise ValueError("vocabulary size must be consistent")
        if any(value > 0 for value in row) or not math.isclose(
                sum(math.exp(value) for value in row), 1.0,
                rel_tol=1e-9, abs_tol=1e-9):
            raise ValueError("rows must be normalized log probabilities")
        if isinstance(target, bool) or not isinstance(target, int):
            raise ValueError("targets must be integers")
        if target == ignore_index:
            continue
        if (isinstance(target, bool) or not isinstance(target, int)
                or not 0 <= target < len(row)):
            raise ValueError("target is out of range")
        values.append(-row[target])
    if not values:
        raise ValueError("no valid targets")
    return sum(values) / len(values)


log_probs = [
    [math.log(0.8), math.log(0.2)],
    [math.log(0.4), math.log(0.6)],
    [math.log(0.5), math.log(0.5)],
]
print(round(masked_nll(log_probs, [0, -100, 1]), 6))
~~~

输出约为 0.458145。第二个位置被忽略，分母是两个有效目标而不是三个位置。教学函数要求所有行均为有限、已归一化的 log probabilities，不接收 logits 或表示零概率的负无穷；也不自动执行 shift。真实 CrossEntropyLoss 还要处理 logits、类别维度、label shift 和 dtype。

## 5.3 Logits、Softmax、Cross-Entropy 与 Perplexity

### logits 是相对分数

logits 不是概率。softmax 只依赖 logits 的相对差异：

~~~math
\mathrm{softmax}(z+c\mathbf{1})
=\mathrm{softmax}(z).
~~~

因此把所有 logits 加上同一常数不会改变概率。解码时温度 T 会改变差异的尺度：

~~~math
p_i(T)
=\mathrm{softmax}\left(\frac{z_i}{T}\right).
~~~

公式要求 T>0；0<T<1 会让分布更尖，T>1 会让分布更平。部分接口把 temperature=0 解释为 greedy 开关，不是代入公式除以零。温度不能修复事实错误，只是改变候选选择的随机性和集中程度。

### Cross-Entropy

对真实类别 y，单个位置的交叉熵为：

~~~math
\ell=-\log p_y.
~~~

如果模型给真实 token 0.9 的概率，loss 较小；如果只给 0.01，loss 较大。训练会提高真实 token 的相对 logit，但不保证某个语义层面的答案一定真实。

### Perplexity

平均 token loss 为 L 时：

~~~math
\mathrm{PPL}=\exp(L).
~~~

PPL 是参考目标 token 逆概率的几何平均，不等于模型预测分布自身的熵。若分布为 `[0.99,0.01]`，却以第二类为目标，PPL 为100；均匀分布的 PPL 为2，尽管均匀分布的熵更高。它适合观察同一评估口径下的预训练收敛和分布适配，但不能单独证明指令遵循、推理、事实性或用户体验。

不同 tokenizer 会改变 token 单位。同一段字符被切成更多 token，loss 和 PPL 的统计单位就不同。因此跨 tokenizer 或跨语言比较时，要说明 tokenizer、数据、有效 token 数和是否换算到字符/字节级。

### 数值稳定性

直接计算 exp(z_i) 可能溢出。减去最大 logit m 不改变 softmax：

~~~math
\mathrm{softmax}(z_i)
=\frac{\exp(z_i-m)}
{\sum_j\exp(z_j-m)},
\qquad
m=\max_j z_j.
~~~

框架的 logsumexp、log_softmax 和 fused cross entropy 通常会处理这类稳定性。手写 loss 时，先确认 logit、mask、有效 label 数和 dtype，再解释 NaN。

### 训练指标的层次

可以把指标分成三层：

~~~text
token 层：loss、PPL、valid token count
任务层：准确率、代码测试通过、引用支持、格式正确
系统层：任务成功率、延迟、成本、安全、采纳和恢复
~~~

上一层变好不保证下一层自动变好。PPL 下降可能只表示更会拟合文本分布，不代表更能执行用户任务。

## 5.4 Base、Instruct、Chat 与 Assistant：后训练改变了什么

### Base model

Base model 主要通过大规模预训练获得语言和世界模式。它更像一个通用续写器，不一定把“请解释……”当作严格指令。它可能继续生成网页、论文、对话或其他与训练分布相似的文本。

Base model 的价值在于：

- 作为继续预训练和领域适配的底座。
- 提供通用语言、代码和知识表示。
- 作为研究中观察预训练能力的对象。
- 为后续 SFT、偏好优化和安全训练提供起点。

### Instruct model

Instruction tuning 用任务说明、输入和目标回答训练模型，让它学会把自然语言要求转换为生成行为。样本质量、任务覆盖、assistant-only mask、格式多样性和负例都会影响结果。

指令微调通常改善零样本任务和格式遵循，但也可能带来：

~~~text
原有知识或代码能力退化
过度拒答
风格变窄
对特定模板过拟合
长度偏置
对错误指令过度顺从
~~~

因此 SFT 不能只用训练 loss 判断，要与 base model 做能力回归和行为分桶对照。

### Chat model

Chat model 通常在多轮消息、角色边界、对话模板和偏好数据上继续训练。它的差异不只来自权重，还来自 tokenizer、special token、chat template、停止条件和后处理。

如果用错误模板，即使模型权重正确，也可能出现角色混乱、无限生成、工具调用解析失败或 system 约束失效。模板版本是模型输入协议的一部分。

### Assistant model 与系统边界

一个 assistant model 追求有帮助、诚实和安全，但这些目标可能冲突。例如，用户希望立即得到答案，事实证据却不足；用户要求执行高风险动作，工具权限却不允许。模型可以表达不确定性或拒绝，但可靠系统还需要后端权限、工具校验、引用、审计和人工升级。

### 后训练不是知识更新的同义词

SFT 或偏好优化主要塑造行为、格式和偏好，不一定可靠地写入最新事实。需要最新数据时，RAG、工具查询或继续预训练可能更合适。把“模型更听话”误认为“模型知识更准确”，会导致错误的评估设计。

## 5.5 Prompt、System Prompt 与 Instruction Following

### Prompt 是运行时条件

Prompt 可以包含：

~~~text
system 规则
用户任务
对话历史
few-shot 示例
检索证据
工具 schema
输出格式
安全和权限上下文
~~~

它是条件输入，不是硬编码规则。Prompt 能调用模型已经学到的能力，不能凭空创建不存在的工具、知识或稳定推理能力。

### System prompt 的作用与边界

System prompt 通常用于角色、规则、风格、工具使用和冲突处理。它提高一致性，但不是权限系统，也不是不可绕过的安全边界。用户输入、检索文档和工具结果都可能包含与系统规则冲突的文本，后端必须区分“数据”与“指令”。

### Instruction following 的组成

指令遵循至少包含：

1. 识别任务类型。
2. 提取约束和输出 schema。
3. 处理多个约束的优先级。
4. 生成满足内容要求的结果。
5. 在不确定或越权时拒答、澄清或升级。
6. 保持角色、格式和终止边界。

因此，instruction following 不是单一问答准确率。评估要覆盖格式、否定约束、多任务、长对话、冲突指令、越权工具和不可满足要求。

### 结构化输出

若下游需要 JSON，要求模型“请输出 JSON”只是弱约束。更可靠的系统还会使用 schema、受限解码、解析重试、字段校验和错误恢复。内容正确但 JSON 不能解析，对业务系统仍然是失败。

## 5.6 In-Context Learning：参数不变的临时适配

### Zero-shot 与 few-shot

Zero-shot 只提供任务说明，不提供示例；few-shot 在 prompt 中加入少量输入输出对。示例可以告诉模型任务边界、标签空间、字段顺序和特殊规则。

例如：

~~~text
文本：这家餐厅服务很棒
标签：正面

文本：等待时间太长
标签：负面

文本：环境很安静
标签：
~~~

模型可能根据前两个示例完成第三个样本。这个过程不更新参数，调用结束后也不会永久改变模型。

### ICL 与微调的差异

ICL 的适配发生在当前上下文中，成本主要是 prompt token 和推理计算；微调改变参数，适配可以跨请求保留，但需要数据、训练、回归和部署。ICL 适合快速试验和任务规则变化，微调适合稳定行为和格式大规模复用，但二者可以组合。

### 示例选择

好的示例不一定越多越好。应同时考虑：

~~~text
与当前输入的语义相关性
标签空间覆盖
边界和反例覆盖
格式一致性
证据是否正确
示例之间是否冲突
token 成本
位置分布
~~~

相似度检索若选到错误标签的近邻，ICL 可能被带偏。示例选择器需要在验证集上测，而不是凭主观感觉。

### ICL conflict rate

若检索到的示例中有一部分与正确标签冲突，可以定义冲突比例：

~~~math
r_{\mathrm{conflict}}
=\frac{N_{\mathrm{conflict}}}
{N_{\mathrm{relevant}}}.
~~~

冲突率高时，模型的失败不一定说明模型不会任务，也可能说明 prompt 内部证据矛盾。需要把无冲突、低冲突和高冲突样本分开评估。

这里是本章的审计口径，不是通用benchmark指标。N_relevant要求大于零，且“相关”和“冲突”要有独立标注规则；没有相关示例时记录不适用，不能把零分母自动算成零冲突。

### Demonstration format consistency

示例的字段、分隔符、输入输出顺序和标签形式应该稳定。把一个示例写成自然语言解释，另一个写成 JSON，再要求模型输出表格，会增加 schema 歧义。对格式敏感任务，示例必须与最终输出协议相同。

### ICL 的评估

一个可复用的 ICL 评估集应包含：

~~~text
zero-shot 与 few-shot 对照
不同示例顺序
不同示例数量
标签空间完整与不完整
正确与冲突示例
首部、中部、尾部位置
示例含噪和边界样本
输出格式与语义正确性
~~~

只有在这些切片上都稳定，才能把一次 prompt demo 看作可迁移证据。

## 5.7 Generation：从 logits 到文本

### 自回归生成闭环

生成过程是：

1. 编码 prompt。
2. forward 得到最后位置 logits。
3. 施加温度、过滤和约束。
4. 选择或采样一个 token。
5. 更新 KV cache 和上下文状态。
6. 检查 EOS、stop、长度和系统策略。
7. 重复直到终止。

训练时可以并行处理序列位置，decode 阶段却通常沿生成长度串行。KV cache 减少历史重复计算，但增加运行时显存和访存压力。

### Greedy decoding

Greedy 每次选择最大 logit token：

~~~math
x_{t+1}
=\mathrm{argmax}_{i}z_{t,i}.
~~~

给定相同logits和固定的并列最大值处理，greedy选择确定；但硬件、kernel、batch和数值误差可能改变logits，不能只靠greedy保证跨环境逐字复现。它可能陷入重复或局部最优，也不保证整条序列概率最大。

### Temperature

温度缩放：

~~~math
p_i
=\mathrm{softmax}(z_i/T).
~~~

低温让高分 token 更占优势，高温增加多样性。温度并不改变模型知识，也不保证高温带来创新或低温带来事实性。

### Top-k 与 Top-p

Top-k 只保留得分最高的 k 个 token；top-p 按概率从高到低累积，保留累计概率达到 p 的最小集合。二者都改变采样支持集。对结构化输出和高风险事实回答，通常需要更强的 schema、证据和停止控制，而不是只调采样参数。

### 停止条件

EOS、stop string、max_new_tokens、工具调用结束和策略中断都可能终止生成。EOS 是模型学到的语义终止，max_new_tokens 是硬上限，两者不能互相代替。流式输出还要处理部分 UTF-8、JSON 和 markdown 边界。

### 一个标准库采样例子

~~~python
import math
import random


def temperature_probs(logits, temperature):
    if not isinstance(logits, (list, tuple)) or not logits:
        raise ValueError("logits must be non-empty")
    if (isinstance(temperature, bool)
            or not isinstance(temperature, (int, float))
            or not math.isfinite(temperature) or temperature <= 0):
        raise ValueError("temperature must be a finite positive number")
    if any(isinstance(value, bool) or not isinstance(value, (int, float))
           or not math.isfinite(value) for value in logits):
        raise ValueError("logits must be finite numbers")
    maximum = max(logits)
    weights = []
    for value in logits:
        difference = value - maximum
        if math.isfinite(difference):
            scaled = difference / temperature
        else:
            scaled = value / temperature - maximum / temperature
        weights.append(math.exp(scaled))
    total = sum(weights)
    if not math.isfinite(total) or total <= 0:
        raise ValueError("softmax normalizer must be finite and positive")
    return [weight / total for weight in weights]


def sample_index(probabilities, seed=7):
    if not isinstance(probabilities, (list, tuple)) or not probabilities:
        raise ValueError("probabilities must be non-empty")
    if any(isinstance(value, bool) or not isinstance(value, (int, float))
           or not math.isfinite(value) or value < 0
           for value in probabilities):
        raise ValueError("probabilities must be finite and non-negative")
    if not math.isclose(sum(probabilities), 1.0, rel_tol=1e-9,
                        abs_tol=1e-9):
        raise ValueError("probabilities must sum to one")
    threshold = random.Random(seed).random()
    cumulative = 0.0
    for index, probability in enumerate(probabilities):
        cumulative += probability
        if probability > 0 and threshold < cumulative:
            return index
    return max(index for index, value in enumerate(probabilities) if value > 0)


probs = temperature_probs([2.0, 1.0, 0.0], temperature=0.7)
print([round(value, 4) for value in probs])
print(sample_index(probs))
~~~

这里使用标准库的稳定指数计算验证 softmax 和采样接口，并不是生产采样器。每次调用都用 seed 创建局部随机流，不会修改全局状态；若循环中反复使用同一 seed，会反复使用同一个分位点，不能代替持续推进的生成随机流。真实实现还要处理 top-k、top-p、重复惩罚、batch、停止条件和数值精度。

数值分支避免相反符号的超大logits先相减溢出。例如 `[1e308,-1e308]`、温度`1e308`的正确分布约为`[0.880797,0.119203]`；不能把减法得到的负无穷误当成缩放后的真实差值。很小温度下极小概率可能下溢为零，这是本教学float计算的表示边界。

## 5.8 Chain-of-Thought、推理轨迹与可验证计算

### 为什么中间步骤可能有帮助

复杂数学、代码和多跳任务包含多个中间状态。让模型生成中间步骤，相当于给它更多 token 作为测试时计算空间。步骤可以帮助分解任务、暴露变量和调用工具，但“写出长推理”本身不保证正确。

### 结果和过程的区别

最终答案正确不代表中间步骤可靠；中间步骤看起来合理也不代表它是真实的内部因果轨迹。需要把过程当作可检查的外部产物，例如：

~~~text
算术表达式交给计算器
代码交给测试执行器
引用交给文档核验
SQL 交给只读数据库
计划交给状态和权限检查
~~~

### CoT 的成本

额外推理 token 会增加延迟、成本、上下文和泄露风险。推理预算应该和任务难度、成功率提升、单位成功成本一起评估。对于简单任务，强制长推理可能只增加错误表述和不必要开销。

### 可验证推理

更可靠的方案是把自然语言分解与可执行验证结合：

~~~math
\mathrm{success}
=\mathrm{answer\_correct}
\land\mathrm{constraint\_satisfied}
\land\mathrm{evidence\_supported}.
~~~

这不是说所有任务都能完全形式化，而是提醒我们：推理文本和任务正确性要分开评估。

## 5.9 Memorization、Generalization 与数据污染

### 记忆与泛化并存

大模型既可能逐字输出训练片段，也可能学到可迁移模式。[Quantifying Memorization](https://arxiv.org/abs/2202.07646)在其研究模型中观察到，提取出的逐字记忆随模型容量、样本重复次数和提示上下文长度增加而上升，跨模型家族关系更复杂。不能把“常见”或“独特”单独当作普遍记忆判据。语法或任务结构也可能与记忆共存，不能仅凭输出内容抽象就认定它在泛化。

### 区分方法

可以使用：

~~~text
时间切分
去重后的测试集
私有评估集
题目和实体扰动
反事实改写
新组合与新领域
训练数据成员推断
引用和来源核验
~~~

如果换名字、数字或关系后能力大幅下降，可能说明模型依赖表面记忆，也可能来自切分、难度或语义变化；需控制这些混淆因素。未见组合上的稳定表现是更强的泛化证据，但单一扰动或成员推断都不能独立证明具体答案的训练来源。

### 评估污染

评测题、答案、网页原文或变体进入预训练语料，会让 benchmark 分数高估能力。污染检查要同时看模型训练语料、抓取时间、评估集版本、近重复文本和 n-gram/embedding 相似度。单纯在模型回答中搜索一段完整题目，不能证明没有污染。

### 多维能力评估

基础语言 loss、任务准确率、推理、事实性、代码执行和用户体验各自观察不同能力。公开 benchmark 的单一分数不能替代私有、分桶、对抗和时间外评估。

## 5.10 Emergent Ability 与 Scaling

### 能力曲线为何看起来突然

当模型规模、数据或计算增长时，某些任务指标可能出现看似突然的跃升。原因可能包括：

1. 模型学到了更复杂的组合模式。
2. 任务需要跨过一个可观测阈值。
3. 离散准确率把连续 loss 改善显示成突变。
4. prompt、示例和评估方法在不同规模上不公平。
5. 数据覆盖在某个规模后突然充足。

因此“涌现”首先是一个需要解释的观测现象，不是模型获得魔法能力的证明。

[Are Emergent Abilities a Mirage?](https://arxiv.org/abs/2304.15004)用固定输出对照不同指标，展示非线性或不连续评分可以制造看似突变的能力曲线。这支持检查指标和统计功效，不等于证明所有新能力都只是评分假象。评估时应同时报告连续得分、离散成功、样本数和不确定性，并保持prompt与测试集一致。

### Scaling law 的基本直觉

在固定架构和训练设定下，验证 loss 常随模型参数、数据量和训练计算平滑变化。简化地说，可以用幂律近似：

~~~math
L(N,D)
\approx L_\infty
+aN^{-\alpha}
+bD^{-\beta}.
~~~

这是 Chinchilla 使用的一类拟合形式：N 是参数量，D 是训练 token 数，指数和常数依赖模型、数据和训练方案。计算量 C 通常作为约束进入优化；对其采用的 dense Transformer 近似，C≈6ND，不能再把 C 当成与 N、D 独立的第三个变量随意相加。这不是所有架构、序列长度和任务的普遍定律，也不直接预测下游准确率。

例如仅为说明约束，若 N=10^9、D=2×10^10，则近似训练量为1.2×10^20 FLOPs；固定该预算而将 N 翻倍，D 就需减半。loss 是否更优还取决于拟合系数和数据，不能只凭参数变大下结论。这里的6ND不包括完整集群运行成本或所有长序列attention开销。

### Compute-optimal

如果只扩大参数而不增加数据，模型可能 undertrained；如果只增加数据而模型容量不足，可能进入容量瓶颈。Compute-optimal 的核心是让参数、token 和总计算在给定预算下合理配比。实际决策还要加入数据质量、重复率、训练稳定性、推理成本和模型更新周期。

### Tokens per parameter

tokens per parameter 可写为：

~~~math
\rho=\frac{D}{N}.
~~~

它是粗略的训练充分度观察量，不是无条件的目标数字。不同数据质量、架构、目标 loss 和重复率会改变合理比例。比较模型时，应报告 N、D、训练 compute、数据去重、验证 loss 和下游任务，而不是只报参数量。

### Scaling 证据

一个架构是否值得规模化，需要同时看：

~~~text
loss 随 compute 的趋势
下游任务是否稳定改善
训练是否可复现
数据和模型是否充分训练
长上下文与多语言切片
推理显存和延迟
kernel 与分布式生态
故障恢复和版本迁移
~~~

## 5.11 幻觉：生成概率与事实依据之间的缝隙

### 幻觉是什么

幻觉是看起来流畅、具体、可信，但不真实、无依据或与给定上下文冲突的输出。它可能表现为：

~~~text
编造论文、引用或 API
把过时信息当作当前事实
错误归因
数字和代码计算错误
把多个实体混合
在证据不足时强行回答
引用存在但不支持 claim
~~~

### 为什么 next-token 目标会产生幻觉

模型的基本训练目标是提高真实 token 的概率，而不是查询一个实时事实库。对于知识缺口，语言分布仍然可能提供一条流畅续写。高置信度只表示模型分布集中，不等于事实概率高。

### 事实性与 groundedness

可以把答案拆成 claims 和 evidence。对每个 claim 检查：

~~~text
claim 是否由证据支持
证据是否与问题相关
证据是否是最新版本
引用是否真的存在
是否存在相互冲突的证据
模型是否表达了不确定性
~~~

RAG 只能提供证据通道，不能自动保证模型使用了正确证据；需要引用支持评估、选择性回答和冲突处理。

### 缓解手段的分工

~~~text
训练 / 后训练：提高拒答、格式和偏好
RAG：提供外部文本依据
工具：执行计算、查询和操作
校验器：检查 schema、公式、代码和权限
交互：允许澄清、引用和人工升级
监控：收集 bad case、漂移和反馈
~~~

没有一种手段能消灭所有幻觉。目标是让错误更少、更可见、更可恢复，并限制高风险动作。

## 5.12 从模型能力到产品场景

### 为什么 demo 不等于产品

Demo 往往使用精心选择的输入、低并发和人工兜底；产品要面对长尾输入、权限、成本、延迟、数据更新、监控、回滚和用户长期使用。一个场景是否值得做，不能只问模型能不能回答。

### 场景选择

可从以下问题筛选场景：

1. 用户是谁，当前如何完成任务。
2. 痛点是否真实、高频或高价值。
3. 任务结果是否可验证。
4. 错误成本和人工接管路径是什么。
5. 数据、权限和工具是否可用。
6. LLM 相比规则、搜索或传统 ML 增加了什么价值。
7. 单次成本和响应时间是否符合工作流。
8. 是否能建立离线评估和线上反馈。

### 任务旅程

“做一个客服机器人”不是完整场景。需要展开真实任务链，例如：

~~~text
用户提出问题
 -> 身份与权限判断
 -> 检索当前政策
 -> 组织带引用的回答
 -> 用户追问
 -> 必要时创建工单
 -> 高风险问题转人工
 -> 记录结果和反馈
~~~

模型可能只适合其中某一步。把模型嵌入工作流，比让它承担所有步骤更容易评估和治理。

### 技术指标与体验指标

离线指标包括准确率、引用支持、结构化输出、工具成功、代码测试和拒答质量；体验指标包括任务完成率、首次成功率、采纳率、追问率、人工接管率、P95 延迟、单位任务成本和用户留存。二者需要建立映射，不能拿一个公开 benchmark 直接代表产品价值。

## 5.13 企业系统的权限、成本与可运营性

### 权限不是 prompt

企业 LLM 应用需要在后端执行身份认证、授权、租户隔离和数据过滤。把“不要泄露机密”写入 system prompt，不等于检索和工具真的不会返回机密。权限应贯穿：

~~~text
登录与身份
检索候选过滤
上下文拼接
引用展示
工具调用
日志查看
缓存复用
人工升级
~~~

### 数据新鲜度与引用

企业知识库的质量取决于文档版本、owner、更新时间、权限、失效策略和引用支持。模型回答得流畅但引用了过期制度，仍然是业务失败。系统应保留文档版本和 evidence id，让答案能够回溯到具体内容。

### 成本账本

单次任务成本不是模型 token 单价一个数字。至少要加总：

~~~math
C_{\mathrm{task}}
=C_{\mathrm{model}}
+C_{\mathrm{retrieval}}
+C_{\mathrm{tool}}
+C_{\mathrm{review}}
+C_{\mathrm{retry}}
+C_{\mathrm{risk}}.
~~~

各项必须互不重叠：若model/tool已经包含所有重试调用，C_retry只能统计尚未计入的额外费用；人工升级若已计入review，不能再计入risk。C_risk可单列未被其他项覆盖的事故或赔付期望损失，并与实际支出分开展示。Agent多轮调用和长上下文会让成本高于表面的一次API调用。

例如100个任务的全部调用及重试共花20元，其中80个满足成功标准，平均任务成本为0.20元，单位成功成本为20/80=0.25元。失败与重试的成本都保留在分子；按任务归并重试后统计分母，全失败时单位成功成本不定义，不能报告为零。

### 延迟与 SLO

产品要记录 TTFT、TPOT、总时延、P95/P99、错误率、超时率和任务完成率。平均延迟掩盖尾部请求；RAG、工具、长上下文和人工接管都可能改变 P95。低延迟但答案不能用，不是好的优化结果。

### 运营闭环

上线后应记录定位问题所需的trace、反馈、审核结果和模型/prompt/索引/工具版本，按权限、脱敏与保留策略管理敏感内容，不能默认把全部原始输入长期落盘。灰度、回滚、回归评估和版本追踪有助于定位问题；trace不足会限制复现能力，但即使有完整版本记录，外部工具状态或非确定性也可能让逐字复现不可得。

## 5.14 评估、反馈与版本迁移

### 评估集的分层

一个可持续的 LLM 评估集应包含：

~~~text
基础能力样本
真实用户任务
高价值和高风险样本
语言、长度和领域分桶
权限和越权样本
引用和事实性样本
工具失败与恢复样本
对抗和 prompt injection 样本
历史线上 bad case
~~~

评估集要版本化、去重、记录来源和答案证据。每次模型、prompt、检索器、工具 schema 或安全策略变更，都要比较冻结 baseline。

### 反馈闭环

反馈不是简单收集点赞。要区分：

~~~text
答案错误
证据不支持
格式无法解析
延迟过高
权限错误
拒答过度
模型不拒答
工具调用失败
用户修改了答案
用户转人工
~~~

这些标签对应不同修复路径。把所有负反馈都用于继续训练，可能把格式、偏好和事实问题混成噪声。

### 灰度与回滚

新版本先进入小流量或低风险用户，比较主指标和护栏指标。若事实性、权限、P95、成本或过度拒答恶化，应能切回旧模型、旧 prompt、旧索引、旧工具 schema 或人工流程。回滚计划是系统设计的一部分，不是事故发生后才临时决定。

### 版本追踪

一次请求至少应能关联：

~~~text
模型与 adapter 版本
tokenizer 与 chat template 版本
system prompt hash
检索索引和文档版本
工具 schema 与权限策略
代码和配置版本
评估集版本
用户反馈与人工处理状态
~~~

LLM 系统的版本远不止 checkpoint。缺少其中任何一项，都可能让线上行为无法复现。

### 可靠性指标的组合

可以将任务成功定义为多个条件的合取：

~~~math
S
=S_{\mathrm{task}}
\land S_{\mathrm{format}}
\land S_{\mathrm{evidence}}
\land S_{\mathrm{permission}}
\land S_{\mathrm{latency}}.
~~~

这说明平均回答质量不能掩盖一次权限泄露或无法解析的输出。实际报告应同时列出主指标、护栏、分桶、失败样例、成本和回滚状态。

这些是按任务选定的布尔验收条件，非所有任务都需要外部证据；不适用项应预先定义，不能事后按结果删除。条件通常相关，联合成功率应逐任务计算合取后再平均，不能直接把各边际通过率相乘。零次安全失败也不证明总体风险为零，仍需报告样本量与覆盖范围。

例如四个任务中，任务正确和格式正确都在前两个任务通过、后两个失败。两项边际通过率均为0.5，但联合通过率仍为0.5，不是0.5×0.5=0.25。逐任务记录才能保留这种相关性。

## 5.15 资料与证据边界

本章的概率目标和 Transformer 背景来自基础论文；预训练规模和 scaling 讨论来自公开研究；后训练、ICL、事实性和产品系统部分需要结合论文、官方文档和目标系统实测。建议优先阅读：

- [Attention Is All You Need](https://arxiv.org/abs/1706.03762)：Transformer 主干。
- [Language Models are Few-Shot Learners](https://arxiv.org/abs/2005.14165)：规模化语言模型与 ICL。
- [Training Compute-Optimal Large Language Models](https://arxiv.org/abs/2203.15556)：参数、数据和计算配比。
- [Training Language Models to Follow Instructions with Human Feedback](https://arxiv.org/abs/2203.02155)：指令微调和人类反馈。
- [Chain-of-Thought Prompting Elicits Reasoning in Large Language Models](https://arxiv.org/abs/2201.11903)：CoT 提示。
- [TruthfulQA](https://arxiv.org/abs/2109.07958)：事实性和真实性评估。
- [FActScore](https://arxiv.org/abs/2305.14251)：原子事实支持评估。
- [SelfCheckGPT](https://arxiv.org/abs/2303.08896)：无外部知识的幻觉检测思路。
- [HELM](https://arxiv.org/abs/2211.09110)：多维语言模型评估。
- [Hugging Face Chat Templates](https://huggingface.co/docs/transformers/main/en/chat_templating)：对话格式接口。
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：风险治理。
- [OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)：LLM 应用安全风险。

这些资料的证据层不同。论文中的 benchmark 结果不能直接变成产品 SLO，官方 chat template 文档不能证明模板在某个 checkpoint 上的质量，教学代码输出也不能替代真实用户、目标硬件和权限环境中的实测。涉及最新模型时，应优先核对官方 model card、配置、tokenizer、许可证、训练截止时间和可复现实验，再把宣传能力与已验证能力分开记录。

## 本章回顾

理解大语言模型，应该能够把以下链路完整讲清楚：

~~~text
next-token probability
 -> teacher forcing and label shift
 -> token loss / perplexity
 -> base model
 -> instruction and preference post-training
 -> prompt / chat template / ICL
 -> decoding and stopping
 -> evidence / tool / verification
 -> task metrics
 -> cost / latency / permission
 -> monitoring / feedback / rollback
~~~

其中最重要的边界有三条：
