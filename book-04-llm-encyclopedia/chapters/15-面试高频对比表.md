# 第 15 章 方法比较与工程取舍

比较两个方法，真正困难的地方不在于列出它们的定义，而在于判断它们是否在解决同一个问题。AdamW 和 FlashAttention 不属于同一层，LoRA 和量化也不属于同一层；把它们都放进“谁更好”的问题里，结论必然失真。

一个可靠的比较要先固定对象和约束：任务是什么，输入长度多大，模型规模多少，训练还是推理，硬件是什么，延迟和成本上限是多少，质量用什么指标，失败的代价是什么。之后再问方法改变了哪一层，以及它把多少资源从一个位置转移到了另一个位置。

本章把常见比较关系拆成独立主题。每节先说明共同问题，再解释机制差异；公式只表达关键数量关系，变量会在正文中定义；代码是无外部依赖的教学实验。表格可以帮助快速定位，但不能代替数据切片、消融、失败分析和目标系统实测。

## 15.1 比较的第一原则：先固定问题和账本

### 同一个指标不等于同一个任务

两个模型都得到 85% 的准确率，并不意味着它们能力相同。一个可能是在短文本分类上测得的，另一个可能是在长上下文、工具调用或代码执行上测得的。即使数据集名称相同，提示模板、答案抽取、采样次数和评估脚本不同，也会改变结果。

比较前至少需要记录：

- 输入分布、长度、语言和用户切片；
- 模型参数量、激活参数量、上下文长度和版本；
- 训练 token、微调数据、解码配置和候选预算；
- GPU、显存、batch、并发、kernel 和软件版本；
- 质量、延迟、吞吐、显存、成本和安全指标；
- 失败是否可逆，以及错误会不会作用于外部系统。

### 质量和成本同时写

设方案 A 和方案 B 在同一目标任务上的质量分数为 QA、QB，单位请求成本为 CA、CB，端到端延迟为 TA、TB。实际记录时，质量要写明数据集和切片；成本要说明按请求、token 还是 GPU 秒计；延迟要注明 p50、p95 或 p99 以及并发度。比较不能只看：

~~~math
\Delta Q=Q_A-Q_B
~~~

还要记录：

~~~math
\Delta C=C_A-C_B,
\qquad
\Delta T=T_A-T_B
~~~

当质量差异和成本差异都存在时，可以画出 Pareto 前沿：如果一个方案在质量、延迟和成本上都不如另一个方案，它被支配；如果它用更高成本换来更高质量，就需要结合业务价值决定是否值得。

### 机制、代价和失败模式

一个完整的比较至少回答五个问题：

1. 两种方法共同解决什么旧问题；
2. 它们在数据流、参数、计算或权限上的机制差异是什么；
3. 质量、显存、延迟、工程复杂度分别发生了什么变化；
4. 哪些输入或部署条件会让优势消失；
5. 如何用反事实、消融和线上切片验证判断。

如果只说“B 更先进”，读者无法知道换了硬件、数据、预算之后结论是否仍成立。

## 15.2 Adam 与 AdamW：权重衰减放在哪里

### Adam 的自适应更新

Adam 为每个参数维护一阶矩和二阶矩。省略偏置修正时，梯度 gt 的更新可写为：

~~~math
m_t=\beta_1m_{t-1}+(1-\beta_1)g_t
~~~

~~~math
v_t=\beta_2v_{t-1}+(1-\beta_2)g_t^2
~~~

~~~math
\theta_{t+1}
=
\theta_t-\eta
\frac{m_t}{\sqrt{v_t}+\epsilon}
~~~

θ 是参数，η 是学习率，β1 和 β2 是矩估计的衰减系数，ε 防止除零。Adam 的每个参数都有自己的有效步长，因此把 L2 正则直接加到梯度中时，正则项也会被二阶矩缩放。[AdamW 原论文](https://arxiv.org/abs/1711.05101) 将这点与“直接缩小参数”的 decoupled weight decay 区分开来。

### AdamW 的解耦衰减

AdamW 把衰减从梯度自适应项中拿出来：

~~~math
\theta_{t+1}^{\mathrm{AdamW}}
=
(1-\eta\lambda)\theta_t
-\eta\frac{m_t}{\sqrt{v_t}+\epsilon}
~~~

λ 是 weight decay 系数。这个更新让参数衰减的作用更直接，不会因为不同参数的 v_t 不同而被不均匀地重塑。

这不意味着 AdamW 在所有数据和任务上都必然更好。原论文报告的改善来自特定 ResNet、CIFAR-10/ImageNet32x32、训练步数和学习率日程；它说明解耦改变了可调参数关系，并不能替目标 LLM 预先给出收益。真正影响结果的还有学习率、warmup、decay 系数、参数分组、是否衰减 bias/normalization 参数和训练步数。公平比较需要固定超参数搜索预算，否则“优化器比较”可能只是“谁调得更充分”的比较。

### 一个最小更新实验

~~~python
import math
from numbers import Real


def _finite(value):
    if isinstance(value, bool) or not isinstance(value, Real):
        return False
    try:
        return math.isfinite(float(value))
    except (TypeError, OverflowError):
        return False


def _validate_optimizer_args(theta, moment, square, grad, lr, beta1, beta2, eps, decay=0.0):
    if not all(_finite(value) for value in (theta, moment, square, grad, lr, beta1, beta2, eps, decay)):
        raise ValueError("optimizer inputs must be finite real numbers")
    if lr <= 0 or not 0 <= beta1 < 1 or not 0 <= beta2 < 1 or eps <= 0 or decay < 0:
        raise ValueError("invalid optimizer hyperparameters")
def adam_step(theta, moment, square, grad, lr, beta1, beta2, eps):
    _validate_optimizer_args(theta, moment, square, grad, lr, beta1, beta2, eps)
    moment = beta1 * moment + (1.0 - beta1) * grad
    square = beta2 * square + (1.0 - beta2) * grad * grad
    update = lr * moment / (square ** 0.5 + eps)
    return theta - update, moment, square


def adamw_step(theta, moment, square, grad, lr, beta1, beta2, eps, decay):
    _validate_optimizer_args(theta, moment, square, grad, lr, beta1, beta2, eps, decay)
    moment = beta1 * moment + (1.0 - beta1) * grad
    square = beta2 * square + (1.0 - beta2) * grad * grad
    update = lr * moment / (square ** 0.5 + eps)
    decayed_theta = (1.0 - lr * decay) * theta
    return decayed_theta - update, moment, square


adam_theta, _, _ = adam_step(1.0, 0.0, 0.0, 0.5, 0.1, 0.9, 0.999, 1e-8)
adamw_theta, _, _ = adamw_step(
    1.0, 0.0, 0.0, 0.5, 0.1, 0.9, 0.999, 1e-8, 0.1
)
print(round(adam_theta, 4), round(adamw_theta, 4))
try:
    adam_step(1.0, 0.0, 0.0, 0.5, 0.0, 0.9, 0.999, 1e-8)
except ValueError:
    print("invalid learning rate rejected")
else:
    raise AssertionError("invalid learning rate was accepted")
~~~

这个实验只展示更新位置的差异，不包含 bias correction、参数组和真实训练。代入代码里的初值，第一步 Adam 得到约 `0.6838`，AdamW 得到约 `0.6738`；多出的 `0.01` 参数收缩来自 `(1-ηλ)`。它适合帮助读者检查实现，而不是证明某个优化器在目标任务上更优。

## 15.3 SGD 与 Adam：统一步长和自适应步长

SGD 的基本更新是：

~~~math
\theta_{t+1}=\theta_t-\eta g_t
~~~

加入 momentum 后，还会累积历史梯度。它的优点是状态简单、额外显存小，有时具有较好的泛化行为；代价是对学习率、schedule 和梯度尺度更敏感。

Adam 为每个参数估计梯度的尺度，通常在训练初期更容易获得稳定下降，尤其适合稀疏梯度、不同层梯度尺度差异很大的模型。代价是需要保存一阶和二阶状态，优化器显存可能接近甚至超过参数本身。

大模型预训练常用 AdamW，不是因为 SGD 在理论上不能训练 Transformer，而是因为许多预训练配方把自适应更新作为成熟基线；[AdamW 原论文](https://arxiv.org/abs/1711.05101) 在所测图像分类任务中报告其改善了 Adam 的泛化、缩小了与动量 SGD 的差距。这个结论不能直接外推到 LLM 的 loss、数据和算力规模。视觉模型或某些大规模监督任务中，SGD 仍可能有竞争力。

比较时要同时观察训练 loss、最终任务、总优化器状态显存、收敛步数和超参搜索成本。若只看前几千步的 loss，可能把“早期收敛快”误认为“最终泛化更好”。

## 15.4 BatchNorm 与 LayerNorm：统计量沿哪条轴计算

BatchNorm 对每个特征通道分别统计。在常见 NCHW 图像张量中，它沿 batch、height、width 维求均值和方差；推理通常使用训练阶段积累的 running statistics。小 batch、分布变化或训练/推理批次差异会让这组统计量变得不可靠。

LayerNorm 则对单个样本的 hidden 维度做归一化：

~~~math
\mathrm{LN}(x)
=
\gamma\odot
\frac{x-\mu(x)}
\sqrt{\mathrm{Var}(x)+\epsilon}
+\beta
~~~

对于每个样本的 hidden 向量，统计量不依赖其他样本；在 Transformer 中常对每个 token 的 hidden 维做归一化，因此更适合变长序列、动态 batch 和自回归推理。[LayerNorm 原论文](https://arxiv.org/abs/1607.06450) 也以训练/测试计算相同、以及可用于循环网络作为设计动机。

两者的主要差异不是“一个新一个旧”，而是统计维度和部署假设不同。BatchNorm 在小 batch、分布变化、逐 token 解码时需要额外处理 running statistics；LayerNorm 每次直接使用当前样本的 hidden 值，代价是对每个 token 做归约。

在多模态模型或视觉语言模型中，两种归一化都可能出现：视觉 encoder 可能采用 BatchNorm 或 LayerNorm，语言 decoder 可能采用 LayerNorm/RMSNorm。不能根据整个系统的输入模态直接推断归一化类型。

## 15.5 LayerNorm 与 RMSNorm：中心化是否值得

LayerNorm 先减均值，再除以标准差；RMSNorm 只控制均方根尺度：

~~~math
\mathrm{RMSNorm}(x)
=
\gamma\odot
\frac{x}
\sqrt{\frac{1}{d}\sum_{j=1}^{d}x_j^2+\epsilon}
~~~

d 是 hidden 维度，γ 是可学习的缩放参数。RMSNorm 不减去均值，只用均方根控制尺度；[原论文](https://arxiv.org/abs/1910.07467) 将假设表述为中心化不变性可能不必要，并在若干模型和任务中报告与 LayerNorm 可比的质量及更短运行时间。它支持这条设计路线，不保证每个 LLM 或硬件上的端到端收益。

选择 RMSNorm 的理由通常是计算路径简单、残差结构配合自然和经验质量足够，而不是它在所有网络上都严格优于 LayerNorm。某些任务需要中心化带来的优化性质，或已有 checkpoint 的归一化结构不能随意替换。

比较时应固定初始化、残差顺序、学习率和 epsilon。把一个已经训练好的 LayerNorm 模型直接改成 RMSNorm，不是公平的结构消融，因为参数分布和训练动态都已经改变。

## 15.6 Pre-Norm 与 Post-Norm：残差路径如何传梯度

Post-Norm 的典型形式是：

~~~math
x_{l+1}
=
\mathrm{Norm}
\left(
x_l+F_l(x_l)
\right)
~~~

Pre-Norm 则是：

~~~math
x_{l+1}
=
x_l+F_l(\mathrm{Norm}(x_l))
~~~

xl 是第 l 层输入，Fl 是 attention 或 FFN 子层。对 Pre-Norm 的 `x+F(Norm(x))` 求导，会得到 `I + J_F J_Norm`，残差支路保留显式恒等项；Post-Norm 的 `Norm(x+F(x))` 则得到 `J_Norm(I+J_F)`，残差路径也经过归一化的 Jacobian。[相关理论分析](https://arxiv.org/abs/2002.04745) 将 Post-Norm 初始化时输出层附近梯度较大、需要 warmup 的结论绑定在特定架构与分析假设下。Pre-Norm 深层训练往往更容易稳定，但不代表它在所有深度、初始化和学习率下都更优。

现代大模型多采用某种 Pre-Norm 或其变体，但这并不意味着“Pre-Norm 永远正确”。超深网络还可能使用额外的 residual scaling、初始化、NormFormer 或 sandwich norm。比较时要一起记录深度、初始化、学习率 warmup、最终 loss 和梯度范数。

## 15.7 BERT 与 GPT：理解式编码和生成式建模

BERT 使用 encoder-only 和 masked language modeling，输入中的 token 可以同时利用左右上下文；GPT 使用 decoder-only 和 causal language modeling，第 t 个位置只能读取 t 之前的内容。可回到 [BERT](https://arxiv.org/abs/1810.04805) 与 [GPT 原始预训练报告](https://cdn.openai.com/research-covers/language-unsupervised/language_understanding_paper.pdf) 核对原始目标，避免把后来的指令微调能力倒推成两种架构原本的训练接口。

这导致两条路线适合不同接口。BERT 的输出是整段输入的表示，适合分类、检索、实体识别和 embedding；GPT 的输出是逐 token 的概率分布，适合对话、代码、长文本和工具调用。

两者不能简单用某个 benchmark 分数比较，因为任务头和训练目标不同。若任务需要为每个 token 生成后续文本，BERT 的双向编码并不会直接提供自然的自回归接口；若任务只需要快速得到句向量，使用大型 decoder-only 模型可能浪费计算。

近年来 decoder-only 模型也可以通过 prompt 完成分类和抽取，encoder 模型也可以被扩展为生成式结构，但这改变了模型和部署成本。架构选择仍应从输出形式、延迟、上下文共享和数据规模出发。

## 15.8 Encoder-Decoder 与 Decoder-Only：两种条件生成组织方式

Encoder-decoder 把输入先编码成双向表示，再由 decoder 生成输出。输入长度和输出长度在结构上分开，翻译、摘要和条件改写很自然；[T5](https://arxiv.org/abs/1910.10683) 是将多种 NLP 任务统一为 text-to-text 的代表实例。

Decoder-only 把输入、指令和输出放在同一个 causal 序列中，用统一的 next-token loss 训练。它的优势是架构简单、预训练目标统一、in-context learning 和对话模板容易扩展。

Encoder-decoder 的 cross-attention 让 decoder 可以直接访问 encoder 表示；decoder-only 需要通过上下文 token 和 causal attention 访问输入。前者可能在某些长输入短输出任务上更高效，后者则更容易把预训练、对话、代码和工具轨迹统一到一个接口。

“通用大模型普遍采用 decoder-only”是生态事实，不是理论定理。文本到文本、语音转文本和某些结构化转换仍然可以从 encoder-decoder 中获益；选择要结合序列长度、输出长度、预训练数据和服务架构。

## 15.9 MHA、MQA 与 GQA：质量换 KV Cache

Multi-Head Attention 为每个 query head 保存独立的 K/V；Multi-Query Attention 让所有 query head 共享一组 K/V；Grouped-Query Attention 则让一组 query head 共享一组 K/V。

若 batch 为 B、层数为 N、缓存长度为 L、KV head 数为 Hkv、head 维度为 dh、元素字节数为 b，粗略 KV cache 大小为：

~~~math
M_{\mathrm{KV}}
\approx
2BNLH_{\mathrm{kv}}d_hb
~~~

2 表示 key 和 value。MHA 取 `H_kv=H_q`，MQA 取 `H_kv=1`，GQA 让多个 query head 共享一组 KV head，介于两者之间。[GQA 原论文](https://arxiv.org/abs/2305.13245) 通过转换已有 MHA checkpoint 并继续 uptrain，报告用原预训练计算量 5% 的配方得到质量接近 MHA、推理速度接近 MQA 的结果；这不是无需适配即可替换结构的保证。GQA/MQA 减少缓存容量和 decode 带宽，但共享过多可能损失注意力表达能力。

这不是只在模型结构表里出现的差异。KV head 数会直接影响并发上限、长上下文可用长度和 paged cache 的物理块数量。比较时要固定模型质量、上下文长度、batch、量化格式和 kernel；否则“GQA 更快”可能只是因为它使用了不同的 batch。

## 15.10 Absolute Position、RoPE 与 ALiBi：顺序信息的三种注入

Absolute position 将位置向量加入 token 表示。学习式位置表不能直接索引训练长度之外的位置；正弦位置函数虽可计算到更远位置，模型也不因此自动具备可靠外推能力。

RoPE 对 Q/K 子空间施加位置相关旋转，使内积带有相对位置关系。ALiBi 则直接在 attention score 上加入距离偏置：

~~~math
s_{ij}
=
\frac{q_i k_j^{\mathsf T}}{\sqrt{d}}
-m_h|i-j|
~~~

d 是 head 维度，`m_h` 是第 h 个 head 的非负距离斜率；因果 mask 仍需屏蔽 `j>i` 的未来位置。[RoPE](https://arxiv.org/abs/2104.09864) 改变 Q/K 的旋转几何，[ALiBi](https://arxiv.org/abs/2108.12409) 改 attention score。三种方法的差异是“改 token 表示”“改 Q/K 几何”还是“改 attention 分数”。ALiBi 原论文的长外推结果是特定模型从 1,024 训练位置到 2,048 推理位置的实验，不能将其理解为任意长度下质量不降。

长上下文比较不能只看最大支持长度。应观察训练长度与推理长度的比例、首尾检索、位置中间的证据利用、不同语言、短上下文质量和 KV cache 行为。窗口声明不等于有效使用能力。

## 15.11 ReLU、GELU 与 SwiGLU：FFN 的非线性和门控

ReLU 是：

~~~math
\mathrm{ReLU}(x)=\max(0,x)
~~~

GELU 使用平滑的概率式门控，SwiGLU 则把一个分支作为门控：

~~~math
\mathrm{SwiGLU}(x)
=
\mathrm{Swish}(xW_g)
\odot
(xW_u)
~~~

Wg 和 Wu 是两组投影，`⊙` 是逐元素乘法。SwiGLU 增加一条门控投影，因此若保持与两矩阵 FFN 相同的中间宽度，参数量会增加；公平比较需要相应缩小 hidden width，使总参数量和 FLOPs 接近。[GLU 变体研究](https://arxiv.org/abs/2002.05202) 在其 Transformer 序列任务中观察到某些门控变体优于常用 ReLU/GELU，不能把这组结果脱离模型宽度和训练预算写成普遍排序。

比较激活函数时要固定 FFN 中间维度、总参数、训练 token 和优化器。若 SwiGLU 模型同时更宽、训练更久，那么不能把全部提升归因于激活函数。实际选择还受 kernel、权重布局和量化支持影响。

## 15.12 SFT、RLHF 与 DPO：三种后训练路线

SFT 使用高质量示范，学习条件分布：

~~~math
\mathcal{L}_{\mathrm{SFT}}
=
-\sum_t m_t
\log p_{\theta}(y_t\mid x,y_{<t})
~~~

mt 是 assistant token mask，避免把用户输入当成需要预测的目标。SFT 擅长模仿格式、风格和任务流程，但上限受示范数据覆盖影响。

这里的 RLHF 采用常见的窄义流程：[InstructGPT](https://arxiv.org/abs/2203.02155) 先做示范 SFT，再用偏好比较训练 reward model，最后用 PPO 优化 policy。文献中 RLHF 有时也泛指更广的“用人类反馈对齐”，因此比较前要先说清讨论的是反馈来源还是具体训练算法。偏好可以表达有用性、风格和安全等难以写成固定标签的目标，但 reward model 只是人类偏好的近似，策略可能学会优化评分器的漏洞。

DPO 直接从 chosen/rejected 对优化 policy，省掉独立 reward model 和 PPO 训练环节的一部分复杂度。[DPO 原论文](https://arxiv.org/abs/2305.18290) 推导的是给定偏好对上的离线目标；长期工具任务和可验证环境若需要根据当前策略的新行为采样，仍可能需要在线反馈或 verifier。

三者不是互斥的替代关系。常见流程是 SFT 先让模型学会任务格式，再使用 DPO、RLHF、RLAIF 或 RLVR 改善偏好、安全和推理。比较时要区分“会做任务”“回答更讨喜”“结果可验证”和“真实行动成功”。

## 15.13 RLHF 与 DPO：在线策略优化和离线偏好优化

RLHF 的奖励模型可表示为对两个回答的偏好概率：

~~~math
P(y_w\succ y_l\mid x)
=
\sigma\left(r_{\phi}(x,y_w)-r_{\phi}(x,y_l)\right)
~~~

rφ 是 reward model；此处用 Bradley–Terry 偏好模型把两回答的分数差映射成偏好概率。训练 policy 时还要处理参考策略 KL、当前采样分布和策略更新。

DPO 将偏好关系转化为相对 log-prob 目标：

~~~math
\mathcal{L}_{\mathrm{DPO}}
=
-\log\sigma
\left(
\beta
\left[
\log\frac{\pi_{\theta}(y_w\mid x)}
{\pi_{\mathrm{ref}}(y_w\mid x)}
-
\log\frac{\pi_{\theta}(y_l\mid x)}
{\pi_{\mathrm{ref}}(y_l\mid x)}
\right]
\right)
~~~

`x` 是 prompt，`y_w` 和 `y_l` 分别是偏好较高/较低的完整回答，`π_ref` 是固定参考策略，`π_θ` 是待优化策略，`β` 控制相对 log-prob 差对 loss 的缩放。RLHF/PPO 可以从更新后的 policy 继续采样，探索当前策略附近的回答，但 reward model 可能被钻漏洞；经典离线 DPO 直接消费已有偏好对，不会自动收集新回答，所以分布外行为缺少新监督。这个差别描述的是数据闭环，不是所有后续 DPO 变体的共同限制；DPO 原论文也将更充分的分布外泛化研究列为后续问题。

因此，偏好数据覆盖充分、任务主要是单轮或离线回答时，可以先比较 DPO 的训练与复核成本；需要长期行动、环境反馈和稀疏奖励时，应比较在线 RL、环境 verifier 或带反馈循环的偏好优化。两种路线的质量需要在相同 policy 初始化、偏好数据、采样预算和验证集上测量；DPO 的“更简单”不等于在所有实现中更稳定或更便宜。

## 15.14 RLHF 与 RLAIF：反馈来源不同，监督风险仍在

RLAIF 的核心是让 AI 产生或辅助产生监督反馈，不等于“所有 RLAIF 都让 judge 直接给最终答案打分”。[Constitutional AI](https://arxiv.org/abs/2212.08073) 展示原则引导的自我批评/修订与 AI feedback 流程；[RLAIF 与 RLHF 对照研究](https://arxiv.org/abs/2309.00267) 比较了 AI 生成偏好后训练 reward model 的 canonical RLAIF，也研究了直接用 AI 模型给 reward 的 d-RLAIF。该论文在摘要、helpful dialogue、harmless dialogue 等任务上报告与 RLHF 可比的偏好结果，不证明所有任务都能用 AI feedback 替代人类。

人类反馈接近目标产品的人类偏好，但成本高、速度慢、标注一致性有限；AI feedback 覆盖大、成本低，却可能继承评价模型偏差和被评价模型的盲点。对高风险二分类任务，应把“危险”定义为正类，保留人工金标准，并按语言、风险等级、长度和任务切片测量漏判率：

如果 AI judge 对高风险样本的漏判率为 q，扩大样本数量不会自动降低这类系统性错误。应该保留人工金标准集，按语言、风险等级、长度和任务切片测量：

~~~math
\mathrm{FNR}_{\mathrm{AI}}
=
\frac{FN_{\mathrm{AI}}}
{TP_{\mathrm{AI}}+FN_{\mathrm{AI}}}
~~~

研究中一种缓解评审位置偏差的方法是把候选顺序互换后再评一次；这会增加调用成本，且不能修复 judge 对事实或专业标准的系统性错误。可将 AI feedback 用于低风险初筛或生成待审样本；高影响发布决策仍需要人工金标准或可执行验证器。两种反馈可以组合，而不是把 AI feedback 当成廉价真值。

## 15.15 Top-k 与 Top-p：限制采样候选集的两种方式

设 logits 为 zi，温度为 T，softmax 概率为：

~~~math
p_i^{(T)}
=
\frac{\exp(z_i/T)}
{\sum_j\exp(z_j/T)}
~~~

Top-k 保留概率最高的固定 k 个 token；top-p 先排序，再保留累计概率首次达到阈值的最小前缀集合。令 `p_(j)^(T)` 是排序后第 j 个 token 的概率，`p_cut` 是 top-p 阈值，则保留的前缀长度为：

~~~math
m=\min\left\{j:\sum_{\ell=1}^{j}p_{(\ell)}^{(T)}\ge p_{\mathrm{cut}}\right\}
~~~

前者控制候选数量，后者控制保留的累计概率质量。

当分布很尖锐时，top-p 的候选可能很少；当分布很平坦时，候选会自动扩大。top-k 在不同上下文下的随机性范围更固定，top-p 对 logits 形状更自适应。

两者都可能破坏结构化输出：只要合法 token 被截掉，JSON、代码或函数参数就可能无法继续。因此结构化生成通常还需要 grammar constraint、schema mask 或专用解码器，而不是只调 k 和 p。

## 15.16 Temperature 与 Top-p：改变分布还是裁剪分布

Temperature 作用在 softmax 前，改变整个概率分布的尖锐程度；top-p 作用在排序和截断阶段，删除低概率尾部。低温通常提高确定性，高温提高候选多样性；top-p 则控制保留下来的概率质量。

例如 logits 为 `[2,1,0]` 时，`T=1` 的 softmax 约为 `[0.665,0.245,0.090]`；`T=2` 时约为 `[0.506,0.307,0.186]`。设 `top-p=0.9`，前者只需保留前两个 token（累计约 0.910），后者要保留三个（前两个累计约 0.813）。温度先改变分布，top-p 再按新分布决定候选集合，因此二者不是两个独立旋钮，实验时应记录组合而不是分别比较。

对于代码、函数调用和数字抽取，优先固定随机性、使用较窄的候选并增加语法约束；对于创意写作，可以增加温度或 top-p，但仍要监控重复、事实性和有害内容。

## 15.17 Greedy、Beam Search 与 Sampling：序列目标怎样被搜索

Greedy 每一步选择当前最大概率 token：

~~~math
\hat{x}_t
=
\arg\max_{x_t}
p(x_t\mid x_{<t})
~~~

它速度快且可复现，但只优化局部选择，不保证完整序列概率最优。

Beam search 保留 b 条候选序列，扩展后再按累计 log-prob 排序。比如第一步 A 的概率为 0.6、B 为 0.4；第二步在 A 后生成目标 token 的概率为 0.1，在 B 后为 0.9。greedy 先选 A，序列概率为 0.06；beam 宽度至少为 2 时能保留 B，最终发现其概率为 0.36。beam 仍是受宽度限制的搜索，长度归一化、停止规则也会改变排序目标。它适合翻译等相对确定的条件生成，但在开放式对话中可能偏向高概率套话、重复和长度偏差。[神经文本退化研究](https://arxiv.org/abs/1904.09751) 展示同一模型的解码策略会影响生成质量，并以 nucleus sampling 处理概率尾部和多样性问题。

Sampling 按概率随机选择 token，能够得到多个不同候选，更适合创意文本、self-consistency 和候选生成；代价是方差、不可复现和安全评估复杂。

解码策略不能脱离任务。一个模型在代码修复中可能需要确定性和语法约束，在故事生成中需要多样性，在数学推理中需要多候选加 verifier。比较时应测质量、重复率、pass@k、成本和跨次稳定性。

## 15.18 LoRA 与全量微调：更新多少参数

全量微调更新整个 W，允许任务梯度直接修改全部权重，但显存、优化器状态和 checkpoint 存储都高；数据量有限时还可能遗忘基础能力。

LoRA 只学习低秩更新：

~~~math
W'=W+\frac{\alpha}{r}BA
~~~

把 `W∈R^(d_out×d_in)`，则 `B∈R^(d_out×r)`、`A∈R^(r×d_in)`；`r` 是 rank，新增参数量为 `r(d_in+d_out)`，远小于原矩阵的 `d_out d_in`。[LoRA 原论文](https://arxiv.org/abs/2106.09685) 冻结基座并学习低秩矩阵，在其所测的 RoBERTa、DeBERTa、GPT-2/GPT-3 任务上报告与全量微调相当或更好的质量和较少训练参数；这是论文任务范围内的结果。LoRA 适合领域风格、格式、轻量任务适配和多个 adapter 共享同一基座。

当任务需要改变大量知识、底层推理能力或多个层的行为时，低 rank 可能成为瓶颈。LoRA 也会引入 adapter 加载、合并、路由和多租户隔离问题。选择不能只看训练显存，还要看质量上限、部署切换、长期维护和安全回归。

## 15.19 LoRA、Adapter 与 Prefix Tuning：改权重、加模块还是改上下文

LoRA 将更新限制在权重低秩子空间；Adapter 在 Transformer 层之间插入小网络；Prefix Tuning 学习虚拟 token 或可训练的 KV 前缀。

三者对基础模型的侵入位置不同。表格比较的是经典方法形态；具体实现是否可合并、是否增加序列长度或 KV 状态，仍需查看目标框架和层级配置。

| 方法 | 主要改变 | 推理影响 | 常见优点 |
| --- | --- | --- | --- |
| LoRA | 权重更新方向（[原论文](https://arxiv.org/abs/2106.09685)） | 可合并时无额外矩阵路径；多租户动态切换仍有路由成本 | 任务 adapter 体积小 |
| Adapter | Transformer 层内插入小网络（[原论文](https://arxiv.org/abs/1902.00751)） | 每层增加模块计算和 kernel 路径 | 多任务参数独立、可组合 |
| Prefix Tuning | 学习虚拟 token/连续 KV 前缀（[原论文](https://arxiv.org/abs/2101.00190)） | 增加注意力可见前缀与 KV 占用 | 可冻结基座，仅学习少量参数 |

Prefix 的参数少不代表任务表达能力无限；Adapter 的模块化也不代表多个模块可以无冲突叠加。比较时应测任务质量、基座保留、多个任务并存、切换延迟和 adapter 间干扰。

## 15.20 Quantization 与 Distillation：压数值还是压能力

量化把权重、激活或 KV cache 从高精度表示映射到低比特表示：

~~~math
\hat{w}
=
s\left(
\mathrm{clip}
\left(
\mathrm{round}\left(\frac{w}{s}\right)+z
\right)
-z
\right)
~~~

s 是 scale，z 是 zero point；`clip` 将整数码裁剪到 `[q_min,q_max]`，再用 scale 和 zero point 反量化。量化通常保留模型结构，但降低存储、带宽和部分计算成本；只有目标硬件有匹配的低比特算子时，低位宽才可能转化为更低延迟。

蒸馏使用教师模型产生 logits、答案、偏好或过程标签，让更小的学生模型学习教师行为。常见温度蒸馏项为：

~~~math
\mathcal{L}_{\mathrm{KD}}
=
T^2
\mathrm{KL}
\left(
p_{\mathrm{teacher}}^{(T)}
\parallel
p_{\mathrm{student}}^{(T)}
\right)
~~~

T 是蒸馏温度。蒸馏改变模型结构和能力分布，量化主要改变数值表示；二者可以组合，但误差也可能叠加。[知识蒸馏原始工作](https://arxiv.org/abs/1503.02531) 从集成教师压缩到单一学生出发；教师监督也可以是 logits、硬标签、答案或过程信号，蒸馏不是单一固定 loss。

如果模型结构已经合适、主要瓶颈是显存和带宽，量化通常更直接；如果需要更低的算力、延迟和部署体积，蒸馏可能更有价值。两种方法都要在真实任务和长尾样本上检查能力回归。

## 15.21 PTQ 与 QAT：什么时候让模型适应量化误差

Post-Training Quantization 在训练完成后量化，权重/激活量化是否需要代表性校准数据取决于具体算法；Quantization-Aware Training 在训练中插入 fake-quant 运算，前向模拟舍入和裁剪误差，反向通常用近似梯度更新浮点参数。[整数推理量化研究](https://arxiv.org/abs/1712.05877) 展示了量化推理与训练期误差适配的联合设计。

PTQ 适合已有 checkpoint、快速试验和量化误差较小的模型。它容易在 activation outlier、长上下文、代码、数学和多模态视觉 token 上出现局部退化。

QAT 可以恢复部分精度，但需要重新训练、保存量化配置和维护额外的训练路径。它也不保证目标硬件上的 kernel 一定支持对应格式。

比较 PTQ 与 QAT 时要报告校准数据、比特宽度、权重/激活/KV 是否量化、训练步数、最终质量和端到端速度。只写“QAT 精度更高”忽略了它的训练成本。

## 15.22 FP16 与 BF16：尾数精度和指数范围

FP16 与 BF16 都使用 16 bit，但位分配不同：FP16 是 1 位符号、5 位指数、10 位尾数，最大有限值约为 65,504；BF16 是 1 位符号、8 位指数、7 位尾数，指数范围接近 FP32，最大有限值约为 `3.39×10^38`，但舍入更粗。[NVIDIA CUDA 浮点格式文档](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html) 给出这些格式字段。

大模型训练常偏好 BF16，因为梯度和激活更不容易溢出，通常少依赖复杂 loss scaling。FP16 在支持良好的硬件上仍然有效，但更需要检查溢出、下溢和归约精度。

位宽相同不代表性能相同。矩阵乘、归约、通信、optimizer state、显存带宽和 kernel 支持共同决定端到端结果。应测训练稳定性、吞吐、峰值显存和最终任务，而不是只比较理论位数。

## 15.23 FlashAttention 与 Sparse Attention：优化实现还是改变连接图

FlashAttention 对全连接注意力使用 tiling 和 online softmax，精确计算标准 attention（忽略浮点运算顺序带来的舍入差异），主要减少 HBM 读写；Sparse Attention 先指定局部、全局或块状 mask，只在 mask 允许的位置连边。[FlashAttention 原论文](https://arxiv.org/abs/2205.14135) 也展示了 block-sparse 扩展；因此“Flash”描述 IO 算法，“sparse”描述连接图，两者可以组合。

稀疏 mask 上的计算可以相对该 mask 是精确的，但相对原本全连接 attention，它省略了边；只有当被省略的依赖对任务不关键时，质量才可能维持。FlashAttention 不会减少全连接 attention 的二次 token-pair 数量，只改善计算它时的内存访问。

Sparse Attention 在长上下文中可能降低复杂度，但如果关键证据落在被剪掉的连接之外，质量会下降；FlashAttention 不会解决二次连接数量，只会降低其实现成本。评估必须包含检索、长距离依赖、随机位置和不同 mask，而不是只测短序列吞吐。

## 15.24 PagedAttention 与 FlashAttention：缓存管理和算子实现

FlashAttention 关注一次 attention 运算如何分块读取 Q/K/V、计算 softmax 并减少 HBM 往返；PagedAttention 将每个请求的逻辑 KV token 块映射到可非连续分配的物理块，并由 vLLM 的 cache manager、共享策略和调度共同管理请求生命周期。[PagedAttention 原论文](https://arxiv.org/abs/2309.06180) 讨论的是 KV cache 管理与 serving 系统，不只是 allocator。

二者处于不同层，可以同时使用：

~~~math
\mathrm{KVBytes}
\approx
2B N_{\mathrm{layers}}L H_{\mathrm{kv}}d_hb_{\mathrm{elem}}
~~~

这里 `B` 是活跃请求数，`N_layers` 是层数，`L` 是每请求缓存 token 数，`H_kv` 是 KV head 数，`d_h` 是每 head 维度，`b_elem` 是每元素字节数；因而它与 15.9 的公式是同一容量账本。PagedAttention 的 block table 需要由对应 attention kernel 支持；两类优化可以在同一 serving 系统共存，但不能假设任意 FlashAttention kernel 都能直接读取分页布局。

如果只替换 FlashAttention，跨请求的 allocator 碎片和 prefix 生命周期可能仍是瓶颈；如果只使用 PagedAttention，单次 kernel 的访存效率仍可能不足。系统 benchmark 需要分开报告 cache 命中、block 利用率、TTFT、TPOT、吞吐和 p99。

## 15.25 KV Cache 与 Activation Checkpointing：避免重算和主动重算

KV cache 是推理阶段的时间换空间：历史 token 的 key/value 保存下来，后续生成不必为旧 token 重新投影 K/V。若 prompt 有 `T` 个 token，再生成第 `T+1` 个 token，无 cache 的实现会重复处理已有前缀；有 cache 时只计算新 token 的 K/V，但新 query 仍需与 `T` 个历史 key 做 attention，因此缓存不会把每个 decode step 的注意力成本降为常数。缓存容量随层数、长度、KV head 数和活跃 batch 增长，估算见 15.9。

Activation checkpointing 是训练阶段的空间换时间：前向只保存选定边界激活，反向时重新运行被丢弃的前向区域，再计算梯度。它降低训练显存，但增加计算；使用 dropout 等随机操作时，重算应保持与原前向一致的随机状态，否则优化轨迹会变化。

两者服务于相反的运行阶段：

| 机制 | 阶段 | 节省什么 | 增加什么 |
| --- | --- | --- | --- |
| KV cache | 自回归推理 | 历史 token 重算 | 显存、缓存管理和泄露边界 |
| Activation checkpoint | 训练反向 | 中间激活存储 | 重算 FLOPs 和训练时间 |

把二者都叫“缓存优化”会误导设计。KV cache 用历史中间表示换取更少重复计算，需要请求级别隔离、释放和复用；activation checkpoint 丢弃训练中间表示以换取反向重算，需要处理随机状态并保持前后向语义一致。

## 15.26 Data、Tensor 与 Pipeline Parallel：沿哪条维度拆分

Data Parallel 让不同 data-parallel rank 处理不同 micro-batch 并同步梯度；Tensor Parallel 把一层中的矩阵或 attention head 切到多卡；Pipeline Parallel 把不同层放到不同 stage。一个实际 GPU rank 往往同时参与 TP、PP 和 DP 进程组，因此 batch 公式里的 `D` 不是简单的 GPU 总数。

若一次 optimizer update 的全局 batch 为 `B_samples` 个训练样本，data-parallel 副本数为 D，每个副本累积 A 个 micro-batch、每个 micro-batch 有 b 个样本，则：

~~~math
B_{\mathrm{samples}}=D_{\mathrm{DP}}\cdot A\cdot b_{\mathrm{micro}}
~~~

`D_DP` 是独立数据副本数，不包含 TP/PP rank；`b_micro` 是每个 DP 副本每步处理的样本数。若样本长度差异大，还要另外记录每次更新的有效 token 数。Tensor Parallel 需要层内 all-reduce、all-gather 或 reduce-scatter，通信频繁但能切开单卡放不下的矩阵。Pipeline Parallel 按层切分模型，却会有 stage bubble；增加 micro-batch 可提高流水线填充率，但也改变梯度累积安排和激活占用。

真实训练通常组合三种并行，再加入 sequence/context parallel 或 expert parallel。比较时应分别计算参数显存、激活显存、通信量、bubble 比例和故障恢复复杂度。

## 15.27 DDP、ZeRO 与 FSDP：复制状态还是分片状态

DDP 每张卡保存完整模型、梯度和 optimizer state，通过 all-reduce 同步梯度，工程简单、吞吐稳定，但当完整状态超过单卡显存时无法启动。ZeRO 按阶段去掉这些 data-parallel 副本：

| 方案 | 分片的训练状态 | 直观代价 |
| --- | --- | --- |
| DDP | 不分片；模型、梯度和优化器状态都复制 | 最少重构，参数状态显存随副本重复 |
| ZeRO Stage 1 | optimizer state | optimizer state 通信/管理增加，梯度与参数仍复制 |
| ZeRO Stage 2 | optimizer state + gradients | 梯度分片/同步更复杂，参数仍复制 |
| ZeRO Stage 3 | optimizer state + gradients + parameters | 最省持久副本；计算前后需要参数 gather/reshard |

FSDP FULL_SHARD 采用类似 Stage 3 的分片账本：模块计算前 all-gather 参数、反向后 reduce-scatter 梯度，并在策略允许时释放未分片参数。[PyTorch FSDP 文档](https://docs.pytorch.org/docs/stable/fsdp.html) 描述了这些运行阶段。它和 ZeRO-3 的目标相近，但包装粒度、API、调度和 checkpoint 实现不同。

理想均匀切分下，持久状态占用可以近似从 S 降到 S/N，其中 S 是完整状态大小，N 是分片 rank 数；但实际峰值还包含 gather、prefetch、通信 buffer、梯度和碎片。

若完整训练状态 `S=80 GB`、8 个 rank 均匀分片，理想的持久状态份额是 `S/N=10 GB/rank`；这不包含被 gather 的全参数、当前层激活、通信 buffer、prefetch 和碎片，因此不能据此直接判定 10 GB 显存就够。选择时要看模型能否单卡放下、网络带宽、参数访问粒度、checkpoint 需求、故障恢复和团队熟悉度。DDP 的简单有时比节省显存更有价值；FSDP/ZeRO 的省显存也会带来更复杂的调试和通信。

## 15.28 RAG 与 Fine-Tuning：知识访问还是行为改变

RAG 把文档放在外部索引中，查询时由 retriever 找候选段落并放进生成上下文；fine-tuning 用训练样本改变参数，使模型更容易执行某类任务、格式或风格。[原始 RAG 工作](https://arxiv.org/abs/2005.11401) 把参数化生成器与可检索的非参数知识库组合，研究目标包括知识密集任务和可更新外部记忆。

如果事实频繁更新、需要按用户权限隔离、要求逐条引用和按文档撤回，RAG 通常更容易把知识源与模型行为分开审计；前提是 ACL 在 retrieval 阶段执行，不能把所有文档都取回后只靠 prompt 要求模型保密。如果问题是模型不会稳定输出指定格式、不会按流程抽取字段或缺少任务行为，微调更直接。微调适合教“怎么做”，不适合充当需要逐条删除和立即生效的权威数据库。

两者也可以组合：微调模型学习如何读取和引用检索证据，RAG 提供最新事实。不能用微调替代一个需要每小时更新的数据库，也不能期待 RAG 自动修复模型不会执行的任务格式。

评估要分开测检索召回、证据支持、答案正确、更新延迟、数据权限和模型行为。一个微调模型在旧知识上准确，并不意味着它能回答新知识；一个 RAG 模型引用了文档，也不意味着结论真的被文档支持。

## 15.29 Dense Retrieval 与 Sparse Retrieval：语义相似和词项精确

Sparse retrieval 依赖倒排索引、词项匹配和 BM25 等统计信号，擅长数字、代码、专有名词和精确短语；dense retrieval 把 query 和 document 编成向量，擅长同义改写和语义相近表达。

Dense 检索可能把相近型号映射到相邻向量，漏掉一个字符的版本差异；纯词项 sparse 检索若 query 与正文没有词项重合，也可能漏掉语义改写。[DPR](https://arxiv.org/abs/2004.04906) 是双编码器 dense retrieval 的代表，但其优劣受训练问答对与目标语料分布影响。企业知识库可以做 hybrid retrieval；由于 BM25 分数和向量相似度通常不在同一量纲，融合前应使用 rank fusion、归一化或学习式融合，不能直接把原始分数相加。

比较时要分别测：

- 同义改写和跨语言召回；
- 数字、版本号、实体名和代码片段召回；
- 文档库增长后的索引成本；
- 过滤条件、权限和更新延迟；
- top-k 候选的证据支持率。

没有一种检索方式在所有数据上都优于另一种。先用同一查询集检查 dense/sparse 各自漏掉了哪些正例，再决定是否融合；否则增加一条检索支路只会增加索引和查询成本。检索器的目标通常是把相关文档送进候选池，最终证据质量还需要 reranker 和上下文构造共同负责。

## 15.30 Retriever 与 Reranker：先扩大候选，再精排

Retriever 面向大规模文档库快速召回 top-k，通常用 query/document 双编码器或倒排索引，查询和文档可预先独立编码；reranker 对 query-document 对做联合交互建模，再把少量候选排序。[BERT passage reranking](https://arxiv.org/abs/1901.04085) 代表后者以更高的单对计算成本换取精排能力。

若每个问题只需一份 gold evidence，令 `R_retriever=Recall@K`，令 `R_reranker|retrieved` 是 gold 已进入 top-K 后 reranker 将其排进 top-M 的条件概率，则链式法则给出证据进入上下文的概率：

~~~math
P(\text{evidence reaches context})
=
R_{\text{retriever}}
\cdot
R_{\text{reranker}\mid\text{retrieved}}
~~~

例如 `Recall@50=0.90`，正确证据已在候选池时 reranker 把它排入 top-5 的比例是 `0.70`，则证据进入上下文的概率是 `0.90×0.70=0.63`。如果一个问题必须同时找到两份证据，不能把单文档 recall 直接当成任务成功率，还要评估证据集合覆盖和组合关系。Retriever 没召回证据时，reranker 无法凭空补救；候选过多又会增加精排开销与上下文噪声。

排障时分别记录 Recall@K、条件 Recall@M 或 MRR/nDCG，以及生成端的引用支持率。只看最终答案无法区分“没有找到证据”“找到了但排错位”和“上下文已有证据但生成未使用”。

## 15.31 Long Context 与 RAG：容量和选择

长上下文让模型一次接收更多材料，适合完整审阅一份固定文档、跨段综合或合并多步工具结果；RAG 在生成前从大规模外部库中选择相关证据，适合动态知识、海量文档和权限过滤。这里比较的是具体访问路径，不是“长上下文窗口”和“检索系统”二选一；线上可以让检索先定位，再把相关材料放入更长上下文。

长上下文的输入处理成本随 token 数和序列长度增加；而且窗口容量不等于信息利用率。[Lost in the Middle](https://arxiv.org/abs/2307.03172) 在多文档 QA 和 key-value 检索中观察到相关信息处于中间位置时性能会下降，但这是该研究任务和模型范围内的现象。[RAG/Long Context 对照研究](https://arxiv.org/abs/2407.16833) 在 Gemini 1.5 Pro、GPT-4o、GPT-3.5 及所选 LongBench/∞Bench 数据上报告长上下文平均质量占优、RAG 成本更低；[2024 年提交的后续再评估预印本](https://arxiv.org/abs/2501.01880) 过滤了无需外部知识的问题并扩大数据后，发现结果随 QA/对话任务与 chunk/summarization retrieval 变化。两篇均是特定 benchmark 和配置下的作者结果，不构成所有语料的通用排名。RAG 减少生成端输入规模，却把部分错误转移到切块、召回、排序和权限过滤。

两者常常组合：RAG 先选择候选证据，长上下文再容纳证据、历史、工具状态和引用。选择指标包括：

~~~math
\mathrm{TotalCost}
\approx
C_{\mathrm{retrieval}}
+C_{\mathrm{rerank}}
+C_{\mathrm{prefill}}(N_{\mathrm{input}},B,\mathrm{hardware})
+C_{\mathrm{decode}}(N_{\mathrm{output}},L_0,B,\mathrm{hardware})
~~~

`N_input`/`N_output` 是输入/输出 token 数，`L_0` 是开始生成时已有的上下文长度；生成期间 KV 长度随输出增长，`B` 是并发或有效 batch。prefill 和 decode 单位成本会随长度、并发、硬件、kernel、缓存命中和服务收费模型变化，所以上式是账本分解，不是可跨系统套用的线性延迟公式。窗口更大不代表应该把所有材料都塞进去；应比较证据覆盖、回答支持、TTFT/TPOT、尾延迟和成本。

## 15.32 Agent 与 Workflow：动态决策和确定流程

这里把 workflow 定义为程序预设主要控制路径，把 agent 定义为模型根据环境反馈动态选择下一步和工具。[Anthropic 的工程文章](https://www.anthropic.com/engineering/building-effective-agents) 也采用这组区分，并建议先用尽量简单的组合模式；这是团队工程经验，不是统一标准定义。Workflow 的控制路径更容易审计，但其中的 LLM 输出仍可能随机或错误；agent 的动态路径适合步骤难以预先枚举的任务。

Agent 的自由度带来状态漂移、循环、工具误用、提示注入和成本失控。Workflow 的限制则可能无法处理长尾和新任务。生产系统常把高影响关键路径固定为 workflow，把局部搜索、文本归类和候选生成交给模型。

判断一个系统是否值得 Agent 化，可以问：

1. 任务步骤是否稳定；
2. 每个动作能否定义输入和验收条件；
3. 错误是否可回滚；
4. 模型是否真的需要动态选择；
5. 动态自由度带来的收益是否超过验证和监控成本。

Agent 不是 workflow 的升级版本，而是把部分控制权从程序转给模型。控制权越多，越需要权限、预算、状态和人工接管。

## 15.33 Chain-of-Thought 与 Tool Use：内部推理和外部证据

CoT 通过额外 token 表示中间步骤；[原始 CoT 研究](https://arxiv.org/abs/2201.11903) 在算术、常识和符号任务中报告了提示中间步骤带来的性能变化。Tool use 则把计算、检索、代码执行、数据库查询或真实动作交给外部系统；[ReAct](https://arxiv.org/abs/2210.03629) 将 reasoning 与 observation/action 交替组织，让模型拿到环境返回值后再继续。

二者不是互斥的。模型可以先规划，再调用计算器，读取结果后继续生成；关键是区分生成的解释文本、外部证据和执行器返回值。[CoT 忠实性研究](https://arxiv.org/abs/2305.04388) 在若干受控输入扰动下发现，模型可能给出流畅但没有提及真正影响答案的解释。因此 CoT 可用于组织步骤，但不能当作忠实的内部决策记录；实时价格、订单状态、复杂算术和代码测试要检查工具结果。

工具调用增加了权限、延迟、失败和副作用，CoT 增加了 token 成本和潜在信息泄露。比较时要测答案正确、证据支持、工具成功、错误恢复、延迟和敏感内容暴露，而不是只看最终文本是否更长。

## 15.34 Human Evaluation 与 LLM-as-a-Judge：谁来判断开放式质量

人评能接近真实用户或领域专家判断，适合高影响、模糊和需要常识的任务，但成本高、速度慢、标注一致性和疲劳效应需要控制。

LLM-as-a-Judge 可以快速比较大量回答，适合回归、初筛和候选排序，但可能有长度偏好、位置偏好、模型自偏好、语言偏差和事实判断错误。[MT-Bench/Chatbot Arena 研究](https://arxiv.org/abs/2306.05685) 在其 judge、prompt 和题目上测到位置、冗长与自我增强偏差；偏差强度还随题型和候选质量接近程度变化。

一个合理的评估链是：先用自动指标和 judge 扩大覆盖，再用多标注者人工金标准校准 judge，最后把分歧、高影响和新分布样本交给人工。成对比较应隐藏模型身份并交换候选顺序，检查评审结果是否随顺序翻转；同时报告 judge 与人工的一致性、分歧切片和错误类型。

“judge 分数提升”不等于用户体验提升。长度、引用数量和格式都可能被评价器奖励，却没有提高事实性或任务成功。

## 15.35 Accuracy 与 Pass@k：一次正确还是候选中有一个正确

Accuracy 统计单次输出是否正确：

~~~math
\mathrm{Accuracy}
=
\frac{1}{N}\sum_{i=1}^{N}c_i
~~~

`c_i` 是第 i 个样本的一次正确指示。Pass@k 关注候选集合中至少有一个通过测试；HumanEval 原工作用测试执行来判定功能正确，并给出下式的无偏估计。[公式来源](https://arxiv.org/abs/2107.03374) 中的 `n` 是实际抽样候选数、`c` 是通过测试的候选数、`k` 是希望估计的候选预算：

~~~math
\mathrm{pass@}k
=
1-
\frac{\binom{n-c}{k}}{\binom{n}{k}}
~~~

例如抽 `n=10` 个候选，其中 `c=3` 个通过，报告 `pass@5` 的估计为 `1-C(7,5)/C(10,5)=1-21/252≈0.917`。它不是“实际只给用户 5 个答案时必然有 91.7% 成功”的保证，而是基于该次抽样估计随机 `k` 个候选至少一个成功的概率。高 pass@k 可能隐藏单次成功率低、候选生成贵、选择器不会挑正确答案等问题。这里要求 `n>0`、`0≤k≤n` 且 `0≤c≤n`；没有候选或超出候选数时应报告 N/A，而不是用默认分母继续计算。

生产系统若只能给用户一个答案，应同时报告 pass@1、pass@k、候选成本、选择器准确率和端到端延迟。

## 15.36 Factuality 与 Grounding：真实和有证据不是一回事

Factuality 问输出中的事实是否符合目标知识源/现实；grounding 问回答中的具体主张是否被本轮允许使用的文档、图像、音频或工具结果蕴含或支持。二者的参照集不同。[FActScore](https://arxiv.org/abs/2305.14251) 展示了把长回答拆为 atomic facts，再逐条检查是否有可靠来源支持的一种 factuality 评测方式。

一个回答可能是事实正确但没有引用证据，也可能引用了相关文档却夸大了文档没有说的内容。RAG 系统需要分别测：

- 事实是否正确；
- 证据是否覆盖结论；
- 引用片段是否与结论对应；
- 不确定时是否明确降级；
- 外部知识和当前证据冲突时如何处理。

因此，引用存在不等于 grounding 成立，grounding 成立也不自动保证外部事实永久正确。

## 15.37 Robustness 与 Generalization：未见数据和扰动稳定

本章把 generalization 操作性定义为从训练分布迁移到目标测试分布的能力，把 robustness 定义为任务语义按设计应保持时，对改写、噪声、格式变化或受控扰动的稳定性。不同研究对这两个词的边界并不完全一致；在评测中要报告具体 shift/扰动，而不是用术语代替测试集定义。

一个模型可以在同分布测试集上泛化良好，却因为换一种语言、插入无关文本或改变上下文顺序而失败。鲁棒性评估应设计受控扰动：

~~~math
\Delta_{\text{robust}}
=
u(x)-u(T(x))
~~~

T 是保持任务语义的扰动，u 是任务效用。理想情况下差值接近零，但不同扰动的可接受范围不同。

鲁棒性不是无限不变。对输入做强语义改变后，输出改变可能是正确的；因此测试集必须明确哪些字段应该保持不变，哪些字段应该触发不同决策。

## 15.38 Over-Refusal 与 Under-Refusal：安全边界两侧的错误

把真实请求分为“危险/安全”，并把危险类设为 confusion matrix 的正类：Under-refusal 是真实危险请求被模型放行，对应 false negative；over-refusal 是真实安全请求被错误拒绝，对应 false positive。两者分母不同：

~~~math
\mathrm{UnsafePassRate}
=
\frac{FN}{TP+FN}
~~~

~~~math
\mathrm{FalseRefusalRate}
=
\frac{FP}{TN+FP}
~~~

假设 50 个危险请求中有 3 个被放行，则 `UnsafePassRate=3/50=6%`；100 个安全请求中 7 个被拒绝，则 `FalseRefusalRate=7/100=7%`。这两个数必须分别报告，因为只报总拒答率会把数据集中危险/安全请求的比例混进指标。降低一个指标可能使另一个上升。系统应按风险等级设计回答、澄清、替代帮助或升级人工的路径。

只看拒答率会奖励过度保守；只看帮助率会掩盖危险漏放。评估还要包含语言、双重用途、用户授权、工具权限和多轮上下文。

## 15.39 Jailbreak 与 Prompt Injection：攻击模型策略还是污染数据边界

这些术语的分类会重叠。本章用 jailbreak 描述攻击目标——诱导模型绕过安全策略；用 prompt injection 描述把不可信内容伪装成指令、影响模型对指令层级的解释。恶意用户直接输入既可能是 jailbreak，也可被称为 direct prompt injection；网页、邮件或代码注释中的内容属于 indirect prompt injection。[越狱安全训练研究](https://arxiv.org/abs/2307.02483) 分析策略目标冲突和泛化错配，[间接注入研究](https://arxiv.org/abs/2302.12173) 展示检索内容使数据与指令边界模糊后可能形成的应用攻击链。

两者都可能利用角色扮演、编码、上下文拼接和多轮诱导，但间接注入还需要处理数据流和执行器。一个系统即使模型被文档诱导，只要外部内容没有获得工具权限，攻击链仍可能在执行前停止。

因此防御要分开验证文本策略和系统授权：模型策略、输入/输出审核与指令层级训练降低文本层攻击成功；将外部内容标成不可信、使用最小权限、验证工具参数、限制副作用并要求高影响动作确认，降低攻击成功后的执行影响。单一关键词过滤无法替代边界和权限。

## 15.40 Helpful 与 Harmless：帮助不等于无条件满足

Helpful 关注用户任务是否被推进，Harmless 关注回答和行动是否会造成伤害。[Constitutional AI](https://arxiv.org/abs/2212.08073) 将 harmlessness 作为原则引导的反馈目标研究；它不意味着把所有高风险领域请求一律拒绝。双重用途请求最能暴露冲突：网络安全、化学、生物、医疗、金融和法律问题都可能既有防御用途又有滥用路径。

系统不应把 harmless 简化成全量拒绝，也不应把 helpful 简化成提供所有执行细节。更细的响应可以是澄清授权、解释风险、提供防御性方法、给出沙箱实验或拒绝高风险动作。

比较两种策略时应同时看正常任务成功、过度拒答、危险漏放、安全替代质量和用户是否获得了可执行但合法的下一步。安全边界最终要落到工具权限和审计，而不仅是回答语气。

## 15.41 Dense Model 与 MoE：每个 token 使用多少参数

Dense 模型每个 token 经过所有层和该层全部 FFN 参数，结构简单、负载稳定、部署直接；MoE 总专家容量大于每个 token 实际选择的专家数。[Switch Transformer](https://arxiv.org/abs/2101.03961) 将稀疏激活用于扩大参数容量，同时将通信、模型并行复杂度和训练稳定性列为系统挑战。

MoE 的路由概率可写成：

~~~math
p_t=\mathrm{softmax}(W_rh_t),
\qquad
e_t=\mathrm{TopK}(p_t)
~~~

`h_t` 是 token 表示，`W_r` 是 router 参数，`e_t` 是被选择的专家集合。total parameters 是所有专家权重的总存储；active parameters/FLOPs 描述每 token 实际执行的路由专家和共享层计算。实际成本还包含专家容量、跨设备 all-to-all、负载均衡、溢出 token、所有专家权重驻留或加载和专家 checkpoint。

Dense 适合资源和延迟可预测、模型规模中等或硬件不适合动态路由的场景；MoE 适合用较大总容量换取每 token 较低激活计算，但通信和服务调度更复杂。

比较时至少报告 total parameters、active parameters、每 token FLOPs、通信量、专家负载分布、显存和尾延迟。MoE 的“激活参数少”不等于部署成本一定低。

## 15.42 一张比较表怎样写才不误导

表格适合放已定义的差异，不适合藏住未经说明的结论。一个可复用的结构是：

### 演练：企业客服知识库该微调还是做 RAG

假设一个客服助手要回答每周更新的产品政策。不同客服只能访问各自客户的合同，回答必须引用适用版本；模型还要输出固定 JSON，遇到无证据的问题要转人工。这是一个教学场景，不代表某家产品的标准架构。

先把“知识事实”和“模型行为”拆成两个变量：

| 需求 | 更直接的机制 | 必须验收什么 |
| --- | --- | --- |
| 政策更新、版本生效和逐条撤回 | 将版本化政策留在受 ACL 保护的知识源，查询时做授权过滤和 RAG | 新版本召回率、过期文档误召回、引用支持率、更新生效延迟 |
| 客服身份对应的合同权限 | 在检索服务端按已认证主体过滤候选，过滤结果再进入 reranker/模型 | 跨租户泄漏率、无权限文档是否进入日志和上下文 |
| 固定 JSON、字段解释和澄清步骤 | 先用 schema/程序校验与少量示范；行为持续不稳定时再用 SFT | schema 成功率、字段级准确率、澄清后任务成功率 |
| 同样事实下的语气与偏好 | 有代表性 pairwise preference 时比较 DPO 等偏好优化 | 人工盲评一致性、拒答回归、长度/位置偏差 |

因此不会把全部政策知识微调进参数，也不会期待 RAG 自动教会模型遵守 JSON。一次请求可以按“认证用户 → ACL 检索 → 精排 → 带版本/来源的证据进入上下文 → 模型生成 JSON → 程序检查 schema 和引用”执行。若新政策没有出现在 top-K，先查索引更新时间、切块和召回；若政策已经入上下文而模型答错，查证据阅读、冲突消解和生成行为；若其他租户文档进入候选，则是权限过滤故障，不能靠提示词补救。RAG 的知识访问和参数微调的行为适配可以组合，验收指标也必须分开。

| 比较维度 | 方法 A | 方法 B | 仍需验证的条件 |
| --- | --- | --- | --- |
| 解决的问题 | 它首先优化什么 | 它首先优化什么 | 任务是否相同 |
| 主要机制 | 改数据、参数、连接或运行时 | 改数据、参数、连接或运行时 | 是否有额外预算 |
| 资源代价 | 显存、通信、延迟、人工成本 | 显存、通信、延迟、人工成本 | 硬件和并发 |
| 失败模式 | 哪些输入会失效 | 哪些输入会失效 | 是否可回滚 |
| 适用边界 | 适合什么 workload | 适合什么 workload | 线上切片是否一致 |
| 评估证据 | 用什么指标和对照 | 用什么指标和对照 | 分母、样本和版本 |

如果表格中的“更快”“更稳定”“更准确”没有对应的 workload 和测量口径，它们只是宣传词。正文应在表格之前解释机制，在表格之后说明如何验证。

## 本章小结

方法比较的核心不是找到一个永远更优的选项，而是理解约束如何在系统中移动。AdamW 把衰减从自适应梯度中分离，RMSNorm 减少归一化路径，GQA 减少 KV head，LoRA 减少可训练更新，量化减少数值位宽，FlashAttention 减少内存 IO，PagedAttention 管理跨请求缓存，ZeRO/FSDP 用通信换状态显存，RAG 把知识放到外部索引，Agent 把部分控制权交给模型。

这些变化都伴随着新代价：质量回归、通信、缓存生命周期、数据新鲜度、工具副作用、评估器偏差或安全风险。真正可靠的结论必须同时说明机制、资源账本、失败模式、适用边界和验证方法。这样，比较表才是知识的入口，而不是把复杂问题压扁成一句“谁更好”。
