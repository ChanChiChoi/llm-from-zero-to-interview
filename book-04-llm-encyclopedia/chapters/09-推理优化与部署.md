# I. 推理优化与部署：把一次生成变成可运行的系统

## 阅读边界：从模型前向到线上平台

第 8 章讨论了模型如何从 next-token 概率中选择输出。本章继续向外展开：同一个模型怎样接收请求、安排 prefill 和 decode、管理 KV Cache、组织 batch、压缩权重、跨 GPU 运行，并在发布后保持延迟、质量、安全和成本可解释。

推理服务不是把 model.generate 包在一个 HTTP handler 里。一次请求会经历鉴权、模板拼接、tokenization、排队、prefill、decode、采样、流式发送和资源释放；每一层都有自己的状态和失败方式。优化一个局部 kernel，也可能因为队列、KV Cache、网络或回滚策略而没有用户可见收益。

本章把生产部署看成一条证据链：

~~~text
请求画像
 -> 生命周期与阶段计时
 -> batching 与调度
 -> KV Cache 容量
 -> kernel / 精度 / 并行
 -> runtime 与模型路由
 -> 扩缩容与保护
 -> 发布、观测与故障恢复
~~~

文中的公式用于建立数量级和变量关系，代码用于演示最小状态转换或账本计算。它们不能替代目标硬件上的压测。尤其要区分三个结论：理论字节数、框架实现的行为、真实业务流量下的实测结果。

## 9.1 请求生命周期：推理服务到底在管理什么

### 先从一个请求的时间线开始

用户发送一段对话文本，服务端不能立即把它交给 GPU。首先要确认身份、模型版本和输入是否允许；然后把 system、user、assistant 角色按模板序列化，再交给 tokenizer。token ids 进入队列以后，调度器决定什么时候做 prefill，模型建立 KV Cache 后才开始 decode。每生成一个 token，输出处理器要检查 EOS、stop sequence 和最大长度，再决定是否向客户端发送增量事件。

一个简化的状态链是：

~~~text
RECEIVED
 -> VALIDATED
 -> TOKENIZED
 -> WAITING
 -> PREFILLING
 -> DECODING
 -> STREAMING
 -> FINISHED / ABORTED / FAILED / TIMEOUT
 -> CLEANED
~~~

真实实现可能把 STREAMING 视为 DECODING 的一个输出状态，但资源语义不能省略：请求是否占用 running slot，KV block 是否仍被引用，客户端是否已经断开，都是后续调度必须知道的事实。

### 对初学者而言，最重要的是状态和资源同时变化

一个请求不仅有文本，还有一组随时间变化的资源：

~~~text
输入 token 与输出 token
当前生成位置
KV Cache block 或连续缓存
running slot
stream queue
模型、tokenizer、模板和采样配置
租户、权限和截止时间
~~~

如果只保存 prompt 和最终文本，就无法解释“为什么首 token 变慢”“为什么取消后显存没有下降”“为什么同一 prompt 在不同版本输出不同”。服务日志必须记录事件，而不是只记录最终结果。

### 专家的阶段账本

设一次请求的阶段耗时为：

~~~math
T_{\mathrm{e2e}}
=T_{\mathrm{auth}}
+T_{\mathrm{route}}
+T_{\mathrm{queue}}
+T_{\mathrm{tokenize}}
+T_{\mathrm{prefill}}
+T_{\mathrm{decode}}
+T_{\mathrm{stream}}
+T_{\mathrm{post}}.
~~~

第一个可见 token 的时间通常近似为：

~~~math
T_{\mathrm{TTFT}}
=T_{\mathrm{auth}}
+T_{\mathrm{route}}
+T_{\mathrm{queue}}
+T_{\mathrm{tokenize}}
+T_{\mathrm{prefill}}
+T_{\mathrm{first\ decode}}
+T_{\mathrm{first\ flush}}.
~~~

如果输出包含 N 个 token，且第一个 token 到达时间为 t_1，最后一个 token 到达时间为 t_N，则常见的后续 token 平均间隔为：

~~~math
T_{\mathrm{TPOT}}
=\frac{t_N-t_1}{N-1},
\qquad N>1.
~~~

不同系统可能把首 token 也放入平均值，因此报告 TPOT 时必须给出时间戳定义。把不同口径的 TPOT 放在同一张表里，会制造一种不存在的性能差异。

### 最小生命周期账本

~~~python
from dataclasses import dataclass, field


@dataclass
class Request:
    request_id: str
    state: str = "RECEIVED"
    events: list = field(default_factory=list)
    kv_blocks: int = 0

    def __post_init__(self):
        if not self.request_id:
            raise ValueError("request_id must not be empty")
        if self.kv_blocks < 0:
            raise ValueError("kv_blocks must be non-negative")

    def move(self, state, detail=""):
        if state not in {
                "RECEIVED", "VALIDATED", "TOKENIZED", "WAITING",
                "PREFILLING", "DECODING", "STREAMING", "FINISHED",
                "ABORTED", "FAILED", "TIMEOUT", "CLEANED",
        }:
            raise ValueError("unknown request state")
        self.state = state
        self.events.append((state, detail))

    def cleanup(self):
        self.kv_blocks = 0
        self.move("CLEANED")


request = Request("r-001")
request.move("VALIDATED", "schema_ok")
request.move("WAITING", "queue_depth=3")
request.kv_blocks = 4
request.move("PREFILLING", "input_tokens=512")
request.move("DECODING", "step=1")
request.move("FINISHED", "reason=eos")
request.cleanup()

print(request.state, request.events)
assert request.state == "CLEANED"
assert request.kv_blocks == 0
~~~

这个例子没有执行模型，却暴露了一个重要不变量：终态不是资源释放完成的同义词。FINISHED 只说明模型不再需要生成，CLEANED 才说明 KV、slot 和流式状态已经回收。线上取消、超时和模型异常也必须走同一类清理路径。

## 9.2 工作负载、吞吐与延迟：为什么 QPS 不够用

### 请求数不是计算量

一个输入 20 token、输出 10 token 的分类请求，与一个输入 32,000 token、输出 4,000 token 的长文请求，都算一次 QPS，但它们消耗的 prefill、decode、KV 和网络资源完全不同。LLM 服务应该至少保存以下工作负载画像：

~~~text
请求到达率与突发形状
输入 token 分布
输出 token 分布
上下文长度分布
长短请求比例
共享前缀比例
租户和优先级
streaming 与非 streaming 比例
工具或外部依赖等待时间
~~~

把请求转换为 token 负载后，吞吐可以分别报告：

~~~math
R_{\mathrm{input}}
=\frac{\sum_i x_i}{\Delta t},
\qquad
R_{\mathrm{output}}
=\frac{\sum_i y_i}{\Delta t},
\qquad
R_{\mathrm{total}}
=\frac{\sum_i(x_i+y_i)}{\Delta t}.
~~~

其中 `\Delta t>0` 是统计窗口，`x_i` 是输入 token 数，`y_i` 是输出 token 数。prefill 更接近输入 token 负载，decode 更接近输出 token 负载，但真实 GPU 利用率还受 batch 形状、缓存命中和 kernel 影响。

### 延迟必须分位数化

平均 TTFT 可能是 200 ms，但 1% 的长请求可能要等 8 秒。交互服务通常至少同时观察 P50、P95 和 P99，并按输入长度、输出长度、模型版本、租户和实例分桶。长尾不是统计噪声：队列堆积、KV block 不足、跨节点传输和慢客户端都可能只影响少数请求，却严重影响体验。

吞吐和延迟还存在结构性冲突。增大 batch 可能提高 GPU 的 token 吞吐，但排队和每步工作量也会增加；连续批处理可能提高总产能，但某个请求的 TPOT 可能变差。因而“更快”必须说明是单请求延迟更低，还是单位时间完成的 token 更多。

### Little 定律的适用边界

在稳定、近似平稳的系统中，可以用 Little 定律建立粗略关系：

~~~math
N_{\mathrm{active}}
\approx
\lambda_{\mathrm{request}}W_{\mathrm{request}}.
~~~

它说明到达率不变时，平均请求时延增加会推高在途请求数，进而推高 KV 占用。LLM 场景不能把它当成精确容量公式，因为每个请求的 token 成本不同、输出长度是随机的，系统还有优先级、拒绝和分阶段队列；它更适合帮助发现“延迟上升会反过来占满资源”的反馈回路。

### 单位成功任务成本

只比较每千 token 成本可能奖励一个经常输出错误答案的系统。更有意义的指标是：

~~~math
C_{\mathrm{success}}
=\frac{C_{\mathrm{gpu}}+C_{\mathrm{network}}+C_{\mathrm{storage}}+C_{\mathrm{ops}}}
{N_{\mathrm{successful\ tasks}}},
\qquad N_{\mathrm{successful\ tasks}}>0.
~~~

成功必须按任务定义，例如代码测试通过、结构化字段通过业务校验、答案得到人工或独立 verifier 支持。若评估窗口内没有成功任务，单位成功任务成本应记录为 `unknown`，而不是用零或一个极小分母制造数字。模型输出越长、best-of-N 候选越多、工具重试越频繁，分子都会增加。

### 用 token 画像做一个容量摘要

~~~python
def workload_summary(requests):
    if not requests:
        raise ValueError("requests must not be empty")
    for item in requests:
        if not isinstance(item, dict):
            raise ValueError("each request must be a dictionary")
        if set(item) != {"input_tokens", "output_tokens"}:
            raise ValueError("request token fields are incomplete or unknown")
        if (not isinstance(item["input_tokens"], int)
                or not isinstance(item["output_tokens"], int)
                or item["input_tokens"] < 0
                or item["output_tokens"] < 0):
            raise ValueError("token counts must be non-negative integers")
    input_tokens = sum(item["input_tokens"] for item in requests)
    output_tokens = sum(item["output_tokens"] for item in requests)
    long_requests = sum(item["input_tokens"] >= 4096 for item in requests)
    return {
        "requests": len(requests),
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "avg_input": input_tokens / len(requests),
        "avg_output": output_tokens / len(requests),
        "long_ratio": long_requests / len(requests),
    }


summary = workload_summary([
    {"input_tokens": 120, "output_tokens": 40},
    {"input_tokens": 5000, "output_tokens": 300},
    {"input_tokens": 800, "output_tokens": 90},
])
print(summary)
assert summary["input_tokens"] == 5920
assert summary["long_ratio"] == 1 / 3
~~~

这个摘要仍然不足以做最终规划，因为它没有包含到达时间、burst、共享前缀和 P99。它的价值在于把“请求很多”改写成可以和阶段耗时、KV 容量、成本对应的 token 事实。

## 9.3 Batching 与调度：把不同生命周期的请求放在一起

### 静态 batch 为什么在生成任务中浪费

分类模型的 batch 往往一次 forward 就结束。生成模型的请求在不同时间结束：短回答已经生成 EOS，长回答还需要数百步；如果固定 batch 直到最长请求结束，已经完成的行会变成空洞。输入长度不同还会引入 padding，短 prompt 的 prefill 可能在无效 PAD 上浪费计算。

动态 batching 在短时间窗口收集新请求后组成 batch，适合单轮或短任务；continuous batching 则把调度粒度降到每一个模型 iteration：本轮结束的请求退出，等待中的请求在后续 iteration 进入。它解耦了请求生命周期和 batch 生命周期，但也把 KV 映射、位置、采样参数和清理复杂度带进了 scheduler。

### 调度器真正要决定的事

每一轮调度至少要决定：

~~~text
哪些请求继续 decode
哪些请求开始或继续 prefill
本轮允许处理多少 token
哪些请求因 KV 不足而等待
完成或取消的请求如何释放资源
新请求何时加入而不破坏 TPOT
长短请求和租户优先级如何平衡
~~~

不能只用请求数做 batch 限制。一个更接近真实系统的预算向量是：

~~~math
\mathbf{b}
=(B_{\mathrm{seq}},
B_{\mathrm{token}},
B_{\mathrm{prefill}},
B_{\mathrm{kv}},
B_{\mathrm{priority}}).
~~~

它分别约束活跃序列数、单轮 token 数、单轮 prefill token、KV block 或字节预算，以及不同优先级的资源份额。某一项先达到上限，都可能阻止更多请求进入本轮。

### Prefill 与 decode 的公平性

decode 请求已经向用户发出部分结果，过度延迟会直接表现为流式卡顿；prefill 请求如果永远等待，又会造成首 token 饥饿。常见策略是 decode-first，再为 prefill 设置有界 token 预算；长 prompt 可以切成 chunk，在多个 iteration 中逐步处理，让短请求有机会插入。

这不是一个固定最优顺序。交互流量偏多时，decode-first 通常更重要；离线长文生成偏多时，吞吐和大 prefill batch 可能更重要。调度策略必须通过 TTFT、TPOT、队列等待、有效 token 吞吐和长短请求分桶来比较。

### 一个有界 token scheduler

~~~python
def schedule(waiting, running, max_sequences, max_tokens):
    if (not isinstance(max_sequences, int)
            or not isinstance(max_tokens, int)
            or max_sequences <= 0 or max_tokens <= 0
            or not isinstance(waiting, list)
            or not isinstance(running, list)
            or len(running) > max_sequences):
        raise ValueError("scheduler limits and queues are invalid")
    selected_decode = list(running)
    used = len(selected_decode)
    selected_prefill = []
    deferred = []
    for request in waiting:
        if (not isinstance(request, dict)
                or not isinstance(request.get("id"), str)
                or not request["id"]
                or not isinstance(request.get("prefill_tokens"), int)
                or request["prefill_tokens"] < 0):
            raise ValueError("invalid waiting request")
        if len(selected_decode) + len(selected_prefill) >= max_sequences:
            deferred.append((request["id"], "sequence_limit"))
            continue
        if used + request["prefill_tokens"] > max_tokens:
            deferred.append((request["id"], "token_limit"))
            continue
        selected_prefill.append(request)
        used += request["prefill_tokens"]
    return selected_decode, selected_prefill, deferred


decode, prefill, deferred = schedule(
    waiting=[
        {"id": "long", "prefill_tokens": 700},
        {"id": "short", "prefill_tokens": 100},
    ],
    running=["r0"],
    max_sequences=3,
    max_tokens=500,
)
print(decode, prefill, deferred)
assert [item["id"] for item in prefill] == ["short"]
assert deferred == [("long", "token_limit")]
~~~

示例先保护已有 decode，再用剩余 token 预算接收 prefill。生产 scheduler 还要加入优先级、KV block 预算、取消、超时和 aging；如果只按队列顺序，长请求可能占满预算，短请求的 P99 会持续恶化。

## 9.4 KV Cache：推理系统的动态显存账本

### 缓存保存什么

Transformer attention 为历史 token 计算 Key 和 Value。自回归 decode 时，新的 Query 要读取这些历史 K/V；KV Cache 保存每层已经算过的 K/V，使后续步骤不必重新投影所有历史 token。它不保存模型权重，也不等于保存完整 hidden state。

设 batch 为 B，层数为 L，平均缓存长度为 S，K/V head 数为 H_kv，每个 head 维度为 D_h，每个元素占 b 字节，则一个数量级估算是：

~~~math
M_{\mathrm{KV}}
\approx
2BLSH_{\mathrm{kv}}D_hb.
~~~

2 来自 K 和 V。这个公式没有包含 block table、对齐、临时 workspace、量化 scale、框架碎片和 CUDA graph，因此它只能给出基本容量，不能直接等于 nvidia-smi 上的可用空间。

### MHA、MQA 与 GQA 的差别落在显存上

MHA 让每个 query head 有对应 K/V head，H_kv 等于 H_q；MQA 让所有 query head 共享一组 K/V；GQA 把 query heads 分成若干组，每组共享一组 K/V。对于相同 B、L、S、D_h 和 dtype，KV 显存与 H_kv 线性相关。

如果 H_q=32，GQA 使用 H_kv=8，理论缓存约为 MHA 的四分之一。但这不是无条件收益：模型架构需要在训练时支持对应 head 分组，kernel 要支持该 shape，质量和吞吐也要实测。

### Cache 的生命周期

~~~text
prefill：为输入 token 建立 cache
decode：每步追加新 token 的 K/V
共享前缀：多个请求引用同一批只读 blocks
完成或取消：减少引用并释放私有 blocks
压力上升：淘汰可重算的缓存，必要时暂停或重算请求
~~~

active decode 所需的 K/V 不能像普通缓存一样随意淘汰。cached-free block 可以丢弃并重算，active block 丢失则需要保存完整上下文和位置状态才能恢复。把“缓存命中率”作为唯一目标，会与在线执行的正确性和 TPOT 发生冲突。

### KV pressure

可用 KV 预算为 B_kv，当前或峰值占用为 M_kv，可以定义压力比：

~~~math
\rho_{\mathrm{KV}}
=\frac{M_{\mathrm{kv}}}{B_{\mathrm{kv}}}.
~~~

这里要求可用预算 `B_{\mathrm{kv}}>0`。当 rho 接近 1 时，系统可能先出现 block 分配失败、排队和 preemption，之后才是 OOM。工程上应为不同请求类型保留余量，并把长上下文、best-of-N、工具轨迹和 streaming 未清理都纳入压力分析。

### KV 账本示例

~~~python
def kv_bytes(batch, layers, tokens, kv_heads, head_dim, element_bytes):
    values = (batch, layers, tokens, kv_heads, head_dim, element_bytes)
    if (not all(isinstance(value, int) for value in values)
            or not all(value > 0 for value in values)):
        raise ValueError("KV dimensions must be positive integers")
    return 2 * batch * layers * tokens * kv_heads * head_dim * element_bytes


mha = kv_bytes(2, 32, 4096, 32, 128, 2)
gqa = kv_bytes(2, 32, 4096, 8, 128, 2)
print("mha_mib=", mha / 2**20)
print("gqa_mib=", gqa / 2**20)
print("ratio=", gqa / mha)
assert gqa / mha == 0.25
~~~

这个算式只统计 K/V 本体。容量规划还要减掉权重、activation、通信 buffer 和 runtime 保留空间，再按目标并发与长度分布做压测。

## 9.5 PagedAttention 与 Prefix Cache：把连续序列改成可管理的块

### 连续缓存的浪费从哪里来

如果每个请求都按照最大上下文长度连续预留 KV，实际输出提前结束时，尾部空间一直闲置；请求长度不同还会制造难以复用的碎片。按固定 block size q 分配时，一个长度为 s 的序列需要：

~~~math
n_{\mathrm{block}}=\left\lceil\frac{s}{q}\right\rceil
~~~

其中序列长度 `s\geq0`、block size `q>0`。它需要 `n_{\mathrm{block}}` 个物理 block。最后一个 block 的内部空洞为：

~~~math
w(s)=
\begin{cases}
0,&s\bmod q=0,\\
q-(s\bmod q),&\text{otherwise}.
\end{cases}
~~~

小 block 减少尾部浪费，却增加 block table、地址翻译和 kernel 元数据；大 block 降低管理成本，却可能浪费更多尾部空间。block size 是内存与计算之间的参数，不是越小越好。

### 逻辑位置与物理地址

PagedAttention 的关键不是改变 attention 的概率公式，而是把逻辑序列位置映射到非连续物理 block。对 token 位置 p：

~~~math
\ell=\left\lfloor\frac{p}{q}\right\rfloor,
\qquad
o=p\bmod q,
\qquad
\mathrm{physical}=\mathrm{block\_table}[\ell].
~~~

kernel 通过 block table 找到 physical block，再读取 offset 为 o 的 K/V。请求增长时只需申请新的 block，不要求一段连续的大显存。

### Prefix cache 需要比“文本相同”更严格

公共 system prompt、工具说明、RAG 文档或对话历史可以复用前缀 K/V，但前缀复用的前提是 token 序列和 forward 条件一致。缓存指纹至少要考虑：

~~~text
模型与权重版本
tokenizer 与 chat template
LoRA / adapter
位置编码与上下文配置
多模态媒体内容
租户与权限域
安全策略与数据版本
~~~

完整 block 才容易安全复用；最后一个 partial block 通常需要继续 prefill。共享 block 要有引用计数，不能因为一个请求结束就释放仍被其他请求使用的前缀。

### 命中率不是收益率

如果命中率高但命中的前缀很短，节省的 prefill token 可能很少；如果命中导致租户隔离变弱，任何性能收益都不可接受。应同时记录：

~~~math
R_{\mathrm{prefix}}
=\frac{N_{\mathrm{hit\ tokens}}}{N_{\mathrm{input\ tokens}}},
\qquad
S_{\mathrm{prefill}}
=N_{\mathrm{hit\ tokens}}\times
\overline{t}_{\mathrm{prefill/token}}.
~~~

还要记录缓存占用、驱逐次数、错误复用次数和命中后的实际 TTFT 变化。

### 一个 block table 与共享引用的例子

~~~python
def locate(position, block_size, table):
    if (not isinstance(position, int) or position < 0
            or not isinstance(block_size, int) or block_size <= 0
            or not table or any(not isinstance(block, int) or block < 0
                                 for block in table)):
        raise ValueError("position, block size and table are invalid")
    logical = position // block_size
    offset = position % block_size
    if logical >= len(table):
        raise IndexError("position is outside the block table")
    return table[logical], offset


block_table = [7, 2, 11]
print(locate(9, 4, block_table))
assert locate(9, 4, block_table) == (11, 1)

refs = {7: 2, 2: 1, 11: 1}
refs[7] -= 1
released = [block for block, count in refs.items() if count == 0]
print("released=", released)
assert released == []
~~~

第一个请求结束后，物理 block 7 仍有一个引用，因此不能回收到 free list。这个小例子正是 prefix sharing 中最容易被忽略的资源不变量。

## 9.6 FlashAttention、IO 复杂度与显存带宽

### 为什么 FLOPs 不是完整答案

标准 attention 的核心乘法是 QK^T 和 AV，但如果把完整注意力矩阵物化到 HBM，读写量会随序列长度平方增长。GPU 的峰值算力很高，HBM 与片上 SRAM/register 的访问速度却差异显著。一个算子即使 FLOPs 不变，也可能因为少写几次中间矩阵而明显变快。

FlashAttention 使用 tiling，把 Q、K、V 分块加载到更快的片上存储中，计算一块 attention 后立即更新输出，不保存完整的注意力矩阵。它是精确 attention 的 IO-aware 实现，不是把 softmax 改成近似算法。

### Online softmax 如何保持精确

对一个 query 行，分块计算 score。处理到当前 block 时，维护已见 score 的最大值 m 和指数和 l。新 block 的最大值为 m_b，则：

~~~math
m_{\mathrm{new}}=\max(m,m_b),
~~~

~~~math
l_{\mathrm{new}}
=e^{m-m_{\mathrm{new}}}l
+\sum_j e^{s_j-m_{\mathrm{new}}}.
~~~

已经累积的输出也按旧最大值和新最大值重新缩放，再加上当前 block 的加权 V。这样既避免指数溢出，又无需把所有 score 放到 HBM 中。

### Decode 为什么常见带宽瓶颈

decode 每一步的 query token 很少，却要读取大量权重和历史 KV；当 batch 较小时，矩阵乘法的计算密度不足，GPU 算力可能没有吃满。量化减少权重字节数，GQA 减少 KV 读取，fused kernel 减少中间张量，batch 增大可以提高复用，但都会带来质量、显存或延迟取舍。

### FlashInfer 不在同一层

FlashAttention、FlashInfer 这类 kernel/backend 组件，负责某些 attention、KV、sampling 或 layout 的高效实现；vLLM、SGLang、TGI 和 TensorRT-LLM 还要负责请求状态、调度、API、streaming、版本和资源治理。把 kernel library 称作完整 serving engine，会掩盖系统边界。

### 分块 softmax 的教学计算

~~~python
import math


def block_softmax(values, block_size):
    if (not values or any(not math.isfinite(value) for value in values)
            or not isinstance(block_size, int) or block_size <= 0):
        raise ValueError("values and block_size are invalid")
    maximum = float("-inf")
    normalizer = 0.0
    for start in range(0, len(values), block_size):
        block = values[start:start + block_size]
        block_max = max(block)
        new_max = max(maximum, block_max)
        normalizer = (
            math.exp(maximum - new_max) * normalizer
            + sum(math.exp(value - new_max) for value in block)
        )
        maximum = new_max
    return maximum, normalizer


maximum, normalizer = block_softmax([1.0, 3.0, -2.0, 2.0], 2)
expected = sum(math.exp(value - maximum)
               for value in [1.0, 3.0, -2.0, 2.0])
print(maximum, round(normalizer, 6))
assert abs(normalizer - expected) < 1e-9
~~~

这里没有计算 AV，只演示 online softmax 的全局最大值和归一化分母如何跨 block 累积。真实 kernel 还要处理 mask、head、stride、低精度和不同硬件的 tile shape。

## 9.7 vAttention 与连续虚拟地址：PagedAttention 之外的路线

### 两种内存抽象

PagedAttention 让 kernel 明确读取非连续 physical blocks，block table 是执行路径的一部分。vAttention 则试图保留连续的虚拟 KV 地址视图，利用 GPU virtual memory management 按需映射物理显存。上层看到的序列可以保持连续，底层物理页可以动态分配和回收。

两条路线都在解决 KV Cache 的动态长度和碎片问题，但工程代价不同：

~~~text
PagedAttention：kernel 感知 block table，生态与调度集成直接
vAttention：保持连续虚拟视图，减少对上层 kernel 的侵入
PagedAttention：需要处理 block size、地址翻译和页表元数据
vAttention：依赖 VMM 能力、映射开销和平台支持
~~~

不能仅凭论文中的 kernel 结果判断哪条路线更适合生产。需要比较模型结构、硬件驱动、VMM 支持、kernel 改造范围、prefix sharing、抢占、跨进程和故障恢复。

### 什么时候替代路线有价值

如果已有大量连续 KV kernel，改造成显式 block table 的代价很高，连续虚拟视图可能降低迁移成本；如果 runtime 已围绕 block manager、prefix cache 和非连续访问优化，PagedAttention 的系统协同收益可能更高。路线选择还要考虑多级 KV、跨节点迁移和调试工具，而不只是单步 attention 时间。

### 虚拟页映射的教学账本

~~~python
def map_virtual_pages(virtual_pages, physical_free_list):
    if (not isinstance(virtual_pages, list)
            or not isinstance(physical_free_list, list)
            or not virtual_pages
            or len(physical_free_list) < len(virtual_pages)
            or len(set(virtual_pages)) != len(virtual_pages)
            or len(set(physical_free_list)) != len(physical_free_list)
            or any(not isinstance(page, int) or page < 0
                   for page in virtual_pages + physical_free_list)):
        raise ValueError("page lists must be non-empty, unique and aligned")
    return dict(zip(virtual_pages, physical_free_list))


mapping = map_virtual_pages(
    virtual_pages=[0, 1, 2],
    physical_free_list=[9, 4, 12],
)
print(mapping)
assert mapping[1] == 4
~~~

这个字典模型没有模拟 GPU VMM，只说明“连续逻辑页”和“物理页”可以分开管理。真正系统还要处理映射更新、TLB 或页表成本、同步、引用计数、异步释放和 active decode 的安全性。

## 9.8 量化：用精度换显存、带宽与部署范围

### 四个容易混淆的对象

量化可能作用于权重、激活、KV Cache 或中间计算。weight-only 量化只压缩权重，激活通常在较高精度下计算；activation quantization 还要处理运行时分布；KV quantization 直接影响长上下文和并发显存；计算 dtype 则决定矩阵乘法的累加和输出精度。

FP32、FP16、BF16、FP8 是浮点格式，INT8、INT4 是整数表示。FP16 的指数范围小于 BF16，BF16 的指数范围接近 FP32 而尾数较短；FP8 需要 scale 管理和硬件支持。不能把“位数更低”直接等同于“速度更快”，速度取决于 kernel 是否能原生利用该格式。

### PTQ 与 QAT

Post-Training Quantization 在训练完成后用校准数据估计 scale 或敏感性，成本低，适合快速部署；Quantization-Aware Training 在训练或微调过程中模拟量化误差，让模型适应低精度，代价是需要额外训练。

对一组权重 w 使用简单对称量化，可以写成：

~~~math
s=\frac{\max |w|}{q_{\max}},
\qquad
\hat w=s\cdot\operatorname{clip}
\left(\operatorname{round}\frac{w}{s},-q_{\max},q_{\max}\right).
~~~

当 `\max|w|=0` 时应采用显式的零张量分支，而不是让 `s=0` 进入除法；实际方法还会使用 per-channel、per-group、非对称 zero point、异常值保护和不同的误差目标。

### GPTQ、AWQ 与校准分布

GPTQ 利用近似二阶信息，在逐层或分组量化时补偿权重误差；AWQ 通过校准样本中的激活统计识别更敏感的权重或通道，优先保护它们。两者都不是“4 bit 无损压缩”，结果依赖校准数据、分组大小、权重格式、kernel、模型架构和任务。

校准集不能只包含短英文问答。长上下文、多语言、代码、数学、结构化输出和真实业务格式都会影响激活范围。最好保存校准集版本，并在量化前后用同一组切片比较困惑度、生成质量、代码测试、数学 verifier、格式解析率和安全行为。

### 量化误差实验

~~~python
import math


def symmetric_quantize(values, bits):
    if (not values or any(not math.isfinite(value) for value in values)
            or not isinstance(bits, int) or bits < 2):
        raise ValueError("values must be finite and bits must be at least 2")
    qmax = 2 ** (bits - 1) - 1
    scale = max(abs(value) for value in values) / qmax
    if scale == 0:
        return [0 for _ in values], 1.0
    quantized = [
        max(-qmax, min(qmax, round(value / scale)))
        for value in values
    ]
    return quantized, scale


weights = [-1.2, -0.35, 0.1, 0.8]
quantized, scale = symmetric_quantize(weights, bits=4)
restored = [value * scale for value in quantized]
mse = sum((a - b) ** 2 for a, b in zip(weights, restored)) / len(weights)
print(quantized, round(scale, 4), round(mse, 6))
assert len(restored) == len(weights)
assert mse >= 0
~~~

这只是 per-tensor 对称量化的教学版本。它没有处理异常值和真实矩阵乘法，因此不能用 toy MSE 推断某个模型的下游退化。真正的部署结论必须包含目标 hardware、kernel 和任务切片。

### 量化上线的失败边界

低比特权重可能降低显存，却因为解量化 kernel 或不匹配的 layout 增加延迟；KV 量化可能提高并发，却伤害长上下文检索和生成稳定性；FP8 可能在新硬件上有效，在旧 GPU 上只是转换开销。每个量化包都应该绑定模型、tokenizer、runtime、校准数据、计算 dtype 和回滚版本。

## 9.9 Runtime、kernel 与平台：不要把不同层混成排行榜

### 三层边界

可以把部署系统分成三层：

~~~text
kernel / backend：attention、GEMM、sampling、KV layout 的设备实现
serving engine：请求状态、batch、scheduler、KV manager、streaming、generate
platform control plane：模型注册、路由、配额、发布、扩缩容、观测和计费
~~~

FlashAttention、FlashInfer 偏第一层；vLLM、SGLang、TGI、TensorRT-LLM 偏第二层，但边界会随集成方式变化；Triton Inference Server 偏通用模型服务控制和后端托管，LLM 仍需要生成式后端处理 KV、流式和动态调度。一个系统可能同时使用 Triton、TensorRT-LLM 和自定义 scheduler，名称不能代替架构分析。

### 常见 runtime 的生态位置

vLLM 的代表性路线是高吞吐通用 serving、Paged KV 和 continuous batching；SGLang 把复杂 LLM program、前缀复用和结构化生成纳入 runtime；TensorRT-LLM 深度利用 NVIDIA kernel、量化和并行能力；TGI 连接 Hugging Face 模型生态与生成服务；Triton 提供多后端、多模型和协议基础设施。实际支持矩阵、版本状态和特定模型适配必须以当前文档和目标环境为准。

选型应从 workload 反推：

~~~text
独立短问答：看 TTFT、TPOT、并发与部署简单度
共享长 system prompt：看 prefix cache 与租户隔离
多步 agent program：看状态复用、结构化输出和工具等待
大模型多 GPU：看 TP/PP/EP、拓扑与故障恢复
极低延迟：看硬件原生 kernel、warm pool 与 p99
多模型平台：看 API、路由、版本、配额和运维边界
~~~

### 不能只比较单点 tokens/s

公平 benchmark 要固定模型权重、精度、tokenizer、模板、硬件、并行方式、输入输出分布、并发、流式模式和 warm-up。还要记录：

~~~text
TTFT P50 / P95 / P99
TPOT P50 / P95 / P99
input / output tokens per second
KV 峰值与 preemption
prefix hit 与节省的 prefill token
错误、超时、取消和 OOM
版本升级后的质量切片
~~~

如果一个 runtime 的吞吐更高，却使长 prompt 的 TTFT P99 或结构化输出解析率下降，就不能称为普遍更优。

### 一个可解释的 runtime 选择器

~~~python
def choose_runtime(workload):
    required = {
        "general_online", "paged_kv", "programs", "shared_branches",
        "nvidia_optimized", "low_latency", "multi_backend",
    }
    if (not isinstance(workload, dict)
            or set(workload) != required
            or not all(isinstance(value, bool) for value in workload.values())):
        raise ValueError("runtime workload flags are invalid")
    candidates = []
    if workload["general_online"] and workload["paged_kv"]:
        candidates.append("vLLM-like")
    if workload["programs"] or workload["shared_branches"]:
        candidates.append("SGLang-like")
    if workload["nvidia_optimized"] and workload["low_latency"]:
        candidates.append("TensorRT-LLM-like")
    if workload["multi_backend"]:
        candidates.append("Triton-control-plane")
    return candidates or ["benchmark-before-choice"]


choice = choose_runtime({
    "general_online": True,
    "paged_kv": True,
    "programs": False,
    "shared_branches": False,
    "nvidia_optimized": False,
    "low_latency": False,
    "multi_backend": False,
})
print(choice)
assert choice == ["vLLM-like"]
~~~

这个选择器不是生产路由器，只把“选择依据”显式化。真正选型必须用同一 workload 做 A/B 压测，并保留一个可回退的 runtime。

## 9.10 模型并行与 CPU Offloading：把容量问题变成通信问题

### Tensor Parallel

Tensor Parallel 把单层矩阵或 attention heads 分到多个 GPU，适合模型权重和单层计算无法放入一张卡的场景。代价是每层可能出现 all-reduce、all-gather 或 reduce-scatter；如果通信跨越慢的节点网络，decode 的每 token 延迟会被放大。

### Pipeline Parallel

Pipeline Parallel 按层把模型切成多个 stage。训练中的 microbatch 可以隐藏一部分 pipeline bubble，在线 decode 的 batch 和序列长度更不规则，bubble、stage 不均衡和 activation 传输需要单独测量。PP 不能简单当作“GPU 数越多越快”。

### Data Parallel 与 Expert Parallel

Data Parallel 复制模型副本，让请求分到多个 replica，适合扩展吞吐，但每个副本有自己的 KV Cache 和 prefix locality。Expert Parallel 把 MoE experts 分散到不同 GPU，受 all-to-all 和 expert 热点影响。一个 serving router 视角的 worker 通常是完整 TP/PP/EP group，而不是单张 GPU。

### 拓扑是性能变量

NVLink、NVSwitch、PCIe 和跨节点网络的带宽、延迟、拥塞不同。TP 高频 collective 通常尽量留在高速互联域；DP 更适合做请求级分流；PP 需要关注 activation 路径；PD 分离需要关注 KV 传输路径。并行策略必须与模型结构、请求长度、KV 容量和故障域共同设计。

### CPU offloading

把权重、KV 或中间状态放到 CPU 可以降低 GPU 显存压力，但 CPU-GPU 传输远慢于 HBM。它适合低并发、离线或容量优先场景，不适合作为默认的低延迟方案。offloading 的真正成本应包括传输时间、同步等待、CPU 内存占用和带宽争用，而不是只比较“模型能否启动”。

### 粗略的并行规划

~~~math
T_{\mathrm{step}}
\approx
T_{\mathrm{compute}}
+T_{\mathrm{collective}}
+T_{\mathrm{pipeline\ bubble}}
+T_{\mathrm{memory\ movement}}.
~~~

增加 GPU 可能降低第一项，却增加后三项。压测时要按 TP/PP 配置记录 per-rank memory、collective time、stage idle time、TPOT 和错误率。

## 9.11 Prefill、Decode 与 PD 分离：先证明干扰，再增加系统复杂度

### 两种阶段的资源画像

prefill 一次处理很多输入 token，矩阵形状更适合并行，通常更偏计算和大批量；decode 每轮处理每个活跃请求的一个或少量 token，反复读取权重和 KV，更容易受带宽和调度影响。它们共享 GPU 时，长 prefill 可能让正在 streaming 的请求等待，decode-first 又可能让长 prompt 的 TTFT 恶化。

### Chunked prefill 解决执行粒度

把一个长 prompt 分成多个 chunk，让 scheduler 在 chunk 之间插入 decode，可以降低长 prefill 对 TPOT 的阻塞。chunk 边界必须保持 position、causal mask、KV block table 和 token 计数连续。chunk 太小会增加调度和 kernel launch 开销，太大又重新造成阻塞。

### PD disaggregation 解决运行位置

PD 分离把 prefill worker 与 decode worker 放到不同资源池，允许按输入输出比例独立扩缩容，并减少相互干扰。它新增了一个关键状态转移：prefill 产生的 KV 要交给 decode worker。传输的元数据至少包含模型版本、dtype、layout、层和 head 分片、位置、block 映射和 session 信息。

收益可粗略写成：

~~~math
\Delta T_{\mathrm{decode}}
\approx
T_{\mathrm{interference,before}}
-T_{\mathrm{interference,after}}
-T_{\mathrm{transfer\ overhead}}.
~~~

如果 KV 传输慢，或请求很短、没有明显 P/D 干扰，最后一项可能吃掉全部收益。PD 不是默认终态，应先用 unified engine、decode-first、chunked prefill、prefix cache 和同机原型证明问题存在。

### 失败和取消比正常路径更重要

prefill 已完成、transfer 只传了一半、客户端此时取消，谁释放 source 和 target 的 KV？decode worker 版本不匹配，是否回退重算？transfer 网络拥塞，是否暂停新 transfer？这些问题决定 PD 是可靠架构还是新的故障放大器。

### PD 取舍记录

~~~python
import math


def pd_decision(prefill_ms, decode_jitter_ms, transfer_ms, complexity):
    values = (prefill_ms, decode_jitter_ms, transfer_ms, complexity)
    if (not all(isinstance(value, (int, float)) and math.isfinite(value)
                for value in values)
            or not all(value >= 0 for value in values)):
        raise ValueError("PD inputs must be finite and non-negative")
    benefit = prefill_ms + decode_jitter_ms
    cost = transfer_ms + complexity
    if benefit > cost * 1.2:
        return "candidate", benefit, cost
    return "keep-unified", benefit, cost


decision, benefit, cost = pd_decision(
    prefill_ms=80,
    decode_jitter_ms=30,
    transfer_ms=20,
    complexity=40,
)
print(decision, benefit, cost)
assert decision == "candidate"
~~~

这只是决策账本，不是通用阈值。真实系统应把输入输出分布、transfer p99、取消率、容量成本和运维复杂度放进同一组实验。

## 9.12 多级 KV 与跨节点网络：移动还是重算

### KV 不只有“命中”和“未命中”

一个 KV block 可能位于：

~~~text
active GPU
cached GPU
CPU memory
remote worker
SSD 或对象存储
尚未保存，需要 recompute
~~~

活跃 decode 的 block 应优先留在 GPU。cached-free block 可以根据成本被淘汰；CPU 或 remote 命中只有在传输成本低于重算时才有意义。SSD 读取延迟可能远高于一次短 prompt prefill，不能因为“命中了缓存”就认为更快。

可以对两条路径做简单比较：

~~~math
C_{\mathrm{fetch}}
=T_{\mathrm{network}}
+T_{\mathrm{deserialize}}
+T_{\mathrm{copy}},
\qquad
C_{\mathrm{recompute}}
=T_{\mathrm{prefill}}.
~~~

选择 fetch 还是 recompute 要按 p50 和 p99、网络拥塞、GPU 当前负载、租户隔离和数据版本判断。

### 跨节点通信的四种形态

TP 是每层或每 token 的高频 collective，通常最怕跨慢网络；PP 传递层间 activation；PD 传递长 prompt 的 KV；remote cache 传递可复用状态。它们的消息大小、频率和关键路径不同，不能只用一个“网络带宽”指标概括。

大对象 KV transfer 还会与控制面争抢网络。数据面应有独立带宽、队列和 backpressure；控制面至少要能继续传递 cancel、health、drain 和失败信号。

### 跨节点路由

路由器除了看 worker 负载，还要看：

~~~text
拓扑距离
TP / PP group 完整性
prefix cache locality
free KV blocks
pending transfer
租户隔离
预计 TTFT / TPOT
~~~

迁移运行中的 KV 很复杂，因为还要保持 position、dtype、layout、parallel group 和 sampling state 一致。实际系统通常优先 sticky routing 和 locality，而不是频繁迁移 active request。

## 9.13 模型路由与自动扩缩容：容量控制面的两面

### 模型路由先过滤，再排序

多模型平台不能先按价格排序，再发现候选模型没有权限或不支持工具调用。合理顺序是：

~~~text
权限与合规区域过滤
 -> 模型能力与协议过滤
 -> 上下文和输入输出预算过滤
 -> 实时健康与容量过滤
 -> 延迟 SLO 与成本过滤
 -> 质量、安全和 fallback 排序
~~~

每次选择都应记录 request intent、候选模型、被过滤原因、最终模型、版本、route reason、fallback 和配置版本。稳定 hash 可以把同一用户或租户固定到 canary bucket，减少版本抖动。

### Fallback 的边界

模型超时可以切换小模型，但已开始 streaming 的请求不能无条件重放；工具调用已经产生副作用时，重试还需要幂等键；安全拒答不能被“降级到一个更愿意回答的模型”绕过。fallback 必须有总时间、总成本、尝试次数和风险策略。

### 扩缩容不能只看 GPU 利用率

GPU 利用率高不一定表示需要扩容，可能是长 prefill；GPU 利用率低也不一定安全，可能是 KV 快满、队列增长或 decode 带宽瓶颈。扩容信号至少包括：

~~~text
queue wait 与 pending tokens
TTFT / TPOT P95/P99
active sequences
free KV blocks 与 KV pressure
input / output tokens per second
OOM、preemption、timeout
冷启动时间与 warm pool
~~~

扩容决策应快扩慢缩，缩容先 drain，不接收新请求并等待 streaming 完成。warm pool 通过提前拉镜像、权重和 kernel warmup 缩短冷启动，但会产生闲置成本。

### 一个多指标副本估算

~~~python
import math


def replicas_needed(current, stable_capacity, reserve=0.2):
    if (not all(isinstance(value, (int, float)) and math.isfinite(value)
                for value in (current, stable_capacity, reserve))
            or current < 0 or stable_capacity <= 0
            or not 0 <= reserve < 1):
        raise ValueError("stable_capacity must be positive")
    safe_capacity = stable_capacity * (1 - reserve)
    return max(1, math.ceil(current / safe_capacity))


needs = {
    "request": replicas_needed(120, 100),
    "prefill_tokens": replicas_needed(9000, 8000),
    "decode_tokens": replicas_needed(4800, 5000),
    "kv_active": replicas_needed(72, 80),
}
planned = max(needs.values())
print(needs, planned)
assert planned == 2
~~~

stable_capacity 必须来自固定 workload 和 SLO 下的压测，而不是 GPU 峰值。副本数还要加入 N+1、滚动发布和故障域余量。

## 9.14 保护策略：限流、接收控制、熔断、重试与降级

### 保护发生在昂贵计算之前

请求 token rate limit 比单纯 QPS 更贴近 LLM 成本；并发限制保护连接、running slot 和 KV；容量检查在 tokenization 或 prefill 前判断是否还有时间、KV 和模型资源。拒绝一个无法满足 SLO 的请求，通常比接收后在 GPU 上排队到超时更诚实。

保护信号包括：

~~~text
租户、用户、API key 和模型配额
输入 token 与最大输出 token
队列长度与等待时间
free KV blocks 与水位
endpoint 健康与错误率
剩余 deadline
优先级与业务重要性
~~~

### Circuit breaker 与重试

熔断器可以有 CLOSED、OPEN、HALF_OPEN 三种状态。OPEN 时快速失败或切换可接受的 fallback，HALF_OPEN 用少量探测请求确认恢复。重试只适用于尚未产生不可逆副作用、且错误被定义为临时的场景。

多层 gateway、router、client 同时重试会形成 retry storm。必须设置总 retry budget，并让每个 attempt 携带 request id、idempotency key 和执行阶段。已经发送部分输出的 streaming 请求，不能当成从未执行过的请求盲目重放。

### Deadline 要分配而不是只设置一个 timeout

总截止时间可以拆为：

~~~math
D_{\mathrm{total}}
=D_{\mathrm{queue}}
+D_{\mathrm{route}}
+D_{\mathrm{prefill}}
+D_{\mathrm{decode}}
+D_{\mathrm{stream}}
+D_{\mathrm{fallback}}.
~~~

若队列已经消耗大部分 deadline，继续进入 prefill 可能只会制造一个必然超时的昂贵请求。每一阶段都要根据剩余预算决定继续、拒绝或降级。

### 降级必须尊重风险

可接受的降级可能包括缩短上下文、减少输出、关闭非必要工具、切换小模型、读取确定性缓存或转异步；高风险任务不能因为主模型过载就绕过安全策略。降级结果要对用户可见，并记录质量、成本和业务影响。

## 9.15 API、流式协议与异步边界

### OpenAI-compatible 不是复制所有行为

兼容 API 应先声明支持的字段和语义。请求层至少要校验 model、messages、role、content、max tokens、sampling 参数和 stream 标志；错误要区分用户输入错误、权限错误、限流、上下文超限、服务故障和取消。usage 统计要说明 prompt、completion 和 total token 的来源。

SSE 流通常以 data frame 发送增量事件，结束时发送明确的终止事件。HTTP 响应开始后，不能再用新的 status code 表达后续错误；引擎异常要通过 stream error event 和 finish reason 传递。客户端断开必须通知 engine，而不是只让 HTTP handler 返回。

### 异步队列的边界

高并发服务可以把 API、tokenizer、engine core、output processor 和 client stream 放进不同队列，但 GPU 调度状态必须由 engine core 单独拥有。慢客户端只能积压自己的 stream queue，不能阻塞所有请求；有界队列要有 backpressure，取消消息要幂等。

~~~text
API admission -> tokenizer queue -> engine input queue
engine core -> engine output queue -> per-client stream queue
client cancel -> cancel queue -> engine cleanup
~~~

队列不是越多越好。每一个异步边界都增加排队、顺序和关闭语义；如果没有队列长度、等待时间和 drain 事件，异步化只会把故障藏起来。

### 流式输出的停止串问题

一个字符串 stop sequence 可能跨越两个 token。增量 detokenization 需要保留尾部缓冲，确认当前片段不可能组成 stop 后再发送；否则用户可能先看到本应被截断的角色标记或工具控制字段。streaming 还要记录首 chunk、最后 chunk、客户端取消、服务端 abort 和已经发送的 token 数。

## 9.16 发布治理、观测与回滚

### 发布包必须能重现一次输出

一个模型权重文件不足以重现线上行为。发布包至少绑定：

~~~text
权重与 checksum
模型 config 与上下文限制
tokenizer 与 chat template
adapter、量化包与校准数据版本
runtime 镜像与 kernel 配置
sampling / stop / safety policy
路由、配额和降级配置
离线质量与安全报告
旧版本和回滚目标
~~~

artifact manifest 应使用不可变 URI 或 digest。模型、tokenizer、模板或 runtime 任意一个变化，都可能导致格式、长度、KV layout 或质量变化。

### 健康状态要分层

startup 表示进程仍在加载镜像、权重、tokenizer、parallel group 或 warmup；liveness 表示进程和事件循环仍然活着；readiness 表示已经能够接收业务流量。把 startup 误当 readiness，会让慢加载实例过早接流量；把 liveness 和 readiness 混为一谈，又可能让加载中的实例被反复杀死。

滚动发布先让新实例 ready，再把流量转入；旧实例停止接新请求并 drain 已有 streaming。canary 要按稳定用户或租户分桶，同时比较质量、TTFT、TPOT、错误、OOM、KV pressure、成本和业务 guardrail。异常时 router 应能把流量切回旧版本，不能依赖重新部署来“回滚”。

### Trace 与 metrics 的关系

metrics 适合看总体趋势，trace 适合解释单个慢请求。一次请求的 trace 至少要关联：

~~~text
auth / route / queue
tokenize / cache lookup
prefill / first decode
每阶段 decode 或聚合 decode
stream flush / client cancel
KV blocks / prefix hit
model version / runtime version
cost / finish reason
~~~

OpenTelemetry 这类通用观测规范可以帮助跨 gateway、engine 和工具服务传递 trace context，但具体指标口径仍要由平台定义。

## 9.17 Benchmark、性能事故与有序诊断

### Benchmark 要先固定实验指纹

一次可复现的 serving benchmark 应保存：

~~~text
模型、权重、tokenizer、模板
硬件、驱动、runtime 和镜像 digest
精度、并行和 scheduler 配置
输入 / 输出 token 分布
到达模式、并发和流式设置
warm-up、随机种子和版本 commit
~~~

每个请求保存 prompt 长度、输出长度、TTFT、TPOT、E2E、finish reason、错误、KV 峰值、prefix hit 和是否 preempt。candidate 吞吐上升时，要同时检查长尾、质量、cleanup 和成本。

### 常见回归的证据路径

TTFT 上升，先拆 queue、tokenize、prefix cache、prefill 和 first flush；TPOT 上升，检查 active sequences、KV bandwidth、decode batch、sampling、stream backpressure 和 speculative acceptance；OOM 或 preemption 上升，检查上下文分布、KV block 水位、缓存驱逐、max batch tokens 和取消清理；质量下降，核对 tokenizer、模板、EOS、量化、sampling 和模型 artifact。

不要把所有延迟问题归因于模型，也不要把所有质量问题归因于 runtime。版本 diff 要包含权重、prompt、模板、量化、runtime、route、cache、safety 和 sampling。

### 事故诊断的顺序

~~~text
确认影响范围：模型、版本、租户、区域、长度和流式比例
固定一条慢请求或失败请求并回放
拆分 queue / prefill / decode / stream 阶段
检查 KV pressure、cache hit、GPU、网络和 worker 健康
对照最近的 artifact、配置和流量变化
采取限流、降级、摘除、扩容或回滚
验证恢复并保存 postmortem 证据
~~~

### 一个分位数与回归摘要

~~~python
import math


def percentile(values, q):
    if (not values or not math.isfinite(q) or not 0 <= q <= 1
            or any(not isinstance(value, (int, float))
                   or not math.isfinite(value) for value in values)):
        raise ValueError("invalid percentile input")
    ordered = sorted(values)
    index = min(len(ordered) - 1, int(q * len(ordered)))
    return ordered[index]


baseline = [100, 110, 120, 130, 800]
candidate = [105, 115, 125, 140, 900]
report = {
    "baseline_p50": percentile(baseline, 0.5),
    "candidate_p50": percentile(candidate, 0.5),
    "baseline_p99": percentile(baseline, 0.99),
    "candidate_p99": percentile(candidate, 0.99),
}
print(report)
assert report["candidate_p99"] > report["baseline_p99"]
~~~

这是 nearest-rank 风格的教学统计，不是所有生产监控系统的精确分位数实现。它的重点是提醒读者：平均值不变时，尾部仍可能明显恶化。

## 9.18 Agent Serving 与结构化生成

### Agent 请求比普通对话多了哪些状态

agent serving 不只是多一次 tool call。一个多轮任务会保存 session history、工具 schema、权限决定、tool observation、下一轮 prompt、KV 或 prefix 引用、stream offset 和任务级预算。工具等待时，GPU 不应继续占用一个 decode slot；工具返回后，runtime 又要恢复正确的消息角色和上下文位置。

完整轨迹可以表示为：

~~~text
user / system context
 -> assistant tool call
 -> permission decision
 -> tool observation
 -> next generation
 -> validation / retry
 -> final answer or task failure
~~~

训练或线上处理时，tool observation 不能自动获得比 system policy 更高的信任级别。外部网页、数据库或工具返回可能包含 prompt injection，工具 schema、权限和幂等性必须在模型输出之外由执行器验证。

### 结构化生成是执行协议的一部分

如果当前 grammar state 为 s，合法 token 集合为 V(s)，约束解码可以把非法 token 的 logit 设为负无穷：

~~~math
z'_i=
\begin{cases}
z_i,&i\in V(s),\\
-\infty,&i\notin V(s).
\end{cases}
~~~

生成后状态转移到 s'。JSON schema、regex、EBNF 和 tool call 参数都可以采用这种方式。它提高结构合法率，却不保证字段语义正确、数字真实或工具有权限。结构 parser、业务 validator、权限检查和工具执行必须分层。

### Agent 的缓存与路由

同一 session 如果不断被路由到不同 worker，prefix cache locality 会下降；固定到同一 worker 又可能造成热点。路由要在 session affinity、负载、租户隔离和故障恢复之间取舍。工具结果中包含敏感数据时，缓存 key、TTL、权限域和删除传播不能沿用公共 prompt 的默认策略。

Agent 还需要任务级指标：

~~~text
任务成功率
模型调用轮数
工具调用成功率
工具等待时间
无效或重复调用
总输入 / 输出 token
每成功任务成本
人工接管率
安全拦截与越权尝试
~~~

只看单次模型 TTFT 或 TPOT，无法判断 agent 是否真的变好。

## 本章回顾

推理优化的主线不是堆叠名词，而是围绕四个守恒关系展开：

1. 请求生命周期必须从接收走到清理，正常完成、取消、超时和失败都不能泄漏 KV 或 stream 状态。
2. 计算量要按 input token、output token、阶段和上下文长度描述，QPS 只能作为流量入口。
3. KV Cache 是 decode 速度和并发容量之间的核心账本；PagedAttention、vAttention、prefix cache 和多级缓存是不同的内存组织路线。
4. 性能优化必须与模型质量、协议正确性、租户安全、发布回滚和单位成功任务成本一起测量。

当系统出现回归时，应先固定请求契约和实验指纹，再拆 queue、prefill、decode、KV、stream 和网络路径，最后对照 artifact、配置和流量变化采取动作。一个真正可用的 serving 系统，不是某个 benchmark 上的峰值，而是能在真实负载下解释自己的延迟、容量、质量、成本和失败恢复。
